## Title
Webhook shop-domain identity spoofing due to HMAC covering only the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` therefore only proves that the *body* bytes were produced by an entity holding `Context.api_secret_key`; it proves nothing about which shop, topic, or webhook the request is claiming to be. `Webhooks::Registry.process` nonetheless treats a passing HMAC check as authorization to dispatch `request.shop` (and `request.topic`) to the app's handler as trusted, verified values.

### Finding Description
The signable string used for HMAC verification is defined as: [1](#0-0) 

Only `@raw_body` is bound to the signature. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead come directly from request headers that are never mixed into `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's shared secret: [3](#0-2) 

`Registry.process` gates on this HMAC check and then forwards the *unauthenticated* `request.shop` and `request.topic` values to the handler as if they were verified: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that has the app installed, any merchant using the app receives real, validly-signed webhooks for their own shop. Nothing prevents that merchant (an "unprivileged" party from the perspective of any other tenant) from re-POSTing that exact `raw_body`/HMAC pair to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. The signature still validates — it never covered those fields — so `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different, victim shop, with attacker-chosen body content that was actually generated under the attacker's own store.

This breaks the binding the library implicitly promises to consumers: *"HMAC-validated request ⇒ `request.shop`/`request.topic` are authentic."* In reality the equality that actually holds is only `HMAC(secret, raw_body) == received_hmac`; `request.shop == origin_shop` is never checked.

### Impact Explanation
This allows cross-tenant request forgery: an attacker who legitimately controls one shop where the target app is installed can cause the app to process attacker-controlled webhook payloads under the identity of a different shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop settings, write records keyed by shop, or make Admin API calls on behalf of that shop), this can result in cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Medium-to-High: exploitation requires only becoming/using an installed merchant of the target app (a normal, unprivileged capability, not a leaked secret) and forging HTTP headers on a replayed webhook body — no knowledge of `api_secret_key` is needed since headers are outside the signed payload.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind these header values to the signature validation, and have `Registry.process` reject requests where the claimed shop/topic cannot be tied to the verified signature.

### Proof of Concept
1. Attacker installs `TargetApp` on their own shop `attacker.myshopify.com` and configures/triggers a webhook (e.g., `orders/create`) whose body they fully control (order description fields, etc.).
2. Shopify delivers the webhook to the app with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using `TargetApp`'s shared secret, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this raw body + HMAC and re-sends it to the same webhook endpoint, replacing only the header `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `raw_body` against the same shared secret.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the app to treat attacker data as originating from the victim shop.
