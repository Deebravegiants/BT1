### Title
Webhook shop-domain header is not covered by HMAC verification, allowing shop-identity spoofing on replayed webhooks - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop` (tenant) identifier is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this header value directly and passes it to the app's webhook handler as the tenant identity, without it ever participating in the HMAC computation. An attacker who can obtain one validly-signed webhook body/HMAC pair (trivially available by installing the app on their own shop) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the gem to authenticate the payload as belonging to a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the header, with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` (and `validate_signature`) computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body — it never incorporates `shop`: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC and then unconditionally forwards `request.shop` to the app's handler as the authenticated tenant for the event: [4](#0-3) 

The equality the gem implicitly claims to hold is:
`shop-domain header == shop that produced/authorized raw_body`

but the code only proves:
`HMAC(raw_body, api_secret_key) == received_hmac`

Since the signature never spans the `shop` header, these two facts are independent. Any body+HMAC pair that is valid for shop A remains HMAC-valid verbatim when re-submitted with a `shop-domain` header claiming to be shop B — `HmacValidator.validate` will return `true` in both cases because it recomputes the digest over `@raw_body` only.

### Impact Explanation
This breaks the tenant/identity binding the gem is expected to enforce for webhook processing: `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is fully attacker-controlled while the HMAC only vouches for the body bytes. Any app built on this gem that branches business logic on `WebhookMetadata#shop` (e.g., looking up the shop's session/access token, updating per-shop billing/subscription state, deleting/creating per-shop data on `shop/redact` or `app/uninstalled`, or writing order/customer data keyed by shop) can be made to attribute another shop's legitimate webhook content to an attacker-chosen shop, or vice versa — a cross-tenant identity confusion at the point the gem is supposed to establish trusted shop context from a verified webhook.

### Likelihood Explanation
Exploitation requires only unprivileged actions: an attacker installs the target app on a shop they control (a free/dev shop qualifies), captures one legitimately Shopify-signed webhook (body + `hmac-sha256` header) for any topic the app subscribes to, and replays that exact body and HMAC header to the app's public webhook endpoint while swapping the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to the victim shop's domain. No access token, `client_secret`, or privileged credential is needed — the attacker never needs the app's secret because they reuse a signature Shopify itself already produced.

### Recommendation
Bind the shop identifier into the verified signable data, e.g., include the `shop-domain` header (and ideally `webhook-id`/`topic`) as part of the HMAC computation, or independently verify that the shop encoded in the payload/topic matches the header before trusting it. At minimum, `Utils::VerifiableQuery`/`HmacValidator` should not be considered to authenticate any header-derived field that isn't included in `to_signable_string`; `WebhookMetadata#shop` should only be trusted once the header is included in what's HMAC-verified.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a real webhook, capturing:
   - `raw_body` (e.g., `{"id":123,...}`)
   - `x-shopify-hmac-sha256: <valid signature for raw_body>`
   - `x-shopify-topic: orders/create`
2. Attacker POSTs to the victim app's webhook endpoint with the same `raw_body` and the same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` — identical to the captured value — so validation passes.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own shop's data>, ...)`, causing the app to process/attribute the payload under the victim shop's identity. [4](#0-3)
