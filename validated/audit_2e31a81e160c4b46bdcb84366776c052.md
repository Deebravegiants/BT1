### Title
Webhook `shop` (and other header metadata) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop-domain` header — which is the tenant identifier propagated into the webhook handler as `WebhookMetadata#shop` — is never part of the signed data. An attacker who legitimately installs the app on their own store (an unprivileged action) will receive real webhooks signed by Shopify with the app's shared `client_secret`. Because that signature covers only the body, the attacker can replay the exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature check still passes.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header, and `Request#to_signable_string` is simply `@raw_body`: [1](#0-0) [2](#0-1) 

`Registry.process` validates the request purely through this body-only signature, then immediately trusts `request.shop` (parsed from the unauthenticated header) as the tenant identity passed into the handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it to the provided HMAC — it has no dependency on `shop`, `topic`, or `webhook-id`: [4](#0-3) 

This breaks the intended binding: `hmac == HMAC(secret, body)` is verified, but the equality that actually matters for tenant isolation — `shop_header == shop_that_the_signed_body_originated_from` — is never checked. Since Shopify apps use a single `client_secret` per app (shared across every merchant/shop that installs it), any shop that installs the app can legitimately obtain valid `(body, hmac)` pairs from real Shopify webhook deliveries. An attacker who installs the target app on their own store can capture such a pair and then replay it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain.

### Impact Explanation
The webhook handler receives `WebhookMetadata` whose `shop` field is attacker-controlled while the signature only proves the body originated from *some* real Shopify install of the app, not that it belongs to the claimed shop. Any host application (following this gem's documented API) that uses `WebhookMetadata#shop` to key into tenant data (e.g., "update shop X's local record based on `customers/redact`/`orders/create` payload") can be tricked into writing or acting on attacker-supplied data under a victim shop's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Requires only that the attacker installs the app on their own shop (a normal unprivileged action available to anyone) and can send an HTTP POST to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header alongside the replayed, still-valid `hmac-sha256` header and body. No access to `client_secret`, access tokens, or the victim's credentials is required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the signed material verified against the HMAC, or otherwise independently confirm that the `shop-domain` header corresponds to a shop session/webhook registration that is expected to produce this specific `webhook-id`. At minimum, `to_signable_string` should not treat header-derived tenant identifiers as separate from the authenticated payload when they are consumed as authoritative tenant context downstream.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and the legitimate `X-Shopify-Hmac-Sha256: H` header (`H = HMAC-SHA256(client_secret, B)`), where `client_secret` is shared across all installs of the app.
2. Attacker crafts a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because HMAC is computed only over the body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` set as desired.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to process attacker-controlled data attributed to the victim tenant.
