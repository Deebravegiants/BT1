### Title
Webhook shop-tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using the shop identity taken from an HTTP header that is never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook-id`, `api-version`) are read from separate HTTP headers that are not part of that signable string: [2](#0-1) 

`Registry.process` verifies only that the HMAC over the body is valid, then builds the metadata passed to the app's handler directly from the unauthenticated `request.shop` header: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, i.e. it only ever verifies the body bytes against the app's shared `api_secret_key`: [4](#0-3) 

Because a single app-wide `api_secret_key`/`old_api_secret_key` is used to compute and verify the HMAC for every merchant/shop that installs the app, and because the `shop-domain` header is not bound into that signature, the identity equality the gem is supposed to enforce — `hmac_verified_bytes == bytes_that_determine_tenant` — does not hold. The bytes that are cryptographically verified are the JSON body only; the bytes that determine which merchant's data the handler acts on (the `shop-domain` header) are parsed from unauthenticated request headers and never checked for consistency with the signed payload.

An attacker who legitimately controls one shop that has the target app installed (e.g., their own free/dev store) will receive real, correctly-HMAC'd webhook deliveries from Shopify for that shop. Because the signature covers only the body and is computed with the same app secret regardless of shop, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` (the body/HMAC pair is unmodified and correctly signed), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem provides application developers no assurance that the `shop` value handed to their webhook handler actually corresponds to the shop that produced the signed payload. Any app that uses `data.shop` from the handler to look up/mutate per-merchant state (e.g. update billing status, deactivate/reinstall flags, cache configuration, trigger fulfillment actions, or write order/product data keyed by shop) can be made to apply attacker-controlled webhook content to a victim shop's tenant record, i.e., cross-tenant access/write. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) attacker has (or creates) a shop that installs the target app and can capture at least one legitimate, correctly-signed webhook body/HMAC pair for a topic the app is subscribed to (trivially satisfied for any topic triggered by normal store activity, e.g. `app/uninstalled`, `orders/create` equivalents on a free dev store), and (2) the ability to POST directly to the app's public webhook endpoint with custom headers, which any unprivileged internet user can do since webhook endpoints are unauthenticated HTTP endpoints by design. No access token, `api_secret_key`, or privileged account is required — likelihood is high for any app relying on the `shop` field from `WebhookMetadata` for tenant scoping.

### Recommendation
Bind the tenant/topic identity into the verified bytes instead of trusting separate headers:
- Compute/verify the HMAC over a canonical string that includes `shop`, `topic`, and `webhook-id` in addition to the raw body (or require and validate that the header-declared shop matches a shop the app has an active session/installation record for before dispatch).
- At minimum, document and enforce in `Registry.process` that `request.shop` must be cross-checked against the app's own session/installation store (looked up independently of the request) before invoking `handler.handle`, rather than trusting the raw header value as the tenant identity for the webhook payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker-shop.myshopify.com`; trigger a webhook (e.g. any subscribed topic) and capture the raw POST body `B` and its `x-shopify-hmac-sha256` header value `H` as delivered by Shopify (correctly signed with the app's `api_secret_key`, since the same secret signs every shop's webhooks for this app).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only exposes/signs `B`, so `Utils::HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is now `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though the payload `B` never originated from that shop — demonstrating the handler receives attacker-controlled shop/body correlation despite passing HMAC validation.
