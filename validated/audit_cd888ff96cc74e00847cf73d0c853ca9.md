### Title
Shared Emporium contract lets an unprivileged attacker drain another user's parked lending-protocol collateral via unrestricted CASE 2 external calls - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable` is a single shared, persistent contract (not a per-user or per-transaction ephemeral account) that acts as `msg.sender`/`address(this)` for every user's CASE 2 "stateless" operations. Because `onlyAllowedRecipient` only restricts who can *call* `runAction` (i.e. the trusted Hinkal contract) and places no restriction on `op.endpoint`/`op.callData` inside a CASE 2 op, an attacker can submit a `runAction` whose op is `pool.withdraw(token, type(uint256).max, attacker)` against a lending pool where a previous victim's op left an aToken balance credited to Emporium (`address(this)`), stealing it directly to `attacker` while completely bypassing the `handleOut`/`balanceChange` accounting.

### Finding Description
Equality claimed broken: `underlying_withdrawn_to(attacker) == 0` (attacker's own UTXO/deposit accounting should authorize 0 withdrawal) but ends up equal to the victim's full deposited collateral.

Trace:
- `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160) executes `stack.ops` decoded from attacker-controlled `circomData.externalActionData.externalActionMetadata`.
- For CASE 2 ("Stateless Interaction", `!op.invokeWallet`), the only guard is a selector blacklist for `callHinkalWallet`/`doSendToRelay` (lines 104-113); otherwise `op.endpoint.call{value: op.value}(op.callData)` is fully attacker-controlled, executed with `msg.sender == address(Emporium)`.
- A prior, unrelated victim transaction can include a CASE 2 op such as `pool.supply(token, amount, address(this), 0)`. Since `address(this)` is Emporium's own address, and Emporium is a **singleton** used across all users' transactions (guarded only by `onlyAllowedRecipient`, which checks the Hinkal router's identity, not per-user isolation), the resulting aToken balance is credited to Emporium and persists on-chain after the victim's transaction completes, because nothing forces the victim (or the protocol) to include the aToken address in `circomData.erc20TokenAddresses`, nor forces balances to zero at the end of `runAction`.
- Post-hoc accounting in `runAction` only tracks tokens explicitly listed by the *current* caller's `circomData.erc20TokenAddresses` (lines 122-151, `handleOut` at 162-184). Since Aave's `withdraw(asset, amount, to)` transfers the underlying directly to the caller-specified `to` and never touches Emporium's own token balance, `balanceChange` for the underlying (even if the attacker chose to list it) stays `0`, so `handleOut` does nothing (`balanceChange <= 0` branch, line 168-170) — no UTXO is minted, no debit is registered against the attacker's proof/UTXOs, and none of `insertNullifiers`, `verifyProof`, `dimensionsCheck`, or the circuit's `inTotal + amountChanges === outTotal` constraint ever see this transfer, because it happens entirely outside the token list the attacker declares for their own transaction.
- Attacker's exact call: submit a `runAction` (via the trusted Hinkal router, using their own legitimately-owned UTXOs/proof for an unrelated 0-value or small operation) whose `EmporiumStack.ops` contains a single CASE 2 op: `endpoint = aavePool`, `callData = abi.encodeCall(IPool.withdraw, (token, type(uint256).max, attacker))`. Emporium's aToken balance (the victim's collateral) is burned and the underlying is sent to `attacker`.

None of the existing guards prevent this: `onlyAllowedRecipient` (contracts/external-actions/ExternalActionBaseUpgradeable.sol:39-46) only checks `msg.sender` of `runAction`, not `op.endpoint`; `verifyWallet` only validates EIP-712 signatures for CASE 1 (`stack.signerAddress != 0`) and is a no-op for CASE 2 beyond message-replay protection; the circuit and `performHinkalChecks` constrain only the attacker's own declared `erc20TokenAddresses`/`amountChanges`, which never include the diverted token since it never touches Emporium's tracked balance.

### Impact Explanation
Direct theft of another user's (or the protocol's) shielded/parked collateral held by the shared `Emporium` contract, with the stolen funds routed straight to an attacker-chosen address, entirely outside Hinkal's nullifier/UTXO accounting. This matches the **Critical** category: direct theft of in-flight/parked user funds via an action (an external call moving assets) that was never authorized or counted by any prover or wallet owner. It is repeatable against any token/lending-position balance left in Emporium by any user's CASE 2 op, and costs the attacker only their own transaction/proof-generation fee.

### Likelihood Explanation
Requires a precondition: some victim transaction (or an intended "supply-then-later-withdraw" yield/strategy flow through Emporium) must leave a non-zero balance (e.g., aTokens) at Emporium's own address that is not included in that transaction's `circomData.erc20TokenAddresses`. Given that CASE 2 is explicitly designed to allow arbitrary external protocol interactions (documented use case: lending/money-market integrations), and nothing in the contract enforces "no residual balance" or "declare every token touched," this window is realistically reachable whenever any legitimate multi-step lending strategy (supply now, withdraw later in a separate tx) is used. The attacker needs no special role — any address that can call the standard deposit/`runAction` flow through the Hinkal router can craft this op. This is a design-level access-control gap in `EmporiumUpgradeable`, not a rare edge case.

### Recommendation
- Do not allow `EmporiumUpgradeable` to hold cross-transaction custodial balances/positions on behalf of individual users at a shared address; require per-user isolation (e.g., deploy per-user proxy/sub-accounts, or use `onBehalfOf`/`to` values pinned to a user-specific address rather than `address(this)`).
- Alternatively, restrict CASE 2 `op.endpoint`/function selectors to an owner-curated allowlist of protocol calls with fixed, safe recipient semantics (e.g., disallow arbitrary `to` parameters that don't resolve back to `address(this)` before `handleOut` processes it), and require `runAction` to assert Emporium's balance for *every* token/asset touched (including derivative tokens like aTokens) returns to a pre-declared, fully-swept state at the end of each transaction.
- Require `circomData.erc20TokenAddresses` completeness to be enforced by allowlisting exactly the assets each endpoint call can affect, rather than trusting the caller's own declared list.

### Proof of Concept
Foundry fork test plan (Aave v3 mainnet fork):
1. Deploy/attach `EmporiumUpgradeable` with a mocked or real Aave `Pool` and `allowedRecipients` including a mock Hinkal router.
2. Victim tx: call `runAction` with `deltaAmountChanges = [-amount]` for `token`, `stack.ops = [{endpoint: pool, invokeWallet: false, callData: abi.encodeCall(IPool.supply, (token, amount, address(emporium), 0))}]`, `circomData.erc20TokenAddresses = [token]` (aToken address intentionally omitted). Assert Aave's aToken balance of `address(emporium)` increases by `amount`, and Emporium's `token` balance nets to 0 (no revert from `BalanceChangeShouldBePositive`).
3. Attacker tx: call `runAction` with attacker's own unrelated proof/UTXOs, `deltaAmountChanges` all `>= 0` (or zero), `stack.ops = [{endpoint: pool, invokeWallet: false, callData: abi.encodeCall(IPool.withdraw, (token, type(uint256).max, attacker))}]`.
4. Assertions:
   - Before: `IERC20(token).balanceOf(attacker) == 0`, `aToken.balanceOf(address(emporium)) == amount`.
   - After: `IERC20(token).balanceOf(attacker) == amount` (victim's full principal), `aToken.balanceOf(address(emporium)) == 0`.
   - Confirm no `UTXO` was minted to attacker for `token` in `runAction`'s return value (`utxoSet` excludes it, since `balanceChange` for `token` was `0`), proving the transfer bypassed `handleOut`/nullifier accounting entirely.
