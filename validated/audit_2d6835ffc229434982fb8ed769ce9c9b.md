## #Vulnerability Found

### Title
Cross-chain amount truncation in `HyperFungibleToken` pallet can mint zero tokens while consuming the full source amount - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `pallet-hyper-fungible-token`'s `on_accept` handler converts an incoming ERC20-denominated amount to the local asset's balance precision using floor (integer) division. When the local asset has fewer decimals than the paired EVM contract's ERC20 decimals — which is the pallet's normal, supported configuration — a legitimate positive `amount` sent from the EVM side can convert to `0` in local units. The pallet then proceeds to mint/transfer `0` to the beneficiary and still emits `TokenReceived` and returns success, exactly mirroring the StUSR "rounding-in-favor-of-sender / zero-effect transfer that still succeeds" bug class from the external report, but here it manifests as an inbound bridge message that is marked delivered while transferring no value.

### Finding Description
`register_token` enforces `config.decimals >= local_decimals` (`ErcDecimalsBelowLocal` check) [1](#0-0) , so `erc_decimals - local_decimals` is always `>= 0` for every registered chain pairing — i.e., truncating division on the inbound path is a normal, expected code path, not an edge case.

`convert_to_balance` performs this scale-down with plain integer division, which floors toward zero: [2](#0-1) 

`on_accept` calls this conversion on the untrusted `message.amount` decoded straight from the incoming EVM `Message` and uses the result directly to mint or release funds, with no check that the converted `amount` is non-zero: [3](#0-2) 

On the EVM side, `HyperFungibleToken.send()` burns the caller's full ERC20 `amount` (in the token's native, typically 18-decimal, precision) and dispatches it unmodified as `message.amount`: [4](#0-3) 

There is no minimum-amount / divisibility check anywhere along this path (EVM `send`, pallet `on_accept`, or `convert_to_balance`) ensuring that `amount` is a multiple of `10^(erc_decimals - local_decimals)`. Consequently, for any `amount < 10^(erc_decimals - local_decimals)` (or any non-multiple, whose remainder is silently dropped), the beneficiary is credited less than intended — down to exactly zero for sub-unit amounts — while:
- The EVM-side tokens were already irrevocably burned from the sender in `send()`.
- `on_accept` returns `Ok(...)`, so the ISMP message is recorded as successfully delivered/processed — there is no timeout/refund path available once processing succeeds, since `on_timeout` only fires for requests that were never delivered.

This is the direct analog of the StUSR bug: a rounding-down conversion in a value-transfer path that can yield a "successful", non-reverting transfer of zero effective value, silently destroying the difference.

### Impact Explanation
Real, burned ERC20 value on the source EVM chain is permanently lost with no tokens credited on the destination substrate chain, and no automatic refund mechanism, because the message is not a "failed"/timed-out request — it is a "successfully processed" request that happened to convert to zero. This is a concrete, permanent loss-of-funds bug reachable by any unprivileged user calling `HyperFungibleToken.send()` with a small enough amount (or an amount not aligned to the destination's decimal granularity), and could also be weaponized to grief a victim beneficiary or to make it appear (via `TokenReceived`/`TokenSent` events) that value moved when it did not, which is dangerous for any off-chain or on-chain system that treats successful message delivery as proof that funds arrived.

### Likelihood Explanation
This requires no special privileges or malicious governance/relayer — a single ordinary user transaction (`send`) with a sufficiently small `amount` relative to the configured decimal gap triggers it deterministically. Any registered pair where `erc_decimals > local_decimals` (the pallet's normal supported case, actively demonstrated in the `BridgeToken`/`BRIDGE` 18-vs-12-decimal test fixture) is exposed. It can happen unintentionally (dust transfers, UI decimal-formatting bugs) or be triggered deliberately.

### Recommendation
In `on_accept` (and symmetrically in `on_timeout`/the `send` direction, if applicable), reject conversions that round the amount down to zero, and/or require that `message.amount` be an exact multiple of `10^(erc_decimals - local_decimals)`, reverting (returning an error, not silently succeeding) otherwise so the ISMP request can time out and be refunded. Consider rounding remainders explicitly (e.g., holding dust in an escrow account and emitting an event) rather than dropping them, and add an explicit `ensure!(amount > 0, ...)` guard before minting/transferring in `on_accept`.

### Proof of Concept
1. Register a token pair via `register_token` with `local_decimals = 12` and `erc_decimals = 18` (as in the existing `BRIDGE` test fixture, see `BridgeTokenTest.t.sol`).
2. On the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, call `send({ amount: 500_000, dest: <substrate chain>, to: <victim>, ... })` — `500_000 < 10^(18-12) = 10^6`, so this is a valid positive amount that gets burned from the caller.
3. The message is relayed and delivered to `on_accept`; `convert_to_balance(500_000, 18, 12)` computes `500_000 / 10^6 = 0`.
4. `Assets::mint_into(asset_id, beneficiary, 0)` (or `NativeCurrency::transfer(..., 0, ...)`) succeeds, `TokenReceived { amount: 0, ... }` is emitted, and `on_accept` returns `Ok(...)`.
5. Result: the sender's 500_000 units were burned on the EVM chain; the beneficiary's balance on the substrate chain is unchanged; the message is permanently marked as processed with no refund path.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
