### Title
Unhandled panic (DoS) via crafted `workflowID`/`workflowOwner` in HTTP trigger gateway handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
The CVE-2016-0797 bug class (unvalidated/oversized numeric-string input causing memory corruption in a C string-to-bignum parser) has a live Go analog here: `normalizeHex` performs unchecked arithmetic on attacker-controlled string lengths and can be driven negative, causing `strings.Repeat` to panic. This is reachable directly from an unauthenticated/unprivileged HTTP trigger request to the gateway, before any workflow authorization occurs.

### Finding Description
`validateHexInput` [1](#0-0)  only checks that the *total* input length does not exceed `expectedLength`, that the string is lowercase, and that the string (after conditionally trimming a literal `"0x"` prefix) decodes as valid hex. It never requires the `"0x"` prefix to actually be present.

Because of this, a `workflowID` consisting of exactly `workflowIDLength` (66) lowercase hex characters with **no** `"0x"` prefix (e.g. any 66-char lowercase hex string that happens not to start with the literal characters `0x`) passes `validateHexInput` cleanly: length is `== 66` (not `>`), it's lowercase, and `hex.DecodeString` succeeds on the 66-character string trimmed of nothing.

This validated value is later passed to `normalizeHex` [2](#0-1)  from `resolveWorkflowID` [3](#0-2) :

```go
func normalizeHex(input string, length int) string {
    hexStr := strings.TrimPrefix(input, "0x")
    expectedHexLength := length - 2
    paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
    return "0x" + paddedHex
}
```

Since `input` has no `"0x"` prefix, `TrimPrefix` is a no-op, so `hexStr` remains 66 characters while `expectedHexLength` is `66-2=64`. The repeat count `expectedHexLength-len(hexStr)` becomes `64-66 = -2`. `strings.Repeat` with a negative count panics ("strings: negative Repeat count"). The identical issue applies to `workflowOwner` at length 42 via the same code path.

The call order confirms this is reachable: `HandleUserTriggerRequest` calls `validatedTriggerRequest` (which runs `validateWorkflowFields`/`validateHexInput`) first, then unconditionally calls `resolveWorkflowID` → `normalizeHex` on the already-"validated" but prefix-less value [4](#0-3) . `HandleUserTriggerRequest` is exposed as the entry point for unauthenticated user trigger requests reaching the gateway's HTTP trigger capability, and authorization (`authorizeRequest`) only happens *after* `resolveWorkflowID` [5](#0-4) , meaning the panic is triggerable pre-authentication/pre-authorization.

I could not find a `recover()` in the gateway handler dispatch path within the indexed portion of the repository (searches for `recover()` in `core/services/gateway/**` returned no matches), so I cannot confirm whether an outer goroutine/HTTP layer recovers this panic. If unrecovered, a panic in a goroutine crashes the entire node process in Go.

### Impact Explanation
If the panic is not recovered upstream, an unauthenticated network client can crash the Chainlink node's gateway process with a single malformed request, causing denial of service to all workflows relying on that gateway (mirroring the DoS impact class of CVE-2016-0797). Even if recovered by some outer middleware not visible in the indexed code, this still represents an unhandled-error/500-class fault reachable pre-authorization, without needing a valid workflow, key, or role.

### Likelihood Explanation
High for triggering the code path: the crafted value is simple to construct (any 66 or 42 character lowercase hex string not literally starting with `0x`), requires no authentication, and the check ordering in `HandleUserTriggerRequest` guarantees `normalizeHex` runs on it. The only uncertainty is whether an outer recovery mechanism (not found via my search) prevents a full process crash.

### Recommendation
In `validateHexInput`, require the literal `"0x"` prefix to be present before applying length/hex checks (reject inputs that don't start with `"0x"`), and/or make `normalizeHex` defensive by clamping the repeat count to `max(0, expectedHexLength-len(hexStr))` and erroring instead of panicking when the trimmed hex is longer than expected. Add a regression test using a 66/42-character lowercase hex string without the `0x` prefix.

### Proof of Concept
Send an HTTP trigger request (`workflows.execute`) with:
```json
{
  "workflow": {
    "workflowID": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "input": {}
}
```
(66 lowercase hex characters `a`, no `0x` prefix — passes `validateHexInput` since length `== 66`, is lowercase, and decodes as hex). This reaches `resolveWorkflowID` → `normalizeHex("aaaa...aaaa", 66)`, computing `strings.Repeat("0", 64-66)`, which panics.

**Uncertainty:** I was unable to confirm within the indexed code whether the goroutine/HTTP layer invoking `HandleUserTriggerRequest` (in `core/services/gateway/handlers/capabilities/v2/http_handler.go`) wraps the call in a `recover()`, since that file's contents were not fully available in the index. A Devin session with full repository access would be needed to verify the exact blast radius (goroutine-only crash vs. full process crash).

```go
func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}
```

```go
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}
```
