## Title
Unbounded gas forwarded to untrusted `IApp` destination in `EvmHost.dispatchIncoming`/`dispatchTimeOut` enables relayer gas-griefing and batch-delivery DoS - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` (for POST requests and GET responses) and `EvmHost.dispatchTimeOut` (for GET/POST timeouts) hand control to an arbitrary, attacker-influenced `IApp` destination contract via a raw `.call(...)` with no gas cap, so Solidity's default 63/64 forwarding rule applies. Any account can dispatch a message whose `to` field points at a contract they control, and when a permissionless relayer later delivers that message through `HandlerV2.handlePostRequests`/`handleGetResponses`, the relayer's transaction gas is consumed by the malicious destination without any limit, matching the reported bug class exactly (uncapped external call gas to an untrusted callee reachable by an unprivileged relayer).

### Finding Description
`HandlerV2.handlePostRequests` is explicitly "Permissionless (can be called by anyone)" and, after proof verification, loops over the batch and calls `host.dispatchIncoming(leaf.request, _msgSender())` for every request in the batch [1](#0-0) .

Inside `EvmHost.dispatchIncoming`, the destination address is derived directly from the request's `to` bytes (attacker-controlled at dispatch time by whoever originated the request) and invoked with an unmetered low-level `.call`: [2](#0-1) 

The same unmetered pattern recurs for GET responses: [3](#0-2) 

and for both GET and POST timeouts: [4](#0-3) 

None of these external calls specify a `gas` value, so each forwards up to `gasRemaining * 63/64` to the destination `IApp`. Since `to`/`from` addresses are set by whoever dispatches the original request (any unprivileged account can dispatch a message with a self-deployed malicious module as the destination), an attacker can:
1. Deploy a malicious `IApp` contract that, in `onAccept`/`onGetResponse`/`onPostRequestTimeout`, deliberately consumes almost all gas forwarded to it (e.g., an unbounded loop or storage-writing loop).
2. Dispatch a request/response/timeout targeting that malicious contract, which any relayer will subsequently be economically incentivized to deliver.
3. When `HandlerV2.handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` iterates the batch and reaches the malicious entry, `EvmHost.dispatchIncoming`/`dispatchTimeOut` forwards up to 63/64 of the relayer's remaining gas to it, which the malicious contract burns.

Because the handler loop does not revert the whole batch on a callback failure (it just deletes the receipt and continues, as documented in `docs/content/protocol/ismp/requests.mdx`), the batch keeps running with drastically reduced remaining gas after the malicious call, causing subsequent *legitimate* requests batched in the same transaction to run out of gas and have their `onAccept` calls fail (their receipts get deleted so they must be retried), even though the relayer estimated gas correctly for the original, unmodified batch contents. This mirrors the reported issue precisely: no per-operation gas cap is attached to the external call, gas conditions can be manipulated between the relayer's estimate and execution, and the relayer bears the cost/failure with no reimbursement mechanism.

### Impact Explanation
This allows an unprivileged actor to grief permissionless relayers economically and disrupt message delivery reliability:
- Relayers pay full gas for a `handlePostRequests`/`handleGetResponses` transaction where a malicious `to` contract consumes the bulk of the forwarded gas, well beyond what a normal `onAccept` implementation would use, degrading relayer profitability and discouraging relaying (a decentralization/liveness concern for the message-delivery route).
- Other legitimate requests batched in the same transaction (a common relayer batching optimization, as seen throughout `tesseract/messaging/evm/src/tx.rs`) can be starved of gas and fail delivery, forcing costly resubmission and delaying otherwise valid cross-chain messages — i.e., a route temporarily unable to deliver messages reliably.
- There is no mechanism (as recommended in the external report) for a per-operation gas cap, a relayer-supplied gas parameter, or a check that sufficient gas remains before forwarding it, so the vulnerability is systemic across all four dispatch/timeout entry points in `EvmHost.sol`.

### Likelihood Explanation
Likelihood is high: any account can dispatch an ISMP request/response with `to` pointing at a contract they deployed and fully control (no privileged role needed), and delivery through the permissionless `HandlerV2` handlers is the normal path every relayer executes. No special conditions beyond deploying a gas-griefing `IApp` and getting a request routed to it are required.

### Recommendation
Attach an explicit, bounded gas stipend to each external call in `EvmHost.dispatchIncoming` and `EvmHost.dispatchTimeOut` (e.g., `.call{gas: gasLimit}(...)`), derived from a per-operation gas field supplied at dispatch time or a protocol-wide cap, and verify `gasleft()` is sufficient to cover that stipend before making the call (reverting/skipping otherwise) so a single malicious destination cannot consume disproportionate gas or starve subsequent batch entries.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` with a gas-burning loop (e.g., repeated storage writes) that consumes essentially all gas forwarded to it.
2. Attacker dispatches a POST request via any source-chain dispatcher with `to = address(EvilApp)` and pays the minimum relayer fee.
3. A relayer batches this request together with several legitimate, already-fee-paying requests into one `HandlerV2.handlePostRequests` call, estimating gas based on the batch contents at submission time.
4. During execution, `EvmHost.dispatchIncoming` reaches the `EvilApp` entry and forwards `gasleft() * 63/64` via the unmetered `.call` at `evm/src/core/EvmHost.sol:809-810`; `EvilApp` burns nearly all of it.
5. Subsequent legitimate requests in the same loop iteration run out of gas, their `onAccept` calls fail, and their receipts are deleted (`evm/src/core/EvmHost.sol:812-816`), requiring costly resubmission — while the relayer has already paid for the full, inflated gas consumption caused by `EvilApp`.
