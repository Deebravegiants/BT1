### Title
Webhook shop identity spoofing - HMAC does not bind the `shop` (or `topic`/`api-version`) claim, allowing cross-tenant webhook forgery ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used by webhook handlers directly from the unauthenticated `X-Shopify-Shop-Domain` header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Any actor capable of obtaining a validly-signed webhook body/HMAC pair for one shop (e.g., their own dev/test store) can replay it against the app's webhook endpoint while substituting the `shop` (and `topic`/`webhook-id`/`api-version`) header for another tenant, and the signature check still passes.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(body_secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field on the `VerifiableQuery`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body/HMAC pair: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the authoritative tenant identifier passed to the app's handler: [4](#0-3) 

The equality the gem implicitly promises to the host application is: `HMAC-verified-body ⇒ shop header is authentic for that body`. In reality the binding only proves `HMAC-verified-body ⇒ this body was produced by someone who owns Context.api_secret_key at some point`, with **no guarantee that the accompanying `shop` header is the one Shopify actually attached to that body**. Because the shop, topic, webhook id and API version headers are excluded from `to_signable_string`, an attacker who can produce (or capture) any legitimately-signed `(body, hmac)` pair — trivially achievable by installing the app on their own store and triggering a real webhook — can resend that exact `(body, hmac)` combination to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header (and arbitrary topic/webhook-id/api-version headers). `Utils::HmacValidator.validate` will still return `true` since it never inspects those headers, and `Registry.process` will hand `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the app's handler with the forged shop identity attached to genuine-looking, HMAC-passed data.

### Impact Explanation
Host applications built on this gem are expected to trust `WebhookMetadata#shop` (validated via `Registry.process`) as the tenant scope for persisting/mutating per-merchant state (inventory sync, order processing, GDPR/compliance webhooks, uninstall/app-scope changes, etc.), since the whole point of `Registry.process` raising `InvalidWebhookError` on bad HMAC is to let callers treat a passing check as "this came from Shopify for the shop presented." An attacker who owns any shop that installs the app can, at will, cause the handler to execute business logic as if it originated from an arbitrary victim shop — i.e., cross-tenant access/write into another merchant's records — without needing the app's `client_secret`, an access token, or any privileged account beyond a self-service store installation. This satisfies the "cross-tenant access" Critical-impact category since attacker-controlled headers determine which tenant's data gets mutated while the payload passes signature verification.

### Likelihood Explanation
Requires: (1) the ability to obtain one genuine `(body, hmac)` pair, which any unprivileged user can get by installing the target app to a store they control and receiving/replaying a real webhook delivery; (2) network access to the app's public webhook endpoint, which is inherently internet-reachable by design. No secrets, tokens, or elevated privileges are needed. Exploitability depends on the host app actually keying data off `WebhookMetadata#shop` without independent verification — the common and encouraged usage pattern per this gem's own docs/tests, which simply pass `data.shop` through.

### Recommendation
Bind the header-derived identity fields to the cryptographic check, or otherwise clearly flag them as unauthenticated:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in `Webhooks::Request#to_signable_string` (or otherwise verify each header value against a value carried in the signed payload / TLS client identity), so a passing HMAC check actually proves those header values are unmodified.
- At minimum, document prominently that `request.shop` is not covered by HMAC verification and must not be trusted for tenant-scoping without additional out-of-band verification (e.g., comparing to a session already on file for the given webhook path/subscription), and consider raising in `Registry.process` if the shop domain fails `Utils::ShopValidator` sanity checks as defense in depth.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook topic the app subscribes to (e.g., `orders/create`). Shopify sends a legitimate request to the app's webhook endpoint with body `B`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker (or a script sitting in front of/replacing the delivery, e.g. via a proxy or by simply re-sending the same captured request) sends a new HTTP request to the same webhook endpoint with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it still equals `H`, so `Registry.process` proceeds without raising `InvalidWebhookError`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed B, ...)`, causing the host app to process attacker-supplied data under the victim shop's tenant identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
