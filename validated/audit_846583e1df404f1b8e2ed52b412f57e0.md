### Title
Webhook shop-domain identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler from an unauthenticated HTTP header, while the HMAC signature verifies only the raw request body. This breaks the intended binding of `hmac == sign(shop + body)` down to `hmac == sign(body)`, letting anyone who can obtain one valid `(body, hmac)` pair for a given secret (e.g. a merchant/attacker who legitimately controls their own Shopify store, or captures a real Shopify webhook delivery) resend that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, and have the gem accept it as authentic for that victim.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` (the untrusted header) straight into `WebhookMetadata`, which is the only tenant identifier passed to the app's `WebhookHandler#handle`: [3](#0-2) 

Consumers of the gem are expected to use `data.shop` from `WebhookMetadata` as the authenticated tenant identity when handling a webhook event, since `Registry.process` has already performed "the" authenticity check (`Utils::HmacValidator.validate(request)`) before invoking the handler. Because `to_signable_string` only covers the body, the equality that should hold — `hmac` authenticates `(shop, body)` — actually only holds for `body`. Any request with a body/hmac pair that is valid for the shared `api_secret_key` (or `old_api_secret_key`) passes validation regardless of which shop header accompanies it.

### Impact Explanation
An attacker who can produce one legitimately-signed webhook body/HMAC pair — trivially achievable by installing the same app on their own Shopify development/trial store and triggering webhooks with attacker-controlled body content (e.g. `orders/create`, `customers/data_request`) — can replay that exact `(raw_body, hmac)` pair while substituting the `shop-domain` header for a different, victim shop. `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate` only checks the body) and dispatch it to the app's handler tagged with the victim's shop. This constitutes cross-tenant data injection/spoofing: apps that use `data.shop` to look up per-tenant sessions/access tokens or to write/update tenant-scoped records (a common, documented pattern) can be tricked into associating attacker-controlled webhook data with another merchant's tenant, potentially triggering unauthorized actions, data corruption, or privacy-relevant mandatory webhooks (`customers/redact`, `shop/redact`) misattribution.

### Likelihood Explanation
Moderate-to-high. Exploitation requires only the ability to generate one valid signed webhook (any developer/attacker with their own Shopify store meets this bar) plus the ability to POST directly to the app's webhook endpoint with custom headers, bypassing Shopify's delivery infra — something not prevented by this gem since it performs no additional binding between the signed bytes and the shop header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop header to the verified payload before it is trusted as the webhook's tenant identity. Since the header value cannot be altered (Shopify signs only the body per their webhook spec), an alternative mitigation available at the gem level is to require and document that host applications must independently verify `request.shop` corresponds to a shop with an active session/access token before treating the payload as authentic, and make this explicit in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with crafted `raw_body` content of choice.
2. Shopify legitimately signs and delivers this webhook: `hmac = HMAC-SHA256(api_secret_key, raw_body)`, `shop-domain: attacker.myshopify.com`.
3. Attacker captures `(raw_body, hmac)` and re-sends a POST directly to the app's webhook endpoint, keeping `raw_body`/`hmac-sha256` header identical but replacing `shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `to_signable_string` (`raw_body`) — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, and any app logic keyed on `data.shop` (session lookup, DB writes, redaction actions) is executed as if legitimately originating from the victim shop. [4](#0-3) [5](#0-4) [6](#0-5)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
