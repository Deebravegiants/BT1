### Title
Webhook shop and topic identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and label the payload are taken from unauthenticated HTTP headers. Anyone who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on their own store and receiving one of its own webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body or to the HMAC secret: [2](#0-1) 

`HmacValidator.validate` verifies exactly that signable string (the raw body) against `Context.api_secret_key`/`old_api_secret_key`, with no reference to shop or topic: [3](#0-2) 

`Registry.process` trusts the HMAC check as proof that the *entire* request — including the header-derived `shop` and `topic` — is authentic, then dispatches the unauthenticated `shop` value straight to the app's handler: [4](#0-3) 

The equality the gem implicitly claims is:
`shop used by handler (request.shop, from header) == shop that the HMAC-secret holder actually intended for this exact body`

But the HMAC only proves:
`raw_body == raw_body signed by secret holder`

It says nothing about which shop or topic header accompanied that body when Shopify originally sent it. Since `shop`/`topic` are excluded from `to_signable_string`, they can be freely swapped by anyone relaying a body+HMAC pair they've legitimately observed once (from their own shop's webhook deliveries), without invalidating the signature.

### Impact Explanation
This breaks the tenant boundary the gem is responsible for enforcing before handing data to the app: `handler.handle` receives `WebhookMetadata` whose `shop` field is attacker-controlled despite `Registry.process` having just asserted `Invalid webhook HMAC.` would be raised otherwise, i.e. the HMAC gate provides false assurance about `shop`. For a multi-tenant app that keys per-shop side effects (order/customer/app-uninstalled processing, data deletion, entitlement changes, etc.) off `WebhookMetadata#shop`, an attacker can inject/replay data attributed to a shop they don't operate, a cross-tenant impact.

### Likelihood Explanation
Likelihood is high for the specific step of obtaining one legitimate signed body: an unprivileged user can simply install the target app on a free/dev store they control, trigger a webhook (e.g. `app/uninstalled`), capture the raw body and its `x-shopify-hmac-sha256` value, and replay them with a different `x-shopify-shop-domain` header value at will since no shop/topic binding constrains reuse.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise bind the caller-supplied headers to the signed material) when computing/validating the webhook HMAC, or independently verify that the `shop` header corresponds to a shop session/installation the app actually manages before trusting `WebhookMetadata#shop` for any tenant-scoped action.

### Proof of Concept
1. Install the target app (built on this gem) on attacker-owned store `attacker-shop.myshopify.com`; trigger any webhook, capture `raw_body` and the `x-shopify-hmac-sha256` header — this pair is validly signed by the app's real `api_secret_key`.
2. Send the same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `@raw_body` (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds.
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled webhook content as if it originated from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
