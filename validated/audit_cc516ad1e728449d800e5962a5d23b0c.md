### Title
Webhook shop attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-ing only the raw request body, while the `shop` (and `topic`/`webhook_id`) values that `Registry.process` hands to the app's handler are read from unauthenticated HTTP headers. This breaks the intended binding `hmac_verified(request) == shop_attributed(request)`: a valid HMAC only proves the *body* came from Shopify's signing key, not that the *shop header* accompanying it is genuine, so a body/HMAC pair legitimately issued for one shop can be replayed with a different shop header and will still pass verification.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from client-supplied HTTP headers with no cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to build the data handed to the app's handler, without any additional binding check: [3](#0-2) 

The `HmacValidator` itself only recomputes the signature over `to_signable_string` (the raw body) and secure-compares it to the supplied header value — it never incorporates `shop`: [4](#0-3) 

The gem's own documentation frames `Registry.process` as verifying "the request did indeed come from Shopify" before invoking the handler, which encourages consumers to treat the resulting `shop` as authenticated: [5](#0-4) 

Because the app's `client_secret` (the HMAC key) is shared across every shop that installs the app, a body+HMAC pair that is genuinely produced by Shopify for shop A remains a valid signature for that same body no matter what `X-Shopify-Shop-Domain` header accompanies it. The equality that should hold — "the shop whose secret produced this HMAC" equals "the shop attributed to the resulting handler call" — is not enforced anywhere in this code path.

### Impact Explanation
An attacker who can obtain one legitimately-signed (body, HMAC) pair for a shop they control (trivial: install the target app on their own store and trigger any webhook-emitting action) can replay that exact body and HMAC to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim shop. Any host application that follows this gem's documented flow and uses `data.shop` to select or mutate per-tenant records (the intended and only realistic use of this field) can be made to attribute attacker-controlled webhook content to another merchant's tenant — a cross-tenant data integrity/confidentiality violation.

### Likelihood Explanation
Any unprivileged internet user can become an "attacker" simply by installing the target app on their own free development/trial store, which lets them capture a genuine (body, HMAC) pair without needing `client_secret`, an access token, or any privileged access. Replaying it to the app's public webhook URL with a modified shop header requires no special network position (no TLS interception needed) and no social engineering.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually HMAC-verified, e.g., require host applications to independently confirm the shop exists in their own installed-shops store before trusting `WebhookMetadata#shop`, or extend `to_signable_string`/the verification contract to incorporate the shop header so a mismatched or replayed shop value fails validation. At minimum, document explicitly that `Registry.process` only authenticates the payload body and that `shop` must be independently corroborated before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and performs an action that triggers a registered webhook (e.g., `orders/create`).
2. Attacker's endpoint (or a proxy/log) captures the legitimate request: raw body `B`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends a new POST to the app's public webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` since `to_signable_string` is just `B`.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-supplied data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
