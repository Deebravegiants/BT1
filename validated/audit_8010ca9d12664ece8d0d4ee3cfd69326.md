### Title
Removing a state machine from the GRANDPA/Tendermint/etc. consensus-client whitelist permanently blocks timeout (and delivery) processing for already in-flight requests, freezing escrowed relayer fees - (File: `modules/ismp/clients/grandpa/src/consensus.rs`, `modules/ismp/core/src/handlers/timeout.rs`, `modules/ismp/core/src/handlers.rs`)

### Summary
`GrandpaConsensusClient::state_machine()` (and the analogous `state_machine()` in the other whitelist-style clients such as `ismp-optimism`/`ismp-arbitrum`/tendermint) gates access purely on the current admin-controlled `SupportedStateMachines` map. This same lookup is used generically by `validate_state_machine()` in `handlers.rs`, which is invoked for **every** ISMP message type including `TimeoutMessage::Post` in `handlers/timeout.rs`. If governance calls `remove_state_machines` on a state machine that still has in-flight (dispatched but undelivered) requests, every subsequent attempt to either deliver or time out those requests reverts with `UnsupportedStateMachine`/`ConsensusStateIdNotRecognized`, permanently locking the escrowed relayer fee for those requests with no way to reclaim it. This mirrors the Blueberry report exactly: a legitimate admin action on a whitelist (not malicious governance, just a routine "remove an unwanted/deprecated chain" operation) blocks a permissionless, otherwise-always-available recovery path (timeout) for funds that were locked before the whitelist changed.

### Finding Description
`add_state_machines`/`remove_state_machines` in `modules/ismp/clients/grandpa/src/lib.rs` (lines 96-135) let the `RootOrigin` add/remove entries from `SupportedStateMachines`. This is documented as routine chain-management ("terminating the trustless connection ... They can always be re-added" – `docs/content/developers/polkadot/solochains.mdx` lines 50-61), not a privileged/malicious action.

So the sequence is:
1. A user/app dispatches a `PostRequest` to a state machine `X` while `X` is in `SupportedStateMachines` (GRANDPA client), paying a relayer fee escrowed on the host (`pallet-ismp`/`EvmHost.fundRequest`).
2. Before the request's timeout elapses (or before a relayer delivers it), governance calls `remove_state_machines([X])` — a routine, documented, non-malicious maintenance action.
3. Once `X` is removed, **every** future call to `validate_state_machine` for proof heights whose `state_id == X` fails with `UnsupportedStateMachine`, because `GrandpaConsensusClient::state_machine` unconditionally checks the current whitelist rather than whether `X` was whitelisted at dispatch time.
4. This blocks both delivery (`handlers/request.rs`, `handlers/response.rs` use the same `validate_state_machine`) **and** the timeout path (`handlers/timeout.rs`), which is the request's only fallback recovery mechanism.
5. The relayer fee funded for that request (and, on `EvmHost`, any escrowed native/ERC20 fee token) is now permanently unreachable: it can never be delivered (frozen for the intended recipient) nor timed out/refunded (frozen for the payer).

The same pattern (a "supported" boolean/whitelist map consulted by `state_machine()` and reused generically for timeout validation) exists in `ismp-tendermint`, `ismp-optimism`, and `ismp-arbitrum` pallets, all of which store simple `SupportedStateMachines` maps toggled by an `AdminOrigin` call, e.g. `modules/ismp/clients/tendermint/src/pallet.rs` lines 49-84. ### Impact Explanation
This is a permanent freezing-of-funds bug reachable from a completely benign, documented operational action (removing a deprecated/unwanted state machine from the whitelist), not from malicious governance. Any request already in flight to/from the removed state machine at the moment of removal has its escrowed relayer fee permanently locked — it can be delivered to neither the destination module nor refunded to the payer via timeout, because the shared `validate_state_machine` gate used by both the delivery and timeout handlers keys off the *current* whitelist state rather than the state at dispatch time. This satisfies "permanent freezing of funds" and is reachable by a single unprivileged dispatched request combined with a routine admin whitelist update — the funds loss is not something the relaying party or the requester can avoid or predict.

### Likelihood Explanation
Likelihood is moderate-to-high: whitelist removal is an explicitly supported, documented operation ("They can always be re-added" in the docs, implying operators are expected to remove and re-add state machines over the lifecycle of the protocol, e.g., for deprecating a solochain, migrating a chain ID, or responding to a security incident on the counterparty chain). Any in-flight request at the time of removal is silently and permanently affected — no explicit check exists anywhere in the dispatch, delivery, or timeout path that ties a request's validity to the whitelist state that existed when it was created.

### Recommendation
Decouple the "is this state machine currently accepted for new consensus updates/new requests" check from the "can I read data (e.g. verify non-membership for timeout) for state commitments that were already accepted while this state machine was whitelisted" check. Concretely:
- Do not gate `validate_state_machine`'s ability to construct a `StateMachineClient` for timeout processing on the *current* `SupportedStateMachines` whitelist; instead, only require that a state commitment already exists at the referenced height (which is only possible if the state machine was whitelisted at the time consensus was updated).
- Alternatively, separate `state_machine()` into `state_machine_for_new_consensus()` (whitelist-gated, used by `verify_consensus`) and `state_machine_for_existing_commitment()` (gated only by presence of a stored commitment), and route timeout/response handling through the latter so in-flight requests can still be resolved (delivered or timed out) after removal.
- Add an explicit migration/drain step in `remove_state_machines` that either rejects removal while there are pending (undelivered, unexpired) request commitments for that state machine, or provides an admin-triggered force-timeout/refund path for such requests before removal takes effect.

### Proof of Concept
1. On the GRANDPA-consuming chain, whitelist state machine `X` via `add_state_machines` and configure a consensus client for it.
2. Dispatch a `PostRequest` with `dest = X` and a future `timeoutTimestamp`, escrowing a relayer fee (`fundRequest`/dispatch fee).
3. Before the request is delivered or timed out, call `remove_state_machines([X])` from `RootOrigin` (a routine op per the docs).
4. Attempt to submit a `PostRequestMessage` delivering the request, or a `TimeoutMessage::Post` proving non-membership at a height for `X`:
   - Both calls go through `validate_state_machine(host, proof_height)` → `consensus_client.state_machine(X)` → `SupportedStateMachines::<T>::contains_key(X)` is now `false` → `Err(GrandpaError::UnsupportedStateMachine(X))`.
5. The request remains in `RequestCommitments` forever; its escrowed fee can never be claimed by the relayer (delivery fails) nor refunded to the payer (timeout fails), even if `X` is later re-added, unless a state commitment for the exact pending height range is somehow re-derived — which GRANDPA re-verification from scratch does not guarantee will match the original in-flight proof height’s trusted consensus state continuity.

```rust
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
```

```rust
	impl<T: Config> Pallet<T> {
```
