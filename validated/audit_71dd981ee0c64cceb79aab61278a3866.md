### Title
Unchecked ERC20 `transfer` return value in `withdraw()`/`SweepDust` permanently freezes escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed tokens using a raw low-level `.call` to the ERC20 `transfer` selector, checking only the call's `success` flag and never inspecting/decoding the returned boolean:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

### Finding Description
`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` POST request is delivered by the host after `authenticate()`, i.e. whenever a relayer submits a proof for an order fill/cancellation completed on the counterpart chain. [2](#0-1) 

Inside `withdraw()`, escrowed tokens for each input asset and accumulated transaction fees are released to the beneficiary via a raw `.call()` to the ERC20 `transfer` selector, and the check only verifies that the outer call did not revert (`success`); it never decodes the returned ABI-encoded boolean: [3](#0-2) 

The same unchecked pattern is used in the `SweepDust` handler within `onAccept`: [4](#0-3) 

This is the same class of bug described in the external report: ERC20 `transfer` success is not validated against the actual boolean return value. Here the risk manifests in the opposite direction from the original report — rather than reverting on missing return data, the contract silently accepts a `false` return (a token that reports failure — e.g. insufficient balance, blacklist, paused state — without reverting) as success, because only the low-level `success` flag is checked, not the decoded return value.

Immediately after the unchecked transfer, `withdraw()` unconditionally updates escrow accounting (`_orders[body.commitment][token] -= amount;`, deleting `TRANSACTION_FEES`) and emits `EscrowReleased`/`EscrowRefunded`, and `_filled[body.commitment]` is already set to the beneficiary at function entry: [5](#0-4) 

Because the incoming ISMP request has already been consumed/authenticated by the host by the time `onAccept` runs, there is no retry path once the request is processed — if the underlying token transfer silently failed (returned `false`), the escrowed funds are marked as withdrawn/refunded in contract state while never actually leaving the contract to the beneficiary, and per-commitment escrow state has already been decremented, so the funds can never be reclaimed.

### Impact Explanation
A token whose `transfer` implementation can return `false` on failure without reverting (a known category of non-standard/edge-case ERC20 behavior, e.g. paused/blacklist-aware tokens, and the exact class of token cited in the external report) causes `withdraw()` to treat a failed transfer as successful. The escrow accounting is finalized and the ISMP message is consumed, so the beneficiary permanently loses access to their escrowed input tokens or fee — a permanent freeze/loss of funds with no retry or recovery mechanism, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Triggering the path requires only the normal intent lifecycle: a solver fills (or the user cancels) an order, and any relayer delivers the resulting `RedeemEscrow`/`RefundEscrow` message through the standard ISMP delivery flow — no special privilege is needed. The vulnerability is latent for any non-fully-standard-compliant ERC20 token configured as an order's input/fee token (a token selection decision made per order, not restricted by the protocol), making it reachable by intent solvers/relayers as part of ordinary usage rather than requiring an adversarial actor.

### Recommendation
Replace the raw `.call`/selector pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported in this file, so both missing return data and an explicit `false` return are handled correctly:
```solidity
SafeERC20.safeTransfer(IERC20(token), beneficiary, amount);
``` [6](#0-5) 

### Proof of Concept
1. Configure/select an ERC20 token as an order's input (or fee) token whose `transfer` returns `false` on failure instead of reverting (e.g., due to an internal balance/blacklist/pause check).
2. A solver fills the order cross-chain (or the user cancels it), and a relayer delivers the resulting `RedeemEscrow`/`RefundEscrow` POST request; `onAccept` is invoked by the host and calls `withdraw()`. [2](#0-1) 
3. If the token's internal condition causes `transfer` to return `false` (contract call itself succeeds, so `success == true`), `withdraw()` does not revert, decrements `_orders[body.commitment][token]`, and emits `EscrowReleased`/`EscrowRefunded` even though the beneficiary never received the tokens. [7](#0-6) 
4. The escrowed tokens remain stuck in the `IntentGatewayV2` contract, the commitment's escrow entry is already decremented, and there is no code path to retry or reclaim the funds — resulting in a permanent loss for the beneficiary.
