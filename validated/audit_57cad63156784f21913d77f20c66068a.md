Webhook `shop` field trusted for tenant routing while excluded from HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, using the app's single, shop-independent `client_secret`. The `shop` value that is subsequently used to route/label the payload to a specific tenant is read directly from the unauthenticated `shopify-shop-domain` HTTP header, which is never included in the signed material.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` define the payload that `HmacValidator.validate` checks: only `@raw_body` is signed. [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is not part of `to_signable_string` and therefore carries no cryptographic binding to the HMAC signature at all. [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which checks only the body against the app's static `api_secret_key` — and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any additional check that the `shop` header corresponds to the shop the body/HMAC actually originated from. [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC using `Context.api_secret_key`, which is one static secret shared across *all* shops that installed the app — it is not shop-specific. [4](#0-3) 

This breaks the identity binding: **the shop the HMAC actually authenticates the body for** must equal **the shop the gem attributes/routes the webhook payload to**. Because the header carrying the second value is excluded from the first check, any HMAC that is valid for *some* shop's payload is equally valid to satisfy `process` regardless of which `shop` header accompanies it — the check answers permissively as long as the body+secret line up, no matter what shop label is attached.

### Impact Explanation
An unprivileged internet user who controls (or can capture traffic from) their own shop's app installation — a completely normal, unprivileged tenant of a multi-tenant app — receives genuine Shopify-signed webhook deliveries (body + `X-Shopify-Hmac-Sha256`) addressed to the app's public webhook endpoint. Because the HMAC secret is the same for every tenant of the app and does not cover the `shop-domain` header, that attacker can resend the exact same body/HMAC pair to the app's endpoint while substituting a different `shopify-shop-domain` header value (a victim shop). `HmacValidator.validate` still returns `true` (the body signature is unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

Any host application that keys session lookup, data writes, or business logic off `WebhookMetadata#shop` (as the gem's documented pattern, `shop: request.shop`, implies) will process attacker-controlled webhook content under the wrong tenant's identity — a cross-tenant data-integrity/authentication-boundary violation, since the same forged payload can be replayed indefinitely and attributed to any target shop. This matches the Critical category: cross-tenant access achieved by an unprivileged actor exploiting a signature that does not cover the field used for identity routing — directly analogous to the Taiko `_isProposerPermitted` bug, where a check on one identity value (`proposerOne`) failed to bind correctly to the actual authorization decision, causing incorrect trust routing.

### Likelihood Explanation
Likelihood is high in any deployment that relies on this gem's stock `Registry.process`/`WebhookMetadata` flow without adding its own cross-check between the shop header and the HMAC/body content or an installed-shops allowlist: the attacker only needs (a) their own legitimate app installation, from which they can capture at least one real webhook delivery (trivial — they can trigger an event like `products/create` on their own store), and (b) the ability to send an arbitrary HTTP request to the app's public webhook endpoint (which is by design internet-reachable). No secrets, tokens, or privileged access are required — only a normal merchant/tenant relationship with the app.

### Recommendation
Include the shop domain (and other routing-relevant headers such as `topic`/`webhook_id`) in the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop that is actually expected/installed (e.g., cross-check against a stored per-shop access token/session) before constructing `WebhookMetadata`. At minimum, document prominently that `HmacValidator.validate` only proves the body originated from *some* Shopify-signed source with the app's secret, and that callers must independently verify shop identity before trusting `request.shop` for tenant-specific processing.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook event (e.g. product update), capturing the legitimate `raw_body` and `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint.
2. Attacker replays this exact `raw_body` + `hmac-sha256` header to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses the forged request; `HmacValidator.validate(request)` recomputes HMAC over `@raw_body` using the app's single `api_secret_key` and it matches (unchanged from step 1), per: [5](#0-4) 
4. `Registry.process` proceeds and invokes `handler.handle` with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's captured body>, ...)`, per: [6](#0-5) 
5. Any host application logic keyed on `data.shop` now processes attacker-supplied content as if it belongs to the victim tenant.
