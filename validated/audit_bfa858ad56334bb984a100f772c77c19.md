### Title
Status/txHash misreported for the wrong withdrawal when multiple same-asset withdrawals share one NEAR transaction - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by `tx.hash` + `index`) by matching entries in the POA bridge's response purely by `assetId`, ignoring `index`, destination address, and amount. When a single NEAR transaction contains more than one withdrawal of the same asset (e.g. a batch withdrawal that sends the same token to two different destinations/amounts), the function can return the status and `transfer_tx_hash` belonging to a different withdrawal entry than the one actually requested.

### Finding Description
`describeWithdrawal` fetches all withdrawals attached to `args.tx.hash` and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [1](#0-0) 

The comment explicitly states the rationale: *"Response list is unsorted, so we match by assetId instead of index"*. This is an equality substitution: the correct key to identify "this specific withdrawal" is `(tx.hash, index)` — or at minimum `(assetId, destinationAddress, amount)` — but the code only checks `assetId`. If a NEAR transaction produces two or more withdrawal intents for the *same* `assetId` (different destination addresses and/or amounts, e.g. a batched multi-recipient withdrawal), `findMatchingWithdrawal` cannot distinguish between them and will return whichever entry in the unsorted list first matches the asset id.

The existing test suite documents intent to match by `assetId` for *different* assets sharing a tx hash (`"matches withdrawal by assetId, not by index"`), but that test only covers the case of two distinct asset ids — it does not cover multiple withdrawals of the *same* asset in one tx, which is the actual gap. [2](#0-1) 

### Impact Explanation
`describeWithdrawal`'s reported `status: "completed"` and `txHash` are consumed by integrators to decide whether a withdrawal has landed and to release/refund funds accordingly. If withdrawal A (say, 100 to address X) is reported as completed with the `transfer_tx_hash` that actually belongs to withdrawal B (say, 50 to address Y) because both share the same `assetId` and NEAR tx, an integrator polling status for A would see a "completed" status backed by a transaction hash that never paid address X. This is a status/hash misreport that can make an integrator credit or refund the wrong withdrawal, or credit twice (once from the misreported hash, once when the real withdrawal for A eventually also gets reported/matched), matching the "status or hash misreport making an integrator credit or refund twice" category.

### Likelihood Explanation
This requires an unprivileged/normal usage pattern — any caller that sends multiple withdrawals of the *same* underlying POA asset in a single NEAR transaction (e.g., batching multiple recipient addresses in one intents call) will reach this code path without any adversarial trust assumption or privileged access. No malicious relayer, bridge operator, or admin behavior is required; the withdrawals list returned by the POA bridge API is explicitly documented as unsorted, making mis-assignment across same-asset entries a realistic occurrence, not merely theoretical, whenever indices are used to disambiguate withdrawals as the `WithdrawalIdentifier.index` field promises.

### Recommendation
`findMatchingWithdrawal` should incorporate more than `assetId` when the withdrawals array contains multiple entries for the same asset — matching should use `destinationAddress` and `amount` (or any other correlating unique field from the underlying API) in addition to `assetId`, or the caller-provided `index` should be honored when there are multiple same-asset withdrawals in one transaction, so that the reported status/txHash is guaranteed to correspond to the exact withdrawal being queried.

### Proof of Concept
1. Submit one NEAR transaction containing two withdrawal intents for the same POA `assetId` (e.g., `nep141:btc.omft.near`) — one for 0.001 BTC to address `X`, another for 0.002 BTC to address `Y`.
2. Call `sdk.describeWithdrawal` for index 0 (intended for address `X`).
3. Because `findMatchingWithdrawal` only filters on `assetId`, and the POA API response list is unsorted, the function may return the entry for the withdrawal to address `Y` (with `Y`'s `transfer_tx_hash` and amount), reported as `{ status: "completed", txHash: <Y's tx hash> }` for a request that was actually about the withdrawal to `X`. [3](#0-2)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
