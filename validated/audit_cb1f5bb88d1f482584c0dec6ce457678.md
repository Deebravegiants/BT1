Audit Report

## Title
Uncapped `number_of_assets` in `pallet_xcm::claim_assets` combined with non-transactional XCM execution permits weight-underestimation DoS and partial state mutation (asset loss) - (File: `polkadot/xcm/pallet-xcm/src/lib.rs`)

## Summary
`claim_assets` derives `number_of_assets` directly from caller-supplied `VersionedAssets` with no upper-bound check analogous to `MAX_ASSETS_FOR_TRANSFER`, then builds `[ClaimAsset{assets, ticket}, DepositAsset{AllCounted(number_of_assets), beneficiary}]` and weighs it via `T::Weigher::weight` before dispatch, without wrapping the call in a transactional storage layer. Verification against the actual weight implementations confirms that `claim_asset`'s benchmarked weight function is a fixed constant independent of the number of assets in the `Assets` list (`fn claim_asset(_assets: &Assets, _ticket: &Location) -> Weight { XcmGeneric::<Runtime>::claim_asset() }` in every checked runtime's XCM weight impl, e.g. asset-hub-westend, bridge-hub-westend, coretime-westend, rococo, westend), so the pre-execution weight charged for `ClaimAsset` does not scale with the number of distinct assets claimed, while the underlying `AssetTraps` storage/execution work does scale with that count.

## Finding Description
`claim_assets` computes `number_of_assets` from the decoded assets with `assets.len() as u32` and no cap, unlike `transfer_assets`, which explicitly enforces `ensure!(assets.len() <= MAX_ASSETS_FOR_TRANSFER, Error::<T>::TooManyAssets)` [1](#0-0) . The claim message is built as `[ClaimAsset{assets, ticket}, DepositAsset{AllCounted(number_of_assets).into(), beneficiary}]` and weighed via `T::Weigher::weight(&mut message, Weight::MAX)` [2](#0-1) , then executed via `prepare_and_execute` with `outcome.ensure_complete()` checked only after execution returns [3](#0-2) .

Across every runtime's generated XCM weight implementation examined (asset-hub-westend, bridge-hub-westend, collectives-westend, coretime-westend, rococo, westend), `claim_asset` is implemented as a fixed constant that ignores the `Assets` argument entirely: `fn claim_asset(_assets: &Assets, _ticket: &Location) -> Weight { XcmGeneric::<Runtime>::claim_asset() }` [4](#0-3) , and the underlying benchmark itself charges a single fixed read/write against `AssetTraps` regardless of how many distinct assets are packed into that one trap entry, e.g. `pub fn claim_asset() -> Weight { Weight::from_parts(9_795_000, ...).saturating_add(T::DbWeight::get().reads(1)).saturating_add(T::DbWeight::get().writes(1)) }` [5](#0-4) . This confirms the claim's central technical premise: the `ClaimAsset` instruction weight is not parameterized by the number of assets contained in the claim, so an attacker-controlled `number_of_assets`/`assets` list is not reflected proportionally in the charged weight for that instruction.

By contrast, `deposit_asset` weight functions do call `assets.weigh_assets(...)` on the `AssetFilter` [6](#0-5) , suggesting some per-asset scaling is intended for `DepositAsset`; however, I was unable to fully confirm within the available tool budget how `weigh_assets`/`WeighAssets` behaves for the `AllCounted(n)` wildcard variant specifically (i.e., whether it derives cost from the wildcard's count field `n` or only from a concrete `Assets` list), since the `WeighAssets` trait definition and its `AssetFilter` impl body were not retrieved before the iteration budget was exhausted. This is a gap in my verification, not a refutation of the claim.

On the transactional-guard point: `claim_assets` has no `#[transactional]` attribute or `with_storage_layer` wrapper, matching the report's description, and `ensure_complete()` is checked only after `prepare_and_execute` runs to completion or partial failure [7](#0-6) .

## Impact Explanation
The confirmed underestimation is narrower than the report frames it: `ClaimAsset`'s charged weight is a fixed per-instruction constant (one storage read/write) regardless of how many distinct assets are bundled under one trap hash, meaning the extrinsic fee/weight charged for the `ClaimAsset` portion does not scale with the number of assets actually matched/removed from `AssetTraps`. Whether this translates into a *practically exploitable* weight-underestimation DoS depends on (a) how expensive iterating N assets inside a single `AssetTraps` entry actually is in the executor (in-memory `Assets` matching, likely fast per item) and (b) whether `MaxAssetsIntoHolding` and other bounds already cap N to values where the fixed weight remains a safe upper bound in practice — this was not fully verified. The non-transactional dispatch is confirmed structurally, but the report's specific asset-loss scenario (trap removed but deposit incomplete leaving `beneficiary` with fewer assets) is a plausible consequence of `ClaimAsset` removing the trap entry before `DepositAsset` completes, though I could not verify the exact ordering/atomicity semantics of `ClaimAsset` removal vs. `DepositAsset` execution within the executor's instruction loop in the time available.

## Likelihood Explanation
The precondition (trapping many low-value assets under one hash via ordinary signed `execute`/`send` calls, then calling `claim_assets` once) is realistic and requires no special privilege, consistent with the report. Actual exploitability hinges on unverified details: whether `MaxAssetsIntoHolding` already bounds N tightly enough that the fixed `claim_asset` weight remains conservative, and whether `DepositAsset`'s AllCounted wildcard weight scales with `n` in a way that compensates.

## Recommendation
- Add an explicit bound on `assets.len()` in `claim_assets` (mirroring `MAX_ASSETS_FOR_TRANSFER`) before constructing the `ClaimAsset`/`DepositAsset` message, rejecting oversized claims with a `TooManyAssets`-style error.
- Verify/parameterize `claim_asset`'s benchmark and weight function by the number of assets in the `Assets` argument rather than using a fixed constant, since the current implementation ignores the argument entirely.
- Wrap `claim_assets` in `with_storage_layer`/`#[transactional]` so an `Outcome::Incomplete` result rolls back any partial `AssetTraps` mutation together with the failed deposit, preserving atomicity between trap accounting and asset delivery.

## Proof of Concept
1. From a signed origin, execute N `WithdrawAsset`+`Trap` XCM programs trapping N distinct low-value `AssetId`s under one trap hash (same origin), for N approaching `MaxAssetsIntoHolding`.
2. Call `claim_assets` with all N trapped assets and a valid beneficiary; measure actual weight consumed by `prepare_and_execute` versus the value returned by `T::Weigher::weight`, specifically isolating the `ClaimAsset` instruction's contribution, which per the fixed `XcmGeneric::claim_asset()` weight function does not grow with N.
3. Repeat with `DepositAsset` partial-failure conditions (e.g., N exceeding `MaxAssetsIntoHolding` during the deposit phase) and assert whether `AssetTraps` is mutated/removed even when `outcome.ensure_complete()` returns an error, confirming or refuting the non-transactional partial-mutation claim.
4. This PoC plan matches the report's proposed test but the actual pass/fail outcome (i.e., whether real divergence and partial mutation occur) was not executed or confirmed against a running node within this investigation — only the static code structure (fixed `claim_asset` weight constant, absence of `MAX_ASSETS_FOR_TRANSFER`-style cap, absence of transactional wrapper) was verified.
