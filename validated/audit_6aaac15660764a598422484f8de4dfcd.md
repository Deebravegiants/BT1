### Title
Arbitrary call in `EmporiumUpgradeable.runAction` lets any prover drain tokens not listed in `circomData.erc20TokenAddresses` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s "stateless" op path lets an unprivileged caller make the Emporium contract execute an arbitrary external call to any address with any calldata. Both Hinkal's and Emporium's balance-accounting only inspect the token list the *prover themselves chooses* (`circomData.erc20TokenAddresses`), so any token/ETH balance the Emporium contract holds outside that chosen list can be moved out with zero accounting — an exact analog of the report's "value moved by an action but not counted in the balance equation" bug class.

### Finding Description
`Hinkal.sol` verifies value conservation only for the tokens the prover lists: [1](#0-0) 
This equality is enforced strictly per-token, but only for tokens present in `circomData.erc20TokenAddresses[]`, an array fully controlled by the caller constructing the proof.

`EmporiumUpgradeable.runAction` (an allowed "external action" invoked by `Hinkal.sol`) independently snapshots balances only for that same attacker-chosen array, then executes a list of `ops` decoded from `circomData.externalActionData.externalActionMetadata` (also attacker-controlled): [2](#0-1) 

The "CASE 2: Stateless Interaction" branch performs a raw low-level call from the Emporium contract itself to an arbitrary `op.endpoint` with arbitrary `op.callData`, only blocking two specific wallet-related selectors: [3](#0-2) 

Because `op.endpoint.call(...)` is executed with `msg.sender == Emporium`, an attacker can set `op.endpoint` to any ERC20 token address and `op.callData` to `transfer(recipient, amount)` (or, for ETH, set `op.value` and target any recipient), moving out any token the Emporium contract currently holds — to any recipient, including an address with no relation to the prover's shielded identity. Crucially, if that token address is *not* included in `circomData.erc20TokenAddresses`, neither Hinkal's balance-diff check (`Hinkal.sol:78-146`) nor Emporium's own `balancesBefore/After` loop (`EmporiumUpgradeable.sol:85-151`) observes or validates the transfer at all — the equality the protocol relies on to bound value movement to what the prover accounted for is simply never evaluated for that token.

The Emporium contract routinely and legitimately holds token/ETH balances: shielded withdrawals are moved into it before `ops` execute (`deltaAmountChanges[i] < 0` path), it exposes a public `receive()` for ETH, and dust/residual balances from prior swaps can persist across transactions: [4](#0-3) [5](#0-4) 

The only gating on triggering this path is `onlyAllowedRecipient`, which restricts *who can call `runAction`* (i.e. `Hinkal.sol` itself) — it does not restrict what `op.endpoint`/`op.callData` a prover can embed in `circomData`: [6](#0-5) 
And when `stack.signerAddress == address(0)`, `verifyWallet` requires no signature at all beyond a one-time-use message nonce, so this is reachable by any unprivileged EOA submitting a syntactically valid Groth16 proof for their own (even zero-value) shielded transaction: [7](#0-6) 

### Impact Explanation
Any ERC20 or ETH balance sitting in the Emporium contract that is not part of the attacker's chosen `erc20TokenAddresses` set for their transaction (protocol/relay fee residue, other users' in-flight withdrawal funds, swap dust, or ETH sent to the contract's `receive()`) can be transferred to an arbitrary address, entirely bypassing the balance-diff equation that is supposed to bound all fund movement to what the proof accounts for. This is theft of protocol/relay/other-user funds held by the contract and an unauthorized asset movement never sanctioned by any prover's accounting — meeting the High/Critical bar ("theft ... of protocol/relay fees," "executing calls or moving assets ... never authorised").

### Likelihood Explanation
Reachable by any unprivileged EOA: constructing the `EmporiumStack.ops` array and `circomData.erc20TokenAddresses` is entirely under the caller's control when building their own proof/transaction; no wallet signature, admin role, or special privilege is required when `signerAddress == address(0)`. The only prerequisite is that the Emporium contract holds a non-zero balance of some token outside the attacker's declared list, which is a normal operating condition given its `receive()` fallback and its role as a transient token-holding contract for withdrawals/swaps.

### Recommendation
Restrict the "stateless" op path so `op.endpoint` cannot be an ERC20/ERC721/ERC1155 token contract performing a raw transfer of Emporium-held funds (e.g., disallow direct calls to addresses in `circomData.erc20TokenAddresses` union a protected-token allowlist, or require every token the Emporium contract could plausibly send during `ops` execution to be included and accounted for in `circomData.erc20TokenAddresses`/`balancesBefore`/`balancesAfter`). Alternatively, snapshot and verify balances across the full set of tokens the contract is known to hold (or an owner-curated allowlist), not merely the prover-supplied subset, closing the same "value moved but not counted in the balance equation" gap the report describes for `ERC20BalanceGteEnforcer`.

### Proof of Concept
1. Emporium holds 100 USDC belonging to another pending flow (or dust/residue), and USDC is not in the current caller's `erc20TokenAddresses`.
2. Attacker builds a valid but otherwise trivial shielded transaction (e.g., zero-value internal move, or a swap of an unrelated token) whose `circomData.externalActionData.externalActionId` targets Emporium, with `circomData.externalActionData.externalActionMetadata` decoding to an `EmporiumStack` where `signerAddress == address(0)` and `ops = [{endpoint: USDC, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attackerEOA, 100e6))}]`.
3. `Hinkal.transact` calls `_externalTransact` → `EmporiumUpgradeable.runAction`, which executes the op via `op.endpoint.call(op.callData)` (`EmporiumUpgradeable.sol:112`), transferring the 100 USDC from Emporium to `attackerEOA`.
4. Because USDC is absent from `circomData.erc20TokenAddresses`, neither `Hinkal.sol`'s balance-diff loop nor Emporium's own `balancesBefore/After` loop observes this token, so the transaction's slippage/balance-equality checks pass unaffected, and no nullifier/commitment accounting reflects the stolen funds.
