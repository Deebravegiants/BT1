### Title
Permanent Freezing of Escrowed Native-Token Funds via Reverting `receive()` in IntentGatewayV2 Escrow Release - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()`, the routine that releases escrowed order inputs (as native ETH or ERC-20) to a beneficiary, forwards native-token amounts through `_sendValue()`, which reverts the entire call with `InsufficientNativeToken()` if the recipient's `receive()`/`fallback()` rejects the transfer [1](#0-0) . This is structurally the same bug class as the Gearbox report: a party who controls the destination address of a mandatory native-ETH payout can make that payout permanently unpayable by deploying a contract whose `receive()` always reverts, and thereby indefinitely block the settlement action that depends on it.

### Finding Description
`_withdraw()` is the single code path used to release escrowed order inputs both when a cross-chain fill is redeemed by a solver (`RequestKind.RedeemEscrow`) and when an order is refunded to its placer after cancellation or timeout (`RequestKind.RefundEscrow`) [2](#0-1) . When any escrowed input token is the native asset (`token == address(0)`), the payout is executed via:

```solidity
function _sendValue(address to, uint256 amount) internal {
    (bool sent,) = to.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [1](#0-0) 

This function is invoked inside `_withdraw()`'s token loop before the fee-forwarding and event-emission logic that finalizes the order [3](#0-2) . Because the whole EVM call reverts on failure (no try/catch, no fallback to a pull-payment or WETH re-wrap path — unlike the WETH-mode handlers in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which explicitly re-wrap ETH into an ERC-20 transfer if the native push fails [4](#0-3) ), `_withdraw()` has no resilience against a beneficiary that categorically refuses native ETH.

This `_withdraw()` path is reachable by an unprivileged actor two ways:
1. **Self-refund path (order placer):** A user places an order with a native-ETH input and later cancels it (`cancelOrder`, described in the docs as ending in a call to `withdraw()`/`_withdraw()` to refund escrow to the user) . If the user is (or later becomes, via a proxy/implementation swap) a contract that reverts on `receive()`, the refund transaction — and any relayed cross-chain `RefundEscrow` message that triggers it via `onAccept` — will permanently fail.
2. **Cross-chain settlement path (relayed message dispatch):** After a solver fills an order cross-chain, a `RedeemEscrow`/`RefundEscrow` message is dispatched back to the source chain and delivered via the ISMP handler to `onAccept`, which ultimately calls `_withdraw()` with the beneficiary decoded from message data. Any beneficiary address that reverts on native ETH receipt (whether the order's own `user` for a refund, or an attacker-controlled beneficiary field) blocks the finalize step for that commitment.

Since `_orders[commitment][token]` is only decremented inside the same reverting call, the escrow state is never mutated on failure — the commitment can never be finalized, and the escrowed native-token input remains locked in the gateway contract with no route to be moved out, because every retry of the same delivery/settlement message hits the identical revert.

### Impact Explanation
This is a direct structural analog to the reported Gearbox vulnerability: a self-inflicted (or attacker-controlled) reverting `receive()` on the payout recipient converts a mandatory native-token transfer inside a settlement/liquidation-equivalent function into a permanently failing call. Here the consequence is permanent freezing of the escrowed native-token order input — funds that were legitimately locked by a user or solver via `placeOrder`/`fillOrder` become unrecoverable, since `_withdraw()` is the only function that releases escrow and it has no non-reverting fallback for native-token transfers. This satisfies the "permanent freezing of funds" acceptance criterion for a Medium/High-severity finding.

### Likelihood Explanation
No privileged role is required. Any account that can be the beneficiary of an order's native-ETH escrow (the order placer for a refund, or the designated recipient for redemption) can deploy or already control a contract wallet whose `receive()`/`fallback()` unconditionally reverts. Triggering the vulnerable path only requires normal placement/cancellation of an order with a native-ETH input, or a normally-delivered relayed cross-chain settlement message — both are permissionless, single-transaction operations available to any user or solver interacting with `IntentGatewayV2`.

### Recommendation
Do not let `_withdraw()`'s native-token leg cause the whole settlement to permanently revert. Adopt a pattern consistent with `WrappedHyperFungibleToken`'s WETH handlers already present in this codebase [4](#0-3) : on a failed native push, fall back to a pull-payment mechanism (e.g., credit the beneficiary an internal claimable balance, or wrap the native asset into WETH/an ERC-20 and transfer that instead) rather than reverting the entire `_withdraw()`/`onAccept()` call. This ensures order finalization and escrow release can always complete regardless of the beneficiary's ability to accept raw native ETH.

### Proof of Concept
1. Deploy a `RevertingBeneficiary` contract with no `receive()`/`fallback()` (or one that explicitly reverts).
2. Place an `Order` on `IntentGatewayV2` with a native-ETH (`token == address(0)`) input, using `RevertingBeneficiary` as `order.user` / refund beneficiary.
3. Trigger a refund path — either via `cancelOrder()` before fill, or by allowing the order to time out and having a relayer deliver the `RefundEscrow` message to `onAccept`.
4. Observe that `_withdraw()` → `_sendValue()` reverts with `InsufficientNativeToken()` on every attempt, because `RevertingBeneficiary.call{value: amount}("")` always returns `sent == false`.
5. Confirm `_orders[commitment][address(0)]` remains unchanged and non-zero indefinitely — the escrowed native ETH is permanently stuck, with no alternate code path in `IntentsBase.sol` to release it.

    /**
     * @dev Releases escrowed tokens to a beneficiary. Iterates over the withdrawal request's
     * token list, decrements the escrow balance for each, and transfers tokens out.
     *
     * When `finalize` is true, the order is marked as filled in the `_filled` mapping,
     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
