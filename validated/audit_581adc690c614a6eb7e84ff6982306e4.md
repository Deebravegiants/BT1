## Finding

### Title
Token-donation-inflated `tokenBalance()` causes `Router._computeBuy`'s overflow-cap branch to underflow-revert, permanently DoS'ing large buys and graduation on the affected curve - (File: packages/contracts/src/Router.sol)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live `tokenBalance()` and back-derives `amountInUsed` from `reserveToken - tokensOut`. This subtraction assumes the protocol invariant `tokenBalance() < reserveToken`, which is guaranteed only for organic curve state. An unprivileged attacker can break that invariant with a plain ERC20 `transfer` of the launched `Token` into the `Pair`, after which the very next buy large enough to hit the overflow-cap branch causes an unchecked Solidity 0.8 underflow panic instead of a handled revert — permanently reverting every large buy (including the threshold-crossing buy needed to graduate) on that curve.

### Finding Description
`Router._computeBuy` ( [1](#0-0) ) is:

```solidity
function _computeBuy(address pairAddr, uint256 amountIn) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
    ...
    tokensOut = reserveToken - (k / newReserveAsset);
    uint256 realBalance = pair.tokenBalance();
    if (tokensOut > realBalance) {
        tokensOut = realBalance;
        uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- underflows if realBalance > reserveToken
        if (cappedReserveToken == 0) revert OverflowCapDegenerate();
        ...
    }
}
```

The `cappedReserveToken == 0` guard only defends against the equality case; it does nothing when `tokensOut` (i.e. `realBalance`) exceeds `reserveToken`, because Solidity 0.8's checked arithmetic reverts with an unconditional panic *before* the `if` is ever reached.

`tokenBalance() < reserveToken` is a protocol invariant under organic trading (see `test_inv_virtualReserveAlwaysExceedsRealBalance`, [2](#0-1) ), but it is **not** enforced against direct `Token` donations to the `Pair`. `Zap.t.sol`'s own donation-attack harness proves the invariant is breakable:

```solidity
function _stageDonationAttack(address tokenAddr) internal returns (...) {
    ...
    donatedTokens = Token(tokenAddr).balanceOf(drainer);
    vm.prank(drainer);
    Token(tokenAddr).transfer(pairAddr, donatedTokens);   // plain ERC20 transfer, no privilege needed
}

function test_donation_realBalanceExceedsReserveToken() public {
    ...
    assertGt(realBalance, reserveToken);   // <- exactly the state Router._computeBuy assumes can't happen
}
```
( [3](#0-2) )

The maintainers already recognized this class of donation-induced underflow and patched **one** of the two call sites that perform this same subtraction: `Bonding.previewLtUntilGraduation` explicitly early-returns when `realBalance >= reserveToken` ( [4](#0-3) ):

```solidity
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;
uint256 cappedReserveToken = reserveToken - realBalance;
```

`Router._computeBuy` — the function that actually **executes** every buy through `Router.buy`, `Bonding.buy`, and `Zap.buy` ( [5](#0-4) ) — has no equivalent guard, so the fix applied to the *preview/quote* path was never mirrored onto the *execution* path that actually needs it.

### Impact Explanation
Once the donation-inflated state (`tokenBalance() > reserveToken`) exists, any single buy whose curve-implied `tokensOut` exceeds the (now-inflated) `realBalance` triggers the cap branch and panics instead of capping. This is exactly the buy shape the protocol relies on for two critical, permissionless flows:
- A large/whale buy on `Bonding.buy` / `Zap.buy` that should be gracefully capped at the pair's real balance (the documented "overflow buy cap" feature, [6](#0-5) ) instead reverts unconditionally.
- The threshold-crossing/closing buy that flips the curve into `Lifecycle.Graduating` via `_enterGraduating` — if that buy needs to hit the cap path (e.g. because the supply-side leg would otherwise bind), it now permanently reverts, bricking that curve's ability to ever graduate via a capped buy.

Since the donation is a cheap, one-shot, unprivileged ERC20 transfer, any attacker (or even an unrelated dust-donating actor) can permanently deny large buys on a bonding curve for as little as the cost of first buying and then donating tokens back to the pair. Small buys below the cap threshold remain unaffected, so the DoS is partial but permanent and re-triggerable on every subsequent oversized buy attempt, degrading the curve's usability and its path to graduation — a permanent freeze of the intended trading/graduation functionality for the affected token.

### Likelihood Explanation
High feasibility, no privilege required: `Token` transfers are unrestricted ERC20 transfers to the `Pair` address, exactly as demonstrated by the existing `_stageDonationAttack` test helper. The only cost is buying enough curve supply to donate (`> reserveToken - tokenBalance()` worth of tokens), which is inexpensive relative to the DoS achieved, and the triggering buy only needs to be large enough to hit the overflow-cap branch — a threshold that is lowered, not raised, by the very presence of graduation-threshold-crossing buys the protocol actively encourages.

### Recommendation
Add the same `realBalance >= reserveToken` early-out (or clamp) to `Router._computeBuy` that `Bonding.previewLtUntilGraduation` already applies, so a donation-inflated `tokenBalance()` cannot drive `cappedReserveToken` negative. Concretely, before the `cappedReserveToken` subtraction, if `realBalance >= reserveToken`, skip capping (treat the buy as if the real-balance ceiling can't bind) or revert with a dedicated, checked error rather than falling through to unchecked subtraction. Add a regression test that stages `_stageDonationAttack` and then issues an oversized buy (as in `test_inv_overflowCap_refundsLt`) to confirm the cap path degrades gracefully instead of panicking.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` (no privilege needed).
2. As an unprivileged attacker, buy a large chunk of the curve's `Token` (e.g. via `Bonding.buy`), then `Token.transfer(pairAddr, receivedTokens)` — the exact steps in `Zap.t.sol`'s `_stageDonationAttack` ( [7](#0-6) ). This drives `pair.tokenBalance() > reserveToken`, as asserted by `test_donation_realBalanceExceedsReserveToken` ( [8](#0-7) ).
3. Any subsequent caller submits an oversized buy analogous to `test_inv_overflowCap_refundsLt`'s `1_000_000_000 ether` LT buy ( [6](#0-5) ) — one that would normally hit the overflow-cap branch and be gracefully capped.
4. Inside `Router._computeBuy`, `tokensOut` is set to the inflated `realBalance`, then `cappedReserveToken = reserveToken - tokensOut` underflows because `realBalance > reserveToken`, causing an unconditional panic revert instead of a capped fill — the buy (and every future buy of that size) permanently fails on that curve.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }
