Audit Report

## Title
`Staking::nominate` fails to check that a target validator exists, allowing nomination of unregistered/removed validators - (File: `substrate/frame/staking/src/pallet/mod.rs`)

## Summary
The `nominate` extrinsic in the legacy `pallet-staking` validates each target only via `!Validators::<T>::get(&n).blocked`, which evaluates to `true` for any account that was never registered as a validator (since `ValidatorPrefs::default().blocked == false`), never checking `Validators::<T>::contains_key(&n)`. This lets a nominator successfully nominate a non-existent or removed validator instead of getting `Error::BadTarget`, exactly matching the bug already fixed in the sibling `pallet-staking-async` crate but never backported.

## Finding Description
In `Pallet::nominate` at `substrate/frame/staking/src/pallet/mod.rs` L1406-1420, the target-check closure is:
```rust
if old.contains(&n) || !Validators::<T>::get(&n).blocked {
    Ok(n)
} else {
    Err(Error::<T>::BadTarget.into())
}
``` [1](#0-0) 

`Validators<T>` is a `StorageMap<_, _, ValidatorPrefs>`, and `ValidatorPrefs::default().blocked` is `false`, so for any account `n` that is not a key in `Validators<T>` (never registered, or previously registered then removed via `chill`/`do_remove_validator`), `Validators::<T>::get(&n).blocked` returns `false`, making `!blocked` evaluate to `true`. The code never calls `Validators::<T>::contains_key(&n)`, so the check is a "not blocked" test rather than the required "is an active/registered validator and not blocked" test.

This is directly confirmed by the corresponding fixed code in `pallet-staking-async`'s `nominate`, which adds the missing `contains_key` check:
```rust
if old.contains(&n) ||
    (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
{
``` [2](#0-1) 

The prdoc explicitly documents this fix and scopes it only to `pallet-staking-async`: [3](#0-2) 

And the regression test `nominating_non_validators_is_not_ok` exists only in `substrate/frame/staking-async/src/tests/bonding.rs`, with no equivalent test present in the legacy `pallet-staking` test suite, confirming the fix and its coverage never reached `substrate/frame/staking`.

## Impact Explanation
A nominator can call `nominate` with an account that is not (or is no longer) a validator, and the extrinsic will succeed and store the invalid target in `Nominators<T>` instead of returning `Error::BadTarget`. This pollutes on-chain nomination state with bogus targets and can dilute or waste a nominator's stake weight across entities that can never be elected, causing the nominator to lose expected staking rewards. This is a concrete logic/accounting flaw reachable via a standard user-facing extrinsic in an in-scope pallet.

## Likelihood Explanation
No privileged role is required: any signed, bonded account with `active >= MinNominatorBond` can call the public `nominate` extrinsic with an arbitrary account ID, including a typo'd address, a stash that later called `chill`/was removed via `do_remove_validator`, or an account that was never a validator. This is trivially and repeatably triggerable.

## Recommendation
Mirror the fix already applied in `pallet-staking-async`: require both that the target is a currently registered validator and not blocked:
```rust
if old.contains(&n) ||
    (Validators::<T>::contains_key(&n) && !Validators::<T>::get(&n).blocked)
{
    Ok(n)
} else {
    Err(Error::<T>::BadTarget.into())
}
```
Apply this change to `substrate/frame/staking/src/pallet/mod.rs::nominate`, and add the equivalent `nominating_non_validators_is_not_ok` regression test to `substrate/frame/staking/src/tests.rs`.

## Proof of Concept
1. Use a `pallet-staking` (non-async) test/genesis setup with validators `{11, 21, 31}` and account `1` unbonded.
2. Call `Staking::bond(RuntimeOrigin::signed(1), 1000, RewardDestination::Stash)`.
3. Call `Staking::nominate(RuntimeOrigin::signed(1), vec![41])` where `41` was never registered via `Staking::validate` and is not in `old`.
4. Observe the call returns `Ok(())` instead of `Error::BadTarget`, because `Validators::<T>::get(&41)` returns `ValidatorPrefs::default()` with `blocked: false`, satisfying `!Validators::<T>::get(&n).blocked`. This mirrors the exact scenario blocked by the `contains_key` check and covered by `nominating_non_validators_is_not_ok` in `substrate/frame/staking-async/src/tests/bonding.rs`, which has no counterpart in `substrate/frame/staking`.
