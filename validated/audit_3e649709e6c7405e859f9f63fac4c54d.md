## Finding: CallDispatcher.sol Cannot Recover Stray or Stuck Native ETH

I found a valid analog to the reported bug class. `CallDispatcher.sol`, the shared execution helper used by `IntentGatewayV2`'s predispatch/postdispatch flows, accepts native ETH via a bare `receive()` but has no function — privileged or otherwise — to withdraw a stranded native balance. [1](#0-0) 

Unlike `EvmHost.withdraw()` [2](#0-1) , `BandwidthManager.onAccept` (Withdraw action) [3](#0-2) , and `IntentsBase._withdraw` [4](#0-3)  — all of which implement an explicit native-token withdrawal path for `address(0)` — `CallDispatcher` has no equivalent mechanism at all.

### Title
CallDispatcher permanently locks native ETH with no withdrawal mechanism - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a shared, stateless helper contract deployed once and referenced by `IntentGatewayV2`/`IntentsBase` (`_params.dispatcher`) to execute predispatch/postdispatch calls on behalf of orders. [5](#0-4)  It declares a public `receive() external payable {}` so it can accept native ETH forwarded during predispatch legs and swap-output sweeps [6](#0-5) , but the contract exposes only `dispatch(bytes)`, which forwards `call.value` to caller-specified targets — there is no owner, no admin, and no function that can move `address(this).balance` back out to a beneficiary.

### Finding Description
Because `receive()` is unrestricted, any account can send native ETH directly to the `CallDispatcher` address at any time, completely independent of an order's lifecycle. The gateway's sweep logic only recovers ETH that corresponds to a specific order's `inputs[i]`/`output.assets[i]` legs by sweeping `address(dispatcher).balance` at a specific point in the flow [7](#0-6) ; ETH sent outside that narrow window, or left over from a previous transaction that already swept a different amount, has no path back to any caller. Since `CallDispatcher` is a single shared singleton across all orders/users (not a per-order or per-user contract) and holds no owner reference, there is categorically no privileged recovery function — not even a governance/multisig path — that can ever move stranded balance out, unlike every other native-ETH-holding contract in the codebase (`EvmHost`, `BandwidthManager`, `IntentsBase`), which all implement an explicit `token == address(0)` withdrawal branch.

### Impact Explanation
Any native ETH that lands in `CallDispatcher` outside the exact window the sweep logic expects — e.g., a plain ETH transfer to the contract, dust from a partially-consumed predispatch leg, or a race between concurrent order fills sharing the same dispatcher instance — is permanently and irrecoverably locked, since the contract has no upgrade mechanism (it is a plain non-upgradeable utility contract) and no admin function. This is a permanent freezing-of-funds bug, matching the "medium" severity class described in the reference report, except here there is no compensating upgradeability to eventually unlock the funds, arguably making it more severe than the reported analog.

### Likelihood Explanation
`CallDispatcher` is on the direct execution path of `IntentGatewayV2.placeOrder`/`fillOrder` for orders that specify `predispatch`/output calldata, which is reachable by any unprivileged user or solver submitting an order transaction. A single stray `send`/`call{value}` to the well-known `CallDispatcher` address (its address is public, referenced in `_params.dispatcher`) is sufficient to trigger the lock; no special conditions or races are strictly required beyond sending ETH to the contract outside an active predispatch/output execution call.

### Recommendation
Add an owner- or governance-gated `sweep(address token, address to, uint256 amount)` function to `CallDispatcher` (mirroring the `adminTransferETH`/`WithdrawParams` pattern already used by `EvmHost`/`BandwidthManager`) that can transfer out any residual native ETH (and stray ERC-20 balances) to a designated beneficiary. Alternatively, restrict `receive()` to only accept ETH from a known, trusted caller (e.g., the gateway) to prevent unrelated ETH from landing in the contract in the first place.

### Proof of Concept
1. Deploy `CallDispatcher` as done for `IntentGatewayV2`'s `_params.dispatcher`.
2. From any EOA, call `address(callDispatcher).call{value: 1 ether}("")` — this succeeds because of the unrestricted `receive()`.
3. Observe `address(callDispatcher).balance == 1 ether`.
4. Attempt to locate any function on `CallDispatcher` capable of transferring this balance out — none exists; `dispatch()` only forwards `value` specified in caller-supplied `Call[]` structs and cannot be used to sweep the contract's own balance to an arbitrary recipient without a corresponding target contract call that itself forwards it back, which is not guaranteed for arbitrary transferred ETH.
5. The 1 ETH remains permanently locked in `CallDispatcher` with no recovery path.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
