### Title
`DirectBridge.describeWithdrawal` reports "completed" for all batched NEP-141 withdrawals sharing a NEAR intent tx, ignoring per-`ft_withdraw`-action outcome - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Finding Description
The claimed equality is: `describeWithdrawal({index: i}).status === 'completed'` should equal "the i-th `ft_withdraw`/`native_withdraw` action inside `tx.hash` actually delivered funds on NEAR." In `DirectBridge.describeWithdrawal` this equality is broken unconditionally: [1](#0-0) 

The method ignores `args.index` entirely and returns `{ status: "completed", txHash: args.tx.hash }` for every `WithdrawalIdentifier`, without querying the NEAR RPC for the actual receipt/promise outcome of that specific action.

Root cause: `createWithdrawIntentPrimitive` builds `ft_withdraw` intents that use `ft_transfer`/`ft_transfer_call` as an outbound cross-contract promise from `intents.near`. The contract schema explicitly documents that these transfers are not guarded against partial failure: "NOTE: No refund will be made in case of insufficient `storage_deposit` on `token` for `receiver_id`" [2](#0-1) . This confirms that on NEAR, a `ft_transfer`/`ft_transfer_call` promise created as part of `execute_intents` can fail (e.g., insufficient storage on the receiver) without reverting the top-level transaction that contains multiple withdrawal actions — the outer tx can still report `SUCCESS` while an individual nested promise/receipt fails.

Because `describeWithdrawal` short-circuits to `'completed'` using only `args.tx.hash` (shared across every batched `DirectBridge` withdrawal in the same intent), a batch containing two `ft_withdraw`/`native_withdraw` actions to two different `receiver_id`s will have both `describeWithdrawal({index:0})` and `describeWithdrawal({index:1})` return the exact same `{status:'completed', txHash: tx.hash}`, even if one receiver-side transfer silently failed at the NEAR runtime while the other succeeded.

No other guard in the reachable path compensates for this: `validateWithdrawal` only validates the destination address format/existence at intent-creation time [3](#0-2) , and `createWithdrawalIdentifier` simply copies the shared `tx` into every identifier without any per-index differentiation [4](#0-3) . Unlike `PoaBridge.describeWithdrawal`, which calls an external status API and matches per-asset outcome before reporting `'completed'` [5](#0-4) , or `OmniBridge`, which fetches a `getTransfer` record with a `finalised` field carrying the actual destination-chain tx hash before reporting completion, `DirectBridge` never inspects the actual NEAR receipt outcome for the specific action it is describing.

### Impact Explanation
An integrator relying on `sdk.createWithdrawalCompletionPromises`/`describeWithdrawal` (per the batch-withdrawal design in `docs/design/rfc-batch-withdrawal-granular-control.md`) to track per-index settlement will be told both withdrawals in a `DirectBridge`-routed batch are `completed`, even though only one NEP-141 transfer promise actually succeeded. This is a status/hash misreport causing the integrator to credit/mark-settled a withdrawal whose destination-side transfer failed, matching the High severity category ("a status or hash misreport making an integrator credit or refund twice"). The user's funds may remain stuck inside `intents.near` (debited from the intents balance but never delivered to the NEAR receiver), while the integrator's bookkeeping shows it as delivered — losing track of an unpaid destination.

### Likelihood Explanation
Preconditions: two or more `nep141`-derived DirectBridge (`RouteEnum.NearWithdrawal`) withdrawals batched into the same intent/transaction, targeting different `receiver_id`s, where at least one receiver lacks sufficient NEP-141 storage deposit (a state fully controllable by a counterparty/attacker supplying `destinationAddress`). This requires no privileged access — any unprivileged NEAR Intents user or a counterparty providing a `destinationAddress` string that the integrator forwards can trigger the storage-insufficiency condition for one of the two withdrawal legs. The path is reachable through standard, public SDK usage (`createWithdrawalIntents` + `describeWithdrawal`), and is repeatable for every batched multi-DirectBridge-withdrawal intent.

### Recommendation
`DirectBridge.describeWithdrawal` should verify the actual on-chain outcome for the specific `index`'s withdrawal action rather than assuming success from the shared `tx.hash`. This requires fetching the NEAR transaction/receipt outcomes for `args.tx.hash`, locating the specific `ft_transfer`/`ft_transfer_call`/`native_transfer` receipt corresponding to `args.index`'s `receiver_id`/`token`/`amount`, and inspecting its `SuccessValue`/`Failure` status before reporting `'completed'`. If the specific receipt cannot be confirmed as successful, return `'pending'` or `'failed'` instead of unconditionally `'completed'`.

### Proof of Concept
```typescript
// direct-bridge.test.ts
import { describe, it, expect } from "vitest";
import { DirectBridge } from "./direct-bridge";
import { Chains } from "../../lib/caip2";

describe("DirectBridge.describeWithdrawal batch misreport", () => {
  it("reports 'completed' for both indices sharing the same tx.hash regardless of per-action outcome", async () => {
    const bridge = new DirectBridge({
      envConfig: {} as any,
      nearProvider: {} as any, // never queried by describeWithdrawal — proves no outcome check occurs
    });

    const sharedTx = { hash: "shared-near-intent-tx-hash", accountId: "user.near" };

    const wid0 = bridge.createWithdrawalIdentifier({
      withdrawalParams: {
        assetId: "nep141:tokenA.near",
        amount: 100n,
        destinationAddress: "receiverA.near", // succeeds on NEAR
        feeInclusive: false,
      },
      index: 0,
      tx: sharedTx,
    });

    const wid1 = bridge.createWithdrawalIdentifier({
      withdrawalParams: {
        assetId: "nep141:tokenB.near",
        amount: 200n,
        destinationAddress: "receiverB.near", // fails on NEAR (insufficient storage)
        feeInclusive: false,
      },
      index: 1,
      tx: sharedTx,
    });

    const result0 = await bridge.describeWithdrawal(wid0);
    const result1 = await bridge.describeWithdrawal(wid1);

    // Both report identical 'completed' status + txHash despite index 1's
    // actual receiver-side transfer having failed on NEAR — no RPC/receipt
    // check was ever performed (nearProvider mock untouched).
    expect(result0).toEqual({ status: "completed", txHash: sharedTx.hash });
    expect(result1).toEqual({ status: "completed", txHash: sharedTx.hash });
  });
});
```

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
