## Title
Webhook Shop Identity Spoofing — HMAC signs only the raw body, not the `shop-domain` header, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` value that is handed to the app's webhook handler — and that the app is expected to trust to know *which tenant* the event belongs to — is read straight from an HTTP header that is **not** included in the signed data. This breaks the intended identity binding `HMAC_valid(raw_body) == authentic(shop, raw_body)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` (and the underlying `validate_signature`) verifies the HMAC using `verifiable_query.to_signable_string`, i.e. the raw body only: [3](#0-2) 

`Registry.process` treats a valid HMAC as sufficient authentication, then dispatches to the handler using `request.shop` verbatim, taken from the unsigned header: [4](#0-3) 

Because the HMAC covers only the body, any request whose body+hmac pair was legitimately produced by Shopify for **shop A** remains "HMAC valid" even if the `shop-domain` header is changed to **shop B**. An unprivileged user who has installed the app on their own store (shop A) can capture one of their own legitimately delivered webhooks (valid `raw_body` + valid `hmac`), then replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (shop B). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the handler with `shop: "B"` and the attacker's chosen body content, even though Shopify never actually signed that combination of shop + body together.

The security property the app relies on — "an HMAC-valid webhook proves this event genuinely belongs to `request.shop`" — does not hold, because `shop` is not part of the signed payload.

### Impact Explanation
This lets an attacker (a normal merchant who merely installed the target app) inject forged, HMAC-"valid" webhook events attributed to a victim shop of their choosing. Depending on how the host application's handlers use `WebhookMetadata#shop` (e.g., to route `orders/create`, `app/uninstalled`, `shop/update`, GDPR data-request events, or to look up/mutate per-shop records), this enables cross-tenant data corruption/injection — the attacker's chosen webhook body is processed as if it originated from and is scoped to a shop they do not control or own. This matches the Critical "cross-tenant access" impact category, since the binding between authenticated bytes and shop identity is broken at the library level and the host app has no way to detect the spoof through this gem's API.

### Likelihood Explanation
Likelihood is realistic but requires two things: (1) the attacker must be an existing installer/merchant of the vulnerable app on some shop so they can capture at least one legitimate `(raw_body, hmac)` pair, and (2) the app's webhook endpoint must be reachable from the internet without additional shop verification (the documented usage pattern in `docs/usage/webhooks.md` shows exactly this pattern — calling `Registry.process` directly on the raw request with no additional shop check). No access to `api_secret_key`, access tokens, or TLS interception is required — only normal use of the gem's documented `Registry.process` API path.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified against the HMAC, or otherwise cryptographically bind the `shop` header to the payload before trusting it (e.g., have `VerifiableQuery#to_signable_string` for webhooks also canonicalize/include the relevant headers actually used downstream, matching how Shopify computes/validates webhook signatures). At minimum, update `Webhooks::Request#to_signable_string` / `HmacValidator` so verification fails if headers used by `WebhookMetadata` (particularly `shop`) can be altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint: `raw_body = B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `B` and `H` (they own the request, e.g., via their own reverse proxy/logging).
4. Attacker sends a new POST to the same webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(secret, B)` and finds it equals `H` — validation passes. [4](#0-3) 
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled event data as if it belonged to `victim-shop.myshopify.com`.
