### Title
Webhook HMAC Covers Only the Raw Body, Not the Shop Domain Header, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable string used for HMAC verification from the raw request body only, while the `shop` (and `topic`/`webhook_id`) values that are trusted and forwarded to the application's webhook handler are read straight from unauthenticated HTTP headers. This breaks the intended identity binding `shop_verified_by_hmac == shop_used_by_handler`.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are parsed directly from caller-supplied HTTP headers with no cryptographic binding to that value: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only re-computes the signature over `to_signable_string` (the raw body), then immediately trusts `request.shop` and hands it to the application's webhook handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms the comparison is solely against `verifiable_query.to_signable_string`: [4](#0-3) 

Because the app's HMAC secret (`Context.api_secret_key`) is shared across **all** shops that install the app (it is not a per-shop secret), any genuine webhook delivery the attacker receives for their own store yields a `(raw_body, hmac)` pair that is valid for that exact body regardless of which shop it is claimed to be from. The `shop-domain` header is never part of the signed material, so an attacker who legitimately installs the app on their own store can capture a real webhook (body + valid HMAC) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `Registry.process` will accept it — the HMAC check passes because it never examined the shop — and the handler will run believing the event belongs to the victim tenant, with `WebhookMetadata#shop` set to the attacker-chosen value: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" bind break: the equality that should hold is `hmac_verified_scope == shop_dispatched_to_handler`, but only the body is inside `hmac_verified_scope`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (from `Registry.process`) to key per-tenant lookups, writes, cache invalidation, or session selection is exposed to cross-tenant data confusion: an attacker-controlled webhook body can be attributed to an arbitrary victim shop domain. Depending on how the host application consumes `data.shop`, this can lead to cross-tenant state corruption (e.g., writing attacker-controlled order/product/customer data into a victim shop's records) — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite is only that the attacker be an ordinary Shopify merchant/developer able to install the target app on their own store (a fully unprivileged, publicly available action) and observe at least one genuine webhook delivery to capture a valid `(body, hmac)` pair. No access to `api_secret_key`, access tokens, or any privileged account is required, and no TLS interception is needed since the attacker is the legitimate recipient of their own webhook. The gem performs no defense against this because `shop`, `topic`, and `webhook_id` are structurally outside the signed payload.

### Recommendation
- Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-signed material verified by `HmacValidator`, or independently verify that the `shop-domain` header matches the shop associated with the session/subscription that the webhook was registered for.
- At minimum, document/require host applications to cross-check `WebhookMetadata#shop` against a known set of shops that have this specific webhook subscription/id registered before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`), receiving a legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
2. Attacker replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` while keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares it to `H` — it matches, since `to_signable_string` never included the shop domain (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The registered handler executes with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's own shop (`lib/shopify_api/webhooks/registry.rb:198-199`).
