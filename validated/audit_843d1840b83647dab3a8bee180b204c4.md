### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body alone, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the raw body's HMAC matches, then hands the header-derived `shop` value straight to the host application's handler as trusted identity data. Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (not shop-specific), any raw body with a valid signature can be replayed with an attacker-chosen `x-shopify-shop-domain` header, breaking the binding between "bytes verified by HMAC" and "shop attributed to that payload."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read verbatim from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `raw_body` only) and, if it passes, immediately builds `WebhookMetadata` using `request.shop` taken from that same unverified header, passing it to the host app's handler as authoritative shop identity: [3](#0-2) 

`HmacValidator.validate` only compares `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC — it has no knowledge of, and does not bind to, the `shop` field: [4](#0-3) 

The broken identity-binding equality is:
`verified(HMAC over raw_body, api_secret_key) == true` is treated as proof that `shop = header["x-shopify-shop-domain"]` is authentic, when in fact the HMAC only proves the *body* bytes were signed with the app's secret — it says nothing about which shop the payload is "for."

Because `api_secret_key` is a single app-level secret shared by all merchants who install the app (this is confirmed by the OAuth/webhook code, which always signs/verifies with the same `Context.api_secret_key` regardless of shop, e.g. in `HmacValidator.validate`), any body/HMAC pair that is valid for one shop is valid for every shop. An attacker who controls a shop that has installed the app can:
1. Trigger a real webhook delivery to their own endpoint for their own shop (a legitimate action they're fully authorized to do), capturing a `(raw_body, hmac)` pair that will validate successfully.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim merchant's shop domain.
3. `Registry.process` validates the HMAC (still valid, since it only checks `raw_body`) and calls the handler with `WebhookMetadata#shop` set to the victim's domain, even though the payload actually originated from the attacker's own shop.

This is a genuine cross-tenant identity-binding break in this gem's own webhook-processing code — the host application never has a chance to catch this because the gem presents `request.shop` as verified data once `HmacValidator.validate` returns `true`.

### Impact Explanation
Host applications built on this gem's documented pattern (`ShopifyAPI::Webhooks::Registry.process` → handler receives `WebhookMetadata#shop`) rely on `shop` as an authenticated tenant identifier to route webhook data (e.g., decide which merchant's session/store to update, invalidate, or act upon). An attacker can force the app to process attacker-controlled webhook content under a victim shop's identity, causing cross-tenant data corruption/impersonation in the host app's persisted state (e.g., triggering uninstall/GDPR-type logic, cache invalidation, or state changes attributed to a shop the attacker doesn't own) purely by exploiting this gem's failure to bind `shop` to the HMAC-covered bytes. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged, low-tier attacker (any merchant who installs the app) make the app treat their forged data as belonging to another tenant.

### Likelihood Explanation
Likelihood is high: exploitation only requires the attacker to install the target app on their own store (a normal, unprivileged action), capture one legitimate webhook body+HMAC, and resend it with a modified shop-domain header — no credentials, tokens, or secrets belonging to the victim or the app are required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signed payload, so that `HmacValidator.validate` fails whenever the shop-domain header has been altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`) pointing to the target app's webhook endpoint.
2. Attacker triggers the webhook naturally (e.g., creates an order in their own store) and captures the raw POST: body `B`, and headers including `x-shopify-hmac-sha256: H` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (leaving body `B` and `x-shopify-hmac-sha256: H` untouched).
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` — identical to `H` — and returns `true`, since the shop header is never part of `to_signable_string`.
5. `ShopifyAPI::Webhooks::Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)`, causing the host app to act on attacker-controlled data as if it came from `victim.myshopify.com`.
