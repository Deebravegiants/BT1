### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once the HMAC check passes, and hands the caller's handler a `WebhookMetadata` object built from `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`. However the HMAC signature only covers the raw request body — it never binds the shop, topic, or webhook id — so any of these fields can be freely rewritten by an attacker while keeping a genuinely-signed body, breaking the implicit equality the gem's own documentation promises: "signed shop == reported shop."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then unconditionally forwards the unauthenticated header-derived `shop` to the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and the app's single, app-wide `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is one shared secret for the entire app (not per-shop), *every* shop that has installed the app receives webhooks whose bodies are signed with the same key. This means the equality the gem implicitly claims to guarantee —

`hmac_valid(body) == true` implies `shop header == the shop that produced this body`

— does not hold. The `shop-domain` header is acted upon (passed to the handler, typically used to look up which shop/session the event belongs to) but is not covered by the HMAC.

The gem's own docs assert the opposite guarantee, telling integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is simply "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

### Impact Explanation
Any merchant/tenant who has installed the app can legitimately trigger a webhook for their own store (e.g. `orders/create`), capture the genuine raw body and `X-Shopify-Hmac-Sha256` value (from their own dev tunnel logs, proxy, or webhook delivery logs), and then POST that exact body/HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a *different* tenant. `Registry.process` will accept it (HMAC still validates, since it only checks the body) and hand the handler `WebhookMetadata` claiming the event belongs to the victim shop. Any host application following the documented pattern (looking up the victim's session/data by `data.shop` and acting on the attacker-controlled body) processes cross-tenant, attacker-influenced data as if it were the victim's own event — a cross-tenant integrity/confusion vulnerability rooted directly in this gem's verification contract.

### Likelihood Explanation
Requires only that the attacker have (or create) their own store installing the target app — no `api_secret_key`, access token, or privileged account is needed, since the app-wide secret only needs to sign *some* body the attacker can legitimately obtain via their own shop's webhook traffic. The gem provides no mechanism, option, or documented caveat instructing consumers that `shop`/`topic`/`webhook_id` are unauthenticated, so any implementation that follows the documented usage in `docs/usage/webhooks.md` is exposed.

### Recommendation
Bind the identity fields into the signed payload verification, e.g. require the host application to independently verify that the shop derived from `X-Shopify-Shop-Domain` corresponds to a session/store the app actually expects for this specific webhook subscription (e.g. cross-check against a per-shop webhook secret, or validate the shop via a separate authenticated channel such as re-querying Shopify for webhook ownership) rather than presenting the header value as a verified fact in `WebhookMetadata`. At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata`'s documentation to explicitly warn that `shop`, `topic`, and `webhook_id` are **not** covered by the HMAC and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g. updates an order) and captures the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header that Shopify sent to the app's webhook endpoint (via their own reverse proxy/tunnel logs).
3. Attacker sends a new HTTP POST directly to the app's public webhook URL with:
   - Body: exactly `B` (unchanged, so `H` still validates against `Context.api_secret_key`)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally also altered
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as an authenticated event for a tenant the attacker does not own.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
