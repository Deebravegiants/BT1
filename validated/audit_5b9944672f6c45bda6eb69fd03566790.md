### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version` and `webhook_id` are read directly from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates only that the body matches the HMAC and then dispatches the handler using the unauthenticated `shop` and `topic` header values, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from headers that are not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.topic` and `request.shop` to dispatch to a handler and build `WebhookMetadata`: [3](#0-2) 

Because the app's `api_secret_key` is shared across every shop that installs the app, and the HMAC only ever covers the body, the binding that should hold is:
`hmac == HMAC(secret, body) AND body identifies shop == header shop-domain`.
In this implementation the second half is never checked — only `hmac == HMAC(secret, body)` is verified. A merchant who has installed the app receives at least one legitimate `(raw_body, hmac)` pair addressed to their own shop. That merchant can replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`) headers for a different tenant, and the HMAC check still passes because it never inspected those headers.

### Impact Explanation
This breaks the shop-identity binding of the webhook, causing the app's webhook handler to run business logic (e.g. mandatory `customers/redact`, `customers/data_request`, `shop/redact`, or any other registered handler) attributed to an arbitrary victim shop that also uses the app, i.e., cross-tenant access initiated by an unprivileged (but installed) merchant, without needing the `api_secret_key`, an access token, or any other privileged credential — they only need one webhook that Shopify already delivered to their own store.

### Likelihood Explanation
Likelihood is realistic for any app that installs on multiple shops sharing one `api_secret_key` (the normal case for public apps): every legitimate webhook delivery gives the attacker a valid `(body, hmac)` pair they can freely re-address to a different tenant since `shop`/`topic` are unauthenticated headers.

### Recommendation
Bind the shop (and ideally topic) into the signed payload check, e.g., require `Registry.process` to receive the expected shop from a caller-supplied, out-of-band value and assert it against `request.shop` before dispatch, or otherwise fold `shop-domain`/`topic` into the HMAC comparison so a replay with altered headers is rejected.

### Proof of Concept
1. App is installed on shop A and shop B, sharing a single `api_secret_key`.
2. Shopify sends a legitimate webhook to the app for shop A: headers `shopify-shop-domain: shop-a.myshopify.com`, `shopify-topic: customers/data_request`, `shopify-hmac-sha256: <valid-hmac-of-body>`, plus `raw_body`.
3. The attacker (owner/operator of shop A's endpoint infrastructure, or anyone who can intercept/replay their own shop's webhook traffic) resends the identical `raw_body` and `shopify-hmac-sha256` value, but changes `shopify-shop-domain` to `shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` still passes because it only recomputes the HMAC over `raw_body`.
5. The handler is invoked with `shop: "shop-b.myshopify.com"`, causing the app to execute shop-B-attributed logic (e.g. redaction/data-request processing) using data crafted by the attacker for shop A. [3](#0-2)
