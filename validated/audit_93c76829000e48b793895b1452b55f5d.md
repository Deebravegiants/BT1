### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC signature exclusively from the raw request body via `to_signable_string`, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler as the tenant identity. Because the client secret used to compute/verify the HMAC is shared across every shop that has installed the app, any holder of one valid `(body, hmac)` pair can replay it to the same endpoint with a forged `shop-domain` header, and `HmacValidator.validate` will still report success while attributing the event to an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` and compares it against the received `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body` — none of the identifying headers are part of the signed content: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all taken verbatim from client-supplied headers (`shopify-shop-domain` / `x-shopify-shop-domain`, etc.) with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` only checks the HMAC of the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` and hands them to the app's handler as the authoritative tenant identity for the event: [4](#0-3) 

The handler contract (`WebhookMetadata`) treats `shop` as a trusted field of equal standing to `topic` and `body`, with no separate verification: [5](#0-4) 

This breaks the identity binding **`shop attributed to the event == shop that produced the HMAC-verified bytes`**. In this gem, HMAC validity proves only "this body was signed with the app's `client_secret`" — a secret shared by *every* shop that has the app installed — it proves nothing about which shop the body/headers actually belong to. An unprivileged internet user who controls (or installs) any shop running the target app can:
1. Trigger a legitimate webhook to their own endpoint for their own shop, capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair.
2. Replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain/ids.
3. `HmacValidator.validate` still succeeds (it never looked at the headers), so `Registry.process` dispatches to the handler with `WebhookMetadata#shop` equal to the victim shop.

Any host application that follows the gem's documented pattern of using `data.shop` to look up the victim's `Auth::Session`/access token or to key per-tenant data (the intended and only way `shop` is meant to be consumed, since the gem provides no other tenant check) is deceived into performing that operation for the wrong tenant — i.e., cross-tenant access using a forged shop identity that never crossed a real trust boundary the gem enforces.

### Impact Explanation
This meets the Critical bar of "cross-tenant access": the same signature-verification result covers arbitrary shop attribution because the client secret is app-wide, not shop-specific, and the gem offers no additional binding (e.g., signing the shop domain, or cross-checking `shop` against a known session) between the verified bytes and the tenant identity forwarded to application code.

### Likelihood Explanation
Medium-to-High: any developer/attacker can install the target app on their own (even free/dev) Shopify store, which is enough to legitimately receive one valid `(body, hmac)` pair for that app's shared `client_secret`. No access token, `client_secret`, or privileged account for the *victim* is required — only ordinary use of the app as any tenant.

### Recommendation
Bind the tenant identity into the verified content instead of trusting an unauthenticated header:
- Include the `shop` header (and ideally `topic`/`webhook_id`) in the signable string used for HMAC computation in `Webhooks::Request#to_signable_string`, matching what is actually signed by Shopify if Shopify includes it, or otherwise cross-validate `shop` against the destination endpoint/registration path so a body signed for shop A cannot be replayed while claiming to be from shop B.
- At minimum, document/require that `Registry.process` callers additionally reconcile `data.shop` against the shop tied to the specific registered webhook endpoint/path, rather than trusting the header unconditionally once HMAC-of-body succeeds.

### Proof of Concept
1. Install the target Shopify app on attacker-owned dev store `attacker.myshopify.com`; trigger any subscribed webhook (e.g. `orders/create`) to capture `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>`.
2. Send a request to the app's webhook endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but with:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic`/`x-shopify-webhook-id` unchanged or forged
3. Server-side, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
```
which succeeds because `HmacValidator` only re-hashes `raw_body` with the app's `client_secret` — identical to step 1 — regardless of the `shop` header value.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, i.e., attacker-controlled data processed under the victim's tenant identity, confirming the cross-tenant identity break.
