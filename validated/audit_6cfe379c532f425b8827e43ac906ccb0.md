### Title
Session-key `SelectSolver` signature does not bind fill amounts, allowing a selected solver to bait-and-switch the escrowed intent order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.select()` and `fillOrder()` are independent `public` functions [2](#0-1) . The EIP-712 message a user's session key signs to authorize a winning solver only commits to `(commitment, solver)` [1](#0-0) , never to the specific output amounts that made that solver's bid attractive. The SDK's off-chain flow presents solvers' bids (`outputs`, `relayerFee`, USD value) via `Bid.outputs`/`outputUsdValue()` and only signs after the user picks the best one [3](#0-2) , but on-chain `fillOrder` only enforces the order's minimum required amounts (`solverAmount >= totalRequired`), never that the selected solver actually delivers the amount it bid [4](#0-3) .

### Finding Description
This is the same trust-boundary failure as the external report: a user is asked to authorize an action (selecting a solver) based on displayed parameters (the bid's promised output amounts) that are not the parameters actually bound by the signature they produce. The `SelectSolver` typehash `SelectSolver(bytes32 commitment,address solver)` [1](#0-0)  is exactly what the session key signs in `CryptoUtils.signSolverSelection` [5](#0-4) , and this signature is what `select()` verifies to authorize `msg.sender` as the solver for that commitment (stored via transient storage) [6](#0-5) . Nothing in the signed payload, nor in `fillOrder`'s validation, ties the authorization to the bid's advertised `outputs`. `fillOrder` only requires `options.outputs[i].token == order.output.assets[i].token` and `solverAmount >= totalRequired` (the order's baseline minimum, not the bid amount) [7](#0-6) , and the same pattern holds in cross-chain fills [4](#0-3) .

Because `select` and `fillOrder` are ordinary `public` functions rather than being cryptographically bound together as a single ERC-4337 UserOperation, an authorized solver is not actually forced to submit the exact fill it bid. The `SolverAccount`/ERC-4337 bundler path binds solver+session signatures to one immutable, pre-signed `userOp.callData` [8](#0-7) , which does close this gap for solvers who go through that path. However, since `select()`/`fillOrder()` remain independently callable on the base contract, any account holding a valid `(commitment, solver)` session signature and matching solver identity can call `select()` and then `fillOrder()` directly with a different, lower-value `FillOptions.outputs` (down to the order's bare minimum) instead of the amount that won the auction — collecting the same escrowed input tokens while shorting the user on the promised output.

### Impact Explanation
A user selects a solver based on a specific promised output amount (often above the order minimum, since solvers compete on price). The chosen solver can instead deliver only the contractual minimum and keep the difference, defrauding the order's beneficiary of the surplus they were shown and relied upon when signing. This is a concrete loss-of-funds/value scenario for the escrow beneficiary, reachable by any solver that has already won selection — an unprivileged, ordinary participant in the intents flow.

### Likelihood Explanation
Likelihood is bounded by whether solvers use the SolverAccount/ERC-4337 batched path (which incidentally binds calldata) versus calling `select`/`fillOrder` as ordinary EOAs/contracts. Nothing in `IntentGatewayV2` enforces that a selected solver must transact through `SolverAccount`; both entry points are `public`. Any solver willing to under-deliver after winning selection can exploit this without needing any privileged position, cross-chain proof forgery, or governance compromise.

### Recommendation
Bind the fill amounts (and other economically relevant `FillOptions` fields) into the `SelectSolver` EIP-712 struct that the session key signs — e.g., `SelectSolver(bytes32 commitment, address solver, bytes32 outputsHash)` — and require `fillOrder` to verify that its `options.outputs` (and `relayerFee`/`nativeDispatchFee`) hash matches the one embedded in the stored, verified selection before releasing escrow. This closes the gap for any call path, not just the ERC-4337 batched one.

### Proof of Concept
1. User places an order with `order.session` set to a disposable session key, and solver selection enabled (`_params.solverSelection == true`).
2. Two solvers bid off-chain; Solver A's `FillerBid.userOp.callData` advertises `options.outputs[0].amount = 150` (order minimum is 100). The SDK surfaces this as `Bid.outputs` and it wins the auction as the "best" bid via `sortBids`/`outputUsdValue` [3](#0-2) .
3. The user's session key signs `SelectSolver(commitment, solverA)` — this signature says nothing about the amount 150 [5](#0-4) .
4. Instead of submitting the pre-agreed UserOperation through the bundler, Solver A (an EOA under its own control) calls `IntentGatewayV2.select(SelectOptions{commitment, solver: solverA, signature})` directly, then in the same or a subsequent transaction calls `fillOrder(order, FillOptions{outputs:[{token, amount: 100}], ...})`.
5. `fillOrder` accepts this because `solverAmount (100) >= totalRequired (100)` [7](#0-6) ; Solver A receives the full escrowed input while delivering only the order minimum instead of the 150 it bid and was selected for.

	static async signSolverSelection(
		commitment: HexString,
		solverAddress: HexString,
		domainSeparator: HexString,
		privateKey: HexString,
	): Promise<HexString | null> {
		const account = privateKeyToAccount(privateKey as Hex)

		const structHash = keccak256(
			encodeAbiParameters(
				[{ type: "bytes32" }, { type: "bytes32" }, { type: "address" }],
				[SELECT_SOLVER_TYPEHASH, commitment, solverAddress],
			),
		)

		const digest = keccak256(concat(["0x1901" as Hex, domainSeparator as Hex, structHash]))
		const signature = await account.sign({ hash: digest })

		return signature as HexString
	}
