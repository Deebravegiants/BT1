### Title
Unvalidated swap routes can execute attacker-chosen contracts under the caller’s authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
The controller accepts caller-supplied route bytes and forwards them to the configured swap router without constraining which venues or contracts the route may invoke. A malicious route can therefore place an attacker-controlled contract inside a `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` call and have that contract request token transfers from the caller. If the wallet signs the authorization tree produced by simulation, the malicious venue can transfer unrelated wallet assets to the attacker.

### Finding Description
The vulnerable path is reachable through the public `swap_collateral` entrypoint, whose caller-controlled `swap: Bytes` argument is passed to `process_swap_collateral`. [1](#0-0) 

That strategy withdraws the caller’s collateral and routes it through `withdraw_and_swap_from_supply`, which reaches `swap_tokens`. [2](#0-1) 

`swap_tokens` validates only that the route is nonempty, snapshots the controller’s input and output balances, authorizes one exact input-token transfer to the configured router, and invokes `execute_strategy` with the uninspected route payload. [3](#0-2) 

The post-call checks bound only the controller’s own `token_in` spend and require a positive `token_out` balance increase. They do not identify, allowlist, or constrain contracts invoked by the route. [4](#0-3) 

Consequently, an attacker can construct a route whose venue is an attacker-deployed contract. That contract can call `transfer(victim, attacker, amount)` on an unrelated token held by the victim; because the venue executes beneath the victim’s controller authorization, the host records the malicious transfer as a child invocation of the victim’s `swap_collateral` authorization. [5](#0-4) [6](#0-5) 

The same missing route constraint applies to the other strategy entrypoints that accept `swap: Bytes`: `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
This permits theft of user funds beyond the collateral supplied to the strategy. A victim who signs a poisoned authorization tree can lose arbitrary amounts of arbitrary wallet tokens selected by the malicious venue, while the controller still observes a valid positive swap output and final account state. [10](#0-9) 

The exploit is not limited to the routed input amount because the malicious child transfer names the victim’s wallet token, attacker recipient, and amount independently. [11](#0-10) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and construct the malicious route bytes. The route can still provide a fair-looking output, so controller-side output and risk checks do not distinguish it from a legitimate route. [4](#0-3) [12](#0-11) 

Execution requires the victim to sign the expanded authorization tree containing the malicious transfer. An honest authorization tree without that child causes the unauthorized transfer to fail, but signing the simulated tree makes the theft succeed. [13](#0-12) 

### Recommendation
Enforce a venue allowlist or cryptographically pinned venue registry for every external contract a route may invoke. Reject routes naming unapproved pool, token, or venue addresses before execution. In addition, surface and require exact authorization-tree expectations for strategy calls so unexpected child invocations cannot be silently accepted as part of a route.

### Proof of Concept
The repository’s `rogue_hop_pool_transfer_joins_caller_auth_tree` test demonstrates the exploit shape:

1. Alice supplies USDC and holds an unrelated wallet token.
2. The router receives controller-authorized swap input and invokes the route-selected `hop_pool`.
3. The attacker-controlled `RogueHopPool::swap` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
4. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization.
5. When Alice signs the recorded tree, the transaction succeeds: Alice’s unrelated wallet balance becomes zero, the attacker receives the balance, and Alice still receives the expected swapped collateral. [12](#0-11) [14](#0-13)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
