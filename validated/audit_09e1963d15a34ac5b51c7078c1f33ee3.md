## Title
Missing per-order relayer authorization gate allows any relayer to force escrow withdrawal outcomes in `IntentGatewayV2` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The Tron variant of `IntentGatewayV2.onAccept`/`onGetResponse` lacks the `_checkRelayer` authorization gate that the equivalent EVM contract `ExtrinsicIntents.sol` enforces on every incoming cross-chain message before decoding its body, matching the OpenClaw bug class of "misconfigured input paths that skip cross-provider requester authorization."

## Finding Description
In `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, both `onAccept` and `onGetResponse` call `_checkRelayer(incoming.relayer)` as the very first action after the `onlyHost` modifier, before any request body is decoded or acted on: [1](#0-0) [2](#0-1) 

This design decision is documented explicitly: only the authorized relayer's delivery is allowed to reach body decoding/authentication; any other relayer's delivery reverts with `Unauthorized` and leaves no receipt, keeping the message retryable by the correct relayer. [3](#0-2) 

The Tron contract `evm/tron/contracts/apps/IntentGatewayV2.sol`, however, implements the analogous `onAccept` and `onGetResponse` callbacks without this `_checkRelayer` gate — it goes straight from the `onlyHost` modifier into decoding `RequestKind` and calling `authenticate`/`withdraw`, with no relayer-identity check anywhere in the file: [4](#0-3) [5](#0-4) 

The contract has no `_relayer` storage variable, `setRelayer` function, or any relayer-restriction logic — confirmed by exhaustive `grep` across the file for `_relayer`, `setRelayer`, `_checkRelayer`, and `onlyRelayer`, all of which return no hits in `IntentGatewayV2.sol` (Tron), unlike its EVM counterpart which gates every `onAccept`/`onGetResponse` invocation on the authorized relayer address.

Since `HandlerV2`/`EvmHost.dispatchIncoming` is permissionless — any address can submit a valid consensus/state proof and become the `relayer` field passed into `onAccept` — the missing gate means the Tron gateway's `RedeemEscrow`/`RefundEscrow`/`NewDeployment`/`UpdateParams`/`SweepDust` handling is reachable by whichever untrusted party relays the message first, rather than only the gateway's designated trusted relayer as intended by the analogous EVM contract's design.

## Impact Explanation
On the EVM side, the relayer gate exists specifically to prevent an unauthorized/adversarial relayer from being the first to deliver governance-sensitive or escrow-affecting requests (`NewDeployment`, `UpdateParams`, `SweepDust`, `RedeemEscrow`, `RefundEscrow`) — and the design docs explicitly call out the risk of a forged/compromised relayer path being used to trigger these effects. In the Tron contract this control is absent, so any relayer able to produce a valid consensus/state proof for a request addressed to the Tron `IntentGatewayV2` can be first to deliver `RedeemEscrow`/`RefundEscrow` withdrawals, or (for hyperbridge-sourced governance actions) at least races the legitimate relayer without a check that would otherwise reject non-authorized deliveries. This directly weakens funds-handling logic (escrow release paths) at the delivery layer.

## Likelihood Explanation
Handler delivery is permissionless by protocol design — `HandlerV2.handlePostRequests`/`handleGetResponses` accept any `msg.sender` as the relayer once the state/consensus proof verifies. Reaching `IntentGatewayV2.onAccept` on Tron requires only a single relayed proof; no privileged role is needed to trigger the missing-gate condition.

## Recommendation
Add the same `_checkRelayer(incoming.relayer)` gate (or equivalent authorized-relayer check) at the top of `onAccept` and `onGetResponse` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, so only the designated relayer's delivery is accepted before any request body is decoded or acted upon.

## Proof of Concept
1. An untrusted party observes (or produces) a valid consensus/state proof for a `PostRequest`/`GetResponse` addressed to the Tron `IntentGatewayV2` instance (e.g., a `RedeemEscrow`/`RefundEscrow` body).
2. They call `HandlerV2.handlePostRequests`/`handleGetResponses` (permissionless) themselves as `_msgSender()`, becoming the `relayer` in `IncomingPostRequest`/`IncomingGetResponse`.
3. `EvmHost.dispatchIncoming` calls `IApp.onAccept`/`onGetResponse` on the Tron gateway; because no `_checkRelayer` gate exists there (unlike `ExtrinsicIntents.sol`), the call proceeds directly to `authenticate`/`withdraw`, executing the escrow withdrawal/governance logic without verifying the caller is the gateway's intended trusted relayer.

**Note on confidence:** I could not fully confirm whether the Tron `IntentGatewayV2` was intentionally designed without a relayer whitelist (i.e., it may be an intentionally "open" relayer model for that chain) versus an accidental omission relative to the EVM `ExtrinsicIntents.sol` pattern, since I was unable to locate a Tron-specific design decision doc analogous to `sdk/packages/core/docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too-and-that-does-not-touch.md` confirming intent for the Tron contract specifically.
