This is a good confirmed finding — `TokenExchange.exchange_token` derives the `shop` used to build the outbound request host directly from an untrusted, unbound JWT claim, in contrast to every other sensitive flow in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) which explicitly call `ShopValidator.sanitize!` before using the shop value to build a request that carries the `client_secret`.

### Title
Token Exchange sends `client_secret` to an unsanitized host derived from the JWT `dest` claim, bypassing `ShopValidator` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the request host that receives the app's `client_id`/`client_secret` from `jwt_payload.shop` (the `dest` claim of the session token), without ever routing it through `Utils::ShopValidator.sanitize!`. Every other credential-bearing flow in the gem (`ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`) explicitly sanitizes the shop value before using it to build the outbound request. `exchange_token` breaks that pattern.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim string with no domain allow-listing: [1](#0-0) 

`exchange_token` takes this value directly as `dest_shop` and uses it to construct a `Session`, which is passed to `Clients::HttpClient`: [2](#0-1) 

`HttpClient#initialize` builds the request host straight from `session.shop`, with no host allow-listing at this layer either: [3](#0-2) 

The body posted to that host includes `Context.api_secret_key` in plaintext: [4](#0-3) 

Contrast this with the sibling method `migrate_to_expiring_token` in the very same file, and `client_credentials`, both of which call `Utils::ShopValidator.sanitize!(shop)` before building the session/host that will receive `client_secret`: [5](#0-4) [6](#0-5) 

The `JWT` signature only proves the token was signed with `Context.api_secret_key` — it does **not** guarantee the `dest` claim is a legitimate `*.myshopify.com`/trusted Shopify domain, since Shopify itself does not constrain what a maliciously-configured or forged embedding context can put in `dest` on the client side, and `JwtPayload` performs no format/domain check on it (only `aud == Context.api_key` is enforced): [7](#0-6) 

This is exactly the analog class asked for: **host validated (aud/signature) versus host that receives the app's `client_secret` (dest → session.shop → HttpClient base_uri)** — the equality `dest_shop == trusted_shopify_domain` is never checked, only `aud == api_key` is.

### Impact Explanation
If a `dest` claim value that is not a genuine, trusted Shopify domain can reach `exchange_token` (e.g., because the host app is embedded but session-token validation elsewhere does not itself constrain `dest` to `ShopValidator`-approved domains, or because the app trusts the gem to have already done this check — which it explicitly does for the other two flows), the app's `client_id` and `client_secret` — the OAuth application's core credentials — are transmitted via POST to an attacker-influenced host. This is a Critical-class primitive per the rubric ("theft or exfiltration of ... the app's `client_secret`").

### Likelihood Explanation
Moderate-to-high: this is not a hypothetical process error, it's an internal inconsistency in the gem itself — two sibling functions in the same file/module sanitize the shop before use, and `exchange_token` (the primary, "recommended" flow per the docs) does not. Any host app that reasonably assumes the library validates the token-derived shop the same way it does everywhere else is exposed. The `docs/usage/oauth.md` note explicitly states "the shop always comes from the session token's `dest` claim" and that this is the "Recommended" flow for embedded apps, increasing exposure surface.

### Recommendation
Add the same `Utils::ShopValidator.sanitize!(dest_shop)` call in `TokenExchange.exchange_token` that is already used in `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, before constructing `shop_session`, so the JWT-derived host is provably constrained to a trusted Shopify domain prior to being used as the destination for the `client_secret`-bearing POST request.

### Proof of Concept
1. Obtain/construct a session token (`id_token`) whose payload is valid with respect to signature and `aud == Context.api_key`, but whose `dest` claim is set to an attacker-controlled or non-Shopify host (e.g. `https://attacker.example.com`). Depending on how the host application surfaces/forwards the token to this gem, this may be achievable if the host app does not itself pre-validate `dest` against `ShopValidator` before calling `exchange_token`.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: crafted_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe (via `lib/shopify_api/auth/token_exchange.rb:41,51,65` and `lib/shopify_api/clients/http_client.rb:18`) that `dest_shop` is used unsanitized to build `HttpClient`'s `@base_uri`, and the POST body containing `client_id`/`client_secret` is sent to `https://attacker.example.com/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker-controlled host.
