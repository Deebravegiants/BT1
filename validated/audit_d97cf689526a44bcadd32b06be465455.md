### Title
Custom-token icon fetch/update paths bypass name-collision checks, allowing icon-cache poisoning for existing asset names (e.g. `bitcoin`) - (File: `features/assets-feature/module/assets-module.js`)

### Summary
`AssetsModule#storeIcons` is invoked directly from `fetchToken`, `#fetchTokens`, and `#fetchUpdates` on tokens returned from the remote Custom Token Registry (CTR) API, without the name-collision guard (`this.getAsset(token.name)`) that protects `addRemoteTokens`/`addTokens`/`#handleFetchedToken`. Because the icon cache adapters (`adapters/storage-icons-browser/src/icons-storage.js` and `adapters/storage-icons-mobile/src/icons-storage.js`) key storage solely by `token.name || token.assetName` with no per-asset-identity/origin binding, a malicious/compromised CTR response whose `name` collides with an existing built-in asset (e.g. `bitcoin`) overwrites the single globally-shared icon cache entry that every `walletAccount` reads via `AssetsModule#getIcon`.

### Finding Description
- `AssetsModule#storeIcons` (`features/assets-feature/module/assets-module.js:676-687`) just forwards `tokens` to `this.#iconsStorage.storeIcons(tokens)` with no name/identity check.
- It is called unconditionally on remote data in three places:
  - `fetchToken()` (`assets-module.js:195-241`): if `#getAssetFromAssetId(assetId, baseAssetName)` doesn't match an existing asset (attacker picks an arbitrary `assetId`), the module fetches `networks/${baseAssetName}` from the CTR, normalizes the response (`normalizeToken`, line 235), and calls `await this.#storeIcons([token])` — using whatever `name`/`assetName` the remote response contains, with **no check that this name collides with an existing asset**.
  - `#fetchTokens()` → `getCustomTokensDefinitions()` (`assets-module.js:258-291`): batch-fetches `tokens` from CTR keyed by `assetId`, then calls `await this.#storeIcons(tokens)` directly on the normalized remote tokens — again no name-collision check.
  - `#fetchUpdates()` (`assets-module.js:519-529`): fetches `updates` from CTR for already-tracked custom tokens and calls `await this.#storeIcons(validatedTokens)` directly.
- Contrast this with the actually-guarded path: `#handleFetchedToken` (`assets-module.js:603-612`) checks `const asset = this.getAsset(token.name); if (asset) return { asset, isAdded: false, updates: [] }` before ever adding/persisting a token, and `addRemoteTokens`/`addTokens` only call `#storeIcons` on `fetchedAndHandledTokens` (i.e., tokens that passed this check). The three functions above skip this guard entirely.
- The icon adapters key storage only by name:
  - Browser: `#storeIcon = async (token) => { const assetName = token.name || token.assetName; ...; await this.#iconsStorage.set(assetName, svg) }` (`adapters/storage-icons-browser/src/icons-storage.js:36-40`).
  - Mobile: `#storeIcon` writes to `${this.#iconsDirectory}/${assetName}.svg` (`adapters/storage-icons-mobile/src/icons-storage.js:51-56`).
- `getIcon(assetName)` in `assets-module.js:661-674` trusts the cache blindly once an asset with that name exists: `const asset = await this.getAsset(assetName); if (asset) return this.#iconsStorage.getIcon(assetName)` — it never re-validates that the cached SVG actually corresponds to the built-in/trusted asset, only that *some* asset with that name is registered (true for `bitcoin`, which is always registered as a built-in).
- Because the icon store is a single un-namespaced storage instance shared by the whole wallet process, this affects every `walletAccount` that later calls `getIcon('bitcoin')`.

### Impact Explanation
An attacker who controls (or can inject into) a CTR-style remote token API response can spoof the icon shown for any existing asset name across the entire wallet (all accounts), since the cache write path in `fetchToken`/`#fetchTokens`/`#fetchUpdates` has no protection against colliding with `bitcoin` or any other already-registered asset name. This is an asset/icon identity-spoofing vector (visual UI trust confusion) rather than key/signing compromise, matching a "state confusion / persisted-state authenticity" impact category rather than direct fund loss.

### Likelihood Explanation
- Reachable purely from a remote API/token-list response — no privileged wallet state or user secrets needed, matching the "unprivileged attacker controlling remote API response" precondition.
- `fetchToken`/`fetchTokens` can be triggered by ordinary "search/preview custom token" UI flows or dApp-initiated custom-token lookups before any explicit "add" approval, and `updateTokens()`/`#fetchUpdates` run as part of the normal periodic refresh cycle for already-added custom tokens, with no user interaction.
- The only precondition is that the attacker's crafted response passes `validateCustomToken`/`isValidCustomToken` schema checks (which validate token schema and icon format, not name uniqueness against the built-in registry) — the code has no separate check preventing `name`/`assetName` collisions in these three call sites.

### Recommendation
Apply the same collision guard used in `#handleFetchedToken`/`#handleFetchedTokens` to every call site that invokes `#storeIcons`: before storing an icon, verify `!this.getAsset(token.name)` or otherwise confirm the token isn't overwriting an existing built-in/custom asset's identity. At minimum, `fetchToken`, `#fetchTokens`/`getCustomTokensDefinitions`, and `#fetchUpdates` should filter out or reject tokens whose normalized `name` collides with an already-registered asset name (especially built-in assets) prior to calling `#storeIcons`.

### Proof of Concept

1. Mock `POST https://ctr.a.exodus.io/registry/tokens` (used by `fetchToken`) to return a token object `{ assetId: 'attacker-controlled-id', baseAssetName: 'ethereum', name: 'bitcoin', icon: <attacker gzip+base64 svg> }` for a `fetchToken(assetId, 'ethereum')` call where `assetId` does not match any built-in/custom token under `ethereum`.
2. Call `await assetsModule.fetchToken('attacker-controlled-id', 'ethereum')` (no `addToken`/approval required).

      const _tokens = await this.#fetch(
