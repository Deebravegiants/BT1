### Title
`describeWithdrawal` reports Bitcoin (UTXO-chain) withdrawals as `completed` using a non-final `pending_sign_id`, which can diverge from the true `finalised.transaction_hash` - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
For UTXO-chain destinations, `describeWithdrawal` returns `{status:'completed', txHash: transfer.utxo_meta?.pending_sign_id}` whenever `typeof window !== 'undefined'`, even though the code's own comment states this id "is not the finalised tx hash" and "may change if the BTC transfer fails to be submitted." This breaks the STATUS TRUTH invariant `(status, txHash) == actual on-chain outcome` for any integrator/browser client consuming this SDK method directly.

### Finding Description
The broken equality: `describeWithdrawal(...) == (status, txHash)` should equal the real Bitcoin chain outcome, i.e. `status:'completed'` should imply `txHash` corresponds to a transaction that is (or will be) permanently confirmed on Bitcoin. In `OmniBridge.describeWithdrawal` at [1](#0-0) , for UTXO chains the code branches on `typeof window !== 'undefined'` and, in the browser branch, uses `transfer.utxo_meta?.pending_sign_id` as `txHash`, reporting `status: 'completed'` immediately. The comment directly above this code acknowledges the id is not final and can change if the BTC broadcast fails: [2](#0-1) . In the non-browser branch the same function correctly waits for `transfer.finalised?.transaction_hash` before reporting completion. Thus the exact same withdrawal, observed through a browser-context caller, can be marked `completed` with `txHash = 'sign-id-1'` and later, when the transfer actually resolves (or fails and is resigned), the authoritative hash reported to a Node/backend caller would be a different value (`'btc-tx-2'`), or the transfer could fail entirely. Nothing in `validateWithdrawal`, `supports()`, or the intents contract can catch this because it is purely a post-hoc status-reporting bug local to `describeWithdrawal`; there is no on-chain verification tying the reported `pending_sign_id` to the eventual Bitcoin transaction.

### Impact Explanation
Any integrator or frontend that calls `describeWithdrawal` (directly or via higher-level completion-tracking helpers such as `waitForWithdrawalCompletion` / `withdrawal-watcher`) in a browser context will receive a `completed` status with a `txHash` that is not guaranteed to ever exist on Bitcoin. If the integrator credits/settles/displays the withdrawal as done based on this response, and the BTC broadcast later fails or resigns with a different hash, the integrator has committed to a non-existent transaction — a status/hash misreport that can cause double-crediting or crediting against a phantom transaction. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice" (the question frames it as Critical, but per the provided severity rubric this class of misreport is explicitly listed under High, not Critical, since no funds are directly moved/misrouted by the SDK itself — the risk is downstream integrator handling of an unreliable status).

### Likelihood Explanation
This triggers on every BTC (or other UTXO-chain) withdrawal observed via `describeWithdrawal` when run in a browser-like environment (`window` defined) — no special attacker action is needed since it is not attacker-triggered but a design behavior baked into the SDK for all browser callers of UTXO withdrawals. The precondition (`typeof window !== 'undefined'`) is common for any dApp frontend using this SDK. The BTC-resubmission-with-different-hash scenario acknowledged in the comment is stated to be rare, but the reporting bug is deterministic and reproducible every time a pending sign occurs before finalization.

### Recommendation
Do not report `status: 'completed'` based on `pending_sign_id`. Either (a) introduce a distinct status such as `pending-broadcast` / `signing` that carries the non-final id separately from `txHash`, or (b) only return `completed` once `transfer.finalised?.transaction_hash` is available in both browser and non-browser contexts, using a separate lightweight "fast" field for UI display of unconfirmed signing state.

// packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.test.ts (conceptual addition)
import { describe, it, expect, vi, beforeAll, afterAll } from "vitest";

describe("describeWithdrawal UTXO status truth", () => {
  beforeAll(() => {
    // simulate browser environment
    (globalThis as any).window = {};
  });
  afterAll(() => {
    delete (globalThis as any).window;
  });

  it("reports completed with a non-final pending_sign_id that later diverges from finalised hash", async () => {
    const bridge = new OmniBridge({ /* ...mock deps... */ });
    vi.spyOn(bridge["omniBridgeAPI"], "getTransfer").mockResolvedValueOnce([
      {
        recipient: "btc:bc1qxxxxxx",
        utxo_meta: { pending_sign_id: "sign-id-1" },
        finalised: null,
      },
    ] as any);

    const result1 = await bridge.describeWithdrawal({ tx: { hash: "near-tx" }, index: 0 } as any);
    expect(result1).toEqual({ status: "completed", txHash: "sign-id-1" });

    // Later poll: the transfer actually finalises with a DIFFERENT hash
    vi.spyOn(bridge["omniBridgeAPI"], "getTransfer").mockResolvedValueOnce([
      {
        recipient: "btc:bc1qxxxxxx",
        utxo_meta: { pending_sign_id: "sign-id-1" },
        finalised: { transaction_hash: "btc-tx-2" },
      },
    ] as any);
    const result2 = await bridge.describeWithdrawal({ tx: { hash: "near-tx" }, index: 0 } as any);

    // Demonstrates result1.txHash ("sign-id-1") never matches the authoritative on-chain hash ("btc-tx-2")
    expect(result2.txHash).not.toBe(result1.txHash);
  });
});
