### Title
Webhook `shop` (and `topic`) identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating `Utils::HmacValidator.validate(request)`, whose signable content is `request.to_signable_string`, defined to be just the raw HTTP body. The `shop`, `topic`, and `webhook_id` values that are handed to the app's handler (and used by the app to decide which tenant/session the event belongs to) come straight from unauthenticated HTTP headers and are never covered by the HMAC digest. This breaks the identity binding: `shop authenticated == shop used as session/tenant key`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request and, on success, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header — again, only the body is covered: [4](#0-3) 

Because the `api_secret_key` used to compute this HMAC is the single, app-wide client secret (the same secret is used for every shop that installs the app, not a per-shop secret), an entity that has legitimately received (or triggered) one authentic webhook for *any* shop knows a valid `(body, hmac)` pair. Since `shop-domain`, `topic`, and `webhook-id` headers are not part of the signed material, that same `(body, hmac)` pair can be replayed with arbitrary `shop-domain` / `topic` / `webhook-id` header values and will still pass `HmacValidator.validate`. The documented processing flow explicitly forwards this unauthenticated `shop` value straight to the app handler as the tenant identifier: [5](#0-4) [6](#0-5) 

This is a genuine break of the identity binding "shop authenticated via HMAC == shop used as the session/tenant key downstream," matching the analog class of "a field acted on but not covered by the HMAC."

### Impact Explanation
An app built on this gem uses `data.shop` from `WebhookMetadata` to decide which merchant/tenant the event belongs to (per the gem's own documented usage pattern, e.g. loading that shop's session/access token to react to the event). Because `shop` is not bound to the HMAC, any party capable of causing (or capturing) one authentic webhook delivery for the app — for example a merchant who installs the app on their own store, an ordinary, unprivileged action — can replay that exact `(body, hmac)` pair while forging the `shop-domain` (and `topic`/`webhook-id`) headers to any other value, including another merchant's shop domain. The webhook still passes `HmacValidator.validate` and is dispatched to the handler labeled as belonging to the spoofed shop. Any app logic keyed off `data.shop` (which the gem's docs explicitly recommend, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will act on attacker-controlled data under the wrong tenant's identity — a cross-tenant confusion/spoofing impact.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send an arbitrary HTTP request to the app's public webhook endpoint (no credentials, no TLS interception, no access token needed), and (2) possession of one previously-observed valid `(raw_body, hmac)` pair for the shared `api_secret_key` — obtainable by any ordinary merchant who installs the app and observes their own webhook deliveries, or by network capture. No knowledge of `api_secret_key` itself is required. This is a low-effort, purely network-reachable attack against the gem's own webhook-processing code path (`Registry.process`), not a misuse of undocumented behavior — the header-derived `shop`/`topic` fields are the gem's documented output contract.

### Recommendation
Do not rely solely on body-HMAC verification when trusting header-derived identity fields (`shop`, `topic`, `webhook-id`) that are forwarded to the handler. Either (a) include the relevant headers (shop domain, topic, webhook id) in the signable content used for HMAC verification so header tampering invalidates the signature, or (b) explicitly document/enforce that `WebhookMetadata#shop` must be cross-checked by the caller against an independently known/registered shop before being used as a session or tenant key, and provide a `Registry.process` variant that accepts an expected shop/topic and rejects mismatches.

### Proof of Concept
1. App has processed at least one legitimate webhook delivery for shop `attacker-shop.myshopify.com`, topic `orders/create`, with raw body `B` and header `X-Shopify-Hmac-Sha256: H` (attacker can simply capture their own installed shop's webhook traffic).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Webhook-Id: <any>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(api_secret_key, B)` — identical to `H` — and passes: [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-supplied content as if it originated from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
