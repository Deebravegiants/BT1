## Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The bug reported externally is a class of "signed payload with more fields than covered by the signature," allowing an attacker to smuggle an unverified field into a request that a validator trusts because it only checks a subset of the payload. The same class exists in this gem's webhook verification: `ShopifyAPI::Webhooks::Registry.process` verifies the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, but the `shop` (`shop-domain` header), `topic`, `webhook_id` and `api_version` fields used to route and attribute the webhook to a tenant are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers, independent of the HMAC: [2](#0-1) 

`Registry.process` only validates that the body matches the HMAC computed with `api_secret_key`, then immediately forwards the *unverified* `shop` value to the app's handler: [3](#0-2) 

The equality that should hold is:
`bytes covered by HMAC (raw_body)` == `bytes the app trusts for tenant identity (shop-domain header)`

This equality is false: the HMAC only binds the body, not the `shop-domain` header. Any party who can obtain one validly-signed webhook body (e.g., a merchant who installed the same multi-tenant app and receives their own legitimate webhooks from Shopify) can replay that exact body to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header for a victim tenant. Since the HMAC computation never touches the shop header, `Utils::HmacValidator.validate(request)` still succeeds, and `WebhookMetadata.new(... shop: request.shop ...)` hands the app a `shop` value that has no cryptographic relationship to the verified bytes.

### Impact Explanation
This breaks the tenant-authentication boundary (cross-tenant access, High/Critical per the given impact categories). An app relying on `WebhookMetadata#shop` to select which merchant's data/store context to act on (e.g., to look up or mutate that tenant's records, access tokens, or trigger side effects) can be tricked into performing legitimate-looking, HMAC-"verified" webhook processing under a spoofed tenant identity supplied by a different, unprivileged installer of the same app.

### Likelihood Explanation
Exploitation requires only the capability to install the same app as a legitimate, unprivileged merchant (to obtain one authentic signed webhook body) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a modified `shop-domain` header — no `api_secret_key`, access token, or privileged access is needed, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signed material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., require the caller to independently confirm shop identity via a signed source such as a stored offline session/access-token lookup before trusting `request.shop`), rather than trusting header-derived tenant identity purely because the body's HMAC passed.

### Proof of Concept
1. Install the target Ruby-based app on Shop A (attacker-controlled) and Shop B (victim), both served by the same app instance sharing one `api_secret_key`.
2. Trigger any webhook topic (e.g. `orders/create`) from Shop A; capture the raw body and the valid `X-Shopify-Hmac-Sha256` value Shopify sends.
3. Replay that exact HTTP request to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` still returns `true` (body unchanged), and `Registry.process` invokes the handler with `WebhookMetadata#shop == "shop-b.myshopify.com"`, even though nothing about the verified bytes originated from or was authorized by Shop B.
