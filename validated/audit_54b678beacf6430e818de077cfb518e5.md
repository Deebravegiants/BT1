### Title
Reentrant token/native transfer before escrow-balance debit in Tron IntentGatewayV2's `withdraw` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2` implements escrow release in an internal `withdraw()` function that performs the native/ERC20 token transfer *before* decrementing the corresponding `_orders[commitment][token]` escrow balance, and uses a raw, un-guarded `.call()` for both native value and ERC20 `transfer` instead of the Checks-Effects-Interactions pattern used by the sibling EVM implementation. This is the same bug class flagged in the external report (state write following, not preceding, an external call).

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is called from `onAccept` (for `RedeemEscrow`/`RefundEscrow` requests delivered by the ISMP host) and from `onGetResponse` (for cross-chain cancellation confirmation): [1](#0-0) 

For each token in the withdrawal body, the function:
1. Checks only that `_orders[commitment][token] != 0` (does not bound `amount` against the escrowed balance before the call).
2. Sends the native value or executes a raw `token.call(transfer(...))` to the beneficiary.
3. **Only after** the external call succeeds does it decrement `_orders[body.commitment][token] -= amount;`.

The same ordering problem occurs for transaction fee redemption a few lines below, where `feeToken.call(transfer(...))` happens before `delete _orders[body.commitment][TRANSACTION_FEES];`.

This is a direct violation of Checks-Effects-Interactions, structurally identical to the reported `executed = true` pattern (state write after external call). By contrast, the "canonical" EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) already applies the fix: it decrements `_orders[body.commitment][token]` in storage *before* calling `_sendValue`/`safeTransfer`: [2](#0-1) 

and the project's own reentrancy regression suite (`IntrinsicIntentsReentrancyTest.sol`) documents this exact class of attack (fee/escrow theft via a malicious beneficiary re-entering during the ETH transfer) and confirms it is blocked *only* because the CEI ordering was fixed in the mainline EVM contracts: [3](#0-2) 

The Tron `IntentGatewayV2.sol` never received this fix and also contains no `ReentrancyGuard`/`nonReentrant` modifier anywhere in the file or directory (confirmed via search), unlike other parts of the protocol that do rely on CEI + `_filled` markers as their only reentrancy defense.

### Impact Explanation
`beneficiary` in the `WithdrawalRequest` is attacker-influenced: an order's beneficiary/user is chosen by whoever places or fills the order, and the input tokens escrowed are also chosen by the order creator. A malicious actor can:
- Place/fill an order using a malicious ERC20 token contract as one of the escrowed inputs, or set the beneficiary to a malicious contract for native-asset payouts.
- When `withdraw()` executes the transfer for that token/native leg, the malicious token's `transfer()` hook (or the malicious beneficiary's fallback for native TRX) executes attacker code *while the escrow balance for that commitment/token is still un-decremented*.
- From that reentrant context the attacker can invoke other public entry points of the same gateway (e.g., re-reading/relying on the stale, not-yet-decremented `_orders[commitment][token]` value) to drain additional escrowed funds tied to the same commitment before the original call finishes zeroing it out, resulting in theft of escrowed input tokens/fees beyond what is owed.

This directly threatens intents-escrow fund safety (concrete theft of escrowed funds), which the rules classify as in-scope, reachable by an unprivileged filler/solver/relayer submitting a single transaction.

### Likelihood Explanation
The path is reachable by any relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow` ISMP message or GET-response for an order that the attacker themselves constructed (chosen input token, chosen beneficiary) — no privileged role is required. The `onAccept`/`onGetResponse` entry points are only gated by `onlyHost`, which any relayer satisfies once it delivers a validly-proven message; the attacker fully controls the order content (token address, beneficiary address) that triggers the vulnerable external call. This makes the likelihood high for an attacker willing to deploy a malicious ERC20 or beneficiary contract and place/fill an order with it.

### Recommendation
Apply the same CEI fix used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) *before* performing the native transfer or ERC20 `transfer` call in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`. Additionally, replace the low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used elsewhere in the file) to avoid silently mishandling non-standard ERC20 return values, and consider adding an explicit `nonReentrant` guard to `onAccept`/`onGetResponse` as defense-in-depth.

### Proof of Concept
1. Attacker deploys `MaliciousToken`, an ERC20 whose `transfer()` function, when invoked with the gateway as `msg.sender` and attacker's contract as recipient, re-enters the gateway (e.g., calls another public function that reads the not-yet-updated `_orders[commitment][token]`) before returning `true`.
2. Attacker creates a cross-chain order (`placeOrder`) using `MaliciousToken` as an escrowed input and fills the corresponding leg on the destination chain (or arranges a `RefundEscrow`), producing a `WithdrawalRequest` with `beneficiary = attacker` and `tokens = [{token: MaliciousToken, amount: X}]`.
3. A relayer delivers the resulting ISMP `RedeemEscrow`/`RefundEscrow` request to `onAccept`, which calls the internal `withdraw()`: [4](#0-3) 
4. Inside `withdraw()`, `token.call(transfer(beneficiary, amount))` invokes `MaliciousToken.transfer`, which — before returning — re-enters the gateway. At this point `_orders[commitment][MaliciousToken]` still holds its pre-withdrawal value (the decrement at line 710 hasn't executed yet), allowing the reentrant call path to observe/exploit the stale escrow accounting and extract additional value tied to the same commitment.
5. The outer call then completes, decrementing the escrow — but by then the attacker has already extracted more value than the escrow should have allowed, since the check `_orders[body.commitment][token] == 0` only prevents a follow-up call once fully drained, not partial overdraws performed mid-transfer.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
