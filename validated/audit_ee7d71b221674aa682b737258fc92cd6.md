### Title
Stale cached operator-QR validity is reused across multiple signups without re-checking backend revocation status - (File: src/plans/mod.rs)

### Summary
`MasterPlan` caches a validated operator QR code (`OperatorData`) together with a `timestamp` after a single successful call to `verify_operator_qr_code` (which calls the backend `operator_status::request`). For the lifetime of `operator_qr_expiration_time` (23 hours by default), subsequent signups reuse this cached `OperatorData` without re-verifying it against the backend, exactly mirroring the Hats Protocol bug: a "toggle"-like authority (the backend operator-status check) is only consulted once, and the local cached "valid" state is trusted afterward, even if the backend's source of truth changes (e.g. operator is deactivated/banned) in the interim.

### Finding Description
In `scan_initial_qr_codes` and `scan_remaining_qr_codes` (`src/plans/mod.rs`), the operator QR code is validated once via `verify_operator_qr_code`, which hits `backend::operator_status::request` [1](#0-0) . On success, the result is stored as `OperatorData { qr_code, location_data, timestamp: Instant::now() }` [2](#0-1) .

For every subsequent signup, `scan_remaining_qr_codes` checks only the elapsed local timer, not the backend, before reusing the cached operator authorization:
```
QrCodes::Both { operator_data, ... } if operator_data.timestamp.elapsed() < operator_qr_expiration_time => { ... }
QrCodes::Operator { operator_data } if operator_data.timestamp.elapsed() < operator_qr_expiration_time => { ... }
``` [3](#0-2) 

Only when the cached timestamp has expired does the code fall through to actually re-scan and re-verify the operator QR code against the backend [4](#0-3) . This is analogous to the Hats bug: instead of calling `checkHatToggle()` (i.e., re-querying the authoritative source) before trusting the current state, the code defaults to the locally cached "valid" status (`hat.config`/`OperatorData`), which may no longer reflect the backend's authoritative state (e.g., the operator's badge was revoked, the operator was suspended, or the operator's location changed such that it should now be rejected).

The default `operator_qr_expiration_time` is `Duration::from_secs(60 * 60 * 23)` — nearly a full day [5](#0-4) , giving a wide window during which a revoked/invalidated operator's credentials continue to be treated as valid by the orb, purely because the local cache hasn't expired — not because the backend re-confirmed validity.

### Impact Explanation
If an operator's authorization is revoked on the backend (fraud, policy violation, account suspension, geofence violation, etc.) after their QR code was validated once, the orb will continue to accept that operator as valid for up to 23 hours (`operator_qr_expiration_time`) without any re-check, allowing them to keep initiating and authorizing signups. This is a concrete unauthorized-signup-authorization impact: signups are gated by trust in the operator, and the trust decision is not kept in sync with the backend's current status, exactly the "unexpected reactivation despite the authoritative source having changed" pattern described in the Hats report.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an operator whose backend status changes to invalid mid-session, and (b) the orb having already cached a valid `OperatorData` before that revocation. Given the long default expiration window (23h) and that revocations are exactly the kind of event that should take effect immediately (compromise, fraud, policy breach), this is a realistic operational scenario rather than a purely theoretical one.

### Recommendation
Before trusting a cached `OperatorData` for a new signup (in `scan_remaining_qr_codes` / `idle_scan_user_qr_code`), re-validate the operator status against the backend (or reduce the reliance on the local timestamp-only check), similar to the Hats Protocol fix of calling `checkHatToggle()` before switching over — i.e., proactively re-sync the authoritative state instead of trusting the stale local flag until an arbitrary expiration timer elapses. At minimum, consider a much shorter re-validation interval, or an explicit backend push/webhook to invalidate cached sessions immediately upon operator revocation.

### Proof of Concept
1. Operator scans an operator QR code; `verify_operator_qr_code` succeeds and `OperatorData` with `timestamp: Instant::now()` is cached [6](#0-5) .
2. Backend-side, the operator's status is revoked (e.g., `valid: false` would now be returned by `backend::operator_status::request`) [7](#0-6) .
3. Within the next `operator_qr_expiration_time` (up to 23 hours), the same operator initiates further signups. `scan_remaining_qr_codes` sees `operator_data.timestamp.elapsed() < operator_qr_expiration_time` is still true and skips re-verification entirely, using the stale cached `OperatorData` to authorize the new signup [3](#0-2) .
4. Signups proceed as though the operator were still valid, despite the backend's authoritative "revoked" status never being consulted again during this window.

pub async fn request(qr_code: &qr_scan::user::Data) -> Result<Status> {
    let request = super::client()?
        .get(format!(
            "{}/api/v1/distributor/{}/orb/{}/status",
            *SIGNUP_BACKEND_URL, qr_code.user_id, *ORB_ID
        ))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    let status: Status = match request.send().await?.error_for_status() {
        Ok(response) => response.json().await?,
        Err(err) => {
            tracing::error!("Received error response {err:?}");
            return Err(err.into());
        }
    };
    if !status.valid {
        tracing::info!(
            "Operator QR-code invalid: {qr_code:?}, reason: {:?}",
            status.reason.as_deref().unwrap_or("<empty>")
        );
        return Ok(status);
    }
