This confirms the finding. The `to_signable_string` for webhook requests is only the raw body [1](#0-0) , while `shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never included in the HMAC computation [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e., the body, against the shared `api_secret_key`) and then trusts `request.shop` when dispatching to the handler [3](#0-2) . Since `api_secret_key` is the same for every shop that installs a given app, this is a genuine identity-binding gap matching the requested bug class.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `HmacValidator.validate` verifies the HMAC solely against that body using the app's single, shop-independent `api_secret_key`. The `shop` value used by `Registry.process` to dispatch webhook data to the handler is read from the `shopify-shop-domain` header, which is completely outside the HMAC's coverage. Any unprivileged party who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still succeed because it never binds the signature to the shop, so `Registry.process` will invoke the merchant's `WebhookHandler` with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop value acted upon by the handler`

In this gem, that equality is broken:
- The HMAC is computed only over `@raw_body` [1](#0-0) .
- `shop` is parsed independently from headers and is never part of the signed payload [2](#0-1) .
- `Registry.process` validates the HMAC and, if it passes, blindly forwards `request.shop` into `WebhookMetadata` for the handler to act on [3](#0-2) .
- `HmacValidator.validate`/`validate_signature` compute the signature using `Context.api_secret_key`, which is a single value shared by the app across *all* installed shops, not per-tenant [4](#0-3) .

Because the secret is shared across tenants and the shop identifier is unauthenticated, any attacker who is a legitimate (even unprivileged) user of the same app on a different shop can capture a valid `(raw_body, hmac)` pair from their own webhook deliveries and replay it against the shared webhook endpoint with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header pointing at a victim shop. The gem reports this forged request as HMAC-valid, and the host application's handler receives attacker-controlled `body` associated with a victim `shop`, since the gem provides no cross-check that the signed content actually originated from that shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: `Registry.process` hands the handler a `WebhookMetadata` claiming data belongs to shop B while the body was actually crafted/replayed by an attacker who only controls shop A. Depending on how the host application's handler trusts `data.shop` (e.g., to look up per-shop tokens, update per-shop records, or trigger the mandatory GDPR redact topics), this enables cross-tenant data injection/corruption — matching the High-severity "cross-tenant access" impact class, since the shop-scoping guarantee that webhook consumers rely on is violated by the gem's own verification logic.

### Likelihood Explanation
Likelihood is significant: the only capability needed is being a legitimate installer of the same public app on any shop (fully unprivileged relative to the victim), enough to receive at least one real webhook and observe its raw body + `hmac-sha256` header. No access to `api_secret_key`, tokens, or the victim's credentials is required — the entire attack replays publicly-observable-to-the-attacker artifacts from their own tenant against the shared endpoint with a spoofed header.

### Recommendation
Bind the shop identity into the verified payload before trusting it: incorporate `shop`, `topic`, and `webhook_id` into the value passed to `to_signable_string` (or perform a secondary check against a known/expected shop for the given handler/session), rather than relying purely on the body-only HMAC and an unauthenticated header for the identifier used downstream.

### Proof of Concept
1. Install the app (or otherwise be a merchant of the app) on attacker-owned shop `attacker.myshopify.com`; capture one legitimate webhook delivery with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay to the same webhook endpoint an HTTP request with the identical raw body `B`, identical `shopify-hmac-sha256: H`, but header `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` [2](#0-1) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(api_secret_key, B) == H` [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` [6](#0-5) , i.e., attacker-supplied data is processed as if it belonged to the victim shop.
