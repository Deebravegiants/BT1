I found a concrete identity-binding issue in the webhook processing path: the `shop` attribute delivered to webhook handlers is taken from an HTTP header that is **not covered by the HMAC signature check**, unlike the request body.

### Title
Webhook `shop` attribution is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only [1](#0-0) , while the tenant-identifying `shop` value is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside of that signature [2](#0-1) . `Registry.process` validates only the HMAC of the body, then forwards `request.shop` (the unauthenticated header) straight to the app's webhook handler as the tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop value trusted by the handler == shop that Shopify actually cryptographically attested for this payload`

In `Request#to_signable_string`, only `@raw_body` is signed [1](#0-0) . `HmacValidator.validate` computes the signature purely over that signable string and the app's secret [4](#0-3) . Nothing in the gem cryptographically ties the `shop-domain` header value to the signed body. `Registry.process` raises only if the body-HMAC fails, then unconditionally trusts `request.shop` (header-derived) when building `WebhookMetadata` passed to the handler [3](#0-2) .

Because a merchant who has legitimately installed the app on their own store (an unprivileged party with respect to any *other* tenant) receives genuine webhook deliveries — valid body + valid HMAC — addressed to their own shop, they can capture one such delivery and replay it to the app's webhook endpoint while only modifying the `X-Shopify-Shop-Domain` header to name a different, victim shop. The HMAC check still passes because it never covered the header. The gem then hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop, when in fact Shopify never attested that binding.

### Impact Explanation
This breaks the tenant/shop identity boundary: an attacker who is a legitimate but unprivileged user of the app (merchant of shop A) can forge webhook events that the host application will attribute to an arbitrary other shop (shop B) merely by replaying a captured, validly-signed body under a different shop header. Any app logic that keys persistence, billing, notifications, or state transitions off `WebhookMetadata#shop` is exposed to cross-tenant data injection/spoofing — this matches the "cross-tenant access" Critical impact category, since the affected shop's data integrity is compromised by another tenant without any credential belonging to the victim.

### Likelihood Explanation
Likelihood is elevated by how little the attacker needs: only a webhook subscription of their own (something any app-installing merchant already has) and the ability to send a normal HTTP POST to the app's public webhook endpoint with a modified header — no `api_secret_key`, no stolen access token, and no privileged account for the victim shop are required. The main constraint is that the replayed body's content must be plausible/useful for the target handler logic (e.g., topics whose payload doesn't itself embed a signed shop reference), which is common for many webhook topics.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) inside the HMAC-signed content, or independently verify `request.shop` against the shop that is expected to own the given webhook subscription/topic before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated by the HMAC and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against the app's own webhook registration records for that topic/shop, or rejecting shops not already known to the app).

### Proof of Concept
1. Merchant A installs the app; the app registers a webhook (e.g., `products/update`) and the app's webhook endpoint receives a real Shopify-originated POST:
   - Headers: `X-Shopify-Hmac-Sha256: <valid>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: products/update`
   - Body: `{"id": 123, "title": "Some Product"}`
2. Merchant A (who controls their own server/network path or can otherwise capture this legitimate request) resends the identical body and HMAC header to the app's public webhook endpoint, but replaces only:
   - `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim shop, also an app installer)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: {...}, ...)` [6](#0-5) , causing the app to process merchant A's forged data as if it came from shop B.
