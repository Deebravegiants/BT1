### Title
Unrestricted `flash_position` receivers can inject wallet-draining token transfers into the caller's authorization tree - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` lets any caller specify an arbitrary deployed Wasm `receiver`, requiring only that it is Wasm and is not the controller or pool. [1](#0-0)  The entrypoint first calls `caller.require_auth()`, then invokes that receiver inside the same authorized invocation with the caller passed as `initiator`. [2](#0-1) [3](#0-2)  Consequently, receiver code can call `token.transfer(initiator, attacker, amount)` for unrelated tokens; simulation records that transfer as a child of the caller's `flash_position` authorization, and execution succeeds if the caller signs the poisoned tree. [4](#0-3) 

### Finding Description
The vulnerable sequence starts at `require_authorized_caller`, which establishes a caller authorization root rather than constraining what nested code may request under that root. [5](#0-4)  `process_flash_position` accepts `receiver` directly from call arguments and validates only its executable type and exclusion from the controller and pool addresses. [1](#0-0) 

The controller then mints the requested debt onto the account, forwards the measured debt tokens to the receiver, snapshots collateral balances, and invokes `execute_flash_position` on the receiver with caller-controlled `data`. [3](#0-2) [6](#0-5)  Neither the callback address nor `data` is allowlisted, interpreted, or limited to operations on the flash proceeds. [6](#0-5) 

Because the callback receives `initiator`, malicious receiver code can invoke an unrelated Stellar Asset Contract as `token.transfer(caller, attacker, victim_balance)`. [7](#0-6)  That token call is below the caller's original `flash_position` invocation, so transaction simulation adds it as a child authorization; the repository's auth-tree test demonstrates that such a nested token transfer is recorded under the strategy caller's root and succeeds when that generated tree is signed. [8](#0-7) [9](#0-8) 

### Impact Explanation
A malicious transaction builder can make the signed `flash_position` call move any victim token balance to an attacker while the receiver simultaneously supplies the declared collateral needed for transaction completion. [10](#0-9)  The receiver may also retain the minted debt proceeds because `flash_position` intentionally leaves debt on the victim's solvent account rather than requiring repayment. [11](#0-10) [12](#0-11) 

The resulting loss is not limited to listed collateral or the declared flash amount: the nested token call can name any token contract and any victim-held balance that the signed authorization tree includes. [13](#0-12)  This is direct theft of user funds.

### Likelihood Explanation
Likelihood is Medium because the victim must sign a simulated authorization tree containing the malicious nested transfer; an honest signing client that rejects unexpected children prevents execution. [14](#0-13)  However, an unprivileged attacker can deploy the receiver, choose the receiver and `data` arguments, and rely on a wallet or integration that presents the operation as a normal `flash_position` while the generated authorization tree contains the extra transfer. [15](#0-14) [6](#0-5) 

### Recommendation
Do not invoke arbitrary Wasm code while a user's authorization root is active. Restrict `flash_position` receivers to a governance-approved allowlist, or redesign the flow so an untrusted callback cannot run beneath the caller's authorization. At minimum, clients must reject any `flash_position` authorization tree containing children other than the expected collateral transfer, but that is a mitigation rather than a protocol-level fix. [13](#0-12) 

### Proof of Concept
1. Deploy a malicious receiver implementing `execute_flash_position`.
2. The victim calls:

```rust
flash_position(
    victim,
    0,                    // create a victim-owned account
    spoke_id,
    PositionMode::Multiply,
    debt_asset,           // flash-loan-enabled market
    debt_amount,
    malicious_receiver,
    attacker_data,
    vec![(collateral_asset, collateral_min)],
    vec![],
)
```

3. The malicious callback executes:

```rust
pub fn execute_flash_position(
    env: Env,
    initiator: Address,
    _account_id: u64,
    _asset: Address,
    _amount: i128,
    _fee: i128,
    _amount_received: i128,
    controller: Address,
    data: Bytes,
) {
    let (stolen_token, attacker, stolen_amount): (Address, Address, i128) =
        DecodeFromData::decode(&env, &data);

    // Injected into the victim's simulated authorization tree.
    token::Client::new(&env, &stolen_token)
        .transfer(&initiator, &attacker, &stolen_amount);

    // Also authorized as a child; supplies the collateral required to finish.
    token::Client::new(&env, &collateral_token(&env))
        .transfer(&initiator, &controller, &collateral_min(&env));
}
```

4. Simulation produces a `flash_position` root containing the extra `stolen_token.transfer(victim, attacker, stolen_amount)` child; signing that tree permits the transfer. [9](#0-8) 
5. The controller measures the transferred collateral, deposits it, and finalizes the solvent debt position, so the injected theft and retained debt proceeds persist. [16](#0-15)

        let baseline = before

        assert_with_error!(
            env,

            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
