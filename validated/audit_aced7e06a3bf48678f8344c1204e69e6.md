## Title
Unprivileged staker action between epoch reward calculation and partitioned distribution can panic the validator via delegation-mismatch `assert_eq!` - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
Partitioned epoch rewards are computed once at the epoch boundary (calculation phase) and then paid out incrementally over up to 10% of the epoch's slots (distribution phase). The per-account reward payload computed at calculation time is later applied against the *live*, current stake account state read from `stakes_cache_accounts` at the time each partition is actually stored. When the legacy (`relax_post_exec_min_balance_check` inactive) code path is used, `Bank::build_updated_stake_reward` asserts that the live delegation amount plus the pre-computed reward exactly equals the delegation amount that was computed at calculation time — with no tolerance for the account having changed in the intervening blocks. This is the same bug class as the reported OpenQ issue: a value is snapshotted at one point in time (bounty balance / stake delegation) and later assumed unchanged when it is consumed, and unprivileged user action in between (refund / stake `Split`, `Merge`, or other delegation-affecting instruction) invalidates that assumption.

### Finding Description
`Bank::distribute_partitioned_epoch_rewards` spreads reward crediting for a whole epoch over multiple blocks [1](#0-0) . For each partition, `store_stake_accounts_in_partition` fetches the account's *current* on-chain state from `self.stakes_cache.stakes()` at the time that specific partition block executes, not the state captured back when rewards were computed at the epoch boundary [2](#0-1) .

`build_updated_stake_reward` then merges the pre-computed reward (`partitioned_stake_reward`, produced during the calculation phase, potentially many blocks earlier) with this freshly-read live account. When the `adjust_delegations_for_rent` feature gate is inactive, the code takes the "else" branch and requires the live delegation stake plus the calculation-time reward to exactly equal the calculation-time delegation-with-reward value, enforced via `assert_eq!`: [3](#0-2) 

`stake.delegation.stake` here comes from the live `stakes_cache_accounts` lookup, while `partitioned_stake_reward.inflation.stake.delegation.stake` was fixed at epoch-boundary calculation time. If a staker legitimately mutates their own delegated stake account between the calculation block and their reward's distribution block (e.g. by splitting the stake account, merging another account into it, or any other stake-program instruction that changes `delegation.stake`), the live value diverges from the value embedded in the already-computed `partitioned_stake_reward`, and `expected_delegation != new_stake.delegation.stake`, tripping the `assert_eq!` and panicking the validator process during block processing/bank freeze.

This mirrors the reported bug's root cause exactly: a balance/state snapshot is taken at one point (bounty `closeCompetition` snapshot / here, epoch-boundary reward calculation), consumed at a later point (claim payout / here, partitioned distribution), and an unprivileged actor's ordinary action in between (refund / stake mutation) breaks the invariant the later code silently assumes still holds.

### Impact Explanation
Unlike the original bug (funds becoming stuck), here the consequence is worse for a validator: the mismatch is enforced by a Rust `assert_eq!`, which panics the running process. Since `distribute_partitioned_epoch_rewards` runs unconditionally for every leader/replaying validator during normal epoch-boundary block production and replay, a panic here is not confined to a single node — every validator that processes the same block sequence (and observes the same stake-account mutation before the relevant partition's block) hits the identical assert and crashes, which can produce a cluster-wide liveness/halt condition rather than an isolated crash. This satisfies the "cross-node divergence or halt" impact bar.

### Likelihood Explanation
The trigger requires only an ordinary, permissionless stake-authority action (e.g., `Split`/`Merge` on one's own delegated stake account) timed to land in a block between the epoch's reward-calculation block and the block that credits that particular stake account's partition — a window that can span up to 10% of the epoch's slots per `get_reward_distribution_num_blocks` [4](#0-3) . This code path is only exercised when the `relax_post_exec_min_balance_check`/`adjust_delegations_for_rent` feature is inactive, so likelihood depends on that feature's activation status on the target cluster; while active clusters use the tolerant `adjust_delegation_for_rent` branch instead, any cluster/testnet running with the feature deactivated (or during phased rollout) is exposed.

### Recommendation
Do not assert hard equality between a calculation-time snapshot of stake delegation and the live value observed later during distribution. Instead, recompute the expected post-reward delegation from the live state (as the `adjust_delegations_for_rent` branch already does), or detect and gracefully handle/burn the reward for accounts whose delegation changed since calculation, rather than panicking the validator.

### Proof of Concept
1. Enter an epoch boundary block where a staker's account earns a non-zero `stake_reward` (recorded into `partitioned_stake_reward.inflation.stake.delegation.stake`).
2. Ensure the cluster/bank has `relax_post_exec_min_balance_check`/`adjust_delegations_for_rent` deactivated, so `build_updated_stake_reward`'s `else` branch (with the `assert_eq!`) is taken.
3. Before the block whose `partition_index` corresponds to this stake account's slot in `partition_indices` (which can be many blocks later, per `hash_rewards_into_partitions`), the staker submits a `Split` (or other delegation-mutating) instruction against their own stake account, changing `stakes_cache_accounts[stake_pubkey].delegation.stake`.
4. When `distribute_epoch_rewards_in_partition` reaches that account's partition, `build_updated_stake_reward` computes `expected_delegation = live_stake.delegation.stake + reward` which no longer equals the value already baked into `partitioned_stake_reward.inflation.stake.delegation.stake`, and the `assert_eq!` at [5](#0-4)  panics, crashing every validator processing the block.

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
