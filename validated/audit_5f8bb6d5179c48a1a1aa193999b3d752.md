## Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook replay/spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop-domain`, `topic`, and `webhook-id` values that are subsequently handed to the app's webhook handler — and which the handler uses to determine *which merchant tenant* the payload belongs to — are taken from unauthenticated HTTP headers that play no part in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

Concretely: [2](#0-1) 

`hmac` is derived from the `hmac-sha256` header, but `to_signable_string` returns only `@raw_body` — the `shop-domain`, `topic`, and `webhook-id` headers are excluded from the signed content.

`Registry.process` validates only that signable string against the HMAC, then immediately trusts the unauthenticated headers to build the `WebhookMetadata` object dispatched to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

In reality the equality is:
`shop covered by HMAC (∅, not present) != shop passed to handler.handle (from X-Shopify-Shop-Domain header)`

Because the raw body is the only HMAC-protected material, any request with a *valid* `(raw_body, hmac)` pair — regardless of where that pair originated — will pass `Utils::HmacValidator.validate(request)` no matter what `shop-domain`, `topic`, or `webhook-id` header values accompany it, since those headers are never fed into `compute_signature`: [4](#0-3) 

### Impact Explanation
An unprivileged internet user who legitimately installs the app on their own shop (any developer/trial Shopify store) receives real webhooks whose bodies are, in many topics (e.g. `orders/create`, `customers/create`), directly influenced by actions they take in their own store, each with a genuine HMAC computed by Shopify using the app's shared secret. Because the `shop-domain` header carrying tenant identity is not covered by that signature, the attacker can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to reference a victim shop. `Registry.process` will accept the forged request as valid and invoke the app's handler with `shop: <victim-shop>` and attacker-controlled body content — a cross-tenant identity/data-integrity break requiring no access token, `client_secret`, or leaked credential, only an HTTP client and a webhook the attacker legitimately received for their own tenant.

### Likelihood Explanation
Any app built on this gem that uses `ShopifyAPI::Webhooks::Registry.process` to dispatch webhooks is affected, since the vulnerable code path (`Request#to_signable_string`/`Registry.process`) is the gem's standard, documented mechanism for webhook verification. No special privileges, secrets, or complex conditions are required — only an attacker capable of running a webhook-triggering action on their own installed store and replaying the resulting HTTP request with a different `shop-domain` header.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) headers into the identity the handler trusts by cross-checking them against an authenticated source of truth (e.g., verify the shop against the caller's known/stored session for that webhook subscription, or include these headers in the value that is HMAC-verified) before invoking `handler.handle`. At minimum, document clearly that consumers of `WebhookMetadata#shop`/`#topic` must not trust these values without additional server-side verification against their own webhook registration records.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target app; app registers `orders/create` webhook.
2. Attacker creates an order in their own store, triggering Shopify to POST a webhook to the app with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, and a JSON body reflecting order contents the attacker fully controls (e.g., custom line-item attributes, notes fields).
3. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only hashes `@raw_body`, which is unchanged: [5](#0-4) 
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...))`, causing the app to process attacker-controlled data as if it originated from the victim's shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
