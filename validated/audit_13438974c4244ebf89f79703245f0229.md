### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers via `shopify_header` [2](#0-1) . `Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string`, i.e. the raw body [3](#0-2) . `Registry.process` trusts `request.shop` as the tenant identity once this check passes and dispatches it straight to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, i.e. the signature should cryptographically bind the request body to the shop/topic it is claimed to belong to. Instead the code only checks `hmac == HMAC(secret, body)`, and `shop`/`topic` are read independently from headers that are never included in the signed material.

Because the HMAC is a function of `raw_body` alone, any HTTP request with a given body and its valid corresponding `X-Shopify-Hmac-Sha256` value will pass `Utils::HmacValidator.validate` regardless of what `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers are attached to it. An attacker who is a legitimate tenant of the app (i.e., who has installed the app on their own store, an "unprivileged" capability available to anyone) can capture a body+HMAC pair generated for their own store's webhook delivery, then resend that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or a different `X-Shopify-Topic`, such as a mandatory GDPR topic like `shop/redact` or `customers/redact`).

`Registry.process` never re-derives or independently checks the shop identity — it validates HMAC first [5](#0-4) , then unconditionally builds `WebhookMetadata` from the header-derived, attacker-controlled `request.shop` and `request.topic` [6](#0-5) . The handler therefore executes believing the event genuinely originated from the victim shop, when only the body's authenticity (as attacker's own store's data) was ever verified.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC is supposed to enforce: an app's webhook handler acts on data/identity for a shop it never actually received a signed event for. Depending on handler logic this can trigger cross-tenant actions such as forced data deletion/redaction (`shop/redact`, `customers/redact`), spoofed `app/uninstalled` events causing premature session/token invalidation for a victim shop, or ingestion of attacker-controlled data attributed to a victim tenant — i.e., cross-tenant access/manipulation, which maps to the Critical impact bucket.

### Likelihood Explanation
Likelihood is realistic: any user can install the target app on their own development/trial store to legitimately obtain valid `raw_body` + `hmac-sha256` pairs, then replay them against the app's public webhook endpoint with a forged shop-domain header — no access token, `client_secret`, or privileged account is required, and no other part of this gem re-validates the shop/topic identity.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material (or otherwise cryptographically bind them to the request), e.g., by having the caller supply and this gem verify the pairing of headers against a per-shop secret/session, or at minimum requiring the app to cross-check `request.shop` against the shop associated with the session/webhook registration before invoking the handler, rather than trusting header-only fields once a body-only HMAC check passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a legitimate webhook, e.g. topic `customers/redact`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H` (e.g., via a proxy they control since it is delivered to a URL they registered).
3. Attacker sends `POST <app-webhook-endpoint>` with the same raw body `B`, the same `X-Shopify-Hmac-Sha256: H` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: shop/redact`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` [5](#0-4) .
5. The app's registered handler for `shop/redact` is invoked with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to perform redaction/deletion or other tenant-scoped actions against the victim shop's data despite Shopify never having sent this event for that shop.
