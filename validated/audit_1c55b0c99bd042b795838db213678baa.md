### Title
RAY-domain debt overflow permanently freezes a whale market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Interest accrual converts scaled debt to its RAY-denominated original value before calculating utilization. When `borrowed * borrow_index` exceeds `i128::MAX`, `accrue_step` panics through `scaled_to_original`. Because every market-changing path accrues before applying the requested state transition, users cannot repay, withdraw, borrow, or liquidate once the market reaches this state. A permissionless `update_indexes` call can expose the condition once enough time has elapsed.

### Finding Description
`global_sync` invokes `accrue_step` before mutating or committing each market. `accrue_step` unconditionally evaluates:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
```

`scaled_to_original` delegates to `Ray::mul`, which panics with `MathOverflow` when the exact result does not fit `i128`. This occurs before `update_borrow_index` can clamp the next index at `MAX_BORROW_INDEX_RAY`.

The stored scaled debt can be within the admitted input domain while its value later grows outside the RAY-value domain. For example, one billion whole tokens at 18 decimals produces `1e36` scaled RAY units; approximately 173.7x index growth makes the borrowed value exceed `i128::MAX`. The repository explicitly documents that valid caps and bounded indexes do not ensure accrued market values fit the RAY domain, and that this can block repayment and withdrawal.

### Impact Explanation
The market becomes permanently unusable rather than merely reverting one transaction:

- `withdraw` calls `ops::load_leg`, which invokes `synced_market` and therefore `global_sync` before shares can be burned.
- `repay` follows the same `load_leg` path, so debt cannot be reduced after the overflow.
- Liquidation and new borrows also depend on market synchronization.
- `update_indexes` itself panics, preventing the market timestamp from reaching the current ledger time.
- The failed accrual leaves `last_timestamp` behind, so subsequent calls continue evaluating the same overflowing product.

This permanently freezes supplier funds, prevents borrowers from repaying, and makes liquidation unavailable for the affected `(hub_id, asset)` market. In-scope impact categories include permanent freezing of funds and protocol accounting becoming unable to operate for the market.

### Likelihood Explanation
The trigger requires an exceptionally large, high-utilization market, but it does not require privileged access or a code flaw outside normal protocol inputs:

1. A supplier deposits approximately `1e27` base units in an 18-decimal asset.
2. A sufficiently collateralized borrower borrows approximately 98% of the market.
3. The market remains highly utilized while its borrow index grows.
4. Any caller invokes `Controller::update_indexes(caller, assets)` with the affected `HubAssetKey`; the endpoint only requires the caller’s authorization.

The repository’s own harness reproduces this condition with `BILLION * 10^18` supplied and 98% borrowed, showing a `MATH_OVERFLOW` from `update_indexes`, followed by matching failures for withdrawal and repayment. Economic cost is the primary constraint, so the practical severity is Medium rather than High.

### Recommendation
Guard accrual before converting scaled debt to its original value. Suitable approaches include:

- Bound total scaled supply/debt so the maximum permitted `scaled * index` cannot exceed `i128::MAX`.
- Detect `scaled_to_original` overflow before utilization and clamp accrued debt to a protocol-defined terminal state.
- Apply the `MAX_BORROW_INDEX_RAY` cap before evaluating value-domain products, where safe.
- Add a recovery path that can lower debt shares or reset a terminally saturated market without first requiring overflowing utilization arithmetic.
- Emit an explicit saturation state and permit repayments based on a capped debt valuation rather than reverting during pre-action accrual.

Regression tests should cover `borrowed * borrow_index > i128::MAX` and verify that at least repayment, liquidation, or a governance-controlled recovery operation remains possible.

### Proof of Concept
The existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the sequence:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e;
    }
}
```

It observes `MATH_OVERFLOW` from `update_indexes`, before `MAX_BORROW_INDEX_RAY` engages, and then verifies that both `withdraw` and `repay` fail with the same error because those operations accrue first.
