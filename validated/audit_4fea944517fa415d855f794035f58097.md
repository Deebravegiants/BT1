### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook authenticity check (`ShopifyAPI::Utils::HmacValidator.validate`) verifies only the raw request body against the `X-Shopify-Hmac-Sha256` header. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers — which `ShopifyAPI::Webhooks::Registry.process` passes on to the host application's handler as the authoritative tenant/event identity — are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors simply read attacker-observable/attacker-suppliable HTTP headers with no cryptographic binding to them: [2](#0-1) .

`Registry.process` relies on `Utils::HmacValidator.validate(request)` as its sole authenticity gate, and once that passes, forwards `request.shop`, `request.topic`, `request.parsed_body`, and `request.webhook_id` to the registered `WebhookHandler` as trusted values identifying which shop/tenant and which event the payload belongs to: [3](#0-2) .

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with `verifiable_query.hmac` using `secure_compare` — i.e. it authenticates *only the body bytes* under the app's shared `client_secret`: [4](#0-3) .

Because the same app-level `client_secret` signs webhooks for every shop that installs the app, and the signature is a function of body content alone, any party who can obtain one genuine `(body, hmac)` pair for the app — e.g., by installing the app on their own store and receiving a real webhook with body content that does not itself encode the shop (many webhook payloads, and any webhook whose payload happens to coincide across shops, satisfy this) — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to point at a different, victim shop. The signature remains valid because those header values were never part of the signed data, so `Registry.process` accepts the forged request and dispatches it to the handler labeled with the attacker-chosen shop.

This is the same "field acted on but not covered by the HMAC" class of bug as the reported staking-contract issue: the report flags that `unstakeFine`, a value acted upon in `_repay`, is never transferred/reconciled although the code treats it as settled; here, `shop`/`topic`/`webhook_id` are values acted upon by `Registry.process` (used to dispatch and attribute the event) without ever being bound into the cryptographic check that is supposed to make the whole request trustworthy. The broken identity equality is: `shop_authenticated_by_hmac == shop_used_to_attribute_event`, which does not hold here.

### Impact Explanation
An attacker can make the host application process a webhook body as if it originated from an arbitrary victim shop domain, without possessing that shop's credentials or the app's `client_secret`. Depending on which webhook topic is impersonated (e.g., `app/uninstalled`, `shop/update`, mandatory GDPR topics `customers/data_request`, `customers/redact`, `shop/redact`), this can trigger cross-tenant side effects such as spurious uninstall handling, data-erasure workflows, or other tenant-scoped business logic being executed against the wrong shop record — a cross-tenant integrity issue.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on any shop the attacker controls (unprivileged, standard app-install flow) to obtain one legitimate `(body, hmac)` pair, and (2) sending a crafted HTTP POST to the app's webhook endpoint with that body/hmac and forged shop/topic headers. No `api_secret_key`, access token, or privileged account is required, and no TLS interception is needed since the attacker is originating the forged request directly.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., derive/verify them from a signed value rather than plain headers) before `Registry.process` trusts and dispatches them to handlers.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture a legitimate webhook delivery for a topic whose body doesn't (or coincidentally doesn't) encode shop-specific data, recording the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H`.
2. Construct a new HTTP request to the app's webhook endpoint using the exact same raw body `B` and `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic` value corresponding to a topic the app also registered).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (`= B`) and successfully matches `H`, since `shop`/`topic` were never part of the signed bytes: [4](#0-3) [5](#0-4) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes it as a legitimate event for that shop: [6](#0-5) .
