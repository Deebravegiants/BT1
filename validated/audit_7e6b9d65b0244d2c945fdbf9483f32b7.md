### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while `to_signable_string` (used by `HmacValidator`) signs only the raw request body. `Registry.process` validates the HMAC and then trusts these header-derived fields to build `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` as the authoritative shop/topic identity for the webhook.

### Finding Description
`HmacValidator.validate` computes/verifies the signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of HTTP headers with no cryptographic binding to the body/HMAC: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only check) before constructing `WebhookMetadata` from these header fields and dispatching to the app's handler: [4](#0-3) 

`WebhookMetadata` is the struct the host application's `WebhookHandler#handle` receives as the trusted shop/topic identity: [5](#0-4) 

The identity binding broken is: **`request.shop` / `request.topic` (acted on by the handler) ≠ `request.hmac` (computed over `raw_body` only)**. The gem's `api_secret_key` is shared across every shop that has installed the app (it is not per-tenant), so any tenant that legitimately receives webhooks from Shopify obtains valid `(raw_body, hmac)` pairs signed with that same shared secret. Because the headers are not part of the signed material, an attacker who controls one shop (their own install of the app) can capture a legitimately-signed `(raw_body, hmac)` pair from their own webhook deliveries and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header for a victim shop. `HmacValidator.validate` still succeeds (it never inspects the headers), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` claiming to be the victim shop while `body` is fully attacker-controlled.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: the gem provides no mechanism to bind the claimed `shop` (and `topic`/`webhook_id`) to the cryptographic proof of authenticity, yet exposes exactly those fields to the host application as if they were verified. Any downstream logic that keys per-tenant state, triggers billing/scope actions, or performs GDPR mandatory-topic handling (`shop/redact`, `customers/redact`, `customers/data_request` — topics this gem explicitly special-cases) off of `WebhookMetadata#shop`/`#topic` can be made to act on a victim shop using attacker-supplied body content, without the attacker ever possessing the app's `api_secret_key`. This matches "cross-tenant access" (Critical) since it lets one tenant of a multi-tenant app impersonate another tenant's webhook identity while still passing this gem's own signature check.

### Likelihood Explanation
Likelihood is realistic for any app built on this gem that is installed on more than one shop (the standard case for a public Shopify app): a malicious merchant only needs to install the app on their own shop (an unprivileged, self-service action), trigger any webhook event, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair sent to their own registered endpoint, and resend it to the app's shared webhook endpoint with modified `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers. No knowledge of `api_secret_key`, access tokens, or victim credentials is required.

### Recommendation
- Do not derive trust-bearing identity (`shop`, `topic`, `webhook_id`) purely from HTTP headers when the HMAC only covers the raw body. Either:
  - Extend `to_signable_string` to include the header fields that are later treated as trusted (mirroring how Shopify's own HMAC computation for OAuth query params covers all fields used downstream), or
  - Document/enforce that consumers must independently verify `WebhookMetadata#shop` against a known/expected shop and not use it as an authorization boundary, and
  - Consider tying webhook acceptance to the registered `webhook_id`/subscription per shop (looked up server-side) rather than trusting the header value verbatim.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets it register a webhook, e.g., `orders/create`.
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and some JSON body `B`.
3. Attacker captures `B` and the valid `X-Shopify-Hmac-Sha256` value.
4. Attacker crafts a new HTTP request to the same public webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic` matching another registered handler).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the shared `api_secret_key` — see [6](#0-5) .
6. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: B, ...)`, i.e., attacker-controlled data attributed to the victim shop, despite the attacker never possessing `api_secret_key` for any shop but their own.
