### Title
Emporium `runAction` orphans non-ERC20 positions and lets any unprivileged caller drain them via unrestricted `op.endpoint.call` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only ever converts balance deltas of tokens explicitly listed in `circomData.erc20TokenAddresses` into outgoing UTXOs bound to `circomData.stealthAddressStructure`; any non-ERC20 asset (NFT, LP-NFT, staking receipt) minted to the Emporium contract during an op is left owned by `address(this)` with no code path that will ever emit a UTXO for it. Because the "Stateless Interaction" branch executes `op.endpoint.call{value: op.value}(op.callData)` with essentially no restriction on target or calldata (only two wallet-selectors are blacklisted), any later unprivileged caller can craft an `EmporiumOperation` whose `endpoint` is that stranded asset's contract and whose `callData` transfers it out of Emporium to themselves.

### Finding Description
Equality claimed broken: `set(asset types ever minted as UTXO for a user via handleOut) == set(asset types that user's ops actually create/receive)`.

- `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) snapshots balances only for `circomData.erc20TokenAddresses` before/after executing `stack.ops`, and the resulting UTXO set is built exclusively from that same array in the loop at lines 132-151, calling `handleOut` per index.
- `handleOut` (lines 162-184) hardcodes `circomData.erc20TokenAddresses[i]` as `UTXO.erc20Address` and `circomData.stealthAddressStructure` as the destination binding — there is no path in which a UTXO's `erc20Address`/token identity can be anything other than an entry of that caller-supplied array.
- If an op mints/receives an asset not present in `erc20TokenAddresses` (e.g., an LP-NFT, staking receipt, or any ERC721/1155), the asset remains owned by the Emporium contract (`address(this)`) after the transaction completes; nothing ever routes it to any stealth address, so it is permanently orphaned under Emporium's custody until someone reclaims it out-of-protocol.
- The "Stateless Interaction" branch (lines 102-113) performs `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == address(EmporiumUpgradeable)`. The only restriction is a selector blacklist for `IHinkalWallet.callHinkalWallet` / `doSendToRelay` (lines 104-110); there is no check binding `op.endpoint`/`op.callData` to `circomData.erc20TokenAddresses`, to `circomData.originalSender`, or to any identity of who created the underlying asset.
- Because `runAction` is only gated by `onlyAllowedRecipient` (i.e. callable via `Hinkal._externalTransact`, reachable by any unprivileged caller supplying a valid proof for their own UTXOs/nullifiers — see `contracts/Hinkal.sol:31-65, 234-261`), any attacker can submit their own deposit/op with `erc20TokenAddresses` containing tokens they own, while separately crafting `stack.ops[i].endpoint = <stranded asset address>` and `callData = transferFrom(address(EmporiumUpgradeable), attacker, tokenId)` (or equivalent `withdraw`/`transfer` call for staking receipts). Since the Emporium contract is the actual on-chain owner/holder of that asset, the call succeeds.
- None of the listed guards prevent this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate the attacker's own nullifiers/roots/`erc20TokenAddresses` balance deltas; the circuit's `inTotal + amountChanges === outTotal` constraint only binds the fungible balance bookkeeping for the caller's declared tokens, never constraining `op.endpoint`/`op.callData` bytes, which are free-form calldata passed straight to `runAction`.

### Impact Explanation
Two compounding critical impacts: (1) permanent freezing of a victim's user funds — a non-ERC20 position (LP-NFT, staking receipt) created via Emporium can never be resolved into a UTXO for the victim, since `handleOut`/`runAction` structurally excludes any asset not in `circomData.erc20TokenAddresses`; and (2) that frozen asset is not even safely frozen — it sits in Emporium's own custody and any unprivileged third party can steal it in a subsequent transaction by crafting an `EmporiumOperation` targeting the asset's contract directly, because the stateless-op call path enforces no ownership/originator binding. This is repeatable for every non-ERC20 asset any user's Emporium op ever creates.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: they need their own funds/UTXOs and a valid proof for their own deposit (standard usage), plus knowledge of the address/interface of the stranded asset (discoverable on-chain from prior Emporium transactions/logs). No special role, victim cooperation, or race condition is required — the theft can happen anytime after the asset lands in Emporium, and is fully deterministic and reproducible.

### Recommendation
Restrict `EmporiumOperation.endpoint`/`callData` execution paths so they cannot be pointed at arbitrary contracts/functions unrelated to the declared `circomData.erc20TokenAddresses`/positions, and add explicit support for non-fungible/receipt assets: either (a) require any asset produced by an op to be enumerated and bound to `circomData.stealthAddressStructure` (e.g., via an NFT-aware UTXO type or an allowlist of "receipt" tokens tracked similarly to `erc20TokenAddresses`), or (b) restrict stateless op calls to a caller-scoped allowlist/permission system so `address(this)`-held assets can't be moved by unrelated third parties, and add tracking so that any asset transferred into Emporium during an op is immediately transferred out to `msg.sender`/wallet by the end of the same transaction rather than persisted in Emporium's own balance.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock ERC721 ("ReceiptNFT") mintable by anyone calling a `stake()`-like function on a mock `Staking` contract that mints/transfers the NFT to `msg.sender`.
2. Victim calls Hinkal's external-transact flow with a valid proof/deposit, with `circomData.erc20TokenAddresses = [depositToken]` and `EmporiumStack.ops = [{ endpoint: Staking, invokeWallet: false, callData: stake(...) }]`; assert `ReceiptNFT.ownerOf(tokenId) == address(EmporiumUpgradeable)` after the tx, and assert the returned `utxoSet` contains no UTXO with `erc20Address == address(ReceiptNFT)` (confirming the equality break: no UTXO for the created position type).
3. Attacker (different EOA, own funds/proof, `erc20TokenAddresses` unrelated to the receipt) submits an Emporium op with `endpoint = ReceiptNFT`, `callData = abi.encodeWithSelector(IERC721.transferFrom.selector, address(EmporiumUpgradeable), attacker, tokenId)`.
4. Assert the call succeeds and `ReceiptNFT.ownerOf(tokenId) == attacker`, proving third-party theft of an asset the attacker never created and had no proof-based claim to, with no revert from `performHinkalChecks`/`runAction`/selector checks.
