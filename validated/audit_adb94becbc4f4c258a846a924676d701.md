### Title
Placing an IntentGateway order with an ERC721 (or other non-standard "token") as an input asset permanently freezes escrowed funds and can be used to steal solver capital - ([File: evm/src/apps/intentsv2/IntentGatewayV2.sol])

### Summary
`placeOrder` accepts any address as `order.inputs[i].token` and escrows it using the ERC20 `transferFrom`/`safeTransferFrom` selector without ever verifying the token is a well-behaved ERC20. Because `ERC721.transferFrom(address,address,uint256)` shares the exact 4-byte selector with `ERC20.transferFrom`, a user can "fund" an order with an ERC721 token id disguised as an ERC20 `amount`. The escrow succeeds, but ERC721 contracts have no `transfer(address,uint256)` function (the selector `IntentsBase._withdraw` calls when releasing escrow), so the withdrawal/refund call reverts every time it is attempted — this is the same "fund ERC721 as ERC20 to block withdraw" bug class as the OpenQ report, but reachable here through the Intent Gateway settlement path.

### Finding Description
`placeOrder` treats every `order.inputs[i].token` as an arbitrary address with no whitelist, then escrows it via the standard ERC20 interface: [1](#0-0) 

If `token` is actually an ERC721 contract and the caller owns the token id equal to `order.inputs[i].amount` (and has approved the gateway), `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` succeeds because `ERC721.transferFrom(address,address,uint256)` has the identical selector (`0x23b872dd`) as `ERC20.transferFrom`. The gateway happily records the NFT id as an ERC20 "amount" in escrow: [2](#0-1) 

When the order is later settled — either on a cross-chain fill via the `RedeemEscrow`/`RefundEscrow` message handled in `onAccept` (`ExtrinsicIntents.sol`), or on a same-chain refund/fill — the escrow is released through `IntentsBase._withdraw`, which unconditionally calls the plain ERC20 `transfer` selector: [3](#0-2) 

ERC721 tokens do not implement `transfer(address,uint256)` (selector `0xa9059cbb`); the low-level call has no matching function and no fallback, so `SafeERC20.safeTransfer` reverts (`"SafeERC20: low-level call failed"`), exactly mirroring the OpenQ proof-of-concept. Because `_withdraw` loops over `body.tokens` and any single failing transfer reverts the whole call, this DoS's the release of **every** token entry tied to that `commitment`, not just the poisoned one.

### Impact Explanation
This is worse than a simple griefing DoS on the placer's own funds:
- For cross-chain orders, the `RedeemEscrow` message is delivered via `EvmHost.dispatchIncoming`/`onAccept`; a revert inside `onAccept` causes the host to delete the request receipt so it can be retried — but retries will deterministically revert forever since the "token" can never satisfy the `transfer` selector, permanently freezing the escrow (`_orders[commitment][token]`) and the message can never be delivered ("a route unable to deliver messages").
- Because the escrow release for an order is atomic across all its input tokens, a malicious user can pair one legitimate, valuable input token with one poisoned ERC721 "input." The solver fills the order and delivers real value on the destination chain, expecting to redeem the escrowed inputs on the source chain. The redemption reverts permanently, so the solver never receives their legitimate reimbursement — a direct theft of solver capital, and a permanent freeze of the legitimately-escrowed token as well, since it is bundled into the same non-recoverable withdrawal.
- The same mechanism applies to `RefundEscrow`/cancellation, so a user could even deny themselves (or an operator relying on refund paths) recovery of escrowed capital, but the more severe case is the solver-theft scenario above, satisfying High severity ("concrete theft ... or permanent freezing of funds").

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with attacker-controlled `order.inputs`; no whitelist of token addresses is enforced anywhere in `IntentGatewayV2.placeOrder`. The only precondition is owning/approving an ERC721 (or any non-standard contract lacking `transfer(address,uint256)`) that the attacker can mint or acquire cheaply, making this trivially and cheaply exploitable by any single dispatched order.

### Recommendation
Validate that every `order.inputs[i].token` (and output/predispatch tokens) is a genuine ERC20 before accepting it into escrow — e.g., require successful `IERC20(token).totalSupply()`/`decimals()` calls, enforce an allowlist of supported tokens, or perform a `try/catch` around the initial `transferFrom` and post-transfer balance checks that fail closed for non-conforming tokens. Additionally, consider isolating each token's release in `_withdraw` (e.g., using low-level calls with individual try/catch and per-token failure accounting) so that one malformed token cannot block redemption of the other legitimately escrowed assets in the same order.

### Proof of Concept
1. Attacker deploys/uses an ERC721 contract `NFT` and mints token id `T` to themselves; approves the `IntentGatewayV2` for `T`.
2. Attacker calls `placeOrder` with `order.inputs = [{token: address(NFT), amount: T}]` and a legitimate output requirement (e.g., real USDC) that a solver will find profitable to fill.
   - `IntentGatewayV2.placeOrder` → `IERC20(NFT).safeTransferFrom(attacker, gateway, T)` succeeds because `ERC721.transferFrom` shares the same selector; `_orders[commitment][NFT] = T` is recorded as if it were `T` units of an ERC20 (`evm/src/apps/intentsv2/IntentGatewayV2.sol:313-373`).
3. A solver, seeing a seemingly valid order (they cannot easily distinguish token type from the ABI-encoded address/amount alone), fills the order on the destination chain, delivering real output tokens to the beneficiary, and the fill dispatches a `RedeemEscrow` message back to the source chain (`ExtrinsicIntents.sol` fill logic).
4. On the source chain, `onAccept` decodes the `WithdrawalRequest` and calls `IntentsBase._withdraw`, which attempts `IERC20(NFT).safeTransfer(solver, T)` (`evm/src/apps/intentsv2/IntentsBase.sol:451-469`). This reverts because `NFT` has no `transfer(address,uint256)` function.
5. The revert causes the source-chain host to mark the request as retryable and delete its receipt, but every subsequent relayer retry will revert identically — the escrow (including any co-escrowed legitimate ERC20 inputs under the same commitment) is permanently frozen, and the solver never recovers the value they already delivered on the destination chain.
