### Title
Emporium's balance-diff accounting loop only covers `erc20TokenAddresses`, letting any unprivileged caller drain non-ERC20 balances (e.g. ERC1155/ERC721 positions) parked in the Emporium contract via an unauthenticated CASE-2 op - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` computes `balanceChange` only for tokens listed in `circomData.erc20TokenAddresses`, and CASE-2 ("stateless") ops in the `EmporiumStack` execute arbitrary calls from the Emporium contract's own address without requiring any wallet signature when `stack.signerAddress == address(0)`. Any asset class outside `erc20TokenAddresses` (such as an ERC1155 token minted to Emporium by a prior action) is invisible to the accounting loop, and any attacker can submit their own `transact` call whose `EmporiumStack` contains a CASE-2 op that calls `safeTransferFrom(Emporium, attacker, id, amount, "")` on that token, succeeding because `from == msg.sender` (both are the Emporium contract) - draining the asset with zero on-chain accounting.

### Finding Description
The broken equality: for every `i` in `circomData.erc20TokenAddresses`, `EmporiumUpgradeable.runAction` asserts `balanceChange == balancesAfter[i] - balancesBefore[i] (+/- deltaAmountChanges[i])` and turns any positive residual into a UTXO via `handleOut`: [1](#0-0) 

This loop's domain is strictly `circomData.erc20TokenAddresses`, an array fully controlled by whoever submits the `transact` call (the attacker, for their own action), via `Transferer.getBalancesForArray` which only knows how to read ETH/ERC20 balances: [2](#0-1) 

If a victim's earlier CASE-2 op causes an ERC1155 (or ERC721) to be received by `address(Emporium)` (e.g. via `onERC1155Received` during a vault-deposit call), that token address is never a member of the victim's `erc20TokenAddresses`, so the accounting loop never computes a `balanceChange` for it, and `handleOut`/`utxoSet` never records it as belonging to the victim: [3](#0-2) 

CASE-2 ops execute as `op.endpoint.call{value: op.value}(op.callData)` directly from `EmporiumUpgradeable`, i.e. `msg.sender` inside the call is the Emporium contract itself, and are blocked only from calling the `callHinkalWallet`/`doSendToRelay` selectors - no other restriction on target or asset: [4](#0-3) 

Crucially, `verifyWallet` requires an EIP-712 signature from `stack.signerAddress` only if `stack.signerAddress != address(0)`; when it's the zero address, the function simply marks the message as used and returns, with no signature check at all: [5](#0-4) 

Therefore an unprivileged attacker can submit their own independent `Hinkal.transact` call (with their own valid proof over their own nullifiers/UTXOs) whose `circomData.externalActionData.externalActionMetadata` decodes to an `EmporiumStack` with `signerAddress = address(0)` and a single CASE-2 op calling `IERC1155(token).safeTransferFrom(address(Emporium), attacker, id, amount, "")`. Since `from == msg.sender` (`Emporium == Emporium`), the ERC1155 contract's authorization check passes trivially, and the transfer succeeds - with `token` never appearing in the attacker's own `erc20TokenAddresses` either, so no `require` in `runAction` or in `Hinkal.transact`'s balance-diff/slippage loop (`contracts/Hinkal.sol:97-147`) ever inspects this asset.

`performHinkalChecks`/`getHashedCalldata` only verify that `calldataHash` matches the caller's own supplied fields (integrity of the attacker's own call), not that the `externalActionMetadata` content is limited to safe operations or bound to a specific victim-owned asset: [6](#0-5) [7](#0-6) 

None of the existing guards (`onlyAllowedRecipient` - which only checks `msg.sender == Hinkal`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, `nonReentrant`) constrain which contracts/assets a CASE-2 op can touch, nor do they reconcile Emporium's holdings against anything but the caller-chosen `erc20TokenAddresses` list.

### Impact Explanation
Critical - direct theft of a victim's shielded-created position (any ERC1155/ERC721 or other non-listed asset sitting in Emporium) with no on-chain accounting event catching it. The attacker's gain equals the full value of the stranded asset per occurrence, and the attack is repeatable against any future victim action that leaves such an asset in Emporium, at the cost of only a normal `transact` call (attacker's own valid proof/UTXO, no special privilege).

### Likelihood Explanation
Requires a precondition that some action (an integration, hook, or CASE-2 call performed by any user) results in Emporium holding a non-ERC20/ETH asset (ERC1155/ERC721) that is not included in that transaction's `erc20TokenAddresses`. Given Emporium's design explicitly allows arbitrary CASE-2 stateless calls to arbitrary `endpoint` contracts (e.g., vault deposits returning share tokens), this is a realistic occurrence for any protocol integration using ERC1155/ERC721 share/receipt tokens. Exploitation itself requires no special access - any EOA can submit the draining `transact` call once the asset is observed sitting in Emporium (e.g., by monitoring on-chain events/balances).

### Recommendation
Extend Emporium's accounting to cover all asset classes that CASE-2 ops can move, not just `erc20TokenAddresses`: either (a) require any asset touched by an op (via static analysis of `op.callData`/`op.endpoint` or an explicit `assetType`/`assetId` field in `EmporiumOperation`) to be declared and balance-diffed the same way ERC20/ETH are, and revert if a positive balance change of an undeclared asset is detected, or (b) restrict CASE-2 stateless calls to a governance-controlled allowlist of `(endpoint, selector)` pairs so arbitrary transfer-type calls cannot be crafted by unprivileged callers, or (c) after every op loop, verify no unaccounted asset increase occurred for a known set of "sensitive" token standards (ERC721/ERC1155 `balanceOf`) tied to `originalSender`/ownership bookkeeping rather than raw contract balance.

### Proof of Concept
Hardhat test plan:
1. Deploy `EmporiumUpgradeable`, `Hinkal`, a mock ERC1155 vault-share token, and a mock vault/hook endpoint that mints/transfers the ERC1155 to `address(Emporium)` inside a CASE-2 `safeTransferFrom`/deposit call.
2. Victim calls `Hinkal.transact` with a valid proof, `erc20TokenAddresses` containing only ETH/ERC20 (never the ERC1155 address), and an `EmporiumStack` with a CASE-2 op that causes the mock vault to send ERC1155 shares to `address(Emporium)`.
   - Assert: `mockERC1155.balanceOf(Emporium, id) > 0` after the call.
   - Assert: the `utxoSet` returned to the victim (and any emitted commitments) never references the ERC1155 token/id - `EmporiumUpgradeable.handleOut` and the `balancesBefore`/`balancesAfter` diff never touched index for that token because it's absent from `erc20TokenAddresses`.
3. Attacker (separate EOA, no special role) calls `Hinkal.transact` with their own valid proof/nullifiers, `erc20TokenAddresses` again excluding the ERC1155 address, and an `EmporiumStack` with `signerAddress = address(0)` and a CASE-2 op: `mockERC1155.safeTransferFrom(Emporium, attacker, id, amount, "")`.
   - Assert: call succeeds (no signature required, `verifyWallet` short-circuits for `signerAddress == address(0)`).
   - Assert: `mockERC1155.balanceOf(Emporium, id) == 0` after attacker's call, `mockERC1155.balanceOf(attacker, id) == amount`.
   - Assert: no `require` in `Hinkal.transact` or `EmporiumUpgradeable.runAction` reverted, and neither transaction's balance-diff loop (`balanceDif`/`balanceChange`) ever included the ERC1155 asset, confirming the accounting equality was never evaluated for it while real value left the contract.

        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
