### Title
Unguarded multiplication overflow in `calculate_reward_and_burn_fee_details` when `transaction_fee` is attacker-inflated - (File: `runtime/src/bank/fee_distribution.rs`)

### Summary
`Bank::calculate_reward_and_burn_fee_details` computes the burn amount using a plain, non-saturating multiplication: `fee_details.transaction_fee * self.burn_percent() / 100`, unlike essentially every other fee/cost computation in the codebase which consistently uses `saturating_mul`/`checked_mul`/`checked_div`. This is structurally the same bug class as the reported `ChainlinkOracleComposite.getPrice` issue: an unguarded `*`/`/` pair fed by a value that can be pushed by ordinary user input (compute-unit price) toward the numeric type's ceiling, causing overflow.

### Finding Description
`calculate_reward_and_burn_fee_details` is called on every fee-charging path — per-transaction (`calculate_reward_for_transaction`) and per-slot at freeze time (`distribute_transaction_fee_details`) [1](#0-0) . The `burn` calculation:

```rust
let burn = fee_details.transaction_fee * self.burn_percent() / 100;
```

uses raw `u64` multiplication instead of `saturating_mul`/`checked_mul` [2](#0-1) . Every neighboring computation in the same function and file uses `saturating_add`/`saturating_sub` [3](#0-2) , and the entire fee/compute-budget/cost-model subsystem elsewhere consistently guards against overflow with `saturating_mul`, `checked_mul`, or `u128` widening before narrowing back to `u64` (e.g. `get_prioritization_fee` in `compute-budget/src/compute_budget_limits.rs:61-69`, `calculate_priority_and_cost` in `core/src/transaction_priority.rs:32-66`, `calculate_signature_fee` in `fee/src/lib.rs:42-56`). This one instance stands out as unprotected.

`fee_details.transaction_fee` originates from `solana_fee::calculate_fee_details`, which sums the signature fee and the attacker-supplied prioritization fee [4](#0-3) . The prioritization fee itself is derived from `ComputeBudgetInstruction::set_compute_unit_price` × `compute_unit_limit`, computed in `u128` and clamped to `u64::MAX` via `.unwrap_or(u64::MAX)` in `get_prioritization_fee` [5](#0-4) . This means an ordinary, unprivileged user can construct a transaction whose `transaction_fee` is arbitrarily close to `u64::MAX` simply by setting an extreme `compute_unit_price`.

### Impact Explanation
With `transaction_fee` near `u64::MAX` and `burn_percent()` = 50 (a `const fn` returning the static `DEFAULT_BURN_PERCENT`) [6](#0-5) , the multiplication `transaction_fee * 50` overflows `u64` well before division by 100 can bring it back into range. In debug/test builds this triggers an arithmetic-overflow panic, which — because this function executes inside `distribute_transaction_fee_details`, called on the bank-freeze path (an unprivileged-user-reachable code path, since any signed transaction can carry an arbitrary `compute_unit_price`) — would halt block production for the affected validator. In release builds (Rust's default `overflow-checks = false` unless overridden), the multiplication silently wraps, producing an incorrect `burn` value that is then used to update `self.capitalization.fetch_sub(total_burn, Relaxed)` [7](#0-6) , corrupting the bank's tracked capitalization and the reward/burn split recorded for the block, without any panics on chain — a form of undeclared value creation/loss and potential cross-node divergence if `overflow-checks` build settings ever differ across validators or between debug tooling (e.g., conformance harness) and production binaries.

### Likelihood Explanation
Reachability requires only a single, unprivileged, ordinary transaction with `ComputeBudgetInstruction::set_compute_unit_price` set to a near-maximal value combined with a large compute unit limit, both of which are entirely user-controlled compute-budget instructions with no special permissions needed. Whether Solana's production release profile has `overflow-checks` enabled is not something I could confirm from the code searched (workspace `Cargo.toml` build profile was not located in the results); if it is disabled, the practical effect is silent capitalization corruption rather than a panic, which lowers the "freeze the network" likelihood relative to the reported oracle bug but keeps a lower-severity accounting-corruption risk. I could not find a fuzz/property test in `runtime/src/bank/fee_distribution.rs` exercising `calculate_reward_and_burn_fee_details` with extreme `transaction_fee` values, only the unrelated `test_deposit_fees_with_overflow` test for `deposit_fees`'s lamport-add overflow handling [8](#0-7) , suggesting this specific overflow path is untested.

### Recommendation
Replace the raw multiplication/division with a saturating or checked equivalent, consistent with every other fee computation in the codebase, e.g.:
```rust
let burn = fee_details
    .transaction_fee
    .saturating_mul(self.burn_percent())
    .checked_div(100)
    .unwrap_or(0);
```
or perform the computation in `u128` and clamp back to `u64`, matching the pattern already used in `compute-budget/src/compute_budget_limits.rs`.

### Proof of Concept
1. Submit a transaction containing `ComputeBudgetInstruction::set_compute_unit_price(u64::MAX)` and a large `set_compute_unit_limit`, causing `get_prioritization_fee` to saturate to (or very near) `u64::MAX` [5](#0-4) .
2. `solana_fee::calculate_fee_details` returns a `FeeDetails` whose `total_fee()`/`transaction_fee` is near `u64::MAX` [4](#0-3) .
3. On bank freeze, `distribute_transaction_fee_details` invokes `calculate_reward_and_burn_fee_details`, where `fee_details.transaction_fee * self.burn_percent()` (i.e., `~u64::MAX * 50`) overflows `u64` [1](#0-0) .
4. In a debug/overflow-checked build this panics, halting the validator; in a release build it wraps to an incorrect `burn` value that is subtracted from `self.capitalization` [7](#0-6) .

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
