The docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , but the only check performed is `Utils::HmacValidator.validate(request)` against `to_signable_string`, which for `Webhooks::Request` returns solely the raw request body [2](#0-1) . The `shop`, `topic`, and `webhook_id` values are read straight from unauthenticated HTTP headers and are never included in the signed string [3](#0-2) . `Registry.process` then passes `request.shop` verbatim into `WebhookMetadata` for the host app's handler [4](#0-3) .

### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC verification only binds the raw JSON body. The `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers, which the gem trusts as the tenant identity for dispatching to handlers, are excluded from the signed payload.

### Finding Description
`Utils::HmacValidator.validate` computes `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC [5](#0-4) . For webhook requests, `to_signable_string` is defined to return only `@raw_body` [2](#0-1) . The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature [6](#0-5) [7](#0-6) .

`Registry.process` validates only the HMAC over the body, then dispatches the handler using the unauthenticated `request.shop`: [4](#0-3) 

The identity binding broken here is: **HMAC-signed bytes (body) ≠ bytes acted on for tenant identity (shop header)**. Because the header is outside the signature, any party who ever legitimately receives one valid `(body, hmac)` pair for their own shop (i.e., any ordinary merchant that has installed the app) can capture that pair from their own webhook traffic and replay the identical body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value for another tenant. `HmacValidator.validate` will still return `true` because the signature check never inspected the header, and `Registry.process` will hand the forged `shop` value straight to the app's `WebhookHandler` as if the event genuinely originated from that other shop.

### Impact Explanation
This breaks tenant isolation for any host application that (reasonably, given the gem's own documentation) trusts `WebhookMetadata#shop` as an authenticated tenant identifier once `Registry.process` succeeds. An attacker-controlled merchant (unprivileged relative to other tenants) can inject a spoofed webhook event attributed to a victim shop into the app's webhook processing pipeline — e.g., triggering `shop/redact`, `orders/create`, or other topic handling logic tagged with an arbitrary victim shop domain, causing cross-tenant data confusion/injection in the host application's session, billing, or data-sync logic keyed by `data.shop`.

### Likelihood Explanation
Any installed merchant of the app already receives real, validly-signed webhook events for their own store and can trivially capture `raw_body` + `X-Shopify-Hmac-Sha256` from their own traffic (no leaked secret needed) and replay it with a different `Shop-Domain`/`Topic` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the target shop's data is required — only a standard, unprivileged merchant install of the app.

### Recommendation
Bind the tenant-identifying headers to the signature verification step, e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or perform a secondary check comparing the header-derived `shop` against a value already known to the host app for that specific installation/session before dispatching), rather than relying on the raw body alone to represent request authenticity for header-derived fields such as `shop`.

### Proof of Concept
1. As a legitimate merchant `shop-a.myshopify.com` with the app installed, trigger a real event (e.g., `orders/create`) and capture the resulting webhook POST: `raw_body` and header `X-Shopify-Hmac-Sha256: <hmac>`.
2. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: shop-victim.myshopify.com` and, optionally, `X-Shopify-Topic` to a different registered topic.
3. `Utils::HmacValidator.validate(request)` returns `true` (it only hashed `raw_body`, unchanged) [2](#0-1) .
4. `Registry.process` looks up the handler by `request.topic` and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`, delivering `shop: "shop-victim.myshopify.com"` to the host app's handler [4](#0-3) , even though the event never came from that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
