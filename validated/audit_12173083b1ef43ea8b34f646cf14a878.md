### Title
Webhook shop/topic identity headers are parsed and dispatched but not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-covered "signable string" as the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and later used verbatim to select the tenant/handler that acts on the payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#shop`/`#topic`/`#webhook_id`/`#api_version` are pulled straight from `@headers` with no cryptographic binding to the body [2](#0-1) . `Registry.process` validates only that this body-only HMAC is correct via `Utils::HmacValidator.validate(request)`, then dispatches to a handler using the unauthenticated `request.shop` and `request.topic` values, passing them into `WebhookMetadata` for the handler to act on [3](#0-2) . `HmacValidator.validate` in turn calls `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received signature [4](#0-3) , so the equality actually enforced is `HMAC(secret, raw_body) == received_hmac`, not `HMAC(secret, raw_body ∥ shop ∥ topic) == received_hmac`.

This mirrors the report's bug class: a field that is acted upon (`shop`, used as the tenant key for dispatch) is not covered by the authenticity check (the HMAC only binds the body). Because Shopify's webhook HMAC secret is the app's single `api_secret_key` shared across every shop that installs the app, any shop that installs the app can obtain a validly-signed `(body, hmac)` pair for a body of its choosing (e.g., a webhook triggered by an action on its own store, whose body content is influenced by the merchant, such as a product/customer field). That attacker-controlled shop can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for a victim shop, and the gem will accept it as authentic and dispatch it under the victim shop's identity.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is supposed to enforce for webhook delivery: `shop` used for dispatch/session lookup ≠ `shop` actually bound by the cryptographic signature. An app relying on `WebhookMetadata#shop` (as returned by `Registry.process`) to select per-tenant state (session/access token, data isolation, redaction processing, etc.) can be made to apply another shop's data/actions under an attacker-chosen shop identity — a cross-tenant integrity issue reachable by any unprivileged internet user who controls a legitimate installation of the app on their own store.

### Likelihood Explanation
Exploitation requires the attacker to operate their own installation of the target app (a normal, unprivileged action any merchant can take) in order to generate at least one validly-HMAC'd webhook body, then replay that raw body/HMAC pair to the app's public webhook endpoint with a modified `shop-domain`/`topic` header. No access to `api_secret_key`, tokens, or the victim's credentials is required — only capturing one's own legitimately delivered webhook traffic, which is straightforward.

### Recommendation
Bind the identity headers into the HMAC-covered signable string (or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the body before verification), and/or require the caller to supply an expected shop or session key to `Registry.process` that must independently match `request.shop` before dispatch, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving legitimate webhooks including one whose body the attacker can influence (e.g. a `products/update` webhook body they control content of).
2. Attacker captures the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` Shopify computed with the app's shared `api_secret_key`.
3. Attacker sends `POST <app_webhook_endpoint>` with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: products/update`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H` [4](#0-3) .
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "products/update", body: parsed(B), ...)` [5](#0-4) , causing the app to act on attacker-controlled data attributed to the victim shop.
