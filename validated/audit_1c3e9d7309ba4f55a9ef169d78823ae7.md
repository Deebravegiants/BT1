This is confirmed. The vulnerability is real and exploitable through the `unified_admin?` / host-matching logic in `sanitize_shop_domain`, not merely a "string concatenation with no re-validation" issue as loosely framed in the question, but the mechanism is the one I traced.

### Title
`ShopValidator.sanitize_shop_domain` accepts a userinfo-confused host as a trusted domain via `%40` encoding bypass - (File: `lib/shopify_api/utils/shop_validator.rb`)

### Summary
`uri_from_shop_domain` rejects a shop string only if it contains a literal `@`, but does not reject percent-encoded `%40`. Because `Addressable::URI.parse` does not treat `%40` as an authority delimiter, a crafted string like `attacker.com%40admin.shopify.com` is parsed as a single host whose `.domain` (eTLD+1) still resolves to `shopify.com`, so `sanitize_shop_domain` returns the entire attacker-prefixed string as a "trusted" shop domain.

### Finding Description
The intended invariant is: `sanitize_shop_domain(shop) == host` implies `host` is a hostname genuinely under `TRUSTED_SHOPIFY_DOMAINS` and safe to use as the network destination for OAuth/API requests carrying `client_secret`, the authorization `code`, and `X-Shopify-Access-Token`.

The guard at [1](#0-0) only checks for a literal `"@"` in the lowercased/stripped string before URI parsing. An attacker submits `shop=attacker.com%40admin.shopify.com` (no literal `@`), so this check passes. Addressable's authority parser splits on a literal `@` to separate userinfo from host; since none is present, the encoded sequence stays embedded in what becomes the single `host` component. Because host segments are dot-separated, the public-suffix–based `.domain` computed in [2](#0-1) still resolves to `shopify.com` off the trailing labels (`admin.shopify.com`), so `from_trusted_domain` is `true`, `no_shop_name_in_subdomain` is `false` (host != bare trusted domain), and the method returns the full string `host` — attacker-controlled prefix included — as the validated shop domain.

This validated-but-poisoned value is then used verbatim to build `@base_uri` in `Clients::HttpClient#initialize`: [3](#0-2) . Any consumer that passes a raw attacker-controlled `shop` string through `ShopValidator.sanitize!`/`sanitize_shop_domain` and then constructs a `Session`/`HttpClient` — e.g. `RefreshToken.refresh_access_token` [4](#0-3)  or `TokenExchange.migrate_to_expiring_token` [5](#0-4)  — will send the request (including `client_secret`, `refresh_token`/`code`, and `X-Shopify-Access-Token` if set on the session) to whatever DNS resolves the mangled host string to, which is attacker-influenced content preceding the real Shopify labels.

The existing guard `test_rejects_userinfo_before_at_sign` in `test/utils/shop_validator_test.rb` only covers the literal-`@` case and does not test the `%40`-encoded variant, so this bypass is untested and unguarded. [6](#0-5) 

### Impact Explanation
If the resulting URI is actually dereferenced with the attacker-prefixed host treated as (or resolving toward) attacker infrastructure, the app's `client_secret`, a refresh/access token, or an authorization code would be sent to a destination not in `TRUSTED_SHOPIFY_DOMAINS`, contrary to the library's stated invariant. This matches the "credential leaving for a host it should not" / theft of merchant token category described in the question, provided a host application ever forwards a raw `shop` string from an unauthenticated context into `refresh_access_token`, `migrate_to_expiring_token`, or similar helpers instead of using the already-established session's stored (already-sanitized-at-install-time) shop.

### Likelihood Explanation
This requires: (1) a host app that re-runs `ShopValidator.sanitize!/sanitize_shop_domain` on a user-supplied `shop` parameter for a privileged flow such as refresh-token exchange (i.e., app calls `RefreshToken.refresh_access_token(shop: params[:shop], ...)` with attacker-controlled `params[:shop]`), and (2) that whatever DNS/HTTP client resolves the resulting malformed host string in a way that lets an attacker-controlled label take effect (this depends on `HTTParty`/`URI`/DNS behavior on a hostname literally containing `%40`, which was not fully verifiable without live network testing). The gem-side logic flaw (accepting `%40` as bypassing the `@` check while still returning a `shopify.com`-suffixed but attacker-prefixed string as "trusted") is confirmed in code; whether it is exploitable end-to-end depends on host-app usage patterns and downstream URL/DNS handling that are outside this gem.

### Recommendation
In `uri_from_shop_domain`, reject the shop string if the raw or percent-decoded form contains any userinfo delimiter (`@` or `%40`, case-insensitive), or more robustly, parse the URI first, and explicitly reject if `uri.user` or `uri.password` (or any userinfo component) is present at all, rather than doing a naive substring check for `"@"` on the raw pre-parse string. Additionally, `sanitize_shop_domain` should validate that `host` is composed of well-formed hostname labels (no percent-encoding, no embedded delimiter characters) before returning it, rather than trusting `Addressable::URI#domain`'s public-suffix computation alone.
