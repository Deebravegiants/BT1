### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as authentic for a given shop as soon as `Utils::HmacValidator.validate(request)` returns true, but the HMAC signature only covers `@raw_body`. The `shop` (and `topic`/`webhook_id`/`api_version`) values passed downstream to the app's handler come from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from caller-supplied headers with no cryptographic binding: [4](#0-3) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only to the received HMAC over that signable string: [5](#0-4)  Since `to_signable_string` is just the body, a valid HMAC only proves "this body was signed with the app's secret" — it proves nothing about which shop, topic, or webhook the body belongs to.

`Registry.process` uses this weak guarantee to build a fully-trusted `WebhookMetadata` object and hand it to the app's handler: [2](#0-1)  `WebhookMetadata.shop` is a plain `String` field with no indication to the consuming app that it is unauthenticated: [3](#0-2)  The documented usage pattern explicitly tells developers to trust `Registry.process` to "verify the request did indeed come from Shopify" before invoking the handler: [6](#0-5) 

**Identity binding broken (equality that should hold but doesn't):**
`hmac_valid(raw_body) == true` is being treated as equivalent to `shop_header == actual_originating_shop`, but the gem never establishes `shop_header ⊂ signed_bytes`. Any party who can obtain one authentic `(raw_body, hmac)` pair signed with the app's shared `client_secret` — e.g., by installing the target app on their own, attacker-controlled development store and receiving one legitimate webhook delivery — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (same secret, same body), so `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, `WebhookMetadata#topic` set to whatever topic string the attacker chooses, and `webhook_id`/`api_version` likewise forged.

### Impact Explanation
Applications built on this gem commonly use the trusted-looking `shop` field from `WebhookMetadata` to look up the corresponding offline `Session`/access token and perform tenant-scoped actions (e.g., syncing orders, updating metafields, triggering fulfillment) attributed to that shop. Because the gem does not bind `shop` to the signed payload, an attacker who legitimately controls one shop that has the app installed can forge webhook deliveries appearing to originate from any other merchant shop, causing the app to process attacker-controlled data (order/product/customer payloads, etc.) under a victim tenant's identity — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is installing the target app on a store the attacker controls (a normal, unprivileged action available to anyone building on the Shopify platform) to obtain one valid `(body, hmac)` pair, then sending a crafted HTTP request directly to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or victim credential is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop actually known/installed for this app (and matches an expected value) before constructing `WebhookMetadata`, rather than trusting header values unconditionally once the body-only HMAC check passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they own) and registers a webhook, e.g. `orders/create`.
2. Shopify delivers a legitimate webhook to the app: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, HMAC(secret, B))` and replays a new HTTP POST directly to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B)` [7](#0-6) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [8](#0-7)  and invokes the app's `handler.handle(data:)`, which will act as if `victim-shop.myshopify.com` sent this webhook payload.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
