### Title
Unchecked raw `IERC20.transfer` return value in predispatch asset settlement lets a non-compliant token corrupt intent escrow accounting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` (Tron variant) uses `SafeERC20` for its direct `escrow`/`safeTransferFrom` calls, but the predispatch-asset settlement path builds a raw, unchecked `IERC20.transfer` call that is routed through `CallDispatcher`, which only checks the low-level call `success` flag and never inspects the ERC20 return value. This allows the gateway to credit escrow for tokens that were never actually received when a non-compliant ("no-op false-return") ERC20 is used as an order input.

### Finding Description
In the `open()`/predispatch flow, when an order has `predispatch.call` and `predispatch.assets`, tokens are first sent to the `dispatcher` (a `CallDispatcher`) via `safeTransferFrom` [1](#0-0) . After the predispatch call executes, the contract builds `Call[]` structs that move the resulting token balance from the dispatcher back to the `IntentGateway` using a manually-encoded, unchecked ERC20 transfer selector instead of `safeTransfer`: [2](#0-1) 

These `Call`s are then executed by `ICallDispatcher(dispatcher).dispatch(...)` [3](#0-2) . `CallDispatcher.dispatch` only reverts if the underlying low-level `call` itself reverts; it never decodes or checks the boolean return payload of the ERC20 call: [4](#0-3) 

Immediately after issuing this unchecked transfer call, `IntentGatewayV2` unconditionally credits the order's escrow ledger with the full "reduced" input amount: [5](#0-4) 

If `token` is an ERC20 that returns `false` on failure instead of reverting (a known non-standard-but-common pattern, e.g. some legacy/blacklist/pausable tokens), the `to.call{...}(data)` succeeds (no revert), `CallDispatcher` treats it as a success, and `IntentGatewayV2` still increments `_orders[commitment][token]` even though the actual token balance of the `IntentGateway` contract never increased.

### Impact Explanation
This breaks the invariant that `_orders[commitment][token]` accounting is backed 1:1 by tokens actually escrowed in the contract. Once escrow accounting is inflated beyond the contract's real token balance, later flows that pay out against `_orders` (fills, refunds/cancellations, dust sweeps) can be drained against real balances contributed by other orders/users, resulting in permanent fund loss/insolvency for the intents escrow. This falls squarely within the "intents escrow" reachable surface called out in scope and represents unbacked/incorrectly-backed escrow accounting reachable from a single order submission using an attacker-chosen input token.

### Likelihood Explanation
The predispatch path is user-controlled: the order submitter picks `order.inputs` tokens and the `predispatch.assets`/`predispatch.call` payload, and Tron's ecosystem includes ERC20/TRC20-style tokens that follow the false-return-on-failure pattern rather than reverting (this exact class of token behavior is the reason `SafeERC20` exists and is already used everywhere else in this same contract). Triggering the bug only requires listing such a token as an order input and having the transfer fail in a way that returns `false` (e.g., an allowance/blacklist/paused condition on the token) — no privileged role is required, only a normal order-opening transaction from a solver or user.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` construction with `SafeERC20.safeTransfer` semantics (or have `CallDispatcher` decode and validate ERC20 return data), and/or verify the `IntentGateway`'s actual post-call token balance increased by the expected amount before crediting `_orders[commitment][token]`, consistent with the `safeTransferFrom`/`safeTransfer` usage already applied elsewhere in the same contract.

### Proof of Concept
1. Deploy/list a non-standard ERC20 token as an order input token that returns `false` (instead of reverting) when a `transfer` fails (e.g., a token with a blacklist or pause flag on the `dispatcher`/`IntentGateway` address).
2. Submit an order via `IntentGatewayV2` with `predispatch.call` and `predispatch.assets` populated, using this token as `order.inputs[i].token`.
3. Cause the balance-pull-back `transfer` call at [6](#0-5)  to fail silently (return `false`) — e.g. by having the predispatch call blacklist `address(this)` (the `IntentGateway`) on the token contract before the transfer executes.
4. `CallDispatcher.dispatch` sees `success == true` (call didn't revert) and returns normally [7](#0-6) .
5. `IntentGatewayV2` credits `_orders[commitment][token] += reducedInputs[i].amount` despite the `IntentGateway` never receiving the tokens [8](#0-7) , creating a phantom escrow balance that can later be paid out against real funds from other orders.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
