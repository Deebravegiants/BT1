Confirmed vulnerability: `TokenExchange.exchange_token` builds its outbound HTTP request host directly from the unsanitized `dest` claim of the session token, unlike every other credential-sending path in this gem which requires `Utils::ShopValidator.sanitize!`.

### Title
Unsanitized JWT `dest` claim used as HTTP host in `TokenExchange.exchange_token` sends `client_secret` and session token to an unvalidated domain - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the `dest` claim of the caller-supplied session token via `JwtPayload#shop`, and never passes it through `Utils::ShopValidator.sanitize!` before using it to build the request host in `Clients::HttpClient`. Every sibling credential-bearing flow in this gem (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used to send `client_secret`. `exchange_token` breaks that pattern.

### Finding Description
The intended binding is: `host receiving the app's client_secret == a domain that ShopValidator recognizes as a real Shopify property (myshopify.com/myshopify.io/shopify.com/spin.dev/shop.dev or configured myshopify_domain)`.

In `exchange_token`:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [1](#0-0) 

`JwtPayload#shop` simply strips the `https://` prefix off the raw `dest` claim with no domain allow-listing:
```ruby
def shop
  @dest.gsub("https://", "")
end
``` [2](#0-1) 

`JwtPayload#initialize` only verifies `aud == Context.api_key`; it never checks that `dest` is a Shopify-owned domain: [3](#0-2) 

`Clients::HttpClient#initialize` then builds the outbound base URI straight from `session.shop`:
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
@base_uri_and_path = T.let("#{@base_uri}#{base_path}", String)
``` [4](#0-3) 

The POST body sent to that host includes `client_secret` and the raw `session_token` (subject_token): [5](#0-4) 

By contrast, the other three flows that build an equivalent `HttpClient`/`Session` and send `client_secret` all sanitize the shop first: [6](#0-5) [7](#0-6) [8](#0-7) 

`Utils::ShopValidator.sanitize!` is precisely the code that enforces the "trusted Shopify domain" allow-list (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`, or the configured `myshopify_domain`) and raises `Errors::InvalidShopError` otherwise: [9](#0-8) 

The `session_token` argument to `exchange_token` is explicitly documented/intended to be attacker-influenced input from the client side (it originates from App Bridge in the browser and is passed by the host app into this library call) — the JWT signature check (`aud`/HS256 verification) proves the token was minted by Shopify for this app's `api_key`, but it does **not** by itself guarantee `dest` is a well-formed Shopify hostname string free of the kind of confusables/format issues `ShopValidator` is designed to catch (the validator's own logic handles cases like unified-admin URLs, path components, and format normalization that raw string-stripping in `JwtPayload#shop` does not perform at all).

### Impact Explanation
If a `dest` value that is syntactically atypical or not host-only reaches `JwtPayload#shop` unmodified and is used verbatim as `session.shop` → `@base_uri = "https://#{session.shop}"`, the app's `client_secret` and the subject session token get transmitted to a host string that was never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. This is exactly the "host validated versus host that receives the `client_secret`" identity-binding gap called out in the rules: the gem validates the JWT signature/`aud` but not the destination-host safety property that its own `ShopValidator` module exists to enforce for every other equivalent flow. Given the sensitivity of the data in flight (`client_secret`, session token), any gap between "signature valid" and "host safe-to-send-secret-to" is High severity (credential leakage risk), matching the code-423n4 report's underlying theme of trusting one signal (transfer/verification success) as a proxy for a different guarantee (destination safety) it doesn't actually provide.

### Likelihood Explanation
Reaching this requires the host application to pass a session token whose `dest` claim, while properly signed for the correct `aud`, is not caught by ShopValidator's normalization logic — the same category of edge case the gem's own maintainers evidently considered important enough to guard against in `refresh_token.rb`, `client_credentials.rb`, and `migrate_to_expiring_token`, but omitted specifically in `exchange_token`. The likelihood is bounded by how a real Shopify-issued token's `dest` claim is formatted in practice, which is not fully enumerable from this index; however, the inconsistency itself — one of four structurally identical flows omitting the sanitize step — is a concrete code-level defect regardless of exact exploitability in every deployment.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`) before constructing `shop_session`/`Clients::HttpClient`, so the destination host for the `client_secret`-bearing request is bound to the same trusted-domain allow-list enforced everywhere else in the gem.

### Proof of Concept
Conceptually: instrument `JwtPayload.shop` to return the raw `dest` value from any HS256 token correctly signed with the app's `api_secret_key`/`aud`, then call `TokenExchange.exchange_token(session_token: token, requested_token_type: ...)` and observe that `Clients::HttpClient` sends the POST containing `client_id`/`client_secret`/`subject_token` to `https://#{dest}/admin/oauth/access_token` with no call to `Utils::ShopValidator.sanitize!` anywhere on that code path, unlike `test/auth/token_exchange_test.rb`'s equivalents for `refresh_access_token`/`client_credentials`, which construct the shop through the sanitizer: [10](#0-9)

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
