## Finding

### Title
`TokenExchange.exchange_token` accepts checkout-extension session tokens for admin token exchange, allowing privilege escalation - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` decodes an attacker-supplied session token via `ShopifyAPI::Auth::JwtPayload` and uses its `dest`/`aud` claims to request a merchant access token, but it never checks the token's `iss` claim to confirm the token was issued for the Admin surface. The gem's own `JwtPayload` class already distinguishes admin-issued tokens from lower-privilege issuers (e.g. checkout UI extension tokens) via `admin_session_token?`, but that check is used only for `shopify_user_id` and is never applied by `exchange_token`. As a result, a session token legitimately issued to an anonymous customer at checkout can be exchanged for a full merchant offline/online access token.

### Finding Description
`JwtPayload#initialize` only validates the `aud` claim (must equal `Context.api_key`) and standard `exp`/`nbf` timing via the `jwt` gem: [1](#0-0) 

The class internally recognizes two categories of caller-supplied tokens — admin tokens (`iss` ends with `/admin`) and non-admin tokens such as checkout UI extension tokens — and gates the sensitive `shopify_user_id` accessor on that distinction: [2](#0-1) [3](#0-2) 

The test suite confirms both token shapes decode identically through this class, e.g. a `checkout_ui_extension_jwt_payload` with `iss: "https://test-shop.myshopify.io/checkouts"` decodes successfully with no rejection: [4](#0-3) [5](#0-4) 

`TokenExchange.exchange_token` takes any decodable `JwtPayload` and forwards it to Shopify's `/admin/oauth/access_token` endpoint as the `subject_token`, using only `dest` (and implicitly the passing `aud` check) to select the shop — it performs no `iss`/`admin_session_token?` check before doing so: [6](#0-5) 

The binding that should hold is: *token issuer surface (`iss`) == the privilege level the exchanged token is minted for*. Instead the code only enforces *token audience (`aud`) == this app's `api_key`*, which is satisfied equally by admin session tokens and checkout/customer-scoped session tokens, since both are minted with the app's own `aud`. Any code path in a host application that calls `exchange_token` with a session token sourced from a non-admin surface (e.g. a checkout UI extension, which is reachable by any anonymous shopper) inherits this gap.

### Impact Explanation
If exploited, an unprivileged customer interacting with a storefront checkout (no merchant/admin credentials required) could supply their checkout-extension session token to an app's token-exchange endpoint and receive back a full offline or online merchant access token for that shop — a credential far more privileged than what the checkout surface is meant to grant. This matches the "Critical: theft ... of a merchant access token" impact category, since it results in exfiltration/acquisition of a merchant access token through an identity-binding gap in the gem's own claim validation, without needing `api_secret_key`, TLS interception, or any privileged account.

### Likelihood Explanation
Exploitability depends on the host application exposing a token-exchange path that can be fed a caller-controlled session token without first restricting it to the Admin surface. Because the gem does not enforce the `iss` binding itself, any app that plugs a session token straight into `ShopifyAPI::Auth::TokenExchange.exchange_token` (following the documented usage pattern) is exposed. The token itself is always validly signed by Shopify (customers cannot forge tokens), so the likelihood centers on whether Shopify's own `/admin/oauth/access_token` endpoint independently rejects non-admin subject tokens; the gem provides no defense-in-depth here, which is the underlying defect being reported. Given the library explicitly implements — but does not apply — the exact classification needed to prevent this, this is a real gap in the gem's identity binding, not merely a host-application misuse issue.

### Recommendation
In `TokenExchange.exchange_token`, require that the decoded `JwtPayload` is an admin session token (`jwt_payload.send(:admin_session_token?)` or an equivalent public check) before using it as `subject_token` for the OAuth token exchange request; raise `ShopifyAPI::Errors::InvalidJwtTokenError` otherwise, mirroring the existing `aud` check pattern.

### Proof of Concept
1. As an anonymous shopper, load a storefront's checkout page where the app's checkout UI extension is active; capture the App-Bridge-issued session token (`iss` ending in `/checkouts`, `aud` = the app's `api_key`).
2. Submit this token to the app's token-exchange endpoint (which internally calls `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: captured_token, requested_token_type: OFFLINE_ACCESS_TOKEN)`).
3. `JwtPayload.new` accepts the token because only `aud`/`exp`/`nbf` are checked; `exchange_token` extracts `dest_shop` and forwards `client_id`/`client_secret`/`subject_token` to `/admin/oauth/access_token` with no `iss` gate — see [7](#0-6) .
4. If Shopify's server accepts the subject token type, the app receives and stores a full merchant access token, which the anonymous shopper effectively caused to be minted using a checkout-level credential.

        def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end

          client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
