### Title
App-lock PIN stored in iOS Keychain without `ThisDeviceOnly` accessibility, allowing extraction via iTunes/iCloud backups - (File: adapters/keystore-mobile/src/index.js)

### Summary
The `@exodus/auth-mobile` PIN gate (used to restrict access to "protectworthy resources such as the mnemonic phrase" per the feature's own README) is persisted through `@exodus/keystore-mobile` into the iOS Keychain. The keystore's default accessibility class is `WHEN_UNLOCKED`, not `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, and `Auth#setPin` never overrides this default, so the PIN secret is backed up to iTunes/iCloud.

### Finding Description
`createMobileKeystore` sets `defaultSetOptions.accessible` to `reactNativeKeychain.ACCESSIBLE.WHEN_UNLOCKED` unless the caller supplies an override via the `opts` parameter of `setSecret`: [1](#0-0) [2](#0-1) 

Elsewhere in the codebase, the constant `ACCESSIBLE_WHEN_UNLOCKED_THIS_DEVICE_ONLY` exists specifically to prevent Keychain items from migrating into backups, and `Auth#setBioAuth` explicitly applies it when storing biometric/device-auth flags: [3](#0-2) 

However, `Auth#setPin`, which stores the user's app-unlock PIN, calls `setSecret` with **no `opts` argument at all**, so it silently falls back to the keystore's default `WHEN_UNLOCKED` accessibility class instead of `ThisDeviceOnly`: [4](#0-3) 

`Auth#isCorrectPin` later compares the stored plaintext PIN directly to user input, confirming the PIN itself (not a hash) is stored in the Keychain item: [5](#0-4) 

The README confirms the PIN is meant to gate access to sensitive wallet material such as the mnemonic ("restrict access to protectworthy resources such as the mnemonic phrase"): [6](#0-5) 

This is inconsistent with the developer's own established mitigation pattern (used for `AUTH_KEYSTORE_BIO_AUTH_KEY`/`AUTH_KEYSTORE_DEVICE_AUTH_KEY`), which explicitly sets `ThisDeviceOnly` — the PIN key is the one exception that was missed.

### Impact Explanation
Because the plaintext PIN value is Keychain-accessible with `WHEN_UNLOCKED` (not `ThisDeviceOnly`), it is eligible for inclusion in encrypted iTunes/iCloud device backups. An attacker who obtains a user's iTunes backup (via physical device access) or iCloud backup (via compromised Apple ID credentials) can extract the plaintext 6-digit app-unlock PIN. Combined with physical/remote access to the restored app state, this undermines the local-authentication gate intended to protect the mnemonic phrase and other protect-worthy resources, and given the PIN's low entropy (6 numeric digits), it is trivially brute-forceable once exfiltrated, unlike biometric/device-auth trigger flags which the code correctly protects with `ThisDeviceOnly`.

### Likelihood Explanation
Low-to-moderate difficulty, consistent with the original report's rating. It requires either physical possession of the device with backup capability, or compromise of the associated iCloud account (e.g., via credential-stuffing/known-password-database attacks referenced in the original report). No app-level vulnerability needs to be triggered by the attacker beyond obtaining a backup — the flaw is a straightforward missing-accessibility-attribute bug in `setPin`, directly analogous to the reported keychain-backup exposure pattern but concretely confirmed here in code rather than iOS-specific `ReceiveViewController`/`RecoveryPhraseDisplayViewController` classes (which don't exist in this repo).

### Recommendation
Update `Auth#setPin` in `features/auth-mobile/module/auth.js` to pass `{ accessible: ACCESSIBLE_WHEN_UNLOCKED_THIS_DEVICE_ONLY }` as the `opts` argument to `this.#keystore.setSecret(...)`, matching the pattern already used in `#setBioAuth`. More broadly, consider changing `keystore-mobile`'s `defaultSetOptions.accessible` default to `WHEN_UNLOCKED_THIS_DEVICE_ONLY` so that any future keystore secret is opt-out rather than opt-in for backup exclusion, reducing the chance of this class of omission recurring.

### Proof of Concept
1. Call `exodus.auth.setPin('123456')`, which invokes `Auth#setPin` → `keystore.setSecret('auth:pin', '123456')` with no `opts`. [4](#0-3) 
2. `keystore.setSecret` merges `opts` (empty) over `defaultSetOptions`, resulting in `{ accessible: reactNativeKeychain.ACCESSIBLE.WHEN_UNLOCKED }` being passed to `reactNativeKeychain.setInternetCredentials`. [2](#0-1) 
3. On a real iOS device this Keychain item, lacking `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, is included in the next iTunes/iCloud backup.
4. An attacker restoring or parsing that backup (e.g., with standard iOS backup-extraction tooling) recovers the plaintext 6-digit PIN string, bypassing the intended local-authentication barrier to wallet-sensitive screens.
