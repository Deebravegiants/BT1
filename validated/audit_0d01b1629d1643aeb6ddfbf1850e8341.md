### Title
Repeated buy/sell round-trips can exploit `Pair.swap`'s `+1` K-invariant slack to erode `assetReserve` below the launch-time virtual LT reserve, causing a permanent underflow revert that bricks all future buys and sells - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2022-42330 is a case where a routine, unprivileged guest operation (`XS_RELEASE` via a Xen "Soft Reset") drives a critical service (`xenstored`) into a state it didn't anticipate, crashing it. The closest analog in alt.fun is that ordinary, permissionless buy/sell traffic on the bonding curve can exploit the loosened K-invariant check in `Pair.swap` (the `+1` slack) to slowly erode the pool's real value below the amount the protocol's own accounting (`canGraduate`/`_prepareGraduationLiquidity`) assumes can never be violated. Once `assetReserve` drops below the recovered launch-time virtual LT reserve, the unchecked subtraction underflows and reverts every subsequent call that touches `canGraduate`, which is invoked on **every buy** and (per the docs) as a pre-check on **every sell**, permanently freezing the curve and any trader/creator funds still on it.

### Finding Description
`Pair.swap` enforces the constant-product invariant with a `+1` grace on both reserves: [1](#0-0) 

This means the *actual* post-swap product `newTokenReserve * newAssetReserve` is allowed to fall slightly below `_pool.k` (down to the point where adding 1 to each side clears the bar), rather than being pinned to exactly `>= k`. Individually this is a benign rounding allowance for `Router`'s ceiling/floor math, but every swap that lands in this slack region leaks a small amount of real value out of the pool relative to what the protocol's graduation math assumes is conserved.

`Bonding.canGraduate` recovers the launch-time virtual LT reserve from the *immutable* `Pair.k()` value and subtracts it from the *live* stored `assetReserve` with no underflow guard: [2](#0-1) 

The invariant the protocol relies on is that `assetReserve` (which only moves via `Router.buy`/`Router.sell` → `Pair.swap`) never drops below the launch-time virtual reserve baked into `k`. That invariant is only as strong as the K-invariant enforcement in `Pair.swap`. Because that enforcement has a `+1` slack rather than an exact `>= k` bound, many buy/sell round-trips against the same curve can, in principle, ratchet `assetReserve` down by fractions of a unit each time until it dips under `_launchTimeVirtualLtReserve(...)`.

Once that happens, the subtraction `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts (Solidity 0.8 checked arithmetic). This function is not a rarely-hit corner: it's called from `_executeBuy` on **every single buy**: [3](#0-2) 

and, per the documented sell flow, `Zap.sell` also evaluates graduatability before executing a curve sell (to decide whether to route into `triggerGraduation` instead of a normal sell): [4](#0-3) 

So a single underflow condition, once reached, reverts **both** the buy path and the sell path for that token, for every trader, permanently (there is no admin recovery/reset function for `assetReserve` — it is derived purely from swap history).

### Impact Explanation
If the underflow condition is reached, the affected bonding curve is permanently bricked: no further buys or sells can execute (`canGraduate` reverts inside `_executeBuy` for buys, and inside `Zap.sell`'s pre-check for sells), and the curve can never reach `finalizeGraduation` either, since phase 1 (`_enterGraduating`) can't fire from a reverting `canGraduate`. Any trader capital already committed as curve tokens becomes permanently illiquid (can't sell, curve never graduates to the HyperSwap pool where they could otherwise exit), and the creator's fee stream and any future graduation for that token are frozen indefinitely. This matches the "permanent freezing of trader, creator ... funds" bar in the validation rules.

### Likelihood Explanation
This requires an attacker (or just a heavy volume of ordinary trading) to push many buy/sell round-trips through the same curve to accumulate enough of the K-invariant's `+1`-slack leakage to underflow `assetReserve` below the virtual reserve. Each round-trip on the public path costs the 0.75% Zap fee, so grinding this out organically is economically costly, and I was not able to fully quantify — within the scope of this review — how many round-trips or what curve parameters would be needed to accumulate a full unit of drift, nor whether `Router._computeBuy`/`_computeSell`'s own floor/ceil rounding might already prevent `assetReserve` from ever landing in the exploitable region in practice. This uncertainty means the likelihood could range from very low (if the rounding conventions in `Router._computeBuy`/`_computeSell` are conservative enough to never let real assetReserve drift below the virtual floor) to plausible-but-slow (if an attacker is willing to pay the cumulative fee cost to grief a specific token, e.g. a competitor's curve, or if a large volume of unrelated organic trading eventually reaches the threshold on a long-lived, high-volume token). I flag this as the most defensible analog given the report's hint set, but recommend treating the likelihood assessment as provisional pending exact numeric modeling of the rounding directions in `Router._computeBuy`/`_computeSell` against the `+1` slack in `Pair.swap`.

### Recommendation
- Change `Pair.swap`'s invariant check from the loosened `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` to an exact `newTokenReserve * newAssetReserve < _pool.k` (or otherwise bound the total slack that can accumulate across the pool's lifetime), removing the compounding leak.
- Add an explicit floor/guard in `Bonding.canGraduate` (and any other call site deriving `realLtRaised`) so that if `assetReserve <= _launchTimeVirtualLtReserve(...)`, it treats `realLtRaised` as `0` rather than reverting — this converts a hard DoS into a benign "not yet graduatable" result and removes the single point of permanent failure.
- Add an invariant test that performs a very large number of alternating buy/sell round-trips on one curve and asserts `canGraduate`/`previewLtUntilGraduation` never revert, to catch regressions in this area (extending the existing `test/GraduationInvariants.t.sol` fuzz suite).

### Proof of Concept
Conceptual (not verified against exact numeric thresholds due to review scope):
1. Launch a token via `Zap.createToken` with a minimal seed (`Bonding.launch` + seed `Zap.buy`).
2. Have a trader alternate `Zap.buy(tokenAddress, minAmount, 0, ...)` and `Zap.sell(tokenAddress, allTokens, 0)` on the same curve many times, always trading amounts small enough to land in the `Pair.swap` `+1`-slack rounding region on both legs.
3. After enough iterations, `Pair.getReserves().assetReserve` drifts below `Pair.k() / Token.TOTAL_SUPPLY()` (the recovered launch-time virtual LT reserve).
4. The next call to `Bonding.canGraduate` (triggered inline by any `Zap.buy`, or by `Zap.sell`'s pre-check) underflows in `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` and reverts, permanently bricking all buy/sell/graduation paths for that token.

Given the effort budget for this analysis, I was not able to run this scenario against the actual `Router._computeBuy`/`_computeSell` rounding to confirm the exact iteration count (if any) needed to trigger the underflow in practice; a Devin session with test-execution access would be needed to fuzz this precisely against `test/GraduationInvariants.t.sol`'s harness.

```text
    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
```

```text
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
```
