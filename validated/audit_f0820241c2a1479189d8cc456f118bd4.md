### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, enabling cross-shop webhook forgery/replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`) values taken from HTTP headers — which are never included in the signed payload — and hands them to the app's handler as the tenant identifier. This breaks the intended binding `shop authenticated == shop the request is processed as`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` and `topic` are read straight from attacker-controllable HTTP headers, entirely outside the HMAC: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body, then immediately dispatches the handler using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is per-app, not per-shop, so any valid `(raw_body, hmac)` pair delivered to the app for *one* installed shop remains a cryptographically valid pair for *any* shop-domain header value. This is exactly the "field acted on but not covered by the HMAC" bug class from the analog report: `interestFee`/timestamp bookkeeping there is trusted without being bound to the value it should be tied to; here `shop`/`topic` are trusted without being bound to the HMAC that is supposed to authenticate the whole webhook.

The library's own documentation reinforces the false guarantee, stating that `Registry.process` "will verify the request did indeed come from Shopify," and instructs apps to key business/tenant logic off `data.shop`: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unprivileged internet user who controls any shop with the target public app installed can capture a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair from a real webhook delivery to their own shop, then replay that exact body/HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic) header with a victim shop's domain. Because `Registry.process` never checks that the shop header is consistent with anything cryptographically bound to the signature, the HMAC check passes and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop. Any app that follows the documented pattern of using `data.shop` to select the tenant/session/record to update will process attacker-supplied data under the victim's identity — a cross-tenant data-integrity/confusion condition (e.g. incorrect GDPR `customers/redact` or `shop/redact` processing, order/customer data attributed to the wrong merchant).

### Likelihood Explanation
Any developer/attacker can install the vulnerable app (or a customized clone) on their own store to legitimately receive real, correctly signed webhooks, since Shopify signs with the app's single `client_secret` shared across all shops. Forging the header afterward requires no secret knowledge — only crafting an HTTP request with different headers around the same signed body. No access token, TLS interception, or privileged account is required.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material that is verified, or otherwise cryptographically tie the header-derived shop to a value Shopify actually signs (e.g., verify the resolved shop against an active, previously-established session/installation record rather than trusting the header verbatim). At minimum, document prominently that `Registry.process` only proves the payload bytes were signed by the app's secret and does **not** prove which shop or topic the request is genuinely for, and require app authors to cross-check `data.shop` against known installed shops before acting on webhook content.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers e.g. `customers/data_request`.
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `Context.api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays it to the same endpoint, changing only the shop-domain header to `victim-shop.myshopify.com` (topic header can also be swapped to any registered topic).
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `OpenSSL.secure_compare(compute_signature(B), H)` — see [6](#0-5)  — with no dependency on the shop header.
5. `Registry.process` calls the app handler with `WebhookMetadata(topic: <forged topic>, shop: "victim-shop.myshopify.com", body: <attacker-controlled B>)`, and any tenant-scoped logic in the handler now acts as if this data legitimately came from `victim-shop.myshopify.com`.
