Based on my investigation, I have enough evidence to confirm the vulnerability.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `ShopifyAPI::Webhooks::Request` class binds the `hmac` signature only to the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are used by `ShopifyAPI::Webhooks::Registry.process` to dispatch to a handler and identify the tenant — are read directly from unauthenticated HTTP headers. Because `Utils::HmacValidator` validates a request purely by recomputing the HMAC over `to_signable_string`, and `to_signable_string` for a webhook only returns `@raw_body`, the header-derived `shop` value that a multi-tenant app relies on for tenant identification has no cryptographic binding to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no verification tying them to the signed bytes: [2](#0-1) 

`HmacValidator.validate` only recomputes and compares the HMAC of `to_signable_string` (i.e., the body) against a single, app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts any request that passes this body-only HMAC check and then dispatches it to a handler using the unauthenticated `request.shop` and `request.topic` values: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop value cryptographically authenticated by the HMAC` ≠ `shop value the handler treats as the tenant identity (request.shop)`.

Because a single app-wide `client_secret`/`api_secret_key` is used for every shop that installs the app, and the HMAC never incorporates the `shop-domain` header, any party who can obtain one genuinely Shopify-signed `(raw_body, hmac)` pair — trivially available to any unprivileged user who installs the app on their own free/development store and receives real webhooks for it — can replay that exact body and HMAC to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` will hand the forged shop identity to the app's handler as if the event genuinely originated from the victim shop.

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide for multi-tenant embedded apps that host a single shared webhook endpoint and rely on `request.shop`/`WebhookMetadata#shop` to know which tenant an event belongs to. An attacker who is merely a legitimate (but unprivileged, from the victim's perspective) installer of the same app on their own store can forge webhook deliveries that appear to come from an arbitrary other merchant, without needing that merchant's access token or credentials. Depending on how the host app's handlers act on `shop` (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific business logic keyed off `shop`), this can result in cross-tenant data manipulation or deletion — a Critical-class cross-tenant access issue.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: many Shopify apps use a single shared webhook URL for all installed shops (the standard integration pattern documented for this gem), and any user can install a public app on their own store to harvest a valid signed webhook body/HMAC pair. No access token, client secret, or privileged account is required — only the ability to receive one genuine webhook for an owned/controlled shop and to send a crafted HTTP request with a different `shop-domain` header to the app's public webhook endpoint.

### Recommendation
Extend `to_signable_string` (or add an additional post-HMAC check in `Registry.process`) to bind the authenticated shop identity to the verified bytes — e.g., include the `shop-domain` header value in the HMAC-covered signable string, similar to how `AuthQuery#to_signable_string` includes `shop` in the OAuth callback signature. At minimum, document and/or enforce that consumers must cross-check `request.shop` against a known/registered shop before trusting it, and consider deriving the per-shop secret when available so that a webhook signed with one shop's context cannot validate against another shop's expected identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimately signed webhook to the app's shared endpoint: body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(api_secret_key, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays a POST to the same shared endpoint with identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`B` only) using the shared `Context.api_secret_key`; validation succeeds because the body and secret are unchanged. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, believing the event genuinely originated from the victim's store, even though nothing in the signature ever referenced that shop.
