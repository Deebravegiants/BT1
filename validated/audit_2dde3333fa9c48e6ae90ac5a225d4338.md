### Title
Unchecked ERC20 return value on escrow withdrawal permanently freezes funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the IntentGateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) releases escrowed input tokens using a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`) but never decoding/validating the boolean return value the ERC20/TRC20 `transfer` function is supposed to return. This is exactly the bug class flagged in the external report ("Use safeTransferFrom/safeTransfer consistently, validate the return value"). The sibling implementation used on other EVM chains (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses OpenZeppelin's `safeTransfer`, showing the Tron contract diverged and reintroduced the exact anti-pattern the audit warned about.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is invoked from `onAccept` for `RedeemEscrow` (solver fill settlement) and `RefundEscrow` (cancellation refund) messages delivered by the ISMP host: [1](#0-0) 

Inside `withdraw`, for every escrowed ERC20/TRC20 token it does: [2](#0-1) 

```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```

`success` only reflects whether the low-level call executed without reverting — it says nothing about whether the token contract's `transfer` function actually moved the tokens. Standards-compliant tokens are supposed to return `true`/`false`, and many real-world/non-standard tokens (a common occurrence on Tron/TRC20, including blacklist-capable or paused tokens) return `false` on failure instead of reverting. Because the return data is never decoded, a `false` return is silently treated as success.

Critically, the escrow debit happens unconditionally right after the `!success` check passes: [3](#0-2) 

`_orders[body.commitment][token] -= amount;` executes regardless of whether tokens were truly transferred, and `_filled[body.commitment] = beneficiary` is already set at function entry: [4](#0-3) 

Once the escrow accounting is zeroed and the order marked filled/refunded, there is no remaining code path to re-claim the tokens — they remain stranded in the contract while the beneficiary (solver or user) receives nothing. The identical unchecked-return pattern is also present in the `SweepDust` handler: [5](#0-4) 

and for transaction-fee redemption: [6](#0-5) 

By contrast, the canonical/shared `IntentsBase.sol` used by other chain deployments correctly uses `SafeERC20.safeTransfer`, which reverts the whole transaction if the token returns `false`: [7](#0-6) 

### Impact Explanation
Any user who places a cross-chain order on the Tron IntentGateway, or any solver who fills one, is subject to permanent loss of their escrowed/earned tokens if the input/output token behaves non-standardly (returns `false` instead of reverting on failure — e.g. due to a blacklist, pause, or non-standard implementation). Because the escrow ledger (`_orders`) is decremented and the order is marked `_filled` even when the transfer silently failed, the funds become permanently stuck in the gateway contract with no code path to retry or recover them. This is a concrete, permanent freezing/loss of user and solver funds, reachable purely through the normal settlement flow (a relayed ISMP message delivering a `RedeemEscrow`/`RefundEscrow` request), not requiring any privileged or malicious actor beyond an ordinary token whose `transfer` can return `false`.

### Likelihood Explanation
Likelihood is Medium-to-High in practice: the Tron ecosystem specifically has non-reverting, boolean-return TRC20 tokens as a common pattern (unlike more standardized modern EVM ERC20s), and any token that can pause/blacklist an address (a widely used compliance pattern, e.g. USDT-style tokens) can trigger this condition for a specific beneficiary without any attacker action. This is not a contrived edge case — it is a realistic operational hazard for the Tron deployment of the Intent Gateway given the diversity of token implementations expected to be listed.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the `SweepDust` branch of `onAccept`, and the fee-redemption path) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures a `false` return value (or missing return data from non-compliant tokens) reverts the entire transaction rather than allowing escrow state to be finalized without an actual transfer occurring.

### Proof of Concept
1. Register/allow-list a TRC20 token on the Tron IntentGateway whose `transfer` function returns `false` on failure instead of reverting (e.g., a token that blacklists the beneficiary address, or any non-compliant/legacy TRC20).
2. A user places a cross-chain order using this token as an output, or a solver fills an order and is due this token as escrowed input; the order proceeds normally through `placeOrder`/`fillOrder` and a `RedeemEscrow`/`RefundEscrow` ISMP message is dispatched to the source chain.
3. The token's `transfer` call to the intended beneficiary fails and returns `false` (e.g. the beneficiary was blacklisted, or the token has since been paused) — `token.call(...)` still returns `success = true` because the low-level call did not revert.
4. `withdraw()` at `evm/tron/contracts/apps/IntentGatewayV2.sol:706-710` passes the `!success` check, decrements `_orders[commitment][token]` to zero, and sets `_filled[commitment] = beneficiary`.
5. The beneficiary never received any tokens, and the escrow accounting states the order is fully settled — the tokens remain permanently locked in the gateway contract with no further recovery mechanism.
