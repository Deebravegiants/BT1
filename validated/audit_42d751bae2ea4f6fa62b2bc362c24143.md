### Title
Unvalidated swap route can inject unauthorized wallet transfers into the caller authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
High. `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept an opaque caller-controlled `swap: Bytes` route and forward it to the configured router after authorizing the caller. [1](#0-0) [2](#0-1) [3](#0-2)  The router can place route-selected third-party contracts below the caller’s authorization; such a contract can request a token transfer from the caller, which simulation records as a child authorization and executes if the caller signs the expanded tree. [4](#0-3) [5](#0-4) 

### Finding Description
`process_swap_collateral` authenticates `caller`, requires account ownership or delegation, then passes the opaque `swap` payload through `withdraw_and_swap_from_supply` without decoding or constraining the route. [6](#0-5) [7](#0-6)  `swap_tokens` authorizes exactly one transfer of the controller’s input token to the router, invokes `router.execute_strategy`, and afterward checks only controller input spend and positive output receipt. [3](#0-2) [8](#0-7)  Those checks do not prevent route-selected code from invoking an unrelated token’s `transfer(caller, attacker, amount)` beneath the caller’s controller authorization. [4](#0-3)  This is analogous to argument injection: the opaque route argument injects an extra contract invocation into a privileged call chain rather than merely selecting a poor exchange rate. [9](#0-8) 

### Impact Explanation
A crafted route can steal arbitrary tokens held directly in the victim’s wallet, including assets unrelated to the lending position. [10](#0-9)  The repository’s regression test demonstrates that an honest root-only authorization rejects the rogue transfer, while the poisoned simulated tree authorizes it and moves the victim’s entire wallet balance to the attacker. [11](#0-10) [12](#0-11) [13](#0-12)  The swap can still return sufficient output for the position accounting and final risk checks to pass, so the theft is not bounded by `min_out`, routed input, or protocol solvency checks. [14](#0-13) 

### Likelihood Explanation
Exploitation requires convincing an account owner or delegate to submit a transaction whose simulated authorization tree contains the injected child transfer. [15](#0-14)  The attack surface is reachable through ordinary route construction because the controller treats `swap` as opaque bytes and the router venue addresses are not constrained by the controller. [1](#0-0) [16](#0-15)  Wallets or clients that only display the top-level call and expected input transfer can therefore sign an authorization tree that silently includes the attacker’s extra child invocation. [17](#0-16) 

### Recommendation
Do not pass opaque route bytes into an arbitrary-address routing surface under the user’s authorization. [3](#0-2)  Decode the route in the controller or have the router expose a canonical manifest, then enforce that every venue, pool, token, recipient, and expected child authorization is on an explicit allowlist or matches the declared input/output assets. [4](#0-3)  Client-side simulation should additionally reject any authorization child other than the expected input transfer, but this should remain a defense-in-depth check rather than the protocol’s only control. [14](#0-13) 

### Proof of Concept
1. Deploy a malicious “pool” contract whose `swap` method calls `token.transfer(victim, attacker, victim_balance)` on an unrelated token held by the victim. [18](#0-17) 
2. Construct a `swap_collateral(caller=victim, account_id, current, amount, new, swap=malicious_route)` transaction whose route selects the malicious pool while paying a valid positive `new` output to the controller. [1](#0-0) [3](#0-2) 
3. Simulation records the malicious token transfer as a child under the victim’s `swap_collateral` authorization. [12](#0-11) 
4. If the victim signs that expanded tree, the malicious transfer succeeds and drains the unrelated wallet token while the swap still returns the expected output. [13](#0-12)
