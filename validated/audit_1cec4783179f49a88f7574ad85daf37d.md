### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw request body only, while the `shop` (tenant identifier) is read directly from the `X-Shopify-Shop-Domain` header without being included in the HMAC-signed payload. `ShopifyAPI::Webhooks::Registry.process` verifies only that the body HMAC is valid and then trusts the unauthenticated `shop` header to build the `WebhookMetadata` object dispatched to the host app's handler. This breaks the intended binding `HMAC(secret, signed_bytes) == received_hmac` ⇒ `shop_header == originating_shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read straight from the (attacker-controllable) HTTP header with no cryptographic tie to the signature: [1](#0-0) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop` to construct the metadata passed to the app's handler: [3](#0-2) 

Because the api secret key (`Context.api_secret_key`) is shared across *all* shops that install the app (it is not per-tenant), and the HMAC is computed purely as `HMAC(secret, raw_body)`, any two webhook deliveries with byte-identical bodies produce byte-identical, valid signatures — completely independent of which shop they were originally sent for. Many real Shopify webhook topics have small, predictable, or even empty bodies (e.g. `app/uninstalled` is delivered with an empty JSON body `{}` in this codebase's own tests): [4](#0-3) 

An attacker who operates their own store with the target app installed will legitimately receive such a webhook (with a valid signature under the shared secret) for their own shop. They can then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes against the secret: [5](#0-4) 

`Registry.process` then dispatches the handler with `shop: request.shop` set to the spoofed victim shop: [6](#0-5) 

The host application's webhook handler (e.g. `shopify_app`'s uninstall/GDPR handlers, which key off `data.shop` to look up and mutate per-tenant records) will act on the forged tenant identity, believing it came from Shopify.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker (any merchant who has installed the app once) can cause the gem to hand the host application a webhook event validated as authentic but labeled with an arbitrary victim shop domain. Depending on the webhook topic replayed (e.g. `app/uninstalled`, `shop/update`, GDPR `customers/redact`), this can trigger data deletion, session/token invalidation, or other tenant-scoped side effects for a shop the attacker does not control — i.e., cross-tenant access/action, which the rules classify as Critical impact.

### Likelihood Explanation
Medium-to-High: the attacker needs only to install the app once on a store they control (a normal unprivileged action) and capture one legitimate webhook delivery with a low/no-entropy body (several real Shopify topics qualify, e.g. `app/uninstalled`). No access to `api_secret_key`, tokens, or the target shop's credentials is required — only the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the tenant identity to the signed payload before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should not treat `request.shop` as authenticated data derived purely from a body-only HMAC check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker uninstalls the app, triggering Shopify to POST a legitimate `app/uninstalled` webhook to the app's endpoint with body `{}` and a valid `X-Shopify-Hmac-Sha256` computed as `HMAC-SHA256(api_secret_key, "{}")`. Attacker captures this request (e.g. via a proxy they control, or because they can predict the body/signature pair offline is not needed — they only need to observe one delivery to their own infrastructure if they run the app's webhook receiver themselves for testing, or via any request logging they control on their own server).
3. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` builds `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` and invokes the host app's handler, which processes an uninstall/GDPR-style action for `victim-shop.myshopify.com` even though that shop never sent this event.
