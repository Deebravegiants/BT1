Based on the investigation, the most concrete analog to the "inherits pause functionality but never invokes it" bug class is the `detect_fraud` function in the signup pipeline, where the mechanism/call is wired into the flow at exactly the point it's needed, but the actual enforcement logic has been stripped out, causing it to unconditionally report "no fraud."

### Title
Fraud Detection Enforcement is a No-Op, Always Returning `false` and Allowing Every Signup to Bypass Fraud Checks - (File: `src/plans/mod.rs`)

### Summary
The `MasterPlan::detect_fraud` function is called at the correct point in the signup pipeline (`do_signup`) to gate whether an enrollment should be flagged as fraudulent, but its body has been reduced to a stub that unconditionally returns `Ok(false)`, meaning fraud is never detected regardless of the biometric pipeline output.

### Finding Description
In the signup flow, `do_signup` explicitly calls `self.detect_fraud(orb, debug_report, pipeline.as_ref())` after running the biometric pipeline, and its boolean result is used to decide the `SignupReason` (`Normal`, `Fraud`, or `Failure`), which in turn determines whether `enroll_user` proceeds with a normal successful enrollment. [1](#0-0) 

However, the implementation of `detect_fraud` itself has been gutted: the pipeline reference is accepted as a parameter but never inspected, and the function unconditionally returns `Ok(false)` with only a comment marking the checks as deleted. [2](#0-1) 

This mirrors the referenced bug class precisely: the surrounding architecture (call site, gating logic, `SignupReason::Fraud` enum variant, debug-report fraud accounting) is fully intact and behaves as if fraud enforcement is active, but the actual enforcing check — analogous to the missing `whenNotPaused` modifier — is absent from the function that is supposed to implement it. The call site trusts `detect_fraud`'s return value as an authoritative signal (`fraud_detected`), and that signal is structurally incapable of ever being `true`. [3](#0-2) 

### Impact Explanation
Because `detect_fraud` can never report a fraud detection, every signup that reaches this stage and has a valid pipeline result is treated as `SignupReason::Normal`, which drives `enroll_user` to attempt full enrollment and iris-code/PCP upload regardless of any anomalies the (deleted) fraud engine would have flagged. This directly matches the accepted impact category of "fraud/liveness bypass": a fraudulent or otherwise disqualifying signup attempt can never be blocked by this stage of the pipeline, leading to unauthorized biometric enrollment succeeding.

### Likelihood Explanation
Likelihood is high because this code path executes unconditionally for every non-extension, non-skipped signup (`self.skip_fraud_checks()` must be false, which is the default operational path), meaning the bypass applies to essentially all normal signups performed on builds using this code, not merely an edge case. [4](#0-3) 

### Recommendation
Restore the actual fraud/anomaly-detection logic inside `detect_fraud` (or, if intentionally delegated to an external/proprietary engine, ensure that engine's result is consulted here) so that the `fraud_detected` boolean genuinely reflects the outcome of the biometric pipeline's fraud checks rather than a hardcoded `false`. At minimum, gate enrollment on this signal only when the underlying engine is verified to be present and active, and fail closed (treat as fraud / block enrollment) if the fraud-check engine is unavailable.

### Proof of Concept
1. Perform a signup that proceeds through the full pipeline (`self.skip_fraud_checks()` returns `false`, which is the default).
2. Regardless of the biometric pipeline output, `detect_fraud` at `src/plans/mod.rs:1390-1406` returns `Ok(false)`.
3. `do_signup` computes `signup_reason = SignupReason::Normal` (assuming `pipeline.is_some()`), and proceeds to call `enroll_user`, completing enrollment. [1](#0-0)
