### Title
Shared reverse state-machine mapping is silently deleted when an unrelated LayerZero EID entry is remapped, freezing inbound delivery for the chain still using it - ([File: sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol])

### Summary
`HyperbridgeLzEndpoint.setEidMapping` maintains a bidirectional map between LayerZero EIDs and ISMP state machine IDs. When more than one EID is (even transiently) mapped to the same state machine, remapping or disabling one of those EIDs unconditionally deletes the shared reverse entry `_stateMachineToEid[keccak256(stateMachineId)]`, without checking whether that reverse entry still belongs to a different, still-active EID. This is the exact bug class described in the external report: removing/altering one entry ("adapter") that is shared by multiple consumers breaks the other consumers still relying on it.

### Finding Description
`_stateMachineToEid` is a single-valued reverse map keyed by `keccak256(stateMachineId)`: [1](#0-0) 

`setEidMapping` deletes the reverse entry keyed by the *old* value of the EID being updated, with no check that this reverse entry still points back to that same EID: [2](#0-1) 

The contract's own test suite confirms that two different EIDs can legitimately map to the same state machine at once, with the reverse mapping pointing to whichever EID mapped last: [3](#0-2) 

Given that state, `onAccept` relies exclusively on the reverse mapping to authenticate the source of an inbound message: [4](#0-3) 

Sequence that breaks a still-valid route:
1. Owner calls `setEidMapping(EID_A, SM_X)`.
2. Owner calls `setEidMapping(EID_B, SM_X)` — now both `EID_A → SM_X` and `EID_B → SM_X` forward mappings exist, and `_stateMachineToEid[SM_X] == EID_B` (last writer wins).
3. Owner later repurposes/disables `EID_A` (unaware it shares `SM_X` with `EID_B`) by calling `setEidMapping(EID_A, "")` or remapping it to a different state machine.
4. Inside `setEidMapping`, `previous = _eidToStateMachine[EID_A] = SM_X`, so `delete _stateMachineToEid[keccak256(SM_X)]` executes — deleting the entry even though it currently belongs to `EID_B`, not `EID_A`.
5. `EID_B`'s forward mapping (`_eidToStateMachine[EID_B] = SM_X`) and `isSupportedEid(EID_B)` remain untouched and valid, so outbound `send()` to `EID_B` keeps working.
6. Any inbound message whose `request.source == SM_X` now resolves `expectedEid = _stateMachineToEid[keccak256(SM_X)] == 0`, which unconditionally reverts with `UnknownSource()` in `onAccept`, per the explicit zero-check added specifically to prevent `srcEid == 0` collisions.

### Impact Explanation
This permanently freezes the inbound leg of a still-configured, still-advertised route (`EID_B ↔ SM_X`): outbound messages can still be dispatched to that chain, but no message from it can ever be delivered, since `onAccept` reverts for every message from `SM_X` regardless of the real `srcEid`. This matches the "route unable to deliver messages" / permanent freezing criterion, and it can be triggered by a normal, expected admin action (removing or repurposing one EID) that has an unintended side effect on an unrelated, still-in-use EID — exactly the shared-adapter-removal bug class from the reference report.

### Likelihood Explanation
The precondition (two EIDs pointing to the same state machine) is not prevented or warned against anywhere in the contract — it is explicitly exercised and validated as acceptable behavior in the project's own test suite. This can arise naturally during EID reconfiguration/migration (e.g., correcting a wrong EID value, or temporarily supporting two LZ endpoint IDs for the same destination chain during a transition) followed by cleanup of the old/duplicate entry, a plausible and realistic operational sequence for the owner.

### Recommendation
Only clear the reverse mapping if it still points to the EID being modified:
```solidity
function setEidMapping(uint32 lzEid, bytes calldata stateMachineId) external onlyOwner {
    if (lzEid == 0) revert InvalidEid();
    bytes memory previous = _eidToStateMachine[lzEid];
    if (previous.length != 0 && _stateMachineToEid[keccak256(previous)] == lzEid) {
        delete _stateMachineToEid[keccak256(previous)];
    }
    _eidToStateMachine[lzEid] = stateMachineId;
    if (stateMachineId.length != 0) {
        _stateMachineToEid[keccak256(stateMachineId)] = lzEid;
    }
}
```
This ensures removing/reassigning one EID never clobbers the reverse pointer of a different EID that still legitimately maps to the same state machine, directly following the reference report's recommendation of checking that a shared entry is not still in use elsewhere before removing it.

### Proof of Concept
1. `endpoint.setEidMapping(EID_A, SM_X)` — forward: `EID_A→SM_X`; reverse: `SM_X→EID_A`.
2. `endpoint.setEidMapping(EID_B, SM_X)` — forward: `EID_B→SM_X` added; reverse updated: `SM_X→EID_B`.
3. `endpoint.setEidMapping(EID_A, "")` (owner disables what they believe is an unused/duplicate EID_A) — inside, `previous = SM_X`, so `delete _stateMachineToEid[keccak256(SM_X)]` runs, wiping the reverse entry that actually belongs to `EID_B`.
4. `endpoint.isSupportedEid(EID_B)` still returns `true` and `endpoint.eidFor(SM_X)` now returns `0`.
5. A legitimate `onAccept` call for a `PostRequest` with `request.source == SM_X` and correct `srcEid == EID_B` in the body now reverts with `UnknownSource()` at line 373, because `expectedEid == 0`, permanently blocking inbound delivery from `SM_X` via `EID_B` until the owner notices and re-registers `EID_B`.
