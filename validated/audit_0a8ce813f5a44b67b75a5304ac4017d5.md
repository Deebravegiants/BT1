### Title
Webhook shop identity is taken from an unauthenticated header not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that identifies *which merchant* the webhook belongs to is read from the `X-Shopify-Shop-Domain` HTTP header, a field that is never included in the signed payload. An attacker who can obtain one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will accept it as authentic and hand the forged shop identity to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (i.e., only checks the body), and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — for webhooks this only binds the raw body: [4](#0-3) 

The broken identity binding is: `HMAC_valid(raw_body) == true` is treated as proof that `request.shop == <the merchant that body was signed for>`, when in fact the HMAC computation never involves `shop`, `topic`, or `webhook_id` at all. This is directly analogous to the audit finding's "field acted on but not covered by the signature/authorization check" pattern — here the shop-domain header used for per-tenant handler dispatch is not part of the signed payload.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing. Since request bodies for common webhook topics (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`) can be structurally identical or attacker-influenced in content while still validly signed for the attacker's own shop, an attacker can capture a legitimate `(body, hmac)` pair from a webhook fired for their own store and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header set to a victim shop. `Registry.process` will pass the forged `shop` value straight to the registered handler via `WebhookMetadata`, causing the host application to execute shop-scoped logic (e.g., data deletion/redaction, session invalidation, entitlement changes) against a shop the attacker does not control. This is a cross-tenant integrity violation reachable purely by an unprivileged internet user who can install the app on any store.

### Likelihood Explanation
Any developer/merchant can install the target app on their own free development store, legitimately trigger a webhook, and capture the resulting raw body and `X-Shopify-Hmac-Sha256` header — no credential theft or privileged access needed. Replaying that captured pair with a modified shop-domain (and possibly api-version/webhook-id) header to the app's public webhook endpoint requires only basic HTTP tooling. The gem provides no mechanism (nonce/shop binding, per-shop webhook secret, or replay window) to prevent this, so exploitability is high wherever the host app trusts `WebhookMetadata#shop` for tenant-scoped actions.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically tie the header claims to the signed body), and/or require the registry to cross-check `request.shop` against an expected shop context supplied by the caller before dispatching to `handler.handle`. At minimum, document that `request.shop` is unauthenticated and must be reconciled against server-side session state (not solely relied upon) before making any tenant-scoped changes.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker.myshopify.com"
# and triggers/receives a legitimate webhook, capturing:
raw_body = '{"id":123,...}'          # exact bytes Shopify sent
hmac     = 'X-Shopify-Hmac-Sha256 header value from that request'  # valid for raw_body

# Attacker replays it to the app's webhook endpoint, changing only the shop header:
POST /webhooks HTTP/1.1
X-Shopify-Topic: app/uninstalled
X-Shopify-Hmac-Sha256: <hmac captured above>
X-Shopify-Shop-Domain: victim-shop.myshopify.com   # forged, not covered by hmac
X-Shopify-Webhook-Id: anything
X-Shopify-Api-Version: 2024-01

<raw_body>

# ShopifyAPI::Webhooks::Registry.process(request):
#   Utils::HmacValidator.validate(request) => true (only checks raw_body)
#   handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app's handler now believes this action pertains to victim-shop.
``` [5](#0-4)
