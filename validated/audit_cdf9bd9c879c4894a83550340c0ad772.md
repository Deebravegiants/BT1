### Title
Unguarded Uniswap V4 spot-price oracle enables flash-loan price manipulation to drain Simplex solver liquidity on intent fills - (File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts)

### Summary
Simplex's "pool-based pricing" feature prices curveless cross-asset pairs directly from a Uniswap V4 pool's current spot price (`sqrtPriceX96`/tick) and uses that price both to quote/fill IntentGatewayV2 orders and to size withdrawals from the solver's own concentrated-liquidity position. The only defense against a manipulated quote — `referencePrice`/`maxDeviationBps` — is optional, off by default, and even when enabled only bounds static deviation, not execution/impact cost. This is the same bug class as the ValueDeFi incident: a single AMM pool's instantaneous price is trusted as an oracle and can be moved by an attacker in the same transaction (e.g., via a large swap or flash loan) before an order is submitted that gets filled/priced against the manipulated rate.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` reads the "best" position by pool liquidity and returns `computeDirectPoolPriceUsd`, which derives the price directly from the pool's live `sqrtPriceX96`/`token0Price`/`token1Price` with no TWAP, no size/impact adjustment, and no fee-tier correction: [1](#0-0) [2](#0-1) 

The flow documentation confirms this is used to quote and fill orders directly from raw pool mid-price, and that the only defense is a static reference-price deviation check — which itself does not account for execution cost or pool fee tier: [3](#0-2) 

The product documentation explicitly acknowledges the pool acts "as the price oracle instead of a static curve," and that the guard fields are optional — "omit both to leave the chain unguarded": [4](#0-3) 

This price feeds directly into `FXFiller.evaluateOrder`/`calculateProfitability`, which sizes the solver's fill (`targetOutput`, `finalOutputAmount`) and funding withdrawal from the Uniswap V4 position, then commits to filling `IntentGatewayV2.fillOrder` at that sized amount: [5](#0-4) [6](#0-5) 

An attacker (an unprivileged order placer / any actor who can execute a swap on the referenced Uniswap V4 pool) can: (1) push the pool's spot price away from fair value with a large swap or flash-loan-funded swap in the same block, (2) immediately submit (or have a colluding relayer/bidder submit) an `IntentGatewayV2` order sized against the now-favorable quote Simplex will compute, and (3) have Simplex's solver fill it — handing over more of the exotic token (or withdrawing more from its own LP position) than the true market price justifies, while the attacker reverses the pool manipulation afterward (e.g. within the same transaction/flash loan) to profit from the difference. This is structurally identical to the ValueDeFi incident, where an imbalanced/thin pool's instantaneous price was manipulated and then relied upon by downstream contract logic, draining protocol/user value.

### Impact Explanation
The exploit directly transfers value out of a solver's escrowed inventory/Uniswap V4 LP position by tricking Simplex into filling at a manipulated rate. Because pool pricing requires no bid/ask curve and the price guard is optional (config default: unguarded), any deployment using pool-based pricing without configuring `referencePrice`/`maxDeviationBps` is fully exposed; even a guarded deployment is only checked against deviation from a static reference and not against the pool's fee tier or trade-size impact, so a manipulation within the tolerated deviation band still allows profitable extraction. This is a concrete theft-of-funds vector against a live participant of the Hyperbridge intents ecosystem (the solver), triggered purely by a permissionless order submission plus a pool-price manipulating trade — both reachable by an unprivileged actor.

### Likelihood Explanation
Likely, because: pool-based pricing is a documented, supported, first-class Simplex configuration path (not a rare edge case); it explicitly targets pairs with low native liquidity/curve support ("exotic" tokens), which are the pools most susceptible to cheap price manipulation; and the protective guard is opt-in and, per the docs, commonly left unset ("omit both to leave the chain unguarded"). No governance or privileged access is required to trigger the manipulation — only a swap against the priced pool and a subsequent order submission.

### Recommendation
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever `[vault.uniswapV4]` pool-based pricing is used, rather than optional.
- Replace or supplement the raw spot price (`sqrtPriceX96`/tick) with a time-weighted average price (TWAP) read over multiple blocks, and require a minimum on-chain liquidity/observation window before trusting a quote.
- Incorporate the pool's fee tier and trade-size price impact into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` rather than treating the mid-price as valid across the full quoted quantity.
- Consider bounding fill size relative to available pool liquidity and rejecting fills whose implied price impact exceeds a safe threshold, independent of the static `maxDeviationBps` reference check.

### Proof of Concept
1. Configure a Simplex solver with `[vault.uniswapV4]` pool-based pricing for a low-liquidity exotic-token/USDC pool and no `referencePrice`/`maxDeviationBps` guard (the documented default/unguarded case).
2. Attacker executes a large swap (optionally flash-loan funded) against that Uniswap V4 pool, moving `slot0.sqrtPriceX96` far from fair value in the same block.
3. Attacker (or a colluding taker) immediately submits an `IntentGatewayV2.placeOrder` sized so that `UniswapV4FundingPlanner.getExoticTokenPrice` → `FXFiller.calculateProfitability` computes a highly favorable `targetOutput`/`finalOutputAmount` from the manipulated spot price (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:206-240`, `sdk/packages/simplex/src/strategies/fx.ts:498-539`).
4. Simplex fills the order via `IntentGatewayV2.fillOrder`, funding it by withdrawing liquidity from its Uniswap V4 position at the manipulated rate.
5. Attacker reverses the initial swap (closing the flash loan), realizing the price difference as profit extracted from the solver's escrowed/LP funds.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions
positions = [
    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

# Filling: how a fill amount is sized, and who else spends the same balance

Verified against the reverted Base fill `0x31de53fe...` (UserOp `0xe090acd1...`), traced end to end.

## Sizing, per leg

`FXFiller.evaluateOrder` walks `order.inputs` and sizes each leg independently (`src/strategies/fx.ts`):

1. `targetOutput` = what the curve will pay (`policyMaxOutput`), in every case. This is the amount the leg intends to hand over, and it may exceed what the user asked for — `IntrinsicIntents.fillOrder` takes `solverAmount > totalRequired` and splits the excess between the beneficiary and the protocol (`surplusShareBps`), and it is the same figure `quotePhantomFill` publishes as the pair's quoted rate. A pair's `maxOrderSize` is optional and does not shorten this: it binds earlier and in the other unit, where `computeLegPolicyOutput` rations `token0ForLeg` against the pair's remaining budget before the rate is applied. `desiredOutput` — the user's ask scaled by the same cap — is no longer a ceiling on payout; it survives as the price gate's comparand and in the short-fill logs.
2. `reserve` = the paymaster reserve for this token (`paymasterReserveForToken`, from `src/services/paymaster`) plus every funding venue's `walletReserveForToken`. Only the vault returns a non-zero venue reserve, its configured `minBalance`; `UniswapV4FundingPlanner` returns `0n`. The paymaster half is seeded outside the venue loop deliberately — the loop is empty when no vault and no V4 positions are configured, and that filler still sizes partial fills.
3. `usableWallet` = balance − reserve. `walletContribution` = `min(targetOutput, usableWallet)`.
4. Any shortfall is requested from each funding venue in turn via `planWithdrawalForToken`, which returns ERC-7821 calls and the amount it expects them to credit. The calls accumulate in `fundingCalls`. For V4 that credit is priced from `liquidityRemoval`, the liquidity the encoded DECREASE_LIQUIDITY actually carries — not the liquidity the planner asked for, which the SDK truncates.
5. `finalOutputAmount` = `min(walletContribution + credited, targetOutput)`.

After the loop, `estimateGasFillPost` prices the fill. A cross-chain order then has to clear one more affordability check: `fillOrder` dispatches the escrow-release message and `HyperApp.dispatchWithFeeToken` pulls `dispatchFee` from the same wallet in the destination host's fee token (USDC on Base — often the token just paid out). The fee is only known here, after the funding calls it depends on exist, and a cross-chain order cannot be partially filled, so the order is skipped when the residue will not cover the fee plus the paymaster reserve.

A capped leg is separately gated as a partial fill when the cap actually shortens it — `capFraction.lt(1) && policyMaxOutput < output.amount`. Both halves matter: with the payout unclamped, a curve running far enough above the order's rate covers the whole ask out of a capped slice, which is a full fill.

Whenever `finalOutputAmount < output.amount` the fill is an under-fill and has to clear `partialEligible()` — same chain, no output calldata, no prior partial — or the order is skipped.

The outputs and the funding calls are cached against the order id (`setFillerOutputs`, `setFundingPrepends`). `ContractInteractionService.prepareBidUserOp` reads them back verbatim and signs them into the bid; nothing re-reads the balance between sizing and execution, and the bid is committed, so an amount that was affordable at evaluation must still be affordable when the UserOp lands.
