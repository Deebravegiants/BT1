## Title
Webhook HMAC signature does not cover the `shop-domain` (or `topic`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw JSON body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Any attacker who can obtain one genuine, HMAC-valid webhook body (e.g., by installing the app on their own store) can replay that exact body with a forged `shopify-shop-domain` header to the merchant's webhook endpoint, and the gem will report the request as validly signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the received HMAC only against this signable string (the body): [2](#0-1) 

`Registry.process` gates on this HMAC check and then unconditionally trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from headers that are never part of the signed bytes — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

This breaks the intended binding: **shop identity asserted by the request == shop identity covered by the HMAC**. In reality, `shop` (the tenant identifier the host app uses to route/attribute the webhook payload) is disjoint from the bytes actually verified (`@raw_body` only). Any entity capable of producing one genuine `(body, hmac)` pair signed with the app's `client_secret` — trivially obtainable by installing the app on an attacker-controlled development store and receiving a legitimate webhook — can resend that same `(body, hmac)` pair with an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, because it only recomputes the HMAC over `raw_body`, and the forged `shop` header sails through unauthenticated.

This is directly analogous to the reported staking-indexer bug class: a check ("is this HMAC valid") answers permissively because the field actually acted upon (`shop`, used to attribute/route data to a tenant) is not the field the check actually covers (`raw_body`).

### Impact Explanation
A host application using this gem's `Webhooks::Registry.process` to multiplex webhook processing across tenants (a common pattern — using `WebhookMetadata#shop` to look up the correct `Session`/tenant record before acting on `body`) can be tricked into attributing an attacker-controlled but validly-signed payload to a victim shop of the same app. Depending on the handler logic, this enables cross-tenant data injection/corruption (e.g., an attacker's own order/fulfillment/customer webhook data being written into the victim shop's records), which falls under the Critical "cross-tenant access" category.

### Likelihood Explanation
High. Any user can install the target app on their own (attacker-controlled) shop for free/trial and receive real, validly-signed webhooks. Since `topic`, `shop`, `webhook_id`, and `api_version` are ordinary HTTP headers with no cryptographic binding to the signed body, forging them and replaying the captured request to the app's public webhook endpoint requires no special access, TLS interception, or leaked secrets — only the ability to send an HTTP POST, which is the normal threat model for a public webhook endpoint.

### Recommendation
Include the routing-relevant headers (`shop`, `topic`, at minimum) in the data that is authenticated, or otherwise cryptographically/contextually bind them to the verified payload. Options:
- Have `to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside `raw_body` (this would require coordinating with Shopify's webhook signing scheme, since Shopify currently signs only the body — so at minimum the gem/host app should cross-check `shop` against a value obtained through a trusted, previously authenticated channel, e.g. verifying the shop has an active, known session/install record before processing).
- At minimum, document prominently (and ideally enforce) that `WebhookMetadata#shop` must be re-validated against the app's own store of installed shops before being used to select tenant state, since it is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) to their own controlled endpoint, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header value `H` (both signed correctly by Shopify with the app's real `client_secret`).
2. Attacker sends an HTTP request directly to the victim merchant-facing webhook endpoint (running the vulnerable host app) with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic` = `orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop = "victim-shop.myshopify.com"` and `body` = attacker-controlled content, despite the request having nothing to do with the victim shop. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
