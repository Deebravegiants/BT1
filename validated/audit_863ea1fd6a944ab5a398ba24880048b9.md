### Title
Webhook shop domain is unauthenticated and not bound to the HMAC signature, allowing cross-tenant `app/uninstalled` replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the shop domain purely from an unsigned HTTP header, while `#to_signable_string` (used by `HmacValidator.validate`) only covers `@raw_body`. Because topics like `app/uninstalled` have a fixed, content-free body (`{}`), an attacker can capture a validly-signed callback for their own shop and replay the identical body+HMAC to the victim's webhook endpoint with the `x-shopify-shop-domain` header rewritten, and `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming the victim's shop.

### Finding Description
The broken binding: the gem implicitly assumes `hmac_authenticated_shop == WebhookMetadata.shop`, but in the code these are two independent values:
- `WebhookMetadata.shop` comes from `request.shop`, which is `T.cast(shopify_header("shop-domain"), String)` — read straight from `@headers`, never covered by any signature check [1](#0-0) .
- The HMAC is validated against `to_signable_string`, which is defined as `@raw_body` only — headers (including the shop-domain header) are never part of the signable content [2](#0-1) .
- `HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the received signature; it has no visibility into `@headers` at all [3](#0-2) .
- `Registry.process` calls `HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and invokes the handler — there is no secondary check tying the header-derived `shop` to anything cryptographically verified [4](#0-3) .

Exploit flow: the attacker installs the target app on their own development shop and registers an `app/uninstalled` HTTP webhook handler pointed at a server they control. When they uninstall the app, Shopify delivers a request with body `{}` and a valid `x-shopify-hmac-sha256` computed over that body with the app's real `api_secret_key`. The attacker then sends a new HTTP request to the target app's webhook endpoint with the same raw body `{}` and the same HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`. `Request.new` accepts it (all three required headers present), `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, and `Registry.process` calls the host app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: "app/uninstalled", body: {})`. The documented usage pattern in `docs/usage/webhooks.md` shows apps trusting `data.shop` directly (e.g., enqueuing work keyed by `data.shop`) [5](#0-4) , so a host app implementing the standard `app/uninstalled` cleanup pattern would delete/deactivate the victim shop's stored session/tokens based on this forged metadata.

No existing guard in this gem closes the gap: `ShopValidator`, `JwtPayload`, and OAuth `state` checks are unrelated to webhook processing; `Context.setup?`/`private?` do not affect webhook validation; Sorbet signatures only enforce types (`String`), not provenance or binding to the signature.

### Impact Explanation
This is a cross-tenant confusion: an unprivileged attacker (an app installer on their own shop) can cause the host app to execute privileged, per-shop side effects (most severely, `app/uninstalled` cleanup — deleting sessions, deactivating access tokens, disabling billing, etc.) against an arbitrary victim merchant they do not control, by replaying their own validly-signed webhook with a rewritten shop header. This is repeatable against any target shop domain (they are public/guessable, e.g. `<name>.myshopify.com`), and works for any topic whose body content is invariant or attacker-known, not just `app/uninstalled`. This matches the Critical category: cross-tenant access driven by treating an unauthenticated value (`request.shop`) as authenticated.

### Likelihood Explanation
Preconditions are low-cost and entirely attacker-controlled: create a development/trial shop, install the target app, register (or receive) an `app/uninstalled` HTTP webhook, capture the raw body and HMAC, and replay to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, no victim cooperation, and no privileged access are required — only the ability to send an arbitrary HTTP POST to the app's known webhook route. The only host-app-side dependency is that it follows the documented pattern of trusting `WebhookMetadata.shop` for shop-scoped actions, which is exactly what the gem's own documentation encourages.

### Recommendation
Bind the shop domain (and other trust-relevant headers, e.g., topic) into the signed/verified content, or independently verify that the shop domain in the header corresponds to a shop with an active, known installation/session before acting on `app/uninstalled` (and other topics). At minimum, `Request#to_signable_string` should not be the sole source of truth for what's "authenticated" — the shop used to select a DB record should be cross-checked against a value derived from something Shopify has bound to the signature (e.g., validate that the webhook_id/shop pairing matches a subscription your app registered), or apps should be documented to enforce shop-domain allowlisting from known installed shops rather than trusting the header verbatim.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_accepts_replayed_body_with_spoofed_shop_domain
  raw_body = "{}"
  secret = ShopifyAPI::Context.api_secret_key
  valid_hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
  )

  attacker_headers = {
    "x-shopify-topic" => "app/uninstalled",
    "x-shopify-hmac-sha256" => valid_hmac,
    "x-shopify-shop-domain" => "attacker.myshopify.com",
  }
  attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
  assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))

  # Replay identical body+hmac, only the shop header changed
  spoofed_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim.myshopify.com")
  spoofed_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

  # Same binding still holds (HMAC unaffected by header change)
  assert(ShopifyAPI::Utils::HmacValidator.validate(spoofed_request))
  assert_equal("victim.myshopify.com", spoofed_request.shop)

  received_shop = nil
  handler = Class.new do
    extend ShopifyAPI::Webhooks::WebhookHandler
    def self.handle(data:)
      # capture what the host app would act on
    end
  end
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "app/uninstalled", delivery_method: :http, path: "cb", handler: handler
  )

  handler.stub(:handle, ->(data:) { received_shop = data.shop }) do
    ShopifyAPI::Webhooks::Registry.process(spoofed_request)
  end

  assert_equal("victim.myshopify.com", received_shop) # attacker forced victim-shop-scoped handling
end
```
This demonstrates that `Request#shop` (unauthenticated header value) diverges from the HMAC-authenticated `raw_body`/secret binding while still passing `HmacValidator.validate`, and that `Registry.process` propagates the attacker-chosen shop domain into `WebhookMetadata` unchecked.
