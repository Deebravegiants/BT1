### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing shop-spoofing / cross-tenant misattribution of an otherwise validly-signed webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` HTTP header — which is never included in the signed bytes — to decide which tenant the payload belongs to. This breaks the intended binding `HMAC-authenticated == (shop, body)`; the implementation only enforces `HMAC-authenticated == (body)`, with `shop` supplied out-of-band and unauthenticated.

### Finding Description
`Registry.process` verifies authenticity with: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns only the raw body — the `shop` value (read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is not part of the signed content at all: [2](#0-1) [3](#0-2) 

Once the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop` and hands it to the app's handler as the authoritative tenant identity, with no cross-check that this header is consistent with anything covered by the signature: [1](#0-0) [4](#0-3) 

The documented handler contract explicitly tells integrators to key application-side actions (job dispatch, tenant lookup, etc.) off `data.shop`: [5](#0-4) 

Because the signature never binds `shop` to `body`, any actor who can obtain one validly-signed `(raw_body, hmac)` pair for a tenant they control (e.g. any user who installs the app on a free/dev store and receives real Shopify webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` forwards the attacker-chosen `shop` string straight to the handler as if it were Shopify-attested.

### Impact Explanation
This is a broken identity binding of the "bytes verified versus bytes parsed" class: the bytes cryptographically verified (raw body) are disjoint from the bytes the handler treats as tenant identity (`shop` header). Any app that uses `data.shop` from the webhook handler to select which merchant's session/data to act on (exactly as the gem's own documentation recommends) can be made to process a foreign payload under a victim shop's identity, or conversely have a victim's genuine webhook body misattributed. This crosses a tenant boundary using only a validly-signed webhook the attacker legitimately received for their own install — no `api_secret_key`, access token, or privileged access is required — matching the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is limited by the need for the attacker to first obtain one legitimately-signed webhook body/HMAC pair, which is trivially possible for any developer/merchant who installs the app themselves (a normal, unprivileged action) and captures a webhook Shopify sends them. From that point, forging the header on replay requires no cryptographic secret. The severity therefore depends heavily on whether the downstream handler trusts `data.shop` for tenant-sensitive actions, which the gem's own documented usage pattern actively encourages.

### Recommendation
Bind the shop identity into the authenticated material rather than trusting an out-of-band header:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string` so the HMAC covers the tuple `(shop, topic, body)`, not just `body`; or
- After HMAC validation, independently verify that `request.shop` corresponds to a shop with an active, known installation/session before dispatching to the handler, and document that host applications must not rely on the unauthenticated `shop` header alone for tenant selection.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":123,...}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify with the app's `client_secret` over that exact body.
2. Attacker replays the identical raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` is `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only (`to_signable_string`) — identical to step 1's body — so validation succeeds despite the spoofed shop header.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's payload> ...)`, and any host logic keyed on `data.shop` (as recommended in `docs/usage/webhooks.md`) now acts on the victim tenant using attacker-controlled data.
