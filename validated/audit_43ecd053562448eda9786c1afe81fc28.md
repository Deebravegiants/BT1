### Title
Denylist-based `IsmpCallFilter` on `handle_unsigned` can be outgrown by new `Message` variants, letting an attacker submit forged BEEFY consensus updates through the naive/ECDSA path instead of the required SP1 proof - ([File: parachain/runtimes/nexus/src/lib.rs], [File: parachain/runtimes/gargantua/src/lib.rs])

### Summary
`IsmpCallFilter::contains` on both the `nexus` and `gargantua` runtimes is a hand-maintained denylist, structurally identical to the OpenClaw bug: it enumerates the specific `RuntimeCall`/`Message` shapes it wants to block (`fund_message`, and `Message::Consensus` targeting the BEEFY consensus state id) and defaults to `true` (allow) for everything else. This is a fail-open pattern rather than a fail-closed allowlist, so any future addition to the `ismp::messaging::Message` enum, or any other call path capable of feeding data into the BEEFY consensus state, is allowed through `BaseCallFilter` by default unless someone remembers to update this specific match arm. [1](#0-0) [2](#0-1) 

### Finding Description
Both runtimes route BEEFY consensus updates exclusively through `pallet-beefy-consensus-proofs`, which enforces SP1 zkVM verification before it will advance BEEFY state. The comment on `IsmpCallFilter` explicitly states the intent: "Allowing raw updates through `handle_unsigned` would bypass that requirement entirely, so any batch that carries a BEEFY consensus message is rejected here." [3](#0-2) 

The filter implements this intent as a denylist over the `Message` enum: it only inspects `Message::Consensus(...)` and matches the `consensus_state_id` against BEEFY's client id via `host.consensus_client_id`. Anything that is not literally a `Message::Consensus` value naming the BEEFY state is passed through (`_ => false` inside the `any()`, i.e. not blocked):

```rust
RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
    let host = Ismp::default();
    !messages.iter().any(|message| match message {
        Message::Consensus(consensus) =>
            host.consensus_client_id(consensus.consensus_state_id) ==
                Some(ismp_beefy::BEEFY_CONSENSUS_ID),
        _ => false,
    })
},
_ => true,
``` [4](#0-3) 

The underlying `handle_unsigned` extrinsic dispatches into `pallet_ismp::Pallet::execute`, which for a `Message::Consensus` calls the registered consensus client's `verify_consensus`. For BEEFY, `BeefyConsensusClient::verify_consensus` (`modules/ismp/clients/beefy/src/consensus.rs`) itself supports *two* proof types read from the first payload byte: `PROOF_TYPE_SP1` (the intended, zk-verified path) and `PROOF_TYPE_NAIVE` (raw ECDSA/`SubstrateCrypto` signature verification, weaker and meant only for the `beefy-consensus-proofs` pallet's controlled `verify_and_apply` flow). The runtime's own defense against a caller reaching this naive path directly is *only* the `IsmpCallFilter` denylist — there is no allowlist that says "only SP1-gated calls into the BEEFY consensus client are permitted"; the guard instead pattern-matches on the exact shape of today's `Message` enum and the exact way `consensus_client_id` resolves BEEFY. [5](#0-4) 

This mirrors the OpenClaw root cause precisely: a security boundary ("agent/attacker-reachable input must not touch this subtree") implemented as a denylist keyed to the current shape of a growing schema (the `Message` enum, and the mapping used to detect "is this BEEFY"), rather than a fail-closed allowlist keyed to the invariant that actually matters (BEEFY state may only be advanced via the SP1-gated pallet). Any future `Message` variant, or any future consensus-client-id aliasing/registration change that lets a state resolve to BEEFY without going through `consensus_client_id` exactly as coded, silently falls through the `_ => true` / `_ => false` default-allow branches.

### Impact Explanation
If the denylist is ever outgrown (e.g., a new `Message` variant is added upstream that can also mutate or seed BEEFY-adjacent consensus state, or a state machine is bound to BEEFY through a path this filter doesn't recognize), an unprivileged caller could submit a raw, unsigned `handle_unsigned` extrinsic that reaches `BeefyConsensusClient::verify_consensus` via the naive ECDSA path instead of the mandatory SP1 path. That would let an attacker forge BEEFY consensus/authority-set state with a weaker proof than the protocol's designed trust model requires, which cascades into forged state-machine commitments and forged message delivery/mint across every parachain and app relying on BEEFY-verified state (a "forged message delivery" / "unsound state commitment" class of impact under the given validation rubric). This is High severity in kind, matching the advisory's severity, because the entry point (`handle_unsigned`) is unprivileged and reachable by any relayed extrinsic.

### Likelihood Explanation
Today's implementation of `IsmpCallFilter` does correctly block the one avenue it was written for (raw `Message::Consensus` batches naming BEEFY's `consensus_state_id`), and the accompanying simnode tests (`parachain/simtests/src/base_call_filter.rs`) verify exactly that behavior. I could not, within the available tooling, enumerate the full current definition of `ismp::messaging::Message` (the file `modules/ismp/core/src/messaging.rs` did not return content before the tool budget ran out) to confirm whether an additional variant already exists today that bypasses this filter. So the concrete, currently-exploitable gap is **unconfirmed** — the finding here is that the *pattern* itself (denylist tied to current schema shape, not a fail-closed allowlist) is the same anti-pattern that produced the OpenClaw advisory, and it is the sole runtime-level guard standing between an unprivileged relayer and the naive-proof BEEFY path. Given the explicit design comment stating this is meant to be a hard boundary ("would bypass that requirement entirely"), any future schema growth in `Message` or in how a state machine gets bound to a consensus client carries out-of-band risk of silently reopening this bypass, exactly as happened with OpenClaw's config paths.

### Recommendation
Replace the denylist logic in `IsmpCallFilter::contains` (both `parachain/runtimes/nexus/src/lib.rs` and `parachain/runtimes/gargantua/src/lib.rs`) with a fail-closed check: rather than asking "is this the one exact shape of message the filter currently knows how to recognize as BEEFY-related," invert it to "does executing this message reach the BEEFY consensus client at all" and reject unless a message can be affirmatively proven *not* to touch BEEFY's consensus/authority state. Concretely:
- Enumerate every `Message` variant explicitly in the match (no wildcard `_ => false` inside the `any()`), so a new variant added upstream defaults to being treated as suspicious/blocked until the filter is updated for it, rather than silently passing.
- Audit `modules/ismp/core/src/messaging.rs` for the full `Message` enum and `modules/ismp/clients/beefy/src/consensus.rs` for every way a call can resolve to the BEEFY consensus client id, and assert the filter's block condition covers all of them (including any `FraudProofMessage` or future consensus-mutation message kinds).
- Add a compile-time or CI check (e.g., an exhaustive match with no wildcard arm) so adding a new `Message` variant forces a decision in `IsmpCallFilter` rather than silently defaulting to allowed.

### Proof of Concept
Not independently reproducible with current tooling: the tool budget ran out before the full `ismp::messaging::Message` enum definition (`modules/ismp/core/src/messaging.rs`) could be retrieved to confirm whether a concrete bypassing variant exists today. The existing simnode test `ismp_call_filter_blocks_only_beefy_consensus_and_fund_message` in `parachain/simtests/src/base_call_filter.rs` demonstrates the filter's current denylist behavior and would be the right harness to extend: add a case constructing any `Message` variant other than `Message::Consensus` that still results in `execute()` invoking `BeefyConsensusClient::verify_consensus` with `PROOF_TYPE_NAIVE`, and confirm whether `IsmpCallFilter` lets it through (`is_bad_origin` rather than `is_call_filtered`).
