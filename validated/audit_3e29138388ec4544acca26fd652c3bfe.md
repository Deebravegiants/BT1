### Title
Webhook shop/topic identity fields are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the event to a tenant are taken from unauthenticated HTTP headers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies the HMAC using exactly this signable string and, once it passes, trusts the header-derived `topic`/`shop` values to dispatch the event to the app's handler: [2](#0-1) 

The `shop` (and `topic`) accessors read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed payload: [3](#0-2) 

The identity binding that should hold is:
`HMAC_secret(raw_body) == received_hmac` **and** `shop header == shop embedded/bound in the signed content`.

What is actually verified is only the first half: `HMAC_secret(raw_body) == received_hmac`, via `Utils::HmacValidator.validate`, which itself just recomputes the digest over `verifiable_query.to_signable_string` (the body) and compares it to the header HMAC: [4](#0-3) 

Because a single `api_secret_key` is shared by an app across *every* shop that installs it (not a per-shop secret), any party who has ever received one legitimate `(raw_body, hmac)` pair from Shopify for *any* shop that has the app installed — e.g., by installing the app themselves on their own store and capturing a webhook delivery — can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary value in the `shop-domain` header. The `Utils::HmacValidator.validate` check still passes (it never looks at headers), and `Registry.process` will hand the (attacker-chosen) `shop` value to `handler.handle(data: WebhookMetadata.new(topic:, shop:, body:, api_version:, webhook_id:))` as if it came from that victim shop.

### Impact Explanation
Any application (this is standard `shopify_app`/host-app pattern, documented in `docs/`) that uses `WebhookMetadata#shop` to select which tenant's DB row/session to mutate (e.g., process `app/uninstalled`, `shop/redact`, `customers/data_request`) will act on the wrong tenant's data using an attacker-forged shop identity, while the request still cryptographically "validates." This is a cross-tenant confusion primitive reachable by an unprivileged attacker who has legitimately received (or can guess/replay) a valid body for any topic the app subscribes to — it does not require the app's `client_secret`, an access token, or any privileged credential, only a previously observed valid webhook delivery (obtainable by self-installing the app).

### Likelihood Explanation
Moderate. The attacker must obtain at least one legitimate `(raw_body, hmac)` pair, which is straightforward for any developer who installs the target app on their own store (a normal, unprivileged action) and captures the resulting webhook call. Many webhook bodies are static or low-entropy (e.g., `app/uninstalled` bodies contain little/no shop-specific data), making a captured pair broadly replayable across shops by simply changing the header.

### Recommendation
Bind the `shop`/`topic`/`webhook_id` identity fields into the signed material, or otherwise cryptographically tie the header-supplied shop to the verified payload, before dispatching to handlers — e.g., require the caller/host app to independently verify that the `shop-domain` header corresponds to a shop for which this specific `(topic, body)` combination is expected, or document explicitly (with enforcement in the library where feasible) that `WebhookMetadata#shop` must not be trusted as an authenticated value and must be re-validated by the host app against its own installed-shops registry before use.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and captures a real webhook delivery, e.g. for topic "app/uninstalled":
raw_body = "{}"  # low/no entropy body typical of this topic
real_hmac = "<value captured from Shopify's X-Shopify-Hmac-Sha256 header>"

# 2. Attacker replays the exact same body+hmac to the app's webhook endpoint,
#    but swaps the shop-domain header to a victim shop they do NOT control:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => real_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks HMAC(raw_body),
# and the handler receives WebhookMetadata with shop == "victim-shop.myshopify.com".
``` [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
