### Title
Consensus-incentive rewards use the current `CostPerBlock` for the entire unpaid backlog instead of accruing at the rate in force when each block was produced - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives` pays relayers for consensus updates by multiplying the *entire* unpaid block span (`latest_height - LastRewardedHeight watermark`) by whatever `StateMachinesCostPerBlock` value is stored **at settlement time**, exactly like MasterChef computing a pool's whole unaccrued reward window against a globally mutated rate instead of first accruing the pending amount at the old rate. Any relayer can let unpaid blocks accumulate and then trigger settlement after a routine `update_cost_per_block` change, capturing (or losing) the entire backlog's value at the wrong rate.

### Finding Description
`Pallet::calculate_reward` in `modules/pallets/consensus-incentives/src/impls.rs` computes: [1](#0-0) 

`baseline` is the `LastRewardedHeight` watermark, which only advances when a reward is actually paid out via `process_message`: [2](#0-1) 

`block_cost` is read fresh from `StateMachinesCostPerBlock` on every call, with no historical record of which rate applied to which block range: [3](#0-2) 

`update_cost_per_block` is a normal, expected governance operation (rate adjustment, e.g. inflation tuning) that simply overwrites the map entry in place — there is no analog to MasterChef's `massUpdatePools()` that would first settle/accrue rewards for the span already produced under the old rate: [4](#0-3) 

Because `on_executed`/`process_message` only run when a `ConsensusMessage` is actually delivered and processed by `pallet-ismp`, the "settlement" moment is controlled by whichever relayer chooses to submit the message — an unprivileged, permissionless action. A relayer (or anyone racing to deliver a queued consensus proof) can therefore choose *when* to trigger `calculate_reward`, and thus which `block_cost` value applies to the whole outstanding span since `LastRewardedHeight`.

### Impact Explanation
If a relayer withholds delivery of already-available consensus proofs while the chain's `latest_commitment_height` keeps advancing (or simply doesn't get around to submitting a backlog), the entire un-rewarded span accrues no cost commitment. When governance later raises `CostPerBlock` for legitimate reasons, the relayer submits the backlog in one batch and `calculate_reward` multiplies the full historical block span by the new, higher rate — over-paying the treasury account (`T::TreasuryAccount`) far beyond what governance intended for that period. This is a direct, unbacked drain of treasury funds triggerable by an unprivileged relayer, with no malicious admin/governance action required (the rate change itself is a routine, honest update). Conversely, a rate decrease silently underpays relayers for work already done, which is an unfair/incorrect-accounting issue but less severe than the treasury drain direction.

### Likelihood Explanation
Any registered relayer that observes `StateMachinesCostPerBlock` governance proposals (a public, on-chain, typically-timelocked extrinsic) can simply delay submitting `[Consensus]` messages for a chain and then batch-submit right after the new higher rate takes effect. No special privilege is needed beyond being a relayer capable of delivering an ordinary consensus message, and the `LastRewardedHeight` watermark design explicitly permits unpaid spans to grow arbitrarily large while waiting.

### Recommendation
Accrue and settle (or at minimum record) the reward due at the *previous* rate for the span up to the current chain tip before applying a new `CostPerBlock`, mirroring MasterChef's `massUpdatePools()` fix: e.g., have `update_cost_per_block` first checkpoint `LastRewardedHeight` to the state machine's current `latest_commitment_height` (crediting the pending reward at the old rate, or explicitly marking it as forfeited/zeroed by design) before installing the new rate. Alternatively, store a rate-history/checkpoint table so `calculate_reward` can split a block span across the rate(s) that were actually in effect for each sub-range instead of applying a single "current" rate to the whole backlog.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[X] = 10` via `update_cost_per_block`.
2. Chain `X` advances consensus commitments from height 1000 to 5000 over time, but no relayer submits the corresponding `ConsensusMessage`s to hyperbridge (`LastRewardedHeight[X]` stays at 1000; `latest_commitment_height` is 5000 on the local `IsmpHost` view once the header/consensus proofs are eventually accepted).
3. Governance later raises `StateMachinesCostPerBlock[X] = 1000` (a normal, legitimate parameter update, e.g. following token price appreciation).
4. A relayer submits the backlog of consensus messages for `X` in a single `on_executed` batch. `calculate_reward` computes `reward = (5000 - 1000) * 1000 = 4_000_000`, i.e., the entire 4000-block backlog priced at the new rate, instead of `4000 * 10 = 40_000` (old rate) — a 100x over-payment drained from `TreasuryAccount` to the relayer, purely by timing the submission around the rate change.

			});

		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}
