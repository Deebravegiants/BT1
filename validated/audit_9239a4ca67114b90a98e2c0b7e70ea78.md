### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw HTTP body, then blindly trusts the `shop-domain` HTTP header as the tenant identifier passed to the app's handler. Since the HMAC signable string only covers `raw_body` and never the `shop` header, the `shop` value is not bound to the signature. Because the `api_secret_key` used to sign webhooks is shared across every shop that has installed a given app (it is not shop-specific), any shop that has legitimately installed the app can capture a real, validly-signed webhook it receives and replay it to the app's endpoint with the `x-shopify-shop-domain` header swapped to a victim shop, producing a webhook that still passes HMAC validation but is now attributed to the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly, unauthenticated, from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. only the body — the `shop` header plays no role in the signature computation or comparison: [3](#0-2) 

`Registry.process` performs exactly this check-then-trust pattern: it validates the HMAC of the request, then immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier handed to the app's handler: [4](#0-3) 

The gem's own documentation instructs host apps to treat `data.shop` from `WebhookMetadata` as the authoritative shop identifier after `Registry.process` has verified the webhook "did indeed come from Shopify": [5](#0-4) [6](#0-5) 

**Broken identity binding (as an equality):**
`shop_header_value` (attacker-controlled, unauthenticated) is expected by the app to equal `shop_that_the_signed_body_actually_belongs_to`. The gem only proves `HMAC(raw_body, api_secret_key) == received_hmac`, which proves the *body* was produced by an entity that knows the app's single, shop-agnostic `api_secret_key` (i.e., Shopify) — it proves nothing about which shop's `shop-domain` header accompanies that body. `request.shop` is therefore returned as "verified" by `Registry.process` even though it is not bound to the HMAC at all.

### Impact Explanation
Because a single `api_secret_key` is shared by the app across *all* shops that install it, any unprivileged user who installs the target app on their own shop (a normal, unprivileged action available to any internet user) receives real, validly HMAC-signed webhooks for their own shop. That user can then replay the exact `raw_body` + `x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a different, victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while `body`/`topic` are the attacker's own genuine webhook data. Any app that uses `data.shop` (as the gem's own documentation tells developers to do) to key per-tenant storage, trigger per-tenant side effects, or scope background jobs (`perform_later(shop_domain: data.shop, ...)` in the doc's own example) will process attacker-supplied data under the identity of a shop the attacker does not control — a cross-tenant confusion/injection primitive. This maps to the "Critical - cross-tenant access" impact bucket defined in scope.

### Likelihood Explanation
Likelihood is high for any app author who follows the gem's documented pattern literally, since the gem provides no shop-binding of its own and the vulnerable code path is the only "verification" step offered (`Registry.process`). The prerequisite — installing the target app to obtain one genuine signed webhook — is achievable by any unprivileged internet user, and replaying an HTTP request with one header changed requires no special access, credentials, or social engineering.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is cryptographically verified, or derive the shop identity from a source that is itself covered by the signature (e.g., verify that the `shop-domain` header matches a shop actually registered/expected for the given webhook subscription, rather than trusting the header unconditionally). At minimum, `HmacValidator`/`Request#to_signable_string` should not present `request.shop` to callers as "verified" data when the header carrying it was excluded from the signed payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com`, completing normal OAuth (no elevated privilege required).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw_body>`, `x-shopify-topic: orders/create`
   - Body: attacker's own order JSON, fully attacker-controlled since it's the attacker's own shop.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are static, replayable, and unaffected by which header values accompany them since `to_signable_string` only returns `raw_body`, per `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. Attacker POSTs this same `raw_body`/`hmac` to the app's webhook endpoint again, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, and any downstream logic keyed on `data.shop` (as recommended in `docs/usage/webhooks.md` lines 12-30) now attributes attacker-controlled content to the victim tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
