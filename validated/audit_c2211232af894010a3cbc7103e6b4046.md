### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by HMAC-verifying only the raw request body, then passes the unauthenticated `shop-domain` header value to the app's handler as the tenant identifier. This mirrors the reported bug class: a field that is acted upon (here, the `shop` used to attribute the webhook to a tenant) is not covered by the cryptographic check that gates the operation (here, the HMAC).

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`; none of the HTTP headers are part of the signed string [2](#0-1) . However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the HMAC digest [3](#0-2) .

`Registry#process` validates only the body's HMAC, then forwards `request.shop` (an unverified header) into `WebhookMetadata`, which the host app's handler uses to identify the tenant the event belongs to [4](#0-3) . The documentation explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used directly to key tenant-scoped work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [5](#0-4) .

Binding broken (as an equality):
`bytes verified by HMAC (raw_body)` ≠ `bytes acted on (shop-domain / topic / webhook_id headers)`

Because the signature only proves body integrity, not header integrity, anyone who can produce one valid `(body, hmac)` pair for their own shop — a normal, unprivileged app user with a real installation, since they legitimately receive real webhook calls containing a body+hmac pair signed with the app's `client_secret` — can replay that exact body/hmac to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's shop domain). `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry#process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop [6](#0-5) .

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: an attacker with a valid installation (and therefore access to genuinely-signed webhook deliveries for their own shop) can cause the host application to process and attribute arbitrary webhook data to a different, victim tenant, since the gem provides no way to detect that the header-derived `shop` doesn't match the body that was actually signed. Depending on how the host app's handler uses `data.shop` (e.g., updating per-tenant records, triggering per-tenant business logic, cache/database writes keyed by shop), this can lead to cross-tenant data corruption or unauthorized actions against another merchant's tenant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is only moderate-to-high conditioned on how strictly the impact bar is read: exploitation requires the attacker to possess at least one legitimately-signed `(body, hmac)` pair, which any app-installing merchant/user can obtain simply by using the app normally (webhooks fire automatically on their own shop's events) — no `api_secret_key` or access-token theft is required, only replay of already-received bytes with a modified header, which is trivial over the internet since the webhook endpoint is a public HTTP callback URL.

### Recommendation
- **Short term:** Do not treat header-derived `shop`, `topic`, `webhook_id`, or `api_version` as trusted/authenticated values distinct from what is verified. Either include these fields in the signed string checked by the HMAC, or explicitly document that `Registry.process` does not authenticate them and require host apps to cross-check `data.shop` against a known/installed shop for that specific webhook subscription (e.g., correlate against the topic+webhook_id combination registered for that tenant) before trusting it.
- **Long term:** Add validation in `Registry#process`/`Webhooks::Request` binding the header-derived tenant identity into the cryptographic check (or reject processing when the claimed shop cannot be independently corroborated), document the trust boundary clearly, and add regression tests that replay a valid body/HMAC with a mismatched `shop-domain` header to assert this can be detected or rejected.

### Proof of Concept
1. App merchant A installs the app; a normal webhook (e.g., `orders/create`) fires to the app's callback URL with a valid raw body and a correct `X-Shopify-Hmac-Sha256` header signed with the app's `client_secret`.
2. Attacker (merchant A, or anyone who intercepts/replays this legitimately-received POST) resends the exact same raw body and HMAC header to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`@raw_body`) — this still matches, so validation passes [7](#0-6) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-controlled `shop-domain` header and passed to the app's handler as though it came from `victim-shop.myshopify.com` [8](#0-7) .
5. The host app processes/attributes the (attacker's own) webhook payload as belonging to the victim tenant.

          received_signature = verifiable_query.hmac

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
