## Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an unauthenticated HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Because the same app-wide `api_secret_key` is used to sign webhooks for every shop that has installed the app, any shop that has legitimately installed the app can obtain a validly-signed webhook body and replay it against the app's webhook endpoint with a forged `shop-domain`/`x-shopify-shop-domain` header naming a different, victim shop. `ShopifyAPI::Webhooks::Registry.process` accepts the request as valid and hands the attacker-chosen `shop` value to the host application's webhook handler as if it were authentic.

### Finding Description
The binding that should hold is:
`shop value trusted by the handler == shop value cryptographically bound to the signed payload`

but it does not, because:

1. `Request#hmac` reads the signature purely from a header [1](#0-0) 
2. `Request#shop` also reads an unauthenticated header, entirely independent of the signature [2](#0-1) 
3. `Request#to_signable_string`, which is the only thing actually verified by the HMAC, returns just the raw body — it does not include the shop domain, topic, or any other header [3](#0-2) 
4. `HmacValidator.validate` computes the signature strictly over `to_signable_string` using the single, app-wide `Context.api_secret_key` (shared by every shop that installed the app) [4](#0-3) 
5. Once validation passes, `Registry.process` forwards `request.shop` (the unauthenticated header) directly to the app's webhook handler as the tenant identity [5](#0-4) 

Because the secret is shared across tenants, an attacker who legitimately installs the app on their own store can trigger a webhook (e.g. via `products/update`) with a body of their choosing, capture its valid `hmac-sha256` signature, and then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` reports success (it never inspected the shop header), and `Registry.process` calls the handler with `shop: <victim-shop>` and attacker-controlled `body`.

### Impact Explanation
Host applications built on this gem are expected to scope all persisted webhook data by `WebhookMetadata#shop` — this is the entire purpose of shipping `shop` in the metadata. Since the gem provides no cryptographic binding between the verified payload and the shop identity, an attacker can inject fabricated data (order/product/customer/GDPR payloads, etc.) that the host application will store or act on as if it belonged to an arbitrary victim shop, i.e. cross-tenant data injection/corruption using only their own (or any) app installation as a signing oracle.

### Likelihood Explanation
Any merchant who can install the app (a normal, unprivileged action) can obtain valid `(body, hmac)` pairs at will and immediately replay them with an arbitrary `shop-domain` header, since no additional secret or privilege is required beyond having one working installation.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is actually verified, e.g. include the `shop-domain` header (and other identifying headers) in `to_signable_string`, or — since Shopify's webhook HMAC scheme is fixed to sign only the body — have the gem require host applications to cross-check `request.shop` against an independently-trusted source (such as the shop associated with the session/store that was used to register the webhook) before trusting it, and document this gap prominently since it cannot be fixed by changing the signable string alone (Shopify's own HMAC only ever covers the body).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook delivery with attacker-controlled content, e.g. update a product to produce a `products/update` webhook; capture the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
3. Replay the exact captured body to the app's webhook endpoint, keeping the same `X-Shopify-Hmac-Sha256` value, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks the body against the app-wide secret [6](#0-5) .
5. The handler executes with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, as constructed here [7](#0-6) .
