### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats `Utils::HmacValidator.validate(request)` as proof that an inbound webhook request — including its `shop` and `topic` — genuinely originated from Shopify for that shop. In fact, the HMAC only authenticates the request body; the `shop-domain` and `topic` HTTP headers are read verbatim and are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is that `hmac` authenticates `to_signable_string`. For webhook requests, `to_signable_string` returns only the raw body: [1](#0-0) 

But `shop` and `topic` are pulled straight from unauthenticated headers, with no cryptographic binding to the body or to the HMAC that was computed over it: [2](#0-1) 

`Utils::HmacValidator.validate` confirms only that `HMAC(secret, raw_body) == received_signature` — it never incorporates `shop` or `topic` into the computation: [3](#0-2) 

`Webhooks::Registry.process` then uses this "validated" request to construct `WebhookMetadata`, forwarding the attacker-controllable `shop` value straight to the app's business logic as the trusted tenant identifier: [4](#0-3) 

The broken identity binding is:
`shop_used_by_handler (from header) == shop_that_the_HMAC_actually_authenticates (undefined, since shop isn't in the signed string)`

Any party who can obtain one validly-signed webhook body+HMAC pair for their *own* shop (which is trivial — any merchant that installs the app receives genuinely-signed webhooks for their own store) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. Because `shop-domain` is excluded from `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` invokes the app's handler believing the event legitimately belongs to the victim shop named in the header.

### Impact Explanation
This lets an attacker who controls any shop with the app installed forge webhook events "from" an arbitrary victim shop that the attacker does not control, with a validator that this gem's own API reports as verified (`HmacValidator.validate` returns `true`). Any app that relies on `WebhookMetadata#shop` (or `request.shop`) to select the tenant/session/access-token to act upon — the pattern the docs themselves recommend — is directly at risk of cross-tenant data corruption or disclosure, since the gem asserts authenticity of a field it never actually signs.

### Likelihood Explanation
Exploitation requires no special privilege beyond installing the target app on any shop (or otherwise obtaining one legitimately-signed webhook body/HMAC pair) and the ability to POST HTTP requests to the app's public webhook endpoint with custom headers — both are unprivileged-internet-user capabilities. No access token, `client_secret`, or leaked credential is needed.

### Recommendation
Bind `shop` (and `topic`) into the signed material that `HmacValidator` checks, e.g. by making `Webhooks::Request#to_signable_string` incorporate the `shop-domain` (and `topic`) header alongside the raw body, or by validating that these headers match values obtained via an independently-authenticated channel before dispatching to the handler. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B` with header `x-shopify-hmac-sha256: H` (a valid HMAC over `B` using the app's real `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equals `H` — validation succeeds because `shop-domain` was never part of the signed string: [5](#0-4) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never sent this event for that shop, and processes it under the victim's tenant context.
