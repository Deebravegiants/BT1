### Title
Flash-loan-manipulable Uniswap V4 spot price drains solver funds via disabled overfill clamp — ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
`FXFiller` prices curve-less, venue-priced legs directly from a Uniswap V4 pool's live `slot0` (spot) price with no TWAP, guarded only by an optional, coarse static-reference band. The per-leg loss bound that used to cap payout when the computed price diverged abnormally from the user's request has been explicitly disabled and downgraded to a warning, so a manipulated spot price now flows straight into the amount the solver actually pays out.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` derives the USD price of the exotic token directly from the live pool mid (`sdkPool.token0Price`/`token1Price`), which is built from `sqrtPriceX96` fetched via `getSlot0` on the `StateView` contract. [1](#0-0) [2](#0-1) 

This is the exact "slot0 as oracle" pattern the source report flags: `sqrtPriceX96`/`tick` are single-block AMM state, freely movable by a flash-loan swap within the same block as the attacker's order.

The FX filler's leg-pricing path (`resolveLegRates`) consumes this venue quote for any curve-less pair whose `token0` is a USD stable, and its only defense is `checkPriceGuard`, which compares the live quote against a *static* `referencePrice` within `maxDeviationBps` — not a TWAP, and entirely optional per pair/chain (a pair with no guard configured is priced unguarded). [3](#0-2) [4](#0-3) 

Even where a guard is configured, the band (e.g. ±2%) is checked against the manipulated price itself, so an attacker only needs to move the pool within that band to obtain a materially mispriced fill; unguarded chains have no bound at all.

Critically, `calculateProfitability` used to clamp payout when the policy-derived output exceeded `(1 + maxOverfillBps) × userRequested`, protecting against exactly this class of bug ("a bug / stale cache / manipulated venue price"). That clamp is now explicitly disabled — the code computes the `overfillCeiling` and, when breached, only logs a warning and pays the full unclamped `rawPolicyMaxOutput`: [5](#0-4) 

The unclamped `policyMaxOutput` then becomes `targetOutput`, which the filler funds first from its own wallet and then, for the shortfall, by withdrawing liquidity from its Uniswap V4 LP position via `planWithdrawalForToken` — i.e., the solver itself pulls the extra tokens out of the same manipulated pool to pay the attacker. [6](#0-5) 

### Impact Explanation
An attacker who flash-loan-manipulates the destination-chain Uniswap V4 pool used for venue pricing, then submits (or has relayed) a cross-chain/same-chain order on a curve-less venue-priced pair, forces the solver's `FXFiller` to size and pay out an inflated `policyMaxOutput`. Because the overfill clamp that previously bounded this loss is disabled, the solver pays the full inflated amount from its wallet and LP inventory — a direct, unbounded (up to the pool's manipulable depth and the solver's balance/LP liquidity) theft of solver funds. This is the same root cause and blast radius as the referenced USSD Rebalancer flash-loan report: an unprivileged actor manipulates an AMM spot price to force a public/automated pricing/settlement path into an unfavorable trade, draining funds.

### Likelihood Explanation
High for chains/pairs where no `referencePrice`/`maxDeviationBps` guard is configured (explicitly optional in config), and still exploitable within the configured band on guarded chains, since the guard only bounds deviation from a stale static reference rather than detecting intra-block manipulation. Any address can submit a qualifying order and combine it with a flash loan against the pool the solver reads — no privileged role is required, and the vulnerable code path (`resolveLegRates` → `computeLegPolicyOutput` → the disabled overfill clamp) executes automatically whenever `canFill`/`calculateProfitability` evaluates such an order.

### Recommendation
- Re-enable and enforce the overfill ceiling as a hard clamp (not warn-only) for venue-priced legs, or reject the fill outright when `rawPolicyMaxOutput` exceeds `(1 + maxOverfillBps) × userRequested`.
- Replace the raw `slot0`-derived spot price with a manipulation-resistant reference (e.g., a time-weighted average price over multiple blocks, or a Chainlink-style external oracle as already used elsewhere in the codebase for native/token pricing) for Uniswap V4 venue pricing.
- Make the `referencePrice`/`maxDeviationBps` price guard mandatory for any curve-less venue-priced pair rather than optional, and consider tightening/auto-updating the reference rather than relying on a static operator-set value.

### Proof of Concept
1. Attacker identifies a curve-less, venue-priced FX pair (e.g. `USDC/CNGN`) funded by a Uniswap V4 position with no `referencePrice` guard configured (allowed by config) — see `sdk/packages/simplex/filler-config-example.toml` guard being optional.
2. In one block, attacker flash-loans into the pool and swaps to move `slot0`'s `sqrtPriceX96` far in the direction that inflates `token1` (exotic) value.
3. Attacker submits an order on the intent gateway matching this pair with `input = USDC`, `output = CNGN` sized to the manipulated rate.
4. `FXFiller.calculateProfitability` → `resolveLegRates` reads the manipulated pool price via `UniswapV4FundingPlanner.getExoticTokenPrice`/`computeDirectPoolPriceUsd`, unguarded (or within a wide/complicit static band).
5. `computeLegPolicyOutput` computes an inflated `rawPolicyMaxOutput`; the overfill ceiling check at `fx.ts:684-701` logs a warning only and does not clamp.
6. The filler pays the inflated `targetOutput`, funding the shortfall via `venue.planWithdrawalForToken`, which withdraws Uniswap V4 LP liquidity — the solver's own funds (wallet + LP) are transferred to the attacker at the manipulated rate.
7. Attacker reverses the flash-loan swap and repays the loan, keeping the excess CNGN/USDC extracted from the solver.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
