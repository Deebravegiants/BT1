### Title
`estimateWithdrawalFee` reports `amount = 0` for prefunded native-fee tokens while a `storage_deposit` intent still drains `nativeFee` wrap.near from the user - ([File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts])

### Summary
When `assetId` is listed in `bridgeConfigs[OmniBridge].prefundedNativeFeeTokens`, `estimateWithdrawalFee` skips the fee-quote step and returns `feeEstimation.amount = 0n`, even though `fee.native_token_fee` (the relayer's native fee) can be greater than zero. That non-zero `nativeFee` is later fed into `deriveOmniWithdrawIntentParams`/`createWithdrawIntentsPrimitive`, which unconditionally emits a `storage_deposit` intent moving `nativeFee` units of wrap.near out of the user's intents balance, independent of the `amount` the fee-estimation call reported.

### Finding Description
The equality being tested is:
`feeEstimation.amount == total value leaving the user's balance beyond withdrawalParams.amount`

In `estimateWithdrawalFee` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:612-632), when `assetId` is in `prefundedNativeFeeTokens`, the branch that calls `getFeeQuote` and adds `quote.amount_in` to `amount` is skipped entirely:

```
if (
    totalAmountToQuote > 0n &&
    !this.bridgeConfig.prefundedNativeFeeTokens.includes(args.withdrawalParams.assetId)
) {
    quote = await getFeeQuote({...});
    amount += BigInt(quote.amount_in);
}
```

`amount` stays `0n` and is returned as `feeEstimation.amount`, while `underlyingFees.relayerFee = fee.native_token_fee` (a value that can be `> 0n`) is still embedded in `feeEstimation.underlyingFees[OmniBridge].relayerFee`.

Later, `deriveOmniWithdrawIntentParams` (omni-withdraw-params.ts:66-153) reads `nativeFee` straight from `underlyingFees.relayerFee`, and because `nativeFee > 0n`, it computes a non-null `storageDepositAccountId`. `createWithdrawIntentsPrimitive` (omni-bridge-utils.ts:56-63) then unconditionally pushes a `storage_deposit` intent with `amount: nativeFee.toString()` targeting `OMNI_BRIDGE_CONTRACT`. This intent debits `nativeFee` yoctoNEAR-equivalent wrap.near from the user's intents balance as part of the same batch of signed intents, regardless of what `feeEstimation.amount` displayed.

`validateWithdrawal` does not close this gap: its only relevant check is
```
if (!isFeeSubsidized && !isPrefundedWithdrawal) {
    assert(args.feeEstimation.amount > 0n, ...);
}
```
which explicitly *exempts* `isPrefundedWithdrawal` tokens from the "fee must be > 0" assertion — it does not assert that `feeEstimation.amount` accounts for `nativeFee`. There is no other guard anywhere in `omni-bridge.ts`, `omni-withdraw-params.ts`, or `omni-bridge-utils.ts` that reconciles `feeEstimation.amount` with the `nativeFee` actually placed into the `storage_deposit` intent.

I was not able to fully trace how `IntentsSDK.processWithdrawal` in `sdk.ts` uses `feeEstimation.amount` together with `feeInclusive` (the search for `feeInclusive` in `sdk.ts` returned no matches, meaning that flag/logic likely lives in a different file I could not locate within the remaining tool budget), so I cannot confirm with certainty whether the top-level SDK entrypoint additionally re-derives or double-checks the fee before signing. This is a genuine gap in my verification.

### Impact Explanation
If the divergence is real end-to-end, a user (or an integrator relying on `estimateWithdrawalFee`) is shown `feeEstimation.amount = 0`, i.e., "this withdrawal costs no NEAR fee," while the actual signed intent batch drains `nativeFee` wrap.near via the `storage_deposit` intent. This is a fee-display/accounting bug: the user is debited an amount they were not told about, which matches "a fee overcharge... beyond the displayed fee" (High, per the target severity categorization in the question). It is repeatable on every withdrawal of a prefunded-fee token whenever the Omni API returns `native_token_fee > 0`.

### Likelihood Explanation
Preconditions: the integrator must have configured `bridgeConfigs[OmniBridge].prefundedNativeFeeTokens` to include the asset being withdrawn, and the Omni Bridge fee API must return `native_token_fee > 0` for that token/route. Both of these are plausible operational states — `prefundedNativeFeeTokens` is documented as an integrator config the target explicitly calls out, and non-BTC/UTXO withdrawals normally require `relayerFee > 0` (enforced elsewhere in `validateWithdrawal` for the non-prefunded path). The attacker does not need special privileges beyond being a normal withdrawing user of an integrator that has this config enabled; the divergence triggers automatically on the intended usage path, not via any documented escape hatch abuse.

### Recommendation
In `estimateWithdrawalFee`, when `prefundedNativeFeeTokens` includes the asset, either:
1. Still add `fee.native_token_fee` (and `storageDepositFee`) to the returned `amount` even though the swap/quote step is skipped (since the value is prefunded but still leaves the user's wrap.near balance via `storage_deposit`), or
2. If "prefunded" truly means the native fee is paid from a source other than the user's balance, change `createWithdrawIntentsPrimitive`/`deriveOmniWithdrawIntentParams` so the `storage_deposit` intent's funding account is not the withdrawing user for these tokens.
Additionally, add an assertion in `validateWithdrawal` or `createWithdrawalIntents` that `feeEstimation.amount` plus any amount not already accounted for equals the sum of all value moved by the produced intents (including `storage_deposit.amount`), for every asset kind, not just wrap.near-denominated relayer fees.

### Proof of Concept
```ts
// vitest, mocking only omniBridgeAPI.getFee (HTTP boundary)
it("prefunded token: feeEstimation.amount is 0 while storage_deposit intent still moves nativeFee", async () => {
  const nativeFee = 1_000_000_000_000_000_000n; // > 0
  vi.spyOn(bridge["omniBridgeAPI"], "getFee").mockResolvedValue({
    native_token_fee: nativeFee,
    gas_fee: null,
    protocol_fee: null,
    min_amount: null,
    insufficient_utxo: false,
  });
  // storage deposit already sufficient so storageDepositFee = 0
  vi.spyOn(bridge as any, "getCachedStorageDepositValue").mockResolvedValue([0n, 0n]);

  const bridgeWithConfig = new OmniBridge({
    envConfig, nearProvider,
    bridgeConfig: { prefundedNativeFeeTokens: ["nep141:sol.omft.near"] },
  });

  const feeEstimation = await bridgeWithConfig.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:sol.omft.near", destinationAddress: "...", amount: 100n },
  });

  // Side A of the equality: displayed fee
  expect(feeEstimation.amount).toBe(0n);

  const intents = await bridgeWithConfig.createWithdrawalIntents({
    withdrawalParams: { assetId: "nep141:sol.omft.near", amount: 100n, destinationAddress: "...", routeConfig: undefined },
    feeEstimation,
  });

  const storageDepositIntent = intents.find((i) => i.intent === "storage_deposit");
  // Side B: actual value moved beyond `amount` (100n) via storage_deposit
  expect(storageDepositIntent).toBeDefined();
  expect(BigInt((storageDepositIntent as any).amount)).toBe(nativeFee);

  // The broken equality: feeEstimation.amount (0) !== actual value moved beyond amount (nativeFee)
  expect(feeEstimation.amount).not.toBe(nativeFee);
});
```
