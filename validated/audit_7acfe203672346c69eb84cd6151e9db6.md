### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from client-supplied HTTP headers and never included in the HMAC-signed payload. `Utils::HmacValidator.validate` verifies only that the body matches a valid HMAC for *some* payload signed with the app's secret; it never binds that signature to the specific `shop-domain` header attached to the request. This is the same bug class as the reported `_formatProof` issue: a value that is later trusted and acted on (`shop`, `topic`, `webhook_id`) is not covered by the cryptographic check (HMAC) that is meant to authenticate the whole message.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def to_signable_string
  @raw_body
end
``` [5](#0-4) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers with no cryptographic tie to the signature:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

`HmacValidator.validate` only ever hashes `to_signable_string` (the body):
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` uses this unauthenticated `shop`/`topic`/`webhook_id` to dispatch to the handler as trusted tenant identity:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

This breaks the intended binding `HMAC(secret, body) == HMAC(secret, body) → shop-domain header is authentic`. In reality the equality only proves the *body* was signed by Shopify for *some* webhook delivery — it says nothing about which shop, topic, or webhook id it was issued for.

An unprivileged attacker who legitimately installs the app on their own store (a normal, unprivileged tenant relationship, not requiring `api_secret_key`) receives real webhook deliveries from Shopify with valid HMACs computed over the JSON body. Because the signature never covers the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers, the attacker can replay the exact same body + HMAC to the app's webhook endpoint while substituting a different victim shop's domain in the `shop-domain` header (and/or a different `topic`/`webhook-id`). `HmacValidator.validate` still returns `true` because the body/HMAC pair is untouched and genuinely valid, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the forged `shop`, causing the host application to attribute/act on data for the wrong tenant.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app that stores or updates per-tenant state keyed off `WebhookMetadata#shop` (e.g., updating order/inventory records, marking a shop's data synced, revoking access, or writing audit logs per tenant) can be made to apply attacker-controlled body content to a victim shop's records, or vice versa mislabel data as belonging to the attacker's own shop. Combined with the unauthenticated `topic` field, an attacker can also invoke a *different* handler than the one Shopify actually intended for that payload (e.g., replay a benign webhook body under a sensitive topic name), since the topic used for handler dispatch is also outside the HMAC.

### Likelihood Explanation
Any merchant/developer who installs the app on their own store obtains genuine `(body, HMAC)` pairs signed by the real `api_secret_key` for their normal webhook traffic, without ever needing to see or extract the secret itself. Replaying that valid pair with modified headers against the app's public webhook endpoint requires no privileged access — only the ability to send an HTTP request, which is exactly the class of unprivileged-internet-user attack this analog targets.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically/contextually bind them to the body (e.g., require the app to independently confirm the `shop` against a known/installed shop list before trusting `WebhookMetadata#shop`, and never rely solely on `Request#shop`/`Request#topic` for tenant or handler dispatch decisions once the HMAC has been checked). At minimum, document prominently that `HmacValidator.validate` only authenticates the raw body and does not authenticate any header, so host applications do not implicitly assume header authenticity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/updated`, with body `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac>` (computed by Shopify over `raw_body` using the app's real secret).
2. Attacker sends a new HTTP POST to the app's webhook endpoint reusing the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - (optionally) a different `X-Shopify-Webhook-Id`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully since required headers are present [7](#0-6) .
4. `Utils::HmacValidator.validate(request)` returns `true`, because `to_signable_string` returns the unmodified `raw_body`, whose HMAC still matches [8](#0-7) .
5. `Registry.process(request)` dispatches to the registered handler for `topic` with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never issued this webhook for that shop [4](#0-3) .

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
