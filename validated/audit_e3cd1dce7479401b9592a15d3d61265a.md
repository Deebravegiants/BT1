No vulnerability found for this question.

**Reasoning:**

The concern misunderstands how Aptos executes transactions within a block. `deny` and `set_position` calls both read/write the same `ExchangeRegistry` resource at `@aptos_experimental`: `deny` mutates `registry.denied` [1](#0-0) , and every `set_position`/`delete_position` call re-validates the capability via `trading_native_capability::assert_valid`, which reads that same `denied` map through `assert_active` before the native write is staged [2](#0-1) [3](#0-2) .

Because both operations read/write the identical Move global resource, Aptos's Block-STM optimistic concurrency control tracks this as a standard read/write dependency. Block-STM's correctness guarantee is that the final committed outputs of a block are always equivalent to a serial execution in the block's fixed commit order — never to arbitrary wall-clock interleaving. If `set_position` speculatively executes and reads the registry before `deny`'s write is visible, but `deny` is ordered earlier in the block, validation detects the conflict and forces re-execution of `set_position` after `deny`'s effects are applied, causing it to abort with `EEXCHANGE_DENIED`. If `set_position` is ordered before `deny` in the block, its success is the correct, intended outcome — `deny` only takes effect for transactions ordered after it, exactly as sequential ledger semantics dictate. There is no "in-flight but uncommitted" state that can slip through: the native write itself is staged only inside that transaction's own VM session and materializes into the change set atomically with the rest of that transaction's effects [4](#0-3) [5](#0-4) .

Additionally, this scenario requires the caller to already hold a valid `TradingNativeCapability`, which can only be minted for an address governance has already `register`ed [6](#0-5) . That is not an unprivileged entrypoint under the review's bounds — it presupposes governance-granted exchange status, and the block-ordering decision itself is controlled by consensus/proposer logic, not by the unprivileged caller.

No custody boundary is crossed: the outcome is fully deterministic per block order, and `assert_valid`'s re-check on every write is precisely the mechanism designed to close any such gap.

fn native_set_position(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    check_feature_enabled(context)?;
    let position_val = args.pop_back().ok_or_else(|| missing_arg("position"))?;
    let account: AccountAddress = safely_pop_arg!(args, AccountAddress);
    let market: AccountAddress = safely_pop_arg!(args, AccountAddress);
    let exchange: AccountAddress = safely_pop_arg!(args, AccountAddress);
    let native_pos = move_value_to_position(position_val)?;
    let ctx = context.extensions().get::<NativePositionContext>();
    let key = TradingNativeKey::Position {
        exchange,
        account,
        market,
    };
    ctx.stage_set(key, native_pos);
    Ok(smallvec![])
}
