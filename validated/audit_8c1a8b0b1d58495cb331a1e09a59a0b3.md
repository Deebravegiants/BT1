### Title
Oversized scaled balances can overflow interest accrual and permanently freeze a market - (File: common/src/rates/simulate.rs)

### Summary
A sufficiently large borrow market can reach a state where `borrowed * borrow_index` no longer fits in `i128`, causing every subsequent accrual to revert with `MathOverflow` before the configured borrow-index ceiling is reached. [1](#0-0) [2](#0-1) 

### Finding Description
An unprivileged user can create the preconditions through `Controller::supply` and `Controller::borrow`, then anyone can trigger the state transition through `Controller::update_indexes(caller, assets)`. [3](#0-2) [4](#0-3) 

The controller forwards index updates to the pool, whose `ops::market::accrue` loads each market and calls `interest::global_sync`. [5](#0-4) [6](#0-5) 

All normal pool mutations use `synced_market`, which performs `global_sync` before the requested operation. [7](#0-6) 

Inside `accrue_step`, utilization starts by multiplying the stored scaled debt and scaled supply by their current indexes via `scaled_to_original`; that helper delegates directly to checked `Ray::mul`. [1](#0-0) [8](#0-7) 

The index ceiling does not prevent this failure because `update_borrow_index` multiplies before clamping, while `update_supply_index` similarly multiplies aggregate shares by the old index before clamping the result. [9](#0-8) [10](#0-9) 

The repository’s own stress test demonstrates a one-billion-token, 18-decimal market at 98% utilization reaching this cliff, with the committed borrow index still below `MAX_BORROW_INDEX_RAY`. [11](#0-10) [12](#0-11) 

### Impact Explanation
Once the aggregate debt or supply value crosses the `i128` representable bound, `update_indexes` cannot commit a new `last_timestamp`, so every later call retries the same overflowing accrual. [13](#0-12) 

Because supply, borrow, withdraw, repay, liquidation-related pool mutations, recapitalization, and revenue claims all synchronize the market first, the affected market can become permanently unusable rather than merely rejecting one oversized input. [14](#0-13) [15](#0-14) 

The regression test explicitly confirms that a subsequent withdrawal and repayment both fail with `MathOverflow`, freezing supplier assets, borrower repayment, liquidation cleanup, and unclaimed revenue in that market. [16](#0-15) 

### Likelihood Explanation
The attack requires an unusually large token position, a high-utilization borrow market, a steep validated rate curve, and enough elapsed time for the index to grow; it is therefore not triggerable from an ordinary-sized account in one transaction. [17](#0-16) 

However, cap validation permits values up to `max_cap_for_decimals`, and the stress scenario uses amounts below that admitted asset-domain maximum rather than an invalid parameter or privileged runtime state. [18](#0-17) [19](#0-18) 

After a market is configured with sufficiently large caps, a single funded user can supply the liquidity and collateral and borrow the target asset through ordinary caller-authorized controller entrypoints. [20](#0-19) 

This is best classified as Medium: permanent freezing of market funds is high-impact, but the capital requirement, market configuration, utilization, and accrual window are substantial preconditions. [2](#0-1) 

### Recommendation
Enforce a maximum scaled balance that remains representable at the highest permitted index, or explicitly bound `scaled <= floor(i128::MAX * RAY / index)` before admitting new supply or debt. [21](#0-20) 

At minimum, accrual should clamp or otherwise handle an index-bound crossing before evaluating aggregate `scaled * index`, and repay/withdraw/liquidation paths need a recovery mode that can operate using a saturated or safely widened aggregate value. [22](#0-21) 

### Proof of Concept
The repository already contains an executable reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. [23](#0-22) 

```rust
// 18-decimal debt market: 175% max APR, 75% optimal utilization.

let debt = principal / 100 * 98;

controller.supply(borrower, 0, spoke_id, vec![(COL, sufficient_collateral)]);
```

The test sets up those positions and repeatedly advances one year until `try_update_indexes_for(&["BIG18"])` returns `MathOverflow`. [24](#0-23) 

It then verifies the stored index is still below `MAX_BORROW_INDEX_RAY` and that both withdrawal and repayment hit the same overflow. [25](#0-24)

```rust
        .with_market(col())
        .with_max_utilization_disabled_all_markets()

    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let failure = loop {

        assert!(
            years <= 40,
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
