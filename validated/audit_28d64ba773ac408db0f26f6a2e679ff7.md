### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers. `Registry.process` validates the HMAC over the body alone and then forwards the unauthenticated `shop` header value to the app's `WebhookHandler` as `WebhookMetadata#shop`. Any actor able to obtain one valid `(body, hmac)` pair for the app's registered client_secret (e.g., a legitimate merchant capturing their own webhook, or replaying a webhook whose body content they control/predict) can resend it with a forged `shop-domain` header. Since the equality that should hold — "the shop the HMAC-authenticated body was generated for == the shop `Registry.process` reports to the handler" — is never checked, the handler acts on an attacker-chosen shop identity while still passing HMAC validation.

### Finding Description
`Registry.process` performs a single check, `Utils::HmacValidator.validate(request)`, which only proves that `request.to_signable_string` (i.e., the raw body) was signed with the app's `api_secret_key`/`old_api_secret_key`. It does not bind that signature to `request.shop`, `request.topic`, or `request.webhook_id`, all of which come straight from attacker-controllable HTTP headers [2](#0-1) . The resulting `WebhookMetadata` (including `shop`) is then handed to the host app's handler as trusted data [3](#0-2) . This mirrors the referenced report's bug class of "acting on a field that is not covered by the authentication mechanism" — here the `shop` identity is disjoint from what is cryptographically bound.

Since Shopify sends the same `client_secret`-derived HMAC to every shop's webhook endpoint for a given app (the secret is shared across all installs of the app, not per-shop), any merchant who has installed the app can obtain a legitimately-signed `(body, hmac)` pair by triggering a webhook on their own store (e.g. `orders/create` with a body they control), then replay that exact request to the app's shared webhook endpoint with the `shop-domain` header changed to a victim shop. `HmacValidator.validate` still succeeds because the signature never depended on the shop header, so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain [5](#0-4) .

### Impact Explanation
This is a cross-tenant identity binding break: the app's webhook handler is documented to key merchant-record lookups and actions directly off `data.shop` [4](#0-3) . An attacker (a regular, unprivileged merchant using the app — no special access needed) can cause the handler to execute logic (e.g., data updates, redaction, uninstall cleanup) against a *victim* shop's record instead of their own, since the `shop` value the gem hands to the handler is not authenticated. This satisfies the Critical bar of cross-tenant access via a binding the gem itself is responsible for establishing.

### Likelihood Explanation
Likelihood is high for any app that registers more than one webhook topic and lets multiple merchants install it (the normal multi-tenant SaaS model this gem is built for). No secrets, tokens, or privileged access are required — only the ability to trigger any webhook on the attacker's own, legitimately-installed shop and then re-POST the captured request to the app's public webhook endpoint with a different `shop-domain` header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or minimally `shop`) as part of the signed material `HmacValidator` verifies for webhooks, or otherwise cryptographically bind the header-derived `shop` to the payload before constructing `WebhookMetadata`. At minimum, `Registry.process` should not trust `request.shop` unless it is provably tied to the same request the HMAC was computed over — e.g. Shopify's own recommended verification incorporates the full raw request, but the value it derives its authorization decision from (which shop to act on) must never come from a header that is outside the HMAC's coverage.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker registers/receives a webhook (e.g. `orders/create`) and captures the legitimate raw HTTP POST Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw body.
3. Attacker replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates `request.to_signable_string` (the unchanged raw body) [6](#0-5) .
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop = "victim.myshopify.com"` and invokes the app's handler, which now acts on the victim's data using the attacker-controlled body [5](#0-4) .
