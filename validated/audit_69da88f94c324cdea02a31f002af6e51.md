Audit Report

## Title
CORS wildcard-origin bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` validates the `Origin` header against `CORSAllowedOrigins` entries, and for wildcard entries (`*.example.com`) strips the `*.` prefix and performs a plain `strings.HasSuffix(originHost, allowedHost)` check with no dot-boundary enforcement. This lets an attacker-controlled domain that merely ends with the same literal substring (e.g. `evilremix.com` against an allowlisted `*.remix.com`) pass the origin check and receive a reflected `Access-Control-Allow-Origin` header, permitting cross-origin reads of gateway HTTP responses.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , the wildcard match strips the `*.` prefix from the allowed host and then calls `strings.HasSuffix(originHost, allowedHost)` without requiring a `.` immediately before the matched suffix or an exact match. Because `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, an operator-configured entry `https://*.remix.com` in `CORSAllowedOrigins` would also match `https://evilremix.com`. This directly parallels the label-boundary confusion pattern referenced from CVE-2014-3613 (unanchored suffix comparison instead of boundary-aware matching).

This check gates `handleRequest` [2](#0-1) , which reflects the incoming `Origin` header into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true, and then forwards the raw request body to `s.handler.ProcessRequest`, writing `rawResponse` back to the client [3](#0-2) . There is no other origin-boundary check, allowlist normalization, or exact-match enforcement elsewhere in the file that would catch this.

The existing test suite exercises only the intended-positive cases (`ethereum.org` vs `*.ethereum.org`) and intended-negative cases that differ by scheme/port/full-mismatch (e.g. `ethereum.remix.org` vs `*.ethereum.org`) [4](#0-3) , but none of the tests cover the boundary-confusion case of a domain that merely shares the suffix without a preceding dot (e.g. `evilremix.com` vs `*.remix.com` or `notethereum.org` vs `*.ethereum.org`), so this gap is not caught by CI.

## Impact Explanation
When `CORSEnabled=true` and a wildcard entry is present in `CORSAllowedOrigins`, an attacker who controls (or merely serves content from) any domain literally ending in the configured suffix can have their site's JavaScript issue cross-origin requests to the gateway and read the JSON-RPC responses via the reflected `Access-Control-Allow-Origin` header. This is a cross-user response exposure / CORS allowlist bypass on the gateway's internet-facing HTTP endpoint, falling under the "allowlist bypass" / "cross-user response corruption" impact categories relevant to the gateway.

## Likelihood Explanation
Exploitation requires only (1) the gateway operator enabling `CORSEnabled=true` with a wildcard entry in `CORSAllowedOrigins` — a supported, documented configuration pattern (see `sample_config.toml`/`sample_config_tls.toml`) — and (2) an attacker registering or controlling any domain ending with the same literal suffix string, which is a trivial low-cost step (e.g. registering `evilremix.com` to bypass `*.remix.com`). No node compromise, peer compromise, or credentials are needed; the entire attack is client-side, from an unprivileged browser context, matching the required "unprivileged actor" bar. This is a real, reachable configuration-dependent bug in the code path itself (not merely an operator misconfiguration; the flaw is in the comparison logic given any wildcard entry).

## Recommendation
Anchor the wildcard suffix match to a label boundary:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This ensures `evilremix.com` no longer matches `*.remix.com` while legitimate subdomains like `sub.remix.com` continue to match. Add regression tests covering suffix-confusion cases (e.g., `notremix.com`/`evilremix.com` against `*.remix.com`).

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled=true` and `CORSAllowedOrigins=["https://*.remix.com"]` (mirrors `startNewServer` helper in `core/services/gateway/network/httpserver_test.go`).
2. Send a POST request to the server's configured path with header `Origin: https://evilremix.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming that `isAllowedOrigin` returned `true` for a host that shares only a literal suffix with, but is not a subdomain of, the allowlisted `remix.com`.
4. This can be codified as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, asserting that `Access-Control-Allow-Origin` is empty for origin `https://evilremix.com` against allowed `https://*.remix.com` — the current implementation would fail this assertion.
