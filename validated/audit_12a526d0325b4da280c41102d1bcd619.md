### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that are subsequently trusted and handed to the app's handler are read straight from unauthenticated HTTP headers that are never included in the HMAC-signed content. This breaks the identity binding `shop_claimed_in_header == shop_that_the_signed_body_actually_belongs_to`, allowing a party who possesses one validly-signed `(raw_body, hmac)` pair (e.g., from their own legitimately installed shop) to replay it against the same app's webhook endpoint while swapping the `shop-domain` header to impersonate a different merchant/tenant.

### Finding Description
The webhook verification flow is:

```
Registry.process(request) -> HmacValidator.validate(request) -> handler.handle(WebhookMetadata.new(shop: request.shop, ...))
```

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns just the raw body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

None of `shop`, `topic`, `webhook_id`, or `api_version` — all read directly from HTTP headers — are part of the signed string: [2](#0-1) 

The signature check itself only compares the computed HMAC of the body against the received one: [3](#0-2) 

Yet `Registry.process` trusts `request.shop` (taken from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler, which apps use to select/act on the correct tenant's data: [4](#0-3) 

Because the API secret used for HMAC computation is per-app (shared across every shop that installs the app) rather than per-shop, any party that has installed the app on their own store can capture one legitimately Shopify-signed `(raw_body, hmac-sha256)` pair from a webhook delivered to them, then re-POST that exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The gem's verification logic has no way to detect this: the HMAC still matches (it only ever covered the body), so `Registry.process` proceeds and dispatches the payload to the handler tagged as belonging to the victim shop.

This is precisely the class of bug described in the reference report: a value that is acted upon (here, the tenant-identifying `shop` field used to route/attribute the webhook) is not covered by the integrity check (here, the HMAC), letting an attacker forge the binding between signed content and claimed identity.

### Impact Explanation
This allows cross-tenant impersonation: an attacker-controlled shop installation can cause the app to process webhook events "as if" they originated from an arbitrary other shop that has installed the same app, using data/body the attacker fully controls (their own legitimately-signed payload) but attributed to a victim's `shop` value. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the victim's session/access token and perform actions, or to write data into the victim's tenant records), this can lead to cross-tenant data corruption, privilege confusion, or the app taking actions against the victim's store using the app's own credentials — a cross-tenant access issue.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop (a normal, unprivileged action for public/dev store apps) to obtain one valid `(body, hmac)` pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is by design internet-reachable). No access token, `api_secret_key`, or other privileged credential is needed — only a header swap on a replayed, already-valid request. This does not depend on the host app doing anything unusual; the gem's own `Request`/`HmacValidator`/`Registry.process` implementation is what fails to bind `shop` to the signature.

### Recommendation
Include the identity-relevant header values (`shop`, and ideally `topic`/`webhook_id`) in the signable string used for HMAC validation, or otherwise cryptographically bind the claimed `shop` to the signed body (e.g., verify that the `shop` header matches an expected/registered shop for that webhook subscription before invoking the handler). At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be trusted by host applications without additional verification (e.g., cross-checking against a known/stored shop for that webhook registration).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this pair is captured by the attacker (e.g., via a proxy on infrastructure they control, since it's addressed to their own endpoint/app instance if self-hosted, or via any means of observing their own webhook traffic).
3. Attacker crafts a new HTTP POST to the same app webhook endpoint with:
   - Body: identical `B`
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs the body)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic`, `x-shopify-webhook-id` as needed
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
