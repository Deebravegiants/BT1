### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`/`api_version`) values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed payload. This breaks the identity binding `shop-that-produced-(body,hmac) == shop-attributed-to-the-processed-event`, allowing any user who can obtain one valid `(body, hmac)` pair from the app (e.g., by legitimately triggering a webhook from their own store) to replay it with a forged `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled webhook data under another shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers, which are entirely outside the signed content: [2](#0-1) 

`HmacValidator.validate` only ever verifies `to_signable_string` (the body) against the `hmac` value, so it has no knowledge of, and provides no integrity guarantee for, the `shop-domain` header: [3](#0-2) 

`Registry.process` performs exactly this check and then immediately forwards `request.shop` (the unauthenticated header) to the application's webhook handler as the tenant identifier: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that has installed the app, any tenant of the app can generate a genuine `(raw_body, hmac)` pair by triggering a real webhook event in their own store. That same body/hmac pair remains valid regardless of which `shop-domain` header accompanies it, since the header is never part of the signed string. An attacker can therefore submit that valid pair to the app's public webhook endpoint with the `shop-domain` header swapped to a victim shop, and `Registry.process` will accept it as authentic and hand the attacker's body content to the handler tagged as belonging to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for inbound webhooks: an unprivileged installer of the app (attacker who can install/use the app on their own store, no special privileges needed) can make the app act on forged data while it believes the data originated from another merchant's shop. Depending on the handler logic (e.g., mandatory GDPR webhooks like `customers/redact`, `shop/redact`, or app-specific business webhooks), this can result in cross-tenant data corruption/spoofing — the gem provides no defense against it because the identity field it hands to handlers is unauthenticated. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: exploitation requires only (1) the ability to install/use the target app on an attacker-controlled shop (a normal, unprivileged capability for any Shopify merchant/dev store), and (2) capturing one legitimate webhook `(raw_body, hmac)` pair, which is routine and easy to obtain (e.g., by triggering `orders/create` on the attacker's own shop). No access token, `api_secret_key`, or privileged credential is required — the app's webhook endpoint is a public HTTP endpoint by design.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` value to the verified body before it is trusted (e.g., require the handler/registry to cross-check `request.shop` against a shop that is known to be installed and expected to emit that specific webhook body/topic, or require Shopify's newer signed payload formats that include shop context). At minimum, document prominently that `request.shop` is unauthenticated and must be independently verified by host applications against their own session/install store before being used to select tenant-scoped data or credentials.

### Proof of Concept
1. Install/use the target app on attacker's own shop `attacker.myshopify.com`; trigger any registered webhook topic (e.g. `orders/create`) to receive a real webhook POST with headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and body `raw_body`.
2. Resend the same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `raw_body` only (per `Request#to_signable_string`) and it matches, so validation succeeds: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` and the attacker-controlled body, even though the event never originated from the victim shop.
