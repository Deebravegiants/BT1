### Title
Webhook shop identity is trusted from an unauthenticated header while HMAC only covers the body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC computation only signs the raw request body. The `shop` value that identifies which merchant/tenant the webhook belongs to is read straight from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. This breaks the binding `HMAC-verified bytes == identity used for dispatch`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers but excluded from the HMAC signable string. `HmacValidator.validate` then computes and compares the HMAC over `to_signable_string` (the body only): [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request came from Shopify, and forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` used by the app's handler: [3](#0-2) 

The gem's own docs instruct app authors to trust `data.shop` as "The shop domain of the webhook" and use it directly for tenant-scoped work (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [4](#0-3) [5](#0-4) 

Because the app's `api_secret_key` is shared across all of the app's installations (it is not per-merchant), an unprivileged internet user who legitimately receives one authentic webhook body+HMAC pair for their own store (e.g. by installing the target app on their own test shop and triggering `orders/create`) can replay that exact `raw_body`/`X-Shopify-Hmac-Sha256` pair directly to the app's public webhook endpoint URL while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the payload to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity confusion: the library asserts to the host application ("this request did indeed come from Shopify" and "here is the verified shop for this webhook") without actually binding the shop identity to the cryptographic proof. Any host app that keys per-tenant records off `WebhookMetadata#shop` (exactly as the gem's own documentation recommends) can have webhook data attributed to, or acted upon for, a shop the attacker does not own — enabling cross-tenant data injection/corruption using only a body the attacker legitimately received for their own store.

### Likelihood Explanation
Requires only: (1) the ability to install/trigger a webhook on any shop connected to the target app (trivial for a public app, since anyone can install it on their own dev store) to obtain one valid `raw_body` + `X-Shopify-Hmac-Sha256` pair, and (2) direct HTTP access to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim shop's credentials is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signable bytes, or otherwise cryptographically bind the shop identity to the signed payload before trusting it in `WebhookMetadata`. At minimum, document that `X-Shopify-Shop-Domain` is not integrity-protected by `HmacValidator` and must be independently verified (e.g., cross-checked against a stored session/shop registered for that webhook subscription) before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers `orders/create`.
2. Attacker's server captures the legitimate delivery: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`.
3. Attacker POSTs the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the same app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the spoofed header; `HmacValidator.validate` succeeds because `to_signable_string` is `raw_body` only, unaffected by the header change:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,      # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
})
ShopifyAPI::Webhooks::Registry.process(request) # passes HMAC check, dispatches with shop = "victim-shop.myshopify.com"
```
5. The app's handler receives `data.shop == "victim-shop.myshopify.com"` with attacker-controlled body content, even though nothing in the request was verified as originating from or about that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
