## Title
Webhook shop/topic identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the host application's handler come from HTTP headers that are **not** included in the signed material. This breaks the identity binding `hmac(raw_body) == valid ⟹ shop header is trustworthy`, allowing any party who can obtain one validly-signed webhook body (e.g. a merchant who has installed the app on their own store) to relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `HmacValidator.validate` call proves only that the raw body bytes were signed with the app's secret key at some point — it says nothing about which shop or topic that signature was originally associated with: [4](#0-3) 

Because a single `api_secret_key` is shared across *all* shops that install a given app, any shop that legitimately receives a webhook obtains a body+HMAC pair that is valid for that app irrespective of shop. That merchant (an unprivileged party relative to other tenants of the same app) can capture the exact bytes of a real, validly-signed webhook delivered to their own endpoint and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header changed to point at a different, victim shop. `Registry.process` will still accept it, since `Utils::HmacValidator.validate(request)` only re-computes the signature over `@raw_body`, which is unchanged.

The bug-class parallel to the external report is direct: just as the withdrawal-queue checkpoint failed to bind claim eligibility to the specific request that earned it, here the "claim" of being from a specific shop is never bound to the credential (HMAC) that is supposed to authenticate the whole request.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism exists to enforce. A host application built on this gem typically uses `WebhookMetadata#shop` to scope data writes/reads (e.g., "find session/store data for this shop, then apply body"). An attacker-controlled shop can forge the shop identity on a request the app will treat as authentic Shopify traffic, enabling cross-tenant data injection or corruption under another merchant's identity — this maps to the "Critical - cross-tenant access" category in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate but unprivileged installer of the target app on their own shop (no special permissions, no access to `api_secret_key`, no TLS interception) — they simply need to intercept/replay their own genuine webhook delivery with a modified header, something fully under their control since it's their own HTTP endpoint receiving Shopify's POST. This is a realistic, low-effort attack path.

### Recommendation
Bind the shop (and ideally topic) identity into the material that is verified. At minimum, incorporate `shop-domain` and `topic` header values into the HMAC-signable string, or independently verify that `request.shop` matches an app-known/expected shop for the delivery before dispatching to the handler, rather than trusting the header verbatim once only the body's signature has been checked.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any webhook subscribed by the app (e.g., `orders/create`), causing Shopify to POST `{raw_body, X-Shopify-Hmac-Sha256: valid_for(raw_body), X-Shopify-Shop-Domain: attacker-shop.myshopify.com, X-Shopify-Topic: orders/create}` to the app's endpoint.
2. Attacker intercepts/records this exact HTTP request (they control their own endpoint infrastructure/proxy).
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — passes, since body is unchanged.
5. Handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: attacker_controlled_json, ...)` and processes it as authentic data for `victim-shop.myshopify.com`.
