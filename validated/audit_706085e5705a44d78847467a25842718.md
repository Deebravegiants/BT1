Confirmed: `process_initialize2` performs no whitelist check on `amm_coin_mint_info`/`amm_pc_mint_info` beyond `coin_mint != pc_mint` [1](#0-0) , and only requires SPL Token Program ownership [2](#0-1) . Any attacker can permissionlessly create a pool with a fee-on-transfer mint pair, then swap against it.

In `process_swap_base_out` (and its v2 sibling), the output amount is computed from vault balances *before* the input transfer occurs, then the input is pulled via `Invokers::token_transfer` and the output pushed via `Invokers::token_transfer_with_authority` using the *nominal* `swap_in_after_add_fee` / `swap.amount_out`, with no post-transfer balance verification:### Title
Fee-on-transfer / rebasing token pool draining via nominal-amount accounting in swap/deposit/init - ([File: program/src/processor.rs])

### Summary
`process_initialize2` allows creation of an AMM pool for any arbitrary SPL mint pair with no whitelist or token-behavior check beyond `coin_mint != pc_mint` and token-program ownership [1](#0-0) [2](#0-1) . All swap and deposit paths compute amounts to transfer/mint based on the *nominal* instruction amount, not the actual token balance delta the vault receives, and never verify post-transfer vault balances against the amount assumed.

### Finding Description
In `process_swap_base_out` (and identically in `process_swap_base_out_v2`), the protocol:
1. Reads pool reserves directly from `amm_coin_vault.amount` / `amm_pc_vault.amount` before any transfer [3](#0-2) .
2. Computes `swap_in_after_add_fee` from the AMM invariant using the *requested* `amount_out` [4](#0-3) .
3. Transfers `swap_in_after_add_fee` from the user to the vault, then unconditionally transfers the full computed `swap.amount_out` from the vault to the user — with no check of what the vault actually received or what the user actually received [5](#0-4) .

If either the input mint (coin or pc) is a fee-on-transfer / transfer-hook-deducting token, the vault's real balance increases by less than `swap_in_after_add_fee` while the program still pays out the full nominal `swap.amount_out` computed under the assumption that the full input amount landed in the vault. The same nominal-vs-actual mismatch exists in `process_swap_base_in`/`_v2` (transfers `swap.amount_in` in, pays computed `swap_amount_out` out, using pre-transfer reserves) [6](#0-5) , in `process_deposit` (transfers `deduct_coin_amount`/`deduct_pc_amount` in and mints LP based on nominal deducted amounts, not actual vault deltas) [7](#0-6) , and in `process_initialize2` (mints initial LP as `sqrt(pc_vault.amount * coin_vault.amount)` measured *after* the deposit transfer, so a fee-on-transfer mint here would just reduce the *pool's own* initial liquidity accounting consistently — this specific path is self-correcting because it re-reads balances after transfer, unlike the swap and deposit paths which fix the output/mint amount before or independent of the real transferred amount).

Unlike the referenced BvbProtocol issue (which tracks a separate `withdrawableFees` ledger that desyncs from real balances), Raydium always re-reads live vault balances (`unpack_token_account(...).amount`) on the next instruction, so cross-transaction desync of "tracked fees" doesn't apply here. However, the *intra-transaction* mismatch between the nominal swap-in amount and the amount actually credited to the vault is a genuine analog of the same root cause (assuming nominal transfer amount equals actual received amount for fee-on-transfer tokens) and directly enables value extraction: an attacker can create a pool with a fee-on-transfer coin/pc mint (permitted, since there is no whitelist), then repeatedly swap in that fee-on-transfer token while pulling out the non-fee token, draining the counter-asset because each swap pays out based on reserves that were never actually topped up by the full nominal input.

### Impact Explanation
Because the payout side (`token_transfer_with_authority`) always sends the full computed `amount_out`/`swap_amount_out`, and the vault-in side only receives `amount_in - transfer_fee`, each swap round-trip permanently drains real value from the pool (the counter-asset) into the attacker, at the expense of remaining LPs. This is a permanent, unbacked loss of pooled funds reachable by any unprivileged user through the ordinary `SwapBaseIn`/`SwapBaseOut` instructions against a pool they create themselves via `Initialize2`.

### Likelihood Explanation
Likelihood requires the attacker to control (or select) a fee-on-transfer/transfer-hook mint for one side of a newly created pool, which `process_initialize2` permits with no restriction on mint type beyond basic SPL Mint unpacking [8](#0-7) . Since Solana Token-2022 transfer-fee/transfer-hook extensions are common and pool creation is fully permissionless and unprivileged, this is straightforward to set up and repeat at low cost (only limited by swap fee spread economics), though it primarily harms LPs of a pool the attacker themselves seeded — impact on *other* pre-existing pools requires the admin/deployer to later reconfigure an already-whitelisted mint to add a fee extension, which is a lower-likelihood but still valid scenario matching the original report's framing.

### Recommendation
Verify actual token deltas rather than trusting nominal instruction amounts: capture vault/user token balances before and after each CPI `token_transfer` in `process_swap_base_in(_v2)`, `process_swap_base_out(_v2)`, `process_deposit`, and `process_initialize2`, and use the measured delta (not the requested amount) for AMM invariant updates, LP minting, and payout sizing. Alternatively, explicitly reject Token-2022 mints with transfer-fee or transfer-hook extensions at pool-creation time and validate this invariant continues to hold before every swap/deposit.

### Proof of Concept
1. Attacker creates mint `M` (Token-2022) with a transfer-fee extension (e.g., 5% fee on transfer) and mint `N` (standard SPL token).
2. Attacker calls `Initialize2` to create a pool with `coin_mint = M`, `pc_mint = N`, seeding e.g. 1,000,000 `M` and 1,000,000 `N` — no check in `process_initialize2` prevents this [9](#0-8) .
3. Attacker calls `SwapBaseIn` with `user_source` = `M`, sending `amount_in` = 100,000 `M`. The vault actually receives only 95,000 `M` (5% fee), but `swap_amount_out` is computed from `total_coin_without_take_pnl` that assumed the vault would hold the full nominal reserve going forward, and the program pays out the full computed `N` amount via `token_transfer_with_authority` [10](#0-9) .
4. Repeating the swap in both directions lets the attacker extract more `N` (and `M`) than the AMM invariant should allow, since the "in" leg is systematically under-credited relative to what the "out" leg pays, draining the pool's real backing over successive swaps.
