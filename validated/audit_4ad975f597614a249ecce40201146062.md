### Title
CEI Violation in `withdraw()` of Tron `IntentGatewayV2` — External Transfer Before Escrow Debit - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` implements escrow release in `withdraw()` with the exact same checks-effects-interactions ordering flaw described in the external report: the external transfer (native `.call{value:}` or ERC20 `.call(transfer)`) is executed **before** the corresponding escrow accounting (`_orders[body.commitment][token] -= amount;`) is decremented, and the function carries **no reentrancy guard**. This is the same bug class as the reported `CreditUSDMinter.mint()` issue (external interaction before state effect), reachable through the intents escrow/relayer-delivery path rather than a mint call.

### Finding Description
`withdraw()` is the internal settlement routine invoked from `cancelOrder` (same-chain path) and from `onAccept`/`onGetResponse` (cross-chain settlement, `RedeemEscrow`/`RefundEscrow`, driven by relayer-delivered ISMP messages) [1](#0-0) [2](#0-1) .

Inside the loop, for every escrowed token it performs the external call first and only afterward mutates the escrow ledger: [3](#0-2) 

The same pattern repeats for the accumulated transaction fee, which is transferred via `feeToken.call(...)` before `_orders[body.commitment][TRANSACTION_FEES]` is deleted [4](#0-3) .

`withdraw()` is a plain internal function — the contract declaration shows it does not inherit any reentrancy guard (`contract IntentGatewayV2 is HyperApp, EIP712`), unlike the fixed mainline EVM `IntentGatewayV2` which explicitly inherits `ReentrancyGuardTransient` [5](#0-4)  vs. [6](#0-5) .

By comparison, the mainline `IntentsBase._withdraw` (used by the audited/fixed `evm/src/apps/IntentGatewayV2.sol`) decrements the escrow **before** performing the transfer, i.e. correct CEI ordering: [7](#0-6) 

This confirms the project is aware of and has fixed this exact ordering issue elsewhere (see also the dedicated regression suite for the CEI fix in fill functions) [8](#0-7) , but the fix was not carried over to the Tron contract's `withdraw()`.

The one mitigating factor is that `withdraw()` sets `_filled[body.commitment] = beneficiary;` at the very top, before the loop [9](#0-8) , which blocks a reentrant `cancelOrder()` call for the same commitment (`if (_filled[commitment] != address(0)) revert Filled();` [10](#0-9) ), and `onAccept`/`onGetResponse` are `onlyHost`-gated so an attacker cannot directly re-enter them. I was unable to identify another function in this file that reads or mutates `_orders[commitment][token]` for a not-yet-decremented token during the reentrant window, so — consistent with the original report's own conclusion — I could not construct a concrete fund-theft path beyond the CEI violation itself.

### Impact Explanation
An attacker who controls the `beneficiary` of a withdrawal (achievable as the order's own `user` via same-chain `cancelOrder`, or as the filling `solver` in a cross-chain `RedeemEscrow` settlement) receives control during the native-ETH `.call` mid-loop while the corresponding escrow slot is still non-zero. No concrete double-spend or fund-drain function was found reachable from that callback window in this file, since the only re-entry points (`cancelOrder`, `onAccept`, `onGetResponse`) are gated by the `_filled` flag or `onlyHost`. As in the original report, the practical impact here is a genuine but currently *bounded* violation of the checks-effects-interactions pattern rather than a demonstrated theft — the same "Medium, no clear profitable exploit" classification as the analog.

### Likelihood Explanation
Every settlement of every escrowed order (same-chain cancellation and cross-chain fill settlement) on the Tron deployment goes through this exact code path, so the vulnerable ordering is on the primary, unprivileged, always-reachable funds-release path of the Tron `IntentGatewayV2`, not a rare corner case.

### Recommendation
Apply the same CEI fix already used in `evm/src/apps/intentsv2/IntentsBase.sol`: decrement `_orders[body.commitment][token]` (and delete the fee entry) **before** performing the native/ERC20 transfer, and add a reentrancy guard (e.g., `ReentrancyGuardTransient`, matching the mainline `IntentGatewayV2.sol`) to `withdraw()` as defense in depth against any future code paths that might read `_orders` mid-loop.

### Proof of Concept
Not applicable as a fund-theft PoC — no reachable secondary entry point into the mid-loop escrow state was found in this file (both alternate entry points, `cancelOrder` and `onAccept`/`onGetResponse`, are blocked by the `_filled` check or the `onlyHost` modifier respectively). The finding is a code-level CEI violation identical in class to the referenced `CreditUSDMinter.mint()` report, confirmed by direct comparison against the already-fixed ordering in `evm/src/apps/intentsv2/IntentsBase.sol:_withdraw`.
