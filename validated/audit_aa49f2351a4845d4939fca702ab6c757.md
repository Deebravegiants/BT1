### Title
Login endpoint (`/sessions`) leaks valid usernames via authentication timing side-channel - (File: core/sessions/localauth/orm.go)

### Summary
The local, LDAP, and OIDC authentication providers all perform a fast-path failure (a single indexed DB lookup, no cryptographic work) when the submitted email does not match a known user, but perform an expensive bcrypt hash comparison when the email does match. This produces the exact same timing oracle described in CVE-2024-54002 for Dependency-Track's `/api/v1/user/login`.

### Finding Description
`CreateSession` in the local authenticator first calls `FindUser`, and only if a user record is found does it proceed to `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))`, which invokes bcrypt (an intentionally slow, tunable-cost hash): [1](#0-0) 

If `sr.Email` does not correspond to any row, `FindUser` returns an error immediately and the function returns without ever calling `CheckPasswordHash`/bcrypt — a fast, near-constant-time DB miss. If the email does exist, bcrypt verification runs, which is measurably slower (tens of milliseconds depending on cost factor) than the DB-miss path. This asymmetry is directly reachable from an unauthenticated `/sessions` login request: [2](#0-1) 

The same bug-class pattern is duplicated in the LDAP and OIDC local-fallback authentication code paths, both of which also gate the expensive `utils.CheckPasswordHash` call behind a user-lookup success: [3](#0-2) [4](#0-3) 

Note that a constant-time comparison (`constantTimeEmailCompare`, using `subtle.ConstantTimeCompare`) is applied to the email string itself once the user row is retrieved, but this only protects against timing differences in comparing two known strings — it does nothing to hide the fact that the expensive bcrypt branch was reached at all versus the fast-fail branch for nonexistent users: [5](#0-4) 

### Impact Explanation
An unauthenticated remote attacker sending POST requests to `/sessions` with different candidate emails can distinguish "email exists" from "email does not exist" purely by measuring response latency (bcrypt vs. no bcrypt), enabling enumeration of valid Chainlink node API usernames. This is a confidentiality-only issue (CVE-2024-54002 was also rated Medium/5.3, C:L/I:N/A:N) — it does not itself grant authentication bypass, but it materially aids credential-stuffing/brute-force campaigns against the node's `/sessions` admin login, which controls job/fund-affecting operations.

### Likelihood Explanation
High likelihood of exploitability: the endpoint is unauthenticated by design (it's the login endpoint), requires no special network position, and the timing gap is a bcrypt hash computation, which is easily distinguishable over the network with a modest number of samples to average out jitter.

### Recommendation
Perform a dummy/fixed-cost bcrypt comparison (against a static, pre-computed hash) on the "user not found" path so that both branches take equivalent time, mirroring the upstream Dependency-Track fix. Apply this consistently in `core/sessions/localauth/orm.go` `CreateSession`, and in the `localLoginFallback` functions of `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`.

### Proof of Concept
1. Create a user with email `known@example.com` and any password via the admin API.
2. Send repeated POST requests to `/sessions` with `{"email":"known@example.com","password":"wrong"}` and measure response time (includes bcrypt compare).
3. Send repeated POST requests to `/sessions` with `{"email":"unknown@example.com","password":"wrong"}` and measure response time (DB miss only, no bcrypt).
4. Compare average latencies — the "known" email path is consistently and measurably slower, confirming user enumeration, as shown by the branching logic at [1](#0-0) .

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
