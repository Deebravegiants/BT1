### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from separate, unsigned HTTP headers. `Utils::HmacValidator.validate` verifies only the body bytes against the `hmac` header, never binding the `shop` field to that signature. `Registry.process` then trusts `request.shop` to build the `WebhookMetadata` passed into the app's handler. This breaks the identity binding: `bytes verified` (raw body) ≠ `bytes acted on for tenant identification` (`shop-domain` header).

### Finding Description
In `lib/shopify_api/webhooks/request.rb`:
```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., `@raw_body`) and compares it with the `hmac-sha256` header:
```
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` accepts the request purely on this body-only HMAC check and then forwards the **unauthenticated** `shop` header straight to the app's handler as the tenant identifier:
```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The equality that should hold is: `hmac(secret, signed_bytes) == received_hmac` AND `signed_bytes ⊇ tenant_identifier (shop)`. Here only the first half holds — the `shop` header is never part of `signed_bytes`. This is exactly analogous to the report's "field acted on but not covered by the HMAC" class: `UnstakeMessenger` hardcoded `user` outside any cross-chain integrity check on the recipient identity, and here the gem's webhook pipeline hardcodes trust in `shop` outside the HMAC-covered payload, while `shop` is later used as the merchant/tenant key for the app's data operations (this is confirmed by every consumer of `WebhookMetadata#shop` in a host app, and by the fact `shop` is not part of `to_signable_string`, unlike `AuthQuery#to_signable_string`, which correctly folds `shop` into the signed string for OAuth callbacks: `params = {code:, host:, shop:, state:, timestamp:}` then HMAC-verified). [5](#0-4) 

Because the body determines the signature independent of `shop`, an attacker who owns any legitimate Shopify store that has installed the app (an ordinary, unprivileged merchant action requiring no special credentials from the victim) receives genuinely-signed webhook deliveries for their own shop — e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact`. The attacker can replay the identical raw body and `hmac-sha256` header to the same webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or topic header, since topic is likewise unsigned) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` passes the forged `shop` value into the handler as if Shopify authenticated it for that tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts webhook authenticity (`InvalidWebhookError` guard) but the guarantee does not cover the value (`shop`) that host applications rely on for tenant isolation. Depending on which mandatory/webhook topic is abused (e.g., `app/uninstalled` to deauthorize a victim's install, `shop/redact`/`customers/redact` to trigger deletion of another merchant's data, or any custom topic that writes/mutates records keyed by `shop`), this enables cross-tenant data corruption, spoofed deauthorization, or injection of attacker-controlled data into another merchant's records — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Reaching this requires only: (1) an attacker-controlled shop that installs the target app (a normal, permissionless action any internet user can perform if the app is public), (2) capturing one legitimate webhook delivery for a topic of interest, and (3) POSTing the same body/HMAC with a substituted `shop-domain` (and optionally `topic`) header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the victim's credentials is needed. Likelihood is High.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values into the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop that has an active, previously-registered session/webhook subscription for that specific `webhook_id`/topic combination before invoking the handler. At minimum, `Request#to_signable_string` should not silently exclude the header-derived `shop` value from the value the caller trusts to key application state — either document that host apps MUST cross-check `shop` against their own registered webhook IDs, or add that check inside `Registry.process` itself (e.g., validate against a per-shop webhook registration lookup) before dispatching to handlers.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":123,"note":"legit order for attacker-shop"}'

# 1. Attacker's own store receives a genuine webhook; hmac is valid for `body`.
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
valid_hmac_header = Base64.encode64(hmac_digest)

# 2. Attacker replays the identical body/hmac but swaps the shop-domain header.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not part of the signed bytes
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# 3. HMAC validation still passes because only `body` is checked.
puts ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process would now dispatch to the handler with
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed_body, ...)
#    even though Shopify never sent this payload for victim-shop.
ShopifyAPI::Webhooks::Registry.process(request)
```
This demonstrates that `shop` is trusted as the tenant key for handler dispatch despite never being covered by the HMAC verification in `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`. [4](#0-3)
