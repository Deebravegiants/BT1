This confirms the design: the docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" based solely on the HMAC over the raw body, while the `shop` field handed to the app's handler comes from an unauthenticated header.

### Title
Webhook `shop` Identity Spoofing via Unauthenticated `shop-domain` Header Bypassing HMAC Binding — Cross-Tenant Webhook Forgery ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop` is read from a separate, unsigned header (`x-shopify-shop-domain`/`shopify-shop-domain`). `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then unconditionally passes the unauthenticated header-derived `shop` value to the app's handler as the trusted tenant identifier. This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC only proves the *body* came from a holder of the app's shared `api_secret_key` — a secret common to every merchant installation of the app — but never proves the body is bound to the claimed shop.

### Finding Description
- `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) signs only `@raw_body`. [1](#0-0) 
- `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) is read straight from the header, entirely outside the signed content. [2](#0-1) 
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only `Utils::HmacValidator.validate(request)` (i.e., body vs. HMAC), then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and dispatches it to the app handler — `shop` is never cross-checked against anything covered by the signature. [3](#0-2) 
- `HmacValidator.validate`/`validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) computes HMAC-SHA256 over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) using `Context.api_secret_key`, which is the **app's** secret — identical across all shops that install the app, not shop-specific. [4](#0-3) 
- The docs confirm the library's own claim that `process` "verify[ies] the request did indeed come from Shopify," implying the `shop` field is also trustworthy, when in fact only the body is authenticated. [5](#0-4) 

Because the same `api_secret_key` verifies webhook bodies for *every* shop that installs the app, an unprivileged internet user can self-install the app on their own (attacker-controlled) shop, trigger a webhook there to obtain a body+HMAC pair that legitimately validates, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the header), so `Registry.process` calls the app handler with `WebhookMetadata#shop` set to the victim's domain and `body` fully attacker-controlled — a cross-tenant identity confusion that lets the attacker impersonate another merchant's webhook stream using data they authored.

### Impact Explanation
This is a cross-tenant identity binding failure: the equality `shop verified by signature == shop the handler acts on` does not hold. Any downstream app logic that trusts `WebhookMetadata#shop` to select the tenant/session/database row to update (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into applying attacker-supplied data (order details, product updates, uninstall/redact events, etc.) to a victim shop's tenant record, without ever needing that victim's credentials, access token, or `client_secret`. This matches the Critical bucket for cross-tenant access.

### Likelihood Explanation
Any internet user can freely create a development/partner store and install the app (self-service, no privileged access to any target required), letting them legitimately trigger a webhook and capture a genuine `(body, HMAC)` pair signed with the shared `api_secret_key`. Replaying that pair against the app's public webhook endpoint with a substituted `shop-domain` header requires no secret, no TLS interception, and no social engineering — only the ability to send an HTTP request with custom headers, which is trivial. This makes the likelihood high wherever the host application relies on `WebhookMetadata#shop` as a trusted tenant key, which is exactly the pattern the gem's own documentation recommends.

### Recommendation
Bind the shop identity into the signed content, or otherwise verify it independently of the raw header before dispatching to handlers:
- Include the `x-shopify-shop-domain` (and ideally `webhook-id`, `topic`) in the value covered by HMAC verification (this requires coordinating with Shopify's signing format, or at minimum documenting that the header is untrusted), or
- Have `Registry.process` refuse to dispatch unless the caller supplies an expected/known shop (e.g., the session's shop) to compare against `request.shop`, or
- Explicitly and prominently document that `WebhookMetadata#shop` is **not** covered by the HMAC and must not be used as a sole tenant-selection key without additional verification (e.g., cross-referencing an existing installed-shop record) before this identity binding gap can be considered mitigated in application code.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (self-service, no special privilege needed).
2. Attacker performs an action that triggers a real webhook (e.g., `orders/create`) from Shopify to the app's registered endpoint, and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid because it's HMAC-SHA256(`B`, app's shared `api_secret_key`), per `lib/shopify_api/utils/hmac_validator.rb:33-40`). [6](#0-5) 
3. Attacker crafts a forged HTTP POST to the same webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` as desired.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app and passed to `Registry.process`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`). [7](#0-6) 
6. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)` to the app's handler (`lib/shopify_api/webhooks/registry.rb:188-200`), which any typical implementation (per the gem's own doc example at `docs/usage/webhooks.md:19-30`) will use to attribute and persist attacker-controlled `body` data to the victim's tenant record — completing the cross-tenant forgery with a fully valid HMAC.
