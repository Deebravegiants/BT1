### Title
Webhook `shop` domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the `shop` value that is handed to the app's `WebhookHandler` (and that the gem's own docs tell developers to use as the tenant key) comes from the `x-shopify-shop-domain` HTTP header, which is completely outside the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [4](#0-3)  This is the only input fed into `HmacValidator.validate`, which computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header: [5](#0-4) 

`Registry.process` gates on that same HMAC check and then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — none of which are covered by the signature: [1](#0-0)  All four accessors simply read raw, unauthenticated headers: [6](#0-5) 

This mirrors the reported bug class: a value that is *acted upon* by security-relevant logic (the sale price used in royalty math; here, the `shop` used to scope tenant data) is not the value that was actually *verified* (the fixed `100` in `royaltyInfo`; here, the raw body that was HMAC'd). The gem documents `data.shop` as "The shop domain of the webhook" and shows it being used directly as the tenant/shop key for queued background work: [3](#0-2) 

Because Shopify's HMAC secret (`api_secret_key`) is per-app, not per-shop, any merchant who has legitimately installed the app can receive a real, validly-signed webhook for their own shop (e.g., `orders/create` for Shop A) and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different value in the `x-shopify-shop-domain` header (e.g., Shop B). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`. Any host application that follows the gem's documented pattern of trusting `data.shop` to select which tenant's records to update, or which shop's session/store to look up, will process attacker-supplied body content under a victim tenant's identity — a cross-tenant confusion driven entirely by data this gem asserts is authenticated but never actually binds to the signature.

### Impact Explanation
This breaks the binding "shop authenticated == shop the webhook data is attributed/acted upon for." Any app relying on the gem's documented contract (`data.shop` as the authenticated shop domain) is exposed to cross-tenant webhook injection: an attacker (a real, if low-privilege, merchant installer of the app) can cause the app to associate legitimate webhook payload content with an arbitrary victim shop of their choosing, since the shop identifier is never covered by the cryptographic check. This falls under Critical - cross-tenant access.

### Likelihood Explanation
Requires only that the attacker be an installed merchant on the app (no special privilege, no leaked secrets) able to capture one legitimate webhook delivery for their own shop and replay it with a modified header to the app's public webhook endpoint. The gem performs no additional binding of `shop` to the signed payload, so exploitation is a direct HTTP replay with header substitution.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) as part of the material verified against the HMAC, or otherwise cryptographically bind the `shop` header to the request before exposing it via `WebhookMetadata`. At minimum, `Utils::HmacValidator` should validate a signable representation that incorporates the `shop-domain` header alongside the raw body, analogous to how `AuthQuery#to_signable_string` binds `shop`, `state`, `code`, etc., into the OAuth callback's signed string: [7](#0-6) 

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (attacker controls Shop A, victim is Shop B), both subscribed to `orders/create`.
2. Attacker triggers an order on Shop A, capturing the legitimate webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`), plus `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` (`B`) — validation passes unchanged: [4](#0-3) 
5. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's order data>, ...)` and, per the documented usage pattern, enqueues/attributes this data to Shop B — a cross-tenant data confusion the gem's signature check does nothing to prevent.
