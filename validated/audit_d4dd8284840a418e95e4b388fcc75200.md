This confirms the vulnerability. The gem explicitly documents this as verifying identity ("This will verify the request did indeed come from Shopify") based solely on `ShopifyAPI::Webhooks::Registry.process`, which only checks `Utils::HmacValidator.validate(request)` — and that validation only covers `raw_body`, never the `shop` header that the app uses to attribute the webhook to a tenant.

### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" and hands the (header-derived) `shop` value straight to the app's handler as the tenant identifier, even though `shop` was never part of what the HMAC signs.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field of the same object [1](#0-0) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from `x-shopify-*`/`shopify-*` headers that are never mixed into the signed content [3](#0-2) .

`Registry.process` gates entirely on this HMAC check and then forwards the header-derived `shop` (and `topic`, `webhook_id`, `api_version`) to the handler as trusted metadata: [4](#0-3) .

The identity binding that should hold is: `shop` used to attribute the webhook to a tenant == `shop` cryptographically bound to the signed bytes. Instead the code only proves body integrity == HMAC(raw_body, api_secret_key); `shop` is asserted, not authenticated.

Because `api_secret_key` is a single shared per-app secret (not per-shop), any merchant who installs the app on their own store receives genuine webhook deliveries with a valid HMAC over their own body content. That attacker-controlled shop can capture one legitimate `(raw_body, hmac)` pair from their own installation, then replay it to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` still passes because it never inspected those headers, and `Registry.process` calls the handler with `shop: <victim-domain>` and the attacker's own body — a cross-tenant spoof.

### Impact Explanation
This is Critical/High under the "cross-tenant access" category: an app that keys any persistence, authorization, or side effects (e.g. `perform_later(shop_domain: data.shop, ...)`, as shown in the gem's own webhook docs) off `data.shop` [5](#0-4)  can be made to write, delete, or act on attacker-chosen data under a victim shop's identity, purely because `shop` is trusted without being bound to the HMAC-verified bytes.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (any developer/merchant can do this for public or even custom apps) and send one crafted HTTP request to the app's public webhook endpoint with a modified header — no access token, secret, or privileged account is needed.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material, or independently verify the `shop` header against a value embedded in the authenticated body (many Shopify webhook payloads already carry `shop_id`/domain-identifying fields), before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned shop `evil.myshopify.com`; trigger any subscribed topic to receive a legitimate webhook `POST` with body `B` and header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`.
2. Replay the exact same body `B` and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC [2](#0-1) ; `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own body>, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it originated from the victim tenant.
