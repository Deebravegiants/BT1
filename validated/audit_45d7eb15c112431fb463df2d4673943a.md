## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop-domain` header — which `Registry.process` hands to the application's webhook handler as the authoritative tenant identifier — is never part of the HMAC-verified content. An attacker who can obtain any single validly-signed webhook payload (e.g. by installing the app on their own shop) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem's validation will accept it as authentic.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, that signable string is defined as just the raw body: [2](#0-1) 

The `shop` accessor, however, is read directly from an unsigned header: [3](#0-2) 

`Registry.process` only checks the body HMAC, then immediately trusts `request.shop` as the tenant identity passed into the application handler: [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == (body, shop)` — but the actual implementation only enforces `hmac_signed_bytes == body`. Because `shop` is excluded from the signed content, the HMAC check validates that "this body was produced with our secret" but says nothing about "for this shop." Any valid `(body, hmac)` pair obtained by an attacker (e.g., from webhooks fired to their own legitimately-installed shop) can be replayed with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header pointing at a victim shop, and the gem will report `data.shop` as the victim's domain to the handler.

This is the same class of bug as the external report: an operation is trusted based on a validated signature, but a field the downstream logic actually keys off of (the tenant/shop) is not included in what was signed — analogous to "a field acted on but not covered by the HMAC."

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding, enabling cross-tenant confusion: the application receives a webhook it believes is verified and attributed to shop A, when in fact the signed payload only proves it originated from the app's secret for *some* shop (possibly the attacker's own shop). Depending on the handler's use of `WebhookMetadata#shop` (session lookup, data deletion/cleanup, compliance actions such as `app/uninstalled`/`shop/redact`), this can let an unprivileged internet user (any merchant who installs the app once) forge events attributed to a shop they don't control, which falls under cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on any shop (or otherwise obtain one legitimately-signed webhook body/HMAC pair) and be able to POST to the app's public webhook endpoint with a custom `shop-domain` header — both are available to an ordinary, unprivileged Shopify merchant/internet user, with no access token, `client_secret`, or leaked credential required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-verified signable content, or explicitly cross-check that the `shop` header corresponds to a shop the current webhook body legitimately belongs to before dispatching to handlers, e.g. bind `shop` into `to_signable_string` for `Webhooks::Request`, or require callers to supply the expected shop and compare it against a value embedded in the verified body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or waits for) a webhook, e.g. `app/uninstalled`, capturing the raw body (often static, e.g. `"{}"`) and its `x-shopify-hmac-sha256` value — both computed with the real `api_secret_key` shared by all installs of this app.
2. Attacker sends a POST to the app's public webhook endpoint with the captured body and HMAC unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — this succeeds.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)`, causing the app to act as though the victim shop sent this event, even though the victim never sent anything.
