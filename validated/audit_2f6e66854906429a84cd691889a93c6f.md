## Analysis

I found a valid analog: an identity field (`shop`) that is **acted upon by the library but not covered by the HMAC signature** that is supposed to authenticate the whole webhook request.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` — the string that `HmacValidator` signs/verifies — is defined as *only* the raw HTTP body: [1](#0-0) 

But the `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers, which are **not** part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC (body only) and then unconditionally trusts `request.shop` to build the tenant-identifying `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

### The identity binding broken

The equality that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

Instead, the code enforces only: `body signed with api_secret_key == body received`, while `shop` (and `topic`/`webhook_id`) ride along unauthenticated in headers, yet are passed to `handler.handle` as if verified.

### Exploit path

The app's `client_secret`/webhook secret is shared across **all shops** that install the app — it is not shop-specific. Any unprivileged internet user who controls a shop that has installed the target app (e.g., a free/dev store) will receive genuine webhooks from Shopify with a valid `hmac-sha256` for their own body content. That attacker can then replay the exact same `raw_body` + `hmac` header to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (only the body is checked), and `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop` set to the spoofed victim domain and `body` fully attacker controlled. Any host app that uses `data.shop` to key tenant records, look up sessions, or gate per-shop side effects (e.g. `customers/redact`, `shop/redact`, order fulfillment triggers) will act on attacker-supplied data under a foreign tenant's identity — a cross-tenant confusion/injection primitive, achievable with only knowledge of the attacker's own valid webhook traffic, no `api_secret_key` or access-token compromise required.

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, and `webhook_id` come from unauthenticated HTTP headers and are trusted downstream by `Registry.process`.

### Finding Description
`HmacValidator.validate` calls `to_signable_string`, which returns `@raw_body` only [1](#0-0) . The `shop` accessor pulls from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that body [2](#0-1) . `Registry.process` verifies the HMAC and then forwards `request.shop` (and `request.topic`, `request.webhook_id`) straight into `WebhookMetadata` passed to the app's handler [3](#0-2) , implicitly treating that value as authenticated when it is not.

### Impact Explanation
Because the app's webhook signing secret (`api_secret_key`) is identical across every shop that installs the app, a low-privilege attacker who merely operates their own installed shop can obtain a genuinely-signed body+HMAC pair and replay it with a forged `shop-domain` header pointing at any victim shop. Handlers that key business logic, data storage, or authorization decisions off `WebhookMetadata#shop` (a documented, expected usage pattern of this library) will act as though the (attacker-controlled) body came from the victim tenant — a cross-tenant integrity/confusion issue.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (including their own) and capture one legitimate webhook delivery — no access token, `client_secret`, or privileged account is needed. This is easily automatable and repeatable for any topic the app registers a handler for.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., by deriving the topic/shop from a value embedded in the signed body), so that `HmacValidator.validate` fails if these header-derived identity fields are altered independently of the signed payload.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; register a webhook for a topic the app handles (e.g. `customers/create`).
2. Capture a legitimate webhook POST from Shopify containing `raw_body` and header `x-shopify-hmac-sha256: <valid-hmac>`.
3. Resend the identical `raw_body` and `hmac` header to the app's webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC and succeeds [5](#0-4) .
5. The handler executes with `WebhookMetadata#shop == "victim.myshopify.com"` and attacker-controlled `body`, despite the request never having originated from Shopify on behalf of `victim.myshopify.com`.
