### Title
Blacklistable/pausable input tokens permanently freeze intent escrow redemption in `IntentsBase._withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s intents system escrows multiple input tokens per order and releases them all atomically to a fixed beneficiary via `_withdraw`. If any one of the escrowed input tokens is a blacklistable/pausable token (e.g. USDC/USDT) and the recipient becomes blacklisted (or the token is paused) for that specific token, the entire redemption — including all other, unrelated tokens in the same order — permanently reverts and can never succeed, since the beneficiary and token set are fixed at order-placement time.

### Finding Description
`IntentsBase._withdraw` iterates over `body.tokens` and unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` for every token entry in a single atomic loop: [1](#0-0) 

If `safeTransfer` reverts for any single token (e.g. because the fixed `beneficiary` address is blacklisted on that ERC-20, or the token contract is paused), the entire function reverts — no tokens are released, not even the unaffected ones in the same `body.tokens` array.

This function is reached from two places:
1. Same-chain fills, via `IntrinsicIntents` calling `_withdraw(body, false, isFullyFilled)` after escrow accounting. [2](#0-1) 
2. Cross-chain settlement, via `ExtrinsicIntents.onAccept` handling `RequestKind.RedeemEscrow`/`RequestKind.RefundEscrow` incoming Hyperbridge POST requests, which decode a `WithdrawalRequest` and call `_withdraw`. [3](#0-2) 

The same pattern exists in the Tron variant's `withdraw()`, which uses low-level `.call` with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and reverts with `TransferFailed()` on any single-token failure, again blocking the whole multi-token payout: [4](#0-3) 

Because `EvmHost` only retries the app callback on failure (deleting the receipt so it can be resubmitted, as seen in the analogous GET-response/POST-timeout handling), a permanently-failing token/beneficiary pair means every future retry of the same `onAccept` call fails identically — the order's `beneficiary` (order.user or the solver address recorded at fill time) and its `body.tokens` list are immutable, so there is no way to work around the stuck transfer: [5](#0-4) 

This is a direct structural analog of the reported OpenQ `ClaimManagerV1` issue: a loop that sends several tokens to one recipient, where any single blacklistable/pausable/failing token reverts the whole batch and blocks release of unrelated funds.

### Impact Explanation
Funds escrowed for legitimate, unrelated tokens in the same order become permanently unrecoverable once one input/output token in that same order is blacklisted for the fixed beneficiary or paused. There is no fallback path (no per-token retry, no ability to redirect a single stuck token, no way to change the beneficiary address post-order). This constitutes a permanent freezing-of-funds condition reachable by any counterparty (issuer of a USDC/USDT-based blacklist action, or the token pauser) without needing privileged access to Hyperbridge itself — a normal user placing/filling an order with a blacklistable stablecoin as one of several input tokens is sufficient to create the at-risk state.

### Likelihood Explanation
Multi-asset orders combining a blacklistable/pausable stablecoin (USDC, USDT) with other tokens are an expected, supported use case for the intents system (`TokenInfo[]` arrays of arbitrary length are explicitly supported in `Order.inputs`/`Order.output.assets`). Blacklisting/pausing events on major stablecoins occur in practice (sanctions compliance, exploit response), so the triggering condition is realistic, not purely theoretical.

### Recommendation
Do not perform all token transfers for a `WithdrawalRequest` atomically in one revert-all loop. Either:
- Wrap each individual token transfer in a try/catch (or low-level call) and, on failure, credit the amount to a per-token/per-beneficiary "pending withdrawal" balance that can be pulled later or redirected, rather than reverting the whole batch; or
- Process each token's release as an independent, separately retryable operation instead of coupling them all into a single all-or-nothing call.

### Proof of Concept
1. Solver places/fills a cross-chain order whose `order.inputs` (or `order.output.assets`) contains two tokens: `USDC` and `DAI`.
2. Before the `RedeemEscrow`/`RefundEscrow` message is delivered, the issuer of `USDC` blacklists the order's beneficiary address (or pauses USDC).
3. Hyperbridge relays the `RedeemEscrow` POST request; `ExtrinsicIntents.onAccept` decodes the `WithdrawalRequest` and calls `IntentsBase._withdraw`.
4. In the loop at `IntentsBase.sol:456-469`, the `IERC20(USDC).safeTransfer(beneficiary, amount)` call reverts because the beneficiary is blacklisted.
5. The entire `_withdraw` call reverts, so the `DAI` amount in the same `body.tokens` array is never released either — `EvmHost.dispatchIncoming` (POST path) marks the callback as failed and allows resubmission, but resubmission hits the exact same revert forever, since the beneficiary and token set cannot change. Both the USDC and DAI escrow are now permanently frozen.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
