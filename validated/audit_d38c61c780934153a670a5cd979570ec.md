### Title
Every live mainnet IntentGateway deployment executes solver bids with no on-chain expiry, letting order placers hold signed quotes as a free option and exercise them once the rate turns against the solver - ([File: sdk/packages/sdk/src/protocols/intents/fillOrderCodec.ts])

### Summary
The 1inch incident stole funds belonging to *resolvers* (order fillers) rather than users, because the resolver contracts still running the deprecated Fusion v1 implementation lacked a protection that the newer implementation had. The IntentGatewayV2 protocol has the structurally identical situation today: `FillOptions.validUntil` — the field that bounds how long a signed solver bid remains executable — was added to fix exactly this resolver-fund-loss class of bug, but every currently deployed mainnet gateway still runs the pre-`validUntil` ("v1") implementation, so the fix is not actually in effect anywhere it is needed.

### Finding Description
`fillOrder` is the function a solver (filler/resolver) calls to execute an order it bid on. A solver's bid is a *signed, irrevocable, indefinitely-executable* quote once placed: `order.deadline` is chosen by the order placer with no upper bound, and retracting a bid on the Hyperbridge coprocessor has no effect on the destination chain's contract state [1](#0-0) . The order placer controls the session key that authorizes which solver's bid gets executed and chooses the moment of execution, so a placer can simply sit on a solver's signed bid and execute it only once the market has moved in the placer's favor (and against the solver) [2](#0-1) .

`FillOptions.validUntil` was added specifically to close this: `fillOrder` reverts `FillExpired` once the caller-set block bound has passed [3](#0-2) . But adding the field changed the function selector, splitting `fillOrder` into two incompatible on-chain shapes — v1 (`0x5cfb1ea5`, no `validUntil`, no protection) and v2 (`0xa5470064`, with `validUntil`) [4](#0-3) . Per the maintainers' own tracking data, `LEGACY_FILL_OPTIONS_IMPLEMENTATIONS` names the one CREATE2 implementation address that is deployed to essentially every mainnet chain, and `CHAINS_WITHOUT_VALID_UNTIL` names the remaining chains not yet redeployed [5](#0-4) . The SDK's own changelog states plainly: "every mainnet gateway still runs the pre-`validUntil` implementation" [6](#0-5) , and the filler-side integration code explicitly warns that on such a chain "bids ... carry no expiry and stay executable until the order's own deadline" and "the bound is dropped — there is nowhere to put it" [7](#0-6) .

This is the direct structural analog of the 1inch report: an "obsolete implementation" still in production use lacks a fix present in the newer implementation, and the funds at risk belong to the resolver/solver counterparty rather than the end user.

### Impact Explanation
A solver's `fillOrder` execution atomically delivers real output tokens to the beneficiary and only afterward releases the escrowed input tokens back to the solver [8](#0-7) . Because every mainnet IntentGateway deployment lacks `validUntil` enforcement, a malicious or opportunistic order placer can withhold selection of a signed, favorably-priced bid and trigger it later — after the market price of the input/output pair has moved — forcing the solver to deliver output tokens at a stale, unprofitable rate while receiving escrow at the old rate. This is a concrete, repeatable mechanism for extracting value directly from solver capital on every live chain, matching the "resolver funds, not user funds, stolen" profile of the 1inch incident. It qualifies as Medium/High severity: it is not a one-off griefing bug but a systemic, unauthenticated economic drain reachable by any order placer against any solver on every currently deployed gateway.

### Likelihood Explanation
Likelihood is high. No special privilege is needed — any order placer (a completely permissionless, unprivileged role) can exploit this simply by delaying `select`/execution of a bid it already received, which is normal, unremarkable interaction with the protocol. The vulnerability is not hypothetical or already patched in production: per the codebase's own tracking constants and changelog, the fix (`validUntil`) exists only in the SDK/encoding layer and in the newer contract implementation, while the actual deployed bytecode on every mainnet chain is still the legacy, unprotected version.

### Recommendation
Redeploy (upgrade) every mainnet IntentGatewayV2 proxy to the implementation that enforces `FillOptions.validUntil`, removing the reliance on `LEGACY_FILL_OPTIONS_IMPLEMENTATIONS`/`CHAINS_WITHOUT_VALID_UNTIL` tracking as the only mitigation. Until upgraded, solvers should treat every bid on an affected chain as unboundedly exercisable and price in that risk, and integrators should surface the `ContractInteractionService` warning as a hard stop rather than a log line.

### Proof of Concept
1. Observe that `getFillOptionsVersion` resolves to `1` for the gateway's implementation address (matches `LEGACY_FILL_OPTIONS_IMPLEMENTATIONS`) [9](#0-8) .
2. A solver signs and submits a competitive bid (`FillOptions` without `validUntil`, v1 selector `0x5cfb1ea5`) for an order via the Hyperbridge coprocessor.
3. The order placer does not select/execute it immediately. Time passes and the relative price of `order.output` vs `order.inputs` moves in the placer's favor.
4. The placer (or any relayer acting for them) submits the still-valid, unexpired bid calldata to `fillOrder` on the legacy v1 gateway. Because there is no `validUntil` field or check in this code path, the call succeeds regardless of staleness [10](#0-9) .
5. The solver is forced to deliver output tokens at the old, now-unfavorable rate and only then receives the escrow, realizing a loss exactly analogous to resolvers losing funds against a stale/obsolete resolver contract implementation in the 1inch incident.

export async function getFillOptionsVersion(client: PublicClient, gateway: HexString): Promise<FillOptionsVersion> {
	// Checked before the slot read: on a chain that has not been redeployed the implementation
	// address tells us nothing useful, and skipping the read saves a round trip.
	const chainId = client.chain?.id
	if (chainId !== undefined && CHAINS_WITHOUT_VALID_UNTIL.has(chainId)) return 1

	const key = gateway.toLowerCase()
	if (knownV2Gateways.has(key)) return 2

	const implementation = await resolveImplementation(client, gateway)
	if (LEGACY_FILL_OPTIONS_IMPLEMENTATIONS.has(implementation.toLowerCase())) return 1

	knownV2Gateways.add(key)
	return 2
}
