### Title
Webhook shop/topic identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop`, `topic`, and `webhook_id` fields that `Registry.process` acts upon to route and attribute webhook data are taken from unsigned HTTP headers.

### Finding Description
`Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` passes [4](#0-3) . That validator recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header [5](#0-4) . For `Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC binds `secret ↔ raw_body` but does **not** bind `secret ↔ shop` or `secret ↔ topic`. However, `shop`, `topic`, and `webhook_id` are parsed straight from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers [2](#0-1) , and `process` passes these header-derived values, unchecked, into `WebhookMetadata` that the host application's handler trusts as the webhook's origin/type [6](#0-5) .

This breaks the identity binding: `hmac_valid(raw_body) == true` should imply `shop == originating_shop ∧ topic == originating_topic`, but neither is actually enforced — only `raw_body` is authenticated. An attacker who legitimately controls their own shop can capture a genuine `(raw_body, hmac)` pair produced by Shopify for one of their own webhook deliveries (e.g., an `orders/create` event with attacker-chosen order content), then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id` headers) to any value they choose. The HMAC still validates because it only covers `raw_body`, but `Registry.process` will dispatch the handler with a forged `shop` (and potentially forged `topic`/`webhook_id`), causing the host app to attribute attacker-supplied webhook data to a shop the attacker does not own.

### Impact Explanation
Because the app's webhook handler receives `WebhookMetadata.shop` as an authenticated fact (it passed HMAC validation), but it is actually attacker-controlled, a malicious actor can inject fabricated webhook events under the identity of an arbitrary target shop/tenant. Any host application logic that uses `data.shop` to look up sessions, update tenant-scoped state, or route side effects (common in `shopify_app`-integrated apps) can be tricked into applying attacker-supplied data to a victim tenant — a cross-tenant data integrity violation reachable without any credentials belonging to the victim.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own Shopify store (freely available) and trigger a webhook for a topic supported by the target app, then replay the captured body/HMAC to the target app's endpoint with a modified shop header. No access to the app's `client_secret`, access tokens, or the victim's credentials is needed, making this practically reachable by any unprivileged internet user who can install/operate a dev/trial shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) in the HMAC-signed material, or at minimum have `Registry.process` verify that the `shop` header corresponds to a shop with an active session/registration for that topic before dispatching to the handler.

### Proof of Concept
1. Attacker creates/uses their own Shopify development store `attacker.myshopify.com` and installs the target app.
2. Attacker triggers a supported webhook topic (e.g. `orders/create`) on their own store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it was computed by Shopify using the real `client_secret` over `raw_body`.
3. Attacker resends this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC [1](#0-0) .
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body content, even though Shopify never sent this event for `victim.myshopify.com` [6](#0-5) .
