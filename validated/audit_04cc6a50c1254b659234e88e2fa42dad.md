## Title
Webhook shop identity not covered by HMAC verification allows cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` to route and label incoming webhook data is taken from a separate HTTP header that is never included in the signed content. Any user who can obtain one legitimate `(body, hmac)` pair for a webhook delivered to their own shop can replay that exact pair against the app's public webhook endpoint while substituting the `shop-domain` header for an arbitrary victim shop, and the gem will accept it as authentic.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Request#shop` is read from a distinct, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`): [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the body), never against `shop`: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once that body-only HMAC check passes, then dispatches the handler using the *unauthenticated* `request.shop` value as the tenant identity, without any additional check binding it to the signed content: [4](#0-3) 

The broken identity binding, as an equality, is:
`shop-domain header used for tenant attribution` ≠ `bytes actually covered by the HMAC (raw body only)`.

Because the app's `client_secret` is shared across all shops that install the app, any merchant (an "unprivileged" party relative to a victim shop) can legitimately trigger a webhook for their own store, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair (e.g., from their own server logs or by controlling their own webhook receiver), and then POST that identical body/HMAC pair directly to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` will still succeed since it only checks the body, and `Registry.process` will hand the (attacker-supplied) body to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding that app handlers rely on when processing webhook data (`WebhookMetadata#shop`), enabling cross-tenant data injection: an attacker-controlled payload (an order, customer, product, or `app/uninstalled` event body they crafted for their own shop) can be attributed to a different, victim shop. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up/update per-shop state, revoke sessions on `app/uninstalled`, or write per-tenant records), this can result in cross-tenant state corruption or spoofed lifecycle events for shops the attacker does not control. This matches the "Cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control (or have installed) the app on at least one shop of their own in order to produce one legitimate `(body, hmac)` pair, and requires the app's webhook endpoint to be reachable and to act on the `shop` field from `WebhookMetadata` in a security-relevant way. No secrets, tokens, or privileged access to the victim's shop are required — only a body/HMAC pair the attacker can generate for themselves and knowledge of the victim's `myshopify.com` domain (public information).

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the `shop` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that host applications must independently verify `WebhookMetadata#shop` against a known/installed-shop list before using it for tenant-scoped operations, since the current HMAC only guarantees body integrity, not shop attribution.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`) with attacker-controlled body content.
2. Attacker captures the delivered raw body `B` and the valid `X-Shopify-Hmac-Sha256: H` computed by Shopify over `B` using the app's shared `client_secret`.
3. Attacker sends a POST request directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`: unchanged
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`.
5. `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and `body` equal to the attacker's crafted content, despite the data never having originated from that shop.
