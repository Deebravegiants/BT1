## Analysis Result

Mapping the "field acted on but not covered by the HMAC" bug class to this codebase, the strongest match is in the webhook verification path.

### Title
Webhook `shop` (tenant) field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the topic, shop domain, webhook id, and API version from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies covers only the raw request body, never the `shop-domain` header. Since the shared `api_secret_key` used to sign webhooks is the same across every shop that installs the app, any shop owner (an unprivileged actor with respect to *other* merchants using the same app) can obtain a validly-signed webhook for body content they fully control, then replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the signature check still passes.

### Finding Description
The equality that should hold is: `verified(hmac) == (body, shop, topic, ...)` — i.e., every field the app later trusts as coming from a specific shop must be inside the signed payload. Instead:

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is read straight from the (unsigned) header: [2](#0-1) 
- `Registry.process` validates only the HMAC of `to_signable_string` (the body) and then forwards `request.shop` unchecked to the handler as the tenant identifier: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, so any field not included there (here, `shop`) is unauthenticated: [4](#0-3) 

Because the `api_secret_key` is the app-wide client secret (not per-shop), a merchant who has legitimately installed the app receives real, validly-HMAC'd webhooks from Shopify whose body content they can fully influence (e.g., via order notes, product titles, customer names, or other webhook payload fields they control on their own store). That attacker can then take a captured, validly-signed webhook request and simply substitute the `x-shopify-shop-domain` / `shopify-shop-domain` header with a different (victim) shop's domain before submitting it to the app's webhook endpoint. `Utils::HmacValidator.validate` re-verifies only the (unchanged) body against the (unchanged) HMAC and returns `true`, so the forged `shop` value is accepted and passed on to the host application's handler as if it were an authentic event from the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary: the `shop` value that a host application uses to select which merchant's session/data to update is not covered by the message authentication code that is supposed to prove the message's authenticity. Any webhook handler that trusts `WebhookMetadata#shop` to decide which tenant's records to create, update, or delete (a common pattern for `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) can be tricked into performing actions attributed to, or affecting data belonging to, a different shop than the one that actually sent the request. This is a cross-tenant integrity issue directly caused by the gem's own `Request`/`HmacValidator`/`Registry` implementation.

### Likelihood Explanation
Exploitation only requires being a merchant who has installed the target app (an "unprivileged internet user" relative to other tenants of the same app) — no access to the app's `client_secret`, access tokens, or infrastructure is needed. The attacker fully controls the payload of webhooks fired from their own store and can capture the resulting HTTP request (including a correct HMAC) via any HTTP proxy, then replay it with a modified `shop-domain` header. This requires only the ability to intercept/replay their own outbound-to-inbound HTTP traffic, well within the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) inside the HMAC-signed content, or otherwise cryptographically bind the shop identity to the payload before trusting `request.shop`/`WebhookMetadata#shop`. At minimum, `Request#to_signable_string` should incorporate the shop domain header value so that `HmacValidator.validate` fails if it is altered after signing.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker-shop.myshopify.com`).
2. Attacker triggers a webhook whose body content they control (e.g. updates an order note) and captures the resulting POST request, including headers `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical request to the app's webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, leaving the raw body and HMAC header untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` (unchanged) using the app's `api_secret_key` and it matches, per: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` now returns `"victim-shop.myshopify.com"`, so the host application processes the attacker-controlled payload as an authentic event from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
