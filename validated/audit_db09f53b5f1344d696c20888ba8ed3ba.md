## Title
Upgradeable `IntentGatewayV2` inherits storage-holding base contracts (`IntentsBase`, `IntrinsicIntents`, `ExtrinsicIntents`) with no reserved gap slots, risking storage collision on future UUPS upgrades - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` is a live UUPS-upgradeable proxy (uses `Initializable`, `reinitializer`, and `ERC1967Utils.upgradeToAndCall` reachable via governance `Execute` requests) that is composed by inheriting `IntrinsicIntents`, `ExtrinsicIntents`, and (transitively) `IntentsBase`, `ReentrancyGuardTransient`, and `Initializable` [1](#0-0) . None of `IntentsBase`, `IntrinsicIntents`, or `ExtrinsicIntents` reserve any `__gap` storage slots, even though `IntentsBase` alone declares seven persistent state variables including mappings and packed booleans that other logic depends on at fixed slots [2](#0-1) . A repo-wide search confirms the only `__gap` pattern in the codebase exists in an unrelated contract (`SimplexPaymaster`), not in any of the intent-gateway base contracts.

### Finding Description
Solidity's storage layout for inheriting contracts is determined by C3 linearization of the declared base contracts, in the order variables are declared across that chain. `IntentGatewayV2` sits behind an `ERC1967Proxy` and is genuinely upgraded in production: `onAccept` handles an `Execute` discriminator that `delegatecall`s `upgradeToAndCall`, and the live mainnet proxy at `0xAe041F7B0CB581876832830baeB6a2Aa2a3C9716` has already been migrated through this path [3](#0-2) .

`IntentsBase` fixes critical storage at specific slots that other logic depends on byte-for-byte — for example `_filled` is required to stay at slot 2 because a cross-chain storage proof for order cancellation is built against that exact slot index (`FILLED_SLOT_BIG_ENDIAN_BYTES`) [4](#0-3) , and `_relayer` was deliberately appended as a bare variable after `_paused` rather than inside the `Params` struct specifically because adding a field to `Params` would shift every mapping declared after it and corrupt escrow accounting on the live proxy [5](#0-4) . This project-internal design note is itself proof that the team is aware storage-slot shifts are catastrophic here, yet no `__gap` reservation was added to any of `IntentsBase`, `IntrinsicIntents`, or `ExtrinsicIntents` to make future additions safe. Any future upgrade that adds a new state variable to one of these base contracts (a very likely change, given the project actively evolves this gateway, as shown by the same relayer-allowlist feature) will insert that variable ahead of every state variable declared in whichever base contract comes later in the linearization, shifting all subsequent slots — corrupting `_filled`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, and `_relayer` on the live proxy.

This mirrors the reported OpenQ bug class exactly: an upgradeable contract's storage layout depends on base contracts inherited without gap slots, exposing every future upgrade to storage corruption.

### Impact Explanation
A storage-shifting upgrade on the live `IntentGatewayV2` proxy would corrupt the interpretation of `_filled`, `_orders`, and `_relayer`. Concretely:
- `_orders[commitment][token]` values (escrowed user/solver funds) could be reinterpreted as unrelated data, permanently freezing or misdirecting escrowed funds on redemption/refund.
- `_relayer`, which gates every `onAccept`/`onGetResponse` delivery, could be corrupted to zero (reopening the gate to any relayer) or to an arbitrary address (permanently locking out the legitimate relayer), undermining the entire delivery-authorization model described in the project's own flow docs [6](#0-5) .
- The cross-chain cancellation proof, hard-coded against slot 2 for `_filled`, would silently prove against corrupted data, breaking cancel/refund logic or enabling forged proofs against stale slot contents.

This qualifies as concrete theft/freezing of escrowed intent funds and forged/unsound message authorization upon a routine future upgrade — a Medium-severity storage-safety defect consistent with the reported bug class.

### Likelihood Explanation
The likelihood is tied to future maintenance rather than an immediately exploitable transaction, matching the reported issue's own framing ("exposing bounties to the risk of potential storage overlap/corruption in future upgrades"). Given the project's demonstrated pattern of actively adding new persistent state to these exact base contracts (the recent `_relayer` addition itself), and the total absence of `__gap` reservations anywhere in the intent-gateway inheritance chain, the probability of an eventual unsafe layout change is non-trivial, and the live-mainnet proxy that already underwent one governance-driven upgrade path is the concrete asset at risk.

### Recommendation
Add explicit storage gaps to every base contract in the inheritance chain of `IntentGatewayV2` that declares persistent storage, sized to the OpenZeppelin convention:
```solidity
// IntentsBase.sol, IntrinsicIntents.sol, ExtrinsicIntents.sol
uint256[50] private __gap;
```
Alternatively, migrate `IntentsBase`'s storage to an ERC-7201 namespaced storage struct (as OpenZeppelin's newer upgradeable contracts, including `Initializable` itself, already do), which removes the ordering-dependency risk entirely regardless of future inheritance changes. Document the chosen gap size and enforce it in CI (e.g., via `forge inspect storage-layout` diffing) so any base-contract change that would shift slots fails the build before deployment.

### Proof of Concept
1. `IntentGatewayV2` is deployed as an `ERC1967Proxy` and already upgraded once on mainnet via the `Execute`/`upgradeToAndCall` governance path [7](#0-6) .
2. Its storage layout is fixed by inheritance order: `IntrinsicIntents, ExtrinsicIntents, ReentrancyGuardTransient, Initializable`, all ultimately deriving from `IntentsBase` [1](#0-0) .
3. `IntentsBase` declares no gap slots after its seven state variables (`_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer`) [2](#0-1) .
4. Suppose a future upgrade adds a new implementation contract `IntentGatewayV3` that adds a state variable to `IntentsBase` (e.g., a new fee-accounting field) to support a feature request — a realistic scenario given the team already added `_relayer` this way. Compiling that new implementation and deploying it via the exact same `upgradeToAndCall` governance flow exercised in `testOnAcceptUpgradeContractPreservesState` [8](#0-7)  would silently shift every slot after the insertion point.
5. Post-upgrade, `intentGateway._filled(commitment)`, `intentGateway._orders(commitment, token)`, and `intentGateway.relayer()` would read from the wrong slots relative to the data written by the pre-upgrade implementation — the exact assertions the existing test suite currently uses to prove state preservation (`_filled preserved`, `_orders preserved`, `relayer survives the upgrade`) would fail, demonstrating escrow and relayer-gate state corruption.

```markdown
# 2026-09-03 — The relayer is a separate storage variable, not a `Params` field

Chosen: `address _relayer` appended after `_paused` in `IntentsBase`, set through its own
`setRelayer` call.

`Params` occupies slots 4 to 8 and `_orders` starts at slot 9. Adding a field to the struct would
push every mapping behind it and corrupt escrow on the live proxy. Reusing `UpdateParams` was
therefore never available, quite apart from it being a Hyperbridge-relayed message: the whole point
is to hold even if Hyperbridge's consensus is compromised, so the setter must not depend on it.
```
