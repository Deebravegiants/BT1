### Title
Duplicate `NewRaise` entry via `poke` + `contribute` causes double `place_bid` execution per block - (File: polkadot/runtime/common/src/crowdloan/mod.rs)

### Summary
`Crowdloan::poke` unconditionally checks `NewRaise` for a duplicate and appends the `para_id`, but it never updates `fund.last_contribution`. If an unprivileged caller then calls `contribute`/`contribute_all` on the same fund in the same block, `do_contribute`'s duplicate-suppression logic (which is driven solely by `last_contribution`, not by inspecting `NewRaise` itself) fails to detect the entry `poke` just added, and appends the same `para_id` to `NewRaise` a second time. This causes `on_initialize` to call `T::Auctioneer::place_bid` twice for the same fund/para within a single block.

### Finding Description
`poke` (call_index 7) is reachable by any signed account for any `para_id` with a non-zero `raised` fund, and only guards against re-appending by checking `NewRaise::<T>::get().contains(&index)`: [1](#0-0) 

Crucially, `poke` does **not** update `fund.last_contribution`, unlike `do_contribute`, which uses `last_contribution` as the sole signal for whether the fund is "already in `NewRaise`": [2](#0-1) 

In the ending-period branch, the code only skips the `NewRaise::append` if `fund.last_contribution == LastContribution::Ending(now)`. Since `poke` never sets this field, any subsequent `contribute` call by the same attacker (or anyone) in the same block on the freshly-poked fund will find `last_contribution` still equal to its pre-poke value (`Never`, `PreEnding(_)`, or `Ending(old_block)`), fall into the `_ =>` arm, and call `NewRaise::<T>::append(index)` again — producing a duplicate entry for the same `para_id` in the `Vec<ParaId>` stored in `NewRaise`.

At the next `on_initialize`, `NewRaise::<T>::take()` retrieves this vector with the duplicate, and the loop iterates over it without deduplication: [3](#0-2) 

Because `filter_map` maps every entry (duplicates included) to `(fund, para_id)`, `T::Auctioneer::place_bid` is invoked twice with identical arguments for the same fund/para within a single block. There is no protection at the `on_initialize` level that deduplicates `new_raise`, and no protection in `do_contribute` that checks `NewRaise` membership directly (it fully trusts `last_contribution` bookkeeping, which `poke` bypasses).

### Impact Explanation
Each duplicate call executes the full `place_bid` logic and emits an extra `HandleBidResult` event, doubling the weight cost of `on_initialize` for that fund relative to what `T::WeightInfo::on_initialize(new_raise_len)` should represent for legitimate, unique entries — this weight is charged in the `Mandatory` dispatch class of a hook, which cannot be skipped/throttled by normal block weight limits. An attacker can repeat `poke` + `contribute` every block throughout the ending period (since `NewRaise` is drained/emptied each `on_initialize`, re-enabling `poke`'s duplicate check to pass again), amplifying wasted weight/PoV in the auction-ending hot path across many funds, which is the scoped "auction state corruption / wasted weight, potential DoS on auction ending-period processing" impact. This also breaks the intended invariant that each fund submits a bid at most once per block during the ending period.

### Likelihood Explanation
The attack requires only an active auction in its ending period and a fund with non-zero `raised` (trivially achievable, since any contributor, including the attacker themselves, can create this precondition via a prior `contribute`). Both `poke` and `contribute` are permissionless, signed-origin extrinsics with no rate limiting beyond normal transaction fees, and the sequence (`poke` then `contribute` within the same block) is fully attacker-controlled and repeatable every block of the ending period for every active fund.

### Recommendation
Make `poke` and `do_contribute` share a single source of truth for "is this fund already in `NewRaise`" — e.g., have `poke` also set `fund.last_contribution = LastContribution::Ending(now)` (or `PreEnding(endings_count)` outside the ending period) before appending, matching exactly what `do_contribute` would have set, so the subsequent `do_contribute` check correctly detects the fund is already queued and skips the second `NewRaise::append`. Alternatively, have `do_contribute` check `NewRaise::<T>::get().contains(&index)` directly instead of relying purely on `last_contribution`.

### Proof of Concept
Rust unit test in `polkadot/runtime/common/src/crowdloan/mod.rs` test module:
1. Set up an active auction and put it into its ending period (`set_ending_period`, mock `TestAuctioneer`).
2. `create` a fund and `contribute` once (pre-ending) so `fund.raised > 0`, then advance blocks so it's a fresh block within the ending period.
3. In one block: call `Crowdloan::poke(signed(attacker), index)`, then `Crowdloan::contribute(signed(attacker), index, MinContribution)`.
4. Assert `NewRaise::<Test>::get().iter().filter(|&&p| p == index).count() == 1` fails (shows it's `2`), demonstrating the duplicate.
5. Advance to next block and trigger `on_initialize`; assert `bids()` (the mock's bid-tracking vector) contains exactly one `BidPlaced` entry for `index` at that height — the test will show two identical entries instead, proving `place_bid` was invoked twice for one fund in one block.
