### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC validated by `Utils::HmacValidator` authenticates the payload bytes but never binds them to the `shop-domain` header that `Registry.process` later trusts as the tenant identifier. An attacker who legitimately receives one valid webhook (e.g., by installing the app on their own store) can replay that same body+HMAC pair while substituting an arbitrary victim `shop-domain` header, and the library will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
`shop` is read straight from an unauthenticated header, with no relation to the signed content: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the raw body) using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

`Registry.process` checks that HMAC, then unconditionally forwards the unauthenticated `request.shop` value into the handler as the tenant identity: [5](#0-4) 

Because the HMAC secret (`Context.api_secret_key`) is the same for every shop that has installed a given app — not a per-shop secret — any merchant who installs the app on their own store can capture a legitimately-signed webhook (valid `raw_body` + valid `hmac`) and resend it directly to the app's public webhook endpoint with the `shopify-shop-domain`/`x-shopify-shop-domain` header changed to any other shop's domain. `HmacValidator.validate` will still succeed (it only checks the body against the shared secret), and `Registry.process` will hand the forged `shop` value to the application's webhook handler as if Shopify itself asserted that identity for that shop.

This breaks the intended binding: `authenticated_body == authenticated_shop` is assumed by `Registry.process`, but the code only proves `authenticated_body == signed_by_app_secret`; `shop` is attacker-controlled and never covered by the HMAC.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which tenant's data/session/access token to act on (the документed, and only, mechanism this gem exposes for webhook tenant scoping) can be tricked into operating on behalf of a victim shop using attacker-supplied body content. This is a cross-tenant confusion/access primitive: an unprivileged attacker who has merely installed the app once can make the app process fabricated events "from" any other shop, without ever needing that shop's credentials.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the target app on a store they control (a normal, unprivileged action for any Shopify merchant/developer), since that is sufficient to obtain a valid `raw_body`+`hmac` pair. No access to `api_secret_key`, tokens, or the victim's account is required — only the ability to send an HTTP POST directly to the app's public webhook URL with modified headers.

### Recommendation
Include the shop identity (and other trust-relevant headers, e.g., topic, api-version, webhook-id) in the HMAC-covered signable content, or otherwise cryptographically bind the asserted `shop-domain` header to the signature before `Registry.process` passes it to handlers. At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against a known/installed-shop list before being trusted for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic, capturing the raw request body `B` and the legitimately computed header `shopify-hmac-sha256: H` (valid because it's HMAC-SHA256(`B`, app's shared `api_secret_key`)).
2. Attacker POSTs directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `shopify-hmac-sha256: H` (unchanged, still valid)
   - Header `shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `shopify-topic`, `shopify-webhook-id`: as needed
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `B`, and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the request never originated from Shopify or from the victim shop.
