### Title
Truncated/non-standard user identifiers are accepted by the User QR-code parser and propagated to signup, cryptographic signing, and data-upload flows without full-UUID validation - (File: src/plans/qr_scan/user.rs)

### Summary
The external report describes `ERC20Vault`/`ERC721Vault` accepting non-standard token metadata (`bytes32` instead of `string`, or empty values) without proper validation, causing malformed data to be silently accepted and propagated downstream where it later breaks or misattributes state. The analogous root cause exists in orb-core's `Data::try_parse` for user QR-codes: a fallback regex (`QR_CODE_V2`) accepts a deliberately shortened, low-entropy "user_id" that does not conform to a full UUID, and this unvalidated value is then used as the trust anchor for signup attribution, custody-package tagging, and cryptographic signing.

### Finding Description
`QR_CODE_V2` in [1](#0-0)  defines the last two UUID groups as optional (`(?: - [a-z0-9]{4} - [a-z0-9]{12})?`), so a code like `userid:3bcf883d-ce22-4a03:1` matches and yields `user_id = "3bcf883d-ce22-4a03"` — confirmed by the repo's own test `test_v2_shortened` [2](#0-1) .

`Data::try_parse` first attempts the strict, cryptographically-backed `decode_qr` path, and only falls back to this loosely-validated regex if that fails [3](#0-2) . `from_v2` performs no additional length/format check before accepting the captured string as the canonical `user_id` [4](#0-3) .

This `user_id` string is then propagated, unchecked, into security- and identity-critical paths:
- It is sent as `userId`/`distributorId` in the actual signup creation request to the backend [5](#0-4) .
- It is mixed directly into the SHA-256 context that is signed by the secure element to produce the iris-code signature, binding the (possibly truncated/low-entropy) identifier cryptographically to the biometric data [6](#0-5) .
- It tags the personal-custody package uploads that carry the encrypted iris/biometric package tiers [7](#0-6)  and [8](#0-7) .
- It is used as the path segment for the operator/distributor status validation endpoint [9](#0-8) .

This exactly mirrors the bug class in the report: an entity boundary (ERC-20 metadata / user QR-code identifier) accepts non-standard/degenerate input without normalizing or rejecting it, and the degraded value is then trusted by downstream systems that assumed a fully-specified identifier.

### Impact Explanation
A drastically shortened identifier (16 hex characters vs. the full 32-hex-character UUID) has far lower entropy and a materially higher collision probability. Since this value becomes the durable "user_id" tied to the biometric signature, the custody package, and the backend signup record, two distinct signup sessions could end up bound to the same truncated identifier — resulting in misattributed signup data or cross-signup state bleed (one user's biometric package/signature associated with another user's `user_id`). This aligns with the accepted impact classes: misattributed signup and cross-signup state bleed.

### Likelihood Explanation
The shortened form is reachable through the normal, unprivileged QR-scanning flow available to any user/operator presenting a QR code during signup — no special access or hardware manipulation is required. It only requires generating a QR code whose text matches the loosened regex, which is straightforward since the format is documented in the same source file.

### Recommendation
Enforce full UUID validation (all five groups, correct total length, and ideally UUID-parse via the `uuid` crate) in the `QR_CODE_V2` fallback path before accepting a scanned code, rejecting truncated/non-standard identifiers rather than silently accepting them the same way a canonical `decode_qr`-produced UUID would be accepted. Alternatively, remove the optional group entirely so it structurally cannot match anything but a complete UUID.

### Proof of Concept
1. Craft a QR code with text `userid:3bcf883d-ce22-4a03:1` (missing the last two UUID groups).
2. Present it during the user QR-code scan phase; `decode_qr` fails, so `QR_CODE_V2.captures` is tried and succeeds, producing `Data { user_id: "3bcf883d-ce22-4a03", .. }` (as shown by the existing `test_v2_shortened` unit test) [2](#0-1) .
3. This truncated `user_id` flows unmodified into `signup_post::request` (backend signup identity) [10](#0-9) , into `make_signature` (cryptographic binding of biometric data) [6](#0-5) , and into the personal-custody-package upload pipeline [11](#0-10) , all without any additional entropy/format check.

    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
