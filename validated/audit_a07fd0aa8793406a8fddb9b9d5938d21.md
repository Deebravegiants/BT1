This is the strongest analog found, and it directly maps to the bug class in the report: a low-total-weight "voting" pool that a single actor with modest absolute holdings can dominate, and use that dominance to set a value other on-chain logic then trusts and acts upon.

### Title
Weighted-median phantom price oracle allows a solver holding over half a leg's inventory weight to unilaterally set the published exchange rate used for pool liquidity/rate accounting - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The phantom-order price discovery pipeline (`aggregatePhantomBids` → `weightedMedian`) computes a per-leg price by taking a liquidity-weighted median of solver bids, where weight is the bidding solver's on-chain balance of the leg's output token. Exactly like the reported `BaseERC20Guild` issue — where a low `totalLocked` lets an attacker cheaply become the "observed voting majority" — a leg with low total backing weight (few or no competing solvers, or solvers with thin balances) lets a single solver acquire "majority weight" cheaply and have `weightedMedian` return its own quoted price verbatim, unchecked by any minimum-liquidity or minimum-participant floor.

### Finding Description
`weightedMedian` in [1](#0-0)  is a *selection*, not a blend: it walks quotes sorted by price and returns the exact price of whichever quote's cumulative weight first reaches half of `totalWeight`. As the code comment itself states, "a solver holding over half the leg's weight sets the published price verbatim" (also documented in [2](#0-1) ).

Weight is computed purely from the bidding solver's own instantaneously-readable balance of the leg's output token (`getBalance`) plus any owned Uniswap V4 position value, per [3](#0-2) . There is no floor on `totalWeight`, no minimum number of distinct backed bidders, and no cap on any single solver's weight share before the median gate is applied — the only filters are "drop zero-weight quotes" and "drop legs with zero backed quotes" ( [4](#0-3) ). This is functionally identical to `BaseERC20Guild`'s reliance on `getTotalLocked()` without a lower bound: when the "pool" (here, per-leg backing liquidity) is small — a new pair, a thin chain, or a leg most solvers decline to quote — one solver can trivially hold >50% of the weight with modest capital and dictate the published price.

That published `medianPrice` then feeds `updateLiquidityPools`, which converts it directly into `PoolChainLiquidity`/`LiquidityPool` `sellRate`/`buyRate` rows via `resolvePoolLeg` and `weightedRate` (documented in [5](#0-4) ), i.e., an unbacked or manipulated oracle price becomes the on-chain-consumed liquidity/rate signal for the pool, downstream of a single dispatched price snapshot.

### Impact Explanation
A solver that can cheaply dominate weight on a thinly-backed leg can post an arbitrarily skewed price (subject only to the ±haircut filters), which becomes `medianPrice`/`lowestPrice`/`highestPrice` for that leg and is folded into the pool's published `sellRate`/`buyRate`. Any consumer (fillers, UIs, other solvers, or routing/pricing logic) that treats these pool rates as a trusted reference for phantom-order routing or profitability decisions can be misled into overpaying or mispricing, and repeated manipulation compounds into the depth-weighted mean at the pool level. This is analogous to a low-quorum governance/voting takeover translated into price-oracle takeover — a medium/high-severity issue for any actor relying on the published rate for financial decisions.

### Likelihood Explanation
Likelihood is proportional to how thin the leg's backing liquidity is at bid-window close: new pairs, low-volume chains, or legs where competing solvers decline to quote are common in a permissionless intents marketplace, and any funded solver can simply hold sufficient balance of the output token to cross 50% of that leg's weight — no special privilege or governance access is required, only capital sized to the (potentially small) total weight.

### Recommendation
Introduce a configurable minimum total backing weight (or minimum distinct-solver count) per leg before `weightedMedian` is trusted to publish a price, mirroring the `minimumTokensLockedForProposalCreation`/`minimumMembersForProposalCreation` mitigation adopted for `BaseERC20Guild`. Additionally consider capping any single solver's contributing weight share (e.g., clamp to some percentage of total) so one solver cannot single-handedly set the exact price even when it legitimately holds a majority of currently-available liquidity, and surface/flag snapshots computed from low-weight legs to downstream consumers rather than treating them identically to well-backed ones.

### Proof of Concept
1. For a given phantom order leg (token pair) with low aggregate solver liquidity — e.g., only one or two other solvers hold trace balances of the output token — an attacking solver funds an account with a modest amount of the output token on the destination chain (enough to exceed 50% of `totalWeight` across all backed quotes for that leg).
2. The attacker submits a bid quoting an arbitrarily favorable-to-itself price for that leg (bounded only by the haircut logic in `applyHaircut`).
3. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids` computes weights per [3](#0-2)  and `weightedMedian` ( [1](#0-0) ) returns the attacker's exact quoted price because its cumulative weight crosses the 50% threshold first.
4. `updateLiquidityPools` writes this manipulated `medianPrice` into `PoolChainLiquidity`/`LiquidityPool` rate rows, which are then consumed by other actors as the trusted market rate for that pair — as confirmed by the unit test demonstrating this exact mechanic in [6](#0-5) .

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
