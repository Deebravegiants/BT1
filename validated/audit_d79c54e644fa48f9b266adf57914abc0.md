### Title
Webhook shop-domain header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw, unauthenticated HTTP headers, while `to_signable_string` (the value the HMAC actually protects) is only the raw request body. `Webhooks::Registry.process` accepts the request as authentic once the HMAC check passes and then forwards `request.shop` unchanged into `WebhookMetadata`, which app handlers use to determine which tenant the payload belongs to. This is the same class of flaw as the reported Solana bug: a value that is *acted on* (here, the tenant-identifying `shop` field) is not covered by the integrity check that is supposed to authenticate the whole message (`pool.amount` vs `shared_escrow`; here, `shop` header vs HMAC-signed body).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cross-check against the signed payload: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The broken identity binding is:
`shop header used by handler.handle(shop: request.shop)` **≠** `shop covered by HMAC(to_signable_string)`

Because the webhook endpoint is a normal public HTTP endpoint, any internet client — not just Shopify — can POST to it. An attacker who installs the target app on their own (even free/dev) store receives genuine webhooks for that store, each with a body and a valid HMAC computed with the real `api_secret_key`. Since the header value `shop-domain` is not part of the signed content, the attacker can replay the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim shop). `HmacValidator.validate` still succeeds because the body/hmac pair is unchanged and valid, and `Registry.process` will call the handler with `shop: <victim-domain>`, `body: <attacker-controlled/attacker's-own-shop payload>`, and a webhook_id/topic of the attacker's choosing.

Downstream app code (per this gem's own documented usage pattern) uses `WebhookMetadata#shop` as the tenant key to route/persist webhook data (e.g., look up the corresponding merchant record and apply the payload). This lets the attacker inject or overwrite data under another merchant's identity despite never possessing that merchant's secret or session — a cross-tenant confusion enabled purely by a gap in what the HMAC covers, mirroring the reported bug's "checked field vs. field that actually holds the truth" mismatch.

### Impact Explanation
This crosses a tenant boundary: an unprivileged attacker (needs only a free store install of the target app to obtain one valid signed webhook) can make the app process attacker-controlled webhook data under a victim shop's identity. This matches the "Critical – cross-tenant access" impact bucket, since the gem's `Registry.process`/`WebhookMetadata` API misrepresents an unauthenticated header as though it were verified alongside the signed body.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) allows public/free installs (most public apps do) and (b) uses `WebhookMetadata#shop` to key persistence/authorization decisions, which is the documented, expected usage of this API. No secret material beyond a self-obtained legitimate webhook is required; the attack is a straightforward header substitution on a replayed HTTP POST.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered content, or otherwise require the caller to independently verify `request.shop` against a value obtained through an authenticated channel (e.g., matching against the session/store on file) before trusting it — do not let `Webhooks::Request` expose header-derived `shop` as if it were part of the verified payload without documenting this gap loudly. At minimum, update `to_signable_string`/`HmacValidator` so verification failure is raised whenever `shop`/`topic`/`webhook_id` cannot be corroborated by data already known for that store.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a real webhook. The app's endpoint (or a proxy the attacker controls, e.g. a request-catching webhook forwarder they configure during install) yields a valid `(raw_body, shopify-hmac-sha256)` pair signed with the real `api_secret_key`.
2. Attacker crafts their own HTTP POST directly to the victim app's public webhook URL, reusing the untouched `raw_body` and `shopify-hmac-sha256` value from step 1, but sets header `shopify-shop-domain: victim-shop.myshopify.com` (and optionally any `shopify-topic`/`shopify-webhook-id` values).
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `HmacValidator.validate` succeeds because `to_signable_string` (body) and `hmac` still match: [5](#0-4) 
4. The handler executes with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, letting the attacker inject data attributed to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
