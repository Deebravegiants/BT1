## Title
Hyper-Fungible-Token decimal-scaling uses `saturating_sub` for a signed exponent, enabling unbacked mint / value-destroying transfers when a registered chain's ERC20 decimals are lower than the local asset decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount conversion helpers, `convert_to_balance` and `convert_to_erc20`, compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. When a token is registered with `erc_decimals < local_decimals` (a legitimate, admin-set configuration for any asset whose EVM representation uses fewer decimals than its local `pallet-assets`/native precision — e.g. a locally 18-decimal asset bridged to a 6-decimal EVM token), the exponent saturates to zero and the conversion silently degenerates into a no-op instead of the required division/multiplication. This causes `send()` to encode a grossly inflated ERC20 amount that gets minted/unlocked on the destination EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, while only a negligible amount was escrowed or burned locally — an unbacked mint that makes the bridge "market" for that asset insolvent.

### Finding Description
`convert_to_erc20` (used by the `send` extrinsic, local → EVM direction) and `convert_to_balance` (used by `on_accept`/`on_timeout`, EVM → local direction) both derive the scaling power with `saturating_sub`: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals`. `erc_decimals.saturating_sub(local_decimals)` clamps to `0` whenever `erc_decimals < local_decimals`, turning the intended scale factor of `10^(local_decimals - erc_decimals)` into `10^0 = 1`. There is no reciprocal division/multiplication on the other branch to compensate.

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` to build the outbound message body that is dispatched to the destination `HyperFungibleToken` contract, which mints (or unlocks) exactly `message.amount` on `onAccept`: [2](#0-1) [3](#0-2) 

`register_token`/`update_token` let a `CreateOrigin` register any `(local_id, chain, decimals)` combination — there is no validation anywhere enforcing `chains[].decimals >= local asset decimals`: [4](#0-3) 

For any asset legitimately configured with `erc_decimals < local_decimals` (a normal, non-malicious configuration — e.g. bridging an 18-decimal native/`pallet-assets` token to an EVM chain where the paired ERC20 uses 6 decimals), a user calling `send()` with a small local `amount` (escrowed for native assets, burned for non-native) produces `erc20_amount = amount` unchanged instead of `amount / 10^(local_decimals - erc_decimals)`. When interpreted at the destination's (coarser) decimal precision, this raw value represents a value up to `10^(local_decimals - erc_decimals)` times larger than what was actually locked/burned, and that inflated amount is unconditionally minted/unlocked on the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract via `onAccept`.

### Impact Explanation
This breaks the fundamental accounting invariant of the hyper-fungible-token bridge — that minted/unlocked supply on one side is always backed 1:1 by escrowed/burned supply on the other. Any unprivileged holder who can call the pallet's `send` extrinsic can mint an arbitrarily inflated amount of the bridged ERC20 token on the destination chain while paying only a negligible real amount, draining the token's backing and rendering the bridge for that asset insolvent (per the report's definition — collateral/backing worth less than issued liabilities). This is a direct path to theft/unbacked-mint of funds, matching the "Critical/High: forged message delivery / unsound state commitment / unbacked mint" impact class.

### Likelihood Explanation
The trigger condition (`erc_decimals < local_decimals` for a registered chain) is not an attacker-controlled or malicious-admin condition — it is a plausible, ordinary token registration outcome, since `local_decimals` (native currency decimals, or a `pallet-assets` asset's own decimals) and `erc_decimals` (the EVM contract's decimals for that chain) are independently configured and there is no cross-check preventing the EVM side from using fewer decimals than the local asset. Any signed account can then call `send` with attacker-chosen amounts; no privileged role is required to exploit it once such a token/chain pair exists.

### Recommendation
Fix the scaling direction to be symmetric and always correct regardless of which side has more decimals: compute a signed difference and either multiply or divide accordingly (e.g. `if erc_decimals >= local_decimals { value * 10^(erc_decimals-local_decimals) } else { value / 10^(local_decimals-erc_decimals) }`), applying the same logic (with the operations swapped) in `convert_to_balance`. Additionally, consider validating in `register_token`/`update_token` that decimal configurations cannot silently zero out scaling, and add round-trip tests asserting `convert_to_balance(convert_to_erc20(x, e, l), e, l) == x` for all `e`, `l` orderings.

### Proof of Concept
1. Admin registers a non-native asset with `local_decimals = 18` (pallet-assets) and `chains[EVM].decimals = 6` via `register_token`.
2. Attacker calls `send(SendParams { asset_id, amount: 1_000_000_000_000 /* 1e12, i.e. 0.000001 of a local token at 18 decimals */, destination: EVM, ... })`.
3. In `send()`, `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `convert_to_erc20` returns `1_000_000_000_000 * 10^0 = 1_000_000_000_000` unchanged.
4. The dispatched `Message.amount = 1_000_000_000_000` is delivered to the destination `HyperFungibleToken` contract, which is decimals-18 by default (or whatever configured), and `_mint(beneficiary, 1_000_000_000_000)` executes — but the equivalent real-world value locked locally was only `1e12 / 1e18 = 0.000001` token, while it should have produced `1_000_000_000_000 / 10^(18-6) = 1` unit at 6-decimal precision on the EVM side; instead the destination mint is denominated at whatever decimals the destination contract uses, over-crediting the attacker relative to what was actually escrowed/burned locally.
5. Repeating this with larger nominal `amount` values scales the over-mint linearly, draining backing for the asset on the destination chain.
