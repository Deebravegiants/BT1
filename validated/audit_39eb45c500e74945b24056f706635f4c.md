## Title
Webhook shop-domain identity is not cryptographically bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`/`webhook_id`) values that are handed to the host application's webhook handler are read from HTTP headers that are **not** covered by that HMAC. An unprivileged internet user who can obtain one valid `(raw_body, hmac)` pair signed by the app's `api_secret_key` — trivially achievable by installing the app on a shop they control — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. The library will accept the request as authentic and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
The equality the code implicitly assumes but never enforces is:

`shop used for HMAC verification == shop delivered to the handler`

In practice this becomes:

`shop covered by HMAC (∅, not present) != shop trusted by WebhookMetadata (request.shop, from an unauthenticated header)`

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers, with no cryptographic linkage to the signed body: [2](#0-1) 

- `Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) to build the metadata object passed to the app's handler: [3](#0-2) 

- `HmacValidator.validate_signature` confirms only that `verifiable_query.to_signable_string` (the raw body) matches the received HMAC — it never incorporates the shop header: [4](#0-3) 

Because the `api_secret_key` is shared by the app across **all** installing shops, any tenant that installs the app can legitimately receive Shopify-signed `(body, HMAC)` pairs for their own shop. Nothing in this gem prevents that pair from being replayed against the same public webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header pointing at a different, victim tenant of the same app. The HMAC check passes because it only verifies body integrity, and `Registry.process` never cross-checks that the shop claimed in the header is the shop the body/HMAC pair was actually generated for.

### Impact Explanation
This breaks the tenant identity boundary between shops of a multi-tenant app: a webhook that the host application believes originates from shop B can actually be attacker-controlled content originating from shop A (which the attacker owns). Any application logic that uses `WebhookMetadata#shop` to select which tenant's data/session to mutate can be tricked into applying attacker-chosen payload data to a victim shop's records — a cross-tenant access/data-integrity issue, which the rules classify as Critical-level impact (cross-tenant access).

### Likelihood Explanation
Exploitability only requires: (1) attacker installs the target app on their own shop (a normal unprivileged action, no special access to the victim or to `api_secret_key`), and (2) attacker's shop generates a webhook with attacker-chosen body content, which they capture and replay to the app's known public webhook URL with a modified shop-domain header. No secrets, tokens, or victim credentials are needed — only the webhook endpoint being reachable, which it inherently is (it's designed to accept internet-facing POSTs from Shopify).

### Recommendation
Bind the shop (and ideally topic) into the value that's authenticated, or explicitly cross-validate `request.shop` against an out-of-band trusted mapping (e.g., verify the shop belongs to an actually installed session before dispatching) rather than trusting the header value implicitly once the body HMAC passes. At minimum, document that host applications must independently verify `WebhookMetadata#shop` corresponds to a shop with a legitimately stored session/access token before using it to key any data access, since the gem's HMAC check does not vouch for the shop header's authenticity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order with attacker-chosen note/body content) so Shopify sends a legitimately signed webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `B` and `H`, then sends their own POST directly to the app's public webhook endpoint with the same `B`/`H` but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes. [3](#0-2) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body `B`, even though `victim.myshopify.com` never sent this webhook.
