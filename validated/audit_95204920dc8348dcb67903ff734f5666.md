This looks like a genuine, concrete bug: the Tron variant of `IntentGatewayV2.instance()` fails open for unregistered peer chains instead of reverting. Let me confirm by reading the full file and comparing to the canonical EVM implementation.## Title
`IntentGatewayV2.instance()` fails open for unregistered peer chains, letting a forged cross-chain message from any unknown source state machine be treated as authenticated - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The analog matches the CVE's bug class: an entity that is not (yet) properly registered/approved is nonetheless treated by the authorization check as if it were trusted. Here, an IntentGateway peer chain that has never been registered via a `NewDeployment` governance message defaults to being treated as `address(this)` — the gateway's own address — instead of being rejected, in `instance()`:

```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:284-300
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

### Finding Description
The canonical/mainline EVM `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol:401-405`) implements the equivalent lookup so that an unregistered peer state machine causes a hard revert:

```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
``` [1](#0-0) 

The Tron variant instead **fails open**: any state machine id that has not gone through `NewDeployment` governance registration resolves to `address(this)`, and `authenticate()` will accept any incoming `PostRequest` whose `request.from` field equals `address(this)` (the gateway's own address, encoded as 20 bytes), regardless of what `request.source` actually is. [2](#0-1) 

Because `IntentGatewayV2` is deliberately deployed at a deterministic CREATE2 address that is intended to be identical across every chain the protocol supports (documented in the mainline contract's constructor comment: "must be identical across chains or the deterministic proxy address diverges"), `address(this)` is a fixed, publicly known value ahead of time. [3](#0-2) 

This means: for any state machine that (a) Hyperbridge's ISMP host already trusts/verifies consensus for, but (b) has not yet been registered as an `IntentGateway` peer/deployment via `_addDeployment`/`NewDeployment` — i.e. exactly a "pending" counterpart in this protocol's terms — the `authenticate()` check silently passes as long as the forged message's `from` field is set to the well-known deterministic gateway address. The actual identity/registration state of the source-side contract is never checked; the message is authenticated purely by matching a hardcoded fallback value.

### Impact Explanation
`authenticate()` gates every privileged `onAccept`/`onGetResponse` branch that this app trusts cross-chain input for: `RedeemEscrow` (releases escrowed input tokens + fees to a solver), `RefundEscrow` (refunds escrow to a user), `NewDeployment` (registers new peer gateways), `UpdateParams` (fee/config governance), and `SweepDust`. If an attacker can get any message accepted by the local Hyperbridge host with `source` equal to a state machine the host already has a live consensus client for, but for which this gateway has no registered peer entry, and set `from = address(this)`, the authentication check is bypassed and the message is treated as coming from a legitimate sibling gateway. This can be used to forge `RedeemEscrow`/`RefundEscrow` deliveries, draining escrowed user funds to an attacker-chosen beneficiary/solver, or to inject a fraudulent `NewDeployment`/`UpdateParams` record, corrupting protocol configuration or peer trust — a direct theft-of-funds / unsound-state-commitment class of impact matching the "concrete theft or unauthorized app action" bar.

### Likelihood Explanation
Exploitability depends on whether an attacker can actually get the ISMP host to deliver a `PostRequest` whose `source` is a state machine for which no IntentGateway deployment was ever registered, while the host still accepts/verifies consensus proofs for that state machine (e.g., a chain onboarded to Hyperbridge generally, but where the IntentGateway app was deployed later, or where governance simply never called `NewDeployment` for it — a realistic operational sequencing gap given that peer registration is a separate governance step from chain onboarding). Given `IntentGatewayV2` is explicitly deployed at the same deterministic address across all supported chains, an attacker does not need to guess or brute-force `address(this)`; it is a known, fixed constant, which raises likelihood significantly once such a state-machine/registration gap exists.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the mainline behavior in `IntentsBase.sol`: revert (e.g. `UnknownInstance`/`Unauthorized`) when `_instances[keccak256(stateMachineId)] == address(0)`, rather than defaulting to `address(this)`. Authentication for any peer state machine should require an explicit registration record; there should be no "silent success" fallback value.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) at deterministic address `G` via the shared CREATE2 factory/salt, as intended by the protocol's cross-chain deployment scheme.
2. Do **not** call `NewDeployment` to register a peer for state machine `X`, even though the local `IsmpHost`/consensus client already tracks and verifies proofs for `X` (e.g., `X` was onboarded to Hyperbridge generally, but the IntentGateway app peer for `X` was not yet configured — a "pending" registration state).
3. Craft (or, via a colluding/compromised relayer, get delivered) a `PostRequest` with `source = X`, `from = abi.encodePacked(G)` (20 bytes equal to the gateway's own deterministic address), and `body` encoding a `RequestKind.RedeemEscrow` (or `RefundEscrow`/`NewDeployment`) payload naming an attacker-controlled beneficiary/solver and an existing order commitment with escrowed funds.
4. When the host calls `onAccept`, `authenticate(request)` computes `instance(X)`; since `_instances[keccak256(X)] == address(0)`, it returns `address(this) == G`, which equals the forged `module` address recovered from `request.from`. The check `instance(request.source) != module` is `false`, so `authenticate()` does **not** revert.
5. The forged `RedeemEscrow`/`RefundEscrow` body is processed, releasing escrowed tokens to the attacker-chosen beneficiary — despite `X` never having been an authorized IntentGateway peer.

Note: I was not able to fully trace whether Hyperbridge's ISMP host enforces additional source-state-machine allow-listing at the consensus-client layer that would independently block delivery from an unregistered `X` before it reaches `onAccept` on Tron deployments specifically; a Devin session with full repo/build access would be needed to confirm end-to-end reachability against the live host/consensus-client configuration used for Tron deployments.
