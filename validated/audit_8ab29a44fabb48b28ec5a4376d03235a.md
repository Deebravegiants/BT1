### Title
Disabled/removed wallet accounts can still be used to sign transactions and messages because the signing APIs never check `WalletAccount.enabled` - (File: features/tx-signer/src/api/index.ts, features/message-signer/src/module/message-signer.ts)

### Summary
The root cause of the referenced Ethos Network finding is that `verifiedProfileIdForAddress` resolves an address to a profile/authorization identity but never re-checks whether that address has since been marked compromised/removed, so downstream contracts keep trusting it. The same architectural pattern exists in `hydra`'s wallet-accounts / signing stack: `walletAccountsAtom` is the single source of truth for account authorization state (including the `enabled` flag that `walletAccounts.disable()` sets to `false` [1](#0-0) ), but the transaction-signing and message-signing entry points resolve a wallet-account name straight from `walletAccountsAtom` and never filter on `enabled` before handing the account to the signer.

### Finding Description
`transactionSignerApi.signTransaction` accepts a wallet account either as an instance or as a string name. When a string is passed, it is resolved with a raw lookup into `walletAccountsAtom`, asserting only that the entry exists — not that it is `enabled`: [2](#0-1) 
That resolved (possibly disabled) `WalletAccount` is then passed straight into `transactionSigner.signTransaction`, which dispatches to the seed-based or hardware signer based only on `isSoftware`/`isHardware`, again with no `enabled` check: [3](#0-2) 

The exact same pattern exists in the message-signing module: `#normalizeWalletAccount` resolves a string wallet-account name from `walletAccountsAtom` and asserts only that the instance exists, not that it's enabled, before signing an arbitrary message with that account's key material: [4](#0-3) 

Meanwhile, `enabled` is a real authorization gate elsewhere in the codebase: `enabledWalletAccountsAtom` is a derived/filtered view used by UI/selectors to decide which accounts are "active"/usable [5](#0-4) , and `disable()` explicitly flips `enabled: false` for software accounts (only hardware accounts have their public keys actually deleted) [6](#0-5) . This shows the intent of the system is that a disabled account should not be usable — but the signing surfaces (`transactionSignerApi`, `messageSigner`) bypass that intent by reading directly from the unfiltered `walletAccountsAtom` instead of `enabledWalletAccountsAtom`, mirroring exactly the Ethos bug class: an entity resolves an identifier to "valid" state without re-validating its current authorization/compromise status.

### Impact Explanation
If a user disables a wallet account (e.g., because they suspect the underlying seed/hardware key or an associated dApp connection has been compromised, or simply to prevent it from being used, similar in spirit to `deleteAddressAtIndex`/`isAddressCompromised` in Ethos), any caller (headless SDK integration, RPC/provider bridge, or another module) that still references that account's string name can still successfully sign transactions and arbitrary messages with it, because neither `transactionSignerApi.signTransaction` nor `messageSigner.signMessage` re-checks the `enabled` flag. This is a direct unauthorized-signing / wallet-authorization-bypass condition: funds can be moved and messages (which may themselves be authorization/auth-bypass primitives, e.g., SIWE-style login messages) can be signed for an account the user explicitly intended to disable.

### Likelihood Explanation
Likelihood depends on whether any caller path (headless consumer app, provider/dApp bridge, or an internal module) can supply an account name string that corresponds to a disabled account. The API signature explicitly supports passing `walletAccount` as a plain string, and the wallet-accounts feature exposes `disable()` while `walletAccountsAtom` (the unfiltered atom) remains an injectable dependency to the signer APIs — so this is architecturally reachable without any privileged access, requiring only a caller that still holds a reference to the disabled account's name (e.g., a previously connected origin, cached UI state, or a queued signing request created before disable() was called). I could not fully verify from the indexed files which concrete UI/RPC caller passes a stale/disabled account name at runtime, so likelihood is moderate rather than confirmed-exploited.

### Recommendation
In `transactionSignerApi.getWalletAccount` (features/tx-signer/src/api/index.ts) and `MessageSigner#normalizeWalletAccount` (features/message-signer/src/module/message-signer.ts), resolve/validate wallet account names against `enabledWalletAccountsAtom` (or explicitly check `walletAccount.enabled`) rather than the raw `walletAccountsAtom`, and throw if the account is disabled — mirroring the Ethos Network fix of adding an explicit "not compromised/not revoked" check before any authorized operation proceeds.

### Proof of Concept
Not executable from static analysis alone; conceptually:
1. Create/enable a software wallet account (e.g., `exodus_1`) and cache its name in a caller.
2. Call `walletAccounts.disable('exodus_1')` — `enabled` becomes `false` [1](#0-0) .
3. Call `transactionSignerApi.signTransaction({ walletAccount: 'exodus_1', ... })` or `messageSigner.signMessage({ walletAccount: 'exodus_1', ... })` using the cached name.
4. Observe the transaction/message is signed successfully because `getWalletAccount`/`#normalizeWalletAccount` only assert existence, not `enabled` [2](#0-1) [7](#0-6) .

    const currentWalletAccounts = await this.#getInternalWalletAccountsWithFallback()

    const walletAccounts = { ...currentWalletAccounts }

    await this.setActive((oldValue) =>
      walletAccountNames.includes(oldValue) ? WalletAccount.DEFAULT_NAME : oldValue
    )

    for (const walletAccount of walletAccountNames) {
      if (walletAccounts[walletAccount].isHardware) {
        delete walletAccounts[walletAccount]
        delete this.#hardwareWalletPublicKeys[walletAccount]
      } else {
        walletAccounts[walletAccount] = this.#disableWalletAccount(walletAccounts, walletAccount)
      }
    }

    await this.#walletAccountsInternalAtom.set(walletAccounts)
    await this.#savePublicKeys()
    await this.#updateFusion()
  }

  #normalizeWalletAccount = async (
    walletAccount: WalletAccount | string
  ): Promise<WalletAccount> => {
    if (typeof walletAccount === 'string') {
      const walletAccounts = await this.#walletAccountsAtom.get()
      const instance = walletAccounts[walletAccount]
      assert(instance, `wallet account ${walletAccount} not found`)

      return instance
    }

    return walletAccount
  }

  signMessage = async (opts: SignMessageParams) => {
    const { baseAssetName, message, purpose } = opts
    const walletAccount = await this.#normalizeWalletAccount(opts.walletAccount)

    const signer = await this.#getMessageSigner(walletAccount)
    return signer.signMessage({
      baseAssetName,
      walletAccount,
      purpose,
      message,
    })
  }

import { compute } from '@exodus/atoms'
import type { WalletAccount } from '@exodus/models'
import type { WalletAccountsAtom } from '../types.js'

export default function createEnabledWalletAccountsAtom({
  walletAccountsAtom,
}: {
  walletAccountsAtom: WalletAccountsAtom
}) {
  const selector = (values: Record<string, WalletAccount>) =>
    Object.fromEntries(
      Object.entries(values).filter(([, account]: [string, WalletAccount]) => account.enabled)
    )

  return compute({ atom: walletAccountsAtom, selector })
}
