### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, while the `shop` value that is handed to the app's webhook handler as the tenant identifier is read from an HTTP header that is never included in that HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` accessor, however, is read directly from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cryptographic binding to the HMAC-signed body: [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler [4](#0-3) , and passes the unauthenticated `request.shop` straight into `WebhookMetadata` as the tenant identifier delivered to the app's handler [5](#0-4) .

Because the api_secret_key that produces the HMAC is a single shared secret per app (not per-shop), any two webhooks with byte-identical bodies delivered to the same app produce byte-identical HMACs regardless of which shop they originated from. An attacker who controls one shop with the app installed (a normal, unprivileged action — installing an app on your own free development or trial store) can capture a legitimate, validly-signed webhook body from their own shop, then replay that exact body to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain, breaking the identity binding: `shop authenticated by HMAC (none)` ≠ `shop acted upon by the handler`.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5) , implying stronger guarantees (including which shop it came from) than the code actually provides.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` to select or scope tenant-specific data (e.g., "update order for shop X", "look up shop X's stored access token/session to act on its behalf") can be tricked into acting on behalf of, or writing attacker-supplied data into, a different tenant's records, using a body the attacker fully controls in shape/content (as long as the app processes attacker-owned data for their own shop first, then replays it against a victim). This is a cross-tenant confusion vulnerability rooted in a broken identity binding in this gem's webhook verification.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on any shop they control (a normal, unprivileged step available to anyone), which yields them legitimately HMAC-signed webhook bodies for their own tenant. No privileged credentials, `api_secret_key`, or access tokens are needed. The webhook endpoint is a public HTTP endpoint by design.

### Recommendation
Bind the `shop` (and `topic`) values into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the signed payload before trusting it as the tenant identity — e.g., require callers to independently look up/validate that the shop has an active registration for the specific `webhook_id`/topic combination server-side, rather than trusting the unauthenticated header value as-is for tenant-scoped side effects.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger an `orders/create` webhook so Shopify sends body `B` with a valid HMAC `H = HMAC-SHA256(api_secret_key, B)` and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [7](#0-6) ; `HmacValidator.validate` succeeds because it only checks `B` against `H` [8](#0-7) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` [9](#0-8) , so the app processes attacker-supplied order data as if it belonged to the victim shop.
