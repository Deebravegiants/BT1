## Title
Unbounded batch size in `pallet_ismp::handle_unsigned` combined with a static/flat declared weight allows a single free unsigned extrinsic to force unmetered, unbounded verification work — computational DoS analog to CVE-2020-13530 - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` and is annotated with a **flat, constant weight** (`weight()` returns `Weight::from_parts(300_000_000, 0)` regardless of batch contents), while the actual work performed — `Self::execute(messages)` — is proportional to the number of messages, the number of requests/responses per message, and the size of their membership/non-membership proofs (merkle multiproofs, signature checks, and for `Message::Consensus` full BEEFY/GRANDPA/sync-committee-style verification). Because the call is unsigned (fee-free, `ensure_none`), any unprivileged network participant can submit a single extrinsic that is cheap to construct but expensive to validate, both in the transaction pool (`validate_unsigned` runs the same `Self::execute` full path) and, if crafted to pass validity, at block-execution time where `CheckWeight` only accounts the static 300M weight instead of the real cost incurred. ### Finding Description
`handle_unsigned` is dispatched from an unsigned origin and simply forwards the raw `Vec<Message>` to `Self::execute`: [1](#0-0) 

`Self::execute` iterates every message and calls `handle_incoming_message`, which for request/response messages performs full merkle membership/non-membership verification over the whole batch of requests, and for consensus messages performs full consensus-client verification (BEEFY/GRANDPA/sync-committee/etc.): [3](#0-2) 

There is no bound on `messages.len()`, on `RequestMessage.requests.len()`, or on proof size — the wire type is a plain `Vec<Message>`. The declared extrinsic weight is a hard-coded constant independent of batch size: [2](#0-1) 

This same unbounded, un-throttled `execute()` call is also invoked directly from `validate_unsigned`, which every node runs for every transaction entering its pool (including transactions gossiped by peers), before any weight/fee accounting applies: [4](#0-3) 

Because `handle_unsigned` is fee-free and its weight is a fixed low constant, an attacker can build one (or many) extrinsics containing a very large number of `Message::Request`/`Message::Response` entries (each with a maximal-size merkle multiproof) or oversized consensus proofs. Each node that receives this transaction — via RPC submission or p2p gossip — must run the full, un-fee-metered `execute()`/proof-verification path in `validate_unsigned` merely to determine validity, and if a variant is crafted to validate successfully, block authors must execute the real (unbounded) work at `apply_extrinsic` time while only debiting the flat 300M weight from the block's weight budget. This directly parallels the CVE-2020-13530 bug class: a sequence of protocol requests, cheap to send, forces the receiving node to perform disproportionate processing, degrading or halting availability — except here the "requests" are ISMP messages reaching Hyperbridge's own unsigned message-dispatch entrypoint rather than an unrelated network service.

### Impact Explanation
This is a computational Denial-of-Service on the reachable, unprivileged message-dispatch path (`handle_unsigned`), which every relayer, and in fact any account, can invoke for free. A successful attack can:
- Cause the transaction pool of every full node to spend excessive CPU validating one (or a burst of) malicious unsigned transactions, since `validate_unsigned` runs `execute()` in full for every submission and every peer-gossiped copy.
- Cause block-production stalls or missed block deadlines if a crafted batch is valid and gets included, since the actual proof-verification cost vastly exceeds the flat weight charged against the block's weight limit, breaking the weight-accounting invariant that block execution time is bounded by declared weight.
- This is reachable in a single submitted, unsigned extrinsic requiring no fee and no privileged role — matching the High severity classification of the DoS analog and the requirement that the bug be reachable from a single relayed message.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be free and open to "anyone" per the pallet's own documentation ("Pallet ISMP uses unsigned transactions for executing cross-chain messages... executed for free"). No length bound exists on the `Vec<Message>` parameter or nested request/proof vectors, and the weight function ignores message content entirely. Constructing a request/response batch with many entries and a maximal merkle multiproof, or a consensus message with an expensive-but-decodable proof payload, requires no special access and is straightforward given the public message/wire formats. [5](#0-4) 

### Recommendation
- Bound the size of `messages: Vec<Message>` accepted by `handle_unsigned` (e.g., via a configurable `MaxMessagesPerBatch`), and similarly bound the number of requests/responses per message and proof sizes, rejecting oversize batches in `validate_unsigned` before any verification work is performed.
- Replace the static `weight()` in `#[pallet::weight(weight())]` with a weight function that scales with the declared/pre-decoded size of the batch (message count, request count, proof length) so `CheckWeight` accounts for the real cost, consistent with how `pallet_call_decompressor` already gates claimed decompressed size before doing work.
- Consider adding a cheap up-front cost/size check in `validate_unsigned` (similar to the `CallSizeOutOfBound` guard in `pallet_call_decompressor::decompress`) that rejects clearly oversized batches before invoking `execute()`.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` extrinsic whose `messages: Vec<Message>` contains a single `Message::Request(RequestMessage)` with an extremely large `requests` vector and an accompanying merkle multiproof large enough to be verified against a real state-machine commitment (or a `Message::Consensus` payload whose proof is expensive to run through the configured consensus client).
2. Submit the unsigned extrinsic via RPC to a node, or broadcast it over the p2p layer so it propagates through gossip to many nodes.
3. Every receiving node runs `pallet_ismp::Pallet::<T>::validate_unsigned`, which calls `Self::execute(messages.clone())` in full — performing full merkle/consensus verification — before any weight or fee is charged, since this happens purely in the transaction pool.
4. Repeat with a stream of distinct (non-duplicate, to bypass `provides`-tag dedup) maximal-size batches to keep every receiving node's pool-validation thread(s) saturated, degrading transaction throughput and block production across the network at negligible cost to the attacker.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
