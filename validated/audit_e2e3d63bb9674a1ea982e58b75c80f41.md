### Title
Unauthenticated `CallDispatcher.dispatch()` lets anyone drain residual token/ETH balances left by intent predispatch/postdispatch calls - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher` is a single shared, stateless contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute arbitrary calldata against funds temporarily parked at its address (swap-then-escrow / fill-then-act composability). Its `dispatch()` function has **no access control whatsoever** — any external account, not just the app contracts that hold a reference to it, can invoke it with an arbitrary `Call[]`. Combined with the fact that the gateway/token contracts only sweep back the *specific, pre-known* set of input/output token addresses after a predispatch/postdispatch call, any token balance the dispatcher ends up holding outside that known set (leftover dust, multi-hop swap intermediates, extra reward tokens, or partially-swept balances) remains stuck at the dispatcher and is trivially stealable by anyone who calls `CallDispatcher.dispatch()` directly with a transfer call for that token.

### Finding Description
`CallDispatcher.dispatch()` executes any `Call[]` handed to it with no `msg.sender` check: [1](#0-0) 

Multiple apps rely on this single deployed instance (`_params.dispatcher`) as a temporary custodian for user funds during composable operations:

- `IntentGatewayV2.placeOrder` transfers `order.predispatch.assets` to the dispatcher, executes user-supplied predispatch calldata, then sweeps back **only** the tokens listed in `order.inputs` by reading `IERC20(token).balanceOf(dispatcher)` for those specific tokens: [2](#0-1) 

- `IntentsBase._execute` (used by both same-chain and cross-chain fill paths) dispatches `order.output.call` and then sweeps residual balances **only** for the tokens enumerated in `order.output.assets` (`outputsLen`): [3](#0-2) 

Any predispatch/postdispatch call that produces a token type not in the swept list — e.g. a DEX route that yields an intermediate token, a reward/airdrop token, rounding dust from a multi-hop swap, or excess native ETH from a call that wasn't fully consumed — is left sitting on the shared `CallDispatcher` contract's balance. Because `dispatch()` is callable by anyone, a third party can, in a completely separate transaction, call `CallDispatcher.dispatch()` directly with a `Call` such as `{to: leftoverToken, data: transfer(attacker, balance)}` (or `{to: attacker, value: balance}` for ETH) and take the residual funds — funds that belonged to whichever user's order deposited them.

This mirrors the referenced report's root cause exactly: a shared intermediary account (`trove` in the report, `CallDispatcher` here) can retain funds after a composable operation because the sweep-back logic only checks for a specific known set of tokens, and the intermediary's own access control is insufficiently restrictive, letting an unrelated subsequent caller benefit from the leftover balance.

### Impact Explanation
This is a direct theft-of-funds vector reachable by any unprivileged actor with no special role. It affects every app that shares the `CallDispatcher` deployment (`IntentGatewayV2` predispatch/postdispatch flows, and any `data`-carrying `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer that dispatches calldata to the same instance). Because the dispatcher is a long-lived, permissionless, stateless proxy for arbitrary calls, any dust or unaccounted token left on it by one user's transaction is permanently exposed to theft by anyone monitoring the dispatcher's balance — a clear violation of the "no residual balances that a subsequent caller can benefit from" invariant class this report class targets.

### Likelihood Explanation
Likelihood is high: predispatch/postdispatch calldata is arbitrary and user/solver supplied by design (swap routes, DeFi composability), so it is easy — even accidental — for a call to leave behind a token that isn't in the input/output list being swept (e.g., a multi-hop swap through an intermediate token, or a partially filled swap leaving unspent input token behind). No privileged role is required to exploit the leftover balance: `CallDispatcher.dispatch()` is public and unauthenticated, so exploitation is a single, cheap transaction by anyone watching dispatcher balances.

### Recommendation
Add access control to `CallDispatcher.dispatch()` so only the authorized app contract(s) that own a given batch of calls can invoke it (e.g., restrict to a registered caller allow-list, or make the dispatcher a per-call ephemeral contract instead of a shared singleton). Additionally, harden the sweep logic in `IntentGatewayV2.placeOrder` and `IntentsBase._execute` to sweep the dispatcher's *entire* balance of any token that could plausibly be produced by the predispatch/postdispatch call (or restrict predispatch/postdispatch calldata to a strict allow-list of target tokens/contracts) so no unaccounted token balance can persist on the shared dispatcher between calls.

### Proof of Concept
1. A user places an order via `IntentGatewayV2.placeOrder` with `predispatch.call` that swaps ETH → TokenA → TokenB through a router where the router returns slightly more TokenA than consumed (or produces a small amount of an unrelated reward token), and `order.inputs` only lists TokenB.
2. `placeOrder`'s sweep loop (lines 260-311 of `evm/src/apps/IntentGatewayV2.sol`) only checks/sweeps balances for tokens in `order.inputs` (TokenB); leftover TokenA (or the reward token) remains on `_params.dispatcher`.
3. Any external account calls `CallDispatcher.dispatch(abi.encode([Call({to: TokenA, value: 0, data: transfer(attacker, leftoverBalance)})]))` directly — this succeeds because `dispatch()` performs no caller check — and the attacker receives the leftover tokens that rightfully belonged to escrow accounting for the order (or to the protocol as dust).     function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
