### Title
Webhook shop/topic identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from HTTP headers that are never part of the HMAC-signed material. `Webhooks::Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`) and, once it passes, unconditionally trusts `request.shop` and `request.topic` to route the payload to a handler and stamp the resulting `WebhookMetadata` with the tenant (`shop`). This breaks the intended binding: `HMAC-verified body == (shop, topic)` that the app relies on for per-tenant dispatch.

### Finding Description [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are separately read from headers with no cryptographic linkage to the body: [2](#0-1) 

`HmacValidator.validate` only checks that the HMAC matches `verifiable_query.to_signable_string` (the body) against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust the header-derived `shop` and `topic` for dispatch and tenant attribution: [4](#0-3) 

Because the webhook HMAC secret (`Context.api_secret_key`, the app's client secret) is shared across *every* shop that has installed the app, any merchant who installs the app can obtain a legitimate `(raw_body, hmac)` pair for their own shop by simply triggering an event that generates a webhook. Since the `shop-domain` (and `topic`) headers are outside the signed material, that same body/HMAC pair remains "valid" if replayed with a different `x-shopify-shop-domain` header. The app has no way to detect this because HMAC validation only checks the body, not the header claims it dispatches on.

### Impact Explanation
This qualifies as cross-tenant access (Critical): a merchant using the app can forge webhook events that the host application will process as if they originated from an entirely different merchant's shop, poisoning that shop's data pipeline (e.g., fake `orders/create`, `app/uninstalled`, or `shop/redact` events attributed to a victim tenant) while still passing this gem's own HMAC verification. Since `Registry.process` is the gem's sanctioned verification+dispatch primitive, host apps that follow the documented API and trust `WebhookMetadata#shop`/`#topic` post-validation inherit this cross-tenant spoofing weakness directly from the gem.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs to be a legitimate (even free/trial) merchant of the app to generate one authentic `(body, hmac)` pair for their own store, then replay it to the app's public webhook endpoint with a modified `shop-domain`/`topic` header. No access to the app's `api_secret_key` or any victim credential is required — this is exactly the "bytes verified versus bytes parsed" binding break: the bytes verified by HMAC (raw body) are not the bytes acted upon for tenant/topic routing (headers).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before dispatch — e.g., have `to_signable_string` return a canonical concatenation of the header claims plus the raw body rather than the raw body alone. At minimum, document and enforce that host applications cannot rely on `Registry.process`/`WebhookMetadata#shop` for tenant isolation unless the shop is independently validated against a known/installed-shop registry before use.

### Proof of Concept
1. App merchant "Attacker Co." installs the app on `attacker.myshopify.com` and triggers any event (e.g., updates a product) so Shopify sends a legitimate webhook:
   ```
   POST /webhooks
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <valid HMAC of raw_body computed with the app's shared api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   {"id": 123, "title": "..."}
   ```
2. Attacker captures this `(raw_body, hmac)` pair (they legitimately received it, since it's their own shop's webhook).
3. Attacker replays the exact same body and HMAC to the app's webhook endpoint, but swaps the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this, `Utils::HmacValidator.validate(request)` succeeds because it only re-computes the HMAC over `raw_body`, which is unchanged.
5. `Registry.process` calls the topic handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "products/update", body: parsed_body, ...)`, and the host app processes/stores this attacker-controlled payload as if it were an authentic event for `victim.myshopify.com`.
