### Title
Untracked ETH balance changes in `EmporiumUpgradeable.runAction` allow draining Emporium's own ETH via attacker-controlled `EmporiumOperation.value` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` only tracks balance deltas for tokens listed in the attacker-supplied `circomData.erc20TokenAddresses` array [1](#0-0) . Because the ETH sentinel `address(0)` can simply be omitted from this array, an attacker can make `op.endpoint.call{value: op.value}(op.callData)` spend Emporium's real ETH balance in "stateless" mode without any signature check and without the post-call balance-change accounting ever noticing.

### Finding Description
The broken equality is: *total ETH leaving Emporium via `op.value` in Case 2 must be ≤ ETH the attacker's own proof deposited into Emporium (tracked by `deltaAmountChanges`)*. This equality is not enforced when `address(0)` is absent from `circomData.erc20TokenAddresses`.

Code path:
1. `runAction` decodes `EmporiumStack` fully from `circomData.externalActionData.externalActionMetadata`, which is attacker-supplied calldata for their own proof [2](#0-1) .
2. `verifyWallet` is called; when `stack.signerAddress == address(0)` it returns immediately after marking `emporiumMessage` used — no EIP-712 signature is required for this path [3](#0-2) .
3. In the ops loop, when `op.invokeWallet == false` (attacker sets it directly, no linkage to `signerAddress`), execution falls into "CASE 2: Stateless Interaction" and performs `op.endpoint.call{value: op.value}(op.callData)` using the contract's own ETH balance, with `op.value` fully attacker-controlled up to `uint128` max [4](#0-3) .
4. `balancesBefore`/`balancesAfter` and the subsequent `deltaAmountChanges` reconciliation loop only iterate `circomData.erc20TokenAddresses` [5](#0-4) . If the attacker's proof/circuit input simply excludes `address(0)` from this array, no revert check (`BalanceChangeShouldBePositive`) or `deltaAmountChanges` entry ever examines Emporium's ETH balance, so ETH drained in step 3 is invisible to the accounting.
5. `getERC20OrETHBalance`/`getBalancesForArray` confirm `address(0)` is treated as the ETH sentinel elsewhere in the codebase, confirming ETH is only tracked when explicitly listed [6](#0-5) .
6. Emporium can plausibly hold nonzero ETH from relay fee flows (`sendToRelay`/`payRelayFees` use `transferERC20TokenOrETH`, which can leave dust or unclaimed leftovers on the contract) [7](#0-6) , and the contract explicitly accepts arbitrary ETH via `receive() external payable {}` [8](#0-7) .

`onlyAllowedRecipient` only restricts `msg.sender` to the allowed caller (Hinkal contract) [9](#0-8) ; it does not constrain the contents of `EmporiumOperation` inside the attacker's own proof metadata. None of the existing guards (`verifyWallet`, `BalanceChangeShouldBePositive` check, `deltaAmountChanges` loop) actually cover ETH once `address(0)` is left out of `erc20TokenAddresses`.

### Impact Explanation
An attacker can redirect Emporium's own residual ETH balance (accumulated protocol/relay fee ETH) to an arbitrary endpoint/calldata of their choosing, with the call framed as coming from Emporium (`msg.sender == Emporium`). If any downstream contract trusts calls from Emporium (e.g., a fee-sink crediting balances by `msg.sender`), the attacker can direct that credit to themselves. This is theft of protocol/relay fee ETH sitting on the Emporium contract — matching the "High" severity category (theft of protocol/relay fees). It is repeatable on every transaction as long as Emporium holds spendable ETH.

### Likelihood Explanation
Preconditions: Emporium must hold nonzero ETH balance (plausible residue from relay fee payment paths or direct ETH sends via `receive()`), and there must exist some endpoint that trusts `msg.sender == Emporium`. The attacker needs no privileged role — they only need to generate their own valid proof/`CircomData` with `erc20TokenAddresses` omitting `address(0)`, and craft an `EmporiumStack` with `invokeWallet=false`, `signerAddress=address(0)` (bypassing the signature check entirely), and `op.value` set to whatever ETH they want to move. Feasibility depends on the existence of a trusting downstream contract, which is an external dependency, but the core Emporium-side accounting gap is real and unconditional.

### Recommendation
Force `address(0)` (ETH) into the tracked balance set unconditionally in `runAction` (not relying on attacker-supplied `erc20TokenAddresses`), or explicitly disallow nonzero `op.value` in Case 2 when the token isn't present in `circomData.erc20TokenAddresses`, or require `op.value` to be sourced strictly from `msg.value`/tracked deposits rather than the contract's standing balance.

### Proof of Concept
Foundry fork test plan:
1. Deploy `EmporiumUpgradeable`, seed it with ETH (simulate leftover from `payRelayFees`/direct send via `receive()`).
2. Deploy a mock "trusted fee-sink" contract that credits a beneficiary based on `msg.sender == Emporium` and calldata-embedded beneficiary address.
3. Construct `CircomData` with `erc20TokenAddresses = []` (excluding `address(0)`), and `externalActionMetadata` encoding an `EmporiumStack` with one `EmporiumOperation{ endpoint: feeSink, invokeWallet: false, value: <Emporium's ETH balance>, callData: <credit attacker> }`, `signerAddress = address(0)`.
4. Call `runAction` from the allowed-recipient (Hinkal) context with matching `deltaAmountChanges = []`.
5. Assert: Emporium's ETH balance before == amount stolen, Emporium's ETH balance after == 0 (or reduced), and the fee-sink credited the attacker's beneficiary — with `deltaAmountChanges` never reflecting this ETH movement, proving no equality was enforced.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }
