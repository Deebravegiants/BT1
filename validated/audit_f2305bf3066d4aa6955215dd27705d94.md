## Analysis

`sell()` calls `canGraduate(tokenAddress)` on **every sell**, and `canGraduate` (and `_prepareGraduationLiquidity`) both perform an **unchecked (non-saturating) subtraction**:

```solidity
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [1](#0-0) 

The same unguarded pattern is used again in the graduation drain path: [2](#0-1) 

`_launchTimeVirtualLtReserve` is recovered from the immutable `Pair.k()/TOTAL_SUPPLY` identity, i.e. it is the launch-time virtual LT reserve `V` that is baked in forever: [3](#0-2) 

`assetReserve` is the pair's *stored* LT reserve, mutated only through `Router.buy`/`Router.sell` → `Pair.swap`, which enforces the K-invariant with a `+1` rounding slack on **both** sides: [4](#0-3) 

Because `Router._computeBuy` floors `tokensOut` and `Router._computeSell` floors `k/newReserveToken` (which rounds `assetOut` *up*, i.e. favorable to the seller), repeated buy→sell round-trips by an unprivileged trader leak the LT reserve out of the pair by rounding dust each cycle: [5](#0-4) 

Enough of these cycles can walk the stored `assetReserve` down to (and, given the `+1` slack, potentially below) the immutable virtual reserve `V`. The moment `assetReserve < V`, `assetReserve - V` underflows and reverts with a raw `Panic(0x11)` — inside `canGraduate`, which is called unconditionally at the top of every `sell()` and is also referenced by `previewLtUntilGraduation` used in every buy path. This mirrors CVE-2020-18770's root cause class: an unvalidated/derived field difference is subtracted without a bounds check, and attacker-reachable inputs (here, ordinary buy/sell traffic) can drive that difference negative, turning a normal operation into an unconditional revert.

I was not able to fully verify, within the remaining budget, whether the actual rounding slack accumulated per cycle is large enough in practice to close the gap to `V` within a realistic number of transactions, or whether some other invariant (e.g., `tokensOut`/`amountInUsed` floors, or the `+1` K-slack direction) coincidentally prevents `assetReserve` from ever dropping below `V` in the honest-buy/dishonest-sell-loop scenario. The repo's existing invariant suite (`GraduationInvariants.t.sol`) does *not* appear to contain a dedicated fuzz/invariant test asserting `assetReserve >= virtualLtReserve` holds for all time under arbitrary buy/sell sequences (unlike the explicitly tested `tokenBalance() < tokenReserve()` invariant), which is why this specific underflow path escaped hardening while the overflow-cap and brick-resistance paths were exhaustively fuzzed.

### Title
Unchecked `assetReserve - virtualLtReserve` subtraction in `canGraduate`/`_prepareGraduationLiquidity` can underflow and permanently DoS a token's curve - (File: packages/contracts/src/Bonding.sol)

### Summary
`canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` all compute `realLtRaised`/`ltFromPair` as `assetReserve - virtualLtReserve` without a saturating guard, unlike other Bonding.sol code paths that explicitly saturate (`_sweepLTToOwner`, `protectedLT` computation, etc., which the code's own comments call out as deliberately "saturating subtract... keep[ing] finalize from bricking on a Panic"). If `assetReserve` (the pair's stored LT reserve) is ever driven below the immutable launch-time virtual reserve `V = Pair.k()/TOTAL_SUPPLY`, this subtraction reverts with an undecodable `Panic(0x11)` arithmetic-underflow instead of a typed error.

### Finding Description
`canGraduate` is called unconditionally on the hot path of every `Bonding.sell()`:
```solidity
if (canGraduate(tokenAddress)) revert TokenIsGraduating();
```
and internally does:
```solidity
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```
`_launchTimeVirtualLtReserve` returns the fixed `virtualLtReserve` recovered from `Pair.k()`, which never changes for the life of the pair. `assetReserve` is mutated only via `Pair.swap`'s K-invariant, which allows a `+1` slack on each side:
```solidity
if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
```
`Router._computeBuy` floors `tokensOut`, and `Router._computeSell` floors `k/newReserveToken`, which rounds `assetOut` up (favorable to the seller). An unprivileged trader can repeatedly buy a small amount and sell it back through `Zap.buy`/`Zap.sell` (or directly via an allowlisted router in the test harness's sense of "any transaction an unprivileged EOA can submit through Zap"). Each round-trip leaks a small amount of LT out of the pair's *stored* `assetReserve` in the seller's favor because of the asymmetric floor/ceil rounding and the `+1` K-slack tolerated by `Pair.swap`. Over sufficiently many cycles this walks `assetReserve` down toward, and potentially past, `virtualLtReserve`.

Once `assetReserve < virtualLtReserve`, every subsequent call into `canGraduate` (i.e., every `sell()`), `previewLtUntilGraduation` (used by `Zap.buy`'s LT pre-sizing), and eventually `_prepareGraduationLiquidity` (the graduation drain) reverts with a bare `Panic(0x11)`. This is worse than the documented, carefully-avoided "brick" scenarios elsewhere in the same file (e.g., the `OverflowCapDegenerate` typed revert, or the explicit saturating subtracts around `protectedLT`), because here there is no saturating guard at all.

### Impact Explanation
Once triggered, `Bonding.sell()` permanently reverts for that token (every sell calls `canGraduate` first), and `Zap.buy()`'s curve path also breaks because it depends on `previewLtUntilGraduation`, which performs the identical unguarded subtraction. Traders holding the token can no longer sell on the curve, and new buys revert — a permanent freeze of trader funds on that curve, matching the "permanent freezing of trader ... funds" impact bar. This is a Medium-severity denial-of-service, directly analogous to the zziplib class of bug: an unvalidated arithmetic relationship between two fields, reachable through ordinary (here: repeated buy/sell) operations, that turns a read/parse path into an unconditional crash.

### Likelihood Explanation
Reachable purely through unprivileged `Zap.buy`/`Zap.sell` calls — no privileged role, no upgrade, and no off-chain/dependency assumption required. The likelihood of actually closing the gap to zero depends on the magnitude of the per-cycle rounding leak relative to `virtualLtReserve` (which is sized to ~`VIRTUAL_LIQUIDITY_USD` in LT terms) and the number of cycles an attacker is willing to pay gas/fees for; this was not fully quantified against the live fee-and-rounding constants, so likelihood should be treated as uncertain until confirmed by a dedicated fuzz/invariant test (the existing `GraduationInvariants.t.sol` suite tests `tokenBalance() < tokenReserve()` explicitly but does not appear to assert `assetReserve >= virtualLtReserve` under arbitrary buy/sell sequences).

### Recommendation
Replace the raw subtraction in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` with a saturating subtraction (returning `0` when `assetReserve <= virtualLtReserve`), mirroring the pattern already used elsewhere in `Bonding.sol` (`finalizeGraduation`'s `protectedLT` computation). Add an explicit invariant/fuzz test asserting `assetReserve >= virtualLtReserve` holds for all reachable buy/sell sequences, and quantify the worst-case per-cycle rounding drift in `Router._computeBuy`/`_computeSell` to confirm whether the `+1` K-slack in `Pair.swap` can ever let `assetReserve` cross below `virtualLtReserve` in practice.

### Proof of Concept
1. Launch a token via `Zap.createToken` with the minimum seed.
2. Repeat N times: `Zap.buy(token, smallUsdcAmount, 0, referrer)` immediately followed by `Zap.sell(token, tokensJustBought, 0)`, exploiting the floor/ceil asymmetry between `Router._computeBuy` and `Router._computeSell` and the `+1` K-slack in `Pair.swap` to leak LT out of the stored `assetReserve` each cycle.
3. Once `assetReserve` drops below the immutable `virtualLtReserve` (`Pair.k()/TOTAL_SUPPLY`), the next `Zap.sell` call reverts with `Panic(0x11)` inside `canGraduate`'s `assetReserve - virtualLtReserve` subtraction, and remains permanently broken for that token thereafter — a genuine PoC run against the deployed constants would be needed to confirm the exact cycle count, which was not completed here.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
