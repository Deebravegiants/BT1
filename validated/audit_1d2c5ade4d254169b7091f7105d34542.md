### Title
Silent Skip on Incomplete Trie Proofs Lets a Malicious Storage Proof Omit Parachain Keys Without Failing Verification - ([File: modules/ismp/state-machines/substrate/src/lib.rs])

### Summary
`read_proof_check_for_parachain` in `modules/ismp/state-machines/substrate/src/lib.rs` walks a caller-supplied Merkle-Patricia storage proof for a set of keys and, when the trie backend cannot resolve a specific key because the proof witness is incomplete (`TrieError::IncompleteDatabase`), it silently `continue`s instead of failing the whole verification. This mirrors the OpenSearch bug class: an error condition on a single read (a corrupted/partial file read there, an incomplete trie witness here) is swallowed and the caller is handed a partial, seemingly-successful result instead of an error, letting the untrusted input steer which parts of a multi-key verification "succeed."

### Finding Description
`read_proof_check_for_parachain` is the SCALE-typed proof reader used to extract values (e.g., parachain head data) from a relay-chain storage proof supplied inside a consensus update message: [1](#0-0) 

For each requested key it distinguishes three trie outcomes: `Ok(Some(val))` (decode and insert), `Ok(None)` (explicit non-membership, insert `None`), and `Err(e)`. In the error arm, `TrieError::IncompleteDatabase` is treated specially — the loop just `continue`s, leaving that key completely absent from the returned `BTreeMap`, rather than surfacing an error or explicitly recording an "unresolved" state. Every other trie error still returns `Err`.

This is the same class of bug flagged in CVE-2022-41917: an unauthenticated/partial read condition (there: analyzer hits EOF/permission edge case; here: the witness for one key is deliberately left out of the proof) is not treated as a hard failure. Instead of the whole proof verification aborting, the function returns a result that looks like a normal, complete answer to any caller that doesn't specifically distinguish "key absent from map because it wasn't asked for / genuinely doesn't exist" from "key absent from map because the submitted proof was intentionally incomplete for that key."

Contrast this with the two attacker-reachable membership checks in the very same file — `verify_membership` and `verify_non_membership`, which back ISMP request/receipt delivery — where every `trie.get` error (including `IncompleteDatabase`) is mapped to a hard `Err(SubstrateStateMachineError::TrieError(...))`: [2](#0-1) [3](#0-2) 

That correct pattern shows the intent: an incomplete trie should fail the batch. `read_proof_check_for_parachain` breaks that invariant for its own key loop: [4](#0-3) 

`read_proof_check_for_parachain` is referenced from the parachain consensus client (`modules/ismp/clients/parachain/client/src/consensus.rs`), which is the code path that extracts a batch of parachain-head storage entries from a relay-chain state proof supplied by a relayer inside a `ConsensusMessage` during `handle_unsigned`/consensus dispatch. Because this proof and the set of keys it must resolve come directly from an untrusted relayer, a relayer can build a storage proof that is complete/well-formed for some parachain IDs in the batch but deliberately drops the trie nodes needed to resolve one particular key. For that key, `trie.get` returns `IncompleteDatabase` and the entry is dropped from the result map instead of aborting the whole call.

### Impact Explanation
If the caller of `read_proof_check_for_parachain` treats "key not present in the returned map" the same as "explicit non-membership" (`Ok(None)`) or simply skips processing for absent keys without distinguishing "proof was incomplete for this key," an attacker-supplied consensus proof can:
- Selectively omit a parachain's head update from an otherwise-valid batch while still having the extrinsic succeed, instead of the whole submission being rejected as malformed.
- Cause state desynchronization for one state machine in a multi-parachain BEEFY/GRANDPA update without any error being raised, which can be leveraged to stall or manipulate downstream ISMP message delivery / state-commitment updates for that specific chain while the rest of the batch (and the extrinsic reward/side effects) proceeds normally.

This is a Medium-severity error-handling flaw: it does not directly forge a value, but it lets an attacker-controlled "malformed proof" input silently degrade into "no data for this key" rather than "verification failed," which is exactly the incorrect-error-handling class described in the report (a failed/partial read being surfaced as if it were a successful, if incomplete, answer).

### Likelihood Explanation
Reachability requires only that a relayer submit a specially-crafted storage proof (available to any unprivileged relayer able to submit a consensus/state-proof message) with intentionally pruned trie nodes for one target key while remaining valid for the others — no special privileges are needed to construct such a proof, only knowledge of the trie structure, which is public.

### Recommendation
In `read_proof_check_for_parachain`, remove the special-case `continue` on `TrieError::IncompleteDatabase` and instead return `Err(Error::Custom(...))` for any trie read error, matching the behavior already used in `verify_membership`/`verify_non_membership` in the same module. If a "best effort, partial result" mode is genuinely required somewhere, it must be an explicit, clearly-named API (e.g., returning per-key `Result` or a separate "unresolved" set) rather than silently omitting failed keys from a map that other callers may reasonably assume is complete.

### Proof of Concept
1. Build a valid relay-chain storage proof covering N parachain-head keys for a BEEFY/GRANDPA consensus update.
2. For one target key, remove the intermediate trie node(s) needed to resolve it, while keeping the proof otherwise valid/well-formed so `codec::Decode` and the rest of `read_proof_check_for_parachain` succeed.
3. Submit the consensus message; `trie.get` for the pruned key returns `Err(TrieError::IncompleteDatabase)`, `read_proof_check_for_parachain` `continue`s, and the returned `BTreeMap` omits that key entirely instead of the call failing.
4. Observe that the extrinsic completes successfully and any caller logic keyed on "is this parachain ID present in the result" silently treats the targeted parachain as having no update, with no error or event indicating the proof was actually incomplete/malformed for that key.

(Note: full confirmation of the downstream handling of the returned `BTreeMap` inside `modules/ismp/clients/parachain/client/src/consensus.rs` — specifically whether it distinguishes "absent key" from "explicit None" — could not be traced to the line level within the available tool budget; this should be verified directly in that file before treating the impact as fully proven.)

/// Lifted directly from [`sp_state_machine::read_proof_check`](https://github.com/paritytech/substrate/blob/b27c470eaff379f512d1dec052aff5d551ed3b03/primitives/state-machine/src/lib.rs#L1075-L1094)
pub fn read_proof_check_for_parachain<H, I>(
	root: &H::Out,
	proof: StorageProof,
	keys: I,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error>
where
	H: hash_db::Hasher,
	H::Out: Debug,
	I: IntoIterator,
	I::Item: AsRef<[u8]>,
{
	let db = proof.into_memory_db();

	if !db.contains(root, EMPTY_PREFIX) {
		Err(Error::Custom("Invalid Proof".into()))?
	}

	let trie = TrieDBBuilder::<LayoutV0<H>>::new(&db, root).build();
	let mut result = BTreeMap::new();

	for key in keys {
		let raw_key = key.as_ref();

		match trie.get(raw_key) {
			Ok(Some(val)) => {
				let decoded = Decode::decode(&mut &val[..])
					.map_err(|e| Error::Custom(format!("Decode error: {e:?}")))?;
				result.insert(raw_key.to_vec(), Some(decoded));
			},
			Ok(None) => {
				result.insert(raw_key.to_vec(), None);
			},
			Err(e) =>
				if let TrieError::IncompleteDatabase(_) = *e {
					continue;
				} else {
					return Err(Error::Custom(format!("Trie fetch error: {e:?}",)));
				},
		}
	}

	Ok(result)
}
