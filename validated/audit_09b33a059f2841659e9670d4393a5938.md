This confirms the finding: the gem's own documentation explicitly tells developers `data.shop` is "The shop domain of the webhook" and shows using it directly (`shop_domain: data.shop`) in host-app business logic, without any suggestion that the value needs independent verification.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header (and `topic`, `webhook-id`, `api-version` headers) to build the `WebhookMetadata` passed to the app's handler. None of these headers are included in the signed payload, so their authenticity is never actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC against that body-only signable string and, once it passes, builds `WebhookMetadata` directly from the unauthenticated `request.shop` header: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute `HMAC-SHA256(api_secret_key, signable_string)` and compare it to the `hmac-sha256` header — again, only over the body: [3](#0-2) 

The identity binding that should hold is: `hmac_valid == true` implies `shop header == the shop Shopify actually generated this webhook for`. In reality the equality only holds for the body bytes: `hmac_valid == true` implies `body == the body Shopify actually generated`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers sit entirely outside that binding.

Because the `api_secret_key` (app client secret) used for signing is the same across every shop that installs the app, a merchant who has legitimately installed the app can:
1. Trigger a real webhook to their own shop (e.g., create an order/product with attacker-chosen content), which Shopify signs correctly using the app's shared secret over that body.
2. Capture the valid `(raw_body, hmac-sha256)` pair from that legitimate request.
3. Replay the same body and HMAC value to the app's webhook endpoint, but substitute the `shop-domain` header with a victim shop's domain (and optionally a different `topic`/`webhook-id`).
4. `HmacValidator.validate` still succeeds (the body/HMAC pair is valid), and `Registry.process` forwards `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the host app's handler.

The gem's own documentation instructs developers to key business logic directly off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this spoofed shop attribution flows straight into per-tenant processing (job queues, database writes, session/access-token lookups keyed by shop), effectively letting one tenant inject attacker-controlled webhook payloads attributed to another tenant — a cross-tenant boundary violation.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide. A validly-authenticated (in the eyes of the gem) webhook can be attributed to any shop of the attacker's choosing, letting one merchant's webhook traffic pose as another's inside the host application. Given the documented pattern of using `data.shop` for downstream shop-specific processing, this is a genuine cross-tenant access path, matching the High/Critical impact category (cross-tenant access) called out in the assessment rules.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker who can install the app on their own store (any public app is installable by any merchant) and can influence content that gets included in one of their own store's outgoing webhooks (trivial — creating orders/products/customers with attacker-chosen field values). No access to `api_secret_key`, tokens, or the target shop is needed.

### Recommendation
Bind the identity-bearing headers to the HMAC computation, or otherwise cryptographically tie `shop-domain`/`topic`/`webhook-id` to the signed payload before trusting them (Shopify itself computes the HMAC only over the body, so this must be mitigated at the gem/app level, e.g., by requiring/validating that the `shop-domain` corresponds to a shop with an active, registered webhook subscription for that exact `webhook-id`/`topic` pair before invoking the handler, or by cross-checking against Shopify's webhook subscription API before processing).

### Proof of Concept
```ruby
# Attacker installs app on their own shop "attacker-shop.myshopify.com"
# and triggers/receives one legitimate webhook, e.g. orders/create,
# capturing the raw body + its valid x-shopify-hmac-sha256 value.

raw_body = '{"id":1,"note":"attacker-controlled content"}'
valid_hmac_for_body = "<hmac captured from Shopify's legitimate request to attacker's shop>"

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_for_body,   # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
)
# HmacValidator.validate succeeds (body/HMAC pair genuinely matches),
# and the registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though Shopify never sent this webhook for victim-shop.
```
