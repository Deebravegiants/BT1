Audit Report

## Title
`NonFungiblesTransferAdapter::transfer_asset` never verifies `from` owns the NFT before delegating to `Assets::transfer`, allowing theft of NFTs via XCM `TransferAsset`/`TransferReserveAsset` - ([File: polkadot/xcm/xcm-builder/src/nonfungibles_adapter.rs])

## Summary
`NonFungiblesTransferAdapter::transfer_asset` resolves `(class, instance)` from the XCM asset and calls `Assets::transfer(&class, &instance, &destination)` using only the resolved destination — the `from` parameter (derived from the XCM instruction's origin) is never checked against the item's actual owner. Both concrete `nonfungibles::Transfer` implementations examined (`pallet_uniques` and `pallet_nfts`) pass a no-op ownership-witness closure (`|_, _| Ok(())`) into their respective `do_transfer` functions, which read the current owner from storage and move the item to `dest` unconditionally. Any account able to get an XCM `TransferAsset`/`TransferReserveAsset` instruction executed can move an NFT it does not own to an arbitrary destination.

## Finding Description
In `transfer_asset` [1](#0-0) , `from` is logged but never used to validate ownership; only `class`, `instance`, and `destination` are passed to `Assets::transfer`.

`pallet_uniques`'s `Transfer` impl supplies a no-op closure to `do_transfer`: [2](#0-1) , and `do_transfer` reads the current owner from storage (`Item::<T, I>::get`) and moves it to `dest` without comparing to any witness: [3](#0-2) .

`pallet_nfts`'s `Transfer` impl behaves identically, also passing `|_, _| Ok(())`: [4](#0-3) , and its `do_transfer` likewise reads `Item::<T, I>::get` for the owner and moves it to `dest` with no `from` comparison in the `with_details` closure: [5](#0-4) . This resolves the original report's uncertainty — `pallet_nfts` is equally exposed as `pallet_uniques`.

The XCM executor's `TransferAsset` and `TransferReserveAsset` instruction handlers pass `origin_ref()` (the message's established origin) as `from` to `AssetTransactor::transfer_asset_with_surplus`/`transfer_asset` without any separate ownership check at the executor level: [6](#0-5) . Since neither the executor nor the adapter nor the pallet's `do_transfer` verifies that `from` (the origin) is the actual owner, the only place ownership is normally checked — the closure supplied by extrinsic call sites like `pallet_uniques::Call::transfer`/`pallet_nfts::Call::transfer` — is bypassed entirely by the XCM path, which supplies its own permissive closure.

## Impact Explanation
Any account capable of getting an XCM program executed (e.g., a signed user via `pallet_xcm::execute`, or via a sovereign/descended-origin flow) can craft a `TransferAsset` or `TransferReserveAsset` instruction naming an NFT `(class, instance)` it does not own and a `beneficiary` it controls, causing the NFT to be moved away from its actual owner without consent. This is direct, unauthorized theft/relocation of NFT assets, contingent on the runtime's `AssetTransactor` configuration.

## Likelihood Explanation
Exploitability requires the runtime to configure `NonFungiblesTransferAdapter`/`NonFungiblesAdapter` backed by `pallet_uniques` or `pallet_nfts` as (part of) its `AssetTransactor` for local `TransferAsset`/`TransferReserveAsset` handling, and for `Matcher::matches_nonfungibles` to resolve attacker-supplied `(class, instance)` pairs. Given both first-party NFT pallets exhibit the identical no-op-witness pattern, any chain wiring either pallet through this adapter for these instructions is exposed. Exploitation requires no special privilege beyond the ability to have an XCM program executed with some origin, which is a standard, low-privilege capability (e.g., `pallet_xcm::execute`).

## Recommendation
Add an explicit ownership check in `NonFungiblesTransferAdapter::transfer_asset` before calling `Assets::transfer`, e.g. resolving `from` to an `AccountId` and asserting `Assets::owner(&class, &instance) == Some(from_account)` (returning `XcmError::NoPermission` otherwise). More robustly, extend the `nonfungibles::Transfer` trait to accept an ownership witness/`from` parameter and require `pallet_uniques`'s and `pallet_nfts`'s `Transfer::transfer` implementations to verify the current owner against it, rather than passing a no-op closure into `do_transfer`.

## Proof of Concept
1. Mint NFT `(collection=0, item=0)` to account `OWNER` via `pallet_uniques` or `pallet_nfts`.
2. Configure the XCM executor's `AssetTransactor` to include `NonFungiblesAdapter`/`NonFungiblesTransferAdapter<Uniques, Matcher, AccountIdConverter, AccountId>` (or the `pallet_nfts` equivalent).
3. Execute an XCM program whose origin resolves to `ATTACKER` (not `OWNER`), containing `TransferAsset { assets: [nft(0,0)], beneficiary: ATTACKER_LOCATION }`.
4. Observe the instruction succeeds and `owner(0, 0) == Some(ATTACKER)`, despite `ATTACKER` never owning the item.
5. Contrast with the signed-extrinsic path (`pallet_uniques::Call::transfer` / `pallet_nfts::Call::transfer`) from `ATTACKER` for the same item, which correctly returns `Error::NoPermission`, demonstrating that the XCM adapter path bypasses the ownership check enforced at the extrinsic call site.

	pub fn do_transfer(
		collection: T::CollectionId,
		item: T::ItemId,
		dest: T::AccountId,
		with_details: impl FnOnce(
			&CollectionDetailsFor<T, I>,
			&mut ItemDetailsFor<T, I>,
		) -> DispatchResult,
	) -> DispatchResult {
		// Retrieve collection details.
		let collection_details =
			Collection::<T, I>::get(&collection).ok_or(Error::<T, I>::UnknownCollection)?;

		// Ensure the item is not locked.
		ensure!(!T::Locker::is_locked(collection, item), Error::<T, I>::ItemLocked);

		// Ensure the item is not transfer disabled on the system level attribute.
		ensure!(
			!Self::has_system_attribute(&collection, &item, PalletAttributes::TransferDisabled)?,
			Error::<T, I>::ItemLocked
		);

		// Retrieve collection config and check if items are transferable.
		let collection_config = Self::get_collection_config(&collection)?;
		ensure!(
			collection_config.is_setting_enabled(CollectionSetting::TransferableItems),
			Error::<T, I>::ItemsNonTransferable
		);

		// Retrieve item config and check if the item is transferable.
		let item_config = Self::get_item_config(&collection, &item)?;
		ensure!(
			item_config.is_setting_enabled(ItemSetting::Transferable),
			Error::<T, I>::ItemLocked
		);

		// Retrieve the item details.
		let mut details =
			Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;

		// Perform the transfer with custom details using the provided closure.
		with_details(&collection_details, &mut details)?;

		// Update account ownership information.
		Account::<T, I>::remove((&details.owner, &collection, &item));
		Account::<T, I>::insert((&dest, &collection, &item), ());
		let origin = details.owner;
		details.owner = dest;

		// The approved accounts have to be reset to `None`, because otherwise pre-approve attack
		// would be possible, where the owner can approve their second account before making the
		// transaction and then claiming the item back.
		details.approvals.clear();

		// Update item details.
		Item::<T, I>::insert(&collection, &item, &details);
		ItemPriceOf::<T, I>::remove(&collection, &item);
		PendingSwapOf::<T, I>::remove(&collection, &item);

		// Emit `Transferred` event.
		Self::deposit_event(Event::Transferred {
			collection,
			item,
			from: origin,
			to: details.owner,
		});
		Ok(())
	}
