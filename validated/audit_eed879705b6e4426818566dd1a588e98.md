### Title
Webhook `shop`/`topic` identity headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never included in the HMAC computation. `Utils::HmacValidator.validate` only checks that the body's HMAC matches the app's shared `api_secret_key`; it never binds that signature to the header-derived identity fields that `Webhooks::Registry.process` later uses to route and label the payload.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are extracted independently from headers [2](#0-1) . `HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and the app's `api_secret_key`/`old_api_secret_key`, comparing it to the `hmac` header [3](#0-2) . `Registry.process` accepts the request once this body-only HMAC passes, and then dispatches the handler using the *header-derived* `shop` and `topic`, which were never part of the signed material: [4](#0-3) .

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who has installed the app legitimately receives real webhook deliveries with valid HMACs computed over their own body. That merchant can capture one `(raw_body, hmac)` pair from their own store and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers with values naming a different shop or a more sensitive topic. `HmacValidator.validate` will still return `true` because the signature is computed only from the unchanged raw body and the correct secret — the header identity fields are never checked.

The broken binding, expressed as an equality that should hold but doesn't:
`shop/topic (used by the handler)` ⊄ `bytes verified by the HMAC (raw body only)`.

### Impact Explanation
This is a cross-tenant identity confusion: the webhook handler receives `WebhookMetadata` whose `shop` and `topic` are attacker-controlled despite `HmacValidator.validate` returning `true`, giving the host application false assurance that the (shop, topic, body) tuple is authentic. Any app whose webhook handler branches on `data.shop` or `data.topic` (e.g., to update per-shop database records, to react to `app/uninstalled`, `shop/redact`, `customers/data_request`, etc.) can be made to act on forged shop attribution supplied by an unprivileged (but app-installed) merchant, contaminating another tenant's data/state. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires an actor who has installed the app on any shop (a normal, unprivileged capability for a public Shopify app) to receive one legitimate webhook and replay it with modified headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only observation of one's own legitimately-delivered webhook traffic.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `Webhooks::Registry.process`/`WebhookMetadata`. At minimum, document that consuming applications must not trust header-derived `shop`/`topic` fields for authorization decisions without additional verification (e.g., cross-checking against a known registered `webhook_id`/subscription for that shop).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a real webhook, e.g. `orders/create`, to the app's webhook endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`.
2. Attacker captures the raw body and its valid HMAC (computed with the app's shared `api_secret_key`).
3. Attacker POSTs the same unmodified raw body and HMAC to the app's webhook endpoint again, but this time sets:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
   `x-shopify-topic: app/uninstalled` (or any topic the app handles).
4. `Utils::HmacValidator.validate` in `Webhooks::Registry.process` still returns `true`, because it only checks the raw body's HMAC [5](#0-4) .
5. The registered handler for `app/uninstalled` is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` [6](#0-5) , even though `victim-shop` never sent this webhook and the attacker has no access to it.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
