### Title
Supplier withdrawals revert unconditionally once utilization reaches `max_utilization`, and the last supplier can never exit while debt exists — ([File: contracts/pool/src/ops/withdraw.rs](contracts/pool/src/ops/withdraw.rs))

### Summary
Analogous to Derby's `blacklistProtocol` — an exit/removal path that reverts on a post-condition the caller cannot satisfy — the pool's `withdraw` op applies `require_utilization_below_max` **after** burning the caller's supply shares. Because burning supply raises utilization, once a market's utilization reaches `max_utilization` *every* non-liquidation withdrawal of any size reverts with `UtilizationAboveMax`. Utilization drifts to the cap passively through interest accrual on `borrowed × borrow_index`, so no attacker action is even required; an attacker can also accelerate it by borrowing to the cap boundary and letting accrual tip it over. Suppliers' funds are frozen until a borrower repays or a liquidation occurs — neither of which suppliers can force. The same gate also freezes `claim_revenue` (unclaimed yield).

### Finding Description
In `withdraw::accounting`, shares are burned first and guards run on the post-state (`gate_and_debit`):

```rust
// contracts/pool/src/ops/withdraw.rs
let remaining = burn_position(env, &mut cache, position, burned);
...
gate_and_debit(env, &mut cache, net_transfer, is_liquidation || empty_close);
```

`gate_and_debit` calls `guards::require_utilization_below_max` for all non-liquidation withdrawals:

```rust
// contracts/pool/src/guards.rs
let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
let supplied = cache.supplied().mul_floor(env, cache.supply_index());
assert_with_error!(env,
    supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
    CollateralError::UtilizationAboveMax);
```

Two consequences:

1. **Absolute post-state check.** The test is `utilization_after <= max_utilization` on the whole market, not on the caller's delta. Burning supply shares only ever raises utilization (`B/(S−x) > B/S`), so once utilization is at the cap there is no withdrawal size — not even 1 unit — that passes. The pool README confirms: "once utilization reaches the cap no withdrawal of any size passes, and interest accrual alone pushes it there" (`contracts/pool/README.md`, guards section). Release happens only "by repayment, or consumed by liquidation."
2. **Last-supplier lock.** `require_supply_for_debt` panics with `PoolInsolvent` when `supplied == 0 && borrowed != 0`, so the final supplier can never fully exit a market with outstanding debt, even if cash is present.

`claim_revenue` runs the same guards (`ops/revenue.rs::accounting`), so protocol revenue is likewise unclaimable while the market is at cap — though revenue shares keep accruing, so that part is delayed rather than lost.

### Impact Explanation
Temporary freezing of user funds (and of unclaimed protocol yield) for an unbounded duration. Suppliers holding shares in a capped market cannot exit at all; the duration depends entirely on third parties (borrowers repaying, or accounts becoming liquidatable). If borrowers are rational and underwater or simply inactive, the freeze persists. This matches the Derby report's class: the emergency/exit operation itself is what reverts, so the protective action (exiting a deteriorating market) is exactly what becomes impossible. Medium severity: no direct theft, but funds are frozen by a state the victim cannot influence.

### Likelihood Explanation
- No attacker is needed: interest accrual mechanically raises `borrow_index`, so a heavily borrowed market crosses `max_utilization` on its own.
- An attacker can force it: borrow up to the cap boundary (borrow enforces the same guard but checks its own post-state), then let one accrual tick push utilization over. The attacker pays only borrow interest.
- Reachable by any unprivileged address via the `withdraw` controller path, which funnels into `pool.withdraw` → `ops::withdraw::apply`.

### Recommendation
Decouple exit from the post-state utilization gate. Either:
- Skip `require_utilization_below_max` for withdrawals entirely (exits do not create new risk; the README already acknowledges liquidation withdrawals skip it), or
- Check utilization on the *pre-withdrawal* state so a withdrawing supplier is never worse-positioned by their own exit, or
- Permit withdrawals that do not increase utilization above the cap, i.e., gate on `utilization_before > max_utilization && utilization_after > utilization_before` style logic.

For `require_supply_for_debt`, allow the last supplier to withdraw down to a residual rather than reverting, or document that a final supplier must wait for repayment.

### Proof of Concept
1. Market: `max_utilization = 0.95 RAY`. Alice supplies 100 USDC; Bob supplies collateral and borrows 95 USDC — passes both `require_reserves` and the buffer guard.
2. Time advances; `borrow_index` accrues, pushing `borrowed × borrow_index / supplied × supply_index` above `0.95 RAY`.
3. Alice calls `controller.withdraw(USDC, 1)` (any positive amount). Inside `pool.withdraw`, `resolve_withdrawal` computes a burn, `burn_supply` reduces `supplied`, then `require_utilization_below_max` computes post-state utilization ≥ 0.95 and panics `UtilizationAboveMax`.
4. Every subsequent `withdraw` and `claim_revenue` on that market reverts identically until a borrower repays or a liquidation withdraws collateral (liquidation skips the gate via `is_liquidation`).
5. If Alice were the sole supplier, even waiting doesn't help: a full close hits `require_supply_for_debt` → `PoolInsolvent` while any debt remains.

The pool README (lines ~292–300) and `INV-ACCT-08` already describe this gate's behavior, so note this may be treated as documented design; the vulnerability is that the guard's *post-state, market-wide* form turns a per-market risk parameter into an unconditional freeze on supplier exits — the same "protective function reverts exactly when needed" shape as M-32. pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
```rust
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
}
```

```rust
/// Panics with `PoolInsolvent` if supplied is zero while borrowed debt is non-zero.
pub(crate) fn require_supply_for_debt(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO && cache.borrowed() != Ray::ZERO {
        panic_with_error!(env, CollateralError::PoolInsolvent);
    }
}
```
