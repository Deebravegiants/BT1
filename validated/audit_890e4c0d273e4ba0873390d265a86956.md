### Title
`Webhooks::Registry.process` trusts an unsigned `shopify-shop-domain` header as tenant identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` only validates the HMAC over the raw request body, but the shop identity handed to the host app's handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed content. An attacker who can reach the app's public webhook endpoint directly (not necessarily through Shopify) can replay a body+HMAC pair they legitimately received for their own shop while substituting the shop-domain header of a victim merchant, and the gem will accept it as authentic.

### Finding Description
The invariant claimed by the question is: shop authenticated by the signature == shop used by the host app to select tenant data. Tracing the code shows this equality is not enforced:

- `Request#to_signable_string` returns only `@raw_body`, never headers: [1](#0-0) 
- `Request#shop` reads the raw `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` compute and compare HMAC solely against `to_signable_string` (the body), never touching `verifiable_query.shop` or any header: [3](#0-2) 
- `Registry.process` validates the HMAC, then builds `WebhookMetadata` directly from `request.shop` (the untrusted header) and hands it to the host app's handler, which "uses it to choose whose records to touch": [4](#0-3) 
- `WebhookMetadata#shop` is a plain `String` const with no validation against any authenticated identity: [5](#0-4) 

Because the signature only covers the body, an attacker who owns their own development shop can legitimately receive a validly-signed webhook (valid `hmac-sha256` header over a real `raw_body`, real `webhook-id`). That same body+HMAC pair remains valid under HMAC re-verification even if the `shopify-shop-domain` header is swapped for an arbitrary victim shop's domain, because the header is never part of the signable string. `Registry.process` will pass HMAC validation and construct a `WebhookMetadata` claiming the (forged) victim shop, which the host app trusts to select which tenant's records to read or mutate.

None of the existing guards prevent this: `HmacValidator.validate` checks body integrity only, not header/shop binding; there is no `ShopValidator.sanitize!`, JWT `aud`/`dest` check, or session-id-derived shop comparison anywhere in this webhook path; `Context.setup?`/`private?`/`embedded?` are unrelated to webhook delivery; Sorbet only enforces that `shop` is a `String`, not that it matches an authenticated value.

### Impact Explanation
An attacker who registers their own webhook endpoint on their own shop can capture a genuinely HMAC-signed body/webhook-id, then send a crafted HTTP POST directly to the app's public webhook endpoint with that same body and HMAC but an arbitrary victim's `shopify-shop-domain` header. If the host app follows the gem's documented usage (trusting `WebhookMetadata#shop` post-`Registry.process` to select the tenant), the attacker can inject attacker-controlled webhook payload content as if it originated from any victim merchant, causing the host app to write or act on data under the victim's tenant scope. This is a cross-tenant access vector matching Critical severity.

### Likelihood Explanation
The attacker only needs: (1) their own development/test shop with the app installed, (2) a registered webhook to observe one real signed body+HMAC+webhook-id, and (3) network access to POST to the app's public webhook endpoint (which is inherently internet-reachable since Shopify itself must reach it over the public internet). No secrets, tokens, or elevated privileges are required. This is fully repeatable against any victim shop domain the attacker chooses, for any topic the host app has registered a handler for.

### Recommendation
Bind the trusted shop identity to the signed content instead of trusting the header in isolation: derive/validate the shop from data embedded in the signed body (Shopify webhook payloads typically include the shop context) or require the host app-level receiver to independently authenticate the origin (e.g., only accept connections proxied by Shopify) and pass that verified shop through explicitly rather than relying on `Request#shop`. At minimum, document/enforce that `WebhookMetadata#shop` must be cross-checked by the host app against a shop already known to have an active registration/webhook subscription matching the `webhook_id`, and consider incorporating the shop-domain header into the HMAC signable string if the gem intends header-derived shop as a trust anchor.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_binding_test.rb
require "test_helper"

class WebhookRegistryShopBindingTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @raw_body = '{"id":123}'
    @secret = ShopifyAPI::Context.api_secret_key
    @hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", @secret, @raw_body)).strip
  end

  def test_shop_header_not_bound_to_hmac
    # legitimate delivery for attacker's own shop
    legit_headers = {
      "x-shopify-topic" => "products/update",
      "x-shopify-hmac-sha256" => @hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "2023-01",
      "x-shopify-webhook-id" => "abc123",
    }
    legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: legit_headers)
    assert ShopifyAPI::Utils::HmacValidator.validate(legit_request)

    # same body + same HMAC, forged shop header for victim
    forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
    forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: forged_headers)

    # HMAC still validates -- proves shop is NOT bound to the signature
    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request)
    assert_equal "victim-shop.myshopify.com", forged_request.shop
  end
end
```
This demonstrates the equality `shop authenticated by signature == shop used downstream` is false: the HMAC validates identically regardless of the `shop-domain` header value, so `WebhookMetadata#shop` can diverge from any shop actually tied to the signed payload.
