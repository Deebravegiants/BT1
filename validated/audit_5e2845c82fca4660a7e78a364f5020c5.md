## Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the value of the unauthenticated `X-Shopify-Shop-Domain` header directly to the app's handler as the tenant identifier. Because the shared HMAC secret (the app's `api_secret_key`) is identical for every shop that has the app installed, and the signature never covers the shop-domain header, any merchant who installs the app on their own store can capture a valid `(body, hmac)` pair and replay it with a forged `shop-domain` header pointing at a victim shop, causing the app to process attacker-controlled webhook data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `to_signable_string` (i.e. the body only) using the shared `Context.api_secret_key`, and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` performs exactly this HMAC check and then forwards `request.shop` — the unauthenticated header — straight into `WebhookMetadata`, which the handler uses as the tenant/shop identifier: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by Shopify == shop the app attributes the data to`. In this implementation the equality is broken because the HMAC only proves "some data came from an app owner holding `api_secret_key`" (true for every shop that installed the app, since the secret is shared per-app, not per-shop) — it does **not** prove "this body belongs to shop X." The library exposes no verification that `request.shop` matches the tenant whose resource IDs/content appear in `request.parsed_body`.

The library's own documentation confirms handlers are expected to trust `data.shop` at face value and use it to route/attribute the webhook (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

### Impact Explanation
This satisfies the "High - scope/tenant check bypass" and borders on "Critical - cross-tenant access" impact bar: a merchant who legitimately installs the app on their own store (an unprivileged actor with respect to other tenants) can generate arbitrary, validly-HMAC'd webhook bodies at will (by triggering real events on their own store, or crafting a body and topic combination Shopify will sign for them), then replay that exact `(body, hmac)` pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim merchant's domain. Because `Registry.process` only checks the HMAC (which still validates, since it never covered the header) it will call the handler with `data.shop` set to the victim's domain and `data.body` set to attacker-chosen content, causing the host application to inject or process attacker-controlled data under the identity of another tenant — a cross-tenant data injection / spoofing primitive.

### Likelihood Explanation
Any developer or business can register as a Shopify Partner and install their own app instance (or any public app) on a free development store at no cost, giving them full control over one legitimate tenant and full ability to receive validly-signed webhooks from Shopify for it. Forging the HTTP header on a replayed request requires no special access — it is a standard HTTP client capability. Likelihood is therefore high for any app that (as this library's documented usage pattern encourages) trusts `data.shop` from `WebhookMetadata` for tenant attribution without independently cross-checking it.

### Recommendation
Do not treat the `shop-domain` header as authenticated by the payload HMAC. At minimum:
- Document explicitly (more strongly than the current docs) that `data.shop` is unauthenticated and must be cross-validated by the host application against a known/installed shop before being trusted for tenant routing.
- Where feasible, have `Registry.process` require/accept a list of currently-known installed shops (or a lookup callback) and reject webhooks whose `shop` is not recognized as having previously completed OAuth for this app.
- Consider exposing a comparison between webhook body content (e.g., resource domain fields, if present) and the claimed `shop` header where the topic's payload includes shop-identifying data.

### Proof of Concept
1. Attacker installs the target app (or already has it installed) on their own store `attacker-shop.myshopify.com`, obtaining a legitimate webhook delivery for topic `orders/create` with body `B` and Shopify-computed header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures the full HTTP request headers and body from this delivery.
3. Attacker replays the request to the app's public webhook endpoint, keeping `body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) using the app's shared `api_secret_key` — this matches `H`, so validation passes: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-supplied data as belonging to the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
