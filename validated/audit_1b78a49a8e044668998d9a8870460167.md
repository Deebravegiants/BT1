**Analysis:**

The actual boundary check lives in `listing::assert_started`, not in `timestamp.move`: [1](#0-0) 

```
public(friend) fun assert_started(object: &Object<Listing>): address acquires Listing {
    let listing_addr = object::object_address(object);
    assert!(exists<Listing>(listing_addr), error::not_found(ENO_LISTING));

    let listing = borrow_global<Listing>(listing_addr);
    let now = timestamp::now_seconds();
    assert!(listing.start_time <= now, error::invalid_state(ELISTING_NOT_STARTED));
    listing_addr
}
```

This is called from `coin_listing::purchase`, `bid`, and `complete_auction` via `listing::assert_started(&object)` before any transfer of custody occurs.

Key points that invalidate the claim:

1. **The comparison is `<=`, not `<`.** The documented semantics are that the listing is live once `now >= start_time`. At `now == start_time`, `listing.start_time <= now` evaluates to `true` deterministically — this is the *intended* inclusive boundary, not an off-by-one bug. There is no nondeterminism: for a given ledger timestamp, every validator computes the identical result, since `timestamp::now_seconds()` returns the consensus-agreed on-chain block timestamp (set once per block via `timestamp::update_global_time`), not something an attacker can independently manipulate per-transaction. [2](#0-1) 

2. **Deterministic test evidence already exists in-repo.** The test suite explicitly constructs listings with `start_time = timestamp::now_seconds()` (i.e., start time equal to current time) and expects `purchase` to succeed, confirming the inclusive-boundary behavior is intentional and consistent, not flaky: [3](#0-2) 

The negative test (`test_not_started_fixed_price`) uses `start_time = timestamp::now_seconds() + 1` and expects failure, which is consistent with `<=` semantics (start_time strictly greater than now fails): [4](#0-3) 

3. **No custody boundary is crossed.** The actual asset transfer (`object::transfer`) only happens inside `listing::close`, gated behind `assert_started` succeeding by design at or after `start_time`: [5](#0-4) 
Ownership only moves to the purchaser when the seller's own pre-configured `start_time` condition is satisfied — this is expected, authorized behavior configured by the seller (a privileged party for their own listing), not an unprivileged escalation.

4. **Scope note:** this code resides in `aptos-move/move-examples/marketplace`, which is example/reference marketplace code, not part of the core production custody framework (`aptos-framework`). The review bounds restrict scope to "Aptos production custody logic only," so even if the semantics were debatable, this module falls outside that scope.

Since the boundary check is a single deterministic comparison against a consensus-agreed timestamp, and the inclusive `<=` semantics are demonstrably intentional and consistently reproduced in existing tests, there is no nondeterministic or unauthorized custody transfer here.
