### Title
Unrefunded native token overpayment gets permanently stranded in Tron `IntentGatewayV2.placeOrder` fee swap - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when `order.fees` is paid via native token and a fee-token swap is required, the contract forwards the entire remaining `msgValue` to `swapETHForExactTokens` but never captures the actual amount spent (`amounts[0]`) nor refunds the unspent remainder to the depositing user. This is analogous to the reported `EthUniswapPCVDeposit` bug class: a function that sends more value than an AMM swap actually consumes, where the AMM returns the excess to the calling contract rather than the original end-user, permanently stranding the difference.

### Finding Description
Compare the two sibling implementations of `placeOrder`'s fee-escrow block.

The maintained EVM contract correctly tracks and refunds unspent value: [1](#0-0) 

The Tron contract omits both the `amounts[0]` bookkeeping and the trailing refund entirely: [2](#0-1) 

`msgValue` at this point is `msg.value` minus whatever was already consumed by native-token order inputs and predispatch assets [3](#0-2) . This is nearly always larger than the ETH actually needed to buy `order.fees` worth of the fee token — either because the caller intentionally over-funds the transaction (as the SDK docs instruct: "unused native is refunded") or simply because the exact swap-input amount can't be predicted client-side.

`UniswapV2Router02.swapETHForExactTokens` refunds any leftover ETH to `msg.sender` of that call — which, since the router is invoked from inside the `IntentGatewayV2` contract, is the `IntentGatewayV2` contract itself, not the original user. Because the Tron `placeOrder` never reads the swap's returned `amounts` array and never performs a subsequent `_sendValue`/refund step (unlike the fixed EVM contract), that ETH refund lands in the contract with no corresponding entry in `_orders[commitment][...]` and no mechanism tying it back to the depositor. The user's overpaid native token becomes indistinguishable protocol-owned dust with no recorded owner.

### Impact Explanation
Any user who pays the solver fee (`order.fees`) in native token — the exact flow documented for the SDK ("native fee" path, where "unused native is refunded") — loses the ETH difference between what they sent and what the swap actually consumed. This is a direct, reachable loss of user funds triggered by a single `placeOrder` transaction from an unprivileged caller, matching "concrete theft or permanent freezing of funds."

### Likelihood Explanation
High. This path is used whenever `order.fees > 0` and the caller pays with native token (`msgValue > 0` after input/predispatch consumption), which is the standard SDK-documented fee-payment method for this chain deployment. No adversarial conditions or special timing are needed — normal usage triggers the loss on essentially every native-fee order, since the amount sent almost never exactly equals the router's required input.

### Recommendation
Mirror the fix already present in the primary EVM contract: capture the `amounts` return value from `swapETHForExactTokens`, decrement `msgValue` by `amounts[0]`, and refund the remaining `msgValue` to `msg.sender` after the fee-escrow block, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 383–397.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.fees = X` (paid in fee token via a native-ETH swap) and sends `msg.value` intentionally larger than the ETH required to buy `X` of the fee token (as is standard/recommended usage per the SDK's fee-quoting flow).
2. `msgValue` (after deducting any native order inputs) is passed in full to `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)`.
3. The Uniswap router consumes only the ETH needed and refunds the excess to `address(this)` (the gateway contract), since it is the caller of the swap.
4. `placeOrder` returns without ever reading the swap's `amounts[0]` or refunding the excess to `msg.sender`; the surplus ETH remains in the `IntentGatewayV2` contract's balance, untracked by `_orders`, and unreachable by the user through any exposed function (compare to the fixed logic in `evm/src/apps/IntentGatewayV2.sol` lines 383-397, which performs this refund correctly).
