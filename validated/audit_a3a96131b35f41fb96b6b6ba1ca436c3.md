Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) it exposes to handler code from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator.validate` is computed only over the raw request body. The header is not part of the signed material, so it can be freely modified without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the tenant identity from a header instead of from the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the identity binding: `hmac_valid(raw_body) == true` is treated as proof that `(shop, raw_body)` together are authentic, when in fact only `raw_body` is covered. The equality that should hold — `shop_verified_by_hmac == shop_delivered_to_handler` — does not, because `shop` is parsed from an unauthenticated header while only the body bytes are verified. This matches the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" bug class from the report (an analogous flaw to the `leave()`/`preFund()` mismatch, where the value acted upon does not match the value actually authenticated).

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as delivered by `Registry.process`) to scope tenant data — a standard and expected usage pattern for multi-tenant Shopify apps — can be made to attribute an attacker-controlled, but HMAC-valid, payload to an arbitrary victim shop domain. An attacker who legitimately installs the app on their own shop can capture a real, correctly-signed webhook (body + valid `hmac-sha256` header) sent by Shopify to their own store, then replay it against the app's webhook endpoint after rewriting only the `x-shopify-shop-domain` header to point at a victim shop. The HMAC still validates because it never covered that header. This is a cross-tenant identity confusion vulnerability: it lets an unprivileged user cause the app to process attacker-supplied data as if it originated from a shop the attacker does not control, e.g. corrupting or triggering tenant-scoped operations, mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), or business logic keyed off `shop`. This satisfies the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker needs only their own legitimate app installation (unprivileged relative to the victim) to obtain one valid signed webhook, and then a simple HTTP replay with a modified header — no access to `api_secret_key`, tokens, or the app's infrastructure is required. The vulnerability is entirely within the gem's own `Webhooks::Request`/`Registry` code path, not a host-application misuse of a documented API, since the gem itself designs `shop` to come from an unsigned header while asserting the request is "valid" via HMAC.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values into the signable string used for HMAC verification (e.g., have `to_signable_string` combine header fields with the raw body in a canonical, delimiter-safe form), or otherwise cryptographically bind the shop identity to the verified payload before it is handed to `WebhookMetadata`/handlers, mirroring how `Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook delivery (e.g. `products/update`), capturing the raw POST body and its `x-shopify-hmac-sha256` header sent by Shopify — this HMAC is valid because it signs only `raw_body`.
2. Attacker replays the exact same HTTP request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` succeeds because it only checks `request.to_signable_string` (`raw_body`), per [4](#0-3) .
4. `handler.handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, per [5](#0-4) , causing the app to process attacker data under the victim's tenant identity.
