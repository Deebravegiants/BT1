Found it: in `Webhooks::Request`, the HMAC signature only covers `@raw_body` (the JSON body bytes), while `shop` (and `topic`, `webhook_id`, `api_version`) are read from HTTP **headers**, which are never included in the signed data.

### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are trusted from unauthenticated headers while the HMAC only covers the body - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by verifying `HMAC(raw_body)` against `Context.api_secret_key`, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler are parsed from HTTP headers that are excluded from that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the signature purely against that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from request headers via `shopify_header` with no cryptographic binding to the signature [3](#0-2) . `Registry.process` validates only the HMAC and then immediately trusts `request.topic` and `request.shop` to dispatch and populate `WebhookMetadata` passed to the app's handler [4](#0-3) .

This breaks the identity equality that a webhook consumer implicitly relies on: `shop_that_authenticated_the_payload == shop_the_handler_believes_sent_it`. An unprivileged internet user who can reach the app's webhook endpoint (webhooks are plain public HTTP endpoints, no TLS client auth or IP allowlisting is enforced by this gem) can take **any legitimately-signed webhook body** (e.g., replay a body they legitimately received for their own trial/dev shop, or any body whose HMAC they can compute if the raw bytes are known) and re-POST it with `x-shopify-shop-domain` and `x-shopify-topic` headers changed to a **different shop and topic combination**, and `process` will accept it as authentic since only the body bytes are checked.

### Impact Explanation
This falls under cross-tenant access: an attacker can cause an app to believe topic/shop-scoped data belongs to a different tenant than it actually does, since `shop` (the tenant identity) is unauthenticated with respect to the signature that gates acceptance. Depending on how the host application keys its data store off `WebhookMetadata#shop`/`#topic` (which is the gem's documented contract), this allows forged attribution of webhook events to an arbitrary shop domain, without possessing that shop's secret or access token — only requiring a single previously-observed valid `(body, hmac)` pair for any shop.

### Likelihood Explanation
Moderate: exploitation requires the attacker to have obtained at least one legitimately-signed `(body, hmac)` pair (e.g. by installing the app themselves on a shop they control, which is trivial for any developer/attacker), then replaying it against the webhook endpoint with altered `shop`/`topic` headers. No secrets, tokens, or privileged access are required beyond what any developer can obtain by installing the target app on their own store.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them, e.g. by deriving expected shop from a separately-authenticated channel), so that `to_signable_string` reflects the full set of trusted fields rather than just the raw body. At minimum, document/enforce that `shop`/`topic` values from `Webhooks::Request` must not be trusted as tenant identity without additional binding, and update `HmacValidator`/`VerifiableQuery` so implementers can't accidentally exclude identity-bearing headers from the signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker replays the exact same body `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`, ignoring the header change [5](#0-4) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now `victim.myshopify.com` even though the payload was never sent by/for that shop [6](#0-5) .
