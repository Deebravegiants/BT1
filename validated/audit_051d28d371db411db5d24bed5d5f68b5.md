### Title
Cost-model `allocated_accounts_data_size` undercounts CPI-wrapped `CreateAccount`/`Allocate`, allowing block accounts-data growth to bypass `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects an iterator produced by `transaction.program_instructions_iter()`, which yields top-level instructions only. When a `system_instruction::create_account`/`allocate`/`allocate_with_seed`/`create_account_with_seed` is issued via CPI from a custom program rather than as a top-level instruction, the function returns `SystemProgramAccountAllocation::None` for that top-level instruction (since `program_id != system_program::id()`), so the transaction's `allocated_accounts_data_size` is computed as `0` even though the account's data is actually grown by `space` bytes at commit time. Because `apply_cost_tracker_during_replay` makes `CostTracker::try_add`'s `allocated_data_size` limit a consensus-relevant check applied identically during block production and replay, an attacker can systematically undercount real per-block accounts-data growth relative to the tracked/enforced budget.

### Finding Description
The vulnerable logic: [1](#0-0) 
only classifies an instruction as an allocation when its top-level `program_id` equals `system_program::id()`. This is fed only the top-level iterator: [2](#0-1) 
and again on the post-execution path: [3](#0-2) 
Both call sites pass `transaction.program_instructions_iter()`, which — per the SVM message trait — enumerates only the transaction's top-level compiled instructions, never instructions invoked via CPI (`program_runtime/src/invoke_context.rs`'s `prepare_top_level_instructions` confirms only top-level instructions are registered from the message before program execution starts; CPI-created instruction contexts are pushed later during execution, not through this iterator).

Consequently, if an attacker's own or a reused arbitrary program CPIs into `system_program::create_account`/`allocate` (a routine, unprivileged pattern — see the CPI test helper `invoke_create_account` in `program-test/tests/cpi.rs:85-117` demonstrating exactly this call shape), `calculate_account_data_size_on_instruction` never sees the underlying `SystemInstruction::CreateAccount`/`Allocate` instruction, and the top-level custom program's instruction returns `SystemProgramAccountAllocation::None`. The resulting `allocated_accounts_data_size` charged to `CostTracker` is `0`, while the actual account growth (correctly tracked at the low level via `TransactionAccounts::update_accounts_resize_delta`/`can_data_be_resized` in `transaction-context/src/transaction_accounts.rs:297-326`, and rolled up into `Bank::accounts_data_size_delta_on_chain` from `AccountsDeltas::accounts_resize_delta` in `runtime/src/bank.rs:4419-4430`) is real and persisted.

The cost-tracker check that this bypasses is consensus-relevant: `check_block_cost_limits` in `runtime/src/transaction_execution.rs:157-169` invokes `CostTracker::try_add` (`cost-model/src/cost_tracker.rs:172-193`), which enforces `allocated_accounts_data_size <= limits.allocated_data_size` (default `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`). Since `apply_cost_tracker_during_replay` (see `feature-set/src/lib.rs:2051-2054`, "apply cost tracker to blocks during replay #29595") makes this check apply during replay as well as block production, all validators compute this same undercount deterministically — so it does not cause a fork/consensus divergence, but it does let an attacker cause actual per-block accounts-data growth to exceed the intended `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget by packing many CPI-wrapped allocations into a block, since the tracker never rejects them for exceeding that specific budget.

### Impact Explanation
This falls under "cost-model ... charge materially less than the real ... memory ... work performed, exhausting block capacity or node resources below true cost." By wrapping allocations in CPI, an attacker can inflate a block's actual on-chain accounts-data growth (and thus AccountsDb/snapshot/replay resource consumption) well past `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, since that specific guardrail is bypassed for CPI-originated allocations while compute/signature/write-lock costs are still charged normally (so it doesn't bypass overall block-cost limits, only the dedicated accounts-data-size budget). Because the underestimate is deterministic and identical on both leader and replaying validators, it does not cause bank-hash divergence — the impact is resource-exhaustion/capacity-bypass of the accounts-data-growth guardrail, not a value-theft or consensus-safety bug.

### Likelihood Explanation
Fully triggerable by an unprivileged attacker: deploy (or reuse) any BPF program that CPIs `system_instruction::create_account`/`allocate`, and submit a top-level instruction invoking it (exactly the pattern already exercised in the repo's own test fixture `program-test/tests/cpi.rs` `invoke_create_account`). No special privileges, staking, or leader control are required — any transaction sender can construct such a transaction. Packing multiple such top-level instructions/transactions per block increases the aggregate undercount.

### Recommendation
Change `CostModel::calculate_allocated_accounts_data_size` (and its use in `calculate_cost`/`calculate_cost_for_executed_transaction`) to account for real, executed account-data growth rather than (or in addition to) a static top-level-instruction scan — e.g., for the post-execution path (`calculate_cost_for_executed_transaction`), use the transaction's actual `accounts_resize_delta` (already computed in `AccountsDeltas`) instead of statically re-parsing `program_instructions_iter()`, so the value fed into `CostTracker::try_add`'s `allocated_data_size` check reflects true bytes allocated regardless of whether the `CreateAccount`/`Allocate` occurred at top level or via CPI.

```rust
// cost-model/src/cost_model.rs (add to #[cfg(test)] mod tests)
#[test]
fn test_calculate_allocated_accounts_data_size_hides_cpi_create_account() {
    // Top-level instruction targets a *custom* program (not system_program::id()),
    // simulating a program that internally CPIs into system_program::create_account.
    let custom_program_id = Pubkey::new_unique();
    let transaction = Transaction::new_unsigned(Message::new(
        &[Instruction::new_with_bincode(
            custom_program_id,
            &(),
            vec![],
        )],
        Some(&Pubkey::new_unique()),
    ));
    let sanitized_tx = RuntimeTransaction::from_transaction_for_tests(transaction);

    // The static cost model reports zero allocation even though, at execution
    // time, this program is assumed (per the exploit scenario) to CPI into
    // system_program::create_account{space: X}, growing on-chain accounts
    // data by X bytes.
    assert_eq!(
        CostModel::calculate_allocated_accounts_data_size(
            sanitized_tx.program_instructions_iter(),
            &FeatureSet::all_enabled()
        ),
        0,
        "cost model must not silently under-count CPI-based account allocation"
    );
}
```
