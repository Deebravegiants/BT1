### Title
Phantom-order price snapshot can be manipulated by flash-loaning a solver's destination-chain balance to seize weighted-median price control - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices each leg of a phantom (price-discovery) order by taking the `weightedMedian` of solver quotes, where a quote's weight is the solver's **live, uncommitted** balance of the leg's output token on the destination chain, read via a plain `eth_call`/`balanceOf` at the chain head (`blockTag = "latest"`) rather than against escrowed or bonded capital. [1](#0-0) [2](#0-1) 

### Finding Description
The weight backing a solver's quote is nothing more than a `balanceOf` read (plus ERC-4626 `maxWithdraw`) taken at the current chain head, with no lock, escrow, or bonding requirement: [3](#0-2) 

`weightedMedian` does not blend the quotes — it *selects* one bidder's exact value verbatim once that bidder's weight crosses the majority threshold for the leg, as documented in the code itself: [4](#0-3) 

This is the direct structural analog of the Gitcoin `QuadraticFundingVotingStrategyImplementation` bug: an actor's influence over a protocol outcome is derived from a balance that is transient and self-controlled within a single block/observation window, rather than from capital that is escrowed, locked, or otherwise costly to acquire and release atomically. Just as a Gitcoin voter could flash-borrow tokens, "vote" (transfer to a grant address they control), and immediately reclaim them in one transaction, a solver here can flash-borrow (or otherwise transiently acquire) a large balance of a leg's output token immediately before the price-discovery window closes (`PhantomBidWindowExhausted`), submit or already have submitted a bid quoting an extreme price, have its weight computed off the inflated balance, and win `weightedMedian` selection for that leg — publishing an attacker-chosen price with zero durable capital commitment. The balance is read fresh (`"latest"`) at aggregation time, not pinned to any block tied to the bid's placement, so the manipulation window is exactly the time between the flash-acquisition and the aggregation's `eth_call`.

### Impact Explanation
The resulting `medianPrice` becomes `PhantomOrderPriceSnapshotV2.medianPrice` and is folded into `LiquidityPool.sellRate`/`buyRate` via `updateLiquidityPools`/`mergeChainRowsIntoPool`, which the SDK's default `quoteIntent` (`indexed_rates` strategy) uses directly to price real intent orders — computing `amountIn`/`amountOut` for genuine cross-chain swaps without further validation. An attacker who can transiently inflate their destination-chain balance can therefore push a fabricated exchange rate into the pool that real users' orders get quoted against, causing them to escrow too much input or accept too little output — a concrete value-extraction path reachable by an unprivileged intent solver via ordinary bid submission, satisfying "intents escrow and bids" as an in-scope, reachable attack surface. [5](#0-4) 

### Likelihood Explanation
The read is unconditionally `"latest"` with no minimum holding period, no snapshot pinned to bid submission time, and no bonding/escrow requirement on the weight-bearing balance; the aggregation code and its own documentation explicitly acknowledge weight is "the solver's inventory... at this snapshot," which any solver holding "over half the leg's weight sets the published price verbatim." Any account capable of a flash loan or other transient balance acquisition on the destination chain, combined with a verified solver bid (a bar that only requires an EIP-7702 delegation and a signed `UserOperation`), can attempt this.

### Recommendation
Require the weight-bearing balance to be committed capital rather than a spot read: pin the balance read to a block at or before the bid's submission (not the aggregation-time head), require a minimum holding duration or escrow/bond for weight-bearing balances, and/or cap any single bidder's contribution to a leg's weighted median (e.g., a maximum weight share) so no single flash-acquired balance can unilaterally select the published price.

### Proof of Concept
1. Solver observes an open `PhantomOrderV2` bidding window for a leg quoting token `T` on destination chain `D`.
2. Immediately before (or during) the block in which the indexer's `handlePhantomOrderPrices` handler runs `aggregatePhantomBids` (triggered by `PhantomBidWindowExhausted`), the solver flash-borrows a large amount of `T` into its EIP-7702-delegated `SolverAccount` address.
3. The solver's previously-submitted (or freshly submitted, if window timing allows) bid quoting an extreme `solverAmount` for that leg is weighted by `getTotalSolverBalance`, which reads `T`'s `balanceOf` at `"latest"` — now inflated by the flash loan.
4. `weightedMedian` selects the attacker's quote verbatim as `medianPrice` because the attacker's weight dominates the leg (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1551`).
5. Solver repays the flash loan in the same transaction; the balance returns to its prior, real value with no capital lockup ever needed for the weight it exploited.
6. The fabricated `medianPrice` propagates through `updateLiquidityPools` into `LiquidityPool.sellRate`/`buyRate`, which `quoteIntent`'s default `indexed_rates` strategy uses to price subsequent real orders against a manipulated market rate.

/**
 * Sums the solver's redeemable balance of a single token on one chain: the raw ERC-20 balance plus
 * any ERC-4626 vault positions wrapping it.
 *
 * This is THE definition of "a solver's balance" — the periodic sweep and any per-event re-read
 * must use it rather than a bare `balanceOf`, because simplex funds fills straight out of a vault
 * inside the fill transaction: the wallet ends the block roughly where it started while
 * `maxWithdraw` is what actually moved, so a wallet-only read misses such a fill entirely.
 *
 * `blockTag` reads the balance as of a specific block ("0x..." or a tag), so a caller replaying an
 * event records the balance as of that event rather than stamping today's balance onto a
 * historical row. It defaults to the chain head, which is what a periodic sweep wants.
 */
export async function getTotalSolverBalance(
	evmRpcUrl: string,
	chain: string,
	token: string,
	solver: string,
	yieldVaults: YieldVaultMap,
	blockTag = "latest",
): Promise<bigint> {
	const padded = solver.replace("0x", "").padStart(64, "0")
	const raw = await ethCallUint(evmRpcUrl, token, `0x70a08231${padded}`, blockTag) // balanceOf(address)
	const vaults = yieldVaults[chain]?.[token.toLowerCase()] ?? []
	const vaultBalances = await Promise.all(
		vaults.map((v) => ethCallUint(evmRpcUrl, v, `0xce96cb77${padded}`, blockTag)), // maxWithdraw(address)
	)
	return vaultBalances.reduce((acc, b) => acc + b, raw)
}
