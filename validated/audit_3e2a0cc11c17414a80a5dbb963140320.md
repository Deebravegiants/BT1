### Title
Supply-index floor clamp resurrects wiped-out supplier claims that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary

When bad debt equal to or exceeding the total supplied value is socialized, `apply_bad_debt_to_supply_index` computes a zero remaining value and a zero reduction factor, then clamps the new supply index **up** to `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000) rather than zeroing out supplier shares. The clamp — a sentinel substituted for the genuinely empty state, the structural analog of dereferencing a non-null placeholder where null was meant — leaves every pre-wipeout supplier with a live, positive claim. Once any new depositor supplies cash, those phantom shares withdraw real tokens, stealing the fresh deposit. This is reachable from the unprivileged `clean_bad_debt` / post-liquidation bad-debt path on the controller (`check_bad_debt_after_liquidation` → pool seize/write-down).

### Finding Description

In `contracts/pool/src/interest.rs:73-89`, `apply_bad_debt_to_supply_index` does:

```rust
let capped = bad_debt.min(total_supplied_value);
let remaining = total_supplied_value.checked_sub(cache.env(), capped);
let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
let new_supply_index = cache.supply_index().mul_floor(cache.env(), reduction_factor);
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value`, `remaining = 0`, `reduction_factor = 0`, `new_supply_index = 0`, and the `.max(SUPPLY_INDEX_FLOOR_RAW)` restores a positive index. All `supplied` scaled shares remain in storage unchanged, so `unscale_supply_floor(old_scaled)` still returns a positive claim against cash the pool no longer owes.

The codebase's own test proves the end-to-end loss: `contracts/pool/tests/interest.rs:372-427` (`test_raw_cache_floor_clamp_strands_claim_without_supply_guard`) applies a write-down larger than supply, observes the index clamped to the floor, then shows that a fresh deposit of exactly the stranded claim size is fully drained by the wiped position's withdrawal (`cache.cash() < fresh_claim`, "funds lost"). The only masking layer is `require_reserves`, which checks cash against the withdrawal amount, not against the orphaned shares — so the first fresh depositor's cash legitimately covers the phantom withdrawal.

Reachability: an unprivileged liquidation on an insolvent account leaves unbacked debt; `check_bad_debt_after_liquidation` (contracts/controller/src/positions/liquidation/mod.rs:135) and `clean_bad_debt` route that residue into the pool's seize/write-down path (contracts/pool/src/ops/seize.rs), which calls `apply_bad_debt_to_supply_index`. Deep insolvency (collateral crash, zero-threshold collateral seized at zero bonus as documented in `docs/reference/formulas.md:225-264`) is exactly the regime where `bad_debt >= total_supplied_value` occurs — precisely when the clamp fires.

### Impact Explanation

Theft of user funds and protocol insolvency. Wiped-out suppliers — whose claims should have been fully written down — retain shares worth `scaled × RAY/1000`. The first unprivileged depositor(s) to supply after the wipeout fund those claims: the stranded withdrawal pays out real tokens and the fresh supplier's claim becomes unbacked (`cash < fresh_claim`). Every token of the resurrected claim is taken from new depositors, not from protocol revenue. If the attacker is among the wiped suppliers (or the bad debt was engineered via a self-liquidated underwater position), the attacker directly collects the stolen funds.

### Likelihood Explanation

Requires bad debt at least equal to total supplied value in a market — a tail-risk event (severe price collapse or zero-weighted collateral leaving debt unbacked). It needs no privileged role: `liquidate` and `clean_bad_debt` are permissionless, and an attacker can manufacture the insolvency on their own account with volatile collateral, then supply again after the wipeout to be the drained party is the *victim* side — the attacker is the wiped supplier claiming the floor-index value. Once the clamp has fired, the theft is deterministic on the next deposit/withdrawal interaction. Medium severity: bounded by market size but requires the insolvency precondition.

### Recommendation

When `capped == total_supplied_value` (full wipeout), explicitly burn the `supplied` (and `revenue`) scaled shares to zero and set the index per the empty-market convention instead of clamping to `SUPPLY_INDEX_FLOOR_RAW`; alternatively, record the wiped state so `resolve_withdrawal`/`unscale_supply_floor` return zero for shares minted before the write-down. At minimum, make `require_reserves` or the withdrawal path aware that post-clamp claims are unpayable, so a stranded share cannot redeem against unrelated fresh cash. Add a regression asserting `unscale_supply_floor(pre_wipe_scaled) == 0` after a full-wipe `apply_bad_debt_to_supply_index`.

```rust
pub(crate) fn apply_bad_debt_to_supply_index(cache: &mut Cache, bad_debt: Ray) {
    let total_supplied_value = cache.supplied().mul(cache.env(), cache.supply_index());

    if total_supplied_value == Ray::ZERO {
        return;
    }

    let capped = bad_debt.min(total_supplied_value);
    let remaining = total_supplied_value.checked_sub(cache.env(), capped);

    let reduction_factor = remaining.div_floor(cache.env(), total_supplied_value);
    let new_supply_index = cache
        .supply_index()
        .mul_floor(cache.env(), reduction_factor);

    cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
}
```
