I have enough evidence to finalize the analog finding: the webhook `shop-domain` header is trusted as the tenant identity but is not part of the HMAC-signed bytes.### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then trusts the unauthenticated `x-shopify-shop-domain` header to identify which tenant the webhook belongs to. Because the header is never part of the signed bytes, an attacker who has one valid `(raw_body, hmac)` pair (e.g. from a webhook Shopify delivered for a shop the attacker controls/installed the app on) can swap the `shop-domain` header to any other shop and the signature check still passes, causing the host application's handler to process the webhook under a victim tenant's identity.

### Finding Description
The equality that should hold for a webhook request to be considered authentic for tenant `S` is:

`bytes_verified_by_hmac == bytes_the_shop_identity_is_derived_from`

In this gem that equality is broken:

- `Utils::HmacValidator.validate(request)` computes the signature over `request.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `request.shop` is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of `@raw_body` and therefore not covered by the HMAC at all: [2](#0-1) [3](#0-2) 

- `Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity passed to the host application's handler: [4](#0-3) 

- `WebhookMetadata.shop` is the only tenant identifier surfaced to the app's `WebhookHandler#handle`, so any host app that uses `data.shop` to look up per-shop records, sessions, or access tokens is fully exposed to this mismatch: [5](#0-4) 

Compare this with the OAuth callback flow, where the shop value that ends up in the signed string (`to_signable_string`) is the *same* field (`shop`) that is later used to build the session (`auth_query.shop`) — i.e., the field acted upon is bound to the field verified: [6](#0-5) [7](#0-6) 

The webhook path has no such binding: the shop used downstream (`request.shop`, from a header) is disjoint from the bytes actually authenticated (`@raw_body`).

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged internet user who can obtain any single legitimate `(body, hmac)` pair for a topic (trivial if they can install the app on their own shop and trigger any webhook, since Shopify signs it correctly for that request) can replay that exact body/hmac to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it as valid (HMAC only checks the body) and hand the host application a `WebhookMetadata` claiming to be from a different shop. Any host application that relies on `data.shop` to decide which merchant record, access token, or session to act on (the documented, expected usage pattern) will act on the wrong tenant — for example, applying a webhook payload (e.g., `shop/redact`, `app/uninstalled`, order/customer data) to the victim shop's records, or looking up and using the victim's stored access token in a background job keyed by `data.shop`. This crosses a tenant boundary and matches the "cross-tenant access" class in scope.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus one legitimately-signed webhook body (obtainable by installing the app to any shop, including a free/dev shop, and triggering any webhook topic already registered) — no access token, secret, or privileged account is needed. This is squarely an "unprivileged internet user" scenario. The severity depends on how the host application uses `WebhookMetadata#shop`, but the gem itself provides no protection and no documented warning that the `shop` field is unauthenticated, so any typical integration (keying storage/session lookup off `data.shop`) is affected.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the header to the payload before trusting it:
- Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the string that is HMAC-verified (e.g., verify header+body together, or require the host app to independently confirm `data.shop` against a known/installed shop list keyed by validated session state) rather than validating the raw body alone and trusting an unrelated header for tenant identity.
- At minimum, document prominently that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be used alone to select which merchant's credentials/session to operate on without additional verification (e.g., cross-check against the shop associated with the currently active/looked-up session, and reject on mismatch).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and register a webhook for topic `orders/create` (or any registered topic).
2. Trigger the webhook from Shopify; capture the exact raw request the app's endpoint receives, including headers `x-shopify-hmac-sha256: <valid_hmac>` and body `<raw_body>`. The HMAC is valid because Shopify signed `<raw_body>` with the app's `client_secret`.
3. Replay the captured request to the same webhook endpoint, but replace the `x-shopify-shop-domain` header value with `victim-shop.myshopify.com`, leaving `<raw_body>` and `<valid_hmac>` unchanged.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) against `<valid_hmac>` — this still succeeds. [8](#0-7) 
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`. [9](#0-8) 
6. Any host application logic that trusts `data.shop` to select the tenant (e.g., load the victim's access token/session and perform data mutation, or process a redact/uninstall action against the victim) is invoked against the wrong tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
