### Title
Webhook shop/topic/webhook_id attribution not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from caller-supplied HTTP headers and are never included in the HMAC-signed material [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

### Finding Description
The binding the gem is supposed to enforce is: `HMAC-verified body == data attributed to shop X`. In reality the equality that holds is only `HMAC-verified body == body bytes`; the `shop` (and `topic`/`webhook_id`) fields are unauthenticated header values that the HMAC computation never covers, since `compute_signature` is calculated over `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body` [5](#0-4) .

An unprivileged internet user who legitimately controls their own Shopify development store can receive a genuine, correctly-signed webhook from Shopify for their own shop (a body + valid HMAC pair, since Shopify signs webhooks with the app's `client_secret`, which this attacker's own store's webhook delivery uses just like any other shop that installed the app). They can then replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to name a *different, victim* shop. Because `HmacValidator.validate` only checks the body bytes, the forged request still validates successfully [6](#0-5) , and `Registry.process` calls the app's handler with `shop: request.shop` set to the attacker-chosen victim shop domain [7](#0-6) .

### Impact Explanation
Applications built on this gem generally trust `WebhookMetadata#shop` to key data mutations, cache invalidation, uninstall/redact flows, or session/store lookups for the shop named in the webhook. Since that field is not bound to the signature, an attacker who has installed the app on any shop they control can forge webhook events that are processed as if they originated from an arbitrary victim shop, resulting in cross-tenant data corruption or triggering of shop-scoped business logic outside the attacker's own tenant.

### Likelihood Explanation
Exploitation only requires installing the target app on any shop the attacker controls (a normal, unprivileged Shopify merchant/developer action), capturing one legitimately delivered webhook body+HMAC, and replaying it with a modified `shop-domain` header to the same public webhook endpoint. No access to the app's `client_secret`, access tokens, or the victim's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind `request.shop` to the verified payload before it is trusted (e.g., verify the value against a previously stored, authenticated association for that specific webhook subscription id) rather than trusting the unauthenticated header end-to-end in `Registry.process`.

### Proof of Concept
1. Attacker installs the victim app on their own shop `attacker.myshopify.com` and lets Shopify deliver a normal webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both are visible to the attacker since they own the destination endpoint or can intercept their own traffic).
2. Attacker POSTs to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the HMAC) [6](#0-5) , and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to act on data intended for the victim tenant.
