## Title
Webhook `shop-domain` / `topic` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string as only the raw request body, while the `shop`, `topic`, and `webhook_id` fields the app actually acts on are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts the request as long as the body's HMAC matches, then dispatches the handler using the header-derived (unsigned) `shop` and `topic`. This breaks the identity binding: `bytes verified by HMAC (body only)` != `bytes the app trusts for tenant identity (shop-domain / topic headers)`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers, which are never included in the signable string: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — i.e., the body's HMAC — then immediately hands the header-derived `shop`/`topic`/`webhook_id` to the app's handler as trusted tenant metadata: [3](#0-2) 

`Utils::HmacValidator.validate` / `validate_signature` compute the HMAC over `verifiable_query.to_signable_string` (the raw body for webhooks) and compare it to the received signature — headers play no part in the computation: [4](#0-3) 

Because the HMAC only binds the *body bytes*, and the app's tenant-identifying fields (`shop`, `topic`, `webhook_id`) come from headers outside that binding, any request carrying a body+HMAC pair that was legitimately produced by Shopify for *any* shop (e.g., the attacker's own store, or a body the attacker manages to capture) will pass `HmacValidator.validate` even if the `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` headers are swapped to arbitrary values. The handler then runs with `WebhookMetadata.shop` and `.topic` set to attacker-chosen values, while `body` is the (still HMAC-valid) attacker-controlled content.

### Impact Explanation
This crosses a tenant boundary: an app whose webhook handler branches or persists data keyed by `data.shop` (the normal, documented way to use this field, per `WebhookMetadata`) can be made to process/store attacker-supplied body content under a victim shop's identity, or to trigger handlers for topics never actually sent by Shopify for that shop. This fits the Critical "cross-tenant access" category, since the merchant/tenant identity the app relies on (`shop`) is not the identity actually authenticated by the cryptographic check.

### Likelihood Explanation
Medium-to-High for an unprivileged internet user with reachability to the app's public webhook endpoint: the attacker needs one valid `(raw_body, hmac)` pair, which is trivially obtainable by installing the target app on the attacker's own development/test store and capturing a real webhook delivery (any topic registered by the app). No `client_secret`, access token, or privileged account on the *victim* is required — only knowledge of the app's own `api_secret_key`-derived signature over attacker-controlled body content, which the attacker gets for free by triggering their own store's webhooks.

### Recommendation
Bind the header-derived identity fields into the signable content, or otherwise cryptographically tie `shop-domain`/`topic`/`webhook-id` to the HMAC (e.g., include them in `to_signable_string`, or require the caller to independently confirm the `shop-domain` header against a shop known to have installed the app with a matching webhook subscription before invoking handlers). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as the sole tenant-identity check by consuming apps.

### Proof of Concept
```ruby
# Attacker step 1: install the target app on their own store "attacker.myshopify.com"
# and capture a legitimate webhook delivery for a registered topic, e.g. "orders/create".
# Shopify sends:
#   body   = '{"id":1,"note":"legit body from attacker store"}'
#   hmac   = Base64.encode64(OpenSSL::HMAC.digest("sha256", app_secret, body))  # valid, signed by Shopify

captured_body = '{"id":1,"note":"legit body from attacker store"}'
captured_hmac = "..." # real Shopify-issued signature for captured_body

# Attacker step 2: replay the body+hmac pair against the same endpoint,
# but with shop-domain / topic headers pointing at a victim shop and/or
# a different registered topic.
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: spoofed_headers)

# Passes HMAC validation because only captured_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process dispatches the handler believing the event is from "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: attacker JSON, ...)
``` [3](#0-2)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          received_signature = verifiable_query.hmac
