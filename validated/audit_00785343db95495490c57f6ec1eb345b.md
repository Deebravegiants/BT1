### Title
Tron `IntentGatewayV2::placeOrder()` does not refund excess native token overpayment, permanently locking user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` accepts `msg.value` for native-token order inputs and solver fees but never validates or refunds any surplus. Unlike the EVM `src/apps/IntentGatewayV2.sol` version of the same function, which explicitly refunds unspent `msgValue` back to the caller, the Tron implementation silently retains any overpaid native token in the contract with no path for the user to reclaim it.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` tracks native token consumption via a local `msgValue` counter that is decremented as inputs and fees are processed: [1](#0-0) [2](#0-1) 

After all inputs and fees are debited from `msgValue`, the function emits `OrderPlaced` and returns immediately — there is no check that the leftover `msgValue` is zero, and no refund of any residual amount to `msg.sender`: [3](#0-2) 

This is directly analogous to the reported `Allo::_fundPool()` issue, where `msg.value` is never reconciled against the intended `amount`, so any user who sends more native token than strictly required loses the difference.

By contrast, the canonical EVM implementation of the same function explicitly guards against this by refunding any unspent value: [4](#0-3) 

and this refund behavior is asserted by dedicated tests (`testPlaceOrder_RefundsExcessNativeToken`, `testPlaceOrder_ExactNativeToken_NoRefundNeeded`) that exist only for the EVM path: [5](#0-4) 

The Tron contract lacks this refund entirely, confirming the divergence is a genuine gap rather than an intentional design difference elsewhere in the file.

### Impact Explanation
Any user placing an order with a native-token input or paying solver fees in native token on the Tron deployment who supplies `msg.value` greater than the sum of `order.inputs[i].amount` (native leg) plus the native amount swapped for `order.fees` will have the surplus permanently stuck in the `IntentGatewayV2` contract balance. There is no user-facing mechanism shown in this function to recover it — it becomes de facto locked/lost funds for the depositor, matching the "permanent freezing of funds" criterion.

### Likelihood Explanation
This can be triggered by any ordinary user in a single `placeOrder{value: X}(...)` call whenever `X` exceeds the exact required native amount (e.g., due to a wallet/UI providing extra buffer, a slippage in the Uniswap `swapETHForExactTokens` fee-quote, or a simple user mistake). No special privileges are needed, and this is a normal flow, not an edge case induced by an attacker acting maliciously.

### Recommendation
Mirror the EVM implementation: after processing inputs and fees, check if any `msgValue` remains and refund it to `msg.sender` before returning, e.g.:
```solidity
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
placed just before (or as part of) the `OrderPlaced` emission in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. User calls `placeOrder{value: inputAmount + overpayment}(order, graffiti)` where `order.inputs[0] = TokenInfo({token: address(0), amount: inputAmount})` and `order.fees = 0`.
2. Inside `placeOrder`, `msgValue` starts at `inputAmount + overpayment`; the native-input branch decrements it by exactly `inputAmount`, leaving `overpayment` in `msgValue`. [6](#0-5) 
3. Since `order.fees == 0`, the fee-swap branch is skipped, so `msgValue` (`overpayment`) is never spent.
4. The function proceeds directly to emitting `OrderPlaced` and returns, without refunding the leftover `overpayment` — those funds remain trapped in the contract's native balance, matching the exact test scenario `testPlaceOrder_RefundsExcessNativeToken` proves refunds for on EVM but which Tron's contract has no equivalent code path for.

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }
