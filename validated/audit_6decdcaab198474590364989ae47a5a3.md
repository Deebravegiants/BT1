## Analysis

I mapped the bug class ("bytes verified vs. bytes parsed") onto the webhook‑processing code in this gem.### Title
Webhook `shop-domain` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop and topic once `Utils::HmacValidator.validate(request)` returns true, but the HMAC only ever covers the raw request body, never the `shop-domain` or `topic` headers that the handler is told to trust.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` uses this body-only check as authorization for the entire request, then hands the *header-derived* (unverified) `shop` and `topic` values straight to the app's handler as if they were verified facts: [3](#0-2) 

`request.shop` and `request.topic` are parsed straight from the `x-shopify-shop-domain` / `shopify-shop-domain` and `x-shopify-topic` / `shopify-topic` headers with no cryptographic binding to the body: [4](#0-3) 

This breaks the equality the caller relies on: `shop authenticated by HMAC == shop passed to WebhookMetadata`. In reality, `bytes verified (raw_body)` ≠ `bytes trusted (shop-domain/topic headers)`.

**Attack path (unprivileged internet user, no credentials needed):**
1. An attacker installs the target app on their own Shopify store (a normal, unprivileged merchant action — no `api_secret_key` or leaked credentials required).
2. Shopify sends the app a legitimately signed webhook for the attacker's own store, e.g. topic `orders/create` with some JSON body `B` and a valid `X-Shopify-Hmac-Sha256` computed over `B` using the app's real secret.
3. The attacker captures this `(headers, body=B, hmac=H)` triple from their own store's outbound webhook (they can trivially observe it by pointing the webhook endpoint at a server they control, or by intercepting their own traffic — no access to the app's secret is needed).
4. The attacker replays the exact same body `B` and `hmac H` to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different registered `topic` header, since `topic` is likewise excluded from the signed bytes).
5. `HmacValidator.validate` still returns `true`, because `B` and `H` are consistent — the validator only asserts "Shopify (holder of the secret) produced this body," not "for this shop/topic."
6. `Registry.process` looks up the handler for the (attacker-controlled) topic and invokes it with `shop: "victim-shop.myshopify.com"`, `body: parsed(B)` — i.e., data the attacker fully controls, attributed to a shop the attacker does not own.

### Impact Explanation
Any app built on this gem that uses `request.shop` from `WebhookMetadata` to select tenant-scoped storage, trigger per-shop side effects (e.g., updating billing state, provisioning resources, writing to a shop's settings/data), or otherwise branch business logic by shop identity is exposed to cross-tenant data injection/corruption: an attacker who is a legitimate but unprivileged installer of the app on their own store can make the app believe an arbitrary controlled payload originated from a different, victim shop. This matches the High-impact category of "cross-tenant access" from a party holding no privileged credentials for the victim tenant.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires only (a) installing the app on an attacker-owned store (which any Shopify merchant can do for public apps) and (b) capturing one legitimate webhook body/HMAC pair, both of which are trivially available to the attacker without needing the app's `client_secret` or any privileged/internal access. The only constraint is that the attacker can only replay bodies Shopify has actually signed for *some* shop (their own), not arbitrary bodies — but shop/topic headers are completely unconstrained, which is enough to redirect that captured payload to any victim shop.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the material that `HmacValidator` verifies, or at minimum have `Registry.process` cross-check `request.shop` against the shop the handler expects/owns (e.g., an app-provided allowlist or session lookup) before invoking `handler.handle`. Since Shopify's own webhook HMAC format only signs the body, the gem should document this limitation explicitly and/or provide a way for consuming apps to bind the header-derived `shop` to a value they can independently trust (e.g., matching against previously stored, OAuth-derived shop domains) rather than passing the raw header value through as trusted metadata.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app there.
# Shopify sends a legitimate webhook for that shop:
body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, body) # attacker cannot compute this themselves,
                                                                            # but captures it from their own store's webhook delivery

# Attacker replays it against the same endpoint with a forged shop-domain header:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac), # unchanged, still valid for `body`
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, NOT covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+hmac match)
# => handler.handle invoked with shop: "victim-shop.myshopify.com", attacker-controlled body
```
