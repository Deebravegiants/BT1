### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC-over-body [3](#0-2) , then trusts `request.shop`/`request.topic` to route the payload and to populate `WebhookMetadata`, which is the tenant-identity value handlers use to persist/act on data.

### Finding Description
The HMAC validator computes and compares a signature only over `to_signable_string`, which for webhooks is the raw JSON body: `Digest.hexencode` of the header value is compared against `HMAC-SHA256(secret, @raw_body)` [4](#0-3) . The `shop` accessor, however, is taken directly and unconditionally from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to that header's value [5](#0-4) . The same is true for `topic`, `webhook_id`, and `api_version`.

`Registry.process` raises only if the body-HMAC fails, then immediately looks up the handler by the (unauthenticated) `topic` and constructs `WebhookMetadata` using the (unauthenticated) `shop`: [3](#0-2) 

Because a webhook's cryptographic integrity is bound only to the body bytes and not to the `shop`/`topic` header values, the equality the code relies on — "the shop that produced a validly-signed request" == "the shop attributed to that request for tenant routing/storage" — does not hold. Any party who can obtain one validly-HMAC'd webhook body (trivially available to any merchant who installs the app on their own store, since Shopify will send them real, validly signed webhooks for their own shop's events) can replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a different, victim tenant. The HMAC check still passes because it never examined those headers, and the app-level handler then processes/stores the attacker-chosen JSON body as if it belonged to the victim shop.

### Impact Explanation
Critical — this breaks the shop/tenant identity binding that all app-side webhook handlers rely on for multi-tenant isolation, enabling cross-tenant data injection/confusion: an unprivileged merchant (attacker on their own store) can cause a receiving app to process and persist attacker-controlled webhook payloads under another (victim) shop's identity, without ever needing the app's `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Medium-High — the only prerequisite is that the attacker install the target app on a store they control (a normal, unprivileged action any merchant can take) and can capture/replay a raw HTTP request. No secret material, TLS interception, or social engineering is required; the vulnerable code path (`Utils::HmacValidator.validate` / `Webhooks::Registry.process` / `Webhooks::Request`) is exercised on every webhook delivery.

### Recommendation
Bind the identity-critical fields into the signed content, or otherwise cryptographically/contextually verify them:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable payload used for HMAC verification (e.g., derive the signable string from headers+body rather than body alone), or
- Require the caller to supply/verify an expected shop for each webhook subscription and reject requests whose header `shop` does not match a shop that this app instance's registry expects for the delivered `webhook_id`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Attacker triggers an event on their own store, causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-for-body>`
   - Body: JSON the attacker fully controls (their own order data).
3. Attacker captures this raw request and resends it to the same public webhook endpoint, keeping the body and the valid `X-Shopify-Hmac-Sha256` header unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes HMAC over `@raw_body` and succeeds [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_json, ...)` [8](#0-7) , and the app persists/acts on attacker data under the victim tenant's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
