### Title
Manipulable Uniswap V2 spot-price swap in `EvmHost.dispatch()`/`fundRequest()` lets an attacker overpay native ETH for a fixed feeToken amount, permanently trapping the surplus ETH in the host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all use `swapETHForExactTokens` against a directly configured `_hostParams.uniswapV2` router with no minimum-output/maximum-input bound and no reference-price sanity check, converting a caller-supplied `msg.value` into an exact `post.fee`/`get.fee`/`amount` of `feeToken`. Any leftover, unswapped ETH from the `msg.value` is never refunded to the caller inside the Host — this mirrors the bDollar root cause: an on-chain flow that reacts passively to a manipulable AMM price, using funds supplied for one purpose (dispatch fee payment) at a rate an attacker controls in the same transaction, with the delta becoming stuck/lost value rather than protocol-owned reinvestment.

### Finding Description
`dispatch(DispatchPost)` in `evm/src/core/EvmHost.sol` (lines 921-932):
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The same pattern repeats verbatim in `dispatch(DispatchGet)` and `fundRequest()`. [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` uses the router's live spot reserves to determine how much ETH is consumed to deliver exactly `post.fee` tokens; standard UniswapV2Router02 semantics refund unused ETH to `msg.sender` (the caller invoking `router.swapETHForExactTokens`, which here is `EvmHost` itself since it calls with `{value: msg.value}`). Because `EvmHost` is the caller of the router, any refunded ETH lands in `EvmHost`, not back to the original transaction sender — the docs explicitly confirm callers are expected to send `msg.value` and get no further handling back: "User must send enough native tokens to cover fees" with no mention of a refund path. [4](#0-3) 

The protocol's own documentation independently flags this router's spot price as sandwich-manipulable when read by `quote()`/`getAmountsIn` off-chain: "Do not call `quote()` in smart contract transactions. It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks." [5](#0-4) 

Yet the on-chain `dispatch()`/`fundRequest()` paths execute the equivalent swap live, in the same transaction, against the same pool, with `path[0] = WETH, path[1] = feeToken`, no `amountInMax` bound, and no check that the pool's reserves haven't been artificially skewed by a prior swap in the same block/transaction (e.g., via a flashloan-funded large trade against the exact `uniswapV2` pool configured in `_hostParams`). An attacker who sandwiches or front-runs their own `dispatch()` call by first dumping WETH into (or pulling feeToken out of) the configured Uniswap V2 pool can force `swapETHForExactTokens` to consume dramatically more ETH than the fair-market cost of `post.fee` tokens, while any leftover ETH refunded by the router stays trapped in `EvmHost` (since `EvmHost` never forwards the refund to `_msgSender()`), and the "true" fee-payer bears an inflated, attacker-influenced native-token cost with no protection.

### Impact Explanation
This is a Medium-severity issue reachable by any unprivileged party who calls `dispatch()`/`fundRequest()` with native `msg.value` (the same entrypoint every `HyperApp` that dispatches a POST/GET request with native payment relies on, per the SDK/docs). Consequences:
- Permanent loss/freezing of native ETH: unused ETH refunded by the router to `EvmHost` (rather than the caller) is not tracked or made withdrawable anywhere in `dispatch()`/`fundRequest()`, so it is stranded in the contract — a "permanent freezing of funds" outcome.
- Users/apps paying dispatch fees in native token can be forced to overpay for the feeToken leg of a self-manipulated pool trade, since the swap uses live spot price with no slippage/price-bound protection (`amountInMax` is effectively `msg.value`, an unbounded ceiling), diverging from the bDollar pattern where a contract passively transacted against an attacker-inflated price when performing its own on-chain action (adding liquidity vs. here, swapping ETH for fee tokens).

### Likelihood Explanation
Likelihood is limited by the fact that the caller itself controls `msg.value` and is typically also the party harmed by overpaying — an external attacker cannot force a *victim's* `dispatch()` transaction to consume more ETH without also controlling timing (e.g., via MEV sandwiching the victim's `dispatch()` call, which is realistic on public mempools) or the victim self-inflicting loss is not attacker profit-motivated. The stranded-refund-ETH class, however, requires no adversarial pool manipulation at all — it happens on ordinary favorable price movement between `msg.value` sizing and actual dispatch execution, making the fund-loss vector (trapped ETH accumulating in `EvmHost`) more likely to occur incidentally than as a deliberate high-profit attack, tempering severity to Medium rather than High/Critical.

### Recommendation
- Track and expose any residual ETH balance in `EvmHost` after `swapETHForExactTokens` calls, and refund it to `_msgSender()` (or `post.payer`/`get.payer`) at the end of `dispatch()`/`fundRequest()`, mirroring what `UniswapRouterV2` would normally refund to a direct caller.
- Add an `amountInMax` parameter (or a configurable max native-cost bound) to `dispatch()`/`fundRequest()` so callers can cap the ETH they are willing to spend, and revert if the live pool price would exceed it — consistent with how `docs/content/developers/evm/messaging/get-requests.mdx` already warns against reading `quote()` on-chain due to sandwich risk.
- Consider adding a TWAP or bounded-deviation guard (similar to the `referencePrice`/`maxDeviationBps` pattern already used in the Simplex Uniswap pricing config) before trusting the router's instantaneous reserves for a state-changing token swap.

### Proof of Concept
1. Attacker identifies the `uniswapV2` router/pool configured in `EvmHost._hostParams.uniswapV2` for `WETH -> feeToken()`.
2. Attacker (or MEV bot) front-runs a pending `dispatch(DispatchPost)`/`dispatch(DispatchGet)` transaction that sends `msg.value` ETH, by swapping a large amount of feeToken out of the pool (or WETH into it), sharply raising the WETH price of `feeToken`.
3. The victim's `dispatch()` call executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` against the now-skewed pool — consuming far more ETH than fair value to acquire the fixed `post.fee` amount of feeToken, per lines 921-932 of `evm/src/core/EvmHost.sol`. [1](#0-0) 
4. Attacker back-runs by reversing their swap, extracting the price premium as profit; meanwhile any ETH left in `EvmHost` from `swapETHForExactTokens`'s internal refund logic is not forwarded back to the caller anywhere in `dispatch()`, `fundRequest()`, or the surrounding contract, so it accumulates as stranded value in `EvmHost`.
5. Repeat across dispatch calls to continually siphon value from native-fee payers and strand ETH in the Host contract, with no on-chain price-deviation guard preventing it (confirmed absent by inspection of `dispatch()`, `fundRequest()`, and `IDispatcher.sol`'s documented behavior). [6](#0-5)

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
}
```
