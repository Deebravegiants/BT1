### Title
`onPostRequestTimeout` refund path is gated by `whenNotPaused`, letting the owner permanently freeze users' burned bridge funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` all gate their timeout-refund handler with the same `whenNotPaused` modifier used for `send()`/`onAccept()`. This mirrors the Telcoin finding: a "pause" that is meant to stop new deposits/sends also blocks the withdrawal/refund path for funds a user has *already* burned or locked, with no time limit and no alternative recovery mechanism.

### Finding Description
`send()` burns (or locks) a user's tokens and dispatches a cross-chain POST request. If that request times out without being relayed/delivered, the *only* recovery path is `onPostRequestTimeout`, which re-mints (or unwraps/transfers back) the user's funds: [1](#0-0) [2](#0-1) 

The same pattern exists in the upgradeable variant: [3](#0-2) 

and in the wrapped/ERC20-backed variant, where the refund also unwraps WETH or transfers the underlying ERC20 back to the user: [4](#0-3) 

All of these refund functions carry the `whenNotPaused` modifier, the exact same modifier that gates the deposit-side `send()` call and the receive-side `onAccept()` call: [5](#0-4) 

Because `pause()`/`unpause()` are `onlyOwner` and unbounded in time, once the owner pauses the contract (e.g., in response to an incident, or simply left paused), any user whose `send()` request times out while the contract is paused cannot reclaim their already-burned/locked tokens until the owner chooses to unpause. There is no separate, always-open withdrawal/refund entry point that bypasses the pause, unlike the deposit path which the pause is presumably meant to protect. This is the exact bug class from the referenced report: pausing indiscriminately blocks both new deposits and the return of funds already committed by users, rather than restricting the pause to only the risky deposit/mint surface.

`BridgeToken` (the nexus-backed token) additionally overrides `onAccept`/`onPostRequestTimeout` to add relayer gating but still calls `super.onPostRequestTimeout`, inheriting the same `whenNotPaused` restriction: [6](#0-5) 

### Impact Explanation
If a `send()` transaction times out (the request is never delivered before its timeout) while the token contract is paused, the sender's funds are burned/locked but the refund mint/transfer via `onPostRequestTimeout` reverts due to `whenNotPaused`. The user cannot recover their funds until the contract owner unpauses — and there is no guaranteed timeline for that. This is a freezing-of-funds condition: assets that should be unconditionally recoverable become contingent on an owner's discretionary action. For any relayer, or a user retrying/relaying their own timeout proof, this makes an otherwise permissionless recovery path privilege-gated by the pause switch.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an in-flight cross-chain transfer that times out (a routine occurrence under network congestion, relayer downtime, or destination-chain issues) to coincide with (b) the contract being paused (a legitimate, foreseeable owner action during an incident response). Since pausing is explicitly designed as an emergency/circuit-breaker mechanism, the overlap between "an incident just occurred" and "in-flight transfers are timing out" is realistic rather than contrived — incidents are often accompanied by network/relayer disruption that increases timeout frequency.

### Recommendation
Do not gate the refund/timeout-recovery path (`onPostRequestTimeout`) with `whenNotPaused` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol`. Pausing should stop new outbound `send()`s and/or new inbound `onAccept()` mints (to contain an active exploit), but the mechanism that returns previously-escrowed/burned funds to their rightful owner after a timeout should remain callable regardless of pause state, consistent with the "withdrawals should never be paused" principle.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`, burning `amount` tokens and dispatching a POST request with a timeout (`dispatch{value}` / `dispatchWithFeeToken`) — `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-282`.
2. The destination chain/relayer fails to deliver the request before `timeoutTimestamp` elapses (e.g., relayer outage during a security incident).
3. Owner calls `pause()` on the token in response to the incident — `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:213-215`.
4. A relayer submits the timeout proof and calls `onPostRequestTimeout` to refund the user; the call reverts because of `whenNotPaused` — `sdk/packages/core/contracts/apps/HyperFungibleToken.sol:321`.
5. The user's burned tokens remain unrecoverable until the owner calls `unpause()`, which may not happen promptly (or at all) if the incident response leaves the contract paused indefinitely.

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
