### Title
Value-transferring EVM `CALL`s always classify as `AllowReentry` regardless of stipend gas, defeating the `AllowNext` reentrancy mitigation - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

### Summary
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides the reentrancy level for an EVM `CALL` using a `match` on `(value.is_zero(), gas_limit == CALL_STIPEND)`. Because the `(false, _)` arm is listed first, **every** value-transferring call (`value != 0`) is routed to `ReentrancyProtection::AllowReentry`, irrespective of the gas amount passed - including the exact `gas_limit == 2300` stipend case that `ReentrancyProtection::AllowNext` was specifically designed to guard.

### Finding Description
The heuristic is implemented as: [1](#0-0) 

```
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
```

Rust `match` evaluates arms top-down, so any call with `value != 0` is captured by `(false, _)` before the `gas_limit == CALL_STIPEND` check is even consulted. The doc comment on `ReentrancyProtection::AllowNext` explicitly states this variant exists for calls that "transfer value but restrict gas so the callee only has a stipend gas amount," because "due to gas scale differences that guarantee does not automatically hold in revive and we enforce it explicitly here": [2](#0-1) 

Yet the code never reaches `AllowNext` when `value != 0` - the exact scenario the comment describes. `AllowNext` is only reachable for `value == 0 && gas_limit == 2300` (the `.transfer(0)`/`.send(0)` corner case per the accompanying prdoc), which carries no fund-transfer risk to begin with.

Meanwhile, `add_stipend = true` for the value-transfer case causes `determine_call_stipend::<T>()` (a real, non-zero weight derived from `EVMGas(CALL_STIPEND)` plus `DepositEvent` weight) to be added to the callee's frame budget: [3](#0-2) 

So the callee genuinely receives usable weight/resources (unlike real Ethereum where 2300 gas is provably insufficient for a further `CALL`), but is granted `AllowReentry`, meaning `Stack::call` never sets `top_frame_mut().allows_reentry = false`: [4](#0-3) 

With `AllowReentry`, nothing blocks the callee from calling back into the caller's frame while it is still on the call stack, i.e., before the caller (victim) has finalized its post-call storage/balance updates - the classic checks-effects-interactions violation the 2300-gas stipend was invented to prevent.

### Impact Explanation
A contract that performs a value-transferring external call intending to rely on the (perceived) 2300-gas-stipend reentrancy guarantee - the same pattern Solidity's `.transfer()`/`.send()` rely on in real Ethereum - gets no reentrancy protection at all in revive. The callee can reenter the caller mid-execution, read/mutate state before the caller's own accounting is finalized, and drain balance or corrupt storage-deposit accounting, matching the scoped impact of fund theft via inconsistent intermediate contract state.

### Likelihood Explanation
This is directly reachable by any unprivileged EVM contract: an attacker deploys two contracts (or induces a victim contract to call an attacker-controlled contract with `value > 0`), and the vulnerable arm is hit for **every** nonzero-value `CALL`/`STATICCALL` regardless of the gas operand - not merely the narrow `gas_limit == 2300` case from the question, making it trivially and repeatably triggerable via ordinary contract deployment and standard `CALL` opcode usage (crafted bytecode or even certain compiler-generated patterns).

### Recommendation
Reorder the heuristic so the stipend-gas check takes precedence over the value check, e.g.:
```rust
let (add_stipend, reentracy) = if gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND) {
    (true, ReentrancyProtection::AllowNext)
} else if !value.is_zero() {
    (true, ReentrancyProtection::AllowReentry) // or reconsider whether this should also be restricted
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```
More importantly, revisit whether relying on `AllowReentry` for any value-transfer with attacker-controllable gas is safe at all, given revive's stipend maps to real usable weight; consider applying `AllowNext` (or `Strict`) whenever `add_stipend` is true, independent of `value.is_zero()`.

### Proof of Concept
Rust unit test extending `substrate/frame/revive/src/exec/tests.rs` patterns (e.g. alongside `call_deny_reentry`):
1. Deploy `Victim` EVM bytecode that does `CALL(attacker, value=1, gas=2300)` then writes `victimBalanceAfter = balance(this)` to storage after the call returns.
2. Deploy `Attacker` EVM bytecode whose fallback, upon being called by `Victim`, immediately issues a second `CALL` back into `Victim` (re-entering before `Victim`'s post-call storage write executes).
3. Assert that `ext.call(..., value=1.into(), ReentrancyProtection::AllowReentry-or-AllowNext-as-computed-by-run_call, false)` succeeds and that the nested re-entrant call into `Victim` is **not** rejected with `Error::<T>::ReentranceDenied` - proving `AllowReentry` (not `AllowNext`) was granted despite `gas_limit == CALL_STIPEND`.
4. Extend with an integration/fuzz test sweeping `gas_limit` around `2299/2300/2301` with `value = 1` to confirm the reentrancy classification never becomes `AllowNext` for any nonzero value, and assert final `Victim` balance reflects double-spend/inconsistent state versus the expected single-transfer outcome.
