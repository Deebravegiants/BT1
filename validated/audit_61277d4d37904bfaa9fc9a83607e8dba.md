Based on the code confirmed, the vulnerability is clear: the HMAC in `Webhooks::Request` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unsigned HTTP headers and passed straight through to the app's handler.

### Title
Webhook shop/topic identity is trusted from unsigned headers while only the body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used to route the request and populate `WebhookMetadata` (which the host app treats as the authenticated tenant identity) are read directly from HTTP headers that are never included in the signed content [2](#0-1) .

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and compares it to the `hmac` extracted from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header [4](#0-3) . None of `shop`, `topic`, `webhook_id`, or `api_version` — all sourced from separate headers via `shopify_header` [5](#0-4)  — are covered by that signature.

`Registry.process` uses `request.topic` to look up the handler and forwards `request.shop` unchecked into `WebhookMetadata`, which the app's handler treats as the identity of the originating store [1](#0-0) .

This breaks the identity binding: `hmac-verified bytes (body)` ≠ `bytes acted upon (shop header)`. Because a given app's `api_secret_key` is shared across every shop that installs it (it is not per-shop), any merchant who has installed the app can legitimately receive a real webhook with a valid body+HMAC pair for their own shop. That merchant can then replay the identical body and HMAC while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a different, victim shop's domain. `HmacValidator.validate` will still succeed, since it only checks the untouched body bytes, and the handler will process the (attacker's own) body as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an app's webhook handler can be made to attribute forged/replayed webhook data to an arbitrary victim shop, letting one merchant impersonate another for a shared app's server-side event processing (e.g., triggering shop-scoped side effects such as GDPR data requests, order/customer sync logic, or entitlement changes keyed by `shop`). This matches the Critical "cross-tenant access" category since the attacker crosses the shop/tenant boundary using only their own legitimate app installation, without needing the app's `api_secret_key` or any privileged credential.

### Likelihood Explanation
Any merchant who installs the vulnerable app has everything needed: a stream of validly-signed webhook bodies for their own shop and full control over the HTTP headers of the request they replay to the app's webhook endpoint (headers are not part of Shopify's HMAC-signed payload by design, and this gem does nothing to re-bind them). No secret material, TLS interception, or social engineering is required.

### Recommendation
Do not trust `request.shop` (or `topic`/`webhook_id`) as authenticated identity data. At minimum, document that these header values are unauthenticated and that host applications must cross-check `shop` against a known/registered shop for the given app before acting on the payload, or bind the shop domain into the HMAC verification step (e.g., require callers to additionally validate `shop` against the session/store that requested the webhook registration) inside `Registry.process` before dispatching to a handler.

### Proof of Concept
1. App "Acme" is installed on `attacker.myshopify.com` and `victim.myshopify.com`, sharing one `api_secret_key`.
2. Shopify sends a real webhook to Acme's endpoint for `attacker.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: customers/data_request`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"customer": {...attacker's own data...}}`
3. Attacker captures this exact body and HMAC header, then re-sends it to the same endpoint but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC over `@raw_body` only [3](#0-2)  — validation succeeds because the body is unchanged.
5. `WebhookMetadata.new(shop: request.shop, ...)` now reports `shop: "victim.myshopify.com"` [6](#0-5) , and the app's handler processes attacker-controlled data as if it belongs to the victim shop.
