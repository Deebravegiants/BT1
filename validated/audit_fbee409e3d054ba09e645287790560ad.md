### Title
Webhook HMAC signs only the raw body, letting an attacker who owns any valid signed webhook forge `shop` for cross-tenant delivery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the body was HMAC-signed with the app's secret; it never binds that signature to the `shopify-shop-domain` header. Because the same app-level `client_secret` signs webhooks for every shop that installs the app, an attacker who installs their own dev shop can obtain a validly-signed body+HMAC pair and replay it to the app's webhook endpoint with a forged `shopify-shop-domain` header, causing `Webhooks::Registry.process` to invoke the handler with an attacker-chosen `shop` value.

### Finding Description
The broken binding, stated as an equality: the code implicitly assumes `HMAC_valid(raw_body) == shop_header_authentic`, but in reality `HMAC_valid(raw_body)` only proves `raw_body` was signed by the app's `api_secret_key` at some point (for any shop that has the app installed) — it says nothing about which shop header accompanies this specific delivery.

Code path:
- `Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) .
- `Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header value, never touching `shop` [3](#0-2) .
- `Registry.process` gates only on `HmacValidator.validate(request)`, then looks up the handler by `request.topic` and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` using the unauthenticated `request.shop` [4](#0-3) .

Because Shopify's webhook HMAC is signed with the single app `client_secret` shared across all merchants of the app (not a per-shop secret), any body+HMAC pair the attacker legitimately receives on their own installed dev shop is a valid signature for that exact body under the app's key, regardless of which shop it was delivered for. The attacker replays that same body/HMAC to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to the victim's domain. `HmacValidator.validate` still returns `true` (body+HMAC unchanged), `NoWebhookHandler`/topic checks pass normally, and `handler.handle` executes with `data.shop == "victim-shop.myshopify.com"` even though that shop never signed or sent this delivery. No other guard in the gem (no `ShopValidator.sanitize!` call, no session lookup, no IP allow-list) intervenes in this path.

### Impact Explanation
This is a cross-tenant authentication bypass at the webhook layer: the handler is invoked believing the payload originates from `victim-shop.myshopify.com`, when in fact it is attacker-controlled content signed against the attacker's own dev-shop delivery. Any merchant-scoped side effect the handler performs (queuing jobs keyed by shop, mutating per-shop state, billing, GDPR redaction actions, inventory sync, etc.) is executed under the wrong tenant's identity. This is repeatable against any shop domain the attacker chooses to put in the header, for every topic the app has registered, as long as the attacker can obtain one valid signed delivery for a body of their choosing (trivial — they control their own dev shop's data that triggers the webhook body).

### Likelihood Explanation
Preconditions are minimal and fully attacker-controllable: install the app on a free dev shop (standard, unprivileged action), trigger any webhook topic the app subscribes to, capture the resulting `raw_body` + `hmac-sha256` header, then POST it to the app's public webhook route with a rewritten `shopify-shop-domain`/`shopify-shop-domain` header. No secrets, no privileged access, and no interaction with the victim are required. The attack is cheap and fully repeatable.

### Recommendation
Do not trust `request.shop` (or any other unsigned header) as an authenticated tenant identifier. At minimum, cross-check the delivered `shop` against a shop the app actually has an active session/webhook registration for, and/or incorporate the shop domain into an application-level integrity check before dispatching to the handler (Shopify webhooks don't sign headers, so the gem should not present `request.shop` to handlers as if it were verified — this should be documented clearly, and ideally the registry should validate that a registration/subscription exists for that specific shop+topic combination, e.g. via a stored webhook_id/shop mapping, before invoking `handler.handle`).

### Proof of Concept
```ruby
# test/webhooks/cross_tenant_forgery_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class CrossTenantForgeryTest < Minitest::Test
      def test_hmac_valid_but_shop_header_is_not_authenticated
        raw_body = "{}"
        real_hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )

        forged_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
          "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not the signing shop
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

        # Binding check: HMAC(raw_body) is valid...
        assert(ShopifyAPI::Utils::HmacValidator.validate(request))
        # ...yet request.shop equals the attacker-forged value, not any signing-shop identity
        assert_equal("victim-shop.myshopify.com", request.shop)

        # Confirm Registry.process invokes the handler with the forged shop
        handler_shop = nil
        handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| handler_shop = data.shop })
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
        )
        ShopifyAPI::Webhooks::Registry.process(request)
        assert_equal("victim-shop.myshopify.com", handler_shop)
      end
    end
  end
end
```
This demonstrates both sides of the broken equality: `HmacValidator.validate(request)` is `true` while `request.shop` is an arbitrary, attacker-chosen value never verified by the HMAC, and `Registry.process` forwards that unauthenticated value straight into the handler as `data.shop`.
