## Finding: PoA Bridge withdrawal status matched by `assetId` only, not by index — enables status/hash misattribution across withdrawals in the same batch

### Title
Withdrawal Status Misattribution in Batched POA Bridge Withdrawals of the Same Asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain status of a specific withdrawal (identified by `WithdrawalIdentifier.index`) by calling `findMatchingWithdrawal()`, which selects a withdrawal record purely by matching `assetId` — the `index` field is never used to disambiguate between multiple withdrawals of the same asset created in one NEAR transaction [1](#0-0) .

### Finding Description
`findMatchingWithdrawal` is documented in-code as matching only by `assetId`, explicitly acknowledging it does not support "multiple withdrawals of the same token in a single transaction" [2](#0-1) . `Array.prototype.find()` always returns the **first** withdrawal in the API response list that matches the `assetId`, regardless of which `index` was requested by `describeWithdrawal`.

The SDK's `WithdrawalIdentifier` structure was designed to distinguish withdrawals in a batch precisely via the `index` field, and `createWithdrawalIdentifiers` / `watchWithdrawal` operate over arrays of such identifiers to track a batch of withdrawals independently [3](#0-2) [4](#0-3) . If a caller submits two withdrawals of the same `assetId` within one NEAR transaction (a supported and unrestricted usage pattern — nothing in `createWithdrawalIntents` or `validateWithdrawal` prevents two identical-asset withdrawals in a batch), calling `describeWithdrawal` for index `0` and index `1` will both resolve to the *same* underlying withdrawal record from the POA indexer, since the lookup ignores index and only checks `assetId` equality.

This breaks the intended equality: **the status/txHash reported for withdrawal N must correspond to the on-chain outcome of withdrawal N**, not to a different withdrawal that merely shares the same asset.

### Impact Explanation
Concretely, in a batch of two same-asset withdrawals where withdrawal #0 completes and withdrawal #1 is still pending (or vice versa, or fails), `describeWithdrawal({index: 1, ...})` can incorrectly report `{ status: "completed", txHash: <hash of withdrawal #0> }`. An integrator/relayer using `waitForWithdrawalCompletion` / `watchWithdrawal` (which polls `describeWithdrawal` per identifier) would then treat withdrawal #1 as completed with a transaction hash that does not correspond to it — either causing a double-credit (crediting the user twice for a single actual on-chain transfer) or attributing a wrong destination transaction hash to a withdrawal request, per the rule's "status or hash misreport making an integrator credit or refund twice" — a High severity outcome.

### Likelihood Explanation
This does not require any adversarial input — it triggers under ordinary usage whenever a caller batches two or more POA-bridge withdrawals of the identical `assetId` in a single NEAR transaction (e.g., a user or integrator withdrawing the same token to two different destination addresses in one call). Nothing in `createWithdrawalIntents`, `validateWithdrawal`, or `supports()` blocks this combination [5](#0-4) .

### Recommendation
Extend `findMatchingWithdrawal` (and the underlying POA bridge indexer contract, if needed) to disambiguate by more than `assetId` — e.g., by sorting both the API withdrawal list and the local withdrawal params by amount (as the existing comment suggests) and pairing them positionally, or by requesting an explicit per-withdrawal identifier from the POA API if one becomes available. Until then, the SDK should either reject/flag batches containing duplicate `assetId` withdrawals, or explicitly surface an "ambiguous/unknown" status rather than a possibly-mismatched "completed" status with a foreign `txHash`.

### Proof of Concept
1. Build and submit a NEAR intents transaction containing two `ft_withdraw` intents for the same `assetId` (e.g., two BTC withdrawals to different addresses), producing `WithdrawalIdentifier`s with `index: 0` and `index: 1`.
2. Suppose the POA indexer completes withdrawal #0 first (status `COMPLETED`, `transfer_tx_hash: "hashA"`) while withdrawal #1 is still `PENDING`.
3. Call `bridge.describeWithdrawal({..., index: 1, withdrawalParams: { assetId: sameAssetId, ... }})`.
4. `findMatchingWithdrawal` returns the array's first match for `assetId` — the record for withdrawal #0 — so `describeWithdrawal` returns `{ status: "completed", txHash: "hashA" }` for withdrawal #1, even though withdrawal #1 has not actually settled. [1](#0-0)

```typescript
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```
