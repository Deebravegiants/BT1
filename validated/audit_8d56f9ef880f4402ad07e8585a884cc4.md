## Title
`swap_and_burn` in the Snowbridge System Frontend pallet performs a permissionless AMM swap with no slippage protection, enabling sandwich attacks - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::add_tip` is a plain `ensure_signed` extrinsic callable by any account, and `Pallet::register_token` is callable by any origin whose location is not `Here`. Both call `swap_fee_asset_and_burn`, which for any fee/tip asset other than the configured `EthereumLocation` delegates to `swap_and_burn`, which invokes `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`.

## Finding Description
`add_tip` (lines 261-273) requires only `ensure_signed` and immediately calls `swap_fee_asset_and_burn` with the caller-supplied `asset`. `register_token` (lines 225-252) similarly calls `swap_fee_asset_and_burn` whenever `origin_location.is_here()` is false. `swap_fee_asset_and_burn` (lines 372-404) routes to `swap_and_burn` (lines 290-317) whenever the fee/tip asset differs from `T::EthereumLocation`. `swap_and_burn` calls `T::Swap::swap_exact_tokens_for_tokens(who, swap_path, tip_amount, None, who, true)` — explicitly passing `None` with the comment "No minimum amount required." The underlying `pallet-asset-conversion` implementation (`do_swap_exact_tokens_for_tokens`, `substrate/frame/asset-conversion/src/lib.rs` lines 980-1002) only enforces the `amount_out >= amount_out_min` check (`Error::ProvidedMinimumNotSufficientForSwap`) when `amount_out_min` is `Some`; passing `None` disables this guard entirely, so the swap executes at whatever spot price the pool has at execution time, with no floor. This matches the code exactly as cited, and no other check (fee, minimum liquidity, price bound) is present anywhere in the call path to compensate.

## Impact Explanation
Any attacker who can observe a pending `add_tip` or `register_token` call in the pool/mempool for a given `tip_asset`/ether pool can front-run it by trading in that pool to move the price unfavorably, let the victim's uncapped swap execute at the degraded price, then back-run to restore the price and capture the price-impact spread. Because there is no `amount_out_min` check, the victim's extrinsic never reverts — it simply produces less `ether_gained` than fair value, silently reducing the relayer tip or the ether value backing a token registration that gets burned/teleported. This is a genuine, reachable impact via a normal, unprivileged, signed extrinsic path (`add_tip`), and via `register_token` for any non-`Here` origin — not an admin-only, governance-only, or node-only path. It is a real value-extraction vector against ordinary users, matching an in-scope impact class (loss of funds/value for a legitimate user action).

## Likelihood Explanation
Exploitability requires: (1) a live `pallet-asset-conversion` pool between the tip/fee asset and ether-representing asset configured as `T::Swap`, (2) block-producer or searcher capability to order transactions within or across blocks (standard MEV/same-block sandwich technique), and (3) sufficient economic incentive relative to pool depth. These are realistic, not contrived, assumptions — sandwiching public AMM swaps lacking slippage protection is a well-established, repeatable attack pattern, and the affected code explicitly disables the protection mechanism that `pallet-asset-conversion` itself provides and documents (`amount_out_min`). The vulnerability is deterministic and repeatable, not merely theoretical, and requires no victim mistake, no privileged access, and no storage mutation tricks — only that the victim submits a normal `add_tip`/`register_token` call while a pool with the relevant pair exists.

## Recommendation
Add slippage protection to `swap_and_burn`: derive a bounded `amount_out_min` on-chain (e.g., via `quote_price_exact_tokens_for_tokens` with a configured tolerance) or expose a caller-supplied `min_ether_out` parameter on `add_tip`/`register_token`, mirroring `pallet-asset-conversion`'s own public swap extrinsics which require the signer to supply `amount_out_min`. Reject the swap (propagate `ProvidedMinimumNotSufficientForSwap`) if the executed price falls outside the accepted tolerance, rather than silently accepting any price.

## Proof of Concept
1. Configure a runtime with `pallet-asset-conversion` pool for `(tip_asset, ether_location)` and set it as `T::Swap` for `snowbridge-pallet-system-frontend`.
2. Victim submits `add_tip(message_id, Asset{ id: tip_asset, fun: Fungible(tip_amount) })`.
3. Attacker submits a front-run swap in the same pool (e.g., ether → tip_asset) to move the price, ordered immediately before the victim's transaction; the victim's `add_tip` executes `swap_exact_tokens_for_tokens(tip_amount, None, ...)` and receives a reduced `ether_gained`, then `burn_for_teleport` burns that reduced amount — the extrinsic does not revert since no minimum is enforced.
4. Attacker submits a back-run swap reversing step 3, restoring the pool price and capturing the price-impact spread.
5. A unit/integration test in the `system-frontend` pallet mock (using `mock_swap_executor.rs` or a real `pallet-asset-conversion` pool) can assert: (a) calling `add_tip` with a manipulated pool price yields materially less `ether_gained` than the pre-manipulation price would produce, and (b) the call still succeeds (`Ok(())`), confirming the absence of any slippage floor.
