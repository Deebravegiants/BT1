### Title
Webhook shop-domain identity spoofing — HMAC only covers the request body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the tenant identifier. Since the HMAC signature never covers that header, an attacker who can produce (or replay/relay) any request with a valid body/HMAC pair can freely choose which shop the webhook is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop` accessor, however, is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: ` [2](#0-1) `.

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (i.e. body-only) and compares it against `request.hmac`: ` [3](#0-2) `. Once that (body-only) check passes, the code immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and forwards it to the app's registered handler: ` [4](#0-3) `. `WebhookMetadata#shop` is a plain `T::Struct` field with no additional verification: ` [5](#0-4) `.

The identity binding that should hold is: **shop-attributed-by-HMAC == shop-delivered-to-handler**. Because the signature is computed over `raw_body` only, `HMAC_valid(body, secret) == true` says nothing about which shop the header claims. An attacker who obtains one legitimate `(body, hmac)` pair for a given topic (e.g., by sniffing/replaying a previously delivered webhook, or via any mechanism that lets them submit arbitrary headers with that same body to the app's public webhook endpoint) can substitute an arbitrary `shop-domain` header value and still pass `HmacValidator.validate`. The app-side handler — which is documented to use `data.shop` to look up the tenant/session for processing — will act on behalf of the attacker-chosen shop using data from a different shop's webhook body, i.e. a cross-tenant confusion at the API boundary this gem is responsible for authenticating.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `Registry.process`/`Utils::HmacValidator.validate` is the only authentication primitive offered before handing data to app code, and it does not bind the `shop` field it exposes. Downstream apps that trust `WebhookMetadata#shop` (the documented, natural use of this field) to select which merchant's data/session to update can be tricked into associating one shop's webhook payload with another shop, i.e. cross-tenant data corruption/leakage. This satisfies the "cross-tenant access" high/critical impact category.

### Likelihood Explanation
Exploitability requires the attacker to have at least one legitimate `(raw_body, hmac)` pair to replay against the endpoint with a forged header (e.g., a previously observed webhook delivery, or a topic/body combination that is attacker-influenced, such as an order or customer webhook body containing attacker data for a shop the attacker controls). Given webhook endpoints are public HTTP endpoints and headers are not signed, this is straightforward to exploit for any actor able to replay a captured webhook request, making likelihood moderate to high depending on how strongly the integrating app trusts `data.shop`.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) values into the signature verification, or otherwise cryptographically tie them to the verified body — e.g., include the shop-domain header in the signable string, or require the handler to independently verify `data.shop` against a known/looked-up shop before trusting it. At minimum, document prominently that `shop-domain` is not covered by HMAC verification, and that consuming applications must not use it as an unauthenticated tenant identifier without corroboration (e.g., cross-checking against the session/shop already on file for the webhook subscription).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) causing Shopify to send a legitimately-signed webhook body `B` with `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` (`B`) only — this matches `H`, so `Registry.process` proceeds: ` [6](#0-5) `.
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's order body, and — if it trusts `data.shop` to select which shop's records to update — writes/acts on `victim-shop`'s tenant using attacker-controlled data.
