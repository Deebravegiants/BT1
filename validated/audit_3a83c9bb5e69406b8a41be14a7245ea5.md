Found: `token_exchange.rb`'s `exchange_token` method uses `dest_shop = jwt_payload.shop` — taken directly from the JWT `dest` claim — **without ever passing it through `Utils::ShopValidator.sanitize!`**, unlike every other credential-issuing path in this gem (`client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token` in the same file all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value).

### Title
Token Exchange uses unsanitized JWT `dest` claim as request host, bypassing the trusted-domain check applied everywhere else - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop/host that receives the app's `client_id`/`client_secret` directly from the JWT `dest` claim (`jwt_payload.shop`), with no call to `Utils::ShopValidator.sanitize!`. Every other OAuth credential-issuing path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly validates the shop against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it. `exchange_token` is the odd one out.

### Finding Description
`JwtPayload#shop` (`lib/shopify_api/auth/jwt_payload.rb:47-50`) simply strips `"https://"` from the `dest` claim:
```ruby
def shop
  @dest.gsub("https://", "")
end
```
`JwtPayload#initialize` only checks the JWT signature (`aud == Context.api_key`, `exp`/`nbf` validity) — it never validates that `dest` is a `*.myshopify.com`/trusted Shopify domain (`lib/shopify_api/auth/jwt_payload.rb:23-45`).

`exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-59`) then does:
```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = { client_id: ..., client_secret: ShopifyAPI::Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```
`Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:16-19`) builds the request target as `"https://#{api_host || session.shop}"`, i.e. `dest_shop` becomes the literal network destination that the POST body containing `client_id`/`client_secret` is sent to — with no `ShopValidator` check in between.

Contrast with `migrate_to_expiring_token` (same file, lines 97-104), `refresh_access_token` (`lib/shopify_api/auth/refresh_token.rb:24-25`), and `client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25-26`), which all call `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the HTTP client's target host.

The binding that should hold is: **shop value that is signature-verified as belonging to the JWT == shop value that is validated as a trusted Shopify domain == host that receives the app's `client_secret`**. In `exchange_token`, the second equality is dropped — only the first is enforced (via the JWT HMAC signature), and the JWT signature only proves the `dest` string wasn't tampered with by a third party who lacks `api_secret_key`; it says nothing about `dest` being a legitimate Shopify-format host rather than an arbitrary string.

### Impact Explanation
If an `iss`/`aud`-valid but attacker-supplied session token (session tokens are provided by App Bridge inside the merchant's browser context, and the `dest` claim's format is not otherwise constrained by this gem) ever contains a `dest` value that is not strictly `{shop}.myshopify.com`, `exchange_token` will happily POST the app's `client_id` and `client_secret` to `https://#{dest_shop}/admin/oauth/access_token`. This is the SSRF-with-credentials scenario called out explicitly in scope ("SSRF with the app's credentials"): the destination host is attacker/embedding-context-influenced and not checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, whereas the parallel code path (`migrate_to_expiring_token`) enforces exactly that check for what is otherwise a structurally identical request.

### Likelihood Explanation
Medium — this requires a session token whose `dest` claim is not a well-formed myshopify domain but still passes JWT HMAC verification and the `aud == api_key` check. Whether Shopify's App Bridge/session-token issuer can ever produce such a `dest` for a given `aud` is outside this gem's control, but the gem provides no defense-in-depth here at all, unlike its sibling functions, breaking the intended "shop is always sanitized before being used as a request host with credentials" invariant that the rest of the codebase enforces.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session`/`Session.from`, mirroring `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`.

### Proof of Concept
1. Obtain/construct a session token whose payload has a valid HMAC for the app's `aud`/`api_key` but a `dest` claim value that is not a genuine Shopify domain (e.g., an attacker-controlled host reachable from the app server).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` is built with `session.shop` equal to the unsanitized `dest_shop`, and the POST request (including `client_id`/`client_secret` in the JSON body) is sent to `https://#{dest_shop}/admin/oauth/access_token` — no `ShopValidator.sanitize!` call occurs anywhere in `exchange_token`, unlike in `migrate_to_expiring_token` in the same file.         def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end

          client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")

        @iat = T.let(payload_hash["iat"], Integer)
        @jti = T.let(payload_hash["jti"], String)
