### Title
Webhook HMAC only signs the raw body, allowing shop/topic/webhook-id header spoofing for cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and are never included in the signed material. `Registry.process` validates the HMAC over the body only and then trusts these header-derived values to build the `WebhookMetadata` handed to the app's webhook handler, breaking the intended identity binding between "the body Shopify actually signed" and "the shop/topic the app believes it came from."

### Finding Description
`lib/shopify_api/webhooks/request.rb`:
- `hmac` is computed from the `X-Shopify-Hmac-Sha256` header.
- `to_signable_string` returns `@raw_body` only [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from request headers with no cryptographic binding to the body or the HMAC [2](#0-1) .

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only proves that the *body* bytes were signed with the app's shared `api_secret_key`. It then immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to dispatch to a handler as `WebhookMetadata` [3](#0-2) . `HmacValidator.validate_signature` compares `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, which is body-only [4](#0-3) .

Because Shopify signs webhooks for *every* shop with the same app-level `client_secret`, and the signature covers only the body (not the shop domain), any (body, hmac) pair valid for one merchant's webhook delivery is also a valid signature for the *same* body claimed to originate from any other shop — the app has no cryptographic way to tell these apart. This is the direct analog of the reported bug class: a field the code acts on (`shop`, used to attribute/scope the webhook event to a tenant) is not covered by the authentication mechanism (the HMAC), so the two "shop identities" — the shop asserted by the header and the shop implicitly authenticated by the signed bytes — are never actually bound to equal each other.

### Impact Explanation
An unprivileged internet user who has (or creates) their own store with the target app installed will legitimately receive real webhook deliveries with valid `X-Shopify-Hmac-Sha256` signatures for their own shop's payload bodies. They can then replay that exact body/HMAC pair directly to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to claim the event belongs to a different, victim shop. `Utils::HmacValidator.validate` will pass because it only checks the body, and `ShopifyAPI::Webhooks::Registry.process` will call the registered handler with `shop: request.shop` set to the attacker-chosen victim domain [5](#0-4) . Any app logic keyed off `WebhookMetadata#shop` (e.g., updating stored records, revoking access, processing GDPR/compliance topics such as `customers/redact` or `shop/redact`, or triggering per-tenant side effects) can be tricked into acting on the wrong tenant's data — a cross-tenant confusion/impersonation that meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is meaningfully high for a determined attacker: no access to `api_secret_key` or any merchant token is required. The attacker only needs to install the target app on their own (even free/dev) store to receive real signed webhook payloads, then replay the body+HMAC with modified headers to the app's public webhook endpoint. This requires zero interaction with any victim and no elevated privileges.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material that is verified, instead of trusting header values that sit outside the HMAC. Concretely:
- Change `Webhooks::Request#to_signable_string` to raise/fail unless the shop domain used by the handler is corroborated by data present in the signed body (Shopify includes the shop domain in most webhook payloads), or
- Require the host application to independently verify that `request.shop` corresponds to a shop with an active, known installation/session before dispatching to handlers, and document this requirement clearly since the gem currently implies HMAC validation alone is sufficient to trust `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app's registered endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid signature of raw_body>`, and some JSON `raw_body`.
3. Attacker captures `raw_body` and `X-Shopify-Hmac-Sha256`.
4. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the same `raw_body` and same `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [6](#0-5) ; `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the secret [7](#0-6) ; `Registry.process` calls the handler with `shop: "victim.myshopify.com"` [3](#0-2) , causing the app to act on the victim's tenant using attacker-controlled event data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
