### Title
`IntentGatewayV2`/`IntentsBase` declares a `_paused` storage flag that is never enforced, leaving no way to pause order escrow in an emergency - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase.sol` declares `bool internal _paused;` in storage, but there is no `pause()`/`unpause()` function, no `setPaused` setter, and no `whenNotPaused` modifier applied anywhere on `placeOrder`, `fillOrder`, or any other user-facing escrow entrypoint in `IntentGatewayV2`. The variable is dead state — this mirrors the reported bug class where a `VaultSetting.isPaused` field existed but had no admin path to actually flip it, leaving the pause mechanism completely non-functional.

### Finding Description
`IntentsBase` (the shared base for `IntentGatewayV2`, inherited via `IntrinsicIntents`/`ExtrinsicIntents`) declares: [1](#0-0) 

immediately followed by the `_relayer` field. The project's own design-decision note confirms this flag is unused: [2](#0-1) 

Grepping the whole `evm/src/apps/**` tree for `_paused`, `setPaused`, `whenNotPaused`, and `Pausable` turns up nothing except the bare declaration in `IntentsBase.sol` — no modifier gates `placeOrder`/`fillOrder`, and no function anywhere (owner, host, or governance) ever writes to `_paused`. Unlike `EvmHost`, which implements a real, authorized freeze path (`setFrozenState`, gated to `_hostParams.admin`/`_hostParams.handler`, checked via `restrict`/`FrozenHost` on `dispatch`): [3](#0-2) 

`IntentGatewayV2` has no equivalent circuit breaker. Its governance update path (`_updateParams`/`UpdateParams` request kind) also never touches `_paused` — it only updates `Params` (host, dispatcher, fee settings, price oracle, `solverSelection`): [4](#0-3) 

This is the identical structural bug to the source report: a boolean pause flag exists in the struct/storage layout suggesting operational-safety intent, but no code path (admin, owner, or cross-chain governance via Hyperbridge's `UpdateParams`/`Execute` request kinds) ever sets it, and nothing reads it to gate the sensitive functions. `placeOrder` and `fillOrder` remain fully callable with no way to halt them in an incident.

### Impact Explanation
Anyone can call `placeOrder` (escrowing user funds) or `fillOrder` (releasing escrowed inputs to a solver) at any time, and there is no mechanism — not even a privileged one — to pause the `IntentGatewayV2` contract. If a vulnerability is discovered in the escrow/fill/cancel logic, an oracle/pricing manipulation is found, or an upgrade needs to be staged safely, the protocol has no way to halt new order placement or fills while a fix or migration is prepared. This exposes escrowed user funds to continued exploitation during an incident window that a working pause switch would otherwise close — a Medium-severity operational-risk gap directly analogous to the reported `VaultSetting.isPaused` issue.

### Likelihood Explanation
This is a design/implementation gap rather than something an attacker actively triggers — it manifests whenever an emergency (bug, oracle failure, compromised relayer/session key, needed upgrade) occurs and the team wants to stop new escrow activity. Given `IntentGatewayV2` handles live escrow of user funds across chains and is upgradeable (per the `version`/`migrate` machinery seen in the tests), the absence of a working pause switch is a realistic and consequential gap, not a purely theoretical one.

### Recommendation
Wire `_paused` into an actual control path: add a `pause()`/`unpause()` (or extend the `UpdateParams`/`Execute` governance request) restricted to the immutable `_owner` and/or the host (mirroring the existing `setRelayer` authorization pattern already established in `IntentGatewayV2.sol`), and apply a `whenNotPaused` check to `placeOrder`, `fillOrder`, and any other fund-moving entrypoints. Emit a `Paused`/`Unpaused` event for observability, consistent with how `HyperFungibleToken.sol` already implements `pause()`/`unpause()` gated by `onlyOwner` with `whenNotPaused` on `send`/`onAccept`/`onPostRequestTimeout`.

### Proof of Concept
1. Deploy `IntentGatewayV2` and call `initialize` as in the existing test helpers (`_freshInitializedGateway` in `evm/tests/foundry/IntentGatewayV2Test.sol`).
2. Observe that `_paused` sits at storage slot 13 (confirmed by `testRelayerSharesSlotThirteenWithPaused`, which explicitly notes "leaving the `_paused` byte zero") — i.e., it is permanently `false` and untouched by any function.
3. Attempt to locate any function selector across `IntentGatewayV2.sol`, `IntentsBase.sol`, `IntrinsicIntents.sol`, and `ExtrinsicIntents.sol` that writes to `_paused` — none exists.
4. Call `placeOrder` after simulating a hypothetical incident (e.g., a compromised price oracle or a bug in fill logic): the call succeeds unconditionally since no `whenNotPaused` check exists, demonstrating that governance/owner has no way to halt escrow activity.
