Based on my analysis, I've confirmed the vulnerability. Here's the finding:

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate(request)` in `Registry.process` only proves that the *body* bytes were signed by Shopify with the app's secret [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are **not** part of the signed content [3](#0-2) . `Registry.process` then hands `request.shop` directly to the app's handler as the authoritative tenant identifier: `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [4](#0-3) .

### Finding Description
This is a direct analog of the reported bug class: a field (`shop`) is *acted on* by the library (passed to the handler as trusted tenant identity) but is *not covered by the HMAC* that the library computes for authenticity. The identity binding that should hold is:

`shop_verified_by_HMAC == shop_used_as_tenant_key`

But in reality:
- `shop_verified_by_HMAC` = ∅ (the signature only proves the body bytes, not the shop header)
- `shop_used_as_tenant_key` = `request.shop`, taken unauthenticated from the `X-Shopify-Shop-Domain` header

Because `shop` is outside the signed scope, any party capable of obtaining one valid `(raw_body, hmac)` pair — trivially achievable by installing the target app on their own (attacker-controlled) development store and receiving a legitimate webhook — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `@raw_body` [5](#0-4) . The forged `shop` value then flows unchecked into `WebhookMetadata`, which host applications use to route webhook data to the correct merchant record/session — see how session IDs elsewhere in the gem are built directly from `shop` (e.g. `"#{shop}_#{user_id}"`) [6](#0-5) , illustrating how central this string is as a tenant key throughout the library's design.

### Impact Explanation
An attacker who is merely a legitimate (even free-tier) merchant of the target app can forge webhook deliveries "from" any other shop domain of their choosing, since the shop attribution is not authenticated. Depending on how the host application consumes `WebhookMetadata#shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`/`customers/redact` compliance topics, or order/product mutation topics), this enables cross-tenant data corruption, forced "uninstall" processing for a victim shop, or injection of attacker-controlled payloads attributed to a victim tenant — a cross-tenant access impact.

### Likelihood Explanation
Moderate-to-high: no secret material is required. Any developer can install the target app on their own store to legitimately receive a validly-signed webhook, then replay the identical body/signature with a modified shop header to the same publicly reachable webhook endpoint. The gem provides no defense-in-depth check (e.g., binding `shop` into the signable string, or requiring the caller to independently confirm the `shop` header matches a known, previously-authenticated tenant) before exposing it as trusted metadata.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered content, or require `Registry.process` to independently verify that `request.shop` corresponds to a session/tenant already established via OAuth for the given `webhook_id`/topic before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be revalidated by the host application against known installed shops before use.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker.myshopify.com` and trigger a webhook (e.g. `app/uninstalled`) to capture a legitimate raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both signed for `attacker.myshopify.com`).
2. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes [7](#0-6) .
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` [4](#0-3) , and the host app's handler processes the attacker's body content as if it originated from `victim.myshopify.com`.
