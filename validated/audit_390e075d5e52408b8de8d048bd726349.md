### Title
`describeWithdrawal` trusts Omni indexer array order over intent signing order, causing cross-recipient status/hash misattribution in batch withdrawals - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal` selects `transfer = (await this.omniBridgeAPI.getTransfer({transactionHash}))[args.index]` and returns that transfer's hash/status without ever checking that `transfer.recipient` matches `args.withdrawalParams.destinationAddress`. For a batch NEAR tx with multiple OmniBridge legs, if the indexer's array order does not match the intents' signing order, the SDK reports one recipient's on-chain outcome under a different recipient's withdrawal identifier.

### Finding Description
The broken equality: `transfer[args.index].recipient == args.withdrawalParams.destinationAddress` is never asserted in `describeWithdrawal`: [1](#0-0) 

The `index` consumed here is produced by `createWithdrawalIdentifiers` in `withdrawal-watcher.ts`, which assigns it as a simple per-route counter over `withdrawalParams` in the order the caller supplied them — not derived from or verified against the Omni indexer's response order: [2](#0-1) 

`describeWithdrawal` then blindly indexes into whatever array `BridgeAPI.getTransfer` returns for that NEAR transaction hash, with no filter by recipient, amount, or any other field from `args.withdrawalParams`, and no ordering guarantee documented or enforced in this codebase. The existing test suite itself encodes this exact assumption — "returns correct transfer by index" mocks the indexer to return transfers in the same order as intents and merely checks the array-position lookup works, without ever validating `transfer.recipient` against `withdrawalParams.destinationAddress`: [3](#0-2) 

None of the other guards in the file protect against this: `validateWithdrawal` and `createWithdrawalIntents` run at withdrawal-creation time and validate the destination address against the asset/chain, not against the indexer's later reported order; `supports()` only gates route selection; there is no `matchesRequest`-style check comparing the fetched transfer to the original request in `describeWithdrawal`.

### Impact Explanation
If the Omni indexer's `getTransfer` array ordering diverges from intents signing order (e.g., sorted by completion time rather than creation/intent order), `watchWithdrawal` — which calls `describeWithdrawal` in a poll loop and returns `status.txHash` as-is — will report leg A's `WithdrawalIdentifier` as completed with leg B's transaction hash: [4](#0-3) 

An integrator relying on this SDK to confirm on-chain settlement per withdrawal leg would credit/refund the wrong recipient using another recipient's transaction hash — funds delivered/reported to the wrong destination with no automatic recovery. This matches "funds delivered to a wrong address ... with no recovery" / "status or hash misreport making an integrator credit or refund twice" severity.

### Likelihood Explanation
This requires: (1) a batch withdrawal with ≥2 OmniBridge legs to different destinations in the same NEAR tx (any ordinary user can construct this), and (2) the Omni indexer returning transfers in an order that differs from intent signing order for that tx hash. The SDK code has no control over, and makes no defensive check against, the indexer's ordering — the bug is a missing invariant check inside this repo's own code path, triggered purely by attacker-controlled batch composition plus indexer behavior that this repo does not constrain. It is repeatable on every batched withdrawal where the indexer's return order doesn't match input order.

### Recommendation
In `describeWithdrawal`, after fetching transfers, select the transfer whose `recipient` (and ideally `amount`/`token_id`) matches `args.withdrawalParams.destinationAddress` (normalized via `compareAddresses`) instead of relying on raw array position. If no unique match is found, fail safe (return `pending` or throw) rather than assuming positional correspondence.

```ts
it("BUG: misattributes recipient B's tx hash to recipient A's withdrawal when indexer order is reversed", async () => {
  const A = "eth:0xAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA";
  const B = "eth:0xBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB";

  vi.spyOn(BridgeAPI.prototype, "getTransfer").mockResolvedValue([
    createTransferMock({ recipient: B, finalised: { transaction_hash: "0xB-tx", chain: "Eth", timestamp_seconds: 1, details: { type: "evm", block_number: 1, transaction_index: null, log_index: null } } }),
    createTransferMock({ recipient: A, finalised: { transaction_hash: "0xA-tx", chain: "Eth", timestamp_seconds: 2, details: { type: "evm", block_number: 2, transaction_index: null, log_index: null } } }),
  ]);

  const bridge = new OmniBridge({ envConfig: configsByEnvironment.production, nearProvider: nearFailoverRpcProvider({ urls: PUBLIC_NEAR_RPC_URLS }) });

  const result = await bridge.describeWithdrawal({
    landingChain: Chains.Ethereum,
    index: 0, // intended for A per signing order
    withdrawalParams: {
      assetId: "nep141:eth.bridge.near",
      amount: 100000n,
      destinationAddress: A.split(":")[1]!,
      feeInclusive: false,
    },
    tx: { hash: "near-tx-hash", accountId: "test.near" },
  });

  // BROKEN EQUALITY: transfer[0].recipient (B) != withdrawalParams.destinationAddress (A)
  // yet describeWithdrawal reports B's hash for A's identifier.
  expect(result).toEqual({ status: "completed", txHash: "0xB-tx" }); // should have been "0xA-tx"
});
```
This demonstrates that `describeWithdrawal(index:0, destinationAddress:A)` returns B's `finalised.transaction_hash` whenever the indexer's array order is reversed relative to intent order, with no equality check catching the mismatch.

```typescript
export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
```
