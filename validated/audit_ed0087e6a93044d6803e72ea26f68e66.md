This confirms the finding: the docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" (line 125 of `docs/usage/webhooks.md`), and hand the resulting `data.shop` to the handler as a trusted tenant identifier (line 14, 26 of the same doc) — but the actual verification only covers the raw body bytes, not the `shop`, `topic`, `webhook_id`, or `api_version` headers.

### Title
Webhook HMAC Verification Does Not Bind the `shop` (or Topic/Webhook-Id) Header, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, but the shop-identifying header (`x-shopify-shop-domain`, exposed as `request.shop`) — along with `topic`, `webhook_id`, and `api_version` — is never included in the signed content. Any party who can obtain one validly-signed webhook body/HMAC pair for the shared app secret (e.g., by legitimately installing the app on their own store and triggering a webhook) can replay that same body+HMAC pair while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header. `Registry.process` will still consider the HMAC valid and pass the forged `shop` value straight to the app's webhook handler as trusted tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers and are not part of the signable content: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it with the provided `hmac` value: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC validity over the body — then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, and dispatches it to the handler as trusted tenant/topic identity: [4](#0-3) 

The gem's own documentation instructs the app developer to trust this flow completely: `Registry.process` "will verify the request did indeed come from Shopify" and hand back `data.shop` as the shop domain of the webhook, with no mention that the caller must independently verify `shop` against the signed payload: [5](#0-4) 

The identity binding that is broken can be stated as an equality that the gem fails to enforce:
`shop authenticated by HMAC` ≠ `shop delivered to the handler as WebhookMetadata#shop`

Because Shopify webhook HMACs are computed with the app's single shared `api_secret_key` (the same secret is valid for every shop that installs the app), any unprivileged internet user who installs the target app on their own store can trigger a webhook for themselves, capture a legitimate `(raw_body, hmac)` pair, and then send that identical pair to the app's public webhook endpoint while swapping in a victim shop's domain (and/or topic/webhook_id) in the headers. The HMAC check in `HmacValidator.validate` still succeeds because it only checked the body bytes, and the forged `shop` is delivered to the app's handler as if Shopify itself asserted it belongs to that shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker who controls one legitimate (even free/low-privilege) shop installation can make the app's webhook handler act as if the event originated from any other shop of the attacker's choosing, since the app has no gem-level way to detect the mismatch. Any host application that follows the documented usage pattern (using `data.shop` to select which merchant's records to update, e.g., enqueuing background jobs keyed on `shop_domain`, per the doc's own example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is exposed to cross-tenant data injection/corruption using attacker-controlled webhook bodies attributed to a victim shop.

### Likelihood Explanation
Likelihood is Low-to-Medium in practice: it requires the attacker to be (or become) a legitimate, even if unprivileged, install of the target app in order to obtain one genuine `(body, hmac)` pair signed with the app's shared secret, plus the ability to POST directly to the app's public webhook endpoint with custom headers (trivial, since it's a plain HTTP endpoint). No merchant/API credentials or elevated privileges are needed beyond a normal app install.

### Recommendation
Bind the identity-critical fields into the verified content, or otherwise cryptographically tie the `shop` (and `topic`/`webhook_id`) to the HMAC-covered body:
- Have `HmacValidator`/`Request#to_signable_string` include the `shop`, `topic`, and `webhook_id` headers in the signed material actually verified against the HMAC (mirroring how Shopify computes/validates these headers together), or
- Have `Registry.process` cross-check that the shop domain embedded/claimed in the payload (if present) matches the `x-shopify-shop-domain` header before dispatching to the handler, and document that host apps must not use the unauthenticated `shop` header as a sole tenant key without additional verification (e.g., checking it against a known/installed-shop list keyed by an already-verified session).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged app install).
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop, capturing the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify sent — this HMAC is valid because it's signed with the app's single shared `api_secret_key`.
3. Attacker POSTs to the app's public webhook endpoint (`ShopifyAPI::Webhooks::Registry.process`) reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` (checking only `raw_body` vs. `hmac`) returns `true`.
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and calls the app's handler, which — per the documented pattern — processes/stores the attacker's payload as belonging to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.
