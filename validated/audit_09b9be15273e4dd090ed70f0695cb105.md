### Title
Webhook HMAC covers only the raw body, not the shop/topic headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given `shop` and `topic` once `Utils::HmacValidator.validate` succeeds. However, the HMAC signature only covers the raw request body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to route and attribute the webhook are never part of the signed material. Any attacker who can obtain one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store, which uses the same app-wide `client_secret`) can replay that exact body/HMAC to the app's webhook endpoint while freely rewriting the `shop-domain` (and `topic`) headers to point at a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and declares the signable content as only the raw body: [1](#0-0) 

Note `hmac` is read from the `hmac-sha256` header, and `to_signable_string` returns `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are also read straight from attacker-controlled HTTP headers: [2](#0-1) 

`Registry.process` validates only this HMAC-over-body and then dispatches the handler using the unauthenticated `shop`/`topic` header values: [3](#0-2) 

The gem's own documentation tells developers that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop`, implying the shop attribution can be trusted: [4](#0-3) 

Because the `client_secret`/`api_secret_key` used to compute the HMAC is shared across every shop that has installed the app, an unprivileged user can:
1. Install the target app on their own (attacker-controlled) store.
2. Trigger a webhook (e.g. `app/uninstalled`, `orders/create`, or a mandatory GDPR topic like `customers/data_request` / `shop/redact`) and capture the genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends — this HMAC is valid because it's computed by Shopify with the real, shared `api_secret_key`.
3. Replay that exact body and HMAC value to the app's public webhook endpoint, but substitute `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) with a victim shop's domain.

`HmacValidator.validate` only recomputes and compares the HMAC over `raw_body`, so it succeeds unchanged, and `Registry.process` calls the handler with `WebhookMetadata` whose `shop` is the attacker-chosen victim domain, even though the payload content actually originated from the attacker's own store.

This breaks the identity binding: `shop that produced/authorized this HMAC == shop the library attributes the event to`. The two sides diverge after the attacker's header substitution, since the header is never covered by the signature.

### Impact Explanation
This enables cross-tenant confusion/injection at the highest severity the library can affect: an attacker fully controls the JSON body of a webhook while forcing the host application to process it as belonging to an arbitrary target shop. Depending on the handler's logic this can cause the app to write attacker-supplied data into a victim tenant's records, trigger data-erasure/redaction flows against a victim's data (mandatory `shop/redact`/`customers/redact` topics), or cause the app to treat a victim shop as uninstalled/reinstalled — all without needing the victim's access token, session, or any credentials, only the shared app secret's HMAC output which Shopify freely provides for the attacker's own store.

### Likelihood Explanation
Any user can install a publicly listed app (or a development/test store install for apps with public distribution) to obtain a legitimately-signed `(body, hmac)` pair for the shared `api_secret_key`, then directly POST to the app's known webhook callback URL with a forged `shop-domain` header. No privileged access, leaked secrets, or social engineering is required — only the ability to become a normal merchant/tenant of the app once, which is the baseline "unprivileged internet user" capability this class of libraries must defend against.

### Recommendation
Bind the shop, topic, and webhook id to the HMAC verification, e.g. by including these header values in the signable string, or by requiring callers to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting the payload. At minimum, the library should document/enforce that `HmacValidator.validate` on a `Webhooks::Request` does not authenticate `shop`, `topic`, or `webhook_id`, contradicting the current doc wording that implies the whole request is verified as coming from Shopify for that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook subscription event (e.g. `orders/create`) with attacker-controlled order content; Shopify POSTs to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and the JSON body.
3. Attacker captures this raw body and the valid HMAC.
4. Attacker sends a new POST request to the same webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds.
6. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, i.e., the app processes attacker-controlled data as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
