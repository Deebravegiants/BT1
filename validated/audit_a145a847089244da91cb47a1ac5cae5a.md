### Title
Webhook HMAC signature does not bind the `shop` (or `topic`/`webhook-id`) header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that raw body. None of the identity-carrying headers — `shop-domain`, `topic`, or `webhook-id` — are covered by the signature. `ShopifyAPI::Webhooks::Registry.process` then trusts `request.shop` (taken straight from the unsigned header) to dispatch data to the app's per-shop handler logic, breaking the binding: `HMAC-verified bytes == raw_body` while `shop used by handler == header value (unverified)`.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  only returns `@raw_body`. `HmacValidator.validate` at [2](#0-1)  computes the signature over `verifiable_query.to_signable_string` and secure-compares it to the received HMAC — so the check only proves the body bytes were signed by Shopify using the app's `client_secret`; it proves nothing about which shop, topic, or webhook the body is attached to.

`Registry.process` then unconditionally trusts the header-derived shop for dispatch: [3](#0-2) 

Because the same `client_secret` (api_secret_key) is used to sign every webhook delivered to every shop that has the app installed, any attacker who controls a shop with the app installed can trigger a webhook whose body they can predict or influence (e.g. `orders/create`, `products/update`, custom metafield content, etc.), capture the resulting `(raw_body, HMAC)` pair that Shopify legitimately signs for their own shop, and then replay that exact `(raw_body, HMAC)` pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body/HMAC pair is untouched, and `Registry.process` hands the attacker-controlled body to the handler tagged with the victim's shop identity.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged user of the app on their own shop can make the host application process attacker-chosen webhook content as if it originated from an arbitrary other shop that also has the app installed, without ever needing that shop's credentials. Depending on how the host application's webhook handlers key data by `shop`, this enables cross-tenant data injection/corruption (e.g., poisoning another merchant's locally stored order/product/customer records, forcing spurious `app/uninstalled` cleanup, or triggering shop-scoped side effects) — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own working installation of the target app (a normal, unprivileged merchant capability), (2) the ability to trigger a webhook whose topic/body content is attacker-influenced, and (3) direct network access to the app's public, unauthenticated webhook endpoint (which by design accepts POSTs from the internet, gated only by HMAC). No secrets, tokens, or elevated access are required, only header manipulation on a replayed request, so likelihood is meaningful for any app that keys behavior by the `shop` value taken from `Webhooks::Request#shop`/`WebhookMetadata#shop`.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., verify the caller's shop against an out-of-band expected value, or require a per-shop stored webhook secret / shop allow-list) so that the HMAC check enforces `verified_bytes == (raw_body + shop + topic + webhook_id)` rather than `verified_bytes == raw_body` alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic whose body content they can influence (e.g., updates a product's metafield to attacker-chosen JSON, causing `products/update`).
2. Attacker captures the legitimately delivered request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — this HMAC is valid per `HmacValidator.validate` since it only checks against `B` ( [1](#0-0) , [4](#0-3) ).
3. Attacker sends a new POST directly to the app's public webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes, then invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `request.shop == "victim-shop.myshopify.com"` — the host app now processes attacker-controlled data under the victim shop's identity ( [3](#0-2) ).
