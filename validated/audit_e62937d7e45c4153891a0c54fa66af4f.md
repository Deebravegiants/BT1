### Title
Attacker-inflated HyperSwap V2 pre-seed can round the graduation LP mint to zero, permanently bricking `finalizeGraduation` - ([File: packages/contracts/src/Bonding.sol])

### Summary
The original report showed that burning LP supply on a custom AMM without withdrawing the underlying reserves lets an attacker drive `totalSupply` down to a value so small that the `P·(…)/T` liquidity-unit formula rounds new depositors' minted units to zero, freezing the pool. alt.fun's analog is the HyperSwap V2 TOKEN/LT pair that `Bonding.finalizeGraduation` seeds via `_seedUniswapV2Direct`/`_seedRebalancing`/`_routerDepositAndDispose`. Because that pair is a standard, permissionless UniswapV2 fork, an attacker can independently manipulate its `totalSupply` (via `mint`+`burn`) and its stored reserves (via direct-transfer `donation` + `sync()`) *before* graduation, producing a state where `totalSupply` is minimal relative to reserves. `Bonding`'s regime dispatch only checks `totalSupply() == 0` (routes to direct-mint) vs. `!= 0` (routes to rebalance+`router.addLiquidity`); it never checks that `totalSupply` is proportionate to reserves. When `finalizeGraduation` ultimately calls the HyperSwap router's `addLiquidity`, the router's mint call computes `liquidity = min(amountToken * totalSupply / reserveToken, amountLT * totalSupply / reserveLT)`, which rounds to `0` when `totalSupply` is tiny relative to the deposited/reserve amounts, and the standard V2 pair reverts with `INSUFFICIENT_LIQUIDITY_MINTED`. Since `finalizeGraduation` calls this synchronously with no fallback for a persistently-corrupted `totalSupply`, the revert is unconditional and repeatable, permanently freezing the graduation.

### Finding Description
`Bonding._prepareGraduationLiquidity` computes `tokensForLP`/`ltFromPair` and drains the curve's real LT via `Router.graduate` [1](#0-0) . Phase 2, `finalizeGraduation`/`_seedUniswapV2Direct`, then seeds the HyperSwap V2 pair, dispatching purely on `IUniswapV2Pair(pair).totalSupply() == 0` [2](#0-1) . If `totalSupply() != 0`, it proceeds to `_seedRebalancing`, whose only pre-seed-size guard (`DIRECT_MINT_PRESEED_BPS`) compares raw reserve sizes to the target `tokensForLP`/`ltFromPair`, never the ratio of `totalSupply` to reserves [3](#0-2) . After rebalancing, `_routerDepositAndDispose` calls the canonical HyperSwap `addLiquidity` with `min0=1, min1=1` and sends whatever `remToken`/`remLT` remain [4](#0-3) .

A standard UniswapV2 pair permits any unprivileged address to: (1) `transfer` TOKEN/LT to the pair and call `mint` to obtain some LP, establishing a nonzero `totalSupply`; (2) `transfer` that LP back to the pair and call `burn` to redeem almost all of it, driving `totalSupply` down to a minimal value (e.g. `1`) while proportionally shrinking reserves; (3) directly `transfer` (donate) TOKEN and LT into the pair without minting, then call `sync()` to update the pair's stored reserves to the inflated, donation-skewed values. This sequence produces a pair whose `totalSupply()` is minimal but whose stored `getReserves()` are large — exactly the `P` (total supply) vs. reserve mismatch from the original bug class, just achieved through legitimate, permissionless V2 primitives instead of a custom `burn()`.

Because `Bonding`'s regime check only looks at `totalSupply() == 0` (which is now false) and the size-guard only compares reserves to target amounts (not to `totalSupply`), the seeding proceeds to `_routerDepositAndDispose`'s `addLiquidity` call. The V2 router/pair's mint math, `liquidity = min(amountToken·totalSupply/reserveToken, amountLT·totalSupply/reserveLT)`, will round to `0` whenever `totalSupply` is small enough relative to the (attacker-inflated) reserves and the deposited amounts, and the pair's `require(liquidity > 0)` reverts the whole `addLiquidity` call — and therefore the whole `finalizeGraduation` transaction — unconditionally and repeatably, since the corrupted `totalSupply`/reserve state persists on-chain.

### Impact Explanation
`finalizeGraduation` is the only path that drains `pendingGraduation[token]`'s parked curve-raised LT and 250M reserved tokens out of `Bonding` and into the LP/`LPLock` [5](#0-4) . If it can be made to revert unconditionally, the token is permanently stuck in `Lifecycle.Graduating` — trading remains frozen (graduation freezes trading per the two-phase design) and all curve-raised LT plus the 250M `LP_RESERVE` tokens are permanently locked in `Bonding` with no rescue path. This is a permanent freezing of creator/trader/protocol funds, meeting the High severity bar.

### Likelihood Explanation
The attack requires only unprivileged calls to the permissionless HyperSwap V2 pair (`mint`, `burn`, plain ERC20 `transfer`, `sync`) executed before `finalizeGraduation`'s phase 2 runs — precisely the "pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" surface already called out as in-scope. The attacker needs to acquire some TOKEN (buyable on the curve) and some LT (mintable via the LT/Zap flow) to fund the initial mint, both of which are cheap, ordinary user actions. No admin role, upgrade, or off-chain component is needed, and the window between phase 1 (`_enterGraduating`, which fires inline) and phase 2 (`finalizeGraduation`, permissionless and possibly delayed) gives ample time to execute the setup.

### Recommendation
Do not gate the seeding regime solely on `totalSupply() == 0`; additionally validate that `totalSupply()` is consistent with the pair's reserves (e.g., require a minimum `totalSupply` relative to `reserveToken`/`reserveLT`, or recompute an expected `totalSupply` from `sqrt(reserve0*reserve1)` and compare). When the pre-seed state is judged to be a degenerate/manipulated `totalSupply`, fall back to the `_seedDirectMint`/`skim`-based empty-pair path (which mints from the desired amounts alone and is immune to this griefing) instead of routing into `router.addLiquidity`, whose `INSUFFICIENT_LIQUIDITY_MINTED` revert is unconditional and unrecoverable for a persistently corrupted pair.

### Proof of Concept
1. Attacker buys some `TOKEN` on the curve and mints/holds some `LT`.
2. Before `finalizeGraduation` phase 2 runs for that token, attacker creates the HyperSwap V2 `TOKEN/LT` pair (or reuses the existing empty one), transfers a small amount of `TOKEN` and `LT` to it, and calls `pair.mint(attacker)` to obtain LP tokens, establishing `totalSupply = L`.
3. Attacker transfers almost all of that LP back to the pair and calls `pair.burn(attacker)`, redeeming almost all reserves and shrinking `totalSupply` to a minimal residual value (e.g. `1`).
4. Attacker directly `transfer`s a much larger amount of `TOKEN` and `LT` into the pair (donation, no mint), then calls `pair.sync()`, so `getReserves()` now reports the large donated amounts while `totalSupply()` stays minimal.
5. Graduation's phase 1 (`_enterGraduating`) fires normally on a threshold-crossing buy, caching `tokensForLP`/`ltFromPair`.
6. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedUniswapV2Direct` sees `totalSupply() != 0`, proceeds via `_seedRebalancing` → `_routerDepositAndDispose` → HyperSwap `addLiquidity(tokenAddress, lt, remToken, remLT, 1, 1, lpLock, ...)`.
7. The V2 router computes the optimal deposit against the inflated stored reserves and calls `pair.mint(lpLock)`, which computes `liquidity = min(remToken*totalSupply/reserveToken, remLT*totalSupply/reserveLT)`. With `totalSupply` minimal, `liquidity` rounds to `0`, and the pair's `require(liquidity > 0)` reverts.
8. Every subsequent call to `finalizeGraduation(token)` hits the same revert since the attacker-corrupted `totalSupply`/reserve state is permanent (no third party can restore proportionality), permanently freezing the token in `Lifecycle.Graduating` along with its parked LT/tokens.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

- **Two-phase split.** Graduation is split across two transactions to fit HyperEVM's small-block (~2M gas) ceiling.
  - **Phase 1: `_enterGraduating`**, fired inline by the threshold-crossing buy (~150-200k of additional gas on top of the buy). Drains the curve, computes the LP-bound amounts, caches them in `pendingGraduation[token]`, flips `lifecycle: Curve → Graduating`, freezes trading. Emits `TokenGraduating`.
  - **Phase 2: `finalizeGraduation`**, **permissionless** big-block tx (~2.5M gas). Creates the HyperSwap pair if needed, seeds liquidity across the empty, donation, and hostile mint-pre-seed regimes, locks LP, flips `lifecycle: Graduating → Graduated`. Emits `TokenGraduated`. A Cloudflare Worker keeper handles the happy path; anyone can call to rescue a stuck token.
- **Brick resistance.** Phase 2 must never revert under any pre-seed shape. Empty/donation pairs use direct pair calls; hostile mint pre-seeds use direct `pair.swap` for rebalance plus router `addLiquidity` for the canonical quote-based deposit. Tested by `test_brick_resistance_frontRun_dust_seed` in [`test/TwoPhaseGraduation.t.sol`](test/TwoPhaseGraduation.t.sol).
