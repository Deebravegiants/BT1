### Title
Excess native token sent to `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and becomes permanently stuck in the contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept an arbitrary `msg.value` and forward the entire amount to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`, but none of them capture or refund the unspent native token left over after the swap. This mirrors the FootiumAcademy analog: a caller who overpays the required fee never gets the excess back.

### Finding Description
In `EvmHost.sol`, the three fee-paying entry points swap the caller's full `msg.value` for an exact amount of fee token, with any dust ETH refunded by the Uniswap V2 router — but the refund goes to `msg.sender` as seen by the router, which is `EvmHost` itself, not the original transaction sender: [1](#0-0) [2](#0-1) [3](#0-2) 

Uniswap V2's `swapETHForExactTokens` computes the exact input amount required (`amounts[0]`) and refunds `msg.value - amounts[0]` to whoever called the router — here that's `EvmHost`, since `EvmHost` is the direct caller (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`). The dust ETH lands in `EvmHost`'s own balance, and none of these three functions track or return it to `_msgSender()`.

This is directly analogous to the reported issue: other parts of this same codebase correctly implement this refund pattern, proving the maintainers are aware overpayment must be returned but omitted it here. For example, `IntentGatewayV2.sol` and `ExtrinsicIntents.sol` explicitly compute `msgValue -= amounts[0]` after the swap and call `_sendValue(msg.sender, msgValue)`: [4](#0-3) [5](#0-4) 

`EvmHost`'s `dispatch`/`fundRequest` functions have no equivalent refund step, so any native token sent above the exact swap-in amount is permanently absorbed by the host contract with no accounting for who paid it and no user-facing withdrawal path.

The documentation itself confirms users are expected to send an estimate (subject to slippage) and warns fee estimation is imprecise, meaning real-world callers routinely send more than the exact amount needed: [6](#0-5) 

### Impact Explanation
Every unprivileged caller who dispatches a POST/GET request or funds an existing request using native token payment (the default, documented flow for user-facing apps) will lose any ETH sent beyond the exact swap-in cost, since `quote()` is explicitly documented as an approximate, slippage-sensitive, off-chain-only estimate. This is a direct, permanent loss of user funds with no recovery mechanism, and it affects the core dispatch path used by every application built on Hyperbridge (any `HyperApp`, `HyperFungibleToken`, `IntentGatewayV2`'s cross-chain leg via `dispatchWithFeeToken`/`dispatch`, etc., whenever they let the end user pay natively). This qualifies as concrete permanent freezing/loss of funds in the message dispatch path.

### Likelihood Explanation
High likelihood: native-token payment is a first-class, documented feature (`Native Token Payment` sections in the docs), `quote()` is explicitly imprecise due to Uniswap slippage, and any reasonable safety margin added by a caller/frontend to cover slippage results in a nonzero, unrefunded excess on every single call. No adversarial conditions are needed — this triggers on ordinary, honest use.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the actual amount spent (`amounts[0]` returned by the swap) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2._placeOrder` and `ExtrinsicIntents._fillCrossChain`/`_post`:

```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = msg.value - amounts[0];
if (refund > 0) {
    (bool sent, ) = _msgSender().call{value: refund}("");
    require(sent, "ETH refund failed");
}
```

### Proof of Concept
1. A user calls `IDispatcher(host).dispatch{value: X}(post)` where `post.fee = F` (in fee token) and `X` (native) is greater than the exact ETH needed to swap for `F` fee tokens via the configured Uniswap V2 router (e.g., the user pads the value to account for slippage, as the docs instruct).
2. Inside `dispatch`, `swapETHForExactTokens{value: X}(F, path, address(this), ...)` executes; Uniswap computes `amounts[0] < X` as the exact input needed, performs the swap, and refunds `X - amounts[0]` — to `EvmHost`, since it is the caller of the router.
3. `EvmHost.dispatch` never reads the swap's returned `amounts` and never forwards any refund to `_msgSender()`; the leftover `X - amounts[0]` wei remains in `EvmHost`'s balance permanently, with no per-user accounting and no user-callable withdrawal function for it.
4. Repeating this on every dispatch/fundRequest call accumulates value in `EvmHost` that the original payer can never reclaim, constituting a systemic loss of user funds. [1](#0-0)

```text
### Payment Method Comparison

| Feature | Native Token | FeeToken (Recommended) |
|---------|-------------|------------------------|
| **Gas Cost** | Higher (includes swap) | Lower (no swap) |
| **Slippage** | Yes (Uniswap swap) | No |
| **Fee Calculation** | Approximate (subject to slippage) | Exact |
| **Token Approval** | Not required | Required  |
| **User Convenience** | High (users have native tokens) | Low (users need feeToken) |
| **Best For** | One-off transactions, user-facing apps | Frequent dispatches, cost optimization |
```
