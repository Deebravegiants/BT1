### Title
Large RAY-denominated market values permanently freeze all market operations - (File: common/src/rates/simulate.rs)

### Summary

Interest accrual converts `borrowed` and `supplied` scaled shares back into RAY-denominated value before calculating utilization, but the multiplication panics when the result exceeds `i128::MAX`. The borrow-index cap does not prevent this because the cap applies to the index, while the overflow occurs when multiplying the already-large share total by that index. Once the state reaches that range, every subsequent market operation runs the same accrual and reverts with `MathOverflow`, permanently freezing the market absent an upgrade.

### Finding Description

`accrue_step` computes `borrowed_original` and `supplied_original` through `scaled_to_original` before calculating utilization and the next interest factor. [1](#0-0)  `scaled_to_original` calls `Ray::mul`, which delegates to `mul_div_half_up`. [2](#0-1) [3](#0-2)  The widened `I256` multiplication is converted back to `i128`, and `mul_div_half_up` panics with `MathOverflow` if that result cannot fit. [4](#0-3) [5](#0-4) 

`update_borrow_index` caps only `borrow_index` at `MAX_BORROW_INDEX_RAY`; it does not cap or safely represent `borrowed * borrow_index`. [6](#0-5)  The pool accrues the market before every mutation via `synced_market`. [7](#0-6)  Consequently, the same overflow blocks repayment, withdrawal, borrowing, liquidation, revenue claims, recapitalization, and even owner-side `update_params`, which also accrues before changing the curve. [8](#0-7) [9](#0-8) [10](#0-9) 

The repository contains an executable regression case demonstrating the cliff: a one-billion-token, 18-decimal market at 98% utilization eventually makes `update_indexes` return `MathOverflow`, after which both withdrawal and repayment fail with the same error. [11](#0-10) [12](#0-11) 

### Impact Explanation

This is a permanent freezing-of-funds and market-availability failure. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate the affected debt, and keepers cannot resynchronize or safely repair the market through the exposed endpoints. `controller::update_indexes(caller, assets)` is permissionless and forwards the asset list to the pool, so any address can trigger the failing accrual once sufficient time has elapsed. [13](#0-12) [14](#0-13) 

### Likelihood Explanation

The attack requires an unusually large listed asset position and sustained high utilization, so it is conditional rather than trivially repeatable. Nevertheless, the trigger uses only ordinary user-reachable actions: supply a very large amount, collateralize a separate account, borrow most of the liquidity, and let interest accrue. The proof test reaches the cliff with a `1e27`-unit 18-decimal position and a 98% borrow, then demonstrates that both exit and repayment remain impossible after the first overflow. [12](#0-11) 

### Recommendation

Prevent a market from entering a state where `supplied * supply_index` or `borrowed * borrow_index` cannot be represented. Enforce a combined shares-times-index ceiling before minting supply, debt, or revenue shares, and derive that ceiling from `i128::MAX` rather than relying only on token-unit caps. Accrual should also use a non-panicking wide-integer or saturation path for aggregate utilization so risk-reducing repayment, withdrawal, liquidation, and bad-debt cleanup remain possible. Alternatively, provide a no-accrual recovery path that can reduce positions using the stored indexes.

### Proof of Concept

```rust
// BIG18 has 18 decimals and a steep high-utilization borrow curve.
let principal = 1_000_000_000i128 * 10i128.pow(18);
let debt = principal * 98 / 100;

// Attacker-controlled market liquidity.
controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(big18.clone(), principal)],
);

// A second attacker-controlled account posts sufficient collateral and
// borrows approximately 98% of BIG18.
controller.supply(attacker, 0, spoke_id, vec![(collateral, enough_collateral)]);
controller.borrow(
    attacker,
    borrower_account_id,
    vec![(big18.clone(), debt)],
    None,
);

// After enough ledger time, anyone may invoke accrual.
controller.update_indexes(attacker, vec![big18.clone()]);
// Eventually panics with GenericError::MathOverflow inside accrue_step ->
// scaled_to_original(borrowed, borrow_index).

// Every later touch of the market syncs first and therefore fails:
controller.withdraw(supplier, supplier_id, vec![(big18.clone(), 1)], None);
controller.repay(attacker, borrower_id, vec![(big18.clone(), 1)]);
controller.update_indexes(attacker, vec![big18]);
```

The integrated test performs this sequence and asserts that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [15](#0-14)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
