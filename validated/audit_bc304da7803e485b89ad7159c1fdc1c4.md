### Title
Unchecked ERC20 return value in `withdraw()` and `SweepDust` handling permanently locks escrowed intent funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed order funds and swept dust using a raw low-level `.call()` to the ERC20 `transfer()` selector, checking only that the external call did not revert (`success`) and never decoding/verifying the boolean return value the ERC20 standard requires callers to check. This is the exact bug class described in the referenced report ("Use `safeTransfer()`/`safeTransferFrom()` instead of `transfer()`/`transferFrom()`"), except here it manifests on the fund-release path of the Intent Gateway rather than a simple swap contract, and combines with unconditional escrow-accounting mutation to produce permanent loss of escrowed funds rather than a mere revert-avoidance issue.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept()` when a relayer delivers a `RedeemEscrow` or `RefundEscrow` cross-chain message, and also from `onGetResponse()` for source-chain cancellations: [1](#0-0) 

For every escrowed token, it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
`success` here only reflects whether the low-level call reverted — it does **not** decode the ABI-encoded `bool` return value that a spec-compliant `transfer()` is required to return on failure. A token that returns `false` without reverting (a legitimate, EIP-20-compliant failure signal, e.g. paused, blacklisted-recipient, or a token designed to silently fail under certain conditions) will make `success == true` even though **no tokens moved**. The function then unconditionally decrements `_orders[body.commitment][token]` and, at the top of `withdraw()`, unconditionally sets `_filled[body.commitment] = beneficiary`, finalizing the order.

The same unchecked-call pattern recurs in the `SweepDust` handler: [2](#0-1) 

and again for protocol fee redemption within `withdraw()`: [3](#0-2) 

By contrast, the canonical (non-Tron) `IntentGatewayV2`/`IntentsBase` implementation uses `SafeERC20.safeTransfer`/`safeTransferFrom` throughout its equivalent escrow release logic, confirming this is a Tron-specific regression rather than intended design: [4](#0-3) 

### Impact Explanation
Because the order is marked filled (`_filled[body.commitment] = beneficiary`) and the escrow ledger is decremented regardless of whether the token transfer actually succeeded, a silent-failure token causes the beneficiary (solver or user) to receive nothing while the contract's internal accounting shows the funds as already disbursed. The tokens remain stranded in the contract with no code path to reclaim them for that commitment, since `_filled`/`_orders` bookkeeping treats the withdrawal as complete. This is a permanent freezing/loss of escrowed user or solver funds reachable via the normal cross-chain settlement flow (a relayed `RedeemEscrow`/`RefundEscrow` message or a GET-response cancellation), which is a core Intent Gateway user journey, not an edge case requiring a privileged actor.

### Likelihood Explanation
Any user placing an order chooses the input token; a token that returns `false` rather than reverting on a failed transfer (a valid, standards-compliant ERC20 behavior) is sufficient to trigger the bug on the very first attempted release of that token from escrow — no attacker privilege is required beyond normal use of the Intent Gateway with a particular token, or a token later entering a state (e.g., paused/blacklist) where its `transfer()` degrades to returning `false`.

### Recommendation
Replace every `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s token loop, the fee redemption, and the `SweepDust` handler) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-revert and false-return failures propagate correctly and prevents escrow accounting/order finalization from advancing on a failed transfer.

### Proof of Concept
1. User places an order (`placeOrder`) escrowing `TOKEN`, a standards-compliant ERC20 that returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or the contract is paused, per its own business logic.
2. Solver fills the order on the destination chain; a `RedeemEscrow` POST request is dispatched back to this Tron `IntentGatewayV2`.
3. A relayer delivers the message; `onAccept()` → `withdraw()` executes `token.call(...transfer(beneficiary, amount)...)`. `TOKEN` returns `false` (transfer silently fails) but the outer call does not revert, so `success == true`.
4. `withdraw()` decrements `_orders[commitment][token]` and sets `_filled[commitment] = beneficiary`, finalizing the order despite the beneficiary balance being unchanged.
5. The escrowed `TOKEN` amount is now unrecoverable: the order is marked filled and cannot be re-withdrawn or refunded, permanently locking the funds inside the contract.
