### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — the raw body only. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from HTTP headers that are never included in the signed material, yet `process` immediately trusts `request.shop` to build `WebhookMetadata` handed to the app's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC and then trusts `request.shop` as the tenant key for the handler callback: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm this — it only ever hashes `verifiable_query.to_signable_string` (the body) against the secret, never the shop header: [4](#0-3) 

The break is an equality that the gem implicitly promises but never enforces:
`hmac_valid(body) == true` should imply `shop_header == shop_that_produced(body)`, but `shop_header` is attacker-controlled and outside the signed payload. Since `api_secret_key` is a single **app-level** secret shared by every shop that installs the app (not a per-shop secret), any user can install the target public/custom app on their own store, trigger a webhook for their own shop, capture the valid `(raw_body, hmac)` pair Shopify sends, and replay it to the same webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim merchant's domain. The signature still validates (body unchanged), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is fully attacker-controlled.

The gem's own documentation reinforces the false guarantee, stating `process` "will verify the request did indeed come from Shopify" and that handlers can rely on `data.shop` as "The shop domain of the webhook."

### Impact Explanation
This is a cross-tenant identity-binding break: the tenant (`shop`) that a host application attributes incoming webhook data/actions to is not the tenant whose signature was actually verified. Any app that uses `data.shop` (as directly recommended in the gem's docs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) to look up shop-specific storage, credentials, or business logic will process attacker-supplied body content under a victim shop's identity — enabling cross-tenant data injection/corruption using only the ability to install the app on one's own store, which is normal, unprivileged usage.

### Likelihood Explanation
Requires only: (1) install the target app on an attacker-controlled store (ordinarily permitted for any public/custom app), (2) trigger any subscribed webhook topic on that store, (3) capture the outbound POST (body + `x-shopify-hmac-sha256`), (4) replay it to the app's webhook endpoint with a rewritten `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged role is needed — the shared `api_secret_key` is never exposed to the attacker and is not required for this attack since it is the *body*, not the header, that is signed.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`) into the signed material, or cross-check `request.shop` against the set of shops the app has legitimately installed for and against the webhook subscription that was registered for that shop/topic pair before invoking the handler. At minimum, document prominently that `data.shop` is unauthenticated and must be independently verified by the host app before being trusted as a tenant key.

### Proof of Concept
1. Install the target app (using this gem) on attacker-owned store `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g. `orders/create`) on that store; capture the Shopify-sent request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. POST to the app's webhook endpoint with:
   - body `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim.myshopify.com` (rewritten)
   - header `x-shopify-topic` set to the registered topic
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity.
