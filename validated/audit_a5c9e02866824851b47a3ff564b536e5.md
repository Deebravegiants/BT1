### Title
Session Hijacking via Deterministic, Unsigned Session Cookie Value in Non-Embedded OAuth Flow - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session lookup key exclusively from the raw value of an unsigned `shopify_app_session` cookie. That value is set by `ShopifyAPI::Auth::Oauth.validate_auth_callback`/`ShopifyAPI::Auth::Oauth::SessionCookie` to a **deterministic, guessable** id (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions) rather than an unpredictable secret token bound to the authenticated request. Because the cookie carries no HMAC/signature and the id format is a pure function of the publicly-known shop domain, an unprivileged attacker can forge the cookie to make the host app's session store resolve another merchant's stored session (and its `access_token`).

### Finding Description
The binding that should hold is: `cookie_bytes_received_by_app == bytes_the_gem_authenticated_and_issued_for_this_specific_browser/session`. In practice the gem breaks this equality because it never authenticates the cookie bytes at all — it treats "possession of the cookie value" as proof of session ownership.

- `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the cookie purely from `session.id`, with no signature: [1](#0-0) 
- `Session.from` computes that id deterministically from the shop domain (and, for online sessions, the numeric Shopify user id, which is also not secret): [2](#0-1) 
- `SessionCookie` is a bare struct (`name`, `value`, `expires`) with no signing/integrity mechanism of its own: [3](#0-2) 
- The gem's own documented integration example stores this value in a plain cookie jar (`cookies[name] = {value:, secure:, http_only:}`), not a signed/encrypted one: [4](#0-3) 
- Finally, `SessionUtils.current_session_id`/`cookie_session_id` reads that cookie value back and hands it directly to the host app as the session identifier, with zero validation that it was actually issued to this browser: [5](#0-4) [6](#0-5) 

Contrast this with the JWT-based embedded flow, where `Auth::JwtPayload` cryptographically binds the shop (`dest`) and app (`aud`) into a signed token before deriving a session id: [7](#0-6) . No equivalent binding exists for the cookie-based path used by non-embedded apps.

### Impact Explanation
Because `offline_#{shop}` and `#{shop}_#{user_id}` are computable from public information (the target's `*.myshopify.com` domain, and — for online sessions — a small, often enumerable numeric user id), an attacker can set `shopify_app_session=offline_victim-shop.myshopify.com` on a request to the app and have the host app's session storage (built exactly as documented) return the victim's `Session`, including its Admin API `access_token`. Subsequent Admin API calls made "on behalf of" the attacker's request would then execute against the victim's shop using the victim's token — a cross-tenant access / token-misuse condition (Critical: cross-tenant access to another merchant's access token).

### Likelihood Explanation
This is exploitable by any unauthenticated internet user who knows (or can enumerate) a target's shop domain — no `api_secret_key`, access token, or privileged access is required, only the ability to send an HTTP request with a crafted `Cookie` header. It requires the host app to follow the gem's own non-embedded documentation literally (plain cookie storage), which is the pattern shown in the gem's docs.

### Recommendation
Do not use a deterministic/guessable value as the session cookie payload. Either (a) sign/encrypt the `shopify_app_session` cookie value (e.g., HMAC it with `Context.api_secret_key`, verifying the MAC before trusting the embedded session id), or (b) issue an unguessable, per-browser random token as the cookie value and store the mapping to the real session id server-side, so that possession of the raw cookie bytes cannot be forged from public information alone.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` completes offline OAuth with the app; the app stores a `Session` keyed by `offline_victim-shop.myshopify.com` (per `Session.from`) and sets `shopify_app_session=offline_victim-shop.myshopify.com` in the merchant's browser (per `Oauth.validate_auth_callback` + docs example).
2. Attacker, from any browser/HTTP client, sends a request to the same non-embedded app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` straight from the forged cookie with no signature check.
4. The host app's session repository looks up and returns the victim's stored `Session` (containing `access_token`), and the app proceeds to serve/act using the victim's credentials for the attacker's request.

        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else
            id = "offline_#{shop}"
          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
            is_online: is_online,
            associated_user_scope: associated_user_scope,
            associated_user: associated_user,
            expires: expires,
            shopify_session_id: access_token_response.session,
            refresh_token: access_token_response.refresh_token,
            refresh_token_expires: refresh_token_expires,
          )
