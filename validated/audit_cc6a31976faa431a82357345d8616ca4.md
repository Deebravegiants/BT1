### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the host application's webhook handler are read directly from unauthenticated HTTP headers. This breaks the intended identity binding `HMAC-verified bytes == data acted upon`, since the signature covers only the body, not the shop/topic metadata used to route and attribute the webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are pulled straight from HTTP headers and are never part of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof that the entire request — including `request.shop` and `request.topic` — is authentic, and forwards those header-derived values straight to the app's handler: [4](#0-3) 

Because the client_secret used to sign webhooks is shared across every shop that installs a given app, any unprivileged user can install the app on their own store, capture one genuine `(raw_body, hmac)` pair from a real webhook delivery, and then POST that identical body/HMAC to the app's public webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header (and any topic value in `x-shopify-topic`). `HmacValidator.validate` still returns `true` because the signature only vouches for the body bytes, not the header claims. The forged `shop`/`topic` values then flow unchecked into `WebhookMetadata`, which the host application uses to attribute/act on data for a specific tenant.

### Impact Explanation
This lets an attacker who has legitimately obtained one valid webhook signature (trivially, by installing the app on their own shop) inject data that is falsely attributed to an arbitrary victim shop and/or an arbitrary registered topic. Host applications built on top of this gem's documented `Registry.process`/`WebhookMetadata` API (see `docs/usage/webhooks.md`) reasonably assume that a passing HMAC check authenticates the `shop` and `topic` fields together with the body, since Shopify's own documentation presents shop/topic headers as trustworthy once HMAC validation succeeds. Exploiting this allows cross-tenant confusion: fabricated webhook events (e.g., "product update", "order create") can be delivered under a victim shop's identity, corrupting per-tenant state in the consuming application without any credential belonging to that victim.

### Likelihood Explanation
Any registered app developer/tester can obtain a valid `(body, hmac)` pair for their own store at will (no privileged access required), and Shopify's webhook endpoints are public HTTP(S) URLs with no additional caller authentication beyond this HMAC check. Replaying the captured pair with modified headers is a simple network request, requiring no secrets belonging to the target shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) values into the signed payload verification path — e.g., include the `shop-domain` and `topic` headers as part of `to_signable_string`, or independently cross-check that the `shop` header matches a shop for which the app holds an active session before invoking the handler. At minimum, document clearly that `request.shop`/`request.topic` are NOT covered by the HMAC and must be independently validated by the host application before being trusted for per-tenant data attribution.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture the raw body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify sends (valid because signed with the app's real `client_secret`).
2. Send a POST to the target app's webhook endpoint with:
   - `raw_body = B`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or any registered topic)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only re-computes HMAC over `B`, and it matches `H`, so validation passes: [5](#0-4) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is constructed with the attacker-forged `shop` value and passed to the host application's handler as if it were an authentic event for `victim-shop.myshopify.com`.
