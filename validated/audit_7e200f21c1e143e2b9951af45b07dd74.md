### Title
Overpaid native-token fee in `EvmHost.dispatch()`/`increaseFeeAmount()` is silently absorbed by the router with no refund path to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and the fee-bump path use `swapETHForExactTokens` to convert any `msg.value` sent by a dispatching application into the exact `post.fee`/`get.fee` amount of fee token, but never capture the router's returned `amounts` array nor refund the unspent native token back to the original caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The identical pattern is used for `dispatch(DispatchGet)`: [2](#0-1) 

Uniswap V2's `swapETHForExactTokens` treats `msg.value` as `amountInMax`: it spends only as much ETH as needed to buy the exact `post.fee` output and refunds any unspent ETH — but the refund destination is `msg.sender` of the router call, which here is `EvmHost` itself (`address(this)` is the recipient of the *tokens*, but the router refund of excess ETH goes to the caller of `swapETHForExactTokens`, i.e., `EvmHost`). `EvmHost` neither reads the `amounts` return value nor forwards any leftover native token back to `_msgSender()` (the app/user that funded the call). Any ETH sent above what the swap actually consumes is permanently stranded inside the `EvmHost` contract, with no accounting variable or withdrawal path tied to the original payer.

This is directly analogous to the reported class of bug: an unprotected swap parameter (there, `minAmountOut` hardcoded to 0; here, the unbounded/unrefunded delta between `msg.value` and actual swap cost) causes value that should return to the caller to be lost due to on-chain price movement or the caller's own margin of safety when estimating `msg.value`. The correctly-implemented sibling function `IntentGatewayV2.placeOrder` shows the intended pattern — it captures `amounts[0]` and refunds the difference: [3](#0-2) 
`EvmHost.dispatch()` omits this refund step entirely.

### Impact Explanation
Any unprivileged contract or EOA dispatching a POST or GET request through Hyperbridge and paying the relayer fee in native token (a documented, supported payment path — "Payment for the request can be made with either the native token or the feeToken. If native tokens are supplied, it will perform a swap under the hood...") loses any native token sent in excess of what the swap actually consumes to buy `post.fee`/`get.fee` fee-token units. Because callers must estimate `msg.value` in advance (quote slippage, gas price volatility, DEX price movement between quote and execution) and cannot possibly send the exact wei amount the router will consume, in practice most native-fee-paying dispatches will overpay and have the excess permanently trapped in `EvmHost` with no recorded owner and no sweep/refund mechanism visible in this function. This is a direct, protocol-wide loss of user/application funds on the primary dispatch path (message dispatch reachable from any transaction), warranting a medium-risk rating consistent with the referenced report's judged severity for missing output/refund handling around an AMM swap.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any caller using the native-token fee payment option (rather than pre-approving the ERC20 fee token) will almost never supply the exact wei amount consumed by the router, since that amount depends on live pool reserves at execution time. This is not an edge case requiring an attacker — ordinary usage triggers fund loss on every overestimated `msg.value`.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)` (and the fee-bump function using the same pattern), and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    _sendValue(_msgSender(), msg.value - amounts[0]);
}
```

### Proof of Concept
1. Deploy/observe `EvmHost` with `_hostParams.uniswapV2` set to a live Uniswap V2 router and `feeToken()` configured.
2. An application (or user) calls `dispatch(DispatchPost)` (or `DispatchGet`) with `post.fee = X` fee-token units and sends `msg.value = Y` native token, where `Y` is a reasonable overestimate of the ETH needed to buy `X` fee tokens (as any caller must do, since exact reserves are unknown at call time and change between quote and inclusion).
3. Internally, `swapETHForExactTokens{value: Y}(X, path, address(this), block.timestamp)` spends `amountIn < Y` ETH to acquire exactly `X` fee tokens and refunds `Y - amountIn` ETH to `msg.sender`, which is `EvmHost`.
4. `EvmHost.dispatch()` does not capture the returned `amounts` array and does not transfer any ETH back to `_msgSender()` (the original caller); the request is dispatched using only `post.fee`/`get.fee`, with no reference to the leftover ETH.
5. The leftover `Y - amountIn` remains in the `EvmHost` contract balance indefinitely, unrecoverable by the original payer, confirmed by comparing `EvmHost`'s ETH balance before and after the call and the absence of any subsequent transfer event to `_msgSender()`.
