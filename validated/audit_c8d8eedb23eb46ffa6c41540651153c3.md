### Title
Tron `IntentGatewayV2.setParams` performs a critical, one-time bootstrap parameter change with no event emitted - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` exposes an initial admin-only `setParams` function that sets all critical operational parameters for the gateway (host, dispatcher, solver-selection flag, fee configuration, price oracle) and irrevocably burns the admin role, but it emits no event, unlike the equivalent cross-chain `onAccept`/`UpdateParams` path which emits `ParamsUpdated` and `DestinationProtocolFeeUpdated`.

### Finding Description
`IntentGatewayV2.sol` (Tron) declares a `ParamsUpdated` event [1](#0-0)  intended to report parameter changes, and the cross-chain `onAccept`/`UpdateParams` governance path correctly emits it together with `DestinationProtocolFeeUpdated` for each destination fee change, as confirmed by the test suite [2](#0-1) .

However, the admin-only bootstrap function `setParams`, which sets `host`, `dispatcher`, `solverSelection`, `surplusShareBps`, `protocolFeeBps`, and `priceOracle` in one shot and then permanently zeroes out `_admin`, never emits `ParamsUpdated` or any other event:

```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
``` [3](#0-2) 

These parameters are exactly the "critical arithmetic parameters" analog to `BondBaseSDA.setDefaults`: `protocolFeeBps` and `surplusShareBps` directly determine how much of every user's escrowed input tokens is retained as protocol fee versus paid to the filler on every `placeOrder` call:

```solidity
uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
if (protocolFeeBps == 0) {
    protocolFeeBps = _params.protocolFeeBps;
}
...
if (protocolFeeBps > 0) {
    reducedInputs = new TokenInfo[](inputsLen);
``` [4](#0-3) 

Because `setParams` runs before `_admin` is burned, and never emits an event, relayers, solvers, integrators, and users have no on-chain log to confirm what fee/host/dispatcher configuration was actually applied at bootstrap. Any off-chain indexer, monitoring pipeline, or solver bot that relies on event logs (as the codebase itself does for the cross-chain path, per the `ParamsUpdated`/`DestinationProtocolFeeUpdated` checks in tests) will silently miss this initial, irreversible configuration and could compute fees, bids, or safety checks against stale/incorrect assumptions.

### Impact Explanation
This is a low-severity, indexing/observability gap rather than a fund-loss bug in the strict sense demanded by the validation rubric (no forged messages, no unbacked mint, no unauthorized state transition — the call is authenticated to `_admin` and the values are still readable via `params()`). It does not on its own enable theft or freezing of funds; it only makes an on-chain state change invisible to off-chain observers who rely on events rather than storage reads.

### Likelihood Explanation
Low — it fires only once, during a deliberate admin-driven bootstrap flow, and is unauthenticated to any attacker (only `_admin` can call it before it self-destructs its own privilege).

### Recommendation
Emit a `ParamsUpdated(Params(0,...), p)`-style event (and, if applicable, `DestinationProtocolFeeUpdated` events for any configured destination fees) inside `setParams` before zeroing `_admin`, mirroring the emission already performed in the cross-chain `onAccept`/`UpdateParams` path, so indexers and solvers can reliably track the gateway's live configuration from genesis.

### Proof of Concept
Not applicable — no exploit is required; the omission is directly visible by reading `setParams` at [5](#0-4)  and comparing to the event-emitting `onAccept`/`UpdateParams` flow verified in the Foundry test at [2](#0-1) .

**Note:** Given the stated rule to accept "Medium, High and Critical only; no low, or resource-only analogs," this finding — while a valid analog of the referenced M-3 bug class — is itself an observability/low-severity issue with no direct path to fund theft or freezing, so it likely does not meet the bar this scan is intended to surface. I flag it transparently but do not claim it clears the Medium+ impact bar.
