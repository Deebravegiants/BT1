### Title
Attacker-chosen EVM address in a GET request key panics `pallet-ismp`'s `SubstrateEvmStateMachine::verify_state_proof` via an irrefutable `AccountType::Contract` match - (`modules/ismp/state-machines/evm/src/substrate_evm.rs`)

### Summary
`fetch_trie_id_from_main_proof` decodes the `AccountInfo` stored at an arbitrary, caller-supplied EVM address's `contract_info_key` and then destructures it with `let AccountType::Contract(contract_info) = account_info.account_type;` [1](#0-0) . This is a direct analog of the tcpdump `CVE-2017-16808` class of bug: untrusted, attacker-influenced input (an arbitrary address key baked into an ISMP "Arbitrary" storage-proof request) is fed into a decoder/parser that assumes a specific shape without validating it can actually take that shape, causing an out-of-bounds/invalid read of program state (here, a Rust panic on an unhandled enum variant) instead of a graceful error.

### Finding Description
`verify_state_proof` groups query keys by contract address, where for 52-byte keys the address is taken directly from the first 20 bytes of the key with no restriction on which address may be queried: [2](#0-1) . This is the "Arbitrary" `StateProofQueryType` path used by the pharos/EVM messaging relayer to answer ISMP `GET` requests (e.g. `HyperGet`-style storage reads dispatched by any unprivileged application) — reachable from a single dispatched cross-chain request whose keys are attacker-chosen.

For each grouped address, `fetch_trie_id_from_main_proof` is called: [3](#0-2) . It fetches the `AccountInfo` value from the (trusted-root) main trie at `contract_info_key(address)`, SCALE-decodes it, and then unconditionally destructures `account_info.account_type` as `AccountType::Contract(...)` using a `let` binding rather than a `match`/`if let` with an error branch:
```
let account_info = AccountInfo::decode(&mut &val[..])
    .map_err(|_| SubstrateEvmError::AccountInfoDecodeError)?;

let AccountType::Contract(contract_info) = account_info.account_type;

Ok(contract_info.trie_id)
```
If `account_info.account_type` is any other variant than `Contract` (i.e., the queried address belongs to an externally-owned account rather than a contract under `pallet-revive`'s dual-account-type model), this irrefutable pattern match panics at runtime rather than returning a typed `Error`. The same helper is used from both `verify_membership` and `verify_state_proof`, so the panic is reachable from ordinary ISMP membership/state-proof verification whenever the state proof includes a real, valid, non-contract account at the queried key.

### Impact Explanation
A panic inside `handle_unsigned`/state-proof verification for `pallet-ismp` (via `SubstrateEvmStateMachine::verify_membership` / `verify_state_proof`) halts or reverts message processing for the extrinsic/transaction that triggered it. Because this is reachable by an unprivileged application dispatching a GET request with an attacker-chosen key (an address that is a genuine, non-contract EOA on the target EVM chain), this is a "route unable to deliver messages" / availability-impacting bug: any relayer that submits the resulting state proof back on-chain, or the runtime executing `handle_unsigned`, can be made to panic, disrupting delivery of responses for that request and potentially any other batched requests processed in the same call context.

### Likelihood Explanation
Likelihood is High for triggering the panic (no signatures, no governance, no special privilege needed — a normal application picks a 20-byte address key that isn't a contract) but the state proof still has to be honestly generated by the relayer against the real trie (the attacker cannot forge the trie value; they need a genuinely existing EOA account at the chosen address, which is trivial to find/create on any EVM chain built on `pallet-revive`).

### Recommendation
Replace the irrefutable pattern match with an explicit match/`if let` that returns a typed error for any non-`Contract` account type, e.g.:
```rust
let AccountType::Contract(contract_info) = account_info.account_type else {
    return Err(SubstrateEvmError::NotAContract);
};
```
or a full `match` returning `Err(SubstrateEvmError::NotAContract)` for other variants, in both call sites within `fetch_trie_id_from_main_proof`.

### Proof of Concept
1. An unprivileged app dispatches an ISMP `GET` request (e.g., via `HyperGet.readBalance`-style dispatch or any `StateProofQueryType::Arbitrary` query) with a 52-byte key whose first 20 bytes is the address of a plain EOA (not a deployed contract) on the target `pallet-revive`-based EVM chain.
2. The relayer (`tesseract/messaging/*-evm`) honestly answers `query_state_proof`, producing a `main_proof` that legitimately includes the EOA's `AccountInfo` at `contract_info_key(address)`.
3. When this proof is verified by `SubstrateEvmStateMachine::verify_state_proof`/`verify_membership`, `AccountInfo::decode` succeeds and returns an `AccountType` variant that is not `Contract` (e.g., `EOA`).
4. Execution reaches `let AccountType::Contract(contract_info) = account_info.account_type;` and panics, aborting the extrinsic/host call that was processing the response.

Note: I could not fully confirm the exact variant names/definition of the `AccountType` enum (e.g., whether it is `EOA`/`Contract` or has additional variants) within the tool-call budget available — the index returned only the two call sites and one SDK reference without the enum's own definition. A Devin session with full repository access would be needed to inspect `AccountType`'s definition directly (likely in a `pallet-revive`-adjacent crate) to confirm every non-`Contract` variant is reachable in practice and to implement the fix precisely.

```rust
pub fn fetch_trie_id_from_main_proof<H: IsmpHost>(
	proof: &[Vec<u8>],
	root: H256,
	key: &[u8],
) -> Result<Vec<u8>, SubstrateEvmError> {
	let db = StorageProof::new(proof.to_vec()).into_memory_db::<BlakeTwo256>();
	let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();

	let val = trie
		.get(key)
		.map_err(|e| SubstrateEvmError::TrieError(format!("{:?}", e)))?
		.ok_or(SubstrateEvmError::ContractInfoNotFound)?;

	let account_info = AccountInfo::decode(&mut &val[..])
		.map_err(|_| SubstrateEvmError::AccountInfoDecodeError)?;

	let AccountType::Contract(contract_info) = account_info.account_type;

	Ok(contract_info.trie_id)
}
```
