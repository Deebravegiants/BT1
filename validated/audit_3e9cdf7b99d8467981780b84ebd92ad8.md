### Title
Same-token batch withdrawals resolve to the wrong `WithdrawalIdentifier`'s status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches PoA bridge withdrawal-status entries to a `WithdrawalIdentifier` solely by `assetId` via `findMatchingWithdrawal`, using `Array.prototype.find`, which always returns the *first* matching entry. When a batch contains two or more withdrawals of the same `nep141:*` token (e.g. `nep141:btc.omft.near`) to different destination addresses/amounts, every identifier for that token resolves to the same first-found withdrawal record, so one withdrawal's `completed` status and destination `txHash` gets misreported for another withdrawal that actually went to a different address.

### Finding Description
The broken equality is: `describeWithdrawal(wid_i).txHash` should correspond to the withdrawal whose `destinationAddress`/`amount` equal `wid_i.withdrawalParams.destinationAddress`/`amount`. Instead, for two identifiers `wid_0` and `wid_1` sharing the same `assetId`, both resolve to the same entry from the API response.

Code path:
- `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) builds one `WithdrawalIdentifier` per `WithdrawalParams` in a batch, with no check that `assetId` values are distinct across the batch, and reuses the same `intentTx` hash for all of them.
- `watchWithdrawal` (`withdrawal-watcher.ts:20-78`) calls `bridge.describeWithdrawal({...wid, logger})` independently for each identifier.
- `PoaBridge.describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry`, which queries `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — since all withdrawals in the batch share the same NEAR tx hash, this call returns the *same list of withdrawals* for every identifier in the batch.
- `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) then does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`. If the list contains two entries with the same `near_token_id` (same `assetId`), `.find()` always returns the first one in API order — regardless of which `WithdrawalIdentifier.index` invoked it, and regardless of amount or destination address.
- The function's own doc comment (lines 409-417) explicitly acknowledges: *"Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."*

Nothing upstream prevents this: `supports()` and `validateWithdrawal()` (poa-bridge.ts:81-259) validate each withdrawal in isolation (address format, min amount, no self-transfer) but never check for assetId collisions across a batch. `createWithdrawalIdentifiers` similarly performs no per-token uniqueness check — it only tracks a per-bridge-route `index` counter that is never used by `describeWithdrawal`/`findMatchingWithdrawal` for disambiguation. There is no invariant enforced anywhere that a `WithdrawalIdentifier`'s reported status corresponds to its own destination/amount when duplicate assetIds exist in a batch.

Attacker input: any unprivileged NEAR Intents user (or a counterparty whose withdrawal params an integrator forwards) can construct a withdrawal batch containing two entries with `assetId: "nep141:btc.omft.near"` but different `destinationAddress` values (and possibly different amounts). The integrator calling `IntentsSDK.waitForWithdrawalCompletion` on this batch will receive, for at least one of the two `WithdrawalIdentifier`s, the `completed` status and `txHash` belonging to the *other* withdrawal's payout.

### Impact Explanation
This is a status/hash misreport: the integrator is told a specific `WithdrawalIdentifier` (bound to their own tracked destination address/amount) is `completed` with a given `txHash`, when the on-chain payout for that `txHash` actually went to a different destination. An integrator that credits a user's ledger balance or releases funds based on this reported completion for `wid_1` could do so even though `wid_1`'s actual payout is still pending (or vice versa), or attribute the wrong `txHash` for auditing/refund purposes, potentially causing a double-credit or a credit against the wrong tx evidence. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category. It is repeatable on every batch with duplicate `assetId`s.

### Likelihood Explanation
Preconditions: the withdrawal batch must contain ≥2 entries with identical `assetId` (same PoA token) but different destinations/amounts — trivially constructible by any caller since `createWithdrawalIdentifiers`/`validateWithdrawal` impose no uniqueness constraint on assetId within a batch. Attacker cost is zero beyond normal withdrawal fees; the divergence occurs purely in the SDK's off-chain status-polling logic (`describeWithdrawal`), not in the underlying PoA bridge settlement itself. This is fully reproducible with a mocked `getWithdrawalStatus` HTTP response containing two entries for the same `near_token_id`.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId` alone — e.g., match on `assetId` + destination address (+ amount) tuple, or if the PoA API cannot support this, explicitly reject/throw when a batch contains multiple withdrawals of the same PoA token instead of silently matching the first candidate. At minimum, `createWithdrawalIdentifiers` (or `PoaBridge.validateWithdrawal`) should detect and reject batches with duplicate `assetId`s routed to `PoaBridge`, since the matching code demonstrably cannot handle them correctly.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
