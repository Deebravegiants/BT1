Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is trusted from unauthenticated headers while the HMAC only binds the raw body — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body via `Request#to_signable_string`, which returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are parsed directly from HTTP headers that are never part of the signed payload, yet they are handed to the app's handler as trusted tenant/routing identity in `WebhookMetadata`.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`. [1](#0-0) 
For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read from request headers with no cryptographic binding to the HMAC: [3](#0-2) 
`Registry.process` then uses the unauthenticated `topic` to select the handler and forwards the unauthenticated `shop` straight into `WebhookMetadata`, which the host application treats as the tenant identity for the event: [4](#0-3) 
This breaks the intended binding `shop_authenticated == shop_used_for_tenant_action`: the HMAC only proves "this body byte-string was produced with our `client_secret`", not "this body originated for shop X". Any unprivileged party who can obtain one valid `(raw_body, hmac)` pair — trivially available by installing the merchant's public app on their own free development store and receiving a legitimate webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. [4](#0-3) 
The gem's own documentation confirms host apps are expected to key their processing off `data.shop` (e.g., enqueuing background jobs by `shop_domain: data.shop`) without any additional verification, because the gem presents `shop` as already-authenticated data: [5](#0-4) 
This is the webhook-processing analog of the report's flagged pattern — "a field acted on but not covered by the HMAC" — where the security-critical field (`shop`, used as the tenant key) is disjoint from the field actually protected by the signature (`raw_body`).

### Impact Explanation
This crosses a tenant boundary: an attacker with no privileged credentials for the victim shop can cause the app to process (and enqueue/act on) webhook data tagged as belonging to a shop they do not control, by simply replaying a body/HMAC pair captured from a webhook delivered to their own store (or any topic with a predictable/empty body, e.g. `shop/redact`, `customers/redact`, `app/uninstalled`). Depending on how the host app keys work off `WebhookMetadata#shop` (e.g., looking up the victim's offline session/access token by shop domain and taking further action, or writing/deleting data under the victim's tenant record), this enables cross-tenant data corruption or triggers privileged actions (e.g., simulated `app/uninstalled` or `shop/redact` for a shop the attacker doesn't own), matching the Critical "cross-tenant access" category.

### Likelihood Explanation
High. No credentials beyond the ability to receive one legitimate webhook (from the attacker's own shop, obtainable by installing any public app that has this gem's webhook processing on a free/dev store) are required. Header forgery of `X-Shopify-Shop-Domain` is fully under attacker control on a direct HTTP POST to the app's webhook route, since the gem performs no host/origin restriction beyond the HMAC-over-body check.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-protected signable string, or otherwise cryptographically bind them (e.g., derive the "authenticated shop" only via the offline access token stored for that shop, not from the header). At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated header values that must not be treated as verified tenant identity by consuming applications, and provide a way to validate `shop` against an expected/allow-listed set of installed shop domains before dispatching to a handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives (or artificially triggers) a webhook such as `app/uninstalled` with body `{}` and a valid `X-Shopify-Hmac-Sha256` header computed by Shopify using the app's real `client_secret`.
2. Attacker replays the exact same raw body (`{}`) and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
3. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC only over the raw body (`Request#to_signable_string`), which still matches, so `HmacValidator.validate` returns `true`.
4. `Registry.process` looks up the handler by the attacker-controlled `topic` and invokes it with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)`.
5. The host app, following the documented pattern of keying background work off `data.shop`, processes an `app/uninstalled` (or other) event for `victim-shop.myshopify.com` that Shopify never actually sent for that shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. - `topic`, `String` - The topic of the webhook

  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
