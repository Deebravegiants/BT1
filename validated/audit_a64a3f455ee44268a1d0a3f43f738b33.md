## Finding [1](#0-0) 

### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , while `#shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) . `HmacValidator.validate` only checks the HMAC over `to_signable_string`, i.e. the body, never the shop header [4](#0-3) . `Registry.process` then trusts `request.shop` as the tenant identity and forwards it straight to the app's handler as the webhook's shop of origin [5](#0-4) .

### Finding Description
The binding that should hold is:
`HMAC-verified(body) == identity-bound(shop)`

but the actual code enforces only:
`HMAC-verified(body) == body`, with `shop` taken from an unauthenticated header that plays no role in signature computation.

A merchant who has installed the app on their own store receives real, validly-signed webhooks for their own shop (topic, body, and a correct `x-shopify-hmac-sha256` computed by Shopify over that body with the app's shared secret). Because the signature never covers the `x-shopify-shop-domain` header, this same merchant can replay the identical body + HMAC pair to the app's public webhook endpoint while substituting a different (victim) shop's domain in the `shop-domain` header. `HmacValidator.validate` will still return `true` because the recomputed HMAC only depends on the (unaltered) body [6](#0-5) , and `Registry.process` will dispatch the handler with `shop: request.shop` set to the attacker-chosen victim domain [5](#0-4) .

Any host application that follows this gem's documented contract — using `WebhookMetadata#shop` (populated straight from `request.shop`) as the tenant key to know which merchant's data the event body applies to — will process attacker-supplied event content under a victim tenant's identity, because the gem asserts the webhook is authentic (`HmacValidator.validate` passed) without ever binding that authenticity to the shop claim it hands back to the app.

### Impact Explanation
This breaks the tenant/shop identity binding for webhook processing: an unprivileged actor (any merchant who has installed the app, with no access to `api_secret_key`) can make the library report an authenticated webhook as originating from an arbitrary victim shop while fully controlling the body content. Depending on how the host app uses `shop` from `WebhookMetadata` (e.g., selecting the merchant record/session to mutate), this enables cross-tenant data injection/corruption — a Critical-class impact (cross-tenant access) achieved purely by exploiting a gap in this gem's own signature scope, with no credential theft required.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops: any single installing merchant already possesses a stream of correctly-signed webhooks for their own shop and only needs to change one HTTP header and resend the request to the app's publicly reachable webhook endpoint. No secret material, session, or privileged access is needed — only the header rewrite that `Request#shop` naively trusts.

### Recommendation
Bind the shop (and, ideally, topic/webhook-id) into the signature verification, not just the body — e.g. include `shop-domain`, `topic`, and `webhook-id` header values in `to_signable_string`, or otherwise cryptographically bind the `shop` field to the HMAC-covered content before exposing it via `WebhookMetadata`. At minimum, document clearly that `request.shop`/`WebhookMetadata#shop` is unauthenticated and must not be used as a tenant-selection key without an independent verification (e.g., cross-checking against a shop already known to be paired with a currently registered webhook subscription for that specific `webhook_id`).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H(B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the exact same raw body `B` and `x-shopify-hmac-sha256: H(B)` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is built; `HmacValidator.validate` recomputes `H(B)` from `to_signable_string` (= `B` only) and matches, returning `true` [2](#0-1) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [5](#0-4) , i.e., the app processes attacker-controlled order data as if it belonged to `victim-shop`.
