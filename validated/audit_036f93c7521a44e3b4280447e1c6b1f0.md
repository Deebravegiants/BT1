### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `HmacValidator.validate` checks covers the JSON payload alone. The `shop` value that `Registry.process` hands to the application's webhook handler is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never part of the signed data.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which returns only `@raw_body`. Meanwhile `shop` is derived from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC over the body and then forwards the header-derived `shop` straight to the handler without any additional binding check: [3](#0-2) 

The identity binding that should hold is: `shop attributed to the webhook == shop bound by the HMAC signature`. Because `shop` (and also `topic`, `webhook-id`, `api-version`) are excluded from `to_signable_string`, that binding does not exist — only `hmac == HMAC(secret, raw_body)` is verified, independent of which shop the header claims to be from.

This is directly analogous to the reported Wormhole `SwiftDest.postBatch` flaw: there, `unlockMsg` was acted upon (deleted, expected to be in the batch) but excluded from the packed/encoded payload that downstream consumers trust; here, `shop` is acted upon (passed to the handler as the tenant identity) but excluded from the HMAC-covered payload that proves authenticity.

### Impact Explanation
Any holder of one genuine, HMAC-signed webhook body (e.g., an attacker who installs the app on their own shop and receives their own legitimate webhooks) can replay that same body to the victim application's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the host application's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain. If the host application uses `shop` from `WebhookMetadata` to select a tenant record, store data, or trigger tenant-scoped side effects (the intended and documented usage), this results in cross-tenant data injection/confusion — an unprivileged attacker (needing only their own installed shop, not the victim's or the app's `client_secret`) can make the app process fabricated events under a different shop's identity.

### Likelihood Explanation
Likely to be exploitable in any host application that follows the gem's documented pattern of trusting `WebhookMetadata#shop` from `Registry.process`/`Request#shop` as the tenant identifier, since the gem itself does not bind that value to the signature and provides no warning that the header is unauthenticated. The only prerequisite is possession of one legitimately-signed webhook body, which any merchant/attacker installing the app can obtain for themselves.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind `shop` to the signed payload before passing it to `WebhookMetadata`. At minimum, `Request#to_signable_string` should not be the only input verified while `shop`, `topic`, `webhook_id`, and `api_version` are consumed unauthenticated — the library should require host applications to be unable to trust the header-derived shop identity for signed authenticity purposes, or explicitly bind it into the signature check in `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with a valid `x-shopify-hmac-sha256` for a given JSON body (e.g., `orders/create` payload).
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload was never signed for that shop, letting the attacker inject data attributed to a tenant they do not control.
