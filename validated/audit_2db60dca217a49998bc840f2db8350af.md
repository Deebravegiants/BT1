Confirmed: the circuit constrains only `erc20TokenAddresses`, `amountChanges`, `inAmounts`/`outAmounts` per token slot (`inTotal + amountChanges[i] === outTotal`) [1](#0-0) , and `calldataHash`/signature bind the whole `CircomData`, but nothing in the circuit or in `Hinkal.sol` constrains `feeStructure.feeToken` to be one of the two swap tokens, nor debits any UTXO for it when it differs from both.

### Title
Swap external action can drain the shared shielded pool of an arbitrary `feeStructure.feeToken` not covered by the balance equation - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` pays `circomData.feeStructure.flatFee` of `feeStructure.feeToken` to `circomData.relay` whenever `feeStructure.feeToken` is different from both the swap's `inputToken` (`erc20TokenAddresses[0]`) and `outputToken` (`erc20TokenAddresses[1]`), but that payment is never reflected in any UTXO output, any `amountChanges` entry, or any nullifier/commitment accounted for by the ZK circuit.

### Finding Description
In `swap()`, the input/output tokens are `circomData.erc20TokenAddresses[0]` and `[1]` [2](#0-1) . The relay fee logic branches on whether `feeStructure.feeToken` equals `outputToken`:

```solidity
if (circomData.feeStructure.feeToken == outputToken) {
    sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
} else {
    sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken);
    sendToRelay(circomData.relay, hinkalFee, outputToken);
}
``` [3](#0-2) 

`totalFee` used to compute `amountToSendToHinkal` only subtracts `relayFee` when `outputToken == feeStructure.feeToken`:

```solidity
uint256 totalFee = hinkalFee +
    (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
uint256 amountToSendToHinkal = swappedAmount - totalFee;
``` [4](#0-3) 

If `feeStructure.feeToken` is neither `erc20TokenAddresses[0]` (input) nor `erc20TokenAddresses[1]` (output), the `flatFee` sent to `circomData.relay` in the `else` branch is drawn straight from the contract's (Hinkal pool's) balance of that arbitrary token. This is only debited from the caller's `inputAmount` when `inputToken == feeToken` (line 47-49) — which is false in this scenario. There is no `amountChanges` entry, `outCommitments`, or nullifier for that third token in this transaction's `CircomData`, and the ZK circuit's balance equation `inTotal + amountChanges[i] === outTotal` is enforced only per-token-slot present in `erc20TokenAddresses` [5](#0-4) . Because `feeToken` need not be one of the two present slots, the pool's balance of that token can be depleted without any corresponding nullifier spend or reduction in any user's shielded UTXO set — the on-chain ERC20 balance backing other users' shielded balances of that token silently shrinks.

Also, `onlyAllowedRecipient` only checks `msg.sender` is `Hinkal` (a per-contract allow-list) [6](#0-5) , and `Hinkal._externalTransact` never validates that `feeStructure.feeToken` belongs to `erc20TokenAddresses` before invoking `runAction` [7](#0-6)  — so the caller (holder of a valid proof for *any* swap) fully controls `feeStructure.feeToken` and can pick a valuable token completely unrelated to their own swap.

### Impact Explanation
This is a High-severity issue: repeated small swaps with `feeStructure.feeToken` set to a high-value token the attacker doesn't hold in the pool, each draining `flatFee` of that token to `circomData.relay` (which the attacker fully controls, since `relay` is also just a `CircomData` field chosen by the caller in `Hinkal._internalTransact`/`_externalTransact`), permanently drains protocol-held ERC20 reserves that back other users' shielded balances of that token — a temporary/permanent freezing (insolvency) of other users' funds and unauthorized asset movement never authorized by those users' proofs.

### Likelihood Explanation
Any unprivileged EOA who can construct a valid swap proof (only needs a valid, unrelated swap with two arbitrary tokens they actually hold) can set `feeStructure.feeToken` to any third-party token and `relay` to an address they control, and repeat the attack on every swap call — likelihood is high, limited only by transaction cost and total pool balance of the targeted token.

### Recommendation
Enforce in `ExternalActionSwap.swap()` (or centrally in `Hinkal._externalTransact`) that `circomData.feeStructure.feeToken` must equal `erc20TokenAddresses[0]` or `erc20TokenAddresses[1]` (i.e., one of the tokens actually included in the balance equation for that transaction), rejecting otherwise. Alternatively, always debit the flat fee against a token slot that is part of `erc20TokenAddresses`/`amountChanges` so it is captured by the circuit's `inTotal + amountChanges[i] === outTotal` constraint.

### Proof of Concept
1. Attacker holds shielded UTXOs of `TokenA` and `TokenB` and constructs a valid transact proof for a normal `TokenA -> TokenB` swap via `ExternalActionSwap.swap()`, with `deltaAmounts[0] = -inputAmount`, `deltaAmounts[1] = +swappedAmount` matching the circuit constraints in `circuits/MainEVMCircuit.circom` lines 149-168.
2. Attacker sets `circomData.feeStructure = { feeToken: TokenC (high-value, held in bulk by the Hinkal pool from other users), flatFee: X, variableRate: 0 }` and `circomData.relay = attackerControlledAddress`.
3. Because `TokenC != inputToken` and `TokenC != outputToken`, the check on line 47-49 does not deduct anything from `inputAmount`, and in `swap()`'s fee branch (lines 78-87) `sendToRelay(relay, flatFee, TokenC)` sends `flatFee` of `TokenC` from the Hinkal pool straight to the attacker's `relay` address, with no reduction to `amountToSendToHinkal` for `TokenC` (line 89-93 only checks `outputToken == feeToken`).
4. No nullifier, `amountChanges`, or `outCommitments` entry for `TokenC` exists in this proof, so no shielded balance is debited anywhere for the stolen `TokenC`.
5. Repeating this across many transactions drains the pool's `TokenC` reserves, which other users' un-withdrawn shielded UTXOs of `TokenC` depend on for redemption — those users can no longer fully withdraw once the pool balance is depleted.
