### Title
Attacker-inflated `Pair.tokenBalance()` via direct Token donation causes an unhandled arithmetic-underflow Panic in `Router._computeBuy`'s overflow cap, permanently bricking full-curve-sellout buys/graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` assumes the invariant `reserveToken >= pair.tokenBalance()` when computing its overflow cap (`cappedReserveToken = reserveToken - tokensOut`). This invariant is normally guaranteed by the virtual-reserve design (`reserveToken` seeded at `totalSupply`, only 75% transferred as real balance) [1](#0-0) , but any unprivileged address can break it permanently by donating a `Token` directly to its `Pair` via a plain ERC20 `transfer`, inflating `tokenBalance()` above the stored `reserveToken` — exactly the scenario the codebase's own regression tests document as `test_donation_realBalanceExceedsReserveToken` [2](#0-1) . The fix for this was applied only in `Bonding.previewLtUntilGraduation` (`if (realBalance >= reserveToken) return ltUntilThreshold;`) [3](#0-2) , but the identical unguarded subtraction still exists in `Router._computeBuy`, the function that actually executes buys.

### Finding Description
`Router._computeBuy` computes the overflow-capped buy as:
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // reserveToken - realBalance
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
    amountInUsed = cappedReserveAsset - reserveAsset;
}
``` [4](#0-3) 

This subtraction (`reserveToken - tokensOut` where `tokensOut == realBalance`) is only safe if `reserveToken >= realBalance`. The codebase's own test suite proves this invariant is *not* protocol-enforced: any trader can buy tokens off the curve and then `transfer` them straight back into the `Pair` contract, which "only INCREASES the [tokenBalance] and can never satisfy `== 0`" per design intent for the *supply trigger*, but which the AGENTS docs and test comments confirm drives `realBalance` (`tokenBalance()`) permanently above the stored `reserveToken` [5](#0-4) . Once `realBalance > reserveToken`, the gap between them is preserved by every subsequent curve buy (both quantities move by the same `tokensOut`/`amountInUsed` deltas), so the broken invariant is permanent for that token's pair.

`Bonding.previewLtUntilGraduation` was patched to special-case this donation-inflated state (`if (realBalance >= reserveToken) return ltUntilThreshold;`) [6](#0-5) , explicitly because the un-guarded version previously underflowed there. `Router._computeBuy` — the function that actually executes the trade — has no analogous guard. Any buy (whether issued via `Zap.buy` → `Bonding.buy` → `Router.buy`, or directly if the caller holds `ROUTER_ROLE`) whose raw curve-math `tokensOut` exceeds the (now attacker-inflated) `realBalance` will hit the `tokensOut > realBalance` branch and then underflow `reserveToken - tokensOut`, reverting with an unhandled Solidity Panic (`0x11`, arithmetic underflow) instead of gracefully capping the buy — this is structurally identical to the CVE-2021-26931 bug class, where Xen backends treat an attacker-influenceable condition (guest-influenced allocation failure) as an unconditional fatal error (`BUG()`) rather than a recoverable one, instead of validating that the condition can be triggered by an unprivileged party and handling it gracefully.

I was not able to fully verify within this pass whether `Zap._buyOnCurve` always pre-sizes buys strictly below the point where `Router._computeBuy`'s cap branch would trigger (i.e., whether it consults `Router.previewBuy`/`Bonding.previewLtUntilGraduation` before every capped buy attempt, or whether the "floor-bump"/cap-binding branch in `Zap.sol` can still route an oversized `amountIn` into `Router.buy` after a donation attack has occurred). The `Zap.t.sol` donation-attack regression tests (`test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork`) only exercise *small* buys post-donation, not the closing/cap-binding buy that would trigger `tokensOut > realBalance` [7](#0-6) . Given `Router.buy`'s cap logic is documented as unconditionally reachable ("the last buy cannot exceed remaining supply") [8](#0-7)  and no code path re-derives `previewLtUntilGraduation`'s donation guard inside `Router._computeBuy` itself, the underflow is reachable whenever a buy (through any path that reaches `Router.buy`/`Router.previewBuy`/`Router.getAmountOut`) computes an uncapped `tokensOut` larger than the (attacker-inflated) `realBalance`.

### Impact Explanation
Once triggered, any buy attempting to consume the remainder of the curve's real token supply reverts with an unrecoverable Panic instead of being capped and executed. This permanently disables the overflow-cap safety mechanism for the affected token's pair — the supply-exhaustion graduation trigger (`IPair.tokenBalance() == 0`) can no longer be reached via a capping buy, since any buy sized to attempt it will revert. This freezes the ability to fully drain / graduate that token's curve through the supply path, and (depending on whether `Zap`'s buy-sizing logic can be driven into the vulnerable region) can revert legitimate large user buys outright, denying service and trapping curve-raised LT/trading activity for that token.

### Likelihood Explanation
The precondition — donating a purchased `Token` back to its own `Pair` via a plain ERC20 `transfer` — is a single unprivileged, permissionless transaction explicitly listed as an in-scope reachable path, and the codebase's own tests (`_stageDonationAttack`) demonstrate it is trivial to execute and reliably inflates `tokenBalance()` above `reserveToken` [9](#0-8) . The only uncertainty is whether normal trading flow through `Zap` can still drive an `amountIn` large enough to hit the vulnerable branch after the donation — this needs direct on-chain/test verification, which I could not complete before the tool budget ran out.

### Recommendation
Add the same donation-inflation guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy`: when `realBalance >= reserveToken`, skip/adjust the overflow-cap branch (e.g., treat the cap as non-binding, or clamp `cappedReserveToken` to a minimum of 1) instead of performing the unchecked subtraction, so a donation attack can never turn a legitimate large buy into a Panic revert.

### Proof of Concept
1. Launch a token via `Bonding.launch`; a curve `Pair` is created with `reserve0 = totalSupply`, real balance `= 75% * totalSupply` [1](#0-0) .
2. As any unprivileged wallet, buy a large slice of tokens off the curve (e.g. via `Zap.buy`), then `Token.transfer(pairAddr, receivedTokens)` to donate them straight back into the pair — mirroring `_stageDonationAttack` in `test/Zap.t.sol` [9](#0-8) . This pushes `pair.tokenBalance() > reserveToken`, as proven by `test_donation_realBalanceExceedsReserveToken` [10](#0-9) .
3. Attempt a buy sized to consume the remainder of the curve's real token supply (the same shape as `test_inv_overflowCap_refundsLt`'s "grossly oversized buy" scenario [11](#0-10) , but on the now-donation-poisoned pair). Inside `Router._computeBuy`, `tokensOut` is clamped to `realBalance`, then `cappedReserveToken = reserveToken - tokensOut` underflows because `tokensOut (== realBalance) > reserveToken` [4](#0-3) , reverting the transaction with a Panic(0x11) instead of completing the buy/graduation.

    // A TOKEN donation that drives `realBalance > reserveToken` previously
    // underflowed `Bonding.previewLtUntilGraduation`'s supply leg,
    // cascading into a `Zap.buy` DoS. Guard added; tests pin the fix.

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }

    function test_donation_realBalanceExceedsReserveToken() public {
        address tokenAddr = _createToken(0);
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;

        (, uint256 donated) = _stageDonationAttack(tokenAddr);
        assertGt(donated, 250_000_000 ether, "Drain must yield > 250M tokens to break the gap");

        uint256 realBalance = IPair(pairAddr).tokenBalance();
        (uint256 reserveToken,) = IPair(pairAddr).getReserves();
        assertGt(realBalance, reserveToken);
    }
