### Title
Excess native `msg.value` sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract instead of the caller, permanently trapping user funds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment and swap it for the exact `feeToken` amount required via Uniswap V2's `swapETHForExactTokens`. None of these functions check that `msg.value` equals (rather than merely covers) the required amount, and none of them forward any unused ETH back to the original transaction sender. This is the same bug class as the referenced Bebop report: any extra `msg.value` supplied above what is strictly needed is lost to the user.

### Finding Description
In each of the three functions, the native-token branch is: [1](#0-0) 

and similarly for `dispatch(DispatchGet)`: [2](#0-1) 

and `fundRequest()`: [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(amount, path, address(this), block.timestamp)` is called with the entire `msg.value`, requesting an exact output amount (`post.fee` / `get.fee` / `amount`). Per the Uniswap V2 Router implementation, any unused ETH (`msg.value - amountIn`) is refunded via a low-level ETH transfer back to `msg.sender` **as seen by the router**, which is `EvmHost` itself (since `EvmHost` is the caller of the router, not the original end user). The refund therefore lands in the `EvmHost` contract's own balance rather than being returned to the account that originally overpaid.

Critically, there is no mechanism in `EvmHost` to sweep or account for stray native ETH balance that accumulates this way — the contract's only fund-management path is the `feeToken` accounting used by `dispatchTimeOut`/`dispatchTimeOut` refunds (`IERC20(feeToken()).safeTransfer`), and the host-manager withdrawal path operates on `feeToken`, not native ETH. So any excess `msg.value` a user or an integrated application (e.g. `HyperFungibleToken.send()`, `HyperbridgeLzEndpoint.send()`, `IntentGatewayV2` order flows — all of which forward `msg.value` directly into `IDispatcher.dispatch{value: msg.value}(...)`) sends over the exact swap requirement is permanently stuck in the `EvmHost` contract with no path to recovery by the depositor.

This matches the reported bug class exactly: the code validates that `msg.value` is sufficient (implicitly, via the router's `require(amounts[0] <= msg.value)` check) but does nothing to return the difference to the caller who supplied it.

### Impact Explanation
Because `EvmHost.dispatch()` is the single most frequently used unprivileged entry point in the whole protocol — reachable by any external account or any downstream app (token bridge `send()`, LayerZero endpoint `send()`, intent gateway order fills/cancels) that forwards `msg.value` — any user who overestimates the required native-token amount (which is common, since exact swap amounts depend on live Uniswap pricing and slippage at execution time) permanently loses the excess ETH/native token. This is a direct, permanent loss of user funds with no recovery mechanism, affecting every dispatch/fundRequest call site across the SDK and app layer.

### Likelihood Explanation
High likelihood: overpayment is nearly unavoidable in practice because the documented pattern (`docs/content/developers/evm/messaging/post-requests.mdx`) explicitly instructs integrators to "estimate fees off-chain" using `quote()`, which itself is called out as being vulnerable to sandwich-attack-driven price movement between estimation and execution — meaning the actual on-chain swap input required at tx time will routinely differ from the `msg.value` sent, and any positive difference is lost, not from slippage protection but from lack of a refund path.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `evm/src/core/EvmHost.sol`, after calling `swapETHForExactTokens`, forward any leftover ETH balance received back to `_msgSender()` (e.g., via a low-level call with the ETH held by the contract before/after the swap), or replace `swapETHForExactTokens` with `swapExactETHForTokens`-style accounting plus an explicit refund of `msg.value - amountIn` to `_msgSender()`. Alternatively, revert if `msg.value` does not exactly match the computed required input amount, so users cannot accidentally overpay.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(DispatchPost)` (or any app forwarding `msg.value`, e.g. `HyperFungibleToken.send()`) with `post.fee = X` and `msg.value = 2 * quote(X)` (double the required amount, either due to slippage buffer or user error).
2. Inside `dispatch()`, `swapETHForExactTokens{value: msg.value}(X, path, address(this), ...)` is invoked; Uniswap computes `amountIn <= msg.value` needed to receive exactly `X` fee tokens, executes the swap, and refunds `msg.value - amountIn` — but to `address(this)` == `EvmHost`, not to the original caller.
3. `EvmHost`'s native ETH balance increases by the refunded amount; there is no function in `EvmHost.sol` that allows the original depositor (or anyone) to reclaim this stray balance.
4. Repeat across any number of dispatch calls: the trapped balance in `EvmHost` grows monotonically and is permanently unrecoverable by the users who overpaid.
