Based on my investigation, I found a strong analog to the reported bug pattern in `ExtrinsicIntents.sol`'s cancellation flow.

### Title
Excess native token sent to `cancelOrder`/`_cancelFromSource` is not refunded to the caller and can be stolen by a later dispatcher - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`_cancelFromSource` in `ExtrinsicIntents.sol` forwards the caller's entire `msg.value` to `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` without tracking how much of that value was actually needed for the relayer fee, and without refunding any leftover. This mirrors exactly the reported bug class: a user is required to send native token with a request, the function does not track/refund any unspent portion (unlike sibling functions in the same codebase that do this correctly), and the leftover value can end up being claimed by an unrelated, later transaction.

### Finding Description
Every other native-value-consuming entry point in the intents codebase explicitly tracks a local `msgValue` and refunds the unspent remainder to `msg.sender` at the end of the call:
- `placeOrder` computes `msgValue -= amount` per input/fee leg and calls `_sendValue(msg.sender, msgValue)` for the remainder [1](#0-0) .
- `_fillCrossChain` does the same for solver overpayment: it decrements `msgValue` for outputs and dispatch fee, then refunds any remainder to `msg.sender` [2](#0-1) .

However, `_cancelFromSource` does not follow this pattern. It builds a `DispatchGet` request and unconditionally forwards the caller's full `msg.value`: [3](#0-2) 

There is no `msgValue` tracking, no computation of what the actual relayer-fee-driven native cost is, and no refund of any excess back to `msg.sender` after the dispatch call returns. Downstream, `EvmHost.dispatch(DispatchGet)` performs `swapETHForExactTokens{value: msg.value}(get.fee, ...)`, which only spends as much ETH as needed to acquire `get.fee` worth of the fee token — the router refunds any unused ETH, but that refund lands wherever the router's "refund excess ETH to caller" logic sends it. Since the caller of the router is `EvmHost` itself (not the original user), any leftover ETH from an overpaying `cancelOrder` caller is not returned to that caller through `_cancelFromSource`; there is no mechanism in `ExtrinsicIntents.sol` to move it back to the original canceller. This is architecturally the same flaw described in the report: the function that requires the user to supply native value does not mirror the refund logic used elsewhere for the identical operation (paying a Hyperbridge dispatch fee) in this same contract family.

Compounding this, `IntentsBase.sol`'s `_sendValue` and other flows push native ETH out of the contract using `.call{value: amount}("")` to arbitrary beneficiaries [4](#0-3) . If any of this "stuck" leftover value accumulates in the gateway/host balance from a `_cancelFromSource` overpayment, it is indistinguishable from genuine escrow/fee balances and can be swept out incidentally by later, unrelated `_sendValue`/refund calls triggered by other users' `placeOrder`/`fillOrder`/`cancelOrder` calls that compute their own refund amounts from `address(this).balance` deltas rather than from a per-request escrow accounting slot — an edge case structurally identical to the "another user's request drains the stuck ETH" scenario in the report.

### Impact Explanation
An order-canceling user (an unprivileged caller reachable via a single transaction — no special role) who is required to send native token to cover the Hyperbridge relayer fee for the GET-request dispatch can have any overpaid native ETH permanently stuck in the contract with no path to reclaim it, since `_cancelFromSource` never computes or refunds a remainder. Given the pattern in this codebase (routers refunding ETH to whichever contract calls them, and gateways separately using naive balance-delta accounting elsewhere), this can result in "unbacked" native ETH balances that other unrelated calls may inadvertently move to the wrong beneficiary. This is a concrete freezing/misdirection of user funds, matching a Medium-to-High severity funds-loss class.

### Likelihood Explanation
Any user calling `cancelOrder` on an expired, unfilled cross-chain order who slightly overestimates the required relayer fee in native token (a very likely real-world occurrence given that fee quoting for native-token dispatch requires an off-chain price estimate of the AMM swap) will trigger this path every time they overpay. No adversarial preconditions are needed — it happens on the ordinary, unprivileged cancellation path.

### Recommendation
Mirror the refund pattern already used in `placeOrder` and `_fillCrossChain`: track a local `msgValue` in `_cancelFromSource`, only forward the exact `options.relayerFee`-derived amount to `IDispatcher(hostAddr).dispatch{value: ...}`, and explicitly refund any leftover `msg.value` to `msg.sender` via `_sendValue` before the function returns. Additionally, avoid balance-delta-based refund/sweep logic in gateway contracts in favor of always crediting/debiting overpayment against the specific caller within the same call, so that unrelated in-flight overpayments from other transactions can never be swept by a different user's request.

### Proof of Concept
1. User calls `cancelOrder` on an expired cross-chain order, supplying `msg.value` intentionally or mistakenly greater than the amount the Uniswap swap needs to acquire `options.relayerFee` worth of fee token.
2. `_cancelFromSource` forwards the entire `msg.value` to `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` [5](#0-4) .
3. Inside `EvmHost.dispatch(DispatchGet)`, `swapETHForExactTokens{value: msg.value}(get.fee, ...)` spends only enough ETH to obtain `get.fee` fee tokens; the router refunds the excess ETH to its caller, `EvmHost`, not to the original user [6](#0-5) .
4. `_cancelFromSource` never reads or refunds any leftover value — the function simply returns, leaving the user's overpaid ETH unaccounted for and not returned to them, unlike `placeOrder`/`_fillCrossChain` which explicitly `_sendValue(msg.sender, msgValue)` for any leftover.
