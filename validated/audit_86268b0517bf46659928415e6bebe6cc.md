### Title
Unvalidated `orb_relay_app_id` used as relay destination allows biometric-session data to be sent to an unverified/mismatched entity - (File: `src/plans/mod.rs`)

### Summary
The external finding describes an `_smartWallet` address that is trusted and used for a critical fund transfer without ever confirming the address corresponds to a real, existing, correctly-owned entity — resulting in ETH being sent to a non-existent destination and permanently lost. The closest analog in orb-core is the `orb_relay_app_id` value returned in `backend::user_status::UserData`, which is used directly as the relay-client destination (`dst_id`) that the orb "announces" itself to and subsequently exchanges signup/self-serve session data with, without the orb performing any independent confirmation that this identifier is bound to the same app/user session that scanned the QR code.

### Finding Description
When a user QR code is scanned, `backend::user_status::request` decodes `authenticated_app_data.orb_relay_app_id` from the backend response and returns it inside `UserData` [1](#0-0) . This value flows unchanged into `do_signup`, which — if self-serve is enabled and `orb_relay_app_id` is present — passes it straight into `orb_relay_announce_orb_id` as the relay `dst_id` [2](#0-1) .

`orb_relay_announce_orb_id` then constructs a new relay `Client::new_as_orb` using `orb_relay_app_id` as the peer/destination identity and immediately connects and sends session-establishing messages (`AnnounceOrbId`) to it: [3](#0-2) . If the connection and blocking send succeed, the orb stores this relay client (`orb.orb_relay = Some(relay)`) and continues the self-serve signup flow using it as the channel for subsequent session messages [4](#0-3) .

The only integrity check performed on the backend-provided `UserData` blob (which includes `orb_relay_app_id`) is `user_data.verify(user_data_hash)`, a call into the external `orb_qr_link` crate [5](#0-4) . This repository does not contain the `orb_qr_link` crate's source, so it cannot be confirmed from this codebase whether `orb_relay_app_id` is actually covered by that hash/signature, or whether the orb performs any additional confirmation that the relay peer it is about to exchange data with actually corresponds to the physical person/app that was just biometrically verified at the orb. Unlike the Ethereum case, there is no local, unprivileged-user-triggerable authenticity check equivalent to "verify the smart wallet has a valid owner" visible in orb-core for this destination identifier before it is used to establish a live data channel.

### Impact Explanation
If `orb_relay_app_id` were ever wrong, stale, or attacker-influenced (e.g., a race in session/QR issuance, backend defect, or QR replay) and not caught by `verify()`, the orb would announce itself and exchange self-serve signup session control-flow data (`AnnounceOrbId`, `SignupEnded`, etc.) with the wrong or an unintended app instance — a form of cross-session/cross-signup state bleed at the relay layer, where session control information tied to one signup ends up delivered to (or expected from) a mismatched destination. This does not match the "funds permanently locked" impact from the finding one-to-one, since the relay send failure path is handled (`Err` → `signup_orb_relay_failure`), and it is not established whether the same protective hash covers this field.

### Likelihood Explanation
Low-to-uncertain. The value originates from the backend and appears to be part of the same `authenticated_app_data` structure that is nominally covered by `user_data.verify(user_data_hash)`, so likelihood of exploitation for an unprivileged user hinges entirely on whether that external verification includes `orb_relay_app_id` — which cannot be confirmed from the orb-core index. Given the `#[cfg(not(feature = "skip-user-qr-validation"))]` gate exists specifically to enforce this check in production builds, the intended design already anticipates this class of risk, unlike the original Solidity code where no such check existed at all.

### Recommendation
Confirm (from the `orb_qr_link` crate, out of scope for orb-core review) that `orb_relay_app_id` is included in the payload covered by `UserData::verify`. If it is not currently covered, include it in the signed/hashed payload so that the orb can cryptographically confirm the relay destination is bound to the same authenticated app session before calling `orb_relay_announce_orb_id`.

### Proof of Concept
Not reproducible from this repository alone: exploitation depends on the internals of the external `orb_qr_link::UserData::verify` function, which is not present in the indexed orb-core codebase. No concrete unauthorized-signup or data-disclosure PoC can be constructed without that crate's source.
