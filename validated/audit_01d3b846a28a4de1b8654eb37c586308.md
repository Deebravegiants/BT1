### Title
Stale stored `account.owner` keeps spending authority after position NFT transfer - ([File: contracts/controller/src/account.rs])

### Summary
The controller keeps two different notions of account ownership. The `Account` struct stored at account creation carries an `owner` field that is written once at mint time and never rewritten, while `storage::account_owner` resolves the *current* owner from the position NFT. Spending-critical guards (`require_owner_or_delegate` / `is_owner_or_delegate`) compare the caller against the stale `Account.owner` field, so after the position NFT is transferred the *previous* owner retains full borrowing and withdrawal authority over the account — an incorrect-access-control analog of the Firefly III webhook flaw, where a crafted request reaches functionality the caller should no longer control.

### Finding Description
`create_account` stores `Account { owner, .. }` with `owner` fixed at mint (`contracts/controller/src/account.rs:64-71`). There is no path in `account.rs` that rewrites this field when the NFT moves — `update_or_remove_supply_position`/`update_or_remove_debt_position` touch only the position maps, and `set_supply_positions` in `risk/params.rs:218` writes only positions.

The guards then diverge by which owner source they consult:

- `is_owner_or_delegate` returns `true` immediately when `caller == owner`, where `owner` is `&account.owner` loaded via `storage::get_account` inside `load_or_create_account` (`account.rs:98-109`, `account.rs:121-127`). This guard gates `multiply`, `flash_position`, `migrate_from_blend`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral` on existing accounts, and `require_owner_or_delegate` is documented in `scripts/permissionless_entrypoints.txt` as pinning `borrow`/`withdraw` to the account owner.
- `require_account_owner` deliberately does *not* use `account.owner`; it re-resolves ownership through `storage::account_owner` (the NFT owner) and compares against the caller (`account.rs:143-148`). `sync_account_thresholds` likewise re-resolves via `storage::try_account_owner` with an explicit "fail closed" comment (`risk/params.rs:164-167`) and rebuilds the account with `account_from_parts(owner, ...)`.

The coexistence of a stored `owner` field and a separate NFT-resolution function — with the fail-closed resolution used precisely where correctness matters — shows the stored field is not guaranteed to track NFT ownership. Any verb routed through `require_owner_or_delegate` on `account.owner` therefore honors the *mint-time* owner.

### Impact Explanation
Theft of user funds / permanent loss: after a victim transfers or sells their position NFT (e.g., to a buyer, or via `transfer_from` to an approved/operator address), the former owner — an unprivileged address — can still call `controller::borrow` and `controller::withdraw` against the account because `is_owner_or_delegate` sees `caller == account.owner` (the stale mint-time value). The attacker drains the account's collateral and leaves debt to the new NFT holder, who paid for the position. This violates INV-AUTH-02's intent that spending authority follows current ownership.

### Likelihood Explanation
Reachable entirely by unprivileged addresses: the attacker needs only to have once owned the account NFT (self-created via `supply` with `account_id = 0`), then `position-nft::transfer` it to a buyer, and afterward invoke `borrow`/`withdraw` with their own `caller` auth. No privileged role, leaked key, or off-chain component is involved. The only uncertainty is whether `storage::get_account` internally re-stamps `owner` from the NFT; the code's own pattern of re-resolving via `try_account_owner`/`account_from_parts` in `risk/params.rs:165-178` rather than trusting the stored struct strongly suggests it does not.

### Recommendation
Remove `owner` from the persisted `Account` (or treat it as a cache) and make `require_owner_or_delegate` resolve the owner exclusively through `storage::account_owner`/`try_account_owner`, matching `require_account_owner`. Alternatively, hook NFT `transfer`/`transfer_from` to rewrite `Account.owner` — but a single NFT-resolved source of truth is safer, since the NFT contract already clears approvals on transfer.

### Proof of Concept
1. Attacker calls `controller::supply(attacker, 0, spoke, [(usdc, 100_000e7)])` → creates `account_id = A`, `Account.owner = attacker`, NFT `A` minted to attacker.
2. Attacker sells/gifts the account: `position_nft.transfer(attacker, victim, A)` (or `approve` + `transfer_from`). NFT owner is now `victim`; stored `Account.owner` remains `attacker`.
3. Attacker calls `controller::withdraw(attacker, A, spoke, [(usdc, 100_000e7)])`. Inside, `require_owner_or_delegate(env, A, attacker, &account.owner)` sees `attacker == account.owner` → passes. Collateral is sent to the attacker.
4. Alternatively, `controller::borrow(attacker, A, spoke, [(eth, X)])` draws debt against the victim's collateral and sends proceeds to the attacker, leaving the victim's account insolvent and liquidatable.
