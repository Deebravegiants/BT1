### Title
Fraud-detected signups still build and upload full biometric personal custody package before enforcement takes effect - (File: `src/plans/mod.rs`)

### Summary
The Wildcat report describes a blocking mechanism (`_blockAccount()`) that is triggered to cut off a flagged account, but the underlying asset transferred into the "blocked" state (the escrow) is not normalized/frozen at the time of blocking, so it keeps accruing value the block was meant to stop. The analogous pattern in `orb-core` is the signup pipeline's fraud enforcement: when the Orb's own fraud detection flags a signup as fraudulent, the enforcement is recorded only as a metadata tag (`SignupReason::Fraud`) rather than being used to gate the transfer/persistence of the sensitive biometric data (the Personal Custody Package). The data is built and uploaded exactly as it would be for a legitimate signup.

### Finding Description
In `do_signup`, fraud is evaluated via `detect_fraud()` and the result is only used to set `signup_reason`: [1](#0-0) 

Regardless of `signup_reason` being `Fraud`, the code unconditionally proceeds to build and upload the Personal Custody Package (containing iris codes, iris code shares, mask codes, normalized iris images, and face-identifier embeddings/thumbnail): [2](#0-1) 

`build_pcp` receives `signup_reason` as a parameter, but the parameter is never used to skip or redact biometric fields — it is simply forwarded into the package as metadata: [3](#0-2) [4](#0-3) 

`personal_custody_package::Plan::run` likewise treats `signup_reason` purely as a string to embed in `info.json`, not as a gate on packaging/uploading the biometric payload: [5](#0-4) [6](#0-5) 

The tier-0/1/2 packages are then uploaded to the backend via `upload_pcp_tier_0` and `data_uploader`, still without any fraud gate: [7](#0-6) 

The actual fraud enforcement (rejecting the signup) only happens later, in `enroll_user`/`report_signup_reason`, after the biometric data has already been persisted/transmitted: [8](#0-7) 

Note: the on-Orb `detect_fraud` implementation itself is a stripped/no-op FOSS build (`N_FRAUD_CHECKS = 0`) which is out of scope as a "no-fraud-checks-present" build artifact, but the structural bug — that a "Fraud" classification does not stop the biometric payload from being built and uploaded — exists in the pipeline logic independent of which checks populate `fraud_detected`.

### Impact Explanation
Just as Wildcat's blocked-account escrow keeps "earning interest" because the scaled balance isn't frozen/normalized before transfer, an Orb signup that the Orb itself classifies as fraudulent still has its full biometric template (iris codes, face embeddings, normalized iris images) packaged and uploaded to the backend/self-custody storage before the fraud verdict is enforced. This contradicts the intended enforcement semantics that a fraud-flagged signup's biometric data collection/dissemination should be halted, resulting in retention/disclosure of biometric data for a signup event that was supposed to be blocked.

### Likelihood Explanation
This occurs on every signup where `detect_fraud` (when populated with real checks) returns true — no special conditions or privileged access needed. It is a deterministic code path reachable by any unprivileged user's signup attempt that trips an on-Orb fraud heuristic.

### Recommendation
Gate `build_pcp` / `personal_custody_package::Plan::run` (and the subsequent `upload_pcp_tier_0` / `data_uploader` calls) on `signup_reason != SignupReason::Fraud`, mirroring the recommendation from the Wildcat report to normalize/freeze state before it is transferred to a place where it continues to be processed — i.e., stop the biometric payload from being built/persisted once an Orb-side fraud determination has been made, rather than only tagging it as fraud after the fact.

### Proof of Concept
1. Trigger a signup where `detect_fraud` returns `true` (fraud detected at the Orb).
2. Observe that `do_signup` still executes `build_pcp` → `personal_custody_package::Plan::run` → `upload_pcp_tier_0` / `data_uploader` sends, uploading the full iris/face biometric package with `signup_reason = "FRAUD"` embedded only as metadata.
3. Confirm the backend-side rejection (via `enroll_user`) happens only afterward, meaning the biometric data has already left the Orb and been persisted/transmitted despite the fraud verdict, matching the "enforcement doesn't prevent continued processing of the underlying asset" root cause from the Wildcat report.

    fn report_signup_reason(
        success: bool,
        signup_reason: SignupReason,
        debug_report: &mut debug_report::Builder,
    ) {
        if signup_reason == SignupReason::Failure {
            tracing::info!("User enrollment failed due to a failure in the pipeline");
            debug_report.signup_orb_failure();
        } else if signup_reason == SignupReason::Fraud {
            tracing::info!("User enrollment failed due to fraud");
            debug_report.signup_fraud();
        } else if success {
            debug_report.signup_successful();
            dd_incr!("main.count.signup.result.success.successful_signup");
        } else {
            tracing::info!("User enrollment failed");
            debug_report.signup_server_failure();
        }
