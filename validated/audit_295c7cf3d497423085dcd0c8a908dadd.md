### Title
Non-embedded session cookie value is a predictable, unsigned session ID, allowing session fixation / cross-tenant session hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/auth/session.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded (and non-JWT) apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the `shopify_app_session` cookie's value directly to the deterministic `Session#id` (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions), rather than an opaque, cryptographically-random, server-bound token. `SessionUtils.cookie_session_id` then trusts this raw cookie value as the session identifier used to look up the merchant's stored session (and its access token) with no signature or MAC over the cookie contents.

### Finding Description
- `Session.from` derives the session `id` purely from public/guessable inputs: the shop domain and the associated user id (`id = "#{shop}_#{associated_user.id}"` or `id = "offline_#{shop}"`). [1](#0-0) 
- `Oauth.validate_auth_callback` writes this same predictable `session.id` verbatim as the cookie value for non-embedded apps, with no HMAC/signature binding the cookie to the session or to the browser that completed OAuth: [2](#0-1) 
- `SessionUtils.current_session_id`/`cookie_session_id` then read this untrusted cookie value directly as the lookup key for the session (and thus its access token) with zero verification that it was actually issued by the server for the current caller: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: *the cookie's bytes == an unforgeable token bound to a specific authenticated session*. Instead the binding actually enforced is: *the cookie's bytes == a deterministic string derivable from public shop domain + a small integer user id*. This is exactly the "session id derived from unauthenticated/unbound bytes" pattern: no HMAC or server-side secret protects the cookie's integrity, so any value satisfying the naming convention is accepted as if the server had legitimately minted it.

### Impact Explanation
An unprivileged attacker who installs the app on their own store (a legitimate but low-privilege action) knows the exact session-id format used by the gem. Because shop domains are public and associated-user ids are typically small sequential integers, the attacker can enumerate or guess another merchant's session id (e.g., `offline_victim-shop.myshopify.com`, or `victim-shop.myshopify.com_1`) and set it directly as their own `shopify_app_session` cookie value when calling the app. If the host application's session storage looks up sessions by this id (which is the documented purpose of `SessionUtils.current_session_id`), the attacker's request is serviced using the victim shop's stored `Session`, including its `access_token`. This is cross-tenant access to another merchant's authenticated session/access token — a critical impact under the stated scope.

### Likelihood Explanation
Likelihood is moderate-to-high for offline sessions since the id is fully determined by the public shop domain (`"offline_#{shop}"`) with no unpredictable component at all. For online sessions, exploitability depends on guessing the numeric Shopify user id, which is often low-entropy/sequential and thus feasible to brute force. The attack requires no access to `api_secret_key`, no TLS interception, and no privileged account — only that the victim shop has an active offline (or online) session and that the app relies on this gem's cookie/session-id scheme for non-embedded session lookup, which is exactly the documented usage pattern in `docs/usage/oauth.md`.

### Recommendation
Do not use the deterministic `Session#id` as the literal cookie value. Instead, issue an opaque, cryptographically random token as the cookie value (e.g., `SecureRandom.uuid`/`SecureRandom.hex`), and maintain a server-side mapping from that opaque token to the actual session id, or sign/HMAC the cookie value (binding it to session id + expiry with the app's secret) and verify the signature before trusting it in `SessionUtils.cookie_session_id`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com`, completing OAuth normally (a legitimate, unprivileged action).
2. Attacker observes/derives that the gem's offline session id format is `"offline_#{shop}"` [5](#0-4) .
3. Attacker crafts an HTTP request to the app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` (or `victim-shop.myshopify.com_<guessed_user_id>` for an online session), where `victim-shop.myshopify.com` is any other merchant known to have installed the app.
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `cookie_session_id(cookies)` — the raw, attacker-supplied string — with no verification: [6](#0-5) .
5. If the app's session storage retrieves the `Session` object by this id (the documented flow), the attacker's request is now processed using the victim's `access_token`, achieving cross-tenant access.
