### Title
Missing ERC20 return-value validation in Tron `IntentGatewayV2.withdraw()`/`onAccept()` allows silent transfer failure and fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.sol` releases escrowed intent tokens using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the *call itself* did not revert (`success`), without decoding and validating the ABI-encoded boolean return value. For ERC20 tokens that fail silently by returning `false` instead of reverting (e.g. `ZRX`-style tokens), this makes the gateway treat a failed transfer as successful, permanently marking escrow as released/finalized while no tokens actually moved.

### Finding Description
In `withdraw()` and the `SweepDust` handler inside `onAccept()`, tokens are transferred with: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three sites the pattern is:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` only reflects whether the low-level call reverted — it does not decode `returndata` to check the boolean the ERC20 `transfer` function is supposed to return. Per the ERC20 standard, a compliant token may return `false` on failure instead of reverting (the exact pattern cited in the source report against Buffer Protocol). Against such a token, `success` is `true` even though the transfer moved zero tokens.

This is directly reachable via a **relayed proof**: `withdraw()` is invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests dispatched by Hyperbridge (authenticated only by `keccak256(incoming.request.source)`), and from `onGetResponse` for GET-based cancellation proofs: [4](#0-3) [5](#0-4) 

The escrowed token is whatever token an unprivileged user chose as an order `input` at `placeOrder` time, so any user (or attacker) can create an order using a non-standard ERC20 as the escrowed asset to trigger this path.

By contrast, the mainline EVM `IntentsBase.sol` (shared by `evm/src/apps/IntentGatewayV2.sol`) correctly uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` throughout `_withdraw()` and `_sweepDust()`: [6](#0-5) [7](#0-6) 
This confirms the raw-call, unchecked-return pattern in the Tron file is a divergence/regression from the safe pattern used elsewhere in the codebase, rather than an intentional design choice.

### Impact Explanation
When `withdraw()` processes a fill/refund for an escrowed token that silently returns `false` on failure:
- `_orders[body.commitment][token]` is still decremented and the order is marked `_filled`, so the release is treated as final and cannot be retried.
- The solver (on `RedeemEscrow`) or the original user (on `RefundEscrow`) receives zero tokens despite the protocol believing the transfer succeeded.
- The escrowed tokens remain stuck in the gateway contract with no accounting path to recover them (no corresponding "dust"/sweep entry is created for this silently-failed amount), resulting in a **permanent freezing/loss of user or solver funds**.

This satisfies the "concrete permanent freezing of funds" bar required for a valid finding.

### Likelihood Explanation
Likelihood is medium-to-high in principle: it requires that the escrowed token contract returns `false` rather than reverting on failure (a known real-world pattern, e.g., ZRX and several older ERC20s), and that a transfer condition causing a `false` return (e.g. paused token, blacklist, insufficient allowance/edge case) occurs at redemption time. Since token addresses are user-supplied at `placeOrder` and the withdrawal path is triggered by routine, permissionless cross-chain message delivery (any relayer submitting the RedeemEscrow/RefundEscrow proof), no privileged or unusual actor is needed to reach the vulnerable code — only a compatible token choice.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. `SafeERC20` decodes and validates the boolean return value (when present) in addition to checking call success, correctly reverting on tokens that fail silently.

### Proof of Concept
1. Deploy (or use) an ERC20 token that returns `false` on a failing `transfer` call instead of reverting (mirroring ZRX's behavior), and register/allow it as a valid input token for the gateway.
2. Place an order via `placeOrder` using this token as `order.inputs[i].token`, escrowing `amount` tokens in `_orders[commitment][token]`.
3. Cause a condition where a subsequent `transfer` from the gateway to the beneficiary would return `false` (e.g., token-specific transfer restriction, paused state that returns false instead of reverting).
4. Have Hyperbridge deliver a `RedeemEscrow`/`RefundEscrow` request for this commitment; `withdraw()` executes `token.call(...)`, `success == true` (the call itself succeeds), so `TransferFailed` is not raised, `_orders[commitment][token]` is decremented, and `_filled[commitment]` is set — even though the beneficiary's token balance never increased.
5. The beneficiary permanently loses the escrowed amount, and the order can never be re-processed since it is marked filled.
