This confirms the vulnerability: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC via `Utils::HmacValidator.validate(request)`, but the `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body` — it never includes `shop`, `topic`, `webhook_id`, or `api_version`. Those fields are read straight from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:20-33`) and passed unchanged into the handler via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` at `lib/shopify_api/webhooks/registry.rb:198-199`.

### Title
Webhook `shop`/`topic` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's webhook signature verification only authenticates the raw request body, not the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers. This breaks the intended binding `hmac_signed(shop) == shop_delivered_to_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then forwards the unauthenticated `request.shop` and `request.topic` straight to the application handler: [3](#0-2) 

Because the shop domain is not part of the signed payload, any body+HMAC pair that is valid for one shop remains valid (by HmacValidator) when replayed with a different `X-Shopify-Shop-Domain` header. An attacker who can trigger genuine webhook deliveries to themselves (e.g., by installing the app on a shop they control, or triggering any webhook event with an attacker-controlled, deterministic body such as an empty `{}` payload used for mandatory GDPR topics or minimal-body topics) obtains a real, validly-signed `(raw_body, hmac)` pair signed with the app's `client_secret`. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` only recomputes the HMAC over `raw_body` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), so it passes, and the app's handler executes believing the event is scoped to the victim shop — a cross-tenant identity binding break entirely analogous to the `minOut`-style "field acted upon but not covered by the signature" bug class in the report.

### Impact Explanation
This is a cross-tenant access vulnerability: an application relying on `request.shop`/`WebhookMetadata#shop` to scope side effects (e.g., updating records, revoking access, redacting data for `shop/redact` or `customers/redact` mandatory topics, or writing to a per-shop data store keyed by `data.shop`) can be made to act on the wrong tenant's data using a signature obtained from the attacker's own shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (or otherwise obtain one genuine, deterministic webhook body+HMAC pair) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with forged headers — both are within reach of an unprivileged internet user, no access token or `client_secret` needed. Likelihood is higher for topics whose bodies are constant or attacker-influenced (e.g., `{}` bodies, or topics where the attacker fully controls the resource content on their own shop).

### Recommendation
Include the authenticating identity fields (`shop`, `topic`, and ideally `webhook_id`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the verified body (e.g., require the shop domain to appear in/be derivable from the signed body, or maintain a side channel that ties webhook subscriptions to specific shops and cross-checks the header value against that record) instead of trusting the raw headers as-is.

### Proof of Concept
1. App developer/attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook handler for a topic with a fixed/predictable body (e.g., a mandatory topic with `{}` payload, or any topic whose payload the attacker fully controls via their own shop's data).
2. Shopify delivers a genuine webhook to the app: headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-SHA256: <valid HMAC of raw_body>`, body `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker sends a forged POST to the app's webhook endpoint with the same `raw_body` and `hmac`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(raw_body)` against `Context.api_secret_key` — this succeeds because `raw_body`/`hmac` are unchanged. [4](#0-3) 
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
