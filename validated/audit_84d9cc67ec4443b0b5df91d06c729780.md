Audit Report

## Title
Overweight XCM messages that structurally exceed `RECURSION_LIMIT` become permanently stuck in `TemporarilyUnprocessable` via `execute_overweight` - ([File: substrate/frame/message-queue/src/lib.rs])

## Summary
A message whose XCM payload exceeds `xcm_executor::RECURSION_LIMIT` (10) can pass the weight-check in `prepare()`/`can_consume()` without ever executing instructions, get enqueued as `Overweight` when the initial service attempt lacks sufficient weight budget, and then deterministically hit `XcmError::ExceedsStackLimit` on every subsequent `execute_overweight` retry regardless of `weight_limit`. `do_execute_overweight_inner` unconditionally maps `StackLimitReached` to `Err(Error::TemporarilyUnprocessable)` [1](#0-0) , so the message can never reach `Processed` through this path.

## Finding Description
`process_message` in `process_xcm_message.rs` first calls `XcmExecutor::prepare` to compute the required weight and checks `meter.can_consume(required)`; if the budget is insufficient it returns `ProcessMessageError::Overweight` **before ever calling `XcmExecutor::execute`** [2](#0-1) . This means the recursion-depth check inside `process()` is never exercised on that first attempt — only the weigher's own limits apply. `XcmExecutor::process()` enforces a fixed `RECURSION_LIMIT = 10` via `recursion_count::using_once`, which resets on every fresh top-level call [3](#0-2) ; this check is purely a function of the message's nested-instruction structure, independent of `weight_limit` or calling context. When the message is later replayed via `execute_overweight` with a larger budget, `execute()` actually runs and deterministically triggers `XcmError::ExceedsStackLimit → ProcessMessageError::StackLimitReached → MessageExecutionStatus::StackLimitReached`, which `do_execute_overweight_inner` maps to `Err(Error::TemporarilyUnprocessable)` on every call, never to `AlreadyProcessed` or a permanent error [4](#0-3) . The pallet's own test `execute_overweight_keeps_stack_ov_message` demonstrates this exact end state (repeated `StackLimitReached` on retry leaves the message stuck in the overweight page) [5](#0-4) , though that specific test uses a mocked toggle (`IgnoreStackOvError`) to simulate the state transition rather than a real recursive XCM payload.

The only mitigating mechanism is `do_reap_page_inner`'s `cullable()` staleness formula, but it strictly requires `page_index < book_state.begin` [6](#0-5) , so a stuck page can only be reaped once the origin's queue advances past it with further traffic; if it is the origin's only/last page, no escape hatch exists until more messages arrive.

## Impact Explanation
The affected origin's specific message is permanently stuck in `OverweightEnqueued`/`TemporarilyUnprocessable`, unresolvable by any `weight_limit` value, and its contribution to `BookStateFor::size`/`message_count` is not released unless the origin's queue advances past that page (enabling `reap_page`'s cullability) or the payload is otherwise removed. This is a localized availability/functional defect for one message on a given origin (e.g., a dormant or low-traffic channel), not an unbounded or origin-independent DoS of the whole pallet.

## Likelihood Explanation
Constructing a payload that (a) weighs successfully under the weigher's instruction-count limit yet (b) structurally exceeds `RECURSION_LIMIT=10` in nesting depth, and (c) is initially serviced with insufficient weight budget to trigger `Overweight` enqueuing rather than immediate discard, is a realistic scenario for XCM reachable via `pallet_xcm::execute`/`send` or routed HRMP/UMP messages carrying attacker-influenced instructions (e.g., nested `SetAppendix`/`Transact`). The failure on `execute_overweight` retry is fully deterministic given the message structure, so it is 100% repeatable once triggered.

## Recommendation
- Treat `StackLimitReached` returned from a manual `execute_overweight` call as permanent (drop/mark permanently unprocessable, emit an event) since retries can never succeed once the structural nesting exceeds `RECURSION_LIMIT`.
- Alternatively, have the weigher/`prepare()` phase detect and reject payloads that will structurally exceed `RECURSION_LIMIT` at execution time, classifying them permanently unprocessable during initial weighing rather than allowing them into the `Overweight` queue.
- Relax `reap_page`'s dependency on `book_state.begin` advancing, or add an explicit permissionless purge path for overweight pages whose message consistently fails with `StackLimitReached`.

## Proof of Concept
1. Construct an XCM message with nested `SetAppendix`/`Transact` instructions exceeding depth 10 (per the pattern in `transact_recursion_limit_works`), sized so `prepare()`/weigher computes a finite weight under the weigher's instruction-count limit.
2. Submit it through `pallet_xcm`/message-queue with initial available service weight too small to cover the computed weight, so `process_message` returns `Overweight` before calling `execute()`, causing `OverweightEnqueued`.
3. Call `MessageQueue::execute_overweight(origin, page_index, index, Weight::MAX)`; assert it returns `Err(Error::TemporarilyUnprocessable)` due to `ExceedsStackLimit`/`StackLimitReached`.
4. Repeat with varying `weight_limit` values; assert the result is always `Err(Error::TemporarilyUnprocessable)`, `BookStateFor` counts never decrease, and the page persists.
5. Assert `reap_page` returns `Err(Error::NotReapable)` while `book_state.begin == page_index`, confirming the message remains stuck until further origin traffic advances `begin`.
