### Title
Operator Self-Referral / Self-Signup Prevention Can Be Trivially Bypassed with a Sybil Identity - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::handle_user_qr_code` in `src/plans/mod.rs` blocks a signup attempt only when the scanned user QR-code's `user_id` is *literally identical* to the operator's own `user_id`. This is meant to stop an operator from enrolling themselves as the "user" of their own signup session (self-referral), but the check is a bare string-equality comparison of two self-reported identifiers. Exactly like the reported NFT-marketplace bug where `msg.sender != marketItem.ownerAddress` is defeated by bidding from a second wallet, this check is defeated by an operator simply presenting a *second* QR-code / identity they control instead of their operator QR-code.

### Finding Description
In `handle_user_qr_code`, the only defense against operator self-signup is: [1](#0-0) 

```rust
// Filter out the operator QR code
if user_qr_code.user_id == operator_data.qr_code.user_id {
    orb.ui.qr_scan_unexpected(QrScanSchema::User, QrScanUnexpectedReason::Invalid);
    tracing::info!("User QR-code is the same as the operator QR-code, retrying");
    ...
    return Ok(None);
}
```

`operator_data.qr_code.user_id` and `user_qr_code.user_id` share exactly the same schema, `qr_scan::user::Data` (the operator schema is literally `Data::Normal(user::Data)` as shown in `src/plans/qr_scan/operator.rs`), so an operator's QR-code and a "user" QR-code are indistinguishable except by the `user_id` value itself. That `user_id` is fully self-issued/self-controlled (via the operator's or user's own app-generated identity, matched against the backend in `backend::user_status::request`), and the operator's `user_id` is also forwarded to the backend as `distributorId` in the signup request: [2](#0-1) 

The intent of the check is to ensure the person acting as *operator* (and thus credited as `distributorId`, i.e. referrer/distributor) is not also the enrolled *user* for that signup — analogous to preventing an auction owner from bidding on, or an item owner from making offers on, their own listing. However, since the comparison only rejects an *exact* match of the same `user_id`, an operator wishing to self-refer/self-enroll can simply generate or use a second identity (a second app account / QR-code) they also control. The orb has no way to verify that the "user" identity presented is not simply another Sybil identity belonging to the same physical operator — the biometric capture that follows only binds the *iris/face* to the *user* identity, it does not bind or compare against the operator's identity at all.

This is structurally the same Sybil-resistance gap called out in the report: a same-address/same-identity check is trivially defeated by using a second, attacker-controlled identity, and "there is currently no effective way to overcome the Sybil resistance problem" for this class of check.

### Impact Explanation
If the backend credits `distributorId` (the operator) for signups it processes — e.g., referral rewards, distributor commissions, or ecosystem incentive programs tied to the number of unique users an operator brings on — an operator can trivially inflate their own referral/incentive count by enrolling themselves repeatedly under freshly generated "user" identities while orchestrating the operator side of the same physical session. The orb-side control that is supposed to prevent this (`user_qr_code.user_id == operator_data.qr_code.user_id`) provides no real protection because it only rejects the literal reuse of the same identifier, not the underlying Sybil case of the same person controlling both identities.

### Likelihood Explanation
Likelihood is high for any operator motivated to abuse a referral/incentive scheme: generating a second QR-code/identity in the companion app is a normal, unprivileged user action (no special access, hardware tampering, or backend compromise required), and the orb-side check performs no cross-identity binding beyond the string comparison.

### Recommendation
Do not rely on this orb-local `user_id` string-equality check as a security boundary against operator self-referral/self-signup. As with the original report's recommendation, the backend should not assume this client-side check is sufficient to prevent Sybil-style self-dealing; any incentive/referral logic keyed off `distributorId` vs `userId` needs backend-side controls (e.g., correlating device/session fingerprints, previous operator-user relationships, or other out-of-band signals) rather than trusting that the orb's simple identifier comparison in `src/plans/mod.rs` is Sybil-resistant.

### Proof of Concept
1. Operator scans their own operator QR-code (`user_id = A`) to start a signup session, as processed in `scan_operator_qr_code`.
2. Instead of reusing QR-code `A` as the "user" QR-code (which would be rejected by the equality check in `handle_user_qr_code`), the operator opens a second, freshly created account in the companion app and scans that QR-code (`user_id = B`) as the user QR-code.
3. The check `user_qr_code.user_id == operator_data.qr_code.user_id` evaluates `B == A` → `false`, so the signup proceeds normally.
4. The operator undergoes the biometric capture themselves (nothing in `biometric_capture`/`biometric_pipeline` verifies that the "user" being captured is a different physical person from the operator).
5. The signup is submitted to the backend with `distributorId = A`, `userId = B`, crediting the operator for referring themselves, exactly mirroring the "bid from a second wallet" bypass described in the original report.
