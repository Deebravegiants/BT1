### Title
Capability-execution path in the confidential relay handler skips owner/workflow authorization enforced on the sibling secrets-get path - ([File: core/capabilities/confidentialrelay/handler.go])

### Summary
`handleCapabilityExecute` builds its dedup/memo cache key and dispatches execution using only the request's self-reported `WorkflowID`/`ExecutionID`/`ReferenceID`/`CapabilityID`, without validating that the Workflow DON actually authorized the claimed `Owner`/`WorkflowID` pair for this request. The sibling `handleSecretsGet` path enforces exactly this check via `verifyWorkflowAuthorization`, explicitly documented as closing the "compromised TEE self-asserts a victim's owner" gap (PRIV-433). `handleCapabilityExecute` has no equivalent call, so a request that passes only attestation validation (which the code itself says a compromised/malicious TEE host can still produce) is executed and its result signed and cached under the attacker-supplied identity.

### Finding Description
`handleSecretsGet` performs, in order: attestation hash validation, enclave-config-vs-DON check, and then `verifyWorkflowAuthorization(localNode.WorkflowDON, params)`: [1](#0-0) 

The `verifyWorkflowAuthorization` function's own documentation states the exact threat this closes — a breached/compromised TEE passes attestation but must not be able to self-assert a different owner without a Workflow-DON-signed quorum naming that owner: [2](#0-1) [3](#0-2) 

`handleCapabilityExecute`, however, only performs attestation validation and the enclave-config-vs-DON check before proceeding directly to the memo/pending-request logic and executing the capability — it never calls `verifyWorkflowAuthorization` or any owner-authorization equivalent for `CapabilityRequestParams`: [4](#0-3) 

The cache/memo key used for capability execution, `capExecKey`, is derived purely from `WorkflowID`, `ExecutionID`, `ReferenceID`, `CapabilityID` — it does not bind to a Workflow-DON-authorized owner claim at all: [5](#0-4) 

`params.Owner` is only used to seed tracing context (`contexts.WithCRE`), not to gate authorization: [6](#0-5) 

Execution then proceeds by resolving the execution handler purely from `WorkflowID`/`ExecutionID` and calling the capability, signing, and caching the result — with no re-check of Owner authorization anywhere in `executeCapability`: [7](#0-6) 

This mirrors the bumpalo bug class conceptually: the sibling `handleSecretsGet` path correctly binds the cached/returned artifact's lifetime/identity to a verified authorization scope (Workflow-DON quorum over `Owner`+`WorkflowID`), while `handleCapabilityExecute` omits that binding, letting an entity that only forges/possesses a valid attestation (not a Workflow-DON quorum) drive execution and caching of a capability response under an arbitrary claimed owner/workflow identity.

### Impact Explanation
Per the code's own threat model comment, a compromised TEE host can produce a genuinely-attested request while self-asserting an owner/workflow it does not represent. On the secrets-get path this is blocked by `verifyWorkflowAuthorization`; on the capability-exec path it is not. This permits request impersonation: an attacker satisfying only attestation (not full Workflow DON quorum) can trigger capability execution and obtain a signed capability response attributed to an arbitrary `WorkflowID`/`Owner`/`ExecutionID`/`CapabilityID` tuple, and that result is memoized and served to subsequent "retries" under the same key — an authorization bypass in the internet/gateway-facing relay handler.

### Likelihood Explanation
Reaching this requires control (or compromise) of the TEE-hosting enclave/host process that talks to the gateway relay handler — the same actor model the code itself calls out for `handleSecretsGet`'s PRIV-433 fix. Since `handleCapabilityExecute` is invoked over the same `HandleGatewayMessage`/`MethodCapabilityExec` gateway entrypoint with no additional authorization gate, exploitation likelihood is directly tied to how the codebase already treats attestation-only requests as an insufficient trust boundary elsewhere.

### Recommendation
Add an owner/workflow authorization check to `handleCapabilityExecute` equivalent to `verifyWorkflowAuthorization`, validating the claimed `Owner`/`WorkflowID` against a Workflow-DON-signed quorum (via `SignedComputeRequests` or an equivalent field on `CapabilityRequestParams`) before checking the memo, creating a pending entry, or executing the capability — mirroring the ordering already used in `handleSecretsGet`.

### Proof of Concept
1. Obtain/forge a valid Nitro attestation for a `MethodCapabilityExec` request (attestation only proves genuine enclave code ran, not that the Workflow DON authorized this specific owner/workflow — per the code's own PRIV-433 comments).
2. Submit `CapabilityRequestParams` with an attacker-chosen `Owner`, existing `WorkflowID`/`ExecutionID` (matching a running execution) via the gateway.
3. `handleCapabilityExecute` validates only attestation and enclave-config-vs-DON, then proceeds through `capExecKey` memo/pending logic and `executeCapability` without ever verifying that a Workflow-DON quorum authorized this `Owner` for this `WorkflowID` — unlike `handleSecretsGet`, which would reject the equivalent request in `verifyWorkflowAuthorization`.

```go
func (h *Handler) handleCapabilityExecute(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	if req.Params == nil {
		return h.errorResponse(ctx, gatewayID, req, jsonrpc.ErrInvalidParams, errors.New("missing params"))
	}
	var params confidentialrelaytypes.CapabilityRequestParams
	if err := json.Unmarshal(*req.Params, &params); err != nil {
		return h.errorResponse(ctx, gatewayID, req, jsonrpc.ErrInvalidParams, err)
	}

	// The enclave's capability calls arrive as fresh gateway messages rather than
	// through the workflow engine, so ctx carries none of the CRE tenants the engine
	// seeds.
	//
	// Seeded as soon as the params are parsed so every ctx use below carries the
	// tenant.
	ctx = contexts.WithCRE(ctx, contexts.CRE{
		Org:      params.OrgID,
		Owner:    params.Owner,
		Workflow: params.WorkflowID,
	})

	// See handleSecretsGet: the gateway request id plus the workflow/execution
	// identity on every line, so logs correlate across the gateway, this node
	// and the enclave for one execution.
	l := logger.With(h.lggr,
		"requestID", req.ID,
		"workflowID", params.WorkflowID,
		"executionID", params.ExecutionID,
	)

	att := params.Attestation
	params.Attestation = ""
	if err := h.verifyAttestationHash(ctx, att, params, confidentialrelaytypes.DomainCapabilityExec); err != nil {
		l.Warnw("rejecting capability request: attestation validation failed", "err", err)
		return h.errorResponse(ctx, gatewayID, req, jsonrpc.ErrInternal, err)
	}

	// Verify the enclave's reported config matches the onchain DON state, same as
	// handleSecretsGet (PRIV-458): the Nitro attestation binds the request hash but
	// not the config value, so a malicious host could otherwise produce a
	// genuinely-attested request over a forged enclave config.
	localNode, err := h.capRegistry.LocalNode(ctx)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, jsonrpc.ErrInternal, fmt.Errorf("failed to get local node: %w", err))
	}
	if err = h.verifyEnclaveConfigMatchesDON(localNode, params.EnclaveConfig); err != nil {
		l.Warnw("rejecting capability request: enclave config does not match DON", "err", err)
		return h.errorResponse(ctx, gatewayID, req, jsonrpc.ErrInternal, err)
	}

	// A retry (same logical identity, new gateway request id) re-fans-out the
	// same request; return the already-computed signed result from the memo
	// instead of re-executing the capability. The signed result is params-bound,
	// not id-bound, so jsonResponse re-wraps it with this request's id.
	key := capExecKey(params)
```

```go
func (h *Handler) executeCapability(
	ctx context.Context,
	l logger.Logger,
	params confidentialrelaytypes.CapabilityRequestParams,
) (*confidentialrelaytypes.SignedCapabilityResponseResult, error) {
	payloadBytes, err := base64.StdEncoding.DecodeString(params.Payload)
	if err != nil {
		return nil, &relayError{code: jsonrpc.ErrInvalidParams, err: fmt.Errorf("failed to decode payload: %w", err)}
	}

	sdkReq := &sdkpb.CapabilityRequest{}
	if err = proto.Unmarshal(payloadBytes, sdkReq); err != nil {
		return nil, &relayError{code: jsonrpc.ErrInvalidParams, err: fmt.Errorf("failed to unmarshal capability request: %w", err)}
	}

	// Resolve the execution handler only after attestation and enclave-config
	// verification, so an unverified callback cannot make the node park a waiter.
	// The enclave's callback can beat this node's own execution start (start-edge
	// race); a bounded wait lets a straggler register and sign instead of dropping
	// below relay quorum (see handleSecretsGet).
	waitCtx, cancel := context.WithTimeout(ctx, h.getExecutionWait)
	defer cancel()
	handler, ok := h.executionHandlers.GetExecutionWithWait(waitCtx, params.WorkflowID, params.ExecutionID)
	if !ok {
		return nil, &relayError{code: jsonrpc.ErrInternal, err: fmt.Errorf("execution handler for workflow %s execution %s not found", params.WorkflowID, params.ExecutionID)}
	}

	capResp, execErr := handler.CallCapability(ctx, sdkReq)

	var result confidentialrelaytypes.CapabilityResponseResult
	if execErr != nil {
		// Not an error from this node's perspective: the execution result is a
		// signed error response the enclave's quorum logic handles; log it so
		// the capability-side failure is attributable to this node.
		l.Infow("capability execution returned an error result", "capability", sdkReq.Id, "err", execErr)
		result.Error = execErr.Error()
	} else {
		// Deterministic marshal so every relay node emits byte-identical
		// response payloads; relay aggregation requires identical bytes to
		// reach quorum. [CL112-05]
		var respBytes []byte
		respBytes, err = proto.MarshalOptions{Deterministic: true}.Marshal(capResp)
		if err != nil {
			return nil, &relayError{code: jsonrpc.ErrInternal, err: fmt.Errorf("marshalling capability response: %w", err)}
		}
		result.Payload = base64.StdEncoding.EncodeToString(respBytes)
	}

	signedResult, err := h.signCapabilityResponse(params, result)
	if err != nil {
		l.Errorw("signing capability response failed", "err", err)
		return nil, &relayError{code: jsonrpc.ErrInternal, err: fmt.Errorf("failed to sign capability response: %w", err)}
	}

	return signedResult, nil
}
```

```go
// capExecKey is the deterministic cache key for a capability-exec request,
// built from its logical identity: the (workflow, execution, step, capability)
// tuple the relay-DON signature binds to. Avoids hashing: the fields are
// required non-empty by Validate, so a plain join is stable and debuggable.
func capExecKey(p confidentialrelaytypes.CapabilityRequestParams) string {
	return strings.Join([]string{capabilityCallDomain, p.WorkflowID, p.ExecutionID, p.ReferenceID, p.CapabilityID}, "/")
}
```
