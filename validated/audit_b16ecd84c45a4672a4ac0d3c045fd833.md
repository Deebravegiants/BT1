### Title
`HotBridge.describeWithdrawal()` reports `completed` for any unrecognized non-hex status string, misreporting withdrawal outcome - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
For non-EVM/Stellar/TON landing chains, `describeWithdrawal()` treats any string value returned by `hotSdk.getGaslessWithdrawStatus()` that is neither the known `"COMPLETED"` sentinel nor a valid hex string as a completed withdrawal (with `txHash: null`), instead of treating it as pending/unknown.

### Finding Description
In `HotBridge.describeWithdrawal()`, the non-EVM/Stellar/TON branch handles the raw status value returned by the underlying HOT SDK/contract view method: [1](#0-0) 

The only two `HotWithdrawStatus` sentinels defined are `Completed` ("COMPLETED") and `Canceled` ("CANCELED") [2](#0-1) . The code correctly special-cases `Completed`. But for any other string that is not a valid hex destination hash, it logs a warning and still returns `{ status: "completed", txHash: null }`:

```
if (typeof status === "string") {
    if (!isHex(status)) {
        args.logger?.warn("HOT Bridge incorrect destination tx hash detected", { value: status });
        return { status: "completed", txHash: null };
    }
    return { status: "completed", txHash: formatTxHash(status, args.landingChain) };
}
```

This breaks the equality that the reported `WithdrawalStatus` should reflect the actual on-chain outcome (see the documented contract in `WithdrawalStatus`): [3](#0-2)  — `completed` is meant to mean "the withdrawal is settled," yet here it is returned for a value the code itself flags as "incorrect" and unparseable, with no verification that funds actually landed on the destination chain (unlike the EVM/Stellar/TON path, which cross-checks against the bridge indexer or HOT API before declaring completion, and even the test suite explicitly asserts that a `Completed` contract status without indexer confirmation must stay `pending` for TON) [4](#0-3) .

### Impact Explanation
`watchWithdrawal()` in the core watcher treats `status: "completed"` as terminal success and immediately resolves the promise (with `hash: null` when `txHash` is null), stopping all further polling: [5](#0-4) . If the underlying HOT contract/API returns any unexpected non-hex string (a new/renamed status enum value, an error message, a transient RPC artifact, etc.), the SDK will falsely report the withdrawal as completed with no destination hash, causing an integrator relying on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to credit or finalize the withdrawal in their own system prematurely, while the funds may still be in transit or the withdrawal may have actually failed. This matches the "status misreport making an integrator credit or refund twice" impact category, since polling stops and the true on-chain state is never re-checked.

### Likelihood Explanation
This path only triggers for non-EVM/non-Stellar/non-TON chains supported by HOT Bridge, and only when the raw status string is neither `"COMPLETED"` nor valid hex. This can occur if HOT's contract/API introduces or already has additional status strings beyond the two currently modeled (`HotWithdrawStatus` only enumerates `Completed`/`Canceled`, implying any other value is "unknown," not necessarily terminal), or transiently returns malformed data. Given the SDK explicitly treats such values as a detected anomaly ("HOT Bridge incorrect destination tx hash detected") yet still classifies it as success, the likelihood of triggering this on any status drift from the external HOT service is non-trivial and entirely outside the caller's control.

### Recommendation
For the non-EVM/Stellar/TON branch, do not default to `completed` when the status string is unrecognized/non-hex. Instead:
- Return `{ status: "pending" }` (matching the safer fallback already used at the end of the function) or explicitly attempt the API fallback (`fetchWithdrawalHashFromApi`) before declaring completion, consistent with how the `null`/other-value case already falls through to the API fallback further down.
- Only report `completed` when either `status === HotWithdrawStatus.Completed` (as currently handled) or a validated hex tx hash is present, mirroring the stricter EVM/TON logic that requires actual hash confirmation before completion.

### Proof of Concept
1. Configure a `HotBridge` withdrawal to a non-EVM/Stellar/TON chain (e.g., BNB/other chain path exercised by the "fallback for other non EVM networks" branch).
2. Mock `hotSdk.getGaslessWithdrawStatus()` to resolve with an arbitrary non-hex string that is not `"COMPLETED"` (e.g., `"PROCESSING"` or any malformed value from an API drift).
3. Call `bridge.describeWithdrawal(wid)`.
4. Observe the result is `{ status: "completed", txHash: null }` despite no actual confirmation of on-chain settlement, and `watchWithdrawal()` immediately resolves with `{ hash: null }`, terminating polling — as demonstrated by the existing unit tests exercising this exact branch: [6](#0-5) .
