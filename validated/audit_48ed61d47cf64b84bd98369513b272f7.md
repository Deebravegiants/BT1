Based on the code I reviewed, the claim's core technical assertions hold up:

- `UncheckedMigrateToV2::on_runtime_upgrade` does collect all v1 orders, sort them, and `try_push` them into the new bounded `OrderQueue` (capped at `ON_DEMAND_MAX_QUEUE_MAX_SIZE`), breaking on the first `QueueFull` and silently dropping the rest with only a `log::warn!`. [1](#0-0) 
- The `pre_upgrade` overflow check exists only under `#[cfg(any(feature = "try-runtime", test))]`, and is wired into `UncheckedOnRuntimeUpgrade::pre_upgrade` only under `#[cfg(feature = "try-runtime")]`, so it is not enforced during a normal (non-try-runtime) production runtime upgrade. [2](#0-1) 
- Payment for on-demand orders is charged at `place_order_*`/`do_place_order` time (withdrawn from the payer and added to `Revenue`), fully decoupled from whether the order later survives the migration. [3](#0-2) 
- The existing test `queue_full_handling` only asserts `queue.len() > 0`, not that dropped orders are accounted for or refunded. [4](#0-3) 

However, this is a one-time storage migration, not an ongoing extrinsic-triggered condition. Key considerations for validity:

1. This is a governance/runtime-upgrade-triggered code path — `on_runtime_upgrade` only executes as part of a `VersionedMigration` during an actual runtime upgrade (`MigrateV1ToV2`), which is itself a privileged, one-time governance action. [5](#0-4) 
2. The claim's likelihood argument (that an unprivileged user can accumulate a backlog exceeding the new bounded queue capacity) requires a truly massive number of concurrent unfulfilled orders, since the v1 queue had no unbounded growth beyond `on_demand_queue_max_size` at `place_order` time either — the old queue is also gated by `Error::QueueFull` when `order_status.queue.len() >= on_demand_queue_max_size` in v1 (mirrored in current code), and orders are consumed continuously by `pop_assignment_for_cores` each block. In practice, exceeding the bounded capacity (`ON_DEMAND_MAX_QUEUE_MAX_SIZE`, the same constant used for the v1 cap per the migration's comment "Old value of ON_DEMAND_MAX_QUEUE_MAX_SIZE from v1" at line 33) requires the backlog to be near-permanently saturated at the maximum queue size for an extended period, which is a systemic congestion scenario rather than something trivially "engineered" by one user pre-upgrade — the claim doesn't demonstrate that v1 and v2 have differing capacities, nor prove that the old queue historically allowed backlogs beyond what v2 can also hold. [6](#0-5) 
3. Even granting the scenario is possible, the core issue — silent truncation without refund during a governance-controlled runtime upgrade — is a real code correctness/accounting gap: it can cause funds paid by ordinary users (via unprivileged `place_order_*` extrinsics) to be permanently lost with no refund mechanism, without any attacker action beyond ordinary usage that happens to coincide with a runtime upgrade under network congestion.

This is a legitimate, narrow accounting/correctness bug reachable through ordinary paid extrinsics, but the exploit trigger (a runtime upgrade being performed while the queue backlog exceeds bounded capacity) is a rare, edge-case condition dependent on both network congestion and a governance action, not a condition an attacker can reliably force on demand. Given the rules require rejecting "governance-only" triggers and given the difficulty of proving the precondition is realistically reachable in production without unrealistic assumptions about sustained max-capacity congestion coinciding with an upgrade, I assess this report as too speculative to accept as a high/critical severity finding, but the underlying code defect (silent drop without refund, cfg-gated safety check) is real and accurately described.

Audit Report

## Title
Silent loss of paid on-demand orders during `UncheckedMigrateToV2::on_runtime_upgrade` when old-queue backlog exceeds new bounded-queue capacity - (File: polkadot/runtime/parachains/src/on_demand/migration.rs)

## Summary
`UncheckedMigrateToV2::on_runtime_upgrade` silently drops v1 on-demand orders that don't fit into the new bounded queue on `try_push` failure, with no refund and no event, while the safety check that would catch this precondition (`pre_upgrade`'s overflow check) is compiled only under `try-runtime`/`test` and is not enforced during a real, non-dry-run runtime upgrade.

## Finding Description
`on_runtime_upgrade` gathers all v1 `FreeEntries`/`AffinityEntries` orders, sorts by `QueueIndex`, and pushes them into the new bounded `OrderStatus::queue` via `try_push`; on the first `QueueFull` it logs a warning and `break`s, dropping remaining orders. [1](#0-0)  No code in this function refunds `Revenue` or emits an event for dropped orders. The `pre_upgrade` guard that checks `total_orders > ON_DEMAND_MAX_QUEUE_MAX_SIZE` only compiles under `#[cfg(any(feature = "try-runtime", test))]`, and is only invoked from the trait's `pre_upgrade` under `#[cfg(feature = "try-runtime")]`, so in a live/production runtime upgrade only `on_runtime_upgrade` runs, unguarded. [2](#0-1)  Payment for orders is collected at `do_place_order` time via `T::Currency::withdraw`/`Credits` deduction and recorded into `Revenue`, fully decoupled from the migration. [3](#0-2)  The existing regression test `queue_full_handling` only asserts `queue.len() > 0` and does not check for refunds or dropped-order accounting. [4](#0-3) 

## Impact Explanation
If triggered, affected orders' payers would receive no coretime and no refund, which is a legitimate loss-of-funds class of bug. However, both v1 and v2 queues are bounded by the same `ON_DEMAND_MAX_QUEUE_MAX_SIZE`-derived capacity concept referenced in the migration module itself, and both the legacy and current `place_order` logic reject new orders once the queue is at `on_demand_queue_max_size` [7](#0-6) , meaning the backlog cannot realistically exceed the bounded capacity under normal operation without sustained network-wide congestion at the maximum queue size persisting through a scheduled runtime upgrade.

## Likelihood Explanation
The precondition — an accumulated backlog exceeding new bounded-queue capacity at the exact moment `MigrateV1ToV2` executes — depends on both sustained network congestion and the timing of a governance-controlled runtime upgrade, not something an unprivileged actor can reliably force on demand. This is a narrow, edge-case operational scenario rather than a readily and repeatably triggerable exploit path, and the report does not demonstrate that this precondition is realistic in production given the shared capacity constants and existing queue-full rejection in `place_order`.

## Recommendation
Enforce a hard capacity check (defensive_assert/abort) inside the always-compiled `on_runtime_upgrade`, not only under `try-runtime`, and add refund/event handling for any orders that cannot be migrated (refunding from `Revenue` and emitting an `OrderRefundedOnMigration`-style event) so that no payer loses funds silently.

## Proof of Concept
Extend `queue_full_handling` (already present) to also seed `Revenue` corresponding to the injected orders, run `on_runtime_upgrade`, and assert that either `Revenue` is reduced by the dropped orders' cost or that a refund event is emitted for each dropped `para_id`; currently no such refund/event exists, demonstrating the gap, though the precondition to reach this state in production (sustained congestion at max queue capacity concurrent with a scheduled upgrade) has not been shown to be realistically achievable.
