## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an inbound webhook using an HMAC that is computed over the raw request body only. However, the `shop` (and `topic`/`api_version`/`webhook_id`) values that are actually acted upon by `ShopifyAPI::Webhooks::Registry.process` are read from unauthenticated HTTP headers that are never included in the signed material. This breaks the equality that should hold between "bytes verified" and "bytes used to identify the tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `x-shopify-shop-domain` / `shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and, once it passes, unconditionally trusts `request.shop` to build `WebhookMetadata` and dispatch it to the app's handler: [3](#0-2) 

`HmacValidator.validate` simply checks the received signature against a signature computed from `verifiable_query.to_signable_string` (i.e. the body), so it does not — and cannot — attest to the `shop-domain` header value: [4](#0-3) 

The binding that should hold is:
`shop attributed to the tenant (used by the handler)` == `shop covered by the verified HMAC`

Because the HMAC only signs `@raw_body`, this equality does not hold: the `shop` identity used to route/process the webhook is disjoint from what the signature actually authenticates.

### Impact Explanation
Any party who can obtain one valid `(raw_body, hmac)` pair for any topic (e.g. by legitimately installing the app on their own store and receiving a real Shopify-signed webhook, such as `app/uninstalled` or `orders/create`) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `x-shopify-shop-domain` header. `Registry.process` will still consider the request valid (the HMAC over the body checks out) and will invoke the registered handler with `WebhookMetadata` claiming the event belongs to the victim shop: [5](#0-4) 

Depending on what the host app's handler does with `shop` (e.g. deprovisioning data, revoking sessions, updating billing/subscription state, marking the app uninstalled for that tenant), this allows one tenant to spoof events against another tenant purely through this gem's webhook verification logic — a cross-tenant identity confusion rooted in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Likelihood Explanation
Webhook endpoints are internet-reachable POST endpoints by design (Shopify calls them from the internet), so no privileged access, TLS interception, or credentials are required. The only requirement is possession of one valid signed body for any topic/shop — trivially obtainable by any merchant who installs the app once. From there, forging the header on a replayed request is unprivileged and requires no secret knowledge, since the secret only ever protected the body, not the header.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, ideally `topic`, `api_version`, and `webhook_id`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. If Shopify's webhook signature scheme genuinely only covers the body (matching Shopify's actual HMAC scheme), the gem should not present `request.shop` as attacker-controlled-header-derived, and downstream consumers must be clearly documented as needing an out-of-band verification (e.g., only trusting `shop` for topics/webhook IDs previously registered for that specific shop, or validating that the `shop` in the header matches a session that has an active registration for that `webhook_id`/topic).

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook delivery, e.g. for `app/uninstalled`, with body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`).
2. Attacker POSTs to the victim-hosting app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and matches `H` — validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host app to process an uninstall/data-wipe/etc. event for `victim-shop.myshopify.com` even though Shopify never sent that event for that shop.
