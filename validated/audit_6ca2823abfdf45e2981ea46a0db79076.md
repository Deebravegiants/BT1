### Title
Missing Shopify domain validation in `Oauth.begin_auth` allows the OAuth authorization redirect to be pointed at an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the merchant-facing OAuth authorization redirect URL directly from a caller-supplied `shop` string, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-issuing flow in this gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`, `Clients::Graphql::Storefront`) validates `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to construct a request host, but `begin_auth` does not. This breaks the binding: `shop used to build the authorize URL == shop confirmed to be a trusted *.myshopify.com/myshopify.io/spin.dev/shop.dev domain`.

### Finding Description
`begin_auth` computes the authorization endpoint as: [1](#0-0) 

`auth_base_uri(shop)` interpolates `shop` straight into `https://#{shop}/admin` (or the dev-server branch) with no format check, then that URI is used to build `auth_route`: [2](#0-1) 

Compare this to `ShopValidator`, which exists specifically to prevent an unauthenticated `shop` value from being treated as a trusted Shopify host, and which is deliberately invoked in the other OAuth-adjacent flows: [3](#0-2) 

`begin_auth` is the entry point apps call with the `shop` parameter taken from an incoming, unauthenticated install/login request (this is exactly the value the callback's HMAC later authenticates in `validate_auth_callback`, confirming that at the `begin_auth` stage it is untrusted, attacker-influenced input): [4](#0-3) 

Because `begin_auth` never sanitizes `shop`, an app that forwards the request's `shop` query parameter into `begin_auth` (the pattern shown in `docs/usage/oauth.md`) will construct `https://<attacker-supplied-host>/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...&scope=...` and issue an HTTP redirect (or render a link) sending the victim merchant's browser to that attacker-controlled host instead of a real `*.myshopify.com` shop.

### Impact Explanation
This is a forced-OAuth-completion / open-redirect primitive in the OAuth initiation path: the victim's browser is redirected off-domain carrying the app's `client_id`, `redirect_uri`, `scope`, and the freshly minted anti-CSRF `state` nonce (which is simultaneously set in the victim's session cookie by `begin_auth`). An attacker controlling the target host can harvest this state/nonce and craft a callback that will pass the later `state == auth_query.state` check in `validate_auth_callback`, forcing the victim's session to complete an OAuth flow chosen by the attacker (session fixation / forced OAuth completion), which matches the High-severity class defined for this analysis (scope/expiry or identity-binding bypass in the OAuth flow). The rest of the callback is still HMAC-protected by Shopify's secret, but the redirection itself, the nonce disclosure, and the resulting confusion for the merchant are a direct consequence of `shop` never being checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` at the point it is turned into a request host — exactly the equality the rest of the gem enforces everywhere else `shop` is used to build a URI.

### Likelihood Explanation
Every host app that follows the documented pattern (take `shop` from the query string of the install/login route and pass it straight into `begin_auth`) is affected, since the gem itself performs no filtering. The vulnerable code path is on the unauthenticated install entry point, so no credentials, tokens, or privileged access are required to trigger it — only the ability to get a merchant to click a link.

### Recommendation
Call `ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `Oauth.begin_auth` before using `shop` in `auth_base_uri`, mirroring the pattern already used in `TokenExchange`, `ClientCredentials`, `RefreshToken`, and `Clients::Graphql::Storefront`, and raise `Errors::InvalidShopError` for any `shop` value that is not a trusted Shopify domain.

### Proof of Concept
1. A vulnerable host app implements the install route exactly as documented, passing the raw `shop` request parameter to `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: ...)`.
2. Attacker sends the victim merchant a link: `https://app.example.com/install?shop=evil.com`.
3. `begin_auth("evil.com", ...)` returns `auth_route = "https://evil.com/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=<nonce>&grant_options[]=..."` and a `SessionCookie` containing `<nonce>`, both of which `lib/shopify_api/auth/oauth.rb` lines 36-51 constructs without ever validating `shop`.
4. The victim's browser is redirected to `evil.com`, which now has the `client_id`, `redirect_uri`, and `state` nonce, and can drive the victim's browser through a crafted flow that completes against the callback endpoint using the leaked `state`, satisfying the `state == auth_query.state` check in `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb` line 71).

          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
