### Title
Backend operator/user QR verification bypass mirrors the "trusted-actor replaces trust boundary and skips signature checks" bug class - (File: src/plans/mod.rs)

### Summary
The C4 finding is about a *privileged* actor (a compromised admin) being able to bypass an authorization/verification step (`approveHash`) and take over a trust anchor (forwarder/admin) to force through unauthorized state changes. Searching orb-core for an analogous *unprivileged-reachable* pattern — where a signup-time verification step can be skipped and replaced with an operator-trusted default — the closest candidate is `MasterPlan::verify_operator_qr_code` in `src/plans/mod.rs`, which short-circuits the backend operator-validation call entirely.

### Finding Description
`verify_operator_qr_code` normally validates the operator's QR code against the backend (`backend::operator_status::request`) before trusting the returned `LocationData` [1](#0-0) . However, if `qr_code.signup_extension()` is true, the function returns a synthetic, fully-trusted `LocationData` (`team_operating_country: "DEV"`, coordinates `0,0`) **without ever calling the backend**: [2](#0-1) 

This bypass is gated on the QR code itself declaring `signup_extension() == true`, and `signup_extension`/`signup_extension_config` parsing is only reachable when the `internal-data-acquisition` Cargo feature is compiled in (`QR_CODE_SIGNUP_EXTENSION` regex parsing is `#[cfg(feature = "internal-data-acquisition")]`) [3](#0-2) . A similar unconditioned bypass exists for `self.operator_qr_code_override.is_some()`, but that value is only settable via CLI flags at process start (`--operator-qr-code`), i.e. it requires local/operator invocation control, not a remote/unprivileged attacker input.

The unprivileged-reachable part of the bug class is the `qr_code.signup_extension()` branch: whoever can produce/present a QR code that the parser recognizes as a "signup extension" code causes the orb to skip the backend operator-identity check and instead trust locally-fabricated location/validity data, propagating into the signup flow (e.g. `scan_remaining_qr_codes` → `verify_operator_qr_code` → `OperatorData`) [4](#0-3) .

### Impact Explanation
If this branch were reachable in a production build (i.e., with `internal-data-acquisition` compiled in and enabled), a party presenting a crafted "signup extension" QR code could skip the operator-identity/location authorization check that is otherwise required before any signup proceeds — an authorization-bypass analogous to the C4 report's "bypass signature/approval boundary via a maliciously-controlled trust actor." This could let an unauthorized operator drive a signup session, or someone impersonate an authorized distributor/location for accounting or fraud purposes downstream in the personal-custody package / backend signup flow (`OperatorData` feeds into `Credentials.operator_qr_code` used later in `enroll_user`/PCP building; see `TryInto<personal_custody_package::Credentials>` at `src/plans/mod.rs` line ~1898-1938).

### Likelihood Explanation
Likelihood is low-to-uncertain given the evidence gathered:
- `internal-data-acquisition` is an internal/optional Cargo feature; I could not confirm from the index whether it is enabled in the default production orb build or only in a special internal-data-collection build variant. If it's disabled in production, `signup_extension`/`signup_extension_config` can never be non-default and this code path is dead in the field.
- The other bypass condition (`operator_qr_code_override`) explicitly requires local CLI control (`--operator-qr-code` flag at binary launch), which is not an unprivileged remote attacker capability, and is excluded per the rules against hardware/local-access analogs.
- I was unable to fully verify the feature-flag matrix used in the actual production build pipeline (Cargo.toml feature defaults, flake.nix build configs) within the available tool budget, so I cannot conclusively state this path is attacker-reachable in the deployed orb.

### Recommendation
If `internal-data-acquisition` (or any equivalent "extension"/debug mode) can be present in fielded orbs, gate the `qr_code.signup_extension()` bypass so it never disables the real backend operator-status check in any build that talks to production endpoints — e.g., require an additional server-side attested flag rather than trusting a locally-parsed QR field, or require this mode to be enabled only via a signed/backend-issued configuration rather than a value derived purely from user-scanned QR content.

### Proof of Concept
Not independently reproducible from the indexed code alone: exploitation would require (1) confirming `internal-data-acquisition` is compiled into a production orb binary, and (2) crafting a QR code matching `QR_CODE_SIGNUP_EXTENSION` so `Data::from_signup_extension` sets `signup_extension: true`, then presenting it as the operator QR code during a signup session so `verify_operator_qr_code` returns the fabricated `LocationData` without a backend round-trip. I could not confirm point (1) with available tools, so this should be treated as an unverified/uncertain analog rather than a confirmed exploit path.

    /// Checks if `qr_code` is a valid operator QR-code through the backend.
    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }
