### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` (tenant) value used by `Registry.process` to route/attribute the webhook is read from an HTTP header that is excluded from the signed payload. An attacker who possesses one validly-signed webhook (e.g., from their own shop where the app is installed) can swap the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header to a victim shop and replay it; the HMAC still validates because the shop header was never part of the signable string.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signable string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string`, so it never binds the `shop` header to the signature: [4](#0-3) 

`Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity passed to the app's handler: [5](#0-4) 

This is exactly the identity-binding break described in the rules: a field (`shop`) that is acted upon (used to attribute/route the webhook to a tenant) but not covered by the HMAC that is verified. The equality that should hold — `shop used for HMAC computation == shop delivered to the handler` — is broken because the HMAC computation uses only `@raw_body`, while `shop` comes from an independently-controlled header.

### Impact Explanation
Any party who can obtain one legitimately-signed webhook body+HMAC pair (trivially available to an attacker who installs the target app on their own store and receives their own webhooks) can replay that same body/HMAC to the app's webhook endpoint while altering the `shop` header to a victim's shop domain. Because `ShopifyAPI::Webhooks::Registry.process` only re-validates the HMAC over the body and then hands `request.shop` (attacker-controlled) to the app's `WebhookHandler` via `WebhookMetadata`, the host application will process attacker-supplied webhook content under a different tenant's identity — a cross-tenant data injection scoped to whatever the app's webhook handlers do with `shop` (e.g., updating per-shop state, triggering GDPR mandatory actions like `customers/redact`, or writing data keyed by shop). This meets the Critical bar of cross-tenant access.

### Likelihood Explanation
The attack requires no privileged access to the target's account, TLS interception, or a leaked `client_secret`. The attacker only needs their own installation of the app (any merchant can install a public app) to obtain one valid signed webhook payload, then can freely re-send it with a modified shop header, since the gem itself does not bind that header to the signature.

### Recommendation
Include the shop/tenant-identifying value in the HMAC-signed payload verification, or otherwise cryptographically bind the `shop` header to the signed body (e.g., verify the header against a value embedded/covered by the signature, or require an out-of-band, per-webhook shop-to-secret mapping) before trusting `request.shop` for any tenant-scoped action in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; receive a legitimate webhook delivery for topic e.g. `orders/paid` with headers `X-Shopify-Hmac-Sha256: <valid hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and some raw body `B`.
2. Replay the exact same raw body `B` and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` only look at `@raw_body`, so `HmacValidator.validate` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled body content under the victim shop's tenant context.
