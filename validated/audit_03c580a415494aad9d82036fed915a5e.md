### Title
Webhook shop-domain and topic are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature that `Utils::HmacValidator` verifies binds nothing but the body bytes. The `shop` (and `topic`) values that `Webhooks::Registry.process` uses to identify which merchant a webhook belongs to are taken from unsigned HTTP headers, breaking the identity binding `HMAC(body) == HMAC(body)` while `shop-domain` is left completely unauthenticated.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only signs `@raw_body`. The `shop` accessor, however, is read straight from a header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately trusts `request.shop` and `request.topic` to dispatch the handler and build `WebhookMetadata`: [3](#0-2) 

Because the app's `api_secret_key` is a single shared secret used for every shop that installs the app (not a per-shop secret), any party who legitimately receives a validly-signed webhook for their own shop (e.g., by installing the app on a store they control) possesses a `(raw_body, hmac)` pair that passes `HmacValidator.validate` regardless of which `shop-domain`/`topic` header accompanies it. The signature check never verifies that the `shop` header matches the shop the body was actually signed for, so the same signed body can be replayed with an arbitrary `x-shopify-shop-domain` header value, and it will still validate successfully.

The equality that should hold is:
`shop authenticated by the signature == shop acted upon by the handler`
but in this implementation the left side is empty (the signature covers only the body), so any attacker-supplied `shop` value is accepted as authentic by downstream handler code that trusts `WebhookMetadata#shop`.

### Impact Explanation
This breaks tenant isolation ("cross-tenant access," Critical per rules) for any app whose webhook handlers key off `WebhookMetadata#shop` to locate/act on a specific merchant's stored session, data, or state (a documented and expected usage pattern for this gem, since `shop` is the field exposed for exactly that purpose). An attacker who controls one shop that has the app installed can capture one of their own legitimately-signed webhook bodies and resend it with the `shop-domain` header swapped to a victim shop, causing the app to process/mutate data as if the event originated from the victim tenant, since the gem's own `Registry.process`/`HmacValidator` provide no protection against this.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs to be a legitimate app installer (any merchant able to install the target app can trigger a real, validly-signed webhook for themselves), then replay the captured raw body against the app's public webhook endpoint with a forged shop header. No knowledge of `api_secret_key` is required to mount this — a valid signed body is obtained legitimately from Shopify's own outbound webhook delivery.

### Recommendation
Include `shop` (and ideally `topic`) in the signable string, or otherwise cryptographically/contextually bind the header-derived `shop` value used for dispatch to the signed payload before trusting it in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the host application against an installation record before being used for any tenant-scoped action.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; Shopify sends a webhook with body `{"id":1}` and header `x-shopify-hmac-sha256: <sig>` computed as `HMAC-SHA256(api_secret_key, "{\"id\":1}")`.
2. Capture `raw_body` and `sig`.
3. Send a forged request to the app's webhook endpoint with the same `raw_body`/`sig`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `HmacValidator.validate(request)`; since validation only checks `HMAC(raw_body)` against the received `sig`, it passes. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and any handler logic keyed on `shop` acts on the victim tenant using attacker-controlled body content.
