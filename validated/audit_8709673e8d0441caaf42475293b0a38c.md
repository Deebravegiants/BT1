### Title
POA bridge withdrawal status is matched by `assetId` only, causing wrong `transfer_tx_hash`/status to be reported for batched withdrawals of the same asset - (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
The POA bridge's withdrawal-status lookup identifies which on-chain withdrawal record corresponds to a caller's `withdrawalParams` using only the token's `assetId` (`near_token_id`), not the full identity of the request (`destinationAddress`, `amount`, or `index`). When a batch withdrawal contains two or more withdrawals of the same asset, the SDK can report the completion status and destination transaction hash of the wrong withdrawal.

### Finding Description
`describeWithdrawal` fetches the POA bridge's withdrawal list and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId`: [1](#0-0) 

The shared `findMatchingWithdrawal` helper used for the lower-level polling path has the exact same limitation, and this is explicitly acknowledged in its own doc-comment: "Currently only matches by assetId (near_token_id). This means multiple withdrawals of the same token in a single transaction are not supported": [2](#0-1) 

A dedicated regression test confirms the intended behavior is "matches withdrawal by assetId, not by index," i.e. the SDK deliberately ignores the withdrawal's index/position and instead scans the unsorted API response for the first entry whose asset matches: [3](#0-2) 

The SDK's own README documents batch withdrawals as a supported feature, where multiple `withdrawalParams` (potentially sharing the same `assetId` but different `destinationAddress`/`amount`) are submitted in one intent and then tracked individually via `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`, with "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`": [4](#0-3) 

This breaks the equality the original report's fix pattern targets: the "extra data"/status returned by the counterparty (here, the POA bridge indexer) is not validated to correspond to the specific request the caller made (`index`/`destinationAddress`/`amount`), only to a coarse, non-unique field (`assetId`). If two withdrawals in the same batch share an `assetId`, `findMatchingWithdrawal` will return whichever matching entry appears first in the (explicitly "unsorted") response list, regardless of which withdrawal index it actually belongs to.

### Impact Explanation
When multiple withdrawals of the same token (same `assetId`) but different `destinationAddress`/`amount` are batched in a single intent, `waitForWithdrawalCompletion`/`processWithdrawal` can report the `completed` status and `transfer_tx_hash` of a different withdrawal than the one the caller is polling for. An integrator relying on `promises[i]` corresponding to `withdrawalParams[i]` (as documented) could:
- Credit/mark as complete a withdrawal to `destinationAddress` B using the transaction hash that actually paid `destinationAddress` A (or vice versa), a hash misreport.
- Potentially credit the same underlying transaction to two different logical withdrawals, resulting in a double credit on the integrator's side even though only one on-chain transfer occurred.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category, since the SDK's returned completion status/hash does not necessarily reflect the actual on-chain outcome for the specific withdrawal being polled.

### Likelihood Explanation
This requires no malicious relayer, bridge operator, or admin action — it is triggered purely by an ordinary, SDK-supported use case: a caller submitting a batch withdrawal (`sdk.processWithdrawal`/`waitForWithdrawalCompletion` with an array of `withdrawalParams`) containing two or more entries with the same `assetId`. The POA bridge API response order is explicitly documented as unsorted, so the mismatch is a deterministic function of "same asset appears more than once in the batch," which the SDK does not detect or reject — it silently returns a matched (but wrong) result rather than erroring.

### Recommendation
`findMatchingWithdrawal` (in both `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) should disambiguate withdrawals using the full identity of the request — at minimum `destinationAddress` and `amount` in addition to `assetId`/`near_token_id` — or the POA bridge API/indexer should expose a stable per-withdrawal index/id that the SDK can correlate with `withdrawalParams[i]`. If uniqueness cannot be guaranteed, the SDK should detect ambiguous matches (multiple candidates for the same criteria) and throw/return an explicit "ambiguous" error rather than silently returning the first match.

### Proof of Concept
1. Submit a batched withdrawal intent with two `withdrawalParams` entries sharing the same `assetId` (e.g., `nep141:usdt.tether-token.near`) but different `destinationAddress` (A and B) and `amount`.
2. The POA bridge processes both withdrawals; its status API returns both entries, unsorted, both `COMPLETED`, each with its own `transfer_tx_hash`.
3. Call `waitForWithdrawalCompletion` (or `createWithdrawalCompletionPromises`) for index 0 (intended for destination A). `findMatchingWithdrawal` scans the unsorted list and matches on `assetId` only, per the existing test `"matches withdrawal by assetId, not by index"` [3](#0-2) ; if the entry for destination B happens to be returned first, `describeWithdrawal` reports index 0 as `completed` with B's `transfer_tx_hash`, even though the caller expected A's transaction.
4. The integrator credits/records withdrawal 0 as completed using the wrong transaction hash, which does not correspond to the actual `destinationAddress`/`amount` requested for that index.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
