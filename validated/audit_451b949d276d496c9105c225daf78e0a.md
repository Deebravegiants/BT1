Confirmed. This is a real, well-scoped vulnerability with clear code evidence.

The `RequestCache` (used elsewhere, e.g. `core/services/gateway/handlers/common/requestcache.go`) correctly keys entries by `globalID{sender, id}` and rejects duplicate requests [1](#0-0) , proving the codebase is aware that `MessageID` alone is not a safe key and that per-sender scoping is the intended mitigation pattern. The `capabilities` handler's `savedCallbacks` map, however, does not use this safer pattern — it keys purely by `msg.Body.MessageID` and unconditionally overwrites any existing entry with no existence/ownership check [2](#0-1) . When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes whatever callback currently sits at that key and delivers the response to it unconditionally [3](#0-2) . `Message.Validate()` only checks length/null-suffix of `MessageID`, providing no uniqueness or sender-binding guarantee [4](#0-3) , and the gateway's `ProcessRequest` entry point is reachable by any unprivileged HTTP caller, creating a fresh `Callback` per call before invoking `HandleLegacyUserMessage` [5](#0-4) . Since `HandleLegacyUserMessage` fans the request out to every DON member and waits asynchronously for the first reply [6](#0-5) , there is a genuine network-round-trip-sized window during which an attacker-supplied duplicate `MessageID` can overwrite another caller's pending callback, causing the original caller's response to be delivered to the attacker's connection instead. This matches all required validation checks: exact file/line references, a clear root cause (missing existence check / lack of sender-scoped keying), a realistic unprivileged exploit path, and a concrete in-scope impact (cross-user response corruption/hijacking on the gateway).

Audit Report

## Title
Race condition in `savedCallbacks` map allows cross-request response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` stores each caller's `Callback` in the shared `savedCallbacks` map keyed solely by the fully attacker-controlled `msg.Body.MessageID`, with no check for an existing pending entry and no sender-scoping. A second request reusing the same `MessageID` silently overwrites the first caller's callback, so the DON's eventual response for the first request is delivered to the second (attacker) caller's HTTP connection instead.

## Finding Description
`HandleLegacyUserMessage` unconditionally writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` without checking whether an entry already exists for that ID [2](#0-1) . `handleWebAPITriggerMessage`, invoked when any DON node later responds, looks up and deletes whatever callback currently occupies that key and forwards the response to it, with no verification that the responding party matches the original requester [3](#0-2) . `Message.Validate()` enforces only length and null-suffix constraints on `MessageID`, not uniqueness or sender binding [4](#0-3) . The gateway's internet-facing `ProcessRequest` validates the legacy message and forwards it straight to `HandleLegacyUserMessage` with a freshly created `Callback` for every HTTP request [7](#0-6) , so any unprivileged client can trigger this path. Notably, the sibling `RequestCache` abstraction used elsewhere in the gateway keys pending requests by `globalID{sender, id}` and explicitly rejects a duplicate `(sender, id)` pair [1](#0-0) , confirming that `MessageID`-only keying without an existence/ownership check is an insufficient safeguard that the `capabilities` handler fails to apply.

## Impact Explanation
This allows cross-user response corruption on the gateway's `web_api_trigger` legacy path: one caller's trigger-response payload can be delivered to a different, attacker-controlled HTTP connection purely via `MessageID` collision. The original caller instead times out via `callback.Wait(ctx)` in `gateway.ProcessRequest`. This maps to the in-scope "gateway request impersonation / cross-user response corruption" impact class, since sensitive trigger-response data intended for one caller is exposed to another.

## Likelihood Explanation
Likelihood is moderate: exploitation requires no privileges beyond the ability to submit two signed legacy messages with an identical `MessageID` before the first completes — a window bounded by the DON's response latency (network round trip to node(s) and back). The attacker must know or guess the victim's `MessageID` in advance (e.g. by controlling both messages, or by racing against a known/predictable value), which is plausible since `MessageID` is entirely client-chosen and only length/format checked.

## Recommendation
In `HandleLegacyUserMessage`, check whether `h.savedCallbacks[msg.Body.MessageID]` already has a live (non-expired) entry before inserting, and reject the new request with a conflict error if so, rather than silently overwriting it. Additionally, scope the cache key by `(Sender, MessageID)` similar to the `requestCache` pattern in `core/services/gateway/handlers/common/requestcache.go`, since `Message.Validate()` already derives `Body.Sender` from the signature.

## Proof of Concept
1. Attacker crafts and sends a valid signed legacy `web_api_trigger` `Message` with `MessageID = "X"` via `gateway.ProcessRequest`, which registers `savedCallbacks["X"] = callbackA` and forwards the request to all DON members.
2. Before any DON node responds, attacker sends a second signed request reusing `MessageID = "X"` (a second HTTP connection), overwriting `savedCallbacks["X"]` with `callbackB`.
3. When a DON node's `web_api_trigger` response for `MessageID = "X"` arrives, `handleWebAPITriggerMessage` retrieves and deletes `callbackB`, delivering the response over the attacker's second connection.
4. The original request from step 1 times out with `RequestTimeoutError` in `gateway.ProcessRequest`, while the attacker's connection receives the trigger-response payload intended for the first caller. A Go integration test in `core/services/gateway/handlers/capabilities/handler_test.go` can simulate two sequential `HandleLegacyUserMessage` calls with the same `MessageID` followed by one `HandleNodeMessage` response to assert which callback receives the payload.
