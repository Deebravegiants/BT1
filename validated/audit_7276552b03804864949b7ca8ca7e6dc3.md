### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never included in that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`: [2](#0-1) 

`Registry.process` checks that HMAC and, once it passes, immediately builds `WebhookMetadata` using `request.shop`, which is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop value the handler acts on == shop value cryptographically bound to the authenticated bytes`. Here, only `@raw_body` is bound to the HMAC; the `shop-domain` header is parsed but never verified. This mirrors the report's bug class exactly — "a field acted on but not covered by the HMAC" — the callback data / sub-operations were unauthenticated relative to the Merkle leaf in the smart-contract analog; here the `shop` identity is unauthenticated relative to the HMAC.

### Impact Explanation
An unprivileged holder of one legitimately-signed webhook (body + valid HMAC) for their own installed shop can replay the identical body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a different tenant. `HmacValidator.validate` still succeeds because the header is not part of the signed material, and `Registry.process` dispatches to the handler with the attacker-chosen `shop`. Any host application that uses `WebhookMetadata#shop` to select which tenant's records to read/write/query (a documented and expected usage pattern) can be tricked into attributing or applying webhook data to a shop the attacker does not own — a cross-tenant identity confusion rooted entirely in this gem's `Request`/`Registry` validation path.

### Likelihood Explanation
The attacker only needs to be an app user/merchant capable of triggering one authentic webhook to their own store (which is normal, unprivileged interaction with any installed Shopify app), then replay it with a modified header — no `api_secret_key`, access token, or privileged access is needed. This is a low-effort, protocol-level HTTP header substitution against a signature check that intentionally (per Shopify's own design) does not cover headers, but this gem exposes `request.shop` as if it were an authenticated field once `HmacValidator.validate` passes.

### Recommendation
Do not treat `request.shop` as authenticated on the strength of `HmacValidator.validate` alone. Either:
- Include the shop domain (and other identity-relevant headers) in the signable bytes checked against a value known independently by the host app (e.g., compare `request.shop` against the shop associated with the resolved webhook subscription/session before dispatch), or
- Clearly document that `WebhookMetadata#shop` is unauthenticated header data and require host applications to cross-check it against their own shop registry before using it to select tenant data.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers a real webhook (e.g. `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends the identical `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)` and it matches `H` (see `hmac_validator.rb:26-31`, `request.rb:35-38`) — validation passes.
4. `Registry.process` proceeds and calls the registered handler with `shop: "victim-shop.myshopify.com"` and body `B` (`registry.rb:188-199`), even though the request never originated from that shop.
