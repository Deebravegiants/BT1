Confirmed: `FeeVault.claim()` reads `$.creatorBalance[msg.sender]` and pays out only to `msg.sender` [1](#0-0) . There is no `claimFor`/allowlisted-rescue path for `creatorBalance`, and `Bonding.transferCreator` lets the current creator redirect all future fee attribution to any nonzero address with zero validation of that address's ability to call `claim()` itself [2](#0-1) .

### Title
Creator role/fee-attribution can be transferred to an address unable to claim, permanently freezing future `FeeVault` creator fees - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.transferCreator(tokenAddress, newCreator)` is a fully permissionless, unprivileged-caller function that lets the current token creator redirect all future creator-fee attribution (and the "official creator" identity used across the launch/fee pipeline) to any address, subject only to a non-zero check [2](#0-1) . This exactly mirrors the "staking for an unchecked receiver" bug class: like `OgvStaking.stake(amount, duration, to)`, which let a stake be attributed to a `to` address that might be unable to call `unstake`, `transferCreator` lets fee accrual be attributed to a `newCreator` that may be structurally unable to call `FeeVault.claim()` on its own behalf.

### Finding Description
Every buy/sell in `Zap` accrues a creator-fee share keyed by `Bonding.creatorOf(tokenAddress)`, which resolves to `tokenInfo[token].creator` [3](#0-2) . `Zap._accrueFee` transfers the fee USDC to `FeeVault` and calls `FeeVault.accrue(token, creator, creatorShare, protocolShare, isBuy)`, which credits `$.creatorBalance[creator] += creatorAmount` [4](#0-3) .

The only way to withdraw that balance is `FeeVault.claim()`, which pays out strictly to `msg.sender`:
```solidity
function claim() external nonReentrant returns (uint256 amount) {
    amount = $.creatorBalance[msg.sender];
    ...
    $.usdc.safeTransfer(msg.sender, amount);
}
``` [1](#0-0) 

There is no `claimFor(address creator)`, no allowlisted rescue, and no owner-controlled sweep for a stuck `creatorBalance[x]` entry — the vault only exposes `claim()` (self-only) and `claimProtocol()`/`sweepDonations()` which are unrelated to per-creator balances.

`Bonding.transferCreator` is the sole mechanism that changes the address future fees accrue to, and it performs no validation that `newCreator` is capable of calling `claim()`:
```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
``` [2](#0-1) 

Any unprivileged token creator can call this with `newCreator` set to:
- a contract with no owner-controlled arbitrary-call/proxy capability (e.g., a simple vault, escrow, or vesting contract that has no function letting anyone trigger an arbitrary external call as itself), or
- any address whose private key is permanently unrecoverable/unknown to the creator (mistaken paste, a burn-style address that isn't literally `0x0`, a CREATE2 address not yet deployed, etc.).

Once `transferCreator` executes, every subsequent buy/sell fee split on that token accrues into `creatorBalance[newCreator]` in `FeeVault`. If `newCreator` can never itself originate a transaction calling `claim()`, that balance is permanently locked — it can never be withdrawn, and it is also not counted by `sweepDonations` (which only mops up USDC balance in excess of `totalAccruedCreator + protocolBalance`, i.e. it explicitly treats a stuck `creatorBalance` entry as "backed", not sweepable) [5](#0-4) .

This is the direct analog of the external report: like `OgvStaking.stake(amount, duration, to)` attributing a stake to a `to` that can't call `unstake`, `transferCreator` attributes ongoing fee-earning rights to a `newCreator` that can't call `claim()`, permanently freezing those funds inside `FeeVault`.

### Impact Explanation
This causes a permanent, unrecoverable freeze of protocol funds: every future 0.25% creator-fee share on all buys/sells of that token accrues to an address that can never call `claim()` to retrieve it. Because `FeeVault.accrue`'s underfund check (`usdc.balanceOf(this) >= totalAccruedCreator + protocolBalance`) treats this balance as legitimately owed [6](#0-5) , the USDC is neither claimable by anyone nor sweepable as a donation — it is permanently locked, growing with every trade on the token for its remaining lifetime.

### Likelihood Explanation
Reachable by a single unprivileged transaction from the current creator — no special role, upgrade, or off-chain step required. It can happen either by a genuine user mistake (typo/paste error, sending to an unintended contract) or could be exploited maliciously by a creator wanting to permanently "burn" future fee rights while still collecting the seed-buy/trading activity, or as a griefing vector against the protocol's own fee accounting invariants.

### Recommendation
Add a validation step before committing `newCreator` in `Bonding.transferCreator`, e.g., require the new creator to accept the role via a two-step handoff (`proposeCreator` + `acceptCreator` called by `newCreator` itself), which naturally proves the address can originate transactions. Alternatively, add a `FeeVault.claimFor(address creator, address to)` guarded by an allowlist/owner path so stuck balances can be rescued to a verified address, analogous to fixing the `OgvStaking` report by separating `stake`/`stakeFor` and verifying the receiver can operate on the funds.

### Proof of Concept
1. Creator launches a token via `zap.createToken(...)`, becoming `tokenInfo[token].creator` [7](#0-6) .
2. Creator calls `bonding.transferCreator(token, badReceiver)` where `badReceiver` is a freshly deployed minimal contract with no functions that let it originate a `claim()` call (or simply an address whose key is lost) [2](#0-1) .
3. Any trader calls `zap.buy(token, usdcAmount, 0, address(0))`; `_buyInternal` accrues the creator share to `creatorOf(token) == badReceiver` via `FeeVault.accrue` [8](#0-7) .
4. `FeeVault.creatorBalance[badReceiver]` now holds real USDC that grows with every subsequent trade; no address can ever call `FeeVault.claim()` as `badReceiver` to retrieve it, and `sweepDonations` will not touch it since it is counted in `totalAccruedCreator` [1](#0-0) .
