### Title
`ShopifyAPI::Webhooks::Registry.process` never validates the `shop` domain and HMAC signing excludes the `shop-domain` header, enabling forged cross-tenant webhook shop identity - (`lib/shopify_api/webhooks/registry.rb`)

### Summary
`Registry.process` verifies only that the raw body's HMAC matches, then hands `request.shop` — taken verbatim from the attacker-controlled `x-shopify-shop-domain`/`shopify-shop-domain` header — straight into `WebhookMetadata#shop` with no call to `Utils::ShopValidator` anywhere in the path. Because `Request#to_signable_string` returns only `@raw_body`, the HMAC signature never binds to the `shop`, `topic`, `webhook-id`, or `api-version` headers, so any request with a genuinely-signed body (which the attacker can obtain by receiving their own real webhook) can have its `shop-domain` header swapped for an arbitrary value and still pass `Registry.process`.

### Finding Description
The broken binding: `WebhookMetadata#shop` (value handed to the host app's tenant lookup) is claimed to equal "a value `ShopValidator` has accepted, and equal to the shop the HMAC was actually issued for." Neither holds.

- `Registry.process` code path: [1](#0-0) . It calls `Utils::HmacValidator.validate(request)` and, if it passes, constructs `WebhookMetadata.new(... shop: request.shop ...)`. There is no call to `Utils::ShopValidator` anywhere in this method or in `WebhookMetadata`/`WebhookHandler`: [2](#0-1) .
- `request.shop` is read directly from the header with no format check: [3](#0-2) .
- Root cause of the exploitability: the HMAC signable string is the raw body only, not headers: [4](#0-3) , and `HmacValidator.validate_signature` computes/compares the signature purely from `to_signable_string`: [5](#0-4) . So `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never covered by the signature.

Attacker's exact request: The attacker creates their own development shop, installs the app, and registers a webhook to their own controlled endpoint. Shopify sends a genuinely HMAC-signed webhook (signed with the real `api_secret_key`) for the attacker's own shop and body. The attacker then replays this exact `raw_body` + `hmac-sha256` header value to the victim host app's webhook endpoint, but substitutes the `x-shopify-shop-domain` header with an arbitrary string (a different real merchant's domain, or any non-Shopify string). `HmacValidator.validate` still succeeds because it never looked at the `shop-domain` header, and `ShopValidator` is never invoked to check the header is a legitimate `*.myshopify.com`/trusted domain. `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker's chosen string, which many host apps use as a raw tenant key (e.g., `Shop.find_by(shopify_domain: data.shop)`).

Existing guards analyzed and found insufficient: `HmacValidator.validate` only proves the body originated from an entity possessing `api_secret_key` for *some* shop's webhook, not that the accompanying `shop` header is truthful — it is unscoped to headers. `ShopValidator.sanitize!`/`sanitize_shop_domain` exist in the codebase (used by OAuth/token exchange/client-credentials flows: [6](#0-5) [7](#0-6) ) but are never invoked from `Registry.process`. Sorbet `sig`s only constrain that `shop` is a `String`, not its shape or trust.

### Impact Explanation
A host app relying on this gem's webhook processing to route data or invalidate/mutate per-tenant state by trusting `WebhookMetadata#shop` (as documented in `docs/usage/webhooks.md`) can be made to associate an attacker-controlled body with an arbitrary victim shop identifier. This is repeatable at will — the attacker only needs one legitimately-signed payload from their own store (freely obtainable by installing the app on their own dev shop) and can then replay it against any target shop string indefinitely, since the signature never expires or binds to shop/topic. Depending on the handler's use of `data.shop` (e.g., writing order/webhook data keyed by shop, triggering per-tenant side effects, or shop-scoped cache invalidation), this constitutes cross-tenant data confusion/injection — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are low-cost and fully within the unprivileged attacker's described capabilities: create a free development shop, install the target app (or any app using this gem in the same way), receive one real signed webhook, then replay it with a modified `shop-domain` header directly to the app's public webhook endpoint. No secrets, no privileged access, and no interaction with the victim's shop are required. This is trivially repeatable against arbitrary "victim" shop strings.

### Recommendation
In `Utils::HmacValidator`/`Webhooks::Request`, include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the signable string used for HMAC validation, or otherwise cryptographically bind the header to the signed body. Additionally, in `Registry.process`, validate `request.shop` with `Utils::ShopValidator.sanitize!` (optionally against the session/shop already on file for that installation) before constructing `WebhookMetadata`, rejecting requests whose `shop` value isn't a trusted Shopify domain.

### Proof of Concept
minitest (extending `test/webhooks/registry_test.rb`) using the existing `@headers`/`@webhook_request` fixtures:

```ruby
def test_process_accepts_hmac_valid_but_arbitrary_shop_domain
  handler_called = false
  captured_shop = nil

  handler = TestHelpers::FakeWebhookHandler.new(
    lambda do |data|
      captured_shop = data.shop
      handler_called = true
    end,
  )

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: @topic, path: "path", delivery_method: :http, handler: handler,
  )

  # Same raw_body + same valid HMAC as @headers (signed only over "{}"),
  # but shop-domain header swapped to an arbitrary, non-Shopify string.
  forged_headers = @headers.merge("x-shopify-shop-domain" => "not-a-real-shop.attacker.example")
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)

  # Registry.process must not raise, proving no ShopValidator check occurs.
  ShopifyAPI::Webhooks::Registry.process(forged_request)

  assert(handler_called)
  # WebhookMetadata#shop equals the attacker string, not a value ShopValidator would ever accept.
  assert_equal("not-a-real-shop.attacker.example", captured_shop)
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Utils::ShopValidator.sanitize!(captured_shop)
  end
end
```

This demonstrates the equality breaks: `WebhookMetadata#shop` ("not-a-real-shop.attacker.example") ≠ any value `ShopValidator.sanitize!` would ever accept, yet `Registry.process` succeeds because the HMAC only signs `raw_body`.
