### Title
Webhook `shop` domain is trusted from an unauthenticated header, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator`, but the HMAC signature only covers the raw request body. The `shop` value that the gem hands to the application's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed payload, so it can be set to any value by anyone controlling the request headers, even when the HMAC over the body is valid (e.g. replaying a captured, validly-signed webhook body with a substituted shop-domain header).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: `lib/shopify_api/webhooks/request.rb:35-38`. [1](#0-0) 

`Request#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of `to_signable_string` and is therefore not bound by the HMAC at all: `lib/shopify_api/webhooks/request.rb:20-23`. [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` — i.e. it verifies the body bytes were signed by Shopify, it says nothing about which shop the header claims to be from: `lib/shopify_api/utils/hmac_validator.rb:12-22`. [3](#0-2) 

This is the same bug class as the `AssetLock.sol` report: a field (`lockEndTime` / here, `shop`) is acted upon by the security-critical logic without being covered by the binding mechanism that is supposed to guarantee its integrity (the recomputed max-of-durations check / here, the HMAC signature). The broken equality is: `shop_claimed_in_header == shop_that_actually_produced_the_signed_body` — this equality is never checked; only `hmac == HMAC(body, secret)` is checked, and `shop` is outside that signed scope.

### Impact Explanation
If an app's webhook controller uses `request.shop` (as returned by this gem) to select the merchant/session to act on — the intended and documented purpose of this field per `lib/shopify_api/webhooks/registry.rb` dispatch logic — an attacker who can replay or forward a validly-HMAC-signed webhook body (for instance, one they legitimately received for their own shop, or one intercepted from a public/log source) can rewrite only the `shop-domain` header and have the HMAC check still pass, while the app processes the payload under a different (victim) shop's identity. This can lead to cross-tenant data corruption or actions being taken against the wrong merchant's session/store, since the shop identity used for dispatch/authorization is not authenticated together with the body.

### Likelihood Explanation
Exploitability depends on the host application's webhook endpoint being reachable by an unprivileged internet user (webhook endpoints are typically public HTTP endpoints with no additional network-level protection) and on the app using `request.shop` from this gem to select tenant context, which is exactly what the gem's `Registry` dispatch is designed to encourage. No access token, `client_secret`, or other privileged secret is required by the attacker — only the ability to submit an HTTP request with attacker-controlled headers and a previously-observed valid signed body.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind the header-derived shop domain to the signed body, so `HmacValidator.validate` fails if the shop header is altered relative to the body that was actually signed by Shopify.

### Proof of Concept
1. Attacker legitimately receives (or captures) a valid webhook delivery for `attacker-shop.myshopify.com`, consisting of `raw_body` and its `X-Shopify-Hmac-Sha256` header — this HMAC validates because it is a genuine signature over that body.
2. Attacker resends the identical `raw_body`/HMAC pair to the same endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
3. In `ShopifyAPI::Webhooks::Request.new`, `@raw_body` is stored and `shop` is computed purely from the (attacker-controlled) header: `lib/shopify_api/webhooks/request.rb:20-23,45-63`.
4. `Utils::HmacValidator.validate(request)` calls `to_signable_string`, which returns only `@raw_body` — unaffected by the header change — so `OpenSSL.secure_compare(computed_signature, received_signature)` still succeeds: `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. The app's webhook handler, trusting `request.shop == "victim-shop.myshopify.com"` because the HMAC check "passed", processes the attacker's payload as if it came from the victim's shop. [4](#0-3) [5](#0-4)

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
