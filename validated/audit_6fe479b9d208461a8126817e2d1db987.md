## Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw HTTP body, while the `shop` (tenant identity) it hands to the app's webhook handler is read from an unauthenticated HTTP header. This breaks the intended binding `hmac_signed_bytes == bytes_used_for_tenant_attribution`, allowing a captured, validly-signed webhook payload from one shop to be replayed with a different `shop-domain` header and be accepted as authentic for another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Webhooks::Registry.process` calls this same validation and then unconditionally forwards `request.shop` (the unauthenticated header) as the tenant identity to the app's handler: [4](#0-3) 

Because the api_secret_key is shared across all shops that install a given app, and the HMAC only binds the JSON body, any body value that is (or becomes) valid for one installation's webhook remains HMAC-valid regardless of which `shop-domain` header accompanies it. An attacker who controls one tenant (their own shop installing the same app) can capture a legitimately-signed webhook body/HMAC pair delivered by Shopify to their own endpoint, then resend that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop that also installed the app. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will dispatch the payload to the handler labeled with the victim's shop domain — the equality the code implicitly assumes, `hmac-verified body == body attributable to header shop`, does not hold.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: the `shop` value passed to `WebhookMetadata`/handler is the basis apps use to key their per-tenant data (e.g., "which shop's order/customer record to update"). Forging that binding lets an attacker who controls one tenant on a shared app cause the app to process (and potentially persist or act on) data under another tenant's identity — cross-tenant data confusion/injection through the webhook channel, without needing the app's `api_secret_key`, access token, or any privileged account.

### Likelihood Explanation
Exploitability requires only:
1. The attacker owns/controls a shop that installs the same third-party app (trivial, e.g. a free/dev store).
2. The attacker can intercept or predict a raw webhook body they legitimately receive from Shopify for their own shop (bodies for many topics are attacker-influenced, e.g. `customers/create`, `orders/create`, since the attacker controls the shop's own data).
3. The attacker replays that captured body+HMAC to the app's public webhook endpoint with a different `shop-domain` header.

No cryptographic secret, credential leakage, or social engineering is needed — only standard, unprivileged interaction with the app as an installing merchant, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and other identity-relevant fields like `topic`/`webhook_id`) into the HMAC-verified surface, or otherwise cryptographically verify that the header-provided shop matches the shop the webhook was actually delivered for (e.g., cross-check against the topic/shop registered for that webhook subscription, or validate the header against a per-shop secret/session rather than trusting it outright). At minimum, document that `request.shop` is unauthenticated and must not be used by host apps as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and installs the target app; they configure a webhook subscription for a topic where the JSON body content is attacker-influenced (e.g. `customers/create` with attacker-controlled customer fields).
2. Shopify delivers a webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw body computed with app's api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - raw body: `{"id":1,"email":"attacker@evil.com", ...}`
3. Attacker intercepts this request (their own traffic) and resends it to the same app endpoint, unmodified except:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes HMAC over `@raw_body` only — matches, so `Registry.process` proceeds:
```ruby
# lib/shopify_api/webhooks/registry.rb
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The handler receives `shop == "victim-shop.myshopify.com"` together with attacker-controlled body content, believing this is authentic data from `victim-shop`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end
