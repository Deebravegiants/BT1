### Title
`describeWithdrawal` misreports status/txHash when two withdrawals share the same `assetId` in one batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`findMatchingWithdrawal` matches a withdrawal from the POA bridge API response purely by `assetId`, ignoring `WithdrawalIdentifier.index`/amount. When a NEAR intent contains two POA-bridge withdrawals of the same `assetId`, `describeWithdrawal` for index 0 and index 1 both resolve to the first array entry returned by `Array.prototype.find`, so both withdrawals report the same `(status, txHash)` even though they are distinct withdrawals with distinct outcomes.

### Finding Description
The claimed invariant is: for withdrawal `i`, `describeWithdrawal({..., index: i})` should report `(status_i, txHash_i)` equal to withdrawal `i`'s actual on-chain outcome, and this should differ from withdrawal `j`'s outcome when `i != j`.

Code path:
- `describeWithdrawal` calls `getWithdrawalStatusWithRetry` (keyed only by `args.tx.hash`, the NEAR tx hash, which is shared by all withdrawals in the same intent) and then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`. [1](#0-0) 
- `findMatchingWithdrawal` uses `Array.prototype.find` and returns the **first** withdrawal whose `near_token_id` maps to the requested `assetId` — it does not use `index` at all: [2](#0-1) 
- The code's own comment explicitly documents this: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."

Batch withdrawals with duplicate `assetId` are a normal, attacker-reachable input: `createWithdrawalIdentifiers` in `withdrawal-watcher.ts` assigns a **per-bridge-route** running index (`indexes.get(bridge.route)`), not a per-`assetId` index, so two POA withdrawals of the same token in one intent legitimately get `index: 0` and `index: 1`: [3](#0-2) 

An ordinary user (or a counterparty whose withdrawal params an integrator forwards) can construct a NEAR intent transaction containing two withdrawal legs of the same `nep141:...omft.near` asset (e.g., "USDC to address A" + "USDC to address B", or a duplicate-refund pattern). Both legs share the same `tx.hash`. When the integrator later calls `bridge.describeWithdrawal` once for `index: 0` and once for `index: 1`, both calls hit the POA bridge status API with the same `withdrawal_hash`, get back a `withdrawals` array with (at least) two entries for that `assetId`, and `findMatchingWithdrawal` returns the same (first-matching) entry for both calls — regardless of which entry actually corresponds to index 0 vs index 1.

None of the existing guards prevent this: `supports()`, `validateWithdrawal()`, `compareAddresses`, and `FeeExceedsAmountError` operate on a single withdrawal's parameters at creation time and have no visibility into sibling withdrawals in the same batch; they do not enforce uniqueness of `assetId` within a batch, and there is no dedup/ordering check between `createWithdrawalIdentifiers` and `describeWithdrawal`.

### Impact Explanation
An integrator that tracks two same-asset withdrawals from one NEAR intent via `PoaBridge.describeWithdrawal` (directly, or through `watchWithdrawal`/`createWithdrawalCompletionPromises`) will receive identical `(status, txHash)` for both indices once the API reports any completed entry for that asset. This can cause the integrator to credit/settle both logical withdrawals against a single actual on-chain transfer (double credit) while the second, genuinely different withdrawal remains unaccounted for — a status/hash misreport that leads to crediting twice, matching the "High" impact category (status misreport causing double credit).

### Likelihood Explanation
Preconditions: the batch intent must contain ≥2 POA-bridge withdrawal legs with the same `assetId` (attacker/integrator-controlled `withdrawalParams` list) submitted in one NEAR transaction. Cost to the attacker/counterparty is trivial — just construct such a batch (no fee, no privileged access, nothing beyond normal intent construction). It is fully repeatable per affected batch and is explicitly acknowledged as unsupported/broken in the source comment, confirming no other layer in this repo compensates for it.

### Recommendation
Do not resolve withdrawal status purely by `assetId`. At minimum, detect duplicate `assetId` withdrawals within `createWithdrawalIdentifiers`/batch construction and either reject such batches for POA bridge, or extend `findMatchingWithdrawal` to disambiguate using amount ordering (as the code comment itself suggests: sort API results and local withdrawal params by amount, since relayer fees are equal for the same token) combined with `index`, so each `WithdrawalIdentifier.index` maps deterministically to a distinct API entry.

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
