## Title
Challenge period is read live at message-handling time instead of being locked in when the state commitment was stored, letting the fisherman veto window shrink retroactively - (`File: evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2` computes the elapsed delay for a state commitment as `block.timestamp - host.stateMachineCommitmentUpdateTime(height)` and compares it against `host.challengePeriod()` — the **current, live** value of the challenge-period parameter — rather than the challenge period that was configured at the moment the commitment was stored. This is the same root cause as the `quitPeriod` finding in the referenced report: a "wait period" is supposed to give watchers (fishermen) time to react to a pending state, but the duration applied is re-read dynamically at consumption time instead of being fixed when the timer started. If the protocol's `challengePeriod` is ever reduced through a normal `updateHostParams` governance call while a state commitment is mid-flight, that commitment's remaining veto window shrinks immediately and retroactively, letting a relayer deliver messages anchored to it earlier than fishermen were promised.

### Finding Description
`EvmHost.sol` stores the challenge period as a single mutable field in `HostParams`, changeable only through `updateHostParams` / `updateHostParamsInternal`: [1](#0-0) 

The consumer-side check in `HandlerV2.sol` never snapshots the challenge period that applied when a given `StateMachineHeight` commitment was written; it always re-reads the parameter that is live at the time the message is finally handled: [2](#0-1) 

The identical live-read pattern is repeated for `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts`: [3](#0-2) [4](#0-3) [5](#0-4) 

Only a timestamp is persisted per state-machine height — the duration itself is never captured: [6](#0-5) 

The equivalent Rust ISMP core has the same structure — `verify_delay_passed` looks up `host.challenge_period(proof_height.id)` fresh, rather than the value locked at `state_machine_update_time`: [7](#0-6) 

Concretely: suppose the challenge period is `T1` when a relayer submits a consensus proof that produces a new (possibly malicious or simply premature) state-machine commitment via `handleConsensus`/`storeStateMachineCommitment`. Fishermen are expected to have the full `T1` window to call `veto`/detect fraud before any message anchored to that height can be delivered. If, before `T1` elapses, Hyperbridge governance issues a routine `updateHostParams` request through `hostManager` that lowers `challengePeriod` to `T2 < T1` (e.g., to speed up finality for a chain governance judges to be safe), every commitment already in-flight — including the one just submitted — instantly satisfies the shorter `T2` requirement the moment `block.timestamp - updateTime >= T2`. Any unprivileged relayer can then immediately call `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` to deliver messages anchored to that commitment, even though fishermen were promised the original `T1` window and have not had that full time to veto it.

### Impact Explanation
This breaks the safety guarantee the challenge period is designed to provide: a guaranteed window during which a fraudulent or premature state commitment can be vetoed before any cross-chain message that depends on it is finalized. Because the duration is not locked to the commitment at storage time, an ordinary parameter tuning event on Hyperbridge can retroactively cut short the veto window for commitments already in flight, allowing an unprivileged relayer to force through `handlePostRequests`/`handleGetResponses`/timeout deliveries before fishermen have had their promised time to react — i.e., unsound state commitment reliance leading to forged/premature message delivery, which can move funds or execute app logic (e.g., `IntentGateway`/`HostManager` actions) based on a state that had not actually cleared its intended review window.

### Likelihood Explanation
No malicious admin action is required — the exploit condition is simply that `challengePeriod` is ever reduced via a legitimate `updateHostParams` call while any state commitment stored under the old, larger period has not yet fully cleared it. Governance parameter tuning (raising/lowering `challengePeriod` to reflect confidence in a client, as the `HostParams` struct explicitly supports) is an expected, routine operation, not an edge case, and the exploiting party (a relayer calling `handlePostRequests` etc.) needs no special privilege — it is exactly the actor path this analysis is scoped to check.

### Recommendation
Snapshot the challenge period alongside the state-machine/consensus update timestamp at the moment the commitment is stored (e.g., extend `_stateCommitmentsUpdateTime`/`storeStateMachineCommitment` and the equivalent Rust `store_state_machine_update_time` to also persist the `challengePeriod` value active at that height), and have `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`, and `verify_delay_passed` compare against that stored value rather than re-reading the live `host.challengePeriod()`/`host.challenge_period(...)`. This mirrors the report's recommended fix of applying the duration at proposal time rather than at execution time.

### Proof of Concept
1. Host is configured with `challengePeriod = T1` (e.g. 1 hour).
2. A relayer submits `handleConsensus`, which via `IConsensusV2.verify` produces an `IntermediateState` and stores a new `StateMachineHeight` commitment through `storeStateMachineCommitment`, recording `_stateCommitmentsUpdateTime[stateMachineId][height] = block.timestamp` (see `evm/src/core/HandlerV2.sol:151-164` and `evm/src/core/EvmHost.sol:687-690`).
3. Before `T1` elapses, Hyperbridge governance dispatches a routine `updateHostParams` request (via `hostManager`) that sets `challengePeriod = T2`, with `T2 < T1` (`evm/src/core/EvmHost.sol:573-636`).
4. Once `block.timestamp - _stateCommitmentsUpdateTime[...] >= T2` (but still `< T1`), any relayer calls `handlePostRequests` (or `handleGetResponses`/timeout handlers) for a request proven against that height. The check `challengePeriod > delay` at `evm/src/core/HandlerV2.sol:184-185` now passes using the new `T2`, even though fishermen were only guaranteed `T1` seconds to veto the commitment when it was stored.
5. The message is delivered, potentially before fishermen have finished evaluating/vetoing the underlying state commitment.

```rust
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
```
