## Analysis: CVE-2020-26033 (Zammad CSRF on Tag/Link REST endpoints) — Analog Check

### Title
Missing CSRF protection on session-cookie-authenticated state-changing REST endpoints - (File: core/web/router.go)

### Summary
Zammad's flaw was that state-changing REST endpoints authenticated by session were reachable without a CSRF token check. Chainlink's node web API has an analogous pattern: many `POST`/`DELETE`/`PATCH` endpoints accept session-cookie authentication (`auth.AuthenticateBySession`) as one of their valid auth methods, and the router pipeline contains no CSRF token validation middleware anywhere in the request chain.

### Finding Description
The core router wires global middleware — logging, `gin.Recovery()`, CORS, `secureMiddleware`, `helmet.Default()`, and rate limiting — but never includes any CSRF-token verification step. [1](#0-0) 

Session authentication is implemented purely via a signed session cookie lookup with no origin/token binding check: [2](#0-1) 

`Authenticate` accepts the first successful method among the ones supplied, and for most `authv2` state-changing routes the accepted methods are `AuthenticateByToken` OR `AuthenticateBySession`: [3](#0-2) 

This means a state-changing request (e.g. `POST /v2/external_initiators`, `DELETE /v2/external_initiators/:Name`, `POST /v2/bridge_types`, `DELETE /v2/bridge_types/:BridgeName`, `POST /v2/jobs`, `DELETE /v2/jobs/:ID`, key create/delete endpoints, etc.) succeeds purely on the presence of a valid session cookie — no anti-CSRF token is required in the request body/header: [4](#0-3) [5](#0-4) 

The CORS handler used for the UI explicitly allows credentials to be sent cross-origin (which is a separate, and slightly widening, issue), but note that a classic CSRF attack (a plain cross-site form POST) does not even require CORS to succeed — the browser will attach the session cookie regardless of CORS headers: [6](#0-5) 

### Impact Explanation
If an authenticated operator/admin visits an attacker-controlled page while their Chainlink Operator UI session cookie is valid, the attacker can forge a cross-site request (e.g. an auto-submitting HTML form) to endpoints like `POST /v2/external_initiators`, `DELETE /v2/jobs/:ID`, `POST /v2/bridge_types`, or key-management endpoints, causing state changes (job deletion, bridge/external-initiator creation, etc.) under the victim's identity without their knowledge — this is the same "request impersonation" class as the Zammad Tag/Link CSRF issue. This impact is not the "no state-modifying impact" case excluded from the security policy; job/bridge/external-initiator/key resources are genuine state-modifying assets.

### Likelihood Explanation
Exploitability depends on whether the session cookie is set with a strict `SameSite` attribute, which would meaningfully mitigate classic CSRF. I located a `SameSite`/cookie configuration reference in `core/services/chainlink/config_web_server.go` and `core/web/router.go`, but was unable to confirm the exact value/default configured for `SessionOptions()` within my available inspection depth — I could not verify whether `SameSite=Strict/Lax` is enforced by default or configurable by the operator. [7](#0-6) 

Given this uncertainty, I cannot conclusively confirm exploitability without knowing the actual `SameSite` cookie policy in effect. If `SameSite=Lax` or stricter is the default (which is standard in modern `gin-contrib/sessions/cookie` usage), the practical CSRF risk for `POST`/`DELETE` (non-navigational) requests would be substantially mitigated, similar to how modern browsers already blunt classic CSRF for many endpoints even without an app-level CSRF token.

### Recommendation
Confirm and enforce a strict `SameSite=Strict` (or at minimum `Lax`) attribute on the session cookie in `SessionOptions()`, and/or add an explicit CSRF token check (e.g. double-submit cookie or synchronizer token pattern) as router middleware for all `authv2` routes that accept `AuthenticateBySession`, particularly state-changing ones (`POST`, `PATCH`, `DELETE`).

// Add CORS headers so UI can make api requests
func uiCorsHandler(ao string) gin.HandlerFunc {
	c := cors.Config{
		AllowMethods:     []string{"GET", "POST", "PATCH", "DELETE"},
		AllowHeaders:     []string{"Origin", "Content-Type", "Accept"},
		ExposeHeaders:    []string{"Content-Length"},
		AllowCredentials: true,
		MaxAge:           math.MaxInt32,
	}
	if ao == "*" {
		c.AllowAllOrigins = true
	} else if allowOrigins := strings.Split(ao, ","); len(allowOrigins) > 0 {
		c.AllowOrigins = allowOrigins
	}
	return cors.New(c)
}

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
