Given the evidence gathered, `dispatchIncoming` in `EvmHost.sol` uses a low-level `.call` and swallows failures (deleting the receipt so the message can be retried) rather than reverting the whole batch, so the exact "batch DoS on revert" analog from the report doesn't reproduce there. The stronger, valid analog is in `WrappedHyperFungibleToken.onAccept` / `onPostRequestTimeout`, where a fixed-amount `IERC20(_underlying).safeTransfer` is not guarded by a balance check, mirroring the Vault bug exactly.

### Title
Insufficient-balance `safeTransfer` in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` causes indefinite delivery/timeout-refund failure - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.onAccept` and `.onPostRequestTimeout` (and their upgradeable counterpart) unconditionally call `IERC20(_underlying).safeTransfer(beneficiary/refundee, message.amount)` (or the WETH unwrap-then-transfer fallback) without first checking that the contract actually holds `message.amount` of the underlying token. This is the same root cause as the reported Vault issue: an ERC20 `transfer`/`safeTransfer` call reverts when the contract's balance is insufficient, and there is no balance check or fallback event before attempting it.

### Finding Description
`send()` locks the underlying token or ETH-as-WETH from the caller and dispatches a `PostRequest` cross-chain [1](#0-0) . On the destination, `onAccept` is invoked by the host via `EvmHost.dispatchIncoming`, which decodes the message and performs the token transfer to the beneficiary: for WETH it first attempts a native push, and falls back to `IWETH.deposit` + `IERC20.safeTransfer`; for non-WETH it directly calls `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` with no balance check [2](#0-1) . The same unguarded pattern exists in `onPostRequestTimeout`, which refunds the original sender the same way [3](#0-2) , and is duplicated verbatim in the upgradeable variant [4](#0-3) .

Because `onAccept`/`onPostRequestTimeout` are called from `EvmHost.dispatchIncoming` / `dispatchTimeOut` via a raw `.call`, a revert inside the app callback does not directly crash the host, but it does mean the app-level side effect ("deliver funds to the beneficiary" or "refund the payer") never completes and must be retried indefinitely, exactly mirroring the reported Vault DoS: the funds transfer keeps failing until the underlying balance is restored, with no graceful degradation, partial-transfer, or explicit accounting/event indicating the shortfall to the beneficiary/relayer.

If underlying-token balance ever falls short of what a single delivered/timed-out message requires (e.g. due to accounting drift across multiple in-flight cross-chain sends, rounding, fee-on-transfer tokens, or any other imbalance between locked supply and actual token holdings), the specific beneficiary's mint/unlock is permanently stuck in a revert loop for that message, and for timeouts the relayer-fee refund logic on the host side (`EvmHost.dispatchTimeOut`, `PostRequestTimeout`) is likewise never reached because `onPostRequestTimeout` never returns success. [5](#0-4) 

### Impact Explanation
This is a Medium-severity denial-of-service on the token-bridge app layer: an affected beneficiary can be permanently unable to receive their bridged tokens, and an affected sender's relayer-fee refund is permanently blocked, for as long as the underlying-token balance shortfall persists. Since `WrappedHyperFungibleToken` is a generic ERC20-wrapping bridge app meant to be deployed for arbitrary underlying tokens, this could also cause a stuck queue of retries competing for the same insufficient balance, effectively freezing legitimate transfers dependent on it.

### Likelihood Explanation
Likelihood is Medium: it requires an underlying-balance shortfall relative to outstanding wrapped-supply obligations, which can arise from any accounting mismatch (fee-on-transfer tokens, rounding, or a burn/mint desync between chains) rather than attacker-controlled state directly, but no privileged action is needed to trigger the stuck state once the shortfall exists — any subsequent relay of `onAccept`/`onPostRequestTimeout` for an amount exceeding the available balance will revert.

### Recommendation
Before calling `IERC20(_underlying).safeTransfer` (or the WETH withdraw/deposit fallback) in `onAccept` and `onPostRequestTimeout`, check `IERC20(_underlying).balanceOf(address(this))` (or use a try/catch) and, if insufficient, record the amount as claimable/pending and emit an event instead of letting the call revert, so that funds are not indefinitely stuck and the retry loop is avoided.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` wrapping a fee-on-transfer or otherwise balance-imprecise ERC20, or simulate a scenario where the contract's underlying balance is less than the sum of outstanding `send()` locks (e.g., due to a prior partial/side-effect failure elsewhere in the system).
2. Have a user call `send()` locking `amount` of underlying tokens; on the destination chain relay the corresponding `PostRequest` so `onAccept` attempts `IERC20(_underlying).safeTransfer(beneficiary, amount)` while `IERC20(_underlying).balanceOf(address(this)) < amount`.
3. Observe `onAccept` reverts; `EvmHost.dispatchIncoming` catches the low-level call failure and deletes the receipt, allowing indefinite retries, but the transfer keeps failing until balance is restored — beneficiary never receives funds. Analogous behavior applies to `onPostRequestTimeout` blocking the relayer-fee refund path in `EvmHost.dispatchTimeOut`.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {

            // if the recipient cannot accept native value (no `receive()` / `fallback()

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
