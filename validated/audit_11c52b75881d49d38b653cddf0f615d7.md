### Title
Webhook `shop` (tenant) identifier is trusted despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, then hands the handler a `shop` value read from the unauthenticated `X-Shopify-Shop-Domain` header. Because the shop identifier is never part of the signed payload, an attacker who can obtain any one valid `(raw_body, hmac)` pair signed by the app's shared `client_secret` can replay that pair while substituting an arbitrary victim `shop` header, causing the app to process attacker-controlled webhook data under a victim tenant's identity.

### Finding Description
The equality the code should enforce but does not is:

`bytes verified by HMAC == bytes/identity acted on by the handler`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's `WebhookHandler`: [4](#0-3) 

Shopify's shared HMAC key for webhooks is the app's `client_secret`, which is identical for every shop that has the app installed — it is not per-tenant. Consequently:
- Before the attack: for shop A's own legitimate webhook, `(raw_body_A, hmac_A)` is valid, and `shop == A`.
- After the attack: the attacker resends `(raw_body_A, hmac_A)` to the app's webhook endpoint but sets the `X-Shopify-Shop-Domain` header to victim shop `B`. `HmacValidator.validate` still returns `true` (it never looked at the shop header), yet `Registry.process` calls the handler with `shop: "B"` while the body is really `A`'s.

The documented usage pattern in `docs/usage/webhooks.md` explicitly relies on `data.shop` to key tenant-specific side effects (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this binding failure propagates directly into host applications built per this gem's own documented contract.

### Impact Explanation
This crosses a tenant boundary using only the gem's own webhook-processing API: an unprivileged user of the app (someone with a store where the target app is installed, or anyone able to observe/replay one legitimate webhook delivery for that app) can make the host application process arbitrary attacker-controlled webhook bodies (e.g. `app/uninstalled`, `customers/data_request`, `orders/create`) as if they originated from an arbitrary victim shop, since only the shop domain header — not the body-shop binding — is forged. Depending on how the host wires `WebhookMetadata#shop` into session/token lookup or data writes, this can trigger cross-tenant state corruption (e.g., falsely marking a victim shop's app as uninstalled, or writing attacker payload data into a victim shop's records), qualifying as Critical cross-tenant access.

### Likelihood Explanation
No secret or privileged access is required beyond having previously received any single legitimate webhook (readily available to any developer/merchant who installs the app on their own store, since HMAC is app-wide, not shop-specific). No TLS interception, credential theft, or code execution capability is needed — only the ability to POST to the app's public webhook endpoint with a modified header, which is exactly the interface `docs/usage/webhooks.md` instructs host apps to expose.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the shop-domain header to the payload before trusting it (e.g., require the host app to independently confirm that the reported `shop` has an active session/webhook subscription matching the delivered `webhook-id`/`topic`, and treat the header purely as a lookup key rather than an authenticated fact). At minimum, `Request#to_signable_string` should not be documented/relied upon as proof that `shop` is authentic, and `Registry.process`/`WebhookMetadata` should not forward `request.shop` as a trusted tenant identity without additional verification.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook delivery from Shopify:
#   headers: { "X-Shopify-Hmac-Sha256" => hmac_A, "X-Shopify-Shop-Domain" => "attacker.myshopify.com",
#              "X-Shopify-Topic" => "orders/create", "X-Shopify-Webhook-Id" => "..." }
#   raw_body: body_A  # fully attacker-controlled content, since it's the attacker's own store

# Step 2: Attacker replays the exact same raw_body/hmac pair, only changing the shop header:
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: body_A,
  headers: {
    "X-Shopify-Hmac-Sha256" => hmac_A,               # still valid: HMAC only covers raw_body
    "X-Shopify-Shop-Domain" => "victim.myshopify.com", # forged, unauthenticated
    "X-Shopify-Topic" => "orders/create",
    "X-Shopify-Webhook-Id" => "replayed-id",
  }
)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body_A/hmac_A match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(body_A), ...))
# The host app now processes attacker-controlled body_A believing it belongs to victim.myshopify.com.
```
