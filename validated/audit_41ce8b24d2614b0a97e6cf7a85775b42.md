Confirmed. The vulnerability is in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* are unmodified relative to the HMAC digest computed with the app's single, shop-independent `Context.api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers with no cryptographic binding to the signed body at all [3](#0-2) .

`Registry.process` then trusts these unauthenticated header values outright: it dispatches on `request.topic` to select a handler, and forwards `request.shop`, `request.webhook_id`, and `request.api_version` into `WebhookMetadata` passed to the app's handler as if Shopify had certified them [4](#0-3) .

Because the same `api_secret_key` signs webhook bodies for *every* shop that installs the app, an attacker who legitimately installs the app on their own shop can capture a genuine `(raw_body, hmac)` pair Shopify sent for a topic/body they control (e.g. a minimal or attacker-influenced payload), then replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop and/or the `topic` header for a different (possibly mandatory/compliance) topic. `HmacValidator.validate` still returns `true` because only the body bytes are checked, not which shop or topic they were minted for.

The binding that should hold is:
`hmac_signed_bytes == (shop, topic, webhook_id, body)` for the value dispatched to the handler.
What actually holds is:
`hmac_signed_bytes == body` while `shop`, `topic`, `webhook_id` are attacker-controlled headers.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to guarantee. An attacker-controlled shop can:
- Forge webhook events attributed to a **different, victim shop** (`request.shop` is passed unauthenticated into the handler), leading to cross-tenant data confusion or corruption if the host app trusts `shop` to select which tenant's records to modify (e.g. order/customer sync, `customers/redact`, `app/uninstalled` handlers deleting/wiping data for the wrong shop).
- Trigger a handler intended for an unrelated topic by changing the `topic` header while reusing a validly-signed body, since topic is not part of the signed material either.

This matches the "Critical - cross-tenant access" impact category: the confidentiality/integrity boundary between tenants (shops) relies entirely on the `shop` header, which carries no cryptographic proof of origin.

### Likelihood Explanation
Exploitation only requires an attacker to be a legitimate merchant on the app (installing it on their own store is unprivileged/self-service for any Shopify app), which lets them receive genuinely-signed webhook deliveries for their own shop and topic. They then simply resend the identical body/HMAC bytes to the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers — no secret material or privileged access is required beyond installing the app once. This is a realistic, low-effort attack path fully reachable through this gem's own `Webhooks::Request` and `Webhooks::Registry.process` API, not dependent on the host app misusing the API.

### Recommendation
Bind the header-derived identity fields into the signed material (or independently authenticate them) before they are trusted:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's webhook signing scheme is extended to support it, or
- At minimum, have `Registry.process` cross-check `request.shop` against the shop associated with the specific webhook subscription/session that registered the handler, rather than trusting the header value outright, and reject topics that don't match the registration the handler was registered under with defense-in-depth checks independent of the header.
- Document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are NOT covered by the HMAC and must not be used as an authorization boundary by consuming apps without additional verification (e.g., checking against a known/installed-shops list).

### Proof of Concept
```ruby
# Attacker legitimately installs the target app on their own shop "attacker.myshopify.com"
# and receives a genuine webhook delivery from Shopify, e.g. for topic "orders/create":
#   headers: {
#     "x-shopify-topic" => "orders/create",
#     "x-shopify-hmac-sha256" => "<valid-hmac-for-body>",
#     "x-shopify-shop-domain" => "attacker.myshopify.com",
#     "x-shopify-webhook-id" => "..."
#   }
#   body: '{"id": 1}'
#
# HMAC is computed only over the raw body:
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, '{"id": 1}')
# valid for ANY shop/topic combination, since to_signable_string == @raw_body only.

# Attacker replays the exact same body + hmac, but swaps headers to target a victim shop
# and/or a different registered topic:
forged_headers = {
  "x-shopify-topic" => "customers/redact",           # different topic, same signed body
  "x-shopify-hmac-sha256" => captured_hmac_base64,    # identical signature, still verifies
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id": 1}', headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body-only check),
#    handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    topic: "customers/redact" — neither of which Shopify actually certified for this body.
