### Title
Stale cached account addresses persist in `connectedOrigins` after account state changes, causing cross-origin account-privilege bleed - (File: `features/connected-origins/module/connections.js`)

### Summary
`ConnectedOrigins` caches per-wallet-account addresses in `connectedAccountsAtom` and only refreshes that cache when the *set* of enabled wallet-account names changes, not when the underlying data behind an existing account name changes. This mirrors the reported bug class: a partial state update (one side of a paired accounting/state relationship is updated, the other side is not), leaving a "phantom" stale value that is later consumed for a trust decision.

### Finding Description
`updateConnectedAccounts` only recomputes the `connectedAccountsAtom` cache when the account **name set** differs from before: [1](#0-0) 

```js
updateConnectedAccounts = async () => {
  const walletAccounts = await this.#enabledWalletAccountsAtom.get()
  const connectedAccounts = await this.#connectedAccountsAtom.get()

  const difference = xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))
  if (difference.length === 0) {
    // up-to-date
    return
  }
  ...
```

This is triggered from `connectedOriginsPlugin`'s subscription to `enabledWalletAccountsAtom.observe`, i.e., it is a reactive, best-effort refresh rather than a synchronous, atomic update alongside every mutation of wallet-account/address state: [2](#0-1) 

Separately, `#getWalletAccountAddresses` prefers a previously cached address over recomputing it, and only falls back to the address provider when nothing is cached yet: [3](#0-2) 

```js
#getWalletAccountAddresses = async (walletAccount, assetNames) => {
  const connectedAccounts = await this.#connectedAccountsAtom.get()
  const entries = await Promise.all(
    assetNames.map(async (assetName) => {
      const existingAddress = connectedAccounts[walletAccount]?.addresses[assetName]
      if (existingAddress) {
        return [assetName, existingAddress]
      }
      const address = await this.#addressProvider.getDefaultAddress({ assetName, walletAccount })
      return [assetName, address.toString()]
    })
  )
  return Object.fromEntries(entries)
}
```

Because the refresh gate in `updateConnectedAccounts` is keyed purely on the **name set** (`xor` of keys), any change to a wallet account that does not add/remove a name — e.g. `disableMany`/`enableMany` toggling `enabled` on the same name (`features/wallet-accounts/src/module/wallet-accounts.ts:416-448`), or changes to underlying account metadata that affect derivation/address without renaming the account — will not invalidate the cached, potentially stale `connectedAccountsAtom` entry. This is the same root-cause pattern as the referenced report: one part of paired state (`enabledWalletAccountsAtom`, the source of truth) is updated, while a dependent aggregate/cache (`connectedAccountsAtom`) used for a downstream trust decision (`getConnectedAccounts`) is not always synchronized with it.

`getConnectedAccounts`, gated only by `isTrusted`, serves this cache directly to any previously-trusted origin: [4](#0-3) 

### Impact Explanation
A connected/trusted dApp origin can continue to receive address information for a wallet account the user disabled (intending to revoke visibility/exposure to connected sites), because the phantom entry in `connectedAccountsAtom` is not guaranteed to be invalidated by `disableMany`/`enableMany` toggles that don't change the account-name set. This is an account-isolation/privilege-bleed issue across the origin trust boundary: the dApp's authorized data scope silently outlives the user's explicit account-level revocation. It does not expose private keys or enable signing, so impact is bounded to address/metadata disclosure and stale-authorization scope, not direct fund loss.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a user connecting/trusting an origin, (2) later disabling (not removing) one of the exposed wallet accounts without also removing/re-adding other accounts (which would change the key set and trigger a full refresh), and (3) the origin polling `getConnectedAccounts` afterward. This is a normal user flow (disable an account they no longer want exposed), reachable without any privileged access, from the unprivileged "connected dApp" surface.

### Recommendation
Make `connectedAccountsAtom` refresh authoritative rather than name-set-diff based: invalidate/recompute the relevant per-account cache entries synchronously whenever `wallet-accounts` disables/enables/updates an account (not only on add/remove), or drop the "existingAddress" short-circuit in `#getWalletAccountAddresses` in favor of consulting `enabledWalletAccountsAtom`'s `enabled`/`compatibilityMode` state before trusting the cache.

### Proof of Concept
1. Connect and trust `exodus.com` for wallet account `exodus_1` (and `exodus_0`), populating `connectedAccountsAtom` with both accounts' addresses (`connections.js#add` → `#setData` → `#getAccounts`).
2. Call `walletAccounts.disable('exodus_1')` (`features/wallet-accounts/src/module/wallet-accounts.ts:420-448`), which persists `enabled:false` on the account but does not remove its key from `enabledWalletAccountsAtom`'s key set if the account remains listed as disabled rather than deleted, so `xor` in `updateConnectedAccounts` sees no key-set difference and skips refresh.
3. Call `connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })` — the disabled account's address is still returned from the stale `connectedAccountsAtom` cache, even though the user disabled that account.

```javascript
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```
