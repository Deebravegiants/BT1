### Title
Escrow withdrawal on Tron `IntentGatewayV2` doesn't validate ERC20 `transfer()` return value, allowing silent-fail tokens to permanently strand escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-specific `IntentGatewayV2` contract escrow release path (`withdraw()`) and the `SweepDust` handler use raw low-level `.call()` invocations of `IERC20.transfer` and only check that the call itself did not revert (`success`), without decoding/validating the ABI-encoded boolean return value. Unlike the mainline EVM `IntentGatewayV2`/`IntentsBase` contracts, which consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which validates return data), this Tron variant is vulnerable to non-reverting ERC20 tokens that return `false` on failed transfers.

### Finding Description
`withdraw()` is the internal function responsible for releasing escrowed order funds to a beneficiary. It is reachable via two unprivileged/relayer-triggered entry points:
- `onAccept()` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, which any relayer can trigger by delivering a valid cross-chain POST request/proof [1](#0-0) 
- `onGetResponse()`, triggered by a relayed GET response proof [2](#0-1) 

Inside `withdraw()`, each escrowed token is paid out using a raw call that only checks `success`, not the decoded boolean return value: [3](#0-2) 

The same unchecked-return pattern is repeated in the `SweepDust` handler inside `onAccept()`: [4](#0-3) 

For an ERC20/TRC20 token that does not revert on a failed transfer but instead returns `false` (a documented non-standard-but-common behavior explicitly called out in the original audit report), `token.call(...)` will return `success = true` even though no tokens were actually moved to `beneficiary`. Because only `success` is checked, execution proceeds past the `if (!success) revert TransferFailed();` guard, and the code unconditionally decrements the escrow accounting: [5](#0-4) 

and, for finalization, marks the order as filled/refunded and emits the corresponding event, permanently closing the withdrawal path for that commitment: [6](#0-5) 

This is precisely the bug class from the referenced Sentiment audit finding (`Account.sol`'s unchecked `try IERC20(...).transfer(...) {} catch {}`), reproduced here as an unchecked raw `.call()` whose returned boolean is ignored.

### Impact Explanation
When a solver, protocol fee recipient, or order beneficiary is owed a token that returns `false` on failed transfer instead of reverting, `withdraw()` will still mark the order as filled/refunded (`_filled[body.commitment] = beneficiary`) and zero out escrow accounting for that token, while the tokens never leave the gateway contract. This is a permanent loss of funds for the intended beneficiary: the escrow slot is deleted/decremented so a legitimate retry of `withdraw`/`RedeemEscrow`/`RefundEscrow` for that commitment is no longer possible (`UnknownOrder()` will be hit on any subsequent attempt since `_orders[body.commitment][token]` is now `0`), while the actual token balance remains locked/unclaimable in the gateway contract. Because this affects the core escrow settlement logic of the intents system reachable by any relayer delivering a valid cross-chain proof, it directly matches the required impact bar: "permanent freezing of funds."

### Likelihood Explanation
Likelihood depends on the destination/settlement token used by an order supporting non-reverting failure semantics (e.g., insufficient balance/blacklist checks implemented via `return false` rather than `require`). Since `IntentGatewayV2` on Tron is a generic, permissionless intents settlement contract accepting arbitrary configured tokens (`address token = address(uint160(uint256(order.inputs[i].token)))`), and Tron's TRC20 ecosystem includes tokens with non-standard/legacy transfer semantics, this is a realistic and directly reachable condition — no special privileges are required, only a relayer delivering a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` message for an order denominated in such a token.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` and the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer` (as already used consistently elsewhere in the mainline `IntentGatewayV2.sol`/`IntentsBase.sol`), which decodes and validates the ERC20 return value (or accepts tokens that return no data), reverting on any transfer that does not genuinely succeed.

### Proof of Concept
1. Configure/settle an order whose output/fee token is a TRC20/ERC20 implementation that returns `false` instead of reverting when a transfer fails (e.g., due to a paused/blacklist check implemented with `return false`).
2. A relayer delivers a `RedeemEscrow` request for a filled order, triggering `onAccept` → `withdraw(body, false)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes; the token's internal check fails and it returns `abi.encode(false)`, but the low-level call itself does not revert, so `success == true`.
4. The `if (!success) revert TransferFailed();` guard is bypassed; `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment] = beneficiary;` is set, and `EscrowReleased` is emitted — even though `beneficiary` received zero tokens.
5. The tokens remain stuck in the `IntentGatewayV2` contract balance, and the commitment can no longer be withdrawn again (escrow record already zeroed/order already marked filled), resulting in permanent loss of the beneficiary's funds.

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
