### Title
Rotating `_instances[stateMachineId]` between dispatch and delivery permanently blocks `RedeemEscrow`/`RefundEscrow` settlement, freezing escrowed funds - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentGatewayV2`'s `_authenticate()` gate checks the *current* value of `_instances[keccak256(source)]` against the peer address embedded in an already-in-flight cross-chain settlement message. Governance can update that mapping at any time via `NewDeployment`. If a `RedeemEscrow`/`RefundEscrow` message is dispatched from one gateway instance and the source-chain registry is repointed to a new instance address before the message is delivered, `onAccept` will permanently revert with `Unauthorized()` for that commitment, exactly mirroring the InvoiceManager pattern where an actor's authorization is re-checked at settlement time instead of pinned at creation time.

### Finding Description
Escrow release/refund is authenticated with a live lookup rather than a value fixed at order/message creation: [1](#0-0) 

`_authenticate` recovers the `module` address embedded in `request.from` (fixed forever, since it was encoded into the request body/hash on the destination chain at fill time) and compares it against `_instance(request.source)`, which is a **live** read of mutable state: [2](#0-1) 

`_instances` is writable at any time by Hyperbridge governance via the `NewDeployment` request kind, processed unconditionally in `onAccept`: [3](#0-2) [4](#0-3) 

Sequence that produces a permanent freeze:
1. A cross-chain order is placed on chain A; a solver fills it on chain B (destination). `_fillCrossChain` dispatches a `RedeemEscrow` `PostRequest` back to chain A, with `to = instance(order.source)` **as resolved on chain B at fill time** and the request's `from` field set to chain B's own gateway address.
2. Before that message is delivered on chain A, governance dispatches a `NewDeployment` update (or an `UpdateParams`/migration flow) that changes `_instances[keccak256(chainB)]` on chain A — e.g., to redeploy/rotate the chain-B gateway instance.
3. When the `RedeemEscrow` message is finally delivered to chain A's `onAccept`, `_authenticate` computes `_instance(request.source)` fresh and compares it to the `module` address baked into `request.from`. Since `_instances` was already changed, the comparison fails and the call reverts with `Unauthorized()`.
4. Because `EvmHost.dispatchIncoming` treats a reverting `onAccept` as retryable (it deletes the request receipt and returns rather than reverting the batch), any relayer can attempt redelivery — but every subsequent redelivery hits the exact same deterministic mismatch, since `request.from` cannot change and `_instances` has moved on. The message can never succeed unless governance reverts the instance mapping back to the exact old address, which defeats the purpose of ever having rotated it.
5. Meanwhile, the solver has already delivered output tokens to the user's beneficiary on chain B and burned gas doing so, and the input tokens remain escrowed in chain A's `_orders[commitment]` mapping indefinitely, since `withdraw()`/`_withdraw()` is only reachable through the now-permanently-failing `onAccept` path (or the mirrored GET-response cancellation path, which is likewise authenticated against the live, mutable `_filled` slot on the *other* chain and does not touch `_instances`).

This is structurally identical to the InvoiceManager bug class: an authorization/state check (`_isSolverActive` there, `_instances`-based `_authenticate` here) is evaluated against present-tense mutable state at settlement/delivery time rather than against the state that was valid when the transaction (invoice/order fill) was created, and there is no code path that lets a legitimately-completed action settle once the checked state has moved on.

### Impact Explanation
Escrowed user input tokens on the source chain become permanently unclaimable by the solver, and the settlement message can never be delivered successfully — this is a direct freezing-of-funds bug reachable by any legitimate order and any subsequent, ordinary governance action (rotating a peer gateway deployment), not requiring any malicious actor. It affects both `RedeemEscrow` (solver payment) and `RefundEscrow` (user refund after cancellation), so either solvers or users can have funds permanently stuck in the gateway.

### Likelihood Explanation
`NewDeployment` (registering/rotating a gateway instance for a state machine) is an expected, routine governance operation — the gateway is explicitly designed to support upgrades/migrations and instance rotation across many chains and long timeframes. Cross-chain messages routinely take non-trivial time to be relayed and challenge-period-gated on the destination, so there is a realistic window in which an in-flight `RedeemEscrow`/`RefundEscrow` message can be caught by an instance rotation that happens for unrelated reasons (e.g., a redeploy on a completely different lane triggering an update to the same `_instances` slot, or deliberate migration of that specific lane). No attacker action is required — ordinary, authorized administration triggers the freeze.

### Recommendation
Do not re-resolve the peer instance address at delivery time using live storage. Either:
- Embed/commit the expected peer instance address (or a version/epoch tag) into the dispatched request body at creation time and validate against that pinned value in `_authenticate`, or
- Version `_instances` (e.g., keep a small history keyed by height/epoch) and accept a message if `request.from` matches *any* instance that was valid for `request.source` at or before the message's dispatch height, or
- Provide an explicit escape hatch (e.g., a governance-only `forceWithdraw`/`sweep` path keyed by commitment) that lets escrowed funds be released once a message becomes permanently unauthenticatable due to an instance rotation, mirroring the InvoiceManager team's fix direction of allowing settlement of pre-existing obligations before/despite a status change.

### Proof of Concept
1. Deploy `IntentGatewayV2` instances `GA` (chain A, source) and `GB` (chain B, destination); register `GA.instance(chainB) = GB` and `GB.instance(chainA) = GA` via `NewDeployment`.
2. User places a cross-chain order on `GA` with `destination = chainB`, escrowing input tokens.
3. Solver calls `fillOrder` on `GB`; `_fillCrossChain` dispatches a `RedeemEscrow` `PostRequest` with `from = GB`, `to = GA.instance(chainA-as-seen-from-B)` i.e. resolved via `GB.instance(chainA)`, back toward chain A.
4. Before this request is delivered/proven on chain A, governance dispatches a `NewDeployment` `onAccept` call on `GA` that sets `_instances[keccak256(chainB)] = GB2` (a new address), simulating a legitimate migration.
5. Deliver the `RedeemEscrow` message to `GA.onAccept`. `_authenticate` computes `_instance(chainB) == GB2` but `module` decoded from `request.from == GB`; `GB2 != GB` so it reverts `Unauthorized()`.
6. Confirm via `evm/tests/foundry/IntentGatewayV2Test.sol` harness patterns (e.g. `testOnAcceptRedeemEscrow`/`testOnAcceptRefundEscrow`) that no other code path can redeliver or otherwise release `_orders[commitment][usdc]`, demonstrating the tokens are permanently stuck in `GA`.      * @dev Authenticates an incoming cross-chain post request by verifying that the
     * sender module matches the registered gateway instance for the source chain.
     * Reverts with InvalidInput if the sender address is malformed, or Unauthorized
     * if the sender is not the expected gateway.
     * @param request The incoming post request to authenticate.
     */
    function _authenticate(PostRequest calldata request) internal view {
        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
