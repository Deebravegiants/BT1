### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the shop identity (`shop-domain` header) that is handed to the app's webhook handler is taken from an unauthenticated HTTP header. This breaks the binding "shop authenticated == shop the handler acts on," analogous to the referenced report's `l1BurntAmountOf` binding being broken by an unchecked field.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhook requests, `Request#to_signable_string` returns only the raw body (`@raw_body`): [1](#0-0) 
The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC, then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` verbatim: [3](#0-2) 

This means the equality actually enforced is:
`HMAC(raw_body, client_secret) == received_hmac`

but the equality the app relies on for tenant isolation is:
`shop-domain header == shop that produced this event`

These are not the same check. Because the app's `client_secret` (and therefore the webhook HMAC key) is shared across all shops that install the app, any unprivileged merchant who installs the app on their own store can trigger a webhook to obtain a body + valid HMAC pair signed with the app's shared secret. That attacker can then replay the identical `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `shop-domain` header (and optionally `topic`/`webhook_id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `WebhookMetadata` is built with the attacker-controlled `shop`: [4](#0-3) 

The library provides no reconciliation between the header-derived `shop` and any signed field, so any host application that keys its persistence/actions on `WebhookMetadata#shop` (which is the intended and documented usage) will attribute attacker-supplied webhook data to a shop the attacker doesn't own.

### Impact Explanation
This is a cross-tenant identity confusion: a merchant who legitimately controls Shop A can cause the app to process arbitrary webhook data (of a type/topic the attacker also controls, e.g. `orders/create`, `customers/update`, `app/uninstalled`) tagged with Shop B's identity. Depending on how the host app consumes `WebhookMetadata#shop` (updating billing state, resource counts, uninstall/cleanup flows, GDPR-related record purges, etc.), this can lead to data corruption or unauthorized state changes scoped to a shop the attacker does not control — a cross-tenant boundary violation as called out in scope ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (the normal, unprivileged merchant flow), (2) capturing one legitimate webhook body+HMAC pair from that shop, and (3) POSTing it to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or any privileged account is required — the attacker only needs the ability to install the app on their own tenant, which is the baseline capability for any Shopify merchant.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the header alone. Options:
- Extend `to_signable_string` (or add a secondary check) to also cover `shop`, `topic`, and `webhook_id`, or
- Require the host application/library to cross-validate `request.shop` against an expected/known set of shops (e.g., a shop with an active session/install record) before dispatching to the handler, rejecting webhooks for shops with no known relationship to this delivery.
- At minimum, document explicitly that `shop`, `topic`, and `webhook_id` are unauthenticated and must be independently verified against installed-shop records by the host app before being trusted for tenant-scoped actions.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) and capture the raw POST: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid since signed with the app's shared `client_secret`).
3. Replay to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>
   X-Shopify-Api-Version: 2024-01

   B
   ```
4. `Utils::HmacValidator.validate` returns `true` because `H` matches `HMAC(B, client_secret)`, independent of the `X-Shopify-Shop-Domain` value: [5](#0-4) 
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))`, causing the host app to act on `victim-shop.myshopify.com`'s behalf using attacker-supplied `B`.
