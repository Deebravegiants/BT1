### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies nothing but the body bytes. The `shop-domain` header — which becomes `WebhookMetadata#shop` and is handed directly to the app's webhook handler as the tenant identifier — is never part of the signed material. This is the same bug class as the external report: an identity field ("shop") that is *acted on* downstream is not *bound* into the integrity check ("HMAC"), so it can be swapped independently of the verified payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` defines: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` (the value that is actually HMAC-verified) is just `@raw_body`. Compare this with the OAuth callback binding, `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed query string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the HMAC: [3](#0-2) 

`Webhooks::Registry.process` trusts this unauthenticated `shop` value and forwards it straight to the app-supplied handler as the tenant key, without any additional shop/session cross-check: [4](#0-3) 

The library's own documentation instructs developers to treat `data.shop` as the authoritative tenant identifier for the webhook (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The identity binding that should hold is: `shop-domain header verified == shop attributed to the webhook body by HmacValidator`. Because `to_signable_string` excludes the shop header, this equality is not enforced — the gem verifies "this body byte sequence was HMAC-signed by our shared `api_secret_key`" but the handler consumes "this body belongs to shop X," and X is attacker-controlled.

### Impact Explanation
Since all shops installed on a given app share the same `api_secret_key`, any legitimate installer of the app (an unprivileged party with respect to any *other* merchant's tenant) can obtain a real `(raw_body, hmac)` pair from a genuine webhook delivered to their own store, then resend that exact `raw_body` + `hmac` to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim merchant's domain). `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any application logic that uses `data.shop` to scope database writes, cache invalidation, background jobs, or session/token lookups for that tenant will process attacker-supplied webhook content as if it originated from the victim shop — a cross-tenant integrity/data-injection issue.

### Likelihood Explanation
Any developer using this gem/webhook flow "as documented" (per `docs/usage/webhooks.md`) is directly exposed, since the doc explicitly tells them to key per-tenant work off `data.shop`. Obtaining a valid `(body, hmac)` pair only requires the attacker to have their own genuine installation of the target app (a normal, unprivileged relationship, not a privileged account on the victim tenant), making exploitation straightforward once such a pair is captured.

### Recommendation
Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed material for webhook requests, or otherwise require the gem/host app to cross-check the header `shop` against a shop the app actually expects/owns a subscription for before dispatching to the handler, mirroring the OAuth `AuthQuery` binding that already folds `shop` into `to_signable_string`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) with body `B` and valid header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `to_signable_string` returns `B`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B) == H` — succeeds, since `shop` was never part of the signed input.
5. `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes attacker-controlled data under the victim tenant's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
