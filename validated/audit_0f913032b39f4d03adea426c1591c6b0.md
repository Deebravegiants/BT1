### Title
Webhook `shop`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` therefore only proves that the *body bytes* were signed with the app's secret; it says nothing about which shop, topic, or webhook the signature was meant for. `Registry.process` trusts `request.shop` and hands it straight to the app's handler as the tenant identifier.

### Finding Description
The `VerifiableQuery` contract used for HMAC validation is: [1](#0-0) 

For webhooks, the signable string is the raw body only, but `shop` is taken from the `shop-domain` header, which is outside that signed string: [2](#0-1) 

`HmacValidator.validate` checks `verifiable_query.to_signable_string` against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts any `request` whose HMAC validates, then dispatches the handler using `request.shop` (and `request.topic`, `request.webhook_id`) taken from the unauthenticated headers: [4](#0-3) 

The identity binding the gem is supposed to enforce is:
`shop asserted by validated request == shop that actually produced the signed bytes`

Because `api_secret_key` is a single per-app secret shared across every merchant install of that app (not per-shop), and the HMAC covers only the body, this equality never actually holds: the HMAC proves the body came from an app-secret holder (Shopify, for *any* shop with this app installed), not that the accompanying `shop-domain` header is truthful for that particular signed body.

An unprivileged actor who has installed the app on their own shop legitimately receives real webhook deliveries (valid body + valid HMAC + their own `shop-domain` header) at whatever endpoint they control or can observe (e.g., their own webhook receiver, or a body/HMAC pair obtained from their own account). They can then replay that exact `raw_body`/`hmac-sha256` pair to the victim app's webhook endpoint while substituting the `shop-domain` header (and optionally `topic`/`webhook-id`) with a different, victim shop's domain. `HmacValidator.validate` still succeeds (it only checks `raw_body` against the secret), and `Registry.process` calls the handler with `WebhookMetadata` claiming the event is for the victim shop: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing. If a host app's webhook handler looks up or mutates per-shop state keyed by `data.shop` (which is the documented/expected usage of `WebhookMetadata`), an attacker-controlled shop identifier lets a merchant inject forged events attributed to a shop they do not control — a cross-tenant access impact, since the attacker never needed the victim's or the app's actual per-shop credentials, only a `hmac_secret`-valid body they can legitimately obtain via their own installation.

### Likelihood Explanation
Any merchant who installs the app can trivially obtain a valid `(raw_body, hmac-sha256)` pair from their own real webhook deliveries, then replay it with a modified `shop-domain` header against the same public webhook endpoint. No secrets, tokens, or privileged access are required beyond a normal app install — this is reachable by any unprivileged internet user who can install the app once.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is actually verified, not left as a bare, unauthenticated header read. Concretely, include the `shop-domain` (and `topic`, `webhook-id`) header value in `to_signable_string`'s covered material before comparing against Shopify's signature, or — if Shopify's wire protocol truly only signs the body — have the gem require host applications to independently confirm that the shop in the header matches a shop for which this exact webhook subscription/`webhook_id` was registered, rather than trusting the header as ground truth in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and captures a legitimate webhook delivery: `raw_body = B`, header `shopify-hmac-sha256 = H` (valid signature of `B` with the app's `api_secret_key`), header `shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker sends a POST to the same webhook endpoint with the same `raw_body = B` and `shopify-hmac-sha256 = H`, but sets `shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Utils::HmacValidator.validate` returns `true`, because it only recomputes the HMAC over `raw_body`, which is unchanged.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the host app processes an attacker-forged event attributed to a shop the attacker does not control.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
