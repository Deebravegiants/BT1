### Title
Unsanitized `shop` parameter in `Oauth.begin_auth` enables open-redirect / forced OAuth flow to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop` string, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other OAuth-adjacent flow in this gem (`TokenExchange`, `ClientCredentials`, `RefreshToken`, the storefront GraphQL client) validates the shop against `Utils::ShopValidator` before using it to build a request host, but `begin_auth` does not, breaking the invariant that "shop used to build a Shopify-bound URL" must equal "shop validated as a trusted `*.myshopify.com`/`myshopify.io`/etc. domain."

### Finding Description
`begin_auth` takes `shop:` as a plain `String` and feeds it straight into `auth_base_uri(shop)`: [1](#0-0) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
```

This is used to build the full OAuth authorize URL: [2](#0-1) 

```ruby
state = SecureRandom.alphanumeric(NONCE_LENGTH)
cookie = SessionCookie.new(value: state, expires: Time.now + 60)
query = {
  client_id: ShopifyAPI::Context.api_key,
  scope: scope.to_s,
  redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
  state: state,
  "grant_options[]": is_online ? "per-user" : "",
}
query_string = URI.encode_www_form(query)
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
{ auth_route: auth_route, cookie: cookie }
```

Nothing in this method verifies `shop` is a real `*.myshopify.com` domain. Compare this to sibling flows that treat `shop`/host binding as security-relevant and explicitly call `ShopValidator.sanitize!`/`sanitize_shop_domain` before using the value to build a request target: [3](#0-2) 

The typical caller pattern for `begin_auth` (mirrored by `ShopifyApp`'s sessions controller, referenced in this gem's own docs) is `shop` coming straight from an unauthenticated query parameter on the app's `/login` route: [4](#0-3) 

Because `auth_base_uri` performs no allow-listing, an attacker can pass `shop=evil.example.com` (or any string), and the returned `auth_route` becomes `https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=<nonce>`. If the host application does what this gem's own docs suggest — redirect the browser to `auth_route` and set the returned `SessionCookie` — the victim's browser is redirected off-Shopify to the attacker's host carrying the freshly generated CSRF `state` nonce in the query string, while the matching nonce is simultaneously placed in the victim's cookie. This breaks the binding "host that receives the OAuth authorize request == a trusted Shopify domain," which is exactly the class of host/identity-binding gap called out in the report (a value used to build a security-relevant URL that isn't validated the way equivalent values are elsewhere in the same codebase).

Note that `validate_auth_callback` still requires a Shopify-issued, HMAC-valid `AuthQuery` (checked in `Utils::HmacValidator.validate`), so an attacker cannot forge the callback itself without the app's `api_secret_key`. The exploitable surface here is limited to the **begin_auth redirect leg**, not full token theft.

### Impact Explanation
This maps to the "session fixation or forced OAuth completion" High-impact category: the attacker can steer a merchant's browser to an attacker-controlled host mid-flow instead of Shopify's real authorize endpoint, using the app's own valid `client_id`/`redirect_uri`/`state`. This can be used for phishing (mimicking Shopify's login/consent screen at a look-alike domain) and for capturing the CSRF `state` nonce, which — combined with the cookie already set on the victim's browser for the app's own domain — undermines the state-based CSRF protection the callback relies on (`state == auth_query.state` check in `validate_auth_callback`).

### Likelihood Explanation
Likelihood is moderate: it requires the host application to pass an unauthenticated, attacker-influenced `shop` value into `begin_auth` (a very common integration pattern per this gem's own linked reference implementation, `ShopifyApp::SessionsController`, which takes `shop` from request params). No credentials, tokens, or prior authentication are needed by the attacker — they only need to get a victim to click a crafted `/login?shop=...` link on the host app.

### Recommendation
Validate/normalize `shop` in `begin_auth` using `Utils::ShopValidator.sanitize!` (as already done in `TokenExchange`, `ClientCredentials`, and `RefreshToken`) before it is used to construct `auth_base_uri`, raising `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host_name: "myapp.example.com",
  scope: ["read_products"], is_private: false, is_embedded: false)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "evil-attacker.example.com", # attacker-controlled query param, e.g. GET /login?shop=evil-attacker.example.com
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://evil-attacker.example.com/admin/oauth/authorize?client_id=key&scope=read_products&redirect_uri=...&state=<random-nonce>&grant_options%5B%5D=per-user"
```
No `Errors::InvalidShopError` (or any error) is raised, and the returned `auth_route` points to the attacker's host while the accompanying `result[:cookie]` still carries the valid CSRF `state` value, ready to be set on the victim's browser by the host app before the (attacker-controlled) redirect happens.

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
