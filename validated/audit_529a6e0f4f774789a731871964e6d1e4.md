### Title
`placeOrder` can register an order with 0 escrowed input against fee-on-transfer tokens when protocol fee is disabled - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` supports fee-on-transfer ERC20 tokens by re-measuring the amount actually received and overwriting `order.inputs[i].amount` with that value. A zero-amount guard exists for the *user-specified* amount, but the guard for the *actual received* amount is only executed inside the `protocolFeeBps > 0` branch. When the destination's protocol fee is `0` (which is the default unless explicitly configured), an order whose real escrow is `0` can still be committed and offered to solvers, who are shown a valid-looking order requiring real output tokens against a phantom (zero) escrow — mirroring the Cooler `collateralFor()` bug where `request()` accepted a non-zero loan amount backed by zero collateral.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, `placeOrder` performs its zero checks on the *pre-transfer* amount: [1](#0-0) 

For an ERC20 input, `order.inputs[i].amount` is only checked for `== 0` *before* the transfer, then immediately overwritten with the actually-received balance delta, which can legitimately be smaller (or, for a 100%-fee/deflationary token, exactly `0`) than what was checked:

```
if (order.inputs[i].amount == 0) revert InvalidInput();   // checks the ORIGINAL amount
...
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;  // can become 0
```

Phase 2 then computes protocol fees from this (possibly zero) "actual received" amount: [2](#0-1) 

The re-validation `if (originalAmount == 0) revert InvalidInput();` (line 344) only runs inside the `if (protocolFeeBps > 0)` branch. When `protocolFeeBps == 0` for the order's destination — the default state unless a per-destination override or the global `_params.protocolFeeBps` is explicitly set nonzero — the `else` branch is taken:

```solidity
} else {
    reducedInputs = order.inputs;   // no zero check here
}
```

The order then proceeds to Phase 3, crediting `_orders[commitment][token] = 0` as valid escrow, and the order is emitted/offered to solvers with a legitimate-looking output requirement but zero backing collateral, exactly analogous to `Cooler.request()` silently accepting a non-zero loan amount when `collateralFor()` rounds to zero.

### Impact Explanation
A solver/filler that executes `fillOrder`/`_fillSameChain` against such an order sends real `order.output` assets to the beneficiary (the attacker) and, per `_fillSameChain`, receives only the escrowed input amount pulled from `_orders[commitment][token]`, which is `0`: [3](#0-2) 

This lets an attacker place an order that pays them real output tokens from a solver while the solver receives nothing in return — direct theft of solver funds, matching the report's "loan without collateral" impact class (Medium/High: concrete loss of funds for any counterparty who does not manually re-derive the true escrowed amount).

### Likelihood Explanation
Exploitation requires only: (1) a fee-on-transfer/deflationary ERC20 token as the order's input asset (explicitly supported and tested in the codebase, e.g. `FeeOnTransferToken` in the test suite), and (2) the destination's protocol fee being `0`, which is the default unless separately configured. No privileged role or governance action is required — any unprivileged order placer can trigger this from a single `placeOrder` transaction.

### Recommendation
Move the zero-amount check on the actually-received `order.inputs[i].amount` so it is unconditionally enforced in Phase 2/3, regardless of `protocolFeeBps`, e.g.:
```solidity
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    ...
}
```
before computing `reducedInputs`/`commitment` in both the `protocolFeeBps > 0` and `else` branches, so an order can never be committed with a zero-value input leg.

### Proof of Concept
1. Deploy a token whose `transferFrom` burns 100% of the transferred amount as a "fee" (or use the existing `FeeOnTransferToken` test helper configured at 100%).
2. Ensure the destination chain has no override in `_destinationProtocolFees` and `_params.protocolFeeBps == 0` (the default for a freshly configured gateway).
3. Call `placeOrder` with `order.inputs[0] = {token: feeToken, amount: 1}` and `order.output.assets[0] = {token: USDC, amount: 1000e6}`.
4. `order.inputs[0].amount` is overwritten to `0` at line 322 of `IntentGatewayV2.sol`; since `protocolFeeBps == 0`, the `else` branch at line 358 skips the zero check, and `_orders[commitment][feeToken] = 0` is recorded, with `OrderPlaced` emitted for a live order.
5. A solver calling `fillOrder` sends 1000 USDC to the attacker's beneficiary and receives `escrowedAmount = 0` back, resulting in a full loss of the solver's output tokens.
