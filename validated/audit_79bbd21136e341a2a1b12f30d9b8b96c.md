### Title
Panic from Unbounded `checked_pow(10, decimals)` in Decimal Normalization Math Can Permanently Freeze Pool Funds - (File: `program/src/math.rs`)

### Summary
The Vyper report describes a compiler that panics (`CompilerPanic: out of range`) instead of returning a controlled error when an expression size overflows memory. The direct analog in this Solana program is the pervasive pattern of `U128::from(10).checked_pow(native_decimal.into()).unwrap()` used throughout the AMM's decimal-normalization math. Because `native_decimal` ultimately derives from an SPL token mint's `decimals` field (a `u8`, legally 0–255) and there is no visible upper-bound check on it before it is used as an exponent, a pool creator can pick coin/pc mints with abnormally large decimals to make this exponentiation overflow `u128`, causing an unhandled `.unwrap()` panic instead of a graceful `AmmError`.

### Finding Description
`Calculator::normalize_decimal`, `Calculator::restore_decimal`, `Calculator::normalize_decimal_v2`, `Calculator::convert_in_pc_lot_size`, and `Calculator::convert_out_pc_lot_size` all compute `10^native_decimal` (or `10^coin_decimals` / `10^pc_decimals`) via `U128::from(10).checked_pow(...).unwrap()`: [1](#0-0) [2](#0-1) [3](#0-2) 

`u128::MAX` is roughly `3.4 × 10^38`, so any exponent ≥ 39 makes `checked_pow` return `None`, and the subsequent `.unwrap()` panics rather than returning `AmmError::CheckedPowOverflow` or similar. `amm.coin_decimals` / `amm.pc_decimals` are stored on `AmmInfo` and consumed by `Calculator::restore_decimal` / `normalize_decimal_v2` inside pnl accounting (`calc_take_pnl`), which is invoked from `process_withdraw` and other trade-affecting paths: [4](#0-3) [5](#0-4) 

These decimal values originate from the coin/pc mint accounts supplied by the (unprivileged) pool creator during `Initialize2`, which unpacks arbitrary user-supplied mint accounts via `unpack_mint`: [6](#0-5) [7](#0-6) 

Nothing in `math.rs` or the error set (`AmmError::CheckedPowOverflow` does not exist) constrains `decimals` to a safe range (e.g., ≤ 38) before it is used as an exponent, unlike the checked arithmetic elsewhere in the file (`checked_mul`, `checked_add`, etc., which return `AmmError` variants instead of panicking).

### Impact Explanation
If a malicious or careless pool creator initializes a pool using a mint with an extreme `decimals` value (up to 255, a legal SPL Mint field), and that value is not caught during `Initialize2`, every subsequent instruction that reaches `calc_take_pnl`/`normalize_decimal`/`restore_decimal` for that pool (swap, deposit, withdraw) will panic. On Solana, a program panic aborts and reverts the triggering transaction, but it does **not** revert prior transactions — so once liquidity providers have deposited into such a pool, they can be permanently unable to withdraw if withdrawal itself is the code path that panics, resulting in a permanent freeze of LP/user funds already locked in the pool's vaults.

### Likelihood Explanation
Likelihood depends on whether `Initialize2` itself exercises the same decimal-normalization code path with the malicious decimals value at pool-creation time. If it does, the malicious `Initialize2` transaction would itself panic and, due to Solana's atomic transaction semantics, roll back — preventing the pool (and any fund lock-in) from ever being created, which would eliminate real-world impact. I was not able to fully confirm within the available context whether `Initialize2`'s initial `TargetOrders`/pnl setup performs an equivalent `checked_pow` call with the same decimals before any deposit is finalized, or whether it defers this exposure to the first subsequent swap/deposit/withdraw. This is the key unresolved fact that determines whether the bug is merely a self-inflicted DoS (no impact) or a genuine fund-freezing vulnerability.

### Recommendation
- Bound `coin_decimals`/`pc_decimals` (and any other decimals used as `checked_pow` exponents) to a safe maximum (e.g., ≤ 19, matching `u64` decimal range, or ≤ 38 for `u128`) during `Initialize2`, rejecting mints with implausible decimals.
- Replace all `.checked_pow(...).unwrap()` call sites in `math.rs` with proper `.ok_or(AmmError::...)?` error propagation so an overflow returns a program error instead of panicking.
- Audit every other `.unwrap()` following `checked_*` operations in `math.rs` and `processor.rs` for similar unchecked-panic risk once inputs originate from attacker-influenced mint/account data.

### Proof of Concept
Conceptual PoC (unverified against actual `Initialize2` decimal validation, due to incomplete code path confirmation):
1. Attacker creates two SPL mints, one with `decimals = 250` (a valid SPL Mint value), and a normal mint for the other side.
2. Attacker calls `Initialize2` with `coin_mint` set to the extreme-decimals mint, funding the pool with a small amount of real liquidity.
3. If `Initialize2` succeeds (i.e., its own pnl/target-order setup does not invoke `normalize_decimal`/`restore_decimal` with the stored decimals, or does so only with values that happen not to overflow at creation-time), the pool becomes live and other LPs may deposit into it.
4. Any subsequent `Withdraw`, `Deposit`, or Swap transaction that reaches `calc_take_pnl` → `Calculator::restore_decimal`/`normalize_decimal_v2` (`program/src/math.rs:96-104`, `106-116`) computes `U128::from(10).checked_pow(250)`, which returns `None`, and the `.unwrap()` panics, aborting the transaction. All LP funds already deposited into the pool's vaults become permanently unwithdrawable through the normal program interface. [2](#0-1)
