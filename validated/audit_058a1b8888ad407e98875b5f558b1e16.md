# Cross-tenant webhook shop-spoofing — HMAC signature does not cover the shop-domain header used for tenant identity (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` identity used by `ShopifyAPI::Webhooks::Registry.process` to route/attribute an inbound webhook to a tenant is read from an HTTP header that is never part of the signed material. An attacker who can obtain one validly-signed webhook payload (trivially achievable by installing the app on a shop they control) can replay that same body with a forged `shop-domain` header pointing at a victim shop, and the HMAC check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`: [2](#0-1) 

But `Request#shop` (as well as `topic`, `api_version`, `webhook_id`) is read straight from an attacker-suppliable header, entirely outside the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop header used for tenant routing == shop the HMAC actually authenticates`. Since the HMAC only authenticates the byte-identical body (proving "signed with this app's `api_secret_key`"), and the same `api_secret_key` is shared across *all* shops that installed the app, a valid signature says nothing about *which* shop the payload belongs to. Concretely:
- Before the attack: attacker installs (or already has) the app on shop `attacker.myshopify.com`, triggers a webhook (e.g., a `products/update` or `app/uninstalled` event) and captures the raw body + valid `X-Shopify-Hmac-SHA256` header Shopify sent.
- Attacker's request sequence: attacker POSTs that exact captured body to the app's webhook endpoint again, but swaps the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally the topic/webhook-id headers).
- After the attack: `HmacValidator.validate` still succeeds (body unchanged), `Registry.process` looks up a handler for the topic and invokes it with `shop: "victim.myshopify.com"`, `body:` attacker-controlled data — the app now processes attacker-controlled data as if `victim.myshopify.com` sent it.

This lets an unprivileged internet user (anyone who can install the app on their own store) forge webhook events "from" any other tenant of the same app, bypassing the tenant boundary the HMAC check is meant to enforce.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide, satisfying the "cross-tenant access" Critical impact category. Depending on how the host app's webhook handlers use `shop`/`body` (e.g., `app/uninstalled` to wipe tenant data, `shop/update` to alter tenant configuration, `customers/data_request` for GDPR flows, billing webhooks), this can let an attacker inject or corrupt another merchant's data, trigger deprovisioning of a victim's install, or otherwise impersonate a victim shop's webhook stream — all without ever possessing that victim's credentials or the app's `client_secret`.

### Likelihood Explanation
Requires only: (1) the ability to install/operate a shop under the attacker's control that installs the target app (unprivileged, e.g. a free Shopify dev/partner store), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with custom headers — both trivially available to an "unprivileged internet user." No access to `api_secret_key`, access tokens, or the target's credentials is required. This is easily automated (capture-and-replay).

### Recommendation
Do not treat the `shop`, `topic`, `api_version`, or `webhook-id` headers as trusted/authenticated merely because the request's HMAC validated. Either:
- Include the shop domain (and topic/webhook id) in the signed material used for HMAC verification, or
- Cross-check `request.shop` against an independently-trusted source (e.g., the shop associated with the currently active/looked-up session for that install) before invoking the handler, rejecting the webhook if they don't match, or
- Document explicitly (and enforce in `Registry.process`) that `shop` from webhook headers must not be used as an authorization/tenant-identity boundary without additional verification, since the HMAC does not cover it.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger any subscribed webhook topic to capture a legitimate `(raw_body, X-Shopify-Hmac-SHA256)` pair.
2. Replay:
```ruby
headers = {
  "x-shopify-topic" => "<captured topic>",
  "x-shopify-hmac-sha256" => "<captured valid hmac>",
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request) # HMAC check passes; handler invoked with shop == "victim.myshopify.com"
``` [4](#0-3)  confirms the handler is invoked with the unverified `request.shop` once `HmacValidator.validate` returns true for the (unmodified) body.
