### Title
Unverified `address` field lets anyone hijack Get-request delivery reputation rewards - ([File: modules/pallets/state-coprocessor/src/impls.rs])

### Summary
`Pallet::handle_get_requests` in `modules/pallets/state-coprocessor/src/impls.rs` mints `ReputationAsset` tokens and records relayer attribution using a self-declared `address: Vec<u8>` field from the submitted `GetRequestsWithProof` payload, with no cryptographic proof binding that address to whoever actually produced/submitted the state and response proofs. This is the same bug class as the Budibase advisory: a privileged identity/credit is attached using an **unverified claim** supplied by the caller, instead of a proof the pallet itself validates (as its sibling reward-claim pallets do).

### Finding Description
`GetRequestsWithProof` carries an `address: Vec<u8>` field documented only as "Address that should be credited with fees" [1](#0-0) . `handle_get_requests` verifies the source-chain membership proof and the destination-chain state (response) proof [2](#0-1) , but never verifies that `address` corresponds to the entity that produced or submitted those proofs. It then mints `ReputationAsset` directly to whatever 32-byte value `address` decodes to, keyed purely off `total_bytes` of proven `GetResponse`s:

```
if let Ok(bytes32) = <[u8; 32]>::try_from(address.as_slice()) {
    let relayer: T::AccountId = bytes32.into();
    ...
    <T as pallet_messaging_incentives::Config>::ReputationAsset::mint_into(&relayer, amount)
``` [3](#0-2) 

`address` is also written into `response_receipt` and emitted as the attributed `relayer` in `GetRequestHandled` [4](#0-3) .

This is a materially weaker authentication model than every sibling reward-claim path in the same relayer/coprocessor family:
- `accumulate_fees`'s beneficiary redirect requires a `Signature` that recovers to the on-chain `delivery_address` the state proof already proved [5](#0-4) .
- `claim_outbound_consensus_delivery_reward` requires the recovered signer to equal the address proven in the destination's `EvmHost._epochs[set_id]` slot [6](#0-5) .
- `claim_outbound_request_delivery_reward` requires the recovered signer to equal the address proven in the destination's receipt slot [7](#0-6) .

In all three of those, the "identity" credited with the reward is *proven* (analogous to checking `email_verified=true` before trusting the claim). In `handle_get_requests`, the identity credited is a bare, self-asserted field — analogous to Budibase trusting the unverified `email` claim outright.

### Impact Explanation
Since the state/response proofs required to submit `GetRequestsWithProof` are, by protocol design, freely reproducible by anyone once a relayer has done the underlying work (Hyperbridge's proofs are public and "freely provided by connected chains" per the relayer incentive docs), any third party who observes a pending/mempool `GetRequestsWithProof` extrinsic (or independently re-derives the same proofs) can resubmit it first with `address` set to their own account, stealing the `ReputationAsset` mint that was meant for the relayer who actually did the work. Because `ReputationAsset` backs collator-candidacy bonding (`set_reputation_balance`/`register_as_candidate` in the collator-manager tests) [8](#0-7) , this is an unbacked-mint / unauthorized-privilege-credit vector: reputation tokens are minted to an address that never verified anything, undermining both relayer fee/reward accounting and downstream collator-security assumptions that rely on ReputationAsset reflecting real proof-verification work.

### Likelihood Explanation
The call is reachable by any unprivileged relayer/message dispatcher submitting Get-request delivery proofs — no special role is required beyond producing a valid state proof, which is by design public and reproducible. The only defenses present (`dedup_requests`, per-request `response_receipt` checks) prevent double-crediting of the *same* request, not misattribution of the credited `address`; they do not stop an attacker from front-running a legitimate submitter's proof bundle with the same proofs and a different `address`.

### Recommendation
Bind the credited `address` to a cryptographic proof analogous to the pattern already used in `accumulate.rs`/`outbound_consensus.rs`/`outbound_request.rs`: require a `Signature` over a payload (e.g., hash of the request commitments/response proof) that recovers to `address`, or otherwise derive the credited identity from something the extrinsic's own origin/signature already commits to, rather than accepting a bare, unauthenticated `Vec<u8>` field. At minimum, gate `handle_get_requests` behind a signed origin whose `AccountId` is used directly as the mint target, eliminating the separate unverified `address` parameter.

### Proof of Concept
1. Relayer A performs the legitimate work: fetches source membership proof and destination state proof for a batch of `GetRequest`s, and constructs `GetRequestsWithProof { requests, source, response, address: A }`.
2. Because these proofs are public/reproducible (per protocol design) and the extrinsic is visible before finalization (mempool) or trivially reconstructible from public chain state, Attacker B copies `requests`, `source`, `response` verbatim and submits `GetRequestsWithProof { requests, source, response, address: B }` first (or in a competing transaction).
3. `handle_get_requests` performs `dedup_requests` and proof verification, which succeed identically for B's copy (same proofs, same requests) [9](#0-8) .
4. `ReputationAsset::mint_into(&B, amount)` is executed, crediting B — who did no verification/relay work of their own — with the reputation reward and relayer attribution intended for A [10](#0-9) .
