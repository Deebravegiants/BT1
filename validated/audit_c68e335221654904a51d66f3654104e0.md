### Title
`do_signup` bypasses the backend duplicate/fraud verification round-trip for `user_centric_signup` flows - (File: `src/plans/mod.rs`)

### Summary
`ArmadaGovernor::_classifyProposal` applies its 5%-of-treasury security gate only to the `DISTRIBUTE_SELECTOR` code path while an equivalent `STEWARD_SPEND_SELECTOR` path reaches the same effect (fund outflow) without the gate. The analogous bug class in orb-core is that the authoritative backend duplicate/fraud check performed via `signup_post::request` + `signup_poll` is applied only on the "standard" enrollment path (`self.enroll_user`), while the `user_centric_signup` branch reaches the identical outcome (marking the signup as successful, having already built and uploaded the PCP) without ever invoking that backend round-trip.

### Finding Description
In `do_signup`, both branches perform the same upstream work: biometric capture, `biometric_pipeline`, `detect_fraud`, and — for signups that decode into `personal_custody_package::Credentials` — building and uploading the PCP via `build_pcp`/`upload_pcp_tier_0`. Only at the final step does the logic fork: [1](#0-0) 

For the non-user-centric path, `self.enroll_user(...)` is invoked, which calls `enroll_user::Plan::run`, which POSTs the iris codes to the backend `/api/v2/signups/{signup_id}` endpoint and polls `signup_poll::request` for the authoritative verdict. The comment in that code explicitly documents that this round-trip is what detects "Backend duplicates," "Backend inflight matches," and "Backend detected fraud": [2](#0-1) 

For the `user_centric_signup` path, this entire backend verification round-trip is skipped. Success/failure is instead derived purely from the locally computed `signup_reason`: [3](#0-2) 

`signup_reason` is computed from `detect_fraud`, which in this build has had all fraud checks deleted and unconditionally returns `Ok(false)`: [4](#0-3) 

Consequently, in the `user_centric_signup` branch, `signup_reason` will almost always resolve to `SignupReason::Normal` (unless the pipeline itself fails to produce output), and the enrollment is marked `Success` without ever contacting the backend's duplicate/fraud detection service that the other path relies on for the same effective outcome. This mirrors the reported bug class exactly: a critical security check (duplicate/fraud verification) is wired into only one of two code paths that lead to the same effect (successful enrollment), while the alternate path bypasses it entirely.

### Impact Explanation
If the backend-side duplicate check is the mechanism that prevents the same iris from being enrolled multiple times (cross-signup state bleed / duplicate signup), then any signup routed through the `user_centric_signup` branch never has that check performed by orb-core, and success is asserted locally. Given the FOSS build's `detect_fraud` is a no-op, this branch essentially always reports success as soon as biometric capture and pipeline complete, independent of whether the backend would have flagged the signup as a duplicate or fraudulent. This is a concrete unauthorized/misattributed enrollment risk consistent with the "cross-signup state bleed" impact category.

### Likelihood Explanation
Exploitability depends on how `user_centric_signup` is set: it originates from `authenticated_app_data.user_centric_signup` returned by the backend/app-signed QR data in `src/backend/user_status.rs` (line 209/242/267), not from an arbitrary unprivileged parameter the orb itself can be tricked into flipping via local input. This is a material precondition, similar to the original report's "hostile elected steward" precondition — the flag must be set by a party controlling the app-side signup flow. Once that precondition holds, the divergent code path in `do_signup` provides zero orb-local backend verification, matching the report's structural pattern of an asymmetric security gate across two equivalent-outcome paths. I could not verify from the indexed files whether an equivalent duplicate check is enforced elsewhere in the backend independent of orb-core's own `signup_post`/`signup_poll` round trip (e.g., during PCP tier upload or app-side enrollment finalization) — this indexed codebase does not contain the backend service internals, only orb-core's client-side logic, so the true end-to-end risk cannot be fully confirmed here.

### Recommendation
Ensure `user_centric_signup` signups also invoke (or are otherwise covered by) the same backend duplicate/fraud verification round-trip that `enroll_user::Plan::run` performs for standard signups before `debug_report.enrollment_status` is set to `Success`, rather than trusting the locally-derived `signup_reason` alone. At minimum, `_classify`-style parity should be enforced: any code path that can mark a signup "successful" must pass through the same backend-verified check as the reference (`enroll_user`) path.

### Proof of Concept
Not executable from the indexed context (no test harness for `MasterPlan`/`do_signup` was found in the index). The control-flow evidence is:
1. `user_data.user_centric_signup` is a backend-supplied boolean surfaced through `qr_codes.user_data.user_centric_signup` and read in `do_signup` at [5](#0-4) .
2. When true (and `ignore_user_centric_signups` is false), `do_signup` sets `enrollment_status` from `signup_reason` alone and never calls `self.enroll_user`, skipping the `signup_post`/`signup_poll` backend duplicate/fraud check that the other branch relies on: [1](#0-0) , [6](#0-5) .
3. `signup_reason` for this branch is effectively always `Normal` because `detect_fraud` is stubbed to `Ok(false)`: [7](#0-6) .
