### Title
Chainlink oracle outage permanently freezes gas-fee payment and fee recycling in `SimplexPaymaster` - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments and recycles fees using direct, unguarded calls to `AggregatorV3Interface.latestRoundData()`. Unlike `_executePermit`, which wraps its external call in `try/catch` [1](#0-0) , `_getOraclePrice` makes a bare, unprotected call to the oracle [2](#0-1) . If any registered Chainlink feed (native or per-token) is paused or taken offline — as Chainlink has done historically during extreme market events — every call that depends on it reverts.

### Finding Description
`_getOraclePrice` is the sole pricing primitive used by:
- `_tokenPrice` (called from `_fetchDetails`, which every `PaymasterERC20`-routed `UserOperation` must go through during ERC-4337 validation) [3](#0-2) 
- `swapAndDeposit`, the fee-recycling function that swaps collected ERC-20 fees into native currency and tops up the paymaster's `EntryPoint` deposit [4](#0-3) 
- `getTokenPrice` / `estimateTokenCost`, the public price views [5](#0-4) 

`_getOraclePrice` calls `oracle.latestRoundData()` with no `try/catch` and no fallback path [6](#0-5) . Both `_tokenPrice` (used by `_fetchDetails`) and `swapAndDeposit` always query `nativeOracle` in addition to the token-specific oracle [7](#0-6) [8](#0-7) . Because `nativeOracle` is a single, shared feed for the whole contract, if it is paused or reverts, every ERC-20-funded `UserOperation` through this paymaster reverts during `_validatePaymasterUserOp`/`_fetchDetails`, and `swapAndDeposit` (the only mechanism that replenishes the `EntryPoint` deposit from collected fees) also reverts.

This mirrors the reported bug class exactly: an oracle call without a try/catch or fallback freezes a critical unprivileged-reachable path — here, gas-fee payment for message dispatch (any unprivileged sender submitting a `UserOperation` that pays gas via this paymaster is a "bandwidth purchaser" of Hyperbridge's fee-payment path).

### Impact Explanation
Recovery requires a governance round-trip: `UpdateParams` (to point `nativeOracle` elsewhere) or `DeactivateToken`/`RegisterToken` for the affected token, both of which are cross-chain `onAccept` governance requests gated to a single authorised relayer [9](#0-8) . Until that round-trip completes:
- No ERC-20-funded `UserOperation` can use this paymaster (mode 0x00 or 0x02), since `_fetchDetails` always reverts.
- `swapAndDeposit` cannot recycle accrued fees into the `EntryPoint` deposit, so if the paymaster's native deposit is drawn down in the meantime, it can no longer sponsor any operation regardless of token, freezing the fee-payment route entirely until governance intervenes.

This is a freezing-of-funds/freezing-of-a-message-delivery-route condition triggered by a third-party dependency outage, not by any protocol misbehavior, so it qualifies as Medium severity.

### Likelihood Explanation
Chainlink has paused feeds during extreme market conditions before (e.g., UST/ETH during the UST collapse), and `maxOracleAge`-based staleness checks in `_getOraclePrice` [10](#0-9)  only catch a stale-but-live feed — they do nothing for a feed that reverts outright or returns no data. Any user attempting to pay gas through this paymaster while the shared `nativeOracle` (or their token's oracle) is down triggers the freeze; no attacker action or governance misbehavior is needed.

### Recommendation
Wrap the `latestRoundData()` call in `_getOraclePrice` in a `try/catch`, and on failure either (a) revert with a distinguishable error that lets off-chain infrastructure quickly route users to alternate payment (native or another token), or (b) fall back to a secondary oracle/price source configured per token, similar to the recommendation in the referenced report. Consider also decoupling `swapAndDeposit`'s dependence on `nativeOracle` risk from unrelated tokens' fee-payment paths.

### Proof of Concept
1. Governance registers `tokenA` with `oracleA`, and sets `nativeOracle` to `oracleN`.
2. `oracleN` (or `oracleA`) is paused/taken offline by its operator such that `latestRoundData()` reverts (as demonstrated by the test harness pattern in `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts`, which show the same call path reverting on bad data [11](#0-10) ; a hard revert instead of stale/invalid data produces the same failure with no recovery option).
3. Any unprivileged user submits a `UserOperation` with `paymasterData` selecting `tokenA` for gas payment. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle,...)` reverts, so the `UserOperation` cannot be included by any bundler.
4. Treasury attempts `swapAndDeposit(tokenA, amount)` to top up the `EntryPoint` deposit; it also reverts at the same `_getOraclePrice` call, so accrued fees cannot be converted into deposit, and once the deposit is exhausted the paymaster cannot sponsor *any* operation, for *any* token, until governance replaces the oracle.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }

    ///         PaymasterERC20._erc20Cost (including its postOp gas cushion).

        TokenConfig memory cfg = tokenConfigs[token];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(token);
