### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` authenticates a webhook solely by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field [4](#0-3) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are read directly from the `X-Shopify-*`/`Shopify-*` HTTP headers and are not part of the signed payload at all [2](#0-1) .

### Finding Description
The identity binding an app relies on to know "this webhook payload belongs to shop X" should be: `HMAC(secret, signed_bytes) == received_hmac` AND `shop == the shop bound inside signed_bytes`. In this gem that equality breaks down to `HMAC(secret, raw_body) == received_hmac` while `shop` is taken from a completely separate, unsigned header. Concretely:

- `HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` [5](#0-4) .
- For webhooks, that signable string is just `@raw_body` [1](#0-0) .
- `Registry.process` uses this body-only HMAC as its sole trust gate, then hands `request.shop` (header-derived, unauthenticated) straight to the app-level webhook handler as the tenant identifier [3](#0-2) .

Because HMAC-SHA256 over a body doesn't depend on any header value, any request with a body/HMAC pair that is valid for shop A remains HMAC-valid no matter what `shop-domain` (or `topic`/`webhook-id`) header is attached to it. An attacker who legitimately controls a shop that has installed the target app receives real webhook deliveries from Shopify for their own store, each with a valid `X-Shopify-Hmac-SHA256` computed over that body. Since the header is never covered by the signature, the attacker can replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain (or a different `topic`) that the attacker does not control. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches the handler with `WebhookMetadata` whose `shop` is the attacker-chosen victim domain.

This breaks the equality: **shop authenticated (via HMAC-covered bytes) == shop the app acts on**. The library asserts the request is genuine ("HMAC validated") while silently allowing the actual tenant-identifying field to be forged, letting one merchant's data get attributed to another merchant inside the host application's webhook handler.

### Impact Explanation
This is a cross-tenant access primitive at the identity-binding level: the host app is told "this validated webhook belongs to shop=X" for an attacker-chosen X, while the only thing actually proven cryptographically is that the attacker previously received *some* webhook (for their own shop) with that exact body. Depending on what the app's `WebhookHandler` does with `data.shop` (e.g., persisting order/customer data, dispatching per-shop side effects, or triggering the mandatory `shop/redact`/`customers/redact`/`customers/data_request` GDPR handlers with a forged shop), this can lead to cross-tenant data corruption or spoofed compliance-relevant events attributed to a shop that never sent them.

### Likelihood Explanation
The prerequisite is that the attacker owns/controls a shop with the target app installed (or otherwise gets one genuine `(body, hmac)` webhook pair to replay) — no `client_secret` or access token is required, and no privileged access to the victim shop is needed. The webhook endpoint is deliberately public-facing since Shopify itself must be able to reach it unauthenticated apart from the HMAC header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable bytes verified by `HmacValidator`, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is handed to app code — e.g., require the host application to independently confirm the `shop` against a known/registered value rather than trusting the header as-is, and clearly document that `request.shop` is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker.myshopify.com`, and receives a legitimate webhook: body `{"id":1}"`, header `Shopify-Shop-Domain: attacker.myshopify.com`, valid `Shopify-Hmac-Sha256` computed by Shopify over that body.
2. Attacker replays this exact body and HMAC header to the same webhook endpoint but sets `Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate(request)` recomputes HMAC over `@raw_body` only [1](#0-0)  and it matches, since the body is unchanged.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
