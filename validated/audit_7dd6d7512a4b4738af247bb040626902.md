### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, and that HMAC is computed purely over the raw request body (`request.to_signable_string` returns `@raw_body`). The `shop` value that is handed to the app's `WebhookHandler#handle` comes from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field of the request. [4](#0-3) 

For a `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the `shop` attribute is read straight from the `shop-domain` header without any cryptographic binding to that body: [1](#0-0) 

`Registry.process` uses this unauthenticated `shop` value to build the `WebhookMetadata` that is passed to the host application's handler: [2](#0-1) 

Because a single `api_secret_key` (the app's `client_secret`) is shared across every shop that installs the app, any merchant who installs the app can generate a webhook payload with a body of their choosing and a *valid* HMAC computed with that shared secret (either by triggering their own real webhook, or, since HMAC only signs the body, by pairing any previously-observed valid `(body, hmac)` pair with an arbitrary `shop-domain` header). The library's `validate` check will pass (`OpenSSL.secure_compare` only checks the body-derived digest), yet `data.shop` handed to the handler can be set to a victim shop's domain. This breaks the identity binding: `shop authenticated by HMAC == shop attributed to the processed data`. The library's own documentation instructs developers to key downstream work off `data.shop` directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this un-bound field flows straight into tenant-scoped business logic. [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate (but malicious) merchant of the app — an unprivileged actor requiring no special access beyond installing the app once — can cause the host application to process webhook data under another shop's identity. Depending on how the host app uses `data.shop` (e.g., to select which tenant's session/access token to update, to attribute inventory/order data, or to trigger per-tenant side effects), this enables cross-tenant data corruption, unauthorized actions attributed to a victim shop, or leakage of information intended for a different tenant. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation only requires the attacker to install the app on their own store (a normal, unprivileged action for any Shopify merchant), obtain one legitimate `(body, HMAC)` pair from their own real webhook traffic, and replay it to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No possession of the `api_secret_key`, access token, or any privileged credential is required beyond what a normal merchant naturally receives.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the value that is HMAC-verified, or independently verify that the `shop-domain` header matches the shop associated with the specific webhook subscription/session before dispatching to the handler. At minimum, `to_signable_string` should incorporate the shop-domain header (as Shopify's server-side signature computation is documented to only cover the body, so this may instead need to be enforced by requiring hosts to independently authenticate `shop` against known installed shops before trusting `data.shop`), and the gem's documentation should explicitly warn that `data.shop` is unauthenticated and must be cross-checked against the app's own list of installed/authenticated shops before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, completing OAuth normally and enabling webhook delivery.
2. Attacker's shop receives (or attacker triggers) a real webhook, e.g. `orders/create`, with body `B` and a valid header `x-shopify-hmac-sha256: H = HMAC-SHA256(secret, B)`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and the same valid `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` and succeeds because `H` is valid for `B` regardless of the shop header.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)` and invokes the host app's handler, which now processes attacker-supplied data as though it originated from `victim-shop.myshopify.com`.
