### Title
`Auth::Oauth.begin_auth` builds the OAuth authorize URL from an unsanitized `shop` parameter, leaking `client_id` and `scope` to attacker-controlled hosts - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` never calls `Utils::ShopValidator.sanitize!` (or any equivalent check) on its `shop:` argument before using it to build `auth_route`. Every other credential-issuing flow in the gem (`ShopifyAPI::Auth::TokenExchange`, `ShopifyAPI::Auth::ClientCredentials`, `ShopifyAPI::Auth::RefreshToken`) explicitly sanitizes `shop` via `ShopValidator.sanitize!`, but `begin_auth` does not, so it will happily embed `Context.api_key` and `Context.scope` into a URL whose host is fully attacker-controlled.

### Finding Description
The claimed binding is: `auth_route.host == ShopValidator.sanitize!(shop)` (i.e., the destination host of the outgoing OAuth authorize redirect must always be a validated Shopify domain).

Tracing `begin_auth`: [1](#0-0) 
`query` is built with `client_id: ShopifyAPI::Context.api_key` and `scope: scope.to_s` (defaulting to `ShopifyAPI::Context.scope`, the app's real configured scopes) at lines 40-46, and `auth_route` is computed as `auth_base_uri(shop) + "/oauth/authorize?#{query_string}"` at line 49.

`auth_base_uri` is where the host is decided: [2](#0-1) 
For the normal (non-dev-server) case it returns `"https://#{shop}/admin"` directly from the raw `shop` string — no call to `Utils::ShopValidator.sanitize!` or `sanitize_shop_domain` anywhere in this method or in `begin_auth`.

Compare this to the sibling OAuth-adjacent flows, which do validate: [3](#0-2) 
`ShopValidator` is referenced in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but is absent from `oauth.rb` entirely (confirmed by search — no match for `ShopValidator` in that file).

`ShopValidator.sanitize!` exists and is designed exactly for this purpose — it only returns a host that resolves within `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or raises `Errors::InvalidShopError`: [4](#0-3) 
but `begin_auth` never invokes it.

Exploit flow: a host app following the documented pattern (`docs/usage/oauth.md`) reads `shop` from the `/install?shop=<value>` query string and passes it straight into `begin_auth(shop: shop, redirect_path: ...)`. If the app relies on the gem to validate `shop` before constructing the OAuth redirect (a reasonable assumption, since the gem does exactly this in `token_exchange.rb`/`client_credentials.rb`/`refresh_token.rb`), an attacker who sets `shop=evil.example.com` gets `begin_auth` to return `auth_route = "https://evil.example.com/admin/oauth/authorize?client_id=<real api_key>&scope=<real scope list>&redirect_uri=...&state=...&grant_options[]=..."`. If the host app then redirects the victim's browser to this URL (which is the entire purpose of `begin_auth`), the app's `client_id` and full requested `scope` list are disclosed to `evil.example.com`, which can render a convincing phishing/consent page and drive the victim through a forced-OAuth-completion flow back to the real app's `redirect_uri` with a `code`/`state` it controls or observed.

None of the gem's existing guards catch this: `Context.setup?` and `Context.private?` only check configuration state, not the `shop` value; `HmacValidator.validate` and the `state` cookie comparison only apply to `validate_auth_callback` on the *return* leg, not to the outbound URL construction in `begin_auth`; Sorbet's `sig` on `begin_auth` only enforces `shop: String`, not domain trust.

### Impact Explanation
Every call to `begin_auth` with an attacker-supplied `shop` string discloses the app's `client_id` (public but sensitive config) and its full `scope` list to a host chosen entirely by the attacker, and causes the victim's browser (if the host app blindly redirects) to be sent to that host with OAuth request parameters. This matches the "High - credential leakage into logs or error output" / SSRF-adjacent forced-OAuth-completion category: it is repeatable against arbitrary victims/merchants (one crafted `shop=` value per attempt), works against any app built on this gem that trusts the gem to validate `shop`, and provides reconnaissance and phishing amplification value without requiring any secret.

### Likelihood Explanation
No special preconditions beyond default gem configuration (`Context.setup?` with any `api_key`/`scope`) are needed. The attacker only needs to control the `shop` query parameter to whatever endpoint invokes `begin_auth`, which is exactly the documented entry point (`/install?shop=...`) per `docs/usage/oauth.md`. Cost is a single unauthenticated HTTP request; the flaw is deterministic and always reproducible since `auth_base_uri` performs no validation in the non-dev-server branch.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate and sanitize `shop` at the top of `begin_auth` (or inside `auth_base_uri`) using `Utils::ShopValidator.sanitize!(shop)`, raising `Errors::InvalidShopError` for untrusted hosts before any query parameters are built or `auth_route` is constructed — mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

def test_begin_auth_auth_route_host_is_always_trusted
  ShopifyAPI::Context.setup(
    api_key: "test_key",
    api_secret_key: "test_secret",
    scope: "read_products",
    host_name: "app.example.com",
    is_private: false,
    is_embedded: false,
    api_version: "unstable",
  )

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "my-shop.myshopify.com", redirect_path: "/auth/callback")
  host = URI.parse(result[:auth_route]).host
  assert_equal "my-shop.myshopify.com", host
  assert_equal ShopifyAPI::Utils::ShopValidator.sanitize!("my-shop.myshopify.com"), host

Currently, the first test fails: `begin_auth` returns a valid-looking hash with `auth_route` pointed at `https://evil.example.com/admin/oauth/authorize?...client_id=test_key&scope=read_products...` instead of raising, demonstrating that `client_id`/`scope` are sent to an unvalidated, attacker-controlled host.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
