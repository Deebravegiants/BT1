### Title
Webhook `shop` field is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`, `webhook_id`, `api_version`) directly from HTTP headers, but `to_signable_string` — the value the HMAC is computed and verified over — is only the raw request body. This breaks the binding `hmac_verified_bytes == bytes_the_app_acts_on`, mirroring the "duplicated locked splits" bug class where the check covers a different set of data than what is later relied upon.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`, etc.) and are never included in the signed bytes: [4](#0-3) [5](#0-4) 

After HMAC validation succeeds, `process` forwards `request.shop` (and topic/body) straight into `WebhookMetadata`, which the host app's handler uses to attribute the event to a tenant: [6](#0-5) 

Because the HMAC only proves "the body was signed with the app's secret" and says nothing about which shop it came from, an attacker who can obtain one valid `(raw_body, hmac)` pair for the app's secret (e.g., by installing the app on their own shop and capturing a webhook Shopify legitimately delivers to them — the HMAC secret is the app's `client_secret`, shared across all shops that installed that app, not per-tenant) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspects the header, so the forged request is accepted as authentic and delivered to the handler labeled with the victim's shop.

This is the same root cause pattern as the external report: a check (HMAC / locked-split loop) verifies one representation of the data (body / percent+beneficiary+allocator+projectId) while a different representation (headers / index-position) is what downstream logic actually consumes and trusts.

### Impact Explanation
This allows cross-tenant impersonation: an attacker-controlled webhook payload can be attributed to an arbitrary victim shop, without possessing that shop's access token or any of the app's genuinely privileged secrets. Depending on how the host app's webhook handler uses `data.shop` (e.g., writing/deleting records keyed by shop, triggering uninstall/billing logic, updating settings), this can lead to cross-tenant data corruption or state manipulation attributed to a shop the attacker doesn't control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to obtain one legitimately-signed `(body, hmac)` pair, which is achievable by any unprivileged user who can install the app on a shop they control (a normal, unprivileged action for a public app) and capture the webhook Shopify sends them. No access token, `client_secret`, or victim credentials are needed — only a header substitution on replay. This is a realistic, low-effort exploit path through the gem's own webhook verification logic.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise validate `request.shop` against a source of truth (e.g., the currently active/expected session or a registered webhook_id → shop mapping) before invoking the handler, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `raw_body` against the secret — it succeeds. [1](#0-0) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never touched that shop, and processes it as if it were a legitimate event from the victim.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
