## Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, but then trusts the `shop` (and `topic`) values taken from unauthenticated HTTP headers when dispatching the webhook to the host application's handler. Because those header values are never bound into the HMAC computation, an attacker who controls one Shopify store (and can therefore trigger a legitimately-signed webhook for that store) can replay the exact same signed body while substituting the `x-shopify-shop-domain` header to point at a different, victim shop. The signature check still passes, and the handler is invoked believing the event originated from the victim shop.

### Finding Description
`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body bytes: [2](#0-1) 

The `shop` value used by `Registry.process` to build `WebhookMetadata` (which the host app treats as the tenant identifier for the event) comes from a header that is parsed but never part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately dispatches using the unauthenticated `request.shop`: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop the handler acts on`

But since the HMAC is computed only over `@raw_body` (never over `shop-domain`, `topic`, `webhook-id`, or `api-version` headers), this binding does not exist. The `api_secret_key` used to compute the HMAC is shared across all shops installed on a given app (it is the app's client secret, not a per-shop secret), so a valid signature only proves "some webhook payload was HMAC-signed with this app's secret" — it proves nothing about which shop the payload is actually for. An attacker who owns/controls their own installed shop can capture a legitimately-signed webhook body+HMAC pair for their store, then re-send an HTTP request to the app's webhook endpoint with the identical body/HMAC but a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value naming a victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` calls the handler with `shop: request.shop` equal to the victim's domain.

### Impact Explanation
This breaks the tenant isolation the host application relies on: the app's webhook handler, and any storage/business logic keyed off `WebhookMetadata#shop`, will process attacker-controlled webhook content (order data, product data, app-uninstall notices, etc., depending on topic) as if it belongs to a different, victim shop. Depending on the handler's logic (e.g. writing state keyed by shop, revoking access, updating merchant data), this can result in cross-tenant data corruption/impersonation — a Critical-impact issue per the given rubric (cross-tenant access), achievable by any unprivileged internet user who has (or creates) their own Shopify development/trial store on the same app.

### Likelihood Explanation
Exploitation requires only that the attacker operate one shop that has installed the target app (freely obtainable via a Shopify development store) and be able to trigger any webhook topic for that shop (many topics are triggered by ordinary shop actions the merchant/attacker fully controls, e.g. `orders/create`, `app/uninstalled`), then replay the HTTP request to the app's webhook endpoint with a modified shop header. No access to `api_secret_key`, tokens, or victim credentials is required, making this a directly and cheaply exploitable path through this gem's own webhook-processing code.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated material before trusting it:
- Include the `shop-domain` (and `topic`) header values in the string that is HMAC-verified (matching Shopify's guidance to treat headers as trusted only after being cryptographically tied to the payload), or
- Require the host application to independently verify that `request.shop` matches an expected/registered shop for the specific webhook subscription (e.g., cross-check against the shop that owns the specific `webhook_id`), rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid and correctly signed with the app's `api_secret_key`.
2. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally an interesting `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and successfully matches the (unmodified) signature.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, so the host app processes attacker data under the victim's tenant identity. [4](#0-3) [5](#0-4)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
