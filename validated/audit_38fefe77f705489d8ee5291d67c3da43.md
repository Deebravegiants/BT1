This confirms the analog is grounded in the gem's own code, not host-application misuse. `ShopifyAPI::Webhooks::Request#hmac` is computed only over `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that `Utils::HmacValidator.validate(request)` passes and then forwards `request.shop` unchanged into `WebhookMetadata` for the handler [3](#0-2) . The docs confirm the shop domain is exposed to and trusted by the app's handler as `data.shop` [4](#0-3) .

### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature Shopify sends only authenticates the *body bytes*. The `shop`, `topic`, `webhook_id`, and `api_version` values are parsed straight from HTTP headers that are never included in the signed content. `Registry.process` accepts the request as long as the body/HMAC pair matches, then hands the untrusted `shop` header directly to the app's webhook handler as `WebhookMetadata#shop` — the exact field host apps are told to use to identify which merchant/tenant the event belongs to.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e. the authenticated shop identity should be cryptographically bound to the payload that was verified. Instead the gem only enforces `hmac == HMAC(secret, body)` [1](#0-0) , while `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [5](#0-4) .

`Utils::HmacValidator.validate` only ever compares the computed signature against `verifiable_query.to_signable_string`, which for webhook requests is the raw body — it never looks at `shop` or `topic` [6](#0-5) . Once that check passes, `Registry.process` builds `WebhookMetadata` straight from the unauthenticated header value and calls the handler [3](#0-2) .

This is the same bug class described in the external report: a value that is *acted upon* (there, the vault share price; here, the shop identity) is not the same value that was *cryptographically bound* by the protection mechanism (there, the deposit/proceeds formula; here, the HMAC). An unprivileged internet user who legitimately owns any store with the app installed will receive genuine `(body, hmac)` pairs signed with the app's real `api_secret_key` for their own shop. Because `shop` isn't part of the signed content, that same valid `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant identity binding without requiring knowledge of `api_secret_key`, an access token, or any credential belonging to the victim. The handler receives `WebhookMetadata#shop` pointing at the victim tenant while `data.body`/`topic` come from the attacker's own genuinely-signed webhook, so any host application that trusts `data.shop` to select which tenant's data/session to write to, invalidate, or act on (exactly the pattern shown in the gem's own documentation example, `shop_domain: data.shop`) can be tricked into cross-tenant data corruption or state changes attributed to a shop the attacker doesn't control. This satisfies the "cross-tenant access" Critical impact category, since the crossing happens purely through the gem's own webhook-verification logic.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free/trial) merchant of an app using this gem to receive at least one real webhook of a topic they want to abuse, then replay it with a modified `shop-domain` header — no interception, no secret, no privileged account, and no host-application misconfiguration required. The validation gem itself performs no binding between the signed body and the identity headers, so this is reachable purely through documented `Registry.process` usage [7](#0-6) .

### Recommendation
Extend `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` (or `HmacValidator`) so that the `shop`, `topic`, and `webhook_id` header values are included in the data that's verified against the HMAC, or otherwise cross-check the header-derived `shop` against a value independently known to be correct (e.g., a session already established for that tenant) before dispatching to handlers.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on their own store "attacker-shop.myshopify.com"
# and captures a real webhook delivery Shopify sends them:
real_body = '{"id": 123, "note": "hello"}'
real_hmac_header = "<base64 HMAC Shopify computed with the app's real api_secret_key>" # attacker did not compute this themselves

# Replay to the app's public webhook endpoint, only changing the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header,   # still valid! HMAC only signs the body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-controlled",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation (Utils::HmacValidator.validate only checks real_body/real_hmac_header)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(real_body), ...))
```
