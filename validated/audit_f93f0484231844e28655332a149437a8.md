### Title
Borrower can brick `liquidate` and `clean_bad_debt` on their own account by breaking the Aquarius LP price read of one collateral leg — (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
Every risk-sensitive controller path computes `calculate_account_risk_totals` over **all** of an account's supply and debt positions, and each price is fetched fail-closed through `Context::fetch_prices` → `price-aggregator.prices` → `engine::resolve` → `force`, which panics on any unusable outcome (stale, deviation, non-positive price, sanity-band violation, or a provider-level error). If an account holds even a dust-sized collateral leg priced via an `AquariusLp` source, any failure in that pool's reads — e.g., pool value falling below `min_pool_value_wad` (`InsufficientAquariusLiquidity`), or a reserve/share/decimals read failing (`NoLastPrice`) — makes `liquidate`, `clean_bad_debt`, `withdraw`, and `update_account_threshold` revert for the entire account. This is the same bug class as the Y2K report: precisely when the protocol needs the emergency path (liquidation/bad-debt cleanup), the hard price gate makes it impossible.

### Finding Description
- `socialize_bad_debt` calls `risk::calculate_account_risk_totals(env, &mut cache, &account.supply_positions, &account.borrow_positions)` before the dust/insolvency gate (`contracts/controller/src/positions/liquidation/mod.rs:222-227`), and `liquidate` builds its plan over the same totals.
- `Context::fetch_prices` calls the aggregator's fail-closed `prices` entrypoint; `cached_price` panics if a feed is missing (`contracts/controller/src/context.rs:142-158`).
- `Outcome::failure` returns `InvalidPrice` for `price_wad <= 0` and `SanityBoundViolated` outside the band, and `force` panics on any failure (`contracts/price-aggregator/src/engine.rs:139-145`, `181-184`).
- The Aquarius provider hard-fails when `pool_value_wad < lp.min_pool_value_wad` (`InsufficientAquariusLiquidity`) or when `aquarius_pool_reserves_call`/`aquarius_total_shares_call`/decimals reads fail (`NoLastPrice`) (`contracts/price-aggregator/src/providers/aquarius.rs:90-93`, `120-122`).
- The repository's own regression test proves the mechanism end-to-end: a stale-price dust leg on an underwater account makes both `liquidate` and `clean_bad_debt` revert with `PRICE_FEED_STALE` (`tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs:36-40`).

### Impact Explanation
A borrower can supply a position whose collateral set includes an Aquarius-LP-priced token, then — using only their own Aquarius liquidity — withdraw enough liquidity (or otherwise push the pool below `min_pool_value_wad`, or drain reserves so a read fails) so that `read` returns `Err(InsufficientAquariusLiquidity)`/`Err(NoLastPrice)`. From that moment, the account is completely unliquidatable and cannot be bad-debt-cleaned, because both entrypoints panic during the price fetch before any health-factor or seizure logic runs. Meanwhile the borrowed assets stay with the attacker; suppliers bear the unbacked debt for the duration — protocol insolvency / temporary freezing of the liquidation mechanism, matching the report's "users who buy insurance receive nothing when they should." Unlike the stale-leg test, this variant requires no third-party oracle failure: the failure is induced unilaterally through permitted Aquarius pool interaction, and `min_pool_value_wad` enforcement is exactly what turns a shallow pool into a full revert instead of a degraded price.

### Likelihood Explanation
Medium. The attack requires: (a) a listed spoke market whose oracle's first source is `PriceSource::AquariusLp`; (b) an Aquarius pool shallow enough that the attacker can push its WAD value below `min_pool_value_wad` or break a pool read using their own liquidity (feasible for pools where the attacker controls a large share of LP, especially combined with a flash loan for transient depth changes — though reads occur post-callback so persistence is needed during the target transaction). Owner/third-party supply cannot plant new legs on a victim's account, so the attacker must act on their own account — which is sufficient, since making one's own account unliquidatable while holding borrowed funds is the profitable direction. Requires governance to have listed an LP-priced collateral, so likelihood is configuration-dependent.

### Recommendation
Do not let a single leg's price failure veto account-level emergency paths. Options: treat an unresolvable collateral leg as zero-valued for the *collateral* side of the risk total (conservative: understates collateral, so liquidation proceeds against resolvable legs), or allow `liquidate`/`clean_bad_debt` to skip collateral legs whose price status is invalid rather than panicking — mirroring how the soft `quotes`/`PriceStatus` path already distinguishes failures (`engine.rs:196-215`). At minimum, debt-side failures should still block (repayment must be priced), but collateral-side failures should degrade to exclusion/zero-weight, never to a hard revert of the whole cleanup path.

### Proof of Concept
1. Governance lists hub asset `LP` (Aquarius share token of pool P) as collateral in a spoke, oracle `PriceSource::AquariusLp{pool: P, ..., min_pool_value_wad: V}`.
2. Attacker: `supply(caller=attacker, account_id=0, spoke_id=S, assets=[(LP, x)])`; `borrow(account_id, borrows=[(STABLE, d)])` with `x` sufficient.
3. Attacker removes their liquidity from P (or swaps P's reserves down) until `price_wad * total_shares / share_unit < V`. Any `liquidate(liquidator, account_id, debt_payments, seize_mode)` now reverts inside `aquarius::read` with `InsufficientAquariusLiquidity` → `resolve` → `force` panic. `clean_bad_debt` reverts identically in `calculate_account_risk_totals`.
4. The account holds unseizable debt; the attacker can keep the pool shallow as long as needed. The test `audit_liquidate_and_clean_bricked_by_unpriceable_dust_leg` demonstrates steps 3–4's revert shape with a stale leg substituted for the drained pool (`tests/test-harness/tests/controller/audit_liquidate_and_clean_stale_leg.rs`).
