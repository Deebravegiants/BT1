## Title
Webhook `shop` and `topic` headers are trusted without being covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC check only authenticates the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are handed to the handler as if verified, breaking the binding between "the bytes that were HMAC-verified" and "the shop/topic the handler acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from request headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then immediately trusts the header-derived `topic`/`shop` to dispatch and construct `WebhookMetadata` for the handler: [3](#0-2) 

The `Utils::HmacValidator.validate` call only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), never the headers: [4](#0-3) 

This is the same bug class as the analog report: a value that is *acted on* (`shop`, used as the tenant/session key downstream; `topic`, used to select the handler) is not covered by the integrity check (`dropBoostQueue`/HMAC), while a different, unrelated value (`raw_body`/`dropBoostQueue.balance`) is checked instead. The gem's own documentation asserts the opposite — that `process` "will verify the request did indeed come from Shopify" — so this is not a case of the host app ignoring documented behavior; the gem's verification routine itself fails to bind the claimed-authenticated fields.

Since Shopify signs webhooks with a single app-wide `api_secret_key` (not a per-shop secret), any shop that has installed the app receives legitimately HMAC-signed webhook deliveries. An attacker who controls such a shop (an "unprivileged" tenant relative to the target) can capture one valid `(raw_body, hmac)` pair delivered to their own endpoint and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain (and/or the topic header changed). The HMAC still validates because it only checks the untouched body, but `request.shop` / `request.topic` used by the handler now falsely claim to originate from the victim shop/topic.

### Impact Explanation
This breaks tenant isolation: the app's webhook handler (as documented, using `data.shop` to key session lookups, job enqueuing, or GDPR-style compliance topics like `shop/redact`/`customers/redact`/`customers/data_request`) can be made to act on the wrong shop's identity while the actual payload content is attacker-influenced/replay-controlled. This is a cross-tenant access issue, since data intended for/verified from one merchant can be attributed to another merchant purely by header manipulation, with no dependency on obtaining the victim's access token or secret.

### Likelihood Explanation
High. Any user who can install the app on their own store (a normal, unprivileged onboarding flow) will legitimately receive properly signed webhooks and can replay them with modified `shop-domain`/`topic` headers, since nothing in `Request` or `Registry.process` binds those headers to the signed body.

### Recommendation
Compute the HMAC over the header-derived security-relevant fields (at minimum `shop` and `topic`) concatenated with the body, or otherwise cryptographically bind them (e.g., require the app to independently confirm `shop` against a known/expected value tied to the webhook subscription, or use per-shop webhook secrets) before trusting them in `WebhookMetadata`. At minimum, update `Registry.process` to fail closed if `shop`/`topic` cannot be verified, and correct the documentation to state that only the body is authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Topic: orders/create`.
2. Attacker resends the identical body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC.
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` and calls the handler, which acts as though the (attacker-controlled) event belongs to `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
