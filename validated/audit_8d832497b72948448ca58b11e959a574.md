### Title
Webhook Shop/Topic Identity Spoofing — HMAC Signature Covers Only `raw_body`, Not the `shop-domain`/`topic`/`webhook-id` Headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` authenticates nothing but the JSON body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all taken from unauthenticated HTTP headers — are never part of the signed data, yet `Registry.process` trusts `request.shop` as the tenant identity when dispatching to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` purely from request headers: [1](#0-0) 

`to_signable_string` — the only thing the HMAC actually protects — is `@raw_body` alone: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the received signature — for `Request`, that signable string is `raw_body` only: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally passes `request.shop` (the unauthenticated header value) into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

The test suite confirms this design: the HMAC fixture is computed strictly over the body (`"{}"`), independent of the `shop`/`topic` headers used in the same request: [5](#0-4) 

**Identity binding broken:** the gem implicitly asserts `hmac_valid(raw_body) ⇒ shop_header_authentic`, but the equality that actually holds is only `hmac_valid(raw_body) ⇒ raw_body_authentic`. `shop`, `topic`, `webhook_id`, and `api_version` are bytes that are *acted on* (used to select and parameterize the handler call) but are *not covered by the HMAC*.

Because many webhook topics have body payloads that carry no shop-specific data at all (e.g. `app/uninstalled` bodies are frequently `{}`, and other topics' JSON payload doesn't repeat the shop domain), the HMAC signature for a given payload is often shop-independent — the same `(raw_body, hmac)` pair is valid regardless of which shop header accompanies it, since the header plays no role in the signature computation.

### Impact Explanation
An unprivileged actor who can capture one legitimate, HMAC-valid webhook delivery (e.g., from their own store, or from any request that transits through/near the app's public webhook endpoint) can replay that exact `(raw_body, hmac-sha256)` pair while substituting an arbitrary `x-shopify-shop-domain` header pointing at a victim tenant. `HmacValidator.validate` will still return `true` because it only checks `raw_body` against the secret, and `Registry.process` will hand the forged shop identity straight to the registered `WebhookHandler`. If the host application uses `WebhookMetadata#shop` to select which tenant's data to create/update/delete (the documented and expected usage pattern), this enables cross-tenant data injection/corruption — writing or triggering actions attributed to a shop the attacker doesn't own. This matches the Critical/High bar of "cross-tenant access" via a broken identity binding.

### Likelihood Explanation
Reaching this requires no credentials beyond capturing a single valid webhook body/HMAC pair, which any merchant using the app can trigger for their own shop (e.g. via `app/uninstalled`, or a generic topic whose body is empty/static). The attacker only needs to replay a POST to the app's known public webhook endpoint with a modified `shop-domain` (and/or `topic`) header — no interaction with `api_secret_key`, access tokens, or privileged accounts is needed. This is exploitable by any internet user who can reach the app's webhook route.

### Recommendation
Include `shop`, `topic`, and ideally `webhook_id`/`api_version` in the signable string (or otherwise cryptographically bind them, e.g. via an HMAC over a canonicalized concatenation of header values + body), mirroring how `AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, `timestamp` together for OAuth callback validation: [6](#0-5) 

At minimum, document prominently that `shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for tenant-sensitive decisions without additional application-side verification (e.g., cross-checking against a known list of installed shops).

### Proof of Concept
1. App installs webhook handler for topic `app/uninstalled` (body typically `{}`).
2. Attacker's own shop triggers this webhook; attacker captures the raw POST: headers `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid-hmac-of-"{}">`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `{}`.
3. Attacker resends the identical body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` (raw_body only) are unaffected by the header change; `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) still returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the event came from the victim's shop.

          received_signature = verifiable_query.hmac
