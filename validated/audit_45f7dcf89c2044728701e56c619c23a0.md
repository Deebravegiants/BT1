Confirmed: both `_fillSameChain` (`IntrinsicIntents.sol:101-106`) and `_fillCrossChain` (`ExtrinsicIntents.sol`) use `safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` for the output side without ever re-measuring `beneficiary`'s actual received balance, unlike the input side in `IntentGatewayV2.sol:230-329`, which explicitly measures `balanceOf` before/after to be fee-on-transfer safe. ### Title
Fee-on-transfer output tokens let a solver under-deliver to the beneficiary while redeeming the full escrowed input - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntentGatewayV2`'s input-side transfer logic (`placeOrder`) is fee-on-transfer aware: it snapshots `balanceOf` before and after every inbound transfer and mutates `order.inputs[i].amount` to the actual amount received [1](#0-0) . The output side of fill logic has no equivalent check: `_fillSameChain` and `_fillCrossChain` compute a nominal `beneficiaryTotal`/`totalRequired + beneficiaryShare` and call `safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)`, then unconditionally treat the fill as complete for that nominal amount.

### Finding Description
In `_fillSameChain`, the code transfers `beneficiaryTotal` from the solver to the beneficiary via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)` [2](#0-1) , and then, when `amountFilled == totalRequired`, releases the *entire* escrowed input amount to the solver via `_withdraw` regardless of what the beneficiary actually received [3](#0-2) .

The same pattern occurs in `_fillCrossChain`: it uses `safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` and then dispatches a `RedeemEscrow` request for the *full* `order.inputs`, again with no verification of what the beneficiary received [4](#0-3) .

If `order.output.assets[i].token` is a deflationary/fee-on-transfer ERC20 (a token type the input path already anticipates and explicitly tests for, per `FeeOnTransferToken` in the test suite [5](#0-4) ), the beneficiary receives less than `totalRequired` even though the solver's nominal transfer amount satisfies the check `remaining == 0`/`amountFilled == totalRequired`. The order is then marked fully filled, `_execute` runs any attached output calldata assuming full payment, and the solver is paid out the entire escrowed input — effectively letting the solver systematically underpay users whenever the requested output token has a transfer fee, or letting a malicious solver exploit rounding/fee edge cases to extract more value from escrow than delivered.

This is the direct structural analog of the reported YearnProvider issue: on one side of the same contract the code correctly measures actual-received balances to be robust to non-standard token semantics, while on the other side it blindly trusts the nominal transfer amount, creating an inconsistency that a fee-bearing token exposes as fund loss rather than the original DoS.

### Impact Explanation
Users placing orders with a fee-on-transfer output token receive strictly less than they were promised (`totalRequired`), while the solver still collects the full escrowed input value as if the order were fully satisfied — a direct value transfer from the beneficiary/order-creator to the solver with no honest recourse (the order is marked filled/`isFullyFilled = true`, so the user cannot re-claim the shortfall). This is a fund-loss condition reachable by any unprivileged solver calling `fillOrder`.

### Likelihood Explanation
Likelihood is proportional to adoption of any output token that charges a transfer fee (deflationary tokens, some stablecoin implementations with rebasing/blacklist fee logic, etc.). Since the protocol does not restrict `order.output.assets` to a fixed allowlist of "safe" tokens at the contract level and the input path already demonstrates first-class support/testing for such tokens, it is reasonably likely such tokens will be used as outputs, and any solver filling such an order (maliciously or not) triggers the shortfall.

### Recommendation
Mirror the input-side pattern on the output/fill side: snapshot `beneficiary`'s (and protocol's) token balance immediately before the `safeTransferFrom` calls in `_fillSameChain` and `_fillCrossChain`, and use the actual balance delta to determine `fillAmount`/`amountFilled`/whether `remaining` has been satisfied, rather than trusting the nominal `beneficiaryTotal`. Only mark the pair as fully filled, execute `_execute`, and redeem the full input escrow once the delta confirms the beneficiary actually received `totalRequired`.

### Proof of Concept
1. Order creator places an order requesting `1000` units of `FOT` (a 1% fee-on-transfer token) as output, escrowing `1000 USDC` as input.
2. Solver calls `fillOrder` with `options.outputs[0].amount = 1000` `FOT`. `safeTransferFrom(solver, beneficiary, 1000)` executes, but due to the 1% fee the beneficiary only receives `990` `FOT`.
3. Because `fillAmount = totalRequired = 1000` was used for accounting (not the beneficiary's actual received `990`), `amountFilled == totalRequired`, so the order is marked fully filled: `_execute` runs, `OrderFilled` is emitted, and `_withdraw`/`RedeemEscrow` releases the **full** `1000 USDC` escrow to the solver.
4. Net result: beneficiary is short `10 FOT` (1%) relative to what they were promised, while the solver still redeems 100% of the input escrow — see the parallel, correctly-handled input-side test `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` [6](#0-5)  for the balance-delta pattern that is missing on the fill/output path.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
