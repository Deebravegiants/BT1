### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC computed by `HmacValidator` authenticates the request body alone. The `shop` (`shop-domain` header), which `Registry#process` uses to attribute the webhook to a tenant, is never covered by that signature. Any unprivileged internet user who can obtain their own genuinely-signed webhook (by installing the app on their own store) can replay that body+HMAC pair while substituting an arbitrary `shop-domain` header, and the library will accept it as coming from that other shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Specifically: [2](#0-1) [3](#0-2) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` (what gets HMAC'd) is only `@raw_body`. `HmacValidator.validate_signature` computes the signature purely from `to_signable_string`: [4](#0-3) 

`Registry#process` validates the HMAC and then trusts `request.shop` as the tenant identity to dispatch to the handler: [5](#0-4) 

The equality the library implicitly relies on is:
`shop bound by HMAC == shop used for tenant dispatch`

But in reality:
`shop bound by HMAC == "" (nothing) ≠ shop used for tenant dispatch (attacker-controlled header)`

Since the app's webhook secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is shared across *all* shops that install the app — not scoped per merchant — any user who installs the app on their own (free/dev) store legitimately receives real webhooks with valid HMACs for arbitrary bodies of their choosing (e.g., they can trigger `orders/create`, `customers/update`, etc. themselves). They can then replay the exact `(raw_body, hmac)` pair to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` hands the forged victim shop identity straight to the app's webhook handler.

### Impact Explanation
This breaks the tenant boundary: data that actually originated from the attacker's own store is processed by the host application as if it came from a different, victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/update per-shop records, sync inventory, trigger financial actions, or write into the victim's tenant data), this enables cross-tenant data injection/corruption — a cross-tenant access vulnerability.

### Likelihood Explanation
High. The only requirement is the ability to install the app on any store (an unprivileged action available to anyone, e.g. via a Shopify partner/dev store), then send one crafted HTTP request to the app's public webhook endpoint with a modified header. No access token, `client_secret`, or privileged account is needed — the `client_secret` is never exposed or required by the attacker in this path.

### Recommendation
Bind the shop identity into the authenticated payload before trusting it: either include the `shop-domain` (and `topic`/`webhook-id`) header values in the HMAC-signed content (matching what `to_signable_string` protects), or independently verify that the shop asserted in the header is one that is actually installed/registered for this app instance before dispatching to handlers, rather than trusting the header value alone once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify store (`attacker.myshopify.com`), which is a normal, unprivileged action.
2. Trigger a real webhook (e.g., `orders/create`) from that store; Shopify sends the app a request with headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, and a JSON body, HMAC-signed with the app's shared `client_secret`.
3. Capture the raw body and the `x-shopify-hmac-sha256` value.
4. Resend the identical body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` (via `HmacValidator.validate`) accepts the request because the HMAC still matches the unchanged raw body, and the handler executes with `shop: "victim-shop.myshopify.com"`, as shown in: [6](#0-5)
