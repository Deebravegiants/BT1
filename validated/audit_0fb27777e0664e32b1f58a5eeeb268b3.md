### Title
Push-model escrow settlement in IntentGatewayV2 permanently freezes escrowed funds when the fixed beneficiary is blocklisted - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s escrow settlement (`_withdraw`) — used for both `RedeemEscrow` (solver payout) and `RefundEscrow` (user refund) — pushes tokens directly to a `beneficiary` address baked into the cross-chain settlement message at fill/cancel time, using `IERC20.safeTransfer`. Exactly like the original Cooler.sol report, this is a push (not pull) settlement model: if the fixed beneficiary is later on a token's compliance blocklist (e.g. USDC/USDT `blacklist`), the transfer reverts and the escrowed input tokens can never be released, since the beneficiary address is immutable once the `WithdrawalRequest` is committed.

### Finding Description
`_withdraw()` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 451-485) decrements escrow accounting and then unconditionally pushes tokens to `beneficiary` via `safeTransfer`: [1](#0-0) 

For cross-chain orders, the beneficiary that ends up in the `WithdrawalRequest` is fixed at the moment the message is dispatched:
- On `RedeemEscrow` (fill), `beneficiary = msg.sender` — the solver's own address — is baked into the message body and sent to the source chain: [2](#0-1) 
- The message travels through the ISMP host, which calls `onAccept()` → `withdraw()`/`_withdraw()` on the source chain to release the escrowed input tokens to that same solver address.

Because `IERC20.safeTransfer` reverts on failure, if the token used has a transfer-time blocklist (USDC/USDT-style) and the solver's `beneficiary` address becomes blocklisted between fill-time and settlement-time (or is already blocklisted and the solver doesn't realize it, or the issuer sanctions it afterward), `_withdraw` reverts. The revert propagates up through `onAccept`, and `EvmHost.dispatchIncoming` deletes the request receipt to allow a retry: [3](#0-2) 

However, retrying delivers the exact same `WithdrawalRequest` with the exact same immutable `beneficiary`, so the transfer fails identically every time. There is no mechanism in `IntentGatewayV2`/`IntentsBase` to redirect the beneficiary or pull the escrow to any other address — the input tokens the user already escrowed (and which the solver already redeemed by delivering output tokens to the user) are stuck in the gateway contract with no recovery path, since the order is only "unstuck" by a successful `safeTransfer` to that one address.

This is the same root-cause bug class as the Cooler.sol report: settlement funds are pushed directly to a party-chosen address baked into on-chain state, rather than escrowed for pull-based claiming, so a blocklist event on that address (regardless of who controls or triggers it) permanently freezes the funds with no fallback.

### Impact Explanation
Once a solver has filled a cross-chain order — delivering output tokens to the user on the destination chain — the corresponding `RedeemEscrow` settlement becomes the solver's only path to recover the user's escrowed input tokens on the source chain. If the solver's beneficiary address is or becomes blocklisted on the input token, that escrow is permanently locked in the `IntentGatewayV2` contract: the solver has already paid out and can never be repaid, and the tokens are unreachable by any other function (no admin sweep of a non-cancelled, non-finalized order; `_sweepDust`/`SweepDust` only handles protocol dust, not live per-order escrow). This is a concrete, permanent freezing of user/solver funds reachable from a normal, permissionless cross-chain fill — a single dispatched settlement message.

### Likelihood Explanation
Any solver who fills a cross-chain order chooses their own receiving address at fill time; USDC/USDT-style blocklisting is a real, externally-triggered event outside the protocol's control, and once triggered there is no recovery mechanism at all in this contract. The condition doesn't require any privileged action — a single `fillOrder` call sets the immutable beneficiary, and a subsequent compliance action on that address is sufficient to permanently strand the escrow.

### Recommendation
Change `_withdraw` from a push model to a pull-based/claimable model for escrow releases: rather than transferring immediately to the embedded `beneficiary`, credit an internal claimable balance keyed by `(beneficiary, token)` that the beneficiary (or a designated alternate recipient they control) can withdraw later via a separate `claim()` call. This mirrors the Cooler.sol recommendation and removes the single point of failure where one address's blocklist status can permanently freeze already-committed settlement funds.

### Proof of Concept
1. User places a cross-chain order on chain A, escrowing input token `T` (a blocklist-capable token such as USDC) in `IntentGatewayV2`.
2. Solver fills the order on chain B (`fillOrder` → `_fillCrossChain`), delivering the required output tokens to the user's `beneficiary`, and dispatches a `RedeemEscrow` message with `beneficiary = msg.sender` (the solver's own address) back to chain A: `evm/src/apps/intentsv2/ExtrinsicIntents.sol:207-213`.
3. Before the relayer delivers the settlement proof to chain A, `T`'s issuer blocklists the solver's address (an event entirely outside the protocol's control).
4. The relayer submits the proof; `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept` → `_withdraw`, which calls `IERC20(T).safeTransfer(solver, amount)` — this reverts because `T` blocks transfers to the solver.
5. `EvmHost.dispatchIncoming` deletes the request receipt so the message "can be retried" (`evm/src/core/EvmHost.sol:809-816`), but every retry submits the identical `WithdrawalRequest` with the same immutable `beneficiary`, so the transfer fails identically forever.
6. The user's escrowed `T` is now permanently stuck in `IntentGatewayV2` — the solver already paid out the output side and has no way to reroute or claim the escrow to a different, non-blocklisted address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
