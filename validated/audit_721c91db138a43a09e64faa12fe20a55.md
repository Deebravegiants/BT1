## Finding: Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via signature replay

### Title
Webhook shop/topic identity fields excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and attribute the event to a specific merchant are taken from unauthenticated HTTP headers that are never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`/`#topic`/`#webhook_id` are read straight from HTTP headers with no cryptographic binding to the signed body [2](#0-1) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` [3](#0-2) , so it proves the body is untampered but proves nothing about the header values. `Registry.process` nonetheless uses the unauthenticated `request.shop` (and `topic`/`webhook_id`) to build the `WebhookMetadata` handed to the app's handler after only checking the body HMAC [4](#0-3) .

The identity binding that should hold is:
`shop attributed to the webhook event == shop whose secret produced the signature`

but the code only enforces:
`HMAC(body, secret) == received_hmac`

with `shop` (a header) entirely outside that equality.

### Impact Explanation
Because the `shop-domain` header is never bound to the signature, anyone who can obtain one valid `(body, hmac)` pair for their own tenant (trivial — an attacker can register their own Shopify development store and receive a legitimately signed webhook to their own endpoint) can resend that exact body+HMAC while substituting an arbitrary `shop-domain` header. `Registry.process` will accept it (the body HMAC still validates) and dispatch it to the app's handler tagged with the attacker-chosen shop. Any app that uses `WebhookMetadata#shop` to select which merchant's records to update, gate access, or key session/data lookups will then apply the attacker-controlled payload to another tenant's data — a cross-tenant integrity/access issue.

### Likelihood Explanation
Likelihood is high for any app that exposes a public webhook endpoint (the documented pattern) and trusts `data.shop` for tenant routing, as shown in the gem's own test/usage patterns [5](#0-4) . The attacker only needs their own Shopify store to legitimately obtain a signed body/HMAC pair, then a single unauthenticated HTTP POST to replay it with a forged `shop-domain` header.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signed material (or otherwise cryptographically bind them to the body/HMAC), or require verification of Shopify's known webhook source before trusting header-derived tenant identity in `Registry.process`.

### Proof of Concept
1. Attacker sets up their own Shopify store/app and subscribes to a webhook to their own publicly reachable endpoint, capturing a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair as constructed in [6](#0-5) .
2. Attacker replays the identical `raw_body` and `hmac` header to the same endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header without complaint (`shop` is just read from headers) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the signature only covers the untouched body [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload/signature actually belongs to the attacker's own store, breaking the shop-identity binding.
