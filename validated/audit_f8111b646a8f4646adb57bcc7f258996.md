## Finding

Looking at how the gem validates and dispatches webhooks, the shop identity that the host application acts on is not covered by the HMAC that authenticates the request.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`), completely separate from the bytes that are HMAC-verified: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the raw body), never incorporating `shop`: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` — the unauthenticated header value — to the app's handler as the tenant identity for the webhook payload: [5](#0-4) 

### Title
Webhook `shop` identity is not bound to the HMAC that authenticates the payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw body only, then passes the caller-supplied `shop-domain` header straight to the app's handler as the tenant identity. The gem never checks that the shop the HMAC was computed for (there is no such binding — the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app) matches the shop asserted in the header used to route/attribute the data.

### Finding Description
The equality that should hold is: `shop used to authorize/authenticate the webhook == shop the payload is attributed to`. Instead, the gem authenticates only `HMAC(raw_body, api_secret_key)` and attributes the event to whatever `shop` header value is present, which is not part of the signed material. Because `api_secret_key` is one shared app secret across all merchants (not per-tenant), any shop that installs the public app can trigger genuine webhook deliveries to a listener they control, capture a valid `(raw_body, hmac)` pair, and then submit that exact `(raw_body, hmac)` pair to the target app's webhook endpoint while substituting the `shop-domain` header for a different, victim merchant. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain, so the attacker-controlled body content gets attributed to and processed for a shop the attacker doesn't operate.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook ingestion: an entity that only controls its own (free/trial) shop installation can inject events attributed to another merchant's tenant, i.e., cross-tenant access/data injection, without ever needing the target's credentials.

### Likelihood Explanation
Any user can install a public Shopify app on their own development/trial store (no special privilege needed), receive genuine webhook deliveries with a valid HMAC for a body they substantially control (e.g., via order/product content), and replay that request against the app's registered webhook endpoint with a modified `shop-domain` header. No secret material needs to be known or brute forced.

### Recommendation
Bind the shop identity into the authenticated material before it is trusted: include `shop` (and ideally `topic`/`webhook_id`) in the value that `HmacValidator` verifies, or otherwise require the caller to cross-check `request.shop` against a shop the app has an active, previously-established offline session/token for before invoking the handler, so the identity acted upon is provably the same one the HMAC was computed for.

### Proof of Concept
1. Attacker installs the target public app on `attacker.myshopify.com` (own shop) and registers a webhook (e.g., `orders/create`) to a listener they control.
2. Attacker creates an order with attacker-chosen content, receives Shopify's webhook POST containing `raw_body` and a valid `X-Shopify-Hmac-Sha256` (computed with the app's shared `api_secret_key`).
3. Attacker replays this exact `raw_body`/`hmac` to the target app's real webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) passes because it only checks the body/hmac pair.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the handler with `shop: "victim.myshopify.com"`, so attacker-controlled data is processed/stored as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
