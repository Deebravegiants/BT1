### Title
Webhook shop/topic identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then dispatches to a handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers. None of these header-derived identity fields are covered by the HMAC, so a request whose body/HMAC pair is genuine (obtained by the attacker's own tenant) can be replayed with a different `shop`/`topic` header and still pass validation, letting one tenant's webhook be reprocessed as if it belonged to another tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`: [1](#0-0) 

For a webhook `Request`, `to_signable_string` returns only the raw body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of caller-supplied HTTP headers, with no cryptographic tie to the body that was HMAC-verified: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts these header-derived values to build the tenant/topic identity handed to the handler: [4](#0-3) 

The equality that should hold but does not is:

`bytes verified by HMAC (raw_body only)` == `bytes acted upon for tenant/topic identity (shop, topic, webhook_id headers)`

Because the header set is disjoint from the signed payload, any request carrying a body+HMAC pair that is valid for the app's `client_secret` — which any tenant that has installed the app can obtain simply by triggering a real webhook to themselves — can be resent to the app's public webhook endpoint with the `shop`/`topic` headers swapped to another tenant's domain or a different registered topic, and `Utils::HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant boundary the webhook handler relies on: the host application's handler receives `WebhookMetadata` with an attacker-chosen `shop` value while believing the request was HMAC-authenticated for that shop, and/or gets dispatched to a handler for a topic that was never actually sent for that payload. This is a cross-tenant access condition — data attributable to one merchant can be injected/processed under another merchant's identity in the host app, purely through the gem's webhook verification, without any access token, client_secret, or privileged credential.

### Likelihood Explanation
Any unprivileged internet user who can install the app on a store they control (a normal trial/dev install, no special privilege) can trigger a legitimate webhook for themselves, capture the resulting body + `X-Shopify-Hmac-Sha256` value, and replay it to the shared public webhook endpoint with a modified `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. No secrets, tokens, or elevated access are required — only the gem's own `Registry.process`/`Request`/`HmacValidator` code path, which is reachable by design from the internet-facing webhook endpoint.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified payload, e.g., by including them in the string signed by `to_signable_string`, or by requiring the host application to independently confirm that `shop` corresponds to a store with an active installation and matches the shop the webhook subscription was registered for, rejecting mismatches before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a subscribed event (e.g. `orders/create`), so Shopify sends a genuine webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, a JSON body the attacker fully controls (their own order), and a correctly computed `X-Shopify-Hmac-Sha256` over that body using the app's real `client_secret`.
2. Attacker captures this request and resends it to the same public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (a real other tenant of the app).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since the HMAC is computed only over `@raw_body`, which is unchanged, validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop = "victim-shop.myshopify.com"` and the attacker's chosen body (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to process attacker-controlled data under the victim tenant's identity despite HMAC validation passing.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end
