## Title
Webhook `shop`/`topic` headers are trusted for tenant attribution but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`) values from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. The equality the code implicitly assumes — `shop used for tenant attribution == shop that produced/authorized this signed payload` — is never actually checked, because the `shop-domain` header is outside the signed byte range.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read straight from headers with no cryptographic binding to that signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof that the entire request — including the `shop` header used to build `WebhookMetadata` — is authentic for that shop, and dispatches the handler with that unauthenticated `shop` value: [4](#0-3) 

Because `shop-domain` (and `topic`, `webhook-id`, `api-version`) are not part of `to_signable_string`, an attacker who can obtain any one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a legitimate webhook delivery) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from the body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field is attacker-controlled but presented as verified. This breaks the binding `verified-signer shop == shop passed to handler`.

### Impact Explanation
Any app built on this gem that keys business logic, data writes, or authorization decisions off `WebhookMetadata#shop` (the documented, intended use of webhook processing) can be made to attribute a signed-but-foreign payload to a victim shop chosen by the attacker. This is a cross-tenant confusion primitive: the attacker supplies the topic/body content (from their own store) but forces it to be processed as if it belongs to a different, victim tenant, since nothing in this gem ties the `shop` header to the HMAC-verified bytes. This matches the High-severity class of scope/identity-binding bypass called out in the rules (shop authenticated vs. shop used for tenant action).

### Likelihood Explanation
Exploitation only requires an unprivileged internet user to run their own Shopify dev/trial store, install the target app, capture one legitimate webhook delivery for a topic the app handles, and replay it against the app's public webhook endpoint with a modified `shop-domain` header (and/or `topic`/`webhook-id` headers, all likewise unsigned). No secrets, tokens, or elevated access are needed — the attacker never needs `api_secret_key` since they are reusing a signature already produced by Shopify for their own legitimate event.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable material, or otherwise cryptographically bind them to the verified payload before constructing `WebhookMetadata`, so that `HmacValidator.validate` can no longer pass for a payload whose tenant-attribution headers were altered after signing.

### Proof of Concept
1. Attacker creates their own Shopify store and installs the target app.
2. App receives a legitimate webhook: body `B`, headers include `x-shopify-hmac-sha256: H` (valid for `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC from `B` only and returns `true`, since `B` and `H` still match.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` from `request.shop` and dispatches it to the app's handler as an authenticated event for the victim shop.
