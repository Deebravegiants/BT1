### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) headers are trusted for tenant identification but are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the shop identity (`shop-domain` header) that `Registry.process` uses to attribute the webhook to a tenant is read from an unsigned header. Any actor who can obtain one genuinely-signed webhook delivery (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while swapping the `X-Shopify-Shop-Domain` header to a victim shop, and the gem will accept it as an authentic webhook for the victim.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over this body-only signable string: [3](#0-2) 

and then constructs `WebhookMetadata` using the unverified `request.shop` value, which is handed to the host application's handler as the tenant identity: [4](#0-3) 

`HmacValidator.validate` only compares the HMAC against `to_signable_string`, i.e., the raw body, using the app's shared `api_secret_key`: [5](#0-4) 

This breaks the identity binding: `HMAC-verified bytes (raw_body)` != `bytes trusted for tenant attribution (shop-domain header)`. Since a single `api_secret_key` is shared across all shops that install a given app, any user who installs the app on their own store can capture one legitimate webhook delivery (valid body + valid HMAC for that body), then replay the identical body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header value. `Registry.process` will pass HMAC validation (the body is unchanged and genuinely signed) and will call the handler claiming the event belongs to whatever shop the attacker put in the header.

### Impact Explanation
This is a cross-tenant identity forgery: the gem provides no guarantee that the `shop` value delivered to a host application's webhook handler actually corresponds to the shop that produced the signed payload. Host applications rely on this `shop` value (as documented in `docs/usage/webhooks.md`) to route the webhook body to per-shop records, trigger uninstall/GDPR flows, or update store-scoped data. An attacker with their own install of the app can forge webhooks that appear to originate from an arbitrary victim shop domain, causing cross-tenant data corruption/injection in the host app driven entirely by this gem's incorrect trust of an unsigned header. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any user can install the target app on a store they control (no privileged access, secrets, or social engineering required), capture one valid webhook delivery, and replay it with a modified `shop-domain` header to the app's public webhook callback endpoint. The only requirement is that the app processes at least one webhook topic where the forged shop value influences server-side behavior (record creation/update, uninstall handling, etc.), which is the documented, expected usage pattern of `ShopifyAPI::Webhooks::Registry.process`.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signable string, or otherwise cryptographically bind the shop identity to the signed payload, so `HmacValidator.validate` fails if any of these identity-bearing headers are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a webhook to the app with a genuine `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `api_secret_key`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this raw body and HMAC value.
4. Attacker (or a script acting for them) sends a new HTTP request to the app's webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (raw body only) and it matches, since the body/HMAC pair is untouched.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never sent this webhook for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
