### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not bound to the HMAC, enabling cross-tenant webhook spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shopify-shop-domain` (and `topic`/`webhook_id`/`api_version`) headers to decide which tenant the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `Registry.process` reads `request.shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, see `shop`/`shopify_header` in `Request`) and forwards it unchecked into `WebhookMetadata`, which is what the host application uses to attribute the webhook to a specific merchant [3](#0-2) , [4](#0-3) .

The broken identity equality is:
`shop authenticated by HMAC` ≠ `shop the payload is attributed to (request.shop header)`.

Since the app's `client_secret`/`api_secret_key` used to sign webhooks is a single **app-wide** secret shared across every shop that installs the app (not a per-shop secret) [5](#0-4) , any merchant who installs the app is a legitimate holder of valid `(raw_body, hmac)` pairs for webhooks Shopify sends to their own store. Because `shop`, `topic`, `webhook_id`, and `api_version` are carried in HTTP headers that are outside the signed content, that same merchant (an "unprivileged internet user" relative to other tenants of the app) can replay an intercepted/legitimately-received `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`) with a victim shop's domain or a different topic. `HmacValidator.validate` will still return `true` because it only checks the body bytes against the signature, and `Registry.process` will happily construct `WebhookMetadata` attributing the (attacker-originated) body to the victim shop or to a target topic the attacker doesn't legitimately have [3](#0-2) .

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide to consuming applications: host apps rely on `WebhookMetadata#shop` to look up the correct merchant session/record and act on it (as documented in `docs/usage/webhooks.md`, where `data.shop` is used to route work per-shop). An attacker-controlled merchant can cause the app to process/store data under another shop's identity, or trigger handlers for topics beyond what was actually delivered — a cross-tenant data confusion/spoofing primitive, rated High under the cross-tenant-access impact category.

### Likelihood Explanation
Any developer/merchant who installs the app receives legitimately signed webhooks for their own store and can capture the raw body/HMAC pair with trivial tooling (e.g., logging their own webhook endpoint). Replaying that request with modified headers to the shared webhook endpoint requires no elevated credentials — it only requires network access to the app's public webhook URL, which is inherently internet-facing. No secret material needs to be reverse-engineered because the header binding is simply never checked.

### Recommendation
Do not trust `request.shop`, `request.topic`, `request.webhook_id`, or `request.api_version` as authenticated values. Either:
- Include these header values in `to_signable_string` so they are covered by the HMAC (this would require a corresponding change in how Shopify computes/sends the signature, so it isn't viable unilaterally), or, more practically,
- Cross-validate `request.shop` against a shop the app already has a stored session/access token for (i.e., the shop must be a known, already-authorized tenant) before dispatching to `handler.handle`, and/or
- Track and validate `webhook_id` for idempotency per registered `topic`, rejecting mismatches between the topic a given `webhook_id`/subscription was registered for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)` per `HmacValidator.compute_signature` [6](#0-5) ).
2. Attacker sends a POST directly to the app's registered webhook path with the same raw body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [7](#0-6) .
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, causing the host app to process attacker-supplied data as though it originated from the victim shop.
