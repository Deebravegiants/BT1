### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing on a genuinely-signed webhook payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the `shop` attribute used by `Registry.process` to attribute the webhook to a tenant is read from the unsigned `x-shopify-shop-domain` / `shopify-shop-domain` header. The HMAC validated by `Utils::HmacValidator.validate(request)` therefore authenticates the body bytes only, not the shop identity that the host application's handler receives.

### Finding Description
`Webhooks::Request#hmac` decodes the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor simply reads the `shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then hands `request.shop` straight to the handler as the tenant identifier, without any independent verification that the shop header matches the entity that the signed body actually belongs to: [3](#0-2) 

The identity-binding equality that should hold is: `shop_covered_by_hmac == shop_used_by_handler`. In this implementation, the HMAC covers only `raw_body`, while `shop` used by the handler is an independent, unauthenticated header value — the equality does not hold. Any entity capable of legitimately receiving a signed webhook for one shop (e.g. a merchant who has installed the app) can capture that valid `(raw_body, hmac)` pair and replay it with the `shop-domain` header changed to any other shop string. `HmacValidator.validate` will still succeed because it only recomputes the signature over `raw_body`, and `Registry.process` will call the handler with `WebhookMetadata.new(shop: <attacker-chosen-shop>, ...)`.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on this gem to enforce. A webhook handler that trusts `WebhookMetadata#shop` (as documented/intended usage of this gem) to scope data writes, lookups, or session retrieval per-tenant can be tricked into processing or storing data under a different shop's identity, resulting in cross-tenant data confusion. Because the request still passes `HmacValidator.validate`, from the host app's perspective it looks like a properly authenticated Shopify webhook.

### Likelihood Explanation
Requires only the ability to receive one genuine webhook delivery (which any installed/legitimate app tenant can do) and then replay the HTTP request to the app's webhook endpoint with a modified `shop-domain` header — no knowledge of `api_secret_key` is needed since the HMAC check never inspects that header. This is a purely gem-level identity-binding gap, not dependent on host-app misuse of undocumented behavior.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the value covered by `to_signable_string`, or independently verify that `shop-domain` matches an expected/registered shop for the delivered `webhook-id`/topic before handing it to `handler.handle`. At minimum, document and enforce that `WebhookMetadata#shop` is not to be trusted unless cross-checked against a shop known to be associated with the signing secret used.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and valid header `shopify-hmac-sha256: H` (where `H = HMAC(api_secret_key, B)`).
2. Attacker (or the same tenant acting maliciously) resends the identical `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds.
4. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed_body, ...))` is invoked — the handler now believes this authentic payload belongs to `shop-b`, even though it was only ever signed as belonging to (and generated for) `shop-a`.
