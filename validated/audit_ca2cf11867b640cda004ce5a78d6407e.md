## Analysis Result

### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The reported Solidity bug is a missing-binding-check issue: `createMarket` writes to `markets[u][m]` without verifying that the slot is still empty, so an unprivileged caller can overwrite an existing (underlying, maturity) binding. The equivalent identity-binding break in this gem is in `ShopifyAPI::Webhooks::Request`/`Registry`: the value used as the tenant identity (`shop`) that gets handed to application webhook handlers is read from an HTTP header that is *not* included in the bytes covered by the HMAC signature, so the "verified" bytes and the "trusted" shop identity are not the same thing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never fed into the signature computation: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., the raw body) against `verifiable_query.hmac` (the `hmac-sha256` header value): [3](#0-2) [4](#0-3) 

Once the HMAC over the body passes, `process` builds `WebhookMetadata` using `request.shop` — a value taken straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which was never part of the signed bytes: [5](#0-4) 

The equality that should hold is: `bytes verified by HMAC == identity (shop) trusted by the handler`. Here it is: `bytes verified (raw_body) != identity used (shop header, topic header, webhook_id header)`. Any request whose body+HMAC pair is valid for the app's secret (i.e., any body+HMAC pair the attacker has ever legitimately received from Shopify for their *own* shop) can be replayed to the app's webhook endpoint with an arbitrary `shop-domain` header value substituted in, and the HMAC check still passes because the header is not covered by the signature.

### Impact Explanation
An unprivileged merchant who has installed the app (and therefore has legitimately received at least one real webhook delivery with a valid body+HMAC pair for their own shop) can capture that body/HMAC and resend it directly to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain. `Registry.process` will accept the request as valid (HMAC only checks the body) and invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any application logic that trusts `data.shop` to scope storage writes, cache keys, or side effects (e.g., updating per-shop settings, marking an order paid, disabling an integration) executes under the wrong tenant's identity — a cross-tenant access/write, matching the Critical impact bucket for cross-tenant access.

### Likelihood Explanation
Exploitation only requires a body+HMAC pair, which any installed shop naturally receives on any of its own webhook deliveries — no possession of `client_secret` or access tokens is needed, and no interaction with Shopify's servers is required beyond one's own installation. The webhook endpoint is a public HTTP endpoint by design, so replay with a modified header is trivial for any internet-reachable attacker who is (or was) a legitimate, if unprivileged, merchant of the app.

### Recommendation
Bind the shop identity (and topic/webhook id if they influence handler behavior) into the verified signature material, or independently authenticate the header values, e.g.:
- Include `shop-domain` (and `topic`) in the signable string alongside the raw body, mirroring the `createMarket` fix of checking the full key before trusting/writing it, or
- Cross-check the `shop-domain` header against a value obtained through an already-authenticated channel (e.g., the shop tied to the specific registered webhook subscription id) instead of trusting the header verbatim.

### Proof of Concept
1. App shop `victim.myshopify.com` and attacker's own shop `attacker.myshopify.com` both have the app installed and registered for `orders/create`.
2. Attacker captures a legitimate webhook delivery for their own shop: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker POSTs the same `raw_body = B` and same `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(secret, B)` — still valid — per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
5. The handler executes with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the event body actually originated from the attacker's own shop, per `lib/shopify_api/webhooks/registry.rb` lines 198-199.
