### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant shop attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler. This breaks the intended binding: `hmac == HMAC(raw_body)` while the effective identity claim used downstream is `shop == header["shopify-shop-domain"]`, a field that was never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

Its `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Registry.process` validates the HMAC (which covers only the body) and then immediately trusts `request.shop`, derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, to build the `WebhookMetadata` handed to the app-defined handler: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it authenticates bytes of the body, not the headers: [4](#0-3) 

Because `shop` is read from a header that is outside the HMAC-signed content, `bytes verified != bytes used for the trust decision`: the signature proves the body came from Shopify (assuming `client_secret` integrity), but it proves nothing about which shop that body belongs to. A party capable of relaying, replaying, or otherwise causing this code path to be invoked with a genuine `(raw_body, hmac)` pair from shop A, combined with a spoofed `shop-domain` header value equal to shop B, will pass `Utils::HmacValidator.validate` and cause the app's handler to receive `WebhookMetadata` claiming the payload belongs to shop B while it is actually shop A's data — a cross-tenant identity confusion at the point this gem hands control to the host application.

### Impact Explanation
This maps to the "Critical - cross-tenant access" category: if the host application's webhook handler uses `data.shop` to select which tenant's records to update/delete/read (a very common pattern, e.g. for `shop/redact`, `customers/redact`, `app/uninstalled`, `orders/*`), the gem's guarantee that "an HMAC-validated webhook accurately identifies its shop" is false. The gem presents `WebhookMetadata#shop` as if it were an authenticated field of the verified request, when in fact it is an unauthenticated header, making it straightforward for host apps built on the documented API of this gem to write logic that attributes actions to the wrong tenant.

### Likelihood Explanation
Exploitability depends on an attacker's ability to get this code path invoked with a header value that differs from the value implied by the signed body content — for example, via request smuggling/replay at an intermediary, a compromised/duplicated body payload being resent with a different header, or any transport in front of the Ruby endpoint that does not itself bind the `shop-domain` header to the specific signed body. The root cause — `to_signable_string` in `lib/shopify_api/webhooks/request.rb` including only the body and never the shop-identifying header — is a real, unconditional gap in this gem's authentication of the `shop` field, independent of any particular host application's mistake.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the HMAC-signable content, or otherwise cryptographically tie them to the verified body (e.g., include them in `to_signable_string`, or require the host app to independently confirm `shop` against a value obtained through an authenticated channel such as the stored session for that shop) before exposing them via `WebhookMetadata`.

### Proof of Concept
Not independently reproducible from the gem alone (requires a transport-layer mechanism to deliver a mismatched header alongside a valid signed body); the root-cause code path is demonstrated by the citations above: `Utils::HmacValidator.validate` only authenticates `Request#to_signable_string` (the raw body) and never `Request#shop`, yet `Registry.process` treats `request.shop` as trusted identity data derived from that same validated request.

            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
