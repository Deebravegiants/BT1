## Analysis

I investigated the HMAC/identity-binding boundaries across `lib/shopify_api/auth/**` and `lib/shopify_api/webhooks/**`. OAuth flows (`Auth::Oauth.validate_auth_callback`, `Auth::JwtPayload`) all sign every security-relevant field (`shop`, `code`, `host`, `state`, `timestamp` for OAuth; `dest`/`aud`/`sub` for JWTs) together under a single HMAC/JWT signature, so no unprivileged actor can rebind those without knowing `api_secret_key`. However, the webhook-processing path has exactly the flaw class described by the analog rule ("a field acted on but not covered by the HMAC").

`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `Webhooks::Request` also exposes `shop`, `topic`, `webhook_id`, and `api_version` sourced straight from unauthenticated HTTP headers: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC only over that raw body via `Utils::HmacValidator.validate`, then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the digest only from `verifiable_query.to_signable_string`, i.e. only the body for webhook requests: [4](#0-3) 

### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC computed exclusively over the raw request body (`Request#to_signable_string` returns `@raw_body`). The `shop-domain`, `topic`, and `webhook_id` values, however, come straight from HTTP headers that are never included in that signed string. Because the app's single `api_secret_key` is shared across every shop that installs the app, any merchant who legitimately receives one authentic webhook delivery obtains a body+HMAC pair that remains valid for that secret regardless of which shop-domain header it is later paired with.

### Finding Description
The binding the system is supposed to enforce is:
`shop_header == shop_that_the_signed_bytes_actually_originated_from`

Before the request reaches the handler: the HMAC only proves "these bytes were produced by someone holding `api_secret_key`." It says nothing about which shop sent them, because `to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38` returns only `@raw_body`. After validation succeeds in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`), the code immediately trusts `request.shop`, `request.topic`, and `request.webhook_id`, all parsed unauthenticated from headers (`lib/shopify_api/webhooks/request.rb:20-32`), and forwards them into `WebhookMetadata` given to the app's handler.

Since `api_secret_key` is one shared value for the whole app (not per-shop), an unprivileged attacker who operates any shop that has the app installed can capture one genuine webhook (body + valid `X-Shopify-Hmac-Sha256`), then resend the identical body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` dispatches the forged event to the handler labeled as coming from the victim tenant.

### Impact Explanation
This breaks the tenant identity binding between an authenticated payload and the shop it is attributed to, letting one tenant forge webhook events "from" another tenant. Any host application logic keyed off `data.shop` (e.g., updating billing state, deleting shop-scoped data, revoking access, syncing inventory) can be triggered against a shop the attacker does not control. This is a cross-tenant access vulnerability.

### Likelihood Explanation
The attacker only needs to be an existing installer of the app (unprivileged relative to other tenants) and to be able to replay/craft an HTTP POST with arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or `api_secret_key` leak is required, since the shared secret is already usable by any shop that installed the app to sign its own webhook bodies.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` field to the payload (e.g., verify that the shop header matches a shop known to have triggered that specific webhook id via a side channel, or require per-shop signing secrets). At minimum, document and encourage host apps to independently verify `data.shop` against their own shop registry before trusting webhook content, since `Registry.process` currently provides no such guarantee.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends `POST /callback/orders/create` to the app with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, and the app processes an attacker-controlled event as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
