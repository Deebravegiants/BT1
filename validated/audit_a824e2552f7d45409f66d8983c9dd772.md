Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from attacker-controllable HTTP headers [2](#0-1) . `HmacValidator.validate` only compares the HMAC against `to_signable_string`, i.e. the body alone [3](#0-2) . `Registry.process` accepts the request once this body-only HMAC checks out and then forwards the unauthenticated `request.shop` value directly into `WebhookMetadata`, which host apps use as the tenant identifier [4](#0-3) [5](#0-4) .

### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook `HmacValidator` only authenticates the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values are taken verbatim from HTTP headers that are never included in the signed material, so `Registry.process` hands a cryptographically-unauthenticated `shop` value to the host app's handler as if it were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [6](#0-5) . `Utils::HmacValidator.validate_signature` computes the HMAC solely over `to_signable_string` (the body) and compares it to the `hmac` header [3](#0-2) . `Webhooks::Registry.process` treats this body-only check as sufficient authentication for the whole request, then constructs `WebhookMetadata` with the attacker-controlled `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app's registered handler [4](#0-3) .

This breaks the intended identity binding `authenticated_shop == shop_used_by_handler`. Because a given app's client secret (used to compute the HMAC) is shared across every merchant/shop that installs the app, an attacker who operates their own (even free/trial) shop can install the app, receive a legitimately-HMAC-signed webhook body for their own shop, and then replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC still validates (it only ever covered the body), so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain even though the request was never sent by Shopify for that shop.

### Impact Explanation
This is a cross-tenant confusion vector: an app that uses the value of `WebhookMetadata#shop` (as returned by this gem, having been "validated") to look up/act on a specific merchant's data (e.g., select which shop's session/access token to use, or which tenant's records to write) can be tricked into performing that action against a different shop's tenant context using data supplied entirely by the attacker. Because the "topic" and "webhook_id" fields are similarly unauthenticated, an attacker can also make the app process an attacker-chosen body as if it were a different topic/webhook than what Shopify actually signed for.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged flow for public apps) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The gem itself provides no protection: it treats the header-derived `shop` as authenticated once the body HMAC passes.

### Recommendation
Bind the tenant-identifying fields into the HMAC computation, or have `HmacValidator`/`Registry.process` require the caller to separately verify `request.shop` against the shop associated with the resolved session/access token before dispatching to a handler. At minimum, document prominently (and enforce in code) that `WebhookMetadata#shop`, `#topic`, and `#webhook_id` are NOT part of the HMAC-verified payload and must not be trusted as tenant identifiers without independent verification.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook, e.g.:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<valid HMAC Shopify computed over the raw body>",
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}
raw_body = '{"id":1,...}'  # legitimately signed for attacker's own shop

# Attacker replays the identical body + hmac, but swaps the shop header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) still returns true, because it only checked raw_body.
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
