### Title
Attacker-forced `i128` overflow in `supplied * supply_index` permanently freezes a market - (File: common/src/rates/index.rs)

### Summary
The analog of the OpenEXR "crafted huge dimension → overflowing multiplication → process abort" is a scaled-share × index multiplication in the accrual path. Every pool op accrues first via `Cache::calculate_utilization` / `update_supply_index`, which compute `scaled_to_original(supplied, supply_index)` and `supplied.mul(old_index)` through `mul_div_half_up`. When `supplied * supply_index / RAY` exceeds `i128::MAX` the `I256` intermediate cannot be narrowed back, and the call panics with `GenericError::MathOverflow`. An unprivileged supplier can push a market past this threshold by depositing a very large amount; from that point every verb that touches the market reverts. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`update_supply_index` computes `total_supplied_value = supplied.mul(env, old_index)` (`common/src/rates/index.rs:34`), and `Cache::calculate_utilization` computes `scaled_to_original(supplied, supply_index)` (`contracts/pool/src/cache/scale.rs:24`). Both funnel into `mul_div_half_up`, which tries `x.checked_mul(y)` and otherwise widens to `I256`, returning `None` when the quotient does not fit `i128`; the wrapper panics with `MathOverflow` (`common/src/math/fp_core.rs:116-117,138-143`).

`supplied` is a RAY-scaled share total: `calculate_scaled_supply` mints `floor(amount * 10^(27-d) * RAY / supply_index)` shares per deposit (`contracts/pool/src/cache/scale.rs:30-37`, `docs/reference/formulas.md:39-43`). For a 7-decimal asset, one base unit contributes `10^20` scaled units, so the panic threshold is roughly `supplied_scaled * supply_index_raw > i128::MAX * RAY ≈ 1.7e65` — e.g. ~`1.7e18` base units (≈1.7×10^11 whole tokens) at index `RAY`, or ~`1.7e17` base units at a 10× grown index. Stellar classic assets can have total supply up to `i64::MAX ≈ 9.2e18` base units, so the threshold is inside the representable domain for high-supply listed tokens, and `supply` rejects neither large amounts nor large resulting scaled totals — only the listing-time supply cap bounds it.

Because accrual runs at the head of every mutation and inside the simulated-index views, once `supplied` crosses the threshold:

- `supply`/`borrow`/`withdraw`/`repay`/`liquidate`/`clean_bad_debt`/`flash_loan`/`flash_position`/`multiply`/`swap_*`/`recapitalize`/`update_indexes` on that market all panic, since `global_sync` → `accrue_step` → `scaled_to_original`/`update_supply_index` overflows.
- The index cap (`MAX_SUPPLY_INDEX_RAY`) does not help: the panic happens while *computing* the value, before clamping.

This is demonstrated end-to-end by the harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which asserts `MathOverflow` on `update_indexes` and then confirms `withdraw` and `repay` are frozen (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360`). [4](#0-3) 

### Impact Explanation
Permanent freezing of funds: once the market's scaled-supply × index product exceeds `i128`, no supplier can withdraw and no borrower can repay, and no liquidator can service the market — every entry path panics in `MathOverflow`. All token balances held by the pool for that market are unreachable; the attacker's own deposit is burned as the cost of the grief. There is no recovery entrypoint (no admin "fix supply" verb is in the permissionless surface, and accrual-prepending blocks admin verbs on the market as well).

### Likelihood Explanation
Triggering requires depositing ~`10^17–10^18` base units of the listed asset (less as the supply index grows — the index grows automatically with borrow utilization, which the attacker can also drive up by borrowing their own collateral). For a high-max-supply 7-decimal classic asset this is inside the token's representable/issuable range, but it demands acquiring a large fraction of total supply, so the attack is capital-intensive and self-freezing. No privileged action is needed on the attack path itself: `supply` is open, `require_cap_within_asset_domain` only constrains the configured cap, and a market listed with a cap at/near the asset's maximum exposes the path. Severity is Medium-consistent: permanent freeze of a single market at high economic cost.

### Recommendation
Make the valuation path overflow-safe rather than panicking:

- Route `supplied * supply_index` in `update_supply_index`, `supply_index_reward_shortfall`, `scaled_to_original`, and `Cache::calculate_utilization` through a saturating or `Option`-returning variant (the code already has `mul_div_floor_saturating` and `calculate_scaled_cap` deliberately saturates "so the cap check fails open rather than trapping an entry path" — `common/src/rates/scaling.rs:18-25`), and clamp the resulting value/`supply_index` instead of trapping.
- Alternatively enforce a hard ceiling on total scaled supply (`supplied` shares) at mint time in `calculate_scaled_supply` / supply cap checks so that `supplied * MAX_SUPPLY_INDEX_RAY / RAY` always fits `i128`.
- Reject deposits that would push scaled `supplied` above `i128::MAX * RAY / MAX_SUPPLY_INDEX_RAY` with a dedicated error rather than letting later accrual trap.

### Proof of Concept
1. Market exists for a 7-decimal asset with a large/absent supply cap and `supply_index ≈ RAY`.
2. Attacker calls `supply(caller, account_id, [(hub_asset, 2e18)])` — depositing `2e18` base units mints `≈2e38` scaled shares (`2e18 * 10^20`).
3. Next accrual (`update_indexes`, or any supply/borrow/withdraw/repay) computes `supplied.mul(supply_index)` = `2e38 * 1e27 / 1e27 = 2e38 > i128::MAX` → `MathOverflow` panic.
4. Thereafter `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `update_indexes` all revert on that market: user funds permanently frozen.

Reference: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-356` already encodes exactly this freeze via sustained accrual (`try_update_indexes_for` → `MATH_OVERFLOW`, then `withdraw`/`repay` → `MATH_OVERFLOW`); the only difference is that here a single oversized `supply` reaches the same `supplied × index` bound directly.

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
