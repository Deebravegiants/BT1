### Title
Webhook shop-domain spoofing via HMAC that only covers the request body, not the shop identifier - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` header to attribute the payload to a tenant. Because the HMAC signature never binds the `shop` value, an attacker who can obtain one valid `(body, hmac)` pair (e.g. by triggering a webhook on their own store, which any merchant/attacker can install the app on) can replay that pair to the app's public webhook endpoint while substituting a different `shop-domain` header. The signature still validates, and the payload is delivered to the host application's handler tagged with an arbitrary victim shop, crossing the tenant boundary this gem is supposed to enforce.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and `shop` is read directly from the (attacker-controllable, since the endpoint is a plain public HTTP route) `shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` only checks the HMAC of the body before dispatching the parsed payload to the host app's handler using `request.shop` as the tenant identity: [3](#0-2) 

This breaks the intended equality binding: `hmac == HMAC(secret, body)` is verified, but the tuple actually acted on is `(body, shop)`, and `shop` is never included in the signed material. Consequently `HMAC(secret, body)` is valid for *any* shop header paired with that same `body`, not just the shop that originally triggered the webhook.

### Impact Explanation
An attacker (any merchant/developer, since installing a Shopify app on one's own store is unprivileged) can:
1. Install the target app on their own attacker-controlled store, triggering a legitimate webhook and capturing the resulting `(raw_body, x-shopify-hmac-sha256)` pair for a topic the app is subscribed to.
2. Replay that exact HTTP request to the app's public webhook endpoint, but with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain.
3. `HmacValidator.validate` still succeeds (body/hmac pair is genuinely valid), so `Registry.process` calls the host app's handler with `WebhookMetadata.new(shop: <victim shop>, ...)`.

Depending on what the host application's webhook handlers do with `shop` (e.g., update order/inventory/customer records, uninstall/reinstall flags, GDPR data-request/erasure processing, billing state), this allows cross-tenant data injection or corruption attributed to a shop the attacker does not control — a cross-tenant access violation.

### Likelihood Explanation
Webhook endpoints are typically plain public HTTP(S) routes with no additional network-level restriction to Shopify's IP ranges enforced by this gem, and any developer/attacker can freely install an app on their own store to harvest a valid `(body, hmac)` sample for any subscribed topic. No credentials, access tokens, or `client_secret` are required by the attacker — only the ability to become a legitimate (if low-privilege) merchant/user of the app, which is the unprivileged-internet-user threat model in scope.

### Recommendation
Include the shop domain (and ideally webhook id / topic) as part of the material verified by the HMAC check, or otherwise cryptographically bind the `shop` header to the specific webhook delivery (e.g., cross-check the header shop against Shopify's own list of registered/expected shops for that webhook subscription, or require the app to independently resolve shop identity from a stored, previously-authenticated session rather than trusting a bare unauthenticated header). At minimum, document and encourage host apps to treat `WebhookMetadata#shop` as HMAC-unverified data.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, triggers a webhook of interest, and captures headers/body from their own endpoint logs or a network capture, obtaining a valid `x-shopify-hmac-sha256` for that `raw_body`.
2. Attacker POSTs the same `raw_body` to the app's public webhook URL, keeping `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `body` vs `hmac` (see `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`).
4. The host app's handler executes with `shop: "victim-shop.myshopify.com"`, processing attacker-supplied data as though it originated from the victim's store.

          received_signature = verifiable_query.hmac
