### Title
Unrestricted route pool addresses let a rogue venue attach malicious `token.transfer` calls to the caller's auth tree and drain wallet funds - (File: contracts/swap-aggregator/src/venues)

### Summary
CVE-2020-6432 maps to insufficient policy enforcement on where a crafted input can "navigate" execution. The swap router decodes a caller-supplied `StrategyPayload` whose `assets` registry names arbitrary pool/token contracts, and `dispatch_hop` invokes whichever pool address the route names with no allowlist. A rogue pool called during a hop executes arbitrary code below the router's call to `sender.require_auth()`-protected `execute_strategy`, and any `token.transfer(sender, attacker, x)` it issues is recorded as a sub-invocation of the sender's own authorization entry — executing if the sender signs the simulated tree.

### Finding Description
`Program::validate` (`contracts/swap-aggregator/src/program.rs:239-303`) checks only structural properties: opcode validity, registry index bounds, `Prev` linkage, same-token swaps, and split-weight ranges. Nothing validates that `assets[idx_a]` (the pool) is a known venue contract. `dispatch_hop` then invokes the pool address from the payload and only measures the router's own `token_in`/`token_out` balance deltas around the call (`skills/xoxno-swap-aggregator/payload.md:100`). The router self-authorizes pool pulls via invoker-contract auth, so venue calls never appear distinctly to the signer.

The threat model confirms the mechanism: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree." (`docs/explanation/threat-model.md:154-165`). The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates a `RogueHopPool` whose `swap` performs `token.transfer(victim, attacker, amount)` for an arbitrary token in the victim's wallet (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:62-71`).

The same exposure exists through the controller: `swap_tokens` calls `router.execute_strategy` with caller-supplied `swap` bytes inside `with_flash_guard` (`contracts/controller/src/strategies/swap.rs:34-38`), so `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` all route through attacker-influenceable XDR, though for controller calls the wallet-drain vector applies to direct `execute_strategy` users and any caller signing a composed tree.

### Impact Explanation
Theft of user funds: a malicious route (served by a compromised/malicious quote or crafted by an attacker targeting users who sign simulated auth trees without decoding children) transfers arbitrary token balances from the signer's wallet to the attacker. The loss is unbounded by `total_in`, `min_out`, or the controller's risk gates — the swap itself can settle fairly while the injected sub-invocation drains unrelated tokens.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign an authorization tree containing the rogue transfer; the swap itself can be made to look completely normal (fair output, min_out satisfied). The defense is entirely client-side ("a client must decode the route it signs and refuse an authorization tree with any other child"), and nothing on-chain enforces it. Any unprivileged user calling `execute_strategy` directly with an attacker-influenced route is exposed, and any quote/UI path that fails to inspect child invocations passes the attack through.

### Recommendation
Enforce policy on-chain instead of relying on client-side auth-tree inspection:
- Maintain an owner-managed allowlist of venue pool contracts per `SwapVenue` in router storage and reject hops whose `assets[pool]` is not registered (mirroring INV-STRAT-03's approved-pool model for Blend migration).
- Alternatively/additionally, wrap each `dispatch_hop` venue call so no code below the router can emit `require_auth`-seeking sub-invocations attributable to the sender — the structural fix is the pool allowlist, since invoker-contract auth only protects the router's own address.

### Proof of Concept
1. Attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, amount)` (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:56-71`).
2. Attacker constructs/serves a `StrategyPayload` for a `token_in → token_out` swap whose hop names the rogue pool as `idx_a` (any venue opcode whose adapter invokes the pool; e.g., an Aquarius-shaped hop, or a route through a wrapper pool).
3. Victim calls `execute_strategy(victim, total_in, swap_xdr)` directly (or signs a composed `swap_collateral`/`multiply` transaction). Simulation records the rogue pool's `token.transfer(victim, attacker, amount)` as a child of the victim's auth entry.
4. Victim signs the simulated tree; on execution the router pulls `total_in`, the pool delivers a fair `token_out` (or a preceding legitimate hop covers `min_out`), and the injected transfer drains `amount` of `wallet_token` from the victim — the call succeeds, `SlippageExceeded` never triggers, and no residual or risk gate bounds the stolen amount.     fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
                    }
                }
                // Liquidity legs spend the full vault balance, so only `Mode::All` is valid.
                Opcode::Burn | Opcode::Mint => {
                    if mode != Mode::All {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_c >= amounts_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                }
            }
        }
