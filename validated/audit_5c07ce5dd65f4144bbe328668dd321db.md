Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) , then trusts the `shop` value — parsed directly from the `X-Shopify-Shop-Domain` HTTP header, which is never part of the signed material — to build the `WebhookMetadata` handed to the app's handler [2](#0-1) .

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`; the `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers that are excluded from the signable string [3](#0-2) . `Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [4](#0-3) , so it proves only that "these exact `raw_body` bytes were signed with the app's `client_secret`" — it proves nothing about which shop header accompanies that signature.

The identity binding broken here is:
`shop authenticated (bytes covered by HMAC) ≠ shop trusted downstream (request.shop, from an unauthenticated header)`.

Since a single app-level `client_secret` is shared across all shops that install the app, any valid `(raw_body, hmac)` pair legitimately produced by Shopify for **one** merchant's webhook delivery remains cryptographically valid when replayed with the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`) header rewritten to name a **different** merchant. `Registry.process` will accept it, because the HMAC check only inspects `@raw_body` [5](#0-4) , and will then hand the handler a `WebhookMetadata` whose `shop` field is attacker-controlled and unauthenticated [2](#0-1) .

Any app that (as this gem's own documentation instructs) uses `WebhookMetadata#shop` as the tenant key to look up the merchant's session/access token or to apply the payload to a specific merchant's data will process another tenant's webhook body under an attacker-chosen shop identity, or misattribute a webhook belonging to one shop to another shop of the attacker's choosing.

### Impact Explanation
This is a cross-tenant confusion primitive: the gem's own webhook-verification API returns a `shop` value that passes signature validation but is not actually bound to the signed body. Any consuming app that trusts `WebhookMetadata#shop` (the documented and only way this gem exposes the requesting shop for webhooks) as the tenant identifier can be made to apply another tenant's event data against a shop record chosen by whoever can replay/relay the request, satisfying the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair generated by Shopify for a webhook topic they can trigger on their own store (e.g., `orders/create`), and the ability to replay/POST that body+HMAC to the app's webhook endpoint with a forged `shop-domain` header — no knowledge of `client_secret` or any merchant's access token is required. This depends on how the host application transports/exposes the `shop` header value and whether it re-derives it from a trusted channel; the gem itself provides no protection and documents `WebhookMetadata.shop` as the field to use, so likelihood is dependent on host-app deployment specifics that could not be further verified from within this gem's index.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signed payload before exposing it via `WebhookMetadata`, so that `HmacValidator.validate` fails if the `shop-domain` header is altered independently of the signed body.

### Proof of Concept
1. Attacker's own shop (`attacker-shop.myshopify.com`) has the app installed and receives a legitimate webhook delivery from Shopify: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint, keeping body `B` and header `H` unchanged but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `to_signable_string` returns `B` only [6](#0-5) .
4. `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation succeeds [5](#0-4) .
5. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [2](#0-1)  — the attacker's own event data is now processed under the victim shop's identity, or vice versa depending on which host-app logic keys off `shop`.
