### Title
Unvalidated swap routes let a malicious venue steal unrelated wallet tokens through the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, `multiply`, and `flash_position` accept an opaque router payload and forward it to the configured swap aggregator without validating the identities of nested venues. [1](#0-0)  The controller bounds only its own input transfer and requires positive measured output; it does not constrain what contract the route invokes or what additional token authorization appears in the caller’s signed authorization tree. [2](#0-1)  A malicious venue can therefore add a `token.transfer(victim, attacker, amount)` invocation beneath the victim’s `swap_collateral` authorization while still returning enough output for the lending operation to succeed. [3](#0-2) 

### Finding Description
`process_swap_collateral` authenticates `caller` and requires account ownership or delegation, then passes the caller-supplied `StrategySwap` into `withdraw_and_swap_from_supply`. [4](#0-3)  The lower-level `swap_tokens` treats that payload as opaque bytes, invokes `router.execute_strategy(controller, amount_in, swap)`, and afterward checks only router spend, unused-input refund, and positive output receipt. [5](#0-4) 

The missing analogue to certificate verification is counterparty identity validation for nested route venues: neither the controller path shown here nor the payload checks performed by the controller establish that every route callee is a trusted pool, router, token, or exchange contract. [6](#0-5)  Because a venue executes below the caller-signed controller invocation, a malicious venue can request the caller’s authorization for an unrelated token transfer, and simulation records that transfer as a child of the user’s controller authorization. [7](#0-6) 

### Impact Explanation
A victim who signs the simulated authorization tree loses unrelated wallet assets to the venue-selected recipient, while the protocol swap can still return fair collateral and leave the lending account healthy. [8](#0-7)  The measured-output check does not bound this loss because the stolen token is not part of the controller’s input or output balance delta. [2](#0-1)  The demonstrated consequence is theft of user wallet funds rather than merely a poor exchange rate. [9](#0-8) 

### Likelihood Explanation
Any unprivileged user can submit the affected strategy entrypoints, and a venue operator can encode a route whose nested pool attempts an additional caller-token transfer. [10](#0-9)  Exploitation requires the victim to sign the authorization tree containing the malicious child transfer, so the practical path depends on route delivery and wallet UX rather than on a privileged key or leaked credential. [11](#0-10)  The host correctly rejects the rogue transfer when the signed tree omits it, which confirms that the exposure is the absence of route-callee verification and safe authorization-tree enforcement rather than a Soroban authorization bypass. [12](#0-11) 

### Recommendation
Restrict router venue calls to a governance-maintained allowlist of audited pool and token contracts, and bind each allowed venue to the exact external interface it may invoke. [6](#0-5)  In addition, make the supported clients reject any `swap_collateral`, `repay_debt_with_collateral`, `swap_debt`, `multiply`, or `flash_position` authorization tree containing children other than the expected protocol-token transfers. [11](#0-10)  A defense-in-depth router check should reject nested token calls whose `from` address is neither the router nor the authorized lending contract input flow. [13](#0-12) 

### Proof of Concept
1. The attacker deploys a route-compatible pool contract whose swap handler both returns a normal output amount and calls `victim_token.transfer(victim, attacker, victim_balance)`.
2. The victim invokes `Controller::swap_collateral(caller=victim, account_id=victim_account, current=USDC_key, from_amount=x, new=ETH_key, swap=route_through_attacker_pool)`. The entrypoint authenticates the victim and account ownership, then sends the opaque route to the configured router. [4](#0-3) 
3. The controller authorizes only its exact collateral input to the router, executes the route, and requires a positive ETH balance increase. [2](#0-1) 
4. Simulation records the attacker pool’s victim-token transfer as a child of the victim’s `swap_collateral` authorization. [7](#0-6) 
5. If the victim signs that simulated tree, the attacker receives the unrelated wallet token while the victim’s ETH supply is credited normally. [8](#0-7)

    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)

    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((

            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
