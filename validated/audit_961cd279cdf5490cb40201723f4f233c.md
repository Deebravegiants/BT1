### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are unauthenticated, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify," but the HMAC signature it checks only covers the raw request body. The `shop`, `topic`, and `webhook_id` values — read straight from unauthenticated HTTP headers — are passed on to the app's webhook handler as trusted identity fields without being part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` returns the value from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the received signature: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately forwards the unauthenticated `shop`, `topic`, and `webhook_id` header values into `WebhookMetadata`, which the app's handler consumes as trusted identity fields: [3](#0-2) 

Because the `client_secret` used to sign webhooks is shared across every shop that has installed a given app, any shop that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for its own webhooks. Since the `shop-domain` header (and `topic`/`webhook-id`) is not part of the signed content, that same valid `(raw_body, hmac)` pair can be replayed with an arbitrary `shopify-shop-domain` header, and the signature will still validate — the binding `header.shop == hmac_signed(shop)` never holds; the gem only enforces `hmac_signed(body) == hmac(body)`.

The documentation explicitly promises full-request authentication, reinforcing that host apps are expected to trust the verified request's `shop` field: [4](#0-3) 

### Impact Explanation
This breaks the identity binding `shop_authenticated == shop_acted_on`: the shop identity attached to processed webhook data is attacker-controlled even though the request passes the gem's own authenticity check. A malicious but legitimate app-installer (any shop) can cause the host application to attribute attacker-chosen webhook payload content to a different, victim tenant, resulting in cross-tenant data confusion/injection through a request the gem itself certifies as verified.

### Likelihood Explanation
Any shop that installs the target app can obtain valid `(body, hmac)` pairs for its own webhook traffic and replay them with a modified `shop-domain` header at will; no secrets, tokens, or privileged access are required beyond normal app installation.

### Recommendation
- Extend the HMAC-signed material (or perform an out-of-band binding check) to include the `shop-domain`, `topic`, and `webhook-id` headers, not just the raw body, so any tampering with these fields invalidates the signature.
- Alternatively, document and/or enforce that `Registry.process` cross-checks `request.shop` against the shop associated with the webhook subscription/session before invoking the handler, rather than presenting it as already "verified" once HMAC-over-body passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared `client_secret`.
2. Attacker replays the exact same raw body and HMAC value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks the (unchanged) raw body against the (unchanged) HMAC.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own order data>, ...)` and processes/stores attacker-controlled content under the victim shop's identity, despite the gem reporting the request as authenticated.
