### Title
Unbounded, fee-free `handle_unsigned` batches allow CPU-exhaustion via full cryptographic message processing during transaction-pool validation - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an unbounded `Vec<Message>` and is validated as an unsigned transaction whose `validate_unsigned` implementation runs the *entire* message-processing pipeline (`Self::execute`) — including membership/non-membership proof verification, consensus-proof cryptography (BEEFY/ECDSA recovery, SP1, GRANDPA, sync-committee, etc.), and per-request dedup/dispatch — before the transaction is even accepted into the pool, for free, with a static declared `Weight` regardless of batch size. This mirrors the CONTINUATION-flood bug class: cheap, unauthenticated attacker input is processed by every node's expensive verification logic before any size/cost-proportional gate rejects it, enabling CPU exhaustion.

### Finding Description
`handle_unsigned` is declared with a fixed weight independent of the number or size of messages in the batch: [1](#0-0) 

```
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
```

used directly by the call: [2](#0-1) 

The call itself takes an unbounded `messages: Vec<Message>` — not a `BoundedVec` — with no cap on the number of messages, number of requests per message, or proof size: [3](#0-2) [4](#0-3) 

Because `pallet-ismp` uses unsigned transactions "to allow anyone to execute ISMP datagrams for free," the pallet's `ValidateUnsigned::validate_unsigned` does not just perform lightweight signature/format checks — it calls `Self::execute(messages.clone())`, which runs the *full* handler pipeline (state-machine validation, membership-proof verification, per-request dedup, and dispatch to module callbacks) as part of transaction-pool admission, before any weight/fee accounting applies: [5](#0-4) [6](#0-5) 

Each `Request(RequestMessage)` in the batch drives a full membership-proof verification (`state_machine.verify_membership`) plus a dedup/receipt scan over all requests in the batch: [7](#0-6) 

and each `Consensus(ConsensusMessage)` in the batch drives a full cryptographic consensus-client verification (ECDSA recovery loops, SP1 proof verification, parachain header decoding, MMR proof walking), as seen in the BEEFY consensus client: [8](#0-7) 

None of this work is gated by the fixed `weight()` used for dispatch accounting, and the docs explicitly acknowledge the free-execution model without describing any cap on batch contents beyond generic block/extrinsic byte-length limits: [9](#0-8) 

An attacker can therefore construct a single unsigned extrinsic packing many `RequestMessage`/`ResponseMessage`/`ConsensusMessage` entries (each with syntactically-valid but ultimately-rejected proofs) up to the maximum extrinsic/block byte-length. Every full node that receives this gossiped transaction must run `validate_unsigned` — i.e., the entire membership-proof and consensus-verification pipeline — against the whole batch before it can even determine the transaction is invalid, at zero cost to the attacker (no fee, no bonded stake, not necessarily included in a block). This can be resubmitted continuously and propagated network-wide, directly analogous to Envoy's HTTP/2 CONTINUATION flood: unlimited frames (here, unlimited messages/requests per unsigned batch) are fully processed by the receiving stack before existing limits (block weight/fees) can reject them, at a CPU cost far exceeding the bytes required to trigger it.

### Impact Explanation
This is a network-wide CPU-exhaustion / denial-of-service vector reachable by any unprivileged party who can submit an unsigned transaction (no signature, no fee, no stake required). Every collator/full-node in the Hyperbridge parachain network must perform expensive cryptographic verification (ECDSA recoveries, SP1/ZK proof checks, trie membership proofs) proportional to attacker-controlled batch size during mempool validation, which is explicitly a "for-free" code path. Sustained submission can degrade block production and transaction propagation, denying legitimate relayers/users the ability to deliver messages — a route-unable-to-deliver-messages condition — qualifying as High severity per the CONTINUATION-flood precedent (~1 CPU-core-equivalent exhaustion pattern, no economic cost to attacker).

### Likelihood Explanation
High. `handle_unsigned` is a public, unsigned, fee-free extrinsic by design (documented behavior), reachable directly from any peer on the network without any prerequisite state (no funded account, no relaying reputation, no prior message in flight). Constructing a batch with many syntactically-valid-but-failing `Request`/`Consensus` messages requires no privileged knowledge — only correctly-typed SCALE-encoded structures. The only constraint is the runtime's generic max extrinsic/block-length limit, which is typically megabytes — enough to pack thousands of proof-bearing messages.

### Recommendation
- Bound `handle_unsigned`'s `messages: Vec<Message>` with a `BoundedVec<Message, MaxMessagesPerBatch>` and impose a cap on `requests` length inside `RequestMessage`/`ResponseMessage`/`TimeoutMessage`, similar to the `BoundedVec<u8, MaxProofSize>` pattern already used in `beefy-consensus-proofs`.
- Make `handle_unsigned`'s declared weight scale with batch size (`messages.len()` and aggregate proof/request length) rather than a flat `Weight::from_parts(300_000_000, 0)`, so block weight accounting reflects actual cost.
- In `validate_unsigned`, perform cheap, size/format checks (e.g., reject batches that are implausibly large, verify basic proof structure) prior to running full cryptographic verification, so a flood of large-but-invalid batches is rejected before expensive computation, mirroring how `pallet-call-decompressor` gates size before decompression.

### Proof of Concept
Conceptual (cannot be executed without a live testnet, but derivable directly from the reachable code paths above):
1. Construct an unsigned `Ismp::handle_unsigned` extrinsic containing hundreds of `Message::Request(RequestMessage)` entries, each with a large `requests: Vec<PostRequest>` and a syntactically well-formed but ultimately-invalid `Proof` (e.g., pointing at a real, previously-verified `StateMachineHeight` but with a corrupted/oversized trie proof `Vec<u8>`), packing the extrinsic up to the runtime's max extrinsic length.
2. Broadcast this unsigned transaction to the network.
3. Every node that receives it, per its `pallet_ismp::pallet::validate_unsigned`, must run `Self::execute(messages.clone())`, which for each `RequestMessage` calls `handle::<H>` — deduplicating every request in the batch, then invoking `state_machine.verify_membership(...)` over the full (attacker-supplied) commitment set and proof — all before the transaction is rejected as invalid and dropped for free (`InvalidTransaction::BadProof`).
4. Repeat/resubmit continuously with fresh nonces/content-unique tags (as validated by the `provides` tag logic in `validate_unsigned`) to bypass the pool's dedup rule and force repeated re-validation cycles across the network, driving up aggregate CPU load with no fee cost to the attacker.

```rust
pub fn handle<H>(host: &H, msg: RequestMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	if msg.requests.is_empty() {
		Err(Error::EmptyBatch)?
	}

	let state_machine = validate_state_machine(host, msg.proof.height)?;
	let consensus_clients = host.consensus_clients();
	let check_state_machine_client = |state_machine: StateMachine| {
		consensus_clients
			.iter()
			.find_map(|client| client.state_machine(state_machine).ok())
			.is_none()
	};

	let router = host.ismp_router();

	// Reject duplicate requests within the batch. Wire format is `Vec`,
	// so this is the line of defence against an attacker padding a
	// batch with identical requests.
	let wrapped: Vec<Request> = msg.requests.iter().cloned().map(Request::Post).collect();
	dedup_requests::<H>(&wrapped)?;

	for req in msg.requests.iter() {
		let req = Request::Post(req.clone());
		// If a receipt exists for any request then it's a duplicate and it is not dispatched
		if host.request_receipt(&req).is_some() {
			Err(Error::DuplicateRequest { meta: req.clone().into() })?
		}

		// can't dispatch timed out requests
		if req.timed_out(host.timestamp()) {
			Err(Error::RequestTimeout { meta: req.clone().into() })?
		}

		// either the host is a router and can accept requests on behalf of any chain
		// or the request must be intended for this chain
		if req.dest_chain() != host.host_state_machine() && !host.is_router() {
			Err(Error::InvalidRequestDestination { meta: req.clone().into() })?
		}

		let source_chain = req.source_chain();

		// in order to allow proxies, the host must configure the given state machine
		// as it's proxy and must not have a state machine client for the source chain
		let allow_proxy = host.is_allowed_proxy(&msg.proof.height.id.state_id) &&
			check_state_machine_client(source_chain);

		// check if the request is allowed to be proxied
		if source_chain != msg.proof.height.id.state_id && !allow_proxy {
			Err(Error::RequestProxyProhibited { meta: req.clone().into() })?
		}
	}

	// Verify membership proof
	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
