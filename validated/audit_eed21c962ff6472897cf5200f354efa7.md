### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as fully authenticated once `Utils::HmacValidator.validate` succeeds, but the HMAC signature computed by the gem only covers the raw request body. The `shop` and `topic` values that the gem extracts from HTTP headers and hands to the app's handler as trusted tenant/routing identity are never included in the signed bytes. This breaks the intended binding `hmac_valid(body) == authentic(shop, topic, body)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic`, however, are pulled straight from attacker-controllable HTTP headers with no cryptographic tie to the body they accompany: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the signable string (the body) against the app's secret: [3](#0-2) 

`Registry.process` uses HMAC success as a gate for trusting the *entire* request, then forwards the unauthenticated `request.shop` and `request.topic` straight to the handler as the tenant/routing identity: [4](#0-3) 

Because the api_secret_key is shared by the app across every shop that installs it (not per-tenant), any user who legitimately installs the app on their own store receives genuine `(body, hmac)` pairs signed with that shared secret for real webhook events on their own shop. Nothing in the gem prevents that same person from POSTing that exact `(body, hmac)` pair to the app's public webhook endpoint again while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never looked at those headers, and `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: <victim shop>, topic: <chosen topic>, body: <attacker's own signed payload>, ...)`, i.e., data the attacker fully controls is delivered to the host application labeled as belonging to a shop the attacker does not own.

### Impact Explanation
Any host application that uses `shop`/`topic` from `WebhookMetadata` as the tenant key to write, update, or route data (the documented and intended usage pattern of this gem, per `WebhookMetadata`/`handler.handle`) can be made to process attacker-supplied content under another merchant's identity — a cross-tenant integrity/confusion issue. This matches the Critical "cross-tenant access" impact category: the gem's own API presents unauthenticated header data as if it had been validated by the HMAC check it just performed, and the exploit path is entirely inside the gem's `process`/`Request`/`HmacValidator` code, not a host-app misuse of an undocumented feature.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on any shop they control (a normal, unprivileged action for using a public Shopify app) — no `api_secret_key`, access token, or privileged account is required. They only need to capture one webhook body+HMAC pair delivered to their own store and replay it with a modified `shop-domain`/`topic` header to the app's public webhook endpoint.

### Recommendation
Include the `shop` domain (and ideally `topic`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., verify the incoming `shop` against the session/store the webhook was registered for, or require the app to independently confirm that the shop is a known, installed shop before trusting `WebhookMetadata#shop`). At minimum, document clearly that `request.shop`/`request.topic` are NOT covered by the HMAC check and must not be used as an authenticated tenant key without additional verification (e.g., cross-checking against stored session data for that shop).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers any webhook event (e.g., `orders/create`) on their own store and captures the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (both fully legitimate, signed with the shared `api_secret_key`).
2. Attacker POSTs the exact same body `B` and header `H` to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B`:
   `lib/shopify_api/utils/hmac_validator.rb:27-31`.
4. `Registry.process` forwards `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` to the registered handler — the host app processes attacker-controlled data as belonging to `victim-shop.myshopify.com`. [4](#0-3) [5](#0-4)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
