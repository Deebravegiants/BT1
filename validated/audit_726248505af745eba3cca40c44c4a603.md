### Title
Emporium signature replay lets an unprivileged attacker reroute relay fees / fee token from a victim's wallet - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EMPORIUM_SIGNATURE_TYPEHASH` only binds `(message, opsHash, maxFee, deadline)` [1](#0-0) , while `circomData.relay`, `circomData.feeStructure` and `deltaAmountChanges` (which drive `payRelayFees`) are never part of the victim's signed payload and are freely chosen by whoever submits the transaction [2](#0-1) . `usedMessages[emporiumMessage]` is only marked spent as a side effect inside a transaction that must fully succeed [3](#0-2) ; if that transaction reverts downstream (e.g. a later balance/slippage `require` in `Hinkal.transact`), the flag rolls back and the leaked `(v,r,s,ops,maxFee,deadline,message)` tuple can be resubmitted by anyone inside a brand-new, self-generated `CircomData`/proof with attacker-chosen `relay`/`feeStructure`/`deltaAmountChanges`. Note: `circuits/SignatureVerifier.circom` (EdDSA-Poseidon verifier for spend-key/nullifier proofs, unrelated to the Emporium ECDSA signature) is not the relevant file for this bug — the actual signature and typehash logic live entirely in Solidity in `EmporiumUpgradeable.sol`.

### Finding Description
Broken equality: the set of values the victim actually authorized via `EMPORIUM_SIGNATURE_TYPEHASH` is `{message, hash(ops), maxFee, deadline}` [4](#0-3) , but the set of values that actually get executed alongside those `ops` at call time is `{feeStructure, relay, deltaAmountChanges, signerAddress-wallet-balance}`, none of which are covered by that hash.

Code path:
1. `Hinkal.transact` verifies the proof and calldata-integrity (`getHashedCalldata(circomData) == circomData.calldataHash`) for the *replaying attacker's own* `circomData`, then calls `_externalTransact` → `EmporiumUpgradeable.runAction` [5](#0-4) .
2. `runAction` decodes `EmporiumStack` from `externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)` [6](#0-5) .
3. `verifyWallet` first sets `usedMessages[emporiumMessage] = true`, then recomputes the EIP-712 hash from `circomData.emporiumMessage` (attacker-supplied, but equal to the leaked `M`), `_hashEmporiumOps(stack.ops)` (unchanged — the attacker cannot alter `ops` without breaking the ECDSA recovery), `stack.maxFee`, `stack.deadline` — all copied verbatim from the leaked tuple — and successfully recovers `stack.signerAddress` (the victim) [7](#0-6) . The only extra check is `feeStructure.flatFee > stack.maxFee` [8](#0-7) .
4. `runAction` then executes `stack.ops` against the victim's `signerAddress` wallet (fixed, victim-authorized) and afterwards calls `payRelayFees(circomData, stack.signerAddress, deltaAmountChanges)`, which pulls fee tokens from the victim's wallet balance and sends them to `circomData.relay` — a value the attacker fully controls and which is not part of the signed hash [9](#0-8) .

Root cause: `usedMessages` is only durable if the whole `transact` call succeeds; a legitimate transaction that fails after `verifyWallet` runs (any `require` further down in `Hinkal.transact`, e.g. the slippage/balance-diff checks at [10](#0-9) ) reverts atomically, undoing the `usedMessages` write and leaving `M` reusable. Since `relay`/`feeStructure`/`deltaAmountChanges` sit outside `EMPORIUM_SIGNATURE_TYPEHASH`, any subsequent caller who reuses the leaked signature tuple with a fresh, self-consistent `CircomData`/proof can redirect relay-fee payments (bounded by `maxFee` for `flatFee`, potentially unbounded for the `variableRate`-derived component) from the victim's wallet to an attacker-controlled `relay` address.

### Impact Explanation
The attacker cannot alter the `ops` themselves (bound by ECDSA signature) or steal shielded UTXOs/mint value (unrelated to this path), so this does not meet the Critical bar (no nullifier/proof bypass, no shielded double-spend). It does meet High: "theft ... of protocol/relay fees" and "moving assets a wallet owner ... never authorised" — the victim signed off on specific `ops` with a fee ceiling, not on an arbitrary `relay` recipient or `feeStructure`/`deltaAmountChanges` combination. Each successful replay lets the attacker redirect up to `maxFee` (and possibly more via `variableRate`) worth of tokens pulled from the victim's `HinkalWallet` to an address the attacker controls, and the attack is repeatable once per leaked/reverted-then-replayable `emporiumMessage`.

### Likelihood Explanation
Requires: (a) a victim-signed `EmporiumStack` whose enclosing `transact` transaction reverts somewhere after `verifyWallet` executes but before the call fully succeeds (achievable via mempool timing, slippage/balance races, or any downstream `require`), and (b) the attacker being able to observe that reverted transaction's calldata (public mempool/chain data) to extract `(v,r,s,ops,maxFee,deadline,message,signerAddress)`. The attacker then only needs to generate their own valid proof over their own UTXOs with a `CircomData` reusing `emporiumMessage = M`; this is fully within an unprivileged actor's capability (self-funded deposit, self-generated proof). No privileged role or victim key is needed.

### Recommendation
Include `relay`, `feeStructure` (or at least `flatFee`+`variableRate`+`feeToken`), `signerAddress`, and ideally a binding to `deltaAmountChanges`/`erc20TokenAddresses` inside `EMPORIUM_SIGNATURE_TYPEHASH` so the victim's signature fully constrains who is paid and how much. Additionally, move `usedMessages[...] = true` bookkeeping to occur before any external calls but ensure it cannot be trivially bypassed by making the whole flow idempotent/non-atomic-revert-safe (e.g., have `cancelEmporiumMessage`-style invalidation happen off-chain-triggered, or require the signature to also commit to a single-use nonce tied to the specific `circomData.calldataHash` so a stale signature cannot be paired with a different fee/relay context even before `usedMessages` is set).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a `HinkalWallet` for a victim signer; fund the wallet with an ERC20 fee token.
2. Have the victim sign a valid `EmporiumStack` (`ops`, `maxFee`, `deadline`) over some `emporiumMessage = M`, and build a legitimate `CircomData_A` with `relay = relayA`, `feeStructure.flatFee = F1`.
3. Submit `transact(A)` but force it to revert after `verifyWallet` runs (e.g. temporarily set `slippageValues` to cause the post-check `require` at `Hinkal.sol` line ~137-146 to fail). Assert `usedMessages[M] == false` after revert.
4. As attacker, build `CircomData_B` reusing the same `emporiumMessage = M`, same `stack.v,r,s,ops,maxFee,deadline`, but `relay = attackerRelay`, `feeStructure.flatFee = maxFee` (the max allowed), and a fresh valid proof for the attacker's own UTXOs consistent with `CircomData_B`.
5. Call `transact(B)` and assert it succeeds: `stack.ops` executed against victim's wallet, and `attackerRelay` balance increased by `flatFee` pulled from the victim's `HinkalWallet`, while `relayA` (the party the victim's flow originally intended) received nothing.
6. Assert the equality break: victim signed `(ops, maxFee)` expecting execution alongside `relay = relayA`/`feeStructure_A`, but the executed transaction paired the same `(ops, maxFee)` with `relay = attackerRelay`/`feeStructure_B` — values EMPORIUM_SIGNATURE_TYPEHASH never constrained.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }
