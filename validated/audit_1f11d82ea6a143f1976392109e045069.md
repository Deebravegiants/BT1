### Title
Webhook tenant identity (shop-domain/topic) not covered by HMAC, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw JSON body via `Utils::HmacValidator.validate(request)` [4](#0-3) . The `Request#to_signable_string` method used for that HMAC computation returns only `@raw_body` [1](#0-0) . However, `request.shop`, `request.topic`, and `request.webhook_id`, which are all taken verbatim from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) [2](#0-1) , are never included in the signed bytes, yet they are the fields the handler acts on as tenant/topic identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [5](#0-4) .

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == bytes the handler uses to determine tenant (shop) and event (topic)`. In this implementation that equality is broken — the HMAC only covers `@raw_body` [1](#0-0) , while `shop` and `topic`, which are used to route the webhook to a per-topic handler and to identify which merchant/tenant the event belongs to, come from unauthenticated headers [6](#0-5) .

Because Shopify signs webhook deliveries with the app-level `api_secret_key`/`client_secret` (shared across every shop that installs the app), rather than a per-shop secret, any attacker who can obtain one legitimate `(raw_body, hmac)` pair — for example by installing the target app on their own shop and capturing a webhook it triggers — has a signature that is valid for that exact body regardless of which shop or topic header accompanies it. `HmacValidator.validate` will accept that same body+hmac pair when replayed with attacker-chosen `shopify-shop-domain` and `shopify-topic` headers, because those headers are outside the signed content [7](#0-6) .

### Impact Explanation
`Registry.process` will treat the replayed request as authentic and hand the handler a `WebhookMetadata` object with a `shop` field of the attacker's choosing (e.g., a victim tenant that also has the app installed) alongside a topic of the attacker's choosing (e.g., a destructive or sensitive topic like `shop/redact`, `app/uninstalled`, or any topic the host app treats specially per shop) [8](#0-7) . Any host application logic that keys per-tenant state, deletion, deauthorization, or business processes off `WebhookMetadata#shop`/`#topic` can be triggered against a shop the attacker does not control, using only a signature obtained from their own installation — a cross-tenant confusion enabled entirely by this gem's webhook verification not binding the signed bytes to the claimed tenant/topic.

### Likelihood Explanation
Exploitation requires the attacker to install the same app in their own store (a normal, unprivileged action for any public/embedded app) and observe one webhook delivery — no leaked secrets, no privileged account, and no host misconfiguration are required. The replay is a routine HTTP POST to the app's public webhook endpoint with swapped headers and the same, still-valid, body/HMAC pair.

### Recommendation
Include the tenant-identifying and event-identifying fields (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for webhook HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., verify that the `X-Shopify-Shop-Domain` matches an expected/allow-listed shop for the session the webhook claims to belong to before dispatching). At minimum, document that `Registry.process` does not authenticate the `shop`/`topic` headers, and require host applications to independently verify `request.shop` against their own tenant registry before acting on the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers any webhook topic subscribed by the app, and captures the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC-SHA256(client_secret, B)`).
2. Attacker sends a new POST to the app's webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: <sensitive-topic>`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H`, returning `true` [10](#0-9) .
4. The handler registered for `<sensitive-topic>` receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and acts on it as if Shopify had genuinely delivered that event for that tenant [5](#0-4) .
