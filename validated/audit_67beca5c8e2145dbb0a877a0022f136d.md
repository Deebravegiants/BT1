### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's `shop` identity from an HTTP header, while the HMAC signature that `HmacValidator` checks is computed only over the raw request body. Any authentic, correctly-signed webhook body (e.g. one legitimately delivered for the attacker's own installed shop) can be replayed with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header pointing at a victim shop, and it will still pass HMAC validation, because the shop field is never part of the signed material.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop` is read from a separate, unsigned header: [3](#0-2) 

`Registry.process` validates the HMAC against `request.to_signable_string` (the body only) and then hands `request.shop` straight to the app's handler as the tenant identity, with no additional check that the shop matches the body or any installed-shop record: [4](#0-3) 

`HmacValidator.validate` in turn only recomputes the signature over `verifiable_query.to_signable_string`, i.e. the body: [5](#0-4) 

Because the signed material excludes the shop header, `shop == HMAC-authenticated shop` does not hold: the equality that actually holds is `HMAC(secret, body) == HMAC(secret, body)`, independent of which `shop` header accompanies that body. Any party who legitimately receives one authentic webhook for their own shop (e.g. by installing the app on their own store, which is not a privileged action) possesses a `(body, hmac)` pair that Shopify signed with the app's `api_secret_key`. That pair can be resent to the app's webhook endpoint with the `shop-domain` header rewritten to name a different, victim shop. `Registry.process` will still consider the HMAC valid and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` (i.e., `request.shop`) as the tenant key for storing or acting on webhook data — which is the documented/intended purpose of this field — can be made to attribute attacker-controlled webhook content to a different merchant's tenant. This is a cross-tenant data-integrity/confidentiality breach reachable by an unprivileged internet user who only needs to be a legitimate (even free/trial) merchant installer of the app to obtain one authentic signed webhook body, then forge the shop header on replay. No `api_secret_key`, access token, or other credential of the target is required.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook processing path as documented (`Registry.add_registration` + `Registry.process`), since the shop identity is exposed via `WebhookMetadata#shop` for exactly this purpose, and the gem provides no cross-check binding the shop header to the signed body or to a known/installed-shop registry. The only requirement is being able to send an HTTP POST with attacker-controlled headers and a previously captured, legitimately-signed body — both trivially available to any merchant who has installed the app once.

### Recommendation
Bind the shop identity into the material that is HMAC-verified (or independently verify that the `shop` header corresponds to a shop for which the app currently holds a valid, matching session/access token) before dispatching to webhook handlers, rather than trusting an unsigned header value as the tenant identifier in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook delivery (raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and finds it equal to `H` — validation succeeds [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled content under the victim shop's tenant identity.
