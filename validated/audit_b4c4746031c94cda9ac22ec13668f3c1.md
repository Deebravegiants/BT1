### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are read straight out of attacker-visible HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies the HMAC and, once it passes, builds `WebhookMetadata` directly from the unauthenticated `request.shop` field, which is handed to the app's handler as the tenant identity: [3](#0-2) 

The identity binding broken is: `shop` covered by the verified HMAC (∅, since `to_signable_string` excludes it) vs. `shop` trusted by the handler as the authenticated tenant context (`request.shop` from `shopify-shop-domain`/`x-shopify-shop-domain` header). Because the signature is computed only over the body with the app's shared `api_secret_key` (the same secret is used for every shop the app is installed on), any two valid `(body, hmac)` pairs are interchangeable across shops — the signature says nothing about which shop it belongs to.

### Impact Explanation
An unprivileged attacker who installs the target app on their own test/trial shop can capture a legitimate `(raw_body, hmac)` pair from a webhook Shopify sends them (this requires no privileges beyond running a free development store). They can then replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Utils::HmacValidator.validate` will pass (the body and secret are unchanged), and the handler will process attacker-controlled webhook data under the identity of the victim shop, since `WebhookMetadata.shop` is taken verbatim from the spoofed header. Depending on how the host app's webhook handler uses `shop` (typical usage is to look up/create/update per-tenant records, as documented in the gem's webhook usage guide), this enables cross-tenant data injection/corruption — a boundary the report class explicitly calls out ("a field acted on but not covered by the HMAC").

### Likelihood Explanation
Exploitation requires: (1) the app's webhook endpoint being reachable from the internet (true by design — Shopify calls it over HTTP), and (2) the attacker obtaining one valid `(body, hmac)` pair, which is trivially achievable by installing the app themselves on a free/dev shop and capturing its own webhook deliveries. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
- Include the shop-domain (and ideally topic/webhook-id) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is trusted.
- At minimum, document prominently that `request.shop` is not authenticated by the HMAC check and that consuming applications must independently corroborate the shop identity (e.g., against a previously stored, verified session/shop record) before using it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`), capturing a real delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid for the app's shared `api_secret_key`).
2. Attacker sends a forged HTTP request to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `shopify-hmac-sha256: H` (unchanged, still valid — it only signs the body)
   - `shopify-shop-domain: victim-shop.myshopify.com` (replaced)
   - `shopify-topic`, `shopify-webhook-id` set as desired
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds because it recomputes the HMAC over `raw_body` only: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied data as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
