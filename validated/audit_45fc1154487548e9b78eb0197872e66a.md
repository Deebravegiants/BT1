This confirms the structure: `attested_header.number` is purely metadata read from the SCALE-decoded `CodecHeader` struct in `BscClientUpdate`, and it is never bound to any cryptographic proof — the BLS aggregate signature only covers `VoteData { source_number, source_hash, target_number, target_hash }` [1](#0-0) , and `verify_bsc_header` only hash-checks `source_header`/`target_header` against `vote_data.source_hash`/`target_hash` [2](#0-1) . Nothing anywhere verifies `attested_header`'s own hash or `number` field. Yet `ismp/clients/bsc/src/lib.rs::verify_consensus` reads that unauthenticated `attested_header.number` to decide the security-critical validator-set promotion, before signature verification even runs [3](#0-2) .

### Title
Unauthenticated `attested_header.number` gates BSC validator-set rotation, allowing forged/early promotion of staged validators - (File: modules/ismp/clients/bsc/src/lib.rs)

### Summary
`BscClient::verify_consensus` decides whether to promote `next_validators` to `current_validators` using `bsc_client_update.attested_header.number` [4](#0-3) , but this field is never cryptographically bound to anything. The BLS aggregate signature verified later in `verify_bsc_header` only covers the RLP encoding of `VoteData` (`source_number`, `source_hash`, `target_number`, `target_hash`) [5](#0-4) , and the only header-hash checks tie `source_header`/`target_header` to those vote hashes [2](#0-1) . `attested_header` itself — including its `number` field — is read from attacker-supplied, SCALE-decoded bytes with zero hash/signature verification tying it to the signed vote or to the real BSC chain.

### Finding Description
This is the same bug class as CVE-2021-29657: a privileged decision is made using one read of untrusted, attacker-controlled data (`attested_header.number`), while the actual cryptographic validation happens against a *different* representation of the data (`vote_data.source_number`/`target_number`, `source_header`/`target_header` hashes) that is never cross-checked against the first read.

Concretely, in `verify_consensus`:
1. `attested_epoch = compute_epoch(bsc_client_update.attested_header.number.low_u64(), epoch_length)` is computed from the raw, unauthenticated header field [6](#0-5) .
2. If `attested_epoch == rotation_epoch && attested_number >= next_validators.rotation_block`, the pending `next_validators` set is immediately promoted to `current_validators` [7](#0-6) .
3. Only *after* this promotion does `verify_bsc_header` run the BLS signature check — against whichever set is now in `consensus_state.current_validators` [8](#0-7) .

Since `attested_header.number` is just a struct field inside the SCALE-encoded `BscClientUpdate` proof blob submitted by any permissionless relayer (via `pallet_ismp::Call::handle_unsigned` / `ConsensusMessage`), and it is never hash-checked or otherwise tied to the signed `vote_data`, an attacker can pair a genuinely BLS-signed vote (any legitimately captured `source_header`/`target_header`/`vote_data`/`agg_signature` tuple) with an arbitrarily forged `attested_header.number`. This lets the attacker force `attested_epoch`/`rotation_epoch` matching on demand — completely defeating the "bind rotation to the recorded `rotation_block`'s epoch" fix the code comments describe, since that fix assumes `attested_header.number` reflects real chain time, which it does not.

The comment block explicitly documents the threat this was meant to close ("an attacker holding the keys of a stale `next_validators` ... could submit an update many epochs later, get their set promoted") [9](#0-8) , but the gate it relies on is itself forgeable because it double-reads header data from two different trust domains without reconciling them.

### Impact Explanation
If an attacker can trigger promotion of a stale/compromised `next_validators` set into `current_validators`, that (now "current") validator set's genuine-but-stale signatures over a malicious `source_header` (with a forged `state_root`) become the trusted BSC state commitment recorded via `ismp::consensus::StateCommitment` [10](#0-9) . That state root then backs `verify_state_proof` for the BSC `EvmStateMachine`, enabling forged message delivery / unbacked state proofs for any ISMP request destined through the BSC light client — a High severity, protocol-reachable forgery of cross-chain state.

### Likelihood Explanation
Consensus proof submission for `pallet-ismp` is explicitly permissionless and free (`handle_unsigned`) [11](#0-10) , so any relayer can submit a crafted `BscClientUpdate`. The prerequisite is possession of one genuinely BLS-signed vote/header set from a validator set that was ever staged as `next_validators` (even one that later became stale/compromised) — this matches exactly the compromised-validator scenario the surrounding code comments already treat as a real threat to defend against, but the defense does not actually authenticate the field it relies on.

### Recommendation
Do not use `attested_header.number` (or any other field of `attested_header`) for security decisions unless it is cryptographically bound to the verified data. Either:
- Verify `attested_header`'s hash against a value covered by the aggregate signature (e.g., require the signed vote's `target_hash`/`source_hash` to relate `attested_header` to `target_header`/`source_header`, or hash-check `attested_header` itself against known chain data), or
- Derive the epoch/rotation decision solely from `source_header.number` / `target_header.number`, which are already hash-verified against `vote_data` in `verify_bsc_header`, instead of the unauthenticated `attested_header.number`.

### Proof of Concept
1. Obtain any one legitimately BLS-signed vote attestation from a validator set that was, at some point, staged as `next_validators` for a given `rotation_block` (e.g., captured from the real chain, or from a validator set later retired/compromised).
2. Construct a `BscClientUpdate` using the real `source_header`, `target_header`, and `attested_header.extra_data` (carrying the genuine `agg_signature`/`vote_data`), but overwrite `attested_header.number` to any value satisfying `compute_epoch(attested_number, epoch_length) == compute_epoch(next_validators.rotation_block, epoch_length)` and `attested_number >= next_validators.rotation_block`.
3. Submit via `pallet_ismp::Call::handle_unsigned` as a `Message::Consensus` targeting the BSC consensus client. `verify_consensus` promotes `next_validators` to `current_validators` based on the forged `attested_header.number` before the BLS signature is checked against the (now-promoted) set, since the signature itself was genuinely produced by that set.
4. With the compromised/stale set now `current_validators`, submit a further update with a forged `source_header.state_root` signed by that set to poison the BSC state commitment used by `verify_state_proof`.
