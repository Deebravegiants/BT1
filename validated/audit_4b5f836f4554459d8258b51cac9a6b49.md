### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` identifier used to attribute the webhook to a tenant is taken from an HTTP header that is never included in the signed material. This breaks the identity binding `shop authenticated == shop used as tenant key`, letting an attacker who possesses one validly-signed webhook body (e.g., from a store they themselves control) relabel it as belonging to any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`/`webhook_id`) values are read from headers that are completely outside the signable string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates acceptance purely on that body-only HMAC check, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity passed to the app's handler: [4](#0-3) 

Because `shop` is never part of the signed payload, the equality the gem implicitly claims — "HMAC-verified request" ⇒ "the `shop` field is authentic for that request" — does not hold. An attacker only needs one legitimately-signed webhook body (obtainable by installing the app on a shop they control and triggering any webhook topic) to swap the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to any victim shop domain, while keeping the original body and its still-valid `hmac-sha256` header. `HmacValidator.validate` returns `true` (the body/HMAC pair is unchanged and genuinely valid), and `Registry.process` dispatches to the registered handler with `shop: request.shop` equal to the attacker-chosen victim domain.

### Impact Explanation
Host applications built on this gem key almost all tenant-scoped logic (data lookups, writes, uninstall/GDPR handling, billing, inventory updates, etc.) off the `shop` value delivered in `WebhookMetadata#shop`. Since the gem itself asserts the webhook is authentic once `HmacValidator.validate` passes, and simultaneously feeds an unauthenticated header as the tenant key to the handler, an attacker with no credentials for the victim can cause the host app to execute cross-tenant actions/writes attributed to a shop they do not own. This meets the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only: (1) the attacker installs the app on their own store or otherwise obtains any single genuinely-signed webhook body/HMAC pair for the target app, and (2) the ability to send an HTTP POST to the app's public webhook endpoint with a modified shop header — no `api_secret_key`, access token, or privileged account is needed. This is fully reachable by an unprivileged internet user through the gem's own documented `Registry.process` entry point.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signature verification, e.g. by requiring the host application to independently verify that `request.shop` corresponds to a shop with an active, matching installation/session before dispatch, or by having `HmacValidator`/`Request#to_signable_string` incorporate the shop header (or an out-of-band verified value) into the value that is compared, so that a body/HMAC pair cannot be replayed under a different shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the resulting valid `X-Shopify-Hmac-Sha256: H` header (`H` is a legitimate signature of `B` under the app's real `api_secret_key`, since Shopify itself signed it).
2. Attacker resends the identical body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, causing the host app to process attacker-controlled data as if it originated from the victim tenant.
