### Title
Out-of-memory DoS via unbounded Borsh allocation when decoding JSON-RPC-submitted transactions - (File: `chain/jsonrpc/src/api/transactions.rs`)

### Summary
The JSON-RPC entry points for submitting and querying transactions (`broadcast_tx_async`, `broadcast_tx_commit`, `tx`) decode the attacker-supplied `signed_tx_base64` payload straight into a `SignedTransaction` via `SignedTransaction::try_from_slice(&bytes)`, with no upper bound on the Borsh-encoded byte size enforced before decoding. [1](#0-0)  This mirrors the gnark advisory's root cause: length-prefixed fields inside a serialized structure are trusted to allocate memory before any content-size validation happens, letting a small on-wire request trigger a disproportionately large allocation.

### Finding Description
`decode_signed_transaction` is invoked by both `RpcSendTransactionRequest::parse` and `RpcTransactionStatusRequest::parse`, which are the parsers for the unauthenticated JSON-RPC methods that submit or query transactions. [2](#0-1)  The function only base64-decodes the string and immediately calls Borsh's `try_from_slice` on the resulting bytes, with no size gate applied first: [1](#0-0) 

Any real bound on transaction size (`max_transaction_size` from `RuntimeConfig`) is only enforced later, inside `ValidatedTransaction::check_valid_for_config`, i.e. **after** the Borsh decode has already completed and allocated memory for every nested `Vec`/`String` field the wire bytes describe: [3](#0-2) 

By contrast, the P2P network layer already recognizes this exact bug class and mitigates it explicitly: `chain/network/src/network_protocol/proto_conv/peer_message.rs` enforces `MAX_TRANSACTION_SIZE_BYTES`/`MAX_ROUTED_MESSAGE_SIZE_BYTES` via `try_from_slice_with_limit` *before* Borsh-decoding a peer-supplied transaction or routed message, with comments stating the purpose is to prevent "a maliciously inflated peer payload" from forcing "a large allocation at decode time": [4](#0-3) [5](#0-4) 

No equivalent gate exists on the JSON-RPC ingestion path in `chain/jsonrpc/src/api/transactions.rs`, even though this is the primary path an unprivileged, unauthenticated external client uses to submit transactions to a node.

### Impact Explanation
Because `SignedTransaction`/`Transaction`/`Action` are Borsh structures containing nested length-prefixed collections (e.g., `Vec<Action>`, `FunctionCallAction::args: Vec<u8>`, `DeployContractAction::code: Vec<u8>`, `AddKeyAction` method-name lists), a crafted (but small, since only the declared length field needs to be large relative to actual trailing bytes for certain Borsh decode strategies, or simply a base64 string that decodes to a request with an inflated declared length) payload can force the node to allocate memory disproportionate to the actual request size before any `max_transaction_size`/`max_contract_size`/`max_arguments_length` check runs. Repeated requests can exhaust node memory, causing a crash (`out of memory`) or severe service degradation — a node panic / unbounded resource use DoS reachable from any external RPC caller, not requiring a validator, peer, or privileged account.

### Likelihood Explanation
High: JSON-RPC is the standard, unauthenticated, publicly exposed submission path for every NEAR node (used by wallets, indexers, and the `broadcast_tx_*`/`tx` RPC methods). No authentication, staking, or prior on-chain state is required to reach `decode_signed_transaction`. The nearcore team has already recognized and patched this precise bug class at the network/peer layer, but the JSON-RPC ingestion path was left with no analogous size gate before Borsh decoding.

### Recommendation
Apply the same defense used in `chain/network/src/network_protocol/proto_conv/util.rs` (`try_from_slice_with_limit`) to `decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs`: reject the base64-decoded byte slice if its length exceeds a conservative upper bound (e.g., the same `MAX_TRANSACTION_SIZE_BYTES` constant, or the node's configured `max_transaction_size` with margin) before calling `SignedTransaction::try_from_slice`.

### Proof of Concept
1. Craft a Borsh-encoded `SignedTransaction` byte buffer whose outer wire size is small but which declares nested collection lengths (e.g., an `Action::FunctionCall` with an inflated `args` `Vec<u8>` length prefix, or a `Transaction::actions` `Vec<Action>` length prefix) far larger than the number of bytes actually supplied after it.
2. Base64-encode the crafted buffer and submit it as `signed_tx_base64` to the JSON-RPC `broadcast_tx_async` (or `tx`) method.
3. Observe that `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs:71-76`) calls `SignedTransaction::try_from_slice` directly, attempting to allocate memory sized to the declared (attacker-controlled) length before `ValidatedTransaction::check_valid_for_config`'s `max_transaction_size` check ever executes, unlike the equivalent, already-mitigated path in `chain/network/.../peer_message.rs`.
4. Repeat/parallelize the request to amplify memory pressure and induce OOM on the target node.

fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))?;
    SignedTransaction::try_from_slice(&bytes)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))
}

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}

/// Upper bound on the Borsh-encoded size of a peer-supplied transaction body,
/// enforced before the body is deserialized to mitigate maliciously inflated
/// transactions exhausting node memory at decode time. Set comfortably above
/// the largest valid transaction (`max_transaction_size`, historically 4 MiB)
/// and far below the 512 MiB peer-frame cap.
const MAX_TRANSACTION_SIZE_BYTES: usize = 16 * MIB as usize;

/// Upper bound on the Borsh-encoded size of a peer-supplied routed-message body,
/// enforced before it is deserialized so a maliciously inflated payload (e.g. a
/// `ForwardTx` carrying an oversized delegate action) cannot exhaust node memory
/// at decode time.
const MAX_ROUTED_MESSAGE_SIZE_BYTES: usize = 64 * MIB as usize;
