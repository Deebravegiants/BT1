Confirmed root cause: `Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-199` validates the webhook HMAC via `Utils::HmacValidator.validate(request)`, but the signable string used for that validation, `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`, is defined as `@raw_body` only. The `shop` value that is subsequently trusted and forwarded to the host app's handler (`request.shop`, read from the `X-Shopify-Shop-Domain` HTTP header at `lib/shopify_api/webhooks/request.rb:20-23`) is never included in the HMAC-signed bytes. This is the exact bug class from the report: a field that is acted upon (`shop`, used as the tenant identifier in `WebhookMetadata`) is not covered by the HMAC that is supposed to authenticate the whole request.

### Title
Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only [1](#0-0)  , while the shop identity used by `Registry.process` to build `WebhookMetadata` (and thus dispatched to the app's handler) is taken from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1)  . `Registry.process` validates only that HMAC before dispatching, and never checks that the header-derived `shop` is consistent with anything inside the signed body [3](#0-2)  .

### Finding Description
The binding that should hold is: `authenticated(shop_used_for_tenant_routing) == shop_covered_by_HMAC(secret)`. In this gem it does not — `shop` is read straight from a header, and the header is explicitly excluded from the HMAC-signed material (`to_signable_string` returns `@raw_body`, never headers) [4](#0-3)  . `Utils::HmacValidator.validate` only proves the `raw_body` bytes were signed by the app's secret; it says nothing about which header values accompanied that body [5](#0-4)  . `Registry.process` then unconditionally trusts `request.shop` to construct `WebhookMetadata` passed to the handler [6](#0-5)  . An attacker who can produce (or replay/relay) any HTTP request carrying a body+HMAC pair that validates for the app's secret — e.g., by capturing a legitimate webhook delivery for their own trial/test shop (attacker is an authenticated merchant of their own store, receiving real, validly-signed webhooks for that store) — can resend that exact body with the `shopify-shop-domain` header swapped to a victim shop domain. The HMAC still validates because it never covered the header, and the framework will hand the (attacker-controlled-domain, but victim-domain-labeled) payload to the app's per-tenant webhook handler as though it originated from the victim shop.

### Impact Explanation
This crosses the tenant boundary that HMAC validation is meant to enforce: the header value used to select/attribute the tenant is not part of the signed content, enabling data to be attributed to, or injected into, a different tenant's flow than the one that produced it. Depending on how host applications key their `handler.handle` logic (many apps trust `WebhookMetadata#shop` to select which merchant's local database row/session to update — this is the officially documented purpose of that field) this can cause cross-tenant data confusion/injection (e.g., faking `orders/create`, `app/uninstalled`, `customers/data_request` events as if they came from a different shop). This matches the "Cross-tenant access" Critical impact category, since the identity used to route or record webhook effects for a tenant can be forged despite the HMAC check reporting success.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid (body, HMAC) pair — most straightforwardly obtainable by having their own Shopify store subscribe to the same app and topic (a mandatory/available capability for any merchant who installs a public or unlisted app), then replaying that body with a spoofed `shop-domain` header value. No secret material is required beyond a legitimately-received webhook of their own. This is a realistic, unprivileged-attacker path rather than a hand-wavy hypothetical, since the gem itself performs no cross-check between the signed body and the header-derived shop.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) in the HMAC-signable material, or validate that any header-derived tenant identifier used downstream is corroborated by data inside the signed body before constructing `WebhookMetadata`. Concretely, change `Request#to_signable_string` to bind `shop`, `topic`, and `webhook_id` alongside `raw_body`, or have `Registry.process` cross-validate `request.shop` against a shop value embedded in `parsed_body` before dispatch.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimately signed webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `HmacValidator.validate` only signs `B`) [7](#0-6)  .
2. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body `B` and HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [8](#0-7)  .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` even though the body/signature actually originated from the attacker's own store [9](#0-8)  .
5. The host application's `handler.handle` receives data falsely attributed to `victim-shop.myshopify.com`, causing cross-tenant effects (e.g. writing attacker-controlled order/customer data into the victim tenant's records) despite the HMAC check reporting success.
