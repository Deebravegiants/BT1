### Title
Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: `lib/shopify_api/webhooks/request.rb`](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop` value used to attribute the webhook to a tenant is read from the unsigned `X-Shopify-Shop-Domain` header. Any party capable of producing one valid `(body, hmac)` pair — such as a merchant who has legitimately installed the app on their own store and receives real signed webhooks for it — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the attacker-controlled payload to the app's handler under the victim's shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over `request` (i.e., over `to_signable_string`, the raw body) and then, on success, forwards `request.shop` — the unauthenticated header — straight to the registered handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever checks `verifiable_query.to_signable_string` against the HMAC secret; it has no knowledge of, and does not bind, any header field such as shop domain: [4](#0-3) 

The broken identity binding, expressed as an equality that the code fails to enforce:
`HMAC-authenticated-bytes (raw_body)` ≠ `shop-attribution-used-by-app (shop-domain header)`.

Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app, any merchant who installs the app receives their own legitimately-signed webhooks (valid `hmac-sha256` header for their own `raw_body`). That merchant can capture one such `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header changed to point at a different (victim) shop. Since the HMAC never covers the shop header, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is the attacker-chosen victim domain but `body` is the attacker's own (fully attacker-controlled, since they control what data exists on their own store to trigger a particular webhook body) content.

### Impact Explanation
This crosses a tenant boundary without any privileged credential: a normal (unprivileged, in the multi-tenant sense) merchant/installer of the app can make the app process arbitrary body content it fully controls under an arbitrary other shop's identity. Depending on how the host app's webhook handlers use `shop` (e.g., to update per-shop billing/subscription state, to fulfill GDPR `customers/redact` / `customers/data_request` / `shop/redact` mandatory webhooks, or to key persisted records), this enables cross-tenant data corruption or spoofed mandatory-compliance actions attributed to a shop that never sent that data — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is non-trivial: obtaining a valid `(body, hmac)` pair requires no secret knowledge beyond installing the app on one's own shop (a normal, unprivileged action), and only the `shop-domain` header (never validated against the signature) needs to be swapped before replay to the shared webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable string for webhooks, or otherwise cryptographically bind the `shop-domain` header to the signed payload (Shopify's actual current webhook contract signs only the body, so this may require the gem to additionally validate that `shop-domain` matches an expected/known shop for the receiving endpoint, or that the topic-declared shop in the JSON body — where present — matches the header, before dispatching to handlers).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g. `customers/data_request`) so their store legitimately receives:
   - `X-Shopify-Hmac-Sha256: <valid hmac over raw_body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `raw_body: <attacker-controlled JSON>`
2. Attacker resends the exact same request to the app's webhook endpoint, only changing the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the untouched raw body) against the HMAC — validation succeeds.
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop = "victim.myshopify.com"` and the attacker's chosen body, and passed to the app's registered handler, which acts as if `victim.myshopify.com` sent that payload.
