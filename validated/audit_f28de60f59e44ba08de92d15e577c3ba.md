### Title
Unmetered full trie scan in `compute_gas_key_balance_sum` allows gas-key flooding DoS on `action_delete_account` - ([File: core/store/src/utils/mod.rs])

### Finding Description
`compute_gas_key_balance_sum` (`core/store/src/utils/mod.rs:458-497`) takes a `TrieUpdate` and an `AccountId` and performs a full trie iteration over `trie_key_parsers::get_raw_prefix_for_access_keys(account_id)` via `state_update.locked_iter(...)`, then for every returned key does an additional keyed lookup with `get_access_key_by_handle` to fetch and sum gas-key balances. The function's signature takes no gas counter, `ActionResult`, or compute-accounting parameter, so none of the trie reads or key-parsing work it performs is charged against the transaction's prepaid gas or the chunk's compute limit.

This function is invoked from `action_delete_account` in `runtime/runtime/src/actions.rs` (imported at line 37, called within the function body) as part of validating a `DeleteAccount` action, before the storage/large-state and `GasKeyBalanceTooHigh`-style checks that would otherwise reject an account with excessive gas keys. Because an ordinary account holder fully controls their own account's key set — adding `AccessKeyPermission`/gas-key entries is a normal, attacker-reachable operation (e.g., via `AddKey` actions or gas-key creation flows) up to whatever storage-staking/key-count limits exist — the attacker can populate their own account with the maximum number of low-balance gas keys the protocol allows before storage-staking rejects further additions. When they then submit a `DeleteAccount` action against that account, `action_delete_account` unconditionally triggers `compute_gas_key_balance_sum`, which walks every gas-key trie entry and performs a corresponding `AccessKey` lookup per entry — all before any gas/compute cost proportional to that I/O has been deducted.

### Impact Explanation
This falls under the "gas or storage metering bypass" / "chunk stall or node crash / unbounded resource use" bounty classes: a validator (chunk producer) applying the `DeleteAccount` receipt must perform O(N) trie reads and access-key deserializations for N gas keys, but the sender is only charged the fixed, N-independent `action_delete_account` action cost. If N can be made large (bounded only by storage-staking economics for creating many gas keys, not by an explicit low cap tied to this operation's gas cost), the attacker gets disproportionately cheap (or free relative to actual work done) validator compute time, which can be repeated across many accounts/receipts to degrade chunk-application throughput.

### Likelihood Explanation
Feasibility depends entirely on how cheap it is to store many gas keys under storage staking — since each gas key occupies trie storage that must be staked for, the attacker's cost scales with N via storage deposit, not via gas. Storage staking is a NEAR-token deposit, not a gas cost, so this doesn't directly let the attacker "print" free CPU cycles for others; it does let them pre-pay (via locked storage stake, refundable on deletion) for an asymmetric, uncharged validator-side workload trigger. The exact severity depends on the maximum number of gas keys permitted per account under the account's storage balance and the per-key trie/storage cost of the read+parse+lookup work, which were not fully enumerable from the available code in this session.

### Recommendation
Charge compute/gas for `compute_gas_key_balance_sum` proportional to the number of gas keys iterated and the trie nodes touched — e.g., accept an `ActionResult`/gas counter parameter and deduct a per-key-iterated cost (similar to how `storage_removes_compute` charges for removal operations), so the cost of resolving `GasKeyBalanceTooHigh`/large-state checks in `action_delete_account` is fully metered before or during the scan, not only via the fixed base action fee.

### Proof of Concept
1. Create an account and fund it with enough NEAR to storage-stake the maximum number of gas keys allowed by protocol/storage-staking rules.
2. Add gas keys (via repeated `AddKey`-style / gas-key-creation actions) until storage staking prevents adding more (recording N).
3. Submit a `DeleteAccount` action for that account.
4. Instrument or benchmark `compute_gas_key_balance_sum` invocation inside `action_delete_account` to measure wall-clock time / trie-read count, and compare against the fixed gas cost charged for the `DeleteAccount` action.
5. Assert: measured I/O/time scales linearly with N while the charged gas for the action remains constant, demonstrating the metering gap. (Exact numeric limits for N, the per-gas-key storage cost, and the fixed `DeleteAccount` action fee were not directly confirmed in this session and should be verified against `core/parameters/res/runtime_configs/parameters.yaml` and the storage-staking implementation before finalizing severity.)
