Audit Report

## Title
CORS `isAllowedOrigin` wildcard suffix match lacks dot-boundary check, allowing origin allowlist bypass - (File: `core/services/gateway/network/httpserver.go`)

## Summary
The gateway's `httpServer.isAllowedOrigin` function validates wildcard CORS allowlist entries (e.g. `https://*.ethereum.org`) using a bare `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, without verifying a `.` boundary precedes the match. This allows an attacker-registered domain such as `evilethereum.org` to satisfy the suffix check for an allowed domain `ethereum.org`, even though it is not a genuine subdomain.

## Finding Description
In `core/services/gateway/network/httpserver.go`, the wildcard match block: [1](#0-0) 
strips the `*.` prefix off the allowed host and then performs a plain suffix comparison. There is no check that `originHost[len(originHost)-len(allowedHost)-1] == '.'`, so any origin host ending in the same character sequence as the allowed domain (with no dot separator) will incorrectly pass. This function is invoked directly from the request-handling entry point: [2](#0-1) 
which reflects the raw `Origin` header value back as `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true, allowing the attacker's page to read cross-origin responses via the browser CORS mechanism. No other validation, redaction, or boundary check exists upstream to catch this. The existing test suite (`httpserver_test.go`) only exercises non-matching-suffix cases (e.g. `ethereum.remix.org` vs `*.ethereum.org`), and does not cover the "ends with allowed suffix but has no dot boundary" scenario, so this bypass is untested and unguarded.

## Impact Explanation
This is a genuine allowlist-bypass in an internet-facing HTTP server component (`UserServerConfig`). An operator who intentionally scopes cross-origin access to a domain family via a wildcard entry has that restriction silently weakened: any attacker who registers a domain ending in the same suffix (e.g. `evilethereum.org`, `notethereum.org`) can have their page's origin accepted, receive a reflected `Access-Control-Allow-Origin` header, and successfully read the JSON-RPC responses from the gateway's user endpoint cross-origin. This maps to the in-scope "allowlist bypass" / "gateway request impersonation via cross-origin response reading" impact category.

## Likelihood Explanation
Exploitation requires only registering an appropriately-suffixed domain and hosting a static page there — no credentials, no privileged role, and no compromise of any node or peer are needed. It is triggerable purely as an unprivileged web client interacting with the gateway's public HTTP endpoint, and is fully repeatable.

## Recommendation
Require a dot boundary (or exact match) when validating wildcard suffixes:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```

## Proof of Concept
1. Configure the gateway's `UserServerConfig.CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From an unprivileged client, send an HTTP request to the gateway's user-facing endpoint with header `Origin: https://evilethereum.org`.
3. Observe the server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, confirming `isAllowedOrigin` incorrectly returned `true` for a non-subdomain look-alike origin.
4. This can be codified as a Go unit test in `httpserver_test.go` analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, but asserting that `origin := "https://evilethereum.org"` against allowed `"https://*.ethereum.org"` incorrectly yields a non-empty `Access-Control-Allow-Origin` header.
