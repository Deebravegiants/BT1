### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted as authenticated metadata despite being excluded from the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (and other headers) to the app's handler as if it were verified, trusted identity metadata. In reality, `Webhooks::Request#to_signable_string` returns only the raw HTTP body — none of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers are covered by the HMAC. Any caller who can produce one HMAC-valid `(secret, body)` pair for the app (e.g., a merchant who legitimately installed the app and received a genuine webhook, since the app's `client_secret` is shared across every shop that installs it) can replay that exact body with an arbitrary `shop-domain` header and have it accepted as coming from a different, unrelated shop.

### Finding Description
`Registry.process` binds trust to `Utils::HmacValidator.validate(request)`, which only proves the raw body has not been altered relative to a secret the requester possesses: [1](#0-0) 

The signable content computed for that check is exclusively the raw body: [2](#0-1) 

and `HmacValidator.validate_signature` verifies HMAC purely over `to_signable_string`: [3](#0-2) 

The identity binding that should hold is: `shop` field trusted by the handler == `shop` that produced/owns the HMAC-signed payload. Because `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from unauthenticated headers, this equality is never enforced — the gem authenticates "bytes of the body" but acts on "bytes of the header" as if they were the same trust domain. `WebhookMetadata` is then constructed with this unauthenticated `shop` and handed to the app's business logic as verified data: [1](#0-0) 

Since Shopify apps share one `client_secret` across every shop that installs the app, an attacker only needs to be a legitimate merchant of the same public/custom app to obtain valid `(body, hmac)` pairs from their own genuine webhook deliveries. They can then replay that exact body to the app's webhook endpoint while setting `x-shopify-shop-domain` (and/or `x-shopify-topic`) to a victim shop, or to any shop string of their choosing, and the HMAC check still passes because the header is never part of the signed content.

### Impact Explanation
This breaks the tenant boundary the app relies on: `request.shop`/`data.shop` is the value apps typically use as the tenant key to route webhook effects (e.g., look up the merchant's stored `access_token`/session, update per-shop records). An attacker-controlled `shop` value with a validly-HMACed body lets an attacker cause the app to process an event under an arbitrary/victim shop identity — a cross-tenant access primitive, matching the Critical impact category.

### Likelihood Explanation
Requires only: (1) the attacker be a merchant who has legitimately installed the target app (unprivileged, self-serve — no special access to the victim), and (2) at least one genuine webhook delivery to capture a valid `(body, hmac)` pair, which happens automatically once webhooks are registered. No access to `api_secret_key`, tokens, or the victim's credentials is needed. This is a low-effort replay, not theoretical.

### Recommendation
Bind the identity fields into what's authenticated: include `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-signable content (or otherwise cryptographically bind them, e.g., by validating them against a signed claim from Shopify), and/or clearly document in `WebhookMetadata`/`Request` that `shop`/`topic` are unauthenticated and must not be used as a trust boundary without additional verification. At minimum, `Registry.process` should not label `request.shop` as safe-to-use tenant identity when only the body has been verified.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. App sends attacker a genuine webhook, e.g. `orders/create`, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <H>`, and body `B` (HMAC computed only over `B`, per `Request#to_signable_string`).
3. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: <H>`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` passes because it only checks `H` against `B`.
5. The handler executes with `data.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop — a forged cross-tenant webhook event.
