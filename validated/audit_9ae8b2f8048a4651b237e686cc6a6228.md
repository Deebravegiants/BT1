### Title
Permissionless `superApprove()` grants unlimited ERC20 allowance from any owner to any spender - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` is `public`, carries no access control (no `onlyRole`, no `msg.sender == owner` check), and directly calls `_approve(owner, spender, type(uint256).max)`. Because this token is deployed as the live fee-token on non-mainnet Hyperbridge deployments (`evm/script/DeployIsmp.s.sol:100-107`) and is minted to arbitrary users via the public `TokenFaucet.drip()`, any address holding a balance of this fee token can have its balance drained by anyone who calls `superApprove(victim, attacker)` followed by `transferFrom`.

### Finding Description
`_approve` in OpenZeppelin's `ERC20` sets `owner`'s allowance for `spender` unconditionally — it performs no authorization check on the caller, that check is expected to be done by the wrapping function. `HyperFungibleTokenImpl.superApprove` exposes this internal primitive as a fully public function with the `owner` parameter attacker-controlled and no restriction tying it to `msg.sender`:

```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
``` [2](#0-1) 

Any account can call `superApprove(victim, attacker)` to set `attacker`'s allowance over `victim`'s balance to `type(uint256).max`, then immediately call `transferFrom(victim, attacker, victim.balanceOf())` to steal the entire balance. This is strictly worse than the referenced H-2 pattern (a DOS from resetting an approval to zero): here the unauthorized public "approve" primitive enables outright theft of funds, not just griefing.

The token is not test-only scaffolding — it is wired into the production deployment script as the fee token collected by `EvmHost.dispatch` for every POST/GET request on non-mainnet chains, and users acquire balances of it through the public, unauthenticated `TokenFaucet.drip()` faucet:

```solidity
function drip(address token) public {
    ...
    HyperFungibleTokenImpl(token).mint(msg.sender, 1000 * 1e18);
}

### Impact Explanation
Any user of the Hyperbridge fee token on a deployment using `HyperFungibleTokenImpl` (all non-mainnet/testnet environments deployed via `DeployIsmp.s.sol`) has their entire token balance permanently stealable by an unprivileged attacker with a single unauthorized `superApprove` + `transferFrom` call pair. This directly enables theft of funds and, since this is the fee token collected by `EvmHost.dispatch` for every dispatched request, an attacker draining a relayer's or user's fee-token balance can also disrupt their ability to pay dispatch fees, cascading into a denial of Hyperbridge message dispatch for the victim.

### Likelihood Explanation
High. The function is `public`, requires no privileged role, no signature, and no preconditions beyond the victim holding a nonzero balance. It is trivially reachable by any address able to submit a transaction, and the victim set (anyone who used `TokenFaucet.drip()` or otherwise received this fee token) is broad by design.

### Recommendation
Remove `superApprove` from production code entirely, or restrict it to a test-only mock contract that is never referenced from `DeployIsmp.s.sol`. If a helper is genuinely needed for testing infrastructure, gate it behind `msg.sender == owner`, an admin role, or move it into a dedicated `Mock`/test contract that is excluded from any deployment script.

### Proof of Concept
1. Deploy `HyperFungibleTokenImpl` as done in `DeployIsmp.s.sol` (non-mainnet path) and grant `TokenFaucet` the `MINTER_ROLE` as scripted. [4](#0-3) 
2. Victim calls `TokenFaucet.drip(feeToken)` and receives `1000e18` fee-token units. [3](#0-2) 
3. Attacker (no role, no relationship to victim) calls `HyperFungibleTokenImpl(feeToken).superApprove(victim, attacker)`. [2](#0-1) 
4. Attacker calls `IERC20(feeToken).transferFrom(victim, attacker, 1000e18)`, draining the victim's entire balance.
