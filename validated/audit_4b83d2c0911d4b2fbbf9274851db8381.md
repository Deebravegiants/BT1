### Title
NULL Pointer Dereference (Crash/DoS) in Vault Gateway `handlePublicKeyGet` via Missing `params` Field - (File: core/capabilities/vault/gw_handler.go)

### Summary
The CVE describes a NULL pointer dereference in libarchive's ACL parser that is triggered when it processes attacker-supplied archive data without validating that a pointer is non-nil before dereferencing it, causing a crash. The chainlink `GatewayHandler.HandleGatewayMessage` for the Vault capability contains a directly analogous pattern: for the `MethodPublicKeyGet` JSON-RPC method, the request `Params` field (`*json.RawMessage`, i.e. a pointer) is dereferenced with `json.Unmarshal(*req.Params, r)` without first checking it for `nil`, unlike the sibling methods `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList`, which are routed through `h.requestProcessor.ProcessRequest` first.

### Finding Description
In `core/capabilities/vault/gw_handler.go`, `HandleGatewayMessage` dispatches on `req.Method`: [1](#0-0) 

For `vaulttypes.MethodPublicKeyGet`, the handler calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly, bypassing `h.requestProcessor.ProcessRequest`, which is the code path used for the other Secrets methods: [2](#0-1) 

`handlePublicKeyGet` then unconditionally dereferences `req.Params`: [3](#0-2) 

`req.Params` is typed as `*json.RawMessage` in the generic `jsonrpc.Request[json.RawMessage]` struct; other call sites in the codebase (e.g. `core/services/gateway/handlers/common/message_util.go` and `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) explicitly guard against `req.Params == nil` before dereferencing it, confirming this is a recognized nil-pointer hazard in this codebase: [4](#0-3) [5](#0-4) 

`handlePublicKeyGet` has no equivalent guard, so a request whose `params` field is omitted (making it JSON `null`, decoded to a nil pointer) will panic on `*req.Params`.

### Impact Explanation
Messages reaching `HandleGatewayMessage` originate from the internet-facing Gateway relaying JSON-RPC requests from unprivileged external clients to the node. A crafted request for the `MethodPublicKeyGet` method with a missing/null `params` field triggers a Go nil-pointer-dereference panic inside the node process. Because this occurs before any request validation/authorization step (`ProcessRequest`/`Authorizer`) is invoked for this specific method, it is reachable pre-auth relative to the vault secrets pipeline. An unrecovered panic in this call path can crash the node process handling the Vault capability, matching the CWE-476/Crash-DoS impact class of the CVE.

### Likelihood Explanation
High likelihood if reachable: no authentication or schema validation gates the `params` field before the dereference for this method, and constructing a JSON-RPC request without a `params` field (or with `"params": null`) is trivial for any client able to reach the gateway's public-key-get endpoint.

### Recommendation
Add an explicit nil check for `req.Params` in `handlePublicKeyGet` (mirroring the pattern already used elsewhere in the codebase, e.g. `common.ValidatedMessageFromReq` and `httpTriggerHandler.validatedTriggerRequest`) and return a `UserMessageParseError`/`ErrInvalidRequest` response instead of dereferencing a possibly-nil pointer. Additionally, verify whether `MethodPublicKeyGet` should also flow through `requestProcessor.ProcessRequest` for consistency with the other Vault methods.

### Proof of Concept
Send a Gateway JSON-RPC request such as:
```json
{
  "jsonrpc": "2.0",
  "id": "poc-1",
  "method": "vault.publicKeyGet"
}
```
(i.e., omitting the `params` field entirely, or supplying `"params": null`). When routed to `GatewayHandler.HandleGatewayMessage` → `handlePublicKeyGet`, `req.Params` decodes to `nil`, and the line `json.Unmarshal(*req.Params, r)` dereferences a nil pointer, panicking the goroutine/process handling the message.

**Note on confidence**: I was not able to fully trace whether `HandleGatewayMessage` for the vault handler runs the panic-prone code in a goroutine with a `recover()` wrapper at a higher level (e.g. in the connector or gateway dispatch loop), which would determine whether this crashes only the single request handling routine or the whole node process. This should be verified by a maintainer/agent with full codebase access before treating this as a definite node-crashing DoS versus a contained per-request panic.
