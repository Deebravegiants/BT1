**Rationale:** The premise assumes `lhs` (the framework "hook" function) in `native_check_dispatch_type_compatibility_impl` could be attacker-crafted, but tracing the actual call path shows it never is. `check_dispatch_type_compatibility_impl` is a `native` function reachable only via the Move wrapper `check_dispatch_type_compatibility`, whose `framework_function` argument is always hardcoded by the framework itself in `register_dispatch_functions` (e.g., `function_info::new_function_info_from_address(@aptos_framework, string::utf8(b"dispatchable_fungible_asset"), string::utf8(b"dispatchable_withdraw"))`), not by the caller of the entry function. [1](#0-0) 

The attacker only controls the `dispatch_target` (`rhs`) argument — the candidate withdraw/deposit/derived-balance hook they wrote — never the `lhs` side, which is always resolved to a real, fixed, well-formed framework function (`dispatchable_withdraw`, etc.) with a module address pinned to `@aptos_framework`. Since that module/function is part of the shipped framework, `lhs.param_tys()` can never be empty in this call path, so the `is_empty()` guard in the native is not a bypassable custody boundary — it is a defensive invariant check on a value the attacker cannot influence. [2](#0-1) 

Even hypothetically, if the compatibility check incorrectly returned `true` for a malformed target, the actual dispatch invocation at runtime independently re-validates `function.param_tys().is_empty()` and type compatibility against the real framework native's declared signature before performing `CallFunction`, providing a second, independent enforcement point at the interpreter level rather than relying solely on the Move-level boolean. [3](#0-2) 

There is no unprivileged entrypoint that lets a caller substitute a zero-parameter (or otherwise malformed) function for the `lhs`/hook side of this check, so the described bypass does not cross a real custody boundary for fungible-asset withdraw-hook registration.
