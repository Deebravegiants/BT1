## Analysis

The core identity-binding vulnerability class described in the report (a mutable field that controls sensitive behavior but is not bound to the caller's cryptographic authentication) has a direct analog in this gem's webhook processing: the `shop` (and `topic`/`webhook_id`/`api_version`) identity fields used by webhook handlers are read from unauthenticated HTTP headers that fall **outside** the HMAC signature's coverage.

### Title
Webhook Shop/Tenant Identity Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values passed to the application's handler are extracted from HTTP headers that are never part of the signed content. This breaks the identity binding `hmac-signed bytes == bytes the handler trusts for tenant attribution`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  This is what `HmacValidator.validate_signature` uses to compute and compare the signature: [2](#0-1) 

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all derived directly from HTTP headers, which are not included in the signable string at all: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then dispatches the handler using these unsigned header-derived values, including `shop`, as the tenant identity for the event: [4](#0-3) 

Because the HMAC only proves "this body was produced using the app's secret for *some* legitimate webhook Shopify sent," but not "this body+shop combination is what Shopify actually sent," an attacker who owns any legitimate installation of the app (i.e., an unprivileged merchant/tenant of their own shop) can capture a validly-signed webhook (raw body + `X-Shopify-Hmac-Sha256`) delivered to their own endpoint, then replay it to the target application's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to name a different (victim) shop. The signature check still passes because it only checks the body bytes, and the handler receives `WebhookMetadata` attributing the event to the victim shop: [5](#0-4) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which overstates the actual guarantee — it verifies the body's provenance, not the shop attribution: [6](#0-5) 

### Impact Explanation
This breaks tenant isolation (cross-tenant access): an attacker who is a legitimate but unprivileged user of the host app (merely by installing the app on their own store) can cause the host application to execute shop-scoped webhook logic (e.g., `app/uninstalled` cleanup, GDPR `customers/data_request` or `shop/redact` processing, order/customer sync, billing-state changes) as if it originated from an arbitrary victim shop domain, without ever needing that shop's access token or credentials. This matches the Critical "cross-tenant access" impact category, since the binding between the cryptographically-verified bytes and the tenant identity asserted to application code is missing.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled test/dev store to receive at least one genuinely Shopify-signed webhook, and (2) the ability to POST directly to the target app's public webhook endpoint with attacker-chosen headers — both are available to any unprivileged internet user/merchant, with no access token, `api_secret_key`, or social engineering required.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or independently bind them: e.g., cross-check `request.shop` against the `Session`/installation the app tracks for that shop before trusting it, and document clearly that only the raw body is authenticated by `HmacValidator`, so consuming apps must not treat header-derived `shop`/`topic` as authenticated without additional verification (such as confirming the shop is a known installed tenant before acting on shop-scoped webhook data).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged install) and registers a webhook (e.g., `orders/create`) pointing to a server the attacker controls.
2. Shopify delivers a legitimately signed webhook to the attacker's endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `<raw_body>`
3. Attacker captures `<raw_body>` and `<valid-hmac>` unchanged, then sends a new POST directly to the target application's real webhook endpoint (the same endpoint used for all merchants) with:
   - `X-Shopify-Hmac-Sha256: <valid-hmac>` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (rewritten)
   - Body: `<raw_body>` (unchanged)
4. `HmacValidator.validate` recomputes the HMAC over `<raw_body>` only [2](#0-1)  — it matches, so `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the host application to process an event as if it came from the victim tenant.
