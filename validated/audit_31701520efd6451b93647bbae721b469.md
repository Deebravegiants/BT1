### Title
Non-embedded session cookie value is the deterministic online session id `"#{shop}_#{user_id}"`, allowing session-id guessing / cross-user session hijack - ([File: lib/shopify_api/auth/oauth.rb], [File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps (and embedded apps hit without an id token), `Oauth.validate_auth_callback` sets the `shopify_app_session` cookie's value directly equal to `session.id`, and for online sessions `session.id` is always the fully deterministic, unauthenticated string `"#{shop}_#{associated_user.id}"` [1](#0-0) [2](#0-1) . `SessionUtils.cookie_session_id` then hands this raw cookie value straight back as the trusted `session_id` with zero verification against `Context.api_secret_key` [3](#0-2) . Since `shop` is public and staff `user_id` values are small sequential integers, an attacker can precompute this string for any victim and present it as their own `Cookie` header.

### Finding Description
Binding claimed/required: `session_id` returned by `current_session_id`/`cookie_session_id` should equal a value only derivable from bytes authenticated under `Context.api_secret_key` (e.g. an HMAC'd or random opaque token), i.e. `session_id == f(secret, ...)`. In the cookie branch it instead holds `session_id == cookies["shopify_app_session"] == session.id == "#{shop}_#{associated_user.id}"` — a value derivable by anyone from two public/enumerable facts, with no secret material involved [2](#0-1) [4](#0-3) .

Code path: `SessionUtils.current_session_id(nil, cookies, true)` → non-embedded branch (or embedded-without-id_token fallback) requires only that `cookies[SESSION_COOKIE_NAME]` be present, then calls `cookie_session_id(cookies)` which returns `cookies[SESSION_COOKIE_NAME]` verbatim [5](#0-4) [3](#0-2) . `Context.api_secret_key` is never consulted in this branch. The only place `HmacValidator.validate` and the `state` comparison run is during the one-time OAuth callback (`validate_auth_callback`), which authenticates Shopify's redirect, not the later per-request cookie value [6](#0-5) . After that callback succeeds, the persistent cookie is simply set to `session.id` with no signature/HMAC binding it to the app's secret [4](#0-3) .

Attacker request: `GET /any-authenticated-route HTTP/1.1` with header `Cookie: shopify_app_session=known-shop.myshopify.com_1`. If the host app (as documented, e.g. via `SessionRepository.store_session`) keys its session store by this same deterministic string, `current_session_id` returns that string, the host app looks up a real stored `Session` for shop `known-shop.myshopify.com` and staff id `1`, and the attacker's subsequent Shopify Admin API calls execute using that victim's `access_token` — this is a cross-tenant/cross-user credential theft.

None of the existing guards intervene: `Context.embedded?` only chooses which branch runs, it adds no authentication to the cookie bytes; `HmacValidator`/`state` only guard the initial callback; `JwtPayload`'s `aud` check is irrelevant to the cookie path; Sorbet typing only enforces `String` shape, not provenance.

### Impact Explanation
Full compromise of another staff user's online session, including their access token, purely by guessing/enumerating a small integer user id against a known/public shop domain — this is cross-tenant, cross-user credential theft, matching the Critical category ("theft of a merchant access token... cross-tenant access"). Repeatable against arbitrary victims/shops since the derivation is a pure deterministic function of two learnable inputs; no rate limiting or entropy stands in the way once the app is a non-embedded app (or an embedded app that falls back to cookies).

### Likelihood Explanation
Requires: (1) app is non-embedded, or embedded but reachable without submitting an id token so it falls back to the cookie branch; (2) the host app's session storage is keyed by the id returned from this gem (the documented pattern, since this is the value the gem tells integrators to use as the storage key, per `docs/getting_started.md`); (3) attacker knows the shop domain (public) and can guess/enumerate the target staff `user_id` (small sequential integer). No credentials, secrets, or victim interaction are required — attacker cost is a handful of trial requests with different guessed cookie values.

### Recommendation
Never set the persistent session cookie value to a deterministic identifier. Instead, generate a cryptographically random opaque cookie value (e.g. `SecureRandom.uuid`) that is unrelated to `session.id`/`shop`/`user_id`, and have the host-side session store map that random opaque value to the actual session (or HMAC-sign the session id with `Context.api_secret_key` and verify the signature in `cookie_session_id` before trusting it). `SessionUtils.cookie_session_id` should reject any cookie value that isn't verified against a secret-derived signature rather than passing raw cookie bytes straight through as a trusted session identifier.

### Proof of Concept
Add to `test/utils/session_utils_test.rb` (or a new test file), using a stub session store to demonstrate the guessable-id hijack without a live shop:

```ruby
def test_cookie_session_id_is_deterministic_and_guessable
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  shop = "known-shop.myshopify.com"
  victim_user_id = 1

  # Simulate what oauth.rb#validate_auth_callback actually sets as the cookie value
  # for a real victim's online session (line: SessionCookie.new(value: session.id, ...))
  victim_session = ShopifyAPI::Auth::Session.from(
    shop: shop,
    access_token_response: ShopifyAPI::Auth::Oauth::AccessTokenResponse.from_hash(
      "access_token" => "victim-secret-token",
      "associated_user" => { "id" => victim_user_id, "email" => "v@example.com", "first_name" => "v",
                              "last_name" => "v", "email_verified" => true, "account_owner" => true,
                              "locale" => "en", "collaborator" => false },
    ),
  )
  cookie_value_set_by_gem = victim_session.id

  # Attacker never sees this cookie; they compute it from public shop + guessed small user id
  guessed_cookie_value = "#{shop}_#{victim_user_id}"

  # Assert both sides of the binding: the "secret" cookie value equals the attacker-computable value
  assert_equal(cookie_value_set_by_gem, guessed_cookie_value)

  # Attacker sends a forged Cookie header with the guessed value
  forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => guessed_cookie_value }

  resolved_session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookies, true)

  # No secret/api_secret_key was ever consulted, yet resolved_session_id matches the victim's real session id
  assert_equal(victim_session.id, resolved_session_id)
end
```

This proves `current_session_id`/`cookie_session_id` accept an attacker-computed value equal to the real victim session id, with no dependency on `Context.api_secret_key`; if the host app's session store (as documented) is keyed by this id, the attacker's next authenticated API call resolves to `victim_session.access_token`.
