### Title
Webhook shop/topic identity fields excluded from HMAC signature allow cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the event are taken from unsigned HTTP headers.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes and compares the HMAC over exactly that signable string against the secret [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` HTTP headers with no cryptographic binding to the body or to each other [3](#0-2) . `Registry.process` validates only the HMAC and then dispatches the handler using these unauthenticated header values as the tenant/topic identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

This breaks the intended identity binding: `HMAC-verified(body) == shop-attributed-to(body)`. In reality the gem only proves `HMAC-verified(body)`; the `shop` (and `topic`) that the body gets attributed to is supplied by an unauthenticated header the caller can set to anything, as long as they can produce a `(raw_body, hmac)` pair that is valid for *some* topic/shop under the app's `client_secret`.

An unprivileged user who installs the target app on their own (attacker-controlled) shop can trigger a legitimate webhook delivery for a topic they control (e.g. `orders/create`, `app/uninstalled`, GDPR topics), capture the genuine `(raw_body, shopify-hmac-sha256)` pair Shopify sends to the app's endpoint, and then directly POST that same body/HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. Because the signature check never covers the shop header, the forged request passes `HmacValidator.validate` and is routed to the app's handler as if the event legitimately originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's own webhook contract lets an attacker who is a legitimate (if unprivileged) merchant of the app inject events under an arbitrary victim shop's identity, since the shop attribution is not covered by the cryptographic proof the gem relies on. Any host application that trusts `WebhookMetadata#shop` (as the API documents it should, since it is the field surfaced after HMAC validation) to select/write per-tenant records is exposed to cross-tenant data corruption or state confusion (e.g., forged `app/uninstalled`, GDPR redaction, or order webhooks attributed to a shop that never sent them). This matches the Critical category of cross-tenant access via a broken identity binding.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal unprivileged flow for any public/embedded app) and can freely trigger topics on their own shop to obtain valid `(body, hmac)` pairs, then replay them with a substituted shop header to the app's public webhook endpoint. No access to the app's `client_secret`, TLS interception, or privileged account is needed — only the gem's own signable-string design, which omits the shop/topic identity headers from the HMAC.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the body), or require the host application to independently verify that `request.shop` corresponds to a shop that actually has this app installed and matches the session/store the webhook subscription was registered against, rather than trusting the header value implicitly once `HmacValidator.validate` returns true.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a topic (e.g. update an order) to receive a real webhook POST with body `B` and header `shopify-hmac-sha256: H` (valid for the app's `client_secret`).
2. Capture `B` and `H`.
3. POST to the app's webhook endpoint:
   - `shopify-hmac-sha256: H`
   - `shopify-shop-domain: victim.myshopify.com` (forged)
   - `shopify-topic: <same topic as B>`
   - body: `B` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) ; since the check only re-hashes `B`, it succeeds despite the forged shop header, and the handler receives `WebhookMetadata` attributing the event to `victim.myshopify.com`.
