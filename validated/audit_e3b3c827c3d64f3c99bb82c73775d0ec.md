Audit Report

## Title
`harvest_rewards` never persists updated pool reward accumulator, causing reward double-accrual and pool insolvency - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`harvest_rewards` retrieves an updated `pool_info` from `update_pool_and_staker_rewards`, which advances the pool's reward-per-token accumulator and last-update block, but discards it without writing it back to `Pools` storage, unlike `stake` and `unstake` which both call `Pools::<T>::insert(pool_id, pool_info)` after the same helper call. This leaves the on-chain pool accumulator stale after every harvest, so the next interaction with that pool recomputes and re-credits rewards for the already-paid time window.

## Finding Description
In `stake`, after calling `update_pool_and_staker_rewards`, the function mutates `pool_info.total_tokens_staked` and persists it via `Pools::<T>::insert(pool_id, pool_info)`. [1](#0-0)  Similarly, `unstake` persists the pool state after updating rewards. [2](#0-1) 

In `harvest_rewards`, the same `update_pool_and_staker_rewards` call is made, producing an updated `pool_info` binding (shadowing the original), but this `pool_info` is only used to read `reward_asset_id` and `account` for the transfer — it is never written back to `Pools` storage anywhere in the function body. [4](#0-3)  Only `PoolStakers` is updated at the end. This means the pool-level accumulator/last-update bookkeeping that `update_pool_and_staker_rewards` computed is discarded, leaving the `Pools` map entry stale at whatever state it was before the harvest.

Because the pool-wide accumulator is not advanced in storage, the next call to `update_pool_and_staker_rewards` (triggered by any staker's `stake`, `unstake`, or `harvest_rewards` on the same pool) will recompute the reward accrual starting from the stale snapshot, effectively re-crediting the reward window that had already been paid out. None of the existing guards (`BadOrigin` origin check, `NonExistentStaker`/`NonExistentPool` existence checks, or the `Assets::transfer` balance check) validate that the pool's accumulator was actually advanced or that payouts are backed by real emission — they only check origin, existence, and current balance sufficiency for a single transfer.

## Impact Explanation
This causes real, in-scope impact: unbacked over-distribution of reward tokens from the pool account, which can deplete the pool's reward asset balance faster than `reward_rate_per_block` intends, leading to failed transfers (insufficient balance) for later legitimate `harvest_rewards`/`unstake` callers, or unfair reward distribution among stakers. This matches an "unbacked mint or pool insolvency" style impact within the pallet's own accounting, not a node/governance/admin-only issue.

## Likelihood Explanation
This is triggerable unconditionally by any unprivileged signed staker via the ordinary `harvest_rewards` extrinsic — no special preconditions beyond having staked and having non-zero pending rewards. The missing write reproduces on every successful call, and the resulting corruption compounds with every subsequent interaction on the same pool by any staker, making this deterministic and fully repeatable rather than a hypothetical edge case.

## Recommendation
In `harvest_rewards`, persist the updated pool state exactly as `stake`/`unstake` do — add `Pools::<T>::insert(pool_id, pool_info)` after `update_pool_and_staker_rewards` returns, before or alongside the `PoolStakers` update, so the pool's reward accumulator/last-update block is advanced to `now` on every harvest.

## Proof of Concept
1. Create a pool with two stakers, `staker1` and `staker2`, each staking equal amounts at block `B0`.
2. Advance to block `B1`. Call `harvest_rewards` for `staker1` — assert success, then read `Pools::<MockRuntime>::get(pool_id)` and show the pool's last-update/accumulator field is unchanged (still reflecting `B0`), demonstrating the missing persistence.
3. Advance to block `B2`. Call `harvest_rewards` for `staker2`. Show that `staker2`'s harvested amount reflects double-counted accrual for the `[B0, B1]` window already paid to `staker1`, exceeding `reward_rate_per_block * (B2 - B1)` proportional share.
4. Show `sum(all harvested amounts) > reward_rate_per_block * (B2 - B0)`, and/or that a later `harvest_rewards`/`unstake` call fails due to depleted pool balance, confirming insolvency.
