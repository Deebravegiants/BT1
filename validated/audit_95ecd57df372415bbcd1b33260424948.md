### Title
`fee_schedule::set_fee_address` allows the marketplace fee address to be set to `@0x0`, permanently burning commission payments - ([File: aptos-move/move-examples/marketplace/sources/fee_schedule.move])

### Summary
This is the direct Aptos-native analog of the reported `PositionsManagerForAave.claimToTreasury` bug: a custody-relevant "treasury/fee" destination address that is never checked against the zero address before being persisted and later used to route real value. In the marketplace example module, `fee_schedule::set_fee_address` lets the object owner set `fee_address` to any address, including `@0x0`, with no validation, and this address is subsequently used by `coin_listing`, `token_offer`, and `collection_offer` to route commission payments on every sale.

### Finding Description
`FeeSchedule.fee_address` is the field that all payment-settlement code paths use as the commission destination: [1](#0-0) 

The mutator that updates it performs only an ownership check — it never validates that the new `fee_address` is non-zero: [2](#0-1) 

The module's own test suite explicitly demonstrates this is reachable and treated as a "valid" state, setting `fee_address` to `@0x0` and asserting success: [3](#0-2) 

`fee_address(fee_schedule)` is then read directly to determine where commission coins/fungible assets get deposited during settlement, e.g. in `collection_offer::settle_payments`: [4](#0-3) 

The same `fee_schedule::fee_address` pattern is used in `coin_listing.move` and `token_offer.move` (confirmed via 6 and 4 call sites respectively) to route the marketplace commission on every trade.

This mirrors the Aave bug precisely: a privileged setter for a "treasury"-style address lacks a zero-address check, and downstream code unconditionally transfers value (here, commission on every marketplace trade) to whatever `fee_address` currently holds.

### Impact Explanation
If the `FeeSchedule` object owner (intentionally or by mistake — e.g., a misconfigured deployment script, or a compromised/careless admin key) sets `fee_address` to `@0x0`, every subsequent commission payment across `coin_listing`, `token_offer`, and `collection_offer` sales is deposited to `@0x0` instead of the intended treasury. On Aptos, deposits to `@0x0` via `aptos_account::deposit_coins`/fungible-asset deposit paths succeed (the zero address is a valid account address with no discoverable private key), so all commission funds routed there are permanently unrecoverable — value loss with no recovery path, satisfying the custody-impact bar for "supply or custody accounting corruption that moves value to the wrong holder ... and destroys recovery rights."

### Likelihood Explanation
This is example/reference marketplace code (`aptos-move/move-examples/marketplace`), not core Aptos framework code, so mainnet exposure depends on whether any project deploys this contract as-is. Given that, likelihood of the specific bug firing is Medium: it requires an owner action (deliberate or fat-fingered) to set the zero address, matching the "Medium Risk" severity of the original Aave report and the fact that Spearbit only acknowledged rather than treated it as critical. There is no privilege escalation involved — it is exactly the same class of missing-invariant bug as the original report, transplanted to an Aptos custody control (`fee_address`) that gates real per-trade fund flows.

### Recommendation
Add an explicit check in `set_fee_address` (and ideally in `init`/`empty_init`) rejecting `@0x0`:
```move
public entry fun set_fee_address(
    creator: &signer,
    marketplace: Object<FeeSchedule>,
    fee_address: address,
) acquires FeeSchedule {
    assert!(fee_address != @0x0, error::invalid_argument(EFEE_ADDRESS_IS_ZERO));
    ...
}
```
Also update the test at `fee_schedule.move:347` (and `:375`) which currently asserts that setting `fee_address` to `@0x0` succeeds — that behavior should become an `expected_failure` case once the check is added.

### Proof of Concept
1. Owner calls `fee_schedule::init`/`empty_init` to create a `FeeSchedule`, then calls `set_fee_address(creator, marketplace, @0x0)` — succeeds today with no error (as shown by the module's own passing test at lines 347/375).
2. A buyer/seller completes a sale via `coin_listing` or a bid via `collection_offer`/`token_offer`.
3. `settle_payments` (or equivalent) reads `fee_schedule::fee_address(fee_schedule)` (now `@0x0`) and calls `aptos_account::deposit_coins(@0x0, commission)`, permanently depositing the marketplace commission to the zero address with no way to reclaim it. [5](#0-4)

    /// Set the fee address
    public entry fun set_fee_address(
        creator: &signer,
        marketplace: Object<FeeSchedule>,
        fee_address: address,
    ) acquires FeeSchedule {
        let fee_schedule_addr = assert_exists_internal(&marketplace);
        assert!(
            object::is_owner(marketplace, signer::address_of(creator)),
            error::permission_denied(ENOT_OWNER),
        );
        let fee_schedule_obj = borrow_global_mut<FeeSchedule>(fee_schedule_addr);
        fee_schedule_obj.fee_address = fee_address;
        let updated_resource = string::utf8(b"fee_address");
        event::emit(Mutation { marketplace: fee_schedule_addr, updated_resource });
    }
