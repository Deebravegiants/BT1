## Title
Webhook shop identity spoofing via HMAC that only signs the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the raw HTTP body as the only HMAC-signed material, while the shop identity used for routing and application logic (`request.shop`) is read directly from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier without that value ever being covered by the signature, breaking the binding `hmac_verified_bytes == tenant_identity_used_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` computes and compares the signature only over `verifiable_query.to_signable_string`, i.e. only the body, never the shop-domain header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the **unauthenticated** `request.shop` value to the app's webhook handler as the authoritative tenant identifier: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any merchant who has installed the app (an unprivileged actor with respect to other tenants) can capture a genuine `(raw_body, hmac)` pair generated for their own shop (e.g., by triggering a webhook to themselves) and replay it directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Because that header is outside the signed material, the HMAC check in `Registry.process` still passes, and the handler receives `WebhookMetadata` claiming the payload originated from the victim shop it never actually sent.

This is the same bug class as CVE-2024-2398's root cause pattern generalized to identity binding: a field (`shop`) that is *acted upon* (used to attribute/route the event) is not covered by the integrity check (`HMAC`) that is supposed to authenticate the whole message.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce (`shop-domain-in-header == shop-domain-covered-by-hmac` does not hold). An attacker-controlled body can be attributed to an arbitrary victim shop domain, letting the attacker forge cross-tenant events for shops they do not control. Depending on how the hosting application keys its data/session lookups off `WebhookMetadata#shop` (which this gem produces and hands to handlers), this can lead to cross-tenant data corruption, injection of forged business events (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`) attributed to a shop the attacker doesn't own, satisfying the "cross-tenant access" criteria.

### Likelihood Explanation
Any user who can install the app on at least one shop (a routine, unprivileged action) can obtain one valid `(body, hmac)` pair for a topic of their choosing and replay it with a forged shop-domain header against the app's public webhook endpoint, since no other credential or secret is required beyond what's already exposed on any genuine webhook delivery.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or otherwise cryptographically bind the shop-domain header to the signed body before it is trusted by `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger any registered webhook topic (e.g. `orders/create`) to capture the genuine raw body and `x-shopify-hmac-sha256` value Shopify sends.
2. Replay that exact `(raw_body, hmac)` pair as an HTTP POST to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to a topic the app has registered.
3. `HmacValidator.validate(request)` in `Registry#process` succeeds because it only checks `raw_body` against the HMAC.
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, causing the host application to process attacker-controlled data as if it were authentically sent by Shopify for `victim-shop.myshopify.com`.           received_signature = verifiable_query.hmac
