### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook-id`, and `api-version` values used to route and process the webhook are taken from unauthenticated HTTP headers. `Registry.process` verifies only that the *body* was signed with the app's `client_secret`, then hands the caller-supplied `shop` header straight to the webhook handler. This lets an attacker who can obtain any one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a genuine webhook delivery) replay that exact body/hmac to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header, causing the app to process the attacker's forged event as if it originated from the victim tenant.

### Finding Description
The identity binding that should hold is:
`shop header validated == shop the HMAC-signed body is asserted to belong to`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no signature or trust binding. [2](#0-1) 
`to_signable_string` — the only material fed into `HmacValidator` — returns solely `@raw_body`. None of `shop`, `topic`, `webhook_id`, or `api_version` are included in the signed content.

`Utils::HmacValidator.validate` computes and compares an HMAC over `to_signable_string` using `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` trusts the header-derived `shop` after only validating the body's HMAC: [4](#0-3) 

Because the `client_secret` HMAC key is shared across **every** shop that installs the app (it is not per-tenant), any user who can install the app on their own store can trigger a genuine webhook delivery to a URL they control, capture the resulting `(raw_body, hmac)` pair, and then send a hand-crafted HTTP POST directly to the app's real webhook endpoint with the same body/hmac but an attacker-chosen `shopify-shop-domain` header (and optionally a different `shopify-topic`, since that header is likewise unauthenticated). The gem's HMAC check passes — it only re-validates the byte-identical body — and the forged `shop`/`topic` are passed unchecked into `WebhookMetadata`, which the host application uses to key per-tenant behavior (e.g., deleting sessions on `app/uninstalled`, updating shop-scoped records on `shop/update`, `orders/*`, etc.).

This mirrors the report's bug class: the check proves the *bytes are authentic* (HMAC over the body), but the downstream action is keyed on a *different, unverified value* (the `shop` header) — i.e., "bytes verified versus bytes parsed" / "a shop authenticated versus the shop acted upon."

### Impact Explanation
This breaks the tenant isolation the gem is expected to provide: an app relying on `WebhookMetadata#shop` from this gem to identify which merchant a webhook event belongs to can be made to attribute an attacker-controlled event to an arbitrary victim shop. Depending on the topic the host app subscribes to, this can range from data confusion to triggering tenant-scoped side effects (e.g., forcing app/uninstall cleanup, session invalidation, or state changes) for a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitability requires only: (1) the ability to install/interact with the target app as a normal merchant (to obtain one genuine, validly-signed webhook body/hmac pair via a self-registered webhook callback URL), and (2) network access to POST directly to the app's public webhook endpoint. No access token, `client_secret`, or privileged account for the *victim* shop is required. This is reachable by any unprivileged internet user who can self-install a publicly available Shopify app.

### Recommendation
Include the identity/topic fields in the signed payload used for verification, or otherwise cryptographically bind the `shop`, `topic`, and `webhook_id` headers to the verified body before trusting them:
- Have `Webhooks::Request#to_signable_string` incorporate the header values (`shop`, `topic`, `webhook_id`, `api_version`) alongside the raw body, matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed string.
- Alternatively, require the host application to independently confirm that `shop` belongs to a shop with an active session/install before trusting the webhook payload for that tenant, and document this requirement clearly in `lib/shopify_api/webhooks/registry.rb` and `docs/usage/webhooks.md`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (any public app allowing self-serve installation).
2. Attacker registers/uses a webhook subscription with a callback URL they control (e.g., via GraphQL `webhookSubscriptionCreate`), triggers an event (e.g., create an order), and captures the raw HTTP request Shopify sends, including:
   - `raw_body`
   - `X-Shopify-Hmac-Sha256` header (valid because HMAC key = app's shared `client_secret`)
3. Attacker crafts a new HTTP POST directly to the target app's real, public webhook endpoint using the exact same `raw_body` and `hmac`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Utils::HmacValidator.validate` (via `lib/shopify_api/utils/hmac_validator.rb#validate_signature`) succeeds because it only checks `raw_body`.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — a forged cross-tenant webhook event.
