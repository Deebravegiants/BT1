## Title
Webhook `shop-domain`/`topic`/`webhook-id`/`api-version` headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which the registry treats as authenticated metadata and hands directly to the app's handler — are taken unauthenticated from HTTP headers and never enter the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this HMAC check as its sole authenticity gate, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which were verified) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This is exactly the "bytes verified vs. bytes parsed" identity-binding break described in the prompt: the equality the code implicitly assumes is `verified_bytes == acted_on_bytes`, but in fact `verified_bytes = raw_body` while `acted_on_bytes = raw_body ∪ {shop, topic, webhook_id, api_version headers}`. The gem's own documentation overstates the guarantee, claiming `process` "will verify the request did indeed come from Shopify," when in reality only the body content is authenticated — the shop attribution and topic routing are not:

```
lib/shopify_api/webhooks/registry.rb:125 (in docs/usage/webhooks.md)
"This will verify the request did indeed come from Shopify and then call the specified handler for that webhook."
```

Because the HMAC secret (`api_secret_key`) is shared across *all* shops that install the same app (not per-shop), any merchant who installs the app on their own store receives genuinely-signed webhook bodies. Since headers are excluded from the signature, that merchant can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with an arbitrarily forged `shop-domain` header (any other merchant's shop), and/or a forged `topic`/`webhook-id`/`api-version` header — all while the HMAC check still passes, since it only re-validates the untouched body bytes.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce: `Registry.process` reports (and downstream app handlers trust) a `WebhookMetadata#shop` and `#topic` that were never authenticated, while only the body was. Since `shop/redact` and `customers/redact` are mandatory topics handled by this same unauthenticated-header path, an attacker who owns any working install of the app can replay one of their own genuine webhook events, changing only the `x-shopify-topic` and `x-shopify-shop-domain` headers, to make the app believe a redaction/GDPR event (or any other topic) occurred for a different, victim shop. This is a cross-tenant confusion vulnerability: the app processes data/actions under the identity of a shop that never sent the request, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation only requires an attacker to have (or create) one legitimate install of the target app on any shop they control — a normal, low-privilege action any developer/merchant can take — and the ability to POST arbitrary headers to the app's public webhook endpoint, which by design is an unauthenticated internet-facing route. No access to `api_secret_key`, tokens, or the real target shop is required.

### Recommendation
Include the security-relevant headers (`shopify-topic`, `shopify-shop-domain`, `shopify-webhook-id`, `shopify-api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified payload, so that `Utils::HmacValidator.validate` fails if any of these values are altered relative to what Shopify actually sent. At minimum, `Registry.process` should not treat `request.shop`/`request.topic` as authenticated when only the body was verified, and the documentation in `docs/usage/webhooks.md` should be corrected to not claim full request authenticity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers for any webhook topic (e.g., `orders/create`).
2. Shopify sends a webhook to the attacker's endpoint with a body `B` and a valid `x-shopify-hmac-sha256` header computed as `HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, hmac)` and re-POSTs it to the target app's `/webhooks` route, replacing headers:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any topic registered by the app)
   - keeping the original body `B` and `hmac` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (headers only checked for presence, not authenticity) and `Utils::HmacValidator.validate(request)` returns `true` because it only re-verifies `B` against `hmac`.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act as though `victim-shop` sent this event, despite it never having done so.
