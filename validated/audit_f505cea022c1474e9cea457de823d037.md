### Title
Unchecked size field in `deserialize_message` can trigger out-of-bounds slice panic across agent-IPC shared memory boundary - (File: agentwire/src/port.rs)

### Summary
`deserialize_message` in `agentwire/src/port.rs` reads a `size` value directly from the shared-memory buffer and then slices `buf[mem::size_of::<usize>()..mem::size_of::<usize>() + size]` without validating that `size` fits within the buffer's actual length. This mirrors the reported bug class ("Lack Of Array Size Checks Before Slicing Or Referencing Array Elements"), applied here to the agent-IPC trust boundary between the main orb-core process and its subprocess agents (e.g. camera workers, Python agents, QR code agent).

### Finding Description
`deserialize_message` is used on both the input and output shared-memory channels: [1](#0-0) 

The buffer passed to it is a fixed-size slice returned by `SharedMemory::input()`/`output()`/`init_state()`, sized at `T::SERIALIZED_INPUT_SIZE`/`T::SERIALIZED_OUTPUT_SIZE`/`T::SERIALIZED_INIT_SIZE`: [2](#0-1) 

The first 8 bytes of that fixed buffer are treated as an untrusted `size` header written by the peer process via `serialize_message`: [3](#0-2) 

`deserialize_message` then computes `mem::size_of::<usize>() + size` and slices the buffer with it, with no check that this value is `<=` the buffer length: [4](#0-3) 

This function is invoked on both sides of the shared-memory channel: by `RemoteInner::init_state()`/`recv()` (used inside the subprocess agent to receive input written by the main process), and — critically — by `spawn_shared_tx_task` in the main process to read the *output* written by the (out-of-process) agent: [5](#0-4) 

Because the `size` header originates from the sending side of the channel and there is no bounds validation before slicing, a corrupted, buggy, or compromised agent subprocess (e.g. one of the Python agents `mega_agent_one`, `mega_agent_two`, `face_identifier`, `iris`, `ir_net`, `rgb_net`, `occlusion`, or the `qr_code` agent) that writes a `size` value larger than `T::SERIALIZED_OUTPUT_SIZE - size_of::<usize>()` into the shared output buffer will cause the main orb-core process to panic with an out-of-bounds slice index when it deserializes that message in `spawn_shared_tx_task`.

### Impact Explanation
A panic in the main orb-core process crashes the entire orb pipeline (all in-flight biometric capture/signup state is lost), since this deserialization runs unconditionally on every IPC message exchanged with agent subprocesses, including the ones that parse untrusted external input first (QR code content in `qr_code` agent, camera frames, ML model outputs). This creates a reliability/availability issue at the agent-IPC trust boundary: any bug, memory corruption, or malicious tampering in an agent process's serialization path can deny service to the main process rather than being handled gracefully. Severity is Medium: it is a crash/DoS vector rather than a memory-disclosure or signup-forgery vector, since the affected code operates on fixed-size, statically-typed shared memory rather than arbitrary network-supplied buffers.

### Likelihood Explanation
Likelihood is Medium-Low. Exploitation requires an agent subprocess to write a corrupted or oversized `size` header into the shared output/input buffer — this could happen due to a bug in `rkyv` serialization growing beyond the statically computed `SERIALIZED_OUTPUT_SIZE`/`SERIALIZED_INPUT_SIZE` (computed from `mem::size_of::<T::Archived>()`), memory corruption in one of the several native/Python agent subprocesses, or, if any agent's serialization logic can be influenced with attacker-controlled sizes (e.g. QR code content flowing through `qr_code` agent's output), an indirect trigger without direct code execution in the main process.

### Recommendation
In `deserialize_message`, validate that `mem::size_of::<usize>() + size <= buf.len()` before slicing, and return an error (or use a safe fallback / drop-and-log) instead of panicking when the bound is violated. Apply the same defensive check to any other place relying on this trusted-but-unchecked `size` header written across the shared-memory IPC boundary.

### Proof of Concept
1. An agent subprocess (any of `mega_agent_one`, `mega_agent_two`, `qr_code`, `iris`, `rgb_net`, etc.) calls `RemoteInner::send()`, which calls `serialize_message` to write into the shared `output` buffer of length `T::SERIALIZED_OUTPUT_SIZE` — see `RemoteInner::send`: [6](#0-5) 
2. If a bug in the agent process (or a corrupted/attacker-controlled serialization value, e.g. from parsing an oversized QR/network payload before re-serializing) causes the written `size` header to exceed `T::SERIALIZED_OUTPUT_SIZE - mem::size_of::<usize>()`,
3. The main orb-core process's `spawn_shared_tx_task` reads that output via `deserialize_message::<T::Output>((*shared_memory).output())`: [7](#0-6) 
4. `deserialize_message` executes `&buf[mem::size_of::<usize>()..mem::size_of::<usize>() + size]` with `size` unchecked against `buf.len()`, causing an index-out-of-bounds panic that crashes the whole orb-core process. [4](#0-3)

fn serialize_message<T>(
    buf: &mut [u8],
    scratch: &mut Option<FallbackScratch<HeapScratch<SCRATCH_SIZE>, AllocScratch>>,
    value: &T,
) where
    T: Archive + for<'a> Serialize<SharedSerializer<'a>> + Debug,
{
    let mut serializer = CompositeSerializer::new(
        BufferSerializer::new(&mut buf[mem::size_of::<usize>()..]),
        scratch.take().unwrap(),
        SharedSerializeMap::new(), // reuse of this map doesn't work
    );
    serializer.serialize_value(value).expect("failed to serialize an IPC message");
    let size = serializer.pos();
    let (_, c, _) = serializer.into_components();
    buf[..mem::size_of::<usize>()].copy_from_slice(&size.to_ne_bytes());
    *scratch = Some(c);
}
