I found a concrete identity-binding gap: `Webhooks::Request` signs only the raw body with HMAC, but the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and tag the webhook are taken from unauthenticated HTTP headers.

### Title
Webhook `shop`/`topic` headers are trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC computed by `Utils::HmacValidator.validate` in `Registry.process` [2](#0-1)  only proves the request body was signed by Shopify. The `shop`, `topic`, `webhook_id`, and `api_version` fields, however, are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) [3](#0-2)  and are never part of the signed payload.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)`, i.e. every value the handler acts on should be covered by the signature. Instead the binding actually enforced is only `hmac == HMAC(secret, body)` [1](#0-0) . `Registry.process` validates this narrower binding and then dispatches using the unsigned `request.shop` and `request.topic` values to build `WebhookMetadata` [4](#0-3) .

Because the shop domain used to attribute the webhook to a tenant (`request.shop`) is not covered by the signature, an attacker who can replay or forward a validly-HMAC'd body from Shop A (e.g., a payload they legitimately received, or one obtained by any means where the body/secret pairing is valid for the configured `api_secret_key`) can attach an arbitrary `shopify-shop-domain` header for Shop B when submitting it to the app's webhook endpoint. Since only the body is checked, `HmacValidator.validate` still returns true, and the host application's handler will process the payload as if it came from Shop B — a cross-tenant identity confusion at the shop-attribution boundary.

### Impact Explanation
This matches the Critical category of cross-tenant access: the webhook handler receives attacker-controlled shop attribution for a signature that only proves the body originated from Shopify, not which shop it belongs to. Any app logic that keys off `WebhookMetadata#shop` (e.g., looking up the merchant record, applying data) is misattributed, exactly mirroring the reported bug-class pattern of "a field acted on but not covered by the HMAC."

### Likelihood Explanation
Exploitation requires the attacker to have or produce a body with a valid HMAC for the app's `api_secret_key`/body pair — this is most practically achieved by capturing/replaying a legitimately-delivered webhook body (same secret, same body content) and re-submitting it with a forged `shop-domain` header, since the shop value plays no role in the signature check. No access token or `client_secret` is needed; only network access to the app's webhook endpoint and a previously observed valid webhook payload/HMAC pair.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or otherwise cryptographically bind them, matching Shopify's actual webhook signing scheme is body-only by design, so instead the gem should treat these header values as untrusted metadata and require the host app to independently verify the shop against its own session-shop mapping) rather than passing `request.shop` directly into `WebhookMetadata` as if it were verified equal to the signed content.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker replays the exact same raw body `B` and HMAC header `H` to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com` (a different, unrelated tenant).
3. `HmacValidator.validate(request)` computes `HMAC(secret, B)` from `to_signable_string` (body only) and it matches `H`, so validation passes [1](#0-0) [5](#0-4) .
4. `Registry.process` dispatches the handler with `shop: request.shop` set to `shop-b.myshopify.com`, even though the signature never bound the payload to that shop [6](#0-5) .
