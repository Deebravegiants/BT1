### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly off the HTTP request and are never included in the HMAC-signed material [2](#0-1) . `Utils::HmacValidator.validate` only proves the body was signed with the app's `client_secret`; it proves nothing about which shop the header claims to be from [3](#0-2) . `Registry.process` passes this unauthenticated `request.shop` straight into `WebhookMetadata` given to the host app's handler [4](#0-3) .

### Finding Description
The identity binding the gem is supposed to enforce is: `shop claimed in request == shop that generated (and is authorized to generate) this signed payload`. Because Shopify's `api_secret_key`/`client_secret` for a given app is the **same secret across every shop that installs that app**, any shop (including one an attacker controls, e.g. a free development store) can receive a legitimately HMAC-signed webhook body from Shopify for its own store. That `(body, hmac)` pair is valid proof only that "some install of this app produced this body," not proof of *which* shop. The `shop-domain` header carrying the tenant identity is completely outside the signed bytes, so an attacker who controls the delivery endpoint or can influence request routing/headers (e.g., a shared/multi-tenant reverse proxy, a header-rewriting component sitting in front of the app, or any component that forwards webhook bodies while allowing header substitution) can present the same valid `(body, hmac)` while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` because it only checks the body against the hmac [5](#0-4) , and `Registry.process` will happily dispatch the handler with the attacker-chosen `shop` [4](#0-3) .

### Impact Explanation
Host applications built against this gem's documented webhook API (`ShopifyAPI::Webhooks::Registry.process`) are told that a request which passes `HmacValidator.validate` is an authentic webhook for `WebhookMetadata#shop`. Since `shop` is not covered by the signature, an app that keys any tenant-scoped action (data lookup, mutation, redaction) off `data.shop` can be made to act on the wrong tenant's data — a cross-tenant access condition, one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitation requires a component that can relay a validly-signed body while altering the shop header en route — not a capability granted to a generic unprivileged internet caller who cannot forge the HMAC on an arbitrary body of their choosing. This limits likelihood: the core assumption "HMAC-over-body authenticates the header-carried shop" only breaks when body and headers can be decoupled, which is not something a purely unauthenticated remote attacker can do against this gem in isolation with default deployment.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the value that is HMAC-verified, or otherwise require the host application to independently authenticate the source shop before trusting `WebhookMetadata#shop`, rather than deriving tenant identity purely from an unsigned header.

### Proof of Concept
1. App installed on attacker's own shop `attacker.myshopify.com`, sharing the app's single `client_secret` with all other installs.
2. Attacker triggers a webhook event on their own shop and captures the legitimate `(raw_body, x-shopify-hmac-sha256)` pair Shopify sends them — this pair is valid per `HmacValidator.validate` because it was truly signed with `client_secret` [6](#0-5) .
3. Attacker (via any component capable of forwarding the request while rewriting headers) resubmits the same body/hmac to the app's webhook endpoint but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Request#hmac`/`#to_signable_string` are unaffected by the header change [7](#0-6) ; `Registry.process` validates successfully and calls the handler with `shop: "victim.myshopify.com"` [8](#0-7) , causing the host app to act as if the event genuinely originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
