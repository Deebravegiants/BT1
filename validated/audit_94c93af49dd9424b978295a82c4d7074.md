### Title
PoA Bridge withdrawal status/hash matched by asset instead of by withdrawal index, allowing txHash to be misattributed to the wrong withdrawal in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain destination hash for a specific withdrawal by locating a matching entry in an **unsorted** list returned by the PoA Bridge indexer, using `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — matched purely on `assetId`, not on the withdrawal's index/identity. When a batch of intents contains multiple withdrawals of the **same asset** (e.g., two BTC withdrawals to two different destination addresses, submitted in one NEAR transaction), this lookup can return the wrong indexer entry for a given `WithdrawalIdentifier`, causing the wrong destination `txHash`/`status` to be reported for a given logical withdrawal.

### Finding Description
`describeWithdrawal` is called per-withdrawal via `WithdrawalIdentifier` (which carries an `index` field distinguishing multiple withdrawals of the same route/asset in one NEAR transaction, as seen in `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts`). For PoA bridge, however, the docstring/comment at [1](#0-0)  explicitly states:

```
// Response list is unsorted, so we match by assetId instead of index
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```

This means the correlation key used to identify *which* withdrawal's status/hash belongs to *which* logical withdrawal request is the asset type, not the withdrawal's unique index or a per-withdrawal identifier (destination address, amount, or another disambiguator). If two or more withdrawals of the same `assetId` exist in the batch (a legitimate, supported scenario per `WithdrawalIdentifier.index` and `createWithdrawalIdentifiers`), `findMatchingWithdrawal` can return the first/any matching entry for both `index: 0` and `index: 1` queries, causing:
- `watchWithdrawal()` in [2](#0-1)  to resolve with the **wrong** `txHash` for a given withdrawal index.
- The reported on-chain outcome (`{status: "completed", txHash}`) not equaling the actual on-chain outcome for that specific withdrawal.

This breaks the equality "status/hash reported for withdrawal N == the actual on-chain outcome for withdrawal N," one of the explicitly allowed analog classes in the report's rules (a status or hash misreport).

### Impact Explanation
An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` per withdrawal index to confirm completion before crediting a user or reconciling ledgers could:
- Mark the wrong destination address's withdrawal as completed with another withdrawal's `txHash`, or
- Treat a still-pending/failed withdrawal as completed because a sibling withdrawal of the same asset completed first.

This matches the "High" impact bucket in the rules: *"a status or hash misreport making an integrator credit or refund twice."* Funds are not directly stolen by an external attacker, but the reported completion status could cause an integrator to release funds/credit balances against the wrong withdrawal, or fail to detect a failed/stuck withdrawal because a same-asset sibling withdrawal masked it.

### Likelihood Explanation
This requires no malicious behavior — merely a legitimate batch withdrawal containing ≥2 withdrawals of the same asset (e.g., splitting a large withdrawal to two destinations, or a user having two separate withdrawal requests of the same token processed in one intent). The SDK's own `WithdrawalIdentifier.index` and `createWithdrawalIdentifiers` machinery (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) demonstrate this exact scenario is expected/supported (separate index counters per bridge route), so the precondition is realistic and not a contrived edge case.

### Recommendation
Change the PoA bridge indexer correlation to use a disambiguator that uniquely maps to the specific withdrawal (e.g., match on `tx_hash` + `index`/sequence within that NEAR transaction, or destination address + amount if a unique per-item identifier from the indexer is unavailable), rather than matching solely by `assetId`. If the indexer response does not expose a stable per-item identifier, the SDK should fail closed (return `pending`/throw an ambiguity error) whenever more than one candidate entry matches the given asset for the same NEAR transaction, instead of silently picking one.

### Proof of Concept
Note: I was unable to view the full body of `findMatchingWithdrawal` (only its call site and the disambiguation comment were available in the indexed context) due to tool-call limits, so I could not fully confirm whether it applies any additional secondary matching (e.g., amount) beyond `assetId`. Based on the explicit comment "we match by assetId instead of index" and the function signature only accepting `(withdrawals, assetId)`, the scenario below is the reachable path if no further disambiguation exists:

1. User builds a batch of intents containing two PoA withdrawals of `nep141:btc.omft.near`:
   - Withdrawal A: index 0, destination `addrA`, amount 100000
   - Withdrawal B: index 1, destination `addrB`, amount 50000
2. Both are submitted in the same NEAR transaction; `createWithdrawalIdentifiers` assigns `wid.index = 0` and `wid.index = 1` respectively for the PoA bridge route (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. The PoA bridge indexer processes them and returns both entries for `getWithdrawalStatus` — as an unsorted array.
4. `describeWithdrawal({..., index: 0, withdrawalParams: {assetId: "nep141:btc.omft.near", ...}})` calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which — matching only on asset — can return Withdrawal B's completed entry (with `addrB`'s `transfer_tx_hash`) for the `index: 0` (Withdrawal A) query.
5. `watchWithdrawal` resolves index 0 as `{status: "completed", txHash: <addrB's hash>}`, misreporting Withdrawal A's outcome using Withdrawal B's on-chain result. [3](#0-2) [4](#0-3)

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
