### Title
Webhook `shop` (and other Shopify-supplied headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers that are entirely outside the data that `Utils::HmacValidator` verifies. Only the raw request body is signed. Since the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that has installed the app, an attacker who controls one shop (an "unprivileged internet user" from the perspective of any other tenant) can obtain a body+HMAC pair that is valid for the shared secret and replay it with an arbitrary `X-Shopify-Shop-Domain` header, causing the receiving application to process the payload as if it originated from a victim shop.

### Finding Description
`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` verifies only the HMAC, then unconditionally trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `hmac-verified bytes == raw_body` but the code treats `hmac-verified bytes == (raw_body, shop, topic, webhook_id, api_version)`. Because the same `client_secret` is shared by the app across all of its installed shops (confirmed in tests, where `ShopifyAPI::Context.api_secret_key` — the app-wide secret — is used to compute the webhook HMAC for any shop): [5](#0-4) 

an attacker who legitimately installs the app on their own shop can capture a genuine `(raw_body, hmac)` pair from a real webhook delivered to their own shop, then re-send that exact body/HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header changed to any other shop's domain. `HmacValidator.validate` still succeeds (it never looked at those headers), and `Registry.process` hands the forged `shop` value straight to the handler as authentic.

### Impact Explanation
This is a cross-tenant integrity violation: an app built on this gem, following its documented `Registry.process` API exactly as shown in the docs, cannot distinguish a webhook that is authentic for shop B from one replayed by an attacker who is a legitimate customer of shop A, because the `shop` field that identifies the tenant is never bound to the signature. Depending on what the handler does with `WebhookMetadata#shop` (e.g., looking up an offline session/access token for that shop to act on the "reported" data), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's store using that merchant's own access token — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any user able to install the app on their own development/trial store (a normal, unprivileged step available to any internet user for public apps) can capture a valid `(body, hmac)` pair from their own legitimate webhook traffic and replay it against the app's public webhook endpoint with a different shop header. No access token, `api_secret_key`, or privileged credential is required — only observation of one's own webhook traffic, which the gem's design implicitly assumes is safe because "the HMAC is the same as Shopify's."

### Recommendation
Bind the tenant/topic identity into the verified material instead of trusting unsigned headers. Concretely:
- Compute the webhook signature over a canonical string that includes `shop`, `topic`, and `webhook_id` in addition to the raw body (this would require coordinating with Shopify's webhook signing, so alternatively):
- Require callers of `Registry.process` to supply the expected `shop`/session context, and reject processing if `request.shop` does not match a shop the app has an active session/installation for at call time, rather than passing the header value through unchecked.
- At minimum, document prominently that `request.shop`/`request.topic`/`request.webhook_id` are unauthenticated header values and must be independently validated by the host application (e.g., checked against a known/installed shop list) before being trusted, since `Utils::HmacValidator` only authenticates the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal unprivileged action for any public app).
2. Shopify sends a legitimate webhook to the app's endpoint:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid hmac over raw_body computed with the app's shared client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id":1,...}
   ```
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker re-sends the identical request to the same endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `@raw_body` [6](#0-5)  — validation succeeds because the body and HMAC are untouched.
6. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop == "victim-shop.myshopify.com"`, even though the event never actually came from that shop [7](#0-6) .
