### Title
Unallowlisted swap venues can wrap unrelated token transfers into sender authorization - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A crafted route can place attacker-controlled pool code inside the sender’s Soroban authorization tree. Although the router only requires authorization for `execute_strategy` and its measured input transfer, a payload-selected venue can invoke an unrelated `token.transfer(sender, attacker, amount)`; if the sender signs the simulated authorization tree containing that extra child, the transfer executes alongside a fair swap.

### Finding Description
`Router::execute_strategy` accepts arbitrary `swap_xdr`, decodes it, and passes the resulting `StrategyPayload` to `execute::run`. [1](#0-0)  `run` authenticates `sender`, pulls `total_in`, and then executes every decoded operation. [2](#0-1)  For a swap operation, the pool address is taken directly from the caller-controlled `assets` registry and passed to `venues::dispatch_hop` without comparing it against an approved venue/pool registry. [3](#0-2) 

`dispatch_hop` invokes the selected venue adapter and validates only the router’s input and output balance deltas. [4](#0-3)  The venue-specific adapter then calls the payload-selected pool address; for example, the Soroswap adapter calls that address’s `get_reserves` and `swap` methods. [5](#0-4) [6](#0-5)  Consequently, attacker-controlled code runs while the sender’s authorization context is active.

The repository’s regression test demonstrates the resulting authorization wrapping: a rogue hop pool calls `token.transfer(victim, attacker, amount)`, simulation records that transfer as a child of the sender’s authorization entry, and signing that tree makes the theft execute. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker can steal unrelated wallet assets from a user who signs a poisoned route authorization, while still returning enough swap output for the router’s measured-output and minimum-output checks to pass. [9](#0-8)  The loss is not limited to `total_in`: the malicious venue can request a transfer of any unrelated token held by the sender, bounded by that sender’s balance and the authorization tree they sign. [7](#0-6)  This is theft of user funds through an authorization-wrapping primitive rather than an ordinary bad-price route.

### Likelihood Explanation
The attacker is unprivileged and only needs to deploy a contract exposing the selected venue ABI, encode it as the hop pool, and cause the victim to submit the generated authorization tree. [10](#0-9) [11](#0-10)  The exploit does require the victim to sign a tree containing the extra transfer, so it is not a purely unilateral contract call; a wallet that inspects and rejects unexpected child invocations prevents it. [12](#0-11)  The reachable impact and plausible signing flow make this a Medium finding.

### Recommendation
Maintain a governance-controlled venue-pool registry keyed by venue type and pool address, and reject any payload-selected pool that is not registered before invoking it. Apply the check centrally in `dispatch_hop` so every venue adapter inherits it. Continue measuring router balances, but do not rely on balance deltas to bound unrelated authorization requests. Clients should additionally reject any authorization tree containing children beyond the protocol-defined input transfer.

### Proof of Concept
1. The victim holds an unrelated `wallet_token` and calls `execute_strategy(sender=victim, total_in, swap_xdr)` directly, or reaches the router through `controller::swap_collateral(caller=victim, account_id, current, amount, new, swap)`.
2. The attacker deploys a contract implementing the selected venue interface, for example Soroswap `get_reserves` and `swap`.
3. The attacker encodes a `StrategyPayload` whose `assets` registry includes the attacker pool as the hop `pool`; structural decoding permits this because pool indices are only bounds-checked, not allowlisted. [13](#0-12) 
4. During the hop, the rogue pool receives the normal venue call and invokes `token.transfer(victim, attacker, wallet_balance)` in addition to paying a fair swap output back to the router.
5. Simulation records the unrelated transfer as a child invocation under the victim’s authorization entry. [14](#0-13) 
6. If the victim signs that tree, the swap succeeds and the unrelated tokens are transferred to the attacker. [15](#0-14)

    sender.require_auth();

    if total_in <= 0 {
        panic_with_error!(&env, Error::InvalidAmount);
    }

    let StrategyPayload {
        amounts,
        assets,
        ops,
    } = payload;
    let program = Program::decode(&env, &ops, assets.len(), amounts.len());

    let input_token = assets.get_unchecked(program.token_in);
    let output_token = assets.get_unchecked(program.token_out);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {

    /// Validates every instruction's opcode, mode, and indices before execution begins,
    /// including the `Prev` chain, same-token swaps, and split-weight bounds.
    fn validate(&self, env: &Env, assets_len: u32, amounts_len: u32, weight_count: u32) {
        for i in 0..self.op_count {
            let record = self.raw(i);
            let Some(opcode) = Opcode::from_u8(record[field::OPCODE]) else {
                panic_with_error!(env, Error::InvalidRouteXdr);
            };
            let mode = Mode::from_u8(record[field::MODE]);
            let (idx_a, idx_b, idx_c) = (
                record[field::POOL] as u32,
                record[field::TOKEN_IN] as u32,
                record[field::TOKEN_OUT] as u32,
            );

            // `Prev` is a purely structural link: the predecessor must exist,
            // must have a single output, and that output must be this
            // instruction's input.
            if mode == Mode::Prev {
                if i == 0 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
                let previous = self.raw(i - 1);
                let produced = match Opcode::from_u8(previous[field::OPCODE]) {
                    // A swap produces its `token_out`, a mint its share token.
                    Some(Opcode::Swap(_)) => previous[field::TOKEN_OUT],
                    Some(Opcode::Mint) => previous[field::TOKEN_IN],
                    // A burn releases every constituent at once.
                    _ => panic_with_error!(env, Error::BrokenTokenChain),
                };
                if idx_b != produced as u32 {
                    panic_with_error!(env, Error::BrokenTokenChain);
                }
            }
            match mode {
                Mode::Fixed(idx) if idx as u32 >= amounts_len => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                Mode::Ppm(idx) if idx as u32 >= weight_count => {
                    panic_with_error!(env, Error::InvalidRouteXdr)
                }
                _ => {}
            }

            if idx_a >= assets_len || idx_b >= assets_len {
                panic_with_error!(env, Error::InvalidRouteXdr);
            }
            match opcode {
                Opcode::Swap(_) => {
                    if idx_c >= assets_len {
                        panic_with_error!(env, Error::InvalidRouteXdr);
                    }
                    if idx_b == idx_c {
                        panic_with_error!(env, Error::SameToken);
