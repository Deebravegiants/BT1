Documentation explicitly states `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and that `data.shop` is "The shop domain of the webhook" (`docs/usage/webhooks.md:14`), which the sample handler uses directly as `shop_domain: data.shop` for `perform_later`. The doc gives no indication that `shop` is unauthenticated — it presents `Registry.process` as validating the entire request. This confirms the gem's own contract implies the `shop` field is verified, when in fact it is not covered by the HMAC.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body alone [1](#0-0) , while `shop` is read from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC and then forwards `request.shop` unchecked to the app's handler as the tenant identity [3](#0-2) .

### Finding Description
This mirrors the reported bug class: a field that is acted upon (here, the tenant-identifying `shop` domain) is not covered by the integrity check (here, the HMAC) that is supposed to bind the whole request together. `HmacValidator.validate` recomputes the signature only over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just `@raw_body` [4](#0-3) [1](#0-0) . The `shop-domain` header is entirely outside this signed string, so its value can be freely substituted without invalidating the HMAC, as long as the raw body and its corresponding valid HMAC are known.

Because the HMAC is keyed with the app's own `api_secret_key` [5](#0-4) , any (body, hmac) pair legitimately produced by Shopify for one shop's webhook remains valid when replayed to the same app's public webhook endpoint with an attacker-chosen `x-shopify-shop-domain` header pointing at a different, victim shop. `Registry.process` performs no additional binding between the header-derived `shop` and the signed content [6](#0-5) , so the forged tenant identity flows straight into `WebhookMetadata#shop`, which is documented as "The shop domain of the webhook" and used by app handlers to route/attribute the payload [7](#0-6) .

### Impact Explanation
An unprivileged internet user who can capture or receive one valid `(raw_body, hmac)` pair for the target app (e.g., by installing the app on their own store and observing a legitimate webhook delivery) can replay that exact body/HMAC to the app's public webhook endpoint while swapping in an arbitrary victim `x-shopify-shop-domain` value. The `hmac` still validates because the header isn't part of the signed content, yet the handler receives a `WebhookMetadata` claiming the payload belongs to the victim shop. Any app logic keyed on `data.shop` (e.g. `shop_domain: data.shop` in the documented sample handler [8](#0-7) ) can be tricked into writing, associating, or acting on data under the wrong tenant — a cross-tenant confusion/access condition.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (protected only by the HMAC check), so no credentials, tokens, or privileged access are required beyond observing one legitimate delivery for the attacker's own installation. Given the class breaks the equality "shop bound by header == shop covered by HMAC," and the gem's own documentation asserts `Registry.process` "will verify the request did indeed come from Shopify" without qualifying which fields are covered, this is a realistic and directly reachable path through the gem's own code.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the HMAC-signed content, or otherwise cryptographically tie the header-derived identity to the verified payload, so that `to_signable_string` cannot be satisfied by a replayed body under a different shop header. At minimum, document prominently that `Webhooks::Request#shop` is not authenticated by the HMAC and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for a webhook topic.
2. Shopify delivers a webhook to the app's endpoint with `raw_body = B` and header `x-shopify-hmac-sha256 = H`, where `H = HMAC-SHA256(api_secret_key, B)` — valid because `to_signable_string` returns only `B` [1](#0-0) .
3. Attacker captures `(B, H)` and replays a request to the same public webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature over `B` only, matches `H`, and returns `true` [5](#0-4) .
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"` even though the body content actually originated from the attacker's own shop [9](#0-8) .
