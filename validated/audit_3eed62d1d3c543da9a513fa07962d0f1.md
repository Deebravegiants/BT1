Audit Report

## Title
JWT replay-cache TOCTOU race allows duplicate HTTP-trigger workflow execution with a single-use JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` performs its replay check via `h.jwtCache.isReplay(claims.ID)` and its replay record via `h.jwtCache.recordUsage(claims.ID)` as two separate, independently-locked operations rather than one atomic check-and-set. Two near-simultaneous requests carrying the identical, validly-signed, single-use trigger JWT can both pass `isReplay` before either calls `recordUsage`, allowing a single JWT to authorize more than one downstream workflow-trigger dispatch.

## Finding Description
`Authorize` verifies the JWT, checks replay with a read-lock-protected lookup, verifies signer authorization, and only afterward takes a write lock to record usage: [1](#0-0) 

The cache's two operations are implemented as independent, separately-locked methods rather than a single atomic operation: [2](#0-1) 

Because `HandleUserTriggerRequest` calls `authorizeRequest` → `Authorize` per inbound request with no per-jti serialization, this is a genuine check-then-act race: two goroutines handling two requests with the same `jti` can both observe `isReplay(...) == false` before either executes `recordUsage(...)`, both passing authorization and each proceeding to trigger its own downstream fan-out via `sendWithRetries`. The comparison to `vault.RequestReplayGuard.CheckAndRecord`, which holds a single mutex across both the "seen?" check and the "record" write, is accurate and confirms the codebase already has a correct pattern for this exact hazard elsewhere: [3](#0-2) 

No other de-duplication layer (e.g., request-ID based dedup prior to `Authorize`) closes this window; `resolveWorkflowID` and `authorizeRequest` run per-request without any additional serialization keyed by JWT ID.

## Impact Explanation
An unprivileged external client holding one valid, signer-authorized, single-use trigger JWT can, by firing the same JWT concurrently, cause more than one accepted authorization and more than one downstream workflow-execute trigger to be dispatched to the DON, in excess of what the single-use JWT was meant to authorize. This maps to the "unauthorized job run" / gateway request impersonation impact category, since the JWT's explicit guarantee ("please generate a new one with a new jti") is a single-use control that this race defeats.

## Likelihood Explanation
Exploitation requires only sending the same signed request twice from concurrent connections — no privileged access, no signature break, and no node compromise. The race window is narrow (two back-to-back independently-locked calls) but is a textbook TOCTOU pattern reliably triggerable with parallel HTTP requests, especially given normal internet-facing latency jitter. This is realistic and repeatable, not merely theoretical, since the code path and lock structure are exactly as described.

## Recommendation
Add a single atomic `checkAndRecord(jti string) bool` method on `jwtReplayCache` that holds the write lock across both the existence check and the insertion (mirroring `RequestReplayGuard.CheckAndRecord`), and call it once from `Authorize` in place of the separate `isReplay`/`recordUsage` calls.

## Proof of Concept
1. Obtain one valid, signer-authorized trigger JWT (`jti = X`) for a target `workflowID`.
2. Fire two concurrent HTTP requests to the gateway's HTTP-trigger endpoint carrying the identical JWT (e.g., two parallel goroutines/connections).
3. Both requests can execute `h.jwtCache.isReplay(claims.ID)` → `false` before either executes `h.jwtCache.recordUsage(claims.ID)`, since these are separate, non-atomic lock acquisitions (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` lines 87–105, 399–412).
4. Both calls to `Authorize` succeed, and `HandleUserTriggerRequest` proceeds twice through `sendWithRetries`, dispatching two separate workflow-execute triggers to the DON from a single-use JWT.
5. A Go unit test that spins up two goroutines calling `Authorize` with the same JWT and asserts both succeed (or a race-detector-enabled integration test hitting the HTTP-trigger endpoint concurrently) would confirm the duplicate-acceptance behavior.

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
