# #Vulnerability found

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, not the shop header. Any actor who possesses one valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` (e.g. from a webhook legitimately delivered to their own installed shop) can resend that exact payload to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and `ShopifyAPI::Webhooks::Registry.process` will hand the handler a `WebhookMetadata` object that attributes the (attacker-controlled) body to a victim shop.

### Finding Description
`Registry.process` validates authenticity purely via HMAC and then trusts `request.shop` as the tenant identifier for the payload: [1](#0-0) 

The HMAC check is: [2](#0-1) 

which calls `verifiable_query.to_signable_string`. For webhooks, that method is: [3](#0-2) 

i.e. only `@raw_body` is signed. But `shop` is read independently from a header that isn't part of the signed data at all: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(raw_body) ⇒ shop_header == originating_shop`

But the code only proves `hmac_valid(raw_body)`; it never proves that the specific `shop` header value was the one Shopify associated with that HMAC. Since the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across *every* shop that has installed the app, a single valid `(body, hmac)` pair obtained by any one merchant (from their own genuine webhook deliveries, which are visible to them since they own that shop and can see the delivered payload/headers) remains a "valid" signed payload no matter which `shop` header is later attached, because the header is not part of `to_signable_string`.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhooks: `WebhookMetadata.shop` (built from `request.shop`) is the field host applications are expected to trust to determine which merchant/tenant a webhook event belongs to (see `Registry.process` passing `shop: request.shop` into the handler). An attacker who is a legitimate (but malicious) user of the app on their own shop can replay their own captured, validly-HMAC'd webhook body against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The handler will treat the attacker-controlled body as authentic data belonging to the victim tenant — a cross-tenant data/event injection that satisfies the "cross-tenant access" Critical impact criterion, since it lets one tenant inject fraudulent, HMAC-"verified" events into another tenant's processing pipeline.

### Likelihood Explanation
Any merchant who has installed the app can trivially capture a real webhook delivery (body + `X-Shopify-Hmac-Sha256` header) sent to their own endpoint, since it is delivered directly to infrastructure they control. Replaying that exact body with a different `Shop-Domain` header to the same public webhook endpoint requires no secret knowledge, no privileged account beyond ordinary app installation, and no cryptographic break — only a basic HTTP replay with one header changed. This is a low-effort, self-serviceable attack path.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind `shop` to `raw_body` before trusting it — e.g., verify the header value against a shop that is independently known to be authorized for the tenant context the app is currently processing, or require the host application to cross-check `request.shop` against session/store records rather than trusting it as ground truth straight out of `Webhooks::Request`. At minimum, document that `request.shop` is unauthenticated and must not be used as a sole tenant selector.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing:
   - `raw_body` (e.g. an `orders/create` JSON payload)
   - `X-Shopify-Hmac-Sha256: <valid hmac over raw_body computed with the app's shared client_secret>`
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the **same** `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `HmacValidator.validate(request)` succeeds because it only hashes `@raw_body`, which is unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's payload> ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity.
