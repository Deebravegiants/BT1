### Title
Third-party dust top-up permanently blocks `clean_bad_debt` on insolvent accounts - (File: contracts/controller/src/positions/liquidation/curve.rs)

### Summary
Analogous to the InstaDApp `build(X)` front-run that flips a precondition and makes `setOwner(X)` revert forever, an unprivileged attacker can flip the precondition of the permissionless `clean_bad_debt` entrypoint by topping up a foreign insolvent account's existing collateral leg. The dust gate in `is_socializable_bad_debt` requires `total_collateral <= BAD_DEBT_USD_THRESHOLD` ($5 in WAD); `supply` lets any caller add to a supply leg an account already holds. A ~$5 top-up pushes collateral strictly above the cap, so every subsequent `clean_bad_debt` reverts with `CannotCleanBadDebt`. Repeating the top-up whenever the oracle price drifts collateral back under the cap keeps the gate shut indefinitely.

### Finding Description
- `clean_bad_debt` → `socialize_bad_debt(account_id, BadDebtGate::DustCapped)` asserts `is_socializable_bad_debt(total_debt, total_collateral)`, i.e. `total_debt > total_collateral && total_collateral <= 5 WAD` (`contracts/controller/src/positions/liquidation/mod.rs:229-235`, `contracts/controller/src/positions/liquidation/curve.rs:25-27`).
- `supply` is permissionless for existing legs: `require_third_party_existing_supply` only rejects assets the account does not already hold (`contracts/controller/src/positions/supply.rs:78-97`), so a stranger can add any amount to the victim's current collateral asset.
- The gate is value-based, not count-based: one leg must carry the account over $5. The Certora spec proves the straddle: `collateral_wad > BAD_DEBT_USD_THRESHOLD && debt_wad > collateral_wad` makes the dust gate reject while the owner-only `InsolventOnly` gate still admits (`certora/controller/spec/boundary_rules.rs:44-103`).
- Liquidation does not rescue the state: a `liquidate` call on the account runs `check_bad_debt_after_liquidation`, which applies the *same* dust gate and merely skips cleanup when it fails (`contracts/controller/src/positions/liquidation/apply.rs:313-315`). Seizing the remaining collateral is what would reopen the gate, but on an insolvent account a full seizure repays less value than it costs the liquidator, so no rational liquidator performs it.
- The only remaining exit is the owner-gated `force_socialize_bad_debt` (`BadDebtGate::InsolventOnly`, `mod.rs:246-249`), which is privileged — exactly like the InstaDApp report's recommended registry-only `build`.

### Impact Explanation
Unsocializable bad debt keeps accruing borrow interest while the account's NFT, debt positions and residual collateral can never be permissionless cleaned. The protocol's only self-service insolvency drain is bricked for as long as the attacker funds the straddle (≈$5 per top-up, forfeited into the account's collateral each time). Until governance executes `force_socialize_bad_debt`, the debt is neither repaid nor written down — a persistent freezing of the bad-debt resolution path that grows the eventual supply-index write-down borne by suppliers. Severity: Medium (escape hatch exists, but it is privileged and delayed; the permissionless path the protocol relies on is DoSed by an unprivileged address at small cost).

### Likelihood Explanation
The attack requires only: an insolvent account whose collateral sits at/below $5 (the exact state `clean_bad_debt` exists for), and a `supply(caller, account_id, spoke_id, [(held_collateral_asset, ~$5+)])` call. No timing race is even needed — the attacker can simply watch for the gate opening and top up in the same ledger. The only cost is the donated collateral, which becomes claimable revenue on cleanup, so each refill is a one-way ~$5 burn; sustainable for motivated griefing of large bad debt.

### Recommendation
Restrict third-party `supply` top-ups on accounts that are insolvent (e.g., reject top-ups when `total_debt > total_collateral`), or make the dust gate count only collateral that existed before the account became insolvent / ignore top-ups below a per-account minimum. Alternatively, allow `clean_bad_debt` to first sweep collateral above the cap as revenue (it already reclassifies all remaining collateral shares as revenue) so the gate cannot be straddled by donations.

### Proof of Concept
1. Alice supplies 20 USDC6, borrows 10 LOW3; price crashes so `total_collateral = $4 < total_debt`. `clean_bad_debt(anyone, alice_id)` would succeed.
2. Attacker calls `supply(attacker, alice_id, spoke, [(USDC6, 2.0)])` — permitted because Alice already holds a USDC6 supply leg (`require_third_party_existing_supply`).
3. Now `total_collateral = $6 > BAD_DEBT_USD_THRESHOLD`; `socialize_bad_debt` asserts `is_socializable_bad_debt` → reverts `CannotCleanBadDebt` (#114).
4. Liquidating is unprofitable (seizing $6 costs >$6 of debt repayment) and `check_bad_debt_after_liquidation` uses the same gate anyway.
5. On any price move that pulls collateral back under $5, the attacker tops up again. The account's bad debt is only removable via owner-gated `force_socialize_bad_debt`.

This mirrors the pinned fixture `test_force_socialize_bad_debt_above_dust_threshold` (`tests/test-harness/tests/controller/bad_debt_index.rs:145-178`), which shows an insolvent account above the dust cap refuses `clean_bad_debt` and needs the privileged path — the attacker just manufactures that straddle state with permissionless `supply`.
