### Title
Webhook HMAC signature does not cover the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw request body only, while the `shop` (tenant identifier) is read directly from an unsigned header. `Registry.process` validates the body's HMAC and then hands `request.shop` straight to the application's webhook handler, so the "shop" value that drives tenant attribution is never bound to the cryptographic signature.

### Finding Description
The signable content for a webhook is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor instead reads a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` validates only this body HMAC and then forwards `request.shop` — the unsigned header — to the handler as the tenant identity for the event: [4](#0-3) 

The identity binding broken here is: `HMAC(raw_body, client_secret)` is treated as proof of `(raw_body, shop)`, when in reality it only proves `raw_body`. Because the `client_secret` used to compute a webhook's HMAC is shared across every shop that has the app installed (it is the app's secret, not a per-shop secret), any merchant who has legitimately installed the app can receive a valid `(raw_body, hmac)` pair for their own shop and then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it never inspects the header), and the handler receives `WebhookMetadata` attributing the (attacker-chosen) body to the victim shop: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary that webhook consumers rely on: an attacker who is themselves an installer of the app (an unprivileged, legitimate multi-tenant user of the gem's host application) can forge webhook events that are cryptographically "valid" per this library's own validation, but attributed to any other shop of the attacker's choosing. Any host application that trusts `WebhookMetadata#shop` (as the library's own API and docs intend) to select which tenant's records to create/update/delete is exposed to cross-tenant data injection/corruption — this satisfies the "cross-tenant access" Critical impact category, since it is achieved purely through this gem's own validation logic without needing the app's `client_secret`, an access token, or any privileged credential beyond being one ordinary installer among many.

### Likelihood Explanation
Likelihood is high for any multi-merchant app: the attacker only needs to install the app on their own store (an ordinary, unprivileged action available to any Shopify merchant) to receive a genuine webhook with a valid HMAC, then replay the captured body/HMAC pair against the app's public webhook endpoint with a different `shop-domain` header. No secret material, TLS interception, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material verified against the HMAC, or otherwise cryptographically tie the header-derived shop to the event before it is handed to application handlers — e.g., require host applications to cross-check `request.shop` against an already-known/authenticated session for that webhook subscription rather than trusting the header outright, or extend `to_signable_string` semantics/documentation so implementers know the shop header is unauthenticated and must be independently verified (e.g., against the shop that the webhook was registered for via `Registry`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC-SHA256(B, client_secret)` and `client_secret` is shared across all installs).
2. Attacker replays this exact request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation passes: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled webhook data under the victim shop's tenant context.
