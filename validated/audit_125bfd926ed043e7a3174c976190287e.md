### Title
Unbounded cyclic-ancestry walk in GRANDPA justification verification allows relayer-triggered infinite loop / DoS - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry`, used to validate GRANDPA finality proofs submitted by any relayer via the `update_client`/consensus-message path, walks parent-hash pointers through an attacker-supplied set of headers (`votes_ancestries` / `unknown_headers`) with no cycle detection and no bound on iteration count. A relayer can submit two (or a few) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches the expected `base` hash, causing the `while current_hash != base` loop to run forever. This mirrors the librsvg CVE-2015-7558 bug class: unvalidated cyclic references driving an unbounded traversal into infinite loop / resource exhaustion.

### Finding Description
`AncestryChain::ancestry` builds a lookup map from an attacker-controlled header list and then repeatedly follows `parent_hash()` pointers: [1](#0-0) 

```rust
pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}
impl<H: HeaderT> AncestryChain<H> {
	pub fn new(ancestry: &[H]) -> AncestryChain<H> { ... }
}
impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H> {
	fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
```

The `ancestry` map is constructed directly from the untrusted proof payload (`votes_ancestries`/`unknown_headers`), which the submitter of a GRANDPA `ConsensusMessage` fully controls: [2](#0-1) 

The loop terminates only when it finds `base` or when a hash is *not* present in the map (returning `NotDescendent`). If the attacker instead builds a small set of headers whose `parent_hash` fields form a closed cycle among themselves (e.g., `H1.parent_hash == hash(H2)`, `H2.parent_hash == hash(H1)`), and neither hash equals `base`, every lookup in the loop succeeds and `current_hash` oscillates between the cycle members forever — the loop never returns.

This function is called from the on-chain finality-proof verification path used by every incoming GRANDPA consensus message, both for the main commit target and for every non-base precommit target: [3](#0-2) 

and from the higher-level verifier invoked when a relayer submits a consensus update: [4](#0-3) 

and again in the fraud-proof path: [5](#0-4) 

None of these call sites impose an acyclicity check or an iteration cap on `ancestry()` before invoking it — the only bounds present elsewhere in the codebase (e.g., `MAX_PROOF_DEPTH` in the unrelated Pharos SPV verifier) do not apply here.

### Impact Explanation
Any unprivileged relayer able to submit a GRANDPA `ConsensusMessage` (via `update_client`) or a fraud-proof message can craft a justification containing a small cyclic set of headers in `votes_ancestries`/`unknown_headers`. When the runtime executes `verify_grandpa_finality_proof` / `GrandpaJustification::verify`, the resulting infinite loop hangs block execution for that extrinsic, exhausting the block's execution time/weight budget and potentially stalling the chain or causing collators/validators to fail to produce/import blocks — a denial of service against the ISMP consensus-verification pipeline that every cross-chain message relies on. Because this sits directly in the path used to accept new GRANDPA-attested state commitments, a successful attack can also stop delivery of all pending cross-chain messages routed through this consensus client until the runtime is patched/restarted.

### Likelihood Explanation
High. Constructing the malicious proof requires only two or three headers with reciprocal `parent_hash` values that hash-collide appropriately (trivial: an attacker fully controls header contents subject only to already-known hash function, no PoW/signature constraint on headers themselves — only the commit/precommit signatures need to be valid, and the ancestry headers used to build the cyclic map do not need any signature at all). Submitting the message requires no special privilege — any account that can call the ISMP `update_client`/consensus message handler (an intentionally permissionless entry point for relayers) can trigger it.

### Recommendation
Add cycle protection and/or an iteration bound to `AncestryChain::ancestry`:
- Track visited hashes in a `BTreeSet` and abort with an error (e.g., `NotDescendent` or a new `CyclicAncestry` error) if a hash is revisited.
- Alternatively, bound the loop to at most `votes_ancestries.len() + 1` iterations (the maximum possible acyclic chain length for the supplied header set), erroring out if exceeded.
- Apply the same fix everywhere `AncestryChain::ancestry` is invoked (`justification.rs::verify_with_voter_set`, `verifier/src/lib.rs::verify_grandpa_finality_proof`, and `consensus.rs::verify_fraud_proof`).

### Proof of Concept
1. Construct headers `H1` and `H2` such that `H1.parent_hash() == H2.hash()` and `H2.parent_hash() == H1.hash()`, with `H2.hash() != base` and `H1.hash() != base` for the target commit under verification.
2. Include `H1, H2` in `votes_ancestries` (for `GrandpaJustification::verify`) or `unknown_headers` (for `verify_grandpa_finality_proof`), and craft a valid commit/precommit signature set pointing a non-base precommit target at `H1.hash()`.
3. Submit this as a `ConsensusMessage::StandaloneChain`/`Polkadot`/`Relaychain` payload to the GRANDPA client's `update_client` handler (or as a fraud-proof to `verify_fraud_proof`).
4. `AncestryChain::ancestry(base, H1.hash())` enters `while current_hash != base`, alternates between `H1.hash()` and `H2.hash()` indefinitely since both are always found in the map, and never returns — hanging the executing node/runtime.

Note: I was not able to execute this PoC against a live runtime within this analysis (no code execution environment available); the finding is based on static review of the loop logic and its unbounded, attacker-controlled input, which is sufficient to demonstrate the non-termination bug is reachable without any additional privilege.

pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

	H::Number: finality_grandpa::BlockNumberOps,
