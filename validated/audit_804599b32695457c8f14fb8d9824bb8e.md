**Analysis:**

The proposed attack scenario is not realizable given how `HotStateLRU` is actually structured and used.

1. **`pending` is a plain `HashMap`, not a queue.** In `HotStateLRU::insert` [1](#0-0) , a re-insertion of the same key first calls `self.delete(&key_hash)` and then `self.insert_as_head(key_hash, slot)`, which does `self.pending.insert(key_hash, slot)` [2](#0-1) . `HashMap::insert` unconditionally overwrites any prior value for that key — there is no "later re-insertion queued in pending" that hasn't taken effect; the map always reflects the last write synchronously. `get_slot` simply does a direct `pending.get(key_hash)` lookup [3](#0-2) , so it can never observe an intermediate value once the corresponding `insert()`/`maybe_evict()` call has returned.

2. **No externally observable intermediate state.** The transient window inside `insert()` between `delete()` (which leaves the old pending entry untouched) and `insert_as_head()` (which overwrites it) exists only within a single synchronous Rust function call on a single thread owning that shard's `HotStateLRU`. There is no yield point, no concurrency, and no external caller (VM execution, API, or another shard) can call `get_slot` mid-way through this call. The struct is constructed, driven to completion, and consumed via `into_updates()` [4](#0-3)  entirely within one shard's sequential computation in `State::compute_state`-style code [5](#0-4) .

3. **`maybe_evict` cannot evict a key that was just re-hotted in the same call.** `maybe_evict` only evicts starting from `self.tail`, i.e., the least-recently-used entries [6](#0-5) . Any key freshly written via `insert()` is moved to `head`, not `tail`, so it cannot be the target of eviction within the same call unless it was never touched afterward — which is correct LRU semantics, not a bug. Evictions are also only triggered at checkpoint boundaries, after all `apply_one_update` calls for that version range have already completed [7](#0-6) , so there's no interleaving of "evict, then re-hot, then read" within a single eviction pass.

4. **No value corruption even in principle.** `StateSlot::to_cold()` preserves the underlying `value`/`value_version` exactly, only dropping LRU chain metadata [8](#0-7) . The hot/cold distinction is a caching/LRU tier marker for the hot-state acceleration structure, not the source of truth for the state value itself; "cold" and "hot" representations of the same version carry identical value data. So even a hypothetical stale read would not yield a different fungible-asset balance — it's not a custody-relevant data corruption, just a caching-tier classification.

Given these three points, there is no unprivileged-input path that can cause `get_slot` to return a stale/incorrect balance value distinct from the correct current value, and no custody boundary (ownership, mint/burn/freeze authority, or balance correctness) is crossed.

    pub fn maybe_evict(&mut self) -> Vec<(HashValue, StateSlot)> {
        let mut current = match self.tail {
            Some(tail) => tail,
            None => {
                assert_eq!(self.num_items, 0);
                return Vec::new();
            },
        };

        let mut evicted = Vec::new();
        while self.num_items > self.capacity.get() {
            let slot = self
                .delete(&current)
                .expect("There must be entries to evict when current size is above capacity.");
            let prev_key_hash = *slot
                .prev()
                .expect("There must be at least one newer entry (num_items > capacity >= 1).");
            self.total_value_bytes -= slot.size();
            evicted.push((current, slot.clone()));
            self.pending.insert(current, slot.to_cold());
            current = prev_key_hash;
            self.num_items -= 1;
        }
        evicted
    }
