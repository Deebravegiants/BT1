### Title
Iris capture score threshold exceeds the metric's valid range, permanently blocking legitimate signups - ([File: src/consts.rs])

### Summary
`IRIS_SCORE_MIN` and `IRIS_SHARPNESS_MIN` in `src/consts.rs` are set to values (1.70 and 1.00) that appear to exceed the normal 0–1 range of the underlying IR-Net sharpness/score metrics, with an explicit `TODO: put back 0.68` comment on both constants indicating the intended, reachable threshold. [1](#0-0)  This mirrors the `ADAPTER_BREAKS_LOSS_POINT` bug class: a numeric guard threshold set so tight/unreachable that the gated code path (a legitimate acceptance condition) is effectively always rejected, making the feature non-functional for real, valid inputs rather than only rejecting bad ones.

### Finding Description
The biometric capture plan gates acceptance of an iris frame with `estimate.score >= IRIS_SCORE_MIN` as one of the conditions for `valid_capture`: [2](#0-1)  If the underlying `score` metric produced by IR-Net is normalized to at most 1.0 (consistent with sibling thresholds such as `THRESHOLD_OCCLUSION_30: f64 = 0.85` and the progress-bar computation `self.max_sharpness / IRIS_SCORE_MIN` clamped to `.min(1.0)`, implying `IRIS_SCORE_MIN` is expected to be a fraction close to but below 1.0), setting `IRIS_SCORE_MIN = 1.70` makes the condition mathematically unsatisfiable — no legitimate iris capture, however sharp, can ever cross the threshold. [3](#0-2)  The same pattern applies to `IRIS_SHARPNESS_MIN: f64 = 1.00`, used identically as a gating comparison in the distance agent (`sharpness > IRIS_SHARPNESS_MIN`), where a score right at the metric's maximum boundary is required to trip a "sharp iris detected" telemetry event. [4](#0-3)  Both constants carry the same explicit developer note `// TODO: put back 0.68`, strongly indicating the current values are not the intended production thresholds and were left in an inflated, effectively-blocking state. [1](#0-0) 

This is the direct analog of the reported issue: a boundary constant meant to filter out only bad/anomalous samples (compromised adapters in the report; low-quality iris captures here) was tuned so aggressively that it filters out virtually all real-world inputs, rendering the gated functionality (adapter fund allocation there; iris biometric capture completion here) non-functional.

### Impact Explanation
If `IRIS_SCORE_MIN`/`IRIS_SHARPNESS_MIN` are unreachable in practice, the `valid_capture` condition in `handle_ir_net` (biometric capture) never becomes true for the iris path, so `left_ir`/`right_ir` slots are never populated, and the biometric capture objective loop in `poll_extra` never completes normally — it can only exit via timeout (`self.timed_out = true`). [5](#0-4)  This effectively blocks all legitimate signups from completing the biometric-capture phase (an unpassable liveness/enrollment gate), a denial-of-legitimate-signup impact analogous to the report's "adapter effectively non-functional for volatile assets." It does not enable fraud or unauthorized signups by itself, but it is a concrete, in-scope reliability/availability failure of the enrollment pipeline for genuine users.

### Likelihood Explanation
This is not a rare edge case — it is the default constant compiled into every build. Every biometric-capture attempt exercises this comparison. The only mitigating factor is uncertainty about the true numeric range of `score`/`sharpness` outputs from the IR-Net model (this could not be independently confirmed since IR-Net's Python implementation is outside the indexed Rust code), but the internal evidence — the `TODO: put back 0.68` comments and the `.min(1.0)` clamp against `IRIS_SCORE_MIN` in the progress-bar math — strongly supports that these thresholds are misconfigured well beyond their intended, reachable range.

### Recommendation
Restore `IRIS_SCORE_MIN` and `IRIS_SHARPNESS_MIN` to the values indicated by the code's own `TODO` comments (around `0.68`), or otherwise recalibrate them against the actual empirical distribution of IR-Net `score`/`sharpness` outputs to ensure the thresholds are reachable by genuine, sharp iris captures while still rejecting low-quality ones. [1](#0-0) 

### Proof of Concept
1. Build/run the orb-core biometric capture flow with the shipped constants `IRIS_SHARPNESS_MIN = 1.00`, `IRIS_SCORE_MIN = 1.70`. [1](#0-0) 
2. During `handle_ir_net`, observe that `estimate.score >= IRIS_SCORE_MIN` in the `valid_capture` computation never evaluates true for any real IR-Net output, since these outputs are bounded well below 1.70. [2](#0-1) 
3. Because `left_ir`/`right_ir` are never set, `poll_extra`'s completion check `if let (Some(_rgb), Some(_ir)) = (rgb, ir)` never triggers, and the phase only ends via the `self.timeout` branch, setting `self.timed_out = true` — i.e., every signup attempt times out instead of completing. [6](#0-5)
