### Title
Shared per-AssetId minting in pallet-hyper-fungible-token lets one compromised remote-chain peer dilute all holders of that asset - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token` maps a single local `AssetId` to *multiple* remote-chain peer contracts via `TokenContracts`/`ContractToAsset` (`DoubleMap<StateMachine, AssetId, Vec<u8>>`), exactly the shared-pool-across-multiple-external-sources pattern that produced the Illuminate bug: several external principal sources feed into one shared local balance. `on_accept` authenticates only that the incoming request's `(source, from)` pair matches a registered peer for that `AssetId`, then unconditionally mints (`Assets::mint_into`) or releases escrow for the decoded amount — with no check that the specific remote-chain peer/contract is healthy, unpaused, or still solvent.

### Finding Description [1](#0-0) 
`TokenContracts` and `ContractToAsset` let one local `AssetId` be registered against contracts on several different `StateMachine`s simultaneously, and `NativeAssets` records only a single native/non-native flag per asset — there is no per-(chain, asset) health/pause flag. [2](#0-1) 
`on_accept` looks up `local_asset_id` purely from `ContractToAsset::<T>::get(source, &from)`, decodes the message, converts decimals, and then calls `Assets::mint_into` (non-native case) or transfers from the pallet's escrow account (native case) — there is no check of whether the peer chain/contract that produced this valid ISMP proof is itself paused, drained, or otherwise compromised on its side. As long as a cryptographically valid ISMP proof for a registered peer arrives, the pallet mints into the shared `AssetId` supply.

This mirrors the Illuminate `Lender.mint()` bug exactly: `Lender.mint()` trusted `IMarketPlace(marketPlace).token(u, m, p)` without checking whether protocol `p`'s underlying was paused/insolvent, and minted Illuminate PTs 1:1 that shared a pooled, per-share redemption with other protocols' PTs for the same market. Here, `on_accept` trusts any registered peer chain's message without checking that peer's health, and mints into an `AssetId` supply that is shared across every other peer chain registered for that same `AssetId`.

### Impact Explanation
If any one of the registered remote peer deployments for an `AssetId` becomes compromised (e.g., its own token contract is drained/insolvent, or an unauthorized-but-cryptographically-valid state transition occurs on that chain enabling a burn-then-cross-chain-mint sequence with unbacked value), the substrate pallet will still honor a valid ISMP proof from that peer and mint fresh supply into the shared local `AssetId`. Since that `AssetId`'s balance is fungible and shared across all chains registered for it, every other holder's claim (e.g., anyone who received the asset via a different, healthy peer chain) is diluted — this is a direct loss of value for uninvolved holders, matching the "theft of at-rest/in-motion funds" impact class from the source report (Medium/High severity: unbacked mint diluting a shared pool).

### Likelihood Explanation
Reachable by any relayer submitting a legitimately-proven ISMP `PostRequest` from any registered peer chain — no privileged/admin action required on the Hyperbridge side. The only precondition is that *one* of the multiple peer deployments backing a shared `AssetId` becomes unsound (paused, insolvent, or exploited on its own chain) while continuing to accept sends/mints locally; nothing in `on_accept` cross-checks peer health before crediting the shared asset. This is analogous to, and just as likely as, the original Illuminate scenario where an external protocol (Pendle) pausing/entering emergency mode did not stop `Lender.mint()` from continuing to accept its (now worthless) PT.

### Recommendation
Add a per-(chain, asset) circuit breaker / health flag that `CreateOrigin`-governance can set to reject `on_accept` for a specific peer chain-asset pairing (mirroring the existing `unpaused`-style gating used elsewhere in the codebase, e.g., `HyperFungibleToken.sol`'s `whenNotPaused`/relayer gating). Consider also tracking supply contributed per-peer-chain so a single compromised peer's contribution can be isolated/frozen without penalizing holders whose balance originated from other, healthy peers, rather than pooling all peers into one fungible, undifferentiated `AssetId` balance.

### Proof of Concept
1. Governance registers `AssetId = X` with peer contracts on both `Chain A` and `Chain B` via `create_erc6160_asset`/`register_token` (both mapped into the same local `AssetId` in `TokenContracts`/`ContractToAsset`).
2. Users on both chains bridge legitimate value into the shared `AssetId` supply on the substrate chain.
3. `Chain A`'s peer contract deployment later becomes compromised/insolvent (its own backing is drained or it is operating in a degraded state) but continues, from its own chain's perspective, to allow burn+dispatch of a valid ISMP `PostRequest` claiming a transfer.
4. A relayer delivers this valid-but-economically-unbacked proof to the substrate chain; `on_accept` (module.rs lines 50-117) finds a matching `ContractToAsset` entry for `(Chain A, from)`, decodes the message, and calls `Assets::mint_into(local_asset_id, beneficiary, amount)` (or releases escrow) with no health check on Chain A's peer.
5. The freshly minted/released amount is now part of the same fungible `AssetId` supply that Chain B's honest depositors also hold, diluting/impairing their claim on that shared asset with no on-chain mechanism to distinguish or freeze the bad inflow per peer chain.

	fn on_accept(
		&self,
		PostRequest { body, from, source, .. }: PostRequest,
	) -> Result<Weight, anyhow::Error> {
		// Authenticate: look up which local asset this contract address maps to
		let local_asset_id = ContractToAsset::<T>::get(source, &from)
			.ok_or(HftError::UnknownSourceContract(source))?;

		// Decode the Message
		let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

		// Convert recipient bytes to substrate AccountId
		// If 32 bytes: use directly. If 20 bytes: left-pad with zeros.
		let mut beneficiary_bytes = [0u8; 32];
		let to_bytes = message.to.as_ref();
		if to_bytes.len() == 32 {
			beneficiary_bytes.copy_from_slice(to_bytes);
		} else if to_bytes.len() == 20 {
			beneficiary_bytes[12..].copy_from_slice(to_bytes);
		} else {
			Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
		}
		let beneficiary: T::AccountId = beneficiary_bytes.into();

		// Convert amount from ERC20 denomination to local
		let decimals = if local_asset_id == T::NativeAssetId::get() {
			T::Decimals::get()
		} else {
			<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
				local_asset_id.clone(),
			)
		};
		let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), source)
			.ok_or(HftError::DecimalsNotConfigured(source))?;
		let amount = convert_to_balance::<
			<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance,
		>(
			U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
			erc_decimals,
			decimals,
		)
		.map_err(|e| HftError::InvalidAmountConversion(format!("{e:?}")))?;

		// Mint or transfer to beneficiary
		if local_asset_id == T::NativeAssetId::get() {
			<T as Config>::NativeCurrency::transfer(
				&Pallet::<T>::pallet_account(),
				&beneficiary,
				amount,
				ExistenceRequirement::AllowDeath,
			)
			.map_err(|e| HftError::TransferFailed(e.into()))?;
		} else {
			let is_native = NativeAssets::<T>::get(local_asset_id.clone());
			if is_native {
				<T as Config>::Assets::transfer(
					local_asset_id,
					&Pallet::<T>::pallet_account(),
					&beneficiary,
					amount.into(),
					Preservation::Expendable,
				)
				.map_err(|e| HftError::TransferFailed(e.into()))?;
			} else {
				<T as Config>::Assets::mint_into(local_asset_id, &beneficiary, amount.into())
					.map_err(|e| HftError::MintFailed(e.into()))?;
			}
		}
