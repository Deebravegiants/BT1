### Title
`EvmHost.dispatch`/`fundRequest` use a hardcoded single-hop WETH→feeToken Uniswap path and never refund unspent native token to the caller, permanently trapping ETH when the swap consumes less than `msg.value` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept native token payment and swap it for `feeToken` through a hardcoded, single-hop UniswapV2 `path = [WETH, feeToken()]` using `swapETHForExactTokens`. Unlike other code paths in this same repository (`IntentGatewayV2.placeOrder`) that capture the router's returned `amounts[0]` and explicitly refund the caller for unspent `msg.value`, these three `EvmHost` functions discard the returned `amounts` and never refund the excess ETH to `_msgSender()`. Because `IUniswapV2Router02.swapETHForExactTokens` refunds unspent ETH to `msg.sender` of the swap call — which here is `EvmHost` itself, not the original dispatcher — any ETH sent above what the exact-output swap consumes is permanently absorbed by the `EvmHost` contract with no accounting or withdrawal path back to the payer.

the same pattern repeats in `dispatch(DispatchGet memory get)`: [2](#0-1)

All three functions build `path = [WETH, feeToken()]` and call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee/amount, path, address(this), block.timestamp)` without capturing the returned `uint256[] amounts`. Per the standard UniswapV2Router02 implementation, `swapETHForExactTokens` computes `amounts = getAmountsIn(amountOut, path)`, requires `msg.value >= amounts[0]`, performs the swap, and — critically — refunds any unspent ETH (`msg.value - amounts[0]`) to `msg.sender` of that call. In this context `msg.sender` of the router call is the `EvmHost` contract itself, not the end user who called `dispatch`/`fundRequest`. Since `EvmHost` neither reads `amounts[0]` nor forwards the leftover ETH back to `_msgSender()`, any ETH sent in excess of the exact amount required for the swap becomes permanently stuck in the `EvmHost` contract balance.

This is the same root-cause class flagged in the referenced report — a hardcoded/naive swap path used inside a payment-collection code path without accounting for the difference between requested input and actual consumed input — except here the naive handling doesn't just risk suboptimal execution price, it structurally discards user funds on every overpayment because there is no refund-forwarding logic, unlike the sibling function in the same codebase, `IntentGatewayV2.placeOrder`, which does it correctly: [4](#0-3) 

Notably `IntentGatewayV2.placeOrder` explicitly computes `amounts[0]` and calls `_sendValue(msg.sender, msgValue)` to refund unspent native token, proving the project is aware refunds must be forwarded — `EvmHost` is missing this logic entirely.

### Impact Explanation
Any unprivileged caller who dispatches a POST/GET request or funds an existing request using native token payment (a very common, encouraged path per the docs: "Native Token Payment... let the Host handle the Uniswap swap") loses the entirety of any ETH sent beyond the exact amount required to produce `post.fee`/`get.fee`/`amount` of `feeToken`. Since `swapETHForExactTokens` requires an exact output, users must generally overestimate `msg.value` (the docs themselves note this is "Approximate (subject to slippage)" and quoted off-chain), so overpayment is the expected normal case, not an edge case. There is no `withdraw`/sweep function visible in `EvmHost` for native ETH, so these funds are permanently frozen in the contract with no path to recovery for the user or even governance (grep for `withdraw`/`native`/`balance` in `EvmHost.sol` shows no ETH-sweep function). This is a direct, protocol-wide loss/freezing of user funds triggered by the single most common integration pattern documented for dispatching messages with native payment.

### Likelihood Explanation
High. Every native-token dispatch or `fundRequest` call is affected, and overpayment is unavoidable in practice because the exact ETH-to-feeToken exchange rate is only knowable off-chain via `quote()`/`getAmountsIn`, which is inherently stale by the time the transaction executes (any block delay, price movement, or conservative buffer added by the caller/SDK produces overpayment). This is not a contrived attacker scenario — it is the default, expected behavior for every user who pays gas/fees in native token, as explicitly documented in the project's own developer docs.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented correctly in `IntentGatewayV2.placeOrder` (`_sendValue(msg.sender, msgValue)`). Additionally, consider whether the hardcoded single-hop `[WETH, feeToken]` path is always the optimal/available route, or whether an admin-configurable path (as recommended in the referenced report) should be supported for chains where no direct WETH/feeToken pair exists with adequate liquidity.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 5 ether}(post)` with `post.fee = 100e18` (feeToken units), intending to pay the relayer fee in native ETH, but sending `5 ether` because the exact ETH cost is unknown/volatile at submission time.
2. Internally: `path = [WETH, feeToken()]`; `IUniswapV2Router02.swapETHForExactTokens{value: 5 ether}(100e18, path, address(this), block.timestamp)` executes. Suppose the actual cost to acquire `100e18` feeToken is `0.5 ether`.
3. The router refunds `5 ether - 0.5 ether = 4.5 ether` to `msg.sender` of the swap call, i.e., to `EvmHost` itself (since `EvmHost` is the caller of the router).
4. `EvmHost.dispatch` never reads this refund nor forwards any ETH back to the original user; the user's transaction returns having spent the full `5 ether` from their wallet, but only `0.5 ether` worth of value was used for its intended purpose — the remaining `4.5 ether` is now sitting in the `EvmHost` contract balance with no function to withdraw or return it.
5. Compare with `evm/tests/foundry/IntentGatewayV2Test.sol` `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` (lines 3714–3752), which demonstrates that the sibling `IntentGatewayV2.placeOrder` correctly refunds excess ETH to the user in an analogous fee-swap scenario — confirming `EvmHost` is missing equivalent logic.
