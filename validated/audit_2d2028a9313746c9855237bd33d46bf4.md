### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates the HMAC over the body only, then trusts these header-derived values to select the handler and to identify the tenant (`shop`) passed into that handler. Any party able to obtain one validly-signed webhook body for their own shop (which Shopify sends to every app installer using the app's single shared `client_secret`) can replay it with arbitrary `shop-domain`/`topic` headers and have it accepted as authentic, impersonating any other shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is included in the signable string. However, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` (shared with OAuth) simply recomputes the HMAC over `to_signable_string` and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts the header-derived `topic` (to select the handler) and `shop` (to identify the tenant) to build the metadata handed to the app's business logic: [4](#0-3) 

The broken identity binding is:
`shop authenticated by HMAC` (empty set — HMAC only covers the body) ≠ `shop acted upon by the handler` (`request.shop`, an attacker-controlled header value).

Because every shop that installs the app shares the same app-level `client_secret`, any installer (an unprivileged tenant relative to other merchants using the same app) legitimately receives a webhook whose body/HMAC pair validates successfully. That attacker can capture their own valid `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain (and/or the `shopify-topic` header changed to a different registered topic). `HmacValidator.validate` still succeeds, since it never inspects `shop` or `topic`, and `Registry.process` dispatches the forged request as if it came from the victim shop under whatever topic the attacker chose.

### Impact Explanation
This is a cross-tenant identity-spoofing vulnerability: an attacker can make the host application's webhook handler execute as if a webhook came from an arbitrary victim shop (e.g., triggering data deletion/redaction handlers, uninstall handling, or any tenant-scoped business logic keyed off `WebhookMetadata#shop`) without ever compromising the app's `client_secret` or any victim credentials. It qualifies as Critical — cross-tenant access — per the stated impact criteria, since the tenant boundary (`shop`) that host applications rely on to scope side effects is not actually authenticated by this gem.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on their own shop (a normal, unprivileged action) — this is enough to obtain a validly-signed webhook body/HMAC pair. No access to the app's `client_secret`, TLS interception, or victim credentials is required; only a header rewrite of a captured request is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so the recomputed HMAC changes if any of these header values are altered. At minimum, `topic` and `shop` — the two values acted upon by `Registry.process` — must be covered.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a webhook to the app with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `client_secret`, plus headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Topic: orders/create`.
3. Attacker captures this `(raw_body, hmac)` pair and resends it directly to the app's webhook endpoint, replacing the headers with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different registered `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged, `Utils::HmacValidator.validate` succeeds because `to_signable_string` only ever returns `@raw_body`, and `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, as shown in: [5](#0-4)
