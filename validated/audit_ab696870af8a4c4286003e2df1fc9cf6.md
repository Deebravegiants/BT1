### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a `Webhooks::Request` as authentic once `Utils::HmacValidator.validate` succeeds, but the HMAC signature only covers the raw request body — it never covers the `shop`, `topic`, or `webhook_id` values that are read from unauthenticated HTTP headers and then handed to the host application as if they were verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over that signable string and compares it to the received `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request — including `request.shop` — is authentic, then forwards `request.shop` straight into `WebhookMetadata` for the app's handler: [3](#0-2) 

`request.shop` itself is read directly from the `shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC or against any known/installed shop: [4](#0-3) 

This breaks the identity binding: `hmac-verified(raw_body)` ≠ `shop used for tenant routing`. Because the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app, an unprivileged merchant who installs the same app on their own store legitimately receives real, validly-signed webhook deliveries for their own shop (e.g. by creating an order to trigger `orders/create`). That attacker can then replay the exact `raw_body`/`hmac-sha256` pair against the victim's webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still passes (it only checks the body), so `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up the victim's session/tenant record and apply the (attacker-controlled) `body` to it — a standard and Shopify-documented usage pattern — the attacker can inject falsified data into another merchant's tenant, i.e. cross-tenant access/data injection, without ever needing the victim's credentials, session, or the app's `client_secret`.

### Likelihood Explanation
The prerequisite is only that the attacker can install the target app on a shop they control (a normal, unprivileged action any merchant/developer can take) and can trigger events that generate webhook deliveries with attacker-influenced body content, then replay the raw body/signature pair with a forged `shop-domain` header to the app's public webhook endpoint. No secret material or privileged access to the victim is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is verified, e.g. include the `shop-domain` header in the signable string used for HMAC comparison, or independently verify that `request.shop` corresponds to a shop with an active session/installation known to the app before trusting it for any tenant-scoped action, and document this requirement clearly for consumers of `Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order) so Shopify delivers a legitimately HMAC-signed webhook to the attacker's own endpoint; attacker records `raw_body` and the `x-shopify-hmac-sha256` value.
3. Attacker sends a POST to the victim app's public webhook route with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <captured value>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body = the captured `raw_body`
4. `ShopifyAPI::Webhooks::Registry.process` builds a `Webhooks::Request`, calls `Utils::HmacValidator.validate`, which succeeds because it only checks the body against the secret-derived HMAC.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, and any host logic keyed on `data.shop` now operates on the victim's tenant using attacker-supplied data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
