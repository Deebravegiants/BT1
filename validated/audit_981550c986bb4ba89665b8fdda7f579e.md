## Title
Predispatch/postdispatch dust‑sweep uses raw `IERC20.transfer` calldata whose return value is never checked, permanently locking escrowed tokens on the `CallDispatcher` for non‑reverting ERC20s - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow and `IntentsBase._execute`'s postdispatch sweep move tokens off the untrusted `CallDispatcher` back to the gateway by encoding a raw `IERC20.transfer` call and routing it through `CallDispatcher.dispatch`. `CallDispatcher.dispatch` only checks the low-level `success` boolean of the call, never the ERC20 `bool` return value, so a non-compliant token that returns `false` instead of reverting on a failed transfer will be treated as a successful sweep even though no tokens actually moved.

### Finding Description
In the predispatch escrow path, tokens produced by the predispatch call are swept from the `CallDispatcher` back to the gateway using manually encoded calldata instead of `SafeERC20.safeTransfer`: [1](#0-0) 

This call is executed through `CallDispatcher.dispatch`, which only reverts on a failed low-level call, not on an ERC20 `transfer` that returns `false`: [2](#0-1) 

Immediately after, the gateway measures "received" only via a balance-delta check and silently accepts whatever amount actually moved (including zero) as the new escrowed amount: [3](#0-2) 

If the token's `transfer()` returns `false` without reverting (e.g. legacy non-compliant ERC20s, or any token that returns `false` on a blacklist/pause/insufficient-allowance condition instead of reverting — the exact bug class cited in the referenced report), then:
- `CallDispatcher.dispatch` sees `success == true` and does not revert.
- The gateway's balance-delta check sees `received == 0` (no tokens actually arrived).
- `order.inputs[i].amount` is set to `0`, and the order is placed/committed with zero escrow for that leg.
- The actual token balance remains stuck on the `CallDispatcher` contract, which has no recovery/sweep mechanism for the predispatch leg outside of order fill/cancel logic that now references a zero-amount input.

The identical raw-`transfer` + no-return-check pattern also exists in the postdispatch dust sweep in `IntentsBase._execute`: [4](#0-3) 

and is duplicated on the Tron deployment: [5](#0-4) 

This deviates from the rest of the codebase, which consistently uses `SafeERC20.safeTransfer`/`safeTransferFrom` for every other token movement (e.g. `IntentsBase._withdraw`, `ExtrinsicIntents._fillCrossChain`, `IntrinsicIntents._fillSameChain`), all of which use `SafeERC20`: [6](#0-5) 

### Impact Explanation
For the predispatch path, tokens that return `false` instead of reverting on failure get permanently trapped on the `CallDispatcher` while the order proceeds with a recorded escrow of `0` (or less than actually deposited) for that input — this is a freezing/loss of user funds triggered from a single `placeOrder` call using such a token as a predispatch output/order input. For the postdispatch path in `_execute`, the impact is limited to protocol "dust" not being collected (lower severity), since it only affects surplus sweep-back, not user principal.

### Likelihood Explanation
Exploitability depends on the involved ERC20 token behaving non-standard (returning `false` rather than reverting on failure) — this is the exact token class the referenced report calls out (e.g., older tokens like ZRX-era semantics, or paused/blacklist-gated tokens that return `false`). The `predispatch` flow accepts an arbitrary token address chosen by the order creator (via the predispatch-call's swap output / `order.inputs[i].token`), so a user (attacker or victim) can trigger this path deliberately or be affected unknowingly when the swap output token has this behavior.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` calldata construction used for the dispatcher→gateway sweep in both `IntentGatewayV2.placeOrder` (predispatch) and `IntentsBase._execute` (postdispatch), and their Tron counterparts, with a mechanism that validates the ERC20 return value — e.g. have `CallDispatcher` decode and check boolean return data for calls whose selector matches ERC20 `transfer`/`transferFrom`, or have the sweep performed directly by the gateway/`IntentsBase` contract using `SafeERC20.safeTransfer` instead of routing it through the untrusted low-level `CallDispatcher.dispatch`.

### Proof of Concept
1. Order creator places an order whose `predispatch.call` swaps native ETH/some asset into `TokenX`, a non-standard ERC20 that returns `false` (instead of reverting) when `transfer()` fails (e.g., recipient temporarily blacklisted/paused).
2. `placeOrder` executes the predispatch call; `CallDispatcher` now holds `TokenX` balance ≥ `requiredAmount`, passing the `balance < requiredAmount` check.
3. The sweep call `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` is dispatched via `CallDispatcher.dispatch`; suppose `TokenX.transfer` internally fails (e.g., because the gateway is temporarily blacklisted) and returns `false` without reverting.
4. `CallDispatcher.dispatch` sees `success == true` (the low-level call didn't revert) and does not revert the transaction.
5. Back in `placeOrder`, `IERC20(token).balanceOf(address(this)) - balancesBefore[i]` computes `received == 0`; `order.inputs[i].amount` is set to `0`.
6. The order is committed and emitted with `0` escrowed `TokenX`, while the actual `TokenX` balance remains permanently stuck in the `CallDispatcher` contract with no path to recover it.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
