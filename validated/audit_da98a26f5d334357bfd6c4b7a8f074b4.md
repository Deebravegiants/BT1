Based on the investigation, I found a valid analog matching the report's bug class: an identity-binding field acted upon but not covered by the cryptographic signature.

### Title
Webhook shop/topic/webhook_id headers are trusted for tenant attribution but are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used to process a webhook entirely from HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns the raw body alone. The shop identity that the application acts upon is therefore never bound to the cryptographic signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.): [2](#0-1) 

But `to_signable_string`, which is the only input fed into the HMAC computation, returns just `@raw_body`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` and the app's `api_secret_key`, and does not incorporate any headers: [4](#0-3) 

This breaks the identity binding `shop_header == shop_bound_by_hmac`: the HMAC only proves "this body was signed by the app's secret," not "this body belongs to shop X." Since the `api_secret_key` is shared across every shop/tenant that installs the same app, any tenant that can obtain one valid `(raw_body, hmac)` pair for their own shop (e.g., by triggering a webhook event on their own installed shop and observing the delivery) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for a victim shop. `HmacValidator.validate` will still return `true` because the signature check never touched those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem lets header-supplied tenant identity pass HMAC verification unbound to the signed content. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up/delete a session, revoke access, or apply the payload to a specific merchant's stored state), an attacker who controls one tenant of a multi-tenant app can forge webhook events attributed to a different, victim tenant — meeting the "cross-tenant access" bar.

### Likelihood Explanation
Requires the attacker to be an actual installed user of the target public app (to legitimately trigger and observe one webhook delivery with a valid HMAC for their own tenant) and to be able to send a crafted HTTP request directly to the app's public webhook endpoint with substituted headers — no access to the `api_secret_key` or victim's tokens is needed. This is a realistic, unprivileged-attacker-reachable path for any multi-tenant Shopify app built on this gem.

### Recommendation
Bind the tenant-identifying fields into the signable content, or otherwise validate that the `shop` (and ideally `topic`/`webhook_id`) claimed by the headers is consistent with an independent, authenticated source before acting on it — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` so they are covered by the HMAC, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `state`, etc. into its signature.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop and captures the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify to the app's webhook endpoint.
3. Attacker replays the identical body and HMAC header to the same webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` (via `Request#to_signable_string` returning only `@raw_body`) succeeds because the signature never covered the shop header.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process attacker-controlled data as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
