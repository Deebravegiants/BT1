## Analysis

Looking at the webhook processing path, I found a concrete binding failure that matches the bug class described in the report.

### Title
Webhook `shop`/`topic`/`webhook-id` headers are trusted but not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the raw request body only, then blindly trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers when constructing the `WebhookMetadata` passed to the app's handler. Because these headers are not part of the signed payload, an attacker who possesses one legitimately-signed webhook (e.g., from their own shop where they installed the target app) can replay the same body/HMAC pair while substituting a different `shop-domain` header, and the gem will report it as an authenticated webhook belonging to the victim shop.

### Finding Description
`Utils::HmacValidator.validate` is invoked in `Registry.process`: [1](#0-0) 

The HMAC check itself only signs `@raw_body`, per `Request#to_signable_string`: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`process` then forwards these unauthenticated header values directly into `WebhookMetadata`, which is the only tenant-identifying data given to the app's handler: [1](#0-0) 

The invariant that should hold is: `shop-header == shop-that-produced-the-signed-body`. Because the header is excluded from the HMAC computation, this equality is never enforced by the gem — only `hmac(raw_body, api_secret_key)` is checked, and `api_secret_key` is shared across every shop that installs the app. Any party who can obtain one valid `(raw_body, hmac)` pair for any shop (trivially achievable by installing the app on their own store and capturing a real webhook delivery) can resend that exact body/HMAC with an arbitrary `shop-domain` header, and `Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the victim shop, while the body content is attacker-chosen data from their own shop.

### Impact Explanation
This breaks the shop-identity binding across tenants: an app relying on `WebhookMetadata#shop` to route webhook data to per-tenant storage (the exact pattern shown in the gem's own docs) can be made to write or process data under a shop it has no relationship to the payload for. This is a cross-tenant data-integrity/confidentiality issue reachable purely through this gem's public `Registry.process` API, without requiring the app's `api_secret_key`, an access token, or any privileged access — only that the attacker is an app user on some shop capable of receiving a legitimate webhook delivery.

### Likelihood Explanation
Moderate-to-high. Exploitation requires nothing more than: (1) installing the target app on an attacker-controlled shop (which is normally open/unprivileged for public apps), (2) capturing one legitimate webhook delivery (body + `x-shopify-hmac-sha256`), and (3) replaying it against the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No secret material needs to be recovered because the HMAC never covered the header in the first place.

### Recommendation
- Do not treat `Request#shop`, `#topic`, or `#webhook_id` as authenticated identifiers derived from the HMAC check; document this loudly since Shopify's own webhook signing scheme only covers the body.
- Where possible, cross-check `request.shop` against a shop identifier embedded in the (HMAC-covered) JSON body, or require callers to independently correlate the delivery with a known, active session/webhook subscription (e.g., validate `webhook_id` against an ID that was returned when the app itself registered the subscription for that specific shop) before trusting `WebhookMetadata#shop` for tenant routing.
- Consider exposing a stricter `process` variant that rejects processing unless the caller supplies the expected shop and the gem confirms consistency, rather than implicitly trusting header data merely because *some* valid HMAC was presented.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook topic they control the payload shape for (e.g., `app/uninstalled` or any subscribed topic), capturing the delivered `raw_body` and `x-shopify-hmac-sha256` header — both valid per `HmacValidator.validate`.
2. Attacker POSTs to the app's webhook endpoint with the identical `raw_body`/`hmac` headers, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) validates the HMAC successfully (it only checks the body) and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`.
4. Any handler logic that persists or acts on `data.shop` now attributes attacker-controlled data to `victim-shop.myshopify.com`, crossing the tenant boundary.
