### Title
Webhook `shop` identity is read from an unauthenticated header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that this gem validates only covers the raw request body, never the header. This breaks the intended binding `shop_header == shop_authenticated_by_hmac`, letting an attacker who controls one legitimate tenant replay a body they legitimately received (with its valid HMAC) while substituting an arbitrary `shop-domain` header, impersonating any other shop to the host application.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines its signable content as the raw body only: [1](#0-0) 

The `shop` value that the host application is expected to trust for tenant identification is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely outside the HMAC-covered material: [2](#0-1) 

`HmacValidator.validate` only proves that `@raw_body` was signed with the app's secret; it says nothing about which header values accompanied that body: [3](#0-2) [4](#0-3) 

Because a single app-level `api_secret_key` (not a per-shop secret) is used to sign webhooks for every installed shop, any legitimate merchant installer of the app receives genuine `(body, hmac)` pairs signed with that same shared secret. Nothing in this gem prevents that installer from re-delivering their own captured `(body, hmac)` pair to the host application's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain — `HmacValidator.validate` will still return `true`, because it never inspects the header, and `Request#shop` will happily report the victim's domain as if Shopify had asserted it.

This is analogous to the reported bug class: a value that downstream logic treats as authoritative (the WETH-reward-bearing balance in TREC-1) is not covered by the same integrity check that gates the rest of the transaction (the transfer/claim step). Here, the tenant-identifying `shop` field used by the host application to route/attribute the webhook is not covered by the same HMAC check that gates payload authenticity.

### Impact Explanation
If a host application built on this gem uses `request.shop` (as the gem's own public API encourages) to decide which merchant's data record to update/delete/mutate on receipt of a webhook, an attacker with one valid installation of the app can forge webhooks appearing to originate from an arbitrary other shop, since the header is unauthenticated. This is a cross-tenant boundary violation — a High/Critical-class impact per the scope (cross-tenant access) — achieved purely through this gem's exposed `Request#shop` API without needing the app's `client_secret` or any victim credentials; only a legitimate account for the *attacker's own* shop is required to obtain one valid `(body, hmac)` sample.

### Likelihood Explanation
Likelihood is elevated by the fact that: (1) the HMAC secret is shared across all shops using the same app (not per-tenant), so any installer can generate/observe valid signed webhook traffic; (2) the gem's documented `Request#shop` accessor is the standard way host apps are expected to identify the webhook's tenant, making misuse very plausible; and (3) no code path in this gem cross-checks the header-derived `shop` against any value inside the HMAC-covered body (e.g. a `domain` field in the JSON payload).

### Recommendation
Do not treat the `shop-domain` header as trusted tenant identity on its own. Either (a) include the shop domain in the HMAC-signable string so it is cryptographically bound to the signature, or (b) require host applications to cross-validate the header-derived shop against a shop identifier embedded within the verified JSON body before using it for any tenant-scoped operation, and document this requirement prominently next to `Request#shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header — both signed validly with the app's shared `api_secret_key`.
2. Attacker replays this exact body and HMAC header to the host application's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Host application constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and calls `ShopifyAPI::Utils::HmacValidator.validate(request)`; this returns `true` because validation only checks `raw_body` against the HMAC — see [5](#0-4)  and [6](#0-5) .
4. `request.shop` returns `"victim-shop.myshopify.com"` — see [2](#0-1)  — even though the payload/HMAC was never associated with that shop by Shopify, allowing the host app to apply attacker-controlled webhook data to the victim tenant's records.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
