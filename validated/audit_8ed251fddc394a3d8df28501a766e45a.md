### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant/routing identifiers.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by computing `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and comparing it to the `hmac` field with `OpenSSL.secure_compare`. [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw request body, `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`), which are never included in the signable string and are therefore not bound to the HMAC at all: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e. only the body) and then dispatches directly to the registered handler using `request.topic`, `request.shop`, and `request.webhook_id` as trusted values, with no additional binding check between the body and these header fields: [4](#0-3) 

The identity-binding equation this breaks is: **bytes verified (raw body) ≠ bytes acted on (`shop` + `topic` + `webhook_id` headers)**. Since only the body is authenticated, any `(raw_body, hmac)` pair that is valid for one legitimate webhook delivery (e.g. a webhook the attacker's own shop received) remains a valid HMAC pass regardless of which `shop`, `topic`, or `webhook_id` header values accompany it. An attacker who has captured (or replays, e.g. via inspecting their own installed app's traffic) one genuine `(body, hmac)` pair signed by the app's real `api_secret_key` can resend that exact body+hmac to the app's public webhook endpoint while freely substituting the `x-shopify-shop-domain` header to name a different (victim) shop, and/or substituting the `x-shopify-topic` header to a different registered topic (e.g. mandatory topics like `customers/redact`, `shop/redact`, `customers/data_request`, or any tenant-scoped topic such as `app/uninstalled`). `Registry.process` will accept it as authentic and invoke the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` bound to the attacker-chosen shop/topic. [5](#0-4) 

This is a genuine gem-level flaw: the gem's own `Request`/`Registry` API presents `shop` and `topic` to consuming apps as authenticated, HMAC-verified data (that is the entire purpose of `Utils::HmacValidator.validate` gating `process`), but the binding between those fields and the verified bytes does not exist. An app author using this gem as documented has no way to know from the gem's contract that `shop`/`topic` require independent verification.

### Impact Explanation
A handler that trusts `data.shop` to scope tenant data (a very common and expected usage pattern for multi-tenant Shopify apps) can be tricked into applying a webhook payload intended for the attacker's own shop against a victim shop's stored records, achieving cross-tenant action/write without any credentials for the victim shop. Combined with mandatory GDPR topics or lifecycle topics (`customers/redact`, `shop/redact`, `app/uninstalled`), this could let an attacker trigger destructive or state-changing operations (data deletion, marking a shop uninstalled, etc.) against a victim shop's data using only a valid HMAC obtained from their own legitimate webhook traffic. This satisfies the "cross-tenant access" criterion for High/Critical impact.

### Likelihood Explanation
Requires the attacker to possess at least one genuine `(raw_body, hmac)` pair — obtainable simply by having the app installed on their own shop and observing one webhook delivery (no leaked `api_secret_key`, access token, or privileged account needed) — plus the ability to POST arbitrary headers to the app's public webhook endpoint, both of which are available to an unprivileged internet user/merchant. The main constraint is that the replayed body's JSON content must be semantically acceptable to the specific handler logic, so exploitability depends on how permissively individual app handlers interpret `data.body` versus `data.shop`/`data.topic`, but the gem itself provides no barrier.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified surface (e.g., include them, or a canonicalized subset, in `to_signable_string`), or otherwise document/enforce that consumers must independently correlate `shop`/`topic` against the caller-known registration state (e.g. compare against session-scoped expectations) before trusting them, rather than presenting them as implicitly authenticated by `HmacValidator.validate`.

### Proof of Concept
1. Attacker's own app installation legitimately receives a webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: customers/redact`, body `B`, valid `x-shopify-hmac-sha256: H` (computed by Shopify with the real `api_secret_key`).
2. Attacker resends the identical `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", ...})` is constructed; `hmac` still equals `H`, and `to_signable_string` still equals `B`. [6](#0-5) 
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`. [7](#0-6) 
5. The registered `customers/redact` handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, causing the app to act on the victim tenant's data using a signature that was never computed over that shop value. [8](#0-7)
