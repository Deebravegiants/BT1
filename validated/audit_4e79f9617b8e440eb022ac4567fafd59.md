### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) Header Trusted Without HMAC Coverage Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop-domain` header — which the registry uses to attribute the webhook payload to a specific merchant/tenant — is read directly from unauthenticated headers and never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string (the body) and compares it against the `hmac-sha256` header using the app's `api_secret_key`: [2](#0-1) 

Meanwhile `request.shop` is parsed straight from the `shop-domain` header with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) and then hands `request.shop` straight to the handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body || shop || topic || webhook_id)`, i.e., the header claiming *which shop* the payload belongs to should be covered by the same signature that authenticates the payload. Instead the gem only enforces `hmac == HMAC(secret, raw_body)`, leaving `shop` (and `topic`/`webhook-id`/`api-version`) completely unauthenticated. This is precisely the "field acted on but not covered by the HMAC" class of bug: two conceptually-bound values (signed body vs. claimed tenant) are verified independently, and the equality that matters (the shop the signature was generated for == the shop asserted in the header) is never checked.

### Impact Explanation
An app that receives webhooks for many merchants (a normal multi-tenant Shopify app built on this gem) determines *which tenant's data to update* using `WebhookMetadata#shop`, sourced from the unauthenticated header. An attacker who can obtain one genuine, validly-signed webhook body/HMAC pair — trivially achievable by installing the app on their own store (an unprivileged action requiring no `api_secret_key`, access token, or leaked credential) and triggering any webhook event — can replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. Because `process` never checks that the shop header is bound to the signature, the request passes HMAC validation and the handler executes as if the payload came from the victim's store. Depending on what the host app does with `WebhookMetadata#shop` (record attribution, cache invalidation, order/product sync, session lookups) this yields cross-tenant data corruption or disclosure — a High/Critical class impact per the scoring rubric (cross-tenant access).

### Likelihood Explanation
The prerequisite is trivial and matches "unprivileged internet user": creating a free/dev Shopify store, installing the vulnerable app, and capturing one legitimate webhook delivery. No access token, no `api_secret_key`, no privileged account, and no TLS interception are required — the attacker only needs their own tenant's genuine signed payload and network access to the target app's public webhook route, which by design is internet-facing and unauthenticated apart from HMAC.

### Recommendation
Include the tenant/identity-bearing headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the signable material, or otherwise cryptographically bind them to the verified body (e.g., verify a canonical string of `raw_body + shop + topic + webhook_id` against the HMAC) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) to obtain a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed by the app's shared `api_secret_key`.
2. POST that exact `raw_body` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to act on the victim tenant using attacker-supplied payload content.
