## Analysis

NEAR's meta-transaction mechanism (`DelegateAction`, NEP-366) is architecturally similar to EIP-7702 delegated calls: a `SignedTransaction` is submitted by a relaying account (`tx.signer_id`), but it wraps a `DelegateAction` whose own `sender_id`/`public_key`/`nonce` identify the *actual* account whose access key authorizes and is mutated by the inner actions [1](#0-0) . Execution-time validation correctly checks and advances the *delegate's* access-key nonce, not the relayer's, in `validate_delegate_action_key` [2](#0-1) .

However, NEAR's delayed-execution ("spice") protection layer, `PendingTransactionQueue`, which exists specifically to prevent the "transaction invalidated mid-block via nonce bump" and unbounded pending-mutation class of issues described in the report (NEP-611 `P_MAX` bandwidth limiting and mid-flight nonce tracking across uncertified chunks), keys all of its accounting to the **outer transaction's** `signer_id`/`public_key`/`nonce`, not the `DelegateAction`'s `sender_id`/`public_key`/`nonce`:

- `add_chunk_transactions` builds `pending_accounts` (P_MAX count) and `pending_nonces` keyed by `tx.signer_id()`, `tx.public_key()`, `tx.nonce()` — the relayer's identity — for every transaction, including ones that wrap a `Delegate`/`DelegateV2` action [3](#0-2) .
- `check_pending`/`has_contract` similarly key on the outer `tx.transaction.signer_id()` and on `account.contract()` looked up for that outer signer [4](#0-3) , [5](#0-4) .
- Only the *deploy-detection* helper (`is_deploy_like_action`) is aware enough to recurse into `Delegate`/`DelegateV2` inner actions [6](#0-5) ; the account-identity and nonce accounting do not receive equivalent treatment.

This is the direct structural analog of the reported flaw: a protection meant to gate/limit the *delegated* actor's mutating operations (`create_inside_delegated_` flag / `EVMC_DELEGATED`) is instead evaluated against the wrong context (`msg.flags = 0` from `create.hpp`, i.e., the immediate caller rather than the delegated identity). Here, `P_MAX` and pending-nonce tracking are evaluated against the relayer's identity instead of the `DelegateAction.sender_id`/`public_key` that actually owns the access key and receives the state mutation.

### Title
NEP-611 `P_MAX` and pending-nonce protections in `PendingTransactionQueue` are keyed to the relayer, not the `DelegateAction` sender, allowing meta-transactions to bypass bandwidth limits and mid-flight nonce-conflict detection - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
`PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` track per-account pending-mutation counts (`P_MAX`) and per-key pending nonces using the **outer transaction's** `signer_id`/`public_key`/`nonce`. When the transaction wraps a `DelegateAction` (meta-transaction), the actual mutating identity is the delegate's `sender_id`/`public_key`/`nonce`, which is never recorded in `pending_accounts` or `pending_nonces`.

### Finding Description
`add_chunk_transactions` computes `signer_id`, `public_key`, and `nonce` solely from the outer `SignedTransaction`/`Transaction` [3](#0-2) . For an `Action::Delegate`/`Action::DelegateV2`, this is the relayer's account/key — the DelegateAction's own `sender_id`/`public_key`/`nonce` (which is what `validate_delegate_action_key` actually validates and bumps in `runtime/runtime/src/actions.rs`) is not scanned into `chunk_data.accounts` or `chunk_data.nonces`. The only special-case handling for `Delegate`/`DelegateV2` in this file is `is_deploy_like_action`'s recursive scan for deploy detection [6](#0-5) ; there is no equivalent recursion for account-identity/nonce accounting.

Consequently:
1. `has_contract` used by `check_pending`'s `P_MAX` gate (`NEP-611` limit of 4 pending access-key mutations for contract accounts) is derived from the outer signer's account, obtained via `signer_overlay.get_or_load_entry_mut(&state_update, validated_tx.signer_id(), ...)` [7](#0-6) . A contract account intending to be limited to `P_MAX` pending mutations can instead have those mutations delivered as `DelegateAction`s relayed through distinct non-contract accounts, so `has_contract == HasContract::No` and the `P_MAX` gate at `chain/client/src/pending_transaction_queue.rs` lines 504-507 never triggers for that account's real state changes.
2. `pending_nonces` (used by `get_pending_constraints`/`max_nonce` to detect conflicting/duplicate nonces across uncertified chunks — precisely the mechanism meant to address the report's "nonce bumped mid-proposal invalidates other transactions" concern) is never populated for the delegate's `(sender_id, public_key)`. Two `DelegateAction`s signed with the same delegate access key and the same nonce, wrapped by different relayer transactions, can both be admitted into different uncertified pending chunks, since the RPC/chunk-producer admission check (`PendingTxSession::check_pending` / `get_pending_constraints`) has no record of the delegate's pending nonce to reject the second one at admission time [8](#0-7) .

### Impact Explanation
This bypasses two purpose-built anti-abuse mechanisms tied to NEAR's delayed-execution ("spice") architecture:
- The `P_MAX` bandwidth limit intended to bound the number of outstanding, uncertified mutations against contract accounts (NEP-611) can be circumvented by routing mutating actions through `DelegateAction`s relayed by non-contract accounts, allowing unbounded pending state-mutation requests against a contract account before certification.
- The mid-flight nonce-conflict detection can be silently bypassed for delegate-signed keys, letting a relayer (or colluding relayers) admit multiple conflicting `DelegateAction`s with the same nonce into distinct uncertified chunks. Only one will ultimately succeed at execution time in `validate_delegate_action_key` (`ActionErrorKind::DelegateActionInvalidNonce`), but the others occupy chunk space and consume chunk-production capacity despite being predictably invalid — the same "occupies proposal space while providing no useful execution" resource-exhaustion pattern flagged in the original report.

### Likelihood Explanation
Triggering this requires only submitting ordinary, validly-signed transactions and meta-transactions (`SignedDelegateAction`) via RPC — no validator or node compromise is needed. The `spice_pending_transaction_queue_enabled` feature gates this code path (test files show it behind `protocol_feature_spice` / `set_spice_pending_transaction_queue_enabled`), so likelihood is tied to that feature being active on the network.

### Recommendation
When scanning transactions in `add_chunk_transactions` (and equivalently in `PendingTxSession::check_pending`'s `has_contract`/session bookkeeping), recurse into `Action::Delegate`/`Action::DelegateV2` payloads and additionally account for the `DelegateAction`'s `sender_id`, `public_key`, and nonce (including its gas-key nonce_index variant) in `pending_accounts` and `pending_nonces`, mirroring what `is_deploy_like_action` already does for deploy detection. `has_contract` for `P_MAX` purposes should also be evaluated against the delegate's `sender_id` account when the transaction wraps a `DelegateAction`.

### Proof of Concept
1. Deploy a contract to account `victim.near` (making it subject to `P_MAX`).
2. Have `victim.near` sign `P_MAX + N` `DelegateAction`s (each incrementing its own access-key nonce) targeting itself, each wrapped and relayed by a *different* non-contract relayer account (`relayer1.near`, `relayer2.near`, ...).
3. Submit all relayed meta-transactions within the same uncertified window (before the previous ones are certified).
4. Observe that `check_pending` admits all of them because `has_contract` is evaluated against each distinct relayer (non-contract) rather than `victim.near`, exceeding the intended `P_MAX = 4` limit on pending mutations to `victim.near`, contrary to `chain/client/src/pending_transaction_queue.rs` lines 504-507.
5. Separately, submit two `DelegateAction`s signed by the same key with the same nonce via two different relayers within the same uncertified window; both are admitted at the pending-queue layer (since `pending_nonces` never tracked the delegate's nonce), and only fail later at actual execution in `validate_delegate_action_key`, having already consumed chunk space.

fn is_deploy_like_action(action: &Action) -> bool {
    match action {
        Action::DeployContract(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::DeterministicStateInit(_) => true,
        Action::Delegate(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)

        Action::DelegateV2(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => false,
    }

    /// constraints needed by `PendingTxSession::check_pending`. This is called
    /// under the lock and should be fast.
    fn query_pending_state(
        &self,
        signer_id: &AccountId,
        public_key: &PublicKey,
        nonce_index: Option<NonceIndex>,
    ) -> PendingStateSnapshot {

        let access_key_tx_count = pending_account.map(|a| a.access_key_tx_count).unwrap_or(0);
        let deploy_tx_count = pending_account.map(|a| a.deploy_tx_count).unwrap_or(0);

            access_key_tx_count,
            deploy_tx_count,
            paid_from_balance,
