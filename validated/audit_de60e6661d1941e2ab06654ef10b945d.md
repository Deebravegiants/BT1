Confirmed: `Observer` runs a periodic background task (`config_update`, triggered every `CONFIG_UPDATE_INTERVAL`) that downloads fresh config from the backend and swaps it into the shared `Arc<Mutex<Config>>` at `src/brokers/observer.rs:187-205`. Meanwhile, `MasterPlan::run` and `MasterPlan::do_signup` in `src/plans/mod.rs` destructure a **snapshot** of `Config` (including `operator_qr_expiration_time`, `self_serve`, `self_serve_button`) at the top of the loop/function and use that stale copy for the entire signup session, rather than re-reading `orb.config` dynamically at each check.

### Title
Stale `operator_qr_expiration_time` snapshot allows signup authorization with outdated expiration policy - (File: src/plans/mod.rs)

### Summary
`MasterPlan::run` and `MasterPlan::do_signup` copy `operator_qr_expiration_time` (and other signup-authorization-relevant config fields) out of the shared `Arc<Mutex<Config>>` once at the start of the loop/function, instead of dynamically re-reading it from the live config on every check. The backend can update this value at any time via the periodic `config_update` background task, but a signup already in progress will keep using the value that was current when the loop iteration started, mirroring the reported Vault `feeReceiver` pattern of caching a security-relevant parameter instead of dynamically querying its authoritative source.

### Finding Description
`Config` is stored centrally in `Arc<Mutex<Config>>` and refreshed by a background task in `DefaultPlan::config_update` in `src/brokers/observer.rs:187-205`, which downloads the latest backend config and swaps `*config.lock().await = new_config` on a timer (`CONFIG_UPDATE_INTERVAL`).

In `src/plans/mod.rs`, `MasterPlan::run` destructures the config once per outer loop iteration: [1](#0-0) 
This `operator_qr_expiration_time` value is then threaded through `scan_initial_qr_codes`, `idle_wait_for_signup_request`, and `idle_scan_user_qr_code` for the whole idle/scan cycle, and it is used again as a locally captured copy inside `do_signup`: [2](#0-1) 
and used to gate `scan_remaining_qr_codes`'s expiration check: [3](#0-2) 

If the backend shortens `operator_qr_expiration_time` (e.g., because an operator's QR/session was flagged as compromised or the operator's authorization was revoked mid-session), the config-refresh task at `src/brokers/observer.rs:196-202` will update the shared `Config`, but the currently running signup/idle loop keeps evaluating expiration against the old (longer) duration it captured at loop start. This is structurally the same root cause as the reported Vault bug: a security-relevant parameter is snapshotted at "initialization" of a unit of work instead of being dynamically re-queried from the single authoritative, mutable source (`orb.config`) at the point of use.

### Impact Explanation
This allows an operator-QR-authorized session window to remain valid for authorizing new user signups for longer than the backend's current policy intends, because the expiration check uses a stale, more permissive value. Since operator-QR validity gates the ability to enroll a user (identity-binding/signup authorization boundary), a stale, longer expiration window could let a signup proceed under a policy the backend has already tightened/revoked, extending unauthorized signup authorization.

### Likelihood Explanation
Requires that config value change (shortened expiration) occur precisely while a signup/idle loop iteration is already in flight using an old snapshot, and the config-refresh only occurs on a fixed interval (`CONFIG_UPDATE_INTERVAL`) and only while `network_unblocked` is true (`src/brokers/observer.rs:475-478`), so the exploitable window is bounded but non-zero and not attacker-controlled (it depends on normal backend-driven config timing rather than a malicious actor manipulating the value).

### Recommendation
Re-read `operator_qr_expiration_time` (and any other authorization-relevant config fields) from `orb.config.lock().await` at the actual point of the expiration check (e.g., inside `scan_remaining_qr_codes`'s loop body and `idle_scan_user_qr_code`) rather than passing down a value captured once at the start of `run`/`do_signup`, so that backend-driven policy tightening takes effect immediately for in-progress sessions.

### Proof of Concept
1. Backend sets `operator_qr_expiration_time` to a large value; orb enters idle/signup loop and captures this value via the destructuring in `MasterPlan::run` (`src/plans/mod.rs:328-336`).
2. Operator scans QR; `OperatorData.timestamp` is recorded.
3. While the idle/signup loop is still running with the old snapshot, backend reduces `operator_qr_expiration_time` (e.g., due to flagged operator abuse) and the `Observer`'s `config_update` task swaps in the new `Config` (`src/brokers/observer.rs:196-202`).
4. `scan_remaining_qr_codes`/`idle_scan_user_qr_code` still compare `operator_data.timestamp.elapsed()` against the old, larger `operator_qr_expiration_time` captured in step 1, allowing the operator QR-authorized window to remain valid past the point the backend intended to invalidate it.
