### Title
Missing shop-domain validation in `TokenExchange.exchange_token` sends the app's `client_secret` to an unsanitized host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound token-exchange request host directly from the JWT `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling method in the auth layer that also sends `client_secret` over HTTP.

### Finding Description
The gem ships a dedicated `Utils::ShopValidator` module specifically to canonicalize/allow-list a caller-supplied "shop" string before it is used to build a request host, with tests explicitly targeting domain-confusion payloads (userinfo-before-`@`, `myshopify.com.evil.com`, `shop.myshopify.com@evil.com`, look-alike suffixes, etc.): [1](#0-0) [2](#0-1) 

Every method in the auth layer that sends the app's `client_secret` to a shop-derived host calls `Utils::ShopValidator.sanitize!` before constructing the `Session`/`HttpClient`: [3](#0-2) [4](#0-3) [5](#0-4) 

However, `exchange_token` - the token-exchange path used with the session token that comes from the embedded app's client-side JS (App Bridge), i.e. the least trusted input source in the whole library - skips this step entirely. It takes the shop value straight from the JWT payload's `dest` claim and uses it unsanitized to build the `Session`, which `HttpClient` then turns directly into the request host that receives `client_id`/`client_secret`: [6](#0-5) [7](#0-6) 

The `shop` accessor on `JwtPayload` performs no canonicalization beyond stripping a literal `"https://"` prefix once: [8](#0-7) 

`JwtPayload` itself only verifies the JWT signature (`aud`/`exp`/`nbf` claims) - it never validates that `dest` is a well-formed, canonical Shopify-owned domain the way `ShopValidator` does: [9](#0-8) 

The binding that should hold is: `host validated by ShopValidator == host that receives client_id/client_secret`. In `exchange_token`, this equality is broken - the host that receives the app's `client_secret` is whatever raw string is present in the `dest` claim, with none of the domain-confusion protections that the library's own authors built and apply everywhere else this exact same class of request is constructed.

### Impact Explanation
If `dest` can ever carry a value that is not already normalized to a bare `shop.myshopify.com`-style host (e.g., a scheme/userinfo/path variant, or any value the library maintainers considered dangerous enough to defend against with `ShopValidator`, as proven by that module's own test suite), the built `HttpClient` will POST the app's `client_id` and `client_secret` to that attacker-influenced host. This is an SSRF carrying the app's own OAuth credentials (`client_secret`), which per the specified impact tiers is a High severity issue (SSRF with the app's credentials / credential leakage). This is exactly the class of risk `ShopValidator` exists to close, and the fact that three sibling methods explicitly close it while `exchange_token` does not represents a genuine, unexplained gap in defense-in-depth for the most externally-influenced entry point (client-supplied session token) in the library.

### Likelihood Explanation
The `dest` claim originates from Shopify-issued session tokens, so under the intended/expected flow, the claim is already a canonical shop domain and the code path is safe in the common case. This finding's severity therefore hinges on the fact that this is an inconsistency the maintainers evidently do not consider safe to skip elsewhere (given they wrote and unit-tested `ShopValidator` specifically for this purpose and apply it to every other `client_secret`-sending call site, including the sibling `migrate_to_expiring_token` in the very same file). Because I cannot fully verify from this repository whether Shopify's session-token issuance path can ever produce a non-canonical `dest` value (that logic lives outside this gem), likelihood should be treated as uncertain/moderate rather than confirmed-high - but the missing guard is a concrete, provable code defect regardless.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session`/`Clients::HttpClient`, consistent with `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
Not independently reproducible from this repository alone, since it depends on whether Shopify's session-token issuer can ever emit a `dest` claim value that `ShopValidator` would reject. What is concretely demonstrable in-repo is the code inconsistency itself:
1. `client_credentials.rb:25`, `refresh_token.rb:24`, and `token_exchange.rb:103` (`migrate_to_expiring_token`) all call `Utils::ShopValidator.sanitize!(shop)` before building the outbound `client_secret`-carrying request.
2. `token_exchange.rb:41` (`exchange_token`) uses `jwt_payload.shop` directly with no equivalent call, then passes it straight into `Session.new(shop: dest_shop)` → `Clients::HttpClient.new(session: shop_session, ...)`, whose `@base_uri` becomes `"https://#{session.shop}"` verbatim [7](#0-6) , the exact host that then receives `client_id`/`client_secret` in the POST body.
