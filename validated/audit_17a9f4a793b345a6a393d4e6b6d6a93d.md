### Title
Order creator can grief solvers via malicious `order.output.call` / `order.predispatch.call` targets executed through `CallDispatcher` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2` lets the order creator embed arbitrary calldata (`order.output.call` for postdispatch, `order.predispatch.call` for predispatch) that gets executed via `ICallDispatcher(dispatcher).dispatch(...)` inside the solver's `fillOrder` transaction. Because `CallDispatcher.dispatch` reverts the whole batch on any failed call (`CallFailed`) and forwards essentially all remaining gas to the user-controlled target, an order creator can point `Call.to` at a contract engineered to consume excessive gas or to revert unconditionally, causing the solver's `fillOrder` transaction to fail or become extremely expensive after the solver has already committed capital/output tokens to the fill.

### Finding Description
`_execute` in [1](#0-0)  unconditionally dispatches `order.output.call` — fully attacker (order-creator) supplied calldata — through the shared `CallDispatcher` as soon as the solver has delivered output tokens (cross-chain path, per the docs: "Cross-chain: Calldata executes immediately after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain").

`CallDispatcher.dispatch` at [2](#0-1)  performs a low-level `.call` to each attacker-specified `to` address and `revert CallFailed(to, result)` if any call in the batch fails — there is no gas cap or try/catch isolation per call. Similarly, `predispatch.call` is dispatched in `IntentGatewayV2._fillOrder`/`placeOrder` flows shown in [3](#0-2)  and the Tron variant [4](#0-3) .

Because the `order` (including `output.call`/`predispatch.call`) is signed/created entirely by the user at order-placement time, a malicious user can set the call target to a contract that:
- burns all forwarded gas (e.g., an infinite loop or gas-bomb pattern) causing an out-of-gas revert deep in the solver's transaction, or
- unconditionally reverts, tripping `CallFailed` and reverting the entire `fillOrder` call.

For the cross-chain path, this occurs **after** the solver has already transferred output tokens to the beneficiary (per the documented execution order), meaning the revert of the whole transaction rolls back that transfer too, but the solver still burns all gas spent on ERC20 transfers, DEX interactions, and the failed calldata before the revert consumes their gas budget. On chains/situations where a solver batches this fill with other actions or has to re-fill after a failed attempt (retry due to `CallFailed`), each solver attempting to fill can be independently griefed, since the malicious order remains fillable (it is never consumed since the transaction reverts) and continues to bait solvers into wasting gas.

### Impact Explanation
This is directly analogous to the reported Rubicon Gladius issue: a user-controlled contract reference (`additionalValidationContract` there, `order.output.call`/`predispatch.call` target here) is invoked unconditionally inside the filler/solver's transaction with no gas limit or isolation, letting the order creator grief the filler with wasted gas, and — because `CallDispatcher.dispatch` reverts the entire batch on failure — can cause the solver's whole `fillOrder` transaction (including already-executed output token transfers to the beneficiary) to revert, wasting all gas spent up to that point. Since orders remain re-fillable and any solver who attempts to service the order suffers, this is a repeatable griefing vector against the solver/filler population, discouraging order servicing (a liveness/funds-loss-by-gas impact), matching a Medium-severity classification consistent with the original report.

### Likelihood Explanation
Likelihood is high for any order that carries non-empty `output.call`/`predispatch.call`: no privileged validation or allow-list restricts what `Call.to`/`Call.data` an order creator may specify (the only check is that the target has code — `NotContract` — not that it's benign or has capped gas). Any solver that chooses to service orders containing calldata is exposed each time it fills such an order, since the calldata executes as part of `fillOrder`/predispatch in the same transaction as the solver's action.

### Recommendation
- Cap the gas forwarded to each target call in `CallDispatcher.dispatch` (e.g., use a fixed gas stipend or a maximum percentage of remaining gas) so a single malicious call cannot exhaust an unbounded amount of the solver's gas.
- Consider isolating call failures per-call (try/catch) rather than reverting the entire dispatch batch, or explicitly documenting/warning solvers to simulate `order.output.call`/`predispatch.call` execution before committing to a fill, and allow solvers to price in / reject orders whose calldata targets are unverified/unknown contracts.
- Optionally allow solvers to specify a maximum gas budget for calldata execution as part of `FillOptions`, reverting early (with a bounded loss) if the calldata attempts to exceed it, rather than letting it consume the whole transaction's gas.

### Proof of Concept
1. Order creator calls `placeOrder` with `order.output.call` encoding a single `Call{ to: GasBomb, value: 0, data: "" }`, where `GasBomb` is a contract whose fallback function contains an unbounded loop (or one that always `revert()`s).
2. A solver observes the order, provides the required output tokens, and calls `fillOrder(order, options)` on the destination chain.
3. During execution, `_execute` (evm/src/apps/intentsv2/IntentsBase.sol:498-503) calls `ICallDispatcher(dispatcher).dispatch(order.output.call)` — this forwards essentially all remaining gas to `GasBomb`.
4. `GasBomb`'s fallback either burns all forwarded gas (causing an out-of-gas revert propagating up through `CallDispatcher.dispatch` and `fillOrder`) or reverts, tripping `CallDispatcher`'s `CallFailed` revert (evm/src/utils/CallDispatcher.sol:59-60).
5. The solver's entire `fillOrder` transaction reverts, having already spent gas on token transfers/DEX interactions and the reverted calldata execution — the solver's gas is wasted and the order remains open to grief the next solver who attempts the fill.

Note: I was unable to find any gas-limit or per-call isolation logic protecting `CallDispatcher.dispatch` or `_execute`/`_fillOrder` calldata execution paths in the indexed portions of the codebase; if such protections exist elsewhere (e.g., in `FillOptions` gas parameters not fully indexed), a Devin session with full repo access should verify this before treating the PoC as conclusive.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
