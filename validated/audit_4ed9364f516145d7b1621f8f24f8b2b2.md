### Title
Missing Sender Authentication in `orb-relay-client` `RequestState` Handler Causes Cross-Session Signup State Disclosure - ([File: orb-relay-client/src/client.rs])

### Summary
The relay client's `PollerAgent::main_loop` handles incoming relay messages and, for every message type except `self_serve::app::v1::RequestState`, verifies the sender against the expected peer (`src.id != self.config.dst_id`) before processing it. The `RequestState` branch skips this check entirely and unconditionally replays `self.last_message` to whoever sent the request. This mirrors the root cause in the external report: a privileged/state-affecting operation is performed without authenticating that the caller is the legitimate counterparty for that session.

### Finding Description
In `orb-relay-client/src/client.rs`, the message-handling `select!` arm matches on incoming `RelayPayload { src, dst, seq, payload }` and does: [1](#0-0) 

```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}: {payload:?}", src.id);
} else {
    self.handle_message(...).await?;
}
```

Every other inbound message type is rejected unless `src.id == self.config.dst_id` (the expected counterparty for this signup session, e.g. the specific app instance tied to a given `session_id`/`orb_relay_app_id`). The `RequestState` branch, however, is checked and answered *before* that authentication gate — the sender's identity (`src.id`) is never compared to `self.config.dst_id`. Any entity able to deliver a message to the orb's relay channel that decodes as `self_serve::app::v1::RequestState` will cause the orb to immediately re-send its `last_message` — the most recent state message the orb sent on this channel (e.g. `AnnounceOrbId`, `CaptureStarted`, `CaptureTriggerTimeout`, `SignupEnded` with `failure_feedback`, per `src/plans/mod.rs`) — without any verification that the requester is the actual app the orb is currently paired with for that signup session. [2](#0-1) [3](#0-2) 

This is structurally the same class of bug as the referenced report: a state-affecting/state-disclosing entry point (`validateUserOp`/here, the `RequestState` handler) fails to authenticate the caller even though an authentication check pattern already exists and is applied to sibling code paths in the very same function.

### Impact Explanation
Because the reply path bypasses the `src.id == dst_id` check that binds a relay session to a specific app instance, an unauthenticated or mismatched peer able to reach the orb's relay message stream can obtain the orb's last self-serve signup state message (including signup success/failure and `failure_feedback` content) intended only for the paired app of that specific signup session. This is a cross-signup/cross-session state disclosure of signup-status data, matching the "cross-signup state bleed" impact category. It does not require any hardware or operator privilege — it is reachable by any relay-connected peer sending a crafted `RequestState` payload.

### Likelihood Explanation
The vulnerable branch is unconditionally reachable on every iteration of `main_loop` for the orb-side relay client used whenever `self_serve` mode is enabled (which is the entire self-serve signup flow). No special timing or race condition is needed — a single `RequestState` payload triggers the unauthenticated reply. The bug is deterministic and does not depend on cryptographic breaks. The main uncertainty (not verifiable from `orb-core` alone) is how strictly the relay backend server scopes/authorizes delivery of messages to a given orb's queue by session/token; if the relay server enforces strict 1:1 session routing, actual exploitability depends on that external service's behavior, which is out of scope for this repo. Within the client code itself, however, the authentication check that protects all other message types is clearly and deliberately absent for `RequestState`.

### Recommendation
Move (or duplicate) the `src.id != self.config.dst_id` authentication check ahead of the `RequestState::matches` branch so that a `RequestState` request is only honored when it originates from the expected paired entity (`self.config.dst_id`) for the current session:

```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. An orb connects to the relay as `Mode::Orb` with `src_id = orb_id`, `dst_id = session_id` (the app's session-specific relay id), matching `Client::new_as_orb` in `orb-relay-client/src/client.rs:146-148`.
2. The orb sends and caches state messages (`AnnounceOrbId`, `CaptureStarted`, `SignupEnded`, etc.) via `send`/`send_blocking`, each stored as `self.last_message` at `orb-relay-client/src/client.rs:499`.
3. Any relay peer capable of delivering a `RelayPayload` to this orb's connection with `payload` decodable as `self_serve::app::v1::RequestState` (regardless of the `src` field/entity id in that payload) causes the orb, at `orb-relay-client/src/client.rs:436-440`, to immediately resend `self.last_message` to the sender — without ever checking that `src.id == self.config.dst_id` — leaking the orb's last signup-state message to that unverified sender.
