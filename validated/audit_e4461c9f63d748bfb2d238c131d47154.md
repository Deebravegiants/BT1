### Title
Shared Emporium action balance lets any caller sweep prior transactions' residual token balance into their own UTXO - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` computes the amount to hand back to the caller as `balanceChange = (balancesAfter - balancesBefore) - deltaAmountChanges[i]` (for negative `deltaAmountChanges[i]`), where `balancesBefore`/`balancesAfter` are just the raw ERC20/ETH balance of the shared, stateless Emporium contract measured around an attacker-crafted set of arbitrary calls (`stack.ops`). Because the contract's balance carries over between unrelated users' transactions in the same block (or even across blocks) and the ops are fully attacker controlled, any balance stranded in the action by a previous transaction can be swept out and forwarded to the attacker's own output UTXO via `handleOut`, with nothing in the code distinguishing "legitimate proceeds of my own deposit" from "someone else's leftover balance."

### Finding Description
The invariant that should hold is: *tokens leaving the action in transaction T == -deltaAmountChanges Hinkal sent it in transaction T* (i.e., only the funds Hinkal itself moved into the action for the current call, plus whatever the current call's own operations legitimately produce from those funds, should be extractable). This equality is not enforced.

Trace of the code path:
1. `Hinkal.transact` -> `_externalTransact` ( [1](#0-0) ) transfers `-deltaAmountChanges[i]` from Hinkal into the Emporium action **before** calling `runAction`.
2. `EmporiumUpgradeable.runAction` snapshots `balancesBefore` of the action (which already includes any dust left over from a prior transaction plus the freshly transferred amount), executes attacker-supplied `EmporiumStack.ops` — arbitrary `endpoint.call(callData)` or wallet-invoked calls, fully decoded from attacker-controlled `externalActionMetadata` ( [2](#0-1) ), then snapshots `balancesAfter`.
3. It computes `balanceChange = balancesAfter - balancesBefore`, and if `deltaAmountChanges[i] < 0`, adds back `-deltaAmountChanges[i]` ( [3](#0-2) ). The code's own comment acknowledges pre-existing balances can exist ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") but only guards the *negative* direction (revert if ops draw down more than deposited). It does nothing to prevent the *positive* direction — i.e., silently sweeping out someone else's stranded/dust balance together with legitimate proceeds.
4. Any positive `balanceChange` is handed to `handleOut`, which unconditionally transfers `balanceChange` to `msg.sender` (the Hinkal contract) and returns a `UTXO` of that full amount ( [4](#0-3) ).
5. Back in `Hinkal.transact`, that returned `utxoSet` is matched against the attacker's own `circomData.amountChanges`/`slippageValues` for their own private output note ( [5](#0-4) ). Since the attacker fully controls their own `circomData` (their own proof, their own UTXO commitment, their own slippage bounds), they simply set these fields to accept whatever larger balance the sweep produces — there is no cross-transaction check tying the amount output for a token strictly to that transaction's own deposit or genuine swap proceeds.

Root cause: the Emporium action is a single shared, stateful-by-balance contract used across all users' transactions, but `runAction`'s accounting treats "any positive delta beyond what I sent this tx" as legitimate output belonging to the *current* caller, with no bookkeeping of which balances belong to which prior in-flight transaction. Because `stack.ops` allow arbitrary calldata to arbitrary endpoints (e.g., a token `transfer`, or a swap router call sized to sweep the contract's entire balance rather than only the freshly deposited amount, or an `approve`+`transferFrom` pattern via a malicious/attacker-deployed router), the attacker can specifically target and pull out balance that was never theirs.

None of the listed guards stop this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the balance/slippage `require`s in `Hinkal.transact` only validate that the attacker's own proof and declared UTXO amounts are internally consistent with the balance change actually observed on Hinkal's own address — they never validate the *provenance* of the tokens that left the action contract.

### Impact Explanation
This is direct theft of funds that were parked in a shared external-action contract — dust or stranded balances that belong to the protocol/other users' in-flight transactions — captured by an unprivileged attacker as their own private UTXO. This matches Critical: direct theft of shielded or in-flight user funds. It is repeatable any time residual balance exists in the Emporium action contract (e.g., left by a prior transaction's imprecise swap output, rounding, or a legitimately failed/partial refund that wasn't fully swept in the same call).

### Likelihood Explanation
Preconditions: some non-zero ERC20/ETH balance of a token must be sitting in the `EmporiumUpgradeable` contract at the start of the attacker's transaction (e.g., left by a prior same-block or prior-block transaction that didn't fully drain its own change, or dust from rounding in a router swap). Given this is a shared, publicly-callable action contract processing arbitrary externally-crafted operations from many independent users, such residues are plausible over time. The attacker's cost is only their own valid deposit/proof generation for a normal Emporium transaction; the exploit path (arbitrary `op.endpoint.call(op.callData)`) is a core, intended feature of Emporium, making it trivial to author calls that pull the contract's *entire* current balance of a token rather than only the freshly-deposited amount.

### Recommendation
Track and constrain Emporium's per-token accounting so that `handleOut` can only ever release, at most, the amount attributable to the *current* transaction: e.g., require the ops to operate only on the amount actually transferred in this call (pass exact amounts to ops instead of letting them read `balanceOf`), or snapshot/require that `balancesBefore` for each token equals zero (or a value provably owned by no pending transaction) before allowing a sweep, or maintain an explicit on-chain ledger of "amount owed back to Hinkal for this call" that is enforced independently of the contract's raw token balance.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (registered as external action), a mock ERC20 `OUT` token, and a malicious/benign router endpoint.
2. Simulate residual balance: directly `deal`/`transfer` `OUT` tokens to the `EmporiumUpgradeable` contract address to represent dust left by a prior transaction (or execute a first legitimate Emporium transaction whose ops intentionally leave `OUT` tokens un-swept in the contract).
3. As an unprivileged attacker (different EOA, no relation to whoever caused the dust), submit a normal `Hinkal.transact` call with `externalActionId` pointing at Emporium, `deltaAmountChanges` reflecting a small legitimate deposit of a different input token, and `EmporiumStack.ops` crafted to call `OUT.transfer` (or a swap router) that moves the *entire* current `OUT` balance of the Emporium contract (dust + any legitimate proceeds) out via `handleOut`.
4. Assert: `utxoOut.amount` returned by `runAction` (and correspondingly the attacker's own private output UTXO amount created in `Hinkal.transact`) equals `dust_from_prior_tx + legitimate_proceeds`, i.e., strictly greater than `-deltaAmountChanges[OUT_index]` sent to the action this transaction — violating the invariant `tokens leaving action == -deltaAmountChanges sent it this tx`.
5. Assert the attacker's shielded balance for `OUT` increases by the dust amount that was never part of their own deposit or `amountChanges`.
