### Title
`EvmHost.withdraw()` can drain relayer fees escrowed for pending/undelivered requests, commingled with protocol revenue in the same `feeToken` balance - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` holds a single ERC-20 `feeToken` balance that mixes two economically distinct pools: (1) protocol revenue intended for governance withdrawal, and (2) relayer fees escrowed per-request in `_requestCommitments[commitment].fee` (`FeeMetadata`), which are owed either to the relayer that delivers the message or refunded to the `payer` on timeout. `withdraw()` has no accounting that distinguishes these pools — it blindly transfers an arbitrary caller-supplied amount of any token to any beneficiary.

### Finding Description
`EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` collect `post.fee`/`get.fee` in `feeToken` and store it as `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})`, an escrow-style entry expected to be paid out on delivery (`dispatchIncoming`, which does `IERC20(feeToken()).safeTransfer(relayer, fee)`) or refunded on timeout (`dispatchTimeOut`, `safeTransfer(meta.sender, meta.fee)`). [1](#0-0) [2](#0-1) [3](#0-2) 

These escrowed fees sit as raw ERC-20 balance in the same contract, indistinguishable on-chain from accumulated protocol revenue. `withdraw()`, gated only by `restrict(_hostParams.hostManager)`, transfers `params.amount` of `params.token` to `params.beneficiary` with no check against total outstanding `_requestCommitments` liabilities: [4](#0-3) 

The withdrawal is triggered end-to-end from Hyperbridge governance via `pallet-host-executive::withdraw`, which lets `HostExecutiveOrigin` supply an arbitrary `WithdrawalParams{beneficiary_address, amount, token}` with no on-chain cross-check against the destination chain's actual unclaimed relayer-fee balance before dispatching: [5](#0-4) 

This is the exact commingling pattern from the reference report: Compound's `claimToTreasury(COMP)` cannot distinguish "reserve" COMP from "reward" COMP because both live in the same underlying balance; here, `EvmHost.withdraw()` cannot distinguish "protocol revenue" `feeToken` from "escrowed-but-undelivered relayer fee / timeout-refund" `feeToken`, because both live in the same ERC-20 balance with no separate liability accounting (no `totalEscrowedFees` counter, no per-token reserved-amount tracking).

### Impact Explanation
If governance (intentionally, via a misconfigured `amount`, or due to a compromised/careless `HostExecutiveOrigin`/relayer key that submits the `Withdraw` action through `HostManager.onAccept`) withdraws more `feeToken` than the true "unencumbered" protocol revenue, it drains funds that are contractually owed to (a) relayers who have already delivered messages but not yet been paid (payment happens lazily at `dispatchIncoming`/`dispatchTimeOut` time, not at delivery-proof-accumulation time), and (b) payers of requests that will time out and expect a refund. Once drained, `dispatchIncoming`/`dispatchTimeOut`'s `safeTransfer` calls will fail for insufficient balance, permanently freezing relayer compensation and payer refunds for any request whose fee was part of the drained balance — a concrete freezing-of-funds condition for the ISMP fee-refund/relayer-reward accounting path reachable from any user or relayer who dispatched/is owed a message fee.

### Likelihood Explanation
`withdraw()` is only reachable via governance (`hostManager` restriction), so a purely external attacker cannot trigger it directly. However, the contract itself provides no invariant enforcement (no on-chain check that `amount <= balance - sum(outstanding FeeMetadata.fee)`), so any governance action that withdraws the full or near-full `feeToken` balance — which is the natural, expected "sweep protocol revenue" operation an operator would perform, exactly analogous to Morpho's `claimToTreasury` — will unavoidably also consume escrowed relayer fees whenever there are pending, undelivered POST/GET requests with non-zero fees at that moment. This makes the bug latent and easy to trigger unintentionally during routine treasury operations, not merely a "malicious governance" scenario, since normal governance has no way to compute the safe withdrawable amount from on-chain state alone.

### Recommendation
Track total outstanding escrowed relayer fees (sum of `_requestCommitments[*].fee` for pending requests) in a running counter incremented on `dispatch()`/`fundRequest()` and decremented on `dispatchIncoming()`/`dispatchTimeOut()`. Have `withdraw()` (or the `hostManager`) enforce `amount <= IERC20(feeToken).balanceOf(address(this)) - outstandingEscrowedFees` when `token == feeToken()`, so cross-chain governance can never withdraw funds still owed to relayers or refundable to payers.

### Proof of Concept
1. Contract A on chain X dispatches a `DispatchPost` via `EvmHost.dispatch()` with `post.fee = 100 feeToken`, `post.payer = alice`. `_requestCommitments[commitment] = FeeMetadata(alice, 100)`; the 100 `feeToken` now sits in `EvmHost`'s balance. [6](#0-5) 
2. Before the request is delivered or times out, Hyperbridge governance calls `pallet-host-executive::withdraw(state_machine, WithdrawalParams{amount: <full feeToken balance>, ...})`, dispatching a governance POST to `HostManager` on chain X. [7](#0-6) 
3. `HostManager.onAccept` decodes the `Withdraw` action and calls `IHostManager(_params.host).withdraw(withdrawParams)`. [8](#0-7) 
4. `EvmHost.withdraw()` transfers the full balance — including alice's 100 `feeToken` escrow — to the treasury beneficiary, with no revert or check. [9](#0-8) 
5. When the request is later delivered, `dispatchIncoming`'s `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts (insufficient balance) or, if it times out, `dispatchTimeOut`'s refund to `alice` reverts — the relayer's reward or alice's refund is permanently unobtainable for that commitment.     function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

            dest: post.dest,
