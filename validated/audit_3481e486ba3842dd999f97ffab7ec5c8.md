## Analysis Result

The reported bug class—using a manipulable AMM spot price for a security‑critical calculation instead of a TWAP—has a direct analog in `EvmHost.sol`'s native-fee dispatch path, which performs an on-chain Uniswap V2 spot-price swap at execution time with no TWAP or manipulation guard.

### Title
Native-fee dispatch relies on unprotected Uniswap V2 spot price, enabling sandwich-extraction of relayer/protocol fees - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert native token to `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, executed synchronously inside the same transaction the unprivileged caller submits. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swapETHForExactTokens` prices the required ETH input against the Uniswap V2 pool's *current reserves* — the AMM equivalent of `slot0` in the referenced report — with no TWAP, oracle cross-check, or deviation guard. The off-chain `quote()`/`HyperApp.quote()` helper used to size `msg.value` calls `getAmountsIn` against the same unprotected reserves: [4](#0-3) 

The project's own documentation explicitly acknowledges that this `getAmountsIn`-based quote is "vulnerable to sandwich attacks" and should only be used off-chain: [5](#0-4) 

However, the *actual on-chain execution* in `dispatch()`/`fundRequest()` still performs the swap against the live pool at call time — the documented risk is not merely an off-chain estimation quirk, it is baked into the protocol's own native-fee payment mechanism. Because reserves can be moved atomically within the same block (flash-loan-funded swap, or classic front-run/back-run sandwich around the victim's dispatch transaction), an attacker can:
1. Front-run the victim's `dispatch{value: X}(...)` call by swapping WETH→feeToken, pushing the feeToken price up.
2. The victim's `swapETHForExactTokens(post.fee, ...)` then consumes more of `msg.value` than the fair-value quote assumed (or reverts if `msg.value` was tightly sized off the pre-attack quote).
3. The attacker back-runs by swapping feeToken→WETH, extracting the spread the victim's swap paid into the pool, capturing value that should have gone to the protocol/relayer fee accounting.

This is directly reachable by any unprivileged party dispatching a message and paying in native token — exactly the "unprivileged message dispatcher" class of caller this codebase's analog rules require.

### Impact Explanation
Value paid by message dispatchers for relayer/protocol fees can be siphoned by MEV sandwich extraction rather than reaching the intended fee recipients, and/or legitimate dispatch calls can revert (denial of dispatch) when reserves are manipulated beyond the `msg.value` cap the caller pre-computed off `quote()`. This is a fee/economic-accounting exploit reachable from a single transaction against `EvmHost.dispatch`/`fundRequest`.

### Likelihood Explanation
High for any Uniswap V2 pool with shallow liquidity (many chains' `feeToken`/WETH pools are thin), since sandwiching a public dispatch transaction requires no privileged access — just mempool visibility and capital for one flash swap. The project's own docs already flag `getAmountsIn` sandwich risk for the *quoting* path, confirming the pricing primitive is known to be unprotected; the same unprotected primitive is used for the *on-chain swap execution*, not just estimation.

### Recommendation
Do not perform the ETH→feeToken swap against live V2 reserves inside `dispatch()`/`fundRequest()`. Either: (a) require callers to pay the exact `feeToken` amount directly (already supported as the else-branch) and deprecate/remove the native-swap convenience path, or (b) if the native-swap convenience must be kept, price it via a TWAP-based oracle or add an explicit maximum-slippage/deviation check against a trusted reference price before executing `swapETHForExactTokens`, and refund any unused native token safely.

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch{value: X}(DispatchPost{fee: F, ...})` transaction in the mempool, where `X` was computed off `HyperApp.quote()`/`getAmountsIn` shortly before submission.
2. Attacker submits a front-run transaction swapping a large amount of WETH for `feeToken` on the same Uniswap V2 pool referenced by `_hostParams.uniswapV2`, moving the pool price so that more WETH is now required to obtain `F` units of `feeToken`.
3. Victim's `dispatch()` executes `swapETHForExactTokens(F, [WETH, feeToken], address(this), block.timestamp)` at the now-worse price — either it reverts (if `X` was insufficient, causing dispatch failure/DoS) or it consumes ETH at the manipulated rate, pushing value into the pool.
4. Attacker back-runs by swapping `feeToken` back to WETH, capturing the price impact/spread created by the victim's forced swap as profit, extracted from the value the victim intended solely for protocol/relayer fees.
