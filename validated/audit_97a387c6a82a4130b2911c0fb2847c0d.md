### Title
Webhook HMAC only signs the raw body, letting an attacker replay their own shop's signed webhook with forged `shop-domain`/`topic` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the body bytes but never binds them to the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. An attacker who has legitimately received one HMAC-signed webhook for their own shop (all installs of an app share the same `api_secret_key`) can replay that exact body to the same endpoint with a different `x-shopify-shop-domain`/`x-shopify-topic` header, and `Registry.process` will accept it as authentic for the forged identity.

### Finding Description
The invariant that should hold is:
`HmacValidator.validate(request) == true` implies `request.shop`, `request.topic`, `request.webhook_id` are values Shopify actually associated with `request.hmac`.

In reality, only:
```
to_signable_string == @raw_body
``` [1](#0-0) 

is fed into `compute_signature`/`OpenSSL.secure_compare` inside `HmacValidator.validate_signature`: [2](#0-1) 

`initialize` only checks that the `topic`, `hmac-sha256`, and `shop-domain` headers *exist* (via `headers.key?`), never that they are well-formed or that they match anything cryptographically bound to the body: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.parsed_body` (all read from unsigned headers/body) to dispatch to the app's handler: [4](#0-3) 

Exploit flow: the attacker creates their own development shop, installs the target app, and lets Shopify legitimately deliver a webhook (e.g. `orders/create`) to the attacker's own endpoint. Because `api_secret_key` is the same client secret for every shop that installs a given app, this webhook's HMAC is computed with a secret the attacker never needs to know or leak — Shopify computes and sends it for them. The attacker then re-POSTs the identical raw body to the victim app's real webhook URL, substituting `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: shop/redact` (or any other topic/shop combination). `HmacValidator.validate` recomputes the HMAC over the unchanged `@raw_body` and it matches, so `Registry.process` treats the forged headers as authenticated and calls `handler.handle` with `shop: request.shop` (the forged victim domain) and `topic: request.topic` (a forged topic, potentially a privileged/mandatory-compliance topic like `customers/redact`).

No existing guard prevents this: `HmacValidator.validate` only checks body/secret integrity, `ShopValidator`/`Context` are not invoked for webhooks, and there is no comparison anywhere in this path between the header values and any signed content.

### Impact Explanation
This lets an unprivileged attacker cause the app to process data or trigger compliance/administrative logic under an arbitrary victim shop's identity, using only a body signed for the attacker's own shop. Since `request.shop` flows directly into `WebhookMetadata.new(shop: request.shop, ...)` and is what most app handlers use to select the tenant record to act on, this is a cross-tenant authentication bypass: the app believes it received an authentic message from `victim-shop.myshopify.com` when it did not. This is repeatable against arbitrary victim shop domains from a single captured (own-shop) signed payload, matching the Critical "authentication bypass — a forged request accepted as authentic" category.

### Likelihood Explanation
Preconditions are minimal and match the documented attacker capability set exactly: attacker installs the target app on their own free development shop, waits for/triggers one real webhook delivery, and replays the raw body with edited headers to the app's public webhook endpoint. No secret material, session, or victim interaction is required, and the attack is trivially repeatable for any topic/shop combination since headers are never checked against the signature.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the body before verification (e.g., construct the signable value as a canonicalized concatenation of body + these headers), so `HmacValidator.validate` fails whenever any of these values are altered relative to what Shopify actually signed.

### Proof of Concept
```ruby
# test/webhooks/request_forgery_test.rb
require "test_helper"

class WebhookForgeryTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @raw_body = '{"id":1,"note":"legit for attacker-shop"}'
    @hmac = Base64.encode64(
      OpenSSL::HMAC.digest("sha256", "secret", @raw_body)
    ).strip
  end

  def test_same_signature_accepted_for_different_shop_and_topic
    headers_attacker = {
      "x-shopify-hmac-sha256" => @hmac,
      "x-shopify-topic" => "orders/create",
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-webhook-id" => "1",
      "x-shopify-api-version" => "2023-10",
    }
    headers_victim = headers_attacker.merge(
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      "x-shopify-topic" => "customers/redact",
    )

    req_a = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_attacker)
    req_v = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_victim)

    assert ShopifyAPI::Utils::HmacValidator.validate(req_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(req_v) # same signature, different shop/topic
    refute_equal req_a.shop, req_v.shop
    refute_equal req_a.topic, req_v.topic
  end
end
```
Both requests pass `HmacValidator.validate` with the identical HMAC, while `shop` and `topic` differ — proving the signature does not bind those values, and `Registry.process` would dispatch the forged webhook to the victim shop's handler.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
