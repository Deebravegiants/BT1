Found a concrete analog: `convert_to_balance` in `pallet-hyper-fungible-token`, where the denominator (a power-of-ten scale factor derived from `erc_decimals - local_decimals`) can exceed the numerator (the incoming ERC20 amount), causing integer division to floor to zero — silently swallowing legitimate cross-chain token transfers on the receiving side.

### Title
Incoming HyperFungibleToken transfers can be floored to zero when `erc_decimals > local_decimals` and the transferred amount is small, silently burning value in transit - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` divides the incoming ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` with no floor/minimum check. When the scaling factor (denominator) is larger than the transferred amount (numerator), the division truncates to `0`. `on_accept` in `module.rs` then proceeds to mint/transfer `0` to the beneficiary and emits success events, while the source chain has already escrowed/burned the sender's non-zero tokens.

### Finding Description
`convert_to_balance` computes:
```rust
let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
``` [1](#0-0) 

This is invoked unconditionally in `on_accept`, the ISMP module handler that is reached whenever a `PostRequest` arrives from a registered peer contract (an unprivileged, relayer-delivered cross-chain message path): [2](#0-1) 

If `erc_decimals` (the sending chain's ERC20 decimals, e.g. 18) is greater than `local_decimals` (the receiving asset's decimals, e.g. 6 or even 0 for some configurations), the divisor is `10^(erc_decimals - local_decimals)`. Any inbound `amount` (attacker/relayer supplied, encoded in the `Message` body from the `BridgeToken`/`HyperFungibleToken` EVM contract) smaller than this divisor floors to `0` in integer division — exactly the denominator > numerator bug class from the referenced report. The handler does not reject a zero-converted amount; it proceeds to call `mint_into`/`transfer` with `amount = 0` and still emits a success path, per the mint/transfer branch immediately following the conversion: [3](#0-2) 

Meanwhile, on the EVM sending side (`send()`), the sender's tokens have already been irrevocably burned/escrowed before dispatch: [4](#0-3) 

### Impact Explanation
This is a fund-freezing/loss bug reachable by any user sending a small cross-chain transfer through the token bridge: source-side tokens are burned/escrowed, but the destination-side credit truncates to zero, permanently losing the transferred value with no revert and no way to recover (the transfer is recorded as delivered/successful). This matches the "unbacked mint/burn accounting break" category for a token bridge.

### Likelihood Explanation
Likelihood depends on decimal configuration: it requires an asset pair where `erc_decimals > local_decimals` by enough that small transfer amounts round to zero (e.g., an 18-decimal ERC20 side paired with a low-decimal or zero-decimal Substrate asset). Given that `register_token`/`update_token` governance sets `Precisions` per `(asset, chain)` and there is no on-chain floor check preventing a decimals gap that would let ordinary small transfers hit zero, this is plausible for real deployments, though it does depend on decimal-mismatch configuration choices rather than being universally triggerable for every asset pair.

### Recommendation
In `convert_to_balance` (and the `on_accept` caller), reject or round up conversions that would floor to zero for a strictly positive input, e.g. return an error (`Error::<T>::AmountTooSmallToConvert`) when `value > 0` but the divided result is `0`, instead of silently minting/transferring zero. Alternatively, enforce a minimum transferable amount at `send()` time on the EVM/Substrate boundary so that no dispatch can be created whose destination-side converted amount is zero.

### Proof of Concept
1. Register an asset with `Precisions::<T>::get(asset_id, evm_chain) == 18` (erc_decimals) while the local asset (`local_decimals`) is configured with `6` decimals (or the native asset with `T::Decimals::get()` set low).
2. From the EVM side, call the peer `BridgeToken`/`HyperFungibleToken` contract's send function with an amount smaller than `10^(18-6) = 10^12` wei (e.g. `1`).
3. The dispatched `Send` message reaches `on_accept` on Hyperbridge; `convert_to_balance` computes `1 / 10^12 = 0`.
4. `mint_into`/`transfer` is called with `amount = 0`; `TokenReceived` event fires with `amount: 0`, while the sender's tokens were already burned/escrowed on the EVM side in step 2 — value is permanently lost.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
