## Finding: Webhook `shop-domain` (and `topic`) header not covered by the Shopify HMAC signature — cross-tenant webhook spoofing

### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw HTTP body only, while the `shop` and `topic` values used to route and act on the webhook are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts these header-derived values, so a value that determines which tenant's data the handler acts on is never part of the authenticated bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` and `topic`, which are handed to the application's webhook handler as the tenant/action identity, are read from headers that are never included in that signable string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body) and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic`: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the hash only covers `verifiable_query.to_signable_string`, i.e., the raw body bytes — nothing else: [4](#0-3) 

This is the exact bug class called out in the analog rules: **a field acted on (`shop`, used as the tenant identity for the handler) but not covered by the HMAC**. The equality that should hold — `shop asserted in header == shop the HMAC secret was scoped/bound to` — is never checked; only `HMAC(secret, body) == received_hmac` is checked, and `secret` is the single app-wide `api_secret_key`, common to all shops using the app. Any shop that has installed the app receives genuine `(body, hmac)` pairs signed with that same shared `api_secret_key`. Because the signature does not bind `shop`/`topic` to the body, an attacker who controls one legitimately-installed shop (unprivileged relative to any other merchant) can take a `(body, hmac)` pair Shopify sent them and resubmit it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header rewritten to name a victim shop. `HmacValidator.validate` still returns true because it only re-derives the hash from the body, and `Registry.process` dispatches the handler with `shop: <victim>` and `body: <attacker-controlled>`.

### Impact Explanation
This is a cross-tenant integrity/access issue: an application built on this gem that uses `WebhookMetadata#shop` to select which tenant's records to update (the documented, expected usage pattern) can be made to write attacker-supplied webhook payload data into a different, victim shop's tenant record — without ever possessing that shop's credentials. This matches the Critical "cross-tenant access" impact category in scope.

### Likelihood Explanation
Likelihood is high for any application accepting webhooks from more than one installed shop (i.e., any typical multi-tenant Shopify app): the attacker only needs their own (unprivileged) shop install to obtain one valid `(body, hmac)` pair, then can replay it with a forged shop header at will, for any topic supported by the app.

### Recommendation
Bind the identity fields to the authenticated bytes: include `shop`, `topic` (and ideally `webhook_id`/`api_version`) in `to_signable_string`, or independently verify that the shop asserted in the header is one that is expected/known-authorized for the delivered `api_secret_key`/webhook subscription before dispatching to the handler, rather than trusting header values that sit outside the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches the (unchanged) HMAC header — validation passes.
4. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: <parsed B>, ...)`, causing the app to act on victim tenant data using attacker-controlled content.
