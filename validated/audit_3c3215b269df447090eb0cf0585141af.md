### Title
Webhook HMAC only covers `@raw_body`, allowing header (topic/shop/api-version/webhook-id) forgery on a legitimately-signed payload - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string` [2](#0-1) . `Registry.process` then trusts `request.topic`, `request.shop`, `request.api_version`, and `request.webhook_id` unconditionally once `HmacValidator.validate` returns true, and hands them to the handler as `WebhookMetadata` [3](#0-2) . None of those four header-derived values are cryptographically bound to the signature.

### Finding Description
The claimed broken binding is real: `signature_valid == (topic, shop, api_version, webhook_id, body all authentic)` is false; in this gem `signature_valid == (body authentic)` only, because `to_signable_string` is defined as `@raw_body` with no header material mixed in [1](#0-0) . `HmacValidator.validate` and `validate_signature` only ever touch `verifiable_query.hmac` (derived solely from the `hmac-sha256` header) and `verifiable_query.to_signable_string` [4](#0-3) . `Registry.process` raises only if the HMAC check fails, otherwise it looks up the handler by `request.topic` and passes `request.shop`, `request.api_version`, `request.webhook_id` straight through to the handler with no further validation [3](#0-2) .

Because `Context.api_secret_key` is the app's single shared client secret (not per-shop), any shop that installs the app can generate its own genuinely-signed webhook for a topic it controls. An attacker who owns a development/test shop with the app installed can capture a real `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to their own endpoint, then replay that exact body+hmac to the victim app's webhook endpoint while substituting arbitrary `shopify-topic`, `shopify-shop-domain`, `shopify-api-version`, and `shopify-webhook-id` headers. `OpenSSL.secure_compare` in `validate_signature` still succeeds because it only re-derives the HMAC from `@raw_body`, which is untouched [2](#0-1) . `Request.new` only checks that required headers are *present*, not that they match anything signed [5](#0-4) . Consequently, the app-level handler receives an internally-consistent-looking `WebhookMetadata` (topic/shop/api_version/webhook_id) that is entirely attacker-chosen while only the JSON body is provably from Shopify — and that body may itself be unrelated to the claimed topic/shop.

No existing guard closes this gap: `ShopValidator.sanitize!`, OAuth `state` checks, and `JwtPayload` claim checks are unrelated code paths (session-token/OAuth flow), not the webhook flow, and `Context.setup?`/`private?`/`embedded?` and Sorbet runtime typing do not perform any additional binding between header values and the signed body.

### Impact Explanation
This is a real signature-coverage gap that lets an attacker misattribute a legitimately Shopify-signed payload to an arbitrary shop, topic, webhook id, or API version of their choosing. If the host application's webhook handler trusts `WebhookMetadata#shop`/`#topic` for tenant attribution, authorization, or dispatch logic (which is the documented and expected usage pattern of this gem, since that's the only shop/topic information exposed to handlers), this enables cross-tenant data confusion: data legitimately belonging to the attacker's own shop can be delivered to the victim's handler labeled as belonging to a different shop, or dispatched to a handler registered for a different topic than the one Shopify actually sent it for (e.g., faking `webhook-id`/`api-version` to defeat idempotency or replay-window checks the app might build on those fields). This matches the "cross-tenant access" Critical category to the extent the host app relies on these fields, though the concrete damage is bounded by what the specific handler does with the metadata — the gem itself provides no protection.

### Likelihood Explanation
Preconditions are modest: attacker needs the ability to install the app on any shop (their own dev/test shop suffices) and to receive one legitimately signed webhook, then replay the body+hmac with forged metadata headers to the target endpoint — this is fully within the described "unprivileged attacker" capability set (own shop, own endpoint, controls headers/body/ordering) and requires no secret material. It is repeatable indefinitely against any body the attacker can get legitimately signed, and against any victim installation of the same app, since the signature never binds shop identity.

### Recommendation
Include the security-relevant headers (`shopify-topic`, `shopify-shop-domain`, `shopify-webhook-id`, `shopify-api-version`) in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. by having `to_signable_string` concatenate a canonical representation of these headers with the body), so that a legitimately-signed request cannot have its topic/shop/webhook-id/api-version headers swapped without invalidating the signature.

# test/webhooks/request_test.rb (new test)
def test_signable_string_ignores_headers
  headers = {
    "shopify-topic" => "orders/create",
    "shopify-hmac-sha256" => Base64.encode64("irrelevant"),
    "shopify-shop-domain" => "attacker-shop.myshopify.com",
  }
  request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers)
  assert_equal("{}", request.to_signable_string)

  # swap topic/shop headers, body+hmac untouched
  forged_headers = headers.merge(
    "shopify-topic" => "shop/redact",
    "shopify-shop-domain" => "victim-shop.myshopify.com",
    "shopify-webhook-id" => "forged-id",
  )
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)
  assert_equal("{}", forged_request.to_signable_string) # identical signable string despite forged metadata
end

# test/utils/hmac_validator_test.rb (new test)
def test_validate_ignores_topic_shop_headers
  ShopifyAPI::Context.setup(api_secret_key: "secret", ...)
  body = "{}"
  hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body))

  legit = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
    "shopify-topic" => "orders/create",
    "shopify-hmac-sha256" => hmac,
    "shopify-shop-domain" => "attacker-shop.myshopify.com",
  })
  forged = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: {
    "shopify-topic" => "shop/redact",
    "shopify-hmac-sha256" => hmac,
    "shopify-shop-domain" => "victim-shop.myshopify.com",
    "shopify-webhook-id" => "forged-id",
  })

  assert ShopifyAPI::Utils::HmacValidator.validate(legit)
  assert ShopifyAPI::Utils::HmacValidator.validate(forged) # still true - proves header forgery is undetected
end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
