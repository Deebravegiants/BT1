### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in processed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that is handed to application webhook handlers directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the intended binding of `signature == HMAC(shop || topic || body, client_secret)`; in reality it is only `signature == HMAC(body, client_secret)`.

### Finding Description
`Request#to_signable_string` returns solely `@raw_body`, and `Request#shop` reads the shop identity straight from a header that is not part of that signable string: [1](#0-0) [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (the body only) and compares it against `verifiable_query.hmac`. Once that succeeds, the registry immediately forwards `request.shop` — the unauthenticated header value — into `WebhookMetadata` and on to the app's handler: [3](#0-2) [4](#0-3) 

Because the app's `client_secret` is shared across every shop that installs the app, a body+HMAC pair genuinely issued by Shopify for the attacker's *own* store (which the attacker can freely create and trigger, e.g. by creating an order in a free development/trial shop) remains a valid `(body, hmac)` pair no matter what `shop-domain` header accompanies it. The documented handler contract explicitly trusts `data.shop` as "The shop domain of the webhook" for routing/persistence decisions: [5](#0-4) 

### Impact Explanation
An attacker who controls any shop that has installed the vulnerable app can capture a legitimate `(raw_body, hmac)` pair generated by Shopify for their own shop, then replay that exact HTTP body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop's domain). Because the HMAC check never inspects the header, the forged request passes `HmacValidator.validate` and is dispatched to the handler labeled as if it came from the victim shop. Depending on how the host application uses `data.shop` (e.g., looking up the victim's session/access token, writing data into the victim's tenant record, or triggering per-shop business logic), this crosses a tenant boundary — the report's cross-tenant-identity-binding class — using attacker-controlled body content misattributed to another merchant's shop record.

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own (or any) shop installed on the same app, which is trivial to obtain since Shopify development/trial stores are free and self-serve, and (2) knowledge of a target shop's domain, which is public (`*.myshopify.com`). No access to `client_secret`, access tokens, or the victim's credentials is needed — the attacker never needs the real secret because they replay a signature Shopify itself already computed for their own traffic. The main constraint is that impact depends on how far the host application trusts `data.shop` without independently correlating it to a known/expected shop for that webhook subscription, which is outside this gem's control but is not blocked or warned against anywhere in the gem or its docs.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header to the signed payload before trusting it. At minimum, `Registry.process` (or the app-facing documentation) should require callers to verify that `request.shop` matches an expected/registered shop for that webhook topic before acting on `WebhookMetadata#shop`, since currently nothing in `lib/shopify_api/webhooks/request.rb` or `lib/shopify_api/utils/hmac_validator.rb` prevents shop-domain spoofing on an otherwise-valid signature.

### Proof of Concept
1. App installs on attacker's own free Shopify dev store `attacker-shop.myshopify.com`, and the app registers an `orders/create` webhook.
2. Attacker performs an action in their own shop that triggers the webhook; Shopify sends a real, correctly-signed POST to the app's endpoint:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}`
3. Attacker intercepts/records this `(body, hmac)` pair (they own this shop, so they can trivially capture their own webhook traffic via a controlled endpoint, or reconstruct via `ngrok`/logging).
4. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the victim-facing webhook endpoint of the same app, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-controlled data as though it originated from `victim-shop.myshopify.com`.
