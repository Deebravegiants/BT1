### Title
Missing zero-amount transfer guard in `IntentGatewayV2.withdraw()` permanently locks escrowed intent funds for zero-transfer-reverting ERC-20 tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The legacy/Tron deployment of `IntentGatewayV2` implements escrow release in an internal `withdraw()` function that unconditionally calls `token.transfer(beneficiary, amount)` for every entry in `body.tokens`, with no check that `amount > 0` before making the call. This is the same bug class as the PuttyV2 finding: certain ERC-20 tokens revert on zero-value transfers, and if any per-token escrow amount in a withdrawal batch is zero, the whole `withdraw()` call reverts, blocking the release of all escrowed assets for that order — not just the zero-amount leg.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` iterates over `body.tokens` and, for each ERC-20 entry, performs a raw low-level call to `transfer`, reverting the entire function if that call fails: [1](#0-0) 

Unlike this function, the current mainline implementation used elsewhere in the codebase (`IntentsBase.sol::_withdraw`) explicitly skips zero-amount legs before transferring: [2](#0-1) 

The tron contract's `withdraw()` is reached from every settlement/refund path that releases escrow: same-chain cancellation, cross-chain cancellation from source (`onGetResponse`) and destination (`onAccept` for `RedeemEscrow`/`RefundEscrow`): [3](#0-2) [4](#0-3) 

The same missing-zero-check pattern also appears in the `SweepDust` handling in the same file, which likewise performs a raw `token.call(transfer, ...)` without checking `amount > 0`: [5](#0-4) 

### Impact Explanation
If a `withdraw()` call's token list includes an entry whose amount evaluates to zero for a token that reverts on zero-value transfers (a well-documented "weird ERC20" behavior, e.g. LEND), the `token.call(...)` returns `success == false`, and the function reverts with `TransferFailed()`. Because the loop transfers all tokens for the withdrawal request in a single atomic call, a single zero-amount leg blocks release of every other (non-zero) token amount in the same request, and — since `_filled[body.commitment]` is set before the loop but the whole transaction reverts on failure — the order's escrow becomes permanently unwithdrawable through the normal path. This is a concrete freezing-of-funds analog to the PuttyV2 finding, reachable by any user/solver whose order or fill happens to produce a zero-amount input entry for such a token.

### Likelihood Explanation
Likelihood is constrained by the fact that, in the current code paths reviewed, `order.inputs[i].amount` used for `cancelOrder`/refund/redeem is the protocol-fee-reduced amount, and reduction to exactly zero is prevented by the `originalAmount == 0` revert guard and `protocolFeeBps < 10_000` sizing — so a zero-amount leg is not trivially producible through the standard placement flow in this specific contract as reviewed. However, the same code path is also used by `SweepDust`, which is driven by governance-configured `TokenInfo` outputs and is not subject to the same non-zero invariant, and the underlying design defect (no `amount == 0` skip before an ERC20 transfer call) is a real, unremediated deviation from the safer pattern already adopted in the mainline `IntentsBase.sol`. Given the uncertainty about whether the Tron contract's fill/partial-fill logic (not fully reviewed) can produce a zero-amount escrow leg, this should be treated as Medium likelihood pending confirmation of all callers of `withdraw()`.

### Recommendation
Mirror the guard already present in `IntentsBase.sol::_withdraw`: skip (via `continue`) any token entry whose `amount == 0` before attempting the ERC20 transfer, in both `withdraw()` and the `SweepDust` handling in `evm/tron/contracts/apps/IntentGatewayV2.sol`. This prevents zero-value transfer attempts from ever reaching tokens that revert on them, eliminating the freezing risk.

### Proof of Concept
1. An order or governance-issued `SweepDust` request results in a `TokenInfo` entry with `amount == 0` for a token that reverts on zero-value `transfer` calls (e.g. LEND-style tokens).
2. `withdraw()` (or the `SweepDust` branch of `onAccept`) executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, 0))`. [6](#0-5) 
3. The token's `transfer` implementation reverts on the zero-value call, `success` is `false`, and the function reverts with `TransferFailed()`.
4. Because this happens inside the batch loop, all other non-zero token legs in the same withdrawal request also fail to be released, and the order's escrow (and, for `SweepDust`, all remaining dust entries in that call) become stuck with no alternate retry path that removes the zero-amount entry.
