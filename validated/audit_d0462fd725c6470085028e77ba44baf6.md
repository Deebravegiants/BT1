## Title
Permissionless phantom-bid solvers can set the published pool price and fabricate liquidity routes via self-declared, balance-only weighting — analogous to unrestricted pool curation - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
The Vader `curatePool`/`replacePool` bug is a class of vulnerability where an unprivileged actor can inject or replace reward/price-determining curation state using only transient capital, and downstream systems (rewards, routing) trust that state without further checks. Hyperbridge's phantom-bid liquidity-pricing pipeline exhibits the same structural pattern: any address can become a "verified" price-setting solver, the published price is a **selection** (not an average) that a single well-funded bidder can set outright, and the bidder's own **self-declared** `acceptedSources` field is used, unchecked, to mint searchable `PoolRoute` entries that downstream consumers (the indexer, `LiquidityEngine`, and simplex's own fill logic) treat as real, tradeable liquidity.

### Finding Description
`isVerifiedSolverBid` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:913-979` only checks that a bid's signer matches its sender and that the sender is EIP-7702-delegated to a (public, reusable) `SolverAccount` implementation. Delegating an EOA to that implementation is a permissionless, self-directed action — there is no allowlist of solvers, matching the "no access restriction" pattern in the original report.

The price for each leg is computed by `weightedMedian` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:709-724`), which is explicitly a **selection**, not a blend: [1](#0-0) 
A bidder holding over half the leg's weight sets the exact published price. Weight is derived purely from an on-chain balance read at aggregation time (`getBalance`/`getTotalSolverBalance`), not from any bonded stake, lock-up, or delivery guarantee: [2](#0-1) 

Separately, the bidder's `acceptedSources` declaration — attacker-controlled data inside `paymasterAndData`, verified only for authenticity (it is covered by the signed `userOpHash`), never for accuracy — is fed directly into `PoolRoute` creation: [3](#0-2) 
Nothing checks that a declaring solver can actually service the declared source chain; the corridor is minted purely because the bidder said so and briefly held the output-token balance.

This mirrors the report's root cause precisely: "anyone can curate" (here, "anyone can become a price/route-setting solver"), and the curation-determining resource (balance) can be acquired transiently and cheaply, then used to overwrite state ("replace" the published rate/routes) that other economic actors rely on.

### Impact Explanation
The published `PoolChainLiquidity`/`PoolRoute` rates and depths are consumed by `LiquidityEngine.getAvailableLiquidity` (`sdk/packages/sdk/src/protocols/intents/LiquidityEngine.ts:80-118`) and by simplex's own fill-pricing strategy (`sdk/packages/simplex/docs/ai/flows/phantom-probe-curve-value-published-price.md`), which size real, capital-bearing decisions off this data. A single actor who temporarily inflates its balance of an output token can:
1. Set an arbitrary published exchange rate for a pool/chain pair (weightedMedian selection), mispricing real intents that clients size against this rate.
2. Fabricate `PoolRoute` corridors for source chains it has no genuine intention or capacity to serve, misleading route discovery and capital allocation for real users, who may escrow funds expecting fillable capacity that does not exist.

This is a manipulation of a protocol-trusted pricing/curation oracle by an unprivileged party, analogous in kind to the curatePool finding's manipulation of the reward-eligible pool set.

### Likelihood Explanation
Becoming a "solver" requires only self-delegating an EOA to the public `SolverAccount` implementation and signing a userOp — no protocol permission is needed. Acquiring transient capital in the specific output token for a snapshot window is realistic given the weighting is a plain point-in-time `eth_call` read rather than a time-weighted or bonded measure. The attack does not require breaking any cryptographic check; it operates entirely within the "legitimate" bid-verification path.

### Recommendation
- Do not let a single unbonded, unstaked balance snapshot alone set the published price outright; require a floor on cumulative distinct backers or dampen selection sensitivity to a single large transient balance (e.g., cap any one bidder's weight share, or require balance persistence across multiple blocks/samples).
- Verify or economically bond `acceptedSources` declarations (e.g., require solvers to be registered/staked per declared corridor) rather than trusting a self-declared, unchecked field to mint `PoolRoute` rows.
- Consider pinning balance reads to the block at which the bid window actually closed (rather than "latest" at indexing time) to shrink the window for capital-timing manipulation, and combine with a minimum holding-period requirement.

### Proof of Concept
1. Attacker deploys/uses an EOA and delegates it via EIP-7702 to the public `SolverAccount` contract deployed for the target chain (no permission required).
2. Attacker signs and submits a `PackedUserOperation` bid for an active `PhantomOrderV2` window, quoting an arbitrary extreme output amount for a leg, with a `paymasterAndData` declaration listing arbitrary `acceptedSources` chains it does not actually serve — this passes `isVerifiedSolverBid` (`phantom-aggregation.ts:913-979`) purely on signature/delegation grounds.
3. Before `PhantomBidWindowExhausted` triggers `handlePhantomOrderPrices` → `aggregatePhantomBids`, attacker acquires (via a lending-protocol borrow, DEX swap, or brief transfer) a balance of the leg's output token exceeding the combined weight of all legitimate solver bidders.
4. `getBalance`/`getTotalSolverBalance` reads this balance at "latest" (`phantom-aggregation.ts:995-1022`, `1479-1497`), giving the attacker's quote overwhelming weight; `weightedMedian` (`phantom-aggregation.ts:709-724`) returns the attacker's quoted price verbatim.
5. `updateLiquidityPools`/`republishChainRows` (`liquidityPool.service.ts:357-449`, `732-788`) persist the attacker's price as the pool's published rate and mint `PoolRoute` rows for the attacker's fabricated `acceptedSources`.
6. Attacker unwinds the temporary balance. The manipulated rate/route data now propagates to `LiquidityEngine.getAvailableLiquidity` and any consumer (simplex fill pricing, client-facing quote UIs) pricing real intents against it. [4](#0-3)

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)
