### Title
Emporium min-circuit path allows signature-free arbitrary calls with zero fund accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol :: runAction/verifyWallet, contracts/CircomDataBuilder.sol :: formInputForCircom/formInputEmporiumMin)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit only proves `message == Poseidon(messageSeed)` plus `timeStamp`/`calldataHash` consistency — it constrains nothing about `EmporiumStack.ops`. Combined with `verifyWallet` returning immediately (no signature check) when `stack.signerAddress == address(0)`, and Hinkal's balance-accounting loop being skipped entirely for an empty token array, an unprivileged attacker can invoke arbitrary `endpoint.call{value}(callData)` from Emporium's own address with zero on-chain accounting of any resulting fund movement.

### Finding Description
The broken equality is: *assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`*.

Trace:
- `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) . That function only outputs `emporiumMessage`, `timeStamp`, `calldataHash` as public signals [2](#0-1) , meaning the ZK proof (verified against a distinct "Min" verifier selected via `buildVerifierId`) carries no constraint over `amountChanges`, nullifiers, UTXOs, or the `EmporiumStack` operations at all.
- Back in `Hinkal.transact`, because `circomData.erc20TokenAddresses.length == 0`, the balance-accounting loop that computes `balanceDif` and enforces `balanceDif == amountChanges[i] + utxoAmount` never executes (loop bound is `erc20TokenAddresses.length`) [3](#0-2) . Likewise `_externalTransact` builds `deltaAmountChanges` as a zero-length array [4](#0-3) .
- `_externalTransact` calls `EmporiumUpgradeable.runAction(circomData, deltaAmountChanges)` (deltaAmountChanges empty). Inside, `stack = abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` is fully attacker-controlled calldata [5](#0-4) .
- `verifyWallet` is called; if the attacker sets `stack.signerAddress == address(0)`, the function marks the message used and **returns without any signature verification**: [6](#0-5) .
- The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` for every attacker-supplied operation (CASE 2, stateless path) with `msg.sender == Emporium` [7](#0-6) . Because `erc20TokenAddresses.length == 0`, `balancesBefore`/`balancesAfter` are empty arrays and the closing accounting loop (lines 132–151) never runs, so any funds moved by these calls (Emporium's own ETH balance via `op.value`, or ERC20 tokens Emporium holds via a direct `transfer` call encoded in `op.callData`) are neither captured into a UTXO nor checked against any invariant. `payRelayFees` is likewise a no-op since it iterates the same empty array.
- If `op.endpoint` is another contract that trusts Emporium via its own `onlyAllowedRecipient` modifier (i.e., Emporium is a registered allowed recipient there), the attacker can make that trusted contract execute privileged logic (e.g., another external action's `runAction`) with `msg.sender == Emporium`, and that callee's own accounting only trusts the caller's identity, not that a genuine proof over its own funds preceded the call.

Existing guards fail to prevent this: `performHinkalChecks`'s `calldataHash` check is self-referential (it only certifies that `calldataHash` matches the very calldata the attacker supplies, not that the calldata is legitimate); `dimensionsCheck` only validates array-length agreement to `dimensions`, which the attacker also fully controls; `relayerIsValid` is bypassed entirely when `circomData.relay == address(0)` (self-relay); `rootHashExists` and nullifier/commitment insertion are irrelevant here since no UTXOs are consumed or created on this path. The only real gate — `onlyAllowedRecipient` on `EmporiumUpgradeable.runAction` — only restricts the caller to Hinkal.sol, which any attacker can trigger permissionlessly via `Hinkal.transact`.

### Impact Explanation
An attacker can drain any ETH or ERC20 balance held by the Emporium contract (in-flight/shielded funds sitting there pending stateful op execution) to an address of their choosing, with a trivially self-generated ZK proof (Poseidon of a self-chosen seed — no ownership of any UTXO required). This is direct theft of protocol/user funds in-flight through Hinkal's Emporium action, matching Critical severity ("direct theft of shielded or in-flight user funds"). The attack is repeatable per unused `emporiumMessage` nonce (attacker can pick many unused values), limited only by Emporium's balance at attack time.

### Likelihood Explanation
Preconditions: Emporium must hold ETH/ERC20 balance at the time of attack, and a Min verifier must be registered for the Emporium action id/dimensions combination (per repository design this appears to be an intended supported feature, not a hypothetical). Attacker cost is a single `Hinkal.transact` call with a locally-generated Groth16-style proof for the trivial Min circuit — no whitelisting, no relay privilege, no valid EmporiumStack signature required. This is fully reachable by any unprivileged EOA as defined in the threat model.

### Recommendation
Do not allow the signature-free (`signerAddress == address(0)`) path to bypass both (a) op-level authorization and (b) balance accounting simultaneously. Specifically:
- Require `erc20TokenAddresses.length > 0` (and full balance accounting) whenever Emporium `ops` perform external calls, or otherwise constrain `ops` inside the ZK circuit for the min path.
- Do not allow `verifyWallet` to skip signature verification for arbitrary third-party calls; the `signerAddress == 0` shortcut should only be usable for extremely restricted, pre-authorized operations (e.g., only whitelisted `endpoint`s with fixed effects), never `.call` with arbitrary `callData`/`value` to attacker-chosen endpoints.
- Ensure the min-circuit path can only be used together with an explicit constraint tying `emporiumMessage`/`calldataHash` to a real, previously-authorized commitment (e.g., a signature or a nullifier proving ownership), not merely a Poseidon hash the attacker can freely generate.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal stack (Hinkal, HinkalHelper, VerifierFacade, EmporiumUpgradeable), register Emporium as allowed external action and as `onlyAllowedRecipient` for Hinkal, register/mock the Min verifier for the Emporium `externalActionId`/dimensions to always return true (or use the real circuit with a self-chosen `messageSeed`).
2. Fund Emporium with ETH (e.g., `vm.deal(address(emporium), 10 ether)`) simulating in-flight funds.
3. As an attacker EOA (no prior deposit), call `Hinkal.transact` with:
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `encryptedOutputs = []`
   - `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: attackerEOA, invokeWallet: false, value: 10 ether, callData: ""})], ...}))`
   - valid proof/public-inputs for the Min circuit with attacker-chosen `messageSeed`.
4. Assert: before tx, `attacker.balance == B0`, `emporium.balance == 10 ether`; after tx, `attacker.balance == B0 + 10 ether`, `emporium.balance == 0`, and no UTXO/commitment was created or debited for the attacker, i.e., `balancesBefore == balancesAfter == []` inside `EmporiumUpgradeable.runAction` (equality asserted via emitted events/storage since the arrays are empty and no `require` ever fired) — proving assets moved (`10 ether` to attacker) while `balancesBefore/After` accounting never touched (both empty), directly violating the stated invariant.
