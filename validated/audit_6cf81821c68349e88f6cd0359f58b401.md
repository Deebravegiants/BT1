### Title
Predictable, unsigned offline session identifier used as sole cookie-based session token enables cross-tenant session hijack - (File: lib/shopify_api/utils/session_utils.rb, lib/shopify_api/auth/oauth.rb)

### Summary
For non-embedded apps, the offline session id that `ShopifyAPI::Auth::Oauth.validate_auth_callback` writes into the session cookie is fully deterministic (`"offline_" + shop`) and carries no signature or nonce binding it to the HMAC-validated callback that created it. `ShopifyAPI::Utils::SessionUtils.current_session_id` then accepts whatever string appears in the `shopify_app_session` cookie verbatim as the session id, with no re-derivation check. An attacker who learns this format from their own legitimate OAuth flow can forge a `Cookie` header naming any other shop's deterministic id and have it resolve identically.

### Finding Description
The broken binding, stated as an equality that should NOT hold but does:
`SessionCookie.new(value: session.id, ...).value` for shop A `== "offline_" + A`, and this same textual construction for arbitrary shop B (`"offline_" + B`) is accepted by `SessionUtils.current_session_id` exactly as if B had genuinely completed OAuth — i.e., **no cryptographic distinction exists between an id that resulted from a real HMAC-validated callback and an id that is merely guessed from the deterministic format**.

Code path:
1. `Oauth.validate_auth_callback` (lib/shopify_api/auth/oauth.rb:100-110) builds the non-embedded cookie as `SessionCookie.new(value: session.id, expires: ...)`, where `session.id` for offline sessions is produced by `SessionUtils.offline_session_id` — `"offline_#{shop}"` (lib/shopify_api/utils/session_utils.rb:63-66). This is confirmed exactly by the existing test `test_validate_auth_callback_offline` (test/auth/oauth_test.rb:137-155), which asserts `expected_cookie = SessionCookie.new(value: "offline_#{@shop}", expires: nil)`.
2. `SessionCookie` (lib/shopify_api/auth/oauth/session_cookie.rb) is a plain `T::Struct` with `name`, `value`, `expires` — no signature, MAC, or any field binding the value to the HMAC-validated callback that produced it.
3. `SessionUtils.current_session_id` for a non-embedded app simply reads `cookies[SessionCookie::SESSION_COOKIE_NAME]` and returns it directly via `cookie_session_id` (lib/shopify_api/utils/session_utils.rb:31-37, 68-71) — no signature check, no re-derivation from `HmacValidator`, no correlation with `auth_query` or `state`. This is confirmed by `test_non_embedded_app_current_session_id_returns_id_from_cookie` (test/utils/session_utils_test.rb:80-89), which shows an arbitrary string is returned verbatim as the trusted session id.

Attacker flow: the attacker installs the target app on their own shop (`attacker.myshopify.com`), completes a real, self-signed OAuth callback, and observes the cookie the gem emits: `shopify_app_session=offline_attacker.myshopify.com`. This confirms the deterministic format `offline_<shop>`. The attacker then sends a fresh, unauthenticated HTTP request to the same app with `Cookie: shopify_app_session=offline_victim.myshopify.com`, substituting a victim shop domain (guessable from any public storefront URL). Because `current_session_id` performs no validation beyond presence, it returns `"offline_victim.myshopify.com"` identically to how it would for a value legitimately set after victim's own real OAuth completion.

None of the existing guards intervene at this stage: `HmacValidator.validate` and the `state` comparison only apply during the OAuth callback itself, not to subsequent cookie-based session lookups; `ShopValidator.sanitize!` only validates shop-domain syntax; `JwtPayload`'s `aud` check applies only to the embedded/JWT path, not the cookie path; `Context.setup?`/`private?`/`embedded?` are unrelated context guards. There is no code point at which the cookie value is cryptographically re-verified as having originated from a genuine callback.

### Impact Explanation
If the host app's session storage (used "as documented," per `docs/getting_started.md`) looks up a stored `Session` — including its real `access_token` — by the id returned from `current_session_id`, then any attacker who merely knows a target shop's domain (public information) can cause the app to load and act using that shop's real offline access token, without ever having completed OAuth for that shop or possessed any secret. This is a cross-tenant compromise of another merchant's offline access token, satisfying the Critical category ("theft of a merchant access token... cross-tenant access"). It is fully repeatable against any shop whose domain the attacker knows, at negligible cost per victim.

### Likelihood Explanation
Preconditions: the app must be configured as non-embedded (`Context.embedded? == false`) and use the documented cookie + `current_session_id` pattern for offline sessions. The attacker needs no credentials — only the ability to run their own OAuth flow against their own shop (to confirm the deterministic format, which is also observable simply by reading this gem's public source/tests) and knowledge of the victim's `myshopify.com` domain, which is typically discoverable from the storefront. The attack requires zero interaction with the victim and no secret material, making it cheap and highly repeatable.

### Recommendation
Do not use a purely deterministic, secret-free string as the sole session-cookie value/lookup key for offline sessions. Bind the cookie value to a random, unguessable session identifier (e.g., a securely generated opaque token stored server-side and mapped to the shop), or sign/MAC the session id with `api_secret_key` and verify the signature in `SessionUtils.current_session_id` before trusting it.

```ruby
require_relative "../test_helper"

class SessionIdGuessableTest < Test::Unit::TestCase
  def test_cookie_value_is_deterministic_format
    shop = "attacker-shop.myshopify.com"
    session = ShopifyAPI::Auth::Session.new(id: "offline_#{shop}", shop: shop, access_token: "tok")
    cookie = ShopifyAPI::Auth::Oauth::SessionCookie.new(value: session.id, expires: nil)
    assert_equal("offline_#{shop}", cookie.value)
  end

  def test_current_session_id_accepts_guessed_victim_id_identically
    ShopifyAPI::Context.stubs(:embedded?).returns(false)

    victim_shop = "victim-shop.myshopify.com"
    forged_cookie_value = "offline_#{victim_shop}" # never issued to attacker by the server

    cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

    result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

    # No rejection occurs: the guessed id for a shop the attacker never authenticated
    # against is accepted exactly as a legitimately-issued one would be.
    assert_equal(forged_cookie_value, result)
  end
end
```

```ruby
# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
  end
end
```
