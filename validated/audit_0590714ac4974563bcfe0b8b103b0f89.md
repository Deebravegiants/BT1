### Title
Webhook `shop` and `topic` identity fields are not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` as plain, unauthenticated HTTP header values, while the HMAC signature that `Utils::HmacValidator` checks is computed over the raw request body only. Any actor who can obtain one legitimately-signed webhook body/HMAC pair (e.g. by subscribing their own store to a webhook) can replay that exact body with a forged `shop-domain`/`topic` header to a target app's webhook endpoint and pass signature validation, causing the app to process attacker-controlled data as if it belonged to a different (victim) shop or a different topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` are read straight from HTTP headers and are never included in the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only compares the HMAC of `to_signable_string` (i.e. the body bytes) against the `hmac` header value, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts this validation and then builds `WebhookMetadata` directly from the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

This breaks the identity binding: **shop/topic acted on by the handler ≠ shop/topic covered by the HMAC**. The signature only proves "this body was produced with the app's secret at some point, for some shop/topic combination," not "this body belongs to this shop and this topic." Since the raw body is signed independently of the headers, any valid `(body, hmac)` pair generated by Shopify for *any* topic/shop remains valid when replayed with different `shop-domain`/`topic`/`webhook-id` headers.

### Impact Explanation
An attacker who owns or controls any Shopify store (even a free dev store) subscribed to the app can trigger one legitimate webhook, capture its body and valid HMAC, and then send that exact body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim merchant (and/or a forged `X-Shopify-Topic`). `HmacValidator.validate` will accept it because only the body is checked. The app's webhook handler then processes the payload as authentic data belonging to the victim shop/topic — this is a cross-tenant data integrity/spoofing issue: attacker-controlled data gets attributed to another tenant's identity, which can trigger data corruption, unauthorized actions, or record injection scoped to the victim's shop within the host application, depending on how the handler uses `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitation requires no credentials beyond the ability to obtain one signed webhook (trivially available to any developer with a Shopify store subscribed to the target app, or any store whose webhook the app processes), and standard HTTP tooling to replay the request with modified headers. No access to `api_secret_key`, access tokens, or privileged accounts is needed — the whole point is that headers aren't cryptographically bound, so forging them requires no secret knowledge.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop` and `topic`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them to the request (e.g., include them as part of the string that is HMAC'd, similar to how OAuth's `AuthQuery#to_signable_string` binds all identity-relevant query parameters). Update `Webhooks::Request#to_signable_string` accordingly and reject requests whose header-derived identity fields don't match a value covered by the signature.

### Proof of Concept
1. Attacker subscribes their own store `attacker.myshopify.com` to a webhook topic supported by the target app; Shopify sends a request with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures `(B, H)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic` to a more sensitive topic registered by the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` — see [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes attacker's body as if it came from the victim shop — see [6](#0-5) .

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
