### Title
Webhook shop/topic/version identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body via `Utils::HmacValidator.validate(request)`, then forwards `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all of which are read from unauthenticated HTTP headers — to the app's handler as trusted `WebhookMetadata`. Because the identity fields (especially `shop`) are never included in the signed bytes, any party who possesses one valid `(raw_body, hmac)` pair can replay it with a different `shop-domain` header and have the payload attributed to an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers that are never part of the signed material: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header — it never binds any header to the signature: [3](#0-2) 

`Registry.process` treats a successful HMAC check as proof the entire request — including `request.shop` — is authentic, and passes it straight through to the app's webhook handler: [4](#0-3) 

Because the app's `api_secret_key` is shared across all shops that install the app (it is not shop-specific), any shop that has the app installed will receive genuine Shopify webhooks with a valid `(raw_body, hmac)` pair signed under that same secret. A malicious merchant (an "unprivileged" party with respect to other tenants — they only legitimately control their own shop) can capture one of their own real webhook deliveries and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. The HMAC check still passes because it only verifies the body bytes, not the shop header, so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's shop even though the body actually originated from the attacker's own shop.

This breaks the intended identity binding: `shop header used to route/attribute the webhook` should equal `shop that the HMAC-signed bytes were actually issued for`, but the gem enforces no such equality.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who controls one legitimate shop installation can cause the host application to process attacker-supplied webhook data (order data, GDPR payloads, app-uninstall notifications, etc.) as if it belongs to a different, victim shop. Any host app that uses `WebhookMetadata#shop` to select which tenant's records to update, uninstall, delete, or otherwise mutate — which is the documented, expected usage pattern — can have another tenant's data corrupted, deleted, or overwritten by an unrelated shop owner. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Low-to-moderate: it requires an attacker to control at least one legitimate shop with the app installed (trivial for a merchant on the Shopify platform, including free development stores) and to be able to POST arbitrary headers/bodies to the app's public webhook endpoint, which is by design internet-reachable and unauthenticated apart from the HMAC. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified material, or otherwise cryptographically tie the `shop-domain` header to the signed body before trusting it. At minimum, `Webhooks::Request#to_signable_string` should include the shop domain (and topic) alongside the raw body, and `HmacValidator`/`Registry.process` should reject requests where these identity fields aren't part of the verified signature. Until then, host apps cannot safely trust `WebhookMetadata#shop` from this gem to select a tenant/session, and the gem should document (or, better, close) this gap explicitly.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both under the same app (shared `api_secret_key`).
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, body `B`.
3. Attacker captures this request and resends it to the app's webhook endpoint, only replacing the shop header:
   - Headers: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <same-valid-hmac-of-body>`, same body `B`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — [5](#0-4)  — which passes because it only checks `raw_body` against the shared secret.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` and processes attacker-controlled body `B` under the victim shop's identity — [6](#0-5) .
