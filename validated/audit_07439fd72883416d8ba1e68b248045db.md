### Title
Escrow and protocol-fee accounting computed from declared input amounts instead of actual transferred balances allows fee-on-transfer tokens to create insolvent escrow ledgers - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron `IntentGatewayV2.placeOrder`, the protocol fee, the `reducedInputs` escrow amounts, and the commitment hash are all computed from the user-declared `order.inputs[i].amount` *before* the actual token transfer happens. Unlike the canonical EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which measures the gateway's actual received balance delta and mutates `order.inputs[i].amount` to that real value before computing fees/commitment, the Tron variant never re-syncs `reducedInputs`/`_orders` to the amount actually held after `safeTransferFrom`/predispatch execution.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` computes `reducedInputs` and the commitment hash at lines 348-385, using `order.inputs[i].amount` (the caller-declared amount) directly: [1](#0-0) 

It then transfers tokens afterward, and for the non-predispatch branch simply does a plain `safeTransferFrom` without measuring the resulting balance delta: [2](#0-1) 

The escrow ledger `_orders[commitment][token]` is then credited with `reducedInputs[i].amount` — the pre-transfer, declared-amount-derived value — regardless of what the gateway actually received: [3](#0-2) [4](#0-3) 

This is the same bug class as the STETHVault report: a value used for downstream accounting (there, `previewDeposit`/`spentCap`; here, `reducedInputs`/commitment/escrow) is computed against stale state — the balance/amount *before* the actual asset movement is reflected — rather than being resynced to the post-transfer reality. The fixed, canonical `evm/src/apps/IntentGatewayV2.sol` explicitly measures `balanceOf` before and after the transfer, overwrites `order.inputs[i].amount` with the real received amount, and only *then* computes protocol fees/commitment/escrow: [5](#0-4) 

The Tron contract lacks this resync entirely, so for any ERC20 whose `transferFrom` delivers less than the requested amount to the gateway (fee-on-transfer tokens, rebasing tokens, or tokens with transfer hooks that can reduce the delivered amount), `_orders[commitment][token]` will record more escrowed value than the gateway actually holds for that order.

### Impact Explanation
Because `_orders[commitment][token]` is a per-commitment ledger backed by a single shared token balance across all orders, over-crediting one order's escrow entry causes the aggregate ledger to exceed the gateway's actual token balance. When that order is later filled/withdrawn (`withdraw()` transfers `_orders[commitment][token]` out via `IERC20.safeTransfer`), the shortfall is paid for out of tokens belonging to other users' unrelated escrowed orders, insolvent-draining their escrow and creating a freezing/theft condition for those other orders' funds once withdrawals are attempted in sequence. This directly matches the "intents escrow" class explicitly in scope, and constitutes fund freezing/loss for legitimate order owners, satisfying a Medium/High severity bar.

### Likelihood Explanation
This is triggerable by any unprivileged user placing an order with a token whose `transferFrom` delivers less than the nominal amount to the recipient (a well-known, common ERC20 pattern). No admin, governance, or privileged role is required — a single `placeOrder` call using such a token, followed by normal fill/withdraw flow, exposes the mismatch. The Tron contract's own in-repo history (evm/src's mainline gateway) already implements and tests exactly this fee-on-transfer accounting fix, which is strong evidence this class of bug is realistic and was previously exploitable/considered here.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: transfer input tokens (and execute predispatch calls) first, measure the gateway's actual received balance delta per token, mutate `order.inputs[i].amount` to the real received value, and only then compute the protocol fee, `reducedInputs`, the commitment hash, and the `_orders` escrow credit. Apply the same phase ordering (transfer → measure actual received → compute fee/commitment/escrow) used in the canonical EVM contract to the Tron variant.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with `protocolFeeBps` configured.
2. Attacker/user places two orders back-to-back using a fee-on-transfer ERC20 token (e.g., 1% transfer fee) as input: Order A for `1000` declared tokens, Order B for `1000` declared tokens from a different account.
3. For each order, `reducedInputs[i].amount` and `_orders[commitment][token]` are computed from the declared `1000` (minus protocol fee), e.g. `~995`, while the gateway's `IERC20.balanceOf` only increased by `~990` (after the 1% transfer fee) per order — a `~5`-token shortfall per order that goes completely untracked.
4. After both orders are placed, the gateway physically holds `~1980` tokens total but the ledger sum `_orders[A][token] + _orders[B][token]` equals `~1990`.
5. When Order A is filled/withdrawn, `withdraw()` transfers the full `_orders[A][token]` (`~995`) out via `safeTransfer`, leaving the contract with insufficient balance to fully honor Order B's escrow entry — Order B's owner cannot receive their full escrowed refund/redemption, demonstrating fund freezing/loss caused directly by the pre-transfer amount computation shown at `evm/tron/contracts/apps/IntentGatewayV2.sol:348-385` and `440-464`.
