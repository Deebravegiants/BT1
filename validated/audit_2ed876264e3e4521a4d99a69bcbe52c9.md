### Title
Duplicate `erc20TokenAddresses` entries in `EmporiumUpgradeable.runAction` cause a single token inflow to be paid out twice, draining co‑mingled balances - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`runAction` snapshots `balancesBefore`/`balancesAfter` once per call via `getBalancesForArray` and then, in the loop at lines 132‑151, computes `balanceChange` independently for every index `i` in `circomData.erc20TokenAddresses` without deduplicating repeated token addresses or debiting the running balance as it pays out. If the same ERC20 address appears at two indices, both indices read identical before/after balances and both compute the identical `balanceChange = X`, so `handleOut` fires twice and `transferERC20TokenOrETH` sends `2X` out for only `X` actually received.

### Finding Description
Equality that must hold: `tokens leaving Emporium in one runAction == tokens that action actually gained (Δreal balance) + funds explicitly moved in from the shielded side (-deltaAmountChanges)`.

Trace:
- `balancesBefore = getBalancesForArray(circomData.erc20TokenAddresses)` reads live `balanceOf`/ETH balance per array slot [1](#0-0) , and `getBalancesForArray` itself has no notion of "distinct token addresses" — it just loops the calldata array and calls `getERC20OrETHBalance` for every index, including duplicates [2](#0-1) .
- After the ops execute (which move `X` of `TOKEN` into the contract), `balancesAfter` is captured the same way [3](#0-2) .
- The payout loop computes `balanceChange = balancesAfter[i] - balancesBefore[i]` per index and calls `handleOut(balanceChange, circomData, i)`, which unconditionally calls `transferERC20TokenOrETH(circomData.erc20TokenAddresses[i], msg.sender, balanceChange)` [4](#0-3) [5](#0-4) .
- Because `balancesBefore`/`balancesAfter` are static snapshots taken once (not re-read after each `handleOut` transfer), duplicating `TOKEN` at indices `i` and `j` makes `balanceChange` identical (`X`) at both indices — the loop has no memory that index `i`'s payout already consumed the real balance increase. The second `transferERC20TokenOrETH` call therefore attempts to move a second, unbacked `X` out of the contract.
- Nothing in `EmporiumUpgradeable.sol` checks `erc20TokenAddresses` for duplicates on-chain; the only claimed protection is the circuit's `distinctErc20AddressChecks` in `circuits/MainEVMCircuit.circom`. I was not able to fully confirm from the available circuit excerpts whether this constraint is applied unconditionally for every `Dimensions`/verifier variant wired to the Emporium `externalActionId`, or only for internal transacts — this is a genuine gap in my verification and would need to be checked against `VerifierFacade`/`Dimensions` selection logic before treating the on-chain fix as optional.
- Regardless of that circuit question, the Solidity logic itself is unsound: even assuming the prover is honest about `deltaAmountChanges`, nothing forces `erc20TokenAddresses[i] != erc20TokenAddresses[j]` at the contract layer, and the balance-delta computation is not resilient to duplicates.
- The second `transferERC20TokenOrETH` only reverts if the contract's *actual remaining* balance (after the first payout removed `X`) is less than `X`. If Emporium holds residual balance from other users' pending deposits (co-mingled custody, since Emporium is a shared contract balance, not per-user segregated), the second transfer succeeds silently by draining that residual balance instead of reverting.

### Impact Explanation
An attacker can extract `2X` for a genuine `X` inflow, stealing the excess `X` directly from other users' co-mingled funds held in Emporium at the time of the call. This is direct theft of user funds via a value-conservation violation in a custodial contract, matching the Critical category (direct theft of shielded/in-flight user funds). It is repeatable per block/per transaction as long as residual co-mingled balance exists to absorb the shortfall, and does not require any privileged role — only crafting `circomData.erc20TokenAddresses` with a duplicate and running one deposit-type op.

### Likelihood Explanation
Preconditions: (1) the attacker can submit `erc20TokenAddresses` containing a duplicate entry for a chosen action — this requires the circuit to not reject duplicate addresses for the Emporium's external-action dimension, which is the open question about `distinctErc20AddressChecks` scoping; (2) Emporium must hold non-zero balance of `TOKEN` from other users' or its own residual deposits at call time for the second transfer to succeed rather than revert. Both preconditions are plausible in normal operation (shared/co-mingled contract balance, asynchronous multi-user deposits), and the attacker cost is a single crafted proof/transaction using their own funds. If the circuit's distinctness check does apply to every dimension used with Emporium, this specific vector is blocked at the proof layer; that determination could not be completed with the available tooling and should be independently verified before considering this exploitable end-to-end.

### Recommendation
- Enforce address distinctness for `circomData.erc20TokenAddresses` on-chain in `EmporiumUpgradeable.runAction` (or in `CircomDataBuilder`/base action validation) independent of any circuit-side guarantee, since external-action parameters should not rely solely on proof constraints that may not be universally scoped.
- Alternatively/additionally, redesign the payout loop to decrement a running "available" balance as each `handleOut` executes, so a duplicate index cannot claim the same real balance increase twice.
- Confirm and, if necessary, unconditionally apply `distinctErc20AddressChecks` in `circuits/MainEVMCircuit.circom` for every `Dimensions` variant reachable via `externalActionId` used by Emporium (and other external actions using the same `getBalancesForArray` pattern, e.g., check `Hinkal.sol`/`ExternalActionSwap.sol` for the same class of bug).

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `TOKEN`, and seed Emporium with a residual balance `R` of `TOKEN` (simulating another user's pending co-mingled deposit).
2. Craft `circomData.erc20TokenAddresses = [TOKEN, TOKEN]` and an `EmporiumStack` whose single op transfers `X` of `TOKEN` into the Emporium contract (e.g., a mock endpoint that calls `TOKEN.transferFrom(attacker, address(Emporium), X)`).
3. Set `deltaAmountChanges = [0, 0]` (pure external deposit, no shielded outflow).
4. Call `runAction`; assert:
   - `balancesBefore == [R, R]`, `balancesAfter == [R+X, R+X]`.
   - Both loop iterations compute `balanceChange = X`.
   - `handleOut` is invoked twice, and `attacker` receives `2X` in `TOKEN`.
   - Emporium's final `TOKEN.balanceOf(Emporium)` equals `R - X` (i.e., `R + X - 2X`), proving the residual `R` (belonging to another party) was partially or fully drained instead of the transaction only moving `X` in and `X` out (equality `tokens out == tokens in` is violated 2:1).
5. Repeat with `R = 0` to show the second transfer reverts (`ERC20: transfer amount exceeds balance`), confirming the exploit is conditioned on co-mingled residual balance as described.

        int256 balanceChange,
        CircomData calldata circomData,
