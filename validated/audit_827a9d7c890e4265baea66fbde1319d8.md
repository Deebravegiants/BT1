### Title
Protocol fee is charged in full at order placement and never refunded on cancellation, penalizing users whose orders are never filled - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` deducts the protocol fee (`protocolFeeBps`, or a per-destination override) from the user's input tokens immediately and irreversibly at order placement, before any solver has provided a fill and before the order has any chance of being executed. If the order later expires unfilled or is cancelled, only the remaining escrow and `order.fees` are returned — the protocol fee is retained as "dust" and is never refunded. This mirrors the Sablier "Protocol and Broker are overpaid in the event of a canceled stream" bug class: a service/settlement fee is collected in full up front for a service that is subsequently never delivered.

### Finding Description
`placeOrder` computes and deducts the protocol fee from each input amount before escrowing the reduced amount, emitting `DustCollected` for the retained fee: [1](#0-0) 

This fee is taken unconditionally at placement, regardless of whether the order will ever be filled. The commitment hash and the escrowed balance both reflect the fee-reduced amount, so the fee is baked in before the order has any counterparty.

Cancellation logic (`cancelOrder` → `_cancelSameChain` / `_cancelFromSource` / `_cancelFromDest`) only returns the *remaining escrow* (the already fee-reduced amount) and `order.fees` (the solver/settlement fee) — never the protocol fee: [2](#0-1) [3](#0-2) [4](#0-3) 

The project's own documentation confirms this is a known, deliberate design choice: the protocol fee is "not refunded if the order expires, receives no bids, or is cancelled": [5](#0-4) [6](#0-5) 

This is structurally identical to the Sablier finding: a protocol/settlement fee calculated over the full committed amount is charged atomically at creation time rather than accruing progressively as the underlying service (order fulfillment / stream vesting) is actually delivered, so any early termination (order never filled, cancelled before deadline, cancelled immediately after placement due to a mistake) results in the user paying for a service that was never rendered.

### Impact Explanation
Users who place an order that is never filled — whether due to a mistake, no solver interest, a solver-side revert, or a same-chain/cross-chain cancellation immediately after placement — permanently lose the protocol fee percentage of their input even though zero settlement work was performed by the protocol. For orders with large notional values (protocol fee scales linearly with the order size, unlike Sablier's per-stream flat parameters), this can represent a nontrivial, unrecoverable loss of user funds on every reverted/cancelled attempt. Because `protocolFeeBps` (or the destination-specific override) is fully governance-controlled and can be raised, the magnitude of this loss is not bounded by a fixed constant.

### Likelihood Explanation
This triggers on any unprivileged, single-transaction flow: a user calling `placeOrder` and then `cancelOrder` (same-chain, immediately reachable in one block) or a cross-chain order that simply goes unfilled until expiry. No special privileges, governance action, or malicious counterparty are required — it is the deterministic default outcome of the documented fee logic, occurring routinely whenever intents fail to attract solver interest or users need to correct order parameters.

### Recommendation
Adopt the same mitigations Sablier itself outlined but applied to the intents flow: either (1) refund the pro-rata protocol fee when an order is cancelled/expires unfilled (mirroring the "gradual accrual" recommendation — since fulfillment here is all-or-nothing rather than time-based, this simply means only debiting the fee once a fill occurs, not at placement), or (2) collect the protocol fee at fill time (deduct it from the solver's redemption in `_withdraw`) rather than escrowing the fee-reduced amount up front. At minimum, document/cap the fee rate and consider refunding it on cancellation before the order has had any chance to be filled (e.g., cancellation initiated in the same block/transaction as placement).

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with `inputs = [100 USDC]` and `protocolFeeBps = 5` (0.05%). The contract deducts `0.05 USDC` as protocol fee, escrows `99.95 USDC`, and emits `DustCollected(usdc, 0.05e6)`: [7](#0-6) 
2. No solver fills the order (e.g., unattractive price, or the user immediately realizes a parameter mistake).
3. User calls `cancelOrder(order, options)` — for a same-chain order this succeeds immediately in the same or a subsequent transaction, refunding only the escrowed `99.95 USDC` via `_cancelSameChain` → `_withdraw`: [2](#0-1) 
4. The `0.05 USDC` protocol fee remains permanently retained by the gateway as dust, sweepable only by governance via `SweepDust`, even though the user received zero settlement service. This is confirmed by the test suite explicitly asserting the fee is taken at placement and by the documented "Not refunded" behavior on cancellation.

                ++i;

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

### What is refunded and what is not

| Amount | On a successful cancellation |
| --- | --- |
| Remaining input escrow | Refunded to `order.user`. For a same-chain partial fill, only the unfilled remainder remains. |
| `order.fees` solver/settlement fee | Refunded to `order.user` when the refund finalizes on the source chain. |
| 5 bps protocol fee deducted at placement | **Not refunded.** It was retained as protocol dust before the order's escrow commitment was created. |
| Placement gas and cancellation gas | **Not refunded.** They are native-chain transaction costs. |
