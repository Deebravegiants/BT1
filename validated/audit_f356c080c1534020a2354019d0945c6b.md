### Title
Wallet passphrase cached and persisted unencrypted in extension session storage - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
The `PassphraseCache` module, used by the `@exodus/application` feature to support auto-unlock, stores the user's raw wallet passphrase in plaintext in a storage backend that is explicitly documented as unencrypted ("Unsafe = no encryption built in"). This is functionally the same bug class as the Halborn finding: the wallet's unlock secret is available in clear text outside of the in-process memory of the signing/keychain module, in a location that can persist and be exfiltrated.

### Finding Description
When the `cachePassphrase` config option is enabled, `features/application/src/index.ts` wires `passphraseCacheDefinition` to a storage aliased to `sessionStorage`: [1](#0-0) 

`PassphraseCache.set()` writes the plaintext passphrase string directly to that storage with no encryption step: [2](#0-1) 

and `PassphraseCache.get()` reads it back as plaintext for use in `#autoUnlock()`: [3](#0-2) 

The `sessionStorage` implementation (`@exodus/browser-extension-adapters/session-storage`) is built directly on top of `unsafe-storage`, which the package README explicitly labels as unencrypted: [4](#0-3) [5](#0-4) 

By contrast, the wallet's actual seed/mnemonic storage (`seedStorage`, seco-storage) is explicitly designed to require a passphrase for encryption/decryption before touching disk: [6](#0-5) 

The passphrase cache bypasses that protection entirely — it is set up specifically so a plaintext copy of the user's unlock passphrase is persisted (with a TTL, default up to 60 minutes) rather than only kept transiently in JS heap memory. This mirrors the Halborn bug class: an unencrypted, plaintext secret sitting in accessible storage, which can be recovered by anything with read access to that storage (e.g. `chrome.storage.session`, or the in-memory fallback if `chrome.storage.session` is unavailable) — analogous to the memory-dump/`strings` extraction described in the report.

### Impact Explanation
Any actor with access to the extension's storage (e.g., another extension exploiting a shared storage bug, a forensic dump of browser profile data, or a compromise capable of reading `chrome.storage.session`) can recover the user's wallet unlock passphrase in cleartext without needing to break any cryptography. Given that passphrase, the attacker can call `wallet.unlock`/`getMnemonic` and directly recover the mnemonic, leading to full wallet compromise.

### Likelihood Explanation
This only triggers when `cachePassphrase` is enabled in the application config, but when enabled, the plaintext passphrase persists for the full configured TTL (default up to 60 minutes) rather than only momentarily in memory, widening the exposure window. No misuse or attacker-controlled input is required — this is inherent to the designed caching behavior.

### Recommendation
Do not store the raw passphrase directly in `unsafe-storage`/`sessionStorage`. Either derive and store a value that cannot be used to unlock the wallet directly without an additional secret (e.g., encrypt the cached passphrase with a key held only in volatile memory, not persisted storage), or restrict the passphrase cache to a genuinely in-memory-only atom that is never written through a `storage-spec` persistence layer.

### Proof of Concept
1. Enable `cachePassphrase: true` in the `application` feature config: [7](#0-6) 
2. Call `exodus.application.unlock({ passphrase })`, which triggers `void this.#passphraseCache.set(opts.passphrase)`: [8](#0-7) 
3. Inspect the storage backing `sessionStorage` (`chrome.storage.session`, or the extension's storage tab in dev tools) — the `passphrase` key is present as a plaintext string, matching the value entered by the user, with no encryption applied by `PassphraseCache.set`.

const createSecoStorage = ({ prefix = '', storage, appVersion } = {}) => {
  assert(appVersion && typeof appVersion === 'string', 'appVersion must be a string')

  const _get = async (key, opts = {}) => {
    const { passphrase } = opts

    const data = await storage.get(key)

    if (!passphrase) return data

    if (data === undefined) return

    const string = await seco.decryptString({
      data,
      key: passphrase,
      encoding,
    })

    return BJSON.parse(string)
  }

  const _set = async (key, value, opts = {}) => {
    const { passphrase } = opts

    if (!passphrase) return storage.set(key, value)

    let data = BJSON.stringify(value)

    data = await seco.encryptString({
      data,
      key: passphrase,
      encoding,
      appVersion,
    })

    return storage.set(key, data)
  }
