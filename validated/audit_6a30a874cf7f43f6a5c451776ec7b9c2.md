### Title
Venue-priced Simplex fills are computed from a live, unprotected Uniswap V4 spot price, enabling sandwich attacks against order fills - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
Simplex's `FXFiller` prices "venue-priced" pairs (pairs configured without `bidPriceCurve`/`askPriceCurve`) directly from a Uniswap V4 pool's current `sqrtPriceX96`, with no TWAP, no execution-size impact term, and only an *optional* static-reference deviation guard. This is the same bug class as the referenced Kyber `Pool.sol` report: a swap/fill amount is priced off a manipulable, single-block spot price, letting an attacker sandwich the price used to size a solver's fill of a user's cross-chain intent order.

### Finding Description
For pairs configured under `[vault.uniswapV4]` with no curve, `resolveLegRates`/`referenceRate` in `sdk/packages/simplex/src/strategies/fx.ts` (around lines 1339-1364) calls `venueUsdPrice(chain, token1Address)`, which resolves to `UniswapV4FundingPlanner`'s price computation (`computeDirectPoolPriceUsd`, documented in `sdk/packages/simplex/docs/ai/flows/venue-pricing-uniswap-v4-funded-pairs.md:1-22`). That function returns "the raw pool mid derived from `sqrtPriceX96`" read live from `UNISWAP_V4_STATE_VIEW_ABI.getSlot0` in `UniswapV4LiquidityState.refresh()` (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4LiquidityState.ts:139-230`).

The only defense on this path is `checkPriceGuard` (`sdk/packages/simplex/src/strategies/fx.ts:428-448`), which is explicitly optional: [1](#0-0) 
and even when configured, it only rejects a quote if it deviates from a static `referencePrice` by more than `maxDeviationBps` — it checks *drift from a fixed number*, not manipulation resistance or execution cost: [2](#0-1) 

This rate (`rate = 1 / venueUsd`) is used both to size the order notional (`sizeOrder`/`referenceRate`, `fx.ts:1277-1364`) and, per the docs, to compute the actual per-leg output amount delivered to the order (`computeLegPolicyOutput`). An attacker can therefore, within a single block, flash-swap the configured Uniswap V4 pool to move `sqrtPriceX96` by up to `maxDeviationBps` (or unboundedly if no guard is configured), causing the solver to fill the victim's intent order at the manipulated rate, and then reverse the swap for profit — the textbook sandwich pattern described in the source report, just relocated from an AMM's own `swap()` to Simplex's solver-side pricing oracle for `IntentGateway` fills.

This differs from, and is a distinct issue from, the already-acknowledged LP-withdrawal griefing case in `UniswapV4FundingPlanner.ts` (decision doc `2026-08-19-the-v4-planner-credits-the-liquidity-the-calldata-encodes.md`), where `amount0Min`/`amount1Min` bound the withdrawal itself. That protection only bounds the token amounts the *removeLiquidity call* receives from the pool; it does nothing to protect the *price the solver quotes to the order placer*, which is fixed before the atomic UserOperation executes and is derived from the same manipulable spot read.

### Impact Explanation
A manipulated venue price directly changes the amount of output tokens a user's cross-chain intent order is filled for (or the tokens the solver pays out), which is a direct value-transfer/theft vector reachable from a single order submission plus an attacker's flash/back-run transactions on the destination-chain pool. Because `checkPriceGuard` is optional and, even configured, only bounds *distance from a static reference* rather than *manipulation within the current block*, an attacker can extract value on every fill of a venue-priced pair up to the configured (or unbounded, if unconfigured) deviation tolerance. This satisfies the "concrete theft of funds" bar for a High-severity issue analogous to the source report.

### Likelihood Explanation
Likelihood is high for any operator who configures a venue-priced pair (`[vault.uniswapV4]` with no curve) without a `referencePrice`/`maxDeviationBps` guard (the guard is explicitly optional per the docs), and non-trivial even with the guard configured, since flash-loan-funded pool manipulation within `maxDeviationBps` is a standard MEV technique and needs no privileged access — only a pending order to sandwich and enough capital/flash liquidity to move the configured pool.

### Recommendation
Replace or augment the spot `sqrtPriceX96` read with a TWAP (time-weighted average price) sourced over multiple blocks, and make the price guard (`referencePrice`/`maxDeviationBps`) mandatory rather than optional for any venue-priced pair. Additionally, size-impact the quote (apply the pool's own fee tier and slippage from `computeLegPolicyOutput`'s linear extension) rather than pricing the whole quantity at the raw mid, and consider circuit-breaking a fill if the spot price and a longer-window TWAP diverge beyond a tight bound.

### Proof of Concept
1. Operator configures a venue-priced pair (`[[pairs]]` with no `bidPriceCurve`/`askPriceCurve`, backed by `[vault.uniswapV4]` positions) and does not set `referencePrice`/`maxDeviationBps` (both optional per `docs/content/developers/evm/simplex/pricing.mdx:70-72`), or sets a wide `maxDeviationBps`.
2. Attacker observes a pending intent order that will be filled by the Simplex solver against this pair.
3. Attacker front-runs with a large swap against the destination-chain Uniswap V4 pool backing the position, moving `sqrtPriceX96` within the accepted band (or unboundedly, if no guard).
4. Simplex's `FXFiller` reads the manipulated `getSlot0` price via `UniswapV4LiquidityState.refresh()` and prices/fills the victim's order off it, under-delivering (or over-delivering, depending on direction) output tokens relative to the true market price.
5. Attacker back-runs, reversing their initial swap, restoring the pool price and realizing profit equal to the value skimmed from the victim's fill (bounded by pool fees/slippage), exactly mirroring the TX1→TX2→TX3 sandwich in the source report.

Note: I was unable to fully trace the exact file/line for `computeDirectPoolPriceUsd` itself (only referenced by name in the flow doc and inferred to live in the Uniswap V4 funding/pricing code under `sdk/packages/simplex/src/funding/uniswapV4/`), and could not verify from the index whether `computeLegPolicyOutput`'s exact output-amount formula additionally clamps against pool depth beyond what `checkPriceGuard` provides — a Devin session with full repo access would be needed to confirm the precise line-level mechanics of the output-amount computation.

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
