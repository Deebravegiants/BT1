### Title
Nomination Pool Members Can Front-Run `payout_stakers` to Siphon Rewards Earned by Other Members - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The external report describes a Liquity-style flash-loan attack: an attacker temporarily injects collateral into a trove, triggers a liquidation, collects a pro-rata share of redistributed rewards, and exits — stealing value from long-term position holders because rewards are split by "current share count" rather than by time-weighted contribution. `pallet-nomination-pools` has an analogous accounting pattern: reward entitlement is computed purely from a member's *current* `points` relative to total pool `points` at the moment a reward is recorded, with no time-weighting of when those points started earning. This creates a similar (though not identical, due to unbonding locks) window for value extraction.

### Finding Description
In `join()`, a new member's points are added to `bonded_pool.points` immediately, and their `last_recorded_reward_counter` is set to the pool's *current* reward counter [1](#0-0) . This correctly prevents a joiner from claiming rewards that were already reflected in the reward account balance *before* they joined.

However, the actual staking reward for an era is computed from `Eras::<T>::get_paged_exposure` / `EraInfo::<T>::get_paged_exposure`, a snapshot of stake taken when the era's validator exposure was recorded — this snapshot is fixed and does not include stake bonded after the snapshot, so an individual nominator directly staking cannot inflate their own share mid-era. But a **nomination pool** bonds to `pallet-staking` as a single nominator; the reward for the *pool's total exposure* is transferred in bulk into the pool's reward account via `payout_stakers` / `do_payout_stakers_by_page` [2](#0-1) . That transfer can be triggered by **any signed account**, at any time after the era ends, independent of individual pool membership.

Inside the pool, once that lump sum lands in the reward account, `RewardPool::update_records` distributes it pro-rata to `bonded_pool.points` *at the time `update_records` runs* [3](#0-2) , not to the points that existed when the underlying stake actually earned that reward (i.e., at the era's exposure-snapshot time).

This produces the following extraction path:
1. Attacker calls `Pools::join()` with a large bonded amount **after** the reward-earning era's exposure was snapshotted, but **before** `payout_stakers` is called for that era. At this point `reward_pool.update_records` runs with the *old* (pre-reward) balance, so the attacker's `last_recorded_reward_counter` is set to the pre-payout value [1](#0-0) , and their large stake is added to `bonded_pool.points`.
2. Attacker (or anyone) calls `payout_stakers`, which transfers the era's staking reward for the pool's stash into the pool's reward account, based on the exposure snapshot that did **not** include the attacker's new bond [4](#0-3) .
3. Attacker calls `claim_payout` (`do_claim_payout` → `do_reward_payout`), which calls `reward_pool.update_records` again, now with the inflated balance, and computes `current_reward_counter` based on `bonded_pool.points`, which **includes** the attacker's freshly-bonded (reward-blind) points [5](#0-4) . The attacker receives a pro-rata share of a reward their capital never actually helped earn, diluting the payout that should have gone entirely to members who were bonded during the exposure-snapshot period.

Unlike a pure nominator, the attacker does not need to control the timing of the era-exposure snapshot itself — they only need to beat the *payout* transaction, which is a routine, delayed, and permissionless operation (`payout_stakers` is commonly executed hours or days after era end by pool operators/bots), giving a comfortable window to front-run it.

### Impact Explanation
This is a real accounting/economic-fairness bug: it lets a well-capitalized actor redirect part of the yield legitimately earned by long-standing pool members to themselves, with essentially zero holding-period risk beyond the pool's `bonding_duration`. Unlike the trove example, the attacker cannot fully exit atomically (unbonding funds requires waiting `BondingDuration` eras via `unbond`/`withdraw_unbonded`), so this is not a true same-block flash-loan drain — the capital is temporarily locked. However, the reward itself is extracted immediately via `claim_payout`, with no principal loss, no slashing exposure beyond normal staking risk, and no requirement to actually keep the capital productively staked for the period that generated the reward. This degrades trust in nomination-pools' reward fairness for smaller/long-term members and effectively is a permissionless MEV/free-rider strategy against them.

### Likelihood Explanation
Likelihood is moderate rather than high: the attack requires (a) the attacker to notice a pool whose accrued-but-unclaimed staking reward for a finished era is significant relative to its current bonded total, (b) the attacker to have (temporarily) enough liquid capital to join with an outsized bond, and (c) a delay between era-end (exposure snapshot) and the `payout_stakers` call for that era — which is common in practice since payouts are not automatic and are often batched/delayed. There is no special privilege required; `join`, `payout_stakers`, and `claim_payout` are all permissionless, unprivileged calls reachable by any account.

### Recommendation
Consider one or more of:
- Snapshot/lock a member's eligible points for pending-but-unclaimed rewards at the time the underlying era reward was earned (e.g., track reward eligibility per bonding-era rather than by "current points at claim time"), similar to how `Eras::<T>::get_paged_exposure` freezes exposure per era for direct nominators.
- Add a minimum bonding delay before newly joined/bonded points become eligible to share in rewards whose underlying era already ended (i.e., only allow new points to participate in rewards accrued from the *next* era's exposure onward).
- Alternatively/additionally, restrict who may trigger `payout_stakers` for a pool's stash, or require pools to claim payouts promptly (reducing the front-running window), though this is a weaker mitigation.

### Proof of Concept
1. Pool `P` nominates validator `V`. Era `E` ends; `V`'s exposure for era `E` (via `ErasStakersPaged`/`ErasStakersOverview`) is snapshotted and includes only existing pool members' stake.
2. Before anyone calls `payout_stakers(V, E)`, attacker calls `Pools::join(pool_id, large_amount)`. This runs `reward_pool.update_records` on the *pre-payout* balance, sets attacker's `last_recorded_reward_counter` accordingly, and adds attacker's points to `bonded_pool.points` [6](#0-5) .
3. Attacker (or anyone) calls `Staking::payout_stakers(V, E)`, which transfers the era-`E` reward for `P`'s stash into `P`'s reward account, based on the exposure snapshot from step 1 (excludes attacker's stake) [7](#0-6) .
4. Attacker calls `Pools::claim_payout()`. `do_reward_payout` recomputes `current_reward_counter` using the now-inflated reward-account balance and `bonded_pool.points` (which include the attacker's newly bonded points), paying the attacker a share of the era-`E` reward [8](#0-7) .
5. Attacker's principal remains bonded until `unbond`/`withdraw_unbonded` completes after `BondingDuration`, but the reward already extracted in step 4 is not clawed back — a portion of value that should have accrued solely to earlier members has been captured by the attacker's temporarily-inflated point share.

**Note on confidence**: I could not find an explicit `SECURITY.md`/`Researcher.md` note calling this out as a known/accepted trade-off in nomination-pools within the indexed code, nor could I confirm exact production timing of `payout_stakers` calls relative to era boundaries (this depends on off-chain bots/operator behavior, not something visible purely in the pallet code). The severity of this finding therefore hinges on how large the delay window between era-end and `payout_stakers` typically is in practice, which is an operational rather than purely code-level fact.

	/// Update the recorded values of the reward pool.
	///
	/// This function MUST be called whenever the points in the bonded pool change, AND whenever the
	/// the pools commission is updated. The reason for the former is that a change in pool points
	/// will alter the share of the reward balance among pool members, and the reason for the latter
	/// is that a change in commission will alter the share of the reward balance among the pool.
	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

		// Store the total payouts at the time of this update.
		//
		// An increase in ED could cause `last_recorded_total_payouts` to decrease but we should not
		// allow that to happen since an already paid out reward cannot decrease. The reward account
		// might go in deficit temporarily in this exceptional case but it will be corrected once
		// new rewards are added to the pool.
		self.last_recorded_total_payouts =
			self.last_recorded_total_payouts.max(last_recorded_total_payouts);

		Ok(())
	}

	/// If the member has some rewards, transfer a payout from the reward pool to the member.
	// Emits events and potentially modifies pool state if any arithmetic saturates, but does
	// not persist any of the mutable inputs to storage.
	fn do_reward_payout(
		member_account: &T::AccountId,
		member: &mut PoolMember<T>,
		bonded_pool: &mut BondedPool<T>,
		reward_pool: &mut RewardPool<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		debug_assert_eq!(member.pool_id, bonded_pool.id);
		debug_assert_eq!(&mut PoolMembers::<T>::get(member_account).unwrap(), member);

		// a member who has no skin in the game anymore cannot claim any rewards.
		ensure!(!member.active_points().is_zero(), Error::<T>::FullyUnbonding);

		let (current_reward_counter, _) = reward_pool.current_reward_counter(
			bonded_pool.id,
			bonded_pool.points,
			bonded_pool.commission.current(),
		)?;

		// Determine the pending rewards. In scenarios where commission is 100%, `pending_rewards`
		// will be zero.
		let pending_rewards = member.pending_rewards(current_reward_counter)?;
		if pending_rewards.is_zero() {
			return Ok(pending_rewards);
		}

		// IFF the reward is non-zero alter the member and reward pool info.
		member.last_recorded_reward_counter = current_reward_counter;
		reward_pool.register_claimed_reward(pending_rewards);

		T::Currency::transfer(
			&bonded_pool.reward_account(),
			member_account,
			pending_rewards,
			// defensive: the depositor has put existential deposit into the pool and it stays
			// untouched, reward account shall not die.
			Preservation::Preserve,
		)?;

		Self::deposit_event(Event::<T>::PaidOut {
			member: member_account.clone(),
			pool_id: member.pool_id,
			payout: pending_rewards,
		});
		Ok(pending_rewards)
	}
