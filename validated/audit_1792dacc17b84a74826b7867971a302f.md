### Title
Reward rate change in `update_cost_per_block` retroactively applies to already-elapsed, unpaid block spans, causing over/under-payment of consensus relayer rewards - ([File: modules/pallets/consensus-incentives/src/lib.rs])

### Summary
`pallet-consensus-incentives::update_cost_per_block` mutates `StateMachinesCostPerBlock` directly with no interaction with the pending, unrewarded block span (`LastRewardedHeight` watermark vs. the state machine's `latest_commitment_height`). When the next consensus proof is delivered and `calculate_reward` runs, it multiplies the *entire* unpaid block span (`latest_height - baseline`) by whatever `cost_per_block` happens to be stored *at claim time*, not the rate(s) that were actually in effect while those blocks accrued. This is the same root-cause pattern as the reported `update_reward_config` bug in Hubble Farms: a rate parameter is changed without first "checkpointing"/settling the value already accrued under the old rate.

### Finding Description
The reward formula is `Reward = (LatestHeight - Baseline) * CostPerBlock`, where `Baseline` is `LastRewardedHeight` (or `previous_commitment_height` if unset) [1](#0-0) . `CostPerBlock` is read fresh from storage at the moment a relayer's proof is processed, via `StateMachinesCostPerBlock::<T>::get(state_machine_id)` [2](#0-1) .

`update_cost_per_block` simply overwrites this map entry with no settlement step:

```rust
pub fn update_cost_per_block(
    origin: OriginFor<T>,
    state_machine_id: StateMachineId,
    cost_per_block: <T as pallet_ismp::Config>::Balance,
) -> DispatchResult {
    T::IncentivesOrigin::ensure_origin(origin)?;
    StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
        *maybe_cost = Some(cost_per_block);
    });
    ...
}
``` [3](#0-2) 

There is no read/settlement of the currently accruing (unrewarded) block span before the rate is swapped. Concretely:

1. `CostPerBlock` for chain X is set to `R1`. A relayer submits a consensus proof advancing `latest_commitment_height` from `H0` to `H1`, but the reward-triggering `on_executed`/`StateMachineUpdated` event processing has not yet run for that advance (e.g., the message is queued, processed in a later block, or the relayer simply hasn't yet delivered a second/triggering proof — `process_message` is only invoked when a `ConsensusMessage` executes) [4](#0-3) .
2. Governance calls `update_cost_per_block` to change the rate to `R2` for chain X — an ordinary configuration update, not malicious, e.g. to correct pricing or react to gas cost changes.
3. The next relayer to deliver *any* qualifying consensus message for chain X triggers `calculate_reward`, which computes `(H1 - Baseline) * R2` — i.e., the entire span of blocks that accrued while `R1` was in effect gets paid out (or under-paid) at `R2`. `LastRewardedHeight` only tracks *height*, not the rate that applied to each sub-span, so once the rate is changed, all subsequent claims for that state machine's unpaid backlog use the new rate.

This is directly analogous to the reported `update_reward_config` flaw: `reward_per_share`/`reward_per_second` is swapped and `last_issuance_ts` reset without settling/accruing rewards for the elapsed time under the old rate first.

### Impact Explanation
If `R2 > R1` (rate increase), the treasury (`TreasuryAccount`) pays out more `$BRIDGE` than the accrued backlog was actually priced for at the time it was earned — an unbacked/inflated payout that drains the treasury faster than intended, and correspondingly over-mints the 1:1 reputation asset (`ReputationAsset::mint_into`) used for collator-selection weighting [5](#0-4) . If `R2 < R1` (rate cut), relayers who already did the honest work of watching and proving the source chain across the old-rate span are underpaid relative to the economics they operated under, which is a fund-loss issue for those relayer operators. Because the backlog can span an arbitrary number of blocks (there is no forced "settle before rate change" checkpoint), the magnitude of the mispriced payout is unbounded by design and scales with how long a chain's proofs go unclaimed before a rate change.

### Likelihood Explanation
`update_cost_per_block` is a normal, expected operational lever (per the pallet's own docs, "used to set or update the reward cost per block") [6](#0-5) , so governance will call it in the ordinary course of operating the network (e.g., adjusting rewards for gas-price changes on a given chain). Any relayer backlog (delay between successive `StateMachineUpdated` reward triggers for a state machine) combined with a rate change in between deterministically produces the mispriced payout — no attacker collusion or malicious governance intent is required, only an ordinary rate update landing while a reward span is outstanding. Likelihood is high because the flaw is triggered by routine parameter maintenance, and reachable end-to-end via a permissionless, unsigned `pallet_ismp::handle_unsigned` consensus-message submission from any relayer, exactly the kind of unprivileged message-dispatcher path in scope.

### Recommendation
Before mutating `StateMachinesCostPerBlock` in `update_cost_per_block`, force settlement of the currently accrued-but-unpaid span for that `state_machine_id` at the *old* rate (e.g., snapshot `latest_commitment_height` vs. `LastRewardedHeight`, pay/checkpoint that span, advance `LastRewardedHeight` to the current latest height) before writing the new `cost_per_block`. Alternatively, store a history of `(effective_height, cost_per_block)` pairs and compute `calculate_reward` as a sum over rate-segments intersecting `[Baseline, LatestHeight]`, so no single flat rate is misapplied across a span that spans a rate change.

### Proof of Concept
1. Governance calls `update_cost_per_block(state_machine_id = X, cost_per_block = R1 = 100)`.
2. Chain X advances from height `H0` to `H1 = H0 + 1000` on Hyperbridge's consensus client, but no relayer has yet triggered a rewarding `ConsensusMessage`/`StateMachineUpdated` event for the full span (e.g., due to relayer downtime or batching) — `LastRewardedHeight` remains at `H0`.
3. Governance calls `update_cost_per_block(state_machine_id = X, cost_per_block = R2 = 10000)` — a 100x rate hike, done as an ordinary, well-intentioned adjustment (e.g. reacting to a spike in the source chain's gas costs going forward).
4. A relayer submits any consensus proof for chain X that triggers `on_executed`/`process_message`. `calculate_reward` computes `reward = (H1 - H0) * R2 = 1000 * 10000`, paying out 100x more `$BRIDGE` from `TreasuryAccount` than was priced for the 1000-block backlog that actually accrued under `R1`, and minting 100x the intended `ReputationAsset` to that relayer [7](#0-6) .
5. The treasury is drained by the mispriced amount, and the relayer's reputation-asset balance (used in collator selection) is inflated far beyond what the actual 1000-block relay contribution warrants — the reverse (rate cut) instead underpays honest relayers for work already performed under the higher rate.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
