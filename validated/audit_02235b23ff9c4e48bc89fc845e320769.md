## Analysis

The OpenQ report's bug class is: **a permissionless actor supplies an attacker-controlled token into a shared pool of funds, then uses a token-level lockup mechanism (blacklist) to permanently block a critical operation (`claimBounty`) for all users who share that pool.** The Raydium AMM has a structural analog to this: pool creation is permissionless via `Initialize2`, and the coin/pc mints are entirely attacker-chosen, but the program only validates the **LP mint's** freeze authority — never the freeze authority of the actual **coin_mint / pc_mint** that back the vaults. [1](#0-0) 

That check only guards the internally-minted LP token. The `coin_mint` and `pc_mint` — supplied directly by whoever calls `Initialize2` — are unpacked and used to create vaults with no analogous freeze-authority validation: [2](#0-1) [3](#0-2) 

Because SPL Token's `freeze_authority` on a mint lets the authority freeze **any** token account of that mint — including accounts it doesn't own — an attacker can create a custom SPL token with themselves as freeze authority, use it as `coin_mint` (or `pc_mint`) when calling `Initialize2` to permissionlessly stand up a new pool, seed it with the required non-zero initial liquidity, and then freeze the pool's own `amm_coin_vault` (or `amm_pc_vault`) token account at will. Once frozen, every SPL Token `Transfer`/`Burn` CPI touching that vault fails, so `Deposit`, `Withdraw`, `SwapBaseIn/Out`, `SwapBaseInV2/OutV2`, and `WithdrawPnl` all revert permanently for that pool — freezing any LP funds (including honest LPs who added liquidity into the same pool) with no recovery path, since the freeze authority is solely the attacker's. [4](#0-3) [5](#0-4) 

This mirrors the OpenQ root cause precisely: the program whitelists/validates one side of the token relationship (LP mint / whitelisted tokens) but omits the same validation on the attacker-reachable side (coin_mint/pc_mint / non-whitelisted funding tokens), letting an unprivileged actor weaponize a blacklist/freeze mechanism to permanently DoS fund movement for a shared resource.

### Title
Missing freeze-authority check on coin_mint/pc_mint in `Initialize2` allows permanent freezing of pool vaults - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` checks that the LP mint has no freeze authority [6](#0-5)  but never performs the same check on `amm_coin_mint_info`/`amm_pc_mint_info`, which are fully attacker-controlled inputs to this permissionless instruction.

### Finding Description
Anyone can call `Initialize2` to create a new AMM pool by supplying arbitrary `coin_mint`/`pc_mint` accounts along with the initial liquidity [7](#0-6) . The processor unpacks these mints and creates PDA-owned vault token accounts for them [2](#0-1) [3](#0-2) , but performs zero validation of `mint.freeze_authority` for either mint — unlike the LP mint, which is explicitly checked [1](#0-0) .

If an attacker mints a custom SPL token retaining `freeze_authority`, then uses it as `coin_mint` when initializing a pool, they can later call `spl_token::instruction::freeze_account` (a standard SPL Token instruction available to any freeze authority holder, requiring no cooperation from the AMM program) directly on the `amm_coin_vault`/`amm_pc_vault` token account. All AMM token-moving instructions rely on `spl_token::instruction::transfer`/`burn` CPIs against that same vault [4](#0-3) , which the SPL Token program will reject once the account is frozen. There is no mechanism in the AMM program to unfreeze the vault or otherwise recover, since only the mint's freeze authority (the attacker) can do so.

### Impact Explanation
Once frozen, `Deposit`, `Withdraw`, `SwapBaseIn/Out`, `SwapBaseInV2/OutV2`, and `WithdrawPnl` all fail for that pool because each performs a token transfer against the frozen vault [5](#0-4) . Any LP tokens minted against that pool by any other user become permanently unredeemable and any coin/pc funds already deposited are permanently locked in the vault — matching the "permanent freezing of user or LP funds" impact class.

### Likelihood Explanation
This requires only a single unprivileged transaction: pool creation via `Initialize2` with a self-controlled malicious mint (permissionless, no admin signer required for this path) followed by a standard `freeze_account` instruction against the vault at any later time. No validator collusion, off-chain component, or privileged key is needed — it is fully reachable from an ordinary user flow (pool creation + funding + swap/LP), matching the allowed threat model (unprivileged pool creator).

### Recommendation
In `process_initialize2`, after unpacking `coin_mint` and `pc_mint`, add the same freeze-authority check that already exists for the LP mint:
```rust
if coin_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
if pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```

### Proof of Concept
1. Attacker creates SPL mint `M` with `freeze_authority = attacker`.
2. Attacker calls `Initialize2` using `M` as `coin_mint` and any standard token as `pc_mint`, funding the pool with the minimum required liquidity [8](#0-7) ; `process_initialize2` succeeds because it never inspects `coin_mint.freeze_authority`.
3. A victim LP deposits liquidity into the pool via `Deposit`, or a swapper swaps into/out of the pool.
4. Attacker submits `spl_token::instruction::freeze_account` against `amm_coin_vault` using their freeze authority over mint `M`.
5. All subsequent `Deposit`, `Withdraw`, `SwapBaseIn/Out`, and `WithdrawPnl` calls on this pool revert at the `token_transfer`/`token_burn` CPI step [4](#0-3) , permanently locking the victim's LP position and any pool funds.
