### Title
Address-squatting via unsigned lamport transfer blocks legitimate `CreateAccount`/`CreateAccountWithSeed` for deterministically-derivable addresses - ([File: programs/system/src/system_processor.rs])

### Summary
`SystemInstruction::CreateAccount` and `CreateAccountWithSeed` fail with `AccountAlreadyInUse` whenever the target account already holds lamports, but any user can pre-fund an arbitrary, not-yet-created address with a single unsigned-recipient `Transfer` before the legitimate owner creates it there, since transfers to a `to` account require no signature from that account.

### Finding Description
`create_account` in `system_processor.rs` rejects account creation as soon as the target already has lamports: [1](#0-0) 
The only bar to reaching that state is a plain lamport transfer, and `transfer`/`transfer_verified` never require a signature from the recipient (`to_account_index`) — only the `from` (sender) account must sign: [2](#0-1) 
Addresses used with `CreateAccount`/`CreateAccountWithSeed` (e.g. stake accounts, nonce accounts, associated-token-style accounts) are frequently deterministic and computable from public information via `Pubkey::create_with_seed(base, seed, owner)`, as done throughout the CLI (`cli/src/stake.rs`, `cli/src/nonce.rs`, `cli/src/wallet.rs`): [3](#0-2) [4](#0-3) 
Because the derived address can be computed by anyone who knows the victim's base pubkey (or a well-known seed), an attacker can send 1 lamport to that address before the victim's `CreateAccount(WithSeed)` transaction lands. This is exactly analogous to the reported bug class: a user-controlled, unauthenticated value (here, a lamport transfer to an unclaimed address) is allowed to seed a "uniqueness" check (`AccountAlreadyInUse`) that a subsequent honest, legitimate request must satisfy, and the honest actor has no way to know in advance that the slot/key has been squatted.

Agave itself has already acknowledged this class of issue: `SystemInstruction::CreateAccountAllowPrefund` (SIMD-0312, feature `create_account_allow_prefund`) was introduced specifically to let a "to" account that already carries pre-funded lamports still be treated as creatable, bypassing the zero-lamports check: [5](#0-4) [6](#0-5) 
This confirms the pre-funding griefing vector is real and was mitigated only for callers who adopt the new instruction. The legacy `CreateAccount`/`CreateAccountWithSeed` paths — still used throughout the CLI stake/nonce/wallet code and by most existing on-chain and off-chain integrations — remain fully exposed.

### Impact Explanation
An attacker who knows a victim's base pubkey and an intended seed (both public/predictable, e.g. well-known seeds like `"stake"`, or a seed the attacker can infer/brute-force from common wallet conventions) can permanently block that specific derived address from ever being created via `CreateAccount`/`CreateAccountWithSeed`, since the account will forever have `lamports > 0`, triggering `SystemError::AccountAlreadyInUse`. This is a denial-of-service against the victim's ability to instantiate a specific deterministic account (stake account, nonce account, escrow-with-seed account, etc.), forcing them to choose a different seed/address or adopt `CreateAccountAllowPrefund` if their integration supports it.

### Likelihood Explanation
High. The attack costs only the minimal transfer amount (as low as 1 lamport) plus network fees, requires no special privilege, no signature from the victim, and can be executed by any unprivileged user against any address whose derivation parameters (base + seed + owner) are public or guessable — consistent with the "malicious user can prevent other users" bug class described in the report.

### Recommendation
For workflows relying on deterministic account addresses, prefer `CreateAccountAllowPrefund` once available/activated, or have callers explicitly account for pre-funded balances (as `create_account_allow_prefund` already does) rather than treating any nonzero lamport balance as proof of "already in use." Where `CreateAccountAllowPrefund` cannot yet be adopted, documentation/tooling should warn integrators that seed-derived addresses are griefable and encourage randomized/secret seeds rather than well-known or easily-inferable ones.

### Proof of Concept
1. Victim intends to create a stake account at `addr = create_with_seed(victim_base_pubkey, "my-seed", stake::program::id())`, following the pattern in `cli/src/stake.rs` `process_create_stake_account`.
2. Attacker, knowing `victim_base_pubkey` and the seed (public or guessable), independently computes the same `addr`.
3. Attacker submits a plain `SystemInstruction::Transfer` sending 1 lamport to `addr` — no signature from `addr` is required per `transfer`/`transfer_verified`.
4. Victim submits `CreateAccountWithSeed` targeting `addr`; `create_account` sees `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, permanently blocking creation at that address.

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}
