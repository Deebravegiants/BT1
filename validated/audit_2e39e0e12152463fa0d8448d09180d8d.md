Audit Report

## Title
Missing role-based access control on `GET /v2/external_initiators` exposes External Initiator `AccessKey`/`OutgoingToken` to any authenticated user - (File: core/web/router.go)

## Summary
The `v2Routes` route table registers `GET /v2/external_initiators` with only base session/token authentication, while the sibling `POST`/`DELETE` routes for the same resource are wrapped in `auth.RequiresEditRole`. `ExternalInitiatorsController.Index` serializes every stored external initiator via `presenters.ExternalInitiatorResource`, which includes `AccessKey` and `OutgoingToken` fields, so any authenticated user — including the lowest-privilege `view` role — can read these values via this endpoint.

## Finding Description
`authv2.GET("/external_initiators", paginatedRequest(eia.Index))` has no role wrapper, unlike `authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))` and `authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))`. [1](#0-0) 

`ExternalInitiatorsController.Index` loads all external initiators from `BridgeORM().ExternalInitiators` and maps each to `presenters.NewExternalInitiatorResource(initiator)`, then returns them via `paginatedResponse`. [2](#0-1) 

`ExternalInitiatorResource` includes `AccessKey` and `OutgoingToken` in its JSON output. [3](#0-2) 

`RequiresEditRole` and `RequiresRunRole` block `view`-role (and, for edit, `run`-role) users from reaching a handler, but since `Index` has neither wrapper, only base authentication (`AuthenticateByToken`/`AuthenticateBySession`) applies, so any authenticated role — including `view` — can call it. [4](#0-3) 

However, `AuthenticateExternalInitiator` requires both `AccessKey` and `Secret` (compared as a salted hash against `HashedSecret`). [5](#0-4)  The `Secret`/`HashedSecret` is never returned by `Index` — it only appears in `ExternalInitiatorAuthentication`, which is returned solely by `Create` at creation time, not by `Index`. [6](#0-5) [7](#0-6)  Therefore, leaking `AccessKey` alone from `Index` is **not** sufficient to forge `AuthenticateExternalInitiator` requests or escalate to `UserRoleRun` — the constant-time comparison of the hashed secret still blocks an attacker who only knows `AccessKey`.

The `OutgoingToken` field is also exposed by `Index`, but no code path was found (bridges, webhook services, or router) demonstrating how this token is consumed to authenticate a privileged action — a grep across `core/services/webhook` found no references to `OutgoingToken`, and its actual verification/consumption point could not be located.

## Impact Explanation
The confirmed impact is: a `view`-role user (least privilege) can read every external initiator's `Name`, `URL`, `AccessKey`, and `OutgoingToken` — data that a `RequiresEditRole`-guarded sibling endpoint implies should be edit-restricted. This is real over-exposure of configuration/identifier data and a broken symmetry in access control between `Index`, `Create`, and `Destroy` for the same resource. However, the report's stated impact — that this allows privilege escalation to trigger job runs via `AuthenticateExternalInitiator`, or replay of outgoing callback secrets — is not substantiated by the code reviewed: `AuthenticateExternalInitiator` requires the `Secret` as well as the `AccessKey`, and the `Secret`/`HashedSecret` is never returned by `Index`. The `OutgoingSecret` (the more sensitive of the outgoing pair) is likewise never exposed by `Index`. No functioning exploit path from `AccessKey`/`OutgoingToken` disclosure to unauthorized job-run triggering or fund movement was demonstrated.

## Likelihood Explanation
Reaching the endpoint requires only a valid authenticated session/token of any role (including `view`), which is realistic in any multi-user deployment. But because the leaked fields (`AccessKey`, `OutgoingToken`) are not, by themselves, sufficient credentials to authenticate as the external initiator or move funds, the concrete exploitable impact required by the in-scope categories (node API authentication/role bypass resulting in unauthorized run/fund movement, or credential exfiltration sufficient for impersonation) is not established.

## Recommendation
Wrap `GET /v2/external_initiators` with `auth.RequiresEditRole` (or `RequiresRunRole`) to restore symmetry with `Create`/`Destroy`, and independently confirm/trace how `OutgoingToken` is consumed to determine whether its disclosure alone enables impersonation of outgoing callbacks — that trace could not be completed with the available tooling.

## Proof of Concept
1. Create two users: one `admin`, one `view` (`POST /v2/users`, `PATCH /v2/users`).
2. As `admin`, `POST /v2/external_initiators` to register an initiator; note the response contains `Secret`/`incomingSecret` (only shown once).
3. As the `view` user, `GET /v2/external_initiators` — observe `accessKey` and `outgoingToken` are returned despite the `view` role.
4. Attempt to use the leaked `AccessKey` alone (without `Secret`) against an endpoint using `AuthenticateExternalInitiator` (e.g., trigger a webhook job run) — observe it fails, because `Secret`/`HashedSecret` is required and was never leaked, confirming the access-control gap discloses non-critical identifiers but does not by itself enable job-run forgery.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// ExternalInitiatorAuthentication includes initiator and authentication details.
type ExternalInitiatorAuthentication struct {
	Name           string        `json:"name,omitempty"`
	URL            models.WebURL `json:"url"`
	AccessKey      string        `json:"incomingAccessKey,omitempty"`
	Secret         string        `json:"incomingSecret,omitempty"`
	OutgoingToken  string        `json:"outgoingToken,omitempty"`
	OutgoingSecret string        `json:"outgoingSecret,omitempty"`
}

// NewExternalInitiatorAuthentication creates an instance of ExternalInitiatorAuthentication.
func NewExternalInitiatorAuthentication(
	ei bridges.ExternalInitiator,
	eia auth.Token,
) *ExternalInitiatorAuthentication {
	var result = &ExternalInitiatorAuthentication{
		Name:           ei.Name,
		AccessKey:      ei.AccessKey,
		Secret:         eia.Secret,
		OutgoingToken:  ei.OutgoingToken,
		OutgoingSecret: ei.OutgoingSecret,
	}
	if ei.URL != nil {
		result.URL = *ei.URL
	}
	return result
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}
