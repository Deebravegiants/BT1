Audit Report

## Title
Unscoped `savedCallbacks` map keyed only by attacker-controlled `MessageID` allows cross-user response hijacking in the WebAPI trigger gateway handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` stores the caller's response `handlers.Callback` in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageID`, with no ownership check or sender-scoping before the write, unlike the newer v2 handler which explicitly rejects duplicate in-flight request IDs. Since the gateway currently has no allowlist/sender-authorization gate in this path (explicitly marked with a `// TODO: apply allowlist and rate-limiting here` comment), any party able to submit a validly-signed legacy message can supply a `MessageID` matching another in-flight request and silently overwrite that entry, redirecting the eventual node response to the attacker's callback and orphaning the victim's.

## Finding Description
`HandleLegacyUserMessage` unconditionally overwrites any existing entry with the caller's new callback: [1](#0-0) 

There is no uniqueness/ownership check performed before this write, in contrast to `TODO: apply allowlist and rate-limiting here` left directly above the method-check logic in the same function, confirming allowlisting is not yet implemented on this path: [2](#0-1) 

`MessageID` is attacker-controlled and only constrained by length/null-terminator checks in `Message.Validate()`, not bound to sender identity: [3](#0-2) 

When a node later responds with `MethodWebAPITrigger` for that `MessageID`, the gateway looks up and delivers to whichever callback currently occupies the key, then deletes it — there is no check that the responding node's answer actually corresponds to the original caller: [4](#0-3) 

By contrast, the newer v2 `httpTriggerHandler.setupCallback` explicitly rejects a request whose ID is already in flight, demonstrating this exact gap was identified and fixed in the newer code path but not backported to the legacy handler: [5](#0-4) 

The existing test suite for this handler explicitly notes the gap is unresolved: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`: [6](#0-5) 

Requests reach `HandleLegacyUserMessage` from `gateway.ProcessRequest`, which only validates message structure/signature format via `msg.Validate()` (signature must be well-formed and verifiable, but any self-generated ECDSA keypair suffices — no allowlist check on `Sender` is performed at this layer either): [7](#0-6) 

## Impact Explanation
This is a cross-user response confusion / gateway request impersonation vulnerability: an attacker with only a self-generated signing key (no special privileges) can cause another user's workflow-trigger response to be delivered to the attacker's own callback while denying the legitimate response to the original caller. Depending on payload contents, this can leak business-sensitive `web_api_trigger` response data across callers and disrupt availability of correct responses for victims. This maps to the in-scope "gateway request impersonation / cross-user response corruption" impact category.

## Likelihood Explanation
Exploitability requires only sending a validly-signed (self-signed, no special permission needed) legacy gateway message with a chosen `MessageID`, and winning a race by resubmitting the same ID while a victim's request is in flight (feasible given the up-to-120s `CallbackMaxAgeSec` default window and no rate limiting/allowlisting currently enforced in this code path, as confirmed by the in-code TODO). No node access, admin role, or host access is required — only reachability to the gateway's public HTTP endpoint.

## Recommendation
Scope `savedCallbacks` (and lookups against it) by both sender identity and `MessageID` (e.g., a composite key like `globalID{sender, id}` already used in `core/services/gateway/handlers/common/requestcache.go`), and/or reject requests whose `MessageID` is already in-flight, mirroring the check in `httpTriggerHandler.setupCallback`. Apply the outstanding allowlist/rate-limiting TODO in `HandleLegacyUserMessage`.

## Proof of Concept
1. Attacker sends a `web_api_trigger` legacy message to the gateway with a self-chosen `MessageID = "X"`, validly signed with an attacker-controlled key.
2. Victim independently (or concurrently) sends a `web_api_trigger` legacy message with the same `MessageID = "X"`.
3. Both requests flow through `gateway.ProcessRequest` → `HandleLegacyUserMessage`; whichever call's `h.savedCallbacks["X"] = &savedCallback{...}` executes last (handler.go:412) silently overwrites the other's entry — no uniqueness check exists.
4. When a DON node later responds for `MessageID = "X"` via `handleWebAPITriggerMessage` (handler.go:148-161), the response is delivered to whichever callback currently occupies `"X"`, potentially the attacker's, regardless of which caller's request produced it.
5. A Go unit test extending `handler_test.go` can demonstrate this: issue two `HandleLegacyUserMessage` calls with identical `MessageID` from different signers, then call `HandleNodeMessage` with a `MethodWebAPITrigger` response for that ID, and assert that only the second caller's callback receives the response while the first's channel times out.
