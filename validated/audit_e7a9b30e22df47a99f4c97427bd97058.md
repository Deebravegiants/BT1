### Title
Local `signup_reason` value substituted for actual backend enrollment verification result in user-centric signup path - ([File: src/plans/mod.rs])

### Summary
The reported bug class is: a "raw"/pre-processed value (`_amount`) is stored into a persisted field (`stake.amount`) instead of the actual post-processing value (`stakedAmount`), causing the recorded state to diverge from what was truly validated/processed. The closest reachable analog in orb-core is in `MasterPlan::do_signup`, where for user-centric signups the recorded `enrollment_status` (and thus signup `success`) is derived purely from the orb's locally computed `signup_reason` instead of from the actual backend enrollment/verification result that is obtained via `enroll_user::Plan::run` (which calls `signup_post`/`signup_poll` against the backend).

### Finding Description
In the non-user-centric path, `success` is determined by actually calling the backend: [1](#0-0) 
which invokes `enroll_user::Plan::run`, which posts the signup to the backend and polls `signup_poll::request` until the backend reports `Completed`/`success: true`, i.e. the stored success/enrollment status reflects a value verified by the backend.

However, when `user_centric_signup` is true (a flag that comes from `orb_qr_link::UserData`, ultimately controlled by data returned to `verify_user_qr_code`/`backend::user_status::request`) and `ignore_user_centric_signups` is not set, the code takes a different branch: [2](#0-1) 
Here `enrollment_status` is set to `Success` or `Error` purely based on the orb’s own `signup_reason` (computed from local `pipeline`/`fraud_detected` results) — the backend `enroll_user` submission/poll cycle is skipped entirely. This mirrors the audited bug: the value ultimately recorded (`enrollment_status`/`success`) is not the “actual” value that would come from confirming with the source of truth (backend signup verification), but a locally-derived stand-in value, analogous to storing the pre-fee `_amount` instead of the truly processed `stakedAmount`.

`report_signup_reason` and `result.success` then propagate this locally-derived status as the final signup verdict: [3](#0-2) 

Additionally, `fraud_check.rs` shows that in this build the actual fraud detection logic used to compute `signup_reason` has been stripped (`N_FRAUD_CHECKS = 0`, `fraud_checks()` returns `[]`), and `detect_fraud` in `plans/mod.rs` unconditionally returns `Ok(false)`: [4](#0-3) [5](#0-4) 
So for the user-centric signup path, `signup_reason` will essentially always be `Normal` (fraud is never detected, and it only becomes `Failure` if the pipeline itself failed), meaning `enrollment_status` is stored as `Success` without any backend-side confirmation that the signup was legitimately accepted (e.g. not a duplicate, not blocked, not fraud-flagged server-side).

### Impact Explanation
This causes the orb to record and act on a locally-fabricated "success" state for user-centric signups rather than the actual authoritative backend verification outcome. Because `result.success` (used for UI feedback, DBus `signup_finished` signal, and Datadog success metrics) is derived from this potentially incorrect stored status, a signup could be reported/treated as successfully enrolled even though the backend never confirmed or could have rejected it (duplicate, fraud, inflight match). This is a state-integrity/misattribution issue directly in the signup-authorization pipeline: the recorded signup outcome does not match the value that should have been authoritative (backend enrollment result), a discrepancy of the same class as the audited "wrong amount stored" bug.

### Likelihood Explanation
This path is reachable whenever the backend marks a QR code's `user_centric_signup` flag as true (an unprivileged, user-driven QR/app configuration value fetched during ordinary signup flow) and the orb's `ignore_user_centric_signups` config is not enabled. Given that fraud detection in this build is entirely disabled/stubbed, `signup_reason` will trivially be `Normal` for nearly every completed capture+pipeline, making the mis-derived "Success" status the common outcome rather than an edge case.

### Recommendation
For the `user_centric_signup` branch, do not synthesize `enrollment_status`/`success` solely from the local `signup_reason`. Instead, still perform (or otherwise obtain) an authoritative backend confirmation of the signup outcome before marking `enrollment_status` as `Success`, mirroring the non-user-centric path's reliance on `enroll_user::Plan::run`'s backend-polled result.

### Proof of Concept
1. Configure a user QR-code/backend response so that `authenticated_app_data.user_centric_signup == true` (as seen in `backend::user_status::UserData::user_centric_signup`, `src/backend/user_status.rs` lines 44-49).
2. Complete a biometric capture/pipeline successfully so `pipeline.is_some()`.
3. Since `detect_fraud` always returns `false` (`src/plans/mod.rs` lines 1390-1406) and `fraud_check::Report::fraud_checks()` is empty (`src/plans/fraud_check.rs` lines 10-21, 64-114), `signup_reason` resolves to `SignupReason::Normal`.
4. In `do_signup`, because `user_centric_signup` is true, `debug_report.enrollment_status(enroll_user::Status::Success)` is set directly (`src/plans/mod.rs` lines 639-645) without ever calling `enroll_user::Plan::run`/`signup_post`/`signup_poll` against the backend.
5. `result.success` becomes `true` and is reported to UI/DBus/Datadog as a successful signup even though no backend confirmation of acceptance (e.g., duplicate/fraud check on server side) ever occurred.

Note: I was unable to fully trace how `ignore_user_centric_signups` is toggled operationally (only its declaration site in `src/config.rs` was located, not its runtime configuration source), so the exact conditions under which this branch is reached in production versus overridden should be verified further if pursuing remediation.
