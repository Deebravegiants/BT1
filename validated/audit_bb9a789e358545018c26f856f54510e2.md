### Title
`cookie_session_id` returns the raw `shopify_app_session` cookie value verbatim, unauthenticated, as a session lookup key - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.current_session_id` / `cookie_session_id` treat whatever value is present in the `shopify_app_session` cookie as an authoritative session ID with no cryptographic verification. Since offline session IDs are deterministically derived as `"offline_#{shop}"` [1](#0-0) , and the cookie set by the gem after OAuth is just that raw string with no signature or MAC attached [2](#0-1) , any client can forge the cookie for a known/target shop domain and have it accepted as their own session ID.

### Finding Description
Binding claimed: `session_id == bytes authenticated under Context.api_secret_key`. Actual: `session_id == cookies["shopify_app_session"]`, taken verbatim with no HMAC/JWT check.

Path: `current_session_id(shopify_id_token, cookies, online)` — when the app is non-embedded, or embedded without an id token supplied for the call, it falls straight to `cookie_session_id(cookies)` [3](#0-2) , which just does `cookies[SessionCookie::SESSION_COOKIE_NAME]` [4](#0-3) . There is no signature, HMAC, or JWT validation anywhere in this path — contrast with the embedded/id-token path, which does go through `Auth::JwtPayload.new(id_token)` and thus benefits from `aud`/signature verification [5](#0-4) .

The cookie value itself, as produced by this gem in `Oauth.validate_auth_callback`, is literally `session.id` (e.g. `"offline_shop.myshopify.com"`) written into a `SessionCookie` struct with no MAC/signature attached by the gem [2](#0-1) . Offline session IDs are fully deterministic: `offline_session_id(shop) = "offline_#{shop}"` [1](#0-0) , and `shop` (the `*.myshopify.com` domain) is public information, not a secret.

Attacker request: send `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` with no `Authorization`/id-token header to any endpoint of a non-embedded app (or an embedded app route that doesn't require the id-token path) built on this gem. `current_session_id` returns `"offline_victim-shop.myshopify.com"` verbatim [6](#0-5) . The host app then uses this string to load a `Session` from its `SessionStorage` implementation, retrieving the victim shop's stored offline access token, and proceeds to make Admin API calls on the attacker's behalf using the victim's credentials.

Why existing guards don't stop this: `HmacValidator.validate` and the OAuth `state` check in `validate_auth_callback` only protect the OAuth callback exchange itself, not subsequent session lookups via the cookie [7](#0-6) . `JwtPayload`'s `aud`/signature check only applies to the id-token branch, which this attack deliberately avoids by omitting the header. `Context.embedded?`/`private?` only route which branch is used, they don't add verification to the cookie branch [6](#0-5) . Sorbet typing only enforces `String`/`Hash` shapes, not provenance/authenticity of the value.

### Impact Explanation
Cross-tenant access: an attacker who knows or guesses a victim's `*.myshopify.com` domain (public) can, without ever compromising `api_secret_key` or the victim, cause a vulnerable app to look up and use the victim's stored offline access token on their behalf. This is directly enabled by the gem's own `cookie_session_id`/`current_session_id` API returning an untrusted client-supplied string as if it were an authenticated session identifier. It is repeatable against any shop for which the offline session naturally follows the `offline_#{shop}` convention (the only convention this gem ships), and works for every request as long as the attacker supplies the crafted cookie. This matches "Critical - cross-tenant access."

### Likelihood Explanation
Preconditions: app is non-embedded, or an embedded app's request-handling code path calls `current_session_id`/`cookie_session_id` without an id token (e.g., any route that doesn't enforce App Bridge session tokens). Attacker cost is trivial — set one cookie header with a guessable, deterministic value; no secrets, XSS, or victim interaction required. Feasibility is high because the ID scheme (`offline_#{shop}`) is fixed by this gem and documented; the only unknown is the shop domain, which is typically public/discoverable (app install flows, storefront URLs, etc.).

### Recommendation
Never trust `cookies[SESSION_COOKIE_NAME]` as an unauthenticated session identifier. Bind the cookie value to something verified server-side to the app's own secret (e.g., store a random opaque session key server-side and use it purely as an index into a signed/encrypted session store, or HMAC-sign the cookie value with `Context.api_secret_key` and verify the signature in `cookie_session_id` before returning it). At minimum, document/enforce that the host application must set this cookie via a signed/encrypted mechanism (e.g. Rails `cookies.encrypted`) rather than a plain `Set-Cookie`, and have `cookie_session_id` reject cookies without integrity protection it can itself verify.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (added test)
def test_cookie_session_id_accepts_unauthenticated_attacker_controlled_value
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  forged_shop = "victim-shop.myshopify.com"
  forged_session_id = "offline_#{forged_shop}"
  attacker_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # No shopify_id_token supplied at all - attacker never authenticated with Shopify.
  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, attacker_cookies, false)

  # LHS: unauthenticated, attacker-chosen string
  # RHS: what a genuine, HMAC/JWT-verified caller would have produced
  assert_equal(forged_session_id, returned_id)

  # Demonstrate no verification occurred: value was never checked against
  # Context.api_secret_key via HMAC or JWT signature - it's returned verbatim.
  assert_equal(attacker_cookies[ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME], returned_id)
end
```
This confirms `current_session_id` → `cookie_session_id` returns an attacker-forged, deterministic session ID (`offline_victim-shop.myshopify.com`) with no cryptographic check, which a host app's `SessionStorage.load_session(returned_id)` would then use to fetch the victim's offline token.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end
