### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that are handed to the application's webhook handler as the tenant identity are taken directly from unauthenticated HTTP headers that are never included in the HMAC-signed material. This breaks the equality `hmac-covered-bytes == identity-bytes-trusted-by-handler`, letting anyone who possesses one valid `(body, hmac)` pair (e.g., a legitimate merchant who has installed the app on their own shop and received a real webhook) replay that same body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, causing the app to process the payload as if it belongs to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors instead read directly from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates authenticity using only `Utils::HmacValidator.validate(request)`, i.e., only the body is checked, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that the HMAC over `to_signable_string` (the body) matches, using the app's `api_secret_key` — a secret shared across *all* shops that install the app, not scoped to a specific tenant: [4](#0-3) 

Because the client secret is common to every installation of the app, any user who legitimately has the app installed on their own store can capture a valid `(raw_body, hmac)` pair from their own real webhook deliveries. They can then submit that same pair to the app's webhook endpoint while forging the `shopify-shop-domain` header (and `topic`/`webhook-id` if desired) to name a victim shop. `Registry.process` will pass HMAC validation (body matches) and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop, even though the body was never bound to that shop identity. The equality that should hold — "the shop asserted to the handler equals the shop that produced the HMAC-signed bytes" — does not, because the shop is not part of the signed bytes at all.

### Impact Explanation
If the host application's webhook handler uses `data.shop` from `WebhookMetadata` to select which merchant's session/data to act upon (a common integration pattern, since this is exactly the field this gem surfaces for that purpose), an attacker-controlled tenant can inject or overwrite data attributed to another tenant — a cross-tenant access/data-integrity breach that lands squarely in the Critical impact bucket for cross-tenant access, achieved without any credentials beyond having legitimately installed the app once.

### Likelihood Explanation
Any merchant/developer who installs the target app (a completely unprivileged action available to any internet user for a public app) automatically receives real webhook deliveries with valid `(body, hmac)` pairs signed with the app's single, install-wide `client_secret`. Replaying such a pair with a spoofed `shopify-shop-domain` header requires no additional privilege and no interaction with Shopify's servers — it is a simple direct HTTP POST to the app's own webhook endpoint. This makes the attack straightforward and reliably reproducible for anyone with the ability to install the app once.

### Recommendation
Do not treat the `shop` (and ideally `topic`/`webhook_id`) values as trusted merely because the body's HMAC validates. Options:
- Include the `shop`, `topic`, and `webhook_id` values in the HMAC-signable string so they are cryptographically bound to the signature, or
- Require the consuming application to independently verify that `request.shop` corresponds to a shop with an active, known session/installation before acting on the payload, and document this requirement prominently since the current API surface (`WebhookMetadata#shop`) implicitly suggests it is already authenticated.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (`attacker.myshopify.com`) — this is a normal, unprivileged action any internet user can perform for a public app.
2. Trigger a real webhook delivery for a subscribed topic (e.g., `products/update`) from the attacker's own store; capture the raw request body and the `X-Shopify-Hmac-Sha256` header value exactly as delivered by Shopify — this is a valid `(body, hmac)` pair signed with the app's shared `client_secret`.
3. Replay this exact `body` and `hmac` to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `request.to_signable_string` (the raw body) — the check passes because the body/HMAC pair is genuinely valid, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` alongside the attacker-originated body content, per `lib/shopify_api/webhooks/registry.rb` lines 188-200, despite the payload never having been authenticated as belonging to that shop.
