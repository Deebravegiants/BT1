### Title

Overflow during interest accrual permanently freezes an oversized high-utilization market - (File: common/src/rates/index.rs)

### Summary

XOXNO Lending’s index accrual can hit the `i128` value ceiling before the borrow-index cap is reached when a market holds an extremely large scaled debt balance at sustained high utilization. Once `borrowed.mul(new_borrow_index)` overflows, every subsequent operation that accrues that market reverts with `MathOverflow`, permanently preventing repayment, withdrawal, liquidation, and further index updates.

### Finding Description

`update_indexes` is permissionless and forwards attacker-selected `HubAssetKey` entries to pool accrual through `markets::update_indexes` and `pool_update_indexes_call`. [1](#0-0) [2](#0-1) 

The pool loads each market and calls `interest::global_sync`, which applies bounded time chunks through `accrue_chunk`. [3](#0-2) [4](#0-3) 

Borrow-index growth itself is capped by `update_borrow_index`, but the cap is applied only after computing `old_index.mul(interest_factor)`. [5](#0-4) 

The fatal operation is the subsequent interest split: `calculate_supplier_rewards` computes both `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)` directly in `i128`-backed `Ray` arithmetic. [6](#0-5) [7](#0-6) 

For a sufficiently large market, `borrowed * new_borrow_index` exceeds `i128::MAX` while `new_borrow_index` remains below `MAX_BORROW_INDEX_RAY`, so the protocol raises `GenericError::MathOverflow` instead of clamping the index or bounding the valuation. [8](#0-7) 

The repository already contains a deterministic regression scenario demonstrating this condition: an 18-decimal billion-token market at 98% utilization reaches `MathOverflow` before the index cap, after which both withdraw and repay fail with the same error. [9](#0-8) 

### Impact Explanation

This is a permanent freezing of user funds and a market-level denial of service. Once the state crosses the representable debt-value boundary, every path that first accrues the affected market encounters the same overflow, so suppliers cannot withdraw, borrowers cannot repay, liquidators cannot clear the debt, and keepers cannot repair the market through `update_indexes`. [10](#0-9) 

Because the panic occurs during accounting rather than during an untrusted callback or malformed input decode, a transaction revert does not roll back an earlier corrupted state; it merely confirms that the already-stored scaled balances and elapsed time make all future accrual attempts impossible.

### Likelihood Explanation

The attack requires an extremely large token position and sustained high utilization, so it is capital-intensive rather than a one-call malformed-payload trigger. However, it does not require privileged access, leaked keys, oracle manipulation, contract upgrades, or a third-party failure: the attacker can supply the large asset through `supply`, borrow against separately supplied collateral through `borrow`, leave utilization high, and later trigger accrual through permissionless `update_indexes` or any ordinary market operation. [1](#0-0) 

The severity is therefore bounded by feasibility rather than reachability. If a listed high-decimal asset and configured caps permit scaled balances near the demonstrated range, the condition is deterministic and cannot be bypassed after it is reached.

### Recommendation

Bound or saturate all aggregate debt-value calculations before multiplying scaled shares by the new borrow index. In particular:

- Detect `borrowed * new_borrow_index` overflow before `calculate_supplier_rewards` panics.
- Clamp or saturate the effective accrued-debt value consistently with `MAX_BORROW_INDEX_RAY`.
- Ensure the index cap is enforced early enough that a market cannot retain an index/scaled-debt pair whose aggregate value is unrepresentable.
- Add production invariants that every accrual path remains executable when the borrow index reaches its cap.
- Extend the existing long-horizon regression test into a mandatory coverage case for withdraw, repay, liquidation, `clean_bad_debt`, and `recapitalize`.

### Proof of Concept

1. List or select an asset with high token decimals and caps large enough to accept a billion-scale whole-token position.
2. Supply approximately `1_000_000_000 * 10^18` raw units of the market asset.
3. Supply sufficient separate collateral and borrow approximately 98% of that market’s supplied liquidity.
4. Maintain that high-utilization state while enough ledger time elapses for the configured interest-rate curve to multiply the debt value beyond `i128::MAX`.
5. Call permissionless `update_indexes(caller, vec![HubAssetKey { hub_id, asset }])`.
6. Pool accrual reaches `calculate_supplier_rewards`, where `borrowed.mul(new_borrow_index)` overflows and raises `GenericError::MathOverflow`. [8](#0-7) 
7. Subsequent `withdraw` and `repay` calls fail with the same `MathOverflow` because they perform accrual before changing the position. [10](#0-9)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

    let new_total_debt = borrowed.mul(env, new_borrow_index);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
