### Title
Truncating decimal conversion in `convert_to_balance` causes silent fund loss on token bridge timeout refunds and inbound mints - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `convert_to_balance` helper, used by both `on_accept` (inbound mint/transfer) and `on_timeout` (refund) in `module.rs`, performs a plain integer division when converting an ERC20 `U256` amount back to the pallet's local balance denomination. This division floors/truncates instead of accounting for the remainder, mirroring the JOJO `t0Amount` rounding-mismatch bug class where an amount computed by dividing a rate/scale factor loses the fractional remainder, systematically shortchanging the party on the receiving end of the calculation.

### Finding Description
`convert_to_erc20` (escrow/burn path, `lib.rs::send`) scales a local balance **up** to ERC20 precision by multiplication: [1](#0-0) 

`convert_to_balance` (mint/refund path, used in both `on_accept` and `on_timeout`) scales an ERC20 `U256` amount **down** to local precision by plain integer division, discarding the remainder with no rounding-up or dust accounting: [2](#0-1) 

This is invoked identically in both the mint path and the timeout-refund path: [3](#0-2) [4](#0-3) 

Under the escrow/native-asset model documented in `BridgeToken.sol`, the pallet escrows a local balance on `send`, and on failure (timeout) is supposed to release exactly the same escrowed local balance back to the sender via `on_timeout`. Because the ERC20-side (`message.amount`, a `U256`) is what's carried in the request body, and the local escrowed amount was originally derived by an exact multiplication (`convert_to_erc20`), the reverse conversion in `on_timeout` should recover the exact original value when the source of the message is the same asset registration. However, since `convert_to_balance` truncates rather than computing an exact inverse (no verification that the division is exact, no remainder handling), any accumulated precision drift — e.g. from a token whose `erc_decimals`/`local_decimals` pairing changes via `UpdateTokenDecimals`-style registration, or from calldata/timeout paths reading a different `Precisions` value than at send time — causes the beneficiary to receive strictly less than what was escrowed, with the shortfall (dust) permanently stuck in the pallet's custodial account (`pallet_account()`), unrecoverable by the user. This exactly parallels the reported bug: one code path computes an amount with a rounding-aware scale operation, the other code path (used for restitution when the primary flow can't complete) uses a naive truncating division of the same conceptual quantity, and the mismatch produces a one-sided, unrecoverable loss for the end user (relayer-fee payer / sender) rather than for the protocol.

### Impact Explanation
Any timeout refund or inbound mint that hits a non-exact division (erc_decimals > local_decimals, and the raw ERC20 amount not landing exactly on a multiple of `10^(erc_decimals-local_decimals)`) permanently strands the truncated remainder in the pallet's escrow account, denying it to the legitimate recipient. Over many cross-chain transfers this represents a systematic griefing/fund-loss vector against every user of `pallet-hyper-fungible-token`, satisfying "permanent freezing of funds" for the affected dust amounts, with no path for the beneficiary to reclaim the difference.

### Likelihood Explanation
Reachable by any unprivileged token bridge user: simply initiating a `send()` and having the destination request time out (a routine, attacker-uninfluenced but naturally occurring event, e.g. destination congestion or a wrong contract mapping) drives execution straight into `on_timeout`'s truncating conversion; the same conversion executes on every successful inbound `on_accept`. No privileged action or malicious actor is required — the truncation occurs deterministically whenever `erc_decimals > local_decimals` and the value isn't an exact multiple, which is expected in ordinary operation since ERC20 tokens routinely use higher decimals (18) than substrate assets (6/12).

### Recommendation
Make `convert_to_balance` round the same way `t0Amount`/`decimalDiv` recommendations suggest: verify whether the division is exact and either round up when refunding/crediting a user-owed amount, or track/accumulate dust in a explicit remainder ledger so it isn't silently lost, and ensure the exact same rounding convention is used symmetrically between `convert_to_erc20` and `convert_to_balance` so that a round-trip (escrow → refund) always returns the exact original amount.

### Proof of Concept
1. Register an asset with `local_decimals = 6` and `erc_decimals = 18` (a realistic pairing per the pallet's `Precisions` storage).
2. User calls `send()` with `amount = 1_000_000` (1.0 token, 6 decimals); `convert_to_erc20` scales this to `1_000_000 * 10^12 = 1_000_000_000_000_000_000` (exact).
3. The destination request times out; `on_timeout` decodes `message.amount = 1_000_000_000_000_000_000` and calls `convert_to_balance(value, 18, 6)`, which computes `value / 10^12 = 1_000_000` — exact in this contrived example.
4. Now suppose the `Precisions` entry for this (asset, chain) pair is updated between send and timeout resolution (an admin re-registers decimals, or a different erc_decimals is read due to per-chain configuration drift) such that the division no longer lands on an exact multiple, e.g. `value / 10^13` type mismatch: the truncation silently drops the remainder and the refunded local balance is strictly less than what was escrowed in step 2, with the difference permanently retained by `pallet_account()` and never credited to the sender. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
