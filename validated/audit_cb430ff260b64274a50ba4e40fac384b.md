### Title
FeesOnly cost model uses `RollbackAccounts::data_size()` instead of real loaded bytes, undercounting cost for failed-load transactions - ([File: svm/src/account_loader.rs])

### Summary
When a transaction fails during `load_transaction_accounts` (producing `TransactionLoadResult::FeesOnly`), the `loaded_accounts_data_size` charged to the cost model is set to `RollbackAccounts::data_size()` — i.e. only the fee payer's (and nonce's) account data length — unless the `define_ltds_fee_only_semantics` feature is active, in which case the correctly-tracked `loaded_transaction_data_size` (real bytes touched before failure) is used instead. Under the legacy path, an attacker can write-lock/read-lock many large accounts in a transaction designed to fail account loading only after several large accounts have already been fetched/deserialized, and be charged cost-model units proportional only to the tiny fee-payer/nonce size instead of the real bytes actually loaded.

### Finding Description
`RollbackAccounts::data_size()` sums only the data length of the fee payer and (if present) nonce account: [1](#0-0) 

This value is explicitly documented as being "used internally when calculating the actual loaded transaction data size for the cost model" and is slated for removal "by the fee-payer data size amendment to SIMD-186," acknowledging it is a stopgap/incorrect legacy calculation.

In `load_transaction`, when account loading fails and the transaction becomes `FeesOnly`, the code branches on the `define_ltds_fee_only_semantics` feature flag: [2](#0-1) 

- If the feature is active: `loaded_accounts_data_size` = `loaded_transaction_data_size.into()`, which is accumulated incrementally as real accounts are loaded/inspected during `load_transaction_accounts` (see `LoadedTransactionDataSize::increase_calculated_data_size`) — i.e., it reflects the true bytes touched up to the point of failure.
- If the feature is **not** active (legacy semantics): `loaded_accounts_data_size` = `tx_details.rollback_accounts.data_size()`, which only reflects the fee payer (+ nonce) account bytes, completely ignoring any other (potentially large) accounts that were fetched from accounts-db and deserialized before the load failed.

This `loaded_accounts_data_size` flows through `ProcessedTransaction::loaded_accounts_data_size()` [3](#0-2)  into the commit result and ultimately into `CostModel::calculate_cost_for_executed_transaction`'s `actual_loaded_accounts_data_size_bytes` parameter, which drives `calculate_loaded_accounts_data_size_cost` [4](#0-3) . This is the page-based CU cost charged for the transaction's account-data footprint against the block cost limit.

Exploit flow: an attacker constructs a transaction that references several large, write- or read-locked accounts (up to the requested `loaded_accounts_data_size_limit`) and is engineered to fail during `load_transaction_accounts` for a reason unrelated to those large accounts (e.g. an account-not-found/invalid-owner condition on an account processed after the large ones, or any other loading-stage error that doesn't abort before the large accounts are fetched). Under legacy semantics, the resulting `FeesOnly` outcome is charged cost-model units based only on the fee payer's tiny account size, not the bytes of the large accounts that were actually read and deserialized from accounts-db during the failed load. Repeating this transaction lets the attacker consume real account-loading I/O/CPU work while only paying (and only counting against block cost limits) for the fee payer's small footprint.

None of the existing guards (signature checks, nonce validation, fee-payer balance checks, or the loaded-accounts-data-size limit checked during loading) prevent this, because the limit check itself uses the same incrementally-tracked `loaded_transaction_data_size` for enforcement — the discrepancy only affects what gets reported/charged to the cost model/cost tracker for the already-failed transaction, not whether the load succeeds.

### Impact Explanation
This falls into "materially underpriced execution / spam vector at fee-only cost" — an attacker can repeatedly force real account-loading work (fetching and deserializing multiple potentially large accounts from accounts-db) while the cost-model/cost-tracker accounting attributes only the fee-payer's small size to the transaction. This can let such transactions consume more of the leader's actual account-loading budget than their tracked cost-model contribution reflects, undermining the cost model's per-block resource-bounding invariant for `FeesOnly` transactions specifically.

### Likelihood Explanation
Reachable by an unprivileged user constructing a normal transaction that: (1) is guaranteed to hit an account-loading failure (`TransactionLoadResult::FeesOnly`) rather than an execution failure, and (2) references large accounts that get processed before the failure point. This requires no special privileges — just crafting account lists/ALTs and instructions to trigger a load-stage error after several other accounts are touched. The condition is entirely feature-gated: the bug only manifests while `define_ltds_fee_only_semantics` is inactive on a given cluster/validator. Determining whether that feature is currently active on mainnet-beta could not be confirmed from the code alone (only its presence in `feature-set/src/lib.rs` was found); this is the primary source of uncertainty in assessing current-day exploitability.

### Recommendation
Ensure `define_ltds_fee_only_semantics` is activated cluster-wide so the `FeesOnly` path always uses the incrementally-tracked `loaded_transaction_data_size` (real bytes touched before failure) rather than `RollbackAccounts::data_size()`. Once activated everywhere, `RollbackAccounts::data_size()` and its legacy branch in `load_transaction` should be removed entirely, as the code comments already indicate is planned.

### Proof of Concept
Rust unit test in `svm/src/account_loader.rs` (or a fuzz/invariant test) comparing charged size vs. real size across `FeePayerOnly`/`SameNonceAndFeePayer`/`SeparateNonceAndFeePayer` variants when `define_ltds_fee_only_semantics` is disabled:

```rust
#[test]
fn test_fees_only_undercounts_loaded_accounts_data_size_legacy_semantics() {
    // Build a transaction with:
    //  - a small fee payer account
    //  - several large (e.g. 10KB) additional accounts that ARE loaded/inspected
    //    during load_transaction_accounts before the failure is triggered
    //    (e.g. one of the later accounts has an invalid owner / doesn't exist,
    //    causing TransactionError that produces FeesOnly)
    let mut feature_set = SVMFeatureSet::all_enabled();
    feature_set.define_ltds_fee_only_semantics = false; // legacy path

    let load_result = load_transaction(/* ...account_loader with large accounts..., */);

    let TransactionLoadResult::FeesOnly(fees_only_tx) = load_result else {
        panic!("expected FeesOnly result");
    };

    // Real bytes touched during the failed load (sum of all accounts fetched
    // before the failure, tracked independently in the test harness).
    let real_bytes_touched = /* sum over all accounts read via mock accounts-db */;

    // Assert the invariant that SHOULD hold but doesn't under legacy semantics:
    // charged size must upper-bound real work performed.
    assert!(
        fees_only_tx.loaded_accounts_data_size as usize >= real_bytes_touched,
        "cost-model charge ({}) undercounts real bytes touched ({})",
        fees_only_tx.loaded_accounts_data_size,
        real_bytes_touched,
    );
}
```

Expected result: the assertion fails under `define_ltds_fee_only_semantics = false`, demonstrating `fees_only_tx.loaded_accounts_data_size == RollbackAccounts::data_size()` (fee payer only) is far smaller than `real_bytes_touched` (fee payer + large accounts loaded before failure), confirming the undercounting. The same test with the feature enabled should pass, since `loaded_transaction_data_size` correctly accumulates all touched bytes.

    // loaded transaction data size for the cost model. This function will be removed by

    pub(crate) fn data_size(&self) -> usize {
        let mut total_size: usize = 0;
        for (_, account) in self.iter() {
            total_size = total_size.saturating_add(account.data().len());
        }
        total_size
    }
