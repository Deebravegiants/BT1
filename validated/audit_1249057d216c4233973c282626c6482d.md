### Title
Emporium min-proof path lets an attacker self-authorize `EmporiumStack.ops` that drain any token balance held by `EmporiumUpgradeable` with zero on-chain accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` / `contracts/CircomDataBuilder.sol` / `contracts/Hinkal.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp` and `calldataHash` [1](#0-0) . Because `erc20TokenAddresses` is empty, both `Hinkal.transact`'s balance/slippage-verification loop and `EmporiumUpgradeable.runAction`'s own `balancesBefore`/`balancesAfter` accounting loop iterate zero times, so no equality is ever checked between what the ops moved and what the proof/circuit claims [2](#0-1) [3](#0-2) . With `EmporiumStack.signerAddress == address(0)`, `verifyWallet` skips all EIP-712 signature checks entirely [4](#0-3) , so the attacker fully controls `stack.ops`, which are executed as `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract's own identity (`msg.sender == Emporium`) [5](#0-4) .

### Finding Description
The invariant that should hold is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and validated against `slippageValues`/`amountChanges` in `Hinkal.transact`)**. This invariant is broken on the min-proof path.

Path traced:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` [6](#0-5) .
2. Attacker sets `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, causing `formInputEmporiumMin` to be used, whose only public inputs are `emporiumMessage`, `timeStamp`, `calldataHash` [7](#0-6) . This circuit does not constrain `amountChanges`, tokens, nullifiers, or `EmporiumStack` contents at all - `emporiumMessage` is simply required to equal `Poseidon(messageSeed)`, a value fully chosen by the attacker.
3. Because `erc20TokenAddresses` is empty, `_externalTransact`'s `deltaAmountChanges` array is empty, so no deposit/withdraw accounting happens before `runAction` is invoked [8](#0-7) .
4. In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed over the same empty `erc20TokenAddresses` array, so they are empty arrays and the post-loop check (`balanceChange < 0` revert, UTXO creation) never executes for any real token [3](#0-2) .
5. `verifyWallet(stack, circomData)` is called with attacker-supplied `stack.signerAddress == address(0)`; it marks `emporiumMessage` used and returns immediately without any signature check [4](#0-3) .
6. The `for (uint256 i = 0; i < stack.ops.length; i++)` loop then executes attacker-chosen `op.endpoint.call{value: op.value}(op.callData)` (`CASE 2`, since `invokeWallet && signerAddress != 0` is false) with `msg.sender == address(EmporiumUpgradeable)` [9](#0-8) . An attacker can set `op.endpoint` to any ERC20 token that the Emporium contract holds a balance of (e.g., tokens parked there from prior deposits, partial fills, or unclaimed relay fees) and `op.callData` to `transfer(attacker, balance)`, or chain multiple such calls across multiple tokens in one `ops` array.
7. Back in `Hinkal.transact`, the post-action balance/slippage-check loop at lines 97-147 iterates over `circomData.erc20TokenAddresses`, which is still empty, so it enforces nothing about the tokens actually drained [10](#0-9) .

No existing guard catches this: `performHinkalChecks` only validates the `CircomData` hash integrity, relay validity, dimension/onchain-creation checks, none of which constrain `EmporiumStack.ops` contents or tie them to `erc20TokenAddresses` [6](#0-5) . `verifyProof`/`buildVerifierId` select a verifier keyed on `dimensions.tokenNumber`/`externalActionId`, but the min-circuit's public inputs never reference tokens or ops. `rootHashExists` only checks the shielded root, unrelated to this path. Consequently, the equality "assets moved == assets accounted" fails: real ERC20/ETH balances of Emporium change, but zero entries in `balancesBefore/After`, `deltaAmountChanges`, `amountChanges`, or `slippageValues` reflect it.

### Impact Explanation
Any unprivileged attacker can drain any ERC20/ETH balance held by the `EmporiumUpgradeable` contract (funds parked there from other users' deposits, partial-fill swaps, unclaimed relay fees, or in-flight operations) directly to their own address, in a single transaction, with a trivially self-generated ZK proof (only requires knowing `messageSeed` such that `Poseidon(messageSeed) == emporiumMessage`, which the attacker picks themselves) and no valid EIP-712 signature. This is repeatable for every token/asset resting in the Emporium contract and matches **Critical - direct theft of shielded or in-flight user funds**.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: no privileged role, no signature, no relay cooperation is required. The attacker only needs (a) the Emporium contract to hold a nonzero balance of some token (a normal operational state given deposits/partial fills/fee flows through Emporium), and (b) a locally generated proof for the trivial min-circuit (message = Poseidon(self-chosen seed)). The attacker cost is one transaction plus gas; the exploit is fully repeatable against any balance the contract accumulates over time.

### Recommendation
- Do not allow the Emporium min-proof path (`erc20TokenAddresses.length == 0`) to execute `stack.ops` that make arbitrary external calls; either require `erc20TokenAddresses`/`amountChanges` to be constrained by the circuit even on the min path, or forbid `ops` execution entirely unless per-token accounting (`balancesBefore/After`) covers every `op.endpoint` involved.
- Require `stack.signerAddress != address(0)` (i.e., always require a valid EIP-712 signature) whenever `ops` contains any call, removing the unauthenticated `signerAddress == 0` bypass in `verifyWallet`.
- Make the `Hinkal.transact` balance-conservation invariant unconditional: assert that the aggregate token balance change of the Emporium contract across the whole action, for all tokens actually touched by `ops`, is zero-sum against `amountChanges`/`deltaAmountChanges`, rather than only checking tokens explicitly listed in the (attacker-supplied, possibly empty) `erc20TokenAddresses` array.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as an allowed recipient/external action), and a mock verifier registered for the min-circuit `verifierId` that always returns `true` for the reduced public-input vector (`emporiumMessage`, `timeStamp`, `calldataHash`).
2. Fund `EmporiumUpgradeable` with `1000` mock ERC20 tokens (simulating parked balance from a prior legitimate operation).
3. Attacker (non-owner EOA) builds `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []`, and `externalActionMetadata` ABI-encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: mockToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))}]}`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA with a proof accepted by the mock verifier.
5. Assert: `mockToken.balanceOf(attacker)` increases by `1000e18` and `mockToken.balanceOf(Emporium)` goes to `0`, while `circomData.slippageValues`/`amountChanges`/`balancesBefore`/`balancesAfter` arrays remain empty throughout - i.e., prove the equality "assets moved by Emporium == assets accounted in balancesBefore/After" is `1000e18 != 0`, confirming unaccounted theft.

        CircomData calldata circomData,
        Dimensions calldata dimensions,

            (circomData.originalSender == address(0) &&
                circomData.relay != address(0)) ||
                (circomData.originalSender == sender &&

        );

        require(
            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,

        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
    }
