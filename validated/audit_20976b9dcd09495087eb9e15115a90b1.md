### Title
Webhook shop domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity by HMAC-signing only the raw request body, while the `shop` identity used by the handler is read from an unauthenticated HTTP header. Any shop that has installed the app can capture one of its own genuine webhook deliveries (valid body + HMAC, both signed with the app's single, shared `client_secret`) and replay it against the host application's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to a victim shop. The signature still validates because the header is not part of the signed data, causing the host app to process attacker-supplied data under another tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is parsed independently from a header that is never mixed into the signed payload: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates `to_signable_string`, i.e. the body) before handing `request.shop` straight to the handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC only over `verifiable_query.to_signable_string` using `Context.api_secret_key`, i.e. the body, never the shop header: [4](#0-3) 

Because Shopify signs webhooks for *every* shop that has installed a given app with that app's single `client_secret` (there is no per-shop secret), the equality the code implicitly relies on — "HMAC(body) valid ⇒ shop header is trustworthy" — does not hold. The correct binding should be `HMAC(body ‖ shop ‖ topic) valid ⇒ (body, shop, topic) are all authentic`, but the shop (and topic) fields are excluded from the signed material entirely.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers. A malicious or compromised merchant who has installed the app can trigger any webhook event on their own store (or capture one previously received), then replay the exact same body/HMAC pair to the app's webhook endpoint with the shop-domain header rewritten to a victim shop. `WebhookMetadata.shop` will report the victim's domain, and any handler logic keyed off `data.shop` (looking up per-shop settings, associating incoming data/PII with the victim's tenant record, triggering mandatory GDPR webhooks like `customers/redact` for the wrong shop, etc.) will act as if the victim shop sent the data. This is a cross-tenant confusion vulnerability reachable by any unprivileged merchant/internet user who can install the app on a store and capture a webhook.

### Likelihood Explanation
Likelihood is high: no access token, API key, or `client_secret` is required — only the ability to install the app on any shop (or observe traffic to any endpoint receiving genuine webhooks from that app) and resend an HTTP request with one header changed. The HMAC computation, header parsing, and dispatch code path are unconditionally exercised by `ShopifyAPI::Webhooks::Registry.process`, which is the gem's documented entrypoint for webhook handling.

### Recommendation
Include the tenant-identifying fields (`shop`/`shop-domain`, and ideally `topic`) in the signable string used by `Utils::HmacValidator`, or otherwise cryptographically bind them to the payload before dispatch, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```
so `HmacValidator.validate` fails whenever the shop header has been altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook (e.g. `orders/create`) to receive a legitimate request with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, and the raw JSON body.
2. Replay the identical raw body and `x-shopify-hmac-sha256` value to the host application's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and matches successfully (the same `Context.api_secret_key` is used for all shops of the app).
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` with attacker-controlled body content, despite the request never having been generated by or for `victim.myshopify.com`.
