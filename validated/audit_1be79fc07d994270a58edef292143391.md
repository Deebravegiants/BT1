### Title
Webhook `shop` domain is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop` attribute — the tenant identity handed to the host application's webhook handler — is read from an HTTP header that is never included in that signable string. An unprivileged attacker who controls any Shopify store (a free dev/partner store is available to anyone) can obtain a genuine, validly-signed webhook for their own shop and then replay the identical body/HMAC pair to the victim app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will report success because it only checks bytes actually covered by the HMAC (the raw body), and `Webhooks::Registry.process` will pass the attacker-chosen `shop` straight through to the app's `handle` callback as if it were authenticated.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` to build the signed material [4](#0-3) . For webhook requests, `to_signable_string` returns just `@raw_body` [1](#0-0) ; the `shop` accessor pulls straight from the `shopify-shop-domain` header without any cryptographic binding to the HMAC [2](#0-1) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and on success immediately builds `WebhookMetadata` using `request.shop`, which is delivered to the app-supplied handler as the trusted tenant identifier [3](#0-2) . The equality the library implicitly promises but fails to enforce is:

`shop attributed to the webhook (request.shop, used by the handler) == shop whose secret produced the HMAC (implicitly, the body's origin shop)`

Because the HMAC covers only the body, this equality is never checked. Any attacker who can get one genuinely-signed webhook body (trivial: install the target app, or any app using this gem, on their own store and capture a webhook delivery) can flip the `shop` header for that same body+HMAC pair to any victim shop domain, and the gem will treat it as authentic.

### Impact Explanation
This breaks the tenant boundary the gem is documented and relied upon to enforce: `ShopifyAPI::Webhooks::Registry.process` is the sole authentication gate host apps use before trusting `data.shop` (per `docs/usage/webhooks.md`) [5](#0-4) . Any application logic keyed off `data.shop` — looking up per-shop settings, writing records, deduplicating by shop, triggering mandatory compliance topics like `shop/redact`/`customers/redact` — can be fed attacker-controlled shop attribution alongside attacker-controlled body content, producing cross-tenant data corruption/confusion. This matches the Critical "cross-tenant access" impact category, since it lets one unprivileged tenant (their own store) inject events attributed to a different tenant.

### Likelihood Explanation
Likelihood is high: the attacker needs no privileged credentials, only their own (or any) Shopify shop to legitimately trigger a webhook and capture the raw body + `X-Shopify-Hmac-Sha256` value, then a single crafted HTTP replay with a modified shop-domain header against the target app's public webhook endpoint. No secret key, access token, or TLS interception is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or independently verify `shop` against the shop actually associated with the delivering webhook subscription (e.g., cross-check against a known/registered shop, or validate the domain format and provenance via Shopify's IP allowlist as a defense-in-depth measure). At minimum, `Webhooks::Request#to_signable_string` should not be the sole basis for trusting `shop`; the gem should document, or enforce, that `shop` is only as trustworthy as the raw body it validates and require callers to independently confirm shop identity before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target (or any) app using `shopify_api` on their own store `attacker.myshopify.com` and triggers a subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — both are legitimately signed with the app's real `api_secret_key`.
2. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the same app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header into `shop` [2](#0-1) ; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the request never having been sent by Shopify on behalf of `victim-shop.myshopify.com` [7](#0-6) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
