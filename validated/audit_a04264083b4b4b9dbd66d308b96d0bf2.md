### Title
Webhook `shop` attribution is not bound to the HMAC signature, enabling cross-tenant webhook replay/spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but the `shop` value used to attribute an inbound webhook to a specific merchant is read from a header that is completely outside the signed content. Any party that can obtain one valid `(raw_body, hmac)` pair for a topic (e.g. from their own shop, where they are a legitimate but unprivileged tenant of a multi-tenant app) can replay that exact HTTP payload to the app's public webhook endpoint while substituting the `shop-domain`/`x-shopify-shop-domain` header, and the library will accept it as an authentic webhook for the victim shop.

### Finding Description
`HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw body: [2](#0-1) 

The `shop` accessor used everywhere downstream simply echoes back an unauthenticated HTTP header: [3](#0-2) 

`Registry.process` validates only the body-based HMAC and then dispatches `request.shop` directly to the app's handler as the authoritative tenant identity: [4](#0-3) 

The identity binding that should hold is:

`shop_bound_by_hmac == shop_delivered_to_handler`

but in fact `shop_bound_by_hmac` does not exist at all — the HMAC only proves `raw_body` was produced with the app's shared secret; it says nothing about which shop the body belongs to. Because the secret (`Context.api_secret_key`) is shared across every shop that has the app installed (it is not per-tenant), any tenant of the app can generate a legitimately-signed `(raw_body, hmac)` pair for their own shop by triggering a webhook-eligible event, then submit that exact body+hmac to the app's public webhook endpoint with a forged `shop-domain` header pointing at a victim shop. `Utils::HmacValidator.validate` still returns `true` (the body/hmac pair is untouched and valid), and `Registry.process` will hand the attacker's body to the handler tagged with the victim's shop, achieving cross-tenant confusion.

### Impact Explanation
This breaks tenant isolation in a multi-tenant Shopify app built on this gem: any single tenant (a legitimate but unprivileged installer of the app) can inject attacker-controlled webhook payloads that the app processes as belonging to a different, victim merchant. Depending on how the app's webhook handlers use `WebhookMetadata#shop`/`#body` (e.g. updating records keyed by shop, triggering `customers/redact`/`shop/redact` GDPR flows, or driving business logic), this can lead to cross-tenant data corruption, unauthorized state changes attributed to another shop, or spoofed mandatory compliance webhooks — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) being any single legitimate tenant able to trigger one real webhook delivery for their own shop, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (which is unauthenticated by design and reachable by any internet user). No access to `api_secret_key`, access tokens, or any privileged account of the target shop is required — only ordinary use of the app as its own customer. The library provides no API or guidance to bind `shop` into the verified bytes, so any host application relying on `HmacValidator.validate` + `request.shop` inherits this gap by construction.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shop-domain` header to the verified payload before trusting it in `WebhookMetadata`.
- At minimum, document and/or enforce that `request.shop` must be cross-checked by the host application against the shop that is expected to own the topic/registration, and reject webhooks whose header-provided shop does not match a shop known to have that webhook registered.
- Consider deriving `shop` from validated body content (where Shopify includes it, e.g. GDPR payloads) rather than solely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` (ordinary, unprivileged tenant onboarding).
2. Attacker triggers any webhook topic they've subscribed to (e.g. `orders/create`) with attacker-controlled body content (order note, custom attributes, etc.), and captures the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — this pair is valid because it is genuinely signed by Shopify with the app's shared `api_secret_key`.
3. Attacker sends a forged HTTP POST directly to the app's public webhook endpoint, reusing the exact `raw_body` and `hmac` header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` returns `true` because `raw_body` is untouched.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON> ...)`, and the app processes attacker data as if it originated from `victim-shop.myshopify.com`.
