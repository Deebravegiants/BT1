## Analysis

The referenced Wild Credit bug is a "promise more tokens out than are actually available" pattern: `liquidateAccount` computes a payout and transfers it via `_safeTransfer` without verifying the contract's actual token balance covers it, so the whole liquidation reverts whenever real, non-malicious external conditions (tokens lent out) reduce the on-hand balance below the promised amount.

The same root-cause pattern exists in `WrappedHyperFungibleToken.send()`: [1](#0-0) 

Compare this with `IntentGatewayV2.placeOrder`, where the developers explicitly account for the fee-on-transfer discrepancy by diffing before/after balances and mutating the recorded amount to the **actually received** amount: [2](#0-1) 

`WrappedHyperFungibleToken.send()` has no such adjustment — it locks tokens with `safeTransferFrom(msg.sender, address(this), params.amount)` but then encodes and dispatches the cross-chain `Message` using the **requested** `params.amount`, not the tokens actually received/held. Any underlying ERC20 with fee-on-transfer, deflationary, or rebasing behavior causes the contract's real balance to fall below the sum of amounts it has promised to unlock across all in-flight and refundable transfers. When a legitimate delivery (`onAccept`) or timeout refund (`onPostRequestTimeout`) later tries to pay out the full promised amount via `safeTransfer`, it can revert for lack of sufficient underlying balance: [3](#0-2) [4](#0-3) 

### Title
Promised-but-unbacked payout in `WrappedHyperFungibleToken.send()` can permanently strand cross-chain unlocks/refunds - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks an underlying ERC20 via `safeTransferFrom` but dispatches the cross-chain message using the caller-requested `params.amount` instead of the amount actually received/held by the contract. For any underlying token that does not transfer 1:1 (fee-on-transfer, deflationary, rebasing), this creates a permanent shortfall between what the contract owes across all outstanding locks and what it actually holds — mirroring the audited `LendingPair.liquidateAccount` bug where a payout function assumes, but never verifies, that the contract holds enough of the underlying asset to fulfill it.

### Finding Description
In `send()`, the contract transfers `params.amount` of `_underlying` from the caller into itself, then unconditionally builds the dispatch message body with that same requested `params.amount`: [5](#0-4) [6](#0-5) 

If `_underlying` charges a transfer fee, burns a percentage, or is rebasing downward, the contract's actual balance increase is strictly less than `params.amount`, yet the destination-chain peer contract (or a later timeout refund on this same chain) is told the full `params.amount` was locked and will attempt to release/refund that full amount later:
- On delivery to a remote peer: the remote `HyperFungibleToken`/`WrappedHyperFungibleToken` mints/unlocks the full `params.amount` that was promised, exceeding actual collateral locked here.
- On timeout: `onPostRequestTimeout` calls `IERC20(_underlying).safeTransfer(refundee, message.amount)` for the original, unadjusted amount, which the pool may no longer hold once other transfers have similarly under-collateralized it.

This is structurally identical to the audited bug: a function that pays out (or promises) tokens equal to a logical accounting value without verifying/limiting to the contract's real, available balance of that token. `IntentGatewayV2.placeOrder` demonstrates that the maintainers are aware of and specifically guard against this exact fee-on-transfer discrepancy elsewhere in the codebase (measuring `balBefore`/`balAfter` and mutating `order.inputs[i].amount`), but the same defensive pattern was not applied in `WrappedHyperFungibleToken.send()`.

### Impact Explanation
Because the wrapper is a shared custody pool for one underlying token across potentially many registered peer chains, a single unprivileged `send()` call with an under-collateralizing underlying token degrades the pool's real-balance-to-promised-liability ratio permanently. Once enough such transfers accumulate (or even a single transfer if the fee is significant), subsequent legitimate `onAccept` unlocks or `onPostRequestTimeout` refunds for *other, unrelated users* can revert for insufficient balance, freezing their funds indefinitely — since there is no fallback (e.g., pro-rata payout or minting an IOU) analogous to what the Wild Credit fix recommended. This is a fund-freezing / insolvency-risk condition reachable by any user simply calling the permissionless `send()` entrypoint.

### Likelihood Explanation
Likelihood depends on the wrapper being configured (by its owner, via `configure()`) with a non-standard ERC20 as `_underlying` (fee-on-transfer, deflationary, or rebasing token) — a deployment/configuration choice, not an attacker action, matching the "external requirements" caveat noted by the original Wild Credit finding. Given the proliferation of such tokens and that the contract advertises generic "existing ERC20 tokens" support without excluding this class, this is a realistic misconfiguration/edge case rather than a purely theoretical one.

### Recommendation
Mirror the fix already used in `IntentGatewayV2.placeOrder`: measure the actual balance delta (`balanceOf(address(this))` before/after `safeTransferFrom`) in `WrappedHyperFungibleToken.send()`, and use that actual-received amount (not `params.amount`) both for the locked accounting and for the `Message.amount` encoded in the dispatched request. Optionally also reject configuring `_underlying` as a fee-on-transfer/rebasing token via an on `configure()`-time balance-invariant check.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer ERC20 that takes, e.g., a 1% fee on every transfer.
2. User A calls `send({ amount: 1000, ... })`. `safeTransferFrom` pulls 1000 from A but the contract's balance only increases by 990 (10 taken as fee). The dispatched `Message.amount` is still `1000`.
3. The remote peer mints/credits 1000 to the destination-chain recipient, or — if the message times out — `onPostRequestTimeout` attempts `safeTransfer(A, 1000)`.
4. If any other user's balance was already tight, or if this is repeated across several fee-charging transfers, the pool's real balance falls below the sum of amounts owed. A later `onAccept`/timeout `safeTransfer` call reverts with insufficient balance, permanently blocking that unlock/refund for its rightful owner while the pool cannot cover it — the direct analog of `LendingPair.liquidateAccount` reverting when the pool's real underlying balance is insufficient to cover the promised payout.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
