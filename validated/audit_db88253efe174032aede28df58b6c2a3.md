### Title
Webhook shop identity spoofing — HMAC signature covers only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the tenant-identifying `shop-domain` header is read separately and never included in what is signed. `Registry.process` validates the HMAC and then trusts the unauthenticated `shop` header to build the `WebhookMetadata` handed to the app's business logic, breaking the binding `shop authenticated == shop the app acts on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` verify the HMAC strictly against `verifiable_query.to_signable_string`, i.e., the body bytes, with the secret key: [2](#0-1) 

But `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) come from HTTP headers that are entirely outside the signed payload: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-vs-hmac), then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and dispatches it to the app's handler as the tenant identity for that event: [4](#0-3) 

Because the `shop-domain` header is not covered by the HMAC, a valid `(raw_body, hmac)` pair generated by Shopify for a webhook legitimately delivered to *any* shop (including a shop the attacker fully controls, e.g., their own free/dev store) remains cryptographically valid regardless of which `shop-domain` header is attached to the replayed request. An unprivileged internet user who controls a Shopify store with the target app installed can:
1. Trigger a webhook delivery to their own store (e.g., `app/uninstalled`, which they fully control the timing/occurrence of) and capture the raw body + `X-Shopify-Hmac-Sha256` value.
2. Replay that exact body and HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with the victim's shop domain.
3. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes against the HMAC, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`.

Equality broken: `shop authenticated by HMAC` (none — HMAC only binds body) `≠` `shop delivered to the app's handler as the tenant scope` (attacker-chosen header).

### Impact Explanation
This is a cross-tenant identity spoofing primitive at the webhook boundary: the app is architected to trust `WebhookMetadata#shop` as the authenticated tenant for that event (this is the gem's documented contract — see `lib/shopify_api/webhooks/registry.rb` `process`), but the value is not actually bound by the cryptographic signature the gem validates. Depending on how the host app uses the webhook `shop` field (e.g. `app/uninstalled` clearing a tenant's stored session/access token, `customers/redact` or `shop/redact` erasing another tenant's data, or any handler keyed by `shop` for authorization decisions), an attacker who controls one shop can forge events attributed to a different, victim shop. This falls under cross-tenant access impact.

### Likelihood Explanation
Requires only an unprivileged attacker with a store where the target app is installed (freely obtainable via a Shopify dev/partner store) plus the ability to replay an HTTP request with a modified header — no access token, secret key, or privileged account is needed. The signature check as implemented provides no defense against this replay because the header is simply outside its scope.

### Proof of Concept
1. Install the target app (built on this gem) on an attacker-owned Shopify store `attacker.myshopify.com`.
2. Trigger a webhook (e.g. uninstall the app, or any subscribed topic) and capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` value sent to the app's webhook endpoint.
3. Resend the identical body and HMAC header to the same endpoint, replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only `topic`, `hmac-sha256`, and `shop-domain` presence is checked, not content binding): [5](#0-4) 
5. `Utils::HmacValidator.validate(request)` returns `true` since it only checks the body bytes.
6. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...))`, causing the app to act as though the event came from the victim shop.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable content in `Request#to_signable_string`, or otherwise require the host application to cross-validate `request.shop` against an independently-authenticated source (e.g., the shop associated with the app's own webhook registration/subscription id) before trusting it as the tenant scope.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
