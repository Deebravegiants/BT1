### Title
Tron `IntentGatewayV2.placeOrder` trusts the shared `CallDispatcher`'s ambient balance instead of a before/after delta, letting anyone donate to or drain the dispatcher to corrupt escrow/dust accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the predispatch escrow flow reads `IERC20(token).balanceOf(dispatcher)` / `address(dispatcher).balance` directly as the ground truth for "amount produced by the predispatch swap," where `dispatcher` is `_params.dispatcher` — a single, persistent contract shared by every order placed through the gateway, whose `dispatch()` entry point has no access control. This is the same bug class as the reported `USSDRebalancer.getSupplyProportion` issue: an externally-fundable balance is read and used unmodified in downstream arithmetic and fund-movement decisions.

### Finding Description
`placeOrder` resolves the shared dispatcher once per call: [1](#0-0) 

then, after executing the user-supplied predispatch calldata, it reads the dispatcher's raw balance to decide how much to sweep and whether the order can proceed: [2](#0-1) 

`balance` here is `IERC20(token).balanceOf(dispatcher)` (or `dispatcher.balance` for native token) — the dispatcher's absolute, ambient balance at that instant — not a measured delta of tokens actually produced by this order's predispatch call. The same `dispatcher` address is reused for every order (also used by `_execute` for postdispatch sweeps): [3](#0-2) 

and `CallDispatcher.dispatch` itself has no access control at all — any address can invoke it to move whatever balance the dispatcher currently holds: [4](#0-3) 

The non-Tron implementation was hardened against exactly this class of issue by snapshotting the gateway's own balance before the sweep and computing `received` as a delta, rather than trusting the dispatcher's absolute balance for anything but the sweep amount: [5](#0-4) 

The Tron variant never took this fix: it uses the raw `balanceOf(dispatcher)` both as the pass/fail gate (`balance < requiredAmount`) and as the swept amount, and computes `dust = balance - requiredAmount` from that same unguarded read: [6](#0-5) 

Because `dispatcher` is a single fixed, public address reused across all orders and its `dispatch()` function is callable by anyone, any unprivileged party can affect what `balanceOf(dispatcher)` returns at the moment a victim's `placeOrder` transaction executes — either by donating tokens directly to it, or by invoking `dispatch()` themselves to move whatever the dispatcher currently holds. This mirrors the report's root cause precisely: a contract's own accounting logic treats an externally-influenceable `balanceOf`/native-balance read as authoritative input to fund-movement and gating decisions.

### Impact Explanation
- The `balance < requiredAmount` revert guard, meant to ensure the predispatch call actually produced enough of the input token, can be bypassed by a third party topping up the dispatcher, silently masking predispatch calls that produced less output than declared.
- Because the full ambient `balance` (not merely the amount the order's own predispatch call generated) is what gets swept via `transferCalls[i]` into the gateway and reported via `DustCollected`, any token sitting on the shared dispatcher for unrelated reasons (donation, incomplete prior sweep, accidental transfer) is misattributed to whichever `placeOrder` call happens to read it next, corrupting the dust/fee accounting the protocol relies on to compute what it has actually collected versus escrowed.
- Combined with `CallDispatcher.dispatch()` having no access control, the dispatcher functions as an unauthenticated shared pot: any balance it holds outside the atomic bounds of a single `placeOrder`/`fillOrder` call can be redirected by anyone.

### Likelihood Explanation
Exploitation requires only an ERC-20 `transfer()` (or a direct, unauthenticated `dispatch()` call) to a publicly known, fixed contract address, and is reachable by any unprivileged actor who observes a pending `placeOrder` transaction that uses predispatch — no special privileges, governance, or trusted role required.

### Recommendation
Apply the same fix already present in the non-Tron `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's own balance immediately before dispatching the sweep calls, and compute the amount credited to escrow (and any "dust") strictly from the delta of the gateway's own balance before/after the sweep, never from the shared dispatcher's ambient `balanceOf`/native balance. Additionally, restrict `CallDispatcher.dispatch()` to callers that are trusted gateway/app contracts (e.g., an `onlyAuthorizedCaller` modifier) so its balance cannot be manipulated or drained by arbitrary external accounts.

### Proof of Concept
1. Read the public/fixed dispatcher address via `IntentGatewayV2._params.dispatcher` (or observe it in a pending `placeOrder` transaction).
2. Before a victim's `placeOrder(order, graffiti)` call (with `order.predispatch.call` and `order.predispatch.assets` set) is mined, submit a plain `IERC20(token).transfer(dispatcher, X)` donating `token` to the dispatcher.
3. When the victim's transaction executes and reaches: [7](#0-6) 
   `balance` now includes the attacker's donated `X`, so `balance < requiredAmount` may pass even if the predispatch swap alone produced less than `requiredAmount`, and `dust = balance - requiredAmount` (attributed via `DustCollected`) is inflated by the attacker's donation rather than reflecting real predispatch slippage/output — demonstrating that escrow/dust accounting for this order is driven by an externally-fundable shared balance rather than a delta the order itself produced.
