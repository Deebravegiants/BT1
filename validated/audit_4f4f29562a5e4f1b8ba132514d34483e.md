### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/routing identity but are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, while `to_signable_string` returns only `@raw_body` and excludes all headers from the HMAC-verified data. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then dispatches to a handler using the unauthenticated `request.shop` and `request.topic` values.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`. [1](#0-0) 
For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 
Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the signed material: [3](#0-2) 
`Registry.process` validates the HMAC and then immediately trusts `request.topic` (for handler routing) and `request.shop` (as the tenant identity passed to the handler) without any additional binding check: [4](#0-3) 

This is structurally the same class of bug as the reported issue: the security check (HMAC validation / snapshot) covers one set of data (the body / checkpointed holders), but a security-relevant field acted upon afterward (`shop`, `topic` / new holders) is not included in what was verified, allowing the two to be desynchronized. Concretely, the equality that should hold is:

`shop authenticated by HMAC == shop used to attribute/process the webhook event`

but the actual code enforces only `hmac(body) == computed_hmac(body)`, leaving `shop` (and `topic`) fully attacker-controllable independent of the HMAC check.

### Impact Explanation
An attacker who can obtain any single valid `(raw_body, hmac)` pair for the app's registered `client_secret` (e.g., by receiving a legitimate webhook to their own shop's endpoint if they run a proxy, or by intercepting/replaying a webhook they are entitled to receive) can resend that exact body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to another (victim) shop, and/or the `shopify-topic` header changed to another topic. `Utils::HmacValidator.validate` still succeeds because the body is unchanged, and `Registry.process` will route the event to a different handler and/or attribute the payload to a different tenant (`WebhookMetadata.shop`/`topic`), since neither is bound to the verified signature. This risks cross-tenant data confusion or triggering shop-scoped side effects (e.g., app-side per-shop state updates, uninstall/GDPR handling, order processing) under an incorrect shop identity — a cross-tenant impact.

### Likelihood Explanation
Requires the attacker to first obtain one legitimate `(body, hmac)` pair signed with the app's real `client_secret` for a webhook topic they can receive/replay (e.g., a webhook sent for their own shop's installation), then replay it against the same public endpoint with modified `shop-domain`/`topic` headers. No possession of `api_secret_key` or any privileged token is needed for the replay step itself, only the ability to capture one webhook delivery they are legitimately a recipient of — a realistic scenario for any merchant who installs the app.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed material verified by `to_signable_string`, or otherwise cryptographically bind them to the raw body (e.g., verify against Shopify's known shop/topic pairing via a secondary authenticated lookup) before using them to route or attribute the event, mirroring the pattern used for `AuthQuery#to_signable_string`, which does include `shop` in its signed payload. [5](#0-4) 

### Proof of Concept
1. App receives a legitimate webhook for `topic=orders/create`, `shop-domain=attacker-shop.myshopify.com`, with body `B` and a valid `hmac = HMAC-SHA256(client_secret, B)`.
2. Attacker captures this `(B, hmac)` pair (they own `attacker-shop`, so they can legitimately view their own webhook deliveries/logs).
3. Attacker sends a new HTTP request to the app's public webhook endpoint with the same body `B` and same `hmac` header, but with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds (only `B` is checked) — see [6](#0-5)  and [7](#0-6) .
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to act on/attribute order data `B` as if it belonged to `victim-shop`, despite the payload never having been signed for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
