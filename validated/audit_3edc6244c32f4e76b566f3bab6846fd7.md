### Title
LiFi swap fee deducted unconditionally even when `relay == address(0)`, permanently stranding `hinkalFee`/`relayFee` in the action contract - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap` computes `hinkalFee` and `relayFee` from `circomData.feeStructure` and subtracts `totalFee` from `swappedAmount` regardless of whether `circomData.relay` is `address(0)`. When `relay == address(0)` (a legitimate, permissionless self-relay path allowed by `HinkalHelper.relayerIsValid`), `sendToRelay` becomes a no-op, so the computed fee is deducted from the user's credited UTXO but never transferred anywhere — it is permanently stranded as dead balance inside the `LifiExternalAction` contract.

### Finding Description
The broken equality: when `circomData.relay == address(0)`, `amountToSendToHinkal` should equal `swappedAmount` (no fee owed to anyone, matching the pattern in `Hinkal._internalTransact` where `relayFee` is explicitly forced to `0` if `circomData.relay == address(0)`) [1](#0-0) . Instead, `ExternalActionSwap.swap` computes `hinkalFee`/`relayFee` unconditionally and subtracts `totalFee` from `swappedAmount` before crediting the UTXO: [2](#0-1) 

`sendToRelay` (in `Transferer.sol`) is guarded by `relay != address(0)`, so with `relay == address(0)` it silently no-ops instead of returning the fee to the user or reverting: [3](#0-2) 

`HinkalHelper.relayerIsValid` only enforces `tx.origin == relay` and whitelisting when `relay != address(0)`; it places no constraint requiring a relay to be present, so any unprivileged EOA can call `Hinkal.transact` directly with `circomData.relay = address(0)` (self-relay), which is the documented/allowed flow: [4](#0-3) 

Exploit flow (attacker = ordinary swapper, no special privilege needed):
1. Attacker calls `Hinkal.transact` for a LiFi swap action with `circomData.relay = address(0)` and any non-zero `feeStructure.flatFee`/`variableRate` (attacker fully controls `feeStructure` as stated in the question's attacker-controlled fields).
2. `Hinkal._externalTransact` invokes `LifiExternalAction.runAction` → `ExternalActionSwap.swap`.
3. `callRouter` performs the LI.FI swap and returns `swappedAmount`.
4. `hinkalFee`/`relayFee` are computed from `swappedAmount` and `feeStructure`; `sendToRelay(address(0), ...)` no-ops.
5. `amountToSendToHinkal = swappedAmount - totalFee` is transferred to Hinkal and credited as the user's UTXO — `totalFee` worth of tokens remains as an untracked balance sitting in the `LifiExternalAction` contract, forever, since the next call's `balanceBefore`/`balanceAfter` diff in `callRouter` only measures the incremental swap delta and never redistributes the pre-existing residual.

Hinkal's own balance-diff invariant (`balanceDif == amountChanges[i] + utxoAmount`) still holds because the UTXO amount matches exactly what was physically transferred out of the action contract to Hinkal — so there is no UTXO over-crediting relative to what left the action contract. The actual break is that the fee is computed and deducted from the user even though there is no relay to receive it, and the deducted value is not returned to the user or forwarded to any protocol treasury — it becomes permanently locked, unreachable dead balance in `LifiExternalAction`, since no sweep/withdraw function exists on that contract or its base classes (`ExternalActionSwap`, `ExternalActionBaseV2`, `OwnerHinkal`).

### Impact Explanation
Every self-relayed (`relay == address(0)`) LiFi swap silently strands `hinkalFee + relayFee` (a `feeStructure.variableRate`-driven cut of `swappedAmount`, plus `feeStructure.flatFee` if the fee token equals the output token) inside `LifiExternalAction`. This value benefits no party — not the user (who loses it from their credited UTXO), not the relay (none exists), not the protocol (no forwarding or sweep mechanism) — and accumulates unrecoverably with every self-relay swap. This matches "High – theft or permanent freezing of protocol/relay fees": the fee amount is permanently frozen/lost with no path to recovery, and from the user's perspective it is value silently taken from their expected swap output without compensation.

### Likelihood Explanation
Trivial precondition: the attacker only needs to submit a normal, self-relayed LiFi swap (`relay = address(0)`, which is an explicitly supported, permissionless flow per `HinkalHelper.relayerIsValid`), with any nonzero `feeStructure.flatFee`/`variableRate` value that the circuit/off-chain proof generation allows the user to set for their own transaction. No special contracts, hooks, or privileged roles are required. The loss is repeatable on every self-relay swap and scales with swap volume, so it is a systemic, low-cost, always-reachable bug rather than a one-off edge case.

### Recommendation
In `ExternalActionSwap.swap`, gate `hinkalFee`/`relayFee` computation on `circomData.relay != address(0)`, mirroring the pattern already used in `Hinkal._internalTransact`: set both fees to `0` when there is no relay so `amountToSendToHinkal == swappedAmount`, eliminating any stranded balance in the action contract.

### Proof of Concept
Foundry test plan (mock LI.FI router):
1. Deploy `LifiExternalAction` with a mock router returning a fixed `outputToken` amount for a given `inputAmount` call.
2. Whitelist `LifiExternalAction` in Hinkal's `externalActionMap`, deposit input token into a UTXO for the attacker.
3. Build `CircomData` for a swap action with `circomData.relay = address(0)`, `feeStructure.variableRate = 500` (5%), `feeStructure.flatFee = 0`, `feeStructure.feeToken = outputToken`, generate the proof locally.
4. Call `Hinkal.transact`. Assert:
   - `IERC20(outputToken).balanceOf(address(lifiExternalAction))` increases by exactly `hinkalFee` after the call (the stranded fee), i.e. `balanceOf(action) after == balanceOf(action) before + totalFee`.
   - The credited UTXO amount (`utxoSet[0].amount` / `amountToSendToHinkal`) equals `swappedAmount - totalFee`, confirming the user received less than the full swap output while `totalFee` went to neither the user nor any relay.
   - Repeat the swap multiple times and assert the residual balance in `LifiExternalAction` for `outputToken` strictly increases each time with no mechanism to withdraw it (no `onlyOwner` sweep function exists to call).
