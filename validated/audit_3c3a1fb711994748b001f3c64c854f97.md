### Title
Webhook HMAC does not cover the `shop` identity field, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body, while the `shop` value that downstream handlers treat as the authenticated tenant identity is read from a separate, unsigned header. Because the app-level `api_secret_key` is a single shared secret for *all* shops/tenants that install the app (not shop-specific), any party who can obtain one validly-signed webhook body/HMAC pair (e.g. from their own store's install of the app) can replay that exact body to the app's webhook endpoint while forging the `x-shopify-shop-domain` header to name a different, victim shop. The HMAC check still passes because the header is not part of the signed data, and the handler receives `WebhookMetadata` claiming the victim shop.

### Finding Description
The identity binding that should hold is:

```
verified_bytes(HMAC) == bytes_the_handler_trusts_as_tenant_identity
```

In this gem that equality is broken:

- `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 
- `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC input: [3](#0-2) 
- `Registry.process` validates the HMAC over `to_signable_string` via `Utils::HmacValidator.validate(request)`, and only after that check passes, forwards `request.shop` (the unsigned header value) straight into `WebhookMetadata`, which the handler treats as the authenticated shop: [4](#0-3) 
- `Utils::HmacValidator.validate` itself only checks `verifiable_query.to_signable_string` against the received HMAC — it has no notion of a shop-bound value: [5](#0-4) 
- `WebhookMetadata.shop` is documented as "The shop domain of the webhook" and handlers are told to trust it for shop-scoped processing (e.g. enqueueing shop-specific jobs): [6](#0-5) [7](#0-6) 

Unlike the OAuth `AuthQuery`, where `shop` is explicitly included in `to_signable_string` and is therefore bound to the HMAC [8](#0-7) , the webhook `Request` has no equivalent binding for `shop`. This is exactly the "unsafe operation" pattern from the report: a value that is acted upon (here, tenant identity) is not covered by the safety check (here, the HMAC), so a value the attacker fully controls can silently substitute for a value the code implicitly assumes was authenticated.

Because the `api_secret_key` used to sign webhooks is one value per app across every installed shop (this is standard Shopify app architecture, not specific to any one merchant), an attacker who is simply a merchant that has installed the same public/custom app on their own store is "unprivileged" relative to any other merchant using that app, yet possesses a fully valid `(body, HMAC)` pair signed with the very secret that also signs webhooks for every other tenant.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for maintaining: an attacker can cause the host application to process forged webhook data attributed to a shop they do not control, while the HMAC check reports success. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (session/tenant lookup, triggering shop-scoped side effects, cache/queue keys, etc.), this enables cross-tenant data injection/confusion under a passing signature check. This matches the Critical "cross-tenant access" impact category, since the gem's own signature-validation primitive is the mechanism the host app is told to rely on for authenticity, and that primitive does not bind the tenant field.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to already possess one legitimately-signed `(raw_body, hmac)` pair. This is trivial to obtain for any threat actor that is itself a merchant using the target app (a normal, unprivileged relationship to that app) — they simply capture a real webhook Shopify sends to their own store's endpoint, since it is signed with the same app-wide `api_secret_key`. No leaked credentials, TLS interception, or privileged account are required.

### Recommendation
Bind the tenant identity into the value that is actually verified:
- Include the `shop` (and ideally `topic`/`webhook_id`) header values as part of `to_signable_string` for `Webhooks::Request`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into the signed payload, or
- Have `Registry.process` independently re-derive/verify the shop from data that is itself covered by the HMAC (e.g., from the JSON body when available) rather than trusting the header, and document that host applications must not treat `WebhookMetadata#shop` as authenticated unless this binding exists.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint: raw body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker replays a POST to the same endpoint with the identical body `B` and identical `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares it to `H` — this still matches because `B` is unchanged: [9](#0-8) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app processes attacker-controlled webhook content as if it were authentically addressed to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
