This confirms the asymmetry: `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`) explicitly folds `shop` into the signed payload via `URI.encode_www_form`, while `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body` — the `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from unauthenticated headers (`shopify_header`) and are never part of the HMAC input.

### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the HMAC signature only to the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to build the dispatched `WebhookMetadata` come from unsigned HTTP headers. `HmacValidator.validate` only proves that `raw_body` matches the secret-derived signature; it does not prove which shop, topic, or webhook produced that body.

### Finding Description
`Registry.process` gates dispatch solely on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

but `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from attacker-controlled headers with no cryptographic binding to that body: [4](#0-3) 

Those unauthenticated fields are passed straight into the dispatched metadata that the host application's handler trusts as the tenant identity: [5](#0-4) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (along with `code`, `host`, `state`, `timestamp`) is explicitly serialized into the signed string, so the OAuth callback path correctly binds `shop` to the HMAC: [6](#0-5) 

The identity binding that should hold is: `shop header value == shop that produced the signed raw_body`. Because the header is outside the signed payload, that equality is never checked — only `hmac(raw_body, secret) == received_hmac` is checked, which is independent of the `shop-domain` header's value.

**Exploit sequence for a multi-tenant app:**
1. An unprivileged attacker installs the app on their own (attacker-owned, free) shop, which is a normal, unprivileged installation flow requiring no special access.
2. Shopify sends a legitimate webhook to the app's public endpoint: `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(B, client_secret)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. The attacker captures this `(B, HMAC(B, client_secret))` pair — no knowledge of `client_secret` needed, since Shopify computed it for them.
4. The attacker sends their own POST request directly to the app's public webhook endpoint, reusing the exact same `raw_body = B` and `x-shopify-hmac-sha256` header, but substituting `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`/`webhook-id`).
5. `HmacValidator.validate` still succeeds, because it only checks `raw_body` against the signature — which is unchanged. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`.
6. The host application's webhook handler, trusting `WebhookMetadata#shop` as an authenticated tenant identifier (as the gem's own webhook contract implies), processes the forged event as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to provide. An attacker with only an unprivileged, self-service shop install can forge which tenant a webhook event is attributed to, resulting in cross-tenant confusion in any handler that keys behavior off `WebhookMetadata#shop` (e.g., triggering `shop/redact`-like state changes, cache/record updates, or session lookups keyed by shop) — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is High: the attacker needs no credentials, access tokens, or `client_secret` knowledge — merely the ability to install the app on their own store (self-service) and replay a captured payload/signature pair with a substituted header to the app's already-public webhook endpoint.

### Recommendation
Fold `shop`, `topic`, `webhook_id`, and `api_version` into the signed payload (analogous to `AuthQuery#to_signable_string`), or at minimum verify that `request.shop` matches an expected/allow-listed shop for the installation before dispatching, so the HMAC check binds the full set of fields the handler relies on, not just `raw_body`.
