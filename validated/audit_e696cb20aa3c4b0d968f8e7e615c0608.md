### Title
Signup marked "Success" and locally-computed liveness/fraud outcome trusted without backend confirmation, after biometric package is already uploaded and bound to the user - ([File: src/plans/mod.rs])

### Summary
In `do_signup`, when a signup is `user_centric_signup` (and the orb config does not override it via `ignore_user_centric_signups`), the code skips the entire backend enrollment/verification round-trip (`enroll_user::Plan::run`, which performs `signup_post::request` + polling via `signup_poll::request`) and instead derives `success` purely from the orb's own locally-computed `signup_reason`. This mirrors the "burn happens, confirmation is skipped" pattern from the cited report: the irrevocable action (uploading and cryptographically binding the user's biometric Personal Custody Package to `signup_id`/`user_id`) has already occurred *before* this branch, but the equivalent of the destination-chain completion check (server-side dedupe/fraud/liveness verification and "Completed" status) is never performed for this signup mode.

### Finding Description
The relevant control flow in `do_signup`: [1](#0-0) 
computes `signup_reason` from purely local checks — `pipeline.is_none()` (agent/internal failure) or `fraud_detected` (local, on-device fraud detection only) — before any backend interaction for enrollment occurs.

The Personal Custody Package (containing encrypted iris/face biometric images and codes) is then built and uploaded to the backend and bound to `signup_id`/`user_id`, an irrevocable, backend-persisted action: [2](#0-1) 

Immediately after this irrevocable upload, the code branches on `user_centric_signup`: [3](#0-2) 

If `user_centric_signup` is true (and the config flag `ignore_user_centric_signups` is not set), `success` is derived from `signup_reason == SignupReason::Normal` alone — the code never calls `enroll_user::Plan::run`, and therefore never calls `signup_post::request` (which posts iris code + signature for the backend's own duplicate/fraud checks) nor `signup_poll::request` (which polls for a `Completed`/`success` verdict from the backend): [4](#0-3) [5](#0-4) 

`user_centric_signup` is a boolean supplied by the *user's own QR/app-controlled payload* (`orb_qr_link::UserData`) that is only integrity-checked via a hash signature, not tied to any independent backend authorization decision about whether verification can be skipped: [6](#0-5) [7](#0-6) 

This is structurally the same bug class as the report: an irrevocable, state-committing action (token burn / biometric upload+binding) is performed, but the step that is supposed to gate final success/authorization on a backend-verified outcome (destination-chain execution / backend dedupe-fraud-liveness verification) is bypassed, and the caller nonetheless reports success and finalizes UX (`Self::report_signup_reason`, `ui_complete_signup`) based only on the unverified local state.

### Impact Explanation
For app/user-centric signups, World ID enrollment "success" is asserted to the user and downstream UI/telemetry (`report_signup_reason`, `debug_report.signup_successful()`) without the backend's own uniqueness/fraud/liveness pipeline (`signup_post`/`signup_poll`) ever confirming it, even though the corresponding biometric data has already been irrevocably uploaded and bound to that `signup_id`/`user_id`. This risks misattributed or unauthorized signup completion: a signup can be locally reported and recorded as `Normal`/successful while the backend never independently validated deduplication or fraud/liveness for that specific enrollment attempt, since the mechanism that would normally do so is skipped entirely in this code path.

### Likelihood Explanation
The path is reachable by any legitimate operator-run signup flow whenever the backend/app marks a session `user_centric_signup: true` and the orb's `ignore_user_centric_signups` config flag is not set — no malicious node, hardware access, or test-only feature flag is required. This is a normal, unprivileged-user-triggered production code path in `do_signup`.

### Recommendation
Do not treat `user_centric_signup` as a reason to skip backend verification for enrollment success. At minimum, still invoke the backend confirmation (`signup_post`/`signup_poll` equivalent) for user-centric signups before finalizing `success`, or ensure the biometric package upload itself is contingent/reversible until an authoritative backend "Completed" verdict is received — mirroring the recommended mitigation in the original report (only finalize/commit after destination-side confirmation, not before).

### Proof of Concept
1. Backend/app returns `authenticated_app_data.user_centric_signup = true` for a user QR-code session, verified only via `user_data.verify(user_data_hash)` (an integrity check, not an authorization decision) — `src/backend/user_status.rs:175-178`.
2. Orb proceeds through `do_signup`, performs biometric capture and pipeline, sets `signup_reason` purely from local pipeline/fraud results (`src/plans/mod.rs:565-571`), builds and uploads the Personal Custody Package binding biometrics to `signup_id`/`user_id` (`src/plans/mod.rs:580-636`).
3. Because `user_centric_signup && !ignore_user_centric_signups`, the code sets `success = signup_reason == SignupReason::Normal` directly, without ever calling `enroll_user::Plan::run` (`src/plans/mod.rs:639-656`) — so `signup_post::request`/`signup_poll::request`, which perform the backend's own duplicate/fraud/liveness verification, are never invoked.
4. The signup is reported as successful (`ui.signup_success()`, `debug_report.signup_successful()`), and the biometric package remains uploaded/bound on the backend, despite no backend-side verification of this specific enrollment ever having occurred.

/// Makes a signup request.
pub async fn request(signup_id: &str) -> Result<Response> {
    let request = super::client()?
        .get(format!("{}/api/v1/signups/{signup_id}", *SIGNUP_BACKEND_URL))
        .basic_auth(&*ORB_ID, Some(get_orb_token()?));
    tracing::debug!("Sending request {:#?}", request);
    let response = request.send().await?;
    tracing::debug!("Received response {:#?}", response);
    response.error_for_status_ref()?;

    let response_body = response.text().await?;
    let parsed_response = serde_json::from_str::<Response>(&response_body)
        .inspect_err(|_| {
            tracing::error!("Failed to parse response JSON. Response body: {:#?}", response_body);
        })
        .wrap_err("Failed to parse response JSON")?;

    tracing::debug!("Received response {:#?}", parsed_response);
    Ok(parsed_response)
}
