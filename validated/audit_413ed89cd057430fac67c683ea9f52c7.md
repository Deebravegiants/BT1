### Title
Webhook HMAC only signs the raw body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `#shop` is read directly from an unsigned header. `Registry.process` verifies the HMAC over the body and then unconditionally trusts the unverified `shop` value when dispatching to the app's webhook handler. This breaks the binding `authenticated_shop == handler_shop`.

### Finding Description
`VerifiableQuery#to_signable_string` is the only material the HMAC covers. For webhooks, this is implemented as: [1](#0-0) 
i.e. only `@raw_body`. The `shop` accessor, however, is derived from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then immediately builds `WebhookMetadata` using the unverified `request.shop` value, handing it to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string`, confirming the header is never part of the signature computation: [4](#0-3) 

Because `hmac == HMAC(body)` regardless of the `shop-domain` header value, any request with a previously-observed valid `(body, hmac)` pair can be replayed with an attacker-chosen `shop-domain` header and will still pass `Utils::HmacValidator.validate`. The equality the gem should enforce is:
`hmac_verifies(body) ∧ shop_header == shop_that_produced(body)`
but it only enforces `hmac_verifies(body)`, silently assuming `shop_header` is trustworthy once the body's signature checks out.

### Impact Explanation
An attacker who controls (or can trigger events on) any shop that has the app installed can capture a legitimately-signed webhook payload+HMAC from Shopify for their own store, then resend that exact body/HMAC to the app's public webhook endpoint while substituting the `shop-domain` header with a victim merchant's domain. `Registry.process` will accept it as authentic (HMAC only covers the body) and hand the attacker-controlled body to the handler tagged with the victim's shop. Any app logic keyed off `WebhookMetadata#shop` (e.g., "update order X for shop Y", cache invalidation, billing/usage records, GDPR data requests) will act on the victim tenant using data supplied by the attacker — a cross-tenant integrity/confusion issue reachable without any credentials belonging to the victim or the app.

### Likelihood Explanation
Exploitation requires: (1) a webhook endpoint reachable from the internet (true by design — Shopify calls it over HTTP), and (2) the attacker being able to obtain at least one genuinely-signed `(body, hmac)` pair, which any merchant installing the app on their own store can trivially obtain by triggering a webhook event (e.g. `orders/create`) on their own shop. No access token, `client_secret`, or privileged account is required — only ordinary app installation, which is the normal unprivileged flow. This makes the likelihood moderate-to-high wherever handler logic branches on `WebhookMetadata#shop`.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the HMAC-covered signable string, or independently verify that the `shop-domain` header matches a shop that is expected/registered for the given HMAC-covered payload before dispatching to handlers. At minimum, `Request#to_signable_string` should incorporate the shop header so a captured `(body, hmac)` pair cannot be replayed under a different shop identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. creates an order), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` from Shopify's genuine delivery.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because the body was not modified.
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, i.e., attacker-controlled data is processed under the victim shop's identity.
