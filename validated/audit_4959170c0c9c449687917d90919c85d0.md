Found a genuine host/origin validation bypass in the gateway's CORS allowlist logic that matches the CVE's "host address validation failing" bug class.

### Title
CORS wildcard origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

### Summary
The gateway HTTP server's CORS origin allowlist check performs a wildcard match using an unanchored `strings.HasSuffix` comparison instead of verifying a dot-separated subdomain boundary, allowing an attacker to craft a hostname that satisfies the suffix check without actually being a subdomain of the allowed domain.

### Finding Description
`isAllowedOrigin` implements the wildcard branch of the CORS allowlist check as: [1](#0-0) 

For an allowed origin configured as `*.remix.com`, `allowedHost` becomes `remix.com` after stripping `*.`, and the check is `strings.HasSuffix(originHost, allowedHost)`. This only checks that `originHost` ends with the literal string `remix.com` — it does not require a `.` immediately before that suffix. An attacker-registered domain such as `evilremix.com` or `notremix.com` also ends with `remix.com` and will pass this check even though it is not a subdomain of `remix.com`.

This check is reached directly from an unauthenticated, unprivileged HTTP client via the `Origin` request header on every request to the gateway: [2](#0-1) 

When `isAllowedOrigin` returns true, the server reflects the attacker-controlled `Origin` value back in `Access-Control-Allow-Origin`, granting the attacker's page CORS access to the gateway's HTTP API responses.

### Impact Explanation
This is a cross-user/cross-origin allowlist-bypass class issue: a malicious website (e.g. `evilremix.com`) can pass itself off as an allowed origin intended for `*.remix.com`, and browsers visiting that malicious site will be permitted (via the reflected `Access-Control-Allow-Origin` header) to make and read cross-origin responses from the gateway on behalf of the victim's browser session. Depending on what the gateway's HTTP-facing handlers expose (job/trigger/capability responses routed through this server), this can lead to unauthorized cross-origin reads of gateway responses that were only meant to be accessible to the legitimately allowlisted origins.

### Likelihood Explanation
Exploitation requires only that an operator has configured a wildcard entry (e.g. `*.remix.com`) in `CORSAllowedOrigins`, and that an attacker registers/controls any domain sharing that suffix (trivial and cheap, e.g. `evilremix.com`, `notremix.com`), then lures a victim's browser to visit it while it makes a request to the gateway endpoint. No authentication or special network position is required — this is reachable directly from any unprivileged web client via `UI:R` (user interaction: victim visits attacker page), matching the CVSS vector of the referenced CVE.

### Recommendation
Fix the wildcard match in `isAllowedOrigin` at core/services/gateway/network/httpserver.go:184-190 to require a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.com"
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
i.e., compare against `.remix.com` (including the leading dot) rather than `remix.com`, so `evilremix.com` no longer matches while `foo.remix.com` still does.

### Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. Send an HTTP request to the gateway's configured path with header `Origin: https://evilremix.com`.
3. Observe that `isAllowedOrigin` returns `true` (since `"evilremix.com"` has suffix `"remix.com"`), and the response includes `Access-Control-Allow-Origin: https://evilremix.com`, even though `evilremix.com` is not a subdomain of `remix.com`.
