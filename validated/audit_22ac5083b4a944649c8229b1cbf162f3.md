## Title
Rotating an `IntentGateway` deployment address via `NewDeployment` permanently strands in-flight cross-chain orders — (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The Intent Gateway resolves the peer gateway address for a state machine through a single mutable mapping, `_instances[keccak256(chain)]`, updated in-place by governance via the `NewDeployment` action. Both the outbound routing of settlement messages (`_post`) and the inbound authentication of settlement messages (`_authenticate`) read this *current* value rather than the value that was valid when an order was placed or filled. A legitimate governance-driven gateway migration/rotation on one chain therefore silently reroutes and rejects the settlement of every order that was already escrowed against the *old* gateway address but not yet settled, permanently freezing that escrow — exactly the same "parameter change orphans pre-existing state" class as the referenced `minSizes` report.

### Finding Description
`_instances` is a single-slot-per-chain mapping updated wholesale by `_addDeployment`, invoked from `onAccept` for `RequestKind.NewDeployment`, itself only gated by "only Hyperbridge may dispatch this": [1](#0-0) 

Both outbound dispatch of settlement messages and inbound authentication resolve the peer address through this same, always-current mapping: [2](#0-1) 

`_post`, called by `_fillCrossChain` (to dispatch `RedeemEscrow`) and by the destination-side cancel path (to dispatch `RefundEscrow`), addresses the message to `_instance(order.source)` at the time the message is sent — not the address that was current when the order was placed on the source chain: [3](#0-2) 

On arrival, the source-chain gateway authenticates the request by checking that `request.from` equals its own currently-registered `_instance(request.source)`: [4](#0-3) [5](#0-4) 

Because `order.inputs`/escrow amounts live in the specific gateway contract instance that was deployed on the source chain at order-placement time (`_orders[commitment][token]` in that contract's storage), any change to the *registered* instance for that chain — via a routine `NewDeployment` governance action (chain migration, contract redeployment, address rotation) — has two independent freezing effects on all orders that are in flight at that moment:

1. **Outbound misroute**: A solver who fills an order on the destination chain *after* the source chain's registered instance changes will have their `RedeemEscrow`/`RefundEscrow` message addressed (`to`) to the *new* gateway address, not the address that actually holds the escrow. The message either reverts at delivery (unknown commitment / different storage) or is silently accepted with a no-op (nothing to release), and the real escrow is never touched.
2. **Inbound misauthentication**: Conversely, if the *destination* chain's registered instance for the source chain changes before a message dispatched under the old routing is delivered, `_authenticate` compares `request.from` (the old gateway address that legitimately dispatched the message) against the *newly* registered instance and reverts with `Unauthorized()`, permanently rejecting that settlement message.

In either direction, there is no way to recover: the escrow was fixed at placement time in a specific contract, but authentication/routing depends only on the live, single-valued `_instances` mapping with no historical/versioned record and no reconciliation path once it changes.

### Impact Explanation
Any order placed or filled shortly before a routine `NewDeployment` gateway rotation on either its source or destination chain becomes permanently unsettleable:
- The user's escrowed input tokens can never be released to the solver who filled the order (RedeemEscrow is misrouted or rejected), and
- The user cannot recover their escrow either, because both the fill-timeout cancellation path (`RefundEscrow`) and the GET-based cancellation path route/authenticate through the same stale-vs-current `_instance` mismatch.

This is a permanent freezing of user and solver funds triggered by an ordinary, expected governance operation (rotating/adding a gateway deployment), not by any malicious actor — it satisfies "permanent freezing of funds" from a single relayed governance dispatch plus ordinary user/solver order flow.

### Likelihood Explanation
`NewDeployment` is an expected, routine governance call (e.g., migrating to a new gateway contract on a chain, or initially registering a peer). Any order in flight — placed but not yet filled, or filled but not yet settled — during the window between dispatch and delivery of such an update is affected. Given that IntentGateway is meant to support many chains and periodic upgrades/redeployments, this window is realistically reached during normal operation, without requiring any adversarial behavior.

### Recommendation
- Do not resolve settlement routing/authentication purely from the live `_instances` mapping. Snapshot the peer gateway address into the `Order` (or into the fill/withdrawal request) at order-placement time and validate/settle against that snapshotted address, or
- Support multiple valid peer addresses per chain (an allow-list rather than a single overwritten slot) with an explicit, governance-controlled deprecation window that keeps prior instances valid for authentication/routing until all orders placed against them have been fully settled or refunded.

### Proof of Concept
1. Gateway `G_A` is registered as the instance for chain A on Gateway `G_B` (chain B), and vice versa.
2. User places a cross-chain order on chain A (escrow recorded in `G_A`'s `_orders` storage), destined for chain B.
3. Before the order is filled, Hyperbridge governance dispatches `RequestKind.NewDeployment` to `G_B`, updating `_instances[keccak256(A)]` from `G_A` to `G_A_new` (e.g., a legitimate gateway migration on chain A).
4. Solver fills the order on `G_B`. `_fillCrossChain` calls `_post`, which addresses the `RedeemEscrow` message `to: _instance(order.source)` → now `G_A_new`, not `G_A`. [6](#0-5) 
5. On chain A, the message is delivered to `G_A_new`, whose `_orders[commitment][token]` storage never held this escrow — the withdrawal finds nothing to release, or the destination-side authentication elsewhere rejects it as coming from an address that no longer matches `_instance`.
6. The user's tokens remain permanently escrowed in `G_A`, unreachable by any subsequent `RedeemEscrow`/`RefundEscrow` message, since all future messages resolve exclusively through the now-updated `_instances` mapping.

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }

     * @dev Registers a new IntentGateway deployment for a remote state machine.
     * Called when Hyperbridge governance adds support for a new chain. The gateway
     * address is stored in `_instances` keyed by the hash of the state machine ID.
     *
     * @param body The deployment info containing the state machine ID and gateway address.
     */
    function _addDeployment(Deployment memory body) internal {
        _instances[keccak256(body.chain)] = body.gateway;
        emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
    }
