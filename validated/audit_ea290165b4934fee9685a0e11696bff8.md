## Title
Missing actual-received-balance check in `IntentGatewayV2.placeOrder` (Tron variant) allows fee-on-transfer/burn tokens to create insolvent escrow accounting - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) credits escrow with the user-declared nominal token amount instead of the amount actually received by the contract. Any ERC20 token that burns, taxes, or otherwise reduces the transferred amount on `transferFrom` (exactly the bug class exploited in the reported WXC incident) will cause the gateway's internal escrow ledger to overstate its real token balance, leading to failed/blocked withdrawals and permanent freezing of funds for legitimate orders sharing that token pool.

### Finding Description
In `placeOrder`, the non-predispatch escrow path does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            ...
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
    }
}
```

`reducedInputs[i].amount` is computed purely from the *nominal* `order.inputs[i].amount` minus the protocol fee percentage — it never reflects what the ERC20 `transferFrom` call actually delivered to the contract. Compare this with the canonical (non-Tron) implementation, which explicitly measures the balance delta to guard against exactly this class of token: [2](#0-1) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

This exact fix (and matching Foundry tests, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`) exists in the main EVM contract: [3](#0-2) 

but the Tron copy of `IntentGatewayV2.sol` was not updated with the same protection, leaving the accounting bug present in a production-deployed variant.

Downstream, `withdraw()` transfers exactly the escrowed (ledger) amount to the beneficiary, trusting that the contract's real balance can cover it: [4](#0-3) 

If the token deducted a fee/burn on the way in, `_orders[commitment][token]` is inflated relative to the actual tokens held, so this transfer can revert (`TransferFailed`) or, in a shared-liquidity scenario, silently drain balance intended for *other* users' orders that use the same token, causing their legitimate withdrawals/refunds to fail as well.

### Impact Explanation
This is a direct accounting-mismatch bug in the token escrow/bridge component reachable by any unprivileged user calling `placeOrder` with an arbitrary ERC20 `order.inputs[i].token` — precisely the "unprivileged token bridger" class in scope. The result is permanent freezing of user funds: once escrow bookkeeping exceeds the contract's actual token balance for a given asset, both `fillOrder`→`withdraw` (solver settlement) and `cancelOrder`→`withdraw` (refund) paths can revert or under-deliver, and other users' orders denominated in the same token can become undercollateralized and unable to be redeemed.

### Likelihood Explanation
Likelihood is high: the attack requires no privileged access — any user can place an order using a fee-on-transfer/burn/rebasing token as an input, which is a common token category on public chains (as demonstrated by the referenced WXC exploit). No special timing, governance, or admin compromise is needed; only picking a token with transfer-time deduction and calling `placeOrder`.

### Recommendation
Apply the same actual-balance-delta pattern already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: record `balanceOf(address(this))` before and after `safeTransferFrom`, use the delta (further reduced by protocol fee) as the escrow credit and as the amount hashed into the order commitment, mirroring the fix and tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`.

### Proof of Concept
1. Deploy a fee-on-transfer/burn ERC20 (e.g., 1% burn on `transferFrom`, as in `FeeOnTransferToken` test helper) and mint to a user.
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. Actual tokens received by the gateway = 990e18 (after burn), but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` derived from the full 1000e18 (minus only protocol fee, not the token's burn).
4. A solver fills the order; `withdraw()` attempts to transfer the escrowed (overstated) amount — this either reverts (`TransferFailed`), or, if other orders share the token's liquidity in the contract, drains balance backing those other orders, leaving them unable to be withdrawn/refunded.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
