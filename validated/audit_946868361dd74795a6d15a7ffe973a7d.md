Found a genuine null-check gap: `Router.buy` at `packages/contracts/src/Router.sol:92-108` looks up `pairAddr` from `factory.getPair(token, asset)` but, unlike every sibling function in the same file (`getAmountOut`, `addInitialLiquidity`, `previewBuy`, `sell`, `graduate` — all of which have `if (pairAddr == address(0)) revert PairNotFound();`), `buy()` omits that guard before dereferencing `pairAddr` via `_computeBuy`, `IERC20(asset).safeTransferFrom(to, pairAddr, ...)`, and `IPair(pairAddr).transferToken/swap`.

### Title
Missing zero-address guard on `pairAddr` in `Router.buy` causes null-reference-style DoS/fund-lock on curve buys - ([File: packages/contracts/src/Router.sol])

### Summary
`Router.buy()` is the sole internal AMM entry point `Bonding.buy()` calls for every curve purchase reachable via `Zap.buy` / `Zap.buyWithPermit` / `Zap.createToken`'s seed buy. It resolves `pairAddr = factory.getPair(token, asset)` and, without validating it is non-zero, immediately dereferences it: `_computeBuy(pairAddr, amountIn)` reads `pair.getReserves()` / `pair.k()` / `pair.tokenBalance()`, and the function then calls `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)` before `IPair(pairAddr).transferToken(...)` / `IPair(pairAddr).swap(...)`. Every other pair-consuming function in `Router.sol` (`getAmountOut`, `addInitialLiquidity`, `previewBuy`, `sell`, `graduate`) explicitly checks `pairAddr == address(0)` and reverts with `PairNotFound()` first — `buy()` is the outlier.

### Finding Description

If `factory.getPair(token, asset)` ever returns `address(0)` for a token that `Bonding` still believes is on `Lifecycle.Curve` (e.g. any state divergence between `Bonding.tokenInfo[token].pair`/lifecycle bookkeeping and `Factory`'s pair registry — a future upgrade to `Factory`, a `Router` swap per `AGENTS.md`'s "Router swapability" note, or any code path that mutates `Factory`'s registry independent of `Bonding`), `_computeBuy` will call `IPair(address(0)).getReserves()`. On an EOA/undeployed address this returns success with empty return data, and Solidity's high-level ABI decoding of that empty data for a multi-value return reverts with an unhelpful low-level panic rather than the clean `PairNotFound()` error the rest of the module produces. Worse, if the call instead partially succeeds or the zero-address branch is hit after `safeTransferFrom(to, pairAddr, amountInUsed)` already moved the trader's LT to `address(0)`, the LT is burned/lost with no recovery path — a direct trader-fund loss, not merely a revert.

### Impact Explanation
This satisfies the Medium bar: freezing/loss of trader funds. If `pairAddr` resolves to zero on the buy path, either (a) every buy for that token DoSes with an opaque revert (denial of a core unprivileged-trader-reachable flow, `Zap.buy`/`buyWithPermit`), or (b) in the worse ordering, the LT `safeTransferFrom(to, pairAddr, amountInUsed)` sends the buyer's minted LT to `address(0)` before the pair-state calls fail, permanently burning trader funds pulled by `Zap._buyOnCurve` on every buy. Both outcomes match the "no null check before dereference" root cause pattern of CVE-2024-36011, mapped onto alt.fun's `Router`/`Pair`/`Factory` shape.

### Likelihood Explanation
Under the current, unmodified `Factory`/`Bonding` wiring, `factory.getPair` should stay in sync with `Bonding.tokenInfo[token].pair` for a `Lifecycle.Curve` token, so the zero case is not trivially triggerable today by an external caller alone — this is the key uncertainty I could not fully rule out from static review (I did not trace every `Factory` mutation path, e.g. `Factory.setRouter`/pair-registry admin functions, to prove or disprove a divergence window). The missing guard is nonetheless a real code-quality/defense-in-depth gap: it is the one function in `Router.sol` inconsistent with its siblings, and the documented "Router swapability" note in `AGENTS.md` (`packages/contracts/AGENTS.md`) explicitly anticipates operational changes to routing that make this consistency important. Likelihood is Medium given the guard is one-line-cheap and its absence is unexplained/inconsistent with the rest of the file, even though I could not construct a fully unprivileged, always-reachable trigger path with the code paths I was able to inspect.

### Recommendation
Add the same guard used in every sibling function to `Router.buy`, immediately after resolving `pairAddr`:
```solidity
address pairAddr = factory.getPair(token, asset);
if (pairAddr == address(0)) revert PairNotFound();
```
placed before `_computeBuy(pairAddr, amountIn)` and before the `safeTransferFrom` / `IPair(pairAddr)` calls, so that any zero-pair condition reverts cleanly with `PairNotFound()` instead of risking an ABI-decode panic or, in the worst ordering, transferring trader LT to `address(0)`.

### Proof of Concept
Static PoC (illustrative, contingent on the unverified precondition that `factory.getPair(token, asset)` can return `address(0)` while `Bonding.tokenInfo[token].lifecycle == Lifecycle.Curve` — I was not able to confirm or rule out such a divergence within this review):
1. Reach a state where `Factory.getPair(token, lt)` returns `address(0)` for a token still recorded as `Lifecycle.Curve` in `Bonding.tokenInfo`.
2. An unprivileged trader calls `Zap.buy(tokenAddress, usdcAmount, 0, referrer)`.
3. `Zap._executeBuy` → `Zap._buyOnCurve` → `Bonding.buy` → `Router.buy(amountIn, token, to)`.
4. `Router.buy` resolves `pairAddr = address(0)` and calls `_computeBuy(address(0), amountIn)`, which calls `IPair(address(0)).getReserves()`/`k()`/`tokenBalance()` — reverting with an undecoded panic instead of `PairNotFound()`, or, if these degenerate to non-reverting zero reads, proceeding to `IERC20(asset).safeTransferFrom(to, address(0), amountInUsed)`, burning the trader's minted LT.     function buy(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 amountInUsed, uint256 tokensOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);

        (amountInUsed, tokensOut) = _computeBuy(pairAddr, amountIn);

        IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed);

        IPair(pairAddr).transferToken(to, tokensOut);
        IPair(pairAddr).swap(0, tokensOut, amountInUsed, 0);
    }
