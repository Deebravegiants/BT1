This is a critical finding: **on the Substrate side, `pallet-ismp`'s `DispatchRequest::Post` / `DispatchRequest::Get` accept a caller-supplied `from` field with no verification that it matches the dispatching pallet's own identity.**

### Title
Unauthenticated `from` field in `pallet-ismp::dispatch_request` allows any pallet to forge the identity of another module's outgoing messages - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`Pallet<T>::dispatch_request` (the `IsmpDispatcher` implementation) builds the outgoing `PostRequest`/`GetRequest` directly from caller-supplied `DispatchPost`/`DispatchGet` structs, copying `dispatch_post.from` / `dispatch_get.from` verbatim into the wire message with no check that the value corresponds to the calling pallet's actual module id.

### Finding Description
`dispatch_request` in [1](#0-0)  constructs the `PostRequest`/`GetRequest` using `self.host_state_machine()` for `source` (correctly bound to this chain) but takes `from` straight from the caller-supplied `DispatchPost`/`DispatchGet` with zero validation. Every runtime pallet that dispatches messages sets `from` to its own well-known module id by convention (`PALLET_ID.to_bytes()`, `MODULE_ID.to_vec()`, etc.), e.g. [2](#0-1) , [3](#0-2) , [4](#0-3)  — but this is purely a convention observed by well-behaved callers, not enforced by `pallet-ismp` itself.

This "coarse" trust model mirrors the Kibana bug exactly: the pallet enforces a coarse authorization gate (any pallet configured with `type IsmpDispatcher`/`type Dispatcher` may call `dispatch_request` at all) but never verifies that the specific resource identifier supplied in the request (`from`, which downstream determines routing, reward eligibility, bandwidth accounting, and destination-side authorization such as `_supportedChains[source] == from` on EVM tokens or `ContractToAsset::get(source, from)` on the HFT pallet) actually belongs to the caller. `pallet-ismp` then uses its own elevated, protocol-level write access (inserting into the child-trie `RequestCommitments`, which any relayer can subsequently prove-and-deliver with Hyperbridge's full consensus-verification weight behind it) to commit a message that impersonates a different module.

Any pallet in the runtime that is wired to a generic `T::Dispatcher: IsmpDispatcher` (a widespread pattern — `pallet-bandwidth`, `pallet-ismp-relayer`, `pallet-intents-coprocessor`, `pallet-hyper-fungible-token`, `pallet-ismp-demo`, and any 3rd-party pallet added to the runtime) can call `dispatch_request` with an arbitrary `from` value, forging outbound messages that appear to originate from a different, more privileged module. Downstream systems that key trust off `request.from` — e.g., `OutboundRequestDeliveryReward` keyed by `module_id = request.from` in [5](#0-4) , `BandwidthGate::try_consume(source, app=from, bytes)` in [6](#0-5) , or EVM-side peer checks like `HyperFungibleToken.onAccept`'s `keccak256(request.from) == keccak256(expectedSource)` in [7](#0-6)  — will treat the forged message as authentic, because the check is purely against the wire-level `from` bytes, which `pallet-ismp` never bound to the actual caller.

### Impact Explanation
A malicious or compromised pallet added to a Hyperbridge runtime (or any pallet with a bug that lets a user influence the `from`/module-id argument passed into a `DispatchPost`/`DispatchGet`) can:
- Forge messages that appear to come from `pallet-ismp-relayer`'s `MODULE_ID` or `pallet-hyper-fungible-token`'s `PALLET_ID`, causing destination-side EVM peers (which authenticate purely by comparing `request.from` bytes) to execute privileged mint/withdraw logic addressed to arbitrary recipients — a forged message delivery / unauthorized app action leading to unbacked mint or fund drain on the destination chain.
- Drain `OutboundRequestDeliveryReward` (keyed by `module_id`) by impersonating a module with a configured non-zero reward, since the pallet only checks source-chain identity and the claimed `from`, not who actually dispatched.
- Bypass or exhaust another app's bandwidth allowance by forging `from` to match a victim app's identity in `BandwidthGate::try_consume`.

### Likelihood Explanation
Requires only that a runtime include more than one pallet wired to `IsmpDispatcher`/`Dispatcher`, or that a pallet's dispatch call site exposes the `from`/module-id parameter to a signed/unprivileged origin (several sample pallets in this codebase — `pallet-ismp-demo`, `pallet-intents-coprocessor` — take pallet-controlled `from` values, but any third-party integrator pallet following the documented `IsmpDispatcher` pattern in [8](#0-7)  could pass a user-controlled `from`). No proof forgery or consensus compromise is needed; only a single dispatched request from any pallet with access to the dispatcher trait is required, satisfying the "single dispatched request" reachability bar.

### Recommendation
`Pallet<T>::dispatch_request` should bind `from` to the caller's actual identity rather than trusting the value embedded in `DispatchPost`/`DispatchGet`. Options: (1) derive `from` server-side from the calling pallet's registered module id (e.g., via a `PalletId`/origin-derived value passed separately from the trait, not embedded in caller-supplied structs), or (2) require callers to prove ownership of the claimed `from` id against a runtime-level registry before `dispatch_request` accepts it, mirroring the destination-side authentication (`ContractToAsset`, `_supportedChains`) that already exists but is trivially defeated at the source.

### Proof of Concept
1. Add (or compromise) a pallet `Evil` in a Hyperbridge runtime, configured with `type Dispatcher = pallet_ismp::Pallet<Runtime>` (or any generic `IsmpDispatcher`).
2. From an unprivileged extrinsic, call `Evil::send_evil`, which builds:
   ```rust
   let post = DispatchPost {
       dest: StateMachine::Evm(<victim_chain>),
       from: pallet_hyper_fungible_token::PALLET_ID.to_bytes(), // forged identity
       to: <victim_token_contract>,
       timeout: 0,
       body: <crafted Message{ to: attacker, amount: X }>,
   };
   T::Dispatcher::default().dispatch_request(DispatchRequest::Post(post), FeeMetadata{ payer, fee: 0 })?;
   ```
3. `pallet-ismp::dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs:92-146`) accepts this with no check that `Evil` owns `pall_hft`'s module id, hashes and commits it to `RequestCommitments`.
4. Any relayer delivers the resulting `PostRequest` to the EVM `HyperFungibleToken`/`BridgeToken` peer contract; `onAccept` sees `request.from == expectedSource` (because the forged bytes match the real peer id) and mints tokens to the attacker-controlled beneficiary, confirming unauthorized minting driven purely by an unauthenticated `from` field at dispatch time.

**Note:** I was not able to fully trace every EVM-side and pallet-side consumer of `request.from` in this session (the codebase is large and only partially indexed here), so I cannot rule out that some destination integrations layer additional per-message authentication beyond the `from`-byte comparisons observed (e.g., `HyperFungibleToken.sol`, `pallet-hyper-fungible-token::on_accept`, `pallet-bandwidth::on_accept`). I recommend a Devin session with full repository access to confirm there is no additional binding between a dispatching pallet's origin and the `from` field it is allowed to set, and to check whether any runtime enforces this via a `BaseCallFilter`/wrapper not surfaced in the indexed search.

```rust
		&self,
		request: DispatchRequest,
		fee: FeeMetadata<T>,
	) -> Result<H256, anyhow::Error> {
		// collect payment for the request
		if fee.fee != Zero::zero() {
			T::Currency::transfer(
				&fee.payer,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| IsmpError::Custom(format!("Error withdrawing request fees: {err:?}")))?;
		}

		let request = match request {
			DispatchRequest::Get(dispatch_get) => {
				let get = GetRequest {
					source: self.host_state_machine(),
					dest: dispatch_get.dest,
					nonce: self.next_nonce(),

					keys: dispatch_get.keys,
					height: dispatch_get.height,

							.saturating_add(dispatch_get.timeout)
					},

			},
```

```markdown

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.
```
