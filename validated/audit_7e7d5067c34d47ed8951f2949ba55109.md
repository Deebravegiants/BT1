Based on the codebase inspection, I found a concrete identity-binding gap in the webhook verification path of this gem.

### Title
Webhook HMAC signature does not cover the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` trusts and dispatches to app handlers are read straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are parsed straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` only proves that `HMAC(api_secret_key, raw_body)` matches the `hmac` header — it says nothing about which shop or topic that body was originally sent for: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` directly to build the metadata dispatched to the app's handler, with no additional check that they match the verified body: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop/topic covered by the HMAC signature == shop/topic the app acts upon` — the left side is the empty set (only `raw_body` is signed), while the right side is attacker/header-controlled.

Because `api_secret_key` is a single, static value shared across every shop installed on a given app (it's a per-app secret, not per-shop), `HMAC(api_secret_key, body)` is identical for any two deliveries of byte-identical bodies, regardless of which shop or topic they were nominally sent for. Shopify's "Send test webhook" feature (available to any merchant who installs the app, including free/unprivileged test stores) delivers a fixed, publicly documented sample JSON payload per topic — identical text for every shop. An attacker who installs the app on their own store and points a webhook subscription at an endpoint they control can capture one such `(raw_body, hmac)` pair. Since that exact sample body is fixed and public, the resulting HMAC is fully deterministic and reusable. The attacker can then replay that same `(raw_body, hmac)` pair against the real target app's public webhook endpoint while freely substituting the `shopify-shop-domain` and `shopify-topic` headers (e.g. targeting a victim shop's domain, or switching topic to `app/uninstalled`, `shop/redact`, `customers/data_request`, etc.), and `HmacValidator.validate` will still report success because those headers were never part of the signed content.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an unprivileged attacker (any user who can install the app on their own store) can forge a webhook that Registry.process treats as validly originating from a **different, victim shop**, dispatching attacker-chosen topic/shop metadata to the host application's webhook handlers. Depending on how the host app implements handlers (following this gem's documented `WebhookMetadata#shop`/`#topic` contract), this can drive cross-tenant actions such as forged uninstall/deprovisioning, forged compliance/redaction requests, or other per-shop side effects attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-owned store (no elevated privilege), (2) capturing one webhook delivery of a fixed/public sample payload via a webhook endpoint the attacker controls, and (3) replaying that body+HMAC to the target's public webhook endpoint with modified `shop-domain`/`topic` headers. No access to `api_secret_key`, tokens, or TLS interception is required, matching the rule's "unprivileged internet user" and "field acted on but not covered by the HMAC" criteria directly.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (or at minimum shop and topic) in the signed/verifiable content, or independently bind them cryptographically to the signature (e.g., verify these header values are consistent with data embedded and covered inside the signed body, or require the host app to cross-check `shop` against its own webhook-subscription registration data before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Request#shop`/`#topic` are **not** authenticated by the HMAC check and must not be used as a tenant-identity boundary without additional verification.

### Proof of Concept

#    a webhook subscription at an endpoint they control, e.g. via
#    Shopify Admin's "Send test webhook" for topic "app/uninstalled" -
#    Shopify sends the fixed, publicly documented sample JSON body, signed with:
#    hmac = HMAC-SHA256(api_secret_key, fixed_sample_body)
#
# 2. Attacker now replays the exact same body+hmac against the target
#    app's real /webhooks endpoint, substituting headers:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_hmac_base64,   # unchanged - matches raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-chosen, NOT covered by hmac
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: fixed_sample_body, headers: headers)

# 3. HmacValidator.validate(request) succeeds because it only checks raw_body,
#    and Registry.process dispatches to the handler believing this is a
#    legitimate "app/uninstalled" event for "victim-shop.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)

          received_signature = verifiable_query.hmac
