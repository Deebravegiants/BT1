This confirms the design: the `Registry.process` "will verify the request did indeed come from Shopify" via `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190`, but that validation only signs `@raw_body` per `Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:36-38`. The `shop`, `topic`, and `webhook_id` values that get passed straight into `WebhookMetadata` (and that the docs explicitly tell app authors to use as the tenant key, e.g. `shop_domain: data.shop`) come from HTTP headers that are never part of the HMAC signable string.### Title
Webhook shop/topic/webhook_id headers are trusted for tenant identification but are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body, then dispatches to the app's handler using the `shop`, `topic`, and `webhook_id` values read straight from HTTP headers, none of which are included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` treats a passing `Utils::HmacValidator.validate(request)` check as proof the webhook "did indeed come from Shopify" for this request's `shop`/`topic`/`webhook_id` [2](#0-1) . But `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker-controllable HTTP headers via `shopify_header` [3](#0-2) [4](#0-3) , and `HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (the body) against the secret [5](#0-4) .

The equality the gem implicitly relies on is: **`hmac-signed bytes == identity used for dispatch`**. In reality: `hmac-signed bytes == raw_body only`, while `identity used for dispatch == request.shop` (header) `!= any signed value`. This breaks the binding between the cryptographic proof-of-origin and the tenant/topic the app acts on.

Because any app owner who has legitimately installed the target app on their own store can receive a validly-HMAC'd webhook body for their own shop, they can capture that `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header rewritten to an arbitrary victim shop domain / topic. `Utils::HmacValidator.validate` still passes because it only checks the untouched body bytes, and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's handler as `WebhookMetadata#shop` [6](#0-5) . The gem's own documentation instructs integrators to use `data.shop` as the tenant/shop key for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) , and explicitly claims that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler [8](#0-7) , which is not true for the shop/topic attribution.

### Impact Explanation
This enables cross-tenant confusion: an unprivileged attacker who controls one shop's webhook delivery can inject data/events under the identity of a victim shop into any app that trusts `data.shop`/`data.topic` (as the gem's own docs recommend) for tenant-scoped side effects such as enqueuing background jobs keyed by shop domain, updating per-shop state, or triggering redaction/data-request workflows (`shop/redact`, `customers/redact`, `customers/data_request` are exactly the kind of high-sensitivity mandatory topics registered through this same path [9](#0-8) ). This matches the "cross-tenant access" criterion since the tenant-identifying header is unauthenticated while being treated as trusted.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (a) installing the target app once on an attacker-controlled/free development store to obtain one legitimately-signed webhook body+HMAC pair, and (b) sending a crafted HTTP POST with rewritten headers directly to the app's public webhook endpoint — no access to `api_secret_key` or any privileged credential is needed, satisfying the in-scope threshold of an "unprivileged internet user."

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic` for dispatch in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and integrators must independently verify shop/topic against their own persisted subscription/session records before acting on them, rather than presenting `Registry.process` as fully verifying webhook provenance for those fields.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives a legitimate webhook for topic `customers/data_request`, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` value Shopify sent.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the *same* `raw_body` and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence, not correspondence, is checked) [10](#0-9) ; `HmacValidator.validate` passes because it only re-hashes `raw_body` [11](#0-10) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: attacker's body, ...)` [12](#0-11) , and any app logic keyed on `data.shop` now operates as if the victim shop sent this event.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
