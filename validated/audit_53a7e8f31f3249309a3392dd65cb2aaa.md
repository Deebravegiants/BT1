### Title
Fixed 4-byte function selectors in the Wallet Contract's Ethereum-transaction dispatcher allow selector-clash attacks that hide privileged `AddKey`/`DeleteKey` actions from the signing user - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`, `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The Wallet Contract (`near-wallet-contract`) lets an eth-implicit NEAR account be controlled via signed, RLP-encoded Ethereum transactions. It dispatches the meaning of a transaction purely from the first 4 bytes of `tx.data`, exactly like Solidity function selectors: `FUNCTION_CALL_SELECTOR`, `TRANSFER_SELECTOR`, `ADD_KEY_SELECTOR`, `DELETE_KEY_SELECTOR` [1](#0-0) , with dispatch performed in `parse_tx_data` by matching on `&tx.data[0..4]` [2](#0-1) . This is architecturally the same trust model as the Ambire report: a 4-byte space (2^32) is used to decide which privileged action a signed message triggers, and the same 4 bytes plus a plausible-looking ABI encoding can be crafted by an attacker to make a privileged call (here, `AddKey` with `is_full_access: true`) look like an innocuous function call to whatever UI is displaying the transaction to the user.

### Finding Description
`ADD_KEY_SELECTOR = 0x753ce5ab` decodes calldata into `(public_key_kind, public_key, nonce, is_full_access, is_limited_allowance, allowance, receiver_id, method_names)` [3](#0-2) , which is turned directly into a NEAR `AddKeyAction` with `AccessKeyPermission::FullAccess` when `is_full_access` is true [4](#0-3) . `DELETE_KEY_SELECTOR` similarly triggers `DeleteKeyAction` [5](#0-4) .

These two selectors are classified as `SelfNearNativeAction`, meaning the intended target is the wallet's own account [6](#0-5) , and `parse_rlp_tx_to_action` only reroutes them to a no-op Transfer when the caller-chosen `target` account happens to be a *different* eth-implicit account; if the target is the wallet's own account (`TargetKind::CurrentAccount`) the privileged action is executed as parsed [7](#0-6) .

The only authentication check on the whole flow is that the *raw byte sequence* `tx_bytes_b64` be a validly-signed Ethereum transaction from the wallet owner's key (`tx.address.raw() == context.current_address`) [8](#0-7) . Nothing in the signed payload conveys the *semantic* meaning "this authorizes adding/deleting an access key" beyond the raw 4-byte selector plus ABI-encoded args — exactly the blind-signing/selector-collision surface described in the Ambire report. Because the selector space is only 4 bytes, an attacker can, exactly as in the Ambire scenario, search for/construct a benign-sounding Solidity-style function signature (e.g., a fake `claim(...)`/`stake(...)`-style name, or one of the many pre-computed 4-byte collisions available for public 4-byte selectors) whose `keccak256` matches `ADD_KEY_SELECTOR` (`0x753ce5ab`) or `DELETE_KEY_SELECTOR` (`0x3fc6d404`), and whose argument layout can be filled with attacker-controlled values that also happen to satisfy `ADD_KEY_SIGNATURE`'s tuple `(uint8, bytes, uint64, bool, bool, uint128, string, string[])`. A malicious dApp can then present this "innocuous" call to the user's normal Ethereum wallet UI (MetaMask, etc., which is entirely outside nearcore's control and typically only recognizes selectors it has an ABI for, or shows raw hex), get it signed, and relay it to `rlp_execute` with `target` set to the victim's own wallet account — resulting in a `FullAccess` key being silently added for the attacker, i.e., complete takeover of the account. This is functionally identical to using a fallback-handler selector clash to hide a call to `setAddrPrivilege()` in the Ambire report.

### Impact Explanation
If exploited, the attacker gains a `FullAccess` `AccessKeyPermission` on the victim's NEAR account (via `AddKey`), or removes the owner's key (`DeleteKey`), through a transaction the user believed authorized an unrelated, benign action. This is unauthorized state/permission change and complete account takeover — concrete impact directly in scope (unauthorized state change / access-key authorization bypass).

### Likelihood Explanation
Exploitability depends on: (1) an attacker's ability to construct plausible ABI signatures that hash-collide with the fixed selectors — feasible with 2^32 brute force, similar difficulty to the original Ambire report; (2) getting the user to sign such a transaction through a compromised/malicious dApp or wallet UI, and (3) getting the victim (or a relayer acting on the attacker's behalf, since `target` is relayer-supplied and unauthenticated) to submit it with `target` equal to the victim's own account. This mirrors the judged severity in the original report: plausible but not trivial, and the wallet team/relayer's honesty assumptions reduce, but do not eliminate, likelihood. It is not a pure network/validator-only or mocked-only issue — the path is reachable purely through the `rlp_execute` public contract method, i.e., through ordinary submitted transactions/contract calls.

### Recommendation
Do not rely on a bare 4-byte selector namespace shared with the broader Ethereum ABI ecosystem to gate privileged self-actions (`AddKey`/`DeleteKey`). Consider: reserving a much larger, non-guessable discriminator for privileged self-actions; requiring these actions be signed with an explicit, human-readable domain-separated message (e.g., EIP-712-style typed data) rather than raw ABI-encoded selectors that look identical to arbitrary contract calls; or restricting `AddKey`/`DeleteKey` dispatch to a specific `to` value/marker that cannot be confused with a normal dApp interaction target, combined with strong user-facing warnings whenever a transaction's target equals the signer's own address.

### Proof of Concept
1. Attacker searches (offline, brute force over function signatures) for a Solidity-style function signature whose `keccak256` first 4 bytes equal `ADD_KEY_SELECTOR = 0x753ce5ab` (analogous search cost to standard 4-byte selector clash attacks), and whose parameter list can be filled to also parse under `ADD_KEY_SIGNATURE = [uint8, bytes, uint64, bool, bool, uint128, string, string[]]` [3](#0-2) .
2. Attacker (as, or via, a malicious dApp/relayer) crafts calldata: selector `0x753ce5ab` + ABI-encoded `(public_key_kind, attacker_public_key_bytes, nonce, is_full_access=true, is_limited_allowance=false, allowance=0, receiver_id="", method_names=[])`, disguising it in their dApp UI as an innocuous action (e.g. "claim rewards").
3. Victim's Ethereum-style wallet software signs the raw transaction (`to` = victim's own eth-implicit address, i.e. `context.current_address`), producing `tx_bytes_b64`.
4. The relayer (attacker) calls `rlp_execute(target = victim_account_id, tx_bytes_b64)`. `validate_tx_relayer_data` passes because `tx.address == context.current_address` and `to == context.current_address` gives `TargetKind::CurrentAccount` [9](#0-8) .
5. `parse_tx_data` matches `ADD_KEY_SELECTOR`, decodes the (attacker-crafted) args, and returns `Action::AddKey{ is_full_access: true, public_key: attacker_key, .. }` as a `SelfNearNativeAction`, which is executed unmodified since target is `CurrentAccount` [7](#0-6) .
6. `try_into_near_action` converts this into `near_action::Action::AddKey` with `AccessKeyPermission::FullAccess` [4](#0-3) , which is then promised/executed against the victim's account, granting the attacker's public key full control.

fn parse_tx_data(
    target: &AccountId,
    tx: &NormalizedEthTransaction,
    fee: NearToken,
    context: &ExecutionContext,
) -> Result<(Action, ParsableTransactionKind), Error> {
    if tx.data.len() < 4 {
        return Err(Error::User(UserError::InvalidAbiEncodedData));
    }
    match &tx.data[0..4] {
        FUNCTION_CALL_SELECTOR => {
            let (receiver_id, method_name, args, gas, yocto_near): (String, _, _, _, _) =
                ethabi_utils::abi_decode(&FUNCTION_CALL_SIGNATURE, &tx.data[4..])?;
            if target.as_str() != receiver_id.as_str() {
                return Err(Error::Relayer(RelayerError::InvalidTarget));
            }
            if yocto_near >= MAX_YOCTO_NEAR {
                return Err(Error::User(UserError::ExcessYoctoNear));
            }
            Ok((
                Action::FunctionCall { receiver_id, method_name, args, gas, yocto_near },
                ParsableTransactionKind::NearNativeAction,
            ))
        }
        TRANSFER_SELECTOR => {
            let (receiver_id, yocto_near): (String, u32) =
                ethabi_utils::abi_decode(&TRANSFER_SIGNATURE, &tx.data[4..])?;
            if target.as_str() != receiver_id.as_str() {
                return Err(Error::Relayer(RelayerError::InvalidTarget));
            }
            if yocto_near >= MAX_YOCTO_NEAR {
                return Err(Error::User(UserError::ExcessYoctoNear));
            }
            Ok((
                Action::Transfer { receiver_id, yocto_near },
                ParsableTransactionKind::NearNativeAction,
            ))
        }
        ADD_KEY_SELECTOR => {
            let (
                public_key_kind,
                public_key,
                nonce,
                is_full_access,
                is_limited_allowance,
                allowance,
                receiver_id,
                method_names,
            ) = ethabi_utils::abi_decode(&ADD_KEY_SIGNATURE, &tx.data[4..])?;
            Ok((
                Action::AddKey {
                    public_key_kind,
                    public_key,
                    nonce,
                    is_full_access,
                    is_limited_allowance,
                    allowance,
                    receiver_id,
                    method_names,
                },
                ParsableTransactionKind::SelfNearNativeAction,
            ))
        }
        DELETE_KEY_SELECTOR => {
            let (public_key_kind, public_key) =
                ethabi_utils::abi_decode(&DELETE_KEY_SIGNATURE, &tx.data[4..])?;
            Ok((
                Action::DeleteKey { public_key_kind, public_key },
                ParsableTransactionKind::SelfNearNativeAction,
            ))
        }
        _ => {
            let (action, emulation_kind) = eth_emulation::try_emulation(target, tx, fee, context)?;
            Ok((action, ParsableTransactionKind::EthEmulation(emulation_kind)))
        }
    }

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }

    Ok(target_kind)
}
