### Title
Webhook `shop` (tenant) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies solely against that body using the app's single, shop-independent `api_secret_key`. The `shop` (`x-shopify-shop-domain`), `topic`, and `webhook-id` headers used by `ShopifyAPI::Webhooks::Registry.process` to route and label the event to a specific merchant are never part of the signed material.

### Finding Description
Shopify webhook HMACs are computed with the app's `client_secret`, which is identical for every shop that installs the app — it is not a per-shop or per-request secret. Because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) equals `@raw_body` only, any HTTP request whose body byte sequence matches a previously-observed, legitimately-signed webhook body will pass `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) regardless of which `shop-domain` header accompanies it. [1](#0-0) [2](#0-1) 

`Registry.process` trusts the `shop` value derived purely from this unauthenticated header and forwards it to the consuming app's handler as the tenant identity for the event, together with the (HMAC-covered) body: [3](#0-2) [4](#0-3) 

The identity binding this breaks is: `hmac(raw_body, api_secret_key)` should equal `hmac(raw_body ‖ shop, api_secret_key)` in the attacker's mental model of "this HMAC authenticates this webhook for this shop" — but the gem never binds `shop` into the signed bytes at all. Since `api_secret_key` is shared across every shop that installs the app, any merchant who has legitimately installed the app receives real, validly-signed webhook deliveries for their own store's events. That merchant can replay the exact same body+HMAC to the app's webhook endpoint while substituting a different value in `x-shopify-shop-domain` (or `shopify-shop-domain`), and `HmacValidator.validate` will still return `true` because it never inspects headers.

### Impact Explanation
This breaks the cross-tenant boundary the gem is meant to enforce for webhook delivery. A host application that (reasonably, given the gem's API) treats `WebhookMetadata#shop`/`data.shop` as an authenticated tenant identifier will process attacker-supplied or replayed body content under another shop's identity — e.g., attributing a fake `orders/create`, `app/uninstalled`, or GDPR-style payload to a victim shop, corrupting per-tenant state, or triggering tenant-scoped side effects (data deletion flows for `customers/redact`, `shop/redact`, etc.) against a shop the attacker does not control. This matches the "cross-tenant access" Critical impact category, since the tenant binding (`shop` field) is not covered by the same authentication mechanism (`HMAC`) that is supposed to authenticate the request as a whole.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate, unprivileged merchant who has installed the target app on their own store (a normal, self-service action requiring no special privilege or leaked secret) — they need no access to `api_secret_key`, access tokens, or any other credential. They passively capture one real, Shopify-signed webhook delivery for their own shop, then replay it to the app's public webhook endpoint with a forged `shop-domain` header value naming a different installed shop. No cooperation from Shopify, from the victim shop, or from privileged infrastructure is needed, making this reasonably easy to carry out for any app operator who trusts `Registry.process`'s `shop`/`data.shop` value as an authenticated tenant identifier.

### Recommendation
Bind the tenant/routing headers into the signed material, or otherwise cryptographically tie `shop`, `topic`, and `webhook-id` to the HMAC check — e.g., include them (in canonical form) in `to_signable_string`, or independently verify that the `shop` header corresponds to a shop with a currently valid, stored session/access token for this app before dispatching to the handler. At minimum, document prominently that `data.shop` from `Registry.process` is not authenticated by the HMAC and must be cross-checked by the host application against its own known-installed-shops list before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, completing OAuth normally (no special privilege required).
2. Attacker triggers an event on their own store (e.g., updates an order) so Shopify sends a real webhook to the app's registered endpoint, with body `B` and header `x-shopify-hmac-sha256: H = HMAC-SHA256(api_secret_key, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays an HTTP POST directly to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches `H`, so validation succeeds.
5. The handler executes with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled body content is processed as if it originated from `victim-shop.myshopify.com`, despite `victim-shop` never having sent this webhook. [5](#0-4)
