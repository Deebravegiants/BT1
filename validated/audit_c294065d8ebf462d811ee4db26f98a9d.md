### Title
Webhook HMAC does not cover the `shop-domain` or `topic` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request **body**. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are all read from unauthenticated HTTP headers and are never included in the signed payload. This breaks the identity binding `shop that produced a valid HMAC == shop attributed to the processed webhook data`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from headers that are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, and other header-derived fields to dispatch the webhook, with no independent cross-check that the `shop` header actually corresponds to the shop that legitimately produced that HMAC/body combination: [4](#0-3) 

Because the signature covers only the body, any two webhook deliveries (from any shop, at any time) that happen to carry byte-identical bodies will have byte-identical valid HMACs. An unprivileged internet user who legitimately installs the app on their own store can generate a webhook delivery with body content of their choosing (for many topics, the merchant substantially controls the resulting JSON, e.g., product/order field values) and obtain a Shopify-computed, valid HMAC for it. They can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) to name a different, victim shop. `HmacValidator.validate` will accept the request because it only checks the body signature, and `Registry.process` will hand the attacker-chosen body to the registered handler tagged with the victim's `shop`, achieving cross-tenant data injection/confusion.

This is analogous to the reported bug class: a field that is *acted upon* (the `shop` identity used to attribute and process webhook data) is not covered by the authentication mechanism (the HMAC), exactly the "field acted on but not covered by the HMAC" pattern called out in the validation rules.

### Impact Explanation
This allows cross-tenant data injection: a request nominally authenticated as coming from Shopify for a given body can be attributed to any shop of the attacker's choosing merely by spoofing an HTTP header, since none of `shop-domain`, `topic`, `webhook-id`, `api-version` are covered by the signature. Downstream applications built on this gem that trust `WebhookMetadata#shop` for tenant identification (a documented, intended use of the field) can have data written to, or actions performed against, the wrong tenant. This meets the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires only:
1. The attacker to be an ordinary merchant capable of installing the target app on their own (attacker-controlled) shop — no privileged access or leaked secrets needed.
2. The attacker to trigger a webhook whose body they can predict/control (feasible for many topics where webhook payloads mirror merchant-editable resource fields).
3. A generic HTTP request replay with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to the app's public webhook endpoint.

No access token, `client_secret`, or TLS interception is required, and the request path (public webhook endpoint) is designed to be internet-reachable by definition.

### Recommendation
Bind the authenticated identity to all header fields that are subsequently trusted:
- Include `shop-domain`, `topic`, `webhook-id`, and `api-version` (or at minimum `shop-domain` and `topic`) in the HMAC signable payload, or
- Independently verify that the `shop` header value belongs to a shop with an active, known installation/session for this app before dispatching the handler, rather than trusting it purely because the body signature validated.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers, e.g., a products/update webhook with a body they fully control:
raw_body = '{"id":1,"title":"anything-the-attacker-wants"}'

# Shopify computes and delivers a *genuine* HMAC for this body using the app's real secret:
genuine_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Step 2: Attacker replays the identical body+hmac to the app's public webhook endpoint,
# but forges the shop-domain header to point at the victim shop:
headers = {
  "x-shopify-topic"        => "products/update",
  "x-shopify-hmac-sha256"  => Base64.encode64(genuine_hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (only body is checked), handler is invoked
#    with WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```
