### Title
Webhook shop/topic/id identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values entirely from HTTP headers, while `Utils::HmacValidator` (invoked in `Registry.process`) only verifies the HMAC over the raw request body. None of the header-derived identity fields are covered by the signature, so an attacker who possesses one valid `(raw_body, hmac)` pair for the shared app secret can replay it with forged identity headers and have it accepted as coming from a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-suppliable HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the raw body, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when dispatching to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the app's single, shared `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is one value per app — not per-shop — the HMAC only proves "this body was signed by Shopify for some webhook to this app," not "this body belongs to shop X." The equality the code implicitly (and incorrectly) assumes is:

`hmac_valid(raw_body) == (shop_header, topic_header, webhook_id_header are authentic for this raw_body)`

That equality does not hold: the header values are parsed but never bound into the HMAC-verified bytes.

### Impact Explanation
Any merchant who can install the target app on their own shop (a normal, unprivileged action) can capture a legitimate webhook delivery (raw body + valid `X-Shopify-Hmac-Sha256`) sent to their app URL, then resend that exact body/HMAC pair while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a different, victim shop's domain. Since `Registry.process` only checks the HMAC against the body, the forged request passes validation and is routed to the handler as `WebhookMetadata.new(topic:, shop: request.shop, ...)` with the attacker-chosen shop value. Any app logic keyed on `shop` (e.g., updating per-shop records, triggering `shop/redact`/`customers/redact` compliance actions, invalidating sessions, or writing audit logs attributed to the shop) can be forged against a shop the attacker doesn't control — a cross-tenant integrity/data issue.

### Likelihood Explanation
Requires only an app install by an unprivileged attacker-controlled shop plus the ability to POST arbitrary HTTP headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged credentials needed. This is realistically exploitable by anyone who can install the target app.

### Recommendation
Bind the identity fields into the signed payload verification, e.g., include `shop`, `topic`, and `webhook_id` header values as part of `to_signable_string` (matching Shopify's documented webhook verification, which signs the raw body — so instead the library should cross-check that the body's own `shop_domain`/topic fields, where present in the JSON payload, are consistent with the headers) or otherwise require the consuming app to independently verify `shop` against a known/installed shop list before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are unauthenticated header values and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's single shared secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`B`) using `Context.api_secret_key` — matches `H`, so validation passes:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [5](#0-4) 
4. The handler is invoked with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC only ever proved authenticity for `attacker-shop.myshopify.com`'s webhook, letting the attacker trigger shop-scoped app logic under a victim shop's identity.
