Audit Report

## Title
Front-running of user-chosen `CollectionId` in `pallet-uniques::create`, breaking batched `create + mint` extrinsics - (File: `substrate/frame/uniques/src/lib.rs`)

## Summary
`pallet-uniques::create` accepts a caller-chosen `CollectionId` and only rejects it if already in use via `ensure!(!Collection::<T, I>::contains_key(collection.clone()), Error::<T, I>::InUse)` in `do_create_collection`, with no allocator mechanism analogous to `pallet-assets`' `NextAssetId`. This confirms the code behaves exactly as claimed: an observer of a pending `create(id, ...)` transaction can front-run it with the same `id`, causing the original transaction — and any batched follow-on calls such as `mint` that depend on the same collection existing under the victim's control — to fail with `Error::InUse`.

## Finding Description
The `create` extrinsic passes the caller-supplied `collection: T::CollectionId` straight through to `Self::do_create_collection`, whose only uniqueness guard is the `contains_key` check shown above [1](#0-0) . `do_create_collection` performs no reservation, locking, or commit-reveal step prior to this check, so whichever transaction with a given `collection` id lands on-chain first claims the slot; the second is rejected outright [2](#0-1) . This matches the finding's core mechanics faithfully. Since Substrate/parachain transaction pools are public prior to block inclusion, and priority/tip ordering can be influenced by any account, an attacker can observe a victim's `create(id, admin)` (especially inside a `utility.batch_all` bundling `create` + `mint`) and resubmit `create(id, attacker)` with higher priority, causing the victim's batch to abort atomically when `create` reverts with `InUse`.

## Impact Explanation
The impact is a griefing/availability issue, not fund loss or state corruption: the attacker merely claims an empty collection at the cost of `CollectionDeposit`, and the victim's batched transaction fails and must be resubmitted with a new id. This is consistent with the low-severity classification given in the report itself and does not rise to fund loss, protocol insolvency, or privilege escalation.

## Likelihood Explanation
The claim's own likelihood analysis is honest and appropriately hedged: it explicitly states it could not confirm whether `pallet-uniques::create` is exposed via an open/signed `CreateOrigin` on any currently maintained runtime (e.g., Asset Hub). I attempted to verify this in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` and `asset-hub-rococo/src/lib.rs`, which do wire `impl pallet_uniques::Config for Runtime`, but I could not conclusively determine, within available tool budget, whether `CreateOrigin` there is bound to an open signed origin, a permissioned origin, or effectively unreachable via a deprecated/disabled call filter. `pallet-uniques` is also explicitly documented in-repo as superseded by `pallet-nfts`, which does not have this issue because it auto-increments `NextCollectionId` rather than accepting a caller-chosen id [3](#0-2) , further narrowing real-world exposure. Given this, the report's likelihood section correctly flags this as an open question the researcher was unable to resolve.

## Recommendation
Same as submitted: adopt an auto-incrementing `NextCollectionId`-style allocator for `pallet-uniques::create` (mirroring `pallet-nfts` and `pallet-assets`'s `AssetIdAllocator`), or deprecate/restrict the permissionless caller-chosen-id `create` path in favor of `force_create`/`pallet-nfts` for new deployments.

## Proof of Concept
1. Victim constructs `utility.batch_all([Uniques::create(X, victim), Uniques::mint(X, item, victim)])` and broadcasts it.
2. Attacker observes `X` in the mempool and submits `Uniques::create(X, attacker)` with a higher tip.
3. Attacker's transaction is included first; `Collection::<T,I>::contains_key(X)` becomes `true` per `do_create_collection`.
4. Victim's batch executes; `create(X, ...)` hits the `InUse` check and fails, and `batch_all` reverts the entire batch, so the intended `mint` never executes.

This reproduces cleanly as a unit test within `substrate/frame/uniques/src/tests.rs` by calling `create` twice with the same `collection` id from different accounts and observing the second call return `Error::<T,I>::InUse`, then wrapping the first `create`+`mint` sequence in `pallet_utility::batch_all` and showing that an interleaved competing `create` aborts the batch.
