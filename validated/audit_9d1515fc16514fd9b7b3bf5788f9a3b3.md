### Title
Webhook shop/topic identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, while the `shop` (and `topic`) values used to route and identify the tenant are taken from HTTP headers that are never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` and `#topic` are read directly from headers, which are not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then builds `WebhookMetadata` using `request.shop` (and `request.topic`) — values that were never bound to the signature: [4](#0-3) 

The equality this breaks is: `shop authenticated (via HMAC) == shop used to route/attribute the webhook data`. Only the request body is bound to the HMAC; the `x-shopify-shop-domain` / `shopify-shop-domain` header used to identify which tenant the payload belongs to is unauthenticated. Any party that has ever received one legitimately-signed webhook body/HMAC pair for their own shop (e.g., a merchant who has installed the app, hence "unprivileged" from the multi-tenant app's perspective) can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still succeed because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
Host applications built on this SDK are expected to trust `WebhookMetadata#shop` to determine which tenant record to update (this is the SDK's documented contract — the handler receives `shop` as the tenant identifier). Because that field is not covered by the HMAC, an attacker who controls one legitimate app installation can forge webhook data attributed to a different (victim) shop, achieving cross-tenant data injection/confusion in the host app's per-tenant records — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Any merchant who installs the app receives real webhook deliveries with valid `(body, hmac)` pairs for their own store. Capturing and replaying such a pair with a modified `shop-domain` header requires no secret material, no privileged access, and only the ability to send an HTTP request to the app's public webhook receiver — a low bar for an "unprivileged internet user" in the multi-tenant app model this SDK is designed for.

### Recommendation
Bind the `shop` (and `topic`, `webhook-id`, `api-version`) headers into the signed material verified by `HmacValidator`, or independently verify that the `shop` header corresponds to a shop that actually has an active webhook registration/session before dispatching to handlers, so that the authenticated identity (HMAC-covered) matches the identity acted upon (`WebhookMetadata#shop`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app's endpoint: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same `raw_body: B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — passes.
5. `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes attacker-controlled data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
