### Title
Tokens sent to or left on the Controller are permanently frozen — no recovery entrypoint exists - (File: contracts/controller/src/lib.rs)

### Summary
Analogous to `renounceVesting` being unable to return ETH, the XOXNO Lending `Controller` contract can hold arbitrary token balances but exposes no entrypoint that can move them out. Every outflow from the controller is a measured, delta-bounded forward tied to a specific operation (`claim_revenue`, strategy refunds, liquidation legs). Stranded balances — direct token transfers to the controller address, undeclared tokens delivered during a `flash_position` callback, or dust left by a receiver — have no path out and are locked permanently, since `upgrade` is the only mechanism that could add a sweep and it is governance-gated.

### Finding Description
The controller routinely holds token custody mid-flow: it measures balance deltas for collateral deposits and refunds in `flash_position`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `migrate_from_blend`, and it forwards measured revenue in `claim_revenue`. None of these paths can touch a pre-existing balance:

- `flash_position` refunds only positive deltas of refund-declared tokens; the docs state explicitly: "An undeclared token left on the controller is neither deposited nor refunded" (skills/xoxno-lending-contracts/flash-loans.md:134) and "Neither category sweeps prior balances" (docs/explanation/threat-model.md:173).
- The regression test `claim_revenue_forwards_the_measured_amount_and_leaves_controller_dust_intact` pins that stranded controller dust "no balance-delta measurement can ever claim" (tests/test-harness/tests/controller/outbound_transfer_measurement.rs:148-151, tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5).
- The full permissionless entrypoint inventory (scripts/permissionless_entrypoints.txt:49-59) contains no sweep/recover/rescue function, and the controller ABI in `contracts/controller/src/lib.rs` exposes only account-scoped operations — no generic `transfer`/`sweep`.

Unlike the pool — where an unbooked donation is fungible with shared custody and can still leave through other users' withdraws/borrows — tokens held by the controller are unreachable by any code path, so the freeze is permanent rather than temporary.

### Impact Explanation
Permanent freezing of funds. Any token balance on the controller address is locked forever: no user, governor, or automated flow can extract it. This covers (a) direct token transfers to the controller — explicitly reachable by any unprivileged address, (b) tokens a flash receiver or intermediate contract pushes to the controller during `execute_flash_position` that are not in the declared collateral/refund lists, and (c) residual strategy balances. The loss equals the full stranded amount.

### Likelihood Explanation
Medium. There is no guard preventing transfers *into* the controller (only borrow/withdraw recipients equal to the controller are rejected via `INVALID_FLASHLOAN_RECEIVER`; inbound `token::transfer` calls are unrestricted). Third-party strategies — DeFindex-style adapters, liquidation bots, aggregators — are the realistic source of stray balances, and the flash-callback design actively invites contracts to deliver tokens to the controller. However, the loss requires a party to err (send a non-declared token or donate), so exploitation is not adversarially triggered against others; it is self-inflicted/asset-recovery in nature, matching the reported bug class.

### Recommendation
Add an owner-gated recovery entrypoint on the controller, e.g. `sweep(recipient: Address, tokens: Vec<Address>)`, that transfers out balances not attributable to any in-flight operation. Since the controller holds no booked balances between transactions, any token balance present outside an active callback is stray by definition and safe to sweep. Alternatively, `flash_position` could auto-refund positive deltas for any token, not only declared ones.

### Proof of Concept
1. Any address calls `token::transfer(victim, controller, amount)` on any SAC/SEP-41 token. The tokens now sit on the controller address.
2. Alternatively, a `FlashPositionReceiver` contract, inside `execute_flash_position`, transfers a token that is absent from both `collaterals` and `refund_assets` in `FlashPositionParams` to `params.controller`. Post-callback, the controller measures only declared deltas, so the token is neither credited nor refunded (flash-loans.md:130-135).
3. Enumerate every controller entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `flash_position`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `update_indexes`, `claim_revenue`, `update_account_threshold`, `recapitalize`): none can produce an outbound transfer of the stranded token — each outbound leg is bound to a measured receipt or an account position.
4. Result: `token::balance(controller)` retains the amount permanently; only a WASM upgrade (privileged, out of scope) could recover it.
