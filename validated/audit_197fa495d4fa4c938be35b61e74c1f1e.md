### Title
Budget-capped HyperSwap pre-seed rebalance lets an attacker force graduation to seed the protocol's locked LP into a pool priced materially off the bonding-curve close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds the HyperSwap V2 TOKEN/LT pool via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`. When an attacker front-runs graduation by creating the pair and self-funding a highly lopsided `pair.mint`, the corrective rebalance swap that is supposed to restore the curve-close ratio is capped at 99% of the protocol's available inventory on the swapped side (`_swapBudget`). For sufficiently extreme pre-seed ratios this cap binds before the pool ratio is corrected, so `finalizeGraduation` completes — by design, to avoid bricking — but permanently locks the protocol's LP into a pool that opens materially off the curve's true close price. This is the same "manipulate reserves before a price gets locked in" class as the Channels Finance/Compound-v2 style price-manipulation report, mapped onto alt.fun's own graduation-time LP seeding rather than a lending market.

### Finding Description
Graduation is split across two transactions (`packages/contracts/AGENTS.md` "Two-Phase, Dynamic LP Seeding"). Phase 1 (`_enterGraduating`) caches `tokensForLP` and `ltFromPair` at the exact curve-close ratio. Phase 2 (`finalizeGraduation`, permissionless) seeds a real HyperSwap V2 pair. Because `factory.createPair` and `pair.mint` are permissionless on any V2 fork, an attacker can, between phase 1 and phase 2:

1. Call `factory.createPair(token, lt)` themselves.
2. `transfer` a self-chosen, highly asymmetric `(reserveToken, reserveLT)` into the pair and call `pair.mint(attacker)`.

`_seedUniswapV2Direct` ( [1](#0-0) ) detects this as a non-empty pool (`totalSupply() != 0`) and routes to `_seedRebalancing`, which tries to correct the ratio via a single direct `pair.swap` (`_pairRebalance`, [2](#0-1) ) before depositing the remaining inventory through the canonical `router.addLiquidity` (`_routerDepositAndDispose`).

The corrective swap input is capped by `_swapBudget`, which reserves only 99% of the available side's balance for the swap: [3](#0-2) 

The natspec explicitly documents that for "catastrophic pre-seeds beyond our budget capacity" this cap binds and the alternative would be bricking `finalizeGraduation` — so the code deliberately proceeds anyway. The team's own regression test proves the resulting pool opens more than 20% off the curve-close price in this regime: [4](#0-3) 

The test only asserts that the *pre-seeder* does not profit (`claimValue <= depositValue`); it does not assert that the protocol's own locked LP retains fair value. Once `finalizeGraduation` completes, `LPLock.recordLock` finalizes the position ( [5](#0-4) ) and `LPLock` has no withdraw path in v1 (per `docs/contracts-scope.md` and `AGENTS.md`), so the mispriced position is permanent. Any third-party arbitrage bot (not necessarily the original pre-seeder) that trades the pool back toward the true market price extracts value directly from this permanently-locked LP, which represents the community's/protocol's curve-raised LT and reserved 250M tokens (`LP_RESERVE`) — i.e., the graduation proceeds of every curve trader who bought into that token.

### Impact Explanation
This is a concrete, permanent value loss on LP funds that can never be recovered (`LPLock` has no rescue/withdraw path), satisfying the "LP seeded away from the curve close price" / "permanent freezing of ... LP funds" impact bucket. The magnitude scales with how far the attacker can push the pre-seed ratio beyond the 99%-budget threshold, and the test explicitly demonstrates a >20% price gap is achievable and accepted by the current mitigation as an "unrecoverable" residual for the *protocol's* LP (only the attacker's own non-profit is guaranteed).

### Likelihood Explanation
Medium. It requires an attacker to front-run a specific token's `finalizeGraduation` window (a `Cloudflare Worker` keeper normally finalizes within ~60s of `TokenGraduating`) with a large, deliberately lopsided LT/Token pre-seed sized precisely to exceed the 1%-reserved rebalance budget. This needs meaningful capital (multiples of `ltFromPair`/`tokensForLP`) and precise timing, but nothing else is privileged — `factory.createPair` and `pair.mint` are permissionless HyperSwap V2 calls, exactly the "pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation" surface explicitly listed as in-scope for unprivileged reachability.

### Recommendation
Either (a) widen the rebalance budget dynamically or split the correction into a bounded number of iterative swaps so the ratio can be driven arbitrarily close to target regardless of the pre-seed's magnitude, capping the residual price gap to a small, fixed bound rather than "whatever fits in one 99%-budget swap"; or (b) if the corrective swap cannot close the gap within budget, deposit into a fresh, protocol-controlled pair/position (skip depositing into the hostile pool at all) and let `finalizeGraduation` retry once liquidity conditions allow a bounded-gap seed, rather than unconditionally locking the mispriced LP forever via `LPLock`.

### Proof of Concept
Reference the existing regression test that already demonstrates the residual, `testFuzz_hostilePreSeed_neverProfitable_neverBricks` / the M-02 scenario immediately preceding it in `test/TwoPhaseGraduation.t.sol`: [4](#0-3) 

This sets `reserveToken = tokensForLP / 100` and `reserveLt = ltFromPair * 200` via `_grieferMintPreSeed`, confirms the optimal rebalance swap exceeds the per-side budget, calls `bonding.finalizeGraduation(tokenAddr)`, and asserts the resulting pool price is more than 20% off the curve-close ratio (`assertGt(_poolPriceLtPerToken(...), ((ltFromPair*1e18/tokensForLP)*12)/10, ...)`) while `bonding.isGraduated(tokenAddr)` succeeds — i.e., the protocol's locked LP is committed at a materially wrong price with no recovery path.

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

        deal(tokenAddr, griefer, reserveToken);

        bonding.finalizeGraduation(tokenAddr);

        // price, is worth a fraction of what they deposited — the attack is
        // cost-negative.
        uint256 claimValue = _lpValueAtCurveClose(hyperPair, tokenAddr, grieferLp, tokensForLP, ltFromPair);
        uint256 depositValue = _depositValueAtCurveClose(reserveToken, reserveLt, tokensForLP, ltFromPair);
        assertLe(claimValue, depositValue, "pre-seeder must not profit (P&L <= 0)");
        assertLt(claimValue * 2, depositValue, "pre-seeder must lose materially, not merely break even");
