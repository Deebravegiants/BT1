### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, and `webhook_id` values are read from unauthenticated HTTP headers. Since the HMAC never binds these header values to the signed payload, a merchant who legitimately receives a validly-signed webhook for their own shop can replay that exact `(body, hmac)` pair while forging a different `x-shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic.

### Finding Description
`AuthQuery`, used in the OAuth callback flow, mixes in `Utils::VerifiableQuery` and its `to_signable_string` explicitly includes `shop` (and `host`, `code`, `state`, `timestamp`) in the signed content: [1](#0-0) 

By contrast, `ShopifyAPI::Webhooks::Request` also includes `Utils::VerifiableQuery`, but its `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are derived purely from caller-supplied HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC only over `to_signable_string`, i.e. only over the raw body, and compares it against the received `hmac` header: [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` relies exclusively on this HMAC check before dispatching to the handler with the (unauthenticated) `request.shop`: [5](#0-4) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant that installs the app can capture a genuinely-signed `(raw_body, hmac)` pair for their own shop's webhook traffic. That pair remains valid under `HmacValidator.validate` regardless of which `shop-domain` header accompanies it, since the header is never part of the signed content. The equality the code should enforce — `shop-domain header == shop bound inside the HMAC-signed payload` — does not hold: the left side is attacker-controlled, the right side doesn't exist.

### Impact Explanation
An attacker who is a legitimate merchant of the target app can replay a validly-signed webhook body while substituting an arbitrary victim `x-shopify-shop-domain` (and/or `topic`/`webhook-id`) header. `ShopifyAPI::Webhooks::Registry.process` will treat the forged shop as authentic and invoke the app's webhook handler with `WebhookMetadata#shop` set to the victim shop while `body` is attacker-controlled content. Any host application that uses `WebhookMetadata#shop` to select the tenant context for processing (e.g., loading/updating the victim's records, associating mutated data or app state to the victim's shop) will act on attacker-supplied data under the identity of a different tenant — a cross-tenant data-integrity breach that satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite is only that the attacker be able to install/use the target Shopify app on their own store (a normal, unprivileged action for any merchant) in order to obtain one genuinely-signed webhook payload, and then send an HTTP request with a forged `shop-domain` header carrying the captured body and HMAC to the app's webhook endpoint. No access to `api_secret_key`, tokens, or the victim's credentials is required, making this reachable by any unprivileged internet user who can install the app.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise cryptographically tie the `shop-domain` header to the signature, e.g. by including `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values in `to_signable_string` (mirroring how `AuthQuery#to_signable_string` binds `shop`, `host`, etc.), so that `HmacValidator.validate` fails if any of these headers are altered independently of the body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the legitimate `raw_body` and `x-shopify-hmac-sha256` value sent by Shopify — both are valid under the app's `api_secret_key`.
2. Send a POST to the app's webhook endpoint with the same `raw_body` and the same `x-shopify-hmac-sha256`, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally alter `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [6](#0-5)  — validation succeeds because the body/HMAC pair is genuinely signed, and the forged `victim-shop.myshopify.com` is passed to the handler as `request.shop` [7](#0-6) , causing the host application's handler to process attacker-controlled data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
