### Title
Anyone can permanently block a fee-token migration by donating dust to the EvmHost contract - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal()` refuses to change `feeToken` unless the host's balance of the *old* fee token is exactly zero. Because that balance is a plain `IERC20.balanceOf` check on a public, permissionless ERC-20, any unprivileged address can `transfer` 1 wei of the current fee token to the host contract at any time and permanently block the cross-chain governance call that would otherwise migrate the fee token, exactly mirroring the reported `updatePayoutToken()` bug class (checking `balance == 0` on a value anyone can top up).

### Finding Description
In `updateHostParamsInternal`, before applying new `HostParams`, the code enforces: [1](#0-0) 

```solidity
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

`oldFeeToken` (e.g. DAI) is an ordinary ERC-20 whose `transfer()` function anyone can call with no permission check. An attacker (or even a benign relayer paying protocol fees) simply calls `feeToken.transfer(address(evmHost), 1)` at any point after the host's revenue has been swept to zero. From then on, `EvmHost.balanceOf(oldFeeToken)` is non-zero again, and any subsequent `updateHostParams` call from the legitimate `hostManager` (itself gated by cross-chain governance via `restrict(_hostParams.hostManager)`) reverts with `CannotChangeFeeToken`: [2](#0-1) [3](#0-2) 

This is the exact bug class from the external report: a `balance == 0` gate on a caller-influenceable token balance can be permanently violated by a single unprivileged 1-wei transfer, making the guarded state-transition (changing the payout/fee token) impossible.

### Impact Explanation
The `feeToken` is the asset the host collects for dispatching cross-chain requests and the asset governance withdraws as bridge revenue (`withdraw()`). If a fee token needs to be migrated (e.g. deprecated stablecoin, compromised/depegged token, or a required security response), governance's only path is `updateHostParams`, which this dust-donation permanently blocks. This is a High-severity griefing vector: it removes a critical admin/governance recovery capability from a live, funded bridge host with a single, cheap, repeatable transaction, and there is no way to sweep or ignore the stuck dust since the check is unconditional on any positive balance.

### Likelihood Explanation
Trivial and cheap to execute: the attacker needs only 1 wei of the current fee token and a single `transfer` call to the `EvmHost` address, repeatable indefinitely after every sweep attempt. No special permissions, timing, or race condition are required — this can be front-run against any pending governance fee-token migration or simply done pre-emptively to keep the host permanently pinned to the current fee token.

### Recommendation
Remove the `balance != 0` gate from `updateHostParamsInternal` (mirroring the report's recommendation), or replace it with a governance-controlled sweep/withdraw step that is executed atomically as part of the same params update rather than requiring a separate pre-condition on an externally-manipulable balance. If preserving old-token draining is desired, perform an internal sweep-to-treasury of the residual balance during the update itself instead of reverting.

### Proof of Concept
1. Governance holds `feeToken = DAI`; host's DAI balance is swept to 0 in preparation for migrating to `feeToken = USDC`.
2. Attacker calls `DAI.transfer(address(evmHost), 1)` (no permission required).
3. Cross-chain governance dispatches `updateHostParams` with `params.feeToken = USDC`; the call reaches `updateHostParamsInternal`, checks `IERC20(DAI).balanceOf(address(this)) != 0` → true → reverts `CannotChangeFeeToken`.
4. Governance cannot migrate the fee token; attacker can repeat step 2 indefinitely (or repeat before any future sweep completes) to keep the host locked. [4](#0-3)

        feeToken.mint(address(host), 1 * 1e18);
        HostParams memory params = host.hostParams();
        params.feeToken = address(this);
        // we can't set host params
        vm.prank(host.hostParams().admin);

        // we can set host params
