## Finding

### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats the incoming webhook's `shop` field as an authenticated tenant identifier, but that field is read from an HTTP header that is never included in the HMAC-signed material. Any party who can produce a `(raw_body, hmac)` pair that is valid for the app's shared `api_secret_key` — e.g. a merchant who installed the app and received a genuine webhook to their own shop — can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. The HMAC check still passes, and the handler is invoked believing the payload originated from the spoofed shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

None of the Shopify-supplied headers — `shop`, `topic`, `api_version`, `webhook_id` — are folded into the signable string. `Utils::HmacValidator.validate` computes/compares the HMAC purely against that signable string: [2](#0-1) 

`Registry.process` gates only on this body-only HMAC check, then trusts `request.shop` (parsed straight from the header, see `Request#shop`) to build the `WebhookMetadata` passed to the application's handler: [3](#0-2) [4](#0-3) 

Because every shop installing the same app shares one `api_secret_key`, the HMAC over the body is identical regardless of which shop it was addressed to. This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == authenticated_shop`, but the equality that is actually proven is only `hmac_valid(body, shared_secret) == true`; the `shop` header is never part of what's authenticated.

### Impact Explanation
An attacker who legitimately installs the target app on their own shop (unprivileged relative to other tenants) receives real webhooks with valid `(body, hmac)` pairs signed with the app's shared secret. By resending the identical body/HMAC to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, the request passes `HmacValidator.validate` and the application-level handler executes as though the event genuinely originated from the victim tenant. Depending on what the host application does inside its webhook handler (e.g., looking up the victim's stored session/access token by `data.shop` and performing actions, or writing attacker-controlled body data into the victim's tenant-scoped records), this enables cross-tenant data injection or cross-tenant action execution — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate-to-high in any app that has more than one merchant installed: obtaining a valid `(body, hmac)` pair only requires being one of the app's own users (no privileged credential, secret, or social engineering needed), and forging the header is trivial once such a pair is captured.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header value into the HMAC-signed material verified by this gem, or require callers to independently verify that `request.shop` corresponds to a session/shop the app already trusts before treating the payload as belonging to that shop. At minimum, `Utils::HmacValidator` and `Webhooks::Request#to_signable_string` should not present the header-derived `shop` as an authenticated value in `WebhookMetadata` without documenting that it is unauthenticated by the HMAC.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; Shopify delivers a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared secret) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` from their own inbox/logs.
3. Attacker POSTs to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — passes.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-supplied data under the victim's tenant identity. [3](#0-2)
