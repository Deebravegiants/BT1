Based on the investigation, I found a valid analog vulnerability in the webhook processing path.### Title
Webhook `shop` / `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and attribute the webhook are read from unauthenticated HTTP headers. This breaks the identity binding between the HMAC-verified bytes and the tenant/topic the library attributes the event to.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `hmac` is likewise derived purely from a header decoded from the request [2](#0-1) . `shop`, `topic`, and `webhook_id`, however, are all pulled straight from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) [3](#0-2) .

`Utils::HmacValidator.validate` verifies only that `to_signable_string` (the raw body) matches an HMAC computed with the app's single shared `Context.api_secret_key` [4](#0-3) . This secret is the same across every shop that has installed the app — it is not per-tenant. Once validation passes, `Registry.process` uses `request.shop` and `request.topic` (the unsigned header values) to build `WebhookMetadata` and dispatch the handler [5](#0-4) .

The binding that should hold is:
`shop_bound_by_hmac == shop_used_by_handler`

But in reality:
`hmac_valid_for(raw_body) == true` while `request.shop` is read from a header that is completely outside the signed content.

### Impact Explanation
Because the app-secret-based HMAC is shared across all shops/tenants of a multi-tenant app, and only the body bytes are covered, a request with a genuine `raw_body` + valid `hmac-sha256` header (captured from any one legitimate webhook delivery the attacker's own installed shop received) can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a different, victim shop domain. `HmacValidator.validate` still returns `true` (it only checked the body), and `Registry.process` will dispatch the handler with `shop: request.shop` set to the forged victim domain. This causes cross-tenant data/event confusion: the host application will process/store/act on webhook data as if it belongs to a different merchant than the one who actually authenticated the payload's origin.

### Likelihood Explanation
Any entity capable of getting the app installed on a shop it controls (a normal, unprivileged flow — no `api_secret_key`, access token, or privileged account needed) will receive genuine webhook deliveries with valid `raw_body`/`hmac-sha256` pairs for topics of interest (e.g., `orders/create`, `customers/data_request`). Replaying that exact body/HMAC pair while altering only the `shop-domain` header is a simple HTTP replay requiring no cryptographic secrets, since the header is never part of the signed content.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or the specific header values the app logic ultimately trusts) in the HMAC-signed content, or otherwise cryptographically bind them to the raw body before dispatch — e.g., by having `to_signable_string` incorporate the shop domain header, or by requiring host applications to independently verify that `request.shop` matches an installed/known session before invoking handlers. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must be independently validated against a known session store by the host app.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged onboarding flow) and registers a webhook (e.g., `customers/data_request`).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because computed with the shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H`, then sends a new HTTP request to the same endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) , `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against `H` [4](#0-3) , and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled webhook data under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
