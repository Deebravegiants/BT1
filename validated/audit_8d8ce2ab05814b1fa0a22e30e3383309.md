## Analysis

The reported bug class — raw ERC-20 transfers whose boolean success return value is never checked (in violation of the OpenZeppelin/ERC-20 pattern of using `safeTransfer`) — has a concrete, in-scope analog in the Tron variant of the intents escrow contract.

### Title
Unchecked ERC-20 `transfer` return value in intents escrow withdrawal permanently marks orders as filled without funds actually moving - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron port of the IntentGateway release escrowed tokens using a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call did not revert — never decoding/validating the ABI-encoded boolean return value. This is the exact anti-pattern the external report flags: OpenZeppelin's `SafeERC20.safeTransfer` exists precisely to guard against ERC-20 tokens that signal failure by returning `false` instead of reverting.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

and the fee payout right after it: [2](#0-1) 

and the `SweepDust` handler: [3](#0-2) 

`success` from a low-level `.call` only reflects whether the callee reverted; it says nothing about the decoded return data. Non-compliant/legacy ERC-20 tokens (and any token that returns `false` on failure rather than reverting, e.g. under a pause, blacklist, or insufficient-balance edge case within the token's own logic) will make this raw call return `success = true` with return data `abi.encode(false)`. The contract never inspects that returned boolean, so it proceeds as if the transfer succeeded.

Immediately after the "successful" but actually no-op transfer, the code:
1. Decrements the internal escrow accounting `_orders[body.commitment][token] -= amount`, and
2. Sets `_filled[body.commitment] = beneficiary`, permanently marking the order/commitment as settled.

This is a materially different (and weaker) implementation than the sibling EVM/general contracts in this repo, which consistently use `SafeERC20.safeTransfer`, e.g. in `IntentsBase.sol`: [4](#0-3) 
`safeTransfer` reverts on both a false return and non-standard/missing return data, which is exactly the protection missing from the Tron port.

### Impact Explanation
Because escrow bookkeeping and the "filled" state are updated unconditionally once the raw call doesn't revert, a token that returns `false` instead of reverting causes the contract to believe the beneficiary was paid when they were not. This results in permanent loss/freezing of the escrowed user funds: the commitment is marked filled/refunded (`_filled[commitment]` set, `EscrowReleased`/`EscrowRefunded` emitted) and the internal escrow balance is decremented, so the tokens can never be withdrawn again through the normal path, while the tokens never left the contract to reach the intended beneficiary. This meets the "permanent freezing of funds" bar for escrow-held intents funds.

### Likelihood Explanation
This path is reached on every `RedeemEscrow`/`RefundEscrow` `onAccept` delivery (permissionless relayer-delivered POST request) and every `onGetResponse` cancellation-refund flow — i.e., the core, unprivileged, high-frequency settlement path of the intents system on Tron. It fires for any token configured in an order whose implementation quietly returns `false` on failure, which is a well-documented and known class of ERC-20 tokens.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with how `IntentsBase.sol` and other Hyperbridge contracts already do it, so that both a reverting token and a token that returns `false` are treated as failures before escrow state is mutated and the order marked filled.

### Proof of Concept
1. An order escrows `amount` of a token `T` whose `transfer` implementation returns `false` (rather than reverting) under some internal condition (e.g., paused state, denylisted recipient, or non-standard implementation).
2. A relayer delivers a `RedeemEscrow`/`RefundEscrow` POST request (or a GET response for cancellation) targeting this order's commitment.
3. `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`. The call succeeds at the EVM level (`success == true`) because `T.transfer` returns `false` without reverting.
4. `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is set; `EscrowReleased`/`EscrowRefunded` is emitted — yet `beneficiary`'s token balance is unchanged.
5. The escrowed tokens remain locked in the `IntentGatewayV2` contract with no code path to retry or reclaim them, since the commitment is already marked filled.
