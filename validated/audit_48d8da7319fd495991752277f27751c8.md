This confirms the mechanism: `RuntimeError::ReceiptValidationError` propagates from `Runtime::apply` and is converted with `panic!("{}", e)` at [1](#0-0) , and `StorageError` from `process_state_update` is likewise turned into `panic!("{err}")` in `apply_chunk` except for a narrow allowlist (`FlatStorageBlockNotSupported`, `MissingTrieValue`) at [2](#0-1) . Since `validate_receipt` on dequeue is unconditionally checked for `max_actions_per_receipt` regardless of `ValidateReceiptMode` (line 69 in `action_validation.rs`, not gated by `mode == NewReceipt`), and `RuntimeConfigStore` selects config purely by the current epoch's protocol version floor lookup at [3](#0-2) , a delayed receipt admitted under an old (higher) `max_actions_per_receipt` limit that is tightened by a later protocol-version config diff will fail `validate_receipt` deterministically on every validator when the delayed queue is drained, producing a **chain-wide deterministic panic (chain halt)** — this is a legitimate reachable-from-unprivileged-transaction analog of the reported bug class (stale snapshotted value vs. later-tightened live minimum, with no on-chain recovery, all queueable paths bricked).

However, I need to check one more thing before finalizing: whether `CONFIG_DIFFS` (the sequence of protocol-version configuration diffs) has, historically or currently, ever *decreased* `max_actions_per_receipt` (or any other unconditionally-enforced `LimitConfig` field also checked for `ExistingReceipt` mode) — this is the fact needed to determine if the path is merely theoretical or concretely reachable given the current diff chain.### Title
Delayed receipts validated against a tightened live `LimitConfig` on dequeue cause a deterministic, unrecoverable chain-wide panic - ([File: runtime/runtime/src/lib.rs])

### Summary
This mirrors the reported bug class: a value snapshotted at admission time (a receipt's action count, sealed into the persistent delayed-receipt queue) is later checked against a *live*, separately-mutable minimum/maximum (`apply_state.config.wasm_config.limit_config`, selected purely by the *current* epoch's protocol version) with no reconciliation between the two. If the live limit is ever tightened below what the queued receipt already satisfies, the check fails deterministically on every validator and is treated as `StorageInconsistentState`, which is escalated to a hard `panic!` in the calling chain code — an irrecoverable, chain-wide halt with no on-chain remedy, exactly like the reported `queue()`/`updateDelay` brick.

### Finding Description
An unprivileged user can submit a function call whose execution creates an outgoing action receipt with up to `limit_config.max_actions_per_receipt` actions, validated at creation via `validate_actions_with_mode` in `ValidateReceiptMode::NewReceipt` mode [4](#0-3) . If the shard is congested, this receipt is not executed immediately but is admitted into the persistent, on-trie `DelayedReceiptQueue` [5](#0-4) , where it can remain for an arbitrarily long time.

When later popped for processing, `process_delayed_receipts` re-validates the receipt using `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` against the **current, live** `apply_state.config.wasm_config.limit_config` — i.e., the config picked for whatever protocol version is active *now*, not the one active when the receipt was admitted: [6](#0-5) 

Critically, `ValidateReceiptMode::ExistingReceipt` is documented as intentionally more lenient than `NewReceipt` specifically to tolerate receipts that were valid under older rules [7](#0-6) , but this leniency is incomplete: the `max_actions_per_receipt` (and total-prepaid-gas) checks inside `validate_actions_with_mode` are **not** gated by `mode` at all — they run unconditionally for both `NewReceipt` and `ExistingReceipt`: [4](#0-3) [8](#0-7) 

The `LimitConfig` used for this check is selected purely from the *current* protocol version via `RuntimeConfigStore::get_config`, floored to the nearest lower registered diff [3](#0-2) , with no per-receipt versioning or reconciliation against the limit that was in effect when the receipt was admitted to the queue. `RuntimeConfigStore`'s `CONFIG_DIFFS` chain is exactly the mechanism (analogous to Armada's governance-controlled `updateDelay`) by which this live value changes over time, gated purely by validator-vote-driven protocol upgrades [9](#0-8) .

If any future `CONFIG_DIFFS` entry lowers `max_actions_per_receipt` (or `max_total_prepaid_gas`, which is also checked unconditionally) below a value already satisfied by a receipt sitting in the delayed queue, `validate_receipt` returns `Err`, which is wrapped into `StorageError::StorageInconsistentState` [10](#0-9) . This propagates out of `Runtime::apply` as `RuntimeError::ReceiptValidationError`, which the chain layer converts unconditionally into `panic!("{}", e)` [11](#0-10) , or, if it instead surfaces as a generic `StorageError`, into `panic!("{err}")` for every storage-error variant except two explicitly allow-listed ones [2](#0-1) .

### Impact Explanation
Because the delayed-receipt queue and the chosen `RuntimeConfig` are both derived from consensus state (the trie and the epoch's protocol version), **every honest validator applying that chunk hits the identical failing check and panics identically** — this is not a divergence bug, it is a deterministic, network-wide chain halt. Recovery requires a further protocol/software hotfix and cannot be resolved by any in-protocol transaction, exactly mirroring the "no on-chain recovery, only a preventive veto before the trigger executes" structure of the original report. The entry point (submitting a large-action-count function call while the shard is congested) is fully reachable by an ordinary unprivileged account; the trigger (a future config diff tightening `max_actions_per_receipt`/`max_total_prepaid_gas`) is analogous to the governance-controlled parameter change in the original report.

### Likelihood Explanation
The historical `CONFIG_DIFFS` entries inspected (`53`–`157.yaml`, and materialized snapshots for versions 63, 69, 77, 78, 83, testnet-129) show `max_actions_per_receipt` has stayed constant at `100` in every version observed, so I could not confirm this specific decrease has ever actually shipped; `87.yaml` does touch related limit fields but its exact direction (increase vs. decrease) was not verified within the available tool budget. Likelihood is therefore assessed as **structural/latent** rather than actively exploited today: the vulnerable code path (unconditional `max_actions_per_receipt`/`max_total_prepaid_gas` checks in `ExistingReceipt` mode, live-vs-snapshot config mismatch with no reconciliation) exists and is reachable, but requires a future protocol upgrade to actually tighten one of these unconditionally-checked limits while a previously-admitted delayed receipt is still queued — a scenario core devs could inadvertently trigger, similar to how the original report's admin could inadvertently pick a value that "sits within the protected band."

### Recommendation
Reconcile delayed-receipt revalidation against the limits that were in effect at admission time rather than the live/current ones, or explicitly exempt `max_actions_per_receipt` / `max_total_prepaid_gas` from `ExistingReceipt`-mode enforcement the same way `max_receipt_size` and per-action checks already are, so a future config tightening cannot invalidate previously-admitted, already-buffered receipts. At minimum, treat this specific validation failure on dequeue as a soft/recoverable error path (e.g., permanently reject/refund without panicking, matching how issue #12606's oversized-receipt handling was made non-fatal) instead of escalating to `panic!`.

### Proof of Concept
Not runnable without a live protocol-version config diff that actually decreases `max_actions_per_receipt` or `max_total_prepaid_gas`; the following documents the exact trigger sequence based on code inspection:
1. Under protocol version `N`, an unprivileged account submits a `FunctionCall` that creates an outgoing action receipt with `actions.len() == limit_config(N).max_actions_per_receipt` (passes `NewReceipt` validation).
2. The receiving shard is congested, so the receipt is pushed into the persistent `DelayedReceiptQueue` [5](#0-4)  and remains queued across a protocol upgrade.
3. A future `CONFIG_DIFFS` entry at version `M > N` reduces `max_actions_per_receipt` below the receipt's action count.
4. Once the network activates version `M`, `process_delayed_receipts` pops this receipt and calls `validate_receipt(..., ExistingReceipt)` against `limit_config(M)` [6](#0-5) ; the unconditional `TotalNumberOfActionsExceeded` check in `validate_actions_with_mode` fails [12](#0-11) .
5. This is wrapped as `StorageError::StorageInconsistentState` and, via `Runtime::apply`'s error mapping, becomes `panic!` on every validator processing that chunk [11](#0-10) , halting the chain.
