### Title
DepositOnChainUtxos mints on-chain UTXOs for `address(0)` (native ETH) without requiring any ETH backing - (File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`DepositOnChainUtxosExternalAction.runAction` only performs a `transferFrom`/backing check for ERC20 tokens (`tokenAddress != address(0)`), while for `tokenAddress == address(0)` (native ETH) it skips any transfer or `msg.value` check entirely but still mints UTXOs with `amount = tokenTotal` into `utxoSet`. This allows an attacker to mint shielded/on-chain UTXOs denominated in ETH with zero backing.

### Finding Description
The claimed invariant is: for every UTXO minted, `sum(utxoAmounts for token T) == value actually transferred/escrowed for token T`. For ERC20 tokens this holds because `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` is called when `tokenAddress != address(0) && tokenTotal > 0` [1](#0-0) .

However, when `tokenAddress == address(0)`, the `if` condition at line 75 is false regardless of `tokenTotal`, so no transfer and no `msg.value` check occurs at all — the loop still builds `utxoSet[utxoIndex]` entries with `amount: amount, erc20Address: tokenAddress` for every entry in `utxoAmounts[i]` before this check is even reached [2](#0-1) . Compare this to the generic `transferERC20TokenFromOrCheckETH` helper elsewhere in the codebase, which explicitly requires `msg.value == _value` for the zero-address (ETH) case [3](#0-2) . `DepositOnChainUtxosExternalAction` does not use this helper and has no equivalent `msg.value` enforcement anywhere in `runAction`.

The result: an attacker calling `Hinkal.transact` with the `DepositOnChainUtxos` action, supplying `erc20TokenAddresses = [address(0)]`, `utxoAmounts = [[X]]` with `X > 0`, and `deltaAmounts = [0]`, and sending `msg.value = 0`, causes `countUtxos` to succeed and `runAction` to mint a UTXO of `amount = X`, `erc20Address = address(0)` with zero ETH ever transferred into the contract. This UTXO can subsequently be spent through the normal shielded-UTXO spend path, effectively minting shielded ETH value out of thin air — a direct violation of the "no minting without backing" invariant.

Existing guards do not catch this: `performHinkalChecks`, `verifyProof`, `insertNullifiers`, and the circuit's `inTotal + amountChanges === outTotal` constraints operate on the *proof's* declared in/out amounts and nullifiers, not on whether the external action's on-chain UTXO amounts are actually backed by any transferred value — the backing check for the on-chain path is solely the responsibility of `runAction`, and it is missing for the native-token branch.

### Impact Explanation
This is a Critical-severity finding: minting shielded/on-chain value (native ETH UTXOs) without any backing deposit, directly matching "minting shielded value without backing" in the reward matrix. Because the vulnerability is in the shared `DepositOnChainUtxosExternalAction` contract, it is reachable identically on every chain where this action is deployed (e.g., Base and Arbitrum), so the same crafted call/proof structure can be replayed to mint unbacked ETH UTXOs on each deployment independently.

### Likelihood Explanation
The attacker only needs to be able to call `Hinkal.transact` with the `DepositOnChainUtxos` action (gated only by `onlyAllowedRecipient`, which authorizes the Hinkal core contract as caller of `runAction`, not by any special user privilege) and supply `erc20TokenAddresses[i] = address(0)` with a positive `utxoAmounts[i][j]` while sending no ETH. No victim interaction, no special preconditions beyond generating a valid proof for the deposit action, and no cost beyond gas — highly likely to be exploitable and fully repeatable.

### Recommendation
In `runAction`, add an explicit `msg.value` check for the native-token branch, mirroring `transferERC20TokenFromOrCheckETH`: when `tokenAddress == address(0) && tokenTotal > 0`, require `msg.value == tokenTotal` (or track and require the sum of ETH-backed `tokenTotal`s across all tokens equals `msg.value`), instead of silently skipping the transfer/check.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `DepositOnChainUtxosExternalAction`, register it as an allowed recipient.
2. Attacker (no special role) constructs `CircomData` with `erc20TokenAddresses = [address(0)]`, `externalActionMetadata = abi.encode([[1 ether]])` (i.e., `utxoAmounts = [[1e18]]`), `deltaAmounts = [0]`, and a valid proof for the `DepositOnChainUtxos` action satisfying circuit constraints for a zero-delta deposit.
3. Call `Hinkal.transact(...)` with `msg.value = 0`.
4. Assert: transaction succeeds, `BlockedUtxosCreated` event emitted, and the returned/inserted `utxoSet[0]` has `amount == 1 ether`, `erc20Address == address(0)`.
5. Assert `address(hinkal).balance == 0` before and after the call (no ETH ever entered the contract), proving the minted UTXO of `1 ether` ETH is entirely unbacked — breaking the equality `sum(minted UTXO amounts for token T) == value transferred for token T`.
6. Optionally spend the minted UTXO through the normal shielded-withdraw path to demonstrate the attacker can extract ETH from the contract's existing pooled balance (funded by other users), confirming direct theft/minting impact.
