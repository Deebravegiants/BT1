### Title
Fee-collecting swaps in `EvmHost` use `block.timestamp` as the Uniswap deadline, providing no actual MEV/deadline protection - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` (and other fee-collection paths in the same file) swap native ETH for the fee token via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the `deadline` argument. This is the well-known "meaningless deadline" anti-pattern: `block.timestamp` is evaluated at execution time, so the deadline check inside the router (`require(deadline >= block.timestamp)`) is always satisfied whenever the transaction is actually mined, no matter how long it sat in the mempool. This is functionally equivalent to having no deadline at all, which is the exact bug class flagged in the referenced Asymmetry/Reth finding.

### Finding Description
`dispatch()` is a public, unprivileged entry point that any user/relayer/app can call by attaching native ETH to pay the protocol's dispatch fee. When `msg.value > 0`, `EvmHost` swaps ETH for the exact fee-token amount needed (`post.fee`) through the configured `uniswapV2` router: [1](#0-0) 

The same pattern recurs in `fundRequest()`, which lets anyone top up the fee for an existing request commitment with native ETH: [2](#0-1) 

In both cases the `deadline` parameter passed to `swapETHForExactTokens` is `block.timestamp`. Because Solidity evaluates `block.timestamp` fresh at execution time — not at transaction-submission time — this deadline can never be exceeded once the transaction is included in a block: the router compares `deadline` against the same `block.timestamp` it was just set to. A transaction using this pattern can be held indefinitely in the mempool (by the submitter, a searcher, or a block builder/validator) and executed whenever market conditions are most favorable to whoever controls inclusion, with the deadline offering zero protection against staleness. This mirrors the exact root cause in the external report — the missing/ineffective `deadline` on `ISwapRouter.exactInputSingle`/`exactInputSingleHop` used by Reth's derivative — except here it affects Hyperbridge's own core dispatch/fee-funding path rather than a downstream integration.

### Impact Explanation
`dispatch()` and `fundRequest()` are core, permissionless entry points used by every app/user paying Hyperbridge dispatch fees in native ETH. A malicious or MEV-seeking block builder/validator can:
- Hold a submitted `dispatch()`/`fundRequest()` transaction and delay its inclusion until the ETH/fee-token pool price has moved unfavorably for the caller, then include it alongside their own trades (sandwich), extracting value from the price impact of the exact-output swap.
- Because the swap is "exact output" (`post.fee` fixed, `amountInMaximum = msg.value`), the caller cannot be forced to pay more than `msg.value`, but the effective ETH cost of acquiring the fee token can still be pushed to the worst point in the caller's supplied slippage budget, and the transaction can be timed to land whenever most profitable to the block producer — a value-extraction vector inherent to unprotected swaps. This affects fee funds flowing into the core protocol on every EVM chain where `uniswapV2` is configured, which is a broadly reachable, high-frequency path (every fee-paying dispatch).

### Likelihood Explanation
High reachability: `dispatch()` and `fundRequest()` are unauthenticated, callable by any account, and are exercised on the primary hot path (dispatching cross-chain messages and funding pending requests) whenever `msg.value > 0`. The vulnerable pattern (`deadline = block.timestamp`) is present in multiple call sites within the same file, indicating it's a systemic coding pattern rather than an isolated typo, increasing the likelihood of repeated exploitation across chains where a `uniswapV2` router is wired up (e.g., mainnet, Base, BSC per the deployed addresses).

### Recommendation
Accept a user-supplied `deadline` parameter (or a maximum acceptable slippage/staleness window) in `DispatchPost`/`fundRequest()` and pass that value — bounded to a reasonably short future window (e.g., `block.timestamp + userDeadline`, validated at submission time by the caller off-chain) — into `swapETHForExactTokens`. Do not derive the deadline from `block.timestamp` inside the function being protected, since that always self-satisfies. Apply the same fix to any other in-repo call site using `block.timestamp` as a swap deadline (e.g., `IntentGatewayV2.sol`'s equivalent swap, `SimplexPaymaster.swapAndDeposit`, and the Tron port of `IntentGatewayV2.sol`), since they follow the identical pattern.

### Proof of Concept
1. A user or app calls `EvmHost.dispatch{value: X}(post)` with `post.fee` set, supplying enough ETH to cover the exact-output swap.
2. The transaction is broadcast to the mempool; `swapETHForExactTokens` is invoked with `deadline = block.timestamp`, as shown at [3](#0-2) .
3. A validator/block-builder observes the pending transaction and, instead of including it promptly, delays inclusion while positioning their own trades against the ETH/feeToken pool (or simply waits for a more favorable price point), because the deadline check `require(deadline >= block.timestamp)` in the router will pass trivially at whatever future block time it is finally included.
4. The dispatcher's swap executes at a time and price chosen by the block producer rather than the original caller, extracting value at the caller's expense — the exact scenario described in the external report, reproduced here on Hyperbridge's own fee-funding swap path instead of a third-party derivative contract.

Note: I could not fully verify whether every one of the 6 `uniswapV2)swap` occurrences in `EvmHost.sol` uses the same pattern (only two were read in full); the remaining occurrences should be checked in a full session to confirm the scope of the fix.

```text
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```
