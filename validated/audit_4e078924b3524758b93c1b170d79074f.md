## Analysis Result

I was able to confirm the core defect but could not locate (due to tool-call budget) the exact decrement code path inside the `Data` receipt branch of `process_receipt`/`apply_action_receipt`; I am relying on the standard NEAR postponed-receipt design (one `data_id` → one uniquely-generated `DataReceipt`, decremented once per newly-received `data_id` in `PendingDataCount`), which is consistent with everything I found in `runtime/runtime/src/lib.rs` and `core/primitives/src/trie_key.rs`.

### Title
Duplicate `input_data_ids` in an action receipt permanently strand it as an un-executable postponed receipt - (`runtime/runtime/src/lib.rs`)

### Summary
`validate_action_receipt` only checks the *count* of `input_data_ids` against `max_number_input_data_dependencies`, never that the ids are distinct. `process_action_receipt` computes `pending_data_count` by iterating over `input_data_ids()` and incrementing once per not-yet-received entry, without deduplicating repeated `data_id`s. Since each `data_id` is produced by exactly one output data-producing receipt, a receipt that lists the same `data_id` twice (or more) will have its `PendingDataCount` initialized above the number of distinct data receipts that can ever arrive, so it can never reach zero and never executes.

### Finding Description
In `validate_action_receipt` (`runtime/runtime/src/verifier.rs:595-600`) the only check performed is: [1](#0-0) 
This bounds `input_data_ids.len()` but never verifies uniqueness of the ids inside it.

In `process_action_receipt` (`runtime/runtime/src/lib.rs:1608-1655`), pending count is derived purely from iterating the (possibly duplicate-containing) list: [2](#0-1) 

If an attacker crafts a receipt whose `input_data_ids` contains the same `data_id` `k` times (all not-yet-received), `pending_data_count` is set to `k` and `TrieKey::PendingDataCount` is persisted with that value. However, `data_id` values are unique identifiers tied to a single output-producing action (e.g. a single `FunctionCall`/promise result); the runtime will only ever generate and deliver **one** `DataReceipt` for that `data_id` to the receiver. When that single data receipt is processed, the postponed-receipt bookkeeping can decrement `PendingDataCount` at most once for that id (the `PostponedReceiptId` entry keyed by `(receiver_id, data_id)` is a single slot, not per-duplicate-occurrence). Consequently `pending_data_count` can only go from `k` to `k-1`, never to `0` for `k > 1`, and `apply_action_receipt` (which fires only when the stored counter reaches `0`) is never invoked for this receipt.

This means the receipt — along with any attached deposit/prepaid gas that was already deducted from the sender/burnt when the receipt was created — is stored forever under `TrieKey::PostponedReceiptId` / `TrieKey::PendingDataCount` and never executes, cleans up, or refunds.

### Impact Explanation
This is a liveness/fund-lock issue rather than direct fund theft: the deposit and gas already committed to the postponed receipt become permanently unrecoverable (never delivered, never refunded), violating the PROGRESS_IS_PRESERVED invariant and effectively a permanent balance lock (a form of BALANCE_CONSERVATION violation, since value enters a state from which it can never be returned or spent). It also leaves orphaned state entries (`PostponedReceiptId`, `PendingDataCount`, the postponed receipt itself) that persist in state forever, contributing to unbounded state growth from repeated exploitation by any account.

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: any account can submit a `FunctionCall` that issues promises with duplicate dependency data ids (e.g. via `promise_and`/`promise_batch_then` referencing the same promise index twice, or by directly crafting the receipt through the actions API if such duplication is reachable from contract-level promise combinators). It requires only normal RPC/transaction submission, is deterministic, and is repeatable at will up to `max_number_input_data_dependencies` per receipt.

### Recommendation
In `validate_action_receipt` (`runtime/runtime/src/verifier.rs`), reject action receipts whose `input_data_ids` contain duplicate entries (e.g., collect into a `HashSet` and compare length), in addition to the existing count-limit check. Alternatively/additionally, harden `process_action_receipt` in `runtime/runtime/src/lib.rs` to deduplicate `input_data_ids` before computing `pending_data_count`, so the counter reflects distinct dependencies only.

### Proof of Concept
Unit test plan for `runtime/runtime/src/lib.rs` (`process_action_receipt`):
1. Construct an `ActionReceipt` with `input_data_ids = [data_id_X, data_id_X]` (duplicate), where `data_id_X` is not yet received in state.
2. Call `process_action_receipt`; assert the persisted `TrieKey::PendingDataCount{receiver, receipt_id}` equals `2`.
3. Simulate delivery of the single `DataReceipt` for `data_id_X` (call the data-receipt processing path once, as would happen in production since only one data-producing receipt exists per `data_id`).
4. Assert `PendingDataCount` becomes `1` (not `0`), and assert `apply_action_receipt` is never invoked for this receipt (no `ExecutionOutcome` produced, receipt remains in `PostponedReceipt` storage).
5. Assert that no further `DataReceipt` for `data_id_X` can ever be produced (by construction, since it's a single-output id), proving the receipt is permanently stranded — violating PROGRESS_IS_PRESERVED.
