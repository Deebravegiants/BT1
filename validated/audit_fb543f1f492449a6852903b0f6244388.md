### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the event belongs to. Because the HMAC signature only covers `@raw_body` and never the `shop-domain` (or any other) header, any party who can obtain one valid `(body, hmac)` pair signed with the app's `client_secret` can replay that pair while substituting an arbitrary `shop-domain` header, causing the app to attribute the payload to a shop it was never sent for.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop` accessor is read directly from an HTTP header without any cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` performs authentication by calling `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. the raw body only) and HMAC-compares it against `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

After the body-only HMAC check passes, the unauthenticated `request.shop` value is forwarded straight into `WebhookMetadata` and handed to the host application's handler as the identity of the shop the event pertains to (`lib/shopify_api/webhooks/registry.rb:198-199`). The binding the report's bug class calls out — "a field acted on but not covered by the HMAC" — is broken here: the equality that should hold is `hmac_signed_bytes == (shop ‖ body)`, but the actual implementation only enforces `hmac_signed_bytes == body`, leaving `shop` completely outside the authenticity check.

Because Shopify apps use a single, app-wide `client_secret` (not a per-shop secret) to sign every merchant's webhooks, any unprivileged user who installs the app on their own (attacker-controlled) shop will receive genuine webhook deliveries with a valid HMAC computed over a body they can fully observe. That attacker can then replay the exact same `(body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint while changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged actor with a Shopify account (any merchant that can install the app) can forge webhook deliveries that the app's own handler logic will process as if they originated from an arbitrary other shop, since only the body — not the shop identity — is authenticated. This falls under cross-tenant access, one of the accepted Critical-impact categories, because the vulnerable code path lives entirely within this gem's HMAC-verification/webhook-dispatch logic (`Utils::HmacValidator`, `Webhooks::Request`, `Webhooks::Registry`) and requires no leaked secret, no privileged account, and no TLS interception — only the ability to install the app once as any Shopify merchant.

### Likelihood Explanation
Medium-to-High: exploitation requires the attacker to (1) install the app on a shop they control (an ordinary, unprivileged action available to any Shopify merchant) to obtain a legitimately-signed webhook, and (2) replay that request with a modified `shop-domain` header to the app's public webhook endpoint. No knowledge of `api_secret_key` or any credential is required — only observation of one legitimate webhook delivery. The main constraint is that the forged webhook's body content is fixed to whatever content the attacker's own shop event produced, limiting attacker control over the payload for a given topic.

### Recommendation
Include the shop identity in the value that is HMAC-authenticated, or otherwise cryptographically bind the `shop-domain` header to the signed body before trusting it — e.g., verify the header value against a shop registered/expected by the host app's session store, or fold the header value into `to_signable_string` if Shopify's webhook HMAC scheme is extended to support it. At minimum, document prominently that `Webhooks::Request#shop` is not authenticity-verified and that host applications must independently validate it (e.g., cross-check against an existing, previously-authenticated session for that shop) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, completing OAuth normally (unprivileged action).
2. Shopify sends the attacker's shop a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `B` and `H` from their own webhook endpoint logs (they are the legitimate recipient).
4. Attacker resends an HTTP request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) and succeeds since `H` still matches.
6. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-supplied data as if it came from `victim.myshopify.com`.
