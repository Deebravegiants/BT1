### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw body [1](#0-0) . The `shop`, `topic`, and `webhook_id` values that `Registry.process` uses to route and label the webhook to the host application's handler are taken verbatim from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) [2](#0-1)  and are never included in the HMAC-signed data.

### Finding Description
The identity binding that should hold is: `shop (verified by HMAC) == shop (acted upon by handler)`. Here the HMAC only authenticates the request body bytes; the `shop-domain`, `topic`, and `webhook-id` headers are outside that signed scope [4](#0-3) . `Registry.process` calls `Utils::HmacValidator.validate(request)` — which only recomputes the signature over `to_signable_string` (i.e. `@raw_body`) — and, once that passes, unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` delivered to the app's `WebhookHandler#handle` [3](#0-2) . Any party capable of resending a byte-for-byte-valid previously-observed body+HMAC pair to the app's webhook endpoint (e.g., a merchant who has installed the app on their own shop and thus legitimately received real signed webhooks) can replay that same body while substituting an arbitrary `shopify-shop-domain` header. The HMAC check still passes because it never covered that header, so the handler executes business logic believing the event originated from a different, victim shop.

### Impact Explanation
This breaks the shop-identity binding the app relies on to attribute webhook data. Handlers commonly key their persisted store/session lookups off `WebhookMetadata#shop` (e.g., `shop/redact`, `customers/redact`, `customers/data_request`, order/product updates) [5](#0-4) . An attacker who controls one legitimate (installed) shop can forge the `shop` attribution of a webhook event to point at a different shop, letting them inject attacker-controlled body content that host applications treat as authentic data for a shop they do not control — a cross-tenant data-integrity/confusion issue delivered through this gem's own trust boundary rather than a host-app misuse.

### Likelihood Explanation
Exploitation requires the attacker to already have a genuine HMAC-valid `(body, hmac)` pair, which any app merchant on the free/dev shop tier can obtain by installing the app and receiving real webhooks signed with the shared `client_secret`. From there, replaying the same body with a substituted `shop-domain` header is trivial and does not require the `client_secret`, an access token, or any privileged access — only crafting an HTTP POST to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signed payload verification, or independently corroborate the header-derived `shop` against a value obtained from a source bound to the signature (e.g., have `to_signable_string` incorporate the relevant headers, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host`/`state` into the signed string) [6](#0-5) .

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`) to their own registered endpoint, capturing the exact `raw_body` and its valid `x-shopify-hmac-sha256` header value (both signed with the app's real `client_secret`, shared across all shops using the app).
2. Attacker POSTs the same `raw_body` and the same `hmac-sha256` header to the app's webhook endpoint, but with `x-shopify-shop-domain: victim.myshopify.com` and any desired `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [7](#0-6) ; `Utils::HmacValidator.validate(request)` succeeds because it only checks the body against the secret [8](#0-7) .
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` and calls the app's handler [3](#0-2) , which now processes attacker-controlled data as though it were authentic data from `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
