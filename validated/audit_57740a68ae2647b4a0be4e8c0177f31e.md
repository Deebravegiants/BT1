Audit Report

## Title
Cross-user response hijack via `MessageID` collision in the WebAPI Trigger capability handler's `savedCallbacks` map - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The Gateway's `capabilities` handler stores the pending caller's callback in `h.savedCallbacks` keyed solely by the attacker-controlled `msg.Body.MessageID`, with no duplicate-ID check and no allowlist/sender validation before the write. This allows an unprivileged second caller to overwrite an in-flight victim's callback slot by colliding on `MessageID`, causing the DON node's later response to be delivered to the attacker instead of the original requester.

## Finding Description
`handleRequest`/`ProcessRequest` decode and dispatch any syntactically valid signed message with no allowlist check at this layer [1](#0-0) . `api.Message.Validate()` only verifies signature well-formedness and recovers a signer address; it performs no allowlist check and no uniqueness guarantee on `MessageID` [2](#0-1) .

In `HandleLegacyUserMessage`, the handler writes `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` unconditionally, immediately preceded by an explicit `// TODO: apply allowlist and rate-limiting here` comment confirming no sender/allowlist validation is enforced at this point [3](#0-2) . This is in contrast to `httpTriggerHandler.setupCallback`, which explicitly checks for an existing in-flight `requestID` and rejects the request with `jsonrpc.ErrConflict` if found [4](#0-3) .

When a node responds, `handleWebAPITriggerMessage` looks up the response destination solely by `MessageID`, regardless of who currently occupies that slot, and delivers the result to whatever callback is stored there [5](#0-4) . The identical unguarded overwrite-and-lookup-by-ID pattern exists in `handler.dummy.go`'s `HandleLegacyUserMessage`/`HandleNodeMessage`. A test file explicitly flags the missing sender/allowlist validation as an open TODO [6](#0-5) .

## Impact Explanation
This constitutes a cross-user response corruption: an unprivileged network caller able to submit any validly-signed message to the Gateway's public endpoint can, by colliding on a `MessageID`, hijack another user's in-flight WebAPI-trigger response, receiving data intended for a different caller. This maps to the in-scope "cross-user response corruption" / "gateway request impersonation" impact category.

## Likelihood Explanation
Exploitation requires only knowledge/guessability of a victim's `MessageID` and winning a straightforward race against the DON node's asynchronous response — no DON membership, allowlist entry, or elevated privilege is required, and the vulnerable code path imposes no rate limiting or duplicate-ID rejection, unlike the sibling `http_trigger_handler.go` implementation which already guards against this exact scenario.

## Recommendation
Add a duplicate-ID guard to `HandleLegacyUserMessage` (and the analogous `handler.dummy.go` methods), mirroring the conflict check in `httpTriggerHandler.setupCallback`, so a second request cannot silently overwrite another caller's pending callback for the same `MessageID`. Additionally, bind `MessageID` lookups to the requester's signer address so a node response can only be routed to the callback of the same signer that originated the request, and implement the allowlist/rate-limiting noted in the outstanding TODO.

## Proof of Concept
1. Submit a validly-signed `api.Message` with `MessageID = "victim-id"` as User A; handler stores `savedCallbacks["victim-id"] = <User A callback>` per `core/services/gateway/handlers/capabilities/handler.go` lines 411-414 and forwards it to DON nodes.
2. Before a node responds, submit a second independently-signed message with the same `MessageID = "victim-id"` as User B; this overwrites `savedCallbacks["victim-id"]` with User B's callback (no duplicate check exists).
3. When a DON node responds for `MessageID = "victim-id"`, `handleWebAPITriggerMessage` (lines 148-162) looks up the map entry and delivers the response to User B's callback instead of User A's, even though the response corresponds to User A's original request.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
