### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-verifiable payload from `@raw_body` only [1](#0-0) . `Registry.process` validates only that the HMAC matches the raw body [2](#0-1) , then forwards `request.shop` (the unauthenticated header value) directly to the app's handler as the identity of the shop that produced the webhook [3](#0-2) .

### Finding Description
This breaks the identity binding: **shop authenticated (bytes covered by HMAC) ≠ shop delivered to the handler (bytes read from header)**. The HMAC only proves that `@raw_body` was signed with `api_secret_key`; it proves nothing about which shop the header claims to be from.

Since a merchant's own legitimate webhook (body + valid HMAC) is delivered to the app's own public webhook endpoint, an attacker who controls that endpoint (or intercepts/replays a request they legitimately received for their own shop) can resend the identical `raw_body`/`hmac-sha256` pair while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. Because `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) only recomputes the signature over `to_signable_string` (the raw body), the forged shop header sails through validation unchanged [4](#0-3) . The handler then receives `WebhookMetadata` with an attacker-chosen `shop`, `topic`, `webhook_id`, and `api_version`, but with body content actually belonging to a different (attacker's own) shop [5](#0-4) .

Per the documented usage pattern, apps are expected to key persistence/business logic (session lookups, background jobs, per-tenant state) off `data.shop` [6](#0-5) , trusting it as the authenticated shop identity — exactly the pattern the gem's own tests validate (`data.shop` is asserted equal to the header value, not something independently verified) [7](#0-6) .

### Impact Explanation
This crosses the tenant boundary: an app relying on this gem's `shop` field to attribute webhook data to a tenant can be made to associate one shop's data/action with another shop's identity, without requiring knowledge of `api_secret_key`, an access token, or any privileged credential — only receipt of one legitimate webhook for the attacker's own (possibly free/trial) shop. This matches "cross-tenant access" impact.

### Likelihood Explanation
High for any app that exposes a single shared webhook endpoint (the common pattern shown in the gem's own docs) and trusts `data.shop`. The attacker only needs to operate a shop that can trigger a webhook to itself (e.g., `app/uninstalled`, `orders/create`) and capture the raw POST body/HMAC pair before replaying it with a modified shop header.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string, or otherwise independently bind the shop-domain header to the HMAC (e.g., validate it against a mapping known only from the offline session/access-token store previously associated with that shop), rather than trusting the header as-is once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receives a webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC(secret, B)`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the same `B`/`H` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only covers `B` [8](#0-7) .
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_B, ...))`, and the app processes attacker-controlled data as if it were authenticated data belonging to `victim.myshopify.com`.
