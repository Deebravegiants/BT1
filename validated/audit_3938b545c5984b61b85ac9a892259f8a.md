### Title
Webhook shop identity not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator.validate` (invoked from `Registry.process`) only authenticates the raw request body via `to_signable_string`. This breaks the identity binding `shop-authenticated == shop-used-as-tenant-key`, mirroring the reported bug class where a value is trusted/acted on without being covered by the same integrity check that "validates" the request.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` reads the shop identity directly from an HTTP header, which is not part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate(request)` as proof the whole request — including `request.shop` — is authentic, and forwards the unauthenticated `shop` value straight into the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a first-class field the gem hands to every registered `WebhookHandler#handle`, so any host application following this gem's own interface uses `data.shop` as the tenant key for the payload: [5](#0-4) 

The equality that should hold is:
`shop bound by HMAC(secret, signed_bytes) == shop used as WebhookMetadata.shop (tenant key)`

Instead, the gem verifies `HMAC(secret, raw_body) == received_hmac` but independently trusts `shop = header["x-shopify-shop-domain"]`, which is never part of `signed_bytes`. Any bytes that produce a valid `(raw_body, hmac)` pair remain valid for **any** header value of `shop-domain`, because the header is orthogonal to the signed content.

### Impact Explanation
An app installed on shop A legitimately receives real Shopify webhooks with a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. Because `shop` is not covered by that signature, the same `(raw_body, hmac)` pair remains "valid" per `HmacValidator.validate` when replayed to the app's public webhook endpoint with `X-Shopify-Shop-Domain` changed to shop B's domain. `Registry.process` will pass this forged `shop` value straight to the handler as `WebhookMetadata#shop` without any additional consistency check. Any host application that follows this gem's documented `WebhookHandler` contract and uses `data.shop` to select which tenant's session/store record to act on (a documented and expected usage pattern, e.g., for GDPR mandatory topics like `customers/redact` or `shop/redact`) will process/act on attacker-chosen shop B using content that was legitimately signed only for shop A. This is a cross-tenant identity confusion rooted in this gem's own `Request`/`Registry` implementation, matching the High-severity "cross-tenant access" criterion.

### Likelihood Explanation
Requires only unprivileged capability: the attacker needs one legitimate `(raw_body, hmac)` pair, obtainable by installing the app themselves on their own shop (which is a normal, unprivileged action) or by intercepting/replaying a webhook delivered to a publicly reachable endpoint. No access to `api_secret_key`, tokens, or any privileged account is needed — the header can be freely modified by anyone able to send an HTTP request to the app's public webhook URL.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) header values into the signed material verified by `HmacValidator`, e.g., by including them in `to_signable_string` if Shopify's real signature scheme supports it, or — since Shopify's HMAC is defined over the raw body only — require the host application/gem to cross-check `request.shop` against an out-of-band trusted value (e.g., the shop recorded for the specific `webhook_id` via a prior GraphQL lookup, or reject processing unless the shop is a member of the app's known/installed-shop set) before invoking `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is **not** cryptographically authenticated and must not be used as a sole tenant-lookup key without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture a real Shopify webhook delivery to the app's public endpoint: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid signature over `B` with the app's secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay the exact same HTTP POST to the same endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (all other headers/body unchanged).
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)` and compares to `H`, per `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:13-31`.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...))` is invoked, per `lib/shopify_api/webhooks/registry.rb:198-199` — the host app now processes attacker-controlled webhook content under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
