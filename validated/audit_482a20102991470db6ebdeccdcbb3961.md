Found the key binding break in `Webhooks::Request` and `Webhooks::Registry.process`. The HMAC verifies `to_signable_string`, which returns only the raw request body [1](#0-0) . The `shop` value used by the handler (`request.shop`) is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the HMAC-signed bytes [2](#0-1) [3](#0-2) . `Registry.process` validates the HMAC over the body and then trusts `request.shop` for dispatch to the handler without any cross-check against the body contents or a shop registered for that HMAC secret [4](#0-3) .

This exactly mirrors the reported bug class: bytes verified (the raw body via HMAC) versus bytes/fields actually trusted for identity (the `shop-domain` header, which is unauthenticated). Since a single app's `api_secret_key` is shared across all shops that installed the app, any merchant/attacker who controls a shop that has installed the app can compute a valid HMAC over an arbitrary crafted body (their own webhook payload from Shopify, or any body if they can get Shopify to sign it, e.g. via a real webhook delivery to their own shop), then replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header value to a victim's shop domain. Because `Registry.process` only checks that the HMAC matches the raw body — not that the header-derived `shop` is bound to that HMAC — the handler will process the webhook as if it originated from the victim shop, invoking data-modifying/redaction handlers (e.g., `shop/redact`, `customers/redact`, `customers/data_request`, or app-registered handlers) tagged with the attacker-chosen shop identity.

However, I want to flag uncertainty here: exploitation depends on the attacker being able to get a validly-HMAC-signed body at all, which normally requires either (a) being a legitimate installed shop of the same app (so they receive real signed webhooks for their own shop and can replay the body with a different shop header), or (b) the app accepting arbitrary attacker-supplied bodies through some other channel. Case (a) is realistic and turns this into a cross-tenant confusion/injection primitive — a malicious merchant of a multi-tenant app can make their own webhook events attributed to a different shop.

### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` only returns the raw body, while `Registry.process` trusts `request.shop`, which is parsed from an unauthenticated header, to determine which tenant a webhook belongs to.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC against `to_signable_string`, i.e., the raw body only [5](#0-4) [1](#0-0) . `Registry.process` calls this validator and, once it passes, unconditionally uses `request.shop` (sourced purely from the `x-shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler [4](#0-3) . The shop identity that the handler acts on is therefore not part of the bytes verified by the HMAC — breaking the equality "bytes verified == bytes trusted for tenant identity."

### Impact Explanation
Because an app's `api_secret_key` is shared across all shops that installed it, any shop that installs the app can legitimately receive a validly-signed webhook body for itself, then resend that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to name a different (victim) shop. The app-registered handler processes the event as if it came from the victim, enabling cross-tenant data confusion for topics like `customers/data_request`, `shop/redact`, or any custom registered handler that keys behavior off `WebhookMetadata#shop`.

### Likelihood Explanation
Any merchant who has installed the multi-tenant app (an "unprivileged internet user" relative to other tenants) can trivially capture one legitimate webhook delivery to their own shop and replay it with a modified shop header — no secrets need to be guessed since the HMAC is unaffected by header changes.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered material, or otherwise cryptographically bind the `shop-domain` header to the signed body (e.g., verify against a per-shop secret/session rather than the shared app secret, or require the shop domain to be embedded in and verified from the signed payload itself).

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (same app, same `api_secret_key`).
2. Attacker (merchant of `shop-a`) receives a real webhook: body `B`, header `x-shopify-shop-domain: shop-a.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker resends the identical body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Registry.process` verifies the HMAC (matches, since body `B` is unchanged) and calls the handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: B, ...)`, causing the app to act on `shop-b`'s tenant context using attacker-supplied data. [4](#0-3)

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
