### Title
Webhook `shop-domain`/`topic`/`webhook-id`/`api-version` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` are parsed straight from unauthenticated HTTP headers. Any party that can obtain one genuinely-signed webhook payload for the shared app secret can replay it with forged identity headers, and the gem will treat it as valid and dispatch it as if it came from an arbitrary victim shop/topic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` and `to_signable_string` only ever look at the `hmac-sha256` header and `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are separate, plain header reads that are never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` (used by `Registry.process`) only verifies `verifiable_query.to_signable_string` (the raw body) against the computed HMAC, using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` then trusts `request.topic` and `request.shop` — taken straight from the unauthenticated headers — to build the `WebhookMetadata` object handed to the app's handler: [4](#0-3) 

The identity binding broken here is: **HMAC-verified bytes (body only) ≠ bytes the gem parses and trusts for shop/topic/webhook-id attribution (headers)**. Because `Context.api_secret_key` (the value used to compute this HMAC) is the app's single shared `client_secret`, it is identical across every shop that has installed the app — it is not shop-specific. Consequently, any merchant who has legitimately installed the app receives real webhooks with valid HMACs computed over their own payload bodies. Nothing stops that merchant (or anyone who can capture such a request, e.g. from their own store's webhook logs) from re-sending the exact same raw body/HMAC pair to the app's webhook endpoint while swapping `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) to a victim shop's domain or a different topic. `Utils::HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` proceeds to invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen value.

### Impact Explanation
Apps built on this gem rely on `WebhookMetadata#shop`/`#topic` (as documented in `docs/usage/webhooks.md`) to identify which tenant/shop a webhook event belongs to and to route/act on that tenant's data (e.g., syncing state, updating billing, deleting data on `app/uninstalled`, etc.). Because the shop/topic attribution is not cryptographically bound to the authenticated payload, an attacker who is a legitimate (even trial/free) merchant of the app can forge webhook events that the host application will process as though they originated from any other shop — a cross-tenant confusion/spoofing primitive reachable purely through this gem's own webhook verification code path.

### Likelihood Explanation
Any developer/merchant capable of installing the target app (a low bar — no special privilege, secret, or token beyond normal app installation) can capture one legitimate webhook delivery to their own endpoint and replay it with modified identity headers against the app's public webhook endpoint. No `api_secret_key`, access token, or credential theft is required; the attacker only needs a webhook body/HMAC pair that was legitimately generated by Shopify for the shared app secret.

### Recommendation
Bind the identity headers into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body (e.g., include them in `to_signable_string`, or independently confirm `shop` against a known/installed-shop registry before trusting it) rather than trusting raw, unauthenticated headers for tenant attribution.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid-hmac-over-body>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: abcd-1234
x-shopify-api-version: 2024-01
Body: {"id": 1, ...}
```
2. Replay the exact same request but replace the header:
```
x-shopify-shop-domain: victim.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` still calls `Utils::HmacValidator.validate`, which only checks the (unmodified) body/HMAC pair and returns `true`.
4. The app's handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ...)`, causing the host app to act as if the event came from `victim.myshopify.com`.
