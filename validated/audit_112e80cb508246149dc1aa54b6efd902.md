### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant event spoofing via header replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The reported fuel-core bug class (an unchecked value flowing into a security-relevant computation without validating the boundary condition that protects it) maps here to a broken identity binding: `ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw body only, while the `shop` (and `topic`) values that the application uses to attribute the webhook to a tenant are read from unauthenticated HTTP headers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` and `#topic` are read straight from caller-supplied HTTP headers with no cryptographic binding to the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` verifies the HMAC over the request (i.e., over `raw_body`) and, if valid, immediately constructs `WebhookMetadata` using `request.shop` — a field the HMAC check never touched: [4](#0-3) 

`WebhookMetadata.shop` is then handed to the host application's `WebhookHandler#handle` as the trusted tenant identifier: [5](#0-4) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC_valid(secret, raw_body) == true` is treated as proof of `(shop, topic, raw_body)` all being authentic, when it only proves `raw_body` is authentic. `shop`/`topic` are attacker-controllable header values that ride along unauthenticated.

Because the HMAC is computed only over the body, anyone who has ever received one legitimately-signed webhook payload (e.g., an attacker who installs their own free/dev app instance and thus legitimately receives a valid `body` + `x-shopify-hmac-sha256` pair from Shopify) can replay that exact `(raw_body, hmac)` pair to the same app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a *different* victim shop. `HmacValidator.validate` will still pass because it only re-derives the HMAC from `raw_body` and compares against the (unchanged) valid signature: [6](#0-5) 

The application's handler then receives `WebhookMetadata` claiming the event came from the victim shop, even though it did not.

### Impact Explanation
This breaks the cross-tenant boundary the webhook mechanism is supposed to enforce: an app that uses `WebhookMetadata#shop` to route data, update per-shop records, or trigger shop-scoped side effects (a standard use documented in `docs/usage/webhooks.md` and demonstrated in the test suite, e.g. `data.shop` used directly by handlers) can be made to attribute attacker-supplied (replayed) event content to an arbitrary, unrelated shop domain — a cross-tenant data-confusion vector. This matches the "cross-tenant access" Critical impact category in scope, since it defeats the tenant-identity guarantee that the HMAC check is meant to provide.

### Likelihood Explanation
Exploitability requires only: (1) the attacker holds any one legitimately-signed webhook body from the target app (trivial — install the app on a shop the attacker controls, or observe/exfiltrate a single delivered payload), and (2) the ability to POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header, which is standard HTTP client capability with no credential requirement. No knowledge of `api_secret_key` or any access token is needed, satisfying the "unprivileged internet user" threat model.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is authenticated, e.g. include the shop domain in `to_signable_string`/the HMAC computation, or independently validate that the `shop` header corresponds to a shop for which this exact signed body was actually issued (for example, by requiring the caller to supply the expected shop and comparing it against a shop recorded when the subscription was registered, not from the request headers alone). At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be trusted for tenant-scoped authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise obtains one legitimate webhook delivery) and captures the raw body `B` plus its valid `x-shopify-hmac-sha256` header `H` (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a POST to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: <same or different topic>`
   - body = `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC from `B` only and matches `H` — validation succeeds.
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes the event as if it genuinely originated from `victim-shop.myshopify.com`.

**Uncertainty:** This is a design characteristic of how the gem constructs webhook authenticity (HMAC over body only, per Shopify's documented webhook signing scheme) rather than an obvious coding defect; whether it rises to a "vulnerability in this gem" versus "expected behavior that host apps must additionally validate" is a judgment call. I flag it because it precisely matches the rule's named analog ("a field acted on but not covered by the HMAC") and is reachable without any privileged access, but note that Shopify's own documented webhook contract does not claim the shop header is authenticated by the HMAC, so some reviewers may classify this as expected/by-design rather than an actionable defect in `lib/shopify_api/webhooks/**`.
