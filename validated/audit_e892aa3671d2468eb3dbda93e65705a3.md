### Title
Webhook shop identity spoofing via HMAC that does not bind the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, while the `shop` value that is handed to the app's handler (and used by the app to attribute the payload to a specific merchant/tenant) is read from an HTTP header that is never included in the signed material. Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app, any shop that can install the app (including an attacker's own trial/dev store) can capture a valid `(body, hmac)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, causing the gem to report the forged payload as authentic data for the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from an attacker-controllable HTTP header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the request using only this body-based HMAC, then immediately trusts `request.shop` (and the rest of the header-derived metadata) when constructing the data passed to the app's registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the supplied signature — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This breaks the identity binding `shop authenticated == shop the handler acts on`: the HMAC only proves "this body was signed with the app's secret by *some* installed shop," not "this body came from *this* shop." Since the same `api_secret_key` is shared by the app across all its installations, any unprivileged user who can install the app on their own store obtains a way to mint an arbitrarily-chosen, validly-signed `(topic, body, hmac)` triple, then present it to the webhook endpoint with a forged `shop-domain` header naming a different, victim shop. `Registry.process` will pass HMAC validation and dispatch the (attacker-crafted) payload to the handler labeled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion at the gem's authentication boundary for inbound webhooks: the field the app relies on to know *which merchant* the data belongs to (`shop`) is not covered by the very mechanism (`HmacValidator.validate`) that is supposed to authenticate the webhook. An app that uses `request.shop` for anything tenant-sensitive (looking up the shop's session/access token, updating per-shop records, triggering per-shop side effects) can be made to act on forged data attributed to a shop the attacker does not control, i.e., cross-tenant access.

### Likelihood Explanation
Exploitation requires only what any user of a public/dev app already has: the ability to install the app on a shop they control and observe the resulting webhook deliveries (body + `X-Shopify-Hmac-Sha256`), then send a crafted HTTP request directly to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` value. No `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material used for verification, or otherwise cryptographically tie the header-derived shop to the specific installation before trusting it — e.g., verify that the resolved shop has an existing, valid session/access token for this app, and/or include the shop domain in `to_signable_string` if Shopify's signing scheme is extended to support it. At minimum, document clearly that `request.shop` is unauthenticated header data and must be independently corroborated (e.g., against known installed shops) before being used for tenant-sensitive operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body B.
3. Attacker crafts a new POST to the app's webhook endpoint using the *same* body `B` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (= `B`) using the app's `api_secret_key` — it matches, since `B` and the HMAC are unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
