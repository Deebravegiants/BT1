### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not bound to the HMAC signature, allowing forged webhook shop attribution - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never included in the HMAC-signed material. `Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` (and `request.topic`) to dispatch the webhook to the app's handler, so the shop that the HMAC actually authenticates and the shop the handler acts on are two different, unbound values.

### Finding Description
The identity binding that should hold is:

`shop authenticated by HMAC == shop acted on by the handler`

but the implementation only produces:

`body authenticated by HMAC` while `shop (and topic, webhook_id) are read unauthenticated from headers`.

`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled straight from headers with no relation to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC via `HmacValidator.validate(request)` — which only checks `verifiable_query.to_signable_string` (i.e. the raw body) against the secret — and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` and invoke the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it computes the signature purely from `verifiable_query.to_signable_string`, never touching `shop`/`topic`/`webhook_id`: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across *every* shop that installs the app (it is not per-shop), any party who can obtain one validly HMAC-signed `(body, hmac)` pair for their own shop's webhook delivery can resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to claim a different, victim shop. `HmacValidator.validate` will still pass because it never inspects those headers, and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim shop's identity: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: the `shop` value that host applications use to look up sessions/tenants (`WebhookMetadata#shop`) is not actually authenticated by the HMAC that is meant to guarantee webhook provenance. A malicious app-installer (an "unprivileged" party relative to other tenants of the same app — they only ever had legitimate access to their *own* shop's webhook traffic) can cause the handler to process attacker-supplied body content while it is attributed to an arbitrary victim shop, i.e. cross-tenant data injection/spoofing through the webhook pipeline. This matches the Critical "cross-tenant access" impact category, since the gem's own verification code fails to bind the acted-upon shop identity to the cryptographic proof.

### Likelihood Explanation
Exploitation requires the attacker to have captured one legitimately-signed `(raw_body, hmac)` pair for their own shop (achievable by any merchant who installs the app and can observe/log traffic delivered to their own webhook endpoint, e.g. via a proxy/log they control) and then replay it against the same public endpoint with a modified `shop-domain` header. No access to `api_secret_key`, TLS interception, or privileged accounts is required beyond the attacker's own (unprivileged) app installation — which is the normal, expected way any user interacts with a public app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload verification (or otherwise cryptographically bind the header-derived identity fields to the body before trusting them), so that `Registry.process` cannot dispatch attacker-controlled data under a spoofed shop domain. At minimum, `to_signable_string` should not be the sole basis for trusting `request.shop`/`request.topic` used downstream in `WebhookMetadata`.

### Proof of Concept
1. App `MyApp` is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing the same `api_secret_key`.
2. Attacker (owner of `attacker-shop`) captures a real webhook delivery to their own registered endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - Body: attacker fully controls the underlying order content by placing a crafted order in their own shop.
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the same public webhook URL, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over the unchanged body and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-199) proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body — the app now processes forged data as though it came from the victim tenant.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
