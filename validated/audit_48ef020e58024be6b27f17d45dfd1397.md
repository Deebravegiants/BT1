This confirms the vulnerability: `WebhookMetadata.shop` (and `topic`/`webhook_id`) are populated directly from unauthenticated HTTP headers, while `ShopifyAPI::Utils::HmacValidator.validate(request)` only signs/verifies `@raw_body`, per [1](#0-0) . The app's `handle` callback then trusts these header-derived values, as documented in `docs/usage/webhooks.md`, to route/attribute webhook processing per shop [2](#0-1) .

### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC-signed payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::HmacValidator` only authenticates the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields that `ShopifyAPI::Webhooks::Registry.process` passes on to the host app's handler are read straight from HTTP headers that are excluded from the HMAC computation, so an attacker who obtains any one legitimately-signed webhook body/HMAC pair can replay it with arbitrary header values and have it accepted as authentic for a different topic/shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` simply returns `@raw_body`: [3](#0-2) 

None of `shop`, `topic`, `webhook_id`, or `api_version` — all read from the `shopify-*`/`x-shopify-*` headers — are part of the signed material: [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body-bound HMAC, then dispatches to the handler using the unauthenticated header fields, including `shop`: [5](#0-4) 

The identity binding that should hold is: `authenticated(shop header) == shop used to attribute/act on the webhook`. Because the HMAC only covers `@raw_body`, this equality does not hold — `shop` (and `topic`/`webhook_id`) can be swapped freely on any body+HMAC pair that was legitimately produced by Shopify for *any* shop (including one the attacker controls, e.g. their own dev/test store where they installed the app and can capture a real webhook delivery), and the swapped fields will still pass `HmacValidator.validate` because the check only re-derives the HMAC from the untouched body.

### Impact Explanation
An attacker who can capture one legitimately-signed webhook (trivial — install the app on their own store to receive real webhook deliveries with a valid `X-Shopify-Hmac-Sha256`) can replay that exact body with a forged `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header pointing at a victim shop. Since `Registry.process` only checks the body HMAC and then trusts the header-derived `WebhookMetadata.shop`/`topic`, host applications that key off `data.shop` to look up the tenant's session, update tenant-scoped local records, or dispatch tenant-specific side effects (exactly as shown in the gem's own documented usage in `docs/usage/webhooks.md`) will process attacker-controlled data under a victim shop's identity. This breaks the tenant boundary the HMAC is supposed to enforce and constitutes cross-tenant data confusion/injection driven entirely from the internet without any credential.

### Likelihood Explanation
Any developer of a Shopify app can install their own app on a store they control and capture a real, validly-signed webhook body/HMAC pair — no leaked credentials or privileged access are required. Replaying it against the victim app's public webhook endpoint with modified `shop-domain`/`topic` headers is straightforward HTTP manipulation once the gem's `process` method is used as documented.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material used for `Request#to_signable_string`, or otherwise cryptographically bind these fields to the HMAC before they are trusted and forwarded to `WebhookMetadata`. At minimum, document that host applications must independently verify `data.shop` against a locally-authenticated tenant record before acting on it, since the gem does not currently guarantee this binding.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify store to receive a legitimate webhook delivery for topic `orders/create`, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Replay the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the victim app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` [3](#0-2)  — validation succeeds because the body/HMAC pair is untouched.
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store [6](#0-5) , causing the host app to process attacker data as if it belonged to the victim tenant.
