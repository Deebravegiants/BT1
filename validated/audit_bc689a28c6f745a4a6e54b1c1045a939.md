### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted for identity/routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used for authorization/routing decisions and handed to application code are taken from unauthenticated HTTP headers. This breaks the binding: **bytes verified (body) != identity fields acted on (`shop`, `topic`, `webhook_id`)**.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then uses the unauthenticated `topic` header to select a handler and passes the unauthenticated `shop` header straight into `WebhookMetadata` given to the app's handler: [3](#0-2) 

The equality that should hold is:
`hmac_signed_content == content_the_handler_trusts_as_authenticated`

but in practice: `hmac_signed_content == raw_body` while `content_the_handler_trusts == {shop, topic, webhook_id, api_version, body}`. Any header outside the body can be freely substituted by anyone who can reach the webhook endpoint with a previously-observed valid `(body, hmac)` pair, and the HMAC check will still pass since it only re-hashes the body.

### Impact Explanation
An unprivileged actor who can obtain any single legitimate `(raw_body, hmac)` pair for the app's client_secret (trivially available by installing the app on their own low-privilege development store and letting it deliver one real webhook) can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and/or a forged `x-shopify-topic` header selecting a different registered handler. `Utils::HmacValidator.validate` still returns true because it only re-computes the HMAC over the body, and `Registry.process` forwards the attacker-chosen `shop`/`topic` values, unauthenticated, to the application's webhook handler via `WebhookMetadata`. Depending on how the host app keys per-tenant data off `WebhookMetadata#shop` (which is the intended, documented use of this field), this enables cross-tenant data confusion/injection using data nominally scoped to the attacker's own shop but attributed to a victim shop.

### Likelihood Explanation
Reaching this requires no credentials, no TLS interception, and no privileged account: any developer can create a free/dev Shopify store, install a public app that uses this library, and receive one authentic webhook body+HMAC signed with the target app's own `client_secret`. From there, replaying the body with edited (non-signed) headers is trivial via any HTTP client. The only defenses in the library are HMAC-of-body-only checks; nothing else validates that the header-derived `shop`/`topic`/`webhook_id` correspond to the shop/topic that actually produced the signed body.

### Recommendation
Do not treat header-derived `shop`, `topic`, `webhook_id`, or `api_version` as authenticated. At minimum:
- Require the host app to cross-check `WebhookMetadata#shop` against a shop known to have received that specific webhook (e.g., via delivery-id de-duplication and shop allow-listing), or
- If Shopify's delivery contract allows it, extend the signable string / validation to also bind `topic` and `shop-domain` (e.g., include the raw header values in the signature check via a defense-in-depth secondary comparison against expected registrations), and
- Document clearly (and enforce where possible) that `webhook_id` should be used for idempotency/replay detection so a captured `(body, hmac)` cannot be replayed indefinitely with arbitrary shop/topic headers.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify dev store; trigger any webhook topic the app has registered (e.g., `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC-SHA256 of `B` under the app's `client_secret`).
2. Replay the exact same request to the app's webhook endpoint, but replace the headers:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - keep `x-shopify-hmac-sha256: H` and body `B` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `hmac` method decodes `H` and whose `to_signable_string` still returns `B`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked, so the application processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`, despite the app never having received an actual signed webhook from that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
