## Analysis

The Tron deployment of `IntentGatewayV2` — `evm/tron/contracts/apps/IntentGatewayV2.sol` — reproduces exactly the bug class from the report: it computes the escrowed/reduced amount from the user-declared input amount instead of the amount actually received, so fee-on-transfer (FOT) tokens cause the escrow ledger to diverge from the contract's real token balance. Notably, the main EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`) was hardened against this exact issue (it measures `balanceOf` before/after transfer and mutates `order.inputs[i].amount` to the actual received value, with dedicated tests `testPlaceOrder_FeeOnTransferToken_WithProtocolFee` / `testPlaceAndFill_FeeOnTransferToken_RoundTrip`), but the Tron variant was not updated to match.

### Title
Escrow over-crediting for fee-on-transfer input tokens in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the no-predispatch branch of `placeOrder`, the Tron `IntentGatewayV2` computes the protocol-fee-reduced escrow amount from the user-supplied `order.inputs[i].amount` and credits `_orders[commitment][token]` with that value, but the actual tokens pulled via `safeTransferFrom` are never measured against the contract's balance delta. For a fee-on-transfer ERC-20 input, the gateway receives less than `order.inputs[i].amount`, yet still books the full (fee-reduced-only) amount into escrow.

### Finding Description
`placeOrder` computes `reducedInputs[i].amount = originalAmount - protocolFee` where `originalAmount = order.inputs[i].amount` (the value the caller specified), *before* any token transfer occurs: [1](#0-0) 

In the non-predispatch escrow path, tokens are pulled with a plain `safeTransferFrom` and the resulting reduced amount is credited to escrow unconditionally, with no check of what the gateway actually received: [2](#0-1) 

If `token` charges a transfer fee, `IERC20(token).balanceOf(address(this))` increases by less than `order.inputs[i].amount`, but `_orders[commitment][token]` is still increased by `reducedInputs[i].amount` (derived from the pre-fee `originalAmount`). This is the same root cause as the referenced report's `doCutDepositFee`/`doCutWithdrawFee`: fee-on-transfer semantics are not measured via balance-diff, only assumed from the nominal transfer amount.

By contrast, the canonical EVM `IntentGatewayV2.sol` fixes this by snapshotting `balanceOf` before and after `safeTransferFrom` and overwriting `order.inputs[i].amount` with the actual delta before computing `reducedInputs`: [3](#0-2) 

The Tron contract's predispatch branch happens to be safe because it explicitly reverts if `balance < requiredAmount` and derives dust from the measured `balance`: [4](#0-3) 
but the default (non-predispatch) branch — the common case for a simple `placeOrder` call — has no such protection.

### Impact Explanation
`_orders[commitment][token]` is a shared per-token escrow ledger backing withdrawals/fills/refunds for all orders using that token. Over-crediting escrow beyond the contract's actual token balance for one order means the aggregate escrow liabilities can exceed the contract's real holdings of that token. When later orders attempt to withdraw their legitimately-escrowed balance (via `fillOrder`/`_withdraw` cancel/refund paths), the contract can run out of tokens, causing legitimate users' funds to become partially or fully unrecoverable — a fund-freezing condition reachable from a single unprivileged `placeOrder` call using an FOT token as input.

### Likelihood Explanation
Triggering this requires only that a fee-on-transfer ERC-20 be configured/available as a supported input token and a user call `placeOrder` without predispatch calldata — a normal, permissionless, single-transaction user flow with no special privileges. Likelihood is directly tied to whether FOT tokens are/will be allowed as intent inputs on the Tron deployment.

### Recommendation
Mirror the main EVM `IntentGatewayV2.sol` fix in `evm/tron/contracts/apps/IntentGatewayV2.sol`: in the non-predispatch branch, snapshot `balanceOf(address(this))` before `safeTransferFrom`, compute the actual received amount from the post-transfer balance, and use that measured amount (not the caller-supplied `order.inputs[i].amount`) as the basis for `reducedInputs`/escrow crediting and the commitment hash.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer token `FOT` (e.g., 1% transfer tax) registered as a valid input.
2. User calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000e18}]` and no predispatch call.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; gateway actually receives `990e18` (1% tax retained/burned by the token).
4. Contract computes `reducedInputs[0].amount = 1000e18 - protocolFee` (based on the nominal `1000e18`) and stores `_orders[commitment][FOT] = reducedInputs[0].amount`, which exceeds the `990e18` actually held.
5. Repeating this (or combined with other orders on the same token) drives cumulative `_orders[...][FOT]` above `IERC20(FOT).balanceOf(gateway)`, so a subsequent legitimate withdrawal/fill/cancel for another order on `FOT` reverts or drains funds meant for others.
