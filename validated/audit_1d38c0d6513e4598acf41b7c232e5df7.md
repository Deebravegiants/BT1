### Title
Unbounded attacker-controlled length in `EventReader::poll_stream` triggers allocator abort / DoS of orb-core process during signup - ([File: src/agents/livestream/upstream.rs])

### Summary
`EventReader::poll_stream` reads a 4-byte big-endian length prefix directly from the TCP livestream socket and immediately allocates `vec![0; len]` with no upper bound check. A remote client that connects to the livestream `Upstream` listener (TCP port 9201) can send a length prefix such as `0xFFFFFFFF` (~4.29 GB) to force a single huge allocation, which on allocation failure triggers Rust's `handle_alloc_error` and aborts the whole process, not just the livestream thread.

### Finding Description
`Upstream::new` binds a `TcpListener` on `0.0.0.0:{PORT}` (`PORT = 9201`) and `Upstream::poll_next` accepts any connecting client and stores it as the active livestream stream [1](#0-0) . Once connected, `EventReader::poll_stream` reads exactly 4 bytes into `self.len`, then immediately does `self.buf = vec![0; u32::from_be_bytes(self.len) as usize]` with no sanity/maximum-size check on the parsed value [2](#0-1) . Because `self.len` is fully attacker-controlled (it is the first 4 bytes the attacker sends), the attacker can request up to `u32::MAX` (~4.29 GB) in a single allocation. If the allocator cannot satisfy this request, Rust's global allocator calls `handle_alloc_error`, which **aborts the entire process** — this is not a catchable panic confined to the livestream agent thread. Because `agentwire::agent::Thread::run` for the livestream `Agent` executes on the shared orb-core process [3](#0-2) , an allocation-triggered abort terminates the whole orb-core binary, including whatever signup pipeline (camera capture, IR/RGB agents, biometric pipeline, backend upload) is running concurrently in other threads of the same process.

### Impact Explanation
A successful trigger aborts the entire orb-core process mid-signup, destroying in-flight signup session state (captured frames, iris code state, fraud checks in progress) and forcing the orb to restart/reboot its software stack. This matches a denial-of-service / signup-state-wedge impact: the current signup is destroyed, and depending on process supervision/restart behavior, the subsequent signup attempt can begin from an inconsistent or partially-initialized state until the supervisor fully re-establishes the process. This is a process-wide crash primitive reachable from an unauthenticated network client, not merely a resource-exhaustion slowdown of a single subsystem.

### Likelihood Explanation
The precondition is minimal: any attacker who can open a TCP connection to port 9201 on the orb (as stipulated in the question) can trigger this by sending 4 bytes (`0xFF 0xFF 0xFF 0xFF`) as the very first bytes after connecting — no authentication, handshake, or valid livestream protocol data is required before the vulnerable allocation happens. The attack is trivially repeatable on every new connection since `EventReader` is reset via `EventReader::default()` after each stream ends [4](#0-3) .

### Recommendation
Bound the accepted length before allocating, e.g. reject or truncate reads where `u32::from_be_bytes(self.len) as usize` exceeds a sane maximum livestream message size (matching the real protocol's expected message sizes), and return an `Err`/close the connection instead of allocating. Consider also using `try_reserve`/fallible allocation APIs so an oversized request produces a recoverable error rather than an allocator abort.

### Proof of Concept
Fuzz/integration test plan:
1. Start `Upstream::new()` bound to a test port (or refactor `PORT` to be injectable for tests).
2. Open a `TcpStream` to the listener from the test.
3. Write 4 bytes `[0xFF, 0xFF, 0xFF, 0xFF]` to the stream.
4. Drive `Upstream::poll_next` (or directly `EventReader::poll_stream`) via a bounded executor and assert that:
   - The call either returns `Poll::Ready(Some(Err(_)))` (graceful rejection) **before** any allocation of `len` bytes occurs, or
   - The allocation is capped by a `MAX_MESSAGE_LEN` constant such that `self.buf.capacity() <= MAX_MESSAGE_LEN`.
5. Negative assertion: without a fix, `vec![0; 0xFFFFFFFF]` is invoked directly (verifiable via instrumentation/logging inserted at `src/agents/livestream/upstream.rs:97`), demonstrating the unbounded allocation path is reached with fully attacker-controlled input.

impl Stream for Upstream {
    type Item = Result<Event>;

    fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Option<Self::Item>> {
        if let Some((stream, event_reader)) = &mut self.stream {
            match event_reader.poll_stream(cx, Pin::new(stream)) {
                Poll::Ready(events) => {
                    *event_reader = EventReader::default();
                    match events {
                        Ok(Some(events)) => {
                            return Poll::Ready(Some(Ok(Event::UiEvents(events))));
                        }
                        Ok(None) => {
                            self.stream = None;
                            return Poll::Ready(Some(Ok(Event::Closed)));
                        }
                        Err(err) => return Poll::Ready(Some(Err(err))),
                    }
                }
                Poll::Pending => {}
            }
        }
        match self.listener.poll_accept(cx) {
            Poll::Ready(Ok((stream, addr))) => {
                self.stream = Some((stream, EventReader::default()));
                Poll::Ready(Some(Ok(Event::Connected(addr))))
            }
            Poll::Ready(Err(err)) => {
                Poll::Ready(Some(Err(eyre!("Error accepting connection: {err}"))))
            }
            Poll::Pending => Poll::Pending,
        }
    }
