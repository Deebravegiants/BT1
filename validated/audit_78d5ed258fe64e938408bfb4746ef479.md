### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) , but the tenant-identifying `shop` value that is handed to the application's handler comes from an HTTP header that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cross-check against the signed payload [3](#0-2) . `HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the `hmac` header [4](#0-3) . Since `to_signable_string` never incorporates `shop`, the equality the code implicitly relies on — "`shop` header == shop that produced this signed `body`" — is never actually checked; only "`body` was signed with our secret" is checked.

`Registry.process` then trusts `request.shop` directly to construct `WebhookMetadata` passed to the app's handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) . The `WebhookMetadata` struct treats `shop` as an authoritative tenant identifier that handlers use to route/attribute the event [6](#0-5) .

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app (it is not per-shop), any merchant who installs the app on their own store is a legitimate, unprivileged holder of body+HMAC pairs signed with that shared secret. Such a user can capture one of their own genuine webhook deliveries (raw body + valid `x-shopify-hmac-sha256`) and replay it to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain). `HmacValidator.validate` still succeeds because it only re-derives the HMAC from the (unmodified) body, and `Registry.process` will invoke the handler with `shop` set to the attacker-chosen value, causing the application to process/attribute the webhook body as belonging to a shop it never actually originated from.

This is the same bug class as the referenced report: a field that is *acted upon* (here, `shop`, used for tenant attribution) is not covered by the cryptographic check (the HMAC), so the "verified" and "trusted" values diverge — `shop_header ≠ shop_that_produced_body`.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled shop can forge webhook events that the app processes as coming from a different, victim shop. Depending on the handler's logic (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, GDPR mandatory topics, billing/fulfillment webhooks that trigger state changes, emails, or data writes keyed by `shop`), this can lead to cross-tenant data corruption, spurious uninstall/redact processing against a victim's data, or business-logic manipulation attributed to another merchant. This matches the "Critical — cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the target app on a shop they control — an "unprivileged internet user" relative to any other tenant of the app, with no access to the app's `client_secret` or any other merchant's credentials. They only need to capture one webhook delivery from their own store (trivially done by logging their own endpoint traffic) and replay it with a modified header. This is fully reachable through the gem's own `Registry.process`/`Request` code path exactly as documented, with no reliance on the host app ignoring documented behavior — the gem's `Request#shop` is presented as the trustworthy webhook shop identifier while its HMAC verification does not bind it.

### Recommendation
- Extend `to_signable_string` (or add a separate binding check in `Registry.process`) so the verified signature material includes the `shop`/`topic`/`webhook_id` header values in addition to the raw body, so a swap of the shop header invalidates the HMAC.
- Alternatively/additionally, require callers of `Registry.process` to supply the expected `shop` (e.g., from the currently loaded session/tenant context) and assert `request.shop == expected_shop` before invoking the handler, rather than trusting the header value unconditionally.
- Document explicitly that `request.shop` is currently unauthenticated and must not be used for tenant-attribution decisions without an out-of-band check.

### Proof of Concept
1. Install the app on an attacker-owned store `attacker-shop.myshopify.com`; the app's `api_secret_key` is the shared client secret for all installs.
2. Trigger any webhook topic (e.g., `orders/create`) on `attacker-shop.myshopify.com`; capture the raw body `B` and the genuine `x-shopify-hmac-sha256: H` header Shopify sends, both valid against the shared secret.
3. Replay a forged HTTP POST to the app's webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256: H` (unchanged, still valid)
   - `x-shopify-topic: orders/create` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (attacker-substituted)
4. `ShopifyAPI::Webhooks::Request.new` parses these headers [7](#0-6) ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` [5](#0-4) , causing the app to process attacker-controlled data as if it originated from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
