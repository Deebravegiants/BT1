### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with pre-transfer amounts, ignoring fee-on-transfer/rebalancing ERC20 losses - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes `reducedInputs[i].amount` from the user-supplied `order.inputs[i].amount` *before* any token transfer happens, and then unconditionally credits that assumed amount into the `_orders[commitment][token]` escrow ledger after calling `safeTransferFrom`, without ever checking how many tokens the contract actually received.

### Finding Description
In `placeOrder`, `reducedInputs` (order amount minus protocol fee) is derived purely from the caller-provided `order.inputs[i].amount`: [1](#0-0) 

This reduced amount is then written to escrow immediately after `safeTransferFrom`, with no balance verification, in both the predispatch branch and the plain-transfer branch: [2](#0-1) 

For the predispatch branch, only the *dispatcher's* balance floor is checked (`balance < requiredAmount`), but the amount credited to escrow is still `reducedInputs[i].amount` — the pre-transfer, fee-unaware value — not the measured `dust`/actual-received value: [3](#0-2) 

This is the exact bug class from the external report: the contract assumes `amount` tokens were received via `transferFrom`, which does not hold for fee-on-transfer or rebalancing ERC20 tokens. The escrow ledger `_orders[commitment][token]` becomes inflated relative to the gateway's actual token balance.

Notably, the primary (non-Tron) implementation at `evm/src/apps/IntentGatewayV2.sol` has already been hardened against exactly this issue by measuring `balanceOf` before/after the transfer and mutating `order.inputs[i].amount` to the actual received value: [4](#0-3) 

The Tron contract lacks this protection entirely, making it a regression/divergent analog of the fixed bug.

### Impact Explanation
When a fee-on-transfer or rebalancing ERC20 is used as an order input:
- The gateway's actual token balance is less than the sum of all `_orders[commitment][token]` entries recorded for that token.
- On fill/redemption, `withdraw()` transfers `body.tokens[i].amount` (matching the inflated committed/escrowed value) to the beneficiary and decrements the ledger: [5](#0-4) 
- Because the contract's real token balance is insufficient to cover the sum of all outstanding escrow entries, later withdrawals for the same token (from unrelated, legitimate orders) can revert or transfer less than recorded, permanently freezing other users' escrowed funds — a shared-token insolvency, not merely a loss to the depositor of the non-standard token.

This is a concrete permanent freezing-of-funds vulnerability reachable by any unprivileged user calling `placeOrder` with a non-standard ERC20, matching the required severity bar (Medium/High freezing of funds).

### Likelihood Explanation
Likelihood is Medium: it requires the gateway operator to register/allow a fee-on-transfer or rebalancing token as a supported input asset. Since `IntentGatewayV2` is a generic ERC20-accepting intents gateway (not restricted to a whitelist of known-safe tokens in the shown code), any token configured or accepted as an input by users triggers this path deterministically on every `placeOrder` call.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom` (and before/after the dispatcher sweep in the predispatch branch), and credit `_orders[commitment][token]` with the actually-received amount rather than the pre-transfer `reducedInputs[i].amount`. The commitment hash should also be computed from the actual received amounts to keep the escrow, commitment, and reconciliation logic consistent, as done in the primary implementation.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and register a fee-on-transfer ERC20 (e.g., 1% fee on `transferFrom`) as an allowed input token.
2. User A calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000}`. `reducedInputs[0].amount` is computed as `1000` (minus protocol fee if any) at line 362-370, before transfer.
3. `safeTransferFrom(userA, gateway, 1000)` actually delivers only 990 tokens to the gateway (1% fee burned) — see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` `FeeOnTransferToken._transfer` for the reference fee model at lines 2726-2734.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` (line 463) records 1000 (or fee-adjusted ~997) even though the gateway only holds 990.
5. User B places a separate order with the same FOT token, again crediting escrow for slightly more than actually held.
6. When orders are filled/redeemed via `withdraw()`, the cumulative recorded escrow across orders exceeds the gateway's real FOT balance; a later legitimate withdrawal fails (`token.call` returns false / balance insufficient) or drains tokens intended for another order, permanently freezing that user's funds.
