Audit Report

## Title
Empty-password LDAP bind allows authentication bypass via unauthenticated bind - (File: core/sessions/ldapauth/ldap.go)

## Summary
`ldapAuthenticator.CreateSession` and `TestPassword` forward the user-supplied password from the `/sessions` login request directly into `conn.Bind()` without ever checking whether the password is empty. Per RFC 4513 §5.1.2, a non-empty DN with a zero-length password is a defined "unauthenticated bind" that many LDAP/AD servers will report as successful, letting an attacker who knows a victim's email obtain a fully authenticated session without any real credential.

## Finding Description
`SessionRequest.Password` is an unvalidated plain string [1](#0-0) , bound directly from the JSON body of `POST /sessions` and passed to the authentication provider with no empty-password check [2](#0-1) . In the LDAP provider, `CreateSession` binds using `sr.Password` verbatim: [3](#0-2) . If the bind succeeds (as many servers will for an unauthenticated bind), the code proceeds to call `FindUser` to resolve the target account's real role and creates a full session for that identity [4](#0-3) . The same unchecked pattern exists in `TestPassword` [5](#0-4) . No other layer performs empty-password rejection: the local/bcrypt fallback path (`localLoginFallback`) is not vulnerable to this class because `utils.CheckPasswordHash` rejects empty input against a bcrypt hash [6](#0-5) , but that path is only reached as a fallback if the LDAP bind attempt fails — meaning a successful unauthenticated bind short-circuits before that safety net is even relevant. The password-complexity utility in `core/utils/password.go` [7](#0-6)  is also not applied at login time (it's used for setting new passwords, not for authenticating existing ones), so it does not mitigate this issue.

## Impact Explanation
If the configured upstream LDAP/AD server permits unauthenticated binds for the resolved user DN — a common legacy/default configuration and exactly the scenario behind CVE-2020-2300 — an unprivileged remote attacker who knows or guesses any valid user email (including an admin's) can obtain a fully authenticated Chainlink node web session for that identity by sending `{"email":"<victim>","password":""}` to `/sessions`, with zero correct credentials. This maps to the in-scope "node API authentication/role bypass" impact category, and could result in privilege escalation to Admin, exposing job management and fund-movement-capable functionality.

## Likelihood Explanation
This is opt-in functionality — the deployment must explicitly enable and configure `ldapAuth` — and the realized impact further depends on the external LDAP/AD server's own configuration permitting unauthenticated binds. That said, given LDAP is enabled, the Chainlink code path performs zero client-side mitigation for this well-known LDAP semantic footgun, so exploitability rests entirely on external server posture rather than any defense in this codebase. Unauthenticated binds being allowed is a realistic, non-exotic misconfiguration that is common enough in enterprise directories that Jenkins treated the equivalent bug as Critical severity.

## Recommendation
Explicitly reject empty passwords before calling `conn.Bind()` in both `CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go`, e.g.:
```go
if sr.Password == "" {
    return "", errors.New("password must not be empty")
}
```
Apply the equivalent check to the `password` parameter in `TestPassword`. This removes reliance on the correctness of the upstream directory server's unauthenticated-bind handling, mirroring the fix Jenkins applied for CVE-2020-2300.

## Proof of Concept
1. Configure the node with `ldapAuth` authentication pointed at a directory server that allows unauthenticated binds for the resolved user DN (or one that follows RFC 4513 §5.1.2 unauthenticated-bind semantics by default).
2. Send:
```
POST /sessions
Content-Type: application/json

{"email":"admin@example.com","password":""}
```
3. Trace through `ldapAuthenticator.CreateSession`: `conn.Bind(searchBaseDN, "")` returns nil error (per RFC 4513 unauthenticated bind), `FindUser` resolves the real admin role, and a session cookie is issued for the admin account [8](#0-7)  — with no correct password ever supplied.
4. As a unit-test equivalent: extend `TestORM_CreateSession_UpstreamBind` in `core/sessions/ldapauth/ldap_test.go` to mock `mockLdapConnProvider.On("Bind", mock.Anything, "").Return(nil)` and assert that `CreateSession` with `Password: ""` still returns a valid session ID with no error, demonstrating the code accepts an empty password whenever the mocked/underlying bind reports success.
