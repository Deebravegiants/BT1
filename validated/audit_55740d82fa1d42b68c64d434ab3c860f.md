### Title
Unrestricted swap venues can attach unauthorized token transfers to the caller’s authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
**Medium.** A caller-controlled swap route can name an arbitrary pool contract, and code executed through that route can request an unrelated `token.transfer` from the original caller; Soroban records the request beneath the caller’s controller authorization, so signing the simulated authorization tree authorizes the theft. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates the caller, accepts the caller-supplied `StrategySwap`, and forwards it through `withdraw_and_swap_from_supply`. [3](#0-2) 

`swap_tokens` authorizes only the exact controller-to-router input transfer, but it then invokes `router.execute_strategy` while the original caller’s authorization remains active for the transaction. [4](#0-3) 

The router takes each hop’s `pool`, `token_in`, and `token_out` from the route’s caller-controlled address registry and dispatches the selected venue without a pool allowlist. [1](#0-0) [5](#0-4) 

A malicious pool can therefore execute `token::Client::transfer(victim, attacker, amount)` for any unrelated token while it is below the victim’s authorized `swap_collateral` invocation. [6](#0-5) 

The adversarial test records that rogue transfer as a sub-invocation under the victim’s `swap_collateral` authorization and demonstrates that signing the poisoned tree moves the wallet token while the swap still supplies the expected output. [7](#0-6) 

### Impact Explanation
An attacker can steal arbitrary token balances from the victim’s wallet, including assets unrelated to the lending position, bounded only by the token balances and the child invocations included in the signed authorization tree. [8](#0-7) 

This is theft of user funds rather than merely a bad fill: measured output checks can pass because the malicious route returns the promised output while adding a separate victim-funded transfer. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The victim must sign an authorization tree containing the malicious child transfer, but the route is supplied as opaque strategy data and simulation naturally reports the rogue transfer beneath the otherwise valid controller call. [11](#0-10) 

The attack is unprivileged because any address can deploy or specify a compatible malicious pool, provide the output needed to satisfy balance-delta checks, and submit the malicious route to a victim for signing. [12](#0-11) [13](#0-12) 

### Recommendation
Resolve swap pools from an immutable or protocol-managed venue registry rather than accepting pool addresses directly from the route payload. [14](#0-13) 

If arbitrary pools must remain supported, add a contract-level venue/pool allowlist and reject any hop whose resolved pool is not authorized for the selected venue. [5](#0-4) 

Client-side auth-tree inspection can reduce exposure, but it does not replace contract enforcement because wallet UX and opaque XDR payloads remain part of the attack surface. [15](#0-14) 

### Proof of Concept
1. Victim supplies `USDC` and owns a valid `account_id`; the attacker deploys a pool-compatible contract with a `swap` method containing `token.transfer(victim, attacker, wallet_balance)` for an unrelated token. [16](#0-15) 

2. The attacker constructs `swap_collateral(victim, account_id, current=USDC, from_amount, new=ETH, swap=payload)`, where the payload’s `assets[idx_a]` is the malicious pool and its input/output assets are `USDC`/`ETH`. [17](#0-16) [14](#0-13) 

3. The malicious pool pulls or receives the routed input, sends enough `ETH` back to satisfy the measured-output check, and additionally calls `token.transfer(victim, attacker, wallet_balance)`. [9](#0-8) [6](#0-5) 

4. Simulation represents the unrelated transfer as a child of the victim’s `swap_collateral` authorization; signing that returned tree executes both the valid collateral swap and the wallet-token theft. [2](#0-1) [8](#0-7)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
