### Title
Webhook `shop` (and topic/webhook_id) identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body, not over any header. This breaks the identity binding `HMAC-verified bytes == bytes used to identify the tenant`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of `@raw_body`), and then immediately forwards `request.shop` — an unauthenticated header — to the app's webhook handler as the trusted tenant identifier: [3](#0-2) 

This is packaged into `WebhookMetadata`, whose `shop` field is a `String` the host application is expected to trust for tenant-scoped side effects (e.g., looking up which merchant's data to redact/mutate): [4](#0-3) 

Because the `shop-domain` header (and `topic`/`webhook-id`) are not part of the HMAC-signed material, an attacker who can produce (or replay) a validly-HMAC-signed body — e.g., by reusing a body/HMAC pair captured from a webhook for their own store, since the same JSON payload shape can be HMAC'd from an attacker-owned shop and still contain arbitrary header values — can present that same signed body while attaching a `shop-domain` header for a **different, victim** shop. `Utils::HmacValidator.validate` only checks that `HMAC(raw_body, secret) == received_hmac`; it never binds the header-supplied `shop` to that computation. The equality the code assumes — "the shop reported in headers equals the shop that produced this HMAC" — is never actually enforced.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as the docs and interface explicitly instruct) to decide which merchant record to act on — e.g., processing `shop/redact`, `customers/redact`, or `customers/data_request` mandatory compliance topics, or any tenant-scoped write — an attacker who can obtain one validly-signed webhook body (their own shop's webhook, which they legitimately receive) can splice in an arbitrary `shop-domain` header value and cause the app to perform the corresponding action against a different, unrelated shop. This crosses the tenant boundary (cross-tenant action) using only a body/HMAC pair the attacker legitimately possesses for their own shop, with no access token or `client_secret` required — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires only that the attacker control one legitimate webhook endpoint delivery for their own shop (any developer/merchant with an app installed on a shop they own can generate any webhook body and its correct HMAC by triggering the corresponding Shopify event), then replay that raw body + HMAC header to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` header. No privileged credentials, TLS interception, or social engineering is needed, and the gem's own `HmacValidator.validate` call in `Registry.process` will report the tampered request as valid.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them) in the value that is HMAC-verified, or require the host application to separately authenticate the webhook delivery's origin against the shop that installed the app (e.g., cross-check `shop` against a known/expected value for that webhook subscription) before trusting `WebhookMetadata#shop` for any tenant-scoped action. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are NOT covered by HMAC verification and must not be trusted for authorization decisions without additional binding.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives (or triggers) a legitimate webhook delivery, e.g. `customers/redact`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`).
2. Attacker resends `POST /webhooks` to the app's endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but replaces `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) only, and matches `H` — validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs its tenant-scoped action (e.g., redaction/mutation) against the victim shop, despite the HMAC never having verified anything about that shop value.
