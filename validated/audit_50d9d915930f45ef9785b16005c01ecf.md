### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unvalidated JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request — the request that carries the app's `client_id` and `client_secret` — directly from the `dest` claim of the caller-supplied session token, without validating that the resulting host is a real Shopify domain. This is the exact class of "identity-binding" break described by the report's bug class: a value that is *cryptographically verified* (the JWT signature) is trusted for a purpose (selecting the network destination for the app's secret) that requires an *additional, separate* validation (that the resulting host is actually `*.myshopify.com`/`*.myshopify.io`/etc.), and that additional validation is missing here even though the same file implements it correctly for a sibling method.

### Finding Description
In `lib/shopify_api/auth/jwt_payload.rb`, the shop value exposed to callers is computed as: [1](#0-0) 

```ruby
def shop
  @dest.gsub("https://", "")
end
alias_method :shopify_domain, :shop
```

`@dest` is taken verbatim from the JWT payload's `dest` claim with only an `aud == Context.api_key` check performed elsewhere in the class: [2](#0-1) 

No check is made that `dest` is a subdomain of a trusted Shopify domain (the kind of check implemented in `ShopValidator`).

`TokenExchange.exchange_token` — the flow documented as the **recommended** OAuth mechanism for embedded apps — then uses this unvalidated value directly as the shop for a `Session`, and that session's `shop` becomes the request host that receives the app's `client_id`/`client_secret`/`subject_token`: [3](#0-2) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = {
  client_id: ShopifyAPI::Context.api_key,
  client_secret: ShopifyAPI::Context.api_secret_key,
  ...
}
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```

`Clients::HttpClient` builds the request URL straight from `session.shop`: [4](#0-3) 

```ruby
api_host = Context.api_host
@base_uri = T.let("https://#{api_host || session.shop}", String)
@base_uri_and_path = T.let("#{@base_uri}#{base_path}", String)
```

The equality that should hold but does not is: `host that is verified as a genuine Shopify domain` == `host that receives the app's client_secret`. Instead, the code implicitly assumes `dest` claim host == trusted Shopify host, without checking it.

This is not a hypothetical inconsistency — the same file demonstrates the intended safeguard is known and used elsewhere: `migrate_to_expiring_token`, in the same module, explicitly sanitizes the shop before it is used to build the request host: [5](#0-4) 

```ruby
def migrate_to_expiring_token(shop:, non_expiring_offline_token:)
  ...
  validated_shop = Utils::ShopValidator.sanitize!(shop)
  shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
```

`ShopValidator.sanitize!` enforces that the shop resolves to one of a fixed set of trusted Shopify domains (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or raises `InvalidShopError`: [6](#0-5) 

`exchange_token` — the primary, documented, "Recommended" embedded-app OAuth path — has no equivalent call anywhere in its execution path.

### Impact Explanation
If the `dest` claim of a session token accepted by `exchange_token` is ever attacker-influenced (e.g., through host-application misuse of App Bridge, non-Shopify token issuance paths, or any scenario where a syntactically-valid-but-non-Shopify `dest` ends up in a token that still verifies for this app's `aud`), the gem will construct a POST request to `https://<attacker-controlled-host>/admin/oauth/access_token` and place the app's `client_id`, `client_secret`, and `subject_token` (the session token itself) directly in that request's body — i.e., SSRF carrying the app's credentials to an arbitrary host, and exfiltration of the app's `client_secret` and `subject_token` to that host.

### Likelihood Explanation
Exploitation requires a session token that still passes this gem's `aud`-matching signature check yet carries a `dest` claim not restricted to real Shopify domains. This gem does not independently constrain what `dest` may contain (unlike the parallel `migrate_to_expiring_token` method), so the guarantee that `dest` is a real Shopify host relies entirely on token-issuance behavior outside this gem's control. This is an internal design inconsistency rather than a fully self-contained exploit in isolation, which lowers confidence relative to a directly demonstrable end-to-end PoC.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `jwt_payload.shop` (the `dest` claim) with `Utils::ShopValidator.sanitize!` before constructing `shop_session`/`HttpClient`, mirroring the safeguard already present in `migrate_to_expiring_token`. Consider also enforcing the same restriction inside `JwtPayload#shop` itself so all callers get the guarantee uniformly.

### Proof of Concept
Conceptual (cannot be fully demonstrated without a session-token-issuance bypass, which is out of this gem's scope):
1. Obtain/produce a session token whose `aud` claim matches this app's `api_key` and whose signature verifies, but whose `dest` claim is set to a non-Shopify host (e.g., `attacker.example`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns `"attacker.example"` unchanged.
4. `Clients::HttpClient` builds `@base_uri = "https://attacker.example"` and POSTs the app's `client_id`, `client_secret`, and the raw `subject_token` to `https://attacker.example/admin/oauth/access_token`, compared with `migrate_to_expiring_token`, which would have rejected `"attacker.example"` via `ShopValidator.sanitize!`.

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
