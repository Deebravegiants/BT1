### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC validity purely over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. Since the same secret and raw body pair remains valid for any header combination, a party in possession of one legitimate `(raw_body, hmac)` pair from their own store's webhook can replay it while swapping the `shop-domain` header to a different tenant, and the app will process/store the payload as belonging to the spoofed shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , meaning the cryptographic binding covers exclusively the JSON body bytes.

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no participation in the signed content [3](#0-2) . `Registry.process` validates only the HMAC of the body and then trusts these header-derived fields to build `WebhookMetadata`, dispatching it to the app's handler as the identity of the originating shop: [4](#0-3) .

This breaks the intended identity binding: `shop` (acted upon by the handler to attribute data to a tenant) ≠ `shop` (covered by the HMAC signature). The signature only proves "this body was produced/signed by an entity possessing `client_secret`" — it says nothing about which shop the body was signed for, because Shopify's real webhook signing also only signs the raw body per-request, using the same app secret across every shop that has installed the app.

### Impact Explanation
Any merchant who has installed the app (an "unprivileged" actor relative to other tenants of the same app) receives real webhooks with valid `(raw_body, hmac)` pairs for their own store. Because the header fields are not part of the signed content, that merchant can resend the exact same body+hmac to the app's webhook endpoint while substituting a different `shopify-shop-domain` (and/or `webhook-id`/`topic`) header pointing at another merchant's shop. `Registry.process` will accept it as valid (HMAC matches) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop [5](#0-4) . Any app that keys persistence, side effects, or authorization decisions off `data.shop` from webhook handlers is exposed to cross-tenant data injection/corruption — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires an actor who can install the app for at least one shop (the normal, low-privilege path for any Shopify merchant) and can capture one legitimate webhook delivery for their own store, then replay it with a modified `shop-domain` header value at the app's public webhook endpoint. No knowledge of `client_secret` or another shop's access token is required, since the HMAC-verified content (the raw body) is unchanged from the original delivery.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` header values in the HMAC-signed payload verification (or otherwise cryptographically bind them, e.g., by having `to_signable_string` incorporate a canonical representation including the shop domain), so header spoofing without invalidating the signature is not possible. At minimum, applications should be told explicitly in documentation that these header fields are unauthenticated and must not be trusted for tenant attribution without additional server-side lookups (e.g., verifying the shop against the app's own installed-shop store), but the library itself should not expose an API (`WebhookMetadata#shop`) that implies these values are verified.

### Proof of Concept
1. Install the target app on shop A (attacker-controlled) and shop B (victim), both served by the same app instance.
2. Trigger a webhook delivery for shop A; capture the raw POST body and the `shopify-hmac-sha256` header value (this pair is valid because it was actually signed by Shopify using the app's `client_secret`).
3. Replay the exact same body and `hmac` header to the app's webhook endpoint, but set `shopify-shop-domain: shop-b.myshopify.com` (and, if desired, spoof `shopify-webhook-id`/`shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the hmac — validation succeeds [6](#0-5) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: ..., ...)` [7](#0-6) , causing the app to process shop A's webhook payload as if it belonged to shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
