[1](#0-0) ### Title
Stale price cache survives governance execution inside `flash_position`, allowing undercollateralized debt minting - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` snapshots oracle prices before invoking an attacker-controlled receiver, but its `Context` continues using those stale prices after the callback returns. A receiver can execute an already-ready governance operation that reprices collateral downward or debt upward, then final solvency is still evaluated at the pre-callback prices, allowing debt to be minted against collateral that is no longer sufficient.

### Finding Description
`process_flash_position` prefetches account and strategy prices at line 117, then enters `with_flash_guard`, mints debt, forwards the proceeds, and invokes the receiver callback at lines 121–141. [2](#0-1) 

`Context::fetch_prices` only fetches assets absent from `token_prices`, while `cached_price` later returns the retained `PriceFeedRaw`; neither function refreshes a cached feed after external execution. [3](#0-2) 

The callback is a user-selected Wasm contract and can invoke separate contracts while the controller is on the stack; in particular, it can call governance’s permissionless `execute` path for an operation whose timelock has already elapsed. [4](#0-3) [5](#0-4) 

After the callback, the controller deposits the measured collateral deltas and calls `strategy_finalize`, still using the same `Context`. [6](#0-5) 

The final gate uses `calculate_account_risk_totals`, which retrieves collateral and debt prices through `cached_price`; consequently, a governance oracle change executed by the callback does not affect the final health-factor or LTV checks. [7](#0-6) [8](#0-7) 

### Impact Explanation
The attacker receives newly minted debt assets before the callback and leaves an account that passed finalization only because it used stale prices. When the ready governance operation lowers collateral valuation or raises debt valuation, the persisted position is undercollateralized under the newly active oracle configuration, enabling the attacker to default and socialize the shortfall into the pool. This is theft of pool liquidity and can create protocol insolvency. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The attack requires a governance operation affecting a relevant oracle to already be executable and the attacker to time `flash_position` around that transition. Those transitions are externally visible, and the receiver can perform the governance execution atomically inside the callback without needing any privileged key. The path is therefore constrained to governance-update windows, but is fully reachable by an unprivileged account once such an operation is ready. [11](#0-10) 

### Recommendation
Do not reuse oracle, market-index, or spoke-configuration snapshots across external callbacks whose code can execute governance. After `invoke_receiver` returns, either reconstruct `Context` or explicitly clear `token_prices`, `market_indexes`, `pool_sync_data`, `spoke_config`, and `spoke_assets` before collateral processing and `strategy_finalize`. Alternatively, execute and commit position/account state before the callback, or block governance execution while the flash-position guard is active. The post-callback risk check must resolve prices under the state active at finalization. [12](#0-11) [13](#0-12) 

### Proof of Concept
1. Governance has a ready `ConfigureAssetOracle` operation that lowers collateral token `C`’s accepted price from `P_old` to `P_new`, where `P_new << P_old`.
2. The attacker deploys a Wasm receiver pre-funded with `N` units of `C`.
3. The attacker calls `Controller::flash_position(caller, account_id=0, spoke_id, mode=Multiply, debt=D_asset, amount=A, receiver, data, collaterals=[(C, N)], refund_assets=[])`.
4. The controller caches the old prices for `C` and `D_asset`, mints `A` debt units, forwards them to the receiver, and invokes `execute_flash_position`. [14](#0-13) 
5. Inside the callback, the receiver calls the separate governance contract’s `execute` entrypoint for the ready oracle operation, then transfers the required `N` units of `C` to the controller.
6. After callback return, the controller deposits `N` units of `C`; `cached_price(C)` remains `P_old`, so `ltv_collateral * P_old >= debt * P_debt` and the health-factor checks pass.
7. The transaction commits an account whose collateral is worth only `N * P_new` under the newly active oracle while holding debt valued above that amount; the attacker keeps the borrowed `D_asset` proceeds. [3](#0-2) [15](#0-14)
