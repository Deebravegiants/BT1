### Title
Accrual overflow panic permanently freezes a market — withdrawals, repayments, and liquidations all revert once `borrowed × borrow_index` exceeds the RAY value domain - (File: common/src/rates/index.rs)

### Summary
The analog of CVE-2019-2530 (a crash/hang DoS) maps onto the pool's accrual path: interest accrual multiplies the market's scaled debt by the borrow index in plain `i128` RAY arithmetic, and panics on overflow instead of saturating. Because `global_sync` runs before every state-changing pool verb, once a market's `borrowed * borrow_index` crosses `i128::MAX`, every subsequent call that accrues that market reverts. The result is a permanent, protocol-wide freeze of that market: no `withdraw`, no `repay`, no `liquidate`, no `clean_bad_debt`, and no further `update_indexes`.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs` invokes `accrue_step` (`common/src/rates/simulate.rs`), which calls `calculate_supplier_rewards` in `common/src/rates/index.rs`. That function computes:

```
let old_total_debt = borrowed.mul(env, old_borrow_index);   // line 80
let new_total_debt = borrowed.mul(env, new_borrow_index);   // line 81
```

`Ray::mul` traps with `MathOverflow` when `scaled * index / RAY` leaves `i128`. The borrow index itself is capped at `MAX_BORROW_INDEX_RAY = 10^36` in `update_borrow_index` (line 15), but that clamp does not protect the *value* multiplication: `borrowed` (scaled shares, up to ~`10^38`-scale depending on caps/decimals) times an index of even a few× RAY overflows `i128` before the index ceiling is ever reached. `update_supply_index` has the same shape at line 34 (`supplied.mul(env, old_index)`).

The regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320`) demonstrates exactly this: after index growth pushes the debt value over the limit, `update_indexes` fails with `MATH_OVERFLOW`, and subsequently both `withdraw` and `repay` revert with the same error — "the market is frozen: exits and repayments accrue first and hit the same panic" (lines 318–356).

Crucially there is no recovery path: accrual is a precondition of every mutation, the panic is deterministic given the stored `borrowed`/`borrow_index`, and nothing shrinks `borrowed` without first accruing.

### Impact Explanation
Permanent freezing of funds. All supplier principal and accrued interest in the affected market becomes irrecoverable, all borrower positions become unrepayable (and unliquidatable, so bad debt can never be closed), and pool revenue in that market is locked forever. On a multi-market pool the frozen book also blocks any path that iterates or accrues it. This is a direct analog of the CVE's "unauthorized ability to cause a hang or frequently repeatable crash" — here the "crash" is a deterministic arithmetic trap and it is permanent rather than restartable.

### Likelihood Explanation
The trigger conditions are attacker-reachable but demanding: the attacker needs a market whose scaled debt times index overflows `i128`. With the token-to-RAY domain admitting ~170 billion whole tokens, a whale can supply and borrow a sufficiently large position (or wait for index growth at high utilization — the test hits the cliff at 98% utilization on a steep curve). A single unprivileged `borrow`/`supply` can also push `borrowed` over the cliff on a market that is already close, since accrual computes values at the *old* index before the new oversized book exists; the *next* `update_indexes` call — permissionless — then bricks the market. Feasibility depends on governance-set caps admitting oversized books, so it requires a large-balance attacker rather than a dust attack, but requires no privileges, no leaked keys, and no oracle manipulation. Given the capital requirement and time/index-growth dependence, Medium severity is appropriate.

### Recommendation
In `calculate_supplier_rewards` and `update_supply_index`, replace the trapping `mul` with a saturating computation (`mul_div_floor_saturating`-style, as already used at line 41 and in `protocol_fee_shares` at line 95) so that a debt value exceeding the RAY domain clamps rather than panics. Alternatively, gate entry (`calculate_scaled_borrow`/`calculate_scaled_supply` and cap admission in `common/src/validation.rs`) with a headroom check that accounts for index growth to the `10^36` ceiling, so a book can never reach a size where its own accrual overflows. Emit an explicit event when accrual clamps at a value ceiling so operators can intervene via `recapitalize` before the cliff.

### Proof of Concept
The existing harness test is the executable PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`):

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);             // unprivileged borrow, 98% util

// advance time; eventually:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), MATH_OVERFLOW);
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), MATH_OVERFLOW);
// last.borrow_index < MAX_BORROW_INDEX_RAY — the cap never engaged
```

All three calls are unprivileged entrypoints (`update_indexes`, `withdraw`, `repay`); once the value overflow is reached, every one reverts deterministically and permanently.
