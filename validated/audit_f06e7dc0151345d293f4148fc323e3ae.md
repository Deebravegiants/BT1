### Title
Webhook `shop` (and `topic`) identity is not bound by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as fully authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler. However, the HMAC only signs the raw request body — never the `shop`, `topic`, `webhook-id`, or `api-version` headers. Any party who can obtain one genuinely-signed webhook body/HMAC pair (e.g., by installing the app on a shop they control) can replay that exact body with a forged `shop-domain` header pointing at a different tenant, and the gem will report it to the handler as an authenticated webhook "from" that other shop.

### Finding Description
`Webhooks::Request#hmac` reads the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` delivered to the app's handler — with no separate verification that this `shop` value actually corresponds to the shop that produced the signed body: [4](#0-3) 

This breaks the identity binding: `hmac == HMAC(secret, body)` says only "this body was signed by our app's secret," while the gem (and its documented handler contract) presents `data.shop` as "this body came from *this* shop." The library's own docs instruct apps to key their handling logic off `data.shop`: [5](#0-4) [6](#0-5) 

Because every shop that installs the same app shares the same `api_secret_key`, a party who controls one legitimate installation (an "unprivileged" tenant relative to other merchants) can capture a real `(raw_body, hmac)` pair from their own shop's webhook deliveries and resend it with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to another shop's domain. `HmacValidator.validate` still returns `true` because the body/HMAC pair is genuinely valid, and `Registry.process` forwards `shop: <victim_shop>` to the handler.

### Impact Explanation
This is a cross-tenant identity forgery: the gem hands the host application attacker-chosen tenant identity (`shop`) under the guise of cryptographic verification. Any app whose webhook handler uses `data.shop` to look up/mutate per-tenant state (which is exactly what the gem's own documentation recommends: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into applying another tenant's webhook body against a victim shop's session/records, or into misrouting `topic`-gated logic (e.g., triggering `shop/redact` or `customers/data_request` handling) for a shop that never sent that event. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on at least one shop (a normal, unprivileged merchant relationship) and be able to send an arbitrary HTTP request to the app's webhook endpoint with custom headers — no access to `api_secret_key`, tokens, or the victim's data is required. The vulnerable code path (`HmacValidator.validate` + header-derived `shop`/`topic`) is on the primary, always-exercised webhook processing flow, not an edge case.

### Recommendation
Bind the tenant/topic identity into the authenticated material instead of trusting bare headers post-HMAC-check:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (mirroring Shopify's guarantee that the signature is meant to authenticate the whole delivery, not just the JSON body), or
- Require the caller (host application) to cross-check `request.shop` against a shop that is known to have this `api_secret_key`/session on file before trusting it, and document this requirement clearly since the gem cannot itself know which shops are "installed."
At minimum, `Registry.process` should not implicitly present `request.shop`/`request.topic` as verified data once `HmacValidator.validate` passes, given they are not part of the signed payload.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures a real webhook delivery, e.g. for topic "customers/create":
raw_body = '{"id":1,"email":"victim@example.com"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker resends the exact same body/HMAC, only rewriting the shop-domain header
forged_headers = {
  "x-shopify-topic" => "customers/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC pair is genuinely valid)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The host app's handler now processes attacker-controlled data as if it belongs to victim-shop.
```
