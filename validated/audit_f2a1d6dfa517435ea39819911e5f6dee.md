Based on the codebase, I found a legitimate binding-break analog. The webhook HMAC signature validates only the raw body, but the `shop` value dispatched to the app's handler comes from an unauthenticated header that is never covered by the signature.

### Title
Cross-Tenant Webhook Spoofing via Unauthenticated `shop-domain` Header Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over that body alone. The `shop-domain` header, which `ShopifyAPI::Webhooks::Registry.process` passes straight through to the app's handler as the tenant identifier, is never included in the signed content. This breaks the identity binding: `hmac-signed(body)` == "authenticated" but `shop` (used as the tenant key for the dispatched event) is fully attacker-controlled and unauthenticated.

### Finding Description
`Webhooks::Request#hmac` decodes the `hmac-sha256` header and `#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Registry.process` verifies the HMAC over the body via `Utils::HmacValidator.validate(request)`, and if it passes, dispatches to the handler using `request.shop` (sourced from the `shop-domain` header, not from the signed payload) as the tenant identity: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. HMAC over the body string only — the `shop` header value is never part of the signed content: [3](#0-2) 

Because `shop` is not part of the signable string, any request with a body+HMAC pair that is valid for shop A (e.g. captured from a legitimate webhook delivered to the attacker's own shop) remains HMAC-valid if the `x-shopify-shop-domain` / `shopify-shop-domain` header is swapped to shop B. The library performs no check that the asserted `shop` matches any session or that it's consistent with the signed content, so `handler.handle` is invoked with `WebhookMetadata` carrying an attacker-chosen `shop` value while the HMAC still validates: [4](#0-3) 

The binding broken is: shop authenticated (nothing authenticates it — only body integrity is checked) vs. shop used as the tenant/session key by the app (`data.shop` passed to the handler, which per the library's own documented usage pattern is used to look up/act on a specific merchant's session and data).

### Impact Explanation
Any unprivileged internet user who can obtain one genuine webhook body+HMAC pair (e.g., by installing the target app on their own trial/free shop and having Shopify deliver a real webhook) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop domain. The library reports this as a validly-signed webhook for the victim shop, and the app-level handler (which trusts the delivered `shop`/`WebhookMetadata#shop` to select the merchant record/session to act on, per the documented handler pattern) will process it as belonging to the victim tenant. This is a cross-tenant access/data-integrity vulnerability: attacker-controlled data is committed under another merchant's identity without possessing any of that merchant's credentials.

### Likelihood Explanation
High. No secret key, access token, or privileged position is required — only possession of one legitimate webhook (obtainable by installing the app on an attacker-owned shop, which most public/free apps allow). The header manipulation is trivial (a raw HTTP replay with one header changed) and the gem provides no built-in check binding `shop` to the signed content or to prior session state before dispatching to the handler.

### Recommendation
Include the shop-domain (and ideally webhook `topic`/`api_version`) in the HMAC-signed content, or independently validate that the `shop-domain` header corresponds to a shop with an active, previously-established session/installation before dispatching to the handler. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop header so `HmacValidator.validate` fails if it is altered, and `Registry.process` should treat `request.shop` as untrusted until cross-checked against known installed shops.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker-shop.myshopify.com` and let Shopify deliver a legitimate webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` with the app's `api_secret_key`, which the attacker never needs to know).
2. Capture `B` and `H`.
3. Replay the request to the app's public webhook endpoint with headers:
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`, body `B` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B, secret) == H` — unaffected by the header change: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied data under the victim shop's tenant identity. [4](#0-3)
