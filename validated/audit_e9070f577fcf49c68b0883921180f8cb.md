## Finding

### Title
Webhook `shop` (and other Shopify-prefixed headers) are trusted for tenant identity but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read unauthenticated and passed straight through to the host application's webhook handler as the tenant identifier. Any actor capable of obtaining one genuine `(body, hmac)` pair (e.g., a normal Shopify merchant who installs the app on their own store) can replay that exact body against the app's shared webhook endpoint while substituting an arbitrary `shop-domain` header, and `ShopifyAPI::Utils::HmacValidator.validate` will still accept it because the header is outside the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates HMAC only, then forwards `request.shop` (the unauthenticated header value) directly into the `WebhookMetadata` that is handed to the app's business logic: [3](#0-2) 

`HmacValidator.validate` in turn only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the body only: [4](#0-3) 

The identity binding that is broken here is: `shop header used to attribute the webhook == shop bytes actually covered by the HMAC`. Those two are not equal - the HMAC only proves the body came from Shopify for *some* shop, not for the specific shop named in the `shop-domain` header.

### Impact Explanation
Any unprivileged individual who can install the target app on their own (even free/dev) Shopify store receives genuinely-signed webhooks for their own shop. Because the signature never covers the shop identity, that person can capture one such `(raw_body, hmac)` pair and re-POST it to the app's single shared webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still succeeds (the body/hmac pair is authentic), and `Registry.process` builds a `WebhookMetadata` whose `shop` field now claims to be the victim's domain. If the host application's webhook handler uses `data.shop` (as the gem's documentation and design imply it should) to select which tenant's records to create/update/delete, this leads to cross-tenant data corruption or disclosure - a Critical-impact class (cross-tenant access) enabled purely by manipulating a header this gem does not authenticate.

### Likelihood Explanation
The prerequisite is only "the attacker can install the app on a shop they control" (a normal, unprivileged Shopify merchant action), plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (an already-known, un-secret URL in most integrations). No access to `api_secret_key`, TLS interception, or any privileged credential is required, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the signed payload before it is trusted:
- Do not rely solely on the `shop-domain`/`x-shopify-shop-domain` header value for tenant attribution. Include it (and `topic`/`webhook_id`) as part of the string being HMAC-verified, or
- Have `ShopifyAPI::Webhooks::Registry.process` cross-check `request.shop` against the specific shop the webhook subscription was registered for (tracked per-endpoint) rather than trusting an arbitrary header, and
- Document clearly (and enforce where possible) that host applications must not use `WebhookMetadata#shop` as an unauthenticated tenant key without an independent registration-time check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) that the app processes, capturing the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify with the app's real secret against `B`).
2. Attacker sends a new POST to the same public webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because HMAC only covers body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (rewritten)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally rewritten too
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `request.hmac` against `request.to_signable_string` (`= B`) - see [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled data as if it belonged to the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
