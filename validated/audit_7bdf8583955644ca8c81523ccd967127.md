### Title
Simplex FX filler prices exotic-token orders directly off manipulable Uniswap V4 `slot0`/`sqrtPriceX96` spot price, with only a static-reference deviation check as a guard - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
Simplex's `FXFiller` strategy can price cross-asset pairs from a live Uniswap V4 pool's spot price instead of a static curve. This spot price is read directly from `slot0`/`sqrtPriceX96`-equivalent V4 state, the same class of manipulable on-chain price the original report warns against, and used to size fills and reference-rate order legs. The only defense is `checkPriceGuard`, which bounds deviation against a static `referencePrice`, not execution cost, TWAP, or slippage-resistant sourcing.

### Finding Description
When a trading pair has no configured bid/ask curves and `token0` is a USD stablecoin, `FXFiller.resolveLegRates` and `referenceRate` fetch a live price from a Uniswap V4 pool via `venueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which returns `sdkPool.token0Price`/`token1Price` derived straight from the pool's current `sqrtPriceX96`/tick read via `StateView.getSlot0`: [1](#0-0) [2](#0-1) 

This is exactly the `slot0`-derived spot-price pattern flagged in the external report: a single-block AMM price with no time-weighting is used as an oracle. The as-documented flow confirms the raw pool mid is used with no fee-tier or size/impact adjustment: [3](#0-2) 

The only mitigation is `checkPriceGuard`, invoked in `resolveLegRates` and `referenceRate`, which rejects the rate only if it drifts beyond `maxDeviationBps` from a static, operator-configured `referencePrice`: [4](#0-3) [5](#0-4) 

The docs themselves acknowledge the risk explicitly but treat the static-reference band as sufficient: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote": [6](#0-5) 

However `referencePrice`/`maxDeviationBps` are optional and the guard is a static band, not a manipulation-resistant oracle (no TWAP, no multi-block confirmation): an attacker can move the pool's spot price within the configured deviation band (or the pair can be run unguarded, since "the two fields must be set together; omit both to leave the chain unguarded") and still extract a mispriced fill. `checkPriceGuard` only bounds *how far* the price can move relative to a stale reference, it does not defend against *manipulation within* that allowed band, nor does it validate liquidity depth or execution slippage.

### Impact Explanation
An unprivileged intent submitter reachable via the IntentGateway (source-chain order dispatcher) can flash-loan-manipulate the configured Uniswap V4 pool's spot price immediately before submitting/triggering a fill priced by `FXFiller`'s venue path. If the manipulated price stays within `maxDeviationBps` of the operator's static `referencePrice` (a realistic condition since that band must tolerate normal market movement, e.g. the documented 200 bps example), the solver will compute `computeLegPolicyOutput` off the skewed mid and either release excess output tokens to the attacker or accept an unfavorable input — a direct value-extraction/theft path against the solver's committed inventory, executed atomically with the flash loan sandwich as described in the source report. Pairs configured without `referencePrice`/`maxDeviationBps` are completely unguarded.

### Likelihood Explanation
Reachable end-to-end from a single submitted intent order — no privileged access is required. The attacker only needs: (1) a flash-loanable pool matching the configured V4 position pair (exotic token vs USDC/USDT), and (2) an order sized to be filled by the venue-priced leg. Given IntentGateway orders are attacker-controlled inputs and the price read happens synchronously at fill-quote time with no TWAP/multi-block smoothing, this is a realistic, self-contained attack requiring only a flash loan and one transaction sequence around the fill.

### Recommendation
Replace the raw `slot0`/spot-price read in `computeDirectPoolPriceUsd` with a manipulation-resistant price source: a Uniswap V3/V4 TWAP (multi-block time-weighted observation) or an external oracle (e.g. Chainlink) for the exotic token, and require `referencePrice`/`maxDeviationBps` guarding to be mandatory (not optional) for any venue-priced pair. Additionally, incorporate liquidity-depth/size-impact checks so `computeLegPolicyOutput` cannot extend a thin pool's mid price linearly across a large notional.

### Proof of Concept
1. Operator configures a curveless pair (e.g. USDC/CNGN) priced via `[vault.uniswapV4]` with a shallow-liquidity pool, optionally with a wide `maxDeviationBps` band (or none at all).
2. Attacker flash-loans a large amount of the pool's stable or exotic token and swaps against the configured V4 pool to shift `sqrtPriceX96`/tick in their favor.
3. In the same transaction bundle, attacker submits/triggers an IntentGateway order that the `FXFiller` prices via `resolveLegRates` → `venueUsdPrice` → `getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the now-manipulated `slot0` state via `getSlot0`. [2](#0-1) 
4. If the skewed price still satisfies `checkPriceGuard`'s deviation bound (or the chain is unguarded), the filler computes and delivers output at the manipulated rate.
5. Attacker reverses the flash-loan swap, netting the difference between the manipulated fill price and the true market price at the solver's expense.

```typescript
	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}
```

```markdown
# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.
```

```typescript
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}
```

```typescript
	private async resolveLegRates(
		orderId: string | undefined,
		leg: ResolvedLeg,
		cappedPairNotional: Decimal,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<LegRates | null> {
		// Explicitly configured curves always win — the venue only prices pairs
		// with no curves at all (and never same-token pairs, where a venue quote
		// would just be the asset's own USD price, not a spread).
		const curveless = !leg.pair.bidPricePolicy && !leg.pair.askPricePolicy
		if (curveless && !isSameTokenPair(leg.pair) && USD_STABLE_SYMBOLS.has(normalizeSymbol(leg.pair.token0))) {
			const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
			if (venueUsd) {
				// Guard compares the venue's token1-per-USD quote against the static reference.
				if (!this.checkPriceGuard(orderId, leg.token1Chain, new Decimal(1).div(venueUsd))) {
					return null
				}
				// A pool mid is ONE price, not a book: there is no opposite side
				// to report a round-trip margin against. The price guard above is
				// the venue-specific defense.
				const venueRate = new Decimal(1).div(venueUsd)
				return { rate: venueRate, oppositeRate: null, priceSource: "venue" }
			}
		}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
