## Analog Vulnerability Found

### Title
Reward distribution with zero `total_stake_shares` permanently locks staked NEAR and bricks the staking pool - (File: `staking-pool/src/internal.rs`)

### Summary
`StakingContract::internal_ping()` in `staking-pool/src/internal.rs` distributes validator rewards to `total_staked_balance` on every epoch transition, but it never checks whether `total_stake_shares` is `0` before doing so. This is the exact same root cause reported against `WrappedVault.sol`: reward/balance accounting keeps advancing independently of whether there is any outstanding "supply" (shares) to claim it, and once this happens the accrued value becomes permanently unclaimable — with the added consequence in this contract that the *entire pool* becomes permanently unusable.

### Finding Description
`ping()` is a fully public, unauthenticated method: [1](#0-0) 

It calls `internal_ping()`, which computes `total_reward` from the difference between the current NEAR account balance (including validator rewards accrued on the previously locked/staked amount) and `last_total_balance`, and then unconditionally folds that reward into `total_staked_balance`: [2](#0-1) 

Crucially, `num_shares_from_staked_amount_rounded_down(owners_fee)` (used to mint the owner's fee shares) is computed as `total_stake_shares * owners_fee / total_staked_balance`. If `total_stake_shares == 0`, this always evaluates to `0` regardless of `owners_fee`, so `num_shares > 0` is `false` and no shares are minted — yet the line `self.total_staked_balance += owners_fee;` (and the earlier `self.total_staked_balance += remaining_reward;`) still executes unconditionally: [3](#0-2) 

This state (`total_stake_shares == 0` while `total_staked_balance` can still be non-zero from residual/pending rewards) is reachable through entirely normal, unprivileged usage: if a single delegator is the only staker in the pool and calls the public `unstake_all()` method, `total_stake_shares` and `total_staked_balance` both go to zero via `inner_unstake()`: [4](#0-3) 

Because NEAR's actual unbonding/unstaking on the validator settles over several epochs, `env::account_locked_balance()` can still reflect residual locked funds (and any protocol reward accrued on them) for a period after the internal `total_staked_balance` has already dropped to `0`. Any unprivileged account can then call the public, unauthenticated `ping()` method during this window; `internal_ping()` will observe `total_reward > 0` and fold it into `total_staked_balance` while `total_stake_shares` remains `0`.

Once `total_stake_shares == 0` and `total_staked_balance > 0` simultaneously, the pool is permanently bricked:
- Any future `stake()`/`deposit_and_stake()` call computes `num_shares_from_staked_amount_rounded_down` as `0 * amount / total_staked_balance == 0`, which trips the `assert!(num_shares > 0, ...)` in `internal_stake()`, reverting every future staking attempt: [5](#0-4) 
- `unstake()`/`unstake_all()` require an account to hold `stake_shares`, but no account holds any shares corresponding to that phantom `total_staked_balance`, so nobody can ever retrieve it.

### Impact Explanation
This matches the "Critical: Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... unstake-withdraw ... flows" category. The NEAR that remains staked/locked in `total_staked_balance` after the last depositor exits becomes permanently unrecoverable, and additionally the entire staking pool contract becomes permanently unusable for all future depositors (denial of service on the core protocol function), since every `stake` call will revert forever once triggered.

### Likelihood Explanation
The precondition — a pool temporarily having zero active stakers (e.g., the sole delegator fully unstaking, which is completely normal, permissionless behavior, not privileged and not self-harm) — is realistic for any staking pool with low/variable participation. The triggering action, calling `ping()`, is public, unauthenticated, and is even automatically invoked by nearly every other contract method (`deposit`, `stake`, `unstake`, `withdraw`), so it will very likely be called during the window when the phantom reward exists.

### Recommendation
In `internal_ping()`, only distribute/accumulate rewards into `total_staked_balance` when `total_stake_shares > 0`. If `total_stake_shares == 0`, either skip reward accrual entirely (do not update `last_total_balance` beyond the actual restakeable amount) or route 100% of the reward to the owner as shares seeded against the reward amount itself (i.e., mint the owner's shares first, from a nonzero baseline), analogous to the recommended "let owner claim rewards accrued when there was no active supply" fix applied in the referenced `WrappedVault.sol` commit. Additionally, add a defensive invariant check that `total_stake_shares == 0` iff `total_staked_balance == 0` before allowing state transitions that could otherwise brick the pool.

### Proof of Concept
1. Deploy the staking pool with `owner_id = A` via `new()`; `A`'s initial deposit stakes the whole initial balance minus `STAKE_SHARE_PRICE_GUARANTEE_FUND`, setting `total_stake_shares == total_staked_balance == N`.
2. `A` calls `unstake_all()`; `inner_unstake()` reduces `total_stake_shares` and `total_staked_balance` to `0`. `internal_restake()` submits a stake(0) promise; the actual protocol-level unbonding completes over subsequent epochs, so `env::account_locked_balance()` may still be `> 0` for a few epochs and may still accrue validator rewards during that window.
3. Any unprivileged account `B` calls `ping()` in a subsequent epoch while `account_locked_balance()+account_balance()` exceeds `last_total_balance` (due to residual locked balance / accrued reward). `internal_ping()` executes with `total_stake_shares == 0`, adding `remaining_reward` and `owners_fee` to `total_staked_balance` without minting any shares.
4. `total_staked_balance > 0` and `total_stake_shares == 0` now hold simultaneously.
5. Any account attempting `stake()`/`deposit_and_stake()` reverts at `assert!(num_shares > 0, ...)` in `internal_stake()` because `num_shares_from_staked_amount_rounded_down` always returns `0` when `total_stake_shares == 0`. The pool is permanently frozen and the residual `total_staked_balance` is unrecoverable by any account.
