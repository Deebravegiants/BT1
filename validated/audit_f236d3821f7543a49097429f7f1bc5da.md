Audit Report

## Title
Unprivileged auction win against a para with a pending `AssignedSlots` temporary slot causes `allocate_temporary_slot_leases` to abort its entire batch via early-return `?`, denying other paras their scheduled temp-slot turn - (File: `polkadot/runtime/common/src/assigned_slots/mod.rs`)

## Summary
`AssignedSlots::assign_temp_parachain_slot` only checks `T::Leaser::already_leased` for the current lease period plus the next `2 * TemporarySlotLeasePeriodLength` periods, leaving further-future recurring temp-slot periods unprotected. An unprivileged account can win a `slots`-pallet auction/crowdloan lease for such a future period overlapping a para's scheduled temp-slot turn, and when `allocate_temporary_slot_leases` later processes that period, `configure_slot_lease` fails with `LeaseError::AlreadyLeased`, and the `?` on `TemporarySlots::try_mutate(...)?` inside the `for` loop propagates the error out of the whole function — aborting processing of every other pending para in that batch and skipping the `ActiveTemporarySlotCount::<T>::set(...)` update.

## Finding Description
`assign_temp_parachain_slot` bounds its `already_leased` check to the current period plus two temp-slot periods ahead: [1](#0-0) 
This leaves unguarded any later recurring turn (`last_lease + 2*period_count` cycles) or a delayed `SlotLeasePeriodStart::Next` first turn. `Auctions::handle_bid` only rejects bids overlapping an *existing* `slots::Leases` entry: [2](#0-1) 
and `bid` requires only `ensure_signed`: [1](#0-0) 
Since `AssignedSlots` calls `T::Leaser::lease_out` lazily, there is no `slots::Leases` entry for a future recurring temp-slot period until that period arrives, so nothing stops a signed account from bidding on (and winning, via `Auctions`/`Crowdloan`) that exact future range for the target para.

`allocate_temporary_slot_leases` then iterates pending paras and, per para, calls `TemporarySlots::<T>::try_mutate(...)` which internally calls `configure_slot_lease` (→ `T::Leaser::lease_out`), mapping any lease error to `Error::<T>::CannotUpgrade`: [3](#0-2) 
The `?` immediately following `try_mutate(...)` at line 560 does propagate the `Err` out of the enclosing `for` loop and out of `allocate_temporary_slot_leases` itself — confirmed by reading the function in full: the loop has no `match`/`let _ =` to swallow the error, and the `ActiveTemporarySlotCount::<T>::set(...)` line (564) is unreachable once an `Err` is returned mid-loop.

This is a real code-path finding: the code exactly matches the claim as read directly from the repository, and the loop does lack per-item error isolation.

## Impact Explanation
Confirmed impact: a single para landing in a lease-conflict state (regardless of how the conflict arose) causes `allocate_temporary_slot_leases` to return early, skipping the remainder of `slots_to_be_upgraded` for that lease-period boundary and leaving `ActiveTemporarySlotCount` un-updated for that period. This denies other unrelated pending paras their scheduled temp-slot turn for that period, a genuine batch-isolation bug in `AssignedSlots`. Because `try_mutate` does not commit on `Err`, no storage corruption occurs, and the affected para's own entry simply remains pending, matching the report's characterization of this as a DoS/error-handling issue rather than corruption.

The exploitability of the *trigger* (an unprivileged auction win against a future — but not yet current+2-period — window) is real given the documented bound of the `already_leased` check in `assign_temp_parachain_slot`, and `Auctions::bid` genuinely requires only a signed origin, no special privilege over the target `ParaId`.

## Likelihood Explanation
The precondition — winning an on-chain auction for a specific future lease-period range overlapping a `AssignedSlots` para's scheduled turn — requires reserving/spending funds via `Auctions::bid` or `Crowdloan::contribute`, and requires an active auction to exist for that period range, and requires winning against other bidders (or at least being the winning bid at auction close). This is a real cost/coordination bar but not a privilege requirement, matching the report's own "feasible, not free" framing. The scenario is reproducible each time a para re-enters "pending" status.

## Recommendation
- In `allocate_temporary_slot_leases`, avoid propagating a single para's `configure_slot_lease` failure with `?` out of the whole function; instead handle the error per iteration (e.g., log a warning and `continue`) so that a lease conflict for one para does not block processing of the remaining `slots_to_be_upgraded` entries, and compute `ActiveTemporarySlotCount` based on leases actually created.
- Consider widening `already_leased` checks in `assign_temp_parachain_slot` to cover the full recurring lifetime of a temp slot, or exclude paras holding an `AssignedSlots` entry from being eligible for `Auctions`/`Crowdloan` bidding entirely.

## Proof of Concept
1. Register two parathreads, `para_a` and `para_b`, and assign both `AssignedSlots::TemporarySlots` entries via `assign_temp_parachain_slot(Root, para, SlotLeasePeriodStart::Next)`.
2. Before the relevant lease-period boundary, have a signed non-privileged account win an `Auctions`/`Crowdloan` bid for `para_a` covering exactly the future period range that `allocate_temporary_slot_leases` will later try to configure for `para_a` (a period beyond the `current + 2*period_count` window checked at assignment time), so that `slots::Leases` for `para_a` becomes populated for that range.
3. Advance to the lease-period boundary that triggers `allocate_temporary_slot_leases` for that period.
4. Observe: `configure_slot_lease` for `para_a` fails with `LeaseError::AlreadyLeased`, `try_mutate(...)?` returns early, and `TemporarySlots::<T>::get(para_b)` remains unchanged (its scheduled turn is skipped) even though `para_b` had no conflict; `ActiveTemporarySlotCount` is also not updated for this period boundary.
