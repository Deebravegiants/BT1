### Title
Webhook shop-domain (and other metadata) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier and passes it straight into the `WebhookMetadata` handed to the app's handler, without that value ever being covered by the HMAC check.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only signs `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are entirely outside the signature: [2](#0-1) 

`Registry.process` validates the HMAC only against the body, then forwards `request.shop` (and the other unsigned fields) as the trusted tenant identity to the app-supplied handler: [3](#0-2) 

This breaks the intended binding: `shop-domain header verified by HMAC == shop attributed to the webhook payload`. In fact the HMAC verifies nothing about `shop`, `topic`, `webhook_id`, or `api_version` — it only verifies the byte-for-byte body content.

Because HMAC verification succeeds as long as the *body* bytes are unmodified, any party who can obtain one legitimately-signed webhook body+HMAC pair for the app (e.g., by installing the same public/dev app on their own store and receiving a genuine webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) header for any other shop domain. `HmacValidator.validate` will still return `true` because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The app's handler then receives `WebhookMetadata` believing the payload was authentically produced by/for the spoofed `shop`, even though neither that shop value nor the topic was ever authenticated: [5](#0-4) 

This is directly analogous to the referenced Trail of Bits report's underlying bug class — "a field acted on but not covered by the HMAC" — here the field is the tenant-identifying `shop` header rather than a refinancing amount.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party controlling their own shop/app installation can cause the host application to process arbitrary webhook bodies (that they've captured from their own legitimate installation) under a victim shop's identity. Depending on how the host app's handler uses `data.shop` (e.g., looking up the merchant record, writing data keyed by shop, triggering mandatory `shop/redact`/`customers/redact`/`customers/data_request` flows), this can result in cross-tenant data corruption or actions being performed against the wrong merchant's account — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker obtain one legitimately HMAC-signed webhook body for the target app (trivially available to anyone who installs the app on their own store, a normal unprivileged action) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint (also trivial, since these endpoints are public HTTP callback URLs). No access to `api_secret_key` or any privileged credential is required — the header tampering happens entirely on unauthenticated metadata that the gem never signs.

### Recommendation
- **Short term:** Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that tampering with any of these headers invalidates the HMAC.
- **Long term:** Treat all Shopify-supplied webhook headers as untrusted unless explicitly covered by the HMAC; document clearly to gem consumers which fields of `WebhookMetadata` are authenticated versus merely parsed from headers.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com`; trigger any registered webhook topic to receive a legitimate webhook request with body `B` and valid header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the captured request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only (see `to_signable_string`), so validation succeeds: [1](#0-0) 
4. `Registry.process` forwards `shop: "victim-shop.myshopify.com"` (read straight from the tampered header) to the app's handler as if the webhook data legitimately pertains to the victim shop: [6](#0-5)
