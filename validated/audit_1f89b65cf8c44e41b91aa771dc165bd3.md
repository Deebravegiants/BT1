### Title
Checks-Effects-Interactions violation in legacy Tron `IntentGatewayV2.withdraw` enables escrow double-spend via reentrant token callback - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-specific `IntentGatewayV2` contract retains a legacy escrow-redemption implementation in `withdraw()` that transfers tokens to the beneficiary via a low-level `.call` **before** decrementing the `_orders` escrow accounting, and its pre-transfer guard only checks that the escrow entry is non-zero rather than sufficient for the amount being released. This is the same class of bug described in the Thetanuts Finance report — a legacy vault whose redemption/claim math let an attacker manipulate escrow accounting via reentrant calls before the state was updated, draining backing supply. The parallel, hardened EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) already fixes this by decrementing escrow before transferring, confirming this Tron copy is an un-patched legacy code path.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691–714) processes each token in a `WithdrawalRequest`: [1](#0-0) 

For every token in `body.tokens` it:
1. Checks only `_orders[body.commitment][token] == 0` (existence, not sufficiency of the amount) — `revert UnknownOrder()` otherwise.
2. Immediately performs the external transfer (native `.call{value: amount}` or an ERC20 `.call` to `transfer`) — an **interaction**.
3. Only afterward does `_orders[body.commitment][token] -= amount;` — the **effect**.

This ordering is a checks-effects-interactions (CEI) violation: the escrow ledger for that token is not decremented until after the external call returns. If the token contract (or the beneficiary, for native transfers) executes attacker-controlled code during the transfer — e.g. a token with reentrant hooks — it can reenter other externally reachable gateway functions (such as `cancelOrder`/refund paths) while `_orders[body.commitment][token]` still reflects the pre-withdrawal balance, and cause the same escrowed balance to be paid out a second time before the first decrement is committed.

This directly mirrors the Thetanuts bug class: a flaw in redemption/claim accounting math (state updated after payout instead of before) that lets an attacker manipulate the underlying balance/supply to their advantage during a single delivered message.

By contrast, the current production EVM contract `IntentsBase._withdraw` already performs the decrement before the transfer: [2](#0-1) 

This confirms the Tron variant is a stale/legacy copy that was not updated with the CEI fix applied elsewhere in the codebase (the same document set also shows the once-present rounding-dust escrow bug in `IntrinsicIntents.sol` was separately patched, indicating this codebase has a documented history of escrow-accounting bugs of exactly this kind).

### Impact Explanation
`withdraw()` is reached from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` messages authenticated against a registered peer gateway) and from `onGetResponse()` (cancellation proof path) — both are triggered by a relayed cross-chain message/proof, i.e., reachable from a single relayed proof delivered by any relayer, exactly the class of entrypoint in scope. A successful reentrant double-withdrawal would permanently drain escrowed user/solver funds beyond what is backed by legitimate deposits — concrete theft/permanent loss of funds.

### Likelihood Explanation
Exploitation requires an order whose escrowed input token (or native-value beneficiary) can execute code during transfer/receipt — i.e., a malicious or non-standard token used as the order's input asset, or a malicious beneficiary contract in the native-ETH case. Because the `withdraw` internal function is only reachable through `onAccept`/`onGetResponse` (gated `onlyHost` and message-commitment-bound), a single delivered message cannot be replayed by the host itself; the attack instead needs a reentrant call from the transferred asset into a *different* externally-reachable gateway function (e.g., `cancelOrder`) that reads the same still-stale `_orders[commitment][token]` entry before it is decremented. This narrows the practical likelihood — it requires the attacker to control the input token contract and craft a race between the in-flight `withdraw` transfer and a reentrant cancel/refund call — consistent with a Medium-severity rating rather than trivial, unconditional theft.

### Recommendation
Apply the same checks-effects-interactions fix already present in `IntentsBase._withdraw`: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed`, not just `escrowed != 0`) before performing any external call/transfer, for every token processed in `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Additionally add a reentrancy guard around all externally reachable state-mutating entrypoints (`placeOrder`, `fillOrder`, `cancelOrder`, `withdraw`) as defense in depth, and replace low-level `.call` ERC20 transfers with `SafeERC20.safeTransfer` as already done in the newer `IntentsBase.sol`.

### Proof of Concept
Conceptual sequence (cannot be fully instantiated without deploying the Tron contract in a test harness, which was outside available tooling in this review):
1. User places an order on the Tron `IntentGatewayV2` escrowing `MaliciousToken` as an input, with `MaliciousToken.transfer()` overridden to call back into `IntentGatewayV2.cancelOrder()` (or an equivalent externally reachable function) for the same `commitment` before returning.
2. A solver fills/settles the order; Hyperbridge delivers the settlement message; `onAccept` invokes `withdraw()`.
3. `withdraw()` reads `_orders[commitment][MaliciousToken] != 0`, then calls `MaliciousToken.transfer(beneficiary, amount)` — before decrementing `_orders[commitment][MaliciousToken]`.
4. Inside `transfer()`, the malicious token reenters `cancelOrder()`, which reads the still-undecremented `_orders[commitment][MaliciousToken]` balance and triggers a second payout of the same escrowed amount.
5. Only after the original `transfer()` call returns does the first `withdraw()` decrement the ledger — by which point the funds have already been paid out twice, draining the gateway's actual token reserves beyond what any single legitimate escrow entry backed.

Note: this finding is based on static code review of the Tron contract; I was unable to find or execute an existing Foundry/Tron test harness in the index exercising this specific reentrancy path, so dynamic confirmation would require a background engineering session with the full repository and Tron test tooling.
