### Title
Same-asset batched withdrawals via POA Bridge are matched by `assetId` only, causing status/hash misattribution across withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status/hash of a specific withdrawal by looking up the POA bridge's `getWithdrawalStatus` response and matching it with `findMatchingWithdrawal`, which selects an entry using only `nep141:${near_token_id} === assetId`. It ignores the withdrawal's `index`, `destinationAddress`, and `amount`. When a single NEAR transaction contains more than one withdrawal of the same asset (a supported/likely scenario given `IntentsSDK.processWithdrawal`/`signAndSendWithdrawalIntent` accept `WithdrawalParams[]` batches), every `WithdrawalIdentifier` for that asset resolves to the *same* first-found API record, so the SDK reports one withdrawal's `txHash`/status for a different withdrawal's identifier.

### Finding Description
`createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) builds one `WithdrawalIdentifier` per batched `WithdrawalParams`, assigning each a per-bridge `index`. For POA Bridge, `createWithdrawalIdentifier` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:295-311) stores this `index` in the identifier, but `describeWithdrawal` (lines 313-343) never uses `index` when resolving the completion status: [1](#0-0) 

The actual matching function only compares the reconstructed asset id: [2](#0-1) 

The code comment itself acknowledges the gap ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing in `describeWithdrawal`, `watchWithdrawal` (packages/intents-sdk/src/core/withdrawal-watcher.ts:20-77), or `sdk.ts`'s `waitForWithdrawalCompletion`/`processWithdrawal` batch path (packages/intents-sdk/src/sdk.ts:783-858) prevents or detects this case — batches of `WithdrawalParams[]` with two entries of the same `assetId` (e.g., two withdrawals of the same token to two different `destinationAddress`/`amount` within one intent) are accepted and processed identically to the single-withdrawal path.

The equality that should hold is: *"the status/hash reported for withdrawal #i must be the on-chain outcome of withdrawal #i specifically (matching its destination and amount), not any withdrawal of the same token in the batch."* `findMatchingWithdrawal` breaks this by returning `Array.prototype.find`'s first match regardless of which of the N same-asset withdrawals it actually corresponds to.

### Impact Explanation
If an integrator or caller batches two (or more) withdrawals of the same token to different destination addresses/amounts in one call to `processWithdrawal`/`signAndSendWithdrawalIntent`, `watchWithdrawal` for each `WithdrawalIdentifier` will call `describeWithdrawal`, and both will resolve to the same matched API record (the first one found in `withdrawals`). This causes:
- The wrong `txHash` being reported for a given withdrawal (misreport of the on-chain outcome), which can make a caller believe funds arrived at address B when the reported hash actually corresponds to a transfer to address A.
- If a caller uses the reported hash/status to credit or reconcile withdrawals (common integrator pattern), this can cause a double credit for one destination while the second withdrawal is wrongly marked completed without its own hash ever being surfaced, or a stuck/never-observed completion for the actual second withdrawal.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category from the rules, provided the batching path is reachable by a caller (as it is exposed via `IntentsSDK.processWithdrawal`/`signAndSendWithdrawalIntent` accepting `WithdrawalParams[]`).

### Likelihood Explanation
Reaching this requires only that a caller submit two withdrawals of the same asset in one batched call — no misbehavior from the relayer, bridge operator, or RPC is required, and no chain-level attack is needed. The code path is a normal, documented feature (batch withdrawals) rather than an edge case requiring adversarial input. However, this is a self-acknowledged limitation ("not supported") rather than a silently-introduced regression, and the SDK doesn't validate/reject such batches at the API boundary, so it can be hit unintentionally by any caller.

### Recommendation
- In `PoaBridge.createWithdrawalIdentifier`/`describeWithdrawal`, disambiguate withdrawals of the same asset by additional fields returned by the POA API (e.g., `address`/destination, `amount`) in addition to `near_token_id`, or fail fast/throw a clear "unsupported: duplicate same-asset withdrawals in one batch" error at `createWithdrawalIdentifiers` time instead of silently misattributing results.
- Alternatively, validate at the SDK entry points (`processWithdrawal`, `signAndSendWithdrawalIntent`) that no two `WithdrawalParams` in the same batch share both `assetId` for a POA-routed asset, rejecting such batches until the API/matching supports proper disambiguation.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:usdt.omft.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive: false }, { assetId: "nep141:usdt.omft.near", amount: 50n, destinationAddress: "0xBBB...", feeInclusive: false } ] })`.
2. Both withdrawals route through `PoaBridge` and get identifiers with `index: 0` and `index: 1` respectively (per `createWithdrawalIdentifiers`).
3. When the POA bridge API `getWithdrawalStatus` returns both withdrawal records (order not guaranteed, per the code's own comment "Response list is unsorted"), `findMatchingWithdrawal` for *both* identifiers resolves to `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — i.e., the same first entry (say, the one to `0xAAA...`).
4. `watchWithdrawal` for the `0xBBB...` withdrawal (`index: 1`) then reports `status: "completed", txHash: <hash of the 0xAAA... transfer>` — an incorrect on-chain outcome for that specific withdrawal identifier.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
