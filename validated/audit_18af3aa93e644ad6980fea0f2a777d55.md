### Title
POA Bridge withdrawal status matched only by `assetId`, not by index/destination — status/hash misreport for batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by a `WithdrawalIdentifier` containing an `index`) by matching PoA Bridge API results **only on `assetId`**, ignoring the index/destination that actually distinguishes withdrawals inside a batch. When a caller withdraws the same asset to two different destinations in one batched intent transaction, `describeWithdrawal` for the second withdrawal can return the `status`/`txHash` that actually belongs to the first withdrawal (or vice versa), reporting an on-chain outcome that does not correspond to the withdrawal actually being queried.

### Finding Description
`createWithdrawalIdentifiers` builds one `WithdrawalIdentifier` per withdrawal param, with the ordering/uniqueness data kept only as a per-bridge-route `index`: [1](#0-0) 

`WithdrawalIdentifier` carries `index` and `withdrawalParams` (including `assetId` and `destinationAddress`), and the whole point of `index` is to disambiguate multiple withdrawals sharing a bridge/route within the same transaction: [2](#0-1) 

However, `PoaBridge.describeWithdrawal` explicitly discards ordering information and matches the API response purely by `assetId`: [3](#0-2) 

The PoA API response itself has no per-withdrawal correlation id (no index/nonce/destination echoed back that `findMatchingWithdrawal` could use to disambiguate two withdrawals of the same token): [4](#0-3) 

The same matching pattern is duplicated in `internal-utils`'s `waitForWithdrawalCompletion`, which also matches by asset-only criteria (`WithdrawalCriteria = { assetId }`): [5](#0-4) 

This is directly analogous to the `commit`/`distribute` bug class in the report: a value meant to keep records strictly ordered/paired (`toBlock` vs `lastBlockRewarded`, here `index`/destination vs `assetId`) is not actually checked/used at the point of consumption, so a caller can end up consuming (here, reporting) a record that does not correspond to the one that was actually validated/requested.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome for the specific withdrawal queried." If a batch contains two withdrawals of the same `assetId` (e.g. same token withdrawn to two different destination addresses, or the same destination twice with different amounts, in a single NEAR intent transaction), `watchWithdrawal`/`waitForWithdrawalCompletion` polling on index 1 can be satisfied by the API entry that actually belongs to index 0 (or vice versa), returning `{status:"completed", txHash: <wrong withdrawal's hash>}`. An integrator relying on this to credit/refund a specific withdrawal could mark the wrong withdrawal as completed (potential double-credit or a stuck/unresolved second withdrawal), matching the "status or hash misreport making an integrator credit or refund twice" High-impact category from the rules.

### Likelihood Explanation
Requires only an ordinary (non-privileged) user/integrator to submit a batch withdrawal containing two entries with the same `assetId` in one call — this is a normal, permitted usage pattern of `IntentsSDK` (`estimateWithdrawalFee`/`createWithdrawalIntents`/`processWithdrawal` all accept `WithdrawalParams[]`). No malicious distributor, relayer, or admin action is needed, unlike the original report's medium likelihood which required a malicious distributor.

### Recommendation
`findMatchingWithdrawal` (in `poa-bridge.ts`) and the analogous logic in `waitForWithdrawalCompletion.ts` should disambiguate using additional fields returned by the PoA API in `data` (e.g. `account_id` + `address` + `amount`/`created` ordering) or track already-consumed withdrawal entries per `intentTx.hash` so that each `index` is matched to a unique entry, never reused across withdrawals sharing the same `assetId`.

### Proof of Concept
1. Call `sdk.processWithdrawal` / `signAndSendWithdrawalIntent` with `withdrawalParams` being an array of two POA-bridge withdrawals for the same `assetId` (e.g. `nep141:btc.omft.near`) but different `destinationAddress`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` to the two withdrawals for the `poa_bridge` route. [1](#0-0) 
3. When polling withdrawal `index: 1`, `PoaBridge.describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, assetId)`, which — matching only on `assetId` — can return the API entry that is actually for withdrawal `index: 0` (e.g. because it appears first in the unsorted list and already reached `COMPLETED`), causing withdrawal `index: 1` to be incorrectly reported as `{status:"completed", txHash: <index-0's tx hash>}` while its own on-chain transfer may still be pending or different. [3](#0-2)

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

export type WithdrawalCriteria = {
	assetId: string;
};

export async function waitForWithdrawalCompletion({
	txHash,
	withdrawalCriteria,
	signal,
	baseURL,
	retryOptions = RETRY_CONFIGS.TWO_MINS_GRADUAL,
	logger,
}: {
	txHash: string;
	withdrawalCriteria: WithdrawalCriteria;
	signal: AbortSignal;
	baseURL?: string;
	retryOptions?: RetryOptions;
	logger?: ILogger;
}): Promise<WaitForWithdrawalCompletionOkType> {
	return retry(
		async () => {
			const result = await getWithdrawalStatus(
				{ withdrawal_hash: txHash },
				{ baseURL, fetchOptions: { signal }, logger },
			);

			const withdrawal = findMatchingWithdrawal(
				result.withdrawals,
				withdrawalCriteria,
			);
			if (withdrawal == null) {
				throw new PoaWithdrawalInvariantError(
					"POA Bridge didn't return withdrawal matching criteria",
					result,
					txHash,
					withdrawalCriteria,
				);
			}

			if (withdrawal.status === "COMPLETED") {
				if (withdrawal.data.transfer_tx_hash == null) {
					throw new PoaWithdrawalInvariantError(
						"POA Bridge didn't return transfer_tx_hash for COMPLETED withdrawal",
						result,
						txHash,
						withdrawalCriteria,
					);
				}

				return {
					destinationTxHash: withdrawal.data.transfer_tx_hash,
					chain: withdrawal.data.chain,
				};
