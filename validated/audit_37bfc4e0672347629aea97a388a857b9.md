### Title
Stale `operator_qr_expiration_time` cached at session start diverges from backend-updated `Config`, allowing an operator QR code to remain valid longer than intended - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::run` reads `operator_qr_expiration_time` (and several other fields) out of the shared `Arc<Mutex<Config>>` exactly once, before entering its main signup loop, and then threads that single cached `Duration` value through every iteration of the loop for the lifetime of the process. Meanwhile, a separate background task (`DefaultPlan::config_update` in `src/brokers/observer.rs`) periodically downloads a fresh `Config` from the backend and overwrites the same shared `Arc<Mutex<Config>>`. Because `MasterPlan::run` never re-reads `operator_qr_expiration_time` from the shared config after its initial snapshot, the two copies of this security-relevant value can diverge for as long as the orb runs, exactly analogous to `RubiconMarketAddress` being cached once in `BathPair` while `BathHouse` can update its own copy independently.

### Finding Description
`orb.config` is a `Arc<Mutex<Config>>` shared between the `Orb` broker (used by `MasterPlan`) and the `Observer` broker, which owns a background config-refresh task: [1](#0-0) 

This task calls `Config::download()` and swaps the entire `Config` object under the mutex on a fixed interval (`CONFIG_UPDATE_INTERVAL`), independent of what `MasterPlan` is doing: [2](#0-1) 

`MasterPlan::run`, however, destructures the config once at the top of the function, capturing `operator_qr_expiration_time` as a local `Duration`, before entering its `loop { ... }`: [3](#0-2) 

That single cached value is then passed unchanged into `scan_initial_qr_codes` and `idle_wait_for_signup_request` on every subsequent loop iteration, for the entire lifetime of the running orb process (which is not restarted between signups unless `oneshot` is set): [4](#0-3) 

The cached `operator_qr_expiration_time` is used to decide whether a previously-scanned operator QR code/session is still considered valid without re-verification, both when deciding to rescan (`scan_initial_qr_codes`) and when bounding the wait for the user QR code (`idle_scan_user_qr_code` / `idle_wait_for_signup_request`): [5](#0-4) [6](#0-5) 

By contrast, `do_signup` (called later, once per completed operator+user QR pairing) *does* re-read `operator_qr_expiration_time` fresh from `orb.config.lock().await` for use in `scan_remaining_qr_codes`: [7](#0-6) 

This inconsistency mirrors the reported bug class precisely: one code path (`BathPair`/`MasterPlan::run`'s outer loop) caches a value once from a shared source of truth that can be updated later (`BathHouse`/backend config-download task), while another code path (`do_signup`) re-reads the authoritative value each time. The result is two logically-inconsistent views of the same configuration parameter coexisting within the same signup session.

### Impact Explanation
`operator_qr_expiration_time` governs how long a scanned operator badge/QR (and its associated location/authorization data) remains acceptable without forcing a fresh operator QR scan and backend re-verification (`verify_operator_qr_code`). If the backend operator pushes a *shorter* expiration window (e.g., in response to an operator being flagged, a policy tightening, or revoking a compromised/legacy operator credential), any orb that is already in its long-running idle/signup loop will continue honoring the old, longer expiration window until the process restarts. This extends the window during which a stale or intended-to-be-revoked operator authorization can be reused to gate/legitimize signups, i.e., a signup-authorization staleness issue tied to the operator identity-binding mechanism. Because the misconfiguration is silent (no error, no log distinguishing stale vs fresh value) and can persist for the entire uptime of the orb process, it is a genuine, if narrow, authorization-window widening bug rather than a purely cosmetic one.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) the backend to actually change `operator_qr_expiration_time` while an orb is mid-session in the idle/signup loop, and (b) an operator QR code scanned before that change to still be within the old (longer) expiration window but past the new (shorter) one. Given orbs are field devices that can run continuously for extended periods without restart, and backend config changes are pushed independently on a timer, this is a realistic but edge-case scenario — similar to the judge's assessment in the original report ("non-zero possibility").

### Recommendation
In `MasterPlan::run`, avoid caching `operator_qr_expiration_time` (and the other config fields captured once before the loop: `self_serve`, `self_serve_button`, `orb_relay_shutdown_wait_for_pending_messages`, `orb_relay_shutdown_wait_for_shutdown`) for the entire loop lifetime. Instead, re-read these values from `orb.config.lock().await` at the top of each loop iteration (as `do_signup` already does), so that a backend-pushed config update takes effect for the very next idle/signup cycle rather than only after the orb process is restarted.

### Proof of Concept
1. Orb boots, `MasterPlan::run` captures `operator_qr_expiration_time = 23h` (default) from `Config` at line 334-336 of `src/plans/mod.rs`.
2. Orb enters the idle loop and an operator scans their QR code; `OperatorData.timestamp` is recorded.
3. While the orb continues idling in the same loop (no restart, no new signup completed), the backend pushes an updated `Config` with `operator_qr_expiration_time = 1h` via the `Observer`'s background `config_update` task (`src/brokers/observer.rs` lines 187-205), updating the shared `Arc<Mutex<Config>>`.
4. More than 1 hour but less than 23 hours after the operator scan, a user approaches for a signup. `idle_wait_for_signup_request`/`idle_scan_user_qr_code` still uses the stale 23h value captured in step 1 (passed down from `MasterPlan::run`), so the operator's session is treated as still valid, even though the backend's new policy says it should have expired after 1 hour.
5. The signup proceeds using operator authorization data that the backend intended to have already expired.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
