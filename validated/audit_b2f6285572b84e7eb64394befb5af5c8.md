This confirms the analog. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers via `shopify_header` [2](#0-1)  and are never included in the HMAC-signed bytes. `Registry.process` validates only the HMAC and then forwards `request.shop` directly into `WebhookMetadata` passed to the host app's handler [3](#0-2) , so the shop-tenant identity trusted by the handler is not bound to the signed content at all.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by the HMAC signature, allowing cross-tenant attribution of webhook bodies - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that are never part of the signed content. `Utils::HmacValidator.validate` only checks that the HMAC matches the raw body against `Context.api_secret_key`; it says nothing about which shop, topic, or webhook id the body belongs to.

### Finding Description
The identity binding the gem is expected to enforce is: `hmac == HMAC(api_secret_key, signed_bytes)` implies `signed_bytes` and every field derived from the request refer to the same, single webhook delivery. In this code, `signed_bytes = @raw_body` only [1](#0-0) , but `shop` [4](#0-3) , `topic` [5](#0-4) , `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers via `shopify_header` [6](#0-5) , unbound to the signature.

`Registry.process` validates the HMAC and then trusts `request.shop` and `request.topic` as-is to select the handler and build `WebhookMetadata` that is handed to the host application's business logic [3](#0-2) . Because a single app-level `api_secret_key` is shared across every shop that installs the app (it is the app's client secret, not a per-shop secret — see `HmacValidator.validate` using `Context.api_secret_key` globally [7](#0-6) ), any party capable of triggering one legitimate webhook delivery for shop A (e.g., an unprivileged merchant who installs the app on their own store and triggers an event) captures a `(raw_body, hmac)` pair that is valid under the app's single shared secret. That pair carries no binding to shop A — the header `shop-domain` is not part of the signed content. Such a party can then submit the same `raw_body` + `hmac` to the app's public webhook endpoint with `shop-domain` (and optionally `topic`/`webhook-id`) rewritten to shop B, and `HmacValidator.validate` will still return true because it only checks the raw body against the shared secret.

Before the attack: `request.shop == "shopA.myshopify.com"`, HMAC valid for that raw body. After: attacker resubmits identical `raw_body`/`hmac` with `shop-domain: shopB.myshopify.com`; HMAC validation still succeeds because the signed string never included `shop` in the first place, so `request.shop` now equals `"shopB.myshopify.com"` while the underlying signed bytes were never actually generated for shop B. The binding `hmac verified ⇒ shop field is authentic` is broken.

### Impact Explanation
Any host application that uses `WebhookMetadata.shop` (or `.topic`/`.webhook_id`) as the tenant key for processing — e.g., to look up which merchant's order/inventory/customer record to update — can be made to apply attacker-supplied webhook payload content under a different shop's identity, since the gem does not bind these fields to the signature it verifies. This is a cross-tenant data-integrity issue rooted entirely in this gem's own signing/verification design, not in host misuse of an out-of-scope feature.

### Likelihood Explanation
Exploitation requires the ability to trigger at least one legitimate webhook delivery under the shared app secret (trivially available to any unprivileged user who installs the app on a shop they control, since Shopify apps are typically installable by any merchant) and the ability to POST arbitrary bytes/headers to the app's public webhook endpoint, which by design accepts unauthenticated internet traffic. No `api_secret_key`, access token, or privileged account is required — only observation of one's own webhook traffic.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the signed/verified content, or otherwise cryptographically bind the header-derived identity fields to the HMAC check before they are trusted and forwarded to `WebhookHandler#handle`. At minimum, document that `WebhookMetadata.shop`/`.topic` must not be treated as authenticated identifiers on their own.

### Proof of Concept
1. Attacker installs the target Shopify app on `shop-a.myshopify.com` (any unprivileged merchant can do this) and triggers a webhook event (e.g., `orders/create`), capturing the resulting `raw_body` and the `x-shopify-hmac-sha256` header — both valid under the app's shared `api_secret_key`.
2. Attacker sends a new HTTP request to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a different, victim shop) and keeps or changes `x-shopify-topic`/`x-shopify-webhook-id` as desired.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the raw body only) [1](#0-0)  and succeeds, since the body/hmac pair is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-set `shop-domain` header [8](#0-7)  and passes it to the host app's `handle` method, which now processes shop-A's webhook data believing it belongs to shop B.
