## Title
Webhook HMAC does not bind `shop`, `topic`, `webhook-id`, or `api-version` headers to the signed payload, enabling cross-tenant webhook forgery — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw JSON body, so the HMAC verified by `Utils::HmacValidator.validate` covers *only* the body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from unauthenticated request headers and forwarded, unverified, into the application's webhook handler. Any actor who can legitimately obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering a webhook with attacker-influenced body content) can replay that exact body+signature to the same endpoint while substituting an arbitrary `shop-domain` and `topic` header. `Registry.process` accepts this because it only checks `Utils::HmacValidator.validate(request)` against the body, then dispatches using the unauthenticated `topic` and passes the unauthenticated `shop` straight into `WebhookMetadata`.

### Finding Description
The equality that should hold is: **the HMAC-signed bytes == the bytes the handler acts on when attributing data to a tenant/topic**. Here that equality is broken:

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from headers with no binding to the signature: [2](#0-1) 
- `Registry.process` validates only the body HMAC, then dispatches by the unauthenticated `topic` and forwards the unauthenticated `shop` into the handler payload: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the body: [4](#0-3) 

Because the signature never covers `shop`, `topic`, `webhook-id`, or `api-version`, a valid `(body, hmac)` pair generated for one shop/topic remains valid when replayed with a different `shop-domain` and/or `topic` header. Any user who can install the app on a shop they control (an unprivileged, ordinary Shopify merchant, not a privileged account and requiring no `client_secret`, access token, or leaked credential) can trigger a webhook with attacker-influenced body content, capture the resulting valid `(body, hmac)`, then POST it directly to the app's public webhook endpoint with a forged `shop-domain` header naming a victim shop and/or a forged `topic` naming a more sensitive handler. The host application's handler will process this as authentic data "from" the victim shop.

### Impact Explanation
This breaks the shop-identity binding of the webhook pipeline: the application processes attacker-supplied data while believing it originated from a specific (potentially victim) tenant, and can invoke a handler under an attacker-chosen `topic`. This is a cross-tenant data-integrity/authentication issue — data attributed to shop/topic is not actually authenticated to that shop/topic, satisfying the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Likelihood is high for any app built on this gem that trusts `WebhookMetadata#shop`/`#topic` (as the library's own documented usage pattern encourages) for tenant-scoped logic such as looking up the shop's session/access token or branching handler behavior. The only prerequisite is the attacker's own ability to install the target app on a shop they control (a normal, unprivileged capability), then capture one legitimate webhook delivery — no secrets, tokens, or privileged access are required.

### Recommendation
Bind the identity-critical headers into the signed material, or otherwise cryptographically tie `shop-domain`/`topic`/`webhook-id` to the payload before dispatch. At minimum, `Registry.process` (or the consuming application) should cross-check that the `shop` and `topic` values are consistent with values independently known/expected (e.g., via a registered webhook id-to-shop mapping, or by including these headers in the HMAC signable string per Shopify's newer verification guidance) before invoking a handler with them.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook whose body they can influence (e.g. `products/create` with attacker-controlled JSON fields).
2. Shopify delivers a legitimate webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, plus `body`.
3. Attacker resends the identical `body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <other registered topic>`.
4. `Utils::HmacValidator.validate` succeeds (it only checks the body against the HMAC) — see [5](#0-4) .
5. `Registry.process` dispatches to the handler for the forged `topic` with `WebhookMetadata.shop` set to `victim-shop.myshopify.com`, even though that shop never sent this data — see [6](#0-5) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
