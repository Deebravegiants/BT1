### Title
Malicious multi-token order can permanently freeze escrowed funds via a single reverting input token, with no recovery mechanism - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` releases every escrowed token for an order in a single, all-or-nothing loop using `IERC20.safeTransfer` with no try/catch or per-token isolation [1](#0-0) . Because a user fully controls the set of input tokens at order placement (`placeOrder`), an order can be crafted with one benign token a solver wants to acquire plus one token that is designed to permanently revert on `transfer` (e.g. a pausable/blacklistable token the order creator controls). Once the solver fills the order and delivers output on the destination chain in good faith, the cross-chain settlement message that should release the source-chain escrow to the solver calls `_withdraw`, which reverts because of the poisoned token — permanently blocking release of *all* tokens in that withdrawal, including the benign one, with no emergency/administrative bypass. This is directly analogous to the reported Alchemy issue: an attacker-chosen, always-reverting component (a plugin hook there, a token contract here) that the victim is forced to interact with can permanently brick a core, unprivileged operation (uninstall there, escrow release/refund here), and there is no override mechanism to recover.

### Finding Description
`placeOrder` lets the caller pick arbitrary ERC-20 addresses for `order.inputs` with no allow-list or validation of token behavior [2](#0-1) . These tokens are escrowed per-commitment in `_orders[commitment][token]`.

Settlement and cancellation both funnel through `IntentsBase._withdraw`, which iterates over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each token in the same loop, with a single revert aborting the whole withdrawal for every token in the request: [1](#0-0) 

`_withdraw` is invoked unconditionally by `onAccept` for both `RedeemEscrow` (pays the solver after a cross-chain fill) and `RefundEscrow` (refunds the user after cancellation), with no try/catch around it: [3](#0-2) 

When this `onAccept` call reverts, `EvmHost.dispatchIncoming` swallows the failure and simply deletes the request receipt "so it can be retried" — it does not brick the wider batch, but it also cannot force success: [4](#0-3) 

If the poisoned token's revert condition is permanent (owner-controlled pause/blacklist targeting this specific escrow contract, or a token designed from the start to always fail), every retry of the settlement message fails identically, forever. There is no per-token skip/retry logic, no admin function to force-release the remaining good tokens, and no way to separate the "good" token payout from the "poisoned" one once they're bundled into the same order/commitment.

### Impact Explanation
A solver who fills a cross-chain order delivers output tokens to the beneficiary on the destination chain *before* the settlement message reaches the source chain [5](#0-4) . If the order's source-chain inputs include one poisoned token alongside a legitimate one the solver actually wants, the solver's payment (the entire withdrawal, including the legitimate token) becomes permanently unrecoverable once `_withdraw` starts reverting — even though the solver already paid in good faith. Symmetrically, a user who cancels such an order can never recover the legitimate portion of their own refund either, since `_cancelFromDest`/`_cancelFromSource` both terminate in the same `_withdraw` call. This is a permanent freeze of funds triggered by a single unprivileged transaction (`placeOrder`), reachable without any special privilege, and there is no admin/governance override in `IntentsBase`/`ExtrinsicIntents` to force a partial release.

### Likelihood Explanation
Any user can call `placeOrder` with arbitrary token addresses; no validation of token behavior (pausability, blacklisting, deliberately-reverting logic) exists at placement time. A solver evaluating an order primarily checks that the outputs it must deliver are profitable and generally trusts that a filled order's escrow will be released via the standard flow; they are not expected to simulate every possible future state of every input token in the order (e.g., a token whose owner can pause it after the order is placed but before settlement completes). This makes the scenario realistically triggerable by an adversarial order creator targeting solvers, or, in the case of a token that later becomes non-transferable through no fault of either party (e.g. issuer-side compliance action), an ordinary chain-of-custody accident with the same catastrophic effect.

### Recommendation
Isolate per-token transfers in `_withdraw` (e.g., wrap each `safeTransfer` in a try/catch or low-level call and only revert/skip the failing token, crediting/queuing it for later retry) so that one poisoned or temporarily-failing token cannot block release of the other escrowed assets in the same order. Additionally, consider an admin/governance-gated emergency path (careful, rate-limited, and clearly logged) that can force-clear a permanently stuck escrow entry after a cooling-off period, mirroring the recommendation in the referenced report to add a deliberate, carefully-scoped override for cases where automatic recovery is impossible.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer` function reverts unconditionally (or reverts only when the recipient is a specific solver address / after the attacker calls a `pause()` function they control).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]` and a generous `order.output` that looks attractive to solvers.
3. A solver, seeing a profitable USDC/EvilToken bundle relative to the requested output, calls `fillOrder` on the destination chain, delivering the output tokens to the beneficiary. This dispatches a `RedeemEscrow` request back to the source chain [5](#0-4) .
4. On the source chain, the relayed message triggers `ExtrinsicIntents.onAccept` → `_withdraw(body, false, true)` [3](#0-2) , which reverts when it reaches the `EvilToken.transfer` call inside the loop [6](#0-5) .
5. `EvmHost.dispatchIncoming` deletes the receipt so the message "can be retried" [7](#0-6) , but every retry fails the same way since `EvilToken` never allows the transfer to succeed.
6. Both the USDC (which the solver earned) and the EvilToken remain locked in the gateway's escrow forever; the solver has no way to claim only the USDC portion, and there is no admin override to force it.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }

### Fill Flow

The solver calls `fillOrder(order, options)` on the **destination chain**. The function verifies the order hasn't expired (`order.deadline >= block.number`), confirms execution is on the correct chain, and checks the order hasn't already been filled. The solver must provide output amounts greater than or equal to the order's required amounts — any amount below the required amount reverts with `InvalidInput()`.

If the solver provides more tokens than required, the excess (surplus) is split according to `surplusShareBps`. If the order includes calldata, 100% of surplus goes to the protocol to prevent manipulation.

After delivering output tokens to the beneficiary, the contract dispatches a cross-chain `RedeemEscrow` message back to the source chain.
