## Title
`calc_take_pnl` invariant check can permanently block `Deposit`/`Withdraw`, freezing LP funds - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the pool's PnL delta by comparing the pool's current constant-product invariant against the last recorded invariant (`target.calc_pnl_x * target.calc_pnl_y`). If the current invariant is smaller than the recorded one, the function hard-fails with `AmmError::CalcPnlError` instead of gracefully handling the case. Because this function is called unconditionally inside `process_deposit` and (for non-`WithdrawOnly` pools) inside `process_withdraw`, any pool state where the current product falls below the recorded baseline permanently reverts both deposits and withdrawals, exactly mirroring the reported Solidity pattern where a strict `require` on a ratio blocks a critical fund-recovery instruction.

### Finding Description
In `calc_take_pnl`, the pool only proceeds with the PnL split if:
```
pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount
``` [1](#0-0) 
Otherwise it unconditionally returns an error: [2](#0-1) 

`calc_pc_amount`/`calc_coin_amount` are derived from `target.calc_pnl_x`/`calc_pnl_y`, which are persisted "checkpoints" of the invariant recorded at the end of every prior `Deposit`/`Withdraw`/`WithdrawPnl` call, using floor-rounded exchange calculations and `checked_sub` on normalized decimal values: [3](#0-2) [4](#0-3) 

`process_deposit` calls `calc_take_pnl` unconditionally, with no way to bypass it: [5](#0-4) 

`process_withdraw` calls it whenever the AMM status is not `WithdrawOnly` (an admin-controlled status that ordinary LPs cannot set themselves): [6](#0-5) 

If rounding losses from the floor-division exchange-rate math (`InvariantPool::exchange_pool_to_token`, `Calculator::normalize_decimal_v2`/`restore_decimal`, which all use `checked_div`/`checked_ceil_div` truncation) ever cause the recomputed pool invariant to fall marginally below the stored `calc_pnl_x * calc_pnl_y` checkpoint, every subsequent `Deposit` call reverts, and every `Withdraw` call reverts unless the pool admin proactively flips the pool into `WithdrawOnly` mode. Unlike the Solidity report's `liquidate` function, ordinary users have no path to trigger the code path that skips the failing check — they can only wait for the admin to intervene, during which their LP-represented coin/pc funds are inaccessible.

### Impact Explanation
This is a permanent, protocol-level freezing-of-funds condition: once the invariant checkpoint drifts above the live pool product (even by rounding dust), depositors can never mint new LP and existing LPs cannot redeem their share through the standard `Withdraw` path, since it always calls the failing function unless the pool is administratively placed in `WithdrawOnly` mode. This matches the High-impact "permanent freezing of LP funds" category the scan targets.

### Likelihood Explanation
Low — under honest, fee-paying swap activity the invariant should generally trend upward, so this requires an unusual accumulation of floor-rounding losses across repeated `Deposit`/`Withdraw` cycles (each of which re-baselines `calc_pnl_x`/`calc_pnl_y` using floor-rounded, truncated decimal math) to push the recorded checkpoint above the live invariant. This mirrors the "Low likelihood / High impact" classification from the reference report.

### Recommendation
Do not hard-revert the whole `Deposit`/`Withdraw`/`WithdrawPnl` instruction when `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`. Instead, treat this as "no PnL to take" (return `(0, 0)` deltas) analogous to the Solidity fix of returning a safe sentinel value instead of reverting, so that legitimate deposit/withdraw operations can still proceed even when the recorded PnL checkpoint temporarily exceeds the live pool invariant due to rounding.

### Proof of Concept
1. Track `target_orders.calc_pnl_x` / `calc_pnl_y`, which are re-baselined on every `Deposit`/`Withdraw` using floor-rounded `exchange_pool_to_token`/`normalize_decimal_v2` results [4](#0-3) .
2. Repeated deposit/withdraw cycles with amounts chosen so that floor-rounding truncates the checkpoint slightly less than it should (i.e., the stored `calc_pnl_x*calc_pnl_y` ends up marginally above the true live invariant after subsequent vault balance changes).
3. On the next `Deposit` or `Withdraw` call, `calc_take_pnl` evaluates `pool_pc_amount*pool_coin_amount < calc_pc_amount*calc_coin_amount` as true and returns `Err(AmmError::CalcPnlError)` [1](#0-0) [2](#0-1) , causing the whole transaction to fail.
4. All subsequent `Deposit` calls fail identically (no bypass path exists), and all `Withdraw` calls fail until the pool admin sets `AmmStatus::WithdrawOnly`, leaving depositors' LP-backed funds frozen in the interim.
