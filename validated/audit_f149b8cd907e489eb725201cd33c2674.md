## Title
Integer truncation of Solidity string length in Pharos BLS key decoding enables unbounded-allocation panic (DoS) in the light client — (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

## Summary
The ALPINE-CVE-2024-46953 bug class is: an integer overflow while parsing a length/format value truncates a wider computed value into a narrower field, and the truncated, attacker-influenced value is later used unchecked to size a buffer/path operation. The same pattern exists in the Pharos consensus light-client's Solidity "long string" decoder: a `U256` length is computed from an on-chain storage value and truncated with `.low_u64()` into a `usize` with no upper bound before being fed straight into `Vec::with_capacity`, which panics/aborts on the truncated value.

## Finding Description
`decode_bls_key_from_string_slot` decodes a Solidity dynamic `string` from raw EVM storage per the Solidity "long string" encoding rule (`header = length*2+1`): [1](#0-0) 

```rust
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
...
let slots_needed = (str_len + 31) / 32;
if data_slots.len() < slots_needed { ... }
let mut string_data = Vec::with_capacity(str_len);
```

`header_val` is a `U256` decoded directly from an unbounded, attacker-controlled on-chain storage value (`decode_u256_from_storage`). `.low_u64()` silently truncates any `U256` whose high bits are non-zero down to its low 64 bits — this is the same "integer overflow when parsing the format/length field results in truncation" pattern as the CVE, just for a string-length field instead of a filename-format field. The identical unguarded pattern also exists in `bls_data_slots_from_header`: [2](#0-1) 

There is no sanity bound (e.g., a `MAX_BLS_STRING_LEN` check) on `str_len`/`slots_needed` for the "long string" branch — unlike the short-string branch a few lines above it, which does bound `len` to `<= 31`: [3](#0-2) 

`str_len` can be forced arbitrarily large (up to ~`u64::MAX/2`) simply by writing a large `header_val` into the validator's `blsPublicKey` string-length slot on the Pharos staking contract. `Vec::with_capacity(str_len)` with such a value will hit Rust's "capacity overflow"/allocation-failure abort path, terminating the runtime execution that is verifying the proof.

This code sits directly on the consensus-verification path that any relayer triggers by submitting a Pharos block/epoch-boundary update: [4](#0-3) 

which calls into `verify_pharos_block` → `state_proof::verify_validator_set_proof` on every epoch boundary: [5](#0-4) 

## Impact Explanation
`verify_consensus` is the standard `ConsensusClient` entry point invoked by pallet-ismp when any relayer submits a consensus update for the Pharos state machine (e.g. via `handle_unsigned`/consensus-update extrinsics). A validator set whose `blsPublicKey` string header encodes an oversized length causes the light-client decode routine to abort the process rather than return a `Result::Err`, because the failure occurs inside an unguarded allocation rather than a checked comparison. This is a route-availability impact: the Pharos consensus client — and therefore all messages routed over the Pharos state machine — can be made permanently unable to process further epoch-boundary updates, matching the "route unable to deliver messages" impact class in the Validate section.

## Likelihood Explanation
Exploitability requires only that the Pharos staking contract's `blsPublicKey` string field for some (even low-stake) validator be written with an oversized length header — a single `SSTORE` to the string's length slot, independent of and far cheaper than actually populating the string body — and that a relayer subsequently submit the resulting epoch-boundary proof to Hyperbridge. Both `bls_data_slots_from_header` (used identically by the prover and the verifier) and `decode_bls_key_from_string_slot` share the same missing bound, so the defect is systemic to this decoding path, not a one-off.

## Recommendation
Add an explicit upper bound on the decoded long-string length before using it for allocation or slicing, e.g.:
```rust
const MAX_BLS_HEX_LEN: usize = 128; // generous bound for a 48-byte key as hex, with/without "0x"
if str_len > MAX_BLS_HEX_LEN {
    return Err(Error::InvalidBlsStringLength);
}
```
applied in both `decode_bls_key_from_string_slot` (`modules/consensus/pharos/verifier/src/state_proof.rs:243-244`) and `bls_data_slots_from_header` (`modules/consensus/pharos/verifier/src/state_proof.rs:649-651`, and its prover-side counterpart in `modules/consensus/pharos/prover/src/lib.rs:538-542`), and replace `Vec::with_capacity(str_len)` with a fallible allocation (`Vec::try_with_capacity` or use the bound above) so malformed on-chain data always yields a `Result::Err` rather than a process abort.

## Proof of Concept
1. On the Pharos staking contract, write the `blsPublicKey` string's length-header slot for a validator's pool to a value such as `U256::MAX - 1` (an odd number, satisfying the "long string" bit), without writing any of the backing data slots.
2. Wait for/trigger an epoch boundary so the validator set is included in the next `ValidatorSetProof`.
3. Any relayer submits the resulting block update via `PharosClient::verify_consensus` (`modules/ismp/clients/pharos/src/lib.rs:98`).
4. During `decode_validator_set_from_storage` → `decode_bls_key_from_string_slot`, `str_len` is computed as `((U256::MAX - 2) / 2).low_u64() as usize`, an astronomically large `usize`.
5. `Vec::with_capacity(str_len)` at `modules/consensus/pharos/verifier/src/state_proof.rs:258` triggers a capacity-overflow abort, crashing/panicking the process executing consensus verification instead of returning a decode error, halting further Pharos consensus updates.

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
