### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing tenant spoofing in multi-tenant apps - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the tenant identity (`shop`), `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identifier passed to the app's handler. This breaks the intended identity binding: "shop the HMAC proves the request came from" vs "shop the app attributes the payload to."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the raw body) against the received HMAC, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then validates the HMAC and, having done so, treats `request.shop` as authenticated, passing it straight into the tenant-scoped `WebhookMetadata` object delivered to the app's handler: [4](#0-3) [5](#0-4) 

The equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_by_app`. Because `shop-domain` is excluded from `to_signable_string`, an attacker can take *any* validly-signed webhook body (signed with the app's own `api_secret_key`, which Shopify issues per-webhook to every shop that installs the app — including the attacker's own shop) and resubmit it with a different `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. The HMAC still validates because it is computed only over the unchanged body, but the shop attribution the app relies on to route/scope the write (e.g., which merchant's data to redact, update inventory for, or mark as uninstalled) is now attacker-controlled.

### Impact Explanation
This is a cross-tenant access vulnerability: a public/multi-tenant app installed on an attacker-controlled shop can generate legitimate signed webhook traffic (any topic the attacker can trigger on their own store, e.g. `app/uninstalled`, `orders/create`, `customers/redact`), capture the raw body + valid `X-Shopify-Hmac-Sha256` header, then replay it with the `shop-domain` header rewritten to point at a victim shop. Because the gem's own webhook-processing path (`Registry.process`) does not bind `shop` into the HMAC-verified content, the forged request passes validation and the host application processes attacker-supplied data under the victim's tenant identity — satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any developer whose app is publicly installable can become an "unprivileged internet user" relative to other merchants using the same app: they only need their own (non-privileged) shop install to obtain a validly HMAC-signed webhook body, then can freely forge the `shop-domain` header on replay since it's a plain HTTP header under full attacker control and not covered by the signature. No access token, `api_secret_key`, or victim credentials are required — the attacker only needs a webhook that was legitimately sent to them.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verifiable content, or at minimum treat these headers as untrusted until independently verified (e.g., cross-check `shop` against a shop known to have valid webhook subscriptions/sessions, or include shop in a canonicalized signable string if Shopify's webhook signing ever supports header-inclusive HMAC). Document prominently that `WebhookMetadata#shop` is not covered by `hmac-sha256` and must not be used to authorize tenant-scoped writes without additional verification (e.g., confirming an active session/install record exists for that shop before trusting the payload).

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g., `customers/redact` or `orders/create`) and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it's signed with the app's real `api_secret_key`.
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks the (unmodified) body: [6](#0-5) 
5. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, and the host app processes/writes data attributed to the victim shop despite the payload originating from the attacker's own store.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
