### Title
Fee-on-transfer/deflationary token escrow over-crediting due to missing balance-verification in `placeOrder` (Tron IntentGatewayV2) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The BGLD exploit worked because the protocol trusted a *stated* transfer amount instead of measuring the *actual* balance change caused by a deflationary token. The Tron deployment of `IntentGatewayV2` has the same class of bug: in the non-predispatch escrow path, it calls `safeTransferFrom` for the full requested `order.inputs[i].amount` and then credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived from the *requested* amount minus protocol fee, never from the tokens actually received — unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before/after transfer and mutates `order.inputs[i].amount` to the real received amount.

### Finding Description
In `placeOrder`, the escrow-crediting loop for the direct-transfer path is:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:451-468
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (token == address(0)) {
        if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
        msgValue -= order.inputs[i].amount;
    } else {
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    }
    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
}
```
`reducedInputs[i].amount` is computed earlier purely from `order.inputs[i].amount * (1 - protocolFeeBps)` — it is never adjusted for a fee-on-transfer/deflationary token’s actual transfer shortfall [1](#0-0) . There is no `balanceOf` snapshot before/after the `safeTransferFrom`, so if `token` burns or redirects part of the transferred amount (as BGLD does), the gateway actually holds less than what it credits to the order’s escrow.

This is a direct behavioral regression from the reference implementation in the main EVM contract, which explicitly guards against this:
```solidity
// evm/src/apps/IntentGatewayV2.sol:319-323
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
and the Foundry test suite explicitly validates this behavior for fee-on-transfer tokens on the main contract [2](#0-1) , confirming the project is aware of and defends against this bug class elsewhere — but the Tron variant was not updated to match.

The predispatch branch of the same Tron file also suffers a related issue: it computes `dust = balance - requiredAmount` (which could underflow/misreport for deflationary tokens) and still credits `reducedInputs[i].amount` (derived from the pre-transfer stated amount) rather than the balance actually swept back to the gateway [3](#0-2) .

### Impact Explanation
Because escrow is credited with more than the gateway actually holds for that token, the internal ledger becomes over-collateralized on paper. When solvers/relayers later redeem escrow via `RedeemEscrow`/withdrawal (which decrements `_orders[commitment][token]` and transfers out the recorded amount), the first redemptions for orders using a deflationary token will succeed by draining real balance that was actually meant to back *other* orders/commitments sharing the same token, since the total credited across all commitments can exceed the true `balanceOf(this)`. This produces either theft (an attacker's order silently receives more escrow credit than tokens deposited, later withdrawn against the shared token pool) or permanent freezing of funds for unrelated legitimate order-holders, whose later withdrawal calls will revert due to insufficient contract balance. This satisfies the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with a deflationary/fee-on-transfer ERC-20 as the input token — a single transaction, no special privileges, no governance/admin required. The precondition is simply that such a token is accepted as an intent input, which the contract does not restrict (no allow-list is evident in this segment).

### Recommendation
Mirror the main EVM `IntentGatewayV2.sol` pattern in the Tron variant: snapshot `balanceOf(address(this))` (or `balanceOf(dispatcher)` for the predispatch path) before and after each transfer, and use the actual balance delta — not the requested `order.inputs[i].amount` — as the basis for `reducedInputs`/escrow crediting and for the commitment hash.

### Proof of Concept
1. Deploy/identify a deflationary ERC-20 (burns X% on every `transfer`/`transferFrom`, analogous to BGLD) and register it as an accepted input token for the Tron `IntentGatewayV2`.
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: DEFL_TOKEN, amount: 1000e18}` after approving the gateway.
3. `safeTransferFrom` moves `1000e18` requested, but due to the token's burn mechanic the gateway's real balance only increases by, e.g., `900e18`.
4. `_orders[commitment][DEFL_TOKEN] += reducedInputs[0].amount` credits ~`1000e18` (minus protocol fee) regardless of the true `900e18` received [4](#0-3) .
5. Repeat with additional orders on the same token from other users/solvers so that the sum of all `_orders[...][DEFL_TOKEN]` credits exceeds the gateway's real token balance.
6. Whichever redemption/withdrawal request is processed first successfully drains real tokens up to its recorded (inflated) escrow amount; subsequent legitimate withdrawal requests for other commitments on the same token revert due to insufficient balance, freezing those users' funds — or, if the attacker structures both the deposit and withdrawal beneficiary, they extract more tokens than they actually deposited.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
