### Title
Missing Reentrancy Guard on Tron `IntentGatewayV2.placeOrder`/`fillOrder`/`cancelOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron port of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) declares `contract IntentGatewayV2 is HyperApp, EIP712` [1](#0-0) , with no `ReentrancyGuard`/`ReentrancyGuardTransient` import or inheritance anywhere in the file, and `placeOrder` is declared `public payable` with no `nonReentrant` modifier [2](#0-1) . This mirrors the reported bug class exactly: the canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) inherits `ReentrancyGuardTransient` and guards `placeOrder`, `fillOrder`, and `cancelOrder` with `nonReentrant` [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) , but the same protection was dropped in the Tron port, just as `createPoolWithCustomStrategy` in the original Allo report was missing the guard that `createPool` had.

### Finding Description
The main EVM `IntentGatewayV2` originally suffered from a real reentrancy vulnerability (documented extensively in `IntrinsicIntentsReentrancyTest.sol`): a malicious ETH-output beneficiary could re-enter `fillOrder` during the outbound ETH transfer in `_fillSameChain`/`_fillCrossChain` and steal escrowed fees or other-token escrow before `_filled[commitment]` was set (CEI violation) [8](#0-7) . The fix applied to the primary EVM contract was twofold: (1) set `_filled[commitment]` before any external call (CEI), and (2) add `nonReentrant` (via `ReentrancyGuardTransient`) to `placeOrder`, `fillOrder`, and `cancelOrder` as defense-in-depth [6](#0-5) [7](#0-6) .

The Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol` implements the identical order-escrow/fill/cancel logic (same `placeOrder`, `predispatch`/`CallDispatcher` flow, same struct layout) but omits `ReentrancyGuard` entirely from the contract's inheritance list [1](#0-0) , and `placeOrder` carries no `nonReentrant` modifier [2](#0-1) . `placeOrder` executes external calls before finishing its bookkeeping — it calls `ICallDispatcher(dispatcher).dispatch(...)` for `predispatch` execution and for the balance-sweep transfer calls, and can call `IERC20(token).safeTransferFrom` on attacker-controlled/fee-on-transfer or malicious ERC-777-like tokens — all while only being protected by cross-tx nonce bumping, not reentrancy protection.

I was not able to fully view `fillOrder`/`cancelOrder`/`_fillSameChain`/`_fillCrossChain` bodies in the Tron file within available context to confirm the exact ETH-output loop code is byte-for-byte identical to the vulnerable EVM pre-fix version, but the grep results confirm these functions exist in the same file that lacks any `ReentrancyGuard`/`nonReentrant` construct, and the file's import list at the top confirms no reentrancy-guard import is present at all [9](#0-8) .

### Impact Explanation
If the CEI-ordering in Tron's `_fillSameChain`/`_fillCrossChain` and `placeOrder`'s external calls to `ICallDispatcher`/`IERC20` are not independently hardened the same way the EVM contract was, the total absence of the `nonReentrant` guard removes the last line of defense against reentrant escrow theft, order double-fill, or state corruption via a malicious ERC-20/beneficiary contract that reenters during a native-token transfer or `CallDispatcher` call. This directly threatens escrowed user funds routed through the Intent Gateway on Tron — a concrete theft-of-funds / permanent-freezing-of-funds class of impact, consistent with the same bug class flagged in the original Allo report (missing `nonReentrant` on a fund-moving function that its sibling function correctly guards).

### Likelihood Explanation
Medium: exploitation requires attacker control over a token behaving atypically (fee-on-transfer, hook-based, or reentrant `receive()`/fallback for native transfers) acting as either the order's output beneficiary or a token used in `predispatch`/`CallDispatcher` flows — the same preconditions that made the original EVM vulnerability exploitable prior to its fix. Because this is a deployed, unprivileged, permissionless entry point (`placeOrder`/`fillOrder`/`cancelOrder` reachable by any solver or user), the likelihood is realistic once such a token/beneficiary is used, mirroring the exact scenario the EVM tests (`IntrinsicIntentsReentrancyTest.sol`) were written to close.

### Recommendation
Bring `evm/tron/contracts/apps/IntentGatewayV2.sol` in line with `evm/src/apps/IntentGatewayV2.sol`:
1. Import and inherit a reentrancy guard (`ReentrancyGuard` or `ReentrancyGuardTransient`) in the Tron contract, matching the pattern used at `evm/src/apps/IntentGatewayV2.sol:24,60`.
2. Add `nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder` in the Tron file.
3. Independently verify/port the CEI fix (`_filled[commitment] = msg.sender` set before any external call) into the Tron `_fillSameChain`/`_fillCrossChain`/equivalent functions, since the guard alone should not be relied upon as the sole protection.

### Proof of Concept
Concrete reproduction was not completed because the Tron `fillOrder`/`_fillSameChain` function bodies were not fully retrievable within the available tool budget to confirm the exact CEI ordering of `_filled[commitment]` versus the ETH/token transfer loop. This should be verified directly against `evm/tron/contracts/apps/IntentGatewayV2.sol` (the same file already confirmed to import `SafeERC20`, `ICallDispatcher`, and to contain `fillOrder`/`cancelOrder`/`_fillSameChain`/`_fillCrossChain`/`_withdraw` per the grep match) before finalizing severity — if the CEI fix was also ported, the missing guard is still a valid defense-in-depth gap; if the CEI fix was not ported, this becomes a directly exploitable High-severity reentrancy theft identical to `testReentrancy_FeeTheft`/`testReentrancy_EscrowTheft_MultiOutput` in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`.
