## Analysis Result

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing shop-identity spoofing on genuinely-signed webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed downstream to the handler unchanged. This breaks the intended identity binding `HMAC-verified bytes == data acted upon`, because the shop identity used to dispatch/act on the webhook is not part of the verified bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `hmac` is derived purely from the `hmac-sha256`/`x-shopify-hmac-sha256` header, decoded independently of the other fields: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — for webhooks this only covers the raw body: [4](#0-3) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata passed to the app's handler: [5](#0-4) 

**The identity binding that should hold:** `shop header == data cryptographically bound to the HMAC-signed bytes`. In this implementation, that equality does not hold — the shop header is disjoint from the signed data.

**Attack sequence:**
1. An unprivileged attacker creates their own Shopify store and installs the (potentially public) app on it — no privileged credentials needed, this is the normal merchant-installation flow.
2. Shopify sends the attacker's store a legitimately HMAC-signed webhook (e.g. `orders/create`) for a body the attacker controls (their own order data), with `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over that body using the app's real `api_secret_key`.
3. The attacker replays this exact HTTP request to the app's webhook endpoint, only rewriting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to a victim shop that also has the app installed.
4. `HmacValidator.validate` recomputes the signature over `@raw_body` only — unchanged — so the signature still matches. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`.
5. The host application's handler (built against this gem's documented `WebhookMetadata#shop` contract) will act as if the payload legitimately originated from the victim shop, e.g. looking up the victim's stored session/access token and processing tenant-specific data under the wrong tenant.

Before the attack: `shop == "attacker-shop.myshopify.com"`, HMAC valid for attacker's own body.
After the attack: `shop == "victim-shop.myshopify.com"`, HMAC still valid (because it never covered `shop`) — the equality `verified-bytes == acted-upon shop` is broken.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: an app relying solely on this gem's webhook verification (as documented) will process/act on a webhook while believing it originated from a different, victim tenant, because the tenant-identifying field is unauthenticated. Depending on how the host handler uses `shop` (e.g., to select the stored access token/session for that shop and perform actions or return data), this can result in cross-tenant access to Shopify data or actions performed against the wrong merchant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (a) attacker installs the app on a store they control (any unprivileged internet user with a Shopify Partner/dev store can do this, or any merchant can install a public app), and (b) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers. No secrets, tokens, or privileged access are required — the attacker legitimately obtains a validly-signed webhook for their own tenant and merely relabels the tenant header. This is straightforward and repeatable.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind them to the verified body — e.g., have `to_signable_string` incorporate the `shop`, `topic`, and `webhook_id` header values alongside the raw body, and reject the request if the recomputed signature does not match all of them together. At minimum, document prominently (and enforce in `Registry.process`) that `shop` must be cross-checked by the host application against a known, previously-registered shop record before being trusted for any tenant-scoped action, since the header itself carries no authenticity guarantee under the current signing scheme.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = '{"id":1,"note":"attacker order"}'

# Step 1: attacker's own shop receives a legitimately-signed webhook
hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body))

attacker_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Step 2: attacker relabels the shop-domain header, replays it against the app's endpoint
forged_headers = attacker_headers.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
)

req = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HMAC validation still succeeds because only the body is signed:
puts ShopifyAPI::Utils::HmacValidator.validate(req) # => true
puts req.shop # => "victim-shop.myshopify.com"  (spoofed, unauthenticated)

# Registry.process will dispatch this to the app's handler as though it came from victim-shop
ShopifyAPI::Webhooks::Registry.process(req)
```
This demonstrates that `ShopifyAPI::Webhooks::Registry.process` and `Utils::HmacValidator.validate` accept a webhook whose `shop` (tenant identity) has been changed after signing, because `Webhooks::Request#to_signable_string` ( [1](#0-0) ) never included the shop header in the signed material.
