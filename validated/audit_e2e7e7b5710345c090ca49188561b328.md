### Title
FeeVault.claim() permanently freezes a creator's accrued USDC fees if the creator address is later blacklisted by USDC - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays the caller's pooled creator-fee balance with a hardcoded recipient of `msg.sender` and no alternate-recipient parameter. `Bonding.transferCreator` only redirects *future* fee attribution — it does not move the balance already accrued under the old creator address in `FeeVault.creatorBalance`. If a creator's address is ever added to USDC's blacklist (Circle's USDC implements `blacklist`/`isBlacklisted`, and the protocol's own docs describe the reserve/fee asset as "real USDC (6dp)"), the outbound `safeTransfer` inside `claim()` will revert for that address forever, and there is no other path to recover the balance.

### Finding Description
`FeeVault.claim()`:
```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [1](#0-0) 

There is no `claimTo(address recipient)` variant and no admin-level rescue for a stuck `creatorBalance[creator]`. The only state-zeroing write to `creatorBalance` happens inside `claim()` itself — if the `safeTransfer(msg.sender, amount)` call reverts, `creatorBalance[msg.sender]` is never zeroed and the funds stay locked and unmovable forever.

`Zap._accrueFee` is the sole depositor path that grows `creatorBalance`, splitting every buy/sell fee 0.5%/0.25% protocol/creator and calling `FeeVault.accrue`: [2](#0-1) 

Creator attribution for a token is set once at launch and can be changed going forward via `Bonding.transferCreator(tokenAddress, newCreator)`: [3](#0-2) 
(test coverage confirming `transferCreator` only updates `tokenInfo.creator` for future attribution) [4](#0-3) 

Critically, `transferCreator` never touches `FeeVault.creatorBalance` — it only changes `Bonding.tokenInfo(token).creator`, which affects the recipient of fees on *future* trades passed into `FeeVault.accrue(token, creator, ...)` by `Zap`. Any USDC balance that has already accrued under the old creator address in `FeeVault.creatorBalance[oldCreator]` is unreachable by the new creator and remains keyed to the (now-blacklisted) old address. The blacklisted address is also the only one permitted to call `claim()` for its own balance (`amount = $.creatorBalance[msg.sender]`), so calling `transferCreator` after the fact does not rescue the already-earned fees.

This is a direct analog of the reported bug class: a `transfer` of the fee/reserve asset to a party that a stablecoin issuer has blacklisted reverts unconditionally, and the affected funds have no alternate withdrawal path — exactly the "don't transfer directly, let the user withdraw on his own" pattern flagged in the source report, except here the withdrawal path itself is the one hardcoded to the now-unusable address with no substitute.

### Impact Explanation
Any creator whose wallet is later placed on USDC's blacklist (a real, on-chain, permissionless-to-trigger-by-issuer event independent of the protocol) permanently loses access to all currently-accrued and any future-misdirected creator fees held in `FeeVault`. This is a permanent freeze of creator funds inside a core protocol contract with no owner-level sweep, no `claimTo`, and no cross-account rescue mechanism — satisfying the "permanent freezing of trader, creator, or LP funds" acceptance bar. Given `FeeVault.claim()` is explicitly one of the analog-eligible unprivileged-reachable functions, and creator fees can be nontrivial over a token's life, this is Medium severity, consistent with the source report's rating for the equivalent DoS-on-transfer bug class.

### Likelihood Explanation
Likelihood depends on an external precondition (USDC blacklisting an address), which is out of the protocol's direct control but is a documented, real capability of the USDC token the protocol integrates with (`docs/contracts-scope.md` explicitly assumes "real USDC (6dp)" as the fee asset). No malicious action by another party is needed to trigger it — normal USDC compliance/blacklist actions (sanctions, regulatory requests, etc.) are sufficient, and once triggered there is no on-chain workaround within the current contracts.

### Recommendation
Add a rescue path that decouples the destination address from the accrual key, e.g.:
- Add `claimTo(address recipient)` (or an admin-callable `rescueCreatorBalance(address creator, address recipient)` gated to the creator's own signature/ownership proof) so a blacklisted creator, or the protocol on their behalf, can redirect the stuck balance to a fresh, non-blacklisted address.
- Alternatively, let `Bonding.transferCreator` also migrate any outstanding `FeeVault.creatorBalance[oldCreator]` to the new creator address, so creators can pre-emptively move their claimable balance before or after their address is sanctioned.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`, and multiple buy/sell trades accrue creator fees into `FeeVault.creatorBalance[C]` via `Zap._accrueFee` → `FeeVault.accrue`.
2. USDC's issuer blacklists address `C` (external event, no protocol interaction required).
3. `C` (or anyone helping `C`) calls `FeeVault.claim()`. `amount = creatorBalance[C]` is read and `creatorBalance[C]` is zeroed, then `$.usdc.safeTransfer(C, amount)` is attempted — this reverts because `C` is blacklisted by USDC, so the whole transaction reverts and `creatorBalance[C]` state change (which would have zeroed it) is rolled back — the balance remains stuck at its full amount, un-claimable through any call path since `claim()` always targets `msg.sender`.
4. `C` calls `Bonding.transferCreator(token, D)` to reassign future fee attribution to a fresh address `D`. This has no effect on the already-accrued `creatorBalance[C]` in `FeeVault` — `D`'s calls to `claim()` only pay out `creatorBalance[D]`, which is `0` for any fees earned before the transfer. The pre-transfer balance under `C` remains permanently frozen in `FeeVault`.
