The gateway's CORS `isAllowedOrigin` implementation reproduces the same flawed wildcard-matching pattern as CVE-2016-9952: it strips the `*.` prefix and then does a raw suffix check without verifying a `.` boundary exists between the stripped label and the wildcard root, exactly like the Windows CE Schannel bug stripped the `*` and did an unanchored suffix comparison.

### Title
CORS wildcard origin matching in gateway HTTP server accepts non-subdomain hosts sharing a suffix - (File: core/services/gateway/network/httpserver.go)

### Summary
`httpServer.isAllowedOrigin` implements wildcard CORS origin matching for the internet-facing Gateway HTTP server by stripping the `*.` prefix from a configured allowlist entry and then testing whether the attacker-supplied `Origin` header host has that stripped string as a suffix via `strings.HasSuffix`, with no check that a `.` separator actually precedes the match.

### Finding Description
In `isAllowedOrigin`, for a configured wildcard entry such as `*.example.com`, the code does: [1](#0-0) 
`allowedHost` becomes `example.com` after stripping `*.`, and the check becomes `strings.HasSuffix(originHost, "example.com")`. This is a purely lexical suffix check with no requirement that the preceding character in `originHost` be a `.`. As a result, an attacker-controlled `Origin` header such as `https://evilexample.com` or `https://notexample.com` satisfies the suffix check and is treated as a legitimate subdomain of `example.com`, even though it is an entirely different, attacker-registrable domain. This is the same root-cause pattern as CURL-CVE-2016-9952: a wildcard indicator is stripped and the remaining string is matched against the untrusted value using an unanchored suffix/substring test instead of validating the label boundary (RFC 6125-style matching requires the match to occur at a `.`-delimited label boundary).

The `Origin` header is fully attacker-controlled and is processed unauthenticated in `handleRequest`, which is reachable by any unprivileged actor sending requests to the Gateway's public HTTP endpoint: [2](#0-1) 

### Impact Explanation
If `isAllowedOrigin` returns true for an origin that was never intended to be trusted, the server sets `Access-Control-Allow-Origin` to that attacker's origin, allowing a page hosted on the attacker-registered domain (e.g. `evilexample.com`) to make cross-origin browser requests to the Gateway and read the JSON-RPC responses via `fetch`/`XHR`. Since the Gateway's `handleRequest` forwards the raw request body to `ProcessRequest` and returns the raw response, any response content that should only be readable by browsers on the intended `*.example.com` subdomains becomes readable by a completely unrelated attacker-controlled origin, which is a cross-origin allowlist bypass / cross-user response confusion condition.

### Likelihood Explanation
This requires the Gateway operator to enable CORS with at least one wildcard entry (`CORSEnabled = true` and a `CORSAllowedOrigins` value starting with `*.`), which is a documented, supported configuration pattern for the Gateway's browser-facing use case (per `core/scripts/gateway/sample_config.toml`). No authentication or special privilege is required by the attacker — only registering a domain that lexically ends with the allowlisted suffix and getting a victim's browser to visit it while making a request to the Gateway.

### Recommendation
Change the wildcard match to enforce a label boundary, e.g. require `originHost == allowedHost` or `strings.HasSuffix(originHost, "."+allowedHost)` after stripping the `*.` prefix, so that `evilexample.com` cannot match `*.example.com` while `sub.example.com` still can.

### Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. From a browser page hosted at `https://evilexample.com` (an attacker-registered domain with no relation to `example.com`), issue a `fetch("https://<gateway-host>/<path>", {method: "POST", body: ...})`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilexample.com", "example.com")` is true, per [1](#0-0) , and the response includes `Access-Control-Allow-Origin: https://evilexample.com`, letting the attacker page read the JSON-RPC response body.
