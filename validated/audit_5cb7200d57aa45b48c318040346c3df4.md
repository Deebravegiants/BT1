### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) purely from HTTP headers, but the HMAC signature that `Registry.process` validates is computed only over the raw request body. This breaks the binding: `hmac_verifies(raw_body)` ≠ `hmac_verifies(shop_header)`. An attacker who can deliver an HTTP request to the app's public webhook endpoint (with a body+HMAC pair captured from any legitimately-signed webhook, e.g. one addressed to their own shop) can freely rewrite the `X-Shopify-Shop-Domain` header to any victim shop, and the request will still pass validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of request headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`, i.e., the raw body: [3](#0-2) 

`Registry.process` uses this same HMAC check and then dispatches the handler using `request.shop` (the unauthenticated header value) as the shop identity for the webhook payload: [4](#0-3) 

Because the signature never covers `shop-domain`, `topic`, or `webhook-id`, any request whose body+HMAC pair was legitimately generated by Shopify for *some* shop can be replayed to the app's endpoint with a forged `X-Shopify-Shop-Domain` (or `x-shopify-topic`/`x-shopify-webhook-id`) header, and `Utils::HmacValidator.validate(request)` will still return `true`. This is the same class of bug as the referenced Seaport issue: data that a downstream consumer relies on for identity/routing decisions (consideration items / recipients) is not actually constrained by the verification step that is supposed to guarantee its integrity (the aggregation check / the HMAC).

### Impact Explanation
This breaks the shop-tenant identity binding for webhook processing. A merchant who has an app installed (and can therefore trigger/capture at least one legitimate webhook body+HMAC pair for their own shop) can replay that exact body with a spoofed `shop-domain` header for a victim shop. Any app logic in `WebhookHandler#handle` that trusts `WebhookMetadata#shop` (built directly from `request.shop`) to select which merchant's data/session to update, e.g. writing to the app's per-shop datastore, revoking data, or triggering shop-scoped side effects, will operate under the wrong shop identity. This is a cross-tenant confusion vector reachable by any party able to POST to the app's public webhook endpoint with a captured, legitimately-signed payload.

### Likelihood Explanation
The webhook endpoint is by design a public HTTP endpoint that must accept unauthenticated inbound POSTs (there is no IP allowlisting or mTLS enforced by this gem). Obtaining one valid raw-body/HMAC pair only requires having a shop where the app is installed (or observing any topic that includes attacker-influenced content, e.g. `products/update` for a product they control) and re-sending it with a different `shop-domain` header. No access to `api_secret_key` or any Shopify credential is required — only knowledge of one previously delivered payload.

### Recommendation
Include the shop domain (and ideally topic and webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop`/`topic`/`webhook_id` values to the signed body before trusting them in `Registry.process` / `WebhookMetadata`. At minimum, document that consumers of `WebhookMetadata#shop` must independently verify the shop against a known, previously-established session/install record rather than trusting it as authenticated solely because `HmacValidator.validate` returned true.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; capture a real webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC(secret, B)`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same body `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers uncritically [5](#0-4) , and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B` [6](#0-5) .
4. `handler.handle` is invoked with `shop: "victim.myshopify.com"` even though the payload actually originated from and pertains to `attacker.myshopify.com` [7](#0-6) , demonstrating the identity confusion.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
