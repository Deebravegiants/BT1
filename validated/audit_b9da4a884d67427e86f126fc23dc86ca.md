### Title
Webhook `shop-domain` header is trusted for tenant identification despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `ShopifyAPI::Webhooks::Request#shop` is read from an unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the app's handler as the tenant identifier, so the field an app uses to decide *which merchant* a webhook belongs to is never bound by the cryptographic check that gates processing.

### Finding Description
`Registry.process` gates webhook processing on HMAC validity and then forwards `request.shop` unchanged to the handler: [1](#0-0) 

The HMAC is computed only over the raw body: [2](#0-1) 

But `shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signed data: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` only compares `verifiable_query.hmac` against an HMAC computed from `to_signable_string` (the body), so it never touches the shop header: [5](#0-4) 

The identity binding that should hold is: `shop that the HMAC proves the payload originated from == shop the app treats the webhook as belonging to`. Because the shop header is unsigned, that equality does not hold. Since a single app's `api_secret_key` is shared across every shop that installs it (this is a multi-tenant secret, not a per-shop one), a genuine, validly-HMAC'd webhook body received for one tenant (e.g., a shop that a malicious actor legitimately installed the app on) remains valid if replayed with the `shop-domain` header rewritten to point at a different, victim tenant. `Registry.process` will still pass HMAC validation (the body and secret haven't changed) and will call the handler with `WebhookMetadata` claiming the victim's `shop`: [6](#0-5) 

This mirrors the report's bug class directly: a field that is *acted on* (the shop used to select/attribute tenant data) is not covered by the binding check (the HMAC) that is otherwise trusted as the authenticity gate.

### Impact Explanation
Any host application that follows this gem's documented pattern — validate via `Registry.process`, then trust `WebhookMetadata#shop` (or `request.shop`) to select or attribute the tenant record to update — is exposed to cross-tenant data confusion/injection. An attacker who is himself a legitimate (if malicious) installer of the app can capture a webhook delivery for his own store and resend it with a forged shop header naming a different merchant, causing the app to apply that webhook's data (e.g., order/customer/product change) against the wrong tenant's records. This falls under the "cross-tenant access" impact category, since it lets one tenant inject or overwrite data attributed to another tenant without ever needing the app's `client_secret`, an access token, or any privileged credential — only the ability to install the app on any shop and observe/replay its own legitimate webhook traffic.

### Likelihood Explanation
Likelihood is contained but real: it requires (a) the app to be multi-tenant (same `client_secret` used to sign webhooks for every installing shop — true by design for all public/embedded Shopify apps), and (b) the host application to rely on `request.shop`/`WebhookMetadata#shop` for tenant scoping without independently re-verifying the shop against the session/store the app already has on record for that installation — which is exactly the pattern this gem's own `Registry.process` API encourages, since it hands back an unauthenticated `shop` value as part of the "verified" webhook metadata. Any attacker able to install the app themselves (a low bar for public apps) can mount this without ever needing `api_secret_key`, an access token, or social engineering.

### Recommendation
- Document prominently (and ideally enforce in `Registry.process`) that `request.shop` is not authenticated by the HMAC and must not be used as the sole tenant identifier; alternatively, cross-check `request.shop` against the shop recorded for the resource identified in the payload before acting on it.
- Consider including the shop domain in the value that is HMAC-validated (e.g., verifying it separately against the session/store already on file for the referenced resource ID) rather than trusting the header on its own.
- At minimum, surface a warning/require callers to pass an expected shop to `Registry.process` so mismatches are rejected by the library itself rather than left to each app implementation.

### Proof of Concept
1. Install the target multi-tenant Shopify app on attacker-controlled Shop A (legitimately, `client_secret` is shared with all installers, no secret exfiltration needed).
2. Trigger a real webhook event on Shop A (e.g., `orders/create`) and capture the raw request: body, and the `x-shopify-hmac-sha256` header Shopify computed over that body.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with Shop B's domain (the victim).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks the body against the HMAC — validation succeeds because neither the secret nor the body changed: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop` set to Shop B, despite the payload actually originating from Shop A, and any app logic keyed off `data.shop` acts on the wrong tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
