## Analysis

The nfsd bug (CVE-2024-46696) is a classic **use-after-drop**: the code releases a reference (drops the delegation) and *then* touches fields embedded in the object, which are no longer guaranteed valid. The reachable analog in this codebase is a **fund-accounting fee read that happens after an untrusted external call, on state that is never invalidated in the success path** — `EvmHost.dispatchIncoming(GetResponse)`.

### Root cause [1](#0-0) 

```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({relayer: relayer, responseCommitment: response.hash()});

    (bool success,) = _bytesToAddress(response.request.from)
        .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

    if (!success) {
        delete _responseReceipts[commitment];
        return;
    }

    // reward the relayer fee
    uint256 fee = _requestCommitments[commitment].fee;   // <-- read AFTER the external call
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
```

`response.request.from` is an application address chosen by whoever originally dispatched the GET request — i.e. attacker-controlled code that Hyperbridge will call into with a low-level `.call`. Compare this to the sibling function `dispatchTimeOut`, which explicitly `delete`s `_requestCommitments[commitment]` **before** invoking the (equally untrusted) app callback: [2](#0-1) 

In `dispatchIncoming(GetResponse)` there is no such invalidation: `_requestCommitments[commitment]` (and its `.fee`) is never cleared on the success path. Combined with the fact that neither `EvmHost.sol` nor `HandlerV2.sol` has any `nonReentrant`/`ReentrancyGuard` protection (confirmed by search — no matches for `nonReentrant`/`ReentrancyGuard` in `evm/src/core/*.sol`), and that `HandlerV2.handleGetResponses` is explicitly documented as callable by anyone: [3](#0-2) 

a malicious `response.request.from` contract can, from inside `onGetResponse`, re-enter `HandlerV2.handleGetResponses` with the *same* proof/message. Because the fee metadata at `_requestCommitments[commitment]` was never deleted, the reentrant call re-verifies the same MMR leaf (nothing on the handler/host side prevents replay of the exact same response commitment inside the same call stack) and pays the relayer fee a second time via `IERC20(feeToken()).safeTransfer(relayer, fee)`. When the outer call resumes, it reads the still-non-zero `fee` and pays it out *again*. This is the same bug class as the kernel CVE: a value that should have been invalidated once "consumed" is instead read/used again after the point where invalidation should have occurred, permitting reentrant reuse of resource state — here draining the host's fee-token balance.

## Title
Stale fee metadata read after untrusted `onGetResponse` callback enables relayer-fee draining via reentrancy — (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse)` performs a low-level `.call` into an attacker-influenced application (`response.request.from`) and only afterwards reads `_requestCommitments[commitment].fee` to pay the relayer. Unlike `dispatchTimeOut`, which deletes the commitment metadata *before* calling the untrusted app, this path never invalidates `_requestCommitments[commitment]`, and neither `EvmHost` nor `HandlerV2` implements reentrancy protection.

### Finding Description
The GET-response delivery path violates checks-effects-interactions: state that gates a token payout (`_requestCommitments[commitment].fee`) is read and consumed for a `safeTransfer` *after* an external call to attacker-influenced code, and is never cleared on the success branch. This mirrors the nfsd UAF pattern of "touch the field after the point where it should already have been released/invalidated." [4](#0-3) 

### Impact Explanation
A relayer fee (in `feeToken()`) can be paid out multiple times for a single GET response delivery, directly draining ERC-20 balance held by `EvmHost` — concrete theft of protocol/relayer funds, reachable from a single permissionless `handleGetResponses` submission.

### Likelihood Explanation
`handleGetResponses` is permissionless [3](#0-2) , and any application can be the target of a GET request's `from` address, giving an attacker full control over the reentrant callback. No `nonReentrant` guard exists anywhere in `evm/src/core/EvmHost.sol` or `HandlerV2.sol` (verified via search), so exploitation only requires deploying a malicious `IApp` and dispatching a GET request from it.

### Recommendation
Delete/zero `_requestCommitments[commitment]` (or otherwise mark the fee as consumed) **before** the external call to `onGetResponse`, mirroring the pattern already used in `dispatchTimeOut`, and/or add reentrancy guards to `EvmHost`'s external-call-bearing dispatch functions.

### Proof of Concept
1. Attacker deploys a malicious `IApp` contract and dispatches a `GetRequest` with `from = maliciousApp`.
2. Once Hyperbridge produces a valid `GetResponseMessage`/MMR proof, attacker calls `HandlerV2.handleGetResponses(host, message)`.
3. `EvmHost.dispatchIncoming(GetResponse)` calls `maliciousApp.onGetResponse(...)`.
4. Inside `onGetResponse`, the malicious app re-enters `HandlerV2.handleGetResponses(host, message)` with the same message/proof; since `_requestCommitments[commitment]` was never cleared, verification succeeds again and `dispatchIncoming` pays the relayer fee a second time.
5. Execution returns to the outer call, which pays the (still non-zero) fee a third time.

**Note on confidence:** I was unable to view lines beyond 239 of `HandlerV2.sol`'s `handleGetResponses` (tool budget exhausted), so I could not independently confirm whether an additional duplicate/response-receipt check exists later in that function that might reduce (but not eliminate, given the reentrancy window occurs *before* any such check would run again) the practical exploitability. The core root cause — reading and spending `_requestCommitments[commitment].fee` after an untrusted external call without invalidating it — is confirmed directly in `EvmHost.sol`.
