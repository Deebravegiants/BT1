### Title
Webhook shop/topic identity spoofing via header fields excluded from HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the HMAC over the raw JSON body matches (`Utils::HmacValidator.validate(request)`), then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers to build the `WebhookMetadata` object dispatched to the app's handler. Because the HMAC signable string is defined as `@raw_body` alone, none of these header-derived identity fields are cryptographically bound to the signature.

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)`, i.e., the shop/topic that the app acts on must be the same shop/topic that Shopify actually signed. Instead the gem implements: `hmac == HMAC(secret, body)` only.

- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` [4](#0-3) .
- For webhooks, `to_signable_string` returns `@raw_body`, excluding all headers [1](#0-0) .
- `shop`, `topic`, `webhook_id`, and `api_version` are read from `x-shopify-*` headers with no cryptographic tie to the body [2](#0-1) .
- `Registry.process` validates the HMAC, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and calls `handler.handle(data: ...)` — the app-supplied handler is documented to key its data-processing/session-lookup off `data.shop` and `data.topic` [3](#0-2) , exactly as shown in the gem's own webhook usage documentation (`data.shop`, `data.topic` used to route work) [5](#0-4) .

Because any merchant can install a public app and thus legitimately receive Shopify-signed webhooks for their own store (with a valid HMAC computed by Shopify using the app's shared `api_secret_key`, not a per-shop secret), an attacker who is merely one of the app's own installed merchants can capture a legitimately-signed webhook body+HMAC pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` and/or `x-shopify-topic` headers rewritten to name a different, victim tenant of the same app. `HmacValidator.validate` still succeeds because it only re-derives the signature from the unmodified body. `Registry.process` then dispatches `WebhookMetadata` carrying the attacker-chosen `shop`/`topic` values as if Shopify had actually sent that webhook for that shop.

### Impact Explanation
This breaks the tenant-identity binding the whole webhook-processing flow is supposed to guarantee: "the shop the HMAC authenticates" versus "the shop the handler acts on" are different fields, and only the former is protected. Any app whose webhook handler uses `data.shop` (the gem's own documented pattern) to select which merchant's session/access token to load or which tenant's data to mutate can be tricked into performing actions attributed to, or scoped to, an arbitrary victim shop that also uses the app — a cross-tenant confusion condition triggered entirely from the unprivileged position of "any merchant who installed the same public app."

### Likelihood Explanation
Exploitation requires no secrets beyond what any installed merchant already legitimately receives (a valid webhook to their own store), and only a header rewrite before replay to the public webhook callback URL, which is a straightforward, config-independent HTTP request. The precondition — a host handler trusting `data.shop`/`data.topic` for downstream authorization — matches the exact usage pattern demonstrated in the gem's own documentation.

### Recommendation
Bind the shop/topic identity into the signed material verified by `HmacValidator`, e.g., include the `shop-domain` and `topic` header values in `Webhooks::Request#to_signable_string` (or otherwise cross-check them against a value derived from the body/registration), so any tampering with these headers invalidates the HMAC check performed in `Utils::HmacValidator.validate`.

### Proof of Concept
1. App merchant A installs the public app; app registers webhook `orders/create` for shop A.
2. Shopify sends a legitimately HMAC-signed webhook to the app for shop A: headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, body `B`, `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker (merchant A) captures this request and resends it to the same webhook endpoint, only changing `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim tenant of the same app), keeping body `B` and the same HMAC header.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — still valid, since headers are excluded from `to_signable_string` [1](#0-0) .
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: "orders/create", body: B, ...)` and invokes the app's handler as if Shopify had sent this event for shop B [3](#0-2) .
