### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only binds the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw HTTP body, but the `shop` value that is passed to the app's handler as the tenant identity is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) using `Context.api_secret_key`: [2](#0-1) 

Meanwhile `Request#shop` is read directly from the `shopify-shop-domain` header without any cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC and then constructs `WebhookMetadata` using `request.shop`, which is handed to the app's registered handler as the source of tenant identity: [4](#0-3) 

The intended identity binding should be:
`hmac_valid(secret, raw_body) == true` implies `(raw_body, shop) is authentic for that shop`.

What is actually proven is only:
`hmac_valid(secret, raw_body) == true` implies `raw_body was produced by an entity holding api_secret_key` (i.e., Shopify, for *some* installation of this app).

Because `api_secret_key` is a single shared secret for one app across all of its installs (shops), and `shop` is carried in a header outside the signed bytes, any unprivileged internet user who has their own store with the same app installed can:
1. Trigger a legitimate webhook (e.g., `orders/create`) to be sent from Shopify to the app's webhook endpoint, capturing the exact raw body and its valid `shopify-hmac-sha256` value.
2. Replay that exact raw body and HMAC to the app's webhook endpoint, but with the `shopify-shop-domain` header (and any other header field, none of which are signed) rewritten to point at a victim shop that also has the app installed.

`Utils::HmacValidator.validate` will report the request as valid (the body and HMAC are an untouched, genuine pair), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` together with body content that is actually the attacker's own store data. Any host application that uses `WebhookMetadata#shop` to select which merchant's tenant record to update (a documented, expected usage pattern of this gem) will write/associate attacker-controlled data under the victim's tenant, i.e., cross-tenant data injection using only the standard webhook processing entry point of this gem.

### Impact Explanation
This breaks the identity binding between the authenticated bytes (raw body signed by the shared `api_secret_key`) and the tenant identity used by the rest of the pipeline (the `shop` header). It enables cross-tenant data confusion/injection through the gem's own `Registry.process` public API, which matches the in-scope "Critical - cross-tenant access" impact category, since the app never receives proof that the specific body belongs to the specific shop named in the header.

### Likelihood Explanation
High for any attacker who is themselves an unprivileged merchant able to install the target app on their own store (a normal, unprivileged action for any public/embedded Shopify app) and can trigger any webhook event under their own store (e.g., placing an order, updating a product). No access token, `api_secret_key`, or TLS interception is required — only the ability to receive one legitimate webhook for their own shop and then send a crafted HTTP POST to the app's public webhook endpoint with an altered `shopify-shop-domain` header.

### Recommendation
- Do not rely on `shopify-shop-domain` alone as the tenant identity for handler dispatch. Bind the tenant to a value that is either covered by the HMAC or independently corroborated, for example: verify the `shop` domain against a store of shops that are actually installed for this app and whose HMAC secret was actually used, or require the webhook body's own top-level shop identifier (if present in payload/topic-specific fields) to match the header before trusting it.
- Where feasible, additionally validate that the webhook was expected for this specific shop (e.g., cross-check against a per-shop webhook registration record maintained by the host app) before invoking the handler, rather than trusting the header value directly from `Webhooks::Request#shop`.
- Document explicitly in `lib/shopify_api/webhooks/registry.rb` / `request.rb` that `shop` is unauthenticated and must not be used as the sole tenant-selection key by consuming applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker performs an action that triggers a webhook subscribed by the app (e.g., `orders/create`), and captures the raw POST body and the `shopify-hmac-sha256` header sent by Shopify to the app's webhook endpoint.
3. Attacker resends the identical raw body and `shopify-hmac-sha256` value to the same webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (a store also using the app) instead of their own domain.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers the untouched raw body (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own order data>, ...)` and, if the host application uses `shop` to select the victim's tenant record, writes attacker-controlled data into the victim's tenant context — a cross-tenant injection achieved purely through this gem's public webhook-processing API.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
