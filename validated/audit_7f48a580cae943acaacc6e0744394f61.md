Audit Report

## Title
Zone-B vault-read restriction can be bypassed via stale DON-membership cache during a capabilities-registry lookup failure - ([File: core/capabilities/vault/zone_b_restriction.go])

## Summary
`zoneBRestrictor.isZoneBWorkflowDON` caches the last successfully-resolved zone-b membership per `WorkflowDonID` and returns that cached value, without any re-validation or TTL, whenever a live `DONByID` lookup to the capabilities registry fails. If a DON is reclassified into the restricted `zone-b` family while a registry lookup failure occurs before a fresh successful resolution, `enforce()` uses the stale non-zone-b decision and skips the `ownerAllowed` allowlist check, letting a non-allowlisted workflow owner read vault secrets.

## Finding Description
`enforce()` gates `vault.GetSecrets` by calling `isZoneBWorkflowDON`, and only checks the `ownerAllowed` gate when the caller resolves to `zone-b`: [1](#0-0) . Membership resolution is documented as authoritative and never based on caller-supplied metadata: [2](#0-1) . However, `isZoneBWorkflowDON` falls back to `zoneCache[workflowDonID]` — the last successfully-resolved value — on any `DONByID` error, and that cache entry is only overwritten on the *next successful* lookup, never invalidated on a registry-side family change: [3](#0-2) .

The underlying `capabilitiesRegistry.DONByID` implementation confirms the documented transient-failure mode (`"metadataRegistry information not available"` when the metadata registry is `nil`, e.g. mid-sync): [4](#0-3) , and DON `Families` are recomputed only when a fresh full sync completes: [5](#0-4) . So there is a genuine window — between a DON's family changing in a completed sync and the previous cache entry being overwritten by a subsequent successful `DONByID` call for that specific DON — during which a fresh lookup failure would return the stale, pre-reclassification cached membership.

The existing unit tests only assert the "safe" direction (cached zone-a stays allowed, cached zone-b stays denied across an outage) and explicitly do not cover a reclassification occurring concurrently with an outage: [6](#0-5) , confirming this exact gap is untested and unhandled by the implementation.

## Impact Explanation
If the race is hit, a workflow owner who is not on the `VaultZoneBGetSecretsAllowed` allowlist can read vault secrets from a DON that has just been moved into the restricted `zone-b` family — an authorization/allowlist bypass leading to secret disclosure, which is a legitimate in-scope impact category (allowlist bypass / key-secret exfiltration).

## Likelihood Explanation
Exploitation is not attacker-triggerable on demand: it requires (1) an operator/registry-side reclassification of a DON's `Families` to include `zone-b`, coinciding with (2) a `DONByID` lookup failure for that specific DON occurring after the reclassification but before that DON's next successful resolution repopulates the cache. Both preconditions are outside the requesting workflow owner's control and depend on registry sync timing/outages rather than anything an unprivileged client can directly cause. This significantly limits practical likelihood, but the root cause is real: the cache has no TTL, no invalidation hook tied to registry updates, and fails open (uses the old, less-restrictive verdict) rather than failing closed toward the safer decision.

## Recommendation
- Add a TTL to `zoneCache` entries, and/or fail closed by treating an unresolved/expired entry as `zone-b` (the more restrictive outcome) during an outage instead of trusting an indefinitely-stale cached value.
- Invalidate/refresh the per-DON cache entry proactively when the registry sync detects a family-membership change for that DON, rather than relying solely on the next successful `DONByID` call triggered by traffic.
- Add a regression test: resolve a DON as zone-a, change its registry family to zone-b, force a `DONByID` failure, and assert the subsequent `enforce()` call denies the non-allowlisted owner rather than allowing them through the stale zone-a cache entry.

## Proof of Concept
1. In a test using `fakeMetadataRegistry` (as in `zone_b_restriction_test.go`), register DON `D` in family `zone-a` and call `z.enforce(ctx, D)` for owner `O` to warm `zoneCache[D]=false`.
2. Mutate the fake registry so `D`'s `Families` now returns `["zone-b"]`.
3. Force the fake `DONByID` to return an error for `D` (simulating the documented `"metadataRegistry information not available"` condition).
4. Call `z.enforce(ctx, D)` again for non-allowlisted owner `O`; assert it returns `nil` (bypass) instead of the expected `"allowlisted workflow owners"` error, demonstrating the stale-cache bypass described in `isZoneBWorkflowDON` at `core/capabilities/vault/zone_b_restriction.go:100-122`.

```go
func (z *zoneBRestrictor) isZoneBWorkflowDON(ctx context.Context, workflowDonID uint32) (bool, error) {
	don, err := z.capabilitiesRegistry.DONByID(ctx, workflowDonID)
	if err != nil {
		// The registry view can be transiently unavailable (e.g. not yet synced
		// after startup, or nil mid-update: DONByID returns "metadataRegistry
		// information not available"). That error is not specific to zone-b
		// callers, so failing closed here would block every vault GetSecrets read
		// DON-wide. Fall back to the last successfully-resolved membership for this
		// DON; only a never-before-resolved DON fails closed.
		if cached, ok := z.cachedZoneMembership(workflowDonID); ok {
			z.lggr.Warnw("capabilities registry lookup failed; using cached zone-b membership",
				"workflowDonID", workflowDonID, "isZoneB", cached, "err", err)
			return cached, nil
		}
		return false, fmt.Errorf("could not resolve caller workflow DON %d for zone-b vault read restriction: %w", workflowDonID, err)
	}
	// Case-insensitive match: family casing may vary across registry sources.
	isZoneB := slices.ContainsFunc(don.Families, func(family string) bool {
		return strings.EqualFold(family, zoneBFamily)
	})
	z.storeZoneMembership(workflowDonID, isZoneB)
	return isZoneB, nil
}
```

```go
// MUST-2: a transient capabilities registry outage must not fail every vault
// read DON-wide. Once a DON's zone membership has been resolved, a subsequent
// registry lookup failure falls back to the cached value instead of erroring;
// a DON never resolved before still fails closed. Crucially, the cached value
// preserves the security decision in both directions: a cached zone-b DON stays
// denied during the outage rather than slipping through.
func TestZoneBRestrictor_RegistryOutageUsesCachedMembership(t *testing.T) {
	t.Parallel()
	const restrictEnabled = `{"global":{"VaultZoneBWorkflowGetSecretsRestrictEnabled":"true"}}`

	t.Run("cached zone-a membership survives outage (still allowed)", func(t *testing.T) {
		t.Parallel()
		z, fake := newOutageTestRestrictor(t, restrictEnabled)
		md := capabilities.RequestMetadata{WorkflowOwner: "0xdeadbeef", WorkflowDonID: zoneADonID}
		ctx := md.ContextWithCRE(t.Context())

		// Warm the cache while healthy: zone-a caller is allowed.
		require.NoError(t, z.enforce(ctx, zoneADonID))
		// Outage: cached (non-zone-b) membership keeps the read allowed.
		fake.fail.Store(true)
		require.NoError(t, z.enforce(ctx, zoneADonID))
	})

	t.Run("cached zone-b membership survives outage (still denied)", func(t *testing.T) {
		t.Parallel()
		z, fake := newOutageTestRestrictor(t, restrictEnabled)
		md := capabilities.RequestMetadata{WorkflowOwner: "0x" + allowlistedOwner, WorkflowDonID: zoneBDonID}
		ctx := md.ContextWithCRE(t.Context())

		// Warm the cache while healthy: zone-b + non-allowlisted owner is denied,
		// and the zone-b membership is cached.
		require.ErrorContains(t, z.enforce(ctx, zoneBDonID), "allowlisted workflow owners")

		// Outage: the cached zone-b membership must still be enforced. The caller
		// is denied via the allowlist, not allowed through by a resolve failure.
		fake.fail.Store(true)
		err := z.enforce(ctx, zoneBDonID)
		require.ErrorContains(t, err, "allowlisted workflow owners")
		require.NotContains(t, err.Error(), "could not resolve caller workflow DON")
	})
```
