### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`/`webhook_id`) values from unauthenticated HTTP headers, while `to_signable_string` — the data actually verified by `Utils::HmacValidator.validate` — only covers the raw request body [1](#0-0) . This breaks the identity binding `HMAC-authenticated-content == shop attributed to the webhook`.

### Finding Description
`Registry.process` gates webhook handling solely on `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the host app's handler [2](#0-1) . `HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` [3](#0-2) , and for `Webhooks::Request` that string is only `@raw_body` — the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers are excluded from the signed material [4](#0-3) .

By contrast, the gem's own OAuth `AuthQuery#to_signable_string` explicitly folds `shop` into the signed query string precisely so the shop identity is bound to the HMAC [5](#0-4) . The webhook path lacks this same binding: a valid HMAC only proves the body bytes came from Shopify with knowledge of the app secret — it proves nothing about which shop the headers claim to be from.

Because Shopify computes the webhook HMAC only over the raw body (not headers), any recipient of a legitimately-signed webhook (e.g., the app's own developer/test shop, or any shop that installed the app and can trigger a webhook with attacker-controlled/predictable body content) can replay that exact `raw_body`+`hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different, victim shop. `Utils::HmacValidator.validate` will still return `true` since it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` [6](#0-5) .

### Impact Explanation
Apps built on this gem are documented to key their session/tenant lookups and side effects off `WebhookMetadata#shop` [6](#0-5) . Since the gem itself never authenticates that field, any host app that trusts it (as the gem's own API implies is safe once `HmacValidator.validate` passes) is exposed to cross-tenant webhook spoofing — e.g., an attacker forging an `app/uninstalled` or `shop/redact` event attributed to a victim shop, or injecting data keyed to a victim's shop record, using only a webhook payload the attacker can legitimately obtain signed for their own shop.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of any one validly-signed webhook (trivially obtainable by installing the app on an attacker-controlled development shop) plus the ability to freely set the `X-Shopify-Shop-Domain` header on the forged request, which is standard for any HTTP client — no privileged credentials, access token, or `client_secret` are needed.

### Recommendation
Bind the shop (and topic/webhook-id) identity to the HMAC in `Webhooks::Request#to_signable_string`, or otherwise have `Utils::HmacValidator`/`Registry.process` cross-check that any identity fields consumed by handlers are themselves covered by the verified signature — mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimately Shopify-signed webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), `X-Shopify-Topic: T`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only hashes `B` [4](#0-3) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the host app to act on/for the victim tenant based on attacker-supplied data.
