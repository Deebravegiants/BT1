## Title
Non-standard ERC20 `transfer()` return value not checked in `CallDispatcher`, allowing unbacked escrow credits in Tron `IntentGatewayV2.placeOrder` predispatch sweep - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` sweeps predispatch-converted tokens from the shared `CallDispatcher` back into the gateway using a raw, ABI-encoded `IERC20.transfer` call routed through `CallDispatcher.dispatch()`. `CallDispatcher` only checks that the low-level `.call()` did not revert — it never inspects the ERC20 return data. The gateway then credits its internal escrow ledger (`_orders[commitment][token]`) unconditionally, *before* verifying that the tokens actually arrived. Non-standard ERC20/TRC20 tokens that signal failure by returning `false` instead of reverting will cause the sweep to silently no-op while the gateway still books the full escrow amount.

### Finding Description
In the predispatch branch of `placeOrder`, tokens are first pulled from the caller into the `CallDispatcher` via `safeTransferFrom` (safe), then the predispatch calldata is executed, and finally the resulting balance is swept from the dispatcher back to the gateway: [1](#0-0) 

Note that `_orders[commitment][token] += reducedInputs[i].amount;` is executed inside the same loop that *builds* the sweep `Call`, before `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` is even invoked, and there is no post-dispatch verification that the gateway's balance actually increased by that amount.

The sweep call itself is a raw ABI-encoded `transfer` forwarded through `CallDispatcher`: [2](#0-1) 

`dispatch()` only reverts if `to.call(...)` itself fails (i.e., reverts); it does not decode/check the boolean returned by `IERC20.transfer`. A non-standard ERC20/TRC20 that returns `false` on failure instead of reverting will make `dispatch()` return successfully even though zero tokens moved from the dispatcher to the gateway.

By contrast, the mainline EVM `IntentGatewayV2.sol` version of the same predispatch sweep correctly protects against this by snapshotting balances before the sweep and computing `received` from the actual post-sweep balance delta, updating `order.inputs[i].amount` (and therefore the escrow credit) from real, measured balances rather than trusting the call's success flag: [3](#0-2) 

The Tron contract omits this balance-delta verification entirely for the predispatch sweep path, reintroducing exactly the "non-standard ERC20 transfer safety" class of bug described in the external report (an unchecked `transfer`/`transferFrom` that can silently fail while the caller proceeds as if it succeeded).

### Impact Explanation
If a listed input token behaves non-standardly (returns `false` on failed `transfer` rather than reverting), a predispatch order can cause:
- The real (post-conversion) tokens to remain stranded in the shared `CallDispatcher` rather than moving into the `IntentGatewayV2` contract.
- The gateway's escrow accounting (`_orders[commitment][token]`) to be credited with tokens it does not hold, meaning any subsequent `fillOrder`/`withdraw`/`cancelOrder` flow attempting to pay out that "escrowed" amount from the gateway's real balance will draw down on unrelated orders' tokens (insolvency / cross-order fund mixing) or revert and freeze the order permanently.
- The stranded balance sitting in the shared `CallDispatcher` can later be misattributed as "dust" during a subsequent, unrelated `placeOrder` predispatch sweep for the same token (`balance = IERC20(token).balanceOf(dispatcher)` picks up the leftover balance), letting an unrelated order silently absorb another user's stuck funds.

This is a fund-freezing / accounting-insolvency vector reachable by any user submitting a `placeOrder` with a predispatch call for a non-standard input token, directly matching the "concrete theft or permanent freezing of funds" / "unsound state commitment" bar.

### Likelihood Explanation
Exploitability depends on the input token's ERC20 compliance. Many real tokens (including some TRC20 deployments on Tron, which is the target chain for this contract) implement `transfer`/`transferFrom` to return `false` on failure rather than reverting; the protocol's own predispatch flow is a permissionless, per-transaction feature (any user can submit a predispatch call), so no privileged actor is required — an ordinary `placeOrder` call with such a token as an input triggers the flaw.

### Recommendation
Mirror the mainline EVM fix in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before calling `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, and credit `_orders[commitment][token]` only with the actually observed balance delta after the dispatch call returns, rather than the pre-computed `reducedInputs[i].amount`. Additionally, harden `CallDispatcher.dispatch()` (or a dedicated ERC20-transfer path) to use `SafeERC20`-style return-data validation for `transfer`/`transferFrom` calls so silent `false`-returning failures revert instead of being treated as success.

### Proof of Concept
1. Deploy a TRC20/ERC20 token whose `transfer(address,uint256)` returns `false` (instead of reverting) when, e.g., the recipient is paused/blacklisted or another internal condition fails, while still returning `true`/success under normal `transferFrom`.
2. Configure that token as an order input with a predispatch call (e.g., a no-op or trivial swap) so it ends up held by the shared `CallDispatcher` after predispatch execution, with `balanceOf(dispatcher) >= requiredAmount`.
3. Arrange (via the token's implementation) for the specific `transfer(gateway, balance)` call issued by `CallDispatcher` to return `false` without reverting (e.g., a per-recipient rule that always fails for the gateway address under some condition the attacker controls).
4. Call `placeOrder`. `CallDispatcher.dispatch()` succeeds because the low-level `.call` didn't revert; `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, but `IntentGatewayV2`'s real token balance is unchanged (tokens remain in `CallDispatcher`).
5. Any later `fillOrder`/`withdraw`/`cancelOrder` referencing that escrow either reverts (freezing the order) or, once other orders replenish the gateway's balance of that token, pays out from funds that belong to unrelated depositors — demonstrating the accounting break.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
