### Title
Unauthenticated `origin` parameter allows any caller to self-declare trust and auto-approve status in `ConnectedOrigins` - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins.add`, `setAutoApprove`, `setFavorite`, `connect`, and `disconnect` accept an `origin` string as a plain argument and mutate the persisted connection record for that origin without ever verifying that the caller invoking the API actually is that origin. This mirrors the `LendingLedger` finding: state-mutating functions (`checkpoint_market`/`checkpoint_lender`) that trust caller-supplied identifiers/values instead of deriving them from a validated, privileged context.

### Finding Description
`ConnectedOrigins#add` writes a record keyed purely by the `origin` field taken from the call arguments, including `trusted` and (indirectly, via later `setAutoApprove`) `autoApprove`: [1](#0-0) 

`setAutoApprove` and `setFavorite` similarly key off the caller-supplied `origin` with no cross-check against who is actually calling: [2](#0-1) 

`connect`/`disconnect` also mutate `activeConnections` for an arbitrary `origin` argument: [3](#0-2) 

These methods are exposed verbatim on the public SDK API surface with no additional origin-binding/authorization wrapper: [4](#0-3) 

The module itself is registered as `public: true`, meaning it is intended to be reachable by the SDK's external API/RPC boundary (the same boundary the browser-extension/web3-provider RPC transport exposes to whatever process holds an RPC/port connection): [5](#0-4) 

`isTrusted` and `getConnectedAccounts` (which returns address books for every enabled wallet account) trust the same unauthenticated `origin` value for their access-control decision: [6](#0-5) [7](#0-6) 

I could not locate, within the indexed portion of the codebase, any wrapper in the browser-extension RPC transport (`libraries/browser-extension-rpc`) that intercepts calls to `connectedOrigins.add`/`setAutoApprove`/`connect` and forces `origin` to match `sender.tab.url` before forwarding to this module — the transport code I found only propagates `senderMetadata` (title/icon) for UI display, not for authorization: [8](#0-7) 

Because this repo indexes JS/TS packages only (no exhaustive index of every background-script call site), it's possible a caller (e.g. the dApp connection/approval flow in the extension background) enforces this binding outside what I could retrieve; if such enforcement exists, it should be treated as the actual mitigating control and this finding would need to be validated against that call site directly rather than the module in isolation.

### Impact Explanation
If any code path exposes these methods to a party who does not control the browser/tab origin verification (e.g., a compromised or malicious content-script-adjacent process, or any RPC client with access to the exposed SDK surface), it can:
- Mark an arbitrary `origin` string as `trusted: true`, which downstream (`isTrusted`) directly gates whether `getConnectedAccounts` discloses the full address book (`accounts[activeWalletAccount].addresses`, `accounts[name].addresses`) for every enabled wallet account of every connected asset.
- Set `autoApprove: true` for an arbitrary origin, which — per the analogous dApp-connection UX — is used elsewhere to skip user confirmation prompts, i.e. a privilege-escalation primitive similar to zeroing out the reward-accounting checkpoint in the original report: the "trust decision" state is corrupted by an unprivileged write instead of a validated user action.
- Forge `connect`/`disconnect` entries in `activeConnections`, corrupting the wallet's record of which origins are actively connected.

This is a direct analog of the H-07 root cause: a state-mutating function accepts an attacker-controlled identifier (there: `_market`/`_forwardTimestampLimit`; here: `origin`) and mutates trust/accounting state keyed on that identifier without validating that the caller is authorized to act on behalf of that identifier.

### Likelihood Explanation
Exploitability depends entirely on whether the RPC/transport layer that fronts this "public" module enforces `origin === sender-verified-origin` before invoking `connectedOrigins.add`/`setAutoApprove`/`connect`. I was not able to confirm such enforcement exists in the indexed code for `libraries/browser-extension-rpc` or `libraries/sdk-rpc`. If enforcement is missing or can be bypassed (e.g., a caller invoking the SDK API directly rather than through the dApp-approval UI flow), the likelihood is high given the API is marked `public: true` and requires no additional capability beyond calling an exposed method.

### Recommendation
- Never accept `origin` as a plain, attacker-suppliable argument for trust-establishing operations. Derive it exclusively from the verified sender context (e.g., `sender.tab.url` origin) at the RPC/transport boundary, and strip/ignore any `origin` field supplied in the request body for these specific methods.
- Add an explicit authorization check inside `ConnectedOrigins.add`/`setAutoApprove`/`connect`/`disconnect` (or a wrapper enforcing it before these are reached) so that state for `origin` can only be mutated by a call that is bound to that verified origin.
- Require that `trusted: true` and `autoApprove: true` can only be set through the dedicated user-approval UI flow, never accepted as a raw boolean passed through the public API.

### Proof of Concept
Given the exposed API surface, any caller able to invoke the public SDK methods can perform:
```js
// attacker-controlled origin string, no verification against actual caller
await exodus.connectedOrigins.add({
  origin: 'https://trusted-dapp.example',
  name: 'Trusted Dapp',
  connectedAssetName: 'ethereum',
  trusted: true,
})

await exodus.connectedOrigins.setAutoApprove({
  origin: 'https://trusted-dapp.example',
  value: true,
})

// now isTrusted/getConnectedAccounts treat this forged origin as trusted
await exodus.connectedOrigins.getConnectedAccounts({ origin: 'https://trusted-dapp.example' })
```
This corresponds to the test flows already present in the repo showing the module accepts and acts on `origin` and `trusted`/`autoApprove` purely from call arguments: [9](#0-8) 

**Caveat:** I could not fully verify, with the tools available, whether the extension's background RPC handler binds/overwrites `origin` from the verified sender before calling into this module. If it does so consistently for every one of `add`, `setAutoApprove`, `setFavorite`, `connect`, and `disconnect`, the practical exploitability is mitigated at that layer and this would reduce to a defense-in-depth gap rather than a directly exploitable bug. A full-repository session (beyond the indexed subset available here) would be needed to trace all background-script call sites and confirm or rule this out conclusively.

```javascript
  connect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnection = { id, createdAt: Date.now() }
    const newConnections = uniqBy([...activeConnections, newConnection], 'id')

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }

  disconnect = async ({ id, origin }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const activeConnections = value.activeConnections || []
    const newConnections = activeConnections.filter((connection) => connection.id !== id)

    await this.#setAttributes({ origin, attributes: { activeConnections: newConnections } })
  }
```

```javascript
  /**
   * Returns the connected accounts for a given origin with the active wallet account sorted first. Can be used while
   * the wallet is locked
   */
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```

```javascript
export const createRPCProxy = ({ extensionName, channelName }) => {
  if (typeof extensionName !== 'string' || typeof channelName !== 'string') {
    throw new TypeError(`Unable to create RPC because channelName or extensionName are missing`)
  }

  const channel = channels[channelName]
  const transport = createWindowRpcTransport({
    name: `${extensionName}-${channelName}`,
    target: `${extensionName}-${channelName}-window`,
  })

  transport.on('data', async (event) => {
    const isResponse = !JSON.parse(event).method
    const senderMetadata = await metadata
    const options = { senderMetadata }

    if (isResponse) {
      channel.sendMessage(event, options)
    } else {
      channel.call(event, options).then(transport.write)
    }
  })

  channel.onMessage((message, sender) => {
    if (sender.tab) return
    transport.write(message)
  })
}
```
