The webhook `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers that `Registry.process` and the app's handler actually act on.This confirms the full path: `Registry.process` validates only `HmacValidator.validate(request)` at [1](#0-0) , then trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the HMAC — to build `WebhookMetadata` passed to the app's handler.

### Title
Webhook HMAC signature does not cover `shop-domain`, `topic`, or `webhook-id` headers, allowing cross-tenant webhook spoofing via signature replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop-domain`, `topic`, and `webhook-id` headers taken from the same request to decide which handler to invoke and what shop/topic/webhook_id metadata to hand to the app. The HMAC binds only the body bytes, not the header fields the app actually acts on — mirroring the reported bug class where a value used in a decision (`afterDeposit`) was computed from data not properly bound to the check that authorizes it.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, that method is defined as: [3](#0-2) 

Notice `to_signable_string` returns `@raw_body` only — none of `shop`, `topic`, `webhook_id`, or `api_version`, which are all parsed straight from headers with no cryptographic binding: [4](#0-3) 

`Registry.process` then uses these unauthenticated header values to select the handler and construct the metadata delivered to the app: [1](#0-0) 

This breaks the intended binding: `HMAC(secret, raw_body) == received_hmac` should imply `(shop, topic, webhook_id, body)` together are authentic, but the equality actually only proves `body == body_that_was_signed`. The `shop-domain` header can be swapped for any other string while keeping the same body and HMAC, and validation still passes because `hmac == HMAC(secret, raw_body)` does not depend on `shop-domain` at all.

### Impact Explanation
An unprivileged internet user who operates their own Shopify store using the vulnerable app receives genuine webhooks from Shopify for their own shop, each with a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. That attacker can replay the exact same HTTP request to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain or a mandatory topic like `customers/redact`/`shop/redact`. Because those headers are outside the signed bytes, `HmacValidator.validate` still returns `true`, and `Registry.process` forwards attacker-controlled `shop`/`topic`/`webhook_id` values, together with the attacker's own body content, to the app's handler as if they came from the victim shop. Depending on how the host app uses `data.shop` (e.g., to select which merchant's DB records to write/update/delete via `perform_later(shop_domain: data.shop, ...)` as shown in the gem's own webhook doc example), this enables cross-tenant data injection/corruption — writing attacker-controlled webhook content under a victim shop's identity.

### Likelihood Explanation
Requires no privileged access, tokens, or leaked secrets: any user who installs the app on their own store (or otherwise obtains one valid webhook body+HMAC pair for that app) can capture and replay it to the app's public HTTP webhook endpoint with modified headers, since header modification requires no cryptographic knowledge.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (in addition to the raw body) in the signed/verified material — e.g., verify the HMAC against the raw body only (per Shopify's protocol, unavoidable), but additionally require and check that `request.shop` corresponds to a shop with an active session/installation known to the app, and treat webhook headers as untrusted unless corroborated by data already inside the HMAC-signed body or by an independently authenticated session. At minimum, document and enforce that callers of `Registry.process` must cross-check `request.shop` against their own installation records before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = Base64(HMAC-SHA256(api_secret_key, B))`.
2. Attacker resends this exact request to the app's public webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or changes `X-Shopify-Topic` to a mandatory topic such as `customers/redact`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — this still equals `H` because the body `B` was not modified. [5](#0-4) 
4. Validation passes; `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the victim shop never sent this webhook.
