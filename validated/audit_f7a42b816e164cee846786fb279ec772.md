## Finding

### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is *not* covered by that signature — to identify which merchant/tenant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never mixed into the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies exactly that signable string against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` then dispatches to the app's handler using the *unauthenticated* `request.shop` value as the tenant identity, without any additional check that the signed body actually originated for that shop: [4](#0-3) 

The identity binding that should hold is:
`shop value the HMAC was computed for == shop value the handler is told acted`

But the HMAC only binds `body`, not `shop`. Since a single app's `client_secret` (`api_secret_key`) is shared across every merchant that installs the app, any unprivileged user can install the target app on their own store, receive a genuine, validly-signed webhook (e.g. `orders/create`) for their own shop, then replay the identical body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. The HMAC check still passes (it never looked at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim's shop domain.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: the gem hands the host application data that is cryptographically authenticated as coming from the app but *not* authenticated as belonging to the shop domain claimed. If the host app uses `WebhookMetadata#shop` (as the documented API contract implies, and as exercised in `Registry` and its tests) to select which merchant's session/data the webhook body should be applied to, an attacker-controlled shop can inject application/order/customer events attributed to an arbitrary other tenant, i.e. cross-tenant access.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) installer of the target app — no leaked credentials, no `client_secret`, and no privileged account are needed, satisfying the "unprivileged internet user" bar. Forging the header on a replayed request is trivial (any HTTP client), and the HMAC remains valid because it never covers the header in the first place.

### Recommendation
Include the shop domain (and topic/webhook id) in the signable/verified material for webhooks, or require callers of `Registry.process`/`Request` to independently verify `request.shop` against a known/installed-shop allowlist before trusting it, and document this requirement prominently since it is not enforced by the gem today.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Attacker triggers an event (e.g. creates an order) and captures the resulting webhook POST, including the valid `x-shopify-hmac-sha256` header and raw body.
3. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks the body against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host app to act as if the event came from the victim shop.
