Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no domain restriction [1](#0-0) , and the OAuth request body carries the app's `client_secret` in plaintext [2](#0-1) .

### Title
Token Exchange sends the app's `client_secret` to an unsanitized host taken from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the destination host for the token-exchange HTTP request directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. Two structurally identical flows in the same file (`ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`) both call `Utils::ShopValidator.sanitize!(shop)` to restrict the destination host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before building the request. `exchange_token` omits this check, breaking the intended binding "host that receives `client_secret` == a Shopify-trusted domain."

### Finding Description
`exchange_token` decodes the caller-supplied session token and takes the shop directly from the decoded `dest` claim: [3](#0-2) . `JwtPayload#shop` simply strips `"https://"` from `dest` with no further domain restriction [4](#0-3) . That value is used unsanitized to build `shop_session`, which is fed straight into `HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, whose constructor sets `@base_uri = "https://#{api_host || session.shop}"` verbatim [1](#0-0) . The subsequent POST to `#{base_uri}/access_token` carries `client_id` and `client_secret` in the JSON body [5](#0-4) .

By contrast, the gem's own `ShopValidator` module exists specifically to restrict any shop-derived host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [6](#0-5) , and it is applied before constructing the request session in the sibling flows `ClientCredentials.client_credentials` [7](#0-6)  and `TokenExchange.migrate_to_expiring_token` [8](#0-7) . `exchange_token` is the outlier that skips this control entirely, even though it is the only one of the three that derives the host from data embedded in an untrusted-input-shaped claim (`dest`) rather than from a caller-supplied literal.

The `JwtPayload` class only verifies the signature and the `aud` claim [9](#0-8) ; it never validates that `dest`/`iss` resolve to a trusted Shopify-owned domain. Session tokens are issued for multiple contexts beyond admin embedded apps — the same class explicitly supports checkout UI extension tokens, distinguished only by `iss` ending in `/checkouts` rather than `/admin` (see `admin_session_token?`) [10](#0-9) , and `dest` for such non-admin contexts is not constrained to be a `*.myshopify.com` host. Because `exchange_token` accepts any session token whose signature validates and never checks `admin_session_token?` or restricts `dest`'s domain, a `dest` value tied to a merchant-controlled/custom checkout domain is sufficient to redirect the outbound request — carrying the app's `client_id`/`client_secret` — to a host outside Shopify's trusted domain set.

### Impact Explanation
This breaks the "host validated versus host that receives the `client_secret`" binding called out as a High-severity class: the equality that should hold is `host(session.shop) ∈ TRUSTED_SHOPIFY_DOMAINS`, enforced everywhere else in this file via `ShopValidator.sanitize!`, but not in `exchange_token`. The result is SSRF carrying the app's `client_secret` to a non-Shopify host, which the rules explicitly list as High impact ("SSRF with the app's credentials ... or credential leakage into logs or error output").

### Likelihood Explanation
Exploitation requires only a validly-signed session token (signed by Shopify using the shared `api_secret_key`, not the attacker) whose `dest` claim resolves to a domain outside `TRUSTED_SHOPIFY_DOMAINS` — this is plausible for non-admin session-token contexts (e.g., checkout/custom-domain contexts) that this same `JwtPayload` class explicitly supports, and does not require possession of the app's `client_secret`, an access token, or any privileged account by the caller of this library's public `exchange_token` API.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `client_credentials` and `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, and/or restrict `exchange_token` to admin session tokens (`jwt_payload.iss` ending in `/admin`) before trusting `dest` as a request host.

### Proof of Concept
1. Obtain (or have App Bridge/Shopify issue) a validly-signed session token whose `dest` claim is a non-`*.myshopify.com` host that the caller controls (e.g., a checkout-context or custom domain claim), signed with the app's shared secret as usual.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: attacker_dest_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `exchange_token` sets `dest_shop = jwt_payload.shop` (no `ShopValidator.sanitize!` call) and builds `HttpClient.new(session: Session.new(shop: dest_shop), base_path: "/admin/oauth")`, then POSTs `{client_id, client_secret, grant_type, subject_token, ...}` to `https://#{dest_shop}/admin/oauth/access_token` — sending the app's `client_secret` to the attacker-influenced host, unlike `client_credentials`/`migrate_to_expiring_token` which reject non-trusted domains with `Errors::InvalidShopError`.
