## Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` (and `topic`/`webhook-id`) values used to route and attribute the webhook to a specific merchant are taken from HTTP headers that are never included in the signed payload. Any actor who can obtain one genuinely-signed webhook (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header for a victim shop's domain, and `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and dispatch it to the app's handler as if it originated from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from HTTP headers, which are attacker-controllable in a crafted request and are not part of the signed material: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (i.e., only the body) against the app's shared `api_secret_key`: [4](#0-3) 

This breaks the intended identity binding `hmac == HMAC(secret, body ∧ shop)`. In reality the gem only enforces `hmac == HMAC(secret, body)`, so `shop` is a free variable that the caller can set to any value without invalidating the signature — structurally the same class of bug as the reported issue, where a value that is acted upon (there: `ve`; here: `shop`) is not bound to the value that was actually verified/authorized (there: `_voteEscrow` param; here: the HMAC-covered content).

Because Shopify apps share a single `api_secret_key` across all shops that install the app, a genuine (even low-privilege) merchant who installs the app on their own store receives real webhook deliveries whose HMAC is valid under the app's shared secret — not a shop-specific secret. That merchant can capture the raw body and its accompanying `x-shopify-hmac-sha256` header from a webhook delivered for their own store, then re-POST the identical body/HMAC to the app's webhook endpoint while changing only the `x-shopify-shop-domain` header to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because it never examines the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop as the source.

### Impact Explanation
This is a cross-tenant identity confusion: the application's webhook handler makes trust and persistence decisions (e.g., "update shop X's record", "mark shop X's order paid", "store data under shop X's tenant") keyed on `request.shop`/`WebhookMetadata#shop`, which is fully attacker-controlled and unauthenticated by the HMAC check. An attacker with only the ability to install the app on their own shop (the normal, unprivileged path any Shopify user can take) can inject arbitrary-but-genuinely-signed webhook payloads under any other merchant's identity, leading to cross-tenant data corruption or disclosure — satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is high for any app that (a) installs on multiple shops sharing one `api_secret_key` (true for essentially all public/multi-tenant Shopify apps using this gem) and (b) trusts `WebhookMetadata#shop` for tenant attribution without independently cross-checking it against a known-installed shop list bound to the specific webhook subscription. The only precondition is that the attacker can install the app once on a shop they control — no leaked secrets, tokens, or social engineering are required.

### Recommendation
Bind the shop identity into the verified material, e.g., include the `x-shopify-shop-domain` (and `x-shopify-webhook-id`/topic) header values in the HMAC-signable string, or independently verify that `request.shop` matches an app-known, previously-authenticated shop for the specific webhook subscription/`webhook_id` before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Install the target app (using this gem) on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook the app subscribes to (e.g., `orders/create`) on `attacker.myshopify.com`; capture the raw request body `B` and header `x-shopify-hmac-sha256: H` from the genuine delivery.
3. Send a new POST to the app's webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, `x-shopify-topic: orders/create`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (`= B`) and succeeds since `H` matches `B` under the shared `api_secret_key`.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act as though the payload came from `victim.myshopify.com`.
