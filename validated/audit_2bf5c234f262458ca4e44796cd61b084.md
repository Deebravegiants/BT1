### Title
Unverified inbound settlement lets `repay`/`recapitalize` "excess refund" drain pool token custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The FFmpeg analog is a missing check on a fallible return value. In the pool, the equivalent defect is a missing check on the funds that back a declared payment: `ops::repay::apply` and `ops::recapitalize::apply` compute a refund purely from the caller-declared `action.amount` and immediately `transfer_out` that refund to the caller, without ever verifying that the declared amount was actually transferred into the pool and without debiting cash or calling `require_reserves`. An unprivileged address can call `pool.repay` with an arbitrary `amount` against a market where the position has zero debt, receive the entire declared amount as an "overpayment" refund, and drain real token custody belonging to suppliers of every market that shares the pool's physical balance.

### Finding Description
`repay` resolves the declared `amount` into burned debt shares and `overpayment` via `cache.resolve_repay(amount, position)` in `ops::repay::accounting`. When the position carries no debt, `current_debt_ceil` is zero, the full-close branch returns the whole amount as `overpayment`, `net_repay` is `0`, and the `net_repay == 0 || burned.raw() > 0` assertion passes on its first disjunct. `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)`, sending real tokens to the caller.

Crucially, `Cache::transfer_out` "moves tokens through the market's `asset_id` token client" and explicitly "does not adjust accounting cash" and performs no `require_reserves` check — it is a raw token transfer of the refund amount from the pool's shared custody. The repay leg assumes "the controller transfers the repay amount into the pool before this call," but nothing in the pool enforces or measures that inbound transfer: the refund is sized from the declared `amount`, not from a measured balance delta. The same shape exists in `ops::recapitalize::apply`/`accounting`, which refunds `amount - applied` the same way.

The repo's own test suite documents the exploit end-to-end: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `pool.repay(&payer, &ract(0, custody_before))` on a fixture with no debt and no inbound transfer, and asserts the entire pool custody balance was paid out to `payer` while the books were left untouched.

### Impact Explanation
Theft of user funds and protocol insolvency. One physical token balance backs multiple `(hub, token)` market books. The refund path pays out of real custody while crediting nothing and debiting nothing, so a single permissionless `repay` call with `amount = token.balance(pool)` sweeps the entire pool balance to the attacker. All `cash` accounting for that asset's markets remains intact on paper while the underlying tokens are gone, so subsequent `withdraw`, liquidation payouts, and `claim_revenue` transfers fail against an empty balance — the markets are rendered insolvent and suppliers' funds are permanently stolen/frozen.

### Likelihood Explanation
A single unprivileged transaction: call `pool.repay` (or `recapitalize`) directly with `action.position.scaled_amount = 0`, `action.hub_asset` set to any listed market, and `action.amount` equal to the pool's token balance. No debt position, no collateral, no prior token transfer, and no authorization is required — the test demonstrates it succeeds on a fresh address with no funding. Likelihood is high; only ordering relative to other refund users is relevant.

### Recommendation
Measure the actual inbound settlement instead of trusting the declared amount: snapshot `token.balance(pool)` before accounting and cap the refund — and the credited `net_repay`/`applied` — at the observed balance delta attributable to this call (or require the controller-mediated transfer and verify custody delta). Alternatively, gate `repay`/`recapitalize` so only the controller can invoke them, and in any case route the refund through `require_reserves`/cash-book debiting so an unfunded refund cannot exceed reserves that were actually received.

### Proof of Concept
Already encoded in the codebase at `contracts/pool/tests/flows.rs` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`):

```rust
// pool custody = custody_before, market has zero debt, payer transfers nothing in
let credited = t
    .client()
    .repay(&payer, &t.ract(0, custody_before)) // declared amount = entire pool balance
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                        // nothing credited...
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before); // ...but custody drained to payer
```

Root cause lines: `contracts/pool/src/ops/repay.rs` (`apply` transfers `outcome.overpayment` derived from declared `amount`), `contracts/pool/src/ops/recapitalize.rs` (`refund = amount - applied` then `transfer_out`), and `contracts/pool/src/cache/cash.rs` (`transfer_out` performs a raw token transfer with no `require_reserves` and no cash debit).
