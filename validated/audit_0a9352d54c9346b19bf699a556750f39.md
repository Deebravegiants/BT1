### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The gem's HMAC validation for incoming webhooks only authenticates the raw request body. The `shop`, `topic`, and `webhook_id` values — which are taken from unauthenticated HTTP headers — are handed to the host application's webhook handler as if they were verified, breaking the identity binding between "HMAC-authenticated bytes" and "the shop/topic the event is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body HMAC, then immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the same `api_secret_key` (the app's single client secret) is used to sign webhooks for **every shop** that has installed the app, a valid HMAC only proves "Shopify (or someone possessing this app's secret) produced this body at some point" — it says nothing about which shop or topic the body belongs to. Any party capable of receiving a legitimately signed webhook for one tenant (e.g., a user who installs the app on their own store, or captures/replays a webhook delivery) can take that valid `(raw_body, hmac)` pair and resubmit it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header (and arbitrary `shopify-topic`/`shopify-webhook-id` headers). `HmacValidator.validate` will still succeed because it never looks at those headers, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the event came from an arbitrary victim shop/topic.

This is the direct analog of the reported bug class: "a field acted on but not covered by the HMAC" — here the shop/topic/webhook-id fields are acted upon (used to route and attribute events) while only the body is authenticated.

### Impact Explanation
This is Critical: cross-tenant access. Applications built on this gem typically use `WebhookMetadata#shop` to decide which merchant's data to mutate (e.g., uninstall/redact records, update subscription/billing state, or trigger per-shop side effects) based solely on this gem's validated result. An attacker who legitimately controls one installed shop can forge webhook deliveries that the host app will process as if they originated from a different, victim shop, causing cross-tenant data corruption or state changes without ever needing that shop's credentials.

### Likelihood Explanation
High. The only prerequisite is the ability to receive any legitimately HMAC-signed webhook body from the target app (trivially available to any developer/merchant who installs the app themselves), plus the ability to POST an HTTP request with custom headers to the app's public webhook endpoint — no access token, secret, or privileged account is required.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signable content used by `HmacValidator`, or otherwise cryptographically bind them to the signed body (e.g., have `Webhooks::Request#to_signable_string` incorporate the header values, or validate that the shop domain in a stored/known-shop registry matches an independently-verified value) so that a signature valid for one shop/topic cannot be replayed to spoof another.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com` and capture one legitimate webhook delivery, e.g. `orders/create`, including its raw JSON body and its `X-Shopify-Hmac-Sha256` header value (valid against the app's shared `api_secret_key`).
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change the headers:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: shop/redact
X-Shopify-Hmac-Sha256: <captured-valid-hmac>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <arbitrary>

<captured raw body>
```
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` (via `lib/shopify_api/utils/hmac_validator.rb`) validates successfully because it only checks the body against the secret. `Registry.process` (in `lib/shopify_api/webhooks/registry.rb`) invokes the app's handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...)`, causing the host app to act on `victim-shop.myshopify.com` despite the request never being produced or endorsed by Shopify for that shop.
