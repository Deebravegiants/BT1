### Title
Webhook shop-domain (and topic) attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::HmacValidator` only verifies the HMAC over the raw request body. The `shop-domain` (and `topic`) headers, which are used to attribute the webhook to a specific merchant and dispatch it to the correct handler, are never included in the signed material. Any party that possesses one valid `(raw_body, hmac)` pair signed with the app's shared secret — e.g. an attacker who has installed the app on their own store and thus receives real, validly-signed webhook deliveries — can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop. The signature still validates, and the app processes the payload as if it belonged to the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, independent of the signed body.

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it with `verifiable_query.hmac`: [2](#0-1) 

`Webhooks::Registry.process` gates on that same body-only HMAC check and then dispatches using the unauthenticated `shop` header: [3](#0-2) 

The identity binding that should hold is: `HMAC-valid ⟺ (body, shop, topic)` all originate from Shopify for that specific delivery. What is actually enforced is only `HMAC-valid ⟺ body` originated from Shopify at some point (for some shop). Because the app's client secret is shared across every shop that installs the app (not per-tenant), any merchant who legitimately installs the app receives real webhook deliveries signed with that same secret. That merchant can capture a `(raw_body, hmac)` pair from their own store and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header changed to a different, victim shop. `HmacValidator.validate` still returns `true` because it never inspected those headers, and `Registry.process` hands the handler `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-chosen shop value.

### Impact Explanation
This breaks tenant isolation: an unprivileged app-installing user can make the application process webhook data under the identity of a different merchant, corrupting per-shop data pipelines, triggering shop-scoped side effects (e.g. inventory sync, order fulfillment automation, GDPR/compliance webhook handling) attributed to the wrong tenant, or poisoning data associated with a victim shop's session/store. This is a cross-tenant access issue, matching the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
Likelihood is significant for any multi-tenant app built on this gem: the only prerequisite is that the attacker be able to install the app on a store they control (a standard, unprivileged action for any Shopify developer/merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint (which by design must be internet-reachable to receive Shopify webhooks). No secret material beyond what the attacker legitimately possesses from their own installation is required.

### Recommendation
Include the routing/attribution fields (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., have `to_signable_string` concatenate body with these headers). At minimum, `Registry.process` should re-derive or cross-check the shop identity from a value that is covered by the signature (or from a per-shop secret) rather than trusting the raw `X-Shopify-Shop-Domain` header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining real webhook deliveries with valid `X-Shopify-Hmac-Sha256` headers over some raw JSON body `B` (signed with the app's shared `api_secret_key`).
2. Attacker POSTs the exact same raw body `B` and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)` is constructed; `HmacValidator.validate` computes the HMAC only over `B` [4](#0-3)  and it matches, so validation succeeds [5](#0-4) .
4. `Registry.process` invokes the registered handler with `shop: request.shop` equal to `"victim.myshopify.com"` [6](#0-5) , causing the application to process attacker-supplied data under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
