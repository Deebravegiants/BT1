### Title
Supply-index floor leaves phantom claims that drain pool cash on withdrawal - (File: contracts/pool/src/interest.rs)

### Summary
The CVE class (a zero-byte/zero input read returning residual memory instead of nothing) maps onto `apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs:73-89`. When bad debt meets or exceeds the market's total supplied value, the write-down should zero every supply claim, but the index is clamped up to `SUPPLY_INDEX_FLOOR_RAW` (`10^24`). Every surviving share therefore still claims `scaled × floor / RAY` of underlying — value that the write-down intended to erase. The withdraw path (`contracts/pool/src/ops/withdraw.rs:111-119`) gates only on `require_reserves` (cash), `require_utilization_below_max`, and `require_supply_for_debt` — it never calls `require_backed_market` — so those phantom claims are payable in real cash.

### Finding Description
`apply_bad_debt_to_supply_index` computes `new_supply_index = supply_index * floor(remaining / total)` and then applies `new_supply_index.max(SUPPLY_INDEX_FLOOR_RAW)` (`interest.rs:83-88`). When `bad_debt >= total_supplied_value`, `remaining` is 0 but the index lands at `10^24`, not 0. The codebase itself demonstrates the consequence: `contracts/pool/tests/interest.rs:317-369` (`test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard`) and `:430-496` show a wiped holder's stranded claim paying out an amount equal to a fresh depositor's entire deposit, draining the pool to zero cash while books remain insolvent.

Attack path for a single unprivileged address:
1. Hold (or acquire before the wipeout) supply shares in a market, then drive it into bad-debt eligibility — e.g., supply collateral, borrow, let price/accrual push `total_debt > total_collateral` with collateral ≤ $5, so permissionless `clean_bad_debt` fires.
2. `clean_bad_debt` burns the debt and calls `apply_bad_debt_to_supply_index`; the clamp leaves all supply shares (including the attacker's and other suppliers') claiming at `10^24` instead of ~0.
3. Call `withdraw(account_id, hub_asset, 0)` — `0` maps to `WITHDRAW_ALL_SENTINEL` — which resolves the full floor-valued claim and transfers cash out. `gate_and_debit` (`withdraw.rs:111`) checks cash (`require_reserves`) and `require_supply_for_debt` (borrowed is now 0), so the payout succeeds even though total floor claims exceed backing.

### Impact Explanation
Theft of user funds / protocol insolvency. After a write-down that should have erased supplier claims, surviving shares retain a claim scaled by the 1000x-above-zero floor. The first withdrawer extracts real cash up to `require_reserves`; each withdrawal leaves remaining suppliers and any `recapitalize` payer further under-backed. `docs/reference/formulas.md:397-401` concedes "the non-zero floor can leave residual claims without backing" but only asserts that *new supply* fails the backing gate — nothing blocks the phantom withdrawal itself.

### Likelihood Explanation
Requires a market to reach full-wipeout bad debt (write-down ≥ total supplied value), which is an extreme but reachable state the code explicitly handles (`SUPPLY_INDEX_FLOOR_RAW` exists precisely for it, and `clean_bad_debt`/`recapitalize` are permissionless entrypoints). Any holder of pre-wipeout supply shares — including the borrower who caused the bad debt via a second position — can trigger the drain with a single `withdraw`. Medium likelihood, high impact.

### Recommendation
Either burn/strand wiped supply shares at write-down time (track that claims below the floor are unpayable), or enforce `require_backed_market` / a per-market "post-wipeout" flag in `withdraw::gate_and_debit` so claims valued only by the index clamp cannot draw cash until `recapitalize` restores backing. Alternatively, cap each withdrawal by the market's actual written-down remaining value rather than the floored index.

### Proof of Concept
Adapt `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` (`contracts/pool/tests/interest.rs:317-369`) through the real entrypoints: (a) seed supply + borrow in one market; (b) manipulate price down so `clean_bad_debt` eligibility holds and invoke it — index clamps to `SUPPLY_INDEX_FLOOR_RAW`; (c) a depositor (or `recapitalize` payer) adds cash; (d) wiped supplier calls controller `withdraw` with amount `0` — `resolve_close_or_partial` pays the floor-valued claim and `transfer_out` moves real tokens to the attacker, leaving `cash < honest_supplier_claim` (insolvency), exactly as the raw-cache test asserts.

Residual uncertainty: whether the controller's `withdraw` path adds a guard (e.g., a deprecated-market or post-cleanup flag) not visible in the pool-level code reviewed; the indexed snippets show none, and the pool op itself is the enforcement point shown above.
