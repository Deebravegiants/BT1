Based on my analysis, I've confirmed the analog vulnerability and root cause. Here's my finding:

### Title
Single global `maxOracleAge` staleness bound applied to all token/native Chainlink feeds regardless of their actual heartbeat, permitting stale-price exploitation of `SimplexPaymaster` gas payments - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments and fee-recycling swaps using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native asset oracle and each registered token oracle, gating staleness with a single contract-wide `maxOracleAge` value rather than a per-feed heartbeat, mirroring the cited `LibUbiquityPool.addCollateralToken` default-heartbeat issue.

### Finding Description
`_getOraclePrice` is the sole staleness check for every oracle read in the contract, and it compares `block.timestamp - updatedAt` against the single storage variable `maxOracleAge`: [1](#0-0) 

That one value is used identically for `nativeOracle` and for *every* registered `TokenConfig.tokenOracle`, in both `_tokenPrice` (gas-payment pricing) and `swapAndDeposit` (fee-recycling swap pricing): [2](#0-1) [3](#0-2) 

The contract's own documentation acknowledges that Chainlink heartbeats vary drastically by chain and feed — "BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h" — yet only one governance-configurable bound exists, capped by `MAX_ORACLE_AGE = 7 days`: [4](#0-3) [5](#0-4) 

The validation in `_setParams` only enforces `0 < maxOracleAge <= 7 days` — it never checks the parameter against each registered token's actual feed heartbeat: [6](#0-5) 

The deployment script itself demonstrates the practical consequence: to avoid reverts on the slowest supported feed (24h heartbeat), it sets a global default of 90,000 seconds (25 hours) for *all* registered tokens, including any fast-heartbeat token (e.g., a BSC stablecoin with a ~27s heartbeat) that might later be registered under the same instance or whose heartbeat characteristics were not what governance assumed when tuning `maxOracleAge`: [7](#0-6) 

Because `RegisterToken` lets governance add any ERC-20/oracle pair without also adjusting `maxOracleAge` per-token, and because `_registerToken` performs no heartbeat validation whatsoever: [8](#0-7) 

any newly added fast-heartbeat feed silently inherits the loose contract-wide bound, exactly as the referenced `LibUbiquityPool` report describes for `addCollateralToken`'s default heartbeat.

### Impact Explanation
If a registered token's real-world price moves sharply (de-peg, crash) faster than the coarse, one-size-fits-all `maxOracleAge` permits detection, `_getOraclePrice` still accepts the outdated Chainlink answer as valid for up to that window (potentially tens of hours). Since `_tokenPrice` and `swapAndDeposit`'s `amountOutMin` are both derived directly from this stale value, an attacker can submit UserOps (or wait for others') that pay gas in the mispriced token, extracting value from the paymaster's treasury/EntryPoint deposit, or force `swapAndDeposit` to execute against a stale minimum-output bound, both draining paymaster-held funds. This is a permissionless-transaction-reachable loss of funds (any account can submit a UserOp with a chosen `paymasterData` mode/token), affecting a component whose only mitigant against oracle manipulation is exactly this staleness bound, so a bound that is looser than the feed's actual heartbeat defeats that mitigant.

### Likelihood Explanation
Likelihood is moderate-to-high: governance need only set (or leave, per the deploy script) a `maxOracleAge` sized for the slowest of several concurrently registered feeds, which is presented in the code/deploy script as the intended, "safe" configuration — meaning the vulnerable state is the expected operating configuration rather than an edge case, and it requires no admin compromise, just normal multi-token registration with heterogeneous heartbeats.

### Recommendation
Store a per-token (and per-native-oracle) staleness threshold in `TokenConfig`/`Params` instead of one contract-wide `maxOracleAge`, set at `RegisterToken`/`UpdateParams` time from each feed's actual heartbeat, and check `_getOraclePrice` against that specific threshold rather than the global value.

### Proof of Concept
1. Governance registers `TokenA` (Chainlink heartbeat ~27s) and `TokenB` (heartbeat ~24h) via `RegisterToken`, both under the shared `maxOracleAge` initialized to 90,000s (25h) per `DeploySimplexPaymaster.s.sol`.
2. `TokenA`'s oracle stops updating (sequencer outage, feed congestion, or a de-peg the aggregator hasn't reported yet) while its true market price drops sharply.
3. For up to 25 hours, `_getOraclePrice(TokenA's oracle, ...)` still returns the last (now stale, inflated) answer because `block.timestamp - updatedAt <= maxOracleAge` (25h ceiling), well beyond `TokenA`'s expected 27s heartbeat.
4. Any user submits a UserOp with `paymasterData` mode `0x00`/`0x02` naming `TokenA`; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` computes `tokenPrice` from the stale, inflated `tokenUsd`, undercharging the true gas cost in `TokenA` units.
5. The paymaster's stablecoin/native reserves are drained relative to gas subsidized, with no revert or protection because the single `maxOracleAge` window has not yet elapsed for that specific fast-heartbeat feed.

    function _registerToken(address token, AggregatorV3Interface oracle) internal {
        if (token == address(0) || address(oracle) == address(0)) revert ZeroAddress();

        bool isNew = !tokenConfigs[token].active && address(tokenConfigs[token].tokenOracle) == address(0);

        tokenConfigs[token] = TokenConfig({
            tokenOracle: oracle,
            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        if (isNew) {
            registeredTokens.push(token);
        }

        emit TokenRegistered(token, address(oracle));
    }

        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

    }

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }
