### Title
HOT Bridge withdrawal status incorrectly reported as "completed" on malformed/non-hex status value - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.describeWithdrawal` treats a withdrawal status that fails hash validation as `"completed"` (with a `null` `txHash`) instead of leaving it `"pending"` or otherwise unresolved, so a caller/integrator can be told a withdrawal has landed on the destination chain when the code has explicitly detected that the returned value is not a valid transaction hash.

### Finding Description
Similar to the Timeswap `burn()` bug, where a function that is supposed to represent a real, verified state transition (burning the ERC-721) instead reports success (returning without error) without actually performing/validating the corresponding on-chain action, `HotBridge.describeWithdrawal` reports the withdrawal `status` field as `"completed"` even when it has just determined the value it received cannot be trusted as a real destination transaction hash: [1](#0-0) 

The relevant branch is reached for "other non-EVM networks" that are not EVM, Stellar, or TON (line 465 `else` branch). When `status` is a non-empty string, the code expects it to be a hexified raw tx hash (per the comment "HOT returns hexified raw bytes without 0x prefix, any other value should be ignored"), and calls `isHex(status)` to validate this. If the check fails, instead of ignoring the value and returning `{ status: "pending" }` (or falling back to the API lookup, as is done in the sibling branches), the code logs a warning and unconditionally returns `{ status: "completed", txHash: null }`.

This breaks the equality between "status reported" and "on-chain outcome": the contract/API only returned an opaque, unparseable string — it did NOT confirm the destination transaction completed — yet the SDK reports `"completed"`.

### Impact Explanation
An integrator (wallet, exchange, or application) that treats `describeWithdrawal` results as the source of truth for crediting a user or releasing custody of funds would see `status: "completed"` for a withdrawal that has not actually been verified to have landed on the destination chain. This maps to the explicit High-impact criterion: "a status or hash misreport making an integrator credit or refund twice." Because `txHash` is `null`, downstream consumers cannot even verify the claim, compounding the risk of premature crediting, double-crediting, or incorrectly closing out a pending withdrawal as done.

### Likelihood Explanation
This code path is reached only for non-EVM/non-Stellar/non-TON HOT chains when the `getGaslessWithdrawStatus` view returns a string value that is not `HotWithdrawStatus.Completed`/`Canceled` and fails `isHex()`. This can occur due to an unexpected/changed contract response format, a bridge upgrade, or a malformed encoding — conditions outside the direct control of an attacker but plausible in production drift between the HOT contract/API and the SDK's parsing assumptions. It requires no malicious actor, only a data format mismatch, making it moderately likely to manifest as a status-reporting bug rather than a targeted exploit.

### Recommendation
Do not default to `"completed"` when the status string fails hex validation. Instead, either:
- Return `{ status: "pending" }` (matching the pattern used elsewhere in the same function, e.g., the API-hash-not-found fallback), or
- Fall back to `fetchWithdrawalHashFromApi` as is already done for other branches, and only report `"completed"` once a hash is actually confirmed.

### Proof of Concept
1. HOT contract/API for a non-EVM/non-Stellar/non-TON chain returns a `status` string that is not `"COMPLETED"`/`"CANCELED"` and is not valid hex (e.g., due to a future encoding change or bug in the queried contract).
2. `isHex(status)` returns `false`.
3. `describeWithdrawal` logs `"HOT Bridge incorrect destination tx hash detected"` and returns `{ status: "completed", txHash: null }`. [2](#0-1) 
4. Any caller polling this status (e.g., a wallet UI or backend ledger) marks the withdrawal as finished, despite no verified destination transaction existing.
