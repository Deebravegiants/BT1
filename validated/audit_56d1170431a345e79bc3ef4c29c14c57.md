### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an inbound webhook from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that this gem verifies via `Utils::HmacValidator` only covers the raw request body, not the shop-domain header. Since the webhook HMAC secret (`Context.api_secret_key`) is a single app-level secret shared across *every* shop that installs the app, a valid `(body, hmac)` pair from any one tenant of the app remains "valid" no matter what `shop-domain` value is attached to it. This breaks the intended identity binding: `authenticated_shop == hmac_signed_shop`.

### Finding Description
- `Request#hmac` and `Request#to_signable_string` show the signable content is exclusively the raw JSON body: [1](#0-0) [2](#0-1) 
- `Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signed payload: [3](#0-2) 
- `Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`; it never folds in `shop`: [4](#0-3) 
- The webhook HMAC secret is the single app-level `api_secret_key`, identical for all shops that have installed the app (there is no per-shop signing secret anywhere in this gem's webhook path), confirmed by the same secret being used for OAuth callback validation and JWT verification across all tenants: [5](#0-4) [6](#0-5) 

Because of this, the equality the gem should enforce — "the shop the HMAC vouches for" == "the shop the application will act on" — never actually holds. `hmac_signed_content` = `raw_body` only, while `identity_used_by_app` = `shopify-shop-domain header`, an attacker-controlled, unauthenticated field. Any party who can capture or replay one legitimate webhook delivery for Shop A (webhooks are delivered over plaintext-inspectable HTTP endpoints the merchant's own app operates, and headers are trivially rewritable by anything sitting in front of, or replaying to, the app's webhook endpoint) can resubmit the identical `(body, hmac)` pair while substituting `x-shopify-shop-domain: shop-b.myshopify.com`. `HmacValidator.validate` will still return `true` because it never inspects the header, and the host application — following this gem's documented `Request#shop` accessor as the source of truth for tenant attribution — will process Shop A's data under Shop B's identity.

### Impact Explanation
This is a cross-tenant identity-binding failure exposed by the gem's own API surface: the library explicitly presents `shop-domain` as a validated/trusted field once `HmacValidator.validate(request)` succeeds, but the validation never actually authenticates that field. Any consumer of `ShopifyAPI::Webhooks::Request` (as documented and exercised in this repo's own webhook registry/handler code) that keys session lookups, data storage, or business logic off `request.shop` after a passing HMAC check is relying on an identity value this gem never bound to the signature — enabling cross-tenant data confusion/injection for any app that has more than one installed shop, which the report class ("field acted on but not covered by the HMAC") flags directly.

### Likelihood Explanation
Exploitation requires only the ability to relay/replay one previously observed valid webhook body+HMAC (no `api_secret_key`, access token, or privileged account needed) with a modified `shop-domain` header value — something achievable by any actor with visibility into a single webhook delivery reaching the app (proxy, logging intermediary, or a malicious co-tenant shop capturing its own legitimate webhook and re-sending it against the shared endpoint with a spoofed header). No TLS interception or credential theft of the target shop is required.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind the `shop-domain` header to the signed payload before exposing it via `Request#shop`, so that `Utils::HmacValidator.validate` fails whenever the shop-domain header does not match the shop the payload was actually signed for.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`:
   - Headers: `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, body: `{"id": 123, ...}`.
2. Attacker/relay resends the exact same body and `x-shopify-hmac-sha256` value, but changes the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` still returns `true` because:
   - `compute_signature` only hashes `request.to_signable_string` (`@raw_body`), per [2](#0-1)  and [4](#0-3) .
4. The host application, trusting the passing HMAC check, calls `request.shop` and processes order `123` under `shop-b.myshopify.com`'s tenant context — a cross-tenant data confusion the gem's HMAC guarantee was supposed to prevent.
