Based on my investigation, I found a valid analog in the Tron variant of `IntentGatewayV2`.

### Title
Excess native `msg.value` sent to `placeOrder()` is not refunded to the user on Tron `IntentGatewayV2` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.placeOrder()` is a `payable` function that any unprivileged user can call to escrow input tokens (including native TRX) and optionally pay `order.fees` via a native-to-feeToken swap. Unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly refunds any unspent `msgValue` back to the caller at the end of `placeOrder`, the Tron version never returns leftover native value, permanently trapping any overpayment in the contract.

### Finding Description
`placeOrder` is `public payable` and reachable by any unprivileged caller. It tracks a local `msgValue = msg.value` and decrements it as native-token inputs are consumed (`msgValue -= order.inputs[i].amount`) and, if `order.fees > 0`, as native value is swapped for the fee token via `swapETHForExactTokens{value: msgValue}(order.fees, ...)`. [1](#0-0) 

After the fee-swap branch, the function does not capture the unspent amount returned by `swapETHForExactTokens` (it ignores the `amounts` return value entirely, unlike the EVM version which does `msgValue -= amounts[0]`), and — critically — it never sends any remaining `msgValue` back to `msg.sender` before emitting `OrderPlaced` and returning: [2](#0-1) 

Contrast this with the canonical EVM `IntentGatewayV2.sol`, which performs the exact same accounting but ends with an explicit refund of any unspent native value to `msg.sender`: [3](#0-2) 

This is functionally identical to the reported `IB_Champions.safeMint()` bug: a payable entry point checks that `msg.value` (or the derived `msgValue`) is sufficient but never refunds the excess, so any TRX sent beyond what's strictly required (whether an all-native order with `msg.value > sum(order.inputs)`, or a native fee swap where `swapETHForExactTokens` spends less than the full remaining `msgValue`) is permanently retained by the contract with no user-facing mechanism to reclaim it.

### Impact Explanation
Any user overpaying `msg.value` on `placeOrder` (e.g., due to slippage-padding a fee-token swap estimate, UI rounding, or simply sending extra native token as a safety margin) permanently loses the excess TRX — it becomes stuck in the `IntentGatewayV2` contract balance, indistinguishable from other escrowed funds, with no owner/admin mechanism identified in the contract to return it to the specific depositor. This is a direct, permanent loss of user funds reachable from a single unprivileged transaction, matching the Medium-severity classification of the original report.

### Likelihood Explanation
High likelihood of occurrence: overpayment is a normal user/relayer behavior pattern (buffering for price swings in the Uniswap V2 fee-token swap, or simple wallet UX rounding up native value), and the code path is on the primary, most-frequently-called entry point of the intents system. No special privileges or unusual conditions are required — a normal `placeOrder{value: X}()` call with `X` slightly above the required amount triggers the loss every time.

### Recommendation
Mirror the EVM implementation: track the actual amount consumed by `swapETHForExactTokens` (via its `amounts[0]` return value) when paying `order.fees` in native token, and after all input/fee accounting is complete, refund any residual `msgValue` to `msg.sender` (e.g., via a low-level `call` with revert-on-failure), exactly as done in `evm/src/apps/IntentGatewayV2.sol` at lines 394-397, before emitting `OrderPlaced`.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: order.inputs[0].amount + 0.5 ether}(order, graffiti)` on the Tron deployment, where `order.inputs[0]` is a native-token input of amount `X` and `order.fees == 0`.
2. Inside `placeOrder`, `msgValue` starts at `X + 0.5 ether`; the native-input loop decrements it by `X`, leaving `msgValue == 0.5 ether` unspent.
3. Since `order.fees == 0`, the fee-swap branch is skipped entirely; `OrderPlaced` is emitted and the function returns without ever transferring the leftover `0.5 ether` back to the user.
4. The `0.5 ether` overpayment remains permanently locked in the `IntentGatewayV2` contract's balance, with no code path to recover it for that specific user (analogous to the `testPlaceOrder_RefundsExcessNativeToken` regression test that exists for the EVM version but has no Tron equivalent). [4](#0-3)

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }
