## Title
`handlePostRequests()`/`handleGetResponses()` batches can be griefed via front-running a single leaf, forcing atomic revert of the entire relayed batch - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests()` and `HandlerV2.handleGetResponses()` process an array of independently-provable MMR leaves in one transaction, but revert the **entire** transaction if even one of the leaves was already delivered. Because each leaf's inclusion proof is independently derivable from the same committed overlay root, an unprivileged actor observing a pending relayer transaction in the mempool can extract a single leaf/proof and front-run the batch with a smaller, cheaper transaction delivering only that one request. This forces the original larger batch to hit `DuplicateMessage()` and revert in full, exactly mirroring the `executePayroll()` split-transaction analog: repeated griefing forces relayers to reconstruct and resubmit shrinking batches, wasting gas and delaying delivery of all other legitimate, still-undelivered requests bundled in the batch.

### Finding Description
In `handlePostRequests()`:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    // duplicate request?
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [1](#0-0) 

The same pattern exists in `handleGetResponses()`: [2](#0-1) 

A `PostRequestMessage`/`GetResponseMessage` bundles many leaves under a single MMR multiproof verified against an already-finalized `overlayRoot`: [3](#0-2) 

Because the root is already committed on-chain (from a prior `handleConsensus` update), any observer can construct a valid single-leaf `PostRequestMessage`/proof for one leaf taken out of a pending relayer's batch calldata and submit it with a higher gas price. That single-leaf delivery succeeds and sets `requestReceipts[commitment]` on the host. When the original, larger batch transaction is then mined, the duplicate check at line 207 (or 244 for responses) causes the **whole transaction to revert**, discarding delivery of every other (still valid, non-duplicate) request bundled with it.

This directly contradicts the design intent visible elsewhere in the same code path: `EvmHost.dispatchIncoming()` explicitly avoids all-or-nothing batch failure for a missing destination contract or a failing `onAccept` callback, using an early `return` instead of a revert, with the comment "instead of reverting the entire batch, early return here": [4](#0-3) 

But the duplicate-detection loop in `HandlerV2` runs *before* `dispatchIncoming` is invoked and still uses a hard `revert`, defeating that intended per-leaf isolation for the specific "already delivered" case — precisely the split/front-run pattern described in the `executePayroll()` report, where partial pre-execution of a batched operation forces the whole batch to fail and be rescheduled.

The compounding case is worse: `batchCall()` lets a relayer atomically combine a `handleConsensus` call with a `handlePostRequests`/`handleGetResponses` call to save gas: [5](#0-4) 
If an attacker front-runs even one leaf inside such a combined batch, the entire `batchCall` — including the consensus update — reverts (`BatchCallFailed`), delaying propagation of the consensus state itself, not just the application message.

### Impact Explanation
This is a griefing vector that renders the batched relaying route unreliable: any unprivileged party can repeatedly force full-batch reverts of legitimate relayer transactions by extracting and front-running single leaves from public mempool calldata. Because relayers rely on batching (`batchCall`, multi-leaf `PostRequestMessage`/`GetResponseMessage`) to amortize gas costs across many pending Hyperbridge messages, an attacker can systematically prevent whole batches — including bundled consensus updates — from landing, forcing relayers to fall back to single-message submission (losing the intended gas efficiency) or to repeatedly reconstruct/resubmit shrinking batches while messages remain undelivered. This matches the accepted "route unable to deliver messages" impact category: it is a repeatable denial of the batched delivery path for POST requests and GET responses.

### Likelihood Explanation
Likelihood is high: `handlePostRequests`/`handleGetResponses`/`batchCall` are fully permissionless entry points reachable by anyone. The state root and multiproof needed to derive an isolated single-leaf proof are public once a relayer's batch transaction is broadcast (visible in the mempool/calldata), and MMR/merkle multiproofs allow trivial extraction of a proof for a single leaf from a superset proof over the same committed root. No special privileges, timing races beyond standard front-running (higher gas price), or capital are required.

### Recommendation
Do not let a single duplicate leaf abort the whole batch. Change the per-leaf loop in `handlePostRequests()` and `handleGetResponses()` to skip already-delivered leaves (e.g., `continue`) instead of reverting, mirroring the early-return pattern already used in `EvmHost.dispatchIncoming()`. Apply the same non-atomic-per-item semantics inside `batchCall()` for the affected call types, or provide a variant that tolerates partial-already-delivered state without discarding the rest of the batch (e.g., returning a per-leaf success/failure result rather than reverting the transaction).

### Proof of Concept
1. Relayer R observes N valid, pending `PostRequestLeaf` deliveries for chain X and submits `handlePostRequests(host, {proof, requests: [leaf_0 ... leaf_N]})` in a single transaction, referencing the already-finalized `overlayRoot` at `request.proof.height`.
2. Attacker A monitors the mempool, extracts `leaf_k` (`0 <= k < N`) and its proof/root data from R's pending calldata, and constructs a minimal `PostRequestMessage` containing only `leaf_k` with a matching (derivable) single-leaf multiproof against the same committed `overlayRoot`.
3. A submits this single-leaf transaction with higher gas price; it is mined first, setting `requestReceipts[hash(leaf_k.request)]` via `EvmHost.dispatchIncoming` (`evm/src/core/EvmHost.sol:794-818`).
4. R's original N-leaf transaction is mined next. In the duplicate-check loop (`evm/src/core/HandlerV2.sol:204-209`), `host.requestReceipts(leaf_k.request.hash()) != address(0)` is true, so the call reverts with `DuplicateMessage()`, discarding delivery of all `N-1` other legitimate leaves and R's entire transaction gas spend.
5. R must reconstruct a new multiproof excluding `leaf_k` and resubmit; A can repeat this against every subsequent batch R submits.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
