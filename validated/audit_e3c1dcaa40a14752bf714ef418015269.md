### Title
Webhook shop-domain attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`) that the library hands to the registered webhook handler are read directly from unauthenticated HTTP headers. This is the "field acted on but not covered by the HMAC" identity-binding break: an attacker who legitimately possesses one valid `(body, hmac)` pair — trivially obtainable by installing the app on their own store and capturing any webhook delivery — can replay that exact body/HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are never included in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received signature — i.e., it authenticates only the body bytes, never the shop header: [3](#0-2) 

`Registry.process` trusts this validation, then forwards `request.shop` (the unauthenticated header value) straight to the handler as the identity of the merchant the event is "from": [4](#0-3) 

The binding that should hold is: `shop-domain used to attribute/authorize the webhook event == shop-domain bound inside the HMAC-verified bytes`. In this implementation, the HMAC only verifies `body`, so `shop` (and `topic`)  can diverge freely from what was actually cryptographically approved by Shopify for that body. This mirrors the "Unrestricted CPI" pattern in the report: the mechanism that establishes trust (HMAC/CPI signer check) does not cover every field that downstream code treats as trusted (adapter program / shop attribution).

Because any Shopify webhook is signed with the *app's own* `client_secret` regardless of which shop triggered it, an attacker who runs the app on their own store (or otherwise gets a legitimate webhook delivery, e.g. via a free trial install) obtains a fully valid `(raw_body, hmac)` pair signed by the developer's real secret. They can then POST that same body/hmac to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header (e.g. a known victim's `*.myshopify.com` domain) and `Registry.process` will accept it as authentic, handing the handler `shop: <attacker-chosen victim shop>` alongside a validly-signed body.

### Impact Explanation
Host applications built on this gem are documented to use `WebhookMetadata#shop` (or the parsed body's shop reference) to route mutations to the correct tenant record — e.g. marking a shop uninstalled, updating shop-level settings, processing `customers/redact`/`shop/redact` GDPR topics, or updating billing/subscription state keyed by shop. Since the shop attribution isn't bound to the signed bytes, an attacker can trigger these handlers against a shop they do not control, causing cross-tenant state corruption (e.g., forcing another merchant's app record into an "uninstalled" state, or triggering a GDPR redact/data-request flow against a shop they don't own). This satisfies the "cross-tenant access" Critical-impact category since the identity boundary (which tenant an inbound authenticated request belongs to) is broken by an unprivileged internet user with no access token or secret of their own — they only need one legitimate webhook sample from their own free/dev installation.

### Likelihood Explanation
High likelihood: obtaining a valid `(body, hmac)` pair requires only installing the app on an attacker-owned development store (trivial, free, and available to any developer), then triggering any webhook topic the app subscribes to (e.g. `app/uninstalled`, `shop/update`). No access to the target's credentials, access token, or `client_secret` is required, and the resulting forged POST is a normal unauthenticated HTTP request to the app's public webhook callback URL.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise re-derive/verify the shop identity against verified body content instead of trusting the raw header. Concretely:
- Include the `shop-domain` header (and `topic`) in `to_signable_string` so the HMAC covers them, or
- Require that the shop attribute used by handlers be independently verified (e.g., cross-checked against the app's own persisted session/install record for that shop and the API version/topic), rather than accepted solely from the header once body-HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) development store `attacker-shop.myshopify.com`, which is signed with the app's real `client_secret`.
2. App fires a webhook (e.g. `app/uninstalled`) to the attacker's dev server; attacker captures the raw POST body and the legitimate `X-Shopify-Hmac-Sha256` value — both valid per:
   `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` == `HMAC-SHA256(client_secret, raw_body)`.
3. Attacker replays the identical `raw_body`/`hmac` to the victim app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds because the body/hmac pair is genuinely valid for the app's secret: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never issued this event for that shop, letting the attacker trigger shop-scoped side effects (e.g. uninstall handling, redact flows) against a tenant they don't control.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
