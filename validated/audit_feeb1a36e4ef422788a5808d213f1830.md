## Equality being tested

For each index `i` in `circomData.erc20TokenAddresses` where the token is ETH (`address(0)`), the code claims:

```
balanceDif[i] = newBalances[i] + msg.value - oldBalances[i]
             == amountChanges[i] + utxoAmount[i]
```

The intended invariant is that a single `msg.value` should be able to satisfy **exactly one** accounting leg. Tracing the code shows this invariant is broken whenever `address(0)` (ETH) appears **more than once** in `circomData.erc20TokenAddresses`.

### Trace

`oldBalances`/`newBalances` are snapshotted with `getBalancesForArray`, which just calls `getERC20OrETHBalance(address(0))` → `address(this).balance` for every occurrence of `address(0)` in the array [1](#0-0) . Because `transact` is `payable`, `msg.value` is already credited to `address(this).balance` *before* `oldBalances` is even read at [2](#0-1) .

The per-index balance check adds `msg.value` unconditionally to every index whose token is `address(0)`, with no deduplication of repeated `address(0)` entries in `erc20TokenAddresses`: [3](#0-2) 

`dimensionsCheck` (called from `performHinkalChecks`) only validates array *lengths* against `Dimensions`, never uniqueness of `erc20TokenAddresses` entries [4](#0-3) . Nothing else in `performHinkalChecks`/`checkOnchainCreation` rejects duplicate token addresses [5](#0-4) .

In `_internalTransact`, for a positive `amountChanges[i]` (deposit leg) the code only requires `msg.value == amountChanges[i]` and, since the destination is `address(this)`, performs **no actual transfer** (the ETH is already resident from the call's value): [6](#0-5) [7](#0-6) 

Because this check only compares `msg.value` to `_value` (not a running total), it passes identically for every duplicated `address(0)` index as long as each `amountChanges[i]` equals the same fixed `msg.value`.

### Concrete break

Let `X` = contract's ETH balance before the tx, `V = msg.value`, and craft `erc20TokenAddresses = [address(0), address(0)]` with `amountChanges = [V, V]`, `onChainCreation = [false, false]`, internal transact (`externalActionId == 0`), `originalSender == msg.sender` (no relay).

- `oldBalances[0] = oldBalances[1] = X + V` (both already include the attached `msg.value`).
- `_internalTransact` runs twice: for both `i=0` and `i=1`, `deltaAmountChange = V > 0`, requiring `externalAddress == msg.sender` and `msg.value == V` — trivially true both times since `msg.value` is constant for the tx. No ETH actually moves (`_to == address(this)`).
- `newBalances[0] = newBalances[1] = X + V` (unchanged).
- `balanceDif[0] = balanceDif[1] = (X+V) + V - (X+V) = V` for **both** indices.
- Required check: `balanceDif[i] == amountChanges[i] + utxoAmount` → `V == V + 0`. **Both pass.**

Yet only one real deposit of `V` ETH occurred; the contract's on-chain accounting now believes **two** independent deposits of `V` each occurred (`amountChanges = [V, V]`). The ZK proof/`outCommitments` for this internal transact can create shielded off-chain UTXOs for both legs (dimensions only require `outCommitments.length == tokenNumber`, no cross-index value-conservation against real ETH received), so the attacker mints `2V` worth of shielded ETH UTXOs backed by only `V` real ETH — the `msg.value` term backed two accounting legs instead of one.

None of `performHinkalChecks`, `checkOnchainCreation`, `verifyProof`, or the balance/slippage `require`s catch this because they operate strictly per-index and never enforce that `erc20TokenAddresses` entries are distinct, nor that the sum of positive `amountChanges` for duplicate ETH legs is bounded by a single `msg.value`.

The specific "WETH + `address(0)` unwrap mid-call via a hook" variant described in the question does **not** hold under close reading: `preHookContract.preTransact` executes *before* `oldBalances` is snapshotted [8](#0-7) , and `postHookContract.afterTransact` executes *after* the balance-equation checks [9](#0-8) , so a WETH-unwrap hook cannot inject value between the snapshot and the check. The exploitable root cause is instead the **duplicate-`address(0)`-entry** double count identified above, which satisfies the same stated invariant violation ("msg.value backing == exactly one accounting term").

### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` back multiple accounting legs, minting unbacked shielded ETH — (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` adds `msg.value` to the balance-difference computation independently for every index in `circomData.erc20TokenAddresses` equal to `address(0)`, with no check that this array contains distinct token addresses. An unprivileged attacker can list `address(0)` multiple times with matching positive `amountChanges`, causing one real ETH payment to satisfy N separate deposit legs and mint N× the deposited shielded ETH value.

### Finding Description
The invariant `msg.value` should satisfy exactly one accounting term is violated because the loop at [3](#0-2)  re-adds `msg.value` for every `address(0)` occurrence, and `dimensionsCheck`/`checkOnchainCreation` never enforce uniqueness of `erc20TokenAddresses` [10](#0-9) . In `_internalTransact`, the ETH deposit check only compares `msg.value` to the per-index `amountChanges[i]` without accumulating a running total across indices, and performs no transfer since the funds are already resident [6](#0-5) . This lets an attacker submit `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]` with a single `msg.value = V`, passing the final balance-equation check twice with `balanceDif == V` for both indices, and mint two independent off-chain shielded ETH UTXOs of value `V` each.

### Impact Explanation
Minting shielded value without backing directly causes protocol insolvency: shielded ETH UTXOs can later be redeemed against the pool's real ETH reserves, draining funds from other depositors. This matches the Critical category ("minting shielded value without backing").

### Likelihood Explanation
No privileged role is required; the attacker only needs to construct their own `CircomData`/proof with a duplicated `address(0)` entry and matching `amountChanges`, which is fully within an unprivileged depositor's control. The attack is repeatable per transaction and its cost is just gas plus the single real ETH deposit `V`, for a gain of `(N-1)*V` minted shielded value per repetition (N = number of duplicated ETH legs).

### Recommendation
Enforce that `erc20TokenAddresses` contains no duplicate entries (e.g., a uniqueness check in `dimensionsCheck` or `performHinkalChecks`), and/or restructure the balance-equation check so `msg.value` is added to the aggregate ETH delta exactly once (outside the per-index loop) rather than once per matching index.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` + helper with a minimal internal-transact-only setup (mocked verifier returning true, matching `calldataHash`).
2. Craft `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`, `originalSender = attacker`, `relay = address(0)`.
3. Call `transact{value: V}(...)`.
4. Assert both per-index checks at [11](#0-10)  pass (`balanceDif == V` for both indices) while `address(this).balance` only increased by `V`, not `2V`.
5. Assert the resulting `outCommitments`/`encryptedOutputs` encode two separate `V`-valued ETH UTXOs — i.e., `2V` of shielded value created against `V` real ETH received, proving `msg.value` backed two accounting terms.
