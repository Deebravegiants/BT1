### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values used to dispatch a webhook to a handler directly from unauthenticated HTTP headers, while the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body. This breaks the intended binding: `hmac(raw_body) == valid` should imply `shop-domain header == the shop that actually generated raw_body`, but the gem never enforces that equality.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` only sign/verify the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates only the body HMAC and then forwards the header-derived `shop` value, unmodified, to the app's handler as trusted metadata: [3](#0-2) 

Because the same `Context.api_secret_key` signs webhooks for every shop that installs the app, and only the body bytes are covered by the signature, a valid `(raw_body, hmac)` pair captured from any one shop's webhook remains cryptographically valid no matter what `shop-domain`, `topic`, `webhook_id`, or `api_version` headers are sent alongside it. The equality the app relies on — "the shop attributed to this webhook equals the shop whose data produced the signed body" — does not hold.

### Impact Explanation
Any unprivileged party who can install the public/multi-tenant app on a shop they control (a normal, unprivileged Shopify merchant action) can capture a legitimately signed webhook `(raw_body, hmac)` for their own shop, then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to a victim shop's domain. `HmacValidator.validate` still passes because it only re-derives the signature from `raw_body`. The handler then processes the payload as if it belongs to the victim shop, via `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`. Depending on how the host app uses this metadata (e.g., keying database writes, cache invalidation, redact/GDPR handling, or triggering actions "for shop X"), this enables cross-tenant data confusion — an attacker-controlled body being attributed to and acted upon under a victim shop's identity.

### Likelihood Explanation
Medium: exploitation requires the attacker to first obtain one genuine signed webhook (achievable simply by installing the app on their own shop, which needs no special privilege for a public app), and requires the receiving application to trust `WebhookMetadata#shop`/`#topic` for shop-scoped side effects, which is the intended and documented usage pattern of this API. No access to `api_secret_key` or any credential is required — only the ability to intercept/replay an HTTP request the attacker's own shop already receives.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived identity fields to the signed payload so a swapped header invalidates the HMAC check in `Utils::HmacValidator.validate`.

### Proof of Concept
1. Install the target app (built on this gem) on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook subscription (e.g., `orders/create`) so Shopify sends a POST to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of raw_body>`, and body `raw_body`.
3. Capture `raw_body` and the HMAC value.
4. Resend the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(..., raw_body)` — this still matches, so validation passes.
6. `request.shop` now returns `victim.myshopify.com`, and the handler receives `WebhookMetadata` claiming the payload is for `victim.myshopify.com`, even though the underlying data originated from the attacker's shop. [4](#0-3) [3](#0-2) [5](#0-4)
