The docs at `docs/usage/webhooks.md:125` explicitly claim `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — but the verification only covers the raw body, not the `shop` field the gem hands to the app's handler as an authoritative identity claim.

### Title
Webhook `shop` domain is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the webhook HMAC over the raw body only, then extracts `shop` from an unauthenticated header and forwards it to the app's handler as if it were verified. An attacker who owns any legitimately-registered shop (a normal, unprivileged app install) can capture one valid `(raw_body, hmac)` pair from their own store's webhooks and replay it against the victim app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to a victim shop. The HMAC check still passes because the signature never covers the shop header, letting the attacker inject events attributed to another tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from a header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, unconditionally trusts `request.shop` as the tenant identity passed to the app's handler: [3](#0-2) 

Since `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the shared secret, and `hmac` and `body` are the only things bound together, the `shop-domain` header is fully attacker-controlled while the HMAC still verifies: [4](#0-3) 

The documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify", encouraging apps to trust the resulting `data.shop` as an authenticated tenant key without separately cross-checking it: [5](#0-4)  and the handler documentation labels `shop` simply as "The shop domain of the webhook" with no caveat that it is unauthenticated: [6](#0-5) 

This breaks the equality the gem implicitly promises: `shop used as tenant key == shop the HMAC-verified body actually originated from`. In reality, `shop` is decoupled from the signed payload, so any shop that can receive genuine webhooks (i.e., any merchant who installs the app — an unprivileged actor with respect to other tenants) can forge webhooks that appear to originate from a different, victim shop.

### Impact Explanation
This is a cross-tenant identity binding failure: the gem authenticates the webhook body but hands the caller an unauthenticated tenant identifier (`shop`) as if it were verified. A host app that follows the gem's documented contract and uses `data.shop` to route/store/attribute webhook data will process attacker-supplied data (of the attacker's choosing, since they crafted the original body from their own store) under a victim shop's identity — a cross-tenant data injection/corruption issue.

### Likelihood Explanation
Any developer/merchant can install the target app on their own store (a normal, unprivileged action), which is enough to receive one legitimately HMAC-signed `(body, hmac)` pair. Replaying it with a modified shop header requires only a normal HTTP client — no access to `api_secret_key`, no privileged account, and no interaction with the victim shop.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed payload used for verification, or require the caller to supply the expected shop and compare it against a value cryptographically tied to the request (not a bare header). At minimum, update the documentation to clearly state that `shop` is not covered by the HMAC and must be independently validated by the host app against its own list of installed shops before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (valid signature over `raw_body` with the app's secret).
2. Attacker POSTs the same `raw_body` and `x-shopify-hmac-sha256` to the victim app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, causing the app to process attacker-chosen data as if it came from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
