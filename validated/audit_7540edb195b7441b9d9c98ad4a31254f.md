### Title
Deposits mint zero shares (silent fund loss / permanent vault brick) when `total-assets-preview` hits zero while shares remain outstanding - (File: `mainnet/contracts/vault/v0-vault-usdh.clar` and equivalent vault contracts)

### Summary
Zest's tokenized vault contracts (`v0-vault-usdh.clar`, `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`) compute share/asset conversions with `convert-to-shares-preview` / `convert-to-assets-preview`. When `total-supply-preview` is non-zero but `total-assets-preview` is zero, `convert-to-shares-preview` returns `u0` instead of reverting. Unlike the referenced SafEth bug (which reverts via divide-by-zero), Zest silently mints **zero shares** for a real deposit, and — because `redeem` explicitly reverts on zero output — the vault can become permanently unable to correctly mint or redeem shares once this state is reached.

### Finding Description
`convert-to-shares-preview` and `convert-to-assets-preview` special-case `ta == 0`: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview)) (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

`total-assets` is derived from the `assets` ledger var (a bookkeeping value, not the raw token balance) plus unrealized interest: [2](#0-1) 

`assets` can be driven to `u0` directly (independent of `total-supply`/outstanding shares) by `socialize-debt`, which reduces `assets` to write off bad debt but never burns any `zft` shares: [3](#0-2) 

Once `total-assets` reaches `u0` while `total-supply` (i.e. outstanding `zft`) remains non-zero:
- `deposit` computes `inkind = convert-to-shares-preview(amount) = u0`. The only guard is `(>= inkind min-out)`, which passes trivially with `min-out = u0` (the default for a naive caller). The deposit then transfers real underlying tokens into the vault and increases `assets` by the full amount, but mints `u0` shares to the depositor: [4](#0-3) 
- `redeem` computes `inkind = convert-to-assets-preview(amount) = u0` for any existing holder, and explicitly reverts with `ERR-OUTPUT-ZERO` since `(> inkind u0)` is asserted: [5](#0-4) 

Because `total-supply` never resets to `u0` (existing holders can never burn their now-worthless shares — `redeem` always reverts), the `(is-eq ts u0)` branch in `convert-to-shares-preview` that would restore a sane `1:1` price is permanently unreachable. Every subsequent depositor is silently minted `u0` shares while their principal is folded into the `assets` ledger with no share representing it.

### Impact Explanation
This breaks the core share-mint-vs-backing identity: `shares_minted * price == assets_deposited` is violated as `shares_minted = 0` while `assets_deposited > 0`. Deposited principal is added to the vault's internal accounting yet permanently unclaimable by anyone (no `zft` is minted to represent it), and pre-existing holders are locked out of `redeem` (`ERR-OUTPUT-ZERO`). This is a permanent freezing of funds for both new depositors (whose deposits mint no shares) and existing holders (who cannot redeem), and it cannot self-heal because `total-supply` can never reach `u0` through the normal contract flow. This matches the impact category of permanent freezing of funds (and de facto theft, since deposited principal has no claimable ownership).

### Likelihood Explanation
The precondition (`total-assets` driven to exactly `u0` while shares remain outstanding) is reachable through `socialize-debt`, a normal (if rare) protocol mechanism for writing off bad debt after undercollateralized positions default; it directly decrements the `assets` ledger without any coordinated share burn. Any vault that experiences a severe/total bad-debt event where the write-down consumes all of `assets` while `zft` is still in circulation enters this broken state. This does not require a flashloan, DAO compromise, oracle manipulation, or leaked keys — it is an internal accounting inconsistency reachable via the vault's own designed bad-debt handling plus a routine `deposit`/`redeem` call by any unprivileged user.

### Recommendation
- In `convert-to-shares-preview`, when `ts != 0` and `ta == 0`, revert instead of silently returning `u0` shares (mirroring the `ERR-OUTPUT-ZERO` guard already used in `redeem`), so that `deposit` cannot accept funds without minting proportional shares.
- Ensure `socialize-debt` (or any path that reduces `assets`/backing without burning shares) either also proportionally burns/marks outstanding shares as impaired, or blocks further `deposit`/`redeem` calls until an explicit re-initialization path resets `total-supply` and `assets` consistently.
- Add an invariant check post-deposit that `inkind > u0` whenever `amount > u0` and `ts > u0`.

### Proof of Concept
1. Vault has non-zero `total-supply` (shares outstanding held by users) and non-zero debt.
2. A large default occurs; the authorized liquidation/bad-debt contract calls `socialize-debt` with a `scaled-amount` large enough that `principal-reduction >= (var-get assets)`, driving `assets` to `u0` and, combined with no pending unrealized interest, `total-assets` to `u0` while `total-supply` remains `> 0`. [6](#0-5) 
3. A new user calls `deposit(amount, u0, recipient)`. `inkind = convert-to-shares-preview(amount) = u0` (since `ts != 0` and `ta == 0`), the slippage check `(>= u0 u0)` passes, `receive-underlying` pulls in real tokens, `assets` increases by `amount`, but `(ft-mint? zft u0 recipient)` mints nothing. [7](#0-6) 
4. Existing holders attempting `redeem` get `inkind = u0` and the call reverts with `ERR-OUTPUT-ZERO`, permanently blocking exit. [8](#0-7) 
5. Since `total-supply` can never reach `u0` (step 4 blocks all redemptions), the vault is permanently stuck minting `u0` shares for all future deposits, freezing all newly deposited principal.
