### Title
Webhook `shop` and `topic` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body when validating the webhook HMAC, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values after a successful HMAC check, breaking the intended binding: `HMAC-verified bytes == raw body only`, but `data acted on by handler == raw body + headers`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then dispatches based on `request.topic` and forwards `request.shop` unchecked into the handler's metadata: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not shop-specific: [4](#0-3) 

Consequence: any merchant who installs the app (an unprivileged party with respect to other tenants of the same app) legitimately receives real webhooks for their own shop, each with a valid `body + HMAC` pair signed with the shared secret. Because `shop-domain` and `topic` are not part of the signed content, that same merchant can resend the identical `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a different tenant's domain (or the `x-shopify-topic` header to a different topic). The HMAC check still passes since it only verifies the body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the spoofed shop/topic: [5](#0-4) 

If a host application uses `data.shop` (as documented/intended) to scope database writes, cache invalidation, or business logic per tenant, this breaks the shop-identity binding and allows one tenant's webhook traffic to be attributed to another tenant.

### Impact Explanation
This crosses a tenant boundary without any credential theft: an attacker with legitimate (their own) app installation can make the library report an arbitrary `shop` value for a webhook payload the app then processes as if it came from that other shop. This matches the Critical "cross-tenant access" impact category, since the gem's own header-parsing/validation logic — not host misuse of an undocumented API — is what fails to bind shop/topic to the HMAC.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the normal case for a public Shopify app). The only prerequisite is that the attacker be a legitimate installer of the app on at least one shop, which is an ordinary unprivileged action, not a leaked credential or admin access. No interception of another tenant's traffic is required — only the attacker's own genuine webhook capture-and-replay with modified headers.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the signable content used by `Request#to_signable_string` (or otherwise cryptographically bind them, e.g., via a per-request signature that covers headers+body), so that `Utils::HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually sent.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers a legitimate webhook (e.g. `orders/create`), capturing the raw body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker POSTs the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [6](#0-5) 
4. `Registry.process` calls the registered handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the payload never originated from that tenant.
