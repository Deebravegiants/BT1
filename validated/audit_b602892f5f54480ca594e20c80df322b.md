### Title
Missing re-entrancy guard in Tron `IntentGatewayV2.placeOrder` allows external token/call hooks to re-enter before escrow accounting is finalized - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron port of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) duplicates the intent-escrow logic of the mainline EVM `IntentGatewayV2` but omits the `nonReentrant` protection that the mainline contract explicitly added. `placeOrder` performs external token transfers (`safeTransferFrom`) and an attacker-controlled `ICallDispatcher.dispatch()` call *before/interleaved with* writing the corresponding escrow accounting (`_orders[commitment][token] += ...`), exactly the same "external interaction before critical state is settled, no re-entrancy guard" pattern flagged in the Pod.sol report.

### Finding Description
`placeOrder` in the Tron contract is declared with no reentrancy modifier: [1](#0-0) . This contrasts with the audited mainline EVM implementation, which inherits `ReentrancyGuardTransient` and marks the equivalent functions `nonReentrant`: [2](#0-1) [3](#0-2) [4](#0-3) .

In the Tron contract's escrow loop, for each declared input token the contract performs the external ERC20 pull and only afterwards increments the escrow ledger for that commitment: [5](#0-4) 

The same interaction/effects ordering issue exists in the predispatch branch, where an attacker-supplied `order.predispatch.call` is dispatched via `ICallDispatcher` — a fully attacker-controlled external call — with escrow bookkeeping performed around/after it: [6](#0-5) .

Because `placeOrder` lacks a re-entrancy guard, any hook-bearing ERC20 (ERC777-style `tokensToSend`/`tokensReceived`, or a malicious "input" token contract) used as an order input can trigger a callback into `msg.sender`'s calling context during `safeTransferFrom`, before the corresponding `_orders[commitment][token] += reducedInputs[i].amount` line executes for that token. From that callback, the attacker can re-enter the gateway (e.g., call `placeOrder`/`cancelOrder` again, or otherwise manipulate shared contract state such as `_nonce`, `_params`, or partially-written escrow for the in-flight order) while the outer call's per-token escrow bookkeeping is still incomplete. This is the same root cause as the Pod.sol report: state-changing bookkeeping is finalized *after* an external, attacker-influenceable call, with no re-entrancy lock to serialize execution.

Note: within the available investigation budget I confirmed the missing guard and the transfer-before-credit ordering in `placeOrder`/predispatch directly from source. I was not able to fully inspect the Tron `fillOrder`/`withdraw` implementations (the file does contain `.call{value...}` and `safeTransfer` sites reachable from `onAccept`/`withdraw`/`cancelOrder`) in this final iteration budget to confirm whether `_filled[commitment]` is set before or after value transfers there, so that portion of the report (whether the fill/withdraw path is separately exploitable) is not verified with the same confidence as `placeOrder`.

### Impact Explanation
`placeOrder` is reachable by any unprivileged user (message dispatcher never involved) — it is a first-class entry point for creating escrowed intents. A successful re-entrancy exploit could corrupt escrow bookkeeping for orders sharing the contract's global state (`_nonce`, `_params`, `_orders`), potentially letting an attacker create escrow records inconsistent with tokens actually held by the contract, or interleave `cancelOrder`/other order lifecycle calls against inconsistent state. This maps to "concrete theft ... of funds" and "unsound state commitment" categories, since the escrow ledger backing solver settlement can be desynchronized from actual custody.

### Likelihood Explanation
Medium-High: the attacker fully controls the order's input token list (can supply a malicious/hookable ERC20 as an input) and, when using predispatch, fully controls the calldata dispatched via `ICallDispatcher`. No special privileges, admin action, or off-chain component is required — a single `placeOrder` transaction from an ordinary EOA/contract triggers the vulnerable code path.

### Recommendation
Add the same `ReentrancyGuardTransient`/`nonReentrant` protection used in the mainline `evm/src/apps/IntentGatewayV2.sol` to the Tron contract's `placeOrder`, `fillOrder`, `cancelOrder`, and `onAccept`/`withdraw` functions, and audit all token-pull loops to follow strict checks-effects-interactions ordering (increment `_orders[commitment][token]` before performing `safeTransferFrom`/native transfers, matching the fix already applied for `_filled[commitment]` in the CEI-fixed same-chain/cross-chain fill functions referenced in `IntrinsicIntentsReentrancyTest.sol`).

### Proof of Concept
1. Deploy a malicious ERC20/ERC777-style token `EvilToken` whose `transferFrom` (invoked via `safeTransferFrom`) calls back into the attacker's contract before returning.
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [EvilToken amount]` (and optionally additional inputs after it in the array).
3. During the `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` call for `EvilToken` [7](#0-6) , before `_orders[commitment][token] += reducedInputs[i].amount` executes for that iteration, the callback re-enters the gateway (e.g., a nested `placeOrder`/`cancelOrder` call) to manipulate shared state (`_nonce`, `_params`, in-flight `_orders` entries) since no `nonReentrant` guard blocks re-entry.
4. Because the mainline EVM contract's dedicated reentrancy test suite (`IntrinsicIntentsReentrancyTest.sol`) demonstrates exactly this class of attack was previously exploitable and required a CEI fix plus `ReentrancyGuardTransient`, and the Tron contract has neither, the same attack class is reproducible against the Tron deployment.
