### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values are taken from plain HTTP headers that are not covered by the signature. Because the HMAC secret (`api_secret_key`) is the app's single shared client secret used for every merchant installation, any unprivileged actor who can obtain one validly-signed `(body, hmac)` pair (e.g., by installing the app on their own free/dev store and observing a webhook delivery to their own endpoint, or via a controlled replay to the app's public webhook route) can resend that exact body/HMAC pair while substituting a different `shop-domain` header. `HmacValidator.validate` will still return `true`, since it only checks the body against the secret, and `Registry#process` will dispatch the payload to the handler as if it originated from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb#L35-L38`), so the equality the HMAC actually proves is:
`HMAC_secret(body) == received_hmac`

But the equality the application *needs* to hold before trusting `data.shop` in the handler is:
`shop_that_produced(body, hmac) == shop-domain header value`

That second equality is never checked anywhere in `Request` or `Registry#process` (`lib/shopify_api/webhooks/registry.rb#L188-L199`). `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from `shopify_header(...)` (`lib/shopify_api/webhooks/request.rb#L20-L23`), i.e. plain, unsigned HTTP header values, and passed directly into `WebhookMetadata` that the host application's handler consumes as trusted, authenticated shop identity:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
Since the app's `api_secret_key` is identical across all shops that install the app (it is not a per-shop key), an attacker who controls one legitimate installation can generate/capture arbitrary numbers of valid `(body, hmac)` pairs for arbitrary topics on their own shop, then reuse them against the app's public webhook endpoint with a forged `shop-domain` header pointing at a victim shop. The signature check succeeds because it never covered the shop field, breaking the intended binding `authenticated_shop == header_shop`.

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys any per-shop side effects, records, or state (order sync, redact/data-request bookkeeping, GDPR mandatory topics, provisioning, billing) off `WebhookMetadata#shop` can be tricked into applying attacker-supplied data/state to a different, victim shop's tenant record, or into believing GDPR/mandatory webhooks came from a shop that never sent them. This matches the "cross-tenant access" class of Critical impact, since the trust boundary between tenants is bypassed using only the capability of an ordinary, unprivileged app installer.

### Likelihood Explanation
Exploitability requires only: (1) installing the target app on an attacker-controlled shop — the normal, unprivileged entry point for any merchant — and (2) capturing one webhook delivery's raw body + `x-shopify-hmac-sha256` header for a topic of interest, which the attacker's own store legitimately receives. No access token, `client_secret`, or privileged account is needed. The remaining work is a header substitution on a replay to the public webhook endpoint, which is squarely reachable by any unprivileged internet user who happens to also be an app installer.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content, or otherwise cryptographically tie the header values to the specific installation before trusting them — for example, include `shop-domain` in `to_signable_string`, or independently verify that `shop` corresponds to a session/access token this app actually issued for that shop before dispatching to `handler.handle`.

### Proof of Concept
1. Install the app on attacker's own shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) on that shop.
2. Capture the POST body and the `x-shopify-hmac-sha256` header Shopify sent to the app's webhook endpoint — this HMAC is valid because it was computed with the app's shared `api_secret_key`.
3. Replay the identical body + `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` as desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` since only `@raw_body` is checked (`lib/shopify_api/utils/hmac_validator.rb#L12-L31`, `lib/shopify_api/webhooks/request.rb#L35-L38`).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload/signature actually originated from the attacker's own shop. [1](#0-0) [2](#0-1) [3](#0-2)
