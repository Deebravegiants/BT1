### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but signs only the raw request body, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` verifies the HMAC and then hands the *unverified* header-derived `shop`, `topic`, and `webhook-id` values straight to the app's webhook handler as the tenant/context identity. Anyone who can present *any* previously-observed valid `(raw_body, hmac)` pair to the app's public webhook endpoint can freely rewrite the `shop-domain` (and other) headers and have the app process the payload as if it came from a different merchant, because those fields are never bound by the signature.

### Finding Description
`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then immediately trusts these header-derived fields to route and populate the handler's tenant context: [4](#0-3) 

This breaks the identity binding: `shop (verified by HMAC) == shop (acted upon by handler)`. In reality only `raw_body (verified by HMAC) == raw_body (used by handler)` holds — the `shop` seen by the handler is never checked against the signature at all.

### Impact Explanation
Because the webhook endpoint is a public HTTP endpoint (it must accept unauthenticated POSTs "from Shopify"), any party who can obtain one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair — e.g., from a webhook Shopify sent for their own store, or from a shop they control installing the app — can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still report `true` because the signature check never looks at the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any handler logic keyed off `data.shop` (looking up per-tenant records, updating per-shop data, granting or revoking entitlements, etc.) will act on the wrong tenant — a cross-tenant data integrity/confidentiality breach driven entirely by this gem's verification primitive.

### Likelihood Explanation
Any unprivileged internet user who can install the app on a shop they control (or who otherwise captures one valid webhook body/HMAC pair for a known event) can mount this attack with a single crafted HTTP request; no access token, secret, or privileged account is required. The only prerequisite is the ability to trigger or observe one legitimate webhook delivery, which is available to any merchant that installs the app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise verify it independently of the caller-supplied header — e.g., have `Registry.process` cross-check `request.shop` against a shop the app is actually expecting for that specific installation/session, and/or extend `to_signable_string` to include the shop domain so header tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs the same body `B` and the same `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unchanged. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body `B`, and performs whatever tenant-scoped action the app implements for that webhook topic against the victim's tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
