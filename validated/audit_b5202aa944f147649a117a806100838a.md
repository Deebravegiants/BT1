### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body (`to_signable_string` returns `@raw_body`). Because the shop-domain header is excluded from the signed material, any actor who can produce or capture one valid `(body, hmac)` pair signed with the app's `api_secret_key` can replay that pair while substituting an arbitrary `shopify-shop-domain` header, and the HMAC check still passes.

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop that produced the HMAC-signed bytes`. In this gem that binding is broken:

- `Registry.process` only requires `Utils::HmacValidator.validate(request)` to be true before dispatching to the handler: `lib/shopify_api/webhooks/registry.rb:188-199`.
- `HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
- For `Webhooks::Request`, `to_signable_string` returns just `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), and `hmac` is derived from the `hmac-sha256` header (`lib/shopify_api/webhooks/request.rb:10-13`). The `shop` value used downstream is read straight from the `shop-domain` header without any cryptographic binding to that HMAC (`lib/shopify_api/webhooks/request.rb:20-23`).
- Since Shopify's app-level `api_secret_key` is the same secret used to sign webhooks for every shop that has the app installed, a merchant/attacker who has the app installed on their own store legitimately receives a valid `(raw_body, hmac-sha256)` pair from Shopify. They can then POST that identical body+HMAC to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`, which is also unsigned) to a victim shop's domain. `Registry.process` accepts it because `HmacValidator.validate` only checks the body bytes, and passes `request.shop` (the attacker-controlled header) into `WebhookMetadata` for the handler: `lib/shopify_api/webhooks/registry.rb:198-199`.
- Any handler that uses `data.shop` to select which tenant's session/access token/database record to act on (a documented and expected usage pattern for this gem) will act on the victim shop's identity using attacker-supplied body content, or attribute attacker data to the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an app whose webhook handler trusts `WebhookMetadata#shop` to select the tenant context can be made to process forged/replayed payloads under a different, victim shop's identity, since only the raw body — not the shop identity — is authenticated. This matches the High-severity class "scope or expiry check bypass" / cross-tenant confusion category, since the check that is supposed to bind the payload to a tenant (HMAC) permissively ignores the tenant-identifying field entirely.

### Likelihood Explanation
Exploitability requires only that the attacker have (or previously had) the target app installed on any shop they control, which is the normal, low-privilege position of any merchant/unprivileged internet user who can install a public app. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only replay of a body+HMAC pair the attacker legitimately received for their own shop, with the mutable header changed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind `shop` to the HMAC before trusting it. Since Shopify's HMAC computation itself is body-only (per Shopify's webhook spec) and can't be changed on Shopify's side, the gem should not expose `request.shop` as trustworthy tenant identity without additional binding — e.g., require callers to cross-check the resolved shop against a shop already known to be authorized (offline session lookup) before acting on the payload, or document/enforce that the `shop` header must never be used as the sole tenant selector without a stored, previously-authenticated session for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint, but rewrites the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   (leaving body `B` and `X-Shopify-Hmac-Sha256: H` unchanged).
3. `Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `to_signable_string` is `B` and `hmac` is `H`; `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) succeeds because it only checks `B` against `H`, never inspecting the shop header.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from the attacker's own shop.
