### Title
Unvalidated route venues let payload-named contracts execute arbitrary token transfers under the caller's auth tree - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
Like the LAM regex that failed to restrict which files could land in a web-accessible directory, the router's instruction decoder validates the *shape* of a route (chained tokens, split weights, amounts) but never validates *which contracts* the route names. Every hop's `pool` address comes straight from the attacker-influenced `assets` registry in `StrategyPayload`, and `dispatch_hop` invokes it as a venue. Because venue calls happen inside the `sender`'s `require_auth` tree, a malicious "pool" contract placed on a route runs with the caller's authorization context and can issue `token.transfer(victim, attacker, amount)` for any token the victim holds — far beyond the `amount_in` the caller intended to spend. The measured input/output checks in `dispatch_hop` bound only the routed tokens; they do not bound what the invoked contract does inside the auth tree.

### Finding Description
`execute_op` builds each `SwapHop` directly from payload indices with no allowlist or venue-identity check: `pool: ctx.assets.get_unchecked(op.idx_a)` [1](#0-0) . `dispatch_hop` then calls the venue adapter against that arbitrary address and only asserts the router's own balance deltas (`spent == amount_in`, `received > 0`) [2](#0-1) . On the composed path, the controller strategy calls `router.execute_strategy(&controller, &amount_in, swap)` after authorizing exactly one input transfer [3](#0-2) , but the end user's auth tree still covers nested children invoked by contracts named in the payload — the threat model itself notes "a route can put third-party code on the call stack below the caller's authorization" and that the loss "is the caller's wallet, not the routed amount" [4](#0-3) . The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool.swap()` that runs `token.transfer(&victim, &to, &amount)` on an unrelated wallet token inside a `swap_collateral` route [5](#0-4) .

### Impact Explanation
Theft of user funds. A crafted `routeXdr` delivered to a victim — through `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or direct `execute_strategy` — can name an attacker contract that transfers any of the victim's tokens to the attacker, while still returning a fair swap output so `SlippageExceeded`, `NoSwapOutput`, and the final health-factor gate all pass. Loss is unbounded by `amount_in` or `min_out`.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign/simulate a transaction whose auth tree includes the rogue child entry; a non-inspecting wallet or a quote response that is signed without decoding the route enables it. No privilege, key leak, or oracle manipulation is needed — the attacker only needs to get a crafted payload to a user (phished quote, malicious frontend, or doctored `routeXdr`), which the allowed threat surface ("own swap route", unallowlisted venues) explicitly contemplates.

### Recommendation
Maintain an on-chain venue/pool allowlist (or venue-pool registry) checked in `execute_op` before `dispatch_hop`, analogous to how the LAM fix tightened the filename check; alternatively, have the venue adapters verify the called contract's Wasm hash or a registered pool id rather than trusting the payload-supplied `pool` address. At minimum, reject any route whose execution produces auth-tree children beyond the single expected input transfer.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: it registers `UnlistedPoolRouter`/`RogueHopPool`, builds a route via `route_through_pool_stealing(amount)` naming the rogue pool, and calls `try_swap_collateral` as Alice — the rogue pool's `swap` transfers `amount` of Alice's unrelated `wallet_token` to the attacker inside her auth tree while the swap still returns `FAIR_OUT_ETH` [6](#0-5) .
