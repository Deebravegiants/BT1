### Title
Webhook `shop` (and `topic`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC computed over it does not bind the `shopify-shop-domain` (or `shopify-topic`) header to the signed payload. Any unprivileged holder of a valid webhook delivery (which they can legitimately obtain for their own shop) can replay the same body/HMAC pair while swapping the `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will happily attribute the payload to the spoofed shop.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` and `topic` are read straight from HTTP headers that are *not* part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates only that the HMAC matches the raw body via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (taken from the unauthenticated header) straight into the handler as the tenant identity: [4](#0-3) 

`HmacValidator.validate_signature` recomputes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it to the header value — it never mixes in `shop` or `topic`: [5](#0-4) 

This breaks the intended identity binding:
`HMAC-verified(body) == body-that-is-signed`, but the code treats it as if `HMAC-verified(body) == (body, shop, topic)-that-is-signed`. Concretely: `hmac_valid(raw_body) ∧ shop_header == "victim.myshopify.com"` is accepted even though the HMAC never covered `shop_header`.

### Impact Explanation
Any merchant who installs the app (an ordinary, unprivileged app user with respect to other tenants) legitimately receives real webhook deliveries for their own store, each with a body and a correctly computed `hmac-sha256` header (computed by Shopify using the app's secret — the attacker never needs to know the secret, only to capture one legitimate delivery to their own store). That attacker can replay the exact same `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` constructs `WebhookMetadata` with the attacker-chosen `shop`, causing the app's webhook handler to process/persist data as if it belonged to the victim tenant. This is a cross-tenant boundary violation — a merchant on the platform can cause the app to associate crafted webhook content (order data, customer data, etc., subject to what the given topic's payload contains) with a different merchant's tenant record, without ever needing the app's `client_secret` or any elevated privilege.

### Likelihood Explanation
Exploitation only requires: (1) being a legitimate/free installer of the target app (a normal unprivileged action for any Shopify merchant/developer), (2) capturing one webhook delivery for a topic whose body content is attacker-influenceable or whose spoofed attribution is damaging on its own (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`), and (3) POSTing the captured body/HMAC pair with a different `shop-domain` header to the app's public webhook URL. No cryptographic secret, session, or token theft is required, making this readily exploitable by any determined unprivileged user.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or independently authenticate the shop identity before trusting the header — e.g., have `to_signable_string` incorporate the shop domain header (matching how Shopify actually signs webhooks, where the shop is not independently derivable from the signature) is not sufficient by itself since Shopify's real signature never covers the header either; instead, the gem/host application should cross-check `request.shop` against a shop that the app already knows installed the app with the given `webhook_id`/topic combination (e.g., verify the shop is registered/expected for that specific webhook registration) before acting on the payload, rather than trusting the header value as an authenticated tenant identifier.

### Proof of Concept
1. Merchant "attacker.myshopify.com" installs the target Shopify app and triggers a webhook (e.g., `shop/update`) for their own store; the app's endpoint receives:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: shop/update`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`
   - Body: `{"id":..., "name": "Attacker Shop", ...}`
2. Attacker replays the identical raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only re-hashes `raw_body`. [6](#0-5) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "shop/update", body: <attacker-crafted parsed body>, ...)`, causing the app to process attacker-controlled webhook data under the victim tenant's identity.
