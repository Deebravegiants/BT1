## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`File: lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values are read straight from unauthenticated HTTP headers. `Registry.process` validates only that the HMAC over the body matches, then forwards the header-derived `shop` value unchanged to the host application's webhook handler via `WebhookMetadata`. Any caller able to produce (or replay) a body/HMAC pair valid for the shared `api_secret_key` can attach an arbitrary `shop-domain` header, and the app has no way to detect the mismatch.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from headers, none of which participate in the signed content: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the body, never against `shop`: [3](#0-2) 

`Registry.process` performs exactly that check and then immediately trusts `request.shop` (and the other header fields) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation before being handed to the host app's `WebhookHandler#handle`: [5](#0-4) 

The broken identity binding is:
`shop authenticated by the HMAC-signed payload` ≠ `shop attributed to the webhook data (WebhookMetadata#shop)`

Because the app's `api_secret_key` is the same for every shop the app serves (it is not a per-shop secret), the HMAC over a given body is identical regardless of which shop that body is claimed to belong to. Any actor who can obtain one valid `(body, hmac)` pair — e.g., an unprivileged merchant who has installed the app on their own shop and therefore legitimately receives real Shopify webhooks with valid HMACs for their own shop — can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the `shop` header, and `Registry.process` will dispatch the payload to the handler labeled with the attacker-chosen shop.

### Impact Explanation
This crosses a tenant boundary: data or state-changing side effects that a merchant-facing app associates with "the shop in the webhook" (e.g., updating billing state, order records, redact/GDPR handling, inventory sync) can be attributed to a shop the requester does not own, using only a webhook payload the requester was legitimately sent for their own store. This is a cross-tenant data/identity confusion issue reachable by any unprivileged internet user who has (or can obtain) one legitimately-signed webhook body — no access token, `client_secret`, or privileged account is required, only knowledge of a single previously-received, validly-HMAC'd webhook payload for their own installation.

### Likelihood Explanation
Likelihood is high for any app that (a) exposes its webhook endpoint publicly (required for webhook delivery) and (b) uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to key state changes, as the gem's own documented pattern instructs host apps to do. The only prerequisite — possessing one valid signed webhook body for an owned shop — is trivially satisfied by installing the app once.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed content, or otherwise cryptographically tie them to the signature, so that `HmacValidator.validate` fails if any of these attributes are altered independent of the body. At minimum, `Request#to_signable_string` should incorporate the `shop-domain` header (and other identity-bearing headers) rather than the body alone, and `Registry.process` should reject requests where the declared `shop` cannot be proven consistent with the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's public webhook endpoint; attacker captures the raw body `B` and the `x-shopify-hmac-sha256` header `H` (valid because `H = HMAC-SHA256(api_secret_key, B)`, and `api_secret_key` is shared across all shops served by the app).
2. Attacker sends a new POST to the same public webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256` = `H` (unchanged)
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`, `x-shopify-webhook-id` optionally altered too.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation passes.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the host app's `handler.handle(data:)`, causing the app to process attacker-controlled order data as if it belongs to `victim-shop.myshopify.com`.
