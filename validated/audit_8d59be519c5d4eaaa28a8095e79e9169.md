### Title
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to an unsanitized `shop` host, unlike every other credential-issuing flow in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the `null_session` that is used to POST the app's `client_id`/`client_secret` from the raw, un-sanitized `auth_query.shop` value [1](#0-0) . Every other credential-issuing code path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive the `client_secret` [2](#0-1) [3](#0-2) . `validate_auth_callback` is the one exception.

### Finding Description
`HttpClient#initialize` builds the outgoing request host directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) . This means whatever string ends up in `session.shop` is exactly the host that receives the POST body containing `client_id`/`client_secret` in the OAuth token exchange.

In `validate_auth_callback`, that string comes straight from `auth_query.shop`, which is only checked for HMAC integrity (`Utils::HmacValidator.validate(auth_query)`) — never checked against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [5](#0-4) . The HMAC only proves that whatever `shop` value was present in the request is unmodified relative to what was signed with `api_secret_key` — it does not enforce that the value is a well-formed, in-scope Shopify shop domain (e.g. `*.myshopify.com`).

Contrast this with the parallel flows that also send the `client_secret`:
- `ClientCredentials.client_credentials` — calls `Utils::ShopValidator.sanitize!(shop)` and raises `Errors::InvalidShopError` for non-Shopify domains (proven by `test_client_credentials_rejects_non_shopify_domain` sending `"attacker.example"`) [6](#0-5) [2](#0-1) .
- `RefreshToken.refresh_access_token` — same sanitize! call before building `shop_session` [3](#0-2) .
- `TokenExchange.migrate_to_expiring_token` — same pattern [7](#0-6) .
- `TokenExchange.exchange_token` — derives `shop` from the JWT `dest` claim, itself HMAC-signed by Shopify's own `api_secret_key` and bound to the app via the `aud` claim check [8](#0-7) , i.e. a different, stronger binding than a raw callback query field.

Only `validate_auth_callback` (the classic authorization-code-grant callback, invoked with attacker-influenced browser query-string data) skips this sanitize step, breaking the intended invariant: *"the shop that is cryptographically bound to the callback request" == "the shop domain that the library will treat as an authoritative Shopify host and hand the app's `client_secret` to."*

### Impact Explanation
This maps to the class of bug in the referenced report ("field acted on but not covered by the identity-binding check"): the `shop` field is only integrity-checked (HMAC), not authorization/format-checked (`TRUSTED_SHOPIFY_DOMAINS`), before being used as the destination host for the app's `client_secret`. If it were possible to obtain any Shopify-produced HMAC-valid callback whose `shop` field is not restricted to `*.myshopify.com`/`myshopify.io`/`shopify.com`/`spin.dev`/`shop.dev` (e.g., through custom/primary domain aliasing accepted by Shopify's authorize endpoint but not modeled by this gem's `ShopValidator`), the missing sanitize! step is what stands between that value and an outbound request carrying the app's `client_secret`. This would be a High/Critical-severity issue (leakage of the app's `client_secret`) if such a value can be produced.

### Likelihood Explanation
Exploitability is **not proven** with certainty from static analysis alone: `Utils::HmacValidator.validate` still requires the query to be signed with `Context.api_secret_key` [9](#0-8) , which only Shopify (or the app) possesses. An attacker without the secret cannot forge an arbitrary `shop` value with a valid HMAC by themselves. The remaining question — whether Shopify's own OAuth authorize/callback infrastructure can ever be induced to sign a callback whose `shop` value falls outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (e.g. via a shop's custom/primary domain, or via the unified-admin path handled specially in `ShopValidator.sanitize_shop_domain` but not in `validate_auth_callback`) — is a question about Shopify's server-side behavior, which is outside this gem and cannot be confirmed from the code alone. Given the in-scope rule set explicitly treats "host validated vs. host receiving `client_secret`" mismatches as a valid analog class, and given the demonstrable, unexplained inconsistency versus three sibling flows that do sanitize the same field before the same operation, this is flagged as Medium-likelihood/High-impact: the missing defense-in-depth check is real and verifiable in code, but full exploitability requires an as-yet-unconfirmed way to obtain a validly-signed callback for a non-canonical shop host.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`), call `Utils::ShopValidator.sanitize!(auth_query.shop)` (as already done in `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`) and use the sanitized value to build `null_session` and the subsequent `Session.from(shop: ...)`, before any request carrying `client_id`/`client_secret` is issued. Apply the same sanitize! call in `Oauth.begin_auth` for the pre-auth `shop` parameter to remove the equivalent open-redirect-style gap at the start of the flow.

### Proof of Concept
Not independently reproducible from this gem's code alone — reproduction would require demonstrating that Shopify's OAuth server can be made to produce a valid `hmac`-signed callback for a `shop` value outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, which cannot be verified without access to Shopify's live infrastructure. The code-level evidence supporting the finding is the direct comparison between:
- `lib/shopify_api/auth/oauth.rb` lines 60–81 (no `ShopValidator.sanitize!` call before building the `client_secret`-carrying request), and
- `lib/shopify_api/auth/client_credentials.rb` lines 25–26 / `lib/shopify_api/auth/refresh_token.rb` lines 24–25 / `lib/shopify_api/auth/token_exchange.rb` lines 103–104 (which all call `ShopValidator.sanitize!` before the identical operation).

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
