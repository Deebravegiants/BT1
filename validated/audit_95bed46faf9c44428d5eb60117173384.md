Confirmed. In the Tron `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`), `_orders[commitment][token]` is credited with the caller-supplied/nominal amount (`reducedInputs[i].amount`, derived from `order.inputs[i].amount` before the transfer), while the actual token movement uses a plain `safeTransferFrom` for the nominal amount without checking the balance actually received. This is unlike the primary EVM `IntentGatewayV2.sol`, which explicitly patches this exact bug class by measuring `balanceOf` before/after each transfer.

### Title
Escrow accounting is credited with the nominal transferred amount instead of actual received balance for fee-on-transfer tokens, causing insolvent escrow entries - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` on the Tron `IntentGatewayV2` computes the escrow credit and order commitment from the caller-specified `order.inputs[i].amount` and simply calls `safeTransferFrom` for that amount, without verifying how many tokens the contract actually received [1](#0-0) . For a fee-on-transfer (deflationary) ERC-20, the balance the gateway actually gains after `safeTransferFrom` is less than `order.inputs[i].amount`, but `_orders[commitment][token]` is nonetheless incremented by the full `reducedInputs[i].amount` computed from the nominal amount [2](#0-1) .

### Finding Description
`placeOrder` first computes `reducedInputs` (nominal amount minus protocol fee) and hashes `commitment = keccak256(abi.encode(order))` using these nominal, pre-transfer amounts [3](#0-2) . It then performs the token transfer with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and immediately credits `_orders[commitment][token] += reducedInputs[i].amount` without ever measuring `balanceOf(address(this))` before/after the transfer [1](#0-0) .

This is precisely the same class of bug as the CollateralManager report: for any token that deducts a fee on transfer, the contract's actual token balance is strictly less than what it just credited in its internal accounting. The sibling, main `evm/src/apps/IntentGatewayV2.sol` explicitly guards against this by snapshotting `balanceOf` before and after every `safeTransferFrom` and rewriting `order.inputs[i].amount` to the actually-received delta before computing the commitment/escrow [4](#0-3) , and this is covered by dedicated fee-on-transfer tests [5](#0-4) . The Tron variant lacks this protection entirely.

### Impact Explanation
`_orders[commitment][token]` becomes an IOU for more tokens than the contract actually holds. When the order is later filled and redeemed (same-chain via `cancelOrder`/`withdraw`, or cross-chain via the `RedeemEscrow`/`RefundEscrow` request handled in `onAccept` → `withdraw`), the contract attempts to `transfer` the full escrowed `amount` to the beneficiary/solver [6](#0-5) . Because the gateway's real balance of that token is short by the transfer-fee amount on every deposit, the contract becomes structurally insolvent for that token: withdrawals either revert (fund freezing, DoS on that route) once the shortfall is exhausted, or — because balances of the same token are shared across all outstanding orders — earlier withdrawers can drain the pool using accounting credits that were never fully backed by real tokens, at the expense of later depositors/solvers whose escrow entries can no longer be honored (loss of funds for those users).

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with a fee-on-transfer token as an input asset; no special permissions are required, and the deployer/owner of the Tron gateway has no control over which ERC-20 a user selects as collateral/input. Fee-on-transfer and deflationary tokens are common and widely used in DeFi (e.g., reflection tokens, tokens with built-in burn-on-transfer), making this readily triggerable in a single transaction.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: record `balanceOf(address(this))` before and after each `safeTransferFrom` in `placeOrder`, use the actual received delta to mutate `order.inputs[i].amount` before computing `protocolFee`/`reducedInputs` and the `commitment` hash, and credit `_orders[commitment][token]` only with the actually-received (post-transfer-fee) amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 (e.g., 1% fee) and approve the Tron `IntentGatewayV2` for `1000e18`.
2. Call `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}`. The contract's real FOT balance increases by only `990e18`, but `_orders[commitment][FOT]` is credited with `1000e18` (or `1000e18` minus protocol fee) per lines 356–469.
3. Repeat with additional orders using the same FOT token to accumulate multiple escrow entries that collectively exceed the gateway's actual FOT balance.
4. Trigger redemption (`withdraw`) for the earliest orders — they succeed, consuming the limited real balance.
5. Attempt redemption for later orders on the same token — the `token.call(...transfer...)` either reverts due to insufficient balance (frozen funds) or, in a partial-liquidity scenario, silently returns `false`/reverts, permanently blocking that beneficiary's promised payout despite `_orders[commitment][token]` showing a nonzero, "valid" balance.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
