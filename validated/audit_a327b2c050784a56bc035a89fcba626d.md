This is a genuine finding: the webhook `shop` (`shop-domain`) field used to route/attribute the webhook is not covered by the HMAC signature, which is computed only over the raw body.

### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `topic`, `shop`, `api_version`, and `webhook_id` values that are handed to the app's webhook handler from HTTP headers, while `to_signable_string` (the value protected by the HMAC in `Utils::HmacValidator`) is only the raw request body. This breaks the binding: `HMAC_valid(body) == true` is treated as proof that `(topic, shop, webhook_id)` are also authentic, but those header values are never included in the signed material.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`: [1](#0-0) 
`to_signable_string` returns only `@raw_body`: [2](#0-1) 
Meanwhile `shop`, `topic`, and `webhook_id`, which are passed straight into the app's handler as `WebhookMetadata`, are read from headers (`shopify-shop-domain` / `x-shopify-shop-domain`, etc.), not from the signed body: [3](#0-2) [4](#0-3) 

The HMAC only guarantees `hexdigest(secret, raw_body) == received_hmac`; it says nothing about which shop sent the request, because the shop domain never enters the signed string.

### Impact Explanation
If a merchant/attacker who legitimately controls one shop can replay (or otherwise obtain) a validly-signed webhook body for that shop, and the host application forwards or otherwise allows header manipulation before this gem processes it (e.g., a reverse proxy, or if the app itself constructs `headers` from data it doesn't fully control), the `shop` value consumed by `WebhookMetadata` and subsequently used to look up the shop's session/tenant data can be substituted while the HMAC signature still validates. This yields cross-tenant confusion in the webhook handler: the request appears cryptographically authentic for shop B, while its content actually originated (and was signed) for shop A. Given the identity-binding rule in scope (the field acted upon — `shop` — is not covered by the HMAC), this satisfies the "cross-tenant access" bar.

### Likelihood Explanation
Exploitability strictly depends on an attacker's ability to influence the `headers` hash that the host application passes into `Webhooks::Request.new`, independent of the signed body — this gem does not fetch headers itself; it trusts whatever `headers:` the caller supplies. Within this gem's own code there is no additional cross-check (e.g., verifying `shop` against the session, or including it in the signable string) to catch a mismatch, so any caller path that lets header values diverge from the body's originating shop is silently accepted as long as the raw body's HMAC matches.

### Recommendation
Include the shop-identifying header (and topic/webhook-id) as part of the signed material verified against the HMAC, or independently verify that the `shop-domain` header corresponds to a shop consistent with the session/API key context before dispatching to `handler.handle`. At minimum, document/require that the host framework must not allow header values to be set from anything other than the verified Shopify request.

### Proof of Concept
1. Capture (or have knowledge of) a legitimately-signed webhook payload/HMAC pair issued by Shopify for `shop-a.myshopify.com`.
2. Construct a request to the app's webhook endpoint with the same raw body and `X-Shopify-Hmac-Sha256` value (so `HmacValidator.validate` passes), but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` → true (body/HMAC match), then dispatches `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...))`.
4. The app's handler processes shop-A's signed data under shop-B's identity, since `lib/shopify_api/webhooks/request.rb` never binds `shop` into the signed string.
