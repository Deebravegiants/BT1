### Title
Webhook `shop-domain` Header Not Bound by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated once `Utils::HmacValidator.validate(request)` returns true, then hands the caller-controlled `shop` header straight to the app's handler as trusted tenant identity. The HMAC, however, is computed over the raw body only — it never covers the `shop-domain` header — so an attacker who possesses any valid `(body, hmac)` pair for the app's shared `client_secret` can relabel that payload with an arbitrary shop domain and have it accepted as a genuine webhook for a different tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read verbatim from attacker-controllable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` signs and compares only `verifiable_query.to_signable_string`, i.e. the raw body, against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` uses this single boolean as the sole gate for authenticity and then forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is what host applications use to resolve which tenant's data/session the payload belongs to: [4](#0-3) 

Because `Context.api_secret_key` is a single, app-wide secret shared by every shop that installs the app (not a per-shop secret), any unprivileged user who installs the same public app on their own store can capture a legitimately signed webhook body/HMAC pair delivered to their own endpoint, then replay that exact body+HMAC to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header (or `shopify-shop-domain`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` dispatches the handler with `data.shop` set to the attacker-chosen victim domain — breaking the equality `shop authenticated by HMAC == shop delivered to the handler`.

### Impact Explanation
This crosses a tenant boundary: the gem asserts webhook authenticity (raising `Errors::InvalidWebhookError` otherwise) but delivers a `shop` value that was never actually verified. Any host application that keys per-tenant behavior (e.g., looking up stored offline access tokens, updating shop-scoped records, honoring `shop/redact`/`customers/redact` GDPR mandatory webhooks, cache invalidation, billing state) off `WebhookMetadata#shop` can be tricked into acting on/for the wrong shop using attacker-supplied body content, which is a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a store they control — a normal unprivileged capability for any public Shopify app — to obtain one valid `(body, hmac)` pair signed with the app's shared secret, and then send a normal HTTP POST with a modified `shop-domain` header to the target app's webhook endpoint. No access token, session, or `client_secret` knowledge is required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed body, e.g. by including it in `to_signable_string`, or by requiring the caller to independently corroborate `request.shop` against a shop known to be associated with the specific access grant/session before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimate webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the exact same request to the app's public webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but rewriting `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and finds it equal to `H` — validation passes [5](#0-4) .
4. `Registry.process` dispatches the registered handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` is `"victim.myshopify.com"` [6](#0-5) , causing the host app to process attacker-controlled data as if it originated from `victim.myshopify.com`.
