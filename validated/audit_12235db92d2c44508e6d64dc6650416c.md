### Title
Escrow over-crediting for fee-on-transfer/deflationary tokens in Tron `IntentGatewayV2.placeOrder` causes insolvent escrow and fund loss - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2` never adopted the fee-on-transfer/received-balance verification that the main EVM `IntentGatewayV2` implements. In the non-predispatch path of `placeOrder`, it credits the escrow ledger with the user-requested (minus protocol-fee) amount instead of the amount actually received by the contract, so any deflationary/fee-on-transfer/rebasing ERC20 used as an order input creates a permanent shortfall between recorded escrow liabilities and the contract's real token balance.

### Finding Description
In the reference (patched) EVM contract, `placeOrder` measures the actual balance delta from `safeTransferFrom` and mutates `order.inputs[i].amount` to the real received amount before computing the commitment and crediting escrow: [1](#0-0) 

The Tron variant computes `commitment`/`reducedInputs` first (based purely on the caller-supplied `order.inputs[i].amount` minus protocol fee), and only afterward performs the token transfer in the "no predispatch" branch with **no balance check whatsoever**: [2](#0-1) 

For fee-on-transfer or rebasing tokens, `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` will deposit less than `order.inputs[i].amount` into the gateway, yet `_orders[commitment][token] += reducedInputs[i].amount` records the full pre-fee (or pre-deflation) amount as owed. The gateway's internal accounting (`_orders` mapping) therefore overstates the tokens it actually custodies. Even the predispatch branch, while it re-measures the dispatcher's post-call balance and reverts if it's below the required amount, still commits the fixed `reducedInputs[i].amount` (not the swept `balance`) into escrow, so any downward drift between the balance check and the escrow write is not reconciled the way the main EVM contract's Phase-1 "received" recalculation does: [3](#0-2) 

This directly matches the external report's root cause: storing a "spot" nominal amount instead of verifying actual transferred/held balance for tokens whose balance can silently deviate (fee-on-transfer, rebasing, variable-balance).

### Impact Explanation
Because escrow bookkeeping (`_orders[commitment][token]`) can exceed the contract's real token holdings:
- On `RedeemEscrow` settlement or `cancelOrder`/`RefundEscrow` withdrawal, the contract will attempt to pay out the recorded (inflated) amount via `withdraw(...)`, which draws from the shared token balance of the whole contract, not a per-order escrow. This means the shortfall from one fee-on-transfer order silently drains balance backing other users' legitimate orders.
- As shortfalls accumulate, later orders' withdrawals can revert (insufficient balance) — a **permanent freezing of funds** for solvent order participants — or, if partial fills/other orders subsidize the gap, other users lose funds to cover the deficit. Both are Medium/High-severity fund-safety issues per the escrow model in `cancelOrder`/`withdraw`: [4](#0-3) 

### Likelihood Explanation
Any unprivileged user can place an order with a fee-on-transfer, deflationary, or rebasing ERC20 as an input token via `placeOrder` — no special permissions or predispatch call are required to hit the vulnerable branch (lines 450-469). The main EVM gateway's own test suite already demonstrates this is an actively-tested and expected token class (`FeeOnTransferToken`), confirming it's a realistic asset category the protocol must support: [5](#0-4) 
The Tron contract is a near-verbatim copy of the same `IntentGatewayV2` app missing only this fix, so likelihood of reachability is high wherever the Tron contracts are deployed and such tokens are listed as allowed inputs.

### Recommendation
Port the same balance-before/after measurement used in `evm/src/apps/IntentGatewayV2.sol` (lines 312-323, and the predispatch sweep logic at lines 260-311) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, mutate `order.inputs[i].amount` to the actually-received amount, and derive `commitment`/`reducedInputs`/escrow credit from that verified amount rather than the caller-supplied nominal amount.

### Proof of Concept
1. Attacker/user deploys or selects an existing fee-on-transfer/deflationary ERC20 `T` (or a rebasing token whose balance can drop after deposit) as an order input.
2. User calls `IntentGatewayV2.placeOrder` (Tron) with `order.inputs[0] = {token: T, amount: 1000}` and no predispatch call.
3. `placeOrder` computes `reducedInputs[0].amount = 1000 - protocolFee` and `commitment` before any transfer: [6](#0-5) 
4. The transfer executes `IERC20(T).safeTransferFrom(msg.sender, address(this), 1000)`, but due to T's fee-on-transfer logic the gateway only receives, e.g., 990 tokens.
5. The gateway nonetheless sets `_orders[commitment][T] += reducedInputs[0].amount` (based on 1000), overstating the escrow liability by the fee amount: [2](#0-1) 
6. When a solver fills the order and redeems escrow, or the user cancels and withdraws, the contract attempts to pay out the recorded (inflated) amount, depleting balance that belongs to other outstanding orders, eventually causing withdrawal failures (fund freezing) or fund loss for other order holders.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
