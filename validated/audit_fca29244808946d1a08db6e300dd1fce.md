### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC, allowing cross-tenant spoofing of webhook origin - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers when building the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the body bytes were HMAC-signed with the app's `api_secret_key` [2](#0-1) . It never verifies the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, which are read directly and unauthenticated via `shopify_header` [3](#0-2) .

`Registry.process` uses exactly this unauthenticated `request.shop` (and `request.topic`) to build the `WebhookMetadata` delivered to the app-supplied handler, right after the body-only HMAC check succeeds: [4](#0-3) 

The `api_secret_key` used for signing is a single app-level secret, identical for every shop that has installed the app — it is not shop-specific. Consequently, an attacker who controls one shop where the app is installed and legitimately receives a validly-signed webhook (raw_body + hmac) can replay that same body/hmac pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. The HMAC check still passes because it only covers the body, so `Registry.process` will invoke the merchant's handler with `WebhookMetadata#shop` claiming to be the victim shop while the body content is fully attacker-controlled.

The binding that is broken is: **shop-domain header (used to route/attribute the webhook) == shop that actually produced/owns the HMAC-covered bytes**. The library treats these as equivalent by construction (both are only checked against the app-level secret), but they are not bound to each other cryptographically.

### Impact Explanation
Any downstream app logic that uses `WebhookMetadata#shop` to select a tenant record, look up a `ShopifyAPI::Auth::Session`, or otherwise scope processing to "the shop the webhook is for" can be tricked into applying attacker-supplied webhook body data under a victim shop's identity — a cross-tenant data-confusion/injection primitive reachable by any unprivileged attacker who can install the app on their own store (a normal, unprivileged action) and send one HTTP POST to the app's webhook endpoint. This satisfies the "cross-tenant access" criterion, since the merchant's own multi-tenant app is misled about the origin shop of otherwise-genuinely-signed data.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-owned Shopify store (an unprivileged action available to anyone), (2) capturing one legitimate webhook body+HMAC for the attacker's own shop, and (3) sending a forged HTTP request to the app's public webhook callback URL with a spoofed `shop-domain` header. No access token, `client_secret`, or privileged account is required, making this readily reachable by an unprivileged internet user.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used by `HmacValidator`, or otherwise cryptographically bind the `shop` field to the signed payload before it is handed to `WebhookHandler#handle`. At minimum, the library should document (and ideally enforce) that `WebhookMetadata#shop` must be cross-checked by the host application against a shop derived from an authenticated source (e.g., matching a `shop` field embedded within the JSON body from Shopify) rather than trusted purely from the HTTP header.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there,
# so they legitimately receive a validly-signed webhook:
raw_body = '{"id": 123, "note": "hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker replays the same body/hmac but swaps the shop header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, not bound to HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

ShopifyAPI::Webhooks::Registry.process(
  ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
)
# -> HMAC validation succeeds (it only checks raw_body against api_secret_key),
#    and the app's handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker JSON, ...)
