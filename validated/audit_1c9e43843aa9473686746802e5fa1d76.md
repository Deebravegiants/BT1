### Title
Unbounded in-memory `BidCache` growth from mempool `place_bid` extrinsics enables node-level resource exhaustion - (File: modules/pallets/intents-coprocessor/rpc/src/lib.rs)

### Summary
`pallet-intents-coprocessor`'s RPC bid-discovery service maintains an in-memory `BidCache` (`HashMap<H256, OrderBids>`) that is populated purely from transactions observed in the node's transaction pool, with no cap on the number of distinct order commitments or bids it can hold, and eviction driven only by a periodic TTL sweep. This mirrors the CVE-2026-66257 bug class (unbounded value caching from untrusted/low-cost input leading to resource exhaustion) but reachable via any account able to get a signed `place_bid` extrinsic into the ready transaction pool.

### Finding Description
`run_bid_watcher` subscribes to `pool.import_notification_stream()` and, for every transaction that becomes "ready," decodes it looking for a `pallet_intents_coprocessor::Call::place_bid` call via `extract_bid`: [1](#0-0) 

Every matching bid is unconditionally inserted into `BidCache`: [2](#0-1) 

`BidCache` is a plain `HashMap<H256, OrderBids>` with no maximum key count, no maximum entries-per-commitment limit, and no bound on the size of the cached `user_op`/`filler` byte vectors: [3](#0-2) 

The only eviction mechanism is a periodic timer (`cleanup_interval`) that calls `remove_expired`, which drops an entire `OrderBids` group only once its `first_seen` timestamp is older than `ttl`: [4](#0-3) 

Because `first_seen` is fixed at first insertion and never refreshed, an attacker can trivially defeat this window by using a *new, unique* `commitment` value on every submitted `place_bid` extrinsic — the on-chain call does not need to correspond to a real/valid order for the extrinsic to be accepted into the transaction pool as "ready" (pool-level validation only checks signature/nonce/fee, not intents-pallet business logic such as order existence). I found no `MaxBidSize`/`MaxUserOpSize`/`BoundedVec` type constraining `user_op` size in the pallet, so each entry can also carry a large arbitrary-length `user_op` payload up to the extrinsic size limit.

This means: within any single TTL window, the number of `OrderBids` entries (and their total byte footprint) is bounded only by how many distinct-commitment `place_bid` transactions an attacker can get accepted into the ready pool during that window — not by any application-level cap. A well-funded or Sybil'd attacker (cheap, low-balance throwaway accounts each submitting one valid signed transaction) can flood the cache with unique commitments faster than the TTL sweep reclaims memory, growing the structure without bound and exhausting the collator/RPC node's memory — a classic unbounded pre-verification caching resource-exhaustion pattern, matching the reported bug class.

### Impact Explanation
Uncontrolled memory growth in the RPC-serving node process (`IntentsRpcHandler`) can degrade or crash the node hosting the intents bid-discovery service, denying legitimate solvers/fillers timely access to mempool bid data and potentially destabilizing the node process serving other RPC/consensus duties (denial of service). This falls under "route unable to deliver messages"/service-availability impact for the intents/bid-discovery path explicitly listed as in-scope ("intents escrow and bids").

### Likelihood Explanation
Medium-High: exploitation only requires the ability to get valid signed extrinsics with a `place_bid` call into the node's ready transaction pool — this does not require the referenced order to exist, nor deep pockets beyond minimal transaction fees per throwaway account, and can be automated to generate a high volume of unique commitments in a short time before the periodic TTL cleanup runs.

### Recommendation
- Enforce a hard cap on the total number of tracked commitments and/or bids per commitment in `BidCache` (e.g., bounded LRU eviction on insert, not just periodic TTL sweep).
- Refresh or independently track per-bid insertion times so an attacker cannot bypass TTL eviction by only varying the commitment key, and bound total cache memory (sum of `user_op`/`filler` sizes).
- Validate that `commitment` corresponds to a real, currently-open order before caching a bid (cheap runtime storage lookup) so unrelated/garbage commitments cannot be cached at all.
- Consider bounding `user_op` size at the pallet/extrinsic level to limit per-entry memory cost.

### Proof of Concept
1. Generate N throwaway signed accounts, each funded with only the minimum balance to pay one transaction fee.
2. From each account, submit a `place_bid(commitment, user_op)` extrinsic where `commitment` is a freshly-random `H256` not tied to any real order, and `user_op` is a maximally-sized byte blob.
3. Each extrinsic passes standard pool validation (valid signature, nonce, fee) and becomes "ready," triggering `run_bid_watcher` to call `bid_cache.insert(commitment, filler, user_op)`, creating a new, permanent-until-TTL `OrderBids` entry.
4. Repeat rapidly with new commitments faster than `cleanup_interval`/`ttl` reclaims old entries; observe `BidCache`'s `HashMap` and resident memory of the RPC node process grow unbounded.

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
