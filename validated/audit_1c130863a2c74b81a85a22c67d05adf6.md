### Title
Webhook HMAC only signs the body, allowing shop-domain header spoofing for cross-tenant webhook confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` value used downstream as the tenant identifier comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the HMAC computation [2](#0-1) . `Registry.process` forwards this unauthenticated header value straight into `WebhookMetadata` handed to the app's handler [3](#0-2) .

### Finding Description
The intended identity binding should be: `hmac == HMAC(secret, raw_body ++ shop)` (or the shop value should otherwise be authenticated). Instead the code enforces `hmac == HMAC(secret, raw_body)` while trusting `shop` from the header unconditionally. Because the app's `client_secret` is shared across every shop/tenant that installs the app (it is not shop-specific), any merchant who has legitimately installed the app receives real, validly-signed webhook deliveries for their own shop. That merchant — an otherwise unprivileged actor with no special credentials beyond installing the same public app — can capture one such legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` recomputes the signature over `raw_body` only, so it still succeeds, and `Registry.process` dispatches the handler with `shop` claiming to be the victim tenant [4](#0-3) .

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: a webhook payload can be attributed to a shop that never sent it. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to key per-tenant records, trigger `shop/redact`/`customers/redact` compliance flows, or update shop-scoped state), an attacker-controlled merchant can inject or corrupt data associated with a different tenant — a cross-tenant access/confusion issue.

### Likelihood Explanation
Any developer/merchant who installs the same public app can obtain a validly-signed webhook for their own shop (no `api_secret_key`, access token, or TLS interception needed), then simply resend it with a modified header. The only friction is guessing/knowing a target shop domain, which is often public knowledge (the `.myshopify.com` domain).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise authenticate the shop identity independently of the header — e.g., have `Utils::HmacValidator` verify the header-derived shop against a value inside the signed payload, or require callers to cross-check `request.shop` against a shop already known to belong to the session/tenant making the call, rather than trusting `shopify-shop-domain` unconditionally in `lib/shopify_api/webhooks/registry.rb#process`.

### Proof of Concept
1. Malicious actor installs the target app on their own shop `attacker.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint: headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`.
3. Attacker captures the raw POST body and its valid HMAC header, then re-sends the exact same body/HMAC to the app's webhook endpoint but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC and passes [1](#0-0) .
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`, causing the host app to process attacker-supplied data as if it belonged to `victim.myshopify.com` [5](#0-4) .

        end
