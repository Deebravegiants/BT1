### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are trusted unauthenticated while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight out of HTTP headers with no cryptographic binding to the HMAC [3](#0-2) . `Registry.process` validates only that the raw body's HMAC is correct, then forwards `request.shop` (and the other unauthenticated header fields) straight to the app's handler as trusted identity data [1](#0-0) . The equality the code implicitly assumes but never enforces is: `shop asserted in the "shopify-shop-domain"/"x-shopify-shop-domain" header == shop whose secret produced the HMAC over this body`. Because the HMAC never covers the shop-domain header, that equality can be broken.

### Finding Description
An unprivileged internet user who legitimately controls **any** Shopify store (e.g., a free development store) can register an HTTP webhook pointed at a target app's webhook endpoint, or otherwise capture a genuine webhook delivery (body + valid `shopify-hmac-sha256`) that Shopify sent for their own shop. Because the HMAC is computed and verified over `@raw_body` only [4](#0-3) , the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a **different**, victim merchant's `myshopify.com` domain that also uses the same app. The signature check in `HmacValidator.validate` still succeeds because it only recomputes the HMAC of the body [5](#0-4) , and `Registry.process` never cross-checks the header-derived `shop` against anything else before calling the handler [1](#0-0) . The `WebhookMetadata` passed to the handler therefore reports an attacker-chosen `shop` value that the app has no way to distinguish from a genuine delivery for that shop.

Note that `ShopValidator` (used elsewhere to sanitize shop domains in OAuth/session flows, e.g. `lib/shopify_api/utils/shop_validator.rb`) is never invoked on the webhook `shop` field, so even a syntactically-arbitrary domain would be accepted and handed to the handler unchanged.

### Impact Explanation
This crosses a tenant boundary: an attacker who only controls their own low-privilege shop can cause the app to process fabricated data as if it originated from an arbitrary other merchant shop that installed the same app (cross-tenant confusion/spoofing). Depending on how the hosting app uses `WebhookMetadata#shop` (e.g., looking up that shop's stored access token/session, updating per-shop records, or triggering shop-specific side effects), this can lead to cross-tenant data corruption or actions being taken against a shop the attacker does not control, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is significant for any app that trusts `WebhookMetadata#shop` for identity-sensitive logic: registering a webhook against one's own store and replaying its exact body+signature with a forged shop header requires no secrets, only network access to the target app's public webhook endpoint and control of at least one shop capable of receiving webhook deliveries.

### Recommendation
Bind the identity-sensitive headers (`shop`, and ideally `topic`/`webhook_id`) into the signable string that is HMAC-verified, or otherwise validate that `request.shop` matches a known/expected shop (e.g., via `ShopValidator.sanitize!`) and is consistent with the caller supplying the raw body (for instance, requiring the calling application to pass the expected shop and comparing it against `request.shop` before dispatch, or since Shopify's own HMAC spec covers only the body, require host applications to additionally confirm that the shop is one of their existing installed shops before trusting `WebhookMetadata#shop`).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers webhook topic `orders/create` pointed at the app's public webhook endpoint.
2. Shopify sends a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds [4](#0-3) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the app to act as though `victim-shop.myshopify.com` sent this webhook data, despite the attacker never having any credential for that shop.
