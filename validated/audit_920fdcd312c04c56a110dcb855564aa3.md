### Title
Contract-existence check bypassed in escrow withdrawal, causing silent-success token loss (Tron `IntentGatewayV2`) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` imports and even declares `using SafeERC20 for IERC20;`, but its escrow-settlement paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `SafeERC20.safeTransfer` and instead perform raw low-level `token.call(...)` transfers, exactly reproducing the reported bug class: a low-level call whose EVM-level "success" does not imply the target contract exists or executed any code.

### Finding Description
In `withdraw()`, escrowed tokens are released using: [1](#0-0) 
and the same unguarded pattern is used for the transaction-fee payout and for the `SweepDust` code path in `onAccept()`: [2](#0-1) [3](#0-2) 

Per the EVM/TVM specification, a low-level `.call()` to an address with no deployed code returns `success == true` with empty `returndata` — this is precisely the behavior called out in the external report for `TransferHelper.safeTransfer`. The contract declares `using SafeERC20 for IERC20;` and even imports `SafeERC20`, and other parts of the same protocol (`evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `sdk/.../HyperFungibleToken.sol`, `sdk/.../WrappedHyperFungibleToken*.sol`) consistently use `IERC20(token).safeTransfer(...)` for the identical purpose: [4](#0-3) 
`SafeERC20`'s internal `Address.functionCall`/`_callOptionalReturnBool` helpers explicitly check `address(token).code.length == 0` and revert when the target has no code, which is the exact contract-existence check the external report recommends. The Tron `withdraw()`/`SweepDust` code paths do not perform this check at all, reintroducing the vulnerability class in this specific file despite the import being present.

`withdraw()` is reached through `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests (delivered via a relayed, proof-verified ISMP POST that only requires passing `authenticate()`) and through `onGetResponse()` for timeout-driven refunds — both are standard, unprivileged message-delivery paths reachable by any relayer submitting a valid proof: [5](#0-4) [6](#0-5) 

### Impact Explanation
If the escrowed `token` at settlement time has no deployed code — e.g. because the token was self-destructed, or because a same-chain order references a token address that was never deployed/was mistakenly configured — the low-level `.call()` in `withdraw()` returns `success = true` even though no tokens moved. The function then unconditionally executes `_orders[body.commitment][token] -= amount;` and marks the order `_filled[body.commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded`. The beneficiary (a user or solver owed the escrowed funds) receives nothing, but the protocol's internal accounting treats the order as successfully settled and the escrow is permanently zeroed out, with no path to retry or reclaim the funds. This is a permanent loss of escrowed funds for the intended recipient, matching the "permanent freezing/loss of funds" impact bar.

### Likelihood Explanation
Exploitation does not require any special privilege: it only requires that at redemption time the referenced ERC20 token contract has no code (self-destructed token, chain re-org/removal scenarios, or a misconfigured/placeholder token address accepted at order-placement time). Given `placeOrder`/order construction allows arbitrary token addresses supplied by users/solvers, and Tron/TVM historically supports `SELFDESTRUCT`-style contract removal, this is a realistic and reachable condition triggered by ordinary relayed message delivery (`onAccept`/`onGetResponse`), not by any privileged actor.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(...)`, consistent with the rest of the codebase (`IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`). This restores the `SafeERC20`-provided contract-existence check (`code.length == 0` revert) that the raw `.call()` currently omits, ensuring settlement reverts instead of silently "succeeding" against a non-existent token contract.

### Proof of Concept
1. A solver/user places a same-chain or cross-chain order in `IntentGatewayV2` (Tron) whose `body.tokens` references token `T`.
2. Before settlement, `T` becomes code-less (self-destructed, or was never deployed).
3. A relayer delivers a valid `RedeemEscrow`/`RefundEscrow` POST (or GET-response timeout) that passes `authenticate()`, invoking `withdraw(body, ...)`.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, "")` per EVM semantics for calls to non-existent contracts.
5. `_orders[body.commitment][token] -= amount;` executes, `_filled[...]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the escrow is marked settled while the beneficiary received zero tokens, permanently losing the escrowed amount. [7](#0-6)
