### Title
Webhook `shop` domain header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Registry.process` is computed only over the raw request body, never over the shop-domain header. This breaks the intended binding: `shop_header == shop_bound_by_hmac`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` and `Request#shop` are both read from separate, unsigned headers: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac` header — the `shop` header plays no part in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and, once it passes, forwards `request.shop` unchanged into `WebhookMetadata`, which is the identity the host application's `WebhookHandler#handle` uses to determine which tenant/shop the payload belongs to: [4](#0-3) [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not a per-shop secret), any actor who legitimately installs the app on their own shop can obtain a genuinely-signed webhook request (valid HMAC, computed only from body bytes they control) and then replay that same body while substituting an arbitrary `shopify-shop-domain` header value. The signature check in `HmacValidator.validate` still passes because it never inspects the shop header, so `Registry.process` will dispatch the payload to the handler labeled with an attacker-chosen `shop` value instead of the shop that actually owns the signature.

This is exactly the bug class in the report: a value that is *acted upon* (the shop identity used for tenant routing) is not the value that is *cryptographically bound* by the same authentication mechanism (the HMAC only binds the body).

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to select the tenant's session/store/data (the documented and expected usage of the `WebhookHandler` interface) can be made to process or store payloads under the wrong shop identity, because the gem itself never verifies `shop == hmac_signed(shop)`. This is a cross-tenant identity confusion delivered entirely by the gem's own validation logic (`HmacValidator`/`Webhooks::Request`/`Registry.process`), not by the host app "ignoring" documented behavior — the host app is doing exactly what the interface tells it to do (trust `data.shop`) and the gem provides no assurance that this field is authentic.

### Likelihood Explanation
Any Shopify Partner can install their own app on a shop they control, which is enough to obtain genuinely-signed webhook traffic (real HMAC, real body) for that shop. Replaying that traffic to the app's webhook endpoint with a modified `shopify-shop-domain` header requires no secret, no privileged access, and no interception — only the ability to send an HTTP POST to the endpoint, which is by definition internet-reachable. This is a low-effort, unprivileged-internet-user path.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`) header value into the HMAC-signed material, or otherwise verify a shop-identity claim inside the signed body itself (e.g. compare `shopify-shop-domain` against a `shop`/`shop_id` field embedded in the webhook body / a per-shop signing key) before trusting `request.shop` in `Registry.process`. Do not treat `shop` as verified solely because the outer HMAC over the body passed.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app's webhook endpoint receives a legitimately signed webhook, e.g. an `orders/create` POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends the identical raw body `B` and the identical (valid) `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only — this still matches, so validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, so any app logic keyed on `data.shop` for tenant lookup now attributes the attacker's own webhook data to the victim shop.
