### Title
Accrual panics on `scaled_to_original` i128 overflow before the `MAX_BORROW_INDEX_RAY` cap engages, permanently freezing a high-value market - (File: contracts/pool/src/interest.rs)

### Summary
`global_sync` runs `accrue_step` at the head of every pool verb. The step's first operation, `scaled_to_original(env, borrowed, borrow_index)`, multiplies scaled debt shares by the borrow index in i128 fixed-point and panics (`MathOverflow`) when the product exceeds `i128::MAX`. The borrow-index safety ceiling `MAX_BORROW_INDEX_RAY = 1e36` is applied only *after* this multiplication inside `update_borrow_index`, so on a market whose scaled-debt × index product reaches `i128::MAX` while the index is still far below the cap (test-observed at ~170×RAY index on a whale-scale book), the index cap never engages and every subsequent call re-panics at accrual. An unprivileged whale can drive a market into this state using only `supply`/`borrow` and elapsed time, permanently freezing all suppliers' and borrowers' funds on that market — including liquidations and bad-debt cleanup.

### Finding Description
The bug class is a reachable panic/availability failure (analogous to CVE-2021-2179's hang/crash DoS): a state a user can create causes every subsequent entry into the component to trap.

Execution order in `common/src/rates/simulate.rs:51-95`:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index); // line 60
let supplied_original = scaled_to_original(env, supplied, supply_index); // line 61
let util = utilization(...); let borrow_rate = ...; let interest_factor = ...;
let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor); // line 66
```

`scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), a half-up `i128` multiply that panics on overflow. The protective clamp lives in `update_borrow_index` (`common/src/rates/index.rs:13-19`), which only runs after lines 60–61 and after `update_borrow_index`'s own `old_index.mul(env, interest_factor)`. So the intended ceiling does not bound the overflow; the multiplication at line 60 overflows first whenever `borrowed_scaled × borrow_index / RAY > i128::MAX`.

`accrue_chunk` invokes `accrue_step` inside `global_sync` (`contracts/pool/src/interest.rs:20-53`), and `global_sync` is the first thing every mutating pool op does — supply, borrow, withdraw, repay, seize/liquidation legs, `net_settle`, `recapitalize`, `claim_revenue`, and the controller's permissionless `update_indexes`. Once the panic condition holds, it holds permanently: `borrowed` (scaled shares) is monotone under accrual (debt shares are never reduced by accrual), and no verb can execute to reduce it because every verb accrues first.

The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates exactly this: at 98% utilization on a steep curve the index grows past ~170×RAY, the next `update_indexes` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` revert with the same error — "the market is frozen: no repay, no withdraw, no liquidation. The index cap never engages."

Attack path (single unprivileged address):
1. `supply` a very large principal of a high-decimals listed asset (the test uses `BILLION * 10^18` raw of an 18-decimal token with caps lifted — caps are governance-set, so this requires either an already-large listed market or the attacker's own capital on an existing uncapped/loosely-capped market).
2. `borrow` ~98% of it against own collateral on a second market.
3. Let interest accrue (permissionless `update_indexes` pokes it along) until `borrowed_scaled × borrow_index` crosses `i128::MAX` below the 1e36 cap.
4. Every later call panics in accrual; the market's supplies, borrows, and the physical pool cash backing them are frozen permanently. No unwind path exists: `repay` accrues first and panics; `liquidate`/`seize` accrue first; `clean_bad_debt`/`recapitalize` accrue first.

### Impact Explanation
Permanent freezing of funds for every supplier and borrower on the affected market, plus loss of the liquidation and bad-debt-socialization paths for that market (so even protocol-level recovery via `recapitalize`/`clean_bad_debt` cannot run, since they also go through `global_sync`). The physical tokens remain locked in the pool contract — a "contract unable to operate" outcome with irreversible fund lockup for all users of that (hub, token) book.

### Likelihood Explanation
Requires a market book large enough that scaled debt × index reaches `i128::MAX` before the index reaches 1e36 — i.e. a whale-scale supply/borrow position (billions of whole-token units in the test) sustained at high utilization for multiple years of accrual, or a steep-rate curve accelerating it. The capital requirement is the main barrier, not privileges: every step (`supply`, `borrow`, `update_indexes`) is permissionless, and once reached the freeze is unrecoverable by anyone. Medium severity: real but capital- and time-gated permanent-freeze risk.

### Recommendation
Make accrual overflow-tolerant rather than panicking:

- In `accrue_step` (`common/src/rates/simulate.rs`), compute `borrowed_original`/`supplied_original` through a saturating or widened (`U256`) `mul_div` — `fp_core` already has widened multiply-divide paths used elsewhere — so utilization is computed correctly at the cliff instead of trapping.
- Alternatively, detect the would-be overflow and clamp the borrow index to `MAX_BORROW_INDEX_RAY` first (short-circuit accrual at the cap, as the sticky-cap rule intends), so the market degrades to "no further interest" instead of freezing.
- Ensure `global_sync` ordering: cap the index *before* any `scaled × index` product is taken, so the cap is a real bound on all downstream arithmetic rather than a post-hoc clamp.

### Proof of Concept
Existing in-repo test: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`.

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance years; try_update_indexes_for(&["BIG18"]) -> Err(MATH_OVERFLOW)
// borrow_index < MAX_BORROW_INDEX_RAY  (cap never engaged)
// try_withdraw_raw(...) and try_repay(...) both revert MATH_OVERFLOW
```

The panic originates at `scaled_to_original` in `accrue_step` (`common/src/rates/simulate.rs:60`), reached via `accrue_chunk`/`global_sync` (`contracts/pool/src/interest.rs:20-53`) before `update_borrow_index` (`common/src/rates/index.rs:13-19`) can clamp to `MAX_BORROW_INDEX_RAY` (`common/src/constants/pool.rs:19`).
