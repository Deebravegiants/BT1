## Analysis

The reported bug class is a TOCTOU/identity-confusion pattern: an identifier used to authorize or route a request (`sender.tab.id`) is disjoint from the data that is actually authenticated, letting an attacker swap the identity between the check and the use.

In `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`, the same class of identity-binding defect exists in the webhook verification path: the HMAC signature only covers the raw request body, but the "shop" identity that is handed to application handlers as the tenant key comes from an HTTP header that the signature never touches.### Title
Webhook `shop` identity is not bound to the HMAC-verified bytes, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then dispatches the handler using a `shop` value read from an HTTP header that is completely outside the signed data. This breaks the identity binding: `shop authenticated (by HMAC) == shop passed to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, and `hmac` is decoded from the `hmac-sha256` header. Separately, `shop` is read from the `shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against `verifiable_query.to_signable_string` (the raw body) and `verifiable_query.hmac` (the header value) — it never inspects `shop`: [3](#0-2) 

`Registry.process` uses this validation result as the sole authentication gate, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity handed to the application's webhook handler: [4](#0-3) 

The `VerifiableQuery` interface itself only requires `hmac` and `to_signable_string`, with no mechanism to bind auxiliary identity fields (like `shop`) into what gets signed: [5](#0-4) 

**Equality that should hold but doesn't:** `shop authenticated by HMAC` ⟺ `shop delivered to the handler as WebhookMetadata#shop`. Before the attacker's action, a genuine webhook has `raw_body`, `hmac`, and `shop-domain` header all consistent, produced together by Shopify for one specific shop. After the attacker's action (replaying the same `raw_body`/`hmac` pair with a different `shop-domain` header value), `Utils::HmacValidator.validate` still returns `true` (body+hmac unchanged), but `request.shop` now returns an attacker-chosen value that has no cryptographic relationship to the verified bytes.

### Impact Explanation
This is a cross-tenant identity confusion: any unprivileged actor who can obtain one valid `(raw_body, hmac)` pair (e.g., by installing the app on a shop they legitimately control and capturing the webhook their own app receives) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The library's `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the attacker-chosen `shop` to the application handler. If the host application uses `data.shop` (as documented/intended, see `Registry#process` and `WebhookMetadata`) to key per-tenant state, this enables cross-tenant data corruption or disclosure — e.g., forging a `shop/redact` or `app/uninstalled` event attributed to a shop the attacker does not own, or injecting data associated with the wrong tenant. This matches the Critical category: cross-tenant access, achieved without any credential, TLS interception, or privileged account.

### Likelihood Explanation
Likelihood is meaningfully bounded by the need for the attacker to obtain a valid `(raw_body, hmac)` pair, which requires either their own shop's genuine webhook traffic (readily available to any developer who installs the app, an unprivileged action) or a body whose content is shop-independent/predictable. It does not require the `api_secret_key`, an access token, or any interception of Shopify's traffic — only a normal HTTP POST to the app's own webhook route with a modified header, which is entirely within a merchant/developer's normal capability. This is a design gap in the gem's verification primitive (`VerifiableQuery`) rather than a host-application misuse, since the library itself instructs the identity field (`shop`) to be trusted post-`HmacValidator.validate` without folding it into the signed bytes.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, or at minimum document/enforce that `Registry.process` re-derive/cross-check the header-provided `shop` against out-of-band knowledge (e.g., an installed-shop registry) before dispatching to handlers, rather than trusting a header that sits outside the HMAC scope. Shorter term, `Utils::HmacValidator` could be extended so `VerifiableQuery` implementations can supply header fields that must be incorporated into `to_signable_string`, closing the gap between "bytes verified" (raw body) and "identity used" (header-derived `shop`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and receives a genuine webhook, capturing `raw_body`, the `x-shopify-hmac-sha256` header, and other headers.
2. Attacker sends a POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC — the `shop-domain` header is never part of the signed input (`lib/shopify_api/webhooks/request.rb:35-43`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload was never actually signed for that shop — demonstrating the broken identity binding.
