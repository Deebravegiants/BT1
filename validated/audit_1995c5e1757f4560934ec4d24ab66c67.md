This confirms the finding: the docs explicitly document `shop` as "The shop domain of the webhook" delivered via `data.shop` — a trusted-looking field — with no caveat that it is unauthenticated. The doc explicitly recommends: `ShopifyAPI::Webhooks::Registry.process` will "verify the request did indeed come from Shopify" [1](#0-0)  — but the verification (`HmacValidator.validate`) only covers `to_signable_string`, which returns just `@raw_body`, never touching the `shop-domain` header [2](#0-1) . This confirms an unauthenticated identity-binding break, in scope per the rules.

### Title
Webhook shop-domain identity spoofing via HMAC-uncovered header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` validation authenticates only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) attributed to the webhook event are read from HTTP headers that are never included in the HMAC-signed content. This breaks the identity binding `shop_authenticated == shop_attributed_to_event`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def to_signable_string
  @raw_body
end
``` [3](#0-2) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e. `@raw_body`) and compares it to the `hmac` value from the `x-shopify-hmac-sha256` header, using a constant-time compare:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

Once validation passes, `Registry.process` dispatches to the app's handler using `request.shop`, which is read straight from the `x-shopify-shop-domain` header — a field that was never part of the signed payload:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [5](#0-4) 

The equality the gem's documented flow is supposed to guarantee is:
`hmac_valid(raw_body) == true` implies `shop_header == originating_shop`.

That implication does not hold, because `shop` (as well as `topic`, `webhook_id`, `api_version`) is entirely outside the HMAC's signable string. Given any single genuine webhook delivery an attacker can observe (e.g. a webhook sent to their own store/app, which they fully control as the destination), they possess a `(raw_body, hmac)` pair that is valid for that exact body under the app's secret. They can replay this same body+hmac pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and `x-shopify-topic`/`x-shopify-webhook-id` if desired). `HmacValidator.validate` only checks the body against the HMAC and returns `true`, and `Registry.process` then invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
This is a cross-tenant identity confusion at the gem's authentication boundary: the gem's own API and documentation instruct developers to treat `data.shop` from a "verified" (per the docs) webhook request as the authoritative tenant identifier [6](#0-5) . Because the shop field carries no cryptographic binding to the signed body, an attacker who owns any single legitimate webhook subscription (any of the widely-available topics, e.g. `app/uninstalled`, `orders/create` on their own dev store) can forge webhook deliveries that the host app's handler will process under an arbitrary target shop's identity. Depending on how the host app uses `data.shop` (e.g., looking up the shop's session/access token and enqueuing an authenticated action, as shown in the gem's own documented example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/spoofing against victim merchants without any credentials for the victim shop.

### Likelihood Explanation
High: the attacker only needs to be a legitimate (even free) merchant/developer able to install any app that uses this gem and receive one genuine webhook for their own store — a capability trivially available to any internet user creating a Shopify dev/partner store. No `api_secret_key` or victim credentials are required; only the observed `(raw_body, hmac)` pair from a webhook addressed to the attacker's own shop, replayed with a spoofed `shop-domain` header.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them (e.g., derive/validate `shop` from the app's own webhook subscription metadata mapped to the specific `webhook_id`/topic returned by Shopify's registration rather than trusting the header verbatim). At minimum, document clearly that `data.shop` (and other header-sourced fields) are NOT covered by the HMAC and must not be trusted as an authenticated tenant identifier by the host application.

### Proof of Concept
1. Attacker installs the vulnerable app on their own Shopify dev store (`attacker.myshopify.com`) and registers for a webhook topic the app subscribes to.
2. Shopify delivers a legitimate webhook to the app's callback URL with headers including a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `client_secret`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact `(raw_body, hmac_header)` pair.
4. Attacker sends a new HTTP request to the app's public webhook endpoint with the same `raw_body` and `hmac_header`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes/compares the HMAC of `raw_body` — it returns `true` [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [8](#0-7) , causing the host app to process attacker-controlled webhook content under the victim's tenant identity.
