Confirmed: the HMAC over a webhook request signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` come from unauthenticated headers.

## Title
Webhook `shop` (and topic/id) fields are trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, then passes the `shop`, `topic`, `webhook_id`, and `api_version` values — all read from unauthenticated HTTP headers — straight to the handler as trusted tenant-identifying metadata.

## Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC exclusively over `verifiable_query.to_signable_string`, which for a webhook `Request` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers, which are never included in the signed material: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (body HMAC) before dispatching the handler with the header-derived `shop`: [3](#0-2) 

The identity binding that should hold is: `shop asserted in X-Shopify-Shop-Domain header == shop whose secret produced the HMAC`. Because the HMAC only covers the body bytes and not the shop header, this equality is never checked. A party who can obtain one genuinely-signed webhook body (e.g. a webhook Shopify sends for their own installed shop, which they legitimately receive with a valid HMAC because it was computed with the app's real `api_secret_key`) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and topic/webhook-id) header. The HMAC still validates because it never depended on those headers, so `Registry.process` invokes the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain.

## Impact Explanation
Any application relying on `WebhookMetadata#shop` (or `#topic`) to route or scope data per tenant will process attacker-controlled webhook content under an arbitrary victim shop identity — a cross-tenant data confusion/injection vector at the credential/tenant boundary the gem is supposed to enforce for its consumers.

## Likelihood Explanation
Exploitation requires only a valid HMAC-signed body from any shop the attacker legitimately controls (or one previously observed) plus the ability to send arbitrary headers to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed, since HMAC validation never binds the header-derived shop/topic to the signed bytes.

## Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them to the body before HMAC verification), so the whole tuple used by consumers is covered by the signature rather than only the raw body.

## Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers webhook for topic `orders/create`.
2. Shopify sends a legitimately HMAC-signed webhook: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, body `B`, `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays the same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since headers aren't part of the signed string [4](#0-3) .
5. `Registry.process` calls the handler with `shop: "victim.myshopify.com"` [5](#0-4) , causing the app to act on attacker data under the victim tenant's identity.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
