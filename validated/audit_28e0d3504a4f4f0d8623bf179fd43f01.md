This confirms the vulnerability. `Registry.process` at `lib/shopify_api/webhooks/registry.rb#L188-200` validates only `Utils::HmacValidator.validate(request)`, which computes the HMAC solely over `to_signable_string` (the raw body) per `lib/shopify_api/webhooks/request.rb#L35-38`. The `shop` field consumed downstream and handed to the host app's handler via `WebhookMetadata.new(... shop: request.shop ...)` at `lib/shopify_api/webhooks/registry.rb#L198-199` is read from the `shop-domain` header at `lib/shopify_api/webhooks/request.rb#L20-23`, which is never part of the signed bytes.

Because `Context.api_secret_key` used for HMAC verification (`lib/shopify_api/utils/hmac_validator.rb#L13-22`) is the app-level `client_secret` shared across every shop that installs the app — not a per-shop key — a valid signature only proves "this body+secret pair was signed by Shopify for some shop using this app," not "this body came from the shop named in this header."

### Title
Webhook shop identity spoofable because HMAC covers only the raw body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature verified by `Registry.process` binds solely to the body bytes. The `shop` attribute exposed to the host app's `WebhookHandler#handle` is taken from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not covered by that signature.

### Finding Description
`Registry.process` at [1](#0-0)  only calls `Utils::HmacValidator.validate(request)` before dispatching to the registered handler. `HmacValidator.validate`/`validate_signature` compute `compute_signature(verifiable_query.to_signable_string, secret)` and compare it to `verifiable_query.hmac` [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `hmac-sha256` header [3](#0-2) ; neither includes `shop`, `topic`, or `webhook_id`. Yet `shop` — read straight from the `shop-domain` header — is passed into `WebhookMetadata` and handed to the app's handler as the tenant identity for this event [4](#0-3) .

Critically, `HmacValidator` verifies against `Context.api_secret_key`, which is the single app-level `client_secret` shared by *all* shops that have installed the app [5](#0-4) ; it is not a per-shop secret. This breaks the intended binding `shop-domain header == shop that produced the signed body`. An attacker who installs the app on their own shop can capture a genuinely-signed webhook body Shopify sends for their shop, then POST that exact `raw_body`+`hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary victim's `shop-domain` header value. `HmacValidator.validate` still succeeds because it never inspects the header, so `Registry.process` treats the forged `shop-domain` as authentic and invokes the host app's handler with `WebhookMetadata(shop: "<victim-shop>", body: <attacker-controlled-but-genuinely-signed-body>, ...)`.

### Impact Explanation
Any host application that keys persistence, authorization, or side effects (e.g., "which merchant does this order/inventory update belong to") off `WebhookMetadata#shop` as returned by this gem will attribute attacker-controlled event data to a shop the attacker does not control — a cross-tenant data-integrity/confusion vulnerability rooted in this gem's failure to bind `shop` (and `topic`/`webhook_id`) into the verified signature.

### Likelihood Explanation
Exploitation only requires becoming an installed merchant of the target app (trivial for public apps) and capturing one legitimately-signed webhook delivered to that attacker-owned shop, then replaying it with a modified header — no access to `client_secret`, access tokens, or victim credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material for webhook requests (or otherwise cryptographically bind the header values to the body before trusting them), so that `Registry.process` rejects any request where the claimed `shop-domain` was not part of what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid for `B`), and swaps `x-shopify-shop-domain` from `attacker.myshopify.com` to `victim.myshopify.com`.
3. Attacker POSTs `B` with the modified headers to the app's webhook route, which builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` and calls `Registry.process`.
4. `HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and passes [6](#0-5) .
5. The host handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it came from `victim.myshopify.com`.
