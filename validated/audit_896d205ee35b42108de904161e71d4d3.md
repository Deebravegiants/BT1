The `whenNotPaused` modifier is applied to the outbound refund/timeout-recovery path (`onPostRequestTimeout`) of the `HyperFungibleToken` cross-chain token bridge, exactly the pattern the external report warns about.

### Title
Applying `whenNotPaused` to `onPostRequestTimeout` allows the owner to permanently strand burned/locked user funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol`)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches an ISMP POST request; the *only* path to recover those tokens if the message is never delivered is `onPostRequestTimeout()`, which re-mints (or unlocks, for the wrapped variant) the tokens back to the sender once a timeout proof is submitted. That recovery function is gated by `whenNotPaused`, so pausing the contract blocks the refund path entirely, mirroring the reported anti-pattern of guarding outbound/exit methods with a pausable modifier.

### Finding Description
`send()` burns tokens up front: [1](#0-0) 

The corresponding refund on timeout is the only mechanism to make the sender whole if delivery never happens, and it carries `whenNotPaused`: [2](#0-1) 

The same pattern exists in the lock/unlock wrapper, where locked underlying ERC20/WETH can only be released back to the sender via a `whenNotPaused`-gated timeout handler: [3](#0-2) 

`pause()`/`unpause()` are `onlyOwner`: [4](#0-3) 

Because both the inbound delivery (`onAccept`) and the outbound recovery (`onPostRequestTimeout`) share the same `Pausable` flag, there is no way to unwind a user's already-burned/locked funds once the contract is paused. If the owner key is compromised, malicious, or the owner renounces ownership (or the `Ownable` role is otherwise lost) while paused, users who called `send()` before the pause and whose message subsequently times out have no way to reclaim their funds — `onPostRequestTimeout` will always revert on the `whenNotPaused` check, and there is no owner-independent unpause mechanism.

### Impact Explanation
Any user who calls `send()` (burning/locking tokens) faces permanent loss of those funds if the contract is paused before their message's timeout proof is submitted and the pause is never lifted (compromised/malicious/renounced owner). This is a direct, permanent freezing-of-funds vector reachable by any ordinary user transaction (`send()`), not just a hypothetical — it requires only the standard bridging flow plus a timeout, which is a routine occurrence (relayer downtime, congestion, or an attacker deliberately withholding delivery until the timeout).

### Likelihood Explanation
Requires a malicious/compromised/negligent owner to pause and not unpause (or renounce ownership while paused), which the report itself frames as the threat model for this bug class (owner key compromise or malicious governance action is the trigger, not a network-level failure). Given `pause()` is a single `onlyOwner` call with no timelock or restriction preventing it from being applied while payments are in flight, this is a realistic single-privileged-action griefing vector.

### Recommendation
Remove `whenNotPaused` from `onPostRequestTimeout` (and any other refund-path functions) in `HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, and `HyperFungibleTokenUpgradeable.sol`, so that pausing only blocks new inbound/outbound transfers (`send`, `onAccept`) but never blocks users from recovering funds already committed to a cross-chain transfer that timed out.

### Proof of Concept
1. User calls `send()` on `HyperFungibleToken`, burning `amount` tokens and dispatching a POST request with a given `timeout`. [5](#0-4) 
2. Before the request is delivered, the owner (compromised, malicious, or acting under duress) calls `pause()`. [6](#0-5) 
3. The request times out on the destination and a relayer submits the timeout proof to the ISMP host, which calls `onPostRequestTimeout()` on the token contract; the call reverts due to `whenNotPaused`. [2](#0-1) 
4. If the owner never unpauses (key lost, owner renounces, or acts maliciously), the burned tokens can never be re-minted to the user — permanent loss of funds with no alternative recovery path in the contract.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
