## Analog Confirmed

### Title
Overpaid native token during `dispatch()`/`fundRequest()` fee-swap is permanently stranded in `EvmHost` instead of refunded to caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are `payable` and let a caller pay the protocol/relayer fee with native token by swapping `msg.value` for `feeToken()` via Uniswap V2's `swapETHForExactTokens`. None of these three functions capture the swap's return value or forward any unspent ETH back to the caller, so any overpayment beyond what the swap actually consumes is not refunded to the user — it is refunded by the router to `EvmHost` itself (since `EvmHost` is the direct caller of the router), where it becomes permanently stuck with no withdrawal path back to the original payer.

### Finding Description
In all three payable entry points, the pattern is identical: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
```

The same construction is repeated in `dispatch(DispatchGet)` and in `fundRequest()`: [2](#0-1) [3](#0-2) 

Standard `UniswapV2Router02.swapETHForExactTokens` only spends `amounts[0] <= msg.value` (equal to the actual price for `post.fee`/`get.fee`/`amount` tokens out) and refunds the difference back to `msg.sender` of that call. Because `EvmHost` calls the router directly (not via delegatecall or forwarding the original caller), the refund's `msg.sender` as seen by the router is `EvmHost`, not the end user who supplied `msg.value` to `EvmHost.dispatch`/`fundRequest`. The refunded dust ETH lands in `EvmHost`'s own balance.

None of these functions capture the `amounts` return array from `swapETHForExactTokens`, nor do they compute `msg.value - amounts[0]` and forward it back to `_msgSender()`. There is no `receive()`-triggered sweep or admin/user-callable rescue function visible in `EvmHost.sol` that would let the affected user recover this stuck ETH.

This is the exact analog of the reported class: a `payable` fee-collection path that doesn't refund overpayment to the caller. Notably, the codebase's own `IntentGatewayV2.placeOrder` shows the correct pattern was known and applied elsewhere — it explicitly captures the swap's `amounts[0]` and refunds the remainder to `msg.sender`: [4](#0-3) 

`EvmHost.dispatch`/`fundRequest` simply omit this step.

### Impact Explanation
Any user or application contract that dispatches a POST/GET request or funds a pending request with native token (the officially documented/recommended payment method per `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`) and supplies `msg.value` greater than the exact wei required to buy `post.fee`/`get.fee`/`amount` of `feeToken` will have the excess permanently locked inside `EvmHost`. Since exact swap pricing (accounting for slippage, pool depth, and price movement between quote-time and execution) is inherently imprecise, callers routinely over-provision `msg.value` as a safety margin — this is standard practice and is exactly what the sibling `IntentGatewayV2` contract defends against. Each such call causes a permanent, irrecoverable loss of user funds. This is a direct, permanent freezing-of-funds bug reachable by any unprivileged caller in a single transaction, satisfying the Medium-severity bar.

### Likelihood Explanation
High likelihood: `dispatch()` is the primary payable entry point for all POST/GET message dispatch via native token, documented as the recommended/simple payment method, and any caller who doesn't compute the exact wei-cost of the Uniswap swap ahead of time (which requires an off-chain quote subject to race/slippage) will overpay to some degree on essentially every call.

### Recommendation
Capture the `amounts` array returned from `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or `msg.sender`), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`/`fillOrder`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch(post)` with `post.fee = X` (small) and `msg.value = 10 * X_worth_of_ETH` (large safety margin, or simply an honest user over-provisioning due to slippage-quote imprecision).
2. Inside `dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router spends only the ETH needed to buy `post.fee` fee-tokens and refunds the rest — but the refund's recipient (`msg.sender` from the router's perspective) is `EvmHost`.
3. `EvmHost`'s native balance increases by the unspent ETH; the function returns without ever inspecting the swap's return value or moving that ETH to the original caller.
4. The original caller has irreversibly lost `msg.value - actualCost` ETH with no function in `EvmHost` to reclaim it.
