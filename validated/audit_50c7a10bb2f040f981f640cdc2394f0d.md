### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant/tenant the webhook belongs to. Because the header is not part of the signed payload, any party who can obtain one validly-signed webhook body from the app's own secret can replay it with a forged `shop-domain` (and `topic`) header, causing the app to process data under an attacker-chosen shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers that are never included in the signed material [3](#0-2) .

`Registry.process` verifies only the body HMAC, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the application's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . There is no check that the `shop` header value matches the shop that actually owns the webhook subscription that generated the signed body.

This breaks the equality the HMAC is supposed to enforce: `verified(bytes) == acted_on(shop identity)`. The bytes verified are `raw_body` only; the identity acted upon by the app (which shop this event belongs to) comes from a header outside the signature.

### Impact Explanation
Any actor able to obtain one webhook payload validly signed by the app's own `api_secret_key` for topic X (e.g., by installing the app on their own shop and receiving a legitimate webhook) can replay that exact signed body while substituting the `x-shopify-shop-domain` header for any other shop the attacker wants to target. Since HMAC verification only inspects the body, the forged request passes `HmacValidator.validate` and is handed to `handler.handle` with `data.shop` set to the attacker-chosen tenant. Depending on how the host application uses `data.shop` (e.g., to look up records, update database rows keyed by shop, or trigger merchant-facing side effects), this enables cross-tenant data corruption or cross-tenant action injection — an app processes another merchant's webhook event under a false identity it fully trusts as authenticated. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Medium: exploitation requires the attacker to already possess at least one genuinely signed webhook body (trivial for anyone who installs the app on their own store, since apps commonly are installable by any merchant), plus knowledge of the target shop's domain (public information, e.g., `some-shop.myshopify.com`). No access to `api_secret_key`, access tokens, or TLS interception is required — only a replay/header-substitution against the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the material that is HMAC-verified, or independently verify that `request.shop` corresponds to a shop with an active, registered webhook subscription for the received `webhook_id`/topic before dispatching to `handler.handle`. At minimum, applications should be warned in documentation that `data.shop` from `WebhookMetadata` is not cryptographically bound to the payload's authenticity and must be cross-checked against the app's own list of installed/authorized shops before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and registers for topic `orders/create`.
2. Shopify sends a legitimate webhook: body `B`, headers `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays this exact body `B` and HMAC header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks `B` against the (unchanged) HMAC [5](#0-4) .
5. `handler.handle` is invoked with `data.shop == "victim-shop.myshopify.com"` [6](#0-5) , causing the application to process attacker-controlled order data as if it originated from the victim shop.
