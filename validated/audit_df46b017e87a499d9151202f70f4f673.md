### Title
Direct-donation DoS bricks the curve's full-sellout graduation trigger via `OverflowCapDegenerate` - ([File: packages/contracts/src/Router.sol])

### Summary
An unprivileged holder of a launched `Token` can grief a still-curving token by transferring their own tokens directly into the token's `Pair` contract (a plain `IERC20.transfer`, not `Bonding.sell`). This inflates the pair's live `tokenBalance()` without touching the AMM's stored virtual `tokenReserve`, collapsing the fixed gap between them. Once that gap reaches zero, `Router._computeBuy`'s real-balance overflow cap divides by a zero `cappedReserveToken` and reverts with `OverflowCapDegenerate()` for any buy attempting to drain the remaining real balance — permanently preventing the curve from ever reaching `tokenBalance() == 0`, i.e. permanently disabling one of the two graduation triggers.

### Finding Description
`Pair.mint` fixes `_pool.tokenReserve = totalSupply` (virtual) while only `curveSupply = 75%` of `totalSupply` is actually transferred to the pair [1](#0-0) . Because `Pair.swap` decrements `tokenReserve` and the real ERC20 balance by the same `tokenOut` on every buy [2](#0-1) , the difference `tokenReserve - tokenBalance()` is invariant at `LP_RESERVE = 250,000,000e18` under normal trading.

`Router._computeBuy` uses this gap implicitly: when a buy's uncapped `tokensOut` exceeds the pair's real `tokenBalance()` (`realBalance`), it caps `tokensOut = realBalance`, then computes `cappedReserveToken = reserveToken - tokensOut` and reverts `OverflowCapDegenerate()` if that value is zero, since it is about to be used as a divisor: [3](#0-2) 

`Token` is a freely transferable ERC20 owned by `Bonding` only for mint/burn purposes; any curve holder can send tokens they legitimately bought straight to the `Pair` address with a raw `transfer`. This increases `IPair.tokenBalance()` (a live `balanceOf` read, per `Pair.tokenBalance()` [4](#0-3) ) but does **not** change the stored `_pool.tokenReserve` used for `k` and the buy/sell math. Donating up to `LP_RESERVE` tokens this way drives `reserveToken - realBalance` to zero. From that point on, any buy whose (uncapped) `tokensOut` would exceed `realBalance` — i.e. any attempt to buy out the remaining real supply, which is exactly the transaction that would normally trip `tokenBalance() == 0` — lands in the capped branch with `cappedReserveToken == 0` and reverts instead of completing.

`Bonding.canGraduate`'s supply trigger explicitly depends on `IPair(pair).tokenBalance() == 0` being reachable [5](#0-4) ; once the donation griefing has permanently disabled the transaction that would zero it out, that trigger is dead for the life of the token. Only the USD-value trigger remains, which is a function of the external LT's live `exchangeRate()` and can be unreachable if the LT depreciates relative to its launch-time snapshot.

### Impact Explanation
This is a griefing/DoS attack reachable by any unprivileged wallet that has bought even a small amount of the launched token (a normal `Zap.buy`), requiring only a subsequent plain ERC20 `transfer` to the `Pair` address — no privileged role, no upgrade, no off-chain component. The result is a permanent, protocol-level failure of one of the two documented graduation triggers (`canGraduate`'s supply leg) for the targeted token, and a hard revert (loss of gas, failed trade) for any trader who later tries to buy the curve's remaining real balance. If the paired LT's price stagnates or drops so the USD trigger also never fires, the token is permanently stuck in `Lifecycle.Curve` — it can never reach `finalizeGraduation`, so its curve-raised LT and reserved LP tokens never leave `Bonding`, freezing the creator's and traders' path to a tradeable post-graduation market indefinitely. This satisfies the "permanent freezing" bar for a Medium-severity DoS analog to the referenced Tomcat CVE (malformed inputs permanently rejecting later legitimate requests).

### Likelihood Explanation
Trivially reachable: buy a nonzero amount of tokens via `Zap.buy`, then call `Token.transfer(pair, amount)` directly (or accumulate several such donations from any holders/bots) until the fixed `LP_RESERVE` gap is exhausted. No special timing, no race condition, no cost beyond the tokens donated (which the attacker already owns and forfeits, a cheap griefing cost relative to the DoS achieved on an entire token launch).

### Recommendation
`Router._computeBuy`'s degenerate-cap branch should not hard-revert the entire buy when `cappedReserveToken == 0`; instead it should treat the situation as "buy the entire remaining real balance" (`tokensOut = realBalance`, `amountInUsed` computed against the true remaining curve capacity, e.g. via `k / (reserveAsset)` reasoning that doesn't require dividing by `cappedReserveToken`), or alternatively `canGraduate`/`_prepareGraduationLiquidity` should derive the "curve exhausted" condition from `reserveToken` reaching its floor rather than relying on the donation-manipulable live `tokenBalance()` matching `reserveToken` exactly for the buy path to succeed.

### Proof of Concept
1. Launch a token via `Zap.createToken` (curve opens with `_pool.tokenReserve = totalSupply`, real pair balance = `curveSupply = 75% * totalSupply`; gap = `LP_RESERVE = 250,000,000e18`).
2. Attacker (or any address) buys a small amount of the token via `Zap.buy`/`Bonding.buy` — cheap, gains real token balance.
3. Attacker calls `Token.transfer(pairAddress, X)` directly for increasing `X` (or multiple donors repeat this) until `IPair(pair).tokenBalance()` equals the pair's stored `tokenReserve` returned by `Pair.getReserves()` (closing the `LP_RESERVE`-sized gap). This never reverts because it's a plain ERC20 transfer with no protocol-level guard against donations to `Pair`.
4. Any trader now calls `Zap.buy`/`Bonding.buy` with an `amountIn` large enough that `Router._computeBuy`'s uncapped `tokensOut` exceeds `realBalance` (e.g., attempting to buy out the remaining curve supply, the natural action that would otherwise set `tokenBalance() == 0` and satisfy `canGraduate`'s supply trigger).
5. `_computeBuy` sets `tokensOut = realBalance`, computes `cappedReserveToken = reserveToken - tokensOut = 0`, and reverts `OverflowCapDegenerate()` [6](#0-5) . This transaction — and every subsequent attempt to fully drain the curve — reverts permanently, so `Bonding.canGraduate`'s `tokenBalance() == 0` branch [7](#0-6)  can never fire again for this token.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
