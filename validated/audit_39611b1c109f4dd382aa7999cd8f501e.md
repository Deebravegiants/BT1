### Title
Fee is deducted from swap output even when `relay == address(0)`, permanently trapping tokens in the swap contract - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap()` unconditionally computes `relayFee` (`feeStructure.flatFee`) and `hinkalFee` (via `variableRate`) and subtracts their sum from the swap output before forwarding the remainder to `msg.sender` (Hinkal). However, the actual payout of those fees, `sendToRelay(circomData.relay, ...)`, is a no-op whenever `circomData.relay == address(0)`, per the guard in `Transferer.sendToRelay` (`if (relay != address(0) && actualAmount > 0)`). This mirrors the reported Merit Circle bug class: a "portion" is computed and deducted from the balance equation, but the corresponding payout is gated on an address that can legitimately be zero, so the deducted value is never paid to anyone and is stranded.

### Finding Description
In `ExternalActionSwap.swap()`: [1](#0-0) 
`relayFee` and `hinkalFee` are always computed from `swappedAmount`, and `totalFee` is always subtracted to compute `amountToSendToHinkal`, which is the only value actually transferred out via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)`. The fee payment itself goes through `sendToRelay`: [2](#0-1) 
which silently skips the transfer if `relay == address(0)`.

`circomData.relay == address(0)` is an explicitly supported, legitimate state elsewhere in the protocol — `Hinkal._internalTransact` treats it as "no relay used" and only requires a relay payment when a relay is actually specified: [3](#0-2) . `circomData.relay` and `circomData.feeStructure` are both bound into the calldata hash / signed message that the circuit verifies [4](#0-3) , so a user/prover can legitimately submit a proof with `relay = address(0)` and a non-zero `feeStructure.flatFee`/`variableRate` (these are independent fields, nothing in the circuit or contract enforces that fee fields must be zero when `relay == 0`).

When this combination occurs on a swap action, the computed `totalFee` amount of `outputToken` is deducted from what gets sent to `msg.sender`/Hinkal, but `sendToRelay` performs no transfer since `relay == address(0)`. The tokens remain in the `ExternalActionSwap` contract's balance, unaccounted for by any UTXO and with no recovery path in this contract (`callRouter` is abstract; no sweep/rescue function is shown in this file).

This breaks the balance equation the report's bug class targets: value is subtracted from what the user receives (and would need to be reflected as delta-amount/UTXO) but is not moved anywhere — it's simply lost from the user's perspective, with no relay, no hinkalHelper, and no user receiving it.

### Impact Explanation
This is a permanent freezing of user funds (the deducted fee amount becomes permanently stuck in the `ExternalActionSwap` contract), which is not offset by any UTXO issued to the user - the UTXO created only reflects `amountToSendToHinkal`, i.e., the post-fee-deduction amount. Depending on `flatFee`/`variableRate` magnitude this can be a meaningful, unrecoverable value loss for the swapping user on every relay-less swap, satisfying the "High: temporary/permanent freezing of user funds" or potentially "Critical: permanent freezing of user funds" bar depending on recoverability.

### Likelihood Explanation
Any user (self-relaying, i.e., not using a whitelisted relay) who submits a swap transaction with a non-zero `feeStructure.flatFee` or `variableRate` while setting `circomData.relay = address(0)` triggers this. Since `relay == address(0)` is a normal, supported "self-relay" mode throughout the protocol, and fee fields are independently signed/hashed data with no cross-field validation forcing them to zero when `relay` is zero, this is reachable by an ordinary unprivileged user/prover without needing any admin, relayer, or another user's key.

### Recommendation
Gate the fee computation/deduction the same way the payment is gated: only compute and subtract `relayFee`/`hinkalFee` (or set them to zero) when `circomData.relay != address(0)`, mirroring the pattern already used in `Hinkal._internalTransact` (`if (circomData.relay != address(0)) { ... }` before computing fees) so `amountToSendToHinkal` equals the full `swappedAmount` when there's no relay to pay.

### Proof of Concept
1. User constructs a valid proof/CircomData for a swap action with `circomData.relay = address(0)` (self-relay, legitimate per `Hinkal.sol`'s handling) but `circomData.feeStructure.flatFee > 0` and/or `variableRate > 0`.
2. `ExternalActionSwap.swap()` runs: `callRouter` returns `swappedAmount`; `relayFee = flatFee`, `hinkalFee = calculateRelayFee(swappedAmount, 0, variableRate)` are computed unconditionally: [5](#0-4) .
3. `sendToRelay(circomData.relay, relayFee[+hinkalFee], ...)` is called but internally does nothing because `relay == address(0)`: [2](#0-1) .
4. `amountToSendToHinkal = swappedAmount - totalFee` is transferred to `msg.sender`, and the UTXO minted reflects only this reduced amount: [6](#0-5) .
5. The `totalFee` worth of `outputToken` remains in the `ExternalActionSwap` contract's balance, not represented by any UTXO and not paid to any relay — permanently stranded.
