### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC-SHA256. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers and are never included in the signable string that is validated. Since a single `api_secret_key` is shared by the app across every shop that installs it, an attacker who controls one shop that has the app installed can capture a legitimately-signed webhook body (with its valid HMAC) sent to their own shop, then replay that exact body + HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The signature still validates (it never covered the shop field), and the app processes the forged webhook believing it originated from the victim shop.

### Finding Description
The binding that should hold is: `HMAC-verified bytes == bytes the app trusts for tenant identity`. Here it does not:
- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all sourced from `@headers`, which are attacker-controllable in a raw HTTP request/mock and are never mixed into `to_signable_string` [2](#0-1) .
- `HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed over `to_signable_string` (the body) [6](#0-5) .
- `Registry.process` trusts this validation and immediately builds `WebhookMetadata` using `request.shop` (the header value) as the tenant identifier passed to the app's handler [3](#0-2) .

Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, any tenant of a multi-tenant app can obtain a validly-signed `(body, hmac)` pair for their own shop (simply by triggering a real event on their own store) and then submit it to the shared webhook endpoint with a forged `shop-domain` header pointing at any other installed shop. The gem's verification logic provides no way for the host application to detect this, since the shop field carries no cryptographic binding to the signature.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the app cannot distinguish "data legitimately belonging to shop A" from "the same data falsely attributed to shop B." Depending on how the host app uses `data.shop` (e.g., to select which merchant record to update, to look up the merchant's access token, or to trigger merchant-scoped side effects), an attacker-controlled shop can inject events attributed to a victim's tenant, corrupting victim data or triggering unauthorized actions scoped to the victim shop. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only that the attacker operate one shop with the target app installed (a normal, unprivileged action — any merchant can install an app) and be able to send an HTTP POST to the app's public webhook endpoint with custom headers, both of which are trivially available to any external actor. No access token, `client_secret`, or other privileged credential is needed.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable string that is HMAC-verified, or otherwise cryptographically bind the header-derived shop to the signed payload before it is exposed to host application handlers via `WebhookMetadata`. At minimum, document that `data.shop` is unauthenticated and must not be trusted for tenant identification without independent verification (e.g., checking against a shop-and-webhook-id combination the app itself registered).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., updates a product), causing Shopify to send a legitimately HMAC-signed webhook with some JSON body `B` and header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures the raw body `B` and the `X-Shopify-Hmac-Sha256` header value (a valid signature since it's computed with the app's shared secret over `B` only) [7](#0-6) .
3. Attacker POSTs the same body `B` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body's HMAC [8](#0-7) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-supplied body content as if it belonged to the victim shop.
