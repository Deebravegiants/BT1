### Title
Unbounded, cheaply-spammable `Bids` storage lets an attacker starve legitimate solver bid discovery through the capped `intents_getBidsForOrder` RPC - ([File: modules/pallets/intents-coprocessor/rpc/src/lib.rs])

### Summary
`pallet-intents-coprocessor`'s `place_bid` extrinsic lets any signed account insert an entry into the `Bids` double-map for an order commitment with only a refundable reserve, and imposes no limit on how many distinct fillers may bid on the same commitment. [1](#0-0)  The RPC that the SDK's default order-execution flow relies on to discover on-chain bids, `intents_getBidsForOrder`, only reads the first `MAX_ON_CHAIN_BIDS = 30` storage keys under the commitment's prefix before merging them with the mempool cache. [2](#0-1)  Because the write side is unbounded and the read side is hard-capped at 30, an attacker can permissionlessly flood a commitment with cheap throwaway bids to push a legitimate solver's bid out of the discovered set — the same "fixed-capacity resource that anyone can fill" bug class as the referenced report's ERC20 token-slot exhaustion, just applied to bid discovery instead of token whitelisting slots.

### Finding Description
`place_bid` is fully permissionless: it only requires `ensure_signed` plus reserving `StorageDepositFee` (governance-set, and fully refunded via `retract_bid`), and there is no per-commitment cap on the number of distinct fillers that may insert into `Bids`. [3](#0-2)  Multiple fillers bidding on the same order is an explicitly supported, unbounded case, as shown by the test `multiple_fillers_can_bid_on_same_order`. [4](#0-3) 

The primary discovery path used by the SDK, `intents_getBidsForOrder`, walks the raw storage keys under the `Bids` prefix (ordered by `blake2_128(filler) ++ filler`, i.e. effectively by hash of the filler account) and takes only the first 30:
```
const MAX_ON_CHAIN_BIDS: usize = 30;
for key in keys.take(MAX_ON_CHAIN_BIDS) { ... }
``` [2](#0-1) 

The SDK's `getBidsForOrder` calls this RPC as its primary, single-round-trip path and only falls back to the unbounded storage-entries query on RPC failure (not on truncation) — so under normal RPC operation, callers only ever see the 30 keys the RPC returns. [5](#0-4)  `OrderExecutor.fetchBids`, which drives the default `execute`/`executeBest` auto-selection flow, depends directly on `intentsCoprocessor.getBidsForOrder` for every polling round during the bid auction. [6](#0-5) 

Since `blake2_128(filler)` is attacker-controllable by generating (or grinding) new signer accounts, and each bid only costs a refundable reservation (`Currency::reserve`, refunded on `retract_bid`), an attacker can:
1. Generate/fund N sybil accounts (cheap: reservation is not spent, only locked briefly and gas-cost per extrinsic is paid).
2. Submit `place_bid` from all N accounts on the target order's commitment.
3. As N grows past a small multiple of 30, the probability that the legitimate solver's key sorts within the first 30 raw storage keys collapses toward zero, and the RPC-based path (which the reference `OrderExecutor` implementation uses) never surfaces the legitimate bid.
4. Optionally, the attacker also submits their own (unfavorable) bid, which the SDK-driven flow will select instead — since the legitimate/best bid is invisible to `getBidsForOrder`.

### Impact Explanation
An intent order placer relying on the default `IntentGateway.execute`/`executeBest` flow can be forced to either (a) never see any legitimate bid, letting the order run out its bid-auction/deadline window and fail to fill (funds effectively stuck in escrow until timeout/cancellation), or (b) unknowingly select and execute an attacker-controlled, inferior bid because it is the only one discoverable, resulting in a worse fill price than the market otherwise offered. Both outcomes are direct value-loss/DoS-of-delivery outcomes for the order placer, driven purely by an unprivileged actor (an "intent solver"/bidder) exploiting the mismatch between the unbounded `Bids` write path and the hard-capped `MAX_ON_CHAIN_BIDS` read path.

### Likelihood Explanation
The attack requires only ordinary signed accounts and the reservable `StorageDepositFee` (fully refundable), so cost scales with the number of extrinsics submitted, not with capital locked — an attacker can cheaply generate and fund many throwaway accounts to bid-spam a specific, high-value order commitment they observe in the mempool/on Hyperbridge. No governance or privileged role is needed; `place_bid` is open to any signed account and imposes no per-commitment cap. [3](#0-2) 

### Recommendation
Enforce a per-commitment bound on the number of bids the pallet accepts (e.g., a `BoundedVec`/counter with a `MaxBidsPerOrder` cap, rejecting further bids once reached, or evicting the worst bid rather than an arbitrary key-ordered one), and/or change `intents_getBidsForOrder`'s on-chain enumeration so it is not sensitive to key-hash ordering (e.g., iterate all keys under the prefix rather than truncating at a fixed count, or select by a criterion meaningful to solvers such as deposit/recency rather than raw storage-key order). At minimum, `MAX_ON_CHAIN_BIDS` should not silently drop bids whose selection could change with attacker-chosen sybil accounts.

### Proof of Concept
1. Order placer submits an intent order on the source chain; commitment `C` becomes visible on Hyperbridge/mempool.
2. Legitimate solver submits `place_bid(C, userOp)` from account `F_legit`.
3. Attacker generates accounts `F_1..F_5000`, funds each with the minimum reservable `StorageDepositFee`, and submits `place_bid(C, garbage_userOp)` from each, so the `Bids` double-map under `C` now has 5001 entries with no on-chain cap rejecting them. [3](#0-2) 
4. The order placer's SDK calls `getBidsForOrder(C)` → `intents_getBidsForOrder` RPC, which enumerates `storage_keys` under the `Bids(C, ·)` prefix and takes only the first 30. [2](#0-1)  With 5000+ sybil entries, `F_legit`'s key has a negligible chance of falling within that first-30 slice.
5. `OrderExecutor`'s auction loop, which polls exclusively via `getBidsForOrder`, never surfaces the legitimate bid; the placer's order either times out unfilled or is filled by one of the attacker's own submitted (unfavorable) bids. [7](#0-6)

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}

	fn get_bids_for_order(&self, commitment: H256) -> RpcResult<Vec<RpcBidInfo>> {
		// Get mempool bids from in-memory cache
		let mut bids =
			self.bid_cache.get_bids(&commitment).map_err(runtime_error_into_rpc_error)?;

		// Query on-chain bids via StorageProvider and read bid data from offchain storage.
		let best_hash = self.client.info().best_hash;
		let prefix = bids_storage_prefix(&commitment);
		let prefix_key = sp_core::storage::StorageKey(prefix.clone());

		let keys = self
			.client
			.storage_keys(best_hash, Some(&prefix_key), None)
			.map_err(runtime_error_into_rpc_error)?;

		const MAX_ON_CHAIN_BIDS: usize = 30;

		for key in keys.take(MAX_ON_CHAIN_BIDS) {
			// Key layout after prefix: blake2_128(filler) ++ filler_encoded
			let filler_start = prefix.len() + 16;
			if key.0.len() > filler_start {
				let filler_encoded = &key.0[filler_start..];

				let offchain_key =
					pallet_intents_coprocessor::offchain_bid_key_raw(&commitment, filler_encoded);

				if let Some(data) = self.offchain_storage.get(STORAGE_PREFIX, &offchain_key) {
					// Bid encoding: filler.encode() ++ user_op.encode()
					if data.len() > filler_encoded.len() {
						if let Ok(user_op) = Vec::<u8>::decode(&mut &data[filler_encoded.len()..]) {
							bids.insert(RpcBidInfo {
								commitment,
								filler: filler_encoded.to_vec(),
								user_op,
							});
						}
					}
				}
			}
		}

	private async fetchBids(params: {
		commitment: HexString
		solver?: { address: HexString; timeoutMs: number }
		solverLockStartTime: number
	}): Promise<FillerBid[]> {
		const { commitment, solver, solverLockStartTime } = params

		const intentsCoprocessor = this.ctx.intentsCoprocessor
		if (!intentsCoprocessor) {
			throw new Error("IntentsCoprocessor required for order execution")
		}

		const fetchedBids = await intentsCoprocessor.getBidsForOrder(commitment)

		if (solver) {
			const { address, timeoutMs } = solver
			const solverLockActive = Date.now() - solverLockStartTime < timeoutMs

			return solverLockActive
				? fetchedBids.filter((bid) => bid.userOp.sender.toLowerCase() === address.toLowerCase())
				: fetchedBids
		}

		return fetchedBids
	}
