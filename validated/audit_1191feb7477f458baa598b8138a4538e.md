### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — HMAC only covers raw body, not headers (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unsigned HTTP headers. `Registry.process` validates the HMAC against the body only, then passes the header-derived `shop` value straight through to the host app's webhook handler. This breaks the intended binding: `shop` identity claimed by the request == `shop` identity cryptographically attested by the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, reads from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)` — which internally calls `request.to_signable_string` (body only) — and then constructs `WebhookMetadata` using the unsigned `request.shop`: [3](#0-2) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares to the header-supplied `hmac` value: [4](#0-3) 

Since the signature never covers the `shop-domain` header, the equality the gem is supposed to enforce — `HMAC-verified sender == shop identity attached to the payload` — does not hold. Any party that has legitimately received one genuine Shopify webhook delivery (with a valid `x-shopify-hmac-sha256` for that specific body, obtainable by any merchant/unprivileged installer of the app, without ever touching `api_secret_key`) can resend that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in `x-shopify-shop-domain`. The signature still validates because it never depended on that header, and the host app receives `WebhookMetadata#shop` set to the attacker-chosen tenant.

### Impact Explanation
This is a cross-tenant confusion vector: the gem hands the host application a `shop` value that has no cryptographic binding to the HMAC-verified payload. A host app that (per the gem's own documented usage) keys session/store lookups or writes off `data.shop` — as shown in the gem's own docs (`docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md`, which instruct handlers to use `data.shop` to route the payload) — can be tricked into applying an attacker-controlled webhook body to a victim shop's tenant context, using no privileged credentials at all (no `api_secret_key`, no access token). This satisfies the "cross-tenant access" Critical impact category, since it is the gem's own signature-verification contract, not an app bug, that fails to bind `shop` to the signed bytes.

### Likelihood Explanation
Likelihood is meaningful but requires the attacker to be an actual (even single, unprivileged) installer of the target app who receives at least one legitimate webhook delivery for their own store — a trivial precondition for any app that registers e.g. `orders/create` or `app/uninstalled`. No secret key, access token, or privileged access is needed; only a captured legitimate HMAC/body pair and control over the header sent to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the signed material used for `to_signable_string`, or otherwise cryptographically bind the `shop-domain` header to the verified payload (e.g., verify shop against the shop already known to have the topic subscription/installed session) before handing it to `WebhookHandler#handle`. At minimum, document prominently that `data.shop` from `ShopifyAPI::Webhooks::Registry.process` is unauthenticated and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. App installer for `shop-a.myshopify.com` triggers/receives a legitimate webhook, e.g. `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC for BODY>`
   - `x-shopify-shop-domain: shop-a.myshopify.com`
   - body: `BODY`
2. Attacker resends the identical `BODY` and identical `x-shopify-hmac-sha256` to the same app endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `BODY` only (`to_signable_string`) — matches, since header wasn't part of the signed content.
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop: "victim-shop.myshopify.com"`, and the host app's handler processes `BODY` as though it belongs to `victim-shop.myshopify.com`, despite the HMAC only proving the payload came from a Shopify webhook addressed to `shop-a.myshopify.com`.
