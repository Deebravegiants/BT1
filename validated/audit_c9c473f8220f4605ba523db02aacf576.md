### Title
Webhook shop-domain identity spoofing via unbound HMAC — cross-tenant webhook data confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` strictly from the `X-Shopify-Shop-Domain` HTTP header [1](#0-0) , while the HMAC signature verified by `Utils::HmacValidator.validate` is computed only over `to_signable_string`, which returns the raw request body and nothing else [2](#0-1) . The `shop` value is never part of the signed bytes, so it can be freely swapped without invalidating the signature.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . `HmacValidator.validate_signature` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field with a constant-time comparison [4](#0-3) . Since `to_signable_string` for the webhook `Request` returns only `@raw_body` [2](#0-1) , the equality that is actually enforced is:

`HMAC(api_secret_key, raw_body) == received_hmac`

but the equality the host application relies on for tenant scoping is:

`shop header == shop that produced (raw_body, hmac)`

These two are not the same binding. Because `api_secret_key` is a single shared secret for the whole app across every installed shop, any shop that has the app installed receives genuine `(raw_body, hmac)` pairs signed with that same secret. An attacker who controls their own shop installation can capture a legitimate webhook delivery, then replay the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim shop). `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` forwards `shop: request.shop` — the attacker-controlled value — to the handler as if Shopify itself asserted that shop identity [5](#0-4) .

This is documented, expected library behavior — `docs/usage/webhooks.md` tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used directly to key work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) . The gem presents `shop` as a trusted, Shopify-asserted identity field, but its own `HmacValidator` never binds it to the signature it verifies.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem markets to integrators: verified bytes (body only) do not cover the claimed tenant identity (`shop` header). A host application that uses `data.shop` from a processed webhook to select which merchant's records to update, credit, cancel, or delete (the exact pattern shown in the gem's own documentation) can be made to apply another shop's legitimate webhook payload under an attacker-chosen `shop` label, or conversely, misattribute the attacker's own shop's webhook to a victim shop. This is a cross-tenant identity confusion rooted entirely in this gem's `Request`/`HmacValidator` design, not in any misuse of undocumented API.

### Likelihood Explanation
Any developer who has the app installed on their own store (a normal, easily obtainable unprivileged capability for any Shopify Partner/developer account) can capture real webhook deliveries for their shop and immediately has a valid `(raw_body, hmac)` pair signed with the app's single shared `api_secret_key`. Forging the `X-Shopify-Shop-Domain` header on a replayed HTTP POST requires no cryptographic material and no privileged access — only the ability to send an HTTP request to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the value that is cryptographically verified, not just into an unauthenticated header:
- Include `shop_domain` (and `topic`) in the signed material checked by `HmacValidator.validate`, e.g., extend `VerifiableQuery`/`to_signable_string` for `Webhooks::Request` to incorporate the header fields the gem trusts, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed params [7](#0-6) .
- Alternatively, since Shopify's real webhook HMAC is computed over the body only by design, the gem should explicitly document that `shop` is unauthenticated and must be independently corroborated (e.g., against a known/registered shop list) by the integrator before being used for tenant-scoped side effects, rather than presenting it as a trusted field in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; wait for (or trigger, e.g. by updating an order) a real webhook delivery to the app's registered endpoint. Capture the raw body `B` and header `X-Shopify-Hmac-Sha256: H` — this pair satisfies `HMAC(api_secret_key, B) == H`.
2. Send a new HTTP POST to the same webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (attacker-chosen)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`: copied or adjusted freely
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equals `H` — validation passes [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to attribute attacker-controlled/attacker-shop webhook content to `victim.myshopify.com`.
