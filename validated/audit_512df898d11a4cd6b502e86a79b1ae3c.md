### Title
New account position maps are written at the network-default TTL instead of the protocol's user TTL window, so `SupplyPositions`/`BorrowPositions` entries can archive early and freeze an account - (File: contracts/controller/src/storage/account.rs)

### Summary
The external bug class is "account creation funded with a hardcoded default resource parameter instead of the live/intended value, leaving the entry under-resourced and subject to premature reclamation (DoS)". The Soroban analog is storage-entry TTL: every new persistent entry receives only the network minimum TTL unless the contract explicitly extends it. The controller bumps `AccountMeta` and `Delegates` to the protocol's 120-day user window on creation via `set_user`/`renew_user_key`, but writes the `SupplyPositions` and `BorrowPositions` maps through `write_side_map`, which calls `persistent.set(key, map)` with no `extend_ttl`. The code comments acknowledge this ("position-map writes do not [renew]"). A position NFT minted alongside the account is explicitly lifted to the user window for exactly this reason (`extend_user_persistent_ttl` in position-nft), so the position maps are left materially shorter-lived than every other piece of the same account.

### Finding Description
`set_supply_positions` and `set_debt_positions` route to `write_side_map` (`account.rs:94-105`), which performs `persistent.set(key, map)` and nothing else. On a fresh write this leaves the entry at the network minimum entry TTL. In contrast, `set_account_meta` uses `set_user`, which extends the key with `TTL_THRESHOLD_USER`/`TTL_BUMP_USER` (30-day threshold, 120-day bump), and `remove_account_entry`/`renew_user_account` treat all four account keys as a single lifetime unit. The account's balance-bearing state (the position maps) therefore expires roughly 90 days before its own metadata and NFT pointer. Only a read via `get_user` or a call to `renew_user_account`/`renew_account` re-extends the maps; nothing extends them at creation.

### Impact Explanation
Once a `SupplyPositions`/`BorrowPositions` entry archives, every controller path touching that account (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `get_account`) fails because archived persistent entries make the transaction footprint invalid until a `RestoreFootprint` operation is submitted. The deposited collateral is frozen until an archive restore is executed — a temporary freezing of user funds, reachable purely by an unprivileged user creating a position and not transacting within the network minimum TTL window. It also creates an asymmetric griefing surface during liquidation: a liquidator who has not prepared a restore transaction cannot liquidate an archived-account borrower.

### Likelihood Explanation
Triggering requires no attacker and no privileged action: any user calls `supply`/`borrow`, creating maps at default TTL, then goes dormant longer than the network minimum (shorter than the 120-day design window). Accounts created for one-off interactions (dust positions, abandoned borrows, bad-debt candidates) are exactly the ones that go dormant. The inconsistency is proven by the code comments themselves and by position-nft `mint`, which performs the missing lift for NFT entries.

### Recommendation
After `persistent.set` in `write_side_map` (or inside `set_supply_positions`/`set_debt_positions`), call `env.storage().persistent().extend_ttl(key, TTL_THRESHOLD_USER, TTL_BUMP_USER)`, matching `set_user` and `renew_user_key`, so all account entries share the same 120-day renewal window from creation.

### Proof of Concept
1. User calls `controller.supply(account_id=0, spoke_id, [(hub_asset, amount)])`. `set_account_meta` bumps `AccountMeta` to ~120 days; `set_supply_positions` writes `SupplyPositions` at network minimum TTL.
2. Advance ledgers past the network minimum but below `TTL_BUMP_USER`. `persistent.has(SupplyPositions)` now resolves to an archived entry while `AccountMeta` and the NFT `Owner` entry remain live.
3. Any `withdraw`, `supply`, or `liquidate` referencing the account traps on the archived footprint; the funds stay frozen until someone submits `RestoreFootprintOp` for the position-map keys.
