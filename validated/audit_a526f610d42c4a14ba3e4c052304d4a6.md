## Valid Analog Found

The reported bug class — a wildcard pattern converted into an allowlist matcher with **broader-than-intended semantics due to a missing subdomain boundary check** — has a direct analog in chainlink's Gateway HTTP server CORS origin allowlist logic.

### Title
CORS wildcard origin allowlist bypass via missing subdomain boundary check in `isAllowedOrigin` - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The Gateway's HTTP server implements a custom CORS origin allowlist that supports wildcard patterns like `*.example.com`. The wildcard matching strips the `*.` prefix and then checks `strings.HasSuffix(originHost, allowedHost)` with no dot-boundary enforcement, so any origin whose hostname merely *ends with* the configured suffix — including malicious sibling domains like `evilexample.com` — is incorrectly treated as a valid subdomain of `example.com`.

### Finding Description
`isAllowedOrigin` parses the request `Origin` header and, for each configured `CORSAllowedOrigins` entry starting with `*.`, strips the `*.` prefix and performs a raw suffix comparison: [1](#0-0) 

Because `strings.HasSuffix` has no notion of a `.` (label) boundary, a configured pattern of `*.remix.com` is meant to match only actual subdomains such as `foo.remix.com`, but it will also match any hostname that happens to end with the literal characters `remix.com`, such as `evilremix.com` or `notremix.com`. This is structurally the same root cause as the reported `@astrojs/netlify` issue: a wildcard/pattern conversion that is not anchored to the semantic boundary (subdomain separator / path segment separator) that the canonical matcher requires, producing a broader-than-intended allowlist.

The existing test suite for this function only validates *true positive* subdomain matches (e.g. `remix.ethereum.org` against `*.ethereum.org`) and *negative* cases that differ by scheme/port/exact suffix mismatch, but never tests a hostile suffix-collision case like `evilethereum.org` against `*.ethereum.org`: [2](#0-1) [3](#0-2) 

This confirms the gap was not intentionally tested/hardened against.

### Impact Explanation
The `Origin` header is fully attacker-controlled (any unprivileged website can be scripted to make a request against the Gateway's public HTTP endpoint from a victim's browser). When `CORSEnabled` is true and the origin incorrectly matches, the handler reflects the attacker's origin into `Access-Control-Allow-Origin`, permitting cross-origin JavaScript running on an unrelated attacker-registered domain (e.g. `evilexample.com`, which merely shares a suffix with a configured trusted wildcard like `*.example.com`) to read the JSON-RPC-style response returned by the Gateway on behalf of the requesting browser context: [4](#0-3) 

This is a cross-origin response confusion / allowlist bypass: it breaks the operator's intended isolation of "only these specific trusted subdomains may read Gateway responses in-browser," allowing an attacker who can register or control a suffix-colliding domain to read responses meant only for the trusted family of subdomains.

### Likelihood Explanation
Exploitability only requires: (1) the Gateway operator has CORS enabled with at least one wildcard entry in `CORSAllowedOrigins`, and (2) an attacker registers or otherwise controls a domain sharing the tail-string of that entry. Domain registration is trivial and does not require any privileged network position — this is a pure unprivileged web-client scenario, consistent with the rules requiring unprivileged-actor reachability via the internet-facing gateway.

### Recommendation
Anchor the wildcard match on a label boundary rather than a raw string suffix — i.e., require that `originHost` equals `allowedHost` or ends with `"." + allowedHost`:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add regression tests covering suffix-collision hostnames (e.g. `evilexample.com` vs `*.example.com`) to prevent regression.

### Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From a browser on attacker-controlled `https://evilremix.com`, issue a cross-origin `fetch` request to the Gateway's HTTP endpoint with `Origin: https://evilremix.com`.
3. `isAllowedOrigin` strips `*.` to get `remix.com`, then `strings.HasSuffix("evilremix.com", "remix.com")` evaluates `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilremix.com`, letting the attacker's page read the JSON response body that was only intended to be readable by genuine `*.remix.com` subdomains.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
