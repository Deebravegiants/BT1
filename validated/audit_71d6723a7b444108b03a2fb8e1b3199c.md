### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain` header — which the registry hands to app handlers as the authoritative tenant identifier — is never included in the signed bytes. Any principal capable of obtaining a validly-signed webhook body/HMAC pair for their own shop (e.g., a merchant who installs the app on their own store) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header. `HmacValidator.validate` will still pass because it never examines the `shop` field, so the handler is invoked believing the event originated from the spoofed shop.

### Finding Description
This is the same identity-binding class the external report describes: a field that is *acted upon* (here, tenant attribution via `shop`) is not covered by the mechanism meant to bind authenticity (here, the HMAC).

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from an unauthenticated header, independent of the signed bytes: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` only ever HMACs `verifiable_query.to_signable_string` (i.e. the body) against `Context.api_secret_key`, so it can never detect header tampering: [3](#0-2) 
- `Registry.process` treats a passing `HmacValidator.validate` as sufficient proof of authenticity, then forwards `request.shop` (from the header) straight into `WebhookMetadata` for the app handler to act on — the shop value is never re-derived from or checked against the signed body: [4](#0-3) 

The correct binding should be: `shop-domain-header == shop-that-generated-this-body-under-the-shared-secret`. Because `shop` is excluded from `to_signable_string`, that equality is never enforced — only `raw_body == raw_body-that-was-signed` is checked.

### Impact Explanation
Any unprivileged internet user who can become a merchant that installs the app (a normal, unprivileged onboarding flow, not requiring theft of `api_secret_key` or an access token) receives genuine Shopify-signed webhook deliveries containing `(raw_body, hmac)` for their own store. Because the header is unauthenticated, they can replay that valid `(raw_body, hmac)` pair to the app's public webhook endpoint with an arbitrary `shop-domain` value naming a victim tenant. If the host application (following this gem's documented `WebhookMetadata.shop`/`Registry.process` contract) uses `data.shop` to select which tenant's database row/session/webhook state to update — which is exactly the intended and documented use of that field — this results in cross-tenant data corruption/confusion: an attacker-controlled payload is attributed to and processed against another merchant's tenant.

### Likelihood Explanation
High reachability: the webhook receiver is by design a public, unauthenticated HTTP endpoint that only gates on `HmacValidator.validate`; no additional identity check on `shop` exists in the library's `process` path. An attacker only needs a normal (unprivileged) app install to obtain valid signed payload bytes.

### Recommendation
Include the `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers in the signed material verified by `HmacValidator`, or independently require the host application to cross-check `request.shop` against a shop that is known to have a currently active session/installation before trusting it for tenant routing. At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated and must be revalidated against installed-shop records before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` via normal OAuth (no credential theft required).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
3. Attacker captures/replays this exact `raw_body` and `x-shopify-hmac-sha256` value in a new HTTP request to the same endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) — `lib/shopify_api/webhooks/request.rb` lines 45-63.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and compares to the (unchanged, still-valid) `hmac` header — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
6. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and dispatches to the app's handler (`lib/shopify_api/webhooks/registry.rb` lines 198-199), which acts on `victim-shop.myshopify.com`'s tenant data despite the payload actually originating from the attacker's own shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
