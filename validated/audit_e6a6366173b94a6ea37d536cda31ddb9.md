### Title
Zero-amount withdrawal via `createWithdrawalIntents` still debits a nonzero `token_diff` fee - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount` independently of `_estimateWithdrawalFee`'s guard logic, so calling it directly with `withdrawalParams.amount: 0n` and `feeInclusive: false` bypasses the only place `FeeExceedsAmountError` is thrown. Every bridge's `createWithdrawalIntents` unconditionally emits a `token_diff` intent sized from `feeEstimation.quote.amount_in`/`amount_out`, independent of `withdrawalParams.amount`, so a zero-value withdrawal still produces a real, nonzero debit.

### Finding Description
The claimed equality is: total debit across produced intents == principal withdrawn (`amount`) + fee, counted once. In `createWithdrawalIntents` (sdk.ts:342-344), when `feeInclusive` is `false`, `actualAmount = args.withdrawalParams.amount` is used as-is with no relation checked against `feeEstimation`. This differs from `_estimateWithdrawalFee` (sdk.ts:421-424), which only throws `FeeExceedsAmountError` when `feeInclusive` is `true` and `amount <= fee.amount` — that guard is never exercised in the `feeInclusive: false` path, and is entirely absent from `createWithdrawalIntents` regardless.

Every bridge implementation (`direct-bridge.ts:120-131`, `omni-bridge.ts:304-315`, `hot-bridge.ts:208-219`, `aurora-engine-bridge.ts:92-103`) pushes a `token_diff` intent built solely from `args.feeEstimation.quote.amount_in` / `amount_out` whenever `feeEstimation.quote != null` — with no check that this fee bears any relation to `withdrawalParams.amount`, and no check that `amount` is nonzero. [1](#0-0) [2](#0-1) 

An attacker (an integrator forwarding caller-supplied `withdrawalParams`/`feeEstimation`, or a caller who bypasses the SDK's own `estimateWithdrawalFee` and constructs `feeEstimation` themselves) can call `createWithdrawalIntents({ withdrawalParams: { amount: 0n, feeInclusive: false, ... }, feeEstimation: { quote: { amount_in: <large>, amount_out: <large>, ... }, amount: <large> } })`. This produces intents including a `token_diff` debiting `amount_in` from the user with no corresponding principal ever withdrawn, since the withdrawal-specific intent (e.g. `ft_withdraw`) carries `amount: "0"`.

Existing guards do not prevent this: `FeeExceedsAmountError` only fires for the `feeInclusive: true` branch inside `_estimateWithdrawalFee`, which callers are not required to invoke before calling `createWithdrawalIntents` directly. `validateWithdrawal`'s `skipMinAmountValidation` is only set from within `_estimateWithdrawalFee` (sdk.ts:439-441) — it is not passed at all from `createWithdrawalIntents` (sdk.ts:346-354), so whatever minimum-amount check exists there would apply, but I could not fully verify (due to tool budget exhaustion) whether the individual bridges' `validateWithdrawal` implementations (e.g., `omni-bridge.ts`, `poa-bridge.ts`) independently enforce `amount > 0` or reject a `feeEstimation.quote.amount_in` that isn't otherwise pinned to `withdrawalParams.amount`. The test at `sdk.test.ts:317-375` demonstrates the SDK trusts the caller-supplied `feeEstimation` verbatim to build the `token_diff`, with no cross-check against `amount`. [3](#0-2) 

### Impact Explanation
If reachable, this results in a `token_diff` intent — signed and executed as part of the withdrawal batch — debiting the user's balance for the quoted `amount_in` while zero value is delivered as principal to the destination. This matches the Critical category: "a fee error draining a material share of the amount" (here, effectively all of it, since principal is zero). The debit would be signed by the user's own intent signer as part of the batch returned by `createWithdrawalIntents`, so it is real funds movement, not merely metadata.

### Likelihood Explanation
This requires the caller (or an integrator on the caller's behalf) to independently supply a `feeEstimation` object rather than obtaining it from the SDK's own `estimateWithdrawalFee`, and to set `amount: 0n, feeInclusive: false`. This is a plausible integration pattern since `feeEstimation` and `withdrawalParams` are separate, uncoupled arguments to a public method with no cross-validation between the quote and the amount. Whether this is actually exploitable end-to-end depends on unverified bridge-level `validateWithdrawal` checks (I was unable to confirm within the available tool budget whether any bridge rejects `amount === 0n` outright in the non-`feeInclusive` case), which is a material uncertainty.

### Recommendation
In `IntentsSDK.createWithdrawalIntents`, validate that `feeEstimation` is consistent with `withdrawalParams.amount` — at minimum, reject `amount === 0n` (or `actualAmount === 0n`) unless it is an explicitly zero-fee scenario (`feeEstimation.amount === 0n` and `feeEstimation.quote == null`), mirroring the `FeeExceedsAmountError` check currently only performed in `_estimateWithdrawalFee`, and enforce it unconditionally regardless of `feeInclusive`.

### Proof of Concept
```ts
// vitest, mocks HTTP only (via existing test harness in sdk.test.ts)
it("rejects zero-amount withdrawal that still debits a real fee", async () => {
  const sdk = new IntentsSDK({ referral: "", intentSigner });
  const feeEstimation = {
    amount: 1_000_000n,
    quote: {
      defuse_asset_identifier_in: "nep141:eth.bridge.near",
      defuse_asset_identifier_out: "nep141:wrap.near",
      amount_in: "1000000",
      amount_out: "1000000000000000000",
      expiration_time: "2099-01-01T00:00:00.000Z",
      quote_hash: "fakehash",
    },
    underlyingFees: {},
  };

  const intents = await sdk.createWithdrawalIntents({
    withdrawalParams: {
      assetId: "nep141:eth.bridge.near",
      amount: 0n,
      destinationAddress: "0x0000000000000000000000000000000000000001",
      feeInclusive: false,
    },
    feeEstimation,
  });

  const tokenDiff = intents.find((i) => i.intent === "token_diff");
  // LHS: total principal delivered == 0
  // RHS: token_diff debit == feeEstimation.quote.amount_in (nonzero)
  expect(tokenDiff?.diff["nep141:eth.bridge.near"]).toBe("-1000000"); // nonzero debit
  const withdraw = intents.find((i) => i.intent === "ft_withdraw");
  expect(withdraw?.amount).toBe("0"); // zero principal delivered
});
```
This demonstrates that the debit side of the equality (`token_diff` = 1,000,000) is nonzero while the principal-delivered side (`ft_withdraw.amount` = 0) is zero, breaking the intended equality.
