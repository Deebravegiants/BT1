Confirmed root cause. The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves the body's integrity, never binding the `shop-domain` header that `Registry.process` trusts as the tenant identifier passed into the handler's `WebhookMetadata` [2](#0-1) . This is a genuine field-not-covered-by-HMAC analog matching the report's bug class.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body via `to_signable_string`, while `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read separately and passed unauthenticated into the webhook handler as the tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` [3](#0-2) . For webhooks, `to_signable_string` returns only `@raw_body`, excluding all headers [1](#0-0) . Meanwhile `shop` is read directly from the `shop-domain` header, independent of the HMAC computation [4](#0-3) . `Registry.process` validates the HMAC against the body only, then forwards `request.shop` straight into `WebhookMetadata` given to the app's handler as the shop for that event [2](#0-1) . As documented, apps use `data.shop` directly to key their own tenant-scoped processing/storage [5](#0-4) . Because the header is outside the signed content, the binding "shop asserted to the handler == shop that produced this signed body" does not hold: an unprivileged attacker who has observed one genuine webhook delivery (body + valid HMAC, e.g. for their own shop/free trial store, or any webhook data made observable to them) can resend the exact same body/HMAC pair to the app's public webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` will still return true since it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, even though Shopify never sent that body for the victim shop.

### Impact Explanation
This crosses tenant boundaries without needing the app's `client_secret`: an app that trusts `data.shop` (as its own documentation recommends) to select the tenant record when persisting webhook data can be made to attribute attacker-controlled body content to a different, victim shop — a cross-tenant data integrity/confidentiality violation using only a previously-observed valid webhook and no credentials.

### Likelihood Explanation
Requires the attacker to have captured one legitimately-signed webhook body/HMAC pair (e.g., from their own store's webhook traffic, which they legitimately receive) and to know/guess a victim shop domain, then replay it against the app's public webhook endpoint with a substituted header. No secret or privileged access is required, but it does require topic/body content to be something benign-looking or attacker-triggerable in their own store (e.g., `orders/create` on their own test shop), then relabeled as another shop's event.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop` to the signed body before constructing `WebhookMetadata`, e.g. by having `to_signable_string` incorporate `shop` alongside `@raw_body`, and reject requests where this binding cannot be verified.

### Proof of Concept
```ruby
# Attacker owns shop A and receives a legitimate webhook from Shopify:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret_unknown_to_attacker_but_signature_captured, raw_body)
)
# (attacker just captures body + hmac header pair from their own real webhook delivery)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,       # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # swapped from attacker's own shop
  "x-shopify-webhook-id" => "replayed-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks raw_body
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed_body, ...)
# App code that uses data.shop to select the tenant record now attributes attacker body to victim shop.
```
