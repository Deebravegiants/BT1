### Title
Webhook `shop-domain` (and `topic`) headers are trusted without HMAC coverage, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC in the `X-Shopify-Hmac-Sha256` header matches a signature computed over the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` header values are never part of the signed material, yet they are the values the gem hands to the consuming app's `WebhookHandler#handle` as authoritative tenant/context identifiers.

### Finding Description
`Utils::HmacValidator.validate` calls `validate_signature`, which computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from mutable HTTP headers with no cryptographic binding to the HMAC [7](#0-6) .

`Registry.process` only gates on `Utils::HmacValidator.validate(request)` before dispatching `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [1](#0-0) . This breaks the intended identity binding: `shop` (and `topic`) claimed by `WebhookMetadata` should equal the shop that actually produced the HMAC-signed `body`, but the gem never checks that equality — any `shop`/`topic` string can be attached to any validly-signed body.

Because the API secret (`client_secret`) is shared across every shop installing the same app, an attacker who controls their own shop can trigger a legitimate webhook delivery to the app's endpoint (a valid `(body, hmac)` pair signed with the app's `client_secret`), capture it, and replay it while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. The gem will report `Utils::HmacValidator.validate` as `true` (the body/HMAC pair is authentic) and pass the forged `shop` value straight through to the app's handler as trustworthy.

### Impact Explanation
This crosses the tenant boundary this gem is supposed to enforce: an app built on `WebhookHandler#handle` typically uses `data.shop` [8](#0-7)  to look up the tenant's offline session/access token and apply the webhook body's data against that tenant's records (e.g., order/customer sync). An attacker-controlled shop can therefore force a genuinely-signed webhook payload to be attributed to and processed for an arbitrary victim shop, resulting in cross-tenant data contamination through the gem's own trusted-metadata contract — matching the "Critical - cross-tenant access" impact bucket, since the confusion is caused entirely by the gem's verification logic, not by any documented misuse by the host app.

### Likelihood Explanation
Requires only an unprivileged attacker who owns any shop installing the same app (a normal, low-privilege position — no access token, `client_secret`, or victim credentials needed) to trigger one real webhook delivery to their own store and replay it with a modified header, which is straightforward given the webhook processing takes headers/body as caller-supplied input (`Registry.process(request)` with `Request.new(raw_body:, headers:)`).

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-signed material, or otherwise verify out-of-band that the `shop-domain` header matches the shop the app expects for that specific delivery/subscription (e.g., cross-check against the webhook subscription's registered shop) before constructing `WebhookMetadata`, rather than trusting the header as-is once only the body's HMAC has been validated.

### Proof of Concept
1. App A is installed on `attacker.myshopify.com` and `victim.myshopify.com`, sharing one `client_secret`.
2. Attacker triggers a webhook event on their own store (`attacker.myshopify.com`), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid signature over `B` using the shared `client_secret`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H, ...})` is built; `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `B` against `H`.
5. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the app to process attacker-controlled data as though it originated from `victim.myshopify.com`.
