### Title
Unsanitized `shop` parameter in `Oauth.begin_auth`/`validate_auth_callback` allows the app's `client_secret` to be sent to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the OAuth token-exchange host directly from the caller-supplied `shop` string without running it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`). Because `validate_auth_callback` posts the app's `client_id`/`client_secret` to `https://#{auth_query.shop}/admin/oauth/access_token`, an unsanitized `shop` value breaks the intended binding "shop authenticated as a real Shopify tenant" == "host that receives the app's `client_secret`".

### Finding Description
`Oauth.begin_auth(shop:, redirect_path:, ...)` computes the authorize URL as: [1](#0-0) 
`auth_base_uri(shop)` simply interpolates the raw `shop` string into `"https://#{shop}/admin"` with no domain-format check.

`validate_auth_callback` then uses the *same unsanitized* `auth_query.shop` to build the session used for the access-token POST that carries `client_secret`: [2](#0-1) 

`HttpClient#initialize` derives the request host directly from `session.shop`: [3](#0-2) 

Contrast this with the other two flows in the same file tree that also transmit `client_secret`, both of which explicitly call `Utils::ShopValidator.sanitize!` (which restricts the host to `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) before constructing the session: [4](#0-3) [5](#0-4) 

`AuthQuery`/`HmacValidator` do cover `shop` in the HMAC signature computed with the app's own `api_secret_key`: [6](#0-5) [7](#0-6) 

However, the HMAC only proves the query string was signed with the app's secret at some point — it does **not** independently prove `shop` is a genuine `*.myshopify.com` (or other trusted) domain. The gem itself provides `ShopValidator` specifically to enforce that constraint on host-supplied `shop` values before they are used to build request/redirect targets, and applies it consistently everywhere else `client_secret` is transmitted — except in `oauth.rb`. This is the exact "host validated versus host that receives the `client_secret`" identity-binding break called out in scope: the equality that should hold is `sanitize(shop) == shop_used_for_client_secret_POST`, but in `oauth.rb` the right-hand side uses the raw, unsanitized value.

### Impact Explanation
If a host application passes a browser/query-supplied `shop` value straight into `begin_auth`/`validate_auth_callback` (which the library's own documented usage pattern explicitly shows — `shop = request.headers["Shop"]` fed directly into `begin_auth`), an unprivileged internet user can supply a non-Shopify hostname as `shop`. Because `begin_auth` never sanitizes it, `auth_route` will point at an attacker-controlled host, and if the flow is later completed (e.g., an attacker-run "Shopify Admin" clone that returns a self-crafted OAuth `code` for its own domain in the callback query), `validate_auth_callback`'s access-token POST — containing `client_secret` in the request body — is sent by the app's server to that attacker-controlled host. This is credential leakage of the app's `client_secret` to a third-party host, which the scope explicitly classifies as a Critical/High-impact outcome (theft/exfiltration of the app's `client_secret`).

### Likelihood Explanation
The library's own documentation shows the exact vulnerable pattern (passing an unvalidated `shop` header value directly to `begin_auth`), and the asymmetry with `ClientCredentials`/`RefreshToken` (which do sanitize) shows the gem's authors are aware this validation is required for any flow that transmits `client_secret`, making its absence here a genuine gap rather than an intentional design choice. Exploitability does require host applications to follow the documented (but insecure) usage pattern of not pre-validating `shop`, and it also requires an attacker to be able to complete a full round-trip through a spoofed authorize endpoint returning a matching `code`/`state`/`hmac` for the callback to succeed with `client_secret` transmission — the `hmac` on the callback is still checked against the app's real secret, but the callback's `shop` field, which the HMAC also covers, is entirely attacker-chosen at the time the attacker's spoofed "Shopify" authorize page redirects back, since `hmac` is not being computed by real Shopify but potentially replayed/derived only if the app blindly trusts a `code` exchange later — this weakens confidence but does not eliminate the root-cause gap: the library provides no defense-in-depth check on `shop` here, unlike its sibling flows.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) inside `Oauth.begin_auth` and use the sanitized value for both `auth_base_uri` and the `AuthQuery`/session construction in `Oauth.validate_auth_callback`, matching the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Host app implements the documented pattern: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. Attacker requests the login route with `Shop: attacker.example`.
3. `auth_base_uri("attacker.example")` returns `"https://attacker.example/admin"`, and the user's browser is redirected to `https://attacker.example/admin/oauth/authorize?...`, fully attacker-controlled.
4. Attacker's server, posing as Shopify, immediately redirects back to the app's real callback URL with a `shop=attacker.example` parameter it controls.
5. If the app's callback flow proceeds to `validate_auth_callback` (or an equivalent code path that does not independently validate `shop`), the resulting `client.request` in `lib/shopify_api/clients/http_client.rb` builds `@base_uri = "https://attacker.example"` from `session.shop` and issues the POST containing `client_secret` in its body to that attacker host.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
