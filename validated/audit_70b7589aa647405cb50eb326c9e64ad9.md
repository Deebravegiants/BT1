Based on my investigation, I've confirmed the root cause. The `topic`, `shop`, `webhook_id`, and `api_version` fields of an incoming webhook are read from HTTP headers, while `Utils::HmacValidator.validate` only checks the HMAC against the **raw request body** — the identity fields are never part of the signed content.

### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw body, then trusts the `shop-domain` (and `topic`/`webhook_id`/`api_version`) HTTP header as-is when building `WebhookMetadata` passed to the host app's handler. Because these header-derived fields are outside the signed payload, any actor who can produce one validly-signed webhook body/HMAC pair for the app's `client_secret` (e.g. by installing the app on their own store and receiving one legitimate webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process/store that body under a victim shop's tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` binds the HMAC exclusively to the body bytes: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC, then unconditionally trusts `request.shop` (and the other header fields) to build the `WebhookMetadata` handed to the host app's handler: [4](#0-3) 

The documented handler contract explicitly instructs apps to use `data.shop` as the tenant identifier for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The equality that should hold — `shop authenticated (cryptographically bound to the HMAC) == shop used as tenant key` — is broken: the gem verifies `hmac == HMAC(body, secret)` but then uses `shop = header value`, a byte range never covered by that HMAC.

### Impact Explanation
Any party that has ever received one legitimately signed webhook from Shopify for the app (trivial: install the free app on any store and trigger any webhook) can capture that raw body + `X-Shopify-Hmac-Sha256` header, then POST it directly to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim merchant. `Utils::HmacValidator.validate` will still return `true` (it only checks the body), and the host app's handler will process/store attacker-supplied data under the victim's tenant. This is a cross-tenant data-integrity/confusion vulnerability reachable without any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented handler pattern: no special access is required beyond having received one webhook delivery for any shop (including the attacker's own store), and the webhook HTTP endpoint is by definition internet-reachable and unauthenticated apart from the HMAC.

### Recommendation
Bind the identity-relevant headers into the signed payload verification, or otherwise force the app to independently confirm `shop` against a known/authenticated tenant (e.g., cross-check `request.shop` against the shop associated with the `webhook_id`/subscription via a server-side lookup) before trusting it as a tenant key. At minimum, document prominently that `data.shop` is unauthenticated and must not be used as a tenant key without independent verification.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `products/update`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header sent by Shopify (H = HMAC-SHA256(B, client_secret)).
2. Replay directly to the app's webhook endpoint:
```
POST /callback/products/update HTTP/1.1
X-Shopify-Topic: products/update
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim.myshopify.com
X-Shopify-Webhook-Id: <any>
X-Shopify-Api-Version: 2024-01

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which (per documented usage) stores/queues the body keyed by `victim.myshopify.com`, even though the payload actually originated from the attacker's own shop.
