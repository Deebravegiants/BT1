## Title
Vesting contract distribution uses raw `coin::balance<AptosCoin>(contract_address)` instead of tracked withdrawal amount, allowing donated/foreign APT to be misdistributed - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::withdraw_stake` computes the amount to distribute to vesting shareholders by reading the entire current `AptosCoin` balance of the vesting contract's resource account, rather than tracking the exact amount returned/deposited by the just-executed `staking_contract::distribute` call. This mirrors the `StabilityPool::calculateRaacRewards` pattern in the external report, where `balanceOf(address(this))` is trusted as the reward-accounting source instead of an internally tracked delta.

### Finding Description
In `withdraw_stake`: [1](#0-0) 
the function calls `staking_contract::distribute(contract_address, vesting_contract.staking.operator)` — an entry function with no return value that deposits the staker's share of unlocked stake directly into the vesting contract's resource-account `CoinStore` via `aptos_account::deposit_coins` inside `staking_contract::distribute_internal`: [2](#0-1) 
Immediately after, `withdraw_stake` reads `coin::balance<AptosCoin>(contract_address)` — the **total** balance of that account — and withdraws and treats that entire amount as `total_distribution_amount`, splitting it pro-rata among `grant_pool` shareholders in `distribute`: [3](#0-2) 

The vesting contract's resource account is created with `coin::register<AptosCoin>(&account_signer)` in `create_vesting_contract_account`, so it can freely receive AptosCoin transfers from any unprivileged account via standard `coin::transfer`/`aptos_account::transfer` calls, since there is no access control on receiving coins: [4](#0-3) 

Because `withdraw_stake` never records what the pre-call balance was, and instead trusts the post-call raw balance query, any AptosCoin sent to the vesting contract's account by anyone (accidental, intentional donation, or an unrelated protocol interaction) becomes indistinguishable from the actual unlocked staking rewards and is swept into `total_distribution_amount`, then redistributed to vesting shareholders/operator according to `grant_pool` shares — not to whoever sent it.

### Impact Explanation
This breaks the custody invariant that only funds legitimately unlocked from the associated stake pool should be distributed through the vesting shareholder split. Any externally deposited APT sent to a known/derivable vesting-contract resource-account address is unconditionally re-routed to the current grant-pool shareholders and operator commission recipients, corrupting supply/custody accounting and moving value to unintended holders. Since vesting-contract addresses are deterministic (derivable from admin address + nonce + salt) and discoverable via view functions like `stake_pool_address`, this is not merely theoretical. The impact is asset **misdirection of AptosCoin to unintended holders**, which the custody impact gate covers as "Supply or custody accounting corruption that moves value to the wrong holder."

### Likelihood Explanation
Exploitation requires only a standard `coin::transfer`/`aptos_account::transfer` to a known, permissionlessly-computable address, followed by a permissionless call to `vest`/`distribute`/`distribute_many` (all public entry functions requiring no special role). No privileged access is needed on either the sending or triggering side, making the likelihood high for any vesting contract that is publicly known (which is standard, since Aptos foundation/team vesting contracts and their addresses are typically public).

### Recommendation
Do not rely on `coin::balance<AptosCoin>(contract_address)` after calling `staking_contract::distribute`. Instead:
- Capture the resource account's `AptosCoin` balance immediately before calling `staking_contract::distribute`, and compute `withdrawn_coins` as the **delta** (post-balance minus pre-balance), so only the freshly unlocked staking rewards are distributed; or
- Modify/wrap the staking-contract distribution flow so it returns the exact `Coin<AptosCoin>` amount distributed to the staker, rather than depositing directly into the account and requiring a balance read-back.

### Proof of Concept
Conceptual sequence (cannot be executed without framework/test harness access in this session):
1. Deploy/observe a `VestingContract` at deterministic address `contract_address` (derivable via `create_resource_account_seed`/`stake_pool_address` view function).
2. Attacker or any user calls `aptos_account::transfer(attacker, contract_address, X)` to send `X` extra APT directly into the vesting contract's resource account (which is registered for AptosCoin).
3. Anyone calls `vesting::vest(contract_address)` or `vesting::distribute(contract_address)`.
4. `withdraw_stake` reads `coin::balance<AptosCoin>(contract_address)`, which now includes the legitimately unlocked stake rewards **plus** the attacker's `X` extra APT.
5. `distribute` splits this inflated `total_distribution_amount` (including `X`) among the vesting contract's shareholders/operator according to `grant_pool` shares, none of which is the address that sent `X`.

**Note:** I was not able to fully execute or verify this end-to-end in a live test environment within this session (no filesystem/terminal access), and I could not locate an explicit doc/comment confirming or denying this "sweep-any-balance" behavior is an intentionally accepted design trade-off in the codebase. If deeper verification is required — e.g., confirming whether any invariant elsewhere restricts external deposits into this specific resource account, or whether `distribute`/`vest` include any balance-sanity check I may have missed — a Devin session with full repository and test-execution access should be used to write and run a Move unit test reproducing this exact sequence against `vesting.move`.

        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
