### Title
Webhook shop-domain identity not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using `request.shop`, a value read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header. That header is never included in the HMAC-signed material, so the tenant identity ("which shop this event belongs to") is not cryptographically bound to the signature that authenticates the payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` for this class returns only `@raw_body`: [1](#0-0) 

`shop` is parsed from a header and exposed as a plain accessor, entirely outside the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` validates the HMAC on the request and then immediately hands `request.shop` — the unauthenticated header value — to the app's webhook handler as the tenant identifier for the event: [4](#0-3) 

The binding that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. In this implementation, `shop_bound_by_hmac` is undefined (the signature covers only the body), while `shop_delivered_to_handler = header["shop-domain"]`. Because the `api_secret_key` used to compute/verify the HMAC is a single per-app secret shared across every shop that installs the app (not a per-shop secret), a valid HMAC over a given body only proves "this body was signed by an entity holding this app's secret" — it does not prove which shop the event pertains to. Any body+HMAC pair that is valid for one shop remains valid unchanged if the `shop-domain` header is swapped for a different shop's domain, since the header plays no role in the signature computation or verification.

### Impact Explanation
An attacker who legitimately controls one shop that has the vulnerable app installed can capture a genuine, validly-signed webhook (body + `hmac-sha256` value) that Shopify sends to the app's webhook endpoint for their own store's events. By replaying that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a different (victim) shop's domain, the forged request passes `HmacValidator.validate` unchanged (the check only looks at `raw_body` and the `hmac` header), and `Registry.process` will invoke the app's handler with `shop: <victim shop>` and attacker-controlled `body`. Any application logic that trusts `WebhookMetadata#shop` as the tenant key (e.g., to look up which merchant's session/data/settings to update) will act on forged data attributed to a shop the attacker does not control — a cross-tenant confusion/impersonation primitive reachable by any unprivileged party who can install the app on a shop they control and can send arbitrary HTTP requests to the app's exposed webhook route.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that are publicly installable (any merchant can install a public app and generate legitimate webhook traffic for their own shop), and the webhook HTTP endpoint is by design internet-reachable and unauthenticated apart from the HMAC check. No secrets beyond ordinary use of the app as any merchant are required; the attacker never needs the `api_secret_key`, an access token, or another merchant's credentials — only the ability to send a forged HTTP POST with a modified header, which is trivial.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting a bare header:
- Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the signed/verified material, or
- Cross-check the header-provided shop against a shop value embedded in the JSON body where Shopify includes one, or
- At minimum, document and enforce that consuming applications must independently verify that `request.shop` corresponds to a shop with an active, matching app installation/session before trusting the webhook payload as belonging to that shop, and consider exposing a combined "verify-and-extract" API that returns the shop only after it has been correlated with signed content.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control).
2. Attacker triggers a real event (e.g., updates an order) causing Shopify to send a legitimately signed webhook to the app's webhook endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `{"id": ..., "attacker-controlled fields": ...}` (attacker fully controls contents of their own store's resources).
3. Attacker captures this raw body and the valid `hmac-sha256` value (e.g. via a proxy on their own infrastructure, since it is their own webhook delivery).
4. Attacker sends a new HTTP request directly to the same app webhook endpoint with the identical `raw_body` and `hmac-sha256` header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [5](#0-4)  and it matches, so validation succeeds.
6. `Registry.process` dispatches `handler.handle` with `shop: "victim-shop.myshopify.com"` and the attacker-crafted body [6](#0-5) , causing the app to process attacker-controlled data under the victim shop's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
