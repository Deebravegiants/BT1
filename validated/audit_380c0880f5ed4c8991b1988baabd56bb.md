### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop attribution via a replayed self-shop payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC over the raw request body only, but the `shop` value that the app's handler uses to attribute the webhook to a tenant is read from the unauthenticated `X-Shopify-Shop-Domain` header. Because the HMAC does not bind the shop identity to the signed bytes, and the same `client_secret`/HMAC key is shared across every shop that has installed the app, an attacker who controls their own installed shop can capture a validly-signed webhook (body + HMAC) sent to them by Shopify, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will accept it as valid and dispatch it to the app's handler labeled as belonging to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor, however, is derived purely from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed bytes: [3](#0-2) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, request.to_signable_string)` and compares it against `request.hmac`. Since `to_signable_string` == `@raw_body` only, this check never touches `request.shop`. After validation succeeds, `request.shop` is passed straight through to the app-defined handler as the tenant identifier: [4](#0-3) 

`Utils::HmacValidator.validate` uses the single, static `Context.api_secret_key` (the app's one `client_secret`) for computing the signature regardless of which shop is claimed — the same secret is valid for every merchant's webhook, since Shopify signs all of an app's webhooks with that one app secret: [5](#0-4) 

The gem's own documentation confirms that `WebhookMetadata#shop` (sourced directly from `request.shop`) is the value host apps are expected to use to identify which tenant a webhook belongs to, e.g. to look up/update that shop's local records: [6](#0-5) [7](#0-6) 

The broken identity binding, stated as an equality that should hold but does not:
`bytes verified by HMAC` (== `@raw_body` only) ≠ `bytes the app actually trusts to identify the tenant` (== `raw_body` + `x-shopify-shop-domain` header, only the first of which is authenticated).

### Impact Explanation
Because the HMAC secret is shared across all shops of a given app, any merchant who has legitimately installed the app is a valid, unprivileged "internet user" with respect to every other merchant's tenant boundary in this gem. That merchant can:
1. Trigger (or wait for) a legitimate webhook to be sent to their own endpoint by Shopify for their own shop, capturing the raw body and its valid `X-Shopify-Hmac-Sha256` value.
2. Replay that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `raw_body` is checked, and then hands `WebhookMetadata.new(shop: request.shop, ...)` — with the attacker-controlled shop — to the app's handler.

This is a cross-tenant confusion issue: the app processes attacker-controlled webhook content while believing it belongs to the victim's shop. Depending on how the host app's `handle` uses `data.shop`/`data.body` (e.g., `perform_later(shop_domain: data.shop, webhook: data.body)` as shown in the gem's own documented example), this can corrupt or overwrite a victim tenant's locally stored records with attacker-supplied data, or trigger tenant-scoped side effects (notifications, syncs, GDPR/redact flows, etc.) attributed to the wrong shop — a cross-tenant access/data-integrity violation rooted entirely in this gem's failure to bind the shop identity into the signed payload.

### Likelihood Explanation
Likelihood is high for any app that has more than one installed merchant (the normal case for a public app): the only prerequisite is that the attacker be a legitimate, unprivileged merchant of the same app (no special access, no leaked secrets, no privileged account needed) and be able to send an arbitrary HTTP POST to the app's public webhook endpoint with a header of their choosing — both trivially available to any internet user.

### Recommendation
Bind the shop identity into the value that is authenticated. Since the HMAC is computed by Shopify only over the raw body, the app-facing API in this gem should either:
- Include verification that `request.shop` matches the shop encoded in the webhook's parsed body (most Shopify webhook payloads carry the shop context, or at minimum the app should correlate the header-derived shop against a known/active session for that shop before trusting it), or
- Explicitly document and enforce that `request.shop` must be cross-checked by the caller against a durable, trusted per-shop identifier (e.g., an already-registered webhook subscription id/shop pairing) before being used for tenant attribution, rather than presenting it as an already-verified value from `Registry.process`.
At minimum, `WebhookMetadata#shop` should not be treated as authenticated by `Registry.process`'s current HMAC check, and the gem should surface this gap rather than silently passing the unauthenticated header value to the handler as if it had been verified.

### Proof of Concept
1. App A is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both sharing the same app `client_secret`.
2. The attacker, as the owner of `attacker-shop.myshopify.com`, receives a legitimate Shopify webhook at their endpoint for some registered topic (e.g. `orders/create`), capturing:
   - `raw_body` (JSON body)
   - `X-Shopify-Hmac-Sha256` header (valid signature over `raw_body`, computed with the shared app secret)
3. The attacker sends a new HTTP request directly to the app's public webhook route with:
   - The captured `raw_body` unchanged
   - The captured `X-Shopify-Hmac-Sha256` header unchanged
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic` and other headers copied as needed to pass the missing-header check in `Request#initialize`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes the HMAC over `raw_body`.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's parsed body, ...))`, causing the app to process attacker-controlled webhook content under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
