### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` in `Registry.process` verifies nothing about the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. An unprivileged internet user who can obtain any single genuine `(body, hmac)` pair for the merchant's app — trivially available by installing the app on a free development store they control — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` and/or `topic` header. `Registry.process` will accept it as valid and hand the forged `shop` value straight to the app's handler via `WebhookMetadata`, which the gem's own documentation instructs developers to treat as the tenant identifier for the event.

### Finding Description
`Registry.process` performs authentication with:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined as just the raw body, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated headers with no participation in the signed content:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(shop ‖ topic ‖ body, secret)`, i.e. the tenant/topic identity the handler trusts must be cryptographically bound to the same bytes that were verified. Instead, the code enforces only `hmac == HMAC(body, secret)`, and `shop`/`topic` are taken from bytes that were never covered by that check — exactly the "field acted on but not covered by the HMAC" break. Before the attack, `verified(shop) == acted_on(shop)`. After the attack, `verified(shop) != acted_on(shop)`: the HMAC validates a body the attacker legitimately obtained (from their own store), but the `shop` value the handler receives and trusts is attacker-supplied and unverified.

Because Shopify's `HMAC-SHA256` body signature for a fixed API secret is deterministic over the body content alone, the same `(body, hmac)` pair remains valid for *any* header combination. The gem's own docs instruct developers to key business logic off `data.shop`: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the app relies on. An attacker who legitimately received one real, HMAC-valid webhook (e.g. by installing the app for free on their own store) can craft new HTTP requests carrying that same raw body but arbitrary `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header values, and the gem will pass `Registry.process`'s HMAC check and dispatch the forged event to the handler as if it genuinely came from a different, targeted merchant. Any app logic that uses `data.shop` to look up/update per-tenant records (installs, uninstalls, order/customer data sync, GDPR/mandatory topics such as `app/uninstalled`, `shop/redact`) can be corrupted or triggered for a shop the attacker does not control — this is a cross-tenant data-integrity / cross-tenant access issue.

### Likelihood Explanation
Requires only: (1) installing the target app on any store, including a free development store, to receive one legitimate webhook, and (2) sending a normal unauthenticated HTTP POST to the app's public webhook endpoint with forged headers and the captured body. No access token, `client_secret`, or privileged account is needed — this is fully reachable by an unprivileged internet user interacting with the gem's public `Registry.process`/`Request` API exactly as documented.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed payload the HMAC verifies, or otherwise cryptographically bind them to the verified body (e.g., verify against the concatenation of headers + body, or cross-check `shop` against a value obtained from an authenticated source such as a stored, previously-registered webhook subscription/session) before trusting `request.shop`/`request.topic` in `Registry.process`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store (free, unprivileged).
2. Capture one genuine webhook delivery, e.g. body `{}` (or `{"id":123}`) with header `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Replay the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or `X-Shopify-Topic` to a registered topic such as `app/uninstalled`.
4. `Utils::HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: {})`, causing the app to act on a forged tenant identity. [1](#0-0) [6](#0-5)
