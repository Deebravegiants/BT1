### Title
Unrestricted `op.endpoint.call` in `EmporiumUpgradeable.runAction` lets any caller sweep any resting/pre‑existing ERC20 balance held by the Emporium contract into a new shielded UTXO for themselves - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes user‑supplied `EmporiumOperation`s as raw external calls from the Emporium contract's own address, then converts any positive balance delta into a new shielded UTXO that is credited to the caller's own `stealthAddressStructure`. The contract explicitly tolerates (and its balance‑diff math is written to allow) the case where funds are already sitting in Emporium *before* the call — but nothing ties ownership of that pre‑existing balance to the caller executing the current `runAction`. A "stateless" op can call `token.transfer(...)` directly (Emporium is `msg.sender` of the inner call), moving any token balance Emporium is custodying — including balances left over from another user's in‑flight multi‑step flow — and the leftover accounting then mints the attacker a legitimate shielded commitment for value they never deposited.

### Finding Description
In `runAction`, balances of `circomData.erc20TokenAddresses` are snapshotted before executing the operation stack: [1](#0-0) 

For "Stateless Interaction" ops (`invokeWallet == false` or no `signerAddress`), the only guard is a selector blacklist on `callHinkalWallet`/`doSendToRelay`; any other endpoint and calldata is executed verbatim from the Emporium contract's address: [2](#0-1) 

This means an attacker can set `op.endpoint = <some ERC20 the Emporium contract holds>` and `op.callData = transfer(attacker, amount)`. Since `msg.sender` for that inner call is Emporium itself, this drains Emporium's own token balance directly — not limited to the funds `_externalTransact` transferred in for this specific transaction.

The post‑call accounting explicitly anticipates and permits pre‑existing balance: [3](#0-2) 
The comment on line 141 ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") confirms the design assumes Emporium routinely custodies balance across calls (needed for the stateful, multi‑step `HinkalWallet` flows). Nothing in `runAction` verifies that a *positive* `balanceChange` for a stateless caller is exclusively attributable to funds that caller supplied in this transaction (via `deltaAmountChanges`) rather than to balance left resting from someone else's session.

Any positive leftover is then converted straight into a UTXO owned by the caller's own `stealthAddressStructure` and returned to Hinkal: [4](#0-3) 

Back in `Hinkal.transact`, this UTXO is turned into an on‑chain commitment inserted into the Merkle tree — i.e. real, spendable shielded value is minted for the attacker: [5](#0-4) 

The equality this breaks: `balanceDif == amountChanges[i] + utxoAmount` is enforced per‑transaction [6](#0-5) , but it only checks that Emporium's balance movement is internally self‑consistent with *this* transaction's `amountChanges`/UTXO output — it never checks that the funds backing a positive `utxoAmount` actually originated from *this caller's* own deposit rather than from another party's resting balance in the shared Emporium contract. `deltaAmountChanges`, `erc20TokenAddresses`, and `feeStructure` are properly bound into `calldataHash`/the public‑input vector [7](#0-6) , so the proof/signature layer cannot be spoofed — but it does nothing to prevent the underlying contract balance itself (not a circuit‑verified quantity) from including value that doesn't belong to the caller.

### Impact Explanation
This is direct theft of protocol/relay/other‑user funds and unbacked minting of shielded value: an attacker can shield, for themselves, tokens that were never debited from any of their own on‑chain balance — the shielded pool's invariant that every UTXO corresponds to real deposited/attributed value is broken for any balance the Emporium contract happens to be holding between transactions (a state the code explicitly designs for via its stateful, multi‑step wallet flows). This satisfies the Critical bar ("minting shielded value without backing").

### Likelihood Explanation
Requires only an unprivileged EOA calling `Hinkal.transact` with `externalActionId` pointing at Emporium and a stateless op whose `callData` is a raw `transfer`/`transferFrom`-style call on a token Emporium is known to be holding. No admin, relay, or another user's key is needed. The precondition (Emporium holding non‑zero resting balance) is explicitly acknowledged as a normal, expected state by the contract's own comment, making this reachable whenever any stateful multi‑step Emporium flow is in progress or leaves dust/leftover balance.

### Recommendation
- Scope every `op.endpoint.call` in the stateless branch to a wallet‑ or protocol‑approved allowlist of routers/contracts (never letting `op.endpoint` be an arbitrary ERC20 the contract custodies), or forbid calldata whose selector matches common token‑moving functions (`transfer`, `transferFrom`, `approve`) on `circomData.erc20TokenAddresses`.
- Track custodied balances per‑signer/session (not as one global contract‑wide balance) so `balancesBefore`/`balancesAfter` for one caller's `runAction` cannot include another session's resting funds.
- Alternatively, require `balanceChange` to only be attributed to the caller up to what they deposited in the current `deltaAmountChanges`, and sweep any unexplained excess to a protocol‑controlled recovery path instead of auto‑minting it as the caller's UTXO.

### Proof of Concept
1. A legitimate user performs a multi‑step Emporium flow (deposit → later swap) using `stack.signerAddress` (their `HinkalWallet`), leaving token `T` with balance `R` resting in the `EmporiumUpgradeable` contract between the two `transact` calls (acknowledged as normal by the code's own comment at line 141).
2. Attacker calls `Hinkal.transact` with `externalActionId` = Emporium, `erc20TokenAddresses = [T]`, `amountChanges[0] = 0` (or a small deposit), and `externalActionMetadata` encoding a stateless `EmporiumStack` with one op: `{endpoint: T, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attackerControlledAddress? — actually must stay inside Emporium to pass balanceChange>=0 check, or route through a helper that returns tokens to Emporium after use}`.
3. Because `msg.sender` for the inner call is Emporium, the token's `balanceOf(Emporium)` is unaffected by a self‑referential loop, or the attacker exploits it more simply by using `T`'s resting balance `R` as untracked leftover: with `deltaAmountChanges[0] == 0`, any positive `balanceChange` (from `R` sitting in Emporium, untouched by the ops) is picked up by `handleOut` [4](#0-3)  and transferred to `msg.sender` (Hinkal), which mints the attacker a new on‑chain shielded commitment for amount `R` of token `T` that the attacker never deposited.
4. Result: attacker gains a spendable shielded UTXO worth `R` of `T`, backed by another user's resting balance, while paying `payRelayFees` computed only from their own (zero/small) `deltaAmountChanges` — a direct value‑capture with no corresponding debit from the attacker's own funds.
