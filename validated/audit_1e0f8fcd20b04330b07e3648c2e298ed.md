### Title
Tokens delivered to the controller during a `flash_position` callback but absent from the declared `collaterals`/`refund_assets` lists are permanently locked with no re-claim or sweep path — (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The Turnstile finding's class is: a value-generating resource is bound once at registration and, once the binding is lost, there is no re-register/re-assign path to recover the accrued value. XOXNO Lending reproduces this shape in `flash_position`: the callback settlement enumerates exactly two allowlists — declared `collaterals` (deposited into the account) and declared `refund_assets` (returned to the caller). Any token balance that lands at the controller during the callback but is not on either list is credited to nobody and refunded to nobody, and the controller exposes no sweep or recovery endpoint, so the funds are permanently frozen.

### Finding Description
`process_flash_position` snapshots controller balances for only the declared sets before invoking the receiver callback (`collateral_before`, `refund_before` at contracts/controller/src/strategies/flash_position.rs:120-143). After the callback, `collect_collateral_deposits` measures deltas only for `collaterals` entries (lines 325-352) and `refund_listed_assets` refunds deltas only for `refund_assets` entries (lines 372-384, via `refund_controller_balance_delta`). `validate_refund_assets` (lines 217-256) additionally constrains the refund list: assets must be unique, must be listed in the debt hub and the account's spoke (`require_listed_active_config`), and must be disjoint from `collaterals`. The protocol's own reference confirms the gap: "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" (docs/reference/endpoints.md:86).

Like Turnstile's `register`/`assign` with `onlyUnregistered`, the declaration is a one-shot binding fixed at call time: there is no later call that lets the owner re-declare an asset, re-attach the stranded balance to the account, or recover it. Unlike the collateral path, there is no `min_amount = 0` catch-all — an asset omitted from both lists simply accrues to the controller address forever, since the controller has no token-forwarding entrypoint reachable by unprivileged callers (`claim_revenue` pays only the accumulator; `recapitalize` pays the pool, not the controller's stray balance).

### Impact Explanation
Permanent freezing of funds. Tokens sent to the controller mid-callback — e.g., a swap venue's change/refund output routed to the controller because collateral must arrive there, an airdrop/rebase credit, or a receiver mis-declaring an asset — become unspendable. The value is neither credited to the position nor returned. For a fee-on-transfer or multi-output route this can be a large fraction of the callback's working capital.

### Likelihood Explanation
Reachable by any unprivileged address: `flash_position` accepts a caller-selected deployed Wasm `receiver`, and callback tokens legitimately arrive at the controller because collateral settlement is measured by controller balance deltas. A receiver composing a Soroswap/Aquarius route whose residual or secondary output lands at the controller (a natural `to` address in this flow), or that forgets to list a refund asset (or cannot list it because it is in `collaterals`, or is not listed/active in the account's spoke — `validate_refund_assets` hard-rejects those), produces stranded funds in normal use. No privileged action, oracle manipulation, or third-party failure is required.

### Recommendation
Add a post-settlement re-claim path analogous to the suggested Turnstile "validate historical registrations and re-register" fix: e.g., an owner/delegate-gated `sweep(account_id, assets)` or an `add_refund_asset` recovery endpoint that forwards positive controller balance deltas for assets not part of the account's positions, or treat any positive callback delta on listed-but-undeclared assets as implicit refund candidates. At minimum, document that the receiver must enumerate every token it may cause to arrive at the controller.

### Proof of Concept
1. User deploys a Wasm receiver and calls `controller.flash_position(caller=receiver, account_id=0, spoke_id=S, mode=Multiply, debt=ETH_key, amount=1e7, receiver=receiver, data=..., collaterals=[(USDC_key, 4_000e7)], refund_assets=[])`.
2. Inside `execute_flash_position`, the receiver swaps on Aquarius specifying `to = controller` for a second output token `XLM` (not declared anywhere), or simply transfers 100 XLM to the controller.
3. The call finalizes: USDC delta is deposited, `refund_assets` is empty so `refund_listed_assets` moves nothing, all risk checks pass.
4. The 100 XLM sits at the controller. No entrypoint (`supply`, `withdraw`, `claim_revenue`, `recapitalize`) can route it back to the user; `claim_revenue` pays only the configured accumulator, and revenue is pool-side shares, not controller token dust. The tokens are permanently locked.
