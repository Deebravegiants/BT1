This confirms the finding is accurate. Both missing `return` statements are present exactly as described in the code at lines 226-230 (missing `return` after the email claim check) and lines 257-260 (missing `return` after the DB insert error check).

The key question is whether this represents an in-scope, exploitable vulnerability. Analyzing the exploit path:

1. **Root cause confirmed**: The `email, ok := claims["email"].(string)` check at line 226-230 writes an error response but doesn't `return`, so execution continues.
2. **Trigger requires IdP cooperation**: To reach this, the attacker needs to control or influence the OIDC provider's response such that the ID token passes full signature/issuer/audience verification (line 207-212) yet lacks an `email` claim. This requires either a misconfigured/compromised IdP or an attacker who already controls the identity provider — not something an unprivileged client can forge directly against the node's `/oidc` endpoint, since the ID token is verified using the provider's public keys before this point is reached.
3. **Actual resulting session is not privilege-escalating beyond IdP-granted role**: The role assigned via `IDClaimsToUserRole` is still derived from the legitimately verified token's group claims — the missing `return` doesn't let the attacker choose an arbitrary role; it just lets a session bind to an empty/lowercased empty `email` string with whatever role the real claims support.

That said, the code defect itself is real and does match the missing-halt bug pattern precisely as cited, and the requirement is only "OIDC login capability" (successful round-trip) plus provider misbehavior — not admin/host access to the node itself. Since the provider's claim content is outside the attacker's direct control unless the attacker also controls the IdP configuration (which is normally operator/admin-controlled, e.g., which claims are mapped/asserted), this leans toward requiring an atypical or misconfigured IdP setup rather than a standard unprivileged exploit against the node.Audit Report

## Title
Missing `return` after failed email-claim extraction and after failed session-insert allows OIDC login flow to complete and return success despite errors - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, the check `email, ok := claims["email"].(string)` writes an HTTP 500 error body when the assertion fails but omits the `return` statement, so execution falls through to role mapping, session creation, cookie setting, and finally a `200 {"success": true}` response — overwriting the earlier error. The same missing-`return` pattern also occurs on the `INSERT INTO oidc_sessions` error branch immediately after. This deviates from every other guard in the same function, which correctly halts execution with `return`.

## Finding Description
The code at [1](#0-0)  performs the email-claim type assertion and, on failure, calls `c.String(...)` but does not `return`. Similarly, [2](#0-1)  logs a DB insert error without halting. By contrast, every other precondition check in the function — invalid JSON body, invalid state, failed token exchange, missing `id_token`, failed token verification, failed claims parsing, failed `ExtractIDClaimValues`, failed role mapping, and failed session save — all correctly call `return` after writing an error, as seen at [3](#0-2)  and [4](#0-3) . Because of the missing `return`, the function proceeds to call `IDClaimsToUserRole` at [5](#0-4) , insert a row into `oidc_sessions` keyed on the empty `email` string at [6](#0-5) , set the session cookie and save the Gin session at [7](#0-6) , and finally emit `200 {"success": true}` at [8](#0-7) , overwriting the earlier 500 response.

However, reaching the vulnerable branch is gated by the ID-token verification step at [9](#0-8) , which validates the token's signature, issuer, and audience against the configured OIDC provider before claims are ever extracted. The `claims["email"]` value being absent or non-string is therefore entirely a function of what the configured identity provider legitimately asserts in its token — it is not a value an unprivileged network client can forge or omit at will while still passing verification, since doing so would require either controlling the trusted IdP or its issued tokens directly (which is outside the threat model of an unprivileged client attacking the node's public API) or a misconfiguration of the IdP by the node operator/admin (an excluded misconfiguration scenario). Likewise, the second missing-`return` branch is only reachable on a genuine database failure, which is an operational condition, not something an unprivileged remote client can trigger on demand.

## Impact Explanation
If reachable, this would create an authenticated, cookie-backed session recorded with an empty `user_email` in `oidc_sessions`, while still deriving `user_role` from the legitimately-verified token's group claims — it does not let an attacker choose an arbitrary role or bypass the underlying OIDC signature/issuer/audience checks. The realistic impact is limited to identity-binding corruption (empty email field) rather than privilege escalation to an attacker-chosen role, since role assignment via `IDClaimsToUserRole` is unaffected by this bug.

## Likelihood Explanation
Triggering the primary vulnerable branch requires the configured, trusted identity provider to issue an otherwise-valid, correctly-signed ID token that omits the `email` claim — this is not attacker-controllable input in a standard unprivileged-client threat model; it depends on either compromising the trusted IdP or an IdP misconfiguration by the operator. The secondary branch requires a genuine transient database failure, an operational condition outside attacker control. Neither condition is triggerable through a normal, unprivileged HTTP request crafted by a client against the node's `/oidc` endpoint alone.

## Recommendation
Add `return` immediately after both error branches to match the established pattern in the rest of the function:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
...
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
    return
}
```

## Proof of Concept
The code defect is confirmed by direct code inspection (see citations above): the `if !ok { ... }` block at lines 226-230 and the `if err != nil { ... }` block at lines 257-260 both lack a `return` statement, unlike every other error branch in `handleTokenExchange`. However, a concrete exploit requires either (a) control over the configured, trusted OIDC identity provider's issued claims (not achievable by an unprivileged client against the node's public API without already compromising or misconfiguring the IdP), or (b) inducing a genuine database failure during the `INSERT INTO oidc_sessions` call (an operational condition, not a client-triggerable input). No reproducible unprivileged-client-only PoC against a standard node configuration with a properly functioning IdP was identified.
