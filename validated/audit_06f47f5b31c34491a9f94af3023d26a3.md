### Title
Withdraw and SweepDust in the Tron IntentGatewayV2 use raw `.call` for ERC20 transfers instead of `SafeERC20`, silently accepting non-reverting `transfer()` failures and permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports `SafeERC20` (`using SafeERC20 for IERC20;`) and uses it correctly for token intake (`safeTransferFrom`), but the token payout paths — `withdraw()` and the `SweepDust` branch of `onAccept()` — bypass `SafeERC20` and instead make a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only that the call itself did not revert (`success`), never decoding/validating the boolean return data.

### Finding Description
In `withdraw()`: [1](#0-0) 

and in the `SweepDust` branch of `onAccept()`: [2](#0-1) 

Both call the token with `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only branch on the outer `success` boolean returned by `.call`. This is the well-known unchecked/low-level-ERC20-return-value pattern: any ERC20 implementation that returns `false` on failure instead of reverting (a common and standards-compliant behavior, e.g. some legacy tokens, and notably common on Tron/TRC20-style tokens which this contract is specifically deployed for) will make `success == true` even though no tokens were actually transferred. `SafeERC20.safeTransfer`, which the contract already imports and uses elsewhere for `safeTransferFrom`, exists precisely to decode and enforce this return value, but is not used on the withdrawal/sweep paths.

Compare this to `withdraw()`'s companion escrow-accounting: escrow balances are decremented (`_orders[body.commitment][token] -= amount;`) and the order is marked filled (`_filled[body.commitment] = beneficiary;`) unconditionally alongside the unchecked transfer call. If the token's `transfer()` returns `false` without reverting, the contract state records the order as fully settled and the escrow as drained, while the tokens remain locked in the contract with no accounting path left to recover them (the `_filled` mapping already marks the commitment as resolved, and `_orders` is already decremented to zero).

### Impact Explanation
This is directly reachable by any user account whose order goes through the standard escrow-redeem flow (`RedeemEscrow`/`RefundEscrow` handled via `onAccept` → `withdraw`), and by `SweepDust` requests dispatched cross-chain. If the token in question (input/fee token configured for an order) returns `false` on transfer failure rather than reverting, the beneficiary permanently loses the escrowed funds: the protocol's internal accounting treats the order as filled/refunded and the funds as delivered, but they remain stuck in the `IntentGatewayV2` contract with no remaining code path to reclaim them. This is a permanent freezing-of-funds condition satisfying the required "concrete theft or permanent freezing of funds" bar, reachable from a plain user-submitted fill/cancel/withdraw flow without any privileged role.

### Likelihood Explanation
Likelihood is token-dependent but non-trivial: it triggers with any ERC20/TRC20 token that returns `false` instead of reverting on transfer failure (a documented, standards-compliant pattern, and one that is not uncommon particularly outside pure Ethereum-mainnet blue-chip tokens — the very class of tokens this Tron-specific contract variant is meant to support). It can also be deliberately triggered by a malicious or non-standard token used as an order's input/fee token, since order tokens are attacker/user-supplied parameters in `IntentGatewayV2`'s order structure.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (the same `SafeERC20` library already imported and used for the intake side via `safeTransferFrom`), ensuring that a non-reverting `transfer()` that returns `false` also reverts the whole operation instead of silently marking escrow as released.

### Proof of Concept
1. A user creates a same-chain or cross-chain order with an input/fee token that is a non-standard ERC20/TRC20 implementation returning `false` (not reverting) when `transfer` fails (e.g., insufficient contract balance due to some other bug/edge case, blacklist, or fee-on-transfer/pausable design).
2. The order is filled/cancelled, triggering `onAccept` → `withdraw(body, isRefund)` in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. `_orders[body.commitment][token] -= amount;` executes, and `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` even though the internal `transfer` logic returned `false` and moved zero tokens.
4. `_filled[body.commitment] = beneficiary;` is set and `EscrowReleased`/`EscrowRefunded` is emitted — the protocol considers the order fully and successfully settled.
5. The beneficiary never receives the tokens, and the tokens remain permanently locked in the `IntentGatewayV2` contract balance with no remaining code path (escrow already zeroed, order already marked filled) to claim them.
