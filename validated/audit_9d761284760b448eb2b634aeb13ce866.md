### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant metadata spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated headers and passed straight into the handler as trusted values. This breaks the identity binding: `HMAC-verified bytes == bytes acted on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` and compares against the `hmac` header: [2](#0-1) [3](#0-2) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from separate, unsigned HTTP headers: [4](#0-3) 

`Registry.process` then hands these unauthenticated header values directly to the application's webhook handler as `WebhookMetadata`, treating `request.shop` (and `topic`) as trusted, verified identifiers: [5](#0-4) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` **is** included in the signed parameter set for the OAuth callback: [6](#0-5) 

For webhooks there is no analogous binding of `shop` (or `topic`/`webhook_id`) into the signed payload. The identity equality that should hold — `HMAC(secret, signed_bytes)` binds `shop` to the payload — does not hold, because `shop` is outside `signed_bytes`.

### Impact Explanation
An attacker who controls their own shop's installation of the app receives valid, correctly HMAC-signed webhook deliveries from Shopify for that shop (this requires no knowledge of `client_secret`; Shopify computes and sends the HMAC). Because the header `shop-domain` (and `topic`/`webhook-id`) are not part of the signed bytes, the attacker can capture one such legitimately-signed request/body pair and resend it to the app's webhook endpoint with an arbitrary `shop-domain` header value (e.g., a victim tenant's domain) while keeping the original body and HMAC intact. `Utils::HmacValidator.validate` will still succeed because it only checks the raw body against the signature, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the payload originated from the attacker-chosen shop. Any host application logic that trusts `request.shop`/`data.shop` to scope tenant data (a common and documented pattern for webhook handlers) can be tricked into writing or acting on attacker-controlled body content under a victim tenant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Requires only that the attacker control one legitimate installation of the app (trivial for any developer/merchant who can install apps on their own store) and be able to replay an HTTP request to the app's public webhook endpoint with a modified header — no secrets, tokens, or privileged access are required. This is a realistic "unprivileged internet user" scenario.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signed material used for HMAC verification (or otherwise cryptographically bind them to the signed body), so that these values cannot be altered independently of a valid signature. At minimum, document that consumers of `WebhookMetadata#shop`/`#topic` must not treat these fields as authenticated unless they are independently confirmed against the shop the endpoint is scoped to.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with body `{}"` and a valid `x-shopify-hmac-sha256` computed over that body using the app's `client_secret` (attacker never needs the secret itself).
2. Attacker captures this request (own traffic to own endpoint).
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `@raw_body` (`Request#to_signable_string`), which is unchanged. [1](#0-0) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, where `shop` is `"victim-shop.myshopify.com"` even though the actual signed content came from the attacker's own shop. [5](#0-4) 
6. Any handler logic keyed on `data.shop` now processes attacker-controlled body content as if it belonged to the victim tenant.
