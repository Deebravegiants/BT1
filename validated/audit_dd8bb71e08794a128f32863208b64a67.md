### Title
`generate-node-key` writes the node's libp2p secret key file with default (world-readable) permissions - (File: `substrate/client/cli/src/commands/generate_node_key.rs`)

### Summary
The `generate-node-key` CLI subcommand generates an ed25519 secret key used as the node's persistent libp2p network identity and persists it to disk using plain `std::fs::write`, which applies default OS permissions (typically `0o644`, world-readable under the standard umask) rather than restrictive `0o600` permissions. This mirrors exactly the pattern described in the external report for `symbol-cli`'s `fs.writeFileSync`: a secret is written to disk without explicitly restricting file permissions, leaving it readable by any local user with access to the filesystem/home directory.

### Finding Description
`generate_key()` in `substrate/client/cli/src/commands/generate_node_key.rs` creates an ed25519 keypair and writes the raw or hex-encoded secret directly to a file via `fs::write(file, file_data)` or `fs::write(key_path, file_data)`: [1](#0-0) 

Neither branch sets explicit file permissions, so the resulting `secret_ed25519` (or user-supplied) file inherits the process umask (commonly `0o644`), making the node's private network identity key world-readable.

This is inconsistent with the codebase's own established secure pattern: when the node auto-generates its network key at startup (rather than via the CLI subcommand), `substrate/client/network/src/config.rs`'s `open_secret_file` explicitly opens the file with `mode(0o600)`: [2](#0-1) 

Similarly, the account/session keystore (`LocalKeystore`) explicitly sets `0o600` permissions on every key file it writes, and has a dedicated unit test asserting this: [3](#0-2) [4](#0-3) 

The `generate-node-key` path is the odd one out: it is the code path an operator explicitly runs (e.g., to pre-provision a validator's persistent identity before deployment) and it silently produces an insecurely-permissioned secret file, exactly the scenario the external report warns about for `symbol-cli.config.json`.

### Impact Explanation
The generated file is the node's persistent Ed25519 secret key, which determines the node's `PeerId` used in libp2p networking (as documented directly in `NodeKeyParams`): [5](#0-4) 

If another local user (or process) on the same machine/CI runner/shared host can read this file, they can impersonate the node's `PeerId` elsewhere, disrupt the identity-based reachability guarantees relied on by peers/authorities (the same file's own doc comments call out that authorities depend on stable identities), or otherwise stage impersonation/DoS against the legitimate node's network presence. This matches the "Denial of Service" classification and local-multi-tenant threat model of the original report (Eve reading Alice's world-readable secret file on a shared host).

### Likelihood Explanation
Likelihood is moderate: it requires local co-tenancy on the host where an operator ran `generate-node-key` (e.g., shared CI, shared bare-metal/VM, or a home directory readable by other local accounts) — the same assumption the original report itself relies on. Unlike a purely theoretical issue, this is a straightforward default-umask outcome with no additional protections in the affected code path, and the inconsistency with the project's own `0o600` pattern used elsewhere (`open_secret_file`, `LocalKeystore::write_to_file`) demonstrates the maintainers already recognize and mitigate this exact risk class in other code paths, just not in `generate_node_key.rs`.

### Recommendation
Explicitly set file permissions to `0o600` (Unix) before/while writing the secret key in `generate_key()` in `substrate/client/cli/src/commands/generate_node_key.rs`, mirroring the existing pattern in `substrate/client/network/src/config.rs::open_secret_file` (e.g., use `fs::OpenOptions::new().write(true).create(true).mode(0o600).open(path)` instead of bare `fs::write`). Add a regression test analogous to `uses_correct_file_permissions_on_unix` in `substrate/client/keystore/src/local.rs` to assert the generated `secret_ed25519`/custom key file has mode `0o600`.

### Proof of Concept
1. On a Unix multi-user host with default umask `0o022`, run: `substrate-node key generate-node-key --base-path /home/alice/.local/share/mynode`.
2. Inspect resulting file permissions: `stat -c '%a' /home/alice/.local/share/mynode/chains/<id>/network/secret_ed25519` → `644` (world-readable), confirmed by the absence of any `set_permissions`/`mode()` call in `generate_key()` at [1](#0-0) , in contrast to the `0o600` enforcement present in `substrate/client/network/src/config.rs` and `substrate/client/keystore/src/local.rs`.
3. Any other local user (Eve) with read access to `/home/alice/` can copy `secret_ed25519` and derive Alice's node's libp2p identity/`PeerId`, enabling impersonation or disruption of that node's network identity.
