### Title
Webhook `shop-domain` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the tenant-identifying fields `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never part of the signed content. `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app secret; it says nothing about which shop or topic that signature is supposed to be attributed to. `Registry.process` then trusts `request.shop` and `request.topic` unconditionally to route the payload and select/attribute the handler call.

### Finding Description
`Request#hmac`, `Request#topic`, `Request#shop`, `Request#webhook_id`, and `Request#api_version` are all derived from HTTP headers: [1](#0-0) 

But the value that actually gets HMAC-verified is only the raw body: [2](#0-1) 

`HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header — it never mixes in `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates only that HMAC, then trusts the unsigned `topic` and `shop` headers to select the handler and to build the `WebhookMetadata` passed into application code: [4](#0-3) 

This is structurally the same class of bug as the reported limiter issue: the system verifies one thing (body integrity via HMAC) but acts on a different, unbound field (`shop`/`topic` headers) as if it had been verified together with it. The binding that should hold is:
`HMAC(secret, body) valid` `⇒` `shop header == the shop the signature was actually issued for`

but the implementation only guarantees:
`HMAC(secret, body) valid` `⇒` `body bytes were signed by this app's secret` (regardless of which shop/topic header accompanies it).

### Impact Explanation
Any store owner that has installed the app is an "unprivileged internet user" relative to *other* tenants of the same app, yet legitimately receives real webhook deliveries (body + valid `x-shopify-hmac-sha256`) for their own shop. Because the header fields are not covered by the signature, that same body/HMAC pair remains valid if replayed to the app's public webhook endpoint with the `shop-domain` (and/or `topic`) header rewritten to a different, victim shop. `Registry.process` will accept the forged headers as long as the (unrelated) body HMAC checks out, and will invoke the registered handler with `WebhookMetadata` attributing the payload to the victim shop: [5](#0-4) 

Depending on how the host app implements its handler (e.g., writing data keyed by `shop`, triggering `app/uninstalled` cleanup, or `customers/redact`/`shop/redact` compliance actions), this allows one tenant to inject falsely-attributed events into another tenant's data/workflow — a cross-tenant access/integrity violation.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate merchant/user of the app (no `api_secret_key`, access token, or privileged access needed), (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers, which is inherent to how webhook endpoints work (they must be internet-reachable, unauthenticated except for the HMAC). No credential leakage, MITM, or TLS interception is required — only header manipulation on a replayed/self-triggered webhook delivery.

### Recommendation
Include the identity-binding fields (`shop`, `topic`, and ideally `webhook_id`) in the signable content, or otherwise cryptographically bind them to the HMAC before trusting them for routing/attribution in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate `shop`, `topic`, and `webhook_id` (not just `@raw_body`), and `HmacValidator` should be updated accordingly so a valid signature can only be replayed under the exact header/tenant context it was issued for.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and legitimately receives a webhook delivery containing raw body `B` with a valid header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP request to the app's webhook endpoint using the *same* body `B` and *same* HMAC header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and/or changes `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (all three required headers are present): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B)` against the unchanged body `B`: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
