### Title
Webhook `shop-domain` identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook_id`) values consumed by the app come from unauthenticated HTTP headers. This is the same identity-binding gap described in the SUI analog report: a field that is *acted upon* (the shop identity) is not covered by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header without any cryptographic binding to that value: [2](#0-1) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which in turn calls `validate_signature`, comparing `compute_signature(verifiable_query.to_signable_string, secret)` against the received HMAC: [3](#0-2) [4](#0-3) 

Because `to_signable_string` is just the raw body, the HMAC only proves "this body byte-string was signed with the app secret at some point" — it says nothing about which shop, topic, or webhook-id it was issued for. The equality that should hold is:

`shop header value == shop that produced/authorized this HMAC'd body`

but the code only checks `hmac == HMAC(secret, body)`, never binding `shop header` into that computation. This is the exact analog of the SUI bug: the receiver/identity field is acted upon (`WebhookMetadata.new(... shop: request.shop ...)`) but not validated/bound by the authentication mechanism that is supposed to guarantee its authenticity.

### Impact Explanation
An unprivileged internet user who can install the app on their own shop (or otherwise obtain one legitimate `(body, hmac)` pair — trivial for any public app since the attacker's own shop is a legitimate tenant) can capture a valid `raw_body` + `x-shopify-hmac-sha256` pair from a webhook delivered to them. They can then replay that exact body+hmac to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the shop header, so `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: ..., shop: <victim shop>, body: ..., ...)`. Any app logic that trusts `data.shop` to select which merchant's session/data record to update (a documented and expected usage pattern of this gem) will act on attacker-controlled body content under an incorrect tenant identity — a cross-tenant data-confusion/write primitive. This satisfies the "cross-tenant access" criterion in the impact rubric.

### Likelihood Explanation
High feasibility: no secrets, tokens, or privileged access are required. An attacker only needs their own (attacker-owned) shop installation of the target app to obtain one valid signed body/HMAC pair, then can freely relabel the shop header on replay since the gem never checks it. This is entirely reachable through the gem's documented webhook processing entry point (`Registry.process`).

### Recommendation
Include the identity fields that the handler will act upon (`shop`, `topic`, `webhook_id`) in the signable content, or otherwise cryptographically bind the header-derived `shop` value to the signed payload (e.g., require the handler-supplied `shop` to be reconciled against a value embedded in and covered by the signed body, or sign a canonical representation of headers+body rather than body alone). At minimum, document prominently that `data.shop` from `WebhookMetadata` is NOT authenticated by the HMAC check and must not be used as a sole tenant-selection key.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify delivers a real webhook: headers include `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `raw_body`.
2. Attacker captures `raw_body` and `x-shopify-hmac-sha256` unchanged.
3. Attacker POSTs to the same app webhook endpoint with headers changed to `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, `x-shopify-topic` unchanged so a real registered handler fires), keeping `raw_body` and `x-shopify-hmac-sha256` identical.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present).
5. `Registry.process(request)` calls `HmacValidator.validate(request)` → `validate_signature` recomputes `HMAC(secret, raw_body)` which matches the replayed HMAC (body untouched), so validation passes.
6. Handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, i.e., attacker-controlled data processed under the victim shop's identity. [3](#0-2)
