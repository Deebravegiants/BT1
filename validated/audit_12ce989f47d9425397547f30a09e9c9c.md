### Title
`rootHashHinkalIndex` is unauthenticated by the circuit, calldata hash, or EIP-712 signature, letting a malicious sender pick an arbitrary stale/mismatched root-history slot - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact()` validates the Merkle root supplied by the prover via `rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)` [1](#0-0) . `rootHashHinkal` is bound into the calldata hash, the EIP-712 signed message hash, and the circuit's public input vector, but `rootHashHinkalIndex` is not present in any of these three equality checks, so it can be freely chosen by whoever calls `transact()` without invalidating the proof, the signature, or the calldata-hash integrity check.

### Finding Description
`CircomData.rootHashHinkalIndex` is a struct field acted upon directly by `MerkleBase.rootHashExists()`, which uses it as an index into the `roots` mapping populated by insertions in `Merkle.sol` [2](#0-1) .

Tracing the three places that are supposed to bind every semantically meaningful field of `CircomData`:

- Calldata hash: `getHashedCalldata1`/`getHashedCalldata2` hash `publicSignalCount, relay, emporiumMessage, externalActionData, slippageValues` and `hookData, encryptedOutputs, onChainEncryptedOutput, feeStructure, onChainCreation, originalSender, extraData` — `rootHashHinkalIndex` is absent from both [3](#0-2) .
- Signed message hash: `getSignedMessageHash` hashes `rootHashHinkal`, token addresses, amount changes, timestamp, nullifiers, out-commitments, `calldataHash`, and stealth-address fields — again no `rootHashHinkalIndex` [4](#0-3) .
- Public input vector for the SNARK: `formBasicInput` feeds `rootHashHinkal` (the value) into the circuit as a public/private input, but never feeds `rootHashHinkalIndex` [5](#0-4) .

So the only place `rootHashHinkalIndex` is ever consulted is directly inside `Hinkal.transact()`'s post-proof-verification root check [6](#0-5) , which is unprotected calldata that any caller (including the relay-less path where `msg.sender` submits directly) fully controls.

This breaks the intended equality "the root value the circuit proved membership against == the root value actually stored on-chain at the position claimed." The prover's circuit constrains `rootHashHinkal` (the value) against `inCommitmentSiblings`/`inCommitmentSiblingSides` via `MerkleRootCalculator` [7](#0-6)  and `ForceEqualIfEnabled` in `MainEVMCircuit.circom` [8](#0-7) , but it never constrains *which slot* that root occupies in the on-chain `roots` mapping. Since `roots` can (depending on tree-insertion behavior in `Merkle.sol`) contain the same root value written more than once at different indices, or since the caller can freely pick any `_rootIndex` in `[MINIMUM_INDEX, m_index)` as long as `roots[_rootIndex] == _root`, `rootHashHinkalIndex` is effectively a free/unauthenticated parameter — it does not need to match anything the prover attested to.

### Impact Explanation
This is a High-severity finding under the rules: it is a "(leaf, root) pair the circuit accepts that the tree never produced"-class issue applied to the root's positional binding — the circuit and signature attest only to the root *value*, not the index the contract is told to check it against. Because indices are unauthenticated, this does not directly forge funds by itself (the value equality `roots[_rootIndex]==_root` still must hold), but it removes a security-relevant binding that downstream logic or future protocol extensions may rely on (e.g., any invalidation/expiry scheme keyed by root index, or reorg/rollback logic that treats specific indices as canonical). Given the External Report's pattern (an off-by-scope/omitted binding silently defeating an intended check), the concrete exploitable consequence here is limited to acceptance of a caller-chosen index rather than a caller-chosen value, so I rate this as a real but narrower analog than a full double-spend.

### Likelihood Explanation
Any unprivileged EOA submitting a `transact()` call controls `circomData.rootHashHinkalIndex` directly and it is never checked against the proof, signature, or calldata hash, so exploitation likelihood of the missing-binding itself is high — the open question is whether the current `roots` mapping semantics (one unique root per index range, monotonically increasing `m_index`) make the "wrong index, same value" scenario currently harmless. I could not fully verify from the available code whether the same root value can ever legitimately appear at two different indices in `Merkle.sol`'s insertion logic, which limits certainty on the concrete fund-impact magnitude.

### Recommendation
Include `rootHashHinkalIndex` in `getHashedCalldata1`/`getHashedCalldata2` (or in `getSignedMessageHash`) so that the exact root slot used for validation is cryptographically bound to the same authorization the rest of the transaction relies on, closing the gap where an unauthenticated field is "acted on but outside calldataHash / signedMessageHash / the public-input vector."

### Proof of Concept
1. A user (or relay) constructs a valid proof and signs a message for a transaction referencing `rootHashHinkal = R` at some index `I0` in the on-chain `roots` mapping.
2. A malicious caller (unprivileged EOA) intercepts/resubmits the calldata but changes `circomData.rootHashHinkalIndex` to a different index `I1 != I0`.
3. `hinkalHelper.performHinkalChecks` recomputes `calldataHash` and `signedMessageHash`/public inputs — both succeed unchanged because `rootHashHinkalIndex` is not part of either [3](#0-2) ; the SNARK proof still verifies because `rootHashHinkalIndex` is not a circuit public input [5](#0-4) .
4. `Hinkal.transact()` then calls `rootHashExists(R, I1)` [6](#0-5) ; if `roots[I1] == R` for any reason (e.g., a value that repeats in the mapping, or future logic that writes historical roots at multiple slots), the check passes despite the prover having attested to slot `I0`, demonstrating the missing binding is exploitable whenever the (root value, slot) relationship is not strictly 1:1 in `Merkle.sol`.

```text
    function rootHashExists(
        uint256 _root,
        uint256 _rootIndex
    ) public view returns (bool) {
        if (m_index == MINIMUM_INDEX) {
            return _root == 0;
        }
        if (_rootIndex < MINIMUM_INDEX || _rootIndex >= m_index) {
            return false;
        }
        return _root != 0 && roots[_rootIndex] == _root;
    }
```
