### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the handler an unauthenticated `shop` value taken straight from a request header. The `shop` field is never part of the signed material, so it can be swapped freely without invalidating the signature, breaking the binding "shop verified by HMAC == shop delivered to the handler."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks that `hmac` matches a signature computed over `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` (and `request.topic`) to construct the `WebhookMetadata` passed to the app's handler, without any check that this shop is the one for which the signed body was originally generated: [4](#0-3) 

Because none of `shop-domain`, `topic`, `webhook-id`, or `api-version` are part of the signed payload, any request bearing a body+HMAC pair that was legitimately produced for one shop (e.g., a webhook delivered to a shop the attacker controls/has installed the app on) remains fully valid if resent with a different `x-shopify-shop-domain` header. The equality the gem should enforce — "shop cryptographically bound to the signed payload" == "shop delivered to the handler" — does not hold; instead, "shop taken from an unauthenticated header" == "shop delivered to the handler."

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as recommended by this gem's own API) to decide which tenant's data to create/update/delete is exposed to cross-tenant data injection: an attacker who has captured one valid (body, HMAC) pair — trivially obtainable by installing the app on their own store and observing a delivered webhook — can replay it against the app's webhook endpoint while claiming an arbitrary victim `shop-domain`. This satisfies the "cross-tenant access" Critical impact category, since the gem's own signature-validation primitive gives applications a false sense that `shop` was authenticated.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user with a Shopify store: obtaining a legitimate (body, HMAC) pair requires no special access to `api_secret_key`, no privileged account beyond installing the target app in a store the attacker controls, and no interception of TLS. Only the ability to POST to the app's public webhook endpoint with attacker-chosen headers is needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that `shop` must not be used as a tenant key unless corroborated by a source that is itself part of the signed material.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook delivery, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` header (a valid pair, since Shopify itself computed it correctly for that body).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body`/`hmac` but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks the body's HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`), and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes `request.shop` (now `victim-shop.myshopify.com`) straight to the app's handler, which processes it as if it were a legitimate event for the victim shop.
