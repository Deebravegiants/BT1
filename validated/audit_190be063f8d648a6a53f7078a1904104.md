### Title
Zero-amount escrow withdrawal reverts DoS the entire order settlement in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` in the Tron variant of `IntentGatewayV2.sol` unconditionally transfers every entry in `body.tokens` without checking for a zero amount before calling `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`. If any escrowed token in the withdrawal batch is a "revert on zero transfer" ERC-20 (per the weird-ERC20 catalogue) and its escrowed amount for that order happens to be zero, the low-level `.call` returns `success == false`, which is interpreted the same as an actual transfer failure and reverts with `TransferFailed()` — blocking release of *all* other (non-zero) escrowed tokens and fees in the same withdrawal for that order. This mirrors the exact bug class of the CVXStaker report: looping token transfers without a zero-value guard.

### Finding Description
`withdraw()`:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
``` [1](#0-0) 

Unlike the non-Tron counterpart in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`, which explicitly guards `if (amount == 0) continue;` before transferring, [2](#0-1) 
the Tron implementation performs no such check. `withdraw()` is reachable from unprivileged, single-transaction paths such as order fill/cancel flows that assemble a `WithdrawalRequest` with `body.tokens[i].amount` derived from proportional/partial-fill math (`(order.inputs[i].amount * fillAmount) / totalRequired` on the corresponding same-chain fill logic used elsewhere in the codebase) or from a cross-chain fill/cancel response — both of which can legitimately produce a `0` entry for one of several escrowed input tokens in a multi-asset order while other entries remain non-zero.

### Impact Explanation
If any escrowed token used in an order is a "revert on zero transfer" ERC-20 and the per-order accounting produces a zero amount for that token in a given `WithdrawalRequest` (e.g. multi-token order where one input's proportional/rounded share resolves to zero on a partial fill, or a fully-zeroed leftover entry on refund/cancel), the entire `withdraw()` call reverts. This permanently blocks:
- Release of escrowed funds (other, non-zero tokens and accumulated `TRANSACTION_FEES`) to the solver/beneficiary for that order,
- Refunds to the user on cancellation,
since `_filled[body.commitment]` and `_orders` mutations are all rolled back together with the revert, and the order can be retried but will hit the same zero-amount token every time — a permanent freeze of escrowed funds for that specific order/commitment. This satisfies "permanent freezing of funds" for affected orders.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an order configured with an ERC-20 that reverts on zero-value transfers among its escrowed tokens, and (b) a code path that produces a zero balance for that token within a `WithdrawalRequest.tokens` array while other tokens/fees in the same batch are non-zero. Both partial-fill accounting and cross-chain settlement in this codebase can legitimately produce zero entries for a token that has already been fully accounted elsewhere, so this is triggerable by a normal solver/filler/user interaction, not just a crafted attack — consistent with the original finding being rated Medium.

### Recommendation
Add a zero-amount guard before each transfer in `withdraw()`, mirroring the fix already present in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`:
```solidity
if (amount == 0) { unchecked { ++i; } continue; }
```
placed before the `token == address(0)` branch, so a zero-amount entry is skipped rather than attempted, keeping the loop resilient to weird-ERC20 revert-on-zero-transfer semantics.

### Proof of Concept
1. Deploy an order whose inputs include token A (revert-on-zero-transfer ERC20) and token B (normal ERC20).
2. Trigger a partial fill or a fill/cancel sequence such that the `WithdrawalRequest.tokens` array passed to `withdraw()` contains `{token: A, amount: 0}` and `{token: B, amount: X > 0}` (e.g., token A's proportional escrow share rounds to zero for the given fill, while token B's does not).
3. Call the path leading into `withdraw()` (fill/cancel handling in `IntentGatewayV2.sol`).
4. `token.call(...)` for token A returns `success = false` because the token reverts on a zero-value transfer; the function reverts with `TransferFailed()`.
5. Token B's escrow and the accumulated `TRANSACTION_FEES` are never released — the beneficiary cannot claim any part of this order, and every retry hits the same revert, permanently freezing the escrowed funds. [3](#0-2)
