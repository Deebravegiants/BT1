## Title
Missing zero-address validation on `admin` in `EvmHost.updateHostParamsInternal` can permanently disable the admin-privileged freeze/consensus-recovery path - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal` validates `hostManager`, `handler`, `consensusClient`, `hyperbridge` and `stateMachines`/`unStakingPeriod` before applying a new `HostParams` struct, but never validates `params.admin` before overwriting `_hostParams.admin`. This mirrors the reported Timelock issue: a privileged address field is accepted and stored without a zero-address check, and once zeroed it can never be recovered because the admin is the only account (besides the handler) capable of exercising admin-only recovery powers.

### Finding Description
`EvmHost`'s constructor sets the initial admin without a zero check, and this is compounded by the update path: `updateHostParamsInternal` copies every field of `HostParams` into storage, including `admin`, with no equivalent to the `InvalidHostManager`/`InvalidHandler`/`InvalidConsensusClient` guards applied to other privileged addresses: [1](#0-0) 

This function is reachable from a **dispatched cross-chain governance request**, not just deployment: `HostManager.onAccept` decodes a `SetHostParam` action from an incoming ISMP request and calls `IHostManager(_params.host).updateHostParams(hostParams)`: [2](#0-1) 

Note that `HostManager` itself explicitly guards against a zero `admin` in its own constructor and in its `SetAdmin` action (`InvalidAdmin` error), reflecting that the project already recognizes zero-admin as an unacceptable state for that contract: [3](#0-2) [4](#0-3) 

But the exact same protection is absent for `EvmHost._hostParams.admin`, both at construction: [5](#0-4) 

and at every subsequent governance-driven update via `updateHostParamsInternal`, which is the sole gate the `HostParams.admin` field passes through.

Once `_hostParams.admin` is zero, the admin-gated `setFrozenState` path becomes half-crippled (only `handler` can unfreeze/freeze), and on `TestnetHost` the admin-privileged `updateHostParams` and repeated `setConsensusState` recovery paths become permanently unusable since `caller == address(0)` can never be satisfied by any real transaction sender: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a governance `SetHostParam` payload (constructed off-chain by the pallet, or replayed/malformed) carries `admin == address(0)`, `updateHostParamsInternal` will accept it silently, permanently zeroing the host's admin. Unlike `hostManager`/`handler`/`consensusClient`, there is no way to recover this because:
- The only entities allowed to change `admin` again are cross-chain governance via `updateHostParams` (still reachable, since that's gated by `hostManager`, not `admin`) — so on mainnet `EvmHost` the impact is more limited since governance itself doesn't depend on `admin`.
- However, on `TestnetHost` deployments (used per the constructor's own documentation as the admin-recovery-enabled variant), a zeroed `admin` permanently disables the admin-driven `updateHostParams`/`setConsensusState` recovery paths that are the entire reason `TestnetHost` exists, and the admin-side of `setFrozenState` (freeze/unfreeze) is lost on any deployment relying on it as a circuit breaker independent of the handler.

This is a Medium-severity permanent-loss-of-privileged-function issue, directly analogous to the reported Timelock finding, reachable through a legitimate dispatched governance request rather than only through deployment-script misconfiguration.

### Likelihood Explanation
Low-to-medium likelihood: it requires a `SetHostParam` payload with `admin == address(0)` to be dispatched and delivered, which would normally be avoided by well-formed governance tooling, but there is no on-chain guard preventing it, unlike the equivalent `HostManager.admin` field which is explicitly guarded in the same codebase in two places (constructor and `SetAdmin`). Since the pattern is inconsistently applied (`HostManager` protects it, `EvmHost` does not), an oversight or encoding bug in the pallet/relayer building the `HostParams` payload silently bricks the field.

### Recommendation
Add the same zero-address defense already used for `hostManager`, `handler`, and `consensusClient` to the `admin` field in `updateHostParamsInternal`, e.g.:
```solidity
if (params.admin == address(0)) revert InvalidAdmin();
```
and add a corresponding check in the `EvmHost` constructor, consistent with the protection already implemented in `HostManager`.

### Proof of Concept
1. Deploy `EvmHost`/`TestnetHost` normally with a valid admin.
2. Hyperbridge dispatches a `SetHostParam` request via `HostManager.onAccept` (`OnAcceptActions.SetHostParam`) with a `HostParams` payload where `admin = address(0)` — this passes all existing checks in `updateHostParamsInternal` (lines 583–621) since none of them reference `admin`.
3. `_hostParams.admin` is set to `address(0)` at line 628.
4. Any subsequent call gated by `caller == _hostParams.admin` (e.g., `TestnetHost.updateHostParams`, `setFrozenState`) can never succeed again since no `msg.sender` can equal `address(0)`, permanently removing that admin capability with no path to restore it outside of another (also-unguarded) governance `SetHostParam` call from `hostManager`.
