## Title
Missing request-receipt persistence when destination has no code allows deferred replay of incoming POST requests - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest, address)` is the handler-only entrypoint that `HandlerV2.handlePostRequests` uses to deliver a verified cross-chain POST request to its destination module [1](#0-0) . Just like the Zend-Session bug where a validator attached before `start()` never gets its "signature" persisted into `$_SESSION['__ZF']['_VALID']` — silently defeating the anti-replay check on the next request — `dispatchIncoming` skips writing the anti-replay receipt (`_requestReceipts[commitment]`) whenever the destination address currently has no code, silently defeating the "exactly-once delivery" invariant that `handlePostRequests`'s duplicate check relies on.

### Finding Description
`dispatchIncoming` computes the destination's code size and, if it is zero, returns immediately **before** the replay-protection write: [2](#0-1) 

Compare this to the deliberate cleanup path used when `onAccept` itself reverts: there, the receipt is written first and then explicitly `delete`d "so that it can be retried" — an intentional, auditable retry mechanism. The `size == 0` branch, in contrast, never writes the receipt at all, so there is no state change and no event recording that this delivery attempt ever happened.

The permissionless dispatcher, `HandlerV2.handlePostRequests`, only rejects duplicates by checking `host.requestReceipts(hash) != address(0)`: [1](#0-0) 

Because no receipt was ever recorded on the first (no-code) attempt, this check will keep passing for every re-submission of the same proof/request as long as the underlying state commitment is retained and the request has not timed out. This means the "one-shot" delivery guarantee for a given `PostRequest` is not actually enforced until a delivery attempt happens to land on a destination that already has code — an unprivileged relayer, or the eventual owner/deployer of that destination address, effectively controls *when* (and whether) the message becomes deliverable, by controlling when code is deployed at the `to` address. This is the same class of bug as the session-validator issue: metadata that is supposed to be persisted to make a security check meaningful is silently omitted under a specific, attacker-observable condition, and the very requestor of the write (the delivery function) has no idea that the invariant did not take effect.

### Impact Explanation
This breaks the exactly-once / anti-replay delivery guarantee central to ISMP's `handlePostRequests` — the same commitment can be legitimately (from the check's point of view) re-processed multiple times before it is first executed against real code, since the receipt bookkeeping never triggers until a `size > 0` attempt succeeds. An address that starts out empty (e.g., a pre-computed CREATE2 target not yet deployed) can be populated with attacker-chosen code between relayer attempts, letting the eventual code owner decide the timing of message execution and consume a message that other parties (source module/sender) assumed had already failed or been dropped, undermining message-delivery integrity for the affected route.

### Likelihood Explanation
`handlePostRequests` is fully permissionless and can be called by anyone holding a valid proof; the destination address `to` is chosen by the source-chain sender and is not restricted to already-deployed contracts. Any request whose destination address does not yet have code at first delivery attempt will hit this silent-skip path, and relayers routinely retry deliveries, making the missing-receipt condition easy to trigger without any special privilege.

### Recommendation
Persist a receipt (or otherwise durably record the delivery attempt) even when `extcodesize(destination) == 0`, or explicitly revert the individual request (rather than early-returning) so the batch handler can distinguish and reject/skip it deterministically, ensuring the anti-replay bookkeeping cannot be conditionally bypassed by the state of the destination address at delivery time.

### Proof of Concept
1. Source chain module dispatches a `PostRequest` whose `to` field is an address that has not yet been deployed to on the destination chain (e.g., a CREATE2 address reserved for future use).
2. A relayer submits `handlePostRequests` with a valid proof before the address has code; `dispatchIncoming` hits `size == 0` and returns without writing `_requestReceipts[commitment]` [3](#0-2) .
3. `handlePostRequests`'s duplicate check (`host.requestReceipts(hash) != address(0)`) still evaluates false because no receipt exists [1](#0-0) .
4. Code is later deployed at the `to` address (by its intended or an unintended party), and the same proof/request is resubmitted (as long as the state commitment and challenge period allow it and it has not timed out), causing `onAccept` to execute against code that did not exist at the time the message was originally dispatched — the timing and target of the message execution were never durably fixed by the protocol.

```text
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
```
