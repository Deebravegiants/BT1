### Title
Origin trust bypass via undefined `trusted` field defaulting to "trusted" - ([File: features/connected-origins/module/connections.js])

### Summary
The strongest analog found for the "empty state silently bypasses a required check" bug class (SafEth's `derivativeCount = 0` skipping the deposit/mint validation loop while still accepting funds) is the `isTrusted` logic in Hydra's connected-origins module. There, an *absent/undefined* `trusted` attribute on a stored origin record is treated as `true` (trusted) rather than failing safe, structurally identical to the SafEth pattern where an absent/zero-value state (`derivativeCount == 0`) causes the code to silently skip a should-be-mandatory gate.

### Finding Description
`ConnectedOrigins#isTrusted` reads: [1](#0-0) 

```js
isTrusted = async ({ origin }) => {
  const value = await this.#getOrigin({ origin })
  if (!value) return false
  // backward compatibility
  return value.trusted === undefined || value.trusted
}
```

If an origin record exists but its `trusted` field was never explicitly set (`undefined`), the function returns `true`. This mirrors the "zero/empty means proceed anyway" root cause of the SafEth bug: instead of failing closed when a piece of expected state is missing, the code fails open.

`add()` accepts `trusted` as an optional parameter with no default value: [2](#0-1) 

Any call path that persists a new origin entry (via `add`) without explicitly passing `trusted: true`/`false` will leave `trusted` as `undefined` in storage, and `isTrusted` will subsequently treat that origin as trusted — bypassing what should be an explicit user-approval gate before a dApp/origin is granted account access.

`isTrusted` directly gates `getConnectedAccounts`, which returns wallet account addresses to the origin: [3](#0-2) 

```js
getConnectedAccounts = async ({ origin }) => {
  const isTrusted = await this.isTrusted({ origin })
  if (!isTrusted) return []
  ...
}
```

### Impact Explanation
If any caller of `add()` (e.g., a connection-request flow that stores an origin optimistically, before the user has explicitly approved it, or a legacy/migration path that doesn't set `trusted`) omits the `trusted` flag, that origin becomes implicitly trusted. This grants a website/dApp cross-origin access to the user's wallet addresses via `connectedOrigins.getConnectedAccounts`/`connectedOrigins.get` without an explicit trust decision, which is an auth/origin-isolation bypass consistent with the required impact categories (cross-origin privilege bleed / auth bypass).

### Likelihood Explanation
I could not find, within this indexed repository, any UI/background caller of `connectedOrigins.add()` in the actual browser-extension connection flow (only test files call `add()` in this repo) to confirm whether production code ever calls `add()` without `trusted`. This is a real limitation: the connection-approval UI that invokes this module likely lives in the browser-extension app, which is not fully represented in this index. Because of this, I cannot conclusively prove that an unprivileged, unapproved-user-controlled path reaches `add()` without setting `trusted`, so likelihood is uncertain rather than confirmed. The root-cause code pattern (fail-open on missing/undefined field) is proven, but full reachability/proof-of-concept from an untrusted origin could not be established with the available files.

### Recommendation
Change `isTrusted` to fail closed on missing data:
```js
return value.trusted === true
```
and ensure `add()` requires an explicit `trusted` boolean (no implicit `undefined` "backward compatibility" fallback), or explicitly default `trusted` to `false` when not provided.

### Proof of Concept
Given the current implementation, the following (illustrative) sequence demonstrates the fail-open behavior purely within `connections.js`:
1. Call `connectedOrigins.add({ origin: 'evil.com', name: 'Evil', assetNames: ['ethereum'] })` (no `trusted` passed).
2. Call `connectedOrigins.isTrusted({ origin: 'evil.com' })` → returns `true` because `value.trusted === undefined`.
3. Call `connectedOrigins.getConnectedAccounts({ origin: 'evil.com' })` → returns the user's wallet account addresses, even though the user never explicitly trusted `evil.com`.

This is confirmed by the existing repo test that directly exercises the `undefined`-trusted-implies-trusted branch: [4](#0-3) 

Note: I was unable to verify a production (non-test) code path that calls `.add()` without `trusted` set, due to indexing limits on this repo (the browser-extension UI layer that likely drives this flow is not represented in the available context). A Devin session with full repo access would be needed to trace the actual connection-approval call sites and confirm end-to-end exploitability.

```javascript
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```
