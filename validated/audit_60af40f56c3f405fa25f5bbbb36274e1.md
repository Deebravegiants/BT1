This confirms the finding: `AuthQuery#to_signable_string` includes `shop` in the HMAC-covered params, while `Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the `shop-domain` header is never covered by the HMAC in the webhook path.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` directly from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against the app's shared `client_secret`-derived HMAC secret. Because the HMAC signable string excludes the shop-domain header, an attacker who can produce one validly-signed webhook body (trivial, since the same `api_secret_key` is used for every shop the app serves) can replay/craft a request claiming an arbitrary `shop-domain`, and `Registry.process` will pass that spoofed shop identity straight into the app's handler as authenticated data.

### Finding Description
`Webhooks::Request` reads the tenant-identifying `shop` field from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

Its `to_signable_string`, which is what actually gets HMAC-verified, returns only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts this validation result and then forwards `request.shop` (and `request.topic`, `request.webhook_id`) — all unauthenticated header values — straight to the host app's handler as `WebhookMetadata`: [4](#0-3) 

Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set, so the shop identity *is* bound to the HMAC there: [5](#0-4) 

This is the same class of bug as the referenced report: a field that is *acted upon* (the tenant/shop identity used to route the webhook payload to the app's business logic) is not covered by the integrity check (the HMAC), so it can be substituted independently of the signed content. Critically, `api_secret_key` is a single per-app secret shared across all shops that install the app — it is not shop-specific. Any user who can get their own shop to legitimately install the app and trigger one webhook delivery (an ordinary, unprivileged action available to any Shopify merchant) obtains a validly-signed `(body, hmac)` pair. Because `shop-domain` is excluded from the signed content, that same signed body can be resubmitted to the app's webhook endpoint with the `shop-domain` header changed to any other shop the attacker wants to impersonate, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the identity binding: `shop` used by the handler == `shop` that produced/authorized the signed payload should hold, but does not. The host app's webhook handler receives `data.shop` believing it to be the authenticated origin of the event, when in fact the attacker fully controls it. Depending on how the host app implements `WebhookHandler#handle` (per the gem's documented usage — see `docs/usage/webhooks.md`, which explicitly tells implementers to key work off `data.shop`), this enables cross-tenant data confusion: a malicious merchant can inject webhook events attributed to a victim shop, causing the app to act on/against the victim's tenant data using the attacker-chosen body content signed under their own shop's legitimately-triggered webhook.

### Likelihood Explanation
Likelihood is high for any app author who follows the gem's own documented pattern of trusting `data.shop` for tenant routing, since the vulnerable code lives entirely inside this gem (`Webhooks::Request` and `Webhooks::Registry.process`) rather than depending on host-app misuse. No credentials beyond ordinary app installation (available to any unprivileged Shopify merchant) are required to obtain one valid `(body, hmac)` pair; from there, spoofing the shop header is a simple raw HTTP replay against the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the HMAC-signable content, mirroring `AuthQuery#to_signable_string`, or — since Shopify's actual webhook HMAC is computed over the raw body only by design — require `Registry.process` to cross-check the `shop-domain` header against a shop that is actually known/installed (e.g., verified against session storage) before dispatching to the handler, rather than treating the header as trusted metadata.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), receiving a request with body `B` and a valid `x-shopify-hmac-sha256` header `H` computed by Shopify over `B` using the app's single `client_secret`.
2. Attacker replays this exact `(B, H)` pair directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from that header unchanged.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`B` only) and it matches `H`, so validation succeeds: [3](#0-2) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...))`, and the host app processes attacker-controlled body content as if it originated from the victim shop.
