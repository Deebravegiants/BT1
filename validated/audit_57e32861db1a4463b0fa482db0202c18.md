### Title
`make_signature` produces a signature with no `signup_id`/nonce binding, enabling attestation replay across signup sessions - ([File: src/plans/enroll_user.rs])

### Summary
`make_signature` (src/plans/enroll_user.rs:290-304) builds the SHA256 context solely from `ORB_ID`, `user_qr_code.user_id`, and the pipeline's iris/mask codes and version strings; it never includes the per-session `signup_id` or any nonce. The resulting signature is sent to the backend by `signup_post::request` (src/backend/signup_post.rs:100-161) only inside the multipart form's `signature` field, while `signup_id` is carried separately as a URL path segment (`/api/v2/signups/{signup_id}`), so the cryptographic attestation itself carries no information tying it to that specific signup transaction.

### Finding Description
`make_signature` computes: [1](#0-0) 
The SHA256 context only covers `ORB_ID`, `user_qr_code.user_id`, and pipeline version/iris/mask code bytes - there is no `ctx.update` call for `signup_id` or any freshness/nonce value. The `signup_id` (a `SignupId`, generated per enrollment attempt) is only used afterwards to build the request path: [2](#0-1) 
and in `signup_post::request` it is interpolated into the URL, disjoint from the signed payload: [3](#0-2) 

Because `signup_id` and any session nonce are absent from the signed digest, two calls to `make_signature` with the same `user_qr_code` and the same `pipeline` (i.e., identical iris/mask codes and version strings) yield byte-identical signatures regardless of which `signup_id` the request is eventually posted under. Since biometric capture and pipeline computation happen entirely client-side, if an attacker can cause the pipeline to emit identical iris/mask code bytes twice (e.g., by presenting the same static iris image/photo to the camera in two separate signup sessions, without any hardware/MCU tampering), orb-core will produce and submit an identical `signature` value for two different `signup_id`s.

### Impact Explanation
If the backend treats this `signature` field as proof of a genuine on-orb signing event for that specific signup, but does not independently bind the signature to `signup_id` server-side, an attacker could replay a previously-produced valid signature to attempt to legitimize a second, unrelated signup attempt (e.g., after modifying other request metadata) since the client-side attestation carries no session-specific binding. This corresponds to an attestation-forgery / replay-of-signing-primitive issue in the signup pipeline.

### Likelihood Explanation
Reproducing this in orb-core is deterministic and trivial: calling `make_signature` twice with identical `user_qr_code`/`pipeline` inputs but different intended `signup_id` values always yields the same signature, because `signup_id` is never part of the function's arguments or the hashed context. Whether this is actually *exploitable end-to-end* depends on backend-side verification logic (not present in this repository) - specifically whether the backend independently binds the `signature` to the `signup_id` path parameter or validates freshness some other way. That backend behavior cannot be confirmed from this codebase, so real-world exploitability of a full unauthorized-second-signup is only partially provable from orb-core alone; the client-side attestation design flaw itself, however, is fully and reproducibly demonstrated in-repo.

### Recommendation
Include `signup_id` (and ideally a server-issued or locally-generated per-attempt nonce/timestamp) in the `Context` updated inside `make_signature` before signing, so that the resulting signature cryptographically commits to the specific signup transaction and cannot be replayed across different `signup_id`s or sessions.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
