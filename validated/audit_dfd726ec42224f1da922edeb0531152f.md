Audit Report

## Title
Missing role-based permission check on node pprof/debug endpoints allowing low-privilege user to access sensitive diagnostics - (File: core/web/router.go)

## Summary
The `/v2/debug/pprof/*` routes registered by `metricRoutes` in `core/web/router.go` are mounted inside the already-authenticated `authv2` group but are not wrapped with any `auth.RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` check, unlike virtually every other sensitive route registered in the same block. Any authenticated user, including the lowest-privileged `UserRoleView` account, can access full Go `pprof` introspection (heap dumps, goroutine stacks, command-line, CPU/execution traces).

## Finding Description
`v2Routes` builds `authv2` requiring only session or token authentication with no role restriction on the group itself: [1](#0-0) . Nearly every sensitive controller action registered on `authv2` is explicitly wrapped with a role-check middleware such as `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole` (e.g. key export/import, user management, transfers): [2](#0-1) .

`metricRoutes(authv2)` is called unconditionally inside that authenticated block, and it registers every pprof handler directly on the group with zero role-check wrapping: [3](#0-2) . For contrast, `debugRoutes` (a similar diagnostic endpoint, `/debug/vars`) is at least separately gated behind its own `auth.Authenticate(...)` call, showing this is an established pattern that was not applied to `metricRoutes`: [4](#0-3) .

Confirming this via the existing RBAC regression test suite: `routesRolesMap` in `core/web/auth/auth_test.go`, which is used by `TestRBAC_Routemap_Admin`, `TestRBAC_Routemap_Edit`, `TestRBAC_Routemap_Run`, and `TestRBAC_Routemap_ViewOnly` to assert the expected role required for every sensitive route, contains no entries at all for `/v2/debug/pprof/*`: [5](#0-4) . This means the pprof routes are not covered by the RBAC regression tests, and the lack of a role check is a genuine gap rather than an intentional, tested design decision.

## Impact Explanation
A user provisioned with only `UserRoleView` (the lowest role in the RBAC model) can hit `GET /v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/cmdline`, and `/v2/debug/pprof/profile`/`trace` (with attacker-controlled `seconds` query parameter). These can leak full process memory contents (potentially decrypted secrets/private keys held in memory), goroutine stacks (revealing internal architecture/data), and process command-line arguments, and can be used as a limited DoS vector via extended CPU/trace profiling. This maps to the in-scope "key/secret exfiltration" and "node API authentication or role bypass" impact categories.

## Likelihood Explanation
Likelihood is high for any deployment that provisions view-only API users (a documented, supported role for e.g. monitoring/read-only integrations). No social engineering or vulnerability chain is required — a single authenticated HTTP GET from a low-privilege, otherwise legitimately provisioned account is sufficient, and it is reachable purely via the node's own HTTP API without host/database access.

## Recommendation
Wrap the pprof route group registered by `metricRoutes` with an explicit `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) middleware, consistent with how every other sensitive `/v2` endpoint in `core/web/router.go` is protected. Add corresponding entries to `routesRolesMap` in `core/web/auth/auth_test.go` so the RBAC regression tests (`TestRBAC_Routemap_*`) catch any future regression.

## Proof of Concept
1. As an admin, create a user with `UserRoleView` (`POST /v2/users` with role `view`).
2. Log in as that view-only user (`POST /v2/sessions`).
3. Issue `GET /v2/debug/pprof/heap?debug=1` (or `/v2/debug/pprof/cmdline`, `/v2/debug/pprof/goroutine?debug=2`) using the view-only session cookie.
4. Observe `200 OK` with full pprof output, in contrast to essentially every other `/v2` route the view role cannot access without `viewOnlyAllowed` being true in `routesRolesMap`.
5. As an integration test extension, add `{"GET", "/v2/debug/pprof/heap", false, false, false}` (expected admin-only) to `routesRolesMap` in `core/web/auth/auth_test.go` and run `TestRBAC_Routemap_ViewOnly` — it will currently pass with 200 instead of 403, demonstrating the gap once the route is included in the coverage table.
