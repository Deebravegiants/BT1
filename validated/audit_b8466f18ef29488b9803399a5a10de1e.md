### Title
Unbounded `u256`→integer coercions in the SP1 BEEFY proof decode path panic the runtime on attacker-chosen values, causing a crash on extrinsic execution - (File: evm/rust/src/conversions.rs)

### Summary
The CVE describes a DDL-path crash in MySQL: attacker-supplied input reaches an unguarded internal operation and crashes/hangs the server. The closest reachable analog in this codebase is the `From<SP1Beefy::SP1BeefyProof>` conversion used when decoding a relayer/prover-submitted SP1 BEEFY proof: it uses `.try_into().expect(...)` on ABI-decoded `uint256` fields, which panics the runtime if the submitted value doesn't fit the target integer type.

### Finding Description
`evm/rust/src/conversions.rs` implements the conversion from the Solidity-ABI-decoded `SP1Beefy::SP1BeefyProof` struct into the internal `Sp1BeefyProof` type: [1](#0-0) 

```rust
impl From<crate::sp1_beefy::SP1Beefy::SP1BeefyProof> for Sp1BeefyProof {
    fn from(value: crate::sp1_beefy::SP1Beefy::SP1BeefyProof) -> Self {
        Sp1BeefyProof {
            block_number: value.commitment.blockNumber.try_into().expect("block number out of bounds"),
            validator_set_id: value.commitment.validatorSetId.try_into().expect("validator set id out of bounds"),
            ...
        }
    }
}
```

`blockNumber` and `validatorSetId` are Solidity `uint256` fields fully controlled by whoever submits the proof bytes. The conversion target is a narrower integer type (`u64`/similar), and any submitted value outside that range causes `.expect(...)` to panic rather than return a typed error.

This conversion is reached from `modules/pallets/beefy-consensus-proofs/src/lib.rs`, where a submitter's raw proof bytes are ABI-decoded and immediately converted with `.into()`: [2](#0-1) 

```rust
let abi_payload = &proof[1..];
let abi_proof = <ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof as SolType>::abi_decode_params(abi_payload)
    .map_err(|_| Error::<T>::AbiDecodeFailed)?;
let scale_proof: beefy_verifier_primitives::Sp1BeefyProof = abi_proof.into();
```

This is `settle_uncle_proof`, callable by any `submitter: T::AccountId` — i.e. any unprivileged account/relayer submitting a consensus proof — not gated by governance/admin. The equivalent "first proof" acceptance path in the same pallet uses the same ABI-decode-then-`.into()` sequence. Since `abi_decode_params` only validates ABI shape (not numeric range), an attacker can craft a syntactically valid `SP1BeefyProof` whose `blockNumber` or `validatorSetId` exceeds the target integer's range, triggering the `.expect()` panic during extrinsic dispatch.

This pattern is the same bug class the codebase has already fixed elsewhere for other attacker-controlled inputs: e.g. `modules/consensus/beefy/verifier/src/lib.rs` explicitly documents and fixes a prior panic from an unchecked `leaf_indices[0]` index reachable "via the unsigned consensus message" [3](#0-2) , and `modules/consensus/sync-committee/verifier/src/lib.rs` documents a fix for a `calculate_multi_merkle_root` panic reachable "via the public unsigned consensus update path" [4](#0-3) . The `SP1BeefyProof` numeric-coercion panic is an un-fixed instance of the same class.

### Impact Explanation
A panic raised inside pallet dispatch logic during block execution is a denial-of-service against block production/consensus processing on the affected chain — analogous to CVSS Availability-only impact of the reference CVE (hang/crash, no confidentiality/integrity loss). Any account able to submit an SP1 BEEFY proof (an unprivileged, permissionless submitter role) can trigger it repeatedly.

### Likelihood Explanation
High likelihood of reachability: the dispatchable is permissionless (`submitter: T::AccountId`), the ABI decode step only checks structural validity, and crafting a `uint256` value outside the target integer range is trivial for any caller.

### Recommendation
Replace all `.try_into().expect(...)` numeric coercions in `evm/rust/src/conversions.rs` (and any similar ABI→SCALE proof conversions) with fallible conversions that propagate a typed decode error (e.g. `AbiDecodeFailed`/`InvalidProof`) instead of panicking, mirroring the fixes already applied to the BEEFY MMR leaf-index and sync-committee multiproof paths.

### Proof of Concept
1. Construct a syntactically valid ABI-encoded `SP1Beefy::SP1BeefyProof` where `commitment.blockNumber` (or `validatorSetId`) is set to a `uint256` value exceeding the target Rust integer type's max (e.g. `u64::MAX + 1`).
2. Submit it as the `proof` argument to `pallet_beefy_consensus_proofs`'s uncle/first-proof extrinsic from any unprivileged account.
3. `abi_decode_params` succeeds (structure is valid); the subsequent `.into()` conversion hits `.try_into().expect("block number out of bounds")` and panics, aborting the extrinsic's execution context.
