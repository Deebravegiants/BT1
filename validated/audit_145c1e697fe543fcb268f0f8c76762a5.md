### Title
`AuroraEngineBridge.describeWithdrawal()` unconditionally reports "completed" without checking the actual cross-contract outcome - (File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts)

### Summary
`AuroraEngineBridge.describeWithdrawal()` always returns a hard-coded `{ status: "completed", txHash: null }` regardless of whether the underlying NEP-141 transfer to the Aurora Engine contract actually succeeded on-chain.

### Finding Description
The withdrawal for the "virtual chain" (Aurora Engine) route is built as an `ft_withdraw` intent whose `msg` triggers a cross-contract `ft_on_transfer` call into `auroraEngineContractId` (or a proxy token contract) to deposit funds into the virtual chain: [1](#0-0) 

NEP-141 `ft_transfer_call`/`ft_on_transfer` semantics are asynchronous: the receiving contract's callback determines how many tokens (if any) are actually accepted, and unaccepted tokens are refunded to the sender via `ft_resolve_transfer`. This means the transfer can partially or fully fail after the NEAR transaction that submitted the intent has already been included, without the intents transaction itself failing.

Despite this, `describeWithdrawal()` for this bridge does not inspect the transaction receipts, does not call any indexer or view method, and does not distinguish success from failure/refund - it just returns `"completed"` unconditionally: [2](#0-1) 

This is in contrast to every other bridge implementation in the same directory structure, which all derive the reported status from an authoritative on-chain/indexer source, e.g. Omni Bridge inspects `transfer.finalised?.transaction_hash` from the bridge API before reporting `"completed"`: [3](#0-2) 
and HOT Bridge cross-checks contract state, bridge indexer, and API fallback before returning a status: [4](#0-3) 

The equality broken here is: *status reported == actual on-chain outcome*. For `AuroraEngineBridge`, the reported status is a constant, decoupled from whether the deposit into the destination virtual chain actually succeeded.

### Impact Explanation
`sdk.waitForWithdrawalCompletion()` (in `packages/intents-sdk/src/sdk.ts`) relies on `describeWithdrawal()` to decide when a withdrawal is done, and integrators are expected to trust the "completed" status to credit users or release downstream funds. If the Aurora Engine deposit fails and tokens are refunded to the intents contract (a legitimate, unprivileged on-chain outcome triggered simply by depositing to an invalid/rejecting recipient, a paused engine, or insufficient min-gas), the SDK still reports the withdrawal as `"completed"`. An integrator building on this SDK could credit the destination account as if funds arrived, while the funds actually remain in (or were refunded to) the NEAR intents contract - a status misreport that can lead to double-crediting or unrecoverable accounting mismatches, matching the "status or hash misreport making an integrator credit or refund twice" impact category.

### Likelihood Explanation
No malicious actor is required; only conditions that a normal user, contract state, or gas configuration can trigger unprivileged: an Aurora Engine deposit rejecting the transfer (invalid/blacklisted destination address, paused/upgraded engine contract, insufficient `min_gas`, or any `ft_on_transfer` revert on the destination) will cause NEP-141 to refund tokens asynchronously, which this bridge implementation cannot detect. Since `describeWithdrawal` never checks anything, this occurs deterministically whenever the deposit callback does not fully accept the amount.

### Recommendation
Make `describeWithdrawal()` verify the actual on-chain outcome before returning `"completed"`, e.g. by inspecting the NEAR transaction receipts/outcomes of `args.tx.hash` for the `ft_on_transfer`/`ft_resolve_transfer` result, or checking the resulting balance/refund amount, similar to how `OmniBridge` and `HotBridge` derive status from authoritative on-chain/indexer data instead of a hard-coded value.

### Proof of Concept
1. Build and submit an Aurora Engine ("virtual chain") withdrawal intent via `createWithdrawalIntents` for a destination address/engine configuration that causes the Aurora Engine's `ft_on_transfer` callback to reject or only partially accept the transfer (e.g., recipient not registered/blacklisted in the destination virtual chain, or the aurora engine contract is paused).
2. NEAR's NEP-141 refund mechanism (`ft_resolve_transfer`) returns some or all of the tokens to the intents contract because the deposit failed.
3. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams, intentTx })`, which internally calls `AuroraEngineBridge.describeWithdrawal()`.
4. Observe that the call returns `{ status: "completed", txHash: null }` unconditionally (see `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts:220-222`), even though the tokens never landed on the destination chain and were refunded — no error, no `"failed"`/`"pending"` status is ever produced by this code path.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const cacheKey = this.getNoncesCacheKey(args.tx);
		const nonces = await this.noncesCache.fetch(cacheKey, { context: args.tx });
		if (nonces == null) {
			throw new HotWithdrawalNotFoundError(args.tx.hash, args.index);
		}

		const nonce = nonces[args.index];
		if (nonce == null) {
			throw new HotWithdrawalNotFoundError(args.tx.hash, args.index);
		}

		const status: unknown = await this.hotSdk.getGaslessWithdrawStatus(
			nonce.toString(),
		);
		// stop polling in case withdrawal is cancelled
		if (status === HotWithdrawStatus.Canceled) {
			return {
				status: "failed",
				reason: "Withdrawal was cancelled",
			};
		}

		const isEvm = args.landingChain.startsWith("eip155:");
		const isTon = args.landingChain === Chains.TON;
		// Bridge indexer is the source of truth for destination hashes on these chains.
		// TON does not fall back to HOT API hashes because they can refer to trace roots instead of CEX-visible transfers.
		if (isEvm || args.landingChain === Chains.Stellar || isTon) {
			try {
				args.logger?.info("Fetching withdrawal hash from bridge indexer", {
					nearTxHash: args.tx.hash,
					nonce: nonce.toString(),
				});
				const bridgeIndexerHash = await this.fetchWithdrawalHashBridgeIndexer(
					args.tx.hash,
					nonce.toString(),
					args.logger,
				);
				if (bridgeIndexerHash !== null) {
					args.logger?.info("Bridge indexer found withdrawal hash", {
						withdrawalHash: bridgeIndexerHash,
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
					});
					return {
						status: "completed",
						txHash: bridgeIndexerHash,
					};
				}
			} catch (error) {
				if (isTon) {
					args.logger?.error(
						"Bridge indexer failed unexpectedly, keeping TON withdrawal pending",
						{
							nearTxHash: args.tx.hash,
							nonce: nonce.toString(),
							error,
						},
					);
					return { status: "pending" };
				}

				// Bridge indexer failed, fallback to HOT API
				args.logger?.error(
					"Bridge indexer failed unexpectedly, trying HOT API fallback",
					{
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
						error,
					},
				);
				const apiHash = await this.fetchWithdrawalHashFromApi(
					args.tx.hash,
					nonce,
					args.logger,
				);
				if (apiHash != null) {
					args.logger?.info("HOT API fallback found withdrawal hash", {
						withdrawalHash: apiHash,
						nearTxHash: args.tx.hash,
						nonce: nonce.toString(),
					});
					return {
						status: "completed",
						txHash: formatTxHash(apiHash, args.landingChain),
					};
				}
			}
		} else {
			// Fallback for other non EVM networks
			// Primary source: contract view method
			if (status === HotWithdrawStatus.Completed) {
				return { status: "completed", txHash: null };
			}
			if (typeof status === "string") {
				// HOT returns hexified raw bytes without 0x prefix, any other value should be ignored.
				if (!isHex(status)) {
					args.logger?.warn(
						"HOT Bridge incorrect destination tx hash detected",
						{
							value: status,
						},
					);
					return { status: "completed", txHash: null };
				}
				return {
					status: "completed",
					txHash: formatTxHash(status, args.landingChain),
				};
			}

			// Fallback: API indexer (when contract returns null/pending)
			const apiHash = await this.fetchWithdrawalHashFromApi(
				args.tx.hash,
				nonce,
				args.logger,
			);
			if (apiHash != null) {
				return {
					status: "completed",
					txHash: formatTxHash(apiHash, args.landingChain),
				};
			}
		}

		return { status: "pending" };
	}
