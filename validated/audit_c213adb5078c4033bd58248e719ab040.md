## Analysis: `CallDispatcher.dispatch()` has no access control

The reported bug class — an arbitrary-call executor with no `msg.sender` restriction, letting anyone route an attacker-chosen call through a contract that later moves funds — maps directly onto Hyperbridge's shared `CallDispatcher` contract.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows any caller to sweep tokens/ETH left on the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes fully attacker-supplied `Call[]` (arbitrary `to`/`value`/`data`) with **no caller authentication whatsoever**, exactly like the reported `D3MMLiquidationRouter.D3Callee()` pattern where `router.call(routeData)` is reachable by anyone. `CallDispatcher` is a single shared singleton used by `IntentGatewayV2` (predispatch/postdispatch swap execution) and `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept` calldata execution), and it only ever gets its balances swept back for the *specific* tokens enumerated by the order/message that dispatched it — not for arbitrary residual balances.

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no modifier, no `onlyHost`, no allow-listed-caller check, and no reentrancy guard: [1](#0-0) 

Any address can call this function directly and force `CallDispatcher` to execute `to.call{value: call.value}(call.data)` for a fully attacker-chosen `to`/`data`, identical in shape to the reported `router.call(routeData)` primitive.

`CallDispatcher` is intentionally used as a *shared* execution sandbox across multiple apps:
- `IntentGatewayV2.placeOrder` transfers predispatch assets into the dispatcher, calls `dispatch(order.predispatch.call)`, then sweeps back **only the tokens listed in `order.inputs`**: [2](#0-1) 
- `IntentsBase._execute` (postdispatch) does the same, sweeping back **only `order.output.assets[i].token`**: [3](#0-2) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken` mint tokens to the dispatcher and then run user-supplied `Call[]` on `onAccept`, per the documented calldata-execution flow: [4](#0-3) 

Because the sweep logic in every caller is enumerated over the *specific tokens that flow belongs to* rather than "whatever balance the dispatcher happens to hold," any token or native ETH that ends up on `CallDispatcher` outside that enumerated set — e.g., dust from a partial DEX swap, a reward/airdrop token, WETH left over from a `deposit()`/swap sequence that isn't one of `order.inputs`/`order.output.assets`, or ETH sent directly to the dispatcher's `receive()` — is never swept by the legitimate flow and simply accumulates in the contract's balance. Because `dispatch()` has no access control, that accumulated balance can be drained by **anyone**, at any time, by calling `CallDispatcher.dispatch()` directly with a `Call` such as `IERC20(token).transfer(attacker, balance)` or a raw ETH-forwarding call — bypassing `IntentGatewayV2`, the ISMP host, and every app-level guard entirely.

### Impact Explanation
Since `CallDispatcher` is shared by every app deployment (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) rather than deployed per-app with a caller restriction, any leftover value on it is a standing, permissionless honeypot. An unprivileged actor with no special role can extract funds that legitimately belong to users/protocol dust accounting, which is a direct theft of funds vector analogous to the reported issue.

### Likelihood Explanation
Exploitation requires only a plain transaction calling `dispatch()` — no proof, no relayer, no privileged role. The likelihood of nonzero balances arising is driven by any predispatch/postdispatch swap path producing tokens outside the exact enumerated set (e.g., partial fills, slippage residue, non-path tokens, or a mis-specified sweep list), all of which are realistic in DEX-routed calldata execution.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., only the registered `IntentGatewayV2`/HFT app addresses, or only the ISMP host), and/or make `CallDispatcher` deployed per-caller instead of shared, and/or have every flow sweep the dispatcher's *entire* balance of any token it could plausibly receive (not just the enumerated order tokens) atomically within the same transaction before returning control.

### Proof of Concept
1. Wait for (or induce, e.g., via a partial-fill swap in `predispatch`/postdispatch calldata) a state where `CallDispatcher` holds a nonzero balance of some token `T` that is not part of the triggering order's `inputs`/`output.assets` enumeration (so it isn't swept back).
2. Call `CallDispatcher.dispatch(abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(T).balanceOf(dispatcherAddress))})]))` directly from any EOA — no `onlyHost`/allow-list check exists to block this.
3. `CallDispatcher` executes the transfer as itself, moving token `T`'s balance to the attacker, as shown in `dispatch()`: [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
