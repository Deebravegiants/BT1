### Title
Setting `circomData.relay = address(0)` while `feeStructure.feeToken != outputToken` permanently strands both `relayFee` (feeToken) and `hinkalFee` (outputToken) in `ExternalActionSwap` - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
In `ExternalActionSwap.swap`, when the attacker-chosen `feeStructure.feeToken` differs from `outputToken`, fees are paid out via two separate `sendToRelay` calls instead of one combined call. `Transferer.sendToRelay` no-ops entirely when `relay == address(0)`, but the fee amounts have already been carved out of the flows that reach the user/Hinkal, so both fee amounts become permanently stuck in the action contract instead of reaching either the relay or the depositor's UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving the action contract == `-deltaAmountChanges` that Hinkal accounted for* (i.e. every unit of a token debited from the action's balance is either forwarded to the relay, the user, or credited into a new UTXO).

Trace of `contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`:
- If `inputToken == feeStructure.feeToken`, `flatFee` is subtracted from `inputAmount` before the swap is executed (line 47-49), but the *full* `deltaAmounts[0]` (including `flatFee`) was already transferred into the action by `Hinkal._externalTransact` before `runAction` is invoked [1](#0-0) . So `flatFee` worth of `inputToken` sits unspent in the contract, intended to be forwarded via `sendToRelay(circomData.relay, relayFee, feeStructure.feeToken)`.
- Because `feeStructure.feeToken != outputToken`, the `else` branch fires two separate `sendToRelay` calls instead of the combined one: [2](#0-1) 
- `totalFee` is computed as `hinkalFee + (outputToken == feeStructure.feeToken ? relayFee : 0)` — since the tokens differ, `relayFee` is excluded, so `amountToSendToHinkal = swappedAmount - hinkalFee` already deducts `hinkalFee` of `outputToken` from what is forwarded to `msg.sender` (Hinkal) [3](#0-2) .
- `Transferer.sendToRelay` is a strict no-op whenever `relay == address(0)`: [4](#0-3) .

An unprivileged EOA can set `circomData.relay = address(0)` legitimately — this is an explicitly supported "self-relay" mode, confirmed by the analogous check in `Hinkal._internalTransact`: `require(circomData.relay == address(0) || hasPaidToRelay, "relay not paid")` [5](#0-4) . `feeStructure` is a free-form field hashed into `calldataHash`/public inputs (via `CircomDataBuilder.getHashedCalldata2`) rather than constrained to equal `inputToken`/`outputToken`, so the attacker (who generates their own proof) can set `feeToken == inputToken` and `outputToken` to a different token with no on-chain check rejecting the combination.

With `relay = address(0)` and `feeToken == inputToken != outputToken`:
1. `sendToRelay(0, relayFee, inputToken)` — no-op, so `relayFee` of `inputToken` (already excluded from the swapped amount) is never moved anywhere and remains on the action contract.
2. `sendToRelay(0, hinkalFee, outputToken)` — no-op, and `hinkalFee` of `outputToken` was already subtracted from `amountToSendToHinkal`, so it also remains stranded on the action contract.

Neither amount is credited to any UTXO, sent to any relay, or returned to the user — both silently vanish from the accounted flow while remaining as real ERC-20 balance sitting on the action contract, violating the leaving-funds-must-equal-accounted-delta invariant for two tokens in a single transaction.

Existing guards do not catch this: `performHinkalChecks`/`dimensionsCheck` validate structural shape and hashes, not that fee amounts are actually delivered; the circuit's `inTotal + amountChanges === outTotal` constrains the declared deltas, not what `ExternalActionSwap` does internally with the post-swap balance; and `sendToRelay`'s own address(0) guard is precisely the mechanism causing the silent drop.

### Impact Explanation
Impact is permanent freezing of protocol/relay fees for two distinct tokens simultaneously in a single call, which the rules classify as High ("theft or permanent freezing of protocol/relay fees"). This is not, by itself, proven to constitute theft of another user's principal shielded value — the amounts stranded are the fee amounts of the depositor's own transaction (self-relayed), and I could not confirm within available context a deterministic on-chain mechanism by which a later, unrelated caller's `swap()` (whose `swappedAmount` is computed strictly as a pre/post router-call balance delta, not the contract's total balance) automatically sweeps this stranded residue into their own UTXO. The described "next caller sweeps it" step would require the attacker's `externalActionMetadata` (fully attacker-crafted calldata to the router) to induce the router to pull more than the declared `inputAmount` via the unlimited approval, which is plausible given `approveUnlimited(inputToken, router)` in `LifiExternalAction.callRouter`, but this second step is not independently verified in the traced code and is router-implementation dependent.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: any unprivileged EOA depositing/swapping their own funds can set `circomData.relay = address(0)` and choose `feeStructure.feeToken == inputToken` with a different `outputToken` while generating a valid proof for their own UTXOs. No special role or victim interaction is required, and the code path (`ExternalActionSwap.swap` else-branch plus `Transferer.sendToRelay`'s guard) is reached on every such call.

### Recommendation
In `ExternalActionSwap.swap`, when `relay == address(0)`, do not silently drop fee amounts. Either (a) revert if `relay == address(0)` but `relayFee > 0` or `hinkalFee > 0` (mirroring `Hinkal._internalTransact`'s `require(circomData.relay == address(0) || hasPaidToRelay, ...)` pattern in reverse), or (b) redirect undeliverable fees back into `amountToSendToHinkal`/the input-side return path so they are always accounted for in the returned `UTXO[]`, ensuring every token unit debited from the action is either forwarded to a relay or credited back into a UTXO.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (or a mock `ExternalActionSwap` subclass with a stub `callRouter`), and a mock router that performs a 1:1 swap of `tokenA` (input) for `tokenB` (output).
2. Craft `circomData` with `feeStructure.feeToken = tokenA`, `erc20TokenAddresses = [tokenA, tokenB]`, `relay = address(0)`, `flatFee > 0`, `variableRate > 0`, and a locally generated valid proof for the attacker's own deposited UTXO of `tokenA`.
3. Execute the transaction and assert:
   - `IERC20(tokenA).balanceOf(action) == flatFee` (stranded relay fee, nonzero) — this is the `relayFee` that should have left the action but didn't.
   - `IERC20(tokenB).balanceOf(action) == hinkalFee` (stranded protocol fee, nonzero) — this is the `hinkalFee` that should have left the action but didn't.
   - Confirm the UTXO returned/committed for the attacker has `amount == swappedAmount - hinkalFee` (excludes the stranded fee) while the action contract's real balances show both fee tokens sitting unaccounted, directly demonstrating `tokens leaving action != -deltaAmountChanges accounted by Hinkal` for both `tokenA` and `tokenB` in the same transaction.
