### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header to attribute the payload to a tenant. Because the HMAC signature never binds the shop identity, and because the signing secret (`Context.api_secret_key`) is shared across every merchant/shop that has the app installed, an attacker who controls any single shop with the app installed can capture a legitimately signed `(raw_body, hmac)` pair from their own store's webhook traffic and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a request header that is never part of the signed material: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (i.e. the body signature) before dispatching the handler with the header-derived `request.shop`: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) only, using the app-wide `Context.api_secret_key`: [4](#0-3) 

The identity binding the code implicitly assumes is: `shop (header, trusted downstream)` == `shop that produced the HMAC-signed body`. In reality the equation is:
`HMAC(secret, raw_body)` only proves *some* shop of this app produced this body — it says nothing about which `shop` header is attached to the HTTP request. Since the same `api_secret_key` signs webhooks for every shop that installs the app, an attacker who is a legitimate (even free-tier) merchant of the app can:
1. Trigger a webhook on their own shop (e.g. `orders/create`) and capture the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify sends them.
2. Replay that identical body + HMAC to the app's public webhook endpoint, but substitute `x-shopify-shop-domain` (or `shopify-shop-domain`) with a victim shop's domain.
3. `HmacValidator.validate` succeeds (body/HMAC pair is genuinely valid for this app's secret), and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim's domain.

Any handler that uses `data.shop` to look up per-tenant sessions/access tokens, write data, or route webhook effects to a specific merchant record will act on attacker-supplied content while believing it originated from the victim shop — breaking the shop-to-payload identity binding entirely.

### Impact Explanation
This is a cross-tenant confusion vulnerability: a low-privilege attacker (any user who can install the app on a shop they control, which is standard/unprivileged for public or unlisted Shopify apps) can cause an application built on this gem to process attacker-chosen webhook bodies under a victim shop's identity, without needing the victim's credentials, access token, or `client_secret`. Depending on how the host application keys off `data.shop` (e.g., for updating fulfillment/inventory/order records, or fetching the tenant's stored access token to act on their behalf), this can result in cross-tenant data corruption or triggering privileged actions against a victim shop.

### Likelihood Explanation
Likelihood is high for any app with more than one installed shop: it only requires (a) the app be installed on an attacker-controlled shop (trivial, unprivileged), (b) the attacker be able to trigger any webhook topic the app is registered for on their own store, and (c) the ability to POST an HTTP request with a custom header to the app's public webhook endpoint — all of which are within reach of an ordinary internet user/merchant, no secrets or elevated access required.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unauthenticated header:
- Reject/flag webhooks whose `shop` header does not match a shop the receiving application actually expects for that specific installed webhook subscription (e.g., cross-check against a per-shop webhook registration record or per-shop signing context) rather than validating solely against the global `api_secret_key`.
- If the library supports per-shop secrets/contexts, prefer validating with the specific shop's secret so a mismatched shop header cannot produce a valid signature.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for authorization decisions without additional verification (e.g., cross-referencing an installed-shop allowlist) before being passed to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (their own store).
2. Attacker triggers a webhook topic the app subscribes to (e.g., updates an order), causing Shopify to POST a signed webhook to the app's endpoint with headers including `x-shopify-hmac-sha256: <H>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
3. Attacker captures `B` and `H` (e.g. via a proxy they control, since it's their own webhook traffic).
4. Attacker sends a new HTTP request directly to the app's public webhook endpoint with the same body `B`, the same `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (body/HMAC pair is genuinely valid for the app secret), then invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body content, as shown in [5](#0-4) .
