Based on my research, I found a concrete analog: `Bonding._SEED_BUY_BYPASS_SLOT` is a single (non-keyed) transient-storage flag that is meant to authorize exactly one specific token's anti-snipe bypass, but it stores only a bare `address` value rather than being scoped per-token (e.g. via a `mapping(address => bool)` in transient storage, or hashed together with a caller/tx-scoped nonce). This mirrors the report's core defect class: a dedupe/authorization key that is not scoped across enough dimensions, so a second legitimate event in the same execution context silently collides with and suppresses the first.

### Title
Single-slot seed-buy bypass flag lets a second same-tx `Bonding.launch` overwrite and suppress the first token's anti-snipe seed buy - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.launch` arms a one-shot anti-snipe bypass by writing the newly-launched token's address into a **single** transient-storage slot, `_SEED_BUY_BYPASS_SLOT` [1](#0-0) . `Bonding.buy`'s `_enforceLaunchDelay` reads that one slot and requires the stored value to equal the token being bought, then clears it [2](#0-1) . Because the slot holds a single scalar rather than being keyed per-token (e.g. `mapping(address => bool)`), it cannot represent more than one pending bypass at a time within a transaction, or across multiple `launch()` calls that land before their matching seed buy consumes the slot.

### Finding Description
`launch()` sets the bypass unconditionally on every call:
```solidity
bytes32 slot = _SEED_BUY_BYPASS_SLOT;
assembly { tstore(slot, tokenAddr) }
``` [3](#0-2) 

`_enforceLaunchDelay` gates every `buy()` on that same single slot:
```solidity
bytes32 slot = _SEED_BUY_BYPASS_SLOT;
address bypass;
assembly { bypass := tload(slot) }
if (bypass != tokenAddress) revert TradingNotOpen();
assembly { tstore(slot, 0) }
``` [2](#0-1) 

The value is a bare address (a "dedupe key") rather than a mapping keyed by token address, meaning it has no dimension to distinguish between multiple tokens launched in the same transaction/call frame. `Bonding.launch` is only reachable by an allowlisted router (`Zap`) [4](#0-3) , and `Zap.createToken` currently calls `bonding.launch` then immediately `_buyInternal` in the same external call [5](#0-4) , so today the slot is always consumed before a second `launch()` can overwrite it. However, this correctness depends entirely on that specific call ordering being preserved inside `Zap`, not on any invariant enforced by `Bonding` itself. `Bonding.launch` has no reentrancy or same-tx-uniqueness guard against being invoked twice for different tokens before either's paired buy executes (its `nonReentrant` guard only prevents *recursive* re-entry into `launch`, not two sequential top-level calls in one tx) [4](#0-3) . Any future router upgrade, a batching/aggregator contract that calls `zap.createToken()` twice in one transaction, or any code path that interleaves `launch(A)`, `launch(B)`, `buy(A)`, `buy(B)` will have `launch(B)`'s `tstore` silently clobber `A`'s bypass token address before `buy(A)` runs — exactly the "dedupe key insufficiently scoped across dimensions → collision → legitimate event suppressed" failure mode from the report, translated to this on-chain single-slot authorization flag.

### Impact Explanation
When the collision occurs, the first token's legitimate creator seed buy is wrongly treated as a "second sniper buy" and reverts with `TradingNotOpen` [6](#0-5) . Since `Zap.createToken` performs `launch` then the mandatory seed buy atomically [7](#0-6) , a reverted seed buy reverts the entire `createToken` call, meaning the creator's launch itself fails/is suppressed rather than merely delayed — this is availability/DoS impact matching the CWE-440 (expected-behavior violation) class in the report, applied to the launch/anti-snipe subsystem instead of a messaging dedupe.

### Likelihood Explanation
Under the current, single, in-repo call path (`Zap.createToken` → `launch` → `_buyInternal` synchronously, with no other entry point calling `Bonding.launch` twice per tx) this is **not exploitable today** — I could not find any reachable unprivileged transaction that invokes `Bonding.launch` more than once before the matching buy consumes the slot. This is a latent/structural weakness in `Bonding`'s own gating design rather than a currently-triggerable bug: the safety property (`one bypass at a time`) is enforced only by `Zap`'s specific calling convention, not by `Bonding.launch`/`_enforceLaunchDelay` themselves. I cannot verify from the indexed contracts whether any additional router, multicall wrapper, or future `Zap` version exists that could reorder or batch these calls — the `Zap.sol` contents I retrieved show only single-launch flows.

### Recommendation
Scope the bypass by token instead of using a single scalar slot: replace `_SEED_BUY_BYPASS_SLOT`'s bare-address value with a transient `mapping(address => bool)`-style keyed slot (e.g., derive the slot as `keccak256(abi.encode(_SEED_BUY_BYPASS_SLOT, tokenAddr))`), so that multiple pending bypasses can coexist safely within one transaction and one token's bypass can never be overwritten by another token's `launch()` call.

### Proof of Concept
Given the current codebase, I could not identify a reachable single-transaction call sequence that invokes `Bonding.launch` for two different tokens before their respective seed buys land — `Zap.createToken` is the only production path to `launch`, and it interleaves `launch`+`buy` atomically per call [5](#0-4) . A concrete PoC would require either a future/alternate router contract or a batching wrapper around `Zap.createToken` that is not present in `packages/contracts/src` today. I flag this as a design weakness rather than a currently-exploitable, standalone finding — treat the recommendation as defense-in-depth hardening of the gating primitive itself rather than a confirmed live vulnerability.
