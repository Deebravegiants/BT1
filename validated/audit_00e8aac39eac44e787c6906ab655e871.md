### Title
Stale account owner lets a previous NFT holder retain privileged account control - (File: `contracts/controller/src/account.rs`)

### Summary

The controller treats the account NFT owner as the source of account ownership, but `borrow`, `withdraw`, and owner-or-delegate strategy paths authenticate against the `Account.owner` field captured when the account was created. A position NFT transfer changes NFT ownership without updating that stored controller-side field. Consequently, the seller retains the practical privileges of account ownership after transfer and can withdraw the buyer’s collateral or borrow against it to an attacker-selected recipient.

### Finding Description

At account creation, `create_account_with` stores `owner` directly in the in-memory `Account` while minting the NFT to that same address. [1](#0-0) 

Privileged account operations then call `require_owner_or_delegate`, whose first acceptance condition is simply `caller == owner`, where `owner` is the stale `account.owner` field loaded with the account. [2](#0-1) [3](#0-2) 

This differs from the account-owner-only paths, which call `storage::account_owner` and compare its result to the caller. [4](#0-3)  That distinction confirms NFT ownership is the current authority source, while `Account.owner` is only the creation-time cached owner.

`withdraw` is the strongest reachable path: it requires caller auth, loads the account, and calls `require_owner_or_delegate` against the stale owner. [5](#0-4)  It then honors the caller-supplied `to` recipient. [6](#0-5)  `borrow` has the same stale-owner gate and likewise routes proceeds to an attacker-selected `to`. [7](#0-6) 

The intended authorization model is explicit in the permissionless-entrypoint declaration: account spending authority must belong to the owner or an active listed delegate, and `borrow`, `withdraw`, and the strategy verbs rely on `require_owner_or_delegate` for that boundary. [8](#0-7) 

### Impact Explanation

A seller can wait for the NFT transfer to settle and then call `withdraw` or `borrow` on the sold account. Because `caller == account.owner` still succeeds for the seller, the contract treats the seller as authorized even though the buyer owns the position NFT. `withdraw(account_id, [(collateral_asset, 0)], to = seller)` drains the account’s collateral to the seller; alternatively, `borrow(..., to = seller)` extracts pool liquidity and leaves debt on the buyer’s account.

This is direct theft of user funds and can leave the protocol holding debt backed by an account whose collateral was removed. Delegate authority is also keyed to the stale owner, so grants made by the seller can continue to authenticate through the same path after the transfer.

### Likelihood Explanation

Exploitation requires only a normal, user-reachable sequence:

1. The victim buys or otherwise receives the account NFT.
2. The seller calls a supported controller entrypoint such as `withdraw` or `borrow`.
3. The seller supplies their own authorization and chooses `to = seller`.

No admin role, leaked key, oracle manipulation, bad parameter, third-party oracle failure, or route-quality assumption is needed. The NFT transfer is itself an explicitly in-scope entrypoint. Because every transfer leaves the controller’s stored owner unchanged, the failure is deterministic rather than timing-dependent.

### Recommendation

Derive spending authority from the current position-NFT owner, not the `Account.owner` snapshot. Replace the `caller == owner` fast path in `require_owner_or_delegate` with a check equivalent to `storage::account_owner(env, account_id) == *caller`, and resolve active delegate grants against that current NFT owner rather than the creator address.

Alternatively, keep the cached owner only as metadata and rename it to avoid treating it as an authorization root. Existing owner-or-delegate flows, liquidation `Credit` receivers, and strategy guards should all use the same current-owner resolution.

### Proof of Concept

1. Alice calls `supply(caller = Alice, account_id = 0, spoke_id = S, assets = [(USDC_key, 1_000e7)])`.
2. The controller creates account `A`, stores `Account.owner = Alice`, and mints NFT `A` to Alice.
3. Alice calls `position_nft.transfer(from = Alice, to = Bob, token_id = A)`. Bob becomes the current NFT/account owner.
4. Alice calls `controller.withdraw(caller = Alice, account_id = A, withdrawals = [(USDC_key, 0)], to = Some(Alice))`.
5. `Alice.require_auth()` succeeds; `require_owner_or_delegate` succeeds because `caller == account.owner`, even though `account.owner` is stale and Alice no longer owns NFT `A`.
6. The controller withdraws Alice’s requested collateral and transfers it to `to = Alice`.
7. The equivalent `borrow` path sends newly borrowed assets to `to = Alice`, while the debt remains on Bob’s account.

```rust
/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```

```rust
/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}
```
