### Title
Webhook `shop-domain` and `topic` are trusted for tenant routing but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the parsed body to the app's handler tagged with the `shop` and `topic` values taken from unauthenticated HTTP headers. Because those identity fields are never part of the signed bytes, any valid `(body, hmac)` pair — trivially obtainable by an attacker who owns/operates their own Shopify development store and installs the app — can be replayed with a forged `shop-domain`/`topic` header to make the receiving app process/store data under a victim tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` accessors are pulled straight from HTTP headers, independent of that signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only ever computes/compares the signature over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately trusts the unsigned `request.topic` and `request.shop` to route the payload and to stamp the `WebhookMetadata` handed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`bytes cryptographically verified (raw_body) == bytes the app attributes the request to (shop, topic)`

That equality does not hold here: the HMAC only proves "this body was produced with knowledge of `api_secret_key`" for *some* installed shop — it proves nothing about *which* shop or *which* topic the body should be attributed to. `shop` and `topic` are attacker-controlled bytes carried in plain HTTP headers alongside the signed body.

### Impact Explanation
Any unprivileged internet user can create a free/development Shopify store, install the target app on it, and receive one legitimately-signed webhook (any topic). That `(raw_body, hmac)` pair remains valid forever for that body, because the signature never binds shop or topic. The attacker can then send that exact body + hmac to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a victim shop. `HmacValidator.validate` passes (it only checks the body), and `Registry.process` calls the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and/or `WebhookMetadata#topic` set to an attacker-chosen topic. Any host application that uses `data.shop` to key per-tenant storage, trigger per-tenant side effects, or bypass additional shop verification (which is exactly the pattern this gem's own webhook docs recommend) will process attacker-supplied data under a different tenant's identity — i.e., cross-tenant data injection/corruption purely from the identity fields exposed by this gem's `Request`/`Registry` API, without ever touching the victim's access token or the app's `client_secret`.

### Likelihood Explanation
High from a mechanics standpoint (no secret needed beyond running the attacker's own store instance; the HMAC is well known to only cover the payload), but impact is entirely dependent on how the host app consumes `WebhookMetadata#shop`/`#topic` — this gem's API surface itself is exactly what an app is expected to trust for tenant/topic routing per its own documented contract, so the exposure is real for any consumer that follows the documented `Registry.process` → `WebhookHandler#handle` flow.

### Recommendation
- Do not treat `HmacValidator.validate` as full request authentication when `shop`/`topic` matter for routing; document (and/or enforce in the gem) that consumers must independently verify `WebhookMetadata#shop` against a known, previously-registered/installed shop for the session/token they hold before acting on the payload.
- Where feasible, have `Registry.process` require the caller to supply the expected shop (e.g., from the URL path or app's own routing) and assert it matches `request.shop`, rather than propagating an unauthenticated header value as trusted metadata.
- Consider surfacing a loud warning/flag in `WebhookMetadata` indicating `shop`/`topic` are not covered by the signature, to prevent silent trust by consumers.

### Proof of Concept
1. Attacker creates a Shopify development store `attacker-shop.myshopify.com` and installs the target app.
2. Shopify sends a legitimate webhook to the app, e.g.:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id":1,...attacker-controlled order payload...}
   ```
3. Attacker captures this exact `body` and `X-Shopify-Hmac-Sha256` value (this HMAC only signs `body`, per `lib/shopify_api/webhooks/request.rb#L35-38` and `lib/shopify_api/utils/hmac_validator.rb#L12-31`).
4. Attacker replays the same `body`/HMAC to the app's public webhook endpoint but sets:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` → passes (body unchanged), then invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)` (`lib/shopify_api/webhooks/registry.rb#L188-200`), causing the app to attribute attacker-controlled data to `victim-shop.myshopify.com`.
