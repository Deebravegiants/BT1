Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that string. The `shop` (and `topic`/`webhook_id`) values, however, are read straight from HTTP headers that are entirely outside the signed payload, then passed unverified into `WebhookMetadata` and handed to the app's `WebhookHandler`.

### Finding Description
The intended identity binding is: **the `shop` value the app acts on == the `shop` value Shopify cryptographically attested to when it signed the webhook**. In this gem that binding is broken.

- `Request#hmac` reads `shopify-hmac-sha256` header, and `Request#shop` reads `shopify-shop-domain` header [1](#0-0) .
- `to_signable_string` returns only the raw body — headers, including `shop`, are excluded from what is signed [2](#0-1) .
- `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — i.e., it only proves the *body* bytes are authentic, saying nothing about which shop the request claims to be from [3](#0-2) .
- `Registry.process` performs exactly this check and then forwards `request.shop` (the unauthenticated header) directly into `WebhookMetadata`, which the host app's handler trusts as the tenant identity for the event: [4](#0-3) .
- The gem's own documentation instructs apps to use `data.shop` as the shop identity for dispatching background jobs (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), confirming this field is treated as a trust boundary by design [5](#0-4) .

Because the signed quantity (body) and the trusted-identity quantity (`shop` header) are decoupled, any request whose body produces a valid HMAC under the app's secret — including a genuine webhook the attacker's own store received from Shopify — can be replayed with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to any other shop domain, and `Registry.process` will accept it as authentic for that victim shop. This is precisely the "field acted on but not covered by the HMAC" identity-binding break called out in scope.

### Impact Explanation
This enables cross-tenant data injection/confusion: an attacker who operates their own Shopify store (an unprivileged internet user relative to the target app) can obtain genuine, validly-HMAC'd webhook bodies from their own shop and resubmit them to the app's public webhook endpoint with a forged `shop-domain` header naming a victim shop. The app (per the gem's documented usage pattern) will process this as if it were an authentic event for the victim tenant — e.g., enqueuing background jobs, writing/overwriting per-shop records, or triggering mandatory-topic handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against the wrong tenant. This is a cross-tenant access impact against the identity-binding boundary this gem is responsible for enforcing.

### Likelihood Explanation
High feasibility for an attacker with the minimum bar assumed by these findings (an unprivileged internet user, no leaked credentials needed): they only need control of one legitimate Shopify store to generate genuinely-signed webhook bodies, then can freely swap the shop header before POSTing to the target app's public webhook route, since nothing in this gem re-derives or cross-checks `shop` against the signed content.

### Recommendation
Bind the shop identity into the verified material: either include the `shop-domain` header value as part of `to_signable_string` (matching how Shopify's own HMAC verification recommendation treats headers as part of context, if supported), or — more robustly — have `Registry.process`/`Request` reject/ignore requests where `shop` cannot be independently corroborated (e.g., by requiring the caller to supply the expected shop for the route being invoked, or validating `shop` against an active, registered session for that webhook subscription) rather than trusting the raw header value that sits outside the HMAC.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, registered for `orders/create` webhooks, pointing at the target app.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint: body `B`, `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker intercepts/replays this exact request but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and the HMAC header unchanged.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the unchanged signature — it passes [6](#0-5) .
5. `WebhookMetadata.new(..., shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the registered handler, which the host app's documented pattern uses to key per-tenant work [7](#0-6) .
