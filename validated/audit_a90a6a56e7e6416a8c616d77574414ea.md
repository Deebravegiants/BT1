### Title
Redeploying a registered `IntentGatewayV2` instance permanently strands escrowed funds tied to the old deployment address - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The Connext report describes an admin action (`removeRouter`) that erases an ownership mapping, causing a downstream authorization check (`getRouterOwner`) to fall through to a value that can never match the legitimate owner again, permanently freezing the owner's funds with no recovery path. The Intent Gateway v2 on Hyperbridge has the same structural flaw around its `_instances` registry: a routine, non-malicious governance action (registering/updating a remote gateway deployment) overwrites the address used to authenticate settlement messages, and any escrow still outstanding under the previous address becomes permanently unauthenticatable and irrecoverable.

### Finding Description
`IntentsBase._instance()` resolves the counterpart `IntentGatewayV2` address for a state machine and **reverts** if it's unset — there is no fallback to a "default"/self-referential address: [1](#0-0) 

`_authenticate` uses this resolved address to validate every incoming `RedeemEscrow`/`RefundEscrow` settlement message by comparing it against `request.from` (the sender contract on the source/destination chain): [2](#0-1) 

The `_instances` mapping is written exclusively by `NewDeployment` governance messages, dispatched only by Hyperbridge itself, and processed unconditionally in `onAccept`: [3](#0-2) 

Nothing preserves the previous mapping value when a new deployment is registered for the same `stateMachineId` — the write is a plain overwrite (see the analogous Tron variant, which shows the same pattern explicitly): [4](#0-3) 

Consequence: if a user places (escrows) an order whose counterpart gateway on the source/destination chain is address `G_old`, and before that order is settled/cancelled Hyperbridge governance issues a `NewDeployment` update pointing `_instances[chain]` at `G_new` (a legitimate migration/redeployment), then any subsequent `RedeemEscrow`/`RefundEscrow` message that legitimately originates from `G_old` (the address the order was actually placed against) will fail `_authenticate` forever, since `_instance(source)` now resolves to `G_new` and the comparison `_instance(request.source) != module` never succeeds for `module == G_old`. The escrowed input tokens (`_orders[commitment][token]`) held in `IntentsBase._withdraw`'s ledger are then permanently unreachable — there is no override path, no legacy-address fallback, and no way for the user or solver to re-authenticate the stale deployment.

This mirrors the Connext bug exactly: an admin/governance action (removing a router / redeploying a gateway) wipes/overwrites the identity mapping used purely for authorization, and the legitimate value holder (router owner / order placer or solver) has no way to satisfy the new authorization check, so their already-escrowed funds are stuck in the contract indefinitely.

### Impact Explanation
Any order still in flight (unfilled, unredeemed, or pending cancellation) at the moment a chain's registered gateway instance is updated has its settlement path permanently severed. This is a real freezing-of-funds condition reachable by an ordinary user/solver's already-submitted transaction (`placeOrder`/`fillOrder`) combined with a subsequent, entirely legitimate governance action — not exclusively a malicious-admin scenario, since gateway redeployments/migrations are an expected operational event (this is precisely the flow `NewDeployment` was built to support). The affected escrow becomes an unbacked, forever-locked balance in the contract, satisfying the "permanent freezing of funds" bar.

### Likelihood Explanation
Medium likelihood: `NewDeployment` requires Hyperbridge governance to dispatch the message, which is expected to be rare, but redeployments/migrations of `IntentGatewayV2` instances are a normal operational need (contract upgrades, chain migrations) rather than solely a compromised-admin event. Any order with escrow outstanding at the exact moment of a legitimate re-registration is affected with certainty (100% loss for that order), and the window is bounded only by how long orders can remain unsettled (up to `order.deadline`), which can be substantial.

### Recommendation
When processing `NewDeployment`, preserve the previous instance address for authentication purposes (e.g., maintain a set/history of previously-valid `(chain, address)` pairs, or version-stamp orders with the deployment address that was current at placement time and match against that snapshot on redemption) instead of doing a hard overwrite that immediately invalidates in-flight orders. At minimum, gate redeployments so they only take effect after all previously escrowed orders referencing the old instance have settled, or provide an explicit emergency-withdrawal path keyed off the order's original `source`/`destination` gateway address rather than the live `_instances` lookup.

### Proof of Concept
1. On chain A, user calls `placeOrder` on `IntentGatewayV2` instance `G_A`, escrowing input tokens; the order settles cross-chain against the registered `IntentGatewayV2` instance `G_B` on chain B (`_instances[keccak(B)] == G_B`).
2. Order is filled on chain B by a solver; `G_B` dispatches a `RedeemEscrow` post request back to chain A, `request.from = G_B`.
3. Before this message is relayed/delivered, Hyperbridge governance dispatches `NewDeployment{chain: B, gateway: G_B_new}` to the chain-A gateway, which is processed via `onAccept` → `_addDeployment`, overwriting `_instances[keccak(B)]` to `G_B_new`. [5](#0-4) 
4. The relayer now delivers the original `RedeemEscrow` message (`request.from = G_B`) to the chain-A gateway. `onAccept` calls `_authenticate`, which computes `_instance(B) == G_B_new != G_B`, reverting with `Unauthorized`. [6](#0-5) 
5. The solver can never re-submit an authenticatable redemption for this commitment (the old `G_B` contract cannot be un-deregistered/re-registered without also breaking newer orders), and the escrowed tokens in `_orders[commitment][token]` remain locked in the chain-A gateway permanently.

Note: I was not able to fully trace whether any compensating mechanism exists elsewhere (e.g., a manual sweep/recovery function) outside the files reviewed; the index does not show one in `IntentsBase.sol`/`ExtrinsicIntents.sol`/`IntrinsicIntents.sol`, but if such a path exists elsewhere in the full repo, it would mitigate this finding — a full Devin session with complete file access would be needed to rule this out definitively.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }
