### Title
Large RAY-valued markets can permanently overflow accrual and freeze user funds - (File: contracts/pool/src/cache/scale.rs)

### Summary
A sufficiently large market can grow its borrow index until unscaling aggregate debt exceeds the `i128` range and panics during mandatory interest accrual. Because every market mutation syncs before executing, the overflow permanently blocks withdrawals, repayments, liquidations, and subsequent index updates for that market. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Controller::supply` accepts a user-funded position and forwards measured receipts to the pool, while `Controller::borrow` permits an owner-controlled account to draw against sufficient collateral. [4](#0-3) [5](#0-4) [6](#0-5) 

Each pool operation calls `synced_market`, which invokes `interest::global_sync` before the requested mutation. [1](#0-0)  Accrual calls `accrue_step` with aggregate scaled borrow and supply state, and utilization/backing calculations unscale those aggregates through `scaled_to_original`, `mul_ceil`, or `mul_floor`. [7](#0-6) [8](#0-7) [9](#0-8) 

The RAY value ceiling is lower than the configured borrow-index ceiling for an extremely large book. At sustained high utilization, the index can grow enough that `scaled_amount * borrow_index` overflows `i128` before the index cap is reached, producing `MathOverflow`. [3](#0-2) 

The existing harness reproduces this by supplying one billion 18-decimal tokens, borrowing 98% of the pool, advancing time, and observing `update_indexes` fail with `MATH_OVERFLOW` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [10](#0-9) 

### Impact Explanation
This is a permanent freeze of all funds and debt operations in the affected `(hub_id, asset)` market. After the threshold is crossed, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot de-risk the book, and keepers cannot repair indexes because all those paths accrue before applying their operation. [1](#0-0) [11](#0-10) [12](#0-11) [13](#0-12) 

### Likelihood Explanation
A single unprivileged attacker can create two owned accounts, supply the vulnerable asset from one account, supply collateral from the other, and borrow most of the liquidity through `Controller::supply` followed by `Controller::borrow`. [4](#0-3)  The attacker then only needs the position to remain at high utilization while ordinary elapsed-time accrual advances the index; permissionless `update_indexes` can subsequently trigger the irreversible overflow state. [2](#0-1) [14](#0-13) 

The required capital is very large and depends on governance-configured market caps, decimals, and the selected interest-rate curve permitting the demonstrated utilization and book size. This makes exploitation economically expensive rather than impossible, supporting Medium severity because successful exploitation permanently freezes unrelated suppliers' assets. [15](#0-14) 

### Recommendation
Enforce a market-level scaled-value bound below `i128::MAX / maximum_reachable_index` at supply and borrow time, taking asset decimals and future index growth into account. Alternatively, clamp or safely handle accrual before index growth can make aggregate unscaling overflow, but do not merely cap the index at `MAX_BORROW_INDEX_RAY` because the demonstrated overflow occurs first. [8](#0-7) [16](#0-15) [17](#0-16) 

Add boundary tests for every decimals/curve combination proving that the configured caps keep the maximum possible RAY value below the checked-arithmetic limit. [18](#0-17) 

### Proof of Concept
The existing test demonstrates the full attack path:

1. Create an 18-decimal market using `xlm_curve` and a collateral market.
2. Attacker-owned account A calls `supply` with `1_000_000_000 * 10^18` units of the target asset.
3. Attacker-owned account B calls `supply` with sufficient collateral and calls `borrow` for 98% of the target-asset liquidity.
4. Advance ledger time one year at a time and call `update_indexes` for the target market.
5. Accrual eventually returns `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` calls on that market fail with the same `MathOverflow`, leaving supplier funds frozen. [19](#0-18)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);

pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );

pub(crate) fn backing_shortfall(cache: &Cache) -> i128 {
    let supplied_claim = cache.unscale_supply_floor(cache.supplied());
    let outstanding_debt = cache.unscale_borrow_ceil(cache.borrowed());
    let backing = cache.cash().saturating_add(outstanding_debt);
    supplied_claim.saturating_sub(backing).max(0)
}

    gate_and_debit(env, &mut cache, net_transfer, is_liquidation || empty_close);

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
