## Analysis Result



### Title
Meta-transaction (`DelegateAction`/NEP-366) signatures omit chain/fork-binding data, enabling cross-chain replay of signed delegated actions - (File: `core/primitives/src/action/delegate.rs`)

### Summary
`DelegateAction`, the payload an account signs to authorize a relayer-sponsored meta-transaction (NEP-366), is bound only by `nonce` (checked against the sender's on-chain access-key nonce) and `max_block_height` (an upper bound on block height). Unlike ordinary `SignedTransaction`s, it carries no `block_hash` or other chain-identity value. Since NEAR's own transaction-freshness/anti-fork mechanism is implemented entirely via `block_hash` binding (not via nonces), a `SignedDelegateAction` produced for one NEAR-protocol chain can be replayed, unmodified, against any other chain that shares the signer's account/access-key state (e.g. a state-forked or state-derived chain, as explicitly supported by nearcore's `tools/mirror`), as long as the access-key nonce there has not yet reached the delegate action's nonce and the current height is below `max_block_height`.

### Finding Description
`DelegateAction` is defined with only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`: [1](#0-0) 

Its signature covers only the NEP-461-tagged hash of this struct: [2](#0-1) 

Execution-time validation (`apply_delegate_action`) checks the signature, `max_block_height`, and that `sender_id` matches the tx receiver, then hands off to `validate_delegate_action_key`, which validates and advances the *access key's own* nonce state: [3](#0-2) [4](#0-3) 

None of this references a block hash or any chain-specific identifier. By contrast, ordinary NEAR transactions include a `block_hash` field specifically so the transaction can be tied to a particular chain/fork and expire against the `transaction_validity_period`: [5](#0-4) 

The RPC layer explicitly treats a stale/foreign `block_hash` as "expired or from a different fork": [6](#0-5) 

nearcore's own mirror tool documents that `block_hash` is exactly what defeats byte-for-byte transaction replay onto a forked target chain, requiring re-signing with a fresh `block_hash` before a transaction can be accepted elsewhere: [7](#0-6) 

Because `DelegateAction` was never given an equivalent field, a captured `SignedDelegateAction` (visible on-chain in the wrapping transaction/receipt once broadcast) can be re-wrapped by any relayer in a *fresh* outer `SignedTransaction` (with its own valid nonce/`block_hash` on the target chain) and submitted to a different NEAR-protocol chain that shares — or has not yet diverged past — the sender's access-key nonce state. The outer transaction's `block_hash` only binds the relayer's own submission; it does nothing to bind the inner, independently-signed `DelegateAction`.

### Impact Explanation
A relayer (or anyone who has observed a broadcast `SignedDelegateAction`) can replay a user's meta-transaction authorization on any other NEAR-protocol chain derived from or sharing state with the original chain (e.g., a state-forked chain created via `view-state dump-state`, a permissioned/private deployment sharing the same genesis records, or any nearcore-based network where the victim account was created with matching keys/nonce). This results in unauthorized execution of the delegated actions (e.g., `AddKey`, `Transfer`, `FunctionCall` with deposits) against the victim's account/funds on that other chain — an unauthorized state/balance change without any further action or consent from the account owner on that chain.

### Likelihood Explanation
Exploitation requires: (1) a `SignedDelegateAction` becoming known to an attacker (trivial once broadcast, since it's on-chain data or is submitted through a relayer that is not fully trusted by design in NEP-366's threat model), and (2) existence of a second NEAR-protocol chain sharing the signer's account and matching (not-yet-advanced) access-key nonce state. Condition (2) is a real, supported nearcore scenario (state-forked/mirrored chains) rather than a hypothetical one, but it does require specific deployment topologies (shared-genesis or forked chains), which limits likelihood to scenarios similar to the original Medium-severity finding it maps to — plausible but not universally applicable to a single production mainnet in isolation.

### Recommendation
Add a chain-binding field to the signed `DelegateAction` payload (e.g., a genesis hash / recent `block_hash`, analogous to `SignedTransaction`), and validate it against the executing chain at `apply_delegate_action` time, in addition to the existing nonce and `max_block_height` checks, so that a `SignedDelegateAction` cannot be replayed against any chain other than the one for which it was signed.

### Proof of Concept
1. On chain A, Alice signs a `DelegateAction{sender_id: alice, receiver_id: alice, actions: [AddKey(attacker_key)], nonce: N, max_block_height: H, public_key: alice_key}` and gives it to Relayer for sponsored submission, per the documented flow: [8](#0-7) .
2. Fork/mirror chain A into chain B before Alice's access-key nonce reaches N on chain B (nearcore's own `tools/mirror` supports and documents exactly this workflow: [9](#0-8) ).
3. On chain B, wrap the *same, unmodified* `SignedDelegateAction` bytes in a brand-new outer `SignedTransaction` (fresh nonce/`block_hash` valid on chain B) and submit it.
4. `apply_delegate_action` on chain B only checks the inner signature, `max_block_height`, `sender_id`, and the access key nonce on chain B — all of which pass — executing `AddKey(attacker_key)` on Alice's chain-B account without her consent, since nothing in the verified data distinguishes chain B from chain A.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

is used to make sure a transaction does not get lost (let's say
