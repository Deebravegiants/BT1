### Title
Missing key validation in `IconsStorage#storeIcon`/`#deleteIcon` allows attacker-controlled custom-token `name` to overwrite another asset's stored icon - ([File: adapters/storage-icons-browser/src/icons-storage.js])

### Summary
Unlike the mobile adapter, `adapters/storage-icons-browser/src/icons-storage.js`'s `#storeIcon`/`#deleteIcon` write to icon storage using `token.name || token.assetName` as the key with no format or uniqueness validation. In several call paths of the shared `AssetsModule`, this key is taken directly from an untrusted custom-token-registry ("CTR") response and passed to storage without first checking whether it collides with an existing asset's name, allowing a malicious/compromised CTR response to overwrite the icon of an unrelated, already-registered asset (e.g. `bitcoin`).

### Finding Description
`adapters/storage-icons-browser/src/icons-storage.js` computes the storage key purely from attacker-influenced token data: [1](#0-0) 
There is no regex/format check comparable to the mobile adapter's `#getPath`, which asserts `iconNameRegex.test(assetName)` before touching the filesystem: [2](#0-1) 

More importantly, several `AssetsModule` code paths call `#storeIcons` directly on tokens fetched/validated from the remote custom-token server, *without* first checking whether `token.name` already collides with an existing registered asset:
- `fetchToken` normalizes and stores icons for a single fetched token with no name-collision check: [3](#0-2) 
- `#fetchTokens`/`fetchTokens` validate schema, normalize, then call `#storeIcons(tokens)` before any registry-collision handling occurs: [4](#0-3) 
- `#fetchUpdates` (used by `updateTokens`) also calls `#storeIcons(validatedTokens)` with no collision check: [5](#0-4) 

By contrast, `addRemoteTokens`/`addToken` route tokens through `#handleFetchedToken`, which explicitly checks `this.getAsset(token.name)` and only pushes genuinely *new* tokens (`isAdded === true`) into `fetchedAndHandledTokens`, the list actually passed to `#storeIcons`: [6](#0-5) ; [7](#0-6) . This dedup/collision guard is absent from `fetchToken`, `fetchTokens`, and `updateTokens`.

`validateCustomToken`/schema validation (when `shouldValidateCustomToken` is enabled, the default) constrains `name` to match the `assetName.pattern` regex — the same pattern the mobile adapter reuses for its `iconNameRegex` — so arbitrary characters like `../` or `__proto__` are rejected by schema validation before reaching storage. However, schema validation only enforces *format*, not *uniqueness against the existing asset registry*. Because the underlying icon storage (a namespaced `Map`/key-value store, e.g. `adapters/storage-memory/src/index.js` or `libraries/browser-extension-adapters/unsafe-storage/storage.js`) is keyed by plain string equality, a valid-format name equal to an existing built-in or already-added custom asset's name (e.g. `"bitcoin"`) is sufficient to overwrite that asset's icon entry when reached via the unguarded paths above.

Note: the prototype-pollution variant of this concern (`__proto__` as key) is not exploitable here — the underlying stores are `Map`-based or single-level key/value writes, not deep-merge object assignments, so setting a key literally named `__proto__` does not pollute `Object.prototype` across the process.

### Impact Explanation
A malicious or compromised custom-token-registry response (reachable via `fetchToken`, `fetchTokens`, or the periodic `updateTokens` flow, all of which are "remote config or API response" ingestion paths) can silently replace the cached icon of an unrelated, legitimate asset (including built-in assets like `bitcoin`) with attacker-controlled SVG content. This is a UI-spoofing / asset-icon-poisoning primitive: the icon rendered for a trusted asset in the wallet UI can be swapped without user consent, which can be used to mislead users (e.g., masquerading one asset's icon as another to facilitate confusion during a transfer/swap). SVG content is passed through `cleanupSVG`/`validate` (`@exodus/svg-safe`), so this does not appear to grant script execution, limiting impact to visual-integrity compromise rather than direct fund theft or key disclosure.

### Likelihood Explanation
The precondition is that the attacker controls (or can MITM/compromise) the custom-token-registry server response consumed by `fetchToken`/`fetchTokens`/`updateTokens`, or otherwise achieves an equivalent trusted-looking token metadata payload flowing through those methods. Given `shouldValidateCustomToken` defaults to true, the attacker must still produce a `name` value that passes the `assetName.pattern` schema check but exactly matches an existing asset's name string — trivially satisfiable by simply reusing `"bitcoin"`, `"ethereum"`, etc. No user interaction, privileged wallet state, or leaked secrets are required beyond the assumed CTR response control.

### Recommendation
Add the same collision/existing-asset check used in `addRemoteTokens`/`addToken` (`#handleFetchedToken`) to `fetchToken`, `#fetchTokens`, and `#fetchUpdates` before calling `#storeIcons`, so icons are only stored for tokens whose name does not already resolve to an existing asset. Additionally, harden `adapters/storage-icons-browser/src/icons-storage.js#storeIcon/#deleteIcon` to validate `assetName` against the same `iconNameRegex`/`assetName.pattern` used by the mobile adapter, so the browser adapter does not rely solely on caller-side schema validation.

### Proof of Concept
Unit test plan (Jest) for `features/assets-feature/module/assets-module.js`:
1. Configure `assetsModule` with `shouldValidateCustomToken: true` and a spy `iconsStorage.storeIcons`.
2. Mock `fetch` so that `fetchToken('some-asset-id', 'ethereum')` (or `fetchTokens`) returns a token with `name: 'bitcoin'` (an existing built-in asset name) and a benign `icon` payload, passing schema validation.
3. Call `await assetsModule.fetchToken('some-asset-id', 'ethereum')`.
4. Assert that `iconsStorage.storeIcons` was called with a token named `'bitcoin'`, and that afterward `assetsModule.getIcon('bitcoin')` returns the attacker-supplied icon instead of the original bitcoin icon — demonstrating the overwrite, expected to fail once the collision guard from `#handleFetchedToken` is applied to this path (i.e., `storeIcons` should not be invoked for a colliding name).
5. Repeat for `updateTokens`/`#fetchUpdates` with a crafted `assetVersions` response containing `name: 'ethereum'`.

  #handleFetchedToken = (token) => {
    const asset = this.getAsset(token.name)
    if (asset) return { asset, isAdded: false, updates: [] }

    const { name } = this.#registry.addCustomToken(token) // add to registry
    const updates = this.#handleCombinedParents(token)

    this.#logger.log('Custom token added:', name)
    return { asset: this.getAsset(name), isAdded: true, updates }
  }

  #handleFetchedTokens = (tokens) => {
    const fetchedAndHandledTokens = []
    const added = []
    const updated = []
    const parentNames = []
    for (const token of tokens) {
      try {
        const { asset, isAdded, updates } = this.#handleFetchedToken(token)

        if (isAdded) {
          added.push(asset)
          fetchedAndHandledTokens.push(token)
        } else {
          updated.push(asset)
        }

        if (updates.length > 0) {
          parentNames.push(...updates)
        }
      } catch (err) {
        this.#logger.error('Handle fetched custom tokens error: ' + err.message, err)
      }
    }

    updated.push(...uniq(parentNames).map(this.getAsset))

    return { fetchedAndHandledTokens, added, updated }
  }
