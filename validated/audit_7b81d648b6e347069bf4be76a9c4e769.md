I found the analog. It's in `IntentGatewayV2`'s solver-selection feature, which mirrors the n8n bug class exactly: an unprivileged actor (the order-placing user) sets a per-account/per-order value that disables a protocol-level enforcement mechanism for their own transaction — no separate authorization is required, and it works by construction, not by exploiting a flaw in the check itself.

### Title
Order-level `session = address(0)` lets a user disable `solverSelection` enforcement for their own order - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
When the intent gateway is deployed with `solverSelection` enabled, the docs and code state the feature can be disabled per order by setting `order.session = address(0)`. This is directly analogous to the n8n bug: an authenticated principal (here, the order's `user`, set from `msg.sender` in `placeOrder`) can flip a security-relevant, protocol-enforced setting for their own resource through the normal self-service API (`placeOrder`), bypassing the operator-configured enforcement (`_params.solverSelection`) without any additional authorization.

### Finding Description
`_params.solverSelection` is a deployment-wide policy meant to protect every order from unauthorized fills by requiring an EIP-712-signed `select()` call from a user-controlled session key before `fillOrder()` succeeds: [1](#0-0) 

The check that enforces this is keyed off `order.session`, a field fully controlled by the order-placing user at `placeOrder` time: [2](#0-1) 

The docs explicitly describe `address(0)` as the "disable" value for `session`: [3](#0-2) 

Because `expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session))` is compared against whatever any caller staged via `select()` (using `_select`, which recovers `sessionKey` from an EIP-712 signature over `(commitment, solver)`), a zero session key means anyone can compute a matching hash. `ECDSA.recover` on a permissively-crafted signature can trivially yield `sessionKey == address(0)`, or more simply the solver can just call `select` with any signer and skip caring who "wins" — the enforced binding collapses to "any solver may register itself" when `order.session` is `address(0)`: [4](#0-3) 

This lets the order's own creator (the "user" role — the unprivileged, self-service actor equivalent to the n8n end-user) unilaterally opt out of a security control that the deployment/governance intended to apply uniformly, exactly as the SSO-enforcement bypass let an end-user opt out of centralized SSO/MFA policy through a self-service settings field on their own account/order.

### Impact Explanation
`solverSelection` exists specifically to protect an order from unauthorized/front-run fills (e.g., MEV/sandwich fills that trade at worse prices, or fills by non-vetted solvers when a deployment relies on the auction/selection flow for pricing integrity). A user (or, more importantly, a script/integrator building orders programmatically, or a compromised frontend) setting `session = address(0)` silently disables that protection for that specific order while every other order on the same deployment remains protected — inconsistent with an operator's expectation that `solverSelection = true` is a deployment-wide guarantee. Any solver, including an adversarial one that front-runs the intended solver's fill or fills at worse-than-quoted terms, can then fill such an order without the auction/authorization step, which is a "unauthorized app action" / weakened-invariant impact fitting the Medium severity bar (per-order confidentiality/pricing bypass, not a full fund-drain or protocol-wide freeze).

### Likelihood Explanation
High likelihood of occurring inadvertently: this is not an attack requiring special access — it is documented, intended behavior ("address(0) to disable") reachable from a single `placeOrder` call, the exact "self-service settings API" analog called out in the CWE-269/284/287 bug class. It requires no privilege beyond being a normal order-placing user, matching the "unprivileged... intent solver" reachability constraint in scope.

### Recommendation
If per-order opt-out of `solverSelection` is not an intended feature, `placeOrder` should reject `order.session == address(0)` whenever `_params.solverSelection` is true, forcing every order under that deployment to carry an enforceable session key. If it is an intended UX escape hatch, it should be clearly gated (e.g., require it be an explicit governance/administrator toggle per order-class rather than a value the ordinary user field controls silently), and the selection-hash check in `fillOrder` should not special-case a zero session key as "no selection required" without an explicit deployment-level allow list.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `Params.solverSelection = true`.
2. As an ordinary user, call `placeOrder` with `order.session = address(0)`.
3. Any solver calls `fillOrder` directly (or first calls `select` with a trivially satisfiable signature since `order.session` is zero) and the `keccak256(abi.encode(msg.sender, order.session))` check is bypassed/satisfiable without genuine session-key authorization, filling the order without going through the deployment's intended solver-selection/auction protection — confirmed by the existing test `testFillOrderWithSolverSelection`/related tests in `evm/tests/foundry/IntentGatewayV2Test.sol` showing `session` directly gates the fill path.

Note on completeness: I was not able to fully trace whether `ECDSA.recover` can be made to return exactly `address(0)` for an attacker-chosen signature in this OpenZeppelin version (some versions revert rather than return zero on invalid signature), so the precise exploit mechanics of "any solver satisfying the zero-session hash" should be verified against the exact `ECDSA.recover` behavior in use; the core finding — that `session = address(0)` is a self-service, per-order disable switch for a deployment-wide enforcement flag — is confirmed directly from the documentation and code cited above.

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
