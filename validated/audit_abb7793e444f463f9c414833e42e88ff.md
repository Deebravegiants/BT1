### Title
`Registry.process` trusts the `shop`, `topic`, and `webhook_id` headers of a webhook request without covering them under the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`, but `Webhooks::Request#to_signable_string` returns only `@raw_body` — none of the identifying headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) are covered by that signature. The gem's own docs promise that `process` "will verify the request did indeed come from Shopify" and then hands the handler a `WebhookMetadata` object whose `shop`, `topic`, and `webhook_id` are taken straight from these unsigned headers.

### Finding Description
`HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For `Webhooks::Request`, `hmac` is read from the `hmac-sha256` header and `to_signable_string` returns just the raw body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from separate HTTP headers that are not part of the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches to the handler using the unsigned `request.topic` and `request.shop`: [4](#0-3) 

Effect: the equality the gem is supposed to guarantee is `shop_that_receives_the_event == shop_that_produced_the_signed_body`. What it actually guarantees is only `hmac(body) == hmac(body)`; `shop`, `topic`, and `webhook_id` are never bound to that signature. Anyone who legitimately installs the app on their own store (an unprivileged action requiring no secret) receives real, validly-signed webhook deliveries for that store. They can capture one such request and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header swapped to point at a different, victim shop, while keeping the original body and HMAC untouched — the HMAC still validates because it only ever covered the body. The handler then executes attacker-supplied JSON `body` content under a victim shop's identity (`WebhookMetadata#shop`), e.g. triggering `app/uninstalled` logic, order/fulfillment processing, or any shop-scoped side effect keyed off `data.shop`, for a shop the attacker does not control.

### Impact Explanation
This breaks the tenant/identity binding the gem's `process` method is documented to enforce ("will verify the request did indeed come from Shopify"), letting an attacker who merely installed the app on any shop of their own inject webhook events that are processed as if they originated from an arbitrary victim shop. Depending on the handler's use of `data.shop`/`data.topic`/`data.body`, this can result in cross-tenant state corruption (e.g. spoofed `app/uninstalled` deactivating a victim's integration, or spoofed order/customer events being applied to the victim's shop record) — a cross-tenant access/confusion condition.

### Likelihood Explanation
Requires only becoming a legitimate merchant/installer of the target app (trivial, unprivileged, and requires no access to `api_secret_key`, tokens, or the victim's data) to obtain one validly signed webhook body/HMAC pair, plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both are within reach of any internet user and do not depend on the host app deviating from the documented API (the vulnerable header handling and un-scoped HMAC coverage are internal to `Webhooks::Request`/`Registry.process`).

### Recommendation
Bind the shop/topic/webhook identity to the authenticated request instead of trusting raw headers post-HMAC-check: e.g. include `shop-domain`, `topic`, and `webhook-id` in the signable string used for HMAC verification (mirroring how `Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signature), or cross-check the header-derived `shop` against a shop known/expected by the app (e.g. an active session/installation record) before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `app/uninstalled` or `orders/create`).
2. Shopify delivers a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{}` (or attacker-controlled JSON, since attacker controls their own store's data that triggers the webhook body content)
3. Attacker captures this request and replays it to the same endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic` to a more sensitive topic if the body shape matches), leaving `x-shopify-hmac-sha256` and the body untouched.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — it matches, since the body was not altered: [4](#0-3) 
5. The handler executes with `WebhookMetadata#shop == "victim.myshopify.com"`, processing attacker-supplied data as if Shopify itself reported this event for the victim's shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
