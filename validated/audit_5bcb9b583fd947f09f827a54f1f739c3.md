### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header values are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using header-derived fields (`shop`, `topic`, `api_version`, `webhook_id`) that are never included in the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then unconditionally trusts `request.shop`/`request.topic` to route and label the payload delivered to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature only against `verifiable_query.to_signable_string`, i.e. the body bytes, with the app's `client_secret`: [4](#0-3) 

Because Shopify signs webhooks with the single app-level `client_secret` — the same secret is used for every shop that installs the app — a valid `(raw_body, hmac)` pair obtained from *any* shop's own webhook delivery (including a shop the attacker legitimately controls/installs the app on) remains HMAC-valid. `Registry.process` uses this fact and then binds the accepted payload to whatever `X-Shopify-Shop-Domain` header the caller chooses to attach, since that header is never part of the signed bytes. This breaks the identity binding: `verified(hmac) == raw_body` but the application then trusts `shop == attacker-controlled header`, which is disjoint from what was actually authenticated.

An unprivileged internet user who is a legitimate merchant of Shop A (able to install the target app on their own store and thus receive genuinely-signed webhook deliveries) can capture a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair for Shop A, then replay that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: shop-b.myshopify.com`. `Utils::HmacValidator.validate` still returns `true` (it never inspects the shop header), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop A's data>, topic: <attacker-chosen>, ...)`.

### Impact Explanation
This is a cross-tenant binding break in a security-relevant path: any host application that keys per-tenant behavior (e.g., data deletion in `customers/redact`/`shop/redact` handling, cache invalidation, billing state, webhook-driven authorization decisions) off `WebhookMetadata#shop` or `#topic` can be made to act on/for the wrong tenant using data and topic labels chosen by the attacker, while still passing this gem's own signature check. This matches the "Critical – cross-tenant access" and "High – scope/expiry check bypass"-style impact categories, since the gem's webhook authentication primitive silently permits attacker control of the tenant identifier and event type despite a "verified" HMAC.

### Likelihood Explanation
Requires only the ability to install the target app on an attacker-owned shop (a normal, unprivileged merchant action) to obtain a validly-signed body/HMAC pair, plus the ability to send an HTTP request with attacker-chosen headers to the app's public webhook endpoint — both trivially available to an unprivileged internet user, no `api_secret_key` or leaked credentials required.

### Recommendation
Include the tenant-identifying and event-identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material used by `to_signable_string`, or otherwise cryptographically bind them (e.g., re-derive/verify `shop` server-side against the session/registration rather than trusting the header), so that `Utils::HmacValidator.validate` fails whenever any of these fields is altered from what was actually signed by Shopify.

### Proof of Concept
1. Install the target app on attacker-controlled `shop-a.myshopify.com`; trigger any webhook topic to capture a legitimate `raw_body` and its `X-Shopify-Hmac-Sha256` value from Shopify's genuine delivery.
2. POST that identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim shop) and/or a different `X-Shopify-Topic`.
3. `Webhooks::Request` parses these headers per [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because only `raw_body` is checked, then invokes the handler with `shop: request.shop` set to the forged value [6](#0-5) .
4. The app's handler processes attacker-supplied `shop-a` data as if it belonged to `shop-b`, demonstrating the cross-tenant confusion enabled by the unauthenticated `shop`/`topic` headers.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
