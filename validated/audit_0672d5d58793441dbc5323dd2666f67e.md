This confirms the vulnerability. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then trusts `request.shop` to build the `WebhookMetadata` handed to the app's webhook handler [3](#0-2) . ### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body [1](#0-0) , but the `shop` field consumed by `Registry.process` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the signed payload [4](#0-3) . `Utils::HmacValidator.validate` only checks that the body's HMAC matches the app's shared `client_secret` [5](#0-4) ; it never binds that signature to the specific shop the request claims to be from.

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook by Registry.process` == `shop whose secret actually produced the HMAC`. In this gem, the HMAC secret (`Context.api_secret_key`) is a single, app-wide value shared across every merchant install, not a per-shop secret [6](#0-5) . The signable string is `@raw_body` only [1](#0-0) , so the `shopify-shop-domain` header is unauthenticated data that is trusted verbatim by `Registry.process` to construct `WebhookMetadata` passed to the app's handler [3](#0-2) .

Any unprivileged user can install the target app on their own Shopify store (a normal, unprivileged action), trigger an event that causes Shopify to send them a legitimately HMAC-signed webhook, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. Because the header is not part of `to_signable_string`, `Utils::HmacValidator.validate` still returns true, and the forged shop identity flows straight into the app's business logic via `WebhookMetadata.shop`.

### Impact Explanation
This breaks the tenant boundary the webhook system is meant to enforce: an attacker-controlled body (their own shop's order/customer/product data, subject line, etc.) can be attributed to a victim shop inside the host application. Depending on how the app's webhook handlers use `data.shop` (e.g., updating per-shop records, triggering shop-scoped side effects, or writing to a datastore keyed by shop), this enables cross-tenant data injection/corruption — classified as High per the cross-tenant impact criteria.

### Likelihood Explanation
Likelihood is high: no privileged credentials, access tokens, or `client_secret` are required. Any user can freely install a public app to obtain a validly-signed sample webhook and then relay it with a forged header to the same app's endpoint.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers an event (e.g., updates a product) so Shopify sends a webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and HMAC value.
3. Attacker POSTs the same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`raw_body` only) and succeeds, since the body/HMAC pair is genuinely valid for the shared secret [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` [8](#0-7) , causing the app to process attacker-controlled data as if it originated from the victim shop.
