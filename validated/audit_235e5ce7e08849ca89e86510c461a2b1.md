### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the shop identity (`request.shop`, sourced from the `X-Shopify-Shop-Domain` header) is never included in that signature and is passed straight through to the app's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload [2](#0-1) . `Registry.process` validates the HMAC and then hands `request.shop` directly to the handler as the authoritative tenant identity, without verifying that this header value is bound to the HMAC-signed bytes: [3](#0-2) 

The broken identity binding is:
`shop-domain header value` ≠ `shop field inside the HMAC-covered body`

Because only the body is signed, the `shop-domain` header can be swapped for any other tenant's shop domain on a webhook delivery whose body+HMAC pair the attacker already possesses (e.g., a webhook legitimately delivered to their own shop's endpoint, or one captured via a shared/misconfigured proxy), and the HMAC check in `HmacValidator.validate` will still succeed since it only compares against `@raw_body` [4](#0-3) .

### Impact Explanation
If a host app uses `request.shop` / `WebhookMetadata#shop` from `Registry.process` to select which tenant's data to update (a documented, expected usage pattern of this gem's webhook processing API), an attacker who can influence or replay the `shop-domain` header on an otherwise-HMAC-valid webhook delivery can cause the app to attribute webhook data to an arbitrary victim shop, resulting in cross-tenant data corruption/access — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires the attacker to control or replay a body+HMAC pair for some shop (trivially available to any merchant that installs the app on their own store, since the app forwards its own webhooks to them) and then modify only the header before it reaches the app's endpoint. This is plausible in any deployment topology where headers pass through infrastructure the attacker partially controls (custom reverse proxies, shared webhook relay endpoints, queue-based delivery to `pub_sub`/`event_bridge` handlers where headers/attributes are attacker-adjacent). Likelihood is moderate — it depends on the host app's exposure and on it trusting `request.shop` without independent verification, which the gem's own API encourages by exposing `shop` as a header-derived, unauthenticated field.

### Recommendation
Bind the shop identity to the HMAC-verified payload instead of trusting a separate, unsigned header:
- Extract `shop` from the signed body payload (most Shopify webhook payloads or an accompanying signed claim) rather than solely from the `X-Shopify-Shop-Domain` header, or
- Include the `shop-domain` header value in the string used for HMAC computation (`to_signable_string`) so tampering invalidates the signature, or
- Have `Registry.process` cross-check `request.shop` against a shop value independently known to the app (e.g., via a stored, per-webhook-subscription callback address/topic mapping) before invoking the handler.

### Proof of Concept
1. App has a webhook registered; Shopify delivers a webhook to the app for `victim-shop.myshopify.com` with raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`), plus header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
2. An attacker who also has the app installed on `attacker-shop.myshopify.com` receives their own legitimate webhook, body `B'`, valid signature `H'`.
3. Because `to_signable_string` only returns the raw body [1](#0-0) , the attacker can replay body `B'`/`H'` to the app's webhook endpoint while modifying the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B'` against `H'` [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop [6](#0-5) , causing the app to process attacker-controlled data under the victim tenant's identity.
