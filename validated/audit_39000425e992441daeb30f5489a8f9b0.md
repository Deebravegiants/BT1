### Title
Unfunded `recapitalize` refund lets any caller drain pool custody by claiming a refund for tokens never paid in — (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` entrypoint computes `refund = amount - applied` and transfers it to `payer` via `transfer_out`, but it never measures or verifies that `amount` was actually transferred into the pool. Like the Derby `unlockTokensFromBasket` flaw (a payout computed from caller input without validating it against what the contract actually received/held for that caller), the pool pays out based on a declared `amount` the caller never had to fund. Any unprivileged address can call `recapitalize` with a large `amount`, receive the "refund" in real tokens, and leave the cash book claiming the funds still exist.

### Finding Description
`accounting` in `contracts/pool/src/ops/recapitalize.rs` computes `applied = min(amount, backing_shortfall)` and `refund = amount - applied`, credits only `applied` to the cash book, and `apply` then calls `outcome.cache.transfer_out(&payer, outcome.refund)`. There is no `transfer_amount_measured` call, no pre/post balance check, and no auth-bound proof that `amount` arrived — the code only assumes "the controller transfers `amount` into the pool before this call" (per the doc comment). The pool entrypoint is reachable directly, so an attacker skips the funding step entirely and receives a refund for money never deposited. The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) demonstrates exactly this: a single `recapitalize` call with `amount = custody` drains the pool's token balance to zero while the `cash` book still reports the suppliers' funds, so subsequent `withdraw` reverts inside the SAC transfer with `BalanceError`, not against any pool guard.

### Impact Explanation
Theft of user funds / insolvency. Every token in the pool's custody can be refunded to an attacker who paid nothing, after which legitimate suppliers' withdrawals clear the pool's own `require_reserves`/solvency checks (the book still shows cash) and then fail at the token layer — the market reports solvency while unable to pay.

### Likelihood Explanation
High. `recapitalize` is a permissionless pool entrypoint; the attack requires one call with `amount` set to the pool's live balance, no capital, and works whenever `backing_shortfall < amount` (including zero shortfall, which refunds the full `amount`).

### Recommendation
Measure the inbound payment like other legs do: record the pool's token balance before crediting and require `post - pre >= amount` (via `common::token::transfer_amount_measured` or equivalent custody delta), or debit the refund from the cash book so an unfunded refund cannot be paid out of supplier-backed custody. At minimum, cap `refund` by the measured inbound amount rather than the declared `amount`.

### Proof of Concept
```rust
// Pool holds `custody` tokens backing supplier deposits.
let custody = token.balance(&pool);
// Attacker calls recapitalize directly, transferring nothing in.
pool_client.recapitalize(&hub_asset, &attacker, &custody);
// applied = min(custody, shortfall); refund = custody - applied is sent
// to attacker. With zero shortfall the full custody is refunded.
assert_eq!(token.balance(&pool), 0);
// cash book still >= deposits; supplier withdraw reverts with SAC
// BalanceError (10), not CollateralError::InsufficientLiquidity.
// See contracts/pool/tests/flows.rs:3408-3483.
```

Note: whether the pool contract's `recapitalize` wrapper adds `require_auth` on `payer` could not be fully verified in the remaining iterations, but `payer` is attacker-controlled so auth on it would not prevent the attack.
