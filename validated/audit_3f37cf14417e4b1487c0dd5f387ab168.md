## Analysis Result

### Title
Unvalidated JWT `dest` Claim Used as HTTP Request Host in Token Exchange, Bypassing Trusted-Domain Check - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the shop host directly from the unvalidated `dest` claim of the session JWT and uses it to build the HTTP request that carries the app's `client_id`/`client_secret` to the OAuth token endpoint, unlike every sibling credential-issuing method in the same module/gem which explicitly runs the value through `Utils::ShopValidator.sanitize!` before trusting it as a host.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#shop` returns the `dest` claim with only `"https://"` stripped off — it is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [1](#0-0) 

`TokenExchange.exchange_token` takes this unvalidated value (`dest_shop = jwt_payload.shop`) and uses it directly to construct `shop_session`, which `Clients::HttpClient` turns into the request host (`@base_uri = "https://#{session.shop}"`): [2](#0-1) [3](#0-2) 

This is inconsistent with every other credential-issuing method in the same file and module, which sanitize the shop value first:
- `TokenExchange.migrate_to_expiring_token` calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host. [4](#0-3) 
- `ClientCredentials.client_credentials` also calls `Utils::ShopValidator.sanitize!(shop)`. [5](#0-4) 

`ShopValidator` exists specifically to prevent an attacker-controlled/non-`myshopify` host from being trusted as the request destination: [6](#0-5) 

The identity binding that should hold is: **host used to send `client_id`/`client_secret` == a Shopify-trusted domain**. In `exchange_token`, that binding is instead: **host used to send credentials == raw `dest` claim from the JWT**, with no trusted-domain equality check enforced.

### Impact Explanation
This maps to the report's bug class ("host validated versus the host that receives the access token or `client_secret`"). If `dest` is not itself independently constrained to a `myshopify.com`/trusted domain elsewhere in the calling application's flow, this path sends the app's `client_id` and `client_secret` (in the POST body) to a host derived from that claim rather than a verified Shopify domain — an SSRF-with-credentials pattern (the impact category explicitly listed as High: "SSRF with the app's credentials"). Note the JWT signature itself is still verified against `api_secret_key`/`old_api_secret_key` in `JwtPayload#initialize`, so a fully valid token is required; the exposure is that no additional trusted-domain check is performed on `dest` before it is trusted as a network destination, unlike the parallel, sanitized code paths in the same module.

### Likelihood Explanation
Medium: exploitation requires a session token that decodes/verifies successfully (bound to the app's `api_secret_key`) but whose `dest` claim is not a genuine `myshopify.com` domain. The library's own `JwtPayload` code enforces `aud == Context.api_key` but performs no equivalent check on `dest`/`iss` format beyond the `admin_session_token?` suffix check used only for `shopify_user_id`. The report's underlying pattern — a security invariant implemented in one code path (`ShopValidator.sanitize!` in `client_credentials.rb` and `migrate_to_expiring_token`) but silently dropped in a structurally identical path (`exchange_token`) — is a maintenance/consistency defect exactly analogous to the TickMath overflow assumption being dropped when the code was "adjusted" for a new context.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session`/making the request, mirroring `migrate_to_expiring_token` and `ClientCredentials.client_credentials`, so the same trusted-domain invariant is enforced on every path that sends the app's `client_id`/`client_secret` to a shop-derived host.

### Proof of Concept
Not independently confirmable from the indexed library code alone: it depends on whether `dest` can take a non-`myshopify` value while still passing JWT signature verification in a real deployment (e.g., via a token issued for a `spin.dev`/custom domain flow, or any environment where the signing secret is reused/misconfigured). Within this codebase, the structural gap is concrete and verifiable: `exchange_token` is the only credential-issuing method in `lib/shopify_api/auth/*` that skips `Utils::ShopValidator.sanitize!` on the shop value before using it as the request host. [7](#0-6)

            )

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
