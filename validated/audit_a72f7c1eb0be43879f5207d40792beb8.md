### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . However, the `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the application's handler are read directly from HTTP headers that are excluded from the signed payload [2](#0-1) . The equality the gem is supposed to enforce — "the shop attributed to this webhook == the shop Shopify actually signed for" — is broken because `to_signable_string` returns only `@raw_body`, never the `shop-domain` header [3](#0-2) .

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC only against that signable string [4](#0-3) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed straight out of HTTP headers with no cryptographic binding to the signature [5](#0-4) .

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — the unauthenticated header values — and dispatches them to the app's handler [6](#0-5) . This is the exact identity-binding gap called out by the rules: a field (`shop`) that is acted on (passed to the handler as the tenant identifier) but not covered by the HMAC.

Attack path: any unprivileged internet user can install a public/development app on their own store, which is a legitimate way to receive genuine Shopify-signed webhook deliveries for that attacker-controlled shop. Because the HMAC is computed by Shopify using the app's shared `client_secret` (not a per-shop secret) and only signs the JSON body, the attacker can capture one of these legitimately-signed requests (valid `hmac` + `raw_body` pair) and replay it to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to name a victim shop. `HmacValidator.validate` still passes, because the header is not part of `to_signable_string`, and the handler receives `WebhookMetadata` with `shop` = victim shop but `body` = attacker-controlled content [7](#0-6) .

### Impact Explanation
Any application handler that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (the gem's own documented/expected usage pattern, since this is the only shop identifier the library exposes for a verified webhook) can be tricked into attributing attacker-supplied webhook content to a victim shop. Depending on the handler's logic this enables cross-tenant data confusion/injection (e.g., the app writing attacker-chosen order/product/customer data into the victim's tenant record, or triggering shop-scoped side effects under the victim's identity) — this satisfies the "cross-tenant access" Critical impact category, since the trust boundary between shop A and shop B is broken purely through gem-level signature verification gaps, not through any documented-API misuse by the host app.

### Likelihood Explanation
The prerequisite is only that the attacker can install the target application on a store they control (normal, unprivileged onboarding flow for any public/free app) and can send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both trivially available to an internet user with no special credentials, TLS interception, or leaked secrets.

### Recommendation
Bind the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the HMAC-signable representation, or independently re-verify the `shop-domain` header against Shopify (e.g., cross-check against a previously stored, authenticated session/shop record) before dispatching to handlers. At minimum, `Request#to_signable_string` should incorporate the same header set that Shopify signs for webhook delivery, and `Registry.process` should not treat header-derived `shop`/`topic` values as trusted for authorization decisions unless they are cryptographically tied to the verified signature.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a real webhook event so Shopify delivers a genuinely HMAC-signed request, e.g.:
```
POST /webhooks
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
X-Shopify-Shop-Domain: attacker.myshopify.com
X-Shopify-Webhook-Id: <id>

{"id": 1, "note": "malicious content"}
```
2. Replay the exact same body/HMAC to the app's webhook endpoint but with the header changed:
```
X-Shopify-Shop-Domain: victim.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `Digest.hexencode(...)` against `to_signable_string` (`@raw_body`) [8](#0-7)  — validation succeeds because the body/HMAC pair is unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {"id"=>1,"note"=>"malicious content"}, ...)` [9](#0-8)  — the app now believes attacker-controlled data legitimately originated from `victim.myshopify.com`.
