### Title
Mirror-sweep extension never resets `ir_face_save_fps_override`/`thermal_save_fps_override`, leaking `Some(f32::INFINITY)` into subsequent signups - ([File: src/plans/biometric_capture/mirror_sweep.rs])

### Summary
`Plan::perform_mirror_sweep` sets `orb.ir_eye_save_fps_override`, `orb.ir_face_save_fps_override`, and `orb.thermal_save_fps_override` to `Some(f32::INFINITY)` before running the sweep, but only resets `ir_eye_save_fps_override` back to `None` afterward. `ir_face_save_fps_override` and `thermal_save_fps_override` are left at `Some(f32::INFINITY)` unconditionally — on both normal completion and early abort — and this state is not reset anywhere in `run_pre`/`run_post` of `biometric_capture::Plan`, so it bleeds into whatever signup session runs next on the same `Orb` instance.

### Finding Description
In `src/plans/biometric_capture/mirror_sweep.rs`, `perform_mirror_sweep` (lines 229-231) sets all three overrides to `Some(f32::INFINITY)` to force full-rate frame saving during the sweep. After `orb.run(self).await?` completes, only line 246 resets `orb.ir_eye_save_fps_override = None`; there is no corresponding reset of `orb.ir_face_save_fps_override` or `orb.thermal_save_fps_override` [1](#0-0) . This contrasts with the sibling `overcapture.rs` extension, which correctly resets all three overrides after use [2](#0-1) .

Because `Orb` is a long-lived broker struct reused across signup sessions, and `biometric_capture::Plan::run_pre`/`run_post` never touch these override fields [3](#0-2) , any signup (attacker's own session) that exercises the mirror-sweep extension leaves `ir_face_save_fps_override` and `thermal_save_fps_override` permanently pinned to `Some(f32::INFINITY)` for every subsequent signup on that orb — regardless of whether the mirror sweep completed normally, was aborted, or timed out via `self.timeout` in `poll_extra` (lines 154-163). If the abort happens before line 246 executes, `ir_eye_save_fps_override` also leaks in the same way.

### Impact Explanation
An attacker who runs (or aborts/times out) a mirror-sweep-enabled signup causes all subsequent signups on that orb to save IR-face and thermal frames at forced-infinite rate instead of the intended throttled rate, independent of that later signup's own configuration. This is a cross-signup state bleed: capture-rate/notary-adjacent state configured under the attacker's `signup_id` persists and silently alters image-capture behavior for the next (potentially victim) signup, defeating the intended per-session rate control and any downstream assumptions about frame cadence tied to notarization/logging.

### Likelihood Explanation
The unconditional part of the bug (missing reset for `ir_face_save_fps_override`/`thermal_save_fps_override`) requires no error injection or abort at all — it triggers on every normal, successful mirror-sweep signup, which is reachable purely by presenting a QR code that selects the mirror-sweep extension parameter. This makes it highly likely/repeatable. The additional `ir_eye_save_fps_override` leak on abort requires `orb.run(...)` to return `Err` mid-sweep, which in this codebase is generally tied to agent/MCU failures rather than something a purely unprivileged, non-hardware-tampering attacker can reliably trigger; that portion is lower confidence.

### Recommendation
In `perform_mirror_sweep`, reset all three overrides symmetrically with what was set, e.g. add `orb.ir_face_save_fps_override = None;` and `orb.thermal_save_fps_override = None;` alongside the existing `orb.ir_eye_save_fps_override = None;` at line 246. Additionally, wrap the sweep body in a guard/`Drop`-based restoration (or explicit cleanup in `run_post`/`run_pre`) so that any early return via `?` still restores all override and notary state before the next signup begins, mirroring the safer pattern already used partially in `overcapture.rs`.

### Proof of Concept
Integration test plan:
1. Construct a `biometric_capture::Plan` for `signup_id_A`, convert into `mirror_sweep::Plan`, and drive `Plan::run` to completion (or force early return by making a mocked `orb.run` return `Err` mid-sweep).
2. After `Plan::run` returns, inspect the `Orb` instance and assert `orb.ir_face_save_fps_override.is_none()` and `orb.thermal_save_fps_override.is_none()`. This assertion will fail (both remain `Some(f32::INFINITY)`), demonstrating the leak.
3. Start a fresh `biometric_capture::Plan::run_pre` for `signup_id_B` on the same `Orb` and assert that frame-saving logic for IR-face/thermal cameras uses the throttled rate rather than `f32::INFINITY`, showing the stale override from `signup_id_A` still governs `signup_id_B`'s capture behavior.
