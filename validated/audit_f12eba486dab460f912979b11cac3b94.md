Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant dispatch despite being excluded from HMAC verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing about the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. `Webhooks::Registry.process` nonetheless uses `request.shop` (and `request.topic`) — taken straight from these unauthenticated headers — to select the handler and to construct the `WebhookMetadata` passed into application code. Any party who can obtain one valid `(body, HMAC)` pair signed with the app's shared secret (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the library will report it as belonging to a different, victim tenant.

### Finding Description
`Request#to_signable_string` binds the HMAC to the body only:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are never part of the signed string:

```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` verifies only the body/secret binding, then dispatches trust-sensitive tenant data derived from the unauthenticated headers:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

The identity binding that should hold is:
`shop reported to handler == shop that produced/authorized the signed body`

Because the signature covers only bytes of the body, and `shop` is parsed from a separate, unsigned header, this equality is never checked. Any actor who can legitimately obtain one `(body, hmac)` pair for the shared app secret — trivially available to anyone who installs the app on their own store, since the same `client_secret` signs every shop's webhooks for a given app — can present that same pair with a forged `shop-domain` header naming a different shop. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` attributes the (attacker-authored) body content to the victim shop when invoking the handler.

### Impact Explanation
This breaks the tenant boundary the library is supposed to guarantee to consuming apps: `Registry.process`/`WebhookMetadata` is the only signal application code has to know "which shop does this payload belong to," and the library asserts this is safe because the payload passed the HMAC check. In reality the HMAC only proves "some installer of this app produced this body," not "this body is attributed to the named shop." A merchant using the app (or anyone who can trial/install it, which is unprivileged since it just requires going through normal app installation) can inject fabricated webhook events under another merchant's identity, causing the host application to process cross-tenant data as if it originated from a victim's store (e.g., firing `orders/create`-style side effects, or mandatory GDPR topics like `customers/redact`) attributed to a shop that never sent them.

### Likelihood Explanation
Requires only: (1) installing the app once as an ordinary unprivileged user to receive a genuinely signed webhook body+HMAC, and (2) sending that same body+HMAC to the app's webhook endpoint with the `shop-domain` header swapped to the victim's domain. No access token, no `api_secret_key` knowledge, and no privileged account is needed — the whole point of the flaw is that the secret-holder-provided body/HMAC pair is reusable across arbitrary claimed tenants because the header is unauthenticated.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the string that is HMAC-verified (mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into its signable string), or otherwise cryptographically bind the header values to the signed payload before they are used for tenant/handler dispatch in `Webhooks::Registry.process`.

### Proof of Concept
1. Install the app on an attacker-controlled store `attacker.myshopify.com` and receive one legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it's HMAC(secret, B), and the secret is shared across all shops using this app installation flow).
2. Replay a request to the app's shared webhook endpoint with the same raw body `B` and same header `H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` at [1](#0-0)  passes because it only checks `B` against `H`.
4. `Registry.process` at [3](#0-2)  invokes the registered handler with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though the body content and signature originated from the attacker's own shop.
