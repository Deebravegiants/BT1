### Title
Missing `VestingSchedule::assert_valid()` enforcement in `LockupContract::new()` / `LockupFactory::create()` allows creation of vesting schedules with invalid timestamp ordering - (File: `lockup/src/lib.rs`, `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` is a public, unprivileged, payable entrypoint that forwards a caller-supplied `vesting_schedule` to `LockupContract::new()` via a cross-contract `function_call`. Although `VestingSchedule` defines an `assert_valid()` method that checks `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`, neither `LockupContract::new()` nor `LockupFactory::create()` ever calls it. This is directly analogous to the referenced RCFactory bug: a validation helper exists for enforcing sequential timestamp ordering, but the entrypoint that actually consumes user-supplied timestamps never invokes it.

### Finding Description
`LockupFactory::create()` is callable by any account and accepts a `vesting_schedule: Option<VestingScheduleOrHash>` parameter directly from the caller: [1](#0-0) 

When the schedule is a plain (non-hashed) `VestingSchedule`, it is passed through unchanged in the `LockupArgs` payload to the deployed lockup contract's `new()` function: [2](#0-1) 

In `LockupContract::new()`, the vesting schedule is stored directly into `VestingInformation::VestingSchedule(vs)` with **no call to `vs.assert_valid()`**: [3](#0-2) 

The `assert_valid()` method exists specifically to enforce `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`, but a repo-wide search shows it is never invoked anywhere in `lockup/` or `lockup-factory/` — it exists only as a dead/unused helper: [4](#0-3) 

Because this check is skipped, an attacker can create a lockup contract whose vesting schedule violates the required ordering (e.g., `end_timestamp < start_timestamp`, or `cliff_timestamp` outside the `[start, end]` range). This schedule is later consumed in `get_unvested_amount()`, which performs unchecked subtraction assuming `end_timestamp >= start_timestamp` and `end_timestamp >= block_timestamp`: [5](#0-4) 

If `end_timestamp < start_timestamp`, the expression `vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0` underflows once execution reaches the "between cliff and end" branch, panicking the transaction. This function is invoked from `terminate_vesting()` (the Foundation's only mechanism to claw back unvested tokens): [6](#0-5) 

If `get_unvested_amount()` unconditionally panics due to the malformed schedule, `terminate_vesting()` can never succeed, permanently disabling the Foundation's contractual ability to terminate vesting and reclaim unvested tokens for that lockup account.

### Impact Explanation
This matches the "High: state-transition bypass ... lets an unprivileged user perform actions beyond intended authority" and "share/vesting/refund accounting divergence" categories: an unprivileged caller of `LockupFactory::create()` (acting as their own `owner_account_id`) can craft a vesting schedule that permanently disables the Foundation's `terminate_vesting()` authority over that lockup contract, defeating the core security guarantee described in the lockup contract's own documentation ("The owner can not prevent the foundation from withdrawing the unvested balance in case of termination"). This directly contradicts that documented guarantee.

### Likelihood Explanation
High — `LockupFactory::create()` has no privilege restriction; anyone with `MIN_ATTACHED_BALANCE` (3.5 NEAR) can call it and directly supply an arbitrary `VestingSchedule`. No special conditions or races are needed; the malformed data is accepted and stored at contract-creation time.

### Recommendation
Call `vesting_schedule.assert_valid()` in `LockupContract::new()` immediately when handling the `Some(VestingScheduleOrHash::VestingSchedule(vs))` branch (and ideally also validate in `LockupFactory::create()` before dispatching the cross-contract call), mirroring the fix recommended and applied for the analogous RCFactory issue:
```rust
Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
    vs.assert_valid();
    VestingInformation::VestingSchedule(vs)
}
```

### Proof of Concept
1. Attacker calls `LockupFactory::create()` with `owner_account_id` = attacker's own account, `attached_deposit >= MIN_ATTACHED_BALANCE`, and:
```json
"vesting_schedule": {
  "VestingSchedule": {
    "start_timestamp": "2000000000000000000",
    "cliff_timestamp": "2000000000000000000",
    "end_timestamp": "1000000000000000000"
  }
}
```
(`end_timestamp < start_timestamp`).
2. `LockupFactory::create()` forwards this unchecked to the new lockup contract's `new()` init call.
3. `LockupContract::new()` stores it directly into `VestingInformation::VestingSchedule` without calling `assert_valid()`.
4. Once `block_timestamp` passes `cliff_timestamp` but is still below the (numerically smaller) `end_timestamp` window logic, or once the Foundation calls `terminate_vesting()`, `get_unvested_amount()` executes `end_timestamp - start_timestamp`, which underflows and panics, causing `terminate_vesting()` to always fail — permanently blocking the Foundation from ever terminating this vesting schedule.

**Note on uncertainty:** I could not confirm from the indexed files whether the Rust build profile for these contracts enables overflow-checks in release/wasm builds (this determines whether the underflow panics or silently wraps to a huge `total_time`, which would instead produce grossly incorrect vesting math rather than a panic — either outcome is a security-relevant accounting/state-machine failure, but the exact failure mode depends on the compiler/profile settings, which I was unable to verify within the indexed content). A Devin session with full repository/build access could confirm the exact `Cargo.toml`/build profile behavior to pin down the precise failure mode.

#[derive(BorshDeserialize, BorshSerialize, Deserialize, Serialize, Clone, PartialEq, Debug)]
#[serde(crate = "near_sdk::serde")]
pub struct VestingSchedule {
    /// The timestamp in nanosecond when the vesting starts. E.g. the start date of employment.
    pub start_timestamp: WrappedTimestamp,
    /// The timestamp in nanosecond when the first part of lockup tokens becomes vested.
    /// The remaining tokens will vest continuously until they are fully vested.
    /// Example: a 1 year of employment at which moment the 1/4 of tokens become vested.
    pub cliff_timestamp: WrappedTimestamp,
    /// The timestamp in nanosecond when the vesting ends.
    pub end_timestamp: WrappedTimestamp,
}

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,
            "Cliff timestamp can't be later than vesting end timestamp"
        );
        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,
            "The total vesting time should be positive"
        );
    }
}

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
