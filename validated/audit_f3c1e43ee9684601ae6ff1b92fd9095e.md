**Analysis:**

The premise that `DeriveSupply.dispatch_function` can be mutated post-registration via `swap_or_fill`/`fill` from unprivileged code does not hold up:

1. **Write path is friend-gated and single-use.** `register_derive_supply_dispatch_function` is `public(friend)` in `fungible_asset.move`, callable only by the framework's `dispatchable_fungible_asset` module, and only accepts a `&ConstructorRef` — which exists exclusively at object creation time and is consumed once per object. [1](#0-0) 

2. **Re-registration is explicitly blocked.** The function asserts `!exists<DeriveSupply>(...)` before `move_to`, so the resource can only be written once per object address; there is no second entry point to `move_to<DeriveSupply>` or `borrow_global_mut<DeriveSupply>` anywhere in the codebase. [2](#0-1) 

3. **The read accessor returns a copy, not a mutable handle.** `derived_supply_dispatch_function` is itself `public(friend)` and returns the `Option<FunctionInfo>` **by value**, not `&mut Option<FunctionInfo>`, so callers of `dispatchable_fungible_asset::derived_supply` (including unprivileged view calls) only ever get a copy to `option::borrow`, never a mutable reference to invoke `swap_or_fill`/`fill` against the stored field. [3](#0-2) [4](#0-3) 

Since there is no exposed function that returns `&mut Option<FunctionInfo>` for `DeriveSupply.dispatch_function`, and the only write path is `public(friend)` + guarded against re-registration, unprivileged Move code has no reachable call path to `swap_or_fill`/`fill` on this field. The custody boundary is closed by module visibility (`friend`) and by the one-time registration invariant, not merely by an incidental check.
