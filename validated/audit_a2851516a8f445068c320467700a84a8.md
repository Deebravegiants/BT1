### Title
LP seeded away from curve-close price via pre-seeded HyperSwap V2 TOKEN/LT pair at `finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The externally reported bug class is an unauthenticated actor exploiting an unprotected "first-run setup" write path to permanently hijack state before the legitimate owner can claim it. The reachable analog in alt.fun is that any unprivileged address can pre-create and pre-seed the external HyperSwap V2 `TOKEN/LT` pair before `Bonding.finalizeGraduation` performs its one-shot LP seed into that same pair, forcing the protocol's `addLiquidity` call to "rebalance" against attacker-chosen reserves rather than reverting, and permanently locking LP at an off-market price.

### Finding Description
Graduation is documented as a two-phase, permissionless process: phase 1 (`triggerGraduation`) pins the LP-seed target (`tokensForLP`) at the last curve price, and phase 2 (`finalizeGraduation`) later calls `addLiquidity(tokensForLP, ltFromPair)` on HyperSwap V2, sending the resulting LP tokens to `LPLock` [1](#0-0) .

The project's own documentation acknowledges that this deposit does not require the pair to be empty: "if the pair already holds live reserves the deposit rebalances, so it is the intended target rather than the exact deposit" [2](#0-1) . HyperSwap V2 (a standard Uniswap V2 fork) allows any address to permissionlessly call `factory.createPair(TOKEN, LT)` and to directly transfer `TOKEN`/`LT` into that pair, seeding arbitrary reserves before `Bonding` ever touches it — this is one of the explicitly reachable analog paths for this codebase (pre-creating/pre-seeding the HyperSwap V2 pair before graduation).

This is distinct from the internal bonding-curve `Pair` used during the `Curve` lifecycle, which the invariant suite documents as donation-resistant by design (`canGraduate`'s USD leg uses stored, not live, reserves, and donated LT to the curve `Pair` "stays locked in the curve pair") [3](#0-2) . The graduation-time HyperSwap V2 pair carries no equivalent protection: its reserves are whatever the standard AMM holds when `finalizeGraduation` calls `addLiquidity`, and the documented "invariant #1" (`ltFromPair × reserve0End ≈ tokensInLP × reserve1End` within 1 bps, i.e. "Zero price gap") is only guaranteed for the *normal* empty-pair case — the same doc explicitly carves out the rebalancing case as a deviation from the pinned target [4](#0-3) .

Because `_deployAndSeed` shows the protocol already relies on `Clones`/`factory.createPair` patterns that assume a specific, protocol-controlled pair for the bonding-curve phase [5](#0-4) , but the graduation-time HyperSwap V2 pair is an *external*, permissionlessly-creatable contract, nothing in the reachable flow stops a third party from front-running the phase-2 seed with a skewed `TOKEN:LT` ratio.

### Impact Explanation
An unprivileged address can, ahead of `finalizeGraduation`, create the `TOKEN/LT` HyperSwap V2 pair and donate a skewed ratio of `TOKEN` and `LT` into it. When `finalizeGraduation` later executes its `addLiquidity(tokensForLP, ltFromPair)` call, the deposit "rebalances" against the attacker's pre-set ratio instead of opening exactly at the curve's last price. This permanently locks LP (via the one-shot `LPLock.recordLock`, which `finalizeGraduation` cannot skip) at an off-market price, freezing creator/LP/protocol value at a mispriced pool and letting the attacker's donated LT/TOKEN be arbitraged out by the first post-graduation trader through `Zap`. This satisfies the "LP seeded away from the curve close price" impact bar explicitly called out as valid.

### Likelihood Explanation
Likelihood is high for any token nearing graduation: creating a Uniswap-V2-style pair and transferring tokens into it are ordinary, permissionless, low-cost operations available to any wallet holding a small amount of the not-yet-graduated `Token` (freely tradable on the curve) and of the reserve `LT`. No privileged role, upgrade, or off-chain component is required — the attacker only needs to act in the window between a token becoming graduatable (`triggerGraduation`) and the permissionless `finalizeGraduation` call.

### Recommendation
`finalizeGraduation` should verify, immediately before calling `addLiquidity`, that the target HyperSwap V2 pair either does not yet exist or holds zero `TOKEN`/`LT` reserves, and revert (or sweep/refund the foreign reserves to a safe destination before seeding) if it has been pre-seeded. Alternatively, compute an expected price band from the pinned curve-close price and enforce it via non-trivial `amountMin` values on the `addLiquidity` call so an off-ratio pool cannot silently absorb the seed.

### Proof of Concept
1. Observe a token approaching `canGraduate(token) == true` on `Bonding`.
2. Before anyone calls `finalizeGraduation`, call HyperSwap V2 `Factory.createPair(TOKEN, LT)` (permissionless) and transfer a skewed ratio of `TOKEN` and `LT` directly into the pair (e.g., mostly `LT`, minimal `TOKEN`).
3. Wait for/trigger `Bonding.triggerGraduation(token)` (permissionless) and then `Bonding.finalizeGraduation(token)` (permissionless).
4. `finalizeGraduation`'s `addLiquidity(tokensForLP, ltFromPair)` call rebalances against the attacker's pre-seeded reserves rather than opening at the pinned curve-close price, per the documented rebalancing behavior [2](#0-1) .
5. LP is minted to `LPLock` at the skewed price; the attacker's pre-seeded imbalance is now capturable by trading against the mispriced pool immediately post-graduation via `Zap`.

    function _deployAndSeed(
        address tokenAddr,
        bytes32 saltMixed,
        string calldata name_,
        string calldata ticker_,
        address ltAddress
    ) internal returns (address pair) {
        BondingStorage storage $ = _s();
        Clones.cloneDeterministic($.tokenImplementation, saltMixed);

        Token(tokenAddr).initialize(name_, ticker_, address(this));

        uint256 totalSupply = Token(tokenAddr).TOTAL_SUPPLY();
        uint256 curveSupply = (totalSupply * CURVE_BPS) / BPS_DENOM;

        pair = $.factory.createPair(tokenAddr, ltAddress);

        uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
        if (exchangeRate == 0) revert ZeroExchangeRate();
        uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
        // The raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out)
        // and is later deposited into a HyperSwap V2 pair, whose reserves are
        // `uint112`. Bound it at launch (4x headroom) so graduation can never
        // exceed that slot.
        if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();

        IERC20(tokenAddr).forceApprove(address($.router), curveSupply);
        // Virtual tokenReserve = full totalSupply; only curveSupply (75%) actually transferred.
        // The launch-time `virtualLtReserve` is recoverable later as
        // `Pair.k() / Token.TOTAL_SUPPLY()`: `Pair.mint` sets `_pool.k =
        // tokenReserve * assetReserve = totalSupply * virtualLtReserve` once
        // and `Pair.swap` never modifies `_pool.k`. That identity is what
        // `_launchTimeVirtualLtReserve` exploits to derive donation-immune
        // raised-LT in `canGraduate` and `_prepareGraduationLiquidity`.
        $.router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, virtualLtReserve);
    }
