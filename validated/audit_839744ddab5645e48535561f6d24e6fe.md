### Title
Webhook shop/topic identity spoofing due to HMAC covering only the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the JSON body bytes. The `shop`, `topic`, and `webhook_id` fields — which `Registry.process` uses to attribute the event to a tenant and dispatch the handler — come from the `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` headers, none of which are part of the signed material.

### Finding Description
`Request#hmac` decodes the `shopify-hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` gates on this HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — read straight from headers — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`bytes cryptographically verified by the HMAC == bytes/fields the handler acts on as the tenant identifier`

Here that equality is broken: the HMAC verifies only `raw_body` bytes, while `shop` (the tenant-scoping field) and `topic`/`webhook_id` are taken from unauthenticated headers. Any party who has observed one legitimate webhook delivery (body + valid HMAC — visible in logs, browser dev tools on a merchant's own webhook debug tools, a compromised low-privilege log-viewer, etc., i.e., no `api_secret_key` needed) can resend that exact body with the same valid HMAC while substituting a different `shopify-shop-domain` header. `Utils::HmacValidator.validate(request)` still returns `true` because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to an arbitrary attacker-chosen shop.

### Impact Explanation
This lets an unprivileged party cause the app's webhook handler to process data under an attacker-chosen `shop` (and/or `topic`) while the HMAC check still reports success, i.e., a cross-tenant identity binding bypass at the point where the gem hands verified data to the application. Apps that rely on `WebhookMetadata#shop`/`#topic` (as instructed by this gem's own API) to select which merchant's data store to write to would attribute/write data to the wrong tenant — a cross-tenant integrity/confidentiality break enabled entirely within this gem's verification logic.

### Likelihood Explanation
Requires only a previously observed body+HMAC pair (not the `api_secret_key`) and the ability to send an HTTP request to the app's webhook endpoint with forged headers — no privileged account or credential theft needed. This is a straightforward, low-effort replay/header-substitution once one webhook body has been observed.

### Recommendation
Include the tenant/topic identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body's HMAC before `Registry.process` trusts them for dispatch — e.g., verify body HMAC as today but additionally require the resulting `shop` to be checked against an out-of-band trusted association (session/subscription record) before invoking the handler, rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker observes one legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` (H = HMAC-SHA256(secret, B)), for `shopify-shop-domain: victim-shop.myshopify.com`.
2. Attacker crafts a new request to the app's webhook endpoint with the same body `B`, the same header `shopify-hmac-sha256: H`, but `shopify-shop-domain: attacker-shop.myshopify.com` (and/or a different `shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → validation passes. [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(shop: "attacker-shop.myshopify.com", ...)`, even though the HMAC never verified that shop value, breaking the shop-identity binding the app relies on.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
