## Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identifier that is handed to the application's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material. An attacker who legitimately receives one valid, HMAC-signed webhook (e.g., by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value, and the gem will report the request as authentic for the attacker-chosen shop.

### Finding Description
The equality that should hold is:

`shop value trusted by the handler == shop value cryptographically bound by the verified signature`

but this gem actually enforces:

`shop value trusted by the handler == unauthenticated header value`

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `ShopifyAPI::Webhooks::Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is **not** part of `to_signable_string`: [2](#0-1) 

- `Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which hashes `to_signable_string`, i.e., only the body) and then, once that check passes, forwards `request.shop` — the unauthenticated header — directly to the registered handler as the tenant identifier: [3](#0-2) 

- `Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` using `Context.api_secret_key`, and never incorporates the `shop` field for webhook requests (unlike `AuthQuery`, whose `to_signable_string` explicitly includes `shop`): [4](#0-3) [5](#0-4) 

Because `shop` never enters the signable string for `Webhooks::Request`, any consumer of the app who can capture (or is itself the recipient of) one legitimately signed webhook body — e.g., by installing the app on their own free/test shop and letting Shopify deliver a real webhook — can retransmit the identical body and HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` passes the forged shop straight into `WebhookMetadata` for the handler: [6](#0-5) 

The recommended integration pattern documented for this gem confirms that the application is expected to trust `Registry.process`'s output as authenticated: it registers the raw request headers and body, and lets the gem alone decide authenticity before invoking the handler: [7](#0-6) 

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on when this gem reports "the webhook HMAC is valid." Any application logic keyed off `WebhookMetadata#shop` (e.g., revoking an access token on `app/uninstalled`, updating billing/subscription status, deleting shop-scoped data, or disabling a shop) can be triggered against a shop the attacker does not control, using a webhook body the attacker legitimately obtained for their own shop. This is a cross-tenant integrity/action issue driven directly by an identity field that the gem's own signature check does not cover, which is squarely a Critical-class cross-tenant impact per the accepted categories (though the concrete blast radius depends on what data the specific handler acts on).

### Likelihood Explanation
Exploitation only requires an unprivileged internet user to be able to install the target app on any Shopify development/trial store (installation of apps by any merchant, including the attacker's own store, is a standard, low-friction workflow) and capture one webhook delivery. No secrets, tokens, or privileged access are required, and the replay itself is a simple HTTP POST to the app's public webhook route with a modified header — well within the "unprivileged internet user" threat model this scan is scoped to.

### Recommendation
Bind the `shop` (and ideally the `topic`) into the HMAC-signed material for webhook requests, or otherwise authenticate the shop header value against the body/signature (for example, by including `shop`/`topic`/`webhook-id` in `to_signable_string` used by `HmacValidator`, mirroring what `Auth::Oauth::AuthQuery#to_signable_string` already does for OAuth). At minimum, document loudly that `WebhookMetadata#shop` is not cryptographically authenticated and that host applications must independently verify the shop exists in their own installed-shop registry before acting on webhook data.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `app/uninstalled`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Inside the gem:
   - `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed.
   - `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only and it matches `H`, returning `true`.
   - `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body(B), ...)`.
4. The application's registered handler executes its logic (e.g., token revocation, uninstall cleanup) believing it received an authentic webhook from `victim-shop.myshopify.com`, even though that shop never sent it.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
