### Title
Permanent lock of escrowed USDC-like blacklistable ERC20 in WrappedHyperFungibleToken when beneficiary is blacklisted on delivery, combined with unusable timeout when `timeoutTimestamp == 0` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol` / `WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lock an arbitrary underlying ERC20 on `send()` and, on delivery, push it out via a raw `safeTransfer` to the beneficiary with no try/catch fallback. If the underlying token is a blacklistable stablecoin (e.g. USDC) and the beneficiary becomes blacklisted between dispatch and delivery, `onAccept` reverts on every retry forever. Because `Message.timeout()` treats `timeoutTimestamp == 0` as "never times out" (`type(uint64).max`), a sender who dispatches with `timeout: 0` (a value the `send()` function does not reject) can never submit a timeout proof to reclaim the escrowed funds via `onPostRequestTimeout`. The escrowed tokens become permanently unrecoverable — the exact bug class described in the external report, reproduced here in Hyperbridge's own token-wrapping app rather than an OP-stack bridge.

### Finding Description
1. A user calls `send()` on `WrappedHyperFungibleToken`, locking `params.amount` of the underlying ERC20 via `safeTransferFrom`, and dispatches a `PostRequest` with an attacker/user-controlled `timeout` field (part of `SendParams`). [1](#0-0) 
2. On the destination chain, `onAccept` decodes the message and unconditionally calls `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` for non-WETH underlyings, with no try/catch or fallback escrow path: [2](#0-1) 
3. If `_underlying` is USDC-like and `beneficiary` is blacklisted, `safeTransfer` reverts, so the whole `onAccept` call reverts. `EvmHost.dispatchIncoming` catches this failure, deletes the request receipt, and returns without reverting the batch — leaving the request permanently retryable but never delivered while the blacklist persists: [3](#0-2) 
4. The only recovery path for the source-chain escrow is a timeout: `HandlerV2.handlePostRequests` checks `timestamp >= leaf.request.timeout()` to reject late delivery, and a separate timeout message flow lets the sender's chain refund escrow via `onPostRequestTimeout`. [4](#0-3) 
5. However, `Message.timeout()` defines `timeoutTimestamp == 0` as "no timeout" (`type(uint64).max`): [5](#0-4) 

`send()` in `WrappedHyperFungibleToken` performs no validation that `params.timeout != 0` before dispatching, so a request with `timeout: 0` can never satisfy a timeout condition, and the escrow can never be recovered through `onPostRequestTimeout` either. Combined with a permanently blacklisted beneficiary, the locked underlying tokens are stuck in the `WrappedHyperFungibleToken` contract forever, with no admin/owner recovery function present in the contract to sweep or redirect stuck funds to a corrected beneficiary.

### Impact Explanation
High: real user funds (e.g., USDC) locked in the wrapper contract become permanently unrecoverable once the destination beneficiary is blacklisted and the request has no expiring timeout. This is a direct, unbacked, permanent freeze of user funds triggerable by ordinary use of the public `send()` API — no privileged actor required. The same pattern is repeated identically in `WrappedHyperFungibleTokenUpgradeable.sol`.

### Likelihood Explanation
Medium: requires (a) the underlying token to be a blacklistable asset like USDC (a realistic and expected deployment given Hyperbridge explicitly documents wrapping arbitrary ERC20s), (b) the beneficiary becoming blacklisted after dispatch but before delivery — plausible during Optimism/L1-style multi-day finality windows the same class of report describes — and (c) `timeout` being set to 0 or a value that expires after the blacklist becomes permanent. Note: even with a nonzero timeout, funds are stuck for the full timeout window and only recoverable if a relayer/user actively submits the timeout proof — before that, `onAccept` will simply keep reverting on retry.

### Recommendation
- Wrap the `safeTransfer` in `onAccept` (and the WETH fallback push) in a try/catch; on failure, credit the amount to an internal `stuckFunds[beneficiary]` mapping instead of reverting the whole delivery, and add a permissionless `withdrawStuckFunds()` function once the address is no longer blacklisted.
- Reject `params.timeout == 0` in `send()` (or otherwise cap the maximum timeout) so every dispatched request has a bounded, enforceable expiry that guarantees eventual timeout-based recovery of escrow.
- Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` configured with underlying = USDC.
2. Call `send({dest, to: bob, amount: 10_000e6, timeout: 0, relayerFee: 0, data: ""})`; USDC is locked in the wrapper via `safeTransferFrom`. [6](#0-5) 
3. Before the message is relayed, `bob` gets blacklisted on the destination chain's USDC contract.
4. Any relayer submits `handlePostRequests`; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `IERC20(usdc).safeTransfer(bob, 10_000e6)`, which reverts due to the blacklist. The host swallows the failure and deletes the receipt, so the request is "retryable" but will keep failing forever since bob's blacklist status is source-chain-independent and never changes. [7](#0-6) 
5. Because `timeout` was 0, `Message.timeout()` returns `type(uint64).max`, so `handlePostRequestTimeouts`/`HandlerV2` timeout checks never allow a timeout proof to be accepted for this request — the escrowed USDC on the source chain can never be released back to the sender via `onPostRequestTimeout`, and there is no other recovery function on `WrappedHyperFungibleToken`. Funds are permanently locked.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)

            IWETH(_underlying).withdraw(message.amount);

                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
