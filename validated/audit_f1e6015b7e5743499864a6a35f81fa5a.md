### Title
Webhook shop-domain header is trusted for tenant attribution without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only the HMAC of the raw request body, then hands the handler a `shop` value read directly from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header. The HMAC never covers the shop identity, so a valid signature proves only "this body was HMAC'd with the app's secret" — it says nothing about which shop the request is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and the HMAC computed over it is checked in `HmacValidator.validate` via `verifiable_query.to_signable_string`: [1](#0-0) [2](#0-1) 

Separately, `shop` is read straight from request headers with no cryptographic binding to the body or signature: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) as authenticated tenant/routing data, passing it to the handler as-is: [4](#0-3) 

The equality the gem implicitly assumes is: `shop_that_produced_the_HMAC == shop_header_value`. But nothing enforces this — the HMAC is computed over `raw_body` alone, so `shop` (and `topic`, `webhook_id`, `api_version`) are fully attacker-controllable fields that ride along with a validly-signed body.

Because all shops installed on a given app share the same `client_secret` (used as the sole HMAC key), any merchant who has installed the app can capture a legitimately-signed webhook delivered to their own endpoint (body + valid `X-Shopify-Hmac-Sha256`), then replay that exact body/signature pair while substituting the `X-Shopify-Shop-Domain` header for a different shop that also uses the app. `HmacValidator.validate` will still return `true` (the body bytes and signature are unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop: [5](#0-4) 

Any handler that uses `data.shop` to key storage, invalidate caches, trigger redactions, or otherwise take shop-scoped action will act on attacker-chosen data under a victim shop's identity — a cross-tenant boundary break using only unprivileged access to one's own shop's app installation.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is expected to provide for webhook processing: bytes are verified, but the tenant (`shop`) they get attributed to is not. A malicious merchant can forge webhook events "from" another merchant's shop (including the mandatory `customers/redact`, `customers/data_request`, `shop/redact` topics), causing the host application to process attacker-controlled data as if it originated from a different, victim tenant — cross-tenant access/data corruption within the meaning of the High-impact category in scope.

### Likelihood Explanation
Exploitation requires no privileged access, no leaked secrets, and no TLS interception: any unprivileged user who installs the app on their own store receives real signed webhooks and can capture/replay them with a modified header, since HTTP headers are trivially attacker-controlled on a raw request being processed by `Webhooks::Request.new(raw_body:, headers:)`. The only constraint is that the victim shop must use the same app (same `client_secret`), which is the normal multi-tenant deployment model for a Shopify app.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise cryptographically verify that the header-derived `shop` corresponds to the shop that Shopify actually delivered the webhook for — e.g., cross-check `request.shop` against a shop that has an active install/session in the host app before invoking the handler, or require the caller to supply the expected shop and compare it to `request.shop` before calling `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be independently verified by the host application before being used for tenant-scoped actions.

### Proof of Concept
1. App has two shops installed: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the app's single `client_secret`.
2. Shopify delivers a real webhook to the attacker's endpoint for `attacker-shop.myshopify.com`, e.g. topic `customers/data_request`, with a valid `X-Shopify-Hmac-Sha256` computed over the raw body.
3. Attacker captures this raw body + HMAC header pair (it is delivered to their own controlled endpoint, so no interception is required).
4. Attacker replays the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` and `to_signable_string` are unaffected by the header change; `HmacValidator.validate` returns `true`.
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, and the host app now processes attacker-controlled data attributed to `victim-shop.myshopify.com`.
