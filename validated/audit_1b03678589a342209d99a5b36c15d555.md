### Title
Browser-context BTC withdrawal status reports `completed` with a not-yet-final `pending_sign_id` as `txHash` - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
In `describeWithdrawal`, for UTXO-chain destinations, when `typeof window !== "undefined"` the code returns `{status:'completed', txHash: transfer.utxo_meta?.pending_sign_id}` instead of waiting for `transfer.finalised?.transaction_hash` [1](#0-0) . The code's own comment states the pending sign id "is not the finalised tx hash" and "may change if the BTC transfer fails to be submitted" [2](#0-1) , meaning a caller can observe a terminal `completed` status bound to a hash that never lands on Bitcoin.

### Finding Description
The claimed equality is: `(status, txHash)` returned by `describeWithdrawal` must equal the actual on-chain Bitcoin outcome. For UTXO destination chains in a browser environment, the code takes `txHash = transfer.utxo_meta?.pending_sign_id` and, as long as that value is truthy, unconditionally returns `{ status: "completed", txHash }` [3](#0-2) . This value is a signing-request identifier, not a Bitcoin transaction id — it is explicitly documented as capable of changing if the BTC broadcast fails and has to be re-signed. `watchWithdrawal` in `withdrawal-watcher.ts` treats any `status === "completed"` as terminal and returns `{ hash: status.txHash }` immediately, stopping polling [4](#0-3) . There is no subsequent re-check, reconciliation, or invalidation path in this repo that revisits a "completed" pending-sign-id result if the underlying BTC transfer is later resubmitted with a different real hash. No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `FeeExceedsAmountError`, `getUnderlyingFee`, `matchesRequest`, or contract-side nonce/signature checks) touches this post-submission status-reporting logic at all — they only apply to intent construction and fee validation, not to the withdrawal-completion status returned to the caller.

### Impact Explanation
An integrator polling `describeWithdrawal`/`watchWithdrawal` in a browser context can receive a terminal `completed` status with a `txHash` equal to a `pending_sign_id` that subsequently gets invalidated and re-signed with a different, final Bitcoin transaction hash. If the integrator uses this terminal signal to credit the user, mark the withdrawal as done, or display/store the txHash as the final receipt, that record permanently diverges from the actual on-chain outcome — a status/hash misreport that can cause double-crediting or crediting against a non-existent transaction. This matches the High severity category ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This triggers automatically, without any special attacker action, whenever: (1) the SDK is invoked in a browser context (`typeof window !== "undefined"`), (2) the withdrawal targets a UTXO chain (e.g. Bitcoin) via Omni Bridge, and (3) the underlying BTC broadcast is retried/resigned before finalization — a scenario the code comment itself acknowledges as a real, expected occurrence ("may change if the BTC transfer fails to be submitted"). No privileged access or malicious input is required; it is a property of ordinary SDK usage in a browser front-end, and it is repeatable on every withdrawal that undergoes a resign.

### Recommendation
Do not report `status: "completed"` based on `pending_sign_id` alone. Either (a) return a distinct intermediate status (e.g., `"pending"` or a new `"submitted"` state) that does not imply finality until `transfer.finalised?.transaction_hash` is available, regardless of environment, or (b) if a fast "submitted" signal is required for front-end UX, expose it via a separate field so `watchWithdrawal` and integrators cannot mistake it for the authoritative terminal txHash, and continue polling until `transfer.finalised?.transaction_hash` is set.

### Proof of Concept
Vitest plan (mocking only `omniBridgeAPI.getTransfer` HTTP call):
1. Set `globalThis.window = {}` to simulate a browser environment.
2. Mock `getTransfer` to return `[{ recipient: <btc OmniAddress>, utxo_meta: { pending_sign_id: "sign-id-1" }, finalised: null }]`.
3. Call `omniBridge.describeWithdrawal({ tx, index: 0 })` and assert it returns `{ status: "completed", txHash: "sign-id-1" }`.
4. Mock a second call to `getTransfer` (simulating the resign after a failed BTC submission) returning `[{ recipient: <btc OmniAddress>, utxo_meta: { pending_sign_id: "sign-id-2" }, finalised: { transaction_hash: "btc-tx-final" } }]`.
5. Call `describeWithdrawal` again and assert `finalised.transaction_hash ("btc-tx-final") !== "sign-id-1"`, demonstrating that the previously reported `completed`/`txHash` from step 3 was not authoritative and diverged from the eventual real Bitcoin transaction hash.
