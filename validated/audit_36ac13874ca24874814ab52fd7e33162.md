### Title
Missing height bound on BSC equivocation evidence lets stale double-votes permanently freeze a live consensus client - (File: modules/ismp/clients/bsc/src/lib.rs)

### Summary
`BscClient::verify_fraud_proof` authenticates two conflicting BLS-signed votes (`target_number` equal, `target_hash` different) purely against the *current* `consensus_state.current_validators` set, with no check that the equivocation's `target_number` is bound to (e.g., at or above) the client's current `finalized_height` or otherwise recent/unresolved. This mirrors the Cosmos Hub/ICS advisory: a missing height-based filter on cryptographic equivocation evidence lets old/irrelevant evidence be processed as if it were current, here weaponized to freeze an otherwise healthy, actively-updating consensus client.

### Finding Description
`verify_bsc_header` (`modules/consensus/bsc/verifier/src/lib.rs:50-133`) validates only: signature/quorum over `vote_data`, and that `target_header` is the direct child of `source_header`. It never receives or checks `finalized_height`.

`BscClient::verify_consensus` (`modules/ismp/clients/bsc/src/lib.rs:88-93`) explicitly guards against staleness for state updates:
```rust
if consensus_state.finalized_height >= bsc_client_update.source_header.number.low_u64() {
    Err(Error::ExpiredUpdate { .. })?
}
```
`BscClient::verify_fraud_proof` (`modules/ismp/clients/bsc/src/lib.rs:174-231`) has no analogous check. It only verifies:
1. both updates authenticate against `consensus_state.current_validators`,
2. `vote_1.target_number == vote_2.target_number`,
3. `vote_1.target_hash != vote_2.target_hash`.

Because BSC's 21-validator set persists across many epochs (only occasionally rotated via governance/`next_validators`), a pair of BLS-signed conflicting votes cast by the then-current validator set far in the past — at a `target_number` well below the client's current `finalized_height`, or corresponding to already-resolved/irrelevant misbehavior — will still verify successfully against `current_validators` today, since the signing keys are unchanged. `freeze_client` (`modules/ismp/core/src/handlers/consensus.rs:124-145`) then permanently freezes the consensus client on this basis, and per the protocol docs, "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized" [1](#0-0) . ### Impact Explanation
Freezing is irreversible and terminal for the affected route ("Frozen consensus clients cannot be unfrozen"). Any permissionless fisherman submitting this `FraudProofMessage` can permanently disable the BSC consensus client, halting all cross-chain message delivery, state proofs, and token bridge operations that depend on it — a "route unable to deliver messages" outcome, and one that can be triggered even though the live BSC consensus is currently healthy and has advanced far beyond the exploited height.

### Likelihood Explanation
This requires a genuine BLS-signed double vote by the (largely static) BSC validator set at some `target_number`, which is a real slashable Parlia event; such events have historically occurred on BSC and remain crypto-economically verifiable indefinitely since there is no expiry/height check tying the evidence to the client's current progress. Any relayer/fisherman holding or discovering such historical vote pairs can submit them permissionlessly at any time to `freeze_client`, regardless of how long ago — or how irrelevant to the client's current trusted state — the equivocation occurred.

### Recommendation
Bind the fraud-proof height to the client's live state the same way `verify_consensus` does: reject `verify_fraud_proof` submissions whose `vote.target_number` is at or below `consensus_state.finalized_height` (or otherwise outside a configured recency/unbonding window), consistent with the height-based filtering pattern ICS re-introduced for consumer equivocation evidence.

### Proof of Concept
1. Identify (or wait for) two conflicting BLS-signed `VoteData` attestations produced by the BSC validator set at some historical `target_number T`, where `T <= consensus_state.finalized_height` on the Hyperbridge BSC consensus client (i.e., already-superseded/irrelevant history).
2. Construct `bsc_client_update_1` and `bsc_client_update_2` with `attested_header`s embedding these two conflicting votes.
3. Submit a `FraudProofMessage { proof_1, proof_2, consensus_state_id: BSC_CONSENSUS_ID, .. }` via `handlers::freeze_client`.
4. `BscClient::verify_fraud_proof` authenticates both against `consensus_state.current_validators` (still valid since keys are unchanged), confirms `target_number` equality and `target_hash` inequality, and returns `Ok(())`.
5. `host.freeze_consensus_client(msg.consensus_state_id)` is called, permanently freezing the BSC route despite it being actively and correctly finalized far past `T`.

	fn verify_fraud_proof(
		&self,
		_host: &dyn IsmpHost,
		trusted_consensus_state: Vec<u8>,
		proof_1: Vec<u8>,
		proof_2: Vec<u8>,
	) -> Result<(), ismp::error::Error> {
		let bsc_client_update_1 =
			BscClientUpdate::decode(&mut &proof_1[..]).map_err(|_| Error::DecodeBscClientUpdate)?;

		let bsc_client_update_2 =
			BscClientUpdate::decode(&mut &proof_2[..]).map_err(|_| Error::DecodeBscClientUpdate)?;

		let header_1 = bsc_client_update_1.attested_header.clone();
		let header_2 = bsc_client_update_2.attested_header.clone();

		let consensus_state = ConsensusState::decode(&mut &trusted_consensus_state[..])
			.map_err(|_| Error::DecodeConsensusState)?;
		let epoch_length = Pallet::<T>::epoch_length().ok_or(Error::EpochLengthNotSet)?;

		// Authenticate both updates against the trusted validator set: this verifies
		// the BLS aggregate signature over each update's `vote_data`.
		let _ = verify_bsc_header::<H, C>(
			&consensus_state.current_validators,
			bsc_client_update_1,
			epoch_length,
		)?;

		let _ = verify_bsc_header::<H, C>(
			&consensus_state.current_validators,
			bsc_client_update_2,
			epoch_length,
		)?;

		// The fraud proof must be bound to the BLS-signed `vote_data`, never to the
		// `attested_header` itself. The header's non-vote fields (e.g. `state_root`,
		// `parent_hash`, `receipts_root`) are not covered by the signature, so a
		// single genuine attestation can be cloned into two distinct-hashing headers
		// that carry the same vote. A genuine BSC equivocation is a slashable double
		// vote: two quorum-signed votes for the same target block number but
		// different target hashes.
		let vote_1 = parse_extra::<H, C>(&header_1)
			.map_err(|_| Error::InvalidFraudProof)?
			.vote_data;
		let vote_2 = parse_extra::<H, C>(&header_2)
			.map_err(|_| Error::InvalidFraudProof)?
			.vote_data;

		if vote_1.target_number != vote_2.target_number {
			Err(Error::InvalidFraudProof)?
		}

		if vote_1.target_hash == vote_2.target_hash {
			return Err(Error::InvalidFraudProof.into());
		}

		Ok(())
	}

pub fn verify_bsc_header<H: Keccak256, C: Config>(
	current_validators: &Vec<BlsPublicKey>,
	update: BscClientUpdate,
	epoch_length: u64,
) -> Result<VerificationResult, Error> {
	let extra_data =
		parse_extra::<H, C>(&update.attested_header).map_err(|_| Error::ParseExtraData)?;
	let source_hash = H256::from_slice(&extra_data.vote_data.source_hash.0);
	let target_hash = H256::from_slice(&extra_data.vote_data.target_hash.0);
	if source_hash == Default::default() || target_hash == Default::default() {
		Err(Error::EmptyVoteData)?
	}

	let validators_bit_set = Bitvector::<VALIDATOR_BIT_SET_SIZE>::deserialize(
		extra_data.vote_address_set.to_le_bytes().to_vec().as_slice(),
	)
	.map_err(|_| Error::DeserializeVoteAddressSet)?;

	// `VALIDATOR_BIT_SET_SIZE` is a fixed 64-bit width; the active
	// validator set is smaller, so bits at positions `>= validators.len()`
	// have no corresponding validator. Setting them would inflate
	// `count_ones()` past the supermajority threshold without any extra
	// validator actually signing.
	if validators_bit_set
		.iter()
		.enumerate()
		.any(|(i, bit)| i >= current_validators.len() && *bit)
	{
		Err(Error::VoteAddressSetBeyondValidatorCount)?
	}

	// We have to use the same threshold specified in the bsc parlia consensus which is 2/3
	// https://github.com/bnb-chain/bsc/blob/da35ee13e2fe38efaeab2d6fb27f112332459b50/consensus/parlia/parlia.go#L557
	let participant_count = validators_bit_set
		.iter()
		.take(current_validators.len())
		.filter(|bit| **bit)
		.count();
	if participant_count < ((2 * current_validators.len()) / 3) {
		Err(Error::NotEnoughParticipants)?
	}

	let source_header_hash = Header::from(&update.source_header).hash::<H>();
	let target_header_hash = Header::from(&update.target_header).hash::<H>();

	if source_header_hash.0 != extra_data.vote_data.source_hash.0 ||
		target_header_hash.0 != extra_data.vote_data.target_hash.0
	{
		Err(Error::HeaderVoteDataMismatch)?
	}

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
