### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` exclusively from HTTP headers, but its `to_signable_string` — the value the HMAC is computed and verified over — returns only the raw request body [1](#0-0) . `Utils::HmacValidator.validate` verifies the HMAC solely against this signable string with `Context.api_secret_key` [2](#0-1) . `Registry.process` accepts the request once that check passes and immediately uses the unauthenticated `request.shop`/`request.topic` header values to route to a handler and populate `WebhookMetadata`, which app code uses to attribute the payload to a merchant/tenant [3](#0-2) , [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e. the shop/topic asserted to the handler should be the same bytes the signature authenticates. Instead the binding that actually holds is `hmac == HMAC(secret, body)` while `shop`/`topic` are read from separate, unsigned headers (`shopify-shop-domain`, `shopify-topic` / `x-shopify-shop-domain`, `x-shopify-topic`) [5](#0-4) . This is precisely the "field acted on but not covered by the HMAC" analog: the body is authenticated, but the tenant-identifying `shop` field that the handler trusts is not part of what's authenticated.

Because the signature is independent of the headers, an attacker who obtains any single genuine `(raw_body, hmac)` pair from a real Shopify webhook delivered to the app (trivially achievable for a public app by installing it on their own store and capturing one webhook delivery) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only recomputes/compares against `@raw_body` [6](#0-5) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged `shop` [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: application code (per the gem's documented usage pattern) is meant to key persistence/business logic off `data.shop` [8](#0-7) . An attacker replaying a validly-signed body under a spoofed shop domain can cause the host application to attribute attacker-controlled webhook content to a victim shop it has never interacted with for that payload, i.e. cross-tenant data injection/confusion, matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Exploitation requires only one legitimately signed webhook body ever observed by the attacker (e.g., from their own store where the same public app is installed) — no access to `api_secret_key`, access tokens, or the target shop is needed. Because the shop/topic headers are never part of the signed material, the replay works against any deployment relying solely on this gem's HMAC check as the authenticity mechanism.

### Recommendation
Include the relevant identity headers (at minimum `shop`, and ideally `topic`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the payload, so `to_signable_string` cannot be satisfied by resending an old body under a new shop/topic. As a defense-in-depth measure, `Registry.process`/`WebhookHandler` consumers should be required or documented to cross-check `request.shop` against a known/installed shop list (with token-bound session) rather than trusting the header value outright.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; app registers `orders/create` at `path`.
2. Shopify sends a legitimate webhook: body `B`, headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H = HMAC(secret, B)`.
3. Attacker captures `(B, H)` (they own the traffic, no interception needed).
4. Attacker POSTs the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` from the header [9](#0-8) .
6. `HmacValidator.validate` recomputes HMAC over `@raw_body` only, matches `H`, returns `true` [10](#0-9) .
7. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, and the application processes/persists data attributed to `victim.myshopify.com` even though it never originated from Shopify for that shop [11](#0-10) .
