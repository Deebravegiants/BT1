### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` value used to attribute that body to a specific merchant tenant is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material [2](#0-1) . Because Shopify apps use a single, shop-independent `api_secret_key` to sign webhooks for every shop that has installed the app, any merchant who has installed the app can generate a genuinely-valid HMAC over an attacker-chosen body (by triggering ordinary store events), then present that body/HMAC pair to the app's webhook endpoint together with an arbitrary victim `shop-domain` header. The signature check passes, and the payload is dispatched to the handler tagged with the victim's shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field using `OpenSSL.secure_compare` [3](#0-2) . For webhooks, `to_signable_string` returns only `@raw_body` [4](#0-3) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers [5](#0-4) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's handler as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) .

The identity binding that should hold is: `shop_that_signed_the_payload == shop_attributed_to_the_payload`. Before the attacker's request: a webhook body signed by shop A's install is only ever delivered by Shopify with shop A's real `shop-domain` header. After the attacker's request: the same valid `(body, hmac)` pair, produced by an attacker who legitimately controls shop A, is replayed by the attacker directly to the app's webhook endpoint with the `shop-domain` header rewritten to shop B (or any other tenant string) — this passes `Utils::HmacValidator.validate` because the header is never part of `to_signable_string`, breaking that equality.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who is a legitimate (but unprivileged, non-staff) user of the Shopify platform — merely someone who can install the app on their own store or otherwise trigger events matching the topics the app registers — can forge webhook deliveries that the host application will process as belonging to a different merchant's shop. Depending on how the host app's `WebhookHandler` uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, sync inventory, issue refunds, or persist customer data), this can result in cross-tenant data corruption or disclosure attributed to the wrong tenant, satisfying the "cross-tenant access" criteria.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on a shop they control (or otherwise cause the app to emit a webhook for a topic it has registered) and then send an HTTP request directly to the app's webhook endpoint with the captured `raw_body`/`hmac-sha256` pair but a substituted `shop-domain` header — no access to `api_secret_key`, access tokens, or any other privileged credential is needed beyond what a normal, permitted app installer already has. The gem's `Utils::HmacValidator` and `Webhooks::Request` provide no mechanism to bind the `shop` header to the signature, so any host application relying on this gem's `Registry.process` for authorization is affected uniformly.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified for webhooks, or otherwise cryptographically bind `request.shop` to the HMAC before it's trusted — e.g., by having `Webhooks::Request#to_signable_string` incorporate the shop header, or by requiring `Registry.process` to cross-check the shop domain against session/tenant records already known to the host app rather than trusting the header unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, giving them the ability to receive genuinely Shopify-signed webhooks for any topic the app has registered (e.g. `products/update`), all signed with the app's single `api_secret_key`.
2. Attacker triggers the event (e.g., edits a product) and captures the resulting webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this is valid per `lib/shopify_api/utils/hmac_validator.rb`.
3. Attacker POSTs directly to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes [7](#0-6) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the host app to process attacker-controlled data as if it originated from the victim's shop.
