Confirmed: the HMAC signature in `ShopifyAPI::Webhooks::Request` covers only the raw request body via `to_signable_string` [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all pulled unauthenticated directly from HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then dispatches the handler using these unsigned header-derived values [3](#0-2) , and `HmacValidator.validate` never inspects `shop`/`topic`, only `to_signable_string` [4](#0-3) .

### Title
Webhook `shop`/`topic`/`webhook_id` Metadata Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking the HMAC of the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are subsequently handed to the app's handler are read directly from HTTP headers, which are entirely outside the HMAC-signed content. Any actor who can obtain one genuine `(raw_body, hmac)` pair — trivially available to anyone who can install the app on their own shop — can replay that same body/HMAC pair while substituting arbitrary `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers, causing the app to process attacker-controlled metadata as if it authentically originated from a different (victim) shop or topic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are derived purely from `shopify_header` lookups on caller-supplied headers [2](#0-1) , with no cryptographic binding to those values. `HmacValidator.validate` computes `compute_signature` over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the `hmac` header value using `OpenSSL.secure_compare` [5](#0-4) . `Registry.process` gates entirely on this body-only check, then builds `WebhookMetadata` from `request.topic`, `request.shop`, and `request.webhook_id` — none of which were included in the signed payload — before invoking the registered handler [6](#0-5) .

The equality this breaks is: **shop authenticated (the tenant whose secret produced a valid HMAC over the body) ≠ shop trusted (the `shop` value the handler receives and acts on)**. Before the attack: a legitimate webhook for shop A arrives with body B and valid HMAC(B); the handler correctly attributes B to shop A. After the attack: an adversary captures a legitimate `(B, HMAC(B))` pair for their own shop A (which they control, e.g. a free/dev store with the app installed), then replays it to the app's webhook endpoint with `shopify-shop-domain: victim-shop.myshopify.com` and any desired `shopify-topic`. `HmacValidator.validate` still succeeds because it only recomputes the signature over `B`, and the handler is invoked with `shop: "victim-shop.myshopify.com"` — a value the signer never attested to.

### Impact Explanation
This breaks the tenant-identity binding that webhook handlers rely on to attribute incoming events to the correct merchant. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop records, triggering per-shop side effects, or looking up sessions/data by `shop`) can be made to act on a victim shop's identity using attacker-supplied body content, and to spoof arbitrary webhook `topic`s from a single captured payload/signature pair. This is a cross-tenant boundary violation: the identity (`shop`) that the handler trusts is not the identity the HMAC actually attests to.

### Likelihood Explanation
An attacker only needs the ability to install the target app on any shop they control (including free development stores) and to trigger any webhook event to capture one valid `(raw_body, hmac)` pair — no access token, `client_secret`, or privileged access to the victim is required. The replay itself is a single unauthenticated HTTP POST to the app's public webhook route with forged `shopify-shop-domain`/`shopify-topic` headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the body), or require the gem/host app to validate that the `shop` header corresponds to a shop with a known, previously-established session/installation before dispatching to handlers. At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be trusted as authenticated unless independently cross-checked against an installed-shop registry.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) to receive a legitimate request with raw body `B` and header `X-Shopify-Hmac-SHA256: HMAC(B)`.
2. Replay to the app's webhook endpoint:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-SHA256: <captured HMAC(B)>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <anything>

   <same raw body B>
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `B` against the signature [5](#0-4) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6) , despite the body/signature having been produced for `attacker.myshopify.com`, not the victim.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
