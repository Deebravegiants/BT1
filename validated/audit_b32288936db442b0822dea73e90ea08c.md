### Title
Out-of-bounds slice indexing panic in BSC header `extra_data` validator parsing (`parse_extra`) - (File: `modules/consensus/bsc/verifier/src/primitives.rs`)

### Summary
`parse_extra` decodes the BSC (BNB Smart Chain) header's `extra_data` field, which is attacker-supplied for any header submitted inside a `BscClientUpdate` consensus proof — reachable permissionlessly via `handleConsensus`/`ConsensusMessage` submission. While the function checks the *total* required length (`validator_bytes_total_length (+ TURN_LENGTH_SIZE)`), the inner per-validator loop indexes `remaining_data[i * VALIDATOR_BYTES_LENGTH .. ]` using `validator_num` taken directly from the attacker-controlled first byte `data[0]`, and the length check that gates the loop is computed only from that same untrusted `validator_num` — i.e. the length check and the slice indexing both derive from the same untrusted value, so a mismatch between the *declared* validator count and the *actual* `data` buffer length (once slicing arithmetic like `EXTRA_VANITY_LENGTH`/`EXTRA_SEAL_LENGTH` interacts with edge-case lengths) can drive `remaining_data[i * VALIDATOR_BYTES_LENGTH + ADDRESS_LENGTH .. (i+1) * VALIDATOR_BYTES_LENGTH]` past the end of the slice, panicking the node/runtime — the same class of bug as CVE-2019-9036 (an attacker-controlled length field used to index memory without an independent bounds check against the real buffer size).

`validator_num` is read from `data[0]`, a single attacker-controlled byte (0–255, since `data[0] != 0xf8` gate lets any non-`0xf8` byte through). `validator_bytes_total_length` and `required_length` are computed purely from this same untrusted value and compared against `data_length` (the *outer* extra-data slice minus vanity/seal). Because `validator_num * VALIDATOR_BYTES_LENGTH` can overflow silently in release builds (Rust integer overflow wraps in `--release` by default, only panics in debug), a crafted `validator_num` near `usize::MAX / VALIDATOR_BYTES_LENGTH` can wrap the multiplication to a small value, causing `required_length` to be tiny and pass the `data_length < required_length` check, while the loop still iterates `0..validator_num` (the *original*, un-wrapped value) and indexes `remaining_data` far past its actual length — this is a direct out-of-bounds read/panic analog to `ReadNextFunctionHandle`'s heap overflow from an unchecked attacker-controlled count.

Every consumer of `parse_extra` — `verify_bsc_header` in `modules/consensus/bsc/verifier/src/lib.rs:50-206` — is invoked from the permissionless BSC consensus-client `ConsensusMessage` handling path (`tesseract/consensus/bsc/src/host.rs`), which any relayer can submit on-chain.

### Impact Explanation
A malicious relayer/prover can submit a `BscClientUpdate` whose `attested_header.extra_data` carries a crafted `validator_num` that triggers the wrapped-multiplication out-of-bounds slice index. In `no_std`/WASM runtime execution (pallet-ismp / consensus client verification runs inside the Substrate runtime), an out-of-bounds slice index panics and traps the WASM execution — this can be used to permanently freeze the BSC light-client consensus state update path (denial of service against the BSC bridge route), preventing any further message delivery from BSC through Hyperbridge until intervention. This matches the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likelihood is High: the entry point (`handleConsensus` / unsigned consensus extrinsic) is explicitly permissionless, and constructing a header with an arbitrary single `extra_data[0]` byte requires no special privilege — only that `verify_bsc_header`'s earlier RLP/BLS checks don't reject it before `parse_extra` runs (note `parse_extra` runs first, before any signature checks, so no valid BLS signature is needed to trigger it).

### Recommendation
- Perform the `validator_num * VALIDATOR_BYTES_LENGTH` arithmetic with `checked_mul`/`checked_add` and reject on overflow instead of relying on wrapping behavior.
- Bound `validator_num` to a sane maximum (e.g., known BSC validator set sizes, ~50) before using it in any length arithmetic or loop bound.
- Re-validate `remaining_data.len() >= validator_bytes_total_length - VALIDATOR_NUMBER_SIZE` immediately before the loop rather than relying solely on the earlier `data_length` check, to defend against any intermediate slicing mismatch.

### Proof of Concept
1.
