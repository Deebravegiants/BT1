This confirms the finding. `WebhookMetadata.shop` (defined at [1](#0-0) ) is populated directly from `request.shop` and handed unverified to every `WebhookHandler#handle` implementation, so any app that keys per-tenant logic off `data.shop` inherits the forged identity.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw JSON body, never the HTTP headers [2](#0-1) . `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header [3](#0-2) [4](#0-3) . Because the signature only binds the body, the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers can be freely altered without invalidating the HMAC check, then `request.shop` is read straight from that unauthenticated header [5](#0-4)  and forwarded as ground truth to the handler via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [6](#0-5) .

### Finding Description
This is the same root cause class as the Infrared report: an identity field (`GOVERNANCE_ROLE` grantee there, tenant `shop` here) is trusted for privileged/attributed logic without being cryptographically bound to the thing that was actually verified. In `AuthQuery` (OAuth callback) the `shop` field *is* included in `to_signable_string` and thus HMAC-protected [7](#0-6) , but the analogous `Webhooks::Request#shop` is not — it is read from a header that sits entirely outside the signed payload.

Any developer using an app that has this gem installed can obtain a legitimately-signed webhook body/HMAC pair for their own store (e.g. by triggering `app/uninstalled`, `orders/create`, or any other subscribed topic on a shop where they control the app installation and can freely produce order/webhook activity). They then replay that exact `raw_body` and its valid `hmac-sha256` value to the app's public webhook endpoint, but substitute the `shop-domain` header with an arbitrary victim shop's `myshopify.com` domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop [8](#0-7) . Any handler that uses `data.shop` to select which tenant's session/access token/database row to read or write (the documented, expected usage pattern per `docs/usage/webhooks.md` [9](#0-8) ) will act on the wrong tenant, breaking the equality `shop authenticated by HMAC == shop attributed to the webhook payload`.

### Impact Explanation
High/Critical depending on handler logic: this allows an unprivileged attacker who controls only their own (possibly free/dev) shop installation to forge webhook events attributed to a different merchant's shop domain, enabling cross-tenant data confusion (e.g. triggering `app/uninstalled` cleanup for a victim shop, or injecting attacker-controlled `orders/create` body content associated with a victim's shop record) purely through this gem's own `Webhooks::Registry`/`Request` verification logic.

### Likelihood Explanation
High: no secret, token, or privileged account is required beyond the ability to install the app on an attacker-owned shop (a normal, unprivileged capability for any Shopify app), and the header substitution requires only a basic HTTP client capable of sending a raw POST with modified headers.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body — e.g., change `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to concatenate/canonicalize the relevant headers with the body before hashing, and update `HmacValidator`/tests accordingly.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`) to receive a legitimate `raw_body` + `x-shopify-hmac-sha256` pair signed with the app's `api_secret_key`.
2. Replay the captured `raw_body` unchanged to the app's webhook endpoint, keeping the original `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` (via `to_signable_string`) and succeeds [2](#0-1) .
4. The registered handler receives `WebhookMetadata#shop == "victim.myshopify.com"` [6](#0-5) , causing the app to act on the victim tenant despite the payload only ever being authenticated for the attacker's own shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.     )
    render json: {success: true}.to_json
  end
end
