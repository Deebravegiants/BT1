### Title
Webhook Header Spoofing via HMAC Coverage Gap — Cross-Tenant Shop Impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates that body against the `X-Shopify-Hmac-Sha256` header using `Utils::HmacValidator.validate`. The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream by the app's handler are read directly from unauthenticated HTTP headers that are never included in the signed payload. Any party who can obtain one genuine, HMAC-signed webhook body/signature pair for the app (trivially available to any merchant who installs the app, since the same `client_secret`/`api_secret_key` signs every shop's webhooks) can replay that exact body+HMAC while substituting the `X-Shopify-Shop-Domain` header for a victim shop, producing a request that `Registry.process` accepts as authentic and hands to the app's handler tagged with the victim's shop identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two members required by `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns `@raw_body` exclusively — headers play no part in the signature computation. `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from `@headers` with no cross-check against the signed body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The HMAC validator itself computes and compares only `verifiable_query.to_signable_string`: [4](#0-3) 

The documented contract for this API is explicit that "this will verify the request did indeed come from Shopify": [5](#0-4) 

That promise is broader than what the implementation actually checks: it protects the body's integrity, but not the origin-identifying `shop` value that the app is told to trust as `data.shop` in its handler. The identity binding broken is: **shop the handler is told the webhook came from == shop covered by the HMAC**. In fact, `shop` (an unauthenticated header) is never bound to the HMAC-signed bytes (only `@raw_body` is), so the two sides of that equality diverge whenever an attacker swaps the header.

### Impact Explanation
An attacker who has installed the app on their own shop (an ordinary, unprivileged merchant — no special credentials, no leaked secrets) legitimately receives real webhooks addressed to their own callback URL, each with a valid `X-Shopify-Hmac-Sha256` signature computed with the app's shared `api_secret_key`. Because the signature covers only the raw body, the attacker can resend that exact body/signature pair to the app's webhook endpoint while changing `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) to name a victim shop. `HmacValidator.validate` still returns `true` (the body and signature match), and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload originated from the victim shop. Any app logic that trusts `data.shop` to select which tenant's records to update, credit, or notify (a normal and expected usage pattern per the gem's own docs example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to attribute attacker-controlled data to another merchant's tenant — a cross-tenant data-integrity/confusion issue reachable by any unauthenticated internet user with a self-service Shopify Partner/merchant account, without leaking or possessing anyone else's credentials.

### Likelihood Explanation
High. No secret material, session, or privileged access is required beyond installing the target app on an attacker-owned test shop (self-serviceable) to harvest one valid signed webhook. Only a single crafted HTTP POST to the app's public webhook endpoint is needed to spoof the shop attribution — this is a direct, mechanically simple attack once the gap in HMAC coverage is understood.

### Recommendation
Include the Shopify-supplied `shop`, `topic`, and `webhook_id`/`api_version` header values in the signable payload validated by the HMAC check (or, at minimum, verify that the `shop` header corresponds to an active, previously registered session/webhook subscription for the given `webhook_id` before invoking the handler), so the identity used downstream is cryptographically bound to the same bytes the HMAC protects.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends the attacker a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (body `B` and `X-Shopify-Hmac-Sha256: H` unchanged).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed and passed to `Registry.process`.
5. `Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), and the app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"`, despite the request never having been signed for, or sent by Shopify on behalf of, that shop.
