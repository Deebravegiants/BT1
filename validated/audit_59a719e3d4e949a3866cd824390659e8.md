### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the shop identity that the handler acts on (`request.shop`) is read from an HTTP header that is never included in the signed content. An attacker who possesses one valid (body, HMAC) pair — trivially obtainable by installing the app on their own store and receiving a real webhook — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will report the request as valid for the attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for webhooks that method returns just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all parsed straight from HTTP headers, none of which participate in `to_signable_string`: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body authenticity) before handing the header-derived, unauthenticated `request.shop` straight to the app's handler: [3](#0-2) 

This breaks the intended identity binding: `hmac-signed bytes == body` but the gem (and by extension the host app, which is only given this gem's verified `WebhookMetadata.shop`) treats it as if `hmac-signed bytes == (body, shop)`. Any request carrying a body/HMAC pair that is valid for shop A will also be accepted as valid — and attributed to whatever shop the attacker puts in the `shop-domain` header — because the header is never bound to the signature.

### Impact Explanation
This is a cross-tenant identity confusion at the gem's core webhook-verification boundary. An unprivileged attacker who can install the app for their own store (or otherwise obtain a single legitimately-signed webhook body/HMAC pair for any topic, e.g. `app/uninstalled`) can resend that exact body to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. `Registry.process` will pass HMAC validation and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, causing the app to perform shop-scoped actions (data deletion/redaction, session/token teardown on `app/uninstalled`, etc.) against a tenant the attacker never authenticated for.

### Likelihood Explanation
Any app that installs on at least one shop (which any developer/attacker can do for free via Shopify's dev store program) can obtain a valid signed webhook body. Because `Request` parses `shop` from a header that isn't part of the signable content, forging a cross-tenant request only requires copying the previously received body/HMAC and swapping one header — no cryptographic material or victim credentials are needed.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the body before trusting `request.shop`/`WebhookMetadata.shop` for shop-scoped operations, mirroring the fix pattern of binding the acting identity to the verified data (as in the analogous `set_freeze_status` access-control fix referenced in the report).

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; Shopify sends a legitimate webhook, e.g. for `app/uninstalled`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B`).
2. Attacker resends the same request to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`, since that header is also unsigned) while keeping body `B` and header `H` unchanged.
3. `Utils::HmacValidator.validate` recomputes the signature over `B` only [1](#0-0)  — it matches `H`, so `Registry.process` proceeds and calls the handler with `shop: "victim.myshopify.com"` [3](#0-2) , causing the app to act on the victim shop's data despite the attacker never having any relationship with that shop.
