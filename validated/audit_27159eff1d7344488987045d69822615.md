### Title
User-Centric Signup Bypasses Backend Enrollment Verification and Fraud/Duplicate Detection - (File: src/plans/mod.rs)

### Summary
For "orb-centric" signups, the orb calls `enroll_user::Plan::run`, which computes a cryptographic signature over the iris data and submits it to the backend via `signup_post::request`, then polls `signup_poll::request` until the backend confirms success — this backend round-trip is where duplicate-signup, fraud, and legacy-signup checks are enforced (`enroll_user.rs:161-168`: "Backend duplicates ... Backend inflight matches ... Backend detected fraud"). For "user-centric" signups, this entire enforcement path is skipped: `do_signup` locally derives `success` purely from the orb's own `signup_reason` without ever contacting the backend for verification.

### Finding Description
In `do_signup` (`src/plans/mod.rs`), after the biometric pipeline runs, the code branches on `user_centric_signup`: [1](#0-0) 

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(
        orb,
        debug_report,
        &capture,
        pipeline.as_ref(),
        signup_reason,
    ))
    .await
    .is_success()
};
```

- The `else` branch (`self.enroll_user`) invokes `enroll_user::Plan::run`, which signs the iris code with the secure element (`make_signature`, `src/plans/enroll_user.rs:290-304`) and submits the signup to the backend (`signup_post::request`, `src/backend/signup_post.rs:100-161`), then polls (`signup_poll::request`) until the backend explicitly reports `Completed`/`success: true`. The comment in the polling loop explicitly documents that this backend interaction is the authoritative point where "Backend duplicates," "Backend legacy signup requests," "Backend inflight matches," and "Backend detected fraud" are caught (`src/plans/enroll_user.rs:161-168`).
- The `if` branch (`user_centric_signup == true`) never calls `enroll_user` at all. It fabricates an `enroll_user::Status` and a `success` boolean purely from the *local* `signup_reason`, which itself is computed from `detect_fraud` — a function that, in this build, is a no-op (`N_FRAUD_CHECKS = 0`, see `src/plans/fraud_check.rs:10-12` and `detect_fraud`'s `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` comment, `src/plans/mod.rs:1390-1406`).
- `user_centric_signup` originates from `backend::user_status::UserData`, which is populated from `authenticated_app_data` returned by the backend/app during QR verification (`src/backend/user_status.rs:145-246`, field `user_centric_signup` at line 242). The only guard against this bypass is the backend-configured `ignore_user_centric_signups` flag (`src/config.rs`, `src/backend/config.rs:67`), which is off by default (`ignore_user_centric_signups: false` in `Config::default`, `src/config.rs:436`).

This is structurally the same class of bug as the reported `L2USDCGateway` issue: one code path (orb-centric enrollment) consistently invokes the enforcement mechanism (backend signature submission + duplicate/fraud polling), while the parallel path performing the equivalent action (user-centric enrollment) never calls it, silently skipping the check instead of enforcing it.

### Impact Explanation
When a signup is marked `user_centric_signup`, the orb never submits the iris signature to the backend and never gives the backend a chance to detect duplicate enrollments, in-flight matches, or backend-side fraud for that signup. The orb unilaterally decides "success" based solely on its own local pipeline result and a fraud-check function that performs no checks in this build. This allows a signup to be reported as fully successful without any backend-side duplicate/fraud enforcement, potentially resulting in unauthorized or duplicated identity enrollment (cross-signup state bleed) that the backend-side rate/fraud-limiting mechanism was designed to prevent.

### Likelihood Explanation
Reachability depends on `user_centric_signup` being set to `true` in the QR-code-derived `UserData`, which is controlled by the app/backend response rather than directly forged by the orb operator. However, this flag is intended to be used in production self-custody signup flows (there is a dedicated backend kill-switch `ignore_user_centric_signups` to disable it), meaning the bypass path is a real, reachable, non-test production code path rather than a debug-only or CLI-gated feature (unlike `skip_fraud_checks`, which is gated behind `allow-plan-mods` and excluded by scope rules). Any unprivileged party able to influence the app's declared `user_centric_signup` value (or exploit a backend that doesn't proactively set `ignore_user_centric_signups`) can trigger the bypass.

### Recommendation
Do not allow a signup to be marked successful purely on local orb-side reasoning. For user-centric signups, still submit the relevant identity/signature data to the backend (or an equivalent lightweight verification call) so backend-side duplicate/fraud detection is enforced symmetrically with the orb-centric path, rather than gating this enforcement behind an opt-out flag (`ignore_user_centric_signups`) that defaults to *not* protecting the path.

### Proof of Concept
Conceptual PoC (based on code inspection only, not executed):
1. Complete biometric capture/pipeline normally so `signup_reason == SignupReason::Normal`.
2. Ensure the backend-returned `UserData.user_centric_signup == true` (and the orb's config has `ignore_user_centric_signups == false`, the default).
3. Observe that `do_signup` takes the `if` branch at `src/plans/mod.rs:639-645`, setting `success = true` without ever calling `enroll_user` — i.e., without ever calling `signup_post::request`/`signup_poll::request`, and thus without giving the backend any opportunity to reject the signup as a duplicate/fraud/in-flight match.

Note: I was unable to fully confirm from the available code index whether `user_centric_signup` can be influenced directly by an unprivileged actor (vs. only set by a trusted backend after its own validation), since `authenticated_app_data` is asserted to come from the backend after `user_data.verify(user_data_hash)`. This uncertainty should be verified with a full Devin session that can trace `orb_qr_link::UserData` generation end-to-end.
