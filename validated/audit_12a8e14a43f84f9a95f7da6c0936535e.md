Audit Report

## Title
Relayer reward paid regardless of message dispatch success on Ethereum - (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` pays the relayer/reward account `order.fee` whenever `order.fee > 0`, without ever inspecting `receipt.success`, even though `DeliveryReceipt` explicitly carries a `success: bool` decoded from the Ethereum `InboundMessageDispatched` event indicating whether the message actually dispatched successfully on the Gateway contract. This decouples reward payment from the field whose stated purpose is to record dispatch outcome.

## Finding Description
`DeliveryReceipt` is defined with a `success` field sourced from the on-chain Ethereum event `InboundMessageDispatched(nonce, topic, success, reward_address)`: [1](#0-0) 

`submit_delivery_receipt` verifies the event proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt`, and forwards it to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` then checks the gateway address, resolves the reward account, fetches the `PendingOrder` by nonce, and pays `order.fee` unconditionally whenever it is nonzero — `receipt.success` is never read anywhere in this function: [3](#0-2) 

This matches the claim precisely: the guard checked is only "was a valid proof of the event submitted," not "did the event report success." The existing integration test only exercises the `success: true` path and confirms the reward is paid: [4](#0-3) 

No test in the repo exercises `success: false` for `DeliveryReceipt`/`process_delivery_receipt` — the `success: false` occurrences found elsewhere in the indexed tests (e.g. `snowbridge_v2_outbound_edge_case.rs`) relate to unrelated `pallet_message_queue::Event::Processed{ success: false }` XCM-processing outcomes on the parachain side, not to the Ethereum delivery receipt at all. Nothing in the reviewed code paths contradicts the claim.

## Impact Explanation
Because `order.fee` (the fee associated with the message when it was queued in `do_process_message`) is paid out purely based on `order.fee > 0` and a valid Gateway-address/proof check, any relayer submitting a valid receipt collects the full fee even when `receipt.success == false`, i.e., even when the Gateway contract on Ethereum reports the inbound message dispatch failed. This breaks the intended incentive that rewards should track successful delivery, and could drain reward funds for deliveries that did not achieve the intended cross-chain effect. This is a real accounting/incentive-alignment defect in in-scope Substrate pallet code, not a node/governance/admin-only issue — the extrinsic is callable by any signed relayer.

## Likelihood Explanation
Triggering the code path requires no privileged role — any account that can submit a validly-proved `EventProof` for the `InboundMessageDispatched` event can call `submit_delivery_receipt`, and reward payment follows automatically once `order.fee > 0`. The exact real-world conditions producing `success == false` (e.g., destination-side revert unrelated to the relayer, or something the relayer can influence, such as gas parameters) reside in the Ethereum Gateway/Solidity contract, which is out of scope for this Rust codebase and could not be verified here. Consequently, likelihood that a relayer can *deliberately* induce `success == false` while still collecting reward is unconfirmed, but the code-level defect (reward paid without checking `success`) is independently verifiable and reproducible whenever a `success: false` receipt is legitimately produced by the Gateway contract for any reason (e.g., a bug, gas exhaustion in the destination call, or a malformed/reverting command), regardless of attacker intent.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `T::RewardPayment::register_reward` — e.g., only pay the full/normal fee when `receipt.success == true`, and either withhold, reduce, or route to a separate handling path when `receipt.success == false`, consistent with the field's documented purpose of representing dispatch outcome.

## Proof of Concept
No PoC exercising `success: false` for `DeliveryReceipt`/`process_delivery_receipt` exists in the indexed repository contents. A concrete unit test would need to be added to `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` constructing a `PendingOrder` with `fee > 0`, then calling `Pallet::process_delivery_receipt` with a `DeliveryReceipt { success: false, .. }`, and asserting that `T::RewardPayment::register_reward` is still invoked (confirming the unconditional payment) — this would need to be written and run to fully confirm behavior, since the existing repo tests only cover the `success: true` case.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
