### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the `shop` attribute that the gem hands to application handlers as the trusted tenant identifier is read from an unauthenticated HTTP header. Any unprivileged internet user who has ever received one genuine webhook for a shop they control can replay that same body/signature pair to the app's public webhook endpoint with a forged `shop-domain` header, causing the app to process the payload as if it belonged to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never fed into the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which in turn hashes `verifiable_query.to_signable_string` (i.e. the body only) and compares it to the `hmac` header via `OpenSSL.secure_compare`: [4](#0-3) [5](#0-4) 

After this check passes, `request.shop` (the unauthenticated header value) is forwarded verbatim into `WebhookMetadata`, which the gem's own documentation describes as the verified "shop domain of the webhook" that a handler should use to attribute the payload to a tenant: [6](#0-5) [7](#0-6) 

The identity binding that should hold is:
`shop attributed to payload (WebhookMetadata#shop)` == `shop that actually produced the HMAC-signed body`

Because the HMAC only covers `raw_body`, this equality is never enforced. `shop` is a completely independent, attacker-controlled field.

**Attack path (no MITM, no client_secret required):**
1. Attacker becomes a normal merchant of the target app (any free/dev Shopify store — no special privilege) and legitimately receives one real webhook for their own shop, e.g. body `B` with a valid `x-shopify-hmac-sha256: H` computed by Shopify over `B` using the app's shared secret.
2. Attacker sends their own direct HTTP POST straight to the app's public webhook route (this route is just a plain internet-facing HTTP endpoint, as shown in the gem's own docs) reusing `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` happily parses this (only checks the three headers exist), `HmacValidator.validate` succeeds because `B`/`H` are still a valid pair, and `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`.
4. The host application, following the gem's documented contract that `data.shop` is the authenticated shop for the webhook, stores or acts on attacker-supplied data (`B`) under the victim shop's tenant context — e.g. writing order/customer data into the victim's records, or triggering shop-scoped automation using the victim's already-stored access token.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged user can make the application attribute arbitrary attacker-chosen webhook content to any other shop known to be using the app, without needing that shop's credentials, the app's `client_secret`, or any network-level interception. This falls under the "Critical - cross-tenant access" impact bucket, since it breaks the tenant isolation the gem's `process` API is documented to guarantee ("will verify the request did indeed come from Shopify").

### Likelihood Explanation
Likelihood is high for any app that (a) is installed by more than one shop and (b) uses `data.shop` from `WebhookMetadata` (as the gem's own documentation instructs) to decide which tenant's record to update. The attacker only needs to be an ordinary merchant of the app (trivial, e.g. free developer store) to obtain one genuine `(body, hmac)` pair, and target shop domains are guessable/enumerable (`*.myshopify.com`).

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the shop to the signature (e.g. validate that the resolved shop has a currently registered webhook subscription with the matching id/topic before dispatch), so that the header cannot be swapped independently of the signed body. At minimum, update the documentation to make clear that `data.shop` is *not* covered by the HMAC guarantee, and that host applications must independently verify shop-body correspondence (e.g. by cross-checking `webhook_id` against Shopify's API, or by parsing the shop domain out of an authenticated field).

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body   = '{"id":1,"note":"legit order for attacker-shop"}' # genuine payload attacker received for their own shop

hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
hmac_b64    = Base64.encode64(hmac_digest)

# Attacker crafts a direct HTTP POST to the app's public webhook endpoint,
# reusing the legitimate (body, hmac) pair but forging the shop header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac_b64,
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # <-- forged, unauthenticated
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes HMAC validation because only `body` is signed:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}, ...))
```
Running this against `ShopifyAPI::Webhooks::Registry.process` (mirroring the existing `test_process_with_new_format_headers` test setup) demonstrates that the handler receives `data.shop == "victim-shop.myshopify.com"` even though the signed body and signature were generated for a completely different (attacker-controlled) shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
