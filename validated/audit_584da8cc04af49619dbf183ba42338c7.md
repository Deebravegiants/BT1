### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to attribute an incoming webhook purely from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. Any party who can produce a validly-signed webhook body (e.g., by installing the app on their own store and triggering a webhook) can resend that exact body with an arbitrary `shop` header value and have it accepted as coming from a different shop, since the signature never binds to the `shop` field.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of that signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` for dispatch to the app's handler, without any further binding check between the verified body and the claimed shop: [3](#0-2) 

This is a direct violation of the equality the gem should enforce: `shop authenticated by HMAC == shop acted upon by the handler`. In contrast, the gem gets this right elsewhere: `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameter set, so the OAuth callback's `shop` claim is cryptographically bound to the signature: [4](#0-3) 

No equivalent binding exists for webhooks — `HmacValidator.validate` just calls `verifiable_query.to_signable_string`, which for `Request` never touches `shop`: [5](#0-4) 

### Impact Explanation
Because the same `api_secret_key` is used across all shops that install the app, and the HMAC only signs the body, any user who can trigger a webhook for their own shop (a normal, unprivileged install — no special credentials needed beyond installing the app they're attacking through) can capture that body+signature pair and replay it to the app's public webhook endpoint with the `shop` header swapped to point at a victim shop. Since `Registry.process` passes `request.shop` straight into `WebhookMetadata` for the host app's handler, the host app will process attacker-controlled body content as if it originated from — and pertains to — the victim shop. This is a cross-tenant identity confusion: data intended to be scoped to one merchant tenant can be attributed to and acted upon for another tenant purely by manipulating an unauthenticated header.

### Likelihood Explanation
The only prerequisite is the ability to install the app on any shop (including the attacker's own free/dev store) to obtain one legitimately-signed webhook body, then issue a raw HTTP POST to the app's public webhook receiver with a forged shop-domain header. No access token, `client_secret`, or privileged account is required — this is squarely within reach of an unprivileged internet user.

### Recommendation
Include the shop identity (and other webhook metadata used for authorization decisions, such as topic) in the HMAC-signed material, or otherwise cryptographically bind the claimed `shop` header to the verified body — e.g., have `Request#to_signable_string` incorporate the shop/topic headers, mirroring the approach already used in `Auth::Oauth::AuthQuery`. Alternatively, require the host application to independently confirm that the requesting shop has an active, matching session/webhook registration for the received topic before trusting `request.shop`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a valid raw body `B` and its HMAC `H = HMAC-SHA256(api_secret_key, B)`.
2. Send a POST request directly to the app's webhook endpoint with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <base64(H)>`
   - `x-shopify-shop-domain: victim.myshopify.com`
   - body: `B`
3. `Utils::HmacValidator.validate` succeeds because it only re-derives the HMAC over `B` (see `to_signable_string` in `lib/shopify_api/webhooks/request.rb`), not over the shop header.
4. `Registry.process` dispatches to the handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the actual payload `B` belongs to the attacker's own shop, achieving cross-tenant attribution of forged data.
