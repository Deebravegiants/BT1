### Title
Webhook shop identity spoofing — HMAC signs only the raw body, not the `X-Shopify-Shop-Domain` header, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates covers only the raw request body, never the shop header. This breaks the binding "shop authenticated == shop acted upon," letting anyone who can produce one valid `(body, hmac)` pair for the app (e.g. the operator of their own shop, who legitimately receives real webhook deliveries for their own store) replay that exact body/HMAC pair while substituting an arbitrary victim `X-Shopify-Shop-Domain` value.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string` (the body), using `Context.api_secret_key`: [2](#0-1) 

`Request#shop` is read straight from the `shop-domain` header, which is not part of the signed content: [3](#0-2) 

`Registry.process` only checks the HMAC before dispatching, then passes the unauthenticated `request.shop` value straight into the handler payload as the tenant identifier: [4](#0-3) 

Before/after equality that should hold but does not:
`hmac_verified_shop == shop_delivered_to_handler` — before the attacker's tampering both sides are equal (the genuine webhook delivery), but the gem never actually checks this equality: HMAC verification proves only that *some* accepted `(body)` combination is genuine for *some* shop, not that the specific `shop-domain` header accompanying this HTTP request is the one Shopify attached to that signed body. An attacker who has one genuine `(raw_body, hmac)` pair (trivially obtainable by installing the app on their own shop and capturing their own webhook delivery) can retransmit the identical body and HMAC to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header replaced by any victim shop domain. `HmacValidator.validate` still returns `true` (it never looked at the header), and `Registry.process` calls the handler with `shop: <attacker-chosen victim domain>`.

### Impact Explanation
This is a cross-tenant identity-binding break: the app's webhook handler is invoked believing the event pertains to shop B while the payload/signature only proves authenticity for the sender's own shop A's data. Any host application that uses `WebhookMetadata#shop` to look up per-shop state, credentials, or to gate business logic (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into processing attacker-controlled data (attacker's own webhook body/topic) under a victim shop's identity — e.g., triggering app-side actions, cache/database writes, or logic keyed to the wrong tenant. This matches the "Critical - cross-tenant access" impact category since it lets an unprivileged (but app-installing) attacker impersonate an arbitrary other merchant to the app's own webhook-processing logic.

### Likelihood Explanation
High feasibility: any actor can install the target app on their own free/dev store (no special privilege needed beyond normal app installation), receive a real webhook with a valid signature, and then freely replay that HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — nothing in `Request` or `Registry` ties the header to the signature. No access token, secret, or TLS interception is required.

### Recommendation
Bind the shop (and other identifying headers such as `topic`, `webhook-id`) into the signable content actually verified, or otherwise cross-check the `shop-domain` header against an independently trusted source (e.g., the registered webhook's known shop, or a per-shop callback URL) before trusting it in `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must never be used as a tenant/authorization key without independent verification, and consider deriving the HMAC signable string over `body + shop-domain` (mirroring how `AuthQuery#to_signable_string` includes `shop` in the signed OAuth-callback string) so verification actually proves the shop identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and configures a webhook receiver they control to log deliveries.
2. Shopify sends a legitimate webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's real secret), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over body `B` only, matches `H`, returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) dispatches to the handler with `shop: "victim.myshopify.com"` and the attacker's chosen body, even though Shopify never issued this event for `victim.myshopify.com`.
