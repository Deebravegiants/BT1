### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field (and `topic`, `webhook_id`, `api_version`) directly from HTTP headers, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw body only. This breaks the binding `hmac-verified bytes == bytes the handler acts on`, exactly the class of bug the reference report describes (a field acted upon but not covered by the integrity check).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but the same object exposes `shop`, `topic`, `webhook_id`, and `api_version` sourced straight from attacker-controllable headers, unauthenticated by the signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata passed to the app-registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [4](#0-3) 

So the equality the gem should enforce is:
`hmac_signed_content == content used to attribute the event to a shop`

but instead it enforces:
`hmac_signed_content == raw_body` while `shop_used_by_handler == header value, unrelated to the signature`.

Because the client secret (and therefore the HMAC key) is identical across every shop that has installed the same app, any party who has legitimately installed the app on their own shop can capture one valid `(raw_body, hmac)` pair delivered to them, and then resend it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header. The signature still validates because those headers are outside the signed content, and `Registry.process` will dispatch the handler with the attacker-chosen `shop`/`topic`, not the shop that actually originated the payload.

### Impact Explanation
This crosses a tenant boundary: an unprivileged-but-legitimate installer of the app on Shop A can make the host application process events as if they came from Shop B, without ever having credentials for Shop B. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, billing/subscription webhooks), this can trigger cross-tenant state changes, data deletion, or misattribution — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker have installed the target app on any shop (a normal, unprivileged action any Shopify merchant can take) and capture one webhook delivery for their own shop; no access token, `api_secret_key`, or privileged account is required, and no TLS interception or code changes on the receiver side are needed beyond the gem's own documented flow.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) so that `shop`, `topic`, `webhook_id`, and `api_version` are included in what is HMAC-verified, or otherwise cryptographically bind the header-sourced attribution fields to the signed payload before they are trusted and forwarded to handlers.

### Proof of Concept
1. Install the target app on attacker-controlled Shop A; receive a legitimately signed webhook `POST` with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`, `x-shopify-topic: orders/create`.
2. Replay the identical `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (and/or a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` builds successfully (all required headers present) and `Utils::HmacValidator.validate(request)` returns `true` because it only re-hashes `@raw_body`, per [1](#0-0)  and [4](#0-3) .
4. `Registry.process` invokes the app's handler with `shop: "shop-b.myshopify.com"`, `topic: "orders/create"` as if the event genuinely originated from Shop B, per [3](#0-2) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
