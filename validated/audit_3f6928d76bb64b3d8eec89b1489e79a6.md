### Title
Webhook shop attribution (`shop-domain` header) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, but the `shop` value that identifies which merchant/tenant the webhook belongs to is taken from an HTTP header that is never included in the HMAC-signed material. An attacker who can obtain one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` (e.g., by installing the app on their own store and capturing a legitimate webhook delivery) can replay that exact body with a forged `shopify-shop-domain` header claiming to be a different, victim shop, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [1](#0-0) 

`HmacValidator.validate` computes an HMAC-SHA256 over `verifiable_query.to_signable_string` (i.e. the body only) using `Context.api_secret_key`, and compares it to the received `hmac`: [3](#0-2) [4](#0-3) 

`Registry.process` relies on exactly this check, then forwards the *unauthenticated* `request.shop` value straight to the app's handler as the tenant identifier: [5](#0-4) 

The binding that should hold is:
`shop value delivered to the handler == shop value cryptographically bound to the signed payload`

but the actual binding is:
`shop value delivered to the handler == an unauthenticated HTTP header`

Because a single `api_secret_key` is shared by the app across all of its installed shops, any merchant that has installed the app (including an attacker who installs it on their own store) can capture a genuinely-signed webhook body/HMAC pair for a topic that carries little or no shop-specific data in the body (e.g., `app/uninstalled`, or any topic whose payload doesn't include an internal shop ID the handler cross-checks), and replay it to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` passes the forged `shop` through to `WebhookMetadata`/the handler unchanged.

### Impact Explanation
This breaks the tenant-identity boundary the gem is expected to guarantee for consumers of `Registry.process`/`WebhookMetadata#shop`: any app that keys per-tenant business logic (e.g., marks a shop as uninstalled, disables billing, revokes access, updates per-shop state) off `WebhookMetadata#shop` can be tricked into applying that mutation to a shop the attacker does not control. This is a cross-tenant access primitive (the attacker forges a message purportedly from shop B while only controlling shop A), matching the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Requires only an attacker-controlled Shopify store that installs the app (a normal, low-privilege action available to any merchant) plus the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers — no access token, `client_secret`, or privileged account is needed. The `api_secret_key` is shared across all shops using the same app, so the HMAC computed for the attacker's own legitimate webhook is valid for any header combination as long as the body is unchanged.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is HMAC-verified, or independently verify that the shop asserted in the header matches shop-identifying data embedded in the verified body/claims, before it is handed to `WebhookMetadata`/application handlers. At minimum, document/require that consuming applications cross-check `WebhookMetadata#shop` against a shop identifier taken from the verified payload itself (e.g. compare to a session/shop record looked up by webhook subscription id) rather than trusting the header value alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery (e.g. `app/uninstalled`) with body `B` and a valid header `x-shopify-hmac-sha256: H`, computed as `HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)`.
3. Attacker sends a POST to the app's webhook endpoint with the same body `B`, the same `hmac` header `H`, but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request from headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation passes — see `lib/shopify_api/utils/hmac_validator.rb:12-22,26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to act on behalf of `victim.myshopify.com` even though the attacker never controlled that shop.
