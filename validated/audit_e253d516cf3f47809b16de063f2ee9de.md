### Title
Emporium `runAction` executes attacker-controlled calls with zero balance accounting when reached via the trivial `formInputEmporiumMin` proof path - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
An unprivileged attacker can call `Hinkal.transact` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, forcing `formInputForCircom` to select `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin`) only constrains `message == Poseidon(messageSeed)` and leaves `calldataHash`/`timeStamp` unconstrained. Because the token list is empty, `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` accounting is over an empty array, so the attacker-supplied `EmporiumStack` with `signerAddress == 0` can execute arbitrary `op.endpoint.call{value: op.value}(op.callData)` as Emporium's own identity (bypassing all signature checks in `verifyWallet`) with no accounting of any resulting asset movement.

### Finding Description
The claimed broken equality is: *assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`*.

Path:
1. `formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [1](#0-0) . That function only emits `emporiumMessage`, `timeStamp`, `calldataHash` as public signals [2](#0-1) .
2. The corresponding circuit `MainEVMCircuitMin` only constrains `message <== Poseidon(1)([messageSeed])`; `calldataHash` and `outTimeStamp` are declared public but never used in any constraint [3](#0-2) . This means the proof carries no constraint tying it to any real deposit, nullifier, or UTXO ownership — the attacker can freely choose `messageSeed` and compute a matching `message`.
3. `performHinkalChecks` only verifies internal self-consistency of `calldataHash` (`getHashedCalldata(circomData) == circomData.calldataHash`) — this does not tie the calldata to any legitimate prior state, since the attacker fully controls all of `circomData` including `externalActionData.externalActionMetadata` [4](#0-3) .
4. In `Hinkal.transact`, with `erc20TokenAddresses` empty, the top-level balance-diff loop (lines 97-147) never executes, and `_externalTransact` computes `deltaAmountChanges` as an empty array before calling `EmporiumUpgradeable.runAction` [5](#0-4) .
5. `EmporiumUpgradeable.runAction` decodes the attacker's `EmporiumStack` from `externalActionMetadata`, computes `balancesBefore`/`balancesAfter` over the (empty) `erc20TokenAddresses`, and calls `verifyWallet`, which for `signerAddress == address(0)` **skips all signature verification** and simply marks the message used [6](#0-5) .
6. The `ops` loop then executes each attacker-chosen `EmporiumOperation`. Since `stack.signerAddress == address(0)`, `op.invokeWallet && stack.signerAddress != address(0)` is false, so every op falls into the stateless branch: `op.endpoint.call{value: op.value}(op.callData)`, executed with `msg.sender == Emporium` and only `callHinkalWallet`/`doSendToRelay` selectors blocked [7](#0-6) .
7. Because `circomData.erc20TokenAddresses` is empty, the post-loop balance-change/`utxoSet` accounting (lines 132-159) also never executes for any token, so any assets moved by the ops (e.g., `ERC20.transfer(attacker, balance)` called directly on a token where Emporium holds a balance, or ETH sent via `op.value` from Emporium's own balance) are completely unaccounted for and not blocked by `BalanceChangeShouldBePositive` [8](#0-7) .

The `EmporiumUpgradeable.runAction` function is only reachable when `msg.sender` is an allowed recipient (Hinkal contract) [9](#0-8) , and the attacker reaches it legitimately through `Hinkal.transact` → `_externalTransact` since `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]` is a registered address [5](#0-4) . No privileged role is required.

I was unable to fully verify the "tree has exactly one prior leaf / `roots[MINIMUM_INDEX]` equals the leaf directly" sub-claim's relevance — `rootHashExists`/`m_index`/`MINIMUM_INDEX` in `contracts/MerkleBase.sol` [10](#0-9)  govern root validity for the *normal* path's `rootHashHinkal` field, but the `formInputEmporiumMin` public input vector never includes `rootHashHinkal` at all, so the root-hash state of the tree is irrelevant to reaching this bug — the min path is fully independent of tree state and does not require any specific number of leaves.

### Impact Explanation
Any unprivileged attacker can drain any ERC20 or native ETH balance held by the `EmporiumUpgradeable` contract (e.g., dust, parked/in-flight relay fees, or funds left mid-operation) by crafting a trivial self-satisfying `MainEVMCircuitMin` proof and an `EmporiumStack` with `signerAddress == 0` and arbitrary `ops`. Since balances aren't tracked at all for the empty token list, multiple different tokens/assets can be drained via multiple chained ops in a single transaction. This is direct theft of protocol/in-flight funds with no accounting or authorization check, matching Critical severity, and is fully repeatable as long as Emporium holds any balance.

### Likelihood Explanation
Preconditions: Emporium contract must hold some ERC20/ETH balance (parked/in-flight funds are a normal operating state for this design, since deposits/relay-fee flows route balances through Emporium). No special tree state, no relayer, no privileged role, and no valid UTXO/deposit is required by the attacker — cost is just gas plus a self-generated Groth16 proof for the trivial min circuit. This makes the attack cheap and highly feasible whenever Emporium holds funds.

### Recommendation
- Reject the "Min" Emporium path (`formInputEmporiumMin`) entirely, or constrain `calldataHash`/`timeStamp` inside `MainEVMCircuitMin` so they cannot be freely chosen, and require `erc20TokenAddresses.length > 0` (or otherwise bind the proof to a real UTXO/nullifier) before allowing `EmporiumUpgradeable.runAction` to execute arbitrary `ops`.
- In `EmporiumUpgradeable.runAction`, never allow `signerAddress == address(0)` (unsigned/unauthenticated stack) to invoke `op.endpoint.call` with attacker-controlled `callData`/`value` — always require a valid EIP-712 signature or restrict unsigned ops to a fixed, non-arbitrary set of allowed selectors/endpoints.
- Track and validate balance changes for *all* tokens actually touched by `ops` (not just `circomData.erc20TokenAddresses`), or disallow arbitrary `call` targets/selectors so Emporium cannot be made to move tokens outside the declared token list.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as allowed recipient/external action), a mock verifier that accepts the trivial `MainEVMCircuitMin`-shaped proof (or use the real `VerifierEVMMin0v4` and locally compute a valid Groth16 proof for `message = Poseidon(messageSeed)` with attacker-chosen `messageSeed`).
2. Fund Emporium directly with an ERC20 token (simulate "parked balance").
3. Craft `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenBalance))})], maxFee: 0, deadline: 0}))`.
4. Compute `calldataHash` to match `getHashedCalldata(circomData)`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker EOA.
6. Assert: `token.balanceOf(attacker)` increases by `tokenBalance` and `token.balanceOf(emporium)` drops to 0, i.e., the equality "assets moved == assets accounted in balancesBefore/balancesAfter" is violated (accounted amount == 0, actual moved == full balance).
