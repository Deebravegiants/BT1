## Title
Unsafe `String::from_utf8_unchecked` on attacker-controlled EVM POST request body causes undefined behavior and unrenderable on-chain event data - (File: `modules/pallets/demo/src/lib.rs`)

### Summary
`pallet-ismp-demo`'s `IsmpModule::on_accept` callback converts the raw, attacker-supplied `PostRequest.body` bytes into a Rust `String` using `String::from_utf8_unchecked` whenever the request's `source_chain` is `StateMachine::Evm(_)`, with no UTF-8 validation performed anywhere beforehand. This mirrors the CVE-2024-51750 bug class: a remote, unprivileged party (here, any EVM-side contract dispatching a message through `EvmHost`/`HandlerV2`, relayed on-chain via `pallet-ismp`'s `handle_unsigned`) can submit malformed data that is deposited as on-chain event data and later fails to render/decode correctly (or worse) downstream.

`request.body` is fully attacker-controlled: it originates from a `PostRequest` dispatched from any EVM chain, relayed to the destination chain via `HandlerV2.handlePostRequests` on EVM, or delivered on the Substrate side through `pallet-ismp`'s message handler (`modules/ismp/core/src/handlers/request.rs`, `handle<H>`), which routes the request to whichever `IsmpModule` matches `request.to` (here, `pallet_ismp_demo::PALLET_ID`) via the runtime's `ProxyModule::on_accept`: [2](#0-1) 

`String::from_utf8_unchecked` is documented by the Rust standard library as producing **undefined behavior** if the input is not valid UTF-8 — the compiler is permitted to assume the resulting `String` always holds valid UTF-8, and code paths that rely on that invariant (e.g. `str` slicing on char boundaries, `.chars()`, or serialization to JSON via `serde_json`) can panic, corrupt memory, or behave unpredictably. There is no length or validity check on `request.body` before this call, so a single malicious cross-chain message with an invalid UTF-8 byte sequence (e.g. a stray continuation byte) reaches this unsafe conversion directly.

This is directly analogous to the reference CVE: a remote, permissionless actor (an EVM-side application/attacker, playing the role of the "malicious homeserver") can craft and dispatch a single cross-chain message whose body is not valid UTF-8. That message is processed and its data is persisted as on-chain event data holding an invalid `String` — any client, indexer, or wallet that subsequently attempts to decode/display that event (SCALE-decode into a `String` and serialize to JSON, as `subxt`/Polkadot.js/SubQuery indexers commonly do) will fail to render it correctly or crash on decode, exactly mirroring "prevent rendering of a single message" from the advisory. Because the field is emitted from a runtime `deposit_event`, its unsoundness (UB) also technically taints on-chain state derived from it, going a step beyond the client-side rendering bug in the original report.

### Impact Explanation
- A single malicious/attacker-controlled POST request from any registered EVM state machine can trigger undefined behavior on the destination Substrate chain when the request targets the `pallet-ismp-demo` module.
- The malformed `String` is persisted in on-chain event data, propagating the malformed/invalid UTF-8 payload to every downstream consumer (indexers, wallets, RPC JSON serializers) that assumes valid UTF-8, causing decode failures/crashes analogous to Element's "unrenderable events/rooms."
- Because `from_utf8_unchecked` is UB rather than a checked panic, impact is not fully bounded to "just a rendering error" — the Rust compiler may miscompile or otherwise misbehave around this invariant violation, which is a stronger correctness/soundness issue than the referenced CVE's simple decode failure.
- This is reachable from a single relayed message and requires no privileged role — matching the required "unprivileged message dispatcher" reachability bar.

### Likelihood Explanation
High, given the low barrier to trigger: any account controlling a contract/EOA on a supported EVM chain can dispatch a `DispatchPost` (via `EvmHost.dispatch`) with `to` set to the demo pallet's module ID and an arbitrary, non-UTF-8 `body`. Once relayed and delivered through `pallet-ismp`'s handler (permissionless `handle_unsigned`), the vulnerable code path executes automatically with no additional conditions.

### Recommendation
Replace `String::from_utf8_unchecked(request.body)` with a checked conversion, e.g. `String::from_utf8(request.body).map_err(|_| IsmpError::Custom("invalid utf8 body".into()))?`, returning an error (which causes the request to remain un-acknowledged/timeoutable per the `IsmpModule` contract) instead of invoking undefined behavior on attacker-supplied bytes. More generally, no `unsafe` UTF-8 conversion should ever be applied to bytes originating from `PostRequest.body`/`from`/`source` fields, since these are fully attacker/relayer controlled across every module in the router.

### Proof of Concept
1. Deploy/own a contract on any configured EVM chain and call `EvmHost.dispatch(DispatchPost)` with `to = pallet_ismp_demo::PALLET_ID` bytes and `body = [0xC0, 0x80]` (an overlong, invalid UTF-8 sequence).
2. Have a relayer (or self-relay) submit the resulting `PostRequest` via the destination chain's `pallet-ismp` `handle_unsigned` extrinsic, along with a valid state/consensus proof.
3. `ProxyModule::on_accept` routes the request to `pallet_ismp_demo::IsmpModuleCallback::on_accept` because `request.to` matches `PALLET_ID`.
4. Since `source_chain` is `StateMachine::Evm(_)`, the handler executes `String::from_utf8_unchecked(request.body)`, producing a `String` that does not hold valid UTF-8 (undefined behavior per Rust's safety contract), and emits it via `Event::Request { data, .. }`.
5. Any indexer/wallet/RPC client attempting to SCALE-decode and render this event's `data` field as UTF-8 (e.g. `serde_json` serialization of the decoded `String`) will fail to render it correctly or panic, analogous to the cited CVE's client-side impact.
