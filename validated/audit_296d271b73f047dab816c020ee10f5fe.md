Webhook `shop`, `topic`, and `webhook-id` headers are not covered by HMAC verification, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` and delivered to the host app's `WebhookHandler` come from unauthenticated headers. Because the gem's HMAC validator only proves that the body bytes were signed with the app's shared client secret, and never binds that signature to the shop or topic claimed in the headers, an attacker who legitimately triggers a webhook for a shop they control can replay the exact same signed body while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to impersonate a different merchant.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` using the app's `client_secret`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw JSON body: [2](#0-1) 

However, `shop`, `topic`, and `webhook_id` are read straight from headers, entirely outside the signed payload: [3](#0-2) 

`Registry.process` only checks the body-only HMAC before dispatching, then forwards the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` to the host application's handler as trusted metadata: [4](#0-3) [5](#0-4) 

This is the same *"a field acted on but not covered by the HMAC"* class of bug as the H1 report: the report shows a stale/unauthenticated credential state being treated as valid because the enforcing check doesn't cover the field that actually determines access. Here, the identity binding broken is:

`hmac_valid(body) == true` should imply `shop_header == shop_that_produced(body, secret)`, but the gem never establishes that equality — the same `client_secret` is shared across every shop that installs the app, and the signature is computed over the body alone.

Contrast this with the OAuth callback verification in the same codebase, which explicitly folds `shop` into the signed string: [6](#0-5) 

The webhook path has no equivalent binding.

### Impact Explanation
An attacker who installs the target app on a shop they control (a normal, permitted action — no privileged credentials needed) can trigger any webhook topic on their own store, capture the legitimately-signed `(body, hmac)` pair Shopify sends to the app, and replay it to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` header to name a victim shop, and/or the `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers to select a different event type. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop name. Any host application logic keyed on `data.shop` (e.g., updating that shop's local records, deactivating billing, processing `app/uninstalled`, GDPR data-erasure webhooks, etc.) is executed against the wrong tenant — a cross-tenant integrity/confidentiality impact driven entirely by this gem's verification logic.

### Likelihood Explanation
Exploitation only requires the ability to install the app on an attacker-owned/development shop (trivial for any developer app or public app) and standard HTTP tooling to replay the captured request with a modified header. No access token, `client_secret`, or victim credentials are needed — this fits the "Critical: cross-tenant access" impact bucket in scope, driven purely through the gem's own `HmacValidator`/`Webhooks::Request`/`Registry` code path.

### Recommendation
Bind the header-derived identity fields into the signed payload the same way `AuthQuery` does for OAuth: either require Shopify's webhook signature to additionally authenticate `shop`, `topic`, and `webhook_id` (Shopify does not include these in the HMAC by design, so the gem/host app must independently verify that `request.shop` corresponds to a shop with an active app installation and stored access token before trusting `WebhookMetadata.shop`), or explicitly document/enforce that consumers must cross-check `data.shop` against their own installation records before acting on webhook payloads. At minimum, add prominent documentation/errors in `Registry.process` warning that the `shop` header is unauthenticated and must not be used as an authorization boundary without an independent installation lookup.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) on that shop; Shopify sends a POST to the app's webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Capture `B` and `H` via a proxy.
4. Replay the same request to the app's endpoint, keeping `B` and `H` unchanged but setting `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H` (see `to_signable_string` returning `@raw_body`) — the shop-domain header is never checked.
6. `Registry.process` dispatches to the app's `WebhookHandler#handle` with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the host app to act as though the event came from the victim shop.
