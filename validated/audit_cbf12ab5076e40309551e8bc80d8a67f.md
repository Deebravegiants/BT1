### Title
Hostile HyperSwap pre-seed can drive `finalizeGraduation`'s deposit to zero, causing `LPLock.recordLock` to revert and permanently brick graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is a permissionless, two-phase graduation step that must, by the protocol's own stated invariant, "never revert under any pre-seed shape" [1](#0-0) . The `_swapBudget` cap that is supposed to guarantee this explicitly documents the *un-mitigated* failure mode as `LPLock.recordLock(...)` "records a zero-sized lock" [2](#0-1) . That assumption is wrong: `LPLock.recordLock` does not silently accept a zero-sized lock — it hard-reverts with `ZeroAmount()` [3](#0-2) . Any pre-seed shape that drives `_routerDepositAndDispose`'s computed `liquidity` to `0` therefore reverts the entire `finalizeGraduation` transaction instead of degrading gracefully — the exact "crash on crafted/malformed input" bug class described in CVE-2017-5854 (an unhandled degenerate condition that the code assumed was safe but is actually fatal).

### Finding Description
`_routerDepositAndDispose` only calls `addLiquidity` when *both* remaining balances are non-zero; otherwise `liquidity` stays `0`:
```
if (remToken > 0 && remLT > 0) {
    ...
    (,, liquidity) = IUniswapV2Router02(routerAddr).addLiquidity(...);
}
``` [4](#0-3) 

`finalizeGraduation` then unconditionally forwards that (possibly zero) `liquidity` value to `LPLock.recordLock`:
```
LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);
``` [5](#0-4) 

`LPLock.recordLock` reverts on `amount == 0`:
```
if (amount == 0) revert ZeroAmount();
``` [3](#0-2) 

The developers' own `_swapBudget` natspec acknowledges the zero-liquidity scenario is reachable via an "extreme hostile pre-seed (massively imbalanced reserves)" that drives the unconstrained `_noFeeSwapInput` past the per-side budget, consuming 100% of one side of Bonding's committed inventory, so that `_routerDepositAndDispose` skips `addLiquidity` entirely [2](#0-1) . The 99% cap in `_swapBudget` is meant to prevent this by always reserving 1% of the swapped-from side's inventory, but this is a probabilistic/economic mitigation, not a hard on-chain guarantee against every reserve/rounding combination reachable by an attacker who fully controls the HyperSwap pair's pre-existing reserves (via `factory.createPair` + `transfer` + `pair.mint`, as described in the "HyperSwap Pre-Seed Defense" section) [6](#0-5) . Because `pendingGraduation[token]`'s `(tokensForLP, ltFromPair)` are cached once in phase 1 and never recomputed [7](#0-6) , and the hostile pool reserves are also attacker-fixed on-chain state, every retry of `finalizeGraduation` deterministically replays the same computation and hits the same `ZeroAmount()` revert — this is not a transient failure, it is a permanent brick.

### Impact Explanation
Once `finalizeGraduation` reverts permanently for a token, that token is stuck forever in `Lifecycle.Graduating`: trading is already frozen (phase 1 froze it) [8](#0-7) , and all curve-raised LT already drained into `Bonding` via `Router.graduate` in phase 1, plus the 250M reserved tokens (`LP_RESERVE`) held by `Bonding`, become permanently unreachable — there is no rescue/retry path that changes the outcome, and `LPLock`/`Bonding` expose no admin override for this state. This is a permanent freezing of trader/creator funds (curve-raised LT and the LP-reserve token allocation), which is squarely in scope per the report's impact criteria.

### Likelihood Explanation
The attack requires only unprivileged actions the report explicitly treats as in-scope: pre-creating the HyperSwap V2 TOKEN/LT pair and seeding it with an attacker-chosen extreme ratio before `finalizeGraduation` runs — this is the documented "hostile mint pre-seed" front-run already acknowledged as reachable by any wallet [9](#0-8) . The `_swapBudget`/`_pairRebalance`/`_seedRebalancing` defense reduces the practical window in which the zero-liquidity condition is reachable, but the underlying architectural gap — a documented "records a zero-sized lock" assumption that the destination contract (`LPLock`) actually reverts on — means any edge case the 99%-cap heuristic doesn't fully close (extreme uint112-bounded reserve ratios, rounding at the swap/deposit boundary, or degenerate `_noFeeSwapInput` outputs) converts straight into a permanent brick rather than a benign degraded state.

### Recommendation
Make the zero-liquidity outcome an explicit, handled case rather than relying on the `_swapBudget` heuristic to prevent it:
- Have `LPLock.recordLock` accept the documented degenerate case, or have `finalizeGraduation` explicitly detect `liquidity == 0` before calling `recordLock` and fall back to a guaranteed-non-reverting path (e.g., routing the residual inventory to a rescue/sweep mechanism instead of attempting an LP lock).
- Add fuzz/invariant tests that adversarially construct HyperSwap pre-seed reserves at the boundary of `_swapBudget`'s 99% cap (including extreme uint112-scale ratios) and assert `finalizeGraduation` never reverts, closing the gap between the natspec's stated assumption and `LPLock`'s actual revert behavior.

### Proof of Concept
1. Creator launches a token via `Zap.createToken` with a minimal viable seed; curve accumulates a relatively small `ltFromPair`/`tokensForLP` at graduation (phase 1 `_enterGraduating` caches these in `pendingGraduation[token]`).
2. Attacker front-runs phase 2: calls `factory.createPair(token, lt)`, then transfers TOKEN and LT to the pair at an extreme ratio sized so that, combined with `Bonding`'s own `_ltSwapInventory`/token balance budget, the `_pairRebalance` swap (capped at 99% of the available side by `_swapBudget`) leaves the *other* side's remaining balance rounding to `0` after the swap and burn/skim bookkeeping in `_seedRebalancing`/`_routerDepositAndDispose`.
3. Attacker (or the keeper) calls `Bonding.finalizeGraduation(token)`. `_routerDepositAndDispose` skips `addLiquidity` (`remToken == 0` or `remLT == 0`), returning `liquidity = 0` [4](#0-3) .
4. `finalizeGraduation` calls `LPLock.recordLock(token, lpPair, 0)`, which reverts with `ZeroAmount()` [3](#0-2) .
5. Every subsequent call to `finalizeGraduation(token)` replays the same cached `pendingGraduation` values against the same attacker-fixed pool state and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, with its curve-raised LT and 250M reserved tokens locked in `Bonding` forever.

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.
