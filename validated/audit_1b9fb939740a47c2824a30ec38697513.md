## Analysis [1](#0-0) [2](#0-1) 

The reported bug class — an atomic multi-token payout loop that reverts (and permanently blocks) the *entire* withdrawal when a single malicious/blacklisting token transfer fails — reproduces in Hyperbridge's Intents system.

### Title
Atomic all-or-nothing escrow release lets an order's creator permanently freeze a solver's escrowed input payout via one poisoned input token - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`_withdraw()` iterates over every escrowed token of an order and transfers them all to the beneficiary in a single atomic loop, reverting the whole call if any single token's `transfer` reverts. Because the order's *creator* freely chooses which ERC-20 tokens are escrowed as `order.inputs` at `placeOrder` time, a malicious user can include a token they control (e.g., one with an address-specific blacklist/revert hook) alongside legitimate tokens. Once a solver fills the order and the fill/redeem flow calls `_withdraw` to pay the solver, the malicious token's transfer to the solver's address can be made to always revert, which reverts the *entire* withdrawal — including the release of all other legitimate escrowed tokens in the same order — permanently denying the solver its earned payout.

### Finding Description
`_withdraw` (and its sibling `withdraw` in the Tron variant) loops over `body.tokens` and calls `safeTransfer`/`.call` per token, reverting the whole function (and hence the whole transaction) if any single transfer fails: [3](#0-2) 

This is invoked from both the same-chain (`IntrinsicIntents.sol`) and cross-chain (`ExtrinsicIntents.sol`, via `onAccept`'s `RedeemEscrow`/`RefundEscrow` handling) fill paths to pay out `order.inputs` to whoever filled the order. The set of escrowed tokens (`order.inputs`) is fully attacker-controlled by the order placer at `placeOrder` time — nothing constrains it to "safe" tokens. A malicious order creator can therefore:
1. Place an order whose `inputs` include one normal, valuable token (e.g. USDC) plus one adversarial ERC-20 that reverts `transfer()` calls to a specific address.
2. Wait for a solver to fill the order (delivering the required output on the destination chain, per the intents protocol's asynchronous cross-chain flow).
3. Once the solver's address is known (it becomes the `beneficiary` of the withdrawal request), ensure the adversarial token reverts transfers to that specific solver address.
4. When Hyperbridge relays the `RedeemEscrow` request and `_withdraw`/`withdraw` attempts to pay out both tokens to the solver in one atomic loop, the poisoned token's revert causes the *entire* transaction — including the legitimate USDC payout — to revert every time it is retried.

Because `_filled` is set at the top of `_withdraw` (CEI pattern) and the whole transaction reverts on transfer failure, the order is never actually marked filled, so the request can be resubmitted indefinitely — but it will always revert the same way, meaning the solver's rightful escrow (including the non-malicious tokens) is permanently unreachable via this code path. This is functionally identical to the referenced C4 finding: a "pool owner" (here, the order creator) chooses which token is in the release list, and by manipulating that token's transfer behavior for one specific target address, prevents that one victim's withdrawal without affecting anyone else's orders.

### Impact Explanation
The solver has already performed the destination-side output delivery (in the cross-chain fill flow) or has otherwise satisfied the order's fill conditions, entitling it to the escrowed input tokens. If even one included input token is adversarial, none of the escrowed tokens for that order — including fully legitimate, valuable ones bundled in the same order — can ever be redeemed by that solver through the intended path. This is a permanent freezing of solver funds/compensation, a real economic loss for an unprivileged participant (the solver) who acted in good faith, triggered entirely by an unprivileged order creator.

### Likelihood Explanation
Likelihood is high: placing an order with an arbitrary `inputs` token list is a normal, permissionless action (`placeOrder`), and crafting an ERC-20 that selectively reverts `transfer()` for a target address is trivial and well-precedented (deny-lists, pausable-per-address tokens, or tokens the "attacker" itself deploys and controls). No special privilege or governance access is required — only that the attacker be the one placing the order, which is unprivileged and always true for a self-serving griefing order.

### Recommendation
Do not couple the release of multiple distinct tokens into a single all-or-nothing loop. Either:
- Track per-token withdrawal state so `_withdraw`/`withdraw` can be retried and will skip (or separately account for) tokens that have already succeeded, continuing to release the remaining tokens even if one fails, or
- Isolate each token transfer with a try/catch (or low-level call ignoring failure with credited "pull" balance) so a single malformed/malicious token cannot block release of the others, or
- Provide an emergency/selective-token withdrawal function allowing a beneficiary to redeem the non-poisoned tokens independently, leaving only the malicious token's specific claim outstanding.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer()` reverts if `to == knownSolverAddress` (or any address the attacker chooses once it learns the filler).
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: X}, {token: EvilToken, amount: Y} ]` and a legitimate-looking `order.output` to attract a solver. [4](#0-3) 
3. A legitimate solver fills the order, delivering the requested output tokens to the beneficiary on the destination chain.
4. The fill triggers a `RedeemEscrow` request; on delivery, `withdraw`/`_withdraw` attempts to pay both USDC and EvilToken to the solver in one loop. [1](#0-0) 
5. `EvilToken.transfer(solver, Y)` reverts, causing the entire withdrawal (including the USDC transfer) to revert. Every resubmission of the redeem message fails identically, permanently locking the solver out of both tokens despite having fulfilled the order.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
