# Custody Analog Finding: Multisig Transaction Payload-Mismatch Check Is Feature-Gated, Allowing Execution of Unapproved Payload

## Custody Invariant Reduction
The WatchPug bug reduces to: *a privileged, unprivileged-facing function has a guard meant to bind its authority to a specific, pre-approved target, but the guard can be bypassed under a reachable state/condition, letting the caller redirect that authority to steal assets.* On Aptos, the analogous custody invariant is: **the entry function/payload executed under a multisig account's signer authority must be exactly the payload that reached quorum approval** — a multisig account is a resource account that can custody APT, fungible assets, and objects [1](#0-0) .

## Candidate Paths Considered
1. `object::unburn`/`TombStone` reclaim logic — reviewed, ownership transfer is gated correctly by current-owner or original-owner checks; no bypass found [2](#0-1) .
2. `dispatchable_fungible_asset` withdraw/deposit hooks — dispatch is bound to metadata-registered `FunctionInfo` with type-compatibility checks at registration; no unprivileged override path found [3](#0-2) .
3. **Multisig transaction payload validation** — kept as strongest candidate (below).

## Finding Description
`multisig_account::validate_multisig_transaction` (the internal validation invoked before `execute_multisig_transaction`) checks the payload supplied by whoever submits the outer `MultisigTransaction` against what owners actually approved, but the check is split into two branches:

```
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [4](#0-3) 

`create_transaction` and `create_transaction_with_hash` are documented as **alternative** storage modes: the former stores the full payload (`payload_hash = None`), the latter stores only the hash (`payload = None`) [5](#0-4) . Consequently, for transactions created via `create_transaction` (full payload on-chain), `transaction.payload_hash.is_some()` is `false`, so the first (unconditional) integrity check never runs. The only remaining check — that the executor-supplied payload equals the owner-approved `transaction.payload` — is gated entirely behind the `abort_if_multisig_payload_mismatch_enabled` feature flag.

The `provided_payload` compared here is derived directly from the outer transaction's own `TransactionExecutableRef::EntryFunction`, i.e., whatever entry function the caller executing the multisig transaction chooses to attach to their own transaction — not something cryptographically tied to what owners approved [6](#0-5) . If the feature flag is disabled, the VM will execute the caller-chosen entry function as the multisig account's signer as long as quorum count and sequence number line up, completely decoupling "what got approved" from "what gets executed" — the same authority-decoupling pattern as the WatchPug `arbitraryCall()`/`incentives[who]` bug, but applied to a resource account's signer capability instead of an incentive-token allowance.

## Impact Explanation
Since a multisig account is a resource account that can hold APT, fungible-asset stores, and objects, an executor able to submit the `MultisigTransaction` (any account, since "any owner can execute" once quorum is reached, and the execution flow itself doesn't re-verify payload identity when the flag is off) can substitute a transfer/withdraw call to drain the multisig-controlled treasury instead of the function that owners actually voted for, while the transaction still gets marked "executed with N approvals" on-chain. This is a full custody-authority hijack of the multisig account.

## Likelihood Explanation
Exploitability depends entirely on the run-time state of the `abort_if_multisig_payload_mismatch_enabled` feature flag. I could not confirm from the indexed code whether this flag defaults to enabled or disabled on mainnet, or whether it is already unconditionally activated network-wide by the time this framework version ships. The naming convention (`abort_if_X_enabled`) and the fact this is implemented as an opt-in feature rather than baked into the base logic strongly suggests it was added later as a hardening fix for previously-missing full-payload verification — meaning older/un-upgraded network states (or any deployment where this flag is off) are exposed. Because I was unable to fully verify the flag's current default/activation status in this environment, this determination has residual uncertainty.

## Recommendation
Make the full-payload integrity check unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate), or equivalently, always populate/verify `payload_hash` regardless of whether the full payload is also stored, so that `sha3_256(payload) == payload_hash` is enforced independent of feature-flag state for every multisig execution path.

## Proof of Concept
1. Owners create a multisig account and call `create_transaction` with a benign entry function payload (e.g., `coin::transfer(multisig_signer, alice, 10)`), which stores the full `payload` on-chain and leaves `payload_hash = None`.
2. Owners approve until quorum (`num_signatures_required`) is reached for that `sequence_number`.
3. On a network/version where `abort_if_multisig_payload_mismatch_enabled` is disabled, any account submits a `TransactionPayload::Multisig` outer transaction whose own `entry_function` field is instead `coin::transfer(multisig_signer, attacker, entire_balance)`.
4. `execute_multisig_transaction` serializes this attacker-chosen entry function as `provided_payload`, `validate_multisig_transaction` skips both the hash check (`payload_hash` is `None`) and the payload-equality check (feature disabled), and `execute_multisig_payload` executes the attacker's entry function as the multisig account's signer, draining its funds — while `successful_transaction_execution_cleanup` still records it as a legitimately quorum-approved transaction [7](#0-6) .

**Caveat:** This finding's mainnet relevance hinges on the activation state of `abort_if_multisig_payload_mismatch_enabled`, which I could not conclusively determine from the available index. A Devin session with terminal/repo access would be needed to check the feature-flag activation history/on-chain config to confirm current mainnet exposure.
