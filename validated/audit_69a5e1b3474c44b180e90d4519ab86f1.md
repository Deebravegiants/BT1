### Title
Missing allowlist/authorization enforcement on `web_api_trigger` messages allows any unprivileged gateway caller to broadcast requests to an entire DON - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The reported Solidity issue is about an owner-level function (`updateBeneficiary`) that lets a privileged actor redirect where protocol funds/fees are sent, with no restriction on the destination. Looking for an analogous "destination/authorization is not properly restricted" pattern reachable by an *unprivileged* actor in this repo, the closest and most concretely provable analog is in the legacy Web API capability gateway handler: `HandleLegacyUserMessage` explicitly skips allowlist checks (`// TODO: apply allowlist and rate-limiting here`) before fanning a user-supplied `web_api_trigger` message out to every node in the DON.

### Finding Description
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` processes inbound `MethodWebAPITrigger` messages from arbitrary gateway clients (an internet-facing, unauthenticated-by-role endpoint at the gateway layer — clients only need to construct a well-formed signed `api.Message`, not hold any node-side role). After basic payload/timestamp/method validation, the code contains this explicit gap: [1](#0-0) 
```
	// TODO: apply allowlist and rate-limiting here
	if msg.Body.Method != MethodWebAPITrigger {
		...
	}
```
Immediately after this, the request is converted and broadcast to every node configured for the DON, with no check that the sender is authorized to target this DON/workflow: [2](#0-1) 
Compare this with the newer v2 HTTP handler, which does enforce workflow-owner scoping and JWT-based authentication for trigger requests (`ValidatedRequestFromMessage`, `validateWorkflowFields`, JWT verification in `httpTriggerHandler`), and with the vault handler, which validates node responses against the original request method/ID. The legacy `capabilities/handler.go` path lacks the equivalent authorization gate — the TODO comment is the maintainers' own acknowledgment that the "destination" (which DON members ultimately receive and process the trigger) is not access-controlled for this message type.

This is structurally analogous to the reported bug class: a "recipient/destination" of a privileged operation (here, "which DON nodes process this trigger, and on whose behalf") is not properly gated by authorization, and the omission is explicit in the code rather than speculative.

### Impact Explanation
Any caller able to reach the gateway's legacy user-message path for a `web_api_trigger` method can cause the gateway to broadcast requests to all DON members without any allowlist enforcement, bypassing the intended per-user/per-workflow authorization boundary. Depending on how `don.SendToNode` and downstream node capability handlers interpret payload contents, this could allow an unprivileged party to trigger workflow executions or actions on nodes they are not authorized to address — an unauthorized-request/allowlist-bypass condition, one of the accepted impact categories (allowlist/quota bypass, unauthorized job run).

### Likelihood Explanation
The gap is not hypothetical — it is called out by an explicit `// TODO: apply allowlist and rate-limiting here` comment directly in the code path that fans messages out to the DON, with no allowlist check present anywhere in `HandleLegacyUserMessage`. Any message satisfying only the payload-decoding, timestamp-freshness, and method-name checks will reach this broadcast. The main uncertainty (which I could not fully resolve given index limits) is whether this legacy handler path is still wired into a production-reachable route in the current gateway configuration, or whether it has been superseded/gated by the newer v2 HTTP trigger handler (which does enforce workflow-owner/JWT checks) in all deployed configurations. If the legacy handler is still registered for any DON in production, the missing allowlist is directly exploitable as described.

### Recommendation
- Implement the allowlist and rate-limiting check called out in the TODO before broadcasting `web_api_trigger` messages to DON members, mirroring the workflow-owner/JWT validation already present in the v2 `httpTriggerHandler`.
- Ensure `don.SendToNode` broadcasts are restricted to nodes/workflows the sender is authorized to address, not just format-validated.
- If the legacy handler is deprecated in favor of the v2 handler, confirm it is not reachable from production DON configurations, or remove it entirely to eliminate the exposed gap.

### Proof of Concept
1. Construct a well-formed `api.Message` with `Body.Method = "web_api_trigger"`, a valid (non-stale) `Timestamp`, and a `TriggerRequestPayload` that passes JSON unmarshalling.
2. Submit it through the gateway's legacy user-message ingress for a target DON.
3. Observe in `HandleLegacyUserMessage` that execution proceeds straight past the `// TODO: apply allowlist and rate-limiting here` comment (no authorization/allowlist function is invoked) and the message is forwarded to every member of `h.donConfig.Members` via `don.SendToNode`, regardless of whether the caller is authorized for that DON/workflow. [3](#0-2)

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JSONRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if payload.Timestamp == 0 {
		h.lggr.Errorw(ErrDecodingPayload)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) { //nolint:gosec // G115: comparing unix timestamps, both fit within uint
		h.lggr.Errorw("stale message")
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.HandlerError),
				"stale message",
				nil,
			),
			ErrorCode: api.HandlerError,
		})
	}
	// TODO: apply allowlist and rate-limiting here
	if msg.Body.Method != MethodWebAPITrigger {
		h.lggr.Errorw("unsupported method", "method", body.Method)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UnsupportedMethodError),
				"invalid method "+msg.Body.Method,
				nil,
			),
			ErrorCode: api.UnsupportedMethodError,
		})
	}
	req, err := common.ValidatedRequestFromMessage(msg)
	if err != nil {
		h.lggr.Errorw(ErrTransformingMessageToRequest)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageID,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrTransformingMessageToRequest,
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}

	h.mu.Lock()
	h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
	don := h.don
	h.mu.Unlock()

	// Send original request to all nodes
	for _, member := range h.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
