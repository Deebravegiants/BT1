### Title
Webhook shop/topic/webhook-id identity headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id` and `api_version` are read straight from HTTP headers and are never part of the signed payload. `Registry#process` trusts `HmacValidator.validate(request)` as proof of authenticity and then forwards these unsigned header values to the app's handler as if they were verified, breaking the identity binding `signed(body) == (shop, topic, webhook_id)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is computed by Shopify over the raw body and compared via `HmacValidator.validate`: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version`, however, are pulled directly from HTTP headers (`shopify_header`) and are **not** included in `to_signable_string`: [3](#0-2) 

`Registry#process` validates the HMAC and then immediately trusts these header-derived fields as authenticated identity, handing them to the app-level handler: [4](#0-3) 

The invariant this code implicitly claims is: *if the HMAC validates, then `request.shop`, `request.topic`, and `request.webhook_id` are the values Shopify actually attested to for this payload.* That invariant is false, because those header values are outside the signed byte range (`@raw_body` only). This is the same class of bug as the ThorChain report: a value that downstream code treats as “verified because a signature check just passed” is not itself covered by that signature check.

### Impact Explanation
Any actor who can obtain one legitimately-signed `(body, hmac)` pair for the target app — which any merchant can do simply by installing the app on their own (even free-trial) store and having Shopify deliver a webhook to it — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values. Since `HmacValidator.validate` only re-derives the signature from `@raw_body`, the forged request still validates successfully. The app's `WebhookHandler` then processes attacker-chosen body content under a **different shop identity** than the one that actually generated it, and/or dispatches it to a handler for a **different topic** than what was actually signed (e.g., replaying a `products/create` payload while claiming topic `app/uninstalled`, or attributing a payload to a victim shop it never came from). This crosses the tenant boundary the gem is expected to enforce and matches the Critical “cross-tenant access” impact category.

### Likelihood Explanation
The secret needed to forge a *new* HMAC is never required — only a single previously-delivered, validly-signed body from the same app (obtainable by any merchant who installs the app, a fully unprivileged action) plus the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged account is needed, matching the rules' unprivileged-internet-user constraint.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material, or otherwise cryptographically bind them before trusting them — e.g., have `to_signable_string` concatenate the header values with the raw body, or require applications to independently verify `shop` against the session/shop that installed the app rather than trusting the webhook header. At minimum, document clearly in `Registry#process` and `WebhookMetadata` that `shop`/`topic`/`webhook_id` are **not** covered by `HmacValidator.validate` and must not be treated as authenticated without additional out-of-band verification (e.g., cross-checking `shop` against a known, previously-stored installed-shop record).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver any real webhook, e.g. `products/create`, capturing the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (both are attacker-controlled/obtainable because the attacker legitimately owns that shop and can trigger the webhook topic).
2. Attacker replays the exact same body `B` and HMAC header `H` to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any other topic value, even one they never actually received)
   - `X-Shopify-Webhook-Id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request#initialize` accepts the headers, and `HmacValidator.validate(request)` recomputes the digest solely from `@raw_body` (`to_signable_string`), which is unchanged — validation passes.
4. `Registry#process` looks up the handler for the forged `topic` and invokes it with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: B, ...)`, causing the app to act (e.g., deactivate/clear data) as though `victim-shop.myshopify.com` sent this request, despite it never having originated from or been attested to for that shop/topic combination.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
