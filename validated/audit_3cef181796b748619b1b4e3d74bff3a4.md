Based on my review of the webhook processing flow, I found a solid analog to the M-6 pattern: a field used for tenant/shop identification that is not covered by the HMAC signature computation.

## Title
Webhook shop-domain header is not covered by the HMAC signature, breaking the binding between the verified body and the tenant identifier used to route webhook data - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by computing an HMAC over the raw request body only, while `shop`, `topic`, and other identifying fields are read from HTTP headers that are entirely outside the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` then hands `request.shop` straight to the app's handler as the tenant identifier, with no cryptographic binding between that value and the HMAC-verified payload.

### Finding Description
The equality that should hold is: *the shop identity attached to a webhook == the shop identity that produced the HMAC-signed bytes*. Instead the gem enforces only: *HMAC(raw_body, api_secret_key) == received_hmac*, and separately, unauthenticated: *shop = header["shop-domain"]*.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from a header that plays no role in the signature: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively from `to_signable_string` (i.e., the raw body) and compares it against the received HMAC — it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) to the handler as the tenant identifier, alongside the HMAC-verified body: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is the same for every shop that installs a given app, any unprivileged user who installs the app on their own store receives legitimately-signed webhook bodies for their own shop. That signed `(raw_body, hmac)` pair remains valid regardless of which `x-shopify-shop-domain` value is sent alongside it, since the header is never part of the signed material. An attacker can therefore replay a legitimately-signed webhook body while substituting an arbitrary `shop` header, and the gem will report it as validated and pass the forged shop value through to the host application's handler as `WebhookMetadata#shop`.

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` (documented as the tenant-identifying field) to decide which merchant's records to create, update, or delete. Because this field is not bound to the HMAC-covered bytes, an unprivileged attacker who can obtain any one validly-signed webhook for the app (e.g., by installing the app on their own store and triggering an event) can forge the tenant identifier for arbitrary target shops. This is a cross-tenant identity-binding break: the payload is bound to the attacker's shop, but the identifier consumed by the app is fully attacker-controlled.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops (the standard public-app model): the attacker only needs to install the app on a shop they control, capture one webhook delivery (raw body + `x-shopify-hmac-sha256`), and resend it to the app's webhook endpoint with a modified `x-shopify-shop-domain` (or `shopify-shop-domain`) header. No credentials, access tokens, or `api_secret_key` knowledge are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the verified payload before it is handed to `WebhookMetadata`/the handler, so that `HmacValidator.validate` fails whenever the shop header does not match the shop that actually produced the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` — both valid because they share the app's `api_secret_key`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and compares to `H` — validation succeeds because `H` was genuinely computed over `B` with the shared secret. [5](#0-4) 
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was signed for `attacker-shop.myshopify.com`. Any host application that trusts this `shop` value for tenant routing processes attacker-controlled data under the victim's identity.
