Based on the confirmed code paths, this is a clear identity-binding gap: the gem's HMAC verification for webhooks only covers the raw body, while the `shop` (and `topic`/`webhook_id`) values that the host app's handler trusts and acts on are taken from unauthenticated HTTP headers.

### Title
Webhook `shop` (and `topic`) identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers when building the `WebhookMetadata` passed to the app's handler. Because those fields are not part of the signed content, an attacker who possesses one valid `(body, hmac)` pair can replay it with arbitrary headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from request headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only this body HMAC via `Utils::HmacValidator.validate(request)`, then forwards the header-derived `shop`/`topic`/`webhook_id` unchanged into `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC solely against `to_signable_string` (the body), confirming headers are outside the trust boundary: [4](#0-3) 

The identity binding that should hold is: `hmac(secret, signed_bytes) == received_hmac` implies `signed_bytes == (body, shop, topic)`. In this implementation the binding actually only proves `hmac(secret, body) == received_hmac`; `shop` and `topic` are parsed from bytes that were never verified. This matches the report's bug class of "a field acted on but not covered by the HMAC" — here the acted-upon field is `shop` (used by the host app to select which tenant's data the webhook body applies to), not the `1e24` price field in the original Beanstalk report, but the identical binding-break structure.

As documented, the intended usage is for the host app's handler to key data updates off `data.shop` and `data.topic`: [5](#0-4) 

### Impact Explanation
Any unprivileged internet user who is able to install the app on their own store (a normal, unprivileged Shopify merchant) will receive genuine webhooks for their shop, each with a body and a correctly computed HMAC. Because the HMAC never covers the `shop`/`topic` headers, that same attacker can POST the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (or the `X-Shopify-Topic` header for a different topic than the one that produced the body). `Utils::HmacValidator.validate` still succeeds because the body and secret are unchanged, and the forged `shop`/`topic` flow straight through to the app's handler, which will process attacker-controlled webhook content under the identity of another tenant. Depending on how the host app uses `data.shop` (e.g., to select which store's records to update, or to make a decision that gates access), this enables cross-tenant data poisoning/confusion in the app's own persistence layer — this satisfies the "cross-tenant access" Critical impact category, since the attacker crosses the tenant boundary of `shop` without ever needing that victim's credentials.

### Likelihood Explanation
High. Exploitation requires only: (1) the ability to install the target app on an attacker-owned/free development store (an ordinary Shopify merchant action, not a privileged operation), (2) capturing one legitimate webhook body+HMAC that Shopify sends the attacker's own installation, and (3) issuing a raw HTTP POST directly to the app's public webhook route with modified headers — all doable by an unauthenticated internet actor with no access to the app's `client_secret` or any merchant's access token.

### Recommendation
Bind the header-derived identity fields into the HMAC-verified signable content, e.g. change `to_signable_string` to include a canonical representation of `shop`, `topic`, and `webhook_id` alongside the raw body (matching what Shopify actually signs, if Shopify's own webhook signature covers more than body — otherwise, at minimum have the host app independently authorize `shop` against a session/subscription record it created during registration rather than trusting the header value implicitly). Document clearly that `Request#shop`/`#topic` are unauthenticated unless independently cross-checked by the host application.

### Proof of Concept
```ruby
# Attacker owns "attacker-store.myshopify.com" and has installed the target app,
# so Shopify legitimately sends them a webhook with a valid HMAC over the body.
captured_body = '{"id":123,"note":"hello"}'
captured_hmac = "shopify-hmac-sha256-value-for-captured_body"  # valid, computed by Shopify with the real secret

# Attacker replays the exact same body+hmac but swaps the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,
  "x-shopify-shop-domain" => "victim-store.myshopify.com", # attacker-chosen, not signed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
# HmacValidator.validate(request) succeeds because it only checks captured_body against captured_hmac.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-store.myshopify.com", ...))
# The app's handler now processes attacker-controlled data under "victim-store.myshopify.com"'s identity.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
