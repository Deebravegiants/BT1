### Title
Webhook `shop` (and `topic`) header trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook HMAC verification in this gem only signs the raw request body, while the shop-identifying header (`X-Shopify-Shop-Domain`) that handlers rely on to determine tenant identity is never included in the signed bytes. This breaks the intended equality "shop the HMAC authenticates == shop the handler is told the event belongs to," allowing a webhook payload legitimately signed for one shop to be replayed with a forged shop-domain header claiming it belongs to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers, entirely outside the HMAC-covered bytes: [2](#0-1) 

`HmacValidator.validate` only checks `hmac(to_signable_string)`, i.e. `hmac(raw_body)`, against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the shop-domain header is "acted on" (used as the tenant identity for the event dispatched to the handler) but is not covered by the HMAC, any unprivileged internet user who has captured/observed one legitimately-signed webhook body+HMAC pair (e.g., by installing the app on their own shop and triggering a webhook, or observing one in transit to a publicly reachable endpoint) can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the attacker-chosen shop.

### Impact Explanation
This crosses a tenant boundary: an attacker can make a merchant's app process (attacker-supplied-body, but validly-signed) webhook data under the identity of an arbitrary other shop domain, without ever possessing that shop's credentials. Any app logic keyed off `WebhookMetadata#shop` (e.g., looking up/updating per-shop records, triggering per-shop side effects) can be manipulated cross-tenant, which is a **Critical - cross-tenant access** impact per the scope's rubric.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send an HTTP POST to the app's public webhook receiving endpoint (always internet-reachable), and (2) possession of one validly HMAC-signed raw body — trivially obtainable by installing the app on an attacker-owned shop and firing any webhook event, since the same `client_secret`-derived HMAC covers only the body and is otherwise shop-independent. No access token, `api_secret_key`, or privileged account is needed beyond the attacker's own (potentially free) shop install.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the header values to the signed body (e.g., verify that the shop for which the HMAC was computed server-side by Shopify matches the shop header via a separate authenticated channel, or require the consuming application to cross-check `request.shop` against the shop associated with the session/webhook_id independently). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (valid since `H = HMAC(secret, B)`).
2. Attacker sends a new POST to the app's webhook endpoint with the exact same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because the shop header is not part of `to_signable_string`. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker-controlled body as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
