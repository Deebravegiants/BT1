### Title
Infinite loop denial-of-service in GRANDPA `AncestryChain::ancestry` via crafted cyclic header proof - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA consensus verifier's `AncestryChain::ancestry` walk-back function has no cycle detection or depth bound. An unprivileged relayer submitting a GRANDPA consensus update (`ConsensusMessage::Polkadot`/`StandaloneChain`) can supply `unknown_headers` containing two or more headers whose `parent_hash` fields point to each other, forming a cycle. When the verifier walks from a target hash back to a base hash, it never terminates, hanging block execution and halting the chain — an on-chain analog of ALPINE-CVE-2022-0711's HAProxy infinite loop from malformed input.

### Finding Description
`AncestryChain::ancestry` is implemented as: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The loop terminates only when `current_hash == base` or the hash is missing from the map — there is no visited-set/cycle check and no maximum iteration bound. The `ancestry` BTreeMap is built directly from `finality_proof.unknown_headers`, a fully attacker-controlled vector of headers decoded from the submitted proof bytes: [2](#0-1) 

Since Substrate headers store their own hash as a function of their content but `parent_hash` is just an arbitrary field, an attacker can construct header `H1` (hash `h1`, `parent_hash = h2`) and header `H2` (hash `h2`, `parent_hash = h1`) and include both in `unknown_headers`. This makes the map `{h1: H1, h2: H2}` and calling `ancestry(base, h1)` for any `base` not equal to `h1`/`h2` oscillates `current_hash` between `h1` and `h2` forever, since both are always present in the map and neither equals `base`.

This function is reachable from two call sites in the verification path, both operating on attacker-controlled data:
1. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` directly on the `unknown_headers`-derived chain: [3](#0-2) 
2. `GrandpaJustification::verify_with_voter_set` builds a second `AncestryChain` from `self.votes_ancestries` (also decoded from the attacker-supplied justification bytes) and calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` per precommit, in addition to the external `finality_grandpa::validate_commit` call which uses the same `Chain::ancestry` implementation internally: [4](#0-3) 

Both `unknown_headers` and `votes_ancestries` originate from `proof: Vec<u8>` passed into `ConsensusClient::verify_consensus`, which is invoked by pallet-ismp when any user submits a GRANDPA consensus update message: [5](#0-4) 

Unlike the Pharos SPV proof verifier in this same repository, which explicitly bounds proof walk depth (`MAX_PROOF_DEPTH`, checked before walking) to prevent exactly this class of issue, the GRANDPA `AncestryChain::ancestry` has no equivalent bound: [6](#0-5) 

### Impact Explanation
Because Substrate block execution is not preemptively interrupted by an actual infinite native loop (weight metering estimates cost ahead of execution but cannot stop a runtime function that never returns), a crafted cyclic header set causes the collator/validator executing the extrinsic to hang indefinitely while processing that block. This stalls block production/finalization for the chain relying on this GRANDPA consensus client — a route unable to deliver messages and a potential full chain halt, matching the "denial of service" impact class described in the ALPINE-CVE-2022-0711 report (infinite loop from crafted input).

### Likelihood Explanation
Any unprivileged account can submit a consensus update extrinsic carrying a crafted `FinalityProof`/`GrandpaJustification` with a two-header parent-hash cycle inserted into `unknown_headers` or `votes_ancestries`. No signature over the state machine's actual authority set is required to trigger the hang, since the infinite loop executes purely from map lookups before/independent of full cryptographic acceptance in some code paths (e.g., the direct `headers.ancestry(from, target.hash())` call happens prior to `justification.verify(...)`). This makes the trigger low-cost and requires only crafting a decode-valid header, no cryptographic break.

### Recommendation
Add cycle/depth protection to `AncestryChain::ancestry`: track visited hashes (or a maximum iteration count bounded by `self.ancestry.len()` or a fixed `MAX_ANCESTRY_DEPTH`) and return `finality_grandpa::Error::NotDescendent` (or a new typed error) once the bound is exceeded or a hash is revisited, mirroring the `MAX_PROOF_DEPTH` guard already used in `modules/consensus/pharos/primitives/src/spv.rs`.

### Proof of Concept
1. Construct header `H2` with arbitrary content; compute its hash `h2`.
2. Construct header `H1` with `parent_hash = h2`; compute its hash `h1`.
3. Recompute `H2` so its own `parent_hash = h1` (headers can be freely constructed off-chain to satisfy this cycle since `parent_hash` is not otherwise constrained).
4. Submit a `ConsensusMessage::StandaloneChain`/`Polkadot` update with `finality_proof.unknown_headers = [H1, H2]` (or embed the cycle in the justification's `votes_ancestries`), with `finality_proof.block` set to `h1` so `target.hash() == h1`.
5. When `pallet_ismp` invokes `GrandpaConsensusClient::verify_consensus` → `verify_grandpa_finality_proof` → `AncestryChain::ancestry(from, h1)`, the loop alternates between `h1` and `h2` forever, hanging the executing node.
