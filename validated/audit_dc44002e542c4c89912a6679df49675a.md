### Title
Missing Concurrency Guard on `Wallet.addSeed()` Allows Race-Condition Bypass of `maxExtraSeeds` Cap - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet.addSeed()` in the `@exodus/wallet` module performs a classic check-then-act (TOCTOU) sequence — read current extra seeds, validate against the `maxExtraSeeds` cap, then write — without any concurrency serialization. This mirrors the root cause of the external report: `Leap.depositEth()` checks `totalRaised + _value > maxRaiseAmount` and only afterward mutates state, with no lock preventing interleaved calls from invalidating the check. In `wallet.js`, the sibling methods `create` and `import` are explicitly wrapped with `makeConcurrent({ concurrency: 1 })` to serialize execution, but `addSeed` (and `removeManySeeds`) are not, leaving the cap-enforcement invariant unprotected against concurrent invocation. [1](#0-0) 

### Finding Description
`addSeed` reads the current extra-seed list, checks the cap and duplicate mnemonic, then pushes and persists: [2](#0-1) 

Because this whole sequence is `async` and not wrapped in `makeConcurrent` (unlike `create`/`import` which explicitly are, at `concurrency: 1`): [3](#0-2) 

two or more near-simultaneous `addSeed({ mnemonic })` calls can each read the same `seeds` array from `#getExtraSeeds()` before either has written back via `#setExtraSeeds()`. Each call independently evaluates `seeds.length >= this.#maxExtraSeeds` against the stale pre-write snapshot and passes, then both proceed to push and persist — the second write overwriting/racing the first depending on storage semantics, but in the arbitrated-interleaving case (e.g., both reads occur before either write, then both writes occur sequentially) the final persisted `extraSeeds` array can exceed the configured `maxExtraSeeds` cap, exactly as the test suite assumes is impossible: [4](#0-3) 

The same unguarded read-check-write pattern also affects the duplicate-mnemonic check (`seeds.some(...)`), so two concurrent `addSeed` calls with the same mnemonic can both pass the "already present" check before either writes.

### Impact Explanation
`maxExtraSeeds` is a deliberate security/product invariant bounding how many seeds can be loaded into the wallet's keychain simultaneously (each extra seed is decrypted and held in the keychain per `unlock()`'s `#getExtraSeeds()` load loop). Bypassing this cap via a race:
- Violates an explicitly enforced and tested invariant (`caps max seeds at configured value`), undermining the correctness guarantee the wallet code depends on elsewhere.
- Could allow storing/loading more decrypted seed material into the keychain than the application is designed to safely manage, and could corrupt `#seedMetadataAtom` bookkeeping if seed IDs collide across racing writes.

I could not find, within the indexed content, a caller path (e.g. an exposed RPC/web3-provider surface) that lets an *external, unprivileged* party invoke `wallet.addSeed()` concurrently without in-wallet user interaction — `addSeed` appears to be a user-facing/settings feature rather than something exposed to arbitrary dApp/RPC callers. This limits confidence that the race is remotely triggerable by an attacker without already controlling code running with wallet-API access (e.g., a compromised UI component or a party who can fire two rapid IPC/RPC calls into the headless SDK). Given the indexing limits noted for this codebase, I cannot fully rule out an RPC-exposed trigger path; a full-repo Devin session would be needed to trace all callers of `wallet.addSeed` across `features/`, `sdks/headless`, and any browser-extension RPC bridge to confirm reachability.

### Likelihood Explanation
Low-to-Medium. The race window requires two `addSeed` (or `addSeed`+`removeManySeeds`) calls to be in flight concurrently against the same wallet instance. This is plausible if the calling surface (UI, headless SDK consumer, or an automated script driving the SDK) can be induced to fire two calls back-to-back, similar to how the external report's attacker races deposit/withdraw transactions. Without confirmed external/RPC reachability, likelihood is lower than the original on-chain analog, where any external account can trivially race transactions.

### Recommendation
Wrap `addSeed` and `removeManySeeds` with the same `makeConcurrent({ concurrency: 1 })` serialization already used for `create`/`import`, so the read-check-write sequence over `#getExtraSeeds`/`#setExtraSeeds` cannot be interleaved by concurrent calls.

### Proof of Concept
Conceptually (test-style), calling `addSeed` twice concurrently near the cap boundary should be added to the existing test suite to demonstrate the bypass:
```js
await wallet.import({ mnemonic })
await wallet.unlock()
await Promise.all([
  wallet.addSeed({ mnemonic: mnemonicA }), // both read seeds.length < maxExtraSeeds
  wallet.addSeed({ mnemonic: mnemonicB }), // before either write completes
])
// extraSeeds.length could exceed maxExtraSeeds, or metadata could be inconsistent
```
This exercises the same check-then-act gap as `Leap.depositEth()`'s `totalRaised` cap check versus its state mutation, referenced against the current unguarded implementation at [1](#0-0) .

  addSeed = async ({ mnemonic, label, compatibilityMode }) => {
    await this.#assertWalletIsUnlocked()

    const seed = await mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })
    const seedId = await getSeedId(seed)
    if (seedId === (await this.#primarySeedIdAtom.get())) {
      throw new Error('Seed already present')
    }

    const dateCreated = this.#clock.now()
    const data = { mnemonic, seed, dateCreated, compatibilityMode }
    const seeds = await this.#getExtraSeeds()
    if (seeds.length >= this.#maxExtraSeeds) {
      throw new Error('Maximum number of seeds reached')
    }

    if (seeds.some((seed) => seed.mnemonic === mnemonic)) {
      throw new Error('Seed already present')
    }

    seeds.push(data)
    await this.#setExtraSeeds(seeds)
    await this.#seedMetadataAtom.set((previous) => ({
      ...previous,
      [seedId]: { dateCreated, label, compatibilityMode },
    }))

    return this.#keychain.addSeed(data.seed)
  }
