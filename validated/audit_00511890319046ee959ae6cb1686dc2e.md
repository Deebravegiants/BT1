### Title
Escrow accounting credited before the actual token sweep completes, allowing fee‑on‑transfer / short‑transfer tokens to create unbacked escrow entries - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron `IntentGatewayV2.placeOrder()` predispatch branch, the escrow ledger `_orders[commitment][token]` is incremented with the *requested* (fee‑reduced) input amount **before** the tokens are actually swept from the `CallDispatcher` back into the gateway. The dust calculation is likewise derived from a balance snapshot taken *before* the sweep transfer executes, not from what the gateway actually receives. This mirrors the reported Aave `liquidityAdded` bug class: an accounting value is fixed using pre-transfer state while the real asset movement happens afterward, so the two can diverge.

### Finding Description
In `placeOrder`, when an order carries `predispatch` calldata, the flow is: [1](#0-0) 

1. `balance = IERC20(token).balanceOf(dispatcher)` is read (pre-sweep).
2. A `transferCalls[i]` is built to transfer the *full* `balance` from `dispatcher` to the gateway.
3. `dust = balance - requiredAmount` is computed and `_orders[commitment][token] += reducedInputs[i].amount` is credited to escrow — **all before** the sweep call actually executes.
4. Only after this accounting is finalized does `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` (line 449) perform the real transfer.

If `token` is a fee-on-transfer / rebasing / deflationary ERC-20 (or any token whose `transfer()` moves less than the nominal `balance` argument), the gateway will actually receive `balance - fee`, which can be less than `reducedInputs[i].amount`. The escrow map is nonetheless credited with the full `reducedInputs[i].amount`, creating an escrow liability that is not fully backed by tokens actually held by the contract.

This is exactly the bug class flagged in the external report: the accounting parameter (`liquidityAdded` there, `_orders[commitment][token]` here) is fixed using a value that does not reflect the asset transfer that has not yet occurred.

Notably, the canonical (non-Tron) `IntentGatewayV2.sol` already fixes this class of issue by snapshotting balances *before* the sweep and *after* the sweep and setting `order.inputs[i].amount` to the actually-received delta: [2](#0-1) 

The Tron fork does not carry this fix forward.

### Impact Explanation
Because the gateway's `_orders[commitment][token]` mapping backs later `withdraw()` payouts to solvers (on fill) or refunds to users (on cancel), crediting escrow beyond what is actually held by the contract creates a systemic shortfall: honest users' escrowed balances for other orders can be drained to cover the overstated entry, i.e., permanent loss/freezing of other users' funds once enough orders exploit the gap. This is a fund-insolvency bug reachable by any unprivileged caller of `placeOrder` supplying a fee-on-transfer input token with a crafted predispatch call, qualifying as Medium/High severity theft-of-funds / insolvency in the intents escrow.

### Likelihood Explanation
Any user can call `placeOrder` with `predispatch.call`/`predispatch.assets` set and an input token that takes a transfer fee (fee-on-transfer tokens are common on Tron/EVM chains and are explicitly acknowledged as a supported case by the sibling EVM contract's comments). No special privileges or governance action are required, only a matching malicious/fee-on-transfer token and a predispatch call that satisfies the `balance >= requiredAmount` guard.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the gateway's own balance before dispatching the sweep transfer, execute the sweep, then compute the actually-received amount as the post-sweep minus pre-sweep balance, and credit escrow (and emit `DustCollected`) using that measured amount rather than the pre-transfer `balance`/`reducedInputs[i].amount`.

### Proof of Concept
1. Create an order whose input token is a fee-on-transfer ERC-20 (e.g., 2% transfer fee) and whose `predispatch.call`/`assets` are crafted so the `CallDispatcher` ends up holding `balance == requiredAmount` (passing the `balance < requiredAmount` check).
2. Call `placeOrder`. The loop at lines 416-449 computes `dust = balance - requiredAmount = 0`, and credits `_orders[commitment][token] += reducedInputs[i].amount` (based on the full nominal amount).
3. `ICallDispatcher(dispatcher).dispatch(...)` then executes `transfer(gateway, balance)`, but due to the 2% fee, the gateway actually receives only `balance * 0.98`.
4. The escrow entry now overstates the gateway's real token holdings for this `token` by 2% of `balance`. Repeating across many orders (or scaling `balance` up) accumulates an unbacked liability that can be claimed via `fillOrder`/`cancelOrder` withdrawals, draining tokens escrowed for other legitimate orders.

            // Build sweep calls and snapshot gateway balances before the sweep.
            Call[] memory transferCalls = new Call[](inputsLen);
            uint256[] memory balancesBefore = new uint256[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                if (order.inputs[i].amount == 0) revert InvalidInput();
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 requiredAmount = order.inputs[i].amount;

                if (token == address(0)) {
                    uint256 balance = address(dispatcher).balance;
                    if (balance < requiredAmount) revert InsufficientNativeToken();
                    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
                    balancesBefore[i] = address(this).balance;
                } else {
                    uint256 balance = IERC20(token).balanceOf(dispatcher);
                    if (balance < requiredAmount) revert InvalidInput();
                    transferCalls[i] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    balancesBefore[i] = IERC20(token).balanceOf(address(this));
                }

                unchecked {
                    ++i;
                }
            }

            ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));

            // Measure actual received, emit dust for excess, update order.inputs.
            for (uint256 i; i < inputsLen;) {
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 received;
                if (token == address(0)) {
                    received = address(this).balance - balancesBefore[i];
                } else {
                    received = IERC20(token).balanceOf(address(this)) - balancesBefore[i];
                }

                if (received > order.inputs[i].amount) {
                    uint256 dust = received - order.inputs[i].amount;
                    emit DustCollected(token, dust);
                } else {
                    order.inputs[i].amount = received;
                }

                unchecked {
                    ++i;
                }
            }
