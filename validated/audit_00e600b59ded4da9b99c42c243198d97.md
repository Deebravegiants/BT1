### Title
Webhook Shop Attribution Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain` header used to attribute the webhook to a tenant is never included in the signed material. Any holder of a validly-signed `(body, hmac)` pair — trivially obtainable by any merchant who has installed the app, since a webhook they legitimately receive is signed with the app's single shared `api_secret_key`, not a per-shop secret — can resubmit that exact body/HMAC pair to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an independent, unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string and then builds `WebhookMetadata` using `request.shop` directly, with no cross-check that the signed body actually originated for that shop: [3](#0-2) 

`HmacValidator.validate` only proves that `secret` (the app-wide `api_secret_key`) was used to sign `verifiable_query.to_signable_string` — it says nothing about which shop the payload belongs to: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` and is therefore cryptographically bound to the signature: [5](#0-4) 

This is the same bug class as the analog report's "field acted on but not covered by the HMAC": the `shop` field is consumed by the handler (`WebhookMetadata.shop`) but is not part of the value that the HMAC actually authenticates. The identity binding that should hold is:

`shop authenticated by signature == shop attributed to the processed webhook data`

but the code only guarantees "body authenticated by signature", allowing `shop` to be substituted freely by anyone who can produce or replay a validly-signed body.

Because `api_secret_key` is shared by the app across all of its installations (it is not shop-specific), any merchant who has installed the app can generate/observe a legitimately-signed webhook `(body, hmac)` for their own store, then POST that exact pair to the app's webhook endpoint while setting `shopify-shop-domain`/`x-shopify-shop-domain` to a victim shop's domain. `Registry.process` will pass HMAC validation and invoke the handler with `WebhookMetadata.shop` set to the victim shop but `body` belonging to the attacker.

### Impact Explanation
This breaks the tenant boundary the app relies on to route webhook data to the correct shop's records. Depending on how the host application's `WebhookHandler#handle` implementations use `data.shop` (e.g., to look up which merchant's records to update, uninstall/reinstall state, or trigger side effects keyed by shop), an attacker-controlled shop can inject data attributed to a victim shop, causing cross-tenant data confusion/corruption — matching the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) merchant who has installed the app and can trigger and capture at least one real webhook for their own store (e.g., `orders/create`) — no access to `api_secret_key`, tokens, or privileged accounts is needed. This is a realistic "unprivileged internet user" position, and replaying an HTTP POST with modified headers is trivial once the (body, hmac) pair is known.

### Recommendation
Bind the shop identity to the signed material, mirroring `AuthQuery`: either include the `shop-domain` header value in the HMAC-signed content (not possible without protocol changes on Shopify's side, since Shopify itself signs only the body), or — more practically — cross-check `request.shop` against an out-of-band trusted source (e.g., only accept the shop domain from a session/installation record the app already trusts for the given webhook subscription/HTTP endpoint, rather than trusting the header value verbatim for tenant attribution). At minimum, document/require host applications to independently verify `data.shop` against their own installation records before using it as a trust boundary, since the gem's own signature does not cover it.

### Proof of Concept
1. App has one shared `api_secret_key`. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g. creates an order) and captures the resulting legitimate webhook request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a forged HTTP request to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: 2024-01

   B
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which equals `H`, so validation passes: [6](#0-5) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.
