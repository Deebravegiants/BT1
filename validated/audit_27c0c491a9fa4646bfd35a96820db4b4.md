### Title
Missing L2 Sequencer Uptime Check in `SimplexPaymaster` Chainlink Price Feeds Allows Undervalued Gas Payments - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native-asset/USD feed and the token/USD feed, deployed on Arbitrum, Optimism, and Base (all Chainlink-recommended L2s requiring a sequencer uptime check) per the price-feed address list. The staleness guard only checks `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`; it never consults the L2 Sequencer Uptime Feed, so a temporary L2 sequencer outage (and the subsequent grace period on restart) can let stale/manipulable prices be treated as valid.

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` fetches Chainlink data and only validates the answer's sign and its recency against `maxOracleAge`: [1](#0-0) 

This is used by `_tokenPrice`, which computes the token/native exchange rate charged to UserOp senders: [2](#0-1) 

`_tokenPrice` is invoked from `_fetchDetails` (called during `_validatePaymasterUserOp`) to derive `tokenPrice`, which the base `PaymasterERC20` and this contract's `_prefund`/`_erc20Cost` logic use to compute the `prefundAmount` an unprivileged UserOp sender must pay in ERC-20 tokens for their sponsored gas: [3](#0-2) [4](#0-3) 

The paymaster is registered/deployed for chains including Arbitrum, Optimism, and Base, which are exactly the Optimistic-rollup L2s Chainlink flags as requiring an `L2SequencerUptimeFeed` check: [5](#0-4) 

No such check exists anywhere in `SimplexPaymaster.sol`; the errors defined only cover `StaleOraclePrice` and `InvalidOraclePrice` — there is no `L2SequencerUnavailable` or equivalent guard: [6](#0-5) 

### Impact Explanation
Any unprivileged party can submit a paymaster-sponsored ERC-4337 UserOperation ("bandwidth purchaser" of gas) through this permissionless paymaster (validation/pricing logic requires no admin permission — it is driven purely by `_validatePaymasterUserOp`/`_fetchDetails`/`_prefund` on user-supplied `paymasterData`). If the Arbitrum/Optimism/Base sequencer stalls, the Chainlink feeds stop updating for the sequencer-down duration, and during the subsequent Chainlink-recommended grace period after the sequencer resumes, stale answers are indistinguishable from fresh ones by this contract's `updatedAt`-only check. During this window an attacker can submit UserOps priced off a stale token/native rate that undervalues the ERC-20 relative to the native asset actually consumed as gas, causing the paymaster to prefund UserOps for far less token value than the native gas it spends via the EntryPoint. This directly drains the paymaster's own EntryPoint deposit/native balance (funded by treasury), a real loss of protocol funds, without requiring any privileged role — matching the "unbacked debit"/fund-loss class described in the report, just realized through gas-fee mispricing instead of a lending-protocol undercollateralized loan.

### Likelihood Explanation
L2 sequencer downtime events are infrequent but have occurred historically on Arbitrum/Optimism, and the exploit window includes not just the outage itself but the entire Chainlink-recommended grace period after sequencer restart, during which price-consumers are expected to reject stale data. Because `SimplexPaymaster` is permissionless to interact with (any UserOp sender picks the token and triggers `_fetchDetails`/`_prefund`), exploitation requires no privileged access — only timing the submission to a sequencer-outage/grace-period window, making this a realistic, if opportunistic, attack.

### Recommendation
Add a Sequencer Uptime Feed check (per Chainlink's L2 example) inside `_getOraclePrice` (or a wrapper it calls) in `evm/src/utils/SimplexPaymaster.sol`, reverting with a new `L2SequencerUnavailable` error if the sequencer feed reports down or if less than the grace period has elapsed since it came back up, for every chain where this paymaster is deployed on an Optimistic L2 (Arbitrum, Optimism, Base per the indexer's chain list).

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum/Optimism/Base with `nativeOracle` and a token's `tokenOracle` both Chainlink feeds, as configured via `RegisterToken`/`UpdateParams` governance requests.
2. Simulate (or wait for) the L2 sequencer going down; Chainlink feed `updatedAt` timestamps stop advancing while `block.timestamp` (fed by L1 batches) may lag or jump once the sequencer resumes.
3. During the outage or the grace period immediately after restart, submit a UserOp with `paymasterData` mode `0x00`/`0x02` selecting a token whose USD value has moved (e.g., dropped) relative to the native asset since the last on-chain update, but where `block.timestamp - updatedAt` is still `<= maxOracleAge`.
4. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` returns the stale/incorrect price; `_prefund`/`_erc20Cost` compute `prefundAmount` off this rate.
5. The attacker pays a `prefundAmount` in tokens that is worth substantially less than the native gas the EntryPoint actually deducts from the paymaster's deposit, repeatable across multiple UserOps to drain the paymaster's funded native balance.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
