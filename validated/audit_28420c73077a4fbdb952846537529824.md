### Title
Unchecked RAY index growth can overflow market totals and permanently freeze a market - (File: common/src/rates/scaling.rs)

### Summary
The pool’s RAY accounting can reach a state where `scaled_amount * index` no longer fits in `i128`, before the configured `MAX_BORROW_INDEX_RAY` cap is reached. Once that happens, interest accrual panics, and because withdrawals, repayments, liquidations, and rate-model updates all accrue first, the affected market becomes permanently unusable. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`scaled_to_original` converts scaled pool shares into RAY-denominated value using `scaled.mul(env, index)`, while `Ray::mul` uses checked `i128` fixed-point multiplication and panics on overflow. [1](#0-0) [4](#0-3) 

Market utilization performs this multiplication for both total scaled debt and total scaled supply during interest accrual. [5](#0-4) 

The intended borrow-index ceiling does not prevent the overflow: `update_borrow_index` multiplies the old index by the interest factor before comparing the result to `MAX_BORROW_INDEX_RAY`, and the accrual path can already panic while deriving total debt or supply from the stored scaled balances and index. [6](#0-5) [7](#0-6) 

The repository contains a regression demonstrating this exact condition: a one-billion-token, 18-decimal market at sustained high utilization reaches the `i128` value ceiling before the index cap, after which both withdrawal and repayment fail with `MathOverflow`. [8](#0-7) 

### Impact Explanation
This causes permanent freezing of user funds and prevents debt resolution in the affected market. Once the stored scaled balance and index cross the representable-value boundary, `withdraw` and `repay` panic during their mandatory accrual step, liquidation paths that load the market encounter the same failure, and even replacing the rate model cannot recover because `replace_rate_model` accrues under the old state before writing new parameters. [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) 

### Likelihood Explanation
The path is permissionless: any authorized caller can create supply collateral, borrow against another collateral position, and invoke `update_indexes(caller, assets)` for the target market as time advances. [13](#0-12) [14](#0-13) 

The practical trigger requires an extremely large market and sustained high utilization under a high-rate segment, but no privileged role, leaked key, oracle manipulation, or third-party exploit is required. The encoded test reaches the condition with one billion 18-decimal units supplied and 98% borrowed, then repeatedly advances ledger time until `update_indexes` fails. [15](#0-14) 

### Recommendation
Compute index-growth and market-total intermediates in a wider representation such as `I256`, or explicitly compare against the maximum representable product before multiplication. Before committing a new index, cap it at both `MAX_BORROW_INDEX_RAY` and a market-specific bound such as `i128::MAX / scaled_total`, using saturating division and wide multiplication so an overflowing candidate clamps instead of panicking. Apply the same invariant to the supply index and add regression coverage that proves accrual, repayment, withdrawal, liquidation, and rate-model replacement remain executable at the boundary. [6](#0-5) [16](#0-15) [17](#0-16) 

### Proof of Concept
1. Create or select a market with 18-decimal asset units and an interest curve capable of sustained high rates. [18](#0-17) 
2. Supply `1_000_000_000 * 10^18` raw units of the target asset to the pool through `supply(caller, account_id, spoke_id, assets)`. [19](#0-18) [20](#0-19) 
3. From an account holding sufficient independent collateral, borrow 98% of that market through `borrow(caller, account_id, borrows, to)`. [21](#0-20) [22](#0-21) 
4. Periodically call `update_indexes(caller, assets)` while advancing ledger time; eventually a call reverts with `MathOverflow` while the stored index remains below `MAX_BORROW_INDEX_RAY`. [14](#0-13) [23](#0-22) 
5. Attempt `withdraw` or `repay`; both revert because the same overflowing accrual occurs before their accounting logic. [12](#0-11)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();
```
