### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `shop` value that is subsequently handed to the app's handler as the tenant identity comes from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header, not from anything covered by that signature [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate_signature` computes the HMAC purely over that signable string [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers [5](#0-4)  and are never included in the signed bytes. `Registry.process` passes `request.shop` straight through to the app's handler as the authoritative tenant identity: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [6](#0-5) . The gem's own documentation instructs consuming apps to treat `data.shop` as the shop the webhook belongs to and to key background work off it (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6) .

Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that has installed a given app (it is not a per-shop secret), any tenant that has installed the app can capture a genuinely Shopify-signed webhook body for its own shop and replay it to the app's webhook endpoint while substituting a different `shopify-shop-domain` header. `HmacValidator.validate` will still pass, since the header is not part of the signed content, and `Registry.process` will invoke the handler with the attacker-chosen `shop` value attached to the victim-shop-unrelated body. This breaks the intended binding: `shop header used by handler == shop that produced/authorized the signed body`.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem, following its documented pattern, will attribute webhook data and downstream side effects (queuing jobs, writing records, invalidating caches, etc.) to a shop domain that the attacker fully controls and that was never verified by the signature. Depending on how the consuming app persists/keys data by `data.shop`, this can lead to writing or associating attacker data under another store's identifier, i.e., cross-tenant access as defined in the Critical impact bucket.

### Likelihood Explanation
Exploitation only requires being a legitimate (self-service) installer of the target app on one's own store — no privileged credentials, leaked secrets, or access to `client_secret` are needed. The attacker needs no more than the ability to receive one real webhook for their own shop and replay it with a modified header to the app's public callback endpoint. This satisfies the "unprivileged internet user" bar.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) as part of the signed payload considered by `HmacValidator`, or independently verify the `shop-domain` header against the known/registered set of shops for the currently processing session/webhook subscription before dispatching to the handler.
- At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata`/`Registry.process` to explicitly warn that `data.shop` is unauthenticated header data and must not be trusted for tenant-scoping decisions without additional verification (e.g., cross-checking against the shop tied to the specific webhook subscription/session store).
- Consider using per-shop verification (e.g., confirming the shop exists in the app's own session store before trusting `data.shop`) as a mitigating control in the library's default flow.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real `orders/create` webhook signed by Shopify with the app's `client_secret`.
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header from that request.
3. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `Digest.hexencode(...)` against `@raw_body`, which is unchanged [8](#0-7) .
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's body [6](#0-5) , causing the app to process/store data as if it belongs to the victim shop.
