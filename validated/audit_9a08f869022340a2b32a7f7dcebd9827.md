Audit Report

## Title
Collator can permanently censor a specific queued DMP message via selective hashing while passing the weak `check_enough_messages_included_basic` rule - (File: cumulus/pallets/parachain-system/src/lib.rs)

## Summary
`Pallet::enqueue_inbound_downward_messages` only invokes the weak `check_enough_messages_included_basic`, which merely requires at least one full message when any hashing occurs, unlike the parallel HRMP path which invokes the size-budget-aware `check_enough_messages_included_advanced`. A collator can hash away an arbitrary target DMP message while including one unrelated small full message, passing both the basic check and the MQC-head assertion, and permanently advance `LastProcessedDownwardMessage` past the censored message so it is stripped from consideration in all future blocks.

## Finding Description
`enqueue_inbound_downward_messages` calls only `downward_messages.check_enough_messages_included_basic("DMQ")` [1](#0-0) , whose logic merely asserts `full_messages.len() >= 1` if any `hashed_messages` exist [2](#0-1) . In contrast, the HRMP path invokes `check_enough_messages_included_advanced`, supplying `AbridgedInboundMessagesSizeInfo` derived from `messages_collection_size_limit()` and channel max message size, which asserts that the full-messages size plus the worst-case first hashed message size exceeds the max budget — i.e., that hashing was actually necessary [3](#0-2) [4](#0-3) . DMP has no equivalent invocation.

Because `extend_downward` (used for full messages) and `extend_with_hashed_msg` (used for hashed messages) compute identical chain contributions for the same message data, a collator that correctly hashes the target message produces the same `dmq_head` as one that delivers it in full [5](#0-4) , so the final `assert_eq!(dmq_head.head(), expected_dmq_mqc_head, ...)` cannot detect the substitution [6](#0-5) .

Critically, the loop over `hashed_messages` still advances `LastProcessedDownwardMessage` even though the hashed message was never passed to `T::DmpQueue::handle_messages` [7](#0-6) . That pointer directly drives `drop_processed_messages`, called in every future `do_create_inherent`, which strips already-"processed" messages from the raw relay-supplied collection before it is abridged into full/hashed messages [8](#0-7) [9](#0-8) . Once dropped this way, the censored message can never again be offered as a full message and never reaches the DMP queue/XCM executor — its hash is permanently recorded as the chain link, but its content is discarded from all future block-building.

## Impact Explanation
A single malicious or bribed collator, acting through the standard `set_validation_data` inherent path, can permanently drop a specific downward message (e.g., an XCM instruction transferring funds or executing a `Transact` intended to benefit a specific user) from ever being executed on the parachain, while the block remains fully valid to the relay chain (correct MQC head, valid weight/size accounting). This is a targeted, durable censorship/fund-freeze vector requiring only ordinary collator block-authoring privileges for a single block — the effect (advanced `LastProcessedDownwardMessage`) persists in on-chain state without further collusion.

## Likelihood Explanation
The weak check is confirmed present verbatim in the codebase at the cited location, and the stronger, size-aware check exists and is actively used for the parallel HRMP path in the same file just a few dozen lines away, demonstrating both that the maintainers are aware of this exact censorship class and that the fix pattern already exists but was not applied to DMP. The attack requires only publicly known DMQ message content (visible on the relay chain) to compute a correct hash — no forged signatures or privilege escalation needed, only the ordinary ability of a rotation-selected collator to author one block.

## Recommendation
Apply the same fix used for HRMP: replace `check_enough_messages_included_basic("DMQ")` with `check_enough_messages_included_advanced`, supplying an `AbridgedInboundMessagesSizeInfo` derived from `messages_collection_size_limit()` and the maximum DMP message size, so a collator cannot hash a message unless the size budget was genuinely exhausted. Additionally, consider not advancing `LastProcessedDownwardMessage` for messages counted only via their hash unless it is guaranteed they were truly delivered/consumed.

## Proof of Concept
1. Construct `AbridgedInboundDownwardMessages` with `full_messages = [msg_1]` (small) and `hashed_messages = [hash(msg_k), hash(msg_3)]`, omitting the victim message `msg_k`.
2. Call `check_enough_messages_included_basic("DMQ")` — it passes since `full_messages.len() == 1 >= 1`, despite `msg_k` never being delivered.
3. Compute `expected_dmq_mqc_head` by chaining `extend_downward(msg_1)`, then `extend_with_hashed_msg(hash(msg_k))`, then `extend_with_hashed_msg(hash(msg_3))`, and call `enqueue_inbound_downward_messages` with this head — the `assert_eq!` at line 1362 passes.
4. Observe `LastProcessedDownwardMessage` is now set past `msg_k`'s position (from the loop at lines 1343-1354), while `T::DmpQueue::handle_messages` was only ever invoked with `msg_1`'s data.
5. Simulate a subsequent honest `do_create_inherent` call with the same raw relay downward-message list (still containing `msg_k` since the relay chain doesn't know it was "skipped") and confirm `drop_processed_messages` (line 1293) strips `msg_k` from consideration, permanently preventing it from being offered as a full message in any future block.

	/// Drop all the messages up to `last_processed_msg`.
	pub fn drop_processed_messages(&mut self, last_processed_msg: &InboundMessageId) {
		let mut last_processed_msg_idx = None;
		let messages = &mut self.messages;
		for (idx, message) in messages.iter().enumerate().rev() {
			let sent_at = message.sent_at();
			if sent_at == last_processed_msg.sent_at {
				last_processed_msg_idx = idx.checked_sub(last_processed_msg.reverse_idx as usize);
				break;
			}
			// If we build on the same relay parent twice, we will receive the same messages again
			// while `last_processed_msg` may have been increased. We need this check to make sure
			// that the old messages are dropped.
			if sent_at < last_processed_msg.sent_at {
				last_processed_msg_idx = Some(idx);
				break;
			}
		}
		if let Some(last_processed_msg_idx) = last_processed_msg_idx {
			messages.drain(..=last_processed_msg_idx);
		}
	}

	/// Check that the current collection contains as many full messages as possible, taking into
	/// consideration the collection constraints.
	///
	/// The `AbridgedInboundMessagesCollection` is provided to the runtime by a collator.
	/// A malicious collator can provide a collection that contains no full messages or fewer
	/// full messages than possible, leading to censorship.
	pub fn check_enough_messages_included_advanced(
		&self,
		collection_name: &str,
		size_info: AbridgedInboundMessagesSizeInfo,
	) {
		// We should check that the collection contains as many full messages as possible
		// without exceeding the max expected size.
		let AbridgedInboundMessagesSizeInfo { max_full_messages_size, first_hashed_msg_max_size } =
			size_info;

			full_messages_size = full_messages_size.saturating_add(msg.data().len());

		// is a max size message.

			full msgs size: {}, first hashed msg max size: {}, max full msgs size: {}",

			full_messages_size,
			first_hashed_msg_max_size,
