### Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values used to route and attribute the webhook are read directly from unauthenticated HTTP headers. Because the app's webhook secret (`api_secret_key`) is shared across every shop that has the app installed, any shop that can legitimately receive one valid `(body, hmac)` pair from Shopify can replay that exact body/HMAC combination while substituting the `shopify-shop-domain` header for a different (victim) shop, and `Utils::HmacValidator.validate` will still accept it.

### Finding Description
`Utils::VerifiableQuery` requires only `hmac` and `to_signable_string`. For `ShopifyAPI::Webhooks::Request#to_signable_string`, the signable content is exactly `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from an HTTP header that is never included in that signable string: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (along with `topic`, `body`, `api_version`, `webhook_id`) to build the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

The identity binding that should hold is: `shop attributed in WebhookMetadata == shop that produced/authorized the signed body`. Because the HMAC only binds `body == body`, and the same `api_secret_key` is used by Shopify to sign webhooks for *every* shop that installed the app, an attacker who controls or has installed the app on their own shop can capture a legitimate `(raw_body, hmac)` pair delivered to their endpoint and re-POST it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `HmacValidator.validate` recomputes the HMAC over the (unchanged) body with the shared secret and it matches, so `Registry.process` proceeds and invokes the handler with `data.shop` set to the victim's domain.

### Impact Explanation
This breaks tenant isolation for any host application that uses `request.shop`/`WebhookMetadata#shop` to decide which merchant's records to create, update, or delete (a very common pattern, e.g. "look up the shop's local record by `data.shop` and apply `data.body`"). An attacker-controlled shop can cause writes/reads to be attributed to an arbitrary other shop known only by its `.myshopify.com` domain, which is public information. This is a cross-tenant access primitive rooted in the gem's own webhook verification code, not application misuse of a documented contract — the gem presents `request.shop` as available only after `HmacValidator.validate` succeeds, implying it is trustworthy, but it is not covered by the signature.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-owned development/trial shop (a normal, unprivileged action any merchant can take), (2) capturing one legitimate webhook body/HMAC pair sent to the attacker's own endpoint, and (3) replaying it to the app's public webhook endpoint with a modified shop-domain header naming the victim shop. No access token, `client_secret`, or privileged credential is required, and the shared `api_secret_key` makes the forged HMAC valid.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the verified content, e.g. include `shopify-shop-domain` (and other routing headers) in `to_signable_string`, or independently verify that the shop domain in the header corresponds to a shop session/installation the host app expects for this specific webhook subscription before trusting `WebhookMetadata#shop`. At minimum, document that `request.shop` is unauthenticated and must be cross-checked by the host application against a known installed-shop list.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify POSTs a signed webhook to the app's endpoint. Capture the raw body `B` and the `x-shopify-hmac-sha256` header `H`.
2. Because the app uses one `api_secret_key` for all installed shops, `H` is a valid HMAC-SHA256 of `B` under that shared secret regardless of which shop is named in the domain header — confirmed by `HmacValidator.validate_signature`, which only checks `hmac(to_signable_string=raw_body)`: [4](#0-3) 
3. Send a new POST to the app's webhook endpoint with the exact same raw body `B` and `hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)` which passes (body unchanged), then invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `victim-shop.myshopify.com`: [5](#0-4) 
5. Any host application logic keyed on `data.shop` (e.g., locating the victim's stored session/access token to act on their behalf, or writing attacker-supplied body content under the victim's tenant record) is executed against the victim shop using attacker-supplied content.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
