Audit Report

## Title
CORS wildcard origin allowlist bypass via unbounded suffix match - (File: `core/services/gateway/network/httpserver.go`)

## Summary
`isAllowedOrigin` in the Gateway's user-facing HTTP server validates wildcard CORS allowlist entries (e.g. `*.remix.com`) by stripping the `*.` prefix and then calling `strings.HasSuffix(originHost, allowedHost)` with no domain-boundary (dot) check. An attacker who controls a domain that merely ends with the same characters as the configured suffix (e.g. `evilremix.com` vs. allowed `remix.com`) will have their origin incorrectly accepted, causing the server to reflect that origin in `Access-Control-Allow-Origin`.

## Finding Description
The relevant logic is: [1](#0-0)  Scheme and port are compared exactly, and the exact-host branch (`originHost == allowedHost`) at [2](#0-1)  is correctly implemented, but the wildcard branch performs a bare suffix comparison after stripping `*.`, with no requirement that the character preceding the matched suffix be a `.`. This means `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, incorrectly treating `evilremix.com` as a subdomain of `remix.com`. This function is invoked directly from the internet-facing request handler: [3](#0-2)  which reads the unauthenticated, attacker-controlled `Origin` header and, if `isAllowedOrigin` returns true, reflects it into `Access-Control-Allow-Origin`. There is no additional validation elsewhere in the file that would catch this — `splitURL` only parses scheme/host/port and does not enforce any boundary semantics: [4](#0-3) .

## Impact Explanation
When an operator enables `CORSEnabled` with a wildcard entry (e.g., `*.mycompany.com`) intending to scope browser access to their own subdomains, an attacker who registers an unrelated domain ending in the same suffix (e.g. `evilmycompany.com`) can have their origin accepted by the Gateway. The browser will then permit an attacker-controlled page to make cross-origin requests to the Gateway's user-facing API (routed through `ProcessRequest`) and read the JSON-RPC responses, which can include workflow/vault-related data intended only for legitimately allowlisted origins. This is a concrete CWE-346 origin-validation/allowlist-bypass affecting the internet-facing Gateway HTTP endpoint.

## Likelihood Explanation
Exploitation requires only: (1) the Gateway operator has enabled `CORSEnabled=true` with at least one wildcard entry in `CORSAllowedOrigins` — a supported, documented configuration pattern; and (2) an attacker registers/controls a domain string ending in the same characters as the allowed suffix and lures a browser with network access to the Gateway to visit it. No node compromise, credentials, or privileged role is required — the attack is triggered purely via a normal unauthenticated HTTP request with a crafted `Origin` header, which any unprivileged client can send.

## Recommendation
Require a domain boundary in the wildcard comparison, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
so that `evilremix.com` no longer matches an allowlist entry of `*.remix.com`.

## Proof of Concept
1. Configure the Gateway with:
```toml
CORSEnabled = true
CORSAllowedOrigins = ["https://*.remix.com"]
```
2. Send an HTTP request to the Gateway's `/user` path with header `Origin: https://evilremix.com`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilremix.com`, confirming the bypass. Equivalently, a Go unit test calling `httpServer.isAllowedOrigin("https://evilremix.com")` with `CORSAllowedOrigins = []string{"https://*.remix.com"}` returns `true`, which should be `false`.
