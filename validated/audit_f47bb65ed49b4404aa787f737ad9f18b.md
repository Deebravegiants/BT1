## Analog Finding

### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with the webhook's `shop` field [1](#0-0) . In reality, the HMAC only authenticates the raw request body bytes; the `shop` (and `topic`) values are read straight from unauthenticated HTTP headers and are never included in the signed content, breaking the equality `shop_authenticated == shop_delivered_to_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all derived from headers that are never mixed into the signable string [3](#0-2) .

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header [4](#0-3) . It never binds the `shop-domain` header into the digest.

`Registry.process` performs exactly that HMAC check and then, on success, immediately constructs `WebhookMetadata` using `request.shop` verbatim and hands it to the app's handler [5](#0-4) . There is no cross-check that the HMAC-verified body actually belongs to the shop named in the header.

Because a single app's `client_secret` is shared across every shop that installs the app (this is the same secret used everywhere in the gem, e.g. `Context.api_secret_key` in `HmacValidator.validate` [6](#0-5) ), any shop that has legitimately installed the app can obtain a `(raw_body, hmac)` pair that is valid under that shared secret. An attacker who installs the target app on their own store receives genuine webhook deliveries with a correctly computed HMAC over their own store's body. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` calls the handler with `shop:` set to the attacker-chosen victim domain [7](#0-6) .

This is the same class of bug as the report: an identity-relevant field (`shop`) is acted upon by downstream logic (tenant routing in the handler) without being included in the value that is actually verified (the HMAC over the body) — an equality the code assumes holds (`verified_body_owner == header_shop`) but never enforces.

### Impact Explanation
Apps are explicitly told in this gem's own docs to key their persistence/business logic off `data.shop` from `WebhookMetadata` [8](#0-7) , and are told that `Registry.process` already "verifies the request did indeed come from Shopify" [9](#0-8) . Because `shop` is unauthenticated, any merchant with a genuine installation of the app can forge webhook deliveries labeled as an arbitrary other tenant, causing cross-tenant data confusion (e.g. having attacker-controlled order/customer data written into a different shop's storage bucket) within apps that follow this gem's documented usage pattern exactly.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-controlled shop (no special privileges beyond being a Shopify merchant) and capturing one real webhook delivery to obtain a valid `(body, hmac)` pair; the header can then be freely rewritten in a replayed request. This does not require access to `api_secret_key`, an access token, or any credential leak — the attacker legitimately possesses a valid signature via their own installation.

### Recommendation
Bind `shop` (and ideally `topic`) into the HMAC-verified content, or otherwise cross-validate the header-derived `shop` against a value embedded in the verified body / a registered subscription record before invoking the handler, so the equality `verified_owner == shop_passed_to_handler` is actually enforced by `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; register a webhook (e.g. `orders/create`).
2. Capture a genuine webhook POST: headers include `x-shopify-hmac-sha256: <valid_hmac>` and `x-shopify-shop-domain: attacker.myshopify.com`, with some `raw_body`.
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `client_secret` [6](#0-5) .
5. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` [7](#0-6) , and the app processes attacker-controlled data as if it belonged to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
