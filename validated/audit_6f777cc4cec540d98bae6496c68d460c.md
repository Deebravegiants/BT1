### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while the `shop` value that downstream code treats as the tenant identity is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` to route the payload to the app's handler, so the binding "HMAC-verified bytes == bytes the shop identity is taken from" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the HMAC computation [2](#0-1) . The HMAC itself is only checked against the body via `Utils::HmacValidator.validate`, which calls `to_signable_string` (i.e., the raw body) [3](#0-2) .

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and passes it straight to the app's `WebhookHandler#handle`: [4](#0-3) 

Because Shopify apps share a single `client_secret` across every shop that installs them, a valid `(body, hmac)` pair generated for one shop's webhook is cryptographically valid for **any** shop under the same app. The equality that should hold is:

`shop bound by HMAC == shop used for tenant routing`

but instead the code has:

`shop used for tenant routing = header value (not signed) != shop implicitly associated with the signed body`

**Attack path (no privileged credentials required):**
1. Attacker installs the app on their own (attacker-controlled) shop — a completely normal, unprivileged action any merchant can perform.
2. Attacker triggers/receives a legitimate webhook (e.g. `orders/create`) from Shopify for their own shop. This request has a valid `X-Shopify-Hmac-Sha256` header computed over the raw body with the app's `client_secret`.
3. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but swaps the `X-Shopify-Shop-Domain` header to the victim shop's domain.
4. `Utils::HmacValidator.validate` succeeds because the signature only covers the (unmodified) body.
5. `Registry.process` builds `WebhookMetadata` with `shop: victim_shop_domain` and invokes the app's handler, which (per this gem's own documented pattern, e.g. looking up a merchant's session/store by `data.shop`) processes attacker-controlled webhook content under another tenant's identity.

This is a genuine authentication/tenant-binding gap in this gem's own webhook-processing code (`Registry.process`), not merely a misuse of an API by the host app — the gem itself supplies `request.shop` as a trusted-looking field in `WebhookMetadata` without binding it to the signed content.

### Impact Explanation
Critical — cross-tenant access. Any app relying on `WebhookMetadata#shop` (as `Registry.process` and this gem's own docs recommend) to determine which merchant's stored data/session to touch can be made to attribute attacker-controlled webhook content to an arbitrary victim shop, since the shop identity is never covered by the signature that is supposed to authenticate the request.

### Likelihood Explanation
Medium-High. The prerequisite (being able to install the app on one's own shop and receive at least one real webhook) is trivial and requires no privileged credentials, stolen tokens, or `api_secret_key` access — it only requires normal, unprivileged use of the app as any other merchant would.

### Recommendation
1. Include the shop domain (and ideally topic/api-version) in the signed material, or otherwise cryptographically bind the `shop-domain` header to the HMAC before trusting it for routing.
2. At minimum, in `Registry.process`, cross-check that the `shop` header value matches an app-side record of which shop the webhook subscription was registered for (e.g., look up the topic+shop pairing) rather than trusting the header verbatim once the body HMAC passes.
3. Document explicitly that `WebhookMetadata#shop` is not itself HMAC-protected so host apps do not assume tenant isolation from it alone.

### Proof of Concept
```ruby
# Attacker captures a real webhook Shopify sent them for their own shop "attacker.myshopify.com":
raw_body = '{"id":1,"note":"payload"}'
valid_hmac_b64 = real_signature_from_shopify_for_attacker_shop # base64, computed by Shopify with app's client_secret

# Attacker replays it to the app's webhook endpoint, only changing the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # unchanged, still valid for this raw_body
  "x-shopify-shop-domain" => "victim.myshopify.com", # swapped
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "123",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (Utils::HmacValidator only validates raw_body),
#    handler.handle is invoked with WebhookMetadata(shop: "victim.myshopify.com", body: parsed attacker payload)
```
