### Title
SSRF-style credential leak: `TokenExchange.exchange_token` sends `client_secret` to an unsanitized, JWT-controlled host - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the request host for the `/admin/oauth/access_token` POST (which carries `client_id`/`client_secret`) directly from the JWT `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other place in the gem that turns a caller-supplied "shop" string into an outbound request host (`Oauth.authorize`/`validate_auth_callback`, `TokenExchange.migrate_to_expiring_token`) either relies on the shop coming from a value already bound by an HMAC-verified query, or explicitly calls `ShopValidator.sanitize!` first. `exchange_token` does neither validation.

### Finding Description
`JwtPayload#shop` simply strips the scheme off the raw `dest` claim: `@dest.gsub("https://", "")` [1](#0-0) . The only checks performed on the JWT are signature/exp/nbf/aud in `decode_token`/`initialize` [2](#0-1)  — there is no constraint that `dest` be a `*.myshopify.com`/`*.myshopify.io`/trusted domain, unlike the dedicated `ShopValidator.sanitize!`/`TRUSTED_SHOPIFY_DOMAINS` allow-list used elsewhere [3](#0-2) .

In `exchange_token`, this unvalidated `dest_shop` is used directly to construct the session that determines the outbound request host: [4](#0-3) 

`HttpClient#initialize` builds `@base_uri` from `session.shop` (unless `Context.api_host` is set) [5](#0-4) , and the request body containing `client_secret` is POSTed to that host [6](#0-5) .

Contrast this with the sibling method `migrate_to_expiring_token`, in the same module, which explicitly sanitizes the shop before building the session and sending the same kind of `client_secret`-bearing request: [7](#0-6) 

This breaks the identity binding the rules describe: "a JWT claim trusted without being bound" and "a host validated versus the host that receives the ... `client_secret`". The equality that should hold is:
`host(dest_shop) == host(sanitized/trusted Shopify domain)`
but instead `exchange_token` uses `host(dest_shop) == host(raw, attacker-influenced JWT claim)`.

### Impact Explanation
A session token is intentionally usable by front-end embedded-app JS (App Bridge) and is not itself proof that `dest` is a genuine `*.myshopify.com` host — the JWT signature only proves the app's secret was used to sign it, not that its `dest` was constrained to a legitimate shop domain. If an attacker who controls a page performing token-exchange calls (or a compromised/rogue embedded-app iframe context) can influence or supply a session token with an attacker-controlled `dest` value, `exchange_token` will happily send `client_id`+`client_secret` (the app's own OAuth credentials, per Critical impact class "theft or exfiltration of ... the app's `client_secret`") in a `POST /admin/oauth/access_token` request to that attacker-controlled host. This is a credential-exfiltration/SSRF-with-app-credentials primitive: the app's `client_secret` leaves the process bound for a host chosen from unvalidated JWT content rather than an allow-listed Shopify domain.

### Likelihood Explanation
Requires the attacker to get an application to call `TokenExchange.exchange_token` with a token whose `dest` is attacker-controlled or otherwise not restricted to a genuine myshopify domain — the JWT must still be signed with the app's `client_secret`, but the gem does not validate that `dest` is a Shopify domain, so any legitimately-issued (or leaked/forwarded) token with an off-domain `dest` claim is sufficient. There's no additional exploit needed against Shopify's servers themselves; the vulnerability lives entirely in this gem's failure to apply the `ShopValidator` allow-list that it uses everywhere else.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`) before constructing `shop_session`/`HttpClient`, raising `Errors::InvalidShopError` if the `dest` claim does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Obtain/craft a session token whose payload has `dest` set to an attacker-controlled host, e.g. `https://attacker.example` (or a value that is technically signed by the app's secret but not constrained to `*.myshopify.com`), keeping `aud` equal to the app's `api_key` and a valid signature under `Context.api_secret_key` — see the shape used for tests in [8](#0-7) .
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `jwt_payload.shop` returns `attacker.example` unmodified [1](#0-0) ; `Session.new(shop: dest_shop)` is built with no `ShopValidator` check [9](#0-8) .
4. `HttpClient.new(session: shop_session, base_path: "/admin/oauth")` sets `@base_uri = "https://attacker.example"` [5](#0-4) , and the POST to `access_token` sends `client_id`/`client_secret`/`subject_token` to `attacker.example` instead of Shopify.
