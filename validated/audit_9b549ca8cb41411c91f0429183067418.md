### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is authenticated via `Utils::HmacValidator.validate`, which HMAC-verifies the object returned by `to_signable_string`. For webhook requests, `to_signable_string` returns only the raw request body: [1](#0-0) 

However, the `shop` and `topic` fields used downstream to route and process the webhook are read directly from HTTP headers, which are **not** included in the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then dispatches to the topic handler using the unauthenticated `topic` and `shop` header values, passing `request.shop` straight into `WebhookMetadata` given to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`bytes covered by HMAC == bytes the application uses to attribute the event to a tenant (shop)`

Here that equality is broken: `to_signable_string == raw_body` but `WebhookMetadata#shop == headers["x-shopify-shop-domain"]`, a value the HMAC never touches.

### Impact Explanation
Because the HMAC only proves that the sender (or someone with the `api_secret_key`, i.e. Shopify) produced *some body B*, and does not bind B to a specific shop, a fixed `(body, hmac)` pair valid for one shop's webhook remains cryptographically valid when replayed with an arbitrary `shop-domain` header. In a multi-tenant app that trusts the `shop` field from `WebhookMetadata` to decide which tenant's records/session to update (a very common pattern, e.g. `MyApp.find_session(data.shop)` then writing `data.body` into that tenant's store), an unprivileged internet user who owns/operates their own Shopify store can:
1. Trigger any webhook topic they've subscribed to on their own store (they legitimately receive a validly-HMAC'd payload from Shopify for events on their own shop).
2. Replay that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint, substituting the victim's `shop-domain` header.
3. The HMAC check in `HmacValidator.validate` still passes because it only ever hashes `raw_body`, and the handler processes the body as if it belongs to the victim tenant, since the header value is passed uncontested via `WebhookMetadata#shop`.

This is a cross-tenant data-attribution/confusion vector (the specific class flagged as Critical: cross-tenant access) caused entirely by the gem's own webhook verification code, not by host-application misuse of a documented API — the gem hands the caller a `shop` value that it itself never authenticated, alongside a boolean "HMAC valid" result that gives false confidence that the whole tuple (topic, shop, body) is trustworthy.

### Likelihood Explanation
Exploitation requires only:
- The attacker controls (or can install the app on) at least one legitimate Shopify store to obtain one real, validly-signed webhook body/HMAC pair for a topic the target app subscribes to.
- Network access to the target app's public webhook endpoint (no `api_secret_key`, access token, or privileged account needed).
- The host app trusting `WebhookMetadata#shop`/`#topic` for tenant/topic routing, which is the standard, documented usage pattern shown in this gem's own docs and tests (`data.shop`, `data.topic` used directly by handlers).

Likelihood is High given how commonly `shop` is used as the tenant key in webhook handler implementations, and the attack requires no compromise of any secret.

### Recommendation
Extend the signed material for webhook requests to include the identity-critical headers (at minimum `shop` and `topic`), or otherwise cryptographically bind them, e.g. by having `to_signable_string` incorporate a canonical concatenation of `shop`, `topic`, and `raw_body`, matching how `AuthQuery#to_signable_string` binds `shop`/`host` for OAuth callbacks. Alternatively, document explicitly (and enforce in `Registry.process`) that callers must independently verify `request.shop` against a known/installed shop for the session being acted upon before trusting `WebhookMetadata#shop`, and reject webhooks whose shop cannot be corroborated by stored session state.

### Proof of Concept
1. App subscribes to `orders/create` and stores/keys data by `WebhookMetadata#shop`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and creates an order, causing Shopify to send a legitimately HMAC-signed webhook:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id":1,...}`
3. Attacker captures `raw_body` and the `hmac-sha256` header value.
4. Attacker POSTs the same `raw_body` and `hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `raw_body`, so `HmacValidator.validate` succeeds (line references above). `Registry.process` dispatches `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` to the handler, which will process the attacker's data under `victim-shop.myshopify.com`'s tenant context. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
