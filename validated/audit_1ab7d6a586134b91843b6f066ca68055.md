### Title
Creator fee claims are permanently frozen if a blacklisted-by-USDC creator address is entitled to accrued fees, with no receiver override even after `transferCreator` - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out a creator's accrued USDC fee balance strictly to `msg.sender`, with no `_receiver` parameter. Fee attribution is keyed by creator address at the time `Zap` calls `accrue`, and that address is fixed to `creatorBalance[creator]` in `FeeVault`'s storage — `Bonding.transferCreator` only changes future attribution, it never moves an already-accrued balance to a new key. If the address currently holding an accrued `creatorBalance` becomes blacklisted by USDC (Circle-style blacklist on the exact ERC20 this protocol uses as its fee/settlement currency), `claim()`'s `safeTransfer(msg.sender, amount)` will revert every time it is called by that address, and no other address can ever pull those already-accrued funds.

### Finding Description
`FeeVault.claim()` reads and zeroes `creatorBalance[msg.sender]` and then does an unconditional `safeTransfer(msg.sender, amount)`: [1](#0-0) 

There is no way to specify an alternate recipient, unlike `claimProtocol()`, which pays a separately admin-configurable `feeTo` address rather than `msg.sender`: [2](#0-1) 

Crucially, the balance is keyed by the creator address recorded at the moment `Zap` invoked `accrue` (which reads `Bonding.tokenInfo(token).creator` for attribution), not by a mutable pointer that tracks `transferCreator`: [3](#0-2) 

`Bonding.transferCreator` only relabels who is credited for *future* accruals on that token — it does not, and cannot, move the creator's already-accumulated `creatorBalance[oldCreator]` entry inside `FeeVault` to the new creator's key: [4](#0-3) 

Since the protocol's entire fee and settlement currency is USDC (accrued and paid out of `FeeVault` in USDC), the exact asset class in the original report — a centrally-blacklistable stablecoin — is the one actually held here: [5](#0-4) 

If the creator's address is ever added to USDC's blacklist (for any reason unrelated to the protocol itself — e.g., flagged elsewhere, sanctioned, compromised and reported), every future `claim()` call from that address reverts inside `SafeERC20.safeTransfer`, and there is no `transferCreator`-driven or admin-driven path to redirect the already-accrued `creatorBalance` to a fresh, non-blacklisted address. The funds are permanently stuck in `FeeVault`.

### Impact Explanation
This is a permanent freeze of creator funds legitimately earned by an unprivileged, reachable actor (any token creator calling `Zap.createToken` and accumulating fees via ordinary buy/sell activity on their token). Given fee volume accrues continuously (0.25% of every buy/sell on a token, forever, both pre- and post-graduation), the frozen amount can be arbitrarily large and grows without bound while the creator remains blacklisted, satisfying the "permanent freezing of trader/creator/LP funds" bar for a valid High-severity finding.

### Likelihood Explanation
Reaching this state requires only that (a) a creator has accrued a nonzero `creatorBalance` (trivially achieved by launching any token and letting normal trading occur), and (b) that the creator's specific address is later placed on USDC's blacklist for any reason. Because USDC blacklisting is a real, externally-triggerable event outside the protocol's control (and is not gated by protocol privilege), any long-lived creator address is exposed to this risk over time; the protocol has no mitigation once it occurs.

### Recommendation
Add a `claim(address receiver)` variant (or a `setClaimRecipient(address)` self-service redirect) so a creator with a stuck balance can nominate an alternate receiving address, mirroring how `claimProtocol()` already decouples the caller from the payout address via `feeTo`. Additionally, consider making `transferCreator` optionally sweep/reassign the outstanding `creatorBalance[oldCreator]` to the new creator address so that fee-attribution transfer also carries forward already-accrued, unclaimed balances.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken(...)` and it trades normally; `Zap._accrueFee` forwards a portion of every buy/sell fee to `FeeVault.accrue(token, C, creatorAmount, protocolAmount, isBuy)`, growing `creatorBalance[C]`.
2. `C`'s address is added to USDC's blacklist (an event entirely outside the protocol's control, exactly as in the referenced report).
3. `C` calls `bonding.transferCreator(token, newAddress)` to try to redirect future fees — this succeeds and updates `TokenInfo.creator`, but `FeeVault.creatorBalance[C]` (the already-accrued balance) is untouched, since it is only ever written by `accrue` keyed on the creator address passed in at accrual time.
4. `C` (or anyone acting for `C`) calls `FeeVault.claim()` — `msg.sender` must equal `C` to read a nonzero `creatorBalance[msg.sender]`, but the subsequent `usdc.safeTransfer(msg.sender, amount)` reverts because `C` is blacklisted.
5. There is no other function in `FeeVault` or `Bonding` that can move `creatorBalance[C]` to a new key or specify an alternate transfer target — the funds are permanently stranded.

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```markdown
## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```
