Based on my investigation, I found a genuine analog to the Sherlock M-12 pattern (using an unadjusted balance where a fee/hook-adjusted value should be used) inside `fungible_asset.move` itself, but I want to be transparent about the limits of what I could confirm before presenting it.

### Title
`fungible_asset::is_balance_at_least` / `is_address_balance_at_least` silently use raw store balance and skip the `derived_balance` dispatch hook that `balance()` is forced to respect - (File: `aptos-move/framework/aptos-framework/sources/fungible_asset.move`)

### Summary
Aptos' `dispatchable_fungible_asset` module is the framework's own analog to Isomorph's "fee-adjusted collateral valuation": it lets a fungible-asset issuer register a `derived_balance` hook so a token whose true redeemable value differs from its raw ledger balance (e.g. a deflationary/fee-charging token, mirroring the Synthetix exchange-fee case) can report an economically correct value. [1](#0-0)  The framework enforces use of this hook for plain balance reads: `fungible_asset::balance()` explicitly `assert`s that no `derived_balance` hook exists and tells callers to use `dispatchable_fungible_asset::balance/derived_balance` instead. [2](#0-1)  However, the sibling sufficiency-check functions `is_balance_at_least` and `is_address_balance_at_least` have no such guard — they read the raw `FungibleStore.balance` (or `ConcurrentFungibleBalance`) unconditionally, with no check for `has_balance_dispatch_function`. [3](#0-2) 

### Finding Description
`dispatchable_fungible_asset::is_derived_balance_at_least` only routes through the dispatch hook when one is registered; when none exists it falls back to `fungible_asset::is_balance_at_least`, which is correct for non-dispatchable assets. [4](#0-3)  The problem is that `fungible_asset::is_balance_at_least` and its friend `is_address_balance_at_least` are also `public`/`public(friend)` and can be (and are) called directly by other modules — e.g. `aptos_account.move` calls `is_address_balance_at_least` directly — bypassing the dispatch-aware wrapper entirely. Unlike `balance()`, which aborts with `EINVALID_DISPATCHABLE_OPERATIONS` if a `derived_balance` hook is registered for the store's metadata, `is_balance_at_least`/`is_address_balance_at_least` perform no such check and will happily answer sufficiency questions using the raw, un-hooked ledger balance for a token whose registered `derived_balance` function says the true value is different (higher or lower).

This is the exact shape of the Vault_Synths bug: one code path (`balance()`, analogous to Vault_Lyra's fee-aware `priceCollateralToUSD`) correctly forces fee/hook-adjusted valuation, while a parallel path (`is_balance_at_least`, analogous to Vault_Synths' unadjusted valuation) silently omits it.

### Impact Explanation
Any downstream custody logic that gates a fund-affecting decision (e.g., "does this account have enough of asset X to satisfy a check") using `fungible_asset::is_balance_at_least` / `is_address_balance_at_least` (or `aptos_account`'s wrapper around it) on a dispatchable FA with a non-identity `derived_balance` hook will make that decision on a value that can diverge from the economically real, fee/hook-adjusted balance. Depending on the sign of the divergence (e.g., a hook that reports less true value than raw balance, similar to Synth exchange fees devaluing the asset), this could let a check pass when it should fail, potentially enabling an operation predicated on sufficient funds when the true redeemable/transferable value is lower. I was not able to fully read `aptos_account.move`'s exact call site and downstream logic within this session's tool budget, so I cannot confirm with certainty whether this specific inconsistency currently reaches a fund-movement decision (as opposed to a purely informational check) in shipped framework code — this is the key gap in fully proving a mainnet custody impact.

### Likelihood Explanation
The asymmetry is unconditional and always present in the deployed framework code whenever a dispatchable FA registers a `derived_balance` function — no privileged action is needed to trigger it, since it's simply an existing exported function with inconsistent guarding relative to its sibling `balance()`. That said, likelihood of actual custody loss depends entirely on whether some caller uses `is_balance_at_least`/`is_address_balance_at_least` as a gate for a value-transferring operation rather than just a read-only display, which I could not fully confirm from `aptos_account.move` in the time available.

### Recommendation
Add the same `has_balance_dispatch_function` guard used in `balance()` to `fungible_asset::is_balance_at_least` and `is_address_balance_at_least` (or, safer, deprecate/restrict their direct external use and force all sufficiency checks through `dispatchable_fungible_asset::is_derived_balance_at_least`, mirroring how `balance()` forces callers to `dispatchable_fungible_asset::balance`).

    /// Check whether the balance of a given store is >= `amount`.
    public(friend) fun is_address_balance_at_least(
        store_addr: address, amount: u64
    ): bool acquires FungibleStore, ConcurrentFungibleBalance {
        if (store_exists_inline(store_addr)) {
            let store_balance = borrow_global<FungibleStore>(store_addr).balance;
            if (store_balance == 0
                && concurrent_fungible_balance_exists_inline(store_addr)) {
                let balance_resource =
                    borrow_global<ConcurrentFungibleBalance>(store_addr);
                balance_resource.balance.is_at_least(amount)
            } else {
                store_balance >= amount
            }
        } else {
            amount == 0
        }
    }
