### Title
Missing Chainlink round-completeness check in SimplexPaymaster's oracle pricing leads to stale/incorrect gas pricing - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` consumes Chainlink's `latestRoundData()` but discards `roundId` and `answeredInRound`, validating only `answer > 0` and a timestamp-based staleness bound. It never checks round completeness, so a stale or carried-over round answer that still satisfies the timestamp bound can silently be accepted as the current price used to charge every ERC-4337 UserOp submitter for gas.

### Finding Description
`_getOraclePrice` is: [1](#0-0) 

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
```

The tuple returned by `latestRoundData()` is `(roundId, answer, startedAt, updatedAt, answeredInRound)`, per the `AggregatorV3Interface` defined at the top of the same file: [2](#0-1) 

`roundId` and `answeredInRound` are both discarded (`(, int256 answer,, uint256 updatedAt,)`), so the contract never verifies `answeredInRound >= roundId`, i.e. whether the returned answer actually belongs to a completed round versus a stale answer carried forward from a prior round (a known Chainlink aggregator behavior during feed outages/aggregator-phase transitions). The timestamp-only check is insufficient because a carried-over round can still report an `updatedAt` inside the staleness window while representing genuinely outdated/incomplete price data — this is the exact bug class from the referenced report.

This function is the sole price source for both `_tokenPrice` (per-token gas conversion used in `_fetchDetails`, invoked on every paymaster-sponsored UserOp validation) and `swapAndDeposit` (fee-recycling swap slippage bound): [3](#0-2) [4](#0-3) 

### Impact Explanation
`_fetchDetails` (via `_tokenPrice`/`_getOraclePrice`) computes `tokenPrice`, which `PaymasterERC20` uses to derive `prefundAmount = _erc20Cost(maxCost, maxFeePerGas, tokenPrice)` charged to any unprivileged UserOp sender that pays gas through this paymaster (the ERC-4337 "bandwidth purchaser" analog buying blockspace/gas). An unchecked stale/incomplete round answer can misprice tokens relative to the native asset, causing solvers/users to be overcharged or undercharged for gas, and can also corrupt the `amountOutMin` slippage bound in `swapAndDeposit`, allowing an unfavorable swap execution price during fee recycling. This is a fund-impacting mispricing issue reachable purely by submitting a normal paymaster-sponsored UserOp, matching Medium severity.

### Likelihood Explanation
Any address can trigger the vulnerable code path simply by submitting an ERC-4337 UserOp that uses this paymaster (mode 0x00 or 0x02); no privileged role is required. The trigger condition (a stale/carried-over Chainlink round that still passes the timestamp check) depends on Chainlink feed behavior during outages or aggregator-phase transitions, which is an externally-triggerable, previously-documented failure mode rather than a purely theoretical one.

### Recommendation
Capture `roundId` and `answeredInRound` from `latestRoundData()` and revert if `answeredInRound < roundId` (and optionally if `startedAt == 0`), mirroring the original report's recommendation:

```solidity
(uint80 roundId, int256 answer, uint256 startedAt, uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
if (answeredInRound < roundId || startedAt == 0) revert StaleOraclePrice(address(oracle), updatedAt);
if (block.timestamp - updatedAt > maxOracleAge) revert StaleOraclePrice(address(oracle), updatedAt);
```

### Proof of Concept
1. Chainlink's `USDC/USD` (or native/USD) aggregator enters a state where the underlying phase aggregator has not produced a new completed round, but `latestRoundData()` returns a previous round's data with `answeredInRound < roundId` while `updatedAt` still falls within `maxOracleAge` (e.g., due to phase transition or feed operator delay patterns documented for Chainlink feeds).
2. Any user submits a UserOp specifying this paymaster with a registered token; `_validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` is executed at `evm/src/utils/SimplexPaymaster.sol:662-676`.
3. `_getOraclePrice` passes both checks (`answer > 0`, timestamp within `maxOracleAge`) despite the round being stale/incomplete, and returns the incorrect price.
4. `prefundAmount` is computed from this incorrect `tokenPrice`, causing the UserOp sender to be charged an incorrect (potentially favorable-to-attacker or loss-causing-to-treasury) amount of ERC-20 tokens for gas.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
