### Title
Attacker-suppressible Aquarius LP pricing makes collateralized accounts unliquidatable - ([File: contracts/price-aggregator/src/providers/aquarius.rs])

### Summary

An account can add a small Aquarius LP collateral leg while the pool is priceable, then withdraw enough liquidity from that same Aquarius pool to push its computed pool value below the configured `min_pool_value_wad`. Subsequent strict price resolution rejects the LP price, so liquidation reverts while loading account risk. Because pro-rata liquidation must value every collateral leg, even a dust LP position blocks the entire account. [1](#0-0) [2](#0-1) 

### Finding Description

`AquariusLpSource` explicitly makes a pool unpriceable when its computed value is below `min_pool_value_wad`. [3](#0-2)  During resolution, `read` calculates `pool_value_wad` from the LP price and total share supply and returns `InsufficientAquariusLiquidity` when it is below that floor. [4](#0-3) 

The controller resolves prices through `PriceAggregatorClient::prices`, which is the strict path rather than the non-reverting `quotes` status path. [5](#0-4)  Liquidation calls `calculate_account_risk_totals` before it normalizes repayment or seizure. [2](#0-1)  That risk calculation loads markets for all supply positions and prices each collateral leg. [6](#0-5)  Consequently, one invalid LP collateral leg aborts the whole liquidation transaction.

Supplying the blocking leg does not itself require a successful collateral valuation: `process_deposit` checks entry gates and position limits, transfers the measured deposit, and merges the pool result. [7](#0-6)  The account owner can therefore attach the dust leg while the Aquarius pool remains above the floor and before suppressing its pool value.

### Impact Explanation

A liquidator calling `liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)` cannot repay any part of the account while the LP price is invalid, regardless of which debt asset is offered, because plan construction fails before repayment is transferred. [8](#0-7)  `SeizeMode::Credit` does not avoid the issue because both modes use the same liquidation plan. [9](#0-8) 

While the attacker keeps the Aquarius pool below the configured value floor, its debt is temporarily protected from liquidation and its collateral remains unavailable to liquidators. If underlying collateral decays or accrued interest makes the account insolvent during the outage, the protocol can accumulate bad debt that cannot be liquidated until the pool is refilled or governance changes the oracle configuration.

### Likelihood Explanation

The attack requires the borrower to control enough Aquarius liquidity to lower the listed pool's total value below `min_pool_value_wad`, or to act when ordinary withdrawals already leave the pool near that floor. Mainnet LP listings configure substantial floors, including `200000000000000000000000` WAD for `AQUAUSDC_LP`, so this is capital-dependent rather than free. [10](#0-9)  No privileged protocol role, leaked key, malicious router, or oracle misbehavior is required; withdrawing one's own Aquarius liquidity is an ordinary venue action explicitly available to an unprivileged user.

### Recommendation

Do not let a single collateral leg's unavailable price unconditionally abort the entire liquidation plan. Options include:

- Price collateral legs independently and construct a liquidation plan from the subset with usable prices.
- Exclude an unpriceable collateral leg from seizure while still permitting debt repayment against the remaining collateral.
- Add a tightly bounded fallback for LP collateral that temporarily treats the unavailable leg as zero collateral value instead of failing resolution.
- Enforce a minimum USD value or minimum percentage-of-pool ownership for Aquarius LP collateral legs, so a dust leg cannot poison liquidation.
- Ensure permissionless bad-debt cleanup has a path that does not require a current LP price once insolvency has already been established.

### Proof of Concept

1. Create or use an account in the spoke where the target LP asset is collateralizable:
   `supply(attacker, 0, spoke_id, [(ordinary_collateral_key, sufficient_amount)])`.
2. While the Aquarius pool value is above `min_pool_value_wad`, add a dust LP leg to the same account:
   `supply(attacker, account_id, spoke_id, [(lp_hub_asset_key, dust_amount)])`.
3. Borrow through:
   `borrow(attacker, account_id, [(debt_hub_asset_key, borrow_amount)], None)`.
4. On Aquarius, withdraw attacker-owned LP liquidity until `price_wad * total_shares / share_unit < min_pool_value_wad`.
5. Wait until the account has `health_factor < 1`, or allow interest/price movement to make it unhealthy.
6. Any liquidator submits:
   `liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)`.
7. `build_liquidation_plan` loads all collateral assets, the aggregator rejects the LP leg with `InsufficientAquariusLiquidity`, and the transaction reverts before debt repayment or collateral seizure. [11](#0-10) [1](#0-0)
