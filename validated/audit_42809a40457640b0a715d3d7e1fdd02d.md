### Title
Webhook `shop`/`topic` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . However, the tenant-identifying fields it then acts on — `shop` and `topic` — are read straight from attacker-controllable HTTP headers and are never included in the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` and compares it to the `hmac` field: [3](#0-2) 

But `Request#shop` and `Request#topic` are pulled from the `x-shopify-shop-domain` / `shopify-topic` headers, independent of the signed payload: [4](#0-3) 

`Registry.process` trusts these header-derived values to route and identity-stamp the webhook: it looks up the handler by `request.topic` and constructs `WebhookMetadata` using `request.shop` as the tenant identity handed to the application's handler: [5](#0-4) 

The broken equality is:
`shop/topic bound by HMAC` (∅, not present in `to_signable_string`) `!= shop/topic acted on by Registry.process` (`request.shop`, `request.topic` from unauthenticated headers).

Because every shop installation of a given app shares the same `client_secret` (and thus the same HMAC key used to sign all of that app's webhooks, per Shopify's webhook signing model), an attacker who controls *any* shop with the app installed can:
1. Trigger a webhook to their own shop (any topic the app subscribes to) and capture the resulting `raw_body` + `x-shopify-hmac-sha256` value — a valid HMAC pair for their own body content, computed with the app's `client_secret`.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but with a forged `x-shopify-shop-domain` header set to a victim shop, and (since `topic` is also unauthenticated) an arbitrary `x-shopify-topic` header to select which handler in the registry gets invoked.
3. `HmacValidator.validate` passes because it only checks body integrity against the shared `client_secret`, not the shop/topic bound to it.
4. `Registry.process` dispatches to the handler chosen by the attacker's forged topic and passes `WebhookMetadata.new(shop: <victim shop>, body: <attacker-controlled body>, ...)`.

This breaks the identity binding "the shop attributed to this webhook" == "the shop that actually generated it," letting an attacker impersonate a different (victim) tenant's webhook stream while controlling both the topic dispatched and the JSON body content.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the host application's webhook handlers key business logic (e.g., updating stored shop data, processing compliance/mandatory topics such as `shop/redact`, `customers/redact`, `app/uninstalled`, or syncing order/customer data) off `WebhookMetadata#shop`, believing it to be an authenticated Shopify-originated identity. An attacker who legitimately installs the app on their own store can forge events "from" any other shop that has installed the same app, injecting attacker-chosen topic/body pairs attributed to a victim tenant. Depending on what the host app's handlers do with `shop` + `body` (e.g., writing merchant configuration, revoking access, deleting data on `shop/redact`), this can lead to cross-tenant data corruption or forced state changes for merchants the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even trial/free) installer of the target app on some shop — no privileged credentials, TLS interception, or social engineering needed — and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with forged headers, which is standard unprivileged internet-user capability. The core defect (signing only the body, not shop/topic) is unconditional in the gem's design, so likelihood is high wherever a host app is directly exposed to `Webhooks::Registry.process`.

### Recommendation
Bind the `shop` and `topic` headers into the signed material checked by `HmacValidator`, or otherwise re-verify that `request.shop` corresponds to a shop domain the app has independently authenticated (e.g., cross-check `request.shop` against a stored, `access_token`-linked shop record) before trusting it for dispatch or handler input, and validate `request.shop` with `ShopValidator.sanitize!` prior to any downstream use.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker-shop.myshopify.com"
# and receives a legitimate webhook, e.g. for topic "orders/create":
raw_body   = '{"id": 1, "note": "attacker-controlled payload"}'
real_hmac  = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)

# Attacker replays the exact body+hmac, changes the shop + topic headers,
# to point at the victim shop and a sensitive registered topic:
forged_headers = {
  "x-shopify-topic"       => "shop/redact",              # attacker-chosen, unauthenticated
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),  # still valid, since it only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true  (only raw_body is checked)
# Handler invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled body)
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
