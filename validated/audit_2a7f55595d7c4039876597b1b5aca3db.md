### Title
Underflow panic in `target_orders.calc_pnl_x`/`calc_pnl_y` update in `process_withdraw()` can permanently freeze all LP withdrawals - (File: `program/src/processor.rs`)

### Summary
`process_withdraw()` recomputes the cached pnl-tracking snapshot `target_orders.calc_pnl_x` / `calc_pnl_y` using bare `.unwrap()` on `checked_sub`, mixing a decimal-normalized cached value (`x1`/`y1`, computed from `total_pc_without_take_pnl` *before* PnL extraction) with a raw-token-derived, re-normalized withdrawal amount (`pc_amount`/`coin_amount`) and the pnl `delta_x`/`delta_y`. Any rounding drift introduced by the decimal conversion round-trip (`normalize_decimal_v2` → raw amount → `normalize_decimal_v2` again) can make the subtraction underflow and panic, aborting the transaction. This is directly analogous to the `xERC4626.beforeWithdraw()` bug: a stale/derived cached accounting variable (`storedTotalAssets` there, `target_orders.calc_pnl_x/y` here) is subtracted against a value computed from a different code path (accrued rewards vs. decimal-normalized pnl), and if the subtrahend can exceed the minuend, every withdrawal that hits this code path reverts, potentially trapping all LPs' funds in the pool.

### Finding Description
In `Processor::process_withdraw` (program/src/processor.rs), the sequence is: [1](#0-0) 

`x1`/`y1` are computed from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` *before* `calc_take_pnl` mutates them, and `calc_take_pnl` also returns `delta_x`/`delta_y` (the sys-decimal-normalized pnl amounts actually credited to `need_take_pnl_pc/coin`, via `Calculator::calc_take_pnl`): [2](#0-1) 

Later, after computing `coin_amount`/`pc_amount` (the tokens to be sent to the withdrawing LP, derived from the **post-pnl** `total_pc_without_take_pnl`/`total_coin_without_take_pnl` via floor division): [3](#0-2) 

the code updates the cached invariant snapshot using unchecked-panic arithmetic: [4](#0-3) 

`normalize_decimal_v2(pc_amount, ...)` re-normalizes a value that was itself derived by floor-dividing an *already-normalized-then-restored* quantity. Because `pc_pnl_amount`/`coin_pnl_amount` (which produce `delta_x`/`delta_y`) go through `restore_decimal` and then get applied via integer division of `pnl_numerator/pnl_denominator` twice (`calc_take_pnl` at lines 228-243 above), and `pc_amount` goes through a separate `Floor` division in `InvariantPool::exchange_pool_to_token`, the two paths do not reconcile exactly at the integer level. When decimals differ between `pc_decimals`/`coin_decimals` and `sys_decimal_value`, or fee ratios produce a remainder, `normalize_decimal_v2(pc_amount) + delta_x` can exceed `x1` by one or more units, causing `.checked_sub(...).unwrap()` to panic.

This mirrors the `xERC4626` root cause exactly: a globally shared cached state variable (`target_orders.calc_pnl_x`/`calc_pnl_y`, analogous to `storedTotalAssets`) is decremented by a quantity computed through a different accounting path than the one used to derive the cached value, with no guard against the subtrahend exceeding it — unlike `calc_total_without_take_pnl_no_orderbook`, which correctly uses `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` for a similar operation.

### Impact Explanation
`target_orders` is a single shared account for the whole pool, so an underflow triggered by one LP's `Withdraw` reproduces deterministically for any subsequent `Withdraw` call that hits the same rounding boundary against the same (unchanged) pool state, since the panic occurs before any state is persisted. If the pool's coin/pc decimal configuration and accrued `calc_pnl_x`/`calc_pnl_y` values reach a state where this condition is met for all achievable `withdraw.amount` values, withdrawals become permanently unavailable for every LP until an external actor (e.g., a swap or `WithdrawPnl` call) shifts `total_pc_without_take_pnl`/`total_coin_without_take_pnl` enough to escape the underflow window — funds are frozen, matching the "permanent freezing of user or LP funds" impact criterion.

### Likelihood Explanation
This requires accumulated decimal-rounding drift between `calc_pnl_x`/`calc_pnl_y` (sys-decimal units) and the raw vault token amounts (coin/pc-decimal units) built up over repeated `calc_take_pnl` invocations (every swap and deposit/withdraw call updates this state) combined with a withdrawal whose floor-divided `pc_amount`/`coin_amount` lands exactly on the rounding boundary. It is more likely in pools where `pc_decimals` and `coin_decimals` differ significantly from `sys_decimal_value`, or where `pnl_numerator/pnl_denominator` doesn't divide evenly — realistic over the long operational lifetime of a busy pool, but not guaranteed on every withdrawal, so likelihood is Medium.

### Recommendation
Replace the `.unwrap()` calls at program/src/processor.rs lines 1819-1838 (and the analogous pattern in `process_withdrawpnl` at lines 1531-1532) with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?`, and/or clamp the subtraction so that `calc_pnl_x`/`calc_pnl_y` never go negative (e.g., `saturating_sub`), similar to how `calc_total_without_take_pnl_no_orderbook` already handles this case gracefully. Additionally, consider deriving `pc_amount`/`coin_amount`'s decimal-normalized equivalent directly from the same normalized arithmetic used to produce `x1`/`delta_x`, rather than round-tripping through raw token units, to eliminate the rounding mismatch at its source.

### Proof of Concept
1. Set up a pool where `pc_decimals != coin_decimals` and both differ from `amm.sys_decimal_value`, with `amm.fees.pnl_numerator/pnl_denominator` chosen such that `restore_decimal`/`normalize_decimal_v2` round-trips lose a unit (e.g., pnl fee ratio like 2/10000 against small trade sizes, which is common in production Raydium fee configs).
2. Perform normal swaps to accrue `need_take_pnl_pc/coin` and update `target_orders.calc_pnl_x/calc_pnl_y` via `calc_take_pnl` repeatedly, so that `calc_pnl_x`/`calc_pnl_y` drift by rounding relative to the vault's raw vs. normalized amounts.
3. Any LP calls `Withdraw` with an `amount` whose floor-divided `pc_amount`/`coin_amount`, once re-normalized via `normalize_decimal_v2` and added to `delta_x`/`delta_y`, exceeds `x1`/`y1` by even 1 unit.
4. `target_orders.calc_pnl_x = x1.checked_sub(normalize_decimal_v2(pc_amount,...)).unwrap().checked_sub(U128::from(delta_x)).unwrap()` panics, aborting the transaction; since `target_orders` state was not written, the same underflow reproduces for every subsequent `Withdraw` attempt against the unchanged pool state, blocking all LP withdrawals until pool state is shifted by an unrelated swap/deposit.
