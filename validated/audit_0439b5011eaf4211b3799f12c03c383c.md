### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`) values used by the host application to attribute the webhook to a tenant are read from unauthenticated HTTP headers. Because the app's webhook secret (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant that can trigger a legitimate webhook on their own store obtains a `(body, hmac)` pair that remains valid if replayed with the `shop-domain` header changed to point at a different (victim) shop.

### Finding Description
`Request#hmac` is computed as `Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))` and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string`, i.e. the raw body — never against the `shop`, `topic`, or `webhook_id` headers: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` (an unauthenticated header) to build `WebhookMetadata` that is handed to the host app's handler: [3](#0-2) 

`Request#shop` and `Request#topic` are read straight from the HTTP headers, with no cryptographic binding to the body/HMAC: [4](#0-3) 

The identity-binding equality that should hold is:
`hmac == HMAC(secret, body || shop || topic)`
but the gem only enforces:
`hmac == HMAC(secret, body)`

Since one shared `api_secret_key` signs webhooks for *every* shop that has installed the app, a merchant who has the app installed on their own store (an unprivileged, non-credentialed party from the app's perspective — they only need their own storefront) can generate a webhook with attacker-controlled body content and a valid HMAC by triggering a real event (e.g. `orders/create`) on their own shop. They can then resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/hmac pair is untouched), so `Registry.process` dispatches the handler with `shop: <victim-shop>` and attacker-controlled `body`, causing the host application to process forged data under the victim tenant's identity.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide via webhook verification, allowing an attacker to inject fabricated events attributed to a shop that is not theirs. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., writing order/inventory/customer data, triggering side effects, or associating billing/webhook payloads to accounts), this is a cross-tenant data-integrity and confidentiality issue — matching the Critical "cross-tenant access" category, since it lets one merchant/tenant inject data that is processed as belonging to another tenant.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate merchant with the app installed on their own store (no `api_secret_key`, access token, or privileged account is needed) plus the ability to send an HTTP POST to the app's public webhook endpoint with custom headers — both trivially available to any unprivileged internet user who has installed the app. The attack is a straightforward capture/replay-with-header-substitution, requiring no cryptographic breakage.

### Recommendation
Bind the shop (and ideally topic) identity into the HMAC-verified data, or otherwise separately validate that the shop claimed in the header actually matches an installation the app expects for that webhook subscription (e.g. cross-check against Shopify's provided `X-Shopify-Webhook-Id` registered for that specific shop/topic, rather than trusting the header value used for dispatch). At minimum, document that `request.shop` is not authenticated by the HMAC and must not be trusted for tenant attribution without additional verification (e.g. looking up the webhook subscription ID against a known per-shop registration table) before using it to key persisted data.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker creates an order on `attacker.myshopify.com`, triggering Shopify to POST a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and a JSON body the attacker fully controls (order fields).
3. Attacker captures this exact `raw_body` and `hmac` header value.
4. Attacker replays the identical body/HMAC to the app's public webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (body unchanged), `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` and invokes the registered handler, which processes attacker-controlled data as if it originated from `victim.myshopify.com`.
