### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an inbound webhook by HMAC-validating only the raw request body, while the `shop` value used downstream for tenant attribution is read directly from an unauthenticated HTTP header. Because a single app-wide `api_secret_key` is used to sign webhooks for *every* installed shop, a valid `(raw_body, hmac)` pair captured from one tenant's genuine webhook delivery remains cryptographically valid when replayed with a different `shop-domain` header, letting an attacker who controls (or has intercepted) one legitimate webhook impersonate another shop to the host application.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC solely over that signable string: [2](#0-1) 

But `shop` is derived independently from the `x-shopify-shop-domain` header, which plays no part in the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC over the request and then, once validation passes, trusts `request.shop` unconditionally as the tenant identifier passed to the app's handler: [4](#0-3) 

The equality the gem implicitly promises to the host application is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata`

In reality the HMAC only proves "this body byte-string was signed with this app's `api_secret_key`" — it says nothing about which shop the header claims to be from. Since Shopify apps use one `api_secret_key`/`client_secret` shared across all installed shops (this is not a per-tenant secret), any party that has legitimately received one valid webhook for their own shop (e.g., a merchant who installed the app — an unprivileged actor with respect to *other* tenants) can capture that valid `raw_body` + `hmac-sha256` header pair and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates (it only checks the body), so `Registry.process` passes the forged `shop` straight to the handler as if it were an authentic delivery from the victim tenant.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: a host application that keys session/data lookups off `WebhookMetadata#shop` (the documented, gem-provided value) can be made to process attacker-supplied payloads under another merchant's identity — e.g., triggering `app/uninstalled`-style side effects, GDPR data-request/redact handling, or business logic keyed on shop, all attributable to a tenant the attacker doesn't own. This is a cross-tenant confusion vector reachable by any user who can obtain one legitimately-signed webhook body for any shop.

### Likelihood Explanation
Requires only that the attacker have (or be able to observe) one valid webhook delivery for *any* shop that shares the same app credentials — a low bar, since any merchant who installs the app receives normal webhook traffic and can capture the exact bytes and HMAC header. No access to `api_secret_key`, access tokens, or victim credentials is needed.

### Recommendation
Bind the `shop` claim to the signed content instead of trusting the raw header: include the shop domain in the material that is HMAC-verified (e.g., verify it against the shop embedded in the parsed webhook body/topic-specific resource, or require host applications to cross-check `request.shop` against an active, previously-established session/installation record) before handing it to `WebhookMetadata`/the registered handler.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both verified with the same `Context.api_secret_key`.
2. Attacker controls `shop-a` and receives a legitimate webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker resends the exact same body `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC over `B` only [2](#0-1) , matches `H`, and passes.
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` == `"shop-b.myshopify.com"` [5](#0-4) , and the handler executes as though this were a genuine `shop-b` event, despite the payload originating from `shop-a`.
