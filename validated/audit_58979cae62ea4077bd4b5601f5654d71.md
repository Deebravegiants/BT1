## Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw request body, never the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers. `Registry.process` validates the HMAC over the body only and then trusts these unauthenticated headers to decide which shop and topic the payload belongs to, breaking the binding "the shop the HMAC was computed for" == "the shop the handler is told the data came from."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate` only ever HMACs `verifiable_query.to_signable_string`: [2](#0-1) 

Meanwhile `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read straight from HTTP headers with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards these header-derived, unverified values to the app's handler as the record of which shop/topic the event came from: [4](#0-3) 

Because only the raw body is signed, any request carrying a `(body, hmac)` pair that is valid for *some* legitimate webhook (e.g. one the attacker received for their own shop after installing the app) will pass `Utils::HmacValidator.validate` regardless of what `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers are attached to it. An attacker can therefore replay a genuine signed body while freely rewriting the shop-domain header, causing the app's webhook handler to process the payload as if it originated from a different (victim) shop — a cross-tenant identity confusion.

This is confirmed by the test suite itself, which computes the HMAC purely over the JSON body with no header inclusion: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: `handler.handle` receives a `WebhookMetadata` whose `shop` field is attacker-controlled while its `body` is only guaranteed to be *some* validly-signed body (potentially from the attacker's own tenant). Any host application that keys persistence, entitlement checks, or side effects (e.g. updating shop records, triggering uninstall cleanup, billing/order webhook effects) off `WebhookMetadata#shop` can be made to apply another shop's or a forged shop's data, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only two things reachable by an unprivileged internet user with no privileged credentials: (1) the ability to install the target app on any shop they control (a normal, permitted action for any Shopify merchant) to obtain one legitimately HMAC-signed webhook body/signature pair, and (2) the ability to POST arbitrary headers to the app's public webhook endpoint, which is exactly what `Webhooks::Request.new(raw_body:, headers:)` is designed to accept from any caller. No `api_secret_key`, access token, or other secret is needed by the attacker.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind them to the verified body (e.g., canonicalize headers + body before hashing, matching how Shopify's own webhook signature is actually computed only over the body but the gem must not attach unauthenticated header values as if they were verified). At minimum, document clearly that `request.shop`/`request.topic` are unauthenticated and require the caller to cross-check them against a shop they already trust before using them for authorization decisions, and/or add a secondary verification path that hashes headers alongside the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `shopify-hmac-sha256: H` (valid signature for `B` using the app's `api_secret_key`, which the attacker never needs to know).
2. Attacker replays this exact `(B, H)` pair to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` and/or `shopify-topic: orders/create` to whatever topic/shop they want to spoof.
3. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`, per `to_signable_string` returning `@raw_body`: [1](#0-0) .
4. `Registry.process` looks up the handler for the forged topic and invokes it with `shop: "victim.myshopify.com"` sourced purely from the unverified header: [6](#0-5) , causing the host application to act on behalf of a shop that never sent this event.
