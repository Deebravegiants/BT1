### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is not covered by the HMAC signature, allowing tenant spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* but never binds the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers to that signature. These header-derived values are nevertheless trusted as the tenant/topic identity and passed straight into the webhook handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the only two members required by `Utils::VerifiableQuery`: [1](#0-0) 
`Request#to_signable_string` returns just `@raw_body`: [2](#0-1) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, entirely outside the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` as the authenticated tenant/topic identity when dispatching to the app-supplied handler: [4](#0-3) 

`Utils::HmacValidator.validate` only proves `HMAC(api_secret_key, verifiable_query.to_signable_string) == verifiable_query.hmac`, i.e. it proves `body` integrity/authenticity, not the tuple `(shop, topic, webhook_id, api_version, body)`: [5](#0-4) 

The identity binding that should hold is:
`hmac_valid ⇒ (shop, topic, webhook_id, api_version, body)` all genuinely originated together from Shopify for that shop.

What actually holds is only:
`hmac_valid ⇒ body` is byte-for-byte what Shopify signed for *some* webhook, for *some* shop that has this app installed.

Because the `shop` (and `topic`/`webhook_id`) fields are read from attacker-controllable HTTP headers and are never part of the signed payload, any party who legitimately receives real signed webhooks for their own store (an ordinary unprivileged merchant who installed the app) can capture one of their own genuine webhook deliveries (valid body + valid HMAC, since Shopify signed it with the shared `api_secret_key`) and re-POST it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The signature still validates (it only checked the body), but `WebhookMetadata.shop` now reports the victim's shop to the handler, letting the attacker forge cross-tenant webhook events without ever needing the victim's or the app's own credentials beyond what a normal installed merchant already legitimately possesses.

### Impact Explanation
This crosses a tenant boundary: an app that keys any side effect (data updates, redaction processing, mandatory GDPR topics, business logic) off `WebhookMetadata.shop` can be made to act on behalf of / against a shop that never sent that event, using data and topic replayed from an unrelated shop's own genuine subscription. This matches the "cross-tenant access" high-impact category since it lets an unprivileged actor (any merchant that installs the app and receives real webhooks) spoof another tenant's identity to the webhook consumer.

### Likelihood Explanation
Likelihood is high given the low bar: the attacker needs only to be a legitimate, unprivileged installer of the app (to receive a genuine signed webhook of their own) and control of the HTTP request they send to the app's own public webhook endpoint (which is by design internet-reachable). No access to `api_secret_key`, access tokens, or any other credential is required — only observation/replay of headers that this gem never authenticates.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g., verify the HMAC over the full raw HTTP payload including these headers, matching how Shopify actually signs), so that `Registry.process` can only trust `request.shop`/`request.topic` when they are provably part of the same authenticated bundle as `raw_body`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures/receives a legitimate webhook subscription (e.g., `orders/create`). Shopify sends a real webhook: body `B`, headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: H = HMAC(api_secret_key, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint but changes only the header `shopify-shop-domain` to `victim-shop.myshopify.com` (topic/webhook_id can likewise be altered).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged, `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` is still `B` and `H` still matches.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...))`, causing the app to process the attacker's payload as if it legitimately originated from `victim-shop.myshopify.com`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
