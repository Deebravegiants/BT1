### Title
Divide-by-zero panic in `Processor::calc_take_pnl` permanently freezes Deposit/Withdraw when a pool's decimal disparity drives the normalized reserve to zero - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` divides by the normalized reserve value `x1` without checking that it is non-zero. Because `Calculator::normalize_decimal_v2` performs integer division that can round a non-zero raw token amount down to `0` whenever `pc_decimals` and `coin_decimals` differ significantly, any unprivileged user can drive the pool into a state where `x1 == 0` while the raw vault balance is still non-zero (and thus passes all swap-side sanity checks). Once in that state, every subsequent call into `Deposit` or `Withdraw` (both permissionless LP entry points) panics on a divide-by-zero, aborting the transaction — an on-chain analog to the NULL-pointer/crash-on-crafted-input class of CVE-2019-12974.

### Finding Description
`calc_take_pnl` computes the post-pnl reserves using U256 math:

<cite repo="AYontt/raydium-amm--015" path="program/src/processor.rs" start="199="' 208" end="208" />
```
let x2_power = Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
``` [1](#0-0) 

`x1`/`y1` are the *decimal-normalized* pool reserves, produced by: [2](#0-1) 

`normalize_decimal_v2(val, native_decimal, sys_decimal_value)` computes `val * sys_decimal_value / 10^native_decimal` using integer (floor) division. `sys_decimal_value` is fixed at pool creation as `10^min(coin_decimals, pc_decimals)`: [3](#0-2) 

When `pc_decimals` (or `coin_decimals`) is materially larger than the other, a small but non-zero raw reserve amount normalizes to `0`. For example, with `coin_decimals = 0` and `pc_decimals = 9` (`sys_decimal_value = 1`), a raw pc reserve of `1` normalizes to `floor(1 * 1 / 10^9) = 0`, even though the raw balance is non-zero.

The swap paths only guard against the raw reserve reaching `0`, not the *normalized* value: [4](#0-3) 

So an attacker can legitimately swap the pool's pc (or coin) side down to a tiny non-zero raw balance (e.g. `1`) that still normalizes to `0`, while `calc_take_pnl`'s guard condition `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` (computed from *raw*, non-normalized amounts) is still satisfied, letting execution proceed into the division branch with `x1 == 0`.

`calc_take_pnl` is invoked from the permissionless `Deposit` and `Withdraw` handlers: [5](#0-4) [6](#0-5) 

Once the pool sits in this state, every `Deposit` and every `Withdraw` (unless the pool is in `WithdrawOnly` status) will panic on `checked_div(x1).unwrap()`, aborting the instruction.

### Impact Explanation
This directly matches "permanent freezing of user or LP funds": once the low-decimal/high-decimal reserve imbalance is created, any user (attacker or legitimate LP) attempting to `Deposit` or `Withdraw` triggers the panic and their transaction reverts. Because the vault balance that produces the `x1 == 0` condition can be trivially re-created or maintained by an attacker performing repeated small swaps, LPs can be denied the ability to withdraw or add liquidity for as long as the attacker chooses to keep the pool in that state — a persistent, attacker-controlled denial of service against pooled funds, reachable purely through pool-creator-selected mint decimals plus a single unprivileged swap transaction.

### Likelihood Explanation
Reachability requires: (1) a pool created with sufficiently disparate `coin_decimals`/`pc_decimals` (fully within a pool creator's control via `Initialize2`, using two legitimate SPL mints with different, real-world decimal configurations — e.g. 0-decimal and 9-decimal tokens are common), and (2) a swap that reduces the affected side's raw reserve to a small residual amount above `need_take_pnl_*`. Both actions are ordinary, permissionless operations reachable from a single submitted transaction with attacker-chosen accounts/data, making this a directly and cheaply reproducible condition rather than a theoretical edge case.

### Recommendation
- In `Processor::calc_take_pnl` (and `Calculator::calc_x_power`), explicitly check `x1 != 0` (and `y1 != 0`) before performing division, returning `AmmError::CalcPnlError` (or similar) instead of relying on `.unwrap()`.
- Alternatively, ensure `normalize_decimal_v2` cannot silently collapse a non-zero raw amount to `0`, e.g., by rejecting pool creation/swaps that would produce a normalized reserve of `0` while the raw reserve is non-zero.
- Replace `unwrap()` calls on `checked_div`/`checked_mul` throughout `calc_take_pnl` with proper error propagation so any transient boundary state fails gracefully with a `ProgramError` instead of a panic.

### Proof of Concept
1. Pool creator calls `Initialize2` for a pool where the coin mint has `decimals = 0` and the pc mint has `decimals = 9` (both ordinary SPL mints), giving `sys_decimal_value = 10^0 = 1`.
2. An attacker performs `SwapBaseIn`/`SwapBaseOut` (coin→pc direction) repeatedly until `total_pc_without_take_pnl` (raw pc vault balance minus `need_take_pnl_pc`) is reduced to a small value such as `1`; this is permitted because the swap-side check only requires `swap_amount_out < total_pc_without_take_pnl` (strict), so it can approach but not reach exactly `0`.
3. At this point, `Calculator::normalize_decimal_v2(1, 9, 1) == 0`, so `x1 == 0` while `pool_pc_amount = 1` (raw) still satisfies the `>=` guard in `calc_take_pnl`.
4. Any subsequent call to `Deposit` or `Withdraw` invokes `calc_take_pnl`, which executes `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` with `x1 == 0`, causing `checked_div` to return `None` and the `.unwrap()` to panic, aborting the transaction and denying that Deposit/Withdraw to all callers while the state persists.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
