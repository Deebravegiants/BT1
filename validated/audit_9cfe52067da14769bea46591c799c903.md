### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute a webhook are all read from unauthenticated HTTP headers. This breaks the identity binding `hmac(signed bytes) == hmac(bytes acted on)`, letting an attacker who can send a POST to the app's webhook endpoint reuse a captured valid `(body, hmac)` pair while forging the `shop-domain`/`topic`/`webhook-id` headers to arbitrary values that still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are derived purely from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the raw body) against the received `hmac`: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the signature — to route the handler and to construct the metadata passed to app code: [4](#0-3) 

The intended identity binding is: `hmac_valid(body) ⇒ (shop, topic, webhook_id) are exactly what Shopify sent for that body`. In reality the binding only proves `hmac_valid(body) ⇒ body originated from Shopify at some point`; it says nothing about which shop, topic, or webhook the body belongs to. Because `shop`/`topic`/`webhook_id` are attacker-controllable inputs to the same POST request that carries `body`, an external caller can pair a previously-observed valid `(body, hmac)` value with forged header values and `Utils::HmacValidator.validate(request)` will still return `true`.

### Impact Explanation
This crosses the tenant boundary explicitly listed as Critical: "cross-tenant access." An attacker (an unprivileged internet user who need not compromise `api_secret_key` or intercept TLS — they simply need one legitimately-observed valid webhook body+hmac pair, e.g. from their own test shop's webhook delivery, or a captured request from any store using the app, replayed directly to the app's public webhook receiver endpoint) can:
- Cause the app to process the replayed payload attributed to an arbitrary victim `shop` domain (spoofed `shop-domain` header), since `WebhookMetadata#shop` is taken verbatim from the unauthenticated header.
- Route the payload to a different handler by spoofing the `topic` header, causing the app to interpret unrelated body content as belonging to a different topic (e.g., mandatory `customers/redact` / `shop/redact` handlers, which govern GDPR-relevant data deletion) or a legitimate-looking `webhook_id` to defeat idempotency/dedup checks.
- Because the gem's own `Registry.process` passes these spoofed values straight to app-provided `WebhookHandler#handle` without any additional binding, any host application built on this library's documented API inherits the cross-tenant confusion — this is a defect in the gem's own verification primitive (`Request`/`HmacValidator`), not a misuse of a documented contract.

### Likelihood Explanation
Likelihood is significant: the webhook receiving endpoint is by design public/internet-reachable (that's how Shopify delivers webhooks), no `api_secret_key`, access token, or TLS interception is required, and the attacker only needs one legitimately obtained `(raw_body, hmac)` pair — trivially obtainable by installing the app on any (even the attacker's own) development store and capturing one webhook delivery — to then replay it with arbitrary `shop-domain`/`topic`/`webhook-id` headers against the same endpoint.

### Recommendation
Include the shop domain, topic, webhook id, and API version in the signed/verified material, or otherwise cryptographically bind them to the body (e.g., verify against a per-shop expected value from a channel already anchored to that shop's install record) before trusting them in `Registry.process`. At minimum, `to_signable_string` should incorporate these header values (in a canonical form) so that `HmacValidator.validate` fails if any of them are altered independent of the body, restoring the identity equality `hmac_valid(payload) ⇒ (shop, topic, webhook_id, body) all match what Shopify actually sent`.

### Proof of Concept
1. Attacker installs the target app on their own store (or otherwise observes one legitimate webhook delivery) and records a valid `(raw_body, x-shopify-hmac-sha256)` pair for topic `orders/create`.
2. Attacker sends a POST directly to the app's public webhook endpoint with the same `raw_body` and same `hmac-sha256` header, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/redact` (or any registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` against the supplied signature — this still validates because `raw_body` and its real `hmac` are unchanged: [5](#0-4) 
4. The app's registered handler for `customers/redact` (or whichever spoofed topic) is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though the body never originated from that shop and was never signed in association with it: [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
