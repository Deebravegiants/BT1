Given the scope constraints (deserialization of untrusted data leading to unauthorized code/action execution) and reachability by an unprivileged cross-chain message sender, the strongest analog found is in the `hyper-fungible-token` pallet's message-handling path.

### Title
Unsigned cross-chain calldata lets an unprivileged bridge message dispatch an arbitrary `RuntimeCall` as another account - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `IsmpModule::on_accept` decodes an ABI-encoded `Message` from an untrusted, attacker-relayable `PostRequest.body`, then SCALE-decodes `substrate_data.runtime_call` into the runtime's `RuntimeCall` enum and dispatches it [1](#0-0) . Where the qcubed advisory unserializes an untrusted POST field into an arbitrary PHP object that then executes attacker-chosen logic, this pallet deserializes an untrusted, cross-chain-supplied byte string directly into an arbitrary `RuntimeCall` variant — i.e., any dispatchable the runtime exposes — and executes it, gated only by `BaseCallFilter` [2](#0-1) .

### Finding Description
`SubstrateCalldata` carries an *optional* signature alongside the raw encoded call [3](#0-2) . When `signature` is `None`, the code skips all cryptographic verification and instead derives the dispatch `origin` purely from the `message.from` bytes that were carried inside the same untrusted ABI-encoded message body: [4](#0-3) 

It then decodes and dispatches the attacker-supplied call as that derived account with no proof that the account whose identity is being used actually authorized this specific `runtime_call`: [5](#0-4) 

The only gate on which `RuntimeCall` variants may be executed is the runtime's `BaseCallFilter` [2](#0-1) , which is a global allow/deny policy, not an authorization check tied to the specific origin or call content. This is structurally the same bug class as the qcubed PHP object-injection issue: an unprivileged party controls the byte string that gets deserialized into an executable "object" (here, a `RuntimeCall` enum variant), and the surrounding code does not independently verify that the resulting action was actually authorized by the party in whose name it executes.

### Impact Explanation
If the "no signature" branch can be reached with `message.from` bytes that resolve to an account other than the actual initiator of the source-chain transaction (this hinges on whether the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract binds `Message.from` to `msg.sender` or allows it to be caller-supplied — this could not be fully confirmed from the indexed Solidity source in the time available), an attacker could dispatch arbitrary allowed extrinsics (e.g., balance transfers, asset transfers, approvals) as an arbitrary victim account, resulting in theft of funds or unauthorized app actions. Even in the best case where `from` is strictly bound to the real depositor, the design still lets a bridged message run privileged application logic without a cryptographic signature over "this call, by this account" whenever `signature` is omitted, which is a materially weaker authorization boundary than the signed branch just above it.

### Likelihood Explanation
This code path is reachable by any unprivileged sender relaying a `PostRequest` from a source chain registered in `ContractToAsset` — a normal token bridger only needs to invoke the send/transfer function on the mapped source contract with a non-empty calldata field to reach `on_accept` and hit the calldata-execution branch [6](#0-5) [7](#0-6) . No special privilege beyond normal bridge usage is required to attempt the no-signature branch.

### Recommendation
Require the signature to always be present and verified for the calldata-execution path, or otherwise cryptographically bind `message.from`/`message.data` to a verifiable action taken on the source chain (e.g., enforce that `Message.from` is exactly the transaction's verified sender as encoded by the audited source contract, and reject `SubstrateCalldata.signature == None` entirely). Treat the decoded `RuntimeCall` as fully untrusted input and require an explicit, per-call authorization proof rather than relying solely on `BaseCallFilter`.

### Proof of Concept
Conceptual (pending confirmation of the exact source-contract encoding of `Message.from`):
1. Attacker calls the source-chain bridge contract's transfer/send function, crafting an ABI-encoded `Message.data` payload containing `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded privileged call> }`, and `Message.from` set to bytes that decode to a target victim account (or any account the attacker wants to act as, if `from` is not enforced to be `msg.sender`).
2. The relayed `PostRequest` reaches `on_accept`, passes the `ContractToAsset` lookup, decodes `Message` and `SubstrateCalldata` [6](#0-5) .
3. Since `signature` is `None`, no verification occurs; `origin` is derived straight from `message.from` [4](#0-3) .
4. `runtime_call` is decoded and dispatched with that origin, subject only to `BaseCallFilter` [1](#0-0) .

Note: full confirmation that `Message.from` is attacker-controllable (rather than strictly bound to `msg.sender`) requires reading the EVM-side `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` send functions, which could not be completed within the available search budget; this should be verified before treating the impact as confirmed rather than conditional.
