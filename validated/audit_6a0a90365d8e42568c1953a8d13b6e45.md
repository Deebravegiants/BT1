## Finding: Withdrawal status/hash misattribution for same-asset withdrawals in a single transaction (POA Bridge)

### Title
Wrong destination tx hash reported when a NEAR transaction contains multiple withdrawals of the same asset — ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary
Both `describeWithdrawal()` in the POA bridge and `waitForWithdrawalCompletion()` in `internal-utils` match a withdrawal record returned by the POA Bridge API using only the `assetId` (`near_token_id`), not the withdrawal's index or destination address. If a single NEAR transaction contains two or more withdrawal intents for the same asset (to different destinations), the SDK can return the wrong record's `transfer_tx_hash`/status for a given withdrawal index.

### Finding Description
`findMatchingWithdrawal()` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` selects the first withdrawal whose `near_token_id` matches the requested `assetId`: [1](#0-0) 

The comment directly above the function acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" by this matching scheme, and the API itself returns an unsorted list. [2](#0-1) 

The same pattern is used by `PoaBridge.describeWithdrawal()`, which explicitly matches "by assetId, not by index" because the response list from the bridge API is unsorted: [3](#0-2) 

This is confirmed by the existing test that asserts assetId-based (not index-based) matching is the intended behavior: [4](#0-3) 

The equality that should hold is: *the destination tx hash reported for withdrawal index N corresponds to the on-chain settlement of withdrawal N* (i.e., `report(N).txHash == onChainOutcome(withdrawalIntent[N])`). When a single NEAR transaction contains two `ft_withdraw` intents for the same `assetId` to two different `destinationAddress` values, `findMatchingWithdrawal` returns the *first* API record matching that `assetId` regardless of which withdrawal (index) is being queried, so `describeWithdrawal({index: 0, ...})` and `describeWithdrawal({index: 1, ...})` for the same asset can both resolve to the same (or the wrong) record and `transfer_tx_hash`.

### Impact Explanation
If an integrator relies on `describeWithdrawal`/`waitForWithdrawalCompletion` to confirm settlement per withdrawal index and then releases funds, marks an order fulfilled, or refunds based on the reported `txHash`/`status`, this mismatch can cause:
- A withdrawal being reported "completed" with a `txHash` that actually belongs to a different withdrawal in the same transaction (status/hash misreport).
- Potential double-crediting: if two withdrawals of the same asset in one transaction both resolve to the same completed record, an integrator could treat both as confirmed even though only one bridge transfer actually completed to that particular destination.

This matches the "status or hash misreport making an integrator credit twice" impact category.

### Likelihood Explanation
Medium. It requires a caller (integrator or the SDK's own batched-intent flow) to submit two or more `ft_withdraw` intents for the *same* `assetId` to different destinations within a single NEAR transaction — a legitimate, non-malicious usage pattern supported by the intents contract's atomic multi-intent execution, not requiring any privileged or malicious actor. The POA Bridge API's unsorted response combined with assetId-only matching makes this a deterministic, reachable data-integrity issue rather than a theoretical one. However, it's already flagged in-code as a known limitation, and no production code path in this repo currently forbids batching same-asset withdrawals in one transaction to trigger it.

### Recommendation
Match withdrawal records using an unambiguous key (e.g., destination address, and/or the position field if the POA API provides an ordering identifier) rather than `assetId` alone. If the API doesn't expose a way to disambiguate multiple same-asset withdrawals within one transaction, the SDK should detect this batching case up front (e.g., in `createWithdrawalIntents`/`validateWithdrawal`) and reject it, or clearly propagate an "ambiguous match" error from `describeWithdrawal`/`waitForWithdrawalCompletion` instead of silently returning a possibly-incorrect record.

### Proof of Concept
1. Build one NEAR transaction with two `ft_withdraw` intents for the same `assetId` (e.g., `nep141:btc.omft.near`) to two different destination addresses A and B, executed atomically via the intents contract.
2. Call `bridge.describeWithdrawal({ ..., index: 0, withdrawalParams: { assetId: "nep141:btc.omft.near", destinationAddress: A, ... } })` and `describeWithdrawal({ ..., index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", destinationAddress: B, ... } })`.
3. `findMatchingWithdrawal` in `poa-bridge.ts`/`waitForWithdrawalCompletion.ts` looks up the API's `withdrawals` array only by `near_token_id === assetId`, so if withdrawal to A is still `PENDING` and withdrawal to B is `COMPLETED` (or vice versa), whichever record matching `assetId` appears first in the (unsorted) API response is returned for *both* index queries — reporting `COMPLETED` with B's `transfer_tx_hash` even for the withdrawal destined to A. /**
```typescript
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```
