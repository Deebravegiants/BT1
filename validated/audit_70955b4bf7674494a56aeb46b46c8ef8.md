Found it: the webhook `shop` binding.

### Title
Webhook `shop` field is read from an unauthenticated header, not covered by the HMAC signature, allowing tenant confusion in webhook handlers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is validated against `to_signable_string`, which is defined as the raw request body only [1](#0-0) . The `shop` value that `Registry.process` hands to application webhook handlers is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed payload [2](#0-1) .

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler [3](#0-2) . `HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is pulled straight from the `shop-domain` header outside of that signed string [2](#0-1) .

This is exactly the bug class described in the report: a field (`shop`) is acted upon by the consumer (`WebhookMetadata.new(... shop: request.shop ...)`) but is not covered by the HMAC that is supposed to authenticate the whole request [5](#0-4) . The binding that should hold is: `shop used by handler == shop authenticated by Shopify's HMAC`. Because only the body bytes are signed, an attacker who can replay/forward a legitimately-signed webhook body (e.g., a webhook for their own shop, or a body captured from any tap/log/proxy that doesn't leak the secret) can attach an arbitrary `shop-domain` header value and have the library treat the payload as originating from a different, victim shop — while the HMAC still validates because the header isn't part of what's signed.

### Impact Explanation
This breaks the tenant identity binding at the point applications key their per-shop logic (session/data lookups, entitlement checks, etc.) off of `WebhookMetadata#shop`. If a host application uses `data.shop` to decide which merchant's data to update (a documented, expected usage pattern), an attacker who obtains one validly-HMAC'd webhook body (their own shop's webhook, which Shopify will happily deliver to them) can relabel it with a victim's `shop-domain` and have it processed as if it came from the victim tenant — a cross-tenant confusion that can lead to cross-tenant data mutation depending on how the handler uses `shop`. This aligns with the "cross-tenant access" impact tier.

### Likelihood Explanation
Exploitability requires the attacker to control the raw HTTP headers of the request reaching the app's webhook endpoint but not the api_secret_key. This is realistic in typical deployments where the endpoint sits behind a reverse proxy/CDN/load balancer that forwards client headers, or where any component in the request path allows header injection/override, since the shop is taken from headers with no cryptographic linkage to the signed body. It also applies straightforwardly to legitimate multi-tenant apps that receive their own valid webhooks (for shop A) and could replay them with a modified `shop-domain` header claiming to be shop B — the HMAC check alone will not catch this because `shop` is outside `to_signable_string`.

### Recommendation
Include `shop` (and ideally `topic`) in the signed material verified against the HMAC, or otherwise derive the acted-upon shop from a source that is cryptographically bound to the HMAC rather than from a raw, unauthenticated header. At minimum, document that `request.shop` is untrusted input and that host applications must independently verify the shop against their own webhook registration records before using it as a tenant key.

### Proof of Concept
1. Obtain a legitimately Shopify-signed webhook payload for shop `attacker.myshopify.com` (raw body `B`, valid `x-shopify-hmac-sha256` computed over `B` with the app's `client_secret`).
2. Send a request to the app's webhook endpoint with the same raw body `B` and the same valid HMAC header, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts it (headers present) [6](#0-5) ; `Utils::HmacValidator.validate` succeeds because it only checks the body bytes [7](#0-6) [1](#0-0) .
4. `Registry.process` dispatches to the handler with `shop: request.shop` equal to `victim.myshopify.com` [8](#0-7) , even though the signed body actually belongs to `attacker.myshopify.com`.

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
