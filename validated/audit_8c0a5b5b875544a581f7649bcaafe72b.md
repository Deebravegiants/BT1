### Title
Dispatch fee overpayment in native token is permanently trapped in `EvmHost` instead of being refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native token (`msg.value`) as payment for the relayer fee and swap it into the fee token via Uniswap V2's `swapETHForExactTokens`. Because the swap is invoked with `EvmHost` itself as the caller (`msg.sender` from the router's perspective), any unused native token dust that Uniswap refunds is sent back to `EvmHost`, not to the original transaction sender. `EvmHost` has no `receive()`/`withdraw` path that returns this native balance to the user who overpaid, so any native token sent above the exact swap requirement is permanently stuck in the contract.

### Finding Description
In `dispatch(DispatchPost memory post)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

`swapETHForExactTokens` computes the exact input amount needed via `getAmountsIn(post.fee, path)` and refunds any leftover ETH to `msg.sender` of the call — which is `EvmHost`, since `EvmHost` itself invokes the router. The refund therefore lands in `EvmHost`'s own balance rather than being returned to the actual end user who sent `msg.value` to `dispatch()`.

This is explicitly acknowledged as expected behavior in the project's own documentation, which warns that native-token fee payment is "Approximate (subject to slippage)" compared to exact fee-token payment [2](#0-1) , and that `quote()` should only be used off-chain for estimation because on-chain use is subject to sandwich/slippage risk [3](#0-2) . Any discrepancy between the estimated `msg.value` and the exact amount consumed by the swap (due to slippage, price movement between quote and execution, or simply a generous buffer as recommended in the LayerZero endpoint adapter, which explicitly applies a "2x buffer" [4](#0-3) ) results in the surplus ETH being swept into and trapped in `EvmHost`.

The identical pattern exists in `dispatch(DispatchGet)`: [5](#0-4) 

There is no mechanism in `EvmHost` for a user to reclaim this stranded native balance; the only withdraw-style functions found are restricted to the `hostManager`/governance path for fee-token revenue, not user-initiated native token refunds.

### Impact Explanation
Any unprivileged caller who dispatches a POST or GET request while paying with native tokens (a standard, documented, user-facing flow explicitly recommended for "one-off transactions, user-facing apps") permanently loses the excess native token sent above the exact Uniswap-computed input amount. Because slippage is unavoidable between off-chain quoting and on-chain execution, and because integrators are advised to pad their native payment for safety margin (as demonstrated by the 2x buffer pattern), some amount of native token loss is essentially guaranteed on every native-paid dispatch, and can be substantial when slippage or buffering is large. Funds are not recoverable by the user, constituting a permanent freezing/loss of user funds in the core dispatch path reachable by any single transaction.

### Likelihood Explanation
High. This is triggered by the most basic, unprivileged, and documented usage pattern of the protocol — a user or app sending native token value to `IDispatcher(host).dispatch{value: msg.value}(post)` — with no special preconditions, misconfiguration, or malicious actor required. It occurs on every dispatch where `msg.value` is not the exact wei amount consumed by the Uniswap swap, which is the normal case given documented slippage and recommended overpayment buffers.

### Recommendation
After the `swapETHForExactTokens` call, compute and refund any unused native token balance (e.g., `address(this).balance` prior to the call minus after, or track the amounts returned by the router) back to `_msgSender()` (or `post.payer`) rather than allowing the router's refund to accumulate in `EvmHost`. Alternatively, switch to `swapExactETHForTokens` semantics with an explicit refund step, or expose a `withdrawExcessNative` guarded to the original payer with proper accounting.

### Proof of Concept
1. User calls `dispatch(DispatchPost)` with `msg.value = X`, intending to cover `post.fee` in fee-token terms, where `X` includes a safety buffer above the exact quoted amount (standard practice per the documentation and the LayerZero adapter's 2x buffer example).
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. Uniswap V2 Router uses only the exact input amount `Y < X` needed to produce `post.fee` tokens, and refunds `X - Y` in native ETH to `msg.sender` of the call, i.e., to `EvmHost`.
4. `EvmHost` now holds `X - Y` extra wei with no code path returning it to the user; the user's excess payment is permanently lost. [6](#0-5)

        // adjust the timeout
