### Title
Webhook `shop`/`topic` identity fields are trusted from unauthenticated HTTP headers while HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) from raw HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), but `HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns solely `@raw_body`. The `shop` value that `Registry#process` hands to the app's webhook handler is never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from headers via `shopify_header`, none of which participate in the signature: [4](#0-3) [5](#0-4) 

`Registry.process` validates HMAC and then immediately trusts `request.shop` (header-derived) to build the `WebhookMetadata` dispatched to the app's handler: [2](#0-1) 

The identity binding that should hold is: *the shop that produced the HMAC-signed bytes* == *the shop the handler is told the webhook is for*. Because the signed bytes are only the JSON body, and the JSON body typically does not repeat the shop domain in a form the library cross-checks, `Utils::HmacValidator.validate` proves only that "some request with this exact JSON body was HMAC-signed with `Context.api_secret_key`" — it says nothing about which shop's `x-shopify-shop-domain` header should accompany that body. A genuine webhook payload/HMAC pair captured for one event can be replayed with a different `x-shopify-shop-domain` (or `x-shopify-topic`) header value, and `Registry#process` will accept it (HMAC check passes because it only checks body bytes) and dispatch to the app's handler tagged with the attacker-chosen `shop`.

### Impact Explanation
If a background app trusts `WebhookMetadata#shop` to select which merchant's data record to update (a standard multi-tenant pattern), an attacker who can obtain any one valid `(body, hmac)` pair for the app (e.g., from their own store, or a leaked/observed webhook) can resubmit it with a forged `x-shopify-shop-domain` header pointing at a victim shop. This crosses a tenant boundary: the app processes attacker-controlled webhook content under another merchant's identity, i.e., cross-tenant data injection/write using the gem's own validated-but-mismatched identity field. This matches the "shop authenticated versus shop stored as session key" analog class in the rules.

### Likelihood Explanation
Requires the attacker to possess at least one legitimately signed `(raw_body, hmac)` pair from the same app (easily obtained by installing the app on their own store, or intercepting one of their own webhooks) and network access to POST to the app's webhook endpoint with a forged shop-domain header — no access token, secret, or privileged account needed. This is a realistic, unprivileged-internet-user analog.

### Recommendation
Bind the header-derived identity fields into the signed material, or independently cross-validate `shop`/`topic` against the parsed body / a known active session before dispatch:
- Include `shop`, `topic`, and `webhook_id` header values in `to_signable_string` (this requires a coordinated change with Shopify's signing side and may not be feasible unilaterally), or
- At minimum, document and/or enforce that consumers of `WebhookMetadata` must independently confirm the `shop` value corresponds to an app-known install before trusting it for tenant-scoped writes, and have `Registry#process` reject processing when `request.shop` isn't already a shop with an active session/installation known to the app.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid and correctly signed with the app's shared secret.
2. Attacker resends the identical body and `hmac` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com` (and optionally alters `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) and succeeds, since the body/HMAC pair is untouched. [6](#0-5) 
4. `Registry#process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged header values and calls the app's registered handler, which believes this is a genuine webhook for `victim.myshopify.com`. [7](#0-6)
