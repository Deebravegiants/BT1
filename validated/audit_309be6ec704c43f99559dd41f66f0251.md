This confirms the vulnerability. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` header, which is completely outside the HMAC coverage [2](#0-1) . `Registry.process` validates only the HMAC over the body and then passes `request.shop` straight into `WebhookMetadata` for the handler [3](#0-2) , so the gem itself hands the host application a "verified" webhook whose tenant field was never authenticated.

### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, but exposes and forwards an unauthenticated `shop` value taken from the `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof the whole webhook (including `shop`) is authentic and hands it to the app's handler, breaking the intended binding `shop-in-signed-content == shop-attributed-to-tenant`.

### Finding Description
`VerifiableQuery#to_signable_string` for the webhook request returns just `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)` and compares it to the `hmac` header, so it only proves the *body bytes* are authentic under the app's shared `api_secret_key` — it says nothing about which shop the request claims to be from [4](#0-3) .

`Registry.process` uses this validation result as a blanket authenticity check, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`: [3](#0-2) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field host apps are expected to use to route/attribute webhook data to a tenant [5](#0-4) [6](#0-5) .

Because Shopify apps share a single `api_secret_key` across all shops that install the app, any unprivileged user who controls one legitimately-installed shop (e.g., a free/dev store) receives real, validly-HMAC'd webhooks for their own shop. Since the HMAC covers only the body, that same `(body, hmac)` pair remains valid when replayed with the `shop-domain` header changed to a victim shop. `Registry.process` will accept it as authentic and dispatch it to the handler labeled with the victim's `shop`, breaking the equality that the library implicitly promises: "the `shop` returned to the handler is the same identity the HMAC authenticated."

### Impact Explanation
This crosses a tenant boundary using only the gem's own verification logic: an attacker with legitimate low-privilege access to any single shop installation of a multi-tenant app can make the app process attacker-controlled webhook bodies "as" a different, victim shop. Depending on how the host app uses `data.shop` (commonly to look up the shop's session/access token and perform actions or store data against that tenant), this can lead to cross-tenant data corruption or actions being taken against the wrong merchant's data — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop the attacker controls (a normal, low-privilege capability for many public apps), (2) capturing one legitimate webhook body+HMAC from that shop, and (3) replaying it to the app's webhook endpoint with a modified `shop-domain` header (topic/webhook-id can be reused too, since none of the identifying headers are covered by the HMAC). No access to `api_secret_key`, tokens, or the victim's credentials is needed.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signature (e.g., require the host application to independently verify that `request.shop` corresponds to a shop with an active, known installation before trusting it). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without an independent check against known installed shops.

### Proof of Concept
```ruby
# Attacker legitimately installs the target app on their own shop "attacker.myshopify.com"
# and receives a real webhook, e.g. for topic "orders/create":
raw_body = '{"id":1,"note":"legit"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_API_SECRET_KEY, raw_body)

# This (raw_body, hmac) pair is valid because HmacValidator only signs raw_body:
# lib/shopify_api/utils/hmac_validator.rb#compute_signature
# lib/shopify_api/webhooks/request.rb#to_signable_string -> @raw_body

# Attacker replays the exact same body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (it only checked raw_body),
#    and the handler is invoked with data.shop == "victim-shop.myshopify.com",
#    even though that shop never sent this webhook.
```
