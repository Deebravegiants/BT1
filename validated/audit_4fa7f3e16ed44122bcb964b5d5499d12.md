### Title
Webhook shop-domain (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable content from the raw HTTP body only, while the `shop`, `topic`, and `webhook-id` values are read from unauthenticated HTTP headers and handed to the app's webhook handler as trusted tenant-identifying data. Since the HMAC signing key (`Context.api_secret_key`) is a single secret shared by the app across *all* installed shops, and the signature never binds to the `shop-domain` header, any party that can obtain one valid `(body, hmac)` pair (e.g., by installing the app on their own free/dev store) can replay that exact body+signature to the app's webhook endpoint while substituting an arbitrary victim `shopify-shop-domain` header. `Utils::HmacValidator.validate` will accept it, and the host application's handler will process the payload as if it came from the victim shop.

### Finding Description
The signable content for a webhook is defined as just the raw body: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are derived purely from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., of the raw body) and then dispatches the handler using the unauthenticated `shop` header: [3](#0-2) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` (the raw body) using `Context.api_secret_key`, the same secret for every shop that has the app installed: [4](#0-3) 

The identity binding this breaks is:
`shop header value used by the handler == shop that actually produced/authorized the signed body`
This equality does not hold: the signature only proves "signed by holder of `api_secret_key`", not "signed for shop X". Because the secret is shared across tenants, a legitimate (if malicious) merchant, Eve, who installs the app on her own shop receives real webhook deliveries whose `(body, hmac)` pair validates successfully. She can then POST that exact body and HMAC directly to the app's public webhook endpoint, replacing the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` forwards `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the host app's handler as if the event genuinely originated from the victim shop.

This is the direct analog of the reported class of bug: a field that is *acted upon* (the tenant identity used by the handler) is not covered by the authenticity check (the HMAC), so an attacker can decouple the two and make the system misattribute authenticated data to a different tenant.

### Impact Explanation
Host applications built on this gem are expected to use the `shop` field returned in `WebhookMetadata` to select which tenant's stored data/state to update in response to the webhook (this is the gem's documented purpose of the `shop` field). Because that field carries no authenticity guarantee, an attacker who can generate one valid signed payload (by installing the app on a shop they control, which any internet user can do via a free Shopify dev/partner store) can cause the app to apply attacker-controlled webhook data under a victim shop's identity — a cross-tenant access/injection primitive. This meets the Critical bar of "cross-tenant access" defined in the assessment rules, since it lets an unprivileged actor make one tenant's authenticated event appear to belong to another tenant.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that trust the `shop` field from `WebhookMetadata` without independently confirming that the shop is one for which they expect that exact webhook body (most apps do not, since this is precisely the API contract the gem presents). Obtaining a valid signed payload only requires installing the app on any shop (free, unprivileged), then replaying the raw body/HMAC while forging headers to the public webhook receiver endpoint — no access token, `client_secret`, or privileged credentials are required.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the signed material that `HmacValidator` verifies, or otherwise cryptographically tie the header-derived tenant identity to the signature — e.g., include the `shop-domain`/`webhook-id` values in `to_signable_string`, or require callers to separately verify that the shop in the payload body (if present) matches the header before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-selection key without additional verification.

### Proof of Concept
1. Eve installs the target Shopify app on her own (free) test/dev shop `eve-shop.myshopify.com`, satisfying the app's OAuth flow legitimately.
2. Shopify delivers a real webhook (e.g., `orders/create`) to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — note `api_secret_key` is the same for every shop using this app.
3. Eve captures `(B, H)` (she is the legitimate recipient of her own webhook, so no interception is needed).
4. Eve crafts a new HTTP POST directly to the app's public webhook endpoint with the exact same raw body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes because `B` and `H` are unchanged and the secret is shared. [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body `B` as if it were an authentic event from the victim shop. [6](#0-5)
