Audit Report

## Title
CORS `isAllowedOrigin` wildcard suffix match lacks a label boundary, allowing origin allowlist bypass - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway HTTP server's `isAllowedOrigin` function validates wildcard CORS entries (`*.domain.com`) using an unanchored `strings.HasSuffix` check with no requirement that the matched suffix be preceded by a `.` label separator. This lets an attacker whose fully-controlled domain merely ends with the same byte sequence as an allowed domain (e.g., `evilethereum.org` vs. allowed `*.ethereum.org`) pass the origin check and receive a reflected `Access-Control-Allow-Origin` header, bypassing the intended subdomain restriction.

## Finding Description
In `isAllowedOrigin`, the wildcard branch strips the `*.` prefix from the configured allowed host and then checks only `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

This has no boundary check verifying that the character immediately preceding the matched suffix in `originHost` is a `.`. As a result, a hostname like `evilethereum.org` incorrectly satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org")` even though it is not a subdomain of `ethereum.org` at all — it's an entirely separate, attacker-registrable domain. The exact-match branch above it (`originHost == allowedHost`) correctly guards the non-wildcard case, but the wildcard branch's suffix check is unanchored. The existing test suite only exercises true subdomain matches (`remix.ethereum.org`, `another.valid.domain.com`, `example.gov`) and does not cover this boundary-omission case, so it went undetected in CI: [4](#0-3) 

Once `isAllowedOrigin` returns `true`, the raw `Origin` header value is reflected directly into `Access-Control-Allow-Origin`, with `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` also set, enabling the browser to permit the cross-origin request/response: [2](#0-1) 

## Impact Explanation
This allows an unprivileged attacker who controls an arbitrary domain crafted to end in the same string as an operator-configured wildcard-allowed domain (trivially achievable via public domain registration, e.g. `evilethereum.org` against an allowed `*.ethereum.org`) to have their web page issue cross-origin requests to the Gateway's `ProcessRequest` endpoint from a victim's browser and read the response, which would otherwise be restricted to the operator's intended trusted subdomains. This falls into the allowlist bypass / cross-origin response corruption impact category since it defeats the operator's origin-based access control intent for the internet-facing gateway endpoint.

## Likelihood Explanation
Exploitability requires the operator to have configured at least one wildcard `CORSAllowedOrigins` entry, which is a supported and tested configuration pattern in this codebase. Given that precondition, the attack requires no credentials, no privileged access, and no victim social engineering beyond getting a victim's browser to visit an attacker page — domain registration to satisfy the suffix match is unrestricted and trivial.

## Recommendation
Enforce a proper label boundary in the wildcard comparison: require `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` instead of the bare `strings.HasSuffix(originHost, allowedHost)`.

## Proof of Concept
1. Configure the Gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}`.
2. Send an HTTP request to the Gateway's configured path with header `Origin: https://evilethereum.org`.
3. Observe `isAllowedOrigin` returns `true` (since `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`), and the response contains `Access-Control-Allow-Origin: https://evilethereum.org`.
4. This can be added as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, asserting that an origin of `https://evilethereum.org` should be rejected but currently is accepted.
