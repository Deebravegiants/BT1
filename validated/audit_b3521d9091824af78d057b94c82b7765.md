### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from an HTTP header that is never included in the signed payload. Because the app's `client_secret` (and thus the HMAC key) is identical for every shop that installs the app, any shop that legitimately receives a webhook can capture a `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting an arbitrary victim shop in the `X-Shopify-Shop-Domain` header. The gem accepts this as a validly-authenticated webhook "from" the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, and for webhook requests that string is just the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header and is never fed into the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` when constructing the `WebhookMetadata` handed to the app's handler, with no check that the shop is bound to the signature: [3](#0-2) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem implicitly assumes is
`hmac_verified(raw_body) == authenticated(shop_header)`,
but in reality only `raw_body` is authenticated; `shop` is attacker-controlled and independent of the signature.

Because Shopify computes the webhook HMAC using the app's single `client_secret` for *all* merchants who install the app, an unprivileged attacker only needs to install the target app on their own (even free/dev) store to legitimately receive real, validly-signed webhooks. They can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while setting `shopify-shop-domain` (or `x-shopify-shop-domain`) to any victim shop's domain. `HmacValidator.validate` will pass (it never looks at the shop header), and the handler will be invoked believing the event legitimately originated from the victim shop.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide. A host application typically uses `WebhookMetadata#shop` to decide which merchant's data/record to update (e.g., resource sync, order/customer processing, uninstall handling). By forging the shop header on a validly-HMAC'd request, an attacker can inject fabricated events attributed to a shop they don't control, causing cross-tenant data confusion/corruption in the host app — the gem provides no protection at all against this because it only exposes `HmacValidator.validate(request)` as the sole authenticity check and openly surfaces `request.shop` as if it were trustworthy. This matches the Critical "cross-tenant access" impact category since the identity (shop) associated with an authenticated payload can be forged.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on at least one store (often trivial — free dev stores, low-friction app installs) — no leaked credentials, TLS interception, or privileged accounts are required. Once installed, they receive real signed webhooks for their own store, extract the body and signature, and can replay them with a spoofed shop header against the app's public webhook endpoint.

### Recommendation
Include the shop domain (and any other header field used by handlers, e.g., topic/api-version) into the HMAC-signed payload verified by `Utils::HmacValidator`, or have `Registry.process` cross-check `request.shop` against an independently-verified value (e.g., compare with the shop associated with a previously stored session/webhook registration) before dispatching to the handler. Short term, document/enforce that host apps must not trust `WebhookMetadata#shop` without independent verification; long term, extend `VerifiableQuery`/`to_signable_string` for webhooks to bind the shop domain into the signature computation, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` already binds `shop` into its HMAC payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving genuine webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures a delivered webhook's raw body `B` and its `X-Shopify-Hmac-Sha256` header value `H` (valid because `HmacValidator.validate` only checks `HMAC(secret, B) == H`, per `lib/shopify_api/utils/hmac_validator.rb` line 26-31 and `lib/shopify_api/webhooks/request.rb` line 35-38).
3. Attacker POSTs the same body `B` with the same `X-Shopify-Hmac-Sha256: H` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds (it only checks the body/hmac pair), then builds `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed victim shop domain (`lib/shopify_api/webhooks/registry.rb` lines 188-199), and invokes the app's handler as if the event came from `victim-shop.myshopify.com`.
