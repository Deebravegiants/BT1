### Title
Unvalidated route pool/token addresses let attacker-crafted swap payloads graft unauthorized token transfers into the caller's auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller strategy verbs (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) forward a user-supplied opaque `swap`/`StrategySwap` byte blob to the configured router, which invokes arbitrary pool and token addresses named in the payload's `assets` registry with no allowlist or validation. A malicious "pool" contract placed in the route executes inside the transaction and can perform `token.transfer(victim, attacker, amount)` calls that the Soroban host records as children of the victim's `require_auth` invocation — i.e., the crafted input causes the protocol to emit attacker-chosen operations under the victim's signature. This mirrors CVE-2022-0124's class: insufficient validation of user-supplied input that is turned into attacker-controlled outbound calls.

### Finding Description
`swap_tokens` authorizes exactly one transfer — `token_in.transfer(controller, router, amount_in)` — then calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is the raw caller-supplied `Bytes` ( [1](#0-0) ). The router decodes the payload into a registry of `assets` (tokens, pools, LP tokens) and a packed instruction stream, and dispatches each hop to a venue adapter keyed only by an opcode byte; pool and token addresses come straight from the registry ( [2](#0-1) ). The venue adapters `invoke_contract` on whatever address the payload names ( [3](#0-2) ). Neither the controller nor the router checks that `pool`/`token_*` entries are legitimate venue contracts.

The harness demonstrates the exploit end-to-end: `UnlistedPoolRouter`/`RogueHopPool` show that a route naming an attacker-deployed pool causes the host to record a `token.transfer(alice → attacker, WALLET_BALANCE)` as a sub-invocation of Alice's `swap_collateral` auth entry, and the transfer executes once she signs that tree ( [4](#0-3) [5](#0-4) ). The threat model confirms no allowlist exists and that the loss is the caller's whole wallet, unbounded by the payload `min_out` or the final risk gate ( [6](#0-5) ).

### Impact Explanation
Theft of user funds. A victim who submits a crafted route (e.g., a poisoned `routeXdr` served by a malicious quote source or frontend) signs an auth tree that silently includes transfers of arbitrary tokens from their wallet to the attacker — demonstrated in the test by draining Alice's entire unrelated `wallet_token` balance while her position still receives a "fair" swap output and passes all risk checks. Neither `RouterOverspend` (501), `NoSwapOutput` (502), nor `total_min_out` bounds the loss, because the stolen transfer is not part of the measured swap flow.

### Likelihood Explanation
Requires a victim to sign a transaction whose recorded auth tree contains the rogue transfer. Simulation surfaces it, so an attentive user or a wallet that renders sub-invocations can refuse — which is why this is Medium rather than High. But the exploitation path is fully reachable by a single unprivileged attacker: deploy a rogue "pool" contract, craft valid `StrategyPayload` bytes naming it, and get a user to submit the route through `execute_strategy` or any of the four controller strategy verbs. All contract-side checks (decode, min-out, measured deltas, solvency) pass.

### Recommendation
Validate route targets before executing hops: maintain an on-chain allowlist of legitimate venue pool contracts (or at minimum a registry check that hop pools are not arbitrary contracts), and/or have the router reject payload token/pool addresses that do not correspond to known venue deployments. At the controller layer, consider requiring routes from a governed route registry. Clients should additionally enforce the documented rule of signing only auth trees containing exactly the single expected input-transfer child.

### Proof of Concept
The repository's own test demonstrates it: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. Alice calls `swap_collateral` with a route whose hop pool is `RogueHopPool`; the recorded auth tree under her `swap_collateral` entry contains `token.transfer(alice, attacker, WALLET_BALANCE)`, and after execution `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while her ETH supply still grows by the fair output.

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
