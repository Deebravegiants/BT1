### Title
Unvalidated `dest` claim in `TokenExchange.exchange_token` sends `client_secret` to an attacker-influenced host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the OAuth token-exchange request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling method `migrate_to_expiring_token` in the same file, which explicitly validates the shop against the trusted-domain allowlist before building the request. This breaks the intended binding: *the host that receives the app's `client_secret` must equal a validated, trusted Shopify domain*, not merely "whatever string appears after `https://` in the token's `dest` claim."

### Finding Description
`ShopifyAPI::Auth::JwtPayload#shop` computes the shop host with a naive string strip: [1](#0-0) 

No call to `ShopValidator.sanitize!`/`sanitize_shop_domain` is made here or anywhere in `JwtPayload`.

`TokenExchange.exchange_token` then uses this raw value as `dest_shop`, builds a `Session` from it, and issues an HTTP POST containing the app's `client_id`/`client_secret` to `https://#{dest_shop}/admin/oauth/access_token`: [2](#0-1) 

Contrast this with `migrate_to_expiring_token` in the very same module, which validates the shop before using it to build a request that also carries the `client_secret`: [3](#0-2) 

`ShopValidator` exists precisely to enforce that any host used to build outbound admin requests belongs to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or the app's configured `myshopify_domain`, rejecting anything else: [4](#0-3) 

The binding that should hold is: `host receiving client_secret == validated trusted Shopify domain`. In `exchange_token`, the binding actually enforced is: `host receiving client_secret == dest claim minus "https://" prefix`, with no allowlist check. This is exactly the "host validated versus the host that receives ... `client_secret`" analog called out in the report's bug class: the field that is *acted upon* (the request host) is not the field that is *checked* (nothing is checked at all for this code path).

### Impact Explanation
If the `dest` claim can ever contain a value other than a canonical, allowlisted Shopify host (e.g., a malformed/crafted domain, `admin.shopify.com/store/<name>` unified-admin path not properly normalized, or any string not stripped/anchored the way `ShopValidator` requires), `exchange_token` will POST the app's `client_id` and `client_secret` to that host. This is Critical-tier credential exfiltration: leakage of the app's `client_secret` to a third party enables full impersonation of the app (forging OAuth flows, minting arbitrary access tokens for any shop) — exactly the "theft of the app's `client_secret`" impact category. It also crosses the tenant boundary that other parts of the code (`migrate_to_expiring_token`) are explicitly designed to prevent by validating the destination host before it is used to route the client secret.

### Likelihood Explanation
Session tokens are HS256-signed with the shared `api_secret_key`, and in the trusted case Shopify itself populates `dest` with the legitimate embedding origin, so exploitation requires a `dest` value that is not a plain trusted Shopify domain to reach this code path (e.g., unusual admin embedding contexts, dev/spin domains, or any host format the gem does not already normalize the way `ShopValidator` does for other flows). I could not fully confirm from the available code whether Shopify's session-token issuance can ever produce a `dest` value that bypasses the allowlist that `ShopValidator` was clearly written to enforce elsewhere in this codebase — this uncertainty affects confidence in real-world exploitability, but the root-cause code defect (missing validation on a security-relevant path that sends `client_secret`) is unambiguous and demonstrably inconsistent with the parallel, validated code path in the same file.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop, myshopify_domain: ...)` (mirroring `migrate_to_expiring_token`) before constructing `shop_session` and issuing the `client.request` call that carries `client_id`/`client_secret`. Raise `Errors::InvalidShopError` if validation fails, exactly as `ShopValidator.sanitize!` already does for other flows.

### Proof of Concept
1. An app is configured with `ShopifyAPI::Context.setup(..., is_embedded: true)`.
2. A session token (`session_token`) is presented to `ShopifyAPI::Auth::TokenExchange.exchange_token` whose `dest` claim is not a canonical, allowlisted Shopify domain (e.g. anything ShopValidator would reject) but is nonetheless successfully HS256-verified (any value signed with the shared secret decodes without further host validation, since `JwtPayload` performs no domain check on `dest`): [5](#0-4) 
3. `exchange_token` sets `dest_shop = jwt_payload.shop` (raw, unsanitized) and builds `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, then POSTs `{ client_id, client_secret, ... }` to `https://#{dest_shop}/admin/oauth/access_token`: [6](#0-5) 
4. Because no `ShopValidator.sanitize!` call occurs (unlike `migrate_to_expiring_token`, line 103), the request host is not constrained to the trusted-domain allowlist, so the app's `client_secret` is sent to whatever host `dest_shop` resolves to.

        [
          "shopify.com",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
