### Title
Single-token transfer revert in `_withdraw()` permanently locks all other escrowed assets of a multi-asset order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw()` iterates over every token in a `WithdrawalRequest` and performs an unconditional `IERC20.safeTransfer`/native-value send for each one inside a single atomic loop. If any single token transfer in that loop reverts deterministically (e.g. a blacklisted/paused ERC-20 such as USDC/USDT refusing to send to the beneficiary), the entire function reverts, and — because the failure is deterministic — every retry of the same message will fail identically, permanently freezing **all** of the order's other, unrelated escrowed tokens along with it. This mirrors the analog bug class (a revert on one item blocking release of the whole batch) described in the referenced sfrxETH mitigation report, except here Hyperbridge's message-delivery layer normally *does* isolate such reverts for retry (`EvmHost.dispatchIncoming` deletes the receipt on failure so the message can be redelivered) — but that retry safety net is useless when the revert condition is permanent (a blacklist or pause), leaving the funds unrecoverable.

### Finding Description
`_withdraw()` releases every token in `body.tokens` in one loop with no isolation between entries: [1](#0-0) 

For each token with a non-zero amount, it decrements escrow accounting and then makes an external call that can fail permanently for reasons entirely out of the solver's/user's control:
- `IERC20(token).safeTransfer(beneficiary, amount)` reverts if `beneficiary` is blacklisted by that specific token (USDC/USDT-style compliance blacklists) or if that token is paused.
- `_sendValue(beneficiary, amount)` reverts if the beneficiary is a contract whose `receive`/`fallback` reverts.

This function is the single settlement path for both fills and cancellations, called from `ExtrinsicIntents.onAccept` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse`, as well as from `IntrinsicIntents._fillSameChain`/`_cancelSameChain` for same-chain orders: [2](#0-1) 

Because `body.tokens` can contain multiple distinct assets for a single order (the docs explicitly describe multi-pair orders, e.g. `testSameChainSwap_MultiplePairs`), a revert on any one asset in the array prevents the release of every other, unrelated asset escrowed for that same commitment — there is no per-token isolation or partial-success path.

Normally Hyperbridge's cross-chain delivery layer tolerates a reverting `onAccept` by deleting the request receipt so the message stays retryable: [3](#0-2) 

However, this retry mechanism only helps for *transient* failures. If the revert is deterministic (permanent blacklist, permanently paused token, or a beneficiary contract that always reverts on receive), every future redelivery attempt fails identically, so the escrow can never be released — the funds are permanently stuck in the gateway. The system has evidently recognized and solved this exact class of problem elsewhere (see `HyperbridgeLzEndpoint.onAccept`, which isolates `lzReceive` with a `try/catch` specifically so "a deterministic revert (zero recipient, over-cap mint, blocklisted recipient, ...) does not revert `onAccept`" and stores the payload for later recovery), but `IntentsBase._withdraw()` was not given the same treatment.

### Impact Explanation
A user placing a multi-asset order (or the intent gateway's own dust/fee sweep bundled with token transfer) can have all of an order's escrowed input tokens permanently frozen if any single asset in that order is or later becomes untransferable to the recipient (blacklist, pause, or a hostile beneficiary contract for the native-ETH leg). This is a permanent freezing-of-funds condition reachable by ordinary users and solvers placing/filling/cancelling intent orders — no privileged action required.

### Likelihood Explanation
Multi-asset orders and native-ETH outputs/inputs are a documented, supported feature (`testSameChainSwap_MultiplePairs`, native ETH legs in `IntrinsicIntents`), and stablecoins with compliance blacklists (USDC, USDT) are commonly used as intent-gateway assets. A solver or user beneficiary address becoming blacklisted by the issuer of just one of several escrowed tokens is a realistic, non-adversarial-admin scenario, making this a plausible-likelihood, high-impact freeze.

### Recommendation
Isolate each token release in `_withdraw()` the same way `HyperbridgeLzEndpoint.onAccept` isolates OApp delivery: wrap each `safeTransfer`/`_sendValue` call in its own `try/catch` (or use a raw `.call` and check success) and, on failure, retain that specific token's escrow balance for later permissionless recovery (e.g. a per-token `claim`/`retry` function) instead of reverting the whole withdrawal. This ensures one uncooperative token/beneficiary combination cannot block release of the other assets escrowed for the same order.

### Proof of Concept
1. User places a same-chain (or cross-chain) order with two input tokens: `USDC` and `DAI`.
2. Solver fills the order; the fill fully completes, triggering `_withdraw(body, false, true)` where `body.tokens` contains both `USDC` and `DAI` amounts owed to the solver.
3. Before settlement executes (or is retried after an earlier transient failure), the solver's beneficiary address is added to USDC's blacklist (a realistic, solver-independent event).
4. `_withdraw()`'s loop reaches the `USDC` entry and `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts; the whole `_withdraw` call reverts.
5. For a same-chain fill this reverts the whole `fillOrder` transaction, but for the cross-chain `onAccept` path, `EvmHost.dispatchIncoming` catches the failure and deletes the receipt so the message can be redelivered — yet every redelivery hits the same deterministic blacklist revert.
6. The `DAI` escrow, entirely unrelated to the blacklist, remains locked in the gateway forever alongside the blacklisted `USDC`, with no code path to release it separately.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
