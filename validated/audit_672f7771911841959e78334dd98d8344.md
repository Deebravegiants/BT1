### Title
Webhook HMAC only covers the request body, not the `shop-domain` header, allowing shop-identity spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string using the app's single, shop-independent `Context.api_secret_key`. The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` are read directly from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`) and are never part of the HMAC-covered bytes.

### Finding Description
The binding that should hold is: `shop bound by HMAC == shop attributed to the webhook payload by the handler`. In reality:

- `Request#hmac` decodes the `hmac-sha256` header and `to_signable_string` returns just `@raw_body`. [5](#0-4) [6](#0-5) 
- `Request#shop`, `#topic`, and `#webhook_id` are read straight from headers with no cryptographic tie to the HMAC. [7](#0-6) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and secure-compares it to the received signature — headers are never fed into the computation. [4](#0-3) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler. [3](#0-2) 

Because the same `api_secret_key` is shared across all shops installing the app (it's the app's client secret, not per-shop), any merchant who has legitimately installed the app can capture one authentic webhook delivery for their own store (a valid `body` + `hmac-sha256` pair), then replay that exact body/HMAC pair to the app's webhook endpoint while altering the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a different, victim shop. `HmacValidator.validate` still returns `true` because the body/HMAC pair is unmodified and valid for that secret; `Registry.process` then dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, with the attacker's own body content. Any app logic that trusts `data.shop` to select which tenant's data/session to update (a very common pattern for GDPR topics, order/customer sync, or state resets) receives forged input attributed to a shop the attacker doesn't control.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve for webhook delivery: `shop-domain` is the sole tenant identifier passed to the handler, and it is not cryptographically bound to the payload the HMAC actually verifies. This satisfies the Critical bar of cross-tenant access, since an unprivileged (but validly-onboarded) shop can inject attacker-controlled webhook data/actions attributed to another merchant.

### Likelihood Explanation
Exploitation only requires an attacker to install the app on their own store (a normal, unprivileged action) to obtain one legitimately-signed body/HMAC pair, then send an HTTP request to the app's webhook endpoint with a modified `shop-domain` header. No access to the app's `client_secret`, another merchant's access token, or any privileged access is needed — only control over headers on an HTTP request, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., verify shop against a separate expected value derived from session state, or include headers in the HMAC input as Shopify's platform-level webhook signature does not cover headers, so the app-layer check must). At minimum, document/enforce that `WebhookMetadata.shop` must not be treated as authenticated unless the app performs its own additional binding (e.g., checking that the shop is one that has an active, stored offline session), and consider rejecting webhooks whose header-derived `shop` cannot be correlated to a known installed shop record before dispatching the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal onboarding).
2. Attacker triggers any webhook topic the app has registered (e.g., `orders/create`), and captures the raw POST body `B` plus its valid `x-shopify-hmac-sha256` header `H` — valid because `HmacValidator.compute_signature` uses `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, B)`, and `api_secret_key` is the same for every shop. [8](#0-7) 
3. Attacker crafts a new HTTP request to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`. [9](#0-8) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop`. [10](#0-9)
