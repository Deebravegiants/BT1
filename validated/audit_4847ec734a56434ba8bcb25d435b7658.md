### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop-domain`, `topic`, and `webhook-id` values used by `Registry.process` to route and label the event are taken from unauthenticated HTTP headers. Any party able to obtain one validly-signed webhook (e.g., by installing the same public app on their own store) can replay that body/HMAC pair with a forged `shop-domain` header and have it accepted as originating from a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.topic` and `request.shop` to route the event and build `WebhookMetadata`, which is handed to the application's handler: [3](#0-2) 

Because the app's `client_secret` (and therefore the HMAC key) is shared across every merchant that installs the app, any user can install the target public app on their own (free/dev) store, trigger a webhook for that store, and receive a validly-signed `(raw_body, hmac)` pair. Since the `shop-domain` header is not part of the signed material, that same body/HMAC pair can be replayed against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop already installed on the same app. `HmacValidator.validate` will still succeed because it only re-computes the HMAC over the body: [4](#0-3) 

This breaks the intended identity binding: `shop domain used by the handler to select tenant data == shop domain covered by the signature`. In practice, the equality that should hold is `HMAC(secret, signed_material) valid ⇒ signed_material fully determines the shop/topic acted upon`; here the signed material (body only) is disjoint from the shop/topic actually used, so the equality does not hold.

By contrast, the OAuth callback HMAC (`AuthQuery#to_signable_string`) does correctly bind `shop`, `host`, `code`, `state`, and `timestamp` into the signed string: [5](#0-4) 
which highlights that the webhook path is inconsistent and omits the tenant-identifying fields from its own equivalent construct.

### Impact Explanation
An attacker who is any ordinary user of the target Shopify app (install it on their own store — no special privilege, no leaked secret, no TLS interception required) can forge webhook deliveries that the host application will attribute to a different, victim shop. Mandatory compliance topics such as `customers/redact`, `customers/data_request`, and `shop/redact` are registered through this exact same `Registry.process` path, so a forged `shop-domain` could trigger cross-tenant data deletion/export logic, or otherwise corrupt per-tenant state keyed off `WebhookMetadata#shop`. This is a cross-tenant identity-binding break, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining a legitimately-signed webhook body requires nothing more than installing the (public) app being targeted on the attacker's own shop and generating any webhook event, which is standard, unprivileged usage of any Shopify app. Swapping the `shop-domain` (and/or `topic`/`webhook-id`) header on the replay is trivial once a genuine body+HMAC pair is captured, since the header is never re-verified against the signature.

### Recommendation
Include the tenant/topic-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., verify against a per-shop expected value known independently, not from the same untrusted header set). At minimum, document and warn integrators that `request.shop`/`request.topic` are unauthenticated header values and must not be trusted as-is for tenant routing without an independent shop/session lookup.

### Proof of Concept
1. Attacker installs the target public Shopify app on their own store `attacker.myshopify.com` (any unprivileged internet user can do this).
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own store, and their endpoint (or a captured proxy) records the raw body `B` and the resulting `x-shopify-hmac-sha256: H` header — a valid signature over `B` using the app's shared `client_secret`.
3. Attacker resends a request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (a shop that has the same app installed) and optionally an interesting `x-shopify-topic` such as `customers/redact`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — validation succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata` whose `shop` is `victim.myshopify.com`, even though the request's HMAC never verified anything about that shop, letting the attacker impersonate a webhook from a shop they do not control.
