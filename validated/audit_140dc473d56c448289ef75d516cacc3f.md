### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC matches, then passes the header-derived `shop` value straight to the app's handler as trusted tenant identity, breaking the equality "shop authenticated == shop acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `Request#shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC over the body and, upon success, immediately forwards `request.shop` into `WebhookMetadata` and the app's handler as the trusted tenant identifier, with no cross-check that the header value is consistent with anything cryptographically bound to the signature: [3](#0-2) 

The `HmacValidator.validate_signature` method confirms the signature only covers `to_signable_string` (the body), never headers: [4](#0-3) 

Because the `hmac-sha256` signature is computed purely over body bytes, any `(body, hmac)` pair that is valid for one shop remains cryptographically valid when replayed with an arbitrary `shop-domain` header. An unprivileged internet user who can obtain one legitimately-signed `(body, hmac)` pair — e.g., by installing the target app on their own free/dev Shopify store and capturing the webhook Shopify sends them — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` will validate the HMAC successfully (it never inspected the header) and dispatch the attacker-controlled body to the app's handler tagged as belonging to the victim shop, per the documented `data.shop` contract in `docs/usage/webhooks.md:14`.

### Impact Explanation
This breaks the tenant isolation the library promises: `docs/usage/webhooks.md#L125` states processing "will verify the request did indeed come from Shopify," implying `shop` is a trustworthy tenant identity once `process` succeeds. In practice, an attacker with no privileges on the victim's shop can inject arbitrary attacker-controlled webhook payloads that are attributed to the victim tenant, causing the host application to perform actions (data writes, job enqueuing, cache updates, order/customer record mutation, etc.) against the wrong tenant's data — a cross-tenant access/data-injection primitive, which fits Critical severity (cross-tenant access) under this gem's own guarantees.

### Likelihood Explanation
Exploitation requires only: (1) a publicly reachable webhook endpoint (a documented, expected deployment topology for this gem), and (2) the ability to obtain one valid `(raw_body, hmac)` pair, which any attacker can trivially get by installing the target app on a shop they control (free/dev stores are readily available) and capturing the resulting webhook request. No access to `api_secret_key` or any victim credential is required.

### Recommendation
Bind the header-derived shop (and ideally topic/webhook-id) into the signed material that `HmacValidator` verifies, or otherwise reject/flag any mismatch before trusting `request.shop`. At minimum, `Registry.process` should not treat `request.shop` as authenticated tenant identity — the header should be documented as untrusted, or the signable string in `Request#to_signable_string` should incorporate the shop domain and other identifying headers so `HmacValidator.validate` fails on any header tampering.

### Proof of Concept
```ruby
# Attacker installs target app on their own shop "attacker.myshopify.com"
# and captures a genuine webhook Shopify sends them:
raw_body = '{"id": 1, "note": "hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
# (attacker does NOT know api_secret_key, but doesn't need to -- Shopify
#  computed and delivered this hmac+body pair directly to the attacker's
#  own shop's webhook already)

# Attacker replays the exact same body/hmac to the app's public webhook
# endpoint, but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks raw_body),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
#    and attacker-controlled body content.
```
