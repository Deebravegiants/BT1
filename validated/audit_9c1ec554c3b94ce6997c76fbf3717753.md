## Title
Rebasing/yield-bearing ERC-20 escrow inputs in `IntentGatewayV2`/`IntentsBase` permanently strand appreciation (and can insolvency-freeze other orders' escrow) - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary ERC-20 as an order input and escrows it by recording a **fixed** amount in `_orders[commitment][token]`, while the actual tokens sit as a **shared, pooled balance** on the gateway contract alongside every other open order's tokens. The accounting never reconciles against `balanceOf(address(this))` again after placement. This is the exact bug class described in the referenced report (M-09, FactoryDAO): the contract assumes the recorded value always equals the withdrawable balance, which is false for rebasing (and other elastic-supply) tokens.

### Finding Description
On `placeOrder`, the gateway already special-cases fee-on-transfer tokens by diffing `balanceOf(address(this))` before/after the transfer to compute the *received* amount and crediting only that to escrow: [1](#0-0) 

But this reconciliation happens **only once, at deposit time**. From that point until `fillOrder`/`cancelOrder` triggers `_withdraw`, the escrow accounting `_orders[commitment][token]` is a static integer: [2](#0-1) 

`_withdraw` releases exactly the stored `escrowed` amount and decrements it — it never looks at the live `balanceOf` of the gateway: [3](#0-2) 

If the escrowed token is a positive-rebasing token (e.g. an aToken-style asset whose `balanceOf` grows for every holder over time), the gateway's real token balance for that asset grows above the sum of all `_orders[*][token]` entries while the order is outstanding (which can be arbitrarily long — up to `order.deadline`, and cross-chain orders wait on relayer/ISMP settlement). There is no owner/protocol function anywhere in `IntentGatewayV2`/`IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` to sweep or account for this excess — the only sweep/dust mechanism (`DustCollected`) fires solely on the immediate transfer-in/transfer-out deltas at `placeOrder`/`_execute` time, not on accrued rebasing yield held during escrow. The accrued yield is therefore permanently unreachable by anyone: not the depositing user, not the solver, not governance.

Because the gateway pools **all orders' funds of a given token together** in one `balanceOf`, the inverse case is worse: a **negative**-rebasing/elastic-supply token (or any token whose balance can shrink independent of transfers) can cause the shared balance to fall below the sum of outstanding `_orders[*][token]` entries. The next unrelated order's `_withdraw`/`safeTransfer` for that token then reverts (insufficient balance), freezing settlement/cancellation for orders that have nothing to do with the token that rebased down — a shared-pool insolvency contagion, not merely lost yield.

### Impact Explanation
- Permanent freezing of funds: rebasing yield accrued on escrowed inputs is trapped in the gateway contract indefinitely, unrecoverable by the depositor, solver, or protocol — directly analogous to the referenced report's finding.
- Potential denial-of-service/fund-freezing for unrelated users: a negative-rebasing input token can make the pooled balance insufficient to satisfy other users' legitimate `_withdraw` calls for that same token, since all orders share one contract-wide balance per token rather than per-order segregated balances.
- This is reachable by any unprivileged user simply by calling `placeOrder` with a rebasing token as `order.inputs[i].token` — no special privilege or governance action is required to trigger the issue.

### Likelihood Explanation
Likelihood is Medium: it requires a rebasing/elastic-supply ERC-20 to be used as an intent input, which the protocol does not prevent (inputs are arbitrary attacker/user-chosen addresses in `Order.inputs`). Positive-rebasing tokens (Aave aTokens, stETH-style tokens, etc.) are common enough in DeFi that unaware users could select them as inputs, and the contagion case only needs one negative-rebasing/elastic token to be escrowed to threaten other users' withdrawals of that same token.

### Recommendation
- Either explicitly reject non-standard/rebasing tokens (document and, where feasible, allowlist input tokens per deployment), or
- Track escrow using shares/pro-rata accounting reconciled against live `balanceOf(address(this))` at withdrawal time (mirroring the deposit-time diffing already done for fee-on-transfer tokens), and
- Segregate token accounting so a shortfall/surplus in one token cannot block or be miscredited against other orders' `_orders[commitment][token]` entries, and provide a governance-gated sweep for any reconciled surplus so it isn't permanently stranded.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs[0].token = rebasingToken`, amount `A`. Gateway records `_orders[commitment][rebasingToken] = A` (after fee-on-transfer diffing) — see [4](#0-3) .
2. Order remains open (e.g., cross-chain settlement pending, or waiting for a solver) for a period during which `rebasingToken.balanceOf(gateway)` increases by yield `Y` for the escrowed shares, with no corresponding transfer event.
3. Order is filled/cancelled; `_withdraw` releases exactly `A` (the stored value), per [5](#0-4) . The `Y` yield remains in the contract with `_orders` accounting for it nowhere, and no function exists to withdraw it.
4. For the contagion case: escrow a negative-rebasing token in order X for amount `A`; while pending, the token's balance mechanically decreases below `A` (still recorded as `A` in storage). A later, unrelated order Y using the same token then hits `safeTransfer` failure/insufficient-balance revert in `_withdraw`, freezing order Y's legitimate settlement.
