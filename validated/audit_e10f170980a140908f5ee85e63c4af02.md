Audit Report

## Title
Unbounded `Topics` field in Web API trigger requests causes O(triggers × topics) CPU amplification in `processTrigger` - ([File: core/capabilities/webapi/trigger/trigger.go])

## Summary
`triggerConnectorHandler.processTrigger` iterates over every registered trigger and, for each one, scans the entire caller-supplied `payload.Topics` slice with no upper bound on either dimension. Since `Topics` comes straight from the unmarshaled, attacker/sender-controlled gateway message body, a single request with a very large topics array multiplies the CPU cost of matching against every registered workflow trigger on the node before any rate-limiting or sender-allowlist check is applied.

## Finding Description
`HandleGatewayMessage` unmarshals the request payload without any bound on array sizes and dispatches to `processTrigger` for `MethodWebAPITrigger`: [1](#0-0) 

Inside `processTrigger`, `topics := payload.Topics` is used directly, and only an empty-topics check is performed before the nested loop: [2](#0-1) 

The handler then snapshots all registered triggers and runs a full cross-product scan: for every trigger, for every topic, it performs a map lookup, and only checks `allowedSenders` and the per-trigger `rateLimiter` *after* a topic match is found — i.e., after the (potentially large) topic list has already been scanned once per registered trigger: [3](#0-2) 

The only structural bound on `len(payload.Topics)` comes from the overall gateway message size limit (`MaxMessageLenBytes`, default 500,000 bytes, documented in `docs/CONFIG.md`), not from any explicit validation in `processTrigger` or `RegisterTrigger`/schema for `TriggerRequestPayload`, whose JSON schema only requires `topics` to be an array of strings with no `maxItems`: [4](#0-3) 

Given a large number of registered triggers (`registeredWorkflows`) on a node and a `Topics` array packed with many short strings (bounded mainly by the overall message-size cap), the number of map lookups performed synchronously by this loop scales with `len(triggers) * len(topics)`.

## Impact Explanation
This is a genuine algorithmic inefficiency: work performed inside a gateway-message handler scales with attacker-supplied array length multiplied by the number of registered triggers, rather than being proportional to the number of actual matches. Each gateway request is processed on its own goroutine per the `Handler` interface's documented model, so the practical impact is increased CPU consumption per malicious message rather than serialized blocking of a single shared worker, but concurrent floods of such messages can still degrade node CPU availability and delay processing of legitimate trigger events for other workflows. This maps to an availability/DoS class rather than data exfiltration or fund movement, and its severity is bounded by the overall gateway message size limit (default 500,000 bytes) which caps how many topic strings can realistically be packed into one message. [5](#0-4) 

## Likelihood Explanation
Reachability requires only that a caller can get a validly-signed `web_api_trigger` gateway message delivered and broadcast to node connectors — the `allowedSenders`/`allowedTopics` checks inside `processTrigger` are applied only after a topic hash-match, not before the loop runs, so any signer capable of producing a valid `Message.Validate()`-passing signature can trigger the full O(triggers × topics) scan regardless of whether they are ultimately authorized for any workflow. No additional size limit is enforced on `Topics` specifically prior to entering the loop. [6](#0-5) 

## Recommendation
- Enforce an explicit maximum length on `payload.Topics` (e.g., reject requests with more than N topics) before entering the matching loop.
- Index triggers by topic (e.g., `map[topic][]*webapiTrigger`) rather than performing a full O(triggers × topics) scan, so lookup cost scales with matches, not the full cross-product.
- Apply sender/global rate limiting or a cheap request-cost check ahead of the loop, not only on the matched-topic branch.

## Proof of Concept
1. Register a moderate-to-large number of workflow triggers via `RegisterTrigger` on a node (each with distinct `allowedTopics`).
2. Craft a `web_api_trigger` gateway message whose JSON body's `payload.topics` field contains as many short unique strings as fit within `MaxMessageLenBytes` (default 500,000 bytes).
3. Sign the message with any valid ECDSA key (does not need to be in any `allowedSenders` list) so it passes `Message.Validate()`.
4. Send it through the gateway so it reaches a node's `triggerConnectorHandler.HandleGatewayMessage` → `processTrigger`.
5. Measure CPU time spent in the nested loop `for _, trigger := range triggers { for _, topic := range topics { ... } }` scaling with `len(triggers) * len(topics)`, compared to a single-topic baseline request — an integration/unit test (e.g., extending `core/capabilities/webapi/trigger/trigger_test.go`) with a benchmark or timing assertion across many registered triggers and a large topics slice would demonstrate the amplification.
