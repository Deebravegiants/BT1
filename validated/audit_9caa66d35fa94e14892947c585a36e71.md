### Title
Missing shop-domain validation in Authorization Code Grant OAuth flow allows client_secret exfiltration to attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` use the caller-supplied `shop` (and `auth_query.shop`) value directly to build request hosts, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike the sibling `RefreshToken`, `ClientCredentials`, and `TokenExchange` flows which explicitly validate the shop domain is one of `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it.

### Finding Description
`Utils::ShopValidator.sanitize!` [1](#0-0)  exists specifically to prevent an untrusted `shop` string from being turned into a request host, and is deliberately used in `RefreshToken.refresh_access_token` [2](#0-1)  before that shop is used to build a `Session` and send `client_secret` via `Clients::HttpClient`.

`Auth::Oauth.validate_auth_callback`, however, takes `auth_query.shop` straight from the `AuthQuery` object and constructs `null_session = Auth::Session.new(shop: auth_query.shop)` with no `ShopValidator` call, then passes that session into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` [3](#0-2) . `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3)  directly from that unsanitized `session.shop`, then the subsequent `request` call POSTs the JSON body containing `client_id`, `client_secret`, and `code` to `https://#{auth_query.shop}/admin/oauth/access_token` [5](#0-4) .

`Auth::Oauth.begin_auth` similarly uses the raw `shop` parameter in `auth_base_uri(shop)` to build the `auth_route` the user is redirected to [6](#0-5) [7](#0-6) .

The `AuthQuery.shop` field is part of the query covered by the HMAC signature and validated via `Utils::HmacValidator.validate(auth_query)` [8](#0-7)  using `Context.api_secret_key`, so under normal Shopify-initiated flows the shop value is Shopify-issued and HMAC-protected. However, this HMAC check only proves the query was signed with the app's own secret — it does not independently verify that `auth_query.shop` is a genuine `*.myshopify.com`/trusted Shopify domain the way `ShopValidator` does. If a host application constructs an `AuthQuery` from parameters that were not strictly the exact callback query Shopify sent (e.g., partially reused/merged params, or scenarios where `begin_auth`'s `shop` input — which is explicitly documented as coming from an incoming request header, e.g. `request.headers["Shop"]` in the docs example — is not itself validated before being handed to `begin_auth`), there is no defense-in-depth check inside the gem analogous to the one deliberately added to `RefreshToken`/`ClientCredentials`/`TokenExchange`. This is an inconsistency in the identity-binding model: `shop` is trusted as "the field an HMAC happens to cover" rather than "a field independently verified to be a Shopify domain," breaking the equality `shop used to build request host == shop validated as a trusted Shopify domain` that the other three flows maintain.

### Impact Explanation
If the unsanitized shop value can be steered to a non-Shopify host (e.g. through `begin_auth`'s directly-supplied `shop` parameter, which per the gem's own documentation is meant to be taken from user/request-controlled input such as a `Shop` header), the app's `client_secret` and authorization `code` would be POSTed to an attacker-controlled host by `validate_auth_callback`, and the OAuth authorize redirect built by `begin_auth` would send users to an attacker-controlled domain. This matches the Critical category: theft/exfiltration of the app's `client_secret` and authorization code, i.e., SSRF carrying the app's credentials to a host not verified as Shopify.

### Likelihood Explanation
Likelihood is moderate-to-low in the strict callback path because the `shop` field embedded in `auth_query` is part of the HMAC-signed data, so a purely network-based attacker without the `api_secret_key` cannot forge a callback with an arbitrary shop value passing HMAC validation. The higher-likelihood path is `begin_auth`, whose `shop` argument is explicitly documented as being sourced from request-controlled data (e.g. a `Shop` header) with no sanitization performed by the gem itself before it is used to build the redirect URL — this is a genuine gap relative to the pattern established in `RefreshToken`/`ClientCredentials`/`TokenExchange`, which all call `ShopValidator.sanitize!` first.

### Recommendation
Add a call to `Utils::ShopValidator.sanitize!(shop)` (or `sanitize!(auth_query.shop)`) at the start of `Oauth.begin_auth` and `Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, mirroring the validation already performed in `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, and `TokenExchange.exchange_token`, before the shop value is used to build `auth_base_uri`, construct the `Session`, or initialize `Clients::HttpClient`.

### Proof of Concept
1. A host application wires up the documented `login` action exactly as shown in `docs/usage/oauth.md`, taking `shop` from `request.headers["Shop"]` and passing it unsanitized to `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. An attacker sends a request with `Shop: attacker-controlled-host.evil.com`.
3. `auth_base_uri` builds `"https://attacker-controlled-host.evil.com/admin" + "/oauth/authorize?..."` [9](#0-8)  and the app redirects the victim's browser there instead of to Shopify, unlike `RefreshToken`, which would reject such a shop value via `ShopValidator.sanitize!` and raise `Errors::InvalidShopError`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),

            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
