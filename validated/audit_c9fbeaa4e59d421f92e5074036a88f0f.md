Audit Report

## Title
Uncapped `last_update_block` after pool expiry causes permanent arithmetic-underflow DoS and frozen staker funds - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` computes elapsed reward blocks by clamping the current block to `pool_info.expiry_block` via `last_block_reward_applicable`, but the companion `update_pool_rewards` function unconditionally stores the real, unclamped current block number into `last_update_block`. Once any pool interaction occurs after expiry (with nonzero `total_tokens_staked`), `last_update_block` exceeds `expiry_block`, and the next reward computation underflows in `expiry_block.ensure_sub(last_update_block)`, permanently reverting every subsequent pool-touching extrinsic and freezing staked funds.

## Finding Description
`reward_per_token` clamps the "now" value to `pool_info.expiry_block` through `last_block_reward_applicable` before subtracting `pool_info.last_update_block`: [1](#0-0) [2](#0-1) 

However, `update_pool_rewards`, called immediately afterward by every pool-touching operation, writes the real current block number (not clamped to `expiry_block`) into `last_update_block`: [3](#0-2) 

This is the root cause: the value written to `last_update_block` and the value used as the baseline in `reward_per_token`'s next computation are asymmetric once `now > expiry_block`. On the first post-expiry call, `reward_per_token` still succeeds because the old `last_update_block` (≤ `expiry_block`) is subtracted from the clamped `expiry_block`. But `update_pool_rewards` then sets `last_update_block` to the unclamped `now` (> `expiry_block`). On the *next* call with nonzero `total_tokens_staked`, `last_block_reward_applicable` again returns `expiry_block` (since `now` is still > `expiry_block`), and `expiry_block.ensure_sub(last_update_block)` underflows because `last_update_block > expiry_block`, returning `Err(ArithmeticError::Underflow)` via `EnsureSub`.

This error propagates through `update_pool_and_staker_rewards`: [4](#0-3) 

`stake` calls this helper unconditionally and with no expiry gating, meaning even staking into an already-bricked pool fails: [5](#0-4) 

`unstake` and `harvest_rewards` also call it, and explicitly permit any account (not just the staker) to invoke them post-expiry — meaning any third party interacting with an expired pool can trigger the state corruption unintentionally: [6](#0-5) [7](#0-6) 

The admin's only recovery path, `set_pool_expiry_block`, also calls `reward_per_token` first and thus fails identically, so there is no way to un-brick the pool once triggered: [8](#0-7) 

I verified the repository's git history contains only a single "Initial commit" for this file, so there is no evidence of a subsequent fix applied to this codebase.

## Impact Explanation
Once the underflow condition is reached, every subsequent `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block` call on that pool reverts with an arithmetic error, as long as `total_tokens_staked` remains nonzero. Since `unstake` is the sole mechanism to release `FreezeReason::Staked` freezes placed during `stake` ( [9](#0-8) ), and it too reverts, all remaining stakers' frozen assets in that pool become permanently locked with no admin remediation available. This is a genuine, concrete denial-of-service plus fund lock-up affecting an in-scope FRAME pallet, triggerable without any privileged access.

## Likelihood Explanation
The trigger requires only: (1) a pool reaching its `expiry_block` while stakers remain active with nonzero `total_tokens_staked`, and (2) two ordinary, permissionless interactions with the pool after expiry (e.g., two calls to `harvest_rewards`/`unstake`, which are explicitly open to any caller post-expiry, or a staker calling `stake` twice). No governance, admin privilege, or unrealistic assumptions are needed — this is a routine post-expiry usage pattern that any unprivileged user (or even innocent normal usage) will trigger, making it highly likely to occur on any pool that reaches expiry with active stakers remaining.

## Recommendation
In `update_pool_rewards`, clamp the stored `last_update_block` using the same `last_block_reward_applicable(pool_info.expiry_block)` helper used by `reward_per_token`, instead of unconditionally assigning `T::BlockNumberProvider::current_block_number()`, so both functions use a consistent, expiry-capped block reference.

## Proof of Concept
1. `create_pool` with `expiry_block = E` (e.g., via `DispatchTime::After(10)`).
2. Staker `A` calls `stake` at block `T1 ≤ E`; `last_update_block = T1`.
3. Advance to block `T2 > E`. Any account calls `harvest_rewards`/`unstake` (or `A` calls `stake` again) on the pool — this succeeds, but `update_pool_rewards` sets `last_update_block = T2` (unclamped, `T2 > E`), per [10](#0-9) .
4. Advance to block `T3 > T2`. Any subsequent `stake`/`unstake`/`harvest_rewards`/`set_pool_expiry_block` call computes `expiry_block.ensure_sub(last_update_block)` with `last_update_block(T2) > expiry_block(E)` in [11](#0-10) , underflows, and the extrinsic fails with `ArithmeticError::Underflow`, permanently locking `A`'s frozen stake with no admin recovery path available.

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);
