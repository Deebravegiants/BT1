### Title
Uniswap V4 venue pricing in Simplex's intent filler uses manipulable spot price with no mandatory guard - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`, `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
Simplex's intent-filling strategy prices "venue-priced" (curveless) pairs directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96` mid-price, exactly the class of flaw described in the source report (`MavEthOracle::getPriceInEth` deriving an LP/pool valuation from live, swappable reserves). An attacker who can move the pool's spot price with a swap (optionally flash-loaned) immediately before submitting an intent order can force the filler to quote and pay out at the manipulated price, and the only defense (`referencePrice`/`maxDeviationBps`) is explicitly optional and disabled by default.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` derives the USD price of the "exotic" token directly from `sdkPool.token0Price`/`token1Price`, which are computed from the pool's current `sqrtPriceX96` — a raw spot price with no TWAP or impact adjustment: [1](#0-0) 

This price is selected as the "best" price by picking the highest-liquidity qualifying position and returned to `getExoticTokenPrice`: [2](#0-1) 

`resolveLegRates` in the fx strategy consumes this venue price directly as the fill rate for any curveless pair whose `token0` is a USD stablecoin, applying only an optional deviation guard against a static `referencePrice`: [3](#0-2) 

The project's own documentation confirms this guard is optional and, when omitted, the chain is explicitly "unguarded": [4](#0-3) 

and separately documents that the pool mid is used unadjusted for fee tier or trade size, with the guard being the only defense and only checking deviation from a static reference rather than execution cost: [5](#0-4) 

This is the same root cause as the `MavEthOracle` bug: a value used to price fills (there, an LP token; here, the venue's exchange rate) is read directly from a pool's current reserves/tick state, which any address can move within the same transaction by performing a swap, with no manipulation-resistant sampling (TWAP, median-of-multiple-pools, or a mandatory deviation bound).

### Impact Explanation
Any unprivileged party can submit an intent order against a curveless, venue-priced pair on a chain where the solver has configured Uniswap V4 LP funding but has not set `referencePrice`/`maxDeviationBps` (an explicitly supported, documented configuration). Before or within the same block/bundle, the attacker manipulates the referenced Uniswap V4 pool's spot price via a swap, causing `computeDirectPoolPriceUsd` to return an inflated/deflated price. The solver's filler then computes `policyMaxOutput` from that manipulated rate and delivers tokens at the bad price, extracting value from the solver's Uniswap V4-backed funding position — a direct fund-loss vector reachable purely by submitting an order plus an ordinary DEX swap, with no admin/governance/relayer trust assumptions violated.

### Likelihood Explanation
Likelihood is high in any deployment that enables Uniswap V4 venue pricing without setting the optional guard, which the docs describe as a normal, supported state ("omit both to leave the chain unguarded"). Even where the guard is set, the guard only checks against a static reference within a bps band, not against trade size/impact, so an attacker can still profit by manipulating price to just within the allowed deviation band while pushing execution economics against the solver, similar to how the original Tokemak bug remained exploitable at scale via flash loans.

### Recommendation
Do not price venue-funded pairs from a single, unguarded, single-block spot read. Options:
- Make `referencePrice`/`maxDeviationBps` mandatory whenever `[vault.uniswapV4]` positions are configured, rather than optional.
- Derive the venue price from a manipulation-resistant source (TWAP over multiple blocks, multiple pools/liquidity sources, or an off-chain oracle cross-check) rather than the instantaneous `sqrtPriceX96`.
- Bound the priced notional by pool depth/impact so the effective execution price, not just the mid, is checked against the reference.

### Proof of Concept
1. Solver configures `[vault.uniswapV4]` for a curveless pair (e.g., `USDC/EXOTIC`) without setting `referencePrice`/`maxDeviationBps`, per the documented supported configuration (`docs/content/developers/evm/simplex/pricing.mdx` lines 40-66, 68-72).
2. Attacker swaps a large amount in the referenced Uniswap V4 pool to move `sqrtPriceX96` so that `sdkPool.token0Price`/`token1Price` reflects an inflated EXOTIC price.
3. Attacker (or their agent) submits an intent order via the intent gateway for that pair; `resolveLegRates` → `venuePriceMemo` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` returns the manipulated price (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts` lines 206-274).
4. `computeLegPolicyOutput` (`sdk/packages/simplex/src/strategies/fx.ts` lines 1397-1434) computes `policyMaxOutput` from this manipulated `rate`, and the filler pays out at the bad price, funded by withdrawing liquidity from the solver's Uniswap V4 position (`UniswapV4FundingPlanner.planWithdrawalForToken`).
5. Attacker reverses the initial swap, retaining the value extracted from the mispriced fill, minus swap fees — the same flash-loan-amplifiable pattern as the original `MavEthOracle` PoC.

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
