### Title
Fee-on-transfer input tokens cause escrow over-crediting and cross-order fund drain in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-chain deployment of `IntentGatewayV2.placeOrder` credits escrow (`_orders[commitment][token]`) using the user-specified/requested input amount (minus protocol fee) instead of the amount actually received by the contract after `safeTransferFrom`. The parallel EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) was explicitly hardened against this by measuring `balanceOf` before/after transfers, but the Tron variant was not updated with this fix, reintroducing the fee-on-transfer accounting bug analogous to the reported `SingleSidedLiquidityVault` issue.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` (lines 338-469), the reduced/escrowed amount is computed purely from `order.inputs[i].amount` supplied by the caller: [1](#0-0) 

and then in the no-predispatch branch the contract pulls tokens with `safeTransferFrom` but never checks the actual balance delta before crediting escrow: [2](#0-1) 

The predispatch branch has the same flaw: it computes `dust = balance - requiredAmount` (based on `dispatcher`'s balance vs the *requested* amount) but still credits `_orders[commitment][token] += reducedInputs[i].amount`, which is derived from `order.inputs[i].amount`, not the amount that actually reaches `address(this)`: [3](#0-2) 

By contrast, the EVM version of this contract was patched to measure `balanceOf(address(this))` before and after the transfer and mutate `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow: [4](#0-3) 

This fix is validated by dedicated fee-on-transfer regression tests in the test suite: [5](#0-4) 

The Tron contract omits this balance-delta check entirely, so if the input token charges a transfer fee (fee-on-transfer / deflationary token), `IntentGateway` will record more tokens in escrow (`_orders[commitment][token]`) than it actually holds.

### Impact Explanation
Because `_orders[commitment][token]` is over-credited relative to the actual token balance held by the contract, subsequent `withdraw()` calls (triggered via `RedeemEscrow`/`RefundEscrow` in `onAccept`, or via same-chain `cancelOrder`) will pay out the inflated escrowed amount to the beneficiary/filler: [6](#0-5) 

Since the contract is a shared pool holding escrow for many concurrent orders, the shortfall caused by the fee-on-transfer deduction is paid out of other users' escrowed balances — i.e., value is not just lost by the depositor's own order, but siphoned from the pooled contract balance funded by other orders, resulting in insolvency/fund drain for the protocol and other users. This is a direct loss-of-funds vulnerability reachable by any unprivileged user submitting `placeOrder` with a fee-on-transfer token as input.

### Likelihood Explanation
Likelihood is realistic: the token used as input is chosen by the order creator, not the protocol, so any user (attacker) can select or deploy a fee-on-transfer ERC20/TRC20 to trigger the mismatch. No privileged role or special conditions are needed — a single `placeOrder` call with a deflationary token suffices to create the escrow/balance divergence, and a corresponding `withdraw` (fill, refund, or cancel) realizes the loss.

### Recommendation
Apply the same fix already implemented in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` (and after the predispatch sweep) and use the actual received delta — not the caller-supplied `amount` — for computing `reducedInputs`, the commitment hash, and the escrow credit in `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a fee-on-transfer TRC20/ERC20 token (e.g., 1% fee on transfer) and mint balance to `user`.
2. `user` calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom(user, address(this), 1000e18)` executes; contract actually receives only 990e18 due to the transfer fee.
4. Contract computes `reducedInputs[0].amount` from the original `1000e18` (minus protocol fee if any) and sets `_orders[commitment][FOT] = reducedAmount ≈ 1000e18 (or 970e18 with fee)`, while the actual token balance increase was only `990e18`.
5. When the order is later filled/cancelled and `withdraw()` is invoked, the contract transfers out the inflated `_orders[commitment][FOT]` amount, which exceeds what was actually deposited for this order — the difference is drawn from tokens escrowed for other orders held by the same contract, causing shortfall/insolvency for those other users. This mirrors the exact `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` test scenario present in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, which passes for the EVM contract but has no equivalent protection in the Tron contract.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
