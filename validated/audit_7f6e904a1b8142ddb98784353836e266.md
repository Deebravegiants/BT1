### Title
Aleo destination-address check bypassed by case variance — `compareAddresses` uses raw string equality while `validateAleoAddress` accepts case-insensitive bech32m — (File: `packages/intents-sdk/src/lib/compareAddresses.ts`, `packages/intents-sdk/src/lib/validateAddress.ts`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.validateWithdrawal` is supposed to guarantee that a withdrawal's `destinationAddress` never resolves to the token's own on-chain address, using `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)`. For Aleo, `compareAddresses` falls through to raw string equality (`a === b`), but `validateAddress`/`validateAleoAddress` accepts bech32m-encoded addresses independent of letter case, because bech32/bech32m decoding (per BIP-173/350, implemented by `@scure/base`) requires only that a string be *entirely* upper- or entirely lower-case, and normalizes to lowercase internally before validating the checksum and curve point. An attacker can submit the token's own address in all-uppercase as `destinationAddress`; it validates as the exact same Aleo account, but the raw-string equality check in `compareAddresses` fails to detect the match, so `DestinationAddressMatchesTokenAddressError` is never thrown.

### Finding Description
The broken equality: `compareAddresses(tokenAddress, destinationAddress, Chains.Aleo)` must be `true` whenever `tokenAddress` and `destinationAddress` denote the same Aleo account (same bech32m payload/curve point), matching the guarantee documented directly above the function: "Compares two addresses for equality using each chain's canonical form ... to block transfers to the token's own address."

Code path:
1. `validateWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 181-219) first calls `validateAddress(args.destinationAddress, assetInfo.blockchain)`. For Aleo this dispatches to `validateAleoAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` (lines 758-799), which calls `bech32m.decodeToBytes(address)`. Bech32/bech32m decoders, per spec, accept a string in either all-uppercase or all-lowercase form and normalize internally to lowercase before checksum/prefix checks — so an all-uppercase copy of a valid Aleo address decodes successfully and passes the on-curve subgroup check identically to the lowercase original.
2. `validateWithdrawal` then calls `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)` (lines 207-219). In `packages/intents-sdk/src/lib/compareAddresses.ts` (lines 48-60), `Chains.Aleo` is grouped with chains that use raw `a === b` comparison — unlike EVM/Aptos/TON/Tron/Stellar, which each get a canonicalizing comparator specifically to catch case/format variants of the *same* address.
3. Because `origin_chain_address` is stored/returned by the PoA bridge API in one canonical case (lowercase, based on the test fixtures), an attacker-supplied all-uppercase version of that same address makes `compareAddresses` return `false` even though the two strings denote the identical Aleo account.
4. `DestinationAddressMatchesTokenAddressError` is therefore not thrown, and `validateWithdrawal` resolves successfully, allowing `createWithdrawalIntents` to build a withdrawal intent sending the token to its own contract address on Aleo.

Root cause: `compareAddresses` for Aleo does not canonicalize case the way `validateAleoAddress` (via bech32m decoding) does, so the two functions disagree on what counts as "the same address."

### Impact Explanation
An unprivileged NEAR Intents user (or an integrator forwarding attacker-controlled `destinationAddress`) can trigger a withdrawal that the SDK itself is supposed to block, sending tokens to the token's own contract address on Aleo with no recovery path. This matches the Critical impact category: "funds delivered to a wrong address/chain/contract with no recovery." The attacker debits their own account for the withdrawal amount and it is destroyed/unrecoverable at the token contract — this is a self-harm griefing/footgun bypass of a safety check rather than theft from others, but it defeats the specific invariant the code claims to enforce and is repeatable for every Aleo asset with a non-native `origin_chain_address`.

### Likelihood Explanation
Preconditions: an Aleo-based POA-bridge asset with `origin_chain_address !== "native"` (the check is skipped entirely for native assets). Attacker cost: trivial — just uppercase the known token address string, no keys or infrastructure needed. The bech32m case-insensitivity of the validator is inherent to the bech32/bech32m spec used by `@scure/base` and not tied to any RPC/relayer trust assumption, so this is fully reachable via the public `IntentsSDK.processWithdrawal` entrypoint with attacker-controlled `destinationAddress`.

### Recommendation
In `compareAddresses.ts`, add an Aleo-specific canonicalizing comparator (e.g., decode both addresses via `bech32m.decodeToBytes`, lower-case/normalize, and compare the decoded byte payloads) analogous to `compareHexAddress`/`compareTonAddress`/`compareTronAddress`, instead of relying on raw string equality for `Chains.Aleo`.

export function validateAleoAddress(address: string): boolean {
	try {
		const decoded = bech32m.decodeToBytes(address);
		if (decoded.prefix !== "aleo") return false;
		if (decoded.bytes.length !== 32) return false;

		// Extract x-coordinate, clearing the y-sign flag (MSB of last byte)
		const bytes = new Uint8Array(decoded.bytes);
		bytes[31] = (bytes[31] as number) & 0x7f;

		let x = 0n;
		for (let i = 31; i >= 0; i--) {
			x = (x << 8n) | BigInt(bytes[i] as number);
		}
		if (x >= P) return false;

		// y² = (1 + x²) / (1 - d·x²)  (equivalent to Rust: (a·x²-1)/(d·x²-1) with a=-1)
		const x2 = (x * x) % P;
		const num = (1n + x2) % P;
		const den = (((1n - ((D * x2) % P)) % P) + P) % P;
		if (den === 0n) return false;

		const denInv = modPow(den, P - 2n, P);
		const y2 = (num * denInv) % P;

		// Decompress: recover y via square root
		const y = modSqrt(y2);
		if (y === null) return false;

		// snarkVM checks both (x, y) and (x, -y) for subgroup membership
		const negY = y === 0n ? 0n : P - y;
		const p1: ExtPoint = [x, y, (x * y) % P, 1n];
		const p2: ExtPoint = [x, negY, (x * negY) % P, 1n];

		for (const pt of [p1, p2]) {
			if (isIdentity(scalarMul(pt, SUBGROUP_ORDER))) return true;
		}
		return false;
	} catch {
		return false;
	}
}
