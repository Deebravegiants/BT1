### Title
POA bridge withdrawal status matched only by `assetId`, misreporting completion/hash for the wrong withdrawal when a batch contains multiple withdrawals of the same token - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` and the lower-level `waitForWithdrawalCompletion` helper identify which entry in the POA bridge's `withdrawals` response array corresponds to a given `WithdrawalIdentifier` (a specific NEAR transaction + `index`) by matching **only on `assetId`** via `findMatchingWithdrawal`, ignoring `amount`, `destinationAddress`, and the withdrawal's `index`. If a single NEAR transaction contains more than one withdrawal of the same token (e.g., two withdrawals of the same NEP-141 asset to two different destination addresses/amounts within one batch), the function can return the status/`txHash` belonging to a *different* withdrawal than the one being queried.

### Finding Description
`findMatchingWithdrawal` in `poa-bridge.ts` selects the first withdrawal in the (explicitly documented as unsorted) API response whose `nep141:${w.data.near_token_id}` equals the requested `assetId`: [1](#0-0) 

`describeWithdrawal` calls this matcher using only `args.withdrawalParams.assetId`, then returns `completed` with `withdrawal.data.transfer_tx_hash` as the destination tx hash for whichever entry matched, without validating that the entry's `amount`/`address` (destination) actually correspond to the specific `WithdrawalIdentifier` (which encodes a specific `index` from the batch): [2](#0-1) 

The equivalent logic in `internal-utils`'s `waitForWithdrawalCompletion` has the identical limitation, matching only by `assetId` in `WithdrawalCriteria`: [3](#0-2) 

The code comments explicitly acknowledge this: "Currently only matches by assetId... This means multiple withdrawals of the same token in a single transaction are not supported," and the test suite for `poa-bridge.ts` only exercises "matches withdrawal by assetId, not by index" for a single distinct-asset scenario, never a same-asset multi-withdrawal batch: [4](#0-3) 

This breaks the equality that the status/hash reported for withdrawal `index=N, destination=D_N, amount=A_N` must reflect the actual on-chain outcome for that specific `(D_N, A_N)` pair — instead it can report the outcome of an unrelated `(D_M, A_M)` withdrawal from the same batch that happens to share the token.

### Impact Explanation
If an integrator processes a NEAR transaction containing two withdrawals of the same token to two different destinations, and calls `describeWithdrawal` for each `WithdrawalIdentifier`, both calls can resolve to the same (first-matched) entry. This can cause:
- A withdrawal that has not actually settled to be reported as `completed` with a `txHash` belonging to a sibling withdrawal (status misreport), potentially causing an integrator to prematurely credit/release funds or mark an incomplete transfer as done.
- A completed withdrawal being reported as `pending` because the matcher returns the sibling entry's `PENDING` status instead, delaying legitimate settlement.

This matches the "status or hash misreport making an integrator credit or refund twice" class of High-impact issue, since downstream systems relying on `describeWithdrawal`'s per-index result would attribute the wrong destination tx hash to a withdrawal request.

### Likelihood Explanation
This requires a batch NEAR transaction that includes two or more withdrawals of the *same* NEP-141 asset (different destinations/amounts) processed through the POA bridge — a legitimate, unprivileged usage pattern (e.g., a user or integrator batching several withdrawals of the same token to different recipients in one intent execution). No malicious actor or admin action is needed; it is triggered purely by normal multi-withdrawal usage that the code and its comments already acknowledge is unsupported/broken.

### Recommendation
- Short term: Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `waitForWithdrawalCompletion.ts`) to disambiguate between multiple same-asset withdrawals using `amount` and `destinationAddress` (or, if available from the API, a proper `index`/`memo` correlation field) in addition to `assetId`, and fail closed (throw/return `pending`) rather than pick an arbitrary match when ambiguity remains.
- Long term: If the POA bridge API cannot provide a stable per-withdrawal correlation identifier, disallow/validate against submitting batches containing multiple withdrawals of the same token in a single NEAR transaction, or explicitly document and enforce this as an unsupported input at the SDK boundary (reject such batches early) instead of silently returning incorrect statuses.

### Proof of Concept
1. A user submits one NEAR transaction with two withdrawals of `nep141:usdc.omft.near`: withdrawal `index=0` → destination `0xAAA`, amount `100`; withdrawal `index=1` → destination `0xBBB`, amount `50`.
2. The POA bridge indexes both; suppose `index=1` (destination `0xBBB`) settles first and appears in the `withdrawals` API response with `status: "COMPLETED"`, while `index=0` (destination `0xAAA`) is still `PENDING`.
3. The integrator calls `describeWithdrawal` for the `WithdrawalIdentifier` of `index=0` (destination `0xAAA`). `findMatchingWithdrawal` matches purely on `nep141:usdc.omft.near` and, because the response array is unsorted per the code's own comment (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:318`), can return the `COMPLETED` entry for `index=1`.
4. `describeWithdrawal` returns `{ status: "completed", txHash: <hash for 0xBBB's transfer> }` for the withdrawal request targeting `0xAAA`, even though `0xAAA` never received funds — a status/hash misreport that could cause the integrator to treat the `0xAAA` withdrawal as settled and credit/release downstream state incorrectly.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
