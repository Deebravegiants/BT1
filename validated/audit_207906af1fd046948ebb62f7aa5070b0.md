### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC solely against the raw request body, while the `shop` (tenant identity) is read from a separate, unauthenticated header. Any user who can obtain one genuine webhook delivery for their own shop (e.g., by installing the target app on their own store) can replay the same body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop, and the gem will accept it as authentic and hand the forged shop identity to the host application's webhook handler.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never folded into the signed material: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, to_signable_string)`, i.e. only the body bytes are authenticated: [3](#0-2) 

`Registry.process` accepts any request that passes this body-only HMAC check and then forwards `request.shop` straight into `WebhookMetadata` for the host application's handler, with no additional binding between the verified bytes and the claimed shop: [4](#0-3) 

The identity binding that should hold is: `shop delivered to handler == shop that produced the HMAC-signed bytes`. Because the signature only covers the body, this equality is never enforced — `shop` is "a field acted on but not covered by the HMAC," matching the bug class in the referenced report (data trusted based on incomplete validation of the source).

### Impact Explanation
Any unprivileged internet user who can install the target Shopify app on a shop they control (a normal, unauthenticated action for public apps) can trigger a real webhook delivery to the app's endpoint and capture a valid `(raw_body, hmac)` pair. They can then replay that exact body and HMAC to the app's webhook endpoint while forging the `shop-domain` header to name a different, victim shop. The gem will validate the HMAC successfully (it only checks the body) and will construct `WebhookMetadata` claiming the payload came from the victim shop. If the host application uses `WebhookMetadata#shop` to select which tenant's record/session to update (the intended and documented use, per `docs/usage/webhooks.md`), this results in cross-tenant data injection/corruption — a bypass of the tenant isolation the HMAC check is meant to guarantee.

### Likelihood Explanation
Likelihood is high for any app builder relying on the gem's `shop` metadata without independently re-validating it: obtaining a signed webhook body is trivial for an attacker who installs the app on their own store (a standard, unauthenticated path for public apps), and no cryptographic secret is required to perform the header substitution, since only the body is signed.

### Recommendation
Include the shop/topic/webhook-id identifying fields in the signable material used for HMAC verification (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any header claimed to identify the tenant is altered relative to what was actually signed by Shopify.

### Proof of Concept
1. Install the target app (using this gem) on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because `H = HMAC(secret, B)`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, B)` and finds it equal to `H`, so validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, attributing attacker-controlled payload content to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
