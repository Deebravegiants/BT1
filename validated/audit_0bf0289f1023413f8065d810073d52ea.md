Audit Report

## Title
External Initiators can trigger job runs even when the `ExternalInitiatorsEnabled` feature flag is disabled - ([File: core/web/auth/auth.go])

## Summary
The `AuthenticateExternalInitiator` middleware, which validates the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers and grants the caller the `UserRoleRun` role, never checks `JobPipeline.ExternalInitiatorsEnabled`. Only `ExternalInitiatorsController.Create` enforces this flag. This confirms that a credential issued while the feature was enabled continues to authenticate and grant the run role after the operator disables the feature.

## Finding Description
`ExternalInitiatorsController.Create` explicitly gates initiator creation on the config flag: [1](#0-0) 

But `AuthenticateExternalInitiator`, which is the actual authentication/authorization path invoked on every request bearing EI credentials, performs no equivalent check — it only validates the access key/secret against the stored `bridges.ExternalInitiator` record and then unconditionally grants `UserRoleRun`: [2](#0-1) 

The `ExternalInitiator` struct has no enabled/disabled state field, confirming there is no mechanism to invalidate a previously issued credential other than deleting it from the database: [3](#0-2) 

This matches the described bug pattern: the restriction (`ExternalInitiatorsEnabled`) is enforced at one entry point (creation) but omitted at the other (authentication/use), so a previously created credential keeps working after the flag is toggled off.

## Impact Explanation
This is a genuine authorization-consistency gap: disabling `ExternalInitiatorsEnabled` is documented/expected to disable the External Initiator feature, but existing credentials remain fully functional for authenticating and triggering job runs via any endpoint using `AuthenticateExternalInitiator`. This falls into the in-scope category of "node API authentication or role bypass" / "unauthorized job run," since a caller retains the `Run` role and can invoke job-run endpoints despite the operator's intent to shut off the feature.

However, the practical severity is limited: the caller must already possess a validly-issued `AccessKey`/`Secret` pair — this is not a bypass reachable by a fully unprivileged attacker with no prior grant; it is a "stale credential remains valid past a config toggle" issue, closer to a soft policy-enforcement gap than a privilege escalation from zero access. It does not grant new privileges beyond what the credential's issuer already possessed (the `Run` role, limited to submitting runs for jobs the EI is already wired to) — it merely fails to revoke that access when the global switch is flipped.

## Likelihood Explanation
Requires: (1) an EI credential having been created while the feature was enabled, and (2) the operator later disabling the flag while expecting existing credentials to stop working. Given no revocation mechanism ties existing credentials to the flag, the bypass is deterministic and repeatable for anyone already holding a valid EI credential. This is a real inconsistency in the code, verified directly by reading both call sites and the `ExternalInitiator` model.

## Recommendation
Add the same `ExternalInitiatorsEnabled` check inside `AuthenticateExternalInitiator` so that authentication fails when the feature is disabled, e.g. by wiring config into the middleware and rejecting with `auth.ErrorAuthFailed` when disabled, mirroring `ExternalInitiatorsController.Create`.

## Proof of Concept
1. With `JobPipeline.ExternalInitiatorsEnabled = true`, create an external initiator via `POST /v2/external_initiators`, capturing `AccessKey`/`Secret` (`core/web/external_initiators_controller.go:62-69`).
2. Operator sets `JobPipeline.ExternalInitiatorsEnabled = false` and restarts.
3. Attacker/EI sends a request to any endpoint protected by `AuthenticateExternalInitiator` with the captured headers.
4. `core/web/auth/auth.go:119-149` validates credentials successfully (no flag check) and sets `SessionUserKey` to `UserRoleRun`, allowing the request to proceed despite the feature being disabled — verifiable via a Go unit test on `AuthenticateExternalInitiator` with a mock `Authenticator` and config having the flag set to `false`.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```
