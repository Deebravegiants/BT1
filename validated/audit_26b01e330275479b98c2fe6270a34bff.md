### Title
Webhook shop-domain identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify a webhook by HMAC-authenticating only the raw request body, while the `shop` (and `topic`/`webhook_id`) values that the registry dispatches to the app's handler are read straight from unauthenticated HTTP headers. The shop identity that is *acted upon* by the handler is never bound to the bytes that are cryptographically verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signature [2](#0-1) .

`HmacValidator.validate` computes the HMAC solely over `to_signable_string` (i.e. the body) and compares it to the `hmac` header [3](#0-2) . It never incorporates `shop`, `topic`, or `webhook_id` into the signed material.

`Registry.process` validates the HMAC and then dispatches the handler using the *header-derived* `request.shop`, `request.topic`, and `request.webhook_id`, none of which were part of the signed bytes: [4](#0-3) .

This reproduces exactly the bug class in the external report: a value used to authenticate/authorize an action (`shop` used as the tenant/session key for the handler) is read/trusted without being covered by the same integrity check that is supposed to bind it to a legitimate source (the HMAC only covers the body). The binding equality that should hold is:

`shop_authenticated_by_signature == shop_used_by_handler`

but in this code the left side does not exist — no shop value is included in the signed payload at all, so the equality trivially fails: any header value can be substituted after the fact without invalidating the HMAC.

### Impact Explanation
An actor who legitimately installs the app on their own store (a normal, unprivileged self-service Shopify merchant, not requiring any of the app's credentials) receives genuine webhook deliveries for their own shop with a valid HMAC over the body. Because the header `shop-domain` is outside the signed material, that same request can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim tenant's domain while keeping the original valid HMAC/body pair intact. `Registry.process` will pass the attacker-chosen `shop` value straight to the host application's handler as the shop that "owns" this payload [5](#0-4) , causing data attributed to the wrong tenant — a cross-tenant boundary violation driven entirely by this gem's verification logic.

### Likelihood Explanation
Likelihood is high for any application that keys tenant-scoped state (order/install records, webhook-driven session or billing updates, etc.) off `WebhookMetadata#shop` as delivered by this gem, since the only gate (`Utils::HmacValidator.validate`) never examines the header the handler subsequently trusts. The attack requires no possession of the app's `client_secret`, access token, or any privileged account — only the ability to install the app on an attacker-controlled store and replay a captured HTTP request with an edited header.

### Recommendation
Include the security-relevant identity fields (`shop`, `topic`, and ideally `webhook_id`) in the signable string that `HmacValidator` verifies, or otherwise cryptographically bind the header values to the payload before they are handed to `WebhookMetadata`/handlers, mirroring the report's recommendation to ensure any value that is acted upon has first been authenticated as part of the same trust boundary.

### Proof of Concept
1. Install the target app on an attacker-controlled trial shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a genuine delivery with header `x-shopify-shop-domain: attacker.myshopify.com`, a JSON body `B`, and a valid `x-shopify-hmac-sha256` computed by Shopify over `B` using the app's secret.
2. Capture this HTTP request and replay it to the same app endpoint, replacing only the header value with `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and the HMAC header unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` which passes (body `B` is unmodified) [6](#0-5) , then calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...))` with `shop == "victim.myshopify.com"` [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
