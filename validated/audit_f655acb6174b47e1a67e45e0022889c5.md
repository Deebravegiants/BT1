### Title
Manipulable Uniswap V4 spot price (`slot0`/`sqrtPriceX96`) used as a venue oracle propagates into the protocol's default intent pricing rate - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The Simplex solver's Uniswap V4 venue-pricing path derives a token's USD price directly from a pool's spot price (`sqrtPriceX96` read via `getSlot0`), with no TWAP. This spot price is used to build a solver's phantom-order bid, which — through the protocol's `weightedMedian` bid-aggregation and indexer pipeline — becomes the `LiquidityPool.buyRate`/`sellRate` that `IntentGateway.quoteIntent()` uses by default for every subsequent intent on that pair, protocol-wide.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` reads the pool's mid price straight from `sdkPool.token0Price`/`token1Price`, which is derived from the live `sqrtPriceX96` fetched in `UniswapV4LiquidityState.refresh()` via `getSlot0` [1](#0-0) [2](#0-1) . This is a spot-price read of the pool's current tick, not a time-weighted average, and it feeds `getExoticTokenPrice`, the "most-liquid qualifying pool" price used for curveless (venue-priced) trading pairs [3](#0-2) .

This venue price flows into `resolveLegRates`/`referenceRate` in `FXFiller`, which is used both to size a real fill and to price a **phantom probe** bid (`quotePhantomFill`) [4](#0-3) [5](#0-4) . The only defense, `checkPriceGuard`, bounds the quote against a **static** `referencePrice` within `maxDeviationBps`, and is explicitly optional ("omit both to leave the chain unguarded") [6](#0-5) . Documentation for this path states plainly: *"Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote"* and *"`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost"* [7](#0-6) .

Critically, this is not an isolated solver-local risk. A phantom probe's quoted output becomes a bid; `aggregatePhantomBids` picks the price per leg via `weightedMedian`, weighted by each solver's on-chain inventory of the output token — meaning a solver holding over half the leg's weight sets the published price verbatim [8](#0-7) . That median is written to `PhantomOrderPriceSnapshotV2` and passed to `updateLiquidityPools`, which merges it into `LiquidityPool.buyRate`/`sellRate` [9](#0-8) . Since the 2026-08-25 change, `IntentGateway.quoteIntent()` defaults to exactly this depth-weighted aggregate rate for pricing all intents on the pair [10](#0-9) .

### Impact Explanation
An attacker who runs (or controls) a solver with dominant on-chain inventory for a leg's output token can cheaply manipulate a thin/low-liquidity Uniswap V4 pool's spot price (a flash-loan-funded swap, or simply trading against a shallow pool) to shift `sqrtPriceX96` before or during the phantom bid window. The static-reference `checkPriceGuard`, where configured at all, only rejects extreme deviations — an attacker can move the price within the allowed band, or the guard may be unconfigured entirely for a given chain. The skewed venue price is baked into the solver's phantom bid, wins the `weightedMedian` selection by inventory weight, and is published as the pair's `buyRate`/`sellRate`. Every subsequent user's `quoteIntent()` call for that pair is then priced off the manipulated rate, letting the attacker systematically underpay or overcharge counterparties across the protocol — a concrete route to theft of user funds via mispriced intents, not merely a self-inflicted solver loss.

### Likelihood Explanation
Reachable by a single unprivileged actor acting as an intent solver: no governance or admin privilege is required, only participation in phantom-order bidding (open to any registered solver) and control/majority weight of a leg's destination-chain inventory, combined with the ability to move a thin V4 pool's spot price. The `referencePrice`/`maxDeviationBps` guard is optional per the documented configuration, and even when present it only bounds deviation from a static value rather than defending against short-term manipulation, so likelihood is non-trivial wherever a curveless (venue-priced) pair is configured against a low-liquidity pool.

### Recommendation
Replace the direct `sqrtPriceX96`/spot-price read in `computeDirectPoolPriceUsd`/`UniswapV4LiquidityState.refresh` with a TWAP (time-weighted average price) sourced from the pool's oracle observations, and make `checkPriceGuard`'s reference dynamic (e.g., tracked against a recent TWAP or an external oracle) rather than a static operator-set value, and require it to be non-optional for any venue-priced pair before its rate is allowed to feed `aggregatePhantomBids`/the indexer's `LiquidityPool` rates.

### Proof of Concept
1. Configure a curveless (venue-priced) pair backed by a thin Uniswap V4 pool, with no `referencePrice`/`maxDeviationBps` guard configured (or one configured with a wide band) [11](#0-10) .
2. Attacker swaps a large amount through the thin pool to move `sqrtPriceX96`.
3. During this window, attacker's solver (with majority weight of the leg's output-token inventory) submits a phantom bid; `computeDirectPoolPriceUsd` prices it off the manipulated spot price [12](#0-11) .
4. `weightedMedian` selects the attacker's quote verbatim as the leg's `medianPrice` [13](#0-12) .
5. `updateLiquidityPools` merges this into `LiquidityPool.buyRate`/`sellRate`, which `IntentGateway.quoteIntent()` uses by default for all subsequent orders on the pair, letting the attacker profit from mispriced fills against unsuspecting users.

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
