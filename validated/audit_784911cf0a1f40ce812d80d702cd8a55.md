### Title
`update_token`'s `remove_chains` deletes `ContractToAsset`/`Precisions` mappings while pending in-flight transfers to that chain still rely on them, permanently stranding refunds and inbound settlements - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Summary
`pallet-hyper-fungible-token::update_token` lets `CreateOrigin` remove a chain's configuration (`TokenContracts`, `ContractToAsset`, `Precisions`) for an asset with no check for outstanding cross-chain state — no verification that there are no unexpired in-flight ISMP requests to/from that chain for the asset. This mirrors the reported bug class (removing a reward/token entry without accounting for unclaimed/outstanding value), but here the stranded value is user principal, not just yield: a removed contract mapping makes both the timeout-refund path and the receive path permanently fail for any message still in flight when the chain is de-configured.

### Finding Description
`update_token` iterates `update.remove_chains` and unconditionally removes `TokenContracts::<T>::remove(chain, asset_id)`, `ContractToAsset::<T>::remove(chain, old_contract)`, and `Precisions::<T>::remove(asset_id, chain)`: [1](#0-0) 

There is no check that no `send()` request to that chain is still outstanding (i.e., has not yet timed out or been delivered). Once removed, two ISMP module callbacks that depend on these mappings will hard-fail for any such pending request:

- `on_timeout` looks up `ContractToAsset::<T>::get(dest, &to)` to determine which local asset to refund the original sender; if missing it returns `HftError::UnknownContractOnTimeout` and the refund never happens: [2](#0-1) 
It also needs `Precisions::<T>::get(local_asset_id, dest)` to convert amounts, which is likewise deleted: [3](#0-2) 

- `on_accept` (inbound message from the remote contract, e.g. a user sending tokens back from the EVM chain) looks up `ContractToAsset::<T>::get(source, &from)` to authenticate/route the incoming message; if missing it errors with `HftError::UnknownSourceContract` and the tokens the remote contract already locked/burned are never credited on this chain: [4](#0-3) 

Because `send()` locks (native) or burns (non-native) the local asset immediately at dispatch time before the cross-chain message resolves: [5](#0-4) 
any transfer dispatched to a chain shortly before `update_token` removes that chain's mapping will have already escrowed/burned the sender's funds. If the request is delivered normally, `on_accept` runs fine on the remote side (unaffected by this pallet's local storage) and mints tokens there; but if that request instead times out, this chain's `on_timeout` cannot resolve the asset/decimals and the refund is dropped — the user's locked/burned principal is permanently lost. Symmetrically, an EVM-side counterpart that had already burned/locked and dispatched an inbound message toward this chain, but whose delivery lands after `remove_chains` executes, is now unroutable via `on_accept` and the corresponding beneficiary never receives their tokens; the funds are stuck as a message that can never be successfully applied by this pallet.

This is the same underlying flaw as the audit report: administrative removal of a token/asset registration entry has no gate on outstanding value tied to that entry, so already-escrowed/legitimately-owed funds become permanently unreachable through the pallet's normal redemption paths.

### Impact Explanation
This is a concrete freezing-of-funds bug reachable by an ordinary user transaction (`send`) combined with a routine administrative action (`update_token` removing a chain), not a malicious-admin scenario — `update_token` is a normal maintenance operation (e.g., deprecating a chain or re-pointing a contract) that the pallet's own documentation treats as benign ("Add or remove chains from an existing token's configuration"). Any user who dispatched a transfer to/from the removed chain in the window before removal takes effect can have their principal permanently stuck — either an un-refundable timeout or an undeliverable inbound settlement. Given `send()` moves real user funds (native currency or fungible assets) before cross-chain resolution, this meets the bar for permanent freezing of funds.

### Likelihood Explanation
Likelihood is moderate: it requires a race between an in-flight `send()`/inbound message and a legitimate `update_token(remove_chains=[...])` call by `CreateOrigin` (which could be root or a token-management multisig, not necessarily malicious). Given `update_token` is documented as a normal lifecycle operation and ISMP request timeouts/finalization windows can span from seconds to hours depending on chain/consensus, an operator removing chain support without first pausing new sends and waiting out all outstanding request timeouts will trigger this deterministically for any in-flight transfer.

### Recommendation
- Retain `ContractToAsset` and `Precisions` entries for removed chains until all currently-outstanding requests referencing that `(chain, asset)` pair have either been delivered or timed out, e.g. by moving them to a "deprecated" map that `on_accept`/`on_timeout` still consult, or by requiring `remove_chains` to pass only after a configurable quiescence period.
- Alternatively, disallow removal while `send()` continues to reference the same `AssetId`/`StateMachine` pair until an explicit drain/pause step confirms no pending commitments exist for that pair (similar to `EvmHost.updateHostParams`'s pattern of requiring the old fee token balance to be fully swept before allowing the fee token to change: [6](#0-5) ).
- At minimum, gate `send()` against dispatching to a chain that is in the process of being removed, and only physically delete the `ContractToAsset`/`Precisions` rows after the maximum in-flight timeout window for that chain has elapsed.

### Proof of Concept
1. Governance registers asset `X` with a chain mapping for `StateMachine::Evm(C)` via `register_token`.
2. User A calls `send(asset_id=X, destination=Evm(C), amount=100, timeout=T)`; `send()` immediately burns/locks 100 units of `X` from A's balance: [5](#0-4) .
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token(asset_id=X, remove_chains=[Evm(C)])`, which deletes `ContractToAsset::<T>::remove(Evm(C), contract)` and `Precisions::<T>::remove(X, Evm(C))`: [7](#0-6) .
4. The request subsequently times out (network delay, destination congestion, relayer failure, etc.). `pallet-ismp` invokes `on_timeout`, which calls `ContractToAsset::<T>::get(dest, &to)`, finds nothing, and returns `HftError::UnknownContractOnTimeout` before any refund occurs: [2](#0-1) .
5. User A's 100 units of `X` are permanently unrecoverable — burned/locked with no path to refund since `on_timeout` cannot resolve the asset without the deleted mapping, and there is no alternate recovery function in the pallet.
