### Title
Destination-side order cancellation permanently forecloses the only cross-chain recovery route for stuck escrow - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_cancelFromDest` (and the equivalent logic in `evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`) writes `_filled[commitment] = order.user` on the destination chain *before* the corresponding `RefundEscrow` message is ever confirmed delivered to the source chain. If that message is never executed on the source chain, the caller has no way to retry: `cancelOrder`'s own `Filled()` guard blocks re-dispatching from the destination, and the only alternate route — cancelling from the source chain — is unconditionally defeated because `onGetResponse` treats the very non-empty slot the cancellation itself created as proof the order was "filled," and reverts. This is the same bug class as the Frankencoin `Position.deny()` finding: a state-mutating action taken in good faith (there, denying a position; here, initiating a destination-side cancel) commits to a "must succeed" cross-chain step while simultaneously closing every fallback path if that step doesn't complete, permanently freezing user funds.

### Finding Description
`cancelOrder` guards all three routes with a single check: [1](#0-0) 

For the destination route: [2](#0-1) 

`_filled[commitment]` is set to the user's address *synchronously and irreversibly on the destination chain*, then a `RefundEscrow` POST is dispatched with `timeout: 0` (no timeout, i.e. it never expires and never gets its `onPostRequestTimeout`/refund path triggered): [3](#0-2) 

The escrowed input tokens actually live on the *source* chain, in that chain's own `_orders`/gateway storage, and are only released when the source chain's `onAccept` processes the `RefundEscrow` body and calls `_withdraw`: [4](#0-3) 

If that POST is never delivered (dropped by relayers due to insufficient fee, delivery revert from `_authenticate` mismatch after a gateway rotation via `UpdateParams`, host frozen at delivery time, etc.), the user's only theoretical alternative is the source-side cancellation route, `_cancelFromSource`, which dispatches a GET request checking whether the destination's `_filled[commitment]` slot is empty: [5](#0-4) 

But that slot is no longer empty — the destination-side cancel already wrote the user's own address into it. `onGetResponse` interprets any non-empty value as "the order was filled" and reverts with `Filled()`, per its own doc comment: [6](#0-5) 

So the same state that was meant only to block a *future solver fill* also poisons the one cross-chain proof the source-side recovery path relies on to distinguish "unfilled" from "filled/cancelled." There is no third path: `cancelOrder` on the destination itself reverts immediately with `Filled()` for any subsequent call once `_filled[commitment]` is non-zero, so the `RefundEscrow` dispatch can never be repeated either. `fundRequest` can only raise the fee on a request that is merely under-incentivized, not one whose delivery reverts deterministically (e.g. after a legitimate `UpdateParams` gateway-address rotation between order placement and cancellation, or any other change that fails `_authenticate` on the source chain permanently).

### Impact Explanation
Once the destination-side path is taken and the resulting `RefundEscrow` message fails to land on the source chain for any durable reason, the escrowed input tokens are permanently unrecoverable: no owner action, relayer action, or protocol-level retry can release them, since both cancellation routes are now closed. This is a genuine, unbounded freezing of user funds reachable from a single, fully unprivileged transaction (`cancelOrder`) that any order owner (or, after `deadline`, any third party acting on their behalf) is expected to call as part of normal, documented recovery flow.

### Likelihood Explanation
The destination-side cancel route is the SDK's and docs' recommended, most commonly used cancellation path (it's presented as the way to "recover promptly," including before expiry). Any of several ordinary, non-malicious conditions — relayer economics discouraging delivery of a low/zero-fee message, a governance-driven gateway redeployment (`UpdateParams`/`NewDeployment`) between order placement and cancellation, or a host freeze window coinciding with delivery — will trigger the permanently-unrecoverable state. No attacker action is required; it is a foreseeable operational failure mode baked into the protocol's own retry logic.

### Recommendation
Do not treat the destination-side cancellation marker (`_filled[commitment] = order.user`) as equivalent to "order filled" for the purposes of the source-side GET-based recovery check. Either (a) use a distinct sentinel/flag (or the actual solver address vs. a reserved "cancelled" marker) so `onGetResponse` can distinguish "cancelled, refund pending" from "filled by a solver," and allow the source-side route to still complete the refund in the cancelled case; or (b) allow `cancelOrder`'s destination route to be re-invoked (re-dispatch `RefundEscrow`, possibly with a bumped fee) when the prior cancellation's message is confirmed not yet delivered, instead of being gated shut by the same `_filled` flag it sets.

### Proof of Concept
1. User places a cross-chain order on chain A with escrowed inputs, destination chain B.
2. Before the order is filled, the user calls `cancelOrder(order, options)` on chain B (destination route). This sets `_filled[commitment] = user` on B and dispatches a `RefundEscrow` POST (`timeout: 0`) toward chain A.
3. Governance rotates the registered gateway instance for chain B via `UpdateParams`/`NewDeployment` before the message is delivered (or relayers simply never pick up a zero/low fee message).
4. The `RefundEscrow` message is never successfully processed by `onAccept` on chain A; the escrow stays in chain A's storage.
5. User calls `cancelOrder` again on chain B: reverts with `Filled()` (blocked by step 2's marker).
6. User instead calls `cancelOrder` from chain A (source route) after `deadline`, supplying a GET proof of chain B's `_filled[commitment]` slot at a height past the deadline. The proof now returns the non-empty value written in step 2.
7. `onGetResponse` on chain A reverts with `Filled()`, because it cannot tell "cancelled" apart from "filled." The escrow on chain A remains locked with no further recourse.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
