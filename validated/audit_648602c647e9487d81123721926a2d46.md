The reported bug class is Solidity-specific: it relies on `msg.value` semantics and an EVM `multicall` pattern where a contract's ambient ETH balance can be double-counted across batched calls in a single transaction. Raydium AMM is a Solana program, and its unprivileged-reachable instructions (`Initialize2`, `Deposit`, `Withdraw`, `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2`) move exact, explicitly-specified token amounts via SPL Token CPIs in `invokers.rs` rather than relying on an ambient `msg.value`-style balance that could be double-spent through batching [1](#0-0) . There is no `multicall`-equivalent entry point in the program; `Processor::process` dispatches a single `AmmInstruction` per call based on `instruction_data`, and Solana transactions batch instructions at the runtime level with each instruction independently validating and moving only its own declared accounts/amounts [2](#0-1) .

The only lamports-rescue-like functionality, `WithdrawExcessLamports`, is restricted to a hardcoded privileged signer (`config_feature::collect_lamports::id()`), which is explicitly out of scope per the rules excluding privileged-signer paths [3](#0-2) . No unprivileged swapper/LP/pool-creator path in Deposit, Withdraw, or the swap instructions exhibits an analogous double-accounting/stuck-funds-theft pattern reachable from a single transaction.
