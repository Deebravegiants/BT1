### Title
Dormant delegate grants re-arm when a position NFT returns to the grantor, letting a stale delegate drain collateral and borrow - (File: contracts/controller/src/storage/account.rs)

### Summary
Each controller account is identified by a transferable position-NFT token id, and delegates are stored as a `DelegateGrant` stamped with the `granted_by` address. The authorization check only compares `granted_by` to the *current* NFT owner — it never records the ownership epoch or clears the grant on transfer. A grant made by a previous holder therefore stays dormant while the token is held by someone else and silently re-activates the instant the token returns to the original grantor, with no fresh authorization. This is the use-after-free analog of CVE-2022-0975: an authorization object that logically died at an ownership boundary is still reachable and is used after the object's lifetime ended.

### Finding Description
`set_delegates` persists `DelegateGrant { granted_by, delegates }` under `ControllerKey::Delegates(account_id)` (contracts/controller/src/storage/account.rs:185-198). `get_delegates` returns the list whenever `grant.granted_by == owner`, where `owner` is resolved live from `owner_of(token_id)` via `try_account_owner` (contracts/controller/src/storage/account.rs:176-181, 35-38). The position-NFT README confirms no cleanup happens on transfer: "the stale grant stays in storage and re-arms if the token returns to `granted_by`" (contracts/position-nft/README.md:174-179), and `remove_account_entry` only wipes `Delegates` when the account is deleted (contracts/controller/src/storage/account.rs:250-256).

Because token ids are never reused and `account_id == token_id`, a returning NFT resurrects the exact same account — and the exact same dormant grant. The grantee (`delegate`) is an unprivileged address that can call owner-gated verbs such as `borrow` and `withdraw` to arbitrary recipients; the mid-callback ownership test shows stale-owner calls fail with `NOT_AUTHORIZED` only because ownership is read live, not because grants were invalidated (tests/test-harness/tests/strategy/flash_position_callback_ownership_transfer.rs:55-58). The integration harness pins the deny path for a previous owner (`Error(Contract, #44)`) and the accept path for a delegate (`prod_delegate_withdraw`), but never tests grant resurrection after a round-trip transfer (tests/integration/flows/production.sh:281-300, tests/integration/flows/nft.sh:33-47).

### Impact Explanation
Theft of user funds. A delegate who was granted once by owner A — e.g., a keeper or "position manager" contract used long ago, later abandoned or compromised — retains a dormant grant after A transfers/sells the position NFT. If the same token id ever returns to A (buyback, marketplace settlement returning the NFT, a `transfer_from` round-trip, or A simply re-receiving it), the grant re-arms with no `add_delegate` call and no on-chain signal. The delegate can then `withdraw` collateral or `borrow` to itself against A's regained account. The victim performed no authorizing action in the current ownership lifetime; the exploit relies entirely on authorization surviving past its intended lifetime, matching the UAF bug class.

### Likelihood Explanation
Medium. It requires (1) a prior `add_delegate` by the victim — routine, since only delegates can perform third-party management and governance activates position managers for this purpose; (2) the NFT leaving and returning to the victim — plausible through sales, lending of the NFT, or protocol flows that custody the token; and (3) the delegate acting maliciously. No timing race, price move, or privileged action is needed; the delegate's window opens permanently upon the token's return.

### Recommendation
Bind grants to an ownership epoch, not to a reusable address: stamp `DelegateGrant` with a per-account transfer counter (incremented in a controller hook invoked on NFT transfer, or derived from a monotonically increasing field), or delete `ControllerKey::Delegates(account_id)` whenever ownership is observed to differ from `granted_by` at any write path, including first touch by a new owner. Alternatively, record grant creation ledger and require periodic re-affirmation by the current owner.

### Proof of Concept
1. Alice holds account `id` (NFT token `id`) with USDC collateral and calls `add_delegate(id, MALLORY)`.
2. Alice transfers the NFT to Bob (`position_nft.transfer(Alice, Bob, id)`); the grant is dormant — `get_delegates(id, Bob)` returns empty because `granted_by == Alice`.
3. Bob later transfers the same token back to Alice (e.g., she repurchases the position). `granted_by == Alice` matches again; `get_delegates(id, Alice)` returns `[MALLORY]` without any new authorization.
4. Mallory calls `controller.withdraw(caller = MALLORY, account_id = id, withdrawals = [USDC, amount], to = Mallory)` — or `borrow` to an arbitrary recipient — and takes Alice's collateral.

Key code: `get_delegates` lifetime check is purely `grant.granted_by == *owner` (contracts/controller/src/storage/account.rs:176-181); grants are only ever deleted by `set_delegates` with an empty list or by `remove_account_entry` on account deletion (contracts/controller/src/storage/account.rs:187-188, 250-256).
