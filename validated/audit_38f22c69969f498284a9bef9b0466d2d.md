### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `to_signable_string` only returns the raw request body. `Utils::HmacValidator` verifies the HMAC solely against that raw body, so the `shop` header is never bound to the signature that authenticates the request. Any party who possesses one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — which every merchant installing the app naturally receives from Shopify for their own webhook deliveries — can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. The HMAC still validates (it only checked the body), but the app processes the webhook as if it belonged to a different, attacker-chosen shop.

### Finding Description
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, and `#webhook_id` are read straight from headers with no cryptographic binding: [2](#0-1) 
- `HmacValidator.validate` computes/compares the signature only over `verifiable_query.to_signable_string` (i.e., the body), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 
- `Registry.process` validates the HMAC and then dispatches to the app's handler using the unauthenticated `request.shop` value as the tenant identity: [4](#0-3) 
- `WebhookMetadata.shop` is the field every consuming app is expected to trust for tenant attribution: [5](#0-4) 

This is a direct analog of the "overslash" root cause pattern requested: a value that is acted upon (`shop`, used to attribute/act on tenant data) is not covered by the integrity check (`HMAC` over body only), breaking the intended binding `HMAC-authenticated(shop) == shop-used-for-tenant-attribution`.

### Impact Explanation
Because the app's `client_secret` is shared across all shops that install the app, the HMAC only proves "this body was signed with our app secret" — it does not prove which shop the request is attributed to. An attacker who is a legitimate merchant of the app (unprivileged relative to other tenants) can capture a webhook delivery sent to their own shop (any topic with a static/predictable body, e.g. `app/uninstalled` or a `shop/redact` GDPR call, or simply reuse any delivery for a topic whose body content doesn't need to differ), then replay the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint with the `shop-domain` header changed to another shop's domain. Since `Registry.process` only checks the HMAC against the body and blindly trusts the header-derived `shop` for dispatching to `WebhookMetadata`, the app is misled into processing the payload as belonging to a different tenant — a cross-tenant data/identity confusion (Critical: cross-tenant access).

### Likelihood Explanation
Any real merchant using an app built on this gem legitimately receives valid, replayable `(body, hmac)` webhook pairs from Shopify for their own store. Forging the `shop-domain` header requires no cryptographic secret and no privileged access — only the ability to send an HTTP request to the app's public webhook endpoint, which is by design internet-reachable. The likelihood is high wherever the consuming app trusts `WebhookMetadata#shop` for tenant lookups/actions (a documented and expected usage pattern of this API).

### Recommendation
Include the shop domain (and topic/webhook id if used for authorization decisions) inside the HMAC-signed material, or otherwise cryptographically bind them (e.g., validate `shop` against Shopify's registered webhook subscription for that specific `topic`+`shop` pair, or require an out-of-band verification such as looking up an existing, valid session for that shop before trusting the header). At minimum, document and encourage consuming apps to independently verify that the shop asserted in the webhook matches a shop with an active installation before acting on `WebhookMetadata#shop`, and make `HmacValidator`/`Request#to_signable_string` include the shop domain in the signable string so the signature actually attests to the sender's identity, not just the body content.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" installs the target app; Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
2. The merchant (or anyone who can observe/replay this HTTP request, e.g. via their own server logs, a proxy, or a MITM-free network capture of their own traffic) resends the exact same request to the app's public webhook endpoint, but changes the `x-shopify-shop-domain` header to `shop-b.myshopify.com` (a victim shop), leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and it still matches, so validation passes.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-controlled `shop` header value and invokes the app's registered handler with `shop: "shop-b.myshopify.com"`, even though the payload was never signed for that shop — resulting in cross-tenant processing.
