### Title
Unauthenticated Denial of Service via Unbounded Error Logging in `pallet-state-coprocessor::validate_unsigned` - (File: modules/pallets/state-coprocessor/src/lib.rs)

### Summary
`pallet-state-coprocessor`'s `ValidateUnsigned::validate_unsigned` re-executes `handle_get_requests` on every gossiped `handle_unsigned` extrinsic before it even reaches a block, and on failure logs the entire error value with `{:?}` formatting. Because the error variants carry the full `Meta`/`Request` data derived directly from attacker-supplied `GetRequestsWithProof.requests`, an attacker can submit arbitrarily large, invalid Get-request batches to trigger large, unbounded log writes on every full node that validates the unsigned transaction gossip — with no signature, fee, or proof-validity requirement gating the call.

### Finding Description
`validate_unsigned` runs `Self::handle_get_requests(message.clone())` for every submitted unsigned extrinsic and logs the raw error on failure: [1](#0-0) 

`handle_get_requests` fails fast (before any proof verification, before dedup against chain state completes meaningfully) on cheap-to-trigger conditions such as timeout or metadata mismatch, and constructs the error directly from the caller-supplied request: [2](#0-1) 

The `Meta` embedded in `Error::RequestTimeout`/`Error::RequestProofMetadataNotValid` is built via `full.clone().into()`, where `full` is `Request::Get(req.clone())` — i.e., it carries the full attacker-controlled `GetRequest`, including its `keys: Vec<Vec<u8>>` and any associated context bytes, none of which are size-bounded in `GetRequestsWithProof`: [3](#0-2) 

Because `handle_unsigned`'s `ValidateUnsigned::validate_unsigned` implementation runs as part of transaction-pool gossip validation on every node (not just the block author, and prior to any block inclusion or fee deduction), an attacker only needs to broadcast a single malformed `GetRequestsWithProof` — with a `requests` vector padded with many large `keys` entries designed to trip an early error path — to force every node in the network that receives the gossiped extrinsic to `Debug`-format and write that entire, attacker-sized error to its log via `log::error!("{:?}", err)`. This is directly analogous to the JupyterHub CVE-2026-54338 pattern: unauthenticated, invalid input to an unauthenticated entry point (form login there / unsigned extrinsic validation here) results in unbounded server-side logging output, causing resource exhaustion (disk I/O / log volume) network-wide rather than on a single victim.

Unlike `pallet-ismp`'s own `HandlingError` (used elsewhere in the codebase), which is explicitly truncated to a bounded size before being stored/logged: [4](#0-3) 
the `ismp::Error` type logged in `pallet-state-coprocessor::validate_unsigned` and `handle_unsigned` has no such bound and is logged verbatim via `{:?}`.

### Impact Explanation
This is a network-wide, unauthenticated availability impact (CWE-400): every full node that validates the gossiped unsigned extrinsic performs the expensive `Debug` formatting and log write of an attacker-controlled, unbounded payload, at essentially zero cost to the attacker (no signature, no fee, and the transaction can be crafted to fail before any proof cryptography is even attempted). Repeated submission of such malformed extrinsics can degrade node performance and fill disk with log output across the relayer/validator set, matching the CVSS breakdown of the referenced advisory (AV:N/AC:L/PR:N/UI:N/A:L) — availability impacted, no confidentiality/integrity loss.

### Likelihood Explanation
High likelihood: `handle_unsigned` extrinsics are explicitly designed to be submittable by unauthenticated/unsigned callers (`ensure_none(origin)?`), and `validate_unsigned` is executed by every peer during normal transaction-pool gossip validation, not gated behind fees or reputation. Triggering the cheap failure paths (`RequestTimeout`, `RequestProofMetadataNotValid`) requires no valid proof — only a `GetRequestsWithProof` whose `source`/`response` height/state_id fields don't match, which is trivial to construct with a large `keys` payload.

### Recommendation
Bound and/or redact the data that ends up in `ismp::Error` variants (`Meta`, `Custom(String)`, etc.) before logging them from unauthenticated/unsigned validation paths, mirroring the truncation already applied in `pallet-ismp`'s `HandlingError` (`modules/pallets/ismp/src/errors.rs`). Concretely: truncate/limit the size of any request-derived data included in log output inside `validate_unsigned`/`handle_unsigned` in `modules/pallets/state-coprocessor/src/lib.rs`, and/or enforce a strict bound on `GetRequestsWithProof.requests` (count and per-request `keys` size) before `handle_get_requests` does any per-request processing, so the worst-case log payload is capped regardless of attacker input.

### Proof of Concept
1. Craft a `GetRequestsWithProof` with `requests` containing one or more `GetRequest`s whose `keys` field is populated with many large byte vectors (bounded only by the runtime's extrinsic/block size limit), and whose `source`/`response` proof heights are set so that `source_chain()`/`dest_chain()` checks fail immediately (no valid proof needed).
2. Submit this as an unsigned extrinsic to `StateCoprocessor::handle_unsigned` (as done by relayers via `submit_get_response`): [5](#0-4) 
3. Every full node receiving the gossiped extrinsic runs `validate_unsigned`, which calls `handle_get_requests`, hits `Error::RequestProofMetadataNotValid { meta: full.clone().into() }` carrying the full oversized `GetRequest`, and logs it verbatim: [6](#0-5) 
4. Repeating this with new nonces/variations lets an attacker force large, repeated log writes across the network with no signature or fee cost.
