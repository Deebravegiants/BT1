### Title
Permanent market freeze via i128 overflow in interest accrual before the borrow-index cap engages - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
The borrow-index cap `MAX_BORROW_INDEX_RAY` is applied to `new_index` in `update_borrow_index`, but the RAY-denominated debt/supply value computations that use the index overflow `i128` first. Once a market's total debt value crosses the `i128` ceiling, every accrual panics with `MathOverflow` inside the value multiplication, the cap never engages, and the market is permanently bricked: no repay, withdraw, liquidation, or bad-debt cleanup can ever execute because all of them run `global_sync` first. The crash-class analog of CVE-2025-56225 (null-deref on unexpected state) maps here to an unrecoverable panic on a reachable market state.

### Finding Description
`update_borrow_index` multiplies and only then clamps:
- `let new_index = old_index.mul(env, interest_factor);` then `if new_index.raw() > MAX_BORROW_INDEX_RAY { return Ray::from(MAX_BORROW_INDEX_RAY) }` [1](#0-0) 

The cap protects the index scalar, not the *values* derived from it. `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)`, and `update_supply_index` computes `supplied.mul(env, old_index)` — each is a checked RAY multiply that panics when `scaled_amount * index` exceeds `i128::MAX` [2](#0-1) . For a large market (e.g., an 18-decimal asset with ~10^28-unit principal at ~98% utilization on a steep interest-rate curve), the debt value `borrowed * borrow_index` crosses `i128::MAX` while `borrow_index` is still far below `MAX_BORROW_INDEX_RAY`, so the defensive cap is unreachable.

`interest::global_sync` runs this arithmetic on every market-touching call before any state write, via `accrue_chunk`/`accrue_step` [3](#0-2) . A panic aborts the whole transaction, so the overflow is self-perpetuating: `supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `flash_loan`, `create_strategy`, `recapitalize`, and `claim_revenue` all funnel through `ops::synced_market` → `global_sync` for that `(hub_id, asset)` book and all revert identically [4](#0-3) .

The repository's own test proves permanence: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` asserts the accrual panics with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and that subsequent `withdraw` and `repay` calls panic the same way — "no repay, no withdraw, no liquidation" [5](#0-4) .

### Impact Explanation
Permanent freezing of all funds in the affected hub asset market and protocol insolvency on the debt side. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `clean_bad_debt`/`recapitalize` cannot restore backing — every path accrues first and hits the same panic. Because `global_sync` panics before `commit`, no recovery transaction exists; even owner calls (`seize_positions`, `update_params` via `upgrade_liquidity_pool_params`, `claim_revenue`) are bricked for that market. This is strictly worse than the CVE's crash-DoS: on-chain the crashed state is persistent, so the denial is forever, matching the accepted "permanent freezing of funds" impact.

### Likelihood Explanation
The trigger is permissionless: any address may call `controller::update_indexes(caller, assets)` [6](#0-5)  — it requires only caller auth, not privilege. Reaching the cliff requires a whale-scale market (principal on the order of `10^28` units for an 18-decimal asset) sustained at ~98% utilization for multiple years on a steep rate curve, so it is not a fast attack; however, an attacker can deliberately construct it by supplying a large position and borrowing most of it, then repeatedly invoking `update_indexes` as time passes. The borrow-side ceiling is also reachable faster on markets where `borrowed` (scaled shares) is already large in RAY terms. Given the extreme capital/time requirement versus a guaranteed permanent freeze once reached, this is Medium likelihood / High impact → High severity.

### Recommendation
Cap the index *before* deriving values, and make the value computation saturating rather than panicking:
- In `update_borrow_index`, compute the candidate index and, before using it in `calculate_supplier_rewards`/`update_supply_index`, clamp it so that `borrowed * new_index <= i128::MAX` — i.e., bound `new_index <= min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed.raw())`.
- Alternatively, use `mul_div_floor_saturating` (already used in `protocol_fee_shares`) for `supplied.mul`/`borrowed.mul` in the accrual path so a saturated value commits a capped accrual instead of panicking, keeping exits functional.
- Add a regression test asserting `withdraw`/`repay` succeed after the value ceiling is crossed.

### Proof of Concept
Reproduced by the existing harness test — set up a market with an 18-decimal asset and the XLM curve, supply `BILLION * 10^18` units, borrow 98%, then advance time year-by-year calling the permissionless `update_indexes`; within ~40 simulated years the accrual panics `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw_raw`/`try_repay` calls panic identically, demonstrating the permanent freeze [5](#0-4) .

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
