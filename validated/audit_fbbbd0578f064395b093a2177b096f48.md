### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to drain any ETH/ERC20 balance left on the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, permissionless, shared contract that `IntentGatewayV2` (predispatch/postdispatch swaps), `HyperFungibleToken`, and `WrappedHyperFungibleToken` all route funds and arbitrary calldata through. Its `dispatch()` function has **no access control whatsoever** — any EOA can call it directly with an arbitrary `Call[]` array. Any ETH or ERC20 tokens that end up sitting on the `CallDispatcher` — whether from un-swept "reward" tokens received during arbitrary predispatch/postdispatch calls, dust from partial or interrupted flows, or accidental direct transfers — can be instantly stolen by any third party who simply calls `dispatch()` with a call that transfers the balance to themselves. This is a direct analog of the reported `SwapExecutor` issue: an unprivileged, arbitrary-call executor that anyone can invoke to sweep out residual value.

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no modifier and no caller restriction: [1](#0-0) 

It also has an unrestricted `receive()` for native ETH: [2](#0-1) 

This single dispatcher address is reused across the protocol's cross-chain calldata-execution features. `IntentGatewayV2`/`IntentsBase` funds it and executes arbitrary user- or solver-supplied calls through it as part of predispatch (swap-then-escrow) and postdispatch (fill-then-act) flows: [3](#0-2) 

The same dispatcher receives freshly minted/unlocked tokens for `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution flows, per the documented pattern of minting/unlocking `to: CALL_DISPATCHER` so that subsequent calls can spend the funds: [4](#0-3) 

The protocol's own sweep logic only accounts for tokens it *expects* to find on the dispatcher (the order's declared `inputs`/`output.assets`), not for arbitrary tokens the executed calls might additionally receive (e.g. router referral rewards, unexpected refunds, or leftover approvals converted into balance by an external actor before the sweep executes): [5](#0-4) 

Because `dispatch()` itself is completely public, this "trusted-until-swept" design is broken: at any point between when value lands on `CallDispatcher` (mint/unlock, direct transfer, dust from an executed call, or a token not enumerated in the sweep loop) and when the protocol's own sweep call executes, **any address can call `CallDispatcher.dispatch()` directly** with a `Call{to: token, data: transfer(attacker, balance)}` (or, for native ETH, `Call{to: attacker, value: address(this).balance, data: ""}`) and steal the funds first. This mirrors exactly the three root causes identified in the original report: (1) protocol-level accounting gaps for non-enumerated reward tokens, (2) arbitrary calls that can cause the dispatcher to receive additional/unexpected tokens, and (3) funds parked on the shared executor between transactions being trivially stealable because the executor imposes no caller restriction.

### Impact Explanation
Any value that transiently or permanently resides on `CallDispatcher` — user escrow funds mid-flight in `IntentGatewayV2` predispatch/postdispatch execution, bridged tokens minted to it by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata flows, or accidental/dust transfers — is a direct, permissionless theft target. This is concrete theft of user/protocol funds, not merely dust — for calldata orders, the dispatcher legitimately holds escrowed input/output tokens and native ETH during a fill, and any transient balance recognized late by the protocol's sweep logic (or simply not on the enumerated asset list) is fully exposed to any attacker able to front-run the sweep transaction or claim tokens the sweep logic doesn't account for.

### Likelihood Explanation
High. `dispatch()` requires no privilege, no proof, and no relationship to any order — it is callable by any address in a single transaction. The dispatcher is intentionally designed to receive tokens and native ETH as part of normal, expected protocol flows (predispatch/postdispatch swaps, HFT/WHFT calldata execution), so residual balances are a routine, not exceptional, occurrence. An attacker merely needs to monitor the mempool/chain for any balance appearing on the known `CallDispatcher` address and front-run or immediately follow with their own `dispatch()` call.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the authorized caller for a given call (e.g., only the `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken`/`WrappedHyperFungibleToken` instance that funded it for the current call), for example via a one-time authorization pattern (transient-storage flag set immediately before dispatch and cleared after, checked in `dispatch()`), or by deploying a fresh, single-use dispatcher/proxy per call rather than reusing one long-lived shared contract. Additionally, ensure sweep logic accounts for *all* token balances actually held by the dispatcher after execution (not just the enumerated order input/output assets) so unexpected reward/dust tokens cannot accumulate unswept.

### Proof of Concept
1. Any transaction routes tokens/ETH to `CallDispatcher` (e.g., a solver's postdispatch fill in `IntentGatewayV2.fillOrder()` sends output tokens to the dispatcher before `_execute()` runs the calldata and sweeps residual balances back, per `IntentsBase._execute`, `evm/src/apps/intentsv2/IntentsBase.sol:498-533`).
2. Before (or in place of) the protocol's own sweep call, an attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls = [Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(address(dispatcher)))})]`.
3. Since `dispatch()` has no caller check (`evm/src/utils/CallDispatcher.sol:44-62`), the call succeeds and transfers the entire token balance held by the dispatcher to the attacker, regardless of who the legitimate beneficiary was.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
