## Analysis Result

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the nominal input amount instead of the actual tokens received, allowing fee-on-transfer/non-standard ERC20 tokens to over-credit escrow and drain gateway reserves - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` (the non-predispatch branch) pulls ERC20 input tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount`, a value derived from the *requested* `order.inputs[i].amount`, not from what the contract actually received.

### Finding Description
In `placeOrder`'s no-predispatch escrow loop: [1](#0-0) 

the contract never measures its own balance before/after the transfer. This is the same bug class as the reported ZERO_VOLUME_SENT issue: the code trusts the *declared* transfer amount to derive downstream accounting (`_volume` / `reducedInputs[i].amount`) instead of the *actually received* amount (`volumeReceived` / real balance delta).

For any ERC20 token that does not transfer the full requested amount to the recipient — fee-on-transfer tokens, rebasing tokens, or tokens with deflationary/burn-on-transfer mechanics — `safeTransferFrom` will succeed while delivering less than `order.inputs[i].amount` to the gateway. The escrow map is nonetheless incremented by the full (fee-adjusted) `reducedInputs[i].amount`, which is strictly derived from the nominal `order.inputs[i].amount`, not the real balance received.

This is a direct regression relative to the canonical EVM `IntentGatewayV2.placeOrder`, which explicitly guards against this by snapshotting balances and recomputing `order.inputs[i].amount` from the actual balance delta: [2](#0-1) 
with the documented rationale: [3](#0-2) 

The Tron variant's predispatch branch does perform a dust/balance check (comparing `balance` to `requiredAmount` for the dispatcher-held tokens): [4](#0-3) 
but the far more commonly used direct-transfer branch (no predispatch) has no such check at all.

### Impact Explanation
`_orders[commitment][token]` is the authoritative escrow accounting used later for redemption/withdrawal (`RedeemEscrow`) and cancellation/refund flows. If the escrow ledger is credited for more tokens than the gateway actually holds, the contract becomes insolvent for that token: legitimate order fillers or the order owner redeeming/cancelling other orders can drain real token balances belonging to other users' escrows, since the ledger no longer reflects the real reserve. This is a concrete freezing/loss-of-funds vector reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer (or similarly non-standard) ERC20 as an input token — no privileged role is required.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point that anyone can call with an arbitrary ERC20 `order.inputs[i].token`. Fee-on-transfer and other non-standard ERC20 tokens are common on-chain, and the test suite for the main EVM gateway even has dedicated `FeeOnTransferToken` regression tests confirming this exact scenario is expected to be handled: [5](#0-4) 
proving the protocol explicitly anticipates and handles this token class elsewhere, but the Tron implementation lacks the corresponding fix.

### Recommendation
Mirror the main EVM gateway's fix in the Tron `IntentGatewayV2.placeOrder`: snapshot the token balance before `safeTransferFrom`, compute the actual received amount from the post-transfer balance delta, and derive `reducedInputs[i].amount` (and the commitment) from that actual received amount rather than the caller-supplied `order.inputs[i].amount`, e.g.:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
uint256 received = IERC20(token).balanceOf(address(this)) - balBefore;
// use `received` (not the nominal amount) for protocol fee reduction and escrow crediting
```

### Proof of Concept
1. User calls `placeOrder` with an input token that is a fee-on-transfer ERC20 (e.g., 1% fee), requesting `order.inputs[i].amount = 1000`.
2. `safeTransferFrom` moves only 990 tokens into the gateway; the call succeeds because `safeTransferFrom` only checks the transfer succeeded, not the amount received.
3. `_orders[commitment][token] += reducedInputs[i].amount` credits escrow with `1000` (or `1000` minus protocol fee), even though the gateway only holds `990`.
4. When this or another order's escrow for the same token is later redeemed/withdrawn via `RedeemEscrow`/refund flows, the ledger claims more tokens exist than the contract actually holds, causing later legitimate redemptions to fail or to drain tokens belonging to other users' escrows — a fund-freezing/loss condition triggered purely by an unprivileged `placeOrder` call.
