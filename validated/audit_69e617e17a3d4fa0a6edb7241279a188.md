### Title
Pharos consensus updates permanently blocked once active validator count exceeds `MAX_VALIDATORS`, freezing the state machine and all its in-flight messages - ([File: modules/consensus/pharos/verifier/src/state_proof.rs])

### Summary
The Pharos light client's validator-set decoding enforces a hard `count > MAX_VALIDATORS` revert on every epoch-boundary consensus update. Since the validator count is read directly from the Pharos staking contract's on-chain state (`activePoolSets` length) and can only grow as validators join, once it exceeds the compiled-in `MAX_VALIDATORS` ceiling, every subsequent Pharos consensus proof is permanently rejected with `TooManyValidators`. This is structurally the same bug class as the reported `reconcileSignerCount()` issue: a count-vs-max check baked into the mandatory verification path (`checkTransaction()` there, consensus verification here) that becomes permanently unsatisfiable once an externally-controlled counter grows past the limit, with no way to shrink or bypass it from within the protocol.

### Finding Description
`verify_pharos_block` (`modules/consensus/pharos/verifier/src/lib.rs:97-113`) requires a `validator_set_proof` whenever the observed epoch advances, and passes it to `state_proof::verify_validator_set_proof`, which calls both `compute_all_storage_keys` and `decode_validator_set_from_storage`. [1](#0-0) 

Both of those functions independently derive the validator count from the on-chain `activePoolSets` array length and unconditionally revert if it exceeds `MAX_VALIDATORS`: [2](#0-1) [3](#0-2) 

This validator count is not a Hyperbridge-controlled parameter — it is whatever the Pharos staking contract reports at the epoch boundary, and it can only increase as new validators register on that external chain. There is no governance call, admin extrinsic, or on-chain mechanism in `modules/ismp/clients/pharos/src/lib.rs` (the `PharosClient::verify_consensus` entry point) or in the ISMP pallet (`modules/pallets/ismp/src/lib.rs`) to raise `MAX_VALIDATORS`, exempt an epoch, or otherwise recover — it is a compile-time constant requiring a runtime upgrade to change. [4](#0-3) 

Once the Pharos validator set naturally grows past `MAX_VALIDATORS`, `verify_pharos_block` will reject every future epoch-boundary proof (since `Ordering::Greater` always requires and re-derives the new validator set), permanently freezing the trusted state at the last successfully verified epoch. `HandlerV2.handleConsensus` and the corresponding pallet `handle_unsigned` path both depend on this verifier succeeding to advance state; when it cannot, no new state machine commitments are ever stored for the Pharos state machine. [5](#0-4) 

### Impact Explanation
Because state commitments for the Pharos chain can no longer be produced, `HandlerV2.handlePostRequests`/`handleGetResponses` (which require `host.stateMachineCommitment(...)` to be non-zero) can never verify new proofs for messages routed to or from Pharos: [6](#0-5) 

This permanently prevents delivery of any request, response, or timeout message crossing that route — freezing funds locked in escrow for intents, bandwidth purchases, or any cross-chain call awaiting delivery through the Pharos consensus client, and cutting the route off from all Hyperbridge traffic. This matches the report's "Availability is important... unable to execute any transactions, all assets locked" impact, scoped to the Pharos state machine route rather than a single Safe.

### Likelihood Explanation
This requires no attacker action — it is triggered purely by organic growth of the Pharos validator set past a fixed, low-visibility constant embedded in the verifier crate. Any chain whose validator/staking pool count naturally exceeds `MAX_VALIDATORS` (a realistic outcome for a growing PoS network) will trip this permanently. The check runs unconditionally on every epoch rotation with no per-chain override, admin escape hatch, or graceful degradation, making this a systemic operational risk rather than a rare edge case, once the network's validator count passes the ceiling.

### Recommendation
- Make `MAX_VALIDATORS` a per-consensus-state, governance-adjustable parameter (analogous to `StateMachineCommitmentCap`'s admin-settable override) rather than a hardcoded constant, so it can be raised via `AdminOrigin` before or after being exceeded.
- Alternatively, redesign the check to gracefully truncate/aggregate low-stake validators (similar to how BEEFY/BSC verifiers cap by supermajority stake, not headcount) so an oversized set does not brick verification entirely.
- Add integration/regression tests exercising a validator count at, and just above, `MAX_VALIDATORS` at an epoch boundary to confirm the failure mode and any recovery path before deployment.

### Proof of Concept
1. Pharos network's staking contract `activePoolSets` count crosses `MAX_VALIDATORS` at an epoch boundary block `B`.
2. A relayer submits `handleConsensus`/`update_consensus_state` proof for block `B`; `verify_pharos_block` reaches the `Ordering::Greater` branch and calls `verify_validator_set_proof` → `decode_validator_set_from_storage`. [7](#0-6) 
3. `count > MAX_VALIDATORS` is true, so `Error::TooManyValidators` is returned, and the consensus update fails.
4. Every later epoch retains or exceeds the same/larger validator count (validators do not shrink below the threshold in normal operation), so all subsequent proofs fail identically — the Pharos consensus client is stuck at height `B-1` forever, and no request/response bound for/from Pharos can ever be delivered through `HandlerV2`.

fn decode_validator_set_from_storage<H: Keccak256>(
	values: &[Vec<u8>],
	epoch: u64,
) -> Result<ValidatorSet, Error> {
	// We need 2 values at minimum: totalStake, activePoolSets length
	if values.len() < 2 {
		return Err(Error::InsufficientStorageValues { expected: 2, got: values.len() });
	}

	// Parse global state
	// Index 0: totalStake
	let on_chain_total_stake = decode_u256_from_storage(&values[0])?;

	// Index 1: activePoolSets array length
	let validator_count = decode_u256_from_storage(&values[1])?;

	let count = validator_count.low_u64() as usize;

	if count > MAX_VALIDATORS {
		return Err(Error::TooManyValidators { count, max: MAX_VALIDATORS });
	}
