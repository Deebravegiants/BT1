### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body alone and then dispatches the handler using this unauthenticated `shop` value, so the field that determines which tenant a webhook is attributed to is never bound to the signature that proves the payload is genuine.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC keyed by the app's single `api_secret_key` over whatever `to_signable_string` returns: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`, while `shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being included in the signed string: [2](#0-1) 

`Registry.process` uses exactly this unauthenticated `request.shop` to build the `WebhookMetadata` passed to the app's handler, after validating only the body-derived HMAC: [3](#0-2) 

The identity binding this breaks, stated as an equality that the gem fails to enforce:

`shop authenticated by HMAC == shop attributed to the webhook payload by Registry.process`

Because `api_secret_key` is a single app-level secret shared across every shop that has installed the app (not a per-shop secret), any merchant that installs the app receives genuine webhooks with a valid `(body, hmac)` pair for their own shop. That same `(body, hmac)` pair remains valid HMAC-wise for *any* `shop-domain` header value, since the header is never part of the signed content. An attacker who is merely an unprivileged installer of the app (or who otherwise observes one legitimate webhook delivery) can replay the same body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and the handler is invoked believing the event originates from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler acts on data tagged with an attacker-chosen `shop`, while the cryptographic proof only certifies "some install of this app produced this body," not "this specific shop produced this body." Depending on how a consuming application uses `WebhookMetadata#shop` (e.g., to look up the corresponding session/access token or to update per-shop state), this allows an attacker to inject forged events attributed to a shop they do not control — a cross-tenant access impact per the Critical criteria.

### Likelihood Explanation
Any user who can install the target app on their own store (an "unprivileged internet user" with respect to other merchants) automatically obtains a valid `(body, hmac)` pair via a legitimate webhook delivery to their own registered endpoint, since delivery bodies for many topics are attacker-influenced or predictable (e.g., `orders/create` bodies containing attacker-controlled order data on their own shop). No access to `api_secret_key`, tokens, or other shops' credentials is required — only the ability to replay an HTTP request with a modified header, which is standard behavior for this gem's documented API since header parsing and dispatch never revalidate `shop` against the signed payload.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before it is used for dispatch in `Registry.process`. At minimum, document and enforce that consuming applications must independently verify `WebhookMetadata#shop` against a known/registered shop list rather than trusting the header value implicitly.

### Proof of Concept
1. App developer installs their own test shop `attacker.myshopify.com` and registers an HTTP webhook handler for e.g. `orders/create`.
2. Shopify delivers a legitimate webhook to the app: headers include `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, and some JSON body.
3. Attacker captures this `raw_body` and its `hmac` value.
4. Attacker sends a new HTTP request to the app's webhook endpoint with the same `raw_body`/`hmac`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the shared `api_secret_key` — validation succeeds: [4](#0-3) 
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)`, causing the app to process attacker-controlled data as if it came from `victim.myshopify.com`.
