## Title
Webhook `shop` (and `topic`) header values are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the HMAC signature (`ShopifyAPI::Utils::HmacValidator.validate`) verifies solely the JSON body bytes. The `shop-domain`, `topic`, `api-version` and `webhook-id` values are read straight from HTTP headers and are never part of the signed content, yet the `shop` value is trusted downstream to identify which merchant/tenant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives `hmac`, `to_signable_string`, `shop`, and `topic` from independent sources: `hmac`/`to_signable_string` come from the raw body while `shop` comes from `shopify_header("shop-domain")` [1](#0-0) . `Registry.process` validates only that the HMAC matches the raw body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` to dispatch to the registered handler and build `WebhookMetadata` [2](#0-1) . `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Request` is defined as `@raw_body` only [3](#0-2)  and [4](#0-3) .

This breaks the intended identity binding: `shop header claimed == shop the HMAC actually authenticates`. Since the signature only covers `raw_body`, any request carrying a body/HMAC pair that is valid for shop A can be replayed with the `x-shopify-shop-domain` header changed to shop B (or any other tenant string) and the HMAC check in `Registry.process` still passes, because the check never looks at the header at all.

### Impact Explanation
An app receiving webhooks for multiple merchants (a common multi-tenant embedded-app pattern) authenticates *only* the body via HMAC and then keys tenant-scoped logic (`WebhookMetadata#shop`) off an unauthenticated header. A merchant/tenant who is a legitimate recipient of real webhooks for their own shop (and therefore possesses valid `(raw_body, hmac)` pairs signed with the app's shared `client_secret`) can re-POST that same body/HMAC combination to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value. The app's handler will process it as authentic data for a different, victim tenant — this is a cross-tenant confusion vector inside the gem's own header/HMAC verification design.

### Likelihood Explanation
Reachable by any entity able to send an HTTP webhook body to the app's inbound webhook endpoint with a `shop-domain` header of their choosing; no `api_secret_key` or access token is required, only a previously-observed valid `(raw_body, hmac)` pair (which the attacker's own shop naturally receives for events on their own store). This is not exotic: apps are expected to build multi-tenant webhook consumers on top of `Registry.process`/`Request`, and the class contract gives no signal that `shop`/`topic` are unauthenticated.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind the header claims to the verified body (e.g., re-derive/verify shop identity from a signed claim rather than a bare header) before dispatching to handlers in `Registry.process`.

### Proof of Concept
```ruby
# Attacker legitimately owns shop-a.myshopify.com and receives a real webhook:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac_for_shop_a = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker replays the exact same body+hmac but swaps the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac_for_shop_a),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks `raw_body`,
# and the handler receives WebhookMetadata with shop == "victim-shop.myshopify.com".
