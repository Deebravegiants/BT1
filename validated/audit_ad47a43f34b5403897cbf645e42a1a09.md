## Analysis: TombStone Reclaim Bypass in `object.move`

The external report's core custody invariant is: **an authorization artifact (a signature) must be invalidated once consumed/superseded, otherwise a stale artifact can be replayed to move value to an unintended holder.** Searching Aptos-native custody flows for the same class of bug — a "mark as used/invalidated" step that is applied on one code path but omitted on a sibling path — turns up a real analog in `aptos_framework::object`'s soft-burn (`TombStone`) mechanism.

### Title
Stale `TombStone.original_owner` Enables Object Theft After Ownership Transfer - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::burn` attaches a `TombStone { original_owner }` marker to an object without changing its owner [1](#0-0) . If the object is later transferred to a new legitimate owner via the ordinary transfer path (`transfer`, `transfer_call`, `transfer_to_object` → `transfer_raw` → `transfer_raw_inner`), the stale `TombStone` is **not** cleared, because only `transfer_with_ref` (the `LinearTransferRef` path) clears it [2](#0-1) . The plain `transfer_raw_inner` helper used by all normal, ungated transfers only updates `owner` and emits an event — it never touches `TombStone` [3](#0-2) .

### Finding Description
`unburn` grants reclaim rights based on two disjoint conditions [4](#0-3) :
1. If the caller currently owns the object, they can simply clear the `TombStone`.
2. If the object's current owner is `BURN_ADDRESS`, the address stored in `TombStone.original_owner` may reclaim it.

The second branch assumes `TombStone.original_owner` always reflects the *most recent* legitimate owner immediately before the object reached `BURN_ADDRESS`. That assumption is false once an object changes hands through a normal transfer while a stale `TombStone` is still attached:

1. Owner `A` calls `burn(A, obj)` → `TombStone{ original_owner: A }` is attached; `A` remains the owner (soft burn only hides the object from indexers).
2. `A` sells/transfers `obj` to `B` via a normal `object::transfer`/`transfer_call` (fully legal — `allow_ungated_transfer` is untouched by `burn`, and `transfer_raw_inner` performs no `TombStone` check or cleanup).
3. `B`, the new legitimate owner, later sends `obj` to the well-known `BURN_ADDRESS` using an ordinary transfer (a common, unrestricted pattern; `BURN_ADDRESS` is just a regular address as far as `transfer_raw_inner` is concerned) [5](#0-4) .
4. `A` calls `unburn(A, obj)`. Since `object_core.owner == BURN_ADDRESS`, and the stale `TombStone.original_owner == A`, the assertion passes and `transfer_raw_inner(object_addr, A)` sends the object back to `A` — even though `A` had no ownership claim at the time `B` burned it.

The developers were clearly aware of this exact hazard: the comment on `transfer_with_ref` explicitly says *"Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later"* [6](#0-5)  — but this cleanup was implemented only for the `LinearTransferRef` path, not for the far more common plain `transfer`/`transfer_call`/`transfer_to_object` paths. This is functionally identical to the reported bug class: an authorization artifact (here, the `TombStone`) that should be invalidated once ownership moves on is instead left valid and can be "replayed" by an unrelated, previous party to redirect custody of the asset.

### Impact Explanation
This allows a previous owner to steal an object-held asset back from `BURN_ADDRESS` (or from whichever legitimate owner burns it) after having sold/transferred it away, purely because a soft-burn tombstone from an earlier point in the object's history was never cleared. This directly violates the custody invariant that "object creation, transfer, burn, extensibility, and ownership refs must preserve the intended controller," and results in supply/custody accounting corruption — value moves to the wrong (stale, unauthorized) holder. This is applicable to any `Object<T>` including NFTs, resource-account-backed objects, or any application relying on `object::burn`/`unburn` semantics, and can affect fungible-asset-holding objects and other high-value object types on mainnet.

### Likelihood Explanation
Likelihood is high in any workflow where objects are resold/re-transferred after being soft-burned once, and later "burned" a second time (by any owner) using an ordinary transfer to `BURN_ADDRESS` rather than a `TransferRef`-based mechanism. Since `burn()`/`unburn()` are public entry functions available to any object owner, and ordinary `transfer`/`transfer_call` require no special permission beyond ungated-transfer being enabled (the default), no privileged access or unusual conditions are needed to set up the exploit — only that the object passes through a `burn()` call once, changes hands normally, and is later sent to `BURN_ADDRESS` by any subsequent owner.

### Recommendation
Clear (or invalidate) any existing `TombStone` in `transfer_raw_inner` (or in `transfer_raw`, ensuring all transfer entrypoints funnel through the cleanup) whenever ownership changes, mirroring the protection already implemented in `transfer_with_ref`. Alternatively, restrict `unburn`'s `BURN_ADDRESS` branch so that it validates the `TombStone` was created by the same transfer/burn event and was not superseded by an intervening non-`TransferRef` ownership change, or simply disallow soft-burn objects with a live `TombStone` from being ungated-transferred at all until unburned.

### Proof of Concept
```
// Pseudocode against object.move public API
object::burn(&A, obj);                       // TombStone{original_owner: A} attached, A still owner
object::transfer_call(&A, obj_addr, B_addr);  // Legit sale/transfer to B; TombStone NOT cleared
object::transfer_call(&B, obj_addr, BURN_ADDRESS); // B intentionally burns via ordinary transfer
object::unburn(&A, obj);                      // owner == BURN_ADDRESS, TombStone.original_owner == A
// => obj ownership transferred back to A, stealing it from B/BURN_ADDRESS
```

```text
    /// Transfer to the destination address using a LinearTransferRef.
    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }
```

```text
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
```
