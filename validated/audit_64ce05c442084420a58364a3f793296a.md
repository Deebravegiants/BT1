## Title
Webhook shop-domain header trusted for tenant routing while excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used to route webhook processing from the `shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the request only covers the raw request body. Because the header is not part of the signed material, an attacker who owns a legitimate installed app (and therefore legitimately receives a validly-signed webhook for their own store) can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the host application to process attacker-controlled data under a different tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, and `#webhook_id` are all read straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body), never incorporating `shop`/`topic`/`webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the authenticated body and the header-derived shop: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by Shopify's signature == shop the handler acts on`

Because the signature covers only the body, this equality is not enforced by the gem: the "authenticated" side is effectively "any shop", while the "acted on" side is an attacker-controllable header value.

### Impact Explanation
An attacker who has (or creates) their own store that installs the target app receives genuine webhooks from Shopify — valid raw body + valid HMAC computed with the app's real `client_secret`, for their own shop's data. By replaying that exact body and HMAC to the app's webhook endpoint while forging the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to name a victim shop, the request still passes `HmacValidator.validate` (since only the body is checked), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application logic that persists or acts on this data keyed by `shop` (e.g., updating order/customer/product records for "that shop") ends up cross-tenant contaminated with attacker-controlled data — this matches the Critical "cross-tenant access" impact class, since data attributable to one merchant is injected into another merchant's tenant boundary without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Exploitability requires only that the attacker control (or have controlled) a shop where the target app is/was installed — a low bar, since apps in the Shopify App Store/dev program can typically be installed on trial/dev stores by anyone. No secret material needs to be extracted; the attacker simply captures one legitimate webhook delivery for their own shop and replays it with a modified header value to the same public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified, or otherwise cross-check the header-derived `shop` against a value that is independently authenticated (e.g., validate that the shop has an active, matching session/webhook registration record before dispatching to the handler) rather than trusting the raw header once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook subscription (e.g., `orders/create`) so Shopify sends a signed webhook: body `B`, header `shopify-hmac-sha256: H` (valid for `B` with the app's secret), `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's public webhook endpoint, replacing the `shopify-shop-domain` header with `victim.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` — attacker-controlled data is now processed as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
