### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop` (tenant) identifier used by `Registry.process` is read from an entirely separate, unauthenticated HTTP header. The binding "HMAC-verified bytes == bytes the handler attributes to a shop" does not hold, so anyone who can produce one valid `(body, hmac)` pair for the shared `api_secret_key` can attach that valid signature to a forged `shop-domain` header and have the payload processed as if it came from a different tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a field that is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the body via `Utils::HmacValidator.validate(request)`, and if it passes, forwards `request.shop` straight into `WebhookMetadata` for the app's handler, with no check that the shop header was part of what was signed: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes and compares the HMAC over `verifiable_query.to_signable_string` (i.e., the body), never touching `shop`: [4](#0-3) 

Because `api_secret_key` is shared across every shop installing the app (it is not per-shop), the identity binding the gem needs — "the shop attributed to this payload is the shop that Shopify actually signed it for" — is broken: `shop-domain` is a field acted upon (used as the tenant key passed to the app's handler) but not covered by the HMAC.

### Impact Explanation
Any actor who can obtain one valid `(body, hmac)` webhook pair from Shopify for the shared app secret (e.g., a merchant installing the app receiving genuine webhooks for their own store, or anyone who can trigger a webhook to their own endpoint) can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and hand the forged shop identity to the app's handler via `WebhookMetadata#shop`. If the host application uses `data.shop` to key its per-tenant logic (as the gem's own design intends, since `shop` is the parameter surfaced to handlers), this crosses the tenant boundary: an attacker can cause the application to act on, or attribute data to, a shop they do not control — a cross-tenant confusion condition.

### Likelihood Explanation
Any merchant that installs the app can trivially capture a legitimate webhook (valid body + HMAC) addressed to their own shop, since Shopify sends real webhooks to every installed app. Forging the `shop-domain` header on replay requires no cryptographic secret and no privileged access — only a basic HTTP request to the app's public webhook endpoint. The only constraint is that the raw body bytes must stay identical to what was originally signed, which still lets an attacker misattribute a known/crafted payload (e.g., their own `orders/create` payload) to a different shop.

### Recommendation
Include the tenant-identifying header (`shop-domain`) in the HMAC-signable string, or otherwise cryptographically bind the shop value to the signed payload (e.g., verify the shop against a separately-authenticated session/webhook-id lookup) before constructing `WebhookMetadata` and invoking the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers/receives a genuine webhook with body `B` and valid header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Registry.process` proceeds.
4. `WebhookMetadata` is built with `shop: "victim.myshopify.com"` and passed to the app's handler, which now processes attacker-controlled data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
