### Title
Unauthenticated CPU-exhaustion DoS via unbounded `Vec<Message>` batches processed during free `handle_unsigned` transaction-pool validation - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an arbitrary, unbounded `Vec<Message>` from any unauthenticated network peer and is fully executed — including consensus-proof decoding/verification, MMR/merkle proof checks, and cryptographic signature recovery — inside `ValidateUnsigned::validate_unsigned`, which runs on every node during mempool/gossip validation, before any weight or fee is charged. [1](#0-0)  This mirrors the Apache Answer bug class: parsing/validation work proportional to attacker-controlled input size is performed on unauthenticated data ahead of any cost-bearing gate, allowing a single crafted submission to burn disproportionate CPU across the network.

### Finding Description
`handle_unsigned` is dispatched with `ensure_none(origin)` (unsigned, free) and its `Vec<Message>` argument has no length or per-message-size bound at the pallet level. [2](#0-1)  Crucially, `ValidateUnsigned::validate_unsigned` — which is invoked by every full node's transaction pool the moment the unsigned extrinsic is gossiped, *before* the runtime's `CheckWeight`/`ChargeTransactionPayment` signed-extensions or block-execution weight limits ever apply — calls `Self::execute(messages.clone())`, running the full message-handling pipeline (proof decoding, consensus client `verify_consensus`, state/MMR membership checks, event hashing) on the entire batch: [3](#0-2) 

```rust
fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
    ...
    let events =
        Self::execute(messages.clone()).map_err(|_| InvalidTransaction::BadProof)?;
```

`Self::execute` iterates the full message list and calls `handle_incoming_message` for each entry, decoding and cryptographically validating requests/responses/consensus/timeout messages before any fee-charging step (`FeeHandler::on_executed`) is reached. [4](#0-3)  Because this happens at the mempool-validation layer — which the docs themselves describe only as a "filter" against spam, not a resource-bounded gate — every peer that receives the gossiped unsigned transaction, not just the block author, re-executes the same expensive validation. [5](#0-4)  An attacker can pack the batch with a large number of `Message::Consensus` or `Message::Request`/`Response` entries carrying malformed-but-plausible proofs (e.g. large digest/validator/header lists) that are only rejected deep into verification, after most of the parsing/decoding/hash work has already run — free of charge, unbounded by weight, and repeated on every node in the gossip path.

This is structurally the same "length-parameter inconsistency" DoS as CVE-2026-48834: attacker-controlled input size/shape drives CPU-bound parsing/verification work in an unauthenticated pre-validation stage, with no size cap tied to that stage.

### Impact Explanation
A single unsigned extrinsic submission can force CPU-intensive decode/verification work onto every relaying full node in the network for free, repeatedly, as the transaction propagates and is re-validated by each peer's pool. Sustained submission of such batches can degrade block production and transaction propagation network-wide — a availability (High CIA "A") impact matching the reported CVSS vector (AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H), reachable from a single unauthenticated unsigned extrinsic dispatch as required by scope.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be callable by anyone without a signature or fee, and the codebase's own documentation acknowledges the trust placed in mempool-level filtering ("Use with caution"). [6](#0-5)  No `Vec<Message>` length bound, per-message size bound, or `MaxEncodedLen`/`BoundedVec` constraint was found gating this path before `validate_unsigned` executes the full verification. Building a batch of malformed-but-structurally-valid messages requires no special access or capital, only knowledge of the SCALE-encoded `Message` format.

### Recommendation
Bound the cost of `validate_unsigned` before any decoding/verification work is performed: cap the number of messages and the cumulative encoded size of `Vec<Message>` (e.g., via a configurable `MaxMessagesPerBatch`/`MaxCallSize`-style check similar to the one already added to `pallet_call_decompressor::decompress`), and reject batches exceeding it with `InvalidTransaction::ExhaustsResources` prior to invoking `Self::execute`. Consider also imposing an early, cheap structural/size check per message variant before any cryptographic or proof-verification work begins.

### Proof of Concept
1. Craft an unsigned `pallet_ismp::Call::handle_unsigned { messages }` where `messages` is a large `Vec<Message>` (limited only by the block's `RuntimeBlockLength`, e.g. 5 MB) filled with `Message::Consensus`/`Message::Request` entries containing maximal nested structures (e.g. many digest items, large proof vectors) and syntactically valid but ultimately-invalid proofs.
2. Submit the unsigned extrinsic to any RPC node; it propagates via gossip to the network.
3. Each receiving node's transaction pool calls `ValidateUnsigned::validate_unsigned`, which executes `Self::execute(messages.clone())` — decoding and attempting full consensus/proof verification of the entire batch — before rejecting it as `InvalidTransaction::BadProof`, at zero cost to the submitter but non-trivial CPU cost to every validating node. [3](#0-2) 
4. Repeat submission (varying content to avoid `provides`-tag dedup) to sustain load across the network.

```rust
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
