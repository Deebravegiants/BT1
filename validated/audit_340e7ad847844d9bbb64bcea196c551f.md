Found the analog. The Tron variant of `IntentGatewayV2.placeOrder` performs an exact-output Uniswap V2 swap for `order.fees` but never refunds the unspent native token left over after the swap, unlike the main EVM version which explicitly does so.

### Title
`placeOrder` in the Tron `IntentGatewayV2` fails to refund unspent native ETH after the fee swap, permanently trapping user funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` performs an exact-output swap (`swapETHForExactTokens`) to acquire the fee token when a user sends native value to cover `order.fees`, but it never refunds the leftover `msgValue` that the swap didn't consume. The mainline EVM `IntentGatewayV2.sol` performs the identical swap and then explicitly refunds `msgValue` back to `msg.sender` — this refund line is missing in the Tron variant.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` handles `order.fees` like this: [1](#0-0) 
It calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` — sending the entire remaining native `msgValue` to the router. Since this is an *exact output* swap, the router will only consume as much ETH as required to produce `order.fees` tokens and refund the rest — but that refund is sent to `msg.sender` of the swap call, which is the `IntentGatewayV2` contract itself, not the original user. The Tron contract records the amounts, but does not decrement `msgValue` afterward, and critically the function ends without any subsequent `_sendValue`/refund of unspent native tokens.

Contrast this with the audited mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`), which performs the same operation but explicitly tracks and refunds the difference: [2](#0-1) 
Here `msgValue -= amounts[0]` correctly accounts for how much ETH the swap actually consumed, and the trailing `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` refunds the user's unspent excess. The Tron variant has neither the `amounts[0]` deduction pattern applied consistently to later refund logic, nor the trailing refund block for unspent native tokens overall in this path.

This is directly analogous to the referenced Sherlock finding (M-1, `rebalanceLite`): a function accepts a caller-supplied amount for a swap-like operation, the underlying AMM call can leave residual/unspent input value in the contract rather than fully consuming it, and that leftover value is not routed back to the user who supplied it — it is stranded inside the protocol contract instead.

### Impact Explanation
Any user placing an order with `order.fees > 0` and paying the fee in native token via the Tron `IntentGatewayV2` will have any ETH not consumed by the exact-output swap permanently stuck in the contract (unless a governance sweep function exists and specifically targets this balance, which regular users cannot trigger themselves). Given that `swapETHForExactTokens` refunds are the norm and slippage/price movement between quote and execution is expected, this is a systematic loss on every fee-swap order placed with any margin of safety in `msg.value`, not an edge case.

### Likelihood Explanation
Any user who over-supplies native token as a safety margin for the fee-swap price (which is the expected/recommended usage pattern, and is exactly what the audited main branch's refund logic exists to handle) triggers this loss on a single `placeOrder` call — no attacker or malicious actor is required, and it reproduces on ordinary usage.

### Recommendation
Mirror the mainline `evm/src/apps/IntentGatewayV2.sol` logic in the Tron contract: capture the `amounts` array returned by `swapETHForExactTokens`, deduct `amounts[0]` from `msgValue`, and add the trailing `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` refund at the end of `placeOrder` (matching lines 386 and 394-397 of the main contract) so any unspent native token (from both the fee swap and any other leftover `msgValue`) is returned to the user rather than trapped in the contract.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: 5 ether}(order, graffiti)` on Tron, where `order.fees` requires the equivalent of ~0.1 ETH worth of fee token and all inputs are ERC-20 (no native `inputs`), so the full 5 ETH is intended only to cover the fee swap with slippage margin.
2. `swapETHForExactTokens{value: 5 ether}(order.fees, ...)` executes; the router consumes only ~0.1 ETH and refunds ~4.9 ETH to `address(this)` (the `IntentGatewayV2` contract).
3. `placeOrder()` returns without transferring the ~4.9 ETH back to the user; the `IntentGatewayV2` contract's native balance permanently retains it (comparable to the equivalent, corrected `testFeeSwap...` behavior verified in the audited main-branch test suite, e.g. [3](#0-2)  which the Tron contract does not replicate).
