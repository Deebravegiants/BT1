Audit Report

## Title
Missing Duplicate-MessageID Guard Enables Cross-User Response Hijacking in Gateway WebAPI Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` in the capabilities `WebAPIHandler` stores each in-flight caller's callback in `h.savedCallbacks` keyed solely by the caller-supplied `MessageID`, with no uniqueness or ownership check before overwriting an existing entry. Since `ProcessRequest` blocks synchronously per HTTP request on `callback.Wait(ctx)`, a second request that reuses an in-flight `MessageID` overwrites the first caller's stored callback, so the DON's eventual response — matched to a callback purely by `MessageID` in `handleWebAPITriggerMessage` — is delivered to the second (attacker) caller instead of the original one.

## Finding Description
`HandleLegacyUserMessage` writes into the shared map without checking for a pre-existing key: [1](#0-0) 

This contrasts with the sibling v2 HTTP trigger handler, which explicitly detects `MessageID`/`requestID` collisions and rejects the second request with `jsonrpc.ErrConflict` instead of overwriting: [2](#0-1) 

The response side looks callbacks up purely by `msg.Body.MessageID`, with no check that the callback belongs to the original requester (e.g., no comparison against `msg.Body.Sender` of the original request): [3](#0-2) 

`MessageID` is a caller-chosen string bounded only by length/format checks in `Message.Validate()` (`MessageIDMaxLen`, non-null-terminated); it is not derived from or bound to the sender's identity, and `Validate()` computes `Sender` independently from the signature: [4](#0-3) . This means two different signers can independently choose to submit the same `MessageID` string; the signature only proves who signed a given message, not that the `MessageID` field is unique to them.

Critically, `gateway.ProcessRequest` runs the entire request-response cycle synchronously per incoming HTTP request, blocking on `callback.Wait(ctx)` until a response arrives at the shared callback: [5](#0-4) 

Exploit flow: (1) Victim's HTTP request with `MessageID=X` is processed by `HandleLegacyUserMessage`, storing victim's callback at `h.savedCallbacks["X"]` and dispatching the request to all DON members; the victim's HTTP handler goroutine is now blocked in `callback.Wait(ctx)`. (2) Before the DON responds, attacker submits their own independently-signed `web_api_trigger` request also using `MessageID="X"`; `HandleLegacyUserMessage` silently overwrites `h.savedCallbacks["X"]` with the attacker's callback, and dispatches the attacker's own request to the DON as well. (3) When the DON eventually returns a `MethodWebAPITrigger` response carrying `MessageID="X"` (intended as the reply to the victim's underlying request), `handleWebAPITriggerMessage` looks up `h.savedCallbacks["X"]`, finds the attacker's callback (since it overwrote the victim's), deletes the entry, and sends the response to the attacker instead. (4) The victim's blocked HTTP request eventually times out with no data. This mirrors the same "second call silently overwrites state set by the first, with only an index/ID as the discriminator" bug class as the referenced Otter Audits CPI-guard finding, and is explicitly avoided elsewhere in this codebase (the v2 `http_trigger_handler.go` conflict check and `requestcache.go`'s `globalID{sender, id}` composite key): [6](#0-5) .

No existing control mitigates this: `Message.Validate()` only checks format/length and computes `Sender` from the signature, it does not enforce ID uniqueness across senders [4](#0-3) ; and the handler's own TODO acknowledges missing allowlisting/rate-limiting at this stage [7](#0-6) .

## Impact Explanation
An unprivileged caller able to submit `web_api_trigger` requests through the gateway can hijack another in-flight caller's DON response by colliding on `MessageID`, causing cross-user response corruption/impersonation: the attacker receives response payload data destined for a different user, while the victim's request silently times out with no response. This falls squarely into the in-scope "gateway request impersonation / cross-user response corruption" impact category.

## Likelihood Explanation
Exploitation requires only unprivileged access to send signed gateway messages (any keyholder can construct and sign a `web_api_trigger` message with an arbitrary `MessageID`) and requires the attacker's colliding request to land after the victim's callback registration but before the DON's response returns — a race window bounded by DON round-trip latency. Feasibility of guessing/colliding on a specific victim's `MessageID` depends on how legitimate clients generate IDs (sequential/predictable IDs make it much easier; the codebase provides no structural protection against it regardless). This is a genuine gap versus the codebase's own established pattern in `http_trigger_handler.go` and `requestcache.go`, which explicitly close this exact class of collision.

## Recommendation
Add the same duplicate-ID rejection used in `http_trigger_handler.go`'s `setupCallback` to `HandleLegacyUserMessage`: reject the second request (returning a conflict-style error) when `h.savedCallbacks[msg.Body.MessageID]` already exists, or key the callback map by a composite `{sender, MessageID}` identity as `requestcache.go` already does, so that colliding IDs from different senders cannot overwrite one another's pending callbacks.

## Proof of Concept
1. Start a gateway with the capabilities `WebAPIHandler` configured with a DON that does not respond immediately (or introduce a delay).
2. Client A sends a signed `web_api_trigger` message with `MessageID="X"` to the gateway via `ProcessRequest`; the gateway calls `HandleLegacyUserMessage`, storing Client A's callback at `h.savedCallbacks["X"]`, and Client A's request blocks in `callback.Wait(ctx)`.
3. Before the DON responds, Client B (independently signed key) sends its own `web_api_trigger` message also with `MessageID="X"`; `HandleLegacyUserMessage` overwrites `h.savedCallbacks["X"]` with Client B's callback.
4. Simulate/allow the DON to respond to Client A's original dispatched request with `MessageID="X"` via `handler.HandleNodeMessage` → `handleWebAPITriggerMessage`.
5. Assert that Client B's `callback.Wait(ctx)` receives Client A's response payload, and Client A's `callback.Wait(ctx)` times out (`api.RequestTimeoutError`) — demonstrating cross-user response delivery. This can be implemented as a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` mirroring the existing `HandleLegacyUserMessage` test harness but registering two distinct signed messages sharing one `MessageID` and asserting callback cross-delivery.
