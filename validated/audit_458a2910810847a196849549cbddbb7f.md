### Title
Unbounded ECDSA signature recovery in BEEFY consensus verification allows free unsigned `handle_unsigned` transactions to exhaust node CPU during mempool validation - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is an **unsigned, feeless** call that anyone can submit. Before it is admitted to the transaction pool, `validate_unsigned` fully executes the message (`Self::execute(messages.clone())`), which for a `Message::Consensus` carrying a BEEFY proof runs `verify_mmr_update_proof`, iterating over every signature in `mmr.signed_commitment.signatures` and performing a `secp256k1_recover` + double keccak256 hash per signature, with no upper bound enforced on the signature count before this expensive loop runs. [1](#0-0) [2](#0-1) 

### Finding Description
`handle_unsigned` is validated via `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` — the *same* full execution path used for actual block inclusion — purely to decide mempool admission: [3](#0-2) 

`execute()` dispatches each `Message` to `handle_incoming_message`, and for `Message::Consensus` this reaches `consensus::update_client` → the registered consensus client's `verify_consensus`, which for the BEEFY client is `beefy_verifier::verify_mmr_update_proof`: [4](#0-3) [5](#0-4) 

Inside `verify_mmr_update_proof`, the loop over `mmr.signed_commitment.signatures` performs `secp256k1_recover` (an expensive elliptic-curve operation) plus two keccak256 hashes for *every* entry, and only *after* this loop is the merkle-multiproof membership check performed: [6](#0-5) 

The only gate before this loop is `check_participation_threshold(signatures_length as u32, authority_set.len)`, which only rejects if the *count* is too low relative to the trusted authority set — it does not cap the absolute number of signatures the caller may supply, nor is `Vec<Message>` (the `handle_unsigned` argument) or `Vec<SignatureWithAuthorityIndex>` bounded by a `MaxSignatures`/`MaxMessages` type. No such bound was found via search of the beefy verifier, primitives, or `pallet-ismp` config. [7](#0-6) 

Because `handle_unsigned` is unsigned and feeless, and validation itself performs this full cryptographic verification, a single crafted extrinsic containing a `ConsensusMessage` with a large number of bogus (but well-formed) `SignatureWithAuthorityIndex` entries — using an unknown/mismatched `validator_set_id` is rejected earlier, but a crafted commitment naming a real (current/next) authority set id with many garbage signatures still passes the pre-loop checks and is only rejected after the full O(n) secp256k1-recover loop completes (either failing to recover, or failing the merkle multi-proof at the end). This mirrors the reported Next.js pattern: a crafted, cheap-to-submit request (Server Action / unsigned extrinsic) triggers disproportionate CPU work in the request-processing pipeline (App Router dispatch / transaction-pool `validate_unsigned`) that runs synchronously in the node process, before it is ultimately rejected — starving that process from processing legitimate transactions and consensus updates in the meantime.

The documentation itself asserts this class of attack is mitigated ("This validity check ensures the transaction can be successfully executed... preventing unnecessary processing and potential network congestion"), which is incorrect precisely because the validity check *is* the expensive processing. [8](#0-7) 

### Impact Explanation
Every node's transaction-pool validation is single-process/synchronous per queued transaction. Repeated submission of such crafted unsigned consensus messages (free of charge, since `handle_unsigned` bypasses transaction fees and requires no signature) lets any unprivileged actor force full nodes/collators to burn CPU cycles on secp256k1 recovery for arbitrarily large (bounded only by extrinsic/block-length limits, which can still admit thousands of 65-byte signatures) signature sets on every resubmission, delaying propagation and processing of legitimate ISMP messages, consensus updates, and other transactions — a denial of service on the message-relay path. This satisfies the "route unable to deliver messages" criterion since delayed consensus/message processing stalls request delivery across the bridge.

### Likelihood Explanation
High likelihood: the call is permissionless, unsigned, and free; no economic cost exists to deter spam, and no explicit size/count bound was found on the `messages` vector or the BEEFY signature vector prior to the expensive cryptographic loop. An attacker only needs a validator_set_id matching a real (current/next) authority set and enough garbage signatures to inflate CPU cost — no valid signatures are actually required to reach and pay for the recovery loop.

### Recommendation
- Bound `mmr.signed_commitment.signatures.len()` to a small multiple of the authority set size before entering the recovery loop (reject early if `signatures_length` is implausibly larger than `authority_set.len`).
- Similarly bound `Vec<Message>` in `handle_unsigned` (a `MaxMessages` config constant) and the SCALE-decoded proof sizes, enforced during `validate_unsigned` before any cryptographic work is performed.
- Consider performing the merkle-multiproof authority membership check (cheap, index-bound) before the batch of `secp256k1_recover` calls (expensive), so malformed/oversized inputs are rejected cheaply first.

### Proof of Concept
1. Craft a `Message::Consensus(ConsensusMessage)` whose `consensus_proof` decodes to a BEEFY `MmrProof` with `commitment.validator_set_id` equal to the trusted chain's current authority set id (public knowledge), and `signatures` containing thousands of syntactically valid but cryptographically bogus `SignatureWithAuthorityIndex` entries (just needs to satisfy `check_participation_threshold` count-wise).
2. Submit as an unsigned `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` extrinsic — no signature, no fee required.
3. Every node running `validate_unsigned` executes `verify_mmr_update_proof`, iterating all signatures through `secp256k1_recover` + keccak256 before ultimately failing the authority merkle-multiproof check.
4. Resubmit repeatedly (varying payload slightly to avoid `provides` dedup) to sustain elevated CPU load across the network's transaction-pool validation, delaying legitimate message/consensus processing.

```rust
pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

	if !valid {
		Err(Error::InvalidAuthoritiesProof)?;
	}
```

```rust
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {

				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
```

```rust
pub fn handle_incoming_message<H>(
	host: &H,
	message: Message,
) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	match message {
		Message::Consensus(consensus_message) => consensus::update_client(host, consensus_message),
		Message::FraudProof(fraud_proof) => consensus::freeze_client(host, fraud_proof),
		Message::Request(req) => request::handle(host, req),
		Message::Response(resp) => response::handle(host, resp),
		Message::Timeout(timeout) => timeout::handle(host, timeout),
	}
}
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
