Audit Report

## Title
Overweight XCM messages that structurally exceed the recursion depth limit (`RECURSION_LIMIT = 10`) can never be resolved by `execute_overweight` (`Error::TemporarilyUnprocessable` forever) - ([File: substrate/frame/message-queue/src/lib.rs])

## Summary
The weigher (`FixedWeightBounds`/`WeightInfoBounds`) enforces a *total instruction count* limit (`instructions_left`, config `M`) via a counter passed by mutable reference through recursive calls, which is a distinct mechanism from the executor's per-call recursion-depth counter (`RECURSION_LIMIT = 10`) enforced in `XcmExecutor::process()`. This allows a deeply nested but instruction-sparse message (e.g., 11+ levels of `SetAppendix`/`SetErrorHandler` wrapping a single inner instruction) to pass `prepare()`'s weight check while still deterministically hitting `XcmError::ExceedsStackLimit` the first time `execute()` actually runs the message. If that first real execution attempt happens via `execute_overweight` (because the initial top-level attempt returned `Overweight` due to insufficient budget *before* ever calling `execute()`), the resulting `StackLimitReached` status is mapped by `do_execute_overweight_inner` to `Error::TemporarilyUnprocessable` on every subsequent retry, regardless of `weight_limit`, since the failure is structural and not weight-dependent.

## Finding Description
`do_execute_overweight_inner` maps `MessageExecutionStatus::StackLimitReached` and `Unprocessable{permanent:false}` to `Err(Error::TemporarilyUnprocessable)`, never to a permanent/discard outcome: [1](#0-0) 

`XcmExecutor::process()` enforces a fixed nesting-depth counter via `recursion_count::using_once`, reset on every fresh top-level call regardless of whether it originates from normal block servicing or from `execute_overweight`: [2](#0-1) 

Separately, `FixedWeightBounds::weight_with_limit` decrements a single `instructions_left` counter passed by mutable reference across recursive calls into nested `SetAppendix`/`SetErrorHandler`/`ExecuteWithOrigin` payloads — this counts *total instructions in the tree*, not nesting depth: [3](#0-2) 

This is corroborated by the test `weigher_weight_limit_correctly_accounts_for_nested_instructions` and `weight_bounds_should_respect_instructions_limit`, which show the weigher's limit tracks total instruction count across nested structures rather than raw depth. A message with depth > 10 but few total instructions (e.g., nested single-instruction `SetAppendix` chains) can pass this weigher check comfortably under typical `MaxInstructions` (100 in most configs) while still exceeding `RECURSION_LIMIT = 10` at actual execution.

`ProcessXcmMessage::process_message` calls `XcmExecutor::prepare` (weight-only, no execution) then checks `meter.can_consume(required)` **before** calling `XcmExecutor::execute`; if the available weight budget is insufficient, it returns `ProcessMessageError::Overweight` without ever invoking `execute()` — meaning the recursion-depth check is never triggered on this first pass: [4](#0-3) 

Only when `execute_overweight` supplies enough weight to pass `can_consume` does `execute()` actually run for the first time, at which point the recursion-depth counter (independent of the supplied weight) deterministically fails with `ExceedsStackLimit` → `ProcessMessageError::StackLimitReached`: [5](#0-4) 

Since this outcome depends only on the message's nesting structure and not on `weight_limit`, every subsequent call to `execute_overweight` will repeat the same `StackLimitReached` → `Error::TemporarilyUnprocessable` result, with no way to make progress. This is directly demonstrated by the existing test `execute_overweight_keeps_stack_ov_message`, which shows a message can be enqueued as `Overweight`, and a later `execute_overweight` call that surfaces `StackLimitReached` returns an error while leaving state unchanged (`StorageNoopGuard`), confirming no forward progress is made: [6](#0-5) 

The report's more nuanced claim that a genuinely first-attempt `StackLimitReached` at *top-level* block servicing gets discarded (not queued as overweight) is also correctly reflected in code/tests (`process_discards_stack_ov_message`), which is consistent with the root-cause mechanism described: the "stuck forever" scenario specifically requires the failure to occur on a retried `execute_overweight` call rather than on the very first top-level attempt.

The report also correctly notes a partial mitigation: `do_reap_page_inner` enforces `ensure!(page_index < book_state.begin, Error::<T>::NotReapable)`, meaning a stuck overweight page can only be culled once the origin's queue has advanced past it via further traffic, via the `cullable()` staleness watermark: [7](#0-6) 

## Impact Explanation
For an affected origin's queue, one specific overweight message becomes permanently stuck: it can never transition to `Processed`, and `execute_overweight` will always return `Error::TemporarilyUnprocessable` regardless of the caller-supplied weight limit, because the true blocking cause (structural recursion depth) is independent of weight. This holds `BookStateFor`'s `message_count`/`size` accounting for that origin until either the origin's queue advances past the stuck page (enabling `reap_page`'s staleness-based culling) or some other mechanism removes the payload. This is a genuine functional/availability defect but is correctly scoped by the report itself as bounded rather than an unconditional, permanent DoS: it does not affect other origins, does not grow unbounded on its own, and does have a traffic-dependent manual recovery path (`reap_page`). The severity is best characterized as low/medium — a stuck-message liveness bug on a specific queue, not a broader chain-wide DoS or fund-loss issue.

## Likelihood Explanation
Constructing a message that is deeply nested (>10 levels via `SetAppendix`/`SetErrorHandler`/`Transact`) yet weighs cheaply enough to pass the weigher's total-instruction-count check, and that is submitted when available weight is insufficient for its first top-level service attempt, is a plausible, attacker-controllable scenario reachable via `pallet_xcm::execute`/`send` or via routed HRMP/UMP messages. The recursion-depth mechanism is fully deterministic given only the message structure, so once triggered on a retried `execute_overweight` call, the outcome repeats indefinitely regardless of retries or weight limit. This matches the documented behavior in `transact_recursion_limit_works` (integration test) and `execute_overweight_keeps_stack_ov_message` (unit test), both already present in the codebase, which increases confidence that the underlying mechanics are real and not speculative.

## Recommendation
- Treat `StackLimitReached` returned specifically from a manual `execute_overweight` call as a permanent/discardable condition instead of always mapping it to `TemporarilyUnprocessable`, since a top-level `execute_overweight` invocation cannot plausibly succeed on any future retry if it fails purely due to message structure.
- Alternatively, make the weigher aware of (or bounded by) the executor's `RECURSION_LIMIT`, so a message that will structurally exceed it is rejected/discarded during weighing rather than admitted into the `Overweight` queue.
- Consider relaxing `reap_page`'s strict `page_index < book_state.begin` requirement, or provide an explicit permissionless purge path for overweight pages whose message deterministically and repeatedly fails with `StackLimitReached`, independent of whether the origin sends further traffic.

## Proof of Concept
1. Build an XCM message nested via `SetAppendix(Xcm(vec![...]))` chains 11+ levels deep, with total instruction count kept low (e.g., one inner instruction per level) so it stays well under `MaxInstructions` for the configured `Weigher`.
2. Submit the message through `pallet_xcm`/the message queue with an initial `ServiceWeight` too small to satisfy `meter.can_consume(required)` on first top-level service, causing `OverweightEnqueued` (verify via `assert_pages` / event) — confirm this path in `process_xcm_message.rs` (lines 79-89) does not invoke `execute()`.
3. Call `MessageQueue::execute_overweight(origin, page_index, index, Weight::MAX)`; assert it returns `Err(Error::TemporarilyUnprocessable)` and a `ProcessingFailed { error: StackLimitReached, .. }` event is emitted.
4. Repeat step 3 with multiple different `weight_limit` values; assert the result is always `Err(Error::TemporarilyUnprocessable)`, `BookStateFor` counters never decrease, and the page persists (`Pages::<T>::get` still returns the unprocessed message) — mirroring the existing `execute_overweight_keeps_stack_ov_message` test pattern.
5. Assert `reap_page` returns `Err(Error::NotReapable)` while `book_state.begin == page_index`, and demonstrate that once further traffic advances `book_state.begin` past `page_index`, `reap_page`'s `cullable()` path eventually succeeds — confirming the issue is a bounded, traffic-dependent stuck-message defect rather than an unconditional permanent DoS.

	/// Same as `do_reap_page` but must be called while holding the `service_mutex`.
	fn do_reap_page_inner(origin: &MessageOriginOf<T>, page_index: PageIndex) -> DispatchResult {
		let mut book_state = BookStateFor::<T>::get(origin);
		// definitely not reapable if the page's index is no less than the `begin`ning of ready
		// pages.
		ensure!(page_index < book_state.begin, Error::<T>::NotReapable);

		let page = Pages::<T>::get(origin, page_index).ok_or(Error::<T>::NoPage)?;

		// definitely reapable if the page has no messages in it.
		let reapable = page.remaining.is_zero();

		// also reapable if the page index has dropped below our watermark.
		let cullable = || {
			let total_pages = book_state.count;
			let ready_pages = book_state.end.saturating_sub(book_state.begin).min(total_pages);

			// The number of stale pages - i.e. pages which contain unprocessed overweight messages.
			// We would prefer to keep these around but will restrict how far into history they can
			// extend if we notice that there's too many of them.
			//
			// We don't know *where* in history these pages are so we use a dynamic formula which
			// reduces the historical time horizon as the stale pages pile up and increases it as
			// they reduce.
			let stale_pages = total_pages - ready_pages;

			// The maximum number of stale pages (i.e. of overweight messages) allowed before
			// culling can happen at all. Once there are more stale pages than this, then historical
			// pages may be dropped, even if they contain unprocessed overweight messages.
			let max_stale = T::MaxStale::get();

			// The amount beyond the maximum which are being used. If it's not beyond the maximum
			// then we exit now since no culling is needed.
			let overflow = match stale_pages.checked_sub(max_stale + 1) {
				Some(x) => x + 1,
				None => return false,
			};

			// The special formula which tells us how deep into index-history we will pages. As
			// the overflow is greater (and thus the need to drop items from storage is more urgent)
			// this is reduced, allowing a greater range of pages to be culled.
			// With a minimum `overflow` (`1`), this returns `max_stale ** 2`, indicating we only
			// cull beyond that number of indices deep into history.
			// At this overflow increases, our depth reduces down to a limit of `max_stale`. We
			// never want to reduce below this since this will certainly allow enough pages to be
			// culled in order to bring `overflow` back to zero.
			let backlog = (max_stale * max_stale / overflow).max(max_stale);

			let watermark = book_state.begin.saturating_sub(backlog);
			page_index < watermark
		};
		ensure!(reapable || cullable(), Error::<T>::NotReapable);

		Pages::<T>::remove(origin, page_index);
		debug_assert!(book_state.count > 0, "reaping a page implies there are pages");
		book_state.count.saturating_dec();
		book_state.message_count.saturating_reduce(page.remaining.into() as u64);
		book_state.size.saturating_reduce(page.remaining_size.into() as u64);
		BookStateFor::<T>::insert(origin, &book_state);
		T::QueueChangeHandler::on_queue_changed(origin.clone(), book_state.into());
		Self::deposit_event(Event::PageReaped { origin: origin.clone(), index: page_index });

		Ok(())
	}

	fn weight_with_limit(
		message: &mut Xcm<C>,
		instructions_left: &mut u32,
		weight_limit: Weight,
	) -> Result<Weight, InstructionError> {
		let mut total_weight: Weight = Weight::zero();
		for (index, instruction) in message.0.iter_mut().enumerate() {
			let index = index.try_into().unwrap_or(InstructionIndex::MAX);
			*instructions_left = instructions_left
				.checked_sub(1)
				.ok_or_else(|| InstructionError { index, error: XcmError::ExceedsStackLimit })?;
			let instruction_weight =
				&Self::instr_weight_with_limit(instruction, instructions_left, weight_limit)
					.map_err(|error| InstructionError { index, error })?;
			total_weight = total_weight
				.checked_add(instruction_weight)
				.ok_or(InstructionError { index, error: XcmError::Overflow })?;
			if total_weight.any_gt(weight_limit) {
				return Err(InstructionError {
					index,
					error: XcmError::WeightLimitReached(total_weight),
				});
			}
		}
		Ok(total_weight)
	}

	fn instr_weight_with_limit(
		instruction: &mut Instruction<C>,
		instructions_left: &mut u32,
		weight_limit: Weight,
	) -> Result<Weight, XcmError> {
		let instruction_weight = match instruction {
			Transact { ref mut call, .. } => {
				call.ensure_decoded()
					.map_err(|_| XcmError::FailedToDecode)?
					.get_dispatch_info()
					.call_weight
			},
			SetErrorHandler(xcm) | SetAppendix(xcm) | ExecuteWithOrigin { xcm, .. } => {
				Self::weight_with_limit(xcm, instructions_left, weight_limit)
					.map_err(|outcome_error| outcome_error.error)?
			},
			_ => Weight::zero(),
		};
		let total_weight = T::get().checked_add(&instruction_weight).ok_or(XcmError::Overflow)?;
		Ok(total_weight)
	}

/// A message that reports `StackLimitReached` will not be put into the overweight queue when
/// executed from the top level.
#[test]
fn process_discards_stack_ov_message() {
	use MessageOrigin::*;
	build_and_execute::<Test>(|| {
		MessageQueue::enqueue_message(msg("stacklimitreached"), Here);

		MessageQueue::service_queues(10.into_weight());

		assert_last_event::<Test>(
			Event::ProcessingFailed {
				id: blake2_256(b"stacklimitreached").into(),
				origin: MessageOrigin::Here,
				error: ProcessMessageError::StackLimitReached,
			}
			.into(),
		);

		assert!(MessagesProcessed::take().is_empty());
		// Message is gone and not overweight:
		assert_pages(&[]);
	});
}
