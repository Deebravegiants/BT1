### Title
Attacker-controlled `swap: Bytes` payload is deserialized and executed as arbitrary contract calls under the caller's authorization tree, draining the signer's wallet — (`contracts/controller/src/strategies/swap.rs`)

### Summary
CVE-2021-35196 is insecure deserialization: Manuskript executed attacker-controlled bytes from a crafted file via `pickle.load()`. The XOXNO analog is the controller's serialized-route surface: `swap_collateral`, `swap_debt`, `multiply`, `swap_debt_with_collateral`, and `repay_debt_with_collateral` all accept a caller-supplied `swap: Bytes` blob, hand it to the configured swap-aggregator, which `from_xdr`-decodes it into a `StrategyPayload` and invokes whatever pool/token contract addresses the blob names — with no venue allowlist. A route can therefore place malicious third-party code on the call stack *below the victim's `require_auth` entry*, and any `token.transfer` that code performs from the victim is recorded as a child of the signed authorization tree. The loss is the signer's whole wallet, not just the routed amount, and neither the payload's `min_out` nor the controller's post-swap risk gate bounds it.

### Finding Description
The controller strategy verbs forward an opaque byte blob for execution:

- `swap_collateral(caller, account_id, collateral_in, amount_in, collateral_out, swap)` → `process_swap_collateral` → `legs::execute_swap` → aggregator `execute_strategy(sender, total_in, swap_xdr)`. The aggregator does `StrategyPayload::from_xdr(&env, &swap_xdr)` and `execute::run`, which invokes the addresses the payload names (`contracts/swap-aggregator/src/lib.rs:250-255`). The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-160`).

The auth-tree poison is demonstrated end-to-end by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a `RogueHopPool` named inside the route performs `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`; simulation records that transfer as a child of Alice's `swap_collateral` auth entry, the swap still pays fair output, and Alice's unrelated wallet token is emptied (lines 195-227 assert `balance(alice) == 0`, `balance(attacker) == WALLET_BALANCE`, and the credited supply).

This is the direct analog of `pickle.load()` on a crafted file: a serialized, attacker-crafted blob (`swap_xdr`) is decoded and its embedded "instructions" (arbitrary contract invocations) execute with privileges the deserializer's caller context provides — here, the victim's signed authorization tree rather than a process's OS privileges.

### Impact Explanation
Theft of user funds. A single crafted `routeXdr` embedded in a `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` transaction that the victim signs lets payload-named code transfer any token the victim holds, in any amount the signer can authorize, to an attacker address. The bound is the signer's wallet contents, not the swap's `amount_in`, and the same exposure exists on the standalone router `execute_strategy` path for every swap user.

### Likelihood Explanation
Reaching it requires getting the victim to sign a poisoned route — e.g., a malicious or compromised quote/route service, phishing UI, or malicious dApp composing `multiply` for leverage users. That is a realistic attack surface since routes are produced off-chain and users sign opaque base64 blobs; an honest route gives no extra child auth entry, so the attack is invisible unless the client decodes the route and inspects the recorded auth tree before signing. No privileged role, upgrade, or leaked key is needed by the attacker; `swap_collateral` et al. are permissionless.

### Recommendation
Enforce what the threat model currently pushes onto clients, at the contract layer:

- In the swap-aggregator (`execute::run`), restrict payload-named venue/pool calls to contracts that cannot `require_auth` the sender — e.g., invoke venues via a sub-context that does not propagate the caller's authorization, or require all venue calls to be self-authorized (`authorize_as_current_contract`) and reject any `require_auth(sender)` issued below the router frame.
- Alternatively/additionally, have the controller validate the route structurally before dispatch (e.g., require a pinned `StrategyPayload` schema version and an allowlist of venue contract ids or wasm hashes set via governance), so attacker-deployed "pools" cannot be named.
- Document and enforce that wallets must simulate and reject any `swap_*`/`execute_strategy` authorization tree containing child invocations beyond the single input `transfer`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` (repo: `Alyssadaypin/rs-lending-xlm--019`):

1. Attacker deploys `RogueHopPool` configured with `(victim, wallet_token, attacker, WALLET_BALANCE)`.
2. Attacker produces `swap_xdr` naming `RogueHopPool` as a hop, with `min_out` set to a fair output so the swap looks legitimate.
3. Victim calls `controller.swap_collateral(alice, account_id, USDC, amount_in, ETH, route)` and signs the recorded auth tree.
4. During execution, `RogueHopPool::swap` runs `token.transfer(alice → attacker, WALLET_BALANCE)`; the transfer is a child of Alice's signed `swap_collateral` entry.
5. Assertions confirm: Alice's wallet token balance becomes `0`, the attacker's becomes `WALLET_BALANCE`, and the swap itself completes normally — the theft is unbounded by `min_out` or the post-swap solvency check.
