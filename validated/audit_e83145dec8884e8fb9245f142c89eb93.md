Based on my investigation, the strongest reachable analog to the reported "identity binding is broken because one component isn't covered by the verification of another" is in the webhook verification path: the shop identity is not covered by the HMAC that this gem validates.

### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing shop-identity spoofing on replayed webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` only returns the raw request body, never the `shop-domain` header. `Utils::HmacValidator.validate` verifies exactly that signable string. `Webhooks::Registry.process` then forwards `request.shop` — a value taken straight from an attacker-controllable header — into the handler payload as the authoritative merchant identity, with no cryptographic binding between the verified bytes and that identity claim.

### Finding Description
`Request#hmac` reads the HMAC from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes and compares the HMAC purely over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` (from the unauthenticated header) as the shop identity handed to the app's handler: [4](#0-3) 

The identity binding that is broken is:
`bytes_verified_by_hmac (raw_body)` ≠ `shop_identity_acted_on (headers["shop-domain"])`.

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app can generate a validly-signed webhook body for their own store, then replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain.

### Impact Explanation
Any host application that follows this gem's documented pattern (using `WebhookMetadata#shop` from `Registry.process` to look up the corresponding merchant's session/access token, as shown in the gem's own webhook usage flow) can be tricked into acting on behalf of a different tenant than the one that actually authorized the request. This is a cross-tenant access issue: an attacker-controlled shop can cause the host app's webhook handler to execute logic keyed to an arbitrary victim shop identity, using an HMAC that only ever proved the (attacker-chosen) body content, not the shop.

### Likelihood Explanation
Exploitation only requires installing the app on any shop the attacker controls (a normal, unprivileged action), crafting a webhook-shaped HTTP POST with a body of their choosing, computing/obtaining the corresponding valid HMAC for that body, and replaying it to the app's webhook endpoint with the `shop-domain` header changed to the victim. No access token, `api_secret_key`, or privileged credential of the victim is required — only knowledge of the shared `api_secret_key` value the app already gives the attacker's own installed shop (since HMAC is computed with that key, which is common to every install of the same app).

### Recommendation
Bind the shop identity into the verified material: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value inside `to_signable_string`, or otherwise require the host application to independently authenticate/authorize `request.shop` against a known, previously-established session/install record before trusting it, rather than passing the raw header value straight through `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining ability to trigger genuine webhooks with attacker-chosen body content (e.g. via `orders/create` on their own store).
2. Shopify sends a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `api_secret_key`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request, and resends it to the same endpoint changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, keeping the same raw body and HMAC.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only ever covered the (unmodified) body: [5](#0-4) 
5. The handler executes with `shop: "victim-shop.myshopify.com"`, so any host-app logic that keys off `WebhookMetadata#shop` (e.g. token lookup) now operates against the victim tenant using attacker-supplied body content.
