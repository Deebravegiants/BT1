### Title
Shared `utxoIndex` counter across all tokens in `DepositOnChainUtxosExternalAction` allows attacker-grindable `timeStamp` collisions with pre-existing commitments - (`File: contracts/external-actions/DepositOnChainUtxosExternalAction.sol`)

### Summary
`DepositOnChainUtxosExternalAction.runAction` uses a single `utxoIndex` counter that increments across the outer token loop and the inner per-token UTXO loop without resetting per token, so the effective `timeStamp` (`circomData.timeStamp + utxoIndex`) assigned to a UTXO for token `Y` depends on how many UTXOs were declared for all preceding tokens in the same call. Since `circomData.timeStamp`, `stealthAddressStructure`, `amount`, and `erc20TokenAddresses[i]` are all attacker-supplied and the UTXO's commitment appears to be deterministic over exactly these four fields (`contracts/types/UTXO.sol`), an unprivileged depositor can grind the shape of `utxoAmounts` to land any token's assigned `timeStamp` on a specific target value and reproduce the exact preimage of any existing (or future, if predictable) leaf, including one belonging to a victim.

### Finding Description
The broken equality: for two "distinct" UTXOs inserted into the tree, `commitment(UTXO_A) != commitment(UTXO_B)` should always hold unless `UTXO_A == UTXO_B` was intentionally created by the same owner. The code allows an attacker to force `commitment(attackerUTXO) == commitment(victimUTXO)` for a UTXO the attacker never owned.

Code path: [1](#0-0)  shows `utxoIndex` is declared once before the outer `for (i < tokenCount)` loop and is never reset when moving to the next token — it only increments in the inner `j` loop, meaning `timeStamp` for a UTXO belonging to token `i>0` is offset by however many UTXOs were emitted for all prior tokens in the same call. Because `utxoAmounts` (the per-token UTXO count/shape) is decoded from `circomData.externalActionData.externalActionMetadata`, which is fully attacker-controlled calldata, the attacker can choose the shape freely to land any token's `timeStamp` on `circomData.timeStamp + N` for any desired `N`.

The `UTXO` struct only has four fields — `amount`, `erc20Address`, `stealthAddressStructure`, `timeStamp` — with no additional attacker-unknown blinding/secret component visible in the struct: [2](#0-1) . `stealthAddressStructure` is also fully attacker-supplied per call (`circomData.stealthAddressStructure`), and per `performHinkalChecks`/`dimensionsCheck` the only enforced constraint on it is `H0x != 0` [3](#0-2) ; there is no check that this stealth address structure is one the caller actually controls, and it can be copied verbatim from a victim's public `NewCommitment` event.

Attacker's exact call: `transact()` with `erc20TokenAddresses=[tokenX, tokenY]`, `deltaAmounts=[0,0]`, and `externalActionMetadata` encoding `utxoAmounts=[[a1,a2],[a3]]`. This drives `utxoIndex` to 0,1 for tokenX and 2 for tokenY, so tokenY's single UTXO gets `timeStamp = circomData.timeStamp + 2`. By grinding the number/lengths of `utxoAmounts[i]` for preceding tokens, the attacker can force this offset to equal `victimTimeStamp - circomData.timeStamp` for any victim leaf whose `(amount, token, stealthAddress, timeStamp)` is publicly known from a prior `NewCommitment` event.

Why existing guards fail: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` validate array-length consistency and `onChainCreation` semantics but do not validate uniqueness of the resulting commitment against the existing Merkle tree, nor do they constrain `stealthAddressStructure` to belong to `msg.sender`/`originalSender`. `runAction` requires real ERC20 transfer of `tokenTotal` from the attacker (so the attacker must actually fund the deposit), but this only proves the attacker owns the tokens being deposited — not that they own the destination stealth address, which the contract never checks.

### Impact Explanation
If commitment uniqueness/insertion has no duplicate-leaf protection, and nullifiers are derived purely from the note's secret opening (not from the leaf's tree position — standard in Tornado-style privacy pools), then two leaves sharing an identical `(amount, token, stealthAddressStructure, timeStamp)` preimage will also share an identical nullifier when the true owner (who holds the private key/secret for that stealth address) later spends the note. Spending either leaf marks that nullifier as used, permanently blocking any future spend attempt referencing the other, functionally-identical leaf. This matches the Critical category: permanent freezing of a victim's shielded funds triggered by an unprivileged depositor.

### Likelihood Explanation
Preconditions are modest: the attacker needs (a) real ERC20 balance of `tokenX`/`tokenY` to fund the deposit legs, (b) a known victim leaf's public fields from an on-chain `NewCommitment` event, and (c) the ability to grind `utxoAmounts` shapes (cheap, off-chain, unlimited attempts, on-chain cost only for the eventually chosen shape). The attack is repeatable against any observed commitment whose four fields the attacker can reproduce, and the offset-grinding technique generalizes beyond two tokens to any number of tokens/UTXOs.

### Recommendation
Reset `utxoIndex` per token iteration (or derive `timeStamp` from a value that cannot be freely re-targeted by array-shape choice, e.g. `block.timestamp`/a monotonic nonce bound to `msg.sender`), and additionally enforce commitment-level protections that are independent of this bug: (1) reject insertion of a commitment value that already exists as a leaf in the tree, and/or (2) require proof that the depositor controls (or has explicit authorization for) the `stealthAddressStructure` being deposited to, rather than accepting it unauthenticated in `CircomData`.

### Proof of Concept
Foundry test outline:
1. Victim calls `prooflessDeposit` for `tokenY`; capture the emitted `NewCommitment` and decode `(amount, token, stealthAddress, timeStamp)`.
2. Attacker computes required `utxoIndex` offset `N = victimTimeStamp - attackerCircomData.timeStamp`.
3. Attacker crafts `utxoAmounts` (e.g., `[[a1, a2], [a3]]`) such that tokenY's slot lands at index `N`, sets `stealthAddressStructure = victimStealthAddress`, `amount = victimAmount`, `erc20TokenAddresses[1] = tokenY`.
4. Call `transact()` invoking `DepositOnChainUtxosExternalAction`, funding the real transferred token amounts from the attacker's own balance.
5. Assert the newly emitted commitment for the tokenY leg equals the victim's original commitment value (`commitment(attackerUTXO) == commitment(victimUTXO)`).
6. Have the victim later spend their original UTXO with a valid proof; assert the nullifier emitted matches, and assert that any subsequent attempt to reference the duplicate leaf (even by the victim, via the other physical leaf index) reverts as "nullifier already used," demonstrating permanent freeze of the twin leaf.

Note: full confirmation of the "freeze" consequence depends on the exact commitment-hash and nullifier-derivation logic (not located within available tool budget — likely in `Hinkal.sol`/`CircomDataBuilder.sol`/circuit files under `circuits/`), which should be inspected to confirm nullifiers are leaf-position-independent before finalizing severity.
