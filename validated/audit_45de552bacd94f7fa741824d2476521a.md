## Finding

### Title
Nil pointer dereference in vault `GatewayHandler.handlePublicKeyGet` via unchecked `*req.Params` - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
The vault node-side `GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet`, bypassing the `requestProcessor.ProcessRequest` pipeline that enforces a `req.Params == nil` check for every other vault method (`MethodSecretsCreate/Update/Delete/List`). `handlePublicKeyGet` immediately dereferences `*req.Params` in a `json.Unmarshal` call with no nil guard, causing a nil pointer dereference (process crash / DoS) if a request with `Params == nil` reaches it — structurally the same bug class as GHSL-2024-118 (dereferencing a pointer assumed non-null that a malformed/incomplete but otherwise well-formed input can leave null).

### Finding Description
`HandleGatewayMessage` routes by method: [1](#0-0) 

For `MethodSecretsCreate`/`Update`/`Delete`/`List`, `p.requestProcessor.ProcessRequest` is invoked first, and each of its per-method handlers explicitly rejects a nil `req.Params`: [2](#0-1) [3](#0-2) [4](#0-3) 

But for `MethodPublicKeyGet`, the code calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly — with no equivalent nil-params guard anywhere on this path: [5](#0-4) 

`handlePublicKeyGet` unconditionally dereferences the pointer: [6](#0-5) 

If `req.Params` is `nil`, `*req.Params` panics with a nil pointer dereference. This is a Go-level analog to the GStreamer bug: a value that other code paths treat as "always validated non-null before use" is dereferenced directly in one code path that skips that validation.

### Impact Explanation
A nil pointer dereference panics the goroutine handling the gateway message. Absent panic recovery isolating this specific handler invocation, this can crash or destabilize the node process handling vault gateway messages, denying vault public-key retrieval (and potentially other in-flight vault operations sharing the process) — a Denial of Service consistent in class with the reported GStreamer CVE (CVSS availability impact).

### Likelihood Explanation
Reachability depends on whether the gateway-side relay (`core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage`) forwards a `MethodPublicKeyGet` request with `Params == nil` through to DON nodes unmodified. I confirmed the gateway-side code treats public-key requests as not requiring authorization and does not appear to enforce a nil-params check before creating the active request and forwarding it (unlike the create/update/delete/list paths, which are gated by `requestProcessor.ProcessRequest`'s nil check). I was not able to fully read the gateway-side `handlePublicKeyGet`/forwarding implementation within the remaining tool budget to conclusively confirm that a `nil`/omitted `params` field in an inbound JSON-RPC user request survives unmodified to the node's `HandleGatewayMessage`. This end-to-end reachability from an unprivileged HTTP client through the gateway to the node handler is the main open question.

### Recommendation
Add an explicit `if req.Params == nil { return h.errorResponse(...) }` guard at the top of `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, mirroring the pattern already used in `gateway_vault_request_processor.go`'s other method handlers, before any `json.Unmarshal(*req.Params, ...)` dereference. Additionally, audit the gateway-side vault handler's public-key-get path to ensure it rejects/normalizes nil `params` before forwarding to nodes.

### Proof of Concept
Not independently executed against a running node; based on static code reading:
1. Send a JSON-RPC request to the gateway's vault user endpoint with `method: "vault.publicKey.get"` and no `params` field (or `params: null`).
2. If the gateway forwards this unchanged to a DON node, the node's `GatewayHandler.HandleGatewayMessage` routes to `handlePublicKeyGet` (bypassing the nil-params-checked `requestProcessor.ProcessRequest`), which executes `json.Unmarshal(*req.Params, r)` and panics on the nil dereference.
