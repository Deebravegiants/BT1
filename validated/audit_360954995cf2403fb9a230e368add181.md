### Title
Missing `protocolFeeBps` / `surplusShareBps` bounds validation in Tron `IntentGatewayV2.setParams` can permanently brick `placeOrder`/fee accounting for all users - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The audited external report flags missing bounds validation in setter functions (`setBondPercentDiv`, `setMinLicenseFee`, etc.) that can later cause division-by-zero or arithmetic underflow for ordinary users. The Tron variant of `IntentGatewayV2` in this repo reproduces exactly this bug class: its `setParams` function stores `Params` (including `protocolFeeBps` and `surplusShareBps`) with **no validation at all**, unlike the canonical EVM `IntentsBase._validateParams` which explicitly bounds `protocolFeeBps < 10_000` and `surplusShareBps <= 10_000`.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`: [1](#0-0) 
```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    _admin = address(0);
    _params = p;
}
```
There is no check on `p.protocolFeeBps`, `p.surplusShareBps`, `p.host`, or `p.dispatcher` — contrast this with the canonical EVM implementation's `_validateParams`, which enforces `surplusShareBps <= 10_000` and `protocolFeeBps < 10_000`: [2](#0-1) 

The unvalidated `protocolFeeBps` is later consumed directly in `placeOrder`'s fee-reduction arithmetic (the same computation pattern as the canonical contract): [3](#0-2) 
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```
If `protocolFeeBps` is ever set (accidentally or via misconfiguration/upgrade mistake, not necessarily malicious intent) above `10_000`, `protocolFee` exceeds `originalAmount` and the subtraction underflows and reverts under Solidity 0.8's checked arithmetic — permanently reverting every subsequent `placeOrder` call for every user on that chain, since `_admin` is zeroed out after the single `setParams` call and there is no recovery path to fix the value. This is a **route unable to deliver messages / permanent denial of order placement** for an ordinary unprivileged caller (the intent user submitting `placeOrder`), which is the exact "reachable by an unprivileged... intent solver" path required.

This is structurally identical to the report's `setBondPercentDiv`/`setMinLicenseFee` finding: a setter with no upper-bound validation whose bad value is only discovered when normal user-facing arithmetic (`bondForRebalance`, here `placeOrder`'s fee subtraction) blows up.

### Impact Explanation
A misconfigured `protocolFeeBps` (>10,000 bps) or `surplusShareBps` bricks the primary user-facing entrypoint (`placeOrder`) permanently for that gateway instance — no further intents can be placed, and since `_admin` is a one-shot field zeroed after the first `setParams` call, there is no way to correct the value afterward. This is a protocol-availability failure (funds already escrowed may become unreachable through the normal fill path), which the scan rules class as Medium (route unable to deliver messages / permanent freezing of new-order flow).

### Likelihood Explanation
Likelihood is moderate: it requires a single `setParams` call with an out-of-range value, which could happen from an off-by-one/percentage-vs-bps confusion (a very plausible operational mistake, e.g., passing `100_00` instead of `100`), and the bug is silent until the first `placeOrder` after the bad value is set. The canonical (non-Tron) `IntentGatewayV2` already guards against exactly this via `_validateParams`, showing the maintainers are aware of the risk class but the Tron port omitted the same guard — a strong signal this is a real gap rather than an intentional design choice.

### Recommendation
Add the same bounds validation used in `IntentsBase._validateParams` to the Tron `IntentGatewayV2.setParams` (and any other chain-specific forks of the contract):
```solidity
function setParams(Params memory p) public {
    if (msg.sender != _admin) revert Unauthorized();
    if (p.surplusShareBps > 10_000) revert InvalidInput();
    if (p.protocolFeeBps >= 10_000) revert InvalidInput();
    if (p.host == address(0)) revert InvalidInput();
    if (p.dispatcher == address(0)) revert InvalidInput();
    _admin = address(0);
    _params = p;
}
```
Also validate any destination-specific fee overrides (`DestinationFee.destinationFeeBps < 10_000`) the same way the EVM `_updateParams` does.

### Proof of Concept
1. Deploy Tron `IntentGatewayV2` with `admin = deployer`.
2. `deployer` calls `setParams(Params{ ..., protocolFeeBps: 15000, ... })` (>100%, e.g. a decimal/percentage unit mistake). This succeeds silently since no bound check exists; `_admin` is now zeroed, so this cannot be corrected.
3. Any user calls `placeOrder(order, graffiti)` with a non-zero input amount.
4. Inside the fee-reduction loop, `protocolFee = (originalAmount * 15000) / 10000 > originalAmount`; the subsequent `originalAmount - protocolFee` underflows and reverts (Solidity 0.8 checked math), reverting the entire `placeOrder` transaction.
5. Because `_admin` was already consumed, `setParams` can never be called again — every future `placeOrder` call on this gateway permanently reverts.

Note: I could not fully trace whether the Tron contract's fee-reduction code is byte-for-byte identical to the canonical `IntentGatewayV2.sol` snippet cited (index coverage for the Tron file's `placeOrder` body was incomplete in the tool results); the vulnerable pattern is confirmed present in `setParams` (missing validation, verified directly) and in the canonical contract's fee arithmetic (verified directly), and the two are wired together via the shared `Params.protocolFeeBps` field. A full review of `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` body is recommended to confirm the exact arithmetic before remediation.
