Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers that the HMAC never covers. An unprivileged internet user who can obtain one genuine, validly-signed webhook (e.g., by installing the app on their own free/dev store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `X-Shopify-Shop-Domain` header, and the gem will accept it as authentic and hand it to the app's handler as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body (`@raw_body`) — headers are excluded from the signed material: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived directly from attacker-controllable HTTP headers, with no cryptographic binding to the HMAC: [3](#0-2) [4](#0-3) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — a pass here proves the body wasn't tampered with, but says nothing about which shop the request came from — and then immediately trusts `request.shop` when dispatching to the registered handler: [5](#0-4) 

This breaks the intended identity binding:
`HMAC(secret, raw_body) == received_hmac` ⇏ `request.shop == the shop that actually sent this webhook`

Because the header `shop-domain` is never included in the signed bytes, any body+HMAC pair generated by Shopify for **any** shop (including a shop the attacker legitimately owns/controls, e.g., a free development store) remains valid when replayed with a different `shop-domain` header value. This is the same bug class as the bitcoinj report: bytes are verified (the signature/HMAC is valid), but the verification never checks that the verified bytes are bound to the identity (`shop`) that the caller then trusts.

### Impact Explanation
This crosses a tenant boundary using only the gem's own verification logic: the attacker's genuine, self-obtained webhook payload can be replayed with a forged shop identity, and the app (relying on this gem's `HmacValidator`/`Registry.process` as its sole authentication of the caller) will process it as if it came from the victim's store. For mandatory topics such as `customers/redact`, `customers/data_request`, or `shop/redact` — or any custom handler that keys off `data.shop` to select/act on a tenant's data — this allows an unauthenticated attacker to trigger destructive or data-disclosing actions attributed to an arbitrary victim shop, without ever needing the app's `client_secret`, an access token, or any privileged credential. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high: obtaining one genuine signed webhook body/HMAC pair requires nothing more than installing the target app on a store the attacker controls (a free/dev store is sufficient) and capturing any delivered webhook. Replaying it with a modified `X-Shopify-Shop-Domain`/`shopify-shop-domain` header requires only a basic HTTP client — no cryptography needs to be broken since the header is simply outside the signed scope.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the authenticated material, e.g., include the `shop-domain` header value in the string that is HMAC-verified, or require the host application to cross-check `request.shop` against an out-of-band trusted value (such as the shop associated with the webhook subscription looked up via the Admin API) before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any subscribed topic (e.g., `customers/data_request`) so Shopify delivers a genuine webhook to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: customers/data_request`, and body `B`.
2. Capture the raw body `B` and the `X-Shopify-Hmac-Sha256` value.
3. Resend an HTTP POST to the same webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches the attacker's original valid HMAC, and passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`) dispatches to the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act as though the request genuinely originated from `victim-shop.myshopify.com`.
