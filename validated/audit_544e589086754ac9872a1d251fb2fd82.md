### Title
JWT session token binds `shop` to the unauthenticated `dest` claim instead of the verified `iss` claim - (File: `lib/shopify_api/auth/jwt_payload.rb`)

### Summary
`JwtPayload` decodes and signature-verifies a Shopify session token, but the identity used everywhere downstream (`shop`/`shopify_domain`, and therefore the session id) is derived from the `dest` claim, while the only claim actually checked against a fixed expectation is `aud` and the format of `iss`. `dest` and `iss` are never cross-checked against each other, breaking the intended binding `shop(from dest) == shop(from iss)`.

### Finding Description
`JwtPayload#initialize` verifies the token signature and enforces `@aud == Context.api_key`, and separately requires `admin_session_token?` (i.e. `iss` ends with `/admin`) is used elsewhere, but never asserts that `dest` and `iss` reference the same shop domain: [1](#0-0) 

`shop` — the value used to build the session id via `SessionUtils.session_id_from_shopify_id_token` / `jwt_session_id` / `offline_session_id` — is taken solely from `dest`: [2](#0-1) 

This value flows directly into session lookup/derivation: [3](#0-2) 

The intended binding is `dest == iss` (Shopify's own token issuance guarantees this under normal operation), but the gem does not enforce it. Any code path that accepts a session token from a different origin than the `iss`-derived shop (e.g., a token where `dest` and `iss` disagree, which can occur if a party in possession of *any* validly-signed token for the configured `api_key`/`api_secret_key` supplies a modified but still-passes-signature token — or more realistically, if `iss` verification is dropped/absent while only `dest` drives shop identity) results in the session being keyed to the wrong shop. Since `aud` is the only claim tied to app identity, and `iss`/`dest` consistency is never checked, the "authenticated shop" (`iss`) and the "shop the library treats as the session owner" (`dest`) are not proven equal.

### Impact Explanation
If `dest` can diverge from `iss` for a token that still satisfies `aud == Context.api_key`, `SessionUtils.current_session_id` / `session_id_from_shopify_id_token` will compute a session id (`"#{shop}_#{sub}"` or `"offline_#{shop}"`) for a shop that was not actually the token issuer. This lets the session-loading logic in a host app resolve to another merchant's session — a cross-tenant session confusion, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
The signature check (`aud`) does protect against fully forged tokens signed with an unknown secret, so this is not exploitable with an entirely attacker-crafted token from scratch. It requires a scenario where a `dest`/`iss` mismatch is possible for a signature that verifies under the app's own `api_secret_key`/`old_api_secret_key` — i.e., malformed or manipulated tokens issued/relayed through legitimate flows without the library asserting `iss == "https://#{dest}/admin"`. Likelihood is therefore Low/Medium: it depends on a token whose `dest` and `iss` are inconsistent still passing the app's signature check, but the missing invariant is a clear root-cause gap distinct from `aud` validation.

### Recommendation
In `JwtPayload#initialize`, after decoding, assert that `dest` and `iss` refer to the same shop, e.g.:
```ruby
raise ShopifyAPI::Errors::InvalidJwtTokenError, "JWT dest does not match iss" unless
  @iss == "https://#{@dest.gsub('https://', '')}/admin"
```
This makes `shop` provably bound to the verified issuer rather than to an independently-trusted `dest` claim.

### Proof of Concept
Not exploitable end-to-end without a token whose signature verifies yet whose `dest` and `iss` disagree; the report is a structural analog (missing invariant check) rather than a demonstrated forgery, consistent with the missing cross-check shown at [4](#0-3) .
