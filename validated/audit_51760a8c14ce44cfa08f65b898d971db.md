### Title
Cross-chain replay of Hyper Fungible Token calldata authorization signatures leads to unauthorized arbitrary runtime call dispatch - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `on_accept` handler of the `hyper-fungible-token` pallet lets an incoming, permissionlessly-relayed ISMP `PostRequest` carry an optional SCALE-encoded `runtime_call` that is dispatched with `Signed` origin on the destination chain, authorized by a lightweight custom signature scheme with no chain/domain binding. Because the signed payload is only `(nonce, runtime_call).encode()`, a signature a user produces to authorize one call can be replayed by anyone to dispatch a different, unintended call against the same account on another chain (or context) that happens to share the same nonce, achieving unauthorized code execution analogous to the RCE class of CVE-2018-8327 (untrusted payload processed into unauthorized execution).

### Finding Description
`on_accept` decodes the ABI `Message` from an arbitrary relayed POST request and, if `message.data` is non-empty, decodes a `SubstrateCalldata{ signature, runtime_call }` and dispatches `runtime_call` with `RawOrigin::Signed(origin)`: [1](#0-0) 

When a signature is present, verification is performed only against the raw keccak256 hash of `(nonce, runtime_call).encode()` — there is no genesis hash, spec version, chain id, `consensus_state_id`, or pallet/asset-specific domain tag mixed into the signed message: [2](#0-1) 

The `nonce` used is simply the current system account nonce of the beneficiary (`frame_system::Pallet::<T>::account_nonce(beneficiary)`), which is a chain-local, pallet-agnostic counter shared by every extrinsic/dispatch the account ever makes, not a value scoped to this bridging flow: [3](#0-2) 

Standard Substrate extrinsics avoid this class of bug by including `CheckGenesis`/`CheckSpecVersion`/`CheckTxVersion` signed extensions so a signature can never be replayed on a different chain or runtime version. This pallet's bespoke meta-transaction-style signature has none of that binding — only `(nonce, runtime_call)` is signed. Any two chains (or two points in time on chains with resettable/duplicate nonces, e.g. freshly funded accounts, migrated/forked chains, or a second deployment of this pallet for a different asset) where the same `AccountId` has the same current nonce will accept a signature that was produced to authorize a specific `runtime_call` byte string for one purpose, letting the identical bytes decode into a different dispatchable elsewhere (because pallet/call indices differ across runtimes), or simply be recycled to force execution the signer did not intend at relay time, since delivery is fully permissionless and controlled by the untrusted relayer/message path.

### Impact Explanation
Successful replay causes an arbitrary `RuntimeCall` — filtered only by `BaseCallFilter`, not scoped to any bridge-specific safe subset — to execute with `Signed` origin as the victim account: [4](#0-3) 
This is unauthorized app/account action performed on behalf of a user without their consent for that specific context, potentially transferring funds, altering governance votes, or triggering any other privileged extrinsic reachable from a `Signed` origin — a critical "unauthorized app action" outcome directly in Hyperbridge's threat model (comparable to remote/unauthorized code execution via a data path that a message relayer, an inherently untrusted role, can reach with a single relayed request).

### Likelihood Explanation
The `on_accept` call path is reachable by any relayer delivering any POST request whose source contract is registered in `ContractToAsset`, i.e., any legitimate HFT bridge deployment; no privileged role is required to relay a captured/authorized message payload. The precondition (matching nonce/account across contexts) narrows exploitation to specific setups (e.g., multiple deployments of this pallet, chain forks/resets, or freshly-created accounts at nonce 0 on multiple chains using the same keypair), so likelihood is moderate rather than trivially universal, but the missing domain separation is a real, concrete protocol design gap rather than a purely theoretical one.

### Recommendation
Bind the signed payload to protocol-specific and chain-specific context before hashing, e.g. include the destination `StateMachine`/`consensus_state_id`, genesis hash, local asset id, and the pallet's own name/version in the signed preimage (`(genesis_hash, chain_state_machine, asset_id, nonce, runtime_call).encode()`), and/or maintain a dedicated nonce/replay-protection map keyed by `(AccountId, source_chain, asset_id)` instead of reusing the shared `frame_system` account nonce.

### Proof of Concept
1. Deploy the `hyper-fungible-token` pallet on two chains (or two independent instances/assets) such that account `A` has nonce `0` on both.
2. User `A` legitimately signs `(0u32, call_bytes).encode()` off-chain to authorize `call_bytes` (decodes to an intended, benign call, e.g. `System::remark`) via a cross-chain transfer message on Chain 1.
3. An observer captures the ABI-encoded `Message.data` (`SubstrateCalldata{ signature, runtime_call: call_bytes }`) from the relayed transaction/mempool.
4. The observer relays an equivalent POST request (with the same `to`/beneficiary bytes producing the same `AccountId`, and the same `data`) to Chain 2, where `call_bytes` decodes (due to different pallet/call indices) into a different, higher-privilege dispatchable.
5. `on_accept` on Chain 2 verifies the signature successfully (same nonce, same signed bytes) at `modules/pallets/hyper-fungible-token/src/module.rs:128-153` and dispatches the reinterpreted call as `Signed(A)` at lines 189-202, executing an action `A` never authorized on Chain 2.
