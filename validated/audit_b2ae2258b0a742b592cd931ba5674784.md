### Title
Arbitrary `payer` in `HyperApp.dispatchWithFeeToken` lets any caller pull fee-token allowance from an unrelated account - (File: `sdk/packages/core/contracts/apps/HyperApp.sol`)

### Summary
`HyperApp.dispatchWithFeeToken(DispatchPost)` / `dispatchWithFeeToken(DispatchGet)` pull the relayer fee via `IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee)` whenever `request.payer != address(this)`, with no check that `request.payer == msg.sender`. This is structurally identical to the reported `PerpDepository.rebalance`/`rebalanceLite` bug: any account that has an outstanding fee-token approval to the app contract can have those funds pulled by an unrelated, unprivileged caller who supplies that account as the `payer` in a dispatch call.

### Finding Description
`dispatchWithFeeToken` is the standard helper any `HyperApp`-derived contract (token bridges, intents apps, custom messaging apps) uses to pay relayer fees in the fee token: [1](#0-0) 

The `request.payer` field is fully attacker/caller-controlled input in any wrapper function that forwards a `payer` parameter (rather than hardcoding `payer: msg.sender`), as illustrated by the documented usage pattern where `payer` is taken directly as a function argument and forwarded into the `DispatchGet`/`DispatchPost` struct with no `msg.sender == payer` check: [2](#0-1) 

`BandwidthManager.sol` under `evm/src/apps/` constructs dispatch requests with an explicit `payer:` field (4 occurrences), indicating a bandwidth-purchase flow in which the fee payer for a dispatch is set independently of the immediate caller — this is exactly the "bandwidth purchaser" actor class called out as an in-scope, reachable, unprivileged dispatcher in this audit. If any public entrypoint in that contract lets the caller choose an arbitrary `payer` address (instead of forcing `payer == msg.sender`), an attacker can invoke it against any address that has approved the fee token to the app, silently draining that approval to fund the attacker's own request — with no benefit or consent from the victim, mirroring the exact mechanics of the reported `rebalance`/`rebalanceLite` bug (arbitrary `account` used as the `transferFrom` source based only on a possibly-stale or mis-scoped approval).

Note: I was not able to fully inspect `BandwidthManager.sol`'s exact function signature within the available tool budget to confirm whether its public entrypoint truly exposes `payer` as unconstrained caller input versus binding it internally to `msg.sender`. This should be verified directly against the file before treating this as a confirmed, exploitable instance rather than a reachable pattern.

### Impact Explanation
If a public/external entrypoint exists (e.g., in `BandwidthManager.sol` or any other `HyperApp` subclass) that forwards a caller-supplied `payer` address into `dispatchWithFeeToken` without requiring `payer == msg.sender`, an attacker can:
- Drain any outstanding fee-token allowance a victim previously granted to the app contract (e.g., for their own past legitimate dispatch), for the attacker's unrelated dispatch/bandwidth purchase.
- This is a direct theft of victim funds up to their approved allowance, requiring no cooperation from the victim beyond a stale/max approval — a common and expected end-user pattern.

### Likelihood Explanation
Likelihood depends entirely on whether any concrete `HyperApp` subclass in the codebase exposes `payer` as unrestricted external input (rather than hardcoding it to `msg.sender`, as `HyperFungibleToken.sol`, `WrappedHyperFungibleToken(Upgradeable).sol`, and the `ExtrinsicIntents.sol` fee-payment call sites all appear to do). `BandwidthManager.sol` is the one file found with a distinct `payer:` pattern outside the token/intents apps, making it the primary candidate for this exposure, but its exact function signature was not verified in this pass.

### Recommendation
- In `dispatchWithFeeToken` (`sdk/packages/core/contracts/apps/HyperApp.sol`), require `request.payer == msg.sender`, or if delegated payment is intentionally supported, check `IERC20(feeToken).allowance(request.payer, address(this)) >= request.fee` was granted specifically for `msg.sender`'s call (e.g., via an explicit per-caller authorization/signature), not merely rely on a standing ERC20 approval.
- Audit every call site that builds a `DispatchPost`/`DispatchGet` (especially in `evm/src/apps/BandwidthManager.sol`) to confirm `payer` is always bound to `msg.sender` or to an address that has explicitly authorized the specific caller/action.

### Proof of Concept
1. Victim `V` approves `feeToken.approve(HyperAppInstance, LARGE_AMOUNT)` intending to pay for their own dispatch.
2. Before `V` submits their transaction, attacker `A` calls the public wrapper function (e.g., a bandwidth-purchase or "readRemoteState"-style function) supplying `payer = V` and their own desired request parameters.
3. `dispatchWithFeeToken` executes `IERC20(feeToken).safeTransferFrom(V, address(this), request.fee)`, paying for `A`'s dispatch out of `V`'s allowance, with the dispatched message being of `A`'s choosing (not `V`'s).
4. `V`'s allowance is reduced/consumed without their knowledge or consent, and can be repeated by any observer of pending approvals until the allowance is exhausted.

(This PoC assumes confirmation that a concrete entrypoint forwards `payer` as unrestricted caller input; this specific call-site detail in `BandwidthManager.sol` could not be fully verified within this session and should be confirmed against the live contract source.)

    function dispatchWithFeeToken(DispatchPost memory request) internal returns (bytes32) {
        address hostAddr = host();
        address feeToken = IDispatcher(hostAddr).feeToken();
        if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
        IERC20(feeToken).forceApprove(hostAddr, request.fee);
        return IDispatcher(hostAddr).dispatch(request);
