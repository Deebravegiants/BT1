## Analog Vulnerability Found

### Title
LDAP Authentication Bypass via Empty Password in `CreateSession` - (File: `core/sessions/ldapauth/ldap.go`)

### Summary
The chainlink LDAP authentication provider forwards a user-supplied password directly into an LDAP simple bind without ever verifying that the password is a non-empty string. This reproduces the exact bug class described in the reported Parse Server CVE (RFC 4513 §5.1.2 unauthenticated bind): an empty-string bind is treated by many directories (e.g., Active Directory default config) as an anonymous/unauthenticated success, letting an unauthenticated client obtain a valid Chainlink session for any known email/uid.

### Finding Description
The public, unauthenticated session-creation route binds a client-controlled JSON body directly to `sessions.SessionRequest`: [1](#0-0) 

Neither `Email` nor `Password` carries a `binding:"required"` tag, so a request body such as `{"email":"victim@example.com","password":""}` binds successfully with `Password == ""`.

This request reaches the internet-facing route: [2](#0-1) 

which is handled by: [3](#0-2) 

`sc.App.AuthenticationProvider().CreateSession(ctx, sr)` dispatches to the LDAP authenticator when `AuthenticationMethod = ldap` is configured: [4](#0-3) 

The LDAP `CreateSession` implementation forwards `sr.Password` straight to `conn.Bind()` with **no check that the password is non-empty**: [5](#0-4) 

If the directory answers the empty-password (unauthenticated) bind with `err == nil` (RFC 4513 §5.1.2 behavior, default on many AD deployments), the code proceeds to `FindUser` to resolve the role and then persists a fully valid `ldap_sessions` row and returns a session cookie — exactly mirroring the reported CVE's root cause (treating any non-error bind response as proof of authentication). The same missing check exists in the sibling credential-testing path: [6](#0-5) 

By contrast, the local-auth and OIDC-local-fallback paths use bcrypt comparison (`utils.CheckPasswordHash`), which inherently rejects empty passwords against any stored hash, so they are not affected: [7](#0-6) 

### Impact Explanation
When the LDAP authentication adapter is enabled and the backing directory answers unauthenticated simple binds with success (default behavior for many Active Directory configurations), an unauthenticated network client who only knows a valid directory email/uid can obtain a legitimate Chainlink node session cookie and assume that user's role (including Admin, if the target account is a group admin), i.e., full account takeover without any credential.

### Likelihood Explanation
Exploitation requires only knowledge of a target's email and requires no other secret; it's a single unauthenticated HTTP POST to `/sessions` with `"password": ""`. It is gated on the operator having selected the LDAP authentication method and the upstream directory accepting unauthenticated binds (not the OpenLDAP default, but a common AD default), matching the CVE's own caveats.

### Recommendation
In `ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` (`core/sessions/ldapauth/ldap.go`), reject the request before calling `conn.Bind` if the password is empty (or not a non-empty string), mirroring the fix applied upstream in Parse Server 8.6.88 / 9.10.1-alpha.7.

### Proof of Concept
1. Configure the node with `WebServer.AuthenticationMethod = "ldap"` pointed at a directory that accepts unauthenticated simple binds (e.g., default AD).
2. Without any credentials, send:
```
POST /sessions
Content-Type: application/json

{"email":"victim@corp.com","password":""}
```
3. `ldapAuthenticator.CreateSession` calls `conn.Bind(dn, "")`; the directory returns success (unauthenticated bind), `FindUser` resolves victim's role, and a valid session cookie is returned in the response — granting the attacker victim's role without any real credential.

```go
func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}
```
