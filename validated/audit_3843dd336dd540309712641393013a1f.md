### Title
Nil Pointer Dereference / Panic via Unauthenticated `vault.publicKeyGet` Request with Missing `params` - ([File: core/capabilities/vault/gw_handler.go])

### Summary
The Vault gateway handler's `handlePublicKeyGet` function on the node side dereferences `req.Params` without checking for `nil` before calling `json.Unmarshal`. Because `MethodPublicKeyGet` requests are explicitly exempted from authorization (per the gateway's comment "Public key requests don't require authorization"), an unprivileged/unauthenticated client can send a JSON-RPC request with the `params` field omitted (or explicitly `null`), causing the request to be relayed to the node and triggering a Go runtime panic when the node attempts `json.Unmarshal(*req.Params, r)`.

### Finding Description
On the gateway side, `handler.HandleJSONRPCUserMessage` special-cases `vaulttypes.MethodPublicKeyGet` and processes it "right away" without going through `h.requestProcessor.ProcessRequest` (the path that would otherwise validate/require `Params` for other methods, e.g. `processCreateSecretsRequest` checks `if req.Params == nil`). [1](#0-0)  This request is forwarded to nodes unmodified via `newActiveRequest`/gateway connector.

On the node side, `GatewayHandler.HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` directly to `h.handlePublicKeyGet(ctx, gatewayID, req)` with no prior validation of `req.Params`. [2](#0-1) 

`handlePublicKeyGet` then does:
```go
r := &vaultcommon.GetPublicKeyRequest{}
if err := json.Unmarshal(*req.Params, r); err != nil {
```
which unconditionally dereferences `req.Params` (a `*json.RawMessage`). [3](#0-2)  If the incoming JSON-RPC request omits the `params` field, `req.Params` is `nil`, and `*req.Params` causes a nil pointer dereference panic — directly analogous to the Istio CVE-2019-25014 pattern where an HTTP GET request missing an expected value led to a nil pointer dereference in an unauthenticated pilot debug endpoint.

Other Vault handler paths (e.g. `processCreateSecretsRequest`) explicitly guard against nil params: `if req.Params == nil { return nil, InvalidVaultParamsError{...} }`, [4](#0-3)  confirming that the `MethodPublicKeyGet` path is missing this same protection specifically because it bypasses `ProcessRequest` entirely.

### Impact Explanation
If the node process panics without protective recovery middleware around `HandleGatewayMessage`, this results in denial of service to the node's Vault capability handling (or potentially the whole node process, depending on goroutine recovery behavior in the connector). Because `MethodPublicKeyGet` explicitly requires no authorization, this is reachable by any unprivileged actor able to reach the gateway's public HTTP endpoint.

### Likelihood Explanation
High likelihood of reachability: the request path requires no credentials, no allowlisting, and no valid signature — only a well-formed JSON-RPC envelope with `method: "vault.publicKeyGet"` and `params` omitted or `null`. [5](#0-4) 

### Recommendation
Add an explicit nil-check on `req.Params` in `handlePublicKeyGet` (core/capabilities/vault/gw_handler.go) before dereferencing, returning a structured JSON-RPC error (e.g. `api.UserMessageParseError`) instead of panicking, consistent with the guard already present in `processCreateSecretsRequest`. Additionally, verify a panic-recovery wrapper exists around `HandleGatewayMessage`/`HandleJSONRPCUserMessage` dispatch to prevent a single malformed unauthenticated request from crashing the node/gateway process.

### Proof of Concept
An unprivileged client sends the following JSON-RPC request to the gateway's public HTTP endpoint (no signature/auth required, since `MethodPublicKeyGet` bypasses the authorization pipeline):
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault.publicKeyGet"}
```
Note the `params` field is entirely omitted. The gateway forwards this to a node (since it isn't cached), and the node's `handlePublicKeyGet` executes `json.Unmarshal(*req.Params, r)` against a nil `*json.RawMessage`, panicking with a nil pointer dereference. [3](#0-2)
