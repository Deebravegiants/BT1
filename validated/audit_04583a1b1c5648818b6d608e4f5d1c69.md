### Title
Missing fee-exceeds-amount check in `createWithdrawalIntents` allows negative withdrawal amount when caller supplies stale/independent fee estimation - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents()` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` for fee-inclusive withdrawals without first checking that `amount > feeEstimation.amount`, unlike its sibling `_estimateWithdrawalFee()` which explicitly guards this subtraction.

### Finding Description
In `_estimateWithdrawalFee`, the SDK subtracts the fee from the withdrawal amount only after validating the amount is large enough: [1](#0-0) 

```
if (args.withdrawalParams.feeInclusive) {
    if (args.withdrawalParams.amount <= fee.amount) {
        throw new FeeExceedsAmountError(fee, args.withdrawalParams.amount);
    }
}
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - fee.amount
    : args.withdrawalParams.amount;
```

`createWithdrawalIntents`, however, performs the identical subtraction without this equality/bound check: [2](#0-1) 

The doc-comment of `deriveOmniWithdrawIntentParams` explicitly acknowledges this asymmetry: *"`actualAmount` Net of `feeEstimation.amount`. `IntentsSDK` subtracts it for a fee-inclusive withdrawal, so a caller that builds the payload itself has to do the same"* [3](#0-2)  — i.e. `createWithdrawalIntents` is a public API entry point that is expected to be called with an independently-obtained `feeEstimation` (e.g., a cached one from an earlier `estimateWithdrawalFee` call, or one supplied by an integrator/relayer), and no re-validation is performed that `feeEstimation.amount < withdrawalParams.amount` at this second call site.

If `feeEstimation.amount >= withdrawalParams.amount` (e.g., because market conditions changed between an earlier quote and this call, or because a caller wires in a fee estimation from a different route/asset), `actualAmount` becomes zero or negative. This is passed straight into `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`.

### Impact Explanation
This does not directly cause fund loss in the way a Solidity `uint` underflow would (bigint negative values do not wrap to `2^256-1`), but it breaks the intended equality "amount debited == requested amount minus fee, and that difference must be positive." Downstream bridge-specific `validateWithdrawal`/`createWithdrawalIntents` implementations are not guaranteed to re-check for a negative or zero actual amount before serializing it (e.g., via `actualAmount.toString()`) into transfer intents such as `ft_withdraw`/`token_diff`, and the built intent message would not match what the caller intended to debit. Whether this manifests as an outright contract-level revert (safe) or a mis-encoded amount depends on route-specific code paths that were not fully verifiable within the scoped review.

### Likelihood Explanation
Low-to-moderate. It requires a caller to invoke `createWithdrawalIntents` with a `feeEstimation` whose `amount` is stale or otherwise inconsistent with the `withdrawalParams.amount` at call time — a scenario acknowledged as valid usage by the SDK's own documentation (callers are expected to supply their own fee estimation for a "fee-inclusive withdrawal"), but not defended against with the same check present in `_estimateWithdrawalFee`.

### Recommendation
Add the same `FeeExceedsAmountError` guard used in `_estimateWithdrawalFee` to `createWithdrawalIntents` before computing `actualAmount`, so a stale or inconsistent `feeEstimation` cannot produce a zero/negative debited amount:
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
    throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```

### Proof of Concept
1. Call `sdk.estimateWithdrawalFee({ withdrawalParams: { amount: 1000n, feeInclusive: true, ... } })` and obtain `feeEstimation.amount = 900n`.
2. Wait until market/route conditions change such that a fair fee would now be `>= 1000n` (or simply pass a `feeEstimation` for a similar asset/route with a larger fee).
3. Call `sdk.createWithdrawalIntents({ withdrawalParams: { amount: 1000n, feeInclusive: true, ... }, feeEstimation })` directly — unlike `estimateWithdrawalFee`, this path performs no `amount <= feeEstimation.amount` check [4](#0-3) , so `actualAmount` becomes `1000n - 1000n = 0n` or negative, and is forwarded unchecked into `bridge.validateWithdrawal`/`bridge.createWithdrawalIntents`.

I could not fully verify, within the reviewed scope, whether every bridge's `createWithdrawalIntents` implementation independently re-validates `amount > 0` before serialization, so the ultimate observable effect (hard revert vs. malformed intent) is not fully confirmed from the code paths inspected.
