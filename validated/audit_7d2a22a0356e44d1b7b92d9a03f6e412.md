### Title
Webhook tenant identity (shop-domain/topic/webhook-id) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` checks the HMAC exclusively against that body using the app's single, shop-independent `client_secret`. The `shop`, `topic`, `webhook_id`, and `api_version` fields — read from HTTP headers — are never included in the signed content, yet `ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as authorization to trust and act on those header values, including passing `request.shop` to the app's handler as the authenticated tenant identity.

### Finding Description
The intended identity binding is: `hmac == HMAC(client_secret, body || shop || topic || webhook_id)`, i.e., the cryptographic proof should cover every field the app relies on to route and process the webhook. Instead the binding actually enforced is `hmac == HMAC(client_secret, body)` only [1](#0-0) [4](#0-3) .

Because the app's `client_secret` (and thus the HMAC key) is identical for every shop that has installed the app, any two webhook deliveries whose bodies are byte-identical (e.g., topics with an empty `{}` payload, or any topic where two different shops produce the same JSON payload) will produce the identical valid HMAC regardless of which shop or topic header is attached. `Registry.process` calls `Utils::HmacValidator.validate(request)` — checking body-only integrity — and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all parsed straight out of attacker-controllable headers, before or without any header-body binding) to build `WebhookMetadata` and dispatch to the registered handler [3](#0-2) . The `shop-domain`/`topic`/`webhook-id` headers are read via `shopify_header`, with no linkage back to the signed bytes [5](#0-4) .

This is the same bug class as the reported analog: a value that is acted upon (the tenant/topic identity) is not covered by the authenticating MAC, so the "verified" bytes (body) and the "trusted" bytes (headers) diverge.

### Impact Explanation
An attacker who legitimately controls one shop that has the vulnerable app installed can capture a genuine webhook delivery for that shop (body + valid `x-shopify-hmac-sha256` value, both fully within the attacker's control as the shop owner triggering their own webhook events) and replay the same body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and, if useful, `x-shopify-topic`) to target a different tenant shop. Since only the body is authenticated, the forged request passes `HmacValidator.validate` and is processed by the handler under the impersonated shop's identity — a cross-tenant access/impersonation via the app's own webhook processing path, using no leaked credentials and no access to the victim shop.

### Likelihood Explanation
Exploitation requires only that the attacker operate (or briefly install the app on) one Shopify store — a normal, low-privilege action — and that the app registers at least one topic whose legitimate body content is shop-independent or predictable (mandatory topics such as `customers/redact`, `shop/redact`, `customers/data_request`, or any topic with sparse/empty payloads are common). No secret material, TLS interception, or social engineering is needed, only a normal HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the tenant/topic identity into the authenticated bytes: verify webhooks the way Shopify's other client libraries do (compute HMAC over the body as delivered, but additionally require that shop-domain corresponds to a shop the app has an active session/installation for, or better, include `shop`, `topic`, and `webhook_id` headers in the signable string / cross-check them against a per-shop registration record) before dispatching to handlers. At minimum, `Registry.process` should reject webhooks whose `shop` does not correspond to a known, currently-installed shop, rather than trusting the header unconditionally once the body-only HMAC passes.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger (or wait for) a webhook delivery for a registered topic with a predictable/empty body, e.g. `customers/data_request` with body `{}`; capture the raw POST body and its `x-shopify-hmac-sha256` header value — both valid against the app's single `client_secret`.
3. Send a forged POST to the app's webhook endpoint reusing the captured body and HMAC header unchanged, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: customers/data_request`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `body` against the shared `client_secret` [6](#0-5) ; the handler is then invoked with `shop: "victim.myshopify.com"` [7](#0-6) , causing the app to act (e.g., purge/redact data, log an event, trigger downstream side effects) against the victim tenant based on an unauthenticated header value.
