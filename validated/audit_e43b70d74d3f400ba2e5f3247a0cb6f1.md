Audit Report

## Title
Cross-Workflow Response Cache Confusion in Gateway HTTP Action Handler - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The `responseCache` in the HTTP Handlers V2 gateway component keys cached HTTP Action responses by `OutboundHTTPRequest.Hash()`, and the repository's own test suite confirms that `Hash()` does not incorporate `WorkflowID`, contradicting the documented "Workflow Isolation" guarantee. As a result, two distinct workflows belonging to the same `WorkflowOwner` that issue an identical outbound HTTP request (same method/URL/headers/body) will collide on the same cache entry and can read/write each other's cached responses.

## Finding Description
The README for this component explicitly states the intended security property: cache entries are "scoped by workflow ID to prevent cross-workflow data leakage" [1](#0-0) . The `responseCache` struct's own doc comment says the cache key is derived from "(method, URL, headers, body, workflowOwner)" — notably omitting `workflowID` [2](#0-1) .

Both `Fetch` and `Set` use `req.Hash()` directly as the map key with no additional workflow-scoping applied at the cache layer [3](#0-2) .

The local test file `response_cache_test.go` directly demonstrates the root cause: `TestRequestHash`'s subtest "having different workflowID results in same Hash" asserts `require.Equal(t, hash1, hash2, ...)` for two requests differing only in `WorkflowID`, while a subsequent subtest confirms differing `WorkflowOwner` values do produce different hashes [4](#0-3) . This test is part of the actual codebase (not a hypothetical), and it locks in the exact behavior described in the claim — the `Hash()` implementation (defined in the `gateway_common` package imported as `github.com/smartcontractkit/chainlink-common/pkg/types/gateway`, referenced from `http_handler.go`) omits `WorkflowID` from the hash inputs, while `WorkflowOwner` is included.

There is no additional workflow-ID-based namespacing anywhere in `Fetch`/`Set` to compensate for this gap — the cache map is keyed solely by the string returned from `req.Hash()`. This breaks the documented workflow-isolation invariant: any two workflows under the same owner making byte-identical outbound HTTP requests will share a cache slot.

## Impact Explanation
This maps to the in-scope "cross-user response corruption" impact class. A workflow can receive an HTTP Action response (status code and body) that was actually fetched/cached on behalf of a sibling workflow owned by the same tenant. This undermines the explicitly documented "Workflow Isolation" security property of the response cache and can propagate stale, wrong, or cross-context data into a workflow's execution logic, particularly since caching TTLs default to 10 minutes and caching is enabled per-request via `CacheSettings.Store`/`MaxAgeMs`.

## Likelihood Explanation
This does not require a malicious actor — it is triggerable by ordinary use: any tenant/owner running two or more workflows that call the same external endpoint with an identical request shape (method, URL, headers, body) and opt into caching will experience the collision. This is a plausible, realistic pattern for reused static GET-style HTTP Actions across a tenant's multiple automations, and is fully reproducible with a Go unit test, as evidenced by the existing `TestRequestHash` test which already documents the exact behavior.

## Recommendation
Incorporate `WorkflowID` into the `Hash()` computation of `OutboundHTTPRequest` (in the `chainlink-common` `types/gateway` package) so cache keys are truly scoped per workflow as documented, not merely per owner. Update the `TestRequestHash` expectations in `response_cache_test.go` to require different hashes for different `WorkflowID`, and verify no other cache-key derivation paths in `responseCache.Fetch`/`Set` bypass this.

## Proof of Concept
1. Construct `req1 := OutboundHTTPRequest{Method: "GET", URL: "https://example.com", WorkflowOwner: "0xOwner", WorkflowID: "wf-A"}` and `req2` identical except `WorkflowID: "wf-B"`.
2. Call `req1.Hash()` and `req2.Hash()` — per the existing `TestRequestHash` subtest "having different workflowID results in same Hash", both return the same value [5](#0-4) .
3. Call `responseCache.Set(req1, respA)`, then `responseCache.Fetch(ctx, req2, fetchFn, true)` with `req2.CacheSettings.MaxAgeMs > 0` — this returns `respA` (workflow A's cached response) for workflow B's request, since `Fetch`/`Set` key exclusively on `req.Hash()` [6](#0-5) .

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
