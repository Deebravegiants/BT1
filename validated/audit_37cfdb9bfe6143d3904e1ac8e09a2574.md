### Title
Webhook shop-domain identity spoofing due to HMAC not covering the `shop` field used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `HmacValidator.validate` verify only the raw HTTP body of an inbound webhook. The `shop` (tenant identifier), `topic`, `webhook_id`, and `api_version` values are all read from HTTP headers that are never included in the signed content, so an attacker with a genuine (validly-signed) webhook body can replay it with an arbitrary `shop-domain` header and have it pass HMAC validation.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the received HMAC [3](#0-2) . For webhook requests, `to_signable_string` returns only `@raw_body` [4](#0-3) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from headers, independent of the signed body [5](#0-4) .

`Registry.process` trusts these header-derived values directly to build the `WebhookMetadata` passed to the app's handler once HMAC validation of the body succeeds: [6](#0-5) 

The identity binding that should hold is: `shop value cryptographically bound in the signed payload == shop value the handler acts on`. In this gem, the right-hand side (`request.shop`, header-derived) is never present on the left-hand side (`request.to_signable_string`, body-only) — the equality is not enforced at all for the `shop` field. Any party who can obtain one genuine webhook delivery for their own store (which any merchant installing the app receives, and can log/replay from their own webhook endpoint or capture via a proxy) has a validly-HMAC'd raw body they fully control the header context for. They can resend that exact body to the app's public webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` still succeeds because it only checks the body bytes against the secret, and `Registry.process` proceeds to invoke the app's handler with `request.shop` set to the attacker-chosen victim domain, per the documented usage pattern where `data.shop` is used directly to route/attribute the webhook payload to a tenant record [7](#0-6) .

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via `WebhookMetadata#shop`. A host application following the documented pattern (using `data.shop` as the lookup/attribution key for the tenant, as shown in the gem's own webhook doc) can be made to associate a spoofed shop's identifier with data controlled by the attacker's own real, validly-signed webhook, resulting in cross-tenant data injection into another merchant's records — one of the explicitly in-scope Critical impacts (cross-tenant access).

### Likelihood Explanation
The attacker only needs to be a normal, unprivileged merchant/user with the app installed on their own store (no `api_secret_key`, no access token, no privileged account required) — they only need to capture one legitimately delivered webhook (any topic) to their own endpoint, since Shopify itself computes and sends that valid HMAC. Header manipulation on a replayed HTTP request requires no special access. The vulnerable code path (`Registry.process` / `HmacValidator.validate` / `Request#shop`) is exercised on every webhook processed by any app using this gem's documented webhook flow.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) header values into the HMAC-verified signable content, or otherwise cryptographically tie the header claims to the signed body (e.g., include them in `to_signable_string`, or require the host app to independently verify `data.shop` against a known-installed-shop registry before trusting it for tenant attribution). At minimum, update documentation to warn that `data.shop`/`data.topic` are not covered by the HMAC and must not be trusted for tenant routing without independent verification (e.g., cross-checking against the shop associated with a previously stored session/access token).

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (a normal, legitimate merchant install — no special privilege).
2. Attacker triggers or waits for a real webhook, e.g. `orders/create`, and captures the raw request Shopify sends to the app's webhook endpoint, including headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` header to the same webhook endpoint, but replaces the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `victim.myshopify.com` [8](#0-7) .
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only compares against `raw_body` [9](#0-8) .
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: request.parsed_body, ...)` [10](#0-9) , causing the host application (following the gem's documented pattern of using `data.shop`) to attribute the attacker's forged order data to the victim's tenant.
