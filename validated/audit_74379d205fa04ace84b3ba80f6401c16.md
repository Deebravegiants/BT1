### Title
`flatFee` cap check in `verifyWallet` is a single scalar comparison but `payRelayFees` pays `flatFee` once per matching `feeToken` index, letting an attacker duplicate the fee-token entry in `circomData.erc20TokenAddresses` to drain a signer's `HinkalWallet` beyond the EIP-712 signed `maxFee` - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The wallet owner's EIP-712 signature over an `EmporiumStack` only binds `ops`, `maxFee`, `deadline` and `emporiumMessage`; it never binds `circomData.erc20TokenAddresses`, `circomData.feeStructure`, or `deltaAmountChanges`, all of which are supplied fresh by the calling prover on every `transact`. `verifyWallet` checks `feeStructure.flatFee > stack.maxFee` exactly once, but `payRelayFees` iterates over every index of `circomData.erc20TokenAddresses` and calls `sendToRelayFromWallet` (drawing from the victim's `HinkalWallet`) for every index whose token equals `feeStructure.feeToken` and has a negative `deltaAmountChanges[i]`. If the prover duplicates the fee-token address across multiple indices, the wallet pays `flatFee` multiple times in one call, exceeding the single-value cap the owner actually signed.

### Finding Description
The claimed equality is: *the total fee charged to the wallet owner's `HinkalWallet` ≤ `stack.maxFee`, as bounded by the owner's signature.*

- `verifyWallet` [1](#0-0)  enforces `feeStructure.flatFee > stack.maxFee → revert` as a single scalar check. The EIP-712 typehash signed by the owner covers only `message, ops, maxFee, deadline` [2](#0-1)  — `feeStructure` and `erc20TokenAddresses` are never part of what is signed.
- `payRelayFees` loops over `circomData.erc20TokenAddresses` (attacker-supplied on every call) and, for every index `i` where `erc20TokenAddresses[i] == feeStructure.feeToken` and `deltaAmountChanges[i] < 0`, sets `flatFee = feeStructure.flatFee` and calls `payRelay(...)`, which for `signerAddress != address(0)` calls `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(...)` [3](#0-2) .
- `HinkalWallet.doSendToRelay` performs no independent cap check; it simply forwards to `sendToRelay` under `onlyEmporium` [4](#0-3) .
- `dimensionsCheck` in `HinkalHelper.sol` only validates array *lengths* against `dimensions.tokenNumber`; it never rejects duplicate token addresses within `erc20TokenAddresses` [5](#0-4) .
- The global per-token balance invariant enforced in `Hinkal.transact` (`balanceDif == amountChanges[i] + utxoAmount`) only constrains the **Emporium/Hinkal contract's own balance**, not the external `HinkalWallet`'s balance [6](#0-5) , so it does not catch or bound the extra funds pulled out of the wallet by repeated `doSendToRelay` calls.

Exploit flow: the attacker (any unprivileged prover) obtains one legitimate `EmporiumStack` signature from a victim wallet owner authorizing some `ops` with `maxFee = flatFee` (i.e., signed to allow exactly one flat fee payment). The attacker then submits `transact` with a `circomData.erc20TokenAddresses` array in which `feeStructure.feeToken` appears at N separate indices, each backed by a small negative `deltaAmountChanges[i]` from the attacker's own valid proof/UTXOs on the Emporium side. `payRelayFees` will then call `sendToRelayFromWallet` N times, draining `flatFee * N` from the victim's `HinkalWallet` to `circomData.relay` in a single call — exceeding the `maxFee` the owner actually signed.

Note: `circomData.relay` itself is separately validated (`relayerIsValid` requires `tx.origin == relay` and that the relay is whitelisted) [7](#0-6) , so the fee cannot be redirected to an arbitrary attacker address — but the *whitelisted relay/relayer* (or a relayer node run by the attacker) still receives more in fees from the wallet than the owner authorized, and the wallet owner's asset movement exceeds their signed terms.

### Impact Explanation
The wallet owner's `HinkalWallet` can be charged `flatFee * N` instead of the single `flatFee` bounded by the signed `maxFee`, for any relay execution the owner authorized. This is unauthorized movement of the wallet owner's assets/fees beyond what their EIP-712 signature permitted, matching the "High - theft or permanent freezing of protocol/relay fees" / "executing calls or moving assets a wallet owner ... never authorised" category. The attack is repeatable on every fresh signed stack the owner produces (bounded by `N` = number of duplicated fee-token indices the attacker can construct, itself limited by dimension/gas limits).

### Likelihood Explanation
Preconditions: attacker needs one valid `EmporiumStack` signature from a victim (obtained through normal usage, e.g., an intercepted or reused authorization for a wallet flow) and the ability to submit their own valid Hinkal proof with `erc20TokenAddresses` containing duplicate fee-token entries — both of which are entirely within an unprivileged attacker's control since `circomData` is freely constructed by the calling prover and only length-checked by `dimensionsCheck`. No privileged role, oracle, or relayer collusion is required (the relay itself only needs to be a legitimately whitelisted relay executing the transaction as usual). This makes the attack low-cost and directly executable by any account holding a signed `EmporiumStack`.

### Recommendation
Bind the total relay fee to the signed cap: either (a) include a hash of `feeStructure`/`erc20TokenAddresses` (or an explicit, signed `maxTotalFee`) in the EIP-712 payload signed by the wallet owner, or (b) track cumulative fee paid from the wallet within `payRelayFees` and revert if the running total across all matched indices exceeds `stack.maxFee`, rather than checking `feeStructure.flatFee` once against `maxFee` before the loop. Additionally, reject duplicate token addresses in `circomData.erc20TokenAddresses` in `dimensionsCheck`, or ensure `feeStructure.feeToken` is charged at most once per transaction regardless of how many indices reference it.

### Proof of Concept
Foundry plan:
1. Deploy `EmporiumUpgradeable`, a `HinkalWallet` for `victim`, and a mock `IHinkalHelper`.
2. `victim` signs an `EmporiumStack` (via `_hashTypedDataV4`/`EMPORIUM_SIGNATURE_TYPEHASH`) with `ops = []` (or a benign op), `maxFee = flatFee` (e.g., 10 units of `feeToken`), `deadline` far in the future.
3. Attacker crafts `circomData` where `erc20TokenAddresses = [feeToken, feeToken, feeToken]` (N=3), `deltaAmountChanges = [-1, -1, -1]` (each individually valid/small), `feeStructure = { feeToken, flatFee: 10, variableRate: 0 }`, `relay` = a whitelisted relay address, `stack.signerAddress = victim wallet`.
4. Fund the victim `HinkalWallet` with `feeToken` (e.g., 100 units).
5. Call `runAction` (via the `onlyAllowedRecipient` path, i.e., through `Hinkal.transact`) with this data.
6. Assert: wallet's `feeToken` balance decreases by `30` (3× `flatFee`), not `10`, i.e., `victimWalletBalanceBefore - victimWalletBalanceAfter > stack.maxFee`, proving the signed cap (`(assets leaving wallet) == maxFee owner signed`) is violated.
