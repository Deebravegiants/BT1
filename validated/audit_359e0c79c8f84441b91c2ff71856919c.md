### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC signature exclusively from the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) fields that `ShopifyAPI::Webhooks::Registry.process` passes on to the app's `WebhookHandler` are read directly from HTTP headers that are never included in the signed content. The equality the gem implicitly claims to enforce — "HMAC-authenticated bytes == the shop this webhook is attributed to" — does not hold, because the `shop-domain` header can be freely modified without invalidating the signature.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [3](#0-2) 

The signable string is only `@raw_body`. `Request#shop` (and `topic`, `api_version`, `webhook_id`) are read from headers via `shopify_header`, entirely outside the signed payload: [4](#0-3) 

`Utils::HmacValidator.validate` only checks that `compute_signature(verifiable_query.to_signable_string, secret)` matches the received signature — i.e. it authenticates the raw body bytes against the app's single, shop-agnostic `api_secret_key`, and says nothing about which shop the body belongs to: [5](#0-4) 

`Registry.process` then trusts `request.shop` as the tenant identifier and hands it straight to the app's handler: [2](#0-1) 

Because the `api_secret_key` is the same for every shop that has installed a given app, any user who can install the app on their own store (an unprivileged, non-victim tenant) can trigger a real Shopify-signed webhook for themselves, capture the `raw_body`/`X-Shopify-Hmac-Sha256` pair, and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to an arbitrary victim shop. `HmacValidator.validate` still returns `true` (the body/secret pair is untouched), so `Registry.process` builds a `WebhookMetadata` claiming the payload belongs to the victim shop: [1](#0-0) 

Any app relying on this gem's webhook verification utility to determine which tenant a webhook body belongs to is therefore trusting a header value that carries no cryptographic binding to the signature that supposedly authenticated the request.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding and yields cross-tenant impact: an attacker (any user who installs the app on any store) can make the app process arbitrary attacker-controlled webhook bodies under a victim shop's identity. Depending on the app's handler logic this can range from data confusion to triggering GDPR-mandatory handlers (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim shop using attacker-forged body content, or injecting fabricated order/customer data attributed to a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high for any app built on this gem's `Webhooks::Registry`/`Request` classes: no access token, API secret, or privileged account is needed — only the ability to install the target app on any (even a free/dev) store to obtain one genuinely signed body/signature pair, then replay it with a modified header, which any unauthenticated HTTP client can do since the webhook endpoint is a public inbound URL.

### Recommendation
Bind the shop (and other header-derived fields the handler relies on) into the signed content, or otherwise cryptographically tie the header value to the specific signature/body combination — e.g. by validating the `shop-domain` header against a shop known to be entitled to the specific `webhook_id`/subscription that produced the signature, or by requiring the caller to prove ownership of the claimed shop through a side channel (verified subscription lookup) before trusting `request.shop` as a tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, uninstalled/free storefront under attacker's control).
2. Attacker triggers a webhook event that produces a body they control (e.g. update a product/order attribute matching the topic they want to abuse), causing Shopify to POST the signed webhook to the app's registered endpoint. Attacker captures `raw_body` and the `X-Shopify-Hmac-Sha256` header from that request (e.g. by intercepting their own traffic or having Shopify deliver it directly to infrastructure they control).
3. Attacker replays that exact `raw_body` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because the signature only ever covered `raw_body`, unaffected by the header change (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31; `lib/shopify_api/webhooks/request.rb` lines 10-38).
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and invokes the app's handler as if the data legitimately originated from the victim shop (`lib/shopify_api/webhooks/registry.rb` lines 188-199).
