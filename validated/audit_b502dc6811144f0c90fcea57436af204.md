Found a valid analog. The LDAP authentication provider in `core/sessions/ldapauth/ldap.go` reproduces the exact root cause of CVE-2018-11407: it forwards a user-supplied password directly into an LDAP simple `Bind()` call without first rejecting empty/null passwords.

### Title
LDAP Authentication Bypass via Empty Password Triggering Unauthenticated Bind - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` pass the client-supplied `sr.Password` / `password` value straight into `conn.Bind(dn, password)` with no check that the password is non-empty. Per LDAP protocol (RFC 4513 §5.1.2 / §6.3.1), a simple bind performed with a non-empty DN but an empty password is defined as an "unauthenticated bind" — most LDAP servers will return success for this bind regardless of whether the supplied DN/username actually exists correctly or matches any real password, since no password verification takes place. This is the identical bug class Symfony fixed in CVE-2018-11407.

### Finding Description
In `CreateSession`, the code builds a DN from the attacker-supplied email and directly calls Bind with the attacker-supplied password, with no guard against an empty string: [1](#0-0) 

The same unguarded pattern exists in `TestPassword`, which is reachable from authenticated password-confirmation endpoints: [2](#0-1) 

Neither function validates `password != ""` before calling `conn.Bind`, unlike Symfony's post-fix LDAP binder which explicitly rejects empty passwords before binding. The request path from an unprivileged, unauthenticated client is: `POST /sessions` → `SessionsController.Create` → `AuthenticationProvider().CreateSession(ctx, sr)` → `ldapAuthenticator.CreateSession`: [3](#0-2) 

If the operator's configured LDAP server permits unauthenticated binds (a common default per RFC 4513, and exactly the misconfiguration scenario the original CVE and Symfony's own advisory describe), an attacker who knows or guesses a valid node-user email can submit that email with an empty password string and have the LDAP `Bind` call return success — bypassing password verification entirely.

### Impact Explanation
A successful bind causes `CreateSession` to proceed to `FindUser`, and on success creates a real `ldap_sessions` row and returns a valid session ID, granting the attacker the full RBAC role of the impersonated user (potentially Admin) with no correct password required. This is a full authentication bypass, matching the CVSS:3.0 C:H/I:H/A:H rating of the original advisory.

### Likelihood Explanation
Exploitability depends entirely on the LDAP server-side configuration allowing unauthenticated/anonymous binds for non-empty DN + empty password, which is a common default behavior unless explicitly hardened (this was precisely the trigger condition documented in Symfony's own CVE-2018-11407 blog post). The chainlink code does nothing to defend against this at the application layer, unlike upstream Symfony's post-patch behavior, which explicitly short-circuits and rejects empty passwords before ever calling Bind.

### Recommendation
Add an explicit check in both `CreateSession` and `TestPassword` in `core/sessions/ldapauth/ldap.go` to reject any request where `sr.Password` (or `password`) is empty/whitespace-only, returning an authentication failure before ever calling `conn.Bind`. This mirrors the fix Symfony applied for CVE-2018-11407.

### Proof of Concept
1. Identify or guess a valid node user's email (e.g., a known admin email as LDAP `uid`).
2. Send `POST /sessions` with body `{"email":"admin@example.com","password":""}`.
3. If the configured LDAP server permits unauthenticated binds (default in many deployments), `conn.Bind(searchBaseDN, "")` in `CreateSession` at `core/sessions/ldapauth/ldap.go:408` succeeds, `FindUser` resolves role/group membership, and a valid session cookie is issued for that user without any correct password having been supplied.
