## Title
Fee-only failed loads charge/cost `RollbackAccounts::data_size()` instead of real bytes touched when `define_ltds_fee_only_semantics` is inactive — ([File: svm/src/account_loader.rs])

## Summary
When a transaction's account loading fails (e.g. `MaxLoadedAccountsDataSizeExceeded`), `load_transaction` in `svm/src/account_loader.rs` reports `loaded_accounts_data_size` for the resulting `TransactionLoadResult::FeesOnly` as either the real accumulated size (`define_ltds_fee_only_semantics` on) or just `tx_details.rollback_accounts.data_size()` — the fee payer/nonce bytes only — when the feature is off. This value is fed directly into `CostModel::calculate_cost_for_executed_transaction` and the block `cost_tracker`, so with the feature disabled the accounted cost for a failed-load transaction can be far smaller than the bytes actually read from accounts-db before the failure was detected.

## Finding Description
`load_transaction` (`svm/src/account_loader.rs:423-472`) computes `loaded_transaction_data_size` incrementally as `load_transaction_accounts` iterates through the message's accounts, failing with `TransactionError::MaxLoadedAccountsDataSizeExceeded` once the running total exceeds the requested/limit-bounded `loaded_accounts_bytes_limit`. On failure it builds a `FeesOnlyTransaction` whose `loaded_accounts_data_size` is:
```
if account_loader.feature_set.define_ltds_fee_only_semantics {
    loaded_transaction_data_size.into()
} else {
    tx_details.rollback_accounts.data_size() as u32
}
```
`RollbackAccounts::data_size()` (`svm/src/rollback_accounts.rs:140-146`) sums only the fee-payer and (if present) nonce account bytes — explicitly noted in-code as legacy: "used internally when calculating the actual loaded transaction data size for the cost model. This function will be removed by the fee-payer data size amendment to SIMD-186."

This reported value is not cosmetic: `create_commit_results` (`runtime/src/bank.rs:4493-4509`) copies it into `CommittedTransaction.loaded_account_stats.loaded_accounts_data_size`, which `get_transaction_costs` (`runtime/src/transaction_execution.rs:171-195`) passes into `CostModel::calculate_cost_for_executed_transaction`, whose `loaded_accounts_data_size_cost` is then added to the bank's `cost_tracker` via `check_block_cost_limits` (`runtime/src/transaction_execution.rs:157-169`) and used identically by banking-stage's `calculate_processed_transaction_costs` (`core/src/banking_stage/consumer.rs:490-520`). An attacker can therefore submit a transaction that: (1) has a tiny fee payer and no nonce, (2) lists many large writable/readable accounts, and (3) is engineered to blow the loaded-accounts-data-size limit or otherwise fail mid-load (e.g. `InvalidProgramForExecution` after loading many accounts). The transaction fails during loading — real bytes have already been fetched from accounts storage for all accounts touched up to the failure point — but with the feature off, only the tiny rollback-account byte count is charged into the cost model, understating the real work performed.

Existing guards do not stop this: transaction signature/lock checks, nonce checks, and fee-payer balance checks all pass normally (the attacker only needs enough lamports for the flat fee); the `MaxLoadedAccountsDataSizeExceeded` check itself is what triggers the FeesOnly path, and it is the very code whose result is discarded for cost-accounting purposes when the feature is off.

## Impact Explanation
This matches the "materially underpriced execution" bounty category: an attacker gets committed, fee-paying transactions whose reported/cost-tracked `loaded_accounts_data_size` is dramatically smaller than actual bytes read from accounts storage. Because the bound on real bytes touched is capped by `loaded_accounts_bytes_limit` (bounded by `MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES`) plus at most one additional oversized account before the incremental check trips, the magnitude of underpricing per transaction is bounded, but it can be repeated across many transactions in a block since each one's cost-tracker contribution is understated, letting an attacker pack more real I/O work into a block than the cost tracker believes it is admitting — a resource-underpricing/DoS-adjacent effect on the transaction cost model, not a bank-hash-affecting cross-cluster divergence (the question's cross-cluster framing is explicitly out of scope and, since feature activation is deterministic per-epoch across the whole cluster, all nodes compute the same understated value consistently — this does not cause consensus divergence by itself).

## Likelihood Explanation
Fully reachable by an unprivileged user submitting ordinary transactions to a public RPC/TPU endpoint; no special privileges are required, only a normal signed transaction with a cheap fee payer and a list of large accounts designed to trip `MaxLoadedAccountsDataSizeExceeded` (or another mid-load failure). It is repeatable per transaction (subject only to the normal one-load-attempt-per-transaction economics: attacker pays the flat/priority fee each time). The condition is fully live **today** if `define_ltds_fee_only_semantics` (SIMD-0186 Amendment) is not yet activated on the target cluster/epoch — this is exactly the legacy branch the code comments say is intended to be removed once that feature activates, indicating the maintainers are aware of the gap and have already implemented (but possibly not yet activated) the fix.

## Recommendation
Activate `define_ltds_fee_only_semantics` cluster-wide (this is the fix already implemented in-repo), and/or remove the legacy `tx_details.rollback_accounts.data_size()` fallback path entirely once the feature is permanently enabled, so `FeesOnlyTransaction::loaded_accounts_data_size` always reflects the actual `loaded_transaction_data_size` accumulated up to the point of failure, matching the invariant asserted by `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs`.

## Proof of Concept
Extend `svm/tests/integration_test.rs::fee_only_loaded_transaction_data_size` (already present at lines 3624-3770) to explicitly assert the invariant violation: with `define_ltds_fee_only_semantics = false`, construct a transaction with a fee payer holding 0 extra data, no nonce, and N large accounts (e.g. 8KB–8MB each) whose cumulative size exceeds `size_limit`, then assert:
```rust
let fail_limit_loaded_size = output.processing_results[1].as_ref().unwrap().loaded_accounts_data_size();
assert!(fail_limit_loaded_size < other_accounts_size); // reported charge understates real bytes touched
```
This mirrors the existing test's own comment ("otherwise it is the raw sum of rollback sizes which here is zero") — i.e., the test file itself already demonstrates `fail_limit_loaded_size == 0` while `other_accounts_size` (real bytes touched before failure) is large, confirming `COST_UPPER_BOUND` is violated whenever `define_ltds_fee_only_semantics` is inactive.
