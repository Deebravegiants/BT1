### Title
HOT Bridge API fallback reports withdrawal as "completed" without checking `verified_withdraw` flag - (File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts)

### Summary
`HotBridge.fetchWithdrawalHashFromApi` parses the HOT API withdrawal response, which explicitly includes a `verified_withdraw: boolean` field per withdrawal record, but never reads or checks this field before returning the withdrawal as `completed`. The status equality that should hold — "report `completed` only if the HOT API/indexer confirms the withdrawal is verified" — is broken because presence of a syntactically valid hex hash is treated as sufficient proof of completion.

### Finding Description
The schema explicitly models `verified_withdraw` as a field returned per-withdrawal: [1](#0-0) 

But in `fetchWithdrawalHashFromApi`, after successfully parsing the response, the code only checks that `withdrawal.hash` is truthy and that it is valid hex — it never inspects `withdrawal.verified_withdraw`: [2](#0-1) 

This function's result is consumed directly by `describeWithdrawal`, which returns `{ status: "completed", txHash: ... }` to the caller as soon as `apiHash` is non-null, in both the EVM/Stellar bridge-indexer-failure fallback path and the "other non-EVM networks" fallback path: [3](#0-2) [4](#0-3) 

The `verified_withdraw` field is clearly meant to gate whether a hash is trustworthy/confirmed (mirrored by the `HotApiWithdrawalSchema` shape used in tests, e.g. `hot-bridge.test.ts`), analogous to the TYPO3 report's pattern where a value intended to gate/validate a request (the jumpUrl hash secret) is present in the response but the validation step that should consult it is skipped or bypassable — here the equality "`status: completed` ⇔ `verified_withdraw === true`" is never enforced; only "`hash` exists and is hex" is checked.

### Impact Explanation
This breaks the equality between the reported on-chain outcome and the SDK's status output: `describeWithdrawal` can report `completed` with a `txHash` for a withdrawal whose HOT-reported `verified_withdraw` is `false`. Integrators typically use `completed` status to finalize accounting (e.g., mark an off-chain balance as settled, release custody, or stop retry/refund flows). A misreport here falls under the rules' explicit High-impact category: "a status or hash misreport making an integrator credit or refund twice." If the withdrawal is later found not to have landed on the destination chain (which `verified_withdraw:false` is presumably signaling), an integrator that already credited the user based on the premature `completed` status has no on-chain guarantee backing that credit.

### Likelihood Explanation
This path only triggers when the primary bridge indexer path fails or is bypassed (EVM/Stellar bridge-indexer-failure fallback, or the "other non-EVM networks" branch when on-chain status is pending/null), which are realistic, reachable conditions since bridge indexer availability is not controlled by the SDK. No malicious actor is required — an ordinary HOT API response with `hash` set but `verified_withdraw:false` (e.g., a provisional/candidate hash before finality) is sufficient to trigger the misreport. This makes it a reachable, no-privilege-required correctness bug rather than a purely theoretical one.

### Recommendation
In `fetchWithdrawalHashFromApi`, only treat a withdrawal as resolvable when `withdrawal.verified_withdraw === true`; otherwise return `null` (keep status `pending`) even if a hex hash is present. Ensure the same check is applied consistently wherever HOT API withdrawal records are consumed for status reporting.

### Proof of Concept
1. Call `describeWithdrawal` for a withdrawal on a non-EVM chain (or EVM chain when the bridge indexer throws).
2. Mock `hotSdk.api.requestApi` to return:
```json
{
  "hash": "abcd1234",
  "nonce": "1",
  "near_trx": "txhash",
  "withdrawals": [
    { "hash": "abcd1234", "nonce": "1", "near_trx": "txhash", "verified_withdraw": false, "chain_id": 56 }
  ]
}
```
3. `describeWithdrawal` returns `{ status: "completed", txHash: "0xabcd1234" }` even though `verified_withdraw` is `false`, despite the API indicating the withdrawal has not been verified.
