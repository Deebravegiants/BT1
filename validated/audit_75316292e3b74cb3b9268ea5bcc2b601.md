### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC-SHA256 signature validated by `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, or `webhook-id` headers. `Registry.process` nevertheless treats `request.shop` as the authoritative tenant identifier and passes it straight into the handler. Because the signature never binds the shop identity to the signed bytes, a request whose body-HMAC is valid for shop A can be replayed unmodified except for the `x-shopify-shop-domain` header, and the library will accept it as belonging to shop B.

### Finding Description
`Request#hmac` / `#to_signable_string` only signs `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers, independent of the HMAC: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body — it never incorporates the shop header: [4](#0-3) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity forwarded to the app's handler: [5](#0-4) 

The broken identity-binding equality is:
`HMAC-verified bytes (raw_body only)` ≠ `tenant identity trusted downstream (request.shop header, unsigned)`

Because Shopify signs HTTP webhooks with a single app-wide secret (`api_secret_key`) shared across every shop that installs the app — not a per-shop key — any account that installs the app on its own store (a free, unprivileged action available to any internet user via the Shopify Partners/App ecosystem) can legitimately trigger a webhook for a topic the app is subscribed to and thereby obtain a body + valid HMAC pair. Nothing in this gem prevents that attacker from replaying the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `Utils::HmacValidator.validate` will still succeed, because the header is not part of the signed content, and `Registry.process` will call the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This crosses a tenant boundary using a signature that this gem itself deems sufficient proof of authenticity. Any host application that keys persistent state, entitlements, or session lookups off `WebhookMetadata#shop` (exactly the intended and documented usage pattern, see `docs/usage/webhooks.md`) can be made to attribute attacker-supplied webhook payloads to an arbitrary victim shop. This matches the Critical "cross-tenant access" impact category — data intended to be scoped to one merchant's session/store can be forced into another merchant's context purely by header manipulation, without possessing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
The only prerequisite is installing the target app on any shop under the attacker's control (a normal, unprivileged, self-service action in the Shopify ecosystem) and being able to POST to the app's public webhook HTTP endpoint — both trivially available to an ordinary internet user. No secret material, session, or elevated privilege is required; only header rewriting of an otherwise-legitimate request.

### Recommendation
Bind the tenant identity into the verified payload instead of trusting unauthenticated headers. Concretely: include `shop-domain` (and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or require the calling application to independently confirm the shop against a value the app itself associates with the raw body (not the header). At minimum, `Request#to_signable_string` should not silently exclude fields (`shop`, `topic`) that `Registry.process` subsequently treats as trusted identity for dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (free, self-service).
2. Attacker triggers a subscribed webhook topic (e.g., `orders/create`) on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it is computed with the app's single, shop-independent `api_secret_key`.
   - Signing surface: [2](#0-1) 
3. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body signature: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` with attacker-controlled body data, even though the request never touched the victim's shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
