### Title
Fee-on-transfer tokens cause escrow over-crediting in `IntentGatewayV2.placeOrder` leading to insolvency/DoS on withdrawal - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, tokens are pulled via `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, but the escrow ledger `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, which is derived from the pre-transfer, user-specified `order.inputs[i].amount` rather than the token balance actually received by the contract. [1](#0-0)  For fee-on-transfer (deflationary) ERC20 tokens, the contract receives strictly less than `order.inputs[i].amount`, yet the escrow accounting records the full pre-fee amount as owed. This is the same root cause identified in the referenced Sherlock report for `Allo._fundPool()`, where `poolAmount` is incremented by the pre-transfer amount instead of the actually-received amount.

### Finding Description
`placeOrder` computes `reducedInputs` (post-protocol-fee amounts) purely from `order.inputs[i].amount`, the value supplied by the caller, before any token transfer occurs: [2](#0-1) 

Then, in the non-predispatch path, it transfers `order.inputs[i].amount` via `safeTransferFrom` and unconditionally credits the escrow with `reducedInputs[i].amount`:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

There is no post-transfer balance check (no `balanceOf` diff) as exists in the sibling implementation at `evm/src/apps/IntentGatewayV2.sol`, which explicitly re-measures `order.inputs[i].amount` from the actual balance delta to account for fee-on-transfer tokens: [3](#0-2)  and does so again in its predispatch/sweep branch using pre/post balance snapshots. [4](#0-3)  The corresponding logic is entirely absent from `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, both in the direct-transfer branch and the predispatch/sweep branch (which also blindly credits `reducedInputs[i].amount` without checking whether the swept `balance` actually equals `requiredAmount` for FOT tokens). [5](#0-4) 

As a result, if the input token is a fee-on-transfer token, the sum of `_orders[commitment][token]` obligations recorded across all orders will exceed the contract's actual token balance for that token. This is a shared-liquidity accounting bug: `_orders` is a per-commitment mapping, but the underlying ERC20 balance is a single pool shared by all orders using that token.

### Impact Explanation
Because escrow obligations for FOT tokens are overstated relative to actual balance held, later calls to `withdraw` (invoked via `cancelOrder`'s same-chain refund path or via `onAccept` processing `RedeemEscrow`/`RefundEscrow` requests) that attempt to transfer out the full recorded `_orders[commitment][token]` amount can fail once accumulated shortfalls exceed the residual balance, since the contract cannot pay out more of a token than it holds. [6](#0-5) [7](#0-6)  This produces a denial of service where legitimate order cancellations/refunds or solver settlements for that token revert, permanently freezing funds for whichever orders can no longer be paid out in full — matching the "permanent freezing of funds" / "route unable to deliver messages/settle" criteria. Earlier claimants (first-come withdrawals) can drain the shared pool, leaving later, equally valid escrow claims unfulfillable.

### Likelihood Explanation
This requires only that a user places an order on the Tron deployment of `IntentGatewayV2` using a fee-on-transfer ERC20 as an input token — a normal, permissionless `placeOrder` call reachable by any unprivileged user/solver. No admin or governance action is needed; the bug triggers automatically whenever a deflationary/fee-on-transfer token is used, which the sibling EVM contract's own test suite (`IntentGatewayV2SameChainTest.sol`) explicitly anticipates as a supported scenario for the main contract. [8](#0-7)  The Tron variant, however, lacks the corresponding balance-diff safeguard, so it is a genuine regression/omission rather than a purely theoretical case.

### Recommendation
In `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, mirror the pattern used in `evm/src/apps/IntentGatewayV2.sol`: record `balanceOf(address(this))` (or the dispatcher, in the predispatch branch) before and after each `safeTransferFrom`/sweep, and use the actual received delta — not the caller-supplied `order.inputs[i].amount` — as the basis for `reducedInputs` and the amount credited into `_orders[commitment][token]`. Apply the same fix to the predispatch sweep loop so `dust`/escrow accounting reflects true balances rather than assumed nominal amounts.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 (e.g. the `FeeOnTransferToken` used in `IntentGatewayV2SameChainTest.sol`) and mint balance to a user. [9](#0-8) 
2. User approves `IntentGatewayV2` (tron) for `inputAmount = 1000e18` and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. Inside `placeOrder`, `safeTransferFrom(user, address(this), 1000e18)` executes; the FOT token burns 1% so the contract's actual balance increases by only `990e18`.
4. `_orders[commitment][FOT]` is nonetheless incremented by `reducedInputs[0].amount` derived from `1000e18` (minus only the protocol fee, if any) — i.e., ~990e18 more than what the contract can actually deliver from this single order's transfer once fees compound, and any further FOT orders compound this shortfall against the shared token balance.
5. When a subsequent `withdraw` (via `cancelOrder` same-chain path or `onAccept`/`RefundEscrow`/`RedeemEscrow`) attempts to pay out the recorded escrow amount for FOT tokens, the ERC20 transfer reverts once the contract's actual FOT balance is insufficient to cover the sum of all outstanding (over-recorded) obligations, freezing legitimate refunds/settlements for that token.         PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output
        });

        vm.startPrank(user);

        );

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
