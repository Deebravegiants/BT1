### Title
Webhook Shop Domain Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while the shop identity (`shop-domain` header) is read independently and never covered by the HMAC. `ShopifyAPI::Utils::HmacValidator.validate` verifies only that the body bytes were signed with the app's shared `client_secret`; it does not bind that signature to the specific shop the request claims to be from. Any unprivileged holder of one genuine, validly-signed webhook (e.g., an attacker who installed the app on their own store and received a real webhook) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value, and the request will still pass `HmacValidator.validate`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is part of the signed/verified data. `shop` is read via a separate, unauthenticated header accessor: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it to the received HMAC — it never incorporates `shop`: [3](#0-2) 

`Registry.process` uses this validation result to gate trust, then constructs `WebhookMetadata` directly from `request.shop`, treating it as if it had been authenticated together with the body: [4](#0-3) 

This breaks the equality that should hold: `shop_bound_by_hmac == shop_delivered_to_handler`. In reality, `shop_bound_by_hmac` is undefined (the signature never covers `shop` at all), so `shop_delivered_to_handler` is fully attacker-controlled while the HMAC still validates as long as the body bytes match some previously-observed signature. Since the `client_secret` used to sign webhooks is shared across all shops installing the same app, any shop owner (an unprivileged party with respect to other tenants) can capture a webhook payload that Shopify legitimately delivered for their own store, then replay the identical body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The gem will report `Utils::HmacValidator.validate(request)` as `true` and hand the handler a `WebhookMetadata` claiming the victim shop, even though the payload's actual content originated from the attacker's own store.

### Impact Explanation
This crosses a tenant boundary: an app author's webhook handler (which typically persists/updates per-shop state such as orders, customers, or app state keyed by `shop`) can be made to attribute attacker-controlled webhook data to a victim shop it never actually came from, or to have their own maliciously-shaped webhook accepted as authoritative for another tenant. This matches the Critical "cross-tenant access" impact category, since it lets one unprivileged shop spoof identity toward another shop's data within the app's webhook-processing logic, using only the gem's documented API (`Webhooks::Request` + `Registry.process`) with no access token or leaked credential needed beyond having (legitimately) received one webhook for their own shop.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker must first obtain at least one genuine `(body, hmac)` pair — which any shop that installs the app can trivially get by triggering an event that fires a webhook to their own endpoint (or an endpoint they control/intercept) — and then send a modified request with a different `shop-domain` header directly to the app's public webhook endpoint. No secret material is required. This is fully reachable by any unprivileged internet user with access to a shop where the app is installed.

### Recommendation
Bind the shop identity into what is cryptographically verified, or otherwise reject the header value as untrusted input. Concretely: derive `shop` for handler dispatch only from a value that is itself covered by the HMAC (e.g., include the `shop-domain` header in the signable string, mirroring Shopify's actual webhook HMAC contract), or require the host application to independently corroborate `request.shop` against the shop record used to register that specific webhook subscription before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop` is not authenticated by `HmacValidator.validate` and must not be used as a tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an event (e.g., creates an order) so Shopify delivers a real webhook to the app's endpoint with a valid `shopify-hmac-sha256` header computed over the JSON body using the app's `client_secret`.
2. Attacker captures the exact raw body and HMAC header from that legitimate delivery.
3. Attacker replays an HTTP POST to the same app endpoint with the identical body and `shopify-hmac-sha256` value, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` returns `true` (line `hmac_validator.rb:12-31`) because only the body was checked.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-originated JSON>, ...)` (`registry.rb:198-199`), causing the app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
