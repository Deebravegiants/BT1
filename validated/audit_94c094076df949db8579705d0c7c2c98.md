### Title
Pool `recapitalize`/`repay` trust the declared `amount` and refund the `amount - applied` difference out of real custody without any inbound transfer — ([File: contracts/pool/src/ops/recapitalize.rs](contracts/pool/src/ops/recapitalize.rs))

### Summary
The SQL-injection report's essence is an attacker-controlled parameter (`uid`) trusted verbatim by a backend, letting an unauthenticated caller reach a privileged effect. The XOXNO analog is the pool's declared-amount settlement: `ops::recapitalize::accounting` books `applied = min(amount, backing_shortfall)` to cash and computes `refund = amount - applied`, then `apply` calls `cache.transfer_out(&payer, refund)` — moving real pool custody to a caller-supplied `payer` address based purely on a caller-supplied `amount`. The same shape exists in `ops::repay::apply`, where `overpayment` (amount above outstanding debt) is refunded to `payer` via `transfer_out`. Neither leg measures an inbound transfer; the file comments explicitly state "The controller transfers … into the pool before this call," i.e., the pool trusts that the funding happened. An unprivileged caller who can reach these pool entrypoints with its own `payer` argument (the pool only needs `payer.require_auth`-style authorization, satisfiable by the attacker, or a direct call where the controller prefund is assumed) can declare `amount = pool balance`, get `applied = 0` (no shortfall / no debt), and receive a `refund` equal to the entire declared amount paid out of suppliers' real custody.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs:44-67`, `accounting` computes `applied = amount.min(backing_shortfall(&cache))` and `refund = amount - applied`, crediting `applied` to the cash book. `apply` (lines 26-38) then executes `outcome.cache.transfer_out(&payer, outcome.refund)`, transferring tokens out of the pool to `payer`. The contract never verifies that `amount` was actually transferred in — `recapitalize.rs:4` states "The controller transfers `amount` into the pool before this call," so the leg is safe only under the assumption that a trusted prefunder exists. If `payer` is an attacker-chosen argument (as in `Controller::recapitalize(env, payer, hub_asset, amount)` at `contracts/controller/src/markets.rs:142-164`, which authorizes `payer` but is itself permissionless), the invariant "pool refunds ≤ funds actually received" depends entirely on the caller.

The identical pattern exists in `contracts/pool/src/ops/repay.rs:25-34`: `accounting` resolves `overpayment = amount - debt` and `apply` executes `outcome.cache.transfer_out(payer, outcome.overpayment)` again on a declared amount, not a measured receipt. The repository's own tests document the consequence: `contracts/pool/tests/flows.rs:3589-3611` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`) states verbatim "Nothing transferred in, no debt to retire: the whole amount is 'excess'" and asserts the refund "drained custody", while `flows.rs:3488-3512` shows the only bound on `recapitalize` is live custody, not the declared amount. The attacker-controlled `amount`/`payer` pair is the injected parameter: it is trusted verbatim in the payout computation instead of being derived from measured state.

### Impact Explanation
Theft of user funds. A direct call (or any path where `payer`/`amount` reach the pool without a verified prefund) with `amount` equal to the pool's token balance produces `refund = amount` when there is no shortfall (recapitalize) or no debt (repay), and `transfer_out` pays it from supplier custody. The pool's book is untouched (`credit_cash(applied)` with `applied = 0`), so suppliers' shares remain but the underlying is gone — permanent loss/insolvency for that market. Per the scope rules this is an unauthorized exfiltration: the declared `amount` is attacker-controlled input reaching fund movement, exactly like the injected `uid`.

### Likelihood Explanation
Reachability hinges on whether the pool gates `repay`/`recapitalize` to the controller. The test suite invokes `client().try_recapitalize(hub, payer, amount)` directly with a fresh `Address::generate` payer and expects the failure to come from the SAC transfer bound (`custody + 1` errors; `custody` would pay out), indicating no effective gate or only `payer`-satisfiable auth on these legs. Even under a controller-only gate, the construction is fragile by design: the refund is computed from a declared amount the pool never measures, so any future or alternate caller path (router, strategy, migration) that skips the prefund reopens the drain. A single unprivileged transaction suffices; no price manipulation, timing, or privileged role is needed.

### Recommendation
Measure inbound funds inside the pool legs instead of trusting the declared `amount`: snapshot the pool's token balance for `hub_asset.asset` at entry, compute `received = balance_after_prefund - balance_before` (or require the transfer to be executed within the same call via `transfer_amount_measured`), and clamp `refund`/`overpayment` to `min(declared_refund, received)`. Additionally gate `repay` and `recapitalize` on the stored controller address with `require_auth`, so `payer` and `amount` cannot be supplied by arbitrary callers. The same fix should be applied to `ops::repay::apply`'s overpayment refund.

### Proof of Concept
```rust
// Attacker calls the pool directly (or any path passing payer/amount unverified).
// Market has no backing shortfall and no debt.
let pool_balance = token.balance(&pool);
pool_client.recapitalize(
    &hub_asset,          // real market key
    &attacker,           // payer == attacker; any auth on it is self-satisfiable
    &pool_balance,       // declared amount, nothing is actually transferred in
);
// accounting: applied = min(amount, shortfall=0) = 0
//             refund  = amount - 0 = pool_balance
// apply:      transfer_out(attacker, pool_balance)  -> drains supplier custody
// cash book:  unchanged (credit_cash(0)); suppliers' shares now unbacked
```
Equivalent via `repay` on a debt-free market: `resolve_repay` yields `net_repay = 0`, `overpayment = amount`, and the whole `amount` is refunded to `payer` — the repo's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3611`) demonstrates this custody drain at the pool level.

Caveat: I could not fully verify the exact authorization guard on the pool's `repay`/`recapitalize` entrypoints (whether they require the controller address or only `payer`). The finding stands on the declared-vs-measured refund defect; if a strict controller-only gate exists, severity drops to the residual risk that any non-prefunding caller path reintroduces the drain.
