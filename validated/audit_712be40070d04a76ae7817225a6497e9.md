### Title
Unrestricted strategy routes can attach wallet-draining calls to a signed controller authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
**Medium severity.** `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` pass caller-supplied route bytes to the configured router while the caller's root authorization remains active. The controller authorizes only its own exact input transfer and checks only measured output, so a malicious venue in the route can add unrelated `victim.require_auth()` calls beneath the caller's signed authorization tree. If simulation returns and the victim signs that expanded tree, the route can transfer arbitrary wallet tokens or the position NFT while still returning valid swap output.

### Finding Description
`swap_collateral` authenticates the caller and verifies ownership or delegate authority, then forwards the opaque `swap` payload through `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1)  `swap_tokens` loads the configured router, snapshots balances, authorizes exactly one transfer from the controller to the router, and invokes `execute_strategy` with the uninspected payload. [3](#0-2)  The helper's authorization entry is limited to `token.transfer(controller, router, amount)` and has no sub-invocations, but it confines only the controller's own contract authorization. [4](#0-3) [5](#0-4)  Afterward, the controller only rejects router overspending and requires a positive measured output; it neither decodes the route nor bounds calls made under the user's separate authorization tree. [6](#0-5) [7](#0-6)  The repository's threat model states that route-selected pool and token addresses are not allowlisted and that a rogue transfer from the caller is recorded as a child of the caller's authorization and executes when that expanded tree is signed. [8](#0-7) 

### Impact Explanation
A malicious venue can steal assets unrelated to the routed input, including the victim's other token balances, by calling token `transfer(victim, attacker, amount)` during the strategy. [8](#0-7)  It can likewise add a position-NFT transfer to the signed tree, transferring control of the lending account after the current operation finishes; the NFT's ordinary transfer path authorizes `from`, while the controller uses NFT ownership as account authority. [9](#0-8) [10](#0-9)  The measured-output and solvency checks do not prevent this because the malicious route can still return economically valid output while the unrelated authorized transfer also succeeds. [11](#0-10) 

### Likelihood Explanation
The attacker needs no privileged role, leaked key, upgrade, or protocol compromise: they can deploy the venue and supply a route that reaches it. [8](#0-7)  The exploit does require the victim to submit a malicious route and sign the expanded authorization tree returned by simulation, so it is not a purely unilateral drain. [12](#0-11) [13](#0-12)  That interaction makes the issue lower likelihood than a direct missing-auth bug, but the impact extends beyond the declared swap input and can include the whole position NFT, supporting Medium severity.

### Recommendation
Do not allow opaque strategies to execute arbitrary venue contracts beneath a user-authenticated controller call. Enforce a governance-controlled venue allowlist or decode and validate the complete route call graph before invoking the router. [3](#0-2)  At minimum, require the integrating client to reject any signed authorization tree containing children other than the expected token pull, and surface that check before signing. [13](#0-12) 

### Proof of Concept
1. The attacker deploys a venue whose `swap` method calls `Token(unrelated_asset).transfer(victim, attacker, victim_balance)` and optionally `PositionNft.transfer(victim, attacker, account_id)`.
2. The victim submits `Controller::swap_collateral(caller=victim, account_id, current, amount, new, swap)`, where `swap` routes through the attacker's venue; the controller authenticates the victim and account before executing the route. [1](#0-0) 
3. `swap_tokens` invokes the configured router with the route bytes after authorizing only the controller's own exact input transfer. [14](#0-13) [5](#0-4) 
4. The attacker's venue performs the unrelated `victim`-authorized transfer; simulation records it as a child invocation beneath the victim's `swap_collateral` authorization. [8](#0-7) 
5. If the victim signs the returned tree, the venue's transfer executes, the router can still return fair `new` output, the controller's positive-output and account-risk checks pass, and the attacker receives the unrelated wallet assets or position NFT. [15](#0-14) [16](#0-15)
