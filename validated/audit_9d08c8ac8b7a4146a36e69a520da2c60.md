## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw request body only, while the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) values are taken directly from HTTP headers that are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts the unauthenticated `shop` header to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the signature: [2](#0-1) [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which only verifies the body against the HMAC) and then passes `request.shop` straight into the handler's `WebhookMetadata`, without any additional binding between the verified body and the claimed shop: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(body) == true` should imply `shop_header == shop_that_actually_produced(body)`.
In this implementation, `HMAC_valid(body)` only proves the body bytes were signed by Shopify for *some* shop with this app installed — it says nothing about which `shop` header value accompanies it. Any merchant who has the app installed can capture a genuinely-signed webhook delivery from *their own* store (many Shopify webhook payloads are minimal/structurally fixed, e.g. `app/uninstalled`, `shop/redact`, or other low/no-body-content topics) and replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` will report success because the body wasn't altered, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce: cross-tenant access/confusion. Host applications built on `Registry.process`'s documented contract reasonably assume that a validated webhook's `shop` field identifies the tenant that generated it, since HMAC validation is the gem's sole authenticity mechanism for webhooks. An attacker (any merchant with the app installed) can leverage this gap to make the host app attribute webhook-triggered actions (e.g., data deletion for GDPR topics, order/inventory state changes, app-uninstalled cleanup) to an arbitrary victim shop, which is a cross-tenant integrity/access violation — meeting the "Critical - cross-tenant access" bar without needing `api_secret_key`, an access token, or any credential leak.

### Likelihood Explanation
Exploitation only requires the attacker to control one legitimate shop with the app installed (to obtain one valid signed webhook body/HMAC pair) and network access to the app's public webhook endpoint — no secrets, no privileged account, no host-application misconfiguration beyond using the gem as documented (`ShopifyAPI::Webhooks::Registry.process`).

### Recommendation
Bind the identity fields into the signed material (or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC check), and/or require the application to cross-check the `shop` header against an expected/registered shop before acting on `WebhookMetadata`. At minimum, document and enforce that `Registry.process` callers must independently authenticate the `shop` claim (e.g., against an active session for that shop) before trusting it for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook topic whose body is fixed/empty (e.g. `{}`), capturing the legitimate `x-shopify-hmac-sha256` value Shopify sends for that body.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `{}` and the same valid HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and desired `x-shopify-topic`.
3. `Utils::HmacValidator.validate(request)` returns `true` because `Request#to_signable_string` only hashes the body, which is unchanged.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to perform shop-scoped logic against `victim-shop.myshopify.com` triggered by the attacker.
