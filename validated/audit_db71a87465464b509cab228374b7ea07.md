### Title
Webhook Shop-Domain Header Is Not Covered by HMAC Verification, Enabling Tenant Spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw request body against the `X-Shopify-Hmac-Sha256` header, then unconditionally trusts the separate, unsigned `X-Shopify-Shop-Domain` header as the tenant identity handed to the app's webhook handler. Because the shop domain is never part of the signed material, a caller who can produce (or replay) one valid `(body, hmac)` pair can pair it with an arbitrary shop-domain header and have the library report that arbitrary shop as the source of the webhook.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature strictly from `verifiable_query.to_signable_string` and compares it to the caller-supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — no headers are folded into the signed content: [2](#0-1) 

Meanwhile, `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (unauthenticated) to the consuming handler as the authoritative tenant identity: [4](#0-3) 

This is the same class of bug as the reported "data for swap might not match its inputs" issue: the value that is cryptographically verified (the body bytes) is disjoint from the value that is operationally acted upon (the shop-domain header). The equality the code should enforce — `shop authenticated == shop bound by the HMAC` — never holds, since the HMAC binds nothing about `shop`.

By contrast, the OAuth callback path in this same library does bind `shop` into the signed content (`AuthQuery#to_signable_string` includes `shop`), showing that the intended design pattern is to sign the identity field, which the webhook path fails to do: [5](#0-4) 

### Impact Explanation
Any application built on this gem that keys per-tenant logic (e.g., deleting/updating shop records, looking up shop-specific state, or triggering compliance actions like `shop/redact`, `customers/redact`) off `WebhookMetadata#shop` is exposed to cross-tenant confusion: an attacker who can obtain one valid `(body, hmac)` pair for a topic whose body content is not shop-specific (or is otherwise attacker-influenced/predictable, e.g., an app installed on the attacker's own free development store) can resend that exact body/HMAC to the app's public webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The HMAC check still passes because it never covered the shop header, so the library hands the handler a `WebhookMetadata` claiming to originate from the victim shop. This crosses a tenant boundary using data the library itself asserts is authenticated.

### Likelihood Explanation
Webhook endpoints are, by design, public HTTP endpoints that accept unauthenticated POSTs from the internet (the entire point of HMAC verification is to authenticate an otherwise-open endpoint). Obtaining a legitimate `(body, hmac)` pair only requires installing the target app on any shop the attacker controls (a normal, unprivileged action) and capturing/replaying a real webhook delivery whose body is generic or attacker-influenced. No access token, `client_secret`, or privileged credential is required — only network access to the app's webhook route and control of one shop where the app is installed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-signed content, or otherwise cryptographically bind the shop identity to the verified body before it is trusted downstream — e.g., have `Webhooks::Request#to_signable_string` incorporate the shop header, or require host applications to independently verify that the shop in the payload/header matches a shop for which the app holds an active, previously-issued access token before acting on the webhook.

### Proof of Concept
1. Install the target app on an attacker-owned development store; capture one legitimate webhook delivery whose JSON body is empty or otherwise generic (many compliance/lifecycle topics qualify), noting the valid `X-Shopify-Hmac-Sha256` value Shopify computed for that exact body.
2. Send a POST request directly to the app's webhook route with:
   - the identical raw body captured in step 1 (so the HMAC still validates),
   - the identical `X-Shopify-Hmac-Sha256` header from step 1,
   - `X-Shopify-Shop-Domain` set to the victim shop's domain instead of the attacker's own.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body bytes; `ShopifyAPI::Webhooks::Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the request was never sent by Shopify on behalf of that shop.
