Confirmed: `WebhookMetadata.shop` and `.topic` come directly from unauthenticated headers, and the handler dispatch keys off `request.topic`, `request.shop`, `request.webhook_id` after only the raw body has been HMAC-verified.### Title
Webhook `shop-domain` / `topic` / `webhook-id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signed content solely from the raw HTTP body via `to_signable_string`, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers [1](#0-0) . `Registry.process` validates only the body against the HMAC and then unconditionally trusts the header-derived `shop`/`topic`/`webhook_id` when building `WebhookMetadata` and dispatching to the registered handler [2](#0-1) . `Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for `Request` is `@raw_body` — never the `shop`, `topic`, or `webhook_id` header values [3](#0-2) .

### Finding Description
This mirrors the HAL-05 bug class: an identity-binding field (here, the tenant/shop identity carried in the `X-Shopify-Shop-Domain` header) is *acted upon* by the application (used to key `WebhookMetadata.shop`, routed to the handler, and typically used by the host app to look up per-shop session/config) but is *not covered* by the cryptographic integrity check that is supposed to authenticate the request. The equality that should hold is:

`bytes verified by HmacValidator == bytes that determine the tenant identity used downstream`

In this gem, that equality is broken: `bytes verified` = `raw_body` only, while `bytes that determine tenant identity` = the `shopify-shop-domain` header (and `shopify-topic`/`shopify-webhook-id`), which sit entirely outside the signed payload [4](#0-3) .

Exploit path: an unprivileged internet user can install the target app on their own Shopify store (a normal, unprivileged action any merchant can perform). Shopify will deliver genuine webhooks to the app's public webhook endpoint for that attacker-owned shop, each with a valid `(raw_body, hmac)` pair signed with the app's `client_secret` — a secret the attacker never needs to see, since Shopify computes it server-side and the attacker merely captures the resulting HTTP request. The attacker then replays that exact `raw_body`/`hmac` pair to the same public endpoint, substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. Because `HmacValidator.validate` only checks `raw_body` against `hmac` [5](#0-4) , the forged request passes validation, and `Registry.process` builds a `WebhookMetadata` asserting the (false) victim shop identity, then invokes the registered `WebhookHandler#handle` as if the event legitimately belongs to the victim tenant [6](#0-5) .

Any host application that trusts `WebhookMetadata#shop` (as the gem's own `docs/usage/webhooks.md` and the struct's public API encourage) to select per-tenant session/storage context inherits a cross-tenant confusion vulnerability directly attributable to this gem's signature scope, not to host misuse of an undocumented API — `WebhookMetadata.shop` is the gem's documented, first-class output of a "validated" webhook.

### Impact Explanation
This breaks the tenant/shop binding that HMAC validation is supposed to guarantee, enabling cross-tenant access/confusion: data or side effects intended for the attacker's own shop can be attributed to, and processed under, a victim merchant's shop identity inside the host application, without needing the app's `client_secret`, any access token, or privileged account. This falls under the Critical impact category "cross-tenant access."

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs to (1) install the target app on their own store — a self-service, unprivileged action — and (2) send one HTTP POST with a swapped header to the app's publicly reachable webhook endpoint. No secret material, no social engineering, and no elevated access are required.

### Recommendation
Include the tenant-identifying and routing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed payload that `HmacValidator` verifies, or independently bind/verify the `shop` header against a value derived from data that *is* covered by the HMAC (e.g., embed shop domain in the body when possible, or require the host app to cross-check `WebhookMetadata.shop` against the shop associated with the actual signed body content). At minimum, document prominently that `WebhookMetadata.shop`/`topic`/`webhook_id` are **not** cryptographically authenticated by `HmacValidator.validate`, and that host apps must not treat them as trusted tenant identifiers derived from the signature check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a genuine webhook (e.g. `orders/create`) to the app's public callback URL with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and body `B`.
3. Attacker captures `B` and the valid `hmac`.
4. Attacker sends a new POST to the same endpoint with identical body `B` and identical `hmac`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` (`B`) against `hmac` [7](#0-6) [8](#0-7) .
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied data under the victim shop's identity [9](#0-8) .
