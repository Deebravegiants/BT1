### Title
Signup marked "Success" based purely on local `signup_reason`, bypassing backend enrollment confirmation when `user_centric_signup` is set - ([File: src/plans/mod.rs])

### Summary
When a user's QR-code data flags `user_centric_signup = true`, orb-core skips the backend enrollment round-trip (`enroll_user::Plan::run`, which posts the signup and polls the backend `signup_poll`/`signup_post` endpoints for a `Completed`/`success` status) and instead derives the signup outcome purely from the orb-local `signup_reason` value. This mirrors the Notional pattern where a value that has not yet been confirmed/settled by an authoritative external source (`pr.supplyFactor` / backend enrollment result) is treated as if it were already final, producing an outcome ("Success") based on incomplete state.

### Finding Description
In `src/plans/mod.rs`, `do_signup` computes `signup_reason` purely from local pipeline/fraud results: [1](#0-0) 

Then, for the `user_centric_signup` branch, the enrollment "success" status is derived directly from this local `signup_reason`, without ever contacting the backend enrollment/duplicate/fraud service that the non-user-centric path uses: [2](#0-1) 

Compare this to the normal path, `enroll_user::Plan::run`, which submits the signup to the backend (`signup_post::request`) and then polls (`signup_poll::request`) until the backend reports `Status::Completed` with `success: true`/`false` — the backend is the authority that performs duplicate-detection and backend-side fraud checks before confirming completion: [3](#0-2) 

In the `user_centric_signup` branch, none of this backend confirmation occurs. `success` and the final `debug_report.enrollment_status` are set to `Success` whenever `signup_reason == SignupReason::Normal`, i.e. whenever the *orb-local* pipeline didn't fail and no *orb-local* fraud check triggered: [4](#0-3) 

This is directly analogous to the Notional bug class: a downstream computation (`totalAssets()` / signup "Success" status) is derived from a value (`pr.supplyFactor` / backend enrollment confirmation) that is expected to reflect a specific settled/confirmed state, but the code proceeds using a stand-in/local value without verifying that the authoritative state transition has actually happened. In Notional, the unsettled state silently defaults to zero; here, the unconfirmed backend state silently defaults to a locally-inferred "Success," even though the backend has not yet (or may never) confirm the signup (e.g., it could still be rejected server-side as a duplicate or backend-detected fraud).

### Impact Explanation
`debug_report.enrollment_status` and `result.success` feed the final signup status reported to the app/operator (`ui_complete_signup`, DBus `signup_finished`, Orb Relay `SignupEnded`) and drive whether the Personal Custody Package upload/signup is treated as a completed, valid enrollment: [5](#0-4) 

If the backend would have rejected the signup (e.g., a duplicate identity, or a backend-side fraud determination) the user-centric path never learns this and unconditionally reports success to the app/operator based only on local signup_reason. This is a misattributed/incorrectly-confirmed signup outcome: the orb asserts a signup is successfully enrolled without the backend's confirmation that enrollment (including duplicate/fraud checks) actually completed.

### Likelihood Explanation
This code path is reached by any ordinary signup flow as soon as the user's QR-code/app data sets `user_centric_signup = true` (a field controlled by the app-provided, backend-signed `UserData`, not by the orb operator) and the orb's config does not set `ignore_user_centric_signups`: [6](#0-5) 
This is a normal, unprivileged user-triggerable code path (no special hardware, no operator/test-only feature required), so the likelihood of the divergent behavior being encountered is limited only to how `user_centric_signup` is used in production and whether backend confirmation is otherwise still enforced server-side out-of-band.

### Recommendation
Do not treat "no local fraud/pipeline failure" as equivalent to "backend confirmed successful enrollment." Even in the `user_centric_signup` flow, either (a) still perform a blocking/authoritative round-trip against the backend before reporting success (mirroring `enroll_user::Plan::run`), or (b) clearly document/gate this behavior and ensure any relying party (app, operator UI, DBus/relay consumers) treats this local success signal only as "no orb-side failure detected," not as a guarantee of backend-confirmed enrollment, and revert/fail closed if backend confirmation is required but unavailable.

### Proof of Concept
Not applicable in the traditional exploit sense; this is a logic/control-flow issue reachable via the standard signup flow. To reproduce: perform a signup where the user QR-code/app payload sets `user_centric_signup = true`; observe in `src/plans/mod.rs` (lines 639-656) that `enroll_user::Plan::run`/`signup_post`/`signup_poll` are never invoked, and that `debug_report.enrollment_status` is set to `Success` solely because `signup_reason == SignupReason::Normal`, with no backend confirmation of enrollment completion, duplicate-check, or backend-side fraud detection.
