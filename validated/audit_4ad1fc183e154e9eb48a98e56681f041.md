### Title
Unearmarked withdrawal of protocol/relayer fee balance can permanently block relayer fee claims and request-timeout refunds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.withdraw` (invoked via `HostManager.onAccept` → `IHostManager.withdraw`) transfers an arbitrary amount of any token — including the fee token — out of the host contract's balance to a beneficiary, with no check that the transferred amount does not exceed the balance that is *not* already owed to pending relayer-fee claims or request-timeout refunds. This is structurally the same defect as the reported Farm contract bug: a withdrawal path checks nothing about future/pending obligations before moving funds out, so a legitimate (even well-intentioned) withdrawal can leave the contract unable to honor claims it has already promised, causing `safeTransfer` reverts for relayers and users when they later try to collect what they are owed.

### Finding Description
When an application dispatches a request, `EvmHost.dispatch` pulls `post.fee` in the fee token into the host contract and records the obligation only in `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` [1](#0-0) . The actual tokens simply become part of the host contract's overall feeToken balance — there is no separate escrow/ledger that reserves this balance against future obligations.

Later, when a request is delivered, timed out, or when a relayer accumulates and withdraws fees through `pallet-ismp-relayer`, the payout ultimately flows through `IHostManager.withdraw(WithdrawParams)` → `EvmHost.withdraw`, which does an unconditional `safeTransfer`/native transfer of `params.amount` to `params.beneficiary` [2](#0-1) . The dispatch path in `HostManager.onAccept` decodes `WithdrawParams` from a governance/relayer-initiated ISMP request and calls `IHostManager(_params.host).withdraw(withdrawParams)` with **no accounting check** that the amount being withdrawn leaves enough balance to cover:
- Outstanding relayer fees for requests dispatched but not yet delivered/accumulated (`_requestCommitments[...].fee`), paid out via `dispatchIncoming` (GET responses) or refunded via `dispatchTimeOut` (POST/GET timeouts) [3](#0-2) .
- The same "protocol revenue withdrawal" and "relayer fee withdrawal" code paths share this single `withdraw` function and the same undifferentiated contract balance — see `IHostManager.withdraw` / `OnAcceptActions.Withdraw` dispatch in `HostManager.onAccept` [4](#0-3) .

This mirrors the Farm contract root cause exactly: the withdrawal function has no notion of "funds already committed to future/pending claims," so a withdrawal that is valid at call-time (balance ≥ amount) can drain funds that are implicitly earmarked for relayers/users who dispatched or delivered messages earlier but haven't yet claimed. Just like the farm's `owner_withdraw_token` only checking `!is_active()` (which is true for a farm scheduled in the future) instead of accounting for already-accrued-but-unclaimed rewards, `EvmHost.withdraw` only checks that the contract currently holds `params.amount` of the token — it has no concept of "committed" vs. "free" balance.

### Impact Explanation
If the withdrawable amount (protocol revenue, computed off-chain/by governance from perceived "surplus") is miscalculated, or if governance/host-manager withdraws feeToken revenue without accounting for pending relayer-fee obligations recorded in `_requestCommitments`, the contract's feeToken balance can drop below what is owed to:
- Relayers who already delivered requests and are entitled to their fee via `dispatchIncoming`'s `IERC20(feeToken()).safeTransfer(relayer, fee)` [5](#0-4) .
- Users/applications entitled to a fee refund on timeout via `dispatchTimeOut`'s `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` [6](#0-5) .
- Relayers withdrawing accumulated fees through `pallet-ismp-relayer`'s `withdraw_fees` flow, which dispatches the exact same `WithdrawalParams`/`IHostManager.withdraw` path [7](#0-6) .

Any of these `safeTransfer` calls reverts once the balance is insufficient, permanently blocking legitimate claims (relayer rewards, user refunds) until new fee inflows happen to cover the shortfall — a form of temporary-to-permanent freezing of relayer/user funds, consistent with the accepted "permanent freezing of funds" impact class. This is High severity because it can halt reward/refund payouts protocol-wide for an affected chain, not just a single user.

### Likelihood Explanation
The likelihood depends on whether governance's off-chain accounting for "withdrawable protocol revenue" already subtracts outstanding relayer-fee/timeout-refund obligations before issuing a `WithdrawParams` request. I could not verify from the indexed code whether such a reserved-balance computation exists anywhere (e.g., in `pallet-ismp-host-executive`'s `withdraw` call, which simply forwards an admin-supplied `WithdrawalParams.amount` without any on-chain check against `_requestCommitments` totals [8](#0-7) ). Because the check is entirely off-chain/trust-based (an admin-supplied amount with no on-chain invariant), any error in that off-chain computation — or a burst of new fee-bearing dispatches after the withdrawal amount was computed — reproduces the exact "Scenario" from the original report: a withdrawal that looked safe at issuance time leaves insufficient funds for obligations that mature afterward.

### Recommendation
Introduce an on-chain invariant in `EvmHost.withdraw` (or in the pallet that constructs `WithdrawalParams`) that tracks total outstanding relayer-fee/timeout-refund liabilities (sum of live `_requestCommitments[...].fee` for undelivered requests) and reverts (or caps the withdrawal) if `amount` would bring the token balance below that reserved liability. Alternatively, maintain a running "free balance" counter that is decremented on `dispatch`'s fee collection and only incremented back on `dispatchIncoming`/`dispatchTimeOut`/expiry, and restrict `withdraw` to that counter rather than the raw ERC-20 balance — analogous to the report's suggested fix of forcing `owner_stop_farm` semantics that account for already-accrued obligations before allowing a withdrawal.

### Proof of Concept
Conceptual PoC (on-chain state, not runnable code, due to lack of a full accounting audit of the withdrawal-amount computation off-chain):
1. Multiple applications dispatch POST/GET requests via `EvmHost.dispatch`, each paying a relayer fee into the host's feeToken balance and recording `_requestCommitments[commitment] = {sender, fee}`.
2. Governance/host-manager computes an "available for withdrawal" figure (e.g., total feeToken balance minus some heuristic) and submits a cross-chain `Withdraw` action via `HostManager.onAccept`, which invokes `EvmHost.withdraw` for that amount — succeeding because the current balance ≥ amount.
3. Because the withdrawal did not subtract the fees already committed in step 1's `_requestCommitments` entries, the host's feeToken balance is now below the sum of pending relayer fees/timeout refunds.
4. A relayer delivers one of the pending requests; `dispatchIncoming`/`dispatchTimeOut` attempts `IERC20(feeToken()).safeTransfer(relayer/sender, fee)` and reverts due to insufficient balance, or a relayer's `pallet-ismp-relayer::withdraw_fees` flow reaches the same `EvmHost.withdraw` and reverts.
5. The relayer/user cannot claim already-earned/refundable fees until unrelated new fee inflows replenish the balance — reproducing the Farm contract's "claim fails despite legitimately earned rewards" outcome.

I was unable to fully trace the off-chain/governance logic that computes the `WithdrawalParams.amount` for the `pallet-ismp-host-executive::withdraw` extrinsic to determine whether it already subtracts pending relayer-fee liabilities; this is the key uncertainty in confirming exploitability versus a purely off-chain-mitigated risk.

        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
