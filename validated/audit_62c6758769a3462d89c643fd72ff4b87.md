### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature (`to_signable_string`) solely over the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values and passes them straight into the app's webhook handler after validating only the body's HMAC.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, i.e., the shop and topic asserted by the request should be part of what is cryptographically verified. Instead, the actual binding implemented is `hmac == HMAC(secret, body)` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers (`shopify_header`) with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately trusts `request.shop` and `request.topic` to dispatch to the registered handler and construct `WebhookMetadata`: [3](#0-2) 

Because the HMAC never binds `shop-domain` to the body, any (body, hmac) pair that is valid for one shop is also valid for the same body sent with an attacker-modified `shop-domain` header (and/or `topic`, `webhook_id`, `api-version`) — the signature check in `HmacValidator.validate_signature` only recomputes over `to_signable_string`, which is just the raw body: [4](#0-3) 

This is the same class of bug as the report's core issue: a value that is "acted on" (here, the shop identity used to route/attribute the webhook) is not covered by the integrity check that is supposed to authenticate the whole message.

### Impact Explanation
An unprivileged internet user who can obtain any single legitimate (body, HMAC) pair signed with the app's own `client_secret`/`api_secret_key` — trivially available to them by installing the app on their own free/trial shop and receiving one real webhook — can replay that exact body with a forged `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header claiming to belong to a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the forged `shop` value to the host application's webhook handler as if it were an authentic event for that other tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up/update tenant records, credentials, or trigger tenant-scoped side effects), this enables cross-tenant confusion/injection of webhook data attributed to a shop that never sent it.

### Likelihood Explanation
The attacker only needs the ability to install the app on any shop they control (a low bar — no special privileges, no leaked credentials, no TLS interception) to harvest one valid (body, HMAC) pair, then can freely craft raw HTTP requests to the app's public webhook endpoint with arbitrary headers. This is straightforward to execute repeatedly, and the flaw is structural (the signing scope is fixed in the gem's code), not dependent on the host app misusing a documented API — the gem itself only signs the body and hands over unauthenticated header values.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the material that is HMAC-verified, or otherwise cryptographically bind the header-derived identity fields to the signed payload before they are used for dispatch/attribution (e.g., verify the shop header against a shop already associated with the specific webhook subscription/session, rather than trusting the header value outright). At minimum, document that `shop`/`topic` from `Webhooks::Request` are unauthenticated relative to the HMAC and must not be used by host apps for tenant-sensitive decisions without an independent binding (e.g., matching against the session/shop that registered the specific `webhook_id`).

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and lets the app deliver one real webhook, capturing the raw request: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(secret, B)` per `HmacValidator.compute_signature`).
2. Attacker sends a new POST request directly to the app's webhook endpoint with the exact same body `B` and HMAC header `H`, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (`hmac`, `topic`, `shop` are all header reads): [5](#0-4) 
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `to_signable_string` (`= @raw_body = B`) and compares to `H` — identical to step 1's computation: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now `victim-shop.myshopify.com`, even though the request body/content and signature originated from the attacker's own shop — demonstrating that the app processes a webhook "as" a shop that never actually sent it.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
