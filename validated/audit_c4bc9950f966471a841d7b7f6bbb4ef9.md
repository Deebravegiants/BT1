### Title
Webhook `shop` (tenant) field is not bound to the HMAC signature, allowing tenant-mismatch payload injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` covers exclusively the body bytes. The `shop` value, which is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header and used as the tenant identity when the payload is handed to the application's webhook handler, is completely outside the signed content.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` and compares it to the `hmac` accessor:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

`Registry.process` uses `Utils::HmacValidator.validate(request)` as the sole authenticity gate before dispatching the webhook, and then forwards `request.shop` (parsed straight from the unauthenticated header) as the tenant identifier to the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The `shop` header value is never included in the bytes fed into the HMAC computation, so it is asserted with the equality "shop trusted for tenant routing" == "shop covered by the HMAC" and that equality does not hold — `shop`, `topic`, `webhook-id`, and `api-version` are all attacker-influenceable header values whose integrity the library does not verify at all, while only the request body is bound to the secret.

### Impact Explanation
Any party that can present a syntactically valid webhook request with a body+HMAC pair that was legitimately signed by Shopify's secret for some shop (for example, a request the attacker's own store received, or any body/signature pair sourced from a Shopify webhook delivery) can resubmit that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still succeed because it never inspects the `shop` header, and `Registry.process` will hand the (attacker-chosen) `shop` value straight to the application's handler as the authenticated tenant, alongside the legitimately-signed body. If the host application uses `WebhookMetadata#shop` to select which merchant's session/data record to update, this allows cross-tenant data injection/corruption without ever knowing the app's `client_secret`.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid (body, HMAC) pair signed with the app's secret — normally obtainable only by being a legitimate, if low-privilege, recipient of that app's webhooks for their own shop (e.g., a merchant who installed the app). No access token, `client_secret`, or TLS interception is required; only replay of a header value that the library never authenticates. This is a design gap in the library's `VerifiableQuery`/`HmacValidator` contract rather than a hypothetical host misuse, since the library itself supplies `shop` from `WebhookMetadata` as the trusted tenant key while excluding it from `to_signable_string`.

### Recommendation
Bind the tenant-identifying header (`shop-domain`) — and ideally `topic`/`api-version`/`webhook-id` — into the signed material that `HmacValidator` verifies, or otherwise document/enforce that `WebhookMetadata#shop` must never be used for authorization decisions without an independent verification (e.g., cross-checking against the session store keyed by an already-authenticated shop, not solely the header value carried on the same request).

### Proof of Concept
1. App owner installs the library and registers a webhook handler that keys data updates off `WebhookMetadata#shop`.
2. Attacker (a legitimate merchant "shop-a.myshopify.com" with the app installed) receives a real webhook: body `B`, valid header `shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's real secret), and header `shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker resends the identical `B` and `H` to the app's webhook endpoint, but sets `shopify-shop-domain: shop-b.myshopify.com` (a different merchant).
4. `Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`to_signable_string`), which still equals `H`, so validation passes. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)`, i.e., data intended for shop-a is now attributed to shop-b's tenant context by the app.
