### Title
Webhook `shop-domain` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, but the HMAC only ever covers the raw request body. The `shop-domain`, `topic`, and `webhook-id` headers — including the value used to identify *which tenant* the event belongs to — are read straight from unauthenticated HTTP headers and handed to the caller's handler unverified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled from separate, unsigned headers: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it against the received `hmac`: [4](#0-3) 

`Registry.process` performs exactly this body-only HMAC check and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the app's handler — there is no check that this shop is the one for which the signed body was actually issued, nor any cross-reference against a known/installed shop: [5](#0-4) 

This is exactly the bug-class pattern from the analog report: a field that is *acted upon* (the tenant identifier, `shop`) is not part of what is cryptographically bound by the HMAC. Two sides of the equality that should hold but don't:
- Expected: `shop-domain header == the tenant for which api_secret_key HMAC-signed this exact body`
- Actual: `shop-domain header` is an independent, attacker-editable HTTP header that is never fed into the signature computation, so it can be swapped freely as long as the body+HMAC pair stays byte-identical.

### Impact Explanation
An unprivileged user can install the target app on their own store (a normal, unprivileged action any internet user can perform for a public Shopify app) and receive a genuinely-signed webhook (body + valid HMAC) for their own tenant. Because the HMAC signature never binds the `shop-domain` header, the attacker can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with an arbitrary victim shop's domain. `Registry.process` will still validate the HMAC successfully (it only checks the body) and will dispatch the event to the app's handler tagged as originating from the victim shop. Any host application that — as this library's own documented usage pattern implies — keys tenant-scoped actions (session lookup, data mutation, `app/uninstalled` cleanup, etc.) off `WebhookMetadata#shop` is exposed to cross-tenant confusion/spoofing, which the ruleset classifies as Critical (cross-tenant access).

### Likelihood Explanation
Medium-High. No secrets, tokens, or privileged access are required — only the ability to install the app on an attacker-controlled shop (trivial for any public app) and issue a raw HTTP POST with edited headers to the app's public webhook receiver endpoint. The library provides no guard, warning, or helper to prevent this; `Registry.process` is documented as "verify the request did indeed come from Shopify," which developers reasonably interpret as authenticating the whole envelope, including the shop it claims to be for.

### Recommendation
Bind the tenant-identifying fields into the authenticated payload before trusting them:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the signable string used for HMAC verification, or
- After body HMAC verification, require the caller (or the library itself) to cross-check `request.shop` against a previously known/installed shop (e.g., an existing session) before acting on it, and clearly document that `shop-domain` is not itself covered by the HMAC guarantee.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers any webhook topic (e.g. `app/uninstalled`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays the exact request to the app's public webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and, if desired, `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over body `B` only and matches `H` — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to act as if the event genuinely originated from the victim tenant.
