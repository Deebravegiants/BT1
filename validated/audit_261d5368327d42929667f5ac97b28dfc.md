## Title
Webhook `shop` (and other header) fields are trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC that is computed **only over the raw request body**, yet the tenant-identifying `shop` (and `topic`/`webhook_id`/`api_version`) values are read from unauthenticated HTTP headers and handed to the application's handler as trusted data. This is the same class of bug as the report's root cause: a downstream operation is applied to bytes/fields that are not covered by the integrity check that "authenticated" the request, allowing the field to diverge from what was actually verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof that the *entire request*, including `request.shop`, is authentic, and forwards `request.shop` straight into the handler's `WebhookMetadata` without any separate validation (e.g. via `Utils::ShopValidator`, which exists elsewhere in the gem specifically to bind an untrusted shop string to a trusted tenant): [4](#0-3) 

The equality the code implicitly assumes but does not enforce is:

`hmac == HMAC(secret, raw_body)` ⇒ `shop header == the tenant that actually generated raw_body`

but the real binding only proves:

`hmac == HMAC(secret, raw_body)` (body integrity only)

Any party who can obtain one genuine, validly-signed webhook body for their *own* shop (any merchant that installs the app receives real Shopify webhooks) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header for an arbitrary value. `Utils::HmacValidator.validate` will still return `true` because it never looks at those headers, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen value while `body` is the attacker's real (but relabeled) payload.

### Impact Explanation
This is a High-severity cross-tenant confusion vector: any application that uses `WebhookMetadata#shop` to key its own tenant-scoped resources (session lookup, product/order association, per-shop data storage) can be tricked into attributing an attacker-supplied, HMAC-"verified" payload to a different shop domain than the one that actually produced it. Because the shop identifier is the exact binding this gem is responsible for supplying reliably to consuming apps (it's what `ShopifyApp` and other consumers rely on to select the correct tenant session — see `docs/usage/webhooks.md`), this breaks the tenant-authentication boundary the gem is supposed to enforce.

### Likelihood Explanation
Exploitation only requires the attacker to control (or install the app on) at least one shop of their own to obtain a genuinely signed webhook body/HMAC pair — no access to `api_secret_key`, access tokens, or other shops' secrets is needed. The attacker then only needs to be able to submit a raw HTTP request to the app's public webhook endpoint with modified headers, which is standard unprivileged-internet-user capability.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload construction, or otherwise independently verify that the `shop` header corresponds to the shop the request was actually routed for (e.g., cross-check against `Utils::ShopValidator.sanitize!` combined with a shop that the app has an active/expected session for) before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` header computed over the raw JSON body.
2. Attacker resends that exact `raw_body` + `hmac` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks the body against the HMAC.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and the attacker's order data, causing the application to process attacker-controlled data as if it belonged to the victim shop.
