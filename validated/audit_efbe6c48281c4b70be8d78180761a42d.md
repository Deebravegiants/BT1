### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values and forwards them to the host application's handler as the identity of the shop the webhook data belongs to, even though none of those headers are bound to the HMAC signature that was verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are parsed straight from the (attacker-controllable) HTTP headers with no cryptographic binding to those values: [2](#0-1) 

`Registry.process` verifies only this body-only HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` when constructing the metadata handed to the app's registered webhook handler: [3](#0-2) 

`Utils::HmacValidator.validate` simply recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [4](#0-3) 

This breaks the identity binding: `shop authenticated-by-HMAC` ≠ `shop delivered to the handler`. The HMAC only proves "this body was signed by Shopify using this app's `client_secret`" — it says nothing about which shop the header claims the body came from. Because a single app's `api_secret_key`/`client_secret` is shared across every shop that installs the app, any merchant who installs the target app on their own (attacker-controlled) store can trigger the app to receive a legitimately-signed webhook for their store, capture the `(raw_body, hmac-sha256)` pair, and then replay it to the same webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` forwards the forged `shop` value to the handler as if Shopify itself asserted it belongs to the victim.

### Impact Explanation
Any host application handler that keys business logic, data writes, or session lookups off `WebhookMetadata#shop` (the documented and expected usage per `docs/usage/webhooks.md` and the `Registry.process` code path) can be made to attribute attacker-supplied webhook payloads to an arbitrary victim shop. This is a cross-tenant identity-binding bypass: an unprivileged attacker who controls only their own installed store can impersonate any other shop's webhook traffic to the same app, without ever needing the app's `client_secret` or a victim's access token.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a store they control (a normal, unprivileged action) and be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no elevated access, secrets, or social engineering needed. The vulnerable code path (`Request#to_signable_string`, `HmacValidator.validate`, `Registry.process`) is on the default, documented flow for verifying and dispatching webhooks.

### Recommendation
Include the security-relevant headers (`shop-domain` at minimum, ideally `topic` and `webhook-id` too) in the signable content used for HMAC verification, or otherwise cryptographically bind the shop/topic to the signed body (e.g., verify the signature over a canonical string that concatenates body + shop + topic) so that any header tampering invalidates the HMAC.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled dev store `attacker.myshopify.com`.
2. Trigger a subscribed webhook topic (e.g. `orders/create`) in that store; Shopify sends a POST to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and the JSON body.
3. Capture `(raw_body, hmac)`.
4. Re-POST the identical `raw_body` and `hmac` to the same endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against `hmac`), and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the host app to process attacker-supplied data as if it originated from the victim shop.
