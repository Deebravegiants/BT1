### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, but `to_signable_string` (the data actually protected by the HMAC) is only the raw body. This breaks the intended binding `verified_bytes == acted_upon_identity`: the HMAC authenticates the payload content but not the shop the payload is attributed to.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the HMAC [2](#0-1) .

`Registry.process` validates only the body's HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, which is what the host application's handler uses to attribute the event to a tenant: [3](#0-2) 

Because Shopify apps share a single `client_secret` across all installing shops, any merchant who has installed the app (a normal, unprivileged user of a public app) legitimately receives HMAC-signed webhook deliveries for their own shop. That merchant can capture one such `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still pass, since it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, while `body` is attacker-controlled content that was legitimately signed for the attacker's own shop.

This exactly matches the report's root-cause pattern: a value used to make a security-relevant decision (`shop`, the tenant key) is not covered by the field that was supposed to guarantee integrity (the HMAC), enabling a value that passes validation to diverge from the value actually protected.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to key sessions, look up access tokens, or scope tenant data (which is the gem's own documented usage pattern for webhook handlers) can be made to process attacker-supplied webhook content under another merchant's identity. This is a cross-tenant confusion/injection primitive: an attacker with no access token, no `client_secret`, and no privileged account — merely a normal install of the app on their own store — can forge events (e.g., fake `orders/create`, `app/uninstalled`, GDPR requests) attributed to an arbitrary other shop that also uses the app, as long as they can guess or discover that shop's domain (which is public, e.g. `victim.myshopify.com`). This satisfies the required "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) installing the target app on an attacker-controlled Shopify dev/trial store to receive one legitimately signed webhook (trivial and free for any app that allows installs), and (2) sending a crafted HTTP request to the app's public webhook endpoint with the captured body/HMAC and a substituted shop header. No secrets, tokens, or privileged access are needed — this is reachable by any unauthenticated internet user willing to install the target app once.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: either include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the signable string used by `HmacValidator`, or independently verify that `request.shop` corresponds to a shop with an active session/installation known to the host app before dispatching to handlers. At minimum, document prominently that `Request#shop` is unauthenticated and must not be trusted as a tenant boundary without additional verification (e.g., cross-checking against `webhook_id`/topic uniqueness combined with a stored shop-to-secret mapping, if per-shop secrets are ever supported).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering the app's own webhook handler and thus a real Shopify-delivered webhook POST with a valid `X-Shopify-Hmac-Sha256` for some body `B`.
2. Attacker captures `(B, hmac)` from the delivery (e.g., via a proxy on their own server, which is the same endpoint the app owns).
3. Attacker crafts a new HTTP request to the same webhook endpoint, headers:
   - `X-Shopify-Topic: orders/create` (or any topic present in `B`)
   - `X-Shopify-Hmac-Sha256: <captured hmac>`
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - body: `B` (byte-for-byte identical)
4. `Utils::HmacValidator.validate` succeeds since it only checks `B` against the shared `client_secret`: [4](#0-3) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to act on attacker-controlled data under the victim's tenant identity [3](#0-2) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
