### Title
Webhook tenant identity (`shop-domain`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook using an HMAC computed **only over the raw request body**, while the `shop` (tenant identity) is read from an HTTP header that is never included in the signed material. An attacker who can obtain one legitimately-signed `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own shop and triggering a webhook) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature check still passes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, however, is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (here, the raw body) and compares it to the supplied `hmac`: [3](#0-2) 

Because `shop` is excluded from the signed string, the equality the library implicitly relies on — "the `shop` header used to route/process the webhook == the tenant the HMAC-signed body actually originated from" — does not hold. An attacker who owns any shop that can install the target app can obtain a validly-signed `(raw_body, hmac)` pair from a real webhook delivery (e.g. `orders/create`), then resend that identical body+HMAC to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return `true` because it never inspects the header.

The gem's own documented usage pattern makes the `shop` field directly consumable as the trusted tenant key: [4](#0-3) 

This is not a case of "host app ignoring documented API" — the documented and intended integration pattern (`data.shop`) is exactly what is unauthenticated.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body (with attacker-chosen order/product/customer content, subject to Shopify's payload schema) can be attributed to an arbitrary victim shop domain in the receiving app, since nothing binds the signed bytes to the shop identity claimed in the header. Depending on how the host app persists/keys data by `shop_domain` (which the gem's own docs explicitly encourage — `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/confusion in the app's backend under a victim's identity, meeting the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
Requires only: (1) the attacker be able to install/trigger a webhook from a shop they control (a normal unprivileged action — creating a dev/trial store and generating events like `orders/create`), and (2) knowledge of the victim's `*.myshopify.com` domain (publicly discoverable/guessable). No access token, `api_secret_key`, or privileged account is required — the attacker only replays a webhook they legitimately received for their own store while forging a header value.

### Recommendation
Bind the shop identity to the signed material, e.g., include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in `to_signable_string`, or independently verify that the shop reported in the header matches a shop for which the app has an active session/installation *and* that the raw body/HMAC pair hasn't already been associated with a different shop. At minimum, document prominently that `Request#shop` must not be trusted as an authenticated tenant identifier on its own.

### Proof of Concept
1. Attacker creates/controls Shop A and installs the target Shopify app (normal, unprivileged onboarding).
2. Attacker triggers a webhook event (e.g., `orders/create`) and captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sent — this HMAC is valid because it is computed only from `raw_body` with the app's `client_secret` (server-side, attacker never sees the secret, but the resulting header value is delivered to them).
3. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of their own domain.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present) and `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC — the forged `shop` header is never verified.
5. The app's registered handler receives `data.shop == "victim-shop.myshopify.com"` alongside attacker-supplied `data.body`, processing/persisting attacker content under the victim shop's tenant key.

Note: I was unable to inspect `lib/shopify_api/webhooks/registry.rb`'s `process` method contents directly (only confirmed its existence via search), so the exact dispatch code path from `Registry.process` to the handler was not directly cited; the vulnerable trust boundary itself (unsigned `shop` header) is fully confirmed in `Request` and `HmacValidator`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
