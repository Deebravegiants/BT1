Found the identity-binding gap that matches the bug class: in `ShopifyAPI::Webhooks::Request`, the HMAC (`hmac-sha256` header) only signs the raw request body via `to_signable_string`, which simply returns `@raw_body` [1](#0-0) . The `shop` value used downstream by `Registry.process` to dispatch the webhook to the app's handler is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely outside the HMAC's signable string [2](#0-1) . `Registry.process` validates only the HMAC of the body and then trusts `request.shop` for tenant attribution when invoking `handler.handle` [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, breaking body↔tenant binding - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw JSON body, while the `shop` (tenant) attribute delivered to the app's `WebhookHandler` is taken from an unauthenticated HTTP header.

### Finding Description
`HmacValidator.validate` computes the signature over `to_signable_string`, and for `Webhooks::Request` that string is just `@raw_body` [1](#0-0) [4](#0-3) . The `shop` method exposed by `Request` (used as the tenant identifier passed to handlers) reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signed body [2](#0-1) . This breaks the intended equality: `hmac-authenticated body == the shop attributed to that body`. An attacker who controls the header (e.g., an intermediary or misconfigured proxy that forwards a valid Shopify-signed body but rewrites/duplicates the shop-domain header) can cause `Registry.process` to attribute a legitimately-signed payload to a different shop than the one whose secret actually produced the HMAC [5](#0-4) .

### Impact Explanation
If an app uses a shared `api_secret_key` model or exposes any component that echoes/allows header manipulation before reaching this gem (e.g., a shared HMAC secret across environments, or webhook forwarding infrastructure), the handler could execute business logic (e.g., `shop/redact`, data updates, cache invalidation keyed by `shop`) against the wrong tenant, i.e., cross-tenant data effects, since only the body—not the shop attribution—is authenticated.

### Likelihood Explanation
Low-to-moderate: exploitation requires an attacker or misbehaving intermediary capable of altering headers of an inbound request that still carries a validly-HMAC'd body, e.g., a proxy/load balancer bug, or an app that queues/relays webhook headers separately from bodies. This is not directly exploitable purely from `lib/shopify_api` in a single unmodified HTTP request between Shopify and app, but the library itself provides no defense — it never checks that the `shop` header is consistent with anything cryptographically verified.

### Recommendation
Include the shop domain (and ideally topic, api version) in the HMAC signable string, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the verified body before they are trusted by `Registry.process`.

### Proof of Concept
1. Attacker/relay intercepts a legitimate Shopify webhook POST (valid body + valid `x-shopify-hmac-sha256` for shop A).
2. Attacker forwards the same body/HMAC to the app but swaps `x-shopify-shop-domain` to shop B (or an attacker-controlled shop string).
3. `HmacValidator.validate(request)` still returns `true` because only `@raw_body` is verified [1](#0-0) .
4. `Registry.process` calls `handler.handle` with `shop: request.shop` set to the attacker-controlled value [6](#0-5) , causing tenant-mismatched processing.
