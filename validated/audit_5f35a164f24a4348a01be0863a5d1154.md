Based on my investigation, the claim is substantively accurate and describes a real, distinct security weakness.

Audit Report

## Title
Unauthenticated `requestID` squatting in confidential relay gateway handler enables frontrunning-style DoS - (File: `core/services/gateway/handlers/confidentialrelay/handler.go`)

## Summary
`HandleJSONRPCUserMessage` in the confidential relay gateway handler only validates that `req.ID` is non-empty and ≤200 characters, then immediately registers the request in a single global, unauthenticated map keyed purely by the client-supplied `req.ID`, before any identity/attestation check occurs. [1](#0-0)  `newActiveRequest` rejects any second request that reuses an already-occupied ID with `"request ID already exists"`. [2](#0-1)  Since the gateway explicitly documents itself as "a dumb relay" that "makes no trust decision" and defers all attestation/signature/quorum verification to the DON nodes, [3](#0-2)  an attacker can occupy a target `req.ID` at the gateway layer without ever needing valid attestation, since the ID-collision check happens strictly before fan-out to nodes.

## Finding Description
Unlike the `vault` handler, which runs `AuthorizeRequest` and namespaces the dedup key by `authorizedOwner + RequestIDSeparator + originalRequestID` before ever touching the pending-request map, [4](#0-3)  the confidential relay gateway handler performs no such binding: `req.ID` is used verbatim as the map key, with no per-caller/per-owner prefix and no authorization gate. The comments in the handler confirm this is by design — the gateway is meant to be a pass-through relay, with all real security enforcement (attestation hash verification, enclave-config matching, and Workflow-DON 2F+1 quorum authorization) happening later, in the DON-side `core/capabilities/confidentialrelay/handler.go` (`handleSecretsGet`/`handleCapabilityExecute`/`verifyWorkflowAuthorization`). Because the gateway's `newActiveRequest` dedup check runs *before* any of that downstream verification, an attacker's request does not need to pass attestation to occupy the ID slot — it only needs to reach `HandleJSONRPCUserMessage` with a colliding `req.ID`. The existing test `TestConfidentialRelayHandler_DuplicateRequestID` confirms the exact collision/rejection behavior. [5](#0-4)  The gateway's top-level `ProcessRequest` entrypoint also performs no authentication for new-style (non-legacy) JSON-RPC requests before dispatching to `HandleJSONRPCUserMessage`; it only decodes the request and length-checks the ID. [6](#0-5) 

## Impact Explanation
This maps to a legitimate DoS/availability impact: an unprivileged party who can reach the gateway's confidential-relay methods (`MethodSecretsGet`, `MethodCapabilityExec`) and who can guess or learn a target `req.ID` can block that specific request from being processed for up to `defaultRequestTimeoutSec` (30s), repeatable indefinitely at near-zero attacker cost. This is a genuine architectural gap relative to the sibling `vault` and `http_trigger_handler` handlers, which both bind the in-flight-request namespace to an authenticated identity before dedup-checking.

## Likelihood Explanation
Exploitability hinges entirely on whether an attacker can predict or observe a victim's `req.ID` before it is submitted. The report itself acknowledges this dependency ("Likelihood is high if request IDs used by legitimate clients/enclaves are predictable, reused across retries, or otherwise able to be inferred/guessed by a third party"), and cites the enclave's retry-loop behavior as the source of reused/predictable IDs. I was not able to fully verify from the available code how `req.ID` values are generated by the enclave client (e.g., whether they are high-entropy random UUIDs, sequential, or otherwise guessable) — this materially affects real-world likelihood, since a random 128-bit ID would make blind squatting infeasible, while a predictable or observable one would make it easy. This is a genuine open question that affects severity, not a fatal issue with the report itself: the underlying code-level flaw (missing authentication and per-identity namespacing at the gateway layer, unlike `vault`/`http_trigger_handler`) is real and independently verifiable regardless of ID entropy.

## Recommendation
Bind the confidential-relay gateway's active-request namespace to a verified requester/workflow identity (or at minimum an unguessable, gateway-generated correlation ID) rather than the raw client-supplied `req.ID`, mirroring the `vault` handler's owner-prefixing pattern, so that an unauthenticated third party cannot pre-claim an ID slot before the legitimate request/attestation is even evaluated.

## Proof of Concept
`TestConfidentialRelayHandler_DuplicateRequestID` already demonstrates the collision-based rejection mechanically: [5](#0-4)  a first `HandleJSONRPCUserMessage` call with `ID: "req-dup"` succeeds, and a second call with the same ID is rejected with `"request ID already exists"` — regardless of attestation, params, or caller identity. To weaponize: submit a `MethodCapabilityExec`/`MethodSecretsGet` JSON-RPC request to the gateway's confidential-relay endpoint with `ID` set to a known/guessed target ID before the legitimate request arrives; the legitimate request is then rejected outright until the squatted entry expires (~30s), and the attack can be repeated indefinitely.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {

		return err
	}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], labels requestLabels, callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID, "executionID", labels.ExecutionID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		labels:    labels,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())

func (g *gateway) ProcessRequest(ctx context.Context, rawRequest []byte, auth string) (rawResponse []byte, httpStatusCode int) {

		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
	isLegacyRequest := false
	var h handlers.Handler
	var handlerKey string
	if msg == nil || msg.Body.DonID == "" {
		serviceName := jsonRequest.ServiceName()

			h = handler
			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {
			// Fallback to legacy service name -> DON ID mapping
			if handler, ok := g.handlers[donID]; ok {
				h = handler
				handlerKey = donID
			}
		}
		if h == nil {
			return newError(jsonRequest.ID, api.HandlerError, "Service name not found: "+serviceName)
		}

		h, ok = g.handlers[handlerKey]

		}

	startTime := time.Now()

	callback := handlerscommon.NewCallback()
	if isLegacyRequest {

		err = h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)
