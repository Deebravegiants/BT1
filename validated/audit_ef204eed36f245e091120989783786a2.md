### Title
Passphrase auto-lock cache lifetime can be extended indefinitely past its configured `maxTtl`, bypassing the auto-lock security ceiling - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
The `PassphraseCache` module caches the wallet's decryption passphrase (used for `autoUnlock`) with a hard security ceiling (`config.maxTtl`, default 60 minutes) meant to guarantee the cached secret cannot outlive that window. However, once the exposed `restartAutoLockTimer()` / `scheduleClear()` path has been triggered even a single time, the cache's expiry check permanently switches to a branch that no longer references `maxTtl` at all, and can be re-armed indefinitely by repeated, unprivileged calls to a public application API method, exactly as the referenced report described locks being "merged" to exceed their intended `MAXTIME` ceiling.

### Finding Description
`PassphraseCache.get()` decides whether the cached passphrase is still valid using two mutually exclusive branches: [1](#0-0) 

- Before `inactiveAt` is ever set, validity is bounded by `addedAt + this.#maxTtl > Date.now()` — this is the intended absolute ceiling.
- Once `inactiveAt` is set (via `scheduleClear()`), validity switches permanently to `inactiveAt + ttl > Date.now()`. This branch never again consults `#maxTtl` or `addedAt`.

`scheduleClear()` is a public method that simply timestamps `INACTIVE_AT_KEY = Date.now()` and reschedules the alarm: [2](#0-1) 

It is invoked from the public, RPC-exposed `application.restartAutoLockTimer()` API method: [3](#0-2) 

which is exposed all the way to the SDK/RPC surface: [4](#0-3) [5](#0-4) 

Because `ttl` (an attacker/UI-controllable value, clamped only to `#maxTtl` via `changeTtl`) is re-applied from the moment of each `scheduleClear()` call, any caller with access to this RPC surface (e.g., the extension UI/renderer process across the `browser-extension-rpc` bridge) can call `restartAutoLockTimer()` repeatedly — at any interval shorter than `ttl` — and the check in `get()` will keep succeeding forever from `inactiveAt + ttl`, never re-imposing the `addedAt + #maxTtl` ceiling that was supposed to be the hard cap. This mirrors the reported ZeroLocker `merge` bug: a value meant to be capped at a maximum (`MAXTIME` there, `maxTtl` here) can be perpetually re-armed by repeatedly invoking a legitimate, low-privilege operation (`merge`/`restartAutoLockTimer`) before the previous window expires, defeating the intended hard limit entirely.

### Impact Explanation
`maxTtl` is the configured security ceiling meant to guarantee that a cached wallet-decryption passphrase (used by `#autoUnlock`) is never held longer than a bounded window: [6](#0-5) [7](#0-6) 

By bypassing this ceiling, the sensitive passphrase (which decrypts the wallet's seed/keys) can remain cached in storage indefinitely, well beyond the operator-configured `passphraseCacheMaxTtl`. This widens the exposure window for secret disclosure if the cache storage (session/unsafe storage) is ever compromised (e.g., via a compromised or malicious renderer/UI process talking to the background process over RPC), and defeats a deliberate defense-in-depth control designed to force periodic re-entry of the passphrase.

### Likelihood Explanation
`restartAutoLockTimer()` requires no special privilege beyond access to the application's own RPC-exposed API surface (the same surface any UI code, or a compromised/malicious script running in the wallet's own extension/renderer context, would use). No cryptographic bypass or elevated permission is needed — only repeated, benign-looking calls timed inside the existing `ttl` window, which is a low-effort, easily automatable action.

### Recommendation
In `PassphraseCache.get()`, always enforce the absolute ceiling regardless of activity state, e.g., require both `inactiveAt + ttl > Date.now()` AND `addedAt + this.#maxTtl > Date.now()` before returning the cached passphrase, so `scheduleClear()`/`restartAutoLockTimer()` can only ever extend validity within the original `maxTtl` window from `addedAt`, never beyond it.

### Proof of Concept
1. Configure `application({ cachePassphrase: true, passphraseCacheMaxTtl: 60 })` (60-minute ceiling) as in `features/application/src/index.ts`.
2. `unlock({ passphrase })` — this caches the passphrase and sets `ADDED_AT_KEY = Date.now()` (see `features/application/src/modules/application.ts:409-426`, `passphrase-cache.ts:50-59`).
3. Immediately (and repeatedly, before each `ttl`/auto-lock-timer window elapses) call `exodus.application.restartAutoLockTimer()`, which internally calls `passphraseCache.scheduleClear()` and resets `INACTIVE_AT_KEY = Date.now()` (`passphrase-cache.ts:101-109`).
4. Continue calling `restartAutoLockTimer()` at intervals shorter than the configured auto-lock `ttl` for longer than the 60-minute `maxTtl`.
5. Observe that `PassphraseCache.get()` keeps returning the cached passphrase well past `addedAt + maxTtl`, because the `inactiveAt`-based branch (`passphrase-cache.ts:70-74`) is the only one ever evaluated once `inactiveAt` is set, and it never re-checks `maxTtl`.

Note: I was not able to execute this against a running instance (index-only access), so this is a static-analysis-derived PoC based on the exact logic shown above; it should be validated by an engineer with runtime access to the wallet.
