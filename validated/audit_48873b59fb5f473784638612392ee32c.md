### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts unauthenticated headers — most importantly `shop`, but also `topic`, `webhook_id`, and `api_version` — to build the `WebhookMetadata` passed to the host app's handler. Because the HMAC signature only binds the raw body, an attacker who legitimately installs the target app on their own (attacker-controlled) shop can capture a genuinely-signed `(body, hmac)` pair from their own store's webhook delivery, then replay that exact body/HMAC pair directly against the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. the victim's shop). The signature still validates because it never covered the header, so the handler processes attacker-controlled body content under the identity of an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` simply reads the `shop-domain` header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body-based HMAC, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` (all unauthenticated headers) to construct the data forwarded to the app's handler: [4](#0-3) 

The equality the code implicitly assumes is:
`shop_that_produced_the_HMAC-signed_body == request.shop (header value used by the handler)`

This equality does not hold: the HMAC signature only proves that *some* body content was signed by Shopify (or by the shared `api_secret_key`) for *some* delivery — it says nothing about which shop's header accompanies it. Any actor who can install the app on a shop they control (an ordinary, unprivileged action — installing an app on your own store) can legitimately trigger webhook deliveries and thereby obtain arbitrarily many valid `(body, hmac)` pairs signed with the app's shared secret. They can then POST that exact body + HMAC to the app's public webhook endpoint while freely choosing the `shop-domain` (and `topic`/`webhook_id`) header value, since none of those headers are part of the signed material.

### Impact Explanation
This breaks the tenant/identity binding between the cryptographically authenticated payload and the shop the host application will act on. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., looking up/updating records, writing state, triggering side effects, or granting access) the attacker can inject attacker-controlled data that gets attributed to an arbitrary target shop, resulting in cross-tenant data corruption/injection. This matches the Critical "cross-tenant access" impact category: an unprivileged actor (their own shop's HMAC secret-signed traffic) is able to make the application treat their data as if it belongs to a different tenant.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's webhook verification exactly as documented: any Shopify merchant can install the app to obtain genuine signed webhook payloads for their own shop, then replay them at the app's public endpoint with a forged `shop-domain` header — no leaked secret, no privileged account, and no host-application logic error required; the gap exists purely in `HmacValidator`/`Webhooks::Request`/`Webhooks::Registry`.

### Recommendation
Bind the shop/topic/webhook identity into the material that is authenticated (or authenticate the delivery via a mechanism that ties body and headers together), for example: reject/flag mismatches where headers do not correspond to previously registered subscription details for that specific shop, or additionally verify that the `shop-domain` header corresponds to a session/shop actually known to have this webhook topic registered before invoking the handler, rather than trusting the header at face value once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (ordinary, unprivileged action).
2. Attacker triggers an event (e.g. updates a product) causing Shopify to deliver a webhook to the app's endpoint with a real `raw_body` and a real `x-shopify-hmac-sha256` computed with the app's `api_secret_key` — attacker captures this `(body, hmac)` pair from their own store's delivery (or via their own reverse proxy/logging).
3. Attacker sends a new HTTP POST directly to the app's public webhook endpoint using the exact same `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body, and `Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-199) forwards `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body` to the app's handler, which will process/store this as data belonging to `victim-shop`.
