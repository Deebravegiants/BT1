Audit Report

## Title
Failed refund-swap fallback forwards entire pre-correction fee and skips `AssetRefundFailed` event, causing potential overcharge - (File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs)

## Summary
In `SwapAssetAdapter::correct_and_deposit_fee`, when the reverse quote used to convert the unspent native refund back into the user's `asset_id` fails (`quote_price_exact_tokens_for_tokens` returns `None`/zero) or `F::can_deposit` fails, the code forwards the entire pre-correction `fee_paid` credit to `OU::on_unbalanceds` and returns the unmodified pre-correction `fee_asset_amount`, which is then reported as `actual_fee` in `AssetTxFeePaid`. [1](#0-0)  The `AssetRefundFailed` event that exists in `lib.rs` specifically to signal this condition is never deposited anywhere in the codebase. [2](#0-1) 

## Finding Description
The code and control flow described in the claim is accurate: when `refund_asset_amount.is_zero()` or `can_deposit` fails, the branch splits `fee_paid` (the full amount of native asset withdrawn pre-correction) into tip/fee, forwards both to `OU::on_unbalanceds`, and returns the original `fee_asset_amount` rather than a value reflecting the corrected fee. [3](#0-2)  This value is used verbatim as `actual_fee` in the `AssetTxFeePaid` event. [4](#0-3)  Grep confirms `AssetRefundFailed` is defined but has zero other references in the repository, meaning it is dead code — never deposited by `payment.rs` or anywhere else.

However, the report's attack model has a critical flaw: `TransactionExtension` hooks (`validate` → `prepare` → dispatch → `post_dispatch_details`) execute atomically for a single extrinsic within `apply_extrinsic`. There is no interleaving point where an attacker's separate extrinsic can execute *between* the victim's `prepare` (where `withdraw_fee` runs, using `quote_price_tokens_for_exact_tokens`) and the victim's `post_dispatch_details` (where `correct_and_deposit_fee` runs, using `quote_price_exact_tokens_for_tokens`) — these are two steps of the same atomic extrinsic execution. The report's claim that "an attacker submits a large swap extrinsic... to drain/skew the pool between the victim's `validate`/`prepare` step and `post_dispatch_details` in the same block" describes an execution ordering that FRAME does not permit: extrinsics are applied fully, one at a time, sequentially; no other extrinsic can run mid-way through another extrinsic's lifecycle.

A more realistic variant — an attacker's swap extrinsic placed immediately *before* the victim's entire extrinsic in the same block — would need the drained pool state to make the *forward* quote (`quote_price_tokens_for_exact_tokens`, used in `withdraw_fee`) still succeed while the *reverse* quote (`quote_price_exact_tokens_for_tokens`, used in `correct_and_deposit_fee`, for a strictly smaller `refund_amount`) subsequently fails or produces a `can_deposit`-rejected amount. This is a real AMM path-dependent scenario, but the report does not establish this variant, does not analyze `quote_price_exact_tokens_for_tokens`'s actual failure conditions (pool non-existence vs. low-liquidity slippage), and does not provide the proof-of-concept it claims to describe — no actual test code was included, only a template of steps.

## Impact Explanation
If the fallback branch is reached, the fee-payer's outstanding fee accounting reflects the pre-correction amount, which the code comments themselves explicitly acknowledge as an intentional trade-off ("No refund given if it cannot be swapped back") rather than an oversight. There is no crediting of the excess to `OU`'s target beyond what was legitimately owed by the withdrawal at `prepare` time — this is the same mechanism used generically whenever a swap-based refund can't be completed (e.g., pool illiquidity, deregistered pool, frozen asset, `can_deposit` limits) and is not unique to attacker-induced pool draining. The report correctly identifies that `AssetRefundFailed` is unused dead code, which is a legitimate observability/tooling gap, but this alone does not constitute a fund-loss or accounting-break vulnerability — it is a missing diagnostic event.

## Likelihood Explanation
The core exploit precondition described (interleaving an attacker's extrinsic between two steps of the victim's single extrinsic's lifecycle) is not supported by FRAME's atomic extrinsic execution model, which the report does not account for. The report does not demonstrate the narrower, plausible variant (front-running before the entire victim extrinsic) with a working PoC; it only outlines a test plan, which was not executed or verified. Given the code comments show explicit design acceptance of this fallback for edge cases (unswappable refund), and the report conflates a known/documented limitation with a novel unrealized vulnerability, this does not meet the bar of a concrete, reproducible, in-scope exploit.

## Recommendation
N/A (claim rejected — see analysis above). Independently, wiring up the unused `AssetRefundFailed` event in the fallback branches of `correct_and_deposit_fee` would be a reasonable observability improvement, but this is a minor code-quality/monitoring gap, not a fund-safety vulnerability as currently demonstrated.

## Proof of Concept
Not provided by the report as a working test; only a template of manual steps was given, and the underlying attack-ordering assumption (interleaving within a single extrinsic's lifecycle) is not achievable in FRAME's extrinsic execution model.
