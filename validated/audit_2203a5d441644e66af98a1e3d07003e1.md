### Title
Pharos SPV internal-node hash collision from positional information loss - (`modules/consensus/pharos/primitives/src/spv.rs`)

### Summary
`hash_internal_node` in the Pharos SPV verifier reconstructs a trie internal-node hash by concatenating only the *non-zero* fixed-size slots of the node and hashing the result, discarding which slot index each value came from. This is the same bug class as the reported `compute_digest_for_modules_and_deps` collision: concatenating variable-composition data without a positional delimiter/padding lets structurally different inputs produce identical hashes.

### Finding Description [1](#0-0) 

```rust
fn is_zero_slot(slot: &[u8]) -> bool {
	slot == ZERO_HASH
}

/// SkipEmpty: `sha256(3-byte header || non-zero slots)`. All-zero node hashes to `[0; 32]`.
fn hash_internal_node(proof_node: &[u8]) -> [u8; 32] {
	let mut data = Vec::with_capacity(INTERNAL_NODE_LEN);
	data.extend_from_slice(&proof_node[..INTERNAL_NODE_HEADER]);

	for i in 0..INTERNAL_NODE_SLOTS {
		let start = INTERNAL_NODE_HEADER + i * INTERNAL_NODE_SLOT_SIZE;
		let slot = &proof_node[start..start + INTERNAL_NODE_SLOT_SIZE];
		if !is_zero_slot(slot) {
			data.extend_from_slice(slot);
		}
	}

	if data.len() == INTERNAL_NODE_HEADER {
		ZERO_HASH
	} else {
		sha256(&data)
	}
}
```

The function builds `data` by iterating over `INTERNAL_NODE_SLOTS` fixed-size positions and appending only the non-zero ones, with **no index/position marker** for the slots that were skipped. Because every appended slot has the identical fixed size (`INTERNAL_NODE_SLOT_SIZE`), the resulting byte stream is indistinguishable between two different "shapes" of the sparse node as long as the sequence of non-zero values (in slot order) is the same — exactly analogous to the reported `MovePackage::compute_digest_for_modules_and_deps` bug, where omitting length-based/positional separation between concatenated items let a two-item input collide with a one-item input. Here, a node with non-zero children at positions `{2, 5}` holding values `[A, B]` hashes identically to a node with non-zero children at positions `{3, 4}` holding the same two values `[A, B]` in the same order, since both reduce to `header || A || B` before hashing.

This function is used by `compute_node_hash` to derive the hash committed to by parent nodes in the Pharos state proof structure, so this is directly reachable by an unprivileged relayer/prover submitting a Pharos consensus/state proof to `pallet-ismp`/the Pharos state machine client for state membership/non-membership verification.

### Impact Explanation
If the hash of the true internal node structure collides with a differently-shaped (attacker-fabricated) node, a relayer could submit a forged `SkipEmpty`/internal proof node whose recomputed hash still matches the parent-referenced digest, while the actual child/value layout it encodes differs from the genuine on-chain trie contents. Since Hyperbridge's state-proof verification path uses this hash to validate the integrity of the Merkle path from root to leaf for Pharos L2 state commitments, a successful collision would let an attacker present forged storage values as verified state, undermining the soundness of the state membership/non-membership proof for that state machine — potentially forging message delivery receipts or state commitments consumed by `pallet-ismp` handlers.

### Likelihood Explanation
Exploitability depends on details I could not fully verify in the time available (exact `INTERNAL_NODE_SLOTS`/`INTERNAL_NODE_SLOT_SIZE` values, whether some other binding — e.g., a bitmap of occupied slots inside the 3-byte header, or the value of `INTERNAL_NODE_HEADER` — already encodes which positions are non-zero and therefore forecloses the collision). I could not read the full file or the calling `compute_node_hash`/proof-verification code to confirm whether the 3-byte header already carries a slot-occupancy bitmap that would prevent this collision; if it does, this specific instance may not be exploitable. This uncertainty should be resolved by reviewing the full file and its callers before treating this as confirmed.

### Recommendation
Bind the slot index into the hashed data for every included slot (e.g., hash `header || index_1 || slot_1 || index_2 || slot_2 || ...` or hash the full fixed-length array including zero slots) so that the digest is a function of both position and value, eliminating the possibility that two structurally different nodes serialize to the same byte stream before hashing — mirroring the Move fix of hashing each item individually and then hashing the concatenation of the individual digests.

### Proof of Concept
Conceptual (I was not able to inspect `INTERNAL_NODE_HEADER`/`INTERNAL_NODE_SLOTS` constants or the encoding of the 3-byte header to build a concrete byte-level PoC in the time available):
1. Construct genuine `proof_node_A` with non-zero 32-byte slots `A` at index 2 and `B` at index 5, all others zero.
2. Construct forged `proof_node_B` with non-zero slots `A` at index 3 and `B` at index 4, all others zero, same header bytes.
3. `hash_internal_node(proof_node_A) == hash_internal_node(proof_node_B)` because both produce `header || A || B` prior to `sha256`.
4. If the parent node's proof only checks this collapsed hash, a relayer can substitute `proof_node_B` for the true `proof_node_A` and still pass verification while attesting to different child slot positions/values downstream.

This PoC's validity hinges on the unverified header/slot semantics noted above — I recommend a Devin session with full file access to confirm whether the header already prevents this collision before treating the finding as fully proven.
