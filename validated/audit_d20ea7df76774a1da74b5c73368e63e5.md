### Title
Zero-amount bridge messages permanently revert `WrappedHyperFungibleToken` delivery/timeout when the wrapped underlying reverts on zero-value transfers - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.SendParams.amount` and the corresponding `WrappedHyperFungibleToken.send()` entry point never validate `amount > 0`. The unvalidated amount is embedded in the cross-chain `Message` and later replayed unconditionally through `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` in both `onAccept()` and `onPostRequestTimeout()`. Per the same weird-ERC20 class referenced in the original report (`d-xo/weird-erc20#revert-on-zero-value-transfers`, e.g. LEND), some ERC20s revert on a `transfer`/`transferFrom` of `0`. Any unprivileged token bridger can self-dispatch (or grief another user by manipulating) a `send()` with `amount == 0`, producing a POST request whose delivery on the destination (`onAccept`) — and, if it times out, the refund on the source (`onPostRequestTimeout`) — both unconditionally call `safeTransfer(..., 0)` and permanently revert if the wrapped underlying is one of these tokens.

### Finding Description
`WrappedHyperFungibleToken.send()` pulls `params.amount` into escrow (`safeTransferFrom`) without any zero check: [1](#0-0) 

The message is built and dispatched as-is, then on the destination chain `onAccept()` unconditionally forwards `message.amount` to the beneficiary via `safeTransfer`: [2](#0-1) 

If the ISMP message times out instead of being delivered, `onPostRequestTimeout()` performs the same unconditional `safeTransfer(refundee, message.amount)` on the source chain: [3](#0-2) 

`HyperFungibleToken.SendParams.amount` (shared struct used by both the burn/mint and lock/unlock variants) has no `InvalidAmount`/`amount == 0` guard anywhere in `HyperFungibleToken.sol` or `WrappedHyperFungibleToken.sol` (confirmed by search — the only `amount == 0` checks in the repo's Solidity code exist in the unrelated `IntentGatewayV2.sol` order-input validation paths, not in the HFT/WrappedHFT bridge apps). This mirrors exactly the root cause of the referenced report: an unguarded ERC20 transfer of a possibly-zero amount, reachable by an ordinary caller (here: any token bridger calling `send()`), against a token type documented to revert on zero-value transfers.

### Impact Explanation
Because `onAccept` is invoked by `EvmHost`/the ISMP module-callback dispatch path when the relayed POST request is delivered, a revert inside `onAccept` for a zero-amount message means that specific request cannot be successfully processed — the module callback for this commitment will always revert, for as long as the underlying token continues to revert on zero transfers, which is a permanent property of the token (not balance-dependent, unlike PublicVault's case, making it strictly deterministic and unavoidable). If the message instead reaches its timeout window and a relayer submits the timeout proof, `onPostRequestTimeout` deterministically reverts too, so the refund path is equally blocked. This is a route unable to deliver a specific message/permanently freezes the bridged escrow for that commitment, since neither delivery nor timeout-refund can ever succeed for that request.

### Likelihood Explanation
Likelihood is high for any `WrappedHyperFungibleToken` deployment that wraps a token from the well-documented "revert on zero transfer" class. Triggering it requires only a single unprivileged call to `send()` with `amount = 0` (or an amount that a malicious/careless integrator computes to be `0` after fee/precision truncation), which any token bridger can submit without special privileges, capital, or front-running — unlike the original PublicVault finding, no specific balance state needs to be engineered.

### Recommendation
Add an explicit `amount == 0` revert (e.g. `InvalidAmount()`) in `WrappedHyperFungibleToken.send()` and `HyperFungibleToken.send()` before escrowing/burning, so zero-amount messages can never be dispatched. As defense in depth, also guard the `safeTransfer` calls in `onAccept()` and `onPostRequestTimeout()` (both in `WrappedHyperFungibleToken.sol` and any peer contracts using the same pattern) with `if (message.amount > 0) { ... }`, matching the mitigation the original report's sponsor confirmed ("just return and do nothing" for zero amounts).

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` wrapping an ERC20 that reverts on zero-value `transfer` (e.g. LEND-style token), per [1](#0-0) .
2. Any user calls `send({..., amount: 0, ...})`; since `amount == 0`, `safeTransferFrom` for a standard ERC20 succeeds trivially (no zero-transfer restriction on the locking side unless the token also reverts there), and the message is dispatched with `message.amount = 0`.
3. On delivery, the relayer submits the proof; `EvmHost` invokes `onAccept()`, which executes `IERC20(_underlying).safeTransfer(beneficiary, 0)` — the underlying token reverts, so the module callback reverts and the request can never be successfully delivered, per [4](#0-3) .
4. If instead a timeout proof is submitted, `onPostRequestTimeout()` similarly reverts on `safeTransfer(refundee, 0)`, per [3](#0-2) , permanently blocking both the delivery and refund paths for that commitment.

Note: I was unable to fully verify, within the available tool budget, whether `HandlerV2`/`EvmHost` isolates a single failing `onAccept` call from the rest of a batched delivery (i.e., whether other unrelated messages in the same batch are also blocked) — this would affect the blast radius but not the core validity of the permanently-stuck-message finding for the specific commitment.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
