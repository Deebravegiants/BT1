Confirmed: the `Message.from` field in `HyperFungibleToken`'s cross-chain ABI body is a Solidity `bytes` (arbitrary length), set by the *sending* contract's caller on the source chain (`from: abi.encodePacked(msg.sender)` in the Solidity contract on send, but the pallet on the Substrate side has no control over what an EVM peer contract puts there, and this is exactly the field the reporter — an unprivileged token bridger dispatching a cross-chain transfer — controls end-to-end through `SendParams`/the source EVM contract's own `Message.from`). On the receiving pallet side this field is consumed in an unchecked fixed-size copy.

### Title
Unvalidated length in HFT `Message.from` causes panic (DoS) in `on_accept` origin derivation - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` decodes the ABI-encoded `Message { from, to, amount, data }` body of an incoming ISMP `PostRequest` and, when calldata execution is requested without a signature, derives the dispatch origin from `message.from` using a fixed-size copy/slice without validating its length first, mirroring the libtiff bug class (a copy operation sized against the wrong length metadata rather than the actual buffer size).

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs` (`on_accept`), when `message.data` is non-empty and no `signature` is supplied in `SubstrateCalldata`, the origin is derived directly from the attacker/peer-controlled `message.from` bytes: [1](#0-0) 

- If `source.is_evm()`: `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, producing an out-of-range index and panicking.
- Otherwise: `account.copy_from_slice(from_bytes)` into a `[0u8; 32]` — if `from_bytes.len() != 32`, `copy_from_slice` panics on the length mismatch, exactly the "copy sized against a mismatched length" bug class the CVE describes for `_TIFFmemcpy`.

`message.from` is a Solidity `bytes` field inside the ABI-encoded `Message` struct (`bytes from; bytes to; uint256 amount; bytes data;`), decoded via `Message::abi_decode(&body)`: [2](#0-1) 

This field is set by whatever contract sends the cross-chain message, and its length is unconstrained by the ABI type (`bytes` is variable length) and unvalidated by the receiving pallet. The only pre-existing checks are for `message.to` (validated to be 20 or 32 bytes), not `message.from`: [3](#0-2) 

The `ContractToAsset::<T>::get(source, &from)` check authenticates the *ISMP request's* `from` (the dispatching contract address on the peer chain), which is a separate field from `message.from` inside the ABI body — it does not constrain the length or content of `message.from`.

### Impact Explanation
A crafted `message.from` of length `< 20` (when `source.is_evm()`) or any length other than exactly 32 (for non-EVM sources), combined with a non-empty `message.data` and no `signature`, causes an unhandled Rust panic inside `on_accept`. Since `on_accept` executes as part of message delivery through `pallet-ismp`'s `handle_unsigned`/dispatch path, a panic here traps the runtime call, aborting extrinsic execution — a denial-of-service against the token bridge's message-handling path for any request that reaches this branch, reachable from a single relayed cross-chain PostRequest. This matches the CVE's severity class: memory-safety-adjacent crash from a length-mismatched copy, producing DoS impact rather than fund theft.

### Likelihood Explanation
Reachable by any unprivileged actor able to get an authorized peer contract to relay a `PostRequest` with attacker-influenced `Message.from`/`data` (e.g., a malicious or compromised integrating dApp on the EVM side that lets users set `from` freely, or any bridging flow where the `from` field isn't strictly enforced to be the transaction sender's address bytes) — no privileged access, governance, or key compromise required. The trigger only requires reaching the calldata-execution branch (`data` non-empty, `signature` absent), which is a normal, supported feature path (transfer-and-call).

### Recommendation
Validate `message.from.len()` before using it, mirroring the length check already applied to `message.to`:
- For `source.is_evm()`, require `from_bytes.len() >= 20` before slicing the last 20 bytes (or require exactly 20).
- For non-EVM sources, require `from_bytes.len() == 32` before `copy_from_slice`.
Return a descriptive `HftError` (e.g., `InvalidSenderLength`) instead of panicking, consistent with the existing `HftError::InvalidRecipientLength` pattern used for `message.to`.

### Proof of Concept
1. On the EVM source chain, dispatch (or have a compromised/misconfigured integrator dispatch) a `PostRequest` to the HFT pallet with body `abi.encode(Message{ from: <bytes of length 5>, to: <valid 20-byte address>, amount: X, data: <non-empty SCALE-encoded SubstrateCalldata with signature = None> })`.
2. `on_accept` decodes the message, mints/transfers as normal, then reaches the calldata branch; since `source.is_evm()` is true and `from_bytes.len() = 5 < 20`, `from_bytes.len() - 20` underflows, causing an index-out-of-range panic (or, for a non-EVM source with a `from` of length ≠ 32, `copy_from_slice` panics directly on the length mismatch).
3. The panic aborts extrinsic execution, denying delivery of that (and potentially subsequent, depending on runtime panic-handling) message(s).
