### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct and then trusts the header-derived `shop` value when invoking the app's handler. Any party who can obtain one valid `(body, hmac)` pair — e.g. an attacker who has installed the app on their own store and receives a legitimately signed webhook — can replay that body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process the webhook as if it belonged to a different, victim shop.

### Finding Description
The HMAC is computed exclusively over `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards the header-derived `shop` (along with `topic`, `body`, `webhook_id`, `api_version`) to the registered handler without any additional binding check between the signed body and the shop claim: [3](#0-2) 

The identity binding broken is:
`hmac_signed(raw_body) == valid` should imply `shop_header == shop_that_produced(raw_body)`, but the gem only checks `hmac_signed(raw_body) == valid`, never binding `shop_header` to the body that was actually HMAC'd.

Because `api_secret_key` (the app's client secret) is shared across every shop that installs the app, any attacker who installs the same app on their own store receives genuinely Shopify-signed webhooks (valid body + HMAC pair) for their own shop. They can capture such a delivery and replay it to the app's public webhook callback URL, overriding only the `x-shopify-shop-domain` header to name any victim shop. `HmacValidator.validate` re-derives the signature from `to_signable_string` (the body) and the shared secret, so the forged request passes validation exactly as if it were a real webhook for the victim shop: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the `shop` identity is trustworthy once HMAC validation succeeds — but that guarantee does not hold for the `shop` field itself: [5](#0-4) 

This is analogous to the reported bug class of "a field acted on but not covered by the HMAC" — here the tenant-identifying `shop` field is the unauthenticated field, and the webhook body/HMAC is the covered-but-irrelevant-to-tenant-binding field.

### Impact Explanation
Applications built on this gem commonly key their tenant data (job dispatch, database writes, order/customer processing, `shop/redact`, `customers/redact`, `customers/data_request`, etc.) by `data.shop` as documented in `docs/usage/webhooks.md`. An attacker who is a legitimate (if low-privilege) merchant using the same app can forge the `shop` identity on a webhook delivery and cause the host application to attribute attacker-supplied webhook payloads to an arbitrary victim shop, achieving cross-tenant data injection/confusion inside the merchant's app — a Critical-impact cross-tenant access issue per the rules, achieved purely through this gem's own webhook verification code path.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on their own Shopify development/trial store (a normal, unprivileged action any internet user can perform for a public app), (2) capture one legitimate webhook delivery (body + HMAC header) sent to their own store, and (3) POST that same body/HMAC to the app's public webhook endpoint with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or the victim's credentials is needed. This is a straightforward replay achievable by any unprivileged actor with app access.

### Recommendation
Bind the `shop` (and other trust-relevant headers) into the HMAC-signed material, or otherwise cryptographically tie the shop identity to the body before trusting it. Concretely, `Request#to_signable_string` could incorporate the `shop` header (matching the documented behavior of some other Shopify libraries), or `Registry.process`/`HmacValidator` could be extended to verify that the delivering shop is registered/expected for the associated webhook subscription rather than trusting the raw header unconditionally.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends the attacker a legitimately signed webhook, e.g. for `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over body B>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body `B`
3. Attacker replays the identical body `B` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not authenticity, of headers is checked): [6](#0-5) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `B`, not the shop header: [7](#0-6) 
6. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host application processes attacker-controlled data attributed to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
