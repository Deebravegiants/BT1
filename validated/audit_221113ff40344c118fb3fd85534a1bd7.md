Audit Report

## Title
GraphQL mutation passwords (e.g. `CreateAPIToken`, `UpdateUserPassword`) are logged in plaintext in the web request debug log due to shallow, top-level-only body redaction - ([File: core/web/router.go])

## Summary
The gin request-logging middleware `loggerFunc` (core/web/router.go:534-569) logs every request body via `readBody`/`readSanitizedJSON` at Debug level, but `readSanitizedJSON` (core/web/router.go:608-629) only redacts blacklisted keys found at the *top level* of the parsed JSON object. The GraphQL endpoint `POST /query` wraps mutation arguments inside `variables.input.password`, a nested field that the redaction logic never inspects, so plaintext passwords submitted to mutations like `CreateAPIToken` are written unredacted to the node's debug logs.

## Finding Description
`loggerFunc` is registered as global middleware on the gin engine (core/web/router.go:64-72) and applies to `POST /query` (core/web/router.go:95-99) as well as all other routes. It buffers the request body, executes the handler, and logs the raw body string produced by `readBody` at `Debug` level [1](#0-0) .

`readBody` delegates to `readSanitizedJSON`, which unmarshals the body into `map[string]any` and iterates only the top-level `k, v := range dst` pairs, redacting a value only if `isBlacklisted(k)` matches [2](#0-1) . There is no recursive descent into nested maps or slices.

For classic REST endpoints such as `POST /v2/user/token`, `password` is a top-level JSON key so it is correctly redacted, matching `UserController.NewAPIToken`'s `ChangeAuthTokenRequest{Password}` binding [3](#0-2) .

However, GraphQL requests to `/query` place mutation arguments inside a nested structure: `{"query": "...", "variables": {"input": {"password": "..."}}}`. The top-level keys are only `query`/`variables`/`operationName` — `password` never appears at the top level, so `isBlacklisted` never triggers on it, and the nested `password` value passes through to the log verbatim. This directly affects `CreateAPIToken`, which accepts `args.Input.Password` and uses it to authenticate the user's real password via `TestPassword` [4](#0-3) , and equivalently affects other password-carrying mutations such as `UpdateUserPassword`.

The `/query` route is protected by `auth.AuthenticateGQL`, meaning the vulnerable code path is exercised during completely ordinary, legitimate use (e.g., the Operator UI itself calling `CreateAPIToken`), not by any attacker-crafted or adversarial payload — the flaw is purely in the logging/redaction layer, not the auth layer.

## Impact Explanation
When `Log.Level = 'debug'` is set (a normal, documented, supported node configuration), any user's real account password sent to confirm a GraphQL mutation is persisted in cleartext in the node's application logs. This is a genuine secret/credential-disclosure defect in the redaction control that Chainlink itself put in place specifically to prevent password leakage (the `blacklist`/`isBlacklisted` mechanism), and it fails against a data shape (nested JSON) that the GraphQL API routinely produces. If such logs are exported, aggregated, or shared for support purposes, an attacker with access to them recovers a live account password, which can then be used to log in or to justify further password-confirmed operations. This falls under the "secret/key exfiltration via logging" impact class referenced in scope.

## Likelihood Explanation
No privileged or admin access is required beyond the ordinary authenticated session/API-token-holder needed to call any GraphQL mutation — this mirrors normal UI behavior when minting an API token or changing a password. The only additional precondition is the operator running with Debug logging, which is a common, legitimate operational choice for troubleshooting, not a hardening bypass. Because the vulnerable code executes on every normal GraphQL mutation call carrying a password, the leak is deterministic and repeatable, not a one-off edge case.

## Recommendation
- Make `readSanitizedJSON` recursively walk `map[string]any` and `[]any` values, applying `isBlacklisted` at every nesting level, not just the top level.
- Alternatively, exclude the raw `/query` GraphQL body from full-body debug logging, or strip an explicit denylist of GraphQL input fields (e.g., all `password`-named fields under `variables`) prior to logging.
- Add regression tests (e.g., extending `TestCheckLoginAuditLog`-style coverage) asserting that a GraphQL body containing `variables.input.password` is redacted in `readSanitizedJSON`'s output.
