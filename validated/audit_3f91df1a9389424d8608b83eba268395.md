### Title
Webhook shop-domain/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when invoking the app's handler. Because the HMAC signature never covers these header-derived fields, a request whose body/HMAC pair was legitimately produced by Shopify for one tenant can be replayed with forged header values (in particular the shop domain) to make the app process it as if it came from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`), independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` gates on this HMAC check alone, and then constructs the metadata passed to the app's handler directly from the unauthenticated header fields (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`), while only `request.parsed_body` is guaranteed to be tied to the HMAC: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, raw_body ‖ shop ‖ topic)`. In reality the gem only enforces `hmac == HMAC(secret, raw_body)`, leaving `shop`/`topic`/`webhook_id` fully attacker-controllable at the transport layer whenever the attacker can present a body+HMAC pair that Shopify legitimately produced (e.g., from a webhook fired for the attacker's own shop, which the attacker fully controls and can trigger events for). The docs confirm the endpoint is a plain public HTTP route the app operator exposes, reachable by anyone who can send it a POST: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who installs the target app on their own store (a normal, unprivileged tenant) can capture a real Shopify-issued webhook `raw_body` + `x-shopify-hmac-sha256` pair for their own shop, then POST it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or a different `x-shopify-topic`/`webhook-id`). `Registry.process` will pass HMAC validation (body unchanged) and invoke the registered handler with `WebhookMetadata#shop` set to the forged victim domain. Any app logic that trusts `data.shop` to select which tenant's records to update, delete, or reset (which is the documented/expected use of this field) can then be made to act on the wrong tenant's data — a cross-tenant integrity/confidentiality break driven entirely by this gem's failure to bind the shop identity to the signature.

### Likelihood Explanation
Likelihood is moderate-to-high: any external party can self-install the app (most Shopify apps allow public installs) to obtain a validly-signed body/HMAC pair for at least the mandatory topics (`customers/data_request`, `customers/redact`, `shop/redact`) and any subscribed topic, then replay it against the public webhook route with a rewritten shop header. No access token, `client_secret`, or privileged account is required — only the ability to install the app once and to send arbitrary HTTP requests to its documented webhook endpoint.

### Recommendation
Bind the shop (and ideally topic) into the value that is actually authenticated, or otherwise verify header-derived identity against server-side state before trusting it:
- Include `shop`/`topic` in the HMAC-covered signable string if Shopify's webhook signing were extended to support it, or
- At minimum, require the application/gem to cross-check the header `shop` value against an independently known, previously-registered shop (e.g., verify the shop is one for which this app currently holds a session/webhook registration for that exact `topic`+`webhook_id` combination) before invoking the handler, rather than trusting `request.shop` derived purely from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` and lets Shopify fire a real webhook (e.g. `orders/create` or a mandatory GDPR topic) to the app's public webhook endpoint. Attacker captures the raw POST: `raw_body` and header `x-shopify-hmac-sha256: H`.
2. Attacker sends a new POST to the same public endpoint with the same `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches `H`, so validation passes: [6](#0-5) 
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"`: [7](#0-6) 
5. Any handler logic keyed off `data.shop` now operates as though the (attacker-controlled) payload belongs to the victim shop, despite the HMAC signature only ever having verified the payload for the attacker's own shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
