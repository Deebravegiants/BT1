### Title
Fixed escrowed `order.fees` payout in `IntentsBase._withdraw` can permanently freeze order escrow if the fee token's balance shrinks below the recorded amount - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`_withdraw` in `IntentsBase.sol` releases an order's escrowed input tokens and its recorded `order.fees` (stored as `TRANSACTION_FEES`) in a single atomic call, using `IDispatcher(host()).feeToken().safeTransfer(beneficiary, fees)` for a fixed amount recorded at `placeOrder` time. If the fee token's `balanceOf(gateway)` ever drops below that recorded `fees` value (e.g., a rebasing/elastic-supply token, or one with negative rebasing/slashing), `safeTransfer` reverts, which reverts the *entire* `_withdraw` call — including the loop that releases the unrelated escrowed input tokens that had nothing to do with the shortfall. Since this is invoked from `onAccept` when Hyperbridge delivers the `RedeemEscrow`/`RefundEscrow` message, and there is no alternate code path to release escrow independent of the fee payout, the order's escrow becomes permanently stuck as long as the shortfall persists.

### Finding Description
`order.fees` is collected into the gateway at `placeOrder` time and recorded per-commitment as a fixed nominal amount (`_orders[commitment][TRANSACTION_FEES] = order.fees;`), exactly analogous to the reported `i_arbiterFee` fixed value: [1](#0-0) 

At redemption time, `_withdraw` releases the escrowed input tokens for the order and, when `finalize` is true, also transfers the *fixed* recorded fee amount out of the gateway's current balance of the fee token — with no check that the current balance actually still holds that much: [2](#0-1) 

This function is called from the ISMP `onAccept` handler when the cross-chain `RedeemEscrow` (successful fill settlement) or `RefundEscrow` (cancellation) message is delivered by a relayer, i.e., from a single relayed/dispatched message a relayer or any caller can trigger: [3](#0-2) 

Because Solidity reverts are atomic, if `IERC20(feeToken).safeTransfer(beneficiary, fees)` fails (insufficient current balance), the preceding loop that decrements `_orders[commitment][token]` and transfers the *escrowed input tokens* to the beneficiary is also rolled back — even though those input tokens are unrelated to the fee token and may be fully solvent. There is no retry/skip path that lets the input-token release proceed independently of the fee payout; `_withdraw`'s `finalize` branch couples both transfers into one atomic step.

The fee token is a governance-configured ERC-20 (`IDispatcher(host()).feeToken()`), and the codebase's own vault documentation confirms rebasing/elastic-supply assets are an explicitly-known risk class for token accounting in this repo (`StreamingYieldVault` calls out "Fee-on-transfer and rebasing assets desync ... accounting" as a real concern for ERC-20 integrations here): [4](#0-3) 

If the deployed `feeToken` is ever a rebasing/elastic asset (or one subject to any mechanism reducing the gateway's held balance below the sum of outstanding recorded `order.fees` across pending orders — e.g. via governance re-pointing `feeToken`, a token migration, or a slashing/negative-rebase event), any order whose `RedeemEscrow`/`RefundEscrow` settlement lands after the shortfall becomes stuck: the message can be redelivered indefinitely and will keep reverting, since the shortfall condition doesn't self-resolve, permanently freezing both the escrowed input tokens and the fee for that order (and potentially cascading to every order sharing that fee-token pool).

### Impact Explanation
This is a permanent freezing-of-funds bug reachable via a single relayed ISMP message (`RedeemEscrow`/`RefundEscrow` on `onAccept`), a path explicitly in scope. Once the fee-token balance shortfall exists, solvers who already delivered outputs to users on the destination chain cannot ever redeem their escrowed input tokens on the source chain, and users cannot get cancellation refunds either — because the exact same atomic `_withdraw` path is used for both success and refund cases. This can lock arbitrary amounts of user/solver funds indefinitely with no recovery mechanism in the given code.

### Likelihood Explanation
Likelihood depends on the fee token's properties remaining a plain, non-rebasing ERC-20 for the life of every outstanding order. Given `feeToken` is a governance-mutable address (`IDispatcher(hostAddr).feeToken()`) and the protocol explicitly documents awareness of rebasing-token accounting hazards elsewhere in the codebase, a future governance change of `feeToken` to (or a bridged/aliased fee token becoming) a rebasing asset is a realistic scenario the contract does not defend against. The bug requires no attacker action beyond normal message delivery — it is purely a latent accounting fragility that surfaces the moment the invariant (`feeToken.balanceOf(gateway) >= sum(outstanding order.fees)`) is violated.

### Recommendation
Decouple the fee-token payout from the escrowed-input-token release inside `_withdraw`, e.g., wrap the fee transfer in a try/catch (or use a non-reverting `transfer` pattern) so a fee-token shortfall degrades to "fee skipped/credited as claimable" rather than blocking release of the unrelated escrowed inputs. Additionally, consider tracking `order.fees` as a share of a fee-token balance snapshot (percentage-based accounting) rather than a fixed absolute amount recorded at placement time, consistent with the original report's recommendation for `i_arbiterFee`.

### Proof of Concept
1. Governance points `feeToken()` at (or migrates to) a rebasing ERC-20, or the current fee token later becomes subject to a negative rebase / balance-reducing event.
2. A user places a cross-chain order via `placeOrder`, paying `order.fees` in the fee token; the gateway records `_orders[commitment][TRANSACTION_FEES] = order.fees` per [1](#0-0) .
3. A solver fills the order on the destination chain and Hyperbridge relays the `RedeemEscrow` settlement message back to the source gateway.
4. Before the message is delivered, the fee token's rebase reduces the gateway's actual `feeToken.balanceOf(gateway)` below the sum of all outstanding recorded `TRANSACTION_FEES` values.
5. `onAccept` → `_withdraw(body, false, true)` executes: the loop transfers the escrowed input tokens successfully, but the subsequent `IERC20(feeToken).safeTransfer(beneficiary, fees)` in [5](#0-4)  reverts due to insufficient balance.
6. The whole transaction reverts, rolling back the input-token release too. Any relayer resubmission of the same message hits the same revert as long as the shortfall persists, permanently freezing the order's escrowed inputs and fee.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
