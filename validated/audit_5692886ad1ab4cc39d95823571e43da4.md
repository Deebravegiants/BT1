### Title
Missing Chainlink circuit-breaker (minAnswer/maxAnswer) validation lets an unprivileged UserOperation drain SimplexPaymaster at a stale, clamped price - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` only validates that a Chainlink `latestRoundData()` answer is positive and not stale by timestamp; it never cross-checks the returned `answer` against the underlying aggregator's `minAnswer`/`maxAnswer` circuit-breaker bounds. This is the exact bug class described in the external report: when a Chainlink aggregator's price falls outside its configured bounds, it keeps reporting the clamped min/max value with a fresh `updatedAt` timestamp, defeating staleness checks while the reported price silently diverges from the real market price.

### Finding Description
`_getOraclePrice` is the sole gate on both the native-asset and per-token Chainlink feeds used to price gas for every ERC-20-sponsored UserOperation: [1](#0-0) 

It reverts only on `answer <= 0` or on staleness measured against `block.timestamp - updatedAt`. Because a Chainlink aggregator that has hit its `minAnswer`/`maxAnswer` circuit breaker still writes a fresh `updatedAt` on every round even though `answer` is pinned to the clamp, both checks pass while the price is wrong by an arbitrary amount (as in the LUNA-crash precedent cited in the report).

This price feeds directly into `_tokenPrice`, which is invoked by `_fetchDetails` on every UserOperation that pays gas with a registered ERC-20 token — a path reachable by any unprivileged bundler/UserOperation sender, not just governance or the treasury: [2](#0-1) [3](#0-2) 

If a token's USD feed (or the native/gas-asset feed) has collapsed to below its configured `minAnswer` (or spiked above `maxAnswer`), the paymaster keeps computing `tokenPrice = nativeUsd * 10^tokenDecimals / tokenUsd` from the stuck clamp value instead of the real price. Any UserOperation sender can then submit ops charged at this stale ratio, so `_erc20Cost`-derived `prefundAmount` in `_prefund`/mode-0x00 `transferFrom` path is computed from the wrong price: [4](#0-3) 

### Impact Explanation
If the pricing token's aggregator is pinned to `minAnswer` (undervaluing the token) while the native-asset oracle correctly tracks a stable or rising price, `tokenPrice` becomes far smaller than the true exchange rate, so every UserOperation sponsored through this paymaster is charged a fraction of the actual USD cost of the gas it consumes. Because sponsorship funds gas out of the paymaster's EntryPoint deposit, an unprivileged attacker can repeatedly submit self-serving UserOperations that drain the deposit's native balance for near-zero token cost — a concrete theft of protocol funds, matching the report's "protocol manipulated to handle calls at an inflated/deflated price" impact. This reaches Medium/High severity because it is a direct, permissionless drain path, not merely a bookkeping error.

### Likelihood Explanation
Exploitation requires only that one of the registered Chainlink feeds (native or an ERC-20 token) hits its aggregator's circuit-breaker bound — a real, historically observed event (LUNA, and other de-pegging/crash events) rather than a contrived condition. No governance, admin, or privileged role is needed; any UserOperation sender using mode `0x00` or `0x02` paymaster data reaches the vulnerable pricing path in normal operation.

### Recommendation
Extend `_getOraclePrice` (and the parallel logic in `_tokenPrice`/`swapAndDeposit`) to fetch each aggregator's `minAnswer`/`maxAnswer` (e.g., via `AggregatorV2V3Interface(address(oracle)).aggregator()` or a governance-configured bound per feed) and revert when `answer` is at or outside those bounds, mirroring the recommendation in the source report. Alternatively, require a secondary/fallback oracle or a bounded reasonable-price check (e.g., against a TWAP) before trusting a Chainlink answer that sits at its extreme.

### Proof of Concept
1. Governance registers token `T` with Chainlink feed `F_T`, and the native asset uses feed `F_N`, both surfaced through `_setParams`/`_registerToken`.
2. `F_T`'s underlying aggregator experiences a crash and its price is clamped to `minAnswer` (e.g., $0.10 reported as $1 floor) while continuing to update `updatedAt` every heartbeat — passing `_getOraclePrice`'s `answer <= 0` and staleness checks.
3. An attacker (any UserOperation sender, no special privilege) submits a UserOperation with paymasterData mode `0x00` naming token `T`; `_fetchDetails` computes `tokenPrice = _tokenPrice(cfg)` using the clamped, inflated `tokenUsd`, understating the real gas cost in `T`.
4. `_erc20Cost`/`_prefund` charges the attacker only the clamped-price amount of `T` via `transferFrom`, while the EntryPoint pays out the operation's real native gas cost from the paymaster's deposit — repeated submissions drain the deposit at the mispriced rate. [5](#0-4)

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
