### Title
EventRateLimit admission plugin builds ambiguous cache keys via unbounded string concatenation, allowing rate-limit bucket collisions/bypass - (File: plugin/pkg/admission/eventratelimit/limitenforcer.go)

### Summary
The `EventRateLimit` admission plugin's `SourceAndObjectLimitType` builds its per-bucket rate-limiter cache key by joining seven user/attacker-influenced strings with no delimiter and no length-prefixing, exactly the `abi.encodePacked`-style ambiguity described in the report (`"xy"+"z" == "x"+"yz"`).

### Finding Description
`getSourceAndObjectKey` constructs the cache key for the `SourceAndObjectLimitType` rate limiter by concatenating `Event.Source.Component`, `Event.Source.Host`, `Event.InvolvedObject.Kind`, `Event.InvolvedObject.Namespace`, `Event.InvolvedObject.Name`, `Event.InvolvedObject.UID`, and `Event.InvolvedObject.APIVersion` with `strings.Join(..., "")` — i.e., no separator at all: [1](#0-0) 

This is used as the lookup key into an LRU cache of per-bucket `flowcontrol.RateLimiter` instances: [2](#0-1) 

`Event` objects (including `Source.Component`, `Source.Host`, and the entire `InvolvedObject` reference) are fields fully controllable by any client permitted to `create` events — a request that is not constrained by the admission plugin itself (it only rate-limits, it doesn't validate content of these fields). Because the fields are concatenated with no delimiter, distinct tuples of `(Component, Host, Kind, Namespace, Name, UID, APIVersion)` can produce identical concatenated strings — e.g. `Component="A", Host="BC"` collides with `Component="AB", Host="C"`, or shifting a character between `Namespace` and `Name` produces the same key across two logically different target objects. This is functionally identical to the packing-collision bug in the reported `TokenDistributor._hashLeaf`: differently-shaped inputs collapse into the same identifier because there is no length prefix or separator to disambiguate boundaries.

This is in contrast to other cache-key builders in the same codebase (e.g. the token-authenticator cache and the impersonation cache) which were explicitly hardened against this exact class of bug by using length-prefixed encoding: [3](#0-2) [4](#0-3) 

`getSourceAndObjectKey` was not updated to use the same safe pattern.

### Impact Explanation
By crafting `Event.Source.Component`/`Event.Source.Host`/`InvolvedObject.*` fields so that their concatenation collides with the key of another, unrelated event stream, a user permitted to create events can:
- Force their own events to share a rate-limit bucket with a different, legitimate source, exhausting that bucket's token budget and causing legitimate events targeting that bucket to be denied by the admission plugin (denial of the intended event ingestion/observability control), or
- Conversely, deliberately choose field values that collide with an already-exhausted bucket belonging to a different source/object, effectively defeating rate limiting for their own bursts of events by "borrowing" a fresh bucket boundary, or fragmenting what should be one bucket into several to bypass the intended per-source cap.

The net effect is an admission-control (rate-limiting) bypass/confusion: the `EventRateLimit` plugin's isolation guarantee between different sources/objects is broken because non-colliding, semantically-distinct inputs can be mapped to the same internal key. This does not grant new object-level RBAC permissions, but it does defeat a control (`EventRateLimit`) whose entire purpose is to isolate/limit different event sources and objects from starving each other.

### Likelihood Explanation
Any principal with permission to `create` events (broadly granted in most clusters, since event creation is generally low-privilege and widely allowed for controllers, kubelets, and often application service accounts) fully controls the values feeding `getSourceAndObjectKey`. No special privilege beyond ordinary event-create access is required, and the collision is deterministic and constructible offline (identical in spirit to the PoC in the report), so exploitation requires no race condition or luck.

### Recommendation
Replace the unstructured `strings.Join(fields, "")` with a length-prefixed encoding (as already done in `cached_token_authenticator.go`'s `writeLengthPrefixedString`/`writeLength` and in `impersonation/cache.go`'s `cacheKeyBuilder`), or insert an unambiguous separator that cannot appear inside any field value together with per-field length encoding, before joining `Component`, `Host`, `Kind`, `Namespace`, `Name`, `UID`, and `APIVersion` into the `getSourceAndObjectKey` cache key.

### Proof of Concept
Given the current implementation:
```go
strings.Join([]string{
    event.Source.Component,
    event.Source.Host,
    event.InvolvedObject.Kind,
    event.InvolvedObject.Namespace,
    event.InvolvedObject.Name,
    string(event.InvolvedObject.UID),
    event.InvolvedObject.APIVersion,
}, "")
```
Two Events with different logical identities produce the same key:
- Event A: `Source.Component="kubelet", Source.Host="node1", InvolvedObject={Kind:"Pod", Namespace:"team-a", Name:"web", UID:"", APIVersion:"v1"}` → key = `"kubeletnode1Podteam-awebv1"`
- Event B: `Source.Component="kubeletnode1Podteam-awebv1", Source.Host="", InvolvedObject={Kind:"", Namespace:"", Name:"", UID:"", APIVersion:""}` → key = `"kubeletnode1Podteam-awebv1"`

Both hash to the identical LRU cache key/bucket in `limitEnforcer.accept` (`plugin/pkg/admission/eventratelimit/limitenforcer.go:89-101`), so an attacker who can submit Event B (with a crafted, oversized `Source.Component` string and empty other fields) shares — and can exhaust — the rate-limit bucket intended solely for Event A's legitimate source/object pair, or vice versa can split what should be one bucket into arbitrarily many by shifting characters across field boundaries.

// getSourceAndObjectKey returns a cache key that is based on the source+object of the event
func getSourceAndObjectKey(attr admission.Attributes) string {
	object := attr.GetObject()
	if object == nil {
		return ""
	}
	event, ok := object.(*api.Event)
	if !ok {
		return ""
	}
	return strings.Join([]string{
		event.Source.Component,
		event.Source.Host,
		event.InvolvedObject.Kind,
		event.InvolvedObject.Namespace,
		event.InvolvedObject.Name,
		string(event.InvolvedObject.UID),
		event.InvolvedObject.APIVersion,
	}, "")

// writeLengthPrefixedString writes s with a length prefix to prevent ambiguities, i.e. "xy" + "z" == "x" + "yz"
// the length of b is assumed to be 4 (b is mutated by this function to store the length of s)
func writeLengthPrefixedString(w io.Writer, b []byte, s string) {
	writeLength(w, b, len(s))
	if _, err := w.Write(toBytes(s)); err != nil {
		panic(err) // Write() on hash never fails
	}
}

// cacheKeyBuilder builds a binary key from structured inputs using uint32 length-prefixed encoding, then hashes
// it with SHA-256.  All methods operate on a single shared buffer to avoid closure and child-builder allocations.
type cacheKeyBuilder struct {
	namespace string // in the programming sense, not the Kubernetes concept
	builder   []byte
}

func newCacheKeyBuilder(namespace string) *cacheKeyBuilder {
	// start with a reasonable size to avoid too many allocations
	return &cacheKeyBuilder{namespace: namespace, builder: make([]byte, 0, 384)}
}

func (c *cacheKeyBuilder) addString(value string) *cacheKeyBuilder {
	c.addLengthPrefixed(func(c *cacheKeyBuilder) {
		c.builder = append(c.builder, value...)
	})
	return c
}

func (c *cacheKeyBuilder) addStringSlice(values []string) *cacheKeyBuilder {
	c.addLengthPrefixed(func(c *cacheKeyBuilder) {
		for _, v := range values {
			c.addString(v)
		}
	})
	return c
}

func (c *cacheKeyBuilder) addBool(value bool) *cacheKeyBuilder {
	var b byte
	if value {
		b = 1
	}
	c.builder = append(c.builder, b)
	return c
}

type builderContinuation func(child *cacheKeyBuilder)

func (c *cacheKeyBuilder) addLengthPrefixed(f builderContinuation) {
	offset := len(c.builder)
	c.builder = append(c.builder, 0, 0, 0, 0) // placeholder for uint32 length
	f(c)
	binary.BigEndian.PutUint32(c.builder[offset:], uint32(len(c.builder)-offset-4))
}
