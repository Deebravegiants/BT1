Based on my investigation, the strongest analog to the "reserves can be re-added" bug class is in `create_client` in the ISMP consensus handler: it never checks whether a consensus client/state already exists for the given `consensus_state_id` before overwriting consensus state, unbonding period, challenge periods, and state-machine commitments — exactly the "should revert but silently overwrites critical state" pattern from the report.

### Title
`create_client` overwrites an existing consensus client's state instead of rejecting duplicate `consensus_state_id` - (File: modules/ismp/core/src/handlers/consensus.rs)

### Summary
The `Error` enum in `modules/ismp/core/src/error.rs` defines both `CannotCreateAlreadyExistingConsensusClient` and `DuplicateConsensusStateId` variants specifically to guard against re-creating an already-existing consensus client [1](#0-0) , but the `create_client` handler that these errors were presumably meant to guard never actually checks for or raises them.

### Finding Description
`create_client` only verifies that a concrete implementation exists for `message.consensus_client_id` via `host.consensus_client(...)`, then unconditionally calls `store_consensus_state`, `store_unbonding_period`, `store_consensus_state_id`, and iterates to store every challenge period and state-machine commitment supplied in the message: [2](#0-1) . There is no lookup of `host.consensus_state(message.consensus_state_id)` to detect that a state already exists for that ID before overwriting — this mirrors the reported bug class exactly: instead of reverting on `reserveAlreadyAdded`, execution proceeds and overwrites live parameters (here: consensus state, unbonding period, challenge periods, and state commitments) that were previously "seeded" and possibly already advanced through legitimate `update_client` calls.

This matters because `create_client` is the underlying primitive reused by higher-level flows such as `initialize_state` in `pallet-beefy-consensus-proofs`, which calls `pallet_ismp::Pallet::<T>::create_consensus_client` to seed/reset the BEEFY consensus state and host state-machine commitment at height 1 [3](#0-2) , and the parachain client's `initialize()` which also calls `handlers::create_client` at genesis/on_initialize [4](#0-3) . If any code path (governance call, pallet extrinsic, or re-triggered initialization) invokes `create_client`/`create_consensus_client` a second time for a `consensus_state_id` that already has live, advanced consensus state, the previously accumulated state (built up over many legitimate `update_client` proof submissions) is silently clobbered back to whatever the second `CreateConsensusState` message specifies — no revert, no `DuplicateConsensusStateId` error, unlike what the error type's name promises.

### Impact Explanation
A silently accepted re-creation of a consensus client resets: the trusted consensus state (potentially rolling back trust to an older/incorrect authority set), the unbonding period, challenge periods per state machine, and state-machine commitments/latest-height for one or more `StateMachineId`s. Because subsequent `update_client` calls, membership/non-membership proof verification, and cross-chain message delivery in `pallet-ismp` all depend on `consensus_state`/`state_machine_commitment` being monotonic and trustworthy, an overwrite can (a) freeze legitimate future updates if the previous-height bookkeeping (`store_latest_commitment_height`, challenge periods) is inconsistently reset, or (b) enable delivery of previously-invalid/forged messages if a stale, less-restrictive commitment or authority set is reinstated. This directly threatens "unsound state commitment" / "forged message delivery" outcomes called out in scope.

### Likelihood Explanation
Likelihood depends on whether any reachable, less-privileged path can invoke `create_client`/`create_consensus_client` a second time for a live `consensus_state_id`. I was not able to fully confirm the origin/permission checks on the pallet-ismp `create_consensus_client` extrinsic itself (only that `initialize_state` in `pallet-beefy-consensus-proofs` gates it behind `AdminOrigin::ensure_origin`) within the available index, nor whether other callers (e.g. governance-XCM-triggered calls documented in `docs/content/developers/polkadot/pallet-ismp/overview.mdx`) impose additional idempotency checks upstream. If the call is admin/governance-gated everywhere, this finding would fall under the excluded "malicious-governance" category per the validation rules; I could not verify this either way with the tools available, and the codebase index (given size limits) may not contain the full extrinsic definition. This should be checked directly with a Devin session that can read the full `modules/pallets/ismp/src/lib.rs` pallet call definitions and permission origins for `create_consensus_client`.

### Recommendation
In `create_client` (`modules/ismp/core/src/handlers/consensus.rs`), before storing anything, check whether `host.consensus_state(message.consensus_state_id)` already returns `Ok` (i.e., a state exists) and return `Err(Error::DuplicateConsensusStateId { consensus_state_id: message.consensus_state_id })` if so — using the error variant that already exists for exactly this purpose [5](#0-4) , rather than allowing an unconditional overwrite.

### Proof of Concept
Not able to construct a concrete end-to-end PoC from the indexed context alone, since I could not confirm the exact origin/dispatch path that allows an external caller to invoke `create_client` twice for the same `consensus_state_id` outside of the admin-gated `initialize_state` extrinsic. A Devin session with full repo access could trace `pallet_ismp::Pallet::<T>::create_consensus_client`'s origin checks and any other callers to determine if this is reachable by less-privileged actors, and if so write a runtime test in `modules/pallets/testsuite` that calls `handlers::create_client` twice with the same `consensus_state_id` but different `CreateConsensusState.state_machine_commitments`/`unbonding_period`, asserting the second call succeeds and clobbers the first (demonstrating no revert occurs today).

/// Handles the creation of consensus clients
pub fn create_client<H>(
	host: &H,
	message: CreateConsensusState,
) -> Result<ConsensusClientCreatedResult, anyhow::Error>
where
	H: IsmpHost,
{
	// check that we have an implementation of this client
	host.consensus_client(message.consensus_client_id)?;

	// Store the initial state for the consensus client
	host.store_consensus_state(message.consensus_state_id, message.consensus_state)?;
	host.store_unbonding_period(message.consensus_state_id, message.unbonding_period)?;
	host.store_consensus_state_id(message.consensus_state_id, message.consensus_client_id)?;

	// Store all challenge periods
	for (state_id, challenge_period) in message.challenge_periods {
		let id = StateMachineId { state_id, consensus_state_id: message.consensus_state_id };
		host.store_challenge_period(id, challenge_period)?;
	}

	// Store all intermediate state machine commitments
	for (id, state_commitment) in message.state_machine_commitments {
		let height = StateMachineHeight { id, height: state_commitment.height };
		host.store_state_machine_commitment(height, state_commitment.commitment)?;
		host.store_state_machine_update_time(height, host.timestamp())?;
		host.store_latest_commitment_height(height)?;
	}

	host.store_consensus_update_time(message.consensus_state_id, host.timestamp())?;

	Ok(ConsensusClientCreatedResult {
		consensus_client_id: message.consensus_client_id,
		consensus_state_id: message.consensus_state_id,
	})
}
