### Title
Webhook `shop` (and `topic`/`webhook-id`) Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the `shop`, `topic`, and `webhook-id` values are read directly from unauthenticated HTTP headers and are never covered by the HMAC signature. `Registry.process` validates only that the body's HMAC matches, then dispatches the handler using the unverified `shop` header, breaking the equality that should hold between "HMAC-authenticated sender" and "shop identity acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors pull straight from caller-supplied headers with no cryptographic binding: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — which in turn only verifies `HMAC(secret, raw_body)` — before dispatching the handler with the header-derived, unverified `shop`: [3](#0-2) [4](#0-3) 

Because a single app-level `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app can generate a validly-signed webhook body from their own store (e.g. by triggering an `orders/create` or `shop/redact` event), capture the exact `raw_body` + `hmac-sha256` pair, then replay that same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop that also has the app installed. `HmacValidator.validate` still succeeds because the signature only ever covered the body, and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` is the attacker-controlled header value: [5](#0-4) 

The broken equality is: `hmac_verified(raw_body)` should imply `shop_header == originating_shop`, but the gem allows `shop_header` to vary freely for a fixed, validly-signed `raw_body`, since the header is parsed but never part of the signed content.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker who is a legitimate but unprivileged installer of a multi-tenant app can forge webhook deliveries that the app will process as if they originated from an arbitrary other shop using the same app installation base. Depending on the host app's handler logic (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`, or business webhooks that trigger data mutations keyed by `shop`), this can cause data belonging to another merchant to be deleted, redacted, or otherwise mutated — a direct violation of tenant isolation, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that: (1) is installed on more than one shop (the normal case for public apps), and (2) exposes a single shared webhook endpoint keyed by the `shop` header, which is the pattern this gem's docs recommend. No access token, `api_secret_key`, or privileged account is required — only the ability to install the app on one's own (attacker-owned) shop and observe/replay its own legitimately signed webhook traffic.

### Recommendation
Bind the tenant identity into the verified material: either (a) require host applications to independently confirm the `shop` header corresponds to a shop known/installed by the app (e.g., cross-check against stored session/shop records) before trusting it, or (b) extend `VerifiableQuery`/`HmacValidator` for webhooks to incorporate the `shop`, `topic`, and `webhook-id` headers into the signed payload comparison so that any header tampering invalidates the signature, consistent with how `Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its own HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate installation, no special privileges).
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop and captures the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header, where `H = Base64(HMAC-SHA256(client_secret, B))`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `HmacValidator.validate` succeeds because `to_signable_string` only checks `B` against `H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act on `victim-shop.myshopify.com` using attacker-supplied body content — a cross-tenant forgery.
