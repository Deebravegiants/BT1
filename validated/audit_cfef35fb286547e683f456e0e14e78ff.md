### Title
PoA Bridge withdrawal-status matching by `assetId` alone causes cross-withdrawal status/hash misattribution in batch withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the internal `waitForWithdrawalCompletion()` helper both resolve a withdrawal's on-chain completion status/`txHash` by matching entries returned from the POA bridge indexer **only by `assetId` (near_token_id)**, ignoring `destinationAddress`, `amount`, or the withdrawal's `index`. When a single batch withdrawal (one NEAR intent tx) contains two or more legs of the *same* asset (e.g., to two different destination addresses), both legs' `describeWithdrawal` calls will match the *same first* record in the indexer response, causing both legs to be reported "completed" with the *same* `txHash` even though only one destination transfer actually happened.

and is invoked from `describeWithdrawal`: [2](#0-1) 

The identical pattern exists in the lower-level helper used elsewhere: [3](#0-2) 

The SDK's public batch-withdrawal API (`processWithdrawal`, `createWithdrawalCompletionPromises`, `waitForWithdrawalCompletion`) accepts an array of `WithdrawalParams` and creates one polling promise per index/leg: [4](#0-3) 

There is no validation anywhere in `sdk.ts`, `signAndSendWithdrawalIntent`, or `estimateWithdrawalFee` that rejects a batch containing two entries with the same `assetId` routed through the PoA bridge (I found no dedup/same-asset guard in `packages/intents-sdk/src/**`). Because `Array.find()` returns the first matching element regardless of which withdrawal leg is asking, **every leg with that assetId receives the exact same withdrawal record and `transfer_tx_hash`** from the indexer.

This breaks the equality the report's bug-class targets: "a status reported that is not the on-chain outcome." Here, two logically distinct withdrawal legs (different destination addresses/possibly different amounts) are both reported `completed` with the identical destination `txHash`, when in fact only one real destination transfer occurred.

### Impact Explanation
An integrator consuming `sdk.processWithdrawal()` / `createWithdrawalCompletionPromises()` for a batch containing duplicate-asset legs would see **both** legs resolve to `status: "completed"` with the same `txHash`. If the integrator's bookkeeping credits/marks each leg as fulfilled independently (which is the intended usage pattern per the SDK's own README, e.g., `promises[0].then(tx => saveUsdc(tx))`, `promises[1].then(tx => saveBtc(tx))`), this results in a double-credit / double-refund condition: the integrator believes two separate destination payments were made and reconciles funds/state accordingly, while on-chain only one destination transfer exists. This matches the report's "High" impact bucket: "a status or hash misreport making an integrator credit or refund twice."

The severity is bounded by: (1) the POA bridge presently only supports a single relayer-side withdrawal per NEP-141 asset per near-tx group in some flows, and (2) the code's own comment states the POA API "doesn't currently support this case either," which suggests the underlying relayer might also collapse/reject such duplicate legs rather than executing two separate transfers - but the SDK itself performs no such validation, so the resulting status report is unconditionally wrong for the loser leg whenever the relayer *does* process multiple same-asset legs (e.g., split-address payouts within one intent).

### Likelihood Explanation
Reachable by any regular SDK user (no privileged or malicious relayer/admin action required) simply by constructing a batch withdrawal with two same-asset, different-destination legs - a normal usage pattern explicitly documented as supported in the SDK's batch-withdrawal README example ("Process multiple withdrawals in a single intent"). Likelihood of the underlying relayer actually executing both distinct transfers (rather than erroring) is uncertain since I could not inspect the POA bridge relayer/indexer implementation (out of scope, external service) to confirm behavior for duplicate-asset batches.

### Recommendation
Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate by more than `assetId` - e.g., match remaining unclaimed indexer records by `destinationAddress` and `amount` (or, as the existing code comment suggests, sort both indexer results and requested withdrawal params by amount and pair them positionally) so that each leg of a batch is matched to a distinct withdrawal record. Until fixed, the SDK should validate at `signAndSendWithdrawalIntent`/`estimateWithdrawalFee` time and throw when a PoA-bridge-routed batch contains multiple legs with the same `assetId`, to prevent silent double-status-reporting.

### Proof of Concept
1. Construct a batch withdrawal via `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdt.tether-token.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive:false}, {assetId: "nep141:usdt.tether-token.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive:false} ] })`.
2. Both legs route through `PoaBridge` (same `.omft.near`-style asset).
3. After the intent settles, the POA indexer returns (at minimum) one `COMPLETED` withdrawal record for `near_token_id = "usdt.tether-token.near"` with `transfer_tx_hash = "0xDEST1"`.
4. `createWithdrawalCompletionPromises` polls both legs (`index 0` and `index 1`); `describeWithdrawal` for each independently calls `findMatchingWithdrawal(withdrawals, "nep141:usdt.tether-token.near")`, which returns the same first record for both.
5. Both promises resolve `{ status: "completed", txHash: "0xDEST1" }` even though leg 1 (destined for `0xBBB...`) either never executed or executed with a different hash - demonstrating the mis-report.

			return { status: "pending" };

			return { status: "pending" };

				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
