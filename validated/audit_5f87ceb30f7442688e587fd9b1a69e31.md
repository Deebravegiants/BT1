### Title
`WebhookMetadata#topic` / `#shop` are dispatch keys but sit outside the HMAC-signed string, letting a header swap re-target any validly-signed webhook body - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` verifies a request purely against `verifiable_query.to_signable_string`, and for webhooks `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Registry.process` then dispatches on `request.topic` and builds `WebhookMetadata` from `request.shop`, both read straight from unsigned HTTP headers [2](#0-1) , with no delivery-id or timestamp tracking to bind a given signature to the header set it was originally delivered with.

### Finding Description
The invariant that should hold is: `handler_input == signed_input`, i.e. every field the handler acts on (`topic`, `shop`, `webhook_id`) must be inside the string HMAC-validated by `HmacValidator`. Tracing the code shows this is false.

- `Request#to_signable_string` returns `@raw_body` only [3](#0-2) .
- `Request#topic`, `#shop`, `#webhook_id`, `#api_version` are all pulled from `@headers` via `shopify_header`, never touching `@raw_body` [4](#0-3) [5](#0-4) .
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and only compares that against `verifiable_query.hmac` [6](#0-5)  — the topic/shop/webhook-id headers never enter the signable string, so they are never authenticated.
- `Registry.process` raises only if the HMAC check fails, then does `@registry[request.topic]&.handler` and builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight from the unauthenticated headers [2](#0-1) .

Because the app's HMAC secret (`Context.api_secret_key`) is shared across all shops/installations of the app (it is derived from the app's `client_secret`, not a per-merchant secret), an attacker who legitimately installs the app on their own development shop and receives even one genuinely-signed webhook (any topic, any body) possesses a `{raw_body, hmac}` pair that will pass `HmacValidator.validate` unconditionally, independent of headers. The attacker can then POST that exact `raw_body`/`X-Shopify-Hmac-Sha256` pair directly to the target app's webhook endpoint with arbitrary `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers of their choosing. `Registry.process` will validate the (unchanged) HMAC successfully, look up the handler for the attacker-chosen topic, and hand the handler a `WebhookMetadata` whose `shop` field names any shop the attacker likes — including a victim merchant's shop domain, or a mandatory-compliance topic such as `shop/redact` — despite that value never having been signed by Shopify.

No mitigating check exists: `HmacValidator.validate` only checks the body signature; `Registry.process` performs no correlation between the signed body and the header-derived `topic`/`shop`; there is no delivery-id de-duplication or timestamp window to reject a re-purposed delivery.

### Impact Explanation
This lets an unprivileged attacker have the app process a forged webhook as if it were an authentic, signed delivery for an arbitrary topic and an arbitrary shop domain of the attacker's choosing, using only a body/HMAC pair they legitimately received for their own store. If a host application trusts `WebhookMetadata#shop` (as documented/intended usage, e.g. to scope data deletion for `shop/redact`, or to select which merchant's records to update) without independently re-validating it against session/install records, this is a cross-tenant authentication bypass: one merchant's signed callback can be replayed to trigger handler logic scoped to a different merchant. This matches "Critical - authentication bypass: a forged or unsigned request is accepted as authentic by the app," since a value (topic+shop) that was never actually signed by Shopify is treated as authenticated by the app.

### Likelihood Explanation
Preconditions are minimal and squarely within the stated attacker capabilities: create a dev shop, install the target app, register (or receive) any one HTTP webhook delivery to obtain a valid `raw_body` + `X-Shopify-Hmac-Sha256` pair, then send a direct HTTP POST to the app's known webhook endpoint with that same body/HMAC but forged `X-Shopify-Topic` / `X-Shopify-Shop-Domain` / `X-Shopify-Webhook-Id` headers. No secret, session, or access token is required. The attack is repeatable indefinitely and against any topic registered in `@registry`, limited only by whichever handler logic exists for that topic in the host app.

### Recommendation
Bind the dispatch-relevant fields (`topic`, `shop-domain`, `webhook-id`, `api-version`) into the signed material — e.g. include them in `Request#to_signable_string` (or verify them against out-of-band records, such as confirming `shop` matches an installed/active session before invoking the handler) — so `HmacValidator` cannot pass for a body whose accompanying headers were altered after Shopify signed the original delivery. At minimum, `Registry.process` should independently verify that the shop named in headers corresponds to a shop with an active installation/session for this app before dispatching, and/or track `webhook_id` to reject re-delivered/re-labeled payloads.

### Proof of Concept
```ruby
# test/webhooks/registry_replay_test.rb (sketch)
def test_header_swap_bypasses_authentication
  body = "{\"order_id\":1}"
  hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  )

  # Attacker's own legitimately-signed webhook for their own shop/topic
  legit_headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    "x-shopify-webhook-id" => "attacker-id",
  }

  # Forged headers reusing the SAME body+hmac, targeting a different topic/shop
  forged_headers = {
    "x-shopify-topic" => "shop/redact",           # different, attacker-chosen topic
    "x-shopify-hmac-sha256" => hmac,               # unchanged signature
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen shop
    "x-shopify-webhook-id" => "forged-id",
  }

  received_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "path", delivery_method: :http, handler: handler,
  )

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
  ShopifyAPI::Webhooks::Registry.process(forged_request) # passes HMAC check

  assert_equal("victim-shop.myshopify.com", received_shop) # unsigned value accepted as authentic
end
```
This demonstrates that `Registry.process` accepts a body/HMAC pair signed for one topic/shop and dispatches it, with attacker-controlled `topic`/`shop`, to a handler as if it were an authentic delivery for that different topic/shop — proving the signature-coverage invariant is broken.
