Based on my investigation, I found a concrete analog of the "check-then-act override" bug class in the hardware wallet signing flow.

### Title
Concurrent signing request override causes silent abandonment of an in-flight approved hardware signing request - ([File: features/hardware-wallets/src/module/hardware-wallets.ts])

### Summary
The Sherlock finding is a check-then-act flaw: a "no active request" guard (`withdrawalRequestPeriod == 0`) is satisfied both by the legitimate "no request yet" state and by an in-progress request's default value, so a second call silently overwrites/destroys the first request's state and its already-accrued value. `HardwareWallets#signGeneric` in this repo has the same structural flaw: it unconditionally overwrites the single in-memory `#signingRequest` slot with no check for an existing pending request, so a second `signTransaction`/`signMessage` call clobbers the state used to track/settle the first request.

### Finding Description
`HardwareWallets` keeps exactly one pending request in `#signingRequest` and exposes it to the UI/device flow through `#signingRequestAtom`: [1](#0-0) 

`#signGeneric` is the entry point used by both `signTransaction` and `signMessage`. It generates a fresh `id`, builds a `deferred` promise, and assigns straight into `this.#signingRequest` with **no check that a request is already pending**: [2](#0-1) 

Although `#signGeneric` is wrapped in `restrictConcurrency` (`make-concurrent`), the wrapped function body returns almost immediately — it does not `await` `deferred.promise` before returning; it only calls `void this.retrySigningRequest(id)` and returns the deferred promise to the caller. So the "critical section" guarded by `restrictConcurrency` finishes essentially synchronously, and the actual signing (which can take an arbitrarily long time — waiting on physical device confirmation, USB/BLE reconnects, retries) happens *outside* that guarded section. This mirrors the Sherlock bug where a period/counter guard only protects the “setup” step, not the entire request lifecycle, letting the check pass again before the first request settles.

Consequently, if a second `signTransaction`/`signMessage` call is triggered (e.g., a caller retries after a slow response, a dApp/asset flow issues overlapping signing calls, or the SDK consumer double-invokes due to UI lag) while the first request is still waiting on the physical device:
- `this.#signingRequest` is overwritten with the new `{id, ...}` object.
- `#updateSigningRequest`/`#signingRequestAtom` now reflect only the new request, so the UI/device interaction for the *first* request is orphaned from the tracking state.
- If the user then approves the *first* (stale) request on the physical device, `retrySigningRequest(firstId)` resolves `request.sign(...)`, but then compares `this.#signingRequest?.id === id` — inside `#deleteSigningRequest` — and since the id no longer matches (overwritten by the second request), the branch falls to the `else` (`No signing request found for id`) and does not clear/resolve the original caller correctly; the original `deferred.resolve/reject` is never invoked through the normal path, and the promise for the first `signTransaction`/`signMessage` call hangs indefinitely (a stuck signing promise), while the newly-injected request now silently drives whatever device operation was already underway for the old one. [3](#0-2) [4](#0-3) 

This is the same root-cause shape as the Sherlock report: a single mutable "current request" slot guarded only at creation time, not for the full duration of the request, allowing a second invocation to silently overwrite/orphan the first one's tracking state before it settles.

### Impact Explanation
The direct, concrete consequence is state corruption in the hardware-signing request tracker: the caller of the first `signTransaction`/`signMessage` invocation loses the ability to be notified of the result of an operation that may already have been approved on the physical device (i.e., the wallet may sign a transaction whose completion/result is never correctly delivered/resolved to the intended caller, and cancellation of the stale request via `cancelSigningRequest`/`retrySigningRequest` is bypassed since IDs no longer line up). This falls short of full "unauthorized signing of attacker-controlled data" or "secret disclosure" because the second request must originate from the same legitimate caller/session (there's no cross-origin or cross-account bypass here) — it is a same-actor race/state-overwrite bug causing a stuck/orphaned signing promise and loss of proper request tracking, not an attacker gaining unauthorized signing capability over another user's/origin's request.

### Likelihood Explanation
Requires two rapid, overlapping `signTransaction`/`signMessage` calls within the window while a device confirmation is still pending (e.g. UI double-submit, retry-on-timeout logic, or a buggy asset caller). No explicit reentrancy guard exists across the full async lifecycle of a signing request, and the `restrictConcurrency` wrapper does not protect against this because the wrapped function returns before the operation completes.

### Recommendation
Add an explicit guard in `#signGeneric` that rejects (or queues) a new signing request while `this.#signingRequest` is already set and unresolved, analogous to requiring `rebalancingPeriod != 0` in the original fix — i.e., check `if (this.#signingRequest) throw/queue` before creating a new request, rather than relying only on `restrictConcurrency` around the initial synchronous setup.

### Proof of Concept
Not independently executable from static analysis alone (requires mocking `#getSelectedDevice`/device confirmation timing to simulate two overlapping calls to `signTransaction`); the trace above is derived directly from reading `#signGeneric`, `#deleteSigningRequest`, and `retrySigningRequest` and is not confirmed to be exploitable to the "concrete unauthorized signing / secret disclosure / cross-origin bleed" bar requested. Given this, I present it as the closest structural analog found in the codebase, but flag that it does **not** clearly meet the strict validation bar (concrete unauthorized signing, secret disclosure, auth bypass, cross-origin/account privilege bleed, or direct wallet-compromise impact) since the exploit requires the same caller/session to race itself rather than an unprivileged attacker gaining privilege they shouldn't have.

Given the uncertainty about meeting the strict impact bar, and since I could not find a clearer analog (e.g., in `connected-origins`, `auth-mobile`, encrypted storage, or RPC bridge code) that reproduces an "unset-default-coincides-with-valid-state" guard bypass with concrete unauthorized-signing/secret-disclosure/cross-origin impact, my confidence in this being a qualifying finding under the stated Validate criteria is low-to-moderate.

  #deleteSigningRequest = async (id: string) => {
    if (this.#signingRequest?.id === id) {
      this.#signingRequest = undefined
      await this.#signingRequestAtom.reset()
      this.#logger.debug(`Signing request with id: ${id} has been deleted`)
    } else {
      this.#logger.warn(`No signing request found for id: ${id}`)
    }
  }

    const request = this.#signingRequest

      this.#logger.warn(`No signing request found for id: ${id}`)
      return
    }
