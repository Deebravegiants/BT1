## Title
Redeploying an IntentGateway instance permanently freezes escrowed funds tied to in-flight cross-chain messages - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The IntentGatewayV2 stores exactly one registered peer address per remote chain in `_instances[keccak256(chain)]`, updated wholesale by `_addDeployment` whenever a `NewDeployment` message arrives. Any `RedeemEscrow` or `RefundEscrow` message that is already dispatched from the *old* peer address but not yet delivered/relayed at the moment `_instances` is overwritten becomes permanently unauthenticatable, freezing the escrowed tokens it was meant to release — the same "feature toggled after use locks funds" pattern as the referenced amAMM report.

### Finding Description
`_addDeployment` unconditionally overwrites the single registered gateway address for a state machine: [1](#0-0) 

`onAccept` authenticates every incoming `RedeemEscrow`/`RefundEscrow` post request via `_authenticate`, which requires the sender module to equal the *currently* registered instance for that source chain: [2](#0-1) [3](#0-2) 

Sequence:
1. A solver fills a cross-chain order on the destination chain (`_fillCrossChain`), dispatching a `RedeemEscrow` post request back to the source chain naming the *current* destination-gateway address as `request.from` (implicitly, the sending contract's own address).
2. Before that message is relayed and delivered, Hyperbridge governance dispatches a `NewDeployment` message re-registering the source chain's `_instances[keccak256(destinationChain)]` entry to a new address (e.g. a gateway migration/upgrade — an ordinary, non-malicious operational action).
3. When the relayer finally delivers the original `RedeemEscrow` message, `_authenticate` compares `request.from` (the *old* gateway address) against `_instance(request.source)` (now the *new* address) and reverts with `Unauthorized()`.
4. This message can never be successfully redelivered — the mismatch is permanent, since the old address is no longer registered anywhere and there is no versioning or allow-list of prior instances.
5. The escrowed input tokens on the source chain (`_orders[commitment][token]`) remain locked forever: `_withdraw` is never called, `_filled[commitment]` is never finalized, and there is no alternate recovery path, mirroring exactly the amAMM report's "pending refunds cannot be claimed" and "deposit gets locked" failure modes.

The identical issue applies to `RefundEscrow` messages dispatched by `_cancelFromDest`, which also marks the destination-side `_filled[commitment]` immediately: [4](#0-3) 
Once that mapping is set, the order can never be re-cancelled or re-filled on the destination chain, so if the matching `RefundEscrow` message is orphaned by a mid-flight registry update, the user's escrow is stranded on the source chain with no path to recover it — the destination side considers the order finished, and the source side will never accept the refund message.

### Impact Explanation
Impact is High: legitimate, already-escrowed user or solver funds (input tokens locked in `_orders`) become permanently unrecoverable. There is no admin sweep, no re-authentication mechanism, and no fallback cancellation route once `_filled` has been finalized on the counterpart chain. This is a genuine freezing-of-funds bug reachable by ordinary protocol operation (gateway redeployment/migration coinciding with normal in-flight order settlement), not by any malicious actor.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a `NewDeployment` registration to land while a `RedeemEscrow`/`RefundEscrow` message from the previously registered instance is still in transit. Gateway redeployments/migrations are expected operational events (the codebase already supports `upgradeToAndCall`/`Execute` for in-place upgrades, suggesting registry changes do occur), and cross-chain message delivery latency (finality + relayer availability) creates a realistic window for this race.

### Recommendation
- Allow `_authenticate` to accept messages from a bounded history of previously registered instances for a chain (e.g., keep the prior address valid for a grace period after `_addDeployment` overwrites it), or
- Version `_instances` so in-flight messages can be tagged with the instance version active when they were dispatched and authenticated against that snapshot, or
- Provide an explicit governance-only escape hatch (analogous to relaxing the amAMM's cancellation/withdrawal conditions) that lets governance manually finalize a withdrawal for orders whose corresponding cross-chain message can no longer authenticate, so escrowed funds are not permanently stranded.

### Proof of Concept
1. User places a cross-chain order; solver fills it on the destination chain, dispatching `RedeemEscrow` toward the source chain (`_fillCrossChain` → `_post`).
2. Before the relayer delivers this message, Hyperbridge governance dispatches `NewDeployment` for the destination chain, and the source gateway's `_addDeployment` overwrites `_instances[keccak256(destinationChain)]` with a new address.
3. The relayer delivers the original `RedeemEscrow` message; `onAccept` → `_authenticate` compares the old `request.from` against the new `_instance(request.source)` and reverts with `Unauthorized()` every time it is retried.
4. The solver's expected escrow release, and the underlying escrowed input tokens (`_orders[commitment][token]`), remain permanently locked in the source `IntentGatewayV2` contract with no available recovery function.

        if (request.from.length != 20) revert InvalidInput();
        address module = address(bytes20(request.from));
        if (_instance(request.source) != module) revert Unauthorized();
    }
