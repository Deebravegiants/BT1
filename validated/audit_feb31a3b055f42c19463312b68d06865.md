### Title
Webhook shop-domain header not covered by HMAC signature allows cross-tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `ShopifyAPI::Webhooks::Request#to_signable_string` used for HMAC verification only signs the raw request body, but the `shop-domain` header — which is passed to app webhook handlers as the authoritative tenant identifier — is never included in the signed content. Any party capable of producing a body+HMAC pair valid under the app's shared `api_secret_key` (e.g., a merchant who has installed the app and receives their own legitimately-signed webhooks) can replay that body with a forged `shop-domain` header to make the app process it as if it came from a different shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over whatever `to_signable_string` returns for the given `VerifiableQuery` [4](#0-3) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight off HTTP headers with no cryptographic binding to the signed payload [2](#0-1) .

`Registry.process` treats a passing `HmacValidator.validate(request)` check as proof the *entire request*, including `request.shop`, is authentic, then hands `request.shop` straight to the app's handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [3](#0-2) .

This breaks the intended identity binding: `shop header used by handler == shop cryptographically bound to signed bytes`. In reality, `shop header used by handler != shop bound to signed bytes` because the signature covers only the body.

Since `api_secret_key` is shared across all shops/tenants using the same app (it's the app's client secret, not a per-shop secret), any merchant who has installed the app can legitimately receive Shopify-signed webhooks for their own shop (valid body + valid HMAC for that body under the shared secret). That merchant can then resend the same body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `shopify-shop-domain`/`x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the attacker-controlled `shop` value to the handler as if it were verified [5](#0-4) .

### Impact Explanation
This allows an unprivileged existing tenant (any merchant with the app installed) to spoof webhook events as belonging to a different shop/tenant. Depending on what the app's webhook handler does with `WebhookMetadata#shop` (e.g., look up or mutate per-shop records, revoke access, redact data, trigger `shop/redact` or `customers/redact` flows keyed by shop), this can result in cross-tenant data corruption, unauthorized actions against another merchant's data, or bypass of shop-scoped authorization checks — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is moderate to high in practice: exploitation requires only that the attacker be able to install the target app on their own shop (a normal, unprivileged action for any Shopify merchant) and can then replay their own legitimately-received webhook body/HMAC with a modified `shop-domain` header. No access to the app's `client_secret`, another merchant's credentials, or TLS interception is required — only observation of a webhook the attacker's own shop legitimately received.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed content, or otherwise cryptographically bind the `shop-domain` header value to the signature verification — e.g., by having `to_signable_string` incorporate the header value being relied upon, or by having `Registry.process` cross-check that the shop making the request matches an expected/registered shop for that webhook subscription rather than trusting an unauthenticated header at face value.

### Proof of Concept
1. Merchant A installs the app on `shop-a.myshopify.com`. Shopify sends a legitimate webhook to the app: body `B`, header `shopify-shop-domain: shop-a.myshopify.com`, header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Merchant A (attacker) captures this request and replays it to the app's webhook endpoint, changing only the header to `shopify-shop-domain: shop-b.myshopify.com` (a victim shop also using the app), leaving body `B` and the HMAC header untouched.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully [6](#0-5) ; `request.shop` returns `"shop-b.myshopify.com"` while `request.hmac` still matches because it's computed only from `B` [7](#0-6) .
4. `Registry.process(request)` passes the HMAC check (`Utils::HmacValidator.validate(request)` validates body `B` against the shared `api_secret_key`, which is unrelated to the shop header) and calls the app's handler with `shop: "shop-b.myshopify.com"` [5](#0-4) .
5. The app's handler processes attacker-supplied data (topic/body from Merchant A's own shop) under Merchant B's tenant identity, with no way to detect the spoofing since the gem never validated `shop` against the signature.
