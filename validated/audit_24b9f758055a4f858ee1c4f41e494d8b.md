### Title
Webhook HMAC Only Covers the Raw Body, Not the `shop`/`topic`/`webhook_id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching `data.shop`, `data.topic`, `data.webhook_id`, and `data.body` to the app's handler. In reality, `ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` binds nothing but the JSON body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all read straight from attacker-controllable HTTP headers — are never part of the signed payload, yet they are trusted downstream as the tenant identity for routing/processing.

### Finding Description
`lib/shopify_api/webhooks/request.rb` implements `Utils::VerifiableQuery`:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled from unauthenticated request headers:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` claim (also from a header) — it never touches `shop`, `topic`, or `webhook_id`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to trust the whole request, including the shop identity, and passes it straight to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The gem's own documentation confirms the intended (but broken) binding: it states that `process` "will verify the request did indeed come from Shopify" and describes `data.shop` as "The shop domain of the webhook" [5](#0-4) [6](#0-5) , implying the shop field is authenticated. It is not.

The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine tenant (shop) identity`

Here that equality fails: the verified bytes are `raw_body` alone, while the tenant identity acted on (`shop`) comes from an unverified `x-shopify-shop-domain` / `shopify-shop-domain` header.

Critically, the HMAC secret (`Context.api_secret_key`, the app's client secret) is the **same for every shop that installs the app** — it is not per-tenant. So a genuine webhook delivered by Shopify to a merchant who installs the app (including an attacker who installs their own test/free store) yields a real `(raw_body, hmac)` pair signed with the app-wide secret, with no cryptographic tie to that merchant's shop domain.

### Impact Explanation
An attacker who has installed the target app on their own Shopify store receives real webhooks from Shopify (with valid HMAC signatures using the shared app secret) for their own store. They can capture one such `(raw_body, hmac-sha256)` pair, then replay it directly at the target app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain (and/or altering `x-shopify-topic`/`x-shopify-webhook-id`, none of which are covered by the signature either). `Utils::HmacValidator.validate` will accept this request as valid because it only checks the body, and `Registry.process` will call the app's handler with `data.shop` set to the forged victim domain. Any app that uses `data.shop` to key per-tenant storage or trigger per-tenant side effects (exactly as shown in the gem's own documented handler example, which does `perform_later(shop_domain: data.shop, ...)`) will process attacker-controlled webhook content under the victim's tenant identity — a cross-tenant data/action confusion.

### Likelihood Explanation
This requires no privileged credentials, no access token, and no interception — only the ability to install the target app on an attacker-owned/free development store (which is unprivileged and normal), capture one legitimate webhook delivery, and replay it against the target's public webhook endpoint with modified headers. The gem's public webhook-processing API is used exactly as documented.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the verified payload (e.g., verify against a per-shop expectation established during OAuth) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` computed as `HMAC-SHA256(app_secret, B)`.
2. Attacker sends a POST to the target app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: orders/create`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `B`; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(app_secret, B)` which equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...))` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to process attacker-controlled webhook content tagged as belonging to `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
