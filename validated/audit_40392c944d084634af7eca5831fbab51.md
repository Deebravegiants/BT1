### Title
`finalizeGraduation` permanently bricks graduation (freezing curve-raised LT and 250M reserved tokens) when `tokensForLP` rounds to zero and `LPLock.recordLock` reverts on the resulting empty liquidity - ([File: packages/contracts/src/Bonding.sol])

### Summary
CVE-2020-7062 is a PHP null-pointer dereference where a "cleanup" routine unconditionally runs on data that was never populated (upload-progress tracking succeeded to the point of being armed, but the actual session data doesn't exist), crashing the process. The analogous pattern in alt.fun is `Bonding.finalizeGraduation`, which unconditionally calls the one-shot, non-skippable `LPLock.recordLock` "cleanup" step even when the preceding LP-seeding math legitimately produced zero liquidity (an empty-data condition), causing a deterministic, irrecoverable revert that permanently freezes the graduating token's raised LT and reserved tokens.

### Finding Description
`_prepareGraduationLiquidity` computes the LP-bound token amount from the curve's own reserves: [1](#0-0) 

`tokensForLP = (ltFromPair * tokenReserve) / assetReserve`. Because `Pair`'s constant-product invariant ties `tokenReserve` and `assetReserve` together via `k = tokenReserve * assetReserve` (baked in at launch and never recomputed, per the `_launchTimeVirtualLtReserve` derivation), a curve that is bought all the way to (or very near) full sellout drives the live `tokenReserve` down toward its floor (as small as the `+1` K-slack allows). When `tokenReserve` is that small relative to `assetReserve`, the numerator `ltFromPair * tokenReserve` is strictly less than `assetReserve`, so integer division floors `tokensForLP` to exactly `0` — even though `ltFromPair` (real LT raised) is large and nonzero.

This value is cached once, at phase 1, into `pendingGraduation` and is never recomputed: [2](#0-1) 

At phase 2, `tokensForLP == 0` flows into `_seedUniswapV2Direct` → (typically) `_seedDirectMint`, which transfers `0` tokens and `ltFromPair` LT to the pair and mints on the empty pair: [3](#0-2) 

Uniswap V2's `mint` on an empty pool computes `liquidity = sqrt(amount0*amount1)`; with one side `0`, `liquidity` is `0` (or in a rebalance-branch case, `_routerDepositAndDispose` explicitly skips `addLiquidity` entirely whenever either remaining side is `0`, also returning `liquidity = 0`): [4](#0-3) 

`finalizeGraduation` never checks `liquidity != 0` before invoking `LPLock.recordLock`, which is the "cleanup"/finalization step here: [5](#0-4) 

`LPLock.recordLock` explicitly reverts on a zero amount: [6](#0-5) 

Because the revert unwinds the entire `finalizeGraduation` transaction, `pendingGraduation[tokenAddress]` (deleted just before the `recordLock` call) is restored to its pre-tx value — the same cached, deterministically-zero `tokensForLP`. Every subsequent call to `finalizeGraduation` recomputes the identical `_seedUniswapV2Direct` result off the same frozen cache and hits the same `ZeroAmount()` revert. There is no owner/admin rescue path for a token stuck in `Lifecycle.Graduating` — `LPLock.isLocker` is add-only and `recordLock` has no bypass, and the contract exposes no function to adjust or clear `pendingGraduation` once cached. The token is permanently stuck: trading is frozen (`buy`/`sell` both revert with `TokenIsGraduating`/`TokenNotTrading`), and the real LT raised by the curve (`ltFromPair`) plus the curve's entire `LP_RESERVE` (250M tokens) sit unrecoverably inside `Bonding`.

### Impact Explanation
This is a permanent freeze of protocol funds reachable by unprivileged actors: once a token's curve is bought down to a near-zero residual `tokenReserve` (an entirely ordinary, expected outcome of the supply-sellout graduation trigger `IPair(pair).tokenBalance() == 0`), graduation becomes permanently unfinalizable. The affected token's traders lose the ability to ever cash out to the graduated liquid market, its creator's raised LT is frozen forever inside `Bonding` with no sweep, and the 250M reserved LP tokens are permanently stranded. This meets the "permanent freezing of trader, creator, or LP funds" bar for a High-severity finding.

### Likelihood Explanation
No attacker collusion or special privilege is required — any sequence of ordinary buys (or a single large buy) that drives the curve to full sellout while `assetReserve` is large relative to the residual `tokenReserve` triggers the rounding-to-zero condition. The condition is more likely, not less, the more successful/heavily-traded a launch is (the more the curve is bought out, the smaller `tokenReserve` becomes relative to `assetReserve`), making this a realistic outcome of normal usage rather than a contrived edge case.

### Recommendation
In `_prepareGraduationLiquidity`, guard against `tokensForLP` (and symmetrically `ltFromPair`) rounding to zero when the other side is nonzero — e.g., floor `tokensForLP` to `1` when `ltFromPair > 0 && tokenReserve > 0` but integer division truncates to `0`, or reject the phase‑1 entry / require a minimum residual amount before allowing `_enterGraduating` to cache a degenerate split. Additionally, `finalizeGraduation` should explicitly check `liquidity != 0` before calling `LPLock.recordLock` and provide an owner-controlled recovery/retry path (e.g., re-derive `tokensForLP`/`ltFromPair` with a corrected floor, or an explicit rescue function) so a degenerate cached split can never permanently brick a token's graduation.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed (`MIN_SEED_USDC`).
2. Have unprivileged buyers repeatedly call `Zap.buy` until the curve's live `tokenBalance()` approaches `0` (the supply-sellout trigger). Because `Router`'s constant-product buy math (`Pair`'s `k` invariant with the `+1` slack) allows the residual `tokenReserve` to shrink to a very small positive value while `assetReserve` grows large, the final buy causes `canGraduate` to return `true` via the supply trigger and `_enterGraduating` fires, caching `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` — which floors to `0` given the small `tokenReserve` and large `assetReserve` (`Bonding.sol:1089`).
3. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_seedDirectMint`/`_routerDepositAndDispose` produces `liquidity = 0`; `LPLock.recordLock(tokenAddress, lpPair, 0)` reverts with `ZeroAmount()` (`LPLock.sol:78`), reverting the whole transaction.
4. Every future call to `finalizeGraduation` for this token reverts identically, because `pendingGraduation[tokenAddress]` was restored to the same cached zero-`tokensForLP` state. The token is permanently stuck in `Lifecycle.Graduating`: trading is frozen, and its raised LT plus the 250M reserved tokens remain locked in `Bonding` with no rescue path.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
