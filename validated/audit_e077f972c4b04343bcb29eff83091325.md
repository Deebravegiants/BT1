This confirms the vulnerability. The `shop` and `topic` fields in `ShopifyAPI::Webhooks::Request` come from HTTP headers (`shopify-shop-domain`, `shopify-topic`) but the HMAC signature only covers `@raw_body` via `to_signable_string`, as defined in [1](#0-0)  and [2](#0-1) . The `Registry.process` method validates only the HMAC over this body, then dispatches the handler using the unverified `shop` header, as seen in [3](#0-2) .

### Title
Webhook shop-domain header not bound to HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [4](#0-3) . `Utils::HmacValidator.validate` verifies only that the `hmac` matches the signable string (the body) using the app's secret [5](#0-4) . `Registry.process` trusts this validation, then hands `request.shop` (identity of the tenant) straight to the app's handler without any cross-check against the HMAC-covered content [3](#0-2) .

### Finding Description
The identity binding broken is: `shop header used for tenant attribution` ≠ `shop covered by HMAC`. Because the HMAC is computed only over `@raw_body`, none of `shop-domain`, `topic`, `api-version`, or `webhook-id` headers are cryptographically bound to the signature. An attacker who captures one legitimate webhook delivery (body + valid HMAC, e.g. from a webhook sent to their own low-privilege shop, or from a shared endpoint receiving webhooks for multiple tenants) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to any other shop domain of the attacker's choosing. `Utils::HmacValidator.validate(request)` will still return true because it only checks the body against the secret [6](#0-5) , and `Registry.process` will dispatch the handler with the attacker-chosen `shop` value [7](#0-6) .

### Impact Explanation
This qualifies as **Critical - cross-tenant access**. Any app that relies on `WebhookMetadata#shop` to attribute webhook data to the correct merchant/tenant (e.g. to look up which stored session/access token to use, or which tenant's database row to update) can be tricked into processing attacker-supplied body content under a victim shop's identity, or attacker's own valid webhook re-labeled as belonging to a different shop. Because host applications built on this gem are documented to key everything off `data.shop`, this breaks the core tenant boundary the gem is supposed to provide.

### Likelihood Explanation
Likelihood is elevated because obtaining one valid `(body, hmac)` pair only requires the attacker to control or observe deliveries to any shop they have access to (including their own free/dev store installing the app), which is an "unprivileged internet user" action relative to any other tenant. No access token, `client_secret`, or privileged account for the target shop is required — only header manipulation on the replayed HTTP request to the app's public webhook endpoint.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with body `B`. Shopify signs it: `hmac = HMAC-SHA256(secret, B)`.
2. Attacker captures the raw POST: headers `x-shopify-hmac-sha256: hmac`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, body `B`.
3. Attacker replays this POST to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` computes HMAC over `body B` only and it still matches, since `shop-domain` isn't part of the signed string [2](#0-1) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [7](#0-6) , causing the host app to process attacker-controlled data under the victim's tenant identity.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the HMAC-verified signable content, or independently verify that the `shop-domain` header corresponds to a shop with an active, stored session/installation known to the app before dispatching the handler. At minimum, document and enforce that consumers must cross-check `request.shop` against their own session store keyed by a value that is itself authenticated (not just present in headers).
