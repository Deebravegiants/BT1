### Title
Webhook shop identity spoofable via unauthenticated `shop-domain` header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook exclusively from the `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator.validate` — the only integrity check performed by `Webhooks::Registry.process` — verifies the HMAC over the raw request body alone.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the signature against that signable string only [2](#0-1) . `Registry.process` gates all further handling solely on this HMAC check: `raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)` [3](#0-2) . Immediately after, it builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and forwards it to the app's handler — but `request.shop` is read straight from the header via `shopify_header("shop-domain")` [4](#0-3) , which is never included in the HMAC-covered bytes.

The binding that should hold is: `hmac_verified_bytes == bytes_that_determine_tenant_identity`. Here, `hmac_verified_bytes = raw_body` while `bytes_that_determine_tenant_identity = shop-domain header`, so the equality is broken — the shop identity field is "acted on but not covered by the HMAC," matching the analog class of the referenced report (a field used for accounting/identity purposes that is not protected by the same binding as the rest of the payload).

### Impact Explanation
Because the header is unauthenticated, anyone who can capture one legitimately-delivered webhook (its raw body plus its valid HMAC digest — trivially obtainable by installing the app on an attacker-controlled development store, which requires no privilege beyond normal internet access) can replay that exact body/HMAC pair to the same public webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will accept it (HMAC still validates against the unchanged body) and will invoke the app's registered handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application that uses this `shop` field to select which tenant's record to update (the documented and expected usage pattern) will apply attacker-controlled webhook data to the wrong tenant, resulting in cross-tenant state corruption/confusion.

### Likelihood Explanation
Medium: requires the attacker to obtain at least one legitimate webhook delivery (achievable by self-installing the target app) and a network-reachable webhook endpoint, both realistic for an unprivileged actor, but the actual exploitation depends on how the host app consumes `WebhookMetadata#shop` versus a body-embedded shop reference.

### Recommendation
Include the identity-bearing header (shop domain, at minimum) in the value that is HMAC-verified, or independently re-derive/cross-check the shop from data inside the signed body where the topic includes shop-scoped payload fields, so that the verified bytes and the bytes used to determine tenant identity are provably the same.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store (`attacker.myshopify.com`) and receives a legitimate webhook, e.g. `orders/updated`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`).
2. Attacker POSTs the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it originated from the victim's shop.
