### Title
Legacy gateway handler allows client-controlled MessageID collisions to overwrite another user's pending callback, causing cross-user response delivery - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` stores each incoming request's callback in a shared map keyed only by the client-supplied `msg.Body.MessageID`, with no check that the ID is not already in use by another in-flight request. A later request that reuses (or predicts/collides with) another user's `MessageID` silently overwrites the earlier entry, so the response the DON eventually returns for that ID is delivered to the second (attacker-controlled) callback instead of the original requester. This mirrors the Cooler `clear()` bug class: the party that is ultimately paid/answered is not necessarily the party that actually initiated the request — the routing key can be hijacked by an unprivileged third party.

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the callback map entry: [1](#0-0) 

When the DON node later replies, the gateway looks the response up purely by `msg.Body.MessageID` and delivers it to whatever callback is currently stored under that key, with no verification that the responding request corresponds to the same requester that registered the callback: [2](#0-1) 

The same unguarded overwrite pattern exists in the dummy/legacy handler used for testing/fallback paths: [3](#0-2) 

By contrast, the newer JSON-RPC based handlers (vault, confidential relay, HTTP trigger v2) explicitly reject a request whose ID already exists in the active-request map before creating a new entry: [4](#0-3) [5](#0-4) 

This shows the project is aware that request-ID collisions from unprivileged clients are a real risk and defends against them in the JSON-RPC paths, but the legacy `capabilities` handler and `handler.dummy.go` path do not apply the same guard.

### Impact Explanation
Because `MessageID` originates from the untrusted, unprivileged client request, one client can intentionally choose a `MessageID` that collides with another in-flight legacy request. Once the collision happens:
- The original requester's callback is silently discarded/replaced (`h.savedCallbacks[msg.Body.MessageID] = ...`), so they may never receive their legitimate response (or get a stale timeout instead).
- The DON's response for the original request is delivered to the attacker's callback, exposing the response content (e.g., web API trigger acknowledgement/result payload) intended for a different user — a cross-user response confusion analogous to funds being routed to the wrong Cooler owner.

This is a request-impersonation / response-hijack primitive reachable directly from the internet-facing gateway with no privileged access required.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where the legacy message path (`HandleLegacyUserMessage`) remains active: any client can pick their own `MessageID`. Exploitation only requires knowing or guessing another party's in-flight `MessageID` (e.g., via traffic observation, common request-ID schemes, or simply flooding with a specific value while the target sends around the same time) and issuing a competing request before the legitimate one resolves.

### Recommendation
Apply the same collision-rejection strategy used by the vault and confidential-relay handlers to the legacy handler: before inserting into `savedCallbacks`, check whether an entry for that `MessageID` already exists and reject the new request (or scope the callback map key by requester/sender identity rather than by client-controlled `MessageID` alone) in `core/services/gateway/handlers/capabilities/handler.go` (`HandleLegacyUserMessage`) and `core/services/gateway/handlers/handler.dummy.go` (`HandleLegacyUserMessage`).

### Proof of Concept
1. User A sends a legacy `web_api_trigger` message with `MessageID = "X"`; the gateway stores A's callback under `savedCallbacks["X"]` and forwards the request to DON members.
2. Before the DON responds, attacker B sends a second legacy message also using `MessageID = "X"`; the gateway overwrites `savedCallbacks["X"]` with B's callback (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
3. The DON node responds to `MessageID = "X"` (originally destined for A's request); `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's entry, and delivers A's response payload to B (`core/services/gateway/handlers/capabilities/handler.go:148-162`).
4. User A never receives a response (their callback silently vanished), while attacker B receives content intended for A.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageID] = &savedCallback{msg.Body.MessageID, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageID,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
