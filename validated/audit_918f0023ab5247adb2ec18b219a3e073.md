## Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to application webhook handlers come from unauthenticated HTTP headers. `Registry.process` only validates the body's HMAC before dispatching these unauthenticated header values to the handler, breaking the intended binding between "the shop the HMAC proves the message is authentic for" and "the shop the handler is told the message came from."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts the unauthenticated headers to build the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms this: it signs/compares only `verifiable_query.to_signable_string`, i.e., only the body, never the shop/topic headers: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. In this implementation, the HMAC only authenticates *bytes of the body*; it says nothing about which shop or topic produced them. So the real binding enforced is: `HMAC(body, secret) == received_hmac`, with `shop`/`topic` supplied out-of-band and unchecked. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — for example, a malicious merchant who installs the app and receives a legitimately signed webhook for their **own** shop — can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while forging the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to point at a **different, victim** shop. `HmacValidator.validate` still returns `true` because it never looks at those headers, and `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler using the attacker-controlled header values.

The gem's own documentation reinforces the false assumption that HMAC validation authenticates the whole request ("This will verify the request did indeed come from Shopify"), when in fact only the body bytes are authenticated: [5](#0-4) 

### Impact Explanation
This is a cross-tenant integrity/authentication issue: a webhook can be delivered to the app under the identity of a shop the sender does not control, causing the app's business logic (order processing, inventory updates, data writes keyed by `shop`, job enqueueing per `data.shop`, etc., per the documented handler contract) to run against a victim tenant's data using attacker-supplied body content that was only ever authenticated for the attacker's own tenant. This matches the "Critical: cross-tenant access" impact category, since it lets one merchant's traffic be attributed to another merchant's `shop` identity purely by header manipulation, without needing the `client_secret`.

### Likelihood Explanation
Exploitation requires only: (1) the attacker to be a legitimate (even trial) merchant of the target app, so they receive at least one real webhook signed with the app's shared `client_secret`, and (2) the ability to POST arbitrary headers to the app's public webhook endpoint (which is unauthenticated by design, per the documented Rails handler example). Both are realistic for any multi-tenant Shopify app, making this a HMAC-validation-passes-but-binding-is-wrong ("field acted on but not covered by the HMAC") class of bug, directly analogous to the report's admin-index/state-mismatch pattern where a value is trusted or acted upon without being tied to the same authenticated context that validation is supposed to establish.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signable material, or otherwise cryptographically bind them to the verified body (e.g., verify the shop by cross-referencing an active, stored session for that shop rather than trusting the header alone). At minimum, document explicitly that `Request#shop`/`#topic`/`#webhook_id` are NOT covered by `HmacValidator.validate` and that host apps must independently corroborate the shop identity (e.g. against known installed shops) before acting on webhook data.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook: body `B`, headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, H)` from their own webhook delivery.
3. Attacker POSTs to the app's public webhook endpoint with the same body `B` and same header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)`, which still equals `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
5. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), even though that shop never sent or authorized this payload.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
