Webhook `shop`/`topic`/`webhook_id` headers are trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking an HMAC over the raw request body, then hands the handler a `WebhookMetadata` object built from `shop`, `topic`, and `webhook_id` values that are read straight from HTTP headers and are never part of the signed bytes. This breaks the identity binding `authenticated_bytes == acted_on_bytes`: the gem verifies the body, but the caller acts on the shop identity, mirroring the report's bug class of a "field acted on but not covered by the HMAC."

### Finding Description
- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled from HTTP headers, none of which feed into `to_signable_string`: [2](#0-1) 
- `Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header value: [3](#0-2) 
- `Registry.process` uses this body-only HMAC check as the sole authentication gate, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived, unauthenticated values — to build the `WebhookMetadata` passed to the host application's handler: [4](#0-3) 

Because Shopify's webhook HMAC scheme (as implemented by this gem) signs only the raw body, any bytes that arrive with a valid body+HMAC pair (e.g., a webhook the attacker legitimately receives for their own installed/test shop) can have its `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers freely rewritten by an on-path or replaying attacker without invalidating the signature check. `HmacValidator.validate` will still return `true`, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the tampered `shop` value, `topic`, and `webhook_id`. This is exactly the "shop authenticated versus shop stored/acted on" binding break called out in the rules: the gem proves the body came from Shopify with the app's secret, but does not prove which shop or topic that body pertains to.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` returned by this gem to route data to the correct tenant record (a standard, documented usage pattern for multi-tenant Shopify apps) can be made to process an attacker-controlled/replayed webhook body under an arbitrary victim shop's identity, since the shop field is not bound to the signature. This is a cross-tenant data-integrity issue: attacker-influenced webhook payloads can be attributed to a shop the attacker does not control, as long as the attacker can obtain (or replay) one validly-signed body for the same app (e.g., from their own installed development store) and control or intercept the headers delivered to the host's endpoint. This maps to the Critical "cross-tenant access" impact category since the gem itself is the layer responsible for authenticating and exposing the identity fields the host application is expected to trust.

### Likelihood Explanation
Medium-High. No access token, `client_secret`, or privileged account is required — this is exploitable by any actor able to deliver an HTTP request to the app's webhook endpoint with a validly-signed body (e.g., an attacker who installs the app on their own free/dev shop obtains genuinely signed webhook bodies for that shop, or an attacker sitting on a network path/proxy in front of the webhook endpoint can rewrite headers on legitimate deliveries). The vulnerability requires no cryptographic break — it exploits the fact that the gem's `HmacValidator` never binds header-derived identity fields to the signature, which is a design gap in this gem rather than a host-application misuse of a documented API.

### Recommendation
Extend the HMAC-covered signable content (or perform a secondary authenticated binding) to include `shop`, `topic`, and `webhook_id`, or clearly document that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must be independently verified (e.g., cross-checked against a known/registered shop domain) before being used for tenant routing. At minimum, `Utils::HmacValidator.validate` should be changed so `Webhooks::Request#to_signable_string` incorporates the shop/topic/webhook-id headers so tampering with them invalidates the signature.

### Proof of Concept
1. App receives (or an attacker legitimately triggers on their own installed test shop) a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this signature depends only on `B`.
2. Attacker (with network path control to the webhook endpoint, or replaying the same request) changes `x-shopify-shop-domain` from `attacker-shop.myshopify.com` to `victim-shop.myshopify.com`, keeping `B` and `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: tampered_headers)` is constructed; `request.hmac` still decodes to `H`, and `request.shop` now returns `"victim-shop.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — this matches `H`, so validation passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the body `B` and its authenticated origin have nothing to do with `victim-shop`: [6](#0-5)
