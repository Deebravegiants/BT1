### Title
Webhook `shop` Identity Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by checking only that the HMAC over the raw request body matches, but the `shop` identity that is subsequently handed to the app's handler is read from the unsigned `shopify-shop-domain` HTTP header. Because the signature never binds to the shop domain, any party who can obtain one genuinely-signed webhook body (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process/attribute the event to a different ("victim") tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes the fields extracted from the raw HTTP request: [1](#0-0) 

`to_signable_string`, which is the only input fed into HMAC computation, returns solely the raw body — the `shop-domain` header is excluded from the signable content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` performs this HMAC check and then, having validated only the body, forwards `request.shop` — the unauthenticated header value — straight into `WebhookMetadata` that is passed to the developer's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain, trusted `String` field with no additional binding to the signature: [5](#0-4) 

The gem's own documentation instructs apps to key their business logic (e.g., background job dispatch, per-shop state updates) directly off `data.shop`: [6](#0-5) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop_domain_covered_by_hmac == shop_domain_delivered_to_handler`

In reality, `to_signable_string` (and therefore the HMAC) covers **only** `@raw_body`; `shop` is read independently from `shopify_header("shop-domain")`, which is attacker-controlled HTTP header data, not cryptographically bound to the signature at all.

Because Shopify apps use a single `client_secret` (`Context.api_secret_key`) shared across every shop that installs the app, any shop that installs the app receives correctly HMAC-signed webhook bodies for its own store. An unprivileged user who controls such a shop can capture one of these legitimately-signed `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a different, victim shop. `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while `body` is the attacker's own webhook payload.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an app relying on `data.shop` (as the docs instruct) to select which merchant's session/access token to use, which per-shop records to update, or which shop to treat an event as originating from, can be made to attribute attacker-supplied data to an arbitrary victim shop. This satisfies the "cross-tenant access" criterion — a party without any relationship to the victim's shop can inject or misattribute events (e.g., fake `orders/create`, `app/uninstalled`, or `shop/redact` payloads) as if they came from the victim, corrupting or exfiltrating cross-tenant application state via this gem's own webhook verification API.

### Likelihood Explanation
Exploitation only requires installing the target app on any single Shopify store (a routine, unprivileged action available to any developer/merchant), capturing one legitimately delivered webhook, and replaying it with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential of the victim is needed — only the app's shared secret behavior, which is inherent to how `HmacValidator`/`Request` are implemented in this gem.

### Recommendation
Bind the shop identity into the value verified by the HMAC, or otherwise cross-check it against server-side state, before it is trusted:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the signable string used for HMAC computation in `Webhooks::Request#to_signable_string`, matching what Shopify actually authenticates for the event, or
- After HMAC validation, verify `request.shop` corresponds to a shop for which this specific webhook subscription/session is known to exist (e.g., cross-reference against the registered webhook's shop) before constructing `WebhookMetadata`, rejecting the request if it doesn't match.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimately signed webhook to the app: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker replays this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` → `HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (`= B`) and it matches the supplied HMAC, so validation passes: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the app processes/enqueues work attributing attacker-controlled content to the victim shop.

          received_signature = verifiable_query.hmac
