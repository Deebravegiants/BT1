### Title
Unchecked length subtraction in `HyperFungibleToken::on_accept` causes panic on malformed cross-chain `from` field - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in the `hyper-fungible-token` pallet's ISMP module decodes an ABI-encoded `Message` from an inbound `PostRequest` body and, when optional calldata is present and unsigned, derives the dispatch origin from `message.from` with:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
}
``` [1](#0-0) 

`from_bytes.len() - 20` is computed on an attacker/sender-controlled length with no minimum-length validation before the subtraction, mirroring the CVE's root cause pattern (`header->size - sizeof(cmd->body)` performed before checking `header->size` is large enough).

### Finding Description
The `Message` struct is ABI-decoded directly from the request body of an inbound ISMP `PostRequest`:
```rust
let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;
``` [2](#0-1) 

Note that elsewhere in the same function, the pallet is careful to validate length before using it, e.g. for `to_bytes`:
```rust
if to_bytes.len() == 32 {
    beneficiary_bytes.copy_from_slice(to_bytes);
} else if to_bytes.len() == 20 {
    beneficiary_bytes[12..].copy_from_slice(to_bytes);
} else {
    Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
}
``` [3](#0-2) 

and the same field (`from_bytes`) is validated in `on_timeout`:
```rust
if from_bytes.len() == 32 {
    sender_bytes.copy_from_slice(from_bytes);
} else if from_bytes.len() == 20 {
    sender_bytes[12..].copy_from_slice(from_bytes);
} else {
    Err(HftError::InvalidSenderLength(from_bytes.len()))?
}
``` [4](#0-3) 

However, the code path taken when the optional calldata carries no signature (`substrate_data.signature` is `None`) skips this validation entirely and computes `from_bytes.len() - 20` directly: [5](#0-4) 

If `message.from` (a Solidity `bytes` field, fully attacker-controlled at ABI-encoding time) is shorter than 20 bytes, `from_bytes.len() - 20` underflows and the subsequent slice index is always out of range, causing an index/arithmetic panic inside `on_accept`.

### Impact Explanation
`on_accept` is invoked by `pallet-ismp`'s message-dispatch machinery when relayed cross-chain requests are delivered to the module. A panic surfacing from a module callback during request delivery is not a normal `Result::Err` — it aborts execution rather than gracefully failing the single request, which can disrupt block/extrinsic execution for the whole dispatch batch depending on how the caller wraps module invocation. At minimum this is a reliable griefing vector against the HFT bridge route (a specific inbound message can always be crafted to crash processing of any batch it's included in), which falls under "a route unable to deliver messages."

### Likelihood Explanation
The trigger requires only that:
1. The request's outer ISMP `source`/`from` pair matches a `ContractToAsset` mapping (i.e. it appears to originate from a registered HyperFungibleToken.sol deployment).
2. The `body` ABI-decodes to a valid `Message` with `data` non-empty, whose decoded `SubstrateCalldata` has `signature = None` and `message.from` shorter than 20 bytes.

I was not able to fully confirm within the available investigation whether the paired Solidity `HyperFungibleToken.sol` contract strictly enforces `message.from == msg.sender` (which would prevent an attacker from freely shortening this field) or whether some other permissionless path (e.g., a governance/registered app allowed to construct raw `Message` payloads) can set `message.from` to fewer than 20 bytes. This reachability gap is the main uncertainty in this finding — if the source-chain contract always sets `from` to a full 20-byte address, this path is unreachable by an ordinary sender and the practical severity would be much lower (Low/no impact).

### Recommendation
Add an explicit length check on `from_bytes` in the unsigned-origin branch of `on_accept`, mirroring the checks already present for `to_bytes` and for `on_timeout`'s `from_bytes`, returning an explicit `HftError` (e.g. `InvalidSenderLength`) instead of allowing the subtraction/slice to run unchecked.

### Proof of Concept
Not independently executed. Conceptually: craft an ISMP `PostRequest` whose `source`/`from` match a registered `ContractToAsset` entry, with `body` ABI-encoding a `Message` where `data` is a SCALE-encoded `SubstrateCalldata{ signature: None, runtime_call: <any valid call bytes> }` and `from` is set to fewer than 20 bytes (e.g., empty). Deliver it through the module's `on_accept`; the `from_bytes.len() - 20` computation at [6](#0-5)  underflows/panics before any signature-based authentication is required, since this is the *unsigned* branch.
