### Title
Webhook shop identity not covered by HMAC signature allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop-domain` header — the tenant identity that is later handed to the app's handler — is never included in the signed material. This breaks the identity binding `shop authenticated == shop acted on`, allowing a holder of any single valid `(body, hmac)` pair to relabel the payload as coming from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from the `shop-domain`/`x-shopify-shop-domain` header, which is part of the request but not part of the signed string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` as the tenant identity and hands it to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever compute and compare the HMAC over `verifiable_query.to_signable_string` (the raw body for webhooks), never touching `shop`, `topic`, `api_version`, or `webhook_id`: [4](#0-3) 

The trusted `shop` value flows directly into `WebhookMetadata`, the struct the host app's `WebhookHandler#handle` implementation uses to decide which tenant's data to read/write: [5](#0-4) 

The identity equality this code is supposed to enforce is:
`shop header the handler receives == shop the api_secret_key-holder (Shopify) actually generated this HMAC for`

Because `shop` is excluded from the signable string, this equality is never checked. Any actor who can obtain one genuinely Shopify-signed `(raw_body, hmac)` pair — trivially available to any merchant/developer who installs the app on their own store and receives one real webhook — can resend that exact body/HMAC to the app's webhook endpoint with the `shop-domain` header changed to any other shop the attacker chooses. `HmacValidator.validate` still succeeds because it never inspected the header, and `Registry.process` dispatches the handler with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged holder of one legitimately-signed webhook can make the app believe a payload originated from a different (victim) merchant's shop. Depending on how the host app implements `WebhookHandler#handle` (a documented, expected usage pattern of this gem — the `shop` field of `WebhookMetadata` is the only tenant discriminator the gem provides), this can be leveraged to write/inject data under, or trigger side effects for (e.g. deprovisioning via `app/uninstalled`, GDPR redact webhooks, order/customer processing) an arbitrary victim shop's tenant record, without ever needing that shop's credentials — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Likelihood is high for any attacker who is themselves able to install the app on a shop they control (the normal, permission-less path any developer/merchant can take): they receive real webhooks with valid raw bodies and HMACs signed with the app's shared secret, and can freely replay that exact body/signature pair against the same public webhook endpoint with only the `shop-domain` header changed — no cryptographic material needs to be broken or guessed.

### Recommendation
Bind the identity fields into the signature check: include the `shop`, `topic`, `webhook_id` (or reconstruct/validate them independently, e.g. against a known list of shops with active app installations) as part of `to_signable_string`, or otherwise verify that the `shop-domain` header on an inbound webhook corresponds to a shop with a currently valid session/installation before dispatching to the handler, rather than trusting the header purely because the body-only HMAC matched.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify send a real webhook, capturing `raw_body` and the resulting `x-shopify-hmac-sha256` header (both legitimately generated by Shopify using the shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, adjusts `x-shopify-topic`/`x-shopify-webhook-id`, which are likewise unsigned).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this matches, so validation passes: `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and invokes the app's `handle`, which now performs whatever tenant-scoped action the handler implements against the victim shop's identity: `lib/shopify_api/webhooks/registry.rb:198-199`.
