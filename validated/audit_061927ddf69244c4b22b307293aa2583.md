### Title
Bypass of backend-verified enrollment (`enroll_user`) when `user_centric_signup` flag is set, allowing signups to be locally approved without backend validation - (File: `src/plans/mod.rs`)

### Summary
The external report describes an IL-protection bypass in vader's `Pools.sol`, where calling `removeLiquidity()` directly skips the protective logic that is only enforced when going through `Router.sol`. The orb-core analog is in `MasterPlan::do_signup`: when the scanned user QR-code/app reports `user_centric_signup == true` (and the orb's config does not override it via `ignore_user_centric_signups`), the code takes a shortcut path that never calls the protective `enroll_user()` function — the function that actually performs the authoritative, backend-verified enrollment request (`signup_post::request`). Instead, "success" is derived purely from a locally computed `signup_reason`, bypassing backend-side signup verification entirely.

### Finding Description
In `MasterPlan::do_signup`, after biometric capture/pipeline and PCP package upload (which already occurs unconditionally), the code branches on `user_centric_signup`: [1](#0-0) 

When `user_centric_signup && !ignore_user_centric_signups` is true, the orb never calls `self.enroll_user(...)`, which is the function that performs the real, backend-authoritative signup submission via `enroll_user::Plan::run` → `signup_post::request`: [2](#0-1) 

`signup_post::request` is the function that actually notifies the backend of the signup, carrying the signature, reason, and other identifying data, and is the equivalent of `Router.sol`'s protective wrapper in the referenced report — it is the path that provides authoritative server-side registration/validation of the signup: [3](#0-2) 

Instead, in the bypass branch, "success" is decided purely by the locally computed `signup_reason`, which itself is derived from `fraud_detected`, a value that is now always `false` because all fraud checks have been deleted from the FOSS build: [4](#0-3) [5](#0-4) 

The `user_centric_signup` flag itself comes from `orb_qr_link::UserData`, decoded from the app-provided QR/backend response in `backend::user_status::request`: [6](#0-5) 

The config flag that is supposed to force the protective (backend-verified) path, `ignore_user_centric_signups`, defaults to `false`: [7](#0-6) [8](#0-7) 

Note that the Personal Custody Package (biometric image/embedding) upload to the backend already happens unconditionally earlier in `do_signup`, before this branch is evaluated: [9](#0-8) 

So under the `user_centric_signup` path, biometric data has already been uploaded to the backend, yet the orb marks the signup "successful" locally without ever invoking the protective `enroll_user`/`signup_post::request` call that would have registered/verified the signup with the backend's authoritative signup endpoint.

### Impact Explanation
This mirrors the report's root cause exactly: a protective function (`enroll_user`, analogous to `Router.sol`'s IL-protected `removeLiquidity`) is bypassed by an alternate code path (the `user_centric_signup` branch, analogous to calling `Pools.sol` directly) that determines success/failure using only local, weaker logic. Because fraud checks are stubbed out to always return `false` (`fraud_check.rs`), the local `signup_reason` computation provides essentially no protection, so any capture that completes the pipeline will be marked `SignupReason::Normal`, and thus reported as a "successful" signup — while never being registered/validated by the backend's authoritative enrollment endpoint. This creates a state where biometric data has been uploaded and the local orb records success, but the backend's own bookkeeping/verification of that specific signup (which the `enroll_user`/`signup_post::request` path exists to perform) never happens, leading to signup state that is locally attributed as legitimate but not backend-verified — a misattributed/orphaned signup scenario.

### Likelihood Explanation
The branch is reachable in normal signup flow whenever the backend-provided `user_centric_signup` flag is `true` for a given user QR code and the orb's `ignore_user_centric_signups` config (which defaults to `false`) has not been explicitly set to override it. This is not a hypothetical edge case — it's a standard, config-driven code path intended to support "app-centric" signups, but it silently skips the enforcement path that provides backend-side signup verification.

### Recommendation
Ensure that any code path which can mark a signup as `success` (or update `debug_report.enrollment_status`) is required to go through the same backend-verified enrollment call (`enroll_user`/`signup_post::request`), instead of allowing an alternate local-only success determination for `user_centric_signup`. If the design intent is to explicitly skip backend registration for app-centric signups, this should be clearly documented and the local fraud/duplicate-prevention logic used in that branch must not rely on a fraud-check subsystem that is a no-op (`N_FRAUD_CHECKS = 0`), since that makes the bypass path unconditionally deterministic (`Normal` for any completed pipeline).

### Proof of Concept
1. A user QR-code/app session where the backend's `authenticated_app_data.user_centric_signup` is `true` completes the biometric capture and pipeline stages of `do_signup` (`src/plans/mod.rs`).
2. PCP tier packages are uploaded to the backend unconditionally (`src/plans/mod.rs:580-636`).
3. Because `orb.config.lock().await.ignore_user_centric_signups` defaults to `false` (`src/config.rs:436`), execution enters the `user_centric_signup` branch (`src/plans/mod.rs:639-645`) instead of calling `self.enroll_user(...)`.
4. Since `detect_fraud` always returns `Ok(false)` (`src/plans/mod.rs:1390-1406`, `src/plans/fraud_check.rs:10-12`), `signup_reason` is `SignupReason::Normal` for any pipeline that produces a `Some(pipeline)`, so `success` becomes `true` without ever calling `signup_post::request` (`src/backend/signup_post.rs:98-109`), meaning the backend's authoritative signup endpoint is never notified for this signup despite biometric data already being uploaded.
