### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header (`x-shopify-shop-domain`/`shopify-shop-domain`) that is never included in the data signed by the HMAC. `Registry.process` validates the HMAC and then forwards `request.shop` to the app's `WebhookHandler` as the authoritative tenant identifier, without that value ever being bound to the signature it just validated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` reads the shop identity purely from a request header, independent of that signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` gates on this HMAC check and then trusts `request.shop` (unverified) as the tenant identity passed into the app's handler via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

**Identity binding broken (equality that should hold but doesn't):**
`shop_identity_used_by_handler (request.shop, from header)` == `shop_identity_covered_by_hmac (none — only raw_body is signed)`

Before the attacker's request: a genuine Shopify-delivered webhook has `raw_body` signed with `Context.api_secret_key`, and the `x-shopify-shop-domain` header correctly reflects the originating shop, but the header itself carries no cryptographic binding to the signature.

After the attacker's request sequence: an attacker who controls their own shop (installed on the same app, e.g. a multi-tenant SaaS app) receives a legitimate webhook for their own shop from Shopify — a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` (the same secret is used for every shop that installs the app). The attacker replays that exact `raw_body`/`hmac` pair to the app's webhook endpoint but substitutes the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks `raw_body` against the HMAC secret, unrelated to the header), so `Registry.process` accepts the request and invokes the app's handler with `WebhookMetadata.shop` set to the victim's domain while the `body` is attacker-controlled content the attacker crafted for their own shop.

Because the shared HMAC secret is not shop-scoped, and the shop identifier used for downstream tenant routing/storage is never part of what's signed, this breaks the binding between "who signed the payload" and "which tenant the payload is attributed to."

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata.shop` (as returned from `Registry.process`) to select or scope tenant data — e.g., to look up/update the correct merchant's records, session, or settings — can be tricked into applying attacker-supplied webhook data under a different, victim shop's identity. This is a cross-tenant access/data-integrity issue: an attacker (a legitimate, unprivileged merchant of the same multi-tenant app) can inject data attributed to another merchant's tenant scope purely by replaying a validly-signed payload with a forged shop header, satisfying the "Critical – cross-tenant access" category.

### Likelihood Explanation
Likelihood is realistic in any real deployment: the attacker needs only to be a legitimate merchant of the target app (which is the normal, unprivileged position for any user of a multi-tenant Shopify app) and capture one legitimate webhook delivery to their own endpoint (trivially achievable by installing the app and configured webhook topics). No access to `api_secret_key`, access tokens, or victim credentials is required — the exploit relies entirely on the gem's own HMAC-vs-header identity mismatch.

### Recommendation
Include the shop domain (and ideally topic/api_version) as part of the signed material, or otherwise cryptographically bind the tenant identity to the payload before trusting it. Since Shopify's outgoing webhook HMAC scheme only signs the body, the gem should not treat the `shop` header as a trusted secondary identity claim; instead, apps should be required/guided to independently verify that the shop asserted in the webhook corresponds to a shop that is actually expected to receive that topic/body (e.g., cross-check against a known/installed-shop registry keyed by more than the header alone), and the gem's documentation/API should make this header's unauthenticated nature explicit rather than exposing it as `Request#shop`/`WebhookMetadata#shop` without qualification.

### Proof of Concept
1. App `MyApp` is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (attacker controls shop-a, victim owns shop-b), sharing one `api_secret_key`.
2. Shopify delivers a legitimate webhook to `MyApp`'s endpoint for `shop-a`: headers include `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body` JSON.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both flow through their own server, so they have full access to them).
4. Attacker (or a compromised/malicious client acting as attacker) resends a request to `MyApp`'s webhook endpoint with the same `raw_body` and same `x-shopify-hmac-sha256`, but with `x-shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — it succeeds since `raw_body`/`hmac` are unmodified: [6](#0-5) 
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "shop-b.myshopify.com"`, even though the payload actually originated from `shop-a`'s webhook stream, giving the attacker the ability to inject/attribute data into `shop-b`'s tenant context.
