Confirmed: the docs explicitly document `data.shop` as an identity field the app is expected to use ("The shop domain of the webhook"), and the sample handler uses it directly (`shop_domain: data.shop`). This is the last piece needed to establish that the gem's own documented contract treats `request.shop` as a trusted per-tenant identifier, even though the HMAC never covers it.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but only binds the raw HTTP body into the signed payload (`to_signable_string`). The `shop` (and `topic`/`api_version`/`webhook_id`) values are taken straight from unauthenticated HTTP headers and are never part of the HMAC-covered string, yet `Registry.process` treats `Utils::HmacValidator.validate(request)` as proof that the *entire* request, including which shop it belongs to, is authentic before dispatching `data.shop` to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or hmac: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `to_signable_string` (i.e., the body) and compares it against the `hmac` header value: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then forwards the unauthenticated `shop` header straight to the app's handler as the tenant identity: [4](#0-3) 

This breaks the identity binding: **shop authenticated by the HMAC ≠ shop delivered to the handler as the session/tenant key.** The HMAC only proves "this body was signed with `api_secret_key`" — it proves nothing about which shop the body is "for." An unprivileged internet user who legitimately controls any shop that has the app installed (e.g., a free/dev store they install the app on themselves) will receive real, validly-signed webhooks from Shopify for their own store's events. They can capture a `(raw_body, hmac)` pair from one of these deliveries, then POST it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim merchant's domain. Since `shop` is not part of `to_signable_string`, the HMAC still validates, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim shop.

### Impact Explanation
The gem's own documentation instructs app authors to key business logic off `data.shop` (e.g., `shop_domain: data.shop`) as the tenant identifier for the webhook payload: [5](#0-4) 
Because the header is unauthenticated, an attacker can inject a validly-"signed" (from the library's point of view) webhook body attributed to any victim shop domain, letting them impersonate another merchant's webhook stream — a cross-tenant data-integrity/confidentiality break in any app that trusts `data.shop` to route/store/act on webhook data, which is exactly what this library's documentation recommends. This matches the Critical "cross-tenant access" category since the attacker never needs the victim's credentials, only their own legitimately-installed shop to harvest a valid `(body, hmac)` pair.

### Likelihood Explanation
Likelihood is high for any attacker who can install the app on a shop they control (common for public/dev-store-testable apps) or who can otherwise observe one legitimate webhook delivery for any shop. No secret material, session, or token is required — only a replay of a previously observed valid `(body, hmac)` pair against the publicly reachable webhook endpoint with a forged shop header.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-covered payload check by validating them together, or require the caller to independently corroborate `request.shop` against known good sessions in `SessionStorage` — but the more direct fix within this gem is to make `to_signable_string`/validation cover, or `Registry.process` cross-check, the `shop` header the same way the OAuth `AuthQuery#to_signable_string` binds `shop` into its signed string, so the domain that receives `data.shop` is provably the same one Shopify actually signed for.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g., `orders/create`).
2. Capture the resulting POST: `raw_body` and the `x-shopify-hmac-sha256` header (a valid HMAC over `raw_body` using the app's real `api_secret_key`).
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `raw_body` against the hmac), `Registry.process` proceeds, and the app's handler receives `data.shop == "victim-shop.myshopify.com"` with attacker-controlled body content, impersonating the victim tenant.
