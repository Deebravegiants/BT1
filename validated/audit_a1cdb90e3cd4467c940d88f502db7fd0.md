### Title
Unallowlisted route contracts can execute attacker code under the caller's authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-supplied `swap` bytes and forwards them to the configured router without limiting which pool contracts the route may invoke [1](#0-0) . A malicious pool can use this nested execution context to request an unrelated token transfer from the strategy caller; if the victim signs the expanded authorization tree returned by simulation, the transfer succeeds and steals wallet funds unrelated to the lending position [2](#0-1) .

### Finding Description
Strategy entrypoints such as `swap_collateral(caller, account_id, current, amount, new, swap)` authorize the caller and verify control of `account_id`, but treat `swap` as opaque routing data [3](#0-2) . The controller authorizes only its exact input-token transfer to the configured router, then calls `execute_strategy(controller, amount_in, swap)` [4](#0-3) . The router decodes pool, token, and venue addresses from the caller-controlled address registry and dispatch stream rather than checking a governance-managed venue/pool allowlist [5](#0-4) . For example, the Soroswap adapter invokes the payload-selected `pool.swap` contract directly [6](#0-5) .

During simulation, a malicious pool's `token.transfer(victim, attacker, amount)` is recorded as a child invocation beneath the victim's `swap_collateral` authorization [7](#0-6) . Signing that simulated tree makes the unrelated transfer valid, while signing only the honest tree causes the rogue transfer to be rejected [8](#0-7) .

### Impact Explanation
The malicious route can drain any unrelated token balance for which the victim signs the extra child authorization, so the impact is theft of user funds rather than merely poor swap execution [9](#0-8) . The same caller-controlled route mechanism is reachable through `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` because all of them forward caller-supplied strategy bytes into `swap_tokens` or `swap_tokens_or_passthrough` [10](#0-9) [11](#0-10) [12](#0-11) .

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool and construct a valid-looking route without any protocol privilege [13](#0-12) . Exploitation does require the victim to use the attacker's route and sign the expanded authorization tree, so wallets that clearly display nested token transfers substantially reduce the practical success rate [14](#0-13) . The issue is nevertheless Medium because route bytes are intentionally opaque to users, and the protocol's measured-output and final-risk checks do not bound transfers from the caller's unrelated wallet assets [15](#0-14) .

### Recommendation
Governance should maintain an allowlist of approved venue pool contracts and the router should reject every hop whose pool or token address is not approved. Prefer explicit venue/pool identifiers over arbitrary registry addresses, and make route decoding surface every external contract before signature. Wallets and SDK route verification should also refuse any authorization tree containing child invocations beyond the expected controller input-token transfer.

### Proof of Concept
1. Deploy a contract exposing the selected venue ABI, such as Soroswap's `get_reserves` and `swap`, and configure it with `(victim, unrelated_token, attacker, victim_balance)` [16](#0-15) .
2. Construct a `swap_collateral` route whose `pool` registry entry points to that contract and whose normal `token_in`/`token_out` values produce a sufficient output to satisfy settlement [17](#0-16) .
3. Have the victim call `swap_collateral(caller=victim, account_id=victim_account, current=USDC_market, amount=50_000_000_000, new=ETH_market, swap=malicious_route)` [18](#0-17) .
4. During simulation, the malicious pool calls `unrelated_token.transfer(victim, attacker, victim_balance)`, and the host records that call as a child of the victim's `swap_collateral` authorization [19](#0-18) .
5. If the victim signs the simulated tree, the collateral swap can still deposit its measured output while the unrelated wallet token is transferred to the attacker [20](#0-19) .

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
