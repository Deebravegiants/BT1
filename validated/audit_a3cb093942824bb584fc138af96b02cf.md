### Title
Blacklisted-recipient permanent freeze in WrappedHyperFungibleToken's ERC20 refund/delivery paths (no alternate-beneficiary override) - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol, sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleToken.onAccept` and `onPostRequestTimeout` (and their `Upgradeable` twin) push the underlying ERC20 directly to a hardcoded address (`beneficiary`/`refundee`, both decoded from the cross-chain message with no override capability) via `IERC20(_underlying).safeTransfer(...)`. Because `underlying` is explicitly documented to support tokens like USDC (`configure(... underlying: USDC_ADDRESS ...)`), a blacklisted recipient/sender causes this transfer to revert unconditionally, with no parameter or fallback path to redirect funds to a different address — mirroring the `MainVault.withdrawAllowance` bug class where the missing `_receiver` param permanently locks a blocked user's funds.

### Finding Description
In the non-WETH branch of both `onAccept` and `onPostRequestTimeout`, funds move as: [1](#0-0) [2](#0-1) 

`beneficiary`/`refundee` are derived purely from message contents (`message.to` / `message.from`), with no parameter allowing the caller (relayer, `onlyHost`, or the original sender) to specify an alternate receiving address: [3](#0-2) [4](#0-3) 

Notably, for the WETH branch the code already recognizes this exact failure mode and defends against it — retrying with an ERC20 WETH transfer if the native push fails — explicitly to avoid "permanently lock[ing] funds": [5](#0-4) [6](#0-5) 

However, the plain-ERC20 (`isWeth = false`) branch has no equivalent fallback or override — it is a bare `safeTransfer` to a fixed address that reverts entirely if the underlying token's `transfer` reverts (as USDC/USDT do for blacklisted addresses). The docs confirm USDC is an intended `underlying` deployment target: [7](#0-6) 

The same pattern (identical logic) exists in the upgradeable variant: [8](#0-7) [9](#0-8) 

### Impact Explanation
- **`onAccept` (delivery path):** If the recipient (`message.to`) has been blacklisted by the underlying ERC20 (e.g. USDC/USDT compliance blocklist) *before* the cross-chain transfer is delivered, `onAccept` unconditionally reverts. Since `onAccept` is invoked by the host as part of message delivery and there is no override mechanism, the locked underlying tokens on the home chain remain custodied by the wrapper indefinitely, and the message can never be successfully delivered — a permanent freeze of the bridged funds and a route that is unable to deliver the message, matching the "route unable to deliver messages" acceptance criterion.
- **`onPostRequestTimeout` (refund path):** If the original sender becomes blacklisted between dispatch and timeout, the timeout refund also reverts unconditionally, permanently freezing the locked collateral with no recovery path — the exact bug class in the source report (missing recipient override on a withdrawal/refund function).

This is a concrete, permanent freezing-of-funds bug reachable by any ordinary user simply by calling `send()` on `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` when wrapping a blocklist-capable ERC20 (USDC/USDT), which the documentation explicitly supports as a target underlying.

### Likelihood Explanation
Moderate likelihood: it requires the source or destination-side account to be blacklisted by the underlying token issuer (USDC/USDT) at some point between locking and delivery/timeout. This is not attacker-controlled in the sense of an exploit, but it is a realistic real-world event (regulatory/compliance blocklisting), and once triggered there is no operator-controlled remedy in these contracts — no admin sweep, no alternate beneficiary parameter, no retry-with-different-recipient path (unlike the WETH branch, which anticipated exactly this class of failure).

### Recommendation
Add a fallback/override path for the plain-ERC20 branches analogous to the WETH branch's retry logic: e.g., on failed `safeTransfer` (checked via low-level call and return-value inspection rather than the reverting `SafeERC20` wrapper), route funds to an escrow/claimable mapping keyed by the intended beneficiary, allowing that beneficiary (or an owner-controlled sweep) to later specify an alternate address to claim the funds. This preserves the accounting invariant while avoiding a permanent freeze when the underlying token blocklists a specific address.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` with `underlying = USDC`, `isWeth = false`.
2. Alice calls `send({dest: Arbitrum, to: Bob, amount: 1000 USDC, ...})`; USDC is locked in the wrapper on the home chain.
3. Before the message is delivered on Arbitrum-side wrapper's `onAccept`, Circle blacklists Bob's address on USDC.
4. When the relayer delivers the message, `onAccept` calls `IERC20(_underlying).safeTransfer(beneficiary=Bob, amount)`, which reverts because Bob is blacklisted (`USDC.transfer` reverts for blacklisted recipients). The message can never be delivered; Bob's 1000 USDC remains permanently locked in the source-chain wrapper with no recovery mechanism.
5. Alternatively, if Alice (the sender) gets blacklisted before the message times out, `onPostRequestTimeout`'s `IERC20(_underlying).safeTransfer(refundee=Alice, amount)` reverts identically, permanently freezing the funds on timeout as well.
