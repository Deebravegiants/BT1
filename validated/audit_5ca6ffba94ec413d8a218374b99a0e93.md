### Title
Emporium Min-proof path lets an unprivileged self-relayed caller run arbitrary `EmporiumStack.ops` with zero balance accounting, draining Emporium's custodied token balances - ([File: contracts/CircomDataBuilder.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `emporiumMessage`, `timeStamp`, and `calldataHash` — nothing about token movement. Because `EmporiumUpgradeable.runAction` executes `stack.ops[]` completely independently of `circomData.erc20TokenAddresses`, an attacker can submit an empty token array (forcing the unaccounted Min path) while still supplying arbitrary `ops` that call any ERC20/endpoint from Emporium's own address, moving Emporium's real custodied balances with no balance check ever executing.

### Finding Description
The broken equality is: **assets Emporium can move in a tx == assets accounted in `balancesBefore`/`balancesAfter`**.

- `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
`formInputEmporiumMin` only constrains `emporiumMessage`, `timeStamp`, `calldataHash` as public signals — no `amountChanges`, no nullifiers, no root, no output commitments: [2](#0-1) 

- `EmporiumUpgradeable.runAction` decodes an attacker-controlled `EmporiumStack` from `externalActionData.externalActionMetadata` and executes every `stack.ops[i]` via `op.endpoint.call{value: op.value}(op.callData)` when `stack.signerAddress == address(0)`, with **no relation to `circomData.erc20TokenAddresses`**: [3](#0-2) 
`verifyWallet` performs no signature check at all when `stack.signerAddress == address(0)` — it just marks the message used and returns: [4](#0-3) 

- The only accounting/guard (`balanceChangeShouldBePositive`) iterates strictly over `circomData.erc20TokenAddresses`, which the attacker forced to length 0 to obtain the Min proof path — so it never executes: [5](#0-4) 

- Likewise, `Hinkal.transact`'s outer balance-diff/slippage enforcement loop also iterates over `circomData.erc20TokenAddresses` and is a no-op for length 0: [6](#0-5) 

- `performHinkalChecks`/`dimensionsCheck` only verify internal array-length consistency relative to `dimensions.tokenNumber` (which the attacker also sets to 0) and that `calldataHash` matches the supplied `circomData` — neither constrains what `ops.endpoint`/`ops.callData` do: [7](#0-6) [8](#0-7) 

**Root cause**: the `ops` execution loop in `EmporiumUpgradeable.runAction` is entirely decoupled from the `erc20TokenAddresses`/`balancesBefore`/`balancesAfter` accounting arrays. Any token the attacker's `ops` touch that is *not* in `circomData.erc20TokenAddresses` is never checked — and forcing that array to length 0 (required to obtain the cheap/near-empty Min proof, per `formInputForCircom`) makes the check a universal no-op for *every* token.

**Attacker's exact call**: Self-relay a `Hinkal.transact` (`circomData.originalSender == msg.sender`, `circomData.relay == address(0)`) with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [ { endpoint: <victimToken>, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, hugeAmount) } ] }`. Supply a proof against the registered Min verifier for `(tokenNumber=0, nullifierAmount=0, outputAmount=0, HINKAL_EMPORIUM_ACTION_ID)` proving only `emporiumMessage == Poseidon(messageSeed)`.

**Exploit flow**: `Hinkal.transact` → `performHinkalChecks` (passes trivially, dimensions=0) → `verifyProof` (passes with the Min verifier) → `_externalTransact` → `EmporiumUpgradeable.runAction` → loop over `stack.ops` executes `victimToken.transfer(attacker, hugeAmount)` as Emporium (msg.sender = Emporium contract) → since `victimToken` is not in `circomData.erc20TokenAddresses` (which is empty), neither `balanceChangeShouldBePositive` nor `Hinkal.transact`'s balance-diff/slippage require ever inspects it → transaction succeeds, funds leave Emporium's custody to the attacker.

**Why existing guards fail**: `onlyAllowedRecipient` only checks `msg.sender == Hinkal`, which is true by construction. `verifyWallet` is a no-op for `signerAddress == address(0)`. `checkOnchainCreation`/`dimensionsCheck` only validate internal array-length parity, not semantic token safety. The balance-accounting invariant that is supposed to bound what an external action can move is scoped to `circomData.erc20TokenAddresses`, an attacker-chosen array that can legitimately be empty precisely because that's the condition selecting the cheap Min proof.

### Impact Explanation
Direct theft of shielded/parked user funds custodied in the `EmporiumUpgradeable` contract's own token balances, for any ERC20 the contract holds on behalf of any user, in one transaction, with no signature or balance check firing. This satisfies **Critical: direct theft of shielded or in-flight user funds** — the attacker gains the entire drainable balance of any token Emporium holds, and the exploit is repeatable across tokens and across transactions (bounded only by a fresh `emporiumMessage` per call since `usedMessages` is keyed per message, not globally).

### Likelihood Explanation
Preconditions are entirely attacker-controlled: any EOA can self-relay (no relay involvement needed), craft `circomData` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, and a malicious `EmporiumStack` with `signerAddress = address(0)`. The only external precondition is that Emporium must actually hold token balances (which occurs naturally as normal users park funds via legitimate Emporium flows) and that the owner has registered a verifier for the `(0,0,0,HINKAL_EMPORIUM_ACTION_ID)` verifier-id — a configuration directly implied by the existence of `formInputEmporiumMin` in the codebase as a supported, intentional code path. Cost is a single proof generation for a near-trivial circuit (3 public signals) plus normal gas. Highly feasible and fully repeatable.

### Recommendation
Decouple the safety of `EmporiumStack.ops` execution from the attacker-chosen `erc20TokenAddresses` array: either (a) require `EmporiumUpgradeable.runAction` to snapshot/verify balances for every token actually touched by `op.endpoint`/`op.callData` (not just the declared array), (b) disallow the Min proof path whenever `stack.ops` is non-empty or targets token-moving selectors, or (c) require a valid EIP-712 signature (non-zero `signerAddress`) for every op execution regardless of `erc20TokenAddresses.length`, removing the unauthenticated `signerAddress == address(0)` bypass for stateless calls that can move arbitrary tokens.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (with `Hinkal` set as allowed recipient), register a mock verifier under `buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)` that always returns `true` (simulating a legitimately-generated Min proof).
2. Fund `EmporiumUpgradeable` with `victimToken.mint(emporium, 1000e18)` to represent another user's parked balance.
3. As attacker EOA, call `Hinkal.transact` with `circomData.erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: victimToken, invokeWallet: false, value: 0, callData: transfer(attacker, 1000e18)}]}`.
4. Assert: `victimToken.balanceOf(attacker) == 1000e18` after the call, and `victimToken.balanceOf(emporium) == 0`.
5. Assert on both sides of the claimed invariant: `balancesBefore[victimToken]`/`balancesAfter[victimToken]` are never computed (array length 0), i.e., the `BalanceChangeShouldBePositive` guard in `EmporiumUpgradeable.runAction` and the slippage/balance-diff require in `Hinkal.transact` never execute for `victimToken`, proving the accounting equality is violated.

            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
