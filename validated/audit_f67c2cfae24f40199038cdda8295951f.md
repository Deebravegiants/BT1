### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches the handler with a `shop` field that is read straight from the `X-Shopify-Shop-Domain` header — a value that was never part of the signed material. This breaks the intended identity binding `hmac_covers(shop) == true`; in reality `hmac_covers(shop) == false`. Any party holding one validly-signed `(raw_body, hmac)` pair (trivially obtainable by installing the app on any myshopify dev/trial store they control, or from any webhook they legitimately receive) can resubmit that exact body+hmac to the app's webhook endpoint while swapping the `shop-domain` header, and the gem will report the request as authentic and hand the attacker-chosen `shop` value to the app's business logic.

### Finding Description
The webhook verification path is:

1. `ShopifyAPI::Webhooks::Request` parses headers, including `shop` from `shopify-shop-domain`/`x-shopify-shop-domain`, and exposes `to_signable_string` as just `@raw_body`: [4](#0-3) 
2. `Registry.process` calls `Utils::HmacValidator.validate(request)` — the only authenticity check — and, if it passes, immediately builds `WebhookMetadata` using `request.shop` and dispatches to the registered handler: [2](#0-1) 
3. `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it against the received `hmac`: [5](#0-4) 
4. `WebhookMetadata.shop` is a plain `String` field populated from the unauthenticated header value and passed to the app's handler as the trusted tenant identifier: [3](#0-2) 

Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, and the signature is computed only over `raw_body`, an attacker who has one legitimately-signed webhook (e.g., from a shop they themselves installed the app on, or a webhook payload they otherwise observed) can replay that identical `raw_body`/`hmac` pair to the app's webhook endpoint with an arbitrary `shop-domain` header value. `HmacValidator.validate` will report success because it never inspects the header, and `Registry.process` will dispatch to the app handler with `data.shop` set to the attacker-controlled domain.

The gem's own documentation instructs integrators to key downstream business logic (e.g., job enqueueing, per-tenant data association) directly off `data.shop`: [6](#0-5) , so this untrusted binding is the exact value applications are told to trust for tenant attribution.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged user who can get any single webhook accepted for one shop (including their own) can cause the host application to process and attribute that webhook's body to a shop of their choosing. Depending on the handler's logic, this can lead to data being written to, or actions taken against, another merchant's tenant context — satisfying the "cross-tenant access" criterion for Critical impact, since the identity binding (`shop` field) that gates per-tenant handling is not authenticated by the HMAC that is supposed to prove the request is genuine.

### Likelihood Explanation
Reaching this requires only: (1) the ability to send arbitrary HTTP requests to the app's public webhook endpoint (any internet user), and (2) possession of one valid `(raw_body, hmac)` pair for the app, which is trivially obtained by installing the target app on a store the attacker controls (a normal, permission-free action for anyone using Shopify's free developer/trial stores) and capturing the webhook Shopify sends. No access token, `client_secret`, or privileged account is needed — only observation of one webhook delivery.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material that `HmacValidator` verifies, or otherwise require the host application to independently confirm that the `shop` in the payload matches a webhook subscription/shop pairing it registered and expects, rather than trusting the raw header. At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must not be used as a sole tenant-selection key without additional verification (e.g., cross-checking against `webhook_id` recorded at registration time, or verifying the shop is one for which the app has an active, registered subscription).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any free/dev store) and lets it receive one legitimate webhook, e.g. `orders/create`, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header — both computed correctly since the app's real `api_secret_key` signed them.
2. Attacker replays the identical `raw_body` and `hmac` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` as `"victim-shop.myshopify.com"` [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and it matches (since the body/hmac pair is untouched) [8](#0-7) .
5. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)`, and the host app processes/stores this as if it were genuine data belonging to `victim-shop`.
