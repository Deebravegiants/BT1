### Title
`current_session_id`'s embedded cookie-fallback trusts an unauthenticated client-supplied cookie value as a session identifier - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`SessionUtils.current_session_id` and `cookie_session_id` return the raw value of the `shopify_app_session` cookie as the session id with no HMAC, signature, or JWT check inside this gem, in both the non-embedded branch and the embedded fallback branch when no `shopify_id_token` is supplied. Because offline session ids are deterministically derived as `"offline_#{shop}"` from a public, guessable shop domain, this value is fully attacker-predictable, not merely attacker-observed.

### Finding Description
The claimed binding is: `current_session_id(nil, cookies, false) == cookies["shopify_app_session"]` with no cryptographic check that this value actually originated from this gem's own OAuth flow for the requesting browser.

Tracing the code: `current_session_id` checks `Context.embedded?`; if embedded and `shopify_id_token` is absent, it falls straight to `cookie_session_id(cookies)` [1](#0-0) , which simply does `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` [2](#0-1) . The non-embedded branch behaves identically [3](#0-2) . There is no HMAC, JWT `aud`/`dest`/`iss` check, or any other authentication of the cookie value performed by this gem in this method; the only alternate, authenticated path (`session_id_from_shopify_id_token`, backed by `Auth::JwtPayload`) is used exclusively when `shopify_id_token` is present [4](#0-3) . The offline session id format itself is `"offline_#{shop}"` [5](#0-4) , which is entirely derivable from a public, discoverable shop domain — no secret or randomness is involved.

The test suite confirms this: `test_non_embedded_app_current_session_id_returns_id_from_cookie` and `test_embedded_app_current_session_id_returns_id_from_auth_header_even_with_cookies` show the cookie value being passed straight through as the returned id with no validation [6](#0-5) .

However, the gem's own `SessionCookie` value is not a raw identifier the gem asks the host to store insecurely by itself — the documented flow explicitly instructs the host app to set this cookie as `secure: true, http_only: true` when writing it to the browser during `begin_auth`/`validate_auth_callback` [7](#0-6) [8](#0-7) . The gem's docs also explicitly state that cookie-based session retrieval is intended **only for non-embedded apps** — "Cookie based authentication is not supported for embedded apps... Non-embedded apps are able to use cookies for session storage/retrieval" [9](#0-8) . Whether an attacker can actually forge this cookie value on the wire depends entirely on how the host application reads and validates the incoming `Cookie` header before passing it into `current_session_id` — this gem receives a plain `T::Hash[String, String]` of "cookies" from the caller [10](#0-9) , and nothing in this repository controls how that hash is constructed by the host framework (e.g., Rails' cookie jar, which by default reads raw `Cookie:` header values as plain strings unless the host explicitly uses `cookies.signed`/`cookies.encrypted`).

This is the crux of the issue for this audit's scope ("the bug must be in this gem's code"): this gem's own contract for the cookie fallback path provides zero integrity guarantee over the value it returns as a "session id," and nowhere in its documentation or code does it instruct the host to use a signed/encrypted cookie jar rather than a plain string. Given that offline session ids are deterministic and predictable, and the API accepts a bare `Hash[String,String]`, if a host app follows the documented, simplistic cookie-passing pattern literally (`cookies.to_h` as shown in the OAuth doc example [11](#0-10) ) without independently adding signed/encrypted cookie protection, the returned session id is exactly the attacker-supplied header value.

### Impact Explanation
If a host app trusts the id returned by `current_session_id`/`cookie_session_id` to directly key its session storage lookup — which is exactly the documented usage pattern this gem provides for non-embedded and cookie-fallback embedded cases — an attacker who can set an arbitrary `Cookie` header on their own HTTP request to the host app (trivial; no browser same-origin restriction applies to a raw HTTP client) can present `shopify_app_session=offline_<victim-shop>.myshopify.com` and obtain the host's lookup of the victim's stored offline session, including its access token, without ever holding any secret. Because the id format is deterministic (`"offline_#{shop}"`), this is systematically repeatable against arbitrary victim shops merely by knowing their `myshopify.com` domain, which is public. This matches the Critical category: cross-tenant access / authentication bypass.

### Likelihood Explanation
Exploitability is conditioned entirely on host-app behavior that is external to this gem: whether the host passes a raw, unsigned cookie header value into `current_session_id` (as its own minimal doc example does via `cookies.to_h`) rather than using a framework's signed/encrypted cookie jar, and whether the host treats the returned id as sufficient proof of authentication without a supplementary check (e.g., re-validating a JWT for embedded requests, as recommended). This gem does not enforce or even recommend cookie signing for this specific value in its own code or method contract, and the embedded-fallback branch actively re-enables the cookie path that the docs elsewhere say is unsupported for embedded apps. Attacker cost is minimal: guess/know a shop domain, send one crafted request.

### Recommendation
`SessionUtils.cookie_session_id` should not be trusted as a bare, unauthenticated identifier for lookups without an explicit warning/enforcement in the method's contract that the cookie value must come from a cryptographically signed/encrypted cookie jar (or the method itself should require/verify some integrity token bound to the value, e.g., signing the returned id with `api_secret_key` at cookie-set time in `SessionCookie`/`Oauth.begin_auth`/`validate_auth_callback` and verifying that signature inside `cookie_session_id`). At minimum, the embedded-app fallback branch that silently accepts a plain cookie value should be removed or gated behind an explicit signature check, since the docs already state cookie auth is unsupported for embedded apps.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (additional test)
def test_embedded_fallback_trusts_forged_offline_cookie_unauthenticated
  ShopifyAPI::Context.stubs(:embedded?).returns(true)
  forged_shop = "victim-shop.myshopify.com"
  forged_cookie_value = "offline_#{forged_shop}"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  # No shopify_id_token supplied; attacker only controls the Cookie header.
  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # Binding under test: returned_id == attacker-forged cookie value, unauthenticated
  assert_equal(forged_cookie_value, returned_id)
  # No HMAC/JWT verification call occurred anywhere in this path — confirmed by
  # the absence of any Auth::JwtPayload/HmacValidator stub/expectation required
  # for this assertion to pass.
end
```
This demonstrates that `current_session_id` returns the exact attacker-supplied string with no cryptographic validation, matching `SessionUtils#cookie_session_id` at [2](#0-1) .

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end

        def session_id_from_shopify_id_token(id_token:, online:)
          raise Errors::MissingJwtTokenError, "Missing Shopify ID Token" if id_token.nil? || id_token.empty?

          payload = Auth::JwtPayload.new(id_token)
          shop = payload.shop

          if online
            jwt_session_id(shop, T.must(payload.sub))
          else
            offline_session_id(shop)
          end
        end

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
