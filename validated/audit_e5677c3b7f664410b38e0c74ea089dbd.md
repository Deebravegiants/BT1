### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop` (tenant) identifier used by webhook handlers is read from an HTTP header that is never included in the signed material. This breaks the identity binding `hmac == HMAC(secret, signed_bytes)` where `signed_bytes` should determine `shop`, but instead `shop` is taken from unauthenticated bytes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over whatever `to_signable_string` returns and comparing it to the `hmac` value on that object [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `x-shopify-hmac-sha256` header [2](#0-1) . Meanwhile `Request#shop` is derived purely from the `x-shopify-shop-domain` header, which is not part of `to_signable_string` at all [3](#0-2) .

`Registry.process` validates the HMAC and then dispatches to the registered handler, passing `request.shop` straight through as the tenant identifier in `WebhookMetadata`, without any additional check that this header matches the body or any other authenticated value [4](#0-3) .

Root cause equality that should hold but does not:
`shop_used_by_handler == shop_bound_by_hmac(signed_bytes)`

Here `signed_bytes = raw_body` only, so `shop` is fully attacker-controllable independent of the signature as long as the attacker can produce *any* valid `(raw_body, hmac)` pair signed with the app's secret for their own shop. Since the app installs on many merchant shops, an attacker who owns/controls their own installed shop can trivially obtain a valid `(body, hmac)` pair (Shopify signs and delivers real webhooks to their shop), then replay that exact body+hmac to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. The signature still validates because the header is not covered.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (i.e., `request.shop`) to scope tenant data — e.g., to decide which merchant's local records to update/delete for topics like `orders/updated`, `app/uninstalled`, `shop/redact`, `customers/redact` — can be tricked into applying attacker-supplied webhook bodies against a victim tenant. This is a cross-tenant data integrity/confidentiality issue reachable by any unprivileged party that can install the app on their own shop (a normal, unprivileged action), satisfying the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Likelihood is high for apps that trust `WebhookMetadata#shop` for tenant scoping (a very common and, per the gem's own docs/tests, expected usage pattern — see `test/webhooks/registry_test.rb` where `data.shop` is asserted directly from the request) [5](#0-4) . The attacker only needs: (1) their own legitimate app installation/shop to receive a real, validly-signed webhook, and (2) ability to POST to the app's public webhook endpoint with a modified `shop-domain` header — both are unprivileged actions requiring no secrets.

### Recommendation
Bind the tenant identity to the signed payload instead of trusting an unauthenticated header:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) inside `to_signable_string`'s signed bytes, or
- Have the host application independently verify `request.shop` against a shop known to be associated with the specific `webhook-id`/subscription before acting on the payload, and document this requirement prominently.

Concretely, update `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop-domain header (matching what Shopify's true trust boundary requires), or add an explicit warning in `WebhookMetadata`/docs that `shop` is not authenticated by the HMAC and must be corroborated by the caller.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimately signed webhook, e.g. topic `customers/data_request` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC over `B` with the app's `client_secret`).
2. Attacker replays the exact same request to the app's webhook endpoint, but rewrites the header:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: H          (unchanged, still valid for body B)
   x-shopify-shop-domain: victim-shop.myshopify.com   (forged)
   body: B                           (unchanged)
   ```
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unmodified [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and performs tenant-scoped actions (e.g., a data-erasure/redaction workflow) against `victim-shop`, even though `victim-shop` never sent or authorized this webhook.
