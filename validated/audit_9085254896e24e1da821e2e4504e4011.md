Confirmed: `WebhookMetadata.shop` is populated directly from the unauthenticated header value, and `Registry.process` only checks HMAC over the body before passing this metadata to the app's handler.### Title
Webhook `shop` identity is trusted from an unauthenticated header and is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller's `shop-domain` header straight through to the app's handler as the trusted tenant identifier. The `shop` field is never included in the HMAC-signed payload, so it is not bound to the signature that "proves" the request's authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are excluded from the signed string: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body only), and then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further verification, and the gem's own documentation instructs consuming apps to treat `data.shop` as the authoritative shop/tenant identifier for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) [5](#0-4) 

**The broken identity binding, as an equality:**
`shop-domain header value` (unauthenticated, attacker-controlled) ≠ `shop bound by the HMAC signature` (nothing — the signature only covers `raw_body`).

**Before the attack:** a legitimate Shopify webhook is delivered with `x-shopify-shop-domain: shop-A.myshopify.com`, a JSON body, and `hmac = HMAC-SHA256(client_secret, body)`. Validation succeeds because the body and HMAC match.

**Attacker's request sequence:** any unprivileged internet user who runs their own Shopify store can install the target app on that store (a normal, unprivileged action any developer/attacker can perform for free on a dev/trial store) and thereby receive a genuine webhook with a valid HMAC for `shop-A.myshopify.com` and an arbitrary body of their choosing. The attacker then replays the exact same body and HMAC to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: shop-B.myshopify.com` (a victim's shop). Because the signable string is body-only, `HmacValidator.validate` still returns `true` — the signature never covered the shop header.

**After the attack:** `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop == "shop-B.myshopify.com"`, `body` fully attacker-controlled, and the app has no way (from the gem's guarantees) to detect that this "shop-B" identity is forged. Any host application that follows the gem's documented pattern of trusting `data.shop` as the tenant key (which the gem explicitly recommends) will process or persist attacker-controlled data under the wrong shop's tenant scope — a cross-tenant data injection/corruption primitive.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem exists to enforce: the gem's only authentication mechanism (HMAC) does not bind the routing/tenant identifier (`shop`) it is meant to protect. Any app that follows the gem's own documented usage pattern is exposed to cross-tenant webhook injection — an attacker with only their own (attacker-owned) store can forge webhook events attributed to any other shop the app serves, with attacker-chosen JSON body content. This matches the Critical "cross-tenant access" impact category, since it defeats the tenant-isolation guarantee the signature is supposed to provide.

### Likelihood Explanation
High. No privileged credentials, leaked secrets, or social engineering are required — an attacker only needs their own (freely obtainable) Shopify store with the target app installed to harvest a validly-signed webhook body/HMAC pair, then modify one HTTP header on replay. The vulnerable code path (`Request#to_signable_string`, `Registry.process`) is the gem's documented, primary webhook-processing entry point, so it is reached on every installation that uses this feature as intended.

### Recommendation
Bind the identity fields used for routing/tenant resolution to the same cryptographic proof used for body integrity:
- Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the HMAC-signed payload used by `to_signable_string`, matching them against a canonical, out-of-band-known value (e.g., the shop stored for the corresponding `webhook_id`/subscription) rather than trusting the header verbatim.
- Alternatively/additionally, require host applications to cross-check `WebhookMetadata#shop` against the shop associated with the specific `webhook_id` in their own subscription records before processing, and document this requirement prominently since the current docs imply `data.shop` is already trustworthy.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there,
# so they legitimately receive a Shopify webhook with a valid HMAC for this body:
raw_body = '{"id":123,"note":"legit order from attacker-owned shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)

# Attacker replays it to the same endpoint, only changing the shop-domain header:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(valid_hmac),   # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",   # forged tenant
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation only checks raw_body, so this succeeds even though shop is forged:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily dispatches with the forged tenant identity:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
