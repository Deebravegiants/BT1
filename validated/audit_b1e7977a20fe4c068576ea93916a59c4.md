### Title
Empty `erc20TokenAddresses` (Emporium-Min path) lets an attacker exfiltrate any token balance held by `EmporiumUpgradeable` via unchecked `stack.ops` calls - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose corresponding circuit (`MainEVMCircuitMin`) only constrains `message == Poseidon(messageSeed)` and carries no UTXO/root/nullifier semantics at all. `EmporiumUpgradeable.runAction`'s balance-conservation loops (`balancesBefore`/`balancesAfter`, `payRelayFees`) iterate over `circomData.erc20TokenAddresses`, so with a zero-length array these loops are complete no-ops, while `stack.ops` (decoded from `externalActionData.externalActionMetadata`) is executed unconditionally and can call arbitrary `endpoint.call(callData)` from the Emporium contract's own context. When `stack.signerAddress == address(0)`, `verifyWallet` performs no signature check whatsoever on the ops. This lets any unprivileged caller sweep out any ERC20/ETH balance sitting in the Emporium contract without any accounting.

### Finding Description
The claimed conserved equality is: `tokens leaving Emporium during runAction == Σ over erc20TokenAddresses of (balancesAfter[i] - balancesBefore[i] adjusted by deltaAmountChanges[i])`.

Trace:
- `CircomDataBuilder.formInputForCircom` (contracts/CircomDataBuilder.sol:139-144) chooses `formInputEmporiumMin` whenever `erc20TokenAddresses.length == 0`, producing a public input vector of only `[emporiumMessage, timeStamp, calldataHash]` (contracts/CircomDataBuilder.sol:150-161).
- The matching circuit, `MainEVMCircuitMin` (circuits/MainEVMCircuitMin.circom:1-18), only constrains `message === Poseidon(messageSeed)`. It contains **no** UTXO root check, no nullifier constraint, no `inTotal+amountChanges===outTotal` value-conservation constraint. Any caller can pick an arbitrary `messageSeed`, compute the resulting `message`, and use it as `emporiumMessage` — no ownership of a UTXO, deposit, or prior state is required to produce a valid proof for this branch.
- `HinkalHelper.dimensionsCheck` (contracts/HinkalHelper.sol:64-90) only requires `erc20TokenAddresses.length == dimensions.tokenNumber`; the attacker freely sets `dimensions.tokenNumber = 0` to satisfy it. Nothing forces `erc20TokenAddresses` to be non-empty for the Emporium action id.
- `Hinkal._externalTransact` (contracts/Hinkal.sol:234-261) builds `deltaAmountChanges` over `circomData.erc20TokenAddresses` (length 0 here), so it is an empty array, and calls `EmporiumUpgradeable.runAction`.
- Inside `runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160):
  - `balancesBefore = getBalancesForArray(circomData.erc20TokenAddresses)` → empty array.
  - `verifyWallet(stack, circomData)` (lines 302-349): if `stack.signerAddress == address(0)`, it only marks `emporiumMessage` used and **returns immediately with no signature verification** (line 314-316).
  - The `stack.ops` loop (lines 91-118) executes every operation unconditionally. For the "Stateless Interaction" branch (line 102-113), it performs `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, blocking only the `callHinkalWallet`/`doSendToRelay` selectors — nothing stops a call such as `IERC20(anyToken).transfer(attacker, balance)`.
  - `balancesAfter` and the entire balance-conservation loop at lines 122-157 iterate over `circomData.erc20TokenAddresses` (still empty), so they never run — no `balanceChange` is computed, `BalanceChangeShouldBePositive` never fires, and `utxoSet` is returned empty.
  - `payRelayFees` (lines 201-260) likewise loops over the empty `erc20TokenAddresses` and does nothing (its post-loop "not found" fallback only triggers if `feeStructure.flatFee != 0`, which the attacker can simply set to 0).

Root cause: the balance-accounting mechanism in `runAction` is scoped exclusively to the caller-declared `erc20TokenAddresses` list, but `stack.ops` execution is unscoped and can touch any token held by the contract. Combining an empty `erc20TokenAddresses` (which is a legitimate, circuit-supported branch for signer-authorized wallet actions) with unsigned (`signerAddress == 0`) stateless ops removes both guards simultaneously: no ZK constraint on value movement (Min circuit) and no balance-diff check in Solidity (empty loop) and no EIP-712 signature gate (`signerAddress == 0`).

Attacker's exact call: call `Hinkal.transact` (or the external-transact entrypoint) with `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [ {endpoint: <victimToken>, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, balanceHeldByEmporium))} ] }`, and a trivially self-generated Min-circuit proof (`messageSeed` chosen freely, `message` set as `emporiumMessage`). `runAction` executes the transfer and returns an empty `utxoSet`; no revert occurs anywhere in the call path.

### Impact Explanation
Any ERC20/ETH balance sitting in `EmporiumUpgradeable` (e.g., stranded swap-output dust from other users whose declared `erc20TokenAddresses` didn't cover a token produced by their own `stack.ops`, leftover fee remainders, or any token accidentally/temporarily held by the contract) can be drained by an unrelated attacker with a nearly proof-free call. This is direct theft of protocol/other-user funds held in-flight by the Emporium contract, satisfying Critical ("direct theft of shielded or in-flight user funds") since it requires no privileged role and no interaction from the victim. It is repeatable for every token/every residual balance that accumulates in the contract over time.

### Likelihood Explanation
- No privileged role needed; the attacker only needs to be able to call `Hinkal.transact`/`externalTransact` as any EOA and generate a trivial proof for the `MainEVMCircuitMin` circuit (self-chosen `messageSeed`), which requires no funds, no UTXO, and no interaction with existing state.
- Preconditions: the Emporium contract must be holding a non-zero balance of some token not scoped by the attacker's own `erc20TokenAddresses` (this can arise from normal usage — e.g., swap slippage/output dust, users mistakenly omitting a token from `erc20TokenAddresses`, or fee remainders) — an inherent occurrence given the design that only declared tokens are swept back to `msg.sender` in `handleOut`.
- Attacker cost is minimal: one transaction, one proof generation, no capital required.
- Fully repeatable against any stray balance that ever accumulates.

### Recommendation
Do not allow `stack.ops` to be executed with zero declared `erc20TokenAddresses` unless `stack.signerAddress != address(0)` and a valid signature is present (i.e., disallow the `signerAddress == address(0)` no-signature bypass entirely, or require `erc20TokenAddresses.length > 0` whenever unsigned stateless ops are present). Additionally, track and assert the full balance-diff for every token actually touched by `stack.ops` (not just the caller-declared list), e.g., by requiring the ops to only touch tokens present in `erc20TokenAddresses`, or by snapshotting/asserting no unaccounted-for token balance decrease occurs across the whole call.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (proxy), a mock ERC20 `VictimToken`, and fund `EmporiumUpgradeable` directly with `VictimToken` (simulating stranded dust from a prior legitimate user action, e.g. by minting tokens directly to the Emporium address).
2. As `attacker` (an unrelated EOA with no deposits), construct `CircomData` with:
   - `erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []`, `onChainCreation = []`, `inputNullifiers = []`, `outCommitments = []` (all matching `dimensions.tokenNumber = 0`).
   - `externalActionData = { externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: VictimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, drainAmount))}], maxFee: 0, deadline: block.timestamp+1})}`.
   - `emporiumMessage` and `calldataHash` computed locally to match `CircomDataBuilder.getHashedCalldata`/`getSignedMessageHash` formulas, with a real Min-circuit proof for arbitrary `messageSeed`.
3. Record `VictimToken.balanceOf(EmporiumUpgradeable)` and `VictimToken.balanceOf(attacker)` before and after calling `Hinkal.transact(...)`.
4. Assert: the call does **not** revert, `runAction` returns an empty `utxoSet`, `VictimToken.balanceOf(attacker)` increased by `drainAmount`, and `VictimToken.balanceOf(EmporiumUpgradeable)` decreased by `drainAmount` — demonstrating that real value left the contract while the value-conservation equality (`0 == 0` over the empty `erc20TokenAddresses` array) was trivially and vacuously satisfied.
