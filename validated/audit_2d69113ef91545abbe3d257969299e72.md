### Title
Deposit function can mint zero shares while charging full underlying amount, permanently freezing user principal - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent per-asset vaults)

### Summary
Across the Zest v2 tokenized vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`), the `deposit` function computes `shares = amount * totalSupply / totalAssets` via `convert-to-shares-preview`, transfers the full `amount` of underlying from the user, then mints the computed share amount. Unlike `redeem`, which explicitly guards `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, `deposit` has no equivalent guard for the minted-share side; only `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` is checked, which a user can satisfy trivially with `min-out = 0`. This mirrors the Sherlock report's root cause: integer division of a proportional identity that can round to zero, but instead of causing a revert, it causes silent loss of principal.

### Finding Description
`convert-to-shares-preview` in each vault performs:
```
(mul-div-down amount ts ta)
``` [1](#0-0) 

and `deposit` uses this value directly as the number of shares to mint, gated only by a slippage check the depositor themselves supplies:
```
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
``` [2](#0-1) 

`total-assets-preview` includes accrued, undistributed interest (`debt-preview` minus `total-borrowed`), so the effective share price (`total-assets / total-supply`) can grow well above 1 over time as interest compounds:
```
(define-private (total-assets-preview)
  (let ((current-assets (var-get assets))
        (debt (debt-preview))
        (borrowed (var-get total-borrowed))
        (interest (if (> debt borrowed) (- debt borrowed) u0)))
    (+ current-assets interest)))
``` [3](#0-2) 

If the share price is high enough (e.g., after a long period of interest accrual, or for a low-decimal underlying), a small deposit amount will make `mul-div-down amount ts ta` round down to `0`. The identity that should be preserved is:
```
assetsHeldByUser_after == assetsHeldByUser_before  (if shares minted == 0)
```
but instead:
```
assets (var-get assets) increases by amount   (full underlying transferred in)
inkind (shares minted to depositor) == 0
```
This breaks the "share minting versus backing" invariant analogous to the referenced report's `owed = totalTokenOut * depositAmount / totalTokenDeposited` rounding to zero — except here the transfer that should have been skipped (the zero-value side) is the *inbound* one that still executes, while the *shares* side that should represent the user's claim is silently zero. The depositor's principal becomes value transferred into the vault with no corresponding claim: it is absorbed proportionally by all other existing shareholders (since `total-assets` grows while `total-supply` doesn't), effectively minting value out of the depositor's principal for other users.

There is no `MINIMUM-LIQUIDITY`-style protection actually applied on the deposit-shares path (it is referenced elsewhere in initialization, not in per-call `deposit`), and no `ERR-OUTPUT-ZERO`-equivalent check gates share minting the way it gates `redeem`'s `inkind`:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
(present only in `redeem`) [4](#0-3) 

### Impact Explanation
A depositor who calls `deposit` with a small enough `amount` relative to the current share price receives `0` zTokens while their full underlying amount is transferred into and permanently retained by the vault (`(var-set assets (+ current-assets amount))`). This is a permanent, irreversible loss of the depositor's principal with no recorded claim to redeem it — meeting the "theft of principal / permanent freezing of funds" bar. It also silently benefits existing shareholders since vault assets increase without dilution of supply. This is asymmetric with the audited report's fix on the withdrawal side; here the analogous fix must be applied on the deposit/minting side.

### Likelihood Explanation
Likelihood depends on the share price ratio `total-assets / total-supply` growing large enough relative to a user's deposit size, which occurs naturally over time as interest compounds without corresponding dilution, and is worsened for underlying assets with low decimal precision (e.g., `sBTC`, 8 decimals) or vaults that accumulate large interest reserves relative to supply. Any user who deposits a small amount (intentionally or via a UI rounding/slippage misconfiguration with `min-out = 0`) after sufficient index growth triggers this condition without needing any privileged action or governance compromise.

### Recommendation
Add an explicit zero-shares guard in `deposit`, mirroring the existing `redeem` guard, before transferring underlying in or minting shares:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed immediately alongside the other `asserts!` checks in `deposit`, for all vault variants (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`), so that a deposit which would mint zero shares reverts instead of silently consuming the user's principal.

### Proof of Concept
1. Vault is live and has accrued substantial undistributed interest such that `total-assets-preview / total-supply-preview` (the effective share price) is, say, `2_000_000` (i.e., 1 share is worth 2,000,000 units of underlying raw precision) — plausible for a low-decimal asset like `sBTC` (8 decimals) after long-running interest accrual.
2. Attacker/careless user calls `deposit(amount=1_000_000, min-out=0, recipient=self)`.
3. `convert-to-shares-preview` computes `mul-div-down(1_000_000, ts, ta)`, which rounds down to `0` because `1_000_000 * ts < ta`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially since `min-out = 0`.
5. `receive-underlying` pulls the full `1_000_000` units of underlying from the user into the vault.
6. `ft-mint? zft 0 recipient` mints zero shares to the user.
7. `var-set assets` increases by `1_000_000`, permanently increasing the redeemable value backing all *existing* shareholders while the depositor holds no shares and cannot recover the deposited amount. [2](#0-1) [5](#0-4)
