### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are trusted despite not being covered by the HMAC signature - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, then blindly forwards attacker-controlled HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) to the app's webhook handler as trusted, verified metadata.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely against this signable string (the raw body): [3](#0-2) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body: [4](#0-3) 

`Registry.process` only checks the body HMAC, then constructs `WebhookMetadata` using the unverified `request.shop` and `request.topic` header values and passes them straight to the app-registered handler: [2](#0-1) 

The identity binding that should hold is: `bytes covered by HMAC == bytes the handler treats as authenticated (shop, topic, webhook_id, api_version)`. In reality only the body satisfies this; the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signed content, so they are fully attacker-controlled as long as the attacker can supply *any* body+HMAC pair that validates.

### Impact Explanation
An unprivileged internet user who has access to at least one legitimately-signed webhook delivery (trivially obtainable by installing the target app on their own free/trial store and triggering any webhook topic, capturing the raw body bytes and the corresponding `X-Shopify-Hmac-Sha256` header) can replay that exact `(body, hmac)` pair directly to the app's public webhook endpoint while forging the `shopify-shop-domain` header to name a victim merchant's shop, and/or forging `shopify-topic` to a different registered topic. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the app's handler believing the event is authentically attributed to the victim shop/topic. Depending on the app's handler logic (e.g., handlers for `app/uninstalled`, `shop/redact`, `customers/redact`, or business logic keyed off `data.shop`), this enables cross-tenant confusion — actions or data processing intended for one shop's event being executed against another shop identity, which the app has no way to detect since the gem itself presents `shop`/`topic` as if verified.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is a single legitimately-signed webhook payload, which any developer/attacker can generate for free by installing the app on their own store and triggering an event. No access token, `client_secret`, or privileged account is required — only public interaction with the app's exposed webhook receiver endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or otherwise cryptographically bind them to the body), or at minimum have `Registry.process` cross-check that these header values are consistent with an independently authenticated source (e.g., verify the shop against an active session, or reject bodies whose declared shop can't be corroborated) before handing them to the handler as authenticated `WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-owned test store; trigger a webhook (e.g., any topic with an empty/predictable JSON body `{}`).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header from that real delivery.
3. Send a new HTTP POST to the app's webhook endpoint with the identical raw body and `X-Shopify-Hmac-Sha256` header, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and optionally change `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. The registered handler is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the request never originated from Shopify for that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
