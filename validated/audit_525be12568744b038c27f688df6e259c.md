### Title
Incorrect decimal-scaling formula in `convert_to_balance`/`convert_to_erc20` causes under-mint on receipt and unbacked over-mint on withdrawal - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `hyper-fungible-token` pallet converts amounts between an EVM ERC20 token's decimals and the local Substrate asset's decimals using a formula that is only correct in one direction of the decimals comparison, exactly the class of bug described in the referenced Vader `TwapOracle` finding (a hard-coded/incomplete scaling expression that silently produces a wrong result instead of reverting).

### Finding Description
`convert_to_balance` and `convert_to_erc20` both compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`: [1](#0-0) 

- `convert_to_balance` (used to scale an incoming EVM amount down to the local balance on `on_accept`/`on_timeout`) divides by `10^(erc_decimals - local_decimals)`.
- `convert_to_erc20` (used to scale a local balance up to the ERC20 representation when sending, i.e. in the outgoing `Message.amount`) multiplies by `10^(erc_decimals - local_decimals)`.

Both use `saturating_sub` in the *same* direction (`erc_decimals - local_decimals`). This is only correct when `erc_decimals >= local_decimals` (the documented/tested case for `BridgeToken`, where EVM `decimals()`=18 and nexus native decimals=12, so the pallet "scales by 10^6 in both directions"): [2](#0-1) [3](#0-2) 

For any registered asset where the local (`pallet-assets`) decimals are *greater* than the paired ERC20 token's decimals (e.g. local asset configured with 18 decimals against a 6-decimal ERC20 like USDC), `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so both conversion functions apply a scaling factor of `10^0 = 1` — i.e., no scaling at all — instead of the correct scale-up-by-`10^12`/scale-down-by-`10^12` that the reverse direction requires.

This conversion is used directly on the money path:
- Inbound mint/transfer: `on_accept` calls `convert_to_balance(erc_amount, erc_decimals, decimals)` and mints/releases the result to the beneficiary. [4](#0-3) 
- Outbound send (not shown in the excerpt I could confirm, but per the module doc and `impls.rs` header, `convert_to_erc20` is the mirror function used to build the outgoing `Message.amount` when a user calls `send`).

### Impact Explanation
Two asymmetric, high-impact failures result from the missing bidirectional scale:
1. **Under-mint / fund loss on receipt**: an inbound ERC20 amount whose raw integer represents a normal 6-decimal quantity (e.g. `1_000_000` = 1.0 token) is credited to the beneficiary unscaled — i.e. as `1_000_000` in an 18-decimal asset, which is effectively dust (`10^-12` of what was actually locked/burned on the EVM side). Funds are permanently stranded relative to what was escrowed.
2. **Unbacked over-mint / drain on send**: the reverse path is the more severe one. Burning/locking a local balance of `X` (18-decimal precision) and building the outgoing ERC20 `Message.amount` with the same missing-scale bug encodes `X` unscaled as the 6-decimal ERC20 amount. The counterpart contract on the EVM chain will then release/mint an amount `10^12` times larger than what was actually escrowed by the sender — a classic unbacked-mint / escrow-drain condition reachable by any ordinary token bridger.

This is analogous to the cited `TwapOracle` bug: a scaling formula whose correctness silently depends on the relative ordering of two decimals values, with no revert or bound check when that ordering is inverted.

### Likelihood Explanation
This triggers whenever `register_token` (a normal, non-privileged-attacker administrative action, but a completely realistic configuration — e.g. wrapping a 6-decimal stablecoin against a locally-created 18-decimal `pallet-assets` asset) results in `local_decimals > erc_decimals` for a given `(asset, chain)` pair. Given `Precisions` and the local asset's decimals are independently configured (`Precisions::<T>` vs `pallet-assets` metadata), this mismatch is easy to introduce unintentionally and is not validated anywhere in `_processTokenDecimalsUpdates`-equivalent registration logic on the Substrate side. Once such an asset is registered, every ordinary user's `send` (bridge-out) or bridge-in delivery silently mis-scales — no special privilege needed to trigger it, only a legitimate token configuration where the local asset decimals exceed the remote ERC20's decimals.

### Recommendation
Replace the one-directional `saturating_sub` scaling with a correct bidirectional conversion, e.g.:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add regression tests covering `local_decimals > erc_decimals` for both `on_accept`/`on_timeout` and `send`, mirroring the existing `erc_decimals > local_decimals` (BridgeToken 18-vs-12) coverage.

### Proof of Concept
1. Register an asset via `register_token` where the local `pallet-assets` asset is created with 18 decimals, and the corresponding EVM contract is configured in `Precisions` with `erc_decimals = 6` (e.g. a token analogous to USDC bridged to a locally 18-decimal-denominated wrapped asset).
2. User bridges `1_000_000` (1.0 unit at 6 decimals) from the EVM contract to nexus. `on_accept` computes `erc_decimals(6).saturating_sub(local_decimals(18)) = 0`, so `convert_to_balance` divides by `10^0`, minting `1_000_000` (effectively `0.000000000001` of a normal 18-decimal unit) instead of `1_000_000_000_000_000_000`. [4](#0-3) [5](#0-4) 
3. Conversely, a user who burns/locks `1_000_000_000_000_000_000` (1.0 unit, 18-decimal local balance) to send back to the EVM chain has that value passed through `convert_to_erc20` with the same `saturating_sub(6,18)=0` collapse, producing an outbound ERC20 `Message.amount` of `1_000_000_000_000_000_000` instead of `1_000_000` — a 6-decimal-token release/mint order of magnitude `10^12` larger than what was actually escrowed. [6](#0-5)
