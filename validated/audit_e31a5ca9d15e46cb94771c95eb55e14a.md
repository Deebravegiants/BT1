## Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (via `x-shopify-shop-domain`/`shopify-shop-domain` header) is read separately and never covered by the signature. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value and hands it straight to the app's webhook handler, breaking the binding `shop authenticated == shop the payload is attributed to`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read independently from a header that participates in no cryptographic check: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the signable string (i.e., the body) against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC of the body, then immediately forwards `request.shop` — an unauthenticated field — to the handler as the tenant identity for the event: [4](#0-3) 

Because Shopify apps use a single `api_secret_key` shared across every shop that installs the app, any merchant who installs the app can legitimately receive at least one valid `(raw_body, hmac)` pair for their own shop. Since the shop header is not part of what's signed, that same `(raw_body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to point at a different (victim) shop. The gem's own HMAC check will still pass — it only verifies that the body was signed with the shared secret, not which shop the request claims to originate from — and the handler receives `WebhookMetadata` attributing the event to the victim shop.

This is exactly the binding-break pattern described in the report: an identity field (`shop`) is acted upon by downstream logic but is not covered by the same authentication mechanism (`HMAC`) that is used to establish trust in the request.

### Impact Explanation
This crosses a tenant boundary within the gem's own validated flow: an unprivileged merchant (attacker) can cause the app to process a cryptographically "valid" webhook attributed to another merchant's shop. Any host application that relies on `Registry.process`/`WebhookMetadata#shop` (as documented and demonstrated in the gem's own tests) to select which tenant's session/data to act on will attribute or apply the forged webhook to the wrong shop — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the app as any shop to legitimately receive one valid webhook delivery (trivially triggered, e.g., via `app/uninstalled` or any store event), (2) capturing the raw body + `x-shopify-hmac-sha256` value, and (3) POSTing that same body/HMAC to the app's webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are needed beyond normal app installation, which is exactly the "unprivileged internet user" class targeted by this analysis.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed payload verification path, or otherwise cryptographically bind the claimed `shop` header to the specific webhook delivery (e.g., cross-check against a per-shop registered webhook id/subscription looked up via the Admin API before dispatching to the handler) rather than trusting `x-shopify-shop-domain` as-is once the body HMAC passes.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker (a normal merchant) receives a legitimate webhook delivery for topic `X` with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's shared `api_secret_key`).
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (victim).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes: [5](#0-4) 
4. The handler executes with `WebhookMetadata#shop == "shop-b.myshopify.com"` even though the payload never originated from, nor was authenticated for, `shop-b`.
