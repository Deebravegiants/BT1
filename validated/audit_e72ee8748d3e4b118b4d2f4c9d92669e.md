### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, then trusts the separate, unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity passed to the app's handler. This breaks the identity binding `hmac_signed_bytes == bytes_the_shop_field_is_derived_from`, analogous to the reported bug where the reward calculation used the totalSupply of the wrong token (`AToken` instead of `DebtToken`) — the value acted upon was not the value that was actually verified/bound.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` method returns only the raw request body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers, which are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this validation result as its *sole* authentication check, and then forwards the unauthenticated `request.shop` header value straight to the app's webhook handler as the tenant identity: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is a single value shared by the app across every shop that installs it, the HMAC over a given raw body is identical no matter which shop it originated from. An unprivileged internet user who controls (or can install the target app on) any shop can:
1. Legitimately receive a webhook from Shopify for their own shop, capturing a valid `(raw_body, hmac)` pair.
2. Replay that exact `raw_body`/`hmac` pair directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header rewritten to the victim's shop domain.
3. `HmacValidator.validate` still returns `true` (it never inspects the shop header), so `Registry.process` accepts the request and dispatches `WebhookMetadata.new(... shop: request.shop ...)` with the victim's shop domain to the handler.

This is the same class of flaw as the report: the value actually used for a downstream security-relevant decision (`totalStaked`/`shop`) is not the value that was cryptographically verified (`scaledTotalSupply` of the wrong token / raw body without the shop header).

### Impact Explanation
Any app built on this handler pattern (as documented in `docs/usage/webhooks.md`, where the handler is told to trust `data.shop`) will process an attacker-controlled shop identity as authentic. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's stored access token/session to act on, or to write/attribute data), this enables cross-tenant data confusion/injection: an attacker can inject webhook events that appear to originate from a shop they do not control, potentially causing the app to perform actions, write data, or make follow-up authenticated Admin API calls against the wrong (victim) tenant's session — a cross-tenant access issue.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint that must accept unauthenticated network requests (that's the entire point of receiving webhooks), so nothing prevents any internet user from POSTing directly to it with arbitrary headers. The only prerequisite is obtaining one valid `(raw_body, hmac)` pair, which any user who can install the target app on their own store (a normal, unprivileged action for public apps) can trivially obtain by triggering any subscribed event on their own shop. No access token, `client_secret`, or elevated privilege is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g. by including the shop-domain header bytes in the HMAC signable string, or by independently verifying that `request.shop` corresponds to a shop that has a currently valid, stored session/installation record before trusting it. At minimum, update `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop-domain header (and other trusted-identity headers) rather than the raw body alone, so the identity used by the handler is provably the same identity Shopify authenticated.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers e.g. an "orders/create" webhook, capturing the real headers/body Shopify sends:
raw_body = '{"id":1,"note":"hello"}'
real_hmac_b64 = "<value Shopify computed with the app's api_secret_key>"

# 2. Attacker POSTs the identical body+hmac to the app's public webhook endpoint,
#    but swaps the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_b64,   # still valid! HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/hmac match),
#    handler.handle is invoked with data.shop == "victim-shop.myshopify.com"
```
This mirrors the test setup pattern already present in the repo (`test/webhooks/registry_test.rb`), confirming that `Registry.process` only checks `Utils::HmacValidator.validate(request)` — which is body-only — before trusting `request.shop`. [5](#0-4)

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
