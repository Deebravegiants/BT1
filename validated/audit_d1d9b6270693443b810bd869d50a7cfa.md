### Title
Global `evm_version = "cancun"` in Foundry config causes transient-storage opcodes (`TSTORE`/`TLOAD`) used by IntentGatewayV2/SolverAccount to be unreachable or reverting on non-Cancun target chains - (File: evm/foundry.toml)

### Summary
The single, project-wide `evm_version = "cancun"` compiler setting is applied to *every* deployment target listed in `evm/foundry.toml`, including chains such as BSC, Gnosis, Polygon, Sei, Soneium, Inkchain and Pharos. `IntentGatewayV2.sol`, `IntentsBase.sol` and `SolverAccount.sol` actively rely on Cancun-only transient-storage opcodes (`TSTORE`/`TLOAD`). Any target chain whose EVM implementation has not activated the Cancun hardfork will either reject deployment of this bytecode or revert every call that touches transient storage, exactly mirroring the referenced Symm.io report where a compiler/EVM-version mismatch (there `PUSH0` on Optimism/Arbitrum) rendered the audited contracts unusable on specific chains.

### Finding Description
`evm/foundry.toml` sets a single global `evm_version = "cancun"` for the whole `src` tree and lists RPC/etherscan entries for a broad set of mainnets — Ethereum, Optimism, Arbitrum, Base, BSC, Gnosis, Soneium, Polygon, Unichain, Inkchain, Sei and Polkadot. [1](#0-0) [2](#0-1) 

Several of these networks historically lag behind Ethereum L1 in hardfork activation (Cancun introduced `TSTORE`/`TLOAD`/`MCOPY`/blob opcodes). Contracts compiled with `evm_version = "cancun"` will contain these opcodes directly in their bytecode. `IntentGatewayV2.sol`, `IntentsBase.sol`, and `SolverAccount.sol` — code paths reachable by any unprivileged intent solver or order placer — make explicit use of transient storage: [3](#0-2) [4](#0-3) 

Because `TSTORE`/`TLOAD` are opcodes introduced specifically in Cancun, deploying or invoking these contracts on any of the listed chains that have not activated Cancun will cause the EVM to either fail to interpret the opcode (deployment/execution failure) or revert with an invalid-opcode error on every call path that touches transient storage — this affects order placement, solver bidding/filling, and settlement flows in the Intent Gateway.

### Impact Explanation
If the Intent Gateway (`IntentGatewayV2`, `IntentsBase`, `SolverAccount`) is deployed to a chain lacking Cancun support, every transaction that exercises the transient-storage code paths — order creation, solver bid/fill, escrow release — will revert, permanently bricking the intents escrow/bids flow on that chain. This is a route-unable-to-deliver/execute-messages condition consistent with the rules' "unable to deliver" criterion, and in the worst case could strand funds already escrowed in `SolverAccount`/`IntentGatewayV2` if the freeze occurs mid-flow (deposits succeed on an earlier-forked network build, subsequent settlement calls that need transient storage fail).

### Likelihood Explanation
High. The mismatch is deterministic and chain-specific, not dependent on attacker behavior — it fires automatically for any deployment to a chain whose client hasn't activated Cancun at the time of deployment, and multiple listed target chains (e.g., BSC, Gnosis, Sei, Soneium, Inkchain) had inconsistent or delayed Cancun rollouts relative to Ethereum mainnet. Any relayer, solver, or user interacting with the intent contracts on such a chain will trigger the failure on the very first transaction that touches transient storage.

### Recommendation
Do not apply a single global `evm_version` across all deployment targets. Either:
1. Split compilation profiles per target chain in `foundry.toml` (e.g., a `cancun`-safe profile for chains confirmed to support it, and a `paris`/`shanghai` profile with a non-transient-storage-reliant implementation of `IntentGatewayV2`/`IntentsBase`/`SolverAccount` for chains that haven't upgraded), or
2. Refactor `IntentsBase.sol`/`SolverAccount.sol`/`IntentGatewayV2.sol` to avoid Cancun-only opcodes (use regular storage instead of transient storage) so the same bytecode is portable across all listed chains, verifying each target chain's active hardfork before every deployment.

### Proof of Concept
1. Compile `evm/src` with `foundry.toml`'s `evm_version = "cancun"` (default profile).
2. Deploy `IntentGatewayV2`/`SolverAccount` to a chain in the RPC/etherscan list (e.g., Gnosis or BSC) whose live EVM client has not activated the Cancun hardfork.
3. Call any solver/intent function that internally hits transient storage (`TSTORE`/`TLOAD`) in `IntentsBase.sol`/`SolverAccount.sol`.
4. Observe the call reverts with an invalid opcode / execution failure, freezing the intents flow on that chain — analogous to the referenced report's `PUSH0` incompatibility bricking contracts on Optimism/Arbitrum.
