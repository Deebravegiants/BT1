### Title
Stale escrow accounting during external transfers in `IntentGatewayV2.withdraw` enables read-only reentrancy against integrators reading `_orders` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron build of `IntentGatewayV2` settles cross-chain intent escrow via an internal `withdraw()` function that sends value/tokens to an attacker-controlled `beneficiary` *before* decrementing the public `_orders` escrow mapping for that token, violating checks-effects-interactions in the same way the referenced Earn-Vault report describes. This mirrors a bug class the maintainers already fixed in the mainline EVM contract (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`), but the Tron variant still contains the pre-fix pattern.

### Finding Description
`IntentGatewayV2.withdraw` (Tron variant) marks the order filled up front, which blocks direct re-entry into itself, but for each escrowed token it performs the external transfer and only afterwards updates the escrow accounting: [1](#0-0) 

Concretely:
1. `_filled[body.commitment] = beneficiary;` is set first (this stops a second call to `withdraw` itself for the *same order*).
2. For each token in the loop, the contract reads `_orders[body.commitment][token]` merely to check non-zero, then makes an **external call** — either a raw ETH `.call{value: amount}("")` to `beneficiary`, or a raw `.call(...transfer...)` to an arbitrary ERC-20 `token` contract.
3. **Only after** that external call returns does it execute `_orders[body.commitment][token] -= amount;`.

During the window between the external call and the state write, `_orders[commitment][token]` (a `public` mapping, directly and freely readable by any other contract or off-chain integrator) still reports the pre-withdrawal (stale/full) escrow balance for that token, even though the funds have already left the contract. This is the exact "read-only reentrancy" primitive described in the source report: state consumers that trust `_orders` (or any derived accounting/oracle) can be tricked into acting on inflated escrow figures during the beneficiary's `receive()`/fallback or a malicious ERC-20's `transfer` hook.

By contrast, the mainline EVM contract already applies the CEI fix for the identical function: [2](#0-1) 

There, `_orders[...] -= amount` happens **before** `_sendValue`/`safeTransfer`, closing this exact window. The Tron contract was not updated to match.

### Impact Explanation
Any protocol, price oracle, liquidation engine, or off-chain accounting system that composes with the Tron `IntentGateway` and reads `_orders[commitment][token]` (its only escrow-accounting surface, since it is a public mapping) mid-transaction — e.g., during the native-ETH `beneficiary.call` or the malicious ERC-20's `transfer` execution — will observe an escrow balance that no longer reflects reality (funds already paid out). This can be leveraged to:
- Double-count escrowed collateral in an external system that grants credit, mints derivative claims, or releases additional funds based on the stale `_orders` value.
- Combine with a multi-token withdrawal request: while token[0]'s native ETH transfer is in flight, `_orders[commitment][token1]` for a not-yet-processed second token is still fully intact, and `_orders[commitment][token0]` has also not yet been decremented — so any external system that reads *all* escrow entries for the commitment during this callback sees the full, unspent original escrow even though token0 has already been sent out.

This is a fund-integrity/state-commitment issue reachable purely from the intents settlement flow (a relayed cross-chain `RedeemEscrow`/`RefundEscrow` message triggering `onGetResponse` → `withdraw`), with the attacker-controlled surface being the `beneficiary` address (solver) chosen at order-fill time, matching the "intents escrow" reachable path in scope.

### Likelihood Explanation
Medium-to-High likelihood. The `beneficiary` of an intent fill is fully attacker-controlled (a solver can direct funds to any contract of its choosing), so triggering the callback window costs nothing beyond deploying a small receiving/hook contract. Exploitation impact depends on whether an external integrator actually consumes `_orders` mid-call, but since the mapping is `public` and is the canonical on-chain escrow-accounting source for this gateway, it is a realistic integration point (analogous to Balancer/Curve pool balance reads that motivated the original report).

### Recommendation
Apply the same checks-effects-interactions ordering already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to the Tron contract's `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** making the native-value `.call` or ERC-20 `.call(transfer(...))`. Additionally, consider adding a read-only reentrancy guard (mirroring Balancer's `VaultReentrancyLib` pattern cited in the original report) so that any external consumer of `_orders` can assert the gateway is not mid-transaction before trusting the value.

### Proof of Concept
1. A solver fills a cross-chain order and becomes `beneficiary` for the settlement `WithdrawalRequest`, using a contract with a `receive()` fallback (for the native-token branch) or deploying a malicious ERC-20 as one of `body.tokens` if it controls the escrowed token list.
2. When the relayed settlement message resolves via `onGetResponse` → `withdraw(body, true)`, `_filled[commitment]` is set, then the loop reaches the attacker's token/beneficiary and executes the external `.call`.
3. Inside `receive()` (or the malicious token's `transfer`), the attacker's contract calls out to any external protocol that reads this gateway's `_orders(commitment, token)` — it will return the pre-payout (full) escrow amount, because `_orders[commitment][token] -= amount` has not executed yet.
4. The attacker uses that stale, inflated read to obtain value/credit from the external integrator (e.g., a lending market that accepts `_orders` balance as proof of unclaimed collateral) before the gateway's own state settles to the correct (already-paid-out) value. [1](#0-0) [3](#0-2)

        // redeem escrowed tokens
        uint256 len = body.tokens.length;

                if (!success) revert TransferFailed();
            }

                ++i;
            }
        }
