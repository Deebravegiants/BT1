### Title
Deterministic, guessable offline session id set as the raw, unsigned `shopify_app_session` cookie value enables session hijacking - ([File: lib/shopify_api/auth/oauth.rb], [File: lib/shopify_api/auth/session.rb], [File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded offline sessions, this gem sets the `shopify_app_session` cookie's value to `session.id`, which for offline sessions is exactly `"offline_#{shop}"` — a value fully reconstructable from the shop's public myshopify domain. `SessionUtils.current_session_id` then trusts that exact cookie value verbatim as the session-storage lookup key, with no cryptographic binding to `Context.api_secret_key` or anything else secret.

### Finding Description
The broken binding: the value trusted by `current_session_id` as the authenticated session id must equal a value derivable only from `Context.api_secret_key`-authenticated bytes. In this codebase it instead equals `offline_session_id(shop) == "offline_#{shop}"`, a pure function of the public shop domain.

Trace:
1. `Auth::Oauth.validate_auth_callback` (lib/shopify_api/auth/oauth.rb:96-110) builds `session = Session.from(shop: auth_query.shop, ...)`. For offline tokens, `Session.from` (lib/shopify_api/auth/session.rb:107-117) sets `id = "offline_#{shop}"` — no randomness, no HMAC, nothing derived from `api_secret_key`.
2. The same method then builds the cookie for non-embedded apps as `SessionCookie.new(value: session.id, expires: ...)` (lib/shopify_api/auth/oauth.rb:105-109). So the literal cookie value handed to the host app to set is `"offline_#{shop}"`.
3. `SessionUtils.current_session_id` for non-embedded apps does `cookie_session_id(cookies)` (lib/shopify_api/utils/session_utils.rb:31-36, 68-71), which just returns `cookies[SESSION_COOKIE_NAME]` unchanged. There is no signature check, no HMAC validation, and no cross-check against `Context.api_secret_key` anywhere in this path.
4. `SessionUtils.offline_session_id(shop)` (lib/shopify_api/utils/session_utils.rb:63-66) independently confirms the id scheme is `"offline_#{shop}"`, callable by anyone with only the public shop domain.

Root cause: the gem uses a deterministic, publicly-derivable string as both the session storage primary key and the bearer value placed in a plain (non-signed) cookie, and the session-id-retrieval code in this gem accepts that cookie value as authoritative without any cryptographic check.

Exploit flow: an attacker who knows (or guesses) a victim shop's `*.myshopify.com` domain — trivially discoverable (public storefront, app listing, etc.) — computes `"offline_victim-shop.myshopify.com"` and sends it as their own `shopify_app_session` cookie to the host app. The host application, following this gem's documented pattern (`current_session_id(nil, cookies, false)` → passed to session storage `retrieve(id)`, as shown in `BREAKING_CHANGES_FOR_V16.md`'s reference implementation), looks up and returns the victim's stored `Session`, including `access_token`. The attacker's subsequent API calls run as the victim shop.

None of this gem's existing guards intervene on this path: `HmacValidator.validate` and the `state` comparison only protect the initial OAuth callback (lib/shopify_api/auth/oauth.rb:64-71), not the cookie session-id lookup that happens on every later request; `JwtPayload`'s `aud` check only applies to the embedded/JWT branch, not the non-embedded cookie branch; `Context.embedded?` merely selects which branch runs, it does not add authentication to the cookie branch.

### Impact Explanation
This is a cross-tenant authentication bypass: any unprivileged attacker who knows a victim shop's domain can cause a host app (built on this gem, in non-embedded/offline mode, following the documented session-storage pattern) to treat them as that shop, exposing/using the victim's `access_token` on the attacker's behalf. It is repeatable against any shop whose domain is known and requires no secret, no valid OAuth flow, and no interaction with the victim. Blast radius spans every shop using the vulnerable non-embedded/offline configuration.

### Likelihood Explanation
Preconditions: the host app is non-embedded and relies on this gem's `SessionCookie`/`current_session_id` offline-session flow exactly as documented, and persists sessions keyed by `session.id` (the documented/reference pattern). Attacker cost is trivial — set one cookie header, no credentials needed, myshopify domain is public. This is highly feasible and repeatable for any targeted shop.

### Recommendation
Never use a deterministic, publicly-derivable string as the bearer value of an unsigned cookie that is later trusted as a session-storage key. Either (a) generate a random opaque token for the cookie value (e.g., `SecureRandom.uuid`) that is separate from `session.id` and mapped server-side, or (b) sign/HMAC the cookie value using `Context.api_secret_key` and verify that HMAC in `SessionUtils.cookie_session_id`/`current_session_id` before trusting it.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_offline_session_id_is_publicly_derivable_and_trusted_from_cookie
  shop = "victim-shop.myshopify.com"

  # Anyone can compute this without secrets:
  guessed_id = ShopifyAPI::Utils::SessionUtils.offline_session_id(shop)
  assert_equal("offline_#{shop}", guessed_id)

  # And it is exactly what the gem places into the non-embedded session cookie
  # for an offline session (see Session.from / validate_auth_callback).
  session = ShopifyAPI::Auth::Session.new(shop: shop, id: guessed_id, access_token: "victim_token")
  assert_equal(guessed_id, session.id)

  # current_session_id trusts an attacker-supplied cookie containing this
  # guessed value with zero verification against api_secret_key:
  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  attacker_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => guessed_id }

  resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, attacker_cookies, false)
  assert_equal(guessed_id, resolved_id) # identical to victim's real stored session id
end
```
This demonstrates both sides of the claimed broken binding matching: the value `SessionUtils.current_session_id` accepts from an attacker-controlled, unsigned cookie is identical to `SessionUtils.offline_session_id(shop)`, computable from public data alone, with no dependency on `Context.api_secret_key`. ## Reference: shopify_app gem implementation

The [shopify_app gem](https://github.com/Shopify/shopify_app) provides a reference implementation of session storage that follows these best practices:

# Stores attributes in database columns
def store(auth_session)
  shop = find_or_initialize_by(shopify_domain: auth_session.shop)
  shop.shopify_token = auth_session.access_token
  shop.save!
end

# Reconstructs using Session.new()
def retrieve(id)
  shop = find_by(id: id)
  return unless shop

  ShopifyAPI::Auth::Session.new(
    shop: shop.shopify_domain,
    access_token: shop.shopify_token
  )
end
