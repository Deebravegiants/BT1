### Title
Native-token fee payment swaps in `EvmHost` lack a caller-settable slippage tolerance, exposing overpaid native tokens to sandwich extraction - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all convert native tokens sent via `msg.value` into the protocol `feeToken` by calling `IUniswapV2Router02.swapETHForExactTokens`, but the caller has no way to bound the acceptable execution price beyond simply not overpaying `msg.value`. Any user who dispatches a request or funds one with native token pays whatever price the pool offers at that block, with the SDK's off-chain `quote()` (documented as itself vulnerable to sandwich attacks) as the only reference point.

### Finding Description
Each of the three entry points builds a two-hop path `[WETH, feeToken]` and calls `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`: [1](#0-0) [2](#0-1) [3](#0-2) 

The `deadline` argument is `block.timestamp` — the same block the transaction executes in — so it provides no real protection against price movement between quote and execution; it only rejects a transaction that is delayed past its own block, which never happens. The only price bound is `msg.value` itself: the router will revert with `EXCESSIVE_INPUT_AMOUNT` if the exact-output swap would need more ETH than supplied. There is no parameter analogous to a slippage-tolerance percentage that a caller can supply to cap acceptable price impact independent of how much native token they choose to send.

The project's own documentation acknowledges the underlying sandwich risk for the companion `quote()` helper that produces the `msg.value` figure callers use: [4](#0-3) 

This is the same bug class as the reported `FlashloanLiquidator.executeOperation` issue: a function reachable by an ordinary (unprivileged) caller performs an on-chain swap of user-supplied value with no caller-configurable slippage tolerance, relying only on an implicit, non-adjustable bound (there, `totalDebt + 1`; here, `msg.value`) that can be degraded by pool-price manipulation immediately around the transaction.

### Impact Explanation
Because callers routinely send a `msg.value` buffer above the exact quoted fee (to accommodate the same price movement the quote function itself warns about, and because `quote()` is explicitly unsafe to call on-chain for precise sizing), an attacker who sandwiches the `dispatch`/`fundRequest` transaction can shift the pool price so that the exact-output swap consumes materially more of the supplied buffer than fair value would require, capturing the difference as MEV at the caller's expense. This is a direct loss of funds for any unprivileged user paying via native token, medium severity since it requires the attacker to observe and front/back-run a pending mempool transaction and requires the victim to have provided a spendable buffer (a normal and expected precaution given the router's exact-output requirement).

### Likelihood Explanation
`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` are all public, unprivileged entry points on `EvmHost`/`IDispatcher` that any account can call by simply sending native token with a request — this is the documented, encouraged path ("Native Token Payment... let the Host handle the Uniswap swap") for one-off dispatches and user-facing apps: [5](#0-4) 
Sandwiching a pending public-mempool transaction against a known AMM pair is a standard, low-cost MEV technique, making exploitation practical whenever a victim's `msg.value` buffer exceeds the true post-manipulation cost.

### Recommendation
Add an explicit, caller-supplied slippage-tolerance/maximum-input parameter to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` (e.g., `maxNativeIn` or a `slippageBps` used to compute it) and pass that value's own upper bound to the router instead of relying solely on the full `msg.value` transfer as the cap. Additionally, replace the meaningless `block.timestamp` deadline with a caller-supplied deadline so a fully-formed transaction cannot be replayed later by a relayer/attacker if it fails to mine promptly.

### Proof of Concept
1. A user (or an app on their behalf) calls `EvmHost.quote(...)` off-chain to size a `DispatchGet`/`DispatchPost` native payment, then submits `dispatch{value: quotedAmount + buffer}(...)` to cover expected slippage since `quote()` itself is documented as unsafe to call on-chain for exact sizing.
2. An attacker observing the pending transaction in the mempool front-runs it with a trade on the same `WETH/feeToken` pair used by `_hostParams.uniswapV2`, shifting the price unfavorably for the victim's swap.
3. `EvmHost.dispatch` executes `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`; because the exact fee-token output is fixed and the deadline is trivially satisfied, the swap consumes a larger share of `msg.value` at the manipulated price than it would have at the pre-attack price.
4. The attacker back-runs to restore the pool price, having captured the price-impact difference; the victim received the expected `post.fee` amount of fee token but at a worse ETH cost, with no on-chain mechanism available to have capped or detected this beyond reverting entirely.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol" icon="solidity"
contract MyApp is HyperApp {
    function readRemoteStateWithNative(
        bytes memory dest,
        bytes[] memory keys
    ) public payable returns (bytes32) {
        bytes memory context = abi.encode(msg.sender, block.timestamp);
        
        DispatchGet memory getRequest = DispatchGet({
            dest: dest,
            height: 0,
            keys: keys,
            timeout: 3600,
            fee: 0,
            context: context
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(getRequest);
```
