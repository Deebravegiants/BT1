### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header verbatim and hands it to the app's handler. Since the HMAC secret (`api_secret_key`) is shared by the app across every shop that installs it, any actor who can obtain one valid `(body, hmac)` pair (trivially, by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header with any victim shop's domain. The library performs no binding between the authenticated bytes (body) and the `shop` field that identifies the tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

The `shop` accessor is read straight from the (unauthenticated) `shop-domain`/`x-shopify-shop-domain` header and is never included in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (the raw body) and compares it with the `hmac` header using a constant-time comparison — it never touches `shop`: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then forwards the untouched `request.shop` value into `WebhookMetadata`, which the host application uses to attribute the payload to a specific tenant: [4](#0-3) [5](#0-4) 

**Binding that is broken (as an equality):**
`shop_header == shop_that_the_HMAC_secret_authenticates` is assumed by every consumer of `WebhookMetadata#shop`, but the gem never establishes or checks this equality. The HMAC only proves `body == body_signed_by_this_app's_secret`; it says nothing about which shop sent it, because the same `api_secret_key` is used to sign webhooks for *every* shop that has installed the app.

### Impact Explanation
Because the signing secret is per-app (not per-shop), any unprivileged user who installs the app on their own (even free/dev) store receives genuine `(body, hmac)` pairs. They can then submit that exact body and HMAC to the app's public webhook endpoint with an arbitrary `shop-domain` header value (e.g., a competitor's or victim's `*.myshopify.com` domain). `ShopifyAPI::Webhooks::Registry.process` will pass HMAC validation and deliver a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain, with `body` fully attacker-controlled (any JSON they can get Shopify to send them, e.g. `orders/create`, `customers/create`, `app/uninstalled`, etc.). Downstream host applications (which resolve the shop's session/store row via `data.shop`) will process this attacker-supplied payload as if it originated from the victim shop — this is a cross-tenant data-injection / spoofing primitive (e.g., fabricating orders, triggering `app/uninstalled` cleanup, or forging customer PII deletion requests) against a shop the attacker never controls. This satisfies the "cross-tenant access" Critical impact category, since one tenant's authenticated channel is used to inject data attributed to another tenant.

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` to select the tenant record (a very common pattern, and the only field the library exposes for that purpose). The only prerequisite is that the attacker can install the target app on some shop they control (trivial — free development stores are self-service) and can reach the app's public webhook endpoint (which is, by definition, internet-reachable). No secrets, tokens, or privileged access are required — this is a pure unprivileged-internet-user attack, consistent with the "shop authenticated versus shop stored as session key" analog described in the prompt.

### Recommendation
Bind the shop identity into the authenticated bytes, or otherwise cryptographically/authoritatively verify it before trusting `request.shop`:
- Include the shop domain (and ideally the webhook id/topic) in the HMAC-covered signable string, or
- Cross-check the incoming `shop-domain` against the webhook subscription previously registered for that shop (e.g., verify `webhook_id` belongs to a subscription created for the claimed shop via a stored mapping), and
- Document/require that consuming applications never trust `WebhookMetadata#shop` without confirming it corresponds to a shop for which they have create/registered this specific `webhook_id`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid-hmac-for-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"customer": {...attacker-controlled...}}
   ```
2. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the same app endpoint, only changing:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` only recomputes the HMAC over the raw body (`to_signable_string`), which is unchanged, so validation succeeds.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, and the host application processes attacker-controlled data as belonging to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
