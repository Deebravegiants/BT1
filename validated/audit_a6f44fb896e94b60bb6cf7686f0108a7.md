### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers via `shopify_header`. `Registry.process` validates the HMAC over the body only and then unconditionally trusts the header-derived `shop` value to build the `WebhookMetadata` dispatched to the app's handler, breaking the equality "shop authenticated by HMAC" == "shop acted upon by the handler."

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field [1](#0-0) . For webhook requests, `hmac` is parsed from the `hmac-sha256` header, but `to_signable_string` returns only `@raw_body` [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers via `shopify_header`, none of which participate in the signed bytes [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to construct `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` as the identity of the shop the event belongs to [4](#0-3) . `WebhookMetadata.shop` is a plain, unauthenticated `String` field [5](#0-4) .

This is not merely a host-application misuse issue: the gem's own documentation for `Registry.process` states it "will verify the request did indeed come from Shopify," implying the whole `Request` — including the shop identity — is authenticated [6](#0-5) . The gem provides no mechanism, and the documented usage sample offers no guidance, for cross-checking `data.shop` against a value that is actually covered by the signature.

### Impact Explanation
An unprivileged internet user who controls (or has previously received) any single genuine `(raw_body, hmac)` pair issued by Shopify for a real event — for example, by installing the app on their own inexpensive/free development store and triggering a `shop/redact`, `customers/data_request`, or any other webhook topic with body content they control or can predict — can replay that exact body and HMAC to the target app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers with a victim shop's domain. `HmacValidator.validate` still returns `true` because the signature only covers the body, and `Registry.process` dispatches the forged event to the handler labeled with the attacker-chosen `shop`. Any app logic keyed off `data.shop` (e.g., updating per-shop state, honoring mandatory compliance webhooks like `shop/redact`/`customers/redact`, enqueuing shop-scoped background jobs) is now attacker-controlled for shops the attacker was never authorized to act on — a cross-tenant identity-binding break.

### Likelihood Explanation
Exploitation requires only unprivileged internet access and knowledge of the app's public webhook endpoint plus one legitimate `(body, hmac)` sample, which is trivially obtainable by installing the (often freely installable) app on the attacker's own store or intercepting their own webhook traffic. No access token, `client_secret`, or privileged credential is required, matching the "unprivileged internet user" threat model, and no cooperation from the host application beyond following the gem's own documented `Registry.process` usage is needed.

### Recommendation
Include the shop-identifying fields (`shop`, `topic`, `webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the raw body before verification — e.g., verify the header-derived `shop` against a per-installation secret/session record rather than trusting it outright. At minimum, update `to_signable_string` so all fields later exposed via `WebhookMetadata` are covered by the same signature that gates `Registry.process`, so the equality "HMAC-authenticated bytes" == "bytes the handler acts upon" holds.

### Proof of Concept
1. Install the target app on an attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) and capture the raw POST: headers include `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`; body is `B`.
2. Replay the exact same `B` and `H` to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` [7](#0-6) [8](#0-7) .
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, believing this is a legitimate event for `victim-shop.myshopify.com`, despite the app never having produced or authorized this event for that shop.
