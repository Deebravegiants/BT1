### Title
Repay/recapitalize overpayment refund pays declared "excess" out of pool custody without a measured inbound transfer - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay` resolves `overpayment` from the **declared** `action.amount` and refunds it to `payer` via `transfer_out`, but the refund is neither debited from the tracked `cash` book nor gated by `require_reserves`, and — critically — the pool never verifies that `action.amount` was actually received. A repay on a market with no (or small) debt makes nearly the entire declared amount "overpayment," so an attacker can call `repay` with a large amount, transfer nothing (or little) in, and walk away with a refund paid out of real pool custody. This is the exact analog of `pullFunds()`: bookkeeping is updated (`credit_cash(net_repay)`, `burn_debt`) and a payout is issued based on a requested/declared figure rather than the actually moved amount, so the tracked books diverge from token reality.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `accounting` computes `(burned, overpayment) = cache.resolve_repay(amount, position)`, credits `net_repay = amount - overpayment` to cash, and `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)` at `contracts/pool/src/ops/repay.rs:32`. The overpayment refund path debits neither `cash` nor reserves — the characterization test in `contracts/pool/tests/flows.rs:3578-3610` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`) pins that "a repay against a market with no debt makes the entire declared amount an overpayment … and the whole amount is refunded out of real custody with the book untouched," explicitly noting the same gap in `ops::recapitalize::apply` (the excess over the measured shortfall). The controller's own paths are safe because they fund the pool first via `payments::transfer_amount_measured` (`contracts/controller/src/positions/liquidation/apply.rs:58`, `contracts/controller/src/strategies/legs.rs:50`), but the pool trusts `action.amount` verbatim — exactly the "deduct/refund the planned amount regardless of what actually moved" defect class. The protocol's own invariant INV-ACCT-03 ("credit equals measured receipt") is only enforced on the controller side; the pool-side refund has no symmetric measurement, so `book + refund ≠ custody`.

### Impact Explanation
Theft of user funds / protocol insolvency. Each call can extract up to the pool's full token balance for that asset by declaring an `amount` far above the position's debt: `resolve_repay` takes the full-close branch, `net_repay` is ~0 (so `RepayRoundsToZeroShares` passes on its `net_repay == 0` disjunct), and `transfer_out(payer, overpayment)` pays the attacker from suppliers' real tokens. Like `savedTotalUnderlying` in the source report, the tracked `cash`/`supplied` book does not reflect the outflow, so the loss also corrupts subsequent accounting (utilization, backing checks, revenue claims).

### Likelihood Explanation
High if `pool.repay` / `recapitalize` are externally callable (the pool test suite calls `client().repay(&payer, ...)` with no auth mocking, suggesting no `require_auth` gate on the leg). Requires only an attacker address and a pool holding tokens; no privileged role, no oracle manipulation, no timing dependency. The only mitigating factor would be an authorization gate on the pool entrypoint restricting it to the controller — this could not be fully verified from the indexed `lib.rs` wrapper, but the unfunded-refund test demonstrates the accounting path itself performs no receipt check.

### Recommendation
- Measure the inbound transfer at the pool layer (or require the caller to be the controller and keep measurement there), and compute `overpayment`/`net_repay` from the **received** amount, not `action.amount`.
- Alternatively, route the refund through the same measured-delta primitive used by `transfer_amount_measured`, and either debit `cash`/pass `require_reserves` for the refund or skip the refund entirely when `net_repay == 0` and no tokens were received.
- Apply the identical fix to `ops::recapitalize`, which refunds "excess over the shortfall" the same way.

### Proof of Concept
1. Market (hub_asset X) holds `cash = B` real tokens, `borrowed = 0` (or any small debt).
2. Attacker calls `repay(payer = attacker, action = {hub_asset: X, position: scaled_amount = 0, amount = B})`.
3. `resolve_repay(B, 0, …)` → `current_debt_ceil = 0` → full-close branch → `overpayment = B`, `burned = 0`, `net_repay = 0`.
4. The `RepayRoundsToZeroShares` assert passes via `net_repay == 0`; `credit_cash(0)`; `transfer_out(attacker, B)` pays the full pool balance to the attacker while `cash`, `supplied`, and `borrowed` books are untouched — a declared-amount refund with zero measured receipt, mirroring `savedTotalUnderlying -= amountToWithdraw` without a corresponding withdrawal.
