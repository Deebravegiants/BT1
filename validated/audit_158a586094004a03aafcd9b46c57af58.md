### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant data injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, but exposes the `shop` (tenant identifier) from an unsigned HTTP header. The `Registry.process` method trusts this unsigned `shop` value and hands it to the app's webhook handler as the tenant context, breaking the equality `shop authenticated by HMAC == shop used for tenant-scoped processing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is never part of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` calls this validator and, once it passes, immediately trusts `request.shop` as the tenant identity, forwarding it into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

Because the HMAC only binds the raw JSON body, an attacker who is a legitimate app-installing merchant (shop A) can capture a real, validly-signed webhook that Shopify delivers to their own endpoint (body + `x-shopify-hmac-sha256` unchanged), and resend the identical body/HMAC pair to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop (shop B). The signature check still passes — the body and HMAC are byte-for-byte legitimate — but `request.shop` now returns the attacker-chosen value. The handler then processes shop-A-origin data (e.g., order/customer content) under shop B's identity, since `WebhookMetadata.shop` is the only tenant binding most apps use to route data into per-shop storage or to select which shop's access token to act with.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: the field the app treats as the authenticated identity (`shop`) is not the field actually covered by the cryptographic proof (`raw_body` + `hmac`). This enables cross-tenant data injection/misattribution — an attacker-controlled shop can inject or misdirect webhook data into another merchant's tenant context inside the host application, which is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is realistic for any unprivileged internet user who can install the app as their own shop (a normal, unprivileged merchant signup) and capture the webhook Shopify legitimately sends them. No possession of `api_secret_key`, access tokens, or privileged accounts is required — only replaying a self-received request with one header edited, since the header is excluded from the signed payload by design of `to_signable_string`.

### Recommendation
Bind the shop domain (and other identity-relevant headers such as `api-version`/`webhook-id` if used for authorization decisions) into the signable string used for HMAC verification, or independently verify the header-derived `shop` against a shop value contained within the verified JSON body before using it as a tenant key. At minimum, document that `request.shop` is unauthenticated and must not be used by consuming apps as the sole tenant-routing key without corroboration from a signed source.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`. Shopify sends a real webhook to the app's endpoint with body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (owner/operator of shop-a) intercepts this request (it is delivered to an endpoint they control/observe) and replays it to the same app endpoint, keeping body `B` and the HMAC header identical, but changing `x-shopify-shop-domain` to `shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — unchanged since only the body is signed — and the check in [5](#0-4)  passes.
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-supplied `shop-b.myshopify.com`, per [6](#0-5) , and the app's handler processes shop-a's data under shop-b's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
