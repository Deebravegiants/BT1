### Title
Truncated ERC20→local decimal conversion in `pallet-hyper-fungible-token` silently burns dust on every cross-chain transfer and refund — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs` performs a raw integer division to scale an incoming ERC20 `U256` amount down to the local (lower-decimal) asset balance, with no remainder/precision check analogous to `BandwidthManager`'s `PriceNotRepresentable()` guard. This is the same bug class as the C4 M-06 finding: a rate/amount conversion is "not accurate enough" for the full range of token decimal combinations, silently rounding down instead of reverting or accounting for the dust, so value is discarded rather than delivered or refunded.

### Finding Description
`convert_to_balance` divides the ERC20 amount by `10^(erc_decimals - local_decimals)` and truncates: [1](#0-0) 

Registration enforces `config.decimals >= local_decimals` (`ErcDecimalsBelowLocal`), so the exponent never underflows, but nothing enforces that the ERC20 amount is an exact multiple of `10^(erc_decimals - local_decimals)`: [2](#0-1) 

`on_accept` (inbound mint/transfer) and `on_timeout` (refund) both call `convert_to_balance` and then move/mint exactly the truncated `amount` — the sub-unit remainder of the original ERC20 value is simply discarded, with no error, no partial credit, and no event reflecting the loss: [3](#0-2) [4](#0-3) 

Contrast this with `BandwidthManager.purchase()`, which performs the analogous 18-decimal→fee-token-decimal scaling but explicitly reverts with `PriceNotRepresentable()` if the division isn't exact, rather than silently under-crediting: [5](#0-4) 

The HFT pallet has no such guard. A sender on the EVM side (an unprivileged party dispatching `HyperFungibleToken.send`) can supply any `U256` amount; on arrival at `on_accept` (or on timeout-driven refund), any sub-`10^(erc_decimals-local_decimals)` remainder of that amount is silently dropped when scaling to the local asset. Because `erc_decimals` can exceed `local_decimals` by many orders of magnitude for legitimately configured pairs (e.g. an 18-decimal EVM token bridged to a low-decimal Substrate asset), this dust is not a rounding artifact of one wei — it's a systematically discardable fraction of the transfer, and it recurs on every single transfer and every timed-out refund.

### Impact Explanation
Every inbound message and every refund permanently and silently destroys the truncated remainder of the bridged value — value that was locked/burned on the source chain (in `send()`, scaled up via `convert_to_erc20`, which is lossless since it always multiplies) but never fully returned or credited on the destination chain. This is a permanent, protocol-level loss-of-funds bug reachable by any ordinary user who calls `send()` with an amount that doesn't align to the destination asset's decimal granularity, or whose message times out. Because the loss happens on the accounting/minting path itself (not a UI display issue), it constitutes an unbacked-value discrepancy between what was escrowed/burned on the source side and what is minted/released on the destination side.

### Likelihood Explanation
High. No privileged role is required — an ordinary sender can trigger this on virtually any transfer whose amount isn't an exact multiple of the decimal-scaling factor, which for large decimal deltas (registrations only require `erc_decimals >= local_decimals`, with no upper bound) is the common case rather than the edge case. Refund-on-timeout doubles the exposure since the same lossy conversion runs again.

### Recommendation
Add an explicit "amount not representable at local precision" check in `convert_to_balance` (mirroring `BandwidthManager`'s `PriceNotRepresentable()` revert), and either reject the transfer amount at `send()` time before scaling to ERC20 units, or preserve/refund the truncated remainder in `on_accept`/`on_timeout` rather than discarding it.

### Proof of Concept
1. Register a token pair where `erc_decimals = 18` and `local_decimals = 6` (satisfies `config.decimals >= local_decimals`).
2. From the EVM side, dispatch a `Message` to `pall_hft` with `amount = 1_000_000_000_000_500_000` (i.e., `1.0000000000005` in 18-decimal terms — not an exact multiple of `10^12`).
3. `on_accept` calls `convert_to_balance(amount, 18, 6)`, computing `amount / 10^12 = 1_000_000` (truncating the `500_000` remainder) and mints/transfers exactly `1_000_000` local units to the beneficiary — the `0.0000000000005` fractional ERC20 value is permanently lost with no event or error.
4. Repeat with a timeout scenario: the same truncation occurs in `on_timeout`, so even the refund path returns less than what was originally escrowed on the source chain via `convert_to_erc20`, leaving a permanent shortfall in the pallet's custody/mint accounting.
