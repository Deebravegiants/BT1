### Title
User-centric signup bypasses backend enrollment/dedup authorization check performed by `enroll_user::Plan` - ([File: src/plans/mod.rs])

### Summary
In `MasterPlan::do_signup`, the orb determines whether a signup succeeds via two structurally different code paths depending on `user_centric_signup` (a boolean sourced from backend-supplied `authenticated_app_data`). The standard path calls `enroll_user()`, which performs an authoritative `signup_post`/`signup_poll` round-trip to the backend — the backend is the entity that actually decides whether the signup is accepted (it explicitly checks for "Backend duplicates," "Backend inflight matches," and "Backend detected fraud"). The user-centric path skips this backend round-trip entirely and instead derives `success` purely from the orb-local `signup_reason` value.

### Finding Description
`do_signup` computes `signup_reason` locally from the biometric pipeline result and `detect_fraud()`: [1](#0-0) 

It then branches on `user_centric_signup`: [2](#0-1) 

- Non-user-centric path: calls `self.enroll_user(...)`, which invokes `enroll_user::Plan::run`, which POSTs to `signup_post::request` and polls `signup_poll::request` in a retry loop, and only reports success if the **backend** confirms completion: [3](#0-2) 
The comment on the failure branch makes explicit that this backend round-trip is the authoritative gate against duplicates/inflight matches/backend fraud detection: [4](#0-3) 

- User-centric path: `success` is set to `signup_reason == SignupReason::Normal` with **no call to `enroll_user`, no `signup_post`, no `signup_poll`** — i.e., the backend's authoritative duplicate/fraud/uniqueness check is never invoked: [5](#0-4) 

Critically, in this build all local fraud checks are stripped (`N_FRAUD_CHECKS = 0`, `detect_fraud` always returns `false`), so `signup_reason` will almost always resolve to `SignupReason::Normal` whenever the biometric pipeline produced output: [6](#0-5) [7](#0-6) 

This exactly mirrors the JUSDBank bug class: one code path (`borrow`, here `enroll_user`) enforces the authoritative safety/limit check via the backend, while a second, parallel code path (`withdraw`, here the `user_centric_signup` branch) is reachable and completely bypasses that same check, even though it performs the equivalent state-changing action (marking the signup as successful, having already uploaded the personal-custody package to the backend at lines 599–636).

Note: `user_centric_signup` is populated from the backend's own `authenticated_app_data.user_centric_signup` field returned during user QR-code validation, so it is nominally "backend-controlled" data, not a raw value forged by an unprivileged operator/user in the current request. This is the one point of uncertainty in this analog: the analysis could not confirm from the indexed code alone whether an ordinary (unprivileged) app/user session can cause the backend to set `user_centric_signup = true` for itself and whether that is intended per-app/session behavior or a value that a malicious client could otherwise influence. The relevant `ignore_user_centric_signups` config exists in `src/config.rs` (only partially visible in the index) as an apparent operator-side kill-switch for this exact bypass, which supports that this branch is recognized internally as an alternate, weaker enforcement path.

### Impact Explanation
If an unprivileged user/app session can reach the `user_centric_signup = true` branch, the orb will locally mark a signup as successful — and the biometric data (iris/face packages) will already have been uploaded via `build_pcp`/`data_uploader` at this point — without the backend ever running its authoritative duplicate-signup or backend-side fraud check that the normal path relies on. This can result in multiple/duplicate World ID enrollments for the same iris being accepted by the orb as "successful" locally, and/or signups being locally attributed as legitimate ("Normal") that the backend would otherwise have rejected as duplicate/fraudulent, i.e. unauthorized or misattributed signup state — directly analogous to the systemic-risk bypass in the reported bug.

### Likelihood Explanation
Reaching this branch does not require any hardware access, malicious peer/operator, or dependency bug — it is a standard, always-live code path in `do_signup` gated only by a boolean sourced from backend user-status data and an orb config flag (`ignore_user_centric_signups`). Given that all local fraud checks are compiled out in this FOSS build (`N_FRAUD_CHECKS = 0`), `signup_reason` collapses to `Normal` in essentially all completed-pipeline cases, making the bypass condition trivially satisfied whenever `user_centric_signup` is true and `ignore_user_centric_signups` is false (its default is unverified from the available index).

### Recommendation
Always route signup finalization through the authoritative backend check (`enroll_user`/`signup_post`/`signup_poll`), regardless of `user_centric_signup`. If the user-centric flow needs a different backend contract, ensure it still performs an equivalent server-side duplicate/fraud verification step before `result.success`/`debug_report.enrollment_status` is set to success, rather than deriving success purely from the orb-local `signup_reason`.

### Proof of Concept
1. Complete a biometric capture/pipeline such that `pipeline.is_some()` and `detect_fraud()` returns `false` (guaranteed in this build since `N_FRAUD_CHECKS = 0`), yielding `signup_reason = SignupReason::Normal`. [1](#0-0) 
2. Have the backend-provided `user_status::UserData.user_centric_signup` be `true` for the session (and orb config `ignore_user_centric_signups = false`).
3. `do_signup` reaches: [5](#0-4) 
and sets `success = true` without ever calling `enroll_user`, hence without any `signup_post`/`signup_poll` round trip that would let the backend reject the signup as a duplicate or fraud match.
4. `result.success` is set from `debug_report.enrollment_status`, which was just set to `Success` locally at step 3: [8](#0-7)
