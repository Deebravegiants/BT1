### Title
Stale `account.owner` snapshot authenticates the previous NFT holder, letting a seller keep spending authority after transferring the position — (File: contracts/controller/src/account.rs)

### Summary
The controller authenticates account spending calls (`borrow`, `withdraw`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `flash_position`, `migrate_from_blend`) against `account.owner`, the address captured once at NFT mint in `create_account` (`account.rs:64-65`). True ownership, however, lives in the position-NFT contract and is read live only by `require_account_owner` via `storage::account_owner` (`account.rs:145`). Like the Bot Connector bug (GHSA-qxx8-292g-2w66), where a crafted claim was incorrectly authenticated, here an *expired* claim — the seller's address still recorded in `account.owner` — is incorrectly accepted as spending authority after `position-nft::transfer` moves the account to a buyer.

### Finding Description
`create_account` mints the NFT to `owner` and stores `owner` inside the in-memory `Account` struct (`account.rs:62-70`). Every mutating position flow calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`debt.rs:43`, and per `permissionless_entrypoints.txt` lines 49-56 the same guard covers `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`). `is_owner_or_delegate` returns `true` whenever `caller == owner` (`account.rs:121-122`) — where `owner` is the *stored* field, not the current NFT holder.

The position-NFT's stock `transfer`/`transfer_from` move the token without any callback into the controller, so nothing rewrites `account.owner`. The codebase itself acknowledges the split: `require_account_owner` (used by `add_delegate`, `remove_delegate`, `renew_account`) deliberately re-reads `storage::account_owner` rather than trusting `account.owner` (`account.rs:143-146`), and the permissionless manifest notes that after a transfer "delegate grants from the previous owner go inactive" — delegates are keyed by `(account_id, owner)` (`account.rs:126`), so the *new* owner has no delegates, but the *old* owner still passes the `caller == owner` branch.

Result: after selling/transferring the account NFT, the seller's address remains a fully authenticated spender on the account.

### Impact Explanation
Theft of user funds. A seller lists or transfers an account NFT holding collateral (and possibly borrow headroom); the buyer takes ownership via `transfer`/`transfer_from` and can even deposit additional collateral. The seller then calls `controller::borrow(account_id, borrows, to=seller)` or `controller::withdraw` — `require_owner_or_delegate` accepts `caller == account.owner` (the seller) — and drains collateral up to the health-factor floor, to any `to` recipient (`debt.rs:45-47`), leaving the buyer's account insolvent or stripped. Seized-collateral receivers in `liquidate` use the same stale check (`resolve_seize_receiver`, `liquidation/mod.rs:180`).

### Likelihood Explanation
Any unprivileged address can execute it: the attack path is `position-nft::transfer` (or an OTC/secondary-market sale) followed by the seller calling `borrow`/`withdraw`. It requires only that the victim acquire an account NFT — which is the designed mechanism for moving accounts — making secondary-market or gift transfers the exposure trigger. No flash loan, privileged role, or oracle manipulation is needed.

### Recommendation
Derive spending authority from live NFT ownership, not the stored field: in `is_owner_or_delegate`/`require_owner_or_delegate`, resolve `owner` via `storage::account_owner(env, account_id)` (as `require_account_owner` already does), or resync `account.owner` in `storage::get_account`. Alternatively, have the controller subscribe to NFT transfer semantics by re-stamping `account.owner` on first touch, and add a regression test that transfers the NFT and asserts the previous owner can no longer `borrow`/`withdraw`.

### Proof of Concept
1. Alice calls `controller::supply` with `account_id = 0`; `load_or_create_account` creates account `A` with `owner = Alice` and mints NFT `A` to Alice (`account.rs:95-96, 63-65`). Alice supplies collateral.
2. Alice transfers NFT `A` to Bob via `position-nft::transfer` (stock OZ path; no controller hook rewrites `account.owner`).
3. Bob supplies additional collateral to `A` — allowed permissionlessly for existing slots (`permissionless_entrypoints.txt:69`).
4. Alice calls `controller::borrow(caller=Alice, account_id=A, borrows=[...], to=Alice)`. `process_borrow` runs `Alice.require_auth()` (`debt.rs:40`), then `require_owner_or_delegate(env, A, Alice, &account.owner)` — `account.owner` is still `Alice`, so `caller == owner` passes (`account.rs:121`).
5. The pool disburses to `to = Alice` (`debt.rs:45, 109`); post-borrow solvency passes because Bob's collateral backs the debt. Bob's account is left leveraged/liquidatable; Alice repeats via `withdraw` for the residual collateral.

Caveat I could not fully verify within the search budget: whether `storage::get_account` silently re-syncs `account.owner` from the NFT on load (`contracts/controller/src/storage/account.rs` was not read in full). If it does, this finding collapses; the existence of the separate live-owner read in `require_account_owner` and the delegate-keying by stored owner strongly suggests it does not.
