### Title
Webhook shop attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the shop identity (`X-Shopify-Shop-Domain`), topic, and webhook id are read directly from unauthenticated headers and forwarded to the app's handler as trusted values. Since Shopify signs webhooks per-app (using the app's `client_secret`) rather than per-shop, any merchant who has the app installed on their own store can obtain a validly-signed webhook body and replay it with a forged `shop-domain` header attributing the event to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The shop, topic, and webhook id are read straight from headers and are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC only against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` checks only this body HMAC, then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The binding that should hold is: `shop credited to the webhook == shop whose data actually produced the signed body`. Because the HMAC secret (`Context.api_secret_key`) is the app's `client_secret`, shared across every shop that installs the app, and the signature covers only the body bytes, any shop with the app installed can produce a body+HMAC pair that is valid for the endpoint. That body can then be replayed with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header, and `Registry.process` will accept it as coming from any shop the attacker names, since none of those header fields are checked against the signature.

### Impact Explanation
This breaks the shop-authentication boundary the gem is documented to provide ("This will verify the request did indeed come from Shopify" — see `docs/usage/webhooks.md`), which the host application reasonably interprets as covering shop attribution as well as body integrity. An attacker who is a legitimate, unprivileged merchant with the app installed on their own shop can trigger genuine webhook deliveries (e.g. by making changes in their own store, or replaying a captured delivery) and then re-send the request to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Because `WebhookMetadata.shop` is trusted downstream, the app can be made to process attacker-crafted data (order/customer/app-lifecycle payloads) under a victim tenant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
Any merchant who can install the target app (a normal, unprivileged action) can obtain a validly-signed webhook body for that app's shared secret and replay it with a modified shop header; no access to `api_secret_key`, tokens, or privileged accounts is required, and the header rewrite is trivial for anyone who controls the HTTP request to the app's own webhook route.

### Recommendation
Bind the identity fields to the signature, or independently verify shop attribution before trusting it: e.g., include the shop domain/topic in the signable payload, or require the receiving app to cross-check `request.shop` against a shop that is known to have this webhook/topic registered (e.g. via a stored, per-shop mapping) before invoking the handler, rather than passing header-derived values straight through as authenticated.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger (or otherwise obtain) a legitimate webhook delivery for topic `customers/update` with body `B`; Shopify computes `HMAC(client_secret, B)` and sends it with header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture the request and resend it to the app's webhook endpoint with the same body `B` and the same (still valid) HMAC header, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` line 190 validates only the body HMAC (`Utils::HmacValidator.validate(request)`), which still passes because the body and signature are unchanged.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)`, causing the app to process attacker-supplied data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
