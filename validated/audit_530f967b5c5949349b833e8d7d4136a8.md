## Finding: Webhook Identity Confusion — `shop`/`topic` Fields Not Covered by HMAC in `ShopifyAPI::Webhooks::Request`

### Title
Webhook Shop/Topic Spoofing via HMAC Scope Mismatch - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by checking only the HMAC over the raw body, yet the `shop` and `topic` values it hands to the app's handler come from unauthenticated headers that are not part of the signed payload. Since the API secret used to sign webhooks is the app-level `client_secret` shared across every shop that installs the app, any merchant who has installed the app can capture a legitimate `(body, hmac)` pair from their own webhook deliveries and replay it against the app's public webhook endpoint with a forged shop-domain/topic header, causing the receiving app to attribute attacker-controlled data to a victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — `shop`, `topic`, and `webhook_id` are read straight from headers and are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then immediately trusts `request.shop` and `request.topic` (both unauthenticated header values) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding broken here is:
`shop authenticated (bytes covered by HMAC = body only)` ≠ `shop acted upon (data.shop, used by the handler for tenant routing/storage)`.

Because `Context.api_secret_key` is the single app `client_secret` shared by all installations (it is not a per-shop secret — see `HmacValidator.validate` using the same `Context.api_secret_key`/`old_api_secret_key` regardless of shop), a valid `(body, hmac)` pair captured from any one merchant's own genuine webhook traffic remains cryptographically valid HMAC-wise no matter which `shop-domain`/`topic` header accompanies it on replay. The library's own documentation reinforces the false guarantee, stating that `process` "will verify the request did indeed come from Shopify": [4](#0-3) 

In reality it only verifies that the *body bytes* were signed by the app's shared secret at some point — not that the accompanying `shop`/`topic` headers are legitimate for that body, nor that the request actually originated from Shopify.

### Impact Explanation
An unprivileged internet user who is merely a legitimate, low-privileged customer of the app (i.e., any merchant who installs the app, which requires no special trust) can:
1. Capture one authentic `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to their own webhook endpoint for their own shop.
2. Replay that exact body/HMAC pair to the app's shared, publicly reachable webhook endpoint while spoofing `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to name a victim shop.
3. Because `Registry.process` treats HMAC success as full authentication of the request, the forged `shop`/`topic` are passed straight to the handler as trustworthy, causing the app to ingest/act on attacker-supplied data under a victim tenant's identity — a cross-tenant data-integrity/access breach.

### Likelihood Explanation
This requires only becoming a merchant/installer of the target app (an ordinary, unprivileged action) and the ability to POST to the app's already-public webhook URL — no access token, `client_secret`, or privileged account is needed. The library performs no source validation or shop/topic binding beyond the body HMAC, so exploitation depends solely on the app following the documented `Registry.process` contract, which itself is misleading about what is actually verified.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the specific installation/session the app already has on file (e.g., reject webhooks whose `shop-domain` doesn't match an actively-installed shop, and never treat header-derived `shop`/`topic` as authenticated purely because the body HMAC matched). Update `to_signable_string` in `Webhooks::Request` and the documentation in `docs/usage/webhooks.md` to make clear that only the raw body is verified, so consuming apps don't conflate this with full request authentication.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger an event (e.g. `orders/create`) so Shopify delivers a webhook to the app's shared endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC_SHA256(client_secret, B)`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture `(B, H)` from network logs/proxy on attacker's own infrastructure.
4. POST to the same public webhook path with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because `to_signable_string` only depends on `B`), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` succeeds (line `lib/shopify_api/utils/hmac_validator.rb:26-31`), `Registry.process` calls the handler with `WebhookMetadata`'s `shop` field set to `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process/store attacker-supplied data under the victim tenant.
