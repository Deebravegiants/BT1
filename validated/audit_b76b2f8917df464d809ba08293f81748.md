Based on the analysis, `EvmHost.dispatch(DispatchPost)` (and the `DispatchGet` variant) accepts caller-supplied `post.dest` and `post.payer` fields with no sanity checks before creating an irrevocable commitment, directly analogous to the Connext `xcall()` finding.

### Title
Missing sanity checks in `EvmHost.dispatch()` allow permanent loss of relayer-fee refunds and self-addressed dispatches - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost memory post)` and its `DispatchGet` counterpart accept a caller-controlled `payer` and `dest` field and use them unchecked to build the `FeeMetadata` refund record and the outgoing request, mirroring the Connext `xcall()` issue where `_args.recovery == 0` or `_args.params.destinationDomain == s.domain` were never validated.

### Finding Description
`dispatch(DispatchPost memory post)` stores `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` without ever checking `post.payer != address(0)` [1](#0-0) . This `sender` field is later used exclusively as the refund destination for timed-out requests in `dispatchTimeOut(PostRequestTimeout ...)`: `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);` [2](#0-1) . If `post.payer` is `address(0)` (either by caller error, or because an integrating contract forwards an unvalidated `payer`/`msg.sender` field, e.g. `HyperApp.dispatchWithFeeToken()` which just copies `request.payer` [3](#0-2) ), any relayer-fee refund on timeout is sent to the zero address via `safeTransfer`, permanently burning the fee tokens.

Separately, `dispatch()` never validates `post.dest != host()` (the local domain identifier), which is the analog of `_args.params.destinationDomain != s.domain`. Nothing in `EvmHost.dispatch()` or `HandlerV2` prevents a user from dispatching a request whose `dest` equals the local state machine id; the request would simply be encoded, fee-collected, and committed, but could never be correctly delivered/relayed back into the same chain through the normal cross-chain path, since delivery is via `HandlerV2.handlePostRequests` verifying a foreign state commitment [4](#0-3) . Funds/fees committed to such a request become effectively stuck until timeout (if any) — and with `timeout == 0` they never time out at all, permanently locking the relayer fee in the contract's accounting with no way to reclaim it via `dispatchTimeOut`.

### Impact Explanation
This is High severity because it results in concrete, permanent loss of user/protocol funds (relayer fees) with no recovery path — analogous to the Connext report's "funds sent to the 0 address are lost" and "funds locked forever" cases. Any application built on top of `IDispatcher.dispatch()` that forwards a caller-supplied `payer` (or fails to default it to `msg.sender`) can trigger silent fee-burning on timeout.

### Likelihood Explanation
Likelihood is Medium-High: `payer` and `dest` are plain fields on a `memory`/`calldata` struct passed by any external caller (EOA or contract) to a permissionless `dispatch()` entrypoint; no additional privilege is required, and simple integration mistakes (or malicious front-ends) can supply `address(0)` as `payer` or the local state machine id as `dest`.

### Recommendation
Add the following checks at the top of `dispatch(DispatchPost memory post)` and `dispatch(DispatchGet memory get)` in `evm/src/core/EvmHost.sol`:
- `require(post.payer != address(0))` / `require(get.payer != address(0))`.
- `require(!post.dest.equals(host()))` (reject dispatching to self, mirroring `_mustHaveRemote()`-style destination checks already used on the receive side in `HandlerV2.handlePostRequests`).

### Proof of Concept
1. Call `IDispatcher(host).dispatch(DispatchPost({dest: someRemoteChain, to: ..., body: ..., timeout: 3600, fee: someFee, payer: address(0)}))` directly (bypassing `HyperApp`, or via an integrator contract that forgot to set `payer: msg.sender`).
2. `_requestCommitments[commitment].sender` is stored as `address(0)` [1](#0-0) .
3. If the request times out and `handlePostRequestTimeouts`/`dispatchTimeOut` is invoked, `IERC20(feeToken()).safeTransfer(address(0), meta.fee)` is attempted [2](#0-1)  — for standard ERC-20 fee tokens this either reverts (soft-locking the timeout permanently, since `EvmHost` has no other path to clear `_requestCommitments[commitment]`) or, for tokens allowing zero-address transfer, burns the fee irrecoverably.
