### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then blindly forwards attacker-suppliable header values (`shop`, `topic`, `webhook_id`, `api_version`) to the host application's handler as authoritative metadata. None of these header-derived fields are covered by the signature, so the "shop that is cryptographically verified" and the "shop the handler acts on" are not the same value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` headers, handing them to the app's `WebhookHandler#handle`: [4](#0-3) 

`WebhookMetadata` documents `shop` as a trusted, authoritative field the host app is expected to use to identify which merchant/tenant the webhook payload belongs to: [5](#0-4) 

The identity binding that should hold is: `shop covered by the HMAC == shop the handler is told to act on`. In this implementation that equality does not hold — the HMAC only proves "this body was signed with our secret at some point", not "this body was delivered for shop X". Any party who can obtain one valid `(raw_body, hmac)` pair — for example an ordinary merchant using the app in their own store, who can trigger real webhook deliveries to their own endpoint and thus possesses genuinely valid `(body, hmac)` pairs signed with the app's `api_secret_key` — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to claim the payload belongs to a different (victim) shop. `Utils::HmacValidator.validate` will still pass because it never inspects those headers.

### Impact Explanation
This breaks the tenant boundary the gem's webhook API is supposed to guarantee to the host application: a request that passes `Registry.process`'s only cryptographic check can present `data.shop` for a tenant the request-sender does not control, letting the sender inject arbitrary attacker-influenced body content (any topic/body they can produce a valid signature for from their own store) attributed to another merchant's shop. Any host application that uses `WebhookMetadata#shop` as a bare tenant key (as the gem documents and its interface implies) is exposed to cross-tenant data injection/spoofing without needing the app's `client_secret`, access token, or any other credential — only the ability to have a real, unprivileged merchant account for the app.

### Likelihood Explanation
Any user who installs the app on their own (even free/dev) store can trigger real webhook deliveries and capture the corresponding body+HMAC pairs; replaying them against the same public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers requires no special access, no secret material, and no interaction with the merchant being impersonated. This makes the attack straightforward for any unprivileged internet user who is a legitimate app user in one tenant.

### Recommendation
Include the identity-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g. via a signed envelope, mutual TLS, or verifying the shop against a known-installed list plus re-fetching/confirming the webhook via the Admin API) before trusting `WebhookMetadata#shop` as a tenant identifier. At minimum, document explicitly and enforce in `Registry.process` that `shop`/`topic`/`webhook_id` are not authenticated by the HMAC and must be independently verified by the host app (e.g. cross-checked against the shop that owns the session/store used for delivery).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a real webhook (e.g. `orders/create`) from Shopify to the app's registered endpoint, capturing the raw POST body and the `x-shopify-hmac-sha256` header — this is a valid `(body, hmac)` pair signed with the app's real `api_secret_key`.
3. Attacker replays the exact same body and `hmac` header to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC only over the raw body, which still matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the host handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: request.topic, body: request.parsed_body, ...)` — data now falsely attributed to the victim shop, despite never being sent by or for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
