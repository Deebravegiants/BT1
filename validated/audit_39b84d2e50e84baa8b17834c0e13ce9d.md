### Title
Selector invalid-label-value carve-out uses a coarse boolean latch instead of per-value diffing, permitting unbounded injection of new invalid label values on update - ([File: staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/validation/validation.go])

### Summary
`LabelSelectorHasInvalidLabelValue` only reports whether *any* value anywhere in a `LabelSelector` is invalid, returning a single boolean rather than identifying which specific values are invalid. Callers use this boolean to set `opts.AllowInvalidLabelValueInSelector` for the entire update validation pass, so once any invalid value exists in the persisted object, `ValidateLabelSelectorRequirement` skips the invalid-value check for the *whole* selector on every subsequent update — not just the originally-invalid value.

### Finding Description
`ValidateLabelSelectorRequirement` (staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/validation/validation.go:78-103) skips `validation.IsValidLabelValue` checks entirely for all `sr.Values` when `opts.AllowInvalidLabelValueInSelector` is true: [1](#0-0) 

The helper meant to compute this opt from "existing persisted invalid values" is a global boolean scan with no correlation to which value is invalid or where: [2](#0-1) 

Update strategies for daemonset, job, and other selector-bearing resources call `metav1validation.LabelSelectorHasInvalidLabelValue(oldSelector)` to compute this opt when validating updates (confirmed usage in `pkg/registry/apps/daemonset/strategy.go` and `pkg/registry/batch/job/strategy.go`, and consumers in `pkg/apis/networking/validation/validation.go` and `pkg/apis/apps/validation/validation.go`). Because the function only returns a boolean (not a set/diff of the actually-invalid values), the resulting opt is a permanent, coarse-grained latch: as soon as the old object's selector contains one invalid value anywhere in any `matchExpressions[].values`, the entire selector's invalid-value validation is bypassed for the new object on that update call.

Attack flow: an unprivileged user with create+update RBAC on a selector-bearing resource (e.g., NetworkPolicy, DaemonSet, Job) creates the object with one invalid label value in `spec.selector.matchExpressions[].values`. On the subsequent update, `LabelSelectorHasInvalidLabelValue(oldSelector)` returns `true` because the old object still has that one invalid value, so `opts.AllowInvalidLabelValueInSelector` is set to `true` for validating the *entire new* selector. The user can therefore introduce any number of additional/different invalid values anywhere in the selector, since the check is entirely skipped rather than being limited to the specific pre-existing invalid value(s). Every subsequent update re-triggers the same latch as long as at least one invalid value remains (or is re-introduced), permitting unbounded injection of malformed selector values.

### Impact Explanation
This breaks validation totality for a persisted, RBAC-adjacent field: `LabelSelector` values are consumed by selector-matching logic across the codebase (NetworkPolicy podSelector/namespaceSelector, Deployment/DaemonSet/Job pod template selectors, etc.). Persisting attacker-controlled malformed values into these selectors risks downstream parsing/matching inconsistencies wherever `labels.Selector` machinery or client tooling assumes selectors satisfy `IsValidLabelValue`. This matches a "persisted invalid/protected field" class finding rather than a direct privilege escalation, since it does not itself bypass RBAC/authz — it bypasses field-level validation invariants.

### Likelihood Explanation
Minimal RBAC needed: standard namespaced create+update verbs on a selector-bearing resource (e.g., NetworkPolicy, DaemonSet, Job), which many ordinary users/serviceaccounts hold. The exploit requires only two ordinary API calls (create with one invalid value, then update) and is fully repeatable — the boolean latch persists as long as at least one invalid value remains in the object, so an attacker can keep swapping/adding invalid values indefinitely.

### Recommendation
Replace the boolean `LabelSelectorHasInvalidLabelValue` latch with a diff-based check that compares the new selector's invalid values against the old selector's invalid values on a per-value (or per-index) basis, exempting only values that already existed as invalid in the persisted object — never permitting introduction of new invalid values. This likely requires computing a set of previously-invalid values from the old object and checking each new value against that set inside `ValidateLabelSelectorRequirement`, rather than passing a single global boolean opt.

### Proof of Concept
Table-driven unit test in `staging/src/k8s.io/apimachinery/pkg/apis/meta/v1/validation/validation_test.go`:
1. Construct `oldSelector` with `matchExpressions: [{Key: "k", Operator: In, Values: ["bad value 1"]}]` (invalid due to space).
2. Construct `newSelector` with the same old invalid value plus a newly introduced invalid value, e.g. `Values: ["bad value 1", "bad value 2"]`.
3. Call `opts.AllowInvalidLabelValueInSelector = LabelSelectorHasInvalidLabelValue(oldSelector)` (expect `true`), then `ValidateLabelSelector(newSelector, opts, fldPath)`.
4. Assert (post-fix expectation): the result should contain a validation error for `"bad value 2"` (the newly introduced invalid value) while allowing `"bad value 1"` (the pre-existing invalid value) — i.e., `len(errs) == 1` referencing only the new value's index.
5. Current behavior (pre-fix, demonstrating the bug): `ValidateLabelSelector` returns `len(errs) == 0`, proving both the old and newly injected invalid values pass validation once any invalid value existed previously.

// LabelSelectorHasInvalidLabelValue returns true if the given selector contains an invalid label value in a match expression.
// This is useful for determining whether AllowInvalidLabelValueInSelector should be set to true when validating an update
// based on existing persisted invalid values.
func LabelSelectorHasInvalidLabelValue(ps *metav1.LabelSelector) bool {
	if ps == nil {
		return false
	}
	for _, e := range ps.MatchExpressions {
		for _, v := range e.Values {
			if len(validation.IsValidLabelValue(v)) > 0 {
				return true
			}
		}
	}
	return false
}
