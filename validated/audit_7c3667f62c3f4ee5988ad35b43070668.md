### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant event/shop spoofing on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read straight from HTTP headers that are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` then trusts these unauthenticated header values to route the request to a handler and to attribute the event data to a specific shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then uses the unauthenticated `request.topic` to select the handler and passes the unauthenticated `request.shop` straight into the data handed to the app's business logic: [3](#0-2) 

`Utils::HmacValidator.validate` only ever calls `verifiable_query.to_signable_string` to compute the expected signature, so any header not included in `to_signable_string` is functionally excluded from the integrity check: [4](#0-3) 

The identity binding broken here is: `shop header used to attribute/route the event` should equal `shop that Shopify actually signed the payload for`, but the gem only enforces `hmac(body) == valid`, leaving `shop_header` and `topic_header` completely free for the request sender to choose. An attacker who legitimately controls their own shop/store (an ordinary, unprivileged action — installing the app on a store they own, and triggering any webhook event on it) obtains a real, Shopify-signed `(raw_body, hmac)` pair for a body whose *content* they authored (e.g., a product title or order note containing attacker-controlled data). They can then submit an HTTP request directly to the app's public webhook endpoint using that exact `(raw_body, hmac)` pair, but substitute the `shopify-shop-domain` header with a victim shop's domain and/or the `shopify-topic` header with any topic the app has a handler for. Since neither field is covered by the signature, the app cannot distinguish this from a legitimate webhook for the victim shop, and `Registry.process` will hand the attacker-authored body to the handler tagged with the victim's shop domain and the attacker-chosen topic.

### Impact Explanation
This breaks the shop-tenant boundary that Shopify apps rely on to keep per-shop data isolated (`WebhookMetadata.new(topic:, shop:, body:, ...)` is built entirely from unauthenticated fields except body). In a multi-tenant SaaS app that persists or acts on webhook data keyed by `shop`, an attacker can inject fabricated, attacker-controlled event data attributed to any other installed shop, and can also re-route their own signed payload to an arbitrary registered topic handler (e.g., feeding order data into a `customers/redact` handler or vice versa). This is a cross-tenant data-integrity/confusion vulnerability reachable by any unprivileged user who can install the app on a store they control — no access token, `client_secret`, or privileged account for another tenant is required.

### Likelihood Explanation
Moderately likely: it requires the attacker to have a working relationship with the app (their own store/install, which is trivial to obtain for any app that supports a public/dev store install) and knowledge of the app's public webhook endpoint (typically documented/predictable, e.g. `/webhooks`). No secrets or credentials belonging to Shopify or the victim are needed — only replay of a body+hmac pair the attacker legitimately received for their own shop, with modified headers.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values in the value that is HMAC-verified (or otherwise cryptographically bind them, e.g. verify them against metadata independently retrievable from Shopify per delivery, or require a signed envelope covering headers+body), so header substitution invalidates the HMAC. At minimum, document that consuming apps must not treat `shop`/`topic` as authenticated without additional verification (e.g., cross-checking against a known/installed-shop list), and consider validating `request.shop` with `Utils::ShopValidator` combined with a check that the shop is actually installed for the topic being processed.

### Proof of Concept
1. Attacker installs the app on their own test shop `attacker-shop.myshopify.com` (ordinary unprivileged action).
2. Attacker triggers a real webhook event (e.g., `products/update`) on their shop with attacker-chosen product data in the body. Shopify computes and sends `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>` together with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and `X-Shopify-Topic: products/update` to the app's webhook endpoint.
3. Attacker captures this exact `(raw_body, hmac)` pair (e.g. by pointing the webhook subscription at a proxy they control, or by inspecting their own network egress since it is a request destined to a URL that ultimately routes to the app).
4. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body's HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) routes to the handler for the spoofed topic and passes `shop: "victim-shop.myshopify.com"` with the attacker-authored body, causing the app to process attacker-controlled data as if it belonged to the victim shop.
