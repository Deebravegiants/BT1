### Title
Permanent market freeze from RAY-value overflow in interest accrual before the borrow-index cap engages - (File: common/src/rates/compound.rs, used by contracts/pool/src/interest.rs)

### Summary
The CVE bug class is an unprivileged remote-triggered crash/DoS. The analog in XOXNO Lending is a permanent, protocol-wide denial of service on an entire market: once accrued debt value crosses the `i128` RAY-value ceiling inside `accrue_step`, every subsequent accrual panics with `GenericError::MathOverflow`. Since every pool verb accrues first (`global_sync` in `contracts/pool/src/interest.rs:20-33`), the market freezes permanently — no `repay`, `withdraw`, `borrow`, `liquidate`, or `clean_bad_debt` can execute for that (hub, token) book.

### Finding Description
`accrue_step` (invoked per chunk in `contracts/pool/src/interest.rs:39-53` via `global_sync`) grows the borrow index and computes `scaled_to_original(borrowed, borrow_index)` in RAY precision. The repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) proves the failure mode end-to-end:

- At ~98% utilization on a steep utilization-curve segment, the borrow index compounds past ~170× within the modeled horizon, and `scaled_to_original` overflows `i128` before `MAX_BORROW_INDEX_RAY` ever engages (asserted at lines 349-353: `last.borrow_index < MAX_BORROW_INDEX_RAY`).
- After the panic, `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` (lines 355-356), confirming the freeze propagates to every entrypoint because accrual runs first.
- The panic is deterministic and permanent: accrual is recomputed from stored `last_timestamp` each call, so the overflowing state is re-derived every time — there is no recovery path, and no admin/governance verb listed in scope bypasses accrual.

The state needed is reachable entirely through unprivileged calls: `supply` a large principal (whale-scale, e.g., 1e9 whole tokens at 18 decimals as in the test), then `borrow` to push utilization to ~98% on a market whose interest-rate curve has a steep high-utilization segment (the test uses the XLM curve). `update_indexes` can be called by anyone to advance accrual. No privileged input is required — only capital and a steep-curve market, both of which are legitimate protocol configurations.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate for the affected market: all supplier principal and yield in that market become unwithdrawable, all borrower collateral in correlated positions cannot be unwound through that market, liquidations cannot execute (so the market simultaneously becomes insolvency-exposed), and `clean_bad_debt`/`recapitalize` paths that touch the market's accrual also trap. Unlike a transaction-level revert, this is a state-level deadlock with no in-scope remediation verb.

### Likelihood Explanation
Likelihood is constrained but non-trivial. It requires (a) a market configured with a steep high-utilization rate curve — the XLM curve in the repo's own configuration qualifies; (b) whale-scale supply so absolute debt value in RAY units approaches `i128` (~1e38, i.e., debt value approaching 1e11 whole tokens at RAY precision after index multiplication); and (c) sustained near-max utilization over an extended period. The harness test demonstrates the sequence is mechanically reachable through ordinary `supply`/`borrow`/`update_indexes` calls; the cost is capital plus time, not privilege. The index cap that appears designed to prevent exactly this fails to engage because the value multiplication overflows earlier — a genuine ordering defect rather than a documented trade-off (the test itself notes the documented bound "is wrong").

### Recommendation
Enforce the `MAX_BORROW_INDEX_RAY` cap *before* computing `scaled_to_original` inside `accrue_step` — i.e., clamp `borrow_index` to the cap and compute accrued value against the clamped index, or short-circuit accrual once the index is saturated so that the market degrades to zero-rate instead of trapping. Alternatively, perform the debt-value multiplication in a checked/widened path that clamps to `i128::MAX` rather than panicking, so `global_sync` remains a no-op-safe operation and all downstream verbs continue to settle. The fix must guarantee `global_sync` can never panic on legitimately reachable stored state, since it gates every market verb.

### Proof of Concept
The repo's own harness test is a ready-made PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`):

1. `LendingTest::new().with_market(big("BIG18", 18, xlm_curve())).with_market(col()).with_max_utilization_disabled_all_markets().build()`
2. `lift_caps(&t, "BIG18", 18)`; `t.supply_raw(BOB, "BIG18", 1e9 * 10^18)` — unprivileged `supply`.
3. `t.supply_raw(ALICE, "COL", ...)` then `t.borrow_raw(ALICE, "BIG18", principal * 98 / 100)` — pushes utilization to 98%.
4. Loop `t.advance_time(YEAR_SECS)` + `t.update_indexes` (callable by anyone) until `try_update_indexes_for(&["BIG18"])` returns `MathOverflow` — index below `MAX_BORROW_INDEX_RAY`, proving the cap never engaged.
5. Assertions confirm the freeze: `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MathOverflow` — funds permanently locked.

Caveat: I verified the failure path and its reachability primarily through the existing harness test and the accrual plumbing in `contracts/pool/src/interest.rs` and `contracts/pool/src/cache/scale.rs`; I did not fully trace `accrue_step`'s internals in `common/src/rates/compound.rs` to pinpoint the exact overflowing line, so the precise fix location within `accrue_step` is inferred rather than confirmed.
