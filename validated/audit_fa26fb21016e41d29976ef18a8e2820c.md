### Title
User-Controlled `user_centric_signup` Flag Bypasses Backend Duplicate/Uniqueness Enforcement, Enabling Repeated Successful Signups - (File: src/plans/mod.rs)

### Summary
The external report's root cause is the removal of a mechanism that verifies historical/authoritative state before treating an action as valid, which permits the same actor to be double-counted (double voting) because the local/immediate view of state is trusted instead of consulting the canonical uniqueness ledger. The closest analog in `orb-core` is the `user_centric_signup` code path in `MasterPlan::enroll_user`, where the orb skips calling the backend's `enroll_user` (which performs the canonical duplicate/uniqueness check against `signup_post`/`signup_poll`) and instead locally marks the signup as `Success` whenever the pipeline’s local `signup_reason == SignupReason::Normal`.

### Finding Description
In the normal flow, `do_signup` calls `self.enroll_user(...)`, which posts to the backend (`signup_post::request` / `signup_poll::request`) and only returns `Status::Success` after the backend confirms uniqueness, explicitly noting that failures include "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" [1](#0-0) . This backend round-trip is the orb-core equivalent of the "historical snapshot" check the external report says was removed from the token contract — it is the authoritative source that prevents the same identity from being counted as enrolled more than once.

However, when the `UserData.user_centric_signup` flag (sourced from `user_status::request`, which is derived from app/QR-submitted `authenticated_app_data`) is `true`, and the orb config `ignore_user_centric_signups` is `false` (its default posture), the orb takes a different branch: it sets the enrollment status directly from the locally computed `signup_reason` without ever invoking `enroll_user` / contacting the backend duplicate-check endpoint:

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
``` [2](#0-1) 

`user_centric_signup` itself originates from data returned by the app/backend session status call and is threaded through as part of the QR-derived `UserData` without any local, orb-side idempotency or uniqueness check of its own [3](#0-2) . In this mode, the orb never asks `signup_post`/`signup_poll` — the component explicitly responsible for detecting "Backend duplicates" and "Backend inflight matches" — whether this particular biometric/user is already enrolled; it simply trusts that the app-side/backend-side flow already handled deduplication elsewhere, and reports local pipeline success as final success.

This mirrors the reported bug class: removal (or bypass) of the canonical, state-tracking uniqueness check in favor of trusting an immediate/local signal, opening a path for the same identity to be signed up (or reported as successfully enrolled) more than once if the assumption that "the app/backend already deduplicated" does not hold for every code path that can set this flag.

### Impact Explanation
If the `user_centric_signup` bypass is reachable with stale, replayed, or manipulated QR/session data, the orb-side success determination no longer depends on the backend's authoritative duplicate/inflight-match check [4](#0-3) . This could let a user complete multiple "successful" biometric signups (cross-signup state bleed / misattributed signup outcome) without the orb itself ever detecting or blocking the duplicate, since the only enforcement point (`enroll_user`) is skipped entirely in this branch [5](#0-4) .

### Likelihood Explanation
Likelihood is moderate and gated by two conditions that must both be true: (1) `ignore_user_centric_signups` must be `false` (its apparent default intent, since the flag exists precisely to force the legacy backend-verified path when needed) [6](#0-5) , and (2) the QR/session data must set `user_centric_signup = true` for the given session [7](#0-6) . Because this flag is app/backend-controlled data flowing through the user QR/session validation path rather than a hardware- or operator-privileged boundary, it falls within the unprivileged-user-controlled surface. I was not able to fully verify (due to index limits) whether the backend independently re-validates uniqueness out-of-band in this mode, which would mitigate — but not eliminate — the orb-side gap.

### Recommendation
Do not treat local pipeline success (`SignupReason::Normal`) as authoritative for final enrollment success when `user_centric_signup` is set. Even in the user-centric path, perform (or require the backend to perform, with an orb-side verification round trip) an explicit uniqueness/inflight check equivalent to what `enroll_user`/`signup_post`/`signup_poll` already implement, before reporting `Status::Success` and before uploading the Personal Custody Package tiers [2](#0-1) .

### Proof of Concept
Concrete exploitation could not be fully demonstrated from static analysis alone (the backend-side dedup semantics for the `user_centric_signup` path are external to this repo and not available in the index). The conceptual PoC is:
1. Attacker-controlled or replayed app QR/session data sets `authenticated_app_data.user_centric_signup = true` for a session tied to an already-enrolled identity [8](#0-7) .
2. Orb completes biometric capture/pipeline locally with `SignupReason::Normal` (no orb-detected fraud), which is possible independent of whether the identity was previously enrolled, since fraud detection here is about capture-time liveness/fraud, not global uniqueness [9](#0-8) .
3. `enroll_user` is skipped and `Status::Success` / signup success is set purely from the local `signup_reason`, without any backend duplicate/inflight check ever executing [2](#0-1) .
