### Title
Undefined behavior from `String::from_utf8_unchecked` on attacker-controlled ISMP request body - (File: modules/pallets/demo/src/lib.rs)

### Summary
The kernel CVE (CVE-2025-21905) fixes a case where a length-unbounded string read/print from untrusted firmware data could read past the end of a buffer because NUL-termination was assumed but not guaranteed. The closest analog in this codebase is `pallet-demo`'s `IsmpModuleCallback::on_accept`, which calls `String::from_utf8_unchecked(request.body)` on the raw body of an inbound ISMP `PostRequest` whose source is `StateMachine::Evm(_)` — i.e., attacker/relayer-controlled bytes are trusted to be valid UTF-8 without any validation, which is undefined behavior in Rust when the assumption is violated (worse than the kernel's OOB-read class, since UB is not merely "read too far" but permits arbitrary compiler-dependent behavior). [1](#0-0) 

### Finding Description
`IsmpModule::on_accept` is the standard callback invoked by `pallet-ismp`'s handler when it delivers a verified inbound `PostRequest` to the destination module. For `pallet-demo`, when the source chain is `StateMachine::Evm(_)`, the code does:
```rust
StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
    source: source_chain,
    data: unsafe { String::from_utf8_unchecked(request.body) },
}),
``` [2](#0-1) 

`request.body` is the raw message payload originally supplied by whoever dispatched the cross-chain `PostRequest` on the EVM source chain (an unprivileged token bridger / message dispatcher). `from_utf8_unchecked` skips UTF-8 validation entirely and is documented by the Rust standard library as undefined behavior if the bytes are not valid UTF-8. This mirrors the class of bug in the CVE: code trusts an external, attacker-influenced byte buffer to satisfy an invariant (NUL-termination in the kernel case, UTF-8 validity here) that is never actually checked at the point of use.

### Impact Explanation
If reachable, this is a memory-safety violation (undefined behavior) triggerable by a single relayed cross-chain message with an arbitrary, non-UTF-8 body. In the worst case this could manifest as a panic/DoS of the runtime, or, depending on compiler optimizations relying on the UTF-8 invariant, memory corruption/logic corruption within the runtime's WASM execution — a "High" class of bug matching the CVE's severity rationale (buffer-oriented UB from untrusted external data).

### Likelihood Explanation
This finding is **not currently exploitable in production** as best I can determine from the repository structure: `modules/pallets/demo` is present in the workspace `Cargo.toml` member list, but I found no reference to `pallet-demo` / `pallet_demo` anywhere else in the codebase (no runtime `Cargo.toml` or `construct_runtime!` wiring includes it), and the crate's own doc comment describes it as "Simple Demo for Asset transfer over ISMP." That strongly suggests it is example/demo code that is compiled as a workspace member but never included in the `gargantua` or `nexus` runtimes that are actually deployed, meaning `on_accept` is never invoked with real relayed messages in production. I was unable to fully verify this negative (i.e., confirm with certainty that no runtime config anywhere includes it) due to index coverage limits — a full-repo grep across generated runtime configuration files was inconclusive beyond the workspace `Cargo.toml`.

### Recommendation
1. Confirm (ideally via a Devin session with full repo access) that `pallet-demo` is not included in any deployed runtime (`gargantua`, `nexus`, or others). If it is genuinely unused, this finding should be downgraded to a hardening/hygiene issue rather than an exploitable production vulnerability.
2. Regardless, replace `String::from_utf8_unchecked(request.body)` with `String::from_utf8(request.body).unwrap_or_default()` or reject/emit an error event on invalid UTF-8, consistent with the pattern already used elsewhere in this codebase (e.g. `as_utf8_string::deserialize` and `PurchaseMessage::try_from`, both of which explicitly validate UTF-8 and reject malformed input rather than assume it) [3](#0-2) [4](#0-3) .
3. If `pallet-demo` is intended purely as sample/reference code, consider excluding it from the production workspace build or clearly gating it behind a `dev`/`example` feature so it cannot accidentally be wired into a runtime later.

### Proof of Concept
Given the reachability is unconfirmed for production, a full working PoC against a live deployment cannot be constructed. Conceptually, if `pallet-demo` were included in a runtime's `IsmpRouter`, the PoC would be:
1. An attacker deploys/controls an EVM-side dispatcher contract that submits an ISMP `PostRequest` to Hyperbridge with `dest` module id routed to `pallet-demo`, and `body` set to a byte sequence that is not valid UTF-8 (e.g., a lone continuation byte `0x80`).
2. Once the message is relayed and delivered on-chain, `pallet-ismp`'s handler calls `IsmpModuleCallback::on_accept` with this `PostRequest`.
3. `on_accept` executes `String::from_utf8_unchecked(request.body)` on the invalid bytes, triggering undefined behavior in the runtime's WASM execution.

Given the inability to confirm the module is wired into a live runtime, I recommend starting a Devin session with full repository/build access to (a) definitively confirm whether `pallet-demo` is reachable from any deployed runtime, and (b) apply the fix above if so.

impl<T: Config> IsmpModule for IsmpModuleCallback<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		let source_chain = request.source;

		match source_chain {
			StateMachine::Evm(_) => Pallet::<T>::deposit_event(Event::Request {
				source: source_chain,
				data: unsafe { String::from_utf8_unchecked(request.body) },
			}),
			StateMachine::Polkadot(_) | StateMachine::Kusama(_) => {
				let payload =
					<Payload<T::AccountId, <T as Config>::Balance> as codec::Decode>::decode(
						&mut &*request.body,
					)
					.map_err(|_| IsmpError::Custom("Failed to decode request data".to_string()))?;
				<T::NativeCurrency as Mutate<T::AccountId>>::mint_into(
					&payload.to,
					payload.amount.into(),
				)
				.map_err(|_| IsmpError::Custom("Failed to mint funds".to_string()))?;
				Pallet::<T>::deposit_event(Event::<T>::BalanceReceived {
					from: payload.from,
					to: payload.to,
					amount: payload.amount,
					source_chain,
				});
			},
			source => Err(IsmpError::Custom(format!("Unsupported source {source:?}")))?,
		}

		Ok(weight())
	}

	/// Deserialize a string into utf8 bytes
	///
	/// The string must be exactly 4 bytes long (bytes, not chars — a 4-char string of
	/// multi-byte codepoints is rejected). Anything else is a deserialization error; this
	/// runs on untrusted RPC input, so it must never panic.
	pub fn deserialize<'de, D, T>(deserializer: D) -> Result<T, D::Error>
	where
		D: serde::Deserializer<'de>,
		T: From<[u8; 4]>,
	{
		let s = <String>::deserialize(deserializer)?;

		// `s.len()` is the utf-8 byte length, which is what the `[u8; 4]` needs to match.
		let bytes: [u8; 4] = s
			.as_bytes()
			.try_into()
			.map_err(|_| serde::de::Error::invalid_length(s.len(), &"a 4-byte utf-8 string"))?;
		Ok(bytes.into())
	}
