### Title
Unvalidated length arithmetic on attacker-controlled cross-chain `from` field can panic message processing - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The curl CVE stems from computing a buffer length/offset from untrusted ASN.1 input without validating it is non-negative/sufficient, then using that length to read memory (`strlen` on a non-null-terminated region). The closest reachable analog in this codebase is in the `hyper-fungible-token` pallet's message-execution path, where the byte length of the untrusted, relayer/attacker-controlled `message.from` field is used in subtraction/slice arithmetic (`from_bytes.len() - 20`) and in a fixed-size `copy_from_slice` (32 bytes) without a preceding explicit length check visible in the code I could inspect.

### Finding Description
In the calldata-execution branch of the hyper-fungible-token module, when no signature is supplied, the beneficiary account is derived directly from the message's `from` field: [1](#0-0) 
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
`message.from` originates from an ISMP cross-chain message that is decoded from a relayed/proven request — its length is attacker/relayer influenced. If `from_bytes.len() < 20` on the EVM branch, `from_bytes.len() - 20` underflows `usize` subtraction (panics in debug/overflow-checked builds, or wraps to an enormous value that then causes an out-of-bounds range panic on the subsequent slice). Similarly, `copy_from_slice` on the non-EVM branch panics if `from_bytes.len() != 32`. This mirrors the CVE's root cause: deriving a length/offset from untrusted input and using it in a buffer operation without first validating the input's size is compatible with the assumed fixed size.

### Impact Explanation
A malformed or intentionally short/long `from` field in a dispatched HFT (hyper-fungible-token) message causes a panic during message execution. Depending on how the pallet's dispatch/`handle_unsigned`/`on_execute` path handles panics versus `Result` errors, this could cause the extrinsic to fail (denial of processing for that specific cross-chain transfer) rather than a clean `Err`. If this code path executes in a context that isn't panic-safely wrapped (e.g., an unsigned/mandatory ISMP message-execution hook), a malicious sender on the source chain could reliably fail delivery of that message, which fits the "route unable to deliver messages" impact category for token-bridge mint/burn message delivery.

### Likelihood Explanation
`message.from` reaches this code via a standard cross-chain token transfer dispatched by `pallet-ismp`'s `handle_unsigned`/message execution — this is a normal, low-privilege path any relayer or source-chain sender can trigger by crafting a message whose `from` address encoding doesn't match the expected 20/32-byte convention. I could not confirm from the snippets retrieved whether an earlier validation step (e.g., in message construction/ISMP encoding) already guarantees `from` is always 20 or 32 bytes before reaching this function, which materially affects whether this is actually exploitable.

### Recommendation
Before performing the length-based slicing, validate `from_bytes.len()` explicitly (`>= 20` for EVM, `== 32` for Substrate) and return a typed `HftError` on mismatch instead of relying on implicit panics from underflow/`copy_from_slice`.
