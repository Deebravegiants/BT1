### Title
Webhook `shop-domain` header is trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook using only the HMAC over the raw request body, then dispatches the handler using a `shop` value read from an HTTP header that is never included in the signed payload. Because the app's HMAC secret (`api_secret_key`) is a single shared secret across all shops that install the app, an attacker who controls a genuine, legitimately-installed shop can capture a real webhook (valid body + valid HMAC) and replay the exact same body/HMAC pair to the app's webhook endpoint while substituting a different, victim shop's domain in the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. The library will accept this as an authentic event for the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw request body — no headers are included: [2](#0-1) 

The `shop` accessor used downstream is read directly from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which is completely outside the HMAC's scope: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then constructs `WebhookMetadata` using the unauthenticated `request.shop` header value, handing it directly to the app-provided handler as the authoritative tenant identifier: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop header == the shop that actually generated this event`, but those are two independent, unlinked values. Since `api_secret_key` is the same for every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), any attacker who is a legitimate merchant on their own store can generate arbitrarily many valid `(body, hmac)` pairs for topics they can trigger (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/update`, etc.), then replay those exact bytes to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. The documented usage in `docs/usage/webhooks.md` confirms host apps are expected to trust `data.shop` as-is from the library after `Registry.process` succeeds — the gem does not document or provide any secondary binding of `shop` to the signed body.

### Impact Explanation
This allows an unprivileged internet user (any merchant who has installed the app on their own store, i.e., an "unprivileged" attacker relative to other tenants) to inject fabricated webhook events attributed to an arbitrary victim shop, without ever needing the victim's credentials or access token. Depending on how the host application acts on `data.shop` (as advised by this gem's own docs example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this can drive cross-tenant state corruption — e.g., spoofing `app/uninstalled` to cause the app to revoke/delete a victim shop's stored session and access token, spoofing `shop/redact` or `customers/redact` (GDPR mandatory topics) to trigger deletion of a victim shop's data, or injecting fabricated order/customer data attributed to a shop the attacker does not own. This is a cross-tenant identity-binding bypass reachable purely through this gem's documented `Webhooks::Request` / `Registry.process` API.

### Likelihood Explanation
High. No secrets beyond a legitimately obtained webhook body+HMAC pair (trivially obtainable by installing the app on an attacker-owned test store) are needed. The attack requires only a single HTTP POST with a forged header value — the header name and format are documented in this gem's own README/docs, and the mismatch between "what is HMAC-signed" (body only) and "what is trusted as tenant identity" (header) is not mentioned anywhere as a caveat for integrators to defend against.

### Recommendation
Bind the shop identity into the verified payload rather than trusting an unauthenticated header:
- Cross-check `request.shop` against the shop associated with the webhook subscription/registration record (fetched from Shopify) before dispatching, or
- Have `Registry.process` require the caller to supply the expected shop (e.g., resolved independently via the registered webhook ID or session store) and verify it matches `request.shop`, rejecting mismatches, and
- At minimum, clearly document that `data.shop` from `WebhookMetadata` is not cryptographically bound to the HMAC-verified body and must not be used as a sole tenant-authorization key without additional verification (e.g., correlating `webhook_id` with a known registration for that specific shop).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook topic the app handles as sensitive (e.g. `app/uninstalled`), capturing the real request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`, and `api_secret_key` is shared across all shop installs of this app).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - Body: the identical bytes `B`
   - Header `X-Shopify-Hmac-Sha256`: the identical `H`
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (a shop the attacker does not control)
   - Header `X-Shopify-Topic`: same topic as captured
3. The app calls:
   ```ruby
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: request.headers.to_h)
   )
   ```
4. Inside `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `raw_body` (`to_signable_string`), which is unchanged. [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, causing the host app to act on behalf of `victim-shop.myshopify.com` even though the event never originated from Shopify for that shop.
