### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw()` / `SweepDust` accepts silent transfer failures as success - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-specific `IntentGatewayV2` contract deviates from the main EVM `IntentGatewayV2.sol`, which consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (see `evm/src/apps/IntentGatewayV2.sol:250,321` and `evm/src/apps/intentsv2/IntentsBase.sol:468,476`). In the Tron fork, the internal `withdraw()` function and the `SweepDust` request handler instead perform a raw low-level `.call` with the `transfer` selector and only check that the *call itself did not revert* — they never inspect or decode the returned boolean payload.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and identically for `SweepDust`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and for transaction fee payout:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [3](#0-2) 

`success` here only reflects whether the low-level call reverted, not the ABI-decoded boolean that `IERC20.transfer` is supposed to return. Many ERC20-like tokens (including several deployed on Tron/TRC20 tokens that mimic ERC20) return `false` on failure instead of reverting (e.g., insufficient balance in some non-standard implementations, blacklist/pause checks that return `false`). Under this pattern, such a failed transfer looks identical to a successful one to this contract: the low-level `call` succeeds (no revert), `success` is `true`, and no exception is raised — this is the exact inverse of the bug class in the external report (which reverts on tokens with no return data), but produces a worse outcome: **silent, undetected transfer failure**.

Critically, `withdraw()` unconditionally finalizes state regardless of whether the token actually moved:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    _orders[body.commitment][token] -= amount;
``` [4](#0-3) 

This function is reached from `onPostRequest`/`onGetResponse` when handling `RedeemEscrow`/`RefundEscrow` kinds, i.e., driven by relayed ISMP messages from Hyperbridge:
```solidity
if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
    authenticate(incoming.request);
    WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
    return withdraw(body, kind == RequestKind.RefundEscrow);
}
``` [5](#0-4) 

Because `_filled[body.commitment]` is set and the escrow accounting is decremented before/without verifying real token receipt, once the underlying token silently returns `false`, the order is marked as filled/refunded and its escrow balance is zeroed, but the beneficiary receives nothing. There is no retry path — a later attempt to redeem the same commitment will hit `UnknownOrder()` (`_orders[...][token] == 0`) or the order is already recorded in `_filled`. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no way for the rightful beneficiary to claim them.

### Impact Explanation
This results in a permanent, unrecoverable loss of the user's/solver's escrowed funds on the Tron deployment whenever the underlying ERC20/TRC20 token implementation returns `false` rather than reverting on a failed transfer (a documented non-standard-but-common behavior). Since escrow release and fee payout are both gated only on call success (not on the actual boolean transfer result), an attacker does not even need special privileges — any order settled in a token with this failure semantics (or one whose balance is manipulated, e.g., via fee-on-transfer/pausable/blacklist mechanics) can trigger a silent no-op transfer that the contract nonetheless treats as a completed payout, permanently freezing the escrowed value. This qualifies as concrete permanent freezing/loss of funds in the intents escrow flow.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: it does not require any protocol misconfiguration or malicious governance — it is triggered purely by using a supported token whose implementation follows the "return false instead of revert" pattern (common among TRC20 tokens and many older/non-standard ERC20 tokens), combined with a normal `RedeemEscrow`/`RefundEscrow`/`SweepDust` relayed message, which is a routine, unprivileged part of protocol operation once an intent order settles.

### Recommendation
- **Short term:** Replace the raw `.call` + `success`-only checks in `withdraw()` (escrow release, refund, and fee payout) and in the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`evm/src/apps/IntentGatewayV2.sol` and `IntentsBase.sol` already use `safeTransfer`/`safeTransferFrom`). `SafeERC20` correctly handles both "no return data" and "returns false" cases by reverting on either.
- **Long term:** Audit the Tron-specific fork for other places that diverge from the shared `IntentGatewayV2`/`IntentsBase` implementations and standardize all token movement through `SafeERC20`, and add a token-integration checklist covering both no-return-value tokens and false-returning tokens.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20-style token whose `transfer()` implementation returns `false` on failure instead of reverting (a real, documented pattern for several tokens, distinct from but adjacent to the USDT no-return-value issue cited in the report).
2. Create and fill an intent order denominated in that token so funds are escrowed in `IntentGatewayV2` on Tron.
3. Cause the payout-time `transfer()` call to fail in a way the token signals via `return false` (e.g., recipient blacklisted, contract paused, or balance manipulated between escrow and redemption) rather than reverting.
4. Relay a `RedeemEscrow` (or `RefundEscrow`) request; `withdraw()` executes the low-level `call`, which returns `success = true` (call didn't revert) with `false` ABI-encoded in the return data — this data is never inspected.
5. `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented as if payout succeeded, while the beneficiary's actual token balance is unchanged. The escrowed tokens are now permanently stranded in the contract with no valid path to reclaim them.
