### Title
Batch withdrawal status matched by assetId only, causing wrong tx-hash / status to be reported when a batch contains multiple withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves per-withdrawal completion status by looking up the POA bridge's withdrawal list and matching **only on `assetId`**, ignoring `index`, destination address, or amount. In a batch withdrawal containing two or more withdrawals of the same underlying token (e.g., same `nep141:` asset to two different destination addresses), `findMatchingWithdrawal` will return the first entry in the (unsorted) API response whose asset matches, regardless of which destination it actually belongs to.

### Finding Description
`describeWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, lines 313-343) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`: [1](#0-0) 

`findMatchingWithdrawal` explicitly matches by `assetId` alone: [2](#0-1) 

The docstring even admits the limitation ("multiple withdrawals of the same token in a single transaction are not supported") [3](#0-2) , but neither `describeWithdrawal`, `watchWithdrawal` (packages/intents-sdk/src/core/withdrawal-watcher.ts), nor `createWithdrawalCompletionPromises`/`processWithdrawal` in `sdk.ts` reject or validate batches for duplicate `assetId` entries before calling this code path. There is no check preventing a caller from constructing `withdrawalParams: WithdrawalParams[]` with two entries sharing the same `assetId` but different `destinationAddress`/`amount` (e.g., refunding the same token to two different users, or one withdrawal plus a fee-token refund of the same asset).

When that happens, `describeWithdrawal` for withdrawal index 0 and index 1 can both resolve against the **same** API record (since the list is "unsorted" per the comment), so the SDK may report the destination tx hash belonging to withdrawal B as the completion of withdrawal A (and vice versa), or report "completed" for both indices based on a single actual on-chain transfer.

### Impact Explanation
This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal index." An integrator relying on `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` per-index results (as documented in the README's "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`") could:
- Credit/mark as "completed" a withdrawal that never actually completed (because it reused another withdrawal's completed record), causing a double-credit/incorrect settlement decision downstream.
- Attribute the wrong destination tx hash to the wrong withdrawal, which for a service that verifies delivery by hash could result in crediting the wrong user's withdrawal as successful.

This matches the High-impact category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Likelihood is limited by the precondition: it only manifests for batch withdrawals containing **two or more entries with an identical `assetId`** (any combination of different destination addresses/amounts). The SDK does not prevent constructing such a batch, and nothing in `sdk.ts`'s batch/estimate/create flows rejects duplicate-asset batches, so any integrator building batches programmatically (e.g. refunding leftover balances of the same token to multiple destinations in one intent) can trigger this unintentionally, without any malicious actor being required.

### Recommendation
- Reject or explicitly document/validate against duplicate `assetId` entries in a single batch when using the POA bridge route, at the point `sdk.ts` builds/validates batch `withdrawalParams`.
- Alternatively, extend `findMatchingWithdrawal` to disambiguate using additional withdrawal-specific fields returned by the POA API (e.g., destination address, amount, or a per-request nonce/index) rather than `assetId` alone, so each `WithdrawalIdentifier` maps deterministically to its own record.

### Proof of Concept
1. Construct a batch withdrawal via `sdk.processWithdrawal({ withdrawalParams: [ {assetId:"nep141:usdt...", amount: A, destinationAddress: addrX}, {assetId:"nep141:usdt...", amount: B, destinationAddress: addrY} ] })` (both use the POA bridge route).
2. After the intent settles, call `createWithdrawalCompletionPromises` / `waitForWithdrawalCompletion` for both entries.
3. Internally, both calls to `PoaBridge.describeWithdrawal` query the same `getWithdrawalStatus` response and `findMatchingWithdrawal` matches by `assetId` only [4](#0-3) , so both promises can resolve using the same underlying record (whichever the API lists first), even though the actual on-chain transfers/tx hashes differ per destination — as illustrated by the existing test explicitly built to probe this exact matching function, `"matches withdrawal by assetId, not by index"` [5](#0-4) .

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
