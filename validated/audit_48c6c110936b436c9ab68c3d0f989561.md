## Title
Global, workflow-unscoped request-ID map lets any authorized workflow owner DDOS other users' HTTP trigger requests - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The Bal-liquidity-provider bug class is a griefing DoS caused by an *exact-match* precondition (`bal == amount`) checked against shared, attacker-influenceable state, letting an unprivileged actor front-run and permanently block a legitimate user's operation. The closest reachable analog in this repo is `httpTriggerHandler.setupCallback`, which enforces exact-match uniqueness on a client-supplied JSON-RPC request ID stored in a single map shared across *all* workflows served by the gateway node, not scoped per workflow/owner.

### Finding Description
`setupCallback` takes the exclusive lock on `h.callbacksMu` and does a presence check keyed purely by the caller-supplied `requestID` string: [1](#0-0) 

`h.callbacks` is a single field on the `httpTriggerHandler` struct — one per gateway node/shard set, servicing *every* workflow the node handles — keyed only by `requestID`, with no workflow or owner component in the key: [2](#0-1) 

Reaching `setupCallback` only requires:
1. `validatedTriggerRequest` (format checks, including `validateRequestID` for length only — no format constraint preventing predictable/attacker-chosen IDs),
2. `resolveWorkflowID` (any registered workflow, including one the attacker owns),
3. `authorizeRequest`, which validates a JWT tied to the workflow the *attacker* controls via `workflowMetadataHandler.Authorize`: [3](#0-2) 

4. a per-workflow rate limit check.

None of these steps require any relationship between the attacker's workflow and the victim's workflow. Because the collision check operates on the shared `h.callbacks` map with no `workflowID` component in the key, an attacker who registers (or already owns) any workflow on the same gateway node can pre-populate the map with a `requestID` they predict or observe a victim about to use, and the victim's genuine request will be rejected outright: [4](#0-3) 

This mirrors the report's root cause: a global, exact-match check against a value an unprivileged party can influence ahead of time, causing legitimate requests to be permanently rejected (DoS) rather than degraded gracefully (e.g., falling back to accept/queue, or scoping the uniqueness check by owner/workflow).

### Impact Explanation
Impact is limited relative to the original finding (no direct fund loss) but matches the "no concrete authentication/fund-movement bypass" caveat only partially — the effect is denial of service against legitimate HTTP-triggered workflow executions: their request is bounced with `jsonrpc.ErrConflict` ("has already been used") and the execution never starts. Because the map is shared across all workflows on the node rather than scoped per workflow/owner, this is a **cross-user** griefing vector, unlike a same-workflow-owner self-DoS, which is the qualifying condition per the validation rules (cross-user response confusion / DoS). Severity is bounded because: (a) the attacker must itself control an onboarded, authorized workflow (some barrier to entry), and (b) if request IDs are generated as high-entropy UUIDs by well-behaved SDKs, blind guessing is impractical — the practical risk is highest when request IDs are predictable/sequential or when the attacker can observe/anticipate a specific victim's ID (e.g., via side channels, shared tooling, or a colluding/observing party).

### Likelihood Explanation
Likelihood is low-to-moderate: exploitation needs the attacker's chosen `requestID` to match a victim's ID before the victim's request lands, and requires the attacker to be an authorized workflow owner on the same node (a real but not-strong access barrier since workflow registration is generally self-service). No cryptographic secret is required; only correct guessing/observation of a request ID within the request's short in-flight lifetime.

### Recommendation
Scope the uniqueness/idempotency key in `h.callbacks` by `(workflowID, requestID)` (or `(workflowOwner, requestID)`) rather than by `requestID` alone, so that a collision can only occur within the same workflow/owner's own request stream, eliminating cross-user griefing. Additionally, consider deriving the dedup key server-side from an owner-bound value (e.g., include a signed nonce or JWT `jti`) rather than trusting the caller-chosen JSON-RPC `id` for global uniqueness enforcement.

### Proof of Concept
1. Attacker registers/owns Workflow A (any account can do this per the app's onboarding flow) and obtains a valid JWT for it via `workflowMetadataHandler.Authorize`.
2. Attacker predicts/observes the `requestID` a victim will use for Workflow B's HTTP trigger request (e.g., low-entropy or sequential IDs, or an observed retry timing window).
3. Attacker sends `HandleUserTriggerRequest` for Workflow A using that exact `requestID` just before the victim's request; `setupCallback` inserts it into the shared `h.callbacks` map.
4. Victim's genuine request for Workflow B with the same `requestID` reaches `setupCallback`, finds the key already present, and is rejected with `jsonrpc.ErrConflict`/"has already been used" — the legitimate workflow execution never starts, as shown by the existing test demonstrating the exact collision behavior: [4](#0-3) .

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
