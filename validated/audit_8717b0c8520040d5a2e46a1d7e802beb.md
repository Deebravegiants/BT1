### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` metadata are unauthenticated header values not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity using an HMAC that is computed only over the raw request body, but then hands the host application `topic`, `shop`, `api_version`, and `webhook_id` values that are read directly from unauthenticated HTTP headers. Since these identity fields are not part of the signed payload, an attacker who possesses one valid `(body, hmac)` pair can freely rewrite the `shop-domain` (and other) headers while keeping the body/HMAC unchanged, and the signature check will still pass — even though the tenant identity delivered to the host app's handler is now attacker-controlled.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `to_signable_string` on the `VerifiableQuery` and compares it against the HMAC using the app's `api_secret_key`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body**: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, none of which are included in the signed string: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., verifies the body bytes match the HMAC) and then dispatches the handler using the unauthenticated `request.shop`/`request.topic`/etc.: [4](#0-3) 

The resulting `WebhookMetadata` struct — which is the only tenant/topic context the host application receives — is built entirely from these unauthenticated fields: [5](#0-4) 

This breaks the intended binding:
`shop authenticated by HMAC == shop attributed to the webhook payload`

In reality the equality holds only for the **body bytes**; the `shop` (and `topic`/`api_version`/`webhook_id`) fields are asserted, not authenticated. This is the same bug class as the RocketPool report — a value is "recorded"/consumed but never bound to the cryptographic check that is supposed to make it trustworthy, in this case a field acted upon (`shop`) is not covered by the HMAC.

### Impact Explanation
An attacker who has access to at least one genuine `(raw_body, hmac)` pair signed with the app's secret (e.g., a webhook delivered to their own shop's endpoint, or one they can otherwise capture/replay, since HMAC-only-signed bodies are transmitted over the wire to the app's public webhook endpoint) can resend that exact body/HMAC to the same endpoint while altering the `x-shopify-shop-domain` header to name a different (victim) shop. `HmacValidator.validate` will still return `true` because it never inspects headers, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that trusts `WebhookMetadata#shop` to select tenant-scoped data, sessions, or access tokens (a normal and documented usage pattern for this field) can be tricked into writing/reading data under the wrong shop — a cross-tenant confusion vulnerability enabled directly by this gem's request-verification design.

### Likelihood Explanation
Any entity that can receive a legitimate signed webhook for its own store (which requires no privileged access — any merchant can install an app and receive its own webhooks) obtains a valid `(body, hmac)` pair. Replaying it with a modified `shop-domain` header against the same public webhook endpoint requires only a normal HTTP request; no access token, `client_secret`, or elevated privilege is needed. The likelihood is moderate-to-high for apps that rely on `WebhookMetadata#shop` (or `topic`/`webhook_id`) as an implicit trust anchor, which is the pattern the gem's own API encourages.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically authenticate them before exposing them to the handler:
- Include `shop`, `topic`, `api_version`, and `webhook_id` in `to_signable_string` (or compute a canonical string covering headers + body) so the HMAC check fails if any of these are tampered with.
- Alternatively, cross-check the `shop-domain` header against a shop the app has an active/registered session for before dispatching, rather than trusting the header value implicitly.
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are not covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., re-fetching the resource via API using the shop's own stored access token).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid signature over `B` using the app's `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new HTTP POST to the app's public webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (all required headers present) — see `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` returns only `B`, the HMAC check passes.
5. The host app's `WebhookHandler#handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the host application to process/store attacker-supplied data under the victim shop's tenant context.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
