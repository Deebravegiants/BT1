### Title
Webhook shop and topic identifiers are trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC over the raw request body only, then blindly trusts the `shop-domain` and `topic` headers — which are not part of the signed data — to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is likewise computed solely from the `hmac-sha256` header value: [2](#0-1) 

`Utils::HmacValidator.validate` then recomputes the signature strictly from `to_signable_string` (the body) and compares it to the provided HMAC: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the *entire request* — including `shop`, `topic`, `webhook_id`, and `api_version` — is authentic, and immediately builds `WebhookMetadata` from those unauthenticated headers before dispatching to the app's handler: [4](#0-3) 

The identity binding that is broken: `bytes_verified_by_HMAC (raw_body)` ≠ `bytes_the_handler_uses_to_identify_the_tenant (shop-domain header)`. Since a single app's `api_secret_key` is shared across every merchant shop that installs it, any party who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own shop and capturing a legitimate webhook delivery) can freely replace the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers with values naming a different merchant, and `Registry.process` will still accept it, because those header values are never part of the signed material.

### Impact Explanation
An attacker who has legitimately received one valid webhook for the app (trivial for any developer/merchant who installs a public app) can replay it while spoofing the `shop` field to impersonate a different, unrelated tenant shop. Any host application that relies on `WebhookMetadata#shop` from this gem to select per-tenant state, credentials, or business logic (exactly what the gem's own `WebhookMetadata` is designed to convey) will act on attacker-controlled data believing it originated from a different merchant — a cross-tenant access condition.

### Likelihood Explanation
Any user who can install the target app on their own store (a normal, low-privilege action) can capture one legitimate webhook body/HMAC pair and reuse it with a forged `shop-domain`/`topic` header set. No secret material beyond what a legitimate installer already possesses (a working webhook delivery) is required, making this a realistic, unprivileged-internet-user path.

### Recommendation
Bind the tenant-identifying and routing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) into the signed material verified against the HMAC — e.g., include them in `to_signable_string`, or independently verify that `request.shop` matches the shop associated with the session/registration expected to receive that webhook — before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. App `X` is installed on `shop-a.myshopify.com` and on attacker-controlled `shop-attacker.myshopify.com`, sharing the same `api_secret_key`.
2. Shopify delivers a legitimate webhook to the attacker's endpoint for `shop-attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(secret, B)`.
3. Attacker resends the same body `B` and same `H`, but replaces `x-shopify-shop-domain` with `shop-a.myshopify.com` (and optionally forges `x-shopify-topic`/`x-shopify-webhook-id`) to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B`; it succeeds since `B` and `H` are unmodified.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop-a.myshopify.com` value and dispatches it to the app's handler, which now believes the (attacker-supplied) body content belongs to `shop-a`.
