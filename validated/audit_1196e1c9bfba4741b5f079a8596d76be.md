### Title
Checks-Effects-Interactions violation and unchecked low-level transfer in `withdraw()` allows silent fund loss / stuck escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` sends native ETH and ERC-20 tokens to the beneficiary via raw external calls **before** decrementing the escrow ledger, and treats the low-level `.call` `success` flag as proof of a valid ERC-20 transfer without inspecting the returned boolean. This reproduces the exact bug class behind the Stars Arena hack (external value-transfer executed before internal accounting is finalized/validated), and diverges from the reference, hardened implementation shipped elsewhere in the same repo.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2` iterates over `body.tokens` and, for each entry, performs the external transfer first and only updates the escrow mapping afterward: [1](#0-0) 

```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

This is a direct Interactions-before-Effects ordering — the same pattern (external value-send executed before internal state is settled) that Beosin identified as the root cause of the Stars Arena `sellShares()` reentrancy drain. Compare this to the hardened reference implementation used on EVM mainnet chains, `IntentsBase._withdraw`, which explicitly performs the effect (`_orders[...] = escrowed - amount`) **before** the interaction (`_sendValue`/`safeTransfer`): [2](#0-1) 

Additionally, the ERC-20 branch uses a bare `token.call(...)` and only checks that the call itself did not revert (`success`), never inspecting the ABI-decoded boolean return value of `transfer()`. Tokens that signal failure by returning `false` (rather than reverting) will cause the contract to believe the transfer succeeded, decrement `_orders[commitment][token]` as if the beneficiary was paid, and permanently strand the tokens in the contract — an unbacked accounting/fund-loss condition parallel to the "throwing money away"/broken-value-flow theme in the report. The mainnet reference implementation instead uses `SafeERC20.safeTransfer`, which reverts on a `false` return, avoiding this class of bug entirely.

`withdraw()` is reachable from a single unprivileged submitted transaction via `cancelOrder()` (same-chain refund path) and via the cross-chain `RedeemEscrow`/`RefundEscrow` message and `onGetResponse` storage-proof callback: [3](#0-2) [4](#0-3) 

While the `_filled[body.commitment]` guard set at the top of `withdraw()` blocks the most direct re-entrant double-withdrawal of the *same* commitment through `cancelOrder`, it provides no protection at all for the unchecked-ERC20-return path — that defect fires unconditionally on any non-reverting-but-failing `transfer()` call, independent of reentrancy guards.

### Impact Explanation
Assets escrowed by users/solvers in the IntentGateway can be permanently lost: any ERC-20 whose `transfer()` returns `false` on failure (insufficient allowance/paused/blacklist-style tokens, or tokens with non-standard return semantics) will have its escrow silently marked as released (`_orders[...] -= amount`) while the tokens never leave the contract and the intended beneficiary receives nothing. Because the same function structure executes external value transfer before internal bookkeeping, this is also structurally the same insecure ordering that made Stars Arena's `sellShares()` drainable — a defense-in-depth violation on a path handling the entire fungible escrow balance of the gateway.

### Likelihood Explanation
`cancelOrder` and the `RedeemEscrow`/`RefundEscrow` message handlers are reachable by any order owner/solver/relayer through ordinary calls, with no special privilege required, and the mismatch between "call success" and "transfer success" is a well-known ERC-20 integration hazard likely to be hit by real-world tokens deployed on Tron.

### Recommendation
Refactor `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow strict checks-effects-interactions: decrement `_orders[body.commitment][token]` before performing the native-ETH `.call` or ERC-20 transfer, mirroring `IntentsBase._withdraw`. Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer`, which properly decodes and validates the return value (and handles tokens with no return value), preventing accounting from advancing on a failed transfer.

### Proof of Concept
1. Deploy (or use) an ERC-20 token whose `transfer()` returns `false` when it cannot fulfill a transfer (e.g., due to a paused/blacklist state that is triggered right before this call) instead of reverting.
2. Place an order with this token as an input via `placeOrder`, escrowing `_orders[commitment][token] = amount`.
3. Trigger the refund/redeem path (`cancelOrder` same-chain branch, or a relayed `RedeemEscrow`/`RefundEscrow` message) so `withdraw()` is invoked with `body.tokens` containing this token.
4. Arrange for the token's `transfer()` to return `false` (without reverting) for this specific call.
5. `token.call(...)` returns `success = true` (the low-level call did not revert) even though the transfer failed; `withdraw()` proceeds to `_orders[body.commitment][token] -= amount`, marking the escrow as released.
6. The beneficiary never receives the tokens, and the tokens remain permanently stuck/unaccounted-for in the `IntentGatewayV2` contract, while the escrow accounting shows them as already paid out.
