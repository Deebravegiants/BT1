### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header is therefore never bound to the signature that authenticates the request, breaking the identity binding: `shop header value == authenticated tenant`.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` (the raw body only) using the app's shared `api_secret_key`, and compares it to the `hmac-sha256` header value: [4](#0-3) [5](#0-4) 

`Request#shop` reads the shop identity from a header that is completely outside that signed scope: [6](#0-5) 

Because the `api_secret_key` is a single app-wide secret shared across all shops/tenants that install the app (not per-shop), any tenant that has the app installed can legitimately obtain a validly-HMAC-signed `(body, hmac)` pair from their own genuine webhook delivery. Since the signature covers only the body — never the `shop-domain` header — that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `shop-domain` header value swapped to a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects `shop` at all, and `Registry.process` will hand the forged `WebhookMetadata` (with the attacker-chosen `shop`) straight to the host application's handler: [7](#0-6) 

This is the same class of bug as the external report: a field that is acted upon (here, the tenant-identifying `shop`) is not covered by the authentication check (here, the HMAC), so the verified bytes (body) and the trusted-and-used bytes (headers, including `shop`) diverge.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to determine which merchant/tenant a webhook belongs to (e.g., to look up that shop's session/access token, update shop-scoped data, or trigger shop-scoped side effects) can be fooled into acting on behalf of an arbitrary victim shop using a signature obtained legitimately from the attacker's own shop. This is a cross-tenant confusion primitive: the attacker controls the webhook body content of their own shop and forces the app to process it as if it originated from a shop they do not control.

### Likelihood Explanation
Exploitation requires only that the attacker have (or create) a shop with the target app installed, so they can trigger a real webhook delivery and capture a valid `(body, hmac)` pair for a chosen action, then replay that request to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged access is needed — this is exploitable by an ordinary merchant/unprivileged internet-facing attacker able to send HTTP requests to the app's webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed payload verified by `HmacValidator`, or otherwise cryptographically bind the shop domain to the request before trusting it — e.g., by including it in `to_signable_string`, or by requiring the host application to cross-check `shop` against a previously known/registered shop record rather than treating the header as authenticated on its own.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, causing Shopify to POST a validly HMAC-signed request `(raw_body, x-shopify-hmac-sha256, x-shopify-shop-domain: attacker.myshopify.com, ...)` to the app's webhook endpoint.
2. Intercept/capture this request. `raw_body` and `hmac-sha256` remain untouched.
3. Replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only checks `raw_body` against `hmac-sha256`; validation succeeds because the header is not part of `to_signable_string`. [8](#0-7) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the payload actually originating from the attacker's own shop, and any shop-scoped logic in the host app now executes under the victim's tenant identity.
