### Title
Asymmetric decimal-scaling bug in `pallet-hyper-fungible-token`'s `convert_to_balance`/`convert_to_erc20` causes unbacked mint or fund loss when a registered asset's local decimals exceed its EVM decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The Shoebill Finance incident stemmed from an "unexpected interaction" created when integrating two similar assets (solvBTC and solvBTC.BBN) with differing decimal/pricing conventions into one oracle configuration, letting an attacker exploit the mismatch. The analogous condition in Hyperbridge exists in `pallet-hyper-fungible-token`'s decimal-conversion helpers, which silently fail to scale amounts correctly whenever a registered asset's local (substrate) decimals exceed its configured EVM `Precisions` decimals — a legitimate, foreseeable configuration for many low-decimal tokens (e.g., 6-decimal USDC-style or 8-decimal WBTC-style assets bridged against an 18-decimal local asset).

### Finding Description
`convert_to_balance` and `convert_to_erc20` both compute their scaling exponent as `erc_decimals.saturating_sub(local_decimals)`, which is only correct in one direction: [1](#0-0) 

- `convert_to_balance(value, erc_decimals, local_decimals)` always **divides** `value` by `10^(erc_decimals.saturating_sub(local_decimals))`. When `local_decimals > erc_decimals`, `saturating_sub` returns 0, so the function divides by `10^0 = 1` — i.e., performs **no scaling at all** — instead of multiplying up to the correct local precision.
- `convert_to_erc20(value, erc_decimals, local_decimals)` always **multiplies** `value` by `10^(erc_decimals.saturating_sub(local_decimals))`. When `local_decimals > erc_decimals`, this again collapses to a no-op multiply by 1, instead of dividing down to the destination chain's lower precision.

Both directions are invoked directly from unprivileged, user-reachable extrinsics:
- `send` (outgoing): calls `convert_to_erc20(amount, erc_decimals, decimals)` and forwards the resulting `U256` as the ERC20 `Message.amount` dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which mints that raw value verbatim. [2](#0-1) 
- `on_accept` (incoming): calls `convert_to_balance(U256::from_big_endian(...), erc_decimals, decimals)` on messages arriving from a registered EVM peer, then mints/releases that amount locally. [3](#0-2) 

The pallet's own documentation confirms the intended (but unimplemented) behavior — that decimals can differ in *either* direction and should be scaled accordingly: [4](#0-3) 

`register_token`/`update_token` are privileged (`CreateOrigin`), but registering an asset whose local decimals (commonly 18, the substrate/assets-pallet default) exceed the EVM token's real decimals (commonly 6 or 8 for stablecoins/BTC-wrapped tokens) is an entirely legitimate, expected configuration — not malicious governance. Once such a token is registered, **every ordinary user's `send` call** triggers the bug.

### Impact Explanation
- On `send` (local_decimals=18, erc_decimals=6, e.g.): a user escrows/burns `amount` at 18-decimal precision, but `convert_to_erc20` forwards the *raw* 18-decimal value unscaled as the ERC20 message amount. The destination `HyperFungibleToken` contract mints that raw number of token base units under its real (6- or 8-decimal) `decimals()`, over-minting by a factor of `10^(local_decimals - erc_decimals)` (e.g., 10^12) relative to the value actually escrowed. This is an unbacked mint that lets any user drain the counterpart's economic backing / mint far more value than they locked.
- On `on_accept` for the return trip, the symmetric bug causes `convert_to_balance` to under-credit incoming transfers by the same factor, permanently destroying value for legitimate senders returning tokens (funds effectively burned with near-zero credit).

Both are concrete theft/unbacked-mint and permanent-fund-loss scenarios directly reachable by a single unprivileged `send` extrinsic once a plausible (non-malicious) low-decimal asset is registered — satisfying the "unbacked mint" / "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
High for any deployment where a bridged asset's EVM-side ERC20 decimals are configured lower than the local substrate asset's decimals — a common, realistic setup (native EVM stablecoins at 6 decimals, WBTC-style tokens at 8 decimals, vs. the common 18/12-decimal substrate defaults). No malicious governance action is required beyond ordinary, expected asset registration; the trigger is a normal `send()` call available to any signed account.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` to branch on which side has more decimals rather than using a single `saturating_sub` in a fixed direction:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit/integration tests exercising `local_decimals > erc_decimals` (and vice versa) round-trips to prevent regression.

### Proof of Concept
1. Governance registers a non-native asset with `native = true/false` and `chains[chain].decimals = 6` (a realistic EVM stablecoin precision) while the local `pallet-assets` asset uses `decimals = 18` (a realistic substrate default), via `register_token`.
2. Any signed user calls `send(SendParams { asset_id, amount: 1_000_000_000_000_000_000 (1 token, 18 dp), destination: chain, .. })`.
3. Inside `send`, `erc20_amount = convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)`. Since `erc_decimals.saturating_sub(local_decimals) = 0`, `erc20_amount = 1e18` unscaled (should have been `1e18 / 10^12 = 1e6`). [5](#0-4) 
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract, which mints `1e18` raw base units of a 6-decimal token — 1,000,000,000,000 (one trillion) tokens instead of the 1 token that was actually escrowed/burned locally, an unbacked mint reachable by any user's ordinary transfer.
