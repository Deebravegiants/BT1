### Title
Unbounded per-request linear scan over the growing allowlisted-requests set enables CPU-exhaustion DoS in Vault gateway auth - ([File: core/capabilities/vault/allow_list_based_auth.go])

### Summary
The reported Solidity bug describes an unbounded loop (`0..currentAvailableRewardPeriod`) whose cost grows without limit as the reward period counter increases, causing `getAvailableReward` to run out of gas for late claimers. The closest reachable in-scope analog is `allowListBasedAuth.findAllowlistedItemWithRetry`/`fetchAllowlistedItem` in the Vault gateway's allowlist-based authorizer, which performs a full linear scan (and a full string-formatting pass) over the *entire* set of on-chain allowlisted requests on every single unauthenticated (no-JWT) Vault gateway request, with no bound tied to the actual size of that set.

### Finding Description
Every Vault gateway request that does not carry a JWT (`req.Auth == ""`) is routed to `authorizeAllowListBasedAuth`, which calls into `allowListBasedAuth.AuthorizeRequest`: [1](#0-0) 

That in turn calls `findAllowlistedItemWithRetry`, which on **every attempt** (up to `retryCount+1 = 11` attempts) pulls back the complete in-memory allowlisted-requests slice via `workflowRegistrySyncer.GetAllowlistedRequests(ctx)` and iterates over the *entire* slice twice: once to build a full debug-string slice (`allowedRequestsStrs`), and once inside `fetchAllowlistedItem` to linearly search for a matching digest: [2](#0-1) [3](#0-2) 

The backing slice `w.allowListedRequests` is populated by the workflow registry syncer's `syncAllowlistedRequests` background loop, which only prunes entries by *expiry timestamp*, not by any hard cap on count, and appends every newly observed on-chain allowlisted request: [4](#0-3) 

Because any workflow owner can call `AllowlistRequest` on the on-chain `WorkflowRegistry` contract to add entries (as exercised in test helpers), the size of this in-memory list is effectively attacker-influenced and grows monotonically until entries expire. Since expiry is owner-chosen (`ExpiryTimestamp`), owners can keep entries alive for long windows, and the total set size can grow large over the life of the DON — directly mirroring the "later claimer" bug-class pattern where a monotonically growing counter/array is walked in full on every operation with no upper bound check.

Unlike the Solidity case (gas limit revert), the consequence here is CPU cost per gateway request growing linearly with the size of the allowlist, multiplied by up to 11 retries for any request whose digest is not (yet) allowlisted. This is squarely in the internet-facing gateway allowlist path called out in scope.

### Impact Explanation
An unprivileged caller can send arbitrarily many Vault gateway JSON-RPC requests with non-allowlisted (or intentionally never-allowlisted) digests. Each such request forces the authorizer to scan the *entire* allowlisted-requests set up to 11 times (due to the retry loop with ~3s sleeps between attempts, worst case ~30s wall time per request) before failing with "request not allowlisted." As the allowlist naturally grows over time (or is deliberately inflated by an attacker registering many long-lived allowlist entries under their own workflow owner), the per-request CPU/memory cost (string formatting of every entry, `fmt.Sprintf` allocation for logging) scales linearly with `len(allowListedRequests)`, with no maximum size enforced anywhere in the sync or auth path. Concurrent requests amplify this because each holds the process busy for the full linear scan under a lock (`w.allowListedMu`) contested with the syncer's own periodic prune/append cycle. This creates a resource-exhaustion/availability risk on the Vault gateway node under load, degrading the gateway for all users, not just the offending client — though this is a degradation/DoS rather than a fund-movement or authentication bypass.

### Likelihood Explanation
Likelihood is moderate: reaching this code path requires no special privilege — any client can send a Vault gateway request with `req.Auth == ""` and an arbitrary/garbage digest, which is the default (non-JWT) path used by existing clients. Triggering meaningful cost requires the allowlist to have grown large, which depends on organic or attacker-driven growth (an attacker can also allowlist many long-expiry, never-consumed requests themselves, since `AllowlistRequest` doesn't appear to be capped per owner in this code path). This is a resource-usage growth issue rather than an instant crash, so exploitation is more probabilistic/gradual than a hard revert, unlike the original Solidity finding.

### Recommendation
- Replace the linear scan in `fetchAllowlistedItem` with a map keyed by `RequestDigest` for O(1) lookups, maintained incrementally by `syncAllowlistedRequests` instead of rebuilt/scanned as a slice each time.
- Remove or gate the full-list `allowedRequestsStrs` debug-string construction behind a debug/verbose flag so it isn't unconditionally built on every auth attempt.
- Enforce (or confirm enforcement of) a hard cap on the number of active allowlisted requests tracked per owner/globally, independent of expiry-based pruning, to bound worst-case per-request cost analogous to bounding the loop in the Solidity fix.

### Proof of Concept
Not applicable as a standalone runnable PoC given the analog is a scalability/DoS pattern rather than a single-transaction exploit; the reachable path is demonstrated by code inspection: any Vault gateway client can invoke `AuthorizeRequest` → `findAllowlistedItemWithRetry` → `fetchAllowlistedItem` with a non-matching digest to force a full unbounded scan of `w.allowListedRequests`, repeated up to 11 times per request, as shown in [2](#0-1) .

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}

func (a *authorizer) authorizeAllowListBasedAuth(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	if a.allowListBasedAuth == nil {
		err := errors.New("AllowListBasedAuth authorizer is nil")
		a.lggr.Errorw("AllowListBasedAuth unavailable", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	return a.allowListBasedAuth.AuthorizeRequest(ctx, req)
}

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (r *allowListBasedAuth) fetchAllowlistedItem(allowListedRequests []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, digest [32]byte) *workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest {
	for _, item := range allowListedRequests {
		if item.RequestDigest == digest {
			return &item
		}
	}
	return nil
}

func (w *workflowRegistry) syncAllowlistedRequests(ctx context.Context) {
	ticker := w.getTicker(defaultTickIntervalForAllowlistedRequests)
	w.lggr.Debug("starting syncAllowlistedRequests")
	for {
		select {
		case <-ctx.Done():
			w.lggr.Debug("shutting down syncAllowlistedRequests, %s", ctx.Err())
			return
		case <-ticker:
			newAllowListedRequests, totalAllowlistedRequests, head, err := w.getAllowlistedRequests(ctx, w.contractReader)
			if err != nil {
				w.lggr.Errorw("failed to call getAllowlistedRequests", "err", err)
				continue
			}
			w.allowListedMu.Lock()
			// Prune expired requests
			activeAllowlistedRequests := []workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest{}
			expiredRequestsCount := 0
			for _, request := range w.allowListedRequests {
				if int64(request.ExpiryTimestamp) > time.Now().Unix() {
					activeAllowlistedRequests = append(activeAllowlistedRequests, request)
				} else {
					expiredRequestsCount++
				}
			}

			// Add new requests
			activeAllowlistedRequests = append(activeAllowlistedRequests, newAllowListedRequests...)
			w.allowListedRequests = activeAllowlistedRequests
			w.lastSeenAllowlistedRequestsCount = totalAllowlistedRequests
			w.lggr.Debugw("synced allowlisted requests",
				"newRequestsNum", len(newAllowListedRequests),
				"expiredRequestsNum", expiredRequestsCount,
				"activeRequestsNum", len(w.allowListedRequests),
				"lastSeenOnchainRequestsNum", w.lastSeenAllowlistedRequestsCount,
				"blockHeight", head.Height,
			)
			w.allowListedMu.Unlock()
		}
	}
}
