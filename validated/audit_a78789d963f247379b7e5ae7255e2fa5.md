### Title
Webhook HMAC validation only covers the request body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining `to_signable_string` as just the raw JSON body, while `shop` (the tenant identifier) is read directly from the `shop-domain`/`x-shopify-shop-domain` header and is never included in the signed material.

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the app's handler: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

And for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` is derived independently from the `shop-domain` header, which is not part of the signed string: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` is the same for every merchant installation of the app, a valid `(raw_body, hmac)` pair obtained from one legitimate webhook delivery (e.g. delivered to the attacker's own store, which they can trivially trigger by installing the app on their own shop and generating an event) remains cryptographically valid regardless of which `shop-domain` header value is attached to it. The equality the code implicitly assumes is:

`shop authenticated by HMAC == shop acted upon (request.shop passed to the handler)`

but in reality the HMAC only proves `raw_body` is untampered; `request.shop` is an independent, unauthenticated header value. An attacker who possesses one valid `(body, hmac)` pair can replay it with an arbitrary `shop-domain` header, and `Registry.process` will pass that forged shop identity straight to the app's handler: [4](#0-3) 

### Impact Explanation
The app's webhook handler receives `WebhookMetadata` with an attacker-chosen `shop` while the payload's authenticity (HMAC) is verified. Since apps use `request.shop`/`data.shop` as the tenant key to route the webhook body to the correct merchant's records (as shown in the test suite's handler pattern), this allows an attacker to make the app process/attribute a valid webhook body under a different (victim) tenant's identity — a cross-tenant integrity/access issue, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to trigger one legitimate webhook delivery for any shop that uses the same app installation's shared `client_secret` (e.g., their own store), then resend the exact same raw body/HMAC pair to the app's webhook endpoint with a different `shop-domain` header. No access to the victim's credentials, access token, or the app's `client_secret` is required.

### Recommendation
Bind the shop identity to the signed material — e.g., include the `shop-domain` header value in the HMAC-signed string (as Shopify already does for OAuth's `AuthQuery`, whose `to_signable_string` includes `shop` — see `lib/shopify_api/auth/oauth/auth_query.rb` lines 34-43), or otherwise cryptographically bind the header-derived shop to the payload before handing it to the app's handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31), and `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 189-199) dispatches the handler with `shop: request.shop` set to `victim-shop.myshopify.com`, even though the payload never originated from that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
