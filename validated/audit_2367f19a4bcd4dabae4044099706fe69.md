### Title
Multisig address/redeem-script derivation uses a caller-supplied `multisigDataIndex` that can point to stale or different cosigner data if `multisigWallet.data` changes between decision and use - (File: features/address-provider/module/address-provider.js)

### Summary
`AddressProvider#getAddress` / `#getMultisigAddress` in `features/address-provider/module/address-provider.js` accepts an optional `multisigDataIndex` that is used to select an entry from `multisigWallet.data`, the array of a wallet account's stored multisig configurations (cosigner sets, xpubs, thresholds). This is structurally the same bug class as the Telcoin `claimFromIndividualPlugin()` issue: a caller (or a cached/queued call) references an array element by positional index, but the underlying array can be mutated between when that index is decided and when it is actually consumed, causing the wrong entry's data (cosigner public keys / threshold / internal xpub) to be used for deriving the address and redeem/witness script.

### Finding Description
`getAddress()` accepts `multisigDataIndex` as an optional parameter [1](#0-0) . It is passed through unresolved into `#getMultisigAddress`, where it indexes directly into `multisigWallet.data`: [2](#0-1) 

If `multisigDataIndex` is omitted, the function defaults to `multisigWallet.data.length - 1` (latest) or `0` (original) [3](#0-2) , and if it is provided, only a length bound-check is performed (`multisigWallet.data.length > multisigDataIndex`) [4](#0-3) ; there is no check that the entry at that index is still the *same* multisig configuration the caller originally intended.

`multisigDataIndex` is also threaded through the address cache lookup/write path (`#addressCache.get`/`.set`) using the same raw index [5](#0-4) [6](#0-5) , meaning positional-index semantics propagate into caching as well.

This mirrors the Telcoin M-1 pattern precisely: a consumer decides to act on "the multisig config at position N" (e.g., resolves `multisigDataIndex` earlier in a flow, such as choosing "the latest cosigner set" for building a transaction/address), and if the wallet account's `multisigWallet.data` array is later modified (a new cosigner set appended, e.g. after a multisig recovery/rotation event) before the index is actually consumed, `data[N]` can silently refer to a *different* multisig configuration (different cosigners/threshold/internal xpub) than what the caller intended - by identity/position rather than by a stable identifier. Each entry does carry an `id` field (`multisigData.id`) as seen in test fixtures [7](#0-6) , but `#getMultisigAddress` never uses `id` for resolution - it always resolves purely by array position.

I was not able to fully trace every caller of `getAddress({ multisigDataIndex })` across the wider codebase (e.g., tx-signer, UI/RPC flows that decide `multisigDataIndex` ahead of time and pass it back later) within available search results, so I cannot confirm a concrete, reachable end-to-end call site where the index is computed asynchronously and then consumed after a mutation. This is a structural weakness in the API surface rather than a confirmed exploited path.

### Impact Explanation
If an out-of-date `multisigDataIndex` is used against a mutated `multisigWallet.data` array, the address returned by `getAddress()` (and the `redeem`/`witness` spending script bound to it) would be derived from the wrong cosigner set - wrong public keys, wrong threshold, wrong internal xpub. This can lead to:
- Funds being sent to (or expected to be received at) an address whose spending policy does not match what the user/application intended.
- A cached, stale address/script being served for what the caller believes is a different (e.g., newly rotated) multisig configuration, since caching keys off the same raw index [5](#0-4) .

This is analogous to "wrong auxData supplied to wrong plugin" in the Telcoin case - here it would be "wrong cosigner set used to derive/spend from an address," a direct fund-safety concern for multisig wallet accounts.

### Likelihood Explanation
Likelihood is lower than the original Telcoin finding because:
- `multisigWallet.data` mutations (adding new cosigner-set entries) are presumably rare/administrative events (e.g., multisig recovery flows), not something an unprivileged attacker can trigger arbitrarily.
- I could not confirm, from indexed code, that any caller stores/reuses a `multisigDataIndex` value across an await boundary that overlaps with a `data` array mutation - this exists as an unsafe API pattern rather than a demonstrated exploited race.
- The typical usage inspected (`getDefaultAddress`, `#getMultisigAddress` default resolution) resolves the index synchronously right before use, which would not be exposed to the race.

Given the lack of confirmed reachability of a mutation racing a stale index consumption, this should be treated as a design weakness/hardening recommendation rather than a proven high-likelihood vulnerability.

### Recommendation
- Resolve multisig configuration by a stable identifier (`multisigData.id`, which is already present on entries) instead of, or in addition to, positional index, similar to the report's recommendation to use `pluginAddress` instead of `pluginIndex`.
- If positional `multisigDataIndex` must be retained for backward compatibility, re-validate that the resolved entry still matches the caller's expected `id`/fingerprint at the point of consumption, and reject/re-resolve if it does not.
- Avoid caching keyed only by positional `multisigDataIndex`; key by the stable multisig config identifier instead.

### Proof of Concept
Not fully constructible from the indexed codebase alone: I could not confirm a concrete caller that (a) computes/stores a `multisigDataIndex` value, (b) awaits across a point where `multisigWallet.data` can be mutated (e.g., new cosigner data appended via a recovery/rotation flow), and (c) then calls `getAddress`/`getEncodedPublicKey` with the stale index. A conceptual PoC:
1. Wallet account is multisig with `multisigWallet.data = [configA]`.
2. Some flow captures `multisigDataIndex = multisigWallet.data.length - 1` (== 0, `configA`) intending to build/verify an address for `configA`.
3. Before that flow calls `getAddress({ ..., multisigDataIndex: 0 })`, a concurrent operation appends `configB` at index 0 and shifts `configA` to index 1 (or replaces index 0 in-place during a rotation).
4. The original flow's stale `multisigDataIndex: 0` now resolves to `configB` in `#getMultisigAddress` [8](#0-7) , producing an address/script derived from the wrong cosigners.

This should be verified with a live Devin session by tracing all runtime callers of `addressProvider.getAddress`/`getEncodedPublicKey` that pass an explicit `multisigDataIndex`, and any code paths that mutate `multisigAtom`'s `data` array, to determine whether a genuinely reachable TOCTOU window exists.
