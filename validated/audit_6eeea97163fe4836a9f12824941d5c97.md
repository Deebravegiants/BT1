## Finding

### Title
Webhook `shop` field is trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — the raw request body only. The `shop` value that is subsequently handed to app handlers via `WebhookMetadata` is read directly from the unauthenticated `shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. The binding the app relies on — "the `shop` passed to my handler is the shop for which this authenticated body was generated" — does not hold: `shop` (header, unauthenticated) ≠ `shop` (implicitly bound in the signed body).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed straight from a header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string` (the body) against the secret, with no reference to headers such as `shop-domain`: [3](#0-2) 

`Webhooks::Registry.process` only calls this HMAC check, then immediately builds `WebhookMetadata` using `request.shop`, passing it to the app-provided handler as trusted tenant identity: [4](#0-3) 

The library's own documentation reinforces the false sense of full-request verification and explicitly tells integrators that `data.shop` is "The shop domain of the webhook," to be used directly (e.g. for enqueuing per-shop jobs), and states that `process` "will verify the request did indeed come from Shopify."

Because `shop` is excluded from the signed payload, any party who can obtain one genuine `(raw_body, hmac)` pair — trivially available to any developer/merchant who installs the app on their own shop and receives a legitimate webhook for it — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `HmacValidator.validate` will still pass (the body and HMAC are untouched and genuinely valid), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain while the `body` content actually belongs to the attacker's own shop.

### Impact Explanation
This breaks the tenant-isolation binding that `shop` is meant to enforce. In any app that uses `data.shop` (as the docs instruct) to select the tenant record, session, or database row for out-of-band processing of the (also attacker-influenced or attacker-known) `body` — e.g. enqueuing `perform_later(shop_domain: data.shop, webhook: data.body)` as shown in the gem's own webhooks doc — an attacker can inject or overwrite data under a shop domain they do not own. Because `body` is arbitrary attacker-controlled content whose meaning depends entirely on `topic`, this allows cross-tenant data manipulation (e.g., faking `orders/create`, `app/uninstalled`, or `shop/redact` payloads attributed to a victim shop), which is a cross-tenant integrity violation classified as Critical impact under this program's scope.

### Likelihood Explanation
The prerequisite — obtaining one genuine `(raw_body, hmac)` pair — requires no credentials beyond installing the app on any shop, including a free/dev shop the attacker fully controls, which is an unprivileged action normally available to any internet user. Replaying it against the same public webhook endpoint with a modified header is trivial and requires no interception, no `api_secret_key`, and no privileged account. The likelihood is therefore high, limited only by whether a given host application chooses to key off `data.shop` for scoping (which is exactly what the library's documentation recommends).

### Recommendation
Do not treat `WebhookMetadata#shop` (or any other webhook header) as authenticated. Either:
- Extract the shop identity from the signed webhook body's content itself where reliably present, or
- Extend `HmacValidator`/`Request#to_signable_string` so the HMAC verification is bound to the `shop-domain` header (e.g., by validating the header against the shop referenced inside the trusted body, or requiring apps to cross-check `data.shop` against a shop they already expect for that webhook subscription), or
- Clearly document that `data.shop` is unauthenticated and must not be used alone to select which tenant's data to mutate, and always correlate it against an independently established per-shop webhook secret/subscription record if the app implements per-shop secrets.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures the app's webhook callback URL (or attacker simply lets Shopify send a normal webhook, e.g. `orders/create`, to the app's public endpoint).
2. Attacker captures the raw request body `B` and the header `x-shopify-hmac-sha256: H` that Shopify sent for that webhook (this is a legitimate signature for `B`).
3. Attacker resends an HTTP POST to the same app webhook endpoint with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but header `x-shopify-shop-domain` set to `victim-shop.myshopify.com` (and topic header unchanged or altered to `app/uninstalled`, `shop/redact`, etc., since topic also isn't signed).
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to act on victim-shop's identity using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
