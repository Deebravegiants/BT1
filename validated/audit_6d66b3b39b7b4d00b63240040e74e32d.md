## Analysis

I found a concrete instance of the reported bug class — **a field acted on but not covered by the HMAC** — in this gem's webhook processing pipeline.

### Root cause

`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns **only the raw request body**: [1](#0-0) 

The `shop` identity used by the library, however, is read straight from an **unauthenticated HTTP header** (`shopify-shop-domain` / `x-shopify-shop-domain`), which is never fed into the signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which only checks the body-derived signature) and then dispatches to the app's handler **using the unverified `request.shop`** as the tenant identifier: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` confirm the check is scoped to `to_signable_string` only: [5](#0-4) 

### The broken binding (as an equality)

The library's guarantee should be:
`HMAC_valid(body, secret) == true` **implies** `shop-domain header is authentic and bound to that body`

But the actual behavior is:
`HMAC_valid(body, secret)` only proves **the app's shared `client_secret`** produced that body — it says nothing about which shop the header claims it's for.

### Why this crosses a tenant boundary

The webhook secret is the app's `client_secret`, shared across **every** shop that installs the app — it is not shop-specific. Any merchant who installs the app receives their own legitimately-signed webhooks (valid body + valid HMAC for their own events). Because the `shop` header is outside the signed payload, an attacker-merchant can capture one of their own valid `(body, hmac)` pairs and replay it directly to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still pass (the body/HMAC pair is untouched and genuinely valid for the app's secret), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain — causing the app to execute the webhook's logic (which is often tenant-scoped, e.g., updating billing/data/settings for "that shop") attributed to the wrong tenant.

This is a genuine cross-tenant confusion introduced by the gem's own webhook-processing code, not a misuse of a documented API by the host app: `Registry.process` and `HmacValidator.validate` are the library's own security boundary for webhooks, and that boundary silently omits the `shop` field from the authenticated bytes while still trusting it downstream.

### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `#shop` (and `#topic`, `#webhook_id`, `#api_version`) come from unauthenticated headers. `Webhooks::Registry.process` validates the HMAC over the body only, then dispatches to app handlers using the unverified `shop` value.

### Finding Description
Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across all shops that install the app, any merchant/attacker who has installed the app can capture a valid `(body, hmac)` pair from their own legitimate webhook delivery and replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a different, victim shop. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) will report the request as valid because it only checks the body signature, and `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) will call the registered handler with `shop: request.shop` set to the attacker-controlled header value.

### Impact Explanation
This breaks the tenant isolation guarantee that "a validated webhook HMAC implies the accompanying shop/topic metadata is authentic for that shop." An attacker can cause the app to process webhook side effects (data updates, redaction actions, billing events, etc.) under an arbitrary victim shop identity, which is a cross-tenant integrity/confidentiality violation — Critical impact per the stated criteria (cross-tenant access).

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own shop (standard, unprivileged action for any public app) and be able to send arbitrary HTTP requests to the app's public webhook endpoint URL — no access token, secret, or privileged account is required. This is realistic for any publicly reachable Shopify app webhook route.

### Recommendation
Include the shop domain (and topic/webhook id) in the signable bytes validated by `HmacValidator`, or otherwise cryptographically bind the header-derived identity to the signed payload before it is trusted by `Registry.process`. Short of a protocol change, the gem should document this limitation prominently and/or provide a mechanism for host apps to correlate `request.shop` against a shop known to have the webhook_id/topic actually registered.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid for `Context.api_secret_key`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`.
4. The registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
