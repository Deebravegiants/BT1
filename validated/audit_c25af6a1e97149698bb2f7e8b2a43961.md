### Title
Sell path permanently reverts (traps trader funds) whenever `exchangeRate()` implies a payout below the dust floor - (File: `packages/contracts/src/Zap.sol`)

### Summary
`Zap._sellInternal` estimates the USDC value of a sell using the paired LT's live `exchangeRate()` and hard-reverts the whole transaction if that estimate falls below `minUsdcAmount()`. Because `exchangeRate()` is an external, live-read value coming from BounceTech's leveraged token (a rebasing/leveraged price that can legitimately trend toward zero for the reserve side of a curve), this check can become permanently unsatisfiable for a given token, at which point every `Zap.sell` call for that token — the only user-reachable exit path while the token is still on the bonding curve — reverts forever, freezing holders' tokens with no way to redeem value. This mirrors the analog bug class (H-37): an oracle/rate read embedded in a critical, must-not-fail user path (there: liquidation, here: sell/exit) can cause that path to revert unconditionally once the read value crosses a boundary, with no fallback.

### Finding Description
`Zap._sellInternal` executes the curve swap first (transferring the user's tokens into `Zap` and running `_sellOnCurve`/`_sellOnUniswapV2`, which mutates `Pair` reserves), and only afterward estimates USDC value and checks it against a floor: [1](#0-0) 

```
address lt = bonding_.ltOf(tokenAddress);
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenAmount);
uint256 ltReceived = bonding_.isGraduated(tokenAddress)
    ? _sellOnUniswapV2(tokenAddress, lt, tokenAmount)
    : _sellOnCurve(tokenAddress, tokenAmount);

uint256 grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18;
if (grossUsdcEstimate / 1e12 < minUsdcAmount()) revert BelowMinAmount();
```

`exchangeRate()` is read live from the external BounceTech LT and is documented throughout the codebase as a value that "drifts" and can move arbitrarily with the underlying's leverage: [2](#0-1) . Nothing in `Zap` or `Bonding` bounds `exchangeRate()` away from very small values once a token has launched — the only place a lower bound on `exchangeRate()` is enforced is at `launch` time (`_deployAndSeed`'s `ZeroExchangeRate`/`ExchangeRateTooLow` checks, which only run once, at token creation): [3](#0-2) .

If the LT's `exchangeRate()` subsequently decays (leverage decay/rebase toward zero is inherent to leveraged/inverse tokens, and is explicitly acknowledged elsewhere in the code as an accepted risk — see the "Retired LTs" note in the graduation docs: [4](#0-3) ), then for any `ltReceived` a holder can realize from a sell, `grossUsdcEstimate` falls below `minUsdcAmount()` and `_sellInternal` reverts with `BelowMinAmount`. Since the swap has already executed inside the same call (curve reserves already mutated in memory before the revert unwinds), the transaction fails atomically each time — but critically, it fails **every time**, because the condition depends only on the now-depressed `exchangeRate()`, not on any per-call parameter the user controls. There is no way to raise `minUsdcOut`/bypass this internal floor from the caller side, and there is no alternate exit path while the token is still `Lifecycle.Curve` (Bonding's `buy`/`sell` are `onlyRouter`-gated and `Zap` is the router users call).

This is structurally the same defect class as H-37: a rate-derived guard embedded inside a function whose job is to let users unwind/exit a position ends up blocking the exit unconditionally once the rate crosses a threshold, with the code offering no "use old/last-known value" fallback (contrast with how `previewLtUntilGraduation` explicitly guards `if (exchangeRate > 0)` to avoid this exact trap: [5](#0-4) ).

### Impact Explanation
Once a paired LT's `exchangeRate()` decays low enough that any realistic sell size values under `minUsdcAmount()`, every holder of that curve token permanently loses the ability to sell/exit through `Zap` — the sole user-facing sell entry point pre-graduation. This is a permanent freezing of trader funds: their tokens remain, but there is no on-chain path to redeem USDC value for them via the protocol. Given leveraged/inverse tokens are explicitly the reserve asset by design, and per-token leverage decay/collapse toward zero is a known property of such instruments, this is not a purely theoretical edge case but a foreseeable end-state for any curve paired against a token whose underlying trends sufficiently against the leverage direction.

### Likelihood Explanation
No special privilege or attacker action is required — the condition is purely a function of the external LT's natural price decay, which is explicitly acknowledged elsewhere in the codebase as something that can happen ("Retired LTs" / leverage-drift discussion). Any trader holding a curve token paired to a decaying/near-worthless LT will hit this deterministically on every sell attempt. Likelihood is Medium-to-High depending on how commonly LTs decay to sub-dust levels over a curve's lifetime, but the impact (permanent fund freeze) is severe enough to warrant a Medium/High finding regardless.

### Recommendation
Do not let a live rate read hard-revert the exit path. Options:
- Remove or relax the `grossUsdcEstimate`-based `BelowMinAmount` guard on `sell`, since the user's actual protection is already `usdcOut >= minUsdcOut` (slippage check) further down; the pre-redeem dust guard is redundant with that and introduces an unconditional-revert failure mode.
- If a dust floor is still desired, gate it behind an amount the user explicitly opts into (e.g., only enforce when `minUsdcOut` is unset/zero, mirroring the graduation-trigger carve-out already present for that case), or cap/skip the check once `exchangeRate()` is below some protocol-known floor rather than reverting unconditionally.
- More generally, ensure no critical exit-path check depends unconditionally on a live external rate without a fallback, consistent with the design principle already applied in `previewLtUntilGraduation`.

### Proof of Concept
1. Launch a token against a `MockLeveragedToken` (or any BounceTech LT) and let a trader buy in normally.
2. Simulate LT price decay by calling `lt.setExchangeRate(rate)` with `rate` set low enough that `(ltReceived * rate) / 1e18 / 1e12 < minUsdcAmount()` for the trader's full token balance (any realistic sell size).
3. As the trader, call `Zap.sell(tokenAmount, tokenAddress, 0, trader)` (or via `Bonding.sell` routed through `Zap`).
4. Observe the call reverts with `BelowMinAmount` — the transaction rolls back and the trader's tokens are returned to them (i.e., the sell never completes).
5. Repeat step 3 for any `tokenAmount` up to the trader's full balance and for any subsequent block — the revert persists as long as `exchangeRate()` remains depressed, demonstrating that the sell path is permanently unusable for this token, with no way for the trader to realize USDC value for their holdings via the protocol.
