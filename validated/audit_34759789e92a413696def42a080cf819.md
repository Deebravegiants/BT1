### Title
`UpdateParams` relayer can front-run `placeOrder()` to raise `protocolFeeBps`/destination fee and collect additional fees from a specific order - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder()` computes the protocol fee deducted from a user's escrowed inputs by reading the live `_destinationProtocolFees[destinationHash]` / `_params.protocolFeeBps` storage at execution time [1](#0-0) . There is no user-supplied maximum-fee bound (no `minAmountOut`-style guard) in `Order`/`placeOrder`, so the amount actually deducted can silently differ from what the user quoted off-chain.

### Finding Description
The gateway's authorised relayer (a designated but still transaction-ordering-unprivileged deliverer, `_relayer`, enforced only by `_checkRelayer`) is the one who decides *when* to submit a Hyperbridge `UpdateParams` message to `onAccept`, which calls `_updateParams` and can raise `_params.protocolFeeBps` or add/raise a `_destinationProtocolFees[chain]` override [2](#0-1) [3](#0-2) . Message content originates from Hyperbridge governance, but its **delivery timing on the destination chain** is chosen by whichever relayer submits the proof — the same "unprivileged actor picks the moment of inclusion relative to a victim's pending transaction" primitive as the original report's referrer front-run.

A user calls `quoteIntent`/builds an `Order` off-chain using the currently observed `protocolFeeBps`, then submits `placeOrder`. If the relayer observes this pending transaction and races an `UpdateParams` delivery ahead of it (raising `protocolFeeBps` for the order's destination), `placeOrder` will:
1. Transfer the full input amount from the user [4](#0-3) .
2. Deduct a now-higher `protocolFee = originalAmount * protocolFeeBps / 10_000` as "dust" retained by the protocol [5](#0-4) .
3. Escrow only the reduced amount, with **no revert path** for the user even though the fee charged exceeds what was quoted.

This mirrors NAZ-M1 exactly: a fee-rate parameter readable and mutable independently of the transaction that pays it, no `minAmountOut`/max-fee slippage guard on the paying call, and an actor who controls delivery timing (relayer here, referrer/protocol in the original) can extract additional fees from a specific victim transaction.

### Impact Explanation
Every `placeOrder` call is exposed to unbounded fee extraction up to whatever `protocolFeeBps` (or the destination-specific override) is raised to at the moment the relayer chooses to deliver `UpdateParams`. Because the deducted fee is retained on-chain as protocol "dust" (`DustCollected`) rather than validated against the quote the user built the order from, the user has no on-chain assurance of the fee they will actually pay. Docs confirm current deployments intentionally rely on the "quoted" rate matching the live on-chain rate with no protection against races: `docs/content/developers/evm/intent-gateway/placing-orders.mdx` explicitly warns integrators to use `quoteIntent()`'s live value because the protocol fee is read live and not locked in by the order structure [6](#0-5) . This is a direct, unbounded (up to `protocolFeeBps < 10_000`, validated only by `_validateParams`) loss of user funds on every affected order — a concrete theft-of-funds impact, satisfying Medium severity.

### Likelihood Explanation
Requires the relayer authorised for the specific `IntentGatewayV2` deployment (`_relayer`) — or, when the gate is open (`_relayer == address(0)`), *any* relayer — to observe a pending `placeOrder` transaction in the mempool and race a governance-originated fee-update delivery ahead of it. Governance fee changes are infrequent, but the relayer, not governance, controls the exact block in which the change lands, so the relayer can hold a legitimate, already-signed `UpdateParams` proof and wait for a profitable target order to appear before submitting it — a low-cost, repeatable MEV-style strategy requiring no special privilege beyond normal relaying rights.

### Recommendation
Add a caller-supplied bound to `Order`/`placeOrder` (e.g. `maxProtocolFeeBps` or `minEscrowedAmount` per input) and revert if the live `protocolFeeBps` applied at execution exceeds what the user authorized, analogous to `minAmountOut` slippage protection. Alternatively, snapshot/commit the effective fee at quote time with a short-lived signed attestation that `placeOrder` verifies, or apply parameter updates with a timelock/delay so a specific pending order cannot be targeted.

### Proof of Concept
1. Governance signs an `UpdateParams` message raising `protocolFeeBps` from 5 bps to, say, 500 bps (still `< 10_000`, passes `_validateParams`) [7](#0-6) .
2. The gateway's authorised relayer withholds delivery of this proof until it observes a large `placeOrder(order, graffiti)` transaction from a victim in the mempool, built using the previously-quoted 5 bps fee.
3. Relayer submits `[Consensus, UpdateParams]` to `onAccept` in the block/transaction immediately preceding the victim's `placeOrder`.
4. `_updateParams` applies the new 500 bps rate [3](#0-2) .
5. Victim's `placeOrder` executes next, deducting `originalAmount * 500 / 10_000` instead of the expected `originalAmount * 5 / 10_000` — a 100x larger protocol fee than quoted, with the excess retained as dust and no revert triggered [8](#0-7) .

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
