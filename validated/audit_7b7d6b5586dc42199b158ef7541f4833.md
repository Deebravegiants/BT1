### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload solely from the raw request body, while the `shop` (and `topic`/`webhook_id`) values that the registry hands to the app's webhook handler are read from HTTP headers that are never included in that signature. This breaks the intended binding: `shop_delivered_to_handler == shop_that_was_actually_HMAC-authenticated`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is completely outside that signed string: [2](#0-1) 

`HmacValidator.validate` verifies the request against `to_signable_string` (the body only): [3](#0-2) 

`Registry.process` checks that HMAC, then immediately forwards `request.shop` (the unauthenticated header value) as the tenant identity into the handler's `WebhookMetadata`: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the same app, any unprivileged user who installs the app on their own store legitimately receives real webhook deliveries — bodies with valid HMACs computed under that shared secret. Since the `shop-domain` header is never part of the signed material, that user can replay the same `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting a different `shopify-shop-domain` header value naming a victim shop. The signature still validates (it only checks the body bytes), so `Registry.process` accepts the request and calls the handler with `shop: <victim shop>`, even though the actually-authenticated bytes came from the attacker's own shop.

This is exactly the "bytes verified vs. bytes parsed" identity-binding break: `HmacValidator` verifies `raw_body` bytes, but the tenant-identifying field consumed downstream (`request.shop`) is parsed from bytes that were never verified.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` from `Registry.process` to route data into a specific tenant's records (session lookup, database writes, GDPR/customer data handling, etc.) can be made to attribute attacker-controlled webhook data to a different, victim shop — a cross-tenant data-injection/spoofing primitive that only requires an ordinary app install, not any secret leakage or privileged access.

### Likelihood Explanation
Likelihood is limited by needing: (1) the attacker to install the target app on a shop they control to obtain a validly-signed webhook body/HMAC pair, and (2) the host app's webhook handler to trust `WebhookMetadata.shop` for tenant attribution without independently verifying it against its own list of subscribed/known shop-webhook pairings. Both conditions are realistic and require no privileged credentials.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) as part of the HMAC-signed material used for validation, or, failing that, require host applications to cross-check `request.shop` against records of shops that are known to have this specific webhook subscription/topic before trusting it for tenant attribution. At minimum, document explicitly that `request.shop` is unauthenticated and must not be used as a sole tenant-identity source.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, causing the app to legitimately register/receive webhooks (e.g., `orders/create`).
2. Attacker captures a real webhook delivery: raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H`, both computed under the app's shared `client_secret`.
3. Attacker replays a POST to the app's public webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` in [5](#0-4)  succeeds because it only checks `B` against `H`.
5. `Registry.process` in [4](#0-3)  invokes the handler with `shop: "victim.myshopify.com"`, causing attacker-controlled body content to be processed/stored as if it belonged to the victim tenant.
