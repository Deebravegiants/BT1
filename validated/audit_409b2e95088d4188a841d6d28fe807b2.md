### Title
Webhook shop-domain is trusted for tenant attribution without HMAC coverage - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant attribution from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body, never the shop-domain header. This breaks the intended identity binding `hmac-authenticated bytes == bytes acted on for tenant identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Request#shop` is read straight from the `shop-domain` header, independent of that signed payload: [2](#0-1) .

`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e. only the body) and compares against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) . Once that body-only HMAC passes, `Registry.process` immediately forwards `request.shop` — the unauthenticated header value — to the app's handler as the tenant identity: [4](#0-3) .

This is precisely the "field acted on but not covered by the HMAC" class of bug named in the report's rules: the cryptographic check binds the caller to the body bytes, but the `shop` field that host applications use to select a tenant/session for processing the webhook is never part of that binding.

### Impact Explanation
Because `shop-domain` is unauthenticated, any request whose body+HMAC pair is valid for **some** shop (e.g., the attacker's own shop, which legitimately receives webhooks with a correctly computed HMAC for that body) can be replayed with an arbitrary `shop-domain` header value substituted in. `HmacValidator.validate` will still return true because it only recomputes the HMAC over `raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different shop than actually signed the payload. Any host application that uses `WebhookMetadata#shop` to select the merchant/session record to update (a very common pattern for webhook processing) can be made to apply an attacker-controlled payload to a victim tenant's data — a cross-tenant identity confusion rooted entirely in this gem's validation logic.

### Likelihood Explanation
Exploitation requires only capturing or generating one valid `(raw_body, hmac)` pair, which any merchant with the app installed can obtain from their own genuine webhook deliveries (no `api_secret_key` needed). No privileged access, TLS interception, or token theft is required — only the ability to send an HTTP request to the app's webhook endpoint with a modified `shop-domain` header, which satisfies the "unprivileged internet user" threat model.

### Recommendation
- **Short term:** Include the shop domain (and other identity-relevant headers/claims, e.g., topic, webhook id, api version) in the string that is HMAC-verified, or otherwise cryptographically bind the `shop-domain` header to the signed body before it is trusted in `Registry.process`.
- **Long term:** Ensure any identity value forwarded to caller code (`WebhookMetadata#shop`) is derived only from data that was part of the verified/signed payload, not from independently-supplied, unauthenticated headers.

### Proof of Concept
1. Attacker owns/operates Shop A with the app installed and receives a legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with the same body `B` and same `hmac` header `H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC of `B` — this succeeds because `B` and `H` are unchanged: [5](#0-4) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...)` and processes body `B` as if it legitimately originated from Shop B: [6](#0-5) .

Note: I could not locate a `webhook_metadata.rb` file in the index to confirm the exact struct fields beyond what is passed at the `WebhookMetadata.new` call site shown above; this may be due to index size limits, and a full session may be needed to inspect that file directly if further verification is required.
