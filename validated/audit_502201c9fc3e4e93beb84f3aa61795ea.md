### Title
POA Bridge misreports withdrawal status/hash for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal's on-chain completion status/txHash by `assetId` alone rather than by the caller-supplied `index`, so when a single NEAR intent batches multiple withdrawals of the same token, every withdrawal in that batch resolves to the status/txHash of whichever entry the API/​`.find()` happens to return first, regardless of which specific withdrawal (destination, amount) is actually being queried.

### Finding Description
`describeWithdrawal` retrieves all withdrawals tied to the originating NEAR transaction hash and picks a match using `findMatchingWithdrawal`, which filters strictly by `assetId`: [1](#0-0) [2](#0-1) 

The code comment acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), but nothing in the SDK actually prevents a caller from constructing a batched withdrawal intent containing two or more `withdrawalParams` entries with the same `assetId` but different `destinationAddress`/`amount`. `createWithdrawalIdentifier` builds a `WithdrawalIdentifier` per withdrawal that carries an `index`, but that `index` is never used in `describeWithdrawal`/`findMatchingWithdrawal` to disambiguate which specific withdrawal's status is being requested: [3](#0-2) 

Because `Array.prototype.find` returns only the first matching element, calling `describeWithdrawal` for `index: 0` and `index: 1` of a same-asset batch returns the identical `withdrawal` record (same `status`, same `transfer_tx_hash`) for both indices. `watchWithdrawal`, which drives integrator-visible completion, simply forwards whatever status/hash `describeWithdrawal` returns: [4](#0-3) 

This breaks the equality "status/hash reported for withdrawal N == the actual on-chain outcome for withdrawal N": an integrator polling withdrawal index 1 (destined for address B) will be told it completed with the txHash that actually corresponds to the on-chain payout for withdrawal index 0 (destined for address A).

### Impact Explanation
An integrator (exchange, custody service, or any system that credits users based on `WithdrawalStatus.completed` + `txHash`) that processes batched same-token withdrawals will get a false "completed" attestation with a wrong/duplicate `txHash` for at least one of the withdrawals in the batch. This matches the "High" bucket: "a status or hash misreport making an integrator credit or refund twice" — the integrator may credit a user as if their specific withdrawal settled on-chain when it did not (or double-count the same on-chain transfer as fulfilling two separate withdrawal obligations).

### Likelihood Explanation
Reachability requires only that an unprivileged caller submit a batched withdrawal intent (multiple `withdrawalParams` in one NEAR transaction) with the same `assetId` appearing more than once. Nothing in `PoaBridge.supports`, `validateWithdrawal`, or the batching path in `sdk.ts` rejects duplicate `assetId` entries in a batch, so this is triggerable purely by normal API usage, not by exploiting a privileged actor.

### Recommendation
Disambiguate `findMatchingWithdrawal` using additional caller-supplied identifying fields (destination address, amount, and/or index/ordering) instead of `assetId` alone, or explicitly reject/validate batched withdrawals that contain duplicate `assetId`s before submission so the ambiguous case can never reach `describeWithdrawal`.

### Proof of Concept
1. Caller submits one NEAR transaction containing two POA-bridge withdrawals with the same `assetId` (e.g., `nep141:btc.omft.near`), different `destinationAddress`es (`addrA`, `addrB`), via the batch withdrawal flow, obtaining `tx.hash = H` and identifiers `{index:0, ...}` and `{index:1, ...}`.
2. The POA bridge indexer/API eventually completes both withdrawals, returning entries under `GET withdrawal_hash=H` with two withdrawal records sharing `near_token_id = "btc.omft.near"` but different `address`/`transfer_tx_hash`.
3. Calling `bridge.describeWithdrawal({..., index: 0, tx:{hash:H}})` and `bridge.describeWithdrawal({..., index: 1, tx:{hash:H}})` both invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which uses `.find()` and returns the **same** first-matching record for both calls.
4. Result: the caller watching index 1 (destined for `addrB`) is told `{status:"completed", txHash: <addrA's transfer_tx_hash>}` — a status/hash that does not correspond to that withdrawal's actual on-chain outcome.

		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
