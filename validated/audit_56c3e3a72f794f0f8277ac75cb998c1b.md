## Title
Session-token audience confusion allows non-admin (checkout) session tokens to be exchanged for full merchant access tokens - (File: `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/jwt_payload.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` accepts *any* JWT that decodes successfully and has `aud == Context.api_key`, without checking that the token was actually issued as an **admin embedded-app session token** (`iss` ending in `/admin`). The same `api_secret_key` is used by Shopify to sign both admin session tokens and Checkout UI Extension session tokens (as shown by the two fixture payloads in the test suite), and both carry the same `aud`. Because `JwtPayload` never binds `iss`/token-purpose to what `exchange_token` is allowed to consume, a lower-privilege customer-facing session token can be replayed through the token-exchange endpoint to mint a full offline/online **merchant** access token.

### Finding Description
`JwtPayload#initialize` only validates the signature and the `aud` claim: [1](#0-0) 

It does expose an `admin_session_token?` helper that checks whether `iss` ends with `/admin`, but that helper is only used internally to gate `shopify_user_id`: [2](#0-1) 

`TokenExchange.exchange_token` builds a `JwtPayload` from the caller-supplied `session_token` and immediately trusts its `dest` claim as the shop to exchange for a token — it never calls `admin_session_token?` or otherwise rejects tokens whose `iss` shows they were issued for a different purpose (e.g., Checkout UI Extensions): [3](#0-2) 

The test fixtures confirm that both admin embedded-app tokens and Checkout UI Extension tokens are signed with the same `api_secret_key` and share the same `aud` value, differing only in `iss`/`sub` semantics: [4](#0-3) 

The identity binding that should hold is: `token.iss (admin session) == token type consumable by exchange_token`. Instead, the code only enforces `token.aud == Context.api_key`, i.e. any signed token for the app — regardless of the surface it was issued for — is treated as an admin session token capable of unlocking a full-scope offline/online access token via `POST /admin/oauth/access_token` using the app's `client_id`/`client_secret`.

### Impact Explanation
If a host application passes through a session token obtained from a less-privileged, more widely exposed context (e.g., a Checkout UI Extension token supplied by client-side JS to the app's backend for customer identification) into `exchange_token`, this library will happily exchange it for a full merchant `access_token` (offline or online) with the shop, because it never checks `iss`. This is a scope/token-type confusion that results in escalation from a customer-scoped identity token to a merchant-level access token — matching the "scope or expiry check bypass" / credential-theft impact class, since the resulting access token is a merchant access token obtained via a token that was never meant to authorize backend admin access.

### Likelihood Explanation
Exploitability depends on a host app design that forwards non-admin session tokens (e.g. from a checkout extension) into `exchange_token`, or on any other future/alternate distribution channel of app-secret-signed JWTs whose `iss` is not `/admin`. Because the library itself provides no enforcement, it pushes the entire trust decision onto every integrator, and the gem's own `JwtPayload` class already computes `admin_session_token?` yet does not apply it here — indicating incomplete binding enforcement within the gem itself rather than solely an integrator error.

### Recommendation
In `TokenExchange.exchange_token`, reject any session token whose `iss` does not end with `/admin` (i.e., call `jwt_payload.send(:admin_session_token?)` or expose/enforce this check publicly) before proceeding with the exchange, so only genuine embedded-admin session tokens can be exchanged for merchant access tokens.

### Proof of Concept
1. Attacker/integrator obtains a Checkout UI Extension session token for shop `victim.myshopify.com`, signed with the app's `api_secret_key`, with:
   `iss: "https://victim.myshopify.com/checkouts"`, `dest: "victim.myshopify.com"`, `aud: <app client_id>`.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: checkout_extension_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new` accepts the token (only `aud` is checked) and `dest_shop` = `"victim.myshopify.com"` is used to request an offline access token via `/admin/oauth/access_token`, returning a full merchant-scoped `ShopifyAPI::Auth::Session`, despite the origin token never being an admin session token.

          unless ShopifyAPI::Context.setup?

          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,

            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
