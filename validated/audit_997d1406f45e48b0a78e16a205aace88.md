### Title
Webhook `shop` identity is trusted from an HTTP header that is outside the HMAC-covered scope, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` (and `topic`/`api_version`/`webhook_id`) values taken from HTTP headers that are never included in the signed material. This breaks the intended identity binding `hmac_signed_bytes == tenant_identity_bytes`: the signature proves the *body* came from a holder of `api_secret_key`, but it proves nothing about which shop that body belongs to, because the shop identifier travels in an unsigned header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cross-check against anything inside the signed body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on that HMAC check alone, then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and hands it to the app's handler as the authenticated tenant context: [4](#0-3) 

Equality that should hold but does not:
`bytes_covered_by_hmac == identity_bytes_acted_on`

Before the request sequence: a legitimately delivered webhook for Shop A has `raw_body = B`, `hmac = HMAC(secret, B)`, `shop header = "shop-a.myshopify.com"`. The signature is valid over `B` only.

Attacker's request sequence: capture/replay this valid `(B, HMAC(secret,B))` pair (e.g. from a webhook the attacker's own dev store received, or from a `network log`/proxy able to relay it, or simply from a webhook the attacker legitimately triggered on a shop they control), and re-send it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to `"shop-b.myshopify.com"` (or any arbitrary shop domain string, since it is never validated against a known-shops list by the gem).

After the request: `HmacValidator.validate` still returns `true` (it only re-hashes `B`), so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)`. The handler — following this gem's documented contract, which explicitly hands it `data.shop` as the trusted tenant identifier — will act on Shop A's payload as if it belonged to Shop B (or an attacker-chosen arbitrary string), e.g. persisting attacker-controlled body content under a foreign or fabricated shop key, or triggering shop-scoped side effects (uninstall/GDPR handling, order/product mutations, cache invalidation) keyed to the wrong tenant.

### Impact Explanation
This crosses the tenant boundary the HMAC is meant to enforce: `shop` is the sole tenant discriminator surfaced by this gem's webhook API, and it is unauthenticated. An attacker who can capture one valid `(body, hmac)` pair for any shop (including their own store, which they legitimately control) can relabel it as belonging to a different, victim shop when replaying it to the app. This is a cross-tenant access vector — data or actions intended for shop A's webhook get attributed to shop B purely by header manipulation, with the gem providing no defense (no comparison of the header-derived shop against any signed field, no per-shop webhook secret binding).

### Likelihood Explanation
The attacker does not need `api_secret_key`: they only need one previously observed valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on a store the attacker controls and capturing the webhook the app receives for that store — and the ability to POST to the app's public webhook endpoint with modified headers, which is always internet-reachable for webhook receivers. No TLS interception, credential leakage, or privileged access is required.

### Recommendation
Bind the shop identity to the HMAC-covered payload: verify that the header-derived `shop` matches a shop value that can be derived from, or cross-checked against, the signed body/topic (or require callers to look up an existing installed-shop session and reject webhooks whose header shop was never associated with a token issued for that exact HMAC secret instance), rather than trusting the `shopify-shop-domain` header on its own once the body HMAC passes.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own store "attacker-shop.myshopify.com"
#    and captures a legitimate webhook delivery:
raw_body   = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker replays the SAME body+hmac but swaps the shop-domain header
#    to a victim shop they do not control:
spoofed_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # not covered by hmac at all
  "x-shopify-webhook-id"   => "any-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)

# 3. HMAC validation succeeds (it only checks raw_body), and the handler
#    is invoked believing this data belongs to "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}))
```
`request.shop` returns the attacker-controlled header value while `HmacValidator.validate(request)` returns `true`, confirming the shop identity is never bound by the signature.
