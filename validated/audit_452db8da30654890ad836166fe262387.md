### Title
Webhook `shop-domain` is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the shop identity (`shop-domain` header) that is handed to the app's webhook handler is read from an unsigned header. This breaks the binding `bytes verified == bytes acted on`: the HMAC proves the body came from Shopify using the app's secret, but it proves nothing about which shop the event belongs to. A holder of any single valid `(body, hmac)` pair (trivially obtainable by triggering a webhook on their own installed shop) can replay that pair to the app's webhook endpoint with an arbitrary `shop-domain` header and have the app process the event as if it originated from a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The shop identity used by the handler is read from a header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the raw body via `Utils::HmacValidator.validate`, and then, once validation passes, dispatches to the handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, none of which are covered by the signature: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC strictly against `verifiable_query.to_signable_string` (i.e., the raw body only): [4](#0-3) 

Because `topic`, `shop`, `webhook_id`, and `api_version` are all sourced from headers outside the signed payload, the equality that should hold — "the shop attributed to this event equals the shop the HMAC signature was computed for" — does not hold. The signature authenticates the body bytes and proves the request came from an entity that possesses the app's `client_secret` (i.e. genuinely from Shopify, for *some* shop/topic), but the mapping of that authenticated body to a specific `shop`/`topic` is left to unauthenticated headers that the caller fully controls.

### Impact Explanation
This is a cross-tenant identity binding failure analogous to the referenced report's core issue: a value (there, `_value`; here, the `shop` identity) is combined with/attributed to an actor without being covered by the authentication mechanism (there, no credit-usage authorization; here, no HMAC coverage of `shop-domain`). An attacker who is a legitimate installed merchant on Shop A can capture one authentic `(body, hmac)` pair from their own shop's webhook delivery, then send an HTTP request directly to the app's webhook endpoint with the identical body/HMAC but with the `shop-domain`/`x-shopify-shop-domain` header rewritten to Shop B (the victim). `Registry.process` will validate the HMAC (which only checks body bytes) and hand the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-controlled body content, injecting spoofed webhook events into the victim's tenant data pipeline — a cross-tenant access/confusion condition.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action requiring no special credentials) can generate as many valid `(body, hmac)` pairs as they like by simply operating their own shop (e.g., creating/updating orders, products, etc., which triggers registered webhooks). Capturing this traffic requires only observing the request the app receives at its own public webhook endpoint (which the attacker controls as the receiving app owner is not required — the attacker only needs to see their own outgoing webhook, e.g. via a debug proxy on their own server) or, in many app setups, simply reusing their own subscribed webhook payloads which they can trivially inspect. No access to `api_secret_key`, tokens, or the victim's data is required.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed payload used for verification, or perform verification through a canonicalized string that binds body + shop + topic together, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `code`, `state`, and `timestamp` together for OAuth callback validation: [5](#0-4) 
At minimum, document that consuming applications must not trust `request.shop` for authorization decisions unless it is independently corroborated against a known/expected shop for that webhook subscription.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and triggers a webhook (e.g., updates a product) causing Shopify to POST a signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some JSON body.
2. Attacker observes/logs this `(raw_body, hmac)` pair from their own delivered webhook.
3. Attacker (or a script) sends a new HTTP POST directly to the same app webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) — validation succeeds because the body/HMAC pair is genuinely valid. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `request.shop` is `"victim.myshopify.com"`, even though the payload/HMAC only ever proved authenticity for `attacker.myshopify.com`'s event. [7](#0-6)
