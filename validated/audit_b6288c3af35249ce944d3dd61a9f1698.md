### Title
Unauthenticated `CallDispatcher.dispatch` allows front-running theft of predispatch/output-call assets - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` executes an arbitrary array of `Call{to, value, data}` for **any caller**, with no check that the invocation originated from the `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents` orchestrator that is supposed to be the sole legitimate caller. This mirrors the reported flash-loan bug class: a privileged-looking callback (`dispatch`) trusts that it is only reachable through the intended orchestration flow, but never verifies "the initiator is the contract itself" (or an authorized caller), letting anyone impersonate the gateway's intended execution context.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes a `Call[]` and executes each entry via low-level `call{value: call.value}(call.data)` — with **no access control whatsoever**: [1](#0-0) 

The intended usage is exclusively from `IntentsBase._execute`, which is called by `ExtrinsicIntents._fillCrossChain` / `IntrinsicIntents._fillSameChain` after the gateway has already transferred order-output tokens to the dispatcher, expecting only the gateway to invoke `dispatch` with its own `Call[]` and then sweep any residual balance back to itself: [2](#0-1) 

Because `CallDispatcher` has a `receive()` and can transiently hold ETH/ERC20 balances (assets are sent to it for predispatch swaps, or output-call execution, before being swept back to the gateway), any window where it holds a non-zero balance is an unauthenticated attack surface: an attacker can call `dispatch` directly, before the gateway's own sweep/execute completes, supplying `Call[]` that drains `CallDispatcher`'s current native/token balance to an address they control. This is the same root cause as the reported issue — a shared/callback entry point (`executeOperation`/`onFlashLoan` in the analog, `dispatch` here) does not verify that the call originated from the expected orchestrator (`initiator == address(this)` in the analog; here, `msg.sender == intentGateway`) — allowing an unprivileged third party to hijack execution that was meant to be exclusively driven by the trusted contract.

### Impact Explanation
If `CallDispatcher` ever holds a non-zero balance (predispatch assets awaiting swap-then-escrow, or output-call assets awaiting fill-then-act, or residual dust before the sweep call in `_execute`), any address can call `dispatch` directly and route those funds anywhere via arbitrary `call{value}(data)`. This is concrete theft of user/solver funds in transit through the dispatcher — a Medium/High severity issue depending on how often/how large a balance the dispatcher transiently holds and whether it is reachable, e.g., via reentrancy or front-running mid-transaction. Impact scope: user escrowed assets sent to `CallDispatcher` for predispatch execution, or solver output assets awaiting postdispatch execution/sweep.

### Likelihood Explanation
Likelihood depends on whether an attacker can observe a moment when `CallDispatcher` holds a non-zero balance and is not atomically protected. Within a single transaction (`placeOrder`'s predispatch or `fillOrder`'s postdispatch), the dispatcher's balance changes happen inside one atomic call sequence, so a purely external front-run cannot interleave — but any call path where `dispatch` is invoked separately from the transfer-in step (e.g., partial execution failing mid-sequence, or a future integration that sends assets to the dispatcher ahead of a `dispatch` call in a different transaction) would make this directly and trivially exploitable, since `dispatch` performs zero validation of `msg.sender`. Given the contract is designed to be a shared, standalone utility (also referenced from `HyperFungibleToken`/`BridgeToken`/etc.), it is more attack-prone than a bespoke internal helper: any future or mistaken funding path exposes 100% of the balance to theft.

### Recommendation
Add an authorization check in `CallDispatcher.dispatch` restricting the caller to the specific orchestrator address(es) permitted to drive it (e.g., an owner/allowlist set at construction, or a `require(msg.sender == authorizedCaller)` check), analogous to the recommended `require(initiator == address(this))` fix in the flash-loan report. Alternatively, redesign so that `CallDispatcher` never persists a balance outside of the atomic call that funds and drains it (i.e., verify no balance exists at the start/end of unrelated transactions), and add reentrancy protections around the transfer-in → dispatch → sweep sequence in `IntentsBase._execute`.

### Proof of Concept
1. Assume/observe (or induce via a partially-failed multi-step operation) a state where `CallDispatcher` holds a non-zero ERC20 or native balance intended for a legitimate order's predispatch/output-call execution.
2. As an unrelated attacker, call `CallDispatcher.dispatch(abi.encode(Call[]))` directly with `Call{to: attackerControlledToken/Contract, value: dispatcher.balance, data: transferOrCallToAttacker}`.
3. Since `dispatch` has no caller restriction ( [1](#0-0) ), the call succeeds and the funds are redirected to the attacker instead of being routed to the intended beneficiary or swept back to the `IntentGatewayV2`.

**Note on uncertainty**: I was unable to fully trace every call path across the repository that funds `CallDispatcher` (e.g., `HyperFungibleToken`/`BridgeToken` usages) within the tool-call budget, so I cannot confirm with certainty whether a real-world transaction sequence leaves a *persistent* (cross-transaction) balance on `CallDispatcher` today — within `IntentsBase._execute` the fund-then-dispatch-then-sweep sequence appears to complete atomically in the observed code. The root architectural weakness (no caller authentication on `dispatch`) is nonetheless real and directly analogous to the reported bug class; a Devin session with full repository access should verify all callers of `ICallDispatcher.dispatch` to confirm whether any code path leaves an exploitable balance window.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
