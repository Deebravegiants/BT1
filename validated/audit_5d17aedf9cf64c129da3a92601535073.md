### Title
Unsanitized swap routes inject unauthorized token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept attacker-controlled `swap` bytes and forward them to the configured router without restricting which pool or token contracts the route invokes. A malicious route can therefore place attacker-controlled contract code beneath the caller’s `require_auth` context and inject unrelated token-transfer sub-invocations into the signed authorization tree.

### Finding Description
`swap_collateral` exposes a caller-supplied `swap: Bytes` argument and passes it to `process_swap_collateral` for an account owned or delegated to the caller. [1](#0-0)  The strategy authenticates the caller and verifies account authority, but preserves the supplied `swap` payload. [2](#0-1)  `swap_tokens` only rejects an empty payload, authorizes the controller’s exact input transfer, and calls `router.execute_strategy(controller, amount_in, swap)` inside the flash guard. [3](#0-2) 

The route payload is not constrained by the controller to a trusted venue set, and the threat model explicitly notes that the router invokes payload-selected pool and token addresses without an allowlist. [4](#0-3)  A malicious hop can consequently execute during the swap and call `token.transfer(victim, attacker, amount)` for a token unrelated to the lending operation. [5](#0-4) [6](#0-5) 

The regression test shows that transaction simulation records this rogue transfer as a child of the caller’s `swap_collateral` authorization, and that signing the returned poisoned tree executes the theft. [7](#0-6) [8](#0-7) 

### Impact Explanation
This is theft of user funds beyond the collateral being swapped. The malicious hop can transfer any victim-held token whose transfer authorization is attached to the signed tree, while the swap itself still returns a valid output and passes the controller’s positive-output and post-position risk checks. [9](#0-8)  The controller’s measured input/output checks bound only the controller-held swap input and do not bound extra child authorizations executed against the caller’s wallet. [10](#0-9) 

### Likelihood Explanation
The attacker must induce a victim to submit a maliciously constructed route and sign the authorization tree produced by simulation. This is feasible where routes are opaque quote-service bytes or where clients do not reject unexpected child invocations, but it requires victim authorization rather than being a purely self-contained attacker transaction. [11](#0-10)  The issue is reachable from the unprivileged `swap_collateral` path and also applies to the other strategy entrypoints that accept non-empty route bytes. [12](#0-11) 

### Recommendation
Restrict strategy routes to governance-approved venues, or decode and validate every hop at the controller boundary so the payload cannot name arbitrary pool or token contracts. At minimum, make clients reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` authorization tree containing child invocations other than the expected exact input transfer. [13](#0-12) 

### Proof of Concept
1. Alice owns a debt-free account with USDC collateral and an unrelated wallet-token balance. [14](#0-13) 
2. The attacker supplies a route whose hop pool is a malicious contract configured with `(victim = Alice, wallet_token, to = attacker, amount = Alice's balance)`. [15](#0-14) 
3. Alice invokes `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, malicious_route)`. [16](#0-15) 
4. During router execution, the malicious hop calls `wallet_token.transfer(alice, attacker, amount)`. [6](#0-5) 
5. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization; if Alice signs that returned tree, the entire unrelated wallet-token balance moves to the attacker while the lending swap succeeds. [17](#0-16) [8](#0-7)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
