### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that reads the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature verified via `Utils::HmacValidator.validate` only covers `@raw_body` (`to_signable_string` returns `@raw_body` alone). This is the same "field acted on but not covered by the HMAC" class of defect described in the source report (fee computed on an amount not covered by the intended base), applied here to tenant identity instead of a numeric amount.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

`Request#hmac` decodes the `hmac-sha256` header for comparison, and `Request#shop` is read from a completely separate header (`shop-domain`) that plays no part in the signed payload: [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header: [3](#0-2) 

Because the HMAC is computed purely over the body bytes and the shared `client_secret`, and does not incorporate `shop-domain`, the equality the caller actually needs — "the shop identity used by downstream tenant-scoped logic == the shop for which Shopify computed this HMAC" — is never checked. The library only proves "this body was signed with our secret"; it does not prove "this body was signed for shop X." Any request carrying a body+HMAC pair that is valid for the app's secret (e.g., a legitimately received webhook for shop A, replayed by an attacker who controls or intercepts webhook delivery for shop A, or reflects a body an attacker can otherwise obtain) can be resubmitted with an arbitrary `shopify-shop-domain` header, and `Request#shop` will report the attacker-chosen tenant while `Request#hmac` still validates successfully, since neither header is part of the signed content.

Contrast with `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed parameters: [4](#0-3) 

The webhook path has no equivalent binding of `shop` (or `topic`/`webhook_id`) into the signature; the gem's `Request` class exposes `shop` as if it were an authenticated attribute of the request, when in fact it is unauthenticated header data, sitting alongside a signature that authenticates only the body.

### Impact Explanation
Downstream host applications are expected to use `request.shop` (after `Utils::HmacValidator.validate` returns true) to determine which merchant/tenant the webhook payload belongs to, in order to load that shop's session/access token and apply the payload. Since the gem allows the `shop` value to pass validation-adjacent code unauthenticated, an attacker who can reuse or forge a valid `(raw_body, hmac)` pair for the app's secret — e.g., by capturing a legitimately delivered webhook body/HMAC (webhook contents/HMACs are not necessarily treated as secret by merchants or intermediate infrastructure, and Shopify's own webhook delivery can be replayed by any party that can observe an HTTP request in transit or via app logs/queues) — can relabel it to a victim shop's domain. Any host code that trusts `ShopifyAPI::Webhooks::Request#shop` as authenticated (which the gem's API implicitly encourages, since it's exposed on the same object whose `hmac` was "validated") would process the payload as belonging to the wrong tenant, i.e., a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Medium: it requires the attacker to already possess a valid `(body, hmac)` pair, which is not secret and not scoped to a specific shop by the signature scheme itself — the gem's own `to_signable_string` guarantees the signature carries no shop binding, so any replay vector (log exposure, network capture without TLS termination being required at the attacker, shared body content, multiple-shop batch webhooks with identical body shape, etc.) is sufficient. The root cause is deterministic and always present, since `to_signable_string` never includes `shop`.

### Recommendation
Include the shop-identifying header (and ideally `topic`/`webhook_id`) inside the signed content compared against the HMAC, i.e., change `Request#to_signable_string` to bind `shop`, `topic`, and `raw_body` together (mirroring `AuthQuery#to_signable_string`), or otherwise document/enforce that `shop` must be re-derived from a value that Shopify itself HMAC-signs rather than from an independent header. At minimum, the library should not expose `shop` as a plain accessor on the same object whose HMAC is validated without clarifying that this attribute is not covered by the HMAC and must be cross-checked against a separately authenticated source (e.g., cross-referenced with the app's own shop/session table via a value that was authenticated at OAuth time).

### Proof of Concept
1. Shopify sends a legitimate webhook for `shop-a.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(client_secret, B)`.
2. `Request.new(raw_body: B, headers: {"shopify-hmac-sha256" => H, "shopify-shop-domain" => "shop-a.myshopify.com", ...})` is validated with `Utils::HmacValidator.validate(request)` → passes, because `to_signable_string` only checks `B` against `H`.
3. An attacker who obtains `(B, H)` (e.g., through log access, a proxy, or replay of an intercepted delivery) constructs a new request with the same `B` and `H` but `headers["shopify-shop-domain"] = "shop-victim.myshopify.com"`.
4. `Utils::HmacValidator.validate` still returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`), and `Request#shop` now returns `"shop-victim.myshopify.com"` (per `lib/shopify_api/webhooks/request.rb:20-23`), even though Shopify never issued a webhook with that shop/body/HMAC combination — demonstrating that `shop` is not bound by the signature the gem validates.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
