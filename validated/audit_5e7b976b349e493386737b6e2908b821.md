### Title
Unauthenticated escrow drain via `IntentGatewayV2` (Tron) instance-fallback authentication bypass - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-targeted `IntentGatewayV2` contract authenticates incoming cross-chain ISMP messages by checking that the `from` field of a `PostRequest` equals the registered peer-gateway address for `request.source`. When no peer is registered for a given source chain, `instance()` silently falls back to `address(this)` instead of reverting, unlike the hardened `IntentsBase._instance()` used by the mainline EVM gateway. This lets anyone deploy an arbitrary contract at the same address as the Tron gateway on any chain that Hyperbridge can produce valid consensus/state proofs for, and use it to submit forged governance/escrow-release messages that the Tron gateway will treat as coming from itself.

### Finding Description
`instance()` in the Tron gateway is defined as: [1](#0-0) 

Compare this with the fixed/hardened pattern used by the current mainline EVM implementation, `IntentsBase._instance()`, which reverts with `UnknownInstance()` instead of falling back to `address(this)`: [2](#0-1) 

and is wired into authentication via `ExtrinsicIntents._authenticate()`: [3](#0-2) 

The Tron gateway's `authenticate()` uses the vulnerable, non-reverting `instance()`:
```
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
```
Because `_instances[keccak256(stateMachineId)]` defaults to `address(0)` for any chain that has never had a `NewDeployment` registered, `instance(unregisteredSource)` returns `address(this)`. An attacker who deploys a contract with the identical bytecode/CREATE2 salt as the legitimate gateway (or simply controls a contract whose address collides with the gateway's own address on a different, unregistered state machine) can dispatch a genuine ISMP `PostRequest` from that chain with `from = address(gatewayOnTron)`. When this message is relayed through Hyperbridge with a legitimate consensus/state proof for that (unregistered, attacker-controlled) chain, `authenticate()` passes because `instance(request.source)` resolves to `address(this)`, matching the forged `from` field — despite the source chain never having been trusted or registered as a peer.

Unlike the mainline gateway, this Tron variant has no separate relayer allowlist gate (`_checkRelayer`) guarding delivery, so authentication is the only barrier standing between an attacker and privileged `RequestKind` operations, including `RedeemEscrow` (release escrowed tokens to an attacker-chosen beneficiary) and `RefundEscrow`, as well as governance-like operations (`NewDeployment`, `UpdateParams`, `SweepDust`).

### Impact Explanation
A successful forgery lets an attacker submit a `RedeemEscrow` request for any real order commitment and redirect the escrowed input tokens to a beneficiary of their choosing, effectively stealing user funds locked in the gateway — a concrete theft-of-funds scenario. It can also be used to forge `NewDeployment`/`UpdateParams` messages that corrupt the gateway's trusted peer set or fee configuration, compounding the damage to future orders. This matches the "concrete theft of funds" / "unauthorized app action" criteria for Medium/High severity.

### Likelihood Explanation
The exploit requires only: (1) deploying/controlling a contract on some state machine that Hyperbridge can produce a valid consensus proof for and that has never been explicitly registered as an `IntentGatewayV2` peer on the Tron deployment, with an address matching the Tron gateway's own address (achievable via CREATE2 factories, which are widely available and use predictable, attacker-controllable salts/bytecode); and (2) dispatching a normal ISMP `PostRequest` from that contract. No privileged role, admin action, or governance compromise is needed — a single relayed message from an unprivileged chain suffices, making this reachable by any unprivileged relayer/attacker submitting a proof through the normal delivery path.

### Recommendation
Change `instance()` (and `authenticate()`) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert when no explicit peer is registered for `request.source`, mirroring `IntentsBase._instance()`'s `revert UnknownInstance()` behavior, so unregistered/unknown source chains can never authenticate as the gateway itself. Additionally, consider adding a relayer allowlist gate (as in `ExtrinsicIntents._checkRelayer`) to this Tron variant for defense in depth.

### Proof of Concept
1. Do not register the attacker's chain state-machine id via a `NewDeployment` message on the Tron `IntentGatewayV2` (i.e., `_instances[keccak256(attackerChainId)] == address(0)`).
2. Deploy a contract at the same address as the Tron `IntentGatewayV2` on the attacker-controlled/unregistered state machine (e.g., via a public CREATE2 factory with matching salt/bytecode, or simply pick any chain where such a collision already exists).
3. From that contract, dispatch an ISMP `PostRequest` to the Tron gateway with:
   - `source = attackerChainId` (unregistered)
   - `from = abi.encodePacked(address(attackerContract))` (equal to the Tron gateway's own address)
   - `body = bytes.concat(bytes1(uint8(RequestKind.RedeemEscrow)), abi.encode(WithdrawalRequest({commitment: <real order commitment>, tokens: <escrowed tokens>, beneficiary: attackerAddress})))`
4. Relay this request through Hyperbridge with a valid consensus/state proof for `attackerChainId` (a legitimate proof is obtainable since the attacker genuinely controls that chain/contract).
5. `onAccept` calls `authenticate(request)`, which computes `instance(attackerChainId) == address(this)` (fallback) and compares to `module == address(attackerContract) == address(this)` — the check passes, and the gateway executes `RedeemEscrow`, releasing the victim's escrowed tokens to the attacker's beneficiary.
