### Title
Cross-Tenant Shop Attribution via Unsigned `shop-domain` Header in Webhook Processing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking the HMAC of the raw request body, but the `shop` value that is subsequently handed to the app's handler as the tenant identifier is read from an HTTP header that is **not** part of the HMAC-signed payload. Any actor capable of producing (or replaying) one valid `(raw_body, hmac)` pair for the shared app secret can attach an arbitrary `shopify-shop-domain` header and have the webhook attributed to a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC over `to_signable_string`, which for webhooks is only the raw body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled from headers that are outside this signed string: [2](#0-1) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identity passed into the handler, with no separate binding between the signed bytes and the shop claim: [3](#0-2) 

The resulting `WebhookMetadata#shop` field is the only tenant identity the app receives from this gem for the webhook: [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is a single, shared per-app secret (not per-shop), the equality the gem is supposed to guarantee is:

`shop that authored the signed bytes == shop attributed to the event`

but what is actually enforced is only:

`HMAC(api_secret_key, raw_body) == received_hmac`

with the `shop-domain` header free to be set to any value independent of the body/HMAC. A party that can obtain one legitimate `(raw_body, hmac)` pair issued for the app (e.g., a merchant who installed the app and can observe/replay their own store's outbound webhook traffic to a locally exposed endpoint, or any actor who otherwise captures a valid webhook delivery) can resend that exact body+hmac to the app's public webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value with a different shop's domain. The gem will report `Utils::HmacValidator.validate` as `true` (body unchanged) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant isolation guarantee the gem is expected to provide to host applications: the `shop` value delivered via `WebhookMetadata#shop` is the field host apps use to look up/scope data (e.g., locate the correct merchant record, access token, or database row) for the webhook payload. An attacker who can produce this cross-tenant attribution can cause the host application to apply another shop's data mutations, GDPR/redaction actions, or business logic under the wrong tenant context — a cross-tenant access condition, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(body, hmac)` pair for the shared app secret. This is realistically obtainable by any shop that has installed the app (a legitimate but unprivileged relationship relative to other shops on the same app) since Shopify delivers real webhooks with valid HMACs to that shop's configured endpoint; the attacker only needs to capture and replay that traffic with a modified `shop-domain` header pointed at the app's public webhook URL. No access to `api_secret_key`, access tokens, or the target shop's credentials is required, satisfying the "unprivileged internet user" constraint, though it does require the attacker to be a shop that has installed the app or otherwise obtain a valid signed webhook body.

### Recommendation
Bind the shop (and topic/webhook id) into the signed material, or otherwise cryptographically/authoritatively verify that the `shop-domain` header corresponds to the shop that actually owns the delivered event (e.g., cross-check against the shop recorded when the specific webhook subscription/topic was registered, or use per-shop webhook secrets/verification tokens) before exposing `WebhookMetadata#shop` to handlers.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) pointed at a locally observable endpoint (e.g., via a captured/proxied request).
2. Shopify delivers a legitimate webhook to that endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{"id":1,...}`
3. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's production webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header; `Utils::HmacValidator.validate` succeeds because it only checks the untouched body against the untouched HMAC.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
