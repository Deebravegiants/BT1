### Title
Webhook shop/topic/webhook_id identity fields are trusted without HMAC coverage, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values from unauthenticated HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.), while `to_signable_string` — the value actually covered by the HMAC check in `ShopifyAPI::Utils::HmacValidator.validate` — is only the raw request body. This breaks the equality that the identity of the tenant ("shop") acted upon should equal the tenant the HMAC was computed for.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from caller-supplied HTTP headers with no cryptographic binding to that body: [2](#0-1) .

`ShopifyAPI::Webhooks::Registry.process` validates only via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (the body) — it never validates that `shop`/`topic`/`webhook_id` are authentic — and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, passing them straight to the host app's handler as trusted data: [3](#0-2) .

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it against the `hmac` header value: [4](#0-3) . Because the shared `client_secret` used to sign a webhook is identical for every shop that has installed the app (it's the app's secret, not a per-shop secret), and many webhook bodies do not embed the originating shop domain (e.g. minimal/filtered payloads, or bodies that happen to be identical across two different shops/stores), a valid `(raw_body, hmac)` pair obtained from a webhook delivered to the attacker's own (unprivileged) store can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to name a victim shop. `HmacValidator.validate` will still succeed because the signed bytes (the body) are unchanged, yet `Registry.process` reports the event as belonging to the victim shop to the handler.

The library's own documentation confirms the intended trust model — that `Registry.process` "will verify the request did indeed come from Shopify," implying `data.shop` can be trusted by the handler: [5](#0-4) , and the handler docs describe `shop` as "The shop domain of the webhook": [6](#0-5) . Nothing in `Registry.process` or `Request` cross-checks the shop header against the signed content, so this expectation of trust is unmet for the shop/topic/webhook_id fields specifically.

### Impact Explanation
This is a Critical cross-tenant access vector: an unprivileged attacker who has installed the app on their own store (a normal, unprivileged action available to anyone) can capture a legitimate `(body, hmac)` pair from a webhook Shopify sends them, then replay it to the shared webhook endpoint with a forged `shop-domain` header pointing at any other merchant that has installed the same app. Since `Registry.process` treats `Utils::HmacValidator.validate` as sufficient proof of authenticity for the whole request — including the shop identity used by the handler to route/attribute data — the host application (following the gem's documented contract) will process attacker-controlled events under another tenant's identity, e.g. triggering tenant-scoped side effects, cache invalidation, order/product state changes, or logging keyed to the wrong shop.

### Likelihood Explanation
Likelihood is realistic for topics with generic, shop-invariant bodies (e.g., `app/uninstalled`, filtered payloads via the `fields` parameter, or any topic whose JSON body doesn't include the shop domain), since installing a free/dev store and receiving one real webhook is trivial and requires no privileged credentials, tokens, or the app's `client_secret`.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) inside the HMAC-signed material used by `Request#to_signable_string`, or independently verify that the shop asserted in the header matches a shop the app has an active, previously-established installation/session for before dispatching to the handler, rather than trusting the header value outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own (unprivileged) Shopify dev store and registers for a webhook topic whose payload body does not vary by shop (e.g., a filtered/empty-body topic).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and body `B`.
3. Attacker captures `(B, valid-hmac-of-B)` and replays a POST to the same app endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`) while keeping body `B` and the same `hmac` header unchanged.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `B` only, which still matches, so `Registry.process` accepts the request and invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host app to act as if the event originated from the victim tenant.
