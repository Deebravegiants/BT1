### Title
Webhook `shop` identity is derived from an unauthenticated header, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` attribute — the value the gem and its documented consumers use to attribute a webhook to a specific merchant/tenant — is read directly from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed data.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` field [2](#0-1) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header [3](#0-2) [4](#0-3) . The `shop` accessor, however, is populated straight from the `shop-domain` header without any cryptographic binding to the body/HMAC [5](#0-4) .

`ShopifyAPI::Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body integrity) and then forwards `request.shop` unchanged to the app's handler via `WebhookMetadata` [1](#0-0) . The gem's own documentation instructs integrators to treat `data.shop` as the authoritative tenant identifier for looking up sessions/access tokens and enqueuing background work: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [6](#0-5) .

This breaks the identity binding: `shop authenticated (HMAC-covered bytes) != shop used as the tenant/session key (unauthenticated header)`. An attacker who can install the target app on their own store (a normal, unprivileged action) legitimately receives a genuinely-HMAC-signed webhook whose body and HMAC are valid for their own shop. Because the `shop-domain` header is outside the signed payload, the attacker can replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` reports the forged victim shop to the handler as `request.shop`.

### Impact Explanation
This qualifies as Critical — cross-tenant access. A host application relying on `data.shop`/`request.shop` (as documented) to select which merchant's session/access token an incoming webhook body should be applied to can be tricked into associating attacker-controlled webhook content with a victim shop's tenant record, or into triggering victim-scoped side effects (e.g., cache invalidation, order/product sync, job enqueuing "as" the victim) using data the attacker fully controls.

### Likelihood Explanation
Any developer who installs the target Shopify app on their own store can capture a fully valid signed webhook and simply resend it with a different `shop-domain`/`x-shopify-shop-domain` header value; no access to the app's `client_secret`, an access token, or the victim's credentials is required, and the gem performs no additional binding check between the signed body and the shop header.

### Recommendation
Include the shop identifier (and ideally topic/webhook id) in the HMAC-signed material used for webhook verification, or otherwise cryptographically bind `shop-domain` to the payload before trusting it (e.g., compare it against `Registration`/subscription records tied to a specific shop rather than trusting the header value directly). At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` and downstream consumers should not treat the `shop-domain` header as authenticated data derived from the HMAC check.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the request to the same webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"` [8](#0-7) , causing attacker-controlled body `B` to be processed as if it were an authentic webhook for the victim shop.
