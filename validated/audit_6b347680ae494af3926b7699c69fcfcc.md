### Title
Webhook shop identity spoofing via HMAC bypass on unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then reads the `shop` (and `topic`, `webhook_id`) values from HTTP headers that are never included in the signed content. An attacker who can obtain one valid `(body, hmac)` pair for the app — e.g. from a webhook delivered to their own shop, since the HMAC secret (`api_secret_key`) is shared by the app across every installed shop — can replay that exact body/HMAC while substituting an arbitrary `shop-domain` header. The library will treat the forged request as authentic and hand the handler a `WebhookMetadata` claiming it originated from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` only checks `hmac` against `to_signable_string` (the body), never the headers: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then immediately trusts `request.shop` as the authenticated tenant identity, forwarding it to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop` reported to the handler == `shop` cryptographically bound to the signed bytes. Instead, the equality actually enforced is only `HMAC(body, api_secret_key) == received_hmac`; `shop` is disjoint from what's signed, so any `shop-domain` value can be attached to a validly-signed body.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying full authenticity of the delivered data including its shop attribution — which is not actually true for the `shop` field: [5](#0-4) 

### Impact Explanation
Because `api_secret_key` is shared across all shops that install the app, any merchant/tenant who installs the app can trigger a genuine webhook to their own endpoint, capture a valid `(body, hmac)` pair, and replay it with a forged `shop-domain` header naming a different (victim) shop. Handlers built on `WebhookMetadata#shop` (as documented and shown in the sample handler) will process the payload as authoritative data for the victim shop — enabling cross-tenant data injection/corruption in any host application that keys persistence, authorization, or business logic off `data.shop` without independent verification. This satisfies the "cross-tenant access" criteria for Critical impact.

### Likelihood Explanation
Exploitation only requires the attacker to be an authenticated user of the multi-tenant app (i.e., install it on their own shop to receive one legitimate signed webhook) — no access to `api_secret_key`, TLS interception, or privileged account is needed. Replaying the HTTP request with a modified header is trivial once one valid signed body is obtained.

### Recommendation
Bind the shop identity into the signed content that `HmacValidator` verifies (e.g., include the `shop-domain`, `topic`, and `webhook-id` header values in `to_signable_string`), or, at minimum, clearly document that `shop`/`topic`/`webhook_id` are unauthenticated request metadata and that host applications must independently verify the reporting shop has an active installation/session before trusting the payload. The current documentation's assurance that `process` "verifies the request did indeed come from Shopify" should be corrected or the verification scope broadened to match that claim.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`: [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, and any host logic keyed on `data.shop` now acts on attacker data as if it came from the victim shop.
