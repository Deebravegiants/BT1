### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body alone, while the `shop` (and `topic`/`webhook_id`) values used downstream by webhook handlers come from unauthenticated HTTP headers that are never mixed into the signed input.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then forwards the header-derived `shop` straight to the app's handler: [3](#0-2) 

This is the same bug class as the report: the identity field that the handler acts on (`shop`) is not part of the data that was cryptographically verified (`sig`/`hmac` only covers the body). Note also that Shopify's `api_secret_key` (the HMAC key) is the app's single client secret, shared across every merchant/shop that installs the app — it is not a per-shop secret. An attacker who installs the target app on their own (attacker-controlled) shop will legitimately receive HTTP webhook deliveries whose body+HMAC pair are valid under the app's shared secret. If the attacker can replay that HTTP request to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, `HmacValidator.validate` still succeeds (it only checks `@raw_body`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop for data that actually originated from the attacker's own store.

### Impact Explanation
If a host application uses `request.shop`/`WebhookMetadata#shop` to select which tenant's session/data to mutate (a documented, expected usage pattern for this gem), an attacker can spoof `shop-domain` on a header level and inject or corroborate crafted webhook payloads under an arbitrary victim shop identity — a cross-tenant impact using the app's own legitimately valid signature.

### Likelihood Explanation
Requires only that the attacker be an unprivileged user who can install the target app on any store (a normal/free Shopify Partner action) and can send an arbitrary HTTP request to the app's public webhook endpoint with a modified header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the shop identity (and topic/webhook id) into the HMAC-signed input, or require the host app to independently authenticate that `request.shop` corresponds to a shop that has an active, previously-established session/installation before trusting header-provided identity fields, consistent with `to_signable_string`'s contract (`lib/shopify_api/utils/verifiable_query.rb`).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic; Shopify delivers a POST with a body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only recomputes the digest over `to_signable_string`, i.e. `B`.
5. `Registry.process` calls the app handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if the (attacker-supplied) payload came from the victim shop.
