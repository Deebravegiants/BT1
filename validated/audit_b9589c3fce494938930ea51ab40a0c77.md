### Title
Webhook `shop-domain` header is trusted without HMAC coverage, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is never covered by that HMAC — to build the `WebhookMetadata` passed to the application's handler. This breaks the intended binding `hmac_signed_bytes == identity_bytes` and lets a holder of any one validly-signed webhook body substitute an arbitrary `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is not part of the signable string: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC only over `verifiable_query.to_signable_string` and compares it against the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` calls this validator and, once it passes, immediately builds `WebhookMetadata` using `request.shop`, which came straight from the unauthenticated header, and hands it to the app's registered handler: [4](#0-3) 

Because the HMAC only proves "this body was produced with the app's secret," and not "this body belongs to shop X," any party who can obtain one legitimately-signed webhook body/HMAC pair (e.g., a merchant on their own shop who receives real webhooks from their own installation) can resend that exact body+HMAC while substituting a different `shop-domain` header. `HmacValidator.validate` still succeeds because the signature check only depends on `@raw_body`, but `request.shop` — and therefore `WebhookMetadata#shop` delivered to the handler — now reflects an attacker-chosen tenant identity that was never authenticated.

This is the same root-cause pattern as the analog report: an identity-relevant field (`shop`) is acted upon downstream but is not covered by the cryptographic check (`hmac`) that gatekeeps the request. The equality that should hold — `hmac_valid(raw_body) ⟺ shop_header_is_authentic` — does not hold, because `hmac_valid` only binds to `raw_body` bytes.

### Impact Explanation
Downstream applications (following this gem's documented pattern, e.g. `shopify_app`) use the `shop` value from `WebhookMetadata` to look up per-tenant sessions/records and process shop-scoped data (order/customer updates, uninstall handling, GDPR data requests, etc.). Since this value is unauthenticated relative to the HMAC, an attacker can cause the app to process webhook data under the identity of a different shop than the one that actually produced it — a cross-tenant confusion vector. Depending on the handler's logic (e.g., "delete data for shop X", "mark shop X uninstalled", or session lookups keyed by `shop`), this can lead to cross-tenant data corruption or actions performed against the wrong tenant.

### Likelihood Explanation
Requires only an unprivileged actor who possesses one valid `(raw_body, hmac)` pair signed by the app's secret — trivially obtainable by any merchant that has installed the app and receives real webhooks from Shopify for their own store. No access to `api_secret_key`, tokens, or privileged accounts is needed; the attacker simply replays a legitimate payload to the app's own public webhook endpoint with a modified shop header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is cryptographically bound to the HMAC check, or otherwise verify that `request.shop` matches a shop already known/authorized by the app (e.g., cross-check against an existing session for that shop) before constructing `WebhookMetadata`. At minimum, document clearly that `shop` in `WebhookMetadata` is not authenticated by the HMAC and must not be trusted as tenant identity without additional verification.

### Proof of Concept
1. Attacker operates their own shop `attacker-shop.myshopify.com` with the vulnerable app installed; the app registers a webhook for e.g. `orders/create`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures this request and resends it to the same endpoint, keeping body `B` and the same valid `hmac` header, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `HMAC(secret, B)` against the header — still valid, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"`, per `lib/shopify_api/webhooks/registry.rb:198-199`, even though `victim-shop` never sent this webhook.
