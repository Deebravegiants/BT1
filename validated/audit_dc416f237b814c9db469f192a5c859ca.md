### Title
Malicious swap route can execute hidden caller-signed token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller forwards an attacker-controlled `StrategySwap` payload to the configured router without constraining which venue contracts that route can invoke. A malicious venue can therefore place an unrelated `token.transfer(victim, attacker, amount)` beneath the victim’s `require_auth` tree; if the victim signs the simulated authorization tree, the router still returns a valid output while the venue drains unrelated wallet assets. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts caller-supplied `swap` bytes, authenticates only the caller and ownership/delegation, and reaches `withdraw_and_swap_from_supply` with that opaque route. [3](#0-2) 

`swap_tokens` snapshots balances, grants the router one exact controller-token transfer, invokes `router.execute_strategy`, and then validates only controller input/output deltas and final account risk. [4](#0-3) 

Those checks do not bound what route-selected code does under the transaction-level caller authorization. The threat model states that unallowlisted route destinations can put third-party code below the caller’s authorization, causing an unauthorized-looking wallet transfer to be recorded as a signed child invocation. [5](#0-4) 

The regression test demonstrates the concrete behavior: a payload-selected pool calls `token.transfer(victim, attacker, amount)`, simulation records it as a child of `swap_collateral`, and enforcement succeeds when the victim signs that poisoned tree. [6](#0-5) [7](#0-6) 

### Impact Explanation
The attacker can steal arbitrary wallet tokens from the victim, including assets unrelated to the lending position and never approved as swap input. The protocol-visible swap can remain economically valid, so balance-delta checks, minimum route output, and post-trade health checks do not prevent the unrelated transfer. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
A victim must sign the transaction whose simulated authorization tree includes the malicious child transfer. This is realistic when a quoting UI or routing service supplies opaque `StrategySwap` bytes and the wallet does not prominently explain that the route grants an unrelated token transfer. The same pattern can be reached through route-accepting strategy entrypoints such as `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [10](#0-9) [11](#0-10) 

### Recommendation
Do not rely on opaque routes traversing arbitrary venue contracts while the user’s transaction authorization is active. Route execution should isolate the caller’s authority, use a dedicated router-owned input allowance rather than a caller-auth tree that can gain unrelated children, or expose and enforce a signed manifest of every expected token transfer and external invocation. Clients should additionally reject any simulated `execute_strategy` authorization tree containing children other than the expected input transfer. [12](#0-11) [13](#0-12) 

### Proof of Concept
1. The victim owns a lending account and holds an unrelated token in the same wallet. [14](#0-13) 
2. The attacker deploys a pool contract whose `swap` function calls `token.transfer(victim, attacker, wallet_balance)`. [15](#0-14) 
3. The attacker supplies a route naming that pool and a fair `token_out` payment. [16](#0-15) 
4. The victim invokes `swap_collateral(caller=victim, account_id, current=USDC, from_amount=5000 USDC, new=ETH, swap=malicious_route)`. [17](#0-16) 
5. Simulation records the unrelated wallet transfer under the victim’s `swap_collateral` authorization, and signing that tree moves the full unrelated wallet balance to the attacker while the victim receives the expected ETH collateral. [18](#0-17)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

final risk gate bounds it. An honest swap strategy gives the caller no child

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
