The analog bug class matches a genuine issue in this gem's webhook processing.

## Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are all taken from HTTP headers that are never part of the signed payload. `Registry.process` validates the HMAC over the raw body only, then trusts the unauthenticated `shop` header as the tenant identifier passed to the app's webhook handler.

## Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from headers, entirely outside the HMAC-covered content: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant binding passed to the handler: [4](#0-3) 

The identity binding the code implicitly assumes is: `HMAC(raw_body) valid` ⇒ `shop header == the shop that produced this body`. This equality does not hold because `shop` is never an input to the HMAC. Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which correctly includes `shop`, `code`, `state`, `host`, and `timestamp` in the signed content: [5](#0-4) 

so the OAuth callback path does bind `shop` to the signature, but the webhook path does not.

## Impact Explanation
Any party who can obtain one valid `(raw_body, hmac)` pair produced for the app (e.g. from a webhook delivered to their own installed store, which they legitimately receive) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header value. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and `Registry.process` forwards the attacker-chosen `shop` value into `WebhookMetadata`, which the host application uses to attribute the event/data to a tenant. This is a cross-tenant identity confusion: the app processes data under a shop that never actually authorized or produced it, potentially triggering shop-scoped side effects (data writes, entitlement changes, uninstall/reinstall handling, etc.) against a victim shop's record using attacker-controlled body content for shared/generic webhook topics.

## Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or `client_secret` — only a body/HMAC pair the attacker already legitimately possesses from their own store's webhook deliveries, plus the ability to send an unauthenticated HTTP POST to the app's public webhook endpoint with a forged `shop` header. Any app using `ShopifyAPI::Webhooks::Registry.process`/`Request` as documented is affected.

## Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC verification, not just the raw body — e.g., by requiring the host app's webhook route to independently verify that the `shop` header corresponds to a known, previously-installed shop before dispatching to handlers, or by having `Registry.process` cross-check `request.shop` against a shop registered/expected for that specific webhook subscription rather than trusting the header verbatim once body-HMAC passes.

## Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `H = HMAC(secret, B)`).
2. Attacker resends the identical `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop: "victim.myshopify.com", hmac: H...})` is constructed.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body, ...))` is invoked, and the host app processes attacker-controlled body content attributed to `victim.myshopify.com`.
