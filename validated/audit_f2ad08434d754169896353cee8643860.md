This is a strong finding: `TokenExchange.exchange_token` and `Auth::Oauth.validate_auth_callback` both send the app's `client_secret` (and, in OAuth's case, the `code`) in a POST body to a host built directly from an untrusted shop-derived string, without ever routing it through `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, unlike every other credential-issuing path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before building the request host.

### Title
Missing shop-domain validation lets a crafted `dest`/`shop` value redirect the app's `client_secret` to an attacker-controlled host in `TokenExchange.exchange_token` and `Oauth.validate_auth_callback` - (File: `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Utils::ShopValidator.sanitize!` exists specifically to guarantee that any `shop` string used to build an admin API host is a trusted `*.myshopify.com`/`*.myshopify.io`/etc. domain [1](#0-0) . Three of the four credential-exchange flows enforce this invariant before constructing the `HttpClient`/`Session` that will carry `client_secret` to the destination host: `ClientCredentials.client_credentials` [2](#0-1) , `RefreshToken.refresh_access_token` [3](#0-2) , and `TokenExchange.migrate_to_expiring_token` [4](#0-3) . However `TokenExchange.exchange_token` — the primary, documented, recommended flow for embedded apps — takes the shop straight from the JWT `dest` claim without any call to `ShopValidator` and immediately builds a `Session`/`HttpClient` that POSTs `client_id`, `client_secret`, and the caller-supplied `session_token` to that host [5](#0-4) . Likewise, `Auth::Oauth.validate_auth_callback` takes `auth_query.shop` and immediately builds `Auth::Session.new(shop: auth_query.shop)` / `auth_base_uri(shop)`, POSTing `client_id`, `client_secret`, and `code` to `"https://#{shop}/admin/oauth/access_token"` with no `ShopValidator` check at all [6](#0-5) [7](#0-6) .

### Finding Description
The binding that should hold is: **host receiving `client_secret` == a value that has passed `ShopValidator`'s trusted-domain check**. For three of the four flows this equality is enforced explicitly. For `exchange_token` and `validate_auth_callback`, the host is instead taken directly from attacker-influenceable input (`dest` claim of a JWT decoded only for signature/`aud`/`exp` — never checked against `ShopValidator`; and `auth_query.shop`, which is only checked to have a *matching* HMAC over the tuple it appears in, not to be an actual myshopify host) [8](#0-7) .

Note the important root-cause nuance versus the reentrancy report's "reentrant call" bug class: here the analogous bug class is "host validated versus the host that receives the `client_secret`" — the check that exists in the library (`ShopValidator`) is applied inconsistently across otherwise-parallel code paths, so the safety net that the sibling functions rely on is silently absent in `exchange_token` and `validate_auth_callback`.

### Impact Explanation
If the `dest` claim (`exchange_token`) or `shop` field (`validate_auth_callback` — which is itself typically populated by the host app from a query parameter/redirect before HMAC binding is even applicable) can be steered to a non-Shopify host (e.g. via a malformed or attacker-supplied domain that still round-trips through the flow), the gem will issue an HTTPS POST containing the app's live `client_secret` to that host. That is direct `client_secret` exfiltration — a Critical-severity outcome per the rules (theft of the app's `client_secret`). It also enables SSRF carrying the app's credentials to an arbitrary host.

### Likelihood Explanation
Medium: for `exchange_token`, exploitation requires the ability to influence the JWT's `dest` claim path (the JWT itself is HS256-signed with the app secret so a raw forgery isn't possible without the secret — but this is exactly why sibling flows still defensively sanitize the shop even though it originates from data the library trusts elsewhere, and why the *absence* of the same defense-in-depth here is the flagged inconsistency). For `validate_auth_callback`, `auth_query.shop` participates in the HMAC signature, but the HMAC only proves the six-tuple was signed together — it does not prove `shop` is a `*.myshopify.com` value, so any code path that constructs a spoofed but internally-consistent HMAC'd query (or reuses `auth_query.shop` outside its original signed context, e.g. after passing shop validation elsewhere in a host app that doesn't re-validate) reaches the vulnerable host construction with no library-side backstop.

### Recommendation
Call `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain` with explicit failure handling) on `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`/`HttpClient`, and on `auth_query.shop` in `Auth::Oauth.validate_auth_callback` before constructing `null_session`/calling `auth_base_uri`, mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Conceptual (library-level) trace showing the missing check:
1. In `exchange_token`, `dest_shop = jwt_payload.shop` is derived purely from the JWT `dest` claim with no `ShopValidator` call [9](#0-8) , contrasted with `migrate_to_expiring_token`'s `validated_shop = Utils::ShopValidator.sanitize!(shop)` two methods below in the same file [10](#0-9) .
2. `Clients::HttpClient.new(session: shop_session, ...)` then issues `POST https://#{dest_shop}/admin/oauth/access_token` with `client_secret` in the JSON body [11](#0-10) .
3. Equivalently, `validate_auth_callback` builds `auth_base_uri(shop)` → `"https://#{shop}/admin"` with no trusted-domain check at all [12](#0-11) , then POSTs the same `client_secret`-bearing body to that host [13](#0-12) .

I was not able to fully confirm within index limits whether any caller-side/library guarantee (outside `lib/shopify_api/**`, e.g. Shopify's JWT issuance guarantees for `dest`) makes `dest`/`shop` unconditionally trustworthy in all deployment configurations; this affects confidence in likelihood but not in the root-cause code-path inconsistency itself, which is directly verifiable in-file.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]

            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
