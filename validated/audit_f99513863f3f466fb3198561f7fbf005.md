### Title
Webhook shop/topic/id attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` only feeds the raw request body into the HMAC verification, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the host application uses to attribute and route the webhook are read directly from unauthenticated HTTP headers. Any actor who can obtain one validly-signed webhook body (e.g. by installing the target app on their own store, which is available to any unprivileged Shopify merchant) can replay that body with a forged `shopify-shop-domain` header pointing at a victim shop, and the signature check still passes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id` and `api_version` are pulled straight out of the (attacker-controllable, when replayed) HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Webhooks::Registry.process` validates only the body/HMAC pair via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` handed to the application's registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`: [4](#0-3) 

The identity binding the gem implicitly claims to enforce is:
`shop that authored/authorized the signed body == shop attributed to the webhook (request.shop)`

In reality the equality only holds for `hmac == HMAC(api_secret_key, raw_body)`; `request.shop` is completely outside that equation. Because `api_secret_key` is the single client secret shared by an app across **all** of its shop installations (not a per-shop secret), any merchant who installs the app on their own store receives a webhook whose body/HMAC pair is valid for that same secret. That merchant can then replay the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected those headers, and `Registry.process` dispatches the forged payload to the handler labeled as coming from the victim shop.

### Impact Explanation
Host applications commonly use `WebhookMetadata#shop` as the tenant key to look up per-shop state (stored access tokens, database records, feature flags) before acting — this is the intended and documented usage pattern of this field. Because the shop attribution is unauthenticated, an attacker can cause the application to process attacker-controlled webhook data under a victim shop's identity, corrupting per-tenant state or triggering shop-scoped side effects (e.g. writes performed using the victim's stored access token) — a cross-tenant confusion that crosses the tenant boundary this field is meant to enforce.

### Likelihood Explanation
Exploitability requires the attacker to have genuinely installed the target app on at least one shop they control (a normal, unprivileged action for any Shopify merchant, requiring no leaked secrets or elevated access) so they can harvest one valid `(raw_body, hmac)` pair, then send a crafted HTTP request with a spoofed `shopify-shop-domain` header directly to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable payload verified by `HmacValidator`, or otherwise cryptographically bind the shop attribution to the request (e.g. cross-check the header shop against a shop that is known to have an active session with a matching webhook subscription/id before trusting `request.shop` for handler dispatch), rather than trusting the unauthenticated `shopify-shop-domain` header on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a real webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(api_secret_key, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the same body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` (it only checks `B` against the secret) — `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Webhooks::Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and invokes the app's handler as if the event legitimately originated from the victim shop — `lib/shopify_api/webhooks/registry.rb:188-200`.
