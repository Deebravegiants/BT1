### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request body, but then hands the handler a `shop` value that is read from the `X-Shopify-Shop-Domain` header — a field never included in the HMAC computation. Because the app's webhook HMAC secret (`api_secret_key`) is the same for every shop/tenant that has the app installed, any user who can trigger one legitimate webhook for their own (attacker-owned) shop obtains a valid `(raw_body, hmac)` pair that remains valid no matter what shop-domain header accompanies it. Replaying that pair with a victim shop's domain in the header causes the app's handler to process attacker-controlled webhook content as if it were authentic data from the victim's store — a cross-tenant identity binding break.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

Only `@raw_body` is fed into `to_signable_string`, so the HMAC is computed purely over the body. Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with zero cryptographic linkage to the signed content: [2](#0-1) 

`HmacValidator.validate` confirms only that the body was signed with the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` performs no additional binding check between the verified body and the header-derived `shop`/`topic`/`webhook_id` before dispatching to the handler: [4](#0-3) 

The equality that should hold but does not is: **shop that produced/authorized the signed payload == shop attributed to the payload by the handler**. Since `api_secret_key` is a single per-app secret shared across all installed shops (not shop-specific), a valid `(body, hmac)` pair generated from a webhook delivered to shop A remains a valid signature for that same body regardless of which `shop-domain` header is attached — the signature proves only "signed by this app's secret", not "belongs to shop X". An attacker who installs the app on a shop they control can capture such a pair (e.g. via a customer/order webhook they trigger themselves) and replay it to the app's public webhook endpoint with the header swapped to a victim's `myshopify.com` domain.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` (as instructed in the gem's own documentation) to key tenant-scoped storage, queue jobs, or apply per-shop business logic (e.g., `perform_later(shop_domain: data.shop, webhook: data.body)`, mirrored in the docs example), the attacker can inject arbitrary attacker-chosen webhook payloads that are processed as originating from a victim shop. This is a cross-tenant data confusion/injection primitive stemming purely from a gap in this gem's own request-authentication design — the shop field an app is told to trust is never bound to the signature the gem itself validates.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on their own (or any) Shopify development/trial store — a normal, unprivileged action any internet user can take — to receive one legitimately signed webhook; and (2) the ability to POST an HTTP request with arbitrary headers to the app's public webhook endpoint, which is by design internet-reachable. No `api_secret_key`, access token, or privileged account is required. This is a highly reachable, low-effort attack path.

### Recommendation
Bind the shop identity to something authenticated, or ensure the shop used by handlers is verified against the app's own installation records (e.g., cross-check `request.shop` against a shop the app has stored a valid session/access token for before dispatching), rather than trusting the raw header value implicitly. At minimum, document/require verification of `data.shop` against known installed shops in `Registry.process`, or extend `HmacValidator`/`Request#to_signable_string` design to make clear that `shop`, `topic`, and `webhook_id` are unauthenticated metadata that callers must independently corroborate before using for tenant-scoped decisions.

### Proof of Concept
```ruby
# Step 1: Attacker installs the app on their own shop and receives a real webhook,
# capturing the exact raw_body and its valid HMAC (computed with the shared api_secret_key):
raw_body = '{"id":1,"note":"attacker-controlled content"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Step 2: Attacker replays the same (raw_body, hmac) pair to the app's webhook endpoint,
# but swaps the shop-domain header to point at a victim shop:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # not covered by hmac
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (it only checks raw_body against the shared secret),
#    and the registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker JSON),
#    despite the payload never being produced/authorized for that shop.
```

          received_signature = verifiable_query.hmac
