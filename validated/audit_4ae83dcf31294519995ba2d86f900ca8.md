Audit Report

## Title
Nil pointer dereference (node crash / DoS) on `MethodPublicKeyGet` gateway messages missing `params` - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `MethodSecretsCreate/Update/Delete/List` through `GatewayVaultRequestProcessor.ProcessRequest`, whose per-method handlers explicitly check `req.Params == nil` before dereferencing, but `MethodPublicKeyGet` is dispatched directly to `handlePublicKeyGet` with no such check. Since `handlePublicKeyGet` unconditionally executes `json.Unmarshal(*req.Params, r)`, a JSON-RPC request with method `vault.publicKeyGet` and an omitted `params` field causes a nil-pointer dereference panic.

## Finding Description
In `HandleGatewayMessage` [1](#0-0) , the `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` branches call `h.requestProcessor.ProcessRequest(...)`, and that processor's per-method handlers all guard against nil params, e.g. `processCreateSecretsRequest` [2](#0-1) , `processDeleteSecretsRequest` [3](#0-2) , and `processListSecretIdentifiersRequest` [4](#0-3) .

By contrast, `case vaulttypes.MethodPublicKeyGet:` calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly [5](#0-4) , and `handlePublicKeyGet` dereferences `*req.Params` with no prior nil check [6](#0-5) . If `req.Params` is nil (JSON `params` field omitted), this line panics with a nil pointer dereference.

The request reaches this code via the connector's read loop, which unmarshals the incoming gateway message into `jsonrpc.Request[json.RawMessage]` and dispatches straight to `handler.HandleGatewayMessage` based on `req.Method`, with no vault-specific params validation at that layer [7](#0-6) . I confirmed there is no `recover()` wrapping this dispatch path in `core/services/gateway/connector/connector.go` or elsewhere under `core/services/gateway/`, so an unrecovered panic in this goroutine will propagate.

Notably, `handleSecretsDelete` and `handleSecretsList` also dereference `*req.Params` without their own nil check [8](#0-7) [9](#0-8) , but they are only reached after `ProcessRequest`'s nil-check has already succeeded, so they are safe. `handlePublicKeyGet` is the only handler on this dispatch path that is invoked without going through that validation, confirming the claim's core distinction is accurate.

## Impact Explanation
An unrecovered panic in the goroutine that processes gateway messages (the connector's `readLoop` goroutine, per `core/services/gateway/connector/connector.go`) will, absent a top-level recover elsewhere in the runtime/service supervisor, crash the node process or at minimum terminate that goroutine, degrading the node's ability to service Vault gateway messages. This maps to an in-scope availability/DoS impact against a DON-member node's Vault capability.

## Likelihood Explanation
Triggering this requires only sending a JSON-RPC request with `method` set to the value of `vaulttypes.MethodPublicKeyGet` and no `params` field — no authentication, valid vault owner, or JWT is needed, since the code path that would normally validate/authorize params (`ProcessRequest`) is never invoked for this method. This is trivial to construct and repeat, and is reachable from an unprivileged caller able to route messages through the Gateway.

## Recommendation
Add a nil check for `req.Params` in `handlePublicKeyGet` before the `json.Unmarshal(*req.Params, r)` call, mirroring the guards in `processCreateSecretsRequest`/`processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`, e.g.:
```go
if req.Params == nil {
    return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, errors.New("request params must not be nil"))
}
```
More robustly, route `MethodPublicKeyGet` through a shared validated envelope step so all vault methods guarantee non-nil `Params` before any handler dereferences it.

## Proof of Concept
1. Send a JSON-RPC 2.0 request to the Gateway targeting a Vault-enabled DON:
```json
{"jsonrpc":"2.0","id":"1","method":"vault.publicKeyGet"}
```
with the `params` field entirely omitted (matching the value of `vaulttypes.MethodPublicKeyGet`).
2. The message is forwarded via the connector's read loop to `GatewayHandler.HandleGatewayMessage`, matching `case vaulttypes.MethodPublicKeyGet:` and invoking `handlePublicKeyGet` directly, without any params validation.
3. `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, causing a runtime panic in the node process.
4. A minimal Go unit test can call `GatewayHandler.HandleGatewayMessage` directly with a `*jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and assert it panics (recovering the panic in the test to confirm), providing a direct reproduction without needing the full gateway stack.
