### Title
Meta-transaction (`SignedDelegateAction`/`DelegateAction`) signatures lack a chain/network domain separator, enabling cross-network replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEP-366/NEP-611 meta-transactions are authorized by a `SignedDelegateAction`/`VersionedSignedDelegateAction`, whose signature only covers a NEP discriminant plus the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). Unlike ordinary `SignedTransaction`s, which embed a recent `block_hash` that is unique to the chain the tx was built against, the delegate-action signing scheme embeds no chain identifier (`chain_id`/genesis hash) at all, so the same signed bytes are valid on any nearcore-based network that shares the signer's account/key/nonce state.

### Finding Description
`SignedDelegateAction::verify` and `VersionedSignedDelegateAction::verify` compute a NEP-461 tagged hash purely from a `MessageDiscriminant` and the `DelegateAction`/`DelegateActionV2` payload: [1](#0-0) [2](#0-1) 

The signed payload contains no chain-specific binding such as `chain_id`, genesis hash, or the block hash used by ordinary transactions. Compare this to normal `SignedTransaction`s, which are bound to a specific chain via a recent `block_hash` and a `transaction_validity_period` window, giving them implicit domain separation between distinct NEAR networks: [3](#0-2) 

At runtime, `apply_delegate_action` only checks the signature, `max_block_height`, and that `sender_id` matches the tx receiver, then delegates access-key/nonce checks to `validate_delegate_action_key`: [4](#0-3) [5](#0-4) 

None of these checks reference a chain identifier. `validate_delegate_action_key` only requires `delegate_nonce > current_nonce` (the value stored under that account's access key) and `delegate_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. Because these values are derived purely from that particular chain's own state, an identical `SignedDelegateAction` byte blob is accepted by *any* nearcore deployment where the same `sender_id`/`public_key` access key exists with a nonce/block-height satisfying these two purely local conditions — exactly the "signature replayable across domains" bug class: the signature's "domain" (chain identity) is never asserted against the contract's (network's) actual deployment state.

This matches realistic nearcore scenarios where account/key/nonce state is duplicated across networks:
- Users/wallets that reuse the same seed phrase (hence the same `public_key`) to create identically-named accounts on testnet and mainnet, both starting at nonce 0.
- Networks bootstrapped from a state dump/snapshot of another network (a supported nearcore workflow for sandbox/testing), which inherit identical accounts, keys, and nonce state at the fork point.

In either case, a relayer (an unprivileged actor, since anyone can act as an NEP-366 relayer by including `Action::Delegate`/`Action::DelegateV2` in a transaction they sign and submit) that obtains a `SignedDelegateAction` meant for use on chain A can resubmit it verbatim as the delegate payload of a self-signed relayer transaction on chain B, and it will pass `apply_delegate_action`'s and `validate_delegate_action_key`'s checks if the nonce/height conditions happen to be satisfied on B.

### Impact Explanation
If a relayer replays a `SignedDelegateAction` intended for one network on another network where the sender account/key/nonce state coincides, the relayer can force execution of the delegated actions (e.g. `Transfer`, `FunctionCall`, `AddKey`) on behalf of the victim account on the un-intended chain, using the victim's real access key authorization without their consent. Depending on the delegated actions, this can move real funds, invoke contracts, or add/remove keys — an unauthorized state/balance change performed by an unprivileged actor.

### Likelihood Explanation
Exploitation is conditioned on the attacker (any relayer) already possessing a validly-signed `SignedDelegateAction` and on the coincidence that the same `sender_id` + `public_key` + satisfying nonce/height window exists on the target chain. This is a real, not purely theoretical, condition given common wallet behavior (same seed phrase reused across testnet/mainnet with fresh, low nonces) and nearcore's supported workflows for bootstrapping new networks/sandboxes from another network's account state. It is not reachable by validators or node operators only — it is exploitable by any party that can observe/collect a signed delegate action and relay transactions, which is standard, unprivileged NEP-366 usage.

### Recommendation
Bind the NEP-366/NEP-611 signing scheme to the chain's identity, mirroring how ordinary `SignedTransaction`s are anchored via `block_hash`. Concretely, include the network's `chain_id` (and/or genesis hash) as part of the `SignableMessage`/`DelegateAction` payload that gets hashed and signed (or as an additional field in `DelegateAction`/`DelegateActionV2` validated in `apply_delegate_action`), so a `SignedDelegateAction` produced for one nearcore deployment fails signature verification when replayed on a different one, even if account/key/nonce state coincides.

### Proof of Concept
1. Generate keypair `K` and create account `alice.testnet` on Network T (testnet-like) and `alice.mainnet`-equivalent account with the same public key `K` on Network M (mainnet-like, or any nearcore fork bootstrapped from a shared/duplicated state, e.g. a state-dump-based sandbox), each with a fresh access key at nonce 0.
2. On Network T, Alice signs a `SignedDelegateAction` (`DelegateAction{ sender_id: alice, receiver_id: bob, actions: [Transfer{..}], nonce: 1, max_block_height: T_h+100, public_key: K }`) via `SignedDelegateAction::sign`, per `core/primitives/src/action/delegate.rs` lines 83-95, intending it to be relayed only on Network T.
3. A relayer intercepts this `SignedDelegateAction` (e.g., it was sent to them for relaying on T, or leaked) and, without modification, wraps the identical bytes as `Action::Delegate` in a new relayer-signed `SignedTransaction` submitted to Network M, choosing a `max_block_height`-compatible block on M.
4. On Network M, `apply_delegate_action` (`runtime/runtime/src/actions.rs` lines 437-518) calls `signed_delegate_action.verify()`, which succeeds because the signed hash contains no chain identifier; `validate_delegate_action_key` succeeds because Alice's access key on M also has nonce 0 and `delegate_nonce=1` is within the valid range for M's current block height.
5. The `Transfer` action executes against Alice's account on Network M even though Alice never authorized any action on Network M — demonstrating cross-chain signature replay.

        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }

fn validate_delegate_action_key(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    delegate_action: VersionedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let sender_id = delegate_action.sender_id();
    let public_key = delegate_action.public_key();
    // 'sender_id' account existence must be checked by a caller
    let mut access_key = match get_access_key(state_update, sender_id, public_key)? {
        Some(access_key) => access_key,
        None => {
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::AccessKeyNotFound {
                    account_id: sender_id.clone(),
                    public_key: public_key.clone().into(),
                },
            )
            .into());
            return Ok(());
        }
    };

    // A plain nonce advances the single access_key.nonce and forbids gas keys;
    // a gas key nonce advances one of the gas key's nonces selected by
    // nonce_index.
    let delegate_nonce = delegate_action.nonce();
    let (current_nonce, nonce_update) = match delegate_nonce {
        TransactionNonce::Nonce { .. } => {
            if access_key.gas_key_info().is_some() {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresNonGasKey,
                )
                .into());
                return Ok(());
            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =
                get_gas_key_nonce(state_update, sender_id, public_key, nonce_index)?.ok_or_else(
                    || {
                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());
    }
