### Title

Unvalidated route callbacks can steal unrelated caller wallet tokens through the signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

Medium — an attacker-supplied strategy route can place attacker-controlled contract code inside a caller-authorized `multiply`, `swap_collateral`, `swap_debt`, or `repay_debt_with_collateral` transaction. That code can request an unrelated `token.transfer(caller, attacker, amount)`, which simulation records as a child of the caller’s authorization; if the wallet signs the simulated tree, the transfer executes while the lending operation still settles normally. [1](#0-0) [2](#0-1) 

### Finding Description

The controller accepts opaque `swap: Bytes` arguments in account-owner-authorized strategy entrypoints, including `swap_collateral(caller, account_id, current, amount, new, swap)`. [3](#0-2)  After authenticating the caller and account owner/delegate, `process_swap_collateral` forwards that route into `withdraw_and_swap_from_supply`. [4](#0-3) 

`swap_tokens` resolves the configured router, authorizes only the controller’s exact input-token transfer to the router, and calls `router.execute_strategy(controller, amount_in, swap)`. [5](#0-4)  The authorization helper creates a leaf transfer authorization for the controller’s funds and intentionally contains no sub-invocations. [6](#0-5) 

That bound protects only the controller’s input grant. The router route can still name a third-party pool/venue, placing arbitrary contract code below the caller’s root authorization. [7](#0-6)  The malicious venue can invoke `token.transfer(victim, attacker, amount)` for a token unrelated to the lending operation. [8](#0-7) 

Soroban simulation records that unauthorized-looking wallet transfer as a child invocation beneath the caller’s `swap_collateral` entry. [9](#0-8)  If the caller signs the poisoned tree, enforcing auth accepts the nested transfer and drains the wallet token while the requested collateral swap completes. [10](#0-9) 

The controller’s post-router checks measure only the controller’s input balance, output balance, positive output, and final account risk; they do not inspect the signed authorization tree or unrelated caller balances. [11](#0-10) 

### Impact Explanation

A victim can lose any token balance that a malicious route contract requests during the strategy call, including assets that are not listed by the lending protocol and are outside `amount_in`. [12](#0-11)  The harness demonstrates a complete loss of an unrelated wallet token while the attacker supplies fair swap output and the account remains valid. [13](#0-12) 

This is theft of user funds rather than only bad route execution: the stolen transfer is authorized by the victim’s signature but is not economically represented by the swap amount, minimum output, or account-health checks. [14](#0-13) 

### Likelihood Explanation

The attacker needs to persuade a position owner or active delegate to submit a malicious route and sign the resulting authorization tree. [15](#0-14)  Wallets or clients that mechanically sign the simulated tree will include the attacker’s token transfer because simulation records it as a required child invocation. [9](#0-8) 

The exploit does not depend on compromising governance, the controller, pool liquidity, or an oracle. The route only has to return enough output for the configured router and controller checks to pass. [11](#0-10) 

### Recommendation

- Enforce a strict authorization-tree policy in every client and wallet integration: for controller strategies, reject any caller authorization entry containing children other than the exact expected transfers.
- For direct router calls, permit only the single expected `token_in.transfer(sender, router, total_in)` child; reject routes producing any additional caller-authorized invocation. [16](#0-15) 
- Decode routes client-side before simulation and restrict venue, pool, token, and receiver addresses to a known-good registry.
- Prefer a router-level venue allowlist so opaque `swap_xdr` cannot select arbitrary contract addresses.
- Surface a high-risk warning whenever simulation adds a child transfer for an asset other than the declared route input.

### Proof of Concept

The harness contains a runnable model of the attack:

1. Deploy `UnlistedPoolRouter`, whose `execute_strategy` pulls the declared input, invokes the route-selected `hop_pool`, and returns fair output. [17](#0-16) 
2. Deploy `RogueHopPool` with `(victim, wallet_token, attacker, amount)`; its `swap` function calls `wallet_token.transfer(victim, attacker, amount)`. [8](#0-7) 
3. Build `swap` bytes naming that pool as the route hop. [18](#0-17) 
4. The victim calls `swap_collateral(alice, account_id, usdc, 5_000 USDC, eth, swap)`. [19](#0-18) 
5. Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` under the victim’s `swap_collateral` root. [20](#0-19) 
6. Signing that tree empties Alice’s unrelated wallet token balance while crediting the expected ETH collateral. [13](#0-12)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
