Webhook tenant identity (`shop-domain` header) is not covered by the HMAC signature, allowing a merchant to forge webhooks attributed to a victim shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers as the tenant identity handed to the app's handler. Because the HMAC only signs the body, any actor who can obtain one valid `(body, hmac)` pair for the app's shared `api_secret_key` (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The gem will report the request as HMAC-valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`; none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed material.

`hmac` and `shop` are both derived purely from headers: [2](#0-1) 

`Registry.process` validates only via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) and compares against the secret-keyed HMAC, then immediately trusts `request.shop` as the tenant for the handler: [3](#0-2) 

The identity binding this breaks is: **shop authenticated (via HMAC) ≠ shop delivered to the handler as the session/tenant key.** The HMAC proves "this body was produced by someone who knows `api_secret_key`" — which for a multi-tenant app is knowledge shared across *all* installed shops, not scoped to a single tenant. It does **not** prove "this body came from shop X." Since the header carrying the tenant identity (`shop-domain`) is excluded from the signed string, an attacker who is a legitimate (but malicious) merchant of the app can:
1. Trigger any webhook topic on their own store (e.g. `orders/create`) to receive a real `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint, but with `shopify-shop-domain` set to a victim shop's domain (and, if desired, a different `webhook-id`/`topic` mapped to a registered handler).
3. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, matches, and `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: <victim_domain>, body: ..., ...)`, handing the attacker-controlled body to the app's handler *as if it came from the victim's shop*.

Per the gem's own webhook docs, app handlers are expected to use `data.shop` to key data storage, look up per-shop sessions, and enqueue per-shop background work: [4](#0-3)  — this is exactly the trust surface being subverted. Depending on how the host application uses `data.shop` (e.g., to fetch and use the victim's stored offline access token to service the "webhook", or to write/mutate data keyed by shop), this becomes a cross-tenant data injection / cross-tenant action primitive, entirely inside this gem's trusted API surface (`Registry.process`, `Request`), not a misuse of an undocumented feature.

This mirrors the GarlicRust bug class: a downstream field (Garlic clove length / here, the `shop-domain` header) is consumed and forwarded without being covered by the same integrity check applied to the rest of the message, letting an attacker who can produce *one* valid signed message repurpose it to smuggle unauthenticated content past the boundary.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive reachable from any unprivileged actor who is a merchant of the app (a very low bar — no `api_secret_key`, access token, or privileged account required, only a normal app installation on any shop). The impact matches the "Critical - cross-tenant access" bucket: an attacker can cause a multi-tenant app to process and act on attacker-chosen webhook data while attributing it to a victim tenant's identity, which can lead to cross-tenant data corruption or triggering actions against the victim's stored session, depending on the host app's handler logic (which is exactly the trust model this gem's documentation directs developers to build on).

### Likelihood Explanation
Likelihood is high for any app that has itself installed by the attacker (trivial, self-service in Shopify) and registers at least one HTTP webhook topic. Obtaining a valid `(body, hmac)` pair requires no secret knowledge — it's delivered directly to the attacker's own endpoint by Shopify when they install the app and trigger the topic. Forging the `shopify-shop-domain` header on the replayed HTTP request requires no cryptographic material.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for HMAC verification, or independently cross-check `request.shop` against an app-known tenant record (e.g., confirm a session already exists for that shop and reject if the topic isn't the install/uninstall lifecycle) before trusting the header value passed to `WebhookMetadata`. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must not be trusted for authorization decisions on its own.

### Proof of Concept
```ruby
# Attacker installs TargetApp on their own shop "attacker.myshopify.com"
# and receives a legitimate webhook POST from Shopify for a registered topic, e.g. "orders/create":
#   headers:
#     shopify-topic: orders/create
#     shopify-hmac-sha256: <BASE64_HMAC_OF_BODY>
#     shopify-shop-domain: attacker.myshopify.com
#     shopify-webhook-id: ...
#     shopify-api-version: 2024-01
#   body: '{"id": 1, "note": "attacker-controlled content"}'

# The attacker now replays this exact body+hmac to the SAME app endpoint,
# but with the shop-domain header changed to a victim shop:
raw_body = '{"id": 1, "note": "attacker-controlled content"}'
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => "<BASE64_HMAC_OF_BODY>",   # unchanged, still valid because body unchanged
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, NOT covered by HMAC
  "shopify-webhook-id" => "any-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is signed)
# => handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The app's handler now processes attacker-controlled content attributed to "victim-shop.myshopify.com".
