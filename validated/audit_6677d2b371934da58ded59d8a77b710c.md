### Title
DirectBridge.describeWithdrawal reports 'completed' unconditionally, misreporting NEAR-side withdrawal status without verifying the underlying cross-contract transfer succeeded - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.describeWithdrawal` returns `{ status: "completed", txHash: args.tx.hash }` unconditionally, with no check of the actual outcome of the withdraw sub-action (`ft_transfer`/`native_withdraw`) that the `execute_intents` call schedules. Because NEAR cross-contract calls are asynchronous, the top-level transaction (`args.tx`) can execute successfully while the downstream transfer receipt for a specific withdrawal in the batch fails and is resolved/refunded internally, yet the SDK still reports that withdrawal as completed.

### Finding Description
The broken equality is: **top-level `args.tx.hash` execution success == this specific `WithdrawalIdentifier`'s withdraw sub-action success**. `DirectBridge.describeWithdrawal` [1](#0-0)  performs zero verification — it does not query the NEAR RPC's `receipts_outcome`, does not check for a resolve/refund callback, and does not inspect logs for the specific withdrawal index. It simply echoes back the parent tx hash it was given.

Trace: `createWithdrawalIdentifiers` assigns the same `intentTx` (the top-level, already-settled tx from `waitForIntentSettlement`) to every `WithdrawalIdentifier` in the batch [2](#0-1) . `watchWithdrawal` calls `bridge.describeWithdrawal` and, on `status === "completed"`, resolves the promise with `{ hash: status.txHash }` without any further check [3](#0-2) . `IntentsSDK.processWithdrawal` obtains `intentTx` from `waitForIntentSettlement` (which only confirms the top-level signed transaction/direct receipt settled) and feeds it straight into `waitForWithdrawalCompletion` → `createWithdrawalCompletionPromises` → `watchWithdrawal` for every withdrawal in the batch [4](#0-3) .

Root cause: NEAR's execution model is asynchronous — a function call (`execute_intents`) that schedules a promise (the token contract's `ft_transfer`, invoked as part of a `ft_withdraw`/`native_withdraw` intent) returns its own `SuccessValue` independent of whether the spawned promise's receipt eventually succeeds. If that nested transfer fails, standard NEP-141 patterns resolve/refund the internal balance in a later receipt within the same transaction's receipt tree, but the top-level transaction hash still shows overall success. `DirectBridge.describeWithdrawal` never distinguishes this case — it treats "the tx hash exists" as proof that *every* withdrawal routed through it in that batch succeeded.

Attacker input: an ordinary NEAR Intents user submits a multi-intent withdrawal batch where one `NearWithdrawal`-routed withdrawal's underlying transfer is engineered to fail internally (e.g., a `ft_transfer` to a receiver account under conditions that panic in the resolve/refund path) while an unrelated failing/succeeding action in the same batch or receipt tree does not abort the top-level receipt. `watchWithdrawal` for that specific `WithdrawalIdentifier` still returns `{ hash: args.tx.hash }` as `completed`.

Existing guards do not catch this: `validateWithdrawal`/`compareAddresses`/`supports()` all run pre-execution and cannot detect a runtime cross-contract failure; there is no `getUnderlyingFee`/`FeeExceedsAmountError` check involved; and `assert` sanity checks in `withdrawal-watcher.ts` only verify indexing consistency, not on-chain outcome.

### Impact Explanation
An integrator building on top of `waitForWithdrawalCompletion`/`processWithdrawal` treats a `completed` status with a `txHash` as proof of funds delivered and credits/marks-paid an off-chain ledger entry accordingly. If the specific withdrawal's transfer sub-receipt actually failed and was refunded internally to the user's intents balance, the user still holds the funds inside `intents.near` and can withdraw them again later — while the integrator has already recorded the withdrawal as delivered. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice," and is repeatable for any batch containing a `NearWithdrawal`-routed leg whose underlying transfer can be made to fail asynchronously.

### Likelihood Explanation
Requires a `NearWithdrawal`-routed withdrawal (an nep141 token withdrawn directly on NEAR) as part of the batch, and a condition that causes the nested `ft_transfer`/`native_withdraw` receipt to fail (e.g., insufficient storage on the receiving account, a receiver contract that rejects the transfer, or any panic in the resolve/refund path) without aborting the parent `execute_intents` receipt — this is achievable by an ordinary user controlling their own destination address/receiver contract, at the cost of one submitted intent batch. It is repeatable on demand for each batch submitted.

### Recommendation
Have `DirectBridge.describeWithdrawal` actually query NEAR RPC for the full execution outcome of `args.tx.hash` (`receipts_outcome`), locate the specific withdraw sub-receipt/log entry corresponding to this `WithdrawalIdentifier.index`, and only report `completed` if that specific receipt succeeded; otherwise report `failed` (or `pending`, if not yet finalized) with the actual failing receipt reason.

### Proof of Concept
Vitest plan (mock only the NEAR RPC provider used by `DirectBridge`):
1. Mock `nearProvider.txStatus`/`viewTransactionResult` (or equivalent used elsewhere in the bridges, e.g. `hot-bridge.ts`/`omni-bridge.ts` NEAR helpers) to return a `FinalExecutionOutcome` where the top-level `status.SuccessValue` is present, but `receipts_outcome` contains a receipt tied to the `ft_transfer` for this withdrawal with `status.Failure` (or a `ft_resolve_withdraw` callback indicating a refund).
2. Construct a `WithdrawalIdentifier` with `tx: { hash: "<mocked tx hash>" }` and call `directBridge.describeWithdrawal(wid)`.
3. Assert current (buggy) behavior: `result.status === "completed"` and `result.txHash === wid.tx.hash`, despite the nested receipt showing failure — i.e., assert **LHS** (`result.status`) `=== "completed"` while **RHS** (actual nested transfer outcome) `=== "failed"`, demonstrating the equality claimed by the code (`tx success ⇒ withdrawal success`) does not hold.
4. After the fix, assert `result.status === "failed"` when the nested receipt fails, restoring the equality.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
