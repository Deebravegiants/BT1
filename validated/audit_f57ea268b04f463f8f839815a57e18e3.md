### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value read from an unauthenticated HTTP header. Because the `shop-domain` header is never covered by the HMAC, an attacker who owns any Shopify store can capture one of their own genuinely-signed webhook deliveries and re-send it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still verifies (it only ever covered the body), so the app processes attacker-supplied data as though it belongs to the victim tenant — an identity-binding break exactly analogous to the reported bug class ("a field acted on but not covered by the HMAC").

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read straight from a request header with no cryptographic tie to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` uses this same HMAC check as its sole authenticity gate, then forwards `request.shop` (the unauthenticated header) directly to the handler as the tenant identity for the event: [4](#0-3) 

The broken equality is:
`HMAC-verified(body)` is treated as if it implies `shop-domain header == tenant that produced body`, but the gem only proves the former, never the latter.

Before the attacker's request: a legitimate webhook for shop A carries `(body_A, hmac(body_A))` and header `shop-domain = A`.
After the attacker's crafted request: the same `(body_A, hmac(body_A))` pair is replayed with header `shop-domain = B` (victim). `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` passes `shop: "B"` to the handler alongside body data that actually belongs to shop A.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who controls (or can trigger events in) any Shopify store can make a merchant's app process/attribute webhook data under a different shop's identity, without ever needing the app's `client_secret` or `api_secret_key`. Depending on how the host app's webhook handler uses `data.shop` (e.g., looking up/updating per-shop records, provisioning, billing, deduplication keys), this enables cross-tenant data corruption or disclosure — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any host app whose webhook handler trusts `WebhookMetadata#shop` without independently re-deriving or cross-checking it (e.g., against a shop stored on the session/subscription). The attacker only needs: (1) a Shopify store of their own (trivial, unprivileged), (2) the ability to trigger a webhook event in that store, and (3) knowledge of the target app's public webhook URL. No secret material is required, since the replayed HMAC was legitimately produced by Shopify for the attacker's own payload.

### Recommendation
Bind the tenant identity into the verified signature material, or independently authenticate the `shop-domain` header against the tenant the request claims to belong to before dispatching to handlers. Concretely:
- Have `Webhooks::Request#to_signable_string` (or the `HmacValidator`) incorporate the `shop-domain` (and other identity-relevant headers) into what is verified, not just the raw body, or
- After HMAC validation, cross-check `request.shop` against an app-side registry of shop→subscription mapping (e.g. via the webhook id or a known list of installed shops) before invoking the handler, so a header alone cannot redirect the reported tenant.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g., updates a product), receiving a legitimate delivery: body `B`, headers including `X-Shopify-Hmac-Sha256: H(B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays this exact request to the app's public webhook endpoint, only changing the header `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to the unchanged `H(B)` — it matches (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing attacker-originated data to be processed under the victim shop's identity.
