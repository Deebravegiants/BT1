### Title
Accrued market-value overflow permanently freezes all market operations - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

The accrual path converts aggregate scaled supply and debt back to RAY-denominated value with `scaled_to_original` before calculating utilization and interest. That conversion panics when `scaled * index / RAY` exceeds `i128::MAX`, even though the indexes themselves remain below their configured caps. Once a market reaches this state, `last_timestamp` remains stale and every subsequent accrual attempts the same overflowing conversion. Because withdrawals, repayments, liquidations, revenue claims, and keeper index updates all synchronize the market before mutating it, the market becomes permanently unusable.

### Finding Description

`accrue_step` unconditionally calls `scaled_to_original` on both `borrowed` and `supplied` before updating the indexes. [1](#0-0)  `scaled_to_original` is a `Ray::mul` of the scaled balance and index. [2](#0-1)  That maps to `mul_div_half_up`, which widens the intermediate product to `I256` but still panics with `MathOverflow` when the final quotient does not fit in `i128`. [3](#0-2) 

The permissionless controller entrypoint `update_indexes(caller, assets)` forwards the requested `(hub_id, asset)` keys to the pool. [4](#0-3)  The controller only requires caller authorization, then calls `pool_update_indexes_call`. [5](#0-4)  The pool implementation loads each market and runs `interest::global_sync`. [6](#0-5) 

The same accrual is embedded in ordinary mutations: `ops::synced_market` loads the cache and calls `global_sync`. [7](#0-6)  Both repay and withdraw reach this helper before resolving positions. [8](#0-7) [9](#0-8) 

The index bounds do not prevent this state. `update_borrow_index` caps only the index at `MAX_BORROW_INDEX_RAY`, after multiplying the old index by the interest factor. [10](#0-9)  The earlier `scaled_to_original` calculation can overflow while the index is still below that cap.

### Impact Explanation

This is a permanent freezing of user funds and protocol revenue for the affected market.

After the overflow boundary is crossed:

- `withdraw` cannot pay suppliers.
- `repay` cannot reduce borrower debt or release collateral.
- Liquidation withdrawal paths cannot settle the market.
- `claim_revenue`, `flash_loan`, and other pool mutations that synchronize first cannot proceed.
- `update_indexes` itself cannot advance `last_timestamp`, so the panic repeats permanently.
- `update_params` also accrues before replacing the rate model, so ordinary parameter governance cannot recover the market. [11](#0-10) 

The repository already contains a reproduction demonstrating that a large 18-decimal market at sustained 98% utilization reaches `MathOverflow` before `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail. [12](#0-11) 

### Likelihood Explanation

Likelihood is market-configuration dependent. An unprivileged caller cannot directly set an arbitrary index, but can call `update_indexes` once an existing market's aggregate scaled value approaches the representable ceiling. For a market with unconstrained or very large caps, a whale can also create the precondition by supplying a very large principal and borrowing most of it, then waiting for index growth.

For an 18-decimal asset, roughly `10^9` whole tokens normalize to approximately `10^36` RAY-scaled shares; an index near `170 × RAY` makes the aggregate value approach `i128::MAX`. The bundled reproduction uses `1_000_000_000` 18-decimal units supplied and 98% borrowed, then advances time until accrual fails. [13](#0-12) 

This requires extreme market size and sustained debt, so it is less likely than an ordinary rounding bug, but no privileged action is required at trigger time once a valid market reaches the condition.

### Recommendation

Do not compute aggregate values in a way whose representability is narrower than the stored share/index domain.

At minimum, make the accrual path handle an unrepresentable aggregate value explicitly before calling `scaled_to_original`, and cap or partition accrual so the market can continue to settle. A practical mitigation is to detect `scaled > i128::MAX * RAY / index` using the existing checked/`I256` helpers and fail forward into a bounded-index or reduced-accrual state rather than leaving `last_timestamp` permanently stale.

A safer accounting redesign would store or update utilization inputs using saturating wide arithmetic and independently bound `supplied` and `borrowed` scaled totals so every admissible pair remains representable after multiplication by `MAX_SUPPLY_INDEX_RAY` or `MAX_BORROW_INDEX_RAY`. Add a regression test asserting that withdrawal, repayment, liquidation, and `update_indexes` remain callable after crossing the current overflow boundary.

### Proof of Concept

The existing harness test is a direct end-to-end reproduction:

1. Create an 18-decimal market and collateral market.
2. Supply `1_000_000_000 * 10^18` base units of the borrowable asset.
3. Supply sufficient collateral and borrow 98% of that principal.
4. Advance ledger time and repeatedly call the permissionless `update_indexes`.
5. The next accrual panics with `MathOverflow` before `MAX_BORROW_INDEX_RAY`.
6. Subsequent `withdraw` and `repay` attempts fail with the same error because they synchronize first. [12](#0-11)

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {

    );

}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
