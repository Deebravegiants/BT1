### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, which computes the HMAC only over the raw request body (`to_signable_string` returns `@raw_body`). However, the `shop`, `topic`, `api_version`, and `webhook_id` values that the rest of the library (and any host application built on it) uses to identify *which tenant* the webhook belongs to are pulled straight from HTTP headers that are never included in the signed payload.

### Finding Description
`Request#to_signable_string` binds the HMAC exclusively to the raw body: [1](#0-0) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read from unauthenticated headers: [2](#0-1) 

`Registry.process` only checks `HmacValidator.validate(request)` (i.e., body integrity) before dispatching to the handler with the header-derived `shop` and `topic`: [3](#0-2) 

The broken identity binding is:
`hmac_verified_bytes (raw body)` == `tenant_identity_used_by_handler (shop header)` — this equality does **not** hold, since the header is parsed but never verified.

Because the app's `api_secret_key` is shared across every shop that has the app installed, any merchant who installs the app on their own store receives real webhooks from Shopify with a valid HMAC computed over a body they fully control/observe. That merchant (an unprivileged actor with respect to any other tenant) can then replay the exact same `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee: a host application trusts `WebhookMetadata#shop` to route data/side effects to the correct merchant's records. An attacker who only controls their own shop's installation can forge webhooks appearing to originate from any other shop, causing cross-tenant data confusion/injection in the host application (e.g., writing attacker-supplied data under a victim shop's records, or triggering mandatory GDPR webhooks like `customers/redact` for a shop they don't own). This meets the Critical - cross-tenant access bar since no victim credentials or admin access are required, only an app installation on an attacker-controlled shop.

### Likelihood Explanation
Likelihood is high: any developer/merchant able to install the app (a normal, unprivileged flow) automatically receives legitimately HMAC-signed webhooks for their own shop and can immediately replay them with a modified `shop-domain`/`topic` header, since header parsing in `Request#initialize` performs no cross-check against the signed body.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that spoofing any of these header values invalidates the signature. At minimum, `to_signable_string` should incorporate the shop domain, matching the pattern already used for `AuthQuery#to_signable_string`, which includes `shop` in the signed payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, receiving genuine webhook deliveries with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures one such delivery: `raw_body` = `{"id":1,...}`, `hmac` = valid signature for that body.
3. Attacker sends this same `raw_body` and `hmac` header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`. [4](#0-3)
