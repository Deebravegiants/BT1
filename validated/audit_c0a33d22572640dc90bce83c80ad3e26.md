### Title
Webhook shop identity is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but it then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the signed payload — to identify which tenant the webhook belongs to. An attacker who can obtain any one validly-signed webhook body from Shopify (e.g. by installing the app on their own store) can replay that body with a forged `shop-domain` header to make the host application process the event as if it belonged to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived independently from an HTTP header that is not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` (which only checks `to_signable_string`, i.e. the raw body) and then immediately uses `request.shop` — the unauthenticated header — to build the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature strictly over `verifiable_query.to_signable_string`: [4](#0-3) 

This is exactly the identity-binding gap called out in the bug class: a field (`shop`) that is acted upon (used as the tenant identifier passed to the app's webhook handler) is not covered by the HMAC that is supposed to authenticate the whole message. The equality that should hold — `shop_bound_by_signature == shop_used_for_tenant_routing` — is broken; the gem lets `shop_used_for_tenant_routing` come from an arbitrary, attacker-controllable header while only `raw_body` is authenticated.

### Impact Explanation
Because the app's own Shopify secret (`client_secret`) is shared across every shop that installs the app, any merchant/attacker who installs the app on their own store legitimately receives HMAC-valid webhook deliveries. By capturing one such raw body + `X-Shopify-Hmac-Sha256` pair and re-sending it to the app's webhook endpoint with a different `X-Shopify-Shop-Domain` header, the attacker forces `Registry.process` to accept the HMAC as valid (since only the body is checked) and to hand `WebhookMetadata` bearing an arbitrary, attacker-chosen `shop` value to the host app's handler. Any handler that uses `data.shop` to select which tenant's records to update (a standard, documented pattern) will attribute attacker-controlled webhook data to a victim tenant, resulting in cross-tenant data injection/corruption — this matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only the ability to install the app on an attacker-controlled shop (a normal, unprivileged capability for any Shopify merchant/developer using a public app) and the ability to send an HTTP request to the app's public webhook endpoint with a custom header — no access token, `api_secret_key`, or privileged account is needed. This is straightforward and repeatable for any topic the app subscribes to.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-covered material, or otherwise cryptographically bind the header-derived shop to the verified request instead of trusting it independently. At minimum, `Request#to_signable_string` should not be the only channel of trust for tenant identity — the gem should document/enforce that consumers cannot rely on `WebhookMetadata#shop` as authenticated unless it's derived from data covered by the signature, or the gem should reject requests where the signed body's own shop-identifying content (if present) disagrees with the header.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request to the app's webhook endpoint.
2. Capture the raw request body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Replay the identical raw body and HMAC header to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the raw body against the HMAC.
5. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` == `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which processes attacker-supplied data under the victim shop's tenant context.
