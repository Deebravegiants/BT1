## Analysis Result

I found a valid analog of the reported vulnerability class ("last-update timestamp not capped at period end, breaking subsequent reward accounting") in the `pallet-asset-rewards` FRAME pallet.

### Title
Uncapped `last_update_block` after pool expiry causes permanent arithmetic-underflow DoS and frozen staker funds - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements the same "reward-per-token accumulator" pattern as THENA's `GaugeExtraRewarder`. Just like the original bug (`lastRewardTime` not clamped to the end of the distribution period), this pallet's `update_pool_rewards` sets `last_update_block` to the real current block instead of clamping it to `pool_info.expiry_block`, while the reward computation in `reward_per_token` correctly clamps using `last_block_reward_applicable`. The mismatch between the two causes a guaranteed arithmetic underflow on the next pool interaction, reverting `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and even `set_pool_expiry_block` — permanently bricking the pool and freezing staked funds.

### Finding Description
`reward_per_token` computes the elapsed "rewardable" blocks by capping the current block at `expiry_block`: [1](#0-0) [2](#0-1) 

However, `update_pool_rewards`, which is called immediately after on every stake/unstake/harvest/admin update, writes the **unclamped, real** current block number into `last_update_block`: [3](#0-2) 

This is exactly the same class of bug described in the THENA report: the "last update" marker should be pinned to the end of the distribution period once the period has passed, but instead advances with real time.

Once `last_update_block` exceeds `expiry_block`, the next call to `reward_per_token` (with nonzero `total_tokens_staked`) computes:
```
last_block_reward_applicable(expiry_block) = min(now, expiry_block) = expiry_block   // since now > expiry_block
rewardable_blocks_elapsed = expiry_block.ensure_sub(last_update_block)               // last_update_block > expiry_block
```
`ensure_sub` (from `EnsureSub`) underflows and returns `Err(ArithmeticError::Underflow)`, which propagates via `?` in `update_pool_and_staker_rewards`/`update_pool_rewards`, aborting the whole extrinsic: [4](#0-3) 

Both `stake` and `unstake`/`harvest_rewards` call this helper before doing anything else, and `unstake`/`harvest_rewards` explicitly allow **any account** to call them once the pool has expired (`now > pool_info.expiry_block || caller == staker`): [5](#0-4) [6](#0-5) 

Critically, the admin's only tool to fix an expired pool, `set_pool_expiry_block`, *also* calls `reward_per_token` first, so it fails for the exact same reason and cannot be used to recover the pool: [7](#0-6) 

### Impact Explanation
Once triggered, every subsequent `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and `set_pool_expiry_block` call on that pool reverts with an arithmetic underflow error. Since `unstake` is the only path to release the `FreezeReason::Staked` freeze placed on staker funds during `stake`, all staked assets in the pool become permanently frozen/unusable, and no admin action can revert the state (extend of expiry itself fails). This is a permanent denial-of-service plus fund-lockup — directly analogous to, and arguably worse than, the original report's "underlying gauge revert during deposit and withdrawal operations."

### Likelihood Explanation
This is trivially reachable by any unprivileged user and requires no special setup beyond waiting for the pool's `expiry_block` to pass:
1. Any interaction with the pool at a block `T2 > expiry_block` (with nonzero `total_tokens_staked`) pushes `last_update_block` past `expiry_block`.
2. The very next interaction with nonzero stake at `T3 > T2` triggers the underflow and permanently bricks the pool.

Because harvesting/unstaking after expiry is explicitly permitted for arbitrary callers, this can even be triggered unintentionally by a routine post-expiry withdrawal, making it near-certain to occur on any pool that reaches its expiry with active stakers.

### Recommendation
In `update_pool_rewards`, clamp the stored `last_update_block` the same way `reward_per_token` clamps its computation, e.g.:
```rust
new_pool_info.last_update_block =
    Self::last_block_reward_applicable(pool_info.expiry_block);
```
instead of unconditionally using `T::BlockNumberProvider::current_block_number()`.

### Proof of Concept
1. `create_pool` with `expiry_block = E` (e.g. `DispatchTime::After(10)`).
2. Staker `A` calls `stake` at block `T1 <= E`. `last_update_block = T1`.
3. Advance to block `T2 > E`. Any account calls `unstake`/`harvest_rewards` (or `A` calls `stake` again) — succeeds, but `update_pool_rewards` sets `last_update_block = T2` (unclamped, `T2 > E`).
4. Advance to block `T3 > T2`. Any subsequent `stake`/`unstake`/`harvest_rewards`/`set_pool_expiry_block` call on the pool computes `expiry_block.ensure_sub(last_update_block)` with `last_update_block(T2) > expiry_block(E)`, underflows, and the extrinsic fails with `ArithmeticError::Underflow`, permanently locking `A`'s frozen stake. 		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		/// Derives the amount of rewards earned by a staker.
		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.
		fn derive_rewards(
			staker_info: &PoolStakerInfo<T::Balance>,
			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}

		fn last_block_reward_applicable(pool_expiry_block: BlockNumberFor<T>) -> BlockNumberFor<T> {
			let now = T::BlockNumberProvider::current_block_number();
			if now < pool_expiry_block {
				now
			} else {
				pool_expiry_block
			}
		}

	fn set_pool_expiry_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_expiry: DispatchTime<BlockNumberFor<T>>,
	) -> DispatchResult {
		let now = T::BlockNumberProvider::current_block_number();
		let new_expiry_block = new_expiry.evaluate(now);
		ensure!(new_expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(new_expiry_block > pool_info.expiry_block, Error::<T>::ExpiryCut);

		// Always start by updating the pool rewards.
		let reward_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, reward_per_token)?;

		pool_info.expiry_block = new_expiry_block;
		Pools::<T>::insert(pool_id, pool_info);
