Based on my investigation, I found a valid analog: the Emporium signature scheme covers `feeStructure` (via `calldataHash`/`getHashedCalldata2`) and `ops`/`maxFee`/`deadline` (via the EIP-712 `EMPORIUM_SIGNATURE_TYPEHASH`), but it does **not** bind `circomData.erc20TokenAddresses` or `deltaAmountChanges` to the signature at all, while `payRelayFees` iterates per-token and can invoke `payRelay` → `sendToRelayFromWallet` multiple times for the same signed operation.

### Title
Emporium wallet-signed transaction allows relay fee to be charged multiple times per token, unauthorized by the signer - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet` validates a signer's EIP-712 signature over `emporiumMessage`, `ops`, `maxFee`, and `deadline`, and separately checks `feeStructure.flatFee <= maxFee` [1](#0-0) . However, `circomData.erc20TokenAddresses` and `deltaAmountChanges` — the arrays that drive how many times and for which tokens the relay is paid from the signer's `HinkalWallet` — are not part of the signed message at all.

### Finding Description
`payRelayFees` loops over `circomData.erc20TokenAddresses`, and for every token with a negative `deltaAmountChanges[i]` (i.e., a wallet outflow), it calls `payRelay(...)` with `relayFee = feeStructure.flatFee` when `signerAddress != address(0)` [2](#0-1) . Because `flatFee` is a single scalar (not divided by token count), each additional token with a negative delta re-triggers a full `sendToRelayFromWallet(relay, signerAddress, flatFee, erc20TokenAddress)` charge against the signer's `HinkalWallet` via `IHinkalWallet(signerAddress).doSendToRelay(...)` [3](#0-2) . The only cap enforced by the signature is `flatFee <= maxFee` — a single per-call bound — not a bound on `flatFee × numberOfNegativeDeltaTokens`. Since `erc20TokenAddresses` and `deltaAmountChanges` are not part of `EMPORIUM_SIGNATURE_TYPEHASH`'s hashed payload (only `emporiumMessage`, `_hashEmporiumOps(ops)`, `maxFee`, `deadline` are signed) [4](#0-3) , a relay/prover constructing the transaction can add extra tokens with negative deltas beyond what the signer's `ops` implied moving, causing the relay to be paid `flatFee` once per qualifying token, all still validated by the one signature the user actually signed. This mirrors the report's root cause: a party (here, the relay/prover assembling `circomData`) can act on fields (`erc20TokenAddresses`, `deltaAmountChanges`) that are outside the authenticated scope (the EIP-712 signature) that the signer actually approved, extracting value that was never authorized.

### Impact Explanation
This allows a relay to move more of the signer's wallet funds as "fees" than the signer authorized in their signature — a theft of protocol/relay fees from the user's `HinkalWallet` beyond the signed `maxFee` bound, executed via a wallet operation (`doSendToRelay`) not authorized by the signer for that magnitude. This fits the High-impact category: "theft or permanent freezing of protocol/relay fees... moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Requires a malicious or compromised relay to construct `circomData` with additional token entries carrying negative `deltaAmountChanges` alongside a validly signed Emporium message; the relay already controls transaction assembly and submission, making this reachable without needing owner/admin/relay-manager keys — an ordinary relay operator suffices.

### Recommendation
Include `circomData.erc20TokenAddresses` and `deltaAmountChanges` (or at minimum the count of chargeable tokens and total aggregate fee) inside the EIP-712 `EMPORIUM_SIGNATURE_TYPEHASH` payload, and/or enforce a single aggregate fee cap across the whole `payRelayFees` execution rather than a per-iteration `flatFee <= maxFee` check.

### Proof of Concept
1. Signer signs an Emporium message authorizing `ops` that only touch token A, with `maxFee = X`.
2. Relay submits `circomData.erc20TokenAddresses = [A, B, C]` with `deltaAmountChanges = [-a, -b, -c]` (negative for all three), where only A's movement corresponds to the signed `ops`.
3. `verifyWallet` succeeds (signature only covers `ops`/`maxFee`/`deadline`, not the token/delta arrays) [5](#0-4) .
4. `payRelayFees` iterates 3 tokens, and for each where `erc20TokenAddress == feeStructure.feeToken` is matched or `foundToken` fallback triggers, `flatFee` is charged from the wallet up to 3 times instead of once [6](#0-5) .

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
