### Title
Unconstrained `op.endpoint.call{value: op.value}` in `EmporiumUpgradeable.runAction` lets an attacker sweep stranded/residual ETH out of the Emporium contract, laundering it as their own withdrawal — (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes fully attacker-controlled `EmporiumOperation`s (decoded from `externalActionData.externalActionMetadata`) with arbitrary `endpoint`/`value`/`callData` when `stack.signerAddress == address(0)` [1](#0-0) . Because `balancesBefore`/`balancesAfter` are only diffed per token (not validated against what the ops were supposed to do), an attacker can add a benign-looking op that transfers ETH sitting in the Emporium contract (residual left over from a previous, unrelated user's action) straight to their own address, as long as they front an equal amount of their own genuine deposit to keep the local `balanceChange >= 0` check satisfied.

### Finding Description
The claimed invariant is: *tokens leaving the Emporium action in a transaction == `-deltaAmountChanges` that Hinkal sent it that same transaction*. This invariant is broken for the ETH leg because `runAction`'s per-token bookkeeping only checks a net, non-negative delta — it never verifies that the balance change is solely attributable to the caller's own `deltaAmountChanges[i]` and the declared ops.

Flow:
1. `Hinkal._externalTransact` sends `-deltaAmountChanges[i]` (the caller's own deposit, `D`) to the Emporium contract for negative deltas, then calls `runAction` [2](#0-1) .
2. `EmporiumUpgradeable.runAction` snapshots `balancesBefore` *after* this deposit has already landed, so it also includes any pre-existing/stranded ETH balance `R` left in the contract from a prior transaction (e.g. a router refund for a token not included in that earlier caller's `erc20TokenAddresses`, or dust) [3](#0-2) .
3. The attacker's `EmporiumStack` (fully attacker-crafted, since `externalActionMetadata` is not circuit-constrained) contains a stateless op with `endpoint = attacker's own address`, `value = R`, `callData = ""`. This is executed with no validation of `endpoint`/`value` beyond the wallet-call selector check [4](#0-3) , sending `R` wei of ETH directly out of the Emporium contract to the attacker.
4. `balancesAfter[i]` is now `D` (i.e. `balancesBefore - R = (R+D) - R`). The reconciliation computes `balanceChange = balancesAfter - balancesBefore`, then, because `deltaAmountChanges[i] < 0`, adds back `-deltaAmountChanges[i] = D`: `balanceChange = (D-(R+D)) + D = D - R` [5](#0-4) . As long as the attacker's own deposit `D >= R`, `balanceChange >= 0`, so the `BalanceChangeShouldBePositive` guard never fires [6](#0-5) .
5. `handleOut` mints a UTXO of `D - R` back to the attacker's own stealth address (returned to Hinkal, which will commit it to the tree) [7](#0-6) .
6. At the outer `Hinkal.sol` level the `balanceDif == amountChanges[i] + utxoAmount` check still holds, because it only verifies *Hinkal's own* balance movement, which is self-consistently `-D + (D-R) = -R` and matches `amountChanges[i] (-D) + utxoAmount (D-R) = -R` [8](#0-7) . The check is blind to the fact that `R` was diverted straight to the attacker's EOA outside of the UTXO/shielded accounting entirely.

Net result: the attacker ends up with raw ETH `R` (stolen residual) plus a legitimate shielded UTXO of `D - R`, i.e. they recover their own `D` in total but have additionally exfiltrated `R`, which belonged to a stranded/refunded amount from an unrelated prior action. None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the circuit's `inTotal + amountChanges === outTotal` constrain `externalActionMetadata`/`op.endpoint`/`op.value`, so nothing prevents this diversion.

### Impact Explanation
This is direct theft of in-flight/stranded protocol funds by an unprivileged attacker: any ETH balance stranded in the Emporium contract (e.g. unclaimed router refunds, dust from prior legitimate actions) can be swept to an attacker's own address by simply fronting an equal amount of the attacker's own genuine deposit for that transaction, which they recover in full as a new shielded UTXO. The attacker's net cost is zero beyond gas; the loss falls on whichever user's transaction left the ETH stranded (or the protocol, if the residual was meant to be recovered later). This is repeatable every time residual ETH accumulates in the Emporium contract. This matches the Critical category: "direct theft of shielded or in-flight user funds."

### Likelihood Explanation
Requires (a) some stranded/residual ETH balance sitting in the Emporium contract (plausible from router refunds on tokens/legs not included by an earlier caller's `erc20TokenAddresses`, or rounding dust from swaps executed through arbitrary ops), and (b) the attacker fronting a deposit `D >= R` of their own funds for one transaction, which they immediately recover as a shielded UTXO. Both preconditions are cheap and fully within an unprivileged attacker's control — they can generate the stranding themselves in a first transaction and harvest it in a second, requiring no special role, no relay, no owner privilege, and no proof-system bypass.

### Recommendation
`EmporiumUpgradeable.runAction`'s stateless-call branch must not allow arbitrary `op.endpoint`/`op.value` to move value that isn't accounted for by the transaction's own `deltaAmountChanges`. Concretely: (1) restrict `op.endpoint` from being an attacker-controlled address/EOA outside of an allow-listed set of routers/protocols; (2) track and require that the *sum* of `op.value` sent out across all ops for token `i` cannot exceed the token's `deltaAmountChanges[i]`-derived deposit for that same transaction, so pre-existing/stranded balances can never be pulled out through an op; and (3) add a mechanism (e.g. a dedicated sweep function gated to the owner/admin, or forcing any leftover balance to always be flushed back via `handleOut` to whoever originally caused the residual) so that stranded balances cannot silently persist as spendable value for unrelated future callers.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock router that intentionally refunds excess ETH beyond what a first caller's `erc20TokenAddresses` includes, stranding `R` wei of ETH in the Emporium contract.
2. As the attacker (a different, unprivileged EOA with their own funded shielded UTXO), call `Hinkal.transact` with `circomData.erc20TokenAddresses` including `address(0)`, `amountChanges[i] = -D` (with `D >= R`), and `externalActionMetadata` encoding an `EmporiumStack` with a single stateless `EmporiumOperation{endpoint: attacker, value: R, callData: ""}`.
3. Assert before/after: attacker's raw ETH balance increases by `R`; assert the new shielded UTXO minted to the attacker has amount `D - R` (not `D`); assert `Emporium` contract's ETH balance decreases by exactly `R` net of the deposit-recovery cycle.
4. Assert the broken equality: tokens leaving the Emporium action in this tx (`R` raw + `D-R` UTXO = `D`) does not equal `-deltaAmountChanges` Hinkal actually sent for accounting purposes of the *residual* `R`, i.e. `R` left the action without any corresponding negative `deltaAmountChanges` entry for it — it was never Hinkal's money to send in this transaction.
