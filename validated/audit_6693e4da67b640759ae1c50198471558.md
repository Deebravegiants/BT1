## Title
Duplicate authority votes let a BEEFY commitment satisfy the 2/3+1 supermajority threshold without a genuine supermajority of distinct signers - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` gates state-commitment acceptance on `checkParticipationThreshold(sigLen, authoritySet.len)`, which only checks the raw *count* of submitted votes (`relayProof.signedCommitment.votes.length`) against `((2 * total) / 3) + 1`. Nothing in the function requires the `authorityIndex` values referenced by those votes to be distinct.

### Finding Description
`checkParticipationThreshold` is defined as:
```solidity
function checkParticipationThreshold(uint256 len, uint256 total) internal pure returns (bool) {
    return len >= ((2 * total) / 3) + 1;
}
``` [1](#0-0) 

It is called with `sigLen = relayProof.signedCommitment.votes.length` — the number of `Vote` structs supplied by the caller — and compares it to `authoritySet.len`, the total number of validators in the trusted authority set:
```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
``` [2](#0-1) 

The threshold check happens *before* any signature-recovery or membership verification, and nothing afterward rejects duplicate `authorityIndex` entries. The loop that builds the merkle leaves for the membership proof simply re-derives `authority` per vote and pushes a leaf keyed on `vote.authorityIndex`:
```solidity
MerkleMultiProof.Leaf[] memory authorities = new MerkleMultiProof.Leaf[](sigLen);
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    authorities[i] =
        MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});
}
bool valid = MerkleMultiProof.VerifyProof(authoritySet.root, relayProof.proof, authorities, authoritySet.len);
``` [3](#0-2) 

Since a validator's own signature over the same `commitmentHash` is deterministic and reusable by anyone (it is broadcast in relay-chain justifications, i.e., public data any relayer can observe), a single real validator's signature can be repeated multiple times in `votes[]`, each copy carrying the *same* `authorityIndex` and recovering to the *same* `authority` address. This inflates `sigLen` — and therefore the leaf array size passed into `MerkleMultiProof.VerifyProof` — without requiring any additional distinct validators to have actually signed. If `MerkleMultiProof.VerifyProof` (an external library from `@polytope-labs/solidity-merkle-trees`) does not itself reject repeated/duplicate leaf indices within the same multiproof call, a proof composed of only a small number of genuinely signing validators, replayed enough times to satisfy `sigLen >= (2/3)*total + 1`, would pass both the participation-count check and the membership-proof check while representing far less than 2/3 of real stake/validators.

This is structurally the same bug class as the reference finding: a numeric threshold (`unitPrice >= config.thresholdPrice` / here, `sigLen >= 2/3+1`) is used as a *proxy* for a real precondition (enough ETH raised / a real supermajority of distinct validators), but the proxy can be satisfied by an attacker without the real precondition holding, because the code never validates that the underlying quantity contributing to the count is unique/non-duplicated. The Rust verifier (`modules/consensus/beefy/verifier/src/lib.rs`) has the identical pattern: `signatures_length` is a raw vote-array length, checked with the same `check_participation_threshold`, and duplicate `authority_indices` are likewise not filtered before being passed into `merkle_proof.verify`.

Compare this to the sibling consensus clients in the same codebase (BSC's `verify_bsc_header`, the sync-committee verifier, and Pharos's `verify_stake_threshold`/`verify_validator_membership`), all of which were explicitly hardened for exactly this class of padding attack — sync-committee and BSC verifiers reject bits set beyond the real committee/validator range, and Pharos's `verify_validator_membership` explicitly deduplicates participant keys with a `BTreeSet` and returns `Error::DuplicateParticipant` on a collision:
```rust
let deduped: alloc::collections::BTreeSet<&[u8]> =
    participants.iter().map(|k| k.as_ref()).collect();
if deduped.len() != participants.len() {
    return Err(Error::DuplicateParticipant);
}
``` [4](#0-3) 

BEEFY's `EcdsaBeefy.sol` and its Rust counterpart have no analogous duplicate-index check, meaning BEEFY is the one consensus client in this family still vulnerable to the padding pattern the others were fixed against.

### Impact Explanation
BEEFY consensus updates gate the acceptance of new relay-chain/parachain state commitments feeding every downstream Hyperbridge application (token bridges, intents settlement, ISMP message delivery) on this same client. If the supermajority check can be satisfied by replaying one or a few validators' signatures, an attacker controlling even a small minority of the real validator set (or simply capturing already-published signatures for an old commitment and combining with a handful of colluding/compromised keys) could push forged state commitments through `EcdsaBeefy.verify`, and subsequently forge state/storage proofs against them. This is unbacked-mint/forged-message-delivery territory — the most severe class in the ruleset — because it undermines the state-commitment root that all downstream state and non-membership proofs rely on.

### Likelihood Explanation
Exploitability is contingent on whether the external `MerkleMultiProof.VerifyProof` implementation (from `@polytope-labs/solidity-merkle-trees`) tolerates or rejects duplicate leaf indices within one multiproof — that library's source was not indexed by the available tools, so I could not confirm from this codebase alone whether the duplicate-index padding actually bypasses `VerifyProof`. If the library does reject duplicate indices (e.g., by requiring `authorities` sorted/unique against `proof`), this specific vector is not exploitable and the finding reduces to a defense-in-depth gap versus the pattern applied elsewhere (Pharos). Given this uncertainty, I flag this with moderate confidence rather than full certainty.

### Recommendation
Deduplicate `vote.authorityIndex` values in `relayProof.signedCommitment.votes` before computing `sigLen` and before running the membership proof, mirroring `verify_validator_membership`'s dedup in `modules/consensus/pharos/verifier/src/lib.rs`. Compute the participation threshold from the count of *distinct* authority indices, not the raw array length, in both `EcdsaBeefy.sol::verifyMmrUpdateProof` and `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`. Additionally, confirm (or add an explicit on-chain check) that `MerkleMultiProof.VerifyProof` rejects duplicate leaf indices within a single call, since the security of the current design implicitly depends on that library-level guarantee holding.

### Proof of Concept
Not verifiable within this codebase alone: exploitation depends on the external `MerkleMultiProof.VerifyProof` behavior for duplicate leaf indices, which is outside the indexed repository content available to me. A concrete PoC would need to: (1) construct a `RelayChainProof` where `votes[]` contains `N` copies of the same `(authorityIndex, signature)` pair such that `N >= (2*total)/3 + 1`, (2) build the corresponding `MerkleMultiProof.Leaf[]` with the duplicated index, and (3) show `MerkleMultiProof.VerifyProof` returns `true` against the real authority-set root despite only one genuine authority having signed. I recommend a Devin session with local build/test access to `evm/src/consensus/EcdsaBeefy.sol` and the `@polytope-labs/solidity-merkle-trees` dependency to write and run this Foundry test and confirm/refute exploitability before treating this as confirmed.
