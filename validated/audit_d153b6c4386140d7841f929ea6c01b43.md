### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant) value that host applications use to route/attribute the webhook comes from an unauthenticated HTTP header. `Registry.process` validates the HMAC and then unconditionally trusts that header-derived `shop` value, breaking the intended binding: `HMAC-verified bytes == raw_body`, but `shop identity used by the handler == request.shop` (header), and these two are never tied together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks the `hmac` field against `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` — the unauthenticated header — to the app's webhook handler as the tenant identifier, without ever verifying that this shop value is bound to the HMAC-covered body: [4](#0-3) 

Because the same app-wide `client_secret`/`api_secret_key` is used to sign webhooks for every shop that has installed the app, an attacker who controls their own shop installation can:
1. Trigger a legitimate webhook delivery to their own store (e.g. a customer/order event they can generate themselves), obtaining a body + a genuinely Shopify-computed HMAC for that body.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain.
3. `HmacValidator.validate` still passes (it only checks the body against the secret, and the secret is shared across shops for this app), while `Registry.process` builds `WebhookMetadata` with the attacker-chosen `shop`, causing the host app's handler to process/attribute the payload as if it came from the victim shop.

This is the same class of bug as the reported issue: a value used to make an identity/ownership decision (here, tenant `shop`) is not covered by the same authentication mechanism (HMAC) that is used to establish trust in the payload, so it can be substituted independently of the verified data.

### Impact Explanation
This crosses a tenant boundary purely through the gem's own webhook verification API: an app built on this gem cannot distinguish a forged-shop webhook from a genuine one using only the documented `Registry.process`/`HmacValidator.validate` flow, since `shop` is never checked against the signed bytes. Any handler logic keyed on `data.shop` (session/store lookup, per-tenant data writes, mandatory GDPR webhook processing, etc.) can be tricked into acting on behalf of a shop the attacker doesn't control, a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs the ability to install the app on a shop they control (which any merchant can do) and to trigger any webhook event on their own store to obtain a validly-signed body; no privileged credentials, access tokens, or `client_secret` compromise are required. Replaying with a modified header is trivial.

### Recommendation
Include the shop domain (and other identity-relevant fields such as `topic`) in the HMAC-signable content, or otherwise cryptographically bind `request.shop` to the verified payload before it is used for tenant attribution in `Registry.process`. At minimum, document/enforce that `WebhookMetadata.shop` must be cross-checked against the shop the receiving endpoint expects for that route.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`, both using the same app `client_secret`.
2. Attacker triggers a webhook (e.g., `orders/create`) on their own shop, capturing the raw POST body `B` and the resulting `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `H` against `B` [5](#0-4) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the app to process attacker-supplied data under the victim's tenant identity.
