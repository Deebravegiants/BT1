### Title
Governance lowering `challengePeriod` retroactively shrinks the veto window for already-stored state commitments - ([File: evm/src/core/HandlerV2.sol])

### Summary
`EvmHost.challengePeriod()` is a single global, mutable parameter that is checked *live* at the time a relayer submits a proof, rather than being snapshotted at the moment each state commitment was stored. This mirrors the reported bug class: an owner/governance parameter update (`skewFractionMax` in the report, `challengePeriod` here) is applied directly without re-validating it against state that is already "in flight" and depends on the old value, unintentionally breaking the protocol's safety invariant.

### Finding Description
`updateHostParamsInternal` allows cross-chain governance (via `hostManager`) to update `_hostParams.challengePeriod` to any new value with no dependency on commitments that are currently pending challenge: [1](#0-0) 

The challenge-period check performed before a relayer is allowed to finalize a request/response/timeout reads the *current* global value, not the value that was in effect when the corresponding state commitment was stored: [2](#0-1) [3](#0-2) [4](#0-3) 

The commitment itself only records the timestamp it was stored at, never the challenge period that applied at that moment: [5](#0-4) 

Because the delay check is `delay = now - storeStateMachineCommitmentUpdateTime`, compared against the *live* `challengePeriod()`, any reduction of `challengePeriod` retroactively applies to commitments that are already stored and awaiting the fisherman veto window that was promised under the old, longer period.

### Impact Explanation
Fishermen rely on the challenge period configured at the time a state commitment is stored to detect and veto (via `deleteStateMachineCommitmentInternal`) a malicious or erroneous commitment before it can be used: [6](#0-5) 

If governance shortens `challengePeriod` while a commitment is already pending, a relayer can immediately call `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` to deliver requests/responses/timeouts sourced from that commitment before fishermen have had the originally-guaranteed window to challenge it. This is an unintended, unsound-state-commitment condition that can enable forged/malicious message delivery — the same "invariant broken because a global threshold parameter change is applied without checking pending in-flight state" root cause as the reported `skewFractionMax` issue.

### Likelihood Explanation
This requires: (1) a legitimate/well-intentioned governance update lowering `challengePeriod` (e.g. via cross-chain governance through `hostManager`), occurring while (2) a state commitment is already stored and its fisherman veto window has not yet elapsed under the old (longer) period. Any single relayer (unprivileged) can then trigger `HandlerV2.handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts` immediately after the parameter update lands, without needing any special privilege — analogous to the trader's leverage-adjust transaction racing the owner's parameter update in the source report.

### Recommendation
Snapshot the challenge period value together with the state commitment when it is stored (e.g., store it alongside `_stateCommitmentsUpdateTime[stateMachineId][height]`), and have `HandlerV2` use that per-height snapshotted value in its elapsed-delay checks instead of the live `host.challengePeriod()`. This ensures a governance change to `challengePeriod` only affects commitments stored after the change, and never shortens the veto window fishermen were promised for commitments already pending — the same "re-check the invariant / don't retroactively apply the new value to existing state" fix recommended in the original report.

### Proof of Concept
1. A relayer submits a consensus proof, causing `storeStateMachineCommitment` to record a new (possibly malicious/incorrect) `StateCommitment` at `block.timestamp = T0`, with `challengePeriod = 24h` in effect.
2. Fishermen begin monitoring the commitment, planning to veto it within the 24h window if it's found to be fraudulent.
3. Hyperbridge governance separately (and for unrelated reasons) submits `updateHostParams` to reduce `challengePeriod` to `1h`. This lands at `T0 + 2h`.
4. Because the check in `HandlerV2.handlePostRequests` (and the response/timeout equivalents) reads `host.challengePeriod()` live and compares to `block.timestamp - stateMachineCommitmentUpdateTime`, the commitment now satisfies `delay(2h) > challengePeriod(1h)` and is treated as fully "challenged".
5. Any relayer can immediately call `handlePostRequests` to deliver requests proven against that commitment, even though fishermen were still within their originally-promised 24h veto window and have not had a chance to call `deleteStateMachineCommitment` to veto it.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

    /**
     * @dev Delete the state commitment at given state height.
     */
    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
