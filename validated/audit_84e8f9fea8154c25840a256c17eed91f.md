### Title
Unrestricted `CallDispatcher.dispatch()` allows any address to hijack the shared dispatcher's identity to steal escrowed assets and mint unbacked tokens - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()` is a public, unauthenticated entry point that executes an attacker-supplied array of arbitrary `{to, value, data}` calls as the `CallDispatcher` contract itself. This mirrors the core defect in CVE-2016-3081 (Apache Struts DMI): a dynamic-invocation surface that is reachable by any remote caller with no whitelist/authorization check on what gets invoked. Because `CallDispatcher` is deployed as a single shared contract reused across `HyperFungibleToken`, `WrappedHyperFungibleToken` and `IntentGatewayV2` deployments, and is documented/granted elevated roles (e.g. `MINTER_ROLE`) and briefly holds user funds mid-transaction, any unprivileged caller can invoke `dispatch()` directly to spend those privileges or sweep any balance the dispatcher happens to hold.

### Finding Description
`dispatch()` has no caller restriction whatsoever: [1](#0-0) 

Unlike the app contracts that gate their ISMP callbacks with `onlyHost`, this function is `external` with no modifier, so it is not restricted to being called only from `HyperFungibleToken.onAccept` / `IntentGatewayV2.placeOrder`. Any address can call it directly with a self-crafted `Call[]`.

The contract is meant to be a shared singleton — the docs instruct users to mint tokens directly to the `CallDispatcher` address so a bundled swap/approval can spend them, and note the dispatcher "holds tokens temporarily during execution": [2](#0-1) 

Test setup further shows the dispatcher is expected to be granted `MINTER_ROLE` on tokens in order to execute bridged calldata that mints: [3](#0-2) 

`IntentGatewayV2.placeOrder` also routes user funds through the same shared dispatcher, transferring assets to it and then dispatching calls against it, with dust intentionally allowed to remain if the predispatch/sweep calls don't fully drain the balance: [4](#0-3) 

Because any residual token balance, ETH balance, or granted role sits on the `CallDispatcher` address itself, and `dispatch()` executes calls in the dispatcher's own `msg.sender` context (`to.call{value: call.value}(call.data)`), any external actor can front-run or simply call `dispatch()` at any point to:
- Call `mint(attacker, amount)` on any token where `CallDispatcher` holds `MINTER_ROLE`, producing unbacked tokens.
- Call `transfer(attacker, balance)` on any ERC20 the dispatcher happens to hold (dust from fee-on-transfer tokens, partially-swept `IntentGatewayV2` escrow amounts, or tokens minted to the dispatcher mid-`onAccept` before the bundled calls execute).
- Drain any native ETH sent to the dispatcher via its unconditional `receive()`.

This is directly analogous to the Struts DMI flaw: a reachable dynamic-dispatch mechanism accepts attacker-controlled method targets/selectors with no authorization boundary, letting the attacker "chain" calls (multiple `Call` entries) to reach privileged operations that were only ever intended to be triggered through the legitimate ISMP delivery or intent-order flow.

### Impact Explanation
This directly matches the required impact bar: unbacked mint (if `MINTER_ROLE` is granted to the shared dispatcher, as the test setup demonstrates is the intended integration pattern) and theft of any funds temporarily custodied by the dispatcher (bridged tokens minted to it awaiting a bundled swap, IntentGatewayV2 escrow dust, or stray ETH). Since the dispatcher is a shared, cross-application singleton, the blast radius extends to every HFT/WrappedHFT/IntentGatewayV2 deployment pointed at the same dispatcher address.

### Likelihood Explanation
High. `dispatch()` requires no proof, no ISMP delivery, and no special caller — a single, ungated external transaction from any address is sufficient. The only precondition is that the shared `CallDispatcher` momentarily holds value or privilege, which is the explicitly documented/intended usage pattern (mint-to-dispatcher-then-swap, MINTER_ROLE grants, escrow transfers in `placeOrder`).

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific app contract(s) that are supposed to invoke it (e.g., an `onlyAuthorizedCaller` allowlist configured per-deployment, or make each app deploy/own its own dispatcher instance instead of sharing one), and avoid granting elevated roles (like `MINTER_ROLE`) to a shared, permissionless contract. At minimum, ensure no token/ETH balance or privileged role is ever left resident on the dispatcher's address between calls.

### Proof of Concept
1. Assume `CallDispatcher` at address `D` has been granted `MINTER_ROLE` on a bridged HFT token `T` (the pattern shown in `evm/tests/foundry/HyperFungibleTokenTest.sol:72-80`, and the composable-call design in `docs/content/developers/evm/hyper-fungible-token/hyper-fungible-token.mdx:121-159` which relies on tokens being minted directly to `D`).
2. An attacker (unprivileged, no ISMP proof, no relayer role) directly calls `D.dispatch(encoded)` where `encoded = abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(T.mint.selector, attacker, type(uint256).max)})])`.
3. Since `dispatch()` has no access control, execution proceeds: `T.mint(attacker, amount)` is invoked with `msg.sender == D`, which holds `MINTER_ROLE`, minting unbacked tokens directly to the attacker.
4. Equivalently, if `D` momentarily holds ERC20 balance from an in-flight `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:250-289`) or unswept dust, the attacker instead crafts a `Call` invoking `IERC20(token).transfer(attacker, D.balance)` to steal it.

```text
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
