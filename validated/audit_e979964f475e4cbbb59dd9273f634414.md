### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (tenant) identity used downstream by the app is read from an HTTP header that is never included in that HMAC computation. This breaks the equality that should hold between "the entity whose secret produced this HMAC" and "the shop the app believes the payload is for," enabling cross-tenant webhook confusion.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  The `shop` accessor, by contrast, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only this body HMAC and then dispatches the handler using the same unauthenticated `request.shop` value: [3](#0-2) 

Critically, the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app — it is not a per-shop key: [4](#0-3)  This means any merchant who has legitimately installed the app can, through their own store, cause the app to emit a validly-HMAC'd webhook body (e.g. by naming a product/order field with attacker-chosen content), capture that `(body, hmac)` pair, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. Because `shop` is not part of the signed material, the HMAC still validates, and the handler receives `WebhookMetadata` claiming to be from the victim shop while the attacker fully controls the body content.

This is precisely the bug class from the report: a field that is acted upon (`open_price`/here, `shop`) is not covered by the authentication mechanism (rounding of stored value/here, HMAC), letting an unprivileged party manipulate downstream logic through a value the verification step does not actually bind.

### Impact Explanation
Any app built on this gem that keys its business logic, data writes, or session lookups off `WebhookMetadata#shop` (the documented and expected usage pattern) can be made to attribute attacker-controlled webhook payloads to a different, victim tenant. This is a cross-tenant access/data-integrity vulnerability: an attacker with no more than "install the app on their own store" access can inject fabricated events into another shop's data pipeline (e.g., forged `orders/create`, `app/uninstalled`, or GDPR-style payloads) purely by relabeling a header, without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
The attack requires only: (1) installing the target app on any shop (which grants a valid, shared `client_secret`-derived HMAC oracle via Shopify's own webhook delivery), and (2) the ability to send an arbitrary POST to the app's public webhook endpoint with a spoofed header — both trivially available to any unprivileged internet user/merchant. No secret leakage, TLS interception, or social engineering is needed. Likelihood is high for any app whose webhook handlers trust `data.shop` for tenant scoping, which is the intended and documented use.

### Recommendation
Bind the tenant identity to the signature: include the `shop` (and ideally `topic`/`webhook-id`) in the signable material verified by `Utils::HmacValidator`, or independently cross-check the header-provided `shop` against an out-of-band trusted value (e.g., verify the shop is one with an active, previously stored session/access token for this app, and reject webhooks for shops with no such registration) before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant scoping without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook Shopify will legitimately sign with the app's `client_secret` (e.g., craft an order/product whose JSON body is attacker-chosen where possible, or simply capture any legitimate webhook body+HMAC pair).
3. Intercept the outbound webhook POST before/as it hits the app's endpoint (attacker controls their own network path since it's their own shop's webhook).
4. Replay the exact `raw_body` and `x-shopify-hmac-sha256` value to the app's real webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared secret: [5](#0-4) 
6. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload originated from and was signed via the attacker's own shop's webhook trigger: [6](#0-5)
