### Title
POA Bridge Withdrawal Status Misattribution for Batched Same-Asset Withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status/destination-tx-hash of a specific withdrawal by matching only on `assetId`, ignoring the `index` that uniquely identifies which withdrawal within a batched NEAR transaction the caller is asking about. When a single NEAR transaction contains two or more `ft_withdraw` intents for the same token (a legitimate, supported use case via the SDK's batch withdrawal processing), the SDK can report the wrong destination transaction hash/status for a given withdrawal index, breaking the equality "status/hash reported for withdrawal *i* == the real on-chain outcome for withdrawal *i*".

### Finding Description
`createWithdrawalIdentifier` [1](#0-0)  builds a `WithdrawalIdentifier` that carries an `index` meant to disambiguate multiple withdrawals originating from the same NEAR transaction (`tx.hash`). This `index` is the mechanism callers rely on to track each individual withdrawal within a batch.

However, `describeWithdrawal` never uses this `index` to select the matching entry returned by the POA bridge API. Instead, it delegates to `findMatchingWithdrawal`, which matches purely by `assetId`: [2](#0-1) 

```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	...
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

The code comment explicitly acknowledges the flaw:
> "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." [4](#0-3) 

Since `Array.prototype.find` always returns the **first** matching element regardless of which `index` the caller asked about, if a NEAR transaction contains two `ft_withdraw` intents for the same `nep141:` token (e.g., two withdrawals to different destination addresses/amounts in one batch), calling `describeWithdrawal` for withdrawal index 0 and withdrawal index 1 both return the **same** matched entry from the POA API — the first one found — including its `transfer_tx_hash` and completion status.

This breaks the required equality that the reported destination-chain outcome (status + txHash) for a given withdrawal identifier corresponds to that specific withdrawal's actual on-chain settlement, not another withdrawal's settlement.

### Impact Explanation
An integrator polling withdrawal status via `watchWithdrawal`/`describeWithdrawal` [5](#0-4)  for a batch containing two same-token withdrawals can:
- Receive `status: "completed"` with a `txHash` belonging to a *different* withdrawal, causing the integrator to believe the second (still-pending or failed) withdrawal settled successfully.
- This can lead to premature crediting/reconciliation of funds that have not actually reached the correct destination, or a double credit if both withdrawals are independently reconciled against the same reported hash.

This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category. No malicious actor is required — this occurs during ordinary use of the SDK's documented batch-withdrawal feature ("Batch Processing: Process multiple withdrawals at a time" [6](#0-5) ) whenever two withdrawals of the same POA-bridged token are included in one transaction.

### Likelihood Explanation
Likelihood is limited by the precondition that a batch must contain two or more withdrawals of the exact same `assetId` routed through the PoA bridge in a single NEAR transaction — a legitimate scenario the SDK's batch API does not prevent or warn against at call time (only in an internal code comment). Any integrator building multi-recipient batch withdrawals of the same token (e.g., paying out multiple users the same asset) would trigger this without any special conditions or privileges.

### Recommendation
Extend `findMatchingWithdrawal` (or the underlying POA API usage) to disambiguate by more than `assetId` — e.g., additionally match on `amount`, `destinationAddress`, and/or by sorting both the API results and the local withdrawal list by amount/order as the code comment suggests, or track a POA-side identifier equivalent to `index`. Until fixed, the SDK should either reject/warn when multiple same-asset withdrawals are batched through the PoA bridge, or document that batching identical-asset PoA withdrawals is unsafe and must be avoided by integrators.

### Proof of Concept
1. Build a batched withdrawal request with two `ft_withdraw` intents for `nep141:btc.omft.near`: withdrawal A (index 0) to address X for 100000n, and withdrawal B (index 1) to address Y for 50000n, executed in one NEAR transaction (`tx.hash`).
2. Call `bridge.describeWithdrawal({ landingChain, index: 0, withdrawalParams: withdrawalA, tx })` and `bridge.describeWithdrawal({ landingChain, index: 1, withdrawalParams: withdrawalB, tx })`.
3. Once the POA bridge API lists both withdrawals for `tx.hash` under `near_token_id: "btc.omft.near"`, `findMatchingWithdrawal` returns the same (first) entry for both calls, per `withdrawals.find((w) => "nep141:" + w.data.near_token_id === assetId)` [7](#0-6) , so both index 0 and index 1 report the same `status`/`transfer_tx_hash`, even though they are distinct withdrawals to different addresses/amounts on-chain — demonstrated directly by the existing unit test acknowledging assetId-only matching: [8](#0-7) .

		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
