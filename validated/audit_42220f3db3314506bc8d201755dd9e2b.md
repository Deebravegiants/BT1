## Analog Found: Flash‑loan‑manipulable Uniswap V4 spot price used to price Simplex intent fills

### Title
Simplex's Uniswap V4 venue pricing trusts an unprotected, manipulable spot price to size intent‑gateway fills, letting a flash‑loan attacker extract value from the solver - (File: `sdk/packages/simplex/src/strategies/fx.ts`, `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex ("FXFiller") prices curveless, exotic-token pairs directly off a Uniswap V4 pool's **instantaneous spot price** (`sqrtPriceX96`/tick), then uses that same live pool state to withdraw liquidity from its own LP position to fund the fill. The only defense is an *optional*, static `referencePrice` ± `maxDeviationBps` band (`checkPriceGuard`). This is functionally identical to the reported `WstethLiquidityVault`/`SingleSidedLiquidityVault` bug class: a spot-pool price is trusted for a payout decision, bounded only by a tolerance band around a reference/oracle, so an attacker can flash-loan the pool to the edge of (or, if unconfigured, entirely outside) that band and extract value proportional to the allowed slippage/deviation.

### Finding Description
`FXFiller.resolveLegRates` (and `referenceRate`) prices a curveless pair whose `token0` is a USD stable by calling the funding venue's `getExoticTokenPrice`, which is `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`: [1](#0-0) 

This returns the **raw pool mid** derived straight from `sdkPool.token0Price`/`token1Price` (i.e. from `sqrtPriceX96`), with no TWAP, no size/impact term, and no fee-tier adjustment, as the project's own flow documentation states: [2](#0-1) 

The only guard is `checkPriceGuard`, which merely bounds the live quote's deviation from a static `referencePrice` by `maxDeviationBps` - and it is optional: [3](#0-2) [4](#0-3) 

That guarded (or fully unguarded, if `referencePrice`/`maxDeviationBps` are omitted) price is then used to compute `targetOutput`/`policyMaxOutput` for the leg - i.e. how many exotic tokens the solver is contractually committing to pay the order's beneficiary: [5](#0-4) 

The same live pool state is also used, moments later in the same evaluation, to plan the LP withdrawal that funds the fill (`planWithdrawalForToken` → `findLiquidityForDeficit` → `buildSdkPosition`), pricing exactly how much liquidity must be pulled from the solver's own Uniswap V4 position to produce the committed output: [6](#0-5) 

This mirrors the reported bug precisely: in `WstethLiquidityVault`/`SingleSidedLiquidityVault`, the on-chain pool balance ratio determines the payout, bounded only by `_isPoolSafe()`'s oracle-deviation `THRESHOLD`; here, the on-chain pool spot price determines both the trade rate and the LP withdrawal amount, bounded only by the optional `maxDeviationBps` band. In both cases, an attacker can flash-loan the pool to move the spot price to the edge of the tolerated band (or entirely free, if the guard is unconfigured — explicitly allowed: *"omit both to leave the chain unguarded"*), profiting by the gap between the manipulated price and the true market price.

The docs even document the profit-extraction pattern for the intended (honest) operator flow, underscoring how directly the price feeds payout: [7](#0-6) 

### Impact Explanation
An attacker who is simply an ordinary Intent Gateway order-placer (fully unprivileged) can:
1. Flash-loan swap through the same Uniswap V4 pool Simplex reads for pricing/funding, pushing the spot price to the edge of `maxDeviationBps` (or unboundedly, on any solver that left the guard unconfigured, which the schema explicitly permits).
2. Submit/execute an order against that pair while the price is skewed, so `resolveLegRates`/`referenceRate` prices the exotic-token leg off the manipulated spot instead of the true market rate.
3. Receive an inflated exotic-token payout while the solver funds it (via wallet balance and/or an LP withdrawal sized off the same manipulated pool state), extracting value bounded only by the configured deviation tolerance (or unbounded when unguarded).
4. Repeat until slippage/fees make it unprofitable, then repay the flash loan.

This is a direct, concrete theft of solver funds through a single attacker-controlled transaction/order, analogous to the reported High-severity finding, and matches "concrete theft ... of funds" and "unauthorized app action" in the validation criteria.

### Likelihood Explanation
- The guard is **optional** (`referencePrice`/`maxDeviationBps` "must be set together... omit both to leave the chain unguarded" - [8](#0-7) ), so any solver instance not configuring it is trivially exploitable with no bound at all.
- Even when configured, the guard only bounds *deviation from a static reference*, not execution cost or price impact, exactly like the original `_isPoolSafe`/`THRESHOLD` limitation the report calls out.
- No privileged access, governance, or special timing is required — only capital for a flash loan and the ability to place/execute an Intent Gateway order, which is the exact unprivileged "intent solver/orderer" reachability required by the scope.

### Recommendation
- Do not price fills, or size LP withdrawals that fund them, from a single instantaneous spot read (`sqrtPriceX96`/tick). Use a manipulation-resistant reference (e.g., a TWAP over a window long enough to make flash-loan manipulation costly, or an external oracle) as the source of truth, with the live pool state only used to check *executability*, not to set the payout price.
- Make the price guard (`referencePrice` + `maxDeviationBps`) mandatory whenever Uniswap V4 venue pricing is enabled, rather than optional.
- Size the guard band tightly and account for the pool's fee tier/impact so that a value equal to the allowed deviation cannot be repeatedly extracted risk-free.

### Proof of Concept
1. Solver configures `[vault.uniswapV4]` for a USDC/EXOTIC pair either with no `referencePrice`/`maxDeviationBps` (unguarded, permitted per [4](#0-3) ) or with a wide `maxDeviationBps`.
2. Attacker flash-loans the underlying Uniswap V4 pool token and swaps to push `sqrtPriceX96` so that `computeDirectPoolPriceUsd` reports the exotic token as more valuable than its true market price, staying inside `maxDeviationBps` (or with no bound at all if unguarded).
3. In the same transaction/block, attacker places (or has ready) an Intent Gateway order sending USDC for the exotic token; Simplex's `evaluateOrder`/`resolveLegRates` reads the manipulated spot price via `getExoticTokenPrice` and passes `checkPriceGuard`, sizing `targetOutput` off the inflated rate (`sdk/packages/simplex/src/strategies/fx.ts:1443-1466`).
4. Simplex funds the fill from wallet balance and/or by withdrawing liquidity from its own Uniswap V4 position at the same manipulated price (`UniswapV4FundingPlanner.planWithdrawalForToken`, `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:352-418`), delivering more exotic tokens to the attacker than the true market rate justifies.
5. Attacker repays the flash loan in the same transaction, keeping the excess value extracted from the solver.

		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
