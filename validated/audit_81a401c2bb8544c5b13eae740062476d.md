## Analysis

The report's bug class — grouping/identity confusion because a value used for grouping decisions is not itself covered by an integrity check — maps to a genuine binding break in this gem's webhook processing path.

**The binding that should hold:** `bytes verified by HMAC == bytes acted upon (including tenant identity)`.

**What actually happens:**

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body — it does **not** include the `shop` (or any header) in the signed material: [1](#0-0) 

But `shop` is read straight from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then forwards `request.shop` — the unverified header — directly to the app's handler as the tenant identity for the event: [3](#0-2) 

So: `HMAC covers {raw_body}` ≠ `tenant identity acted upon = {shop header}`. Any party that can obtain one legitimately-signed webhook body (e.g., by installing the app on their own store and triggering a webhook — a normal unprivileged action) can replay that exact body to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` still passes because the signature only certifies the body bytes, not the header, and the gem hands the forged shop value onward as authoritative (`WebhookMetadata.new(... shop: request.shop ...)`).

### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop` (and other headers) are read unauthenticated and passed through as the trusted tenant identifier by `ShopifyAPI::Webhooks::Registry.process`.

### Finding Description
`HmacValidator.validate` computes/compares the HMAC using `verifiable_query.to_signable_string`, which for webhooks equals `@raw_body` alone [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all taken directly from HTTP headers with no cryptographic binding to the body or to each other [4](#0-3) . `Registry.process` treats `request.shop` as trustworthy tenant context once the HMAC check passes [3](#0-2) . An attacker who legitimately owns a development/trial shop can trigger any webhook topic on their own store, capture the (validly-signed) raw body, and replay it to the app's shared webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature still validates because it never covered the shop header in the first place.

### Impact Explanation
This breaks the binding `hmac_verified_bytes == tenant_identity_bytes`, letting an attacker who controls only their own shop cause the host application to process an event as if it originated from a different merchant (cross-tenant confusion). Depending on the webhook topic the app has registered (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or order/product topics), this can trigger tenant-scoped side effects (data deletion, deprovisioning, state changes) against a shop the attacker does not control, using data/timing entirely of the attacker's choosing.

### Likelihood Explanation
Requires only: (1) the attacker installs the app on a shop they control (normal, unprivileged action any developer/merchant can do), and (2) the app exposes a single shared webhook endpoint for all merchants (the common integration pattern documented for this gem). No access token, `client_secret`, or Shopify-side credential is needed — only the ability to send an HTTP request with an attacker-chosen `shop-domain` header and a body/HMAC pair obtained from the attacker's own legitimate webhook delivery.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the signable string used for HMAC verification, or independently verify that the `shop` header corresponds to a shop actually known to have an active webhook subscription/session before trusting it as tenant context in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets any registered webhook (e.g., `orders/create`) fire; captures `raw_body` and the valid `x-shopify-hmac-sha256` header Shopify computed for that body.
2. Attacker POSTs to the app's shared webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since `to_signable_string` only checks `raw_body` [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the app to act on the victim's tenant data/context using attacker-controlled payload content.
