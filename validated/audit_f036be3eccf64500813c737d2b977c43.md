## Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The MOMP bug is a case where a value used for a security-relevant decision (the denominator in a price calculation) is bound to the wrong scope (borrower debt) instead of the scope the calculation is supposed to protect (pool debt). The equivalent break-an-equality pattern in this gem is `ShopifyAPI::Webhooks::Request#hmac` validating only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` — the fields the receiving app uses to attribute and route the event — are read straight from unauthenticated HTTP headers and are never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are not part of the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC over that signable string only, and then trusts `request.topic`/`request.shop`/`request.webhook_id`/`request.api_version` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the HMAC over `verifiable_query.to_signable_string` (i.e. the body) with the app's single, shop-agnostic `Context.api_secret_key`: [4](#0-3) 

The binding that should hold is:
`HMAC(secret, bytes-that-determine-shop-and-topic) == received_hmac`

What actually holds is:
`HMAC(secret, raw_body) == received_hmac`, while `shop`/`topic`/`webhook_id` are taken from separate, unsigned header bytes.

Because a single app-level `client_secret` (`api_secret_key`) is shared across every shop that installs the app (there is no per-shop signing key), any merchant who installs the app on their own store can obtain a real, validly-signed `(raw_body, hmac)` pair from Shopify for their own shop's events. Since the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers are not covered by that signature, the same attacker can resend that exact `(raw_body, hmac)` pair to the app's shared webhook endpoint while substituting the `shop-domain`/`topic`/`webhook-id` headers with a victim shop's domain or a different topic/id. `HmacValidator.validate` still returns `true` because the signature check only ever looks at `raw_body`, and `Registry.process` will happily route the (attacker-supplied) `shop`/`topic`/`webhook_id` values to the registered handler as if they came from Shopify for that shop/topic: [5](#0-4) 

### Impact Explanation
This breaks the tenant identity binding the app relies on to attribute webhook data to the correct shop: the app-level handler receives `WebhookMetadata` claiming to originate from shop B (or from a mandatory topic like `shop/redact`/`customers/redact`/`customers/data_request`) while the signed body actually belongs to shop A. Depending on how the host app trusts `data.shop`/`data.topic` (e.g. to select which shop's session/data-store record to write, delete customer data for, or trigger uninstall/redact flows), this enables cross-tenant data confusion/injection: an attacker who legitimately controls one shop can forge events attributed to any other shop that installed the same app, without ever needing that shop's access token or the app's `client_secret`. This matches the "High: cross-tenant access" impact category via a credential/identity-binding break, not a documented-API-misuse issue — the gem itself only checks the body, and exposes `shop`/`topic`/`webhook_id` as if they were authenticated.

### Likelihood Explanation
Any unprivileged internet user can install the target app on a store they control (many Shopify apps are publicly installable/dev-store installable), then capture a legitimate webhook delivery for their own shop and replay it against the app's shared, internet-reachable webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers. No secrets, tokens, or TLS interception are required — the attacker only needs a webhook that Shopify legitimately sent to them for their own store, and control over the raw HTTP request they resend.

### Recommendation
Include the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered bytes, or independently verify them out-of-band (e.g., compare `request.shop` against the shop associated with the session/subscription that the app registered and reject mismatches) before dispatching to the handler. At minimum, document that `shop`/`topic`/`webhook_id` from `ShopifyAPI::Webhooks::Request` are unauthenticated headers and must not be trusted for authorization decisions without additional cross-checking by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own shop; Shopify sends a POST with `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`.
3. Attacker captures this legitimate request (`raw_body`, `hmac`) — valid because `HmacValidator.validate_signature` only checks `OpenSSL.secure_compare(computed_signature, received_signature)` over `raw_body`, per `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`, e.g. `customers/redact`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-derives the signature from `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
6. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on victim-shop's tenant context using attacker-controlled body/topic — a cross-tenant identity binding break.
