### Title
Webhook shop-domain (and topic) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature it verifies only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and passes it straight through to the application's webhook handler without any cryptographic binding between that value and the signature that was validated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled from headers, entirely outside that signed string: [2](#0-1) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header - it never validates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` only calls `HmacValidator.validate(request)` and then immediately forwards `request.shop` (and `topic`, `webhook_id`, `api_version`) to the application's handler via `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop authenticated by the HMAC`. Because the signature is computed purely over the raw body, this equality is never enforced — the `shop-domain` header can be swapped to any value without invalidating the signature, as long as the body bytes are unchanged. For many webhook topics (especially the mandatory compliance topics `shop/redact`, `customers/redact`, `customers/data_request`, or any webhook whose payload doesn't itself embed a shop identifier the handler cross-checks), an attacker who can obtain one genuinely-signed webhook delivery (e.g., by having Shopify send a real webhook to their own development/trial store, since the payload for many topics is small/predictable and the app's HMAC secret is shared across all shops using the same app) can replay that body with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret, and `Registry.process` passes the attacker-chosen `shop` value to the handler as if it were authenticated.

### Impact Explanation
This breaks the shop-tenant binding that host applications rely on to determine which merchant's data a webhook handler should act on. If a handler uses `WebhookMetadata#shop` to select the tenant record to update or delete (a common and documented pattern, e.g. GDPR `customers/redact`/`shop/redact` handlers), an attacker can cause the app to perform actions attributed to, or scoped to, a shop they do not control — a cross-tenant confusion vulnerability reachable purely through this gem's exposed webhook-processing API surface (`Registry.process`), without needing the victim's access token or `client_secret`.

### Likelihood Explanation
Exploitation requires the attacker to possess one validly-signed webhook body for the shared app secret — attainable by installing the app on a shop the attacker controls, since Shopify signs webhooks with the app's single `client_secret`/`api_secret_key` regardless of which shop triggered them. The attacker then only needs to replay that body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secrets belonging to the victim are needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable payload used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed body (e.g., require host apps to cross-check `request.shop` against a shop they expect, and document that `shop` is unauthenticated). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` so that the HMAC covers the shop-domain header, closing the gap where a verified-body request can carry an arbitrary, unverified tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a genuine webhook (e.g. `customers/redact`) — this produces a body `B` and a valid `X-Shopify-Hmac-Sha256` header `H` computed over `B` with the app's `api_secret_key`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint using the same body `B` and the same `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, causing the application to process a redact/data action for `victim.myshopify.com` that was never actually sent by Shopify for that shop.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
