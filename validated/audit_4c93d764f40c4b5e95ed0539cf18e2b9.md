Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate_signature` computes the HMAC only over `verifiable_query.to_signable_string` [3](#0-2) , and `Registry.process` accepts any request whose body/HMAC pair is valid, then forwards `request.shop` (and other headers) unchecked to the handler [4](#0-3) .

### Title
Webhook shop-domain/topic/id headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and validates only the raw HTTP body via HMAC-SHA256, but the `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which the registry and downstream handlers treat as trusted, shop-scoped identity data — come from unauthenticated headers that are excluded from the signed payload.

### Finding Description
`Request#to_signable_string` is defined as simply `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers with no cryptographic binding to the body or to each other [5](#0-4) .

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` using the app's single, shop-independent `Context.api_secret_key` [6](#0-5) . Since the secret is identical for every shop that installs the app, and the signature covers only the body bytes, **any body+HMAC pair that was valid for shop A remains a valid signature no matter which shop-domain header is attached to it.**

`Registry.process` raises only if the HMAC check itself fails; it never cross-checks that the `shop` header is consistent with anything cryptographically bound to the body. It then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and passes it straight to the app's handler [4](#0-3) .

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop_header_claimed == shop_actually_authenticated_by_signature` — the signature authenticates only "this app's secret produced this HMAC over this body," not "this body/HMAC came from shop X."

### Impact Explanation
This is a cross-tenant data-integrity/impersonation issue (High): an attacker who can install the target app on their own shop (any public app can be freely installed by any Shopify merchant) can capture a legitimate webhook body+HMAC pair for their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop domain. Because the HMAC only covers the raw body, the signature check still passes, and the host application's webhook handler will process data it believes originated from the victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select a tenant's DB record, session, or billing state), this allows cross-tenant data corruption or confusion attributed to a shop the attacker doesn't control.

### Likelihood Explanation
Medium-High: no privileged credentials are required beyond installing the app on an attacker-controlled shop (a normal, permitted action for any Shopify merchant/app installer), and the attack only requires replaying a captured legitimate webhook to the same public webhook endpoint with a modified header. Header spoofing is trivial since HTTP headers are attacker-controlled on outbound-facing requests to the webhook receiver, and the signature check has no dependency on them.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the signed payload verification, or otherwise validate that the shop-domain header is consistent with a value cryptographically tied to the request (Shopify's own webhook signing already ties the HMAC only to the body, so the gem should instead require host applications to cross-validate `request.shop` against an authenticated session/tenant record before trusting it, and this expectation should be enforced/documented explicitly in `Webhooks::Registry.process`). At minimum, document loudly in `Request`/`Registry` that `shop`, `topic`, and `webhook_id` are NOT authenticated by the HMAC and must not be used as a sole tenant-identity source without additional verification against a known-good record.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC(secret, B)`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` computes `HMAC(secret, B)` and finds it equals `H` via `OpenSSL.secure_compare`, so validation passes [3](#0-2) .
4. `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` even though the payload never originated from, nor was authenticated for, that shop [7](#0-6) .
