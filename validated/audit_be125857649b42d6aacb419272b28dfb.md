### Title
Reentrancy in Tron `IntentGatewayV2.withdraw()` allows repeated draining of escrowed order tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) performs external token/native transfers to a caller-controlled `beneficiary` *before* decrementing the corresponding escrow accounting, and unlike its mainline EVM sibling, this contract carries no reentrancy protection at all.

### Finding Description
`withdraw()` is reached from two unprivileged-triggerable settlement paths: `onAccept()` (gated `onlyHost`, but the host simply relays a delivered/relayed ISMP message whose `WithdrawalRequest.beneficiary` is attacker-controlled data carried over from the destination-chain fill) and directly from `cancelOrder()` for same-chain orders. [1](#0-0) 

Inside `withdraw()`, for each escrowed token the contract checks only that the escrow slot is non-zero, then makes the external transfer, and only afterwards subtracts the amount from `_orders[body.commitment][token]`: [2](#0-1) 

Because `beneficiary` can be an attacker-deployed contract, the native-token `.call{value: amount}("")` (or the ERC-20 `token.call(transfer(...))` for tokens with callback/hook semantics, or via a fallback triggered by the plain `.call`) hands control back to the attacker before `_orders[body.commitment][token] -= amount` executes. A reentrant call into `withdraw()` (via `onAccept`/`cancelOrder` re-dispatch, or any other externally reachable path that reaches `withdraw` for the same `commitment`) will see the stale non-zero escrow balance and pay out again, transferring the same escrowed funds multiple times before any state is updated. The same pattern applies to the transaction-fee payout later in the function, which is also paid via `.call` before any reentrancy-blocking primitive exists.

This directly contradicts the pattern already fixed and defended-in-depth on the mainline EVM contracts: `evm/src/apps/IntentGatewayV2.sol` inherits `ReentrancyGuardTransient` and its `IntrinsicIntents`/`ExtrinsicIntents` fill functions apply Checks-Effects-Interactions by setting `_filled[commitment] = msg.sender` before any external call, which is specifically regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. [3](#0-2) [4](#0-3) 

The Tron contract has none of this: it neither inherits any reentrancy guard nor imports one. [5](#0-4) 

### Impact Explanation
This is a direct theft/permanent-freezing-of-funds vulnerability class: escrowed order inputs (user deposits held by the gateway pending fill/cancel settlement) can be drained more than once through a single relayed settlement message or a single `cancelOrder` call, at the expense of legitimate order participants and/or the protocol's escrow solvency. This matches the "concrete theft ... of funds" acceptance bar for Medium/High severity.

### Likelihood Explanation
Reachable by any solver/user who controls the `beneficiary` address of an order (routine, unprivileged) combined with a relayer delivering a `RedeemEscrow`/`RefundEscrow` message, or directly via `cancelOrder` for same-chain orders where the order's own `beneficiary`/`user` is attacker-controlled. No special privileges, governance, or consensus compromise are required — only a malicious contract as beneficiary and a native-token or malicious-token escrow entry, mirroring exactly the reentrancy attack scenario the team already built dedicated tests for on the mainline contract.

### Recommendation
Apply the same fixes already present in the mainline EVM `IntentGatewayV2`/`IntentsBase`:
1. Add a reentrancy guard (e.g. `ReentrancyGuardTransient`) to the Tron `IntentGatewayV2` contract and mark `withdraw`/externally-reachable entry points (`onAccept`, `cancelOrder`, `fillOrder` if present) `nonReentrant`.
2. Apply Checks-Effects-Interactions in `withdraw()`: decrement `_orders[body.commitment][token] -= amount` (and clear the fee entry) *before* performing the native/ERC-20 transfer, mirroring `IntentsBase._withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 451-485) which already does effects-then-interaction.

### Proof of Concept
1. Attacker places (or is the beneficiary of) an order whose output/escrow includes a native-token (or malicious ERC-20) entry, with `beneficiary` set to an attacker-controlled contract `Evil`.
2. `Evil` implements a `receive()`/token callback that, upon receiving the payout inside `withdraw()`, re-enters `onAccept()`/`cancelOrder()` with the same `commitment` before the first call returns.
3. In `withdraw()` at line 700-704, the guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` still passes because `_orders[...] -= amount` (line 710) has not executed yet.
4. `Evil` receives a second payout for the same escrowed amount; the loop/decrement in the original call then finally executes, but the funds have already been double-paid, draining the escrow (or protocol reserves) by the reentered amount. [6](#0-5)

```text
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
```
