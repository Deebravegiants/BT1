Audit Report

## Title
Unprivileged clients can hijack/DoS Web API trigger responses by front-running `MessageID` before the legitimate request in the Gateway's WebAPI capability handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` stores the pending-request callback keyed solely by the caller-supplied `MessageID` with no uniqueness/collision check before the map write, unlike sibling handlers in the same codebase. Any actor who can produce a validly-signed message (signed with their own arbitrary key — no allowlist enforcement exists at this layer yet) can submit a colliding `MessageID` and overwrite another in-flight caller's saved callback, causing the original caller's request to time out and the node's eventual response to be delivered to the attacker's callback instead.

## Finding Description
In `HandleLegacyUserMessage`, the handler unconditionally overwrites `h.savedCallbacks[msg.Body.MessageID]` without first checking whether an entry for that ID already exists: [1](#0-0) 

`msg.Body.MessageID` is fully attacker-controlled and `Validate()` only checks length/format, never uniqueness or binding to a specific sender: [2](#0-1) 

The handler is reachable from the Gateway's public JSON-RPC entry point `ProcessRequest`, which routes any legacy (DonID-bearing) request straight to `HandleLegacyUserMessage` after only format validation of the message, not authorization/allowlisting: [3](#0-2) 

The code itself acknowledges this gap with an explicit TODO comment ("apply allowlist and rate-limiting here"), and the handler's own test suite has an outstanding TODO noting that sender validation/rate limiting is unresolved: [4](#0-3) [5](#0-4) 

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes by `MessageID` alone and delivers the payload to whichever callback currently occupies that slot — last writer wins: [6](#0-5) 

By contrast, the HTTP trigger v2 handler and the Vault handler both explicitly reject a request whose ID is already in flight before storing it: [7](#0-6) [8](#0-7) 

This asymmetry between handlers confirms the missing check is a genuine gap rather than an intentional design choice.

## Impact Explanation
An actor with any valid ECDSA keypair (no DON membership or special role required, since sender allowlisting is explicitly not yet implemented at this layer per the code's own TODOs) can submit a legacy `web_api_trigger` request carrying a `MessageID` equal to a victim's in-flight request. This overwrites the victim's `savedCallback` entry; the victim's original HTTP call to the Gateway subsequently times out via `callback.Wait(ctx)` in `ProcessRequest`, and the node's eventual response for that `MessageID` is instead delivered to the attacker's callback. This is a griefing/DoS condition and a cross-user response-confusion risk consistent with the "gateway request impersonation" / "cross-user response corruption" impact categories.

## Likelihood Explanation
Exploitability hinges on the attacker knowing or guessing the victim's `MessageID` and winning the race before the node responds. The reference client tooling in this repo treats `MessageID` as an arbitrary, non-randomized, caller-supplied string (e.g., a CLI flag defaulting to a fixed value), which suggests some client integrations may use predictable or even static IDs, making the race practically feasible: [9](#0-8) 
No signature forgery of the victim is required — the attacker signs their own message with their own key — and no allowlist currently blocks this because the enforcement point is explicitly marked as not-yet-implemented in the handler.

## Recommendation
Add a uniqueness check in `HandleLegacyUserMessage` before inserting into `h.savedCallbacks`, mirroring `httpTriggerHandler.setupCallback` and `vault handler.newActiveRequest`: if an entry for `msg.Body.MessageID` already exists (and has not expired), reject the new request with an explicit error instead of silently overwriting the existing callback. Additionally, prioritize implementing the sender allowlist/rate-limiting already flagged by the TODO comments in this handler.

## Proof of Concept
1. Send a signed legacy `web_api_trigger` request with `MessageID = "X"` signed by key A to the Gateway; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards to DON nodes.
2. Before a node responds, send a second legacy request with the same `MessageID = "X"` signed by an unrelated key B; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = callbackB` with no collision check.
3. When a DON node emits a `MethodWebAPITrigger` response for `MessageID = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers the response to caller B.
4. Caller A's original HTTP request times out in `ProcessRequest`'s `callback.Wait(ctx)`, never receiving a response — demonstrable via a Go unit test extending `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go` with two distinct signing keys sharing one `MessageID`, asserting `cbA.Wait` times out while `cbB` receives the node's response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
