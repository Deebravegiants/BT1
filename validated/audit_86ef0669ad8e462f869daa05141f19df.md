### Title
Unvalidated `shop` Parameter in OAuth Callback Leaks `client_secret` to Attacker-Influenced Host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request host directly from the `shop` field of the incoming `AuthQuery`, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, the domain-allowlist check that this same codebase already uses in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`. As a result, the `client_id`/`client_secret`/authorization `code` are POSTed to whatever host string is present in the callback's `shop` value.

### Finding Description
`validate_auth_callback` only verifies the HMAC signature over the query string (which includes `shop` as one of the signed fields) and that the `state` cookie matches — it never checks that `shop` actually resolves to a trusted `*.myshopify.com` / Shopify-controlled domain: [1](#0-0) 

The unvalidated `shop` is then used to build the base host for the access-token request, and the request body — carrying `client_id`, `client_secret`, and the authorization `code` — is sent to that host: [2](#0-1) [3](#0-2) 

The `HttpClient` used to perform the request derives its `base_uri` straight from `session.shop`, with no domain restriction applied at this layer either: [4](#0-3) 

The equality that should hold — but is broken here — is:
`host that the app validated as a legitimate Shopify shop` == `host that actually receives the app's client_secret`.

The gem already codifies the correct binding elsewhere via `ShopValidator`, which restricts shop domains to an explicit allowlist (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, or a configured `myshopify_domain`) before it is trusted: [5](#0-4) 

That check is applied in the Token Exchange, Client Credentials, and Refresh Token flows (`lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`), but is conspicuously absent from the Authorization Code Grant callback path in `oauth.rb`, which is the one flow that directly transmits the `client_secret` in a request body rather than only using it as an HMAC key or Basic-Auth-style secret validated server-side by Shopify.

### Impact Explanation
`shop` in the OAuth callback is attacker/redirect-influenced input (an unprivileged party can drive the value that ultimately appears in the callback query before the request is processed by this method — the method's only defense is HMAC-over-the-query, not host-allowlisting). Since the method builds the host for the client_secret-bearing HTTP request directly from this field with no domain restriction, a value that is not a genuine Shopify domain results in the app's `client_secret` (plus the authorization `code`, which can be exchanged for a merchant access token) being sent to a host outside Shopify's trust boundary. This is SSRF carrying the app's own OAuth credentials — matching the High-impact criterion for "SSRF with the app's credentials" and creating a path toward client_secret/authorization-code exfiltration.

### Likelihood Explanation
Likelihood is constrained by the fact that `shop` is one of the fields covered by the HMAC, so the request must still pass through Shopify's own callback-signing process; a fully attacker-controlled forgery without any legitimate Shopify-triggered redirect is not directly demonstrated here. However, the omission is structural and inconsistent with the rest of the codebase's own defense-in-depth: every other place that turns a caller-supplied `shop` into a network destination for the same `client_secret` (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) enforces `ShopValidator.sanitize!`, while the historically most security-sensitive path — the Authorization Code Grant callback that directly ships `client_secret` in a POST body — does not.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(auth_query.shop, myshopify_domain: Context.myshopify_domain)` (or the equivalent sanitize/validate call already used in `token_exchange.rb`) at the top of `validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, before `auth_query.shop` is used to construct `null_session`, `auth_base_uri`, or any outbound HTTP request, and raise `Errors::InvalidOauthError` if validation fails.

### Proof of Concept
1. An attacker triggers the OAuth Authorization Code Grant flow such that the callback delivered to the app's redirect URI contains a `shop` value that is not restricted to `*.myshopify.com` (e.g. a custom/unified-admin style or otherwise non-allowlisted domain string) alongside a `hmac` that validates for that exact query string.
2. `ShopifyAPI::Auth::Oauth.validate_auth_callback` accepts the request because `Utils::HmacValidator.validate` only checks signature integrity of the byte string, not the semantic validity of `shop` as a Shopify domain (`lib/shopify_api/auth/oauth.rb:64`).
3. `auth_base_uri(shop)` (`lib/shopify_api/auth/oauth.rb:117-119`) and `Clients::HttpClient#initialize` (`lib/shopify_api/clients/http_client.rb:18`) construct the request host directly from this unvalidated `shop`.
4. The library issues `POST https://<shop>/admin/oauth/access_token` with body `{ client_id, client_secret, code, expiring }` (`lib/shopify_api/auth/oauth.rb:74-90`) to that host, disclosing the app's `client_secret` and authorization `code` outside Shopify's trust boundary.

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
