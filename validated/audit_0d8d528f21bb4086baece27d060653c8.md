Audit Report

## Title
PSM permanently DoS's mint/redeem for an external asset if its live decimals metadata changes after registration - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`pallet-psm` snapshots an external asset's decimals into `ExternalAssetInfo::decimals` at `add_external_asset` time, and the internal asset's decimals into `PsmInfo::internal_decimals` at `create_psm` time. Every mint/redeem call enforces strict equality between these snapshots and the live decimals reported by `pallet-assets` via `ensure_decimals_match`, so any decimals metadata change made by the asset's own team/owner (via `set_metadata`/`force_set_metadata`, entirely outside PSM admin control) permanently breaks minting/redeeming for that asset pair.

## Finding Description
`ExternalAssetInfo::decimals` and `PsmInfo::internal_decimals` are point-in-time snapshots taken respectively when an external asset is approved and when the PSM instance is created. `ensure_decimals_match` is invoked on every mint/redeem path and rejects the call with `Error::DecimalsMismatch` if the live decimals (queried through `T::Fungibles::decimals`, backed by `pallet-assets`) no longer equal the stored snapshot for either the internal or external asset. Decimals are part of `pallet-assets` metadata, mutable independently via `set_metadata`/`force_set_metadata` by that specific asset's Owner/Issuer (or Root), which is a completely different authority than the PSM instance's `full_admin`/`emergency_admin` checked in `ensure_psm_admin`. There is no cross-pallet hook or extrinsic in PSM to refresh the cached snapshot when live metadata changes, so a legitimate metadata correction on the underlying asset by its own team permanently desynchronizes the snapshot from the live value for that PSM instance.

## Impact Explanation
Once decimals diverge, all mint/redeem calls for the affected `(internal_asset, external_asset)` pair on that PSM instance revert with `DecimalsMismatch` indefinitely, since the check runs unconditionally on every call and nothing in the pallet updates the stored snapshot. The pallet's documented remediation is `remove_external_asset` followed by re-`add_external_asset`, and `remove_external_asset` requires debt to reach zero first — which cannot happen if redemptions (needed to drain outstanding debt) are also blocked by the same check. This is a genuine denial of service of core economic functionality for an in-scope pallet, matching the claimed severity of freezing user funds/operations for the affected asset pair.

## Likelihood Explanation
The trigger requires the external asset's own Owner/Issuer (or Root) to call `set_metadata`/`force_set_metadata` on `pallet-assets` changing decimals after the PSM has already onboarded that asset — a realistic, non-privileged-to-the-PSM administrative action from an independent authority. No compromise of the PSM's own admin roles is needed, and the PSM has no visibility into or control over the external asset's metadata authority, which is precisely the unsynchronized-state trust-boundary issue described.

## Recommendation
- Avoid hard-reverting on live-vs-snapshot decimals mismatch; either recompute conversions from live decimals, or provide a permissionless/PSM-admin extrinsic to refresh the stored snapshot when a mismatch is detected.
- Track debt/reserve in decimals-agnostic units so a later metadata change cannot invalidate outstanding conversions.
- Ensure `remove_external_asset` (or an emergency-only variant) remains callable even when `ensure_decimals_match` would fail, so an asset pair is never simultaneously untradeable and unremovable.

## Proof of Concept
1. Asset team creates external asset `X` with `decimals = 6` in `pallet-assets`.
2. PSM admin calls `add_external_asset(internal_asset, X)`, storing `ExternalAssetInfo { decimals: 6, .. }`.
3. Users mint/redeem normally while live decimals (6) match the snapshot.
4. `X`'s Owner/Issuer (or Root) calls `set_metadata`/`force_set_metadata` changing `decimals` to `8`.
5. Any subsequent `mint`/`redeem` call on `(internal_asset, X)` now fails `ensure_decimals_match` with `Error::DecimalsMismatch` permanently, and `remove_external_asset` is blocked while `PsmDebt` remains nonzero (since redemptions needed to drain it are themselves blocked), leaving the pair untradeable and unremovable until root/governance intervention.
