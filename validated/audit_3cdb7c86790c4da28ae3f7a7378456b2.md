### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the value handed to app webhook handlers (`shop`, `topic`, `webhook_id`, `api_version`) purely from unauthenticated HTTP headers, while `ShopifyAPI::Utils::HmacValidator` only verifies the raw request body bytes. An attacker who can obtain one valid `(raw_body, hmac)` pair for *any* shop (e.g. by installing the target app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. The signature still validates because the shop identity is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body only: [2](#0-1) 

Yet `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers that are not part of the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values: [4](#0-3) 

The gem's own documentation instructs apps to use `data.shop` as the tenant key to route/persist webhook effects (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), treating it as a trusted, verified identity because it arrived through `Registry.process` after "HMAC verification": [5](#0-4) 

This is the identity-binding break called out in the rules: the field that is *acted on* (`shop`, used as the tenant/session key by the handler) is not the field that is *covered by the HMAC* (only `raw_body` is). Concretely: `shop_used_by_handler (header) ≠ shop_bound_by_signature (none)`.

### Impact Explanation
Because the HMAC is body-only, an attacker can:
1. Cause a legitimate webhook to be sent to the app for a shop they control (any dev/free store the attacker installs the app on), capturing a valid `(raw_body, x-shopify-hmac-sha256)` pair for a topic whose body is fixed/predictable/empty (e.g. `app/uninstalled`, or any topic where the JSON payload content is attacker-influenced or generic, such as `"{}"`).
2. Replay that exact body and HMAC to the app's public webhook receiver endpoint, but with the `x-shopify-shop-domain` header rewritten to the victim's `*.myshopify.com` domain (and/or a different `x-shopify-topic`).
3. `HmacValidator.validate` passes because it only checks the body bytes; `Registry.process` then invokes the app's handler with `WebhookMetadata` carrying the victim's `shop`, causing the app to perform tenant-scoped side effects (e.g. marking the victim shop uninstalled, deleting the victim's stored session/access token, or processing forged order/customer data) — a cross-tenant action triggered without ever presenting the victim shop's credentials.

This crosses the tenant boundary using only the attacker's own shop and no privileged material from the victim, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (a) the ability to install/trigger a webhook from any shop, including a free attacker-controlled store, and (b) knowledge of a topic whose body is constant, predictable, or attacker-controlled (uninstall/deletion topics are commonly near-empty JSON). No access token, `client_secret`, or leaked credential is needed — this is a pure unprivileged internet-user replay against the gem's own webhook-processing logic.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material verified by `HmacValidator`, or otherwise cryptographically bind them to the body (e.g., include them in `to_signable_string`, or require the app to cross-check `shop` against a known/installed shop list before trusting it) rather than trusting header-derived identity purely because the body HMAC validated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers `app/uninstalled` (or any topic with a fixed/empty body), capturing the raw POST including headers `x-shopify-hmac-sha256: H` and body `B = "{}"`.
2. Attacker POSTs to the app's webhook callback route with headers:
   - `x-shopify-topic: app/uninstalled`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - body `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request object; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`.
4. `Registry.process` looks up the handler for `app/uninstalled` and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: {}, ...)`, causing the app to perform victim-tenant-scoped teardown/logic despite the request never having been sent by Shopify on behalf of the victim shop. module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
