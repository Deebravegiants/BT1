### Title
Unchecked decimal-scaling direction in `convert_to_balance`/`convert_to_erc20` can under-scale cross-chain HFT transfers - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The `pallet-hyper-fungible-token` converts amounts between the local (Substrate) asset's decimals and the remote ERC20's decimals using `saturating_sub` on the decimal difference, exactly the class of bug described in the external report: a slippage/amount value computed without correctly accounting for asymmetric decimals between two representations of the "same" transfer amount.

### Finding Description
`convert_to_erc20` and `convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs` compute the scaling factor as `10u128.pow(erc_decimals.saturating_sub(local_decimals))` (or the mirrored subtraction), rather than handling both the "erc_decimals > local_decimals" and "erc_decimals < local_decimals" cases symmetrically: [1](#0-0) 

- `convert_to_balance(value, erc_decimals, local_decimals)` divides `value` by `10^(erc_decimals.saturating_sub(local_decimals))`. This is only correct when `erc_decimals >= local_decimals`. If `local_decimals > erc_decimals` (the local asset has *more* decimals than the registered ERC20 side), `saturating_sub` returns `0`, so no division is performed at all — the raw ERC20-scaled `value` is used directly as the local balance, which is `10^(local_decimals - erc_decimals)` times too large.
- `convert_to_erc20(value, erc_decimals, local_decimals)` multiplies by `10^(erc_decimals.saturating_sub(local_decimals))`. If `erc_decimals < local_decimals`, this saturates to `0` and no scaling occurs — the local-decimals-scaled `value` is sent as-is to the ERC20 side and interpreted there in the (smaller) `erc_decimals`, inflating the amount by `10^(local_decimals - erc_decimals)`.

This precision-mismatch pathway is used directly in the `send` extrinsic, which is reachable by any signed, unprivileged user: [2](#0-1) 

Here `erc_decimals` is read from `Precisions::<T>::get(...)` (governance-configured per asset/chain) and `decimals` is either `T::Decimals::get()` (native) or the pallet-local asset's own metadata decimals. `convert_to_erc20` is used to build the ERC20 `Message.amount` that mints on the destination EVM `HyperFungibleToken`/wrapper contract. If a misconfiguration (or a token registered with local decimals greater than the destination ERC20's decimals) ever occurs, the `saturating_sub` silently drops the scaling instead of reverting or erroring, so the destination mint amount is computed with the wrong magnitude — directly analogous to the reported `AssetLogic._swapAsset` bug, where a slippage/min-out value silently ignored a decimals mismatch instead of adjusting for it.

This differs from the external Connext bug in that the root cause there was an intentional but incomplete percentage calculation; here it is an arithmetic function whose "always non-negative" `saturating_sub` masks the reversed-decimals case instead of asserting `erc_decimals >= local_decimals` (or handling both directions). The net effect is the same failure mode: silent magnitude error from decimal mismatch feeding directly into a cross-chain value used for minting/burning tokens.

### Impact Explanation
If this path is ever hit with `local_decimals > erc_decimals` for a configured asset/chain pair, `send()` would burn/escrow the correct (small, local-decimals) amount from the user but dispatch a POST request instructing the destination `HyperFungibleToken` contract to mint an amount that is `10^(local_decimals - erc_decimals)` times too large — an unbacked mint on the destination chain, i.e. counterfeit token supply. Conversely, the receiving side's `convert_to_balance` divides by 0 exponent under the mirror condition, again producing a magnitude mismatch (in this direction, it would under/over-credit the local balance relative to what was actually burned on the EVM side). Both directions are on the critical "unbacked mint" / "loss of funds" impact categories called out in the validation criteria.

### Likelihood Explanation
This requires governance (via `Precisions` storage, populated through token registration) to register a pair where the local asset's decimals exceed the destination ERC20's decimals, or vice versa for the receive path — this is a configuration-dependent, not purely user-triggered, precondition. The core arithmetic function itself, however, is unconditionally reachable by any signed account through the public `send` extrinsic once such a configuration exists, and the `saturating_sub` masks the misconfiguration silently rather than causing an assertion failure that operators would notice at registration time. Given decimals asymmetry between different asset standards (e.g., a Substrate asset minted at 12 decimals mapped to an 18-decimal wrapped ERC20, or vice versa) is a realistic operational configuration (the codebase's own `BridgeToken.sol` comment notes exactly this kind of 12-vs-18-decimal mismatch being handled by pallet-side scaling), the likelihood of hitting the unhandled direction is non-trivial if any future asset registration inverts the assumed ordering.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling in `convert_to_erc20`/`convert_to_balance` with logic that explicitly branches on which side has more decimals (multiply on one branch, divide on the other), mirroring the pattern already used correctly elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount` in `evm/src/utils/VWAPOracle.sol`, which handles both `_decimals < 18` and `_decimals > 18` branches). Additionally, assert at token-registration time (`Precisions` write path) that decimals values are sane, and add unit tests exercising both `local_decimals > erc_decimals` and `local_decimals < erc_decimals` configurations to catch silent saturation.

### Proof of Concept
1. Governance registers a local asset with `local_decimals = 18` and sets `Precisions::<T>::insert(asset_id, dest_chain, erc_decimals = 6)`.
2. A user calls `send` with `params.amount = 1_000_000_000_000` (1e12), which is burned/escrowed correctly at 18-decimal local precision (a tiny fraction of one token).
3. `convert_to_erc20(1_000_000_000_000, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6saturating_sub(18) = 0`, so `erc20_amount = 1_000_000_000_000 * 10^0 = 1_000_000_000_000`.
4. This value is dispatched as the `Message.amount` field to the destination EVM contract, which interprets it at its own (18-decimal, ERC20-standard) precision — a mint of `1e12 / 1e18` ETH-equivalent units is negligible, but if the roles/decimals are configured the opposite way (`erc_decimals = 18`, `local_decimals = 6`) the same code path multiplies by `10^12`, so burning `1` local-unit (base unit at 6 decimals) yields a destination mint instruction for `10^12` ERC20 base units — a 10^6-times overmint relative to the 6-decimal token's intended unit value, unbacked by any real escrow. /// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
