## Title
Outbound delivery reward claims lack chain/genesis binding, enabling signature replay across Hyperbridge chain forks - (File: `modules/pallets/relayer/src/outbound_request.rs`, `modules/pallets/relayer/src/outbound_consensus.rs`)

### Summary
`pallet-ismp-relayer`'s outbound-delivery reward claims (`process_outbound_request_delivery_claim` and `process_outbound_consensus_delivery_claim`) authenticate a relayer solely via a signature over `(commitment, destination, payee)` or `(set_id, destination, payee)`. Neither payload binds the signature to the Hyperbridge chain itself (no genesis hash, spec version, or other chain identifier of the *source* chain producing the claim). Replay protection relies exclusively on on-chain storage flags (`OutboundRequestsClaimed` / `OutboundConsensusRotationsClaimed`), which are chain-local state. If Hyperbridge (the relay chain hosting this pallet) ever forks — e.g. a contentious runtime upgrade or client bug causing chain split, the exact "eventual chain forks" scenario the referenced report describes for `HardenedTopupProxy` — a signature captured on one fork remains valid on the other, because all signed fields (`commitment`/`set_id`, `destination`, `payee`) are identical on both forks while the "already claimed" storage diverges independently per fork.

### Finding Description
The signed message construction functions: [1](#0-0) [2](#0-1) 

hash only `(commitment, dest_chain, payee)` and `(set_id, dest_chain, payee)` respectively via `sp_io::hashing::keccak_256`, with no field identifying the source (signing) chain. This mirrors exactly the `constructMsg` flaw in the referenced report, which hashed `MOVER TOPUP` fields without `block.chainid`.

The signature is verified generically in `Signature::verify`, which simply recovers/validates against the raw message bytes with no domain separation: [3](#0-2) 

Replay protection is implemented purely as an idempotency flag scoped to the pallet's own storage: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

If the chain forks after a claim's underlying commitment/state proof exists on both forks (which is guaranteed since both forks share identical pre-fork state, and the destination state commitment the claim proves against does not change), the `OutboundRequestsClaimed`/`OutboundConsensusRotationsClaimed` maps become independent per fork. A relayer who submitted `OutboundRequestDeliveryClaim`/`OutboundConsensusDeliveryClaim` on fork A can resubmit the exact same extrinsic (same `state_proof`, same `signature`) on fork B: the state proof still verifies against fork B's own stored state commitment for the destination (state commitments for external destinations like EVM chains are unaffected by a Hyperbridge-side fork), and the signature still recovers the same address/bytes, since nothing in the signed payload changes between forks.

This is contrasted with the withdrawal flow, `modules/pallets/relayer/src/withdrawal.rs`, which does include a per-relayer `nonce` in its signed message: [8](#0-7) 

but the nonce there is also chain-local storage (`Nonce::<T>`), so it suffers the identical cross-fork replay weakness — a withdrawal signed and consumed (nonce incremented) on fork A remains valid and unconsumed on fork B.

### Impact Explanation
On a chain split, an unprivileged relayer can resubmit identical, previously-valid reward claim extrinsics on each resulting fork, draining the `TreasuryPalletId` account (or double-collecting fees via the withdrawal path) on every fork independently — a direct, permanent theft of protocol treasury funds proportional to the number of forks times the configured `OutboundRequestDeliveryReward`/`OutboundConsensusDeliveryReward`. This is unbacked value extraction from the treasury with no attacker cost beyond re-broadcasting an already-known signed payload.

### Likelihood Explanation
Chain forks of a governed Substrate/Polkadot-style parachain are rare, but Polkadot-ecosystem chains have experienced unplanned splits from client/runtime bugs, and Hyperbridge's own governance-driven runtime upgrades are a plausible trigger, matching the "eventual chain forks" premise the original report itself relies on for its High severity rating. Because none of these signed payloads bind to chain identity, exploitation requires zero additional relayer action beyond replaying an existing signature after a fork is observed — no fresh cryptographic material or privileged access is needed.

### Recommendation
Include a chain-identifying value in every signed message used for these claims — e.g. `frame_system::Pallet::<T>::block_hash(0)` (genesis hash) or `<T as frame_system::Config>::Version::get().spec_version` — as part of `outbound_request_delivery_message`, `outbound_consensus_delivery_message`, and the withdrawal `message` function, so a signature produced pre-fork cannot validate on a chain that diverges from the signer's intended chain. Equivalently, adopt a proper domain-separated signing scheme (e.g., include the genesis hash the way Substrate's own `signed_extensions` design guards extrinsics against replay across forks/chains).

### Proof of Concept
1. Relayer delivers a hyperbridge-originated request to a destination and submits `OutboundRequestDeliveryClaim { request, state_proof, payee, signature }` where `signature` is over `outbound_request_delivery_message(commitment, destination, payee)`; `process_outbound_request_delivery_claim` succeeds, inserts `OutboundRequestsClaimed[commitment]`, and pays `reward` from treasury.
2. Hyperbridge chain forks into fork A (continuation) and fork B (new chain) at a height after step 1. Both forks share the state at the fork point, including the previously stored destination state commitment used in step 1's proof, and both have independent copies of `OutboundRequestsClaimed`.
3. On fork B, `OutboundRequestsClaimed[commitment]` was already set before the fork (it was set at the fork point since the claim happened pre-fork) — so consider instead a claim made post-fork on fork A only: relayer submits the claim on fork A (succeeds, marks claimed on fork A only).
4. Relayer resubmits the byte-identical `OutboundRequestDeliveryClaim` extrinsic on fork B. `OutboundRequestsClaimed[commitment]` is unset on fork B, the state proof verifies against fork B's own (independently maintained) destination state commitment, and `signature.verify(&msg, None)` still recovers the same `delivered_by` address because `msg` (`commitment`, `destination`, `payee`) is chain-agnostic. The claim succeeds again on fork B, paying out a second `reward` from fork B's treasury for a reward already collected on fork A. [9](#0-8)

	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);

		let module_id: BoundedVec<u8, ModuleIdBound> = request
			.from
			.clone()
			.try_into()
			.map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
		let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
		ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);

		ensure!(destination == request.dest, Error::<T>::MismatchedStateMachine);

		let state_machine = ismp::handlers::validate_state_machine(&host, state_proof.height)
			.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let receipt_key = state_machine
			.receipts_state_trie_key(vec![commitment])
			.into_iter()
			.next()
			.ok_or(Error::<T>::OutboundRequestUnsupportedDestination)?;
		let proof_results =
			Self::verify_withdrawal_proof(&*state_machine, &state_proof, vec![receipt_key.clone()])
				.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let raw = proof_results
			.get(&receipt_key)
			.cloned()
			.flatten()
			.ok_or(Error::<T>::OutboundDeliveryNotProven)?;

		let delivered_by = Self::decode_receipt_relayer(destination, &raw)?;

		let msg = outbound_request_delivery_message(commitment, destination, payee);
		let recovered = signature.verify(&msg, None).map_err(|_| Error::<T>::InvalidSignature)?;
		ensure!(recovered == delivered_by, Error::<T>::OutboundRequestSignerMismatch);

		let treasury: T::AccountId =
			<T as Config>::TreasuryPalletId::get().into_account_truncating();
		let payee_account: T::AccountId = payee.into();
		<<T as pallet_ismp::Config>::Currency as Mutate<T::AccountId>>::transfer(
			&treasury,
			&payee_account,
			reward,
			Preservation::Preserve,
		)
		.map_err(|_| Error::<T>::OutboundRequestRewardTransferFailed)?;

		OutboundRequestsClaimed::<T>::insert(commitment, ());

		Self::deposit_event(Event::OutboundRequestDeliveryRewarded {
			commitment,
			state_machine: destination,
			module_id,
			relayer: payee_account,
			amount: reward,
		});

		Ok(())
	}
