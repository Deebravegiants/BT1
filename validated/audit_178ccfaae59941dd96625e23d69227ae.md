### Title
Shared Emporium identity in CASE2 (stateless) ops allows cross-user hijack of `msg.sender`-authenticated state in external contracts - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
In `EmporiumUpgradeable.runAction`, CASE2 ("Stateless Interaction") executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract itself, so every Hinkal user who routes an operation through CASE2 presents the identical `msg.sender` (the singleton Emporium address) to the target contract. Any external protocol that binds authorization or ownership to `msg.sender` (e.g., `beneficiary = msg.sender` on initialization) will therefore treat all Hinkal/Emporium CASE2 users as one indistinguishable principal, letting any unprivileged attacker later satisfy that same `msg.sender` check and redirect the associated funds to themselves.

### Finding Description
The broken equality is: *the on-chain principal that initialized state in a third-party contract via Emporium == the on-chain principal that later claims/controls that state via Emporium*. This should always be true per Hinkal user, but is not for CASE2 operations.

`EmporiumUpgradeable.runAction` branches on `op.invokeWallet`: [1](#0-0) 

- CASE 1 (`op.invokeWallet == true` and `stack.signerAddress != address(0)`): the call is proxied through `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`, and inside `HinkalWallet.callHinkalWallet` the low-level call to `endpoint` originates from the wallet contract's own address: [2](#0-1) 
Because `stack.signerAddress` is authenticated via an EIP-712 signature that must recover to that exact address, this address is unique per signer, so `msg.sender` seen by the endpoint is a per-user identity.

- CASE 2 (the `else` branch, no `invokeWallet` requirement enforced): `op.endpoint.call{value: op.value}(op.callData)` is invoked directly from within `EmporiumUpgradeable` itself, so `msg.sender` as observed by `op.endpoint` is the Emporium contract's own address — the same value for every user of the protocol, regardless of who called `transact()`/`runAction`. [3](#0-2) 

`runAction` itself is guarded only by `onlyAllowedRecipient`, which checks that the caller is an allow-listed Hinkal-facing contract, not that the *op* is routed through a per-user wallet: [4](#0-3) 
There is no check anywhere forcing `op.invokeWallet == true` for endpoints whose authorization model is keyed on `msg.sender` — this decision is entirely delegated to the end user crafting the `EmporiumStack`/`EmporiumOperation[]`.

Exploit flow:
1. Victim calls `transact()` with a CASE2 op targeting a vesting/lock contract's `initializeVesting(msg.sender)` (or similar) via the Emporium external action. Because the call executes from Emporium's own code, `beneficiary` is recorded as the Emporium contract's address, not the victim's identity.
2. Attacker (any unprivileged EOA who can generate their own proof/`CircomData` and craft their own `EmporiumStack`) later calls `transact()` with their own CASE2 op invoking the same vesting contract's `release()`. Inside `release()`, `onlyBeneficiary` compares `msg.sender` (Emporium) to the stored `beneficiary` (also Emporium) — check passes.
3. Tokens are transferred by the vesting contract to `msg.sender`, i.e., to the Emporium contract's balance.
4. Back in the attacker's own `runAction` execution, `balanceChange = balancesAfter - balancesBefore` picks up this increase and `handleOut` mints a UTXO for it using the attacker's own `circomData.stealthAddressStructure`: [5](#0-4) 
The attacker thus claims a shielded UTXO for funds that were vested for the victim, with no proof or nullifier constraint preventing this, because from the circuit/UTXO-accounting perspective this is a completely valid "balance increased, mint UTXO to caller" flow — the vulnerability lives entirely in the *external* contract's trust of Emporium's shared identity, which Hinkal's CASE2 path exposes without warning or restriction.

None of the existing guards (`onlyAllowedRecipient`, `verifyWallet`'s EIP-712 signature check, `payRelayFees`, the balance-non-negative check, nullifier/root checks) address this, because they all operate correctly on Hinkal's own internal accounting; the flaw is that CASE2 silently reuses the singleton Emporium address as the caller identity for arbitrary external calls that a user might reasonably (or carelessly) use for stateful, `msg.sender`-authenticated interactions.

### Impact Explanation
Any Hinkal user who uses a CASE2 (`invokeWallet == false`) Emporium operation to interact with a third-party contract that authorizes actions based on `msg.sender` exposes that state to every other Hinkal user, because all such calls share the same caller identity (the Emporium contract). An attacker can hijack that state (e.g., claim vested/locked funds, reassign ownership, drain an allowance granted to "the caller") and mint a shielded UTXO crediting themselves via `handleOut`. This is direct theft of another user's off-chain-authorized-but-on-chain-`msg.sender`-keyed assets, funneled into Hinkal's shielded pool under the attacker's control — matching the Critical category (direct theft of funds routed through Hinkal's shielded accounting).

### Likelihood Explanation
Requires the victim to have used a CASE2 op against a contract whose security model relies on `msg.sender` identity (common pattern: `initialize(...)` implicitly using `msg.sender` as owner/beneficiary, or `approve`/deposit-then-claim flows). This is a precondition dependent on victim behavior/contract choice rather than a universal always-exploitable bug, but it requires no privilege from the attacker beyond normal Hinkal usage (their own funds, their own proof, their own crafted `EmporiumStack`), and is fully repeatable against any victim who makes this mistake with any vulnerable external contract. Given CASE2 is explicitly offered as a general-purpose "call any endpoint" primitive with no allowlist or endpoint-classification, and there is no on-chain enforcement steering `msg.sender`-authenticated interactions to CASE1, this is a realistic and repeatable attack surface once a suitable external target exists.

### Recommendation
Do not allow arbitrary, unrestricted `msg.sender`-shared calls from the shared Emporium singleton to be a first-class, unguarded primitive. Options:
- Enforce that CASE2 endpoints are restricted to an owner-curated allowlist (mirroring `onlyAllowedRecipient`/`isAllowedRecipient` pattern already used elsewhere) of contracts verified to be stateless w.r.t. `msg.sender`, rejecting arbitrary endpoints by default.
- Alternatively, require `op.invokeWallet == true` (routing through a per-user `HinkalWallet`) for any endpoint not on a "known-stateless" allowlist, so that stateful/authorization-sensitive calls always execute with a per-user caller identity rather than the shared Emporium address.
- Document prominently (and ideally enforce at the SDK/proof-generation layer) that CASE2 must never be used against contracts that key state or authorization off `msg.sender`.

### Proof of Concept
Foundry test plan:
1. Deploy a mock `Vesting` contract with `initializeVesting()` that stores `beneficiary = msg.sender` and locks a token amount, plus `release()` with `onlyBeneficiary` (`msg.sender == beneficiary`) that transfers the vested amount to `msg.sender`.
2. Deploy `EmporiumUpgradeable`, allow-list it as an external action recipient on a test `Hinkal` instance.
3. Victim: fund the vesting contract and call `transact()`/`_externalTransact` with a CASE2 `EmporiumOperation` (`invokeWallet=false`) whose `callData` is `Vesting.initializeVesting(...)`. Assert `vesting.beneficiary() == address(emporium)`.
4. Attacker: with their own valid proof/UTXOs (no relation to victim), call `transact()` with a CASE2 op whose `callData` is `Vesting.release()`, and with `circomData.stealthAddressStructure` set to the attacker's own stealth address.
5. Assert: `release()` succeeds (equality `msg.sender(=emporium) == beneficiary(=emporium)` holds), the vested tokens land in Emporium's balance, and `handleOut` mints a UTXO of that amount to the attacker's stealth address — proving the equality "claimant of vested funds == funder of vesting (victim)" is broken, with the attacker instead ending up as the claimant.
