### Title
Webhook Shop/Tenant Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the raw request body was signed with the app's shared `api_secret_key`. The `shop-domain` header, which is used afterwards as the tenant identifier passed to the webhook handler, is never included in the signed material. Since a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who has installed the app can obtain a genuinely-signed webhook for their own store and replay it to the same endpoint with the `shop-domain` header swapped for a victim shop, producing a webhook that the library reports as authentic and cross-tenant.

### Finding Description
`HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw HTTP body — none of the Shopify headers are part of the signed content: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` uses `Utils::HmacValidator.validate(request)` purely as a body-authenticity gate, then dispatches to the handler using the *unverified* `request.shop` as the tenant identity for the event: [4](#0-3) 

The equality the code implicitly (and incorrectly) assumes is:

`shop authenticated by HMAC(secret, raw_body) == shop asserted in the shop-domain header`

But the HMAC proves only "this body was produced by someone holding `api_secret_key`" — it says nothing about *which* shop the body belongs to. Because `api_secret_key` is a single, app-wide secret shared by every shop that installs the app (not a per-shop secret), any shop that has installed the app can legitimately obtain body+HMAC pairs signed with that same secret (from Shopify's real webhook delivery to their own store). Nothing stops that shop from re-delivering the same signed body to the app's webhook endpoint with a different `shop-domain`/`topic`/`webhook-id` header, since those headers are outside the signed scope.

### Impact Explanation
This breaks the tenant boundary between shops installed on the same app (cross-tenant access), which the rules classify as Critical impact. A malicious merchant, who is otherwise an ordinary, unprivileged user of the platform with no access to `api_secret_key`, an access token, or any victim credentials, can cause the app to process a webhook it believes originates from a different shop. Depending on the handler logic (e.g. `app/uninstalled`, `customers/data_request`, order/customer webhooks), this can trigger data deletion, GDPR-request mishandling, cache/session poisoning, or business-logic actions attributed to the wrong tenant.

### Likelihood Explanation
Any user who can install the target app on their own store automatically receives genuinely-signed webhook deliveries. Replaying such a delivery with modified headers to the same publicly reachable webhook endpoint requires no special access, credentials, or privileged actions—only a basic HTTP client. The library performs no additional binding between the signed body and the tenant-identifying headers, so likelihood is high wherever `Registry.process`/`Request` is used to determine which shop a webhook affects.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used for verification, or otherwise cryptographically bind the header values to the body (e.g., verify the shop domain embedded in the JSON payload, when present, matches the header, and require the two to agree before dispatch). At minimum, document and enforce that `Registry.process` callers must independently corroborate `request.shop` against a value derived from already-authenticated context (e.g., an existing stored session/webhook subscription id for that shop) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`. Shopify delivers a legitimate webhook, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `api_secret_key` (shared across all installs of the app) and headers `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this valid `(raw_body, hmac)` pair.
3. Attacker POSTs the identical `raw_body` and `hmac` to the same app webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this still succeeds because headers aren't part of `to_signable_string`.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to act as though the (forged) event came from the victim's shop.
