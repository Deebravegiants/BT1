### Title
Reentrant `schedule_named`/`cancel_named` calls into the currently-servicing `Agenda` slot are silently dropped due to stale-snapshot write-back in `service_agenda` - ([File: substrate/frame/scheduler/src/lib.rs])

### Summary
`Pallet::service_agenda` reads `Agenda::<T>::get(when)` into a local `Vec` once at the start, dispatches every task in that slot (which can itself invoke `Scheduler::schedule_named`, `cancel_named`, or `reschedule_named` for the very same `when`), and only writes the *local, stale* snapshot back to storage (or unconditionally removes the key) at the end of the loop. Any storage mutation a reentrant nested call makes to `Agenda::<T>(when)` during that loop is silently clobbered by this final write-back, causing legitimately (and even freshly, reentrantly) scheduled tasks to be lost while their `Lookup` entry remains, producing a dangling reference.

### Finding Description
`service_agenda` (substrate/frame/scheduler/src/lib.rs) works as follows: [1](#0-0) 
- Line 1278: `let mut agenda = Agenda::<T>::get(when);` — a **local copy** is taken before any task is executed.
- Line 1297-1309: for each entry in `ordered` (computed once, before dispatch, from that same local copy), the task is `take()`n from the local vector and dispatched via `Self::service_task`, which calls into the runtime dispatcher with the task's call.
- Lines 1325-1329: after the loop, the function writes back `Agenda::<T>::insert(when, agenda)` (using the **local, pre-dispatch-based** vector) or, if `postponed == 0 && dropped == 0`, calls `Agenda::<T>::remove(when)` unconditionally.

If a task being serviced at `when` dispatches `Scheduler::schedule_named` (or `reschedule_named`) targeting the *same* `when`, the nested call's `push_to_agenda`/`place_task` reads current storage (`Agenda::<T>::get(when)`, still the pre-loop value because the outer function hasn't written back yet), appends the new task at a new index, and writes it to storage: [2](#0-1) 
The new index (e.g. index 2) is **not** part of `ordered`, which was computed from the original 0/1-length agenda before the reentrant insert. Since the outer loop only tracks `postponed`/`dropped` for indices in `ordered`, it will conclude the agenda is fully drained (`postponed == 0 && dropped == 0`) and execute `Agenda::<T>::remove(when)`, permanently erasing the reentrantly-inserted task from storage even though `Lookup::<T>::insert(name, (when, 2))` was already committed by the nested call. The `Lookup` entry now points to a removed agenda slot — a dangling/orphaned reference — and the task never executes.

Symmetrically, `do_cancel_named`/`do_reschedule_named` invoked reentrantly on a task at an index that has *already* been read into the local snapshot but not yet reached by the loop will mutate storage (`Agenda::<T>::try_mutate`) which is immediately overwritten by the outer function's final write-back derived from its own stale local copy — meaning a "cancelled" task can still be dispatched (from the stale local slot) despite its cancellation succeeding in storage, an equally serious accounting desync (opposite direction from vanishing, but same root cause). [3](#0-2) [4](#0-3) 

None of the existing checks (`ensure_privilege`, `Lookup::contains_key` uniqueness check, `MaxScheduledPerBlock` bound) protect against this because they only validate the logical/permission correctness of an individual schedule/cancel operation — none of them account for the fact that `service_agenda` holds and later overwrites a stale, pre-dispatch in-memory snapshot of the exact same storage key that the nested call is concurrently mutating within the same block's execution.

### Impact Explanation
A task that is legitimately scheduled (either pre-existing at the same `when` slot, or newly scheduled by a reentrant nested call during that block's servicing of `when`) can be permanently and silently dropped from the `Agenda` while its `Lookup` mapping still references it, or conversely a cancelled task can still be executed despite the cancellation appearing to succeed. This matches the scoped impact: a legitimately scheduled dispatch is permanently lost/desynced from the `Lookup` index — a critical, silent queue-integrity failure for `pallet_scheduler`, which underlies governance execution timers, treasury payouts, and numerous parachain runtime automation flows (including calls reachable from cumulus xcmp-queue-adjacent runtime logic that schedule follow-up dispatches).

### Likelihood Explanation
Exploitability requires that the attacker (or an attacker-influenced call reachable via proxy/multisig/governance-enactable calls) has a path to get `Scheduler::schedule_named`/`cancel_named`/`reschedule_named` dispatched *from within* a call that is itself being serviced by the scheduler at the same `when`. This is only reachable if `ScheduleOrigin` (or the effective origin check inside `schedule_named`/`cancel_named`) permits the calling context used by the reentrant dispatch — in most production runtimes (Westend, Rococo, Asset Hub) `ScheduleOrigin` is restricted to privileged origins (root/governance), which significantly limits unprivileged reachability; a fully signed-origin-permitted configuration would make this trivially and repeatably triggerable by any account able to schedule a self-referential/nested task. Given the question's stated precondition that `ScheduleOrigin permits Signed`, the underlying pallet logic bug is real and deterministically reproducible whenever that precondition holds.

### Recommendation
`service_agenda` must not use a snapshot taken before dispatch as the source of truth for the final write-back. Re-read `Agenda::<T>::get(when)` (or use `try_mutate`/index-scoped mutation) immediately before the final insert/remove, merging only the specific indices this invocation actually serviced (setting them to `None`) into the *current* storage state, rather than blindly overwriting the whole vector with the stale local copy. Alternatively, disallow (via `BaseCallFilter`/`CallerOrigin` filtering while inside `service_task`) any nested dispatch of `Scheduler::schedule_named/cancel_named/reschedule_named/schedule/cancel` calls that would mutate the currently-servicing `when` bucket.

### Proof of Concept
Rust integration test in `substrate/frame/scheduler/src/tests.rs`:
1. At block N-1, schedule task A (unnamed, priority 0) at `when = N` whose call is `Scheduler::schedule_named(id = "C", when = N, ..., call = remark_with_event)` — i.e. A reentrantly schedules a new named task C into the very slot being serviced.
2. Also schedule benign named task B ("B", priority 1) at the same `when = N`.
3. Run `on_initialize(N)`.
4. Assertions:
   - `System::events()` should contain a `Scheduled` event for C's insertion (proving the nested call succeeded in storage).
   - After block N processing, assert `Lookup::<Test>::get("C")` — either it's `None` (properly cleaned up) or, in the buggy case, it still returns `Some((N, idx))` while `Agenda::<Test>::get(N)` no longer contains that entry (removed by the unconditional `Agenda::<T>::remove(when)`), proving desync.
   - Advance to block N+1 and assert C's `remark_with_event` was **never** dispatched (no matching event), proving the task was permanently lost despite having been validly scheduled.
