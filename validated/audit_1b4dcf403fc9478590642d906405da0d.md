This confirms the vulnerability: the `AuthQuery` used in OAuth includes `shop` inside `to_signable_string` (so `shop` is HMAC-bound there) [1](#0-0) , but `Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain`, `topic`, and `webhook-id` headers from the signature [2](#0-1) . The `shop` used downstream to attribute webhook data is read straight from an unsigned header [3](#0-2) , and `Registry.process` passes that unauthenticated `request.shop` value directly into the handler after only checking the body HMAC [4](#0-3) .

### Title
Webhook `shop` (and topic/webhook-id) Identity Not Bound to HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` only proves that the HMAC matches `verifiable_query.to_signable_string` [5](#0-4) . For webhooks, `to_signable_string` is defined as just `@raw_body` [6](#0-5) , while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to dispatch and attribute the webhook come from HTTP headers that are never part of the signed payload [7](#0-6) .

### Finding Description
The equality the gem is supposed to guarantee is: `shop authenticated by HMAC == shop the handler acts on`. In `Registry.process`, the only check performed is `Utils::HmacValidator.validate(request)`, which recomputes the signature over `request.to_signable_string` (the raw body) and compares it to the `hmac` extracted from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header [8](#0-7) . Once that check passes, `request.shop`, `request.topic`, and `request.webhook_id` — all read from separate, unsigned headers via `shopify_header` [9](#0-8)  — are trusted and forwarded into `WebhookMetadata` for the handler to act on [10](#0-9) .

Because the app's `client_secret`/`api_secret_key` is shared across all shops installed on the app (it is not per-shop), any tenant that has installed the app can obtain a validly-signed webhook body/HMAC pair for their own shop (Shopify sends them real webhooks). That attacker-controlled tenant can then replay the same body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` still returns `true` because it never inspects the `shop` header, so the handler processes attacker-supplied data under the identity of a shop the attacker does not control — a direct break of the shop-authenticated-vs-shop-acted-upon binding.

This is the same bug class as the referenced report (a security check applied inconsistently/incompletely relative to the data actually consumed downstream), mapped onto this gem's own webhook HMAC verification rather than the middleware coverage gap described in the report.

### Impact Explanation
This crosses a tenant boundary: a handler that persists or acts on webhook data keyed by `shop` (e.g., updating per-shop state, uninstalling flags, GDPR redaction handling, order/customer sync) can be made to operate on/inject data for a shop the attacker does not control, using only a webhook the attacker legitimately received for their own shop. This matches the Critical "cross-tenant access" impact category, since no additional secret beyond a webhook the attacker already legitimately possesses for their own tenant is required to spoof another tenant's identity in the handler.

### Likelihood Explanation
Likelihood is realistic for any app that: (1) has multiple shops installed, and (2) exposes a reachable webhook HTTP endpoint (as is standard for embedded/public Shopify apps built on this gem). An attacker who installs the app on a shop they control automatically receives real, validly-signed webhooks from Shopify for that shop, giving them all they need (raw body + HMAC) to forge the header identity for a different, targeted shop.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically tie the header-derived `shop` to the verified payload before it is trusted. Concretely, `Webhooks::Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` (and other identity-bearing headers) into what is verified, or `Registry.process` should independently confirm that `request.shop` corresponds to a shop session/registration that this app instance actually manages before invoking the handler with that shop, rather than trusting the header once only the body-HMAC has been validated.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a genuine webhook from Shopify:
raw_body = '{"id": 1, "note": "hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "attacker.myshopify.com", # attacker swaps this...
  "shopify-webhook-id" => "whatever",
  "shopify-api-version" => "2024-01",
}

# 2. Attacker replays the SAME body/hmac to the app's webhook endpoint,
#    but changes only the shop-domain header to a victim shop they do not control:
headers["shopify-shop-domain"] = "victim-shop.myshopify.com"

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HmacValidator.validate only checks raw_body against the HMAC —
#    it never checks shop-domain — so this succeeds:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler believing this is
#    genuinely "victim-shop.myshopify.com" data:
ShopifyAPI::Webhooks::Registry.process(request)
```
