### Title
Untruncated QR payload can exceed `SERIALIZED_OUTPUT_SIZE`, causing repeated panic/crash-restart of the `qr-code` agent - ([File: src/agents/qr_code.rs])

### Summary
`decode_rxing` copies the full decoded QR text into `Output.payload` with no length check, and this `Output` is serialized into a fixed 4096-byte shared-memory buffer via `port.try_send`. A QR code near maximum capacity (QR version 40 alphanumeric mode allows up to ~4296 characters) produces an archived `Output` that can exceed `SERIALIZED_OUTPUT_SIZE`, causing `serializer.serialize_value(value).expect(...)` in `serialize_message` to panic.

### Finding Description
`Agent::run` in `src/agents/qr_code.rs` receives camera frames, calls `decode_rxing`, and on success does `port.try_send(&chain(output))`: [1](#0-0) 
`decode_rxing` places the raw decoded text directly into `Output.payload` with no length validation or truncation: [2](#0-1) 
`SERIALIZED_OUTPUT_SIZE` for this agent's `SharedPort` implementation is fixed at 4096 bytes: [3](#0-2) 
`try_send`/`send` route into `serialize_message`, which serializes into a `&mut [u8]` slice of exactly that fixed size and calls `.expect(...)` on the result: [4](#0-3) [5](#0-4) 
If the archived `Output` (string payload + corner points + rkyv overhead) does not fit in the buffer, the underlying `BufferSerializer` returns an overflow error and the `.expect("failed to serialize an IPC message")` panics inside the qr-code child process, since a maximal alphanumeric QR payload (~4296 bytes) alone already exceeds the 4096-byte budget with no headroom left for `Points` and rkyv archive metadata.

### Impact Explanation
This causes the `qr-code` agent's dedicated OS process (`agent::process::Process`) to panic and terminate. Per `exit_strategy`, this agent uses `ExitStrategy::Restart`: [6](#0-5) 
On restart, `spawn_process_impl` tears down and fully recreates the shared-memory segment and its semaphores from scratch on every loop iteration (`into_shared_memory` at loop top, `SharedMemory::destroy` during `close`): [7](#0-6) 
Because the shared memory and its semaphores are destroyed and freshly re-initialized (`sem_init` sets `output_tx` back to 1) on every restart, the IPC channel is **not** permanently corrupted or wedged across signups as hypothesized — the restart logic is self-healing by design. The concrete, verifiable impact is a repeated crash/restart loop of the qr-code agent for as long as the oversized QR remains in frame, which is a bounded, self-recovering denial-of-service on QR ingestion rather than persistent cross-signup IPC corruption.

### Likelihood Explanation
Trivial to trigger: an unprivileged attacker only needs to present a QR code encoded near maximum alphanumeric capacity to the RGB camera during the QR-scanning phase of signup. No authentication, privilege, or backend interaction is required, and the condition is fully deterministic and repeatable (the agent's own comment acknowledges "crashes are deterministic for this agent").

### Recommendation
Validate/bound the decoded QR payload length in `decode_rxing` (or immediately after decoding, before constructing `Output`) against a safe margin under `SERIALIZED_OUTPUT_SIZE`, rejecting or truncating payloads that would not fit, and returning a decode error instead of an `Output` that can overflow the shared buffer. Alternatively, make `serialize_message` return a `Result` instead of `.expect()`-panicking, and have `try_send`/`send` propagate a bounded error so oversized payloads are dropped cleanly without process crash.

### Proof of Concept
Integration test plan:
1. Build a synthetic maximal-length alphanumeric string (~4296 bytes, e.g., all `"A"`s) and construct an `Output { payload, points: vec![] }` directly (bypassing actual QR generation/decoding for determinism).
2. Call `RemoteInner::<qr_code::Agent>::try_send` (or the lower-level `serialize_message` with a `SERIALIZED_OUTPUT_SIZE`-sized buffer) with this `Output`.
3. Assert that today this call panics (`serializer.serialize_value(value).expect(...)`) rather than returning a bounded error — demonstrating the fix requirement is to make this a graceful `Result`/reject path.
4. After the fix, assert `try_send` returns `false`/an error cleanly for the oversized payload, and that a subsequent normal-size QR scan in the same (or a fresh) signup session still succeeds via `port.recv()`/`try_send()` round-trip.

fn serialize_message<T>(
    buf: &mut [u8],
    scratch: &mut Option<FallbackScratch<HeapScratch<SCRATCH_SIZE>, AllocScratch>>,
    value: &T,
) where
    T: Archive + for<'a> Serialize<SharedSerializer<'a>> + Debug,
{
    let mut serializer = CompositeSerializer::new(
        BufferSerializer::new(&mut buf[mem::size_of::<usize>()..]),
        scratch.take().unwrap(),
        SharedSerializeMap::new(), // reuse of this map doesn't work
    );
    serializer.serialize_value(value).expect("failed to serialize an IPC message");
    let size = serializer.pos();
    let (_, c, _) = serializer.into_components();
    buf[..mem::size_of::<usize>()].copy_from_slice(&size.to_ne_bytes());
    *scratch = Some(c);
}
