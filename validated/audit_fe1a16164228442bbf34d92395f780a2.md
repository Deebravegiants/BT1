### Title
Cookie-based session id is a predictable, unsigned lookup key, allowing cross-tenant session/access-token theft in non-embedded apps - (File: lib/shopify_api/auth/oauth.rb)

### Summary
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, when the app is non-embedded, the `shopify_app_session` cookie is set to `session.id` in plaintext with no signature or MAC. `Session.id`/`Session.from` derives this id deterministically as `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`. `SessionUtils.cookie_session_id` and `current_session_id` treat whatever value is presented in that cookie as an authenticated lookup key into `SessionStorage` with no verification that the presenter actually completed OAuth for that id. Anyone who can predict or learn a victim's `shop` + `associated_user.id` can forge that cookie and have the app retrieve the victim's stored `Session`, including its real `access_token`.

### Finding Description
Broken binding (before/after):
- Intended: `cookie.value == session.id` should imply "this browser is the one that just completed OAuth token exchange for `session`", i.e. presenting the cookie should be cryptographically equivalent to holding proof of that OAuth completion.
- Actual: `cookie.value` is just the string `session.id`, which is a deterministic, non-secret function of public/guessable inputs: `"offline_#{shop}"` [1](#0-0)  or `"#{shop}_#{associated_user.id}"` [2](#0-1) . `shop` is the merchant's public `*.myshopify.com` domain and `associated_user.id` is Shopify's numeric user id (often low/sequential and sometimes learnable from other public app flows). There is no HMAC/signature over this id before it's placed in the cookie.

Code path:
1. `validate_auth_callback` builds the outgoing cookie: for non-embedded apps, `SessionCookie.new(value: session.id, expires: ...)` [3](#0-2) . This is only reached after `Utils::HmacValidator.validate(auth_query)` and the `state` cookie/query match are checked [4](#0-3) , but those checks only authenticate the *callback from Shopify*, not the value later placed in the cookie's re-presentation.
2. On subsequent requests, `SessionUtils.current_session_id` for non-embedded (or embedded-without-JWT) flows calls `cookie_session_id(cookies)`, which simply returns `cookies[SESSION_COOKIE_NAME]` verbatim, with zero validation [5](#0-4) , and this id string is then used to look up the full `Session` (including `access_token`) from `SessionStorage`.

Attacker request: attacker installs the app on their own dev shop (a valid app install), learns/observes the `Session.from` id derivation logic (this gem is open source), and separately learns or guesses a target merchant's shop domain and (for online sessions) their Shopify user id — both of which are not secrets protected by this gem. The attacker then sends any authenticated-looking request to the host app with `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` (or `<victim-shop>_<user_id>` for online sessions). The host app calls `SessionUtils.current_session_id`/loads the session, retrieves the victim's already-stored `Session` object — including its live `access_token` — and, per the gem's documented usage, activates that session for subsequent Admin API calls made in the request context.

Why existing guards don't stop this: `HmacValidator.validate`, the `state` nonce check, `ShopValidator.sanitize!`, `JwtPayload`'s `aud`/`sub` checks, and `HttpRequest#verify` all protect the *original OAuth callback and JWT id-token* paths, but none of them run on the plain cookie-based lookup path (`cookie_session_id`) — that function is a raw hash read with no cryptographic verification at all [5](#0-4) .

### Impact Explanation
This allows a Critical cross-tenant authentication bypass: the "session id equals cookie value" binding is not tied to proof of OAuth completion, so an attacker can impersonate any tenant whose id they can construct, causing the host app to load and use that tenant's real access token on the attacker's behalf. It is fully repeatable against any victim shop/user for which the attacker can construct the deterministic id string, and the blast radius spans every merchant using a non-embedded install of an app built on this gem, since offline session ids need only the (public) shop domain.

### Likelihood Explanation
Preconditions: the host app must be non-embedded (`Context.embedded?` false) and use the cookie-based session flow from `SessionUtils`/`validate_auth_callback` as documented by the gem — this is a normal, supported configuration, not a misuse. For offline sessions, the only unknown is the victim's shop domain, which is typically public/discoverable (it's the merchant's storefront-adjacent admin domain). For online (per-user) sessions, the attacker additionally needs the associated Shopify user id, which is a smaller, often sequential integer and may leak through other unrelated channels (not needed for offline). Attacker cost is a single HTTP request with a forged cookie header — no secrets, tokens, or privileged access required.

### Recommendation
Never use a raw, predictable session id as the sole cookie value trusted for lookup. Either (a) sign/HMAC the cookie value (e.g., `id + "." + HMAC(secret, id)`) and verify the MAC before trusting it in `cookie_session_id`/`current_session_id`, or (b) issue a separate high-entropy, unguessable session token (unrelated to the deterministic `shop`/`user_id`-derived storage key) that is stored server-side and mapped to the real session id, so that possession of the cookie is the actual proof of the completed OAuth flow rather than a guessable string.

### Proof of Concept
```ruby
# test/utils/session_utils_forged_cookie_test.rb
require "test_helper"

class SessionUtilsForgedCookieTest < Test::Unit::TestCase
  def test_forged_cookie_returns_victim_session_with_access_token
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.example.com",
      scope: "read_products", is_embedded: false, api_version: "unstable",
      is_private: false, session_storage: ShopifyAPI::Auth::FileSessionStorage.new
    )

    victim_shop = "victim-shop.myshopify.com"
    victim_session = ShopifyAPI::Auth::Session.new(
      shop: victim_shop,
      id: "offline_#{victim_shop}",
      access_token: "victim-real-access-token",
    )
    ShopifyAPI::Context.session_storage.store_session(victim_session)

    # Attacker never authenticated; simply predicts the deterministic id and sets it as their cookie.
    forged_cookie_value = "offline_#{victim_shop}"

    looked_up_id = ShopifyAPI::Utils::SessionUtils.current_session_id(
      nil,
      { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value },
      false,
    )

    assert_equal victim_session.id, looked_up_id

    retrieved = ShopifyAPI::Context.session_storage.load_session(looked_up_id)
    assert_equal victim_session.access_token, retrieved.access_token
  end
end
```
Both sides of the intended binding — "cookie value corresponds to a session actually established by this requester" vs. "cookie value == an id string derivable from public shop name" — diverge: the test shows the attacker-controlled cookie (constructed with no credentials) resolves to the victim's stored session and its real `access_token`.
