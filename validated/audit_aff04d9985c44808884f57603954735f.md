Found it — the webhook `shop-domain` header used as the tenant identity is **not** covered by the HMAC that `Utils::HmacValidator` checks, unlike the OAuth `AuthQuery` case where `shop` is explicitly part of `to_signable_string`.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, breaking the binding between authenticated payload and tenant identity - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers without being part of the signed data [2](#0-1) . `Registry.process` validates only the raw body against the HMAC and then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken from those unauthenticated headers [3](#0-2) .

### Finding Description
The intended identity binding is: `HMAC-SHA256(body, client_secret) == received_hmac` AND `shop == shop that produced this payload`. In this gem, the second half of that equality is never enforced — the `shop` (and `topic`/`webhook_id`) values consumed by `WebhookMetadata` come from `x-shopify-shop-domain` (or `shopify-shop-domain`) headers that are not included in `to_signable_string`, so they can be freely set by anyone who can reach the app's webhook endpoint with *any* previously-observed valid `(body, hmac)` pair for their own shop. Since Shopify signs the exact same webhook body/HMAC pair to every shop for identical-content webhook payloads (the signature only proves "this body was signed with our secret," not "this event belongs to shop X"), an attacker who has legitimate access to their own shop's webhook deliveries can replay the raw body + hmac while substituting an arbitrary `x-shopify-shop-domain` header value, causing the host application's handler to process (and typically persist) inbound webhook data under a victim shop's identity, in contrast with `Auth::Oauth::AuthQuery`, which explicitly folds `shop` into `to_signable_string` so it cannot be swapped without invalidating the HMAC [4](#0-3) .

### Impact Explanation
This is a cross-tenant identity confusion: the merchant/tenant binding for webhook events is decided by an attacker-controlled, unauthenticated header rather than by data actually covered by the cryptographic signature. Host applications built on top of this gem's documented `Registry.process` API (see `docs/usage/webhooks.md`) trust `WebhookMetadata#shop` to route stored data, trigger sync jobs, or key access-token lookups per tenant; a forged `shop` value can cause the app to attribute another merchant's data/events to the wrong shop or trigger shop-scoped side effects for a shop the attacker doesn't own.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair, i.e., a real webhook delivery to a shop they control (readily available to any developer/merchant who installs the app once). No access token, `client_secret`, or privileged credential is needed — only the ability to POST to the app's public webhook endpoint with modified headers, which satisfies the "unprivileged internet user" bar.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of `to_signable_string`/the fields Shopify's HMAC actually authenticates, or, more precisely, verify the header-derived `shop` against a shop already known to be associated with this app (e.g., cross-checked with stored session data) before dispatching to handlers — mirroring how `AuthQuery#to_signable_string` binds `shop` into the HMAC-verified payload.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and captures one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `client_secret`).
2. Attacker POSTs to the app's public webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`to_signable_string`) — this passes because `B`/`H` are a genuinely valid pair [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `request.shop` is `"victim.myshopify.com"`, taken unauthenticated from the header [6](#0-5) [7](#0-6) .
5. The host application processes the event as if it belongs to `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
