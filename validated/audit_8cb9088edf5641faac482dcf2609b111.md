### Title

Attacker-controlled swap routes can hide wallet-draining token transfers beneath `swap_collateral` - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

**Severity: High.** `swap_collateral` accepts caller-supplied route bytes and executes them through the configured router while the caller’s authorization remains active. [1](#0-0)  A malicious venue named by the route can invoke an unrelated token’s `transfer` from the caller; Soroban records that transfer as a child of the caller’s `swap_collateral` authorization rather than rejecting it merely because it is unrelated to the swap. [2](#0-1) 

### Finding Description

`Controller::swap_collateral` authenticates `caller`, verifies that the caller controls the account, withdraws the requested collateral to the controller, and passes the caller’s opaque `swap` bytes to `swap_tokens_or_passthrough`. [3](#0-2)  For distinct token addresses, `swap_tokens` authorizes only the controller’s exact input-token transfer to the configured router, then invokes `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3) 

The router decodes the route into an attacker-controlled address registry and executes each hop’s selected pool contract. [5](#0-4)  The swap opcode resolves `hop.pool` directly from the route’s asset registry. [6](#0-5)  No venue-pool allowlist constrains that address; the protocol’s own threat model states that a route can place third-party code below the caller’s authorization and that a token transfer from the caller is accepted if the caller signs the resulting authorization tree. [7](#0-6) 

The repository’s host-level proof shows a malicious hop contract calling `token.transfer(alice, attacker, WALLET_BALANCE)` during a fair `swap_collateral`. [8](#0-7)  Simulation records that unrelated transfer as a child of Alice’s controller authorization, and enforcing mode executes it when Alice signs the poisoned tree. [9](#0-8) 

### Impact Explanation

A crafted route can steal arbitrary tokens from the caller’s wallet, including assets that were never supplied to the lending protocol and are not represented by the route’s input, output, collateral, debt, slippage, or health-factor checks. [7](#0-6)  The proof transfers Alice’s entire unrelated wallet balance while still crediting her position with the expected swap output. [10](#0-9) 

The controller’s measured-output check does not bound the loss because it only verifies that the controller receives more `token_out` than it held before the router call. [11](#0-10) 

### Likelihood Explanation

An unprivileged attacker can deploy a malicious venue contract, construct a valid packed route naming it, and offer a victim a transaction that produces a legitimate swap output. [12](#0-11)  Exploitation requires the victim to sign the authorization tree containing the rogue transfer, so wallets or interfaces that clearly display every child invocation can prevent it. [13](#0-12) 

The likelihood remains material because an incorrect or incomplete signing UI can present this as an ordinary collateral swap even though the poisoned tree authorizes an unrelated wallet transfer. [14](#0-13) 

### Recommendation

Do not allow arbitrary route-selected contract addresses to execute inside a user-authorized lending transaction. Bind accepted venue/pool addresses to protocol-registered, reviewed venues, or architecturally isolate router execution so a nested venue cannot satisfy `caller.require_auth()` through the controller’s root invocation. Client-side validation should additionally decode the route and reject any signed authorization tree containing children beyond the expected controller input flow.

### Proof of Concept

1. Alice owns a debt-free account with 10,000 USDC collateral and holds `WALLET_BALANCE` of an unrelated token. [15](#0-14) 
2. The attacker constructs a route whose hop pool is `RogueHopPool`, configured to call `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` while still allowing a fair USDC-to-ETH output. [16](#0-15) 
3. Alice calls `Controller::swap_collateral(alice, account_id, usdc, 5_000_0000000, eth, malicious_route)`. [17](#0-16) 
4. Simulation produces a controller authorization whose child is the unrelated wallet-token transfer to the attacker. [18](#0-17) 
5. Alice’s unrelated wallet token balance becomes zero and the attacker receives the full balance, while the lending position still receives the fair ETH collateral output. [19](#0-18)

pub(crate) fn process_swap_collateral(
    env: &Env,
    caller: &Address,
    params: SwapCollateralParams<'_>,
) {
    let SwapCollateralParams {
        account_id,
        current,
        from_amount,
        new,
        swap,
    } = params;

    require_authorized_caller(env, caller);

    assert_with_error!(env, current != new, GenericError::AssetsAreTheSame);
    config::require_hub_active(env, current.hub_id);
    require_positive_amount(env, from_amount);

    let mut account = storage::get_account(env, account_id);
    account::require_owner_or_delegate(env, account_id, caller, &account.owner);
    let mut cache = Context::new(env);
    // Check the destination before withdrawing existing collateral.
    require_can_supply(env, &mut cache, account.spoke_id, new);

    let extra_assets = vec![env, current.asset.clone(), new.asset.clone()];
    prefetch_strategy_prices(&mut cache, &account, &extra_assets);

    let swapped_amount = withdraw_and_swap_from_supply(
        env,
        &mut account,
        &mut cache,
        caller,
        current,
        from_amount,
        &new.asset,
        swap,
        events::PositionAction::SwColWd,
    );

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
