## Title
Webhook shop identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with the shop identity attached. In practice, the HMAC signature only covers the raw request body — the `shop-domain` header that the gem hands to the handler as the authoritative tenant identifier is never part of the signed bytes. This breaks the identity binding `verified_bytes == acted_on_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` gates on that same HMAC check, then immediately trusts `request.shop` (parsed from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header) as the tenant identity forwarded to the application's webhook handler: [3](#0-2) 

`Request#shop` is read directly from headers with no cryptographic tie to the HMAC: [4](#0-3) 

The gem's own documentation asserts that `process` "will verify the request did indeed come from Shopify," implying the shop attribution is trustworthy — but the equality that should hold, `hmac_signed_bytes == (body, shop)`, does not; it only holds for `(body)`. Since `api_secret_key` (the HMAC key) is a single per-app secret shared across every shop that installs the app, anyone who controls one installation of the app receives genuine Shopify-signed webhook bodies keyed with that same shared secret. They can then replay that exact `raw_body` + valid `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (the body/signature pair is genuinely valid), and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler.

### Impact Explanation
This is a cross-tenant identity spoofing primitive against any host application that uses `request.shop` (as documented) to select which merchant's session, data or records to update, matching the Critical "cross-tenant access" category: a malicious/compromised merchant on the shared app can forge webhook events attributed to a different, victim merchant, causing the host app to act on stale/fabricated data under the victim's tenant identity (e.g. record deletion via `shop/redact`, `customers/redact` mandatory topics, or data mutation flows keyed by shop).

### Likelihood Explanation
Any developer/merchant who has installed the app is, by definition, an "unprivileged internet user" relative to other tenants of the same app, and automatically receives real signed webhook traffic they can capture and replay — no access token, `client_secret`, or leaked credential is required, only observation of their own inbound webhook traffic and the ability to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cross-check the header-derived shop against an independently trusted source (e.g. the registered/active session for that shop, or Shopify's per-shop signing) before dispatching to the handler. At minimum, update `Utils::VerifiableQuery`/`HmacValidator` usage for webhooks so `to_signable_string` incorporates the shop-domain header, and document clearly that `request.shop` is otherwise unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a genuine webhook to the app's endpoint with body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's single `api_secret_key`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and re-POSTs them to the same endpoint, replacing only `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `H` against `B`.
6. `Registry.process` invokes the host app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data as if it originated from the victim's store.
