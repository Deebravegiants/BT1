Based on my research, I found a plausible but only partially-verified analog in the Intent Gateway's cross-chain deployment registry, plus several other candidate configuration-update paths that I checked and ruled out (`EvmHost.updateHostParams`, `pallet-hyper-fungible-token::update_token`, `pallet-bandwidth`'s manager registration) because they either explicitly guard against stranded balances (`CannotChangeFeeToken` check requiring the old fee token be drained first, `Withdrawal.token` letting governance sweep stale balances) or don't track per-counterparty balances that would duplicate on a swap.

The one path that reproduces the Fenix bug class — a stored counterparty reference being replaced while state created under the old reference is still outstanding — is the Intent Gateway's remote-instance registry.

### Title
Overwriting an IntentGateway remote deployment address permanently freezes escrow for orders already in flight - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
`_addDeployment` unconditionally overwrites `_instances[keccak256(chain)]` for a state machine, and the coprocessor pallet's `add_deployment` extrinsic does the same to `Gateways` and then propagates the new address to every other registered gateway. Incoming `RedeemEscrow`/`RefundEscrow` settlement messages are authenticated by comparing `request.from` against the *current* value of this mapping. A legitimate redeployment (address rotation, upgrade, or correction) therefore invalidates authentication for any settlement message dispatched by the previously-registered gateway before the swap, exactly mirroring the reported bug class: state accrued against an "old" counterparty becomes inaccessible once the counterparty reference is swapped, because the withdrawal/redemption path only recognizes the newly configured address.

### Finding Description
`IntentsBase._addDeployment` stores the trusted counterpart for a remote chain with no check for an existing entry: [1](#0-0) 

On Hyperbridge, `intents-coprocessor::add_deployment` performs the same unconditional overwrite and then re-broadcasts the new address to every other chain's gateway: [2](#0-1) 

Incoming settlement messages are authenticated against this mapping by strict equality (verified pattern, mirrored across the Tron contract variant which shares the same `_instances`/`authenticate` design): [3](#0-2) 

The docs confirm this is exactly the authentication gate used on the settlement path: "The handler authenticates the message (verifying it came from a known IntentGateway instance)." [4](#0-3) 

Escrow itself is tracked per order commitment, independent of which gateway address is currently registered: [5](#0-4) 

**Attack/failure scenario:** A cross-chain order is placed on the source chain and filled by a solver on the destination chain while the destination's registered gateway is address `A`. The fill dispatches a `RedeemEscrow` POST request with `request.from = A`. Before that message is relayed and delivered, governance legitimately redeploys/rotates the destination gateway to address `B` (e.g., to fix a bug or migrate infrastructure) via `add_deployment`, which overwrites the source chain's `_instances` entry for that state machine to `B`. When the pending `RedeemEscrow` message finally arrives, authentication compares `request.from == A` against `_instance(request.source) == B`, fails, and the delivery is rejected (per the host's not-delivered/retry semantics used throughout this contract family). Because `A` will never again equal the current `_instances` value under normal operation, the message can never successfully authenticate — the escrowed input tokens for that order remain locked on the source chain, while the solver has already paid out the output tokens on the destination chain and receives nothing in return.

This is structurally identical to the reported class: a legitimate reconfiguration of "who the trusted counterpart is" orphans balances/obligations that were created against the previous counterpart, because the contract validates strictly against the *current* configuration rather than accounting for state created under the prior one.

### Impact Explanation
Escrowed user funds and solver reimbursement become permanently unreachable for any order whose settlement message was in flight at the moment of a deployment-address rotation. This is a permanent freezing of funds impact, matching the report's severity class, and it also economically harms honest solvers who already delivered outputs on the destination chain but can never redeem the corresponding source-chain escrow.

### Likelihood Explanation
Redeployments/rotations of gateway addresses are an expected, documented governance operation (the analogous `BandwidthManager` docs explicitly describe address rotation via `set_manager`/`add_deployment`-style overwrites as a supported redeployment path), so this is not a hypothetical or malicious-governance scenario — it is a normal maintenance action with an unintended side effect on any order that happens to be mid-flight, which is likely whenever the two chains have non-trivial relay latency.

### Recommendation
Before completing a redeployment, drain/re-authenticate in-flight settlement messages addressed to the old instance — either accept both the previous and current registered address for a configurable grace window, or require governance to first quiesce (block new orders and let outstanding cross-chain settlements complete) before rotating `_instances`/`Gateways`. Alternatively, tie authentication to a per-order-recorded destination gateway snapshot rather than the live `_instances` value, so a later rotation cannot invalidate already-dispatched settlement messages.
