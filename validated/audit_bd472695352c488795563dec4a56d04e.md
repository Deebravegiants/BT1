### Title
Shared, non-seed-scoped `restoreAtom` can be raced to `false` while an added seed's assets are still restoring - ([File: features/application/src/plugins/lifecycle.ts])

### Finding Description
`restoreAtom` is a single global boolean flipped by two independent, uncoordinated triggers of `Hook.AssetsSynced`:

1. `Application#unlock()` fires `Hook.Migrate`/`Hook.Unlock` then calls `void this.#restoreIfNeeded()` **without awaiting it** [1](#0-0) . Inside `#restoreIfNeeded`, after an unrelated `isRestoring()` check, it fires `this.fire(Hook.AssetsSynced).catch(...)` — also fire-and-forget [2](#0-1) .
2. `Application#addSeed()` sequentially awaits `Hook.AddSeed` (sets `restoreAtom=true`), then awaits `Hook.RestoreSeed` (which `restoreAssetsPlugin.onRestoreSeed` uses to block on `restoreProgressTracker.restoreAll(true)` + `waitAllAssetsRestored()` for the new seed's assets), and only then fires `Hook.AssetsSynced` [3](#0-2) .

Both call sites ultimately invoke the same `onAssetsSynced` handler in `applicationLifecyclePlugin`, which unconditionally does `restoreAtom.set(false)` [4](#0-3) . `Application#fire()` has no cross-call mutex — it only serializes listeners *within* a single `fire()` invocation via `executeHooks` [5](#0-4) ; two separate `fire(Hook.AssetsSynced)` calls originating from `unlock()`'s detached `#restoreIfNeeded` and from `addSeed()` can run and resolve in any order.

Attack flow: attacker calls `unlock({passphrase})`, which kicks off `#restoreIfNeeded` in the background and returns. Attacker immediately calls `addSeed({mnemonic})`. `onAddSeed` sets `restoreAtom=true`. While `addSeed`'s own `Hook.RestoreSeed` await is still blocked waiting on `restoreProgressTracker`'s `waitAllAssetsRestored()` for the new seed's assets, the unrelated, concurrently-running `#restoreIfNeeded`'s `Hook.AssetsSynced` fire (triggered by `unlock`) resolves and calls `onAssetsSynced`, flipping `restoreAtom` back to `false` — even though the newly added seed has not finished syncing.

### Impact Explanation
UI/consumers observing `restoreAtom` (exposed via `port.emit('restore', ...)` through the `createAtomObserver` in `lifecycle.ts`) will see `restore=false` and treat the wallet as fully synced/restored while the newly added seed's addresses/balances are still being discovered. This can lead to the UI or dapp-facing address/account selection surfacing an under-restored seed's accounts (e.g., incomplete address gap scanning) as ready, since the shared boolean is the only restore-completion signal consumed downstream, rather than a per-seed indicator.

### Likelihood Explanation
This requires only unprivileged, ordinary RPC access to `unlock` and `addSeed` (both are exposed API surface, no special privilege beyond an already-unlockable wallet) and a specific but realistic interleaving: calling `addSeed` shortly after `unlock` so that `unlock`'s detached `#restoreIfNeeded` `AssetsSynced` fire races the `addSeed`-driven `RestoreSeed`/`AssetsSynced` sequence. Both hook chains are fire-and-forget from the application module's perspective (`void this.#restoreIfNeeded()`, `this.fire(Hook.AssetsSynced).catch(...)`), so no explicit synchronization prevents this ordering; it is timing-dependent but reproducible by forcing `restoreProgressTracker`'s asset-restore completion for the general wallet to occur before the new seed's `waitAllAssetsRestored()` resolves.

### Recommendation
Make `restoreAtom` (or an equivalent restore-completion signal) reference-counted or seed/account-scoped instead of a single shared boolean flipped by any `AssetsSynced` fire. For example, track a set of "pending restore reasons" (e.g., `startup`, `import`, `addSeed:<seedId>`) and only clear the boolean when all pending reasons are cleared, or emit a per-seed restore-completion event and have consumers key off `seedId`. Additionally, avoid firing `Hook.AssetsSynced` from `unlock()`'s detached `#restoreIfNeeded` while an `addSeed`/`RestoreSeed` flow is in-flight, e.g. by serializing/guarding concurrent `fire(Hook.AssetsSynced)` invocations with a single in-flight promise or mutex in `Application`.

### Proof of Concept
Integration test using the IoC application (similar to `sdks/headless/__tests__/restore-complete.integration-test.js`):
1. Start and unlock a wallet, wait for its initial restore to fully complete (`restoreAtom === false`).
2. Stub/delay `restoreProgressTracker.restoreAll`/`waitAllAssetsRestored` for the *new seed* so it doesn't resolve immediately.
3. Concurrently: call `application.unlock({ passphrase })` (do not await completion of its internal `#restoreIfNeeded`), then immediately call `application.addSeed({ mnemonic })`.
4. Assert that after `onAddSeed` fires (`restoreAtom === true`), and before the new seed's `RestoreSeed`/`waitAllAssetsRestored` resolves, `restoreAtom` transiently becomes `false` (driven by `unlock`'s independent `AssetsSynced` fire) — demonstrating the invariant violation: "restore state must accurately reflect per-account/per-seed sync completeness" is broken by a racy global boolean.
5. Expected (fixed) behavior: `restoreAtom` must remain `true` until the new seed's own `RestoreSeed` hook (asset sync) resolves, regardless of unrelated `AssetsSynced` fires from `unlock`.

  private executeHooks = async (hooksFns: HookFn[], concurrent = false) => {
    if (concurrent) {
      return Promise.allSettled(hooksFns.map((fn) => fn()))
    }

    for (const hook of hooksFns) {
      await hook()
    }
  }

  fire = async (
    hookName: ValueOf<typeof Hook>,
    params?: unknown[] | unknown,
    { concurrent }: { concurrent?: boolean } = {}
  ) => {
    assert(HOOKS.has(hookName), `no such hook: ${hookName}`)

    this.#logger.debug(`firing hooks ${concurrent ? 'concurrently' : 'sequentially'}`, hookName)

    const hooks = this.#hooks[hookName] || []

    if (this.#hookNeedsSorting[hookName]) {
      hooks.sort((a, b) => (b.priority || 0) - (a.priority || 0))
      this.#hookNeedsSorting[hookName] = false
    }

    const hookFns = hooks.map((hook) => async () => {
      try {
        await hook(params)
      } catch (err) {
        this.#logger.error(`application lifecycle hook failed: ${hookName}`, hook.name, params, err)
        throw err
      }
    })

    await this.executeHooks(hookFns, concurrent)
    this.emit(hookName, params)
  }
