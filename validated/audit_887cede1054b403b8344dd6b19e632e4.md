The strongest analog to the Slack webhook URL leak (GHSA-4mjx-2gh5-ph8h) is a direct plaintext logging of API credentials in the TRON relayer transport used by tesseract's messaging pipeline.

### Title
Plaintext CatFee API key/secret exposure via `{:#?}` Debug logging - (File: tesseract/messaging/tron/src/catfee.rs, tesseract/messaging/tron/src/lib.rs)

### Summary
`CatFeeConfig` derives `Debug` and stores `api_key`/`api_secret` as plain `String` fields with no redaction wrapper. [1](#0-0) 
`TronClient::new` logs this struct verbatim at `info` level using the pretty-debug formatter whenever CatFee integration is enabled, printing the raw credentials to whatever sink consumes the relayer's logs. [2](#0-1) 

### Finding Description
CatFee is used by the TRON transport to purchase on-chain energy before broadcasting relayed ISMP messages (per the module doc comment describing the HMAC-authenticated `CF-ACCESS-KEY`/`CF-ACCESS-SIGN` scheme). [3](#0-2) 
`CatFeeConfig` is constructed directly from the relayer's TOML/env configuration (`config.catfee_api_key`, `config.catfee_api_secret`) inside `TronClient::new`, and the resulting struct — including both secret fields — is passed straight into `log::info!("CatFee integration enabled: {:#?}", catfee_config)`. [2](#0-1) 
Because `CatFeeConfig` derives `#[derive(Debug, Clone)]` with no custom `Debug` impl or masking (unlike, e.g., the `maskSecret`/`maskUrlKey` redaction pattern used elsewhere in the SDK's filler config), the `{:#?}` format specifier serializes `api_key` and `api_secret` in cleartext directly into the log stream at the routine `info` level (not even gated behind `debug`/`trace`), guaranteeing the credentials are captured by any default log aggregation, monitoring, or crash-reporting pipeline that ingests relayer logs.

### Impact Explanation
An attacker who can read the relayer's stdout/log storage (log aggregators, crash dumps, support bundles, misconfigured log retention) obtains the CatFee `api_key`/`api_secret` pair. With that HMAC secret they can forge valid `CF-ACCESS-SIGN` signatures and act as the relayer operator against the CatFee API: draining the operator's CatFee balance (theft of funds) or exhausting/blocking energy purchases needed to submit TRON transactions, which stalls the relayer's ability to deliver ISMP messages on the TRON route (denial of message delivery). This matches the "route unable to deliver messages" / concrete theft impact categories.

### Likelihood Explanation
Likelihood is high: the log line fires unconditionally at `info` level on every relayer startup whenever CatFee is configured — no special trigger, debug flag, or attacker action is required beyond normal log collection, which is standard operational practice for relayer infrastructure.

### Recommendation
Remove `api_key`/`api_secret` from the `Debug` output of `CatFeeConfig` (implement a manual `Debug` that redacts these fields, or wrap them in a secret-masking type similar to `maskSecret` used in `sdk/packages/simplex/src/cli/init/prompt-utils.ts`), and change the startup log line in `tesseract/messaging/tron/src/lib.rs` to log only non-sensitive fields (e.g., `api_base`, `timeout`) or a boolean "CatFee enabled" flag instead of the full config struct.

### Proof of Concept
1. Configure a TRON chain with `catfee_api_key` and `catfee_api_secret` set.
2. Start the relayer; `TronClient::new` runs and executes `log::info!(target: LOG_TARGET, "CatFee integration enabled: {:#?}", catfee_config);`.
3. Inspect stdout/log storage: the emitted record contains `api_key: "<real-key>"` and `api_secret: "<real-secret>"` in cleartext.
4. Use the recovered key/secret to compute valid `CF-ACCESS-SIGN` HMAC signatures and call the CatFee API as the victim operator.
