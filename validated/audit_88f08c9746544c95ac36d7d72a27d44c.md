### Title
Webhook `shop` identity is trusted for tenant routing but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header, while the HMAC that authenticates the webhook only signs the raw body. `ShopifyAPI::Webhooks::Registry.process` accepts the request as soon as `Utils::HmacValidator.validate(request)` succeeds and then forwards `request.shop` to the app's handler as trusted tenant data, without that field ever participating in the HMAC computation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on that HMAC check alone, then immediately builds `WebhookMetadata` using the *unauthenticated* `request.shop` value and dispatches it to the host app's handler as the tenant identity: [4](#0-3) [5](#0-4) 

The identity binding the gem implicitly promises to the host application is: `shop attributed to this webhook == shop bound by the verified HMAC`. In fact the equality that holds is only `raw_body bytes verified == raw_body bytes parsed`; the `shop` header is disjoint from what is cryptographically checked. Any request whose body/HMAC pair is valid for the app's `client_secret`/`api_secret_key` — regardless of which shop header accompanies it — will pass `Utils::HmacValidator.validate` and have its `shop` value delivered to the handler as authoritative.

Because a single `api_secret_key` is shared across all shops installed on a given app, an attacker who is a legitimate merchant on the app (or can otherwise obtain one valid `(raw_body, hmac)` pair, e.g. via their own shop's webhook deliveries or via a proxy/CDN that allows header rewriting) can replay that exact body/HMAC pair while substituting the `shopify-shop-domain` header for a different, victim tenant's shop domain. The gem will validate the HMAC successfully (it never looked at the header) and hand the host application a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: an authenticated-looking webhook can be attributed to an arbitrary shop chosen by the attacker. Any host application that uses `data.shop` from `WebhookHandler#handle` to look up per-tenant records, write data, or make trust decisions (which is the gem's documented intended use of this field) can be made to act on another tenant's behalf — a cross-tenant access vulnerability rooted entirely in this gem's verification logic, not in host misuse.

### Likelihood Explanation
Exploitation requires only unprivileged, internet-reachable capability: knowledge of one valid `(raw_body, hmac)` pair for the app (trivially obtainable by any merchant who installs the app and receives a real webhook, or by an on-path party able to modify headers before they reach the app's webhook endpoint) and the ability to replay/re-issue the HTTP request with a modified `shop` header to the app's public webhook URL. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` identity into the authenticated material, or otherwise cryptographically tie the shop header to the signed payload before trusting it: e.g., include the shop domain in `to_signable_string`, or verify the shop against a value obtained from a trusted, HMAC-covered source (or a shop already known/whitelisted for this specific `webhook_id`/subscription) rather than an arbitrary unauthenticated header before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook delivery, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` value computed by Shopify with the app's shared `api_secret_key`.
2. Attacker (or an intermediary capable of rewriting headers en route to the app's public webhook endpoint) resends the identical `raw_body`/`hmac` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `raw_body` [6](#0-5)  and finds it matches — the shop header was never checked.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled data as if it originated from the victim shop.
