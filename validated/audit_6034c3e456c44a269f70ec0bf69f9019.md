Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . The registry only validates the HMAC over that signable string before dispatching the handler with the header-derived `shop` [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values used by the handler are taken from HTTP headers that are never included in the signed payload [5](#0-4) . This breaks the intended binding `shop-domain header == shop that produced/authorized the signed body`.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field [6](#0-5) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) ; none of `shop`, `topic`, `webhook_id`, or `api_version` participate in the signature, since they are read straight out of `@headers` via `shopify_header` [7](#0-6) [8](#0-7) .

`Registry.process` raises only if the HMAC fails, then dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . Consequently a request with an unmodified, validly-signed `raw_body` but an attacker-substituted `x-shopify-shop-domain` header will still pass HMAC validation, and `data.shop` handed to the app-supplied `WebhookHandler` will be whatever domain the attacker chose — not the shop that actually owns the signed payload.

### Impact Explanation
Any entity that can obtain one valid `(raw_body, hmac)` pair for a topic — e.g. a merchant with the app installed on their own store, replaying their own legitimate webhook, or anyone who can view a Shopify webhook payload for a public/low-sensitivity topic — can re-POST that exact body/HMAC to the app's webhook endpoint while swapping the `shop-domain` header to an arbitrary victim shop domain. Because host applications identify which tenant/session a webhook belongs to via `data.shop` (per this gem's own documented handler contract) [9](#0-8) , this lets an attacker impersonate webhook traffic "from" a shop they do not own, causing cross-tenant confusion in any app logic keyed off `data.shop` (e.g. writing attacker-controlled body content into another tenant's records, forging `shop/redact` or `customers/redact` compliance events for a shop the attacker doesn't operate, or triggering per-shop side effects). This is a cross-tenant identity-binding break reachable purely from the gem's own webhook-processing API.

### Likelihood Explanation
The attacker only needs access to any single valid signed webhook body for the target app (trivial if they run the app on their own store — every legitimate webhook delivered to them is a valid `(raw_body, hmac)` pair) and the ability to POST to the app's public webhook callback URL. No secret, token, or privileged access is required; only the header is modified, and headers are explicitly excluded from what `to_signable_string` returns.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) header values, or at minimum the shop domain, as part of the HMAC-signed material check, or independently verify that the header's shop domain corresponds to a shop with a currently registered webhook/session before trusting `request.shop` in `WebhookMetadata`. Shopify's actual webhook signature only covers the body by design, so the gem should not expose `request.shop`/`request.topic` to handlers as "trusted" fields without documenting that callers must independently authenticate them (e.g., by cross-checking `shop` against an active app installation/session rather than trusting the header verbatim).

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value Shopify sent for it.
2. Attacker POSTs to the app's webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [4](#0-3) .
4. The registered handler is invoked with `data.shop == "victim-shop.myshopify.com"` and `data.body` equal to the attacker's own webhook payload, even though `victim-shop` never sent this event [10](#0-9) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
