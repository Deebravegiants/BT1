### Title
Webhook shop/topic/id attribution is unauthenticated header data outside the HMAC-signed bytes, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds an incoming webhook's identity (`shop`, `topic`, `webhook_id`, `api_version`) to raw, unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the request body bytes. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every merchant install, any party who legitimately receives one valid webhook (e.g., by installing the app on their own store) can replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header. Verification still passes, and the forged shop identity is what the host application receives and acts on.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature only over `verifiable_query.to_signable_string` and compares it to the supplied HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the fields used to attribute the webhook to a specific merchant/tenant and to route it to a handler — are read straight from HTTP headers that are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts these header-derived values unconditionally to build the metadata passed to the app's handler: [4](#0-3) 

This is exactly the "bytes verified versus bytes parsed" identity-binding break called out in the rules: the equality the code implicitly assumes is `hmac_signed_bytes == identity_bytes`, but in reality `hmac_signed_bytes (raw_body) != identity_bytes (shop-domain/topic/webhook-id headers)`. Because `Context.api_secret_key` is one shared secret for the whole app (not per-shop), any store that has installed the app can obtain a validly-HMAC-signed `raw_body` from a real Shopify webhook delivery, then replay that same body+HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` still returns true because it never inspects the header.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged actor who merely installs the app on their own store (no special privilege, no leaked credentials, no `api_secret_key` needed) can cause the host application to process attacker-controlled webhook payloads under another shop's identity. Downstream handlers built on `WebhookMetadata#shop`/`#topic` (e.g., GDPR `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific data-sync handlers) will act as if the data belongs to the victim shop, leading to cross-tenant data confusion/injection — data written, deleted, or acted upon under the wrong tenant's record. This matches the "Critical — cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must first obtain at least one genuinely signed webhook body (trivial — install a free/dev app instance on their own store, or use any topic they can trigger, e.g. `app/uninstalled`), then send a forged HTTP request directly to the app's public webhook endpoint with a swapped shop header, keeping body and HMAC unchanged. No secrets, tokens, or elevated access are required — only network access to the merchant app's public webhook URL, which is unprivileged-internet-user reachable by design.

### Recommendation
Bind the identity fields into the signed payload the gem verifies, not just the raw body:
- Compute/verify the HMAC over a canonical string that includes `shop`, `topic`, and `webhook_id` in addition to `raw_body` (this requires coordinated support from Shopify's webhook signing on the server side, so at minimum the gem should not present these header values as unauthenticated-but-trusted attributes without documenting the trust boundary).
- At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values and that host applications MUST cross-check `request.shop` against an actively-registered/installed shop for that specific topic/webhook subscription (e.g., verify the `shop` exists in the app's own session store and that a subscription for that `webhook_id`/topic was actually registered for that shop) before trusting `WebhookMetadata`.
- Consider adding an optional strict mode that rejects processing unless the resolved shop has an active session/installation record known to the app.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `app/uninstalled`) to receive a legitimately Shopify-signed POST containing `raw_body` and header `X-Shopify-Hmac-Sha256`.
2. Capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` value from that request.
3. Craft a new HTTP POST to the app's public webhook endpoint reusing the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds: [5](#0-4) 
5. `request.shop` returns `"victim-shop.myshopify.com"` (attacker-controlled header) and is forwarded to the handler via `WebhookMetadata`, causing the app to process attacker-supplied webhook data under the victim shop's identity: [6](#0-5)
