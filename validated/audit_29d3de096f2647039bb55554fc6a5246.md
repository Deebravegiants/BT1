### Title
Truncating division in ERC20→local balance conversion can mint 0 tokens for a legitimately-bridged deposit - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `convert_to_balance` scales an incoming ERC20 `U256` amount down to the pallet's local balance precision by integer division: `value / 10^(erc_decimals - local_decimals)`. When the EVM-side token has more decimals than the local asset (which is the normal, expected configuration — `register_token`/`update_token` explicitly *require* `config.decimals >= local_decimals`, see `ErcDecimalsBelowLocal`), any incoming amount smaller than the scale factor truncates to zero. This mirrors the reported bug class exactly: `optionShare = (optionTokenBalance * 1e18) / totalOptionTokenSupply` rounding to 0 and silently destroying legitimate value.

### Finding Description
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs`: [1](#0-0) 

This is invoked from the ISMP `on_accept` handler (per the pallet README) when an inbound `Send` message arrives from the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract — i.e. reachable by anyone who calls the EVM contract's send function and gets a relayer to deliver the resulting cross-chain message: [2](#0-1) 

The scale factor is `10^(erc_decimals - local_decimals)`, enforced to be non-negative at registration time: [3](#0-2) 

For example, `BridgeToken` on EVM uses 18 decimals while the native `BRIDGE` asset on nexus is 12 decimals, giving a scale factor of `10^6`: [4](#0-3) 

Any inbound ERC20 amount below `10^6` wei of BRIDGE (a perfectly valid, dust-but-nonzero, EVM-side transfer that the EVM contract escrows/burns without any minimum-amount check) truncates to `0` when converted back to the local (nexus) balance. There is no post-conversion check that rejects or reverts a zero-resulting mint; the pallet proceeds to credit the beneficiary with `0` while the sender's tokens on the EVM side have already been irrecoverably burned/escrowed.

### Impact Explanation
This is a permanent, unrecoverable loss of user funds on the sending side with the receiving side crediting nothing — the same failure mode as the reported analog (a legitimate participant's on-chain balance rounds to zero and they receive nothing back for value they gave up). Because `register_token`/`update_token` *require* `erc_decimals >= local_decimals` (the pallet cannot be configured any other way), every cross-chain pair configured through this pallet is exposed to this truncation whenever `erc_decimals > local_decimals` and the bridged amount is smaller than the resulting scale factor — this is not a theoretical edge case reserved for "10,000,000,000 supply" scenarios as in the client's rebuttal to the original report; it triggers for ordinary small transfers (e.g., anything under 0.000001 BRIDGE for the 18↔12 decimal BridgeToken pairing).

### Likelihood Explanation
High. No minimum-amount validation exists in the EVM `HyperFungibleToken`/`BridgeToken` send path or in the pallet's `on_accept`/`convert_to_balance` path to prevent dust amounts from being bridged, and any user (not a privileged actor) can trigger this simply by sending a small amount cross-chain from the EVM side.

### Recommendation
- In `convert_to_balance`, reject (return an error) rather than silently producing `0` when `value` is non-zero but the scaled result is `0`.
- Alternatively, enforce a minimum bridgeable amount on the EVM `send`/`HyperFungibleToken` path (and/or in the pallet's `on_accept`) equal to at least the scale factor `10^(erc_decimals - local_decimals)`, so no dust amount can be escrowed/burned on one side while minting `0` on the other.
- Add symmetry checks/tests asserting `convert_to_balance(convert_to_erc20(x, ...), ...) == x` fails gracefully (with an explicit error) rather than losing value whenever `x` is below the precision floor.

### Proof of Concept
1. `register_token` configures asset `BRIDGE` (local, 12 decimals) with an EVM chain contract at 18 decimals (scale factor `10^6`), as is done for `BridgeToken.sol`.
2. A user calls the EVM `BridgeToken`/`HyperFungibleToken` contract's send function with `amount = 500_000` wei (i.e., `0.0000005` BRIDGE, an 18-decimals value less than `10^6`). The EVM contract burns/escrows this amount — there is no minimum-amount check in `BridgeToken`'s `send`/`onAccept` flow (per `evm/src/apps/BridgeToken.sol`).
3. The ISMP message is relayed to nexus; `pallet-hyper-fungible-token`'s `on_accept` calls `convert_to_balance(U256::from(500_000), 18, 12)`.
4. `500_000 / 10^6 == 0` (integer division), so `dec_str = "0"`, and the beneficiary is minted/credited `0` local tokens via `TokenReceived { beneficiary, amount: 0, source }`, while the sender's EVM-side tokens are already gone.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
