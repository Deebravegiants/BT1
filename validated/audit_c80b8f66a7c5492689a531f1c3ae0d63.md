### Title
Webhook Shop/Topic/Metadata Spoofing via Header Fields Excluded from HMAC Signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw, unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator.validate` checks only covers the raw request body. This breaks the intended binding "the shop authenticated == the shop the handler acts on," allowing a caller who possesses one valid `(raw_body, hmac)` pair to replay it with an arbitrary `shopify-shop-domain` header and have the webhook processed as if it originated from a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from the HTTP headers, which are not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts these header-derived fields to build the handler's metadata: [3](#0-2) 

`HmacValidator.validate` only proves that `verifiable_query.to_signable_string` (i.e., the raw body bytes) was signed with the app's `client_secret`; it says nothing about the header values: [4](#0-3) 

Equality that should hold but doesn't: `shop_used_by_handler == shop_that_the_HMAC_actually_authenticates`. Because `shop` (and `topic`/`webhook_id`) live outside `to_signable_string`, any request whose `raw_body` byte-for-byte matches a previously-observed valid `(raw_body, hmac)` pair — e.g., one the attacker received as a legitimate webhook for their own shop — will pass HMAC validation regardless of which `shopify-shop-domain` header value is sent. The verified bytes (body) and the parsed/trusted bytes (headers) diverge.

### Impact Explanation
An attacker who operates their own Shopify store (an unprivileged, unrelated tenant of the same app) receives genuine webhooks for their own shop, each with a valid HMAC computed over the body only. They can resend that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a victim shop's domain or a different topic/webhook id. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: <victim shop>, topic: <attacker-chosen topic>, ...)`. Any host application that keys tenant-scoped side effects (e.g., de-provisioning, data deletion for `shop/redact`/`customers/redact`, updating per-shop records) off `request.shop`/`request.topic` will perform those actions against the wrong tenant, i.e., cross-tenant access/impersonation using forged identity fields that were never protected by the signature.

### Likelihood Explanation
Any merchant/attacker who has installed the app on their own store can trivially collect valid `(body, hmac)` pairs from webhooks Shopify sends them, since nothing prevents reusing that pair with attacker-chosen headers when calling the app's public webhook endpoint directly (bypassing Shopify's real delivery). No access token, `client_secret`, or privileged access is required — only a legitimate, low-privilege installation of the app, which is the normal onboarding path for any merchant.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind them to the body (e.g., verify `shop`/`topic` against values embedded in the signed body/payload sent by Shopify) so that the HMAC check authenticates the same fields the handler subsequently trusts.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B`), header `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`.
2. Attacker sends a POST directly to the app's webhook endpoint with the same body `B` and same `H`, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`B`) — it succeeds since `B`/`H` is a valid pair: [5](#0-4) 
4. The handler is invoked with `shop: "victim.myshopify.com"` even though the HMAC never authenticated that value, demonstrating the identity-binding break.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
