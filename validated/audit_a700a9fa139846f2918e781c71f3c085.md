### Title
`updateWalletAccount` allows changing `compatibilityMode` on an existing wallet account with no re-derivation safeguard, silently orphaning previously-derived funds - (File: features/wallet-accounts/src/module/wallet-accounts.ts)

### Summary
`WalletAccounts.update`/`updateMany` builds the new account by merging arbitrary caller-supplied fields over the existing record and only guards a small allow-list of fields (`source`, `id`, `index`, and `seedId` once set). `compatibilityMode` is not protected, even though it directly determines the derivation path (and therefore which keys/addresses/funds belong to that wallet account).

### Finding Description
`updateWalletAccount` in `features/wallet-accounts/src/module/wallet-accounts.ts` merges `newData` into the existing `WalletAccount` and only asserts invariants on `source`, `id`, `index`, and (separately) `seedId`: [1](#0-0) 

Nothing prevents `compatibilityMode` from being changed on an account that already has activity/funds. `compatibilityMode` is not cosmetic metadata — it feeds directly into key/address derivation throughout the stack. `getSupportedPurposes`/`getDefaultPurpose` pick the BIP purpose (44/49/84/86) based on `compatibilityMode`: [2](#0-1) 

And `AddressProvider`/`PublicKeyProvider`/the tx signer all pass `walletAccount.compatibilityMode` straight into `baseAsset.api.getKeyIdentifier(...)` to compute the derivation path used to fetch keys, sign transactions, and compute receive/change addresses: [3](#0-2) [4](#0-3) [5](#0-4) 

The wallet's own test fixtures demonstrate how drastically `compatibilityMode` changes the derived path and resulting address for the *same* wallet account/index (e.g. `exodus` mode derives `bitcoin` receive address at `m/0/0` purpose 84, while `ordinals84` mode derives from `m/0` and produces a completely different address for the same account): [6](#0-5) [7](#0-6) 

Same pattern for EVM `metamask` compatibility mode vs. default derivation (different derivation path formula entirely, bumping `addressIndex` vs `accountIndex`): [8](#0-7) 

This value is exposed through the public `walletAccountsApi.update` surface with no exposure/impact analysis for outstanding balances at the old derivation path: [9](#0-8) 

The design explicitly treats `seedId` as needing a one-way lock ("`seedId` can only be set if previously undefined") because changing it would change the effective keys — but the same reasoning was never applied to `compatibilityMode`, which has the identical effect on derivation.

### Impact Explanation
This is the direct analog of the reported class: a mutable “which source of truth to use” parameter (there: `alchemist` address; here: `compatibilityMode`) can be switched on a live account holding funds without any check that the old derivation path has zero exposure. After the switch, `AddressProvider.getReceiveAddress`/`getChangeAddress`, `PublicKeyProvider`, and the transaction signer will all compute a *different* derivation path/keys/addresses for the same named wallet account, so funds that were sent to (or held at) the previously-derived addresses become unreachable through the normal wallet flows tied to that account — the wallet no longer look for balances/UTXOs at the old path, and the signer will no longer produce the old key for that account's default paths. Recovery requires the user to manually know to revert `compatibilityMode` back, exactly the “tedious and error-prone manual recovery” scenario called out in the original report. Given `compatibilityMode` differences also change the BIP purpose (44/49/84/86) used for signing, an incorrect or careless switch could also mean subsequent transactions are signed and broadcast using an entirely different key than what a user or integrator expects for a given account name.

### Likelihood Explanation
`update`/`updateMany` are reachable through the public `walletAccountsApi.update` (part of the SDK/headless API surface), and nothing in `updateWalletAccount` blocks `compatibilityMode` changes on non-default, already-used accounts. Any caller with access to the wallet-accounts API (SDK integrator, or a compromised/careless UI flow) can trigger this by passing `compatibilityMode` in an update call with no confirmation, checks on existing balances/history, or migration path. This mirrors the "admin-only, but no exposure check" pattern from the reference finding — it's not restricted to a hostile third party, but the lack of guardrails makes an operational mistake (or a bug in any caller that passes compatibilityMode) directly fund-affecting.

### Recommendation
Apply the same category of guard that already exists for `seedId` and the immutable fields (`source`, `id`, `index`) to `compatibilityMode`:
- Disallow changing `compatibilityMode` once it has been set/derived from for a wallet account (mirror the `seedId` "can only be set if previously undefined" assertion), or
- Require an explicit, guarded migration path (e.g. verify zero balance/tx history at the old derivation paths, similar to the recommended `getTotalCredit()==0`/`getTotalUnderlyingBuffered()==0` checks in the original report) before allowing `compatibilityMode` to change on a wallet account that has already been used.

### Proof of Concept
1. Create/enable a wallet account (e.g. default `exodus_0`) with `compatibilityMode` unset (default exodus derivation) and receive funds at its bitcoin receive address, e.g. `bc1qcgclnu4m5lv5k8eg2hytysvnlkjlhmyuyhtrna` (path `m/0/0`, purpose 84) as shown in the "exodus mode" fixture.
2. Call `walletAccounts.update('exodus_0', { compatibilityMode: 'ordinals84' })`. `updateWalletAccount` (features/wallet-accounts/src/module/wallet-accounts.ts:45-77) only checks `source`/`id`/`index`/`seedId`; `compatibilityMode` passes through unchecked.
3. Subsequent calls to `addressProvider.getReceiveAddress`/`getChangeAddress` for the same wallet account now derive from `m/0` under purpose 84 producing a different address (`bc1q025ae0e9cl5yc0aw94l8tnvh8tpehr44a4hmtq` per the "ordinals84 mode" fixture), and the tx-signer/public-key-provider compute keys from the new path — the wallet's UI/balance calculation for this account will no longer surface or be able to spend funds sitting at the old `m/0/0` address without the user manually reverting `compatibilityMode`.

const updateWalletAccount = (
  walletAccounts: Record<string, WalletAccount> = Object.create(null),
  walletAccount: string,
  newData: Record<string, unknown>
) => {
  const before = walletAccounts[walletAccount]

  if (!before) throw new Error(`${walletAccount} is not a known wallet account`)

  if (walletAccount === DEFAULT_WALLET_ACCOUNT.toString() && newData.enabled === false) {
    throw new Error("Can't disable default walletAccount")
  }

  const after = new WalletAccount({
    ...before,
    ...newData,
  })

  for (const key of ['source', 'id', 'index']) {
    assert(
      (before as unknown as Record<string, unknown>)[key] ===
        (after as unknown as Record<string, unknown>)[key],
      `cannot change account ${key}`
    )
  }

  assert(
    !before.seedId || before.seedId === after.seedId,
    'seedId can only be set if previously undefined'
  )

  return after
}
