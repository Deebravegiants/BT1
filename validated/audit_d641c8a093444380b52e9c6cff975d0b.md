### Title
`shop`/`topic`/`webhook_id`/`api_version` headers are trusted unauthenticated by `Registry.process` and `WebhookMetadata` while only `raw_body` is HMAC-covered - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` only proves that the *body* was signed by the app's client secret [2](#0-1) . `Registry.process` nonetheless dispatches on `request.topic` and forwards `request.shop` into `WebhookMetadata` as if they were authenticated, even though both come straight from unsigned HTTP headers [3](#0-2) . Because the same `client_secret` is shared across every shop that installs the app, an attacker who legitimately receives one signed webhook body (e.g. on their own development shop) can replay that exact body+HMAC to the app's public webhook endpoint while substituting `x-shopify-shop-domain` and/or `shopify-topic`/`x-shopify-topic` for arbitrary values, and the handler will accept it as coming from an arbitrary shop/topic.

### Finding Description
The binding the code implicitly assumes is:
`HmacValidator.validate(request) == true` ⇒ `(request.topic, request.shop, request.webhook_id, request.api_version, request.parsed_body)` are all authentic.

Tracing the code shows this is false. `to_signable_string` is defined as simply `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` header [2](#0-1) . None of `topic`, `shop`, `webhook_id`, or `api_version` — all read via `shopify_header(name)` from the raw, unauthenticated `@headers` hash [4](#0-3) [5](#0-4)  — are included in the signed string.

`Registry.process` performs exactly one authentication check (`HmacValidator.validate(request)`), then immediately uses the unauthenticated `request.topic` to select `@registry[request.topic]&.handler` and to build `WebhookMetadata`, and uses the unauthenticated `request.shop` as the `shop` field of that metadata [3](#0-2) . Any downstream handler that trusts `data.shop` as "the shop this webhook came from" (a normal, encouraged usage per the `WebhookHandler#handle(data:)` interface [6](#0-5) ) is trusting a value that carries zero cryptographic guarantee.

Exploit flow:
1. Attacker creates their own development shop, installs the target app, and lets the app deliver them one legitimately-signed webhook — capturing `raw_body` and the matching `hmac-sha256` header. (The app's `client_secret`/`api_secret_key` is identical for every install, per `Context.api_secret_key` used in `HmacValidator.validate` [7](#0-6) .)
2. Attacker POSTs the same `raw_body` + `hmac-sha256` to the app's public webhook endpoint again, but this time sets `x-shopify-shop-domain` to a victim merchant's domain and/or `shopify-topic`/`x-shopify-topic` to a different registered topic.
3. `HmacValidator.validate` still returns `true` — the body/HMAC pair is unchanged and valid.
4. `Registry.process` dispatches to the handler for the attacker-chosen topic and hands it `WebhookMetadata` claiming the victim's shop domain, even though the actual signed payload has nothing to do with that shop or topic.

The header-normalization detail cited in the question (`sub("http_", "")` in `initialize` [8](#0-7) ) does not add an additional collision beyond this: `shopify_header` already OR's `"shopify-#{name}"` over `"x-shopify-#{name}"` [5](#0-4) , so whichever variant an attacker supplies, both are equally unauthenticated — the real break is the absence of header coverage in `to_signable_string`, not a specific key-collision.

None of the existing guards close this gap: `HmacValidator.validate` only checks the body [7](#0-6) ; there is no `ShopValidator.sanitize!` call anywhere in `Registry.process`; there is no per-topic or per-shop authorization step before `handler.handle` is invoked [3](#0-2) ; Sorbet typing only enforces that `topic`/`shop` are `String`, not that they are authentic.

### Impact Explanation
This is an "unauthenticated value being trusted as authenticated" and enables cross-tenant confusion: the `shop` field delivered to every app's webhook handler — commonly used to look up which merchant's session/data the event applies to — is controllable by any attacker who has captured one valid signed body from any installation (including their own throwaway dev shop). The `topic` used to select the handler is likewise unauthenticated, so a signed body captured under topic A can be redelivered and processed as topic B, causing type/schema confusion in the handler (e.g., a `customers/data_request` or `shop/redact` handler could be invoked with a body shaped for an unrelated topic). This is repeatable indefinitely against arbitrary victim shop domains, since the attacker only needs one valid signed body once. It falls short of full "forge a request from nothing" (a real HMAC over some real body is still required), but for handlers that key authorization or scoping decisions on `WebhookMetadata#shop`/`#topic`, this is a genuine cross-tenant/authentication-bypass class issue.

### Likelihood Explanation
Preconditions: the app must expose its webhook endpoint publicly (standard for Shopify webhook delivery, no additional auth beyond HMAC) and must instantiate `Webhooks::Request`/call `Registry.process` per Shopify's documented flow — both are default usage of this gem. Attacker cost is low: they only need to install the app once on a self-created development shop to obtain one valid signed body, then can replay it with arbitrary header values at will. No secret material is required. This is fully repeatable against any number of "victim" shop-domain claims from the same captured signature.

### Recommendation
Bind the security-relevant metadata into the signed material, or add an explicit post-HMAC authorization step in `Registry.process`/handler dispatch that does not rely on `request.shop`/`request.topic` alone (e.g., verify that the claimed `shop` actually has an active session/installation before trusting it, and treat `topic` dispatch as advisory only after independently validating webhook_id/shop against Shopify's Admin API or a locally stored registration). At minimum, document loudly (in code, not just docs) that `WebhookMetadata#shop` and `#topic` are unauthenticated and must not be used for authorization decisions without additional verification.

### Proof of Concept
minitest + WebMock/Mocha plan (add to `test/webhooks/request_test.rb` or `registry_test.rb`):
```ruby
def test_topic_and_shop_are_not_covered_by_hmac
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
  raw_body = '{"id":1}'
  hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
  hmac_b64 = Base64.encode64(Digest.hexdecode(hmac))

  request_victim = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "HTTP_X_SHOPIFY_TOPIC" => "orders/create",
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac_b64,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim-shop.myshopify.com",
    },
  )
  request_attacker = ShopifyAPI::Webhooks::Request.new(
    raw_body: raw_body,
    headers: {
      "HTTP_X_SHOPIFY_TOPIC" => "orders/create",
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac_b64,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "attacker-shop.myshopify.com",
    },
  )

  # Equality that should hold if shop were authenticated: it does NOT.
  assert ShopifyAPI::Utils::HmacValidator.validate(request_victim)
  assert ShopifyAPI::Utils::HmacValidator.validate(request_attacker)
  refute_equal request_victim.shop, request_attacker.shop
  assert_equal request_victim.to_signable_string, request_attacker.to_signable_string # same signed content
  # -> handler.handle receives two different `shop` values for one identical signature/body
end
```
This directly demonstrates the fast-validation scenario: one signature, two different `x-shopify-shop-domain` values, both accepted by `HmacValidator.validate`, proving `shop` (and by identical reasoning, `topic`) is outside signature coverage while still being used by `Registry.process`/`WebhookMetadata` as if authenticated.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
