## Title
Webhook shop-domain spoofing via HMAC that only covers the payload body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw HTTP body only, while `shop` is read straight from an unauthenticated header. `Registry.process` accepts the request as long as the body's HMAC is valid and then hands the header-derived `shop` value to the app's webhook handler as the tenant identifier, without any check that this `shop` is the one the signed body actually originated from.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw request body: [2](#0-1) 

`shop` (and `topic`, `api_version`, `webhook_id`) are pulled directly from HTTP headers that are never mixed into the signed string: [3](#0-2) 

`Registry.process` validates only this body HMAC and then dispatches to the handler using the unauthenticated `request.shop`: [4](#0-3) 

Because the app's webhook signing secret (`Context.api_secret_key`) is a single shared secret across *all* merchants that have installed the app, an unprivileged user who runs their own shop with the app installed legitimately receives real webhook deliveries with a valid `(body, hmac)` pair signed by that shared secret. Nothing in this gem binds that pair to the `x-shopify-shop-domain`/`shopify-shop-domain` header. Replaying the same `(body, hmac)` to the app's public webhook endpoint with the header changed to a victim shop's domain passes `HmacValidator.validate` unchanged, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: "<victim-shop>.myshopify.com", ...)`, i.e. attacker-controlled body content is attributed to a victim tenant.

This is exactly the identity-binding failure class from the report: a field acted upon (`shop`) is not covered by the authentication code (HMAC), so the binding `hmac-verified-body == shop the app trusts` does not hold — the equality that should be enforced (`request.shop` bound to the same secret-holder that produced `request.hmac`) is never checked.

### Impact Explanation
This allows an unprivileged attacker (any user who can install the app on their own trial/dev store) to forge webhook events that appear to originate from an arbitrary victim shop domain, feeding attacker-chosen JSON bodies (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, order/product mutations mirrored into the host app's DB) tagged with a victim's shop domain. Any host application that uses `WebhookMetadata#shop` to key session/data lookups (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) will act on forged data as if it came from the victim tenant — a cross-tenant data integrity/confusion issue reachable purely from the public webhook endpoint with no access token or secret required by the attacker.

### Likelihood Explanation
Requires only that the attacker control one shop with the app installed (achievable by any unprivileged internet user via a free/dev store) and knowledge of the app's public webhook endpoint (typically documented/discoverable). No credentials or privileged Shopify access are needed. The replay is a straightforward HTTP POST with a substituted header.

### Recommendation
Bind the header-derived identity to the signed content: include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload check (e.g., verify against Shopify's per-webhook delivery guarantees), or independently verify that the shop domain in the header matches an app-side record (e.g., a known/installed shop or a nonce/timestamp replay-protection keyed by shop) before dispatching to handlers. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`; app's webhook secret is `Context.api_secret_key` (shared across all shops).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this `(B, HMAC)` pair and resends it directly to the app's public webhook endpoint, replacing only `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — unchanged since `to_signable_string` ignores headers — and passes.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, i.e. attacker-controlled data attributed to `victim-shop.myshopify.com`.
