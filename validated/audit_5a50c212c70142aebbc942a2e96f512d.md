Based on my analysis, I've confirmed a valid analog exists in the Hyperbridge codebase, directly matching the reported bug class in `EvmHost.sol`'s low-level calls dispatching to arbitrary application contracts.

### Title
Unbounded return-data copy in `EvmHost.dispatchIncoming`/`dispatchTimeOut` low-level calls enables gas-griefing DoS of message batches - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest,...)`, `dispatchIncoming(GetResponse,...)`, and both `dispatchTimeOut` overloads deliver cross-chain messages to arbitrary, attacker-influenced destination contracts (`request.to`/`request.from`) via unguarded low-level `.call(...)`, forwarding all remaining gas and copying the full return data with no size cap.

### Finding Description
Each dispatch path resolves the destination address from message fields controlled by whatever module registered on a remote chain, then executes:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [1](#0-0) 
and analogously for `onGetResponse`, `onGetTimeout`, and `onPostRequestTimeout`. [2](#0-1) [3](#0-2) [4](#0-3) 

These calls are invoked from `HandlerV2.handlePostRequests`/`handleGetResponses`, which are permissionless — "All handler methods are permissionless - anyone can call them to relay messages" — and which loop over an entire batch of requests/responses in a single relayer-submitted transaction, calling `host.dispatchIncoming(...)` per item inside the loop. [5](#0-4) 

Because Solidity's low-level `.call` (without an explicit gas stipend) forwards essentially all remaining gas and unconditionally copies the entire `returndata` into memory, a malicious/misbehaving destination module (an `IApp` implementation deployed by anyone, since `to`/`from` are arbitrary addresses decoded from cross-chain message bytes) can return a very large payload. The memory-expansion cost of copying that payload grows quadratically and can consume all gas remaining in the outer relayer transaction, causing the entire batch (`handlePostRequests`/`handleGetResponses`, potentially wrapped further in `batchCall`) to revert with out-of-gas — this is exactly the "Excessively Safe Call" pattern flaw the external report describes for `forwardCall`.

### Impact Explanation
Because `handlePostRequests`/`handleGetResponses`/`dispatchTimeOut` process an entire batch of otherwise-legitimate messages per transaction, one malicious destination module deployed anywhere on a remote chain can render every batch containing its message unprocessable, forcing relayers to repeatedly pay gas for failing transactions or to isolate/drop the poisoned message (delaying delivery of unrelated, legitimate messages routed to the same batch) — a denial-of-service on message delivery that degrades a core "unable to deliver messages" guarantee of the protocol. Relayers absorb repeated gas costs with no compensation since the transaction reverts before fee transfer.

### Likelihood Explanation
Likelihood is high: any account can deploy an `IApp`-shaped contract on a destination chain with an `onAccept`/`onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` function that returns an oversized payload, then get a message routed to it (e.g., by dispatching a request `to` that address from any source chain, since `dispatchIncoming` performs no allowlisting beyond an `extcodesize` check). [6](#0-5) 
No special privileges, races, or timing are required — a single crafted contract and a single dispatched message trigger the condition.

### Recommendation
Bound the return data captured from these low-level calls (e.g. cap gas forwarded and/or copy at most a fixed number of bytes, following the "excessively safe call" pattern) in `EvmHost.dispatchIncoming` (both overloads) and both `dispatchTimeOut` overloads, so a malicious destination module cannot force unbounded memory-expansion gas costs onto the relayer's transaction. Consider using a low-level assembly call with an explicit `returndatacopy` bound (e.g. 32 bytes) instead of the current `abi.encodeWithSelector(...)` + `.call(...)` pattern that copies full return data into a `bytes` return value.

### Proof of Concept
1. Deploy `EvilApp` implementing `IApp.onAccept` that, before returning, does `assembly { return(0, 1000000) }` (or otherwise crafts a huge return buffer).
2. From any source chain, dispatch a `PostRequest` with `to = address(EvilApp)`.
3. Have a relayer submit `HandlerV2.handlePostRequests` containing this request alongside other legitimate requests in the batch.
4. Observe that the `destination.call(...)` in `EvmHost.dispatchIncoming` [1](#0-0)  consumes all remaining transaction gas copying the return data, causing the entire `handlePostRequests` transaction (and every co-batched request) to revert with out-of-gas, repeatedly, until the relayer identifies and excludes the poisoned message.
