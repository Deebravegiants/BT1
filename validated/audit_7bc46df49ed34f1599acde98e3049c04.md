### Title
POA bridge `findMatchingWithdrawal` misreports status/txHash for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a single NEAR intent contains two or more POA-bridge withdrawals of the same `assetId` (e.g., two `ft_withdraw`/`mt_withdraw` operations withdrawing `nep141:usdc.omft.near` to different `destinationAddress`es), `PoaBridge.describeWithdrawal` cannot distinguish between them and reports the same withdrawal record (status + `txHash`) for both. This causes an integrator to observe two distinct destinations "completing" with the identical on-chain payout hash, misreporting the state of one of them.

### Finding Description
The broken equality: `describeWithdrawal({wid: index_i}).txHash` should equal the actual on-chain payout for withdrawal `index_i` specifically, but instead both `index 0` and `index 1` resolve to whichever entry `findMatchingWithdrawal` finds first.

Trace:
- `createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts, lines 80-107) assigns a bridge-route-scoped, purely sequential `index` per withdrawal (`indexes.get(bridge.route) ?? 0`), with no dependency on `assetId`, `destinationAddress`, or `amount`. Two POA withdrawals of the same token get `index: 0` and `index: 1` respectively via `PoaBridge.createWithdrawalIdentifier` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts, lines 295-311), but `index` is never embedded into the returned `WithdrawalIdentifier` in any way that reaches the matching logic — it is present in the struct but unused downstream.
- `watchWithdrawal` (packages/intents-sdk/src/core/withdrawal-watcher.ts, lines 20-78) polls `bridge.describeWithdrawal({...wid})` independently for each identifier.
- `PoaBridge.describeWithdrawal` (poa-bridge.ts, lines 313-343) calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is a `.find()` over the bridge API's returned list, matching solely on `nep141:${w.data.near_token_id} === assetId` (lines 418-427). The `index` field of `WithdrawalIdentifier` is never used to disambiguate.
- The code itself documents this exact limitation: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." (poa-bridge.ts, lines 410-416).

Attacker/caller input: any caller of `sdk.processWithdrawal` / `sdk.signAndSendWithdrawalIntent` / `sdk.createWithdrawalCompletionPromises` with a batch `withdrawalParams` array containing two entries with the same POA `assetId` but different `destinationAddress` (e.g., self-service batch withdrawal to two addresses, or a withdrawal split across a fee-inclusive and non-fee-inclusive leg). Both entries pass `supports()`, `validateWithdrawal()` and are included in the same signed intent, since nothing in `validateWithdrawal`, `supports()`, or the intents contract itself rejects duplicate `assetId` within one batch/intent.

Exploit flow: after the intent settles and the two POA withdrawals are executed independently on the bridge, `watchWithdrawal` for both `index 0` and `index 1` call `describeWithdrawal`, both hitting the same `getWithdrawalStatus` response list, and both resolve to the array's first entry matching that `assetId` — regardless of which one actually completed. If withdrawal-1 completes and withdrawal-2 is still pending/failed, both `watchWithdrawal` calls report the withdrawal-1's `COMPLETED` status and `txHash`.

No existing guard prevents this: `validateAddress`/`compareAddresses` only validate the destination format, `FeeExceedsAmountError` and `getUnderlyingFee` are fee-only checks, `supports()` ordering only picks the bridge type, and none of these check for duplicate `assetId` within a batch.

### Impact Explanation
An integrator/caller that relies on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` results to decide when to credit, refund, or reconcile a withdrawal will see both withdrawal legs (different destinations) reported as "completed" with the identical `txHash`, even though only one payout actually happened on-chain. This is a status/hash misreport that can cause the integrator to credit or consider settled a withdrawal that never actually landed at its destination — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable on every batch of same-asset POA withdrawals until the bridge API/matching logic supports discriminating by more than `assetId`.

### Likelihood Explanation
Preconditions are simple and require no bridge/relayer misbehavior: any batch withdrawal (a supported, documented SDK feature via `withdrawalParams: WithdrawalParams[]`) with two or more legs sharing the same POA `assetId` and going through the POA bridge route. This can be triggered by an ordinary caller using their own funds, at effectively no extra cost, and reproducibly on every occurrence of same-token batched POA withdrawals.

### Recommendation
Extend `findMatchingWithdrawal` (or the POA bridge API contract) to disambiguate withdrawals of the same token by more than `assetId` — e.g., sort withdrawals and identifiers deterministically by `amount`/`destinationAddress` and match positionally by `index`, as hinted in the existing code comment, or request that the POA bridge API return a caller-supplied correlation ID per leg so `describeWithdrawal` can match unambiguously.

		args: WithdrawalIdentifier & { logger?: ILogger },

		// Response list is unsorted, so we match by assetId instead of index

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
