### Title
`Webhooks::Request#shop` returns an unauthenticated header value that `Registry.process` feeds directly into `WebhookMetadata`, letting an attacker relabel any validly-signed webhook body to a victim shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `HmacValidator.validate` checks covers *exclusively the body bytes*, never the `shop-domain` (or any other) header. `Request#shop` is derived purely from `shopify_header("shop-domain")`, i.e. `@headers["shopify-shop-domain"] || @headers["x-shopify-shop-domain"]`, a value with zero cryptographic coverage. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which host apps use to attribute the event to a merchant.

### Finding Description
The invariant that should hold is:
`bytes(shop) ⊆ bytes(to_signable_string)` — i.e. the tenant identifier used to route/act on the webhook should be covered by the same signature that authenticates the payload.

Tracing the code:
- `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns `@raw_body` only. [1](#0-0) 
- `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) reads the private `shopify_header("shop-domain")`, which just does `@headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]` (`lib/shopify_api/webhooks/request.rb:67-70`) — no signature involvement whatsoever. [2](#0-1) [3](#0-2) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` (body only) and compares it against `verifiable_query.hmac` (also header-derived, but the *HMAC value* header, not the *shop* header). [4](#0-3) 
- `Registry.process` calls `HmacValidator.validate(request)`, and on success immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, passing the raw, unverified `shop` value straight to the host app's handler. [5](#0-4) 

Root cause: the `api_secret_key`/`old_api_secret_key` used for HMAC computation is the app's single shared client secret, identical for every shop that installs the app — it is not per-shop. Because the signature covers only the body, and the shop attribution comes from an unsigned header, any request with a *valid body+HMAC pair* (for any shop) passes `HmacValidator.validate` regardless of what `shop-domain` header accompanies it.

Attacker flow, staying within the stated unprivileged capabilities ("may create their own development shop, install the app on it, register their own webhook endpoint, receive their own validly signed callbacks and webhooks"):
1. Attacker installs the target app on their own shop and registers a webhook, e.g. `orders/create`, pointed at their own listener.
2. Shopify delivers a legitimately signed webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact `(B, H)` pair directly to the target app's public webhook endpoint (documented pattern in `docs/usage/webhooks.md`), but substitutes `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `compute_signature(B, S)`, which still equals `H` — the body wasn't altered, and `S` is shared across all shops of this app, so validation succeeds.
5. `Registry.process` sets `WebhookMetadata#shop = "victim-shop.myshopify.com"` and dispatches to the host app's handler, which — per this gem's own docs (`docs/usage/webhooks.md:26`, `handle(data:)` using `data.shop`) — is expected to use `data.shop` to decide which merchant's records the event body pertains to. [6](#0-5) 

No existing guard stops this: `HmacValidator.validate` never inspects `shop`; there is no `ShopValidator.sanitize!` call anywhere in the webhook path; and Sorbet typing only enforces that `shop` is a `String`, not that it is authenticated. The `shopify_header` preference of `shopify-<name>` over `x-shopify-<name>` is not itself the enabling mechanism (the attacker directly controls the request headers when replaying to the app's own endpoint, so header-precedence "smuggling" is unnecessary) — the real defect is that `shop` is never covered by the signature at all, by either header name.

### Impact Explanation
An attacker who has ever received one legitimately signed webhook for their own shop can attribute that webhook's body content to an arbitrary victim `myshopify.com` domain when relaying it to the target host app's webhook endpoint. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (which the gem's own documentation encourages, e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), this can cause the host app to write, update, or delete records under the victim tenant's namespace using attacker-supplied body data — a cross-tenant data-integrity issue. This matches "Critical - cross-tenant access: one shop's request reads or mutates another merchant's data." The attack is repeatable against any victim `myshopify.com` domain the attacker chooses (the domain is a free-form string, not validated) and can be repeated for every webhook topic the app has registered.

### Likelihood Explanation
Preconditions: the host app must use `data.shop` from `WebhookMetadata` to select which merchant's data to touch (a pattern explicitly shown in this gem's own docs) and must not independently verify shop ownership (e.g. checking it against a database of shops that registered that webhook topic/id). Attacker cost is low — a free development store, installing the app once, and capturing one webhook delivery, which is explicitly within the permitted attacker capability set. No secrets are required.

### Recommendation
`Registry.process` / `Request` should not trust the header-derived `shop` as authoritative. Options: bind webhook processing to the previously-stored `webhook_id`/shop mapping from registration (verify the delivered `shop` matches the shop that owns that `webhook_id` in the app's own database) before invoking the handler; alternatively, document prominently that `WebhookMetadata#shop` is unauthenticated and host apps MUST independently verify shop ownership before using it to scope any read/write, and consider deprecating/renaming the field to make this explicit.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_shop_domain_header_is_unauthenticated_and_can_be_relabelled
  ShopifyAPI::Context.setup(api_secret_key: "secret", ...)

  body = '{"id":1}'
  hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), "secret", body)
  hmac_b64 = Base64.encode64(Digest.hexdecode(hmac))

  headers_victim = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac_b64,
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-supplied
  }
  headers_attacker = headers_victim.merge("x-shopify-shop-domain" => "attacker-shop.myshopify.com")

  req_victim = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_victim)
  req_attacker = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_attacker)

  # Same body -> identical HMAC -> both validate, despite different shop attribution
  assert_equal(req_victim.hmac, req_attacker.hmac)
  assert(ShopifyAPI::Utils::HmacValidator.validate(req_victim))
  assert(ShopifyAPI::Utils::HmacValidator.validate(req_attacker))
  refute_equal(req_victim.shop, req_attacker.shop) # "victim-shop..." vs "attacker-shop..."
end
```
This demonstrates that `HmacValidator.validate` accepts identical bodies regardless of the `shop-domain` header value, confirming `shop` is never covered by the signature and is fully attacker-controllable at replay time.
