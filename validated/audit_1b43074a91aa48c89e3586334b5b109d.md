### Title
Shared per-app bandwidth allowance in `pallet-bandwidth` can be drained by any unprivileged dispatcher to DoS all other users of that app - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` enforces a single shared byte-allowance bucket keyed by `(source chain, app)`, not per end-user. Any transaction that causes the app (e.g. `TokenGateway`) to dispatch an ISMP `PostRequest` from a given source chain consumes bytes from this one shared pool. Because the byte cost of a request is a near-fixed function of its ABI-encoded size — independent of the value transferred — an attacker can cheaply flood the shared allowance with many small/self-relayed messages and exhaust it, denying delivery for every other user routing through that same `(chain, app)` pair until governance or the app operator tops up the subscription. This mirrors the reported Axelar ITS flow-limit DoS: a shared, per-epoch/period rate-limit resource that any unprivileged actor can consume to lock out everyone else.

### Finding Description
`Allowance<T>` is a `StorageDoubleMap` keyed by `(StateMachine, AppKey)` holding a FIFO list of subscriptions for that app on that source chain [1](#0-0) . Every non-purchase inbound `PostRequest` from a registered source chain is routed through `BandwidthGate::try_consume(source, app, bytes)` before being processed by the ISMP router in the parachain runtime's `ProxyModule::on_accept` [2](#0-1) .

`try_consume` looks up the allowance keyed only by `(source, app)` — i.e., by the sending contract address, not by the individual end user who triggered the dispatch — and atomically drains bytes from the FIFO head across the shared pool: [3](#0-2) 

Since `app = request.from` is the *dispatching contract* (e.g. the shared `TokenGateway` deployment on a chain used by all bridgers), every user's transfer through that contract draws from the same finite byte budget. The cost charged is `ismp::abi::encode_post_request(&request).len()` — a function of message size only, unrelated to the value being transferred [4](#0-3) . Any unprivileged token bridger who can trigger a cheap outbound dispatch (small teleport/message) can therefore issue many such requests in rapid succession to burn through the app's entire remaining allowance, since the gate performs no per-caller/per-account limiting — only a global `(source, app)` sum check with no fairness or rate-spreading: [5](#0-4) 

Once `Allowance` for `(source, app)` is exhausted, subsequent requests are rejected with `GateError::Insufficient`/`GateError::NoAllowance` and the router surfaces this as a hard error, aborting message processing for every other user of that app on that chain [6](#0-5) . There is no per-account submeter, no fee-based cost scaling with attack cost, and no automatic self-healing — the app must wait for its next top-up window or for governance to `force_credit`/allowlist it [7](#0-6) .

This is architecturally identical to the reported Axelar bug class: a shared rate-limited resource (flow limit / bandwidth allowance) that resets/refills on a schedule and can be drained in full by a single unprivileged actor issuing minimum-cost operations, blocking all other legitimate users sharing that resource until the next refill or an operator intervention.

### Impact Explanation
Exhausting the `(source, app)` bandwidth allowance blocks *all* inbound POST requests from that app on that source chain from being processed by Hyperbridge — meaning every user attempting to bridge tokens or dispatch messages via the shared app (e.g. `TokenGateway`) on the targeted lane is denied service until the allowance is refreshed. This is a route-unable-to-deliver-messages condition affecting the availability of the token bridge/dispatcher for an entire `(chain, app)` pair, not just the attacker's own transfers.

### Likelihood Explanation
The attack requires only the ability to trigger outbound dispatches from the app on the source chain (something any bridger/relayer can already do) and does not require capital proportional to the allowance — unlike the token-value-bound Axelar flow limit, the bandwidth cost here is proportional to message *byte size*, so an attacker can drain the pool using minimal-value transfers or otherwise cheap dispatches, repeated until the shared FIFO list is empty. No privileged role is needed; only ordinary dispatch capability through the targeted app.

### Recommendation
Consider per-account or per-sender sub-limits within the shared `(source, app)` allowance (accepting the Sybil trade-off noted in the original report), rate-spreading consumption over time rather than allowing a single burst to exhaust the whole bucket, or exposing an emergency top-up/allowlist path that can be triggered without requiring a full governance cycle so operators can respond quickly to an observed drain.

### Proof of Concept
1. Governance registers a `BandwidthManager` for source chain `C` and app `A` (e.g. `TokenGateway`), and app `A` purchases a modest tier, crediting `Allowance::<T>::get(C, A)` with a bounded `remaining_bytes` pool [8](#0-7) .
2. An unprivileged actor repeatedly triggers small dispatches from app `A` on chain `C` (e.g., minimal-value `TokenGateway` teleports or direct `IDispatcher.dispatch` calls where available), each incurring only the `abi::encode_post_request` byte cost, not proportional to value moved.
3. Each request passes through `ProxyModule::on_accept` → `BandwidthGate::try_consume(C, A, bytes)`, draining `Allowance::<T>` FIFO entries [5](#0-4) .
4. Once cumulative `remaining_bytes` across all live subscriptions for `(C, A)` drops below the next legitimate user's request size, every subsequent dispatch from any other user of app `A` on chain `C` is rejected with `GateError::Insufficient`/`NoAllowance`, denying service until the app is topped up.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

/// Why the gate refused a request. Surfaces back to the ISMP router.
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum GateError {
	/// The app has no live subscriptions on `(chain, app)`.
	NoAllowance,
	/// Live subscriptions exist but the sum of `remaining_bytes` is
	/// short of what the message needs. The gate makes no mutation in
	/// this case — the caller can retry after a top-up.
	Insufficient { remaining: u128, required: u128 },
}

impl core::fmt::Display for GateError {
	fn fmt(&self, f: &mut core::fmt::Formatter<'_>) -> core::fmt::Result {
		match self {
			GateError::NoAllowance => f.write_str("no bandwidth allowance"),
			GateError::Insufficient { remaining, required } => {
				write!(f, "insufficient bandwidth: have {remaining} bytes, needed {required}")
			},
		}
	}
}

## Force-Credit (Migrations & Refunds)

`force_credit` appends a subscription to any `(chain, app)` bucket without going through a purchase flow:

```rust
BandwidthPallet::force_credit(
    RawOrigin::Root.into(),
    ForceCreditParams {
        app_chain: StateMachine::Evm(8453),
        app: AppKey::truncate_from(app_address.to_vec()),
        tier: TierIndex::TierOne,        // label only — doesn't need to be configured
        bytes: 5_000_000,
        duration_secs: 30 * 24 * 3600,
    },
);
```

Unlike a real purchase, the `tier` field here is **just a label** — it doesn't have to match a configured `TierConfig`. This is the admin escape hatch: refunds for bad purchases, credits during a runtime migration, one-off grants. The same FIFO/cap rules apply — pushing onto a full list evicts the oldest entry with `SubscriptionEvicted`.
