## Title
JWT replay-protection check-then-record race in gateway HTTP trigger authorization allows one-time JWT reuse - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` verifies a caller's JWT, checks its `jti` claim against a replay cache via `isReplay`, and only records the `jti` as used via `recordUsage` after subsequent authorization checks succeed. These two operations are protected by separate lock acquisitions (`RLock`/`RUnlock` for the check, `Lock`/`Unlock` for the write) in `jwtReplayCache`, rather than a single atomic check-and-set, creating a classic TOCTOU race.

## Finding Description
`Authorize` is invoked from `httpTriggerHandler.authorizeRequest`, which is called for every inbound `workflow.execute` HTTP trigger request reaching the gateway's internet-facing, unprivileged-caller endpoint. Within `Authorize`, confirmed at [1](#0-0) , the JWT is verified, `isReplay(claims.ID)` is checked, then (only after the signer-authorization check passes) `recordUsage(claims.ID)` is called. The cache methods use disjoint lock scopes, confirmed at [2](#0-1) : `isReplay` takes an `RLock`, reads, and releases; `recordUsage` later takes a separate `Lock` to insert. There is no shared critical section spanning both operations, so two goroutines processing requests with an identical `jti` can both observe `isReplay == false` before either calls `recordUsage`, both pass the authorized-signer check in between (`keys[key]` lookup), and both proceed to call `recordUsage`, with the second write simply overwriting the timestamp rather than being rejected. `VerifyRequestJWT` in `core/utils/jwt.go` only validates signature, digest, expiry, and issued-at bounds — it performs no replay/uniqueness enforcement of its own, so `isReplay`/`recordUsage` in `jwtReplayCache` is the sole replay-protection mechanism, and it is not atomic.

## Impact Explanation
The `jti` claim exists specifically to make each signed JWT single-use for a `workflow.execute` HTTP trigger request, as reflected by the explicit error message "JWT token has already been used. Please generate a new one with new id (jti)". A successful race lets an attacker (or a legitimate client retrying/duplicating traffic) get two authorization successes for the same JWT, each of which independently proceeds through `HandleUserTriggerRequest` to trigger a workflow execution fan-out to DON nodes. This is a genuine bypass of a documented single-use security control on an internet-facing endpoint, mapping to the "gateway request impersonation" / unauthorized job-run impact category, since the JWT's single-use guarantee is defeated and a duplicate, unauthorized-by-design execution can occur.

## Likelihood Explanation
Exploitation only requires capturing or reusing an already-issued, validly signed JWT (e.g., a legitimate client's own token) and firing it via two near-simultaneous requests — no special privilege, credential leakage, or victim interaction is required beyond what an ordinary caller of the HTTP trigger endpoint already has. The race window is real but narrow, bounded by the time between the `RUnlock` in `isReplay` and the `Lock` in `recordUsage` (which includes a map lookup and signer comparison), making it a low-but-nonzero-probability race per attempt, similar in character to the referenced Spring Security CVE.

## Recommendation
Merge the check and record into a single atomic operation — e.g., add a `checkAndRecord(jti) bool` method on `jwtReplayCache` that holds a single `Lock` for the full duration of checking map membership and inserting the entry (or use `sync.Map.LoadOrStore`), and call this atomic method from `Authorize` immediately after the JWT is otherwise valid, instead of separately calling `isReplay` then `recordUsage`.

## Proof of Concept
1. Issue a valid, signed JWT for a `workflow.execute` request with a fixed `jti` (as done in the existing `TestWorkflowMetadataHandler_Authorize` "JWT replay protection" subtest at `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go` lines 1193-1217).
2. Instead of calling `handler.Authorize` sequentially as the existing test does, invoke it concurrently from two goroutines with the same token and request.
3. Observe that both calls can return `(key, nil)` without error when the goroutine scheduling causes both `isReplay` checks to execute before either `recordUsage` call, demonstrating the non-atomic check-then-act race and violation of the single-use JWT guarantee.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())

	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
