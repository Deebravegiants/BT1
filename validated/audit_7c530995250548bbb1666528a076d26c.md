### Title
Missing chain-binding in NEP-366/461 `DelegateAction` signature enables cross-network replay of meta-transactions - (File: core/primitives/src/signable_message.rs, core/primitives/src/action/delegate.rs)

### Summary
The signed payload for NEAR meta-transactions (`DelegateAction` / `DelegateActionV2`, NEP-366/NEP-461) never binds the signature to a specific chain instance (no genesis hash / chain id / block hash is included). This is the same class of bug as the reported EIP712 issue: a signature scheme that omits a chain-identifying value from the signed message, making signatures replayable on any network that shares the same account/nonce state (e.g. a state fork created via `tools/fork-network` or `tools/mirror`).

### Finding Description
`SignedDelegateAction::verify` hashes and checks a signature over `SignableMessage::new(&delegate_action, SignableMessageType::DelegateAction)`, which serializes only a 4-byte NEP discriminant plus the `DelegateAction` fields: [1](#0-0) [2](#0-1) 

The `SignableMessage` wrapper itself only prepends a NEP/on-chain discriminant; it carries no chain identity: [3](#0-2) 

The only replay-protection primitives are (1) the sender's access-key `nonce`, checked and bumped in `validate_delegate_action_key`, and (2) `max_block_height`, an absolute integer height with no binding to a specific chain's block hash: [4](#0-3) 

This is architecturally different from ordinary `SignedTransaction`s, which include a `block_hash` referencing a recent block on the specific chain the sender observed — that block hash is unique per chain and thus inherently chain-binding. `DelegateAction`, however, was deliberately designed to avoid needing a fresh block hash (so relayers, not users, refresh recency), and instead relies purely on nonce + height, neither of which is chain-specific data: [5](#0-4) 

nearcore itself ships tooling that produces exact state (and thus identical access-key nonce values) forks of a live network, e.g. `tools/fork-network` and `tools/mirror`, the latter of which explicitly re-signs `DelegateAction`s when porting them to a new network because it recognizes signatures don't carry over automatically for remapped keys: [6](#0-5) 

That re-signing logic only exists because the *key* changes during mirroring; when the key/account state is left untouched (the common case for a straightforward state fork, disaster-recovery restore, or an unofficial "mirror" chain), a `DelegateAction` signed by a user for one network verifies identically on the forked network, since `sender_id`, `public_key`, `nonce`, and `max_block_height` can be made to coincide exactly at the fork point.

### Impact Explanation
If a network operator (or attacker) stands up a second network whose genesis state is a snapshot/fork of an existing NEAR network (a supported and expected operation, given the existence of `fork-network`/`mirror` tooling), any previously broadcast `SignedDelegateAction` (these are visible in the receiver's transaction/receipt, and are commonly handed to third-party relayers, who are untrusted by design in the meta-tx model) remains valid on the fork until its `nonce` is consumed there. An attacker with access to a broadcast `SignedDelegateAction` — e.g., a malicious or curious relayer, or anyone reading it off the original chain's finalized receipts — can resubmit it as the outer transaction's action on the forked network (wrapped in any relayer-signed outer transaction, since only the inner signature is checked against `sender_id`/`public_key`), causing sender-authorized actions (transfers, `AddKey`, `FunctionCall` with deposit, etc.) to execute on the fork without the account owner's renewed consent. This constitutes unauthorized state/balance changes on the forked chain, executed by an unprivileged party using only publicly observable data — directly mirroring the EIP712 replay-on-fork scenario, especially dangerous combined with actions such as `AddKey` (full-access key takeover) replayed onto the fork.

### Likelihood Explanation
Requires two conditions: (1) existence of a second network sharing account/nonce state with the original (a legitimate, tooled-for scenario in this codebase via `fork-network`/`mirror`, and also plausible for accidental/duplicate localnet or disaster-recovery deployments), and (2) an attacker obtaining a previously signed, unconsumed `SignedDelegateAction` (trivial, since these values are exchanged with untrusted relayers by design and are visible on-chain once included). No cryptographic break is needed — likelihood is moderate, gated primarily by the existence of a state-compatible second network, which nearcore's own tooling makes straightforward to create.

### Recommendation
Incorporate a chain-identifying value into the NEP-461 signable message for `DelegateAction`/`DelegateActionV2` — e.g., mix in the genesis hash or `chain_id` from `ApplyState`/`EpochManager` into `SignableMessage`/`get_nep461_hash`, similar to how EIP712 recommends deriving `DOMAIN_SEPARATOR` dynamically from `block.chainid` rather than caching it. Verification in `apply_delegate_action` must then also check this value against the executing chain's own genesis hash/chain id, so a signature produced for one network's genesis cannot verify on any other, regardless of matching nonce/account state.

### Proof of Concept
1. Operator/attacker forks a live network's state (e.g. via `tools/fork-network`) at height `H`, producing network `B` with identical accounts, access keys, and nonces as network `A`.
2. On network `A`, Alice signs a `DelegateAction{sender_id: alice, actions: [AddKey(attacker_key, FullAccess)], nonce: N, max_block_height: H+1000, public_key: alice_pk}` and sends it to a relayer for a legitimate purpose.
3. The relayer (or anyone who captured the payload from network `A`'s receipts) submits the same `SignedDelegateAction` bytes wrapped in a fresh outer `SignedTransaction` (any valid `block_hash`/nonce for the relayer) to network `B`.
4. `apply_delegate_action` on `B` calls `signed_delegate_action.verify()` — verification succeeds because the signed hash never referenced network `A`'s identity: [7](#0-6) . `validate_delegate_action_key` succeeds because Alice's access key on `B` still has `nonce < N` (fork state matches): [8](#0-7) .
5. `AddKey(attacker_key, FullAccess)` executes on Alice's account on network `B` without her consent for that network.

```markdown
## Limitation: Accounts must be initialized

Any transaction, including meta transactions, must use NONCEs to avoid replay
attacks. The NONCE must be chosen by Alice and compared to a NONCE stored on
chain. This NONCE is stored on the access key information that gets initialized
when creating an account.

Implicit accounts don't need to be initialized in order to receive NEAR tokens,
or even $FT. This means users could own $FT but no NONCE is stored on chain for
them. This is problematic because we want to enable this exact use case with
meta transactions, but we have no NONCE to create a meta transaction.

For the MVP, the proposed solution, or work-around, is that the relayer will
have to initialize the account of Alice once if it does not exist. Note that
this cannot be done as part of the meta transaction. Instead, it will be a
separate transaction that executes first. Only then can Alice even create a
`SignedDelegateAction` with a valid NONCE.
```
