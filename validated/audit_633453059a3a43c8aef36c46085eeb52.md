Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted but never covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and passed unchanged into the app's webhook handler as trusted identity data. This breaks the intended binding: `hmac == HMAC(secret, full_identity_of_the_event)` should hold, but in this gem it only holds for `hmac == HMAC(secret, body)`, so `shop` can be forged independently of the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from attacker-controllable HTTP headers via `shopify_header`, with no cryptographic tie to those values: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` only checks the signature against `to_signable_string` (i.e., the body), so it can never detect header tampering: [4](#0-3) 

`Registry.process` performs this exact check and then forwards `request.shop` (an unverified header) straight into `WebhookMetadata`, which the host app's handler is documented to treat as the authoritative tenant identifier: [5](#0-4) [6](#0-5) 

The gem's own documentation instructs developers to key their per-tenant work off `data.shop` from the handler, confirming this field is meant to be authoritative: [7](#0-6) 

The identity binding that should hold is:
`hmac == HMAC(api_secret_key, shop ‖ topic ‖ webhook_id ‖ api_version ‖ body)`

but the gem actually enforces only:
`hmac == HMAC(api_secret_key, body)`

Because Shopify's `api_secret_key`/HMAC signing key is per-app (shared across every shop that has installed the app), any shop that has installed the app can produce a body+HMAC pair that is valid for your app secret (simply by triggering any webhook event in their own store). An attacker (any merchant who installs the app - an "unprivileged internet user" relative to other tenants of the app) can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to point at a victim shop. `HmacValidator.validate` still passes because the signature check never inspects those headers, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

### Impact Explanation
If the host application uses `data.shop` from the handler to look up per-tenant records, sessions, or to perform actions scoped to "the shop that sent this webhook" (exactly as the gem's own documentation recommends), an attacker can cause the application to process attacker-supplied webhook content under a victim shop's identity - a cross-tenant confusion/write primitive. Depending on the webhook topic (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`), this can lead to state corruption, data leakage, or unauthorized actions attributed to a shop the attacker does not control. This satisfies the Critical criterion of "cross-tenant access" because the binding between the verified body and the claimed tenant (`shop`) is not enforced by the gem.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple independent shops (i.e., any public/multi-tenant Shopify app, which is the primary use case for this gem): an attacker only needs their own free/dev shop installation to legitimately trigger a webhook, capture the raw body and its valid HMAC, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is required - only a normal, self-service app installation.

### Recommendation
Bind the identity headers into the signed material, or otherwise cryptographically authenticate `shop`, `topic`, `webhook_id`, and `api_version` before trusting them. Concretely, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should include these header values (in a canonical, unambiguous encoding) as part of the signed string, not just the raw body, so that `HmacValidator.validate` fails whenever any of these fields are tampered with independently of the body.

### Proof of Concept
1. App is installed on shop `attacker.myshopify.com` and shop `victim.myshopify.com` (both real, self-service installs - no privileged access needed).
2. Attacker triggers any subscribed webhook on their own store (e.g., updates a product), causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H` (e.g., via their own server logs, a proxy, or a webhook-forwarding tool they control).
4. Attacker replays an HTTP POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a valid request object; `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `B`, matching `H` [1](#0-0) [8](#0-7) 
6. `Registry.process` invokes the app handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the body content originated from the attacker's own shop [5](#0-4)
