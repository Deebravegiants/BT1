### Title
Permanent freeze of curve-sellout graduation via direct Token donation into `Pair` desyncs the buy overflow cap - ([File: packages/contracts/src/Router.sol])

### Summary
`Bonding`'s dual graduation trigger includes a "curve sellout" path (`IPair.tokenBalance() == 0`). That path is only reachable through `Router._computeBuy`'s overflow-cap branch, which caps `tokensOut` at the pair's *live* `tokenBalance()` and derives `cappedReserveToken = reserveToken - tokensOut`. Any unprivileged holder can call the plain ERC20 `transfer` of the launched `Token` directly into its `Pair` (bypassing `buy`/`sell`), inflating the pair's real token balance without touching the virtual `reserveToken` tracked in `Pair._pool`. Once the donated amount is large enough, the overflow-cap branch in `_computeBuy` becomes mathematically unreachable for the rest of the curve's life, permanently blocking full curve sellout and, for tokens that never independently cross the USD graduation threshold, permanently freezing the token in `Lifecycle.Curve` with its raised LT and remaining supply locked in the `Pair`/`Bonding` contracts.

### Finding Description
`Router._computeBuy` computes an uncapped output and then caps it against the pair's real balance: [1](#0-0) 

`tokensOut` from the uncapped formula is always strictly less than `reserveToken` (constant-product asymptote: `tokensOut = reserveToken - k/newReserveAsset`, and `k/newReserveAsset > 0` for any finite `newReserveAsset`). Under normal operation, `realBalance = reserveToken - LP_RESERVE` (the constant gap fixed at launch by `_deployAndSeed`/`Router.addInitialLiquidity`, see `Bonding.sol:460-495`), so for a sufficiently large buy `tokensOut(uncapped) > realBalance` becomes true and the cap branch fires, letting the last buyer legitimately drain `tokenBalance()` to `0` and trip the supply-based graduation trigger in `canGraduate`: [2](#0-1) 

Because `Token` is a standard ERC20 owned by `Bonding` but freely transferable by any holder, any unprivileged address that holds launched tokens (bought earlier off the curve) can `transfer` them directly to the `Pair` address. This raises `IPair.tokenBalance()` (real balance) without touching `_pool.tokenReserve` (the virtual reserve), since `Pair.swap`/`Pair.mint` are the only functions that mutate `_pool`: [3](#0-2) 

Once the cumulative donated amount `D` reaches the `LP_RESERVE` gap (`250,000,000` tokens — the constant, invariant difference between virtual `reserveToken` and real `tokenBalance()` under normal trading), `realBalance = reserveToken - LP_RESERVE + D ≥ reserveToken` for the remainder of the curve's life. Since `tokensOut(uncapped) < reserveToken ≤ realBalance` always, the condition `tokensOut > realBalance` in `_computeBuy` can never be true again — the overflow-cap branch, and therefore full curve drain (`tokenBalance() == 0`), becomes permanently unreachable. Every subsequent buy silently succeeds via the uncapped path, but the pair can never be emptied out, so `canGraduate`'s supply leg is permanently disabled for that token.

The USD leg of `canGraduate` remains theoretically available, but for any token whose paired LT's `exchangeRate()` stays low enough that the raised LT never crosses `graduationThresholdUsd` (a real, permissionless-launch condition — nothing in `Bonding.launch`/`initialize` guarantees rate growth), the token has no remaining path to `_enterGraduating`/`triggerGraduation`. It is then permanently stuck in `Lifecycle.Curve`, with all previously raised LT and the un-sellable tail of curve supply locked inside `Pair`/`Bonding` — this is a permanent freeze of trader and creator funds reachable by a single unprivileged transaction (a bare ERC20 transfer), directly analogous to the external report's "unauthenticated user-supplied input causing a permanent crash/denial of service" class (CWE-400), mapped here onto alt.fun's own bonding-curve overflow-cap logic explicitly called out as a risk area (`Router._computeBuy`'s overflow cap).

### Impact Explanation
This is a High-severity permanent denial-of-service / fund-freezing bug: it does not require any privileged role, oracle manipulation, or upgrade — only holding and donating launched tokens, an action any trader can already perform. It permanently disables one of the two only graduation triggers for the affected token, and for any token whose USD leg never crosses the threshold, the entire curve — creator's raised LT, buyers' locked capital, and the un-mintable LP — is frozen with no recovery path (there is no admin rescue for `Pair`/`Bonding`'s LT/token balances outside the graduation flow).

### Likelihood Explanation
Likelihood is Medium-High: the attack requires no special privilege, no timing race, and no cooperation from other actors — a single address that has bought any amount of the launched token (even from the open curve) can `transfer` it into the `Pair`. Accumulating `LP_RESERVE` (250M tokens, 33% of the 750M curve supply) worth of tokens costs real capital, but is fully within reach of a well-funded griefer, a competing project, or the token's own creator wishing to trap competitors' capital, and the donation is a single, cheap, irreversible transaction once the tokens are held.

### Recommendation
Do not rely on the pair's live ERC20 `balanceOf` (`tokenBalance()`) as the authoritative "real balance" input to the overflow cap or to the supply-based graduation trigger. Instead, track sold/unsold curve supply via `Pair`'s own internal accounting (e.g., a stored `soldSupply` or `realTokenReserve` updated only by `Pair.swap`/`Pair.mint`), so that donations cannot desynchronize the cap logic from the curve's true state. Alternatively, have `_computeBuy` cap against `(realBalanceState - LP_RESERVE)` derived purely from `_pool` state (mirroring how `_launchTimeVirtualLtReserve` derives donation-immune LT figures), rather than a live token balance read that donations can inflate.

### Proof of Concept
1. Creator launches a token via `Zap.createToken` → `Bonding.launch`; curve opens with `reserveToken = 1_000_000_000e18`, real `tokenBalance() = 750_000_000e18` (`LP_RESERVE = 250_000_000e18` gap, per `Bonding._deployAndSeed`/`Router.addInitialLiquidity`).
2. An attacker (or colluding buyer) accumulates ≥`250_000_000e18` of the launched `Token` through ordinary curve buys (`Zap.buy`/`Bonding.buy`).
3. Attacker calls the standard ERC20 `Token.transfer(pairAddress, 250_000_000e18)` directly — no `Bonding`/`Router` call involved, fully unauthenticated w.r.t. the launchpad's own access control.
4. From this point, for any buy amount, `Router._computeBuy`'s uncapped `tokensOut` is provably `< reserveToken ≤ realBalance` (inflated), so the `tokensOut > realBalance` branch that would otherwise cap-and-complete the curve sellout is never entered again — `IPair.tokenBalance()` can approach but never reach exactly `0`.
5. `Bonding.canGraduate`'s supply leg (`IPair(pair).tokenBalance() == 0`) is now permanently `false`; if the LT's `exchangeRate()`-driven USD leg never independently crosses `graduationThresholdUsd`, `canGraduate` never returns `true`, and `triggerGraduation`/`_enterGraduating` are permanently unreachable — the token is stuck forever in `Lifecycle.Curve` with raised LT and un-sellable token supply locked in `Pair`.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

        uint256 assetIn,

        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
