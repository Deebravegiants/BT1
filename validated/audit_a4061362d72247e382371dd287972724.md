### Title
Sell-driven K-slack rounding underflows `ltFromPair` in `_prepareGraduationLiquidity`, permanently bricking the curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Pair.swap` enforces the K invariant with a `+1` rounding slack on both sides: `if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();` [1](#0-0) . This slack lets `assetReserve` legitimately settle to a value one wei below the launch-time virtual LT reserve when `tokenReserve` is driven back up toward `TOTAL_SUPPLY` via sells (i.e., the `(tokenReserve+1)` term absorbs a unit of slack that the strict product would not allow). `Bonding._prepareGraduationLiquidity` then computes `ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr)` as a raw, non-saturating subtraction [2](#0-1) . If `assetReserve` is even 1 wei below the recovered virtual reserve, this line reverts with a Solidity `Panic(0x11)` underflow. This function is invoked unconditionally from `_enterGraduating`, which itself fires inline at the end of *every* buy that satisfies `canGraduate` [3](#0-2) , and is also reachable directly and permissionlessly via `triggerGraduation` [4](#0-3) .

### Finding Description
The protocol explicitly documents `_launchTimeVirtualLtReserve` as an exact identity recovered from `Pair.k() / Token.TOTAL_SUPPLY()`, relying on `k` being fixed once at `Pair.mint` and never mutated by `Pair.swap` [5](#0-4) . The invariant that `assetReserve >= virtualLtReserve` at all times is assumed but not actually guaranteed by `Pair.swap`'s K-check, because that check uses a `+1` slack on *both* reserves simultaneously: `(newTokenReserve + 1) * (newAssetReserve + 1) >= k`. Near the boundary where `tokenReserve` approaches `TOTAL_SUPPLY` (i.e., a trader who bought and then sells most of their tokens back, pushing the curve near its original virtual state), the slack on the `tokenReserve+1` side permits `newAssetReserve` to be driven 1 wei below the pure `k / (tokenReserve+1)` floor — i.e., 1 wei below the launch-time virtual reserve — while still satisfying the K-check.

Once `assetReserve < virtualLtReserve` by even 1 wei, `_prepareGraduationLiquidity`'s subtraction at line 1084 underflows and reverts. Because this function is called unconditionally by `_enterGraduating`, and `_enterGraduating` fires automatically inside `_executeBuy` whenever `canGraduate()` is true, any buy that trips the graduation trigger while this rounding condition holds will revert — reverting the *entire buy transaction*. Since `canGraduate` itself doesn't get evaluated to false as a result (the underlying reserve state is unchanged by the revert), any subsequent buy that also satisfies the graduation condition will hit the exact same revert path, and `triggerGraduation` (permissionless) hits it too. This can leave a token's curve in a state where it can never successfully graduate and where every buy that would cross the graduation threshold reverts — a form of permanent trading paralysis for anyone trying to complete the threshold-crossing trade, and a stuck curve until the underlying reserve ratio drifts back away from the boundary (which may never happen if buys keep reverting before they can move the reserve).

This is the same bug class as CVE-2017-1000112: a length/size value that is computed as a straightforward subtraction of two quantities the code assumes are always ordered a particular way, but whose true ordering can be perturbed by a rounding/slack artifact introduced elsewhere in the same subsystem (the UFO/non-UFO path switch there; the `+1` K slack here), producing a negative (underflowing) intermediate that the code was not written to handle.

### Impact Explanation
This freezes trading progress on the affected bonding curve: a legitimate unprivileged trader's buy that would otherwise cross the graduation threshold reverts instead of executing, and the permissionless `triggerGraduation` path also reverts, so the token cannot graduate through the normal flow while the reserve sits at this rounding boundary. This is a "permanent freezing of trader/creator funds" class issue — the curve is stuck and the anticipated LP for that token can never be seeded via the affected trigger path, matching the impact bar in the assignment ("permanent freezing of trader, creator or LP funds").

### Likelihood Explanation
Reaching the exact 1-wei rounding boundary requires the curve's `tokenReserve` to be pushed very close to `TOTAL_SUPPLY` via sells (i.e., almost all sold tokens bought back), which is a specific but organically reachable state for actively-traded low-liquidity curves or for a trader deliberately probing the boundary with buy/sell round-trips designed to land `assetReserve` exactly 1 wei under `virtualLtReserve` before submitting the threshold-crossing buy. No privileged role is needed — only `Bonding.buy`/`Bonding.sell` (via `Zap`) and `Bonding.triggerGraduation`, both callable by any address.

### Recommendation
Use a saturating subtraction for `ltFromPair` (mirroring the pattern already used elsewhere in `Bonding.sol`, e.g. `_ltSwapInventory` and the `protectedLT` computation): `ltFromPair = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;`. Additionally audit `Pair.swap`'s K-check to confirm whether the `+1`/`+1` slack should instead be one-sided (only on the side receiving output) to avoid allowing `assetReserve` to dip below the virtual floor at all.

### Proof of Concept
I was not able to fully build and run a concrete Foundry PoC within this investigation to confirm the precise reserve values at which the `+1`/`+1` slack in `Pair.swap` permits `assetReserve` to fall 1 wei below `virtualLtReserve` (this requires numeric reserve-boundary analysis or a fuzz run against `Pair.swap`/`_prepareGraduationLiquidity` that I did not have the tool access to execute). The existing test suite's `test_inv_virtualReserveAlwaysExceedsRealBalance` in `test/GraduationInvariants.t.sol` only asserts `tokenBalance() < tokenReserve` (a different invariant, about real vs. virtual *token* balance), and does not test the `assetReserve >= virtualLtReserve` invariant that `_prepareGraduationLiquidity` silently depends on [6](#0-5) . A concrete PoC would need to: (1) launch a token, (2) perform a sequence of buys/sells that drives `tokenReserve` close to `TOTAL_SUPPLY` while probing sell sizes for the `+1`/`+1` K-check boundary, (3) confirm `assetReserve` lands 1 wei below the recovered `Pair.k()/TOTAL_SUPPLY()`, and (4) show that a subsequent threshold-crossing buy or `triggerGraduation` call reverts with a `Panic(0x11)`. I recommend a background Devin session run a targeted fuzz/invariant test against `Pair.swap` and `_prepareGraduationLiquidity` to confirm or refute reachability of this exact boundary before treating this as a confirmed exploit rather than a code-level defect.

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;

    /// @dev Recovers the launch-time virtual LT reserve from immutable
    ///      identities: `Pair._pool.k = tokenReserve_init * assetReserve_init
    ///      = TOTAL_SUPPLY * virtualLtReserve_init` is set ONCE in
    ///      `Pair.mint` and never modified by `Pair.swap` (swap only
    ///      mutates `tokenReserve` / `assetReserve` and asserts K-floor).
    ///      So `Pair.k() / Token.TOTAL_SUPPLY()` returns the exact
    ///      `virtualLtReserve` that was passed to `addInitialLiquidity` at
    ///      launch — for any pair, in any phase, with no storage of our own.
    ///
    ///      Going through this derivation rather than a stored mirror
    ///      eliminates an admin-writable economic-state slot and makes the
    ///      donation-immunity property a pure consequence of the pair's
    ///      already-immutable accounting. The `TOTAL_SUPPLY`-equality check
    ///      in `setTokenImplementation` keeps the divisor consistent across
    ///      impl rotations, so tokens launched under different
    ///      `tokenImplementation` versions still derive the same way.
    function _launchTimeVirtualLtReserve(
        address token_,
        address pair_
    ) internal view returns (uint256) {
        return IPair(pair_).k() / Token(token_).TOTAL_SUPPLY();
    }
