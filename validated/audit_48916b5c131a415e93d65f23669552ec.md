### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by webhook handlers exclusively from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. This breaks the identity binding `HMAC(payload) == HMAC(payload bound to shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controlled HTTP header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` trusts `request.shop` unconditionally once the (body-only) HMAC check passes, and forwards it to the app's handler as the tenant identity: [4](#0-3) 

Because `shop` (and `topic`, `webhook-id`, `api-version`) are excluded from `to_signable_string`, the binding `verified_bytes == acted_on_bytes` fails: the bytes verified by HMAC (raw body) are not the bytes acted on (shop identity used by the handler). Any request bearing a body + HMAC pair that is valid for shop A can be replayed with the `shop-domain` header rewritten to shop B, and the gem will report a valid HMAC while handing shop B's identity to the app's webhook handler with shop A's payload content.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged holder of one valid (body, hmac) webhook pair for their own shop can cause the app to process that payload under a different shop's identity, since the gem provides no cryptographic binding between the verified content and the shop attribution it hands to the handler. Per the rules, this maps to the High/Critical "cross-tenant access" impact category, since the boundary broken is exactly the shop/tenant authenticated (via a header) versus what the HMAC actually attests to (only the body).

### Likelihood Explanation
Exploitation only requires the ability to send an HTTP POST to the app's webhook endpoint with a valid `(raw_body, hmac)` pair — which any merchant using the app already receives from Shopify for their own shop's events — and the ability to modify the `shop-domain` header, both of which are available to any unprivileged internet user/app-installing merchant without needing the `client_secret`, an access token, or any Shopify-side privilege.

### Recommendation
Include `shop`, `topic`, `webhook-id`, and `api-version` in the HMAC-signable content (or otherwise cryptographically bind the shop domain to the verified payload), so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` cannot be satisfied by a body+hmac pair captured for one shop but replayed under a different shop's header, e.g.:
```ruby
def to_signable_string
  "#{shop}#{topic}#{@raw_body}"
end
```
(matching whatever canonicalization Shopify actually signs) and re-derive `HmacValidator` accordingly.

### Proof of Concept
1. App merchant "Attacker" owns `attacker-shop.myshopify.com` and receives a legitimate webhook POST from Shopify with body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` with the app's secret) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and hmac `H` to the app's webhook endpoint but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `Request#to_signable_string` still returns `B` unchanged, so `HmacValidator.validate` succeeds because it never inspects the `shop-domain` header: [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: request.shop` set to `"victim-shop.myshopify.com"` and `body: request.parsed_body` from `B`, letting the attacker inject content attributed to `victim-shop.myshopify.com` despite never controlling that shop: [6](#0-5)
