**Analysis:**

The premise of the question is incorrect. When `HotStateLRU::maybe_evict` evicts an entry, it calls `slot.to_cold()` before inserting it into `pending`: [1](#0-0) 

`StateSlot::to_cold()` converts a `HotOccupied` slot into a `ColdOccupied` slot while **preserving** both `value_version` and `value` fields verbatim — it does not clear, default, or drop the value/owner payload: [2](#0-1) 

The `value` field (a `StateValue`) is the full serialized resource bytes — for a code/package object this is the entire on-chain representation including the owner/upgrade-authority fields. `to_cold` only strips the LRU linked-list bookkeeping (`lru_info`) and the `hot_since_version` marker, not the actual state content. So the evicted cold slot inserted into `pending` in `maybe_evict` (line 123) already reflects whatever `slot` was passed to `insert` prior to eviction — i.e., the latest write for that key within this LRU pass, not a "default/empty value."

`into_updates` (lines 187-203) simply returns `self.pending` unchanged, so it exports exactly the cold slot produced by `to_cold()`, which carries the up-to-date value/owner. There is no code path where a hot slot's value is discarded upon eviction; the eviction logic is specifically designed to fall back to the cold representation while retaining the payload for JMT/cold-DB commit via `maybe_update_jmt`, which reads `value_version`/`value` directly from the (now cold) slot: [3](#0-2) 

The included proptest-based test suite in the same file (`test_empty_overlay`, `test_nonempty_overlay`) already exercises eviction plus commit round-trips across many random block sequences and asserts state consistency, further supporting that no owner/value data loss occurs on eviction: [4](#0-3) 

No unprivileged input can force `into_updates` to export a cold entry with a stale/default owner — the eviction path is value-preserving by construction.
