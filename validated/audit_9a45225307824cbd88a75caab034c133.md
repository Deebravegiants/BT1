## Title
Overpaid native ETH in `EvmHost.dispatch` is refunded to the host itself instead of the fee payer, permanently trapping excess funds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` without first checking that `msg.value` matches the exact amount required for the fee swap, mirroring the `PythOracle.commit`/`_validateAndGetPrice` pattern where `msg.value` is spent on an external call without validation against the expected cost. [1](#0-0) [2](#0-1) 

### Finding Description
The standard Uniswap V2 Router `swapETHForExactTokens` function refunds any *unspent* ETH to `msg.sender` of that call — but the caller of the router here is `EvmHost` itself (since `EvmHost` is the contract invoking `swapETHForExactTokens{value: msg.value}`), not the original transaction sender (`_msgSender()`) who supplied the overpaid `msg.value` to `dispatch()`. As a result, any ETH sent in excess of the exact `post.fee`/`get.fee` swap cost is refunded back into `EvmHost`'s own balance rather than back to the user/app that called `dispatch()`.

Unlike `PythOracle`, which at least has no logic dealing with the refund at all (bug is simply "no refund"), here the code path actively receives the refund but sends it to the wrong recipient — the host contract — with no subsequent step to forward it to `_msgSender()`/`post.payer`/`get` caller. This is functionally identical to the report's root cause: unvalidated/uncontrolled `msg.value` usage in a payable external call that spends less than what was sent, with the leftover value becoming unreachable by the original payer.

This is directly reachable by any unprivileged caller: any app or user invoking `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)` with `msg.value` greater than the exact wei needed to acquire `post.fee`/`get.fee` fee-tokens via the configured Uniswap V2 router will have the difference silently absorbed into the host contract.

### Impact Explanation
Any excess native ETH sent by a caller to `dispatch()` becomes permanently locked in `EvmHost`'s balance because it is credited to the host as the router's `msg.sender`, not to the depositor. Repeated overpayment (e.g., off-by-a-few-wei slippage estimates, or apps that pad `msg.value` for safety) accumulates unrecoverable ETH inside the protocol's core dispatcher contract — a direct freezing-of-funds condition for end users/apps that is unrelated to any admin/governance action and is triggered purely by normal usage of the permissionless `dispatch` entrypoint.

### Likelihood Explanation
High likelihood: exact-output swaps (`swapETHForExactTokens`) essentially always leave some dust/excess ETH unless the caller can predict the router's exact fee-token price at execution time, which is generally impractical (AMM price can move between quote and execution, and callers commonly send extra ETH as a buffer, as acknowledged elsewhere in the codebase's own fee-quoting comments about needing "generous buffers"). Every `dispatch()` call funded with native ETH is exposed.

### Recommendation
After calling `swapETHForExactTokens`, compute the ETH actually spent (via the returned `amounts[0]` or balance delta) and refund the remainder to `_msgSender()` (or `post.payer`/the appropriate payer), following the same pattern already implemented correctly elsewhere in the codebase (e.g., `IntentGatewayV2.sol`'s refund-to-`msg.sender` logic and `UniV4UniswapV2Wrapper.sol`'s balance-delta refund). Alternatively, wrap the swap call through a wrapper contract that refunds excess directly to the original caller rather than to `EvmHost`.

### Proof of Concept
1. User (or an app on behalf of a user) calls `EvmHost.dispatch(DispatchPost)` with `msg.value = X` where `X` is deliberately or accidentally greater than the exact wei cost to acquire `post.fee` amount of fee tokens from the configured Uniswap V2 pool.
2. Inside `dispatch`, `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`.
3. The router spends only the wei needed (`amountIn < X`) to buy `post.fee` fee-tokens and refunds `X - amountIn` back to `msg.sender` of that call, which is `EvmHost`.
4. `EvmHost` never forwards this refund to `_msgSender()` (the original caller of `dispatch`); the refunded wei stays in `EvmHost`'s contract balance with no code path returning it to the original payer.
5. Repeating this across many `dispatch()` calls accumulates permanently stranded ETH inside `EvmHost`. [1](#0-0)

        if (msg.value > 0) {
            address[] memory path = new address[](2);
