### Title
Stale `account.owner` lets the previous NFT holder retain spending authority after a position transfer - (File: contracts/controller/src/account.rs)

### Summary
XOXNO Lending represents each account by a position NFT whose owner is the account owner. The controller, however, stores `owner` inside the `Account` struct at creation time (`create_account_with`, `account.rs:64-70`) and spends authority is checked against that stored field via `require_owner_or_delegate` / `is_owner_or_delegate` (`account.rs:115-140`). Only `require_account_owner` re-reads live ownership through `storage::account_owner` (`account.rs:143-148`). When the NFT changes hands (`position-nft::transfer`, `transfer_from`), no code path restamps `account.owner`, so the stored owner and the true owner diverge permanently.

### Finding Description
The bug class is improper access control: an actor the protocol no longer considers authorized still exercises a restricted capability, while the legitimate principal is denied it.

- `process_withdraw` authenticates the caller and then checks `require_owner_or_delegate(env, account_id, caller, &account.owner)` against the stale stored owner (`positions/supply.rs:147-150`), and pays out to an arbitrary `to` recipient (`supply.rs:152-157`).
- The same stale-owner guard is used by `borrow`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `flash_position` and `migrate_from_blend` (via `AccountGuard::Migrate`/`Multiply` in `load_or_create_account`, `account.rs:99-109`, and the guard calls in `strategies/*.rs`).
- `is_owner_or_delegate` also resolves the delegate list under the stale owner key (`storage::get_delegates(env, account_id, owner)` with `owner = account.owner`, `account.rs:124-126`), so delegates granted by the seller keep authority too — contradicting the declared invariant in `scripts/permissionless_entrypoints.txt` that "delegate grants from the previous owner go inactive".

A single unprivileged address can reach this: sell/transfer the position NFT via `position-nft::transfer_from`, then call `controller::withdraw(account_id, withdrawals, to: Some(attacker))`. The stale `account.owner` still equals the seller, `require_owner_or_delegate` passes, and collateral is withdrawn to the attacker-chosen recipient, subject only to post-pool solvency — which the seller can satisfy by leaving minimal collateral or by first repaying residual debt via permissionless `repay`. Conversely, the buyer — the real NFT owner — fails `require_owner_or_delegate` on every account-spending entrypoint and cannot withdraw, borrow, or manage delegates at all.

### Impact Explanation
- Theft of user funds: the seller (or its stale delegates) drains withdrawable collateral to an arbitrary recipient after the transfer.
- Permanent freezing of funds: the legitimate new owner cannot pass `require_owner_or_delegate`, so the position is unmanageable; only the ex-owner can move it.
- Delegate grants intended to die on transfer stay active under the stale owner's key, extending the theft surface.

### Likelihood Explanation
Any secondary-market trade, OTC sale, or wallet migration of a position NFT triggers the split. The attacker needs no privileges, no flash capital, and no oracle manipulation — `transfer_from` followed by `withdraw` suffices. The only mitigations would be an ownership resync on NFT transfer or a check comparing `account.owner` to `storage::account_owner`; neither is present in the guard path. If a resync hook exists elsewhere in the NFT contract (unverified within index coverage), the finding reduces, but the dual source-of-truth pattern itself (`account.owner` vs `account_owner`) demonstrates the access-control divergence.

### Recommendation
Make NFT ownership the single source of truth for spending authority: resolve `account.owner` from `storage::account_owner(env, account_id)` inside `require_owner_or_delegate`/`is_owner_or_delegate` (or restamp `account.owner` from the NFT owner whenever the account is loaded), and key delegate lists to the current NFT owner so grants cannot survive a transfer.

### Proof of Concept
1. Alice owns `account_id` with 1,000 USDC collateral, `account.owner = alice`.
2. Alice sells/transfers the position NFT to Bob via `position-nft::transfer_from(alice, bob, account_id)` (approved or owner call). Controller storage still holds `account.owner = alice`.
3. Alice calls `controller::withdraw(alice, account_id, [(USDC, amount)], to: Some(alice))`. `require_owner_or_delegate` sees `caller == account.owner` (`account.rs:121`) and passes; the pool pays Alice.
4. Bob calls `controller::withdraw(bob, account_id, ...)`: `is_owner_or_delegate` compares `bob` to stale `account.owner = alice` → `NotAuthorized` panic (`account.rs:139`). Bob owns the NFT but cannot touch the account — funds are frozen for him and already stolen by Alice.
