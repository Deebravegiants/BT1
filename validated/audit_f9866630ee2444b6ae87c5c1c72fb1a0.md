## Title
POA Bridge withdrawal status matched only by `assetId` in batch withdrawals causes cross-withdrawal status/hash misattribution - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain completion status/tx hash for a withdrawal by matching entries returned from the POA bridge API using **only `assetId`** (`nep141:<near_token_id>`), ignoring `index`, `amount`, or `destinationAddress`. When a single intent contains two or more withdrawals of the **same token** (a supported and documented feature — batch withdrawals — see `sdk.ts` `processWithdrawal`/`signAndSendWithdrawalIntent`), both withdrawals resolve against the *same* matched API record, so the SDK can report the wrong `txHash`/status for a given `WithdrawalIdentifier`.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 418-427) finds the first withdrawal entry whose `near_token_id` maps to the requested `assetId`: [1](#0-0) 

This function is called per-withdrawal, per-poll, from `describeWithdrawal`: [2](#0-1) 

The comment explicitly acknowledges the limitation: "Currently only matches by assetId... This means multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) . An identical, independently-implemented copy of this same limitation exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` [4](#0-3) .

However, the SDK's batch withdrawal feature does not prevent two withdrawals of the same token from being submitted in one intent — `signAndSendWithdrawalIntent`, `createWithdrawalCompletionPromises`, and `processWithdrawal` all accept `WithdrawalParams[]` without any uniqueness constraint on `assetId`, and `createWithdrawalIdentifiers` assigns a `WithdrawalIdentifier.index` per bridge route to distinguish entries in the batch [5](#0-4) . But that `index` is never used to disambiguate the POA API response — `describeWithdrawal` only reads `args.withdrawalParams.assetId`, discarding `args.index` entirely.

Because the underlying API response list is unsorted and keyed only by token, two same-token withdrawals to *different destination addresses* in the same batch will both resolve to whichever matching record `Array.find` returns first. This breaks the equality "status/hash reported for withdrawal N corresponds to the on-chain outcome of withdrawal N" — instead, withdrawal N may be reported using another withdrawal's `transfer_tx_hash` and completion status.

### Impact Explanation
This falls under the allowed impact class: "a status or hash misreport making an integrator credit or refund twice" and "a withdrawal stuck until manual intervention". Concretely:
- An integrator polling `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` for two same-token withdrawals (e.g., paying out two different users the same token in one batched intent) can receive Withdrawal A's `txHash` for Withdrawal B's promise (or vice versa) if timing/pending-vs-completed states of the two legs diverge during polling. An integrator that credits/marks-complete based on the reported `txHash` per index could attribute the wrong transaction to the wrong recipient, or mark one leg "completed" using a `txHash` that actually belongs to the other leg — enabling a double-credit/misdelivery bookkeeping error on the integrator side, or leaving one leg falsely "pending" forever (stuck until manual intervention) if the same record keeps satisfying the other index's poll first.
- This is a genuine equality violation (status reported ≠ actual on-chain outcome for that specific `WithdrawalIdentifier`), not a pure availability/DoS issue, since the wrong-but-plausible result may be returned instead of an error.

### Likelihood Explanation
Moderate. It requires an integrator to batch two withdrawals of the *same* `assetId` in a single intent (explicitly supported by the batch withdrawal API, no validation prevents it), and for both withdrawals' statuses to be indexed/returned in the same polling window with the naive `find` returning a shared record. This is plausible in normal usage of batch withdrawals (e.g., paying two different users the same token) and does not require any malicious counterparty — it's a logic defect triggered by legitimate concurrent batch use.

### Recommendation
Disambiguate matching using more than `assetId`: incorporate `amount`, `destinationAddress`, and/or ordinal position (sorting both the withdrawal params and the API response by amount, as the existing code comment already suggests) so each `WithdrawalIdentifier.index` in a batch maps deterministically to the correct API record. Until the POA API supports a stable per-withdrawal identifier, reject/validate batches containing duplicate `assetId` entries in `PoaBridge`, or fail the polling loop loudly (throw) instead of silently returning another withdrawal's `txHash`/status when the match is ambiguous.

### Proof of Concept
1. Build a batch withdrawal with two `WithdrawalParams` entries of the same `assetId` (e.g., `nep141:usdt.tether-token.near`) but different `destinationAddress`/`amount`, and submit via `sdk.processWithdrawal({ withdrawalParams: [paramsA, paramsB] })`.
2. `createWithdrawalIdentifiers` assigns `index: 0` and `index: 1` for the two POA-bridge legs [5](#0-4) .
3. When polling completion, `describeWithdrawal` is invoked independently for each `WithdrawalIdentifier`, each time calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) .
4. Since the POA API response array contains two entries with the same `near_token_id` and `Array.prototype.find` always returns the first match, both `index: 0` and `index: 1` polls that occur before both legs are `COMPLETED` may match the *same* entry (e.g., the one for index 0 leg only, or an entry for the leg that completed first) rather than their own. The `WithdrawalCompletionPromises[0]` and `[1]` can therefore resolve with a `txHash`/status that does not correspond to their own destination address/amount, confirming the misattribution.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
