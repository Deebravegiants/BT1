### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw request body only, while the `shop` (tenant) identity is read from an HTTP header that is never included in that signable string. `Registry.process` validates the HMAC and then forwards `request.shop` straight to the host application's handler as the trusted tenant identifier, breaking the binding between "bytes verified" and "tenant acted on."

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `to_signable_string` and comparing it to the caller-supplied `hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw JSON body: [2](#0-1) 

But `Request#shop` — the value used to identify which tenant/shop the webhook belongs to — is pulled directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then constructs `WebhookMetadata` using this unverified `shop` header, handing it to the app's `WebhookHandler#handle` as the trusted tenant context: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop-header == HMAC-covered-shop`. Instead it is `HMAC covers body only`, while `handler.handle` trusts `shop-header` as-is. This is exactly the "field acted on but not covered by the HMAC" bug class from the report: the VM bug conflated two operations because it didn't distinguish/verify one side of an equality before writing state; here, `Registry.process` conflates "body signature is valid" with "shop header is trustworthy," writing/acting on tenant data (`shop`) that was never cryptographically bound to the signature.

### Impact Explanation
Any actor capable of receiving a legitimately-signed webhook from the same Shopify app (e.g., an unprivileged merchant who installs the target app on their own store, which they fully control) can capture a valid `(raw_body, hmac)` pair. Because the `shop` header is excluded from the signed content, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop. If the host application uses `data.shop` to look up sessions, update per-tenant records, or trigger merchant-scoped side effects, this enables cross-tenant data injection/spoofing — meeting the "cross-tenant access" bar in the Critical impact category.

### Likelihood Explanation
Likelihood is moderate to high for any first-party or third-party developer whose app installs on multiple shops (the common case for public Shopify apps): the attacker only needs to be a normal merchant who can install the app on their own store to obtain a validly-signed webhook body, then can replay it with a forged shop header. No access to `api_secret_key`, tokens, or privileged accounts is required — only observation of one's own legitimately delivered webhook traffic, which is standard "unprivileged internet user" capability.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified surface, or otherwise cryptographically tie the header-derived shop to the signed body before it is trusted downstream. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to ensure the `shop` header cannot be swapped independently of the signed payload — e.g., by validating shop against a value embedded in the payload/topic context that Shopify actually signs, or by rejecting/flagging when the same `(body, hmac)` pair is observed for more than one shop.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to (e.g. `orders/create`). Capture the delivered `raw_body` and `shopify-hmac-sha256` header — both are validly signed with the app's shared secret for that specific body.
2. Replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only hashes `raw_body` — unchanged from step 1. [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and performs shop-scoped state changes as if the event genuinely originated from `victim.myshopify.com`, even though the tenant identity was never covered by the signature.
