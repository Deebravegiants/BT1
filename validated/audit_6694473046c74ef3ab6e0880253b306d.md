## Title
Webhook shop-domain/topic headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are read directly from the (unauthenticated) HTTP headers and handed to the webhook handler as trusted identity data, even though none of them are included in the signed content. Any holder of a single valid `(body, hmac)` pair — trivially obtainable by installing the app on an attacker-controlled store — can replay that pair against the app's public webhook endpoint while forging the `shop-domain` (and `topic`) header to impersonate a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

Yet `Registry.process` derives `shop`, `topic`, `webhook_id`, and `api_version` straight from the (unsigned) headers and passes them into the handler as authenticated identity fields once the (body-only) HMAC check passes: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all simple header reads with no cryptographic binding to the signed payload: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that installs the app, any store owner can install the app on their own shop, capture a legitimately-signed `(raw_body, hmac)` pair addressed to them, and then resend that exact pair to the same webhook endpoint with a rewritten `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header pointing at a victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the body against the secret — it never validates that the `shop`/`topic` headers correspond to the entity the payload was actually generated for. This breaks the intended identity binding `authenticated_shop == acted_upon_shop`; the gem authenticates the body, but the identity fields the host application acts on (`WebhookMetadata#shop`, `#topic`, `#webhook_id`) are attacker-controlled.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who has legitimate, unprivileged access to the app (by installing it on their own store) can cause the library to hand the host application webhook data falsely attributed to another merchant's shop. Any host application that keys its business logic off `WebhookMetadata#shop` (e.g., updating order/customer/fulfillment state for "that shop") can be tricked into applying attacker-supplied data to a victim tenant, i.e., cross-tenant access/data injection — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to install the target app on a store the attacker controls (a normal, unprivileged action any Shopify user can perform) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. The replay is trivial: capture one webhook, resend it with a modified header.

### Recommendation
Bind the HMAC to the full identity context, not just the raw body — e.g., have `to_signable_string` (or a new signature check in `Registry.process`) incorporate the `shop`, `topic`, and `webhook_id` header values, or otherwise cryptographically verify that the `shop-domain`/`topic` headers match values embedded in (or otherwise bound to) the signed payload before dispatching to a handler. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not authenticated by `Utils::HmacValidator.validate` and must be independently corroborated by the host application (e.g., against the registered webhook subscription per shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`
   - Body: `{"id":1,...}` (attacker-controlled order content, since it's their own store)
3. Attacker captures this exact `(body, X-Shopify-Hmac-Sha256)` pair.
4. Attacker resends an HTTP POST to the same public webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`: [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the payload was never generated for that shop — enabling cross-tenant data injection in the host application.
