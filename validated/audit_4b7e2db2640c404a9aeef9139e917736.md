### Title
Small position holders can be permanently locked out of selling once curve price drops below the mint/redeem floor, with no sell-side escape hatch analogous to the buy-side "floor-bump" — (File: `packages/contracts/src/Zap.sol`)

### Summary
`Zap._sellInternal` enforces a hard floor (`minUsdcAmount()`, mirroring BounceTech's LT mint/redeem minimum) on the *entire* sell being executed, with no fallback. `Zap._executeBuy` has an explicit "floor-bump" mechanism to rescue trades that would otherwise fall into this same dead band, but the sell path has no equivalent. Because every position is created above the floor (buys are also floor-gated) but the bonding-curve price can fall after purchase due to other sellers, a small holder's *entire* remaining balance can end up worth less than the floor, and they then have no way to exit via `Zap.sell` — the analog of the original finding's "last MIN_AMOUNT can never be withdrawn."

### Finding Description
`Zap._sellInternal` pulls the seller's full `tokenAmount`, executes the curve (or post-graduation V2) sale, and then checks the *gross* USDC value of what was received against the live floor: [1](#0-0) 

If `grossUsdcEstimate / 1e12 < minUsdcAmount()`, the call reverts with `BelowMinAmount()` — before any tokens are actually redeemed to USDC, but *after* the caller has committed to selling their whole intended amount (`IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenAmount)` already ran). There is no partial-sell batching, no chunked retry, and no analog to the buy-side rescue.

Compare this to the buy side, where the same floor problem was explicitly engineered around. `_executeBuy` detects when the cap-implied `baseToConvert` would land below `minUsdcAmount()` and bumps it up to the floor, refunding the LT overshoot rather than reverting: [2](#0-1) 

This "floor-bump" is exercised and validated in `test_buy_capPath_floorBump_succeeds`, which explicitly frames the cap-implied amount landing "squarely in the structural-stuck band" and shows the bump rescues it: [3](#0-2) 

No equivalent exists for sells. The sell-side floor test only demonstrates the revert, with no rescue path: [4](#0-3) 

Every position is created above the floor because buys are gated by the same check (`minUsdcAmount()`/`minSeedUsdc()`), so a $10-minimum buyer's initial position is always worth ≥ floor at purchase time: [5](#0-4) 

However, the bonding-curve price for a token is not fixed after purchase — `Router._computeSell` derives the sell price from the live `(reserveToken, reserveAsset)` state, which other sellers can push down over time: [6](#0-5) 

So a holder who bought exactly at (or just above) the floor, and later sees the curve price fall because other traders sold into the pool, can end up holding a position whose *entire* remaining balance sells for gross USDC below `minUsdcAmount()`. Since `Zap.sell`/`sellWithPermit` are the only unprivileged, on-curve exit paths and neither has a floor-bump, that holder cannot execute any sell of their full position (selling less only makes the estimate smaller, not larger) until the curve price recovers — which is not guaranteed, especially for an abandoned or declining token that never reaches the graduation threshold.

### Impact Explanation
This is a permanent-freezing-of-trader-funds bug class, directly analogous to the referenced H-02: a hardcoded minimum-amount check applied without regard to the caller's actual remaining balance can make it structurally impossible to exit a position. Here it manifests per-trader rather than pool-wide, but the mechanism and outcome are the same — funds become inaccessible through the sanctioned exit path (`Zap.sell`) once the tradable value drops below the floor, with no escape analogous to the one deliberately built for buys.

### Likelihood Explanation
Likelihood is realistic but conditional: it requires (a) a holder positioned near the $10 floor (easy — the floor is exactly the minimum allowed buy size) and (b) subsequent net selling pressure that drags the curve price down before the holder exits. Low-liquidity or declining tokens that never cross the graduation threshold are the most exposed, and nothing in the protocol prevents a token from sitting indefinitely in `Lifecycle.Curve` at a depressed price.

### Recommendation
Add a sell-side rescue symmetric to the buy-side floor-bump: e.g., allow `Zap.sell` to accept a caller-specified "sell everything, accept `usdcOut == 0` if below floor and simply refund the un-sold LT/tokens back to the caller" path, or let sells below the floor return the underlying LT directly to the seller (mirroring the buy-side `ltExcess` refund) instead of unconditionally reverting the whole trade.

### Proof of Concept
1. Trader buys the minimum allowed amount via `Zap.buy(tokenAddr, minSeedUsdc()/minUsdcAmount(), 0, address(0))`, receiving a small token balance whose value is just at the `minUsdcAmount()` floor (as in `test_buy_revertsBelowMinAmount`, the boundary is exactly `zap.minUsdcAmount()`).
2. A second, larger trader sells a large amount into the same curve, driving `reserveAsset`/`reserveToken` down per `Router._computeSell`, lowering the curve price for the token.
3. The first trader calls `zap.sell(tokenAddr, theirFullBalance, 0)`. `_sellOnCurve` returns `ltReceived` whose `grossUsdcEstimate` (line 444 of `Zap.sol`) is now below `minUsdcAmount()`; the call reverts with `Zap.BelowMinAmount()` exactly as exercised by `test_sell_revertsBelowMinAmount`, but here through organic price movement rather than an exchange-rate mock.
4. There is no chunked-sell or floor-bump fallback (unlike `test_buy_capPath_floorBump_succeeds` for buys), so the trader's tokens remain frozen in their wallet until/unless the curve price recovers.

        address tokenAddr = _createToken(0);

        // overflow cap, so the next cap-binding buy sizes `amountInUsed

        // without an additional buy. 10% bump puts the LT raised

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
