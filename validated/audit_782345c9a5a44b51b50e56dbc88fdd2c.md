### Title
Permanent freezing of Intent Gateway escrow when a blacklistable-token beneficiary is denylisted - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentsBase._withdraw()` (EVM) and `IntentGatewayV2.withdraw()` (Tron variant) release escrowed order inputs to a beneficiary fixed at order-placement/fill time (`order.user` for refunds, the filler for redemptions) using a plain `safeTransfer`/low-level `.call` per token, with no fallback if the transfer reverts. If the escrowed token is a blacklist-capable stablecoin (e.g. USDC) and the beneficiary address becomes blacklisted, every future attempt to release that escrow reverts, permanently freezing the funds — the same non-atomic-transfer bug class as the referenced Y2K `mintRollovers()` report, but here it locks user/solver escrow rather than merely stalling an emissions queue.

### Finding Description
`_withdraw` iterates `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each escrowed token, and the Tron variant's `withdraw()` uses a raw `.call` to `transfer` and explicitly `revert TransferFailed()` on failure: [1](#0-0) [2](#0-1) 

The beneficiary is not chosen by the caller of `_withdraw`/`withdraw` at redemption time — it is baked into the order or fill:
- Same-chain cancel: beneficiary is always `order.user`, set at order placement and immutable thereafter. [3](#0-2) 
- Cross-chain `RefundEscrow`/`RedeemEscrow` delivered via `onAccept`: the `WithdrawalRequest.beneficiary` is decoded straight from the incoming message and passed to `_withdraw`, again with no per-token fallback path. [4](#0-3) 
- The GET-response cancellation path on the destination-authoritative chain also routes through the same `withdraw()`. [5](#0-4) 

Because the entire external call (`onAccept`/`onGetResponse`/`cancelOrder`) reverts atomically when any single-token transfer fails, and `_filled[commitment]` is only set (and only persists) if the whole transaction succeeds, a blacklisted beneficiary causes:
1. `_filled[commitment]` to never be set, so the escrow can never be marked settled.
2. The escrowed balance in `_orders[commitment][token]` to remain locked, since every retry of the withdrawal hits the same revert.
3. No alternate recovery path exists in the contract — `cancelOrder`/`onAccept`/`onGetResponse` all funnel through the same non-resilient `_withdraw`/`withdraw`.

This is structurally identical to the reported `mintRollovers()` bug class: a single blacklisted recipient in a batch/queue transfer causes the whole operation to keep reverting indefinitely, but here the "queue" is the Intent Gateway's escrow-release mechanism and the impact is a fund freeze rather than a stalled emissions distribution.

### Impact Explanation
Any order whose `order.user` (refund beneficiary) or filler (redeem beneficiary) is later blacklisted by the escrowed ERC-20 (realistic for USDC/USDT-style tokens which are commonly used as intent inputs) results in that order's escrow becoming permanently unrecoverable: refunds cannot be issued to the user, and redemptions cannot be paid to the filler. Because `_filled` is never durably set, the funds sit frozen in the gateway with no functional cancellation or redemption path — a permanent freezing of user/solver funds, which is a Medium/High-severity impact under the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: it requires the escrowed/output token to be a centrally-blacklistable asset (true for USDC, USDT, and similar tokens frequently used in intents) and requires the beneficiary address to be denylisted by that token's issuer — an event outside the protocol's control but realistic given intents commonly settle in USDC. No attacker action against the protocol itself is needed beyond placing/filling an order with a beneficiary that is (or becomes) blacklisted; a malicious actor could also intentionally get their own counterparty blacklisted (e.g., by using that address in flagged activity elsewhere) to grief a specific order.

### Recommendation
Make per-token payout in `_withdraw`/`withdraw` resilient to individual transfer failures instead of reverting the whole settlement:
- Wrap each token transfer in a try/catch (or low-level call with failure handling) and, on failure, credit the amount to a claimable/escrow-claim mapping keyed by `(beneficiary, token)` instead of reverting.
- Still finalize `_filled[commitment]` and emit the settlement event even if one token's transfer could not be completed, so the rest of the payout and future order state are not blocked.
- Provide a separate `claim(token)` function beneficiaries can call (potentially specifying an alternate recipient) to retrieve tokens that failed to transfer directly, decoupling settlement finality from any single token's transfer success — analogous to the "emissions claimer" recommendation in the original report.

### Proof of Concept
1. User places a same-chain order with USDC as the escrowed input (`order.user = attacker`), or a cross-chain order settling in USDC where the filler's payout address is `attacker`.
2. `attacker`'s address is added to USDC's blacklist (via Circle's blacklist policy, triggered by unrelated malicious activity).
3. User calls `cancelOrder()` → routes to `_cancelSameChain` → `_withdraw(body, true, true)` with `beneficiary = attacker`. [3](#0-2) 
4. Inside `_withdraw`, `IERC20(USDC).safeTransfer(attacker, amount)` reverts because USDC's `transfer` reverts for a blacklisted `to` address. [6](#0-5) 
5. The entire `cancelOrder` transaction reverts; `_filled[commitment]` is never set and `_orders[commitment][USDC]` retains the escrowed balance.
6. Every subsequent cancellation/redemption attempt for this commitment reproduces the same revert — the escrow is permanently frozen with no path to recovery in the current contract logic.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
