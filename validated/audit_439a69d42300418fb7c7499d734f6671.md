## Finding

### Title
Webhook HMAC validation does not bind the `shop` identity to the signed payload, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`) values that are handed to the application's webhook handler come from HTTP headers that are never included in the HMAC-signed material. This breaks the identity binding `shop_verified_by_hmac == shop_delivered_to_handler`, allowing a party who possesses one valid `(body, hmac)` pair (e.g. from a webhook legitimately delivered to their own shop) to relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `Request#to_signable_string` returns only the raw request body — none of the Shopify-supplied headers are part of the signed string: [2](#0-1) 

Yet `shop`, `topic`, and `webhook_id` — all read straight from unauthenticated HTTP headers — are exactly the values used to route and label the event when the registry processes it: [3](#0-2) 

`Registry.process` only checks the body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when constructing the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the `shop-domain` header sits entirely outside the HMAC's coverage, anyone holding one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on any shop and receiving one legitimate webhook — can replay that exact pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`webhook-id`) header value. `HmacValidator.validate` will still return `true` because it never looks at those headers, and the handler will process the request believing it originated from the spoofed shop.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce: the shop identity that reaches application logic is not cryptographically bound to the authenticated payload. An app that keys any per-shop state, side effects, or database writes off `WebhookMetadata#shop` can be made to attribute attacker-controlled webhook data to an arbitrary victim shop, i.e. cross-tenant access/confusion driven entirely by this gem's own validation logic.

### Likelihood Explanation
High. No secret material is needed beyond what any legitimate app installer already possesses (one valid webhook delivery to their own store). The webhook endpoint is by design internet-reachable so Shopify can deliver to it, so a forged request can be sent directly by any unprivileged internet user who has captured one legitimate `(body, hmac)` sample.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the material verified against the HMAC (or otherwise cryptographically bind them, e.g. by validating the shop domain that owns the sending relationship against session/app installation state) before trusting these header values in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`).
2. Send a POST directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`), and `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied webhook content as if it came from the victim's shop.
