### Title
Unbounded panic on `Vote.signature` length mismatch during ECDSA-BEEFY proof decoding - ([File: evm/rust/src/conversions.rs])

### Summary
The `From<Vote> for SignatureWithAuthorityIndex` conversion, used when decoding an EVM-side ECDSA-BEEFY consensus proof back into Substrate's `SignatureWithAuthorityIndex` type, copies an attacker/relayer-supplied `bytes signature` field into a fixed-size `[0u8; 65]` array via `copy_from_slice` without first checking that the input is exactly 65 bytes long.

### Finding Description
`evm/rust/src/conversions.rs` implements:
```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
``` [1](#0-0) 

`value.signature` originates from the Solidity `Vote` struct's `bytes` field, which is decoded from calldata/proof bytes that a relayer submits (an EVM-encoded `RelayChainProof`/ECDSA-BEEFY consensus proof). `Rust`'s `copy_from_slice` panics if `sig_bytes.len() != 65` — this is exactly the bug class in CVE-2019-14198: a length that is not checked before being used to drive a fixed-size copy operation. This directly parallels the pattern the codebase has otherwise been systematically hardened against elsewhere (e.g. the `as_utf8_string` fix and `consensus_state_id_from_str` fix, both explicitly noting that "wrong lengths must be ... errors" rather than panics on untrusted input) [2](#0-1)  and the `ByteVector<N>::decode` length-checked SCALE decoding hardening [3](#0-2) . The `Vote`/`SignatureWithAuthorityIndex` conversion was not brought in line with that pattern.

### Impact Explanation
A relayer submitting an ECDSA-BEEFY consensus proof (`RelayChainProof`) containing a `Vote` whose `signature` field is not exactly 65 bytes will trigger a Rust panic in this conversion path. Because this conversion executes off-chain (in `evm/rust`, used by tooling/tesseract-side conversion of proofs) rather than inside the EVM contract itself, the reachable blast radius is limited to whichever process performs this Rust-side conversion when constructing/relaying an ECDSA-BEEFY proof — panicking that worker/thread is a denial-of-service against that specific proof-processing path rather than a memory-safety or fund-theft bug (Rust panics abort/unwind safely; no out-of-bounds write occurs). It does not, by itself, allow forged message delivery, unbacked mint, or fund theft.

### Likelihood Explanation
Reaching this code requires supplying a `Vote.signature` of the wrong length inside an otherwise-parseable `RelayChainProof`/`Vote` ABI-encoded blob. This is plausible for any party able to submit or relay an ECDSA-BEEFY consensus proof, since ABI-decoded `bytes` fields impose no length constraint on `signature` before this conversion runs.

### Recommendation
Replace the panicking `copy_from_slice` with a fallible length check that returns an error (mirroring the `as_utf8_string`/`ByteVector<N>` hardening pattern elsewhere in the codebase), e.g. `TSignature::try_from(sig_bytes.as_slice()).map_err(|_| ...)?` and propagate a decode error instead of aborting the conversion, so a malformed `Vote.signature` length is a clean SPHINCS+-safe rejection of the proof rather than a panic in the conversion path.

### Proof of Concept
Construct an ECDSA-BEEFY `RelayChainProof` whose `signedCommitment.signatures` array contains a `Vote` entry with a `signature` field of length ≠ 65 (e.g., 0 or 64 bytes) — trivially producible since the ABI encoding of `bytes` places no constraint on length. When the Rust-side tooling calls `SignatureWithAuthorityIndex::from(vote)` during proof construction/verification, `signature.copy_from_slice(&sig_bytes)` panics with a slice-length mismatch, since `TSignature` is a fixed `[u8; 65]` array and `copy_from_slice` requires an exact length match.

/// Length-checked SCALE decoding.
///
/// A derived `Decode` here delegates to the inner `Vector`, which carries its own derive and
/// so accepts any length — leaving a `ByteVector<N>` holding something other than `N` bytes.
/// That matters because the SSZ hash root is not sensitive to trailing zero bytes: a value
/// packs into `ceil(N / 32)` chunks with the tail already zero-padded, so appending zeros up
/// to the next chunk boundary consumes padding that was already there and leaves the root
/// unchanged. A consumer that authenticates only by `hash_tree_root` would therefore accept an
/// over-length value and persist it, and the length would not be caught until some later
/// operation — for a BLS key, a point decompression far away from this decode.
///
/// Reject at the boundary instead, reusing the same `deserialize` the byte-slice conversions
/// above go through so there is one definition of the length rule.
///
/// The wire format is unchanged: `Vector`'s SCALE representation is just its inner `Vec`, as
/// its merkle cache is `codec(skip)`.
impl<const N: usize> codec::Decode for ByteVector<N> {
	fn decode<I: codec::Input>(input: &mut I) -> Result<Self, codec::Error> {
		let bytes = Vec::<u8>::decode(input)?;
		if bytes.len() != N {
			return Err(codec::Error::from("ByteVector: decoded length does not equal N"));
		}
		ByteVector::<N>::try_from(bytes)
			.map_err(|_| codec::Error::from("ByteVector: SSZ deserialization failed"))
	}
```
