### Title
Webhook shop-domain identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` (the value that `Utils::HmacValidator` actually verifies) is only the raw request body. The `shop` value that is handed to the host application's webhook handler is therefore never bound by the HMAC signature, breaking the intended identity binding `hmac_valid(body) == shop_is_authentic`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers, with no cryptographic tie to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac-sha256` header value: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (from the header) to build `WebhookMetadata` that is passed to the app's handler, with no re-derivation of shop identity from signed data: [4](#0-3) 

Because the signature only covers the JSON body, an attacker who has legitimate control of any one shop that installs the vulnerable app can capture a valid `(body, hmac)` pair generated for their own shop, then replay it to the app's webhook endpoint while substituting a victim's `shop-domain` (and/or `topic`/`webhook_id`) header. `HmacValidator.validate` will still pass because it only checks the untouched body, but `Registry.process` will dispatch the payload to the handler labeled with the attacker-chosen `shop`. If the host application uses `WebhookMetadata#shop` to select tenant context (e.g., look up a session/access token for that shop, apply data to that shop's records), this crosses tenant boundaries using only the identity binding this gem itself provides — the header, not the signed bytes, decides who the data belongs to.

This matches the report's underlying bug class: an "identity field acted on but not covered by the HMAC" (shop-domain analog of the un-validated nested expression in the Vyper advisory: the value used by downstream logic is not the value validated by the security check).

### Impact Explanation
If the host application (per this gem's documented usage in `docs/usage/webhooks.md`, which shows handlers keying behavior off `WebhookMetadata#shop`) relies on `shop` being authentic once `HmacValidator.validate` returns true, an attacker with control of only their own (unprivileged) shop can produce fully "verified" webhook deliveries impersonating a different shop domain. This can result in cross-tenant data corruption/exfiltration inside the host app (e.g., app records or side effects attributed to the wrong merchant) — a High-severity, cross-tenant identity-boundary break attributable to this gem's own webhook-verification code, not to the host app ignoring documented behavior, since the whole point of `HmacValidator`/`Webhooks::Registry.process` is to certify that the entire request (including `shop`) is authentic.

### Likelihood Explanation
Likelihood is moderate: the attacker needs a legitimate installation of the target app on a shop they control (or one legitimately owned webhook delivery they can capture, e.g. via their own store's outbound logs/proxy), which is realistic for any "unprivileged internet user" who can install a public Shopify app on their own free/dev store. No secrets, tokens, or privileged access are required — only the ability to replay an HTTP request with a modified header, since the header is not part of the signed material.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document that `HmacValidator.validate` only certifies body integrity and that host applications must independently re-verify `shop` (e.g., by confirming the shop has valid session/token state) before performing tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering a real webhook delivery with a valid `x-shopify-hmac-sha256` computed over `raw_body = "{}"` (or any real payload) using the app's shared secret.
2. Attacker intercepts/replays this exact HTTP request to the app's webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` (`Webhooks::Request#to_signable_string`) — this still matches the header value, since the body was untouched: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim.myshopify.com"`, even though the HMAC never certified that value: [6](#0-5) 
5. Any host-app logic keyed on `data.shop` (session lookup, tenant-scoped writes) now operates under the victim shop's identity using attacker-controlled body content.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
