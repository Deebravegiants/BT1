### Title
Crafted `overcapture` QR-code wavelength parameter causes a panic (assertion failure) in `Configuration::parse_wavelength_configuration` - ([File: src/plans/biometric_capture/overcapture.rs])

### Summary
The `overcapture::Plan::from` conversion parses the attacker-controlled `parameters` field of a signup-extension QR code with `parse_u8_octal`, which accepts any valid octal string and returns a `u8` in the full `0..=255` range without bounding it to 3 bits (0-7). This value is later fed into `Configuration::parse_wavelength_configuration`, which formats it as a 3-bit binary string and asserts the resulting string has exactly 3 characters, panicking whenever the parsed value exceeds 7.

### Finding Description
The QR-code regex `QR_CODE_SIGNUP_EXTENSION` in `src/plans/qr_scan/user.rs:39-60` accepts `parameters` matching `[a-z0-9:]+` with no numeric-range validation, and `Data::from_signup_extension` (`src/plans/qr_scan/user.rs:142-157`) stores this raw string as `SignupExtensionConfig.parameters`. When the QR's mode is `SignupMode::Overcapture`, `biometric_capture::overcapture::Plan::from` (`src/plans/biometric_capture/overcapture.rs:107-131`) splits the parameter on `:` and parses the wavelength part with:

```rust
fn parse_u8_octal(src: &str, default: u8) -> u8 {
    u8::from_str_radix(src, 8).unwrap_or(default)
}
``` [1](#0-0) 

Any octal string up to `"377"` (255 decimal) parses successfully, since `u8::from_str_radix` only fails on invalid digits/overflow past `u8::MAX`, not on values `>7`. The resulting `wavelength_parameter` is passed to `Configuration::new` → `Configuration::parse_wavelength_configuration`:

```rust
fn parse_wavelength_configuration(configuration_value: u8) -> VecDeque<IrLed> {
    let binary_repr = format!("{configuration_value:0>3b}");
    assert_eq!(
        binary_repr.chars().count(),
        3,
        "Overcapture wavelength parameter needs to be octal (<=3 bit)!"
    );
    ...
}
``` [2](#0-1) 

For any `configuration_value >= 8` (e.g. octal `"10"` → 8 decimal, binary `"1000"`, 4 characters), the `assert_eq!` fires and panics. This is reachable end-to-end: `Data::try_parse` (feature `internal-data-acquisition`) → `handle_user_qr_code`/`try_parse` accepts the extension QR when signup-extension mode is enabled on either operator or user QR (`src/plans/mod.rs:1060-1083`) → `biometric_capture()` dispatches to `overcapture::Plan::from(plan)` (`src/plans/mod.rs:1204-1207`) → panics inside the `Plan::from` conversion, before any capture even begins.

The `focus_sweep.rs` and `mirror_sweep.rs` extensions contain the identical `assert_eq!`-guarded 3-bit binary formatting pattern (confirmed via grep matches on `assert_eq|binary_repr|parse_wavelength_configuration` in both files), so the same class of crafted-parameter panic likely applies to `SignupMode::FocusSweepExtension` and `SignupMode::MirrorSweepExtension` as well, though the full `SweepConfiguration::new`/`parse_wavelength_configuration` body for those files was not fully read in this session to confirm the exact assertion text.

No validation exists at the QR-parsing layer (`src/plans/qr_scan/user.rs`) or in `Data::from_signup_extension` to reject non-3-bit octal wavelength values before they reach the extension `Plan::from` conversions.

### Impact Explanation
An attacker who presents a crafted signup-extension QR code (requires an `internal-data-acquisition` build with signup-extension mode enabled, per the stated preconditions) can trigger a Rust panic in the async task performing biometric capture, aborting/crashing the in-progress signup and wedging or crashing the capture-extension state machine. This matches the "crash/hang of capture-extension state machine via crafted QR parameters" impact scoped in the question — a denial-of-service against the orb's signup flow via untrusted, unvalidated QR input.

### Likelihood Explanation
Exploitation only requires presenting a single QR code matching `userid:<id>:<policy>::overcapture:<octal>[:<duration>]::` with an octal wavelength value `>= "10"` (decimal 8) to an orb build with `internal-data-acquisition` and signup-extension mode enabled. This is deterministic and 100% repeatable — no timing races, no operator collusion, and no cryptographic material needed. The only precondition is the build feature flag, consistent with the question's stated preconditions.

### Recommendation
Validate `wavelength_parameter` to the range `0..=7` immediately after parsing (e.g., clamp/reject values outside this range and fall back to the `default` instead of panicking), or replace the `assert_eq!` in `parse_wavelength_configuration` with a graceful fallback path (e.g., mask to 3 bits with `configuration_value & 0b111` or return a `Result`/log-and-default) so malformed QR parameters can never cause a panic. Apply the same fix to the equivalent logic in `focus_sweep.rs` and `mirror_sweep.rs`.

### Proof of Concept
Add a unit test in `src/plans/biometric_capture/overcapture.rs` (or an integration test constructing a `biometric_capture::Plan` with a `SignupExtensionConfig`):

```rust
#[test]
fn overcapture_from_crafted_parameter_does_not_panic() {
    let config = qr_scan::user::SignupExtensionConfig {
        mode: qr_scan::user::SignupMode::Overcapture,
        parameters: Some("10:500".to_string()), // octal "10" = 8, out of 3-bit range
    };
    let biometric_plan = biometric_capture::Plan::new(&[], None, Some(config), &Config::default());
    // Expected: no panic; e.g. Plan::from should clamp/default the wavelength parameter.
    let _plan = overcapture::Plan::from(biometric_plan);
}
```
Currently this test panics with `"Overcapture wavelength parameter needs to be octal (<=3 bit)!"` inside `Configuration::parse_wavelength_configuration`, confirming the crash. After the fix, the assertion should be replaced so the test passes without panicking, and a fuzz test over `parameters` strings (empty, `":"`-only, non-numeric, and octal values `0`-`377`) should assert no panic occurs and `overcapture_wavelengths.len() <= 3` (bounded queue) for all inputs.
