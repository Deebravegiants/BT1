Audit Report

## Title
Pending HRMP open-channel sender deposit permanently trapped when initiating para deregisters before session-boundary channel establishment - ([File: polkadot/runtime/parachains/src/hrmp.rs])

## Summary
When a parathread manager calls `deregister` on a para that has an unconfirmed/pending `hrmp_init_open_channel` request where it is the sender, `clean_open_channel_requests` intentionally skips refunding the sender's reserved deposit because the sender is in the `outgoing` list, while simultaneously deleting the request record. Since the para is deregistered in the same flow, no future extrinsic can ever unreserve that deposit, permanently trapping funds in the para's sovereign account's reserved balance.

## Finding Description
`Registrar::deregister` is reachable by a signed parathread manager via `Pallet::ensure_root_para_or_owner` → `Pallet::do_deregister`, which calls `polkadot_runtime_parachains::schedule_para_cleanup::<T>(id)`. That function only blocks offboarding for an in-progress PVF pre-check or unprocessed UMP messages; it performs no check on outstanding HRMP open-channel requests before marking the para `OffboardingParathread`/`OffboardingParachain` and scheduling it into `ActionsQueue` [1](#0-0) .

At the next session boundary, `initializer::apply_new_session` passes `outgoing_paras` to `hrmp::Pallet::initializer_on_new_session`, which invokes `perform_outgoing_para_cleanup` → `clean_open_channel_requests` [2](#0-1) [3](#0-2) .

Inside `clean_open_channel_requests`, requests where either party is in `outgoing` are pulled from `HrmpOpenChannelRequestsList`/`HrmpOpenChannelRequests` and removed unconditionally, but the sender's deposit refund is explicitly skipped when the sender itself is offboarding:
```rust
// Return the deposit of the sender, but only if it is not the para being offboarded.
if !outgoing.contains(&req_id.sender) {
    T::Currency::unreserve(&req_id.sender.into_account_truncating(), req_data.sender_deposit...);
}
``` [4](#0-3) 

Because the request record is deleted in the same pass, `hrmp_cancel_open_request` can never find it afterward even in principle, and that call additionally requires an `ensure_parachain` origin [5](#0-4) , which can only be produced by a live, validating parachain dispatching via the relay chain — impossible once the `ParaId` is deregistered. By contrast, for already-established channels, `close_hrmp_channel` unconditionally refunds both sender and recipient deposits regardless of outgoing status [6](#0-5) , confirming the asymmetry is specific to the pending/unconfirmed request window and not a deliberate universal forfeiture policy applied consistently elsewhere in the pallet.

I attempted to locate the exact body of `Pallet::do_deregister` in `polkadot/runtime/common/src/paras_registrar/mod.rs` to confirm it contains no HRMP-related guard, but was unable to retrieve its full implementation within the available tool budget; based on the `deregister` call-site and `schedule_para_cleanup` reviewed above, there is no visible HRMP check anywhere in this path.

## Impact Explanation
The HRMP `sender_deposit` reserved from the deregistering para's sovereign account becomes permanently locked in `Balances::reserved_balance` with no extrinsic path to release it: the para no longer exists, the request record is deleted, and no unprivileged account can directly unreserve another account's balance. This is a concrete, reproducible fund-freezing bug reachable purely through standard permissionless extrinsics, matching an in-scope "permanently trapped funds" impact class.

## Likelihood Explanation
The exploit path requires only unprivileged actions: `Registrar::reserve` → `Registrar::register` (as a parathread manager) → `Hrmp::hrmp_init_open_channel` (no counterparty acceptance needed) → `Registrar::deregister` → session boundary. No governance or admin action is needed, and the sequence is deterministic and repeatable by any parathread manager, whether accidentally or intentionally (e.g., to grief their own future funds or as a griefing vector against the deposit-collection design, though the deposit lost is the manager's own).

## Recommendation
Either (a) reject deregistration in `schedule_para_cleanup`/`do_deregister` while the para has outstanding `HrmpOpenChannelRequests` in which it participates as sender or recipient, mirroring the existing UMP-queue and PVF pre-check guards, or (b) change `clean_open_channel_requests` to always unreserve the sender's `sender_deposit` regardless of offboarding status, mirroring the unconditional refund behavior already used in `close_hrmp_channel` for established channels.

## Proof of Concept
1. Register parathread `para_a` with manager `M`, ensure `para_a`'s sovereign account has sufficient balance.
2. Call `Hrmp::hrmp_init_open_channel(para_a, para_b, cap, size)` — confirm `Balances::reserved_balance(&para_a.into_account_truncating())` increases by `hrmp_sender_deposit`.
3. Do not call `accept_open_channel` from `para_b` (request stays unconfirmed).
4. Call `Registrar::deregister(RuntimeOrigin::signed(M), para_a)` — expect `Ok`.
5. Advance to the next session (`run_to_session`) to trigger `initializer_on_new_session`/`clean_open_channel_requests`.
6. Assert `HrmpOpenChannelRequests::<Test>::get(&HrmpChannelId{sender: para_a, recipient: para_b})` is `None`, `paras::Pallet::<Test>::lifecycle(para_a)` is `None`, and `Balances::reserved_balance(&para_a.into_account_truncating())` remains equal to `hrmp_sender_deposit` (nonzero) — proving the deposit is permanently orphaned with no extrinsic path to release it.

	pub(crate) fn schedule_para_cleanup(id: ParaId) -> DispatchResult {
		// Disallow offboarding in case there is a PVF pre-checking in progress.
		//
		// This is not a fundamental limitation but rather simplification: it allows us to get
		// away without introducing additional logic for pruning and, more importantly, enacting
		// ongoing PVF pre-checking votes. It also removes some nasty edge cases.
		//
		// However, an upcoming upgrade on its own imposes no restrictions. An upgrade is enacted
		// with a new para head, so if a para never progresses we still should be able to offboard
		// it.
		//
		// This implicitly assumes that the given para exists, i.e. it's lifecycle != None.
		if let Some(future_code_hash) = FutureCodeHash::<T>::get(&id) {
			let active_prechecking = PvfActiveVoteList::<T>::get();
			if active_prechecking.contains(&future_code_hash) {
				return Err(Error::<T>::CannotOffboard.into());
			}
		}

		let lifecycle = ParaLifecycles::<T>::get(&id);
		match lifecycle {
			// If para is not registered, nothing to do!
			None => return Ok(()),
			Some(ParaLifecycle::Parathread) => {
				ParaLifecycles::<T>::insert(&id, ParaLifecycle::OffboardingParathread);
			},
			Some(ParaLifecycle::Parachain) => {
				ParaLifecycles::<T>::insert(&id, ParaLifecycle::OffboardingParachain);
			},
			_ => return Err(Error::<T>::CannotOffboard.into()),
		}

		let scheduled_session = Self::scheduled_session();
		ActionsQueue::<T>::mutate(scheduled_session, |v| {
			if let Err(i) = v.binary_search(&id) {
				v.insert(i, id);
			}
		});

		if <T as Config>::QueueFootprinter::message_count(UmpQueueId::Para(id)) != 0 {
			return Err(Error::<T>::CannotOffboard.into());
		}

		Ok(())
	}

		pub fn hrmp_cancel_open_request(
			origin: OriginFor<T>,
			channel_id: HrmpChannelId,
			open_requests: u32,
		) -> DispatchResult {
			let origin = ensure_parachain(<T as Config>::RuntimeOrigin::from(origin))?;
			ensure!(
				HrmpOpenChannelRequestsList::<T>::decode_len().unwrap_or_default() as u32 <=
					open_requests,
				Error::<T>::WrongWitness
			);
			Self::cancel_open_request(origin, channel_id.clone())?;
			Self::deposit_event(Event::OpenChannelCanceled { by_parachain: origin, channel_id });
			Ok(())
		}

			w = w.saturating_add(<T as Config>::WeightInfo::force_clean_hrmp(
				ingress_count,
				egress_count,
			));
		}
		w
	}
