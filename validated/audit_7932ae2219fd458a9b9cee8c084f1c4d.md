### Title
Rounding-drift underflow in `canGraduate` permanently bricks curve trading and graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
The TensorFlow advisory is a class of bug where a function performs an internal `CHECK`/assert on attacker-influenceable input shape without validating it first, causing an unrecoverable crash instead of a clean error. The alt.fun analog is `Bonding.canGraduate` [1](#0-0) , which performs an unchecked subtraction `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` that is only safe if `assetReserve` never drops below the immutable launch-time virtual LT reserve baseline. `Pair.swap`'s invariant check has an explicit "+1" slack [2](#0-1)  that permits the stored `assetReserve` to legitimately settle a few wei below the mathematically exact constant-product floor after ordinary buy/sell round-trips. When that happens, `canGraduate`'s subtraction underflows and reverts with an arithmetic Panic (`0x11`) instead of the intended boolean/graceful-error result.

### Finding Description
`canGraduate` recovers the launch-time virtual LT reserve from the immutable `Pair.k()`/`TOTAL_SUPPLY()` identity and subtracts it from the live stored `assetReserve`: [3](#0-2) 

This subtraction assumes `assetReserve >= _launchTimeVirtualLtReserve(...)` always holds. That assumption relies on `Pair.swap`'s K-invariant enforcement: [4](#0-3) 

The check is `(newTokenReserve+1) * (newAssetReserve+1) >= k`, not a strict `>= k` on the unshifted reserves. `Router._computeBuy`/`_computeSell` compute `tokensOut`/`assetOut` via floor division against the current stored reserves [5](#0-4) , which rounds every trade slightly in the trader's favor. Because `Pair.swap` validates each new state only against the fixed, immutable `k` (never against the *previous* state's own rounding residue), the "+1" slack lets `assetReserve` settle up to a few wei below the value that `k / tokenReserve` would give at `tokenReserve == totalSupply` (i.e., below the exact `virtualLtReserve` baseline) once `tokenReserve` is driven back up toward `totalSupply` by sells that return previously-bought tokens.

`canGraduate` is not a peripheral view — it is invoked unconditionally on the hot path of both trading entry points:
- every `buy()` via `_executeBuy` [6](#0-5) 
- every `sell()` [7](#0-6) 
- `triggerGraduation()` [8](#0-7) 

So a single underflowing state permanently reverts every subsequent `buy`, `sell`, and `triggerGraduation` call for that token — there is no other entry point to move the token out of `Lifecycle.Curve`.

### Impact Explanation
Once the underflow is triggered, the token is permanently stuck in `Lifecycle.Curve`: no more buys, no more sells, and `triggerGraduation` also reverts (it calls the same `canGraduate`), so the token can never reach `_enterGraduating`/`finalizeGraduation`. All LT already raised on the curve and all curve-held tokens become permanently frozen with no rescue path in `Bonding` (the owner has no function to force-unstick a bricked curve token; only a UUPS upgrade could fix it). This is a permanent freezing of trader and creator funds, satisfying the "Medium/High, concrete freezing" bar.

### Likelihood Explanation
This requires a sequence of buy/sell round-trips (or careful sizing of a single sell) that drives `tokenReserve` back near `totalSupply` while intentionally exploiting the floor-rounding direction so the resulting `assetReserve` sits below the recovered `virtualLtReserve` baseline by at least 1 wei. This is reachable by any unprivileged trader through ordinary `Zap.buy`/`Zap.sell` calls (which route straight through `Bonding.buy`/`Bonding.sell` to `Router._computeBuy`/`_computeSell`/`Pair.swap`), requires no special privileges, and is economically cheap since each round trip only costs the sell/buy fee — well within reach of a determined attacker willing to grief a specific token's curve. The precise number of round-trips needed to accumulate the 1-2 wei drift depends on exact reserve magnitudes and would need on-chain/fork verification to pin down the minimal repro, which I was not able to fully simulate here.

### Recommendation
Make the `canGraduate` (and `previewLtUntilGraduation`) subtraction saturating, mirroring the defensive pattern already used elsewhere in `Bonding` (e.g. `finalizeGraduation`'s comment on saturating subtraction against Panics [9](#0-8) ): treat `assetReserve < _launchTimeVirtualLtReserve(...)` as `realLtRaised = 0` instead of allowing the raw subtraction to underflow. Additionally, consider tightening `Pair.swap`'s K-check (removing or reducing the `+1` slack, or checking against the previous state rather than only the fixed `k`) to eliminate the drift vector at its source.

### Proof of Concept
Conceptual repro (exact minimal round-trip count requires fork-level numeric verification):
1. Launch a token via `Zap.createToken`, establishing `Pair.k = TOTAL_SUPPLY * virtualLtReserve`.
2. Attacker calls `Zap.buy` for some LT amount, receiving tokens (`Router._computeBuy` rounds tokensOut up in the buyer's favor).
3. Attacker immediately calls `Zap.sell` for the exact tokens received, returning `tokenReserve` toward its prior value (`Router._computeSell` rounds `assetOut` up in the seller's favor, extracting slightly more LT than the exact curve value).
4. Because `Pair.swap` only enforces `(tokenReserve+1)*(assetReserve+1) >= k` against the fixed `k`, repeated round-trips (or a single carefully sized trip that lands `tokenReserve` back at `TOTAL_SUPPLY`) can leave the stored `assetReserve` 1+ wei below `Pair.k()/TOTAL_SUPPLY()`.
5. Any subsequent call to `canGraduate(token)` — triggered from `buy()`, `sell()`, or `triggerGraduation()` — executes `assetReserve - _launchTimeVirtualLtReserve(...)`, underflows, and reverts with a Panic, permanently bricking the token's curve.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }
