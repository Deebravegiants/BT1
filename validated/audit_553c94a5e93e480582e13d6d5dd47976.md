**Rationale:**

The `TokenBucket` struct in `rate_limiter.move` is a bare, non-key-having, `copy`+`drop`+`store` value type — it is never stored under a global address on its own, and it deliberately carries no identity field because it's a reusable utility struct, not a custody primitive. [1](#0-0) 

The only framework consumer that ever embedded a `RateLimiter` in a keyed map was `permissioned_delegation::AccountDelegation`, which stored `rate_limiter: Option<RateLimiter>` inside a `BigOrderedMap<DelegationKey, AccountDelegation>` keyed on the delegation's own public key under a specific master account's `RegisteredDelegations` resource — not a shared global map indexed by attacker-controlled identifiers. [2](#0-1) 

Critically, that entire module has been deprecated and gutted: every public function (`add_permissioned_handle`, `remove_permissioned_handle`, `permissioned_signer_by_key`, `handle_address_by_key`, `authenticate`) unconditionally aborts with `EPERMISSIONED_SIGNER_REMOVED`, so there is no live entrypoint through which an unprivileged caller can create, populate, or collide bucket keys in production today. [3](#0-2) 

Since `rate_limiter::request` ( [4](#0-3) ) only ever operates on a `&mut RateLimiter` reference that the *caller* already resolved from storage, any key-collision scenario depends entirely on a hypothetical downstream custody module choosing to key a shared map by attacker-supplied identifiers rather than by verified account address — no such module exists in the current aptos-core framework, and the review bounds require tracing from an actual unprivileged entrypoint into a real custody surface, not a speculative misuse pattern in code that doesn't exist. The lack of an address field in `TokenBucket` is a library-level design choice (analogous to `Option<u64>` having no owner field); the custody obligation to bind buckets to verified addresses belongs to whatever module stores them, and no in-repo module currently does this insecurely.

    public fun request(limiter: &mut RateLimiter, num_token_requested: u64): bool {
        refill(limiter);
        if (limiter.current_amount >= num_token_requested) {
            limiter.current_amount -= num_token_requested;
            true
        } else {
            false
        }
    }
