Based on my investigation, I found a genuine analog in the Hyperbridge EVM host contracts.

### Title
Cross-chain governance `withdraw()` can drain feeToken balance escrowed as relayer fees for pending/undelivered requests - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.withdraw()` transfers an arbitrary amount of `feeToken` (or native token) from the host to any beneficiary, gated only by `restrict(_hostParams.hostManager)`. [1](#0-0)  That balance, however, is not solely "protocol revenue" — it also includes relayer fees escrowed by *any unprivileged caller* via `fundRequest()`, which is fully permissionless and can be called by anyone to top up a pending request's fee. [2](#0-1)  There is no accounting reservation that segregates committed, undelivered relayer fees (`_requestCommitments[commitment].fee`) from the general withdrawable balance.

### Finding Description
Anyone can call `fundRequest(commitment, amount)` on a pending request and it transfers `feeToken` into the `EvmHost` contract, incrementing `_requestCommitments[commitment].fee`. [2](#0-1)  These funds are meant to be paid out to whichever relayer successfully delivers the response/timeout, as seen in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)`, all of which pay `meta.fee`/`fee` straight out of the host's `feeToken()` balance to the relayer or refund the payer. [3](#0-2) 

Separately, `withdraw()` — callable only through cross-chain governance via `HostManager.onAccept`'s `Withdraw` action — moves an arbitrary `amount` of `feeToken` (or native currency) to any `beneficiary`, with no check against `_requestCommitments` totals or any "reserved" balance tracking. [4](#0-3) [5](#0-4)  Because the contract's `feeToken` balance is a shared pool comprising both real protocol revenue and committed-but-undelivered relayer fees/refund obligations, governance withdrawing "protocol revenue" (or simply misconfiguring/overestimating the withdrawable amount) can drain funds that were escrowed by third parties (relayers funding requests via `fundRequest`, or users' `payer` refund entitlements on timeout) — mirroring the original Chainlink report where anyone could permissionlessly fund a resource, but a privileged party could withdraw it regardless of who funded it.

### Impact Explanation
If the withdrawable amount exceeds true protocol-owned revenue (i.e., it includes escrowed relayer fees for requests that are still pending, or funds meant as timeout refunds to a `payer`), governance withdrawal causes:
- Relayers who already delivered work / are waiting to deliver lose their fee, because when they later complete delivery, `safeTransfer` calls in `dispatchIncoming`/`dispatchTimeOut` will attempt to pay out of an insufficient balance and could revert (denial-of-relayer-payment) or, if governance targeted a different token, could otherwise leave insufficient balance.
- Payers who funded requests via `dispatch`/`fundRequest` lose their timeout-refund guarantee.
This is a fund-loss/fund-freezing condition materially identical in class to the reported issue: permissionless deposits made by unprivileged third parties (relayers, requesters) can be swept away by a privileged withdrawal path that has no segregation of "committed" vs "free" balance.

### Likelihood Explanation
The `hostManager`/governance withdrawal path is presumably intended to be trusted (only Hyperbridge parachain governance can dispatch a `Withdraw` action, verified against `request.source.equals(hyperbridge())` and gated by the `admin` relayer key in `HostManager`). [6](#0-5)  This reduces likelihood relative to a fully unprivileged attacker, since it requires governance to withdraw more than true accrued revenue (whether by error or by being compromised). However, because there is no on-chain invariant/accounting preventing withdrawal beyond "true revenue" (host contract does not track total outstanding `_requestCommitments` fees vs free balance), the protocol has no on-chain guarantee that governance withdrawals cannot exceed non-escrowed funds — the safety currently rests entirely on off-chain bookkeeping/trust in the Hyperbridge relayer-fee pallet's accuracy, not a contract-enforced invariant.

### Recommendation
Track the sum of all outstanding (`undelivered`) `_requestCommitments[...].fee` amounts on `EvmHost` (increment on dispatch/fundRequest, decrement on delivery/timeout/refund), and enforce in `withdraw()` that `amount <= feeTokenBalance - totalOutstandingFees` for the `feeToken` case. This makes the escrowed relayer-fee/refund pool for pending requests structurally un-withdrawable by governance, closing the same class of issue as the reported Chainlink LINK-theft bug (permissionless funding + broad privileged withdrawal with no reservation accounting).

### Proof of Concept
1. Relayer/user `A` dispatches a POST/GET request with `fee = 0` (self-relay) via `dispatch()`. [7](#0-6) 
2. Anyone (unprivileged) calls `fundRequest(commitment, X)` to top up the relayer fee for that pending request, transferring `X` feeToken into `EvmHost`. [2](#0-1) 
3. Before the request is delivered, Hyperbridge governance (via `pallet-host-executive`'s `withdraw` call → `HostManager.onAccept` → `EvmHost.withdraw`) withdraws `X` (or more) of `feeToken`, believing it to be accrued protocol revenue, since there's no on-chain distinction. [8](#0-7) [4](#0-3) 
4. When the relayer later delivers the response/timeout for that commitment, `dispatchIncoming`/`dispatchTimeOut` attempts `safeTransfer(relayer/payer, fee)` — with insufficient balance remaining in `EvmHost`, this reverts, freezing the relayer's earned fee or the payer's due refund. [3](#0-2) 

**Note:** I was unable to fully confirm from the indexed code whether the off-chain `pallet-host-executive`/relayer-fee accounting on the Hyperbridge (Polkadot) side reliably prevents governance from ever requesting a withdrawal that exceeds true "free" revenue on each EVM chain — that computation happens off-chain/in a separate pallet whose logic I could not fully trace here. If a Devin session with full repo access confirms that pallet does maintain a strict "free" vs "escrowed" split before issuing withdrawal extrinsics, the severity of this finding should be downgraded to informational, since the missing invariant would then only be a defense-in-depth gap rather than an exploitable path.

            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);

        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;
