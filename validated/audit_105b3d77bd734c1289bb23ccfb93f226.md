Missing try/finally around plaintext wipe in decryptCompressed leaves decrypted secret data resident in memory when gunzip fails - ([File: libraries/secure-container/src/compressed.js])

### Summary
`decryptCompressed` calls `decrypt()` (AES-GCM decryption of the passphrase-protected blob) to obtain `expanded`, then attempts `gunzip(gzipped)` before wiping `databuffer`/`expanded`/`gzipped` with `randomFill`. Because the `gunzip` call and the wipe calls are not wrapped in a `try/finally`, a thrown error from `gunzip` (e.g., corrupted gzip payload) causes the function to exit without ever zeroing the decrypted plaintext buffers.

### Finding Description
`decryptCompressed` at [1](#0-0)  performs:
1. `databuffer = Buffer.from(encryptedData)` — copy of ciphertext.
2. `{ data: expanded, ... } = await decrypt(databuffer, passphrase)` — this fully decrypts the AES-GCM blob (see `decrypt()` in `index.js`, which decrypts the blob key from metadata and then decrypts the ciphertext blob) [2](#0-1) . At this point `expanded` holds the real plaintext (potentially a BIP39 seed / mnemonic / keyval data).
3. `gzipped = expandTo32k ? shrink32k(expanded) : expanded`.
4. `result = await gunzip(gzipped, { format: 'buffer' })` — if the gzip stream is corrupted or attacker-crafted, this throws synchronously/asynchronously.
5. Only *after* a successful `gunzip` does the code call `randomFill(databuffer)`, `randomFill(expanded)`, and conditionally `randomFill(gzipped)` at lines 41-43.

Since there is no `try/finally`, when step 4 throws, execution jumps straight out of the function and the wipe calls at lines 41-43 never execute. `databuffer` (ciphertext copy) and, more critically, `expanded` (decrypted plaintext) remain fully intact and referenced by the caller's local scope/garbage until GC reclaims and the underlying memory pages are overwritten by unrelated allocations — an indeterminate and potentially long window. The encrypt-side sibling function `encryptCompressed` has the analogous ordering issue but is out of scope for this question [3](#0-2) .

No existing guard mitigates this: `decrypt()` itself performs no buffer wiping of its own output, and none of the call sites intercept the thrown error to wipe `expanded` themselves; the unit tests only assert that decryption `rejects` on password/format mismatch, never checking memory hygiene on the corrupted-gzip path [4](#0-3) .

Attacker input reaches this path via any caller that decrypts an attacker-supplied or attacker-tamperable seco container using a valid/known passphrase (e.g. a wallet import/restore flow, or an unlocked session that decrypts a locally cached blob) where the outer gzip layer has been corrupted while the AES-GCM authentication of the outer blob still passes (this requires the corruption to occur inside the plaintext that AES-GCM protects, i.e., the attacker must be able to produce a validly-authenticated encrypted container with a corrupted gzip payload — feasible if the attacker can supply the passphrase-encrypted blob directly, e.g., a QR/import payload, since AES-GCM authentication only certifies integrity of whatever bytes were encrypted, not that those bytes are valid gzip).

### Impact Explanation
If a heap-inspection or memory-dump primitive is later reachable through another surface (e.g., a debug/log/crash-report exporter or a co-resident malicious library reading process memory), the unwiped `expanded` buffer exposes the fully decrypted plaintext (potentially wallet seed/keyval secrets) that should have been ephemeral. This is a secret-disclosure / defense-in-depth failure that extends the disclosure window for sensitive material beyond its intended scope, matching a "secrets stay secret" invariant violation under Hydra's secret-disclosure impact category.

### Likelihood Explanation
Preconditions are narrow but realistic: the attacker must supply (or cause the wallet to load) a seco container that decrypts successfully under a real or session-cached passphrase (i.e., the attacker either knows/controls the passphrase used, or supplies the container to be decrypted by an already-unlocked wallet session with a passphrase-derived key it possesses), while the plaintext-that-should-be-gzip is corrupted. This is achievable by an attacker who can craft/import their own encrypted container (self-authored ciphertext with a corrupted gzip payload inside), which is a normal input path for import/restore flows. The actual "later heap inspection primitive" required to realize disclosure is external and not demonstrated in this codebase, so full end-to-end exploitability depends on that separate primitive existing — reducing but not eliminating likelihood, since the code-level memory hygiene invariant is nonetheless violated and repeatable (deterministic in a unit test).

### Recommendation
Wrap the decrypt-then-decompress logic in `decryptCompressed` (and the compress-then-encrypt logic in `encryptCompressed`) in `try/finally`, ensuring `randomFill(databuffer)`, `randomFill(expanded)`, and `randomFill(gzipped)` (when distinct) execute unconditionally regardless of whether `gunzip`/`gzip` succeeds or throws:
```js
export async function decryptCompressed(encryptedData, passphrase, { expandTo32k = false } = {}) {
  const databuffer = Buffer.from(encryptedData)
  const { data: expanded, blobKey, metadata, header } = await decrypt(databuffer, passphrase)
  const gzipped = expandTo32k ? shrink32k(expanded) : expanded
  try {
    const result = await gunzip(gzipped, { format: 'buffer' })
    return { data: result, blobKey, metadata, header }
  } finally {
    randomFill(databuffer)
    randomFill(expanded)
    if (expanded !== gzipped) randomFill(gzipped)
  }
}
```

Unit test plan:
1. Use `encryptCompressed` to build a valid encrypted container from arbitrary plaintext with a known passphrase.
2. Tamper with the resulting `encryptedData` such that after AES-GCM decryption the recovered bytes are *not* valid gzip but the outer AES-GCM authentication still validates (e.g., construct the plaintext-to-encrypt directly as non-gzip bytes and encrypt with `encrypt()` directly, bypassing `gzip()`, to simulate a corrupted gzip payload post-decryption).
3. Spy/monkey-patch `randomFill` (or wrap `Buffer` in a spy) to record whether it was invoked on the `expanded` buffer.
4. Call `decryptCompressed(tamperedData, passphrase)` and assert it rejects (gunzip failure).
5. Assert that `randomFill` was called on `expanded`/`databuffer` — expected to **fail** with current code (calls never happen), confirming the invariant violation; after applying the `try/finally` fix, assert the wipe calls do occur even though the promise rejects.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
