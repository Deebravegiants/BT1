## Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id` and `api_version` fields are read from separate, unsigned HTTP headers. `Registry.process` accepts any request whose body/HMAC pair is valid and then hands the *header-derived* `shop` value to application webhook handlers as the tenant identity, without that value ever being bound to the cryptographic signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `hmac` field: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which are part of the signed payload: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body integrity) and then dispatches to the handler using `request.shop` as the tenant identity, with no additional binding between `shop` and the signed body: [4](#0-3) 

This breaks the identity equality that a webhook consumer implicitly relies on: `shop authenticated by HMAC == shop used to key the tenant's data/session`. In reality the HMAC only proves `raw_body was signed with api_secret_key`; the `shop` header is uncoupled from that guarantee. An entity that can obtain one legitimate signed body/HMAC pair (e.g. a merchant who installed the app and can observe/replay their own inbound webhook traffic) can resend that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`/`webhook-id`) header to name a different shop. `Registry.process` will pass HMAC validation (body unchanged) and invoke the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, body: <replayed body>, ...)`, causing cross-tenant data to be attributed to, or acted upon under, another merchant's identity.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app-level handler is told a specific shop originated a signed webhook body when in fact only body authenticity, not shop identity, was verified. Any host application that trusts `WebhookMetadata#shop` to select/create/update per-tenant records (a documented, expected usage pattern of this gem) can have another tenant's data associated with, or overwritten under, an arbitrary shop domain — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to have obtained one legitimate signed webhook body+HMAC pair for any topic/shop they control (e.g. their own installed app instance, or a captured webhook delivery), which is realistic for any merchant/developer who installs the target app. No access to `api_secret_key`, access tokens, or the app's `client_secret` is required — only replay of previously-observed traffic with a modified header.

### Recommendation
Bind the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) into the signed payload used for HMAC verification (e.g., include a canonicalized representation of these headers alongside the raw body in `to_signable_string`), or otherwise cryptographically tie the header values to the signature so a replayed body cannot be revalidated under attacker-chosen header values.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` (or otherwise captures one legitimate inbound webhook request+headers destined for the host app).
2. Attacker captures the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` for that webhook (HMAC only covers `B`, per `to_signable_string`).
3. Attacker resends `POST /webhook` to the host app with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body `B` is unmodified.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <parsed B>, ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.
