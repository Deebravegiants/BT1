### Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Event Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, while the `shop` identity that is subsequently handed to the application's webhook handler is read from an HTTP header that is never included in that signature. Any unprivileged party who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the host app on their own store and receiving a real webhook) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, causing the handler to process the event as if it originated from a different (victim) shop.

### Finding Description
`Registry.process` verifies authenticity via `Utils::HmacValidator.validate(request)`, which computes `HMAC(api_secret_key, request.to_signable_string)` and compares it to the received signature [1](#0-0) . Critically, `Request#to_signable_string` returns only the raw body — it does not include `topic`, `shop-domain`, `webhook-id`, or `api-version` [2](#0-1) . Meanwhile `Request#shop` is read directly and unauthenticated from the `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) , and `process` forwards this unauthenticated value straight into the dispatched `WebhookMetadata` used by the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop ∥ topic)`, i.e., the signature should bind the shop attribution to the signed bytes. Instead the actual binding is `hmac == HMAC(secret, body)` while `shop` is taken from `parsed(headers)`, a completely separate, unauthenticated channel. Because `api_secret_key` is shared across all shops installing the app (not shop-specific), any shop where the app is installed — including one controlled by an unprivileged attacker who simply installs the app on their own dev/trial store — will receive real, validly-HMAC'd webhook deliveries. The attacker can capture that body+HMAC pair and re-POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `x-shopify-topic` header changed, since topic is likewise unsigned). `HmacValidator.validate` still succeeds because it only checks the (unmodified) body signature, and the handler is invoked believing the event legitimately came from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook processing: an attacker with no privileges beyond installing the app on their own store can inject events attributed to a shop they do not control. Depending on how the host application acts on `WebhookMetadata#shop` (e.g., `customers/redact`, `app/uninstalled`, `shop/redact`, or order/customer data handlers keyed by shop), this can drive cross-tenant data mutation, spoofed compliance/redaction actions against a victim's data, or injection of forged business events under another merchant's identity — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app author who trusts `WebhookMetadata#shop` for authorization or data-scoping decisions in their handler (which is the documented intended use, since `Registry.process` provides no other authenticated shop value). No credentials beyond installing the app on an attacker-owned shop are required, and HTTP header replay/tampering is trivial for any client capable of sending arbitrary POST requests to the app's publicly-reachable webhook endpoint.

### Recommendation
Include the shop domain (and topic/webhook id) in the HMAC signable string, e.g. change `Request#to_signable_string` to bind `shop-domain`/`topic`/`webhook-id` alongside the body (matching Shopify's webhook signing scheme if it supports a canonical string), or, at minimum, document/enforce that consumers must not treat `WebhookMetadata#shop` as authenticated unless verified independently (e.g., cross-checked against a shop known to have valid registration/session state) before acting on it.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app registers for (e.g. `orders/create`).
2. Capture the resulting POST: raw body `B`, and header `x-shopify-hmac-sha256` = `HMAC_SHA256(api_secret_key, B)` (valid, since `api_secret_key` is shared).
3. Replay this exact body `B` and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and any desired `x-shopify-topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B)` [5](#0-4) ; the handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [6](#0-5) , causing the app to act on forged data attributed to the victim shop.
