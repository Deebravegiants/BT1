### Title
Unchecked i128 overflow in ray-value accrual permanently freezes a whale market before the borrow-index cap can engage - (File: contracts/pool/src/interest.rs)

### Summary
`global_sync` runs inside every mutating pool verb (`supply`, `borrow`, `withdraw`, `repay`, `seize_positions`, `flash_loan`, `recapitalize`) and calls `accrue_step` (in `common::rates`) to grow `borrow_index`/`supply_index`. The rescale from scaled shares to original value (`scaled_to_original`) panics with `MathOverflow` once `borrowed * rate_value` exceeds the `i128` ray ceiling. That ceiling is hit **before** the `MAX_BORROW_INDEX_RAY` cap engages, so the panic is not a designed bound — it is an unhandled crash in the shared accrual path. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves the crash happens first and that `withdraw` and `repay` both revert afterwards. [1](#0-0) [2](#0-1) 

### Finding Description
- `Cache::load` → `interest::global_sync` is the first step of every market mutation, per the documented flow `entrypoint → Cache::load → interest::global_sync → mutate → guards → commit`. [3](#0-2) 
- `global_sync` splits elapsed time into `MAX_COMPOUND_DELTA_MS` chunks and calls `accrue_chunk`, which invokes `accrue_step(env, params, borrowed, supplied, borrow_index, supply_index, delta_ms)` and unconditionally writes the new indexes. [4](#0-3) 
- `accrue_step` must unscale `borrowed` (RAY-scaled shares) to a token value to apply the rate. For a large market — e.g., ~1e9 × 10^18 base units at ~98% utilization on a steep curve — the index passes ~170x within a few years and the ray-value product overflows `i128`, raising `MathOverflow` instead of clamping at `MAX_BORROW_INDEX_RAY`. [2](#0-1) 
- Because `borrow_index` is monotone non-decreasing and the accrual is recomputed from persisted state on every call, once the product overflows it overflows on **every subsequent call**: there is no amount of waiting or partial interaction that avoids the panic. `borrow`, `repay`, `withdraw`, `liquidate`/`seize_positions`, `flash_loan`, `recapitalize`, and `update_indexes` all trap in `global_sync` before doing any work. [5](#0-4) [6](#0-5) 

This is the analog of CVE-2017-11522's null-deref crash on a crafted input: an attacker crafts **market state** (a huge supply book at sustained near-total utilization) through ordinary permissionless verbs, and the shared accrual code dereferences an out-of-domain numeric invariant, crashing every future entrypoint for that market.

### Impact Explanation
Permanent freezing of funds for the affected `(hub, token)` market: once the overflow state is reached, no supplier can withdraw, no borrower can repay, no liquidator can seize, and `recapitalize` also accrues first and panics. All `cash` held by the pool for that market — every depositor's balance — becomes unreachable, and any controller position depending on that market is bricked. This is the "permanent freezing of funds" / "contract unable to operate" acceptance class, not a fail-closed single-transaction revert. [7](#0-6) 

### Likelihood Explanation
Reaching the cliff requires a market with a very large scaled book: on the order of a billion units of an 18-decimal asset supplied and ~98% borrowed, held at the steep segment of the rate curve for multiple years. The capital requirement is extreme for major assets but feasible for low-priced, high-decimal tokens where a billion units is cheap; the attacker only needs permissionless `supply`/`borrow`/`update_indexes` calls and can pre-position the state early in a market's life so the freeze lands years later with no further attacker action. The precondition that `max_utilization` does not cap utilization below the cliff depends on market parameters; the demonstrating test disables the max-utilization guard, so on markets where that cap is set conservatively the attack is harder. Two further caveats: (1) the trigger is multi-year, so it is a slow, planted DoS rather than an immediate exploit; (2) the repository already contains a test asserting the `MAX_BORROW_INDEX_RAY` bound in `docs/reference/formulas.md` is wrong, indicating partial awareness — but the code remains unpatched and the crash is reachable rather than a documented accepted behavior. Medium severity is appropriate given the permanence of the freeze and the high setup cost.

### Recommendation
- Clamp inside the accrual path, not outside it: in `accrue_step` (common/src/rates.rs), cap the unscaled borrow/supply value or short-circuit the step when `borrowed` exceeds `i128::MAX / rate`, so `borrow_index` saturates at `MAX_BORROW_INDEX_RAY` instead of panicking.
- Alternatively, make `global_sync` bound `borrow_index` to `MAX_BORROW_INDEX_RAY` before performing value rescales, so the designed cap actually engages before the i128 ceiling.
- Add a regression test asserting that after the index cap engages, `withdraw`, `repay`, and `seize_positions` still succeed on a whale market — the current test only asserts the panic. [4](#0-3) 

### Proof of Concept
Reproduced by the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`: [8](#0-7) 

1. Create an 18-decimal market on the XLM rate curve; lift its supply/borrow caps and disable max-utilization.
2. Attacker supplies `principal = 10^9 * 10^18` base units, then supplies collateral and borrows ~98% of `principal` — all via permissionless `Controller::supply`/`borrow`.
3. Advance time; call `Controller::update_indexes` (or any verb) periodically. At the steep segment the index grows past ~170x, and `accrue_step` panics with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Verify permanence: `try_withdraw` and `try_repay` both return `MathOverflow` — every exit path accrues first and hits the same panic, permanently freezing all pool cash in that market.

Uncertainty note: I could not read `common/src/rates.rs::accrue_step`/`scaled_to_original` to cite the exact overflowing expression; the test attributes the panic to `scaled_to_original` inside accrual, and the fix should target that multiplication regardless of its exact line.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
```
