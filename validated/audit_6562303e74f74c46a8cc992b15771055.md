### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain HTTP header reads, while `to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes and compares the HMAC exclusively over `to_signable_string` (the raw body) against the `hmac` header [2](#0-1) . `Registry.process` accepts the request once this body-only HMAC check passes, then hands `request.shop` straight to the app's handler as the tenant identifier for the event [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop header used to route/attribute the webhook == shop the signed bytes were actually generated for`. Because `HmacValidator` only signs `@raw_body` and never incorporates the `shopify-shop-domain` / `x-shopify-shop-domain` header into the signable string, the equality does not hold — the HMAC proves the body's integrity but proves nothing about which shop the header claims it came from.

Any party capable of triggering (or previously capturing) one genuine webhook delivery for a shop they control — the `api_secret_key` is shared by Shopify across every shop that has the app installed, so this requires no privileged access to the app's secret — can take that valid `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop. `HmacValidator.validate` still returns `true` because it only re-derives the HMAC from `raw_body`, and `Registry.process` will invoke the app's handler with `WebhookMetadata` built from `request.shop` (the attacker-controlled header) and `request.parsed_body` (the original, validly-signed body) [3](#0-2) . This is the classic "bytes verified versus bytes parsed" mismatch: the bytes verified are the body only, but the identity field actually acted upon (`shop`) is parsed from unauthenticated headers.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as returned by this gem) to decide which tenant's records to create, update, or delete — the documented and expected use of this field — an attacker who can obtain one legitimately-HMAC-signed webhook body (from their own installed shop) can relabel it and have the app process it as belonging to an arbitrary other shop, causing cross-tenant data manipulation without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any app author following the gem's own `WebhookMetadata`/`Registry.process` contract, since the vulnerable field (`shop`) is the exact field the gem hands to handlers for tenant attribution, and no additional privilege beyond controlling one's own installed shop (to generate one authentic, replayable payload) is required. It does not depend on the host ignoring documented behavior — it depends on the host trusting the field the gem itself exposes as `WebhookMetadata#shop`.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the HMAC-signed content, or independently authenticate the shop claim against a known-installed shop record before dispatching to handlers, so that the shop identity used for routing is cryptographically bound to the same bytes verified by `HmacValidator`.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a real webhook (e.g., `orders/create`) to the app's endpoint with a valid `x-shopify-hmac-sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
2. Attacker captures this `(raw_body, hmac_header)` pair.
3. Attacker POSTs the same `raw_body` and `hmac_header` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it (all three required headers present) [4](#0-3) .
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the (unchanged) `hmac` [2](#0-1) .
6. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body content, even though that body was never generated for the victim shop [3](#0-2) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
