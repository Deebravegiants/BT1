### Title
Job-Scoped Pipeline Run Endpoint Ignores Job ID, Allowing Cross-Job Run Data Disclosure (BOLA) - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PipelineRunsController.Show` handler is routed at `GET /v2/jobs/:ID/runs/:runID`, implying the run is scoped to the named job. In practice the handler discards the `:ID` (job) URL parameter entirely and fetches the pipeline run using only the `:runID` value, with no check that the returned run actually belongs to the job named in the path. This is the same root-cause pattern as the Vikunja finding: an authorization/routing surface implies scoping by one identifier (task ID / job ID) while the actual record lookup is keyed exclusively by an attacker/caller-controlled sequential ID (attachment ID / run ID), producing cross-resource response confusion.

### Finding Description
`Show` is defined as: [1](#0-0) 

It parses only `c.Param("runID")` into `pipelineRun.SetID(...)` and calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)` — the job ID from the URL (`c.Param("ID")`) is never read or validated against the run's actual `JobID`. This mirrors the Vikunja `GetTaskAttachment`/`ReadOne` flaw exactly: the URL/route implies a resource is scoped under a specific parent (task → attachment; job → run), but the actual data-fetch keys only off the child ID, so any caller who can reach the `Show` endpoint with a valid `runID` can retrieve run data regardless of which `jobID` segment they supply in the path (including a job ID they are nominally authorized to view, per the Vikunja "specify a task you CAN access but an attachment ID from elsewhere" trick).

By contrast, `Index` — which lists runs — correctly scopes by job ID via `prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)`: [2](#0-1) 
This inconsistency (list is job-scoped, show is not) is itself evidence that job-scoping was intended for this API surface but not implemented on the single-record lookup path.

### Impact Explanation
`pipeline.Run` records can contain sensitive information: task inputs/outputs, bridge request/response bodies, and error details tied to a job's execution. `FindRun` performs no ownership or job-membership check: [3](#0-2) 
Any authenticated caller who can enumerate or guess a `runID` (sequential integer, same class of weakness as Vikunja's sequential attachment IDs) can pull run details for jobs outside the one they navigated to via the URL. In a node instance where API access is intended to be partitioned per job/team (e.g., multi-tenant CRE or feeds-manager-provisioned jobs), this allows cross-job/cross-tenant disclosure of run data — a direct analog to the report's "cross-user response confusion" impact category.

### Likelihood Explanation
Exploitation requires only a valid authenticated session capable of reaching `GET /v2/jobs/:ID/runs/:runID` (any role, since this is a plain GET), and knowledge/guessing of a `runID` — trivial given runs are created with monotonically increasing integer IDs. No special privilege escalation, extra tokens, or race conditions are needed, making this a low-effort, high-reliability path once a target `runID` is known.

### Recommendation
Modify `Show` to resolve the job ID from `c.Param("ID")` and verify the fetched run's `JobID` matches it (mirroring the fix recommended for Vikunja's `ReadOne`: add the parent-scoping predicate to the lookup, e.g. `FindRun(ctx, jobID, runID)` or fetch-then-compare `pipelineRun.JobID == jobID`), returning 404 on mismatch. Apply the same scoping check to `Create`'s `respondWithPipelineRun` helper if it can be reached with a mismatched job/run pairing.

### Proof of Concept
1. As an authenticated node user, create/find any job you have URL access to (`jobA`), and separately note that another job (`jobB`) has produced pipeline run `runID=1234`.
2. Send `GET /v2/jobs/{jobA}/runs/1234`.
3. `Show` ignores `jobA` and calls `FindRun(ctx, 1234)`, returning the full run resource that actually belongs to `jobB`, disclosing its execution details, task outputs, and any embedded bridge responses. [4](#0-3)

// Index returns all pipeline runs for a job.
// Example:
// "GET <application>/jobs/:ID/runs"
func (prc *PipelineRunsController) Index(c *gin.Context, size, page, offset int) {
	id := c.Param("ID")

	// Temporary: if no size is passed in, use a large page size. Remove once frontend can handle pagination
	if c.Query("size") == "" {
		size = 1000
	}

	var pipelineRuns []pipeline.Run
	var count int
	var err error

	ctx := c.Request.Context()
	if id == "" {
		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, nil, offset, size)
	} else {
		jobSpec := job.Job{}
		err = jobSpec.SetID(c.Param("ID"))
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, err)
			return
		}

		pipelineRuns, count, err = prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)
	}

	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResources(pipelineRuns, prc.App.GetLogger())
	paginatedResponse(c, "pipelineRun", size, page, res, count, err)

// Show returns a specified pipeline run.
// Example:
// "GET <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
