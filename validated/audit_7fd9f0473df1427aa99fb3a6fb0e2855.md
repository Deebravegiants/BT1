This confirms the vulnerability: `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-190`) only calls `Utils::HmacValidator.validate(request)` before dispatching, and `HmacValidator` computes the signature over `request.to_signable_string`, which for `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb:35-38`) is only the raw HTTP body (`@raw_body`). The `shop` field returned by `request.shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:20-23`), which is never included in the HMAC-signed bytes, yet it is trusted and forwarded verbatim into `WebhookMetadata` (`lib/shopify_api/webhooks/webhook_handler.rb:6-11`) that host apps use to attribute the webhook to a specific merchant/tenant, as documented in `docs/usage/webhooks.md:12-14`.

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `X-Shopify-Shop-Domain` HTTP header, but `to_signable_string` (used by `HmacValidator`) only signs the raw body. Any party able to reach the app's public webhook endpoint with a body/HMAC pair valid for their own shop can substitute a different `shop-domain` header, and `Registry.process` will accept it as authentic and hand the forged shop identity to the app's handler.

### Finding Description
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) performs exactly one authenticity check: `Utils::HmacValidator.validate(request)`. That validator (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value. For webhooks, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`) — it does not include any headers. Meanwhile `request.shop` is read directly, unauthenticated, from `x-shopify-shop-domain`/`shopify-shop-domain` (`lib/shopify_api/webhooks/request.rb:20-23`), and that same header-derived value is passed straight through into `WebhookMetadata.shop` (`lib/shopify_api/webhooks/webhook_handler.rb:6-11`), which the gem's own documentation tells integrators to use as "The shop domain of the webhook" for routing/attribution (`docs/usage/webhooks.md:12-14`).

The identity binding that should hold is: `shop header value == shop the HMAC was computed for`. Because the HMAC only covers the body, this binding is never enforced. Since the same `api_secret_key` is shared across all shops that have the app installed, any legitimate (but otherwise unprivileged, from another tenant's perspective) merchant who has genuinely installed the app can obtain a body+HMAC pair that is valid under the app's secret (e.g., by triggering a real webhook delivery from their own store, or by controlling body content that Shopify signs on their behalf), then resend that exact body/HMAC to the app's public webhook endpoint while swapping the `shop-domain` header to a victim shop. `HmacValidator.validate` still returns `true` because the bytes it checks (`@raw_body`) are unchanged, and `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop.

### Impact Explanation
This breaks tenant isolation: an attacker-controlled webhook payload can be attributed to an arbitrary victim shop domain, letting a request forged by one tenant be processed as if it belonged to another. Any host application logic that uses `data.shop` to select which merchant's session/store/data to act on (exactly as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into applying attacker-supplied webhook data to a different, unrelated merchant's account — a cross-tenant access/confusion condition.

### Likelihood Explanation
Exploitation requires only: (1) the attacker have the app installed on some shop of their own (a normal, unprivileged onboarding action, not a leaked secret or privileged account), and (2) the ability to send an HTTP POST directly to the app's public webhook route with attacker-chosen headers — both trivially available to any internet user who can install the app. No access to `api_secret_key`, tokens, or TLS interception is needed, since the raw body/HMAC pair the attacker replays was legitimately produced by Shopify for the attacker's own shop.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before trusting `request.shop` inside `WebhookMetadata`. At minimum, document/require that consuming apps independently verify `request.shop` corresponds to a shop with an active session/installation before acting on webhook data, but the stronger fix is to make `Webhooks::Request#to_signable_string` and `HmacValidator` cover the shop-domain header explicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (legitimate self-service action), obtaining a working installation that shares the app's single `api_secret_key` across all shops.
2. Attacker triggers a real webhook (e.g. `orders/create`) from their own shop, capturing the POST Shopify sends to the app's registered callback URL: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this is valid per `lib/shopify_api/utils/hmac_validator.rb:33-39`.
3. Attacker crafts a new POST request to the same public webhook endpoint using the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` parses this into a `Webhooks::Request`; `HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/webhooks/registry.rb:189-190`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to act on the victim shop using attacker-controlled body content.
