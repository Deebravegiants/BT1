### Title
`CookieJar.set` forwards attacker-controlled `domain` to native store without origin scoping - ([File: modules/networking-mobile/src/cookie/cookie-jar.ts])

### Summary
`CookieJar.set` calls `validate(cookie)` before forwarding the cookie to the native store, but `validate` only checks `name` and `value`, never `domain`. The `assertMatchingDomain` function exists specifically to enforce that a cookie's `domain` matches the requesting origin's URL, but it is exported and never invoked anywhere in `validate` or `CookieJar.set`.

### Finding Description
`validate` in [1](#0-0)  only runs `validateName` and `validateValue`, leaving `domain`, `path`, and `protocol` completely unchecked. `CookieJar.set` in [2](#0-1)  calls `validate(cookie)` and then immediately forwards the cookie via `asNativeCookie(cookie)` to `this.store.set(url, asNativeCookie(cookie), true)`. `asNativeCookie` in [3](#0-2)  spreads all the cookie's fields including `domain` directly into the native cookie object, so whatever `domain` value the caller supplied is passed straight to the native cookie store (`@react-native-cookies/cookies`).

`assertMatchingDomain`, defined in [4](#0-3) , implements RFC 6265 §5.1.3-style domain matching and is designed precisely to reject a `domain` that is a third-party origin relative to the request URL's host, or that spans an subdomain the caller shouldn't be able to set. It is exported from the module (`export { validate, assertMatchingDomain }`, line 74) and re-exported from `modules/networking-common/src/cookie/index.ts` [5](#0-4) , but a repo-wide search confirms it is referenced only in `validators.spec.ts` test file — never called from `validate()`, `CookieJar.set()`, or any other production code. There is also no wrapper/decorator class instantiating `CookieJar` with additional origin checks; the only production consumer directly calls `new CookieJar(OperatingSystem.iOS/Android)` without further validation.

As a result, any caller (e.g. a wallet-embedded browser or dapp-facing bridge that lets a page request a cookie be set) that supplies a `Cookie` object with a `domain` field pointing to an unrelated host will have that domain honored by the native cookie store, since neither `validate` nor `set` cross-checks `domain` against the `url` parameter.

### Impact Explanation
An unprivileged origin/dapp that can trigger `CookieJar.set` with attacker-controlled cookie fields (as opposed to only a raw `Set-Cookie` string, which is parsed from the actual response) can plant or overwrite cookies scoped to a domain different from its own origin. This breaks connected-origin/session isolation for other sites/dapps that rely on cookie-based state (e.g. auth session cookies, CSRF tokens, feature flags) inside the wallet's networking layer, potentially enabling session fixation or cookie-tossing style attacks against a different origin trusted by the wallet.

### Likelihood Explanation
The vulnerable code path is reached whenever `CookieJar.set` is called with a `Cookie` object (not a raw string) whose `domain` differs from the `url` argument's host — this requires no privileged state, keys, or social engineering, only that some caller (e.g., a webview/dapp bridge) passes through attacker-supplied cookie object fields. The bug is deterministic and repeatable: every call with a mismatched `domain` will pass `validate()` unmodified and be forwarded to `store.set`.

### Recommendation
Call `assertMatchingDomain(cookie.domain, new URL(url).hostname)` (or equivalent) inside `CookieJar.set` before invoking `this.store.set`, or fold this check into `validate` by threading the origin URL through. Reject/throw when `cookie.domain` does not match or is not a valid sub/superdomain relationship per the existing `assertMatchingDomain` semantics.

### Proof of Concept
Integration test extending `modules/networking-mobile/src/cookie/cookie-jar.spec.ts`:
```ts
import CookieJar from './cookie-jar'
import { OperatingSystem } from '../shared/types'

test('rejects cookie with cross-origin domain', async () => {
  const mockStore = {
    set: jest.fn(),
    get: jest.fn(),
    getAll: jest.fn(),
    clearAll: jest.fn(),
    setFromResponse: jest.fn(),
  } as any
  const jar = new CookieJar(OperatingSystem.iOS, mockStore)

  await expect(
    jar.set(
      { name: 'session', value: 'abc', domain: 'attacker-controlled-other-origin.com' },
      'https://legit-dapp.example.com'
    )
  ).rejects.toThrow()

  expect(mockStore.set).not.toHaveBeenCalled()
})
```
Expected (current, failing) behavior: `mockStore.set` is called with `domain: 'attacker-controlled-other-origin.com'`, no error thrown. Expected (fixed) behavior: the promise rejects and `mockStore.set` is never invoked.

```typescript
function assertMatchingDomain(domain: string | undefined, originDomain: string) {
  if (domain === undefined) return

  // Domain matching: https://datatracker.ietf.org/doc/html/rfc6265#section-5.1.3
  if (domain === originDomain) return

  if (isSubdomain(domain, originDomain)) {
    throw new Error(
      `Cannot set a cookie for a subdomain. Tried to set ${domain} with origin ${originDomain}`
    )
  }

  if (isSubdomain(originDomain, domain)) {
    return
  }

  throw new Error(
    `Cannot set a cookie for a third party origin. Tried to set ${domain} with origin ${originDomain}`
  )
}
```

```typescript
  async set(cookie: string | Cookie, url?: string): Promise<void> {
    if (!url) {
      throw new Error('Host is required')
    }

    if (typeof cookie === 'string') {
      await this.store.setFromResponse(url, cookie)
      return
    }

    validate(cookie)

    await this.store.set(url, asNativeCookie(cookie), true)
  }
```
