This report addresses the potential vulnerability of missing `disableInitializers()` calls in upgradeable contracts, which could allow re-initialization of implementation contracts. The `AuditingProject/AllProjects` repository contains a record of a systematic scan that specifically looked for this issue, identifying 314 implementations across various projects that lacked `_disableInitializers()`. 

### Title
Missing `_disableInitializers()` Call in Upgradeable Contracts - (Multiple Projects)

### Summary
A systematic scan identified 314 upgradeable contract implementations across various projects within the `AuditingProject/AllProjects` corpus that do not call `_disableInitializers()` in their constructors.  While the classic attack vector of bricking proxies via `selfdestruct` is mitigated by OpenZeppelin's `onlyProxy` guard and post-Dencun Ethereum changes, this oversight still allows an attacker to take ownership of an implementation contract's empty storage. 

### Finding Description
The vulnerability arises when an upgradeable contract, inheriting from an `*Upgradeable`/`Initializable` base and declaring an `initializer`/`reinitializer` function, does not include a call to `_disableInitializers()` in its constructor.  This leaves the implementation contract susceptible to direct initialization, allowing an attacker to become its owner. 

### Impact Explanation
The direct initialization of an implementation contract by an attacker allows them to gain ownership of that contract's storage.  Although the ability to brick associated proxies via `selfdestruct` is largely mitigated by OpenZeppelin's `onlyProxy` guard (present in versions 4.3.2 and later) and post-Dencun Ethereum changes,  the attacker's control over the implementation's storage could still be problematic if that address is later granted privileges or sent value.  This is considered a hygiene finding rather than a direct fund-loss vulnerability. 

### Likelihood Explanation
The likelihood of this issue is high, as a systematic scan identified 314 instances across the corpus.  The issue is a common oversight in upgradeable contract development.

### Recommendation
It is recommended to include a call to `_disableInitializers()` in the constructor of all upgradeable logic contracts. This prevents unauthorized initialization of the implementation contract, even if the direct impact is currently limited.  For projects that already apply this guard in other contracts, its absence in some indicates an inconsistency that should be addressed. 

### Proof of Concept
A scanner, `_hunt2/initscan.py`, was developed to identify this vulnerability.  It searches for concrete contracts that inherit from `*Upgradeable`/`Initializable` bases, declare `initializer`/`reinitializer` functions, but do not call `_disableInitializers()`. 

Examples of projects with such instances include:
*   **listadao**: 4 UUPS contracts missed `_disableInitializers()`, despite 285 other contracts being protected.  Specific examples include `PumpBTCProvider.sol` and `mBTCProvider.sol`. 
*   **velvetcapital**: 13 unprotected implementations, including `FeeModule` and `AssetManagerConfig`, which are live on-chain. 
*   **katana**: 3 unprotected implementations, including `DefaultStrategy`. 
*   **account-abstraction-bugs**: 6 unprotected implementations. 
*   **gammaswap**: 12 unprotected implementations.
