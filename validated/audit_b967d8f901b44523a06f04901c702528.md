## Analysis

`SimplexPaymaster.sol` prices ERC-20 gas payments and fee-recycling swaps directly from Chainlink `AggregatorV3Interface.latestRoundData()`, validating only positivity and staleness — it has no L2 sequencer-uptime check, matching the report's bug class exactly, and it is deployed on Arbitrum/Optimism/Base per `evm/config.testnet.toml` and `evm/script/DeploySimplexPaymaster.s.sol` (the SDK's `CHAINLINK_PRICE_FEED_CONTRACT_ADDRESSES` also lists Arbitrum/Optimism/Base mainnet feeds).

### Title
Missing L2 sequencer-uptime check on Chainlink price feeds lets `SimplexPaymaster` price gas off stale/incorrect data during Arbitrum/Optimism/Base sequencer downtime - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` is an ERC-4337 paymaster, deployed to Arbitrum, Optimism, and Base (all OP-Stack/Arbitrum L2s with a sequencer), that converts ERC-20 stablecoin gas payments and fee-recycling swaps into native-asset cost using Chainlink `AggregatorV3Interface` feeds. `_getOraclePrice` only checks `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`; it never verifies the Chainlink L2 sequencer-uptime feed (`0xBCF85224fc0756B9Fa45aA7892530B47e10b6433`-style feed for Arbitrum, and the equivalent Optimism/Base feed) as Chainlink's docs mandate for L2 deployments. [1](#0-0) 

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used throughout pricing: [2](#0-1) 

It is invoked from `_tokenPrice` (used by `_fetchDetails`, which runs on every UserOp validated by the EntryPoint) and from `swapAndDeposit` (fee recycling): [3](#0-2) [4](#0-3) 

On Arbitrum/Optimism/Base, if the sequencer goes down, transactions still land on L2 once the sequencer resumes or via forced inclusion, but during the outage window the last Chainlink update recorded on that L2 can remain within `maxOracleAge` of the (locally computed) `block.timestamp` while the *true* off-chain market price has since diverged materially — this is precisely the failure mode Chainlink's L2 sequencer-feed guidance exists to catch, and which the staleness-only check here cannot detect. `_fetchDetails` is reached by any bandwidth-purchasing UserOp sender through the ERC-4337 EntryPoint's normal validation flow, with no privileged caller required: [5](#0-4) 

### Impact Explanation
An attacker (or any user racing the outage window) can submit UserOps priced against a stale-but-"fresh" oracle answer to pay for gas at a favorable rate, draining the paymaster's stablecoin reserves relative to its native-asset EntryPoint deposit/stake, or conversely overcharging honest users. The same stale price feeds into `swapAndDeposit`'s `amountOutMin` computation, letting a sandwich attacker extract value from the treasury-triggered swap since the on-chain "expected" price no longer reflects reality. This is a direct fund-loss vector against the paymaster's treasury and EntryPoint stake, which only governance can otherwise access.

### Likelihood Explanation
L2 sequencer downtime is an infrequent but recurring, publicly observable event on Arbitrum/Optimism/Base, and the vulnerable window (from sequencer halt until the next Chainlink round update after resumption) is exploitable by any unprivileged UserOp sender with no special access — only permissionless gas-payment transactions are needed, making this a Medium-severity, externally-triggerable issue whenever a sequencer outage coincides with market volatility.

### Recommendation
Add the Chainlink L2 sequencer-uptime feed check (per-chain `AggregatorV3Interface` sequencer feed address, checked via `latestRoundData()` for `answer == 0` and a grace period after `startedAt`) as a precondition in `_getOraclePrice`, reverting (or falling back safely) whenever the sequencer is reported down or within the recommended grace period after recovery, for every L2 deployment of `SimplexPaymaster`.

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum One with `nativeOracle`/`tokenOracle` set to the chain's Chainlink feeds, per `evm/script/DeploySimplexPaymaster.s.sol`.
2. Simulate an Arbitrum sequencer outage during which the underlying market price of the native asset or gas token moves significantly off the last on-chain Chainlink update, while `updatedAt` for that last round remains within `maxOracleAge` of `block.timestamp` once transactions resume.
3. Submit a UserOp with `paymasterData` selecting the mispriced token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:662-676`) accepts the stale round because only `answer > 0` and heartbeat-staleness are checked, with no sequencer-uptime gate.
4. The UserOp is charged at the stale rate, extracting value from the paymaster's reserves versus the true market rate — repeatable for every UserOp submitted during the outage/recovery window.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
