### Title
Unverified alignment between `order.inputs` and `order.output.assets` in `_fillSameChain` can permanently strand escrowed input tokens - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` iterates over `order.output.assets` (length `outputsLen`) but uses the *same* loop index `i` to read `order.inputs[i]` when computing escrowed amounts to release, exactly the "two arrays assumed aligned, but never checked" pattern from the reported `LiquidationRow._performLiquidation` issue.

### Finding Description
In `_fillSameChain`, the fill loop is bounded by the output-asset array length: [1](#0-0) 

but inside that same loop, the code reads from the *inputs* array using the output-loop index `i`, assuming index `i` of `order.inputs` is the escrow leg paired with output leg `i`: [2](#0-1) 

Nowhere in `_fillSameChain`, nor in the shared base contract `IntentsBase.sol` (`_withdraw`, `_execute`, `_sweepDust`, `_validateParams`, etc., all reviewed in full), is there a check that `order.inputs.length == order.output.assets.length`. `Order` is user-supplied calldata at `placeOrder` time, so unless `IntentGatewayV2.sol`'s `placeOrder` enforces this equality (which I was **not able to confirm** within my remaining tool budget — this is the one open question in this analysis), a user can construct an order where `order.inputs.length > order.output.assets.length`.

If that mismatch is allowed:
- The loop only ever touches `order.inputs[0..outputsLen)` when building `escrowedInputs`, so any input legs at indices `>= outputsLen` are never included in the `WithdrawalRequest` passed to `_withdraw`.
- On a full fill, `_filled[commitment]` is set and the order can never be filled or cancelled again (`cancelOrder`/`_cancelSameChain` requires the order not already filled).
- The escrow balance for those un-referenced input tokens (`_orders[commitment][token]`) is never decremented and never paid out to anyone — it is permanently stuck in the contract.

This mirrors the reported class exactly: two parallel arrays (`vaultsToLiquidate`/`vaultsBalances` there, `order.output.assets`/`order.inputs` here) that must stay index-aligned for a proportional-distribution loop, with no explicit alignment check before indexing.

### Impact Explanation
If the length mismatch is reachable, this leads to permanent freezing of user escrowed funds inside `IntrinsicIntents`/`IntentGatewayV2` — input tokens beyond the shorter output array can never be withdrawn once the order is marked filled, since neither cancellation nor a later fill path revisits those indices.

### Likelihood Explanation
Likelihood hinges entirely on whether `IntentGatewayV2.sol`'s order-placement path (`placeOrder`) validates `inputs.length == output.assets.length` before escrowing. I reviewed `IntentsBase.sol` in full and found no such invariant enforced there, and the fill-side code (`IntrinsicIntents.sol`) performs no defensive check either — it unconditionally trusts index alignment. I was unable to complete review of `IntentGatewayV2.sol`'s `placeOrder` function within my tool-call budget, so I cannot state with certainty whether this specific mismatch is currently blocked upstream. This is a genuine gap in my verification, not a confirmed exploit.

### Recommendation
Add an explicit `if (order.inputs.length != order.output.assets.length) revert InvalidInput();` check either in `placeOrder` (source of truth, cheapest place to reject) and/or defensively at the top of `_fillSameChain` (and the cross-chain counterpart in `ExtrinsicIntents.sol`, which has the same `order.inputs[i]`/`order.output.assets[i]` pattern) before any escrow accounting occurs.

### Proof of Concept
Not executed — this would require confirming, via a Devin/full-repo session, whether `IntentGatewayV2.placeOrder` currently rejects `order.inputs.length != order.output.assets.length`. If it does not, a PoC would: (1) call `placeOrder` with `inputs.length = 2`, `output.assets.length = 1`; (2) have a solver call `fillOrder`/`_fillSameChain` to fully fill the single output leg; (3) observe `_orders[commitment][inputs[1].token]` remains non-zero and unrecoverable since `_filled[commitment]` is now set.
