### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant identity), `topic`, and `webhook_id` fields used by the application's webhook handler are taken directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are parsed straight out of headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only that the body's HMAC is correct, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` values and dispatches it to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the raw body for webhooks) using the app-wide `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `shop_header == shop_that_produced(raw_body, hmac)`. Because `shop` is excluded from `to_signable_string`, that equality is never checked — the HMAC only proves "this body/HMAC pair was produced with this app's shared secret," not "this body belongs to this shop." Since `Context.api_secret_key` is the same secret for every shop that has ever installed the app, any tenant that has legitimately installed the app can obtain body+HMAC pairs that Shopify signed for events in their own store (e.g. by triggering `orders/create`, `app/uninstalled`, `shop/redact`, etc. in their own dev/test store), and then replay that exact `raw_body`/HMAC pair against the same webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header for a victim tenant's domain. `Registry.process` will accept it as valid and hand the attacker-chosen data to the handler tagged as belonging to the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC is meant to enforce in a multi-tenant SaaS app built on this gem: an attacker with only a legitimate installation of the app on their own store can inject webhook events that the host app will process as if they originated from an arbitrary victim merchant. Depending on how the host app's handler acts on `WebhookMetadata#shop`/`#body` (e.g. updating per-shop billing/order state, or reacting to `app/uninstalled`/`shop/redact` for data deletion), this yields cross-tenant data corruption or unauthorized actions attributed to another merchant, which falls under the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
The attacker only needs the ability any unprivileged internet user has — installing the app on a store they control and knowing (or guessing/enumerating, since shop domains are often public) a target's `*.myshopify.com` domain. No access to the `api_secret_key`, access tokens, or the victim's credentials is required, since the HMAC secret is shared across all installs and the check never binds the body to the shop header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string that the HMAC is computed over, or otherwise cryptographically bind the shop domain to the signed payload before `Registry.process` trusts `request.shop` for dispatch. At minimum, document/require that host applications independently verify `request.shop` corresponds to a shop that actually has an active, matching webhook subscription before acting on the payload.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real event (e.g. updates an order) causing Shopify to POST a legitimately HMAC-signed webhook (`raw_body`, `x-shopify-hmac-sha256`) to the app's webhook endpoint, addressed to `attacker-shop.myshopify.com`.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` header directly to the same public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the shared secret; `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` then invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, as seen in `lib/shopify_api/webhooks/request.rb`.
