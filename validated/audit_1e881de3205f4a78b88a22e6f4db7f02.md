## Title
`calc_total_without_take_pnl_no_orderbook` underflow permanently freezes swap/deposit/withdraw once accumulated `need_take_pnl` exceeds real vault balance - (File: `program/src/math.rs`)

### Summary
Every core AMM instruction — `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`, `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — begins by computing the "effective" pool reserves via `Calculator::calc_total_without_take_pnl_no_orderbook`, which subtracts the accrued-but-unwithdrawn PnL (`amm.state_data.need_take_pnl_pc/coin`) from the raw SPL vault balances: [1](#0-0) 

This is structurally identical to the Dyad `UnboundedKerosineVault::assetPrice` bug: a subtraction of an "obligation" value (`need_take_pnl_*`, analogous to `dyad.totalSupply()`) from a "total" value (raw vault balance, analogous to `tvl`) that is expected to always stay non-negative by invariant, but is not actually enforced anywhere before this call executes.

### Finding Description
`need_take_pnl_pc`/`need_take_pnl_coin` are continuously incremented inside `Processor::calc_take_pnl`, which is invoked from swap, deposit, and withdraw paths every time the pool state advances: [2](#0-1) 

The PnL delta added each call is derived from a chain of lossy `u128`↔`u64` decimal round-trips (`normalize_decimal_v2` / `restore_decimal`) and an integer-square-root approximation of the constant-product invariant (`x2 = sqrt(last_k * current_price)`): [3](#0-2) [4](#0-3) 

Because these amounts are only ever added to `need_take_pnl_pc/coin` (via `checked_add`) and never validated against the actual vault balance until `process_withdrawpnl`'s late-stage check, there is no invariant enforcement preventing `need_take_pnl_pc` or `need_take_pnl_coin` from drifting above the real token balance held in `amm_pc_vault`/`amm_coin_vault` over many swap/deposit/withdraw operations. Once that happens, `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc)` (or the coin equivalent) underflows and every instruction that calls `calc_total_without_take_pnl_no_orderbook` fails with `AmmError::CheckedSubOverflow`: [5](#0-4) [6](#0-5) [7](#0-6) 

Critically, `process_withdrawpnl` — the only instruction capable of *reducing* `need_take_pnl_pc/coin` back toward a safe value — itself calls the same vulnerable `calc_total_without_take_pnl_no_orderbook` before its own safety check (`need_take_pnl_coin <= amm_coin_vault.amount`) is ever reached: [7](#0-6) [8](#0-7) 

So exactly like the Dyad case where `UnboundedKerosineVault::assetPrice` reverts until TVL organically exceeds `dyad.totalSupply()` (a condition users cannot force), here the pool has no recovery path: the one instruction meant to correct the imbalance is blocked by the very same underflow it is supposed to fix.

### Impact Explanation
Once `need_take_pnl_pc` or `need_take_pnl_coin` exceeds the raw vault balance, all of swap (base-in/base-out, v1/v2), deposit, withdraw, and withdrawpnl revert for that pool. This is a permanent freeze of all LP and swapper funds in the affected AMM pool — no unprivileged user, and no privileged `pnl_owner`, can move funds in or out, since every entry point funnels through the same underflowing subtraction before any protective branch is reached.

### Likelihood Explanation
This state is reached purely through ordinary use of the public swap/deposit/withdraw instructions by unprivileged users — no special permissions or malicious validator behavior are required. The likelihood depends on how much decimal-truncation drift accumulates in `calc_take_pnl`'s `restore_decimal`/`normalize_decimal_v2` round trips and integer-sqrt approximation relative to actual fee accrual over the pool's lifetime; pools with many swaps and infrequent `withdrawpnl` calls (which are gated to `pnl_owner`/`amm_owner` and therefore may not be called often) are more exposed.

### Recommendation
Add a hard invariant check after every `checked_add` to `need_take_pnl_pc`/`need_take_pnl_coin` in `calc_take_pnl`, verifying the new values do not exceed the corresponding raw vault balance, and clamp/reject the PnL delta if they would. Additionally, `process_withdrawpnl` should recompute and validate its take-pnl amounts using the raw vault balances directly, rather than depending on `calc_total_without_take_pnl_no_orderbook` succeeding first, so that the recovery path can never itself be blocked by the condition it exists to resolve.

### Proof of Concept
1. Deploy a pool and drive many alternating swaps (base-in/base-out) through `process_swap_base_in_v2`/`process_swap_base_out_v2`; each call invokes `calc_take_pnl`, incrementing `need_take_pnl_pc`/`need_take_pnl_coin` based on lossy decimal-normalized invariant math.
2. Do not call `process_withdrawpnl` (it is owner-gated and not required for normal trading), letting `need_take_pnl_pc/coin` accumulate across many swaps while true vault growth lags due to truncation in `restore_decimal`/`normalize_decimal_v2` and the `integer_sqrt` approximation of `x2`.
3. Once `need_take_pnl_pc > amm_pc_vault.amount` (or the coin equivalent), submit any of `swap_base_in`, `swap_base_out`, `deposit`, or `withdraw` — each calls `Calculator::calc_total_without_take_pnl_no_orderbook` first, which now underflows and returns `AmmError::CheckedSubOverflow`, aborting the transaction.
4. Attempt `process_withdrawpnl` to fix the imbalance — it also calls `calc_total_without_take_pnl_no_orderbook` before its own `need_take_pnl <= vault.amount` check, so it fails identically, leaving the pool permanently frozen with no on-chain remediation path.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
