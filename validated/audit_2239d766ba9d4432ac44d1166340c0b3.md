### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are trusted for shop/topic attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts several other request headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that are **not** part of the signed content, to route the payload and to populate `WebhookMetadata` passed to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id` and `api_version` accessors instead read directly from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. only the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs exactly one integrity check — the body HMAC — and then dispatches using the unauthenticated headers: [4](#0-3) 

The broken identity binding, stated as an equality: the library treats
`shop_attributed_to_handler (from the "shopify-shop-domain" header)` as equal to `shop_that_produced_the_HMAC-signed_body`, but the HMAC only proves *"this body byte-sequence was signed with the app's `api_secret_key`"* — it proves nothing about which shop, topic, or webhook id that body belongs to. Any party capable of causing an HTTP POST to the app's webhook endpoint with a body+HMAC pair that is valid for the app's secret (e.g., a merchant replaying/relaying a webhook legitimately delivered to their own shop) can substitute an arbitrary `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` header while keeping the same valid `(body, hmac)` pair from a different, legitimately-received webhook.

### Impact Explanation
Because the handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` built from unauthenticated headers, an application that uses `shop` to decide which tenant's record to update/create/delete based on the webhook body will attribute data to the wrong shop — a cross-tenant data-integrity break, since the shop identity that "passed" the cryptographic check (the body signer) is not the shop identity actually acted upon (the header value). This matches the "Critical — cross-tenant access" impact category, since the library gives host applications no way to know that `shop`/`topic`/`webhook_id` weren't authenticated at all; only the body bytes were.

### Likelihood Explanation
The precondition is possession of at least one legitimate `(raw_body, hmac)` pair generated by Shopify for the app (any shop with the app installed receives such pairs continuously through ordinary webhook deliveries they are entitled to see, e.g. their own `orders/create` webhook). No knowledge of `api_secret_key` is required — the attacker only needs to replay a previously observed valid body+hmac combination while altering the transport-level headers when delivering it to the app's public webhook endpoint. This is a realistic, low-effort scenario for any merchant/attacker who has legitimate webhook traffic to observe (their own shop's webhooks), making likelihood moderate-to-high, gated on the host app trusting `shop`/`topic` from the metadata to key its own writes (a very common usage pattern per the documented `WebhookMetadata` API).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string (or verify them against an independent authenticated source, e.g. a signed JWT/session, or bind them cryptographically per Shopify's documented webhook verification guidance) rather than trusting raw headers, so that shop/topic/webhook-id cannot be swapped independently of the signed body.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid-for-body>
   shopify-shop-domain: shop-a.myshopify.com
   Body: {"id":1,"total_price":"10.00"}
   ```
2. Attacker (who legitimately received this exact webhook for their own shop, or who can intercept/replay it before it reaches the app) resends the identical body and HMAC header, but swaps the shop header:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <same-valid-hmac>          # unchanged, still valid for the same body
   shopify-shop-domain: victim-shop.myshopify.com   # attacker-chosen
   Body: {"id":1,"total_price":"10.00"}
   ```
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body bytes.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {...}, ...)` even though `victim-shop.myshopify.com` never sent or authorized this webhook — the shop attribution was never cryptographically verified.
