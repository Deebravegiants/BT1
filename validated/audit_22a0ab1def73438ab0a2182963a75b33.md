### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant identifier (`shop`) from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` verifies covers only the raw request body. This breaks the identity binding: the field the handler acts on (`shop`) is not the field the signature actually authenticates.

### Finding Description
`Registry.process` validates a webhook solely with: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw body: [2](#0-1) 

The `shop` accessor is read straight from an HTTP header that is never included in the signed content: [3](#0-2) 

`HmacValidator.validate` confirms `HMAC(secret, raw_body) == received_hmac`: [4](#0-3) 

After that check passes, `Registry.process` forwards `request.shop` directly to the handler as the trusted tenant context, with no independent verification that this shop matches the body or an installed session: [5](#0-4) 

**Identity binding that should hold:**
`shop_acted_on (WebhookMetadata.shop, used by the app to select which tenant's data to mutate) == shop_covered_by_hmac`

**What actually holds:**
`shop_covered_by_hmac == ∅` (the signature authenticates only `raw_body`), so `shop_acted_on` can be set to any value the caller of the webhook endpoint chooses, independent of the signature check.

### Impact Explanation
An unprivileged internet user can install the target app on a shop they control (free/dev store), and receive a genuine webhook — a real `(raw_body, hmac)` pair correctly signed by the target app's `api_secret_key` via Shopify's own webhook delivery. Because `to_signable_string` never includes the shop header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain that also has the app installed. `Registry.process` still finds the HMAC valid (body-only check) and dispatches the payload to the handler tagged with the victim's shop. If the app's webhook handler uses `data.shop` to select which tenant's records to create, update, or delete (a common pattern, e.g. `app/uninstalled`, `customers/data_request`, inventory or order sync handlers), the attacker can inject or corrupt data under a shop they do not own/control — a cross-tenant integrity/confidentiality break using only their own legitimate app installation, no credentials of the victim required.

### Likelihood Explanation
The only prerequisite is that the attacker be able to install the app on a shop of their own (or otherwise obtain one legitimately signed webhook body/hmac pair from the app), and that they can send an HTTP POST to the app's public webhook receiving endpoint with attacker-controlled headers — both trivially satisfiable by any unprivileged internet user, since webhook endpoints must be internet-reachable to receive genuine Shopify traffic. No TLS interception, secret leakage, or privileged access is required.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload check, or
- Require the caller (the hosting app, via `shopify_app` or similar) to cross-check `request.shop` against a stored/expected shop for the installation before acting, and document this requirement prominently in `ShopifyAPI::Webhooks::Registry.process`.
- At minimum, expose a way for `Registry.process`/handlers to reject a webhook whose `shop` was not the shop that installed the corresponding session/access token, closing the gap between "signature valid" and "tenant claim trustworthy."

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a real store they control), triggering a genuine webhook delivery. They capture the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's real `api_secret_key`.
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (any shop that has the app installed)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request object whose `shop` returns `"victim-shop.myshopify.com"`.
4. `Registry.process(request)` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because the shop header was never part of the signed content.
5. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to perform whatever action the handler implements (data deletion, resync, uninstall cleanup, etc.) against the victim tenant, using an attacker-controlled body that was never actually sent by Shopify for that shop.

          received_signature = verifiable_query.hmac
