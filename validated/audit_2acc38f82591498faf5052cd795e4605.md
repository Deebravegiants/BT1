### Title
Permanent max WETH allowance to the Uniswap V3 swap router in `UniV3UniswapV2Wrapper.init()` exposes native-fee WETH to theft if the router is compromised - (File: `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`)

### Summary
`UniV3UniswapV2Wrapper` is deployed as the `uniswapV2` router substitute wired into `EvmHost`/`HostParams` on chains lacking a native Uniswap V2 deployment (Uniswap V3-only chains). `init()` grants `params.swapRouter` an unlimited (`type(uint256).max`) WETH allowance once, at initialization, and this allowance is never reduced or reset for the lifetime of the contract.

### Finding Description
`init()` at [1](#0-0)  sets an unbounded approval on the wrapper's own WETH balance to `params.swapRouter`, the same pattern flagged in the external report (`want.safeIncreaseAllowance(address(tfUSDC), type(uint256).max)`). The wrapper's `swapETHForExactTokens` function at [2](#0-1)  is invoked directly by `EvmHost.dispatch()` whenever a caller pays fees with native ETH — `EvmHost` forwards `msg.value` to this wrapper via `swapETHForExactTokens`, per [3](#0-2) . Between the WETH deposit (line 122) and the router's `multicall` (line 140), the wrapper transiently holds WETH balance that the pre-approved `swapRouter` can pull via `transferFrom` using the standing max allowance — not just the `amountInMaximum` for that call, but the entire WETH balance the contract holds at any point in time (including any WETH left over from partial/failed refunds, or WETH sent by unrelated flows). Because the router address is set once via `init()` and the allowance is never revoked, if the configured Uniswap V3 SwapRouter02 deployment is ever compromised (proxy upgrade, add­ress substitution via governance misconfiguration, or a vulnerability discovered in the router itself), it can call `transferFrom` on the wrapper for the router's entire WETH balance with no signature or additional authorization required, exactly as described in the referenced TrueFi report.

### Impact Explanation
Any WETH balance sitting in the wrapper contract (from swap dust, partial multicall settlement, or unexpected transfers) can be drained by the swap router if it is ever compromised or misconfigured, without any additional user action. Because this wrapper sits directly in the dispatch fee-payment path for every EVM-based hyperapp/relayer/dispatcher call that pays fees in native ETH on chains using this wrapper, a compromised or malicious router address effectively gets standing pull rights over protocol-adjacent funds. This satisfies the "concrete theft ... of funds" bar for Medium severity.

### Likelihood Explanation
Likelihood is contingent on the swap router being compromised or misconfigured — the same trust assumption flagged in the original TrueFi report about `TrueMultiFarm`. Uniswap's SwapRouter02 is generally treated as immutable and not upgradeable, which lowers likelihood versus the original finding's upgradeable `TrueMultiFarm`, but the underlying anti-pattern (constructor/init-time unlimited allowance rather than per-call, minimal, zero-after-use allowance) is identical, and the wrapper is reachable from every ETH-fee dispatch through `EvmHost.dispatch()`.

### Recommendation
Replace the standing `approve(params.swapRouter, type(uint256).max)` in `init()` with a per-call, exact-amount approval issued immediately before each swap (using `forceApprove`/`safeIncreaseAllowance` for the precise `amountInMaximum`/`msg.value`), and reset the allowance to zero after each swap completes, mirroring the pattern already used correctly elsewhere in this codebase for token-in approvals in `swapExactTokensForETH` (`IERC20(token).forceApprove(_params.swapRouter, amountIn)` at [4](#0-3)  — which is per-call though still not zeroed after use).

### Proof of Concept
1. `UniV3UniswapV2Wrapper` is deployed and `init()` is called by `_deployer`, setting `IERC20(WETH).approve(swapRouter, type(uint256).max)` at [5](#0-4) .
2. `EvmHost.dispatch()` is called with `msg.value > 0`, invoking `swapETHForExactTokens` on the wrapper at [3](#0-2) .
3. The wrapper wraps `msg.value` into WETH at [6](#0-5) , temporarily holding a WETH balance before the router's `multicall` consumes it.
4. If `swapRouter` is compromised (e.g., through a governance parameter update pointing to a malicious/hijacked address, or an exploit in the deployed router), the attacker calls `transferFrom(wrapper, attacker, wethBalance)` directly on the WETH token using the standing max allowance, without waiting for or needing any wrapper-initiated call.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }

        uint256[] memory amounts = new uint256[](2);
        amounts[0] = spent;
        amounts[1] = amountOut;

        return amounts;
    }
