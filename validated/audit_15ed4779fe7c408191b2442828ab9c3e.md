### Title
Stale operator location data accepted within a long expiration window can authorize signups based on outdated location - (File: `src/plans/mod.rs`, `src/backend/user_status.rs`)

### Summary
The reported bug class is: a time-sensitive value (Chainlink price) is accepted from within a wide tolerance window around the intended timestamp, so a stale value is used to determine a security/outcome-critical decision, producing a result different from what should have been computed at the correct instant. The orb-core codebase has a structurally analogous pattern in the signup-authorization flow: an operator's location snapshot, captured once at QR-scan time, is treated as valid for the entire `operator_qr_expiration_time` window (23 hours by default) and reused to authorize potentially many different user signups, instead of being re-verified at the time each authorization decision is actually made.

### Finding Description
When an operator QR-code is scanned, `verify_operator_qr_code` fetches `LocationData` (team operating country, session coordinates, stationary coordinates) from the backend and stores it in `OperatorData` together with a capture `timestamp`: [1](#0-0) 

This `OperatorData` (and its embedded, one-time-captured `location_data`) is considered valid as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, which defaults to 23 hours: [2](#0-1) [3](#0-2) 

Within that window, the same cached `operator_data` (including its stale `location_data`) is reused across the idle loop to validate subsequent, distinct user QR-code scans without re-checking the operator's current location: [4](#0-3) 

That stale `location_data.session_coordinates` is then sent directly to the backend as the basis for authorizing the user's signup when `user_qr_validation_use_only_operator_location` is enabled (which is the default): [5](#0-4) [6](#0-5) 

Exactly like the reported bug — where a price sampled up to 10 minutes away from `endTime` is accepted as if it were the price at `endTime`, changing who is deemed the "winner" — here a location sampled up to 23 hours in the past is accepted as if it were the operator's current location, changing whether a signup is deemed "authorized." The authorization decision does not correspond to the real-time state it is supposed to represent.

### Impact Explanation
If `user_qr_validation_use_only_operator_location` is set (the documented default), any signup authorized during the up-to-23-hour validity window is granted or denied based on a location reading that may no longer reflect where the orb/operator actually is. Because the same cached snapshot backs many distinct signups (`scan_remaining_qr_codes` / `idle_scan_user_qr_code` reuse `operator_data` for the whole window), a geolocation-based authorization/geofencing decision can be systematically wrong for an extended period, misattributing which users are permitted to sign up at a given orb — analogous to winners being wrongly determined in the reported bug.

### Likelihood Explanation
This does not require a malicious operator or special privileges — it triggers under normal, intended usage of self-serve mode, since the code path that reuses the stale `operator_data` across multiple signups is the default idle-loop behavior, not an edge case. The 23-hour default expiration window (`operator_qr_expiration_time`) makes the staleness window very large by default, increasing the chance that a real location change occurs before the cached data is refreshed.

### Recommendation
Re-fetch or re-validate the operator's location (or otherwise bind the authorization check to a location reading taken at or near the actual moment of each individual signup's authorization) instead of trusting a single snapshot for the entire `operator_qr_expiration_time` window. If a longer QR validity period is desired for UX reasons, decouple "QR-code identity validity" from "location freshness used for authorization," and shrink the freshness threshold for the location data specifically.

### Proof of Concept
1. Set `self_serve = true` and leave `user_qr_validation_use_only_operator_location = true` (default) and `operator_qr_expiration_time` at its default (23 hours).
2. Scan the operator QR-code once; `verify_operator_qr_code` records `location_data` and `timestamp` into `OperatorData` (`src/plans/mod.rs:133-142`, populated in `scan_initial_qr_codes`/`scan_remaining_qr_codes`).
3. Physically move the orb (or have the operator's real location change) to a location that should not be authorized.
4. Within the next 23 hours, a user scans their QR code; `idle_scan_user_qr_code`/`scan_remaining_qr_codes` reuse the original cached `operator_data` (`src/plans/mod.rs:456-488`, `788-820`) without re-querying the operator's current location.
5. `verify_user_qr_code` → `backend::user_status::request` sends the stale `session_coordinates` to the backend (`src/backend/user_status.rs:119-125`), and the signup is authorized/denied based on outdated location rather than the orb's actual current location.

    async fn idle_scan_user_qr_code(
        &mut self,
        orb: &mut Orb,
        operator_data: &OperatorData,
        operator_qr_expiration_time: Duration,
        mut ui_idle_delay: Option<time::Sleep>,
    ) -> Result<Option<(qr_scan::user::Data, backend::user_status::UserData, String)>> {
        loop {
            orb.reset_rgb_camera().await?;
            match idle::Plan::with_user_qr_scan(
                ui_idle_delay.take(),
                Some(operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())),
                #[cfg(feature = "internal-data-acquisition")]
                self.data_acquisition,
            )
            .run(orb)
            .await?
            {
                idle::Value::UserQrCode(qr_scan_result) => {
                    if !check_signup_conditions(orb).await? {
                        continue;
                    }
                    if let Some(Some((user_qr_code, user_data, user_qr_code_string))) =
                        self.handle_user_qr_code(qr_scan_result, orb, operator_data, None).await?
                    {
                        break Ok(Some((user_qr_code, user_data, user_qr_code_string)));
                    }
                }
                idle::Value::TimedOut => break Ok(None),
                idle::Value::ButtonPress => unreachable!(),
            }
        }
    }

#[cfg(not(feature = "skip-user-qr-validation"))]
async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
