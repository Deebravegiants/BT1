## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` treats the `X-Shopify-Shop-Domain` header as the authoritative tenant identifier for every inbound webhook, but the HMAC signature that `Utils::HmacValidator` verifies is computed **only over the raw request body**, never over the shop header. Any party who can obtain one genuinely-signed webhook body/HMAC pair for the app (trivially available to an attacker who installs the app on their own store and receives a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the forged shop identity is handed to the app's webhook handler as if it were authentic — a direct cross-tenant identity-binding break, analogous to the reported "field acted on but not covered by the HMAC" class of bug.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the (attacker-suppliable, over-the-wire) header with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` performs no additional binding of `shop` to the signature — it validates the HMAC once, then immediately forwards the (unauthenticated) `request.shop` value to the merchant-supplied handler as the identity of the webhook's originating store: [4](#0-3) 

The equality that should hold is:
`shop bound by HMAC == shop delivered to handler`

but in reality:
`shop bound by HMAC == {}` (nothing) while `shop delivered to handler == header value chosen by whoever sends the HTTP request`.

Because the webhook secret (`Context.api_secret_key`) is shared across every shop that has installed the app, any attacker who legitimately installs the app on their own store will receive real webhooks with valid `(body, hmac)` pairs signed with that same shared secret. They can then replay that exact body and HMAC directly to the app's public webhook receiving endpoint, only changing the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to name a victim shop. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` dispatches the forged `shop` value straight to `WebhookMetadata`/the handler.

### Impact Explanation
This breaks the tenant-authentication boundary the whole HMAC check exists to enforce: an attacker can make the app process (and typically persist, since webhook handlers commonly key data storage/session lookups on `shop`) attacker-controlled payloads under the identity of a shop they do not own. Depending on the handler's use of `shop` (e.g. `app/uninstalled`, `orders/*`, `customers/data_request`), this can lead to cross-tenant data corruption, triggering of privileged actions (e.g. app uninstall/cleanup, GDPR erasure) against a victim shop, or injection of attacker-controlled data into another merchant's application state — this is classified as Critical (cross-tenant access) per the given impact taxonomy.

### Likelihood Explanation
The barrier to exploitation is low: an attacker needs only to install the target app on a store they control (a normal, unprivileged action any developer can perform), capture one legitimate webhook delivery, and replay it against the app's own public callback URL with a modified shop header. No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the shop identity to the signature verification: include the `shop-domain` header (and ideally `topic`/`webhook-id`) inside `to_signable_string`, or — more robust — after validating the body HMAC, cross-check that the resolved shop actually corresponds to a store known to be installed for this app (e.g. verified via a stored session) before dispatching to handlers. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant routing without an independent installation/session check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimately signed webhook:
   - Body: `{"id":123}`
   - Header: `X-Shopify-Hmac-Sha256: <valid HMAC of body using the app's shared secret>`
   - Header: `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Attacker replays the identical body and HMAC to the app's webhook endpoint, but changes only:
   - Header: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body-derived HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, believing it originated from the victim's store.
