Audit Report

## Title
JWT Replay via TOCTOU Race in Gateway HTTP Trigger Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` performs the JWT replay check (`isReplay`) and the replay record (`recordUsage`) as two separate, independently-locked operations on `jwtReplayCache`, rather than a single atomic check-and-set. This creates a check-then-act race window where two concurrent requests carrying the same single-use JWT can both pass the replay check before either records usage, allowing the same signed token to authorize a workflow trigger execution twice.

## Finding Description
`Authorize` verifies the JWT, then calls `h.jwtCache.isReplay(claims.ID)` (RLock/RUnlock), then performs signer authorization checks, and only afterward calls `h.jwtCache.recordUsage(claims.ID)` (Lock/Unlock) on success: [1](#0-0) . The two cache methods acquire and release the mutex independently instead of performing an atomic check-and-insert: [2](#0-1) .

Because there is no single lock hold spanning both the existence check and the insertion, two goroutines invoking `Authorize` concurrently with the same `jti` can both observe `exists == false` from `isReplay` before either calls `recordUsage`, letting both proceed through signer validation and be authorized.

`Authorize` is reached from `httpTriggerHandler.authorizeRequest`, called directly from `HandleUserTriggerRequest`, the entry point for unprivileged, internet-facing HTTP trigger requests to the Gateway: [3](#0-2) [4](#0-3) .

The existing `callbacksMu`/`setupCallback` in-flight-request-ID guard is keyed by the outer JSON-RPC `req.ID`, not by the JWT's `jti`, and is checked/locked separately from `Authorize`: [5](#0-4) . This does not close the JWT-cache race, since an attacker can send two requests with distinct outer request IDs but the same signed JWT/`jti`.

The codebase's own `RequestReplayGuard.CheckAndRecord` in the Vault capability demonstrates the correct atomic pattern (check and insert under a single lock hold), confirming that the non-atomic pattern in `jwtReplayCache` is inconsistent with the established secure design elsewhere in the codebase.

## Impact Explanation
A successfully replayed single-use JWT allows a workflow-trigger execution request to be dispatched twice to the DON via `sendWithRetries`, resulting in duplicate/unauthorized workflow executions from what was intended to be a single-use, short-lived credential. This maps to the "unauthorized job run" impact category, since it defeats an explicit anti-replay security guarantee reachable by an unprivileged client through the internet-facing Gateway HTTP trigger path.

## Likelihood Explanation
Exploitation requires only sending two concurrent requests carrying the same valid signed JWT to the Gateway's HTTP trigger endpoint with different outer JSON-RPC request IDs — a race that is trivial to win over a normal network round trip, and requires no elevated privilege, node/peer compromise, or credential leakage beyond possessing one legitimately issued (but not-yet-consumed) token.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-record method (analogous to `RequestReplayGuard.CheckAndRecord`) that holds the write lock across both the existence check and the cache insertion, and invoke it once immediately after JWT signature/digest verification in `Authorize`, before any other authorization logic proceeds.

## Proof of Concept
1. Issue a single workflow-trigger JWT with a fixed `jti = X`, signed by an authorized workflow key.
2. Construct two `HandleUserTriggerRequest` JSON-RPC calls with distinct top-level request IDs but the same JWT (`jti = X`) in the `Auth` field, targeting the same `workflowID`.
3. Fire both requests concurrently against the Gateway. In a Go unit test, call `WorkflowMetadataHandler.Authorize` from two goroutines simultaneously with the same `claims.ID`, using a `sync.WaitGroup`/barrier to force both to reach `isReplay` before either reaches `recordUsage`; assert both calls return `nil` error, demonstrating the token was accepted twice.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())

	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
