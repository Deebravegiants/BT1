### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC only over the raw request body, but exposes `shop` and `topic` as trusted attributes read directly from unauthenticated HTTP headers. Any app that authenticates a webhook via `Utils::HmacValidator.validate(request)` and then uses `request.shop` to route or persist data is trusting a value the HMAC never covered.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the `X-Shopify-Hmac-Sha256` header: [1](#0-0) [2](#0-1) 

`shop` and `topic`, however, are pulled straight from the `shopify-shop-domain` / `shopify-topic` headers with no cryptographic binding to the body or to the HMAC computation: [3](#0-2) 

`Utils::HmacValidator.validate` (the same routine used for OAuth callback validation) only re-computes the signature over `to_signable_string` and compares it to `hmac`: [4](#0-3) 

So the only thing proven by a passing HMAC check is "this body was signed with the app's `client_secret` by Shopify for *some* shop" — it proves nothing about which shop the `shop` header claims to be. This is the same bug class as the report's `block.number`-for-`block.timestamp` substitution: the identity/authorization check (HMAC) answers a *different* question than the field the app relies on afterward. Concretely, the equality that should hold is:

`shop bound by HMAC == shop used for tenant/session lookup`

but instead the code guarantees only:

`hmac(raw_body) == hmac(raw_body)` while `shop` is taken from an out-of-band, unsigned header.

### Impact Explanation
Any consumer of this gem that validates a webhook with `HmacValidator.validate(request)` and then dispatches on `request.shop` (the documented pattern for the `Webhooks::Registry`) can be tricked into processing an otherwise-legitimate, correctly-signed webhook payload under the wrong shop identity. An attacker who can capture or receive one valid webhook delivery for their own (attacker-controlled) shop can replay that exact body/HMAC pair to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. Since the shop field is never part of the signed content, the HMAC check still passes, and the app will attribute/act on the payload as if it came from the victim tenant — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Exploitability depends on the host application's webhook endpoint accepting attacker-controlled headers unmodified (i.e., not behind a proxy that strips/overwrites `X-Shopify-Shop-Domain`) and on the attacker being able to obtain at least one valid signed webhook body for their own shop (trivial — any developer can install their own app instance and receive real webhooks for their own store, since HMAC only requires knowledge of the shared `client_secret`, which every merchant's copy of the app's webhook delivery already demonstrates). No secrets need to be stolen; this is exploitable by any unprivileged party who can install the app on their own shop.

### Recommendation
Bind `shop` (and ideally `topic`/`api-version`) into the signed payload verification, e.g. by including the shop header value inside `to_signable_string`, or by having the gem expose an explicit warning/contract that `shop` and `topic` are unauthenticated metadata that callers must independently validate against the shop that installed the app (e.g., cross-check against a known/registered shop record) before using them for any tenant-scoping decision. At minimum, document clearly that HMAC validation of `Webhooks::Request` only authenticates the body, not the `shop`/`topic` header values.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — both are valid because they were genuinely signed by Shopify with the app's `client_secret`.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. The app calls `ShopifyAPI::Utils::HmacValidator.validate(request)` — this passes because `to_signable_string` only checks `@raw_body`, per [2](#0-1) .
4. The app then reads `request.shop` (`"victim.myshopify.com"`) per [5](#0-4)  and processes/stores the attacker's order payload under the victim's tenant, causing cross-tenant data confusion despite a "valid" HMAC.
