Based on the webhook processing code, I found a valid analog matching the specified bug class: an HMAC that covers only the request body while the `shop` field used downstream is taken from an unauthenticated header.

### Title
Webhook HMAC validation covers only the raw body, allowing the `shop` (tenant) identity to be spoofed via unsigned headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the *body bytes* only. The `shop` (and `topic`, `webhook_id`) values consumed by `Registry.process` are read straight from HTTP headers that are never included in the signed payload, breaking the equality `HMAC-authenticated bytes == bytes the handler trusts for tenant identity`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` exclusively. Meanwhile `shop`, `topic`, and `webhook_id` are pulled from headers that are not part of the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity for dispatch, without any additional binding check: [3](#0-2) 

`HmacValidator.validate` confirms this: it only compares `verifiable_query.to_signable_string` against the received HMAC — for a `Request`, that string is the body, never the shop header: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single shared `client_secret` — not a per-shop secret — any request bearing a body+HMAC pair that was legitimately generated for *one* shop's webhook delivery remains a valid signature no matter what `shopify-shop-domain` header value accompanies it. An attacker who controls a shop where the app is installed (e.g., a free/dev store) can legitimately receive a real webhook (valid body + valid HMAC), then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value. `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the attacker-chosen `shop` to the app's handler: [5](#0-4) 

### Impact Explanation
Any webhook handler in the host application that keys per-tenant side effects off `WebhookMetadata#shop` (e.g., updating billing state, deleting shop data on `app/uninstalled`, revoking access, syncing settings) can be triggered for a shop the attacker does not own, purely by replaying a signature that was legitimately computed for the attacker's own shop. This is cross-tenant action/data corruption without possessing the target's access token or the app's `client_secret` — the attacker only needs to be a merchant of the app on any shop to obtain one valid (body, hmac) pair.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design (Shopify itself calls it unauthenticated apart from the HMAC). Any user who can install the app on a shop they control (trivial via a free development store) can capture one legitimate webhook delivery and immediately has a valid, replayable signature. No secret material beyond what Shopify already reveals to that merchant is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string used for HMAC computation/verification, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted in `Registry.process`. At minimum, document that `request.shop` is unauthenticated header data and must be cross-checked against a known/installed shop list by the host application before use.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`. Trigger any generic webhook topic (e.g. `app/uninstalled`) so Shopify delivers a legitimate request: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay this exact HTTP POST to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim.myshopify.com` (leave body `B` and HMAC `H` untouched).
3. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (per `to_signable_string`), which still equals `H`, so validation passes: [6](#0-5) 
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to act on the victim shop's tenant identity using data/body the attacker fully controls.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
