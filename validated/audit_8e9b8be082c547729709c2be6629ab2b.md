## Title
Graduation and sell-guard USD math hardcodes 1e18 scaling for the LT reserve asset, breaking if the paired LT's decimals differ from 18 - (`packages/contracts/src/Bonding.sol`, `packages/contracts/src/Zap.sol`)

### Summary
This is the closest in-scope analog to the `UniV2LPOracle` decimals bug: instead of a UniV2 LP price computation ignoring pair-token decimals, `Bonding` and `Zap` compute a USD/threshold value from a live-priced reserve asset (`exchangeRate()`) and unconditionally divide by a hardcoded `1e18`, assuming the paired BounceTech LT always has 18 decimals. Nowhere in `packages/contracts/src` is `IERC20Metadata.decimals()` ever called on the LT or on `Token` — the scaling constant is baked in.

### Finding Description
`Bonding.canGraduate` computes the USD trigger as: [1](#0-0) 

```
address pair = info.pair;
if (IPair(pair).tokenBalance() == 0) return true;

(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
return valueUsd >= $.graduationThresholdUsd;
```

`realLtRaised` is a raw balance read straight from `Pair.getReserves()` — i.e., it is denominated in whatever decimals the LT ERC20 actually uses, since `Pair`/`Router` treat both sides of the AMM purely as raw token units (no decimals normalization anywhere in `Pair.sol`/`Router.sol`, consistent with a vanilla constant-product AMM). `exchangeRate()` is documented as "USDC per LT unit, 18-dp": [2](#0-1) , i.e. an 18-decimal fixed-point *price per one raw LT unit*. The formula `realLtRaised * exchangeRate / 1e18` is only dimensionally correct if the LT itself also has 18 decimals — exactly the same "ignore the reserve token's decimals" bug class as `UniV2LPOracle`, which multiplied raw `r0`/`r1` reserves by 18-decimal oracle prices without accounting for `r0`/`r1`'s own decimals.

The same unguarded `/1e18` assumption repeats in:
- `Bonding.previewLtUntilGraduation` (`thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate`): [3](#0-2) 
- `Zap._executeSell`'s min-sell guard: `grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18` then further divided by `1e12` to compare against the 6-decimal `minUsdcAmount()`: [4](#0-3) 
- `DeployHelper._ltForUsd` mirrors the same on-chain convention (`(usd18dp * 1 ether) / lt.exchangeRate()`): [5](#0-4) 

None of `Bonding.launch`, `_deployAndSeed`, or `Zap.createToken` validate that the LT passed in actually has 18 decimals; the only external gate is BounceTech's own `ltExists` registry check, which says nothing about `decimals()`. `grep` across `packages/contracts/src` confirms zero calls to `.decimals()` anywhere in production code, so the 18-decimal assumption is completely unenforced.

### Impact Explanation
If BounceTech ever registers (or already has registered) an LT with decimals ≠ 18:
- **LT decimals < 18** (e.g. 6, mirroring USDC-style leveraged wrappers): `realLtRaised` is 10^12x smaller in raw terms than the formula expects, so `valueUsd` is computed 10^12x too low. The USD graduation trigger can never fire — the token is stuck relying solely on the supply trigger (`tokenBalance() == 0`), and `previewLtUntilGraduation`'s USD leg becomes an effectively infinite/irrelevant cap, silently distorting the documented dual-trigger design and the `Zap._executeBuy` floor-bump sizing that depends on it (`ltUntilGraduation` computed from `previewLtUntilGraduation`, see `packages/contracts/src/Zap.sol` lines 324-357).
- **LT decimals > 18** (e.g. 24): `valueUsd` is inflated by the same factor, so `canGraduate` can return `true` almost immediately after a token launches, well before any meaningful real LT is raised. This forces an unintended, premature two-phase graduation (`_enterGraduating` → `finalizeGraduation`) with a near-empty curve, cutting the bonding-curve phase short and moving trading to a HyperSwap pool with a fraction of the raise the $9K threshold was meant to guarantee — degrading the economic design the graduation threshold exists to protect, and doing so for every buyer/creator on that LT.
- `Zap`'s sell-side `minUsdcAmount` guard (`grossUsdcEstimate`) would also be systematically wrong by the same factor, either blocking legitimate small sells or letting dust sells through that should have been rejected — the exact same "decimal scale not normalized" class the code's own regression test (`test_sell_belowMinAmount_normalisesDecimalScale`, issue #313) was written to catch, but only for the USDC/LT 6-vs-18 boundary, not for a non-18-decimal LT.

### Likelihood Explanation
Every trader interacting normally via `Zap.buy`/`Zap.sell` on any token launched against such an LT would trip this path — no privileged action or attacker input is required beyond BounceTech (an external, already-trusted integration per the protocol's own trust model) registering a non-18-decimal LT. The codebase's `AGENTS.md`/docs never state or enforce an 18-decimal invariant on the LT, and no on-chain check exists to reject a launch against a differently-scaled LT, so this is a latent integration-assumption bug rather than a hypothetical.

### Recommendation
Read `IERC20Metadata(ltAddress).decimals()` once at `Bonding.launch` time (mirroring the existing `TOTAL_SUPPLY`-equality check done for `Token` implementations), store it, and normalize every `exchangeRate()`-based USD computation (`canGraduate`, `previewLtUntilGraduation`, `Zap._executeSell`'s `grossUsdcEstimate`) to the LT's actual decimals instead of a hardcoded `1e18`. Alternatively, explicitly reject LTs whose `decimals() != 18` at launch time so the assumption becomes an enforced invariant rather than an implicit one.

### Proof of Concept
1. Deploy (or have BounceTech register) an LT with `decimals() == 6` instead of 18, satisfying `ltExists == true`.
2. Creator calls `Bonding.launch` / `Zap.createToken` against this LT — no special privilege needed, this is the standard permissionless launch path.
3. Buyers trade normally via `Zap.buy`; `assetReserve` in the `Pair` accumulates raw 6-decimal LT units.
4. `Bonding.canGraduate` computes `valueUsd = (realLtRaised * exchangeRate) / 1e18`. Because `realLtRaised` is ~10^12x smaller than an 18-decimal-LT equivalent raise, `valueUsd` never reaches `graduationThresholdUsd` (e.g. `$9,000 * 1e18`) regardless of how much real economic value has actually been raised.
5. The token can only ever graduate via the supply trigger (`tokenBalance() == 0`), permanently distorting/breaking the documented "dual trigger" graduation design and the `previewLtUntilGraduation`-driven floor-bump logic in `Zap._executeBuy`, for the lifetime of every token launched against that LT.
