This confirms the vulnerability class: the `ShopifyAPI::Webhooks::Request#shop` field is read directly from an HTTP header and is **never covered by the HMAC signature**, yet it is passed downstream as the tenant identifier that host applications use to route/attribute webhook data (per the documented `WebhookHandler` contract).

### Title
Webhook `shop` (and `topic`) identity fields are excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then forwards `request.shop`/`request.topic` verbatim to the app's handler as the tenant/topic identity [3](#0-2) .

### Finding Description
The `HmacValidator.validate` call only proves that `@raw_body` was signed with `Context.api_secret_key` [4](#0-3) ; it says nothing about which shop the body belongs to, because `shop-domain` is not part of `to_signable_string`. This is exactly the "field acted on but not covered by the HMAC" bug class from the analog prompt (mirroring the ID-accounting mismatch in the reference report, where the value trusted for identity bookkeeping diverges from the value actually verified).

Because a single `api_secret_key` is shared across every shop that installs the app, any unprivileged merchant/attacker who has installed the app on their own store legitimately receives Shopify-signed webhook bodies with a valid `hmac-sha256` header for that body. Since `shop-domain` (and `topic`) are ordinary headers outside the signed payload, the attacker can replay that same signed body to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (the body signature matches), and `Registry.process` calls `handler.handle` with `WebhookMetadata.new(shop: request.shop, ...)` carrying the attacker-chosen shop value [5](#0-4) . Any host application following the documented contract — which explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows using it directly for job dispatch/tenant routing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5)  — will process attacker-supplied body content attributed to a victim tenant it never came from.

### Impact Explanation
This breaks the identity binding `shop-in-verified-bytes == shop-used-for-tenant-attribution`: the bytes verified by HMAC (`raw_body`) never include the shop, yet `shop` is what the gem hands off as the source-of-truth tenant label. An attacker with no privileges beyond installing the app on their own store can inject arbitrary (but validly-signed-for-their-own-shop) webhook payloads that the host app will process as belonging to any other shop, resulting in cross-tenant data confusion/injection in every application built per this gem's documented webhook contract.

### Likelihood Explanation
Any developer following the gem's own documented pattern (`docs/usage/webhooks.md`) is exposed; no special configuration is required, and the only capability an attacker needs is having the app installed on a shop they control, which is normal for any public/unprivileged Shopify merchant.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable material (or otherwise cryptographically bind them to the body/signature) in `lib/shopify_api/webhooks/request.rb`, so `Utils::HmacValidator.validate` fails if any of these identity fields are altered independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook: headers `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-for-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `{"malicious":"payload"}`.
2. Attacker replays the identical body and `hmac-sha256` header to the app's webhook endpoint but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `hmac_validator.rb` still succeeds because it only checks `raw_body` against the secret [7](#0-6) .
4. `Registry.process` calls the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"malicious":"payload"}, ...)`, which the host app (per the gem's documented usage) treats as authentic data for `victim-shop` [3](#0-2) .
