### Title
Rebasing/deflationary pool tokens permanently brick all swap, deposit and withdraw instructions via unrecoverable `checked_sub` underflow on `need_take_pnl_pc`/`need_take_pnl_coin` - (File: `program/src/math.rs`)

### Summary
`Calculator::calc_total_without_take_pnl_no_orderbook` subtracts the internally-tracked, monotonically-increasing PnL accounting fields (`amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin`) from the *live* SPL token vault balance read at instruction time. If either pool token's real balance can decrease outside of a transfer performed through this program (e.g. a rebasing/deflationary token, or a token with a negative-rebase/fee mechanism, is registered as `coin_mint`/`pc_mint`), the vault balance can drop below the recorded `need_take_pnl_*` value. When that happens, every instruction that calls this helper — `Deposit`, `Withdraw`, both swap instructions, and `WithdrawPnl` itself — reverts with `AmmError::CheckedSubOverflow`, and there is no code path to reduce `need_take_pnl_*` other than a successful `WithdrawPnl` call, which is itself blocked by the same check. This permanently freezes all LP and swap funds in the pool.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` is the shared helper used to compute the tradable/withdrawable pool reserves net of accrued (but not yet withdrawn) protocol PnL: [1](#0-0) 

```rust
pub fn calc_total_without_take_pnl_no_orderbook<'a>(
    pc_amount: u64,
    coin_amount: u64,
    amm: &'a AmmInfo,
) -> Result<(u64, u64), AmmError> {
    let total_pc_without_take_pnl = pc_amount
        .checked_sub(amm.state_data.need_take_pnl_pc)
        .ok_or(AmmError::CheckedSubOverflow)?;
    let total_coin_without_take_pnl = coin_amount
        .checked_sub(amm.state_data.need_take_pnl_coin)
        .ok_or(AmmError::CheckedSubOverflow)?;
    Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
}
```

`pc_amount`/`coin_amount` are always the *live* `spl_token::Account.amount` of `amm_pc_vault`/`amm_coin_vault`, unpacked right before the call, e.g. in `process_deposit`, `process_withdraw`, and `process_withdrawpnl`: [2](#0-1) [3](#0-2) 

`need_take_pnl_pc`/`need_take_pnl_coin` are internal counters incremented every time `calc_take_pnl` accrues protocol PnL (in `Deposit`, `Withdraw`, and both swap instructions): [4](#0-3) 

and only ever decremented back to `0` inside `process_withdrawpnl`, which itself is gated by the same check: [5](#0-4) 

The protocol implicitly assumes the invariant `real_vault_balance >= need_take_pnl_*` always holds because, under normal SPL-token semantics, the vault balance only ever changes through transfers performed by this program. This is exactly the same class of assumption violation described in the external report: the design does not account for tokens whose balance changes outside of transfers (rebasing, elastic-supply, or otherwise deflationary tokens). If the `coin_mint`/`pc_mint` registered for a pool is such a token and it experiences a negative rebase/contraction after PnL has accrued, the real vault balance can fall below the tracked `need_take_pnl_*` value. From that point on, `calc_total_without_take_pnl_no_orderbook` will always return `Err(AmmError::CheckedSubOverflow)`, which propagates out of every one of:
- `process_deposit`
- `process_withdraw`
- `process_swap_base_in`
- `process_swap_base_out`
- `process_withdrawpnl`

since all of them call this helper before doing anything else that could otherwise remediate the state. There is no admin/permissionless instruction that resets or reconciles `need_take_pnl_*` against the actual balance, so the pool becomes permanently unusable.

Unlike the Axelar report's sub-section 1 (message payload amount going stale across chains, which requires a multi-step/cross-chain time window), this Raydium analog is closer to sub-section 2: an on-chain "tracked value" (`need_take_pnl_*`) that is assumed to always be `<=` the real balance, and which reverts unconditionally via `checked_sub` when that assumption breaks for a balance-changing-outside-transfers token — exactly mirroring `update_token_balance`'s `checked_sub` revert in `state.rs` of the Axelar ITS hub.

### Impact Explanation
Once the underflow condition is triggered, all economic activity on the pool — swapping, adding liquidity, and removing liquidity — becomes permanently impossible, and the accrued but unclaimed protocol PnL amount also becomes permanently stuck (since `WithdrawPnl` fails the same check). This constitutes a permanent freeze of both LP funds (unable to withdraw liquidity) and swap liquidity (unable to trade), which is a High/Medium severity impact class (permanent freezing of user funds) consistent with the analog bug class from the source report.

### Likelihood Explanation
Triggering this requires a pool to be created for/with a token whose balance can be reduced by a mechanism outside of the standard SPL transfer path used by `Invokers::token_transfer`/`token_transfer_with_authority` (e.g., a deflationary/rebase token, or a token-2022 extension with negative interest/fee-like balance mutation not routed through this program's transfer calls). Raydium AMM v2/v3 pools are permissionlessly created (`Initialize2`) for arbitrary SPL mints, so an attacker or an unaware pool creator can select such a token as `coin_mint` or `pc_mint`. Given enough trading activity to accrue `need_take_pnl_*` and any subsequent negative balance adjustment of the token outside program-mediated transfers, the freeze is deterministic and irreversible, not probabilistic. The likelihood is bounded by whether such a token is ever paired in a live pool, but the code contains no defense (no token allowlist/type check for balance-changes-outside-transfers) preventing it.

### Recommendation
- Do not rely on unconditional `checked_sub` against a live vault balance for a value (`need_take_pnl_*`) that is meant to represent a subset of that balance; instead clamp: `total_pc_without_take_pnl = pc_amount.saturating_sub(need_take_pnl_pc)` combined with also clamping `need_take_pnl_pc` itself to `min(need_take_pnl_pc, pc_amount)` when it is used/updated, so a balance shortfall degrades PnL accounting gracefully instead of bricking the pool.
- Alternatively, explicitly document/enforce (at `Initialize2`) that only tokens whose balances cannot change outside of program-mediated transfers (no rebasing, no external burn/mint, no transfer-hook-driven balance changes) are permitted as `coin_mint`/`pc_mint`.
- Add a recovery path (e.g., a privileged instruction) allowing `need_take_pnl_pc`/`need_take_pnl_coin` to be reconciled down to the actual vault balance in case of an unexpected shortfall, so pools cannot be permanently bricked by this condition.

### Proof of Concept
1. `Initialize2` a pool where `coin_mint` is a token that supports a negative rebase / balance-reduction mechanism not implemented via a standard SPL `Transfer`/`Burn` instruction issued by this program (e.g., an elastic-supply token that periodically reduces all holder balances, including the AMM's vault ATA, via its own rebase logic).
2. Perform normal trading (`SwapBaseIn`/`SwapBaseOut`) so that `calc_take_pnl` accrues `amm.state_data.need_take_pnl_coin > 0`, tracked in `AmmInfo.state_data`.
3. Trigger (or wait for) a negative rebase event on the coin token that reduces the real balance of `amm_coin_vault` below `amm.state_data.need_take_pnl_coin`.
4. Submit any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut`, or `WithdrawPnl` instruction. Each one calls `Calculator::calc_total_without_take_pnl_no_orderbook` early in its execution path (see citations above), which now returns `Err(AmmError::CheckedSubOverflow)`, causing the transaction to fail.
5. Because `need_take_pnl_coin` can only be zeroed by a successful `WithdrawPnl` call — which fails for the same reason — the pool is permanently frozen: no further deposits, withdrawals, swaps, or PnL withdrawals can succeed.
