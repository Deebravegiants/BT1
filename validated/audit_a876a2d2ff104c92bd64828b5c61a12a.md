Confirmed — `process_initialize2` treats `market_info` as an arbitrary account used purely as a PDA seed ("Just a seed for AMM account. Can be any account."), with no validation that it's a genuine, unique OpenBook/Serum market. This makes the pool-creation path griefable in the same way as the reported NFT bug: a one-time, irreversible binding to an external identifier that anyone can pre-empt.

### Title
Permanent DoS of legitimate pool creation via front-running Initialize2 with a griefed market seed - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives all pool-related PDAs (AMM account, LP mint, coin/pc vaults, target orders) solely from `market_info.key` and fixed seed constants via `get_associated_address_and_bump_seed`. Any unprivileged caller can call `Initialize2` first for a given `market_info` pubkey with trivial token amounts and their own wallet, permanently occupying every PDA tied to that market before the legitimate pool creator does so.

### Finding Description
`generate_amm_associated_account` / `generate_amm_associated_spl_token` / `generate_amm_associated_spl_mint` derive addresses using `Pubkey::find_program_address(&[program_id, market_account.key, associated_seed], program_id)` [1](#0-0) . If the account already has an owner other than the system program, they return `AmmError::RepeatCreateAmm` and abort [2](#0-1) .

Because `market_info` is documented as "Just a seed for AMM account. Can be any account" and is not required to be owned by a real market program or to have any particular market data, an attacker can supply the exact `market_info` pubkey that a legitimate project intends to use (e.g., their real OpenBook market, which is public/predictable before pool launch) [3](#0-2) . The attacker calls `Initialize2` with that market seed, their own wallet as `user_wallet_info`, and minimal `init_pc_amount`/`init_coin_amount`, which is fully permitted since the only signer check is that the caller wallet itself signs [4](#0-3) .

This single transaction causes the program to `invoke_signed` allocate+assign on the AMM account, LP mint, coin vault, pc vault, and target-orders PDAs for that market seed, and to complete initialization (`amm.initialize(...)`) [5](#0-4) [6](#0-5) . Once `amm.status != Uninitialized`, any subsequent `Initialize2` call using the same `market_info` seed fails: the associated-account helpers see the target account already owned by the program (not the system program) and return `AmmError::RepeatCreateAmm`, and even if that were bypassed, `AmmInfo::load_mut` would reject re-init via `AmmError::AlreadyInUse` [7](#0-6) . Since these are PDAs with no corresponding private key, the resulting pool cannot be migrated, closed, or reassigned to a new pool — this is the same class of "rigid, non-recoverable identifier binding" root-caused in the reported MeritDutchAuction NFT-mint DoS, where an out-of-band mint permanently prevents further mints tied to a fixed id derivation.

### Impact Explanation
The legitimate team is permanently unable to create their intended AMM pool for that market — the market seed is burned forever, since the PDAs are deterministic and the "squatted" pool now occupies them with attacker-controlled (or negligible) liquidity and status `Initialized`. This is a permanent freezing of the ability to create the pool (denial-of-service on core `Initialize2` functionality), matching the Medium-severity impact accepted in the source report (auction/pool becomes permanently unusable for that identifier).

### Likelihood Explanation
Likelihood is meaningful whenever a project's intended market account is known or guessable ahead of pool launch (which is generally the case, since the OpenBook/Serum market must be created and its pubkey shared/integrated with front-ends before the AMM pool transaction is submitted). The attack requires only one unprivileged transaction with attacker-chosen accounts/data and a negligible `init_pc_amount`/`init_coin_amount`, with no special permissions needed.

### Recommendation
Require `market_info` to be validated as a genuine, program-owned market account (e.g., verify it is owned by the expected Serum/OpenBook market program and matches the coin/pc mints), rather than treating it as an arbitrary seed value. Alternatively, bind AMM PDAs to a value that cannot be griefed by outsiders, such as a nonce chosen by the legitimate creator combined with an admin-gated allowlist, or require the pool-fee-destination-signed authorization step to occur before allowing PDA creation for a given market.

### Proof of Concept
1. Off-chain, observe or predict the `market` pubkey a project intends to use for their upcoming Raydium pool (OpenBook markets are typically created and publicized before the AMM pool exists).
2. Attacker (unprivileged) submits `Initialize2` with `market_info` = that market pubkey, `user_wallet_info` = attacker's own wallet, `user_token_coin_info`/`user_token_pc_info` = attacker-owned token accounts with minimal balances, and `init_pc_amount`/`init_coin_amount` set to the smallest values that pass `InitLpAmountTooLess`.
3. `process_initialize2` derives and creates the AMM account, LP mint, coin vault, pc vault, and target-orders PDAs from that market seed via `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`, then calls `amm.initialize(...)`, marking the pool `Initialized`.
4. When the legitimate project later submits their own `Initialize2` call with the same `market_info`, every associated-account helper finds the target PDA already owned by the AMM program (not the system program) and returns `AmmError::RepeatCreateAmm`; even if bypassed, `AmmInfo::load_mut` returns `AmmError::AlreadyInUse` since `amm.status != Uninitialized`.
5. The legitimate pool for that market can never be created — permanent denial of service.
