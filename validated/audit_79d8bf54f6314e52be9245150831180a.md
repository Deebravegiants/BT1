### Title
Reward-per-share truncation to zero via fixed integer-precision scaling in `pallet-asset-rewards` - (`substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Synthetix-style "reward per share" JIT accrual scheme analogous to the `accHaloPerShare` pattern in the HAL-08 report. Instead of an 18-decimal-scaled constant, it uses a fixed `u16` scaling factor `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . Because this constant is far smaller than a typical 18-decimal precision factor and is never adapted to the staked/reward asset decimals or magnitude, the integer division in `reward_per_token()` can truncate to zero much more easily than in the original Solidity report, silently halting reward accrual for all stakers in a pool.

### Finding Description
`reward_per_token()` computes the incremental reward-per-token as:

```
reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked
``` [2](#0-1) 

`ensure_mul`/`ensure_div` here are checked-arithmetic helpers that only guard against overflow/div-by-zero; ordinary integer-division truncation (rounding toward zero) is not treated as an error, so when the numerator is smaller than `total_tokens_staked`, the increment silently evaluates to `0`, exactly like the `accHaloPerShare` computation in the reported Solidity bug. `derive_rewards()` performs a matching division by the same `PRECISION_SCALING_FACTOR` [3](#0-2) .

Unlike the mitigation adopted for `pallet-nomination-pools`, which uses `FixedU128` (an effectively 18-decimal-precision fixed-point type) for its reward counter and explicitly reasons about/tests the resulting dust-loss bound [4](#0-3) [5](#0-4) , `pallet-asset-rewards` uses a constant, non-scaling `u16` value (4096 ≈ 2^12) regardless of the staked/reward asset's decimals or the total value staked. Any `fungible`/`fungibles` asset (via `T::AssetsFreezer`/`T::Assets`) can be configured as the staked or reward asset for a pool [6](#0-5) , so pools can be created for asset pairs with large decimal counts and correspondingly large `total_tokens_staked` values relative to `reward_rate_per_block`.

Crucially, once a pool is created (a privileged, `CreatePoolOrigin`-gated action), `stake`, `unstake`, and `harvest_rewards` are fully permissionless calls open to any signed account [7](#0-6) [8](#0-7) [9](#0-8) . Any unprivileged staker can grow `total_tokens_staked` simply by staking a large amount of the staking asset, which — combined with the fixed 4096 scale factor — can drive future `reward_per_token` deltas to zero for every block, denying reward accrual to all other stakers in that pool going forward. This mirrors the exact root cause and DoS-style impact described in HAL-08 ("once a certain amount of tokens are staked, no more rewards will be accrued").

### Impact Explanation
If `reward_rate_per_block * elapsed_blocks * 4096 < total_tokens_staked`, `reward_per_token_stored` stops increasing even though the pool's reward account continues to be depleted proportionally to intent (the pool operator still expects rewards to be distributed). Legitimate stakers silently stop accruing/receiving rewards despite tokens being staked and the pool still active, with no error or event to signal the fault. This is an accounting/DoS-type impact on protocol reward distribution, not a fund-theft bug, and is analogous in class and mechanism to the HAL-08 finding.

### Likelihood Explanation
Pool creation is gated behind `CreatePoolOrigin` [10](#0-9) , so the specific combination of staked/reward asset and reward rate is chosen by a permissioned actor, not a fully open attacker — this is a mitigating factor versus the original permissionless Solidity deployment. However, once a pool exists, no privileged action is required to trigger the truncation: any unprivileged staker can push `total_tokens_staked` high enough (via ordinary `stake()` calls) to zero out `reward_per_token` increments for the configured `reward_rate_per_block`, especially given the very small (4096) fixed precision factor. The likelihood therefore depends on pool configuration choices made by a semi-trusted (not root-level, but still privileged relative to end users) `CreatePoolOrigin`, combined with subsequent unprivileged staking activity to realistically trigger it.

### Recommendation
Increase and/or make `PRECISION_SCALING_FACTOR` configurable/large enough (e.g., a `u128` scaled to the involved assets' decimals, similar in spirit to `FixedU128`/`Perquintill`-based approaches used elsewhere in FRAME) so that reward-per-token increments cannot trivially truncate to zero for realistic asset decimal/supply combinations. Alternatively, track sub-unit remainders (a "dust" carry-over) across `reward_per_token` updates so no reward is permanently lost to rounding, and add explicit bounds/documentation (as `pallet-nomination-pools` does) describing the minimum `reward_rate_per_block` / `total_tokens_staked` ratio needed for correct accrual.

### Proof of Concept
1. `CreatePoolOrigin` calls `create_pool` with a staked asset having 18 decimals and a modest `reward_rate_per_block` (e.g., 10 reward-asset units per block) [11](#0-10) .
2. An unprivileged user (or several) calls `stake()` repeatedly to bring `total_tokens_staked` above `reward_rate_per_block * PRECISION_SCALING_FACTOR` (4096) per block, e.g. total staked > 40,960 for a rate of 10/block [7](#0-6) .
3. On the next call to `reward_per_token()` (triggered by any `stake`/`unstake`/`harvest_rewards` call), `reward_rate_per_block.ensure_mul(blocks_elapsed).ensure_mul(4096).ensure_div(total_tokens_staked)` evaluates to `0` due to integer truncation [2](#0-1) .
4. `reward_per_token_stored` stops increasing; all stakers' `derive_rewards()` computations yield no new rewards despite the pool continuing to emit its configured reward rate, matching the HAL-08 failure mode.

Note: I was not able to execute this scenario in an actual test harness within this session (no tool access to run `cargo test`); the analysis above is based on static reading of `substrate/frame/asset-rewards/src/lib.rs` and its arithmetic. A background Devin session could reproduce this concretely via the pallet's existing `tests.rs` harness (`substrate/frame/asset-rewards/src/tests.rs`) to confirm exact numeric thresholds.

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

	#[test]
	fn smallest_claimable_reward() {
		// create a pool that has all of the polkadot issuance in 50 years.
		let pool_bond = inflation(50);
		ExtBuilder::default().ed(DOT).min_bond(pool_bond).build_and_execute(|| {
			assert_eq!(
				pool_events_since_last_call(),
				vec![
					Event::Created { depositor: 10, pool_id: 1 },
					Event::Bonded {
						member: 10,
						pool_id: 1,
						bonded: 1173908528796953165005,
						joined: true,
					},
					Event::MetadataUpdated { pool_id: 1, caller: 900 },
				]
			);

			// the smallest reward that this pool can handle is
			let expected_smallest_reward = inflation(50) / 10u128.pow(18);

			// tad bit less. cannot be paid out.
			deposit_rewards(expected_smallest_reward - 1);
			assert_ok!(Pools::claim_payout(RuntimeOrigin::signed(10)));
			assert_eq!(pool_events_since_last_call(), vec![]);
			// revert it.

			remove_rewards(expected_smallest_reward - 1);

			// tad bit more. can be claimed.
			deposit_rewards(expected_smallest_reward + 1);
			assert_ok!(Pools::claim_payout(RuntimeOrigin::signed(10)));
			assert_eq!(
				pool_events_since_last_call(),
				vec![Event::PaidOut { member: 10, pool_id: 1, payout: 1173 }]
			);
		})
