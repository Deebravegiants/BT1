## Title
Unsigned `handle_unsigned` fully executes ISMP messages (proof verification + state mutation) during transaction-pool validation with a fixed weight, enabling a free, unauthenticated compute-exhaustion DoS — ([File: modules/pallets/ismp/src/lib.rs])

### Summary
The Atomix/ONOS advisory describes an attacker sending unauthenticated, false link-event messages that a privileged/master node accepts and processes, exhausting resources and causing a DoS. `pallet-ismp`'s `handle_unsigned` extrinsic is the closest reachable analog: it is an `ensure_none` (fully unauthenticated) entrypoint that any peer/relayer can submit, and its `ValidateUnsigned::validate_unsigned` implementation runs `Self::execute(messages.clone())` — the *entire* ISMP message handler including consensus/state proof verification — every time the transaction is validated by the pool, for a static, content-independent weight, with no fee.

### Finding Description
`Call::handle_unsigned` is dispatched via `ensure_none(origin)?` [1](#0-0) , meaning literally anyone can submit it without a signature or balance.

Both the dispatch path and the pool-validation path fully execute the batch. `validate_unsigned` calls `Self::execute(messages.clone())` unconditionally to determine transaction validity [2](#0-1) . This means every full-node in the network that gossips or receives this unsigned extrinsic must run complete proof verification (consensus client `verify_consensus`, MMR/state membership or non-membership checks, signature checks, etc.) just to decide whether to accept it into the pool — before any weight/fee accounting from the real dispatch ever applies.

The dispatch weight assigned to `handle_unsigned` is a static constant, unrelated to the actual cost of the batch: `weight()` returns a fixed `Weight::from_parts(300_000_000, 0)` regardless of how many messages, how large the proofs, or which consensus client (BEEFY, sync-committee, GRANDPA, BSC, etc.) is invoked [3](#0-2) . The pallet's own docs acknowledge unsigned messages are executed "for free" and rely entirely on transaction-pool validity checks to prevent spam [4](#0-3) , but that validity check is itself the expensive full-execution path, not a cheap pre-filter.

Because `ValidTransaction` sets `longevity: 25` and `propagate: true` [5](#0-4) [6](#0-5) , transactions that pass validation propagate to every peer for up to 25 blocks, each of which independently re-runs the same expensive `Self::execute` to validate it — amplifying a single crafted submission across the whole network's collator/validator set. An attacker can construct arbitrarily many message batches (e.g. varying `consensus_proof` bytes per state or replaying near-miss but ultimately-invalid consensus/state proofs across supported clients like BEEFY, sync-committee, GRANDPA, BSC, Tendermint, or Pharos/L2 clients) and submit them continuously at zero cost, forcing full cryptographic verification work on every receiving node before the transaction is (eventually) rejected as invalid — a CPU/bandwidth exhaustion DoS directly analogous to the false-link-event flood in the Atomix/ONOS advisory, where unauthenticated messages accepted by a trusted/master component drove resource exhaustion.

### Impact Explanation
This is reachable by any unprivileged party capable of submitting an extrinsic or gossiping it over the p2p transaction pool — no signature, balance, or special role is required (`ensure_none`). Sustained submission of computationally heavy but invalid batches degrades block production and message-relay throughput network-wide (a route/chain becoming unable to deliver messages in a timely fashion), which meets the "route unable to deliver messages" acceptance bar. Because verification is repeated by every node validating/re-validating/gossiping the transaction, the amplification factor scales with network size, and it costs the attacker nothing since these are unsigned, feeless transactions.

### Likelihood Explanation
High likelihood: the entrypoint is explicitly designed to be unauthenticated and free ("This allows users execute ISMP datagrams for free. Use with caution.") [7](#0-6) , requires no special access, and the only stated mitigation (pool validity filtering) is itself the expensive operation being abused. Crafting proofs that are plausible enough to enter the verification routines (but ultimately invalid) is straightforward for any of the several consensus clients supported, since `consensus_state_id` selection and proof encoding are attacker-controlled inputs to `handle_unsigned`.

### Recommendation
- Add a cheap, pre-verification static/structural check in `validate_unsigned` (e.g. bounded message/proof size limits, consensus_state_id existence, freshness/replay checks) before invoking `Self::execute`, so invalid or duplicate-looking batches are rejected without running full cryptographic verification.
- Decouple `validate_unsigned` from full execution: only run cheap idempotent checks (e.g., structural decode, replay/commitment-exists checks) during validation, and defer full proof verification to `pre_dispatch`/dispatch under transactional weight accounting.
- Replace the static `weight()` with a weight function proportional to message count/proof size/consensus-client type so nodes can rate-limit or price expensive batches appropriately even when unsigned.
- Consider a per-peer/per-block cap on the number of `handle_unsigned` batches accepted into the pool to bound worst-case verification cost per block.

### Proof of Concept
1. An attacker crafts a `Vec<Message>` containing a `Message::Consensus(ConsensusMessage { consensus_proof: <large/garbage bytes>, consensus_state_id: <valid existing id>, .. })` targeting an expensive consensus client (e.g. BEEFY/sync-committee), varying `consensus_proof` per submission so each hashes to a unique `provides` tag and is accepted into distinct pool slots [8](#0-7) .
2. Submits `Ismp::handle_unsigned { messages }` as an unsigned extrinsic repeatedly, exactly as the tesseract relayer does via `send_unsigned_extrinsic` [9](#0-8) .
3. Each node that receives the gossiped extrinsic must call `validate_unsigned`, which runs `Self::execute` and thus the full `update_client`/consensus verification path [10](#0-9)  before rejecting the transaction as invalid.
4. Repeating this at high volume (feeless, unsigned, `longevity: 25`, `propagate: true`) forces continual expensive verification work network-wide, degrading throughput for legitimate message delivery — the DoS.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.

pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
