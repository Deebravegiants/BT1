Found it: `Webhooks::Request#shop` (the `shop` field the caller receives via `WebhookMetadata.shop`) is read from the `X-Shopify-Shop-Domain` header, while `to_signable_string` — the data that the HMAC actually authenticates — is only the raw request body.

### Title
Webhook `shop` identity is taken from an unauthenticated header, not covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that library consumers use (via `WebhookMetadata#shop`) to determine which merchant/tenant a webhook belongs to, but that value is never included in the HMAC-signed payload, so it is not cryptographically bound to the signature that authenticates the request.

### Finding Description
`Request#shop` reads the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header directly: [1](#0-0) 

The HMAC is verified against `to_signable_string`, which returns only `@raw_body` — the shop header is not part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` and compares it with the `hmac-sha256` header value: [3](#0-2) 

This is the same class of defect the external report flags — a value acted upon in application logic ("field acted on") that is not covered by the authentication mechanism ("HMAC"), creating a binding mismatch: the equality that should hold is `hmac_verified(shop) == shop_used_by_app`, but in this implementation `shop` is read straight from an attacker-controllable header and the HMAC only verifies `raw_body`. Because `Request#shop` and `to_signable_string` are decoupled, an attacker who can reach the app's webhook endpoint (e.g., replaying or forging a POST with a valid-looking body/signature pair captured for shop A, or more directly, simply appending/overwriting the `X-Shopify-Shop-Domain` header on a request whose body+hmac corresponds to shop A) can cause the consuming application to process the payload while `data.shop` reports an arbitrary shop B of the attacker's choosing, since nothing in this gem re-derives or checks `shop` against the HMAC-covered content. [4](#0-3) 

### Impact Explanation
Applications that use `ShopifyAPI::Webhooks::Request` typically use `WebhookMetadata#shop` to look up the tenant's stored session/access token and to route webhook data into the correct tenant's records. If `shop` is not part of the authenticated data, an attacker who controls the header (for example replaying a previously-observed, still-signature-valid body from their own shop while swapping the shop-domain header) can make the host application attribute and process webhook data under a different merchant's identity — a cross-tenant data-confusion / cross-tenant access condition, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitability depends on whether the host application's webhook endpoint is reachable by an unprivileged party and whether the transport (e.g., a reverse proxy) allows attacker control of the `X-Shopify-Shop-Domain` header on an otherwise-valid request; this gem itself does no cross-check of `shop` against signed content, so the exposure is real for any app that trusts `data.shop` from this API without independent verification. This is a design/library-level gap rather than a proven end-to-end exploit against a specific deployment, so likelihood is moderate and contingent on host application behavior.

### Recommendation
Bind the shop identity to the authenticated payload: either require and verify `shop` against a field encoded and covered inside the signed body/HMAC computation (matching Shopify's actual webhook payload conventions), or, at minimum, document/enforce that `Request#shop` must not be trusted for authorization decisions unless independently corroborated with data inside the verified body. Consider including the shop-domain header value in `to_signable_string` verification logic or cross-checking it against a `shop_id`/`shop_domain` present in the parsed body before exposing it via `WebhookMetadata`.

### Proof of Concept
1. Attacker obtains (or generates, if they control any shop) a legitimately signed webhook request body + `X-Shopify-Hmac-Sha256` header for shop `attacker-shop.myshopify.com`.
2. Attacker resends the same body and HMAC header to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC, ignoring the shop header: [5](#0-4) 
4. The host application receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and processes the attacker's body content as if it belongs to the victim tenant.
