### Title
`RollbackAccounts::data_size()` fallback undercounts loaded-accounts-data-size cost for failed transactions - ([File: svm/src/account_loader.rs])

### Finding Description
When a transaction fails during `load_transaction_accounts` (e.g. it exceeds the requested `loaded_accounts_data_size` limit, references a program owned by a non-loader account, or a program account is not found), `load_transaction` converts it into a `FeesOnlyTransaction` and must still report a `loaded_accounts_data_size` for cost-model charging [1](#0-0) . The code branches on the `define_ltds_fee_only_semantics` feature gate: if active, it uses `loaded_transaction_data_size` — the size actually accumulated while walking accounts up to the point of failure; if inactive, it falls back to `tx_details.rollback_accounts.data_size() as u32` [2](#0-1) .

`RollbackAccounts::data_size()` only sums the data length of the fee-payer (and nonce, if present) accounts that will actually be persisted on rollback — it explicitly excludes every other account touched during loading (large token accounts, ALT-referenced accounts, program/programdata accounts, etc.) [3](#0-2) . Since a typical fee payer is a system-owned wallet with zero account data and no nonce is used, this fallback size is frequently **zero**, even though `AccountLoader`/accounts-db actually read (and, in the case of `MaxLoadedAccountsDataSizeExceeded`, read up to the requested limit of) potentially large account data before the failure occurred.

This behavior is directly confirmed by an existing test comment: "blowing limit with `define_ltds_fee_only_semantics` sets the size to the limit otherwise it is the raw sum of rollback sizes which here is zero" and the corresponding assertion that the fee-only loaded size is `0` when the feature is inactive despite real account bytes having been loaded (fee payer + program account sizes) [4](#0-3) .

An attacker can:
1. Craft a transaction that references many/large accounts (directly or via ALTs) so that loading accumulates significant `loaded_transaction_data_size`.
2. Design the transaction to fail load validation after the bulk of the accounts are read — e.g., by setting `SetLoadedAccountsDataSizeLimit` just below the true required size (triggering `MaxLoadedAccountsDataSizeExceeded`), or by referencing an invalid/non-loader-owned "program" id late in the instruction list (triggering `InvalidProgramForExecution`), or a missing program account (`ProgramAccountNotFound`).
3. Ensure the fee payer (and any nonce account) has zero or minimal account data.

The result is a `FeesOnlyTransaction` whose `loaded_accounts_data_size` is charged as (near) zero via `CostModel::calculate_loaded_accounts_data_size_cost` [5](#0-4) , even though accounts-db actually performed the reads for those large accounts. This breaks the invariant that the loaded-accounts-data-size estimate upper-bounds real read work performed.

### Impact Explanation
This causes systemic underpricing of the loaded-accounts-data-size I/O component of the cost model for a broad class of failed transactions whenever `define_ltds_fee_only_semantics` is not active on the cluster. An attacker can repeatedly submit transactions engineered to fail late in account loading (after reading large accounts) while being charged ~0 bytes for loaded-accounts-data-size, allowing cheap admission of expensive account-load work into blocks — degrading validator throughput/I/O and enabling a low-cost resource-exhaustion vector against block producers. This matches the "systemic underpriced I/O work admitted into every block" impact category (cost-model / resource-accounting correctness).

### Likelihood Explanation
This is fully reachable by an unprivileged user broadcasting ordinary transactions to a public RPC/TPU: no special privileges, no leader/validator control, and no snapshot manipulation are required. The only precondition is that the feature gate `define_ltds_fee_only_semantics` (declared in `feature-set/src/lib.rs` and `svm-feature-set/src/lib.rs`) is not yet activated cluster-wide — which is the default/legacy behavior path explicitly retained in the code (`else` branch) and exercised by the project's own test suite. Constructing the failing transaction (compute-budget `SetLoadedAccountsDataSizeLimit` just under actual needs, or a bogus/missing program id) is straightforward and fully deterministic, making the exploit trivially repeatable across many transactions in a block.

### Recommendation
Remove the legacy fallback branch (or make `loaded_transaction_data_size` the sole source of truth) so that `FeesOnlyTransaction::loaded_accounts_data_size` always reflects the actual accumulated `loaded_transaction_data_size` computed during loading, regardless of feature-gate state, matching the already-corrected `define_ltds_fee_only_semantics` behavior. If backward-compatible rollout is required, expedite activation of `define_ltds_fee_only_semantics` cluster-wide and treat the old rollback-only sizing as deprecated/insecure.

### Proof of Concept
Rust unit test to add to `svm/src/account_loader.rs` test module (mirrors existing `test_load_accounts_v1_instructions_sysvar_overflow`-style tests), asserting the undercount when the feature is inactive:

```rust
#[test]
fn test_fee_only_loaded_accounts_data_size_undercounts_without_feature() {
    // Build a mock bank where the fee payer has zero-length data,
    // and a second account referenced by the tx has large data (e.g. 10_000 bytes).
    let fee_payer = Pubkey::new_unique();
    let large_account = Pubkey::new_unique();
    let mut mock_bank = TestCallbacks::default();
    mock_bank.accounts_map.insert(
        fee_payer,
        (AccountSharedData::new(1_000_000, 0, &Pubkey::default()), 0),
    );
    mock_bank.accounts_map.insert(
        large_account,
        (AccountSharedData::new(1, 10_000, &Pubkey::default()), 0),
    );

    // Build a transaction: request loaded_accounts_data_size_limit just under
    // TRANSACTION_ACCOUNT_BASE_SIZE*2 + 10_000, so loading fails with
    // MaxLoadedAccountsDataSizeExceeded *after* the fee payer & large_account
    // have already been read.
    // (message construction omitted for brevity — uses `large_account` as a
    // writable, non-signer account, program id set to a valid loader-owned id.)

    let mut account_loader = (&mock_bank).into();
    let mut error_metrics = TransactionErrorMetrics::default();

    let validation_result = TransactionValidationResult::Loadable(ValidatedTransactionDetails {
        rollback_accounts: RollbackAccounts::FeePayerOnly {
            fee_payer: (fee_payer, mock_bank.accounts_map[&fee_payer].0.clone()),
        },
        loaded_accounts_bytes_limit: /* just below true required size */ 200,
        loaded_fee_payer_account: LoadedTransactionAccount {
            account: mock_bank.accounts_map[&fee_payer].0.clone(),
            loaded_size: TRANSACTION_ACCOUNT_BASE_SIZE,
        },
        ..ValidatedTransactionDetails::default()
    });

    // feature_set.define_ltds_fee_only_semantics = false (default/inactive)
    let load_result = load_transaction(
        &mut account_loader,
        &sanitized_message, // references fee_payer + large_account
        validation_result,
        &mut error_metrics,
        &Rent::default(),
    );

    let TransactionLoadResult::FeesOnly(fees_only) = load_result else {
        panic!("expected FeesOnly result");
    };

    // BUG: reported loaded_accounts_data_size is 0 (fee payer has no data),
    // even though ~10,000+ bytes were actually read from accounts-db before
    // the limit was hit.
    assert_eq!(fees_only.loaded_accounts_data_size, 0);

    // The cost model then charges ~0 for loaded-accounts-data-size:
    let cost = CostModel::calculate_loaded_accounts_data_size_cost(
        fees_only.loaded_accounts_data_size,
        &FeatureSet::default(), // define_ltds_fee_only_semantics inactive
    );
    assert_eq!(cost, 0); // should be > 0 to reflect the real 10KB+ read
}
```

Expected assertion demonstrating the bug: `fees_only.loaded_accounts_data_size == 0` and the derived cost-model charge `== 0`, despite the loader having actually read the fee payer plus a 10,000-byte account from accounts-db before failing — confirming `RollbackAccounts::data_size()` undercounts true read work and lets the attacker underpay for loaded-accounts-data-size on failed transactions.

            total_size = total_size.saturating_add(account.data().len());
