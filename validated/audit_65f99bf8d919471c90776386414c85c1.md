### Title
Webhook `shop` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` value used to route and process the webhook comes from an unauthenticated HTTP header. This breaks the intended identity binding `HMAC-covered bytes == data acted upon`, since the tenant identifier (`shop`) is acted upon by the handler but excluded from what the HMAC actually authenticates.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against the HMAC, i.e. it verifies the body bytes, never the `shop` header: [3](#0-2) 

`Webhooks::Registry.process` then passes this unauthenticated `request.shop` straight into `WebhookMetadata`, which is what app handlers use to determine which tenant/session the payload belongs to: [4](#0-3) [5](#0-4) 

This is asymmetric with how the gem handles the equivalent OAuth callback binding: `Auth::Oauth::AuthQuery#to_signable_string` explicitly folds `shop` into the signed string so the shop is cryptographically bound to the HMAC: [6](#0-5) 

For webhooks, no such binding exists — the identity equality that should hold is `shop authenticated by HMAC == shop acted upon by handler`, but instead the `shop` acted upon is taken from a header that is entirely outside the HMAC-covered bytes.

### Impact Explanation
Any unprivileged internet user who can obtain one genuinely-signed webhook body+HMAC pair (e.g. from their own shop, which they legitimately control and which receives real Shopify webhooks) can replay that exact body/HMAC pair against the same public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim merchant. `HmacValidator.validate` will accept the request because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any app that uses `data.shop` to select the tenant/session context to act on (e.g. to look up which merchant's access token or store to update) will process attacker-supplied data under the wrong tenant identity — a cross-tenant confusion enabled purely by this gem's failure to bind the shop to the signed bytes.

### Likelihood Explanation
Webhook endpoints are, by design, public, unauthenticated HTTP endpoints that must accept POSTs from the internet, so an attacker fully controls all headers of the request including `x-shopify-shop-domain`. Obtaining one genuinely HMAC-signed payload only requires operating (or trialing) any Shopify store and installing the target app, which is trivial and requires no privileged access, leaked secrets, or social engineering.

### Recommendation
Include the shop domain (and other Shopify-supplied identifying headers such as `topic`/`api-version`/`webhook-id` if they influence handler behavior) inside `Request#to_signable_string`, mirroring the approach used in `Auth::Oauth::AuthQuery#to_signable_string`, so that `HmacValidator.validate` cryptographically authenticates the `shop` value before it is exposed to handlers via `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook: body `B` with header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new POST to the app's public webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Request#hmac` still equals `H`, and `Request#to_signable_string` still returns `B`, so `HmacValidator.validate` in [7](#0-6)  succeeds.
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"`, as shown in [8](#0-7) , and the app's handler processes attacker-controlled body `B` believing it originated from `victim.myshopify.com`.
