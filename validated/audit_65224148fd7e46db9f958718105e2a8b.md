### Title
Webhook `shop` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing tenant spoofing in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then trusts the header-derived `shop` value to construct `WebhookMetadata` and dispatch it to the app's handler. This breaks the binding "the shop that produced the signed bytes == the shop attributed to the delivered event."

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and `shop` (along with `topic` and `webhook_id`) is pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately trusts the unauthenticated `request.shop` value to build the metadata delivered to the app's handler: [3](#0-2) 

Since the app's `client_secret` is the same across every shop that installs the app, any merchant who installs the app receives genuine, validly-HMAC-signed webhook deliveries for their own store. Because the signature covers only the body and not the `shop` header, that same attacker-controlled shop can replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because the body bytes are unchanged, and `Registry.process` forwards `WebhookMetadata` claiming the victim's shop as the origin, even though the payload content is attacker-controlled.

This is a case of "bytes verified versus bytes parsed": the HMAC verifies the body, but the identity-critical `shop` field used downstream is parsed from bytes that were never covered by that verification.

### Impact Explanation
Any application relying on this gem's webhook validation to bind a delivered payload to a specific tenant (which is the documented usage pattern — `WebhookMetadata#shop` is the only tenant identifier surfaced to `WebhookHandler#handle`) can be made to process attacker-supplied data under another merchant's identity. Depending on the handler's logic (e.g., writing order/product/customer data keyed by `shop`), this enables cross-tenant data injection/corruption using only a low-cost step of installing the app on an attacker-controlled shop — no access token, API secret, or privileged account is required. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: any user can install a public app on their own dev/trial store, capture the app's legitimate webhook delivery (raw body + valid HMAC), and replay it to the app's public webhook endpoint with a modified `shop` header. No secrets need to be forged — the attacker reuses a genuine signature that Shopify itself produced for their own webhook. The only constraint is that the injected payload content is whatever data the attacker can arrange to exist in their own store's webhook body.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise verify that the header-derived `shop` matches an independent, trusted identity, before constructing `WebhookMetadata`. Concretely, `HmacValidator`/`Request#to_signable_string` for webhooks should incorporate the `shop`/`topic` headers into the HMAC computation (mirroring Shopify's account for this in later API guidance), or `Registry.process` should cross-check `request.shop` against a shop already known/authorized for that specific webhook delivery (e.g., via the `webhook_id` looked up against the registration created for that specific shop) rather than trusting the raw header value unconditionally.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) so Shopify sends a body `B` with header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Capture `B` and the valid HMAC value.
3. Replay a POST to the app's webhook endpoint with unchanged body `B` and unchanged HMAC header, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in [1](#0-0)  succeeds because it only checks `B` against the HMAC.
5. `Registry.process` in [3](#0-2)  dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler, which processes attacker-controlled data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
