### Title
Fee-on-transfer tokens are escrowed at their pre-fee amount in the Tron `IntentGatewayV2.placeOrder` non-predispatch path, causing under-collateralized escrow that reverts or shorts fills/refunds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes `reducedInputs` (the amount credited to escrow) directly from the user-submitted `order.inputs[i].amount`, then calls `safeTransferFrom` for that same nominal amount and credits `_orders[commitment][token] += reducedInputs[i].amount` without ever checking the gateway's actual token balance before/after the transfer. For fee-on-transfer ERC20 inputs, the contract will hold strictly less than the amount it records in escrow, exactly mirroring the Metrom root cause.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

`order.inputs[i].amount` (the gross, user-specified amount) is passed straight into `safeTransferFrom`, and the escrow ledger `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, which is derived only by subtracting the protocol fee from the original nominal amount: [2](#0-1) 

Unlike the main EVM `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf(address(this))` before and after the `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment/escrow (`evm/src/apps/IntentGatewayV2.sol:320-322`), the Tron contract never reconciles actual received balance against the escrow bookkeeping in this code path. For a fee-on-transfer token, the gateway's real balance after `safeTransferFrom` will be `amount - fee`, but `_orders[commitment][token]` is incremented by `amount - protocolFee`, i.e. a value larger than what the contract actually holds.

The predispatch branch partially self-corrects by checking `balanceOf(dispatcher)` against `requiredAmount` before sweeping (`evm/tron/contracts/apps/IntentGatewayV2.sol:428-429`), but this check uses the un-reduced nominal `requiredAmount` rather than the actual escrowed `reducedInputs[i].amount`, and still reverts the whole `placeOrder` transaction outright for any fee-on-transfer token rather than adjusting amounts — so no order with a fee-on-transfer input can ever be placed via predispatch, and in the direct (non-predispatch) branch the order succeeds but leaves the escrow ledger overstated relative to the real token balance.

### Impact Explanation
Because `_orders[commitment][token]` overstates the gateway's real holdings, later settlement (`withdraw`, invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow`, or from `cancelOrder`) will attempt to transfer out `amount = body.tokens[i].amount` (up to the escrowed value) as seen in: [3](#0-2) 

This can revert (freezing the order's escrow permanently, since the failing transfer blocks `withdraw` for that commitment) or, in a multi-input order sharing a token balance across commitments, allow the contract's ERC20 balance to become insufficient to honor legitimate withdrawals of other unrelated orders that used the same token, effectively causing shared insolvency/fund freezing across users of that token — a direct analog to the reported Metrom issue, but affecting an unprivileged solver/relayer settlement path in the intents system rather than an admin-only campaign creator.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with an arbitrary ERC20 input token, including any fee-on-transfer token; the intent-gateway design explicitly documents "any ERC20 is allowed" style flexibility (as evidenced by the main EVM gateway's dedicated fee-on-transfer handling and tests). The Tron gateway is a straight fork of the same contract that omits the balance-reconciliation fix present upstream, so the vulnerable path is trivially reachable from a single `placeOrder` transaction with a fee-on-transfer token, with no special permissions required.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: for each ERC20 input in the non-predispatch (and predispatch sweep) branches of `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, snapshot `balanceOf(address(this))` (or `balanceOf(dispatcher)`) before and after the transfer, replace `order.inputs[i].amount` with the actual received delta, and only then compute `reducedInputs`/`commitment`/`_orders[commitment][token]` from that real amount, so escrow accounting can never exceed the gateway's actual token balance.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 (`FeeOnTransferToken`) and fund `user` with 10,000 tokens, mirroring the existing test helper already present in the EVM test suite: [4](#0-3) 
2. `user` approves the Tron `IntentGatewayV2` for `inputAmount = 1000e18` and calls `placeOrder` with a single ERC20 input of `1000e18` and `protocolFeeBps = 0`, taking the non-predispatch branch (`evm/tron/contracts/apps/IntentGatewayV2.sol:450-469`).
3. The gateway's real token balance after `safeTransferFrom` is `990e18` (1% fee deducted), but `_orders[commitment][token]` is set to `1000e18` (no protocol fee, no balance check applied).
4. When the order is later filled/settled and `withdraw` attempts to pay out `1000e18` from `_orders[commitment][token]` ( [3](#0-2) ), the ERC20 transfer reverts because the gateway only holds `990e18`, permanently freezing that order's funds (or, if other orders share the token balance, draining tokens rightfully belonging to other users).

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
