### Title
`challengePeriod() == 0` disables the fishermen veto window for `HandlerV2` message delivery - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`EvmHost.challengePeriod()` returns the raw `_hostParams.challengePeriod` value with no lower bound, and `HandlerV2` treats `0` as "challenge period disabled" rather than "not yet configured." Any state machine (or the initial host deployment) whose `challengePeriod` param is unset or intentionally left at `0` allows a relayer to deliver POST/GET requests and timeouts the instant a state commitment is stored, with zero time for fishermen to veto a fraudulent commitment — the same class of bug as the `getNextEntropy` finding: a default/uninitialized numeric value (`0`) is read and silently treated as a valid "pass" condition instead of gating the operation or reverting.

### Finding Description
`EvmHost.challengePeriod()` simply returns the configured parameter: [1](#0-0) 

`HandlerV2.handlePostRequests` and `handleGetRequestTimeouts` gate delivery on this value with an explicit `!= 0` escape hatch: [2](#0-1) [3](#0-2) 

That is, the check `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` is a no-op whenever `challengePeriod` is `0`. Since `_hostParams.challengePeriod` is a plain `uint256` field on the `HostParams` struct with no dedicated initialization guard (unlike `_latestStateMachineHeight`, which the codebase explicitly documents as "0 = unsupported" and resets to `1` rather than `0` after a veto to avoid this exact collision — see `deleteStateMachineCommitmentInternal`), any host whose admin has not yet called `updateHostParams` to set a nonzero challenge period — or who deliberately/mistakenly sets it to `0` — accepts every state commitment as immediately actionable. This mirrors the `EntropyGenerator.getNextEntropy()` bug: a storage slot that is legitimately `0` before configuration is indistinguishable from a slot that is `0` by deliberate design, and the reachable, permissionless code path (`HandlerV2.handlePostRequests`/`handleGetRequestTimeouts`, callable by any relayer submitting a message) treats the ambiguous zero as "skip the safety check" rather than reverting or requiring explicit configuration.

The challenge period exists specifically so that `pallet-fishermen`/fisherman infrastructure has a window to veto a bad state commitment (`deleteStateMachineCommitment`/`vetoes`) before any funds move on faith of that commitment. With `challengePeriod == 0`, this entire security window collapses to zero, and a malicious or compromised consensus-proof submission (or one relying on a fraudulent-but-later-provably-invalid commitment) can be immediately exploited by any relayer delivering a POST/GET request before the fishermen have any chance to veto.

### Impact Explanation
If `challengePeriod` is `0` — whether because a state machine's host params were never explicitly set post-deploy, or an admin misconfiguration — any submitted (even eventually-vetoable) state commitment can be used instantly to deliver POST/GET requests and drain funds tied to app-level `onAccept` logic (e.g., token bridge mints, intent fills) before fishermen can react. This is a concrete freezing/theft-of-funds vector reachable by a single relayer-submitted message, consistent with the required "concrete theft ... or unsound state commitment" impact bar.

### Likelihood Explanation
Likelihood depends on an operational/deployment gap (challenge period unset or zero) rather than a pure code-logic bug reachable in all deployments, mirroring the C4 report's acknowledged validity nuance ("valid because there could be a timeframe where ..." was confirmed valid by the sponsor despite deployment scripts normally setting it). Any state machine added via `updateHostParams` (e.g., in `testCanAddwhitelistedStateMachines`) inherits a fresh, unset `challengePeriod` for that mapping only if per-state-machine values are used; here `challengePeriod` is host-global, so the window exists primarily at genesis/before first `updateHostParams`, or if an admin explicitly sets it to `0` (e.g., for a testnet-configured value carried into production, or a governance action lowering it to `0`).

### Recommendation
Do not let `0` mean "disabled." Either (a) enforce a nonzero minimum `challengePeriod` in `updateHostParams`/host construction and revert on `0`, or (b) change `HandlerV2` to always enforce `challengePeriod > delay ⇒ revert`, with a dedicated `MIN_CHALLENGE_PERIOD` constant substituted when the configured value is `0`, so unconfigured/misconfigured state can never be treated as "no waiting required."

### Proof of Concept
1. Deploy `EvmHost` with `HostParams.challengePeriod = 0` (default, or via `updateHostParams` before an explicit nonzero value is set).
2. Handler/consensus proof stores a new `StateCommitment` via `storeStateMachineCommitment` (`EvmHost.sol:687-699`).
3. Immediately (same block, `delay == 0`), a relayer calls `HandlerV2.handlePostRequests` with a valid MMR proof against that commitment.
4. `challengePeriod = host.challengePeriod()` returns `0`; the guard `challengePeriod != 0 && challengePeriod > delay` evaluates `false`, so no revert occurs — the request is dispatched without allowing fishermen any veto window, in contrast to the intended non-zero-challenge-period design elsewhere in the protocol.
