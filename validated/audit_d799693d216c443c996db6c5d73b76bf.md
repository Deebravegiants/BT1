Based on my investigation, I found a plausible analog rooted in decimal/precision conversion logic in `pallet-hyper-fungible-token`, structurally similar to the Defibox root cause: an unbacked/unvalidated assumption about a token's on-chain behavior (there, EMOON's burnable supply; here, an asset's decimal precision) that silently breaks the bridge's accounting.

### Title
Silent no-op decimal scaling in `convert_to_balance`/`convert_to_erc20` can mint/refund the wrong amount when `erc_decimals < local_decimals` - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token` converts amounts between a remote EVM token's decimals (`erc_decimals`, stored in `Precisions`) and the local asset's decimals (`local_decimals`, read live from `Assets::decimals()`) using `saturating_sub` when computing the scaling exponent.

### Finding Description
`convert_to_balance` and `convert_to_erc20` compute the scale factor as `10^(erc_decimals.saturating_sub(local_decimals))`: [1](#0-0) 

This assumes `erc_decimals >= local_decimals` always holds. The pallet even declares an error variant documenting this invariant, `ErcDecimalsBelowLocal` ("Configured ERC decimals are less than the local asset's decimals; precision conversion requires erc_decimals >= local_decimals"): [2](#0-1) 

However, in the actual conversion call sites — `on_accept` (mint path) and `on_timeout` (refund path) in `module.rs`, and `send` in `lib.rs` — `local_decimals` for non-native assets is read live via `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)`, not fixed at registration time: [3](#0-2) 

`Precisions` (the `erc_decimals` side) is only set once via `register_token`/`update_token` at registration/update time, per the storage/extrinsic documentation: [4](#0-3) 

If the underlying `pallet-assets` asset's decimals metadata is later changed (a routine, non-privileged-relative-to-this-pallet action available to the asset's own issuer/owner) to a value greater than the recorded `erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` becomes `0` instead of underflowing/erroring. The conversion then silently divides/multiplies by `10^0 = 1` — i.e., it does **no scaling at all** — instead of raising `ErcDecimalsBelowLocal`. This means an ERC20-precision amount from the remote chain (e.g. 18 decimals) is minted 1:1 as if it were already in the (now higher) local decimal precision, over-minting the local asset by a factor of `10^(local_decimals - erc_decimals)`, or conversely under-crediting an ERC20 amount on `send`, breaking the escrow backing.

This mirrors the Defibox root cause exactly at the structural level: a fixed assumption baked into the bridge/AMM contract (constant decimals / non-burnable pot) that the paired asset's actual on-chain behavior (mutable decimals metadata / external burn) violates, with no live safety check that would have caught the exact scenario the error variant names.

### Impact Explanation
An asset decimals change after registration turns every subsequent cross-chain delivery for that asset into an unbacked mint (or, on the `send`/refund path, an incorrect burn/refund amount), permanently breaking the 1:1 backing between the escrowed/burned local asset and the amount represented on the remote HyperFungibleToken contract. This is a direct fund-safety break in the token bridge mint/burn accounting reachable purely by a relayed message being processed after the decimals drift — no attacker action on the ISMP layer is needed once the precondition (decimals drift) exists.

### Likelihood Explanation
Likelihood depends on whether `Precisions`/registration flow actually re-validates `erc_decimals >= local_decimals` at every mint/burn (I could not fully confirm this in the time available — `register_token`'s and `update_token`'s exact enforcement logic in `lib.rs` was not read before the tool budget ran out). If the check is enforced only once at registration time and not re-checked against the live `Assets::decimals()` read used in `on_accept`/`on_timeout`, the drift scenario is entirely plausible for any asset whose metadata is not permanently frozen, making this a real, if narrower-window, risk rather than a purely theoretical one.

### Recommendation
Replace `saturating_sub` with a checked/explicit comparison in `convert_to_balance`/`convert_to_erc20` that returns `Err(ErcDecimalsBelowLocal)` (rather than silently coercing the exponent to zero) whenever `erc_decimals < local_decimals`, and re-validate this invariant against the live `Assets::decimals()` value on every `on_accept`/`on_timeout`/`send` call, not only at `register_token` time.

### Proof of Concept
1. Register asset `X` (non-native) via `register_token` with `local_decimals = 6` and `Precisions[X][EVM-1] = erc_decimals = 18` (valid, `erc_decimals >= local_decimals`).
2. The asset's issuer calls `pallet-assets::set_metadata` (or equivalent) to change `X`'s decimals to `24`.
3. A legitimate cross-chain `Send` message from `EVM-1` for asset `X` arrives; `on_accept` reads `local_decimals = 24` live, `erc_decimals = 18` from storage.
4. `erc_decimals.saturating_sub(local_decimals) = 18.saturating_sub(24) = 0`, so `convert_to_balance` divides by `10^0 = 1` instead of the mathematically required multiply/divide, minting the beneficiary an amount `10^6` times larger than the ERC20 amount actually represents.

Note: I was unable to fully verify, within the available tool budget, whether `register_token`/`update_token` re-checks this invariant against live decimals on every delivery — this should be confirmed by reading the full `register_token`/`update_token` implementations in `modules/pallets/hyper-fungible-token/src/lib.rs` before treating this as conclusively exploitable end-to-end.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
