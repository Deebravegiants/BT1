### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC only over the raw request body, while the `shop` (and `topic`/`webhook_id`) values used by the registry to route/attribute the webhook are read directly from unauthenticated HTTP headers. This breaks the intended binding `hmac == HMAC(secret, body ‖ shop)`; in reality it is only `hmac == HMAC(secret, body)`, so the `shop` field can be freely substituted after a genuinely signed body is obtained.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then forwards the header-derived, unverified `shop`/`topic`/`webhook_id` straight to the app's handler: [3](#0-2) 

`HmacValidator.validate` simply compares the computed signature of `to_signable_string` against the received `hmac`; it has no notion of `shop` at all: [4](#0-3) 

Because the app's `api_secret_key` (`client_secret`) is a single, app-wide secret shared across every installing shop (not per-tenant), any merchant who installs the app receives genuinely-signed webhook deliveries for their own store. Such a merchant is an "unprivileged" party with respect to other tenants of the same app. That merchant can capture one of their own legitimately-signed webhook deliveries (valid `raw_body` + valid `hmac`) and resend the identical body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with another shop's domain. `HmacValidator.validate` still returns `true` because only the body is checked, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming `shop: <victim-shop>` even though the payload actually originated from and was signed for the attacker's own shop.

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure: the equality that should hold — `verified_bytes == (body, shop)` — is really only `verified_bytes == body`, letting `shop` be forged independently of the proof of authenticity.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as intended and documented) to decide which tenant's records to update, delete, or emit side effects for, can be tricked into applying attacker-controlled webhook data to another merchant's account/store. This is a cross-tenant access/write vulnerability — the attacker never needs the victim's credentials, only their own valid app installation, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Likelihood is high for any determined but otherwise unprivileged app user: obtaining one authentic signed webhook from their own store is trivial (Shopify sends these automatically to any installed app), and replaying an HTTP POST with a modified header is a common web-request-tampering technique requiring no special access to the gem's secrets.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the signable content that is checked in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the header-derived `shop` to the verified payload (e.g., by requiring the host app to independently reconcile the header shop against a shop already known to be the same tenant that the session/webhook subscription was registered for) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving genuine Shopify-signed webhook POSTs (valid `raw_body` and `hmac-sha256` header) at their configured endpoint.
2. Attacker captures one such delivery (`raw_body`, `hmac-sha256`, `topic`).
3. Attacker sends a forged HTTP request to the app's webhook endpoint with the same `raw_body`/`hmac-sha256` header but `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because only `raw_body` is checked (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-controlled data as if it belonged to the victim shop.
