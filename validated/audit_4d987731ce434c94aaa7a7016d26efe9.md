### Title
Unbounded RAY market valuation overflows during accrual and permanently freezes repayment, withdrawal, and liquidation - (File: common/src/rates/index.rs)

### Summary
A market whose scaled debt multiplied by the borrow index no longer fits in `i128` cannot complete interest accrual. Every pool mutation synchronizes the market before applying the requested operation, so the overflow blocks `withdraw`, `repay`, liquidation-driven settlement, and even `update_indexes` itself.

### Finding Description
`accrue_step` computes `new_total_debt` through `borrowed.mul(new_borrow_index)` in `calculate_supplier_rewards`. [1](#0-0) [2](#0-1)  That multiplication eventually invokes `mul_div_half_up`, which returns `MathOverflow` when the exact RAY-scaled result does not fit in `i128`. [3](#0-2) [4](#0-3) 

The pool runs this accrual before each market leg through `synced_market`, and `update_indexes` runs the same synchronization independently. [5](#0-4) [6](#0-5)  Consequently, once aggregate debt valuation crosses the representable RAY ceiling, no mutation can reach its repayment or withdrawal logic; the call reverts during synchronization. `repay::accounting` and `withdraw::accounting` both call `load_leg`, which synchronizes before their settlement logic. [7](#0-6) [8](#0-7) 

The borrow-index ceiling does not prevent this condition because it is applied only to the index; the separate `borrowed * borrow_index / RAY` valuation can overflow before the index reaches `MAX_BORROW_INDEX_RAY`. [9](#0-8)  The repository’s integration test demonstrates that a sufficiently large borrowed book under sustained high-utilization accrual reaches this state, after which both repayment and withdrawal return `MathOverflow`. [10](#0-9) 

### Impact Explanation
All suppliers’ funds in the affected `(hub_id, asset)` market become permanently unavailable, borrowers cannot repay, liquidators cannot unwind insolvent accounts, and the market cannot advance indexes. Because revenue is included in total supplied shares, unclaimed protocol yield is likewise frozen. The impact is permanent freezing of user funds and unclaimed yield.

### Likelihood Explanation
An unprivileged borrower can increase `borrowed` through controller `borrow`, subject to collateral, liquidity, utilization, and configured caps; accrual then monotonically raises `borrow_index`. A permissionless `update_indexes` call exposes the overflow once the aggregate scaled debt and index cross the arithmetic ceiling. Likelihood is bounded by the need for an exceptionally large admitted market and sustained debt accrual, so this is Medium rather than High.

### Recommendation
Detect unrepresentable market valuations before performing index accounting and provide an escape path that does not depend on the overflowing `accrue_step`. For example:

- cap or clamp aggregate scaled debt before its RAY valuation can exceed `i128`;
- add an explicit insolvency/quarantine state reachable when valuation overflows, preserving withdrawal or settlement logic that does not require recomputing aggregate accrued value;
- compute the interest delta with a saturating or widened domain and reduce stored scaled balances before overflow;
- at minimum, allow full repayment/write-off and liquidation settlement while skipping ordinary interest accrual once the valuation ceiling is reached.

### Proof of Concept
1. An attacker supplies collateral through controller `supply`.
2. Through controller `borrow`, the attacker creates a very large debt position in a target market that admits sufficiently large caps.
3. The market remains at high utilization while `update_indexes` compounds the borrow index.
4. `borrowed * new_borrow_index / RAY` becomes unrepresentable in `i128` inside `calculate_supplier_rewards`.
5. A subsequent call to controller `update_indexes`, `repay`, `withdraw`, or `liquidate` invokes pool market synchronization and reverts with `MathOverflow`.
6. No subsequent market operation can proceed because every mutation starts with the same overflowing synchronization.

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
