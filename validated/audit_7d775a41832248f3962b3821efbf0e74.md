### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header — which is never included in the signed content — as the tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`; none of the Shopify headers, including `shop-domain`, are part of the signable string: [1](#0-0) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. body-only) and then builds `WebhookMetadata` directly from `request.shop`, the unauthenticated header value, and hands it to the app's handler as the tenant context: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field, using a single app-wide `Context.api_secret_key` shared across all shops that install the app: [3](#0-2) 

Because the HMAC secret is the app's `client_secret` (identical for every merchant using the app) and the signature covers only the body, the binding that should hold — `authenticated_shop == shop_used_for_tenant_context` — does not hold. Any party who can obtain one validly-signed webhook body (e.g., by installing the app on their own store and receiving their own legitimate webhooks) can replay that exact body to the app's public webhook endpoint while substituting the `shop-domain` (and `x-shopify-shop-domain`) header for a different, victim merchant's domain. The HMAC check in `Registry.process` still passes because it never inspected the header, so `WebhookMetadata#shop` ends up asserting an arbitrary shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (the value the gem hands the developer's handler) to key any tenant-scoped operation — looking up a session/access token by shop, writing merchant data, or triggering shop-specific side effects — an attacker who is merely a legitimate low-privilege installer of the app on their own shop can forge webhook events attributed to any other shop, causing cross-tenant data confusion within the app. This matches the Critical "cross-tenant access" impact category, since the boundary between one merchant's webhook data and another's is broken purely by an unauthenticated header value.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled store (a normal, unprivileged action for any Shopify app that supports public installs), (2) capturing one legitimate webhook payload/HMAC sent to that store's endpoint, and (3) replaying it with a modified shop header. No access token, `client_secret`, or privileged account is needed — the shared app secret and body-only signature are both intrinsic to how this gem validates and exposes webhook identity.

### Recommendation
Do not treat `request.shop` as authenticated tenant identity from the HMAC check alone. Either include the shop domain (and other identifying headers) in the signed/verified content, or require the host application to cross-check `request.shop` against a shop that is already known/registered (e.g., matches a shop with a stored, active session) before acting on `WebhookMetadata#shop`. At minimum, the library should document explicitly and loudly that `shop` in `WebhookMetadata` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification by the app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing legitimate OAuth so the app is active for that store.
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's webhook endpoint with body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256` computed over `B` using the app's single `client_secret`.
3. Attacker captures `B` and the valid HMAC value (e.g., by observing their own webhook, or by triggering webhooks with attacker-chosen body content such as an order note).
4. Attacker replays a POST to the same app endpoint with the identical body `B` and identical valid HMAC, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `HmacValidator.validate(request)`, which only checks the body/HMAC pair — this passes — then invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, as shown in [2](#0-1) , causing the app to process attacker-controlled data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
