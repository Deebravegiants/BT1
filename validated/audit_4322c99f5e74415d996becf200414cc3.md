### Title
Fee tokens are permanently stranded in the swap action when `circomData.relay == address(0)` while `variableRate`/`flatFee` are non-zero - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` always subtracts `totalFee = hinkalFee + (feeToken==outputToken ? relayFee : 0)` from `swappedAmount` to compute `amountToSendToHinkal`, but the actual fee transfer is routed through `sendToRelay`, which silently no-ops whenever `relay == address(0)`. Because `circomData.relay` is an attacker-supplied field with no on-chain or circuit constraint forcing it to be non-zero when fees are non-zero (unlike the internal-transfer path which enforces `"relay not paid"`), an attacker can set `relay = address(0)` and any positive `flatFee`/`variableRate`, causing `totalFee` worth of `outputToken` to be permanently stuck in the action contract's balance instead of reaching either the relay or Hinkal.

### Finding Description
The claimed equality: `tokens leaving the action == -deltaAmountChanges Hinkal sent it (i.e., amountToSendToHinkal returned to Hinkal + fee actually paid out to relay)` should equal `swappedAmount` (all tokens the action received from the router).

Code path:
1. `ExternalActionSwap.swap` (contracts/external-actions/swaps/ExternalActionSwap.sol:63-93) computes `swappedAmount`, `relayFee`, `hinkalFee`, calls `sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken)` (or the two-token variant), then computes `totalFee` and `amountToSendToHinkal = swappedAmount - totalFee`, transferring only `amountToSendToHinkal` back to `msg.sender` (Hinkal).
2. `Transferer.sendToRelay` (contracts/Transferer.sol:178-190) guards with `if (relay != address(0) && actualAmount > 0)`. If `relay == address(0)`, the fee transfer is skipped entirely — no revert, no redirection to Hinkal.
3. `circomData.relay` is fully attacker-controlled calldata with no circuit/on-chain check requiring it be non-zero whenever `flatFee`/`variableRate` are non-zero on the external-action (`_externalTransact`) path. The only such guard, `require(circomData.relay == address(0) || hasPaidToRelay, "relay not paid")`, exists solely in `_internalTransact` (contracts/Hinkal.sol:226-229) and is never invoked for swaps, which go through `_externalTransact` → `IExternalActionV2.runAction`.
4. Back in `Hinkal.transact`, the balance-equality check (contracts/Hinkal.sol:137-146) only verifies `balanceDif == amountChanges[i] + utxoAmount`. Since `utxoAmount` is derived from the UTXO the action itself returned (`amountToSendToHinkal`), and `balanceDif` on the output token equals exactly what the action sent back (`amountToSendToHinkal`), this check trivially passes — it never verifies that `totalFee` actually left the action contract to any recipient.

Net effect: `totalFee` of `outputToken` is received by the action from the router, never transferred to relay (no-op) and never transferred to Hinkal (deliberately excluded from `amountToSendToHinkal`), so it remains as excess ERC20 balance sitting in the action contract, with no accounting trail and no built-in mechanism shown in this contract to recover it.

### Impact Explanation
Protocol/relay fee tokens (`totalFee` worth of `outputToken`) become stuck in the swap action contract (e.g. `LifiExternalAction`) rather than reaching Hinkal or the relay — this is a permanent freezing of protocol/relay fees, matching the "High" severity bucket. Whether this later becomes outright theft by a subsequent caller depends on how `callRouter`/`LifiExternalAction` computes `swappedAmount` (e.g., balance-diff vs. absolute-balance based); that implementation was not available to inspect in this session, so the "second attacker drains it into their own UTXO" escalation to a repeatable steal-by-anyone path is plausible but unverified. The freezing portion of the impact is confirmed by the code shown.

### Likelihood Explanation
Trivial precondition: the caller need only set `circomData.relay = address(0)` while `circomData.feeStructure.flatFee > 0` and/or `variableRate > 0` on a normal, unprivileged swap transaction they are fully entitled to construct (their own deposit/UTXO, their own proof). No special role, no race condition, and it is repeatable on every swap transaction the attacker performs. `circomData.relay` is not enforced by the audited circuit-side checks nor the on-chain `performHinkalChecks`/`dimensionsCheck` calls referenced in this scope.

### Recommendation
Enforce the same invariant used in `_internalTransact` for the external-action swap path: require `circomData.relay != address(0)` whenever `flatFee > 0 || variableRate > 0`, or alternatively redirect any fee that cannot be sent to `relay` (i.e., when `relay == address(0)`) into `amountToSendToHinkal`/the resulting UTXO, so `totalFee` is never silently dropped from the balance accounting.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` (or a minimal harness inheriting `ExternalActionSwap`) with a mock router that returns a fixed `swappedAmount` of `outputToken`.
2. Craft `circomData` with `feeStructure.flatFee > 0`, `feeStructure.variableRate > 0`, `feeStructure.feeToken == outputToken`, and `relay = address(0)`.
3. Call `swap`/`runAction` (tx1) and assert: `IERC20(outputToken).balanceOf(address(action)) == totalFee` after the call (computed as `hinkalFee + relayFee` from the same formula used in the contract), and that `amountToSendToHinkal` sent to `msg.sender` equals `swappedAmount - totalFee` — confirming `totalFee` is neither at the relay nor forwarded to Hinkal.
4. As a second step, attempt a subsequent swap (tx2) by a different caller through the same action and inspect whether `callRouter`'s `swappedAmount` computation incidentally includes the stranded balance (this requires reading the concrete `callRouter` implementation in `LifiExternalAction.sol`, not available in this session) to determine if the frozen fee can later be captured into another user's UTXO.
