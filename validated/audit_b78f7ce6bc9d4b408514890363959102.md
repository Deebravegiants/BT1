### Title
Fixed-amount unlock in `WrappedHyperFungibleToken` can lock rebasing-token surplus or permanently strand refunds when the underlying rebases downward - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` locks an exact `params.amount` of an arbitrary configured ERC20 (`_underlying`) on `send()`, and later unlocks the exact `message.amount` encoded in the cross-chain message on `onAccept()` (or refunds it on timeout), using `safeTransfer`/`safeTransferFrom` against fixed integer amounts rather than reconciling with the contract's actual live token balance. There is no view of, or reconciliation against, `IERC20(_underlying).balanceOf(address(this))`, and no sweep/rescue function exists in this contract to recover any surplus. If the underlying token is a rebasing token (the report's `stETH`/`OHM`/`AMPL` class), the sum of amounts locked and not-yet-unlocked can diverge from the contract's actual balance over time, exactly analogous to the Velvet Capital `balanceAtRemoval` vs. live-balance mismatch in `tokenExclusionManager`.

### Finding Description
`send()` pulls exactly `params.amount` of `_underlying` into the contract and dispatches a message carrying that fixed `amount`: [1](#0-0) 

`onAccept()`, invoked by the ISMP host for any relayer-delivered message from the registered peer, decodes the fixed `message.amount` and unlocks exactly that quantity via `safeTransfer`, with no comparison to the contract's current balance: [2](#0-1) 

The cross-chain `Message` struct that carries this fixed `amount` is shared verbatim across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the substrate `pallet-hyper-fungible-token`, and the docs explicitly describe the model as "the WrappedHFT accumulates locked tokens as users bridge out and releases them when users bridge back" — i.e., a pooled custody contract backing many independent lock/unlock legs, not a 1:1 escrow-per-request contract: [3](#0-2) [4](#0-3) 

Because many users' locks/unlocks share this single pooled contract balance, and the accounting unit is a fixed nominal `amount` fixed at lock time rather than a live balance read, a rebasing `_underlying`:
- **Increasing rebase** (e.g., stETH): the contract's actual balance grows beyond the sum of outstanding locked amounts still owed to in-flight bridges. This surplus is stuck permanently — there is no sweep/drain function in `WrappedHyperFungibleToken` (confirmed absent from this file; sweep/rescue logic only exists in the unrelated `IntentGatewayV2`/`IntentsBase` contracts, not in the HFT app family).
- **Decreasing rebase** (e.g., OHM/AMPL-style negative rebase): the contract's actual balance can fall below the sum of amounts still owed to users whose bridge-back messages have not yet arrived. When their `onAccept()` (or the timeout `Refunded` path) executes, `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` reverts because the contract lacks sufficient balance — freezing that user's bridged funds. Since the relayer can retry the message indefinitely and the shortfall does not self-heal (rebase continues to shrink the balance further, or is fixed by unrelated third-party inflows/withdrawals), this is a permanent freeze of that user's funds, not merely a transient one.

This is the same root-cause pattern as the external report: an accounting value fixed at time T (here, `message.amount`/locked `params.amount`) is used later to move real tokens out of a pooled custody contract, without reconciling against the token's live, possibly-rebasing balance, and with no drain/rescue mechanism for the resulting surplus.

### Impact Explanation
- Permanent freezing of user funds: a user whose bridge-back message lands after the underlying has rebased downward can have their `onAccept()` unlock (or timeout refund) revert indefinitely, because `safeTransfer` requires more tokens than the pooled contract actually holds.
- Unbacked/locked value: on an upward rebase, the surplus balance accrues in the contract with no function to sweep it to any beneficiary — it is permanently stranded, unrecoverable capital.
- Reachable by any relayer delivering a legitimate, correctly-signed/proven cross-chain message (`onAccept` is only gated by `onlyHost` + peer-source check, not by balance sufizhing at message-construction time), so this triggers under entirely honest usage once a rebasing token is configured as `_underlying` — no malicious actor is required.

### Likelihood Explanation
Medium likelihood: it requires the deploying integrator to configure `WrappedHyperFungibleToken.underlying()` to a rebasing ERC20 (the report itself notes "all tokens will be supported" was confirmed for the analogous Velvet Capital protocol, and nothing in `WrappedHyperFungibleToken`/`configure()` restricts `_underlying` to non-rebasing tokens). Given HyperFungibleToken is documented as a general-purpose bridging primitive for "existing ERC20 tokens" without any rebasing-token exclusion or balance-consistency check, this is a realistic deployment configuration, not a contrived edge case.

### Recommendation
- Track escrowed balances as an internal ledger keyed per-request/per-user rather than relying purely on the token's nominal `amount`, and additionally clamp the actual transfer in `onAccept()`/timeout refund to `min(message.amount, IERC20(_underlying).balanceOf(address(this)))`, reverting or queuing the shortfall explicitly rather than silently failing.
- Add an owner-gated sweep function restricted to tokens that are *not* the configured `_underlying` in active accounting, or a dedicated mechanism to redistribute rebase-driven surplus proportionally, analogous to the Velvet-Capital mitigation of exposing controlled drain from the escrow.
- Document and/or enforce (e.g., via a decimals/supply-invariant check at `configure()` time, or an explicit allow-list) that `_underlying` must not be a rebasing/dynamic-balance token, since the lock/unlock accounting model assumes 1:1 balance conservation.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A with `_underlying` set to a rebasing ERC20 `R` (rebase mechanics identical to stETH/AMPL: `balanceOf` changes for all holders over time without transfers).
2. User1 calls `send()` with `amount = 1000e18` of `R`; the contract's `_underlying` balance becomes `1000e18` (see `send()` at lines 266-281).
3. Time passes; `R` rebases down 5%. The contract's actual `balanceOf(address(this))` is now `950e18`, but the outstanding message still encodes `amount = 1000e18` (per the `Message.amount` field defined in the shared cross-chain message format).
4. The corresponding burn/timeout message arrives; `onAccept()` (or the timeout refund path) attempts `IERC20(R).safeTransfer(beneficiary, 1000e18)` — this reverts because only `950e18` is held, permanently freezing User1's funds (relayer retries will not fix the shortfall since the rebase does not reverse).
5. Conversely, if `R` instead rebases up 5% before message delivery, the contract holds `1050e18` while only `1000e18` is owed; the `50e18` surplus is permanently unrecoverable since no sweep function exists in `WrappedHyperFungibleToken.sol`.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
