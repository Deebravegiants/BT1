## Title
Webhook HMAC validation only covers the request body, not the `shop`, `topic`, `webhook-id`, or `api-version` headers, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only from the raw request body, while the shop domain, topic, webhook id and API version used by the app to route and process the webhook are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, then dispatches to a handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`: [1](#0-0) 

The signable string used for HMAC verification, however, is only the raw body: [2](#0-1) 

`HmacValidator.validate_signature` computes the digest purely over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

Because the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers are never part of the HMAC-signed bytes, they are not bound to the signature at all. Any request whose `raw_body` + `hmac` pair is valid (i.e., was legitimately produced by Shopify for the app's `client_secret` on *any* shop and *any* topic) will pass `HmacValidator.validate` regardless of what `shop`, `topic`, `webhook_id`, or `api_version` header values accompany it. Since a single app's `client_secret` is shared across every shop that installs the app, an attacker who controls one installed shop can capture a legitimately-signed webhook body (e.g. from `orders/create` on their own store) and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and/or the `topic` header rewritten to any registered topic. The equality the gem should enforce — "shop value the handler acts on" == "shop value the signature was computed over" — does not hold, because the shop field is outside the HMAC boundary entirely.

### Impact Explanation
This breaks the tenant boundary the gem is meant to protect: a webhook signature that is valid for shop A's data can be replayed, with forged headers, to make the host application believe the event/topic/data belongs to shop B. This maps to the "cross-tenant access" critical-impact category — an unprivileged actor who merely operates their own installation of the app (a normal internet user relationship to the app, not a privileged account) can inject or spoof events attributed to another merchant's shop, since the header fields consumed by the handler (`shop`, `topic`, `webhook_id`) carry no cryptographic binding to the signed body.

### Likelihood Explanation
Any attacker with a legitimate install of the target app (a completely unprivileged capability — anyone can install a public Shopify app on a shop they control) can obtain valid `raw_body`/`hmac` pairs for arbitrary topics on their own store, then POST them to the app's public webhook endpoint with rewritten `shop-domain`/`topic` headers. No access token, `client_secret`, or privileged access is required — only the ability to trigger webhook events on the attacker's own shop and to send raw HTTP requests to the app's exposed webhook route.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or at minimum verify that the shop the app is about to act on is one it actually expects/has a session for, rather than trusting header values that sit outside the signature. If Shopify's HMAC scheme genuinely only signs the body (matching Shopify's real webhook signing, which is body-only), the mitigation must live in the host app's usage guidance: document explicitly that `request.shop`/`request.topic` are NOT authenticated by `hmac` and must be cross-checked against a known/expected shop registry before being trusted, and warn against enabling non-Shopify-verified content in the routing decision.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`.
2. Attacker triggers a benign webhook event (e.g., `orders/create`) on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this signature is valid because it's computed with the app's single `client_secret`, which is shared across all shops using the app: [4](#0-3) 
3. Attacker replays the exact same body and `hmac` header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses these attacker-controlled headers without validating them against the signature: [5](#0-4) 
5. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the body's HMAC, then invokes the app's handler with `shop: request.shop` set to `victim-shop.myshopify.com`: [1](#0-0) 
6. The host application's webhook handler now processes/persists data believing it originated from `victim-shop.myshopify.com`, achieving cross-tenant data injection/confusion.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
