## Title
`Bonding._noFeeSwapInput`'s `Math.mulDiv` can overflow on an attacker-sized hostile pre-seed, permanently bricking `finalizeGraduation` - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where `reserveIn`/`reserveOut` are read live from the attacker-influenceable HyperSwap V2 pair [1](#0-0) . An attacker who front-runs graduation with `factory.createPair` + `transfer` + `pair.mint()` at an extreme, self-funded reserve ratio can push `reserveIn * reserveOut` toward the `uint112` ceiling on one or both sides while `targetD` (`ltFromPair`/`tokensForLP`, values the protocol — not the attacker — controls and which can be small for a lightly-traded or thinly-seeded curve) stays small, driving the final quotient past `2^256`. `Math.mulDiv` reverts when the result overflows `uint256`, which the developers' own test explicitly reproduces and documents [2](#0-1) . That revert propagates all the way up through `finalizeGraduation`, which the codebase's own invariant states must **never** revert under any pre-seed shape [3](#0-2) .

### Finding Description
`_noFeeSwapInput`'s natspec itself flags the exact risk: "Call sites must keep [`reserveIn * reserveOut * targetN / targetD`] inside [uint256]... Constructed adversarial inputs that violate this would `revert` rather than silently truncate" [4](#0-3) .

```solidity
function _noFeeSwapInput(
    uint256 reserveIn,
    uint256 reserveOut,
    uint256 targetN,
    uint256 targetD,
    uint256 maxSwap
) internal pure returns (uint256) {
    if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
        return 0;
    }
    uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
    ...
}
``` [5](#0-4) 

`reserveIn`/`reserveOut` come straight from `IUniswapV2Pair(pair).getReserves()`, which is a `uint112` pair the attacker fully controls by front-running: create the pair, `transfer` self-funded TOKEN/LT amounts, then `pair.mint(attacker)` — exactly the Regime-3 exploit the codebase's own docs walk through [1](#0-0) , [6](#0-5) . `targetD` is `ltFromPair` or `tokensForLP`, cached in `pendingGraduation` at end of phase 1 from real (not attacker-set) curve state, and is only *upper*-bounded (by `LP_RESERVE`/curve raise size) — the codebase's overflow-safety reasoning only bounds these values' magnitude, never their lower bound relative to `reserveIn*reserveOut` [7](#0-6) . A thinly-traded or thinly-seeded launch (attacker can also be the token creator, since `Zap.createToken` is permissionless and has no seed ceiling [8](#0-7) ) yields a small `ltFromPair`/`tokensForLP`, letting a self-funded pre-seed pair with reserves in the tens-of-thousands-to-uint112-max range push the discriminant past `2^256`, tripping `Math.mulDiv`'s built-in revert.

Because the attacker only needs to *hold* LP against the pre-seeded pair (recoverable later via standard `removeLiquidity` on the resulting real V2 pool, independent of `Bonding`), the capital is not burned — the attack is gas-plus-temporary-lockup cost, not a burn.

### Impact Explanation
Once `finalizeGraduation` reverts unconditionally for a given token, the token is permanently stuck in `lifecycle: Graduating`: trading is frozen (`_enterGraduating` already froze the curve), all curve-raised LT and the `LP_RESERVE` (250M tokens) remain parked inside `Bonding` with no rescue path, and `LPLock.recordLock` — a one-shot call inside `finalizeGraduation` — can never fire. Every trader who bought the token and every LP that would have received locked LP is permanently frozen out. This directly matches the accepted impact class of "permanent freezing of trader, creator or LP funds" via a "permissionless two-phase graduation that parks all curve-raised LT and 250M tokens on Bonding between phases," and violates the codebase's own stated invariant that this exact code path "MUST never revert under any pre-seed shape" [3](#0-2) .

### Likelihood Explanation
Reachable by any unprivileged wallet with no special role: `factory.createPair` and `pair.mint` are permissionless V2 primitives, and the graduation trigger itself fires from ordinary `Zap.buy`/`Bonding.buy` traffic. The developers' own fuzz/unit test (`test_overflowSafety_atRealisticMax`) proves the overflow is mathematically reachable at V2's real `uint112` reserve ceiling [2](#0-1) , and their safety argument only bounds `targetN`/`targetD`'s magnitude, not a minimum size relative to `reserveIn*reserveOut` — so any graduation whose cached `ltFromPair`/`tokensForLP` is small relative to an attacker-affordable pre-seed size is exposed. This is a griefing-class DoS, not requiring the attacker to profit, which historically makes it cheap and attractive to execute against competitors' or arbitrary tokens.

### Recommendation
Bound the reserve inputs to `_pairRebalance`/`_noFeeSwapInput` (e.g., cap `reserveIn`/`reserveOut` used in the discriminant, or reformulate the sqrt computation to avoid the `reserveIn * reserveOut * targetN / targetD` single-shot `mulDiv`), and wrap the rebalance attempt in a try/catch that falls back to `_seedDirectMint` (mirroring the existing `s == 0` / `expectedOut == 0` fallback) whenever the swap-sizing math reverts, so no pre-seed shape can brick `finalizeGraduation`.

### Proof of Concept
1. Attacker calls `Zap.createToken` (or targets any existing thinly-traded token) so that the eventual `pendingGraduation[token].ltFromPair` / `tokensForLP` cached by `_enterGraduating` is small.
2. Before `finalizeGraduation` is called, attacker front-runs: `factory.createPair(token, lt)`, `transfer(pair, largeTokenAmt)`, `transfer(pair, largeLtAmt)` sized so `reserveIn * reserveOut` approaches `uint112.max^2`, then `pair.mint(attacker)`.
3. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)`, whose quotient exceeds `2^256`, and the call reverts (per `test_overflowSafety_atRealisticMax`'s own worked arithmetic [2](#0-1) ).
4. Every subsequent call to `finalizeGraduation(token)` reverts identically — the token is permanently stuck in `Graduating`, and the attacker can later `removeLiquidity` to recover their own deposited capital from the standard V2 pair.

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
