### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then forwards the unverified header-derived `shop`/`topic` values straight into `WebhookMetadata` passed to the host app's handler.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Request` is defined as just `@raw_body`: [1](#0-0) 

Meanwhile `shop` and `topic` are pulled from the `shopify-shop-domain` / `shopify-topic` headers, which are never included in the signed material: [2](#0-1) 

`Registry.process` verifies only the HMAC over the body, then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 

This breaks the intended identity binding: `shop authenticated-by-HMAC == shop acted upon by the handler`. In reality, the equality only holds for the body bytes — the `shop` and `topic` attribution is unauthenticated header data that rides alongside a validly-signed body. Because Shopify's HMAC scheme (as implemented in this gem) never binds headers to the signature, any raw_body+hmac pair that an attacker legitimately receives (e.g., a webhook delivered for their own, attacker-controlled shop) remains cryptographically valid when replayed with a forged `shopify-shop-domain` header pointing at a different merchant, or a forged `shopify-topic` header selecting a different, more sensitive handler. `WebhookHandler#handle` (host app code) receives a `WebhookMetadata.shop`/`.topic` that the gem asserts was verified, but which was never actually covered by the cryptographic check.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem lets an attacker who can obtain any one valid `(raw_body, hmac)` pair for their own shop re-attribute that payload to an arbitrary target shop domain or arbitrary topic and have it accepted as authentic by `Registry.process`. Any host app that relies on `WebhookMetadata.shop`/`.topic` for cross-tenant dispatch (e.g., looking up per-shop sessions, triggering `app/uninstalled` cleanup, or writing per-shop data) can be made to act on the wrong tenant's behalf using only the attacker's own legitimately-signed webhook material — meeting the cross-tenant access bar.

### Likelihood Explanation
Requires no privileged credentials: any developer/merchant who installs the app on their own store (unprivileged relative to the target shop) receives genuine, validly-signed webhooks from Shopify and can freely modify the header set (which the gem does not protect) before replaying the request to the app's public webhook endpoint.

### Recommendation
Bind `shop`, `topic`, and any other header-derived identity fields into the signable content (or otherwise cryptographically verify them, e.g., by cross-checking `shop-domain` against the session actually associated with the HMAC-validated payload) before constructing `WebhookMetadata`, rather than trusting header values verbatim once only the body HMAC has been checked.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a genuine webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker POSTs the same body `B` and same `hmac` header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or `x-shopify-topic` to a different registered topic).
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [4](#0-3)  — it still matches `H`, so validation passes.
4. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)` [5](#0-4) , causing the host app to process attacker-controlled data as if it originated from and pertains to `victim.myshopify.com`.
