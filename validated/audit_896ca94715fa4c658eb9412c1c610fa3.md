## Title
`HyperFungibleTokenImpl.burn` lets any `BURNER_ROLE` holder destroy user token balances without owner approval - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl` is a role-based ERC20 utility meant to back multi-minter/multi-burner cross-chain token deployments. Its `burn(address from, uint256 amount)` function destroys tokens directly from an arbitrary `from` address as long as the caller holds `BURNER_ROLE`, with no allowance/approval check from the token owner [1](#0-0) . This mirrors the reported `HolographERC721.sourceBurn`/`sourceTransfer` bug class: a role granted to an integrating "bridger" contract can unilaterally seize user funds instead of going through the standard `approve`/`allowance` flow that `ERC20Burnable.burnFrom` enforces.

### Finding Description
Standard OpenZeppelin `ERC20Burnable.burnFrom` requires the caller to have an allowance from the token owner before burning on their behalf. `HyperFungibleTokenImpl.burn` bypasses this entirely: it only checks `onlyRole(BURNER_ROLE)` and then calls `_burn(from, amount)` directly, with `from` fully attacker/caller-controlled and no allowance deduction [2](#0-1) . Compare this to the project's mock `ERC20Token.burn`, which correctly spends the owner's allowance when `account != msg.sender` [3](#0-2) , and to `HyperFungibleToken.send`, which only ever burns `msg.sender`'s own balance [4](#0-3) .

`BURNER_ROLE`/`MINTER_ROLE` are intended to be granted to a bridge/gateway contract handling cross-chain token teleports (per the contract's own doc comment: "Useful for scenarios where multiple contracts need minting capabilities") [5](#0-4) . Once granted, that role holder becomes a single point of failure that can burn ANY holder's balance without their consent — exactly the "trusted extension can rob users without approval" pattern flagged in the source report, since a compromised key, a bug in the gateway contract, or a malicious upgrade to the role-holder contract can drain arbitrary user balances.

### Impact Explanation
Any account holding `BURNER_ROLE` (intended to be a token-bridge/gateway contract) can burn tokens from any user's balance without their signature or approval, resulting in permanent, unrecoverable loss of user funds. This is a direct token-theft/loss-of-funds primitive reachable through the token-bridge mint/burn surface explicitly in scope.

### Likelihood Explanation
Exploitation requires compromise or misuse of a contract/address already holding `BURNER_ROLE` — the same trust model that made the original `sourceBurn`/`sourceTransfer` finding Medium severity in the C4 report (compromised owner key or buggy privileged contract, not require of end-user actions). Given `HyperFungibleTokenImpl` is explicitly documented for multi-integration/gateway usage, granting `BURNER_ROLE` to a third-party bridging contract is an anticipated deployment pattern, making the risk realistic rather than purely theoretical.

### Recommendation
Require the token owner's explicit allowance before burning on their behalf, mirroring `ERC20Burnable.burnFrom`: have `burn` call `_spendAllowance(from, msg.sender, amount)` before `_burn`, so a `BURNER_ROLE` holder can only burn what has been explicitly approved rather than any user's full balance.

### Proof of Concept
1. Admin deploys `HyperFungibleTokenImpl` and grants `BURNER_ROLE` to a gateway/bridge contract via `grantBurnerRole` [6](#0-5) .
2. A user holds a balance of the token without ever approving the gateway contract to spend it.
3. The gateway contract (or an attacker who compromises/exploits it) calls `burn(userAddress, userBalance)`.
4. Because `burn` only checks `onlyRole(BURNER_ROLE)` and never checks `allowance(userAddress, msg.sender)`, the call succeeds and the user's entire balance is destroyed without their consent [7](#0-6) .
