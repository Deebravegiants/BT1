Audit Report

## Title
`Pallet::payout` unconditionally rejects any account that already carries a `pallet_vesting` schedule, letting a user (or a third party) permanently trap owed purchase balance - ([File: polkadot/runtime/common/src/purchase/mod.rs])

## Summary
`payout` re-checks `T::VestingSchedule::vesting_balance(&who).is_none()` before crediting a purchaser [1](#0-0) . Since `pallet_vesting::vested_transfer` is an unprivileged, signed extrinsic that can target any account, an attacker (including the victim's account owner or an unrelated third party) can create a vesting schedule on the purchase-tracked account after `update_balance` has fixed the entitlement but before `PaymentAccount` calls `payout`, causing `payout` to fail with `Error::VestingScheduleExists` and blocking the payout indefinitely.

## Finding Description
The purchase flow is: `create_account` -> `update_validity_status` -> `update_balance` (fixes `free_balance`/`locked_balance` in `Accounts<T>`) -> `payout` (called only by the fixed `PaymentAccount`). `create_account` checks for an absent vesting schedule up front, but `update_validity_status` and `update_balance` do not re-check this [2](#0-1) , leaving a real window between the account being marked valid/funded and `PaymentAccount` actually executing `payout`.

`payout` performs the same `vesting_balance(&who).is_none()` guard, and this check occurs *before* the `Accounts::<T>::try_mutate` block that would set `status.validity = AccountValidity::Completed` and transfer funds [3](#0-2) . `pallet_vesting::vested_transfer` is a plain signed extrinsic that creates a `Vesting` storage entry on an arbitrary target account, and such an entry is only cleared by an explicit, separate `vest`/`vest_other` call. There is no code path in `purchase::mod.rs` that lets `PaymentAccount` or `ConfigurationOrigin` bypass or override this vesting check, so once it fails, `Accounts<T>` retains the fixed `free_balance`/`locked_balance` and the account's `validity` stays non-`Completed` until the externally created vesting schedule is separately purged by a `vest`/`vest_other` call — an event entirely outside the purchase pallet's control.

This is a faithful and accurate description of the code as it exists in this repository; the cited line ranges match the actual source.

## Impact Explanation
The impact is real but narrow: a purchase participant's already-approved, already-funded entitlement (`free_balance` + `locked_balance` tracked in `Accounts<T>`) becomes temporarily unpayable via the `payout` extrinsic for as long as an externally created vesting schedule exists on that specific account. This is a self-DoS/griefing vector against the purchase-payout flow of a specific, purpose-built pallet (`pallet-purchase`) used for a one-time token sale process, not a general protocol insolvency, fund-loss, or unauthorized-fund-movement bug. The DOTs owed are not lost or stolen — they remain recorded in on-chain storage (`Accounts<T>`) and become payable again once the interfering vesting schedule is cleared (either it fully vests and someone calls `vest`/`vest_other`, or `PaymentAccount`/governance intervenes off-chain, e.g. by not calling `payout` until the schedule is dealt with, or by using other mechanisms outside the pallet). The griefing is real (any unprivileged account can target another via `vested_transfer`), but the affected surface is a narrow, legacy purchase pallet rather than a core consensus, balance-transfer, or staking primitive.

## Likelihood Explanation
The precondition and trigger are both realistically achievable with unprivileged calls: `vested_transfer` requires no special origin beyond being signed and meeting `MinVestedTransfer`, and it can target any account, including one already registered in the purchase pallet. The race window between `update_balance` (privileged, done by `ValidityOrigin`) and `payout` (privileged, done by `PaymentAccount`) is a normal multi-transaction gap that any observer of on-chain purchase-flow events could exploit against a victim's account before the payout transaction lands. No chain-level race conditions, privileged access, or unrealistic assumptions are required.

## Recommendation
Avoid treating any pre-existing vesting schedule as an unconditional, unrecoverable blocker inside `payout`. Reasonable options: (a) have `payout` still transfer the `free_balance` portion unconditionally, and only skip/retry the `add_vesting_schedule` step (or merge into the existing schedule) when a schedule already exists, rather than aborting the entire payout and leaving `validity` non-`Completed`; (b) allow `PaymentAccount` to force the vesting schedule to merge with any existing one instead of erroring; or (c) provide a way to recover/complete payout for these accounts (e.g. an explicit governance or self-service call) so a legitimately owed balance is never left gated indefinitely behind an unrelated pallet's storage state.

## Proof of Concept
Rust integration test extending the existing purchase-pallet mock (which wires in `pallet_vesting`):
1. Run `create_account`, `update_validity_status(who, ValidLow)`, `update_balance(who, free, locked, vat)` for `who`.
2. As `who` (or a third party), call `Vesting::vested_transfer(RuntimeOrigin::signed(attacker), who, VestingInfo::new(min_transfer, 1, current_block))`, creating a `Vesting` entry for `who`.
3. As `PaymentAccount`, call `Purchase::payout(RuntimeOrigin::signed(payment_account), who)`.
4. Assert the call returns `Error::<Test>::VestingScheduleExists`, and that `Accounts::<Test>::get(who)` still shows `validity != Completed` with unchanged `free_balance`/`locked_balance`.
5. Show that `payout` continues to fail on retry until an unrelated `vest`/`vest_other` call clears the `Vesting` entry, at which point `payout` succeeds normally and the owed balance is paid out — demonstrating the DoS is temporary/recoverable rather than a permanent loss of funds.
