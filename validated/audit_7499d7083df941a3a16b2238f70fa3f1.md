### Title
Vault gateway cannot process `SecretsDelete` cleanup requests once a workflow is removed from the on-chain allowlist, permanently orphaning secrets - (File: core/capabilities/vault/allow_list_based_auth.go)

### Summary
The Vault gateway's allowlist-based authorization path treats every JSON-RPC method identically: a request is only authorized if its exact digest currently appears in the on-chain `WorkflowRegistry` allowlist. There is no bypass or grace mechanism for `MethodSecretsDelete`, so once a workflow owner's entry is no longer present in the allowlist (e.g., the workflow is deregistered, paused, or its allowlist authorization expires/is not renewed), the owner can no longer submit an authorized delete request to clean up their own previously-created secrets — mirroring the reported Blueberry issue where `repay` (needed to `closePosition`) fails once a token is removed from a whitelist, permanently trapping the position.

### Finding Description
`allowListBasedAuth.AuthorizeRequest` computes a digest of the incoming request and requires it to match a `WorkflowRegistryOwnerAllowlistedRequest` currently returned by `workflowRegistrySyncer.GetAllowlistedRequests`, retrying for a bounded window before failing with "request not allowlisted": [1](#0-0) 

This same authorization function is invoked uniformly for all vault methods — `Create`, `Update`, `List`, and `Delete` — through the shared `authorizer.authorizeAllowListBasedAuth` path, with no special-casing for delete/cleanup operations: [2](#0-1) 

`processDeleteSecretsRequest` in `GatewayVaultRequestProcessor` funnels through the identical `authorizeAndStamp`/`AuthorizeRequest` call used by create/update, with no alternate authorization route for removing a client's own previously-stored secrets: [3](#0-2) 

Because the allowlist entries are populated per-request from on-chain `WorkflowRegistry` events tied to an active/registered workflow, if that workflow is deregistered, deactivated, or its allowlist grant expires (the code explicitly checks `ExpiryTimestamp` and rejects expired grants), the owner has no way to get a *new* digest allowlisted for a `SecretsDelete` call, since obtaining an allowlist entry itself presumably requires the workflow to be active/registered. This is structurally identical to the reported bug: the "closing"/cleanup action (`repay`/`closePosition` there, `SecretsDelete` here) is gated by the same whitelist/allowlist check as the "opening" actions, with no allowance for an unwound/removed principal to clean up state they already created.

### Impact Explanation
A workflow owner whose workflow is removed from the on-chain allowlist can no longer delete secrets they previously stored via the vault gateway. This leaves secret material permanently orphaned in vault storage with no supported client-side remediation path, and could also block a legitimate security response (e.g., an owner trying to delete a compromised secret after their workflow registration lapses).

### Likelihood Explanation
This requires only routine lifecycle events (workflow deregistration, allowlist grant expiry, or workflow pause) rather than any attacker action — the same "medium" likelihood profile as the original report, since it is triggered by a normal state transition rather than an adversarial one.

### Recommendation
Allow `SecretsDelete` requests to be authorized via a distinct, more permissive path that does not require the workflow to still hold an active on-chain allowlist entry — e.g., verify only signature/ownership of the secret identifier rather than requiring a live allowlisted digest, similar to the report's recommendation to let `repay` succeed for non-whitelisted tokens so users can still close positions.

### Proof of Concept
Not independently reproducible from static analysis alone (requires a live vault DON + WorkflowRegistry deployment). Conceptually:
1. Workflow owner creates secrets via `SecretsCreate` while their workflow is registered/allowlisted.
2. Owner's workflow is deregistered or their allowlist grant expires (`ExpiryTimestamp` passes) per [4](#0-3) .
3. Owner submits `MethodSecretsDelete` for their own secret; `findAllowlistedItemWithRetry` finds no matching un-expired allowlist entry and `AuthorizeRequest` returns `"request not allowlisted"` [5](#0-4) , so the delete is rejected and the secret can never be removed by its owner.

func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}

func (a *authorizer) authorizeAllowListBasedAuth(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	if a.allowListBasedAuth == nil {
		err := errors.New("AllowListBasedAuth authorizer is nil")
		a.lggr.Errorw("AllowListBasedAuth unavailable", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	return a.allowListBasedAuth.AuthorizeRequest(ctx, req)
}

func (p *GatewayVaultRequestProcessor) processDeleteSecretsRequest(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
) (*AuthorizedGatewayVaultRequest, error) {
	if req.Params == nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: errors.New("request params must not be nil")}
	}

	var deleteReq vaultcommon.DeleteSecretsRequest
	if err := json.Unmarshal(*req.Params, &deleteReq); err != nil {
		return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
	}
	if p.stripOwnerPrefixForAuth {
		deleteReq.RequestId = req.ID
		if err := marshalVaultParams(req, &deleteReq); err != nil {
			return nil, InvalidVaultParamsError{Method: req.Method, Err: err}
		}
	} else {
		deleteReq.RequestId = coalesceRequestID(deleteReq.RequestId, req.ID)
	}

	if err := p.validator.ValidateDeleteSecretsRequest(ctx, &deleteReq); err != nil {
		return nil, p.validationError(req, err)
	}

	return p.authorizeAndStamp(ctx, req, func(prefixedRequestID string) error {
		deleteReq.RequestId = prefixedRequestID
		vaultutils.ApplySecretIdentifierNamespaceDefaults(deleteReq.Ids)
		return marshalVaultParams(req, &deleteReq)
	})
