## Title
Flash‑loan spot‑price manipulation of Simplex's Uniswap V4 venue pricing lets an intent placer drain solver funds — ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's `FXFiller` prices curveless (venue-priced) intent legs directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96`, with no TWAP, no size/impact term, and an optional, static-reference deviation guard. An attacker who flash-loan-manipulates the referenced V4 pool in the same block as placing/filling an intent order can force the solver to price and fill at a manipulated rate, extracting solver funds — the same "flash loan → manipulate pool ratio → drain funds paid out at the bad ratio" pattern used in the Allbridge Core incident.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` reads the pool's current `slot0` and derives price straight from `sqrtPriceX96` via `computeDirectPoolPriceUsd`, picking the most-liquid position and returning `sdkPool.token0Price`/`token1Price` verbatim as USD price: [1](#0-0) [2](#0-1) 

This spot price is a single-block AMM ratio read with no TWAP protection, exactly the manipulation surface exploited in the Allbridge incident. It is documented as intentional but unguarded against execution/manipulation risk: [3](#0-2) 

The pricing flows into `resolveLegRates`, which trusts the venue quote for any curveless USD-stable pair and only checks it against `checkPriceGuard`: [4](#0-3) 

`checkPriceGuard` is **optional per chain** — if `referencePrice`/`maxDeviationBps` are not both configured, the quote is accepted unconditionally: [5](#0-4) 

Even when configured, the guard only rejects gross deviation from a **static** reference price — it does not detect or prevent manipulation that stays within `maxDeviationBps`, and it does not account for execution cost, pool fee tier, or price impact at the actual fill size: [6](#0-5) 

The docs for the pricing path explicitly flag the missing size/impact term: "there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the whole priced quantity," meaning a manipulated tick is extended linearly across the entire order size with no slippage correction. [3](#0-2) 

### Impact Explanation
An attacker (an ordinary intent placer, requiring no special privilege) can:
1. Flash-loan borrow assets and swap heavily in the referenced Uniswap V4 pool to push the tick/`sqrtPriceX96` far off the true market price, either exceeding no guard at all (default, unconfigured chains) or staying within a loosely configured `maxDeviationBps`.
2. Simultaneously (same block, via a submitted order/bundle) submit an intent order on that pair.
3. The solver's `FXFiller` prices the leg from the manipulated pool (`getVenueUsdPrice` → `getExoticTokenPrice` → `computeDirectPoolPriceUsd`) and computes `computeLegPolicyOutput` linearly off that bad mid-price, then commits to filling at that rate.
4. The solver overpays the attacker in the output token, or accepts far less value than it should for the escrowed input, and the attacker unwinds the flash loan for guaranteed profit at the solver's expense.

This directly drains solver/LP capital, which is theft of funds reachable from a single submitted order plus a same-block on-chain price manipulation — analogous to the reported Allbridge Core flash-loan/AMM-ratio exploit.

### Likelihood Explanation
- The attack requires only capital for a flash loan and gas — no privileged role.
- Guard configuration is optional (`referencePrice`/`maxDeviationBps` must both be set; many chains/pairs may ship unguarded per the docs' explicit callout that omitting both "leaves the chain unguarded").
- Even guarded pairs remain exploitable within the configured band, since the guard compares against a static number, not manipulation-resistant TWAP data.
- Uniswap V4 pools with concentrated liquidity are commonly thin enough (especially for exotic/curated stablecoin pairs like cNGN, ZARP, XSGD, TRYB referenced in the docs) that a modest flash loan can move price meaningfully.

### Recommendation
- Replace the instantaneous `slot0`/`sqrtPriceX96` read with a manipulation-resistant TWAP (or require corroboration from an external oracle) before using it as a fill price.
- Make the price guard mandatory (not optional) for every venue-priced pair, and update the reference dynamically (e.g., from a TWAP or independent oracle) rather than a static operator-set value.
- Apply price-impact/slippage accounting proportional to order size instead of extending the pool mid linearly across the whole quantity.
- Consider bounding maximum fill size relative to available pool liquidity so a single flash-loaned trade cannot move the whole priced range.

### Proof of Concept
1. Operator configures a Simplex `FXFiller` pair with no curves and Uniswap V4 venue pricing (`[vault.uniswapV4]` position, no `referencePrice`/`maxDeviationBps` set) — a supported, documented configuration.
2. Attacker flash-loans a large amount of the stable/exotic token and swaps through the same V4 pool to move `sqrtPriceX96` far from fair value.
3. Attacker submits an intent order for the pair in the same transaction bundle/block.
4. `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` returns the manipulated price (no guard blocks it, since none is configured, or the manipulation stays within a static-band guard).
5. `computeLegPolicyOutput` extends this bad mid-price linearly over the whole order size (no impact term) and the solver signs/executes a fill at the manipulated rate.
6. Attacker repays the flash loan, keeping the difference extracted from the solver's wallet/LP position — funds are permanently lost by the solver, mirroring the Allbridge Core loss mechanism.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

		sdkPool: V4Pool,

		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
