### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the `shop` identifier that the handler uses to attribute the event to a tenant is read from an HTTP header that is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values used by the rest of the pipeline are pulled directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (body only) and compares against `hmac` (header only) — the `shop` header plays no role in signature computation or verification: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop_that_produced_valid_hmac(body) == shop_attributed_to_the_event_by_the_handler`. Because `shop-domain` is excluded from the signable string, this equality is not enforced by the gem — the HMAC only proves "some entity holding `api_secret_key` signed this exact body," not "this specific shop sent this event." Any two webhook deliveries whose bodies are byte-identical (which is common — e.g. `customers/redact`, `shop/redact`, or app-uninstalled payloads with sparse/identical JSON structure, or bodies an attacker's own shop can influence) will produce the same valid HMAC regardless of which shop domain header is attached. An attacker who controls a legitimate installed shop can capture a validly-signed webhook body from their own store, then resend the same raw body/HMAC pair with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `Registry.process` will pass HMAC validation and dispatch the handler with `WebhookMetadata` carrying the spoofed victim shop: [5](#0-4) 

This is the direct structural analog of the reported bug class: a field that is *acted upon* (the shop used to key data/actions) is not *covered* by the authenticity check (the HMAC), so the two can diverge under attacker control.

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` (as intended/documented usage of this field) to select which tenant's data to mutate, delete, or look up, an attacker can cause the app to perform actions attributed to a shop they do not own, using only a validly-signed webhook they legitimately received for their own store. This is a cross-tenant data integrity/access issue at the trust boundary this gem is responsible for (HMAC-based sender authentication of webhooks).

### Likelihood Explanation
Likelihood is Medium: it requires (1) the attacker to operate their own installed shop instance so they can receive genuinely-signed webhooks, and (2) a webhook topic/body that is identical or attacker-predictable across shops (several mandatory/system topics like `shop/redact`, `customers/redact`, `app/uninstalled` have minimal or attacker-influenceable bodies), and (3) the host app trusting `metadata.shop` without an independent secondary check. No secret material is required beyond receiving Shopify's normal webhook deliveries to the attacker's own shop.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before computing the digest, so that `Utils::HmacValidator.validate` fails if the shop header is altered independently of the body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook for a topic with a fixed/empty body, e.g. `customers/redact` with body `{}` and header `shopify-shop-domain: attacker-shop.myshopify.com`, HMAC `H = HMAC_SHA256(secret, "{}")`.
2. Because `to_signable_string` returns only the raw body, `H` remains valid for body `{}` regardless of the shop header.
3. Attacker resends the same `raw_body: "{}"` and `shopify-hmac-sha256: H` to the app's webhook endpoint, but with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H})` is constructed, and `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`"{}"`) against `H`: [5](#0-4) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)`, causing the host app to process a redact/uninstall/other action as if it originated from `victim-shop.myshopify.com`, even though that shop never sent this request.
