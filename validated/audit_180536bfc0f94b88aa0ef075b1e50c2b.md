### Title
Emporium's Stateless CASE 2 Ops Allow Anyone to Steal ERC721/ERC1155 Assets Held by Emporium - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
Emporium's `runAction` only tracks fungible balance changes for tokens explicitly listed in `circomData.erc20TokenAddresses`; it has zero accounting for ERC721/ERC1155 assets, and its "CASE 2: Stateless Interaction" branch allows any caller to make Emporium execute an arbitrary `.call` to any contract with arbitrary calldata. Because `Transferer.onERC721Received`/`onERC1155Received` unconditionally accept any incoming NFT and Emporium never records which `stealthAddress`/depositor an asset in its custody belongs to, any unprivileged attacker B can later submit a CASE 2 op that calls `transferFrom(emporium, B, tokenId)` on that NFT and steal it, since the call is made with `msg.sender == Emporium` and Emporium is the token owner.

### Finding Description
The broken equality is: **"asset held in Emporium's custody == asset claimable only by the stealthAddress/originalSender whose transaction placed it there."** Nothing in the code enforces this.

- `EmporiumUpgradeable.runAction` ( [1](#0-0) ) iterates `stack.ops` and for CASE 2 (`op.invokeWallet == false` or `stack.signerAddress == address(0)`) directly does `op.endpoint.call{value: op.value}(op.callData)` with no restriction other than blocking two specific wallet selectors.
- The only balance accounting performed afterwards is over `circomData.erc20TokenAddresses` ( [2](#0-1) ), which is exclusively for ERC20/ETH; ERC721/ERC1155 token contracts are never part of this array and therefore never balance-checked at all.
- `Transferer.onERC721Received`/`onERC1155Received` return the selector unconditionally with no state recorded about sender or token ( [3](#0-2) ), so an NFT sent/minted to Emporium via a CASE 2 op leaves no owner record.
- Crucially, when `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only feeds `emporiumMessage`, `timeStamp`, `calldataHash` as public signals ( [4](#0-3) ) — i.e., with an empty token array there are zero nullifiers/UTXOs to spend, so this "stateless" mode requires no proof of ownership of any specific funds or the NFT itself, just a fresh `emporiumMessage` and a self-chosen stealth address, both of which an unprivileged EOA can freely generate.
- `verifyWallet` only checks the `emporiumMessage` hasn't been used and, since CASE 2 doesn't require `stack.signerAddress != address(0)`, returns early with no signature check ( [5](#0-4) ).

Exploit flow:
1. Attacker A, via `Hinkal.transact()`, submits `circomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID` and an `EmporiumStack` whose CASE 2 op calls `NFT.mint(emporium, tokenId)` or `NFT.safeTransferFrom(A, emporium, tokenId)`. Emporium's `onERC721Received` accepts silently; the NFT now sits at `address(Emporium)` with no linkage to A recorded anywhere on-chain.
2. In a completely separate `transact()` call, attacker B (any unprivileged EOA who deposited nothing related to this NFT) submits a fresh `EmporiumStack` with `erc20TokenAddresses = []`, `stack.signerAddress = address(0)`, and a CASE 2 op with `endpoint = NFT`, `callData = abi.encodeCall(IERC721.transferFrom, (emporium, B, tokenId))`.
3. `runAction` executes `NFT.transferFrom(emporium, B, tokenId)` with `msg.sender == address(Emporium)` (the owner), which succeeds under standard ERC721 semantics (owner-initiated transfer). No balance check applies because the NFT contract is not in `circomData.erc20TokenAddresses`.
4. `verifyProof`/`performHinkalChecks`/`dimensionsCheck` all pass trivially because `dimensions.tokenNumber == 0` means no nullifiers, no UTXOs, and no linkage to A's identity is required for B's transaction.

Existing guards (`insertNullifiers`, root-hash checks, `onlyAllowedRecipient`, `nonReentrant`, balance/slippage requires in `Hinkal.transact`) all operate only over the ERC20/ETH accounting model (`amountChanges`, `slippageValues`, `erc20TokenAddresses`) and never constrain arbitrary calls made in CASE 2 to other contracts, nor any non-fungible asset custody.

### Impact Explanation
Direct theft of an NFT (or any other asset type not represented in `erc20TokenAddresses`, including stranded ERC20/ETH balances left in Emporium from any prior partial operation) that another user placed into Emporium's custody, by any unprivileged EOA, with no signature or proof tying the stolen asset to the thief. This matches "Critical - direct theft of shielded or in-flight user funds ... executing calls or moving assets a wallet owner or prover never authorised" and is repeatable against any NFT/asset that ever transiently sits in Emporium via a CASE 2 op.

### Likelihood Explanation
No privileged role is required. The attacker only needs: (1) knowledge that an NFT (or other untracked asset) is currently custodied by Emporium — observable on-chain via `Transfer` events; (2) the ability to submit a normal `transact()` call with a self-generated Groth16 proof for the zero-token "Emporium min" input path, which requires no ownership of the victim's funds. This is inexpensive (one transaction) and fully repeatable for every asset left in Emporium.

### Recommendation
Emporium must record custody at the point an asset (NFT or otherwise) enters its control via a CASE 2 op, binding it to the `circomData.stealthAddressStructure`/`originalSender` of that same transaction (e.g., maintain a `tokenId => owner-commitment` mapping populated whenever a CASE 2 op results in an incoming NFT), and CASE 2 ops that move an owned NFT/ERC1155 out must verify the caller's proof corresponds to the recorded owner commitment before allowing `transferFrom`/`safeTransferFrom` calls targeting Emporium-held tokens. Alternatively, disallow generic stateless calls to arbitrary token contracts entirely and require all NFT operations to go through an explicit, ownership-checked external action rather than raw CASE 2 passthrough calls.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, a mock `ERC721` (mintable), and register Emporium as `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`.
2. As attacker A: call `Hinkal.transact()` with a locally generated snarkjs proof for `circomData` where `erc20TokenAddresses = []`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{ops: [{endpoint: nft, invokeWallet:false, value:0, callData: abi.encodeCall(nft.mint,(emporium, tokenId))}], signerAddress: address(0), ...}}`. Assert `nft.ownerOf(tokenId) == emporium`.
3. As attacker B (different EOA, fresh `emporiumMessage`, own generated proof, no relation to A): call `Hinkal.transact()` with `EmporiumStack{ops: [{endpoint: nft, invokeWallet:false, value:0, callData: abi.encodeCall(nft.transferFrom,(emporium, B, tokenId))}], signerAddress: address(0)}`.
4. Assert the equality "position claimant == stealthAddress that created it" is broken: `nft.ownerOf(tokenId) == B` after step 3, despite A's proof/signature never authorizing any transfer to B, and no shared secret/UTXO/nullifier links A's and B's transactions.
