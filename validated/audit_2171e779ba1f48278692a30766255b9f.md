### Title
RAY-scaled accrual overflows before the borrow-index cap and permanently freezes the market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
The accrual path unscales `borrowed` and `supplied` by multiplying each RAY-scaled share balance by its index before the borrow-index cap can be applied. On a sufficiently large market at sustained high utilization, this multiplication overflows `i128`, causing every subsequent operation that accrues the market to revert with `MathOverflow`.

### Finding Description
`accrue_step` computes utilization by calling `scaled_to_original` on both the borrowed and supplied RAY balances before updating either index [1](#0-0) . `scaled_to_original` performs the raw `Ray` multiplication without checking whether the resulting value fits in `i128` [2](#0-1) .

The borrow index has a cap, but that cap is applied only while computing the next index; it does not prevent the prior step's already-large index from overflowing the current `borrowed × borrow_index` or `supplied × supply_index` calculation [3](#0-2) . An unprivileged user can drive an eligible market toward this state through ordinary `supply`, `borrow`, and `update_indexes` calls, subject to the market's configured caps, available token supply, collateral, and rate curve.

The repository's regression test demonstrates the exact condition: a billion whole tokens at 18 decimals, 98% utilization, and the XLM rate curve eventually makes `update_indexes` fail with `MathOverflow` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY` [4](#0-3) .

### Impact Explanation
Once the product overflows, the failure is persistent rather than a one-transaction rejection. Every entrypoint that must accrue the affected market first—including `update_indexes`, `withdraw`, `repay`, and liquidation flows—hits the same panic, leaving supplier principal and borrower repayment functionality frozen indefinitely [5](#0-4) . This is permanent freezing of user funds for the affected market unless contract code or stored market state is later repaired through privileged intervention.

### Likelihood Explanation
Likelihood is low-to-moderate: the attacker needs a listed market whose supply and borrow caps permit an extremely large position, enough liquidity/collateral to establish high utilization, and enough elapsed high-rate accrual for an index to grow into the overflow region. The condition is nevertheless reachable through allowed user actions once compatible market parameters exist; the checked-in test reaches it within 40 simulated years and demonstrates the permanent failure [6](#0-5) . The requirements reduce practical likelihood, but they do not remove the underlying arithmetic flaw.

### Recommendation
Make accrual overflow-safe before unscaling large positions. Specifically:

- compute the pre-accrual `borrowed × borrow_index` and `supplied × supply_index` values with a wider/checked representation or an explicit ceiling;
- derive the largest representable index for the stored scaled balances and clamp the index update before any `i128` product can overflow;
- ensure the borrow-index cap takes precedence over the utilization read instead of being evaluated only after `scaled_to_original`;
- add a production-level regression covering `withdraw`, `repay`, `liquidate`, and repeated `update_indexes` at the boundary.

### Proof of Concept
The existing test creates a large 18-decimal debt market, supplies `1_000_000_000 × 10^18` base units, supplies sufficient separate collateral, and borrows 98% of the market [7](#0-6) . It then advances ledger time yearly and calls the public `update_indexes` path until the call returns `MathOverflow`; afterward, both `withdraw` and `repay` fail with the same error [8](#0-7) . The failing operation is the `borrowed`/`supplied` unscale inside `accrue_step`, not the borrow-index cap itself [9](#0-8) .

pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);

    let new_supply_index = update_supply_index(env, supplied, supply_index, supplier_rewards);

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
