### Title
Withdraw slippage protection is silently disabled unless both `min_coin_amount` AND `min_pc_amount` are supplied - ([File: program/src/processor.rs])

### Summary
`process_withdraw` accepts two independently-optional slippage-protection fields, `min_coin_amount` and `min_pc_amount`, in `WithdrawInstruction`. The enforcement code only runs the slippage check when **both** options are `Some`; if the caller supplies only one of them (e.g. sets `min_coin_amount` but leaves `min_pc_amount` as `None`, which is a perfectly normal way to build the instruction since each field is independently `Option<u64>`), the entire check is skipped and the withdrawal proceeds with no minimum-out enforcement at all — identical in structure to the Camel bug where a check was silently skipped whenever some (but not necessarily all) of the relevant optional configuration was absent.

### Finding Description
In `Processor::process_withdraw`: [1](#0-0) 

```rust
if coin_amount < amm_coin_vault.amount && pc_amount < amm_pc_vault.amount {
    if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some() {
        if withdraw.min_coin_amount.unwrap() > coin_amount
            || withdraw.min_pc_amount.unwrap() > pc_amount
        {
            return Err(AmmError::ExceededSlippage.into());
        }
    }
    ...
}
```

`min_coin_amount` and `min_pc_amount` are declared as two independent `Option<u64>` fields on `WithdrawInstruction`, and the public instruction builder `withdraw()` in `instruction.rs` accepts them as two separate `Option<u64>` parameters with no requirement that both be set together: [2](#0-1) 

Because the enforcement uses a conjunction (`&&`) rather than checking each bound independently, a caller who legitimately wants to protect only the coin leg (or only the pc leg) of the withdrawal — a fully valid and documented usage pattern given the independent `Option` types — gets **zero** slippage protection on either leg. The computed `coin_amount`/`pc_amount` (derived from `calc_take_pnl` and the pool's live vault balances at execution time) are compared against nothing, and the transfer proceeds at whatever the current pool ratio yields.

This mirrors the CVE bug class exactly: two independently-configurable guard conditions (`jwtIssuer`/`jwtAudience` there, `min_coin_amount`/`min_pc_amount` here) are wired together with an "all-or-nothing" gate, so a partial (and otherwise valid) configuration silently degrades to "no validation at all" instead of enforcing whichever bound was actually supplied, and there is no error, log, or warning surfaced to the caller when this happens.

### Impact Explanation
Because Solana transactions execute atomically but pool state (vault balances, `calc_pnl_x/y`, `amm.lp_amount`) can shift between when a client computes an expected withdrawal amount and when the transaction lands (e.g. due to interleaved swaps, deposits, or other withdrawals in the same slot/block), `min_coin_amount`/`min_pc_amount` are the only on-chain defense a withdrawing LP has against receiving fewer tokens than expected (sandwich/front-running style value extraction). A caller/UI that only sets one of the two bounds (for example, only caring about downside on the pc leg) has no actual protection on the coin leg, and vice versa, despite believing slippage protection is active. An attacker who can influence pool state ahead of the withdrawal transaction (e.g., via a sandwiching swap) can shift the coin/pc ratio and extract value from the withdrawing LP with no on-chain check preventing it, resulting in fund loss to the LP that the instruction's documented design was supposed to prevent.

### Likelihood Explanation
This is reachable directly from an unprivileged LP's own `Withdraw` transaction — no privileged signer or special accounts are required, since `min_coin_amount`/`min_pc_amount` are attacker/caller-chosen instruction data on a call the LP itself submits. The triggering condition (supplying only one of the two `Option<u64>` fields) is a natural, expected usage of the independently-optional API surface, not an exotic edge case, making it likely to occur in real client integrations, especially any that treat the two fields as independently settable (which their `Option<u64>, Option<u64>` typing invites).

### Recommendation
Change the slippage check to enforce each supplied bound independently instead of requiring both to be `Some`:
```rust
if let Some(min_coin) = withdraw.min_coin_amount {
    if min_coin > coin_amount {
        return Err(AmmError::ExceededSlippage.into());
    }
}
if let Some(min_pc) = withdraw.min_pc_amount {
    if min_pc > pc_amount {
        return Err(AmmError::ExceededSlippage.into());
    }
}
```
This ensures that whichever bound a caller actually configures is always enforced, rather than being silently ignored whenever the other bound is left unset.

### Proof of Concept
1. LP calls `withdraw()` with `min_coin_amount = Some(X)` (a real minimum they require) and `min_pc_amount = None` (they don't care about the pc-side minimum) — a valid call per the instruction's `Option<u64>, Option<u64>` signature. [3](#0-2) 
2. In `process_withdraw`, `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` evaluates to `false` because `min_pc_amount` is `None`. [4](#0-3) 
3. The slippage branch is skipped entirely, so even though `coin_amount < X` (violating the LP's stated minimum), no `ExceededSlippage` error is raised, and `Invokers::token_transfer_with_authority` proceeds to transfer the sub-minimum `coin_amount` to the LP anyway. [5](#0-4) 
4. If an attacker sandwiches this withdrawal with swaps that shift the pool ratio unfavorably right before it lands, the LP receives less than the `min_coin_amount` they explicitly configured, with no on-chain rejection.
