## Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop` (tenant identity) that the registry hands to application webhook handlers is read straight from the `x-shopify-shop-domain` HTTP header, which is completely outside the HMAC's protected content. This breaks the intended binding `HMAC(body, secret) == received_hmac ⇒ (body, shop) is authentic`, because the equality only ever verifies `HMAC(body, secret) == received_hmac`, never anything that ties `shop` to that specific `body`/`hmac` pair.

### Finding Description
The webhook processing pipeline is: [1](#0-0) [2](#0-1) 

`shop` is parsed directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no validation against the signed content: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header) straight to the app's handler as the tenant identifier: [4](#0-3) 

The HMAC validator only signs/verifies `to_signable_string`, i.e. the raw body — never the `shop`, `topic`, `webhook-id`, or `api-version` headers: [5](#0-4) 

The security-relevant identity object `WebhookMetadata` that is handed to the app's `WebhookHandler#handle` combines the *unauthenticated* `shop` header with the (correctly) authenticated `body`: [6](#0-5) 

Because Shopify signs webhooks with the app's single `client_secret` (shared across every shop that installs the app, not a per-shop secret), `HMAC(body, client_secret)` is identical for a given `body` regardless of which shop actually triggered the event. An attacker who can obtain even one genuine `(body, hmac)` pair for content they fully control (e.g. by observing an inbound webhook delivered to their own test/dev endpoint — an ngrok tunnel, a request-inspection tool, or their own instance of the app pointed at attacker infrastructure, all of which are things an ordinary merchant/app-installer can legitimately do) can replay that exact `body` + `hmac` to the production app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop. `Utils::HmacValidator.validate` will still return `true` because it never looked at the shop header, and `Registry.process` will hand the forged event to the app's handler labeled with the victim's shop.

This crosses the exact identity-binding boundary the reference bug class describes: "a field acted on (the tenant `shop`) but not covered by the HMAC."

### Impact Explanation
This is a **cross-tenant** vulnerability (Critical): a webhook handler acting on `data.shop` (a very common pattern — e.g. handlers that delete/redact data, revoke access, mark accounts uninstalled, or otherwise mutate per-tenant state keyed by `shop`) can be triggered against a shop the attacker does not control, using event bodies of the attacker's choosing (since body content for many topics, e.g. product/order creation on the attacker's own shop, is attacker-influenced). This can be used to corrupt or manipulate another merchant's app state, trigger deletion/redaction workflows for a victim, or otherwise cause the app to act cross-tenant, entirely from the perspective of an unprivileged internet user (an app-installing merchant) who never needed the `client_secret`.

### Likelihood Explanation
Moderate-to-high: no `api_secret_key`/access token is needed, only observation of one legitimate webhook delivery for content the attacker controls (trivially achievable by installing the app on any shop the attacker owns, or via widely-used testing proxies/logging tools that show raw inbound HTTP requests). The replay itself (posting to the shared webhook endpoint with a forged shop header) requires nothing more than standard HTTP tooling.

### Recommendation
Bind the tenant identity into the authenticated content before trusting it: include `shop`/`topic`/`webhook_id` in the signed material (or independently authenticate them, e.g. re-fetch/verify the shop that installed the app matches a value derived from a per-shop secret or the offline access-token record), and/or cross-check the header `shop` against a shop value embedded in the verified body when available, rejecting mismatches. At minimum, document loudly that `request.shop` is unauthenticated and must never be used as the sole tenant key without an independent binding.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and points a request-inspection proxy (e.g. local ngrok debugging UI) at the delivery endpoint, or otherwise observes the raw webhook HTTP request Shopify sends for a topic whose body the attacker can shape (e.g. `products/create`).
2. Attacker captures the exact `raw_body` bytes and the corresponding `x-shopify-hmac-sha256` value Shopify computed with `client_secret`.
3. Attacker replays an HTTP POST to the production app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `raw_body` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-chosen JSON>, ...)`, causing the app to act on the victim tenant using attacker-supplied data.
