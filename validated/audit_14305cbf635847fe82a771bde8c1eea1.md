### Title
Webhook `shop-domain` header is trusted for shop attribution but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and attribute the webhook come from unauthenticated HTTP headers that are never included in the signed content. Any attacker who can obtain one valid `(raw_body, hmac)` pair for the shared app secret can replay it with a forged `shop-domain` header to make the gem attribute the webhook payload to an arbitrary victim shop.

### Finding Description
`HmacValidator.validate` accepts a `VerifiableQuery` and validates only `hmac` against `to_signable_string`: [1](#0-0) 

The `VerifiableQuery` interface only requires `hmac` and `to_signable_string`: [2](#0-1) 

For webhooks, `Request#to_signable_string` returns solely the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from the (attacker-controllable, unsigned) HTTP headers: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken straight from those unsigned headers: [5](#0-4) 

Because the shop attribution field is "acted on" (passed into `WebhookMetadata` and the app's handler) but is not part of the HMAC-covered bytes, the binding `hmac_valid(raw_body) == shop_is_authentic(shop_header)` does not hold. Since the app's webhook secret (`Context.api_secret_key`, i.e., the app's `client_secret`) is shared across every shop that installs the app, any user who installs the app on their own (attacker-controlled) shop will legitimately receive webhooks with valid `(raw_body, hmac)` pairs computed with that same shared secret. The attacker can then re-POST that exact `raw_body` with the same `hmac` header to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still return `true` (it only checks `raw_body` against `hmac`), and `Registry.process` will hand the attacker-controlled body to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant isolation the gem is supposed to provide: a webhook handler that trusts `WebhookMetadata#shop` to select or scope a merchant's data (e.g., to look up a session, write records, or trigger shop-specific side effects such as `app/uninstalled` or GDPR webhooks) can be made to act on forged data while believing it originates from a shop the attacker does not control. This is a cross-tenant access primitive stemming entirely from this gem's `Webhooks::Request`/`Registry` implementation, not from host-application misuse.

### Likelihood Explanation
Any internet user can install the merchant app on their own free development/trial shop to obtain a valid `(raw_body, hmac)` pair signed with the app's shared secret, then replay it against the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only the ability to install the app once as a normal merchant, which is the intended, unprivileged entry point for any Shopify app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string, or otherwise cryptographically bind `request.shop` to the validated payload (e.g., by validating that the shop belongs to a session/install the app already created via OAuth) before dispatching to handlers in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, receiving a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(app_secret, B)`).
2. Attacker replays an HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` returns `true` because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the app to process attacker-controlled data as if it came from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
