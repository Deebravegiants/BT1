### Title
Permanent freeze of curve-raised LT and creator token allocation via unrecoverable revert in HyperSwap V2 `mint()` during `finalizeGraduation` - (File: packages/contracts/src/Bonding.sol)

### Summary
The CVE describes a resource that is allocated and never freed, causing a permanent denial of service. The analogous class in `Bonding.sol` is the two-phase graduation pipeline: once a token enters `Lifecycle.Graduating`, its curve-raised LT and 250M LP-bound tokens are "parked" on the `Bonding` contract and there is no path back to `Lifecycle.Curve` and no alternate recovery function — `finalizeGraduation` is the only exit. If the amounts handed to the underlying HyperSwap V2 pair's `mint()` are small enough to underflow the `MINIMUM_LIQUIDITY` subtraction, `finalizeGraduation` reverts unconditionally and forever, permanently freezing the parked funds exactly like the CVE's un-freed resource causing permanent denial of service.

### Finding Description
`_enterGraduating` moves a token to `Lifecycle.Graduating` and caches `(tokensForLP, ltFromPair)` in `pendingGraduation`, pinned at the last curve price [1](#0-0) . While in this state, `buy` and `sell` unconditionally revert with `TokenIsGraduating`, and `triggerGraduation` also reverts for the same reason [2](#0-1) . The only function that can move the token forward is the permissionless `finalizeGraduation`, which ultimately calls `_seedUniswapV2Direct` → `_seedDirectMint` (empty-pair path, ~99% of graduations) which does `IUniswapV2Pair(pair).mint(_s().lpLock)` [3](#0-2) .

Standard Uniswap-V2-style `mint()` computes `liquidity = sqrt(amount0 * amount1) - MINIMUM_LIQUIDITY` on the first mint into an empty pool; if `sqrt(amount0*amount1) < MINIMUM_LIQUIDITY` (1000), this subtraction underflows and the pair's `mint` reverts. `tokensForLP` and `ltFromPair` are derived purely from the curve's own state at the moment of crossing a graduation trigger [4](#0-3) . Because graduation can fire off either the USD trigger or the supply-sellout trigger (`IPair(pair).tokenBalance() == 0`) [5](#0-4) , and because the LT reserve asset is an external rebasing-priced token whose `exchangeRate()` can drift arbitrarily between launch and the moment of the sellout trigger, it is possible for the curve to fully sell out (`tokenBalance()==0`) while `ltFromPair` (real LT raised, net of the recovered virtual reserve) is proportionally tiny — because `tokensForLP` is derived at the same fixed ratio as `ltFromPair` (`tokensForLP = ltFromPair * tokenReserve / assetReserve`), both sides of the product `tokensForLP * ltFromPair` shrink together. If that product's square root falls under 1000 units (18-dp reserves make this a narrow but non-empty band achievable through LT appreciation between launch and sellout, or through a series of very small trailing buys that exhaust `tokenBalance()`), the `mint()` call inside `finalizeGraduation` reverts every single time it is retried, since the cached `(tokensForLP, ltFromPair)` in `pendingGraduation` never change and there is no alternate code path or admin recovery function that can un-stick the token.

The `RebalanceParams`/`_seedRebalancing` cold path (hostile pre-seed defense) is also gated on `_seedDirectMint` as its own fallback for tiny reserves, so it does not provide an escape from this same underflow condition either [6](#0-5) .

### Impact Explanation
Once stuck, the token's entire curve-raised LT reserve (buyer funds) and 250M reserved LP tokens (creator's allocation) are permanently trapped on `Bonding` with no owner-only or permissionless rescue function reachable while `Lifecycle.Graduating` — `buy`/`sell`/`triggerGraduation` are all gated shut and `finalizeGraduation` is the sole, permanently-reverting exit. This is a permanent freezing of trader and creator funds, satisfying the required impact bar.

### Likelihood Explanation
Reaching the underflow requires the LP-seed amounts to fall below the `MINIMUM_LIQUIDITY`-derived floor at the exact moment a graduation trigger fires. This is a narrow but realistic band given the system's own acknowledged LT-appreciation drift (`_deployAndSeed`'s natspec explicitly documents that the curve's USD depth "drifts with the LT") and the supply-sellout trigger's independence from USD value — an attacker could deliberately walk the curve to `tokenBalance()==0` via many minimal trailing buys after LT price has moved to concentrate the trailing `ltFromPair`/`tokensForLP` values below the mint floor.

### Recommendation
Add a recovery path for a token stuck in `Lifecycle.Graduating` whose `finalizeGraduation` cannot succeed — e.g., an owner- or permissionless "abort graduation" that returns the parked LT/tokens to the curve or refunds them, or floor `tokensForLP`/`ltFromPair` at `_prepareGraduationLiquidity` time so the product can never fall under the V2 `MINIMUM_LIQUIDITY` bound.

### Proof of Concept
1. Launch a token; let the LT's `exchangeRate()` appreciate substantially after launch (external rebasing asset, outside protocol control).
2. Drive the curve to the sellout trigger (`IPair.tokenBalance() == 0`) via a sequence of minimal-size trailing buys near the end of the curve, such that the residual `assetReserve` (hence `ltFromPair` and the proportionally-scaled `tokensForLP`) is minimized.
3. `canGraduate` returns true via the supply leg; `_enterGraduating` caches the tiny `(tokensForLP, ltFromPair)` pair in `pendingGraduation`.
4. Anyone calls `finalizeGraduation(tokenAddress)`; `_seedDirectMint`'s call to `IUniswapV2Pair(pair).mint(lpLock)` reverts due to `MINIMUM_LIQUIDITY` underflow.
5. Every subsequent call to `finalizeGraduation` reverts identically (cached amounts are immutable), and no other function can move the token out of `Lifecycle.Graduating` — the curve's raised LT and the creator's LP token allocation are frozen permanently.

        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();

        if (info.creator == address(0)) return false;

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
