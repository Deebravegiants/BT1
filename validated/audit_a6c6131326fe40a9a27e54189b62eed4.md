### Title
Unchecked ERC20 return value in `withdraw()`/`SweepDust` allows silent transfer failure and permanent freezing of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` pays out escrowed order tokens using a raw low-level `.call()` to the token's `transfer` selector, and only checks that the call did not revert (`success`), never decoding/validating the returned `bool`. Non-standard ERC20s that return `false` on failure instead of reverting (the same token-behavior class cited in the referenced Cooler audit finding) will make the payout appear successful while the beneficiary receives nothing, yet the escrow accounting is unconditionally decremented and the order is marked filled/refunded.

### Finding Description
In `withdraw()`: [1](#0-0) 
and in the `SweepDust` branch of `onAccept()`: [2](#0-1) 

the contract does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` only reflects whether the external call reverted, not whether the token's `transfer()` returned `true`. For a token that returns `false` on failure (rather than reverting), `success` is `true` even though no tokens moved. Despite this, the function proceeds to:
- decrement `_orders[body.commitment][token] -= amount;` (escrow accounting reduced as if paid out),
- set `_filled[body.commitment] = beneficiary;` (order marked as filled/refunded),
- emit `EscrowReleased`/`EscrowRefunded`.

This path is reached unprivileged by any relayer delivering a `RedeemEscrow`/`RefundEscrow` POST request (`onAccept`) or a GET response confirming a fill (`onGetResponse`), both standard, permissionless message-delivery flows in the intents system: [3](#0-2) [4](#0-3) 

Notably, the input-escrow path (`placeOrder`) correctly uses OpenZeppelin's `safeTransferFrom` via `using SafeERC20 for IERC20;`: [5](#0-4) 
so `SafeERC20` is already imported and used elsewhere in the same file, but the payout path (`withdraw`, `SweepDust`, and the fee redemption at line 720) was written with a manual low-level call instead, breaking the safety guarantee for non-conforming tokens.

### Impact Explanation
For any ERC20 that does not strictly conform to reverting on failed transfer (return `false` instead), a legitimate beneficiary's escrowed funds can be silently "swept" as accounted-for without the tokens actually leaving the contract. Because `_orders[...][token]` is decremented and `_filled[...]` is set regardless of actual token movement, there is no remaining code path to retry or reclaim the balance — the tokens become permanently stuck/unaccounted in the contract while the on-chain state asserts the order was already filled/refunded. This is a fund-loss/freezing bug reachable purely by relayed message delivery for orders that use such tokens as inputs, with no privileged role required to trigger it.

### Likelihood Explanation
The trigger requires the order's input token to be a non-standard ERC20 (return-false-on-failure, e.g., legacy tokens like ZRX or any token with such a compatibility mode) and the transfer to actually fail (e.g., due to blacklist/pause conditions on the token, or precise edge conditions causing `transfer` to fail without reverting). This is a realistic scenario given the protocol explicitly intends to support "all ERC20s" as intent-input tokens, and Tron/TRC20 tokens historically include many non-standard implementations, making this contract (a Tron-specific deployment) particularly exposed to this class of token.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;` in this file) instead of the raw `.call()` + `success`-only check, in all three payout locations: `withdraw()`'s token loop, the fee-token redemption, and the `SweepDust` branch:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This reverts on both call failure and `false` return values, ensuring escrow state is only decremented when the transfer genuinely succeeded.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an input token `T` that implements ERC20 but returns `false` (not revert) when `transfer` fails (e.g., blacklisted recipient, paused state, or insufficient allowance edge case triggered post-order).
2. User places an order with `T` as input; `placeOrder` correctly escrows `T` via `safeTransferFrom`.
3. Order is filled/cancelled on the destination chain, and a relayer delivers a `RedeemEscrow`/`RefundEscrow` POST request (or a `Filled`-check GET response) to this contract's `onAccept`/`onGetResponse`.
4. `withdraw()` calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`. Suppose the transfer condition inside `T` causes it to return `false` (e.g., beneficiary temporarily blacklisted at settlement time) — the low-level call still succeeds (`success == true`) because the token doesn't revert.
5. `withdraw()` proceeds: decrements `_orders[commitment][token]` to zero and sets `_filled[commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded`, even though the beneficiary's `T` balance never increased.
6. The escrowed `T` tokens remain in the `IntentGatewayV2` contract with no code path to redeem them (`_orders` already zeroed, order already marked filled), permanently freezing the beneficiary's funds.
