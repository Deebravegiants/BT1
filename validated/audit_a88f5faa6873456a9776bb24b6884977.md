Confirmed: the webhook HMAC covers only the raw body, while `shop`, `topic`, and `webhook_id` are read from unauthenticated headers and forwarded directly to the app handler.

### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC signs only the body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed in `ShopifyAPI::Webhooks::Registry.process` binds the request signature exclusively to the JSON payload. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers (`shopify_header`) and are never part of the signed material, yet `Registry.process` uses `request.shop` as the tenant identity forwarded to the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` establish the signable material as `@raw_body` alone: [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors instead read directly from caller-supplied headers with no cryptographic binding: [2](#0-1) .

`Registry.process` validates only this body-bound HMAC and then immediately trusts `request.shop` as the tenant key handed to the registered handler: [3](#0-2) . The equality the system implicitly relies on is `authenticated_identity == request.shop`, but the HMAC only proves `authenticated_identity == raw_body`; `request.shop` is disjoint from what is authenticated.

This is the same bug class as the report's fee-encoding mismatch: a value that is consumed by downstream logic (`transactionFee` there, `shop` here) is not actually covered by the validation/encoding contract that is assumed to bind it, so the two "identities" (signed value vs. acted-upon value) silently diverge.

### Impact Explanation
Any party who can obtain one legitimately-signed webhook body/HMAC pair for their own Shopify store (trivial: install the app on their own dev store and receive a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will pass HMAC validation (the body is untouched) and hand the handler a `WebhookMetadata` claiming an attacker-chosen `shop`: [4](#0-3) . Host applications that key data-mutating logic (order/customer/product sync, GDPR data deletion routing, etc.) off `data.shop` as the documented app is expected to do (per `docs/usage/webhooks.md`) can be made to apply another merchant's webhook payload to a different tenant's records — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Reaching this requires only: (1) the ability to obtain one valid signed webhook (self-service via installing the app on any store, including the attacker's own), and (2) the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header, both of which are available to an unprivileged internet user with no access to `api_secret_key`.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-covered material, or at minimum require host apps to cross-check `request.shop` against a known/installed shop record before trusting it, and document this requirement explicitly since the current `WebhookHandler` example in `docs/usage/webhooks.md` treats `data.shop` as trusted without caveat.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; capture a real webhook delivery — raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's real secret).
2. POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HMAC(secret, B)` and it matches `H`, so `Utils::HmacValidator.validate` returns `true`: [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's payload>, ...)` and processes it as if it originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
