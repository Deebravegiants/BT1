### Title
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorize redirect from an unsanitized `shop` value - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`begin_auth` interpolates the caller-supplied `shop` argument directly into `auth_base_uri(shop)` (`"https://#{shop}/admin"`) with no call to `Utils::ShopValidator.sanitize!`, unlike every sibling auth flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all validate `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it. This lets a caller-controlled `shop` string steer the generated `auth_route` to an arbitrary host/path instead of a genuine `*.myshopify.com` domain.

### Finding Description
Binding claimed: `auth_route.host == <trusted Shopify domain sanitized by ShopValidator>`. Actual code: [1](#0-0) [2](#0-1) 

`auth_base_uri` does raw string interpolation of `shop` (`"https://#{shop}/admin"`) with no `ShopValidator.sanitize!` call, whereas the comparison methods explicitly validate first: [3](#0-2) [4](#0-3) 

`ShopValidator.sanitize!` (`lib/shopify_api/utils/shop_validator.rb:56-64`) is the only gate that forces `shop` to resolve to one of `TRUSTED_SHOPIFY_DOMAINS` (or a configured `myshopify_domain`); `begin_auth` never calls it, so an attacker-influenced `shop` (e.g. `"attacker.com/x?redirect_uri=https://attacker.com/steal"`) produces an `auth_route` whose host/path is fully attacker-controlled, since the injected `?` breaks URL parsing and swallows the legitimately-built `/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=...` segment into the query string of `https://attacker.com/x`.

The downstream callback path (`validate_auth_callback`) is protected: it requires `Utils::HmacValidator.validate(auth_query)` to pass, which recomputes an HMAC over the query using `Context.api_secret_key`/`old_api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:13-31`). An unprivileged attacker without `api_secret_key` cannot forge a callback that would pass this check, so they cannot make the app's token-exchange step trust a forged `shop`. This means the exploitable surface is strictly limited to the **initial redirect** built by `begin_auth`, not the callback/token-exchange leg.

Exploiting this requires: (1) the host application to pass an attacker-influenced value into `begin_auth`'s `shop:` argument (the documented pattern of reading `shop` from a header/query param, as referenced in the question), and (2) the victim merchant's browser to actually follow the resulting `auth_route`. Realizing account compromise from the misdirected redirect (e.g., a convincing phishing page capturing the merchant's real Shopify login, or relaying the flow back to genuine Shopify) requires additional victim interaction, which falls into social-engineering territory explicitly excluded by the rules. What remains squarely in-scope and demonstrable purely via this gem's code is: `begin_auth` fails to enforce the same domain-trust invariant (`ShopValidator.sanitize!`) that its sibling OAuth methods enforce, producing a `auth_route` whose destination host is not guaranteed to be a genuine Shopify domain.

### Impact Explanation
This matches the High-severity category "session fixation or forced OAuth completion": the app can be made to direct the merchant's browser into an OAuth flow whose destination is not Shopify, exposing `client_id`, `scope`, `redirect_uri`, and the CSRF `state` nonce to a non-Shopify host. It does not by itself achieve token theft or authentication bypass, because (a) `client_id`/`scope` are not secrets, and (b) the callback-side HMAC check (`HmacValidator.validate`) still blocks a forged callback from being accepted as a legitimate token exchange, since the attacker never possesses `api_secret_key`. Full compromise (stealing a real authorization code or access token) additionally requires the victim to interact with a spoofed page or the attacker relaying to real Shopify — social engineering, out of scope. Blast radius is per-victim-merchant, repeatable against any merchant the attacker can lure to a crafted install/OAuth-initiation link.

### Likelihood Explanation
Requires: (1) a host app that forwards an untrusted `shop` value into `begin_auth` without its own validation (the gem provides no protection here, unlike its sibling methods), and (2) the merchant to click through to the crafted URL. Attacker cost is low (crafting a URL), but achieving real damage needs merchant interaction beyond merely receiving the redirect.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or an equivalent domain-format check) at the top of `Oauth.begin_auth`, before building `auth_route`, exactly as done in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, and raise `Errors::InvalidShopError` for any `shop` that isn't a trusted Shopify domain.

# test/auth/oauth_test.rb (new case)
def test_begin_auth_rejects_or_sanitizes_untrusted_shop
  ShopifyAPI::Context.setup(..., is_private: false)

  malicious_shop = "attacker.com/x?redirect_uri=https://attacker.com/steal"

  # EXPECTED (post-fix): raises Errors::InvalidShopError, matching ClientCredentials/RefreshToken behavior
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/callback")
  end

  # CURRENT (vulnerable) BEHAVIOR: no exception, and auth_route host is not a trusted Shopify domain
  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/callback")
  uri = URI.parse(result[:auth_route])
  refute ShopifyAPI::Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS.any? { |d| uri.host&.end_with?(d) }
  # demonstrates auth_route.host == "attacker.com" != <trusted Shopify domain>, breaking the CREDENTIAL DESTINATION binding
end
