## Verdict: No vulnerability found for this question.

### Analysis

The question conflates two distinct checks that are correctly separated by design:

**1. Structural signature compatibility (registration-time, static)**

`check_dispatch_type_compatibility_impl` in `function_info.rs` compares the *static* argument/return type structure of the framework dispatcher (`dispatchable_withdraw<T: key>`) against the registered hook, matching `ty_param_abilities`, `return_tys`, and `param_tys` [1](#0-0) . This check is inherently generic — both sides use the *same* type parameter `T`, so there is no "concrete instantiation" to validate at this point; it only confirms the hook has a compatible generic signature. It runs once, during `register_dispatch_functions`, and the result (`DispatchFunctionStore`) is immutable thereafter (`EALREADY_REGISTERED` guard) [2](#0-1) .

**2. Which hook gets invoked at call time (dynamic, but not type-based)**

`native_dispatch` in `dispatchable_fungible_asset.rs` does not need to re-validate `T` because the function it dispatches to is *not selected based on the generic type argument at all*. It is selected by `fungible_asset::withdraw_dispatch_function(store)`, which looks up the `DispatchFunctionStore` resource keyed on the **store's metadata object address** [3](#0-2) . The module/function name to dispatch (`module_name`, `func_name`) is baked into that on-chain resource at registration time and simply forwarded as a `SafeNativeError::FunctionDispatch` / `NativeResult::CallFunction` to the VM [4](#0-3) . The generic parameter `T` is only a compile-time/type-safety artifact of the `Object<T>` handle threaded through the call — it plays no role in *which* hook is chosen, and `Object<T>` construction/validation (that the address actually holds a resource of type `T`) is enforced by Move's own bytecode verifier and object-address-to-typed-object conversion logic elsewhere in `object.move`, not inside `native_dispatch`.

Because dispatch-target selection is address-keyed (one `DispatchFunctionStore` per object, fixed at creation) rather than type-parameter-keyed, there is no path by which supplying a mismatched `T` at a withdraw/deposit call site causes the VM to invoke a *different* store's hook or execute against the wrong `TransferRef`/store metadata. The `transfer_ref` passed into the hook is likewise fetched via `borrow_transfer_ref(store)`, which resolves the `TransferRefStore` at the same object address [5](#0-4) , so it is bound to the object being operated on, not to the caller's generic type annotation.

This does not cross a custody boundary: an unprivileged caller cannot use type-parameter mismatch to redirect a withdraw/deposit onto another object's transfer ref or dispatch hook, since selection is address-bound and immutable post-registration, and Move's own generic/ability type system (verified independent of this native) prevents constructing an `Object<T>` value that doesn't correspond to the actual on-chain type at that address.

pub(crate) fn native_dispatch(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut arguments: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    let (module_name, func_name) = extract_function_info(&mut arguments)?;

    // Check if the module is already properly charged in this transaction.
    let check_visited = |a, n| {
        let special_addresses_considered_visited =
            context.get_feature_flags().is_account_abstraction_enabled()
                || context
                    .get_feature_flags()
                    .is_derivable_account_abstraction_enabled();
        if special_addresses_considered_visited {
            context
                .traversal_context()
                .check_is_special_or_visited(a, n)
        } else {
            context.traversal_context().legacy_check_visited(a, n)
        }
    };
    check_visited(module_name.address(), module_name.name()).map_err(|_| {
        SafeNativeError::abort_with_message(
            abort_codes::ENOT_LOADED,
            format!(
                "Module {}::{} is not loaded prior to native dispatch",
                module_name.address(),
                module_name.name()
            ),
        )
    })?;

    context.charge(DISPATCHABLE_FUNGIBLE_ASSET_DISPATCH_BASE)?;

    // Use Error to instruct the VM to perform a function call dispatch.
    Err(SafeNativeError::FunctionDispatch {
        module_name,
        func_name,
        ty_args: ty_args.to_vec(),
        args: arguments.into_iter().collect(),
    })
