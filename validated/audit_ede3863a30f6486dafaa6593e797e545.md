### Title
Unvalidated swap routes can hide wallet-draining calls in signed authorization trees - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied opaque `StrategySwap` bytes and forward them to the configured router without decoding or restricting the venues encoded inside the route. `swap_tokens` only authorizes the exact `token_in.transfer(controller, router, amount_in)` needed by the router, then measures the controller’s input and output balances. A malicious application can therefore provide a route whose venue contract performs an unrelated token transfer from the victim; transaction simulation attaches that transfer as a child of the victim’s `swap_collateral` authorization. If the victim signs the poisoned authorization tree, the rogue venue can steal unrelated wallet funds while the router still returns a valid output and the controller’s balance checks pass.

### Finding Description
`swap_collateral` authenticates the caller and verifies that the caller owns or delegates the target account, but it accepts the caller-provided `swap` argument without inspecting its contents. The requested collateral is withdrawn and passed to `withdraw_and_swap_from_supply`, which reaches `swap_tokens`. `swap_tokens` rejects only an empty route, authorizes one exact input transfer from the controller to the configured router, and invokes `router.execute_strategy(&controller, &amount_in, swap)`. Afterward it checks only that the controller did not gain input, spent no more than `amount_in`, and received positive `token_out`.

The payload can name an attacker-controlled venue. Such a venue can invoke `wallet_token.transfer(victim, attacker, amount)` while it is below the victim’s controller authorization in the call tree. Soroban records that unrelated token transfer as a child of the victim’s signed root invocation. Neither the controller’s exact controller-to-router authorization, its positive-output check, nor the final account-risk check rejects that unrelated child transfer.

### Impact Explanation
A victim can lose unrelated wallet tokens that were never supplied to the lending position and were not part of the swap’s `token_in`. The stolen amount is bounded by the victim’s token balances and the malicious transfer included in the signed authorization tree, not by `amount_in` or the route’s declared minimum output. The transaction can still deliver the expected collateral and pass all account checks, making the theft atomic with an otherwise successful `swap_collateral` operation.

### Likelihood Explanation
Exploitation requires victim interaction: a malicious interface, quote service, or contract-composition path must convince the victim to sign a transaction whose authorization tree contains the hidden transfer. No protocol privilege, leaked key, oracle manipulation, or vulnerable token is required. The malicious venue only needs to return normally while the router delivers enough output for the controller’s positive-output and final-risk checks.

### Recommendation
Do not allow route payloads to name arbitrary contract addresses. Enforce an on-chain allowlist of venue contracts before dispatch, or replace arbitrary venue calls with fixed adapters for governance-approved venues. In addition, clients must decode the complete authorization tree before signing and reject any entry other than the expected input transfer, but off-chain verification should not be the only protection because users may sign poisoned trees through compromised or malicious interfaces.

### Proof of Concept
1. The victim owns a healthy lending account with supplied USDC and also holds an unrelated `WALLET_TOKEN`.
2. The attacker deploys a contract whose swap-compatible function calls `WALLET_TOKEN.transfer(victim, attacker, victim_balance)`.
3. A malicious interface submits `swap_collateral(caller=victim, account_id, current=USDC market, from_amount, new=ETH market, swap=crafted_route)`, where `crafted_route` directs the router through the attacker contract.
4. The controller authorizes only `USDC.transfer(controller, router, amount_in)`, invokes `execute_strategy`, and measures the resulting ETH receipt.
5. The attacker contract executes the unrelated `WALLET_TOKEN.transfer(victim, attacker, victim_balance)` during the route.
6. Simulation records that transfer as a child of the victim’s `swap_collateral` authorization. If the victim signs that tree, the host accepts the transfer, the router pays the expected output, and the victim loses the unrelated wallet balance.
