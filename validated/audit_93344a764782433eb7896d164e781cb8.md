### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` value returned by `Request#shop`, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , which is not part of the signed payload.

### Finding Description
`Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)` [4](#0-3) , then forwards `request.shop` (an unauthenticated header) straight into `WebhookMetadata` and to the app's handler [5](#0-4) . The binding that should hold is:

`shop` value trusted by the handler == `shop` value cryptographically bound by the HMAC

but in this gem that equality does not hold: the HMAC only binds `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers with zero cryptographic binding [6](#0-5) . Since Shopify signs `hmac-sha256` over the body with the app's shared secret, and that secret is shared across every shop installing the app, any tenant whose shop can trigger delivery of a webhook with a given body (or any actor who can compute/replay a valid HMAC for a body, e.g. a shop replaying another merchant's previously observed webhook body/signature pair) can present an arbitrary `shop-domain` header value alongside it. The gem provides no mechanism, and documents none, for verifying that the header-asserted `shop` actually corresponds to the tenant that produced the signed body.

### Impact Explanation
Passing an unauthenticated `shop` value to the host application's webhook handler is a cross-tenant identity binding break: any application built on top of this gem that uses `WebhookMetadata#shop` (returned by `Registry.process`) to select which tenant's data/session/DB row to mutate is relying on a value this gem never authenticates. This matches the "Critical - cross-tenant access" impact category, since a webhook processed under one shop's signed body can be attributed to a different, attacker-chosen shop.

### Likelihood Explanation
Exploitability depends on an unprivileged actor's ability to get any valid `(body, hmac)` pair delivered with a forged `shop-domain` header. Because HTTP headers are outside Shopify's webhook signature scope for this gem's own verification code, and the gem does not cross-check `shop` against the signed content in any way, this is a structural gap in the gem itself rather than a host-application bug — it is reachable purely by controlling headers on an otherwise validly-signed request, which is why this is flagged instead of dismissed as a host-application responsibility.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed payload verification, or otherwise cryptographically bind them (e.g., verify against a shop-specific secret, or require the host app to independently confirm `shop` against session storage before trusting it) rather than exposing `Request#shop` as a directly trusted, unauthenticated field in `WebhookMetadata`.

### Proof of Concept
1. Attacker observes/receives one legitimately signed webhook delivery (raw body `B` and its correct `hmac-sha256` header `H`, computed by Shopify over `B` with the app's shared secret — the same secret for all shops using the app).
2. Attacker (or a malicious/compromised shop) replays a POST to the app's webhook endpoint with body `B`, the same valid `hmac-sha256` header `H`, but a forged `shopify-shop-domain` header set to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`@raw_body`) against `H` [1](#0-0) [7](#0-6) .
4. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop` is the forged `victim-shop.myshopify.com` header value [5](#0-4) .
5. Any host application logic that trusts `data.shop` to select tenant-scoped resources now operates on the wrong tenant's data using an unauthenticated identifier.
