### Title
Cross-Tenant Webhook Spoofing via Shop-Domain Header Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `HmacValidator` computes the webhook signature exclusively over the raw HTTP body, while the `shop`, `topic`, and `webhook_id` fields consumed by `Webhooks::Registry.process` are taken directly from HTTP headers that are entirely excluded from that signature. This breaks the binding "bytes verified == bytes acted on": the app authenticates the body but trusts an unauthenticated header to attribute that body to a tenant (shop).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or its HMAC: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then forwards the unauthenticated `request.shop` value into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate` signs/compares against `verifiable_query.to_signable_string`, i.e., body-only for webhook requests, per `hmac_validator.rb`: [4](#0-3) 

Critically, Shopify webhook HMACs are computed with the **app-level** `client_secret`/`api_secret_key`, which is identical for every shop that installs the app — it is not a per-shop secret. This means any shop that installs the app (including one owned by an unprivileged attacker) can generate a body+HMAC pair that is valid under the app's shared secret. An attacker who operates their own installation of the app can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from a real webhook delivery to their own endpoint (or via any means of resending a request directly to the app's public webhook endpoint), then submit a request to that same endpoint with the same valid body/HMAC but a forged `X-Shopify-Shop-Domain` header naming a victim shop. Because the header is not part of the signed content, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the handler with `WebhookMetadata.new(..., shop: <victim-shop>, body: <attacker-authored-body>, ...)`.

This is the direct analog of the reported bug class: "a field acted on but not covered by the HMAC." In the original report, the tick that determined liquidity accounting was skipped by the boundary-crossing loop yet still used to compute rewards; here, the `shop` field is used to attribute/act on webhook data yet is never included in the value that the HMAC actually authenticates.

### Impact Explanation
Any downstream application logic that keys per-tenant behavior off `WebhookMetadata#shop` (data isolation, order/customer/inventory updates scoped by shop, billing/subscription events, GDPR/data-request webhooks, etc.) can be tricked into applying attacker-controlled webhook payloads to a different, victim tenant's data, because the gem asserts the body is authentic while silently trusting an unauthenticated header for tenant attribution. This satisfies the "cross-tenant access" criterion (Critical) since the security boundary between two merchants' installations of the same app is crossed using only a header value under attacker control, with no access token, TLS interception, or social engineering required — only an ordinary (attacker-owned) app installation and the ability to POST directly to the app's public webhook endpoint.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint by design (Shopify webhook receivers are open by necessity), so a request forger only needs the endpoint URL (typically documented/predictable, e.g. `/webhooks`) and one legitimate `(raw_body, hmac)` pair, which is trivial to obtain by installing the app on an attacker-controlled shop and triggering the webhook topic themselves. No secret material, privileged account, or host cooperation beyond normal app installation is required, making this readily exploitable wherever the host app trusts `WebhookMetadata#shop` for authorization or data-scoping decisions.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before use, e.g., by having `Webhooks::Request#to_signable_string` concatenate a canonical representation of these header values with `@raw_body`, and re-deriving/validating the HMAC over that combined string. At minimum, document loudly (and ideally enforce in this gem) that host applications must independently corroborate `shop` against the specific webhook subscription/mandate registered for that shop, rather than trusting the header value as an authenticated tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own development shop (`attacker-shop.myshopify.com`), obtaining a normal installation with the app's shared `api_secret_key` used for HMAC signing (same secret shared by every installer of this app).
2. Attacker triggers a webhook topic (e.g. `orders/create`) on their own shop, causing Shopify to POST a real webhook to the app's public endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the shared app secret. Attacker captures this exact `(raw_body, hmac)` pair (e.g., via a proxy they control, since it is their own shop's traffic).
3. Attacker crafts a new HTTP POST directly to the same public webhook endpoint, reusing the captured `raw_body` and `X-Shopify-Hmac-Sha256` value verbatim, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against `hmac` — see [5](#0-4) .
5. `Registry.process` calls the app's registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, and any host-app logic that scopes actions by `data.shop` now processes attacker-controlled data as if it belonged to the victim shop.
