## Title
Unchecked ERC20 `transfer` return value in `IntentsBase._execute` sweep lets non-standard tokens silently fail while dust is recorded and calldata still executes - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._execute()` builds sweep `Call`s that raw-encode `IERC20.transfer.selector` and routes them through `CallDispatcher.dispatch()`, which only checks that the low-level `call` did not revert — it never checks the ERC20 boolean return value. `DustCollected` is also emitted optimistically, before the sweep call is even executed. Non-compliant ERC20 tokens (e.g., tokens like `BADGER` that return `false` instead of reverting on failure) can leave tokens stranded in the `CallDispatcher` while the protocol believes it "collected" that balance as dust and the postdispatch calldata execution (`ICallDispatcher(dispatcher).dispatch(order.output.call)`) has already run.

### Finding Description
In `_execute` (`evm/src/apps/intentsv2/IntentsBase.sol:498-545`), after running solver-supplied `order.output.call` via the `CallDispatcher`, the code sweeps any residual token balance left on the dispatcher back to the gateway: [1](#0-0) 

The sweep calldata is `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)`, dispatched via `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))`: [2](#0-1) 

`CallDispatcher.dispatch` only checks whether the low-level `call` reverted, never the ABI-encoded boolean return value of `transfer`: [3](#0-2) 

For an ERC20 implementation that returns `false` on failure instead of reverting (the exact bug class from the referenced report), `to.call{...}(call.data)` succeeds (`success == true`) even though no tokens moved. `DustCollected(token, balance)` is emitted before this call even runs (line 526), so the event/accounting records dust that was never actually transferred into the gateway. Compare this to the correctly-guarded pattern used elsewhere in the same codebase — e.g. `IntentGatewayV2.sol` measures the *actual* balance delta after the sweep dispatch rather than trusting the transfer call succeeding: [4](#0-3) 

`_execute`, by contrast, has no such balance-delta verification after the sweep — it simply assumes the pre-sweep `balanceOf(dispatcher)` reading equals what was actually collected.

### Impact Explanation
Because the vulnerable path is reachable by an unprivileged solver/filler simply by specifying a non-standard ERC20 as an output token with attached postdispatch calldata (`order.output.call`), tokens legitimately owed to the beneficiary/protocol can be left stuck in the `CallDispatcher` contract while the system's internal dust accounting believes they were swept. This is a fund-freezing condition on the affected output token: the tokens are neither delivered to the recipient (beneficiary already received their portion earlier in the fill logic; this sweep is for solver-supplied surplus/dust) nor properly credited/tracked by the gateway, and there is no re-check or recovery mechanism visible in this function to detect or correct the discrepancy. Given the "medium" severity precedent in the analog report (silent failure of transfer causing incorrect balances/lost funds), and the requirement that only concrete freezing of funds/unsound accounting counts, this matches: dust/tokens can become permanently unswept and unaccounted for.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an order with non-empty `order.output.call` (postdispatch calldata — a supported, documented feature) and (2) an output token that is a non-ERC20-compliant implementation returning `false` rather than reverting on transfer failure (e.g., insufficient balance/allowance edge cases, blacklisted-recipient tokens, or tokens with quirky implementations). Any solver or integrator choosing to route an order's output through such a token, or a token that transiently returns `false` under specific conditions, triggers this silently. No malicious insider or governance action is required — this is triggerable by ordinary calldata content supplied with a fill.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in this same file) instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` routed through the low-level `CallDispatcher`, or explicitly decode and check the boolean return value from `CallDispatcher.dispatch`'s returned bytes for each sweep call. Additionally, adopt the balance-delta verification pattern already present in `IntentGatewayV2.sol` (measure `balanceOf` before/after the sweep dispatch) before emitting `DustCollected`, so dust accounting reflects tokens actually received rather than an assumption that the encoded `transfer` call succeeded.

### Proof of Concept
1. Deploy (or use) a non-standard ERC20 as an intent output token whose `transfer` function returns `false` (rather than reverting) when, e.g., invoked under a specific balance/allowance condition — mirroring the `BADGER` token behavior described in the referenced report.
2. Have a solver fill an order via `IntrinsicIntents`/`ExtrinsicIntents` (which call `IntentsBase._execute`) with `order.output.assets` including this token and a non-empty `order.output.call` (postdispatch calldata), and arrange for the dispatcher to hold a positive balance of this token after the calldata execution (e.g., token minted/transferred to the dispatcher inside `order.output.call`, or leftover from a swap).
3. `_execute` reads `IERC20(token).balanceOf(dispatcher) > 0`, builds a sweep `Call` with `IERC20.transfer.selector`, and emits `DustCollected(token, balance)` optimistically.
4. `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))` executes the transfer; the token's `transfer` returns `false` but the low-level call does not revert, so `CallDispatcher` treats it as success.
5. Verify post-transaction: `IERC20(token).balanceOf(dispatcher)` is unchanged (tokens never moved) while `DustCollected` was emitted and any downstream protocol accounting/treasury sweep assumes the gateway holds that balance — tokens are now stranded in the `CallDispatcher` with no code path shown in `_execute` to detect or recover them.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
