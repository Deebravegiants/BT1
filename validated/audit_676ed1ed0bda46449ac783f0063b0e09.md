### Title
Unchecked-length `copy_from_slice` panic on attacker-controlled BEEFY `Vote.signature` — denial of service in consensus proof conversion (`evm/rust/src/conversions.rs`)

### Summary
`evm/rust/src/conversions.rs` converts an ABI-decoded `Vote` (from a `BeefyConsensusProof`/`SignedCommitment`, i.e. untrusted relayer-submitted consensus proof data) into a `SignatureWithAuthorityIndex` by copying `value.signature` into a fixed `[u8; 65]` buffer with `copy_from_slice` — with no length check beforehand. This is the same bug class as CVE-2017-12837: a length-unchecked copy into a fixed-size buffer driven by attacker-controlled input, causing an out-of-bounds write/panic (denial of service) rather than a validated rejection.

### Finding Description
`evm/rust/src/conversions.rs:356-366`:
```rust
impl From<Vote> for SignatureWithAuthorityIndex {
	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		SignatureWithAuthorityIndex {
			signature,
			index: value.authorityIndex.try_into().expect("authority index out of bounds"),
		}
	}
}
``` [1](#0-0) 

`Vote` is a struct decoded from the `BeefyConsensusProof`/`SignedCommitment` type defined in the Solidity/ABI `EcdsaBeefy.sol` layer and consumed by this Rust conversion module (`beefy` submodule, `cfg(feature = "substrate")`), used when reconstructing a BEEFY signed commitment from an on-chain/relayer-submitted proof for consensus verification. [2](#0-1) 

Rust's `<[u8]>::copy_from_slice` panics if the source slice length does not equal the destination length. Since `value.signature` is `Bytes` decoded straight from attacker/relayer-controlled proof bytes (an ECDSA signature is expected to be 65 bytes, but the ABI encoding places no on-chain-enforced length constraint before this conversion runs), a `Vote.signature` of any length other than 65 causes an immediate panic in the conversion path.

This mirrors the same class of defect the codebase has explicitly hardened elsewhere — e.g. `modules/utils/serde/src/lib.rs:529-532` documents that an identical unchecked `copy_from_slice` into a fixed `[u8;4]` "panics on any length mismatch — and it runs on untrusted RPC input… the panic aborted the node's `rpc` worker thread and took the process down," and was fixed to return a serde error instead. [3](#0-2)  The BEEFY `Vote` conversion in `evm/rust/src/conversions.rs` was not given the same treatment: it directly `copy_from_slice`s without a length check, unlike the sibling `TSignature`/H160/H256 conversions elsewhere in the file which mostly use `try_into().expect(...)` on integer conversions (which will also panic but on integer overflow only, not attacker-supplied variable-length byte data).

### Impact Explanation
If this conversion executes in a process that handles untrusted, externally-submitted BEEFY consensus proofs (relayer/prover/consensus-update pipeline), a malformed `Vote.signature` of any length ≠ 65 bytes crashes the executing thread/process via panic. In a relayer, prover, or verifier binary that processes proofs from potentially multiple relayers/chains, this is a denial-of-service vector: a single malformed BEEFY proof can be crafted by anyone (no privileged role required, since consensus-update messages are typically dispatched by any unsigned/permissionless relayer submission) to crash the process responsible for advancing consensus state, halting message delivery on that route until the operator restarts the affected component — directly matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
`Vote`/`SignedCommitment`/`BeefyConsensusProof` are ABI types decoded from bytes supplied in a consensus proof, which per the wider system design is submitted by any relayer as part of a permissionless "update consensus" call (see `ihandler.mdx`: "Access: Permissionless (can be called by anyone)" for the consensus verification entrypoint). Triggering the crash requires only constructing a `Vote` whose `signature` field is not exactly 65 bytes and feeding it through this conversion — a low-cost, easily reproducible operation for any party able to submit or relay a proof.

### Recommendation
Replace the unchecked `copy_from_slice` with a length-checked conversion (e.g. `TryFrom<&[u8]>` returning a `Result`/`Option`, mirroring the fix already applied to `as_utf8_string` in `modules/utils/serde/src/lib.rs`), and propagate a decode error instead of panicking when `value.signature.len() != 65`. Apply the same audit to any other `copy_from_slice`/`try_into().expect(...)` conversions in `evm/rust/src/conversions.rs` that operate on externally-supplied variable-length byte fields (as opposed to fixed integer widths) to ensure malformed proof/consensus data is rejected gracefully rather than causing a panic.

### Proof of Concept
1. Construct a `BeefyConsensusProof`/`SignedCommitment` ABI payload where one `Vote.signature` is any byte length other than 65 (e.g. 64 or 66 bytes) — a shape trivially producible by any relayer/attacker who controls the raw proof bytes submitted to the permissionless consensus-update entrypoint.
2. Submit the malformed proof through the normal consensus-update path that triggers `From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs`.
3. `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, aborting the executing thread/process (relayer/prover/verifier) instead of returning a decode error — a denial of service directly analogous to CVE-2017-12837's out-of-bounds write triggered by malformed input during parsing.
