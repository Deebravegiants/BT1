### Title
Unchecked ERC20 return value in Tron `IntentGatewayV2.withdraw`/`onAccept` (SweepDust) permanently traps escrowed user/solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves escrowed intent tokens using a raw low-level `.call()` to the ERC20 `transfer` selector and only checks that the *call itself* did not revert, never decoding the boolean return value of `transfer`. Any ERC20 that returns `false` on failure instead of reverting (the exact class of non-compliant token flagged in the referenced Talos `collectProtocolFees` report) will cause the internal accounting (`_orders[...]`, `_filled[...]`) to be updated as if the transfer succeeded, while the tokens never leave the contract, permanently freezing user/solver funds.

### Finding Description
`withdraw()` is the internal function that releases escrowed order funds to a beneficiary (used for both `RedeemEscrow` fills and `RefundEscrow` cancellations) and for the transaction-fee payout: [1](#0-0) 

For every ERC20 token in the order, it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and then unconditionally does `_orders[body.commitment][token] -= amount;`. The same unchecked pattern is used for the fee payout a few lines below, and again in the `SweepDust` handler inside `onAccept`: [2](#0-1) 

`success` here only reflects whether the external call reverted — it does not decode/verify the ABI-encoded `bool` that `transfer()` returns. Non-standard ERC20 tokens (a known and common class, e.g. tokens with blacklist/pausable logic, or any token that simply returns `false` instead of reverting on failure) will make the low-level call succeed (`success == true`) even though no tokens were moved. Because the check only guards against `success == false`, such tokens sail through unnoticed.

This is functionally identical to the referenced Maia/Talos `collectProtocolFees` finding, where `token.transfer()`'s return value was ignored, except here the impact is broader since `withdraw` is reachable by an unprivileged actor's cross-chain message flow:
- `onAccept` (called by the `EvmHost`/dispatcher on any relayer-delivered `RedeemEscrow`/`RefundEscrow` POST request) calls `withdraw`.
- `onGetResponse` (delivered by any relayer proving the destination `_filled` slot is empty) calls `withdraw` for the cancel-from-source flow.
- `cancelOrder`'s same-chain branch calls `withdraw` directly for the order owner.

Once `withdraw` runs, `_filled[commitment]` is set and `_orders[commitment][token]` is decremented/zeroed regardless of whether the token transfer actually succeeded, so the order can never be retried, and the tokens sit forever in the `IntentGatewayV2` contract balance with no accounting path left to recover them.

Notably, the primary EVM `IntentsBase.sol`/`IntentGatewayV2.sol` implementation already fixed this exact issue by using OpenZeppelin's `safeTransfer`: [3](#0-2) 

but the Tron fork at `evm/tron/contracts/apps/IntentGatewayV2.sol` still uses the unchecked low-level `.call()` pattern, meaning the same bug class was reintroduced/never ported to this deployment target.

### Impact Explanation
Escrowed user input tokens or solver-owed output tokens (and protocol/relayer fee tokens) can become permanently and irretrievably locked in the `IntentGatewayV2` contract on Tron if any escrowed asset is a non-reverting-on-failure ERC20. The internal state (`_filled`, `_orders`) is finalized as though the payout succeeded, so there is no retry mechanism and no owner-level sweep for these funds (the `SweepDust` path suffers the identical unchecked-transfer bug, so it cannot reliably recover them either). This is a direct, permanent freezing/loss of user and solver funds in the intents escrow — a core money-movement path of the bridge.

### Likelihood Explanation
Likelihood is realistic: token pausability/blacklisting or transfer-restriction logic exists in numerous widely used tokens, and any cross-chain intent involving such a token as an input/output asset on the Tron deployment would trigger the silent failure the moment the beneficiary is on a token's deny-list or the token otherwise chooses to return `false`. No malicious privileged actor is required — any relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow` request, or a user cancelling same-chain, exercises this code path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and in the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both call-level reverts and false-boolean returns cause the entire transaction (and its accounting updates) to revert, preventing accounting from advancing past a failed transfer.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` returns `false` instead of reverting when the recipient is blacklisted (or under any failure condition), and register it as an order input token.
2. A user calls `placeOrder` escrowing this token via `IERC20(token).safeTransferFrom(...)` — this succeeds normally since `placeOrder`'s escrow path already uses `safeTransferFrom`.
3. A relayer delivers a `RedeemEscrow` (or `RefundEscrow`) POST request that reaches `onAccept` → `withdraw(body, ...)` in `evm/tron/contracts/apps/IntentGatewayV2.sol:691-723`, targeting a beneficiary that the token's `transfer()` will silently fail for (returns `false`).
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself doesn't revert) even though the internal `transfer` logic returned `false` and moved no tokens.
5. `_orders[commitment][token] -= amount` executes, `_filled[commitment] = beneficiary` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the order is now considered fully settled.
6. The tokens remain in the `IntentGatewayV2` contract's balance with no order record pointing to them and no owner-level withdrawal function that checks/recovers this residual balance, permanently freezing the funds.
