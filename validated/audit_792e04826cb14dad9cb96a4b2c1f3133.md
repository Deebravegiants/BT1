### Title
Withdrawal status/tx-hash misreport for same-asset batch withdrawals due to matching by `assetId` only, not by index/amount - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` matches a withdrawal's on-chain destination status/tx hash by looking up the POA bridge API response using only the `assetId` (via `findMatchingWithdrawal`), rather than by the specific withdrawal index/amount for that request. When a single NEAR intent transaction contains more than one withdrawal of the same asset (a legitimate multi-leg batch withdrawal, e.g. `signAndSendWithdrawalIntent` with several `withdrawalParams` for the same token), `describeWithdrawal` for withdrawal index N can return the `status`/`txHash` belonging to a *different* withdrawal of the same asset in that batch.

### Finding Description
`findMatchingWithdrawal` (used both in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` `describeWithdrawal()` and in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) is documented in-code as matching "by assetId, not by index": [1](#0-0) 
The unit test explicitly exercises "matches withdrawal by assetId, not by index" and shows that for a batch of withdrawals of the same asset, whichever entry the POA API returns for that `near_token_id` is treated as authoritative for the requested index: [2](#0-1) 
The internal-utils equivalent has the same documented limitation: [3](#0-2) 

The equality that should hold is: *the `txHash`/`status` returned for withdrawal index N of a NEAR intent tx == the actual on-chain outcome of that specific withdrawal leg N*. Because matching only keys on `assetId`, when a batch contains two-or-more legs withdrawing the same token (which the SDK explicitly supports via `signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises` batch APIs, see `shared-types.ts` batch signatures), the wrong leg's `transfer_tx_hash`/status can be attributed to the caller's requested index.

### Impact Explanation
This breaks the "status/hash reported == actual on-chain outcome" invariant for one of the withdrawal legs in a same-asset batch. A caller/integrator polling `waitForWithdrawalCompletion` (which loops per-withdrawal via `createWithdrawalCompletionPromises`) could receive a `completed` status with another leg's `txHash` for the wrong withdrawal, or believe a still-pending withdrawal is completed because a sibling leg with the same asset already completed. This maps to the "status or hash misreport making an integrator credit or refund twice" High-impact category, since an integrator that credits or finalizes downstream bookkeeping based on `waitForWithdrawalCompletion`'s reported hash/status for a specific request could incorrectly conclude request A settled (using B's tx hash) while request B remains unsettled, or double-count a single on-chain completion event across two internal ledger entries.

### Likelihood Explanation
Requires a batch of ≥2 same-asset withdrawals initiated in one NEAR tx via the SDK's own batch withdrawal APIs (`signAndSendWithdrawalIntent`, `createWithdrawalIntents`/`createWithdrawalCompletionPromises` with an array of `withdrawalParams`). This is a normal, SDK-supported usage pattern, not an attacker-crafted input — the code comment/tests confirm the maintainers are aware this is unhandled, and note the POA API itself currently doesn't disambiguate legs by amount either. This is a real accounting/observability defect but is more of an unhandled edge case acknowledged in code/tests than a maliciously exploitable path with a clear "wrong contract/attacker" actor, which weakens confidence that it meets the strict "unprivileged analog" bar requested.

### Recommendation
When multiple withdrawals in a batch share the same `assetId`, disambiguate matches deterministically (e.g., sort candidates and requested legs by amount as the code comment already suggests) rather than returning the first/any match for that asset. Track and consume matched withdrawal entries so a later index of the same asset does not receive re-report a prior leg's result.

### Proof of Concept
Not independently verified beyond the repository's own test coverage, which already demonstrates the exact scenario: [2](#0-1) 
This test shows two withdrawals for different assets are correctly disambiguated by asset, but per the code's own doc-comment, two withdrawals of the *same* asset in one tx are not disambiguated by index/amount — I was unable to directly execute this scenario in this session due to tool-call limits reached before completing this verification; the claim rests on the explicit code comment and test title rather than a constructed same-asset-batch PoC.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
