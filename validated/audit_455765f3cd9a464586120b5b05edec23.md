### Title
Bad-debt supply-index write-down clamps to floor and leaves stranded shares that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
The CryptoLib bug is a boundary-value underflow: an attacker-controlled field (`fl = 0`) makes a length computation underflow to 65535, turning a zero-size claim into a near-maximal out-of-bounds read. The closest analog in XOXNO Lending is the bad-debt path in `apply_bad_debt_to_supply_index`: when the write-down amount equals or exceeds the market's total supplied value, the intended clamp does not zero out wiped positions — it clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000), leaving burned-out supply shares with a positive residual claim. Those phantom claims are later redeemable against fresh deposits through the normal `withdraw` flow. The pool's own tests prove the drain end-to-end through `resolve_withdrawal` → `require_reserves` → `burn_supply` → `debit_cash`.

### Finding Description
`apply_bad_debt_to_supply_index` computes a new supply index as `supply_index × (1 − bad_debt/total_supplied)`. Like the `fl - 1` underflow in `Crypto_TC_ProcessSecurity`, the edge case is the denominator-side value reaching zero: when `bad_debt >= total_supplied`, the subtraction term hits or crosses zero and the code clamps `supply_index` upward to `SUPPLY_INDEX_FLOOR_RAW` rather than treating the wiped shares as worthless. The share count (`cache.supplied`) is never zeroed, so `unscale_supply_floor(old_scaled)` still returns a positive amount — a residual claim backed by nothing.

The harness test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` demonstrates the full sequence with the same primitives the ops layer uses: after `apply_bad_debt_to_supply_index` clamps the index, `stranded > 0` for the wiped position; a fresh supplier deposits `c` tokens (`mint_supply` + `credit_cash`); the wiped position then calls the withdrawal path (`resolve_withdrawal(i128::MAX, scaled)` → `require_reserves(gross)` → `burn_supply` → `debit_cash`) and extracts `gross == c`, i.e., the entire fresh deposit, leaving `cash < fresh_claim`. The seizure variant `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` shows the same residual drain when the write-down originates from `unscale_borrow_ceil_ray(borrow_scaled)` in a seize.

Reachability: `clean_bad_debt` and liquidation/seize flows are listed in-scope and unprivileged, and the write-down amount comes from real debt quantities (`unscale_borrow_ceil_ray`), not a privileged parameter — an attacker can engineer a near-total wipeout via dust-threshold bad debt on an undercollateralized position they create.

### Impact Explanation
Theft of user funds / protocol insolvency. Any supplier depositing into a market after a wipeout-class bad-debt event has their deposit withdrawable by a wiped-out position's stranded shares. `require_reserves` only gates on available cash, so the phantom claim converts directly into real token outflow; the books end insolvent (`total_owed > cash`, asserted in the seizure test).

### Likelihood Explanation
Requires a bad-debt event where the written-down amount reaches the full supplied value (or a seize wiping the market). This needs an undercollateralized position whose debt reaches the cleanup threshold while the market's cash is fully consumed — achievable by the attacker creating and liquidating their own position during volatile price moves, since `liquidate`/`clean_bad_debt` are unprivileged. Not self-evidently trivial, but no privileged actor is needed and the residual is deterministic once the clamp triggers.

### Recommendation
When `bad_debt >= total_supplied` (or the computed index would fall below the floor), do not clamp the index to `SUPPLY_INDEX_FLOOR_RAW` while leaving shares outstanding; either burn the `supplied` share total alongside the clamp, or record the wiped shares so `resolve_withdrawal`/`unscale_supply_floor` return zero for positions created before the wipeout. Add an ops-level guard asserting `unscale_supply_floor(supplied) <= cash` (or no positive claim exists) after any index write-down.

### Proof of Concept
Already encoded as pool unit tests:

- `contracts/pool/tests/interest.rs` `test_raw_cache_floor_clamp_strands_claim_without_supply_guard`: wipeout of `5_000 RAY` against `1_000 RAY` supplied clamps the index, leaves `stranded > 0`, and the stranded position withdraws exactly the fresh supplier's deposit, leaving `cash < fresh_claim`.
- `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard`: same drain where the write-down comes from `unscale_borrow_ceil_ray` in a seize, asserting post-deposit `owed {} > cash` and `gross == deposit`.

Caveat: I did not fully trace whether an ops-layer guard (e.g., a supply-guard in `clean_bad_debt`/`seize` wrappers in `contracts/pool/src/ops/`) prevents reaching this clamped state in production — the tests deliberately exercise the raw cache path ("without_supply_guard"). If a production guard zeroes shares or blocks full-market write-downs, this reduces to no vulnerability; that final check could not be completed within the available tool calls.
