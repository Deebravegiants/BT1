### Title
Accrual path panics on an expected arithmetic overflow before the index cap engages, permanently freezing every position in the market - ([File: common/src/rates/index.rs])

### Summary
Like the Linux `page_pool` bug, this is a datapath that hits an expected resource-limit condition without the defensive handling the layer above it is supposed to provide. In the kernel, drivers forgot `GFP_NOWARN` so routine Rx allocation failures produced OOM splats; here, the accrual engine forgets that `supplied * supply_index` can legitimately overflow `i128` long before `MAX_SUPPLY_INDEX_RAY` is reached, so an expected saturation condition is converted into a hard `MathOverflow` panic in `update_supply_index` / `scaled_to_original`. Because `global_sync` runs at the head of every pool verb, once the market crosses this ray-value ceiling the panic is unconditional and permanent.

### Finding Description
`accrue_step` computes `supplied_original = scaled_to_original(supplied, supply_index)` and `update_supply_index` computes `total_supplied_value = supplied.mul(old_index)`, both via `Ray::mul`, which panics with `MathOverflow` on `i128` overflow (`common/src/rates/scaling.rs:14`, `common/src/rates/index.rs:34`, `common/src/rates/simulate.rs:60-71`). The design already acknowledges the ceiling: `MAX_SUPPLY_INDEX_RAY`/`MAX_BORROW_INDEX_RAY` clamp the indexes, and `calculate_scaled_cap` deliberately saturates instead of panicking. But the multiply that produces the *value* used for the clamp has no such guard — it multiplies before it can clamp.

The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` demonstrates the exact failure: a market holding ~10^27 units of an 18-decimal asset at 98% utilization on a steep curve overflows inside accrual while `borrow_index < MAX_BORROW_INDEX_RAY`, and afterwards `try_withdraw_raw`, `try_repay`, and `update_indexes` all revert with `MATH_OVERFLOW`.

### Impact Explanation
Permanent freezing of funds. Every state-changing controller/pool entrypoint (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, flash paths) calls `global_sync` first, so once `supplied * supply_index` exceeds `i128`, no supplier can withdraw, no borrower can repay, and no liquidator can touch the market — ever. Suppliers' entire principal in that market is bricked. This is the strict analog of the kernel bug: an expected limit condition (OOM there, fixed-point saturation here) that should be absorbed by the subsystem instead propagates as an unhandled failure to every caller.

### Likelihood Explanation
Reachable by unprivileged addresses through ordinary `supply`/`borrow` calls plus time; it requires whale-scale liquidity (billions of whole 18-decimal tokens) and sustained high utilization over years, and requires the market's supply cap to permit the position size — but caps are settable up to `max_cap_for_decimals` and the harness reproduces it with contract-legal inputs. The condition is a one-way ratchet: once crossed it cannot be undone, since the overflow happens inside accrual before any corrective action is possible. Medium-High likelihood within the report's threat model; impact is the maximum (permanent freeze of all market funds).

### Recommendation
Handle the saturation gracefully in the same layer that already defines the index caps, mirroring the kernel fix of pushing the defensive flag down into the shared allocator:

- In `update_supply_index`, replace `supplied.mul(env, old_index)` with a saturating mul (e.g. `mul_div_floor_saturating`-based): when `supplied * old_index` would overflow, the rewards-increase fraction is negligible anyway, so returning `old_index` (or clamping to `MAX_SUPPLY_INDEX_RAY`) is the correct degenerate behavior.
- In `accrue_step`/`scaled_to_original`, saturate `borrowed_original`/`supplied_original` at a domain bound rather than panicking; utilization at saturating supply is ~0 anyway, so the step is a near-no-op.
- Alternatively, enforce the index ceiling *before* the value multiplication so `MAX_SUPPLY_INDEX_RAY` actually engages before the ray-value cliff, as `update_borrow_index` intends but currently does after the overflowing multiply.

### Proof of Concept
Encoded in the repo's own harness: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`.

1. Market "BIG18" (18 decimals, price $1, XLM stress curve with `max_borrow_rate = 175%`, `optimal_utilization = 75%`) with caps lifted via `max_cap_for_decimals`.
2. BOB `supply("BIG18", 1e9 * 10^18)`; ALICE supplies "COL" collateral and `borrow("BIG18", ~98% of supplied)` — all unprivileged calls.
3. Advance time in one-year steps, calling `update_indexes` each year. Within ~40 years at sustained high utilization, `global_sync → accrue_chunk → accrue_step → scaled_to_original` panics with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.
4. Thereafter `withdraw`, `repay`, and `liquidate` all revert identically — the market and all supplied funds are permanently frozen.
