### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the `shop-domain` header — which is what identifies *which merchant* the webhook event belongs to — is never included in the signed content. An attacker who can obtain one validly-signed webhook payload (e.g. by installing the app on their own shop and triggering an event) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header, and the gem will accept it as authentic and hand it to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`Registry.process` performs exactly one authenticity check: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature strictly over `to_signable_string`, which for `Webhooks::Request` is defined as the raw request body only: [2](#0-1) 

The `shop` accessor used to build the `WebhookMetadata` passed to the app's handler is read from the `shop-domain` header, which is parsed from unauthenticated headers and is never part of the signed string: [3](#0-2) [4](#0-3) 

and it is exactly this unauthenticated value that is trusted as the tenant identity for the event: [5](#0-4) 

This is the same bug class as the reported analog: the "signature" (HMAC) does not bind to the identity field (`shop`) that downstream logic treats as authoritative, so a valid signature obtained in one context (the attacker's own shop) can be replayed with a forged identity value (a victim shop) without invalidating the signature. The documentation for this gem explicitly claims `process` "will verify the request did indeed come from Shopify," which is only true for the body bytes, not for the claimed shop: [6](#0-5) 

Formally, the binding that should hold but doesn't:
`hmac_valid(raw_body, secret) == true` should imply `shop_header == shop_that_actually_produced(raw_body)`; instead `hmac_valid` only proves `raw_body` integrity under the shared app secret and says nothing about `shop_header`, since `shop_header ∉ to_signable_string`.

### Impact Explanation
An attacker who legitimately installs the target app on a shop they control (an "unprivileged internet user" relative to any other merchant) can capture a genuinely-signed webhook body/HMAC pair from their own store, then replay it against the app's webhook endpoint with the `shop-domain` header changed to any victim `myshopify.com` domain. `ShopifyAPI::Webhooks::Registry.process` will treat this as an authentic, verified event for the victim shop and invoke the app's handler with `WebhookMetadata.shop` set to the victim — this is a cross-tenant identity/data-integrity compromise (e.g., forging `app/uninstalled`, `orders/create`, or other tenant-scoped events for a shop the attacker never controls), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to install the app on any shop (including a free development store) to obtain one legitimately signed body, plus the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — no access to `api_secret_key`, access tokens, or the target merchant's credentials is needed. This is straightforward for any developer who can install the target app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or cross-check the `shop-domain` header against a shop identifier embedded in the verified body/session before trusting it, rather than relying on an unauthenticated header for tenant identity — analogous to appending a fixed context string to the signed payload as recommended in the reported bug's remediation.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify over `B` with the app's real secret).
2. Replay the exact same request to the app's webhook endpoint, but replace the header `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com` (and set the appropriate `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate` succeeds because it only re-computes the HMAC over `B`, seen in: [7](#0-6) 
4. `Registry.process` passes validation and dispatches to the handler with `shop: "victim.myshopify.com"`, as shown at: [1](#0-0) 
5. The host application processes attacker-controlled data as if it originated from `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
