### Title
Unchecked ERC20 `transfer` return value in Tron IntentGatewayV2 escrow release/sweep allows fake successful settlement and fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed tokens using a raw low-level `.call` to the ERC20 `transfer` selector and only checks that the *call itself* did not revert (`success`). It never decodes/validates the boolean return value that ERC20 `transfer` is expected to produce. Any token that returns `false` on failure instead of reverting (a well-known non-standard-but-common ERC20 behavior, the same class of behavior flagged in the referenced Nibiru finding) will cause the gateway to treat a failed transfer as successful, permanently debiting the internal escrow accounting without the beneficiary ever receiving funds.

### Finding Description
`withdraw()`, the handler for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow` messages delivered through `onAccept`, and the `SweepDust` branch of the same `onAccept` dispatcher, both settle ERC20 payouts like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

and identically in the `SweepDust` and fee-forwarding branches: [2](#0-1) [3](#0-2) 

`success` here only reflects whether the external call reverted, not whether the transfer actually succeeded. A token contract that returns `abi.encode(false)` on failure (rather than reverting) — this is explicitly the class of non-compliant ERC20 behavior called out in the referenced report — will make `token.call(...)` return `success = true` even though no tokens moved. The code then proceeds to decrement `_orders[body.commitment][token] -= amount` and emit `EscrowReleased`/`DustSwept`, permanently marking the escrow as paid out while the beneficiary received nothing.

This is inconsistent with the rest of the codebase: the file imports and declares `using SafeERC20 for IERC20;` (`evm/tron/contracts/apps/IntentGatewayV2.sol:39,56`) and the canonical EVM version of the same contract (`evm/src/apps/intentsv2/IntentsBase.sol:_withdraw`) correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`, which reverts on both an explicit `false` return and non-standard no-return tokens. [4](#0-3)  The Tron file diverges from this safe pattern for no functional reason evident in the code.

### Impact Explanation
`withdraw()` is reached from the `RedeemEscrow`/`RefundEscrow` message path, which is delivered by any relayer submitting a valid cross-chain ISMP POST from an authenticated peer `IntentGatewayV2` instance, and `SweepDust`/fee-forwarding is dispatched by Hyperbridge governance messages. In both cases, a token whose `transfer` returns `false` instead of reverting on failure (e.g., due to a paused state, blacklist, insufficient balance edge case, or any custom-logic ERC20 that signals failure via return value) will cause escrowed user or protocol funds to be marked as released/settled without ever leaving the contract. This is a permanent loss/freezing of funds: the escrow slot is decremented (or fully finalized via `_filled[...] = beneficiary`), so the legitimate beneficiary cannot re-claim the tokens even though they were never transferred, while the tokens remain stuck in the gateway contract with no accounting pointing to them.

### Likelihood Explanation
This requires a token used in an intent order (or the fee token) to exhibit the "return `false` instead of revert" non-compliant behavior. This is a common real-world ERC20 pattern (widely discussed in the `weird-erc20` list referenced by the source report) and is entirely plausible for arbitrary tokens users choose to bridge/trade through the intents system — the gateway does not restrict which ERC20s can be used as `TokenInfo.token`. Because the flawed code path is the only path used for every payout (successful fills, refunds, dust sweeps, fee payouts) on the Tron deployment, any single occurrence silently and irreversibly loses funds.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and aliased with `using SafeERC20 for IERC20;`) instead of raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and the `SweepDust`/fee-forwarding branches, matching the pattern already used in `IntentsBase.sol`. `safeTransfer` correctly handles both no-return-value tokens (treats no revert + no data as success) and tokens that explicitly return `false` (reverts), closing the discrepancy between the Tron and canonical EVM implementations.

### Proof of Concept
1. Register a peer `IntentGatewayV2` on another chain, and use (or have a user place an order in) an ERC20 token whose `transfer()` returns `false` on failure rather than reverting (e.g., simulate insufficient allowance/paused state that the token handles internally by returning `false`).
2. A relayer submits a valid `RedeemEscrow` ISMP POST for that order/commitment; `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`.
3. The call succeeds (`success == true`) because the token contract does not revert, but the beneficiary's balance is unchanged.
4. `_orders[body.commitment][token] -= amount` and `_filled[body.commitment] = beneficiary` still execute, and `EscrowReleased` is emitted — the escrowed tokens are now permanently unaccounted for and unrecoverable by the beneficiary, despite never having moved.
