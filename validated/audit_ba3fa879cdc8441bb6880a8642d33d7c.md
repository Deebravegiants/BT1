## Title
Webhook `shop` (and `topic`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `Registry.process` trusts `request.shop` (and `request.topic`) — both parsed from unauthenticated HTTP headers — to build the `WebhookMetadata` handed to the app's handler. The HMAC only binds the *body bytes*, not the shop-domain header that identifies which tenant the webhook belongs to.

## Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop`/`request.topic` to construct the metadata dispatched to the app handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., just the body) against the app's single, shared `api_secret_key`: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, body ++ shop ++ topic)`. What actually holds is: `hmac == HMAC(secret, body)`, with `shop`/`topic` parsed independently and never covered by the signature — this is exactly the "field acted on but not covered by the HMAC" class of bug from the report analog (SCR searched/attributed to a shard without the correlating identity being enforced).

Because `api_secret_key` is the same for every shop that installs the app (it is not merchant-specific), any merchant who has legitimately installed the app can capture a real `(body, x-shopify-hmac-sha256)` pair delivered to their own webhook endpoint for their own shop, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header value with a different shop's domain that also uses the same app. `HmacValidator.validate` will still succeed because it never inspects the shop/topic headers, and `Registry.process` will hand the attacker-controlled `shop` value to the app's handler as if it were authentic: [5](#0-4) 

The documented handler contract explicitly tells app authors `data.shop` is "The shop domain of the webhook" without any caveat that it is unauthenticated — so any host application relying on the gem's own guarantee that `Registry.process` "will verify the request did indeed come from Shopify" (per `docs/usage/webhooks.md` line 125) reasonably treats `data.shop` as authenticated, when in fact only the body bytes are verified.

## Impact Explanation
This crosses a tenant boundary: an app that keys business logic (e.g., data storage, entitlement checks, per-shop side effects) off `WebhookMetadata#shop` can be tricked into attributing/processing a legitimately-signed payload under a different shop's identity, without possessing that shop's access token or any privileged credential. This matches the Critical bucket "cross-tenant access" since the shop-scoping guarantee the gem purports to provide (`Registry.process` "will verify the request did indeed come from Shopify") is broken for the identity field, not just the payload.

## Likelihood Explanation
Requires only that the attacker (or any of the app's other legitimate merchant users) has app-installed access to receive one real webhook for their own shop — no secret key, access token, or privileged access needed, and any shop using a multi-tenant app satisfies this. The webhook endpoint is by design a public HTTP endpoint, so replay with a modified header is trivial once a valid (body, hmac) pair is obtained.

## Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body before `Registry.process` uses them to build `WebhookMetadata`. At minimum, document prominently that `data.shop`/`data.topic` are not covered by the Shopify webhook HMAC and must be independently cross-checked (e.g., against shops that have valid, stored offline sessions) before being trusted for tenant-scoped decisions.

## Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and legitimately receives a real webhook, capturing `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>` (signed with the app's shared `client_secret`).
2. Attacker (or any user who can reach the app's public webhook endpoint) sends a request with the identical `raw_body` and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a different shop that also installed the app).
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (forged) header.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared secret — see `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` to the app's handler, which processes the payload as if it belonged to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
