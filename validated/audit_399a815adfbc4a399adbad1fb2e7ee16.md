### Title
Unsigned calldata dispatch trusts a padded, non-canonical EVM→Substrate account mapping as origin - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in `hyper-fungible-token` decodes untrusted, attacker-supplied cross-chain message bytes into a `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` and, when no signature is present, dispatches the embedded `T::RuntimeCall` with `RawOrigin::Signed(origin)` where `origin` is derived purely from the message's `from` field via a **zero-padding** conversion (`EvmToSubstrate::convert`), not from any cryptographic proof of control. [1](#0-0) [2](#0-1) 

### Finding Description
The pallet accepts an ABI-decoded `Message { from, to, amount, data }` from a registered source contract, and if `message.data` is non-empty, SCALE-decodes it into `SubstrateCalldata`: [3](#0-2) 

If `substrate_data.signature` is `None`, the dispatch origin is computed by taking the raw `message.from` bytes and mapping them to a 32-byte `AccountId` using `T::EvmToSubstrate::convert`, whose default implementation is a naive **left-zero-pad**: `account[12..].copy_from_slice(&addr.0)`. [4](#0-3) [5](#0-4) 

The decoded `runtime_call` is then dispatched as that derived, *signed* origin without any signature or proof-of-key check: [6](#0-5) 

This zero-padding scheme is **not collision-free with genuine 32-byte substrate AccountIds**. Any 32-byte AccountId that happens to have its first 12 bytes equal to zero is indistinguishable from — and reachable by — an EVM-address-derived origin. Concretely:
- Pallet/well-known/derived AccountIds (e.g. sovereign accounts, pallet accounts such as `Pallet::<T>::pallet_account()`, or any AccountId generated by `frame_support`'s `PalletId::into_account_truncating()`/`derivative_account_id` schemes) are frequently constructed by hashing or truncating a seed into 32 bytes, and it is well known that such derivations do not guarantee non-zero leading bytes. If any account of interest (custody/pallet accounts, sovereign accounts, or accounts with a "vanity" collision that a relayer/user could brute-force by scanning `H160` addresses) has 12 leading zero bytes, an attacker can set `message.from` to the corresponding 20-byte suffix and impersonate that account with zero cryptographic proof — merely by triggering a cross-chain `PostRequest` from the registered source contract with `from = accountId[12..32]`.
- Even absent a specific pallet-account collision, this is a structural authentication bypass: the security model silently assumes "unsigned calldata is safe because it can only act as the message's declared EVM sender," but the sender-to-AccountId mapping is a lossy, many-to-one truncation (all substrate AccountIds sharing the same last 20 bytes collapse to the same derived origin), meaning **any 32-byte substrate account whose low 20 bytes match an attacker-chosen value can be impersonated** for unsigned-calldata dispatch, not just accounts that were legitimately bridged from that same EVM address.

This mirrors the CWE-502 bug class from the reference advisory: untrusted bytes (an unauthenticated wire message) are deserialized directly into a structure (`SubstrateCalldata`/`RuntimeCall`) that is then used to perform a privileged, security-relevant operation (dispatch as a `Signed` origin) — the "poisoned" data is not validated against any secret/signature before being trusted as an identity/authorization proof.

### Impact Explanation
If a genuine on-chain account (pallet custody account, treasury/sovereign account, or any account whose AccountId happens to have 12 leading zero bytes) is reachable this way, an attacker can dispatch **arbitrary runtime calls** (subject only to `BaseCallFilter`) as that account's signed origin — e.g., transferring away escrowed pallet funds, transferring assets out of a sovereign/treasury account, or performing any other privileged extrinsic that account is authorized to call. This is unauthorized app action / potential theft of funds, reachable from a single relayed cross-chain message that any holder of a registered source contract's minting/burning path can trigger (an unprivileged token bridger).

### Likelihood Explanation
The precondition (a real AccountId with 12 leading zero bytes matching an attacker-controllable 20-byte value) is not something I can fully confirm from the indexed code alone — it depends on how specific runtime AccountIds are derived in the deployed runtime(s) using this pallet. Given the widespread convention of `PalletId::into_account_truncating` and similar padding/truncation schemes across Substrate runtimes, and that this pallet ships a **default** `EvmToSubstrate` implementation that itself uses zero-padding (i.e., the pallet's own convention for legitimate EVM-derived accounts already produces 12-leading-zero-byte AccountIds), the risk is structural rather than hypothetical: any account created by this pallet's own default conversion, or by any other zero-padding/truncation scheme in the runtime, is trivially impersonable via unsigned calldata.

### Recommendation
Do not allow `RawOrigin::Signed` dispatch without a verified signature. Options:
1. Require `substrate_data.signature` to always be present for `runtime_call` execution; reject `None`.
2. If an "implicit" origin is desired, derive it from a domain-separated, non-collidable hash (e.g. `blake2_256(b"hft-evm-origin" ++ source_chain_id ++ from_bytes)`) instead of naive zero-padding, so it can never coincide with a "real" substrate AccountId.
3. At minimum, restrict the unsigned-origin dispatch path so that the resulting origin's call surface excludes privileged/asset-moving calls (tighten `BaseCallFilter` specifically for this path), and audit all in-runtime accounts for 12-leading-zero-byte collisions before enabling this pallet.

### Proof of Concept
1. Attacker identifies (or the runtime's own tooling reveals) a privileged AccountId `A` (32 bytes) whose first 12 bytes are `0x00...00` — this is guaranteed for the pallet's own EVM-bridged accounts by construction (`EvmToSubstrate::convert` default impl), and plausible for other pallet/sovereign accounts derived via truncation.
2. Attacker computes `evm_addr = A[12..32]` (the last 20 bytes of `A`).
3. Attacker (as any user permitted to call the registered source-chain `HyperFungibleToken` contract's `send`) crafts a cross-chain `PostRequest` whose ABI-encoded `Message.from = evm_addr` and `Message.data = SCALE-encode(SubstrateCalldata { signature: None, runtime_call: <arbitrary call, e.g. Balances::transfer_allow_death from A to attacker> })`.
4. Relayer delivers the message; `pallet_ismp`'s `handle_unsigned` invokes `HyperFungibleToken::on_accept`, which decodes `SubstrateCalldata`, takes the `else` branch (no signature), computes `origin = EvmToSubstrate::convert(evm_addr) == A`, and dispatches `runtime_call` as `RawOrigin::Signed(A)` — moving `A`'s funds to the attacker with no signature ever checked. [7](#0-6) 

Note: full confirmation that a specific privileged AccountId with 12 leading zero bytes exists in a given deployed runtime requires runtime-specific inspection beyond what the indexed snippets show; I flag this as the key uncertainty for a defender to verify.

/// Converts an EVM address to a substrate AccountId
pub trait EvmToSubstrate<T: frame_system::Config> {
	fn convert(addr: H160) -> T::AccountId;
}

/// Default implementation: zero-pads the 20-byte address into a 32-byte AccountId
impl<T: frame_system::Config> EvmToSubstrate<T> for ()
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
		let mut account = [0u8; 32];
		account[12..].copy_from_slice(&addr.0);
		account.into()
	}
}
