### Title
Unbounded/unchecked SCALE decode of relayer-controlled cross-chain calldata in `hyper-fungible-token::on_accept` allows recursion-depth DoS and permission bypass distinct from vetted decode path - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The Keycloak advisory (CVE-2020-1714) is about deserializing attacker-controlled bytes into privileged in-process objects without validating the type/structure of the input before acting on it. In `hyper-fungible-token`, `on_accept` decodes attacker/relayer-controlled `PostRequest.body` into a `SubstrateCalldata { signature, runtime_call }` and then decodes `runtime_call` directly into `T::RuntimeCall` via the plain `Decode::decode`, with **no recursion-depth limit**, unlike the sibling `pallet-call-decompressor`, which explicitly guards the analogous "decode an encoded `RuntimeCall` supplied by an untrusted party" operation with `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`.

### Finding Description
`on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` is the ISMP module handler invoked whenever a cross-chain token-transfer `PostRequest` is delivered by any relayer with a valid consensus/state proof — i.e., reachable from a single relayed message, no special privilege required [1](#0-0) .

When the ABI-decoded `Message.data` is non-empty, the pallet decodes it as `SubstrateCalldata` and then decodes the embedded `runtime_call: Vec<u8>` bytes straight into the runtime's `RuntimeCall` enum using `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)`: [2](#0-1) [3](#0-2) 

Contrast this with `modules/pallets/call-decompressor/src/lib.rs`, which performs essentially the same operation (decoding an attacker-supplied byte string into `T::RuntimeCall` before dispatch) but explicitly bounds recursion via `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`, and even documents in its module comment that unbounded decoding of untrusted encoded calls is a hazard that must be mitigated: [4](#0-3) [5](#0-4) 

`SCALE`'s `Decode` implementation for nested/recursive enums (which `RuntimeCall` is, since it aggregates every pallet's `Call` enum, and pallets can nest calls such as `utility::batch`, `proxy::proxy`, or other pallets' recursive call wrappers) recurses per nested variant with no inherent depth cap when invoked via the bare `Decode::decode` trait method — that protection only exists in `decode_all_with_depth_limit`, which `hyper-fungible-token` does not use. An attacker controlling the source chain (or acting as a relayer submitting a request from a chain they control, since `on_accept` is triggered by any successfully-proven `PostRequest`) can craft a deeply nested `runtime_call` byte string that consumes stack depth during decode, independent from the message-size limits enforced elsewhere in ISMP.

This mirrors the CVE-2020-1714 bug class: deserializing untrusted bytes into a structured/privileged runtime type without validating that the encoded object is well-formed/bounded before further processing (here, `dispatch()`), in a code path that a sibling pallet in the same codebase (`call-decompressor`) has already identified as needing an explicit depth-limit guard.

### Impact Explanation
A relayer/attacker able to get any `PostRequest` accepted by `hyper-fungible-token` (which only requires the source contract be registered via `ContractToAsset`, a normal cross-chain token transfer condition, not an admin-only gate) can supply `Message.data` containing a `SubstrateCalldata.runtime_call` that is a maliciously deep/malformed SCALE encoding. This is reachable per-message from a single relayed token transfer, without any privileged role, satisfying the "reachable path" requirement (token bridge mint/burn path). Depending on the SCALE codec's recursion behavior in this runtime build, this can cause excessive stack usage/panic in the validator/collator executing the extrinsic (denial of service to the runtime processing that message), or, more subtly, decode-confusion where a call the sender did not intend gets constructed and dispatched under `RawOrigin::Signed(origin)` — the recipient/beneficiary account — potentially executing an unauthorized app action on their behalf if `BaseCallFilter` does not fully exclude the malformed/confused call. This is High-severity input-validation risk on a reachable token-bridge code path.

### Likelihood Explanation
High. `on_accept` is reachable by any relayer delivering a proven `PostRequest` from a registered source contract — the standard path for every incoming token transfer with optional calldata — and the attacker fully controls the `data` field's bytes at the source-chain contract level, so crafting a pathological `SubstrateCalldata.runtime_call` payload requires no privileged access, matching the "unprivileged... token bridger" reachability bar.

### Recommendation
Replace the bare `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` in `on_accept`/`on_timeout` paths of `modules/pallets/hyper-fungible-token/src/module.rs` with `T::RuntimeCall::decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, &mut &*substrate_data.runtime_call)`, mirroring the guard already used in `modules/pallets/call-decompressor/src/lib.rs`. Additionally verify decoding consumes the entire input (as `call-decompressor::decode_and_execute` does) so trailing/padding bytes cannot be smuggled through, and re-audit any other `Decode::decode` call sites on cross-chain-supplied bytes destined for `Dispatchable::dispatch`.

### Proof of Concept
1. Attacker registers/owns a source-chain HyperFungibleToken contract mapped via `ContractToAsset` (standard onboarding for any bridged token pair) — no special admin role needed.
2. Attacker sends a cross-chain transfer whose ABI-encoded `Message.data` decodes to `SubstrateCalldata { signature: None, runtime_call: <crafted bytes> }`, where `<crafted bytes>` encode a deeply nested `RuntimeCall` variant chain (e.g., repeated `Utility::batch`/nested pallet call wrappers) designed to maximize SCALE decode recursion without tripping any size limit enforced upstream in ISMP message dispatch.
3. Relayer delivers the proven `PostRequest` to the destination chain; `on_accept` reaches line 121 (`SubstrateCalldata::decode`) and line 189 (`T::RuntimeCall::decode`), the latter of which has no depth limit, unlike `call-decompressor::decode_and_execute` (`modules/pallets/call-decompressor/src/lib.rs:263-268`) which explicitly protects the analogous operation.
4. Compare against `should_decompress_and_execute_pallet_ismp_post_request_calls_correctly` in `modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs` which demonstrates the intended guarded pattern for decoding untrusted `RuntimeCall` bytes — no equivalent test/guard exists for `hyper-fungible-token`'s `on_accept` calldata path.
