### Title
Webhook shop identity spoofing: HMAC verification covers only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook impersonation - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC check only authenticates the raw request body. The `shop` (and `topic`/`webhook_id`/`api_version`) values that are handed to the app's handler as trusted webhook metadata are read straight from unauthenticated HTTP headers and are never bound to the HMAC-verified bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are parsed from headers that are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC solely over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the unauthenticated `request.shop` (and other header-derived fields) to the app's handler as trusted `WebhookMetadata`: [4](#0-3) 

The identity binding this breaks is: `shop verified-by-HMAC == shop delivered-to-handler`. In reality only `body verified-by-HMAC == body delivered-to-handler` holds; the shop domain is never bound to the signature. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which is materially incomplete and encourages host apps to trust `data.shop` as authenticated, per the documented handler contract and example: [5](#0-4) [6](#0-5) 

Critically, the HMAC secret used for webhook signing (`Context.api_secret_key`) is the app's single global `client_secret`, shared across every shop that installs the app — it is not shop-specific. Any merchant who installs the app on their own store is an "unprivileged internet user" from the perspective of every other tenant, yet they receive genuinely Shopify-signed `(raw_body, hmac)` pairs for their own shop's events.

### Impact Explanation
Because the shop identity is not bound to the HMAC-verified bytes, and the signing secret is shared across all tenants of the app, any merchant who has legitimately installed the app can capture one authentic `(raw_body, hmac-sha256)` pair from their own store's webhook deliveries, then replay that exact body/HMAC to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Any host application following this gem's documented pattern (using `data.shop` to key persistence, authorization or job dispatch — exactly as shown in `docs/usage/webhooks.md`) will process attacker-controlled data (body content genuinely signed for the attacker's own shop) under a victim shop's identity — a cross-tenant data-injection / spoofing primitive.

### Likelihood Explanation
Any user of the app (a legitimate but unprivileged merchant) can obtain valid `(body, hmac)` pairs for their own store simply by installing the app and observing an ordinary webhook delivery (e.g., via a request logger/proxy in their own environment). No secrets, tokens, or privileged access to another tenant are required — only the ability to modify the HTTP headers of the replayed request, which is standard for any internet client.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified payload before handing it to the handler as trusted `WebhookMetadata`. At minimum, update `Utils::VerifiableQuery`/`Registry.process` so `shop` is validated (e.g., checked against a known-installed-shop store, or included in signature verification) rather than trusted purely from an unauthenticated header, and correct the documentation's claim that `process` fully verifies "the request did indeed come from Shopify."

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers an order event on their own store and captures the resulting webhook POST, including `raw_body`, `X-Shopify-Hmac-Sha256`, and other `X-Shopify-*` headers.
3. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (still-valid) HMAC. [7](#0-6) 
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, causing the host application to attribute attacker-controlled data to the victim tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
