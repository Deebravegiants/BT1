### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity that is handed to the app's webhook handler. Because the HMAC signable string never includes the shop domain, an attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's secret can replay it with a forged `shop-domain` header pointing at a different, victim shop, and the gem will accept it as authentic and bind the payload to the wrong tenant.

### Finding Description
The equality this analog breaks is: **shop authenticated (bytes verified by HMAC) vs. shop asserted/used (the `shop-domain` header value passed to the handler)**.

- `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it via `OpenSSL.secure_compare` to the received HMAC. [1](#0-0) 

- For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

- Note that `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers, none of which are part of the signable string — only the raw body is authenticated. [3](#0-2) 

- `Registry.process` validates only this body-based HMAC, then immediately forwards `request.shop` (an unauthenticated header value) to the app handler as the tenant identity, without any independent verification that the shop actually matches the body's origin: [4](#0-3) 

Because the same `api_secret_key` is used for HMAC computation across all shops installed on the app (it is not shop-specific, and is not mixed into the signable string), a valid `(raw_body, hmac)` pair generated for one shop's webhook event remains a valid, HMAC-passing pair regardless of which `shop-domain` header accompanies it. An attacker who can obtain even one legitimate webhook delivery for a shop under their control (e.g., by installing the same public app on their own store and triggering an event) can replay that exact body and HMAC to the app's webhook endpoint while substituting the victim's `x-shopify-shop-domain` header. `HmacValidator.validate` returns `true` (the body+secret pair is genuinely valid), and `Registry.process` proceeds to call the handler with `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)`, where `shop` is now the attacker-chosen, forged victim domain. [5](#0-4) 

Applications built on this gem naturally trust `WebhookMetadata#shop` (or `Request#shop`) as the authenticated tenant key to look up sessions, update shop-scoped state, or key their own data stores — this is the gem's own documented/intended usage of the `shop` accessor exposed by `Request`. Since the gem itself performs no binding between the authenticated bytes (body) and the claimed identity (shop header), the trust boundary this gem is responsible for enforcing (body integrity ⇒ tenant identity) is broken at the library level, not merely by host misuse.

### Impact Explanation
This enables cross-tenant confusion: an attacker who controls a shop with the same app installed can, with a replayed body and a forged shop header, cause the app to process webhook data (or side effects triggered by it) under a different merchant's tenant identity. Depending on how the host stores/keys data by `shop`, this can lead to cross-tenant data association or processing under an incorrect shop record — matching the "cross-tenant access" Critical impact bucket, since the vulnerability is rooted entirely in this gem's `HmacValidator`/`Webhooks::Request`/`Registry` not binding the shop identity to the signed bytes.

### Likelihood Explanation
Medium: the attacker must be able to obtain at least one genuine `(body, hmac)` pair, which is achievable if the vulnerable app is a public app (attacker installs it on their own store to receive a legitimately signed webhook), or if any webhook body is otherwise capturable/replayable (webhooks are delivered over HTTP(S) POST to a public callback URL controlled by the app, and shop domain headers are trivially forged by any client sending requests to that endpoint).

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed material verified against Shopify's canonical webhook signing method, or — since Shopify's real webhook HMAC only ever signs the body — perform a secondary authenticated verification that the shop header corresponds to a shop actually known/installed for this app (e.g., cross-check against a stored, previously authenticated shop record) before trusting `request.shop`/`WebhookMetadata#shop` as a tenant key. At minimum, the gem should document loudly, and ideally enforce, that `shop` from `Webhooks::Request` is unauthenticated header data and must not be used as a sole tenant-binding key without additional verification (such as confirming an active OAuth session/install record exists for that shop before applying webhook effects).

### Proof of Concept
1. Install the public app under attacker's own shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to receive a legitimate `raw_body` and `x-shopify-hmac-sha256` value signed with the app's `api_secret_key`.
2. Replay that exact `raw_body` and `hmac` header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, raw_body)`: [6](#0-5) 
4. `Registry.process` calls the handler with `shop: request.shop` = `"victim.myshopify.com"`, even though the payload never originated from or was signed in association with that shop: [4](#0-3)
