## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant/tenant the webhook belongs to. Because the HMAC signature never covers the `shop` (or `topic`/`api-version`/`webhook-id`) header, any party who can obtain one genuinely-signed webhook body/HMAC pair for a given app can relabel the `shop-domain` header to a different merchant and have the handler process it as if it belonged to that other tenant.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw JSON body: [1](#0-0) 

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header — headers such as `shop`, `topic`, `webhook_id`, and `api_version` never enter the signature computation: [2](#0-1) 

`Registry.process` performs the authentication check, then immediately trusts `request.shop` (the unauthenticated header) to construct `WebhookMetadata` that is handed to the app's business-logic handler: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The identity binding that is broken is: **the HMAC-verified bytes (body) ≠ the bytes that determine the tenant (shop-domain header)**. The gem verifies "is this body byte-for-byte what was HMAC-signed with our `api_secret_key`?" but then answers a different, unauthenticated question — "which shop does this webhook belong to?" — using a header that carries zero cryptographic binding to that signature. This is structurally identical to the `RiskEngine` bug class: a gate/verification decision is made using one set of values (body bytes), while a materially different, security-relevant value (tenant identity) that should be covered by the same check is not, allowing the check to pass while the trusted downstream fact (which shop this is for) has silently diverged from what was actually authenticated.

Because a single app (identified by one `api_secret_key`) is installed on many merchant shops, and Shopify sends every merchant's webhooks signed with that same app secret, a party who legitimately receives a real webhook for Shop A (e.g., an app they installed on their own store, or any shop where they can trigger/observe an event that fires a webhook) obtains a body+HMAC pair that is valid for the app's secret. Nothing in `Request` or `HmacValidator` ties that HMAC to Shop A's domain specifically. If that request is relayed to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B, `HmacValidator.validate` still succeeds (body unchanged) and `Registry.process` will hand the handler `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"`, causing the app to act on Shop B's tenant data using Shop A's payload.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem's own webhook-processing code passes an unauthenticated `shop` value straight through to application handlers immediately after HMAC validation, giving host applications a false sense that `data.shop` is as trustworthy as the HMAC-verified body. Any host app that uses `data.shop` (as documented/intended, see `WebhookMetadata`/`Registry` usage in `test/webhooks/registry_test.rb`) to select which tenant's records to update is exposed to cross-tenant data corruption or disclosure without needing the app's `api_secret_key`, access token, or any privileged credential — only possession of one legitimately-signed webhook body for the same app.

### Likelihood Explanation
Moderate-to-high: obtaining a legitimately-signed webhook body is straightforward for anyone who can install the app on their own store or trigger a webhook-firing event on any shop using the app (e.g., a merchant on shop A creating an order to receive an `orders/create` webhook), since the same `api_secret_key` signs all shops' webhooks for a given app. Rewriting an HTTP header before relaying the request requires no cryptographic material.

### Recommendation
Bind the shop identity into the authenticated signable content, or independently authenticate it, before trusting `request.shop`. Options:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC-signed material (`to_signable_string`) so any header substitution invalidates the signature, mirroring how the report's suggested fix binds `spot`/`current` together instead of checking them independently.
- Alternatively, require host applications to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription that was registered, rather than trusting the header verbatim.
- At minimum, document prominently in `lib/shopify_api/webhooks/registry.rb` and `request.rb` that `shop` is NOT covered by the HMAC and must not be used for tenant selection without additional verification.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both using the same `api_secret_key`.
2. Attacker (who controls or can trigger events on `shop-a.myshopify.com`) receives (or intercepts, e.g. via their own endpoint proxy) a genuine webhook: body `B`, headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker replays the exact body `B` and hmac `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and hands `B`'s data to the handler, which now applies shop-a's event data to shop-b's tenant context. [4](#0-3)
