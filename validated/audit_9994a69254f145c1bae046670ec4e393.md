No vulnerability found for this question.

**Reasoning:**

The `cachedSodiumEncryptorRpc` factory at [1](#0-0)  merely wraps whatever `cachedSodiumEncryptor` module/adapter is registered via `createRpcFeature`, which exposes it both as an internal IOC module and as an SDK API surface [2](#0-1) . This is not a dapp-facing signing RPC (like `eth_sign`/`personal_sign`); it is an internal primitive used by `unlockEncryptedStorage` to encrypt/decrypt the `WALLET_INFO` secure-storage blob [3](#0-2) .

The underlying `CachedSodiumEncryptor` class restricts key derivation strictly to a hard-coded allow-list (`WALLET_INFO`, `FUSION`) via `#checkIfAllowed`, throwing `'Key source not allowed for caching.'` for any other `keyId`, and all params are validated by strict Zod schemas (`keySourceSchema`, `encryptSecretBoxParamsSchema`, etc.) that reject unrecognized keys [4](#0-3) [5](#0-4) . Signing-related keys and arbitrary asset key derivation paths are excluded from this cache entirely, so there is no path from this module to "sign with a different seed, key, or wallet account than the user approved."

`seedId` is attacker-suppliable as a string, but it is only used to call `keychain.exportKey({ keyId, seedId, exportPrivate: true })` [6](#0-5) , which is scoped to seeds already present in the local keychain instance — an attacker cannot inject external/foreign seed material through this path; they could at most reference another already-imported local seed, which is not an authorization bypass into new wallet material.

Regarding the "cache must be cleared on lock/clear" invariant: the package is explicitly documented as designed to operate "regardless of lock (after initial unlock)" for the two whitelisted key IDs [7](#0-6) , and the code comment confirms `WALLET_INFO` storage is "unlocked only once during the runtime lifecycle of the application, and never re-locked" [8](#0-7) . The absence of a lock/clear listener wired to this cache is intentional behavior for this specific whitelisted, non-signing storage-encryption use case, not a violation of an invariant — no listener clears it in the SDK bootstrap either [9](#0-8) .

Since the allow-list blocks any signing-capable or arbitrary-asset key derivation, and `seedId`/`keyId` are both schema-validated and scoped to local keychain state (no externally injected seed/key material), there is no reachable path for an unprivileged dapp/origin request to cause the SDK to sign with an unapproved seed, key, or account through this module.

export const ALLOWED_KEY_IDS = [
  // 'WALLET_INFO' is used for secure storage - everything that's not the seed/private keys. Examples: tx-history, address cache, nfts, etc.
  // for historical reasons, secure storage is unlocked only once during the runtime lifecycle of the application, and never re-locked.
  EXODUS_KEY_IDS.WALLET_INFO,
  EXODUS_KEY_IDS.FUSION,
]

export class CachedSodiumEncryptor {
  readonly #keychain: Keychain
  readonly #cache = new Map<string, Buffer>()

  constructor({ keychain }: Dependencies) {
    this.#keychain = keychain
  }

  async #derivePrivateKey({ keyId, seedId }: KeySource) {
    const { privateKey } = await this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })
    return privateKey
  }

  #checkIfAllowed = ({ keyId }: KeySource) => {
    return ALLOWED_KEY_IDS.some((allowedKeyId) => KeyIdentifier.compare(allowedKeyId, keyId))
  }

  #getPrivateKey = restrictConcurrency(async (params: KeySource) => {
    assert(this.#checkIfAllowed(params), 'Key source not allowed for caching.')

    const cacheKey = getCacheKey(params)
    if (!this.#cache.has(cacheKey)) {
      this.#cache.set(cacheKey, await this.#derivePrivateKey(params))
    }

    return this.#cache.get(cacheKey)
  }) as (keySource: KeySource) => Promise<Buffer>
