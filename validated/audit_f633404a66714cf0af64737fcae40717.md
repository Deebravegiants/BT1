### Title
Webhook HMAC validation signs only the raw body, allowing shop/topic header spoofing for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated request headers. `Utils::HmacValidator.validate` verifies the HMAC over that signable string only, so the identity fields the registry dispatches on (`request.shop`, `request.topic`) are never bound to the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 

`hmac` is derived from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, but `to_signable_string` returns only `@raw_body` — `shop`, `topic`, `webhook_id`, and `api_version`, all sourced from separate headers, are excluded from the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` then validates the HMAC and dispatches purely on the unauthenticated `request.topic` and forwards the unauthenticated `request.shop` to the handler as the tenant identity: [4](#0-3) 

The equality this breaks is: **shop authenticated == shop acted on**. The HMAC proves "this body was signed by the app's `api_secret_key`" but not "this body belongs to shop X" or "this body is for topic Y." Because a merchant's own app-secret is shared across every shop instance of that app, any body+HMAC pair that was legitimately generated for one shop's webhook delivery remains a valid HMAC pair regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it on replay.

### Impact Explanation
An unprivileged actor who operates (or has installed) the app on their own shop receives legitimate webhook deliveries containing valid `raw_body` + `hmac-sha256` pairs from Shopify. Because the signature covers only the body, that same body/HMAC pair can be replayed directly against the app's webhook endpoint with a forged `shopify-shop-domain` header claiming to be a different shop, and/or a forged `shopify-topic` header selecting a different handler. `HmacValidator.validate` will pass (the HMAC still matches the untouched body), and `Registry.process` will hand `WebhookMetadata` with the attacker-chosen `shop` and `topic` to the registered handler. Any handler logic that trusts `data.shop` to key per-tenant records (the intended and documented use, matching `WebhookMetadata`'s `shop` field) will attribute the attacker's own body content to an arbitrary victim shop, i.e., cross-tenant data injection through the app's own trusted dispatch path.

### Likelihood Explanation
Obtaining a valid raw_body/HMAC pair only requires operating one instance of the app (a normal merchant install), which is achievable by any unprivileged actor with no credentials, tokens, or secrets belonging to the victim. Sending a forged header replay to the app's public webhook endpoint requires no special access. The likelihood is constrained only by the target app actually keying tenant-sensitive logic off `WebhookMetadata#shop`/`#topic` in its handler, which is the intended and documented use of this API.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind the header-derived identity fields to the signed payload), so `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`, topic `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker (who owns `shop-a` and thus legitimately received the webhook) replays a POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the identity of `shop-victim`.
