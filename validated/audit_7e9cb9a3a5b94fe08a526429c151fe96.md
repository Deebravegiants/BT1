### Title
Webhook Shop Attribution Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given shop once the HMAC validates, but the HMAC is computed only over the raw request body — the `shop-domain` header that the gem uses to attribute the event to a tenant is never included in the signed material. Anyone who can obtain one validly-signed webhook body for the app (e.g., by having their own shop install the app and receive a genuine webhook) can replay that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a different, victim shop. The signature check still passes because it never looked at the header, and the handler is invoked believing the event originates from the victim's shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` verifies the signature purely against `to_signable_string` and the app's shared `client_secret` — the same secret is used for HMACs across every shop that installs the app: [2](#0-1) 

`Registry.process` only checks that the HMAC (over the body) validates, then immediately trusts `request.shop` (parsed from the unauthenticated `shop-domain` header) as the tenant identity handed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is documented as "the shop domain of the webhook" and is the value app developers are expected to use to route/attribute the webhook payload to a specific merchant record: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header used for tenant attribution == shop bound into the HMAC-signed bytes`. Because the shop header is entirely outside `to_signable_string`, this equality is never enforced by the gem — the bug class matches the report's "a field acted on but not covered by the HMAC" pattern.

### Impact Explanation
Since the webhook HMAC secret (`client_secret`) is shared across all shops that install a given app, any unprivileged party who controls one installed shop (their own test/dev store) can obtain a legitimately-signed webhook body from Shopify for their own shop, then resend that same body to the app's public webhook endpoint with the `shop-domain` header rewritten to any target shop domain of their choosing. Because `Registry.process` never binds the header to the signed bytes, the forged request passes HMAC validation and is delivered to the app's handler tagged as coming from the victim shop. Depending on how the host application uses `data.shop` (e.g., to look up and mutate the victim's local records, enqueue jobs "on behalf of" that shop, or make follow-up authenticated API calls using the victim's stored session), this enables cross-tenant data injection/corruption — a violation of the tenant isolation boundary this gem is responsible for enforcing via HMAC verification.

### Likelihood Explanation
Exploitation requires only an unprivileged HTTP client and knowledge of one shop's genuine webhook traffic (trivially obtainable by installing the app once on the attacker's own free/dev store), no leaked secrets, tokens, or privileged access — well within the unprivileged-internet-user threat model. The webhook endpoint is a public, unauthenticated HTTP route by design, so no additional network position or bypass is required beyond header manipulation.

### Recommendation
Bind the shop identity into the verified material before it is trusted. Options include: incorporate the `shop-domain` header into `to_signable_string` (if that is compatible with the HMAC scheme actually used by Shopify — recheck against Shopify's documented mandatory-webhook HMAC construction), or, more robustly, cross-check `request.shop` against records of shops that are actually registered/installed for this app (e.g., verify the shop has an active session/webhook registration) before invoking the handler, so a forged header pointing at an uninvolved shop is rejected even when the body's HMAC is valid.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, client_secret) == H`, regardless of the shop header.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it belonged to the victim's tenant.
