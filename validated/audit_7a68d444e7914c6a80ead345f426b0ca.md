### Title
Race between `Application#changePassphrase` and `Application#lock` re-caches new passphrase after lock clears cache - ([File: features/application/src/modules/application.ts])

### Summary
`changePassphrase` performs `#wallet.changePassphrase(...)` followed by an unconditional `await this.#passphraseCache.set(newPassphrase)` with no coordination against a concurrently-invoked `lock()`. Because both RPC-exposed methods mutate the same passphrase-cache storage and lock state independently and are not mutually exclusive, a `lock()` call interleaved between the wallet-level passphrase change and the cache-set can complete its `clear()` before `changePassphrase` writes the new passphrase, leaving a live cached secret while `#lockedAtom` reports `true`.

### Finding Description
`changePassphrase` at [1](#0-0)  executes: `await this.#wallet.changePassphrase(...)` then `await this.#passphraseCache.set(newPassphrase)`. `lock` at [2](#0-1)  executes `await this.#wallet.lock()`, `await this.#lockedAtom.set(true)`, `await this.#passphraseCache.clear()`. Both are `async` instance methods on `Application` with no mutex/queue serializing calls, and both are reachable independently via RPC (per the question's stated preconditions). If `lock()` is invoked by any caller (including the RPC caller who initiated `changePassphrase`, or a concurrent tab/dapp session) after `#wallet.changePassphrase` resolves but before `#passphraseCache.set(newPassphrase)` resolves, the following interleaving is possible:

1. `changePassphrase`: `#wallet.changePassphrase` resolves (wallet's internal passphrase is now `newPassphrase`).
2. `lock`: `#wallet.lock()` → `#lockedAtom.set(true)` → `#passphraseCache.clear()` all complete.
3. `changePassphrase`: `#passphraseCache.set(newPassphrase)` executes, writing `newPassphrase` back into `PassphraseCache` storage via `batchSet` at [3](#0-2)  — after the wallet has already reported locked.

At this point `#lockedAtom` is `true` (locked) but `PassphraseCache.get()` will return the valid `newPassphrase` (not expired, since `addedAt`/`ttl` were just set), because `get()` only checks TTL/inactivity, not lock state, per [4](#0-3) . Nothing in `Application` re-validates lock state before or after the cache write, and no lock/mutex guards the sequence spanning `#wallet.changePassphrase` + `#passphraseCache.set`. This directly parallels the same class of unguarded async interleaving already present between `unlock()`'s `#passphraseCache.set(opts.passphrase)` (fire-and-forget, `void`) at [5](#0-4)  and `lock()`'s `clear()`.

### Impact Explanation
A stale/live passphrase persists in the unencrypted-by-lock-state cache after the wallet is nominally locked. Any subsequent app restart or code path that calls `#autoUnlock()` (which trusts `PassphraseCache.get()` whenever `#wallet.isLocked()` is true, at [6](#0-5) ) will silently auto-unlock the wallet using this leaked passphrase, defeating the user's expectation that `lock()` immediately revokes cached secret access. This matches a "privilege persistence / secret disclosure past lock boundary" impact class — an attacker or malicious surface with the ability to trigger `lock()` and `changePassphrase()` concurrently (e.g., a compromised dapp origin with RPC access to both, or a UI race from double-clicking/rapid successive calls) can cause the wallet to remain unlockable using the passphrase despite the locked indicator.

### Likelihood Explanation
This requires that both `changePassphrase` and `lock` be reachable and invocable concurrently without the RPC/host layer serializing calls to the same `Application` instance — which is explicitly stated as a precondition in the question, but I could not verify from the code searched here whether the surrounding RPC/host layer (e.g., `sdk-rpc`, wallet-accounts RPC bindings) enforces serialization/mutex over `Application` method calls. If such serialization exists at a layer outside `features/application`, this race would not be exploitable in practice. Within `features/application/src/modules/application.ts` itself, there is no serialization, so the race is real at this layer.

### Recommendation
Serialize state-mutating `Application` methods (`lock`, `unlock`, `changePassphrase`) behind a single mutex/queue so no interleaving of cache writes and lock/clear operations can occur. Additionally, `changePassphrase` should re-check `#wallet.isLocked()` (or a monotonic "generation"/version token incremented by `lock()`) immediately before calling `#passphraseCache.set(newPassphrase)`, and skip the cache write if the wallet was locked in the interim.

### Proof of Concept
Property-based/invariant test in `features/application/src/modules/__tests__/application.test.ts` (or similar):
1. Construct `Application` with a fake `#wallet` whose `changePassphrase` resolves after a controllable delay, and a real `PassphraseCache` backed by an in-memory `Storage`.
2. Fire `application.changePassphrase({ currentPassphrase, newPassphrase })` and `application.lock()` concurrently with `Promise.all`, arranging (via delay injection in the fake wallet) for `lock()`'s `#wallet.lock()`/`clear()` sequence to complete strictly between `#wallet.changePassphrase` resolving and `#passphraseCache.set` being invoked.
3. Assert: after both promises settle, `await passphraseCache.get()` is `undefined` when `await lockedAtom.get()` is `true`. 
4. Run this interleaving many times (fuzzed delays) asserting the invariant `locked === true ⇒ passphraseCache.get() === undefined` never fails; the current code is expected to fail this assertion in the described interleaving.

    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

    }
