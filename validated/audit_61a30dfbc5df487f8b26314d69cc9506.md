### Title
ERC721 tokens can be escrowed as ERC20 inputs in `IntentGatewayV2.placeOrder`, permanently freezing the deposited NFT - (File: `evm/src/apps/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` accepts any `address` as an input/output "token" and blindly moves it with `IERC20(token).safeTransferFrom(...)` without verifying the address is actually an ERC20 contract. Because ERC721's `transferFrom(address,address,uint256)` shares the exact same function selector as ERC20's `transferFrom`, a user can escrow an ERC721 token (using its `tokenId` as the "amount") into the gateway. The escrow accounting then treats it as a fungible-token balance, and every release path (`_withdraw`) later calls `IERC20(token).safeTransfer(...)`, which has no matching function on the ERC721 contract and reverts unconditionally — permanently freezing the asset in the gateway.

### Finding Description
`placeOrder` moves input tokens into escrow purely by address, with no ERC20/ERC165 validation: [1](#0-0) 

The generic ERC20 branch does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
```
`safeTransferFrom` on `IERC20` encodes to the selector for `transferFrom(address,address,uint256)` — bit-for-bit identical to `IERC721.transferFrom(address,address,uint256)`. If `token` is actually an ERC721 contract and `order.inputs[i].amount` happens to be a `tokenId` owned by `msg.sender` and approved to the gateway, the call succeeds and moves the NFT into the gateway, while `_orders[commitment][token]` is credited with that value as if it were an ERC20 balance: [2](#0-1) 

Every subsequent release of this escrow entry — whether via a solver fill (`RedeemEscrow`), a cancellation refund (`RefundEscrow`), or same-chain fill — routes through `IntentsBase._withdraw`, which unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)`: [3](#0-2) 

Standard ERC721 implementations (e.g. OpenZeppelin's `ERC721`) do not implement `transfer(address,uint256)` and have no fallback, so this call reverts every time. There is no code path anywhere in `IntentsBase`/`IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` that validates a `TokenInfo.token` is a real fungible token before escrowing or releasing it.

### Impact Explanation
Once an ERC721 token is deposited as an "input" via `placeOrder`, its associated escrow entry (`_orders[commitment][token]`) can never be released:
- A solver cannot claim it via `RedeemEscrow`/fill, because `_withdraw`'s `safeTransfer` call reverts.
- The order cannot be refunded via cancellation/timeout (`RefundEscrow`) for the same reason.

This is a permanent freezing-of-funds bug reachable by a single unprivileged `placeOrder` transaction: the escrowed NFT is irrecoverably locked in the `IntentGatewayV2` contract, with no governance or admin path to extract it (the sweep/dust functions are for accumulated protocol dust, not user escrow, and also use `safeTransfer`, so they cannot rescue it either). Additionally, because the affected `_orders[commitment][token]` slot never reaches zero, any partial-fill/finalize accounting logic tied to that slot is permanently stuck in an inconsistent state for that order.

### Likelihood Explanation
Any user can trigger this unintentionally or deliberately by specifying an ERC721 contract address as `order.inputs[i].token` and a valid, approved `tokenId` as the `amount` in a single call to `placeOrder`. No special privileges, timing, or race conditions are required — this is a direct, deterministic consequence of missing token-type validation in the escrow path, matching the reported bug class (ERC721 mis-classified and permanently stuck as an ERC20 deposit).

### Recommendation
Reject non-ERC20 tokens at escrow time. Options:
- In `placeOrder` (and `predispatch`/output handling), require that `token` supports `IERC20` semantics (e.g., check that `IERC20(token).balanceOf`/`allowance` behave as expected, or maintain an explicit allow-list/registry of supported tokens) and explicitly reject addresses that implement `IERC165`/`IERC721`/`IERC1155` (via `supportsInterface`) before calling `transferFrom`.
- Alternatively, disallow depositing any token whose `code` responds to `supportsInterface(0x80ac58cd)` (ERC721) or `0xd9b67a26` (ERC1155) returning `true`.

### Proof of Concept
1. Deployer owns an ERC721 collection at address `NFT`, with `tokenId = 1` owned by `user`.
2. `user` approves `IntentGatewayV2` for `tokenId 1` (`NFT.approve(gateway, 1)`).
3. `user` calls `placeOrder` with `order.inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(NFT)))), amount: 1})` (using `1` as both "amount" and NFT `tokenId`).
4. Inside `placeOrder`, `IERC20(NFT).safeTransferFrom(user, gateway, 1)` resolves to `NFT.transferFrom(user, gateway, 1)` and succeeds, moving the NFT into the gateway (`evm/src/apps/IntentGatewayV2.sol:312-329`). `_orders[commitment][NFT] = 1` is recorded (`evm/src/apps/IntentGatewayV2.sol:364-373`).
5. Any attempt to release this escrow — a solver `fillOrder`/`RedeemEscrow`, or `user` cancelling the order after expiry for a `RefundEscrow` — calls `IntentsBase._withdraw`, which executes `IERC20(NFT).safeTransfer(beneficiary, 1)` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`). Since `NFT` has no `transfer(address,uint256)` function, this reverts, and the NFT remains permanently locked in the `IntentGatewayV2` contract with no recovery path.
