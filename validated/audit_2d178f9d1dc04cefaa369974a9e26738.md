### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, but that HMAC check only covers the raw request body. The `shop`, `topic`, `webhook-id`, and `api-version` values — which are read straight from unauthenticated HTTP headers — are never part of the signed material, yet they are exactly the fields the library uses to select the handler and to tell the host application which tenant the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate_signature` computes/compares the HMAC solely over that signable string: [2](#0-1) 

`Registry.process` performs exactly one authenticity check — this body-only HMAC — and then immediately uses two header-derived, unsigned fields to make security-relevant decisions: `request.topic` to select the handler out of the registry, and `request.shop` to populate the `WebhookMetadata` passed to that handler as the acting tenant: [3](#0-2) 

Both `topic` and `shop` are read directly from request headers with no cryptographic binding to the body or to each other: [4](#0-3) 

This is precisely the class of bug described in the external report: a value that is *acted on* (here, tenant/topic identity used to dispatch a handler and identify the shop) is not included in the value that is *cryptographically verified* (the body-only HMAC). The equality the code implicitly assumes — "the `shop`/`topic` headers accompanying a validly-HMAC'd body are the `shop`/`topic` that produced that body" — does not hold, because nothing enforces it.

**Concrete exploitation path:** An attacker who runs their own store and installs the target app (an ordinary, unprivileged action requiring no special credentials) can trigger a legitimate webhook from their own shop. Since `api_secret_key` is shared across all shops for a given app, the HMAC over that attacker-controlled body is valid — the attacker can compute it themselves once they see one legitimate delivery, or simply intercept/replay a webhook Shopify sent them. They then POST that same `(body, hmac)` pair directly to the app's public webhook receiving endpoint (implemented via `Registry.process`), but with `x-shopify-shop-domain` and `x-shopify-topic` headers rewritten to point at a victim shop and/or a different topic (e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`). `HmacValidator.validate` still passes because the body/HMAC pair is genuinely valid; `Registry.process` then invokes the handler for the forged topic with `WebhookMetadata.shop` set to the victim's domain and attacker-controlled body content.

### Impact Explanation
If the host application (as documented and intended for this gem) uses `WebhookMetadata#shop`/`#topic` to look up the tenant's session/record and act on it — e.g., to delete a shop's data on `shop/redact`, revoke access on `app/uninstalled`, or process `customers/data_request`/other business webhooks — an attacker can force the app to execute tenant-scoped side effects against a shop they do not control, using data and a topic of their choosing while only proving authenticity for their own shop's traffic. This is a cross-tenant boundary violation stemming directly from the app trusting an unauthenticated identity field as if it were bound by the HMAC.

### Likelihood Explanation
Requires only: (1) installing the app on an attacker-owned/free development store to legitimately trigger at least one signed webhook, and (2) being able to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — both are unprivileged, internet-reachable actions requiring no `api_secret_key`, access token, or social engineering.

### Recommendation
Do not trust `shop`/`topic`/`webhook-id`/`api-version` headers as authenticated identity unless they are cryptographically bound to the request. At minimum:
- Have `Request#to_signable_string` (or a separate check in `HmacValidator`/`Registry.process`) include the `shop` and `topic` header values in the material that is HMAC-verified, or
- Cross-check the header-derived `shop` against an independently trusted source (e.g., require the caller to supply the expected shop for the endpoint and compare) before dispatching to a handler, and document clearly that consumers must not rely on `request.shop`/`request.topic` for authorization decisions without additional verification.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store `attacker.myshopify.com`, and capture (or trigger) one webhook delivery, obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's real `api_secret_key`.
2. Send a new HTTP POST to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured valid HMAC
   - body: the captured raw body (unchanged, so the HMAC still verifies)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - `x-shopify-topic`: a topic of choice, e.g. `shop/redact`
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (body/HMAC match), and `ShopifyAPI::Webhooks::Registry.process` dispatches the `shop/redact` (or chosen) handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the host app to act on the victim tenant despite the request never having been authenticated for that shop or topic.
