## Title
Precision loss in cross-chain amount decimal conversion causes silent, permanent token loss - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `hyper-fungible-token` pallet's `on_accept` handler converts an incoming ERC20-denominated amount to the local asset's balance denomination by **dividing** when the source ("ERC20") decimals exceed the local asset's decimals. This division truncates towards zero and is never checked for a zero result, so a user who bridges a small-enough amount has their tokens burned/locked on the source chain but receives **nothing** on the destination — the difference is permanently lost, with no revert and no way to reclaim it.

### Finding Description
`convert_to_balance` computes `value / 10^(erc_decimals - local_decimals)` and returns whatever integer results, including zero: [1](#0-0) 

`on_accept` uses this helper to translate the incoming EVM message amount into the local mint/transfer amount, with no floor/zero check before crediting the beneficiary: [2](#0-1) 

The `erc_decimals` value comes from the `Precisions` storage map (typically 18, matching standard ERC20 tokens), while `decimals` is the local asset's (or native currency's) decimals, which can be much lower (e.g. 6): [3](#0-2) 

Critically, the tokens on the EVM source side are already irreversibly burned from the caller **before** the cross-chain message is dispatched — there is no compensating check on that side either: [4](#0-3) 

If `erc_decimals - local_decimals = d` and the ERC20 amount sent is less than `10**d`, `convert_to_balance` returns `0`. The `on_accept` flow then proceeds to `mint_into`/`transfer` of `amount = 0` into the beneficiary, emitting `TokenReceived { amount: 0, .. }` without ever reverting the message — so the request is treated as successfully delivered even though the user received nothing, while their original tokens are gone forever on the source chain.

This exactly mirrors the referenced SolverVaults report: a decimal-conversion division silently floors small amounts to zero, with no `require(amountInCollateralDecimals > 0)`-style guard, resulting in a permanent, un-refundable loss of the user's funds.

### Impact Explanation
Any unprivileged user who calls `send()` on a `HyperFungibleTokenUpgradeable` (or the equivalent pallet `send` extrinsic in the other direction) with a "dust" amount relative to the decimals gap can lose their entire transferred amount with no recourse: the source-side burn/lock is unconditional and irreversible, and the destination-side credit silently becomes zero. This is a direct, permanent loss of user funds reachable from a single ordinary cross-chain transfer — no relayer, validator, or governance action is malicious or required.

### Likelihood Explanation
Any pair of registered chains/assets where the EVM contract decimals (commonly 18) differ from the local Substrate asset's decimals (e.g. 6 for a USDC-like asset) is exposed. A user simply needs to send an amount below `10^(erc_decimals - local_decimals)` raw units — a very small, plausible dust amount, or an amount miscalculated by a wallet/dApp doing decimal math — to trigger total loss. No special conditions or race are needed; likelihood is high given normal token transfer usage.

### Recommendation
In `convert_to_balance` (and its usage sites in `on_accept`/`on_timeout` in `module.rs`), reject conversions that round down to zero (e.g. return an error such as `AmountTooSmallForDecimals` when the source amount is nonzero but the converted amount is zero) rather than silently minting/transferring `0`. Apply the same check to the `on_timeout` refund path, and consider adding a similar guard in the reverse (`convert_to_erc20`) direction to fail fast on any future decimals combination that could produce equivalent truncation.

### Proof of Concept
1. Register a token pair where the EVM contract (source) reports 18 decimals (`Precisions[asset][evmChain] = 18`) and the local Substrate asset uses 6 decimals.
2. On the EVM side, a user calls `HyperFungibleTokenUpgradeable.send()` with `amount = 10**12 - 1` (less than one unit of the local 6-decimal asset when scaled): tokens are burned from the caller immediately (`_burn(msg.sender, params.amount)`).
3. The ISMP POST is delivered to the pallet's `on_accept`; `convert_to_balance(value=10**12-1, erc_decimals=18, local_decimals=6)` computes `(10**12-1) / 10**12 = 0`.
4. `mint_into`/`transfer` executes with `amount = 0`; `TokenReceived { amount: 0, .. }` is emitted, and the ISMP request is considered successfully handled (no revert).
5. The user's `10**12 - 1` raw EVM tokens are permanently gone — burned on the source chain and never credited on the destination.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
