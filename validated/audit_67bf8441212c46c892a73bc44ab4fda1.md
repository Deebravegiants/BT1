### Title
Reserve fee (treasury-lp) rounding to zero on frequent `accrue()` calls permanently loses protocol interest income - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
In every Zest vault contract (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), the protocol's fee cut of accrued interest (`treasury-lp`, later minted to `.dao-treasury`) is computed from `debt-delta`, the change in `total-debt` between two consecutive index updates. When `accrue()` is called very frequently (every block/transaction that touches the vault: deposits, withdraws, borrows, repays, liquidations), `debt-delta` per call becomes very small, and `mul-div-down` truncation can cause the fee-reserve mint (`treasury-lp`) to permanently round down to zero on each call, even though the lending index (and hence lenders' claim on interest) keeps advancing.

### Finding Description
`accrue()` computes the new borrow/liquidity index (`next-index`, `next-liquidity-index`) and, from the resulting `debt-delta`, computes the protocol's reserve cut: [1](#0-0) 

```
(let ((next (next-index))
      (nliq (next-liquidity-index))
      (scaled-principal (var-get principal-scaled))
      (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
      (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
      (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
      (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
  (if (not (is-eq idx next)) (var-set index next) false)
  (if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
  (if (> treasury-lp u0) (try! (ft-mint? zft treasury-lp .dao-treasury)) false)
  (if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)
  (ok { index: next, lindex: nliq }))
```

The identical pattern appears in the other vaults, e.g. `calc-treasury-lp-preview`: [2](#0-1) 

The value identity that should hold is:

`fees charged (protocol share of interest accrued via index growth) == fees forwarded (treasury-lp minted to .dao-treasury)`

`reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` uses integer (floor) division. If a caller — or simply organic high-frequency protocol usage (deposits/withdraws/borrows/repays/liquidations all call `accrue()`) — keeps `time-delta` between successive `accrue()` invocations very small, `debt-delta` for that interval is proportionally small. Once `debt-delta * fee-reserve < BPS` (e.g. `debt-delta` of only a few units against a `fee-reserve` in basis points on a vault with large `total-debt`/`principal-scaled`), `reserve-inc` truncates to `0`, so `treasury-lp` is forced to `u0` and the `ft-mint?` to `.dao-treasury` never happens for that slice of interest. Meanwhile `index` still advances by however small an amount, so the condition `(not (is-eq idx next))` is true, `last-update` is advanced to `stacks-block-time`, and the loop can repeat indefinitely: each call permanently discards a slice of protocol fee income to rounding rather than deferring/accumulating it. This mirrors the referenced Yield finding exactly: `rewardsPerToken_.accumulated` (here, cumulative `treasury-lp`) stays constant/rounds to zero on tight update intervals while `lastUpdated` (here, `last-update`/`index`) is continually advanced, so the tracked quantity that should compound never actually accrues — the fee income for that slice of interest is permanently lost rather than merely delayed, because there is no carry-over/residual tracking of the truncated `reserve-inc` between calls.

### Impact Explanation
This breaks the "fees charged versus fees forwarded" identity: interest is created and distributed to lenders through the growing liquidity index, but the protocol's corresponding reserve cut is never minted to `.dao-treasury` for the intervals where truncation occurs. Because there is no accumulator that carries the truncated remainder into the next `accrue()` call, this loss is permanent, not merely delayed — it is a High-severity impact per the "theft/permanent freezing of unclaimed yield" category, since it is the DAO treasury's unclaimed protocol yield that is systematically eroded. On any vault with large `total-debt`/`principal-scaled` (e.g. large-cap pools like the USDC or STX vault) and typical `fee-reserve` (basis points) values, ordinary transaction frequency alone (each deposit/withdraw/borrow/repay/liquidation triggers `accrue()`) is enough to keep `debt-delta` per call small, making this loss a naturally-occurring condition rather than requiring a dedicated attacker.

### Likelihood Explanation
Likelihood is high because `accrue()` is invoked as part of nearly every state-changing vault operation (`system-borrow`, deposits, withdrawals, repayments, liquidations), so in an actively used vault the interval between accruals is frequently short by default — no adversarial timing manipulation is strictly required, only ordinary usage volume, exactly as noted in the original report ("wouldn't even need an attacker").

### Recommendation
Track a persistent, unrounded remainder for the reserve-fee computation (similar to a `rewardsPerToken_.accumulated`-remainder pattern): instead of computing `reserve-inc` fresh from each `debt-delta` and discarding the truncated fraction, accumulate the truncated remainder across calls (e.g., store a running fractional remainder in higher precision, or compute the treasury share directly proportional to the full outstanding `total-debt` rather than only the incremental `debt-delta` since the last accrual) so that fee income is never definitively lost to rounding regardless of how often `accrue()` is invoked.

### Proof of Concept
1. Vault has a large `total-debt`/`principal-scaled` (e.g. corresponding to a pool with substantial deposits) and a `fee-reserve` set in basis points (e.g. 1000 = 10%).
2. A user (or organic traffic) repeatedly triggers any vault function that calls `accrue()` (e.g., alternating small `deposit`/`withdraw`, or `system-borrow`/`system-repay`) every block.
3. Each call: `time-delta` is minimal → `next-index` increases by a tiny amount → `debt-delta = mul-div-down(scaled_principal, next-old, INDEX-PRECISION)` is small.
4. `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` truncates to `0` because `debt-delta * fee-reserve < BPS`.
5. `treasury-lp` stays `0`, no `ft-mint?` to `.dao-treasury` occurs, yet `index` advances and `last-update` is set to `stacks-block-time`.
6. Repeating this over the full accrual period, the DAO treasury's protocol fee for that period is never minted, even though borrowers paid interest and lenders' liquidity index grew — the fee income is permanently lost to rounding.
