## Analog Found

### Title
Cross-chain calldata execution in `pallet-hyper-fungible-token` bypasses the runtime's `BaseCallFilter` via `pallet_utility::batch` nesting - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
Jenkins Matrix Project's `FilterScript` sandbox bypass (GHSA-qxf8-8837-hq7w) let a permission-gated actor smuggle code past a security check that was applied at the wrong layer. The structural analog here is `pallet_hyper_fungible_token`'s cross-chain calldata executor: it manually re-implements the runtime's `BaseCallFilter` check because it dispatches decoded calls outside of `frame_executive::Executive`'s normal extrinsic pipeline, but that manual check only inspects the *outer* `RuntimeCall` variant, not calls nested inside a `pallet_utility::batch`. Since `pallet_utility` dispatches its inner calls via `dispatch_bypass_filter` (trusting that `Executive` already filtered the top-level call — an assumption that does not hold on this path), a filtered call reaches execution anyway.

### Finding Description
`Pallet::on_accept` in `pallet-hyper-fungible-token`, reachable by any relayer delivering an HFT token-bridge message with a non-empty `data` field, decodes attacker-supplied bytes into a `T::RuntimeCall` and dispatches it directly: [1](#0-0) 

The comment at lines 191-193 states the intent plainly: this manual `BaseCallFilter::contains(&runtime_call)` check exists *because* `runtime_call.dispatch(...)` here bypasses the normal filtering that `Executive::apply_extrinsic` would otherwise apply to a top-level extrinsic. But `Contains` implementations wired into the parachain runtimes' `BaseCallFilter` — `ReputationCallFilter`, `IsmpCallFilter`, `CollatorSelectionCallFilter` — are all shallow, single-level pattern matches that fall through to `_ => true` for any call they don't explicitly recognize: [2](#0-1) [3](#0-2) 

`RuntimeCall::Utility(pallet_utility::Call::batch { calls })` (or `batch_all`/`force_batch`) matches none of these filters' patterns, so the manual check at `module.rs:194` passes for a `Utility::batch` wrapper regardless of what it contains. `pallet_utility`'s batch implementation dispatches each inner call via `dispatch_bypass_filter`, which — by Substrate's design — never re-applies `BaseCallFilter`, because normally the filter was already enforced once at the top level by `Executive` before `pallet_utility` ever saw the call. `pallet_hyper_fungible_token::on_accept` never goes through `Executive`; it is invoked from the ISMP router as part of message delivery, so that upstream guarantee does not hold, and the inner call executes completely unfiltered.

Concretely: any account (attacker) that has bridged HFT tokens to itself (or that another party mapped via `EvmToSubstrate`, or with a valid `MultiSignature` per `SubstrateCalldata`) can construct `data` whose decoded `runtime_call` is `Utility::batch{ calls: [ RuntimeCall::Assets(pallet_assets::Call::transfer{ id: ReputationAssetId, target: <attacker2>, amount }) ] }`. `ReputationCallFilter` exists specifically to make the reputation/incentive asset non-transferable by ordinary dispatch — the filter is defeated for the nested case, letting the signer freely move that asset, undermining the incentive-accounting invariant the filter was built to protect. [4](#0-3) 
confirms `pallet_hyper_fungible_token` is wired into the nexus runtime's message routing, so the path is live.

### Impact Explanation
Bypassing `ReputationCallFilter` breaks the non-transferability invariant of the protocol's reputation/incentive asset — an unauthorized app action against an accounting primitive explicitly named in scope ("relayer fee and reward accounting"). The same shallow-filter root cause generalizes to any other call the runtime's `BaseCallFilter` is meant to block on this dispatch path (e.g. safe-mode/maintenance filtering), since none of it survives a `Utility::batch` wrapper. This is a protection-mechanism failure (CWE-693), reachable by an unprivileged cross-chain message sender, matching the "unauthorized app action" acceptance criterion.

### Likelihood Explanation
Medium-High. The only prerequisites are: (1) the destination runtime includes `pallet_utility` in its `RuntimeCall` enum (confirmed present in both `gargantua` and `nexus` weight/config wiring), and (2) the attacker controls, or can validly sign for, an account holding the asset/state they want to manipulate. No governance, admin, or validator privilege is required — this is exactly the "unprivileged token bridger" class the scoping rules call out.

### Recommendation
Do not rely on a single shallow `Contains::contains` check against the outer call when dispatching attacker-supplied calls outside the normal extrinsic pipeline. Either recursively unwrap and filter `pallet_utility::{batch, batch_all, force_batch}` (and any other call-wrapping pallet reachable via `T::RuntimeCall`, e.g. proxy/scheduler if present) before dispatch, or reject any `RuntimeCall::Utility(..)` (and other wrapper) variant outright on this cross-chain calldata-execution path, since `dispatch_bypass_filter` semantics make wrapper calls fundamentally unsafe to allow through a manually-applied filter.

### Proof of Concept
1. Attacker (or colluding account) accumulates a balance of the reputation asset (`ReputationAssetId`) through normal protocol operation (e.g. earned relayer incentives).
2. Attacker bridges a minimal amount of HFT tokens to themselves via `send()`, setting `data` to a `SubstrateCalldata` whose `runtime_call` decodes to:
   `RuntimeCall::Utility(pallet_utility::Call::batch { calls: vec![RuntimeCall::Assets(pallet_assets::Call::transfer{ id: ReputationAssetId::get(), target: <attacker2>, amount: <balance> })] })`
   and whose `signature` is a valid `MultiSignature` over `(nonce, runtime_call)` for the beneficiary account (per `module.rs` lines 124-173).
3. A relayer delivers the message; `on_accept` runs the manual filter check against the outer `Utility::batch` call — which passes because `ReputationCallFilter`'s match arm only inspects `RuntimeCall::Assets(...)` directly, not calls nested inside `Utility::batch`.
4. `runtime_call.dispatch(Signed(beneficiary))` executes `pallet_utility::batch`, which internally calls `dispatch_bypass_filter` on the nested `Assets::transfer`, moving the reputation asset despite `ReputationCallFilter` being designed to block exactly this transfer.

**Uncertainty:** I was not able to directly inspect the vendored `pallet_utility` source in this repository (it is pulled in as an external `polkadot-sdk` crate) to confirm the exact `dispatch_bypass_filter` call sites for this crate version, nor did I get a complete view of every runtime's `construct_runtime!` pallet index list confirming `pallet_utility` and `pallet_hyper_fungible_token` are simultaneously enabled on every deployed chain. The behavior described (`batch`/`batch_all`/`force_batch` bypassing filters on inner calls) is standard, long-documented Substrate/FRAME semantics, and `nexus`'s `ismp.rs` confirms `pallet_hyper_fungible_token` routing is live there; a Devin session with full repo/dependency access should verify the exact `pallet_utility` version's dispatch semantics and enumerate every runtime where both pallets coexist before treating this as fully confirmed.

pub struct ReputationCallFilter;
impl Contains<RuntimeCall> for ReputationCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		let rep = ReputationAssetId::get();
		match call {
			RuntimeCall::Assets(
				pallet_assets::Call::transfer { id, .. } |
				pallet_assets::Call::transfer_keep_alive { id, .. } |
				pallet_assets::Call::transfer_all { id, .. } |
				pallet_assets::Call::approve_transfer { id, .. } |
				pallet_assets::Call::transfer_approved { id, .. },
			) => *id != rep,
			_ => true,
		}
	}
}
