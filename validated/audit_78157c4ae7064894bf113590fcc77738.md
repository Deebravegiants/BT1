Based on my investigation, I found a valid analog vulnerability. The `x-shopify-shop-domain` header value that identifies the tenant is trusted by the webhook processing pipeline without being covered by the HMAC signature, which only authenticates the raw body.

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — HMAC only binds the raw body, not the tenant identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header to the app's handler as the authoritative tenant identity. Because the HMAC never binds to that header, any party holding one valid `(body, hmac)` pair for the app's shared `api_secret_key` can replay it with an arbitrary `shop-domain` value and have the handler believe the event belongs to a different, victim tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  None of the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) participate in the signed content.

`Registry.process` treats a passing HMAC check as proof of the entire request's authenticity, then forwards `request.shop` — read directly from the unauthenticated header — to the registered handler as the tenant identity: [2](#0-1)  `Request#shop` simply reads the header verbatim with no cross-check against the HMAC: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. Since the HMAC is computed from a per-app shared secret (`Context.api_secret_key`) and not the shop, the binding fails: `HmacValidator.validate` succeeds for `(body, hmac)` regardless of which shop's header accompanies it: [4](#0-3) 

An attacker who is a legitimate installer of the app on their own store (unprivileged, no special credentials) receives genuine webhooks signed with the same `api_secret_key` that is used for every shop on the app. They can capture one such `(raw_body, x-shopify-hmac-sha256)` pair and resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and the app's handler receives `WebhookMetadata#shop` claiming the victim's identity: [5](#0-4) 

This is consistent with how the gem's own documentation instructs consumers to use `data.shop` as the tenant key for subsequent processing (e.g., enqueuing shop-scoped jobs): [6](#0-5) 

### Impact Explanation
Handlers commonly key their business logic (session/access-token lookup, GDPR/mandatory topics like `shop/redact` and `customers/redact`, data mutation, or job enqueueing) off `data.shop`. Because that value is forgeable independently of the HMAC, an attacker can cause the app to process attacker-timed/attacker-triggered events under a victim shop's identity — a cross-tenant confusion that can trigger actions (e.g., redaction/uninstall handling, state changes, or GraphQL calls performed using the victim's stored session) attributed to the wrong tenant. This crosses the tenant boundary the gem's own webhook contract is meant to preserve.

### Likelihood Explanation
Any user can install the app on a shop they control (a normal, unprivileged onboarding action) and will legitimately receive webhooks signed with the app's shared secret. Replaying a captured `(body, hmac)` pair to the app's public webhook endpoint with a different `shop-domain` header requires no additional secrets, no access token, and no privileged access — only network access to the app's webhook URL, which is intentionally public.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed content, or independently verify that the shop header corresponds to a shop actually known/installed for this app before trusting it, e.g., cross-reference `request.shop` against a shop that has a stored, previously-authenticated session, rejecting webhooks for shops without an active install. At minimum, `Registry.process` should not treat HMAC success as validating the `shop` header, and downstream handler documentation should not imply `data.shop` is itself authenticated by the HMAC check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, permitted action for any Shopify merchant/developer).
2. App emits real webhooks to attacker's endpoint, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <hmac of body with the app's api_secret_key>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures the raw body bytes and the valid HMAC header value.
4. Attacker sends a request to the app's public webhook endpoint with the identical body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the shared secret — validation succeeds: [7](#0-6) 
6. The registered handler executes with `data.shop == "victim-shop.myshopify.com"`, even though the request never actually came from Shopify on behalf of that shop.
