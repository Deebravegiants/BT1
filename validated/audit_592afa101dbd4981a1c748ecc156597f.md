### Title
Webhook `shop-domain` Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant identifier) is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` to route the payload to the app's per-shop handler, breaking the binding between "bytes verified" and "bytes used to determine tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the raw body via `HmacValidator.validate(request)`, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only compares the HMAC against `to_signable_string`, so it never covers the shop header: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop that the HMAC-signed body actually originated from`. Because the app's `client_secret` (used to compute the HMAC) is the same across all shops installed on a given app, any party who can obtain one validly-signed `(raw_body, hmac)` pair for their own shop — e.g. from a webhook fired against their own store, or a store they control — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body signature, and `Registry.process` will hand the attacker-controlled body to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the cross-tenant boundary that `WebhookMetadata.shop` is supposed to guarantee to host applications: the gem represents an unauthenticated header value as an authenticated tenant identifier. Any host app that uses `data.shop` (as documented) to scope database writes, look up sessions, or otherwise select per-tenant state, per the gem's own documented handler contract, can be made to apply attacker-supplied webhook content under a victim shop's identity — a cross-tenant data confusion/injection primitive attributable to this gem's `Request`/`Registry` design, not to host misuse.

### Likelihood Explanation
The attacker needs a valid `(raw_body, hmac)` pair, which is trivial to obtain by installing the app (or by using a shop they control) since app installers are inherently untrusted parties able to trigger events in their own store. They only need to swap the shop-identifying header value in the replayed HTTP request, which requires no secret material at all — only network access to the app's public webhook endpoint. This makes the attack low-effort for any unprivileged user of the app.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind the `shop` claim to the signed payload, e.g., compute/verify the HMAC over a canonical string containing `shop-domain` in addition to the raw body, so `Registry.process` cannot be fed a genuinely-signed body under a forged shop identity.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any webhook topic (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both computed with the shared `client_secret`.
2. Attacker sends this same body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `OpenSSL.secure_compare(computed_signature, hmac)` against `to_signable_string` (`@raw_body`) — this succeeds since the body/HMAC pair is genuinely valid. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` and processes it as if Shopify sent this data for the victim shop.

        end
