### Title
Session hijacking via predictable, unsigned session cookie value in `SessionUtils.current_session_id` - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
The identity binding that should hold is: `cookie value received from the client == an id that can only be produced by (or on behalf of) the shop that legitimately completed OAuth`. In this gem, that binding does not exist: the cookie value is a deterministic string derived only from the shop domain and is never signed or otherwise bound to a secret, so any client can supply it directly.

### Finding Description
When an app uses cookie-based session lookup for non-embedded flows, `ShopifyAPI::Utils::SessionUtils.current_session_id` simply returns whatever is stored under the `shopify_app_session` cookie name, with no verification: [1](#0-0) 

That cookie's *value* is `session.id`, which for the two supported session kinds is fully deterministic and derivable from public information (the shop domain, and for online sessions the Shopify user id): [2](#0-1) 

The cookie itself is only a plain, unsigned identifier set by `SessionCookie`, a bare `T::Struct` with `name`, `value`, `expires` — no signature, no HMAC, no binding to a secret: [3](#0-2) 

`SessionCookie::SESSION_COOKIE_NAME` is a public constant (`"shopify_app_session"`), and the cookie's `http_only`/`secure` flags (set by the host app per the docs) only prevent JavaScript access from a browser — they do nothing to stop a non-browser HTTP client (curl, a script, a proxy tool) from sending an arbitrary `Cookie` header value directly in a request. Because `current_session_id` trusts this raw value as the lookup key into the app's session store (per the documented pattern in `docs/getting_started.md` and `docs/usage/oauth.md`), an unprivileged user who knows or guesses a target shop's domain (`*.myshopify.com` domains are guessable/enumerable, and many are publicly known storefront names) can present `Cookie: shopify_app_session=offline_target-shop.myshopify.com` to the app. The gem returns that exact string as the "current session id" without any proof that the request actually originated from a session that Shopify authorized for that shop.

This directly matches the target bug class: **a session id derived from unauthenticated bytes** — the "bytes" here being the client-supplied cookie header, which the gem treats as authoritative shop-session-selection input despite never validating it against anything cryptographic (unlike the JWT/HMAC-backed paths in the same file, e.g. `session_id_from_shopify_id_token`, which do verify a signed token before deriving an id).

### Impact Explanation
If the host application follows the gem's documented pattern (call `current_session_id`, then look up the corresponding stored `Session` — which holds the real Shopify access token — and use it to serve the request), an attacker can force the app to select and act under another merchant's session purely by supplying a guessed cookie value. This is a session fixation / cross-tenant access primitive: the attacker's unauthenticated request is bound to a victim shop's stored access token, enabling the attacker to view or trigger API calls scoped to the victim's shop through the app. This lands squarely in the specified High-impact category: "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is high for offline sessions specifically, since `offline_#{shop}` requires no secret knowledge beyond the shop domain, which is either publicly discoverable (storefront URLs) or trivially enumerable. No credentials, access tokens, or `client_secret` are needed — only the ability to send an HTTP request with a custom `Cookie` header, which is available to any unprivileged internet user with a non-browser HTTP client.

### Recommendation
Do not use a client-suppliable, unsigned, deterministic value as the sole session-lookup key. Sign/HMAC the cookie value (or wrap it in a signed cookie jar, e.g. Rails' signed cookies) so `cookie_session_id` can verify authenticity before returning an id, or bind the returned id to a value that cannot be derived without possessing a previously-issued, server-generated secret (as is already done for the JWT-based `session_id_from_shopify_id_token` path).

### Proof of Concept
1. Determine or guess a target shop's domain, e.g. `victim-shop.myshopify.com` (many are publicly discoverable via storefront URLs).
2. Send any request to the host app's protected route with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged and unverified: [4](#0-3) 
4. Following the documented pattern, the app retrieves the stored `Session` for that id (containing the victim's real access token) and proceeds to serve/act on the attacker's request as if it were the victim's authenticated session.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
