### Title
Webhook shop identity is not bound to the HMAC-authenticated payload, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the shop identity that the framework hands to app-supplied webhook handlers (`request.shop`) is read from an unauthenticated HTTP header. Since the HMAC secret (`Context.api_secret_key`) is the same for every shop installed on a multi-tenant app, any shop that has completed OAuth can obtain a genuinely-signed `(body, hmac)` pair from its own webhook deliveries and replay it to the app's webhook endpoint with a forged shop-domain header, causing the app to process the payload as belonging to a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, which becomes the tenant identifier passed downstream, is parsed straight from the `X-Shopify-Shop-Domain` header and is never included in the signed string: [2](#0-1) 

`Registry.process` verifies only the body/HMAC pair, then immediately trusts `request.shop` to build the metadata delivered to the app's handler: [3](#0-2) 

`HmacValidator.validate` performs `OpenSSL.secure_compare` of the computed HMAC over `to_signable_string` (body only) against the received HMAC, using `Context.api_secret_key`, which is a single, app-wide secret shared by all shops that have the app installed: [4](#0-3) 

The equality this design should enforce is:
`shop_that_the_HMAC_proves_authorship_for == request.shop (header used for tenant routing)`

That equality does not hold: the HMAC only proves "this body was signed with the app's shared `api_secret_key`" (i.e., it came from *some* installed shop, or was replayed by one), not "this body came from the shop named in the headers." Because `api_secret_key` is not shop-specific, a malicious merchant who has installed the app can:
1. Trigger any webhook on their own store (e.g. `customers/data_request`, `customers/redact`, `app/uninstalled`, `orders/create`) and capture the genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends them.
2. Replay that exact body+HMAC to the app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate(request)` succeeds because it never inspects the shop header.
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop` set to the victim's domain while `body` is attacker-controlled content from the attacker's own shop.

### Impact Explanation
Because per-tenant webhook handlers in the documented usage pattern key their side effects (data updates, session/token revocation, GDPR redaction, uninstall bookkeeping) off `WebhookMetadata#shop`, an attacker-controlled payload can be attributed to a shop the attacker does not own. This is a cross-tenant integrity/confidentiality break: the attacker can inject or overwrite data associated with another merchant's tenant record (e.g., forging an `app/uninstalled` or `customers/redact` event against a victim shop, or writing attacker-chosen order/product data into the victim's tenant state) purely by controlling headers on a replayed, still-validly-HMAC'd request — without ever needing the victim's credentials, `api_secret_key`, or access token. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (a) being a merchant who has legitimately installed the target app (no special privilege beyond normal app installation), (b) capturing one of their own genuine webhook deliveries (trivial — install the app, trigger any topic), and (c) sending an HTTP POST to the app's public webhook endpoint with a modified shop header. No cryptographic secret needs to be broken since the shared `api_secret_key` HMAC is satisfied by replaying an already-valid signature; only the unsigned header is forged. This is straightforward for any unprivileged internet user who can install the target app (many apps have open/self-serve installation).

### Recommendation
Bind the shop identity into the HMAC-signed material, or otherwise cryptographically tie it to the verified session/installation record, before it is trusted for tenant routing:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `Request#to_signable_string`, e.g. by validating against a per-shop stored secret/session lookup instead of (or in addition to) the raw body, so a forged shop header invalidates the HMAC.
- Alternatively, have `Registry.process` cross-check `request.shop` against a shop that is known to be currently installed/authorized for this specific webhook `webhook_id`/subscription (e.g., verify against Shopify's registered subscription for that shop) rather than trusting the header verbatim.
- Document clearly (and enforce in the gem, since host apps depend on `WebhookMetadata#shop` for tenant scoping) that the shop header is unauthenticated relative to the current signing scheme, or fix the signing scheme so it is authenticated.

### Proof of Concept
Conceptual PoC (illustrates the missing binding; requires no secrets beyond a legitimate self-installation of the target app):
```ruby
# Attacker installs the target app on their own store "attacker-shop.myshopify.com"
# and triggers, e.g., an `app/uninstalled` webhook, capturing:
raw_body = '{"...attacker-controlled uninstall/redact/order payload..."}'
hmac_header = "<genuine X-Shopify-Hmac-Sha256 signed with the shared api_secret_key>"

# Attacker replays it to the app's webhook endpoint, forging the shop header:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_header,     # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com"
#    even though the payload originated from and was signed for attacker-shop.
```
I was not able to inspect `lib/shopify_api/webhooks/webhook_handler.rb` in detail (only match counts were retrieved, not file contents) or the exact `WebhookMetadata` field usage by real-world handlers; this PoC and impact analysis rely on the documented contract that `shop` in `WebhookMetadata` is the tenant-identifying field passed to app-supplied handlers, as shown in `Registry.process`.
