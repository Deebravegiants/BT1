This confirms the vulnerability. `Registry.process` at [1](#0-0)  validates the HMAC over `request` and then unconditionally passes `request.shop` — derived purely from the unauthenticated `shopify-shop-domain` header ( [2](#0-1) ) — into `WebhookMetadata`, which the host app's `handler.handle` uses to identify the tenant. The HMAC itself only covers `@raw_body` ( [3](#0-2) ), never the `shop-domain` header, so the field that binds the webhook to a specific merchant tenant is completely outside the signed content.

### Title
Webhook tenant binding (`shop-domain` header) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (merchant identity) is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and never included in the signed payload. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier passed to the host application's webhook handler.

### Finding Description
The intended binding for a webhook should be: `shop` (tenant) == `shop` covered by HMAC(secret, payload). In this gem that equality does not hold:

- `Request#hmac` reads the `hmac-sha256` header and decodes it. [4](#0-3) 
- `Request#shop` reads the `shop-domain` header, completely independent of the HMAC. [2](#0-1) 
- `Request#to_signable_string` returns only `@raw_body`. [3](#0-2) 
- `Utils::HmacValidator.validate_signature` recomputes the signature over `to_signable_string` (i.e. body only) using `Context.api_secret_key`, and compares it with the `hmac` header via `OpenSSL.secure_compare`. [5](#0-4) 
- `Registry.process` calls `Utils::HmacValidator.validate(request)`, and — provided that check passes — immediately builds `WebhookMetadata` using `request.shop`, which is handed to the app's `WebhookHandler#handle`. [1](#0-0) 

Because the HMAC only authenticates the body bytes, not the `shop-domain` header, any entity that possesses one valid `(body, hmac)` pair for the app's webhook secret — for example, the operator of any shop that has installed the app and legitimately receives webhooks with valid HMACs — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The signature check still passes because it never inspected the header, and the app's handler receives a `WebhookMetadata` claiming an attacker-chosen shop identity while actually processing attacker-supplied body content that was only ever authenticated for the attacker's own shop.

This is directly analogous to the reported class of bug: the abstraction (`HmacValidator`/`VerifiableQuery`) hides that the field the caller ultimately trusts for identity (`shop`) is disjoint from the field verified by the cryptographic check (raw body only), exactly like the report's "PaymentExitGame accepts a `txType` it never actually checks" issue — here, the webhook processing pipeline accepts a `shop` value it never actually authenticates.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook processing: an app relying on `WebhookMetadata#shop` (as documented/intended usage of this gem's webhook registry) to route data or scope database writes per merchant can be tricked into attributing attacker-controlled webhook content to a victim shop, or vice versa, enabling cross-tenant data injection/confusion without any access token or `client_secret` leakage — only a validly-signed webhook from any shop that has installed the app (which the attacker can obtain simply by installing the app on their own store, an ordinary unprivileged action). This qualifies as Critical (cross-tenant access) under the given impact criteria.

### Likelihood Explanation
Likelihood is high: obtaining a legitimate `(body, hmac)` pair requires nothing more than installing the app on any shop (a normal, unprivileged action available to any internet user) and capturing one of its own inbound webhook deliveries. No secret material, no access token, and no host cooperation beyond normal SDK usage is required — the header can be freely rewritten by the attacker's HTTP client before forwarding to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the value that is cryptographically verified, not just into a side-channel header trusted after the fact. Concretely:
- Include the shop domain (and other identity-bearing headers) in `Request#to_signable_string`, or
- Have `Registry.process` cross-check that the shop implied by any out-of-band mechanism matches an app-side expectation (e.g., a known/registered shop for that webhook subscription) before dispatching to `handler.handle`, and document clearly that `WebhookMetadata#shop` is not itself authenticated by the HMAC so host apps do not mistakenly rely on it as a trust boundary.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) so Shopify sends a POST to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and a JSON body.
2. Capture the raw `body` and `X-Shopify-Hmac-Sha256` value.
3. Replay the exact same `body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `request.to_signable_string` (the body only) and it matches, so validation passes at `lib/shopify_api/webhooks/registry.rb:190`.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the host app's `handler.handle`, which now processes attacker-controlled webhook content under the identity of `victim.myshopify.com`.
