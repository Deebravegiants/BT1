### Title
Webhook `shop` (and `topic`) header is trusted for tenant attribution while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which HMACs only `request.to_signable_string` (the raw body). The `shop` (and `topic`) values that are subsequently handed to the app's webhook handler as the tenant identifier are read straight from HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are outside this signable string: [2](#0-1) 

`HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` (the raw body) using the app's shared `api_secret_key` and compares it with the `hmac` header: [3](#0-2) 

`Registry.process` performs no further binding check between the validated body and the claimed `shop`/`topic` — it trusts the header values directly to build the object passed to the app's handler: [4](#0-3) 

Because `api_secret_key` is a single shared secret for the entire app (not per-shop), and the HMAC covers only the request body (never `shop-domain`), the binding `hmac == HMAC(secret, shop || body)` that a caller might assume does **not** hold. In reality the binding is only `hmac == HMAC(secret, body)`, decoupled from `shop`. Any body/HMAC pair that is valid for one shop is equally valid, unmodified, for a `shop-domain` header claiming to be a different shop, since the shop value plays no part in the signature.

### Impact Explanation
An attacker who is an ordinary (non-privileged) internet user can install the target app on their own store — a normal, unprivileged action for any public/embedded Shopify app — and thereby receive genuinely Shopify-signed webhook deliveries containing valid `(raw_body, hmac)` pairs computed with the app's `api_secret_key`. Because that secret is shared across every install of the app (it is not shop-specific), the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Registry.process` will still accept it (`HmacValidator.validate` only checks the body) and will invoke the app's handler with `WebhookMetadata` claiming to originate from the victim shop: [5](#0-4) 

For webhooks whose body content is predictable, low-entropy, or fully attacker controlled from a legitimate install (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or topics with minimal/empty bodies), this allows the attacker to make the app believe an action (uninstall, data-deletion, GDPR redaction, etc.) occurred for a shop the attacker does not own — a cross-tenant impersonation that can trigger destructive or state-changing logic keyed off the `shop` value the handler receives, without possessing that victim's access token or credentials.

### Likelihood Explanation
Exploitability depends on the app's webhook endpoint being reachable from the internet (standard for webhook receivers) and on the attacker being able to obtain at least one genuine `(raw_body, hmac)` pair by legitimately installing the app on their own store — both are realistic, low-privilege prerequisites. The harder part is finding a topic/body combination whose content is generic enough to be replayed meaningfully against a different shop (e.g., empty-body or fixed-shape topics); this narrows practical impact but does not eliminate it, since several mandatory/compliance topics have small, predictable payload shapes.

### Recommendation
Bind the webhook's tenant identity into the verified material instead of trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`) header values in the HMAC-signed content the library validates, or
- After HMAC validation, require the caller/host app to verify that `request.shop` corresponds to a shop that has an active, stored session/installation for this app before invoking the handler, and document this as a mandatory step in `Registry.process`.
- At minimum, update `docs/usage/webhooks.md` and `Registry.process` to make explicit that `request.shop` is unauthenticated and must be cross-checked against known installed shops before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify sends a genuine webhook, e.g. `app/uninstalled`, to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC of raw_body with shared api_secret_key>`
   - Body: `{}` (or another fixed/predictable payload for that topic)
3. Attacker records the raw body and its `hmac-sha256` value.
4. Attacker crafts a new HTTP request to the same webhook endpoint with the identical raw body and `hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) raw body against the shared secret: [6](#0-5) 
6. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the app to process an uninstall (or other topic-specific) event attributed to `victim-shop.myshopify.com`, even though the victim never sent this webhook and the attacker holds no credentials for that shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
