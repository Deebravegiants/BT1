### Title
Webhook HMAC only covers the request body, not the `shop-domain`/`topic` headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while `shop` and `topic` — the fields the gem hands to the app's webhook handler as the trusted tenant identifier — are taken from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, bytes_that_determine_tenant_and_action)`. In this gem it instead holds only:

`hmac == HMAC(secret, raw_body)` ≠ `HMAC(secret, raw_body + shop-domain + topic)`

`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Request#shop`/`Request#topic` are read straight from the `shopify-shop-domain`/`shopify-topic` headers with no cryptographic tie to the body or to the HMAC [2](#0-1) . `HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. only the body [3](#0-2) . `Registry.process` nonetheless trusts `request.shop` as the tenant identity it hands to the app's handler: it validates the HMAC, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it [4](#0-3) . This is the documented, intended usage of the gem, not host-application misuse.

Because a single `api_secret_key` is shared across every shop that installs the app, any shop owner (an "unprivileged" tenant relative to other merchants) can legitimately trigger a real webhook on their own store and thereby obtain a body+HMAC pair that Shopify signed with the app's shared secret. That attacker fully controls the `shop-domain` and `topic` headers on replay to the app's webhook endpoint, since neither is covered by the signature.

### Impact Explanation
An attacker (a legitimate installer of the app, but unprivileged with respect to other tenants) can take a validly-signed webhook body from their own store and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain (and/or the `shopify-topic` header changed). `HmacValidator.validate` still passes because it only checks the body bytes. The app's registered handler then receives `WebhookMetadata` claiming the event belongs to the victim shop, with attacker-chosen JSON content and topic. This is cross-tenant data injection/spoofing — the app processes attacker-controlled data as if it originated from, and pertains to, a different merchant's shop.

### Likelihood Explanation
Any user who can install the app on their own store (a standard, low-privilege action) can obtain a genuine body/HMAC pair and replay it with forged headers to the shared webhook endpoint. No access to `api_secret_key`, tokens, or victim credentials is required — only standard use of the gem's documented `Registry.process`/`WebhookMetadata` flow, which is the exact validation path shipped in this library.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the signed material that `HmacValidator` checks, or otherwise cryptographically bind the header values to the verified payload before constructing `WebhookMetadata`. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for cross-request identity unless those values are covered by the HMAC computation.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`) on their own store, capturing the raw POST body and the `shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it's computed with the same shared `api_secret_key`.
2. Attacker resends this exact body and `hmac-sha256` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and optionally a different `shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the payload never originated from or was authorized for that shop [5](#0-4) .
