### Title
Missing relayer gate in the Tron `IntentGatewayV2.onAccept` reintroduces the forged-handler-swap route the mainline EVM fix closed - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
NATS-Server's bug was that ACL enforcement, applied broadly to message subjects, was silently skipped in one namespace (`$MQTT.>`), letting an unprivileged client bypass authorization there. The analogous gap in Hyperbridge is that the relayer-authorization check added to the mainline EVM `IntentGatewayV2`/`ExtrinsicIntents` delivery path was never applied to the Tron deployment of the same contract, leaving that "namespace" (the Tron chain instance) permanently open to the exact attack the mainline fix was written to close.

### Finding Description
On mainline EVM, `ExtrinsicIntents.onAccept` runs `_checkRelayer(incoming.relayer)` before any request body is even decoded: [1](#0-0) 
This gate exists specifically to defend against a forged consensus update swapping the host's `handler` for a malicious contract that reports an attacker-controlled address as the relayer on every delivery (documented directly in the project's own decision log): [2](#0-1) 
and reiterated in the delivery-flow write-up: a delivery from anyone but the authorised relayer "never decodes the body, never runs `_authenticate`, and leaves no receipt." [3](#0-2) 

The Tron contract `evm/tron/contracts/apps/IntentGatewayV2.sol` implements the same `onAccept` dispatch (`RedeemEscrow`/`RefundEscrow`/`NewDeployment`/`UpdateParams`/`SweepDust`) but has no `_relayer` state, no `_checkRelayer`, and no `setRelayer`/`migrate` machinery at all — only `onlyHost` and, for escrow actions, `authenticate(incoming.request)` (a source-module check), and for governance actions, a bare `request.source == hyperbridge` check: [4](#0-3) 
Grepping the whole `evm/tron/contracts` tree confirms `relayer`/`_relayer`/`checkRelayer`/`restrict(` never appear outside this one file, and no `HostManager.sol` equivalent exists in the Tron contract set either — the relayer-gating pattern that was retrofitted onto `HostManager.sol` and `ExtrinsicIntents.sol` on mainline was not carried over to the Tron deployment target.

### Impact Explanation
If the Tron ISMP host's consensus client or handler is ever compromised/forged (the same threat model the mainline fix targets), an attacker can deliver a `SetHostParam`-style handler swap or otherwise get an arbitrary "relayer" address accepted through `dispatchIncoming`, and `IntentGatewayV2.onAccept` on Tron has no second check to fall back on: any address delivering a message that passes `onlyHost` and the source/module checks is honored. This directly threatens `RedeemEscrow`/`RefundEscrow` withdrawals of escrowed order funds — concrete theft of user-escrowed tokens — with no relayer-identity check standing between a forged delivery and the fund-moving `withdraw` call.

### Likelihood Explanation
Exploitation requires a forged consensus/handler-swap primitive on the Tron ISMP host — the same precondition the mainline `HostManager`/`ExtrinsicIntents` fix was built for, so it is not a trivial single-transaction bug on its own, but it is a real, currently-unpatched regression: the security property mainline chains now have is absent on Tron, and the gap is a straightforward code-omission (a whole class of protection missing in one deployment target while present in another), which is exactly the kind of ACL-namespace-scoping mistake the source report describes.

### Recommendation
Port the `_relayer` / `_checkRelayer` / `setRelayer` / `migrate` gate (and the corresponding `HostManager` relayer restriction) from the mainline `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/src/core/HostManager.sol` into the Tron contract set (`evm/tron/contracts/apps/IntentGatewayV2.sol` and its host-manager equivalent), so the Tron deployment enforces the same relayer authorization on every `onAccept`/`onGetResponse` path before decoding the body.

### Proof of Concept
Not independently reproducible from the index alone (no local test harness for the Tron contracts was found in the indexed files); the gap is established by direct comparison of `onAccept` implementations: [5](#0-4)  vs. [4](#0-3) , plus the mainline Foundry test that demonstrates the attack the gate blocks on mainline (`testForgedHandlerSwapIsRefused`), which has no Tron counterpart: [6](#0-5)

        _checkRelayer(incoming.relayer);

        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));

# 2026-09-03 — `HostManager` deliveries are gated too, and that does not touch permissionless relaying

Chosen: `HostManager.onAccept` refuses any relayer but the one the host admin set, zero included.

The app gates check an address the host reports, and the host takes it from its handler. The
handler is a host parameter that a `SetHostParam` governance message can replace, and until now
any relayer could deliver that message once its consensus proof verified. Under a forged consensus
an attacker would swap in a handler that reports the whitelisted relayer on every message, and the
app gates would pass. Gating the HostManager closes that route.

It does not weaken the open-relayer model because the HostManager never carries user traffic. Its
first check already rejects anything not sourced from Hyperbridge, so the only messages it ever
sees are Polytope's own `Withdraw` and `SetHostParam`. Third-party relayers keep delivering every
ordinary message to every ordinary app exactly as before.

    function testForgedHandlerSwapIsRefused() public {
        MaliciousHandler malicious = new MaliciousHandler();
        HostParams memory params = host.hostParams();
        address honestHandler = params.handler;
        params.handler = address(malicious);
        PostRequest memory swap = _setHostParamRequest(params);

        // Delivered by the attacker (through the honest handler, proof assumed forged).
        vm.prank(address(handler));
        host.dispatchIncoming(swap, OUTSIDER);
        assertEq(host.hostParams().handler, honestHandler, "handler unchanged");

        // The attacker's contract is not the handler, so it cannot inject a relayer address.
        PostRequest memory forged = _setHostParamRequest(host.hostParams());
        vm.expectRevert(EvmHost.UnauthorizedAction.selector);
        malicious.deliver(EvmHost(payable(address(host))), forged, address(this));
    }
