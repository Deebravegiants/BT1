### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, but the tenant-identifying `shop`, `topic`, `webhook_id`, and `api_version` fields — which are read straight from unauthenticated HTTP headers — are handed to the webhook handler as trusted metadata without being covered by that HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `HmacValidator.validate` computes/compares the HMAC solely against this signable string: [2](#0-1) .

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from HTTP headers with no cryptographic binding to the body: [3](#0-2) .

`Registry.process` uses `Utils::HmacValidator.validate(request)` (body-only check) to gate execution, then dispatches based on `request.topic` and forwards `request.shop` into `WebhookMetadata` as the trusted tenant/shop identifier passed to the app's handler: [4](#0-3) .

The identity binding that should hold is: `shop header value == shop the HMAC was computed for`. Because the HMAC covers only `@raw_body`, this equality is never enforced — any `(raw_body, hmac)` pair that is valid for *some* shop/topic combination remains valid for *any* other `shop-domain`/`topic`/`webhook-id` header value an attacker chooses to send, since `OpenSSL.secure_compare(computed_signature, received_signature)` only checks that the *body* bytes match what was signed, independent of headers.

### Impact Explanation
This is a cross-tenant confusion vector: an unprivileged holder of one legitimate `(body, hmac)` pair (e.g., a merchant using the app who receives real webhooks for their own shop, or any attacker who can observe one valid webhook delivery for the app) can resend that exact body and HMAC to the app's webhook endpoint while forging `x-shopify-shop-domain` to name a *different* shop and/or `x-shopify-topic` to a *different* registered topic. Because `HmacValidator.validate` passes (body bytes are unchanged), `Registry.process` will invoke the topic's handler with `WebhookMetadata.shop` set to the attacker-chosen shop and process attacker-controlled body content as if it legitimately originated from that shop/topic combination. Host applications that key persistence, authorization, or business logic off `WebhookMetadata.shop`/`.topic` (which is the gem's documented, intended usage) will attribute the payload to the wrong tenant — a cross-tenant data/action confusion.

### Likelihood Explanation
Moderate. The attacker needs at least one valid `(raw_body, hmac)` pair, which is trivial to obtain if the attacker is itself a merchant with the app installed (any of their own real webhook deliveries qualify, since the HMAC is over the body only and doesn't encode which shop/topic it belongs to). No access to `api_secret_key` or any token is required — only a previously observed legitimate webhook delivery for the same app.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable material (or otherwise cryptographically tie the header values to the payload before trusting them), or, at minimum, document/enforce that host applications must not treat `WebhookMetadata.shop`/`.topic` as authenticated unless independently validated against a per-shop registration/allowlist.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, with raw body `B` and valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's secret).
2. Attacker replays a request to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different registered `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and the attacker-supplied body content, even though this body never actually originated from `victim-shop`.
