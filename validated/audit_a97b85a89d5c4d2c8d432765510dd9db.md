## Title
Unbounded `U128` multiplication in `calc_take_pnl` can panic and permanently freeze LP deposits/withdrawals when attacker-inflated vault balances are used - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl`, invoked by `process_deposit`, `process_withdraw` and `process_withdrawpnl`, multiplies the live token-vault balances (`total_pc_without_take_pnl` / `total_coin_without_take_pnl`) using `U128::checked_mul(..).unwrap()`. These balances are read directly from the SPL vault accounts, which any unprivileged actor can inflate via a plain SPL token transfer (no AMM-program interaction is required). If the product of the two balances exceeds `U128::MAX`, `checked_mul` returns `None` and the subsequent `.unwrap()` panics, aborting the transaction. Because the panic is triggered purely by reading the current vault balances (which the attacker keeps inflated forever), every future call to Deposit, Withdraw and WithdrawPnl for that pool will panic identically, permanently freezing LP funds in that pool — the same “balance-dependent revert causing DOS” bug class as the reported `LinearDistributor.declareReward` issue, but reachable through vault-donation instead of buffer forfeiture.

### Finding Description
`calc_take_pnl` is the central PnL-accrual routine shared by Deposit, Withdraw and WithdrawPnl: [1](#0-0) 

The two pool-side quantities fed into the unchecked multiplication come straight from `calc_total_without_take_pnl_no_orderbook`, which is just `vault.amount - need_take_pnl`, i.e. it tracks the *actual* SPL token account balance minus a bookkeeping deduction: [2](#0-1) 

Both `amm_pc_vault.amount` and `amm_coin_vault.amount` are unpacked directly from the raw SPL token account state, e.g. in `process_deposit`: [3](#0-2) 

and in `process_withdraw`/`process_withdrawpnl`: [4](#0-3) [5](#0-4) 

Because vault token accounts are just standard SPL accounts owned by the AMM authority PDA, **anyone** can increase their `amount` field with an ordinary `spl_token::instruction::transfer` sent from outside the AMM program (e.g. a pool creator minting/transferring their own custom token supply into their pool's vaults, or any user donating tokens to an existing pool). The AMM program never validates that the vault balance stays within a range that keeps `pool_pc_amount * pool_coin_amount` inside `U128` bounds before calling `calc_take_pnl`.

When `pool_pc_amount.checked_mul(pool_coin_amount)` overflows `U128` (product ≥ 2^128), `.unwrap()` panics at line 190 of `processor.rs`. Since this computation is re-derived from the current, attacker-controlled vault balances on every invocation, the panic recurs on every subsequent Deposit, Withdraw, and WithdrawPnl call for that pool — a permanent Denial of Service, exactly analogous to the reported bug where a donation-inflated balance permanently broke a `require`/assert.

### Impact Explanation
Once triggered, `calc_take_pnl` panics unconditionally for the affected pool on:
- `process_deposit` (LP deposit blocked, `program/src/processor.rs:1166-1173`)
- `process_withdraw` when the pool is not in `WithdrawOnly` status (`program/src/processor.rs:1740-1748`)
- `process_withdrawpnl` (protocol PnL sweep blocked, `program/src/processor.rs:1495-1502`)

This permanently freezes further deposits and (for non-`WithdrawOnly` pools) withdrawals of LP funds for that pool, since the vault balances that trigger the overflow cannot be reduced through any normal instruction (swap does not touch `calc_take_pnl`, and the very instructions that could rebalance/withdraw are the ones that panic). This matches the reported bug class: fund availability itself is not directly stolen, but LP capital in the affected pool becomes permanently inaccessible via the documented program interface.

### Likelihood Explanation
The attack is unprivileged and requires only a single SPL `transfer` CPI into the pool's coin/pc vault plus one subsequent Deposit/Withdraw/WithdrawPnl call to confirm the panic — reachable by any pool creator or any actor who can move a large balance into a vault (e.g. minting a custom token with near-`u64::MAX` supply for a self-created pool, or targeting a pool paired with a token whose mint authority the attacker controls). It requires reaching a product of vault balances exceeding `U128::MAX` (~3.4×10^38), which requires both vault balances to be on the order of `2^64` raw units simultaneously — feasible for pools involving attacker-minted/high-supply SPL tokens, but not for typical low-decimal, low-supply pairs, which limits generality and justifies a Medium rather than Critical/High rating (in line with the judge's downgrade of the analogous report to Medium).

### Recommendation
- Replace the unchecked `checked_mul(..).unwrap()` in `calc_take_pnl` (`program/src/processor.rs:190-191`) with a `checked_mul(..).ok_or(AmmError::CalcPnlError)?` (or equivalent saturating/graceful-error handling) so an overflow returns a program error instead of panicking.
- More generally, avoid deriving critical invariant checks directly and solely from externally-mutable SPL token account balances without bounding/sanity-checking them against expected pool state (e.g., compare against `target_orders`/`AmmInfo` tracked amounts, or clamp/reject balances outside a safe range) so that a single unsolicited transfer into a vault cannot permanently disable Deposit/Withdraw/WithdrawPnl for that pool.

### Proof of Concept
1. Attacker creates two SPL mints (or reuses one attacker-controlled mint) and creates a Raydium pool via `Initialize2` pairing them, becoming the pool creator.
2. Attacker mints/transfers ~`u64::MAX`-scale raw token amounts of both the coin and pc mint directly into the pool's `amm_coin_vault` and `amm_pc_vault` token accounts via plain `spl_token::instruction::transfer` calls (no AMM instruction needed).
3. Attacker (or anyone) calls `Deposit`, `Withdraw`, or `WithdrawPnl` on this pool. `calc_total_without_take_pnl_no_orderbook` (`program/src/math.rs:238-250`) returns the inflated balances, and `calc_take_pnl`'s `pool_pc_amount.checked_mul(pool_coin_amount).unwrap()` (`program/src/processor.rs:190`) overflows `U128` and panics, aborting the transaction.
4. Because the vault balances remain inflated (no instruction path exists to reduce them without first succeeding through the now-panicking Deposit/Withdraw/WithdrawPnl paths), every future call to these three instructions for this pool panics identically — a permanent DOS freezing LP capital in the pool.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
