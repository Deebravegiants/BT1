Confirmed: `ShopValidator` is not used in the webhook `Request` class at all—`shop` is only validated for format in OAuth/token-exchange flows, not for webhooks, and it is never bound into the HMAC signature computed in `Utils::HmacValidator`.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with `WebhookMetadata`, including `shop`. In reality, `Utils::HmacValidator.validate` only authenticates the raw HTTP body; the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly off the unauthenticated headers and passed straight through to the handler with no cryptographic binding to the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from headers that are never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac-sha256` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` uses this validation as the sole authenticity gate, then forwards the unauthenticated `shop` header straight to the application handler: [4](#0-3) 

The equality the code implicitly claims to hold is:
`bytes_verified_by_HMAC == bytes_the_handler_treats_as_the_authenticated_tenant_identity`

In fact `bytes_verified_by_HMAC = raw_body` while `bytes_the_handler_trusts_as_tenant = shop-domain header`, which is disjoint from the signed content. Unlike the OAuth `AuthQuery`, which explicitly folds `shop` into `to_signable_string` before hashing: [5](#0-4) 

the webhook `Request` has no equivalent binding for `shop`. Because every webhook for a given app is signed with the same app-level `api_secret_key` regardless of which shop triggered it, any entity that can obtain one valid `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own store and capturing a delivered webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because it never inspects the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (forged) shop as the source: [6](#0-5) 

The gem's own documentation tells implementers that `Registry.process` "will verify the request did indeed come from Shopify," which reasonably implies the whole tuple (shop, topic, body) is authenticated — not merely the body — making this a genuine breach of the library's documented guarantee rather than a misuse of an undocumented API contract.

### Impact Explanation
Any app that uses `data.shop` from `WebhookMetadata` as the authoritative tenant key when persisting or acting on webhook data (the pattern shown in the gem's own `docs/usage/webhooks.md` example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be tricked into attributing another merchant's data mutation, or writing attacker-controlled data under another shop's tenant record, purely by spoofing the `shop-domain` header while replaying a validly-signed body captured from the attacker's own installation. This is a cross-tenant identity confusion at the trust boundary the gem is documented to enforce.

### Likelihood Explanation
Exploitation requires the attacker to obtain one legitimate `(raw_body, hmac)` pair for the target app, which is trivially available to anyone who installs the app on their own (free) development store and captures a delivered webhook — no access to `api_secret_key`, tokens, or the target merchant's credentials is needed. The attacker then only needs to send an HTTP POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header, since that field is not covered by the HMAC.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string` for webhook `Request`, or alternatively require `Registry.process`/app code to verify that the `shop` header corresponds to a shop with an active, previously-registered session/webhook subscription before invoking the handler, rather than trusting the header as an authenticated value derived from the HMAC check alone.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker triggers the webhook and captures the delivered request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared `api_secret_key`).
3. Attacker POSTs to the same app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because HMAC only covers `B`)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Body: `B` (unchanged)
4. `Utils::HmacValidator.validate` returns `true` since it only recomputes the HMAC over `B`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e. the app processes attacker-controlled data as though it came from `victim-shop`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
