## Analysis

The `FxUSDBasePool.requestRedeem` bug class is: a party registers/commits to an action now, waits out a mandatory delay, then executes the action later at a moment of their choosing — with no expiry forcing them to re-register against current conditions. This lets someone lock in a stale, favorable state and cash in on it whenever it benefits them.

Hyperbridge's Intent Gateway has the structurally identical exposure in its solver-fill flow, and the team's own design notes for `evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/IntentsBase.sol` describe it almost verbatim: a solver signs a bid (`fillOrder` calldata) once, and after that has "no further say in when it is used" — the order's `deadline` is controlled by the placer with no upper bound, so "without a bound here they may sit on a signed bid and execute it whenever the price has moved in their favour." [1](#0-0)  The mainline fix was to add `FillOptions.validUntil`, a block-number bound checked at fill time in `fillOrder`. [2](#0-1) [3](#0-2) 

Searching for `validUntil` across the whole indexed codebase, every reference is confined to `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/*`, `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`, and their associated SDK/ABIs/tests — `evm/tron/contracts/apps/IntentGatewayV2.sol` does not appear in that result set at all, even though it defines its own `FillOptions` struct, `fillOrder`, `onAccept` (RedeemEscrow/RefundEscrow), and `onGetResponse` logic mirroring the mainline contract. [4](#0-3)  This strongly indicates the Tron deployment never received the `validUntil` bound that was added to the EVM contracts specifically to close this bug class.

### Title
Tron IntentGatewayV2 fillOrder lacks a bid-freshness bound, letting a signed fill be executed at an arbitrarily favorable later time - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The mainline `IntentGatewayV2.fillOrder` enforces `FillOptions.validUntil` so a solver's signed fill cannot be replayed indefinitely after market conditions move against the solver. This was a deliberate fix for exactly the "waiting can be gamed" bug class. The Tron variant of the contract does not appear to carry this field or check, based on codebase-wide search for `validUntil`.

### Finding Description
A solver "signs" a fill (via a `UserOperation`/session-key selection or a direct `fillOrder` call) committing to specific output amounts for an order. Once signed, only `order.deadline` (set by the order placer, with no upper bound) constrains when the fill can land on-chain; the solver has no further say. Anyone holding that signed fill payload can wait and submit it at the moment most favorable to them (e.g., after the underlying asset price moves), extracting value from the solver who is contractually locked into stale pricing. The mainline fix adds `validUntil`, a solver-controlled block-number bound checked in `fillOrder`, explicitly to close this window. [2](#0-1)  The Tron contract's `fillOrder`/`FillOptions` does not surface in any `validUntil` search hit across the repo, suggesting the equivalent bound is missing there. [4](#0-3) 

### Impact Explanation
If confirmed, this allows theft of value from solvers filling orders on the Tron deployment: a malicious order placer (or anyone who captures a signed bid) can delay submission of a fill until price movement makes the solver's committed output disadvantageous, forcing the solver to deliver at a stale, unfavorable rate while the counterparty benefits — a direct, reachable-by-unprivileged-transaction fund-extraction path, matching the report's "redemption waiting can be gamed" pattern applied to intent settlement instead of pool redemption.

### Likelihood Explanation
Medium-to-High if the gap is real: any solver or relayer submitting fills through the Tron IntentGatewayV2 is exposed passively, with no special privilege needed by the attacker beyond holding/observing a signed bid and choosing when to submit the transaction (or an order placer choosing when to reveal a captured session-signed selection).

Have a background Devin session directly read `evm/tron/contracts/apps/IntentGatewayV2.sol` in full to confirm whether `FillOptions` (or its Tron equivalent) has a `validUntil`/freshness bound and whether `fillOrder` checks it.     function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

struct FillOptions {
    /// @dev The fee paid in feeTokens to the relayer for processing transactions.
    uint256 relayerFee;
    /// @dev The fee paid in native tokens for cross-chain dispatch.
    uint256 nativeDispatchFee;
    /// @dev Last block number at which this fill may be executed. Zero means no bound.
    ///
    /// @dev A solver bidding through the coprocessor signs this calldata and then has no
    /// further say in when it is used: the order's `deadline` is chosen by the placer with
    /// no upper limit, and retracting the bid on Hyperbridge does not reach this chain. The
    /// placer holds the session key, so without a bound here they may sit on a signed bid
    /// and execute it whenever the price has moved in their favour. Setting this caps how
    /// long the quoted price stands.
    ///
    /// @dev Denominated in blocks, matching `order.deadline`, so both are read against the
    /// same clock (`_blockNumber()`, which is the L2 block number where that differs).
    uint256 validUntil;
    /// @dev The output tokens with amounts the solver is willing to give
    /// @dev Must be strictly >= the amounts requested in order.output.assets
    TokenInfo[] outputs;
}

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
