### Title
Decimal-scaling underflow in `pallet-hyper-fungible-token`'s ERC20 amount conversion causes unbacked over-minting on the destination chain when a registered token's EVM decimals are lower than its local decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token::send` is a signed, permissionless extrinsic that lets any user burn/escrow a local asset and dispatch an ISMP `POST` that instructs a peer `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint tokens to a recipient. The amount carried in that message is produced by `convert_to_erc20`, which scales the local balance to the registered EVM decimals for that `(asset, destination)` pair using `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent [1](#0-0) . Because `saturating_sub` on `u8` clamps to `0` instead of allowing a negative exponent, any token pair where the registered EVM decimals are *lower* than the local asset's decimals silently skips scaling down (multiplies by `10^0 = 1`), inflating the message amount by `10^(local_decimals - erc_decimals)`. That inflated `amount` is minted verbatim on the destination EVM contract via `_mint(beneficiary, message.amount)` [2](#0-1) , producing tokens with no backing escrow — the same class of bridge loophole ("wrong-direction/ missing decimal scaling in a cross-chain token bridge") referenced in the Umbrella/ChainSwap incident.

### Finding Description
The pallet stores per-`(asset, destination chain)` EVM decimals in `Precisions` and treats the local asset's decimals independently (native currency uses `T::Decimals`, other assets use `fungibles::metadata::Inspect::decimals`) [3](#0-2) . Nothing in `register_token`/`update_token` or in `send` enforces `erc_decimals >= local_decimals`.

`send()` computes the outbound amount with:
```rust
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
``` [4](#0-3) 

and `convert_to_erc20` is defined as:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [5](#0-4) 

When `erc_decimals < local_decimals` (e.g. a local `pallet-assets` token configured with 18 decimals bridged to an EVM contract configured with 6 decimals, mirroring common assets like USDC/USDT), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the function multiplies by `1` instead of dividing by `10^(local_decimals - erc_decimals)`. The raw, unscaled local-precision value is dispatched as the ISMP message `amount` and delivered unchanged to `onAccept` on the destination chain, which mints it directly with no further scaling [6](#0-5) . This mints `10^(local_decimals - erc_decimals)` times more tokens than the user actually escrowed/burned.

The reciprocal function `convert_to_balance`, used on `on_accept`/`on_timeout` for inbound EVM→substrate messages, has the same asymmetric flaw (`erc_decimals.saturating_sub(local_decimals)` also clamps to 0 in the same misconfiguration direction), causing severe under-crediting on that side instead [7](#0-6) [8](#0-7) .

### Impact Explanation
This is a direct, unbacked-mint vulnerability reachable from a single signed extrinsic (`send`) by any unprivileged holder of a misconfigured asset — no relayer, admin, or governance action required beyond the initial (legitimate-looking) `register_token`/`update_token` configuration that sets `erc_decimals < local_decimals` for some chain pair. Once such a pair exists, every `send()` call amplifies the minted amount on the destination EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract by a fixed decimal factor, letting an attacker drain the wrapped-token's backing supply (in `WrappedHyperFungibleToken`, minted claims exceed the actual escrowed ERC20/WETH) or create unlimited non-native supply (in plain `HyperFungibleToken`). This satisfies "unbacked mint" / concrete theft criteria.

### Likelihood Explanation
Requires only a token registration where the EVM-side registered decimals are lower than the local asset's decimals — a realistic configuration mistake since many EVM stablecoins use 6 decimals while substrate assets commonly default to 12 or 18. Once registered, exploitation needs nothing more than calling the public `send` extrinsic, so likelihood is high for any deployment that bridges a token whose decimals differ in this direction.

### Recommendation
Fix the scaling helpers to handle both directions symmetrically, e.g. compute the signed decimal delta and either multiply or divide accordingly instead of relying on `u8::saturating_sub`, and/or add an invariant check in `register_token`/`update_token` that documents and validates the expected decimals relationship (or supports both directions explicitly) so an amount is never silently left unscaled.

### Proof of Concept
1. `register_token` a non-native asset with `local_decimals = 18` (e.g., a `pallet-assets` asset) and `Precisions[(asset, destChain)] = 6` (as if bridging to an EVM contract using USDC-like 6 decimals).
2. Any signed user calls `send(SendParams { asset_id, destination: destChain, amount: 1_000_000_000_000_000_000 /* 1.0 token, 18 decimals */, .. })`.
3. In `send`, `erc20_amount = convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)`. Since `6u8.saturating_sub(18) = 0`, `erc20_amount = 1e18 * 10^0 = 1e18` (raw units), instead of the correct `1e18 / 10^12 = 1_000_000` (1.0 token at 6 decimals).
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken.onAccept`, which executes `_mint(beneficiary, 1e18)` [2](#0-1)  — minting 1,000,000× more tokens than the 1.0 token that was actually escrowed/burned on the source chain.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
