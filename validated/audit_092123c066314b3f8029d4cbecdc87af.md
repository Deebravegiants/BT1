## Title
Webhook shop identity is not authenticated by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` identity delivered to the application's webhook handler comes from the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header. Because the app's API secret is shared across every shop that installs the app, anyone who can obtain one genuine `(body, hmac)` pair from Shopify (e.g., by triggering a webhook on their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header. `HmacValidator.validate` will report success because it never binds the header-derived shop to the signed bytes.

Note `to_signable_string` returns `@raw_body` only — the `shop` accessor (`shopify_header("shop-domain")`) is never included in the bytes that are HMAC-verified: [3](#0-2) 

`Registry.process` then hands this unauthenticated `shop` value straight to the host application's handler as the trusted tenant identifier: [4](#0-3) 

This is exactly the identity-binding break called out in the rules: "a shop authenticated versus the shop stored as a session key." The HMAC proves *the body bytes* were produced with the app's secret, but it proves nothing about *which shop* the request is claimed to originate from — that comes from an attacker-controlled header. Since one API secret is shared by the app across all merchant installations, any merchant/attacker who installs the app on their own store can legitimately trigger a webhook, capture the `(raw_body, hmac)` pair the app's own secret produces, and then POST that identical body+HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The verification in `HmacValidator.validate` still returns `true` because it only checks body integrity against the shared secret, not shop provenance.

### Impact Explanation
This breaks the tenant boundary: `authenticated_bytes(secret, body) == authenticated_bytes(secret, body)` holds for any shop using the same app, but the library treats the header-supplied `shop` as trustworthy scoping information passed into `WebhookMetadata`. A host application that persists/acts on webhook data keyed by `data.shop` (the documented and expected usage pattern) can be made to apply attacker-influenced webhook payloads (e.g., order/customer data the attacker fully controls on their own store) under a victim shop's identity — i.e., cross-tenant data injection/confusion, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on their own Shopify store (standard, unprivileged action available to any merchant/developer), (2) the attacker triggers a webhook whose body they control, capturing the resulting HMAC, and (3) the attacker replays that request directly to the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged credential is needed — only participation as a normal, unprivileged Shopify merchant/app installer, which satisfies the "unprivileged internet user" analog requirement.

### Recommendation
Bind the claimed shop to the HMAC-verified content. Options: (a) require and validate the shop against the destination shop from the resolved session/token used by the app rather than trusting the raw header, or (b) have `Webhooks::Request#to_signable_string` (or an additional verification step in `Registry.process`) incorporate the `shop-domain` header into the value that is HMAC-checked, or otherwise cross-check that the header-derived shop matches a shop known to be entitled to receive this specific webhook payload before dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and creates an order (or other webhook-triggering resource) with attacker-chosen field values.
2. Shopify delivers a legitimate webhook to the app: raw body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this exact request and replays it to the same app endpoint, changing only the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. In `Webhooks::Request.new`, `shop` is read from the (now forged) header; `to_signable_string` returns the unchanged body `B`. `HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches, per: [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, so the app processes attacker-controlled data as though it belongs to the victim shop.
