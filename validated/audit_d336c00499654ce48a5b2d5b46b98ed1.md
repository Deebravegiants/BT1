### Title
Race condition in Gateway JWT replay-guard allows a single-use HTTP trigger token to authorize multiple workflow runs (TOCTOU) - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize()` is the internet-facing gateway authorization check for HTTP-triggered workflow executions. It is designed so that each signed JWT (identified by its `jti` claim) may authorize exactly one workflow run — a second use of the same JWT must be rejected with "JWT token has already been used." However, the check-then-act sequence (`isReplay()` then, several steps later, `recordUsage()`) is not atomic, creating a TOCTOU race that lets an attacker who can send two requests carrying the same JWT concurrently get both accepted, defeating the single-use guarantee. This is the same underlying bug class as the reported `Staking.unstakeRequestWithPermit()` issue: a check against a consumable, single-use credential (a permit signature / nonce there, a JWT `jti` here) is not atomic with its consumption, so a racing request can slip through the gap.

### Finding Description
`Authorize()` performs the replay check and the "mark used" write as two separate, unsynchronized critical sections protected by different lock scopes inside `jwtReplayCache`: [1](#0-0) 

`isReplay()` takes an `RLock`, checks membership, and releases the lock; `recordUsage()` is only called at the very end of `Authorize()`, after workflow-existence and signer-authorization checks have already been performed: [2](#0-1) 

Because `isReplay()` and `recordUsage()` are independent lock acquisitions rather than one atomic "check-and-set" operation, two concurrent calls to `Authorize()` carrying the identical JWT (same `jti`) can both execute `isReplay()` and both observe "not yet seen" before either one reaches `recordUsage()`. Both requests then pass authorization and are forwarded to `httpTriggerHandler.authorizeRequest` → `sendWithRetries`, triggering the workflow twice from a token that was only meant to authorize a single execution.

This directly mirrors the reported bug class: a consumable, single-use authorization artifact (permit signature/nonce in the original report, JWT `jti` here) is checked and then consumed in two non-atomic steps, so a second concurrent/racing use can slip through the window between check and consumption. The `duplicate request ID` and `duplicate JWT token and request ID` tests only cover *sequential* reuse, not concurrent reuse, so this race is not exercised by the existing test suite: [3](#0-2) [4](#0-3) 

Note also that `Authorize()` reads `h.authorizedKeys[workflowID]` without holding `h.mu` at all, which is a separate concurrency concern on top of the JWT race, but the JWT single-use bypass is the concrete, security-relevant issue.

### Impact Explanation
An attacker (or a buggy/malicious client, or simply two nearly-simultaneous submissions of the same captured JWT) can cause a single, single-use authorization token to trigger a workflow execution more than once. Since HTTP-triggered workflows can move funds, call external systems, or perform other side effects, duplicate unauthorized execution from one credential is an "unauthorized job run" — the gateway's core authorization invariant (`one JWT == one run`) is broken. This also undermines the DoS/anti-replay protection the `jwtReplayCache` was specifically built to provide.

### Likelihood Explanation
Exploitation requires the ability to submit two requests bearing the same JWT to the gateway at (or near) the same time — trivial for anyone in possession of a valid signed JWT for a workflow trigger, since the race window is a small but real gap between two independently-locked map operations spread across the length of `Authorize()`. No cryptographic breaking is required; only ordinary request concurrency.

### Recommendation
Make the "check for replay" and "mark as used" operation atomic under a single lock acquisition (e.g., a `CheckAndRecord`-style method on `jwtReplayCache`, analogous to the pattern already used in `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`), so that no two goroutines can observe "not yet used" for the same `jti` simultaneously.

### Proof of Concept
1. Register a workflow and its authorized signer key as in `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate JWT token and request ID" setup.
2. Sign a single JWT-bearing HTTP trigger request (`req.Auth = createTestJWTToken(...)`).
3. Instead of calling `handler.HandleUserTriggerRequest` sequentially (as the existing test does), spawn two goroutines that call `handler.workflowMetadataHandler.Authorize(workflowID, token, req)` concurrently with the same `req`/token, synchronizing them so both execute `isReplay()` before either executes `recordUsage()` (e.g., by adding a short sleep between the `isReplay` check and `recordUsage` call for the purposes of the PoC, or running many iterations under `go test -race` to observe both calls returning success).
4. Observe that both calls to `Authorize()` return `(key, nil)` instead of the second one returning the expected "JWT token has already been used" error, confirming the same single-use JWT authorized two separate workflow trigger sends.

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

```go
		handler, mockDon := createTestTriggerHandler(t)
		privateKey := createTestPrivateKey(t)
		registerWorkflow(t, handler, workflowID, privateKey)
		callback1 := hc.NewCallback()

		triggerReq := gateway_common.HTTPTriggerRequest{

			},
			Input: []byte(`{"key": "value"}`),

		require.NoError(t, err)

		rawParams := json.RawMessage(reqBytes)

			Version: "2.0",
			ID:      requestID,
			Method:  gateway_common.MethodWorkflowExecute,
			Params:  &rawParams,
		}
		// First request should succeed
		req.Auth = createTestJWTToken(t, req, privateKey)
		mockDon.EXPECT().SendToNode(mock.Anything, mock.Anything, mock.Anything).Return(nil).Times(3)
		err = handler.HandleUserTriggerRequest(t.Context(), req, callback1, time.Now())
		require.NoError(t, err)

		// Second request with same ID should fail
		req.Auth = createTestJWTToken(t, req, privateKey)
		err = handler.HandleUserTriggerRequest(t.Context(), req, callback2, time.Now())
		require.Error(t, err)
		require.Contains(t, err.Error(), "in-flight request")
```
