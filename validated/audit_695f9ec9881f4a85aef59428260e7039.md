Confirmed root cause: `ShopifyAPI::Auth::TokenExchange.exchange_token` derives `dest_shop` straight from the session-token's `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling credential-issuing method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before building the `Session` used for the outbound request.

### Title
Unsanitized `dest` claim from session token used as request host in `TokenExchange.exchange_token`, allowing SSRF with app's `client_id`/`client_secret` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `dest` claim of a JWT session token, strips only the `https://` prefix via `JwtPayload#shop`, and uses that raw string directly as the `Session#shop` value that `Clients::HttpClient` turns into the outbound request's host. Every other credential-exchange method in the same module/sibling modules (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly calls `Utils::ShopValidator.sanitize!` to constrain the shop value to a Shopify-trusted domain before doing this. `exchange_token` skips that call entirely.

### Finding Description
The binding that should hold is: `host that receives client_id/client_secret == a domain in Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

In `exchange_token`: [1](#0-0) 
`dest_shop = jwt_payload.shop` is used unsanitized to build `shop_session`, which is passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`. `JwtPayload#shop` only does `@dest.gsub("https://", "")`: [2](#0-1) 
— no validation that `dest` resolves to a `*.myshopify.com`/`myshopify.io`/etc. domain.

`HttpClient` then builds the request host directly from `session.shop`: [3](#0-2) 

The `dest` claim only needs to satisfy `JWT.decode(...)` signature/exp/nbf/aud checks and `aud == Context.api_key`: [4](#0-3) 
None of those checks constrain the *value* of `dest` to a Shopify domain — they only prove the token was signed with the app's own `api_secret_key` and targets this app's `api_key`. The library's threat model treats `dest`/session tokens as attacker-influenced input requiring sanitization — that's exactly why `Utils::ShopValidator` was introduced and wired into `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`, but the wiring was missed in `exchange_token`.

Contrast with the correctly-guarded sibling: [5](#0-4) 
which sanitizes `shop` before constructing the exact same kind of `HttpClient`/`Session` pair that leaks `client_id`/`client_secret` in the POST body.

### Impact Explanation
If a session token's signing key is ever the app's own secret (the normal case; the host app is expected to pass it through from Shopify's embedded-app JS bridge, but the JWT's `dest` field itself is not otherwise constrained by Shopify's signature to be a legitimate shop domain) and the resulting `dest` value is attacker-influenced or malformed (e.g. a shop record replaced during a migration, or the host application forwarding a manipulated `dest`/token from an untrusted flow), `exchange_token` will POST `client_id` and `client_secret` in JSON body to whatever host is embedded in `dest`. This is SSRF carrying the app's own OAuth credentials to an attacker-controlled host — matching the report's underlying bug class (an identity/host binding assumed but not actually enforced), which lets credentials leak to a domain that was never checked against the trusted Shopify domain list that the rest of the codebase enforces.

### Likelihood Explanation
Medium: `dest` is protected by JWT signature/`aud` checks, so exploitation requires a scenario where the host application obtains or forwards a `dest` value that isn't itself already constrained to a real Shopify shop (e.g. multi-tenant apps that mint or relay their own session tokens, or any deviation from Shopify's strict embedded-app token issuance). It is not trivially exploitable by a pure unauthenticated internet user without some such intermediary condition, but the missing sanitization is a real gap relative to the rest of the codebase's explicit defensive pattern.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` the same way `migrate_to_expiring_token` does:
```ruby
dest_shop = ShopifyAPI::Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
before constructing `shop_session`, ensuring the `client_id`/`client_secret` are only ever sent to a domain in `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is `https://attacker.example` (or any non-Shopify host) but which is otherwise validly signed with the app's `api_secret_key` and has `aud == Context.api_key` (e.g., a host application that mints its own JWTs for internal token-exchange flows, or a compromised upstream that forwards a manipulated `dest`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns `"attacker.example"` unmodified.
4. `Clients::HttpClient` builds `@base_uri = "https://attacker.example"` and POSTs `{client_id, client_secret, grant_type, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, leaking the app's `client_id`/`client_secret` to the attacker-controlled host.
