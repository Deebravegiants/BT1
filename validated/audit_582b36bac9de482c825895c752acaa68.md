### Title
Webhook `shop` (and `topic`) header trusted for tenant identification while the HMAC signature only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw HTTP headers, but its `to_signable_string` method — which is what `Utils::HmacValidator` actually authenticates — returns only the raw request body. This means the `shop` value that `Registry.process` hands to the app's webhook handler as the tenant identifier is never covered by the HMAC that "validates" the request, exactly mirroring the reported bug class of a value being acted on that isn't bound by its supposed integrity check.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC over exactly that signable string and compares it to the `hmac` header: [2](#0-1) 

But `Request#shop` and `Request#topic` are read straight from attacker-controllable headers, never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately uses the unauthenticated `request.topic` to select the handler and passes the unauthenticated `request.shop` straight into `WebhookMetadata`, which is the tenant identity the host app's handler code will act on: [4](#0-3) 

The intended binding is: **shop attribution used by the handler == shop bound by the HMAC-verified bytes**. In reality: **HMAC-verified bytes == raw body only**, while **shop attribution == `shop-domain` header**, an entirely separate, unsigned channel. Since a Shopify app's `client_secret` (and therefore the webhook-signing secret) is shared across every shop that has installed the app, any shop owner who has installed the app can capture one legitimate `(raw_body, hmac)` pair from their own store's webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` (and/or `topic`) header swapped to a victim shop. The signature check still passes because it only ever validated the body, so the handler executes believing the event originated from the victim shop.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC check is supposed to enforce: an attacker who legitimately installed the target app on their own store can forge webhook events that the app processes as belonging to a different merchant. Any host application logic that trusts `WebhookMetadata#shop` (e.g., to look up per-shop data, trigger shop-scoped side effects, or drive access-token/session lookups keyed by shop) can be manipulated into acting on the wrong tenant — a cross-tenant access issue.

### Likelihood Explanation
Likelihood is Medium: the attacker only needs to be a legitimate (if unprivileged relative to the victim) installer of the same app on their own shop, capture one webhook delivery, and replay it with a modified `shop-domain` (and/or `topic`) header — no access to the victim's credentials, TLS interception, or the app's `client_secret` is required.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`, `api_version`, `webhook_id`) in the signed material that `to_signable_string` returns, or otherwise bind them cryptographically to the HMAC (e.g., by having `HmacValidator`/`Registry.process` verify that the headers used for routing/attribution are themselves part of the signed payload) so that a valid signature can only be replayed for the exact shop/topic it was issued for.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
2. Attacker resends the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only and it matches `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the registered handler, which now processes an event under the victim's tenant identity despite the request actually having been forged by the attacker.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
