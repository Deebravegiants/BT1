### Title
Webhook shop/topic identity spoofing due to HMAC signature not covering identifying headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, and `webhook_id` values used by `ShopifyAPI::Webhooks::Registry.process` entirely from unauthenticated HTTP headers, while the HMAC signature that the gem validates only covers the raw request body. This breaks the intended identity binding: `shop == the tenant that actually produced/authorized the signed payload`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` — the values used to route and attribute the webhook — are read straight from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` HTTP headers, none of which are included in the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC of the request and then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata` passed to the app's handler, with no cross-check that the signed body actually corresponds to that shop or topic: [4](#0-3) 

Concretely, the equality the gem is supposed to enforce is:
`shop claimed in header == shop that Shopify actually generated/signed this payload for`

But the HMAC only proves:
`bytes verified (raw_body) == bytes signed by client_secret`

It says nothing about which shop or topic the signature was intended for. Any party that can produce (or replay) a validly-signed body/HMAC pair — trivially available to any merchant with the app installed on their own store, since Shopify sends them a real signed webhook — can pair that same body+HMAC with an arbitrary `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` header set and the gem's `Registry.process` will accept it as valid and dispatch it to the handler as if it came from the spoofed shop/topic.

### Impact Explanation
This is a cross-tenant identity-binding bypass in the gem's own webhook verification logic (not a host-application misuse issue): `Registry.process` is the gem-provided, documented entry point for webhook handling, and it hands the handler `WebhookMetadata` whose `shop` field has no cryptographic binding to the verified bytes. Any downstream logic that uses `data.shop` to scope state per merchant (a normal and expected pattern, since that's the field's entire purpose) can be made to act on shop B's tenant context while being fed attacker-controlled body content that was only ever signed for shop A. This matches the Critical "cross-tenant access" impact category, since the vulnerability is in the trust boundary the gem itself establishes for identifying which tenant a webhook belongs to.

### Likelihood Explanation
Exploitation requires only that the attacker control (or previously receive) one legitimately-signed webhook body/HMAC pair for their own shop — something any merchant who installs the app can obtain — and the ability to send an HTTP request with modified headers to the app's webhook endpoint. No access token, `client_secret`, or privileged credential is required, and the header-swap can be done by any unprivileged internet-capable actor once they have a valid installation.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., derive/validate shop identity from a source that is itself covered by the signature) so that `Registry.process` cannot be fed a validly-signed body under a spoofed shop/topic identity.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a real webhook with a valid `shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
2. Attacker captures this `{raw_body, hmac}` pair.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`).
4. `Webhooks::Request.new` accepts the headers (only checks presence, not binding), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — this succeeds because the body/HMAC pair is genuinely valid.
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...))`, causing the app to process attacker-supplied content under the victim shop's identity. [4](#0-3)
