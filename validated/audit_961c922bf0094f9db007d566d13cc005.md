### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then constructs a `WebhookMetadata` object whose `shop` field is taken directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header. Because that header is never part of the signed material, an attacker who possesses one legitimately-signed webhook payload (e.g., from their own store) can replay it with a different `shop-domain` header value and have it accepted as authentic for an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC-SHA256 signature against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body — the `shop` accessor is derived from a separate header and is not included in the signable string at all: [2](#0-1) [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` to build the metadata handed to the app's handler, with no additional binding between the body's HMAC and the shop identity: [4](#0-3) 

The identity binding that should hold is: `shop (authenticated by HMAC) == shop (acted upon by the handler)`. Since the HMAC only signs the body bytes and the `shop` value comes from an unsigned header, this equality does not hold — the header can be swapped freely while keeping a genuine, valid signature+body pair from a completely different (attacker-controlled) shop. `WebhookMetadata` propagates this untrusted `shop` value verbatim to every app-level webhook handler: [5](#0-4) 

### Impact Explanation
Any consuming application that uses `WebhookMetadata#shop` to select which merchant's session/data record a webhook body should be applied to (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be tricked into associating attacker-supplied webhook content with an arbitrary victim shop domain. Since the attacker only needs one valid HMAC/body pair from a shop they control (their own store, or any store whose webhook they can observe) to forge webhooks that appear to originate from any other tenant, this breaks the app's tenant isolation — a cross-tenant confusion whereby data ostensibly from Shop A is processed under Shop B's identity. This satisfies the Critical "cross-tenant access" impact category, since the boundary that is supposed to separate one merchant's data/events from another's is not actually enforced by the cryptographic check the gem performs.

### Likelihood Explanation
The attack requires no privileged credentials: an unprivileged actor with any live shop connected to the app (or any captured/replayed genuine webhook body+HMAC pair) can send a raw HTTP POST directly to the app's webhook endpoint with a forged `x-shopify-shop-domain` header, because the gem's `Registry.process` performs no cross-check between the header and the signed body — it only verifies the HMAC is valid for the body content, an operation the attacker can trivially satisfy using a webhook they legitimately received.

### Recommendation
Include the shop domain (and other webhook headers such as topic, api-version, webhook-id) in the HMAC-signed material, or otherwise separately authenticate the `shop-domain` header against a trusted table of shops with active app installations before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should reject webhooks whose `shop` does not correspond to a shop known to have installed the app, rather than passing an unauthenticated header value straight through to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook for a topic the app handles; captures the raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` against the app's `client_secret`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and dispatches it to the registered handler, which now processes attacker-controlled body content under the victim's identity: [7](#0-6)
