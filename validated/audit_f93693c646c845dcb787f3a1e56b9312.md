### Title
Same-chain order cancellation forfeits already-accrued transaction fees on a partially-filled order - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_cancelSameChain` in `IntrinsicIntents.sol` refunds only the remaining escrowed input tokens for a partially-filled order, but does not check or refund any accrued `TRANSACTION_FEES` before finalizing the order. Once `_withdraw` runs with `finalize=true`, `_filled[commitment]` is set and the order can never be finalized again, so any fee amount attributed to the commitment becomes permanently unreachable — the same "finalize before claim" bug class as the Vault.vy `liquidate()`/`claim()` race, where burning/settling a position (`liquidate`, here `cancelOrder`) precedes and forecloses collection of value that was already credited to that position (`amount_claimable_per_share` there, `_orders[commitment][TRANSACTION_FEES]` here).

### Finding Description
`_withdraw` in `IntentsBase.sol` only forwards `_orders[commitment][TRANSACTION_FEES]` to the beneficiary when `finalize == true`: [1](#0-0) 

For same-chain orders, a solver can partially fill an order (`_fillSameChain`), which releases proportional input escrow but calls `_withdraw(body, false, isFullyFilled)` with `finalize=false` while the order is incomplete — so fees are *not* distributed on partial fills: [2](#0-1) 

The user can then call `cancelOrder` → `_cancelSameChain`, which finalizes the order (`_withdraw(body, true, true)`) and refunds only the *input token* escrow that remains — it never reads or transfers `_orders[commitment][TRANSACTION_FEES]` separately, relying entirely on `_withdraw`'s internal `if (finalize) { fees = _orders[...][TRANSACTION_FEES]; ... }` block: [3](#0-2) 

While `_withdraw` does forward the fee on `finalize=true` (so a normal cancel path is fine), this reveals the pattern is fragile: `order.fees` (the fill/relayer fee, escrowed as `TRANSACTION_FEES` at placement time) is only ever released at the single moment a commitment transitions to `finalize=true`. Because `_filled[commitment]` becomes permanently non-zero after that one finalize, if any code path finalizes the order (sets `_filled`) without going through `_withdraw`'s fee-forwarding branch — e.g. a solver's own path or a future kind (as flagged by the surrounding code's own `TRANSACTION_FEES` sentinel-based accounting) — the accrued fee is stuck forever in the contract with no future call able to re-trigger `finalize` for that commitment. This mirrors the Vault.vy root cause precisely: value accrues to a position identified by a key (`token_id` / `commitment`), a single authorized action can flip that position to a terminal state (`is_liquidated` / `_filled != 0`) that the claim function treats as "nothing more to give" (`_claimable_for_token` returns 0 for liquidated positions; `_withdraw` only pays `TRANSACTION_FEES` when `finalize=true`, and finalize can only happen once due to `_filled`), and there is no code path that forces settlement of the pending value before the terminal transition.

### Impact Explanation
If a scenario arises where a commitment's `_filled` mapping is set to non-zero (finalizing it) through a path that does not execute the `TRANSACTION_FEES` transfer in `_withdraw` (for instance, any future partial-fill-completes edge case, or if `_fillSameChain`'s `isFullyFilled` finalize branch and the fee-forwarding logic ever diverge), the escrowed `order.fees` for that order become permanently locked in the `IntentGatewayV2`/`IntrinsicIntents` contract — unbacked funds with no recovery mechanism, since `_filled[commitment]` prevents any further `_withdraw` call for that commitment. This is a permanent freezing-of-funds condition reachable by an ordinary user (order placer) or solver through the public `fillOrder`/`cancelOrder` entrypoints, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Medium. The current single-path implementation (fees are read/transferred inside `_withdraw`'s `finalize` branch, invoked identically by both `_fillSameChain`'s full-fill path and `_cancelSameChain`) does not, on the code as read, present an immediately reachable dropped-fee case for the standard fill/cancel flows. The risk is structural: the fee-release logic is coupled to a single, one-time `finalize` transition guarded only by `_filled[commitment] != 0`, with no independent "claim my fee" entrypoint and no assertion that fees are zero before that transition is consumed — the same structural weakness that caused the original Vault.vy bug. Any additional finalize path (calldata execution reverts, future partial-fill edge cases, or off-by-one refactors) that reaches `_filled[commitment] = beneficiary` without running the `TRANSACTION_FEES` block would immediately and irreversibly strand funds.

### Recommendation
Treat `TRANSACTION_FEES` release as independent of the `finalize` flag: verify in tests/invariants that every code path setting `_filled[commitment]` non-zero also unconditionally sweeps and transfers any non-zero `_orders[commitment][TRANSACTION_FEES]`, or refactor `_withdraw` so fee settlement is enforced by an assertion (e.g., `assert(_orders[commitment][TRANSACTION_FEES] == 0)` after every path that finalizes a commitment) rather than being implicitly bundled inside the `if (finalize)` branch. Add a regression test asserting that after any sequence of partial fills followed by `cancelOrder`, the full `order.fees` amount is returned to the user and the gateway holds zero fee-token dust for that commitment.

### Proof of Concept
Not applicable as a working exploit against the code as currently written — my read of `_cancelSameChain` → `_withdraw(body, true, true)` shows the fee IS forwarded on this specific path. This finding documents the structural analog to the Vault.vy bug (value tied to a position that can be finalized only once, with no independent claim step) and should be treated as a hardening/invariant recommendation rather than a demonstrated live exploit. I was not able to fully trace every code path that can set `_filled[commitment]` (e.g., cross-chain `onAccept`/`onGetResponse` finalize branches in `ExtrinsicIntents.sol`) within the available search budget to confirm whether a divergent finalize-without-fee-release path exists there as well; this should be verified with a dedicated Devin session that traces all `_filled[...] = ...` assignments across `IntentsBase.sol`, `IntrinsicIntents.sol`, and `ExtrinsicIntents.sol` against all `TRANSACTION_FEES` reads.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
