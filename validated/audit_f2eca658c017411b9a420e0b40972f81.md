### Title
Webhook `shop`, `topic`, and `webhook_id` are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers. Those header values are never included in the HMAC computation, so the identity binding "HMAC-verified bytes == data acted upon" is broken: the signature proves the *body* came from Shopify (signed with the app's shared `api_secret_key`), but proves nothing about which shop, topic, or webhook the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled straight from headers and are not part of the signed material: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever checks `verifiable_query.to_signable_string` against the HMAC secret: [3](#0-2) 

`Registry.process` uses this validator as the sole authentication gate, then immediately trusts the unauthenticated header fields to build `WebhookMetadata` and route to the app-registered handler: [4](#0-3) 

By contrast, the OAuth `AuthQuery` (used for the callback HMAC) *does* fold the identity-relevant field (`shop`) into the signed string: [5](#0-4) 

This is exactly the class of bug described in the report: a field ("shop"/tenant identity) that is acted upon by downstream logic but not covered by the HMAC that is supposed to authenticate the message. The equality that should hold is:

`shop bound by HMAC == shop dispatched to handler`

but the implementation only guarantees:

`body bound by HMAC == body dispatched to handler`

while `shop`, `topic`, and `webhook_id` are asserted purely from attacker-controllable headers.

### Impact Explanation
Because `api_secret_key` is a single shared secret across all shops that install a given app, any merchant who installs the app receives genuine `(body, hmac)` pairs for their own shop's events. Since the HMAC never binds `shop` (or `topic`/`webhook_id`), that merchant (an otherwise unprivileged, non-credentialed actor with respect to any other tenant) can replay the same valid `(body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to impersonate a different, victim shop. `Registry.process` will pass HMAC validation (body signature is intact) and hand the handler a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` with attacker-controlled body content. Any app logic that trusts `data.shop` for tenant-scoped operations (looking up sessions, updating per-merchant records, crediting/debiting, triggering merchant-specific side effects) can be manipulated into acting on behalf of, or against, a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Moderate-to-high: the webhook receiver endpoint is by design internet-reachable and unauthenticated beyond the HMAC check. Obtaining one valid `(body, hmac)` pair requires nothing more than installing the app on any shop (a normal, low-privilege action, not requiring `api_secret_key` or any victim credential), after which the header substitution and replay is trivial to script.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`) in the signed/verified material, or otherwise cryptographically bind them to the body (e.g., verify HMAC over a canonical string containing shop+topic+webhook_id+body, mirroring how `AuthQuery#to_signable_string` incorporates `shop`). At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for dispatch/authorization decisions unless those fields are covered by the verified HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, and captures a legitimate webhook delivery, e.g. body `{"id":1,...}` with header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, body)`), per `HmacValidator.validate_signature`: [3](#0-2) 
2. Attacker resends the same raw body and the same `x-shopify-hmac-sha256: H` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the raw body: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` where `shop == "victim.myshopify.com"` even though the body/topic never originated from Shopify for that shop: [7](#0-6)
