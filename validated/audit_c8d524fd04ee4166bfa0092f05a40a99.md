### Title
Webhook shop/topic/id identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that identify *which tenant and event* the payload belongs to are read from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The tenant-identifying fields are pulled straight from headers, independent of the signature: [2](#0-1) 

`Registry.process` only checks that the HMAC over the body is valid, then immediately trusts `request.topic` and `request.shop` (plus `webhook_id`/`api_version`) to build the data passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes/compares the signature purely against `verifiable_query.to_signable_string` (the raw body for webhooks) and the app's `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` is shared across *all* shops that install a given app (it is not per-shop), any shop that installs the app receives legitimately Shopify-signed webhooks whose HMAC is valid for that same secret. An attacker who controls one shop (an ordinary, unprivileged app installer — not a privileged account, and without ever needing to know the `api_secret_key`) can capture one of their own legitimately-signed webhook deliveries and replay it against the app's public webhook endpoint after changing the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. The HMAC check still passes because it only verifies the untouched body, not the headers. `Registry.process` then dispatches to the handler with `WebhookMetadata#shop` set to the victim's domain, breaking the identity binding `signed_shop == acted_upon_shop`.

Downstream host applications (per this gem's own documented pattern, e.g. `docs/usage/webhooks.md`) commonly use `data.shop` to look up the merchant's stored session/access token and to attribute/write data for that shop. A forged `shop` header therefore lets one merchant impersonate another merchant's webhook events, causing the host app to act on/associate attacker-supplied body content with the victim tenant — a cross-tenant confusion driven entirely by this gem's failure to bind the header-derived tenant identity to the HMAC-verified payload.

### Impact Explanation
This breaks the equality that should hold: `hmac_verified(body) ⇒ shop_header is authentic for that body`. In practice, the signature only proves "some shop's api_secret_key produced this body," not "this body belongs to the shop named in the headers." Any app that keys shop-scoped logic (session lookup, database writes, deduplication) off `WebhookMetadata#shop`/`#topic`/`#webhook_id` is exposed to cross-tenant event injection, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only an ordinary, low-privilege capability: install the target app on any shop (something an unprivileged internet user/merchant can normally do), capture one legitimate webhook delivery, and resend it with a modified shop/topic header to the public webhook endpoint — no possession of `api_secret_key`, no TLS interception, and no privileged account needed.

### Recommendation
Bind the tenant-identifying headers into the signed material, e.g., include `shop`, `topic`, and `webhook_id` in the HMAC computation (or require the host app to separately verify the shop against its own installation record before trusting `WebhookMetadata#shop`), matching Shopify's guidance to always confirm the webhook's shop domain corresponds to an installed shop before processing.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) so Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Capture the raw request: body `B`, and headers including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Replay the exact same body `B` and HMAC `H` to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`); `Registry.process` then calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never originated from that shop.
