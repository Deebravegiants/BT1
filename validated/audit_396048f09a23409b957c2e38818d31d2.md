Audit Report

## Title
Full JSON-RPC request (including the `Auth` bearer token) is logged unredacted at Debug/Info level in the Vault gateway handlers - (File: `core/services/gateway/handlers/vault/handler.go`, `core/capabilities/vault/gw_handler.go`)

## Summary
`core/services/gateway/handlers/vault/handler.go:403` logs the entire `jsonrpc.Request[json.RawMessage]` struct via `"request", req` at Debug level, and `core/capabilities/vault/gw_handler.go:182` and `:231` similarly log `"req", req` at Debug and the full response at Info. The `Request` struct's `Auth` field is populated directly from the client-supplied `Authorization: Bearer <token>` header, so when structured logging serializes the whole request object, the raw bearer token is written to the log stream in plaintext.

## Finding Description
The `Auth` field on `jsonrpc.Request` carries the client's bearer JWT, confirmed by its consistent use elsewhere as `req.Auth != ""` in boolean-only log statements in `core/capabilities/vault/authorizer.go:99-118`, and by `req.Auth = token` assignment patterns referenced from JWT-auth test helpers. Every other logging call site in the vault authorization pipeline (`authorizer.go`, `jwt_based_auth.go`, `gateway_vault_request_processor.go`) deliberately avoids logging the raw request/token and instead logs only `"hasAuth", req.Auth != ""` or derived claims — establishing that the redaction convention is a recognized security control in this codebase. The two call sites in question bypass that convention entirely by passing the full `req` object (which a structured JSON/console logger will serialize field-by-field, including `Auth`) directly to `Debugw`/`Infow`. The existing regression test `TestVaultHandler_InvalidParamsDoesNotLogRawParams` in `handler_test.go` explicitly notes in its own comment that it excludes "the pre-existing whole-request Debug log" from its assertions — meaning this exact log line was known to developers and left unaddressed rather than fixed, confirming the gap was not accidental oversight caught by existing tests.

## Impact Explanation
Disclosure of `req.Auth` in logs allows anyone with access to debug-level logs (log aggregation, journald, shipped logs, support bundles) to obtain the raw bearer JWT used to authenticate vault secret operations (`vault.secrets.create/update/delete/list`) for a given `workflowOwner`/`orgID`. Since the authorization layer treats a valid token as sufficient proof of caller identity, capturing it enables impersonation of that caller for secret create/update/delete/list operations — this maps to the in-scope "key/secret exfiltration" and "node API authentication/role bypass" impact categories.

## Likelihood Explanation
The only precondition is that the node/gateway operator has `Log.Level` set to `debug` — a supported, documented configuration mode (not a misconfiguration outside normal operation), as seen in the codebase's own test fixtures that set `Log.Level = 'debug'`. Once that log level is active, any unprivileged external client sending a normal vault JSON-RPC request with an `Authorization: Bearer <token>` header to the gateway's public HTTP endpoint triggers the log write — no special network position or privileged access is required to *trigger* the leak (though reading the resulting log requires log access, which is the actual disclosure vector).

## Recommendation
Redact the `Auth` field before logging the request object at both sites: replace `"request", req` and `"req", req` with a redacted copy (e.g., a shallow copy with `req.Auth = ""`) or with `"hasAuth", req.Auth != ""` plus non-sensitive fields (`method`, `id`), mirroring the pattern already established in `authorizer.go` and `gateway_vault_request_processor.go`. Also review `reqLggr.Infow("Sent message to gateway", "resp", response)` for any sensitive fields in the response payload.

## Proof of Concept
1. Configure a node/gateway with `Log.Level = 'debug'`.
2. As an unprivileged client, send a `vault.secrets.list` (or create/update/delete) JSON-RPC request to the gateway HTTP endpoint with header `Authorization: Bearer <JWT>`.
3. Observe the node's debug log output for the log message `"handling vault request"` emitted at `core/services/gateway/handlers/vault/handler.go:403`, or `"received message from gateway"` emitted at `core/capabilities/vault/gw_handler.go:182` — the serialized `req` field will contain the full `Auth` value (the raw bearer JWT) in cleartext.
4. Write a Go unit test using `logger.TestObserved` (as done in `handler_test.go`) asserting that log entries for `"handling vault request"` / `"received message from gateway"` do not contain the literal token string set on `req.Auth`, and confirm it currently fails.
