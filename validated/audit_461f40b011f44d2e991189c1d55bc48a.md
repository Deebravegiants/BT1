### Title
Webhook Shop-Domain Spoofing via HMAC Scope Gap Enables Cross-Tenant Webhook Attribution - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity (`x-shopify-shop-domain` header) that `ShopifyAPI::Webhooks::Registry.process` uses to attribute the event is read straight from an unauthenticated header. Any party that can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` — which happens for every merchant that installs the app, since all shops share the same app-level HMAC key — can replay that pair to the app's webhook endpoint with an arbitrary `shop-domain` header and have the event accepted and attributed to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor used downstream is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using `request.shop`, `request.topic`, etc., taken from the same unauthenticated headers: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the body — it has no visibility into headers such as shop domain, topic, webhook id, or API version: [4](#0-3) 

The broken identity binding is:
`request.shop` (used to attribute the webhook to a tenant) ≠ `shop that produced the HMAC-signed body` (which the signature actually authenticates).

Because the HMAC key (`client_secret`) is shared across every shop that has installed the app, an unprivileged attacker who installs the app on their own store receives real, validly-signed webhook deliveries for their own shop. Since the signature never covers the `shop-domain` header, the attacker can capture one such `(body, hmac)` pair and POST it to the app's public webhook endpoint with the `shop-domain` header rewritten to name any other merchant using the same app. `Utils::HmacValidator.validate` will accept it because the body/HMAC pair is genuinely valid — it merely doesn't validate whose shop it is. `Registry.process` will then invoke the registered handler with `WebhookMetadata.shop` set to the victim shop, causing the host application to process attacker-controlled webhook content as if it originated from a shop it does not control.

### Impact Explanation
This is a cross-tenant data confusion vector: an app that keys any per-shop logic (e.g., session/access-token lookup, inventory sync, order processing, entitlement changes) off `WebhookMetadata#shop` can be tricked into applying attacker-supplied payload data under a victim shop's identity. Depending on the handler's logic, this can corrupt another tenant's state, trigger unintended actions against the victim's store using the app's access token for that shop, or leak information through the app's response/side effects tied to the spoofed shop — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be an unprivileged user who can install the target app on their own development/test store (a normal, permitted action for any Shopify merchant/developer) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — only a captured legitimate webhook delivery for the attacker's own shop, which arrives automatically via normal app usage.

### Recommendation
Bind the identity fields used for authorization/attribution into the signed material, or otherwise cryptographically tie the `shop-domain` (and ideally `topic`/`webhook-id`) header to the HMAC. Since Shopify's own signature scheme only signs the body, the mitigation belongs in this gem: `Webhooks::Request`/`Registry` should require callers to independently verify that the `shop-domain` in the webhook corresponds to a shop with an active, known session/installation before trusting it, and should document this gap prominently. At minimum, expose a way to reject/flag events whose `shop-domain` does not match an expected value provided by the host application.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) and capture the raw POST: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay the exact same request to the app's webhook endpoint, changing only the header to `x-shopify-shop-domain: victim-shop.myshopify.com` (topic/webhook-id may also be altered as desired).
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` using the shared `client_secret`: [5](#0-4) 
5. `Registry.process` dispatches the registered handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though the event never originated from that shop.
