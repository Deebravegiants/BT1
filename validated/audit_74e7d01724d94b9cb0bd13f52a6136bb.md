This confirms the vulnerability: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC of the body only, then dispatches to the handler using `request.shop` and `request.topic`, which are never covered by the signature [3](#0-2) .

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, but derives the `shop`, `topic`, `webhook_id`, and `api_version` values from HTTP headers that are entirely outside the signature. `Registry.process` trusts these header-derived values to route and label the payload passed to the host app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the expected HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value, both supplied by the `Request` object [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is decoded from the `shopify-hmac-sha256` header [5](#0-4) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) with no cryptographic binding to the body or to each other [2](#0-1) .

`Registry.process` validates only the body HMAC and then calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) . This breaks the intended identity binding: `shop-header-claimed-tenant == HMAC-authenticated-tenant`. In reality, the HMAC only proves "Shopify (or holder of the api_secret_key) produced this exact body bytes at some point"; it proves nothing about which shop, topic, or webhook the body belongs to.

Any user who can get the app to deliver at least one legitimately signed webhook to themselves — e.g., by installing the app on their own development/trial shop (a normal, unprivileged action available to any Partner/merchant) and triggering an event whose body content is shop-agnostic or attacker-influenced (many topics have bodies that are static, predictable, or fully attacker-controlled, e.g. `shop/redact`, `app/uninstalled`, or metafield/webhook payloads with attacker-supplied text fields) — can capture the `(body, hmac)` pair. Because the header fields are unauthenticated, the attacker can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain, or substituting `shopify-topic`/`shopify-webhook-id` to relabel the payload. `Registry.process` will pass HMAC validation (since the body/hmac pair is genuinely valid) and then invoke the handler believing the data originated from the victim shop/topic.

### Impact Explanation
This directly crosses a tenant boundary: an app built on this gem that uses `WebhookMetadata#shop` to key persistence, authorization, or session lookups (a normal and expected usage pattern, since that is the only tenant identifier the gem exposes to handlers) can be made to attribute attacker-supplied webhook data to a different, victim shop. Depending on the handler's semantics this enables cross-tenant data injection/corruption, forced processing of mandatory-compliance webhooks (e.g., spoofing `customers/redact` or `shop/redact` for a shop the attacker does not own) or topic confusion where a payload validated for one topic is processed as another, more sensitive topic. This matches the "cross-tenant access" impact category, since the tenant field (`shop`) that host apps rely on is not bound to the cryptographic proof despite the gem presenting the `shop` field as reliable in `WebhookMetadata`.

### Likelihood Explanation
Reaching the app's public webhook endpoint requires no privileges. Obtaining at least one valid `(body, hmac)` pair is realistic for any attacker who can install the app on a shop they control (a standard, permissionless action for any Shopify Partner) or who can influence the body of a webhook topic whose payload includes attacker-controlled text. No access token, `api_secret_key`, or leaked credential is needed. Because Shopify's real webhook delivery mechanism does not sign the shop/topic headers as part of the documented HMAC computation, and this gem faithfully reproduces that check without any additional binding, every consumer of `Webhooks::Registry` inherits this gap.

### Recommendation
Bind the tenant/topic identity into the signed material that the app trusts, e.g.:
- Cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription the app registered (via a stored mapping from webhook_id → shop) rather than trusting the header value verbatim, or
- Require host apps to independently verify that `request.shop` matches an expected/previously-known shop before acting on the payload, and document this requirement prominently, or
- If Shopify's webhook delivery contract is extended in the future to include headers in the signable string, adopt that scheme in `to_signable_string`.

At minimum, the library should not silently expose `shop`/`topic`/`webhook_id` on `WebhookMetadata` as though they were validated by the HMAC, since `Registry.process` only validates the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and triggers a webhook whose topic delivers a body the attacker controls or that is constant across shops (e.g. an app/uninstalled or a custom app webhook with attacker-editable metafield text).
2. Attacker captures the raw POST: body `B` and header `shopify-hmac-sha256: H`, where `H` is a genuine HMAC-SHA256(`api_secret_key`, `B`) computed by Shopify.
3. Attacker resends the exact same body `B` and header `H` to the app's public webhook endpoint, but changes `shopify-shop-domain` to `victim.myshopify.com` (and optionally `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) , `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) , and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [3](#0-2) , despite the payload never having been produced for or authorized by that shop.
