## Analysis

The reported bug class in M-12 is that a value the protocol *acts on* (the unassigned fee) is not covered by the accounting/binding mechanism (the `earningsAccumulator` update), letting an attacker exploit the mismatch between what's checked and what's used. The directly analogous pattern in this gem is in the webhook verification path: the `shop` identity value that the host application acts on is **not covered by the HMAC signature** that is supposed to authenticate the request.### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the raw request body against the HMAC. `Registry.process` then hands this unauthenticated `shop` value straight to the host application's webhook handler as the tenant identity, without it ever being part of the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string (the body) and compares it against the `shopify-hmac-sha256` header: [2](#0-1) 

Meanwhile, `Webhooks::Request#shop` is read directly from the `shopify-shop-domain` header, which is never part of the HMAC-signed material: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards `request.shop` — the unauthenticated header value — to the app's handler as the authoritative tenant identifier: [4](#0-3) 

This is exactly the identity-binding break called out in the report class: a field that is *acted on* (`shop`, used by the host app to select the tenant/session context) is not *covered by the HMAC* that is meant to authenticate the request. The equality that should hold is:

`shop asserted in header == shop that actually produced the HMAC-signed body`

but nothing in this gem enforces that equality — the HMAC only proves "this body was signed with the app's `api_secret_key` by *some* shop installation," not "this body came from the shop named in this header."

Since `api_secret_key` is shared by the app across every shop that installs it (it is the app's client secret, not a per-shop secret), any merchant who has installed the app can generate a validly-HMAC-signed webhook body from their own store (e.g., by triggering an event in their own shop, or via any endpoint that yields a signable body), and then re-POST that same raw body to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` will still succeed because the check never looks at the shop header, and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to enforce: an unprivileged internet user (or malicious app-installing merchant) can cause the host application to process attacker-controlled data under another merchant's shop identity. Any app that uses `WebhookMetadata#shop` to select which tenant's session/store/data to update (a standard integration pattern documented for this gem) is exposed to cross-tenant data corruption or disclosure — e.g. an attacker can spoof `app/uninstalled`, `shop/redact`, or order/customer events "from" a victim shop and have the app act on the victim's account instead of the attacker's, without any of the app's credentials being compromised. This matches the Critical "cross-tenant access" impact category defined in the rules.

### Likelihood Explanation
Likelihood is high in any deployment where the webhook HTTP endpoint is reachable by anyone (which is the standard model for Shopify app webhooks) and where the attacker can install the same app to their own shop to obtain a genuine HMAC-signed body (a normal, low-privilege action any merchant can take). No secret material, session, or access token is needed — only a body/HMAC pair harvested from the attacker's own legitimately-owned shop installation and a forged header value on the replay request.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the asserted `shop` header to the verified body (e.g., derive/verify the tenant via a lookup keyed by a value that is itself covered by the signature, or require the host app to compare the header shop against a previously-stored expected shop for that installation before trusting it). At minimum, update `Webhooks::Request#to_signable_string` so the shop domain is part of what `HmacValidator` verifies, and update `Registry.process` to reject the request if the shop asserted in the header cannot be tied to the signing key that produced the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining the app's shared `api_secret_key` exposure only indirectly — they trigger any webhook (e.g. `app/uninstalled`) and capture the raw POST body and its `shopify-hmac-sha256` header sent by Shopify.
2. Attacker re-sends that exact body/HMAC pair directly to the app's webhook endpoint, changing only the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`: [5](#0-4) 
   This succeeds because the HMAC is computed only from `@raw_body`, which is unchanged.
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` — the app processes attacker-supplied data as if it came from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
