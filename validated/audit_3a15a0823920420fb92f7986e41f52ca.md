**Rationale:**

`ExplicitSyncWrapper` is a low-level internal synchronization primitive used exclusively inside the BlockSTMv2 parallel execution engine (block-executor crate) to bypass Rust's compile-time aliasing checks where the scheduler already guarantees exclusive/sequential access by construction [1](#0-0) . Its `dereference`/`dereference_mut` methods intentionally have no `AtomicBool`/generation check because correctness is enforced externally by the scheduler's commit ordering (`next_to_commit_idx`, `committed_marker`, `queueing_commits_lock`), not by the wrapper itself [2](#0-1) .

`cold_validation.rs`'s `ColdValidationRequirements` uses this wrapper to track module-publish validation requirements for BlockSTMv2's on-demand (non-wave) validation, and `is_commit_blocked` gates the scheduler's `start_commit` so that a transaction cannot be committed while an unfulfilled cold-validation requirement exists for it [3](#0-2) [4](#0-3) . This mechanism governs whether the *executor* considers a transaction's module reads valid before committing its output into the block's final results; it has nothing to do with granting Move-level capabilities (e.g., a resource account's `SignerCapability`) to callers. Move-level authority checks (signer capability retrieval, object ownership refs, multisig authorization) are enforced by the Move VM and framework modules, entirely independent of this internal executor synchronization mechanism.

There is no path from unprivileged transaction, bytecode, or authenticator input into this code that could cause "stale validation state" to grant a capability. This is purely a single-node execution-engine implementation detail affecting local re-execution scheduling; even a hypothetical staleness bug here would at most cause a non-deterministic execution result that would be caught by other invariant checks (e.g., `code_invariant_error` panics throughout `cold_validation.rs`) or diverge from the deterministic on-chain state computed via consensus, not silently grant custody of assets. The premise that reading a superseded `ExplicitSyncWrapper` value could cause a "resource account's control capability to be granted" is not supported by any code path found in the block-executor — capability minting/checking lives in Move framework code (`resource_account.move`, `account.move`), not in the executor's internal scratch buffers.

    pub(crate) fn is_commit_blocked(&self, txn_idx: TxnIndex, incarnation: Incarnation) -> bool {
        // The order of checks is important to avoid a concurrency bugs (since recording
        // happens in the opposite order). We first check that there are no unscheduled
        // requirements below (incl.) the given index, and then that there are no scheduled
        // but yet unfulfilled (validated) requirements for the index.
        self.min_idx_with_unprocessed_validation_requirement
            .load(Ordering::Acquire)
            <= txn_idx
            || self.deferred_requirements_status[txn_idx as usize].load(Ordering::Relaxed)
                == blocked_incarnation_status(incarnation)
    }
