### Title
LI.FI swap does not bind attacker-controlled router calldata to the declared input/output tokens, allowing router-approval abuse against other pooled tokens - (File: contracts/external-actions/swaps/LifiExternalAction.sol / contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` reads `inputToken`/`outputToken` from the circuit-committed `circomData.erc20TokenAddresses[0]`/`[1]`, but the actual on-chain effect of the swap is driven entirely by `externalActionMetadata`, an arbitrary calldata blob forwarded verbatim to the fixed LI.FI `router`. Nothing ties that calldata to the declared token pair, and the post-swap accounting only measures the balance delta of the declared `outputToken`. `LifiExternalAction.callRouter()` grants the router unlimited approval for `inputToken` via `approveUnlimited` before every call.

`callRouter` in `LifiExternalAction.sol` only measures the balance change of `outputToken` and unconditionally forwards `externalActionMetadata` to the trusted router, approving unlimited `inputToken` allowance first: [2](#0-1) 

The circuit's `MainEVMCircuit` and `CircomDataBuilder` bind `erc20TokenAddresses`, `amountChanges`, nullifiers, etc. into `signedMessageHash`/`calldataHash`, but the raw router `externalActionMetadata` bytes are opaque to the circuit — the circuit only guarantees that *this* transaction's `inputToken`/`outputToken`/`inputAmount` fields are what the user signed, not that the router call constructed from `externalActionMetadata` will only touch these two tokens. `ExternalActionSwap`/`LifiExternalAction` is a **shared, stateful contract used by every Hinkal user**, so it can hold non-zero balances and lingering unlimited ERC20 approvals to the router from prior, unrelated swaps performed by other users (each call to `callRouter` re-approves whatever `inputToken` is passed for that specific call, but a previous swap's approval to the router for a *different* token is never revoked).

Because the balance equation in `swap()`/`transact()` only checks the delta of the two tokens declared in `circomData.erc20TokenAddresses`, any additional token movement triggered by the attacker-crafted `externalActionMetadata` (e.g., a call into the LI.FI diamond that pulls a different, already-approved token from `LifiExternalAction`'s balance, or drains ERC20 balance left over in the contract from previous fee roundings/unclaimed leftovers) is invisible to the on-chain accounting and to the circuit's public inputs. This mirrors the reported bug's root cause exactly: **a value-moving parameter (here, the router calldata / the tokens it actually touches) is trusted without being checked against the equality that the rest of the protocol (proof + balance diff) is supposed to enforce.**

### Impact Explanation
If the shared `LifiExternalAction`/`ExternalActionSwap` contract accumulates a nonzero balance or a stale unlimited approval for a token `T` unrelated to the current swap's declared pair, an attacker can submit a cheap/self-funded swap (e.g., dust `inputToken`) with `externalActionMetadata` engineered to also route token `T` out of the contract to the attacker via the router, since the balance-diff check only inspects `outputToken`. This is theft of protocol/other-users'-in-flight funds not authorized by the prover's committed token pair — a High/Critical impact class (temporary/permanent freezing or theft of funds a wallet owner never authorized for that token).

### Likelihood Explanation
Exploitability depends on (a) the LI.FI router/diamond actually exposing a generic-call surface that lets calldata move previously-approved tokens (a known real-world LI.FI exploit pattern), and (b) `LifiExternalAction` holding a stale approval/balance for another token at attack time. This is not guaranteed on every block, but the contract design provides no defense-in-depth: it neither revokes prior approvals, nor checks that no token other than `inputToken`/`outputToken` moved, so the window is entirely dependent on external, uncontrolled state (residual approvals/dust) rather than protocol logic ensuring safety.

### Recommendation
- After every `callRouter` invocation, explicitly zero the router's allowance for `inputToken` (already done at the start via `approve(router,0)` then `approve(router,value)`, but add a symmetric revoke *after* the call) and assert no other token balances held by the contract decreased.
- Alternatively, restrict `externalActionMetadata` execution to a scoped calldata whitelist verified to target only `inputToken`/`outputToken`, or use a per-call ephemeral approval that is provably bound to the exact `inputAmount` and revoked immediately after the call regardless of success.
- Consider tracking and asserting full balance snapshots (`getBalancesForArray` over all tokens ever routed) before/after `callRouter`, not just the declared pair, so any unauthorized token movement reverts the transaction.

### Proof of Concept
1. User A performs a legitimate swap `tokenX -> tokenY` through `LifiExternalAction`; `approveUnlimited(tokenX, router)` leaves the router with unlimited allowance for `tokenX` on the `LifiExternalAction` contract, and due to rounding/leftover, `LifiExternalAction` retains a small residual `tokenX` balance.
2. Attacker (any unprivileged EOA) submits their own `transact()` call with `circomData.erc20TokenAddresses = [dustToken, dustToken2]` and crafts `externalActionMetadata` that, when sent to the fixed LI.FI `router`, invokes a generic execute/diamond function that calls `tokenX.transferFrom(LifiExternalAction, attacker, amount)` using the leftover unlimited allowance from step 1.
3. `callRouter` only measures `getERC20OrETHBalance(outputToken=dustToken2)` before/after, so the `tokenX` drain is undetected; `swap()`'s balance check passes; the attacker walks away with `tokenX` that was never part of their proof's committed token pair.
(Full confirmation requires an actual LI.FI router that exposes such a generic-call surface — the analysis above establishes that this repo's `ExternalActionSwap`/`LifiExternalAction` code provides no on-chain safeguard against it.)

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
