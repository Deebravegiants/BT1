### Title
Direct-transfer donation to `StreamingYieldVault` bypasses the yield-vesting mask and instantly inflates `totalAssets()`/`maxWithdraw()`, letting an unprivileged actor forge the liquidity-weighted median price of an Intent Gateway phantom order — ([File: sdk/packages/core/contracts/vaults/StreamingYieldVault.sol])

### Summary
`StreamingYieldVault.totalAssets()` is defined as `IERC20(asset()).balanceOf(address(this)) - _lockedYield()`, where `_lockedYield()` only masks the specific tranche amount recorded by the last `onlyOwner`-gated `addYield()`/`onTransferReceived()` call. It does **not** mask an arbitrary, unauthenticated `asset.transfer(vault, amount)` sent straight to the vault's address. Any unprivileged actor can therefore "donate" the underlying asset directly to the vault, instantly and fully inflating `totalAssets()`, `convertToAssets()`, and `maxWithdraw()` for every share, with no vesting delay — a textbook ERC-4626 donation attack, structurally identical to the Curve LlamaLend `DolaSavings.stake()` donation that inflated an oracle-referenced exchange rate.

### Finding Description
`_lockedYield()` is keyed only on `_vestingAmount`/`_vestingStart`, the state set by `_startVesting`, which is reachable only through `addYield` (`onlyOwner`) or `onTransferReceived` (require `from == owner()`): [1](#0-0) 

But `totalAssets()` reads raw `balanceOf(this)`, which reflects *any* incoming transfer of the underlying token, whether it went through `addYield` or was sent by a plain, permissionless `IERC20.transfer(vault, amount)` call from any address: [2](#0-1) 

Because `_lockedYield()` only tracks tranches deliberately started by the owner, a bare donation is invisible to the vesting mask and is recognized as backing assets in the very same block. This defeats the contract's own stated invariant ("no single block can be sandwiched around a yield event") for any donation that does not go through `addYield`.

This directly maps onto the ERC-4626 "solver balance" reader that Hyperbridge's intent infrastructure uses as the *weight* in its liquidity-weighted median price for phantom orders: [3](#0-2) 

`maxWithdraw(address)` on a standard ERC-4626 vault is derived from `convertToAssets(balanceOf(owner))`, which is itself derived from `totalAssets()`. Inflating `totalAssets()` via a bare donation therefore instantly inflates `maxWithdraw()` for every shareholder of that vault, including the attacker if they hold shares. This balance feeds `weightedMedian`, whose own comment states plainly: "a solver holding over half the leg's weight sets the published price verbatim": [4](#0-3) 

and is fanned out into the published `PhantomOrderPriceSnapshotV2.medianPrice`, which the indexer renormalizes directly into `LiquidityPool` sell/buy rates consumed by integrators and by Simplex's own price-guard logic: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who is (or colludes with) a delegated solver holding shares in a `StreamingYieldVault` configured as one of the `yieldVaults` for a token can flash-loan the underlying asset, transfer it directly to the vault (bypassing `addYield`'s owner check), instantly inflate their `maxWithdraw()` reading, submit/back a phantom bid at that inflated weight so `weightedMedian` selects their price verbatim, then redeem their shares to recover the donated principal (since donations benefit shareholders pro-rata and the attacker can be majority/sole holder of that vault) — all within the same transaction/block. This is the same attack shape as the Curve incident: a single-transaction donation that distorts a price/weight input trusted by downstream financial logic, without needing any privileged role. The result is a forged published exchange rate (`PhantomOrderPriceSnapshotV2` / `LiquidityPool` rates) that other integrators, and Simplex's own venue-quote price guard, treat as ground truth, enabling mispriced fills and value extraction from real intent orders — a form of unauthorized/forged pricing rather than a simple no-impact rounding bug.

### Likelihood Explanation
Medium-High reachability, but bounded by preconditions: the attacker needs (a) a flash-loanable amount of the vault's underlying asset, (b) to hold or acquire vault shares in the specific `StreamingYieldVault` deployment configured in `yieldVaults` for a token/chain, and (c) to be (or collude with) a delegated Solver whose bid is counted by `isVerifiedSolverBid`. None of these require any protocol-level privilege — plain ERC-20 transfers and permissionless vault deposits are sufficient — so the class is reachable from a single submitted transaction/bid, matching the report's donation-attack bug class.

### Recommendation
Have `StreamingYieldVault.totalAssets()` mask *all* unrecognized incoming balance, not just the tracked `_vestingAmount`: track a running "last-known accounted balance" and treat any positive delta observed at read time beyond what `addYield`/`onTransferReceived` recorded as still-locked (or reject/sweep unsolicited transfers), so a bare `transfer()` to the vault cannot move `totalAssets()`/`convertToAssets()`/`maxWithdraw()` before an authorized `addYield` call recognizes it. Alternatively, snapshot `balanceOf` at the start of each vesting cycle and compute `totalAssets()` as `snapshotBalance + vestedPortionOfCurrentTranche`, so unsolicited donations are excluded entirely until the owner explicitly starts a new tranche for them.

### Proof of Concept
1. Deploy `StreamingYieldVault` with asset `USDC`; attacker deposits a small amount and becomes a shareholder (deposit allowed while `!_isVesting()`).
2. Attacker flash-loans a large amount of `USDC` and calls `USDC.transfer(vaultAddress, largeAmount)` directly (no `approve`/`addYield`, no owner permission needed).
3. `totalAssets()` immediately reflects `balanceOf(vault) - _lockedYield()`; since `_vestingAmount` is unrelated to this donation, `_lockedYield()` does not mask it, so `totalAssets()` (and thus `convertToAssets`/`maxWithdraw` for the attacker's shares) jumps instantly.
4. Off-chain, `getTotalSolverBalance` reads `maxWithdraw(attacker)` on this vault for the phantom-order weight computation, now inflated; `weightedMedian` selects the attacker-controlled quote as the leg's published price.
5. Attacker calls `redeem`/`withdraw` to pull the donated principal back out (they can own 100% of that vault's shares to make this lossless modulo gas/flash-loan fee), completing the flash-loan-plus-donation round trip within one transaction, exactly mirroring the Curve LlamaLend `DolaSavings.stake()` donation pattern.

    /// @dev Linear unlock of the current tranche, keyed on `block.timestamp` so that a deposit
    ///      and withdrawal within the same block observe an identical, unchanged share price.
    function _lockedYield() internal view returns (uint256) {
        uint256 start = _vestingStart;
        uint256 elapsed = block.timestamp - start;
        if (elapsed >= VEST) return 0;
        return (_vestingAmount * (VEST - elapsed)) / VEST;
    }

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
