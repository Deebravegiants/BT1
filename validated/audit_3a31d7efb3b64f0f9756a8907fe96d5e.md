Audit Report

## Title
Same-call-stack `charge_deposit` + `terminate()` ordering in `try_into_deposit`'s refund-before-charge processing can strand storage-deposit funds - (File: substrate/frame/contracts/src/storage/meter.rs)

## Summary
`RawMeter::terminate` computes the termination refund as `Deposit::Refund(info.total_deposit())`, where `info.total_deposit()` reflects in-memory increases to `ContractInfo::storage_base_deposit` (via `update_base_deposit`, e.g. from `set_code_hash`) made earlier in the same call frame, before the matching `charge_deposit` transfer has actually been placed on hold. `RawMeter::try_into_deposit` processes all queued `Deposit::Refund` charges before any `Deposit::Charge` charges, so the refund's `transfer_on_hold` under-transfers (best-effort) against a hold that doesn't yet include the pending increase, and the later `transfer_and_hold` for that increase deposits fresh balance onto the now-terminated, already-swept contract account with no future code path to release it.

## Finding Description
`ContractInfo::total_deposit()` is `extra_deposit() + storage_base_deposit` [1](#0-0) . `update_base_deposit`, called from `set_code_hash`, mutates `storage_base_deposit` in-memory immediately, and only queues the corresponding balance movement via `nested_storage.charge_deposit(...)`, which pushes a `Charge` entry into `self.charges` without performing any transfer [2](#0-1) . `charge_deposit` itself only records the deferred charge: [3](#0-2) .

If, within the same call frame/execution, the contract subsequently calls `terminate`, `Ext::terminate` fetches the (already mutated) `ContractInfo` and calls `nested_storage.terminate(&info, beneficiary)` [4](#0-3) , which sets `own_contribution = Contribution::Terminated { deposit: Deposit::Refund(info.total_deposit()), .. }` — a refund amount that already includes the not-yet-held delta [5](#0-4) .

When this nested meter is absorbed into its parent, both the earlier queued `Charge(delta)` entry and the new `Refund(total_including_delta)` entry (produced from `own_contribution`) end up together in the same `charges: Vec<Charge<T>>` [6](#0-5) .

`try_into_deposit` then processes all `Refund` entries first, and only afterward all `Charge` entries [7](#0-6) . In the refund pass, `ReservingExt::charge`'s `Deposit::Refund` branch uses `Precision::BestEffort` on `transfer_on_hold` — if the amount held on the contract account is smaller than the requested refund (because the delta was never actually transferred and held), the call silently returns a partial `transferred` amount and merely logs an error [8](#0-7) . Immediately after, because `state` is `Terminated`, the contract's remaining `reducible_balance` is swept to the beneficiary and its consumer ref decremented [9](#0-8) . Only afterward does the second pass execute the earlier `Charge(delta)` entry (whose `state` field was recorded as `ContractState::Alive` at `charge_deposit` time, not `Terminated`), performing `transfer_and_hold` from `origin` to the contract account and placing a fresh hold under `HoldReason::StorageDepositReserve` [10](#0-9) .

By the time this second-pass charge executes, the contract's `ContractInfoOf` entry has already been removed from storage (`ContractInfoOf::<T>::remove(&frame.account_id)` executes synchronously inside `Ext::terminate`, before `try_into_deposit` even runs) [11](#0-10) , so no contract code exists at that address anymore and no future call can ever trigger the storage-meter refund logic needed to release this hold. This matches the claim: the deposit becomes stranded on a dead account.

The design comment's assumption that refund-before-charge ordering makes "the order of storage changes irrelevant with regard to the deposit system" [12](#0-11)  is true only for the aggregate `origin` balance sufficiency check, not for the per-account hold bookkeeping used by `transfer_on_hold`/`transfer_and_hold`, which is exactly what this bug exploits.

The reachable exploit path checked out: a contract can call `seal_set_code_hash` (which increases `storage_base_deposit` and queues a `Charge`, without trapping) and then call `seal_terminate` in the same execution — `terminate` traps (`TrapReason::Termination`) only *after* `Ext::terminate` has already mutated the meter, so both host calls operate sequentially on the same nested meter/frame before any `enforce_limit`/absorption occurs. Nothing in `is_recursive()` or the surrounding checks in `Ext::terminate` [4](#0-3)  guards against this same-frame sequencing.

## Impact Explanation
This is a concrete, in-scope "stuck/lost funds" issue: storage-deposit balance can be permanently held under `HoldReason::StorageDepositReserve` on a terminated contract account with no remaining code path (contract entry removed from `ContractInfoOf`) to ever release it. The amount at risk is bounded by the size of the same-frame deposit increase preceding self-termination (e.g., a `set_code_hash` base-deposit delta), which could be sizeable depending on code deposit/lockup parameters, but each occurrence is bounded per exploit invocation rather than unboundedly large or systemic across all deposits.

## Likelihood Explanation
Both `seal_set_code_hash` and `seal_terminate` are ordinary, unprivileged host functions callable by any contract, and the sequencing (deposit-increasing call immediately followed by self-termination in the same call) is fully controllable by a contract author without any special permission, victim cooperation, or unrealistic assumption. The mechanics were traced through the actual code (`update_base_deposit` → `charge_deposit` → `terminate` → `try_into_deposit`) and appear consistent with the claim. This is repeatable at will by any contract deployer targeting their own contract.

## Recommendation
Make `terminate()`'s refund computation account for outstanding not-yet-held `charges` entries belonging to the same contract (e.g., net `Charge`/`Refund` per-contract before computing the refund amount, or process charges causally/per-contract instead of via two global passes), so that `transfer_on_hold` can never be requested for an amount that was never actually transferred and held on the contract account.

## Proof of Concept
Extend `termination_works` in `substrate/frame/contracts/src/storage/meter.rs`: within one nested meter, call `charge_deposit(contract, Deposit::Charge(X))` to simulate the `set_code_hash` base-deposit increase applied to `info` first, then call `terminate(&info, beneficiary)` where `info.total_deposit()` already includes `X`; absorb into root and call `try_into_deposit`, asserting the mock `Ext::charge` invocation order is `Refund(total_including_X)` before `Charge(X)`. For an end-to-end reproduction, an integration test using `ReservingExt` with a contract that calls `set_code_hash` then `terminate` in one call should show `transferred < amount` in the refund branch (triggering the `log::error!` best-effort path) and a residual `HoldReason::StorageDepositReserve` hold left on the dead contract account after execution, with the sum of origin's post-call free balance plus that residual hold being less than origin's pre-call balance.

		if self.is_recursive() {
			return Err(Error::<T>::TerminatedWhileReentrant.into());
		}
		let frame = self.top_frame_mut();
		let info = frame.terminate();

		ContractInfoOf::<T>::remove(&frame.account_id);

			Self::decrement_refcount(*code_hash);
			frame

				.charge_deposit(frame.account_id.clone(), StorageDeposit::Refund(*deposit));
		}

		Contracts::<T>::deposit_event(Event::Terminated {
			contract: frame.account_id.clone(),
			beneficiary: beneficiary.clone(),
		});
		Ok(())

	pub fn absorb(
		&mut self,
		absorbed: RawMeter<T, E, Nested>,
		contract: &T::AccountId,
		info: Option<&mut ContractInfo<T>>,
	) {
		let own_deposit = absorbed.own_contribution.update_contract(info);

			.saturating_add(&own_deposit);

			self.charges.push(Charge {
				contract: contract.clone(),
				amount: own_deposit,
				state: absorbed.contract_state(),
			});
		}
	}
