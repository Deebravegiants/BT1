## Finding: Silent truncation in `convert_to_balance` permanently destroys value on inbound `hyper-fungible-token` transfers

The reported Ajna bug is a decimal-scaling defect: a fixed 18-decimal assumption baked into a size/threshold check breaks for tokens whose real decimals differ. The reachable analog in this codebase is `pallet-hyper-fungible-token`'s ERC20→local amount conversion, which has the same root cause (naive `10^(decimalsA - decimalsB)` scaling with no floor/dust handling) but a worse outcome: silent, irreversible fund destruction instead of a mere revert.

### Finding Description
`convert_to_balance` truncates via integer division and is used unconditionally on the inbound message path: [1](#0-0) 

`register_token` only enforces `erc_decimals >= local_decimals`, it does not bound how much larger `erc_decimals` may be relative to `local_decimals`: [2](#0-1) 

On `on_accept`, an incoming message's `amount` (an arbitrary `U256` chosen by whoever calls `send`/`bridge` on the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract) is converted with this same helper and then minted/transferred to the beneficiary with no check that the conversion was exact: [3](#0-2) 

Because the ERC20-side amount is escrowed/burned on the EVM chain *before* the message is dispatched (in `HyperFungibleToken.sol`, not audited here but implied by the pallet's own docs: "Outgoing transfers burn the local representation … incoming messages mint fresh tokens" / "escrows the native balance … incoming messages release from escrow"), any remainder discarded by the division is not credited anywhere on the destination chain and is not returned to the sender. It is simply gone. [4](#0-3) 

The scale factor is `10^(erc_decimals - local_decimals)`, which can be arbitrarily large — e.g. an asset registered locally with 0 or 6 decimals but paired with a component with default 18-decimal precision (as documented for `BridgeToken`, whose ERC20 face uses 18 decimals against nexus's 12-decimal native asset, scale = `10^6`): [5](#0-4) 

If `local_decimals` were even smaller (e.g. an asset with 0 decimals paired against an 18-decimal ERC20 image — permitted by `register_token`'s `>=` check), the scale factor becomes `10^18`, meaning up to *just under one whole token* of value can be destroyed on a single transfer whose ERC20 amount is not an exact multiple of the scale factor.

By contrast, the outbound `send` path is safe: it multiplies up via `convert_to_erc20`, which is loss-free by construction (`erc_decimals >= local_decimals` guarantees an integer multiplier): [6](#0-5) 

and the `on_timeout` refund path reconverts an amount that was itself produced by that same exact multiplication, so it recovers precisely: [7](#0-6) 

Only the inbound `on_accept` conversion operates on an amount chosen independently on the EVM side, and is the one path where truncation is not guaranteed to be zero.

### Impact Explanation
Any single unprivileged cross-chain transfer from the paired EVM chain into this pallet whose ERC20 amount is not an exact multiple of `10^(erc_decimals - local_decimals)` has its remainder permanently destroyed: burned/escrowed on the EVM side, never minted/transferred on the substrate side, and never refunded. Depending on the registered decimals pairing (bounded only by `erc_decimals >= local_decimals`, with no cap on the gap), the destroyed amount can range from negligible dust up to nearly one whole unit of the bridged asset per transfer — a permanent, unrecoverable loss of user funds.

### Likelihood Explanation
Reachable by a normal user of the EVM-side token contract performing an ordinary cross-chain send with no special amount alignment — no malicious actor, admin, or relayer collusion is required; a relayer merely delivering a legitimately proven message triggers the loss. Any token pair configured with a decimals gap (which the pallet explicitly supports and even documents, e.g. `BridgeToken`'s 18-vs-12 pairing) is affected on every transfer whose amount isn't a clean multiple of the scale factor.

### Recommendation
- Require the incoming ERC20 `amount` to be an exact multiple of `10^(erc_decimals - local_decimals)` in `on_accept`, rejecting (or refunding to a dust-recovery account) any amount that would truncate to a different value than intended.
- Alternatively/additionally, track discarded remainders per beneficiary/asset and expose a claim mechanism, or emit an event surfacing the truncated dust so it isn't silently lost.
- Consider bounding the allowed gap between `erc_decimals` and `local_decimals` in `register_token`/`update_token` to limit the maximum possible per-transfer loss.

### Proof of Concept
1. `register_token` an asset with `local_decimals = 0` (or any small value) and `Precisions` configured with `erc_decimals = 18` for an EVM chain (allowed: only `erc_decimals >= local_decimals` is enforced).
2. On the paired EVM `HyperFungibleToken` contract, a user sends `amount = 999_999_999_999_999_999` (18-decimal units, i.e. just under 1 whole token) to a substrate beneficiary. The EVM side burns/escrows this amount and dispatches the cross-chain message.
3. On `on_accept`, `convert_to_balance(999_999_999_999_999_999, 18, 0)` computes `999_999_999_999_999_999 / 10^18 = 0` (integer division), so the beneficiary is minted/transferred `0`.
4. The nearly-whole token burned/escrowed on the EVM side is never credited to anyone on the substrate side and there is no refund path — the value is permanently destroyed.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

## Overview

A registered token is classified as one of two custody models:

- **Native** (`native = true`) — the asset originates on this chain. Outgoing
  transfers move the local balance into the pallet's escrow account; incoming
  messages release from escrow.
- **Non-native** (`native = false`) — the asset originates on a remote chain.
  Outgoing transfers burn the local representation; incoming messages mint
  fresh tokens.

The chain's own native currency (`T::NativeAssetId`) is always treated as
native, with `T::NativeCurrency` providing custody.

Decimals between this chain and each remote chain may differ; per-pair
`Precisions` storage records the EVM-side decimals so amounts get scaled at
the boundary.
