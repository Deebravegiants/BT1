### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Shop Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request **body**, then dispatches the handler using a `shop` value taken from an **unsigned header**. Because the `shop-domain` header is never part of the HMAC-covered content, the identity used by the handler (`request.shop`) is not bound to the identity that was cryptographically verified (`request.to_signable_string` == raw body only). This mirrors the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`hmac` and `to_signable_string` derive strictly from the `hmac-sha256` header and `@raw_body`. The `shop` accessor reads a **separate, unsigned** header (`shopify-shop-domain`): [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), never the shop header: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop` as the tenant identity passed into the handler: [4](#0-3) 

The equality that should hold is:
`shop authenticated (bound inside HMAC-signed payload) == shop acted upon (passed to WebhookMetadata/handler)`

Here, the right side is read from an attacker-controllable header that is completely outside the scope of the left side's cryptographic check. Any party who has ever received one legitimately-signed webhook (e.g., by installing the app on their own store, which is unprivileged/self-service on Shopify) possesses a `(raw_body, hmac)` pair that remains valid for that exact body under the app's secret **regardless of which `shop-domain` header accompanies it**. They can replay that same body+hmac while substituting the `x-shopify-shop-domain` header for any other shop that has the app installed, and `Registry.process` will accept it and route the attacker's own captured body to the handler labeled as `data.shop = <victim shop>`.

### Impact Explanation
Consuming applications built on this gem are documented to key their per-tenant logic off the value passed via `WebhookMetadata#shop` (used to look up sessions/data for the tenant). Because that value is unauthenticated, an attacker can make the host application process attacker-controlled webhook content under a different, victim tenant's identity — i.e., cross-tenant access/data confusion, one of the qualifying Critical impacts.

### Likelihood Explanation
Exploitation requires no privileged access, no leaked secrets, and no TLS interception: any actor can install the app on a shop they control (a normal, unprivileged action on Shopify) to legitimately obtain a valid `(body, hmac)` pair, then send a forged HTTP request with a different `shop-domain` header directly to the app's public webhook endpoint. The vulnerability is triggered purely by the gem's own `HmacValidator`/`Registry.process` logic never binding the header to the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signable string, or otherwise cryptographically bind the `shop-domain` header value to the signed body (e.g., verify shop against a value embedded/signed in the payload, or require the caller to additionally confirm the shop is one they expect before trusting `data.shop`). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-identity source.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Same raw body and same `X-Shopify-Hmac-Sha256` value captured in step 1.
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (any shop with the app installed).
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only checks `@raw_body` against the shared secret — unaffected by the swapped shop header. [5](#0-4) 
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` while `body` is the attacker's own shop's order data, causing the host app to act on/for the victim tenant using attacker-supplied content.
