### Title
Webhook shop-domain (and topic/webhook-id) header is not covered by HMAC verification, allowing shop-identity confusion in `Webhooks::Request` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely the JSON body against the app's `client_secret`. The `shop` value that `Webhooks::Registry.process` passes on to application handlers as the authoritative tenant identifier is taken from the `x-shopify-shop-domain` header, which is completely outside the HMAC's signed scope.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` is defined as just the raw body [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` relies on `Utils::HmacValidator.validate(request)` purely to authenticate the request, then immediately forwards `request.shop`, `request.topic`, etc. to the registered handler as trusted, verified data [4](#0-3) . Because the secret used to sign a webhook (`Context.api_secret_key` / `client_secret`) is the app's secret and is identical for every shop that installs the app, any actor who can trigger a legitimate webhook delivery to their own shop (e.g., by installing the public app on a shop they control) obtains a valid `(raw_body, hmac)` pair. That pair remains valid for **any** value of the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, since none of them are part of the signed string.

The bug class matches the described pattern exactly: "a field acted on but not covered by the HMAC" — here, `shop` is acted on (passed to `WebhookMetadata` and used by the handler to identify the tenant) but is not part of the HMAC-signed payload.

### Impact Explanation
This breaks the binding `shop authenticated == shop the handler acts on`. An attacker who owns/installs the app on their own store can capture one valid signed webhook delivery and replay it to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `topic`/`webhook-id`) header. The HMAC check still passes, so the host application's webhook handler executes business logic (e.g., processing `app/uninstalled`, `orders/create`, GDPR/mandatory webhooks) attributing it to a victim shop chosen by the attacker. If the host application uses `WebhookMetadata#shop` to look up/act on that shop's stored session or access token (the documented and expected usage pattern in `docs/usage/webhooks.md`), this results in cross-tenant action/confusion driven entirely by attacker-controlled, unauthenticated header data. This qualifies as Critical (cross-tenant access) under the stated impact criteria.

### Likelihood Explanation
Likelihood is realistic for any actor with an unprivileged Shopify Partner/dev account: they can install the target's public app on a shop they control, capture a real, correctly-signed webhook body+HMAC (using standard tools, no credential leakage or social engineering needed), then replay that exact body to the app's public webhook endpoint with modified headers. No secret, access token, or elevated privilege is required — only observation of one's own legitimate webhook traffic.

### Recommendation
Bind the identity-bearing headers into the signed payload before verifying, e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching what is actually trusted downstream), or require the host application to independently verify that `request.shop` corresponds to a shop with an active, verified session/install record before processing — but the library-level fix is to make `HmacValidator` cover every field that `Registry.process`/`WebhookMetadata` treats as authenticated.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. body `{"id":1}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of {"id":1} with app secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Replay the identical raw body and HMAC header to the same webhook endpoint, but change:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Utils::HmacValidator.validate` recomputes HMAC over the unchanged body and it matches, so `Registry.process` proceeds and invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [5](#0-4) , even though the payload never actually originated from or concerned `victim.myshopify.com`.
