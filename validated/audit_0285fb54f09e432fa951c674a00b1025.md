### Title
Unchecked ERC20 return-value in Tron `IntentGatewayV2.withdraw()` permanently freezes escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron variant of `IntentGatewayV2` marks an order's escrow terminally settled (`_filled[body.commitment] = beneficiary`) and then moves each escrowed token with a raw low-level `.call` to `IERC20.transfer`, checking only that the call itself did not revert (`success`) rather than decoding and checking the boolean the ERC20 standard requires the token to return. A non-reverting, non-standard token that returns `false` on failure (e.g. due to a pause, blacklist, or insufficient balance handled without reverting) will make `success == true` even though no tokens moved, while `_filled` has already been committed. Because `_filled` gates all future fill/refund/cancel paths and there is no governance or retry mechanism to un-set it, the escrowed principal for that commitment becomes permanently unrecoverable — structurally the same "mark success without verifying the external transfer actually happened" failure mode as Booster's `shutdownPool()` in the referenced report.

### Finding Description
`withdraw()` is the terminal settlement path for both the `RedeemEscrow` and `RefundEscrow` flows, reached from `onAccept()` (message delivered via Hyperbridge/ISMP from either the counterparty gateway on fill, or from the local cancel-from-destination path) and from `onGetResponse()` (cancel-from-source refund path): [1](#0-0)

The ERC-20 branch only checks that the low-level `.call` did not revert. It never inspects the ABI-decoded return data. Per EIP-20, a compliant `transfer()` that fails is supposed to either revert or return `false`; this code accepts `false` silently as success, because Solidity's raw `.call` reports `success = true` for any call that completed without reverting, regardless of the return value. The sibling production contract, `evm/src/apps/intentsv2/IntentsBase.sol`, uses OpenZeppelin's `SafeERC20.safeTransfer`, which does decode and enforce the boolean, confirming this check is the intended safety property and that the Tron contract's raw `.call` diverges from it: [2](#0-1) 

Because `_filled[body.commitment]` is written unconditionally at the top of `withdraw()`, before any of the per-token transfer attempts, a token that returns `false` without reverting leaves the commitment permanently marked as filled/refunded while the actual asset never left the contract to the beneficiary. The same unchecked pattern is repeated for the transaction-fee payout and in `SweepDust`: [3](#0-2) [4](#0-3) 

There is no un-fill, retry, or governance recovery path for `_filled`: every subsequent path (`cancelOrder`, `onAccept`, `onGetResponse`) checks `_filled[commitment] != address(0)` and reverts with `Filled()`, so once falsely marked, the escrowed balance recorded in `_orders[commitment][token]` is permanently orphaned in the contract with no legitimate way to reach the intended beneficiary.

### Impact Explanation
This is a concrete permanent freeze of user principal: the escrowed input tokens (for a fill settlement) or the user's own tokens (for a refund/cancellation) become permanently stuck in the gateway contract once a non-standard token silently returns `false`. Unlike the reverting failure paths (`InsufficientNativeToken`, `TransferFailed` on a `.call` that itself reverts), this failure mode leaves no revert trace and commits `_filled` irreversibly, exactly mirroring the root cause the referenced report flags in Booster's `shutdownPool()`: an irreversible state transition is committed on the optimistic assumption that the guarded external operation succeeded, with no verification and no unwind path. Given Tron/TRON-adjacent token ecosystems commonly include non-standard TRC20/ERC20-like tokens that do not strictly follow return-value semantics, this is a realistic trigger, not a purely theoretical one.

### Likelihood Explanation
Likelihood depends on at least one configured input/output/fee token used with this Tron gateway returning `false` on transfer failure instead of reverting — a known and common category of non-standard ERC20/TRC20 tokens (as opposed to fully-compliant tokens like OpenZeppelin's, which revert). Any condition that would cause such a token's `transfer` to fail (temporary pause, blacklist, insufficient contract balance from fee/rounding edge cases) is sufficient to trigger permanent loss for that specific order's escrow, without requiring any privileged or malicious actor — an ordinary relayer delivering a normal `RedeemEscrow`/`RefundEscrow` message is enough to reach this code path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and `SweepDust` handling with OpenZeppelin's `SafeERC20.safeTransfer`, matching `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()`. This decodes and enforces the ERC20 boolean return value (and tolerates tokens that return no data, like real USDT), causing a genuine transfer failure to revert the whole transaction — including the `_filled` write — instead of silently committing state that assumes success. As defense in depth, consider moving `_filled[body.commitment] = beneficiary;` after the transfer loop succeeds (or making it conditional the way `_withdraw`'s `finalize` flag pattern already does in the main contract), so a reverting transfer failure can never partially commit terminal state even under future refactors.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with an ERC20/TRC20 token `T` used as an escrowed input, where `T.transfer()` returns `false` (rather than reverting) when the sender lacks sufficient balance or the recipient is blacklisted/paused — a real behavior seen in several non-standard tokens.
2. A user places a cross-chain order escrowing `T` via `placeOrder`.
3. The order is filled on the destination chain and Hyperbridge delivers a `RedeemEscrow` `PostRequest` back to the source chain, invoking `onAccept()` → `withdraw(body, false)`.
4. At the moment `withdraw()` executes, arrange for `T.transfer(beneficiary, amount)` to return `false` (e.g., token is paused, or beneficiary is temporarily blacklisted) without reverting.
5. `(bool success,) = token.call(...)` returns `success = true` (the call itself did not revert), so the `if (!success) revert TransferFailed();` guard is bypassed.
6. `_filled[body.commitment]` was already set to `beneficiary` before the loop and the transaction completes successfully; `EscrowReleased` is emitted despite no tokens having moved.
7. Any later attempt to re-trigger settlement for this commitment (fill, refund, or cancel) reverts with `Filled()` since `_filled[commitment] != address(0)`, and there is no governance call to clear it — the escrowed `T` balance recorded under `_orders[commitment][token]` is permanently stranded in the contract.
