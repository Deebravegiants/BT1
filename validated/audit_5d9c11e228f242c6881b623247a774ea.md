Audit Report

## Title
Unauthenticated `/v2/resume/:runID` Endpoint Allows Duplicate/Replay Resume of an Already-Finished Pipeline Task Run - (File: core/services/pipeline/orm.go)

## Summary
The route `PATCH /v2/resume/:runID` is registered in the `unauthedv2` route group with no auth middleware, and its handler (`PipelineRunsController.Resume` → `ResumeJobV2` → `runner.ResumeRun` → `orm.UpdateTaskRunResult`) allows any unauthenticated caller who knows/guesses a task-run UUID to overwrite that task run's `output`/`error`/`finished_at` fields more than once. The guarding `SELECT ... FOR UPDATE` only checks the parent `pipeline_runs.state IN ('running','suspended')`, never checking `pipeline_task_runs.finished_at IS NULL`, so a task run that was already resumed/finished can be resumed again while its parent run remains non-terminal.

## Finding Description
Confirmed in the current code:
- `unauthedv2.PATCH("/resume/:runID", prc.Resume)` sits outside the `authv2` group that requires `auth.Authenticate(...)`, at `core/web/router.go` lines 238-243.
- `UpdateTaskRunResult` in `core/services/pipeline/orm.go` (lines 271-308) executes:
```go
SELECT pipeline_runs.*, ...
FROM pipeline_runs
JOIN pipeline_task_runs ON (pipeline_task_runs.pipeline_run_id = pipeline_runs.id)
...
WHERE pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')
FOR UPDATE
```
followed by an unconditional
```go
UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1
```
There is no `finished_at IS NULL` predicate anywhere in this query (verified via repo-wide search — the only `finished_at IS NULL` occurrences are in unrelated migration files and a Prometheus reporter, not in this ORM function). This means the guard is based solely on the *parent run's* state, not on whether the *specific task run* has already been completed. As long as the parent pipeline run remains `running` or `suspended` (which is expected for pipelines with multiple pending/async branches), the same `taskID` can be submitted repeatedly via `PATCH /v2/resume/:taskID`, each time overwriting the previously recorded result and, when the run was `suspended`, restarting the pipeline again.

This matches the root cause described in the claim precisely, and I was unable to find any additional check upstream (in `ResumeJobV2` or `runner.ResumeRun`) that verifies the task run hasn't already finished before calling `UpdateTaskRunResult`.

## Impact Explanation
This allows an unauthenticated actor who can observe or guess a pending async task-run UUID (exposed via the `responseURL` sent to external bridge/adapter callbacks) to overwrite the recorded result of an already-completed task run and potentially force a duplicate restart of downstream pipeline execution with attacker-controlled data. This falls under the in-scope "unauthorized job run" / data-integrity impact category, since it lets an external, unauthenticated party corrupt or replay a job run's task result without any credential.

## Likelihood Explanation
Exploitation requires only network access to the node's HTTP API and knowledge of a task-run UUID — no API key, session, or role is needed, since the route is explicitly unauthenticated. The main constraint (learning the UUID) is realistic for a compromised/malicious external adapter or a party able to observe the async callback in transit, which is a plausible threat model for this endpoint (the audit log even labels the event `UnauthedRunResumed`, acknowledging its unauthenticated nature).

## Recommendation
Add `AND pipeline_task_runs.finished_at IS NULL` to the `SELECT ... FOR UPDATE` guard in `UpdateTaskRunResult` (core/services/pipeline/orm.go) so an already-finished task run cannot be matched and overwritten again. Return a distinct "already finished" error when no row matches, and propagate that as a client error (e.g., HTTP 409/410) from `PipelineRunsController.Resume` instead of silently succeeding.

## Proof of Concept
1. Create a webhook job with an async bridge task producing a `responseURL` of the form `http://<node>/v2/resume/<taskUUID>`.
2. Send `PATCH /v2/resume/<taskUUID>` with a legitimate value; the task run is marked finished and the pipeline resumes/restarts if the run was suspended.
3. While the parent pipeline run is still `running`/`suspended` (e.g., other branches still pending), send a second `PATCH /v2/resume/<taskUUID>` with a different value.
4. Observe that `UpdateTaskRunResult`'s query matches again (since only `pipeline_runs.state` is checked) and the unconditional `UPDATE pipeline_task_runs SET output=..., finished_at=...` overwrites the first result, and — if the run was suspended — the pipeline restarts a second time with the new value. A Go unit test on `orm_test.go` calling `UpdateTaskRunResult` twice on the same `taskID` with the parent run left in `running` state would demonstrate the second call succeeding and overwriting the first result, when it should instead return an error.
