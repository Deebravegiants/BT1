### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-signing only the raw request body, while the `shop`, `topic`, `api-version`, and `webhook-id` values are taken directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC matches, then hands the caller-supplied (unsigned) `shop` value straight to the handler. This breaks the identity binding: `HMAC(secret, raw_body) == valid` should imply `shop header == shop that generated this body`, but the gem only checks the former.

### Finding Description
`to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the body HMAC via `HmacValidator.validate`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it only against the received HMAC — it never inspects or binds any header value: [4](#0-3) 

Because the app's `api_secret_key` (used as the webhook HMAC secret) is shared across every shop that installs the app — not a per-shop secret — any user who legitimately installs the app on a shop they control will receive genuinely-signed webhooks with a valid `HMAC(raw_body)` for that body content. Since the `shop-domain` header sits outside the signed payload, that same signed body/HMAC pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to name a **different, victim** shop. `Registry.process` will accept it (HMAC matches) and dispatch it to the handler labeled as coming from the victim shop.

### Impact Explanation
This is a cross-tenant identity break: the gem asserts webhook authenticity is proven by body-HMAC validity alone, then forwards an attacker-controlled `shop` claim to the host application's business logic (`WebhookMetadata#shop`) as if it were verified. Any application that uses `data.shop` from `Registry.process`'s callback to select which tenant's records to create/update/delete (a standard and documented usage pattern) can be made to apply a validly-signed webhook body under a spoofed shop identity, i.e. cross-tenant data injection/corruption, without needing the target's secret or any privileged credential — only a legitimate (even free/attacker-owned) app installation is required to obtain one genuinely-signed body/HMAC pair to replay.

### Likelihood Explanation
Any developer/merchant able to install the app on their own store (the normal, unprivileged flow for any public/embedded Shopify app) can capture a genuine webhook delivery (raw body + valid HMAC) for their own shop, then replay it to the app's public webhook endpoint with only the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed. No secret material, token theft, or social engineering is required — this is a direct consequence of the library's signing scope (`to_signable_string` = body only), so likelihood is high wherever the host app trusts `WebhookMetadata#shop` from `Registry.process`.

### Recommendation
Bind the shop identity into the verified signature, e.g. include `shop-domain` (and ideally `topic`) in the signable string / verification, or independently cross-check that the header-provided `shop` matches an expected value known out-of-band for that delivery (e.g. via a per-shop webhook secret, or validating that the shop is one that is currently subscribed with the app for that topic/webhook id before dispatch) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(secret, B)`.
2. Attacker POSTs to the app's public webhook endpoint with the identical raw body `B` and HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, B)` and compares to `H` — this passes because `B` and `H` are unchanged. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)`, and any host logic keyed off `data.shop` operates on the victim shop's tenant using attacker-controlled body content.
