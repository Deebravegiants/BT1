### Title
Unmetered `pallet-state-coprocessor::handle_unsigned` lets unauthorized senders force full state-proof verification before the bandwidth allowlist gate runs - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet_state_coprocessor::handle_unsigned` is a fee-less, permissionless (`ensure_none`) extrinsic that any address can submit and that every full node re-executes end-to-end in `ValidateUnsigned::validate_unsigned` just to admit it into the transaction pool. The handler `handle_get_requests` runs full cryptographic state/membership proof verification for an unbounded batch of `GetRequest`s and an unbounded number of `keys` per request *before* it ever consults `BandwidthGate::try_consume`, the only place the sender's authorization (purchased bandwidth or allowlist membership) is checked. An unauthorized, unallowlisted sender can therefore force expensive proof-verification work onto every node in the network for free, then get rejected only after the work is done — the same "preflight work before authorization" bug class as the reported Telegram audio-transcription issue.

### Finding Description
`handle_unsigned` is declared with `ensure_none(origin)` so it accepts the unsigned/`None` origin and can be submitted by anyone, without a fee: [1](#0-0) 

Its `ValidateUnsigned::validate_unsigned` implementation unconditionally calls the full handler on *every* submitted unsigned transaction while validating it for the mempool — i.e. this run happens on every peer node that gossips or re-validates the transaction, independent of whether it is ever included in a block: [2](#0-1) 

Inside `handle_get_requests`, the cheap checks (dedup, timeout, source/dest match, duplicate-response check) run first, but then two full cryptographic proof verifications run over an attacker-controlled, unbounded batch — `verify_membership` over all `requests`, and per-request `verify_state_proof` over an unbounded `keys` vector — with **no size/weight bound on `requests.len()` or `keys.len()`** anywhere in this path: [3](#0-2) 

Only *after* `verify_state_proof` has already run for a given request does the code consult the authorization gate: [4](#0-3) 

The pallet's own documentation states the intended design goal explicitly — the gate is supposed to be consulted "before any state proof work" — but the implementation charges bandwidth only "after proof verification": [5](#0-4) [6](#0-5) 

By contrast, every other authorization-gated verification pipeline in this codebase deliberately orders the allowlist/blacklist check *before* the expensive verification step — e.g. the outbound relayer-reward claim path explicitly rejects on the allowlist before any state-proof work runs: [7](#0-6) [8](#0-7) 

and the Optimism/Arbitrum consensus clients explicitly check a fisherman blacklist "before the heavy proof verification": [9](#0-8) 

`pallet-state-coprocessor` is the one path where this ordering is inverted: authorization (the bandwidth gate, which is the coprocessor's analog of an allowlist) is checked last, per-request, after the expensive work for that request (and the batch-wide membership proof) has already executed.

### Impact Explanation
Because `handle_unsigned` is unsigned and free, and `validate_unsigned` performs the full proof-verification pipeline as part of admitting the transaction into the pool, any unauthorized sender — one with zero purchased bandwidth and no allowlist entry for `(source, from)` — can submit crafted `GetRequestsWithProof` payloads with large `requests` batches and large `keys` vectors per request. Every node that receives and validates this gossiped transaction performs the full membership-proof and state-proof verification (trie walks, multi-proof hashing) for the entire attacker-controlled payload before the bandwidth gate ever gets a chance to reject it. This lets an unauthorized party consume validator/node CPU resources at will and for free, which is a resource-consumption/DoS vector matching CWE-408/CWE-770 exactly as in the reported analog, without requiring any funded bandwidth subscription or allowlist membership.

### Likelihood Explanation
High likelihood of triggerability: the call is unsigned, requires no fee, no prior setup, and no bandwidth purchase. Any external party can construct and gossip such a transaction. The only constraints are extrinsic size limits inherited from the runtime, but there is no explicit bound on `requests.len()` or per-request `keys.len()` inside this pallet's logic to cap the verification cost, unlike other paths in the codebase (e.g., `pallet-call-decompressor`'s explicit `MaxCallSize` check) that were specifically hardened against this class of issue.

### Recommendation
Move the `BandwidthGate::try_consume` (or an equivalent authorization/allowlist pre-check) to run before `verify_membership` and before `verify_state_proof` in `handle_get_requests`, using a cheap upper-bound estimate of the request/response size (e.g., based on `keys.len()` and `context.len()` alone, as already computed via `max(sum(keys.len()) + context.len(), 32)` per the pallet's own doc comment) so unauthorized/unfunded `(source, from)` pairs are rejected before any proof verification is attempted. Additionally, bound `requests.len()` and per-request `keys.len()` explicitly so the mempool-validation cost of a rejected call is capped regardless of authorization.

### Proof of Concept
1. Attacker (no bandwidth purchased for `(source, from)`, not on the `Allowlist`) crafts a `GetRequestsWithProof` message with a large `requests` vector, each `GetRequest` carrying many `keys`, and a syntactically well-formed (but ultimately irrelevant to authorization) `source`/`response` `Proof`.
2. Attacker submits `pallet_state_coprocessor::Call::handle_unsigned { message }` as an unsigned extrinsic.
3. Every node in the network runs `ValidateUnsigned::validate_unsigned`, which calls `handle_get_requests`, which executes `source_state_machine.verify_membership(...)` over the whole batch and then, for each request, `dest_state_machine.verify_state_proof(...)` over its `keys` — all before `BandwidthGate::try_consume` is invoked for that request.
4. `BandwidthGate::try_consume` finally runs and rejects the call (`GateError::NoAllowance`), but only after the full cryptographic verification work has already been paid for, in CPU time, by every validating node — for free and repeatedly, since the attacker can resubmit variations indefinitely.
