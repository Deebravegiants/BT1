### Title
Webhook shop identity spoofing via cross-shop HMAC replay — HMAC covers only the raw body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the raw request body against the `X-Shopify-Hmac-Sha256` header. The `shop` identity that is handed to the app's webhook handler is read from the unauthenticated `X-Shopify-Shop-Domain` header and is never covered by the HMAC signature. Any actor who can obtain a body+HMAC pair signed with the app's shared `api_secret_key` (trivially available to them by simply installing the app on their own store and receiving real webhooks) can replay that exact body/HMAC pair while substituting an arbitrary victim shop's domain in the header, causing the handler to process attacker-controlled data under another tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely over that signable string: [2](#0-1) 

`Registry.process` uses this validator as the sole authenticity check, and then forwards `request.shop` (sourced from the `shop-domain` header, not from the signed bytes) directly into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The `shop` accessor is a plain header read with no cross-check against the HMAC-covered payload: [4](#0-3) 

The library's own documentation instructs apps to trust `data.shop` for tenant routing (e.g., enqueuing per-shop background jobs), reinforcing that this field is treated as an authenticated tenant identifier by consuming applications: [5](#0-4) 

This breaks the intended binding: `HMAC(raw_body, api_secret_key) == received_hmac` should imply `(raw_body, shop) is exactly what Shopify sent for that shop`. In reality the equality only proves `raw_body` integrity; `shop` is asserted by the caller and never bound into the signable string, so the equality that actually holds is `HMAC(raw_body) == received_hmac` regardless of which `shop` header value accompanies it.

### Impact Explanation
Because `api_secret_key` is shared across all shops that install the app, any unprivileged user can install the app on their own (attacker-controlled) test store and receive genuine, validly-signed webhook deliveries (e.g., `orders/create`, `customers/data_request`) for that store. The attacker can capture the exact `raw_body` and its correctly computed `X-Shopify-Hmac-Sha256` value, then POST that same body/HMAC pair to the app's webhook endpoint while forging `X-Shopify-Shop-Domain` (and freely also `X-Shopify-Topic`/`X-Shopify-Webhook-Id`, which are likewise unauthenticated) to name any victim shop. `Registry.process` will accept it as valid and the app's handler will process attacker-supplied content attributed to the victim's tenant — a cross-tenant data injection/confusion (e.g., fake orders, fake customer-redaction requests, or fake data attributed to a shop that never sent it), meeting the "cross-tenant access" bar.

### Likelihood Explanation
High for any developer relying on the app's documented `data.shop` field for per-tenant handling — which is exactly what the gem's own docs recommend. The only prerequisite is that the attacker install the app on any shop (a normal, unprivileged action) to obtain one legitimate signed webhook payload, then replay it with a forged header; no access to `api_secret_key`, tokens, or other credentials is required.

### Recommendation
Bind the shop identity (and topic/webhook id) into the HMAC-covered signable content, or otherwise authenticate the `shop-domain` header against a value derived from a source Shopify actually signs (e.g., verify the shop against the `Session`/subscription record already known to have registered that specific `webhook_id`/topic pair) before trusting it in `WebhookMetadata`. At minimum, document and enforce that consuming apps cross-check `data.shop` against their own known list of shops that registered for that specific webhook subscription rather than trusting it implicitly.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends this exact `(B, H)` pair to the same app webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — this passes. [6](#0-5) 
5. The handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it originated from the victim shop.
