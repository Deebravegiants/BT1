### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant identity spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body, then trusts the `shop` value taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header — a field that is never included in the HMAC-signed content — to identify the tenant for the handler.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` performs exactly one authenticity check before dispatching to a handler: [4](#0-3) 

The HMAC validation calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` header value: [5](#0-4) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop` — the value that `Registry.process` passes into `WebhookMetadata` as the tenant identifier for the handler — is read directly from an HTTP header that is completely outside the HMAC-signed content: [3](#0-2) [6](#0-5) 

This is the exact identity-binding break named in the analog list: a field (`shop`) acted on but not covered by the HMAC. Because the HMAC is computed with the app's static `api_secret_key` and depends only on the raw body bytes, any request whose body was previously HMAC-signed by Shopify remains valid regardless of what `shop`-domain header accompanies it. An attacker who legitimately receives real webhook deliveries for their own shop (trivial: install the target app on their own store to trigger topics such as `app/uninstalled`, `orders/create`, etc.) can capture one such `(raw_body, hmac)` pair and replay it to the same webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the signature, and `Registry.process` then calls the topic's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain — a value host applications are expected to trust for looking up the correct tenant/session (per the documented example that treats a processed webhook as verified "to have...come from Shopify" [1](#0-0) ).

### Impact Explanation
This breaks the equality `shop-authenticated-by-hmac == shop-used-as-tenant-key`, letting an attacker who controls one legitimate webhook body/HMAC pair cause the gem to hand host applications data falsely labeled as belonging to another tenant shop. Any host application that trusts `WebhookMetadata#shop` to select or mutate per-shop state (a pattern the gem's own documentation and API surface encourage) is exposed to cross-tenant data confusion/injection driven entirely by an unprivileged internet user who merely has their own shop install of the app — satisfying the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high: no secret material is needed beyond obtaining one authentic webhook delivery for a shop the attacker legitimately controls (any app installer can do this trivially), and no additional cryptographic work is required — only replaying the exact `raw_body` with a modified shop-domain header, since the header is never covered by the signature check in `Utils::HmacValidator.validate`.

### Recommendation
Bind the `shop` identity into the value that is HMAC-verified — e.g., include the `shop`-domain header (and ideally `topic`/`webhook-id`) inside `to_signable_string`, or independently verify the shop header against Shopify by cross-referencing it with an authenticated source (session, prior registration, or the payload contents) before constructing `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST from Shopify, e.g. body `{"id":123}` with headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the identical raw body and HMAC header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts this (headers only checked for presence, not binding) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [8](#0-7) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim tenant's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
