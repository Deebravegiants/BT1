## Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` trusts these unauthenticated header values to determine which tenant ("shop") a webhook event belongs to, even though only the body bytes are cryptographically verified.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are pulled directly from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. only the raw body for webhooks) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then dispatches to the handler using the **unauthenticated** `shop`, `topic`, and `webhook_id` header values: [4](#0-3) 

The identity binding that should hold is: `HMAC_valid(body) ⇒ shop_header == shop_that_actually_produced(body)`. In this implementation, `HMAC_valid(body)` only proves the body bytes were produced by *some* holder of the app's `api_secret_key` (i.e., the shared app secret used for **all** merchants of the app) — it proves nothing about which shop's header value is legitimate. Because `api_secret_key` is one value shared across every merchant that installs the app, any unprivileged user can install the public app on their **own** store, receive a validly HMAC-signed webhook body for that store, and then replay that same body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers for a victim shop. `HmacValidator.validate` still succeeds (body bytes are unchanged and were legitimately signed), and `Registry.process` will invoke the handler believing the event originates from the victim shop.

### Impact Explanation
This breaks tenant isolation ("cross-tenant access"): a webhook handler that persists or acts on `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering uninstall/GDPR cleanup, altering app-level state keyed by shop domain) can be made to act on behalf of an arbitrary victim shop domain chosen by the attacker, using only content the attacker legitimately generated for their own store. No access token, `client_secret`, or privileged account is required — only the ability to install the app (a normal unprivileged action) and send a crafted HTTP POST to the app's public webhook endpoint.

### Likelihood Explanation
Exploitation requires no secrets: an attacker installs the target public app on a store they control, captures one legitimately delivered webhook (headers + body + valid HMAC), and replays it against the same endpoint with a forged `shop-domain` header. This is straightforward and repeatable by any internet user able to install the app.

### Recommendation
Bind the identity fields to the signature verification, not just the body. Options:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` if compatible with Shopify's documented webhook signing scheme, or
- After body HMAC validation succeeds, additionally verify `request.shop` against a shop known to be associated with this webhook subscription/handler (e.g., cross-check with stored session/shop registry) before dispatching, so header-only fields cannot be trusted blindly for tenant routing.
- At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are **not** authenticated by the HMAC check and must not be used as the sole tenant identifier by consuming applications.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`; Shopify sends a real webhook, e.g. an empty-body `app/uninstalled` topic:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid HMAC of "{}">
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {}
   ```
2. Attacker resends the identical body and valid `X-Shopify-Hmac-Sha256` value to the same endpoint, but swaps the shop header:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <same valid HMAC of "{}">
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {}
   ```
3. `ShopifyAPI::Webhooks::Request.new` parses headers and body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `Digest.hexencode(Base64.decode64(hmac_header))` against `HMAC(raw_body)` — see [5](#0-4) .
4. The registered handler is invoked with `shop: "victim-shop.myshopify.com"`, even though the event content originated from the attacker's own store, as shown at [6](#0-5) .

          received_signature = verifiable_query.hmac
