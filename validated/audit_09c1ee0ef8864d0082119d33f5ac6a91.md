## Finding

### Title
Panic via unchecked `message.from` length in `hyper-fungible-token::on_accept` calldata execution path - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` decodes an attacker-supplied ABI body (`Message::abi_decode`) that arrives from any registered source contract via `pallet-ismp`'s dispatch path. While the `to` (recipient) field is defensively length-checked (`to_bytes.len() == 32` / `== 20` else `Err(HftError::InvalidRecipientLength)`), the `from` field used for optional calldata execution is not, and is sliced with an unchecked arithmetic subtraction.

### Finding Description
In the optional-calldata branch of `on_accept`, when no signature is supplied and the source is an EVM chain, the code does: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else { ... }
```

`message.from` is decoded straight out of the attacker-controlled `body` bytes via `Message::abi_decode(&body)` at [2](#0-1) , with no length validation anywhere before this slice operation — unlike the parallel handling of `to_bytes`, which is explicitly checked for `32` or `20` bytes and otherwise rejected at [3](#0-2) . If `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), producing either an immediate arithmetic-overflow panic or a wildly out-of-range start index, and the subsequent slice indexing (`from_bytes[huge_index..]`) panics with an out-of-bounds index — the on-chain analog of the CVE's out-of-bounds memory access due to a missing bounds check before consuming attacker-supplied length data.

This is reachable by any token bridger that has a registered `(source, from)` contract mapping in `ContractToAsset` — i.e., a whitelisted bridge contract, but the *content* of the cross-chain message body (including the `from` field and optional `data`/`SubstrateCalldata`) is fully attacker-controlled by whoever calls that contract on the source chain, since it's simply ABI-encoded calldata forwarded through ISMP. The attacker only needs to trigger a `PostRequest` whose body decodes to a `Message` with `data` non-empty, `SubstrateCalldata.signature = None`, and `from` shorter than 20 bytes.

### Impact Explanation
A panic during extrinsic execution in a Substrate runtime is not a "graceful" dispatch error — it is a WASM execution trap. Since this occurs inside `on_accept`, which runs as part of ISMP message dispatch/handling for every validating node executing that block, this can halt block execution / cause a state-transition failure across the network, effectively making the affected route/parachain unable to deliver messages until the input is filtered out — matching the accepted impact category "a route unable to deliver messages." At minimum, it is a reliable DoS vector for the hyper-fungible-token bridging channel, triggerable by any party controlling calldata sent through a registered source-chain bridge contract.

### Likelihood Explanation
High — any user of the (already-registered) source EVM contract that constructs and sends a cross-chain transfer with accompanying calldata can control the `from` field length and the `data.signature` presence, requiring no privileged position, validator collusion, or governance action. This is a directly reachable, single-transaction trigger.

### Recommendation
Validate `from_bytes.len()` before slicing, mirroring the `to_bytes` handling: require exactly 20 bytes when `source.is_evm()` (and exactly 32 otherwise), returning a typed `HftError` (e.g. `InvalidSenderLength`) on mismatch instead of performing unchecked arithmetic/slicing.

### Proof of Concept
1. Register a bridge contract `C` on EVM chain `E` as a valid source in `ContractToAsset::<T>` for some local asset.
2. From `E`, dispatch a `PostRequest` to the hyper-fungible-token pallet whose ABI-encoded `body` decodes to a `Message` where:
   - `to` = valid 20-byte address (so recipient conversion succeeds),
   - `amount` = any valid amount,
   - `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`,
   - `from` = a byte string of length ≠ 20 (e.g., 0 or 5 bytes).
3. When `pallet-ismp` delivers this request and `on_accept` executes, the mint/transfer succeeds, then execution reaches `from_bytes.len() - 20`, underflows/panics, and the extrinsic execution traps.

Note: this analysis assumes the ABI type of `message.from` is a dynamic-length `bytes` field (consistent with the fact that the code branches only on `to_bytes.len()` without a hard-coded fixed-size type and lacks any check on `from_bytes.len()`). I was not able to inspect the `Message` ABI/struct definition itself within available context to confirm the exact Solidity type of `from`; if `from` is instead statically typed as a fixed 20-byte `address`/`bytes20` at the ABI level, the length would always be 20 and this specific panic would not be reachable — this should be confirmed by inspecting the `Message` sol! type definition (likely in `modules/pallets/hyper-fungible-token/src/types.rs` or similar) before treating this as fully confirmed.
