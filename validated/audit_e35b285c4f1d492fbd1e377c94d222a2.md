### Title
Missing deadline parameter on `Zap.buy` / `Zap.sell` (and permit variants) allows stale pending trades to be executed and sandwiched at outdated slippage bounds - (File: `packages/contracts/src/Zap.sol`)

### Summary
`Zap.buy`, `Zap.buyWithPermit`, `Zap.sell`, and `Zap.sellWithPermit` are the only unprivileged entry points a trader has to swap USDC for a launched Token (or vice versa), whether the token is still on the bonding curve or has graduated to the HyperSwap V2 pair. None of these functions accept a `deadline` parameter, so a signed/submitted transaction that stays pending in the mempool (low gas price, congestion, etc.) can be mined arbitrarily far in the future and will still execute against whatever price the curve/pool has drifted to, protected only by the caller's originally-chosen `minTokensOut`/`minUsdcOut`, which is stale by the time of execution.

### Finding Description
`Zap.buy` / `Zap.buyWithPermit` call `_buyInternal`, and `Zap.sell` / `Zap.sellWithPermit` call `_sellInternal`: [1](#0-0) 

Neither function signature, nor any internal helper, references `block.timestamp` as a deadline bound. The only protection against price movement is the post-hoc slippage check performed after the trade has already executed: [2](#0-1) 

For the sell path the same pattern applies — slippage is checked only after `redeem`/swap execution: [3](#0-2) 

Post-graduation, both buy and sell route through `_swapOnUniswapV2`, which executes a **direct `pair.swap(...)` call on the HyperSwap V2 TOKEN/LT pair** with no deadline, no sqrt-price-limit-style protection, and no expiry — the only guard is the caller's `minTokensOut`/`minUsdcOut`, computed against the price at signing time: [4](#0-3) 

This is structurally identical to the reported bug class: a swap performed directly against an AMM (Uniswap-V3-style `pool.swap` in the report; here `pair.swap` on HyperSwap V2 and the internal curve `Router.buy/sell`) with a fixed slippage bound but no deadline. If the transaction is delayed — intentionally by the user under-pricing gas, or via a builder/searcher holding it — the reserve ratio (curve reserves, or LT `exchangeRate()` for the LT leg, or the HyperSwap pool ratio) can have moved significantly by execution time. The user's `minTokensOut`/`minUsdcOut`, chosen against the old price, no longer reflects current market conditions and permits a sandwich attack (front-run + back-run) up to the full stale slippage band, or simply forces the user into a bad fill they can no longer cancel by "expiring" the tx.

### Impact Explanation
An MEV searcher monitoring the mempool/private-order-flow can detect a stale, still-valid `Zap.buy`/`Zap.sell` (or their permit variants) whose `minTokensOut`/`minUsdcOut` no longer matches current pool/curve pricing, and sandwich it: front-run to push the price to the edge of the stale slippage tolerance, let the victim's trade execute at the worst allowed price, then back-run to capture the difference. This is a direct value-extraction (theft) vector against ordinary traders using the protocol's primary buy/sell interface, satisfying the "concrete theft ... of trader ... funds" acceptance bar. It affects both the bonding-curve venue and the post-graduation HyperSwap V2 venue, since `Zap` is the sole unprivileged entry point for both.

### Likelihood Explanation
Any user who submits a `Zap.buy`/`sell` transaction with anything less than a maximally tight `minTokensOut`/`minUsdcOut` (which is the normal case, since tight bounds cause unnecessary reverts on legitimate minor price movement) is exposed whenever their transaction is delayed for any reason — low gas price during congestion, private relay delays, or a searcher intentionally holding/replaying it. Given HyperEVM's throughput and typical wallet UX (setting a generous slippage percentage without any transaction expiry), this is a realistic, low-cost, high-frequency opportunity for MEV extraction rather than a theoretical edge case.

### Recommendation
Add a `deadline` parameter to `Zap.buy`, `Zap.buyWithPermit`, `Zap.sell`, and `Zap.sellWithPermit` (mirroring the `PermitData.deadline` pattern already used for permits) and revert with a clear error (e.g. `Expired()`) if `block.timestamp > deadline`, checked at the very start of `_buyInternal`/`_sellInternal` before any state-changing calls execute.

### Proof of Concept
1. Alice calls `Zap.buy(token, usdcAmount, minTokensOut, referrer)` for a graduated token, with `minTokensOut` computed against the current HyperSwap V2 pair price, but submits with low gas so it sits pending.
2. Time passes; the HyperSwap TOKEN/LT reserve ratio moves substantially (organic trading or LT `exchangeRate()` drift).
3. A searcher, seeing Alice's pending tx and her now-stale `minTokensOut`, front-runs with a trade that pushes the pool price to the edge of what still satisfies Alice's `minTokensOut` in `_buyInternal`'s post-hoc check at `Zap.sol:256`.
4. Alice's transaction executes via `_swapOnUniswapV2` (`Zap.sol:542-562`) at the worst price her stale bound still permits.
5. The searcher back-runs, extracting the difference — Alice receives the protocol-guaranteed minimum but loses value she would not have lost had the trade executed near submission time, and had no way to bound the transaction's execution window since no `deadline` parameter exists on any `Zap` buy/sell entry point.

    function _buyInternal(
        address tokenAddress,
        uint256 usdcAmount,
        uint256 minTokensOut,
        address referrer
    ) internal returns (uint256 tokensOut) {
        if (usdcAmount == 0) revert InvalidInput();
        if (tokenAddress == address(0)) revert InvalidInput();
        if (usdcAmount < minUsdcAmount()) revert BelowMinAmount();
        Bonding bonding_ = _s().bonding;
        if (bonding_.creatorOf(tokenAddress) == address(0)) revert TokenNotTrading();
        if (bonding_.isGraduating(tokenAddress)) revert TokenIsGraduating();

        uint256 grossSpent;
        uint256 actualFee;
        (tokensOut, grossSpent, actualFee) = _executeBuy(tokenAddress, usdcAmount);

        if (tokensOut < minTokensOut) revert SlippageExceeded();

    function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.
        amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn);

        IERC20(tokenIn).safeTransfer(pair, amountIn);

        (uint256 amount0Out, uint256 amount1Out) = inIsToken0 ? (uint256(0), amountOut) : (amountOut, uint256(0));
        IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
    }
