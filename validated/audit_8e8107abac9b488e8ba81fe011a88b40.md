### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unauthenticated HTTP headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but the signature only covers the raw JSON body. The `shop`, `topic`, `api_version`, and `webhook_id` values used to route and label the payload downstream are read straight from HTTP headers that are never included in the signed bytes, breaking the binding "bytes verified == bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and compares it to the `hmac-sha256`/`x-shopify-hmac-sha256` header value: [2](#0-1) 

However, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from separate, unsigned headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands `request.topic` and `request.shop` (both unauthenticated) to the caller's handler as trusted identity metadata: [4](#0-3) 

Because the app's `api_secret_key` (`Context.api_secret_key`) is a single shared secret used for HMAC verification across every shop/tenant that installs the app (not a per-shop secret), a valid `(body, hmac)` pair only proves "this body was produced by/for this app," not "this body belongs to shop X." Any entity that can obtain one genuine `(body, hmac)` pair signed with the app's secret — e.g., by installing the app on their own store as an ordinary, unprivileged merchant and receiving real webhooks for their own shop — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `shop-domain`, `topic`, and `webhook-id` headers. `HmacValidator.validate` still returns `true` because those headers are outside the signed string, and `Registry.process` will dispatch the payload to the handler labeled as coming from an arbitrary victim shop/topic of the attacker's choosing.

This is the direct analog of the reported inflation attack: the "shares" check (HMAC) never covers the "assets" that downstream logic actually consumes and trusts (shop identity, topic, delivery id), so a value manipulated outside the verified channel produces state that a legitimate check erroneously accepts.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (produced from `request.shop`) as a tenant key — e.g., to look up/store per-shop data, invalidate a shop's cache, mark a shop as uninstalled, or process `customers/redact`/`shop/redact` compliance actions — can be made to act on the wrong tenant's data using attacker-supplied, arbitrary shop/topic labels riding on a validly-signed but otherwise unrelated payload. This is a cross-tenant integrity break stemming entirely from this gem's webhook verification API, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker does not need the app's `api_secret_key` itself — only a single genuine webhook delivery for a shop they control (trivial: install the app themselves, or observe any webhook they legitimately receive), which they can then replay with the identity headers rewritten. `HmacValidator` performs no binding between the signed body and the `shop`/`topic`/`webhook_id` headers, so this requires no credential theft, TLS interception, or privileged access — only being an ordinary merchant/user of the app.

### Recommendation
Include the identity-critical fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., require the app to independently confirm `shop` against a value obtained through an authenticated channel, such as the session/shop that requested the corresponding action, before trusting `WebhookMetadata#shop`). At minimum, document prominently that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated and must never be used as a tenant identity key without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and a valid `x-shopify-hmac-sha256` header `H` computed over `B` with the app's shared secret.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the exact same body `B` and header `H`, but sets:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: customers/redact` (or any registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only checks presence, not authenticity) — `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — `lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — causing the host app to perform a redact/compliance/data-mutation action attributed to `victim.myshopify.com` using attacker-chosen content.
