### Title
Pool `repay` refunds the declared overpayment out of custody without an inbound transfer — unprivileged drain of supplier funds - (File: contracts/pool/src/ops/repay.rs)

### Summary
The bug class in the reference report is an error path that releases/accounts the same value twice. The XOXNO Lending analog lives in the pool's repay leg: `ops::repay::apply` trusts that the controller already transferred `action.amount` into the pool, computes an `overpayment = amount - debt` derived purely from the *declared* amount, and pays that overpayment back to `payer` via `cache.transfer_out` — without debiting `cash`, without `require_reserves`, and without any measurement that the inbound funds ever arrived. Calling `pool::repay` directly on a market with little or no debt makes the entire declared amount "overpayment," which is paid out of supplier custody while the books stay untouched.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `accounting` calls `cache.resolve_repay(amount, position)` which returns `(burned, overpayment)` where `overpayment` is the excess of the declared `action.amount` over the position's current debt (`net_repay = amount - overpayment`, and `RepayRoundsToZeroShares` passes on its `net_repay == 0` disjunct). Only `net_repay` is credited to cash via `cache.credit_cash(net_repay)`; `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` [1](#0-0) . The doc comment states the assumption: "The controller transfers the repay amount into the pool before this call" [2](#0-1) . But the pool entrypoint itself performs no inbound transfer and does not verify custody actually grew by `amount`; the refund leg is a double-payment of value never received. The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` demonstrates exactly this: a `repay` against a market with zero debt credits `actual_amount == 0` yet `assert_unfunded_refund_drained_custody` confirms the full declared amount left pool custody with the book untouched [3](#0-2) . The same shape exists in `ops::recapitalize::apply`, where `refund = amount - applied` is transferred out with only `applied` credited to cash [4](#0-3) , and its "bounded by custody" test only shows the payout is capped by the SAC balance check, not prevented [5](#0-4) .

### Impact Explanation
Theft of user funds. An unprivileged address calls `pool::repay` (or `controller::repay`-adjacent paths if the pool entrypoint is auth-gated only by payer `require_auth`, which the direct test call shows it is not for the inbound) with `amount` equal to the pool's token balance on a market with no debt on their position. The whole amount is refunded out of supplier custody; `cash`/`borrowed`/`supplied` are unchanged, so subsequent withdrawals revert or socialize the loss across remaining suppliers. The identical refund-without-cash-debit in `recapitalize` lets a caller declare any `amount` above the backing shortfall and receive `amount - shortfall` back without ever funding it, bounded only by live custody.

### Likelihood Explanation
A single unprivileged transaction; no price manipulation, no timing, no governance action needed. The reachable surface is `repay` (permissionless per the allowed entrypoints) and `recapitalize` (explicitly permissionless). The only mitigating uncertainty is whether production deployments restrict `pool::repay` to the controller address — the code shows no such gate, and the harness test drives the pool client directly and succeeds. Even via the controller path, if the controller's inbound transfer uses declared rather than measured amounts (measured-receipt settlement is used elsewhere, e.g. `transfer_amount_measured` in the recapitalize path of the controller), the same declared-vs-actual gap applies for fee-on-transfer or hook tokens.

### Recommendation
Measure the inbound transfer instead of trusting the declaration: snapshot the pool's token balance before crediting and bound `overpayment`/refund by the measured received amount, as `transfer_amount_measured` already does on the controller side. Alternatively, gate `pool::repay`/`recapitalize` behind a controller-only check and have the controller pass the measured received amount rather than the requested one. The refund should never exceed `measured_inbound - net_repay`, and the refund leg should be asserted against `require_reserves` so custody cannot fall below the book.

### Proof of Concept
Encoded already in `contracts/pool/tests/flows.rs:3589-3610`:

```rust
// contracts/pool/tests/flows.rs
let custody_before = token.balance(&t.pool);
assert_eq!(before.borrowed, 0);              // no debt on the market
// Declare `amount == custody_before`; nothing is transferred in.
let credited = t.client()
    .repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0)
    .actual_amount;
assert_eq!(credited, 0);                     // zero debt retired
// ...assert_unfunded_refund_drained_custody: payer gains custody_before,
// pool custody drops by custody_before, book (cash) unchanged.
```

The `overpayment` leg in `ops::repay::apply` (`cache.transfer_out(payer, overpayment)` where `overpayment == amount` when `current_debt_ceil == 0`) is the double-release: the protocol "frees" the declared value once as a refund, although it was never received — mirroring the rtase double-free where the same skb was released by both the fragment cleanup and the common error path.

/// The refund gap is not specific to `recapitalize`. Two pool legs refund an
/// excess derived from a declared inbound amount, not from the cash book:
/// `ops::recapitalize::apply` (the excess over the shortfall) and
/// `ops::repay::apply` (the excess over the debt). Neither refund debits `cash`
/// or passes `require_reserves`.
///
/// A repay against a market with no debt makes the entire declared amount an
/// overpayment: `current_debt_ceil` is zero, so `resolve_repay` takes the
/// full-close branch and `net_repay` is zero. The `RepayRoundsToZeroShares`
/// assert in `ops::repay::accounting` passes on its `net_repay == 0` disjunct,
/// and the whole amount is refunded out of real custody with the book untouched.
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
