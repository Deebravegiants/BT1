### Title
Fraud-check pipeline silently treats missing/unavailable operand data as "no fraud detected" instead of surfacing the failure - (File: fraud-engine/src/pipeline.rs)

### Summary
The external report describes `UniswapAnchoredView.getUnderlyingPrice` deviating from its interface contract by reverting instead of returning the documented "unavailable" sentinel (zero) when no price data exists. The analogous defect in `orb-core` is the inverse failure mode of the same bug class — a function whose behavior on "data unavailable" silently diverges from what the caller relies on for a security decision. In `fraud-engine/src/dsl.rs`, `Rule::evaluate` returns an `Err` when an operand path referenced by a fraud rule cannot be found in the serialized signup data [3](#0-2) . `Pipeline::run`, which drives fraud enforcement for a signup, catches this `Err` with `.ok()` and stores `None` as the check result without logging the error or propagating a failure signal [4](#0-3) .

### Finding Description
`Rule::evaluate` builds an `evalexpr` context by walking dot-separated JSON paths (`operand_mapping`) into the serialized signup/pipeline data via `extract_value_from_serialized_data`, which returns `None` if any segment of the path is missing [5](#0-4) . When a path is missing, `build_evalexpr_context` converts this into an `eyre!("failed to extract operand...")` error [6](#0-5) , and `evaluate` propagates that `Result::Err` up to the caller.

`Pipeline::run` iterates over all configured fraud `checks`, calls `check.rule.evaluate(&serialized_data)`, and stores the boolean result — but converts any `Err` into `None` via `result.ok()` before inserting it into `check_results` [7](#0-6) . No error is surfaced to the top-level `Result<Report>` returned by `run`; the pipeline reports success (`Ok(Report {..})`) even though one or more individual fraud checks silently failed to evaluate due to missing data [8](#0-7) .

This mirrors the reported bug class: a function that is expected to have a well-defined, safe behavior when the queried data is unavailable (analogous to `PriceOracle`'s "return zero" contract) instead has an implicit, untested, and unlogged behavior — here, "unavailable" data silently becomes a `None` check result rather than an explicit failure that halts or flags the signup. Just as the oracle bug is "not tested in the contract's test suite," this path — the `Err` branch of `check.rule.evaluate` inside `Pipeline::run` — has no unit test coverage in `fraud-engine/src/pipeline.rs`; the only pipeline tests use well-formed data (`test_pipeline_run`, `test_checks_with_same_identifier`).

### Impact Explanation
If a fraud-detection rule's operand path stops resolving (e.g., due to a schema/field-name change in the pipeline/biometric-capture data structures, a partially-populated capture, or any refactor that renames/removes a field referenced by `operand_mapping`), the corresponding check silently evaluates to `None` rather than causing an error that operators or the signup flow can act on. Depending on how downstream code (e.g., `Report::fraud_detected` and its consumer in `src/plans/fraud_check.rs`) treats a missing/`None` result, this can result in a fraud rule being effectively disabled without any alert — a fail-open condition in a security enforcement path (fraud/liveness) rather than a fail-closed or explicit-error condition. This is a deviation from safe defaults similar in spirit to the referenced report: the interface consumer (`Pipeline::run`'s caller, ultimately the signup flow) cannot distinguish "check ran and found no fraud" from "check silently failed to run at all."

### Likelihood Explanation
Likelihood is moderate: exploitation does not require an attacker to control fraud data directly, but any legitimate code change that alters the shape of serialized pipeline data (adding/renaming fields consumed by `operand_mapping`) — a fairly common occurrence during ordinary iteration on the fraud engine or biometric pipeline schema — would trigger this silent-failure path for every affected signup, without any test currently catching it.

### Recommendation
`Pipeline::run` should not use `.ok()` to discard evaluation errors. Instead, either:
1. Propagate the error from `check.rule.evaluate` up as `Err` from `Pipeline::run` so a broken/misconfigured rule halts the fraud pipeline explicitly, or
2. Keep the per-check `Option<bool>` `None` semantics, but log the error (`tracing::error!`) and route it to `Report` such that consumers (`fraud_detected()` and `src/plans/fraud_check.rs`) can distinguish "not evaluated due to error" from "evaluated: no fraud" and treat the former as fail-closed (i.e., a signup-affecting condition) rather than silently ignoring it.
Add unit tests in `fraud-engine/src/pipeline.rs` that exercise a rule referencing a non-existent operand path and assert on the resulting `Report`/`fraud_detected()` behavior, mirroring the recommendation in the source report to add tests for the "price unavailable" branch.

### Proof of Concept
1. Construct a `Pipeline` with a `Check` whose `Rule::operand_mapping` references a path not present in the serialized signup data (e.g., `"nonexistent.field"`), as already demonstrated in the existing unit test `test_rule_evaluation`'s "using non-existent operand path" case, which asserts `rule.evaluate(...).is_err()` [9](#0-8) .
2. Run this `Check` through `Pipeline::run`. Observe that `Pipeline::run` returns `Ok(Report { check_results: {"id": CheckResult { enabled: true, result: None }} })` rather than surfacing any error [10](#0-9) .
3. Trace how `Report::fraud_detected()`/`CheckResult.result == None` is consumed by `src/plans/fraud_check.rs` to confirm whether a `None` result is treated equivalently to "no fraud detected," which would confirm the fail-open impact (this final consumption logic was not fully inspected in this pass and should be verified directly in the repository).

    fn build_evalexpr_context(
        &self,
        serialized_data: &serde_json::Value,
    ) -> Result<HashMapContext> {
        let mut context = HashMapContext::new();
        for (name, path) in &self.operand_mapping {
            let serde_value = extract_value_from_serialized_data(path, serialized_data)
                .ok_or_else(|| eyre!("failed to extract operand ({}, {})", name, path,))?;
            let evalexpr_value = serde_to_evalexpr_value(serde_value)?;
            context.set_value(name.to_owned(), evalexpr_value)?;
        }

        Ok(context)
    }

fn extract_value_from_serialized_data<'a>(
    path: &str,
    serialized_data: &'a serde_json::Value,
) -> Option<&'a serde_json::Value> {
    let mut current_value = serialized_data;
    for key in path.split('.') {
        current_value = current_value.get(key)?;
    }
    Some(current_value)
}

    pub fn run<T: Serialize>(&self, data: &T) -> Result<Report> {
        let serialized_data = serde_json::to_value(data)?;
        let mut check_results = HashMap::with_capacity(self.checks.len());

        for check in &self.checks {
            let result = check.rule.evaluate(&serialized_data);
            tracing::info!("{}: {:?}", check.identifier, result);

            if check_results
                .insert(check.identifier.clone(), CheckResult {
                    enabled: check.enabled,
                    result: result.ok(),
                })
                .is_some()
            {
                return Err(eyre!(
                    "pipeline checks with the same identifier \"{}\" found.",
                    check.identifier
                ));
            }
        }

        Ok(Report { check_results })
    }
