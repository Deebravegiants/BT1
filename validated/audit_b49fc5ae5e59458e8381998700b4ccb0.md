### Title
Missing native-token refund in Tron `IntentGatewayV2.placeOrder()` permanently strands user ETH/TRX in the gateway - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` computes a running `msgValue` (native token remaining after escrowing inputs and swapping for `order.fees`) but never returns any leftover to the caller at the end of the function, unlike the canonical EVM implementation which explicitly refunds unspent native tokens.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` tracks `msgValue = msg.value` and decrements it as native inputs are escrowed [1](#0-0) . When `order.fees > 0` and the caller pays with native token, the function calls `swapETHForExactTokens{value: msgValue}(order.fees, ...)` to buy the exact fee-token amount needed [2](#0-1) . Uniswap's `swapETHForExactTokens` only consumes the ETH required to purchase `order.fees` worth of the output token and refunds the remainder to `msg.sender` of the swap call — which is the `IntentGatewayV2` contract itself, not the original user. That refunded ETH lands in the gateway's balance.

Compare this to the mainline EVM contract `evm/src/apps/IntentGatewayV2.sol`, whose `placeOrder()` performs the identical fee-swap logic but then explicitly refunds any leftover `msgValue` to `msg.sender` before returning [3](#0-2) . This refund step, and the corresponding `msgValue -= amounts[0]` adjustment that computes the true swap consumption, is absent from the Tron variant's `placeOrder()`, whose function ends immediately after crediting escrow and emitting `OrderPlaced` with no refund path [4](#0-3) .

There is no `msgValue -= amounts[0]` after the swap either (the Tron code doesn't even capture the swap's return value), and no residual-value transfer anywhere else in the function body. Any TRX/ETH sent beyond what native inputs plus the exact swap cost require is silently absorbed by the contract balance.

### Impact Explanation
Every user who overestimates the native-token amount needed to cover `order.fees` (a routine client-side estimation, since exact Uniswap V2 output pricing at execution time is unknown in advance, as documented for the sibling EVM contract's equivalent test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` [5](#0-4) ) permanently loses the unspent difference. There is no sweep, withdraw, or admin recovery function found in the Tron contract for reclaiming stranded native balance, so funds accumulate unrecoverably in the contract — a permanent loss/freezing of user funds triggered by a normal, single `placeOrder` transaction from an ordinary user.

### Likelihood Explanation
High. Any caller funding the order fee via native token (the common path shown across the codebase's docs and tests, e.g. `docs/content/developers/evm/intent-gateway/placing-orders.mdx` lines 275-284) must overshoot the exact swap cost to guarantee `swapETHForExactTokens` succeeds, since the precise AMM cost cannot be known synchronously at call time. This is not a rare edge case but the expected normal usage pattern for native-fee payment, making the loss occur on essentially every such order placement.

### Recommendation
Mirror the mainline EVM implementation: capture the `amounts` return value from `swapETHForExactTokens` and decrement `msgValue` accordingly, then after all escrow/fee logic, add:
```solidity
if (msgValue > 0) {
    (bool sent, ) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
before emitting `OrderPlaced`, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 394-397.

### Proof of Concept
1. User calls `placeOrder` with an ERC-20 (non-native) input and sets `order.fees = 1e18` (1 fee-token unit), sending `msg.value = 5 ether` intending to cover the Uniswap swap for fees.
2. Execution enters the `else` branch (no predispatch call) and escrows the ERC-20 inputs without touching `msgValue` [6](#0-5) .
3. Since `order.fees > 0` and `msgValue == 5 ether > 0`, the contract calls `swapETHForExactTokens{value: 5 ether}(1e18, ...)` [7](#0-6) ; suppose the swap only actually costs `0.001 ether`.
4. The Uniswap router refunds the remaining `~4.999 ether` to `address(this)` (the gateway), not to the user.
5. `placeOrder` returns without any refund step, so that `~4.999 ether` stays locked in the gateway contract's balance permanently, with no withdrawal mechanism identified in the contract for the user or protocol to recover it.

            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
