### Title
Unbounded resource consumption in `pallet-ismp::handle_unsigned` due to fixed weight for arbitrarily large/expensive message batches - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`handle_unsigned` is an unsigned, fee-free extrinsic that anyone can submit with a `Vec<Message>` batch of ISMP requests, responses, timeouts, or consensus messages. Its declared weight is a hard-coded constant (`weight()` → `Weight::from_parts(300_000_000, 0)`), completely independent of the number of messages in the batch or the size/complexity of the proofs they carry. Because it is unsigned, it is also fully re-executed by every node's transaction pool via `validate_unsigned` before being gossiped or included in a block — meaning the real (unbounded) computational cost is paid at least twice per submission, by every validating node, for zero fee.

### Finding Description
`Pallet::execute` iterates over the *entire* caller-supplied `messages: Vec<Message>` and, for every message, calls `handle_incoming_message`, which dispatches to expensive cryptographic verification routines: trie/child-trie membership and non-membership proof verification (`verify_membership`/`verify_non_membership` walking arbitrarily large `StorageProof` sets), MMR batch-proof verification, BEEFY/consensus-client verification, and per-request dedup/hashing: [1](#0-0) 

The dispatchable itself is declared with a static weight regardless of `messages.len()` or the size of any embedded `Proof`: [2](#0-1) [3](#0-2) 

`handle_unsigned` requires only `ensure_none(origin)` — no signature, no fee — so any party can submit it: [4](#0-3) 

Worse, `ValidateUnsigned::validate_unsigned` calls `Self::execute(messages.clone())` a *second* time (in addition to the actual dispatch execution) purely to validate the transaction before it enters the pool or is gossiped: [5](#0-4) 

This means every peer's node performs the full, unmetered proof-verification workload on unsigned gossip before any weight accounting or fee-based rejection can occur — a classic uncontrolled resource consumption (CWE-400/CWE-770) pattern: cost of processing scales with attacker-supplied input size (batch length × proof size, e.g. multi-request `RequestMessage`/`ResponseMessage`, deep MMR multiproofs, large `StorageProof` trie-node sets), but the accounted/limited weight does not.

Other parts of the codebase show engineers were aware of and closed similar gaps (e.g., `pallet-call-decompressor`'s zstd-bomb gate, Pharos's `MAX_PROOF_DEPTH`, BEEFY's `MaxProofSize`), but the core `handle_unsigned` extrinsic path itself still charges a flat weight irrespective of the batch it processes.

### Impact Explanation
An attacker can craft a single `handle_unsigned` call (or a burst of them) containing a large `Vec<Message>` with many `RequestMessage`/`ResponseMessage`/`TimeoutMessage` entries, each carrying maximal proof payloads (bounded only by the extrinsic/block-length limit, not by declared weight). Because the extrinsic is free and unsigned:
- It is validated (fully executed) by every node's transaction pool on gossip, and again on block execution/import — multiplying the CPU cost network-wide.
- The weight system's purpose — bounding per-block execution time to keep block production live — is defeated because the accounted weight (300M, i.e. a fixed fraction of block weight) does not reflect true execution time, which scales with proof size and message count.
- This can degrade block production time, cause missed slots, or be used to censor/starve legitimate relayer traffic, satisfying "a route unable to deliver messages" under sustained attack. This is a High-severity, protocol-wide DoS analogous to CVE-2022-23913 (uncontrolled resource consumption via unbounded/mis-costed message processing).

### Likelihood Explanation
High likelihood: the entry point requires no signature, no fee, and no allowlist — literally anyone able to submit an extrinsic (or reach the RPC/gossip layer) can trigger it, and the tx-pool's own validation logic (`validate_unsigned`) guarantees the expensive path runs pre-inclusion on every node that receives the gossiped transaction, not just the block author. The only natural throttle is the runtime's max extrinsic/block length, which bounds message-batch and proof size but not the CPU work needed to verify them.

### Recommendation
Make the weight charged by `handle_unsigned` proportional to the actual work implied by the submitted batch (e.g., a per-message and per-proof-byte weight component, similar to how `pallet-call-decompressor` bounds `encoded_call_size` before doing work), and/or impose an explicit cap on `messages.len()` and per-message proof size before invoking `Self::execute`. Consider charging weight based on `messages.encode().len()`/proof length pre-execution (a cheap check) and rejecting oversized batches early in both `validate_unsigned` and the dispatchable, mirroring the `MaxCallSize`/`CallSizeOutOfBound` pattern already used in `pallet-call-decompressor`.

### Proof of Concept
1. Construct a `Vec<Message>` containing many `Message::Request(RequestMessage { requests: <N PostRequests>, proof: <maximal Proof up to extrinsic-length limit>, .. })` entries, chained until the encoded extrinsic approaches the runtime's max extrinsic/block length.
2. Submit as an unsigned `Ismp::handle_unsigned(messages)` extrinsic via RPC (`author_submitExtrinsic`) to multiple full nodes simultaneously.
3. Each receiving node's `ValidateUnsigned::validate_unsigned` invokes `Self::execute(messages.clone())`, which walks every request's trie/MMR proof verification — a heavy CPU operation — before the transaction is even accepted into the pool, all while the runtime's declared weight for the call remains the fixed `Weight::from_parts(300_000_000, 0)`.
4. Repeating this from multiple sources concurrently multiplies validation cost network-wide with no fee cost to the attacker, since `handle_unsigned` is free and unsigned.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
