### Title
Webhook `shop-domain` identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, then hands the caller-supplied `x-shopify-shop-domain` header straight to the handler as the identity of the shop that "sent" the webhook. Because the HMAC signature covers only the request body and not the shop header, an attacker who possesses one validly-signed webhook body (trivial to obtain, since the same `api_secret_key` is used for every shop the app is installed on) can replay that body with an arbitrary `shop-domain` header and have it accepted as authentic for a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC using exactly this signable string and, once it passes, immediately forwards `request.shop` (attacker-controlled header) to the registered handler as trusted identity data: [3](#0-2) 

`HmacValidator.validate` only proves that `raw_body` was signed with the app's `api_secret_key` — it says nothing about which shop the body/HMAC pair originated from: [4](#0-3) 

Because Shopify webhooks for a given app all share the same `api_secret_key` regardless of which merchant shop triggered the event, a valid `(raw_body, hmac)` pair captured from one shop (e.g. the attacker's own store, where they installed the app) remains cryptographically valid when replayed with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header pointing at a different, victim shop.

The broken identity binding, stated as an equality: the gem implicitly assumes `hmac-verified body == shop-attributed identity`, but in reality `HMAC covers {raw_body}` while `handler-trusted identity == {raw_body, shop header}`, and the `shop` component is never bound to the signature.

### Impact Explanation
This is a cross-tenant identity confusion: any host application that uses `WebhookMetadata#shop` (or `request.shop`) to determine which shop's data/session/credentials to act on — the exact intended and documented use per `docs/usage/webhooks.md` (`data.shop` is handed to the app's handler) — can be tricked into processing attacker-controlled event content under an arbitrary victim shop's identity, entirely through requests this gem itself certifies as "verified". No access token, `api_secret_key`, or privileged access is needed by the attacker; only the ability to install the target app on their own shop (an ordinary, unprivileged capability) to obtain one legitimately-signed body/HMAC pair.

### Likelihood Explanation
High. All that is required is: (1) install the app being audited on an attacker-controlled shop to receive one real webhook of any subscribed topic, (2) capture the raw body and its `hmac-sha256` header, (3) POST that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to the victim's `myshopify.com` domain. `Registry.process` performs no additional binding check between the two.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed payload verification path, or independently verify that `request.shop` corresponds to a shop that is actually expected to be sending this specific webhook (e.g., cross-check against a per-shop registration/session record) before invoking the handler. At minimum, document prominently that `request.shop` is *not* authenticated by the HMAC and must not be trusted as-is by consuming applications; better, have `Registry.process` reject processing unless the caller supplies the expected shop and it matches `request.shop`.

### Proof of Concept
```ruby
# 1. Attacker installs the app on attacker-shop.myshopify.com and receives a real webhook:
raw_body = '{"id": 1}'
hmac_header = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the exact same (raw_body, hmac) pair but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,          # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. This passes HMAC validation, because HmacValidator only checks raw_body:
ShopifyAPI::Webhooks::Registry.process(forged_request)
# => handler invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
