### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the *unauthenticated* `shop`, `topic`, and `webhook_id` header values straight to the app's `WebhookHandler`. The identity binding "shop the payload is attributed to" ≟ "shop actually covered by the HMAC" is broken: only the body bytes are signed, while the tenant-identifying header is not.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which in turn calls `to_signable_string`, i.e. body-only) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unsigned `String` field passed on to the consuming app's `handle` method: [5](#0-4) 

This is the same bug class as the `Ext01Handler` report: a field that is *acted upon* (here, the tenant/shop identity used to route and process webhook data) is not covered by the same authenticator (`msg.value`/HMAC) that is supposed to bind the whole operation together. Concretely, the equality that should hold but doesn't is:

`shop authenticated by HMAC` ≠ `shop the app processes the payload as`

Since the app's `client_secret` (used to compute the webhook HMAC) is shared across every shop that installs the app, any attacker who has legitimately installed the app on a shop they control receives real, validly-HMAC'd webhook deliveries for that shop. Because `shop` (and `topic`/`webhook_id`) are not part of the signed content, the attacker can replay the identical `raw_body` + `X-Shopify-Hmac-SHA256` value to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
This allows cross-tenant data injection/spoofing: an attacker-controlled webhook body can be attributed to an arbitrary victim shop identity that the app never sent that payload for. Any host application that uses `data.shop` from `WebhookMetadata` to scope database writes, trigger tenant-specific side effects, or select which merchant's session/state to mutate can have its per-tenant isolation violated by a user who only controls their own shop's installation — i.e., cross-tenant access without ever obtaining the victim's credentials.

### Likelihood Explanation
Requires only that the attacker installs the app themselves (a normal, unprivileged action available to anyone) on their own store, captures one legitimate webhook delivery, and replays it with a modified `shop-domain` header at the app's public webhook endpoint. No access to the app's `client_secret`, the victim's access token, or any privileged capability is needed.

### Recommendation
Bind the tenant/topic identity to the authenticated signature, or otherwise cryptographically or out-of-band verify that `shop` matches an app installation the caller is authorized to represent, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into the OAuth HMAC), or
- Require the calling application to verify that `request.shop` corresponds to a session it created for that specific webhook delivery before trusting it, and document this requirement clearly since the current API silently exposes an unauthenticated `shop` field as if it were verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw body, using app client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: abcd-1234
   Body: {"id": 1, "note": "malicious note"}
   ```
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, only changing:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` in [6](#0-5)  still returns `true` because it only checked the raw body.
4. `ShopifyAPI::Webhooks::Registry.process` in [3](#0-2)  constructs `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled data as if it belonged to `victim-shop`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
