Based on my review of `contracts/Hinkal.sol`, `contracts/HinkalBase.sol`, `contracts/HinkalHelper.sol`, and `contracts/CircomDataBuilder.sol`, I found an analog to the ArtGobblers class of bug: a place where a value-bearing on-chain effect (commitment insertion into the Merkle tree) is decoupled from the equality check that is supposed to gate it, exactly like `gobblersOwned` being incremented outside of what `_mint()` already accounted for.

### Title
On-chain commitment array is sized by `utxoSet.length` but populated by an unrelated address-matching loop, letting `insertCommitments` mint zero/duplicate leaves outside the balance equation - (File: `contracts/Hinkal.sol`, `contracts/HinkalBase.sol`)

### Summary
In `Hinkal.transact()`, the array that will become on-chain Merkle leaves is allocated with a size equal to `utxoSet.length`, but it is filled by a nested loop that only writes a slot when an external-action-returned UTXO's `erc20Address` happens to match one of the (attacker/prover-supplied) `circomData.erc20TokenAddresses[i]` entries. Neither the fixed allocation size nor the downstream `insertCommitments()` counts insertion by the number of actual matches — `insertCommitments` uses `onChainCommitments.length` directly. This breaks the equality the code itself documents ("CHANGE IN BALANCE SHOULD EQUAL TO 1) change in off-chain utxos 2) change in on-chain utxos").

### Finding Description
In `contracts/Hinkal.sol`: [1](#0-0) 

`onChainCommitments` is allocated with `new OnChainCommitment[](utxoSet.length)`, but is only written at `onChainCommitments[onChainCommitmentCounter]` when `utxoSet[j].erc20Address == circomData.erc20TokenAddresses[i]` for some `i`. Because `circomData.erc20TokenAddresses` is attacker-supplied calldata (only length-checked against `dimensions.tokenNumber` in `dimensionsCheck`, with no uniqueness constraint), and because `utxoSet` itself is produced at runtime by `_externalTransact()` calling into an admin-registered `IExternalActionV2.runAction()` (not fixed by the ZK proof), the number of true matches can diverge from `utxoSet.length`: [2](#0-1) 

If a UTXO's token address is never present in `circomData.erc20TokenAddresses` (i.e., the token is outside the balance-equation loop entirely, since that loop only ranges `i < circomData.erc20TokenAddresses.length`), its slot in `onChainCommitments` is never written and stays a zero-valued struct (`commitment == 0`). This zero-valued struct is still counted and inserted as a real leaf in `HinkalBase.insertCommitments()`: [3](#0-2) 

`length += onChainCommitments.length;` (not `onChainCommitmentCounter`) and the leaf-copy loop `leaves[index++] = onChainCommitments[i].commitment;` blindly copies every slot, matched or not. Meanwhile, the value that the external action actually moved for that unmatched token address never appears in the balance-equation check at all, because that check only iterates over `circomData.erc20TokenAddresses`: [4](#0-3) 

This is structurally identical to the ArtGobblers bug: an on-chain effect (`_mint`'s `gobblersOwned++`) already happened, and a second, independently-computed adjustment (`+1` in `mintLegendaryGobbler`) is applied without regard to what the first one already accounted for — here, the "supposed to be exhaustively reconciled" `utxoAmount`/balance-equation accounting and the "actually inserted" `onChainCommitments` array are populated by two different, unsynchronized index spaces (`circomData.erc20TokenAddresses` iteration order vs. raw `utxoSet` array position), so the equality "every real token movement corresponds to exactly one committed leaf, validated by the balance-diff check" does not hold when the address lists diverge.

### Impact Explanation
Real tokens received by Hinkal from an external action for a token address that is absent from (or duplicated relative to) `circomData.erc20TokenAddresses` are (a) never validated against any `balanceDif` requirement, and (b) never given a real, spendable commitment in the Merkle tree — the value is stranded in the Hinkal contract with no UTXO owner, while a meaningless zero-value leaf is permanently written to the tree instead. This is a permanent freezing of user funds: the depositor who triggered the external action loses access to the returned value with no code path to recover it, and the shielded pool's Merkle tree gains a garbage leaf. This matches the "value moved by Hinkal or an external action but not counted in the balance equation" analog category and the "permanent freezing of user funds" impact tier.

### Likelihood Explanation
Reaching this requires a registered `IExternalActionV2` implementation whose `runAction()` can return a `utxoSet` entry for a token not present (or over/under-represented) in the caller-supplied `circomData.erc20TokenAddresses` array — a plausible scenario for swap/bridge-style external actions where the exact set of output tokens is not enumerable in advance the same way the dimension array is constructed. I could not fully confirm the concrete `utxoSet`-construction logic of `contracts/external-actions/swaps/ExternalActionSwap.sol` within the available investigation budget, so the exact trigger path through a specific registered external action is not conclusively verified — this is a real, code-level uncertainty that would need to be checked in the actual `runAction()` implementation before treating this as fully proven end-to-end.

### Recommendation
- Size `onChainCommitments` and drive `insertCommitments`'s leaf count from the actual match/write counter (`onChainCommitmentCounter`), not from `utxoSet.length` or `onChainCommitments.length`.
- Require that `utxoSet` returned by any external action can only contain `erc20Address` values that are a subset of `circomData.erc20TokenAddresses`, and revert if any `utxoSet` element fails to match an index, rather than silently dropping it.
- Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck()` so no token index can absorb another's matches.

### Proof of Concept
Not independently executable without the concrete `runAction()` implementation of a registered external action (needed to demonstrate a `utxoSet` element whose `erc20Address` is absent from `circomData.erc20TokenAddresses`). The structural defect (fixed-size array populated by an unrelated matching loop, and `insertCommitments` using raw array length instead of the write counter) is directly demonstrable by code inspection at the cited lines in `contracts/Hinkal.sol:92-132` and `contracts/HinkalBase.sol:78-102`.
