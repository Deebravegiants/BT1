### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used for tenant dispatch from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed only over the raw request body. Since the shop field is never bound into the signed bytes, any request with a *valid* `(raw_body, hmac)` pair — regardless of which shop actually produced it — will pass HMAC validation no matter what `shop-domain` header value is attached, letting an attacker relabel a genuine webhook payload as originating from an arbitrary victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only reference `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop`, however, is read straight from the (attacker-controlled, transport-level) header, entirely independent of what is HMAC-signed: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, which — for a webhook `Request` — is just the body, so it never incorporates `shop`: [4](#0-3) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity passed to the app's handler, with no secondary check that this shop matches any known/installed shop or the shop the payload was actually generated for: [5](#0-4) 

The broken binding, stated as an equality that should hold but doesn't:
`HMAC_valid(raw_body, hmac) == true` is being used by the caller to imply `shop_header == shop_that_generated(raw_body)`. In reality `HMAC_valid` only proves `raw_body` was byte-for-byte produced/signed with `api_secret_key`; it says nothing about which shop the header claims. Before the attacker's request: `(raw_body, hmac)` is valid for shop A only. After the attacker's request: the same `(raw_body, hmac)` is presented with `shop-domain = B`, and `HmacValidator.validate` still returns `true`, so `Registry.process` forwards `WebhookMetadata(shop: "B", body: <A's body>)` to the app handler as if it were an authentic event from shop B.

### Impact Explanation
This breaks the tenant boundary (cross-tenant access) at the library level: the gem hands the host application a `shop` value inside `WebhookMetadata` that carries no cryptographic assurance of being tied to the signed payload. Any application that trusts `data.shop` from `ShopifyAPI::Webhooks::Registry.process` (which the documented API encourages, since it's the only shop value surfaced) to select which merchant's data/record to read, mutate, or delete can be manipulated into acting on the wrong tenant's data, or into accepting fabricated events (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`) attributed to a shop that never sent them. This matches the "cross-tenant access" Critical impact category, since the identity binding between authenticated bytes and the shop the app believes sent them is broken entirely within this gem's own validation code path.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one valid `(raw_body, hmac)` pair — trivially available to any unprivileged internet user who installs the app on their own store and receives any webhook, since they legitimately control that shop and its data; and (2) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain`/`shopify-shop-domain` header — no secret, token, or privileged access is needed. This is directly reachable through the gem's public `Webhooks::Request`/`Registry.process` API as documented, not a misuse of an undocumented feature.

### Recommendation
Bind the shop identity into the authenticated material before trusting it, e.g. by requiring the host application (or the gem itself) to cross-check `request.shop` against a shop that is actually registered/subscribed for that specific webhook topic/session before dispatching to handlers, or by including the `shop-domain` (and `topic`/`webhook-id`) header values in `to_signable_string` if Shopify's signing scheme is extended to support it, or at minimum documenting prominently that `data.shop` from webhook processing is not itself authenticated and must be cross-verified by the host app against known installed shops prior to any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent — both valid because they were signed with the app's real `api_secret_key` over `B`.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and topic `shopify-topic: orders/create`.
3. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)` and compares to `H` — they match, since neither `to_signable_string` nor `hmac` reference the shop header at all: [6](#0-5) 
5. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)`, even though `victim-shop.myshopify.com` never sent this event: [7](#0-6) 
6. Any app logic keyed on `data.shop` (e.g. writing/deleting per-shop records, revoking access on `app/uninstalled`, purging data on `shop/redact`) is now executed against the victim shop's tenant record using attacker-supplied data, despite passing HMAC validation.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
