### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — HMAC binds only the body, not the tenant identity - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, but the tenant identity (`shop`) that is handed to the host application's handler is read from an HTTP header that is never covered by that HMAC. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the body only) — the `shop` header plays no role in the signature check — and then forwards `request.shop` unchecked into `WebhookMetadata`, which is passed to the app's `WebhookHandler#handle`: [3](#0-2) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and only compares that against the received HMAC — again, only the body is authenticated: [4](#0-3) 

Because the HMAC is computed over `@raw_body` only, any request with a body+HMAC pair that is valid for shop A remains a **valid** signature no matter what value is placed in the `shop-domain` header. An attacker who can obtain one legitimate `(raw_body, hmac)` pair — trivially available to them, since they can install the target app on their **own** shop and capture the webhook their own shop legitimately receives, or observe/replay any webhook delivery they have access to — can resend that exact body with the same valid HMAC but substitute an arbitrary `shop-domain` header value pointing at a **different** merchant's shop. `Registry.process` will accept it as valid (the HMAC check passes) and will construct `WebhookMetadata.new(shop: request.shop, ...)` with the attacker-chosen shop, then dispatch it to the app's handler as if it originated from that other shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the authenticated fact ("this body+signature pair was generated by Shopify") does not carry any binding to the shop domain claimed in the request. Any host application that uses `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's session/data to update — the documented and expected usage pattern of this gem's webhook API — can be tricked into attributing an attacker-controlled event to an arbitrary victim shop. This enables cross-tenant data injection/confusion (e.g., forging `orders/create`, `app/uninstalled`, `shop/redact`, GDPR webhooks, etc. against a victim shop), which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite is only the ability to send one HTTP request to the app's public webhook endpoint with attacker-controlled headers, plus possession of any single valid `(body, hmac)` pair. The latter is obtainable without any privileged credentials: an attacker can register their own shop with the target app (unprivileged internet user, no API key/secret needed) and capture a webhook Shopify sends them, then replay that exact payload against the same endpoint with a forged `shop-domain` header. No TLS interception, leaked secrets, or social engineering is required — this is purely a design gap within the gem's own webhook-verification code path.

### Recommendation
Bind the shop identity to the authenticated content. Either:
- Include the `shop-domain` header value in `to_signable_string` so the HMAC also authenticates the tenant claim (not possible unilaterally since Shopify's own signature scheme excludes headers — so this must instead be enforced at the call site), or
- Require callers of `Registry.process`/`WebhookHandler#handle` to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription (fetched via the Admin API) before trusting it, and document prominently that `Request#shop` is **not** authenticated by the HMAC and must not be used as a sole tenant identifier without additional verification.
- At minimum, update the docs/comments on `ShopifyAPI::Webhooks::Request#shop` and `WebhookMetadata#shop` to explicitly warn that this value is unauthenticated and must not be trusted for tenant-sensitive operations without further validation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker sends a POST to the app's webhook endpoint with:
   - Body: the exact captured `raw_body` (unchanged, so HMAC still matches)
   - Header `X-Shopify-Hmac-Sha256`: the exact captured HMAC value (unchanged)
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (the unchanged body) against the unchanged HMAC — the forged shop header is never inspected.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and calls the app's `handler.handle(data: ...)`, causing the host application to process an authenticated-looking webhook as if it came from `victim-shop.myshopify.com`.
