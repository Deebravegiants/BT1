### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers and passed downstream to the app's webhook handler as trusted tenant/routing identity. This breaks the intended binding: `hmac(raw_body) == valid` should imply "this whole webhook event, including which shop it is for, is authentic," but in fact only the body bytes are authenticated.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all derived from headers that are never mixed into the signed bytes: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body-only HMAC and then forwards the header-derived `shop`, `topic`, `api_version`, and `webhook_id` straight to the app's handler as the trusted identity of the webhook event: [3](#0-2) [4](#0-3) 

The equality that should hold is: `shop asserted in HMAC-signed bytes == shop delivered to WebhookMetadata`. Instead, the gem only guarantees `hmac(raw_body)` is valid; the `shop` field consumed by `WebhookMetadata.shop` (and used by apps to look up per-tenant records/access tokens) is architecturally outside the signed content, contrary to `Utils::VerifiableQuery`'s implied contract that `hmac`/`to_signable_string` authenticate the object as a whole.

Compare this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop`, `host`, `code`, `state`, and `timestamp` are all explicitly included in `to_signable_string` and therefore covered by the HMAC: [5](#0-4) 

The webhook path lacks this equivalent binding for the header fields.

### Impact Explanation
Any unprivileged internet user who obtains one valid `(raw_body, hmac)` pair for a given app (e.g., by triggering a genuine low-value webhook, or capturing one in transit/logs) can replay that exact body/HMAC pair while freely substituting the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers, since none of them are checked against the signature. If the host app relies on the gem's `Registry.process` / `WebhookMetadata.shop` value to select which tenant's database record, session, or access token to update/act on, this allows spoofing which merchant a legitimate-looking, HMAC-valid payload is attributed to — a cross-tenant confusion primitive. This matches the "field acted on but not covered by the HMAC" pattern (the `shop` used to route/act on data is not the `shop` verified by the signature).

### Likelihood Explanation
Exploitability is bounded by the attacker's ability to obtain at least one valid `(body, hmac)` pair; this gem does not itself leak or expose one, and Shopify's webhook body/HMAC pairs are otherwise treated as secrets, so it is not a fully unauthenticated bypass, but the design defect is unconditional and reachable by any caller that can invoke `ShopifyAPI::Webhooks::Registry.process` with attacker-controlled headers alongside any previously-observed valid `(body, hmac)` combination for the app.

### Recommendation
Include the tenant/routing-critical header fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used by `HmacValidator`, or otherwise fail closed if the host app needs a binding between these headers and the signed payload (Shopify's actual webhook HMAC only covers the body per their documented spec, so any fix should be done carefully with awareness of the real signature scheme — this may require documenting to consumers that `shop`/`topic`/etc. from `Request` must not be trusted as authenticated unless independently verified, e.g. against the shop derived from a stored access token/session).

### Proof of Concept
1. Obtain any valid `(raw_body, hmac)` pair for the target app's webhook endpoint (e.g., a real webhook delivery for shop A, topic `app/uninstalled`).
2. Replay the same `raw_body` and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: shop-b.myshopify.com`, `x-shopify-topic: orders/create`, and `x-shopify-webhook-id: <different-id>`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not correctness, is checked): [6](#0-5)  and `Registry.process` validates HMAC successfully because it only checks `@raw_body`, then dispatches `WebhookMetadata` with the attacker-chosen `shop`/`topic`/`webhook_id` to the app's handler: [7](#0-6) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
