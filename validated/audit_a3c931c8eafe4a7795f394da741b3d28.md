## Title
Webhook HMAC only covers the request body, not the `shop-domain` header — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity used for dispatching the webhook (`shop-domain` header) is read separately and is **not** included in the HMAC-signed material. Any user who can obtain a validly-signed webhook body (e.g. by installing the app on their own store) can replay that exact body with a forged `shop-domain` header, and `HmacValidator.validate` will still accept it, causing the gem to dispatch the payload under an attacker-chosen tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable payload as: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only. Meanwhile the `shop` used for tenant routing is pulled straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over the body only and then dispatches the handler using the header-derived, unverified `shop`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it against the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

Because Shopify signs webhooks with the app's `client_secret` — which is **shared across every shop that installs the app**, not per-shop — a merchant who installs the app on their own store legitimately receives webhook deliveries with a valid `hmac-sha256` for a body they fully control the shape of (any JSON webhook topic body Shopify will emit for their own store's data, e.g. `orders/create`, `customers/redact`, `app/uninstalled`). That attacker can then replay the identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes because the header is not part of the signed data, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` where `shop` is the attacker-forged value.

This breaks the identity binding: **shop authenticated (covered by HMAC) ≠ shop used for tenant dispatch (`request.shop` from header)**. The gem asserts authenticity of the payload but silently trusts an out-of-band, unauthenticated field for which tenant that payload belongs to.

### Impact Explanation
This is a cross-tenant boundary violation reachable by any unprivileged internet user who can install the app on their own shop (a normal, low-privilege action for any app listed on the Shopify App Store or dev app). Host applications built on this gem (e.g. via `shopify_app`) look up per-shop session/data using `WebhookMetadata#shop` to route/process the webhook — an attacker can cause the library to hand off attacker-controlled webhook bodies "signed" as coming from an arbitrary victim shop domain, since the gem itself performs no binding between the authenticated body and the claimed shop. This matches the Critical "cross-tenant access" category, since the vulnerability is in the trust boundary this gem is responsible for (HMAC verification of webhook authenticity + tenant attribution) and does not depend on the host app ignoring documented behavior — the header value is exactly what the gem's own `Request#shop` and `WebhookMetadata` API exposes as the trusted tenant identifier.

### Likelihood Explanation
High practical likelihood: obtaining a legitimately-signed webhook body requires nothing more than installing the target app on an attacker-owned development/trial store (a normal, unprivileged action), then capturing any webhook Shopify sends to the app's registered endpoint. Replaying that body with a modified `shop-domain` header requires no cryptographic secret at all, since the header is outside the signed material.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is exposed via `WebhookMetadata`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate `shop`, and `HmacValidator`/`Registry.process` should reject requests where the header-derived shop cannot be attributed to the same signing context as the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`; the app's OAuth flow completes normally (unprivileged action).
2. Shopify sends a legitimate webhook, e.g. `customers/redact`, to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and some JSON `raw_body`.
3. Attacker captures `(raw_body, hmac)`.
4. Attacker resends the exact same `raw_body` and `hmac` value to the app's endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` matches `HmacValidator.validate` (since validation only checks `raw_body`) — see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
6. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...))`, causing the host application to act as though `victim.myshopify.com` sent this webhook payload — e.g. triggering data deletion/redaction, session invalidation, or other per-tenant side effects for a shop the attacker does not control.
