### Title
Stale delegate authorization reactivates when a position NFT returns to its prior owner, allowing theft of collateral and borrowed assets - (File: contracts/controller/src/storage/account.rs)

### Summary
Controller delegate grants are keyed only by `account_id` and stamped with the granting owner's address, not invalidated permanently by NFT transfer. `get_delegates` returns a stored grant whenever its `granted_by` equals the current NFT owner, so a grant that is dormant under an intermediate owner becomes active again if the NFT returns to the original owner. The reactivated delegate can then call `withdraw` or `borrow` and choose an external recipient, stealing the account's withdrawable collateral or maximum permitted borrow proceeds.

### Finding Description
The controller resolves live ownership from the position NFT, while delegation state remains in persistent controller storage under `ControllerKey::Delegates(account_id)`. `get_delegates` filters the grant by comparing `grant.granted_by` with the current owner, but does not clear the grant on transfer or bind it to an ownership epoch. [1](#0-0) 

When the NFT moves to another address, the old grant reads as empty because `granted_by != owner`; however, the entry remains in storage. If the NFT later returns to the original owner before the intermediate owner calls `add_delegate` or `remove_delegate`, the equality holds again and the original delegate list is returned. [2](#0-1) 

`is_owner_or_delegate` admits any currently active position manager present in the returned delegate list. [3](#0-2)  `process_withdraw` uses that check, permits `amount = 0` as withdraw-all, and sends proceeds to caller-selected `to`. [4](#0-3)  `process_borrow` uses the same authorization and likewise sends proceeds to caller-selected `to`, subject to post-borrow solvency. [5](#0-4) 

This is the same TOCTOU shape as CVE-2015-8239: authorization was valid when originally checked, the checked object changes hands, and stale authorization is later reused against the restored object without a fresh authorization decision by the owner.

### Impact Explanation
The reactivated delegate has broad economic control over the account. For a debt-free account, it can call `withdraw(caller=delegate, account_id, withdrawals=[...], to=Some(delegate))`, including a zero amount to withdraw an asset's whole position. [4](#0-3)  For a collateralized account, it can borrow to itself up to the protocol's post-borrow solvency limit, then abandon the debt or transfer the position away. [6](#0-5) 

The impact is theft of user funds and unauthorized debt creation against the user's collateral. The protocol risk checks bound the amount by the position's remaining health, but they do not constrain the payout to the owner or prevent the delegate from receiving the proceeds.

### Likelihood Explanation
The attack requires the victim to have previously granted the attacker as an active position manager. The NFT must then move to another owner and return to the granting owner without the intermediate owner modifying the account's delegate entry. Intermediate-owner `add_delegate` overwrites the stale grant, and intermediate-owner `remove_delegate` deletes it, so these actions prevent resurrection. [7](#0-6) 

Such round trips are plausible for NFT custody changes, marketplace settlement and return, temporary escrow, wallet migration, or accidental transfer back to the original holder. The attacker needs no protocol role beyond remaining a globally active position manager and needs no fresh signature from the victim after the NFT returns.

### Recommendation
Invalidate all account-scoped delegate grants permanently whenever NFT ownership changes. Because the NFT contract does not currently notify the controller on transfer, store an ownership epoch or NFT transfer counter in the `DelegateGrant` and compare it with a controller-maintained epoch that changes on observed ownership transitions. Alternatively, store grants under a key that includes `granted_by` and a per-account ownership generation, and advance the generation when `try_get_account` observes a different owner.

A simpler but weaker mitigation is for every NFT transfer integration to require the recipient to purge stale grants before returning the NFT. That does not reliably protect generic NFT transfers, so an ownership-generation check at authorization time is preferable.

### Proof of Concept
1. Alice owns account `A` with withdrawable collateral.
2. Mallory is registered as an active position manager.
3. Alice calls `add_delegate(caller=alice, account_id=A, delegate=mallory)`, creating `DelegateGrant { granted_by: alice, delegates: [mallory] }`.
4. Alice transfers NFT `A` to Bob. Controller authorization now resolves `owner = bob`, so `get_delegates(A, bob)` filters out Alice's grant and Mallory is dormant.
5. Bob does not call `add_delegate` or `remove_delegate`, leaving Alice's stale grant in storage.
6. Bob transfers NFT `A` back to Alice. Controller authorization again resolves `owner = alice`.
7. `get_delegates(A, alice)` now returns `[mallory]` because `grant.granted_by == alice`; `is_owner_or_delegate(A, mallory, alice)` passes.
8. Mallory calls `withdraw(caller=mallory, account_id=A, withdrawals=[(collateral_key, 0)], to=Some(mallory))`; the zero amount withdraws the whole collateral position to Mallory.
9. Alternatively, Mallory calls `borrow(caller=mallory, account_id=A, borrows=[(debt_key, amount)], to=Some(mallory))` up to the maximum amount that leaves the account solvent.

No fresh approval from Alice occurs after the NFT returns, yet the prior grant resumes controlling the same account.

/// Returns grants stamped by `owner`, or an empty list. Ownership changes
/// invalidate a previous owner's grants without deleting them.
pub(crate) fn get_delegates(env: &Env, account_id: u64, owner: &Address) -> Vec<Address> {
    get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
        .filter(|grant| grant.granted_by == *owner)
        .map(|grant| grant.delegates)
        .unwrap_or_else(|| Vec::new(env))

/// Adds a delegate, enforcing `MAX_DELEGATES`; returns false for duplicates.
/// Overwrites stale grants with a list stamped by the current owner.
pub(crate) fn add_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let mut delegates = get_delegates(env, account_id, owner);
    if delegates.contains(delegate) {
        return false;
    }
    assert_with_error!(
        env,
        delegates.len() < MAX_DELEGATES,
        GenericError::RegistryCapReached
    );
    delegates.push_back(delegate.clone());
    set_delegates(env, account_id, owner, &delegates);
    true
}

/// Removes a live delegate and reports whether it changed the list.
/// Deletes stale grants but returns false, preventing those grants from
/// reactivating if the NFT returns to their original owner.
pub(crate) fn remove_delegate(
    env: &Env,
    account_id: u64,
    owner: &Address,
    delegate: &Address,
) -> bool {
    let key = ControllerKey::Delegates(account_id);
    let Some(grant) = get_user::<DelegateGrant>(env, &key) else {
        return false;
    };
    if grant.granted_by != *owner {
        env.storage().persistent().remove(&key);
        return false;
    }

/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
