### Title
`rootHashHinkalIndex` is unconstrained by the proof, `signedMessageHash`, and `calldataHash`, allowing root-existence check bypass/tampering - (File: contracts/Hinkal.sol, contracts/CircomDataBuilder.sol, contracts/MerkleBase.sol)

### Summary
`CircomData.rootHashHinkalIndex` is used on-chain to select which historical root slot must match `circomData.rootHashHinkal`, but this field is never included in the circuit's public-input vector, in `getSignedMessageHash`, or in `getHashedCalldata`. It is therefore not bound by the prover's EdDSA signature nor by the `calldataHash` integrity check, so any relay/submitter of an otherwise-valid proof can freely choose `rootHashHinkalIndex` at call time.

### Finding Description
`Hinkal.transact` validates the merkle root with: [1](#0-0) 
which calls `rootHashExists(_root, _rootIndex)`: [2](#0-1) 
`rootHashHinkalIndex` selects which `roots[index]` slot is compared against the prover-supplied `rootHashHinkal`.

However, the circuit's public inputs only include `rootHashHinkal` (not the index) — see the declared public params list and signal inputs in `MainEVMCircuit.circom`: [3](#0-2) 

The on-chain input-vector builder (`formBasicInput`) likewise never places `rootHashHinkalIndex` into the public-input array supplied to the verifier: [4](#0-3) 

`getSignedMessageHash`, which is the value the prover's EdDSA signature covers (`signedMessageHash`), also omits `rootHashHinkalIndex`: [5](#0-4) 

And `getHashedCalldata`/`getHashedCalldata1`/`getHashedCalldata2` (which produce `calldataHash`, itself just another unauthenticated field in `CircomData`) also do not include `rootHashHinkalIndex`: [6](#0-5) 

So `rootHashHinkalIndex` is a `CircomData` field that is *acted on* (used to gate a security-critical `require` in `transact`) but sits completely outside `calldataHash`, `signedMessageHash`, and the public-input vector fed into the zk-SNARK verifier. The equality this breaks is: "the (root, rootIndex) pair accepted by `rootHashExists` must be the pair the prover actually intended/signed for and the tree actually produced together." Since the index is unauthenticated, a submitter (which need not be the original prover — `transact` can be called by any relay/msg.sender carrying a valid `(a,b,c, circomData)` payload) can substitute any `rootHashHinkalIndex` value within `[MINIMUM_INDEX, m_index)` at submission time.

### Impact Explanation
This is Medium/High-severity depending on further tree semantics: because `roots[index]` values are unique per state-appending Merkle insertion in normal operation, an attacker cannot generally forge a *different* stale/mismatched root to pass unless a duplicate root value happens to occur at another index (e.g., through a no-op insert or coincidental recomputation) — which would let a proof built against an old/outdated root be replayed against the current tree state (or vice-versa) as long as the numeric root value repeats at a different index the attacker chooses. Because the exploit is contingent on the underlying Merkle tree ever storing the same root hash under two different indices — which is not something this scope's code demonstrably prevents but also not something the code guarantees will happen — I can only confirm the root cause (missing binding) with the current file's logic; I cannot within this repo prove a two-distinct-index root collision is reachable in practice without deeper analysis of `MerkleTree`/`insert()` (out of the currently inspected files). I flag this as the identified authentication gap but cannot fully substantiate an end-to-end double-spend/theft PoC with the files reviewed.

### Likelihood Explanation
Low-to-Medium: requires either (a) a coincidental or crafted root repeat across two `roots[]` slots, or (b) some other on-chain path that causes `roots[i] == roots[j]` for `i != j`. The missing binding itself is a definite finding; the practical exploitability depends on tree implementation details not fully surfaced in the reviewed files.

### Recommendation
Include `rootHashHinkalIndex` in the value covered by `getSignedMessageHash` (and/or in the public-input vector verified by the zk-SNARK) so that the prover binds their proof to the exact root index they intended to spend against, preventing any post-hoc substitution of the index by whoever submits the transaction.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end within the given scope):
1. User generates a valid proof `(a,b,c)` and `circomData` with `rootHashHinkal = R` and `rootHashHinkalIndex = idx1`.
2. A relay/submitter observes that `roots[idx2] == R` for some `idx2 != idx1` (whether by coincidence, replay, or a contract-level condition not fully verified here).
3. Relay submits `transact` with `circomData.rootHashHinkalIndex` swapped to `idx2`; `rootHashExists(R, idx2)` still returns true since only equality of the stored root at that slot is checked, and neither the signature (`signedMessageHash`) nor `calldataHash` cover the index, so `performHinkalChecks`'s integrity check at [7](#0-6) 
does not catch the tampering.
4. Transaction proceeds despite the root/index pairing not being the one the prover explicitly signed for.

    function rootHashExists(
        uint256 _root,
        uint256 _rootIndex
    ) public view returns (bool) {
        if (m_index == MINIMUM_INDEX) {
            return _root == 0;
        }
        if (_rootIndex < MINIMUM_INDEX || _rootIndex >= m_index) {
            return false;
        }
        return _root != 0 && roots[_rootIndex] == _root;
    }

    function getSignedMessageHash(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData,
        uint256 emporiumMessage
    ) internal pure returns (uint256) {
        // split into two encode calls to avoid "stack too deep"
        uint256 hash1 = uint256(
            keccak256(
                abi.encode(
                    chainId,
                    verifyingContract,
                    circomData.rootHashHinkal,
                    _encodeTokenAddresses(circomData.erc20TokenAddresses),
                    _encodeAmountChanges(circomData.amountChanges),
                    circomData.timeStamp,
                    _flatUint256Matrix(circomData.inputNullifiers),
                    _flatUint256Matrix(circomData.outCommitments),
                    circomData.calldataHash,
                    emporiumMessage
                )
            )
        );
        uint256 hash2 = uint256(
            keccak256(
                abi.encode(
                    circomData.stealthAddressStructure.H1x,
                    circomData.stealthAddressStructure.H1y,
                    circomData.stealthAddressStructure.H0x,
                    circomData.stealthAddressStructure.H0y
                )
            )
        );
        return
            uint256(keccak256(abi.encode(hash1, hash2))) % CIRCOM_P;
    }
