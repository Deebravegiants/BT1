### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop-domain`, `topic`, `webhook-id` and `api-version` headers to determine which merchant/topic the payload belongs to before invoking the app's handler. The HMAC only proves the body bytes were signed with the app's shared `api_secret_key`; it says nothing about which shop or topic the payload is claimed to be for. This breaks the identity binding: `HMAC-verified(raw_body)` ≠ `shop used to dispatch data to the handler`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with `secure_compare` against the header-supplied HMAC: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which are part of the signed content: [3](#0-2) 

`Registry.process` checks only the body HMAC, then unconditionally trusts `request.shop` and `request.topic` to route the event to the registered handler: [4](#0-3) 

Because `api_secret_key` is a single shared secret for the whole app (not per-shop), any shop that has legitimately installed the app receives correctly-HMAC'd webhook deliveries from Shopify. A malicious merchant (an "unprivileged" tenant with respect to other merchants of the same app) can capture one such legitimate `raw_body` + `x-shopify-hmac-sha256` pair from their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`/`x-shopify-webhook-id`). Since `HmacValidator.validate` only checks the body, the forged request passes validation and `Registry.process` calls the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, body: <attacker's own body>, ...)`: [5](#0-4) 

The library's own documentation encourages hosting apps to trust this call as proof the data "did indeed come from Shopify" for the given shop: [6](#0-5) 

This is exactly the bug class in the report: a calculation/check (HMAC validation) silently omits a field (`shop`) that is subsequently trusted for a security-relevant decision (which tenant's data the handler processes), just as `num-bigint`'s modexp silently omitted the even-modulus cost from the gas calculation.

### Impact Explanation
Host applications built on this gem's documented API pattern will process attacker-supplied webhook data under a victim shop's identity (`data.shop`), because that identity is not covered by the HMAC. This satisfies the "cross-tenant access" impact class: a malicious/unprivileged merchant of a multi-tenant app can inject fabricated webhook events attributed to another tenant, potentially triggering unauthorized writes, notifications, or business-logic side effects keyed by `shop`.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately received at least one webhook for their own (attacker-controlled) shop, which is trivial for any developer/merchant that installs the app. No access token, `api_secret_key`, or privileged account is required — this is an internet-reachable HTTP endpoint that any registered shop's normal webhook traffic exposes.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body, e.g. by concatenating them before hashing), so header-controlled routing values cannot be substituted independently of the signed payload. At minimum, document and/or enforce that the `shop` used to dispatch the webhook must match a shop with an active session/installation known to the host app.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid_hmac_for_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any `x-shopify-topic`/`x-shopify-webhook-id` of choice).
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` via `to_signable_string`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: {"id"=>1}, ...)`, causing the host app to act on attacker data as if it belongs to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
