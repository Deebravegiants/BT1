### Title
Duplicate entries in `circomData.erc20TokenAddresses` let a single real on-chain UTXO be double-inserted into the Merkle tree while a second, differently-addressed UTXO from the same external action is silently dropped — ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact()` reconciles the UTXOs returned by an external action (`utxoSet`) against `circomData.erc20TokenAddresses` purely by address matching inside a nested loop, with no requirement that the addresses in `erc20TokenAddresses` be distinct. Exactly like the KUMA `changePayees()` bug — where `addPayee()` rejects duplicates but the batch path never checks for them — Hinkal's per-token accounting (`dimensionsCheck` / `checkOnchainCreation` in `HinkalHelper.sol`) validates array *lengths* but never validates *uniqueness* of `erc20TokenAddresses`. This breaks the "one physical UTXO ↔ one on-chain commitment" invariant.

### Finding Description
In `Hinkal.transact()`: [1](#0-0) 

For every index `i` of `circomData.erc20TokenAddresses`, the inner loop scans the *entire* `utxoSet` and matches by `erc20Address`. If the caller supplies `erc20TokenAddresses = [X, X]` (duplicate token address) instead of `[X, Y]`, and the external action actually produced two UTXOs — one for `X` and one for a different token `Y` — then:

- At `i=0` (address `X`), the loop finds `utxoSet[0]` (token `X`) and writes `onChainCommitments[0]`.
- At `i=1` (address `X` again), the loop scans `utxoSet` again and matches the *same* `utxoSet[0]` entry (since its fields/timestamp are unchanged, `createOnchainCommitment` produces the identical commitment hash via `hash4(...)`), writing it into `onChainCommitments[1]`.
- `utxoSet[1]` (token `Y`) never matches any index in `erc20TokenAddresses` (since `Y` was never listed) and is never turned into an `OnChainCommitment` at all.

Because `onChainCommitments` is sized exactly `utxoSet.length`, this exactly fills the array (`onChainCommitmentCounter` reaches `utxoSet.length` without reverting), so the bug produces no revert — it silently succeeds. [2](#0-1) 

The balance-equation check is also computed only over the tokens named in `erc20TokenAddresses`: [3](#0-2) 

Since `Y` is absent from `erc20TokenAddresses`, `getBalancesForArray` never observes token `Y`'s balance change, so the real value received in token `Y` is not counted in the balance equation at all — it is neither returned to a user-controlled UTXO commitment nor checked against slippage/amount, and is simply stranded in the Hinkal contract's token balance forever (no code path re-derives or reclaims it later since the associated UTXO struct is discarded).

Meanwhile, `insertCommitments` is called with the doubled `onChainCommitments` array: [4](#0-3) 

It inserts both identical commitment values as two separate Merkle leaves at two distinct indices, emitting two `NewCommitment` events. Both leaves are cryptographically valid (same commitment preimage), so the attacker can later spend each leaf as an independent UTXO with its own nullifier/merkle-proof, i.e. the shielded pool now credits token `X` with `2×A` spendable value while only `A` of token `X` was actually received from the external action — a classic unbacked-minting/double-count of shielded value, achieved purely through duplicate entries in a `CircomData` field that neither `HinkalHelper.dimensionsCheck`/`checkOnchainCreation` nor the balance-diff loop in `Hinkal.transact()` ever require to be unique.

### Impact Explanation
This breaks the fundamental balance equation "total value inserted into the shielded Merkle tree == total value actually received by the Hinkal contract" for a given `transact()` call:
- Critical: minting shielded value without backing / double counting of a single physical UTXO as two independently-spendable leaves in the Merkle tree.
- Additionally, the second real UTXO (token `Y`) becomes an unbacked, permanently-stranded balance in the contract because it is dropped from `erc20TokenAddresses`, is never turned into an `OnChainCommitment`, and never appears in any off-chain-output/nullifier bookkeeping — permanent freezing of value that the external action legitimately produced.

### Likelihood Explanation
Reachable by any unprivileged EOA calling `transact()` with `externalActionData.externalActionId != 0` (i.e., any external-action swap/liquidity path that returns more than one `UTXO` in `utxoSet`) and simply repeating a token address in `circomData.erc20TokenAddresses` instead of listing each distinct output token once. Nothing in `HinkalHelper.dimensionsCheck`, `checkOnchainCreation`, or `Hinkal.transact()` enforces uniqueness of the token address list, and the array-size bound on `onChainCommitments` (`= utxoSet.length`) means the exploit does not trigger an out-of-bounds revert as long as the total number of address matches across all indices equals `utxoSet.length` (achieved by "stealing" the match count from the orphaned token).

### Recommendation
- Enforce uniqueness of `circomData.erc20TokenAddresses` in `HinkalHelper.dimensionsCheck` (or a dedicated check), reverting on duplicate entries, mirroring the KUMA fix that rejects duplicate payees instead of silently accumulating shares against a wrong total.
- In `Hinkal.transact()`, instead of re-scanning the full `utxoSet` for every `i` and allowing the same `utxoSet[j]` to be matched by more than one `erc20TokenAddresses[i]`, mark each `utxoSet[j]` as "consumed" once matched (e.g., using a `bool[] consumed` array) so a physical UTXO can only be turned into one `OnChainCommitment`, and additionally assert at the end that every entry of `utxoSet` was consumed exactly once (so no UTXO the external action produced can be silently dropped/stranded).

### Proof of Concept
1. Register/craft an external action whose `runAction()` returns `utxoSet = [UTXO{token: X, amount: 10}, UTXO{token: Y, amount: 20}]` (e.g., a swap that legitimately produces two output tokens).
2. Call `Hinkal.transact()` with `circomData.erc20TokenAddresses = [X, X]` (list length 2, matching `dimensions.tokenNumber`, with `amountChanges`/`slippageValues` chosen so both per-index balance checks at `contracts/Hinkal.sol:111-146` pass using the real observed balance delta for `X`).
3. `onChainCommitmentCounter` reaches `utxoSet.length = 2` without reverting: `onChainCommitments[0]` and `onChainCommitments[1]` both equal `createOnchainCommitment(utxoSet[0], ...)` (token `X`, amount 10).
4. `insertCommitments` inserts the identical commitment hash as two separate Merkle leaves; the attacker later spends both leaves independently (two nullifiers), redeeming 20 units of token `X` in the shielded pool though only 10 was ever received for `X`.
5. Meanwhile the 20 units of token `Y` genuinely transferred into the Hinkal contract by the external action are never represented by any commitment, off-chain output, or nullifier, and remain permanently stuck in the contract's balance.

    function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }
