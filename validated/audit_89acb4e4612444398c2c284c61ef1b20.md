## Broken equality

`value actually leaving EmporiumUpgradeable's token balances in a tx` **should equal** `Σ(-deltaAmountChanges[i])` for every token that changes hands, as enforced by the `balanceChange < 0` revert in `EmporiumUpgradeable.runAction` and by `Hinkal.transact`'s `balanceDif == amountChanges[i] + utxoAmount` check.

Both of these checks only iterate over `circomData.erc20TokenAddresses` — the array the *caller* chooses to declare for their own transaction. Any token that Emporium happens to be holding but that the caller does **not** list in their own `erc20TokenAddresses` is never inspected by either invariant, even though the attacker fully controls the ops executed inside `runAction`.

## Finding Description [1](#0-0) 

When `stack.signerAddress == address(0)` (the "stateless" path), each `EmporiumOperation` is executed as a raw, unauthenticated call:

```solidity
bytes4 selector = bytes4(op.callData);
if (selector == IHinkalWallet.callHinkalWallet.selector ||
    selector == IHinkalWallet.doSendToRelay.selector) {
    revert UnauthorizedWalletCall();
}
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [2](#0-1) 

`op.endpoint` and `op.callData` come straight from the attacker-supplied `externalActionMetadata` (decoded as `EmporiumStack`), and `verifyWallet` performs **no signature or authorization check whatsoever** when `signerAddress == address(0)`:

```solidity
if (stack.signerAddress == address(0)) {
    return;
}
``` [3](#0-2) 

The only forbidden selectors are `callHinkalWallet` and `doSendToRelay`. Nothing prevents `op.endpoint` from being an arbitrary ERC20 token address whose balance Emporium currently holds (residual from prior interactions, dust left by partial swaps/stakes, refunds, tokens mistakenly sent to Emporium, etc.), with `op.callData = transfer(attacker, strandedAmount)`. Since the low-level call originates from Emporium (`address(this)` context), this moves tokens straight out of Emporium's own balance to the attacker.

The post-loop accounting only checks tokens the *attacker* lists in their own `circomData.erc20TokenAddresses` for that call:

```solidity
for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
    int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
    if (deltaAmountChanges[i] < 0) { balanceChange -= deltaAmountChanges[i]; }
    if (balanceChange < 0) { revert BalanceChangeShouldBePositive(); }
    UTXO memory utxoOut = handleOut(balanceChange, circomData, i);
    ...
}
``` [4](#0-3) 

If the attacker simply omits the stranded token from their own `erc20TokenAddresses` array (e.g. they use it only to deposit/withdraw an unrelated token, tokenA), the drained token (tokenB) is never checked here. `Hinkal.transact` mirrors the same limitation — its balance-diff/UTXO-sum check also only walks `circomData.erc20TokenAddresses`:

```solidity
for (uint64 i; i < circomData.erc20TokenAddresses.length; i++) {
    ...
    require(balanceDif == (... ) + int256(utxoAmount), "Balance Diff Should be equal to sum...");
}
``` [5](#0-4) 

so a token completely absent from the array (tokenB) is invisible to Hinkal too. The attacker's own proof/nullifiers/UTXOs for tokenA remain fully valid; the exfiltration of tokenB via the raw `call` is a pure side effect that neither `performHinkalChecks`, `dimensionsCheck`, `verifyProof`, nor the circuit constraints ever touch, because those all operate purely on the declared `erc20TokenAddresses`/`amountChanges` for the caller's own inputs, not on arbitrary calls made inside `runAction`.

**Attacker's call:** `Hinkal.transact(a, b, c, dimensions, circomData)` where:
- `circomData.externalActionData.externalActionId` → Emporium
- `circomData.erc20TokenAddresses = [tokenA]` (attacker's own legitimate small deposit/withdraw, satisfying `dimensionsCheck`/circuit constraints)
- `circomData.externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: tokenB, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmountOfTokenB)}], ...}`

Since `tokenB` is not in `circomData.erc20TokenAddresses`, `strandedAmountOfTokenB` leaves Emporium straight to the attacker's EOA with no on-chain accounting anywhere in the call stack.

## Impact Explanation

Any unprivileged caller can drain any ERC20 (or ETH, via `op.value`) balance sitting in `EmporiumUpgradeable` that is not part of their own declared token set, for tokens belonging to other users' in-flight or stranded funds. This is direct theft of shielded/in-flight protocol funds, matching the Critical impact category. It is fully repeatable for every token/amount the contract accumulates and costs the attacker only their own transaction gas plus a trivial legitimate deposit/withdraw to pass Hinkal's proof and dimension checks.

## Likelihood Explanation

Preconditions: (1) `EmporiumUpgradeable` holds some non-zero balance of a token not covered by the attacker's own `erc20TokenAddresses` in a given call (residual/refund/dust/mid-flow balance — plausible any time ops interact with DeFi protocols, receive rewards, or partial swaps/withdraws leave leftovers), and (2) the attacker uses the unsigned stateless path (`signerAddress == address(0)`), which requires no signature and no permission beyond being a normal Hinkal user with a valid proof for their own UTXOs. Both are trivially attacker-controlled/achievable; the attack is deterministic and repeatable as long as any stranded balance exists.

## Recommendation

In the stateless (`signerAddress == address(0)`) branch of `EmporiumUpgradeable.runAction`, restrict `op.endpoint` to a whitelisted set of protocol endpoints (or require it be distinct from any ERC20 token address currently custodied by Emporium), and/or forbid `op.callData` from invoking `transfer`/`transferFrom`-style selectors on arbitrary token contracts. More robustly, track balances for *all* tokens Emporium has ever held (or require the caller's `erc20TokenAddresses` to include every token touched by their ops) so `Hinkal.transact`'s balance-diff/UTXO-sum invariant cannot be bypassed by simply omitting a token from the declared array.

## Proof of Concept

Foundry plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, two ERC20 tokens (`tokenA`, `tokenB`).
2. Seed the residual: directly `tokenB.transfer(address(emporium), strandedAmount)` (simulating dust/refund left from any prior flow) — assert `tokenB.balanceOf(emporium) == strandedAmount` and attacker's `tokenB` balance `== 0`.
3. As an unprivileged attacker EOA, deposit a trivial amount of `tokenA` into Hinkal to obtain a valid shielded UTXO.
4. Build `CircomData` with `erc20TokenAddresses = [tokenA]`, generate a valid proof for a small `tokenA` deposit/withdraw via Emporium, and set `externalActionMetadata` to an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(tokenB), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)}]}`.
5. Call `Hinkal.transact(...)`.
6. Assert: `tokenB.balanceOf(attacker) == strandedAmount` and `tokenB.balanceOf(emporium) == 0`, while `Hinkal.transact` succeeded and `tokenA`'s balance/UTXO invariant held exactly — proving `tokenB` left Emporium with zero entries in `deltaAmountChanges`/`amountChanges`/`utxoSet`, breaking the claimed equality.
