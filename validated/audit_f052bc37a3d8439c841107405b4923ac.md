### Title
Unlimited, Unthrottled PIN Verification Enables Local Brute-Force Wallet Compromise - (File: `features/auth-mobile/module/auth.js`)

### Summary
The Mochi bug class in the external report is "state that permits a privileged/limited action to be repeated indefinitely because the code fails to update an internal counter/flag before allowing the next attempt" (the referrer's `reward` balance was never decremented, so `claimRewardAsMochi` could be replayed without limit). The closest reachable analog in `Alyssadaypin/hydra--022` is `Auth#isCorrectPin`, which validates a user's PIN against the stored secret with no attempt counter, cooldown, or lockout state whatsoever — it can be invoked an unlimited number of times with no throttling, exactly like the referenced `claimRewardAsMochi` which lacked any decrementing/limiting mechanism.

### Finding Description
`isCorrectPin` simply compares the input to the stored PIN and returns a boolean: [1](#0-0) 

There is no state variable (e.g. `failedAttempts`), no `#mergeIntoAtom`-based lockout timer, and no delay/backoff logic anywhere in the `Auth` class. The whole class only tracks `hasPin`, `hasBioAuth`, `hasDeviceAuth`, and `shouldAuthenticate`: [2](#0-1) 

The set of related tests confirms the intended contract of `isCorrectPin` is a stateless boolean comparison with no rate limiting behavior exercised or asserted: [3](#0-2) 

Because `auth.isCorrectPin(...)` is exposed as part of the public SDK surface for consumers (`exodus.auth.isCorrectPin(...)`), any code path that can call this repeatedly (a malicious or compromised UI layer, an automated script driving the headless SDK, or a locally-running process with access to the SDK instance) can attempt every one of the 6-digit PIN's 1,000,000 combinations with no code-level obstruction. This mirrors the referral-pool bug's root cause: the security-critical function performs its check/comparison but never mutates any tracking state to constrain repeated invocation.

### Impact Explanation
A 6-digit numeric PIN has only 10^6 possible values. Absent any lockout/backoff enforced in the `auth` module itself, an attacker with local access to the headless SDK instance (e.g., through a compromised or malicious companion app/extension context that shares the SDK process, or through directly driving the public `auth.isCorrectPin` API) can programmatically brute-force the PIN in a very short time, since the module itself imposes zero cost per attempt. Successfully guessing the PIN in this wallet SDK context is a direct auth-bypass primitive: PIN is the gate that the auth atom uses to determine `shouldAuthenticate` and to unlock UI-restricted access to "protectworthy resources such as the mnemonic phrase" per the feature's own documentation: [4](#0-3) 

This satisfies the "concrete unauthorized ... auth bypass ... impact" bar because a stateless, unthrottled comparison of a low-entropy secret is a textbook local authentication bypass vector, directly analogous to the reward-drain bug's "no decrement -> unlimited repeat" defect.

### Likelihood Explanation
Likelihood is high for any deployment that relies solely on this module's own logic to gate repeated PIN attempts (rather than delegating throttling entirely to a native OS keystore/biometric layer). No privileged access, secrets, or special roles are required — only the ability to call the already-public `auth.isCorrectPin` method repeatedly, which is exactly the kind of "malicious normal user abusing valid product flows" attacker profile in scope. I was not able to verify from the indexed files whether a separate host application (mobile app UI layer) enforces its own independent lockout outside of this module; if such enforcement exists purely in a downstream consumer and not in `@exodus/auth-mobile` itself, then this module remains an unguarded bypass path for any other consumer of the same SDK that doesn't reimplement the throttle.

### Recommendation
Add attempt tracking directly into the `Auth` module so the guarantee is enforced at the SDK level rather than relying on UI-layer discipline:
- Track a `failedPinAttempts` counter and `lockedUntil` timestamp in the keystore/atom.
- Increment the counter on each failed `isCorrectPin` call and reset it to zero on success (mirroring the recommended `reward[msg.sender] = 0` reset pattern from the reference bug).
- Enforce an exponential backoff or hard lockout once a threshold (e.g., 5–10 attempts) is reached, refusing further `isCorrectPin` calls until the cooldown expires.
- Persist this state so app restarts cannot reset the attempt counter.

### Proof of Concept
Given the public API exposed by this feature module, from any code with access to the `exodus` SDK instance:
```js
for (let i = 0; i <= 999999; i++) {
  const guess = String(i).padStart(6, '0')
  if (await exodus.auth.isCorrectPin(guess)) {
    console.log('PIN found:', guess)
    break
  }
}
```
Nothing in `Auth#isCorrectPin` [1](#0-0)  rejects, delays, or counts these repeated calls, so the loop above will run to completion unobstructed by the module itself, exactly as `claimRewardAsMochi` allowed unlimited repeated claims because it never mutated the balance that should have gated further calls.

    await this.#authAtom.set((current) => {

      data.hasBioAuth = hasBioAuth && !!biometry
