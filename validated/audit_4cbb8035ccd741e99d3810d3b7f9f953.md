### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` (tenant identity) is taken from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` trusts this unsigned `shop` value to attribute the incoming webhook to a tenant. An attacker who controls (or receives) any single legitimately-signed webhook body/HMAC pair for their own shop can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it with the received `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` — the unsigned header — as the tenant identity passed to the handler: [4](#0-3) 

The binding that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_dispatch`. Because `shop` is excluded from `to_signable_string`, this equality does not hold — the signature only binds the body bytes, not the header the library uses to select the tenant. Any entity capable of obtaining one valid `(raw_body, hmac)` pair for a topic they control (e.g., because they operate a shop that installed the app and receives real webhooks) can resend that identical body and HMAC to the app's public webhook endpoint with the shop-domain header rewritten to any other merchant's `myshopify.com` domain. `HmacValidator.validate` will report the request as valid, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen victim domain, despite Shopify never having sent that shop's webhook.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an unprivileged party (a shop owner using the app, with no special credentials) can make an app believe a webhook body originated from a different merchant. Any handler logic that keys persistence, cache invalidation, entitlement, or access-token/session lookups off `WebhookMetadata#shop` can be corrupted this way (e.g., an `app/uninstalled` webhook forged against a victim shop, or order/product data attributed to the wrong tenant), which is a cross-tenant confusion/integrity issue — meeting the "cross-tenant access" bar for this class of finding.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately received at least one webhook for their own store (trivial — install the app, trigger any subscribed event) and the ability to POST directly to the app's public webhook endpoint with custom headers (also trivial, since the endpoint is a normal internet-reachable HTTP route). No access token, `client_secret`, or other secret is needed; the attacker never has to compute a valid HMAC themselves, they only replay one they already legitimately possess.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook_id`) inside the value that is HMAC-verified, or otherwise cryptographically bind the header to the signed payload before `Registry.process` uses `request.shop` for dispatch. Since Shopify's own webhook HMAC scheme only signs the body, the gem should not treat the `shop-domain` header as authenticated data derived purely from `HmacValidator.validate`; at minimum, document this and/or require callers to independently confirm the resolved shop is one they have an active session/install for before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook subscription (e.g. `products/update`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (valid for `B` under the app's `client_secret`).
2. Attacker sends a new HTTP POST directly to the app's webhook endpoint with:
   - Body: the same bytes `B`
   - Header `X-Shopify-Hmac-Sha256: H`
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - Header `X-Shopify-Topic:` same topic as before
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` [3](#0-2) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the app to process attacker-controlled data under the victim's tenant identity.
