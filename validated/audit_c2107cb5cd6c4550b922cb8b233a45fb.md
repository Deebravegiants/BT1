## Title
POA Bridge withdrawal status matched only by `assetId`, causing hash/status misattribution across multiple same-asset withdrawals in a batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the twin implementation in `internal-utils`'s `waitForWithdrawalCompletion()` resolve the on-chain destination status of a withdrawal by matching entries in the POA bridge API response using **only the token `assetId`** — with no distinction between multiple withdrawals of the *same* token issued in a single intent transaction. `Array.prototype.find` returns the first matching entry, so when a batch of withdrawals contains two or more legs with the same `assetId` (e.g., splitting a `nep141:btc.omft.near` withdrawal to two different destination addresses in one intent), every leg with that `assetId` is described using the *same* API record, regardless of which destination address/amount it actually corresponds to.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  explicitly matches by `assetId` alone:
```
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId)
```
The same pattern exists in [2](#0-1) .

This function is called from `describeWithdrawal()` [3](#0-2) , which is in turn invoked once per withdrawal leg via `watchWithdrawal()` [4](#0-3) , and exposed to integrators through `sdk.createWithdrawalCompletionPromises()` [5](#0-4) , which explicitly documents "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" (see README) — a per-leg 1:1 guarantee that the matching logic does not actually provide when two legs share an `assetId`.

Both matching sites carry the same acknowledgement comment: "multiple withdrawals of the same token in a single transaction are not supported," but this is a code comment, not an enforced invariant — `createWithdrawalIdentifiers()` and `createWithdrawalCompletionPromises()` accept an arbitrary `withdrawalParams` array with no validation rejecting duplicate `assetId`s, so nothing prevents a caller/integrator from submitting such a batch.

Concretely, if `withdrawalParams = [{assetId: X, destination: A, amount: 100}, {assetId: X, destination: B, amount: 200}]` is submitted in one NEAR transaction:
- Both `describeWithdrawal` calls (`index: 0` and `index: 1`) query the same POA `withdrawal_hash`/criteria and both receive the *same* first-matching withdrawal record (say, the leg going to `A`).
- `promises[1]` (which should track the withdrawal to `B`) resolves with `status: "completed"` and `txHash` belonging to the transfer to `A`.

This breaks the equality "status/hash reported == actual on-chain outcome for that specific withdrawal leg."

### Impact Explanation
This falls into the explicitly listed High-impact category: "a status or hash misreport making an integrator credit or refund twice." An integrator relying on `promises[i]`/`describeWithdrawal` per-leg guarantees (as documented in the SDK's own README/JSDoc) could:
- Mark withdrawal to `B` as completed using `A`'s destination tx hash, crediting/confirming the wrong leg as done while the actual transfer to `B` status is silently ignored.
- If both legs are polled and both eventually resolve to the same tx hash, an automated reconciliation system could treat a single destination transfer as proof for two separate withdrawal legs, leading to double-crediting downstream bookkeeping.

### Likelihood Explanation
Likelihood is limited to legitimate batch-withdrawal use cases with duplicate `assetId`s (e.g., splitting a POA-bridged asset to two recipients in one intent) — a plausible, non-malicious integrator pattern rather than an attacker-controlled exploit against the protocol itself. There's no validation anywhere in `createWithdrawalIdentifiers`/`createWithdrawalCompletionPromises`/`sdk.ts` rejecting or warning about duplicate-`assetId` legs before hitting this matching logic, so it will silently misreport rather than fail loudly.

### Recommendation
- Reject (throw) at `createWithdrawalIdentifiers()`/SDK entry points when a batch contains multiple withdrawal legs sharing the same POA-routed `assetId`, until the POA bridge API supports disambiguation.
- Alternatively, implement the amount-based ordering disambiguation already suggested in the code comment (sort both the API results and the withdrawal params by amount for a given `assetId`, since POA fees are constant per token) so each leg's promise resolves to its correct destination transfer.

### Proof of Concept
Given two withdrawal params for the same `assetId` (`nep141:btc.omft.near`) to different destinations submitted via `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [legA, legB], intentTx })`:
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return two `COMPLETED` withdrawal records for `near_token_id: "btc.omft.near"`, one with `transfer_tx_hash: "tx-A"` (matching `legA`'s destination) and one with `transfer_tx_hash: "tx-B"` (matching `legB`'s destination).
2. Call `bridge.describeWithdrawal` for `index: 0` (legA) and `index: 1` (legB).
3. Both calls invoke `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which uses `Array.prototype.find` and returns the *first* array entry for both calls — so `promises[1]` (legB) resolves with `{status: "completed", txHash: "tx-A"}` instead of `"tx-B"`, exactly as demonstrated by the existing test `"matches withdrawal by assetId, not by index"` [6](#0-5) , which only tests the *different-asset* disambiguation case, not the same-asset collision case, confirming the gap is untested and unguarded.

				txHash: withdrawal.data.transfer_tx_hash,

	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
