### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` passes, and then hands `request.shop` straight through to the app's `WebhookHandler` as the trusted tenant identifier. However, the HMAC signature only covers the raw body, not the `shop` (or `topic`/`webhook_id`/`api_version`) headers, so the "verified" and "acted on" data sets diverge: the bytes that are cryptographically checked are not the bytes that determine which shop the event is attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which internally recomputes the HMAC over `to_signable_string` (i.e. body only) and compares it against the `hmac` header: [3](#0-2) 

Once that check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and passes it to the app-registered handler as the trusted per-tenant key: [4](#0-3) 

`WebhookMetadata.shop` is documented and consumed by host applications as the authoritative shop for the event (e.g. used to key data storage/processing): [5](#0-4) 

The identity binding broken is:
`verified(bytes) = raw_body` **≠** `attributed_tenant(bytes) = shop header`

Since a single app-wide `api_secret_key` is used to sign webhooks for every shop that installs the app, an HMAC that is valid for a body delivered for one shop is equally valid for that same body claimed to originate from any other shop — because the header carrying the shop identity is completely outside the signed byte range. An unprivileged party who merely operates their own store with the app installed (a normal, unprivileged tenant, not requiring `api_secret_key` disclosure) can capture one genuine `raw_body`+`hmac` pair delivered to their own endpoint and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (only the body/hmac pair is checked), and `Registry.process` will construct `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application's handler to process/store the replayed payload as if it legitimately originated from the victim shop.

### Impact Explanation
This breaks the tenant-identity binding the gem is expected to enforce before invoking application webhook handlers, enabling cross-tenant data confusion/injection: a malicious webhook payload (topic, body) can be attributed to an arbitrary victim shop domain that the attacker does not control, without needing the app's `client_secret` or any privileged access — only participation as a normal merchant on the same app. Depending on the handler's use of `data.shop` (e.g., updating per-shop billing/subscription state, honoring `customers/redact`/`shop/redact` semantics, writing to shop-scoped storage), this can lead to cross-tenant data corruption or unauthorized state changes attributed to another merchant's shop.

### Likelihood Explanation
Requires only routine access to a webhook delivered to one's own shop's app installation (any merchant that installs the app can trigger events on their own shop and observe the raw HTTP request), plus the ability to POST a crafted HTTP request with a modified header to the app's public webhook endpoint. No secrets, tokens, or elevated privileges are required.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the signed content the gem validates, or otherwise cryptographically bind the header-derived `shop` to the verified payload before constructing `WebhookMetadata`. At minimum, the gem should not silently pass an unauthenticated header value as if it were a verified attribute — `Registry.process` should require/document that consuming applications independently confirm `request.shop` corresponds to a shop that has an active, previously-established session/installation, rather than treating passage of `HmacValidator.validate` as proof that the shop attribution is trustworthy.

### Proof of Concept
1. App merchant M installs the app on `m-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw HTTP request Shopify sends, including `raw_body`, `X-Shopify-Hmac-Sha256`, and `X-Shopify-Shop-Domain: m-shop.myshopify.com`.
2. M resends the identical request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only (`to_signable_string`) — this still matches the original signature, since the shop header is not part of the signed string (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:190-199`), causing the app to process/store attacker-controlled webhook data attributed to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
