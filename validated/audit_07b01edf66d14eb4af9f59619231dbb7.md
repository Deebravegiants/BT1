Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant impersonation via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers of an incoming webhook. Yet `ShopifyAPI::Webhooks::Registry.process` forwards these unauthenticated header values directly to the app's `WebhookHandler` as trusted identity fields (`WebhookMetadata#shop`), which is the exact binding host apps rely on to route/attribute webhook data to a tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`, never any of the `shopify-*` headers.

`HmacValidator.validate` computes the HMAC exclusively over whatever `to_signable_string` returns: [2](#0-1) 

`Registry.process` gates on this HMAC check, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all read straight from HTTP headers — to build the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

Those header accessors are plain unauthenticated getters: [4](#0-3) 

The documented contract explicitly tells app authors that `data.shop` is "The shop domain of the webhook" and to use it for tenant attribution (e.g. `shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

This breaks the identity binding: `shop that the HMAC authenticates == shop delivered to the handler`. In reality the equation is `shop that the HMAC authenticates == "" (nothing)`, and `shop delivered to the handler == attacker-controlled header value`.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimate, validly-signed webhook delivery for the app (trivially achieved by installing the app on their own free/dev store and letting it fire a webhook, e.g. `orders/create`) can capture the `(raw_body, X-Shopify-Hmac-Sha256)` pair. They can then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. `HmacValidator.validate` still succeeds because only the body is checked, and `Registry.process` passes the forged `shop` value straight through to the app's handler as authentic. Any app that uses `data.shop` to attribute, store, or act on webhook data per-tenant (exactly as the gem's own documentation instructs) will process or persist attacker data under a different tenant's identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Reachable by any unprivileged internet user with no access to the app's `client_secret` or any merchant's access token: they only need the ability to trigger one legitimate webhook to themselves (installing the app on a store they control) and then send a crafted HTTP request to the app's public webhook callback endpoint with a modified `shop-domain` header. No privileged credentials or app secrets are required.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the signable string that `HmacValidator` verifies (or otherwise cryptographically bind them to the HMAC), so that any header value delivered to the handler is provably authenticated by Shopify rather than trusted verbatim from the HTTP request.

### Proof of Concept
1. Install the app on an attacker-controlled development store; trigger any webhook (e.g. `orders/create`) and capture the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header `H` — this pair is validly signed by Shopify with the app's real `api_secret_key`.
2. Send a new HTTP POST to the app's webhook endpoint with the identical body `B` and header `H`, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string == B` only — it passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `victim-shop.myshopify.com` header value and invokes the app's handler, which believes the webhook body legitimately originated from `victim-shop.myshopify.com`.
