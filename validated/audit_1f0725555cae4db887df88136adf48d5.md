## Title
Escrow accounting credited with requested transfer amount instead of actual amount received — Tron `IntentGatewayV2.placeOrder()` (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sherlock report describes Derby's Vault `pullFunds()` decrementing `savedTotalUnderlying` by the amount *requested* for withdrawal rather than the amount *actually* withdrawn, causing the internal accounting variable to permanently diverge from the funds truly available. The Tron `IntentGatewayV2` contract contains the mirror-image defect on the deposit side: it credits its escrow ledger `_orders[commitment][token]` with the amount the user's order *claims* to transfer, without ever verifying the amount the contract *actually received*. On any token whose `transferFrom` delivers less than the nominal amount (fee-on-transfer, deflationary, or otherwise non-standard ERC20s), the escrow ledger becomes permanently overstated relative to the contract's real token balance.

### Finding Description
In `placeOrder()`'s direct-transfer branch (no predispatch), the contract does: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` (minus the protocol fee), never from the contract's post-transfer balance. There is no `balanceOf` check before/after `safeTransferFrom`, unlike the fixed EVM mainline contract, which explicitly measures actual receipt to defend against fee-on-transfer tokens: [2](#0-1) 

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```

The predispatch branch in the same Tron contract at least performs a dust check on the sweep leg (`dust = balance - requiredAmount`), but this only measures what the `CallDispatcher` forwards — it does not correct for a fee-on-transfer loss on the initial `safeTransferFrom(msg.sender, dispatcher, amount)` leg either.

The escrow ledger is later drawn down against the pooled contract balance on withdrawal/fill/refund: [3](#0-2) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
        _orders[body.commitment][token] -= amount;
```

Because every order's tokens of the same ERC20 sit in one shared contract balance, an overstated ledger entry for one order does not fail immediately — it silently consumes real tokens that belong to other, later orders' escrow entries.

### Impact Explanation
Exactly as in the Vault `savedTotalUnderlying` bug, this is not a one-off rounding error but a systemic, compounding accounting drift: every `placeOrder()` call using a fee-on-transfer/deflationary token overstates `_orders[commitment][token]` by the transfer-fee amount, while the contract's real ERC20 balance is short by that same amount. As more such orders accumulate, the sum of all escrow ledger entries for that token exceeds the contract's actual balance. Eventually a legitimate solver/beneficiary withdrawal or refund for an earlier order will attempt to transfer more than the contract holds, reverting (`TransferFailed`) and permanently freezing that user's/solver's funds, or — depending on transfer ordering — silently draining tokens that were escrowed for a different, unrelated order. This is a protocol-wide, cross-user fund-freezing/loss vector, not confined to the token's own transfer-fee "loss" — it manifests as another party's assets becoming unrecoverable.

### Likelihood Explanation
Any fee-on-transfer, deflationary, or rebasing ERC20 configured as an input asset triggers this on every `placeOrder()` call through the non-predispatch path — no attacker action beyond normal usage is required, and it accumulates automatically with each such order. The bug class is proven exploitable in this codebase because the sibling EVM mainline contract (`evm/src/apps/IntentGatewayV2.sol`) was explicitly patched to defend against it (with dedicated fee-on-transfer regression tests), confirming both the codebase's exposure to such tokens and that the Tron variant lacks the corresponding fix.

### Recommendation
Mirror the EVM mainline fix in the Tron `IntentGatewayV2.placeOrder()`: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and in the predispatch leg, before/after the `dispatcher`-bound transfer as well), and credit `_orders[commitment][token]` using the actually-received delta rather than the caller-supplied `order.inputs[i].amount`, consistent with how the commitment/escrow reconciliation is already done on the EVM side.

### Proof of Concept
1. Configure/permit a fee-on-transfer ERC20 (e.g., 1% fee) as an input token for the Tron `IntentGatewayV2`.
2. User calls `placeOrder()` with `order.inputs[0].amount = 1000` of that token, taking the non-predispatch branch (lines 450-469).
3. `safeTransferFrom` delivers only 990 tokens to the gateway (contract's real balance increases by 990), but `_orders[commitment][token] += reducedInputs[0].amount` credits 1000 (minus protocol fee, still based on the nominal 1000, not the 990 actually received).
4. Repeat with additional orders using the same token; the aggregate `_orders[...][token]` ledger across all commitments grows faster than the contract's actual token balance.
5. When solver/beneficiary calls the withdrawal path (`withdraw()`) for an earlier commitment after later escrow entries have been recorded, the shared token balance is insufficient to honor all ledger entries — a withdrawal reverts with `TransferFailed`, permanently freezing that order's escrowed funds, or drains balance intended for another order's escrow.
