## Title
Webhook HMAC only signs the request body, letting a forged `shop-domain` header spoof tenant identity in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, and `webhook_id` values used by `Webhooks::Registry.process` to attribute and dispatch the webhook are taken from HTTP headers that are never included in the HMAC computation. This breaks the identity binding `hmac-authenticated bytes == bytes used to determine the shop the event is attributed to`.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`. For webhooks, this is defined as: [1](#0-0) 

Only `@raw_body` is signed. However, `shop`, `topic`, and `webhook_id` are all pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the body HMAC, then dispatches the handler using these header-derived, unauthenticated values as the tenant/topic identity: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any unprivileged internet user can:
1. Create a free/development Shopify store and install the target app (no privileged access required).
2. Trigger any webhook event on their own store, capturing a legitimately-signed `(raw_body, hmac)` pair delivered to the app's public webhook endpoint.
3. Replay that exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint again, but with an attacker-chosen `shopify-shop-domain` header (a victim shop) and/or `shopify-topic` header.

`HmacValidator.validate` still passes because the signature only ever covered `raw_body`, which is unchanged. `Registry.process` then invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled shop/topic, crossing the tenant boundary the HMAC was supposed to enforce.

### Impact Explanation
This lets an unprivileged attacker forge webhook deliveries that the app will treat as authentic events for a different, victim shop (e.g. spoofing `app/uninstalled`, `shop/redact`, or order/customer events attributed to a victim's shop domain while carrying attacker-controlled body content from their own store). Since the shop identity used to key data storage and app logic downstream is exactly this unauthenticated header value, this is a cross-tenant access/impersonation vector qualifying as Critical impact.

### Likelihood Explanation
High. No privileged credentials, TLS interception, or social engineering are needed — only a free Shopify store and the ability to install the target public app once, both trivially available to any internet user, plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint (which by design must accept unauthenticated internet traffic from "Shopify").

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`/or at minimum `shop`) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind the header values to the signature (e.g., compute/verify the HMAC over `headers + body` rather than body alone), so a replayed body cannot be re-attributed to a different shop or topic.

### Proof of Concept
1. Attacker creates a free development store `attacker-shop.myshopify.com` and installs the target app, which registers a webhook (e.g. `orders/create`).
2. Attacker triggers the event on their own store, and their controlled webhook receiver (or network capture, since it's their own tenant/app installation) records the delivered `raw_body` and the `X-Shopify-Hmac-Sha256` header the app itself would receive — this pair is valid per `HmacValidator.validate` because it only signs `raw_body`.
3. Attacker sends a new POST to the app's public webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (body unchanged), then dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-supplied data as if it originated from the victim tenant.
