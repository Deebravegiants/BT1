### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC only over the raw request body, while the `shop` attribute used downstream to identify which merchant/tenant the webhook belongs to is read from an HTTP header that is completely outside the signed material. An attacker who can obtain one legitimately-signed webhook body/HMAC pair (e.g., from a shop they control that has the target app installed) can replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value. `HmacValidator.validate` will still succeed because it only checks the body, but `ShopifyAPI::Webhooks::Registry.process` hands the attacker-chosen `shop` value to the handler as if it were verified, breaking the binding `shop authenticated == shop the HMAC actually vouches for`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

and

```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` verifies the request by recomputing an HMAC-SHA256 over `to_signable_string` (i.e. only `@raw_body`) and comparing it against the `hmac` field: [3](#0-2) 

The `shop` value is never part of `to_signable_string`, so it is never covered by the HMAC. `Registry.process` nevertheless trusts `request.shop` as the authenticated tenant identifier once the HMAC check passes:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Before/after the attacker's request:
- Before: a valid `(raw_body, hmac)` pair is bound only to *content*, with no cryptographic link to the `shop-domain` header. `shop_that_HMAC_vouches_for` is undefined — the gem treats `shop` as trusted metadata despite it never entering the signable string.
- After: attacker resends the same `raw_body`/`hmac` with a different `shop-domain` header. `HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` forwards the attacker-chosen `shop` to the handler as `WebhookMetadata#shop`, i.e. `shop_authenticated == shop-domain header (attacker controlled) != shop_that_actually_produced_the_signed_body`.

Any application logic that keys per-tenant state (offline session/access-token lookup, data writes, webhook idempotency) off `WebhookMetadata#shop` will process the event under the wrong tenant, i.e. cross-tenant access using a webhook that was cryptographically valid for a different shop.

### Impact Explanation
This breaks the identity binding between the cryptographically-verified payload and the tenant it is attributed to, allowing an attacker who possesses at least one valid webhook (obtainable by installing the app on a shop they control) to make the receiving application believe the payload originated from a different, arbitrary shop. This is a cross-tenant access vector as listed under Critical impact criteria in the rules.

### Likelihood Explanation
The attacker only needs: (1) the target app installed on a shop they control (or any way to obtain one legitimate `raw_body`+HMAC pair, e.g. a webhook whose body content is attacker-influenced, such as a customer/order-created webhook they trigger themselves), and (2) the ability to POST to the app's public webhook endpoint with custom headers, which is inherent to any HTTP client. No access token, `client_secret`, or elevated privilege is required — only unprivileged internet access to the app's webhook URL.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind `shop` to the verified payload before exposing it via `Webhooks::Request#shop`/`WebhookMetadata`. At minimum, document loudly that `shop` is unauthenticated header data and must never be trusted for tenant-sensitive decisions without an independent server-side verification (e.g., cross-checking against a stored session for that shop before trusting the payload).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (they own the shop, so this data is available to them, e.g. via server logs of a proxy they control, or from an app that echoes the payload back).
3. Attacker crafts a new HTTP POST to the same webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only, which matches, so validation passes at [5](#0-4) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload was never generated for that shop, at [6](#0-5) .
6. Any handler logic that trusts `data.shop` to select tenant context (e.g. fetch stored offline access token for `victim-shop.myshopify.com` and act on it, or write data attributed to that shop) is now operating under attacker-controlled tenant identity.
