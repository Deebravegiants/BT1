### Title
Stale position-manager delegation silently reactivates when a position NFT returns to its prior owner - (File: contracts/controller/src/storage/account.rs)

### Summary

Delegate grants are stored as a `DelegateGrant` keyed by `account_id` and stamped only with the granting owner’s address. When a position NFT is transferred, the grant becomes inactive because the current NFT owner no longer equals `granted_by`, but the grant is not deleted or bound to a unique ownership epoch. If the NFT later returns to the original owner, the same stale grant becomes valid again without a fresh `add_delegate` authorization.

### Finding Description

The controller resolves account ownership dynamically from the position NFT, while `get_delegates` accepts a stored grant whenever `grant.granted_by == owner`. [1](#0-0)  A caller qualifies as a delegate when it is currently registered as an active position manager and appears in that returned list. [2](#0-1) 

An NFT transfer changes the owner and therefore disables the previous owner’s delegate list, but it leaves the storage entry untouched. The grant consequently re-arms if the token later returns to `granted_by`; only a subsequent owner calling `add_delegate` or `remove_delegate` replaces or deletes the stale list. [3](#0-2) 

The reactivated delegate can then invoke owner-or-delegate account functions. In particular, `withdraw` authenticates the caller, accepts an owner or delegate, allows zero-amount full withdrawals, and permits an explicit recipient. [4](#0-3)  Likewise, `borrow` accepts an owner or delegate and can send borrowed assets to an external recipient. [5](#0-4) 

### Impact Explanation

A formerly approved position manager can steal collateral or borrowing power after the original owner reacquires the position NFT, even though the owner never authorized that manager for the new ownership period. For a debt-free account, the delegate can withdraw the full collateral balance to itself. For a collateralized account, it can borrow up to the permitted LTV to itself and leave the debt on the victim’s account, or withdraw any excess collateral that still passes the post-operation solvency checks.

This is theft of user funds. The attack does not require the owner to sign a new delegation after regaining the NFT.

### Likelihood Explanation

The attack requires three preconditions:

1. The original owner previously granted an active position manager.
2. The position NFT was transferred away without a later owner deleting or replacing the stale delegate list.
3. The NFT later returns to the original owner while that manager remains active.

Those conditions can arise through NFT sale, temporary custody, wallet migration, or other ordinary transfers. Afterward, the stale delegate itself can submit the harmful controller call. The manager must still be an active registered position manager, but that is a normal delegated account role rather than a privileged administrative role.

### Recommendation

Do not allow a delegation grant to survive an ownership transition. Clear `ControllerKey::Delegates(account_id)` whenever the position NFT transfers, for example through a controller callback from the NFT transfer path.

If callbacks are undesirable, store an ownership epoch in account metadata and in each `DelegateGrant`. Increment the epoch whenever the observed NFT owner changes, and accept a grant only when both `granted_by` and the epoch match. This also prevents reactivation when the same address becomes owner again.

### Proof of Concept

1. Alice calls `supply` and creates account `1` holding collateral.
2. Governance has previously registered `Manager` as an active position manager.
3. Alice calls `add_delegate(caller=Alice, account_id=1, delegate=Manager)`. The controller authenticates Alice as the current NFT owner and stores `DelegateGrant { granted_by: Alice, delegates: [Manager] }`. [6](#0-5) 
4. Alice transfers position NFT `1` to Bob. Since account id equals token id, the account and its positions move with the NFT. [7](#0-6) 
5. Bob never calls `add_delegate` or `remove_delegate`, so the stale grant stamped by Alice remains in storage.
6. Bob transfers NFT `1` back to Alice.
7. `Manager` calls:
   `withdraw(caller=Manager, account_id=1, withdrawals=[(collateral_hub_asset, 0)], to=Some(Manager))`.
8. `account_owner(1)` resolves to Alice. `get_delegates` compares the stale grant’s `granted_by` with Alice, returns `Manager`, and `require_owner_or_delegate` accepts the call. The zero amount requests the full collateral position and the pool pays it to `Manager`, subject to the normal post-withdrawal solvency check.

No fresh authorization from Alice occurs after she reacquires the account.
