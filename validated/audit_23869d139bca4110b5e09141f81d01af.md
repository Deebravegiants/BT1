### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by HMAC-checking only the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers when invoking the app's handler. Because the app's `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs the app, any merchant who installs the app (an ordinary, unprivileged action) can capture a validly-signed webhook delivered to their own endpoint and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, causing the app to process attacker-influenced data under another tenant's identity.

### Finding Description
The webhook signature verification is implemented as: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` uses this validation, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which participated in the signature) to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop that produced/signed the webhook body == shop the app attributes the webhook data to`. Because the HMAC only signs the body and not the `shop-domain` header, this equality is not enforced — an attacker can present `signed_body` from shop A together with `shop-domain: victim-shop.myshopify.com`, and `HmacValidator.validate` will still return `true` since it only re-hashes `raw_body`.

Critically, the signing secret (`api_secret_key` / the app's `client_secret`) is the same for every shop that installs a given app — it is not shop-specific. This means:
1. An attacker installs the target app on their own shop (an ordinary, unprivileged merchant action requiring no special credentials).
2. Shopify sends a legitimately signed webhook (e.g. `products/update`) to the app's callback URL for the attacker's own shop. The attacker can influence some webhook body content (e.g. product titles/notes on their own store) and captures the raw body + valid `hmac` header for this delivery.
3. The attacker replays this exact `raw_body`/`hmac` pair directly to the app's webhook endpoint, but swaps the `X-Shopify-Shop-Domain` header for a victim shop's domain (and optionally the topic/webhook-id headers).
4. `HmacValidator.validate` passes because it only checks the (unmodified) body against the (unmodified, correctly-computed) HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, so the app processes attacker-supplied content as if it originated from the victim tenant.

This directly matches the report's bug class: a "field acted on but not covered by the HMAC" — here `shop`/`topic`/`webhook_id` headers are consumed as trusted identity data by `Registry.process` while being entirely outside the signed payload.

### Impact Explanation
This breaks tenant isolation between installations of the same app: data attributed to one shop can be forged to appear as though it belongs to another shop. Depending on what the app's webhook handler does with `data.shop` (e.g., looking up/updating a `shop`-keyed record, writing order/customer data, or granting shop-scoped effects), an attacker can inject or corrupt data associated with a victim tenant they do not control, which qualifies as cross-tenant access/data confusion — a Critical-tier impact per policy (cross-tenant access).

### Likelihood Explanation
The precondition is low-effort and requires no leaked credentials or privileged access: any user can install the target app on their own store (a normal, unprivileged action for anyone using the target platform), trigger a webhook of their choosing, capture a valid `(raw_body, hmac)` pair, and replay it toward the app's public webhook endpoint with a forged `shop-domain` header, since the header is never validated or bound to the signature.

### Recommendation
Include the webhook identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content, or otherwise cryptographically bind them to the HMAC rather than only signing `raw_body`. At minimum, `ShopifyAPI::Webhooks::Registry.process`/the gem's documentation should require/perform verification that `request.shop` corresponds to a shop actually known to have an active installation with an `api_secret_key`-derived signature that also incorporates the shop identity, so a signed body from shop A cannot be relabeled as belonging to shop B. Consider updating `Request#to_signable_string` and `HmacValidator` to include these header values in the signed string (matching how Shopify's real webhook signature construction should authenticate the full request context, not just the body).

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and triggers e.g. a products/update webhook, capturing the delivery:
raw_body = '{"id":123,"title":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
encoded_hmac = Base64.encode64(valid_hmac)

# 2. Attacker replays the same body+hmac to the app's public webhook endpoint,
#    but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => encoded_hmac,          # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. Registry.process passes HMAC validation (body unchanged) and calls the
#    handler with shop: "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...attacker content...}))
``` [4](#0-3) [3](#0-2)
