### Title
Missing `protocolFeeBps`/`destinationFeeBps` bounds validation in Tron `IntentGatewayV2.onAccept` `UpdateParams` handler permanently DoSes `placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) duplicates the `UpdateParams` governance-update logic that exists in the mainline EVM `IntentsBase.sol`, but drops the validation helper that the mainline calls before writing state.

### Finding Description
In the mainline EVM implementation, both the initial setup and every subsequent update of gateway parameters go through `_validateParams`, which enforces `protocolFeeBps < 10_000` and, in `_updateParams`, additionally enforces every `destinationFeeBps < 10_000` before values are written to storage: [1](#0-0) 

The Tron contract re-implements the equivalent `UpdateParams` handling directly inside `onAccept`, but never calls any validation function — `_params` is overwritten and `_destinationProtocolFees[stateMachineId]` is written from `feeBps` with no upper-bound check at all: [2](#0-1) 

The corresponding one-time `setParams` admin function in the same Tron contract also writes `_params` with zero validation: [3](#0-2) 

This is exactly the bug class from the external report: the validation logic exists as a "helper" that is only invoked from one code path (the EVM mainline's `_updateParams`), and a second, independently-written code path performing the same conceptual operation (the Tron `UpdateParams` handler) forgot to call it. Once `_params.protocolFeeBps` or any `_destinationProtocolFees[stateMachineId]` entry is set to `>= 10_000` (100%), every subsequent `placeOrder` call for that destination computes: [4](#0-3) 
`protocolFee = (originalAmount * protocolFeeBps) / 10_000` can exceed `originalAmount`, making `reducedAmount = originalAmount - protocolFee` underflow and revert unconditionally for every order routed to that state machine (or globally, if `_params.protocolFeeBps` itself is the bad value).

### Impact Explanation
Any single malformed `UpdateParams` message delivered to the Tron gateway (whether from a benign governance mistake or a compromised/misrouted message, exactly the "Alice makes an erroneous assumption" scenario in the source report) permanently bricks `placeOrder` for every unprivileged intent user/solver on that destination — a protocol-wide denial of service with no recovery path short of another governance message correcting the value. This matches the "route unable to deliver messages" / permanent freezing-of-funds class (escrowed inputs from users who called `placeOrder` before the bad update remain locked if the corresponding `fillOrder`/cancel flow also becomes unusable, and no new orders can be placed at all afterward).

### Likelihood Explanation
The bug is a straightforward duplication defect: the exact validation exists and is tested in the mainline EVM contract (`testRevert_UpdateParams_DestinationFeeBpsTooHigh`), showing the protocol authors are aware of and value this invariant, but the Tron fork's hand-duplicated `onAccept` logic omits it entirely. Because Tron's `onAccept` is reached by any relayed Hyperbridge governance-originated `PostRequest` of kind `UpdateParams` (gated only by `request.source == hyperbridge()`, not by any bounds-checking on the payload), a single value that a human operator or the pallet's dispatch logic fails to bound-check on the way out will silently brick the Tron deployment permanently, with no defense-in-depth on the contract side.

### Recommendation
Add the same bounds checks used in `evm/src/apps/intentsv2/IntentsBase.sol::_validateParams` / `_updateParams` to the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch (reject `protocolFeeBps >= 10_000` and any `destinationFeeBps >= 10_000` before writing) and to `setParams`. More broadly, per the external report's long-term recommendation, this validation should live in a single shared library invoked identically by every implementation (mainline and Tron) rather than being re-implemented ad hoc per fork, to prevent this exact "assumption that the helper ran" class of defect from recurring on future duplicated code paths.

### Proof of Concept
1. Hyperbridge governance (or a relayer, if the payload is not independently bound-checked before dispatch) delivers a `PostRequest` to the Tron `IntentGatewayV2` with `body[0] == RequestKind.UpdateParams` and `ParamsUpdate.params.protocolFeeBps = 10_000` (or a `destinationFees` entry with `destinationFeeBps = 10_000`).
2. `onAccept` at `evm/tron/contracts/apps/IntentGatewayV2.sol:644-660` decodes and writes this value directly into `_params`/`_destinationProtocolFees` with no revert.
3. Any user subsequently calls `placeOrder` targeting that destination; `evm/tron/contracts/apps/IntentGatewayV2.sol:359-365` computes `protocolFee == originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows against `originalAmount` when `protocolFeeBps > 10_000`, or produces a `0` output but more importantly any `protocolFeeBps > 10_000` reverts the subtraction — reverting every future `placeOrder` call for that destination and freezing the gateway.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
