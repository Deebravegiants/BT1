### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the handler come from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then dispatches `WebhookMetadata` (including the header-derived `shop`) to the app's handler as the trusted tenant identifier.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., body bytes only): [3](#0-2) 

`Registry.process` trusts this validation and then forwards the request's header-derived `shop` (and `topic`) to the handler unchanged: [4](#0-3) 

This breaks the binding: **shop authenticated (used to dispatch/act on tenant data) ≠ shop covered by the HMAC signature**. The signature only proves "this body was signed with the app's secret at some point"; it proves nothing about which shop, topic, or webhook-id the signer intended. Any HTTP header value can be substituted after the fact without invalidating the signature, since headers are never part of `to_signable_string`.

### Impact Explanation
An attacker who can obtain one legitimately signed `(raw_body, hmac)` pair emitted by Shopify for the app (e.g., by installing the same app on a shop they control, or observing a webhook delivered to their own store) can replay that exact body/HMAC pair while altering the `shop-domain` (and/or `topic`/`webhook-id`) headers to name a different, victim shop. Because `HmacValidator.validate` never inspects those headers, the forged request still passes signature verification, and `Registry.process` will hand the attacker-chosen `shop` value to the app's webhook handler as if it were authentic. Any handler logic that uses `data.shop` to select which tenant's records to create/update/delete (a very common pattern for webhook handlers) can be tricked into writing data cross-tenant, corrupting or leaking another merchant's state — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation requires obtaining at least one valid signed webhook body for the target app (trivial for anyone who can install the app on their own store, since app installation itself is typically self-service and unprivileged with respect to this gem) and does not require the `api_secret_key`, an access token, or any privileged account for the target shop. The header substitution itself is achievable purely by any client capable of sending arbitrary HTTP headers to the app's webhook endpoint. No man-in-the-middle or TLS interception is needed.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the value that is HMAC-verified, or otherwise cryptographically bind the header-derived identifiers to the signed payload before they are trusted by handler dispatch. At minimum, document and/or enforce that the `shop` used for any storage/session lookup in a webhook handler must be independently confirmed against a known-installed/authorized shop list rather than trusted solely because `HmacValidator.validate` returned `true`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimately Shopify-signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `topic`/`webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` computes HMAC over `@raw_body` (still `B`) and compares against `H` — validation succeeds because headers are never part of the signed content: [5](#0-4) 
4. `Registry.process` proceeds to call the handler with `shop: request.shop` = `"victim-shop.myshopify.com"`, even though the signed body `B` was never actually sent by/about that shop.
