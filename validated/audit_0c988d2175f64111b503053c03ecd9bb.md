### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers. `Registry.process` trusts the header-derived `shop` value and hands it directly to the app's webhook handler as the tenant identity for that event, without the header being covered by the signature that `Utils::HmacValidator.validate` checks.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery`/`HmacValidator` — recomputes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header: [3](#0-2) . Since `to_signable_string` is body-only, this check proves nothing about the `shop-domain` header. Immediately after this check succeeds, `Registry.process` builds `WebhookMetadata` using `request.shop` taken straight from that unauthenticated header and forwards it to the app's handler as the trusted tenant identifier: [4](#0-3) .

The identity binding that should hold is:
`shop authenticated by signature == shop the app acts on`

but the actual binding implemented is:
`shop the app acts on == shop header value (unauthenticated, attacker-controlled)`

Documentation confirms downstream apps are expected to trust `data.shop` as the tenant identity for handling business logic (e.g. enqueuing per-shop jobs): [5](#0-4)  and [6](#0-5) .

### Impact Explanation
An unprivileged internet user who is a legitimate merchant with the app installed on their own store (no `api_secret_key`, access token, or privileged account needed) can:
1. Trigger any subscribed webhook topic on their own shop, causing Shopify to POST a body `B` with a valid `HMAC(secret, B)` to the app's shared webhook endpoint.
2. Capture that `(B, hmac)` pair (they control the receiving traffic to/through their own infrastructure, or simply intercept it if the app logs/echoes it back, or via a proxy they control before forwarding to the real app if they run their own instance for testing).
3. Replay the exact same `raw_body`/`hmac-sha256` pair to the app's shared webhook endpoint, but swap the `X-Shopify-Shop-Domain` header to a victim shop's domain.

Because the HMAC check only covers `raw_body`, the forged request still validates successfully, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that uses `data.shop` to route/attribute effects (billing changes, data sync, order processing, cache invalidation, GDPR/redact actions, etc.) is exposed to cross-tenant data corruption or unauthorized action attribution — this satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to be a real, if malicious, merchant with the app installed (a normal, unprivileged relationship to the app — no leaked secrets or tokens needed), and to know/guess a target shop's domain (which is often public, e.g. `victim.myshopify.com`). The attack does not require breaking any cryptography — it only requires that the signed byte range (`raw_body`) not change between the legitimate and forged requests, and swapping a header the gem does not protect.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) in the signable string that is HMAC-validated, or otherwise independently verify that the `shop` claimed in the webhook headers matches a shop the app has an active, `HMAC-endorsed` relationship with (e.g., cross-checking against a registered/installed shop list) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop` is unauthenticated and must not be trusted for tenant-identity decisions without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and trigger a subscribed webhook topic (e.g. `orders/create`) to receive a legitimate signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H = base64(HMAC-SHA256(secret, B))`.
2. Construct a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Topic: orders/create` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed, and `ShopifyAPI::Webhooks::Registry.process(request)` is called (as shown in the gem's documented integration pattern in `docs/usage/webhooks.md`).
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`, which is unchanged.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)` — code confirmed at [4](#0-3)  — despite the event never actually originating from Shopify for `victim-shop`.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
