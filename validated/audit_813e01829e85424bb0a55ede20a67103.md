### Title
Arbitrary external call in `EmporiumUpgradeable.runAction` bypasses all balance/UTXO accounting when `erc20TokenAddresses=[]` — theft with zero accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`onlyAllowedRecipient` only restricts the caller to being the `Hinkal` contract, it does not authenticate who authorized the `EmporiumStack` payload's contents [1](#0-0) . When an attacker submits `circomData.erc20TokenAddresses = []`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only supplies `emporiumMessage`, `timeStamp`, `calldataHash` as public circuit inputs to the trivial `MainEVMCircuitMin` circuit (`message <== Poseidon(1)([messageSeed])`, no constraint at all on tokens/amounts/nullifiers/commitments) [2](#0-1) [3](#0-2) . Inside `runAction`, when `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without checking any signature [4](#0-3) , and the "Stateless Interaction" branch performs a raw, attacker-controlled `op.endpoint.call{value: op.value}(op.callData)` gated only by two forbidden selectors [5](#0-4) . Since `circomData.erc20TokenAddresses` is empty, none of `balancesBefore`/`balancesAfter`/`handleOut`/the `BalanceChangeShouldBePositive` accounting loop ever execute for token `X` [6](#0-5) , so any token `X` balance sitting at the Emporium contract can be drained via a self-crafted call op (e.g. `op.endpoint = X`, `op.callData = transfer(attacker, balance)`) with zero UTXO/amountChange accounting.

### Finding Description
**Equality claimed broken:** every token unit that leaves Emporium custody during `runAction` must be reflected either in `amountChanges`/`deltaAmountChanges` (accounted balance movement) or as a newly-created UTXO in `utxoSet`/`outCommitments` (accounted off-chain value). i.e. `Σ(balance leaving custody) == Σ(deltaAmountChanges) + Σ(utxoSet.amount)`.

**Trace:**
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which verifies `calldataHash` integrity and calls `CircomDataBuilder.formInputForCircom` [7](#0-6) .
2. Because `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputEmporiumMin` is used, producing only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) for the `MainEVMCircuitMin` verifier [8](#0-7) . That circuit does not constrain any spend/UTXO/nullifier/amount data whatsoever — `message` is simply `Poseidon(messageSeed)` with no relation to tokens moved [3](#0-2) . Any attacker can trivially produce a valid proof for arbitrary `calldataHash`/`timeStamp`/`emporiumMessage` because there is no secret witness tying it to real balances.
3. `Hinkal.transact` snapshots `oldBalances = getBalancesForArray([])` (empty array, no-op) and calls `_externalTransact` → `EmporiumUpgradeable.runAction` [9](#0-8) .
4. In `runAction`, `stack = abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` is fully attacker-controlled. Attacker sets `stack.signerAddress = address(0)`, causing `verifyWallet` to return early (no EIP-712 signature check at all) [10](#0-9) .
5. The ops loop takes the "Stateless Interaction" branch and executes `op.endpoint.call{value: op.value}(op.callData)` directly with no ownership check on `op.endpoint`/`op.callData`, other than blocking the two `IHinkalWallet` selectors [5](#0-4) . Attacker sets `op.endpoint = X` (the token contract) and `op.callData = abi.encodeCall(IERC20.transfer, (attacker, balanceOfEmporium))`. Since `msg.sender` from token X's perspective is the Emporium contract, this transfers X's entire Emporium-held balance to the attacker.
6. Post-loop, `circomData.erc20TokenAddresses.length == 0`, so the loop computing `balanceChange`, the `BalanceChangeShouldBePositive` revert, and `handleOut` (which would create a UTXO and transfer proceeds back into Hinkal's shielded pool) never run for token X [6](#0-5) . `utxoSet` returned is empty (`erc20TokenAddresses.length == 0` array).
7. Back in `Hinkal.transact`, the `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` accounting loop also does not iterate (0 iterations), so the "balance diff equals amountChanges + utxoAmount" invariant is never checked for token X [11](#0-10) .

**Root cause:** the "min" code path for Emporium (designed to save proving costs for pure external-call flows that don't touch shielded balances) allows fully unauthenticated, arbitrary external calls (`op.endpoint.call(op.callData)`) whenever `signerAddress == address(0)`, combined with the fact that the accounting/UTXO-creation logic is keyed entirely off `circomData.erc20TokenAddresses`, which the same untrusted caller sets to `[]`. Nothing forces the tokens acted upon by `stack.ops` to be a subset of `erc20TokenAddresses`, and the ZK proof for the "min" circuit provides no real constraint linking `ops` to `erc20TokenAddresses` or to authorized value.

**Why existing guards fail:**
- `onlyAllowedRecipient` only checks `msg.sender == Hinkal` [1](#0-0) ; it does not validate the contents of `externalActionMetadata`.
- `verifyWallet`'s EIP-712 check is bypassed entirely when `signerAddress == address(0)` — this is a documented, valid, no-signature code path (Case 2), not a bug in signature verification itself, but it means the "stateless" ops are entirely un-authorized apart from calldata-hash binding, and the calldata hash is checked against a circuit that constrains nothing about balances.
- `performHinkalChecks`'s calldata-hash check merely ensures the tx's `circomData` matches what was hashed into the (unconstrained) proof; it does not itself validate the ops' target tokens against `erc20TokenAddresses`.
- The core value-conservation checks in `Hinkal.transact` (lines 97-146) and in `EmporiumUpgradeable.runAction` (lines 126-160) are both driven by `circomData.erc20TokenAddresses`, which the attacker sets to `[]` to skip them for token X.

### Impact Explanation
Any ERC20/ETH balance sitting at the `EmporiumUpgradeable` contract for any reason (residual dust from prior transactions, other users' in-flight funds moved into Emporium as part of a multi-op Emporium sequence before being swept out, or funds deposited by any third party) can be transferred to an attacker-chosen recipient with zero on-chain accounting: no `amountChanges` entry, no UTXO, no nullifier, no commitment. This is direct theft of protocol-custodied / in-flight user funds with no cryptographic trace, matching the **Critical** severity bucket (theft of shielded or in-flight user funds with no accounting). It is repeatable any time the Emporium contract holds a non-zero balance of any token not represented in the attacker's chosen `erc20TokenAddresses` array.

### Likelihood Explanation
- **Preconditions:** Emporium contract must hold a non-zero balance of token `X`. This is plausible because the Emporium pattern intentionally routes funds through the contract during multi-step external interactions (deposits into Emporium prior to a later sweep, dust left after slippage, ETH `value` forwarded to ops, etc.).
- **Attacker cost:** trivial — the attacker only needs to submit a `transact` call with `erc20TokenAddresses=[]`, a self-crafted `EmporiumStack` with `signerAddress=address(0)` and one stateless op calling `X.transfer(attacker, balance)`, and a proof for the unconstrained `MainEVMCircuitMin` circuit (which requires no genuine secret/authorization since it only outputs `Poseidon(messageSeed)`).
- **Feasibility/Repeatability:** fully repeatable for any token X the Emporium happens to hold at call time; attacker can also engineer the precondition by interleaving with other legitimate Emporium flows or dust-producing transactions.

### Recommendation
- Require `circomData.erc20TokenAddresses` (and thus the accounting/UTXO loops) to include every token address touched by `stack.ops` when in the "min"/stateless code path, or otherwise cryptographically bind `ops`'s target token set to `erc20TokenAddresses` before allowing the min-circuit path.
- Alternatively, disallow the "min" (`erc20TokenAddresses.length == 0`) proof path entirely for `runAction` calls whose `EmporiumStack` contains Case-2 "Stateless Interaction" ops that could move ERC20/ETH balances held directly by the Emporium contract (e.g. require `signerAddress != address(0)` and route all token-moving calls exclusively through `IHinkalWallet.callHinkalWallet`, which operates on the signer's own external wallet, not on Emporium's own token custody).
- At minimum, add a post-condition check comparing Emporium's balance of every ERC20 token actually referenced by `stack.ops.endpoint`/`callData` before and after, reverting if any decreases without matching accounted `deltaAmountChanges`/UTXO output — independent of whatever `erc20TokenAddresses` the caller declared.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), register `MainEVMCircuitMin` verifier for the relevant `verifierId` (or mock `IVerifier.verifyProof` to return `true` for the test, since the circuit is unconstrained anyway).
2. Fund `EmporiumUpgradeable` directly with `100e18` of mock ERC20 token `X` (simulate leftover/in-flight balance from "any source").
3. Craft `CircomData` with: `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = EmporiumUpgradeable address`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: X, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer, (attacker, 100e18))})], maxFee:0, deadline: type(uint256).max}))`, matching `calldataHash`.
4. Call `Hinkal.transact` with a proof accepted by the (mocked/registered) `MainEVMCircuitMin` verifier.
5. Assert: `X.balanceOf(EmporiumUpgradeable) == 0`, `X.balanceOf(attacker) == 100e18`, and separately assert `utxoSet.length == 0` (no `outCommitments` inserted into the Merkle tree/roots mapping) — proving value left custody with zero leaves, zero nullifiers, and zero `amountChanges` entries referencing token X.
