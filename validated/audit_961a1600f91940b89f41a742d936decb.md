### Title
Payload-named venue pool addresses are unallowlisted: a malicious route puts attacker code on the call stack below the caller's authorization and drains the caller's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary

The OpenRefine class — an attacker-supplied string that toggles loading and executing arbitrary external code — maps onto the swap-aggregator's route payload: every hop's `pool` (and the token addresses) come from the caller-supplied `assets` registry, with no allowlist. `execute_strategy` decodes the route, pulls `token_in` under `sender.require_auth()`, then `dispatch_hop` invokes whatever contract address the payload names as the "pool". That contract runs arbitrary code inside the transaction; any `token.transfer(sender, attacker, x)` it issues is recorded by the host as a child of the sender's own authorization entry, and executes if the sender signs the simulated auth tree — exactly like `enable_load_extension=true` turning a benign input into arbitrary code execution.

### Finding Description

- `Router::execute_strategy(sender, total_in, swap_xdr)` decodes a `StrategyPayload` whose `assets` registry supplies every hop's `pool`, `token_in`, and `token_out`. Decoding checks format and index bounds only (`Program::decode`); there is no venue/pool allowlist — documented: "The router calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:154-156`).
- `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs:23-59` builds a `HopContext` directly from `hop.pool` and calls the venue adapter, which invokes that address. The measured-delta checks (`received > 0`, `spent == amount_in`) bound only the router's own balances.
- While that foreign code runs, `sender.require_auth()` from `execute_strategy` is still the active authorization: Soroban recording mode attaches any `from == sender` transfer the rogue pool makes as a sub-invocation of the sender's root entry. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves this end-to-end through the controller's `swap_collateral`: a route through `RogueHopPool` steals Alice's entire unlisted-token wallet balance while paying a fair swap output, so `SlippageExceeded`, `ZeroOutput`, and the final risk gate all pass.
- The same exposure exists on the direct `execute_strategy` path and on every controller strategy verb that forwards a route (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position` callbacks), since the controller authorizes only one exact input transfer and performs no venue check of its own (`contracts/controller/src/strategies/swap.rs`).

### Impact Explanation

Theft of user funds beyond the routed amount: an attacker who supplies the route (malicious quote server, compromised frontend, or a route passed through a controller strategy) can drain any token balance of the executing account, not just `total_in`. Neither the payload `min_out` nor the controller's post-swap solvency check bounds the loss, because the stolen transfer is orthogonal to the measured swap legs.

### Likelihood Explanation

Exploitation requires the victim to sign an authorization tree containing the rogue `transfer` child. Simulation records it honestly, so a wallet/client that decodes the tree can refuse it — the threat model explicitly pushes this duty to the client (`docs/explanation/threat-model.md:156-165`). In practice most signing flows display only the top-level invocation, and the attack needs no privileged access, no oracle manipulation, and works against any account calling route-bearing entrypoints. Medium likelihood, high per-victim impact → High overall.

### Recommendation

- Enforce a governance-managed allowlist of pool addresses per venue (or per token pair) in the router's `storage`, checked in `dispatch_hop` before invoking `hop.pool`.
- As defense in depth, reject routes whose `assets` registry contains addresses that are neither known pool contracts nor whitelisted tokens.
- Until an allowlist exists, the router could sandbox hop invocations so that no `require_auth`-bearing call from `sender` can be attributed below the router's own frame.

### Proof of Concept

See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`: `route_through_pool_stealing(WALLET_BALANCE)` builds a payload naming an attacker `RogueHopPool`; `swap_collateral` succeeds, the recorded auth tree contains the rogue `transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's entry, and Alice's wallet balance goes to zero while the swap output and risk checks pass. On the real router the same shape is reached via `execute_strategy(sender, total_in, swap_xdr)` where `swap_xdr` names the attacker's contract in a hop's `pool` slot of the `assets` registry.
