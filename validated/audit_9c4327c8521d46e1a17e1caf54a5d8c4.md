### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is taken from unauthenticated HTTP headers that are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values that are read directly from HTTP headers — none of which are included in the HMAC-signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never mixed into the signed string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (i.e., the raw body) against the secret — it never checks the headers: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` is trusted as the tenant identifier and handed to the app's handler via `WebhookMetadata`, and `request.topic` is trusted to select which handler runs: [5](#0-4) 

Because Shopify signs webhooks using the app's single `client_secret` (the same secret is used for every shop that installs the app), an attacker who controls their own shop that has the app installed will legitimately receive a genuinely-HMAC-valid webhook (valid raw body + valid signature) from Shopify for their own store. Since the signature covers only the raw body and not the `shop-domain`/`topic` headers, that attacker can replay this genuine request to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to impersonate a victim shop. `Registry.process` will accept it (HMAC over raw body is still valid) and invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, breaking the identity binding: `shop-header-received == shop-value-acted-on` should equal `shop-covered-by-hmac`, but here `shop-covered-by-hmac` doesn't exist at all.

### Impact Explanation
This is a cross-tenant identity confusion: the shop identity that host applications rely on to route data (e.g., updating the correct merchant's local records, triggering `shop/redact` or `customers/redact` GDPR flows, or any app logic keyed by `WebhookMetadata#shop`) is not covered by the cryptographic authentication this gem performs. An attacker can cause the receiving application to process attacker-controlled body content while asserting it belongs to a different (victim) tenant, since `shop` is not bound to the signature.

### Likelihood Explanation
An attacker only needs to install the app on their own shop (an unprivileged, self-service action available to anyone) to obtain genuinely-signed webhook deliveries, and then craft a raw HTTP request replaying that body while forging the `shop-domain`/`topic` headers to the target endpoint. No access token, secret, or privileged account for the victim is required — only network reachability to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them, e.g. Shopify's own signed values), or at minimum document/enforce that `to_signable_string` must incorporate all header-derived fields the gem exposes as trusted, so that any tampering with those headers invalidates the signature.

### Proof of Concept
1. Attacker creates a development/trial shop and installs the target app, receiving events such as `orders/create` webhooks with a valid `X-Shopify-Hmac-Sha256` computed by Shopify using the app's `client_secret`.
2. Attacker captures one such raw request (`raw_body` + valid `hmac-sha256` header).
3. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret: [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-supplied data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
