### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then hands the handler a `shop` value read from an **unsigned** header. The identity binding that should hold — "the shop that was cryptographically authenticated == the shop the handler acts on" — is broken, because the signature never covers the shop field that the handler is given.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, and if valid, immediately builds a `WebhookMetadata` object using the unauthenticated `request.shop` header value and passes it to the app's handler as the tenant identity: [3](#0-2) 

No comparison is made between `request.shop` and any value that is actually bound to the HMAC. `Utils::HmacValidator.validate` only recomputes `OpenSSL::HMAC.hexdigest(sha256, secret, signable_string)` where `signable_string == raw_body`: [4](#0-3) 

The identity equality that should hold is:
```
shop authenticated by HMAC == shop acted on by the handler
```
Because the HMAC is computed over `raw_body` alone, this reduces to `∅ == request.shop`, i.e. the shop the handler is told to act on is never verified at all.

### Impact Explanation
Because Shopify's HMAC-SHA256 webhook signature is computed by Shopify over the request body using the app's own `api_secret_key`, any legitimate installer of the app (an ordinary, unprivileged merchant who installs the app on their own free/dev store) will receive genuinely signed `(body, hmac)` pairs for their own shop's webhooks. Since the shop identity is carried in a separate, unsigned header (`x-shopify-shop-domain` / `shopify-shop-domain`), that attacker can replay a captured, validly-signed body to the target application's shared webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept the HMAC (it only checks the body) and dispatch the handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to process attacker-chosen webhook data under a victim tenant's identity. If the host app uses `WebhookMetadata#shop` to scope writes/reads (a common and expected pattern, since that's the only tenant field the gem exposes from the webhook), this results in cross-tenant data corruption/read — a Critical impact under this program's rubric (cross-tenant access), reachable entirely through the gem's own webhook processing API without needing the app's `api_secret_key`, an access token, or any privileged credentials.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on any Shopify store (including a free development store), which is available to any internet user, then triggering an event that generates the desired webhook topic/body. The only additional step is sending a crafted HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no cryptographic secret needs to be broken since that header sits entirely outside the signed content.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material that `HmacValidator` verifies, or require callers of `Registry.process` to independently verify that `request.shop` corresponds to a shop that has an active session/installation before invoking the handler. At minimum, update `Webhooks::Request#to_signable_string` (or the validation flow in `Registry.process`) to also authenticate the shop-domain header instead of trusting it verbatim from an unauthenticated header, and document clearly that `WebhookMetadata#shop` is not covered by the HMAC so host applications don't use it as a sole tenant key.

### Proof of Concept
1. As an ordinary internet user, register a free Shopify development store and install the target app (using its published app URL) — this is available to anyone, no privileged/internal access required.
2. Trigger a webhook event the app subscribes to (e.g. `orders/create`) on the attacker-controlled store. Shopify sends a POST to the app's webhook endpoint with a body `B` and header `X-Shopify-Hmac-SHA256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this HMAC is valid because it only covers `B`.
3. Capture `(B, H)` from the attacker's own store delivery (e.g., via a debugging proxy on their own infrastructure, or via the app's own webhook logs if exposed to them).
4. Send a new POST request directly to the app's public webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-SHA256: H`, but replace `X-Shopify-Shop-Domain` with the victim shop's domain (e.g. `victim-shop.myshopify.com`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` (`B`) and secret, matches `H`, and passes validation — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — causing the app to process attacker-supplied webhook content under the victim shop's tenant identity.
