### Title
Unbounded memory/CPU consumption in `TrieViewer::view_state` via unpaginated `include_proof=true` requests - (File: runtime/runtime/src/state_viewer/mod.rs)

### Summary
`view_state` builds a `TrieIterator` and, when `include_proof` is requested, calls `iter.remember_visited_nodes(true)`, causing every visited trie node to be recorded into memory. When the request is not paginated, `item_cap`/`byte_cap` are set to `None`, so the only limit on iteration size is the amount of state actually stored under the target account's storage prefix, which an attacker fully controls by writing many/large keys through ordinary contract calls.

### Finding Description
In `TrieViewer::view_state`, pagination controls are used to bound the number of items and bytes returned, but this bound is only applied `if paginated`; for `include_proof=true` full (non-paginated) requests, `(item_cap, byte_cap)` become `(None, None)` [1](#0-0) . When `include_proof` is set, the iterator is switched into proof-recording mode via `iter.remember_visited_nodes(true)` [2](#0-1) , which accumulates every trie node touched while walking the account's full storage subtree into an in-memory buffer with no size limit.

This code path is reachable from the public JSON-RPC `query` API (`view_state` request type) through `chain/jsonrpc/src/api/view_state.rs` → `view_client_actor.rs` → `chain/chain/src/runtime/mod.rs` → `TrieViewer::view_state`, i.e. any unauthenticated RPC caller can request a full, proof-included state dump for an arbitrary account without submitting any signed transaction or paying any gas. Because state under an account (contract storage) can be grown arbitrarily by that account's owner through ordinary, gas-metered contract calls, an attacker can (1) pay once to grow a large/deeply nested storage trie under their own account, then (2) repeatedly issue free `view_state(include_proof=true)` RPC calls with no pagination to force the serving node to walk and buffer the entire subtree's proof nodes in memory on every call. Unlike the gas-metered `TrieRecorder`/storage-proof accounting enforced during real chunk application (which caps witness/proof size per protocol limits), this view-only code path performs no such capping, gas charging, or size ceiling.

### Impact Explanation
This is a resource-exhaustion / availability issue against the specific node serving RPC `view_state` queries (memory spikes and CPU time proportional to attacker-controlled state size, repeatable at near-zero cost per query). It matches the "node panic or unbounded resource use" bounty class, but only in the "unauthenticated resource use" sense — it does not affect chunk production, consensus, balances, or metering correctness, because `view_state` is a read-only, non-consensus RPC path entirely separate from the gas-metered execution/state-transition function; it can degrade or crash the specific view/RPC-serving node/process handling the query, not the chain itself.

### Likelihood Explanation
Feasible and repeatable: any account holder can grow account storage via normal contract calls (paying standard storage/gas cost once), then send unlimited free `view_state` RPC queries with `include_proof: true` and no pagination parameters against public RPC endpoints. No special privilege, validator access, or node compromise is required — only ordinary transactions plus public RPC access.

### Recommendation
Enforce the same `item_cap`/`byte_cap` (or an equivalent maximum node/byte limit for the recorded proof) unconditionally in `TrieViewer::view_state`, regardless of whether the request is paginated, when `include_proof` is set; alternatively, disable/limit `remember_visited_nodes` accumulation size and return an error or require pagination once a hard cap on visited nodes/bytes is exceeded.

### Proof of Concept
Add a test in `integration-tests/src/tests/runtime/state_viewer.rs` that:
1. Deploys a contract to a test account and writes N large key/value storage entries (e.g., increasing N across test parameters: 1k, 10k, 100k entries or deeply nested key prefixes).
2. Calls `TrieViewer::view_state` with `include_proof: true` and no pagination (`prefix: None`, unpaginated variant).
3. Measures peak memory (e.g., via `jemalloc`/`dhat` allocator stats) and wall-clock time of the call.
4. Asserts that memory/time grows roughly linearly and unbounded with N, with no cap applied — contrasted with a second test invoking the paginated variant showing bounded memory/time regardless of N, and with the gas-metered witness/proof recording path used in chunk application (`ApplyState` / `TrieRecorder`) which has an explicit size limit.
