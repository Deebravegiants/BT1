### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw JSON body, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unsigned HTTP headers when building the `WebhookMetadata` object that is handed to the app's handler. Because these tenant-identifying fields are never covered by the HMAC, an attacker who can obtain any single valid `(body, hmac)` pair for a webhook (trivially available for their own store's events) can replay that pair to the app's public webhook endpoint while freely rewriting the `shop-domain` and `topic` headers, causing the app to process attacker-controlled data as if it originated from an arbitrary victim shop and topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed separately from headers and are not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely over `to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and, once it passes, unconditionally forwards the unauthenticated `request.shop` and `request.topic` header values into `WebhookMetadata`, which is passed directly to the app's handler: [4](#0-3) 

The break in identity binding is: `shop-header-verified-by-HMAC` (false — never checked) vs. `shop-header-acted-on-by-handler` (true — used directly as the tenant identifier). The gem's own documentation instructs handlers to trust `data.shop` as the tenant key (e.g. `shop_domain: data.shop`) without any additional verification, since the gem's `process` method is documented as verifying "the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
Any internet-reachable attacker who has one legitimate `(body, hmac)` pair — trivially obtainable by installing the app on their own store and triggering any webhook event — can forge requests to the app's public webhook endpoint with the `shop-domain` header set to an arbitrary victim shop and the `topic` header set to any registered topic, while keeping the attacker's own valid body/HMAC. `process` accepts this as authentic (since only the body is checked) and the handler receives data falsely attributed to the victim shop/topic. Depending on the host app's use of `data.shop` (e.g., keying database writes, triggering order/customer sync, billing/inventory actions), this enables cross-tenant data injection and confusion — an app processing attacker-chosen payloads under another merchant's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. No privileged credentials, access tokens, or the app's `client_secret` are required — the webhook endpoint is a normal public HTTP route, and the attacker only needs to be able to trigger a webhook for their own store (a normal capability of installing any public app) to obtain a valid `(body, hmac)` pair, then replay it with modified headers.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed content that `HmacValidator` checks, or otherwise cryptographically bind them to the verified body before constructing `WebhookMetadata`. At minimum, `Registry.process` should re-derive/validate `shop` against an authoritative source (e.g., the session/shop the webhook was registered for) rather than trusting the raw header value once body HMAC succeeds.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the legitimate request body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify over `B` using the app's `client_secret`).
2. Attacker sends a POST directly to the app's registered webhook path with:
   - body: `B`
   - header `x-shopify-hmac-sha256`: `H`
   - header `x-shopify-shop-domain`: `victim-shop.myshopify.com`
   - header `x-shopify-topic`: any topic the app has registered a handler for
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B) == H` — this passes because `to_signable_string` never includes the headers: [1](#0-0) 
4. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the victim shop never sent this webhook: [7](#0-6)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
