### Title
Webhook shop-domain header is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop-domain` header — which `Registry.process` later hands to the app's webhook handler as the tenant identifier — is never part of the signed content, so it can be freely rewritten by anyone who possesses one valid `(body, hmac)` pair for the shared app secret.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header and `Request#shop` reads the `shop-domain` header independently: [1](#0-0) 

The value that is actually HMAC-verified is only the raw body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` recompute the signature purely from `to_signable_string` (the body) and the app's single, shared `Context.api_secret_key` — the same secret used for every shop that installs the app: [3](#0-2) 

Once validation passes, `Registry.process` trusts `request.shop` as the tenant identity and forwards it, unchecked, to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop that produced a valid HMAC == shop attributed to the processed event`

Because `to_signable_string` never includes the shop-domain header, this equality does not hold. Any shop that has legitimately installed the app receives real webhooks — i.e., valid `(raw_body, hmac)` pairs signed with the app's shared `api_secret_key`. That merchant (an unprivileged, non-victim tenant) can resend that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never checked the header, and `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain — a cross-tenant identity spoof.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: the party proven to hold a valid signature (a shop that installed the app) is not the same as the shop the event is subsequently attributed to inside the host application. Any app logic keyed off `WebhookMetadata#shop` (data updates, GDPR/compliance actions, cache invalidation, order processing, etc.) can be triggered under a forged tenant identity — classified as cross-tenant access, a Critical-tier impact per the accepted categories.

### Likelihood Explanation
High. The only prerequisite is that the attacker legitimately installs the app on any shop (a normal, unprivileged action) to obtain one valid `(body, hmac)` pair, then replays it with a modified `shop-domain` header — no access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Bind the shop identity into the verified signature material, or independently verify the `shop-domain` header against a trusted record (e.g., the shop associated with the currently active/looked-up session) instead of trusting the raw header value once HMAC-over-body succeeds. At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate/cross-check `shop`, `topic`, and `webhook_id` so that these fields cannot be swapped independently of the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` calls `to_signable_string` (→ `B`) and confirms `H` matches — validation passes.
4. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler as if the event genuinely originated from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
