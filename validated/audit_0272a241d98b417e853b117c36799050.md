### Title
Webhook shop-domain header is unauthenticated and not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating the HMAC of the *raw body only*, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers and forwards them to the app's handler as the tenant identity for that webhook.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac` header value: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are all pulled straight from HTTP headers and are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` object dispatched to the app's handler, with no binding between the verified body/HMAC and the claimed shop: [4](#0-3) 

The identity binding that should hold is: `shop header == shop whose secret produced the HMAC`. Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that installs the app, any actor who can obtain one genuine `(raw_body, hmac)` pair from Shopify — for example by triggering a webhook-eligible event on their own store that has the app installed — possesses a value pair that will pass `HmacValidator.validate` regardless of which shop's domain is later placed in the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header. The header is never checked against anything derived from the HMAC/secret, so `request.shop` can be set to any victim tenant's domain while the body remains attacker-supplied.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide via `Registry.process`: an app relying on `WebhookMetadata#shop` to select the tenant/session context for otherwise-legitimately-HMAC-verified data would process attacker-controlled payload content under a victim shop's identity — a cross-tenant integrity issue in multi-tenant apps built on this gem's documented webhook API.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop already installed on the app (any address able to install the app, unprivileged with respect to other tenants), (2) the ability to trigger an event that fires a webhook with attacker-influenced body content, and (3) the ability to POST an HTTP request to the app's public webhook endpoint with a forged shop-domain header, all reachable by an ordinary internet/merchant actor without needing the app's `client_secret`, an access token, or TLS interception.

### Recommendation
Bind the shop identity to the verified payload before trusting it — e.g., include the shop domain in the signable bytes used for HMAC verification, or require the app to independently confirm (e.g., against a known/installed-shop list) that the `shop` header matches an expected value for the endpoint/session context, rather than trusting the header purely because the body's HMAC validated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker triggers an event so Shopify sends a real webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
3. Attacker replays `POST` to the same endpoint with the same body `B` and hmac `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` passes (only `B`/`H` are checked, per `to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the app to act on attacker-chosen data as if it belonged to the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
