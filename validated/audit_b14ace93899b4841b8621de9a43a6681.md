Audit Report

## Title
Missing `return` After Failed Email-Claim Extraction Lets OIDC Token Exchange Silently Continue and Issue an Authenticated Session - ([File: core/sessions/oidcauth/oidc.go])

## Summary
In `handleTokenExchange`, the check `email, ok := claims["email"].(string)` writes an HTTP 500 error body on failure but does not `return`, unlike every other error branch in the same function. Execution falls through to role mapping, DB session insertion, audit logging, and a final `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`, meaning the client ends up with a valid, cookie-backed authenticated session (with `user_email = ""`) despite the server detecting and logging a claim-validation failure.

## Finding Description
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` extracts OIDC claims after code exchange and ID-token verification. At lines 226-230, the `email` claim type assertion is checked, and on failure the handler logs and writes `c.String(http.StatusInternalServerError, "Failed to get email from claims")` but omits the `return` statement present in all six other error branches of this function (lines 166-171, 177-182, 189-195, 200-203, 208-211, 215-218, 241-244). As a result, execution continues to `IDClaimsToUserRole`, inserts a row into `oidc_sessions` with `strings.ToLower(email)` (empty string), sets the session cookie via `ginSession.Save()`, and finally emits `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`. Gin permits multiple writes to the response (only warning on “superfluous” header writes), so the last write (`200 OK` with a valid session cookie) is what the client observes. The same missing-`return` pattern also exists after the DB insert error at lines 257-260, compounding the problem by handing out a session cookie even when persistence to `oidc_sessions` failed. [1](#0-0) [2](#0-1) 

## Impact Explanation
This is a genuine logic/control-flow bug within the OIDC login callback that silently mints an authenticated Chainlink session tied to an empty-string email whenever an IdP omits or misformats the `email` claim, or when the session DB insert fails. Because `FindUser`/session lookups elsewhere key off `user_email`, all such degenerate sessions collapse onto the empty-string identity, risking cross-session identity confusion, and the role attached is still derived from `IDClaimsToUserRole`, so a session with an elevated (admin/edit) role could be issued without a properly bound, verifiable identity. This maps to an in-scope "node API authentication/role bypass"-style impact since it produces a functioning authenticated session the caller (and a triager) can verify via a subsequent authenticated request. [3](#0-2) 

## Likelihood Explanation
The vulnerable path is the primary, unauthenticated OIDC login callback (`handleTokenExchange`), reachable by anyone who can complete a normal OIDC redirect and present a valid `code`/`state` pair obtained from a legitimately initiated login flow — no privileged role or credential is needed beyond going through the standard login UI. Triggering the missing-claim branch specifically depends on the configured/compromised IdP's claim response (e.g., IdP scope configuration omitting `email`, or returning it as null/non-string), which is a realistic configuration/response edge case rather than a contrived scenario, and it is deterministically reproducible each time such a response occurs.

## Recommendation
Add `return` immediately after the error response write in the `email` claim check:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Also add `return` after the DB insert error at lines 257-260 so a failed `oidc_sessions` insert never proceeds to `ginSession.Save()` and the `200 OK` response.

## Proof of Concept
1. Stand up or configure a test OIDC provider whose token/UserInfo response omits the `email` claim (or returns it as a non-string/null), while including whatever claim `oi.config.ClaimName()` expects so `ExtractIDClaimValues` succeeds.
2. As an unauthenticated client, perform the standard login redirect (`GET` to the login endpoint) to obtain a valid `state`, complete the IdP flow, and call the token-exchange endpoint (backing `handleTokenExchange`) with the resulting `code` and matching `state`.
3. Observe that the server logs "Failed to get email from claims" and writes an interim 500 body, but the actual HTTP response returned to the client is `200 OK` with `{"success": true}` and a `Set-Cookie` session header.
4. Use the returned session cookie to call an authenticated endpoint and confirm it succeeds, proving a valid authenticated session was issued despite the detected claim failure.
5. (Optional) A Go test in `core/sessions/oidcauth/oidc_test.go` can directly invoke `handleTokenExchange` with a mocked `claims` map lacking `email`, and assert that the final recorded response is `200 OK`/`Success: true` and/or that `ginSession.Save()` was called, confirming the fall-through.
