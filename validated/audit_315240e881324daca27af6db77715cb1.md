### Title
Local acceptance of `user_centric_signup` bypasses backend duplicate/fraud verification, allowing a signup to be recorded as successful without the actual server-side identity check that the design otherwise requires - (File: `src/plans/mod.rs`)

### Summary
In `MasterPlan::do_signup`, the enrollment "success" bookkeeping is split into two paths: a normal path that calls the backend `enroll_user::Plan` (which performs `signup_post`/`signup_poll`, the actual server-side duplicate/fraud verification), and a `user_centric_signup` path that marks the signup as `Success`/`Error` purely from the *local* `signup_reason`, never invoking the backend verification step. This mirrors the reported bug class: an accounting/status update (`debug_report.enrollment_status(...)`, `signup_successful()` counters, and the already-uploaded PCP tiers) is committed as if the "real" side-effect (backend-confirmed, duplicate-checked enrollment) had happened, when in fact that side-effect was skipped.

### Finding Description
`do_signup()` computes `signup_reason` from the **local** biometric pipeline result and local fraud detection: [1](#0-0) 

Note also that in this build all fraud checks have been deleted (`N_FRAUD_CHECKS = 0`), so `detect_fraud()` always resolves to "no fraud": [2](#0-1) [3](#0-2) 

Personal Custody Package (biometric credential bundle) upload to the backend already happens unconditionally once `signup_reason` is computed, regardless of which enrollment path is later taken: [4](#0-3) 

The actual enrollment/success decision then branches: [5](#0-4) 

- In the normal branch, `enroll_user::Plan::run` submits the signup to the backend via `signup_post::request` and polls `signup_poll::request` until the backend explicitly reports `Completed`/`success`. The code comments make clear this backend step is what actually catches "Backend duplicates," "Backend inflight matches," and "Backend detected fraud": [6](#0-5) 

- In the `user_centric_signup` branch, none of this backend confirmation happens. `success` is derived solely from whether the *local* `signup_reason == SignupReason::Normal`: [7](#0-6) 

This is the same root-cause pattern as the referenced report: a state that is supposed to reflect a verified, server-confirmed action (`pendingTokenWithdrawals` credited only after `tokenTransferPlatformLogic()` actually moved funds; here, `enrollment_status`/`signup_successful()` set only after the backend's `signup_post`/`signup_poll` actually confirmed non-duplicate enrollment) is instead set from a locally-computed value without the corresponding real side effect (the backend duplicate/fraud check) ever executing.

### Impact Explanation
Because the backend's `signup_post`/`signup_poll` step is the mechanism that performs cross-signup duplicate detection ("Backend duplicates," "Backend inflight matches") and backend-side fraud checks, skipping it for `user_centric_signup` means the Orb can locally record a signup as `Success` (and has already uploaded the full PCP tiers to the backend as if enrollment were confirmed) without the backend ever validating that the same biometric identity has not already been enrolled elsewhere. Combined with the fact that Orb-local fraud detection is entirely disabled in this build (`N_FRAUD_CHECKS = 0`), the only remaining defense against duplicate/misattributed signups for `user_centric_signup` flows is removed, creating a path for a cross-signup state bleed / misattributed signup: a device or session could be marked as "signup successful" for a user identity that was never confirmed unique by the backend.

### Likelihood Explanation
`user_centric_signup` is a boolean returned by the backend as part of `authenticated_app_data.user_centric_signup` and is verified against a QR-embedded hash before use: [8](#0-7) [9](#0-8) 
Because this flag flows from the backend/app response, it is not directly forgeable by an unprivileged orb operator, but it is the mechanism intentionally designed to select the "app-centric" signup path in place of the backend-confirmed `enroll_user::Plan` path. Whenever this flag is exercised (per its design purpose), the Orb never validates the signup against the backend's duplicate/fraud pipeline — this is a deterministic code path, not a race condition or timing bug, so likelihood is high whenever `user_centric_signup=true` and `ignore_user_centric_signups=false` (the default expected configuration for this feature).

### Recommendation
For `user_centric_signup` flows, still submit the signup outcome to the backend (or an equivalent authoritative check) before recording `enrollment_status`/`signup_successful()` and before/instead of unconditionally uploading full PCP tiers, so that duplicate/fraud verification is not bypassed. At minimum, ensure the local `signup_reason == SignupReason::Normal` shortcut in `src/plans/mod.rs:639-645` cannot substitute for the backend's `signup_post`/`signup_poll` confirmation that the referenced comments in `src/plans/enroll_user.rs:162-168` describe as authoritative for detecting duplicates and fraud.

### Proof of Concept
Not applicable in the traditional sense (no exploit script), since the flow requires the backend to actually assert `user_centric_signup = true`. The concrete code trace demonstrating the flaw:
1. `do_signup()` computes `signup_reason` purely from local pipeline/fraud state: [1](#0-0) 
2. PCP tiers are uploaded to the backend unconditionally, before any success determination: [10](#0-9) 
3. If `user_centric_signup` is true, `success` and `enrollment_status` are derived from the local `signup_reason` alone, bypassing `enroll_user::Plan::run` (the only code path that calls `signup_post`/`signup_poll` to obtain backend duplicate/fraud confirmation): [11](#0-10) 
4. `report_signup_reason` then records `debug_report.signup_successful()` based on this unverified local `success` value: [12](#0-11)

            tracing::info!("User enrollment failed due to a failure in the pipeline");
