### Title
Redeploying an IntentGateway instance via `NewDeployment` permanently freezes escrow for orders already filled through the old address - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._authenticate` verifies an incoming `RedeemEscrow`/`RefundEscrow` message by reading the *live* `_instances` mapping (`_instance(request.source)`) at delivery time, rather than the gateway address that was actually authoritative when the corresponding fill (or cancellation) happened on the counterparty chain. Because `_instances` is mutable via a legitimate, timelock/governance-gated `NewDeployment` message that can land at any time, a solver who filled a cross-chain order against the gateway address that was live *at fill time* can have their `RedeemEscrow` message permanently rejected if governance rotates the destination chain's registered instance before the message is relayed — exactly the same "live mutable slot read at resolution instead of the value captured at the time of the earlier action" defect described in the external ArmadaGovernor report.

### Finding Description
`_instances` is a single mapping keyed by `keccak256(stateMachineId)` that is written only by `_addDeployment`, itself only reachable from `onAccept`'s `NewDeployment` branch, gated to messages whose source is Hyperbridge itself: [1](#0-0) 

The escrow-release path binds an outgoing cross-chain message's destination `to` address, and the corresponding inbound authentication check, to whatever the *current* value of this mapping is at each call site:

- At fill time, `_fillCrossChain` posts the `RedeemEscrow` body to `_instance(order.source)` — this is a read of the live mapping at the moment of the fill. [2](#0-1) [3](#0-2) 

- At delivery time on the *destination* side of that message (the order's source chain), `onAccept` authenticates the incoming message by re-reading `_instance(request.source)` — a second, independent read of the same live mapping, taken later in time: [4](#0-3) [5](#0-4) 

The `_instance(request.source)` check in `_authenticate` compares `request.from` (the sender module address embedded by the *destination chain's* gateway when it dispatched `RedeemEscrow`/`RefundEscrow`) against whatever `_instances[keccak256(order.destination)]` holds *now*, on the source chain. Nothing binds that comparison to the specific gateway instance address that was actually used when the order was filled. If a legitimate `NewDeployment` message rotates the destination chain's registered instance (e.g. a redeploy/migration of the destination gateway) between the moment a solver fills the order against the old address and the moment the resulting `RedeemEscrow` message is relayed back and processed by `onAccept`, `_authenticate` will reject the message: `request.from` (old gateway) no longer equals `_instance(request.source)` (new gateway). The message keeps failing every retry (the host records it as undelivered and it can be resubmitted, but the check is deterministic and always fails once the mapping has moved on), permanently stranding the solver's escrowed input tokens — the solver has already paid out the order's outputs on the destination chain and can never recover the corresponding inputs.

This is structurally identical to the reported ArmadaGovernor defect: an accountability/authorization decision that should be pinned to the state that existed when an earlier, already-finalized action took place is instead re-derived from a mutable slot that a separate, legitimate governance action can move in between.

### Impact Explanation
A solver's escrowed input tokens become permanently unrecoverable through the intended protocol path: `_filled[commitment]` is already set (so the order can never be filled or refunded via the normal cancellation route), and the only remaining path to release escrow — the `RedeemEscrow` message — is unconditionally rejected by `_authenticate` once the source-chain's registered instance for the destination diverges from the address embedded in the message. This is a permanent freezing of user/solver funds triggered purely by ordinary, honest gateway redeployment/migration governance action landing during the delivery window of an in-flight fill — no malicious actor is required.

### Likelihood Explanation
`NewDeployment` is an expected, routine governance operation (redeploying/migrating an `IntentGateway` instance on a chain, or onboarding replacement infrastructure) and is documented as part of normal `onAccept` handling. Any window between a solver's on-chain fill (`_fillCrossChain`) and the relayer's delivery of the resulting `RedeemEscrow` message — which can span multiple blocks/finality delays inherent to Hyperbridge's cross-chain proof pipeline — is sufficient for a legitimate redeployment to race the escrow-release message. No attacker coordination is needed; this can occur purely from ordinary operational timing.

### Recommendation
Do not authenticate the incoming `RedeemEscrow`/`RefundEscrow` message against the live `_instances` mapping. Instead, bind authentication to the destination gateway address that was actually registered at the time the order was created/filled — e.g., record the resolved instance address in the order commitment context (as is already done for other order data), and have `_authenticate` accept either the currently registered instance *or* the instance address that was valid when the corresponding fill/cancel occurred, or maintain an allow-list of historical valid gateway addresses per chain that is only pruned after in-flight orders against the old address have settled.

### Proof of Concept
1. Register `_instances[keccak256(chainB)] = gatewayB1` via a `NewDeployment` message from Hyperbridge (`onAccept`), as in `evm/tests/foundry/IntentGatewayV2Test.sol` `testOnAcceptNewDeployment`.
2. User places a cross-chain order on chain A with `destination = chainB`.
3. Solver fills the order on chain B through `gatewayB1` (`fillOrder` → `_fillCrossChain`), which dispatches `RedeemEscrow` with `from = gatewayB1`.
4. Before the message is relayed and processed, governance issues a second legitimate `NewDeployment` for `chainB`, updating `_instances[keccak256(chainB)] = gatewayB2` on chain A (e.g. a gateway migration).
5. The relayer delivers the `RedeemEscrow` message to chain A's `onAccept`. `_authenticate` computes `_instance(order.source... /* chainB */)` = `gatewayB2`, compares against `request.from = gatewayB1`, and reverts with `Unauthorized`.
6. Every resubmission of the same message reverts identically since `_instances[chainB]` remains `gatewayB2`. The solver's escrowed input tokens on chain A are permanently stuck; the solver already delivered the outputs on chain B and has no recourse.

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
