### Title
`Pool::recapitalize` pays out an unearned refund without measuring the injected cash — unprivileged caller can drain pool custody (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The kernel bug class is a missing reference drop on error/refund paths: a resource is acquired, and the release path runs against a value that was never actually held. The exact analog lives in the pool's recapitalization leg. `recapitalize::accounting` books `applied = min(amount, backing_shortfall)` into the cash book and computes `refund = amount - applied`, then `apply` calls `cache.transfer_out(&payer, outcome.refund)` — paying real tokens out of pool custody — purely from the *declared* `amount`. The code comment admits the funding assumption: "The controller transfers `amount` into the pool before this call" (contracts/pool/src/ops/recapitalize.rs:4). The pool never measures `token.balance(pool)` before/after, so a direct call with no prior transfer receives a refund for money that was never deposited.

### Finding Description
In `apply`/`accounting` (contracts/pool/src/ops/recapitalize.rs:26-67):

1. `applied = amount.min(guards::backing_shortfall(&cache))` — capped at the book's measured shortfall, which is `0` on any healthy market.
2. `refund = amount - applied`.
3. `cache.credit_cash(applied)` and `commit()` update the accounting book.
4. `outcome.cache.transfer_out(&payer, outcome.refund)` sends `refund` tokens to `payer` from the pool's SAC balance.

There is no `balance_delta` measurement and no check that `payer` (or anyone) transferred `amount` in. The pool trusts a caller-supplied `amount` as if it were custody. The repo's own test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3408-3433) demonstrates the primitive end-to-end: with a solvent book, a direct `pool.recapitalize(hub, payer, token.balance(pool))` call reduces `token.balance(&pool)` to `0` while `cash` still claims the full supplier deposit.

Two consequences compose:

- **Direct theft leg**: `refund` is paid out of real custody for an unfunded `amount`. With shortfall `s < balance`, `amount = balance` yields `refund = balance - s` paid to the caller and `applied = s` credited to cash with zero backing — a double leak: tokens leave *and* the book overstates custody.
- **Phantom-solvency leg**: after the drain, `cash` still reports the funded amount, so `require_reserves`/`PoolInsolvent` guards pass. Supplier `withdraw` calls clear the pool's own liquidity guards and then revert inside the SAC transfer (`BalanceError = 10`), per the same test's assertions — every later exit fails on custody the book claims exists.

The `repay` leg (contracts/pool/src/ops/repay.rs:32) has the same shape (`transfer_out(payer, overpayment)` trusting a pre-transfer), but repay is driven by the controller, which does measure the inbound transfer (`payments::transfer_amount_measured` in `apply_liquidation_repayments`, contracts/controller/src/positions/liquidation/apply.rs:58-65). `recapitalize` is documented as an *open* controller endpoint ("Measured backing injection; refund surplus", docs/reference/endpoints.md:40), and the pool-level leg accepts an arbitrary `payer`/`amount` pair — nothing in this file authenticates that tokens moved first.

### Impact Explanation
**Theft of user funds + protocol insolvency.** An unprivileged address calls the pool `recapitalize` entrypoint directly with `payer = self` and `amount = token.balance(pool)` (bounded by whatever `backing_shortfall` allows to be *credited* — the refund is uncapped relative to custody). The pool transfers `amount - min(amount, shortfall)` to the attacker out of supplier custody. On a solvent market (shortfall = 0) the attacker receives the entire `amount`; the only limit is the pool's token balance. Simultaneously, `credit_cash(applied)` on the unfunded portion poisons the book, so the market reports reserves it cannot pay — suppliers' withdrawals revert inside the token transfer. This satisfies theft of user funds, permanent freezing of remaining supplier funds, and pool insolvency.

### Likelihood Explanation
Single transaction, single unprivileged caller, no timing dependence: invoke `recapitalize(hub_asset, attacker, pool_balance)` on any listed market. No price oracle, governance action, or counterpart behavior is needed. The only prerequisite is that the pool entrypoint is reachable without controller gating — which the in-repo test exercises directly through the pool client. The attacker's cost is one contract invocation. Likelihood is high; the exploit is deterministic and repeatable across markets.

### Recommendation
Make the recap leg measured, like every other settlement path in the codebase:

- Snapshot `token.balance(pool)` inside `apply`, pull/transfer `amount` from `payer` into the pool within the same call (or verify the measured delta ≥ `applied`), and compute `refund = measured_received - applied` — never `declared - applied`.
- Alternatively, restrict the entrypoint to the controller and keep the controller's pre-transfer measured (`balance_delta_since` pattern as in `mint_and_forward`, contracts/controller/src/strategies/flash_position.rs:269-282), so the pool can assert custody grew by ≥ `applied` before committing `credit_cash`.
- Add a `require_reserves`-style custody check after `commit`: `token.balance(pool) >= cache.cash()`.

### Proof of Concept
The repository already contains the executable PoV — `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3408-3483):

```rust
// Supplier deposits 10_000_000_000; cash book == custody.
token_admin.mint(&t.pool, &deposit);
t.client().supply(&t.sup(0, deposit));

// Attacker: no transfer in. `payer` is an arbitrary generated address.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);   // custody drained to `payer`
assert!(t.state_snapshot().cash >= deposit); // book still claims funds

// Supplier exit passes the pool's liquidity guards, then fails in the SAC:
// Error::from_contract_error(10) — BalanceError, not InsufficientLiquidity.
let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
assert!(outcome.is_err());
```

Attack sequence on a live market: mint nothing, call `pool.recapitalize(hub_asset, attacker_addr, pool_token_balance)`; `accounting` computes `applied = min(amount, shortfall)`, `refund = amount - applied`, and `transfer_out` sends the refund from custody the attacker never funded. If `backing_shortfall > 0`, the unfunded `applied` portion additionally inflates `cash`, masking the drain from `get_reserves` until withdrawals hit the SAC.

One caveat worth noting: the diff between the pool-side trust assumption and the controller wrapper (which does transfer before calling) means the vulnerability hinges on the pool entrypoint being callable without an actual prior transfer — the test demonstrates it is, and the file contains no authorization or custody check of its own, but I did not trace `lib.rs` entrypoint gating in the remaining budget; if an outer guard restricts `recapitalize` to the controller, the exploitable surface reduces to the phantom-book/custody-mismatch half of the finding (still a solvency-accounting defect, reachable via any path that credits cash without measured custody).
