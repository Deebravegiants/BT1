### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and passed straight to the app's handler. This breaks the identity binding `shop authenticated == shop acted upon`: any actor who can obtain a validly-HMAC'd webhook body (e.g. from their own shop that has the app installed) can relabel it with a different `x-shopify-shop-domain` header and have it pass `HmacValidator.validate`, since headers are never part of the signed content.

### Finding Description
`Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the handler: [1](#0-0) 

The actual verification is: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

For webhooks, `to_signable_string` returns only the raw body — none of the Shopify headers are included in the signed material: [4](#0-3) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from those same unauthenticated headers and forwarded into `WebhookMetadata`, which the handler is expected to trust for tenant attribution: [5](#0-4) [6](#0-5) 

The gem's own documentation confirms `data.shop` is meant to be the trusted, verified shop identity that apps key their side effects on (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [7](#0-6) 

Because the `api_secret_key` used to compute the HMAC is shared across all shops that install a given app (it is the app's client secret, not a per-shop secret), any shop that has the app installed can capture a legitimately-signed webhook body+HMAC pair delivered to its own endpoint, then replay that identical body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's values. `HmacValidator.validate` will still succeed because it never inspects those headers, and the handler will process attacker-supplied body content under the identity of the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem's documented guarantee ("verify the request did indeed come from Shopify") is violated for the `shop` field specifically, since `shop` is never cryptographically bound to the payload. A host application that follows the documented pattern (using `data.shop` to select the tenant record/session to act on) can be made to apply attacker-controlled webhook data against another merchant's tenant context, meeting the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control (or install the app on) at least one shop so they can obtain a body/HMAC pair signed with the app's shared secret — no leaked credentials, TLS interception, or privileged account access is required beyond the normal unprivileged ability to install a public/embedded Shopify app. The replay itself is a trivial HTTP request with a modified header, since `HmacValidator` and `Request` never bind headers to the signature.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g. via a canonicalized string of headers + body) rather than relying solely on the raw body for verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - body `B`
3. Attacker captures `B` and its valid HMAC, then sends a new request to the same endpoint with:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-hmac-sha256: <same valid HMAC>`
   - body `B` (unchanged, since HMAC only covers the body)
4. `ShopifyAPI::Webhooks::Registry.process` → `Utils::HmacValidator.validate` succeeds (body unchanged, HMAC matches), and the handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the host app to process attacker-originated webhook content as if it originated from the victim tenant.         def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
