Confirmed: there's no refund handling anywhere in `EvmHost.sol` for excess ETH from `swapETHForExactTokens` — the swap sends any unused `msg.value` back to `address(this)` (the host) as native ETH with no code path returning it to the original caller, and this pattern is repeated across `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`.

### Title
Native-fee-payment dispatches (`dispatch`, `fundRequest`) swap through an unprotected Uniswap V2 pool, exposing callers to sandwich-attack value extraction - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` allow any unprivileged caller to pay the ISMP relayer fee in native token. When `msg.value > 0`, the host performs an on-chain swap via `IUniswapV2Router02.swapETHForExactTokens` to acquire the exact `feeToken` amount needed, using `msg.value` as the implicit `amountInMax` bound and `block.timestamp` as the deadline (i.e., no real deadline protection either).

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these three entry points executes `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` against the pool configured at `_hostParams.uniswapV2`. This is exactly the pattern the external report describes for `deposit()`/`withdraw()`: an unprivileged, price-agnostic AMM interaction with no spot-price bound, executed atomically in a single transaction that any MEV searcher can sandwich.

Concretely:
1. An attacker observes a pending `dispatch()`/`fundRequest()` call carrying `msg.value` in the mempool.
2. The attacker front-runs by buying `feeToken` (or selling WETH) into the same Uniswap V2 pool, pushing the WETH→feeToken price up.
3. The victim's transaction executes `swapETHForExactTokens`, and because the exact-output amount (`post.fee`/`get.fee`/`amount`) is fixed, the router now needs more ETH input to fill the same output at the manipulated price — consuming a larger fraction of (or reverting on) the victim's `msg.value`.
4. The attacker back-runs, selling the tokens/WETH back to restore price and pocketing the price-impact spread extracted from the victim's swap.

This is worse than the referenced Aera case in one respect: any ETH left over after the swap (the `amountInMax - amountIn` refund that `swapETHForExactTokens` normally returns to its immediate caller) is refunded to `address(this)` — i.e., to the `EvmHost` contract itself — not to the original `msg.sender` of `dispatch`/`fundRequest`. There is no `receive()`/refund bookkeeping visible in the contract for this leftover native balance, so a manipulated price does not just cost the victim a worse rate; any ETH beyond what the manipulated swap consumes is not returned to the caller at all.

### Impact Explanation
Any unprivileged party dispatching a cross-chain ISMP request or funding one and choosing to pay the relayer fee in native token is exposed to value extraction via sandwiching of the embedded Uniswap V2 swap, and additionally risks losing unrefunded native token to the host contract. This affects a widely reachable, permissionless code path (message dispatch is the core "message dispatcher" surface named in scope), and losses accrue per-transaction with no cap other than pool liquidity/attacker capital — consistent with a High-severity, concrete-theft finding of the kind described in the source report.

### Likelihood Explanation
Any address can call `dispatch()`/`fundRequest()` with `msg.value > 0` on a live EVM host, and any address can front-run/back-run against the configured Uniswap V2 pool. No special privilege, governance action, or malicious admin/node is required — only mempool visibility of the pending transaction, making this a standard, economically-rational MEV target whenever meaningful fee amounts are paid in native token.

### Recommendation
- Add a caller-supplied maximum acceptable input / minimum-out-equivalent parameter (slippage bound) to `dispatch`/`fundRequest`, separate from just capping at `msg.value`.
- Refund any unused native token to `_msgSender()` rather than leaving it credited to the host.
- Consider requiring `lastChangeBlock`-style same-block protection, or moving native-fee swaps off a manipulable spot-priced AMM (e.g., an oracle-informed rate or a two-step swap-then-dispatch flow), mirroring the mitigations Gauntlet/Spearbit recommended for Aera V1.

### Proof of Concept
1. Deploy `EvmHost` configured with a low-liquidity Uniswap V2 WETH/feeToken pool.
2. Victim calls `dispatch(DispatchPost{fee: F, ...})` with `msg.value = M` (M sized for the pool's current price).
3. Attacker front-runs: swaps WETH → feeToken (or feeToken → WETH depending on direction) to move the spot price against the victim.
4. Victim's transaction executes `swapETHForExactTokens(F, [WETH, feeToken], address(this), block.timestamp)`; the router now needs more ETH input than at the pre-attack price. If `M` was sized tightly, the call reverts (DoS) or consumes materially more of `M`, and any true excess is refunded to `address(this)`/`EvmHost`, not the victim.
5. Attacker back-runs to restore price, netting the price-impact profit extracted from the victim's forced trade. [1](#0-0)
