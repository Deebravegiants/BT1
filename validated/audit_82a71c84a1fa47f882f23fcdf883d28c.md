## Title
Unrestricted arbitrary call in EmporiumUpgradeable's unsigned stateless op path lets an unprivileged attacker drain any token EmporiumUpgradeable holds (e.g. via a stale approval or stray balance) without it being counted against `deltaAmountChanges` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

## Summary
When `EmporiumStack.signerAddress == address(0)`, `EmporiumUpgradeable.runAction` executes `op.endpoint.call{value: op.value}(op.callData)` with the endpoint and calldata fully controlled by the caller's `externalActionMetadata`, without any signature or endpoint allowlist check [1](#0-0) . Because the post-execution balance/invariant check only iterates over the attacker-supplied `circomData.erc20TokenAddresses` array, any token the attacker excludes from that array is completely invisible to the accounting, letting stray/approved balances leave the shared `EmporiumUpgradeable` contract with zero relation to `-deltaAmountChanges`.

## Finding Description
The invariant that should hold is: *tokens leaving EmporiumUpgradeable in a transaction == `-deltaAmountChanges` that Hinkal sent it that transaction*, enforced by:
```solidity
int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
if (deltaAmountChanges[i] < 0) { balanceChange -= deltaAmountChanges[i]; }
if (balanceChange < 0) revert BalanceChangeShouldBePositive();
UTXO memory utxoOut = handleOut(balanceChange, circomData, i);
``` [2](#0-1) 

This loop only runs over `circomData.erc20TokenAddresses`, which is entirely attacker-chosen (per the target's "Attacker controls" list). `verifyWallet` only enforces a signature when `stack.signerAddress != address(0)`; when it is zero it returns immediately after marking the nonce used, so no authorization is checked on `stack.ops` contents at all [3](#0-2) . In `runAction`'s CASE 2 branch, the only restriction is blocking the two `IHinkalWallet` selectors - `endpoint` and the rest of `callData` are unconstrained [1](#0-0) .

`EmporiumUpgradeable` is a single shared contract used by all Hinkal users (via `onlyAllowedRecipient`, gated only at the Hinkal.sol → action-contract level, not per-user) [4](#0-3) . Because prior legitimate ops (from this attacker or any other user) may call e.g. `token.approve(router, amount)` as part of a multi-step DEX/router interaction and leave a residual (unused) allowance, or simply leave stray token/ETH balance stranded on the contract, that state persists indefinitely - there is no revoke-on-exit logic anywhere in `runAction`.

Exploit flow:
1. Attacker calls `Hinkal.transact` → `EmporiumUpgradeable.runAction` with `stack.signerAddress = address(0)` (stateless path, no signature required).
2. Attacker sets `circomData.erc20TokenAddresses` to omit the stranded/approved token entirely (or includes only unrelated tokens with `deltaAmountChanges = 0`), so `balancesBefore`/`balancesAfter` never observe it.
3. One of `stack.ops` calls the router/token that holds EmporiumUpgradeable's residual approval (or simply directly calls `token.transfer(attacker, amount)` on a token EmporiumUpgradeable happens to hold), routing output to the attacker's own address - executed with `msg.sender == EmporiumUpgradeable` inside that external call.
4. Because that token was excluded from `circomData.erc20TokenAddresses`, `runAction`'s balance-invariant loop never runs for it - `BalanceChangeShouldBePositive` can never fire, and no accounting or slippage check anywhere else covers tokens outside that array.
5. The attacker walks away with value that never matched any `-deltaAmountChanges` entry Hinkal recorded for that transaction.

Existing guards do not prevent this: `performHinkalChecks`, proof verification, nullifier insertion, and `dimensionsCheck` in `Hinkal.transact` validate the shielded-side bookkeeping (`inTotal + amountChanges === outTotal`, roots, nullifiers) but have no way to constrain which real-world ERC20 addresses the external action's arbitrary calldata touches, since `erc20TokenAddresses` is exactly the array the on-chain balance-diff check trusts and the attacker fully controls its contents.

## Impact Explanation
This is direct theft of funds parked in a shared protocol contract (`EmporiumUpgradeable`) - any stray token balance, refund, dust, or (most severely) any left-over ERC20 approval granted by `EmporiumUpgradeable` to any router/endpoint in a past transaction (by this or any other user) can be swept out by an unprivileged attacker to their own address, entirely decoupled from the `-deltaAmountChanges` the attacker's own shielded proof claims to move. This matches the "Critical: direct theft of shielded or in-flight user funds" category, and is repeatable for every distinct stranded balance/approval that ever accumulates on the contract.

## Likelihood Explanation
- Requires the shared `EmporiumUpgradeable` contract to hold some non-zero token balance or approval that isn't accounted for by other users' subsequent transactions (a realistic and common occurrence for router integrations that approve more than they immediately spend, or leave rounding dust).
- Requires no privileged role - only the ability to call `Hinkal.transact` with `stack.signerAddress = address(0)` and a fresh `emporiumMessage` nonce, and to craft `externalActionMetadata`/`erc20TokenAddresses` - all explicitly listed as attacker-controlled fields.
- Zero cost beyond gas; fully repeatable each time new residual value accumulates.

## Recommendation
- Require `circomData.erc20TokenAddresses` to be checked against (or derived from) the addresses actually touched by `stack.ops` (e.g. decode/allowlist target tokens/endpoints so every asset moved is forced into the balance-diff array), or maintain an explicit on-chain accounting of "action-owned" balances instead of relying on `balanceOf` deltas over a caller-chosen array.
- In the stateless (`signerAddress == 0`) branch, restrict `op.endpoint` to an owner-managed allowlist of routers/contracts, and/or forbid arbitrary `approve` calls from `EmporiumUpgradeable`, or force full revocation (`approve(spender, 0)`) of any allowance created within the same `runAction` call before it returns.
- Alternatively, snapshot and diff balances over the full set of tokens/ETH actually referenced in `stack.ops.callData` rather than trusting only the attacker-supplied `erc20TokenAddresses`.

## Proof of Concept
Foundry plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20, and a mock "Router" contract that exposes `pull(address token, address to, uint256 amount)` calling `IERC20(token).transferFrom(EmporiumUpgradeable, to, amount)`.
2. Simulate the "prior op" precondition: as a legitimate user's stateless op, have `EmporiumUpgradeable` call `token.approve(router, 1000e18)` and only consume 100e18 in that same transaction (leaving 900e18 residual allowance), and/or directly seed a stray balance via `token.transfer(EmporiumUpgradeable, 900e18)`.
3. As a second, unrelated attacker EOA, call `Hinkal.transact` → `EmporiumUpgradeable.runAction` with `stack.signerAddress = address(0)`, `circomData.erc20TokenAddresses` excluding `token`, and `stack.ops` containing a call to `router.pull(token, attacker, 900e18)`.
4. Assert: `token.balanceOf(attacker)` increases by 900e18 after the call, while the sum of `deltaAmountChanges` supplied/verified for that transaction is `0` for `token` (or `token` is absent entirely from `circomData.erc20TokenAddresses`) - proving `tokens leaving EmporiumUpgradeable != -deltaAmountChanges`.
5. Confirm `runAction` does not revert with `BalanceChangeShouldBePositive` (since `token` is never included in the balance-diff loop).

Note: full end-to-end proof generation for the shielded side (real Circom proof, `Hinkal.transact` full call) was not exercised here due to tool/iteration limits; the core Solidity-level logic demonstrating the missing invariant is fully traced and cited above from `EmporiumUpgradeable.sol` and `Transferer.sol`.
