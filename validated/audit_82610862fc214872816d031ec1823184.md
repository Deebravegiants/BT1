This confirms the finding. `Utils::HmacValidator.validate` for webhooks only signs `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only validates the HMAC of the body and then dispatches to the handler using the unverified `request.shop` and `request.topic` [3](#0-2) . The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app [4](#0-3)  — it is not a per-shop secret. Documentation confirms the host app is expected to trust `data.shop` from the processed webhook as the shop identity [5](#0-4) .

### Title
Webhook shop/topic identity headers are unauthenticated — cross-tenant webhook spoofing via HMAC/header binding mismatch - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers exclusively the JSON body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values — all acted upon by the library and handed to the application's webhook handler — are read straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are never part of the signed payload.

### Finding Description
The identity binding that should hold is:
`shop asserted to the handler == shop that the signed bytes originated from`

Instead the code enforces only:
`HMAC(raw_body, client_secret) == received_hmac`

with `shop`, `topic`, `webhook_id`, `api_version` completely outside that computation [6](#0-5) . `Registry.process` trusts these unauthenticated fields directly:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [3](#0-2) 

Critically, `client_secret` used to sign webhooks is the app's single credential, identical for every merchant/shop that has installed the app — it is not scoped per tenant [7](#0-6) . This means any merchant who has legitimately installed the app can, for their own store, trigger a real Shopify webhook (e.g. `orders/create`) and receive a `(raw_body, hmac)` pair that is valid under the shared app secret. Because the `shop-domain` and `topic` headers are not covered by that HMAC, the attacker can replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and/or a different `x-shopify-topic`). `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` calls the application's handler asserting `shop: <victim-shop>` with attacker-influenced body content.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: any unprivileged-but-legitimate app installer (an attacker who merely installed the app on their own shop, no elevated privileges needed) can inject events that the host application will treat as authentic data for a shop they do not control. Depending on how the host app's webhook handler uses `data.shop`/`data.body` (e.g., updating cross-tenant records, marking an order paid, triggering fulfillment/`shop/redact` logic, or writing to the victim's tenant records), this is a cross-tenant data-integrity/confidentiality breach reachable purely through this gem's `Webhooks::Request`/`Registry` API surface, matching the audit's "field acted on but not covered by the HMAC" identity-binding class.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on at least one shop (the normal, unprivileged path any merchant can take) and replay an HTTP POST with modified headers to the app's public webhook endpoint — no access token, secret, or privileged account is needed, and no TLS interception is required since the attacker crafts their own outbound request.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material verified against the HMAC, or otherwise cryptographically bind them (e.g., require the app to independently confirm `shop` against a known/registered session before trusting `data.shop`). At minimum, `Request#to_signable_string` should not be the sole gate — `Registry.process` should not pass headers that were excluded from the signature computation directly to the handler without additional verification that ties them to the signed body's origin.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal onboarding, no elevated privileges).
2. Attacker triggers a real event (e.g., creates an order) causing Shopify to POST a legitimately signed webhook to the app: headers `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
3. Attacker captures `raw_body` and `hmac` header value.
4. Attacker sends a new POST to the same webhook endpoint with identical `raw_body`/`hmac`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present) [8](#0-7) ; `Utils::HmacValidator.validate` returns `true` because it only hashes `raw_body` [9](#0-8) .
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, which the host app will treat as authentic data belonging to the victim tenant [3](#0-2) .
