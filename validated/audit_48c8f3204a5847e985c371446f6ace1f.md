### Title
Webhook `shop` domain is not bound to the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator` verifies covers nothing but the JSON body. The `shop` value used by `ShopifyAPI::Webhooks::Registry.process` and handed to every app's `WebhookHandler` comes from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes.

### Finding Description
`Request#to_signable_string` [1](#0-0)  only signs the raw body, while `Request#shop` reads directly from an HTTP header with no cryptographic binding [2](#0-1) . `HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` using the app's shared `client_secret` and compares it to the `hmac` header [3](#0-2) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler, passing `request.shop` straight through as the trusted tenant identifier [4](#0-3) . Because the same `client_secret` is used to sign webhooks for every shop that installs a given app, a valid `(body, hmac)` pair generated for one shop remains cryptographically valid when replayed with a different `shopify-shop-domain` header value — the equality the gem should enforce, `hmac_signed(shop) == header(shop)`, is never checked; only `hmac_signed(body) == header(hmac)` is checked.

### Impact Explanation
An unprivileged user who can install the target app on their own store (or otherwise obtain one legitimately-signed webhook body/HMAC pair, e.g. via a shared/dev store) can capture a genuine webhook delivery and replay it to the app's webhook endpoint with the `shop` header rewritten to a victim shop's domain. Any app whose `WebhookHandler#handle` trusts `data.shop` from `WebhookMetadata` (as the documented usage pattern instructs) — for example to look up that shop's session/access token and act on its behalf, or to write/delete data keyed by shop — will perform that action against the victim's tenant using attacker-controlled, replayed content. This crosses a tenant boundary using only a valid-for-attacker's-own-shop credential, matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high for topics with static/predictable bodies (e.g., mandatory compliance topics like `customers/redact`, `shop/redact`, or webhooks whose payload doesn't include the shop's own domain, or where the attacker doesn't need the body content to differ). No secret is required — only observation of one's own legitimately received webhook and the ability to POST to the app's public webhook callback URL with modified headers, which is exactly the documented processing flow shown in the gem's own docs [5](#0-4) .

### Recommendation
Bind the shop domain into the signed material, or otherwise cryptographically verify it. Concretely, `HmacValidator`/`Request` should either (a) include the `shopify-shop-domain` header in `to_signable_string`, or (b) cross-check the header's shop against an independently-authenticated source (e.g., correlate with the offline session/access token already on file for that shop rather than trusting the header verbatim) before invoking the handler in `Registry.process`.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g. `customers/redact`) and capture the raw POST: body `B`, and headers including `x-shopify-hmac-sha256: H` (valid because `HMAC(client_secret, B) == H`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same request to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and, if desired, `x-shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which recomputes `HMAC(client_secret, B)` and finds it still equals `H`, since `B` is unchanged — validation passes.
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body: B`, and performs the app's redact/processing logic against the victim tenant, even though the request never touched Shopify for that shop.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
