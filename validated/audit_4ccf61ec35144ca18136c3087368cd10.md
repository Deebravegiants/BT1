I found a concrete instance of this bug class in this gem: the `Webhooks::Request#shop` field is used to derive the shop/tenant, but it is not covered by the HMAC signature.

### Title
Webhook shop-domain header is unauthenticated and not bound to the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature validated via `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop-domain` header is never included in the signed bytes, so an attacker can send a validly-signed webhook body while forging the `shop` header value used by the host application to route the payload to a tenant/session.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes the signature purely from `to_signable_string` and compares it to the `hmac` field read from the `X-Shopify-Hmac-Sha256` header [2](#0-1) . Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely independent of the signed body [3](#0-2) .

This breaks the intended equality: `bytes verified == bytes used to identify the tenant`. Since only the raw body bytes are HMAC-covered, and `shop` comes from an unauthenticated header rather than from the signed payload, `hmac_valid(body) != true` implies nothing about the authenticity of the `shop` header value. Any client who can reuse/replay a legitimately-signed webhook body (or who controls a body Shopify signs, such as the payload of a webhook for shop A) can pair it with an attacker-chosen `X-Shopify-Shop-Domain` header when handing the request to a host app that trusts `Request#shop` after `HmacValidator.validate` succeeds.

### Impact Explanation
If the host application authenticates a webhook solely via `HmacValidator.validate(request)` and then uses `request.shop` to select which merchant/tenant session or access token to act on (a common integration pattern, since the gem exposes `shop` specifically for that purpose), an attacker who can obtain one validly HMAC-signed webhook (e.g., delivered to their own shop, or any shop under their control) can relabel the `shop-domain` header to point at a victim tenant. The signature will still validate because it never covered the header. This yields cross-tenant confusion: a request cryptographically "proven" only to have unmodified body bytes for shop A can be attributed to shop B, letting an attacker trigger tenant-B-scoped webhook processing (e.g., data updates, uninstall/order flows) using body content the app already trusts as "signed."

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuinely Shopify-signed webhook body (readily obtainable if they operate/install the app on their own shop and receive webhooks), plus the ability to control or replay the HTTP headers presented to the host app's webhook endpoint. This is a realistic scenario since the gem's own `Registry`/handler flow is designed around exactly `raw_body` + `headers` being passed in from the host framework by `Request.new(raw_body:, headers:)` [4](#0-3) , and nothing in this gem cross-checks the header-derived `shop` against any signed claim.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting `Request#shop` for tenant routing. At minimum, document that `shop` is unauthenticated and must not be used for tenant selection without an independent binding (e.g., verifying it matches a shop domain already associated with a known offline session/access token before processing).

### Proof of Concept
1. Attacker installs/operates the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, headers include `X-Shopify-Hmac-Sha256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the same body `B` and the same valid `H`, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Host app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` then `ShopifyAPI::Utils::HmacValidator.validate(request)` — validation succeeds because `to_signable_string` only reflects `B`, unaffected by the header change:
   `OpenSSL.secure_compare(compute_signature(request.to_signable_string, secret), H)` → `true`.
4. Host app then reads `request.shop` → `"victim-shop.myshopify.com"` and processes the (attacker-controlled-timing) webhook as if it originated from the victim's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
