I found a genuine analog to the CVE's bug class in `oidc.go`. The Xerte vulnerability's root cause is: **a security-relevant error condition writes a response but fails to halt execution (`exit()`/`die()`), letting the request continue to perform privileged operations.**

The exact same pattern (missing `return` after writing an error response) exists in `handleTokenExchange`:### Title
Missing `return` After Failure/Error Responses in OIDC Token Exchange Allows Continued Processing With Unvalidated State - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` follows the same faulty pattern as CVE-2026-34413: after writing an HTTP error response, the handler function does not `return`, so execution continues into privileged operations (DB session insert, audit log, and session cookie establishment) using state that was never validated.

### Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go:163-276`), two failure branches write an error response to the client but omit `return`, letting the function fall through to security-relevant logic below:

1. `core/sessions/oidcauth/oidc.go:226-230` — when `claims["email"]` is not a string, the code writes a 500 response via `c.String(...)` but does **not** `return`: [1](#0-0) 
Execution continues to `IDClaimsToUserRole`, and then inserts a new row into `oidc_sessions` using the zero-value `email` (`""`), which is then persisted with the derived RBAC `role`: [2](#0-1) 
The audit log records a successful login (`AuthLoginSuccessNo2FA`) for an empty email, and the session cookie (`webauth.SessionIDKey`) is set and saved: [3](#0-2) 
Finally, a `200 OK` JSON success response is written on top of the earlier (ignored) 500 response: [4](#0-3) 

2. `core/sessions/oidcauth/oidc.go:257-260` — if the DB insert itself fails, the code again writes an error via `c.String(...)` without `return`, and the function still proceeds to set the auth cookie and respond `200 OK` with `Success: true`, even though no session row exists in `oidc_sessions`. [5](#0-4) 

The root cause mirrors the external report exactly: an intended early-exit-on-error path (`c.String(...)` write) is not paired with a `return`, so PHP/Go execution silently continues into the "authenticated" code path that stamps the session cookie and returns success.

The `Authenticate` middleware that later validates sessions (`core/web/auth/auth.go:155-173`) trusts whatever session ID is stored via `AuthorizedUserWithSession`, so a client that reaches this broken branch can obtain a valid, cookie-backed session tied to an empty-email `oidc_sessions` row with a real RBAC role, or a session cookie despite a failed session persist.

### Impact Explanation
An attacker controlling the OIDC callback flow (e.g., a malicious/compromised IdP, or an attacker able to complete the `code` exchange with a permissive IdP) can trigger the `claims["email"]` type-assertion failure or force the DB insert to fail, and still receive `HTTP 200 {"success": true}` with a valid `webauth.SessionIDKey` cookie set. This is a cross-user/identity confusion and integrity issue: the resulting session is tied to an empty or non-persisted email but carries a legitimate RBAC role (Admin/Edit/Run/View) derived from group claims, undermining per-user attribution and potentially producing an authenticated node-API session that does not correspond to any real, auditable local user.

### Likelihood Explanation
Exploitability depends on the ability to influence the `email` claim value (e.g., IdP returning claims without an `email` string field, or a race/DB failure on insert) during the OIDC callback, which is a client-controlled/attacker-influenced external-initiator flow reachable by any party that can complete part of the OIDC handshake against `/oidc-exchange`. It is not fully unauthenticated in the same trivial sense as the elFinder CVE (a valid provider code exchange is still required), so likelihood is Medium rather than High.

### Recommendation
Add `return` immediately after every `c.String(...)`/`c.JSON(...)` error write in `handleTokenExchange`, specifically at `core/sessions/oidcauth/oidc.go:229` (after the `email` type-assertion failure) and at `core/sessions/oidcauth/oidc.go:259` (after the `oidc_sessions` insert failure), so the function aborts instead of proceeding to set the session cookie and return success.

### Proof of Concept
1. Configure/control an OIDC provider such that the ID token's claims payload omits an `email` field or returns a non-string value for `email` (while still satisfying `ClaimName`/group claims validation).
2. Complete the normal `/oidc-login` → provider → `/oidc-exchange` flow with a valid `code`/`state`.
3. Observe that despite the internal `c.String(http.StatusInternalServerError, "Failed to get email from claims")` write, the response body is ultimately `HTTP 200 {"success":true}` and a `Set-Cookie` for the session is present, because execution fell through past the missing `return` at `core/sessions/oidcauth/oidc.go:229`.
4. Use the returned session cookie against any authenticated node API route guarded by `auth.Authenticate(..., auth.AuthenticateBySession)` (`core/web/router.go`) to confirm a working authenticated session was created despite the error path.
