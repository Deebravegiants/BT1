The webhook processing path in this gem has the same root-cause bug class as the report: a field that downstream code trusts and acts on (`shop`) is not covered by the HMAC that is supposed to authenticate the request.

### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates nothing but the body bytes. The `shop`, `topic`, and `webhook_id` values are read directly from attacker-controllable HTTP headers and are never part of the signed content, yet `Registry.process` uses them to select the handler and to populate `WebhookMetadata` passed to app code.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` purely from headers: [1](#0-0) 

Concretely: [2](#0-1) 

The `hmac` accessor decodes the `hmac-sha256` header, and `to_signable_string` — the only value fed into HMAC computation — returns just `@raw_body`, never any header: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`, i.e. it authenticates `raw_body == raw_body_signed_by_shopify`, and nothing about `shop`, `topic`, or `webhook_id`: [5](#0-4) 

`Registry.process` trusts these unauthenticated fields to route the request and to build the metadata handed to the app's handler: [6](#0-5) 

The identity binding that should hold is: `shop header == shop that produced/authorizes raw_body`. In fact, the HMAC only proves `raw_body` was signed by an app secret holder (Shopify) — it says nothing about which shop the header claims. Because the api client secret is shared across every shop that installs the app, any body+HMAC pair that is valid for one shop (e.g. one the attacker legitimately controls, such as their own dev/test store where they installed the app and can trigger a real webhook) remains HMAC-valid when replayed with a different `shopify-shop-domain` header value. `Registry.process` will accept it and hand `data.shop` = the spoofed value to the app's registered handler.

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: apps are told to build handlers using `WebhookMetadata#shop` as the tenant identifier for looking up sessions or performing per-shop operations (per `docs/usage/webhooks.md`). An attacker who can obtain one authentic, HMAC-signed webhook payload from Shopify (trivially available to anyone who installs the app on their own store — no special privilege required beyond that) can replay it against the app's public webhook endpoint with an arbitrary victim `shop-domain` header (and/or `topic`) while the HMAC check still passes, because the signature never covered those headers. Depending on how the host handler uses `data.shop` (e.g., to look up/act on that shop's stored session or data), this enables cross-tenant data corruption/spoofing — the app processes and attributes attacker-controlled content to a shop the attacker does not control.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app once on any shop the attacker controls (or otherwise obtain one signed body/HMAC pair, e.g. via a public test store), and (2) network access to the app's webhook endpoint, which is normally internet-reachable since Shopify posts to it directly. No access to `api_secret_key`, access tokens, or the merchant's own credentials is needed. This is directly reachable through the gem's documented API (`Registry.process(Request.new(...))`), not a misuse of undocumented behavior.

### Recommendation
Bind the header fields into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC before they are trusted. At minimum, `to_signable_string` should incorporate these header values (matching however Shopify actually computes the webhook HMAC, if it already covers headers) so that `HmacValidator.validate` fails when any of them is altered independently of the body signature host applications rely on `request.shop`/`request.topic` for tenant/handler routing.

### Proof of Concept
1. Attacker installs the target app on a shop they control (`attacker-shop.myshopify.com`) and triggers a webhook event (e.g. `orders/create`), capturing the raw POST: `raw_body` and header `x-shopify-hmac-sha256`.
2. Attacker re-sends this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — validation succeeds because the body is untouched.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process attacker-supplied data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
