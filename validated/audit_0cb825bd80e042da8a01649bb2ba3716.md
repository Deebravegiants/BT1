### Title
Checks-Effects-Interactions Violation in Tron `IntentGatewayV2.withdraw()` Allows Escrow Over-Withdrawal via Reentrancy - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` implements escrow release (`withdraw()`) with the external token/native transfer happening *before* the escrow balance is decremented and *before* the transferred `amount` is validated against the remaining escrowed balance. This is the same root-cause class as the reported Tokemak issue: a withdrawal path that executes an external transfer of a caller/message-supplied `amount` without first confirming sufficiency of the internally tracked available balance, deferring that check to *after* the external interaction has already occurred.

### Finding Description
`withdraw()` in the Tron gateway [1](#0-0)  only checks `_orders[body.commitment][token] == 0` (i.e., "is there *any* escrow left") — not whether the requested `amount` is actually covered by that escrow — and then immediately performs the external transfer (`.call{value: amount}` for native tokens or `token.call(transfer(...))` for ERC-20s) before decrementing `_orders[body.commitment][token] -= amount`. The sufficiency check is only enforced retroactively, via Solidity's checked-arithmetic revert on `-= amount` underflow, which happens strictly *after* the external call has already executed.

This is precisely analogous to the reported flaw: `_ensureLocalUnderlyingBalance` in Tokemak's `DestinationVault` executes an external withdrawal for an unvalidated `amount` and only relies on the downstream contract to fail if funds are insufficient — instead of validating availability up front. Here, the gateway relies on a downstream revert (arithmetic underflow) to enforce the invariant, but that revert comes only after external control has already been transferred to `beneficiary` or `token`.

Contrast this with the corresponding function in the primary EVM production path, `IntentsBase._withdraw()` [2](#0-1) , where the escrow balance is decremented (`_orders[...] = escrowed - amount`, which reverts on insufficiency) *before* the external transfer is made — the correct CEI ordering. The codebase's own reentrancy regression tests confirm this exact bug class was previously found and fixed for `fillOrder`/`_withdraw` reentrancy by setting state (`_filled[commitment]`) before any external calls [3](#0-2) . The Tron contract's `withdraw()` was not brought in line with that fix: it transfers funds first and validates/updates escrow state second.

### Impact Explanation
If the `beneficiary` for a native-token escrow release is a contract with a fallback function, or the `token` being released is a token with transfer hooks/callbacks (e.g., ERC-777-style or any token capable of reentering), that callback executes while `_orders[body.commitment][token]` still reflects the pre-withdrawal (undecremented) balance. A reentrant call that can reach `withdraw()` again for the same `commitment`/`token` before the first call's decrement completes would pass the `!= 0` check a second time and trigger a second external transfer against escrow that has not yet been reduced, resulting in the gateway releasing more value than was actually escrowed for that order — a direct loss of funds for the protocol/other users whose escrow shares the same token balance pool.

### Likelihood Explanation
Reachability of a genuine reentrant second call to `withdraw()` for the *same* commitment is constrained by the host's replay protection (`EvmHost`/Handler request receipts are written before `onAccept` is invoked, preventing exact request replay). However, the vulnerable code pattern itself — transfer before balance decrement/validation — is a clear, concrete deviation from the checks-effects-interactions pattern that the team has explicitly fixed elsewhere in this same codebase for the identical bug class (see the reentrancy test above), and remains present, unpatched, in the Tron variant of the same contract family reachable by any relayer delivering a `RedeemEscrow`/`RefundEscrow` message.

### Recommendation
Mirror the fix already applied in `IntentsBase._withdraw()`: decrement `_orders[body.commitment][token]` (relying on Solidity's checked arithmetic to enforce `amount <= escrowed`) *before* performing the external native-token call or `token.call(transfer(...))`. Apply the same effects-before-interactions ordering to the transaction-fee payout block later in the same function.

### Proof of Concept
1. A relayer delivers a `RedeemEscrow`/`RefundEscrow` post request whose `body.beneficiary` is a malicious contract, or whose `token` is a callback-capable token.
2. `onAccept` → `withdraw()` reads `_orders[commitment][token] != 0`, then executes `beneficiary.call{value: amount}("")` (or `token.call(transfer(...))`) — control passes to attacker-controlled code while `_orders[commitment][token]` still holds its pre-withdrawal value.
3. Within that callback, the attacker triggers a path that re-enters `withdraw()`/the transfer logic for the same `commitment`/`token` before the first invocation's `_orders[body.commitment][token] -= amount` executes.
4. The second invocation's `_orders[...] == 0` check still passes (state not yet updated), causing a second transfer of `amount` against escrow that was only funded once — draining more value than was deposited for that order. [4](#0-3)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
