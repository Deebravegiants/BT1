### Title
`Oauth.begin_auth` builds the OAuth authorize redirect from raw, unsanitized `shop` input - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`Oauth.begin_auth` interpolates the caller-supplied `shop` string directly into `auth_base_uri(shop)` and thus into the returned `auth_route` without ever calling `Utils::ShopValidator.sanitize!` or any other host-allowlist check. If a host app takes `shop` from an untrusted source (as the gem's own documentation example does — `shop = request.headers["Shop"]`) and passes it straight to `begin_auth`, the app will redirect the user's browser to an attacker-chosen host carrying the real `client_id` and `redirect_uri`.

### Finding Description
The binding that should hold is: `auth_route.host == ShopValidator-approved myshopify/host` for every value returned by `begin_auth`. Tracing `begin_auth` in `lib/shopify_api/auth/oauth.rb` (lines 22-52) shows `shop` flows unmodified into `auth_base_uri(shop)` (lines 117-128), which simply does `"https://#{shop}/admin"` unless `shop.include?(".my.shop.dev")`. There is no call to `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) anywhere in `oauth.rb` — confirmed by searching the file, which has zero occurrences of `ShopValidator`/`sanitize!`. `ShopValidator.sanitize!` is used elsewhere in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`), but the OAuth authorization-start path (`begin_auth`) is not one of them.

The gem's own documented usage pattern in `docs/usage/oauth.md` (lines 180-198) takes `shop` straight from a request header (`request.headers["Shop"]`) and calls `begin_auth(shop: domain, ...)`, then 307-redirects the browser to `auth_response[:auth_route]`. With this documented pattern, an attacker who controls the `Shop` header of their own request can set `shop = "evil.example.com"`, causing `auth_route` to become `https://evil.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...`. The app's server will issue a redirect to that attacker-controlled host, carrying the real `client_id` and `redirect_uri` and a per-request `state` cookie value.

Existing guards do not prevent this: `HmacValidator.validate` and the `state` comparison only run in `validate_auth_callback` (the callback leg), never in `begin_auth`; `Context.setup?`/`private?` checks only guard configuration, not the shop value; and `ShopValidator` is simply never invoked on this path.

### Impact Explanation
Every request through this path leaks the app's `client_id` and configured `redirect_uri` to an attacker-chosen host, and drives the merchant's/victim's browser to an attacker-controlled server instead of Shopify — an SSRF-adjacent, forced-redirect condition affecting the OAuth authorization leg. This does not by itself hand over an access token or `client_secret` (those only move in `validate_auth_callback`'s POST to Shopify, which is unaffected), and it requires the host application to follow the documented anti-pattern of feeding a raw untrusted value into `shop:`. This matches **High** (SSRF-style forced redirect / credential-adjacent leakage to an unintended host), not Critical, since no access token, refresh token, or `client_secret` is exfiltrated directly by this bug alone.

### Likelihood Explanation
Exploitability depends entirely on the host application echoing an attacker-controlled value (header, query param, etc.) into `begin_auth(shop:)` without first validating it via `ShopValidator.sanitize!`. The gem's own documentation demonstrates exactly this pattern (`shop = request.headers["Shop"]`), which is a realistic and even encouraged integration pattern, making this a plausible real-world misuse. No secrets or special privileges are needed by the attacker — only the ability to set an arbitrary header/param value on their own request.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: Context.my_shopify_domain)` (or equivalent) at the top of `Oauth.begin_auth` before using `shop` in `auth_base_uri`, raising `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain — mirroring what `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb` already do.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
test "#begin_auth raises for a non-Shopify shop host" do
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example.com", redirect_path: "/callback")
  end
end

test "#begin_auth does not build an auth_route pointing off myshopify.com" do
  auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example.com", redirect_path: "/callback")
  refute_match(/\Ahttps:\/\/evil\.example\.com/, auth_response[:auth_route])
rescue ShopifyAPI::Errors::InvalidShopError
  # expected once the fix (ShopValidator.sanitize!) is applied
end
```
Currently (before a fix), `begin_auth(shop: "evil.example.com", redirect_path: "/callback")` returns `auth_route` starting with `https://evil.example.com/admin/oauth/authorize?client_id=...`, with no call to `ShopValidator.sanitize!` anywhere on the call stack — demonstrable via `Utils::ShopValidator.expects(:sanitize!).never` in a Mocha-based test around the `begin_auth` call.
