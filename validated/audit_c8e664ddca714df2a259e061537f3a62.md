### Title
Non-atomic read-modify-write in `#removeManySeedsMetadata` causes lost-update race with concurrent `addSeed`, resurrecting metadata for removed seeds - (File: features/wallet/module/wallet.js)

### Summary
`wallet.js`'s `#removeManySeedsMetadata` reads `seedMetadataAtom.get()`, mutates the plain object locally, and calls `seedMetadataAtom.set(metadata)` with a plain value instead of using the atom's functional-update form. Because this `get()`/mutate/`set()` sequence is not serialized against other pending `set()` calls (such as the one inside `addSeed`), a concurrently running `addSeed` can be silently overwritten (lost update), producing stale/incorrect persisted `seedMetadata` state.

### Finding Description
`seedMetadataAtom` is created via `createStorageAtomFactory({ storage })({ key: 'seedMetadata', isSoleWriter: true })` [1](#0-0) . The atom's `set` is wrapped with `makeConcurrent(...)` (concurrency 1) in `enforceObservableRules`, and correctly supports a functional form (`set(prev => next)`) that reads the current value and writes atomically relative to *other* `set()` calls [2](#0-1) . `addSeed` correctly uses this safe functional form:
```
await this.#seedMetadataAtom.set((previous) => ({ ...previous, [seedId]: {...} }))
``` [3](#0-2) 

However, `#removeManySeedsMetadata` does NOT use the functional form. It calls `get()` directly (which is not queued behind pending `set()` calls — only `set()` calls are serialized against each other), mutates the returned object, then calls `set(metadata)` with the final plain object:
```
#removeManySeedsMetadata = async (seedIds) => {
  const metadata = await this.#seedMetadataAtom.get()
  seedIds.forEach((seedId) => delete metadata[seedId])
  await this.#seedMetadataAtom.set(metadata)
}
``` [4](#0-3) 

Because the `get()` snapshot is taken outside of the `set` queue, if `addSeed(A)`'s `set(fn_A)` call computes and commits its update to storage *after* `#removeManySeedsMetadata` took its snapshot but *before* `#removeManySeedsMetadata`'s own `set(metadata)` call executes (both queued in the same `makeConcurrent` `set` queue, in either order), the plain-object `set(metadata)` will overwrite the whole atom with a stale snapshot that lacks the concurrently-added seed's metadata entry — a classic lost update. This can either drop the newly added seed's metadata (if remove's write lands last) or, depending on ordering/timing, leave a metadata entry present for a seedId that was actually removed from the keychain (since removal of keychain material happens in a separate step, `#keychain.removeSeeds`, independent from metadata bookkeeping).

Compounding this, `removeManySeeds` does not `await` the metadata-cleanup call at all:
```
await this.#setExtraSeeds(remainingSeeds)
this.#removeManySeedsMetadata(seedIds)   // missing await
await this.#keychain.removeSeeds(...)
``` [5](#0-4) 
This makes `removeManySeeds()` resolve to the caller before the metadata bookkeeping has completed, further widening the window in which the metadata for a still-in-flight `addSeed` (or another concurrent `removeManySeeds`) can be clobbered, since callers have no way to sequence against it.

### Impact Explanation
The impact is limited to a data-integrity/bookkeeping issue in `seedMetadataAtom`, not to the keychain itself. `#setExtraSeeds` (the actual `EXTRA_SEEDS_KEY` seed material array) and `#keychain.removeSeeds` are each updated with their own atomic/sequenced calls, so the underlying key material removal path is unaffected by this specific race. What can happen is:
- A ghost/ stale metadata entry survives in `seedMetadataAtom` for a seedId whose key material was actually removed (label/dateCreated preserved even though `getExtraSeedIds()`/keychain no longer has the key), or
- A newly added seed's metadata is silently dropped from `seedMetadataAtom` even though its key material and passphrase-encrypted seed record were persisted successfully via `#setExtraSeeds`/`keychain.addSeed`.

This is a persisted-state consistency bug that can mislead UI/account-isolation logic relying on `getSeedMetadata()` (e.g., a removed seed still shown as "present" with a label, or an added seed with no metadata/label). It does not, by itself, grant unauthorized signing, secret disclosure, or origin/auth bypass — key material presence/absence is governed by `#setExtraSeeds` and `keychain`, not by `seedMetadataAtom`.

### Likelihood Explanation
The race requires two concurrent multi-seed wallet operations (`addSeed` and `removeManySeeds`) to be in flight on the same unlocked wallet instance at the same time, with `maxExtraSeeds > 0`. `wallet.addSeed` / `wallet.removeManySeeds` / `wallet.removeSeed` are exposed through the `walletApi`/`applicationApi` surfaces [6](#0-5) [7](#0-6) , but from what is indexed I could not confirm whether these specific application-level methods are reachable directly from an untrusted dApp/origin RPC surface, or only from the trusted extension/mobile UI process. I found the generic RPC transport (`@exodus/sdk-rpc`, `browser-extension-rpc`) that exposes whichever methods are registered, but no explicit origin/permission gating logic for `wallet.addSeed`/`removeManySeeds` in the indexed code. This is a meaningful gap: if these calls are only issuable by the wallet's own trusted UI process (not by arbitrary dApp origins), then the "unprivileged attacker" precondition in the question is not actually satisfiable, and this would be a same-process double-invocation/race bug rather than an externally-exploitable one.

### Recommendation
Rewrite `#removeManySeedsMetadata` to use the atom's atomic functional-update form so it is properly serialized against other `set()` calls, e.g.:
```js
#removeManySeedsMetadata = async (seedIds) => {
  await this.#seedMetadataAtom.set((previous) => {
    const next = { ...previous }
    seedIds.forEach((seedId) => delete next[seedId])
    return next
  })
}
```
Also fix the missing `await` in `removeManySeeds` so the metadata cleanup is properly sequenced with the rest of the operation before the method resolves.

### Proof of Concept
Integration test (extending `features/wallet/module/__tests__/index.test.js`):
```js
it('does not lose metadata under concurrent addSeed/removeManySeeds', async () => {
  await wallet.create()
  await wallet.unlock()

  const seedIdB = await wallet.addSeed({ mnemonic: otherMnemonic, label: 'B' })

  const addPromise = wallet.addSeed({ mnemonic: 'abandon '.repeat(12).trim(), label: 'A' })
  const removePromise = wallet.removeManySeeds([seedIdB])

  const [seedIdA] = await Promise.all([addPromise, removePromise])

  const metadata = await seedMetadataAtom.get()
  const extraSeedIds = await wallet.getExtraSeedIds()

  // Assert seedMetadataAtom.get() matches only seeds actually present in EXTRA_SEEDS_KEY
  expect(Object.keys(metadata).sort()).toEqual(
    [await wallet.getPrimarySeedId(), ...extraSeedIds].sort()
  )
  expect(metadata).toHaveProperty(seedIdA) // added seed's metadata must survive
  expect(metadata).not.toHaveProperty(seedIdB) // removed seed's metadata must be gone
})
```
Expected (buggy) behavior: depending on interleaving, `metadata` either lacks `seedIdA` (lost update from add) or still contains `seedIdB` (stale metadata resurrected/retained after removal), demonstrating the non-atomic read-modify-write in `#removeManySeedsMetadata`.
