### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later verifies) only the raw HTTP body via `to_signable_string`, while the `shop`, `topic`, `api_version`, and `webhook_id` fields are read directly from HTTP headers that are excluded from the HMAC computation. `Registry.process` accepts any request whose body HMAC validates and then dispatches the handler using the unauthenticated `shop` header value, breaking the binding "bytes verified == bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `api_version`, `webhook_id` are pulled straight from headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` validates only that body-HMAC, then immediately trusts the unauthenticated `shop` header to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the identity binding: `HMAC-verified-bytes == raw_body` but `shop-used-for-tenant-routing == header value`, and the header is not part of the verified bytes. Because Shopify computes HMAC over the raw request body only (matching this gem's implementation), any entity capable of obtaining one legitimately-signed webhook body+HMAC pair for a *given payload* (e.g., a merchant receiving webhooks for their own store, or any attacker who can trigger/replay a webhook whose body content is attacker-controllable or generic, such as `app/uninstalled` boilerplate bodies) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header to name a different shop. The HMAC still validates (it never covered the header), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen tenant.

### Impact Explanation
This is a cross-tenant boundary violation: an app's webhook handler typically uses `shop` to look up the session/store record and apply the delivered payload to that tenant's data (e.g., updating orders, deleting resources, revoking access on `app/uninstalled`). Since `shop` is not authenticated, an attacker can cause the payload to be attributed to and applied against a shop they do not own, corrupting or leaking that tenant's data - a cross-tenant access impact.

### Likelihood Explanation
Exploitability depends on the attacker's ability to obtain a validly-signed body for a chosen or replayable payload (e.g., from webhooks delivered to their own shop, or from any predictable/static payload topic) and then replay it with a substituted `shop-domain` header value. This requires only unprivileged access as a Shopify merchant/app installer (no `api_secret_key`, no access token) capturing a real webhook of their own and modifying non-signed headers before forwarding it to the target app's public webhook endpoint.

### Recommendation
Include the authenticated `shop` (and ideally `topic`) in the material verified against the HMAC, or otherwise cryptographically bind the header-derived identity to the signed payload before it is trusted for tenant routing, matching Shopify's guidance to treat the header purely as informational once verified against an independently trusted source (e.g., cross-checking against the shop recorded for the webhook subscription via a lookup, not solely the header).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook (e.g., generic `app/uninstalled` with an empty/static body `{}`), capturing the valid `x-shopify-hmac-sha256` value computed over that body.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body bytes: [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`: [6](#0-5) , causing the app to process the webhook against the victim tenant instead of the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
