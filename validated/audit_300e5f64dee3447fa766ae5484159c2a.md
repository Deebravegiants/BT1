### Title
Batch withdrawals sharing the same `assetId` cause the POA bridge to misreport (status, txHash) across indices - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the destination-chain payment for a `WithdrawalIdentifier` by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches solely on `assetId` via `Array.prototype.find`, ignoring `index` and `destinationAddress`. When a batch's `withdrawalParams` contains two entries with the same `assetId` but different `destinationAddress`, both entries' `wid`s resolve to the identical first-matching record from the POA API response, so `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` report the same `(status, txHash)` for both indices regardless of which recipient actually got paid.

### Finding Description
Equality that must hold: `describeWithdrawal(wid_i).txHash == the txHash of the on-chain payment actually made to withdrawalParams[i].destinationAddress`, for every `i` in a batch.

Trace:
- `sdk.ts`'s `createWithdrawalCompletionPromises` (`packages/intents-sdk/src/sdk.ts:557-608`) derives `wids` positionally from `createWithdrawalIdentifiers(bridges, withdrawalParams, intentTx)` and calls `watchWithdrawal({ bridge, wid: entry.wid })` for `wids[index]`. `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) correctly builds one `wid` per input, each carrying `withdrawalParams` and a `bridge`-route-local `index`.
- `PoaBridge.describeWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:313-343`) fetches all withdrawals for the shared `intentTx.hash` via `getWithdrawalStatusWithRetry` (a single NEAR tx can contain multiple withdrawal legs), then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`.
- `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:409-427`) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)`. It never inspects `index`, `destinationAddress`, or `amount`. The code comment explicitly acknowledges: *"multiple withdrawals of the same token in a single transaction are not supported."*
- Consequence: if `withdrawalParams[0].assetId === withdrawalParams[1].assetId` (e.g., both `nep141:btc.omft.near`) but different `destinationAddress`, then `describeWithdrawal` invoked for `wid` index 0 and for `wid` index 1 both call `find()` with the identical predicate and therefore both return the **same** first-matching array element, independent of which index/destination they were asked about. Both promises in `createWithdrawalCompletionPromises` resolve with the identical `txHash` (whichever withdrawal happens to be first in the unsorted API response), even though the two legs paid two different `destinationAddress`es with two different `transfer_tx_hash`es.
- No downstream guard prevents this: `validateWithdrawal`, `compareAddresses`, `FeeExceedsAmountError`, and `getUnderlyingFee` operate on fee/amount/address validity per-withdrawal at creation time, not on cross-referencing the completion-status lookup; they don't detect or reject duplicate `assetId` entries in a batch. The `supports()`/route-selection logic in `findBridgeForWithdrawal` also does not deduplicate or flag same-asset batch entries.
- The attacker/input here is entirely attacker-controlled: an ordinary NEAR Intents user (or a counterparty whose `assetId`/`destinationAddress` strings an integrator forwards) simply submits a normal, publicly documented batch withdrawal (`sdk.processWithdrawal` / `signAndSendWithdrawalIntent` + `waitForWithdrawalCompletion`) with two legs of the same token to different addresses — no misuse of any special escape hatch is required, and the public README's "Batch Withdrawals" section does not warn against this.

### Impact Explanation
An integrator that keys off `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`'s per-index result to credit or reconcile per-recipient completion will attribute the destination-chain `txHash` of one recipient's payment to the other recipient's withdrawal record. This is a status/hash misreport that can make an integrator credit (or refund) the wrong party, or double-credit the same `txHash` against two different recipients/withdrawal records — matching the **High** impact category ("a status or hash misreport making an integrator credit or refund twice"). It affects any batch containing ≥2 legs on the same NEP-141 asset routed through `PoaBridge`, and is repeatable on every such batch.

### Likelihood Explanation
Preconditions are trivial and fully attacker/user controlled: build a batch `withdrawalParams` array with two (or more) entries sharing `assetId` (any NEP-141 asset supported by the POA bridge) but differing `destinationAddress`, then call the documented batch APIs. No special privileges, no cooperation from a malicious relayer/bridge/RPC is required — the flaw is purely in the SDK's own `findMatchingWithdrawal` matching logic. Cost to trigger is one ordinary batch withdrawal.

### Recommendation
In `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`), disambiguate same-`assetId` entries deterministically and consistently between the withdrawal-creation and status-lookup sides — e.g. sort both the local per-asset-route `withdrawalParams` list and the API's `withdrawals` list by `amount` (or another stable, request-derivable key) and match by position within the same-asset group, as the existing code comment suggests. Alternatively, reject/throw (fail closed) in `createWithdrawalIdentifiers`/`describeWithdrawal` when a batch contains duplicate `assetId` entries for the POA route until proper per-leg matching is implemented, rather than silently returning a possibly-wrong `txHash`.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
