## Title
Unchecked division-by-zero panic in `Calculator::swap_token_amount_base_in` / `InvariantToken` when pool reserves reach zero via attacker-controlled swap/deposit accounts - (File: `program/src/math.rs`)

### Summary
CVE-2018-18521 is a divide-by-zero crash in `arlib_add_symbols()` caused by an unchecked, attacker-influenced denominator (`sh_entsize`) derived from untrusted input. The analogous pattern in this codebase is the pervasive use of `.checked_div(...).unwrap()` on denominators built from pool reserve values (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) inside `Calculator::swap_token_amount_base_in`/`base_out` and `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin`, which are reached directly from the public `SwapBaseIn`/`SwapBaseOut`/`Deposit` instructions with attacker-chosen amounts and accounts.

### Finding Description
`Calculator::swap_token_amount_base_in` computes `amount_out = total_pc/coin.checked_mul(amount_in).unwrap().checked_div(denominator).unwrap()` where `denominator` is `total_coin_without_take_pnl.checked_add(amount_in)` or `total_pc_without_take_pnl.checked_add(amount_in)` [1](#0-0) . Likewise `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` divide directly by `self.token_coin`/`self.token_pc`, which are populated from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` in `process_deposit` [2](#0-1) [3](#0-2) .

These reserve values are derived every call via `Calculator::calc_total_without_take_pnl_no_orderbook(pc_amount, coin_amount, amm)`, which is simple subtraction with no floor/zero-protection beyond overflow checks: `pc_amount.checked_sub(need_take_pnl_pc)` and `coin_amount.checked_sub(need_take_pnl_coin)` [4](#0-3) . If either result is `0` (a real vault balance fully consumed net of pending pnl), any subsequent call in the same or a later transaction into `exchange_coin_to_pc`/`exchange_pc_to_coin` divides by that zero reserve, and `checked_div` returns `None`, causing `.unwrap()` to panic. All of these code paths — `process_deposit`, `process_swap_base_in`/`_out` (and their V2 variants) — are reachable by any unprivileged user submitting a single transaction with attacker-chosen swap/deposit amounts and standard SPL token accounts [5](#0-4) [6](#0-5) .

### Impact Explanation
A panic on `.unwrap()` from a `None` returned by `checked_div` aborts the transaction with a runtime panic rather than a graceful `ProgramError`, which is a denial-of-service condition — directly analogous to the "application crash" impact of CVE-2018-18521. However, I was unable to conclusively confirm from the indexed code that an attacker can actually drive `total_coin_without_take_pnl` or `total_pc_without_take_pnl` to exactly `0` using only standard swap math: the swap output amount computed by `swap_token_amount_base_in`/`base_out` is bounded by the constant-product invariant, and I did not find (within the indexed portions of `processor.rs`) an explicit check rejecting `amount_out == total_coin_without_take_pnl` before invoking `token_transfer`, nor did I find code preventing `need_take_pnl_pc`/`need_take_pnl_coin` from growing to equal the raw vault balance. Because I could not fully trace every branch of `process_swap_base_in`/`out` and `process_withdrawpnl` in the indexed content, I cannot definitively prove the zero-reserve state is reachable from a single attacker transaction, only that the resulting divide-by-zero panic is unguarded if that state is ever reached.

### Likelihood Explanation
Reaching a zero-reserve state through legitimate AMM constant-product swaps is generally difficult because output amounts are proportionally capped by the invariant (denominator grows with `amount_in`, so output approaches but should not reach the full reserve for finite input). The more likely trigger is via `need_take_pnl_pc`/`need_take_pnl_coin` growing (through repeated `WithdrawPnl`/pnl accounting in `calc_take_pnl`, `program/src/processor.rs:167-281`) until it approaches the raw vault balance, at which point `calc_total_without_take_pnl_no_orderbook` yields a very small or zero effective reserve. Given the reliance on unrelated fee/pnl accounting to reduce the reserve to exactly zero, this is a lower-likelihood, edge-case scenario rather than a trivially reachable one.

### Recommendation
Replace `.unwrap()` on `checked_div` calls in `Calculator::swap_token_amount_base_in`/`base_out`, `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin`, and `InvariantPool::exchange_pool_to_token`/`exchange_token_to_pool` (`program/src/math.rs`) with proper `ok_or(AmmError::...)?` error propagation, and explicitly reject swaps/deposits/withdrawals when the computed reserve denominator is zero before performing the division, mirroring the pattern already used for `AmmError::CalculationExRateFailure` elsewhere in `process_deposit`.

### Proof of Concept
Not fully constructible from the indexed code: a concrete PoC would require confirming a code path (not found in the indexed `processor.rs` content) that permits `total_coin_without_take_pnl` or `total_pc_without_take_pnl` to reach exactly zero via a single attacker-submitted `SwapBaseIn`/`SwapBaseOut`/`WithdrawPnl` transaction sequence. I recommend a Devin session with full repository access to trace `process_withdrawpnl` and the `need_take_pnl_pc`/`need_take_pnl_coin` growth logic end-to-end to determine definitively whether this zero-reserve state is attacker-reachable.

        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
