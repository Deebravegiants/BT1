Confirmed: `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all call `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` but never capture the returned `amounts[0]` (actual ETH spent) nor refund the difference to `_msgSender()`. This is a direct structural analog of the Velodrome `SwapRouter` bug, and notably the codebase's own `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`/`IntrinsicIntents.sol` already implement the correct pattern (`msgValue -= amounts[0]; if (msgValue > 0) _sendValue(msg.sender, msgValue);`), confirming this is a known bug class in this codebase that was fixed in some contracts but missed in `EvmHost`.

### Title
EvmHost fails to refund unspent native token after fee swap, permanently trapping user overpayment - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native token payment and internally swap it via Uniswap V2 for an exact amount of `feeToken()`. None of these functions capture the actual ETH spent or refund the leftover to the caller, unlike the equivalent, already-fixed pattern used in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Finding Description
In each of these functions, when `msg.value > 0`, the code does: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` (per the standard UniswapV2Router02 implementation) sends exactly `msg.value` in, buys the exact `fee`/`amount` of tokens, and refunds any unused ETH back to the caller of the swap function — here that caller is `EvmHost`, not the original end user (`_msgSender()`). Any excess ETH sent above the amount actually required for the swap (e.g., a caller overestimating the required native value, or the router's Uniswap price shifting favorably) is never returned to `_msgSender()`. It stays inside `EvmHost`'s own balance as raw ETH, with no accounting for it as an app-level “bridge revenue,” and can only be extracted through the privileged `IHostManager.withdraw()` path, which is governance/`hostManager`-restricted: [4](#0-3) 

This mirrors the reported `SwapRouter` bug class exactly: ETH sent for a swap that is not fully consumed is not returned to the sender who paid it, leading to loss of user funds. The same codebase already recognizes and fixes this exact pattern elsewhere: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged user calling `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native-token payment and providing `msg.value` greater than the true amount needed for the swap (which is common since callers must estimate the ETH amount off-chain before the swap executes on-chain, and slippage/price movement between estimation and execution can leave a surplus) permanently loses that surplus. The funds are not burned but become effectively "donated" to the protocol and can only be moved by the privileged `hostManager`, not returned to the user — a direct, permanent loss of user funds triggered from a normal, unprivileged transaction. This is a High severity issue matching the report's own severity rating for the identical bug class.

### Likelihood Explanation
This will trigger any time a user pays with native token and the swap uses less than the supplied `msg.value` (over-estimation of gas/fee input value, or beneficial price movement in the AMM). Given `dispatch()` and `fundRequest()` are the primary entry points for paying Hyperbridge messaging fees in native token as documented, this is a routine call path, not an edge case — every native-token payer is exposed unless they compute `msg.value` with perfect precision matching the exact on-chain AMM price at execution time.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` (as `IntentGatewayV2.sol` and `ExtrinsicIntents.sol` already do), compute the ETH actually spent (`amounts[0]`), and refund any remaining `msg.value - amounts[0]` back to `_msgSender()` via a low-level call at the end of the function, mirroring the `_sendValue(msg.sender, msgValue)` pattern already used elsewhere in the codebase.

### Proof of Concept
1. Configure `EvmHost` with a real Uniswap V2 router/WETH/feeToken pair.
2. Call `dispatch(DispatchPost{fee: X, ...})` with `msg.value = 2 * expectedEthForFee` (an over-estimate, e.g. due to slippage buffer or price movement between quote and execution).
3. `swapETHForExactTokens` spends only the ETH required to acquire `X` feeToken and refunds the rest to `address(this)` (`EvmHost`).
4. Observe that `address(EvmHost).balance` increases by the unspent amount, while `_msgSender()`'s balance decreases by the full `msg.value`, not just the amount actually needed — the difference is unrecoverable by the user, contrasting with the `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` test in `IntentGatewayV2Test.sol` which verifies the correct, safe behavior for the same swap pattern elsewhere in the codebase.
