## Analog Found

### Title
Unbounded ABI `bytes` signature field causes a `copy_from_slice` panic (DoS) in BEEFY consensus proof conversion - (File: `evm/rust/src/conversions.rs`)

### Summary
The Ghostscript CVE is a fixed-size buffer overflow triggered by attacker-controlled input reaching an unchecked memory copy. The Hyperbridge analog is the `From<Vote> for SignatureWithAuthorityIndex` conversion, which copies an ABI-decoded, attacker-controlled dynamic `bytes` field into a fixed 65-byte array with `copy_from_slice` and no length check.

### Finding Description
`ismp-abi`'s `conversions.rs` reconstructs the SCALE `beefy_verifier_primitives` types from Solidity ABI-decoded proof structs so that on-chain code (and off-chain provers) can consume EVM-encoded BEEFY proofs: [1](#0-0) 

`signature: TSignature = [0u8; 65]` is filled via `signature.copy_from_slice(&sig_bytes)`, where `sig_bytes = value.signature.to_vec()` comes straight from the decoded `Vote.signature` field. `Vote` is imported from the generated `ecdsa_beefy::Beefy` bindings [2](#0-1)  — Solidity has no fixed `bytes65` type, so ECDSA signatures are represented as dynamic `bytes`, which places no length constraint on the ABI decoder. `copy_from_slice` panics if the source slice length does not exactly equal the destination array length (65), unlike the sibling checks elsewhere in the same file that use `.try_into()` with `.expect(...)` guarded by prior validation, or the explicitly hardened `WithdrawalParamsError::InvalidBeneficiaryAddressLength` pattern seen in `evm/rust/src/host_params.rs`.

This conversion sits directly on the reachable path from a permissionless extrinsic: `pallet-beefy-consensus-proofs::verify_and_apply` ABI-decodes a `BeefyConsensusProof` from raw `proof` bytes supplied by any relayer via `submit_proof`, then converts it into the SCALE proof with `.into()`: [3](#0-2) 

`abi_proof.into()` walks `BeefyConsensusProof -> ConsensusMessage -> RelayChainProof -> MmrProof`, and `MmrProof`'s constructor maps every vote through `Into::into`: [4](#0-3) 

Since `abi_decode_params` places no restriction on the length of a Solidity `bytes` field, an attacker can craft a `Vote.signature` of any length other than 65 (e.g., 0 or 64 bytes) that still decodes successfully at the ABI layer, and the panic fires downstream inside `copy_from_slice` during the type conversion — before signature verification is ever reached.

### Impact Explanation
A panic inside `verify_and_apply`, called from an unsigned/permissionless dispatchable (`submit_proof`), traps block/extrinsic execution. Depending on how the pallet's error handling wraps this call, this is either a caught error (harmless) or an unrecoverable Wasm trap that can halt processing of that extrinsic/block — a denial-of-service on the BEEFY consensus-update path used by relayers to keep the light client (and therefore all downstream message delivery) synced. This matches the "route unable to deliver messages" acceptance criterion: if the panic is not gracefully caught by the runtime's dispatch machinery, an attacker can permanently or repeatedly block consensus updates, freezing all messages that depend on fresh consensus/state commitments.

### Likelihood Explanation
High trigger reliability, low cost: `submit_proof` is described as reachable by any signed account (`submit_signed(..., Keyring::Bob)` in the simulation tests) with no special privilege, and constructing an ABI payload with an arbitrary-length dynamic `bytes` field requires no cryptographic work — the check happens before/independent of signature verification. Every other similarly-shaped conversion in the same repo has been hardened with explicit length checks and typed errors (e.g., `modules/ismp/core/src/host.rs`, `modules/utils/serde/src/lib.rs`, `evm/rust/src/host_params.rs`), which indicates the maintainers are aware of and have systematically patched this exact bug class elsewhere, but this specific site in `conversions.rs` was missed.

### Recommendation
Validate `value.signature.len() == 65` before calling `copy_from_slice`, returning a typed conversion error (mirroring `WithdrawalParamsError::InvalidBeneficiaryAddressLength`) instead of panicking; propagate that error through `BeefyConsensusProof -> ConsensusMessage -> RelayChainProof -> MmrProof` conversions as a `TryFrom` chain, and have `pallet-beefy-consensus-proofs::verify_and_apply` map it to `Error::<T>::AbiDecodeFailed` (consistent with its existing error handling for malformed ABI payloads).

### Proof of Concept
1. Craft a `BeefyConsensusProof` (Solidity ABI struct) where `signedCommitment.votes[0].signature` is a `bytes` value of length ≠ 65 (e.g., 64 or 66 bytes) — this still ABI-decodes successfully since `bytes` has no fixed length.
2. Prefix the ABI-encoded payload with `PROOF_TYPE_NAIVE` and submit it via the `BeefyConsensusProofs::submit_proof` extrinsic from any signed account, as done in the existing test harness at `parachain/simtests/src/pallet_beefy_consensus_proofs.rs` (lines 355-387) which already exercises malformed/oversized proof submission through this exact call.
3. `verify_and_apply` decodes the ABI payload and calls `.into()`, which reaches `From<Vote> for SignatureWithAuthorityIndex::copy_from_slice` with a mismatched-length slice, causing a runtime panic instead of the expected `Error::<T>::AbiDecodeFailed`.

**Confidence note**: I was not able to directly inspect the generated `ecdsa_beefy.rs` Solidity binding to confirm the exact declared type of `Vote.signature` (dynamic `bytes` vs. some other representation) before running out of tool iterations — this is inferred from the import of `alloy_primitives::Bytes` in `conversions.rs` and the absence of a fixed-size Solidity byte type for 65-byte ECDSA signatures. A Devin session with full file access should confirm this field's exact ABI type in `evm/rust/src/generated/ecdsa_beefy.rs` before treating this as final.
