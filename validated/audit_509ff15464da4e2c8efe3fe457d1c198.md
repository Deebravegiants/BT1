### Title
Webhook shop-domain identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-verifiable payload solely from the raw request body, while the `shop` (tenant identity) is read from the `x-shopify-shop-domain` header, which is **not** included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC-over-body and then dispatches the handler with the caller-supplied, unauthenticated `shop` value. This breaks the equality that should hold: `hmac_signed_bytes == bytes_that_determine_tenant_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that plays no part in that signable string: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC using `verifiable_query.to_signable_string` (i.e. only the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates dispatch solely on this HMAC check, then builds `WebhookMetadata` using the unauthenticated `request.shop`, which is handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

Because the secret (`Context.api_secret_key`) is shared across every shop that installs the app (it's an app-level secret, not a per-shop one), any merchant who has installed the app can obtain a genuinely HMAC-signed webhook body/signature pair for their own shop (either by triggering a real event or via Shopify's webhook-testing tools). That signed `(raw_body, hmac)` pair remains valid for **any** `shop-domain` header value, since the header is never part of the signed bytes. An attacker can therefore replay the untouched body and HMAC to the app's public webhook endpoint while substituting an arbitrary victim shop's domain in `x-shopify-shop-domain`. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` calls the app's handler with `shop: <victim-shop>` alongside attacker-chosen `body` content, spoofing a cross-tenant webhook event.

This is exactly the "field acted on but not covered by the HMAC" pattern: the shop identity used downstream to route/attribute the webhook is disjoint from the identity actually authenticated by the signature.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `request.shop`) to select which tenant's data to update — e.g. processing `app/uninstalled`, `shop/update`, `orders/create`, GDPR/mandatory webhooks, or any custom topic — can be tricked into acting on behalf of a shop the attacker does not control, using a payload the attacker fully controls (from their own genuine, differently-topic-consistent delivery). This is a cross-tenant boundary break driven purely by an unauthenticated header value standing in for the shop identity that the HMAC was supposed to bind.

### Likelihood Explanation
Exploitability only requires: (1) the attacker installs the app on their own shop (or otherwise obtains one genuine signed webhook body+HMAC pair for any topic the app subscribes to), and (2) the app's webhook endpoint is reachable over the internet, which is a documented requirement for all Shopify webhook consumers using this gem. No access token, `api_secret_key`, or privileged access is needed — only the ability to receive/capture one legitimate webhook delivery, a capability available to any merchant.

### Recommendation
Include the tenant-identifying header(s) — at minimum `x-shopify-shop-domain` — in the signable string used for webhook HMAC verification, or otherwise cryptographically bind shop identity to the signed payload before it's exposed to consuming apps via `WebhookMetadata`. Until fixed, document that `WebhookMetadata#shop` must not be trusted as authenticated and that consuming apps must independently verify shop identity (e.g., cross-reference against an existing stored session) before acting on webhook data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, enabling a webhook topic the app registers.
2. Shopify delivers a genuine webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — note `B`/`H` never reference `attacker-shop.myshopify.com` since `to_signable_string` only serializes the body: [1](#0-0) 
3. Attacker replays a forged HTTP POST to the app's public webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H`: [5](#0-4) 
5. `Registry.process` dispatches the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, spoofing an event for a tenant the attacker never authenticated as: [4](#0-3)
