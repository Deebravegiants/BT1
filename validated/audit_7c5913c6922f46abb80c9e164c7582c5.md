Audit Report

## Title
Sensitive fields (passwords/secrets) nested inside JSON request bodies are logged in cleartext due to non-recursive redaction - ([File: core/web/router.go])

## Summary
The Gin request-logging middleware `loggerFunc` in `core/web/router.go` logs every incoming HTTP request body at debug level after "sanitizing" it via `readSanitizedJSON`. That function only inspects top-level keys of the JSON body, so any sensitive field nested inside an object—such as GraphQL `variables.input.oldPassword`/`newPassword` sent to the authenticated `POST /query` endpoint—is written to the log in cleartext.

## Finding Description
`loggerFunc` buffers the full request body and passes it to `readBody` → `readSanitizedJSON` for logging at `Debug` level: [1](#0-0) . `readSanitizedJSON` unmarshals the body into a flat `map[string]any` and only checks top-level keys against `isBlacklisted`, never recursing into nested maps: [2](#0-1) . The blacklist itself is a small hardcoded set of password-related keys plus a substring check for `"password"`, with no coverage for "secret", "token", or similar sensitive names: [3](#0-2) . The `POST /query` GraphQL endpoint, protected only by `auth.AuthenticateGQL` (i.e., reachable by any authenticated, unprivileged session), wraps all mutation inputs under `variables`, one or more levels below the top level: [4](#0-3) . The `UpdatePasswordInput` GraphQL type used by the self-service `updateUserPassword` mutation carries `oldPassword`/`newPassword` fields exactly at that nested location: [5](#0-4) . Because `readSanitizedJSON` never descends into `variables.input`, these values are logged unredacted whenever debug logging is enabled.

## Impact Explanation
This is a confidentiality/secret-exfiltration issue: an authenticated but otherwise unprivileged user's own plaintext old/new password (submitted through a completely normal, self-service GraphQL mutation) ends up recorded in cleartext in node debug logs. Anyone with read access to those logs (log aggregation, support/troubleshooting workflows, crash dumps) can recover the password. This maps to the in-scope "key/secret exfiltration" impact category, since sensitive authentication material is disclosed due to a redaction defect in code, not due to log/host access misconfiguration by itself — the underlying defect is that the sanitizer is non-recursive and incomplete.

## Likelihood Explanation
The vulnerable code path is triggered by any standard authenticated request to `/query` carrying a nested sensitive field — no special role or privilege beyond a normal user session is required, and `updateUserPassword` is exactly the kind of self-service mutation ordinary users invoke to change their own password. The only condition is that debug-level logging is active, which is a common operational configuration, not an artificial precondition. This is fully reproducible and repeatable via a single crafted HTTP request.

## Recommendation
Modify `readSanitizedJSON` (and `redact` for query-string values) to recursively walk nested maps/slices and redact any key matching the blacklist at any depth. Expand the blacklist to cover generic secret-like key names (e.g., `secret`, `token`, `apikey`, `accesskey`) in addition to password variants, or switch to an allow-list approach for what is permitted to be logged from GraphQL mutation payloads.

## Proof of Concept
1. Enable debug logging on the node (a supported/common operational configuration).
2. As an authenticated user, `POST /query` with:
```json
{
  "query": "mutation($input: UpdatePasswordInput!) { updateUserPassword(input: $input) { ... } }",
  "variables": {
    "input": {
      "oldPassword": "MyOldSecretPassw0rd!",
      "newPassword": "MyNewSecretPassw0rd!"
    }
  }
}
```
3. Inspect the node's debug log output produced by `loggerFunc`/`readSanitizedJSON`. Since `oldPassword`/`newPassword` are nested under `variables.input` rather than at the top level, `isBlacklisted` never sees them and they appear in cleartext in the logged `"body"` field.
4. A Go unit test asserting `readSanitizedJSON` on a payload with `{"variables":{"input":{"oldPassword":"x"}}}` returns the value unredacted (contrasted with a top-level `{"password":"x"}` payload, which is redacted) would concretely demonstrate the defect.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

		}
