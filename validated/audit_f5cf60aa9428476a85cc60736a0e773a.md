### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the shop identity (`shop-domain`) used by `ShopifyAPI::Webhooks::Registry.process` to attribute the event to a tenant is read directly from an HTTP header that is never included in the signed bytes. Any unprivileged actor who can obtain one valid `(body, hmac)` pair for the shared app `client_secret` (trivially available to any merchant who has legitimately installed the app on their own store) can replay that body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will treat the forged request as authentic and attribute it to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` is what `HmacValidator` hashes and compares against the received HMAC: [1](#0-0) 

Specifically: [2](#0-1) 

`hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `to_signable_string` returns only `@raw_body`: [3](#0-2) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read straight from unauthenticated headers: [4](#0-3) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e. the body) against the HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [5](#0-4) 

`Registry.process` relies exclusively on this HMAC check before trusting `request.shop` as the tenant identity passed to the handler: [6](#0-5) 

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared by the app across **every** shop that installs it (it is not a per-shop secret), a genuine, unprivileged merchant who installs the app on their own shop can trigger a real webhook and obtain a valid `(body, hmac)` pair for content they fully control. They can then replay that exact `body`/`hmac` pair to the app's public webhook endpoint while setting `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to a victim shop's domain. `HmacValidator.validate` still succeeds because it never checked the shop header, so `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`. This breaks the identity binding: `shop authenticated (bound by HMAC) == shop used by the handler as the session/tenant key`. In truth `shop` is never bound by the HMAC at all.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker with no privileges beyond installing the app on their own store can forge webhook events that the app attributes to an arbitrary victim shop. Any consuming application that uses `WebhookMetadata#shop` (as the docs/tests show is the intended usage — `data.shop`) to look up the victim's session/access token, update the victim's local records, or trigger tenant-scoped business logic will act on attacker-controlled data believing it originated from the victim, i.e. cross-tenant access/injection. This matches the Critical impact bucket ("cross-tenant access").

### Likelihood Explanation
High. No credentials, TLS interception, or social engineering are required beyond installing the app on the attacker's own shop (something any user can normally do for install-anywhere apps), which yields a legitimate `(body, hmac)` pair signed with the shared `client_secret`. The header spoofing itself is a single HTTP request with a modified `Shop-Domain` header sent directly to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the signed content, or otherwise cryptographically verify it, before trusting `request.shop`:
- Extend `to_signable_string` (or add a dedicated check in `HmacValidator`/`Registry.process`) to incorporate the `shop-domain` header (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, matching what Shopify actually signs, or
- Require applications to cross-check `request.shop` against the shop associated with the currently stored session/access token before processing, rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Attacker triggers any webhook subscription (e.g. `products/create`) on their own store, capturing the raw POST body `B` and the corresponding `X-Shopify-Hmac-Sha256: H` header sent by Shopify (computed with the app's shared `client_secret`).
3. Attacker sends a new POST request directly to the app's webhook endpoint with:
   - Body: the same `B`
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it signs `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
   - Header `X-Shopify-Topic`/`X-Shopify-Webhook-Id` optionally altered too.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds.
5. The app's registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data is processed as if it came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
