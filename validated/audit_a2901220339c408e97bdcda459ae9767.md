### Title
Unbacked cross-chain mint from deflationary/fee-on-transfer underlying tokens in `WrappedHyperFungibleToken.send()` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain message encoding the *requested* `params.amount`, without ever checking how much the contract actually received. If the configured `_underlying` token burns or deducts a fee during `transfer()`/`transferFrom()` (a fee-on-transfer or burn-on-transfer token — exactly the bug class in the referenced Fire ($FIRE) incident, where a flawed burn mechanism inside `transfer()` was exploited), the contract escrows less than `params.amount` while the peer `HyperFungibleToken` on the destination chain mints the full, unreduced `params.amount`. This creates unbacked supply on the destination chain that is not backed by the locked collateral on the home chain.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params);
``` [1](#0-0) 

`_buildDispatchPost` encodes `params.amount` verbatim into the cross-chain `Message.amount` field: [2](#0-1) 

There is no balance-before/balance-after comparison to determine the *actual* amount locked, unlike the sibling `IntentGatewayV2` contract, which explicitly guards against this exact class of token by measuring `balanceOf` deltas around transfers: [3](#0-2) 

On the destination chain, `HyperFungibleToken.onAccept()` mints exactly `message.amount` to the beneficiary with no knowledge of what was actually escrowed on the home chain: [4](#0-3) 

Because `WrappedHyperFungibleToken` is the home-chain custodian holding the real underlying reserve for the entire multi-chain HFT topology (Ethereum `WrappedHFT` ↔ remote `HFT` mint/burn peers), any shortfall between locked collateral and minted supply directly reduces the pool available to back legitimate redemptions across all remote chains.

### Impact Explanation
Every `send()` call against a deflationary/burn-on-transfer/fee-on-transfer underlying token mints the destination-chain `HyperFungibleToken` supply in excess of what is actually custodied by `WrappedHyperFungibleToken`. This is an unbacked-mint condition: the attacker (or any regular user, even unintentionally) receives full-value minted tokens on the destination chain while only a reduced amount was locked at home. As usage accumulates, later users attempting to bridge back and unlock their share of the underlying will find insufficient collateral in the home contract — resulting in theft of the discrepancy for early actors and permanent freezing of funds for later redeemers. This satisfies the "unbacked mint" / "theft of funds" impact criteria for token bridge mint/burn paths.

### Likelihood Explanation
The path is reachable by any unprivileged user calling the public `send()` function with a single transaction — no privileged role is required. The only precondition is that the token owner configures `_underlying` to an ERC20 with a fee-on-transfer or burn-on-transfer mechanism (a common token category, and precisely the bug class described in the Fire ($FIRE) incident). The codebase itself demonstrates awareness of this exact risk in `IntentGatewayV2` (which has dedicated fee-on-transfer tests, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), showing the mitigation is a known necessary pattern that `WrappedHyperFungibleToken` omits.

### Recommendation
In `WrappedHyperFungibleToken.send()`, measure the actual amount received by comparing `balanceOf(address(this))` before and after the `safeTransferFrom` call (as already done in `IntentGatewayV2`), and encode that actual received amount into the dispatched `Message`, rather than the caller-supplied `params.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.sol` if it shares this pattern.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that burns 5% of every transferred amount (a `FeeOnTransferToken`-style contract, as used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2735).
2. User calls `send({amount: 1000, dest: remoteChain, to: attacker, ...})`.
3. `safeTransferFrom` moves only 950 tokens into the contract (50 burned by the token's own transfer logic), but `_buildDispatchPost` encodes `Message.amount = 1000`.
4. Once the ISMP request is delivered, the remote `HyperFungibleToken.onAccept()` mints 1000 tokens to `attacker`, even though only 950 units of real collateral were locked on the home chain.
5. Attacker can now bridge the full 1000 minted tokens back to another chain or redeem via a different route, extracting the extra 50-unit shortfall from the shared collateral pool — repeatable to drain the reserve or cause later legitimate users' unlocks to revert due to insufficient underlying balance.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
