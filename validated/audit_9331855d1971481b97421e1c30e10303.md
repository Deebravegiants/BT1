This confirms the claim's core technical premise. `msg.Body.MessageID` is set directly from the caller-controlled `jsonrpc2.Request.ID` (`request.ID`) in `DecodeJSONRequest` [1](#0-0) , and `Message.Validate()` only checks length/null-suffix on `MessageID` — it never ties `MessageID` to `Sender` or enforces uniqueness [2](#0-1) . `HandleLegacyUserMessage` then unconditionally overwrites `h.savedCallbacks[msg.Body.MessageID]` with no existence check [3](#0-2) , and `handleWebAPITriggerMessage` looks up/deletes/delivers strictly by that same attacker-chosen `MessageID` key [4](#0-3) . The map itself is `map[string]*savedCallback` keyed only by string ID, with no sender component in the key [5](#0-4) . This contrasts with `RequestCache.NewRequest`, which explicitly keys on `(Sender, MessageID)` and rejects duplicates [6](#0-5) , and with the v2 JWT-based trigger handler which prevents ID reuse [7](#0-6) .

The exploit path is directly reachable by two unprivileged clients: both send ordinary legacy `web_api_trigger` requests to the gateway's HTTP endpoint with the same JSON-RPC `id`. Client B's request overwrites client A's map entry before any DON response arrives, and when a node responds, the response is delivered to B's connection instead of A's — a genuine cross-user response confusion. `Message.Validate()` calls `ExtractSigner` and computes `Sender` [8](#0-7) , but this signer identity is never used to scope or check the `savedCallbacks` map key, so the check is present but insufficient to prevent the collision — the security assumption is broken exactly as claimed.

Audit Report

## Title
Unprivileged client can hijack another user's pending Gateway callback via colliding `MessageID` (cross-user response confusion) - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The legacy `capabilities.handler.HandleLegacyUserMessage` stores pending callbacks in `h.savedCallbacks` keyed only by the caller-supplied `MessageID`, with no uniqueness or sender-scoping check, unlike `RequestCache.NewRequest` which explicitly rejects duplicate `(Sender, MessageID)` pairs elsewhere in the gateway. Two unprivileged clients submitting requests with the same `MessageID` can cause one client's pending request to be silently overwritten, so the DON's eventual response is delivered to the wrong caller's connection.

## Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request and sets `msg.Body.MessageID = request.ID` directly from the caller-supplied JSON-RPC `id` field [1](#0-0) , subject only to a length check (`<= 200` chars) in `ProcessRequest` [9](#0-8)  and `Message.Validate()`'s length/null-suffix checks, which never tie `MessageID` uniqueness to `Sender` [2](#0-1) .

`HandleLegacyUserMessage` then unconditionally writes into the shared map: `h.savedCallbacks[msg.Body.MessageID] = &savedCallback{...}` with no check for an existing entry [3](#0-2) . Later, when a DON node responds, `handleWebAPITriggerMessage` looks up and deletes the entry by `MessageID` alone and sends the response to whatever callback currently occupies that slot [4](#0-3) . Because the map type is `map[string]*savedCallback` (keyed only on the raw ID string, not sender) [5](#0-4) , a second unprivileged client choosing the same `MessageID` as a victim's still-pending request will overwrite the victim's callback, causing the DON's response to be delivered to the attacker instead of the victim.

This is a real gap: the codebase demonstrably knows how to prevent this class of bug (`RequestCache.NewRequest` rejects duplicate `(sender, MessageID)` with `"request already exists"` [6](#0-5) , and the v2 HTTP trigger handler rejects ID reuse via JWT-bound tracking [7](#0-6) ), but the legacy `HandleLegacyUserMessage` path has no equivalent protection.

## Impact Explanation
An unprivileged client can cause another unprivileged user's Gateway response (routed through the legacy `web_api_trigger` capability path) to be delivered to the attacker's own HTTP connection instead, while the victim's request is silently dropped until pruned (default max age 120s, per `defaultCallbackMaxAgeSec` [10](#0-9) ). This is a cross-user response confusion, which maps to an in-scope Chainlink impact category (potential information disclosure plus availability impact on the victim's request).

## Likelihood Explanation
Exploitation only requires two ordinary unauthenticated/unprivileged HTTP requests to the gateway with the same client-chosen JSON-RPC `id`, timed so the attacker's request lands after the victim's but before the DON responds — well within the default 120-second callback window and the 20000-entry capacity (`defaultMaxSavedCallbacks`) [10](#0-9) . No credentials, roles, or special network position are required; the attacker just needs to guess or race to collide with a victim's `MessageID`, which is plausible in scenarios where IDs are predictable (sequential counters, low-entropy client-generated IDs) or where an attacker can flood many IDs to win the race.

## Recommendation
Key `h.savedCallbacks` by a composite that includes the verified `Sender` (populated during `Message.Validate()`'s `ExtractSigner` call) together with `MessageID`, e.g. `savedCallbacks[senderAddr+"|"+messageID]`, or reject `HandleLegacyUserMessage` outright if an entry already exists for that key — mirroring `RequestCache.NewRequest`'s `"request already exists"` behavior. Longer term, migrate this legacy handler onto the same `RequestCache` abstraction already used and hardened elsewhere in the gateway.

## Proof of Concept
1. Craft two signed legacy `web_api_trigger` JSON-RPC requests with different signers/senders but the identical `id`/`MessageID` value (e.g., `"X"`).
2. Submit request A to the gateway's HTTP endpoint; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards to DON nodes [11](#0-10) .
3. Before any DON node replies, submit request B with the same `id = "X"`; this overwrites `savedCallbacks["X"] = callbackB`.
4. Have a DON node (or a test harness driving `HandleNodeMessage`) respond with `MessageID = "X"`; verify via unit test that `handleWebAPITriggerMessage` delivers the response to `callbackB`, not `callbackA` [4](#0-3) .
5. A Go test in `core/services/gateway/handlers/capabilities/handler_test.go` calling `HandleLegacyUserMessage` twice with the same `MessageID` and two distinct `handlers.Callback` mocks, then invoking `HandleNodeMessage` with a matching node response, can assert that `callbackA.SendResponse` is never called while `callbackB.SendResponse` is called — directly demonstrating the cross-user delivery.
