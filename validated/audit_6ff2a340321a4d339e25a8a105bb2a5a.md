### Title
`transfer_assert_minimum_deposit` measures raw store balance instead of the dispatched `derived_balance`, silently defeating its own slippage guarantee for custom fungible-asset hooks - (File: `aptos-move/framework/aptos-framework/sources/dispatchable_fungible_asset.move`)

### Summary
`dispatchable_fungible_asset::transfer_assert_minimum_deposit` is the framework's answer to exactly the class of bug in the Olympus report: a caller specifies an `expected` amount they must receive, and the function is supposed to guarantee that the recipient actually ends up with at least that much value after any custom withdraw/deposit hook logic runs. However the check is implemented using the raw internal store accounting (`fungible_asset::balance`) rather than the dispatched/derived balance (`dispatchable_fungible_asset::derived_balance`) that the same module explicitly exposes for tokens whose real economic value diverges from their raw stored amount (rebasing, deflationary, or "clamped" tokens, as documented in the module's own comments and test fixtures). [1](#0-0) 

### Finding Description
The module's own doc comment states its purpose is to let issuers "customize the logic for withdraw and deposit operations," explicitly listing deflation tokens and other value-distorting hooks as intended use cases. [2](#0-1) 

To let external code observe the *real* economic value of a store when a hook exists, the module exposes `derived_balance`, which dispatches to the token's custom `derived_balance_function` when registered: [3](#0-2) 

The `clamped_token` test fixture demonstrates this divergence directly: it maintains a separate `BalanceStore` that is the source of truth for `derived_balance`, distinct from the amount held in the raw `FungibleStore` referenced by `fungible_asset::balance`. [4](#0-3) 

The framework itself is aware of this distinction: `primary_fungible_store::balance` (the canonical "what does this account really have" view function) deliberately calls `dispatchable_fungible_asset::derived_balance`, not the raw `fungible_asset::balance`: [5](#0-4) 

Despite this, `transfer_assert_minimum_deposit` — the one function whose entire job is to give a caller a slippage/minimum-receipt guarantee across an arbitrary deposit hook — samples the raw balance before and after, not the derived balance:

```
public entry fun transfer_assert_minimum_deposit<T: key>(
    sender: &signer,
    from: Object<T>,
    to: Object<T>,
    amount: u64,
    expected: u64
) acquires TransferRefStore {
    let start = fungible_asset::balance(to);
    let fa = withdraw(sender, from, amount);
    deposit(to, fa);
    let end = fungible_asset::balance(to);
    assert!(end - start >= expected, error::aborted(EAMOUNT_MISMATCH));
}
``` [1](#0-0) 

This is the precise structural analog of the Olympus BLVaultLido bug: a "minimum received" check that samples a value which is not the value actually accruing custody/economic benefit to the recipient. In BLVaultLido, `minTokenAmounts_` was checked against the pool-level output, while the real user-received amount was determined later by a post-check skim. Here, `expected` is checked against the raw internal store delta, while the real economic value delivered to the recipient (what wallets, DeFi integrators, and the recipient themselves would observe via `derived_balance`/`primary_fungible_store::balance`) is determined by the token's custom deposit hook, which can freely diverge from the raw store amount (e.g., mark part of the deposit as "locked", route it into an internal shadow ledger, or apply an oracle-based skim similar to BLVaultLido, all while the raw `FungibleStore.balance` field still reflects the full nominal transfer amount).

### Impact Explanation
A fungible-asset issuer (or any composing protocol built on dispatchable FA, e.g., a wrapped/synthetic asset, vault share token, or bridged asset) can register a deposit hook whose `derived_balance` legitimately reports less value than the raw store balance (this is an explicitly supported, intended pattern per the module's own tests). Any caller relying on `transfer_assert_minimum_deposit` (directly, or via `primary_fungible_store::transfer_assert_minimum_deposit`, which is the public entry point most integrators would call) to protect against receiving less value than expected gets a false sense of security: the check can pass even though the recipient's real, indexable, spendable balance (as measured by `derived_balance`) is below `expected`. This breaks the custody invariant that "the recipient's real balance must be provably preserved or exceed the minimum specified by the transacting party" across deposit hook execution — the exact invariant the Olympus finding targeted for `BLVaultLido#withdraw`. Any protocol or user that composes with a dispatchable FA whose derived balance is intentionally lower than raw balance (skim, deflation, escrow-on-deposit, etc.) can have value silently diverted while the on-chain slippage guard reports success.

### Likelihood Explanation
This requires a token/issuer that (a) uses the dispatchable fungible asset framework (a first-class, documented AIP-73 feature) and (b) registers a `derived_balance_function` that diverges from raw store balance — both are explicitly supported and demonstrated patterns in the framework's own test suite (`clamped_token.move`, `deflation_token.move`). No privileged access or unusual configuration is needed beyond normal token issuance; any third-party token creator can trigger this by design, and any user/integrator calling `transfer_assert_minimum_deposit` against such a token inherits the false guarantee. This is realistic on mainnet as more DeFi protocols adopt dispatchable/hooked fungible assets.

### Recommendation
Change `transfer_assert_minimum_deposit` (and any related "guaranteed minimum deposit" helpers) to measure `dispatchable_fungible_asset::derived_balance(to)` before and after the deposit rather than `fungible_asset::balance(to)`, so the guarantee is enforced against the value that is actually attributed to the recipient post-hook, consistent with how `primary_fungible_store::balance` already treats derived balance as the canonical balance for dispatchable stores.

### Proof of Concept
1. Deploy a fungible asset with `register_dispatch_functions` registering a custom `deposit` hook and a custom `derived_balance_function` (mirroring `clamped_token.move`'s pattern), where the deposit hook always credits the raw `FungibleStore` with the full deposited amount, but the paired `derived_balance` hook reports a value reduced by some issuer-controlled skim (e.g., tracks a separate `BalanceStore` that only credits `amount - fee`).
2. Attacker/issuer sets the skim fee such that `derived_balance` after a transfer of `amount` is less than `expected`.
3. Victim calls `dispatchable_fungible_asset::transfer_assert_minimum_deposit(sender, from, to, amount, expected)` (or the `primary_fungible_store` wrapper).
4. The check computes `end - start` from `fungible_asset::balance(to)`, which reflects the full raw amount deposited (>= `expected`), so the assertion at line 147 passes.
5. Victim's actual usable/economic balance, as reported by `derived_balance(to)` / `primary_fungible_store::balance`, is below `expected` — the slippage guarantee was violated without the on-chain check detecting it.
