### Title
Attacker can permanently DoS a program deployment by pre-funding the derived `ProgramData` PDA before `DeployWithMaxDataLen` runs - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
`UpgradeableLoaderInstruction::DeployWithMaxDataLen` creates the program's `ProgramData` account at a deterministic PDA (`Pubkey::find_program_address(&[new_program_id.as_ref()], program_id)`) using the plain `system_instruction::create_account` CPI, which unconditionally fails if the target address already holds any lamports. [1](#0-0)  Because the `ProgramData` address only depends on the (often publicly known ahead of time) `program_id`, any unprivileged user can pre-fund that address with 1 lamport before the legitimate `DeployWithMaxDataLen` transaction lands, permanently blocking the deploy — structurally the same class of bug as the Salty DAO issue, where an adversary claims a derived name/address ahead of time to block a required confirmation step of a multi-step process.

### Finding Description
The `system_processor::create_account` function used by `DeployWithMaxDataLen` rejects account creation whenever the destination already has `lamports > 0`, returning `SystemError::AccountAlreadyInUse`: [2](#0-1) 

`DeployWithMaxDataLen` derives the `ProgramData` address purely from `new_program_id` (the to-be-deployed program's own address) and invokes this exact vulnerable `create_account` path via CPI: [1](#0-0) 

Since the program address (a keypair) is frequently known before the on-chain deploy transaction executes — e.g., published in source repos, vanity-generated program IDs, audited/whitelisted ahead of mainnet launch, or simply observed once the deploy transaction is broadcast/simulated but not yet landed — any third party can send a `SystemProgram::Transfer` of as little as 1 lamport to the derived `ProgramData` PDA. When the real `DeployWithMaxDataLen` transaction subsequently executes, the CPI’s `create_account` sees `lamports > 0` and fails with `AccountAlreadyInUse`, aborting the whole deploy instruction. Because the target address is a PDA (not backed by a private key), the deployer cannot reclaim/close it and must generate an entirely new `program_id` to retry deployment — a strictly worse (permanent, non-recoverable per-address) outcome than the cyclical DoS in the referenced Salty report.

Agave engineers are aware of the class of bug: a new `SystemInstruction::CreateAccountAllowPrefund` was added specifically to tolerate "the account has already had rent paid in whole or in part before creation" scenarios, and it is gated behind the `create_account_allow_prefund` feature flag: [3](#0-2) [4](#0-3) 
Similarly, the Core BPF migration path explicitly added an `allow_prefunded` parameter so that a pre-funded `ProgramData` address does not block migration: [5](#0-4) 

However, the legacy Loader-v3 `DeployWithMaxDataLen` handler in `programs/bpf_loader/src/lib.rs` has **not** been updated to use `CreateAccountAllowPrefund`/`create_account_allow_prefund` — it still calls the strict `system_instruction::create_account`, meaning the griefing vector on program deployment remains open in this path. The CLI only mitigates a related but distinct case (excess balance on the *program account* itself, a user-controlled keypair) with a friendly pre-check error, not the `ProgramData` PDA case: [6](#0-5) 

### Impact Explanation
This blocks a legitimate, unprivileged action (deploying a new upgradeable program) with no way to recover the specific `program_id` once griefed, since the colliding account is a PDA with no signing key. This is a direct availability/DoS impact on protocol-level infrastructure (new program rollout, akin to the price-feed contract rollout blocked in the original report), fitting "prevent availability of a function of the network" style impact, though it is scoped to program deployers rather than validators.

### Likelihood Explanation
Exploitation requires only a public RPC endpoint and knowledge of an upcoming program's public key, which is commonly available before/at the moment of deployment (vanity keys, published repos, simulated-but-unlanded transactions, mempool/gossip observation). No special privileges or validator/operator role are needed — it is a plain `SystemProgram::Transfer` from any funded account. It can be launched at any time prior to the real deploy transaction landing.

### Recommendation
Update the `DeployWithMaxDataLen` (and equivalent `bpf_loader_upgradeable::deploy_with_max_program_len`) account-creation CPI in `programs/bpf_loader/src/lib.rs` to tolerate pre-funded `ProgramData` PDAs, mirroring the `create_account_allow_prefund`/`CreateAccountAllowPrefund` pattern already introduced in `programs/system/src/system_processor.rs`, instead of relying on the strict zero-lamports `system_instruction::create_account`.

### Proof of Concept
1. Determine (or vanity-generate) the target `program_id` before the deployer's `DeployWithMaxDataLen` transaction lands.
2. Compute the `ProgramData` PDA: `Pubkey::find_program_address(&[program_id.as_ref()], &bpf_loader_upgradeable::id())`.
3. Submit a `SystemProgram::Transfer` of 1 lamport from any funded account to that PDA address.
4. When the legitimate deploy transaction executes `DeployWithMaxDataLen`, the internal `system_instruction::create_account` CPI at `programs/bpf_loader/src/lib.rs:296-310` observes `lamports > 0` on the `ProgramData` account and fails with `SystemError::AccountAlreadyInUse` (per the check at `programs/system/src/system_processor.rs:160-171`), causing the entire deploy transaction to fail. The deployer cannot recover this specific `program_id` and must generate a new keypair to redeploy.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}

impl TargetBpfV2 {
    /// Collects the details of a Loader v2 BPF program and verifies it is properly
    /// configured.
    ///
    /// The program account should exist and it should be marked as executable.
    pub(crate) fn new_checked(
        bank: &Bank,
        program_address: &Pubkey,
        allow_prefunded: bool,
    ) -> Result<Self, CoreBpfMigrationError> {
        // The program account should exist.
        let program_account = bank
            .get_account_with_fixed_root(program_address)
            .ok_or(CoreBpfMigrationError::AccountNotFound(*program_address))?;

        // The program account should be owned by the loader v2.
        if program_account.owner() != &bpf_loader::id() {
            return Err(CoreBpfMigrationError::IncorrectOwner(*program_address));
        }

        // The program account should be executable.
        if !program_account.executable() {
            return Err(CoreBpfMigrationError::ProgramAccountNotExecutable(
                *program_address,
            ));
        }

        let program_data_address = get_program_data_address(program_address);

        let program_data_account_lamports = if allow_prefunded {
            // The program data account should not exist, but a system account with funded
            // lamports is acceptable.
            if let Some(account) = bank.get_account_with_fixed_root(&program_data_address) {
                if account.owner() != &SYSTEM_PROGRAM_ID {
                    return Err(CoreBpfMigrationError::ProgramHasDataAccount(
                        *program_address,
                    ));
                }
                account.lamports()
            } else {
                0
            }
        } else {
            // The program data account should not exist and have zero lamports.
            if bank
                .get_account_with_fixed_root(&program_data_address)
                .is_some()
            {
                return Err(CoreBpfMigrationError::ProgramHasDataAccount(
                    *program_address,
                ));
            }

            0
        };

        Ok(Self {
            program_address: *program_address,
            program_account,
            program_data_address,
            program_data_account_lamports,
        })
    }
