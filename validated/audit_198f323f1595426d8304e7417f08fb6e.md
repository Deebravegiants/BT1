### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only signs the raw body, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the caller a `WebhookMetadata` object whose `shop` field is read straight from the `x-shopify-shop-domain` HTTP header — a value that is never included in the HMAC computation. This breaks the intended binding `authenticated_body == data_attributed_to(shop)`, letting anyone who can obtain one valid `(body, hmac)` pair for their own shop replay it to the same endpoint with a different `shop-domain` header, causing the host app to process/attribute that payload to an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `shop` is read from headers with no cryptographic tie to the signed content: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, i.e. the body, never the shop header: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards `request.shop` (the unauthenticated header) directly into the handler as the tenant identity for the payload: [4](#0-3) 

So the equality the design implicitly promises to consumers of this API — "if `HmacValidator.validate` returns true, then `WebhookMetadata#shop` truthfully identifies the tenant that produced this body" — does not hold. The signature covers `body` only; `shop` is parsed from headers that sit entirely outside the signed byte range. Any entity that can legitimately trigger a webhook for shop A (e.g., a merchant who installed the app) receives a valid `(body, hmac)` pair computed with the shared `client_secret`. That exact pair can be re-sent to the same endpoint with the `x-shopify-shop-domain` header changed to shop B; `HmacValidator.validate` still returns `true` (it never looked at the header), and the handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-A's data>, ...)`.

### Impact Explanation
This is a cross-tenant identity-binding break: the field the application logic relies on to key per-tenant records (`shop`) is disjoint from the field the cryptographic check actually covers (`body`). An app that persists or acts on webhook data keyed by `WebhookMetadata#shop` (the pattern this gem's own API and tests encourage — see `data.shop` assertions in `test/webhooks/registry_test.rb`) can have another tenant's data attributed to, and processed under, a victim shop's identity, which is a tenant-isolation break stemming directly from this gem's HMAC/identity design.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to receive one legitimate webhook delivery for any shop (trivial for anyone who can install a public/free app, or any existing merchant of a multi-tenant app) and the ability to replay an HTTP request with a modified header, which is unprivileged internet-user activity.

### Recommendation
Bind the shop identity into the authenticated material: include the `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed string, or otherwise verify that `request.shop` matches a shop already known/authorized for this integration before constructing `WebhookMetadata`, rejecting the request if they diverge.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; trigger any webhook (e.g., `orders/create`) to obtain a legitimate `body` and its correct `x-shopify-hmac-sha256` value (computed by Shopify using the app's `client_secret`).
2. Resend that identical `(body, hmac)` pair to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` because it only checks `body` against `hmac`; `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <shop-a's payload>, ...)` and invokes the handler, which now processes/attributes shop A's data as shop B's.
