### Title
Webhook shop/topic/webhook_id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and handed to the app's webhook handler as trusted values. Since Shopify signs webhooks with the app's single shared `api_secret_key` (not a per-shop secret), any user who can get one legitimately signed webhook (e.g. by installing the app on their own store) can replay that exact body with a forged `x-shopify-shop-domain` header and have it accepted as belonging to any other shop.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` using `Context.api_secret_key` and comparing it to the value in `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `#hmac` decodes the `X-Shopify-Hmac-Sha256` header: [2](#0-1) [3](#0-2) 

Crucially, `shop`, `topic`, `webhook_id`, and `api_version` are read from separate headers that are never mixed into `to_signable_string`: [4](#0-3) 

`Registry.process` validates only this body-only HMAC and then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [5](#0-4) 

The equality the library implicitly claims to guarantee is:
`shop asserted to the handler == shop authenticated by Shopify's signature`

In reality the signature only proves:
`raw_body authenticated == raw_body received`

and says nothing about which shop, topic, or webhook id that body was associated with. Because Shopify signs all webhooks for an app using the single app-wide `api_secret_key` (the same secret is used for every merchant's shop, not a per-tenant key), a valid `(body, hmac)` pair obtained from *any* shop that has installed the app (including a shop the attacker controls, e.g. a free/trial development store) is a valid `(body, hmac)` pair for *every* shop. An attacker can therefore:
1. Install the target app on their own store (no privilege required beyond normal app installation).
2. Capture one legitimately-signed webhook request (any topic with a body they can produce, e.g. by editing/creating a resource that triggers a webhook they registered).
3. Replay the identical raw body to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) rewritten to a victim shop's domain.
4. `HmacValidator.validate` still succeeds because it only checks the untouched raw body, so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain.

Documentation explicitly instructs host apps to trust `data.shop` as the shop domain of the webhook, so this is a defect in the gem's own guarantee, not a misuse of an undocumented contract: [6](#0-5) 

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on to route webhook data to the correct merchant record. An app that uses `data.shop` (as documented) to look up/act on a specific shop's session, data, or credentials can be made to attribute attacker-controlled webhook content (order data, product data, app-uninstall events, etc.) to an arbitrary victim shop, resulting in cross-tenant data corruption/injection — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
The only prerequisite is obtaining one valid `(body, hmac)` pair signed with the app's `api_secret_key`, which any unprivileged user can do by installing the target app on a store they control (e.g. a free Shopify partner/dev store) and triggering any webhook. No access to the victim's tokens, the app's `client_secret`, or privileged access is required, making this practically exploitable by any internet user willing to install the app once.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content, or otherwise cryptographically bind them to the payload before computing/verifying the HMAC, so that `Request#to_signable_string` can't be satisfied by a body signed for a different shop/topic. At minimum, document and provide a way for consuming apps to independently confirm that the shop in a webhook request matches a shop that has an active, expected installation/session prior to trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the exact raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H`, both signed with the app's shared `api_secret_key`.
3. Attacker POSTs to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally forged too
4. `Utils::HmacValidator.validate` succeeds because it only re-derives the HMAC from `B`, ignoring the forged headers: [7](#0-6) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, and the host app processes attacker-supplied content as if it belonged to the victim tenant.
