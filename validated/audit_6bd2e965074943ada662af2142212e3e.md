## Analysis Summary

The external report's bug class is: **a validation check that doesn't actually enforce the invariant it's supposed to guard**, causing behavior other than what the check implies. I traced this to `aptos_framework::multisig_account`, where the on-chain payload-consistency check for multisig transaction execution is **feature-gated and conditionally skipped**, breaking the multisig custody invariant that "the executed action must be the one approved by quorum."

### Title
Multisig transaction execution can diverge from the quorum-approved payload when full payload is stored on-chain - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` is the VM prologue check that gates execution of a `MultisigTransaction`. For transactions created via `create_transaction` (full payload stored on-chain, `payload_hash = None`), the function only verifies that the payload actually being executed matches the approved, stored payload if the feature `abort_if_multisig_payload_mismatch_enabled` is turned on [1](#0-0) . If that feature is not enabled, and the transaction was created without a hash (so the `payload_hash.is_some()` branch is skipped too), there is no code path in this function that actually enforces that the payload used at execution equals what the owners voted on.

### Finding Description
The multisig quorum flow votes on and approves a specific transaction payload stored via `create_transaction` (full payload) or `create_transaction_with_hash` (hash only) [2](#0-1) . Execution authority is granted purely by vote count (`can_execute` / `can_be_executed`) [3](#0-2) , and only afterwards does the code attempt to verify the payload content itself:

```
// hash-only case: unconditionally enforced
if (transaction.payload_hash.is_some()) {
    assert!(sha3_256(payload) == *payload_hash, ...);
};

// full-payload case: only enforced behind a feature flag AND only if payload is non-empty
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
``` [1](#0-0) 

For the "full payload stored" path (`create_transaction`), `payload_hash` is `option::none`, so the first, unconditional check is skipped entirely [4](#0-3) . The second check — the only remaining safeguard — is gated by the `abort_if_multisig_payload_mismatch_enabled` feature flag. If that flag is not enabled on a given network/deployment, an executing owner can supply a `transaction_payload` for the outer `Multisig` transaction that differs entirely from what was approved by the other owners, and `validate_multisig_transaction` will not detect the mismatch, because the only comparison that could catch it is disabled.

The very existence of this feature as an opt-in flag (rather than being baked in unconditionally) strongly indicates it was added specifically to close a gap where the actually-executed payload was not being verified against the approved one for the "full payload on-chain" creation path.

### Impact Explanation
This breaks the "Multisig-owned assets... must not leak upgrade, freeze, or transfer authority to unprivileged callers" custody invariant. A single owner who is one of the required signers (or who colludes to get enough approvals on an innocuous-looking transaction, e.g., "transfer 1 APT to owner_1") can, at execution time, submit a completely different `transaction_payload` (e.g., "transfer entire multisig balance to attacker") when `abort_if_multisig_payload_mismatch_enabled` is disabled and the transaction was created without a hash. This can result in outright theft/drain of APT or fungible-asset balances held by the multisig-controlled resource account, or unauthorized reassignment of owner/authority if the payload calls `add_owners`/`swap_owner`/`update_signatures_required`. This is a critical custody impact: unauthorized transfer of multisig-held value without genuine quorum consent for the actually-executed action.

### Likelihood Explanation
Likelihood is directly tied to whether `abort_if_multisig_payload_mismatch_enabled` is active on the target network. I was not able to confirm the current default/enabled status of this feature flag on mainnet within the available search budget — this needs verification via `aptos_framework::features` on-chain state or `types/src/on_chain_config/aptos_features.rs`. If the flag is disabled by default (which its being an explicit, separately-named opt-in feature suggests it may not universally be turned on for older or non-upgraded deployments), the attack requires no privileged access beyond being one of the multisig owners who can get their proposal past quorum and then be the one to submit the final execution transaction — an unprivileged-relative-to-custody-control action within the multisig's own governance model, but one that should never permit unilateral payload substitution.

### Recommendation
Make payload verification for the "full payload stored on-chain" case unconditional (not feature-gated), i.e., always assert `payload == *stored_payload` whenever `transaction.payload.is_some()`, regardless of `abort_if_multisig_payload_mismatch_enabled` and regardless of whether the caller-supplied `payload` is empty. If an empty payload is submitted for a transaction with a stored payload, the VM should be required to substitute the stored payload for execution rather than silently proceeding without a comparison.

### Proof of Concept
Conceptual (requires runtime/VM confirmation of exact payload plumbing, which could not be fully traced in the available search budget):
1. Owner A creates a 2-of-3 multisig transaction via `create_transaction` with an innocuous payload P1 (e.g., transfer 1 APT to A).
2. Owners A and B approve, reaching quorum (`can_be_executed` returns true) based on vote count only.
3. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, Owner A submits the final execution transaction as `Multisig { multisig_address, transaction_payload: Some(P2) }` where P2 drains the full multisig balance to A's own address.
4. `validate_multisig_transaction` skips the `payload_hash` check (none was stored) and skips the payload-match check (feature disabled), so the execution proceeds with P2 instead of the approved P1.

**Caveat:** I could not fully verify, within the tool-call budget, whether the Move VM's execution dispatch for `MultisigTransactionPayload` always uses the transaction's own `transaction_payload` field for both validation and execution (which is the scenario that makes this exploitable) or whether it separately substitutes the on-chain stored payload for execution regardless of what's supplied for validation. This distinction is critical to confirming exploitability and should be verified against `aptos-move/aptos-vm/src/aptos_vm.rs` and `types/src/transaction/multisig.rs` before treating this as fully confirmed.
