This confirms the vulnerability. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `HmacValidator.validate` only checks that body string against the secret [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from unauthenticated HTTP headers [3](#0-2)  and are trusted directly by `Registry.process`, which passes `request.shop` into the `WebhookMetadata` given to the app's handler once HMAC validation of the body passes [4](#0-3) .

### Title
Webhook tenant (shop) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw request body only. The `shop-domain`, `topic`, `api_version`, and `webhook_id` header values — which are the only tenant-identifying fields the host application receives and forwards to its webhook handler — are never part of the signed bytes. Anyone who can obtain one genuine `(body, hmac)` pair signed with the app's shared `client_secret` can replay that exact body to the app's public webhook endpoint with an arbitrary `shop-domain` header, and the library will report the webhook as valid and hand the data to the handler under the attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`HmacValidator.validate` computes the HMAC only over that signable string and compares it to the `hmac-sha256` header: [5](#0-4) 

Meanwhile, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Webhooks::Registry.process` validates only the body's HMAC and then immediately trusts `request.shop`/`request.topic`/etc. to build the `WebhookMetadata` delivered to the app's handler: [4](#0-3) 

This breaks the identity binding `shop header == shop that produced the signed body`. Since a single app's `client_secret` is shared across every shop that installs it, any developer/attacker who installs the app on their own store legitimately receives correctly-HMAC-signed webhook deliveries for their own shop. They can then POST that exact `raw_body` + `hmac-sha256` value directly to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim shop). `HmacValidator.validate` still passes because it never inspected the header, and `Registry.process` attributes the (attacker-controlled) body to the spoofed shop.

### Impact Explanation
This is a cross-tenant identity confusion: an app that uses `WebhookMetadata#shop` (or `request.shop`) to select which tenant's data/session/record to update will act on behalf of the wrong tenant using attacker-supplied content, i.e., cross-tenant data injection/corruption. Per the classification this maps to "cross-tenant access," a Critical-severity outcome, since the gem hands the host application data that appears authenticated but is not actually bound to the claimed shop.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any Shopify store (no special privilege, any developer/merchant account works), which yields a legitimate signed webhook body/HMAC pair for topics the attacker's own actions can trigger (e.g., `orders/create`), and (2) sending a direct HTTP POST to the app's known/discoverable webhook callback URL with a forged `shop-domain` header. No access to `api_secret_key`, no TLS interception, and no social engineering are required, matching the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the tenant-identifying headers into the HMAC-signable representation (or otherwise verify them cryptographically) so that the `shop`, `topic`, `webhook_id`, and `api_version` values cannot be swapped independently of the signed body. At minimum, `Request#to_signable_string` should incorporate the raw header values used for that request, and `Registry.process`/handlers should not treat `request.shop` as authenticated unless it is covered by the signature.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers an event (e.g., creates an order), and the app's webhook endpoint legitimately receives:
   - `raw_body = '{"id":1,...}'`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body under the app's shared client_secret>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker replays the identical `raw_body` and `X-Shopify-Hmac-Sha256` value in a new POST to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC header — this still succeeds because the body/hmac pair is genuinely valid (line: `lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled content under the victim shop's identity.
