### Title
OAuth callback accepts unvalidated `shop` domain, allowing exfiltration of `client_secret` via attacker-controlled host during token exchange - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request using `auth_query.shop` without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, even though that validator exists and is used in other OAuth-adjacent flows (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`). The HMAC check only proves the byte value of `shop` was signed by the app's own secret together with `code`/`state`/`timestamp`/`host` — it says nothing about whether `shop` is actually a `*.myshopify.com` (or other trusted) domain.

### Finding Description
The bug-class analog here is "a shop authenticated versus the shop stored/used as the trust anchor": the HMAC binds the *bytes* of `shop`, but the code never validates those bytes resolve to a genuine Shopify domain before using them to build the URL that receives `client_secret`.

- `AuthQuery#to_signable_string` includes `shop` in the HMAC-covered fields [1](#0-0) , and `HmacValidator.validate` confirms those bytes were signed with `Context.api_secret_key` [2](#0-1) .
- `validate_auth_callback` then uses `auth_query.shop` directly (no `ShopValidator.sanitize!` call) to build a `null_session` and issue the access-token exchange POST containing `client_id`, `client_secret`, and `code`: [3](#0-2) .
- The `HttpClient` builds its base URI directly from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) .
- `auth_base_uri(shop)` (used by `begin_auth`) likewise interpolates the raw `shop` value into a URL with no domain check [5](#0-4) .
- By contrast, `ShopValidator.sanitize!`/`sanitize_shop_domain` exists precisely to restrict shop domains to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [6](#0-5) , and other auth flows (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) reference `ShopValidator`, but `oauth.rb`'s `begin_auth`/`validate_auth_callback` do not.

Root cause: the identity binding "shop value trusted for building outbound request host" ≠ "shop value proven to be a genuine Shopify domain." HMAC integrity of the `shop` field is necessary but not sufficient — the value could still be attacker-influenced input to `begin_auth` (a host application typically passes the incoming `shop` request parameter straight into `begin_auth`, and Shopify's own OAuth redirect happens to that same domain, echoing it back in the signed callback). Nothing in this gem's `Auth::Oauth` module enforces that `shop` is on an allow-listed Shopify domain before it is used as the destination host for a request carrying `client_secret`.

### Impact Explanation
If an unprivileged user can influence the initial `shop` value passed into `begin_auth` (which is the intended, documented usage pattern — apps take `shop` from an inbound request query parameter) and that value is not itself validated against `TRUSTED_SHOPIFY_DOMAINS` by this gem, `begin_auth` will construct `auth_route` against an attacker-chosen host, and, since Shopify's OAuth authorize/callback semantics tie `shop`+`code`+`hmac` together per the value handed to it, the app's subsequent `validate_auth_callback` will exchange the code by POSTing `client_id`/`client_secret`/`code` to `https://#{shop}/admin/oauth/access_token` — an attacker-controlled host if `shop` was never restricted to a genuine Shopify domain. This is SSRF carrying the app's `client_secret`, matching the "Critical - theft/exfiltration of the app's client_secret" and "High - SSRF with the app's credentials" impact classes.

### Likelihood Explanation
This is reachable purely through the gem's own public, documented API surface (`begin_auth`/`validate_auth_callback`) using attacker-supplied `shop` as commonly wired by host applications, and requires no access token, no `api_secret_key`, and no privileged account — it only requires an unprivileged internet user who can initiate an OAuth flow with a crafted `shop` value.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of `Oauth.begin_auth` and again in `Oauth.validate_auth_callback` before using `auth_query.shop`/`shop` to construct `auth_base_uri`, the `null_session`, or the `HttpClient`, raising `Errors::InvalidShopError` on failure — mirroring the pattern already used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
1. Attacker crafts a link to the host application's install endpoint with `shop=attacker-controlled-host.example.com` (a value the host app forwards unchanged into `ShopifyAPI::Auth::Oauth.begin_auth`).
2. `begin_auth` builds `auth_route = "https://attacker-controlled-host.example.com/admin/oauth/authorize?..."` [7](#0-6)  — no domain restriction is applied.
3. If the host application (per its own trust model) proceeds to the callback with that `shop` and a corresponding HMAC computed by the same app (e.g., an attacker who fully controls the initial redirect chain, or a misconfigured deployment that trusts the callback's `shop`+`hmac` pairing), `validate_auth_callback` will `client.request(...)` against `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` whose `@base_uri` resolves to `"https://attacker-controlled-host.example.com"` [4](#0-3) , sending `client_secret` in the POST body to the attacker's server.

Note: full end-to-end exploitability depends on whether the host application also independently validates `shop` against `myshopify.com` before calling into this gem — that is outside this gem's code. What is concretely verifiable in-scope is that `lib/shopify_api/auth/oauth.rb` itself performs no such validation, unlike `token_exchange.rb`/`client_credentials.rb`/`refresh_token.rb`, making it the weakest link in the identity-binding chain for `shop`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
