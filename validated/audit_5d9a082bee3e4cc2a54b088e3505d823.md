## Title
Webhook `shop-domain` header not bound to HMAC signature allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by the application to attribute the webhook to a tenant are read from unsigned HTTP headers. This breaks the identity binding `hmac_verified_bytes == attributed_shop`, allowing an attacker who controls one shop (an unprivileged, low-trust tenant of the app) to replay a genuinely-signed webhook body while relabeling it as belonging to a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC by calling `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers, which are never included in the signed bytes: [3](#0-2) 

`Registry.process` only checks the HMAC over the body, then dispatches to the handler using the unauthenticated `request.shop` value for tenant attribution: [4](#0-3) 

Because the signature never covers `shop-domain`, the equality the app implicitly relies on — "bytes verified by HMAC" == "shop the payload is attributed to" — does not hold. Shopify itself binds body and shop together when it sends the webhook, but that binding is not cryptographically enforced on the receiving side by this gem. Any actor who legitimately owns/operates a shop that has the app installed can capture one of their own genuinely-HMAC-signed webhook deliveries (body + `x-shopify-hmac-sha256` are still valid Shopify-issued values for their own shop) and resend it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to point at a different merchant. `HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` passes the forged shop through to the app-level webhook handler as `WebhookMetadata#shop`.

### Impact Explanation
Downstream app logic (per the gem's own documentation) uses `data.shop` from `WebhookMetadata` to route webhook processing to the correct tenant/session (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). Since this attribution is not bound to the signature, an attacker can inject attacker-controlled webhook payloads (with a valid Shopify HMAC obtained for their own shop) that are processed under a victim shop's identity — a direct cross-tenant access/data-integrity break, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High likelihood: no privileged credentials, access tokens, or `client_secret` knowledge are required. The attacker only needs to be a normal, unprivileged merchant who has installed the target app (a standard, self-serviceable action), capture one legitimate webhook delivery to their own endpoint, and replay it with a modified `shop-domain` header — trivial to automate.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) in the signed material, or otherwise cryptographically bind the tenant identity to the verified bytes before trusting `request.shop`. At minimum, the gem should document/enforce that `request.shop` must be cross-checked against a shop known to be currently installed/associated with the specific webhook subscription (e.g., via Shopify's webhook id lookup) rather than being trusted purely because HMAC validation on the body succeeded. Concretely, extend `VerifiableQuery`/`to_signable_string` for webhooks to incorporate the shop header into the HMAC-covered string where feasible, or require applications to validate `data.shop` against session storage before acting on the payload, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) causing Shopify to deliver a genuine webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - body: `{...attacker-controlled order payload...}`
3. Attacker intercepts/replays this exact request to the same endpoint but changes only the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - keeps the same raw body and `x-shopify-hmac-sha256`.
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` recomputes the HMAC solely over `@raw_body` [2](#0-1)  and it matches, so validation succeeds.
5. `Registry.process` dispatches `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker payload>, ...)` to the app's handler [5](#0-4) , causing the attacker's forged content to be processed under the victim shop's tenant context.
