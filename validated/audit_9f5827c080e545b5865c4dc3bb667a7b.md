### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `topic`, `shop`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers and are never mixed into the HMAC-covered content. `Registry.process` validates the HMAC over the body only and then forwards the unauthenticated `request.shop` value to the app's webhook handler as the tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`; none of `topic`, `shop`, `api_version`, or `webhook_id` are part of the signed content — those are pulled directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) and then unconditionally uses the unauthenticated `request.shop` header value to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because Shopify signs webhooks with a single per-app secret shared across all shops that installed the app (not a per-shop secret), any shop that has legitimately installed the app can capture a validly-HMAC'd `(raw_body, hmac)` pair from its own genuine webhook deliveries. That attacker-controlled shop can then replay the exact same body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different shop. `HmacValidator.validate` will still succeed (it never looked at the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop, with attacker-chosen body content.

This is a direct analog of the identity-binding class in the prompt: "a field acted on but not covered by the HMAC" — the equality that should hold is `signed(shop) == acted-on(shop)`, but instead `signed(body only)` is checked while `acted-on(shop)` comes from an untrusted header.

### Impact Explanation
Any application built on this gem that relies on `WebhookMetadata#shop` (or `request.shop`) for tenant routing/scoping in its webhook handler — a documented and expected usage pattern (`handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) — is exposed to cross-tenant data injection: an attacker who controls one shop that installed the app can spoof events (order/customer/product updates, GDPR redact requests, etc.) as if they originated from a different, arbitrary shop, since the shop identity is never authenticated. This matches the Critical "cross-tenant access" impact criterion in the rules, since the tenant boundary (`shop`) that gates which merchant's data a webhook affects is not bound to the cryptographic proof of authenticity.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer — no `api_secret_key`, access token, or other credential of the victim is needed) and be able to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers, which is trivial. No interaction with the victim shop is required.

### Recommendation
Include the shop domain (and ideally topic/api_version/webhook_id) in the data that's cryptographically bound to the request — e.g., have `Registry.process` cross-check `request.shop` against an out-of-band trusted value (such as the shop associated with the webhook registration/session), or require host applications to independently verify shop identity via a second authenticated channel before trusting `WebhookMetadata#shop` for tenant scoping. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is NOT covered by the HMAC and must not be used as a sole tenant-identity check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, permitted action).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body B>`, and body `B`.
3. Attacker captures `(B, valid HMAC)` and replays it to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body `B`, even though the event never originated from `victim-shop`.
