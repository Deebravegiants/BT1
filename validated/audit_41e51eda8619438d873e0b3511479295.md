### Title
Session identifier used as a bearer cookie value is deterministic and guessable, enabling cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps (and as a fallback for embedded apps without an id token), `ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw, unauthenticated cookie value supplied by the caller as the session identifier, with no cryptographic verification of that value. The session identifier that is meant to be kept secret and placed in this cookie is generated by `ShopifyAPI::Auth::Session` as a fully deterministic string derived from public information (the shop's `myshopify.com` domain, and for online sessions the associated user id), not a random secret. Anyone who knows (or can enumerate) a shop's domain can therefore construct the exact session-cookie value the app expects, without ever completing OAuth for that shop.

### Finding Description
The identity binding this cookie is supposed to enforce is:
`cookie_value == secret_token_issued_only_to_the_browser_that_completed_OAuth_for_shop_X`

What is actually implemented is:
`cookie_value == Session#id`, where `Session#id` is computed as `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions: [1](#0-0) 

This deterministic id is exactly what is placed into the browser cookie by `Oauth.validate_auth_callback` (`cookie = SessionCookie.new(value: session.id, ...)`): [2](#0-1) 

When retrieving the current session, `SessionUtils.current_session_id` accepts a caller-supplied cookie hash and, for non-embedded apps (or embedded apps without an id token), returns the cookie's raw value as the trusted session id with zero verification that it was actually issued by this gem/app to this browser: [3](#0-2) [4](#0-3) 

Because `shop` is public (it is the storefront's own domain, often visible in the app's own admin URL, referrer headers, or simply guessable/known to any user of that store) and, for offline sessions, is the *only* input to the id, the resulting cookie value `"offline_<shop>.myshopify.com"` requires no secret knowledge to compute. This is confirmed by the test suite, which shows `current_session_id` returning whatever raw string is present in the cookie hash, unchanged and unverified: [5](#0-4) 

The library's own documentation confirms this is the intended, supported usage pattern for non-embedded apps — passing raw request cookies directly into `current_session_id` to resolve "the" session: [6](#0-5) 

### Impact Explanation
If a host application follows this gem's documented pattern — storing/retrieving sessions keyed by the id returned from `current_session_id` (as the docs' `MyApp::SessionRepository.store_session(auth_result[:session])` / `retrieve_session_for_shop` pattern illustrates) — then any unprivileged internet user can synthesize a `shopify_app_session` cookie value of `offline_<any-known-shop>.myshopify.com` in their own HTTP request to the app and cause the app to load and act under another merchant's stored offline `Session`, including that merchant's `access_token`. This is cross-tenant access to another merchant's Shopify Admin credentials achieved purely by guessing a public shop domain — no phishing, no cookie theft, and no interaction with the victim's browser is required, since the attacker submits the forged cookie in their own request.

### Likelihood Explanation
The only precondition is that the app follows the documented cookie-based session flow for non-embedded apps (the primary supported flow for that app type) and that the attacker knows the target's `*.myshopify.com` domain, which is routinely public (e.g., visible in storefront URLs, `X-Shopify-Shop-Api-Call-Limit` headers, app-install links, etc.). No possession of `api_secret_key`, access tokens, or any privileged state is required, satisfying the unprivileged-internet-user constraint.

### Recommendation
Do not use the deterministic `Session#id` as the literal bearer value stored in the session cookie. Instead:
- Generate a cryptographically random, unguessable token (e.g., `SecureRandom` bytes) as the cookie value, and store a mapping from that random token to the actual `Session#id` server-side, or
- Sign/HMAC the cookie value (similar to `Utils::HmacValidator`) so `cookie_session_id` can reject any value not produced and signed by the app, rather than returning the raw client-supplied string unchecked as in `lib/shopify_api/utils/session_utils.rb:69-71`.

### Proof of Concept
1. Merchant `victim-shop.myshopify.com` installs the app via the non-embedded OAuth flow. `Oauth.validate_auth_callback` creates `Session#id == "offline_victim-shop.myshopify.com"` and sets it as the `shopify_app_session` cookie value (`lib/shopify_api/auth/oauth.rb:100-110`, `lib/shopify_api/auth/session.rb:107-117`).
2. Attacker, who only knows the public domain `victim-shop.myshopify.com`, sends their own request to the app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged and unverified (`lib/shopify_api/utils/session_utils.rb:19-37,63-71`).
4. The app looks up its session store by this id (per the documented pattern in `docs/usage/oauth.md:261-266`) and retrieves the victim's real `Session`, including `access_token`, activating it for the attacker's request — granting the attacker full API access to the victim's shop.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
