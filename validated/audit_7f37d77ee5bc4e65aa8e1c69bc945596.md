### Title
Unallowlisted route venues run arbitrary code under the caller's signed auth tree, enabling wallet-draining token transfers - ([File: contracts/swap-aggregator/src/execute/mod.rs](contracts/swap-aggregator/src/execute/mod.rs))

### Summary
The bug class in CVE-2024-9392 is an isolation escape: code from an untrusted origin executes with the privileges of a trusted context. The direct analog exists in the swap pipeline used by `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. The swap aggregator invokes pool and token addresses taken verbatim from the caller-supplied route payload, with no venue/token allowlist, while the controller's (or direct user's) `require_auth` entry is active. A hop contract named by the payload can therefore execute `token.transfer(victim, attacker, amount)` on any token the victim holds, and the Soroban host attaches that transfer as a child of the victim's signed authorization entry. An attacker only needs to deploy a rogue "pool" contract and get a victim to sign the simulation-produced auth tree to drain the victim's entire wallet of any listed or unlisted token.

### Finding Description
`execute_strategy` decodes `StrategyPayload` instructions whose `assets` registry supplies arbitrary `pool`, `token_in`, and `token_out` addresses; `venues::dispatch_hop` then invokes the named pool contract directly. Neither the router nor the controller validates that the hop pool is a real DEX venue — the router "calls the pool and token addresses its payload names and keeps no allowlist of them" (docs/explanation/threat-model.md:154-165). On the controller path, `swap_tokens` authorizes one exact `token_in.transfer(controller, router, amount_in)` via `authorize_transfer_as_current` and then calls `router.execute_strategy` inside `with_flash_guard` (contracts/controller/src/strategies/swap.rs:34-38). The controller's balance-delta checks (`RouterOverspend`, `NoSwapOutput`) only bound the *routed* amount; they do not constrain what other calls the rogue pool performs beneath the live auth tree.

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the primitive end to end: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, WALLET_BALANCE)` on a token the protocol never listed, and the recorded auth tree shows the theft attached as a child of Alice's `swap_collateral` entry (lines 62-71, 194-227). In enforcing mode, the same route succeeds only because the simulation-returned tree already contains the poisoned child — which is exactly the tree a standard client signs after `simulateTransaction` (lines 229-269). The test also shows the attack works under `SourceAccount` credentials without any entry signature (lines 322-368).

### Impact Explanation
Theft of user funds beyond the routed amount and beyond any slippage bound. The victim loses arbitrary balances of arbitrary tokens held in the signing account — bounded only by wallet contents, not by `min_out`, the final account risk gates, or the measured-output checks. On the direct `swap-aggregator::execute_strategy` path the same exposure applies to every swap user. Severity: Critical, mirroring the 9.8 class.

### Likelihood Explanation
Reachable by any unprivileged address: the attacker deploys a rogue pool contract (no permission needed) and crafts a valid `swap_xdr` route naming it as a hop; the victim submits `controller::swap_collateral` / `swap_debt` / `repay_debt_with_collateral` / `multiply` — or `execute_strategy` directly — with that route. The exploit succeeds whenever the victim signs the auth tree the simulator returns, which is the default flow for Soroban clients; the protocol's own docs acknowledge this is exactly what simulation produces. The only mitigation is client-side route decoding, which the on-chain code does not enforce.

### Recommendation
Constrain the route execution surface on-chain rather than relying on clients to reject poisoned auth trees:
- Maintain an allowlist of pool contracts per venue opcode in the swap aggregator (governance-managed), and reject hops to unlisted pools during `Program::decode`/execution.
- Alternatively/additionally, have the controller dispatch routes through a thin trusted adapter that performs venue calls from its own context so a rogue pool cannot emit calls that join the user's auth subtree.
- Document that `execute_strategy` is unsafe for direct wallet use until venue allowlisting exists, and enforce route-hash attestation for routes served by the quote server.

### Proof of Concept
Implemented and pinned by `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. `UnlistedPoolRouter::execute_strategy` (lines 39-47) pulls `token_in`, invokes `route.hop_pool.swap()`, and returns fair `token_out` — mirroring the real dispatch shape of `venues::dispatch_hop`.
2. `RogueHopPool::swap` (lines 62-71) executes `token.transfer(alice, attacker, WALLET_BALANCE)` on an unlisted token Alice holds.
3. `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194-227) shows the recorded tree containing the stolen `transfer` as a child of the `swap_collateral` entry, with `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE`.
4. `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229-269) shows the same call succeeds in enforcing mode with the simulation-produced tree, i.e., the default signing flow authorizes the theft. [1](#0-0) [2](#0-1) [3](#0-2)
