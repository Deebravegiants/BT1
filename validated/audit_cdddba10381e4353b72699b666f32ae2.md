### Title
Fee-on-transfer tokens cause escrow over-crediting in IntentGatewayV2 (Tron variant) `placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` does not correct escrow accounting for fee-on-transfer ERC20 tokens in the non-predispatch branch. It calls `safeTransferFrom` for the user-specified `order.inputs[i].amount`, but credits `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived only from the *requested* amount minus protocol fee, not from the token balance actually received by the contract.

### Finding Description
In `placeOrder` (no-predispatch branch): [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();

        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        _orders[commitment][token] += reducedInputs[i].amount;
```

There is no balance-before/balance-after measurement around `safeTransferFrom`, so if `token` deducts a transfer fee, the gateway's actual token balance increases by less than `order.inputs[i].amount`, while `_orders[commitment][token]` is still credited with `reducedInputs[i].amount` (only reduced by the *protocol* fee, not by the token's transfer fee). This inflates the internal escrow ledger relative to actual holdings.

This is precisely the bug class described in the referenced report (Gitcoin Allo `increasePoolAmount` recording a requested amount rather than an actually-received amount). Notably, the sibling EVM implementation in this same repo (`evm/src/apps/IntentGatewayV2.sol`) was patched to defend against exactly this: it snapshots balance before/after the transfer and mutates `order.inputs[i].amount` to the actual received amount before computing `reducedInputs`/commitment: [2](#0-1)

The Tron contract's `placeOrder` never applies this correction in the non-predispatch path, leaving the ledger inconsistent with real balances whenever a fee-on-transfer token is used as an order input.

The escrowed value later determines exactly what the `withdraw` function (invoked on fill via `RedeemEscrow` or on cancel/refund via `RefundEscrow`) is permitted to pay out: [3](#0-2) 

Because withdrawal amounts are keyed off `_orders[commitment][token]` (the inflated escrow record) rather than actual token holdings, the contract can be instructed to pay out more of a fee-on-transfer token than it actually holds for that specific order, at the expense of the pooled balance of other users' escrowed funds in the same contract.

### Impact Explanation
This causes escrow accounting for the affected token to diverge from the contract's real balance. Since all orders for a given ERC20 share the same custody pool inside the gateway contract, over-crediting one order's escrow with more tokens than were actually deposited effectively creates an unbacked liability that can only be satisfied by consuming other users' deposited/escrowed balances of the same token, i.e., permanent freezing/loss of funds for other legitimate order participants (their fills/refunds can revert due to insufficient balance, or, in aggregate, the pool becomes insolvent). This matches the "permanent freezing of funds" / accounting-insolvency impact class.

### Likelihood Explanation
Any unprivileged user can trigger this by placing an order (`placeOrder`) with a fee-on-transfer ERC20 as an input token — this only requires a normal user-submitted transaction with no special privileges, and fee-on-transfer tokens are common enough (deflationary/tax tokens) that a user or attacker can simply pick or deploy one and route it as an intent input. The bug is deterministic, not probabilistic, and is reachable on every `placeOrder` call using such tokens on the Tron deployment.

### Recommendation
Apply the same balance-snapshot fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure the contract's actual token balance before and after each `safeTransferFrom` call (in both the predispatch and non-predispatch branches) and use the actually-received amount — not the requested `order.inputs[i].amount` — as the basis for `reducedInputs`, the commitment hash, and the `_orders[commitment][token]` escrow credit.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee on transfer, as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) and mint balance to a user.
2. User approves the Tron `IntentGatewayV2` for `inputAmount = 1000e18` and calls `placeOrder` with that token as `order.inputs[0]`, with `protocolFeeBps = 0`.
3. `safeTransferFrom` moves `1000e18` from user but, due to the 1% fee, the gateway's actual balance only increases by `990e18`.
4. `reducedInputs[0].amount` (with `protocolFeeBps = 0`) equals the full requested `1000e18`, and `_orders[commitment][token] += 1000e18` is recorded — 10e18 more than the gateway actually holds for this order.
5. When this order is later filled/redeemed via `withdraw`, the contract will attempt to pay out `1000e18` of a token pool that only received `990e18` net for this order, drawing the missing `10e18` from the shared token balance backing other users' escrowed orders. [3](#0-2)
