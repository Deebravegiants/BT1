### Title
RAY-value i128 overflow in index accrual permanently freezes a market — no repay, withdraw, or liquidation — (File: common/src/rates/index.rs)

### Summary
The analog of CVE-2023-3618's "crafted input drives a buffer overflow into a crash" is an `i128` overflow inside the fixed-point `Ray::mul` used by interest accrual. `update_supply_index` computes `supplied.mul(env, old_index)` at common/src/rates/index.rs:34, and the same product is computed for debt in `calculate_supplier_rewards` (index.rs:80-81) and for utilization in `Cache::calculate_utilization` (contracts/pool/src/cache/scale.rs:23-24). `Ray` products are `scaled * index / RAY` on raw `i128`; once `supplied * index` exceeds `i128::MAX` the multiply panics with `MathOverflow`. [1](#0-0) [2](#0-1) 

### Finding Description
Every state-changing pool verb (supply/withdraw/borrow/repay/liquidate legs, flash paths) accrues interest first, so once `supplied_scaled * supply_index` or `borrowed_scaled * borrow_index` crosses `i128::MAX`, every subsequent call on that market panics at accrual time. Critically, the designed mitigation does not fire: `update_borrow_index`/`update_supply_index` clamp the *index* at `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` (index.rs:13-18, 43-44), but the overflow happens in the *value* product `shares × index`, which can exceed `i128::MAX` long before the index cap is reached. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the freeze: after enough accrual at ~98% utilization on a large book, `update_indexes` returns `MATH_OVERFLOW`, the borrow index is still below its cap, and both `withdraw` and `repay` then fail with the same error. [3](#0-2) 

Reachability for a single unprivileged address: `supply` and `borrow` are permissionless, `update_indexes` is permissionless (contracts/controller/src/lib.rs:370-372), and entry caps are enforced in the scaled-share domain via `calculate_scaled_cap`, which *saturates* at `i128::MAX` rather than rejecting (common/src/rates/scaling.rs:26-33) — so a governance-admitted cap can still leave headroom to build a book whose `shares × index` later overflows. An attacker seeds a large supply, borrows near `max_utilization`, and lets interest accrue (or pushes it with `update_indexes`) until the product overflows; from that ledger onward the market is permanently bricked for everyone. [4](#0-3) [5](#0-4) 

### Impact Explanation
Permanent freezing of funds and effective protocol insolvency for the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate (liquidation also accrues first), and `recapitalize`/`clean_bad_debt` touch the same accrual path. Unlike the CVE's process crash, the Soroban panic reverts the transaction — but because the overflow lives in committed state (`supplied`, `borrowed`, indexes), every retry fails identically and forever, which is strictly worse than a transient crash. [6](#0-5) 

### Likelihood Explanation
Medium. The attack requires real capital (a whale-scale position, e.g. ~10^27 raw units on an 18-decimal asset) and sustained high utilization; it cannot be conjured by a dust account. However it needs no privileges, no oracle manipulation, and no victim cooperation — `supply`/`borrow`/`update_indexes` are all callable by any authenticated address, and the saturating cap conversion means listed caps do not provably exclude the overflow region. The threat-model itself flags that "finite RAY value capacity can be exhausted before the index ceiling" and that "caps must account for plausible index growth," i.e. admitted configs do not prevent it. [7](#0-6) 

### Recommendation
Make accrual overflow-safe rather than relying on index caps:
- In `update_supply_index` and `calculate_supplier_rewards`, compute the products via `mul_div_floor_saturating` / a widened path instead of `Ray::mul`, or detect the would-be overflow and clamp the index to `MAX_SUPPLY_INDEX_RAY`/`MAX_BORROW_INDEX_RAY` before the multiply (the cap result is well-defined even when the intermediate product is not).
- In `Cache::calculate_utilization`, compare `borrowed/supplied` in the scaled domain or saturating domain so a frozen-value market still reports utilization instead of trapping.
- At listing/cap validation time, enforce `cap × 10^(27−d) × MAX_INDEX < i128::MAX` (extend `max_cap_for_decimals` to account for index growth) so no admitted configuration can reach the overflow corner.

### Proof of Concept
Reproduced by the existing harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (lines 320-361): supply `1e9 × 10^18` units of an 18-decimal asset, borrow 98% of it, advance ledger time in yearly chunks calling permissionless `update_indexes`; accrual eventually reverts with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, after which `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` — permanent freeze. pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}

/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}
