This confirms the vulnerability. The gem's documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" based solely on the HMAC check [1](#0-0) , and the `data.shop` field is documented as trustworthy tenant-identifying data for the app to key its `perform_later(topic: data.topic, shop_domain: data.shop, ...)` job dispatch [2](#0-1) , yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the signed payload [3](#0-2) .

### Title
Webhook tenant identity (`shop`, `topic`) not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [4](#0-3) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed by an app-secret holder [5](#0-4) . The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to route and tag the webhook to a specific tenant are read directly from unauthenticated HTTP headers and never included in the HMAC input [6](#0-5) [7](#0-6) .

### Finding Description
The equality broken is: **`hmac_signed_bytes == tenant_identifying_bytes_acted_on`**. Only `@raw_body` is fed into `to_signable_string`/HMAC verification [8](#0-7) , while `Registry.process` trusts `request.shop` and `request.topic` — sourced purely from the `x-shopify-shop-domain`/`x-shopify-topic` headers [9](#0-8)  — to build the `WebhookMetadata` that is handed to the app's handler [10](#0-9) .

Since a single app uses one `api_secret_key` for every installed shop, any merchant who has installed the app is a legitimate holder of valid `(body, HMAC)` pairs for webhooks Shopify sends about *their own* shop. Because the HMAC covers only the JSON body — not the shop-domain, topic, or webhook-id headers — that merchant can replay the same body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different, victim tenant. The signature still validates (`Utils::HmacValidator.validate(request)` passes because the body is unchanged) [11](#0-10) , but the app's handler receives `WebhookMetadata` claiming the event belongs to the victim shop [12](#0-11) . The gem's own documentation instructs apps to trust `data.shop` for tenant-scoped work (job dispatch, session lookup, data writes) [13](#0-12) , and explicitly claims `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  — a claim that is only true for the body, not the shop/topic identity.

### Impact Explanation
This is a cross-tenant integrity failure: an attacker who controls one tenant (a shop that installed the app) can cause the app to attribute arbitrary attacker-controlled webhook content to a victim tenant, corrupting per-shop data pipelines, triggering victim-scoped background jobs, or polluting per-shop caches/state keyed by `shop`. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate merchant/tenant of the app (no special privilege beyond installing the app) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with forged headers and a previously-observed valid `(body, hmac)` pair from their own shop's webhook traffic — both trivially available to any installed merchant.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed input, or independently verify that the `shop` header value is consistent with a shop the app expects/has a stored session for before acting on `request.shop`/`request.topic` in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
```ruby
# Attacker controls shop-a.myshopify.com (a legitimate installed tenant)
# and has observed a real Shopify webhook delivery for their own shop:
raw_body = '{"id":1,"note":"legit order for shop-a"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
)

# Attacker replays the same body+hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,          # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body unchanged)
# => handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload never originated from victim-shop.
```
