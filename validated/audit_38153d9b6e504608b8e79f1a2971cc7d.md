### Title
Unbounded `amount_in` on `exact_amount_out` fee quotes lets a colluding solver overcharge withdrawal fees - (File: `packages/intents-sdk/src/lib/estimate-fee.ts`)

### Summary
`getFeeQuote`'s primary path requests an `exact_amount_out` quote and returns whatever `solverRelay.getQuote` resolves to without any sanity check on `amount_in`. Because `handleQuoteResult`'s `matchesRequest` only verifies the fixed side of the trade (`amount_out` for exact-out requests) and leaves `amount_in` completely unconstrained, a solver can return an inflated `amount_in` that gets adopted verbatim as `feeEstimation.amount` by `HotBridge`, `OmniBridge`, `DirectBridge`, and `AuroraEngineBridge`.

### Finding Description
The broken equality is: `feeEstimation.amount == real market cost of obtaining feeAmount of feeAssetId`. On the exact-out path this equality is not enforced anywhere in the code.

Trace:
- `getFeeQuote` (`packages/intents-sdk/src/lib/estimate-fee.ts:64-80`) sends `exact_amount_out: feeAmount.toString()` and returns the resolved quote directly with `return await solverRelay.getQuote({...})` — no post-hoc ratio check like the fallback branch has.
- Inside `solverRelay.getQuote` → `handleQuoteResult` (`packages/internal-utils/src/solverRelay/getQuote.ts:32-94`), each candidate quote is checked only via `matchesRequest` (lines 119-138): for `exact_amount_out` requests, it returns `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)` [1](#0-0) . `amount_in` is never compared against any expected bound.
- `sortQuotes` (lines 96-113) picks the minimum `amount_in` among *valid* quotes for exact-out requests, but this only helps if multiple independent quotes are present; if the attacker is the only (or colluding) solver responding, the "minimum" is trivially the inflated value.
- All four call sites unconditionally trust this value: `amount: feeQuote ? BigInt(feeQuote.amount_in) : feeAmount` in `HotBridge.estimateWithdrawalFee` [2](#0-1) , `DirectBridge.estimateWithdrawalFee` [3](#0-2) , `AuroraEngineBridge.estimateWithdrawalFee` [4](#0-3) , and `OmniBridge` (`amount += BigInt(quote.amount_in)`) [5](#0-4) .

Root cause: the exact-out happy path in `getFeeQuote` has no equivalent to the exact-in fallback's `actualRatio > 1500n` guard (`estimate-fee.ts:141-151`) [6](#0-5) . That ratio check exists only in the `catch (QuoteError)` branch, which is reached only when the exact-out request itself fails — it does not protect the (much more common) case where the exact-out request *succeeds* but with a manipulated `amount_in`.

The relay is documented as an untrusted aggregator of independent, permissionless solvers ("a buggy or malicious solver can return a quote that doesn't match what we asked for" — comment at `getQuote.ts:60-65`), so a single malicious/colluding solver answering the exact-out request is within the threat model of an "unprivileged solver."

I could not fully verify, within the remaining budget, whether `sdk.ts`'s `FeeExceedsAmountError` check (referenced in `packages/intents-sdk/src/sdk.ts`, `classes/errors.ts`) bounds this — that check appears intended to reject fees exceeding the withdrawal `amount` when `feeInclusive` is used, which does provide a partial upper bound (fee cannot exceed the amount being withdrawn) but does not validate that the fee is *reasonable* relative to the real market cost; a large withdrawal can still absorb an inflated-but-sub-amount fee. This partial mitigation reduces but does not eliminate the impact — it does not restore the amount_in ≈ market cost equality, only caps it at withdrawal amount.

### Impact Explanation
`feeEstimation.amount`, which is later embedded as the debited `amount_in` in the `token_diff` intent signed by the user, can be inflated by a colluding solver far beyond the real cost of the fee. This directly debits more of the user's asset than warranted, matching the Critical category "a fee error draining a material share of the amount." Each withdrawal request through the affected bridges (HotBridge, OmniBridge, DirectBridge, AuroraEngineBridge) is independently exploitable and repeatable per call, provided the malicious solver's quote is the only/best one returned by the relay for that request.

### Likelihood Explanation
Requires a solver (or colluding group of solvers) capable of answering relay quote requests to respond to the specific `exact_amount_out` request with an artificially large `amount_in`, and for that response to be the winning (or only) quote returned by the relay for this particular request. Feasibility depends on relay/solver market conditions not fully verifiable from this codebase alone (e.g., whether other solvers also compete on that same asset pair) — genuine solver competition would naturally push `amount_in` down via `sortQuotes`' ascending sort, but nothing in the code enforces an absolute ceiling, so a low-liquidity asset pair, and/or solver collusion, is entirely plausible.

### Recommendation
Add an upper-bound sanity check on `amount_in` for the exact-out happy path in `getFeeQuote`, analogous to the 1.5x ratio guard already applied to the exact-in fallback — e.g., using price data (already fetched in the fallback) to reject any quote whose `amount_in` exceeds a reasonable multiple of the expected fee value, and throwing/falling back to the exact-in flow otherwise.

// packages/intents-sdk/src/lib/estimate-fee.test.ts
import { describe, it, expect, vi } from "vitest";
vi.mock("@defuse-protocol/internal-utils", async (importOriginal) => {
  const actual = await importOriginal<any>();
  return { ...actual, solverRelay: { ...actual.solverRelay, getQuote: vi.fn() } };
});
import { solverRelay } from "@defuse-protocol/internal-utils";
import { getFeeQuote } from "./estimate-fee";

it("accepts an exact_amount_out quote with inflated amount_in unmodified", async () => {
  const feeAmount = 1000n;
  const maliciousQuote = {
    quote_hash: "evil",
    defuse_asset_identifier_in: "nep141:token",
    defuse_asset_identifier_out: "near",
    amount_in: (feeAmount * 1000n).toString(), // 1000x inflation
    amount_out: feeAmount.toString(),          // satisfies matchesRequest
    expiration_time: new Date(Date.now() + 60_000).toISOString(),
  };
  vi.mocked(solverRelay.getQuote).mockResolvedValueOnce(maliciousQuote as any);

  const result = await getFeeQuote({
    feeAmount,
    feeAssetId: "near",
    tokenAssetId: "nep141:token",
    envConfig: {} as any,
  });

  // BROKEN EQUALITY: no upper bound check — inflated amount_in is returned as-is
  expect(result.amount_in).toBe(maliciousQuote.amount_in);
  // feeEstimation.amount would be set to this inflated value unconditionally
  expect(BigInt(result.amount_in)).toBe(feeAmount * 1000n);
});
