## Analysis

The reported bug class (`matrix-js-sdk` accepting an unrelated, attacker-supplied "predecessor" link to replace a tombstoned room because the relationship between two entities is never actually validated) maps onto Hyperbridge's EVM BEEFY consensus clients, which accept an unvalidated `stateMachineId` ⇄ parachain-header linkage when deriving `IntermediateState`s from a legitimately finalized relay-chain proof.

### Title
Unvalidated parachain-id linkage lets any relay-chain parachain inject trusted `StateMachineCommitment`s into `EvmHost` via `EcdsaBeefy`/`SP1Beefy` - (File: evm/src/consensus/EcdsaBeefy.sol, evm/src/consensus/SP1Beefy.sol)

### Summary
`EcdsaBeefy.verifyParachainHeaderProof` and `SP1Beefy.verifyConsensus` build `IntermediateState`s directly from the attacker-chosen `para.id`/`header.id` field embedded in a merkle-multiproof-verified parachain header, without checking that this id belongs to the set of parachains the consensus client is actually meant to track. `HandlerV2.handleConsensus` then unconditionally persists these commitments into `EvmHost` for whatever `stateMachineId` was supplied, as long as its height exceeds the currently stored latest height for that id.

### Finding Description
In `EcdsaBeefy.sol`, `verifyParachainHeaderProof` decodes every parachain header included in the proof and emits an `IntermediateState` keyed by the raw, prover-supplied `para.id`: [1](#0-0) 

The same pattern exists in `SP1Beefy.sol`, where `para.id` from the ZK-proven headers is used verbatim as `stateMachineId`: [2](#0-1) 

Neither contract restricts `para.id`/`header.id` to a whitelist of tracked/expected parachains. Compare this with the Rust/Substrate BEEFY consensus client (`modules/ismp/clients/beefy/src/consensus.rs`), which explicitly filters out any parachain not registered as tracked before building intermediates: [3](#0-2) 

and additionally gates `state_machine()` lookups behind `C::is_parachain_tracked(para_id)`: [4](#0-3) 

The GRANDPA client applies an analogous whitelist via `SupportedStateMachines`: [5](#0-4) 

The EVM `IConsensusV2` clients have no equivalent check. `HandlerV2.handleConsensus` then persists every returned intermediate whose height exceeds the currently recorded `latestStateMachineHeight` for that `stateMachineId`, with no filter on which ids are expected: [6](#0-5) 

`EvmHost.storeStateMachineCommitment` writes this straight into the trusted `_stateCommitments` mapping used later to validate incoming request/response proofs: [7](#0-6) 

Because any parachain that exists on the same relay chain (Polkadot/Kusama) is finalized under the same legitimate BEEFY authority set and MMR that `EcdsaBeefy`/`SP1Beefy` verify, an attacker can register or operate their own unrelated parachain on that relay chain. Its headers will pass every cryptographic check in `verifyMmrUpdateProof`/`verifyParachainHeaderProof` (or the SP1 proof) because those checks only validate that the header is *genuinely finalized on the relay chain* — they never validate that the header's `para.id` is the one this `EvmHost` deployment is supposed to trust (e.g., only the Hyperbridge parachain, id 3367, per the SP1 test fixture comment). The attacker fully controls the `state_root`/ISMP digest fields of their own parachain, so they control the resulting `StateCommitment` content (`overlayRoot`, `stateRoot`, `timestamp`) that gets stored under their chosen `stateMachineId`.

### Impact Explanation
Once a forged `StateMachineCommitment` is stored for an arbitrary `stateMachineId`, an attacker who also controls that parachain's runtime state can construct membership proofs against their own `overlayRoot`/`stateRoot` and submit them through `HandlerV2.handlePostRequests`/`handleGetResponses`, which trust `host.stateMachineCommitment(request.proof.height)` at face value: [8](#0-7) 

This allows forged message delivery / unsound state commitment injection into `EvmHost`, undermining the integrity guarantee that only the intended, configured state machine's finalized state can be used to authorize incoming ISMP requests — the same "insufficient validation of a linking identifier lets an unrelated entity replace/inject trusted state" pattern as the reported matrix-js-sdk advisory.

### Likelihood Explanation
Exploitation only requires operating (or having operated for you, e.g. a public testnet/relay-chain parachain slot) an arbitrary parachain on the same relay chain the consensus client tracks, and relaying its finalized BEEFY proof — no privileged relayer, admin, or governance role is needed, and the crypto verification itself succeeds because the header genuinely is finalized by the real authority set. This is reachable by any unprivileged relayer submitting a consensus proof transaction.

### Recommendation
Add an explicit allow-list check for `para.id`/`header.id` inside `EcdsaBeefy.verifyParachainHeaderProof` and `SP1Beefy.verifyConsensus` (mirroring `is_parachain_tracked`/`SupportedStateMachines` in the Substrate clients), filtering out or reverting on any parachain id that is not configured as tracked before constructing `IntermediateState`s, and/or enforce the restriction at `HandlerV2.handleConsensus`/`EvmHost.storeStateMachineCommitment` so only pre-registered `stateMachineId`s can ever be written.

### Proof of Concept
1. Attacker acquires/controls a parachain slot (`para.id = X`) on the same relay chain tracked by a deployed `EcdsaBeefy`/`SP1Beefy` consensus client (e.g. Polkadot), where `X` is not the intended tracked chain (e.g. not 3367).
2. Attacker sets arbitrary values in their parachain's ISMP consensus digest (`child_trie_root`, `mmr_root`) to whatever `stateRoot`/`overlayRoot` they want.
3. Attacker (or any relayer) submits the genuinely-finalized BEEFY commitment + parachain header proof containing this header to `HandlerV2.handleConsensus`.
4. `EcdsaBeefy`/`SP1Beefy` verification succeeds (all signatures/MMR proofs are legitimate), returning an `IntermediateState{stateMachineId: X, height, commitment}` built from attacker-controlled fields.
5. `HandlerV2.handleConsensus` stores this via `EvmHost.storeStateMachineCommitment` since `X`'s previous latest height was lower.
6. Attacker crafts a `PostRequestMessage` with `proof.height.stateMachineId = X` and a merkle multiproof rooted at their self-chosen `overlayRoot`, which `HandlerV2.handlePostRequests` accepts and dispatches to a destination module on `EvmHost`.

        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();

            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }

    /**
     * @dev Store the state commitment at given state height alongside relevant metadata.
     * Assumes the state commitment is of the latest height.
     */
    function storeStateMachineCommitment(StateMachineHeight memory height, StateCommitment memory commitment)
        external
        restrict(_hostParams.handler)
    {
        _stateCommitments[height.stateMachineId][height.height] = commitment;
        _stateCommitmentsUpdateTime[height.stateMachineId][height.height] = block.timestamp;
        _latestStateMachineHeight[height.stateMachineId] = height.height;

        emit StateMachineUpdated({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId), 
            height: height.height
        });
    }
