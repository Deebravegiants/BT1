### Title
Unvalidated, header-derived `shop` in `ShopifyAPI::Webhooks::Request#shop` allows cross-tenant shop-key forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the raw `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header value with no domain-format or trust validation, and this value is not included in the HMAC signature computed over `to_signable_string` (which is just `@raw_body`). `Registry.process` passes this unvalidated string straight into `WebhookMetadata#shop`, which host apps use as a raw tenant lookup key, unlike every OAuth/token code path in this gem which runs shop values through `ShopValidator.sanitize!`.

### Finding Description
The broken binding: `shop value trusted by handler (WebhookMetadata#shop)` should equal `shop value passed through ShopValidator.sanitize! or equivalent`, but in the webhook path this gem never performs that check.

Trace:
- `ShopifyAPI::Webhooks::Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) does `T.cast(shopify_header("shop-domain"), String)` — a direct, unvalidated read of the `x-shopify-shop-domain` header.
- `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns only `@raw_body`. The HMAC computed by `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) is `HMAC(secret, raw_body)` — it covers only the body, never any header, including `shop-domain`.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `HmacValidator.validate(request)` (validates body integrity only), then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the host's `handler.handle(data:)`.
- `WebhookMetadata` (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`) is a plain `T::Struct` with `const :shop, String` — no format/trust constraint is applied.
- By contrast, every OAuth-adjacent entry point in this gem (`lib/shopify_api/auth/oauth/auth_query.rb`, `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/refresh_token.rb`, `lib/shopify_api/auth/client_credentials.rb`) calls `ShopValidator.sanitize!` to constrain the shop value to `TRUSTED_SHOPIFY_DOMAINS` (`lib/shopify_api/utils/shop_validator.rb:9-18, 56-64`). No such call exists anywhere in `lib/shopify_api/webhooks/`.

Exploit flow: an attacker who owns a legitimate development shop can install the app and receive genuinely-signed webhook callbacks from Shopify (HMAC computed with the real `api_secret_key` over the real body) at their own server. Because the HMAC never covers the `x-shopify-shop-domain` header, the attacker can take that entire valid request (unchanged body + unchanged `x-shopify-hmac-sha256` header) and replay/forward it to the app's shared webhook endpoint while substituting `x-shopify-shop-domain` with an arbitrary string — e.g. the exact domain of a victim merchant, or any non-`.myshopify.com` value. `HmacValidator.validate` still returns `true` (it never inspects the shop header), so `Registry.process` proceeds and calls the host's handler with `WebhookMetadata#shop` set to the attacker-chosen string. If the host app (as this gem's documentation implies is acceptable, since the gem gives no `ShopValidator` call for webhooks) uses `data.shop` directly as a `Shop.find_by(domain: ...)` key, this is a cross-tenant write/read: the attacker's own webhook body (e.g. `orders/create`, `app/uninstalled`, etc.) gets attributed to and processed against the victim's shop record.

No existing guard in this gem prevents this: `HmacValidator.validate` checks body integrity only; there is no `ShopValidator.sanitize!` call in the webhook path; `Context.setup?`/`private?`/`embedded?` are unrelated to webhook shop trust; Sorbet's `T.cast` in `Request#shop` performs no runtime validation of content, only a type assertion.

### Impact Explanation
This lets an unprivileged attacker (with only their own development shop and its genuine webhook delivery) forge the tenant identity attached to arbitrary webhook payloads processed by the host app, as long as the host trusts `WebhookMetadata#shop` as a raw lookup key (a usage pattern this gem does not warn against or prevent, since it supplies `ShopValidator` for every other entry point but not this one). This is a cross-tenant data-integrity/access issue — Critical category — repeatable against arbitrary victim shop domains and arbitrary webhook topics/bodies the attacker's own dev shop can trigger.

### Likelihood Explanation
Preconditions: host app looks up shop by `WebhookMetadata#shop` without independently validating it against a known-shops table or a `.myshopify.com` format check — a pattern that is plausible and even natural since this gem provides no built-in guard for webhooks. Attacker cost is low: create a free development shop, install the app, trigger any webhook topic, capture the raw HTTP request at their own receiving server, and forward it to the app's shared webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets are required. Fully repeatable against any victim shop domain the attacker chooses.

### Recommendation
Have `Registry.process` (or `Webhooks::Request#shop`) run the header value through `Utils::ShopValidator.sanitize!` before constructing `WebhookMetadata`, rejecting/raising when the shop header is not a trusted `*.myshopify.com` (or configured custom) domain, matching the same guarantee already provided on the OAuth/token paths. Additionally, document/enforce that host apps must only trust `WebhookMetadata#shop` after this sanitization, and that it must correspond to a shop that has genuinely completed OAuth for this app (not merely be a syntactically valid domain).

### Proof of Concept
```ruby
# test/webhooks/request_shop_trust_test.rb
require "test_helper"

class RequestShopTrustTest < Test::Unit::TestCase
  def test_shop_is_never_validated_or_sanitized
    ShopifyAPI::Utils::ShopValidator.expects(:sanitize!).never

    raw_body = '{"id":1,"event":"orders/create"}'
    secret = "test_secret"
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: secret, host_name: "host",
      scope: "read_products", is_private: false, is_embedded: true)

    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body),
    )

    forged_shop = "victim-shop.example.com" # not a *.myshopify.com domain, or a victim's exact domain

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "x-shopify-topic" => "orders/create",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => forged_shop,
        "x-shopify-api-version" => "2024-01",
        "x-shopify-webhook-id" => "abc123",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(request), "HMAC over body should still validate"
    assert_equal forged_shop, request.shop, "unsanitized attacker-controlled shop passes straight through"

    handler = mock
    handler.expects(:handle).with do |data:|
      data.shop == forged_shop # binding is broken: forged value reaches the handler untouched
    end
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http,
      path: "/webhooks", handler: handler)

    ShopifyAPI::Webhooks::Registry.process(request)
  end
end
```
This demonstrates the equality `request.shop == ShopValidator.sanitize!(request.shop)` does **not** hold — `sanitize!` is never invoked, and the attacker-forged, non-validated `shop` string flows unchanged into `WebhookMetadata#shop` and the host handler.
