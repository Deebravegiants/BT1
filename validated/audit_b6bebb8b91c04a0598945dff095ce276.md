### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone weaponize any stale unlimited approval left by past order/bridge calldata to drain funds routed through the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, permissionless contract used by both `IntentGatewayV2` (predispatch/postdispatch calldata) and `HyperFungibleToken`/`WrappedHyperFungibleToken` (bridge-and-call). Its `dispatch()` function can be called by anyone, with arbitrary `Call[]`, at any time — it has no caller restriction and no restriction on the `to` targets. This is structurally identical to the Footium bug: a party who once had legitimate, transient control over the shared account's calldata can leave behind a persistent ERC20 approval that outlives their control, letting them (or anyone who discovers it) later drain assets that belong to unrelated parties and transiently pass through the same shared account.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each `to.call{value}(data)` with the dispatcher itself as `msg.sender`, reverting the whole batch on any failure [1](#0-0) . There is no modifier restricting who may call `dispatch()` — unlike `IntentGatewayV2`/`IntentsBase`, which gate calls behind `onlyHost` or internal callers, `CallDispatcher` exposes `dispatch` as a bare `external` function.

This dispatcher is a single, long-lived, shared contract address (`_params.dispatcher`) reused across *every* order placed through `IntentGatewayV2`, for both predispatch (swap-then-escrow) and postdispatch (fill-then-act) calldata [5](#0-4) [6](#0-5) . It is also the documented target (`to: CALL_DISPATCHER`) for calldata execution attached to `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain sends, where tokens are minted or unlocked directly to it before the attached calls run [7](#0-6) .

Any order's calldata (fully controlled by the order's own user, or by whoever composes the bridge message's `data` field) can leave the dispatcher with a standing, unlimited ERC20 allowance to a chosen spender — the documented pattern for a DEX swap explicitly does this: `IERC20.approve.selector, uniswapRouter, type(uint256).max` [3](#0-2) . Once granted, that approval is a permanent, on-chain fact about the shared dispatcher's balance — it is never revoked by the protocol, and nothing ties it to the order/message that created it.

Because `dispatch()` has no access control, anyone (not just the router that was approved) can subsequently call `CallDispatcher.dispatch()` directly with calldata that invokes that pre-approved spender (e.g., a Uniswap-style router function that pulls `amountIn` from `msg.sender=dispatcher` and sends the output to an attacker-chosen recipient), sweeping out ANY token balance the dispatcher happens to be holding at that moment — including balances that belong to a completely unrelated, contemporaneous order or bridge transfer that is mid-flight through the same dispatcher (tokens minted/transferred to the dispatcher are held there for the duration of that transaction's `dispatch()`/sweep sequence). This mirrors the Footium pattern precisely: the "bad club owner" (the order/message author who set the approval) no longer needs any privilege over the dispatcher to keep benefiting from it — the stale, unrevoked approval alone is the attack surface, and it is reachable by an unprivileged relayer/attacker with a single submitted transaction.

### Impact Explanation
Concrete theft of funds routed through the shared `CallDispatcher`: any tokens transiently held by the dispatcher (from any user's predispatch escrow, any order's postdispatch output delivery, or any HyperFungibleToken/WrappedHyperFungibleToken bridge-and-call mint/unlock targeting the dispatcher) can be redirected to an attacker as soon as a prior approval exists for a callable spender, and that spender can be invoked by anyone through the unguarded `dispatch()` entrypoint. This is a direct loss of user/solver funds across the Intent Gateway and Hyper Fungible Token products, satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
High. Setting a `type(uint256).max` approval from the dispatcher to a router is the exact pattern shown in the codebase's own tests and documentation for legitimate swap flows [3](#0-2) , meaning ordinary usage of the documented swap-through-dispatcher feature will routinely create the exploitable approval. Any single order or bridge message placed by any unprivileged user establishes the standing allowance; any subsequent unprivileged caller can then trigger `dispatch()` at will, with no special timing or front-running needed beyond waiting for the dispatcher to hold a nonzero balance of the approved token (which happens on every subsequent order/transfer that routes that token through the same dispatcher instance).

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the registered `IntentGatewayV2`/`HyperFungibleToken` contracts (an `onlyAuthorizedCaller` allowlist), and/or make the dispatcher single-use/ephemeral per order (deploy a minimal-proxy dispatcher per call, or clear/verify zero residual allowances and balances at the end of every `dispatch()` invocation). At minimum, forbid `approve`/`increaseAllowance` calls with non-exact (e.g., `type(uint256).max`) amounts from executing through `dispatch()`, and require the caller-supplied `Call[]` to leave the dispatcher's allowance to any token back at zero before returning control.

### Proof of Concept
1. Attacker (or any user) places an `IntentGatewayV2` order (or crafts a `HyperFungibleToken.send` with `data`) whose predispatch/postdispatch `Call[]` includes `IERC20(TOKEN).approve(ROUTER, type(uint256).max)`, executed via `CallDispatcher.dispatch()` as shown in `evm/tests/foundry/IntentGatewayV2Test.sol:1358-1363`. This leaves `CallDispatcher` with an unlimited standing allowance to `ROUTER` for `TOKEN`.
2. At any later time, a different, unrelated order/bridge transfer causes `TOKEN` to be transferred into or minted at the `CallDispatcher` address as part of its own predispatch/postdispatch/bridge-and-call flow.
3. Before (or instead of racing) the legitimate sweep, the attacker directly calls `CallDispatcher.dispatch(encodedCalls)` — a public function with no access control (`evm/src/utils/CallDispatcher.sol:44`) — where `encodedCalls` invokes `ROUTER`'s swap/transfer function with `msg.sender=CallDispatcher` (satisfied by the pre-existing max approval) and directs the output/proceeds to the attacker's own address.
4. The attacker receives the victim order's/transfer's `TOKEN` balance that was sitting in the shared dispatcher, without ever being an authorized party to that order or transfer.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
