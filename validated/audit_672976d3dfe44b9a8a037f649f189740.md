Confirmed: `ShopValidator.sanitize!` is used in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb` (for the `shop` parameter passed by the deprecated caller), but `lib/shopify_api/auth/oauth.rb`'s `begin_auth` and `validate_auth_callback` methods never call it. `auth_query.shop` flows directly into `auth_base_uri(shop)` and into `Auth::Session.new(shop: auth_query.shop)`, which is then used by `Clients::HttpClient` to build `@base_uri = "https://#{api_host || session.shop}"` — the exact host the `client_id`/`client_secret`/authorization `code` are POSTed to.

### Title
Unsanitized `shop` in OAuth callback allows attacker-controlled host to receive `client_secret` and authorization code - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever validating that it is a genuine `*.myshopify.com`/trusted Shopify domain, unlike `ClientCredentials.client_credentials` and `RefreshToken`, which explicitly call `Utils::ShopValidator.sanitize!` on `shop` before constructing a session/host.

### Finding Description
`validate_auth_callback` in [1](#0-0)  only checks the HMAC over the query string and the `state` cookie match, then immediately does `null_session = Auth::Session.new(shop: auth_query.shop)` and issues the access-token POST via `Clients::HttpClient`. `HttpClient#initialize` computes `@base_uri = "https://#{api_host || session.shop}"` [2](#0-1)  — i.e., the exact network destination for the `client_id`/`client_secret`/authorization `code` body is taken verbatim from `session.shop`, which is `auth_query.shop`.

Unlike this path, `ClientCredentials.client_credentials` explicitly sanitizes the shop before use: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [3](#0-2) , which restricts the resulting host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [4](#0-3) . The OAuth callback path has no equivalent check.

The identity binding that should hold is: `host that receives client_secret == a genuine Shopify domain (validated the same way ClientCredentials/RefreshToken validate it)`. Because `shop` is only covered by the HMAC (a signature over `code+host+shop+state+timestamp` per `AuthQuery#to_signable_string` [5](#0-4) ), the HMAC proves the query bytes weren't tampered with in transit from Shopify — it does *not* independently prove `shop` is a well-formed `*.myshopify.com` domain rather than some other string. If Shopify's own callback (or a redirected browser request crafted by an attacker who can produce a valid HMAC, e.g. via a compromised/rotated secret window using `old_api_secret_key`, or a host application that constructs `AuthQuery` from arbitrary request parameters as shown in the gem's own docs example `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))` [6](#0-5) ) ever supplies a non-canonical `shop` string, the gem will happily POST the app's `client_id`/`client_secret`/authorization `code` to that host.

### Impact Explanation
If reachable with attacker-influenced `shop`, this results in the app's `client_secret` and authorization `code` being sent to a non-Shopify host — credential exfiltration of the app's `client_secret`, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is constrained: `shop` is part of the HMAC-signed query, so a completely unauthenticated third party cannot arbitrarily rewrite `shop` without invalidating the signature under the current `api_secret_key`. The realistic trigger surface is narrower than a full auth bypass and depends on factors outside this gem (e.g., how the host app assembles `AuthQuery`, or behavior during secret rotation via `old_api_secret_key`). I could not find code in this gem's HMAC/OAuth path that further constrains `shop` to a myshopify-style domain the way `ShopValidator` does elsewhere, which is the inconsistency worth flagging, but I could not confirm a concrete unauthenticated exploitation path within this gem alone.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(auth_query.shop)` in `ShopifyAPI::Auth::Oauth.validate_auth_callback` (and in `begin_auth`) before using the value to construct `Auth::Session`/`auth_base_uri`, mirroring the checks already performed in `ClientCredentials.client_credentials` and `RefreshToken`.

### Proof of Concept
Not independently verifiable as a fully unauthenticated exploit purely within this gem's code — the HMAC binding on `shop` prevents a generic internet attacker from freely substituting the host without the shared secret. This is reported as a defense-in-depth / consistency gap relative to `ShopValidator` usage elsewhere in the codebase rather than a demonstrated end-to-end unauthenticated bypass.
