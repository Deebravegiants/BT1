### Title
Attacker-Seeded HyperSwap Pre-Seed Lets a Pre-Grad LP Position Siphon Real Curve-Raised LT via the Graduation Rebalance Swap - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds the post-graduation HyperSwap V2 pool through `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`, which uses the curve's real, raised LT (`ltFromPair`) to swap against whatever reserves already sit in the (attacker-influenceable, permissionlessly creatable) V2 pair in order to "fix" a hostile pre-seed ratio. Because the pre-seeder's LP tokens are never routed through `LPLock` (only the protocol's freshly-minted LP is locked), an attacker who self-mints a sizeable, deliberately off-ratio LP position in the pair *before* `finalizeGraduation` runs can force `Bonding` to pump real curve LT and `tokensForLP` inventory into that same pool via the rebalance swap, then immediately withdraw their own (unlocked) LP for a share of the resulting reserves — capturing value that was supposed to back only the locked LP. [1](#0-0) 

### Finding Description
`_seedUniswapV2Direct` branches on whether the HyperSwap V2 pair already has LP supply: [2](#0-1) 

The HyperSwap `Factory.createPair(token, lt)` call is permissionless, and the launched token's address is deterministic (`Bonding.predictTokenAddress`). An attacker can pre-create the TOKEN/LT V2 pair and call `pair.mint(attacker)` against a self-funded, deliberately off-ratio deposit at any point before `finalizeGraduation` runs — landing in "Regime 3" (`totalSupply != 0`, mint pre-seed), handled by `_seedRebalancing`: [3](#0-2) 

Only pre-seeds where *both* sides are below `DIRECT_MINT_PRESEED_BPS` (1 bp) of the LP targets are neutralized by direct-minting over them: [4](#0-3) 

Any larger pre-seed instead takes the rebalance path, where `_pairRebalance` swaps up to 99% of the curve's real raised LT (`_ltSwapInventory` / `_swapBudget`) directly into the *attacker's own pre-existing pool* to move its ratio toward the cached curve-close price: [5](#0-4) [6](#0-5) 

The rebalance swap is executed directly against the pair the attacker already controls a share of (via their unlocked, self-minted LP), which then increases the pool's total reserves. `_routerDepositAndDispose` subsequently deposits the remaining matched TOKEN/LT via `addLiquidity(min0=1, min1=1)`, minting *new* LP only to `LPLock`: [7](#0-6) 

The attacker's original LP tokens are never touched or locked — `LPLock.recordLock` only ever records the amount minted to `lpLock_` in this same call, and has no visibility into (or claim on) the attacker's separately-held LP tokens: [8](#0-7) 

The code's own natspec concedes the captured share is *proportional* to the pre-seed size and "vanishes" only for pre-seeds *small enough* to fall under the swap-quote-rounds-to-zero fallback — implying it does **not** vanish, and is bounded only by `uint112` pair-reserve limits and the 99%-of-`ltFromPair` swap cap, for a sufficiently large, deliberate pre-seed: [9](#0-8) 

Once the rebalance swap and matched deposit land, the attacker calls `pair.burn` (or the V2 router's `removeLiquidity`) on their own unlocked LP tokens and redeems a proportional slice of the pair's post-rebalance TOKEN and LT reserves — reserves that were funded by the curve's real raised LT (`ltFromPair`) and the protocol's `tokensForLP`/`LP_RESERVE` allocation, both of which are supposed to exclusively back the locked LP.

### Impact Explanation
This lets an unprivileged attacker extract real, curve-raised LT (backing trader deposits) and protocol-reserved TOKEN supply intended for the locked LP, at the moment of graduation, for every token whose creator/community does not race to grab the pool first. This is concrete theft of trader/LP funds and results in an LP seeded (and immediately partially drained) away from the intended curve-close economics — squarely within the accepted impact classes (theft of LP funds, LP seeded away from curve close price). Because `finalizeGraduation` is fully permissionless and can be called by anyone (including the attacker) right after they've pre-seeded, the attacker fully controls both the setup and trigger of the exploit.

### Likelihood Explanation
- Creating the V2 pair and minting an arbitrary-ratio LP position is fully permissionless and requires only that the attacker hold some TOKEN (buyable pre-graduation on the curve) and LT (mintable via BounceTech / Zap).
- The attacker only needs to front-run/observe an in-progress graduation (`TokenGraduating` event, phase 1 → phase 2 window, documented as ~60 seconds) — a routine MEV-style race, not a privileged action.
- The defense mechanism explicitly documented in the code (`DIRECT_MINT_PRESEED_BPS`) only neutralizes *dust*-sized pre-seeds; anything above roughly 0.01% of the LP-bound sides is handled by the exploitable rebalance path.
- `finalizeGraduation` itself is callable by anyone, including the attacker, removing any dependency on keeper timing.

### Recommendation
- Do not use the curve's own raised LT/TOKEN inventory to rebalance against a pool the attacker already holds an unlocked LP position in. Instead, detect any non-zero pre-existing `totalSupply()` on the target V2 pair as hostile and refuse to graduate into it (revert / require an owner-mediated recovery), or deploy a fresh, deterministic pair address that cannot be pre-seeded (e.g., a CREATE2 pair owned/gated so only `Bonding` can mint into it once).
- Alternatively, cap the rebalance-swap budget as a function of the pre-seed's own reserves (not a flat 99% of the full `ltFromPair`), so the maximum value transferable to a hostile pre-existing LP position is bounded to a negligible amount regardless of the pre-seed's absolute size.
- Require the attacker's pre-existing LP (if any) to be diluted/locked pro-rata alongside the newly minted LP, or force a `skim`+full `burn`-and-remint of any pre-existing LP supply before depositing curve funds.

### Proof of Concept
1. Attacker predicts the token address for an upcoming `Bonding.launch` (or targets any live curve token) and predicts/derives the deterministic HyperSwap V2 pair address for `(token, lt)`.
2. Attacker calls `IUniswapV2Factory.createPair(token, lt)` (permissionless) before the token graduates.
3. Attacker acquires a meaningful amount of `token` (via curve buys through `Zap.buy`) and `lt` (via `IBounceLeveragedToken.mint` or `Zap`), transfers both into the pair, and calls `pair.mint(attackerAddress)`, self-minting LP at a deliberately off-ratio (e.g., TOKEN-heavy) deposit sized to a meaningful fraction of the eventual `tokensForLP` / `ltFromPair`.
4. The token graduates normally (via `Bonding.buy` crossing the threshold, or via `Bonding.triggerGraduation`), entering `Lifecycle.Graduating` and caching `(tokensForLP, ltFromPair)` in `_enterGraduating` / `_prepareGraduationLiquidity`.
5. Anyone (including the attacker) calls `Bonding.finalizeGraduation(token)`. Because the pair's `totalSupply() != 0` and the attacker's reserves exceed the `DIRECT_MINT_PRESEED_BPS` dust band, `_seedRebalancing` executes `_pairRebalance`, swapping up to 99% of `ltFromPair` (or `tokensForLP`) directly into the attacker-seeded pool, then `_routerDepositAndDispose` deposits the remainder, minting new LP to `LPLock`.
6. Attacker calls `pair.burn` (or `IUniswapV2Router02.removeLiquidity`) on their original, unlocked LP tokens, redeeming a proportional share of the pool's post-rebalance TOKEN and LT reserves — extracting value derived from the curve's real raised LT and the protocol's `LP_RESERVE` token allocation.

Note: exact numeric profit depends on chosen pre-seed size versus `tokensForLP`/`ltFromPair` for the specific token, and on live BounceTech LT `exchangeRate()`/mint floors at the time of the attack; I was not able to run the Foundry test suite in this environment to produce concrete extracted-value figures, so likelihood/impact sizing here is qualitative based on the code's own documented (and conceded) proportionality of the captured share.

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }
        // else: pool already at curve-close ratio (rare — e.g. attacker
        // pre-seeded at exactly target). Skip swap, deposit directly.

        return _routerDepositAndDispose(tokenAddress, lt, protectedLT);
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

            IERC20(tokenAddress).forceApprove(routerAddr, 0);

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
