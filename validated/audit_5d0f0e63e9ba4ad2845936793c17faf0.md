### Title
Webhook HMAC only covers the raw body, letting an attacker with any single valid webhook forge the `shop`/`topic` attribution for another tenant - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers and are never included in the HMAC-covered bytes. `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` (which checks only the body) and then unconditionally trusts the unsigned `shop`/`topic` headers to build the `WebhookMetadata` handed to the host application's handler.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are parsed from separate, unsigned headers: [2](#0-1) 

`Registry.process` validates the request using only this body-only HMAC, then immediately trusts `request.shop` and `request.topic` (both unsigned) to dispatch the handler and construct the metadata object delivered to the app: [3](#0-2) 

The binding that should hold is: `bytes cryptographically verified == bytes the application acts on for tenant identity`. Here, the verified bytes are `raw_body` alone, but the application acts on `shop`/`topic` headers that are outside that verified scope. Since the HMAC key (`Context.api_secret_key`) is a single per-app secret shared across all shops installing the app (not a per-shop secret), any shop that has received one legitimate webhook possesses a valid `(raw_body, hmac)` pair. That user can replay this pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header of a different (victim) shop and/or a different `x-shopify-topic` header. `Utils::HmacValidator.validate` still returns `true`, because it only recomputes the HMAC of `raw_body`, and `Registry.process` proceeds to dispatch the handler with `shop: request.shop` set to the attacker-chosen victim shop.

### Impact Explanation
This breaks the tenant-identity binding at the point the gem hands data to the host application: the merchant handling code cannot distinguish a legitimate webhook for shop A from a replayed body relabeled as shop B, since the library's only integrity check does not cover the shop/topic fields. This falls under the "cross-tenant access" impact category, since a request cryptographically valid for one tenant is delivered as if it belonged to another tenant, letting an attacker who controls one shop inject or corrupt processing for a shop they do not control (e.g., causing the host app to record forged order/customer data under, or trigger business logic tied to, another merchant's shop record).

### Likelihood Explanation
Any developer or shop owner who has legitimately installed the app receives real webhook deliveries (body + valid HMAC) for their own shop. Reusing that pair against the same public webhook endpoint with a modified `shop-domain`/`topic` header requires no secret knowledge, no privileged access, and no interaction with Shopify's platform beyond having received one webhook — it is a pure unprivileged replay from any user who has an installed instance of the app.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signable string (or otherwise cryptographically bind them to the body), so `Utils::HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed. Alternatively, require and validate the topic/shop against the values already known for the session/registration the webhook is claimed to belong to, rather than trusting header values wholesale after only a body-integrity check.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and receives a legitimate webhook: headers include `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, plus a JSON body.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different registered `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — this still matches, so validation passes: [4](#0-3) 
4. The handler executes with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: ..., ...)`, where `shop` is `victim-shop.myshopify.com` even though the payload was never generated by or for that shop — the host application processes attacker-supplied data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
