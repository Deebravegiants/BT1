The report's core pattern — a value that downstream code trusts and acts on, without being cryptographically bound to the signature that "proves" authenticity — has a direct analog in this gem's webhook processing.

### Title
Webhook shop-domain spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking the HMAC, then hands the handler a `shop` value that was never included in the signed material. An attacker who controls one Shopify shop with the app installed can replay a validly-signed webhook body while substituting the `shop-domain` header for a victim shop, causing the app's webhook handler to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`Registry.process` gates on HMAC validity before dispatching to the handler: [1](#0-0) 

The HMAC is computed only over the raw request body, never over headers: [2](#0-1) [3](#0-2) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string`: [4](#0-3) 

`Utils::HmacValidator.validate` only ever checks the HMAC against the signable string (the body), never the shop header: [5](#0-4) 

The unauthenticated `shop` value is then forwarded straight into the handler's data as the tenant identity: [6](#0-5) 

The gem's own documentation states that `process` "will verify the request did indeed come from Shopify," and describes `data.shop` as "The shop domain of the webhook" without qualification — implying it is part of what's verified, when in fact it is not bound to the signature at all: [7](#0-6) [8](#0-7) 

This is the same class of bug as the report: an "adjustment"/field (there, `debt_amount_final`; here, `shop`) is trusted and acted upon by downstream logic, while the invariant-enforcing check (there, invariant math; here, HMAC) never covers that field, breaking the implicit binding `verified_bytes == acted_on_bytes`.

### Impact Explanation
The app's `api_secret_key` is shared across all shops that install the app — it is not per-shop. Any merchant who installs the app receives a request whose body is legitimately HMAC-signed with that shared secret. By replaying that same body with the `shop-domain` header changed to a different (victim) shop's domain, the attacker gets `Registry.process` to accept the forged request as valid and dispatch to the handler with `data.shop` set to the victim's domain. Any host application that uses `data.shop` to look up a per-shop session, write shop-scoped data, or trigger shop-scoped side effects (exactly what the docs' example handler does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied data under a victim tenant's identity — a cross-tenant data/action confusion.

### Likelihood Explanation
Exploitation requires the attacker to be an existing (even free/self-service) merchant installer of the app so they can obtain one legitimately-signed webhook body, then simply replay it to the app's webhook endpoint with a modified header — no possession of `api_secret_key`, access token, or any privileged account is required. This is easily reachable by any unprivileged app-installing party.

### Recommendation
Bind the shop identity into the signed material that `HmacValidator` checks (e.g., include the `shop-domain` header in the signable string, or independently verify that the shop in the webhook belongs to a session/webhook subscription the app itself registered) so the value handed to handlers as `data.shop` cannot be forged independently of the HMAC-covered payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook: body `B`, `x-shopify-hmac-sha256: H(B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC header `H(B)` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` parses this; `to_signable_string` returns `B` only.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B)` and compares it to the supplied `H(B)` — it matches because the body is untouched.
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...))` is invoked; the host app processes attacker-controlled body content attributed to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
