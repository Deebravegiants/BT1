### Title
Rounding-Slack Drain of Curve LT Reserve Causes Permanent Underflow-Panic DoS in `canGraduate` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` recovers the "real LT raised" by subtracting the launch-time virtual LT reserve from the pair's stored `assetReserve`: `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(...)` [1](#0-0)  using Solidity 0.8's checked (panicking) arithmetic. `Router._computeSell` and `Router._computeBuy` round in the trader's favor via floor division with no protocol fee to offset it [2](#0-1) , and `Pair.swap`'s K-check only tolerates a `+1` slack [3](#0-2) . An unprivileged trader repeatedly round-tripping tiny buy/sell pairs through `Bonding.buy`/`Bonding.sell` can erode `assetReserve` by accumulated 1-wei rounding losses until it dips below the recovered virtual reserve, at which point the subtraction underflows and reverts (Panic 0x11) on every future call — permanently.

### Finding Description
`canGraduate` is invoked unconditionally at the end of every successful buy (`_executeBuy` → `canGraduate`) [4](#0-3) , at the top of every sell (`Bonding.sell`) [5](#0-4) , and inside `triggerGraduation` [6](#0-5) . Its USD leg performs a plain, unguarded subtraction:

```solidity
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [7](#0-6) 

`_launchTimeVirtualLtReserve` recomputes the pair's launch-time virtual LT reserve as `k() / TOTAL_SUPPLY()` [8](#0-7) , a constant fixed forever at `mint`. The invariant the code relies on is that live `assetReserve` never drops below this constant. But `Router` deliberately has "No fees here" [9](#0-8) , and both `_computeBuy`/`_computeSell` use floor division against `k`, which systematically rounds in the trader's favor by up to 1 wei per call:

```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [10](#0-9) 

`Pair.swap`'s K-check only rejects a swap when `(newTokenReserve+1)*(newAssetReserve+1) < k` [11](#0-10) , i.e. it tolerates exactly the kind of sub-wei rounding slack `Router` produces. Because `reserveToken` is bounded above by `Token.TOTAL_SUPPLY()` (the virtual token reserve can never exceed total supply, since real balance transferred out via buys is capped at `curveSupply`), the tightest bound on `newAssetReserve` at `reserveToken == TOTAL_SUPPLY` is only fractionally below the launch-time `virtualLtReserve` — a margin on the order of `virtualLtReserve / TOTAL_SUPPLY`. An unprivileged trader who repeatedly performs small buy-then-sell round trips through `Bonding.buy`/`Bonding.sell` (each one extracting ~1 wei of rounding slack from `assetReserve` in their favor, since there is no protocol fee to cancel it out) can, given enough iterations (cheap, since each call is a tiny trade), erode `assetReserve` past that thin margin and below `_launchTimeVirtualLtReserve`.

The moment that happens, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts with a Panic — exactly the "parser panics on malformed/edge-case input" bug class in the reference advisory, except here the "input" is a legitimately-reachable sequence of ordinary buy/sell calls rather than a malformed expression string. Because `canGraduate` is called unconditionally inside every subsequent `buy()` and `sell()` for that token, the panic now fires on **every future call**, permanently:
- `Bonding.buy` → `_executeBuy` → `canGraduate` reverts, so no buy can ever complete again.
- `Bonding.sell` reverts before executing the sell (`canGraduate` check at line 598).
- `triggerGraduation` reverts inside its own `canGraduate` call, so phase-1 graduation can never be triggered either.

There is no owner/admin rescue path for a curve-phase `Pair` — `Router.graduate` is only reachable from `_prepareGraduationLiquidity`, which is itself unreachable once `canGraduate` cannot return `true`. The token, its real LT reserve, its real token balance, and the `LP_RESERVE` tokens minted for eventual LP seeding are all permanently stuck in `Pair`/`Bonding` with no way to trade, graduate, or recover funds.

### Impact Explanation
This is a permanent freezing of funds: all real LT and token balances held by the affected `Pair`, and the associated `LP_RESERVE` allocation reserved for LP seeding, become permanently unreachable once the underflow condition is triggered — no trading, no graduation, no admin override exists to unstick a `Lifecycle.Curve` token. This satisfies the "permanent freezing of trader, creator or LP funds" bar for a valid analog, and is reachable purely through unprivileged `Zap`/`Bonding` buy/sell calls.

### Likelihood Explanation
The rounding margin an attacker must close is extremely small in absolute terms (bounded by `virtualLtReserve / TOTAL_SUPPLY`, a small fraction of a wei-scale unit relative to 18-decimal LT amounts), and each round-trip buy/sell extracts up to 1 wei of favorable rounding slack with no protocol fee counteracting it. An attacker only needs gas to perform enough cheap round trips (bounded by `Zap`'s `minTransactionSize`/`MIN_SEED_USDC`-style floors, but still feasible over many transactions) to close that gap. This does not require any privileged role, timing, or race condition — only patience and gas.

### Recommendation
Replace the unguarded subtraction in `canGraduate` (and the identical pattern in `previewLtUntilGraduation`) with a saturating subtraction, mirroring the pattern already used elsewhere in `Bonding` (e.g. `finalizeGraduation`'s `ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0` and `_ltSwapInventory`) [12](#0-11) , so that `assetReserve` dipping at or below the recovered virtual reserve degrades gracefully (`realLtRaised = 0`) instead of reverting. Additionally, consider whether `Router._computeBuy`/`_computeSell` should round in the protocol's favor (ceiling on the amount charged, floor on the amount paid out) rather than the trader's, to remove the systematic erosion of `assetReserve` below its floor.

### Proof of Concept
1. Launch a token via `Zap.createToken`, establishing `Bonding`'s `canGraduate` invariant `assetReserve >= virtualLtReserve` at `_deployAndSeed`/`addInitialLiquidity` time [13](#0-12) .
2. As any unprivileged wallet, repeatedly call `Zap`'s buy/sell wrappers (or directly the allowlisted-router path) performing minimal-size `Bonding.buy` immediately followed by `Bonding.sell` of the exact tokens received, on the same token, many times. Each round trip exploits the floor-division rounding in `Router._computeBuy`/`_computeSell` [2](#0-1)  to extract a small amount of LT from the pair's stored `assetReserve` beyond what the exact curve formula would allow, tolerated by `Pair.swap`'s `+1` K slack [11](#0-10) .
3. Once accumulated rounding loss pushes `assetReserve` below `_launchTimeVirtualLtReserve(token, pair) = Pair.k() / Token.TOTAL_SUPPLY()` [8](#0-7) , the next call to `canGraduate` — triggered automatically inside the very next `Bonding.buy` or `Bonding.sell` — underflows at `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with a Panic.
4. From that point on, every `Bonding.buy`, `Bonding.sell`, and `triggerGraduation` call for that token reverts unconditionally, permanently freezing the token's curve, its real LT/token balances in `Pair`, and its reserved `LP_RESERVE` allocation with no recovery path.

        Token(tokenAddr).initialize(name_, ticker_, address(this));

        uint256 totalSupply = Token(tokenAddr).TOTAL_SUPPLY();
        uint256 curveSupply = (totalSupply * CURVE_BPS) / BPS_DENOM;

        pair = $.factory.createPair(tokenAddr, ltAddress);

        uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();

        // The raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out)
        // and is later deposited into a HyperSwap V2 pair, whose reserves are
        // `uint112`. Bound it at launch (4x headroom) so graduation can never
        // exceed that slot.
        if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();

        $.router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, virtualLtReserve);

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    /// @notice Tokens in → LT out.
    function sell(
        uint256 amountIn,
        address token,
        address to
    ) external onlyRole(BONDING_ROLE) returns (uint256 tokensIn, uint256 assetOut) {
        if (amountIn == 0) revert ZeroAmount();

        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        tokensIn = amountIn;

        IERC20(token).safeTransferFrom(to, pairAddr, amountIn);

        assetOut = _computeSell(pairAddr, amountIn);

        IPair(pairAddr).transferAsset(to, assetOut);

        IPair(pairAddr).swap(amountIn, 0, 0, assetOut);
    }

    function _computeSell(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
        assetOut = reserveAsset - (k / newReserveToken);
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
