## Title
Webhook shop/topic identity spoofing via unsigned headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the shop domain, topic, and webhook id used to route and process that body are read from separate, unsigned HTTP headers. This breaks the identity binding `HMAC-verified bytes == bytes used to identify the tenant/topic`: an attacker who can obtain one valid `(body, hmac)` pair for the app's single shared `client_secret` (e.g., from webhooks delivered to their own installed shop) can resend that exact body to the app's public webhook endpoint while substituting the `shopify-shop-domain` and `shopify-topic` headers, and the app will accept it as if it came from a different, victim shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only cover the raw body: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are pulled directly from HTTP headers that are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely against `to_signable_string` (the body) and the `hmac` header — it has no knowledge of `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` (unauthenticated header values) to build the metadata handed to the app's handler, with no cross-check that these values are bound to the verified body: [4](#0-3) 

Because a single app-wide `api_secret_key` is shared across every shop that installs the app, any shop (including one controlled by an unprivileged attacker who simply installs the app on their own store) can capture a legitimate `(body, hmac)` pair delivered to it and replay that body to the app's webhook endpoint with the `shopify-shop-domain`/`shopify-topic` headers rewritten to target another tenant. `HmacValidator.validate` will still return `true` because it never inspected those headers, so `Registry.process` will invoke the handler believing the (attacker-chosen) body legitimately originated from the victim shop/topic.

### Impact Explanation
This is a cross-tenant identity confusion: the equality the code implicitly assumes — "the shop/topic that produced HMAC-valid bytes" == "the shop/topic recorded in `WebhookMetadata`" — does not hold. An attacker can cause the host application to process attacker-crafted data (or a legitimate self-generated payload) as if it belonged to a different merchant's shop/topic (e.g. spoofing `app/uninstalled`, `shop/redact`, or order/customer topics for a shop they do not control), corrupting per-tenant state, deleting/altering another merchant's stored session or data, or triggering tenant-specific business logic under a false identity. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Low/Medium: the attacker needs to be able to install the target app on at least one shop they control (a normal, unprivileged action) in order to receive a genuinely HMAC-valid `(body, hmac)` pair, then send a crafted HTTP request directly to the app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic` headers. No access token, `api_secret_key`, or TLS interception is required — only the ability to install the app once and to send arbitrary HTTP requests to its exposed webhook route.

### Recommendation
Bind the identity fields into the verified signature domain instead of trusting separate headers: include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them, e.g., via a per-shop secret/session lookup validated after HMAC success), and reject requests where the header-derived shop is not the one the verified payload was actually generated for.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker.myshopify.com`, receiving a legitimate webhook POST with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC(app_secret, B)`, plus `shopify-shop-domain: attacker.myshopify.com` and `shopify-topic: app/uninstalled`.
2. Attacker re-sends an HTTP POST to the app's public webhook endpoint with the identical body `B` and `hmac H`, but with headers rewritten: `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:10-13`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to act on victim's shop under a forged identity.
