### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw JSON body via HMAC, while the `shop`, `topic`, `webhook-id`, and `api-version` values are read from unauthenticated HTTP headers. Because Shopify signs webhooks with the app's single, shop-agnostic `api_secret_key`, any merchant who installs the app on their own shop can obtain a genuinely-signed webhook body and then relabel it with an arbitrary victim shop domain, and the library will still accept it as authentic.

### Finding Description
The identity binding that should hold is:

`shop asserted to the handler == shop that produced/authorized the signed bytes`

In this gem that binding never exists. `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) using the app-wide `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` then dispatches to the handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, none of which were validated against the signature — only `HmacValidator.validate(request)` (body-only) gates processing: [4](#0-3) 

Because Shopify signs every webhook — for every installing shop — with the same app-level `client_secret`, a merchant with their own (even free/dev) shop installation can capture a validly-signed webhook body and headers, then modify only the `shop-domain` (and/or `topic`/`webhook-id`) header before replaying it to the app's webhook endpoint. The gem's verification path recomputes the HMAC over the body only, so the forged header sails through `Registry.process`'s `Utils::HmacValidator.validate(request)` check and the handler receives `data.shop` equal to the attacker-chosen victim domain with `data.body` fully controlled by the attacker (subject to matching a body that was legitimately signed, which is trivial since the attacker is the one who received the original webhook and knows its exact bytes).

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook processing: the app cannot distinguish "this event genuinely originates from shop X" from "an attacker relabeled a payload they legitimately received as originating from shop X." Any app logic keyed off `data.shop` (e.g., writing to per-shop records, triggering per-shop side effects, invalidating/refreshing sessions, billing state, or provisioning) can be manipulated by an unprivileged merchant to inject events attributed to another tenant — a cross-tenant access/confusion vulnerability with no privileged credentials required beyond running the app on the attacker's own store.

### Likelihood Explanation
Any merchant who can install the app (a normal, unprivileged flow) can generate real, validly-HMAC'd webhook bodies at will and capture the raw signed bytes. Forging the `shop-domain` header on a plain HTTP replay requires no cryptographic material beyond what Shopify already handed the attacker as part of a routine app installation, making this readily reachable by any internet-facing merchant.

### Recommendation
Bind the shop identity to the signature verification: either include the shop domain (and topic/webhook-id) in the HMAC-signed content, or cross-check `request.shop` against a shop known to have a stored, active session/access token for this app before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store (`attacker-shop.myshopify.com`) and triggers a webhook (e.g., `orders/create`) with body `B`, receiving headers including a valid `x-shopify-hmac-sha256` computed over `B` with the app's `api_secret_key`.
2. Attacker replays the identical raw body `B` and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `to_signable_string` returns `B` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and succeeds because `B` and the HMAC are unaltered — [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` even though the payload never actually originated from Shopify on behalf of that shop — [6](#0-5) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
