### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied, HMAC-uncovered `shop-domain` header to the app's handler as the trusted shop identity for that authenticated payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is read straight from the `hmac-sha256` header without any binding to the other headers [2](#0-1) . `shop`, `topic`, `api_version` and `webhook_id` are all pulled from headers that are never part of the signed payload [3](#0-2) .

`Registry.process` validates the request purely with `Utils::HmacValidator.validate(request)`, which computes `HMAC(secret, raw_body)` and compares it to the `hmac-sha256` header [4](#0-3) . Once that check passes, `process` builds `WebhookMetadata` using `request.shop` — i.e., the attacker-controllable `shop-domain` header — and passes it directly to the app's registered handler as the authenticated shop for that webhook body [5](#0-4) .

This is the exact bug class from the external report: an argument/field (`receiver` there, `shop-domain` header here) that is acted upon downstream is not covered by the binding that was actually verified (the token exchange there, the HMAC here). The equality that should hold is:

`shop covered by HMAC == shop delivered to handler`

but what is actually enforced is only:

`HMAC(body) == received_hmac`, with `shop` taken from an independent, unsigned header.

Because a legitimate webhook delivery for *any* shop that has ever installed the app (including one the attacker controls, e.g. a free/dev shop the attacker owns) produces a genuinely valid `(raw_body, hmac)` pair signed with the app's `client_secret`, that pair can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header swapped to a victim shop's domain. The HMAC check still succeeds because it never inspects the shop header, and `Registry.process` will invoke the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually belongs to the attacker's own shop.

### Impact Explanation
This breaks the tenant-isolation binding between an authenticated payload and the shop it is attributed to, which is exactly the class of cross-tenant issue in scope (Critical: cross-tenant access). Any app that uses `WebhookMetadata#shop` to key data (as shown in the gem's own documented usage: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will store or act on attacker-supplied body content under another merchant's shop identity — enabling cross-tenant data injection/corruption without needing the victim's access token, `client_secret`, or any privileged credential.

### Likelihood Explanation
The attacker only needs: (1) their own working relationship with the app (a shop that installed it, even a free dev store) so Shopify sends them a genuinely-HMAC-signed webhook, and (2) the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header, which the app's controller passes straight into `ShopifyAPI::Webhooks::Request.new(headers: request.headers.to_h)` as documented in `docs/usage/webhooks.md` [6](#0-5) . No secrets belonging to the victim are required, only the attacker's own valid webhook traffic and header manipulation on an unauthenticated network path, which fits the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and topic) identity into the signed material, or otherwise cryptographically tie the header values to the HMAC-verified body: e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require the host application to independently confirm the `shop` header corresponds to a shop with a stored session before trusting it. At minimum, document/enforce that `WebhookMetadata#shop` must never be treated as authenticated without a lookup against known installed shops.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering Shopify to deliver a real webhook (e.g. `orders/create`) with a body `B` and a valid `hmac-sha256` header `H = HMAC(client_secret, B)` and `shop-domain: attacker.myshopify.com`.
2. Attacker replays this exact `(B, H)` pair to the app's public webhook endpoint but replaces the `shop-domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `B` and compares to `H` [4](#0-3) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the attacker's own webhook body to be processed/stored as if it belonged to the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
