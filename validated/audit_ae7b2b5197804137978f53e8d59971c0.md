## Title
`vesting::distribute()` / `staking_contract::distribute_internal()` permanently locks all shareholders' unlocked stake if any single recipient's deposit reverts - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
The external report's custody invariant is: *a batch-distribution routine that pays out several recipients in one call must not let a single recipient's failure (inactive/blocked state) revert the entire distribution for all other, legitimate recipients.* The Aptos-native analog is `vesting::distribute()` (and structurally the same pattern in `staking_contract::distribute_internal()`), which iterate over all shareholders in a single atomic transaction and call `aptos_account::deposit_coins()` for each one.

### Finding Description
`vesting::distribute()` withdraws all currently-unlocked stake from the contract's stake pool and then pays every shareholder in a loop: [1](#0-0) 

Each iteration calls `aptos_account::deposit_coins(recipient_address, share_of_coins)`, which — for a recipient with no existing `CoinStore<AptosCoin>` who has previously called `set_allow_direct_coin_transfers(false)` — aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [2](#0-1) 

Because Move transactions are atomic and this loop has no per-iteration error handling (`for_each_ref` simply calls the deposit and propagates any abort), a single non-cooperative or malicious shareholder/beneficiary can make `distribute()` abort unconditionally, every time it is called, for the whole vesting contract — not just for their own share. This is the exact bug class from the seed report (`RewardThrottle._sendToDistributor` reverting for all pools if one distributor is inactive), reproduced at the Move/Aptos custody layer for AptosCoin distribution.

The impact escalates further because `terminate_vesting_contract()` unconditionally calls `distribute()` first, before it will flip contract state to `VESTING_POOL_TERMINATED`: [3](#0-2) 

and `admin_withdraw()` — the only function that can move the remaining stake pool balance to the withdrawal address — requires the contract to already be in `VESTING_POOL_TERMINATED` state: [4](#0-3) 

So if `distribute()` can never succeed, `terminate_vesting_contract()` can never succeed either, and `admin_withdraw()` becomes permanently unreachable. All remaining unlocked/vested stake becomes stuck in the vesting contract's stake pool with no recovery path — a "permanent lock of ... resource-account-held value" per the custody impact gate, since vesting contracts are backed by resource accounts (`create_vesting_contract_account`).

The same structural pattern (loop over `distribution_pool.shareholders()`, deposit via `aptos_account::deposit_coins` inside a `while`) exists in `staking_contract::distribute_internal()`: [5](#0-4) 

The framework's own formal-verification specs explicitly acknowledge this can't be reasoned about and disable verification for exactly this abort-in-loop pattern: [6](#0-5) 

### Impact Explanation
This breaks the custody invariant that deposit/withdraw/transfer paths must preserve holder access to their entitled value. A single griefing shareholder (or even an inadvertently-configured one, e.g. someone who ran `set_allow_direct_coin_transfers(false)` before ever receiving direct AptosCoin) can indefinitely freeze payout of vested/unlocked stake for every other beneficiary of the same vesting contract, and prevent the admin from ever terminating the contract or withdrawing the remainder — a non-recoverable loss of resource-account-held value for all co-beneficiaries, not just the griefer.

### Likelihood Explanation
I was unable to fully verify two preconditions with the tools available before running out of budget:
1. Whether `coin::is_account_registered<AptosCoin>` / `coin::register` still gate deposits this way post the fungible-asset migration for `AptosCoin` specifically, or whether `aptos_account::deposit_coins` now silently succeeds via the FA path regardless of `DirectTransferConfig` for coins that have migrated to a `FungibleStore`.
2. Whether `vesting::set_beneficiary` is admin-only, and whether an ordinary shareholder can influence which address is actually targeted by `get_beneficiary()` (i.e., can the griefing address be freely chosen by the shareholder, or only by the admin).

If AptosCoin has been fully migrated such that `deposit_coins` never hits the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` abort path for AptosCoin, the concrete trigger described here would not apply for AptosCoin (it could still apply for other, non-migrated `CoinType`s used with `staking_contract`/`vesting`, and the frozen-`CoinStore` variant of the same DoS remains possible for any coin type with an active freeze capability). This uncertainty means the finding should be treated as a **likely but not fully confirmed** DoS/permanent-lock vector, contingent on the exact current registration/deposit semantics of `aptos_account::deposit_coins` for the coin type in use.

### Recommendation
- Make `distribute()` (and `distribute_internal()`) resilient to a single recipient's deposit failure: e.g., wrap each `aptos_account::deposit_coins` call so a failure only skips/re-queues that shareholder's share (leaving their shares un-redeemed in the pool) rather than aborting the whole loop.
- Decouple `terminate_vesting_contract()` from a successful `distribute()` call, or provide an explicit "force terminate, sweep remaining pool to withdrawal address ignoring individual redemption failures" escape hatch so a single uncooperative recipient cannot hold the entire resource-account-held stake hostage.
- Confirm and, if necessary, harden `aptos_account::deposit_coins` behavior for both legacy `CoinStore` and FA-migrated stores so that per-recipient opt-out/registration state cannot be leveraged to grief batch payout functions used by custody-relevant framework modules (`vesting`, `staking_contract`).

### Proof of Concept
Conceptual reproduction (pending confirmation of registration semantics noted above):
1. Admin creates a vesting contract with shareholders `A` and `B` via `vesting::create_vesting_contract`, each with a nonzero grant.
2. Shareholder `B` (or an address `get_beneficiary` resolves to for `B`) calls `aptos_account::set_allow_direct_coin_transfers(false)` before ever receiving/registering an `AptosCoin` `CoinStore`.
3. Time passes; stake accrues rewards and vests. Anyone calls `vesting::distribute(contract_address)`.
4. The loop reaches `B`'s deposit, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The whole transaction, including `A`'s payout and the stake withdrawal, is rolled back. `distribute()` will abort identically on every future call as long as `B`'s configuration is unchanged.
6. `terminate_vesting_contract()` also aborts (step 1 of that function calls `distribute`), so `admin_withdraw()` is permanently unreachable — all remaining stake-pool value for the vesting contract (affecting both `A` and `B`) is stuck.

        distribute(contract_address);

        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );
