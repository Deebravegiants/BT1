### Title
`Bonding.transferCreator` performs an irrevocable, single-step creator-ownership change with no confirmation step, unlike every other sensitive-role transfer in the protocol - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external report describes Nextcloud missing a password re-confirmation before a sensitive account-level configuration change (external storage), so a hijacked session can immediately and silently reconfigure/destroy storage credentials with no second check. The analogous bug class in alt.fun is a state-changing function that permanently reassigns control of a valuable on-chain role in a single transaction, with no confirm/accept step, no time delay, and no way for the legitimate party to recover — even though the codebase explicitly adopts a two-step confirmation pattern (`Ownable2StepUpgradeable`) everywhere else specifically to protect against this exact failure mode.

### Finding Description
`Bonding.transferCreator` reassigns the `creator` of a launched token in one atomic call, gated only by `msg.sender == info.creator`: [1](#0-0) 

There is no pending-transfer / accept-by-new-creator step, no time lock, and no owner override. Compare this to the protocol's own stated rationale for using `Ownable2StepUpgradeable` on `Bonding`, `Zap`, and `FeeVault`: the doc comments explicitly say a single-step transfer to a fat-fingered or compromised address is unacceptable because it is irreversible and "would otherwise brick every owner-only path," so the protocol deliberately requires the new owner to explicitly accept the role before it takes effect: [2](#0-1) 

That same rationale applies with equal force to `transferCreator`, since the `creator` role controls all future protocol-fee routing for the token, yet no such safeguard exists there. Any signature phished from the creator's wallet, a copy/paste mistake in the destination address, or a compromised hot-key session lets an attacker (or a bug) call `transferCreator` directly and instantly redirect the role — with zero opportunity for the legitimate creator, or the protocol owner, to detect and cancel the change before it takes effect, exactly mirroring the "missing confirmation before a sensitive account-level change" bug class in the external report.

The role is not merely cosmetic: `Zap._accrueFee` reads the *current* creator via `bonding_.creatorOf(tokenAddress)` on every buy/sell to route the creator's share of trading fees into `FeeVault.creatorBalance`: [3](#0-2) [4](#0-3) 

and `FeeVault.claim()` pays out whatever `creatorBalance[msg.sender]` currently holds: [5](#0-4) 

Once `transferCreator` fires, every subsequent trade's creator-fee share accrues to the new address, permanently and irrevocably, for as long as the token trades.

### Impact Explanation
A single unconfirmed call to `transferCreator` permanently redirects 100% of all future creator-fee revenue (`creatorFeeBps` share of every buy/sell fee, for the token's entire remaining lifetime, including the entire post-graduation lifetime) away from the legitimate creator to whatever address ends up as `info.creator` — with no recourse, no owner override, and no ability to reverse. This is a permanent freezing/redirection of creator funds, reachable by exactly the class of unprivileged, direct-caller interaction the report is scoped to.

### Likelihood Explanation
`transferCreator` is a fully public function requiring only that `msg.sender` equal the current stored creator; the only friction is that the creator's key/session must be used once. Phishing a single signature, a fat-fingered destination address, or a drained/compromised creator hot wallet is a realistic and common attack vector for launchpad creators (who are typically less operationally secure than the protocol multisig), making this a plausible, medium-likelihood exposure, especially since the protocol's own code comments show the team already recognized and mitigated this exact risk class for `Ownable2StepUpgradeable` roles but did not extend the same protection to `transferCreator`.

### Recommendation
Convert `transferCreator` to a two-step pending/accept pattern analogous to `Ownable2StepUpgradeable`: store a `pendingCreator` on the first call, and only finalize the transfer when `pendingCreator` calls a second `acceptCreator()` function. This mirrors the mitigation the report and the protocol's own owner-transfer pattern both converge on, closing the fat-finger/compromised-signature/no-confirmation gap without weakening the permissionless design.

### Proof of Concept
1. Attacker phishes the creator of token `T` into signing/sending a transaction (or the creator's key is compromised) calling `Bonding.transferCreator(T, attacker)`.
2. `msg.sender == info.creator` check passes trivially since the call originates from the legitimate creator's own compromised session/key — no second confirmation, no delay, no owner check exists to stop it.
3. `info.creator` is immediately and permanently set to `attacker` (`Bonding.sol:746`).
4. From this point on, every `Zap.buy`/`Zap.sell` for `T` routes the creator-fee share to `attacker` via `FeeVault.accrue` (`Zap.sol:259`, `Zap.sol:465`), and `attacker` can call `FeeVault.claim()` to drain all future creator earnings; the true creator has no way to recover the role or the diverted fees.

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```text
    function _accrueFee(
        address token,
        address creator,
        uint256 feeAmount,
        bool isBuy
    ) internal {
        ZapStorage storage $ = _s();
        uint256 creatorShare = (feeAmount * $.creatorFeeBps) / BPS_DENOM;
        uint256 protocolShare = feeAmount - creatorShare;
        $.usdc.safeTransfer(address($.feeVault), feeAmount);
        $.feeVault.accrue(token, creator, creatorShare, protocolShare, isBuy);
    }
```
