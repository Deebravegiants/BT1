Based on my investigation, I found a genuine analog to the reported bug class in `orb-core`.

### Title
Unverified attacker-controlled `user_centric_signup` flag allows unauthorized signup crediting without backend confirmation - (File: `src/plans/mod.rs`)

### Summary
The MonoX bug credited liquidity-pool tokens ("minted") based on a *declared* transfer amount rather than the *actual, verified* amount moved. The structural analog in `orb-core` is in `MasterPlan::do_signup`: when the QR-scanned user data sets `user_centric_signup = true`, the orb credits the signup as successful/completed purely from its own locally-computed `signup_reason` (device-side pipeline/fraud result), and it never performs the authoritative round trip to the backend (`enroll_user`, which calls `signup_post::request` + `signup_poll::request`) that would confirm the signup was actually accepted/completed server-side.

### Finding Description
In `src/plans/mod.rs`, `do_signup` computes `signup_reason` purely from on-device signals (`pipeline.is_none()`, `fraud_detected`) at [1](#0-0) . It then branches on `user_centric_signup`, a boolean taken from `qr_codes.user_data.user_centric_signup` [2](#0-1) :

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
``` [3](#0-2) 

When `user_centric_signup` is true, the orb sets `enroll_user::Status::Success`/completes the signup **without ever calling `enroll_user`**, i.e. without the backend `signup_post`/`signup_poll` round trip that authoritatively records a completed, backend-confirmed signup [4](#0-3) . The one true fraud-detection gate that would prevent bogus credit is also permanently a no-op: `detect_fraud` in this build always returns `false` because "WE HAVE DELETED ALL FRAUD CHECKS" [5](#0-4) .

`user_centric_signup` is sourced from `authenticated_app_data` returned by the backend's user-status endpoint and is gated only by a hash-consistency check (`user_data.verify(user_data_hash)`) between data supplied via the user's own QR code and data returned from the backend [6](#0-5) . This is exactly analogous to MonoX trusting a self-declared transfer/amount instead of measuring the real, backend-verified outcome: the orb credits a "successful signup" state based on the *locally declared* completion condition (device pipeline result mapped directly to `Status::Success`) rather than a verified backend-confirmed state.

### Impact Explanation
If the on-device `signup_reason`/fraud path can be forced into `SignupReason::Normal` (trivial, since fraud detection is entirely disabled in this build) while `user_centric_signup` is true, the orb marks the signup as `Success` and finalizes debug/report state without any backend confirmation that the signup was actually accepted, deduplicated, or fraud-checked server-side. This creates a cross-signup state-bleed / misattributed-signup risk: locally credited "successful signup" telemetry/state diverges from backend ground truth, and mirrors the MonoX pattern of crediting on unverified declared state.

### Likelihood Explanation
Likelihood depends on whether an unprivileged user (the person being enrolled, controlling their own phone's QR data) can set `user_centric_signup = true` for their own session and rely on the always-disabled fraud check. Given `detect_fraud` is a hardcoded no-op returning `false` in this build [7](#0-6) , `signup_reason` is `Normal` whenever the pipeline runs to completion, making this reachable during any normal user-centric signup — not requiring a broken/malicious peer or operator.

### Recommendation
Do not derive a final `Success` enrollment status purely from locally-computed `signup_reason` when `user_centric_signup` is set. Require an explicit backend acknowledgment (analogous to `signup_post`/`signup_poll`) confirming the signup was actually recorded server-side before setting `enroll_user::Status::Success`, mirroring the MonoX fix of deriving credited state from verified, measured outcomes rather than declared/local ones.

### Proof of Concept
1. Complete a normal biometric capture/pipeline so `pipeline.is_some()`.
2. Since `detect_fraud` always returns `false` [7](#0-6) , `signup_reason` resolves to `SignupReason::Normal`.
3. With `user_centric_signup = true` (set via the user's own scanned QR-derived backend response) and `ignore_user_centric_signups = false`, `do_signup` sets `enroll_user::Status::Success` and `result.success = true` at [8](#0-7)  without ever invoking `enroll_user` / the backend `signup_post`+`signup_poll` confirmation flow used in the non-user-centric path [9](#0-8) .
