Confirmed: there is no rescue/redirect/pull-payment mechanism in `IntentsBase`/`ExtrinsicIntents` — `_withdraw` unconditionally pushes tokens via `IERC20.safeTransfer(beneficiary, amount)` [1](#0-0) , and the beneficiary for `RedeemEscrow` is the solver address baked into the cross-chain message at fill time on the destination chain [2](#0-1) , with no way to change it once dispatched.

### Title
Permanent freezing of escrowed input tokens when the RedeemEscrow beneficiary (filler) is blacklisted by a compliance-controlled ERC20 (e.g., USDC/USDT) - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` releases escrowed order-input tokens by pushing them directly to a fixed `beneficiary` address via `IERC20.safeTransfer`. For cross-chain fills, that beneficiary is the solver's `msg.sender` address, captured immutably inside the `RedeemEscrow` message body when `_fillCrossChain` dispatches it from the destination chain [3](#0-2) . If that solver address is later blocklisted by the escrowed token's issuer (USDC/USDT-style contract-level blocklist), every attempt to deliver the `RedeemEscrow` message on the source chain will revert forever, since the beneficiary address cannot be changed after the message is committed and signed over by ISMP.

### Finding Description
On a cross-chain fill, `_fillCrossChain` marks the order filled, delivers output tokens to the user, and dispatches a `RedeemEscrow` `WithdrawalRequest` naming `msg.sender` (the filling solver) as `beneficiary` [3](#0-2) . When this message arrives on the source chain, `onAccept` authenticates it and calls `_withdraw(body, false, true)` [4](#0-3) . `_withdraw` decrements the escrow accounting and unconditionally does `IERC20(token).safeTransfer(beneficiary, amount)` for every escrowed input token, plus a second `safeTransfer` of accumulated fee-token fees to the same beneficiary [5](#0-4) .

If the input token is a blocklist-capable stablecoin and the solver address held in the already-dispatched message has since been blocklisted (or was blocklisted by the time delivery is attempted), this transfer reverts. `EvmHost.dispatchIncoming` treats a reverting `onAccept` call as "not delivered" and deletes the stored request receipt so the message "can be retried" [6](#0-5) . However, retrying is futile here: the beneficiary address is fixed inside the already-committed message body (part of the request hash verified by the MMR membership proof in `HandlerV2.handlePostRequests`), so every future relayer submission reaches the identical `safeTransfer(blacklistedBeneficiary, amount)` call and reverts identically, forever.

The order is already marked filled on the destination chain (`_filled[commitment] = msg.sender`) and the user has already received their output tokens there, so there is no cancellation path back to the user on the source chain — the escrowed input tokens are permanently stuck in the `IntentGatewayV2` contract, unreachable by the solver (blocked), the user (order already filled/settled), or governance (no sweep/rescue function exists for a specific stuck order's principal — `SweepDust` only sweeps protocol-fee dust, not escrowed order funds). This mirrors the referenced Cooler audit finding: a push-only payment to a party that can become non-transferable turns a normal settlement into a permanently stuck state.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any solver who fills a cross-chain order with escrow denominated in a blocklist-capable ERC20 (USDC, USDT, and similar). No malicious protocol actor is required — an external stablecoin issuer's compliance action against the solver's address after (or even before, if front-run) the fill is sufficient to lock the corresponding escrow permanently, since Hyperbridge's message-delivery retry semantics cannot alter the already-committed beneficiary. This qualifies as High severity: concrete, permanent loss of user/solver funds with no available recovery path in the current contract.

### Likelihood Explanation
Likelihood is moderate to high in the medium-to-long run given IntentGatewayV2 supports arbitrary ERC20 inputs and USDC/USDT are among the most liquid, most commonly bridged/escrowed assets. Any solver whose address is later placed on Circle's or Tether's blocklist (a routine compliance action, e.g. due to prior unrelated on-chain activity, sanctions exposure, or flagged counterparties) will have all of their pending in-flight `RedeemEscrow` claims for that token become permanently unrecoverable the moment the blocklist takes effect before delivery completes.

### Recommendation
Replace the direct push-transfer in `_withdraw` with a pull-payment pattern for cases where the transfer can fail: on `safeTransfer` failure (caught via a low-level call/try-catch), credit the beneficiary's claimable balance in an internal accounting mapping instead of reverting the whole delivery, and expose a separate `claim(token, amount)` function that lets the beneficiary (or a governance-controlled rescue path) redirect/withdraw to an alternate address. This prevents any single blocked address from causing indefinite non-delivery and permanent fund lock-up of escrowed order tokens.

### Proof of Concept
1. A solver `S` fills a cross-chain order whose input token is USDC, calling `fillOrder` on the destination chain; `_fillCrossChain` sets `_filled[commitment] = S`, delivers outputs to the user, and dispatches a `RedeemEscrow` `WithdrawalRequest{beneficiary: S}` to the source chain [3](#0-2) .
2. Before the message is relayed and delivered on the source chain, Circle blocklists address `S` on USDC.
3. A relayer submits the `RedeemEscrow` proof via `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept` → `_withdraw` [7](#0-6) ; the `USDC.transfer(S, amount)` call inside `safeTransfer` reverts because `S` is blocklisted.
4. `dispatchIncoming` catches the failure and deletes the request receipt, logging it as retryable [6](#0-5) .
5. Every subsequent delivery attempt replays the identical committed message body (`beneficiary = S`), so the transfer reverts identically forever; the escrowed USDC remains locked in `IntentGatewayV2` on the source chain with no function available to redirect it to an unblocked address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }
