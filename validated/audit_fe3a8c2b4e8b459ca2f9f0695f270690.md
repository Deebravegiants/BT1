### Equality claimed broken
`value moved out of Emporium's on-chain position by op.endpoint.call(...)` **≠** `amountChanges[i] + utxoAmount[i]` summed over `circomData.erc20TokenAddresses` — because `erc20TokenAddresses = []` on the Min-path transact, so both sides of every accounting loop are vacuously `0`, regardless of what value actually left Emporium.

### Title
Unauthenticated Emporium `EmporiumStack` execution via Min-path (`erc20TokenAddresses=[]`, `signerAddress=0`) allows arbitrary `msg.sender==Emporium` calls draining any asset Emporium holds - (File: `circuits/MainEVMCircuitMin.circom`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
When `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes the proof through the trivial `MainEVMCircuitMin` circuit, which only proves knowledge of a `messageSeed`. Every balance/UTXO accounting loop in `Hinkal.sol` and `EmporiumUpgradeable.runAction` is keyed off `circomData.erc20TokenAddresses`, so with an empty array none of them execute, and `EmporiumUpgradeable.verifyWallet` skips the EIP-712 signature check entirely when `stack.signerAddress == address(0)`. The net effect is that any unprivileged EOA can force Emporium to execute an arbitrary `op.endpoint.call{value: op.value}(op.callData)` as `msg.sender == address(Emporium)`, with zero on-chain economic constraint, redirecting any asset Emporium holds (vault shares, tokens, ETH) to the attacker.

### Finding Description
`CircomDataBuilder.formInputForCircom`: [1](#0-0) 
selects `formInputEmporiumMin` whenever `erc20TokenAddresses.length == 0` for the Emporium action, which corresponds to the `MainEVMCircuitMin` template: [2](#0-1) 
This circuit constrains nothing about tokens, nullifiers, or amounts — it only proves `message = Poseidon(messageSeed)`, a value the attacker freely chooses.

`dimensionsCheck` in `HinkalHelper.sol` only requires internal array-length consistency (all zero-length when `tokenNumber == 0`); it never requires `tokenNumber > 0`: [3](#0-2) 

In `Hinkal.sol`, `_externalTransact` and the entire post-call balance/slippage/UTXO reconciliation loop iterate strictly over `circomData.erc20TokenAddresses`: [4](#0-3) [5](#0-4) 
With `erc20TokenAddresses = []`, these loops execute zero iterations — no balance is ever checked, no slippage, no `amountChanges`/`utxoAmount` equality is evaluated for whatever token actually moves.

Inside `EmporiumUpgradeable.runAction`, the same is true: `balancesBefore`/`balancesAfter` and the resulting `utxoSet` are computed only over `circomData.erc20TokenAddresses` (again empty), so the internal "BalanceChangeShouldBePositive" guard never runs for any token not in that list: [6](#0-5) 

Critically, `verifyWallet` — the only remaining authorization gate on the arbitrary `ops` array — is a no-op whenever the attacker sets `stack.signerAddress = address(0)`: [7](#0-6) 
It only marks `circomData.emporiumMessage` as used (an attacker-chosen, unconstrained value) and returns — no EIP-712 signature, no restriction on `stack.ops` content is enforced.

`stack.ops` is then executed as CASE 2 "Stateless Interaction": [8](#0-7) 
`op.endpoint.call{value: op.value}(op.callData)` executes with `msg.sender == address(Emporium)`. Emporium is a single shared contract instance for all protocol users, so any asset it holds from any user's earlier legitimate multi-token transact (e.g., ERC4626 vault shares obtained where the share token differs from, and is therefore absent from, that deposit transact's `erc20TokenAddresses`) is available to be moved by this call.

Exact attacker call: attacker calls `Hinkal.transact(...)` with:
- `circomData.externalActionData.externalActionId` = Emporium's registered id, `externalAddress` = Emporium
- `circomData.erc20TokenAddresses = []`, all dimension-linked arrays `[]`
- `circomData.originalSender = attacker`, `circomData.relay = address(0)` (so `relayerIsValid` and the `originalSender` check both pass trivially for an unprivileged caller)
- `circomData.externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: victimVaultOrToken, invokeWallet: false, value: 0, callData: redeem(shares, attacker, address(emporium)) or transfer(attacker, balance) }] }`
- a valid proof for `MainEVMCircuitMin` (trivial — prover just picks any `messageSeed`), and any existing historical `rootHashHinkal`/index (the Min circuit does not constrain `rootHashHinkal` at all, so any valid tree root satisfies `rootHashExists`).

Because `owner == msg.sender == address(Emporium)` in the `redeem` call (or because the endpoint is the token itself), no allowance/authorization from any legitimate depositor is required, and the underlying assets/tokens go straight to the attacker. No nullifier is spent, no root-hash-tied membership is proven for this value, and no balance-diff check anywhere catches the outflow, since every accounting structure is empty by construction.

### Impact Explanation
Critical — direct theft of protocol/relay-held (Emporium-held) value: any token or ETH balance sitting in the shared `EmporiumUpgradeable` contract (deposited there via legitimate prior multi-token transacts by any user, or vault shares/redemption proceeds accrued there) can be extracted to an attacker-chosen address by an arbitrary unprivileged party. This is not limited to the "fake vault" framing in the question — since `op.endpoint`/`op.callData` are fully attacker-controlled and unconstrained, the attacker can equally target any legitimate vault holding Emporium's shares, or directly call `transfer` on any ERC20 Emporium is currently holding, or drain its ETH via `op.value`-less calls. The action is repeatable for every distinct `emporiumMessage` value and against every asset the contract holds at time of attack.

### Likelihood Explanation
Preconditions: Emporium contract must hold some redeemable/transferable value from prior legitimate activity by any user of the protocol (a normal, expected state given Emporium's role as position-holder). Attacker cost is a single `transact()` call with a proof for the trivial Min circuit (cheap, self-generatable) and no dependency on any privileged role, relay, or victim's keys — fully feasible for any unprivileged EOA as defined in scope.

### Recommendation
Do not allow the Min-path / empty-`erc20TokenAddresses` route to reach `EmporiumUpgradeable.runAction` with `stack.signerAddress == address(0)` and arbitrary `stack.ops`. Specifically:
- Require `stack.signerAddress != address(0)` (i.e., mandatory EIP-712-authorized wallet signature) for any Emporium call that carries no token-list accounting (`erc20TokenAddresses.length == 0`), so unauthenticated "stateless" arbitrary calls can never execute as `msg.sender == Emporium` without the legitimate position owner's signature.
- Alternatively/additionally, tie the Min-path authorization to a real economic constraint (e.g., require the circuit to bind `emporiumMessage`/`ops` hash to a spent nullifier or owner-specific commitment), so that only the party who actually deposited/owns the underlying Emporium position can trigger stateless ops against it.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, a mock ERC20 `Underlying`, and a mock ERC4626-like `Vault`.
2. Victim performs a legitimate multi-token `transact()` depositing `Underlying` into `Vault` via Emporium, resulting in Emporium holding `shares` (share token address not included in that transact's `erc20TokenAddresses`). Record `Vault.balanceOf(emporium) == shares` and `Underlying.balanceOf(attacker) == 0`.
3. Attacker crafts `EmporiumStack{signerAddress: address(0), ops:[{endpoint: vault, invokeWallet:false, value:0, callData: abi.encodeCall(vault.redeem,(shares, attacker, address(emporium)))}]}`, sets `circomData.erc20TokenAddresses = []`, `originalSender = attacker`, `relay = address(0)`, generates a Min-circuit proof locally, and calls `Hinkal.transact(...)`.
4. Assert: `Underlying.balanceOf(attacker)` increases by the redeemed amount; `circomData.erc20TokenAddresses.length == 0` for this call; and that no `require` in `Hinkal.sol`'s balance-diff loop (lines 96-146) or `EmporiumUpgradeable.runAction`'s balance loop executed (since both arrays are empty) — i.e., value moved (`Underlying` transferred to attacker) is strictly greater than `amountChanges + utxoAmount` accounted for that token (which is `0`).
