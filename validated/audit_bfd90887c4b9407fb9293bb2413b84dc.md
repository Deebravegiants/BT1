### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request **body**, but the `shop` value that is subsequently handed to the app's webhook handler (used by the host app to attribute the event to a tenant) is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP **header**, which is never included in the signed material. This breaks the identity binding `hmac_signed_bytes == bytes_attributed_to_shop`, allowing an attacker who possesses one validly-signed webhook body (e.g. from their own store, or from any publicly obtainable webhook payload for the shared app secret) to replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook for a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from unauthenticated headers with no involvement in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

The equality that should hold is:

`HMAC(client_secret, raw_body) valid  ⇒  shop attributed to that body is the shop that actually sent it`

But the gem only proves `HMAC(client_secret, raw_body)` is valid — it proves nothing about which shop the body belongs to, because `shop` is outside the signed bytes. Any header value can be substituted without invalidating the signature, since a single `client_secret` is shared across all shops installed on a multi-tenant app, and the signature is computed over the body alone.

### Impact Explanation
This is a cross-tenant identity-binding break (matches "bytes verified versus bytes parsed"/attribution-not-bound-to-signature class from the report). An attacker who operates their own shop with the target app installed can capture one legitimately-signed webhook body+HMAC pair for their own store (trivial, since they receive their own webhooks), then replay that exact body/HMAC to the app's webhook endpoint while spoofing `x-shopify-shop-domain` (and, since it isn't checked either, `x-shopify-topic`/`x-shopify-webhook-id`) to point at a victim shop. `Registry.process` will pass HMAC validation and invoke the app's handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker's own body>, ...)`. Depending on how the host app uses `shop` to look up/act on tenant records (e.g. `app/uninstalled`, `shop/update`, `customers/data_request`), this can cause cross-tenant state corruption — an explicit Critical-tier impact category ("cross-tenant access").

### Likelihood Explanation
Requires the attacker to be an unprivileged user who can install the target app on their own store (or otherwise obtain one valid signed webhook payload) and send an HTTP request to the app's public webhook endpoint with forged headers — no access token, `api_secret_key`, or privileged account needed. This is a realistic, low-effort attack against any host app that relies on this gem's `Registry.process`/`WebhookMetadata.shop` for tenant attribution.

### Recommendation
Bind the shop (and topic/webhook id) to the signature verification, not just the raw body: reject the webhook if the caller cannot independently corroborate the `shop-domain` header (e.g., by looking up the shop in the app's own registered-webhook or session store before trusting `data.shop`), or extend `VerifiableQuery`/`HmacValidator` so it accepts a canonicalized string that includes the shop/topic headers rather than only `raw_body`, mirroring how `AuthQuery#to_signable_string` includes `shop` in its signed parameters (`lib/shopify_api/auth/oauth/auth_query.rb`, lines 34-43). At minimum, document prominently that `WebhookMetadata#shop` is not integrity-protected by the HMAC check and must not be trusted for tenant lookups without additional verification.

### Proof of Concept
1. Attacker installs the target (multi-tenant) app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint, but changes only the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com` (keeping body `B` and hmac `H` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes, because validation only recomputes `HMAC(client_secret, B)` and compares to `H`, per [5](#0-4) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <parsed B>, ...)`, per [6](#0-5) , causing the host app to process attacker-controlled webhook content as if it originated from the victim shop.
