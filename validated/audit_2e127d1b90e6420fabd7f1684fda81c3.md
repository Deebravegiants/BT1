This is `ismp-abi`, a crate that generates Rust types mirroring the Solidity ABI and converts them into the types consumed by `beefy-verifier-primitives` for verification — it is a cross-language ABI/type-conversion layer, not a CLI or offline-prover-only tool (unlike `dnsreplay`). It sits directly in the path that turns relayer-submitted, ABI-encoded consensus proof calldata into the structures fed to BEEFY consensus verification.

### Title
Panic-inducing fixed-size buffer copy in BEEFY `Vote`→`SignatureWithAuthorityIndex` conversion - (File: evm/rust/src/conversions.rs)

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` copies an attacker/relayer-supplied, dynamically-sized `bytes` field into a fixed 65-byte array using `copy_from_slice` without first validating the length of the source slice. [1](#0-0) 

### Finding Description
`SignedCommitment.votes` in the `BeefyConsensusProof` ABI type carries a `Vote { signature: bytes, authorityIndex: uint32 }` for each authority signature. When converting a decoded `Vote` into the internal `SignatureWithAuthorityIndex` used by `beefy-verifier-primitives`, the code does:
```rust
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
``` [2](#0-1) 
`TSignature` is a fixed `[u8; 65]` array. [3](#0-2) 
Because `signature` is a Solidity `bytes` field, an attacker submitting a `BeefyConsensusProof` (e.g., through a relayer-facing consensus-update entry point) can supply a signature of any length other than 65. `Vec::copy_from_slice` panics whenever the source and destination lengths differ — this is the Rust memory-safe analog of the C-style stack buffer overflow in `dnsreplay`: a fixed-size buffer is populated from unchecked, attacker-controlled variable-length input. Instead of corrupting memory, in Rust it triggers an unconditional panic/abort of the process performing the conversion.

### Impact Explanation
A malformed `signature` length in a submitted BEEFY consensus proof would cause the process performing this ABI-to-internal-type conversion to panic. If this conversion executes inside a consensus-update code path that is directly reachable by any unprivileged submitter of a `BeefyConsensusProof`/`RelayChainProof`, this becomes a denial-of-service that can halt consensus-state updates, blocking the "route" that delivers cross-chain messages relying on that BEEFY light client (mapping to the "route unable to deliver messages" impact category).

### Recommendation
Regardless of exact call-site reachability, replace the unchecked `copy_from_slice` with a length-checked conversion (e.g., `TryFrom<&[u8]>` returning an error on any length other than 65), and propagate that error through the `From` impl's caller (converting it to a `TryFrom` impl) so malformed proofs are rejected gracefully instead of panicking.

### Proof of Concept
1. Construct a `BeefyConsensusProof` ABI payload whose `SignedCommitment.votes[i].signature` is not exactly 65 bytes (e.g., 64 or 66 bytes).
2. Submit/relay this proof through whatever path invokes the `substrate`-feature `From<BeefyConsensusProof> for ConsensusMessage` conversion (which transitively calls `From<Vote> for SignatureWithAuthorityIndex`). [4](#0-3) 
3. Observe the process panics on `signature.copy_from_slice(&sig_bytes)` due to length mismatch, before any cryptographic verification of the signature is attempted.
