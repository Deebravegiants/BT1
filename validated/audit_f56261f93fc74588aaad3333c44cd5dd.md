### Title
stSTXbtc collateral is priced as if it were plain STX with no exchange-rate adjustment, mispricing collateral value - (File: `mainnet/contracts/utility/v0-1-data.clar`, `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/proposals/mainnet/v0-init.clar`)

### Summary
The `stSTXbtc` asset (a liquid-staked-STX derivative token, described in docs as "Liquid staking with BTC-denominated yield") is registered with a Pyth oracle feed pointing at the raw `STX-FEED-ID` and with `callcode: none`, meaning its USD price is computed as literally the STX/USD price with no adjustment for its actual STX-per-token exchange rate.

### Finding Description
In `v0-init.clar` (and the mirrored `proposal-protocol-init.clar`), asset registration for `stSTXbtc` explicitly sets: [1](#0-0) 
This differs from the analogous `stSTX` asset registration a few lines above, which is deliberately given `callcode: (some CALLCODE-STSTX)` so that the STX price is scaled by the live STX-per-stSTX staking ratio before use: [2](#0-1) 

The price is then consumed identically to any other asset via `get-asset-price` / `price-resolve` in `v0-1-data.clar`, where `stSTXbtc` returns the raw Pyth STX price with no ratio applied, unlike `stSTX` which explicitly multiplies by its staking ratio: [3](#0-2) [4](#0-3) 

This value is directly used to compute collateral USD value for LTV/health-factor checks, e.g. `sum-collateral-usd` in `v0-1-data.clar` multiplies raw token `amount` by this `price`: [5](#0-4) 

The identity that should hold is:
```
price(stSTXbtc) = price(STX) × (STX redeemable per stSTXbtc)
```
but the registered oracle configuration instead computes:
```
price(stSTXbtc) = price(STX) × 1
```
which is correct only if 1 `stSTXbtc` is permanently redeemable for exactly 1 STX. This is the same bug class as the Lido finding: an intermediate/wrapped yield-bearing token's price is read directly from the base asset's oracle feed without applying the conversion ratio between the wrapped token and its underlying.

### Impact Explanation
Because I was unable to fully retrieve the `ststxbtc-token-v2`/vault-ststxbtc source (tool truncation prevented reading its `convert-to-assets`/redemption-rate logic in this session), I cannot conclusively prove whether `stSTXbtc` actually accrues an appreciating (or depreciating) exchange rate relative to STX in the way `stSTX` does. If it does — which is strongly suggested by the docs describing it as a "Liquid staked STX" token with its own vault (`vault-ststxbtc`) distinct from `stSTX`, and by the `UNDERLYING` pointing to a separate `ststxbtc-token-v2` contract rather than being pegged 1:1 to STX — then every position using `stSTXbtc` (or its ztoken `zstSTXbtc`) as collateral would have its collateral USD value systematically mis-stated by whatever the true, unaccounted-for exchange rate is. An overstated price would let users borrow more than their real collateral backs (protocol insolvency / theft of protocol funds); an understated price would unfairly restrict borrowing/trigger unwarranted liquidations (freezing of funds).

### Likelihood Explanation
This is not a triggerable "attack" in the traditional sense — it is a static oracle-configuration defect that is always active whenever `stSTXbtc`/`zstSTXbtc` is used as collateral, so likelihood of the mispricing being live is high if the underlying token's exchange rate diverges from 1:1 with STX at any point (which is the entire economic point of a liquid-staking-derivative token). However, without being able to confirm the actual redemption mechanics of `ststxbtc-token-v2` / `vault-ststxbtc` in this session, I cannot fully validate that a real STX-per-token ratio exists and diverges from 1, versus this being an intentional design decision (e.g., if `stSTXbtc` is deliberately kept 1:1 redeemable to STX by protocol design, analogous to how `wstETH`→`stETH` was later argued to be fine post-Shanghai).

### Recommendation
Confirm whether `ststxbtc-token-v2` (or the `vault-ststxbtc`/`ststxbtc.clar` wrapper) has a non-1:1, time-varying exchange rate versus STX (e.g. a `get-stx-per-token` or similar accessor). If so, register `stSTXbtc` with a dedicated callcode (analogous to `CALLCODE-STSTX`) that fetches and applies that live ratio to the STX price before it is used in collateral/debt valuation, mirroring how `stSTX` is handled. If `stSTXbtc` is genuinely intended to be a fixed 1:1 STX-redeemable token, this should be explicitly documented and enforced at the token level, and the finding would not apply.
