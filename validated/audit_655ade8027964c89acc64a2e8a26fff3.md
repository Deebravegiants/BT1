## Confirmed Analog

This codebase already contains a clear analog to CVE-2024-0901's bug class (an attacker-controlled, "correctly-sized-envelope but internally malformed" packet triggering an unchecked memory operation that panics/crashes the node), and unlike the many hardened examples found elsewhere in the codebase (`empty_hp_prefix_returns_error_not_panic`, `nibble_at_depth` guard, `parse_extra` length checks, sync-committee multiproof length check, etc.), this specific path has **no such guard**.

### Title
Unvalidated `message.from` length causes a panic (DoS) in `pallet-hyper-fungible-token`'s cross-chain calldata origin derivation - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` (the `IsmpModule` handler invoked for every incoming ISMP POST request delivered to the hyper-fungible-token pallet) derives the dispatch origin for optional cross-chain calldata execution from `message.from`, an ABI-decoded, attacker-influenced byte string, without validating its length before slicing/copying it.

### Finding Description
In `on_accept`, when the incoming message carries calldata (`message.data` non-empty) and no `substrate_data.signature` is supplied, the origin account is derived directly from `message.from`: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

`message` is decoded from the request body via `Message::abi_decode(&body)` [2](#0-1)  — `Message.from` is a `bytes` field, so its length is attacker-controllable independent of the outer ABI-encoded body's overall correctness (the "correct length" packet, malformed contents, matching the wolfSSL bug class). No length check is performed on `from_bytes` before use, unlike the sibling code paths in the same file that *do* validate lengths for the analogous `to`/`from` fields:

- `to_bytes` (recipient) is explicitly checked for `== 32` or `== 20`, else a typed error is returned: [3](#0-2) 
- `from_bytes` in `on_timeout` is likewise explicitly checked for `== 32` or `== 20`, else `HftError::InvalidSenderLength` is returned: [4](#0-3) 

But the `on_accept` calldata-origin branch omits this check entirely:
- `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize` and panics ("attempt to subtract with overflow" in debug, or wraps to a huge index causing a slice-index-out-of-range panic in release) before any indexing occurs.
- `account.copy_from_slice(from_bytes)` in the non-EVM branch panics immediately if `from_bytes.len() != 32` ("source slice length does not match destination slice length").

This is precisely the same bug class the project has already hardened against elsewhere in the codebase — the regression tests in `modules/trees/ethereum/src/tests.rs` (`empty_hp_prefix_returns_error_not_panic`), `modules/consensus/pharos/primitives/src/spv.rs` (`nibble_at_depth` / `MAX_PROOF_DEPTH`), `modules/consensus/sync-committee/verifier/src/lib.rs` (multiproof length check), and `modules/utils/serde/src/lib.rs` (`as_utf8_string`) all show the team explicitly fixing "attacker-controlled length causes indexing/copy panic on untrusted wire data." This one path was missed.

### Impact Explanation
Any relayer/attacker who can get a message accepted by the pallet's peer-authentication (`ContractToAsset::<T>::get(source, &from)`) can construct a `Message.from` field of the wrong length combined with non-empty `data`. Since `pallet_ismp::handle_unsigned` is a permissionless unsigned extrinsic that executes `on_accept` for any relayed, proof-verified request, a message crafted with a valid mint (correct `to`/`amount`) but with `from` deliberately shortened/lengthened and `data` non-empty will panic inside the runtime call. In Substrate/FRAME, an unhandled panic during dispatch aborts the transaction execution (via `panic_handler`/`set_and_run_with_metadata` unwind boundaries) but more importantly, because this same message can be *replayed identically by any relayer* (it is a deterministic, proof-backed message), and because `handle_unsigned` is validated in `validate_unsigned`/`pre_dispatch` (which re-executes `Self::execute(messages.clone())` to compute transaction validity) [5](#0-4) , a panicking payload executed during transaction-pool validation can crash/abort the node's transaction-pool validation worker for every node that receives the transaction over the network before it is ever included in a block — a remote out-of-bounds/DoS crash triggered by a single malformed (but proof-valid) message, matching the "remotely executed crash / out-of-bounds via malformed packet with correct length" pattern of CVE-2024-0901.

### Likelihood Explanation
High: the attacker only needs (1) a legitimate/registered peer contract mapping (`ContractToAsset`) for some `(source, from)` pair — standard configuration for any deployed HFT token pair — and (2) the ability to submit an ISMP message with a state/consensus proof for that source chain (which any relayer, or the token's own home-chain contract acting adversarially, can produce, since `Message.from`/`data` are attacker-controlled `bytes` fields inside the dispatched request body and are not constrained by the peer address check, which only validates the *sender contract address*, not the encoded `Message.from` payload). No signature is required to reach the vulnerable branch (`substrate_data.signature` is `None`), only `message.data` must be non-empty with any malformed `SubstrateCalldata`.

### Recommendation
Mirror the length validation already present for `to_bytes` (in `on_accept`) and `from_bytes` (in `on_timeout`) before deriving the calldata-execution origin: explicitly check `from_bytes.len() == 20` (EVM) or `== 32` (non-EVM) and return `HftError::InvalidSenderLength` (or equivalent) otherwise, instead of directly slicing/copying into fixed-size buffers.

### Proof of Concept
1. Register a peer mapping via `ContractToAsset::<T>::insert((source, from_contract), asset_id)` as part of normal token deployment.
2. From the source chain, dispatch (or have the relayer relay) a POST request whose body ABI-decodes to `Message { from: vec![0u8; 5], to: <valid 20-byte recipient>, amount: <valid>, data: <non-empty valid-looking SubstrateCalldata with signature: None> }`.
3. Submit this as part of a `handle_unsigned` extrinsic with a valid state/consensus proof for the request.
4. During `Pallet::on_accept`, execution reaches `&from_bytes[from_bytes.len() - 20..]` with `from_bytes.len() == 5`, causing `5usize - 20` to underflow and the subsequent slice operation to panic, aborting transaction validation/execution for any node processing this message (both during `validate_unsigned` re-execution and final dispatch).
