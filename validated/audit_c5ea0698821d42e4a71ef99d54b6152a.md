## Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler. Any user who can trigger a legitimately signed webhook for their own shop (a normal unprivileged action — installing the app on a shop they control) can replay that exact body+signature pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled data as if it belonged to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `hmac`, `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read from independent, unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` uses this single body-only HMAC check as the sole authentication gate, then immediately forwards the unauthenticated `request.shop` (and `topic`, `webhook_id`, `api_version`) to the app's handler as trusted tenant/session metadata: [4](#0-3) 

Because the app's HMAC secret (`api_secret_key`) is shared across every shop that installs the app, an attacker who installs the app on their own shop (Shop A) legitimately receives real, correctly-signed webhook deliveries. They can capture one such `(raw_body, hmac)` pair from their own shop and replay it directly to the app's public webhook endpoint while swapping the `shop-domain` header to a victim shop (Shop B) that also uses the app. `Registry.process` will accept it — the HMAC still validates because it never covered the shop field — and will invoke the handler with `shop: "victim-shop.myshopify.com"` even though the payload content actually came from the attacker's own store. This breaks the identity binding: **shop asserted by the HMAC-authenticated request ≠ shop the application logic keys its per-tenant state to** (`request.shop` used as the session/tenant key in `WebhookMetadata`).

### Impact Explanation
This allows cross-tenant data injection/impersonation: any handler that uses `data.shop` to select which merchant's records to update, sync, or act upon (a documented and expected usage pattern of `WebhookMetadata`) can be tricked into applying attacker-supplied webhook content to another tenant's data scope. This matches the Critical "cross-tenant access" impact category, since the boundary between one merchant's data and another's is defined entirely by this unauthenticated header.

### Likelihood Explanation
High/practical: no secrets, tokens, or privileged access are required beyond installing the app on a shop the attacker already controls (which any internet user can do for any public Shopify app) and issuing a normal unauthenticated HTTP POST with a captured legitimate `(body, hmac)` pair and a forged shop header. Every app built with this gem that trusts `WebhookMetadata#shop` for tenant-scoped logic is affected identically, since the vulnerable binding lives in the gem's own `Registry`/`Request` classes rather than in app-specific misuse.

### Recommendation
Bind the tenant-identifying fields to the authenticated payload before trusting them:
- Reject/flag webhooks where the `shop-domain` header does not correspond to a shop with an active, previously-established session/installation record known to the app (defense the gem can enable by exposing a shop-scoped secret-lookup hook), and/or
- Document explicitly (and enforce where feasible) that `request.shop`/`topic` are **not** cryptographically bound by `HmacValidator.validate`, and require host applications to independently verify shop ownership/installation state before acting on webhook content — but ideally, cache/validate the webhook per-shop by cross-checking against a known list of shops that have this webhook registered (matching webhook_id → shop) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com`.
2. Attacker performs an action that triggers a real webhook (e.g. `orders/create`) to the app's endpoint; Shopify sends:
   - Body: `{"id":1,...}` 
   - Header `X-Shopify-Hmac-Sha256`: `HMAC-SHA256(body, api_secret_key)` (base64)
   - Header `X-Shopify-Shop-Domain`: `attacker.myshopify.com`
3. Attacker captures this exact `(body, hmac)` pair.
4. Attacker POSTs the same body and hmac header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (body/hmac match, as shown in `hmac_validator.rb` lines 12-31), and the handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_body, ...)` as seen in `registry.rb` lines 198-199 — the app now processes attacker data under the victim's tenant identity.
