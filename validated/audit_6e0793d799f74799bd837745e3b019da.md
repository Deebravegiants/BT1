No vulnerability found for this question.

The reported issue concerns unrevocable ERC20 `approve(..., type(uint256).max)` calls to an external lending pool in a Solidity contract. Raydium AMM does not use the SPL Token `Approve`/delegate pattern anywhere in its instruction handlers — token movements are done via direct `spl_token::instruction::transfer` calls where the user wallet or the PDA `amm_authority` signs as owner, never via a delegated approval that could be left dangling. This is visible in `Invokers::token_transfer` and `Invokers::token_transfer_with_authority`, which construct spl-token `Transfer` instructions directly. [1](#0-0) 

Additionally, `Initialize2` explicitly rejects any vault token account that already has a delegate or close authority set, further showing the program's design deliberately avoids the delegate/approval pattern that the report's bug class depends on. [2](#0-1) 

Since there is no analogous "approval that cannot be revoked" mechanism reachable by an unprivileged swapper, LP, or pool creator in this codebase, the bug class does not map to any concrete vulnerability here.
