## Analysis

The ION-DTN CVE is a crash triggered by an **unvalidated “null” value** (`dtn:none`) reaching a code path that has no defensive handling, permanently breaking that node's bundle processing (DoS). The closest analog in alt.fun's contracts is a **zero-liquidity edge case in `Bonding.finalizeGraduation`** that is likewise unvalidated and, once hit, deterministically re-reverts on every retry — permanently bricking that token's graduation.

`finalizeGraduation` is permissionless and calls `_seedUniswapV2Direct`, which in the "hostile pre-seed" (Regime 3) branch rebalances the pool and then deposits via `_routerDepositAndDispose`: [1](#0-0) 

If either `remToken` or `remLT` computed there is `0`, the `addLiquidity` block is skipped entirely and the function's named return `liquidity` is never assigned — it stays at its default value `0`. That `0` propagates straight back up through `_seedUniswapV2Direct` into `finalizeGraduation`: [2](#0-1) 

`finalizeGraduation` passes this unvalidated `liquidity` value straight into `LPLock.recordLock`, which has a strict, unbypassable guard: [3](#0-2) 

`recordLock` reverts with `ZeroAmount()` whenever `amount == 0`. Because the whole call is wrapped in `nonReentrant` and any revert unwinds every state change made earlier in the same transaction (the `skim`, the rebalance `swap`, the `burn` of unsold tokens, etc.), a token that lands in this zero-liquidity configuration reverts on **every** subsequent call to `finalizeGraduation` — the on-chain state that produces the zero result (curve-close reserves cached in `pendingGraduation`, the pre-seeded V2 pair's reserves) never changes, so the outcome is deterministic and permanent.

This is architecturally identical to the CVE's bug class: a value that should be treated as a "null"/degenerate case (`dtn:none` in ION-DTN, `liquidity == 0` here) is passed into a downstream code path with no fallback, and the resulting failure is not transient — it permanently disables processing for that object (a bundle queue in ION-DTN; a specific token's graduation here), which the contract's own comments acknowledge is fatal: `LPLock` has "no removal path" and "no rescue path in v1," and `Bonding`'s own natspec elsewhere states that anything landing in this dead-end state is "permanently stuck."

### Title
Zero-liquidity deposit result in `finalizeGraduation` permanently bricks graduation via `LPLock.recordLock`'s `ZeroAmount` guard - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.finalizeGraduation`'s hostile-pre-seed rebalancing path (`_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`) can produce a `liquidity` value of exactly `0` when the post-rebalance token or LT balance consumable by `addLiquidity` is `0`. This unvalidated `0` is forwarded to `LPLock.recordLock`, which unconditionally reverts on `amount == 0`. Since the whole transaction (including the rebalance swap and reserve state it depends on) reverts atomically, and the underlying pre-seeded V2 pair reserves plus the cached `pendingGraduation` values never change on failure, every future call to `finalizeGraduation` for that token replays the identical computation and reverts identically.

### Finding Description
`finalizeGraduation` is permissionless — "keeper drives the happy path; anyone can rescue a stuck token" per its own natspec [4](#0-3) . It is designed to be "brick-proof against a front-runner pre-creating the pair and dust-seeding it between phases" [5](#0-4) , but this brick-resistance analysis only covers `pair.swap` reverting (`INSUFFICIENT_OUTPUT_AMOUNT`) — it does not cover the case where the rebalance succeeds but leaves the deposit step with one side of the balance fully consumed, yielding `remToken == 0` or `remLT == 0` in `_routerDepositAndDispose`.

In that case, the `if (remToken > 0 && remLT > 0)` guard skips `addLiquidity` silently and `liquidity` is left at its zero default — there is no fallback (e.g., a re-attempt at direct-mint) for this specific outcome, unlike the `s == 0` / `expectedOut == 0` cases in `_pairRebalance`, which do have an explicit `_seedDirectMint` fallback [6](#0-5) . The unvalidated `liquidity = 0` then hits `LPLock.recordLock`'s `ZeroAmount()` revert, and because `finalizeGraduation` performs no state writes until after this call succeeds, the entire transaction reverts and leaves the token exactly where it was — `Lifecycle.Graduating` with the same `pendingGraduation` snapshot and the same (now further pre-seeded) V2 pair reserves, guaranteeing the identical zero-liquidity outcome on retry.

### Impact Explanation
Once a token is stuck in this state:
- Trading is permanently frozen: `buy`/`sell` on the curve both revert with `TokenIsGraduating` while `lifecycle == Lifecycle.Graduating` [7](#0-6) .
- The token can never reach `Lifecycle.Graduated`, so no HyperSwap V2 market ever opens.
- All curve-raised LT (`ltFromPair`) and the up-to-250M reserved tokens (`tokensForLP`/`LP_RESERVE`) parked on `Bonding` for this graduation become permanently unreachable — there is no owner rescue path, no retry path, and `LPLock` explicitly has no lock-removal/rescue mechanism.

This matches the "permanent freezing of trader, creator or LP funds" impact bar.

### Likelihood Explanation
This requires an attacker to pre-seed/mint into the HyperSwap V2 TOKEN/LT pair before graduation with a reserve ratio engineered so that, after `_pairRebalance`'s swap consumes (up to 99% of) one side's inventory, the residual balance on that side is exactly zero — a pre-creation/pre-seeding action explicitly listed as in-scope and reachable by any unrelated wallet. Because the deposit uses live `balanceOf` reads rather than fixed rounded amounts, and the swap sizing (`_noFeeSwapInput`, `_swapBudget`) is fully deterministic from attacker-chosen reserves, this is a crafted-but-reachable griefing scenario rather than a routine occurrence — consistent with a Medium-severity DoS bug class, matching the CVE's severity rating. I was not able to fully enumerate every reserve combination that forces an exact-zero residual within this session; a background engineering pass (fuzzing `_seedRebalancing`/`_routerDepositAndDispose` against adversarial pre-seed ratios) would be needed to confirm concrete numeric inputs that trigger it deterministically.

### Recommendation
Add a fallback in `_routerDepositAndDispose` (or its caller) for the `remToken == 0 || remLT == 0` case — e.g., fall back to `_seedDirectMint` at the cached ratio, mirroring the existing fallback used when `_pairRebalance` returns `false`. Alternatively, validate `liquidity != 0` inside `finalizeGraduation` before calling `LPLock.recordLock` and revert with a distinct, retriable error that also resets/adjusts the rebalance state rather than leaving the token in a deterministically-doomed loop, or have `LPLock.recordLock` accept a `0`-liquidity "no-op" record for tokens that need protocol-owner intervention.

### Proof of Concept
Not independently verified end-to-end (would require a concrete numeric reserve pre-seed reproduced in a Foundry test against `_seedRebalancing`/`_routerDepositAndDispose`). The conceptual PoC:
1. Launch a token via `Zap.createToken`; let it accumulate curve trades until `canGraduate` is true and phase 1 (`_enterGraduating`) fires, caching `tokensForLP`/`ltFromPair` in `pendingGraduation`.
2. Before anyone calls `finalizeGraduation`, an attacker directly creates/mints into the HyperSwap V2 TOKEN/LT pair (`_ensureUniswapV2Pair` will find and reuse this pair) with a reserve ratio chosen such that, given the cached `tokensForLP`/`ltFromPair` target ratio and `_pairRebalance`'s swap-budget cap, the post-swap `remToken` or `remLT` balance in `Bonding` computed in `_routerDepositAndDispose` is exactly `0`.
3. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `liquidity` resolves to `0`, `LPLock.recordLock` reverts with `ZeroAmount()`, the whole transaction reverts.
4. Every subsequent call to `finalizeGraduation(tokenAddress)` replays the identical state and reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, and its escrowed LT/tokens on `Bonding` are permanently unrecoverable.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
