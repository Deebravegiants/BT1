### Title
Webhook `shop-domain` header is trusted as the tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while `to_signable_string` (the value that `Utils::HmacValidator` actually verifies) is defined as only the raw request body. `Registry.process` accepts any request whose body HMAC is valid and then forwards `request.shop` — a value the signature never covered — straight into `WebhookMetadata`, which host applications use as the authoritative tenant identifier for the event. This is the same "field acted on but not covered by the HMAC" identity-binding break described in the report (there, the affiliate-commission recipient wasn't bound to an active/authorized party; here, the tenant identity forwarded to the handler isn't bound to the signed bytes).

### Finding Description
- `to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 
- `shop` is read straight from a header that is never mixed into the signable string: [2](#0-1) 
- `HmacValidator.validate` computes/compares the HMAC purely over `to_signable_string`, i.e., only the body bytes, never the shop header: [3](#0-2) 
- `Registry.process` gates handling solely on that body-only HMAC check, then immediately trusts `request.shop` as the tenant identity passed to the handler: [4](#0-3) 
- The resulting `WebhookMetadata#shop` field is a plain `String` const with no additional binding to the signed payload: [5](#0-4) 

**Identity binding broken (as an equality):**
`hmac_verified(raw_body)` is treated as `hmac_verified(raw_body) == shop_is(request.shop)`, but the gem's own code proves `to_signable_string == raw_body` only — the `shop` header is disjoint from what is signed. Any body+HMAC pair that is valid for tenant A's `client_secret` (which is shared across all tenants of a multi-tenant public app) remains valid verbatim if replayed with a different `shopify-shop-domain` header value, because the header plays no role in `validate_signature`.

### Impact Explanation
In a multi-tenant Shopify app (the standard integration pattern this gem targets), a single `api_secret_key`/`client_secret` is shared by every installed shop. Anyone can install the app on their own shop (a normal, unprivileged action) and thereby learn/produce arbitrary genuinely-HMAC-valid `(raw_body, hmac)` pairs for their own tenant by triggering webhook-eligible events. Because `Request#shop` (and hence `WebhookMetadata#shop`) is taken from a header outside the signed scope, that attacker can resend the exact same signed body while substituting any victim shop's domain in the `shopify-shop-domain` header. `Registry.process` will validate the HMAC successfully and hand the handler a `WebhookMetadata` claiming the event belongs to the victim tenant — a cross-tenant identity confusion at the gem's own trust boundary. This is a Critical-class outcome per the given rubric (cross-tenant access), since it lets one tenant inject data/events attributed to another tenant's `shop` value, which apps commonly use to key session/data lookups (e.g., `Session` retrieval, per-shop state updates).

### Likelihood Explanation
Likelihood is moderate-to-high for any multi-tenant public app relying on this gem's webhook helpers exactly as documented: the attacker only needs their own (unprivileged) shop installation to generate a validly-signed body, and a way to POST to the app's public webhook endpoint with a modified `shop-domain` header — both are within reach of an ordinary internet user with no special credentials, tokens, or access to `api_secret_key`.

### Recommendation
- **Short term:** Include the `shop-domain` (and ideally `topic`, `webhook-id`) headers in the HMAC-signable content, or otherwise cryptographically bind the shop identity to the request before handing it to `WebhookHandler#handle`, and reject any process call where the shop cannot be proven to match the signed payload's origin.
- **Long term:** Require callers to supply/verify the expected shop (e.g., cross-check `request.shop` against a shop already known to be installed with the same `client_secret`/session store) before invoking handlers, and document that `shop` is not currently authenticated by `Utils::HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: HMAC(client_secret, B)` — this HMAC is valid because `to_signable_string` only ever returns `B`: [1](#0-0) 
2. Attacker replays this exact `(B, hmac)` pair to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` and succeeds regardless of the shop header: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, i.e., attacker-controlled body content is now attributed to the victim tenant: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
