### Title
Webhook `shop` (tenant) identity is taken from an unauthenticated header and not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identity directly from the `X-Shopify-Shop-Domain` HTTP header, but `Request#to_signable_string` (used by `Utils::HmacValidator.validate`) only signs the raw request body. The `shop` value is therefore never bound by the HMAC, and `Registry.process` passes this unverified value straight into the app's webhook handler as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request purely by checking `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the shop domain, topic, webhook id, or API version: [3](#0-2) 

Meanwhile, `shop` is read directly and unmodified from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is attacker-controlled request metadata, not part of the HMAC-signed payload: [4](#0-3) [5](#0-4) 

`Registry.process` then forwards this unauthenticated `shop` value straight to the host application's handler as the trusted tenant identifier, along with the verified body: [6](#0-5) [7](#0-6) 

This breaks the intended equality: `hmac(raw_body) == valid` should imply `shop == the shop that actually sent this webhook`. In reality, `hmac` validates only `raw_body`, while `shop` is parsed independently from a header that carries no cryptographic binding to that body or to Shopify's signature. An attacker who can get an app's public webhook endpoint to process *any* legitimately-signed payload for the correct HMAC secret (e.g., replaying a previously captured, genuinely-signed webhook body for shop A, or crafting a request whose body happens to validate — note this still requires knowledge of the `api_secret_key` to forge the HMAC itself, so exploitation is limited to replay/header-substitution scenarios) can present it as belonging to an arbitrary `shop-domain` header value. Because `WebhookMetadata#shop` is the field host applications are documented to use for tenant-scoping (e.g., to know which shop's data to update), any host application that trusts `shop` from `WebhookMetadata` as authoritative for multi-tenant dispatch is exposed to a shop-identity/tenant-confusion condition purely due to this gem not binding `shop` into the HMAC-verified content, unlike topic-based frameworks that recompute or bind all Shopify webhook headers.

This is directly analogous to the reported Standard DAO bug class: a value acted upon by the vault/removeAsset logic (`token.addr`/Hypervisor token) was not covered by the validation check that was supposed to secure it (`canRemoveCollateral`), letting the attacker bypass the collateralization binding. Here, the value acted upon by the tenant-dispatch logic (`shop`) is not covered by the validation check that is supposed to secure it (the HMAC signature over `to_signable_string`), letting an attacker submit a body validly signed for one context but claim it belongs to a different `shop`.

### Impact Explanation
If exploited (via a replay of a genuinely-HMAC-signed request body with a substituted `shop-domain` header, since forging the HMAC itself requires `api_secret_key`), a malicious actor could get a webhook accepted by the target app but attributed to a different merchant/tenant (`shop`) than the one that actually originated it. Because `shop` is the field host apps use to route webhook data per-tenant, this constitutes a cross-tenant data-integrity issue: a webhook payload validly signed by Shopify for shop A could be replayed to make the host app believe it came from shop B, corrupting per-tenant state without requiring the attacker to possess shop B's access token. This maps to the "cross-tenant access" Critical impact category since the tenant boundary (`shop`) is not authenticated by the same mechanism (HMAC) that authenticates the payload.

### Likelihood Explanation
Exploitation requires the attacker to already have a validly-signed webhook body (e.g., from a webhook sent to their own shop, or a captured webhook), and then resend it to the app's webhook endpoint with a modified `shop-domain` header — no possession of `api_secret_key` is needed to do this replay, only to have received one genuine webhook previously. Given every shop that installs the app receives real webhooks whose bodies are signed with the *same* app-wide `api_secret_key`, a malicious merchant can capture their own genuine webhook and replay it while spoofing another shop's domain in the header, since the HMAC never covers the `shop-domain` header value at all. This is a realistic, low-effort attack path for a malicious app-installer, not merely theoretical.

### Recommendation
Bind `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the verified body — for example by including it in `to_signable_string`, or by cross-checking `request.shop` against the shop associated with the session/webhook subscription that the app itself registered, rather than trusting the header verbatim. At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated header data and must not be used by host applications as an unverified tenant identifier for security-sensitive dispatch.

### Proof of Concept
1. App receives a genuine Shopify webhook for `shop-a.myshopify.com`, with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's `api_secret_key`.
2. Attacker (a user with admin access to `shop-a`, or anyone able to intercept/capture that webhook delivery) resends the identical raw body and HMAC header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the raw body against the HMAC — the tampered `shop-domain` header does not affect the computed signature (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` invokes the host app's handler with `WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...)`, causing the host app to process shop A's webhook data as if it belonged to shop B (`lib/shopify_api/webhooks/registry.rb:198-199`).

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
