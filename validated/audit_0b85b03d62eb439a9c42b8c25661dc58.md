### Title
Webhook `shop` field is not covered by the HMAC signature, allowing tenant-identity spoofing in `WebhookMetadata` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns `@raw_body` alone. The header is never part of the signed bytes, so `Registry.process` treats the request as authentic (based on the body's HMAC) while forwarding an unauthenticated `shop` value to the app's webhook handler via `WebhookMetadata#shop`.

### Finding Description
`Registry.process` gates handling entirely on `Utils::HmacValidator.validate(request)` [4](#0-3) . That validator computes `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header value [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [6](#0-5) , while `shop` is read straight from the `shop-domain` header with no cross-check against the signed body [7](#0-6) .

The equality that should hold is: `bytes verified by HMAC == bytes the app trusts for tenant identity`. Here that breaks down to `HMAC(raw_body) is valid` ⇏ `shop header is authentic`, since the header is fully attacker-controlled and outside the signed scope. `Registry.process` then constructs `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` and hands it to the app's `handler.handle` [8](#0-7) , so any downstream code that uses `data.shop` to resolve which merchant/session a webhook belongs to (as the gem's own documentation recommends: "shop_domain: data.shop") is relying on an unauthenticated value.

### Impact Explanation
An unprivileged internet user who is a merchant with their own shop installed on the app can obtain a genuinely-HMAC-signed webhook payload for their own store (e.g., by triggering an `orders/create` event on their own shop), capture the raw POST, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. Because the HMAC only covers `raw_body`, the signature still validates, and the webhook handler receives `WebhookMetadata#shop` claiming to be the victim shop. If the host application uses `data.shop` to look up which tenant's session/data the webhook body should be applied to (as the documented usage pattern implies), this results in cross-tenant data injection/confusion — data belonging to the attacker's shop being attributed to, or acted upon in the context of, a different merchant. This lands in the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is Low: exploitation requires the attacker to already be a legitimate, unprivileged app user (has their own shop and can trigger authentic webhooks for it), and additionally requires that the host application trust `WebhookMetadata#shop` for tenant/session resolution without independently confirming it against a registered/known shop list. The gem's own documentation encourages exactly this trust pattern (`shop_domain: data.shop`), making the pattern realistic but not universal.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the verified payload, so `Utils::HmacValidator.validate` fails if any Shopify-supplied header is tampered with. At minimum, document prominently that `WebhookMetadata#shop` is derived from an unauthenticated header and must be cross-checked by the host app against its own list of installed/authorized shop domains before being used for tenant resolution.

### Proof of Concept
1. App merchant A installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw request: body `B`, and headers including a valid `x-shopify-hmac-sha256: H` (where `H = HMAC(secret, B)`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (matches `H`, since body `B` is unchanged) and returns `true`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, even though this webhook never originated from Shopify for `victim-shop`.
