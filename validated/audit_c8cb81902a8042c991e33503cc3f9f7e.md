## Title
Webhook HMAC validates only the raw body, not the `shop-domain` header used for tenant routing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the *payload bytes* but never binds that signature to the `shop`, `topic`, `webhook-id`, or `api-version` header values that the gem hands to the app's webhook handler. Anyone who legitimately owns a Shopify store (an unprivileged internet user, e.g. a free development store) can install the target app, receive real, correctly-signed webhook deliveries for their own store, then replay the exact `raw_body` + `x-shopify-hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Registry.process` will accept the request as valid and route it to the handler tagged as belonging to the victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC purely over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the whole request, then builds `WebhookMetadata` directly from the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header accessors: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: **shop authenticated by the HMAC == shop attributed to the webhook data by the handler**. Because the HMAC only covers `@raw_body`, that equality does not hold — the `shop-domain` header can be swapped freely without invalidating the signature, as long as the body bytes are unchanged.

### Impact Explanation
An attacker who owns any shop that installs the app can capture a legitimately-signed webhook (body + HMAC) sent to the app for their own store, then resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `Registry.process` still validates because the HMAC only checks `@raw_body`. The app's handler receives `WebhookMetadata` claiming the event came from the victim shop, causing the app to attribute attacker-controlled event data (order/customer/product payloads etc., generated from the attacker's own store activity) to the victim tenant. Any app logic that trusts `shop` for per-tenant state changes, notifications, or access-token lookups can be manipulated cross-tenant this way, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the ability to install the app on any shop (a normal, unprivileged capability for anyone, including via a free Shopify development store) and the ability to capture/replay one's own webhook HTTP request with a modified header — no access token, `client_secret`, or victim credentials are needed.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the signable string (or otherwise cryptographically bind them to the HMAC), or independently verify that the `shop-domain` header corresponds to a shop for which the receiving app instance holds an active session/installation before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's endpoint. They capture the raw request body `B` and the `x-shopify-hmac-sha256` header `H` — both valid, since `H = HMAC-SHA256(secret, B)`.
2. Attacker resends an HTTP POST to the same endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (== `B`) — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook data as if it originated from the victim shop.
