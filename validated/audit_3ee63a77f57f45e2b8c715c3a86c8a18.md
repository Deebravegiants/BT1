## Analysis

The reported bug class is: code assumes a "no-loss / 1:1 success" invariant instead of consulting the authoritative source for the real outcome, causing consumers to trust a locally-derived value rather than the ground truth—resulting in mis-attributed outcomes. The reachable analog in `orb-core` is in the signup-authorization flow, specifically `do_signup()` in `src/plans/mod.rs`.### Title
Signup outcome trusted from local pipeline result without backend duplicate/fraud confirmation for user-centric signups - (File: `src/plans/mod.rs`)

### Summary
The audited bug assumes an invariant (1 PT redeems ≥ 1 underlying) holds unconditionally and never consults the authoritative source (Sense's `Divider`/`Periphery`) for the real, possibly-lossy outcome, so a locally-assumed value is trusted over ground truth. The reachable analog in `orb-core` is in `do_signup()`: when the backend flags a signup as `user_centric_signup`, the code determines final enrollment `success` purely from the orb's own local `signup_reason` value, and never invokes the actual authoritative backend confirmation path (`enroll_user::Plan::run`, i.e. `signup_post`/`signup_poll`) that alone can detect duplicate/inflight/fraudulent signups.

### Finding Description
In `MasterPlan::do_signup`, after the biometric pipeline runs, the enrollment outcome is computed as: [1](#0-0) 

If `user_centric_signup` is `true` (a flag delivered from the backend as part of `authenticated_app_data` in the QR-derived user data) and the local config flag `ignore_user_centric_signups` is `false`, the code sets `success` to simply `signup_reason == SignupReason::Normal` — a value computed entirely from the orb's own local biometric-pipeline/fraud outcome (see `SignupReason` in `signup_post.rs`): [2](#0-1) 

This bypasses the actual authoritative round-trip that the `else` branch performs — `enroll_user::Plan::run`, which posts the signup to the backend and polls for its real status. That authoritative path explicitly exists to catch cases where the *local* outcome ("normal") does not match the *backend's* authoritative determination: [3](#0-2) 

The comment there enumerates exactly the kind of "known loss/mismatch scenarios" the local-only path skips: backend duplicates, backend legacy signup requests, backend inflight matches, and backend-detected fraud. In the audited bug, `Redeemer.redeem()` assumed redemption is always ≥ the minted amount and never asked Sense's `Divider`/`Periphery` whether a legitimate loss had occurred; here, `do_signup()` assumes the orb's own `signup_reason` is always sufficient and never asks the backend (the authoritative source for identity uniqueness/fraud) whether the signup should legitimately be rejected.

The flag itself comes from backend-supplied, QR-code-derived data verified against a hash: [4](#0-3) [5](#0-4) 

### Impact Explanation
When `user_centric_signup` is set, the orb declares enrollment success/failure without ever confirming with the backend's authoritative signup-status endpoint. This means the backend's duplicate-detection, inflight-match-detection, and fraud-detection logic — which is exactly what `enroll_user::Plan::run` exists to consult — is never exercised for this signup, and the debug report/UI/dbus events (`debug_report.signup_successful()`, `ui.signup_success()`, `SignupEnded { success }`) are all driven by the untrusted, backend-unconfirmed local value. This falls squarely in the "misattributed signup" / "fraud enforcement bypass" impact category: a signup that the backend would have rejected (duplicate, inflight match, or fraud) can be locally recorded and reported to the operator/app as `Success`, and conversely a legitimately backend-accepted signup marked `Failure`/`Fraud` locally is never given a chance at backend confirmation.

### Likelihood Explanation
The `user_centric_signup` branch is gated by backend-controlled data and a config flag (`ignore_user_centric_signups`), so it is not directly attacker-triggerable by an unprivileged signup subject in the same way the escalated Sherlock issue was (external market conditions). However, unlike the original bug (which required rare Lido-slashing conditions), this code path is a *deterministic* design choice that is taken on every signup for which the backend sets this flag — it isn't a rare edge case, it's the normal/expected control flow whenever `user_centric_signup` is enabled, meaning the fraud/duplicate-check bypass is systematic rather than conditional on adversarial market behavior. I could not fully verify from the index how `ignore_user_centric_signups` is toggled in production (`src/config.rs` content beyond a doc comment was not available in the index), so the exact deployment likelihood is uncertain.

### Recommendation
Do not let a purely local `signup_reason` determine final enrollment success/failure when `user_centric_signup` is true. Even for user-centric flows, the orb should still perform (or the app-side confirmation should be cryptographically tied to) the backend's authoritative duplicate/inflight/fraud check before reporting the signup as `Success`, mirroring the non-user-centric path in `enroll_user::Plan::run`.

### Proof of Concept
Not applicable in the same form as the original financial exploit — this is a control-flow/trust-boundary gap, not a value-arithmetic one. The relevant code path to reproduce/inspect is: `do_signup()` sets `success = signup_reason == SignupReason::Normal` directly whenever `user_centric_signup && !ignore_user_centric_signups`, entirely skipping the call to `self.enroll_user(...)` (which wraps `enroll_user::Plan::run`) that is used in the `else` branch.
