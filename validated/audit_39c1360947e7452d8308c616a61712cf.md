### Title
Withdrawal status matched by non-unique `assetId` instead of a unique per-withdrawal identifier, causing status/hash misreport for concurrent same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain outcome of a specific withdrawal (`index` + `tx.hash` + `destinationAddress`) by looking up the POA bridge API response and matching against it using only the token's `assetId`. Because `assetId` is not unique per withdrawal (multiple withdrawals of the same token in one NEAR transaction share it), the match is ambiguous, and `describeWithdrawal` can report the status/tx-hash of a *different* withdrawal than the one requested.

### Finding Description
`describeWithdrawal` fetches all withdrawals associated with a transaction hash and delegates matching to `findMatchingWithdrawal`: [1](#0-0) 

The matching function explicitly ignores the caller-supplied `index` (the unique identifier distinguishing multiple withdrawals from the same transaction) and instead matches purely by `assetId`: [2](#0-1) 

The code comment even documents the flaw: *"multiple withdrawals of the same token in a single transaction are not supported"*. The equality that should hold is:

```
withdrawal returned by describeWithdrawal(index=i) == the i-th withdrawal that was actually created for that assetId in that tx
```

Because `findMatchingWithdrawal` uses `Array.prototype.find`, which returns the *first* element satisfying `nep141:${w.data.near_token_id} === assetId`, any call to `describeWithdrawal` for a different `index` withdrawing the *same* token in the *same* transaction will return the exact same record — regardless of which index/destinationAddress was actually requested. This mirrors the reported bug class: using a non-unique, spoofable/reused identifier (`assetId`, akin to a "full name") to resolve identity/state instead of the truly unique identifier (`index`, akin to a "username").

### Impact Explanation
If a single NEAR transaction batches two `ft_withdraw` intents for the same token to two different destination addresses (e.g., one already completed, one still pending, or one failed), calling `describeWithdrawal` for the pending/failed withdrawal's `index` will incorrectly return the completed withdrawal's `status: "completed"` and `txHash`. An integrator (or the SDK's own polling logic) that treats `describeWithdrawal` as authoritative for "has this specific withdrawal happened" would:
- Mark the wrong withdrawal as completed and release/credit funds or mark an internal ledger entry as settled, while the real withdrawal for that index may still be pending, have failed, or point to a completely different destination.
- Potentially report the transfer hash of another user's withdrawal as proof of completion for this one — a status/hash misreport that can lead to double-crediting or incorrect settlement decisions downstream.

This matches the "High" impact bucket: *"a status or hash misreport making an integrator credit or refund twice."*

### Likelihood Explanation
This triggers whenever a caller batches ≥2 withdrawal intents for the *same* POA-bridged token within one NEAR transaction (a supported use case in this SDK, since `WithdrawalIdentifier` carries an explicit `index` field precisely to distinguish multiple withdrawals from one tx) and then queries `describeWithdrawal` per index while the withdrawals are in different states. No malicious actor is required — it's a straightforward same-token batch-withdrawal scenario, which the SDK's own `WithdrawalIdentifier.index` field implies is supported.

### Recommendation
Match withdrawals using a unique identifier instead of `assetId` alone. If the POA bridge API doesn't return a stable per-withdrawal key, disambiguate using `index` combined with amount/destination-address ordering (as the code comment itself suggests: sort both API results and local withdrawal params by amount, since fees are equal per token, to derive a positional/unique match), or reject/guard batched same-token withdrawals until the API provides an unambiguous correlation ID.

### Proof of Concept
1. Submit one NEAR transaction containing two `ft_withdraw` intents for `nep141:btc.omft.near`: intent A → address X (index 0), intent B → address Y (index 1).
2. Suppose the POA relayer completes A first (`status: COMPLETED`, `transfer_tx_hash: "tx-A"`) while B is still `PENDING`.
3. Call `describeWithdrawal({ index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", ... }, tx })`.
4. `findMatchingWithdrawal` scans `response.withdrawals` and returns the *first* entry whose `near_token_id` matches `btc.omft.near` — which is A's completed record — regardless of `index: 1`.
5. `describeWithdrawal` returns `{ status: "completed", txHash: "tx-A" }` for withdrawal B, even though B (to address Y) has not been transferred at all.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
