### Title
Webhook shop/topic identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands off `shop`, `topic`, and `webhook_id` — all taken from unsigned HTTP headers — to the app's handler as the trusted tenant identity. Since these header values are never part of the HMAC-signed content, an attacker who can obtain one valid `(raw_body, hmac)` pair from Shopify (e.g. by receiving a legitimate webhook for their own shop) can replay that same body/HMAC pair while substituting a different value in the `X-Shopify-Shop-Domain` header, and the app will process it as if it originated from that other tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the request: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are not part of the signed string at all: [3](#0-2) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the metadata passed to the app's handler: [4](#0-3) 

This is exactly the identity-binding gap described in the analog report: a field that is *acted on* (the `shop` used to route/attribute the webhook to a tenant) is not covered by the cryptographic check that is supposed to authenticate the request. The equality the library implicitly assumes — "HMAC-verified body ⇒ headers authentically describe that body's shop/topic" — does not hold, because `compute_signature(to_signable_string, secret) == hmac` only proves `raw_body` bytes are untampered; it says nothing about the headers.

### Impact Explanation
Any actor who can capture one legitimately-signed `(raw_body, hmac-sha256)` pair — trivially available to any merchant/installer of the app, since every shop using the app shares the same `api_secret_key` for computing webhook HMACs — can re-POST that identical body/HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to point at a different, victim shop. `Registry.process` will accept the HMAC as valid (it only checks the body) and dispatch the handler with `shop: <victim-shop>`, `topic: <attacker-chosen>`. If the host application uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (a common and expected usage pattern, e.g., `customers/redact`, `shop/redact`, order/product upserts keyed by shop), this becomes cross-tenant data corruption or disclosure attributed to an arbitrary shop of the attacker's choosing — satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Exploitation requires only: (1) installing the app (or otherwise being sent a legitimate webhook, e.g., an app that is publicly installable) to obtain one valid signed payload, and (2) the ability to send an arbitrary HTTP POST with attacker-controlled headers to the app's public webhook endpoint — both trivially available to an unprivileged internet user/merchant. No access to `api_secret_key`, tokens, or the real Shopify platform is needed, since the attacker is replaying an already-valid signature rather than forging one.

### Recommendation
Bind the tenant/topic identity into the authenticated material rather than trusting unsigned headers:
- Cross-check the `shop`/`topic` claimed in headers against a `shop`/`topic` field embedded in the JSON body itself (Shopify webhook payloads generally include shop-scoped identifiers), rejecting mismatches.
- Alternatively (or additionally), require the host application to independently confirm that the shop named in the webhook has an active session/installation before honoring destructive or tenant-scoped operations, rather than relying on the webhook's header-derived `shop` value as ground truth.
- Document clearly in `Webhooks::Request`/`Registry` that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must not be treated as authenticated without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `products/create`), capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` header — both computed with the shared `api_secret_key`.
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act on behalf of `victim-shop` using attacker-supplied data, despite the request never having been authenticated for that shop.

        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
