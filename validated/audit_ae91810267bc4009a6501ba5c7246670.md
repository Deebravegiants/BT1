## Title
Missing Domain Separation Between `withdraw_fees` and `accumulate_fees` Signed Payloads Allows Cross-Context Signature Replay - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
The pallet-relayer fee-withdrawal and fee-accumulation-with-redirect flows both authenticate a relayer's per-chain identity with an ECDSA/sr25519/ed25519 signature over a hash of `(nonce, state_machine, beneficiary)`. Both message builders — `withdrawal::message()` and `accumulate::beneficiary_message()` — SCALE-encode the identical tuple shape and share the same `Nonce<T>` counter, so a signature the relayer created to authorize *one* privileged operation is byte-for-byte valid for the *other*. This mirrors the KubeVirt bug class: two functionally distinct privileged channels (there, `virt-api`↔`virt-handler` vs `virt-handler`↔`virt-handler`; here, `withdraw()` vs `accumulate()`'s beneficiary redirect) share one identity credential with no context/domain tag distinguishing which operation it authorizes.

### Finding Description
`withdrawal::message()` computes: [1](#0-0) 

`accumulate::beneficiary_message()` computes an equivalent hash: [2](#0-1) 

Both are `keccak_256` over the SCALE encoding of `(nonce: u64, StateMachine, beneficiary bytes)`, and both are checked against the same `Nonce<T>` storage key `(address, state_machine)`:
- `withdraw()` reads `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` and verifies `message(nonce, dest_chain, beneficiary)`. [3](#0-2) 
- `accumulate()` reads `Nonce::<T>::get(&delivery_address, state_machine)` and verifies `beneficiary_message(nonce, state_machine, &beneficiary_address)`. [4](#0-3) 

Because the encoded byte layout and the nonce namespace are identical, a signature produced by a relayer to authorize one operation (e.g. redirecting the newly-proven delivery fee to a beneficiary during `accumulate_fees`, which only mutates the internal `Fees` ledger) is also a valid signature for the other operation (`withdraw()`, which drains the relayer's entire current `Fees[dest_chain][address]` balance and dispatches a real cross-chain ISMP withdrawal to the destination chain's host manager). Both `withdraw_fees` and `accumulate_fees` are unsigned, permissionless extrinsics (`ensure_none` origin), so any observer who sees a relayer's signed payload (visible in the transaction pool/block before the relayer's intended call lands) can submit it through the *other* code path while the nonce is still current.

### Impact Explanation
An attacker who intercepts a relayer's `beneficiary_message` signature (intended only to redirect a specific proven delivery's fee credit) can instead submit it as `withdraw()`'s `WithdrawalInputData`, forcing an unintended, unauthorized real cross-chain fund dispatch of the relayer's *entire* accumulated balance on that chain — an operation with materially different consequences (external dispatch vs. internal ledger update) than what was signed for. This also consumes the shared nonce, causing the relayer's originally-intended `accumulate_fees` call to fail signature verification and be dropped, denying that specific fee credit. This satisfies the "unauthorized app action" / forged-authorization class from the rules: a credential scoped to one privileged action is accepted for a different privileged action due to missing domain separation, directly analogous to the KubeVirt shared-CN identity confusion.

### Likelihood Explanation
Exploitation only requires observing a submitted (but not-yet-finalized) unsigned extrinsic containing a relayer's signature — routine for anyone monitoring the transaction pool — and racing a second unsigned extrinsic ahead of it, which any unprivileged party can submit since both calls use `ensure_none` origins.

### Recommendation
Add a distinct domain separator/discriminator byte (or type tag) to each signed payload (`message()` vs `beneficiary_message()`) so a signature produced for one pallet-relayer operation cannot be replayed as authorization for the other, consistent with the domain-separation pattern already used elsewhere in the codebase (e.g. EIP-712 domain separators in `sdk/packages/sdk/src/protocols/intents/CryptoUtils.ts`).

### Proof of Concept
1. Relayer signs `beneficiary_message(nonce=N, state_machine=X, beneficiary=B)` and submits `accumulate_fees` with `beneficiary_details = Some((B, sig))`.
2. Attacker observes `sig` in the pending transaction and constructs `WithdrawalInputData { signature: sig, dest_chain: X, beneficiary: Some(B) }`.
3. Attacker submits `withdraw_fees(WithdrawalInputData)` before the relayer's `accumulate_fees` is included; `message(N, X, B) == beneficiary_message(N, X, B)`, so `signature.verify(&msg, ...)` succeeds against the relayer's key, draining `Fees[X][relayer]` in full to `B` and incrementing `Nonce[relayer][X]`.
4. The relayer's original `accumulate_fees` extrinsic now fails (`InvalidSignature`/nonce mismatch), so the intended fee credit for the newly-delivered commitments is dropped rather than applied.
