### Title
`Webhooks::Request#initialize` accepts an unauthenticated `x-shopify-shop-domain` header as tenant identity, while HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#initialize` only checks that `topic`, `hmac-sha256`, and `shop-domain` headers are *present*, never that `shop-domain` is bound to the signed content. `to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the body was HMAC'd with the app's shared `api_secret_key` - it says nothing about which shop the body belongs to. Since Shopify apps share one `client_secret`/`api_secret_key` across every shop install, an attacker who installs the app on their own shop can capture one legitimately-signed webhook (valid body + valid HMAC) and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim's domain; the request still passes `HmacValidator.validate` and `Registry.process` hands the handler `WebhookMetadata` with the attacker's `body` labeled as the victim's `shop`.

### Finding Description
The claimed binding is:
`hmac == compute_signature(to_signable_string, api_secret_key)` should imply the tuple `(shop, topic, body)` is trustworthy as a unit. In fact only `to_signable_string` (== `@raw_body`) is covered: [1](#0-0) 

`shop` is read straight off the unsigned header with no cross-check against the signed payload: [2](#0-1) 

`initialize` validates only presence of the three headers, never their well-formedness or any relationship between them: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the signature over `to_signable_string` (the raw body) and the app-wide `Context.api_secret_key`/`old_api_secret_key` - never over `shop`: [4](#0-3) 

`Registry.process` validates the HMAC, then forwards the *unauthenticated* `request.shop` straight into the handler alongside the *authenticated* `request.body`: [5](#0-4) 

The documented handler pattern trusts `data.shop` as the routing/session key while acting on `data.body`: [6](#0-5) 

Exploit flow: the attacker creates their own development shop, installs the target app, and lets Shopify deliver one real webhook to the app - e.g. `orders/create` - which arrives with a body `B` and a valid `hmac-sha256 = HMAC(api_secret_key, B)`. The attacker replays this exact `(B, hmac)` pair directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`. `Request#initialize` accepts it (all three headers present); `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it still matches, because the shared `api_secret_key` is identical for the victim's installation too, and `B` is unchanged. `Registry.process` then calls `handler.handle` with `topic` and `body` from the attacker's own webhook but `shop: "victim-shop.myshopify.com"`. Any handler that uses `data.shop` to select which merchant's session/access token to act on (the pattern the gem's own docs recommend) will now mutate or read the victim's data using attacker-controlled body content, or persist attacker data keyed to the victim's shop.

Existing guards do not stop this: `HmacValidator.validate` (checked above) only binds the body to the shared secret, not the shop header; `ShopValidator.sanitize!` is never invoked anywhere in this path; there is no `state`/nonce comparison for webhooks (that only exists in OAuth); `JwtPayload`'s `aud` check is unrelated (App Bridge session tokens, not webhooks); `Context.setup?`/`private?`/`embedded?` govern OAuth/App Bridge config, not webhook processing; Sorbet's runtime typing only enforces that `shop` is a `String`, not that it matches the signed body's origin.

### Impact Explanation
Any shop that installs the app can forge webhooks that Registry-processed handlers will attribute to any other merchant of the same app, because the shared `api_secret_key` HMAC covers only the body, never the shop identity carried in `x-shopify-shop-domain`. This is repeatable per victim domain and per captured legitimate webhook the attacker owns, and the blast radius spans every merchant of the host app - matching Critical cross-tenant access ("one shop's request reads or mutates another merchant's data") if the host app (as the gem's own docs recommend) uses `data.shop` to select the target merchant's session/access token for follow-up work.

### Likelihood Explanation
Preconditions: the app must use `Webhooks::Registry.process`/`Request` as documented, and the handler must key merchant-specific storage or API calls off `data.shop` (the pattern shown in `docs/usage/webhooks.md`). Attacker cost is low: create a free/dev shop, install the app, receive one legitimate webhook, then send one crafted POST with a relabeled header - no secrets, tokens, or privileged access required, fully within the stated attacker capabilities.

### Recommendation
Bind `shop` to the signed content instead of trusting the header alone: include the shop domain in the signable string (if supported by future Shopify webhook formats), or - more practically today - have `Registry.process`/host apps cross-check `request.shop` against an actively-registered webhook subscription/session for that exact `topic` + shop before invoking the handler, and reject/flag mismatches. At minimum, document prominently that `request.shop` is unauthenticated and must never be used alone to select which merchant's session/access token to act on.

### Proof of Concept
```ruby
# test/webhooks/cross_tenant_replay_test.rb
require_relative "../test_helper.rb"

class CrossTenantReplayTest < Test::Unit::TestCase
  def test_replayed_webhook_with_relabeled_shop_still_validates
    body = '{"id":1,"note":"attacker-controlled"}'
    hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => Base64.encode64(hmac),
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
    }
    victim_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

    req_attacker = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
    req_victim = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: victim_headers)

    # BYTE IDENTITY assertion: same signable bytes for both requests
    assert_equal(req_attacker.to_signable_string, req_victim.to_signable_string)

    # Same HMAC value regardless of shop-domain header content
    assert_equal(req_attacker.hmac, req_victim.hmac)

    # Both pass HmacValidator despite claiming different shops
    assert(ShopifyAPI::Utils::HmacValidator.validate(req_attacker))
    assert(ShopifyAPI::Utils::HmacValidator.validate(req_victim))

    # Registry.process forwards attacker body under the victim's shop label
    received_shop = nil
    handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
    )
    ShopifyAPI::Webhooks::Registry.process(req_victim)
    assert_equal("victim-shop.myshopify.com", received_shop)
  end
end
```

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
