## Analysis

I traced this bug class through Hyperbridge's PostRequest fee-escrow lifecycle, looking for a path where escrowed relayer fees become permanently unreachable, analogous to Velodrome's `claimable[_gauge]` being stranded after `killGauge()`.

Confirmed root cause:

1. **Escrow on dispatch.** A `PostRequest` fee is collected up front and held either in `RELAYER_FEE_ACCOUNT` (Substrate, `pallet-ismp`) or in `EvmHost`'s balance, keyed by the request commitment via `FeeMetadata`/`RequestMetadata`. [1](#0-0) [2](#0-1) 

2. **The only two exits for that escrow are delivery and timeout.** Both paths are gated by `validate_state_machine`, which unconditionally checks `host.is_consensus_client_frozen(...)` before permitting the operation to proceed for both incoming requests/responses *and* `Post` timeouts. [3](#0-2) [4](#0-3) 

3. **Freezing is explicitly declared irreversible.** Per the protocol design, once `freeze_client` (triggered permissionlessly by anyone submitting a valid fraud proof) fires, the consensus client can never be unfrozen — a brand-new client must be created via `create_client` instead: "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead." [5](#0-4) 

Consequence: any in-flight `PostRequest` targeting (or routed through) that state machine, whose fee is already escrowed, can neither be delivered (blocked by `FrozenConsensusClient`) nor timed out (the `Post` timeout branch also calls `validate_state_machine`, which fails identically) once its source/dest consensus client is frozen. Unlike the `Get` timeout branch, which has no proof requirement and doesn't call `validate_state_machine`, `Post` timeouts require a non-membership proof verified against the (now permanently frozen) client. There is no code path in `on_request_timeout`, `dispatchTimeOut`, or elsewhere that sweeps escrowed fees for requests whose consensus client has been frozen — the funds sit in `RELAYER_FEE_ACCOUNT` / `EvmHost` indefinitely with no admin or governance recovery function found in the reachable dispatch/consensus code.

This is a legitimate structural analog to the Voter.sol issue: an unprivileged, permissionless action (`freeze_client`, callable by any fisherman with a valid fraud proof) irreversibly locks a class of state (the consensus client), and pre-existing escrowed value tied to that state becomes permanently unrecoverable because both exit paths depend on the now-dead state being alive.

I was not able to fully verify whether `pallet-ismp-relayer`'s `Fees`/accumulate flow has any separate sweep mechanism for such stranded per-request escrows, nor whether governance instruments elsewhere in the runtime (outside the traced dispatch/consensus/timeout code) could manually redirect `RELAYER_FEE_ACCOUNT` balances — this would require deeper review of pallet-level governance calls, which is out of scope for the reachable-by-transaction analysis requested.

### Title
Permanently Locked Relayer Fee Escrow for In-Flight PostRequests When a Consensus Client Is Frozen - (File: modules/ismp/core/src/handlers/timeout.rs)

### Summary
When a consensus client is frozen via `freeze_client` (permissionlessly triggerable by anyone submitting a valid fraud proof), any `PostRequest` already in flight against that state machine has its escrowed relayer fee stranded forever: delivery is blocked by the frozen-client check, and `Post` timeout processing — the only other path capable of returning the fee to the payer — is gated by the identical frozen-client check, and frozen clients are explicitly unrecoverable.

### Finding Description
`EvmHost::dispatch` and `pallet-ismp`'s `dispatch_request` escrow the relayer fee at dispatch time, keyed to the request commitment (`_requestCommitments` on EVM, `RequestMetadata`/child-trie on Substrate). [6](#0-5) [7](#0-6) 

Both the successful-delivery path (`handlers::request::handle`) and the `Post`-timeout path (`handlers::timeout::handle`) call `validate_state_machine`, which fails with `Error::FrozenConsensusClient` if `host.is_consensus_client_frozen` returns an error. [8](#0-7) [9](#0-8) 

`freeze_client` is declared explicitly irreversible by protocol design: once frozen, a client can never resume processing consensus/request/response/timeout messages, and a wholly new client must be created instead. [10](#0-9)  There is no code path found that releases or refunds the escrowed fee for requests whose relevant consensus client has entered this permanent frozen state — `on_request_timeout` (the refund function) is only ever invoked from within the timeout handler after `validate_state_machine` succeeds. [11](#0-10) 

This mirrors the reported Velodrome bug class: an unprivileged/permissionless state transition (`killGauge` / `freeze_client`) irrecoverably strands value (`claimable[_gauge]` / escrowed relayer fees) that was indexed/escrowed against that piece of state, with no sweep-back mechanism to a recoverable account (e.g., `Minter` / the original payer or protocol treasury).

### Impact Explanation
This is a permanent freezing-of-funds bug. Every `PostRequest` fee escrowed for delivery to (or timeout on) a state machine whose consensus client gets frozen becomes permanently locked in `RELAYER_FEE_ACCOUNT` (Substrate) or the `EvmHost` contract balance (EVM), with no code path to recover it — satisfying the "permanent freezing of funds" acceptance criterion. The value at risk scales with the volume of in-flight requests and their attached fees at the moment of freeze, which can be significant during periods of high cross-chain activity.

### Likelihood Explanation
`freeze_client` is permissionless — any fisherman holding a valid fraud proof of a consensus fault (double signing/equivocation) can trigger it at any time. [5](#0-4)  While triggering the freeze itself requires an actual consensus fault on the counterparty chain (not attacker-controlled on demand), such faults are an expected and designed-for occurrence in the protocol's threat model (this is precisely why the freeze mechanism exists), making the scenario realistic rather than purely theoretical — especially for any user/relayer who has funded a `PostRequest` with a non-zero fee at the time a fault occurs.

### Recommendation
Add a fee-recovery path that does not depend on the frozen client's liveness: e.g., allow an admin/governance-gated (or permissionless, past a grace period) reclaim of escrowed fees for requests whose destination/source consensus client is confirmed frozen, refunding to the original `payer`. This mirrors Velodrome's fix of returning `claimable` to the `Minter` instead of leaving it stranded — here, the equivalent would be an explicit `reclaim_fee_for_frozen_client(commitment)` entry point in both `pallet-ismp` and `EvmHost` that bypasses `validate_state_machine`'s liveness check but still verifies frozen status and request existence before refunding.

### Proof of Concept
1. User dispatches a `PostRequest` from chain A to chain B via `EvmHost::dispatch` (or `pallet-ismp`'s `dispatch_request`), paying a non-zero relayer fee; the fee is escrowed and `_requestCommitments[commitment]` / `RequestMetadata` is stored. [6](#0-5) 
2. Before the request is delivered or times out, a fisherman submits a valid `FraudProofMessage` for chain B's (or A's) consensus client, causing `freeze_client` to succeed and permanently freeze that consensus state. [5](#0-4) 
3. Any attempt to deliver the request via `request::handle` now fails at `validate_state_machine` with `Error::FrozenConsensusClient`. [8](#0-7) 
4. Once the request's `timeout_timestamp` elapses, submitting a `TimeoutMessage::Post` to reclaim the fee also fails at the same `validate_state_machine` call inside `timeout::handle`. [4](#0-3) 
5. Since the frozen client can never be resumed and no other code path calls `on_request_timeout`/refunds the fee, the escrowed amount remains locked in `RELAYER_FEE_ACCOUNT` / `EvmHost` indefinitely.

/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}

The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs.
