Confirmed: `Clients::HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop`, with no validation that `session.shop` is a genuine `*.myshopify.com`/trusted domain. [1](#0-0) 

### Title
OAuth callback sends `client_id`/`client_secret` to an unvalidated `shop` host, breaking the shop-authenticated = shop-trusted binding - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` authenticates the callback query with an HMAC check, but never verifies that `auth_query.shop` is an actual Shopify-owned domain (`*.myshopify.com`/etc.) before using it as the host that receives the app's `client_id` and `client_secret` in the access-token exchange request.

### Finding Description
The bug-class analog here is "the host validated versus the host that receives the access token or `client_secret`." In `validate_auth_callback`, the only binding enforced is the HMAC over `code, host, shop, state, timestamp` [2](#0-1) , verified via `Utils::HmacValidator.validate(auth_query)` [3](#0-2) . That check only proves the query bytes were signed with the app's secret key — it says nothing about whether `shop` is a genuine Shopify domain.

The unvalidated `auth_query.shop` value is then used to build a `null_session` and passed straight into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which POSTs the OAuth token-exchange body — containing `client_id` and `client_secret` — to that host: [4](#0-3) . `HttpClient#initialize` builds the request base URI directly from `session.shop` with no domain allow-list check: [1](#0-0) .

Likewise, `begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` with no sanitization: [5](#0-4) . The library ships a dedicated `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` utility whose explicit purpose is to reject non-Shopify hosts [6](#0-5) , but neither `begin_auth` nor `validate_auth_callback` calls it. So the equality the code should enforce — `shop used for OAuth requests == shop verified to be a Shopify-owned domain` — is never checked; only `shop signed by our own secret == shop received` is checked, which is a different, weaker binding.

### Impact Explanation
If an application built on top of this gem passes a user/attacker-controlled `shop` value straight into `begin_auth` (which the gem's own docs example does, taking it from `request.headers["Shop"]`) [7](#0-6) , the gem itself performs no defense-in-depth check before completing the flow. Because the gem is the last line of defense that actually issues the `client_secret`-bearing HTTP request, an attacker able to influence `shop` (e.g., a host app that forwards a query/header value without pre-validation, which is a very common integration mistake this library is supposed to guard against) can cause the app's `client_id` and `client_secret` to be POSTed to an attacker-chosen host. This is credential exfiltration of the app's `client_secret` to an attacker-controlled server — a Critical-class impact per the report's own categorization (theft of the app's `client_secret`), and separately an SSRF-with-app-credentials condition (High).

### Likelihood Explanation
The HMAC check does prevent a fully remote, credential-less attacker from forging a `code`/`shop` pair on their own since the secret key is required to pass `HmacValidator.validate`. However, the finding is that the gem's OAuth implementation provides no independent domain check on `shop` at all — relying solely on the calling application to pre-sanitize `shop`, and even documenting a `ShopValidator` utility for exactly this purpose without ever invoking it in `begin_auth`/`validate_auth_callback`. This is a real gap in the library's own trust boundary enforcement, not merely a host-app documentation issue, since the vulnerable code path (`HttpClient` construction from `session.shop`) is entirely internal to the gem.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of both `Oauth.begin_auth` and `Oauth.validate_auth_callback`, raising `Errors::InvalidShopError` before constructing `auth_base_uri` or the `null_session`/`HttpClient` used for the access-token request. This ensures the host that ultimately receives `client_id`/`client_secret` is always cryptographically constrained to a trusted Shopify domain, closing the gap between "HMAC-valid query" and "trusted destination host."

### Proof of Concept
1. A host application calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` without pre-validating `params[:shop]` (as shown in the gem's own documented usage) [7](#0-6) .
2. `begin_auth` builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."` with no domain check [8](#0-7) .
3. If the flow completes with `auth_query.shop` set to a non-Shopify host (any value that only needs to pass the HMAC check, which in a misconfigured/legacy integration or a compromised intermediary could already carry a validly-signed but incorrect `shop`), `validate_auth_callback` builds `null_session = Auth::Session.new(shop: auth_query.shop)` and issues the token request through `Clients::HttpClient.new(session: null_session, ...)` [4](#0-3) .
4. `HttpClient` sends `https://#{session.shop}/admin/oauth/access_token` with `client_id`/`client_secret` in the JSON body, exfiltrating the app's `client_secret` to `session.shop` [1](#0-0) .

        [
          "shopify.com",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
