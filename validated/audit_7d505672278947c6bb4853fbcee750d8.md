### Title
Emporium Min-circuit path with `signerAddress == 0` and empty token array lets any caller execute arbitrary calls as Emporium with zero accounting - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose only proven constraint is `message == Poseidon(messageSeed)` [1](#0-0)  and [2](#0-1) . Because `erc20TokenAddresses` is empty, every balance-accounting loop in `Hinkal.transact` and in `EmporiumUpgradeable.runAction` is a no-op (loop bound is 0), and `verifyWallet` skips the ECDSA signature check entirely whenever `stack.signerAddress == address(0)` [3](#0-2) . This lets an attacker submit an `EmporiumStack` with arbitrary `ops` that execute `op.endpoint.call{value: op.value}(op.callData)` directly with Emporium's identity as `msg.sender`, with no signature and no balance check constraining what is done.

### Finding Description
The broken equality: "assets Emporium can move in a tx == assets accounted in balancesBefore/balancesAfter" is violated because both arrays are empty by construction.

Path:
1. Attacker calls `Hinkal.transact` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`. `dimensionsCheck` (in `HinkalHelper.sol` lines 64-90) is satisfied trivially since every length-check is `0 == 0`, and `checkOnchainCreation` loop body never executes because `circomData.onChainCreation.length == 0` [4](#0-3) .
2. `formInputForCircom` selects `formInputEmporiumMin`, whose only public constraint is a self-chosen `message = Poseidon(messageSeed)` [5](#0-4) . The attacker can trivially satisfy this proof for any values they choose since `messageSeed` is fully attacker-controlled and unconstrained elsewhere.
3. `Hinkal.transact`'s balance-accounting loop over `circomData.erc20TokenAddresses` (lines 97-147) never executes because the array is empty [6](#0-5) .
4. `_externalTransact` builds an empty `deltaAmountChanges` array and calls `EmporiumUpgradeable.runAction` [7](#0-6) .
5. In `runAction`, `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array, so they are meaningless empty arrays [8](#0-7) . `verifyWallet` is called with `stack.signerAddress == address(0)`, which returns immediately after marking `emporiumMessage` used, skipping the ECDSA check entirely [3](#0-2) .
6. The loop over `stack.ops` then executes `op.endpoint.call{value: op.value}(op.callData)` as `msg.sender == Emporium` for any endpoint/calldata the attacker supplies, as long as the selector isn't `callHinkalWallet`/`doSendToRelay` [9](#0-8) . Nothing constrains `op.endpoint` or `op.callData` to relate to any token in `erc20TokenAddresses` (which is empty anyway).

Root cause: the "Min" fast-path was designed to skip balance accounting only for tokens explicitly listed (empty list), but Emporium's `runAction` unconditionally executes `stack.ops` regardless of the (empty) token list, and skips the wallet-signature check when `signerAddress == 0`. There is no invariant tying "the ops that get executed" to "the tokens whose balances are checked" — an attacker can execute privileged calls under Emporium's identity that touch tokens/state entirely outside the (empty) accounted set.

Concretely, an attacker can set `op.endpoint = <any ERC20 held by Emporium>`, `op.callData = approve(attacker, type(uint256).max)`, `op.invokeWallet = false`. This executes as Emporium and grants the attacker unlimited allowance over whatever balance Emporium holds of that token — with zero signature check and zero balance-diff enforcement, because the checked-array is empty.

### Impact Explanation
If Emporium ever holds any ERC20 balance (residual dust from previous multi-step operations, fees in transit, or funds temporarily routed through Emporium as part of another user's in-flight transaction), the attacker can drain it via `approve()`/`transfer()` calls issued as Emporium's identity, with no signature authorization and no balance-diff check to catch it. This matches "executing calls or moving assets a wallet owner or prover never authorised" (High), and if actual token balance is present in Emporium at call time, "direct theft of shielded or in-flight user funds" (Critical). This is fully repeatable per transaction (bounded only by `usedMessages[emporiumMessage]` replay protection, which the attacker trivially avoids by picking a fresh `emporiumMessage`/`messageSeed` each time) and costs the attacker only gas and one self-chosen proof.

### Likelihood Explanation
Preconditions: attacker needs a self-generated valid proof for `MainEVMCircuitMin` (trivial — pick any `messageSeed`, compute Poseidon off-chain), and `erc20TokenAddresses.length == 0`/`dimensions.tokenNumber == 0`, both fully attacker-controlled inputs, requiring no special privileges. Everything downstream — `EmporiumStack` construction, `signerAddress = address(0)`, arbitrary `ops` — is fully within attacker control per the stated threat model (they craft every field of `CircomData`/`externalActionMetadata`). The only external dependency for actual fund theft is Emporium holding a non-zero token balance at call time, which is plausible given Emporium's design as an intermediary that receives funds via `deltaAmountChanges` and forwards them through `ops`; residual/leftover balances (e.g., dust, fee-token remainders, or funds from a preceding unresolved operation) are a realistic occurrence in production usage.

### Recommendation
- Require `stack.signerAddress != address(0)` whenever `erc20TokenAddresses.length == 0` (the Min path), so stateless/self-authorized calls are never allowed without a valid signature.
- Alternatively/additionally, disallow execution of `stack.ops` entirely when `circomData.erc20TokenAddresses.length == 0`, or require the Min circuit path to still enforce that any external call in `ops` operates only on assets whose balances are checked before/after.
- Ensure `verifyWallet`'s skip-if-`signerAddress==0` branch is only reachable when the tx's balance-accounting loop actually covers every token/endpoint touched by `stack.ops`, closing the gap between "ops executed" and "balances checked."

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), and a mock ERC20 token `T`.
2. Fund Emporium directly with `T.mint(emporiumAddress, 1000e18)` to simulate residual/in-flight balance.
3. As attacker (non-privileged EOA), construct `CircomData` with:
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, `onChainCreation = []`, `amountChanges = []`, `slippageValues = []`, `inputNullifiers = []`
   - `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(T), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})], maxFee: 0, deadline: block.timestamp + 1}))`
   - `emporiumMessage`, `messageSeed` self-chosen; generate a valid `MainEVMCircuitMin` proof locally for `message = Poseidon([messageSeed])`.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert before/after: `T.allowance(emporiumAddress, attacker) == 0` before call, `== type(uint256).max` after call — i.e., the invariant "assets Emporium can move == assets accounted in balancesBefore/After" is broken since `balancesBefore`/`balancesAfter` arrays were empty throughout.
6. Follow with `T.transferFrom(emporiumAddress, attacker, 1000e18)` to demonstrate actual fund theft, asserting attacker's `T` balance increases by the full amount Emporium held.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }

        if (utxoSetLength < circomData.erc20TokenAddresses.length) {
            utxoSet.skipLast(
                circomData.erc20TokenAddresses.length - utxoSetLength
            );
        }

        return utxoSet;
    }
