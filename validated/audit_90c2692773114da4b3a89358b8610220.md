### Title
JWT Replay Guard TOCTOU Race in `WorkflowMetadataHandler.Authorize` Allows Same Token to Authorize Multiple Concurrent HTTP Trigger Requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status and records usage as two separate, non-atomic steps. Concurrent requests carrying the identical JWT (same `jti`) can both pass the `isReplay` check before either call reaches `recordUsage`, letting an unprivileged caller authorize and dispatch the same one-time-use token more than once — the same "check state, do external/expensive work, then update state" pattern that made the reported `distribute()` re-entrancy exploitable.

### Finding Description
`Authorize` performs:
```

	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	...
	if h.jwtCache.isReplay(claims.ID) {
		...
		return nil, errors.New("JWT token has already been used. ...")
	}
	keys, exists := h.authorizedKeys[workflowID]
	...
	h.jwtCache.recordUsage(claims.ID)

``` [1](#0-0) 

The check (`isReplay`) and the write (`recordUsage`) are two distinct calls to `jwtReplayCache`, not a single atomic "check-and-set" operation, unlike the pattern used elsewhere in the codebase (e.g. the vault capability's `replayGuard.CheckAndRecord`, which is explicitly one atomic call): [2](#0-1) 

Between the `isReplay` check and `recordUsage` write, the caller also performs JWT signature verification and an authorized-key map lookup — enough work that two goroutines processing two copies of the same JWT (e.g., replayed by an unprivileged external client at the gateway's public HTTP trigger endpoint) can both observe `isReplay == false` and both proceed to `recordUsage`, each succeeding in `Authorize`. Each caller then proceeds through `HandleUserTriggerRequest` — `authorizeRequest` → `checkRateLimit` → `setupCallback` → `sendWithRetries` — dispatching two independent workflow executions from a single supposedly one-time-use signed request: [3](#0-2) 

The only downstream de-duplication is on the JSON-RPC `req.ID`, checked in `setupCallback`: [4](#0-3) 
An attacker who wants to bypass the JWT-based single-use guarantee can simply mint two `jsonrpc.Request` envelopes with different top-level `ID` fields but bind both to the *same* JWT (the JWT's digest is computed over the request body/params, not the JSON-RPC envelope `ID` alone, per the "JWT digest mismatch" test which only checks params match) — this would let the same signed authorization drive two distinct `req.ID`s past `setupCallback`'s per-ID dedup, defeating the JWT replay guard's intended one-time semantics.

This is the same defect class as the reported `distribute()` re-entrancy: a security invariant ("this JWT authorizes exactly one execution") is enforced by a check performed before the corresponding state mutation, with intervening work (crypto verification, map lookups, or concurrent scheduling) creating a window in which the invariant can be violated by an unprivileged caller replaying their own signed message.

### Impact Explanation
A workflow owner (or anyone in possession of a single valid signed HTTP-trigger JWT) can exploit the race to have their workflow executed multiple times from what is meant to be a single-use trigger token. Depending on the workflow's side effects (on-chain transactions, external API calls, capability executions), this can result in duplicated fund movement, duplicate job/workflow runs, or duplicate consumption of downstream resources — a direct analog to the "acquire allocation repeatedly" impact in the report, translated to "trigger execution repeatedly."

### Likelihood Explanation
Exploitation requires only the ability to send two requests to the gateway's public HTTP trigger endpoint at (or near) the same time using the same JWT (which the requester already legitimately possesses since they signed it) — no privileged access is needed. The race window is small but real, since `VerifyRequestJWT` (crypto signature verification) and the authorized-key map lookup both occur between the `isReplay` check and `recordUsage` write, and `HandleUserTriggerRequest` runs the whole authorize→dispatch pipeline per incoming request without any earlier de-duplication keyed on the JWT `jti` itself.

### Recommendation
Make the JWT replay check-and-record a single atomic operation (mirroring `replayGuard.CheckAndRecord` used by the vault authorizer), e.g. an `Add`-style cache operation that atomically inserts the `jti` and reports whether it was already present, and reject the request if insertion fails — eliminating the check/act window. Additionally, guard the whole `Authorize` call (or the segment from JWT verification through `recordUsage`) with a mutex keyed on `jti` to prevent any concurrent duplicate processing.

### Proof of Concept
1. Client signs a JSON-RPC HTTP trigger request with JWT `jti = "abc"` for workflow `W`.
2. Client fires two concurrent HTTP POSTs to the gateway's trigger endpoint, each wrapping the same signed JWT but with distinct outer `jsonrpc.Request.ID` values (`req-1`, `req-2`).
3. Both requests reach `WorkflowMetadataHandler.Authorize` roughly simultaneously; both call `h.jwtCache.isReplay("abc")`, both observe `false` (cache not yet updated), both proceed through signature/authorized-key checks, and both call `h.jwtCache.recordUsage("abc")`.
4. Both `Authorize` calls succeed, so both `HandleUserTriggerRequest` calls (with distinct `req.ID`s, so `setupCallback`'s dedup does not trigger) advance to `sendWithRetries` and dispatch the workflow to the DON — resulting in two full executions of the workflow from one JWT that was meant to authorize exactly one.

*Note: I could not directly view the internals of `jwtReplayCache.isReplay`/`recordUsage` (only grep matches were returned, not file contents), so the exact locking granularity inside `jwtReplayCache` is inferred from the calling code's structure and the two-call pattern in `Authorize`. If `jwtReplayCache` itself already implements an atomic check-and-set under a single lock spanning both calls, this exact race would not exist; verifying this requires reading `workflow_metadata_handler.go`'s `jwtReplayCache` methods in full, which a Devin session with full file access could confirm.*

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
