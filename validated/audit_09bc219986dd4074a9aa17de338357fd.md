This confirms the vulnerability path. `WebhookMetadata.shop` (used by every host app's `handle` implementation to attribute the payload to a tenant) is populated directly from `request.shop` (the `shopify-shop-domain`/`x-shopify-shop-domain` header), while the HMAC that `Registry.process` validates only covers the raw body via `Request#to_signable_string`, which returns `@raw_body` alone.### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC over the raw request body only, but the shop (tenant) identity delivered to the host application's handler is taken from an unauthenticated HTTP header. This breaks the binding: `shop verified by HMAC == shop attributed to the payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC purely against `to_signable_string`, i.e. only the body: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` (and sibling) headers, which are not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata`, which is handed to the host application's handler as the trusted tenant/topic context: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further verification performed by the gem: [5](#0-4) 

Because the HMAC only proves "this body was HMAC-signed by someone holding `api_secret_key` at some point for some shop" and not "this body belongs to shop X", any attacker who possesses one valid `(body, hmac)` pair for their own tenant (which they legitimately receive as the owner of their own shop/webhook endpoint) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The signature still validates (it never covered the header), and the host application's handler will process the payload as if it came from the victim shop named in the forged header — a direct violation of `shop authenticated == shop stored/acted upon`.

### Impact Explanation
This is a cross-tenant data/identity confusion: an attacker-controlled webhook body (with a valid HMAC for the attacker's own shop) can be attributed by the handler to any other shop domain the attacker chooses, since `WebhookMetadata.shop` is trusted by every downstream consumer (e.g., to look up sessions, write records, or trigger tenant-scoped side effects) without independent verification. Depending on how the host application keys its per-shop storage/session lookup off `WebhookMetadata.shop` (which is the intended and documented use of that field), this can let an unprivileged attacker inject or corrupt data under another merchant's identity — a cross-tenant access vulnerability.

### Likelihood Explanation
Exploitation requires the attacker to have at least one real, validly-HMAC'd webhook body (trivial: register their own store/app installation, which is normal unprivileged access, and capture any webhook delivery), then replay it to the shared webhook endpoint with a different `shop-domain` header. No possession of `api_secret_key`, access tokens, or the victim's credentials is needed. The gem performs no correlation between the signed body and the header-derived shop, so likelihood of successful exploitation is high wherever a host app trusts `WebhookMetadata.shop` for tenant attribution (which is its only documented purpose).

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind the header-derived shop to the verified payload before constructing `WebhookMetadata`. At minimum, `HmacValidator`/`Request` should incorporate the `shop-domain` header into `to_signable_string`, or `Registry.process` should independently verify that the `shop-domain` header corresponds to a shop with a currently valid stored session/access token before dispatching to the handler, rejecting mismatches.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers/captures a legitimate webhook delivery: raw body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` computed with the app's `api_secret_key`), along with `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but rewrites `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only (`Request#to_signable_string` returns `@raw_body`) — validation succeeds because `B` and `H` are unmodified. [6](#0-5) 
4. `WebhookMetadata.new(shop: request.shop, ...)` now carries `shop: "victim.myshopify.com"` even though the body/hmac pair was never issued for that shop, and the host app's handler processes the request as authentic data for the victim tenant. [7](#0-6)
