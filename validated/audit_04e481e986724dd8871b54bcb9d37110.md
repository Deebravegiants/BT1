### Title
Flash-loan receiver is caller-chosen; the pool pulls principal+fee via `transfer_from` on the victim's standing allowance without its authorization - (File: contracts/pool/src/ops/flash.rs)

### Summary

`Controller::flash_loan(caller, asset, amount, receiver, data)` lets any unprivileged caller name an arbitrary WASM contract as `receiver`. The pool pays the principal to that receiver, invokes its `execute_flash_loan` callback, and then repays itself with `token.transfer_from(pool, receiver, pool, amount + fee)` — gated only by `asset.allowance(receiver, pool) >= total_repayment`. No `require_auth` on `receiver` exists anywhere in the path. A victim integrator contract that keeps a standing token allowance to the pool (the standard documented flash-receiver integration pattern: "Receiver approves `amount + fee` to the pool") can be named as `receiver` by anyone and forced to pay the flash fee out of its own allowance, repeatedly, up to the full allowance. This is the exact CVE-2018-1063 class: a privileged operation (context relabel / `transfer_from` pull) applied to an attacker-selected target the attacker does not control.

### Finding Description

In `contracts/controller/src/strategies/flash_loan.rs`, `process_flash_loan` authenticates only `caller` (`require_authorized_caller`), then forwards the caller-supplied `receiver` to the pool after only `require_wasm_receiver` — which checks the address is a contract, not that it consented.

In `contracts/pool/src/ops/flash.rs`:

- `apply` transfers `amount` to `receiver` and invokes `execute_flash_loan` on it.
- `collect_repayment` (lines 166–180) asserts `asset.allowance(receiver, pool) >= terms.total_repayment` and calls `asset.transfer_from(pool, receiver, pool, &terms.total_repayment)`.

The victim receives `amount` and loses `amount + fee` from its balance via its own allowance — net loss = `fee` per call, paid into protocol revenue (`book_fee`). Because the allowance check is the only consent mechanism, an attacker iterates `flash_loan` at maximum `amount` on the victim's token; each iteration burns `fee` of the victim's funds into protocol revenue until the allowance or balance is exhausted. Unlike classic `transfer_from` allowance drain, the victim never authorized this invocation — the Soroban `transfer_from` model delegates spender authority to the pool permanently once approved, and nothing binds the loan to an auth from `receiver`.

The callback requirement narrows but does not eliminate the victim set: any deployed contract exposing an `execute_flash_loan` entrypoint that returns successfully (i.e., exactly the integrator contracts that hold the standing allowance) is a valid target. There is no check that the callback actually repaid or that `receiver` initiated anything; the "repayment" is unconditional confiscation of `amount + fee`.

### Impact Explanation

Theft of user funds: funds sitting in a victim integrator/vault contract that maintains a pool allowance are forcibly converted into protocol revenue, `fee` per call, without the victim's consent or action. For a 10 bps fee on a market with 1M units of cash, each permissionless call destroys ~1,000 units of the victim's balance; looping to the market's `require_reserves` cap drains up to `fee_rate × reserves` per transaction and `fee_rate × allowance` in aggregate across calls. The victim also cannot prevent it short of racing to revoke its allowance, because `flash_loan` is fully permissionless.

### Likelihood Explanation

Medium-high. The precondition — a contract with a live `allowance(receiver → pool)` on a flash-loanable asset and an `execute_flash_loan` entrypoint — is precisely the documented integration shape for flash-receiver contracts (SKILL/docs instruct receivers to approve `amount + fee` to the pool). Approval windows in Stellar asset tokens are ledger-bounded, so allowances are typically left wide. The attack costs the caller nothing (it funds nothing — the pull comes from the victim's allowance), succeeds atomically, and only fails if the callback reverts or allowance is insufficient.

### Recommendation

Bind the loan to the receiver's consent:

1. Require `receiver.require_auth()` (or `require_auth_for_args` over `amount`/loan terms) inside `apply` or in `execute_flash_loan` enforcement, so a contract must actively sign for each loan taken out under its allowance.
2. Alternatively, replace the `transfer_from` pull with the measured-receipt pattern used elsewhere in the codebase (assert `balance_after_repayment` is reached by the callback pushing tokens back), so a standing allowance is never consumed by an uninitiated loan.
3. Optionally let the receiver's callback declare/lock repayment intent keyed to `initiator` and `data`, so a stale allowance cannot be weaponized.

### Proof of Concept

```rust
// Victim: a legitimate flash-receiver integrator that pre-approved the pool.
// It holds BALANCE tokens and allowance(victim -> pool) = MAX.

// Attacker (unprivileged EOA), per call:
controller.flash_loan(
    &attacker,                       // caller — only auth required
    &HubAssetKey { hub_id: 0, asset: usdc },
    &(pool_cash - 1),                // amount: max reserves pass require_reserves
    &victim_contract,                // receiver: attacker-chosen, never authorizes
    &Bytes::new(&env),               // data
);

// Inside pool::flash::apply:
//   transfer(pool -> victim, amount)          // victim +amount
//   victim.execute_flash_loan(attacker, ...)  // victim's own impl returns Ok
//   transfer_from(pool, victim, pool, amount+fee) // consumes victim allowance
//
// Net per call: victim balance -fee, allowance -amount+fee... allowance only
// decrements by total_repayment; victim receives amount, pays amount+fee.
// Repeat until allowance < amount+fee or balance < total_repayment.
// Victim total loss ≈ fee × number_of_calls, bounded below by fee ×
// (allowance / total_repayment) iterations at maximum amount.
```

Note on residual uncertainty: I verified the full controller → pool → token flow, the absence of any `receiver.require_auth`, and the allowance-gated `transfer_from` pull in `collect_repayment`. I did not enumerate deployed integrators to confirm a live victim with both a standing allowance and a non-reverting `execute_flash_loan`; the finding stands on the in-scope contract logic, which permits the drain whenever such a receiver exists — the allowance itself is the documented integration requirement.
