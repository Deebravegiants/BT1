### Title
Stale cached spoke config lets a flash_position/multiply callback rebind listing parameters between validation and settlement via permissionless governance `execute` - (File: contracts/controller/src/context.rs)

### Summary
The external bug is a TOCTOU: a path is validated, then written later against state an attacker rebinds in between. Soroban transactions are atomic, but the controller reintroduces the same shape inside one transaction: `Context` snapshots spoke asset configuration, pool sync data, prices, and market indexes on first use and never re-reads them. Every callback-equipped entrypoint (`flash_position`, `multiply`, router strategies) opens a window between "validation" (cache population) and "use" (deposit/risk gates at finalization). Inside that window, an unprivileged receiver can drive `governance.execute(executor=None, ...)`, which executes any `Ready` scheduled op with no authentication, mutating `SpokeAssetConfig` in storage while the controller continues against the stale cache.

### Finding Description
`Context::cached_spoke_asset` loads `SpokeAssetConfig` once per invocation and retains it (`context.rs:192-204`); `cached_pool_sync_data` does the same for pool params (`context.rs:94-102`). In `process_flash_position`, `validate_collaterals` → `require_can_supply` and the `is_flashloanable` check populate those caches *before* the receiver callback runs (`flash_position.rs:87-111`, `:174-215`). After the callback, `process_deposit`, `refund_listed_assets`, and `strategy_finalize`'s LTV/health-factor/collateral-floor gates all read the same cached configs — there is no storage re-read.

The rebind primitive is `governance.execute`: with `executor = None`, "no executor role check (anyone may drive execution of a ready op)" (`governance/src/api.rs:53-67`; `endpoints.md:199`; regression test `tests/governance/permissionless_execution.rs:59-71`). The op executes inside the flash callback and calls controller admin functions such as `edit_asset_in_spoke`, which rewrite the listing's LTV, threshold, caps, and halt flags directly in storage. The flash guard (`storage::with_flash_guard`) blocks protected *monetary* entrypoints (supply/borrow/withdraw/repay/liquidate — INV-FLASH-02 in `docs/reference/invariants.md:614-625` enumerates the six guarded windows), but admin mutators reached through governance are not monetary entrypoints and are not enumerated in that list.

So an attacker can: wait until a governance op that tightens a listing is `Ready` (ops sit executable for the full `TIMELOCK_OPERATION_GRACE_LEDGERS = 120_960` window), open `flash_position` declaring that asset as collateral so the old permissive config is cached, execute the op from the receiver callback (e.g., `EditAssetInSpoke` setting `loan_to_value = 0`, `paused = true`, `supply_cap = 0`, or `is_collateralizable = false`), then let finalization mint debt judged against the pre-change LTV/caps. The account is written with debt the live parameters would forbid.

### Impact Explanation
The post-action risk gates (`require_post_pool_risk_gates`: `ltv_collateral ≥ total_debt`, `HF ≥ 1`, `ltv_collateral ≥ min_borrow_collateral_usd`) and the cap checks in `SpokeUsageContext::apply_entry` are the only things standing between `flash_position`'s fee-free debt mint and undercollateralized borrowing. All of them evaluate on the stale snapshot. Borrowing against collateral whose live `loan_to_value` is now 0, or past a just-lowered borrow cap, leaves the protocol holding debt with no collateral backing — direct insolvency, the same "write outside the validated boundary" outcome as the ZIP rebind.

### Likelihood Explanation
The attacker cannot create the governance op, so exploitation requires a genuinely scheduled op. However: (a) param/spoke edits are routine ops; (b) once `Ready`, the op is executable by anyone for a 120,960-ledger grace window, so the attacker picks the exact transaction; (c) no privilege, timing race, or oracle manipulation is needed — a single `flash_position` call bundles everything. Main uncertainty: whether controller admin functions invoked via governance check the flash guard; the guarded-window enumeration in INV-FLASH-02 covers only monetary entrypoints, suggesting they do not, but I could not fully verify the admin path's guard behavior.

### Recommendation
Treat cached risk config the way the ZIP fix treats the file handle: bind settlement to the validated identity. Either re-read `SpokeAssetConfig`/`PoolSyncData` from storage inside `strategy_finalize` (drop or refresh `cache.spoke_assets`/`pool_sync_data` after the callback), or record each cached config's mutation epoch/storage-version and assert it unchanged after the callback returns. A cheaper belt: make governance-driven controller admin mutators reject while the flash guard is active, matching the monetary entrypoints.

### Proof of Concept
```text
Precondition: PROPOSER has scheduled AdminOperation::EditAssetInSpoke for
(hub H, USDC, spoke S) setting loan_to_value = 0; the delay elapsed, op is Ready.

1. Attacker calls controller.flash_position(
       caller=attacker, account_id=0, spoke_id=S,
       mode=Multiply, debt=HubAssetKey{H, USDC}, amount=A, receiver=R, ...)
   - validate_collaterals → cached_spoke_asset(S, XLM) caches LTV=7500 (old config)
   - cached_pool_sync_data(USDC) caches params (is_flashloanable, caps)
   - borrow_into_controller mints A USDC debt shares, transfers to receiver R

2. Inside R.execute_flash_position callback:
   - call governance.execute(None, controller, "edit_asset_in_spoke",
         args(new_config_with_ltv_0), predecessor, salt)   // permissionless
   - storage now holds LTV=0 for XLM; Context still holds LTV=7500
   - transfer declared collateral to controller (any token with min>0)

3. Back in process_flash_position:
   - process_deposit credits collateral under stale config
   - strategy_finalize → require_post_pool_risk_gates computes ltv_collateral
     with cached LTV=7500 → HF ≥ 1 → passes
   - position persists with debt A against collateral that, under live
     parameters, backs 0 borrow capacity

Result: undercollateralized debt created in one transaction; a second Ready op
raising a borrow cap back (or none needed) leaves the debt outstanding.
```
