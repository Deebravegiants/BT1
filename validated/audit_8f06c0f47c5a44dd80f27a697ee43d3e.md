### Title
Withdrawal status/tx-hash misattribution across same-asset withdrawals in a batched intent - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a single NEAR intent transaction contains two or more PoA-bridge withdrawals of the same token (e.g., two `btc.omft.near` withdrawals to different destination addresses/amounts within one `intentTx`), `PoaBridge.describeWithdrawal()` cannot tell them apart. It ignores the caller-supplied `index` and returns whichever entry in the POA API response first matches the `assetId`, regardless of which index/destination the caller actually asked about.

### Finding Description
`createWithdrawalIdentifiers()` builds a `WithdrawalIdentifier` per withdrawal, assigning a monotonically increasing `index` per bridge route so that callers (integrators/relayers polling withdrawal status) can track each individual withdrawal within a multi-withdrawal transaction [4](#0-3) .

However, `PoaBridge.describeWithdrawal()` never uses `args.index` to select the matching entry from the POA API's `withdrawals` array. It only matches by `assetId` via `findMatchingWithdrawal`, whose own doc comment states: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) :

```
// Response list is unsorted, so we match by assetId instead of index
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```

The equality that should hold is: *the status/hash reported for withdrawal index N* == *the on-chain outcome of withdrawal index N specifically*. Because matching is asset-only, if two withdrawals of the same asset exist in one transaction (e.g., different `destinationAddress` or `amount`), `describeWithdrawal({index: 0, ...})` and `describeWithdrawal({index: 1, ...})` can both resolve to the very first matching array entry, so the wrong `transfer_tx_hash`/status is returned for one of the withdrawals. The same defect exists in the sibling helper `waitForWithdrawalCompletion()` in `internal-utils`, whose `findMatchingWithdrawal` has the identical limitation [5](#0-4) .

### Impact Explanation
`watchWithdrawal()` propagates whatever `describeWithdrawal()` returns directly as the completion result (`{hash: status.txHash}`) to the caller [6](#0-5) . An integrator that batches multiple same-asset withdrawals to different users/addresses in one intent transaction and polls per-index status would receive a status/tx-hash for the wrong withdrawal, potentially causing it to mark the wrong recipient's withdrawal as "completed" with someone else's destination tx hash — a misreport that can lead an integrator to credit or reconcile the wrong withdrawal, matching the "status or hash misreport" High-impact class.

### Likelihood Explanation
This requires the integrator to submit more than one PoA-bridge withdrawal of the identical `nep141:` asset within a single NEAR transaction, which the SDK's public batching API (`createWithdrawalIdentifiers`, used by `sdk.ts`) explicitly allows and assigns distinct indexes for; no malicious actor is needed to trigger it, only ordinary use of the batch withdrawal feature with duplicate-asset entries. Likelihood is limited to integrators that actually batch withdrawals of the same token per transaction, but the code path is directly reachable through public SDK usage without any extra privileges.

### Recommendation
Use `args.index` to disambiguate among same-asset withdrawals returned by the POA API — e.g., filter all withdrawals matching `assetId`, then select the Nth match ordered by amount/creation time (as the existing code comment already suggests), rather than always taking the first match, in both `PoaBridge.describeWithdrawal()` and `waitForWithdrawalCompletion()`. At minimum, when more than one match exists for the same asset in the response, the SDK should raise an explicit error/ambiguous-match warning instead of silently returning a possibly-wrong result.

### Proof of Concept
1. Build an intent with two `ft_withdraw` PoA withdrawals of `nep141:btc.omft.near`: one to address A for amount X, one to address B for amount Y, in a single NEAR transaction.
2. Call `createWithdrawalIdentifiers` — this yields `wid` with `index: 0` for the A withdrawal and `index: 1` for the B withdrawal, both same `tx.hash`.
3. Call `bridge.describeWithdrawal({..., index: 0, withdrawalParams: {assetId: "nep141:btc.omft.near", destinationAddress: A, ...}})` and `describeWithdrawal({..., index: 1, ...B...})`.
4. Because `findMatchingWithdrawal` only checks `assetId`, both calls resolve to `response.withdrawals.find(...)` — the same first array entry — so both report the same `transfer_tx_hash`, even though the underlying array contains two distinct entries with two distinct destination addresses/tx hashes. Depending on API ordering, the withdrawal for B can be reported as complete under A's identifier and vice versa. This is confirmed by the maintainers' own test comment: "matches withdrawal by assetId, not by index" [7](#0-6) , which currently only validates cross-asset disambiguation, not same-asset multi-withdrawal disambiguation.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
