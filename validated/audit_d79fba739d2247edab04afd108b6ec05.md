### Title
Predictable, unsigned session identifier enables cross-tenant session hijacking for non-embedded apps - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded (and cookie-fallback) apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` trusts the raw `shopify_app_session` cookie value as the session identifier with no cryptographic verification. That identifier, generated by `ShopifyAPI::Auth::Session.from`, is a fully deterministic, non-secret string (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{user_id}"` for online sessions) derived only from the public shop domain. Nothing binds the cookie bytes to the OAuth flow that created the session, so any party who knows (or guesses) a shop's `.myshopify.com` domain can construct the exact cookie value used to key that shop's stored access token.

### Finding Description
`ShopifyAPI::Auth::Session.from` builds the session `id` purely from public/predictable inputs: [1](#0-0) 

This `id` becomes the literal value of the `shopify_app_session` cookie handed to the browser after OAuth completes: [2](#0-1) 

On subsequent requests, `SessionUtils.current_session_id` (for non-embedded apps, or as the documented embedded-app fallback) reads that cookie and returns its value *verbatim* as the session id — with no HMAC, signature, or other proof that the value actually originated from this app's own OAuth flow: [3](#0-2) [4](#0-3) 

The documented integration pattern is to use this returned id to look up the previously stored `Session` (containing the real `access_token`) from app-side storage: [5](#0-4) 

The security-relevant identity binding that should hold is:
`cookie_value == session_id issued to *this* browser as a result of a real, HMAC-verified OAuth callback for shop S`

What is actually checked is only:
`cookie_value == some string equal to "offline_{S}"`, a value computable by anyone who knows `S` — there is no secret material in this binding at all. Compare this to the embedded-app path, where the equivalent identity is carried inside a JWT signed with `Context.api_secret_key` (see `ShopifyAPI::Auth::JwtPayload#decode_token`, `lib/shopify_api/auth/jwt_payload.rb:76-81`) — cryptographically bound. The cookie path has no analogous protection.

### Impact Explanation
An attacker who knows a target merchant's `.myshopify.com` domain (typically public/discoverable) can set their own browser's `shopify_app_session` cookie to `offline_{victim-shop}.myshopify.com` (or `{victim-shop}_{guessed-user-id}` for online sessions) when interacting with a non-embedded app built on this gem. Following the documented pattern, the host app will use this attacker-supplied, unauthenticated string to fetch the victim shop's stored `Session`/`access_token` from its session storage and proceed to make Admin API calls on the attacker's behalf using the victim's credentials. This is a cross-tenant session hijack, and depending on scopes granted the app could grant Critical-level cross-tenant access to merchant data using the merchant's own access token, without the attacker ever needing that token, the app's `client_secret`, or valid OAuth flow.

### Likelihood Explanation
Likelihood is high for any host application following the gem's own documented `current_session_id`/cookie pattern for non-embedded apps: the shop domain is usually public, the id format is fixed and documented, and no cryptographic material is required to forge it. The only assumption is that the host app persists/looks up sessions keyed by this id and doesn't add its own independent binding — which is exactly the flow shown in this gem's own `docs/getting_started.md`.

### Recommendation
Do not use a value derived solely from public data (`shop`, `user_id`) as a bearer credential in an unsigned cookie. Either:
- Sign/HMAC the cookie value (e.g., wrap it similarly to the OAuth state/HMAC validation already used in `Utils::HmacValidator`) so `current_session_id` can reject tampered/forged cookie values, or
- Store a separate, cryptographically random session token in the cookie (distinct from the internal storage key `id`), and resolve `shop`/`access_token` only through that random token server-side.

### Proof of Concept
1. Note or guess a target's shop domain, e.g. `victim-shop.myshopify.com` (often public).
2. As an unauthenticated attacker, send a request to the non-embedded app with cookie header:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged (`lib/shopify_api/utils/session_utils.rb:35`, `cookie_session_id` at line 68-71) — no verification performed.
4. Following the documented pattern, the host app looks up `MyApp::SessionRepository` using this id, retrieves the victim shop's real `Session` (including `access_token`), and the attacker's request proceeds authenticated as the victim shop.

### Sessions

Sessions are required to make requests with the REST or GraphQL clients. This Library provides helpers for creating sessions via OAuth. Helpers are provided to retrieve session ID from a HTTP request from an embedded Shopify app or cookies from non-embedded apps.

Session persistence is handled by the [ShopifyApp](https://github.com/Shopify/shopify_app) gem and is recommended for use in the Rails context. See that gem for documentation on how to use it.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
