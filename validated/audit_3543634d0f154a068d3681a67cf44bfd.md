## Finding

### Title
Webhook Shop/Topic Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it checks only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which the app uses to attribute the webhook to a specific tenant — are read from unauthenticated HTTP headers and are never bound to the signature. This is the same class of bug as the reported analog: a value that is *acted upon* (tenant/shop attribution) is not covered by the identity check (HMAC) that is supposed to authenticate it.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is computed from the `shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read straight from headers and are **not part of `to_signable_string`**: [2](#0-1) 

`HmacValidator.validate` signs/compares only `to_signable_string` (the raw body) against the secret: [3](#0-2) 

`Registry.process` treats this body-only check as validating the whole request, then forwards the unauthenticated `shop` header straight to the app's handler as the tenant identifier: [4](#0-3) 

The documentation reinforces the false guarantee, stating that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

**The broken identity binding, stated as an equality that fails:**
`shop_bound_by_hmac == shop_used_for_tenant_attribution`

Before request: HMAC covers only `raw_body`; the shop the HMAC actually authenticates is "whichever body I hold, however Shopify originally produced it" — no shop identity at all.
After request: `data.shop` (used by the handler for tenant routing/isolation) is taken verbatim from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which carries zero cryptographic binding to the signature.

Since any body/HMAC pair the requester possesses (e.g., their own legitimately received webhook for their own shop, or any publicly observable webhook payload) remains valid under `HmacValidator.validate` regardless of which `shop-domain` header accompanies it, an attacker who owns a legitimate installation of the app (an unprivileged merchant, not a privileged party, and without ever touching `api_secret_key` or another shop's access token) can take a real webhook they legitimately received for their own shop and replay it against the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `Registry.process` will accept it (HMAC over body still matches) and hand the handler `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem's own documentation promises ("verify the request did indeed come from Shopify" / shop domain of the webhook). Any app that uses `data.shop` from the handler to select which merchant's records to create/update/delete (the pattern shown in the gem's own usage example, `perform_later(shop_domain: data.shop, ...)`) can be made to process a validly-HMAC'd payload under a spoofed tenant identity — i.e., cross-tenant data injection/corruption using only material the attacker (as a legitimate but unprivileged app user) has legitimate access to. This falls under the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-low but realistic: the attacker needs at least one legitimately delivered webhook body+HMAC pair (trivial to obtain by installing the app on their own store and triggering any registered topic, e.g. `orders/create`), and network access to the app's public webhook endpoint (which is public by design). No secrets, tokens, or privileged access are required — only normal merchant-level interaction with the app plus the ability to send a raw HTTP POST with modified headers, matching the "unprivileged internet user" threat model.

### Recommendation
Do not treat `Utils::HmacValidator.validate(request)` as authenticating the shop/topic/webhook_id/api_version headers. Either:
- Extend the signable payload to bind these header values into the signature check the gem performs, or
- Explicitly document (and enforce, e.g., via a required callback) that consuming apps must independently verify `data.shop` against a shop they have an active, previously-established session/installation record for before trusting it for tenant attribution, rather than implying `process` fully authenticates the request as shown in the current docs example.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and registers for webhook topic `orders/create`.
2. Attacker places an order, triggering Shopify to POST a legitimately-HMAC-signed webhook to the app's public endpoint, e.g.:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {...order json...}
   ```
   The attacker captures this raw body and its accompanying HMAC (their own webhook, no interception needed).
3. Attacker replays the exact same body and HMAC header, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`:
   ```ruby
   headers = {
     "x-shopify-topic" => "orders/create",
     "x-shopify-hmac-sha256" => captured_hmac,   # unchanged, still valid for body
     "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled
   }
   ShopifyAPI::Webhooks::Registry.process(
     ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
   )
   ```
4. `Utils::HmacValidator.validate` succeeds (it only checks `captured_body` against the secret), and the app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-supplied order data as if it belonged to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
