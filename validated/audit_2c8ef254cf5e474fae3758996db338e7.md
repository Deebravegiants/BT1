### Title
Permanent market freeze via i128 overflow in `scaled_to_original` once scaled position value exceeds the RAY-value ceiling - (File: common/src/rates/scaling.rs)

### Summary
Every state-mutating pool verb and every controller risk/liquidation path accrues interest first by computing `scaled_amount * index`. That product is a RAY-scaled value; once a market's `supplied` or `borrowed` share count is large enough, `scaled_to_original` overflows `i128` and panics with `MathOverflow` (`common/src/math/fp_core.rs`, `common/src/rates/scaling.rs:14-16`, `common/src/rates/simulate.rs:60-61`). From that point on, every verb that touches the market — `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `claim_revenue`, `update_indexes` — reverts in the same accrual pre-step, so the market is frozen permanently. This mirrors the CVE-2024-21056 class (an operation that repeatably crashes the service → complete DoS), mapped onto XOXNO Lending's RAY share/index arithmetic.

### Finding Description
`global_sync` runs chunked accrual before any mutation (`contracts/pool/src/interest.rs:20-33`), and `accrue_step` calls `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` (`common/src/rates/simulate.rs:60-61`). `scaled_to_original` is `scaled.mul(index)`, i.e. `scaled * index / RAY` in `i128`/widened `I256` (`common/src/math/fp_core.rs`). The widened path still must fit `i128`, so once `scaled * index / RAY > i128::MAX`, the multiplication panics. `i128::MAX ≈ 1.7e38`; with `index` near `RAY` (1e27) the cliff is already at `scaled ≈ 1.7e38` — i.e. ~1.7e11 whole tokens of an 18-decimal asset — and the cliff lowers as the borrow/supply index grows, so ordinary accrual pushes a whale market over it even if entry was safe.

The production test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`) demonstrates the freeze concretely: after the accrual panic, `try_withdraw`, `try_repay`, and `update_indexes` all fail with `MATH_OVERFLOW`, and the stored index is still below `MAX_BORROW_INDEX_RAY`, meaning the `update_borrow_index` clamp (`common/src/rates/index.rs:13-19`) never engages to stop growth — the value-overflow cliff is reached first and there is no recovery path, since cleanup/recapitalization entrypoints also accrue first. ### Impact Explanation
Permanent freezing of funds for every supplier of that market, and protocol insolvency for the stranded debt leg: no withdrawal, repayment, liquidation, bad-debt cleanup, or revenue claim can execute because all of them re-enter the panicking accrual. The attacker path is a single unprivileged `supply` (or `supply` + `borrow` for the debt side) of a very large nominal amount of a high-decimal listed asset whose supply cap permits it — cap checks compare scaled caps that saturate fail-open (`common/src/rates/scaling.rs:26-33`), and the entry itself succeeds because at supply time `supplied` was small/zero. Once the position is in place, either the entry size alone (≥ ~1.7e38 RAY shares) or subsequent index growth crosses the cliff and the market bricks irreversibly. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
Medium. Reachability requires a listed market on a high-decimal, high-nominal-supply token (or many years of accrual on a smaller book at steep utilization), plus a supply/borrow cap permissive enough to admit the position — all conditions an unprivileged caller can satisfy only where governance-listed parameters allow it. The cost is real capital locked in the pool, but the payoff is a permanent, unrecoverable freeze of all other suppliers' funds in that market. The cliff is a tested, acknowledged domain boundary rather than an exotic edge. [7](#0-6) 

### Recommendation
Make accrual value-overflow-safe so the market degrades instead of bricking: use `mul_div_floor_saturating` (already used by `calculate_scaled_cap`) or a checked path in `scaled_to_original`/`position_value_*` for the utilization and index-growth computation, clamping the saturated value so `update_borrow_index` can still advance toward `MAX_BORROW_INDEX_RAY` and stop interest rather than panic. Alternatively, bound `supplied`/`borrowed` scaled shares at entry (a `POSITION_LIMIT_MAX`-style ceiling on total scaled supply per market) so `scaled * index` can never reach `i128::MAX` before the index cap engages.

### Proof of Concept
```
1. Governance has listed an 18-decimal asset with a large/uncapped supply cap.
2. Attacker calls controller::supply(caller=attacker, account_id=0,
   assets=[(hub, asset, N)]) where N ≥ ~1.7e11 whole tokens
   (scaled shares × supply_index/1e27 ≥ i128::MAX). Supply succeeds:
   accrual ran with the pre-supply (small) `supplied`.
3. Any subsequent call — victim withdraw, attacker repay, permissionless
   update_indexes, liquidation, clean_bad_debt — enters global_sync →
   accrue_step → scaled_to_original(supplied, supply_index), which panics
   MathOverflow. The panic is permanent: accrual is the first step of every
   verb and no entrypoint can write a smaller `supplied`.
```
The harness test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` is the executable version of this PoC (it reaches the cliff via index growth at 98% utilization; the entry-size variant reaches it at index = RAY). [8](#0-7)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
pub fn scaled_to_original(env: &Env, scaled: Ray, index: Ray) -> Ray {
    scaled.mul(env, index)
}

/// Converts an asset-unit `cap` to a scaled `Ray` value, rounding down.
///
/// The division saturates at `i128::MAX` instead of panicking, so the cap check
/// fails open rather than trapping an entry path. The asset-to-RAY
/// rescale still panics on overflow; listings validate caps with
/// [`crate::validation::require_cap_within_asset_domain`]. Position accounting
/// uses [`calculate_scaled_supply`] and [`calculate_scaled_borrow`], which panic
/// on overflow.
pub fn calculate_scaled_cap(env: &Env, cap: i128, decimals: u32, index: Ray) -> Ray {
    Ray::from(fp_core::mul_div_floor_saturating(
        env,
        Ray::from_asset(env, cap, decimals).raw(),
        RAY,
        index.raw(),
    ))
}
```
