### Title
Cross-tenant webhook shop-domain spoofing — the `shop` field trusted by handlers is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler unverified. The identity binding the app relies on — "the HMAC-authenticated request equals the request for shop S" — never actually checks that `shop` is bound to the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string (i.e., the body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` treats HMAC success as full authentication of the request and then builds a `WebhookMetadata` object using `request.shop`, which is read directly from the `shop-domain` header with no relationship to the HMAC-signed bytes: [3](#0-2) [4](#0-3) 

The equality the app believes holds is:
`HMAC_valid(body, secret) == true` implies `shop-domain header == the shop that generated this signed body`.

That equality does not hold, because `shop-domain` is never an input to the HMAC computation. Any bytes with a valid HMAC for the app's own shared secret can be replayed with an arbitrary `shop-domain` header and will still pass `Utils::HmacValidator.validate`.

An unprivileged attacker who has installed the app on their own store (a normal, non-privileged tenant) receives genuine, validly-signed webhooks from Shopify for their own shop. They can capture the raw body and its valid `x-shopify-hmac-sha256` value, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop. Because `Registry.process` only checks the HMAC-over-body, the forged request passes validation, and the handler receives a `WebhookMetadata` claiming to be from the victim shop, carrying attacker-controlled body content: [5](#0-4) 

The gem's own documentation instructs apps to use `data.shop` directly as the tenant identifier for storage/lookups (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this is the gem's documented, expected usage pattern — not a case of the host application ignoring the API: [6](#0-5) 

### Impact Explanation
This breaks the tenant isolation the webhook subsystem is supposed to provide. An attacker who is a legitimate (but unprivileged) merchant of the app can forge webhook deliveries that any downstream handler will attribute to a different, victim shop, while fully controlling the JSON body content (subject only to producing a body that yields the same HMAC they already captured — but since they control their own store's data, they can produce many bodies naturally, and any one they get signed for their shop can be replayed as "belonging" to another shop). This is a cross-tenant confusion vector: it can be used to inject attacker-controlled data into another merchant's data path (e.g., a handler that writes order/product data keyed by `data.shop` into a merchant's tenant record), corrupting or polluting a victim tenant's state with data the attacker chose, or misleading business logic that trusts `data.shop` for authorization/attribution decisions. This matches the "cross-tenant access" class of Critical impact defined in scope, since the shop identity — the sole tenant/authentication boundary in the webhook flow — can be spoofed by a party that has valid signing capability only for their own tenant.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs multiple merchants (the normal SaaS model) and relies on the documented `data.shop` field to key per-tenant work, as instructed by this gem's own docs. Exploitation requires no special access: any installed merchant is, by definition, capable of receiving genuinely-signed webhooks for their own store and can freely modify HTTP headers on a replayed request to the app's public webhook callback URL. No secret, admin access, or privileged token is required — only participation as an ordinary tenant of the app plus control over which headers accompany a resent HTTP POST.

### Recommendation
Bind the tenant identity to the signed payload instead of trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC signable string, matching how the value is actually used downstream, so any header tampering invalidates the signature.
- Where possible, cross-check the `shop-domain` header against a known/expected shop context (e.g., the session or webhook registration the request maps to) before invoking the handler.
- Update `docs/usage/webhooks.md` to warn that `data.shop` must not be trusted for authorization decisions unless the HMAC computation is extended to cover it.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and registers for `orders/create` webhooks.
2. Shopify delivers a genuine webhook to the app for that shop:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body B>`
   - Body: `B`
3. Attacker captures this exact `(B, valid_hmac)` pair (they control their own store, so they can trigger a webhook with any body content they want, e.g., via a fake order).
4. Attacker resends a POST to the app's webhook callback URL with the same body `B` and same `hmac` header, but with `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds because the body and HMAC are unchanged: [7](#0-6) 
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-chosen JSON>, ...)`, and any logic keyed on `data.shop` now operates on the victim tenant using attacker-supplied data.
