### Title
Webhook `shop` (and `topic`/`webhook_id`) header trusted without being covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC signature only ever covers the raw request body (`Request#to_signable_string` returns `@raw_body`). The `shop-domain`, `topic`, and `webhook-id` headers—which are trusted verbatim and handed to the app's handler as the identity of the tenant the event belongs to—are never included in the signed material. Since the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any merchant that installs the app can capture a legitimately-signed `(body, hmac)` pair from their own store's webhook traffic and replay it to the app's webhook endpoint with a forged `shop-domain` header naming a victim shop. `Registry.process` will accept the HMAC as valid and invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim, even though the body actually originated from the attacker's own shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the raw body is used to compute/verify the HMAC. The `shop`, `topic`, and `webhook_id` accessors read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata passed to the app handler: [3](#0-2) 

`HmacValidator.validate` computes the signature using `Context.api_secret_key`, which is one shared secret for the whole app across every shop that installs it: [4](#0-3) 

The identity binding that should hold is: `shop header used by handler == shop that the HMAC actually authenticates`. Because the signable string never includes `shop`, this equality does not hold — the HMAC only proves "some shop that has this app installed produced this body," not "this specific shop produced this body." The gem's own documentation promises stronger semantics than it delivers: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" (`docs/usage/webhooks.md` lines 125). In reality it verifies only that the body was signed by the app's global secret, not that the accompanying `shop-domain` header is bound to that signature.

An unprivileged attacker's path (no `api_secret_key`, no access token needed):
1. Attacker installs the target app on their own store (any unprivileged internet user can do this — it's a standard app install, not a privileged action, and grants no access to the victim's data).
2. Attacker triggers a webhook event on their own store (e.g., updates a product), causing Shopify to send a legitimately HMAC-signed webhook request to the app's callback URL, with body `B` and header `hmac = HMAC(secret, B)`.
3. Attacker captures this `(B, hmac)` pair (they control the destination endpoint indirectly via replay, or can simply reuse a value they can observe/log if the callback endpoint is reachable, e.g. via request logging, a public tunnel, or a webhook-forwarding proxy they control).
4. Attacker replays the exact same `(B, hmac)` to the app's webhook endpoint, but swaps the `shopify-shop-domain` header to `victim-shop.myshopify.com`.
5. `HmacValidator.validate` recomputes `HMAC(secret, B)` and it still matches, because `shop-domain` was never part of the signed material.
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`.

The application, trusting the library's guarantee that the request "did indeed come from Shopify" for the given shop, will process attacker-controlled body content under the victim's tenant context (e.g., writing attacker-controlled order/product data into the victim's records, or triggering shop-scoped side effects keyed off `data.shop`).

### Impact Explanation
This is a cross-tenant boundary violation: data or events belonging to one shop (the attacker's) can be injected into another shop's tenant context (the victim's) purely by manipulating an unauthenticated header, without needing the app's `client_secret`/`api_secret_key`, an access token, or any privileged account — only an ordinary app install on the attacker's own shop. Applications built on this gem key their side effects (`shop_domain:`, record lookups, session retrieval, background job routing) off `data.shop`, per the gem's own documented usage example: [5](#0-4) 

Because `data.shop` is not bound to the HMAC, this satisfies the Critical impact category of cross-tenant access.

### Likelihood Explanation
Likelihood is high for any app that exposes its webhook callback endpoint at a reachable HTTP URL (which is required for `:http` delivery per the gem's own documented flow). The attacker needs no special privileges beyond installing the app on a shop they control — a capability inherent to any unprivileged internet user for any public app — and the ability to observe/replay one webhook body+HMAC pair they legitimately received, which is trivial (e.g., via their own server logs, a debugging proxy, or a webhook capture tool).

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified material, e.g. by:
- Including the `shop-domain` header value in the string that is HMAC-verified (this deviates from Shopify's wire format, so alternatively:
- After the body-HMAC check passes, cross-verify the claimed `shop-domain` against an out-of-band trusted binding — e.g., require the caller to also supply/verify the webhook's `X-Shopify-Webhook-Id` against a shop-scoped record created at registration time, or require apps to look up and confirm that the `shop-domain` in the header actually has an active session/installation matching the topic before trusting it, and document this requirement clearly since the library cannot enforce it purely from the HMAC.
- At minimum, update `docs/usage/webhooks.md` to make explicit that `Registry.process` only authenticates the body, not the `shop`, `topic`, or `webhook_id` headers, so implementers are not misled by the current "verify the request did indeed come from Shopify" wording into trusting `data.shop` for tenant-sensitive logic.

### Proof of Concept
1. Configure `ShopifyAPI::Context` with a single `api_secret_key` shared by the app across all shops (as is standard).
2. As shop A (attacker-controlled), trigger any registered webhook topic; capture the resulting `raw_body` and `X-Shopify-Hmac-Sha256` header sent to your callback endpoint.
3. Construct a new HTTP request to the same callback endpoint using the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim shop, not installed/controlled by attacker) and any `X-Shopify-Topic`/`X-Shopify-Webhook-Id` desired.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request as valid, per: [6](#0-5) 
and invokes the handler with `WebhookMetadata.shop == "shop-b.myshopify.com"`, even though the payload and signature actually originated from shop A.
