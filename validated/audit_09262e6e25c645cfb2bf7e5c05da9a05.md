This confirms the vulnerability: `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` only verifies the raw request body against the HMAC digest, while the `shop` (and `topic`/`webhook_id`) fields are read directly from unauthenticated HTTP headers and forwarded to the app's handler untouched.

### Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC validated by `Utils::HmacValidator.validate` never covers the `shopify-shop-domain` header. `Registry.process` nonetheless trusts `request.shop` (parsed straight from that header) and passes it into `WebhookMetadata`, which app handlers use to attribute the webhook body to a specific merchant/tenant.

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_the_app_treats_as_the_authenticated_webhook_source (body + shop)`. Instead, the equality only holds for the body:
- `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns `@raw_body` alone. [1](#0-0) 
- `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload. [2](#0-1) 
- `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) compares the received HMAC only against `to_signable_string` (the body), never the shop header. [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — which is what app-level handlers use to route/attribute data per-tenant. [4](#0-3) 
- The documented handler contract explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" and to use it for tenant routing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that this field is treated as an authenticated identity binding by design. [5](#0-4) 

Because a single app installation uses one shared `api_secret_key` across every merchant/tenant that installs it, a webhook body that is legitimately, validly signed for Shop A (e.g. captured by a merchant who is a customer of the SaaS app, or via any endpoint that echoes webhook traffic) can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header changed to Shop B. `HmacValidator.validate` still succeeds because it only checks the untouched raw body, and `Registry.process` reports the event as belonging to Shop B via `WebhookMetadata#shop`.

### Impact Explanation
This breaks the shop-to-webhook identity binding across tenants: an app processing the webhook (e.g., persisting order/customer data keyed by `data.shop`, updating billing state, or triggering the mandatory GDPR topics `shop/redact`, `customers/redact`, `customers/data_request`) can be tricked into attributing one merchant's authentic webhook payload to a different merchant's tenant record. This is a cross-tenant data confusion/injection vector that matches the "cross-tenant access" impact category, since the app relies on this library's stated contract (`data.shop`) as the authenticated tenant identifier.

### Likelihood Explanation
Exploitation requires the attacker to obtain a body+HMAC pair that was validly delivered for their own shop (which any merchant installing the app can trivially capture, since it is delivered to an HTTP endpoint they control or observe) and then re-POST it with an altered `shop-domain` header. No access to the `api_secret_key` or `client_secret` is required — only observation of one legitimate webhook delivered to any tenant. This makes the likelihood moderate-to-high for any host application that trusts `WebhookMetadata#shop` as documented.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-signed payload verification, or at minimum cross-check `request.shop` against the shop associated with the webhook subscription/session before invoking the handler. Concretely, `Request#to_signable_string` should incorporate the shop header (or the registry should independently verify the shop is one that has this specific webhook_id registered) rather than trusting the header value verbatim.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's registered endpoint; attacker captures the raw POST body and the `x-shopify-hmac-sha256` header (both are visible to them since they control network trace tools / a proxy in front of their own store's webhook receiver, or simply observe it if the endpoint echoes/logs it).
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the raw body (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` constructs `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the app's handler processes attacker-supplied order data as if it belonged to the victim shop.
