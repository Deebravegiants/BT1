## Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhook bodies - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are never part of the signed payload, yet `Webhooks::Registry.process` treats `request.shop` as trustworthy and hands it to app-provided handlers via `WebhookMetadata`, which apps commonly use as the tenant/session key to decide which merchant a webhook belongs to.

### Finding Description
The identity binding that should hold is: `shop value trusted by the handler == shop value cryptographically authenticated by Shopify`. This gem breaks that equality.

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read straight from an attacker-controllable header, independent of the signature: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook-id`: [3](#0-2) 
- `Registry.process` accepts the request once the body HMAC checks out, then forwards the unauthenticated `shop` header value straight into `WebhookMetadata`, which is the object handlers use to key off the tenant: [4](#0-3) [5](#0-4) 

Because the signature only binds the body, any two requests with the same raw body and the same (valid) HMAC are indistinguishable to `HmacValidator`, regardless of which `shop-domain` header accompanies them.

### Impact Explanation
A merchant who installs the app on their own store (an "unprivileged internet user" with respect to any *other* tenant) legitimately receives real, correctly-HMAC-signed webhook deliveries for their own shop from Shopify. Because the signature never binds the `shop-domain` header, that attacker can capture one such `(raw_body, hmac)` pair and replay it to the app's single shared webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because the body/HMAC pair is untouched, and `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-chosen JSON>, ...)` to the handler. Any handler that uses `data.shop` as the tenant/session key (the normal, gem-recommended usage pattern) will process attacker-controlled webhook content under the victim's tenant identity — a cross-tenant identity confusion rooted entirely in this gem's verification primitive, not in host-application misuse of a documented caveat (no such caveat exists anywhere in this gem's public API surface, e.g. `WebhookMetadata`/`WebhookHandler`).

### Likelihood Explanation
Any merchant that can install the app (a normal, unprivileged path — no `api_secret_key`, access token, or other privileged material required) can obtain at least one genuine `(body, hmac)` pair for their own shop and replay it against the same publicly reachable webhook endpoint with a forged `shop-domain` header. No brute force or secret knowledge is needed; only header manipulation on an otherwise-valid, previously-observed request.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is verified, e.g. include `shop-domain`, `topic`, and `webhook-id` header values in `Request#to_signable_string` (or otherwise validate them independently, such as requiring the `shop` to match a known/installed shop before trusting it), so `Utils::HmacValidator.validate` cannot be satisfied by a replayed body carrying a different shop-domain header. At minimum, document prominently in `WebhookMetadata`/`WebhookHandler` that `shop` is unauthenticated by the HMAC and must be independently verified by the caller before being used as a tenant/session key.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any subscribed event (e.g. `orders/create`) so Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under `Context.api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay the exact bytes of `B` and `H` to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` dispatches to the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own order JSON>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the payload actually originated from the attacker's own shop.
