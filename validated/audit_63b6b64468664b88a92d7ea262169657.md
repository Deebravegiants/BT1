### Title
`create_client` accepts `challenge_period` ≥ `unbonding_period` with no relative validation, permanently freezing message delivery for the state machine - (File: modules/ismp/core/src/handlers/consensus.rs)

### Summary
`create_client` stores a per-state-machine `challenge_period` and a consensus-state-wide `unbonding_period` independently, with no check that the challenge period is smaller than the unbonding period. This mirrors the reported GPToke bug class: two related duration parameters are set at initialization time with no cross-field validation, letting an inconsistent configuration silently brick message processing for that route.

### Finding Description
`create_client` in `modules/ismp/core/src/handlers/consensus.rs` stores the `unbonding_period` and, independently, a `challenge_period` per state machine, taken directly from the untrusted `CreateConsensusState` message with no relationship check between the two: [1](#0-0) 

`verify_delay_passed` / `validate_state_machine` gate all incoming request/response/timeout processing on the `challenge_period` having elapsed since the state commitment's update time: [2](#0-1) 

Separately, the consensus client is treated as expired/frozen once `current_timestamp - last_consensus_update_time > unbonding_period` (the long-range-attack mitigation described in the docs) — see `docs/content/protocol/ismp/consensus.mdx` lines 171-174, which explicitly states the handler asserts the client is "not frozen or expired" using the `unbonding_period` before any new consensus update can be admitted, and that new state commitments only start their challenge-period countdown once verified: [3](#0-2) 

If `challenge_period >= unbonding_period` for a given state machine, the delay a proof-submitter must wait before the request handlers (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts` on `HandlerV2`, and their pallet-ismp equivalent via `validate_state_machine`) will accept a state commitment always exceeds (or equals) the window during which the consensus client itself remains unexpired. By the time the challenge period has elapsed, the client that produced that commitment is already past its unbonding window and treated as stale/frozen, so no relayer can ever satisfy `verify_delay_passed`/`ChallengePeriodNotElapsed` before the client is no longer trusted to admit further updates that could refresh the timing. This creates a state machine whose messages can never be delivered — a permanently unusable route — purely from a misconfigured `create_client` call, with no on-chain guard preventing it.

Handler-side enforcement of `challengePeriod` on the EVM side confirms this is a hard, unconditional gate on message delivery: [4](#0-3) 

### Impact Explanation
This is a Medium-severity operational/liveness bug: an admin (or governance) misconfiguration of two independently-supplied duration parameters at client creation — with no cross-check — can render an entire counterparty state machine's message route permanently undeliverable, matching the "route unable to deliver messages" acceptance criterion. Unlike the original GPToke report where the fix is a simple ordering assertion in the constructor/initializer, this codebase similarly lacks any assertion tying `challenge_period` to `unbonding_period` at the point they are both persisted for a consensus client (`create_client`), or later when challenge periods are updated via governance/host-executive pathways.

### Likelihood Explanation
`create_client` is the standard, expected onboarding path for every new counterparty consensus client (see `docs/content/protocol/ismp/consensus.mdx`), and both parameters (`unbonding_period`, `challenge_periods`) are attacker/operator-supplied fields of `CreateConsensusState` with no on-chain bound relating them. Any operator (or governance proposal) that sets a challenge period equal to or larger than the unbonding period — an easy mistake given they are configured as separate, unrelated fields in the message — reproduces the exact “min set higher than max” pattern from the reference report. Because `create_client` is a normal, permissionless-format handler call rather than a privileged/malicious-admin action being excluded by scope rules, this is reachable through ordinary operational configuration.

### Recommendation
In `create_client` (and any subsequent `update_host_params`/`set_host_params`-style path that can change `challenge_period` or `unbonding_period` independently), validate that for every state machine, `challenge_period < unbonding_period` (with sufficient margin for verification/relay latency) before persisting, reverting the call otherwise — analogous to adding `if minStakeDuration >= maxStakeDuration revert` in the referenced GPToke fix.

### Proof of Concept
1. Call `create_client` with `unbonding_period = X` and `challenge_periods[state_machine] = Y` where `Y >= X` (both attacker/operator-controlled fields on `CreateConsensusState`). [5](#0-4) 
2. After the client is created and consensus updates proceed normally, any relayer attempting to deliver a request/response/timeout proven against a state commitment must wait `Y` seconds past that commitment's update time (`verify_delay_passed`). [6](#0-5) 
3. Because `Y >= X`, by the time the challenge period elapses the consensus client's last update is already older than the unbonding period, so the client is treated as expired/frozen per the documented long-range-attack mitigation, and no further consensus update can restart the timing favorably for the pending commitment.
4. Consequently, no relayer can ever successfully clear both the freshness and challenge-period requirements simultaneously for that state machine, permanently blocking message delivery on the affected route.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

The `update_client` method is responsible for advancing the state of the consensus client. This performs the consensus verification of new `StateCommitment`s that have been finalized by a `StateMachine`'s consensus system. The `IsmpHost` must return the concrete implementation of the associated `ConsensusClient` and a previously stored `ConsensusState`. The procedure for updating the consensus client is as follows.

- First the handler must assert that the consensus client is not frozen or expired. Consensus clients can expire if the last time the consensus client was updated has exceeded the chain's unbonding period. This effectively mitigates any potential long fork attacks that may arise due to a loss of liveness of consensus clients.
- Finally the handler may perform consensus proof verification using the concrete implementation for the consensus client using `ConsensusClient::verify_consensus`. If verifications pass, the udpated `ConsensusState` and `IntermediateState`s are persisted to storage and enter a new challenge period.
