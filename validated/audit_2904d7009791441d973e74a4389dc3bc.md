Based on my investigation, I found a genuine custody-relevant analog in the `multisig_account.move` timelock feature, which is structurally similar to the reported bug: a security-gate (`dropBoostQueue` timestamp check in the external report vs. `MultisigAccountTimeLock` timestamp check here) that relies on a timestamp set by an *unrelated* prior action, allowing the gate to be trivially/incorrectly satisfied.

### Title
Multisig timelock delay can be silently bypassed for transactions created before the timelock was enabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
The multisig account's timelock protection (`MultisigAccountTimeLock`) is meant to force a minimum delay between when a transaction accrues enough approvals and when it can actually be executed, giving other owners time to detect and reject fraudulent transactions targeting multisig-controlled APT/assets. However, the elapsed-time check is computed from `MultisigTransaction.creation_time_secs`, which is unconditionally stamped at `create_transaction`/`create_transaction_with_hash` time regardless of whether a timelock configuration exists yet [1](#0-0) .

### Finding Description
`can_execute_with_timelock` computes `elapsed = now_seconds() - pending_transaction.creation_time_secs` and permits execution once `elapsed >= timelock` (or the approval count meets `override_threshold`) [2](#0-1) . This is analogous to the `dropBoost`/`dropBoostQueue` pattern in the external report: a gating check is based on a timestamp field that is set by a different, unguarded code path.

Concretely:
1. A multisig account with no `MultisigAccountTimeLock` resource yet allows an owner to `create_transaction`, which stamps `creation_time_secs = now_seconds()` at creation time [1](#0-0) .
2. If owners later configure a timelock (to add protection, e.g., after suspecting a compromised co-signer, or simply adopting the new v2 enhancement feature) the already-pending transaction's `creation_time_secs` remains the original, older timestamp — it is never reset or excluded.
3. When `validate_multisig_transaction` runs `can_execute_with_timelock` for that pending transaction, `elapsed` is computed from the stale `creation_time_secs`, which can already exceed the newly-configured `timelock_period`, causing the timelock gate to pass immediately [3](#0-2) .
4. The result: a malicious/compromised-owner-created transaction (e.g., transferring the multisig resource account's `AptosCoin`/fungible-asset balance or rotating its auth key) that accumulates quorum after the timelock is turned on can be executed with **zero actual real-time delay**, defeating the entire purpose of the timelock as a custody safeguard.

I was not able to fully inspect the function that creates/enables `MultisigAccountTimeLock` within my tool budget, so I cannot confirm whether it includes a safeguard that blocks enabling a timelock while transactions are pending, or resets `creation_time_secs` for pending transactions. This is a material gap in verification.

### Impact Explanation
If confirmed, this breaks the custody-grade invariant that a security delay applied to multisig-controlled funds (APT, FA, or upgrade authority) must actually elapse before execution. It would allow immediate execution of a transaction that owners intended to be time-delayed, potentially enabling theft or unauthorized reassignment of multisig-held value with no real protective window — a High impact given multisig accounts commonly custody significant value and rely on the timelock explicitly as a fraud-response mechanism.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a transaction already pending before timelock is enabled/updated, and (b) quorum being reached after enabling — a realistic operational sequence (e.g., owners enable timelock reactively after suspecting compromise, not realizing existing pending proposals are unaffected). Without having verified the enable/setup function, I cannot rule out an existing mitigation, so this likelihood/confidence should be treated as provisional.

### Recommendation
When enabling or updating `MultisigAccountTimeLock` (`timelock_period`/`override_threshold`), either (a) reject the operation if there are pending transactions, or (b) explicitly reset/require re-approval (and refresh `creation_time_secs`, or track a separate `timelock_start_secs` per transaction set at the time the timelock policy applies) so that the delay is measured from when the policy actually took effect, not from the original proposal time.

### Proof of Concept
1. Create a multisig account with no timelock configured; `num_signatures_required = 2`.
2. Owner A calls `create_transaction` with a malicious payload (e.g., transferring the resource account's coin balance to an external address). `creation_time_secs = T0`.
3. Some time later (`T0 + timelock_period` or more), owners enable a timelock policy (`timelock_period`, e.g. 1 hour) intending it to apply going forward.
4. Owner B (compromised or colluding) calls `approve_transaction`, reaching quorum.
5. Any owner calls execute; `can_execute_with_timelock` computes `elapsed = now() - T0 >= timelock_period` (already true, since `T0` predates the timelock enablement) and returns `true`, allowing immediate execution with no observed delay after the timelock was supposedly turned on [2](#0-1) .

**Caveat:** This finding is based on the visible `can_execute_with_timelock`/`create_transaction` logic. I could not, within the available iterations, locate and review the exact function that creates/enables `MultisigAccountTimeLock`, so I cannot fully rule out an existing guard against this scenario. A Devin session with full repo access should verify that function before treating this as conclusively exploitable.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
