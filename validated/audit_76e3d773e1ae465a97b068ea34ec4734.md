### Title
Receipts can grow past `max_receipt_size` after size validation, producing oversized receipts that are never rejected - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The External Report describes a Solidity contract that fails to bound the size of data returned from an external call, allowing an attacker to make a low-level call return an unbounded amount of data, exhausting gas mid-execution so that state (`forwarded[id]`) is never updated and the pending item is retried forever. The closest concrete analog in nearcore is a self-acknowledged bug (tracked as [nearcore#12606](https://github.com/near/nearcore/issues/12606)) where a receipt passes the `max_receipt_size` check at creation time, but is subsequently mutated (e.g. `output_data_receivers` appended, or a large `value_return`/`promise_return` result attached) so that the *actual* receipt exceeds `max_receipt_size` — yet this oversized receipt is never rejected, instead only worked around downstream.

### Finding Description
`LimitConfig::max_receipt_size` (4 MiB) is meant to be a hard limit: "All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected" per `docs/misc/state_witness_size_limits.md` [1](#0-0) . However, the check is performed against a receipt at the point of creation, before it is later expanded with `output_data_receivers` or a `value_return`/`promise_return` payload. Two host-level test cases explicitly document that this later mutation pushes the receipt over the limit without being rejected:

- `test_max_receipt_size_promise_return`: "A function call will generate a new receipt. Size of this receipt will be equal to `max_receipt_size`... but then `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`. The receipt should be rejected, but currently isn't because of a bug" [2](#0-1) .
- `test_max_receipt_size_value_return`: "Return a value that is as large as max_receipt_size. The value will be wrapped in a data receipt and the data receipt will be bigger than max_receipt_size. The receipt should be rejected, but currently isn't because of a bug" [3](#0-2) .

The `value_return` host function only checks the raw payload length against `max_length_returned_data` (4 MiB) — it does not consider the framing/receipt overhead that will be added when the value becomes a `DataReceipt` [4](#0-3) . The runtime is aware that oversized receipts can be produced and only mitigates the *forwarding* consequence, not the root validation gap: `ReceiptSinkV2::try_forward` explicitly clamps any receipt whose size exceeds `max_receipt_size` down to `max_receipt_size` "to avoid receipts getting stuck", citing issue #12606 directly in the comment [5](#0-4) . The test suite confirms these oversized receipts genuinely reach the chain by asserting an oversized incoming receipt is found in committed blocks (`assert_oversized_receipt_occurred`) [6](#0-5) .

This is structurally analogous to the Solidity bug: a size/resource bound that is *supposed* to be a hard invariant is not actually enforced at the point where the dangerous growth occurs (post-validation mutation vs. arbitrary-size low-level call return), and the system instead relies on a downstream patch (gas metering by return-data size in Solidity; clamping in `try_forward` in nearcore) rather than rejecting the operation outright.

### Impact Explanation
Oversized receipts violate the documented invariant that `ChunkStateWitness` stays bounded (~21 MiB total, with `max_receipt_size` as one of the load-bearing hard limits) [7](#0-6) . Receipts exceeding `max_receipt_size` bypass the intended hard limit, which can inflate the actual size of chunk witnesses beyond the values chunk validators assume when validating them, and can also cause a receipt to be permanently unable to be forwarded across shards in some configurations (only avoided today by clamping the *comparison*, not the actual bytes transmitted). This falls into the "unbounded resource use" category since a single contract call can produce data that violates a supposedly hard 4 MiB bound, which downstream code paths (state witness construction, receipt buffering/bandwidth accounting) were not designed to handle safely — the fix in `try_forward` is explicitly labeled as a workaround for a still-open bug rather than a real fix.

### Likelihood Explanation
This is trivially triggerable by any unprivileged account issuing a function call: the existing regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) reproduce it deterministically using ordinary contract calls (`promise_return`, `value_return`) with no special permissions, and are already present in the codebase specifically to characterize this known, currently-open issue.

### Recommendation
Enforce `max_receipt_size` validation *after* all receipt-mutating steps are finalized — i.e., after `output_data_receivers` are populated and after `value_return`/`promise_return` payloads are attached — rather than only at initial receipt construction, and reject the action (fail the receipt) if the final serialized size exceeds `max_receipt_size`. Remove or tighten the `try_forward` clamp workaround once genuine oversized receipts can no longer be created, since that clamp currently only avoids receipts getting "stuck" rather than preventing state-witness/protocol invariant violations.

### Proof of Concept
Use the existing reproduction already checked into the repository:
- `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` [8](#0-7)  deploy the standard test contract, call `max_receipt_size_promise_return_method1` / `max_receipt_size_value_return_method` with payloads sized to hit exactly `max_receipt_size`, and then call `assert_oversized_receipt_occurred`, which walks the chain and asserts a receipt above `max_receipt_size` was actually included on-chain [6](#0-5) .

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
