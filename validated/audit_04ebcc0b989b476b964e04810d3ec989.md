### Title
Unchecked fixed-size buffer copy from attacker-controlled ISMP message `from` field causes a panic in the token bridge - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`CVE-2019-7629` is a stack buffer overflow where a fixed-size buffer is written from attacker-controlled, variable-length network data without validating the length first. The Hyperbridge analog is in the `hyper-fungible-token` pallet's calldata-execution path, where a `[u8; 32]` buffer is filled via `copy_from_slice` from an ISMP message's `from` field without first checking that the field is exactly 32 bytes.

### Finding Description
When an incoming ISMP `PostRequest` carries optional calldata with no attached signature, the pallet derives the dispatch origin directly from `message.from`. For non-EVM sources it does: [1](#0-0) 

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]));
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```

`message.from` is an ISMP `PostRequest` field fully controlled by the source-chain application/message that a relayer delivers cross-chain — it is not bound in size to 32 bytes anywhere before this call. `copy_from_slice` requires the source and destination slices to have exactly equal lengths and panics otherwise (`source slice length (N) does not match destination slice length (32)`). Unlike the EVM branch, which defensively slices the tail 20 bytes (`from_bytes.len() - 20..`, itself panicking on underflow if `from_bytes` is shorter than 20 bytes), the non-EVM branch performs no length check at all before the fixed-size copy.

This mirrors the root cause of CVE-2019-7629: a message-derived byte sequence of attacker-chosen length is written into a fixed-size buffer with no length validation, the only difference being that Rust's memory safety turns the out-of-bounds write into a deterministic panic rather than memory corruption.

### Impact Explanation
A panic inside pallet dispatch logic reached from an incoming cross-chain message is a route-availability/dispatch-failure issue: any source chain (or a relayer forwarding attacker-crafted `from` bytes of a length other than 32 or 20) can construct a `PostRequest` with calldata and a `from` field whose length is neither 32 nor 20 bytes, causing this code path to panic when the message is executed. Because this runs inside the runtime's message-handling/dispatch flow, it can abort processing of that message and potentially the surrounding extrinsic/block execution context, which is a "route unable to deliver messages" outcome for the hyper-fungible-token bridge — a Medium/High-severity availability issue for a token bridge integration, without requiring any privileged action.

### Likelihood Explanation
The trigger only requires a message reaching the pallet's calldata path with a non-EVM `source` and a `from` field length not equal to 32 bytes, and no `signature` field set (or paths where this branch is taken). Since `from` originates from ISMP request data that a source-chain module or a malicious relayer can shape, likelihood is high once a message reaches this code path, though it depends on whether this pallet is deployed/enabled for a given deployment and reachable without additional origin/module-address gating upstream.

### Recommendation
Validate `from_bytes.len() == 32` (mirroring the check already implicitly required by `copy_from_slice`) before the fixed-size copy, returning a decode/format error (e.g., `HftError::InvalidFromLength`) instead of panicking; likewise harden the EVM branch to check `from_bytes.len() >= 20` before slicing the tail, so malformed `from` fields are rejected gracefully rather than causing a runtime panic.

### Proof of Concept
1. Construct an ISMP `PostRequest` destined for the `hyper-fungible-token` pallet with non-empty `message.data` (so the calldata branch executes), `source` set to a non-EVM `StateMachine`, and `from` set to a byte vector of length ≠ 32 (e.g., 31 or 33 bytes) and no `signature` in the decoded `SubstrateCalldata`.
2. Deliver/dispatch this message through the normal ISMP message-handling flow so `module.rs`'s calldata-execution branch runs.
3. `account.copy_from_slice(from_bytes)` panics because `from_bytes.len() != 32`, aborting the dispatch instead of returning a handled error. [2](#0-1) 

Note: I was not able to fully trace every caller/entry point that constructs the `Message` reaching this branch (e.g., whether an upstream gate already restricts `from` to exactly 20/32 bytes for this pallet's registered module id), nor find explicit regression tests analogous to the ones seen elsewhere in the codebase (e.g., in `bls-utils` or `pharos` verifier) guarding this specific `copy_from_slice`. This should be verified against the pallet's ISMP module registration/routing before treating the exploitability as fully confirmed.
