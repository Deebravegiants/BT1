### Title
Front-running of unpermissioned `#[init] new()` initializers on manually-deployed lockup/staking-pool contracts - (File: `lockup/src/lib.rs`, `staking-pool/src/lib.rs`)

### Summary
The external report's root cause — an unpermissioned `initialize()`/proxy-init function whose execution is not atomic with contract deployment, allowing any unprivileged party to front-run it and seize ownership — has a direct analog in this codebase. `LockupContract::new()` and `StakingContract::new()` are `#[init]` methods guarded only by `assert!(!env::state_exists())`, with no caller-permission check (no `onlyOwner`/deployer binding). When these contracts are deployed and initialized through `lockup-factory`/`staking-pool-factory`, deployment and init are bundled into a single atomic `Promise` (create_account → transfer → deploy_contract → function_call("new", ...)) executed as one receipt, which is safe. However, the project's own documented manual deployment workflow performs account creation, contract deploy, and `new` initialization as three separate transactions, reproducing exactly the "deploy-then-initialize-in-a-later-transaction" gap described in the external report.

### Finding Description
`StakingContract::new()` [1](#0-0)  and `LockupContract::new()` [2](#0-1)  only guard against re-initialization (`assert!(!env::state_exists(), ...)`); they never verify that the caller is the intended deployer/owner. `WhitelistContract::new()` has the same shape [3](#0-2) .

When these contracts are created via `StakingPoolFactory::create_staking_pool` or `LockupFactory::create`, the create-account, transfer, deploy-contract, and `function_call("new", ...)` actions are chained onto a single `Promise` and execute as one atomic receipt [4](#0-3) [5](#0-4) , so there is no window between "contract code deployed" and "contract initialized" that an outside party can exploit — this path is not vulnerable.

The vulnerability is that this atomicity is not enforced at the contract level: it depends entirely on the deployment tooling used. The project's own recommended manual deployment procedure for a standalone staking pool (i.e. not created via the factory) issues account creation, `near deploy`, and `near call ... new` as three independent CLI transactions. Once the second transaction (deploy) lands on-chain, the contract exists with code but no state, and `new()` becomes callable by anyone until the legitimate `new` transaction is mined. Any unprivileged observer of the mempool/recent blocks can submit their own `new(owner_id=attacker, ...)` call first: `assert!(!env::state_exists())` will still pass (state does not yet exist), the call succeeds, and the attacker becomes `owner_id`, gaining full administrative control (staking key rotation, fee changes, ability to drain deposits via `owner`-gated withdraw/vote/pause methods) of the pool before the legitimate owner's initialization lands.

### Impact Explanation
This matches the High-severity "Unauthorized execution / confirmation bypass / state-transition bypass" and Critical "unauthorized control over pooled/locked NEAR" categories: an attacker who wins the initialization race becomes the sole `owner_id` of the staking pool (or lockup contract), controlling staking keys, reward fee, pause/resume, and later owner-only withdrawal/vote paths, effectively hijacking a contract that legitimate depositors/validators believe is theirs. For a `LockupContract`, `owner_account_id` set this way controls all lockup owner methods including staking pool selection and (if vesting is absent) transfer of the full locked balance once transfers are enabled.

### Likelihood Explanation
Likelihood is limited to deployments that do not go through `staking-pool-factory` / `lockup-factory` (i.e., standalone validator/lockup deployments using the documented manual `create_account` → `deploy` → `call new` flow). Contracts created via the factories are provably atomic and not affected. Because standalone staking-pool deployment (for validators) is the documented, supported workflow in this repository, and NEAR mempool transactions are publicly visible before inclusion, an attentive attacker monitoring `deployContract` transactions to freshly created accounts can realistically race the subsequent `new` call.

### Recommendation
- Bind `new()` to a permissioned action, e.g. require `predecessor_account_id() == owner_id` (self-bootstrapping is not possible before init, but at minimum require `predecessor_account_id() == env::current_account_id()` is not applicable here) — more practically, disallow standalone deployment entirely and require deployment to occur only via `staking-pool-factory`/`lockup-factory`, where atomicity is enforced.
- If standalone deployment must remain supported, update deployment tooling/docs to bundle `createAccount` + `transfer` + `deployContract` + `functionCall("new", ...)` into a single `signAndSendTransaction` call (as already done in `deploy_whitelist.sh`/`deploy_staking_pool_factory.sh`) rather than issuing them as separate `near create_account` / `near deploy` / `near call new` commands.
- Add explicit post-deployment verification tooling that confirms `owner_id`/`foundation_account_id` match expectations immediately after initialization.

### Proof of Concept
1. Deployer runs `near create_account my_validator --masterAccount=owner` then `near deploy --accountId=my_validator --wasmFile=res/staking_pool.wasm` (per documented workflow) [6](#0-5) .
2. Attacker observes the `deployContract` transaction land on-chain (account now has code but `env::state_exists()` is false).
3. Before the deployer's `near call my_validator new ... --account_id owner` transaction confirms, attacker submits `near call my_validator new '{"owner_id":"attacker", ...}' --account_id attacker`.
4. `StakingContract::new()` executes because `assert!(!env::state_exists())` still holds [7](#0-6) ; `owner_id` is now `attacker`, and the legitimate deployer's later `new` call reverts with "Already initialized," permanently ceding control of the pool to the attacker.

    #[init]
    pub fn new(
        owner_id: AccountId,
        stake_public_key: Base58PublicKey,
        reward_fee_fraction: RewardFeeFraction,
    ) -> Self {
        assert!(!env::state_exists(), "Already initialized");
        reward_fee_fraction.assert_valid();
        assert!(
            env::is_valid_account_id(owner_id.as_bytes()),
            "The owner account ID is invalid"
        );
        let account_balance = env::account_balance();
        let total_staked_balance = account_balance - STAKE_SHARE_PRICE_GUARANTEE_FUND;
        assert_eq!(
            env::account_locked_balance(),
            0,
            "The staking pool shouldn't be staking at the initialization"
        );
        let mut this = Self {
            owner_id,
            stake_public_key: stake_public_key.into(),
            last_epoch_height: env::epoch_height(),
            last_total_balance: account_balance,
            total_staked_balance,
            total_stake_shares: NumStakeShares::from(total_staked_balance),
            reward_fee_fraction,
            accounts: UnorderedMap::new(b"u".to_vec()),
            paused: false,
        };
        // Staking with the current pool to make sure the staking key is valid.
        this.internal_restake();
        this
    }

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
