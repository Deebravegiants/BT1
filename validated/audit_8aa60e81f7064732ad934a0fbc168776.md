### Title
RAY-scaled debt overflow during interest accrual permanently freezes a market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
A sufficiently large borrowed position can make `borrowed * borrow_index` exceed `i128::MAX` before the configured borrow-index ceiling is reached. [1](#0-0) [2](#0-1) 

Every pool mutation first calls `interest::global_sync`, so once this condition exists, repayments, withdrawals, borrows, liquidations, and permissionless `update_indexes` all revert before reaching their operation-specific logic. [3](#0-2) [4](#0-3) 

### Finding Description
`Controller::update_indexes` is permissionless and accepts an attacker-selected `Vec<HubAssetKey>`. [5](#0-4) 

The pool loads each market and calls `interest::global_sync`. [6](#0-5) 

Each accrual chunk calls `accrue_step`, which calculates the current borrowed value through `scaled_to_original(borrowed, borrow_index)` before calculating or clamping the next index. [7](#0-6) 

`scaled_to_original` delegates to `Ray::mul`, and `Ray::mul` performs fixed-point `i128` multiplication that panics with `MathOverflow` when the represented value exceeds the RAY domain. [8](#0-7) [9](#0-8) 

The index clamp in `update_borrow_index` cannot prevent this condition because the pre-clamp value multiplication happens earlier in the same step. [10](#0-9) 

### Impact Explanation
This permanently freezes all funds and accounting operations for the affected `(hub_id, asset)` market. [3](#0-2) 

Repayment calls `ops::load_leg`, which syncs the market before resolving or burning debt, so borrowers cannot repay after the overflow threshold is crossed. [11](#0-10) 

Withdrawal likewise syncs before resolving shares or debiting cash, so suppliers cannot withdraw principal or yield. [12](#0-11) 

The in-repository regression case demonstrates `MathOverflow`, a borrow index still below `MAX_BORROW_INDEX_RAY`, and subsequent failure of both withdrawal and repayment. [13](#0-12) 

### Likelihood Explanation
The attack is conditional on a market admitting enough exposure for scaled debt multiplied by a reachable borrow index to exceed `i128::MAX`; configured caps can prevent it. [14](#0-13) 

However, the caps are validated only against the initial asset-to-RAY domain, while accrued values can exceed that domain before either index reaches its ceiling. [15](#0-14) [2](#0-1) 

A single funded address can open one account supplying the target asset and another collateralized account borrowing it, then any address can trigger the failing accrual through `update_indexes` once ledger time advances. [16](#0-15) [17](#0-16) 

### Recommendation
Do not multiply a scaled balance by an index unless the product is known to fit the RAY value domain.

At minimum, enforce a market-entry and accrual invariant such as `borrowed <= max_supported_value / borrow_index` and `supplied <= max_supported_value / supply_index`, accounting for the configured index ceilings.

Prefer calculating utilization and index transitions with a wider intermediate representation or checked division-based formulas so a temporarily large product cannot make the market unrecoverable.

Add a pre-commit regression test proving that the highest admitted scaled exposure remains accrutable through `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY`, or tighten cap validation to enforce that bound.

### Proof of Concept
The following reachable sequence matches the repository's regression scenario. [13](#0-12) 

```text
let big18 = HubAssetKey { hub_id, asset: BIG18_TOKEN };
let collateral = HubAssetKey { hub_id, asset: COLLATERAL_TOKEN };

// Account A creates the target-market supply.
let supplier_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(big18, 1_000_000_000 * 10^18)]
);

// Account B supplies collateral belonging to the same unprivileged caller.
let borrower_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral, sufficient_collateral)]
);

// Account B borrows approximately 98% of the target market.
controller.borrow(
    attacker,
    borrower_id,
    vec![(big18, 980_000_000 * 10^18)],
    Some(attacker)
);

// After sustained high-utilization accrual:
controller.update_indexes(attacker, vec![big18]);
// => MathOverflow inside scaled_to_original(borrowed, borrow_index)

// Thereafter these also revert before mutation:
controller.repay(attacker, borrower_id, vec![(big18, 1)]);
controller.withdraw(attacker, supplier_id, vec![(big18, 1)], None);
controller.liquidate(liquidator, borrower_id, payments, SeizeMode::Transfer);
```
