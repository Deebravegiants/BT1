### Title
Front-runnable, seed-only `market_info` account lets an attacker permanently squat the deterministic AMM pool PDA and block legitimate pool creation - ([File: program/src/processor.rs])

### Summary
`Initialize2` derives the `amm_info` pool account's address deterministically from the `market_info` account key alone (via `AMM_ASSOCIATED_SEED`), and the code explicitly treats `market_info` as an arbitrary, unvalidated seed rather than a real OpenBook/Serum market. Because this address is fully predictable and the instruction is permissionless, an attacker can front-run a legitimate pool creator's `Initialize2` transaction for the same `market_info` key, permanently squatting the deterministic pool PDA and blocking the legitimate pair from ever being created for that market seed — directly analogous to the reported UniswapV2Factory precomputed-address front-running bug.

### Finding Description
`process_initialize2` explicitly documents `market_info` as "Just a seed for AMM account. Can be any account," and in the alternate (non-19-account) branch even the market program account is unused/unchecked ("Won't use. Can be any account."). [1](#0-0) [2](#0-1) 

The pool (`amm_info`), lp mint, target-orders, and vault accounts are all derived deterministically with `get_associated_address_and_bump_seed`, whose seeds are `program_id`, `market_address` (i.e. `market_info.key`), and a fixed associated-seed constant — nothing else ties the derivation to a specific coin/pc mint pair or to caller identity: [3](#0-2) 

`generate_amm_associated_account` (used to create `amm_info` itself) checks that the derived PDA matches the passed-in account, and if that PDA is already owned by something other than the system program, it fails with `RepeatCreateAmm` instead of proceeding: [4](#0-3) [5](#0-4) 

Since (1) the resulting address is fully computable off-chain by anyone who knows/observes the `market_info` pubkey (which is either a well-known, pre-existing account or is visible in the legitimate creator's pending transaction), and (2) `Initialize2` requires no permission beyond being a fee-paying signer, an attacker can submit their own `Initialize2` with the same `market_info` account (using arbitrary or attacker-favorable coin/pc mints and minimal init amounts) ahead of the legitimate creator's transaction. This claims the deterministic `amm_info`/vault/lp-mint PDAs first, so the legitimate creator's later `Initialize2` call for the *same* `market_info` permanently fails with `RepeatCreateAmm` — there is no reclaim path since account ownership assignment to the program is irreversible on-chain.

This mirrors the reported issue exactly: a deterministic, precomputable "pair" address tied to a single external identifier (ERC721 collection there, `market_info` here) can be squatted by front-running the canonical creation instruction, permanently denying legitimate pool creation for that identifier.

### Impact Explanation
A malicious actor can permanently block any specific `market_info`-keyed AMM pool from ever being legitimately created by Raydium/integrators, since the PDA collision is irreversible (`RepeatCreateAmm`). For markets with a fixed canonical identity (e.g., a specific OpenBook market pubkey a project intends to use, or any well-known/precomputed seed account), this is a permanent denial-of-service on pool creation for that pair, and if the attacker instead completes a squatted pool with mismatched or malicious mints and minimal liquidity, subsequent depositors/traders directed to that PDA interact with an illegitimate pool. This matches the Medium severity assigned to the analogous UniswapV2Factory report.

### Likelihood Explanation
Exploitation requires only observing/knowing the `market_info` pubkey a party intends to use (trivial for well-known markets, or via mempool observation of a pending `Initialize2` transaction) and submitting a single unprivileged `Initialize2` transaction ahead of it — no special access or race beyond standard front-running is needed, making this readily reachable by any unprivileged actor.

### Recommendation
Do not allow `market_info` to be an arbitrary, unvalidated seed account. Either (a) require and validate that `market_info` is genuinely owned by/associated with a specific market program and that its stored coin/pc mints match `amm_coin_mint_info`/`amm_pc_mint_info`, or (b) derive the `amm_info` PDA from the coin/pc mint pair (and/or `amm_config`) instead of an arbitrary externally-supplied seed account, so the resulting address cannot be squatted independent of the actual token pair being created.

### Proof of Concept
1. Legitimate project intends to create a pool using a known `market_info` pubkey `M`, coin mint `A`, and pc mint `B`.
2. Attacker computes the deterministic `amm_info` address as `get_associated_address_and_bump_seed(program_id, M, AMM_ASSOCIATED_SEED, program_id)` (same for lp mint/vault seeds) — no cryptographic secret is involved, `M` is public.
3. Attacker submits `Initialize2` first, using `market_info = M`, but with arbitrary/garbage mints and dust `init_coin_amount`/`init_pc_amount`, successfully creating and assigning the PDA accounts to the program (`generate_amm_associated_account` succeeds since the account is still system-owned) — see `program/src/processor.rs` lines 748-825 for the account-creation sequence.
4. Legitimate project's later `Initialize2` call with the intended mints `A`/`B` and the same `market_info = M` now fails at `generate_amm_associated_account` with `AmmError::RepeatCreateAmm` (`program/src/processor.rs` lines 541-544), permanently preventing creation of the intended pool for market `M`.
