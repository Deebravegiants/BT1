### Title
Unbounded slippage in `SwapFirstAssetTrader::buy_weight` allows AMM price manipulation to overcharge XCM fee payers - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader::buy_weight` computes a fixed `Target`-denominated fee via `WeightToFee::weight_to_fee(&weight)` and then swaps the user's entire supplied payment asset for that exact `Target` amount using `SwapCredit::swap_tokens_for_exact_tokens`, without passing or enforcing any maximum-input / slippage bound. Because `pallet_asset_conversion` pool prices are freely and permissionlessly moved by any liquidity-pool participant, the amount of the user's asset actually consumed to cover a fixed weight/fee is fully dependent on the pool state at execution time, with no cap protecting the payer.

### Finding Description
In `SwapFirstAssetTrader::buy_weight` [1](#0-0) , the fee is computed statically from `WeightToFee::weight_to_fee(&weight)` [2](#0-1) , and the full `credit_in` (all of the fungible asset offered in the `BuyExecution` payment) is handed to `SwapCredit::swap_tokens_for_exact_tokens(vec![swap_asset, Target::get()], credit_in, fee)` [3](#0-2) . This is an "exact-output" swap: the pallet computes however much of `swap_asset` is required, at the *current* pool ratio, to yield exactly `fee` units of `Target`, and consumes that amount from `credit_in` (the remainder becomes `credit_change` and is returned to the holding register). No `amount_in_max`/slippage-limit argument is passed by the trader to bound how much of the user's asset can be consumed relative to a fair-value estimate — the only implicit "cap" is the total balance of `credit_in` itself (if the pool-implied input exceeds the entire payment, the swap fails and `XcmError::FeesNotMet` is returned).

Because `pallet_asset_conversion` pools are permissionless (any unprivileged account can `swap_exact_tokens_for_tokens` / `swap_tokens_for_exact_tokens` against the `swap_asset`/`Target` pool), an attacker can skew the pool ratio immediately before a victim's XCM message with `BuyExecution` is executed. When `SwapFirstAssetTrader::buy_weight` subsequently executes at the skewed price, it will consume a correspondingly larger amount of the victim's `swap_asset` to produce the same fixed `Target`-denominated `fee`, up to the full amount the victim supplied in `BuyExecution`. There is no check comparing the consumed amount against a reference/quoted price (the trader does not call `QuotePrice` before swapping) or bounding the acceptable slippage.

### Impact Explanation
A victim's XCM `BuyExecution` can be made to pay dramatically more of their asset than `WeightToFee::weight_to_fee(&weight)` should require in fair-value terms, up to the entire amount they offered as payment. This is a direct asset-drain against a normal, unprivileged XCM sender whose message happens to be executed while the pool is in a manipulated state; the excess is captured by the attacker via arbitrage/price reversal in the pool (classic sandwich mechanics), or simply extracted as slippage loss transferred to LPs/attacker-controlled liquidity.

### Likelihood Explanation
The precondition (a permissionless `pallet_asset_conversion` pool for `swap_asset`/`Target` with attacker-controllable liquidity/swap actions) is realistic wherever `SwapFirstAssetTrader` is configured to use on-chain AMM pools for paying XCM fees in non-`Target` assets. Reliable "front-running" in the strict same-block-before-the-message sense is limited by the fact that parachains typically process inbound XCM (UMP/HRMP) before extrinsics within a block; however, an attacker only needs the pool to be in a skewed state *at the time* the victim's message is processed — this can be achieved by leaving a manipulated pool state from a preceding block/extrinsic (skew now, victim's message arrives and is processed against the still-skewed pool, then attacker reverses/arbitrages afterward), which is fully within reach of an unprivileged, repeatable actor and does not require exact same-block ordering. Thin/low-liquidity pools worsen the achievable price impact.

### Recommendation
`SwapFirstAssetTrader::buy_weight` should enforce a slippage bound: e.g., use `QuotePrice::quote_price_tokens_for_exact_tokens` to determine an expected/maximum acceptable `swap_asset` input before calling `swap_tokens_for_exact_tokens`, and pass a bounded maximum-input variant (or explicitly reject/limit the swap when the amount consumed from `credit_in` exceeds the quoted price by more than an acceptable tolerance), returning `XcmError::TooExpensive` instead of silently paying whatever the skewed pool demands.

### Proof of Concept
Rust xcm-simulator / integration test plan:
1. Set up a runtime with `pallet_asset_conversion` and a pool for `(swap_asset, Target)` seeded with modest liquidity, and configure `SwapFirstAssetTrader<Target, AssetConversion, WeightToFee, ...>` as the `WeightTrader`.
2. Record `expected_fee = WeightToFee::weight_to_fee(&weight)` and query the pool's current quote via `quote_price_tokens_for_exact_tokens` to get `baseline_input`.
3. As an unprivileged account, call `pallet_asset_conversion::swap_exact_tokens_for_tokens` to substantially skew the pool ratio (e.g., dump a large amount of `Target` into the pool to make `swap_asset` cheap relative to `Target`, or vice versa to make it expensive).
4. Execute a `BuyExecution` XCM instruction (via `Executor::execute_xcm` or the xcm-simulator) using `swap_asset` as payment, invoking `SwapFirstAssetTrader::buy_weight` for `weight`.
5. Assert that `credit_in_consumed = given_credit_amount - credit_change.peek()` exceeds `baseline_input` by more than a defined bound (e.g., >20%), demonstrating unbounded slippage — i.e., assert the amount consumed is **not** bounded by any multiple of the pre-manipulation quoted price, contrary to the expected invariant. 	fn buy_weight(
		&mut self,
		weight: Weight,
		mut payment: AssetsInHolding,
		_context: &XcmContext,
	) -> Result<AssetsInHolding, (AssetsInHolding, XcmError)> {
		log::trace!(
			target: "xcm::weight",
			"SwapFirstAssetTrader::buy_weight weight: {:?}, payment: {:?}",
			weight,
			payment,
		);
		let Some((id, given_credit)) = payment.fungible.first_key_value() else {
			return Err((payment, XcmError::AssetNotFound));
		};
		let id = id.clone();
		let given_credit_amount = given_credit.amount();
		let first_asset: Asset = (id.clone(), given_credit_amount).into();
		let Ok((fungibles_id, _)) = FungiblesAssetMatcher::matches_fungibles(&first_asset) else {
			log::trace!(
				target: "xcm::weight",
				"SwapFirstAssetTrader::buy_weight asset {:?} didn't match",
				first_asset,
			);
			return Err((payment, XcmError::AssetNotFound));
		};

		let swap_asset = fungibles_id.clone().into();
		if Target::get().eq(&swap_asset) {
			log::trace!(
				target: "xcm::weight",
				"SwapFirstAssetTrader::buy_weight Asset was same as Target, swap not needed.",
			);
			// current trader is not applicable.
			return Err((payment, XcmError::FeesNotMet));
		}
		// Subtract required from payment
		let Some(imbalance) = payment.fungible.remove(&first_asset.id) else {
			return Err((payment, XcmError::TooExpensive));
		};
		// "manually" build the concrete credit and move the imbalance there.
		let mut credit_in = fungibles::Credit::<AccountId, Fungibles>::zero(fungibles_id);
		credit_in.saturating_subsume(imbalance);

		let fee = WeightToFee::weight_to_fee(&weight);
		// swap the user's asset for the `Target` asset.
		let (credit_out, credit_change) = match SwapCredit::swap_tokens_for_exact_tokens(
			vec![swap_asset, Target::get()],
			credit_in,
			fee,
		) {
			Ok(a) => a,
			Err((credit_in, error)) => {
				log::trace!(
					target: "xcm::weight",
					"SwapFirstAssetTrader::buy_weight swap couldn't be done. Error was: {:?}",
					error,
				);
				// put back the taken credit
				let taken =
					AssetsInHolding::new_from_fungible_credit(id.clone(), Box::new(credit_in));
				payment.subsume_assets(taken);
				return Err((payment, XcmError::FeesNotMet));
			},
		};
