### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Data Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight through to the app's handler as the identity of the merchant the event belongs to. Because the shop field is never part of the signed content, any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` can replay it while substituting a different shop domain, causing the app to attribute the webhook to a shop that never sent it.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from an HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is completely independent of the HMAC computation: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (i.e. only the body) and compares it against `Context.api_secret_key`: [3](#0-2) [4](#0-3) 

The validated request's unauthenticated `shop` field is then forwarded into `WebhookMetadata`, which host applications are documented to use as the identity of the shop the event belongs to: [5](#0-4) 

The identity equality the app relies on is: **HMAC-authenticated bytes (body) == identity used by the handler (shop header)**. These are not the same data. Since Shopify apps share a single `api_secret_key` across all shops that install the app, an attacker who controls their own shop can capture a legitimate, correctly-signed `(raw_body, hmac)` webhook delivery from their own store (e.g. `orders/create`), then POST it directly to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body/secret, not the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the shop-identity binding that the host application is documented to trust (`data.shop`), enabling cross-tenant data confusion: an attacker-controlled shop can inject webhook payloads that the app processes as belonging to a different, victim tenant. Depending on how the host app uses `data.shop` (e.g., to look up which merchant's session/access token to act with, or to write attacker-supplied order/product data under the victim's record), this can escalate to cross-tenant data corruption or actions being performed against the wrong merchant's resources. This matches the "cross-tenant access" impact category, since the gem itself provides no way for the host app to distinguish a genuine victim-originated webhook from a replayed one with a spoofed shop header.

### Likelihood Explanation
Any developer/merchant who has installed the app on their own store can obtain a validly signed webhook body+HMAC through normal use (no credential theft required — this is inherent to the shared-secret design), and the webhook HTTP endpoint is a public internet-facing endpoint. No access token, `api_secret_key`, or privileged account is required — only the ability to run a shop that has the target app installed and to send a crafted HTTP POST. This is a realistic, low-effort attack path reachable by any unprivileged, ordinary merchant.

### Recommendation
Bind the shop identity into the integrity check rather than trusting an unauthenticated header:
- Reject webhooks whose `shop` header does not correspond to a shop for which the app currently holds a valid, previously-established session/registration.
- Consider incorporating the shop domain (and/or webhook id) into the value verified against the HMAC, or requiring the caller to additionally validate that the `webhook_id` has not been previously processed. At minimum, document prominently that `data.shop` is not cryptographically bound by the HMAC check and must be independently corroborated (e.g., against known installed shops) before being trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body under api_secret_key>`
   - raw body: `{"id": 1, ...}`
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker crafts a new POST directly to the app's public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present) and `Utils::HmacValidator.validate` returns `true`, because it only hashes `raw_body`: [4](#0-3) 
6. `Registry.process` calls the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, i.e. the app processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`. [3](#0-2)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
