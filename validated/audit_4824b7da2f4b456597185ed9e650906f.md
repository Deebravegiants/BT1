Audit Report

## Title
Unauthenticated NULL pointer dereference / node crash via missing `params` in `vault_publicKeyGet` gateway message - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor.ProcessRequest`, which is the only place that guards against `req.Params == nil` before dereferencing. `handlePublicKeyGet` unconditionally executes `json.Unmarshal(*req.Params, r)`, so a request with omitted/null `params` causes a nil-pointer dereference panic.

## Finding Description
In `core/capabilities/vault/gw_handler.go`, the dispatch switch sends `MethodSecretsCreate/Update/Delete/List` through `h.requestProcessor.ProcessRequest`, whose per-method handlers in `core/capabilities/vault/gateway_vault_request_processor.go` (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) all check `if req.Params == nil` before unmarshalling. [1](#0-0) 

`MethodPublicKeyGet`, however, is dispatched directly to `handlePublicKeyGet` with no such guard and no authorization step: [2](#0-1) [3](#0-2) 

Tracing the request origin confirms this is externally reachable: on the gateway side, `handler.HandleJSONRPCUserMessage` special-cases `MethodPublicKeyGet` to skip authorization entirely ("Public key requests don't require authorization") and, on cache miss, forwards the *unmodified* incoming request (including whatever `Params` the caller supplied, nil or not) straight to nodes via `fanOutToVaultNodes` → `h.don.SendToNode`, with no params validation performed anywhere in that path. [4](#0-3) [5](#0-4) 

On the node side, the connector's `readLoop` dispatches the parsed JSON-RPC request to the registered handler (`GatewayHandler.HandleGatewayMessage`) with no `recover()` around the call, so any panic inside the handler chain would propagate and crash that goroutine (and potentially the process, depending on Go panic propagation across goroutines without recovery). [6](#0-5) 

The root cause is a broken security assumption: `handlePublicKeyGet` implicitly assumes `req.Params` is always non-nil (mirroring the internal `fetchVaultPublicKey` caller, which always marshals an empty `GetPublicKeyRequest{}` into `Params`), but external/user-supplied requests are not required to include a `params` field per JSON-RPC 2.0, and no validation enforces that assumption on the externally-reachable path.

## Impact Explanation
This maps to an in-scope "node crash / denial of service via node API" class of impact. A single crafted JSON-RPC request with `method: "vault_publicKeyGet"` and omitted/null `params`, submitted to the gateway's user-facing endpoint, is forwarded unauthenticated and unvalidated to DON nodes, where it triggers a nil-pointer panic in `handlePublicKeyGet`. Because `MethodPublicKeyGet` deliberately bypasses authorization (by design, since the public key is meant to be publicly retrievable), this is exploitable by any unauthenticated actor able to reach the gateway's vault endpoint.

## Likelihood Explanation
High. No credentials, allowlist membership, or JWT are required — `HandleJSONRPCUserMessage` explicitly skips authorization for this method. The only precondition is a cache miss on the gateway (`getCachedPublicKey()` returns nil), which is trivially the case on gateway/node restart or before the periodic 1-minute refresh populates the cache, and is otherwise likely already warm in most deployments (which would reduce, but not eliminate, real-world exploitability — an attacker could also potentially race a cold cache window, e.g. right after gateway restart). Submitting a well-formed JSON-RPC envelope with `params` omitted is trivial for any external caller.

## Recommendation
Add a `req.Params == nil` guard in `handlePublicKeyGet` (mirroring the guards in `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest`) before dereferencing `*req.Params`, returning a JSON-RPC error response instead of panicking. Also consider adding `recover()` around the handler dispatch in the connector's `readLoop` (`core/services/gateway/connector/connector.go`) as defense-in-depth against any single handler panic taking down the node process.

## Proof of Concept
1. Ensure the gateway's cached public key is empty/stale (e.g., immediately after gateway restart, before `fetchVaultPublicKey`'s first tick, or by targeting a gateway/DON path in that state).
2. Send an unauthenticated JSON-RPC request to the gateway's vault endpoint:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
with the `params` field omitted (or `"params": null`).
3. `handler.HandleJSONRPCUserMessage` (gateway side) sees the cache miss and calls `handlePublicKeyGet` → `fanOutToVaultNodes`, forwarding the request as-is to DON nodes.
4. On the node, `connector.readLoop` dispatches to `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet`; `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, panicking in the read-loop goroutine.
5. A Go unit test constructing `GatewayHandler.handlePublicKeyGet(ctx, gatewayID, &jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil})` directly reproduces the panic without needing the full gateway round-trip.

func (h *handler) handlePublicKeyGet(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
	if cachedPublicKey != nil {
		l.Debugw("returning cached public key response")

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
