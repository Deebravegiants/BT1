### Title
Overpaid native-token fees in `EvmHost.dispatch`/`fundRequest` are permanently stranded instead of refunded - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all convert user-supplied native ETH into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, but none of the three functions capture or refund the ETH the router returns when `msg.value` exceeds the amount actually spent on the swap.

### Finding Description
Each of these entry points calls `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. [1](#0-0) [2](#0-1) [3](#0-2) 

Uniswap V2 Router's `swapETHForExactTokens` is an exact-output swap: it computes `amounts[0]` (the ETH actually required for the given output amount and current pool price) and reverts if `amounts[0] > msg.value` ("EXCESSIVE_INPUT_AMOUNT"). If `msg.value > amounts[0]`, the router refunds the *dust* — but the refund target is `msg.sender` as seen by the router, which is `EvmHost` itself (the router is called by `EvmHost`), not the original external caller (`_msgSender()`). None of the three `EvmHost` functions capture this returned `amounts[0]` value or forward the leftover ETH back to `_msgSender()`.

This is the direct sibling of the correct pattern implemented elsewhere in the same codebase: `IntentGatewayV2.placeOrder` performs the identical native→feeToken swap but explicitly tracks `amounts[0]` and refunds any leftover `msgValue` to the caller. [4](#0-3) 

Because `EvmHost` omits this bookkeeping, any ETH sent above the exact amount required by the current pool price for the requested `fee`/`amount` is silently absorbed into the `EvmHost` contract's balance with no on-chain accounting tying it back to the payer, and no user-facing recovery path was found in `EvmHost.sol` (no `withdraw`/`sweep`/`receive` logic that could restore it to the original sender).

### Impact Explanation
Any unprivileged caller of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` who slightly overestimates the ETH needed (which is expected in practice, since callers must overshoot to avoid reverts on `getAmountsIn` volatility, per the docs' own warning that `quote()` is sandwich-able and only an estimate) loses the difference permanently. This is a direct, unprivileged loss-of-funds path reachable from a single transaction — every dispatcher call that pays in native token is affected, not an edge case.

### Likelihood Explanation
High likelihood of occurrence in normal operation: the documentation itself instructs integrators to estimate fees off-chain via `quote()` and warns that on-chain price is subject to slippage/sandwiching, meaning callers routinely send `msg.value` with headroom above the exact required amount to avoid reverts. Every such call leaks the excess into the host contract permanently.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` and refund `msg.value - amounts[0]` to `_msgSender()` (mirroring `IntentGatewayV2.placeOrder`'s `_sendValue(msg.sender, msgValue)` pattern), or use `swapExactETHForTokens` with a computed minimum output.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost{..., fee: 100e18, ...})` with `msg.value = 1 ether`, expecting the swap to need close to 1 ether for 100 feeTokens based on an off-chain quote.
2. Pool price is slightly better than quoted (or the caller intentionally overshoots `msg.value` for safety margin), so the router only consumes `amounts[0] = 0.98 ether` and refunds `0.02 ether` back to `msg.sender`, i.e., `EvmHost`.
3. `EvmHost.dispatch` never reads `amounts[0]` nor forwards the `0.02 ether` back to the caller; it is retained by the `EvmHost` contract with no state variable or event tying it to the original payer.
4. Repeating this over many dispatches accumulates ETH inside `EvmHost` that the payers can never reclaim.

Note: I was unable to fully verify whether `EvmHost` (or an inherited base contract not captured in the index) exposes any governance-controlled `withdraw`/`sweep` function that could later redirect this stranded ETH somewhere (to governance/treasury rather than back to payers) — the index did not return such a function within `evm/src/core/EvmHost.sol`. If a background Devin session is used to fix this, it should first confirm via full source access whether any such recovery path exists elsewhere in the inheritance chain before concluding severity conclusively.
