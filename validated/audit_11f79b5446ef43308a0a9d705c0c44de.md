### Title
Webhook `shop` identifier is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates its HMAC over the raw request body only, while the `shop` (tenant) identifier is read from an HTTP header that is never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` then hands that unauthenticated `shop` value straight to the app's webhook handler. An attacker who can obtain any one valid `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a legitimate webhook delivery) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim store. The HMAC check still passes because it never covered the header, so the handler acts as if the (attacker-supplied) body belongs to the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is completely outside that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` against the received `hmac`: [3](#0-2) 

`Registry.process` gates on that HMAC check and then forwards the (unauthenticated) `request.shop` straight into the handler's `WebhookMetadata`: [4](#0-3) 

The `api_secret_key` used for the HMAC is the app's single client secret, shared across every shop that installs the app — it is not per-shop. Consequently, a valid `(raw_body, hmac)` pair proves only "this body was sent by someone who owns/received a delivery from an app installation," not "this body concerns shop X." Because the header carrying the shop identity is unauthenticated, the equality the gem implicitly relies on —

`shop asserted in the validated request == shop the signed body actually concerns`

— does not hold. This is structurally identical to the report's bug class: a field the code *acts on* (`shop`) is not covered by the cryptographic check that is supposed to bind identity (`hmac`), so a value that should be pinned can be substituted by an unprivileged party without invalidating the signature.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to select per-tenant data, credentials, or session state (which is the gem's own documented usage pattern — `data.shop` is the mechanism by which host apps are expected to route webhook payloads to the correct tenant) can be made to associate an attacker-controlled body with a different, victim shop domain. This crosses the tenant boundary that the whole `shop`-based session/data model is built on, matching the Critical "cross-tenant access" impact category. The attacker does not need the app's `client_secret`, an access token, or any privileged access — only the ability to install the app on their own store (or otherwise obtain one legitimate webhook body/HMAC pair) and to make an HTTP POST to the app's public webhook endpoint with a forged header, which is well within an "unprivileged internet user" acting against a multi-tenant app.

### Likelihood Explanation
Exploitation requires no secrets: capturing one's own legitimate webhook (trivial for anyone who installs the app) and replaying it with a different `shop-domain` header value to the app's public webhook endpoint. `Request.new` only checks for header *presence*, not any relationship between the header and body/HMAC, and `HmacValidator.validate` has no way to detect the mismatch since the header was never part of the signed message.

### Recommendation
Bind the shop identity to the verified content instead of trusting an unauthenticated header value:
- Extract the shop domain from the webhook payload body itself (many Shopify webhook payloads include shop-identifying fields) and/or cross-check the header value against a shop derived from data that is actually covered by the HMAC (e.g., correlate against the currently active/known session for that delivery), rejecting the request if they disagree.
- At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used by itself to select per-tenant secrets or data, and require host apps to corroborate it against another authenticated source (e.g., the shop tied to an already-stored offline session/webhook subscription id) before trusting it.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `client_secret`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body `B` and HMAC `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — passes, since `B`/`H` are unchanged and valid. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, even though the body content actually originated from, and pertains to, `attacker-shop.myshopify.com` — a cross-tenant identity confusion the app has no way to detect from within this gem's API surface.
