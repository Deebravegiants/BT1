This confirms the vulnerability claim. The commitment hash is computed as `hash4(utxo.amount, erc20Address, stealthAddressStructure.stealthAddress, timeStamp)` at [1](#0-0) , which never includes or binds to `onChainEncryptedOutput`'s content — the encrypted output is stored as a sibling field for off-chain discovery purposes only, and its correctness relative to the commitment is unchecked. The `performProoflessDepositChecks` function only validates array-length equality and that each `onChainEncryptedOutputs[i]` is non-empty and `amounts[i] > 0`; it never validates that the encrypted output actually encrypts the correct `(amount, erc20Address)` for the recipient named in `stealthAddressStructures[i]` [2](#0-1) .

### Title
Deliberately mismatched `onChainEncryptedOutputs[i]` in `prooflessDeposit` freezes discoverability of victim's spendable UTXO - ([File: contracts/HinkalHelper.sol], [File: contracts/Hinkal.sol])

### Summary
`performProoflessDepositChecks` and `_createProoflessDepositCommitments` never verify that `onChainEncryptedOutputs[i]` actually encrypts the real `(amount, erc20Address)` values for the recipient encoded in `stealthAddressStructures[i]`. An attacker calling `prooflessDeposit` can supply a correct `stealthAddressStructures[i]` naming victim V (so the resulting leaf is real, correctly backed, and spendable by V's nullifying key) while pairing it with a garbage or attacker-encrypted `onChainEncryptedOutputs[i]`, making V's UTXO undiscoverable by V's wallet even though it is safely on-chain and spendable via proof.

### Finding Description
The broken equality: "recipient encoded in `stealthAddressStructures[i]`" == "recipient who can decrypt `onChainEncryptedOutputs[i]`" is never enforced anywhere in the deposit path.

`prooflessDeposit` in `contracts/Hinkal.sol` accepts four parallel arrays (`erc20Addresses`, `amounts`, `stealthAddressStructures`, `onChainEncryptedOutputs`) tied only by index and length [3](#0-2) . It calls `hinkalHelper.performProoflessDepositChecks`, which only checks that all four arrays have equal length, that the array length doesn't exceed `MAX_LEAVES_PD`, that each `onChainEncryptedOutputs[i]` is non-empty, and that `amounts[i] > 0` [2](#0-1) . There is no cryptographic or on-chain binding check between the two fields.

`_createProoflessDepositCommitments` then builds the on-chain commitment via `createOnchainCommitment`, which computes `commitment = hash4(utxo.amount, erc20Address, utxo.stealthAddressStructure.stealthAddress, utxo.timeStamp)` — the `onChainEncryptedOutput` bytes are attached to the `OnChainCommitment` struct purely for emission via `NewCommitment`/`insertCommitments`, and are not part of the commitment hash at all [1](#0-0) . Since the leaf's spendability is governed entirely by the `(amount, erc20Address, stealthAddress, timeStamp)` fields hashed into the Merkle leaf — fields that circuits later verify directly, independent of the encrypted output content — the attacker can set `onChainEncryptedOutputs[i]` to any garbage (or an output encrypted under the attacker's own key) without affecting the leaf's cryptographic correctness or V's ability to later prove spend knowledge via V's nullifying key against `stealthAddressStructures[i]`.

Attacker's exact call: `prooflessDeposit(erc20Addresses=[V_token], amounts=[X], stealthAddressStructures=[StealthAddressStructure for V], onChainEncryptedOutputs=[garbage_bytes_or_attacker_encrypted], createBlockedUtxos=false, orderId="")`. This deposits real attacker funds, mints a genuine leaf spendable only by V, but V's wallet — which discovers UTXOs by scanning `NewCommitment` events and attempting decryption of `onChainEncryptedOutput` with V's key — will fail to decrypt or will decrypt garbage, and thus never surfaces this UTXO to V.

Existing guards do not prevent this: `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, proof verification, and nullifier/root checks all operate on the `transact` (spend) path, not on `prooflessDeposit`. None of them constrain the relationship between `stealthAddressStructures[i]` and `onChainEncryptedOutputs[i]` at deposit time, since the encrypted output is never a circuit input for the deposit itself.

### Impact Explanation
Victim V's funds are real, correctly backed, and eventually spendable via a valid proof (since the leaf hash only depends on amount/erc20Address/stealthAddress/timeStamp, all correctly set to V's values). However, V has no practical way to discover the UTXO's existence without off-chain brute-force scanning of all leaves and testing nullifying keys against every leaf on the tree — impractical at scale. This is a temporary freezing of victim funds due to a discoverability failure, matching the "High - temporary freezing of user funds" category. The attacker gains no direct financial benefit (they still pay for the deposit) but can grief a target repeatedly, front-run a legitimate deposit-notification flow, or disrupt off-chain indexer-based wallet UX for arbitrary victims at the cost of one deposit each time.

### Likelihood Explanation
Preconditions: attacker just needs to know a victim's public stealth-address parameters (which are typically shared for receiving deposits) and be willing to fund the deposit amount themselves (since `_handleTransfersFromProoflessDeposit` pulls funds from `msg.sender`) [4](#0-3) . No special tree state or timing is required. This is fully repeatable per victim per deposit call and costs only the deposited amount plus gas, with no privileged role needed.

### Recommendation
Bind `onChainEncryptedOutputs[i]` to `stealthAddressStructures[i]` (and the amount/token) cryptographically or require the encrypted payload to be verifiable/re-derivable from public data, or alternatively include a commitment/hash of the encrypted output tied to the stealth address as part of the leaf hash so a mismatch is either provably detectable on-chain or impossible to construct without knowledge of V's public key material used correctly. At minimum, add an off-chain/relay-level sanity check plus emit a way for wallets to detect "orphaned" commitments (e.g., a periodic reconciliation job scanning `NewCommitment` events against expected decrypt failures), though this only mitigates rather than fixes the root cause.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a mock ERC20; register V's `StealthAddressStructure` (with real `H0x/H0y/H1x/H1y/stealthAddress` derived from V's nullifying key, as used elsewhere in tests for legitimate deposits).
2. As attacker EOA, call `prooflessDeposit` with `erc20Addresses=[token]`, `amounts=[100e18]`, `stealthAddressStructures=[V's real structure]`, `onChainEncryptedOutputs=[bytes("garbage")]` (any non-empty bytes), `createBlockedUtxos=false`.
3. Assert deposit succeeds, `NewCommitment` event emitted with correct `commitment = hash4(100e18, token, V.stealthAddress, timestamp)` and the garbage `onChainEncryptedOutput`.
4. Assert V's off-chain decryption routine (mock) fails to recover `(amount, erc20Address)` from the garbage bytes — confirming discoverability failure.
5. As V, construct a valid `transact` proof directly from the known leaf fields (amount, erc20Address, stealthAddress, timeStamp, leaf index) using V's nullifying key — bypassing wallet-side discovery — and call `Hinkal.transact` to spend the UTXO.
6. Assert the spend succeeds (nullifier inserted, funds transferred to V), proving the funds were real and spendable, isolating the vulnerability strictly to off-chain discoverability rather than fund loss.
