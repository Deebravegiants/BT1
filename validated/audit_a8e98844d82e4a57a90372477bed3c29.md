Based on my investigation, I found a genuine structural analog to the Allora H-7 bug class in the `liquidate-multi` / `socialize-debt-asset` batch-processing code, but I was unable to fully verify the exact failure conditions of `vault-socialize-debt` and `debt-remove-scaled` before running out of tool iterations. I present what I found with that caveat.

### Title
Batch liquidation and bad-debt socialization silently swallow per-item errors, letting partial state writes persist while the operation is reported as failed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` calls `call-liquidate` via `map` over a list of positions and always wraps the result in `(ok ...)`, regardless of whether any individual `liquidate` call returned `(err ...)` [1](#0-0) . Because the outer call never returns `err`, the whole transaction is treated as successful by the chain, so any contract-calls already executed and committed inside a failing `liquidate` invocation (each `contract-call?` to `.v0-market-vault` / vault contracts commits independently as soon as it returns `ok`) are **not** rolled back just because a later step in the same `liquidate` execution fails.

### Finding Description
Inside `liquidate`, the sequence performs several independent, sequentially-committing side effects:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — real funds move from the liquidator into the vault. [2](#0-1) 
2. `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` — reduces the borrower's per-user debt ledger. [3](#0-2) 
3. `collateral-remove` transfers collateral to the liquidator. [4](#0-3) 
4. If the position ends with zero collateral (`no-collateral-left`), remaining debt on *other* assets is force-written-off via `fold socialize-debt-asset` and gated by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. [5](#0-4) 

`socialize-debt-asset` itself performs three sequential, independently-committing sub-calls per debt entry: `vault-socialize-debt` (writes down the vault's aggregate accounting — total-borrowed/assets/index), then `vault-accrue`, then `debt-remove-scaled` (clears the per-borrower obligation entry) — each guarded only by `unwrap!` returning a `failed-status` accumulator, not a full rollback of the earlier two calls in the same fold iteration [6](#0-5) .

If the first sub-call (`vault-socialize-debt`, which already commits the vault-side write-down) succeeds but a later one (`vault-accrue` or `debt-remove-scaled`) fails, `socialize-debt-asset` returns `{success: false}`, propagating up to `ERR-BAD-DEBT-SOCIALIZATION-FAILED` and making the whole `liquidate` call return `(err ...)`. However, because `liquidate-multi` unconditionally wraps the `map` results in `(ok ...)`, this `err` is never surfaced as a transaction failure — the transaction still commits. Since `vault-socialize-debt` already committed its write-down of the vault's aggregate total-borrowed/assets, but `debt-remove-scaled` (which would clear the corresponding per-user scaled-debt entry in `.v0-market-vault`) failed and did not commit, the vault's aggregate accounting and the per-user debt ledger diverge: the vault believes the debt was written off, while the borrower's obligation record still shows it outstanding. This is exactly the "per-user debt ledger versus the vault aggregate" identity break called out as an acceptable analog class.

### Impact Explanation
This breaks the invariant `sum(per-user scaled debt) == vault aggregate scaled/total-borrowed`. The borrower's now-zero-collateral position retains phantom debt that can never again be liquidated (no collateral left to seize) while the vault has already reduced its own accounting for that same debt, permanently understating total system debt relative to the sum of individual obligations (or vice versa depending on which side lags). This is a protocol-insolvency-class accounting drift.

### Likelihood Explanation
Reaching this requires: (a) a liquidation via `liquidate-multi` that fully drains a borrower's collateral (`no-collateral-left`) while other debt remains, entering the `socialize-debt-asset` fold, and (b) one of the fold's later sub-calls (`vault-accrue` or `debt-remove-scaled`) failing after `vault-socialize-debt` already succeeded for that asset. I was **not able to confirm within the available iterations** under what concrete conditions `vault-socialize-debt`, `vault-accrue`, or `debt-remove-scaled` would return an error in a way that is reachable by an attacker/liquidator rather than only by extreme edge-case arithmetic states — the definitions of `vault-socialize-debt` and `debt-remove-scaled` in `market-vault.clar`/`v0-market-vault.clar` were located but not read in time. This materially affects confidence in exploitability versus this being a purely theoretical, hard-to-trigger internal-consistency gap.

### Recommendation
Use a checkpoint/rollback pattern (Clarity doesn't have `CacheContext`, but the equivalent is to ensure the *entire* per-position liquidation, including bad-debt socialization, either fully commits or the enclosing `liquidate-multi` call itself returns `err` for that batch entry) — or restructure `socialize-debt-asset`/`liquidate` so that `vault-socialize-debt`'s vault-side write and `debt-remove-scaled`'s per-user write happen atomically as a single guaranteed pair (e.g., validate all preconditions for every debt entry before performing any writes), rather than committing step-by-step with `unwrap!`-only error capture.

### Proof of Concept
Not constructed — I was unable to verify, within the tool-call budget, the exact runtime conditions under which `vault-accrue` or `debt-remove-scaled` fail after `vault-socialize-debt` succeeds for the same debt entry, which is required to demonstrate concrete reachability. This should be validated against the full bodies of `vault-socialize-debt`, `vault-accrue`, and `debt-remove-scaled` in `market-vault.clar` / `v0-market-vault.clar` [6](#0-5)  before treating this as a confirmed, actionable finding.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
