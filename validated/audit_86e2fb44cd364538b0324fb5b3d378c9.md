Audit Report

## Title
Legacy WebAPI Gateway Handler Allows Unauthenticated Callback-Slot Hijacking via Attacker-Controlled `message_id` Collision — ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` in the Gateway's legacy WebAPI capability handler stores an in-flight caller's `callback` in the shared `savedCallbacks` map keyed solely by the caller-supplied `msg.Body.MessageID`, with no check for an existing entry and no binding to the message's cryptographically-verified sender. An unprivileged, unauthenticated client can submit a second legacy request reusing another party's in-flight `message_id`, silently overwriting the map entry, orphaning the original caller's callback, and causing the DON's eventual response to be delivered to the attacker instead.

## Finding Description
`gateway.ProcessRequest` routes any request with a `DonID` set as a "legacy request," validates only structural fields via `Message.Validate()`, and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) . `Message.Validate()` checks signature length, `MessageID`/`Method`/`DonID` length and null-byte suffixes, and calls `ExtractSigner()` to populate `m.Body.Sender` — but performs no uniqueness or ownership check on `MessageID`, and nothing ties `MessageID` to `Sender` [2](#0-1) . Any party holding an arbitrary ECDSA key can sign a message with any chosen `MessageID`, since the signature only covers the message's own fields, not any global uniqueness constraint [3](#0-2) .

Inside `HandleLegacyUserMessage`, after payload/timestamp/method checks, the handler unconditionally writes into the shared map:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [4](#0-3)  There is no `if _, found := h.savedCallbacks[msg.Body.MessageID]; found { reject }` guard here, unlike the sibling v2 handler's `setupCallback`, which explicitly checks `h.callbacks[requestID]` and returns `jsonrpc.ErrConflict` on collision [5](#0-4) .

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the entry purely by `MessageID` and delivers the response to whichever callback is currently stored — with no check that the responding trigger corresponds to the original sender:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageID]
delete(h.savedCallbacks, msg.Body.MessageID)
h.mu.Unlock()
if found {
    ...
    return savedCb.SendResponse(...)
}
``` [6](#0-5) 

I also confirmed there is a code comment acknowledging that allowlisting/rate-limiting is not yet applied on this legacy path (`// TODO: apply allowlist and rate-limiting here`) [7](#0-6) , and grepping the handler package confirms `savedCallbacks` is never keyed or filtered by `Sender` anywhere in the file.

The net effect: if two requests (legitimate victim + attacker) reach the gateway with the same `DonID` and the same `message_id` before the first is resolved, the second unconditionally clobbers the first's callback entry. The victim's HTTP request hangs until gateway timeout (`callback.Wait(ctx)` in `gateway.go`), and the DON's response — intended for the victim's triggered workflow — is delivered to the attacker's callback instead.

## Impact Explanation
This is a genuine, code-confirmed logic flaw: an unauthenticated party can (a) cause denial of service to a specific in-flight request by orphaning its callback, and (b) receive a response payload intended for another user's request if `message_id` collision is achieved. This maps to the in-scope "cross-user response corruption" / gateway request impersonation impact category, since the response for one user's triggered request can be redirected to another unprivileged actor's connection.

## Likelihood Explanation
No privileged role, credential, or DON-side access is required — any client able to reach the gateway's `ProcessRequest` endpoint and produce a validly-formed, self-signed `Message` (any key works; the signature only needs to be internally consistent) can attempt this. Exploiting it against a specific victim requires knowing or guessing the victim's `message_id` within the short window before the DON's first response arrives, which is feasible if IDs are predictable/sequential or if the client population reuses/handshakes IDs, and is trivially and deterministically reproducible by an attacker targeting their own request to demonstrate the flaw (self-collision), which alone is sufficient to prove the missing guard causes callback loss/misdelivery.

## Recommendation
In `HandleLegacyUserMessage`, before writing to `savedCallbacks`, check for an existing entry keyed by `msg.Body.MessageID` and reject the new request (e.g., respond with a conflict error) rather than overwriting, mirroring the collision guard already present in `httpTriggerHandler.setupCallback` at `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go` lines 419-426. Optionally, additionally scope/validate `MessageID` uniqueness against `Sender` to prevent any residual cross-tenant collision.

## Proof of Concept
1. Configure a gateway with a legacy DON handler.
2. Client A sends a legacy `web_api_trigger` request with `message_id = "X"`, valid signature, and waits for response (`callback.Wait`).
3. Before the DON responds, Client B (using a different, unrelated keypair) sends a second legacy request to the same DON with the same `message_id = "X"`.
4. Observe: `h.savedCallbacks["X"]` now points to Client B's callback; Client A's original callback reference is lost from the map.
5. When the DON eventually sends its `MethodWebAPITrigger` response for the request, `handleWebAPITriggerMessage` looks it up by `MessageID` only, finds Client B's callback, and delivers the response to Client B.
6. Client A's request stalls until timeout in `gateway.ProcessRequest`'s `callback.Wait(ctx)`, returning `api.RequestTimeoutError`.
This can be implemented directly as a Go unit test on the `handler` type, calling `HandleLegacyUserMessage` twice with the same `MessageID` and distinct callbacks, then calling `HandleNodeMessage`/`handleWebAPITriggerMessage` once and asserting which callback receives the response and that the other never fires.
