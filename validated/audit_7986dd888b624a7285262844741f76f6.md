### Title
Reentrancy through attacker-controlled `predispatch.call` in Tron `IntentGatewayV2.placeOrder()` enables escrow double-accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.placeOrder()` executes an order's `predispatch.call` through the permissionless `CallDispatcher`, then measures the dispatcher's post-call token balance to compute the amount escrowed for the order (`_orders[commitment][token] += reducedInputs[i].amount`), exactly mirroring the InfinityPools `swapForwarder`/`infinityPoolPaymentCallback` pattern: attacker-controlled calldata runs in the middle of a balance-diff/escrow-accounting routine with no reentrancy guard.

### Finding Description
In the EVM (mainline) implementation, `IntentGatewayV2.placeOrder` is protected with `nonReentrant` (`ReentrancyGuardTransient`): [1](#0-0) 

The Tron variant re-implements the exact same `predispatch` logic but the contract declares no reentrancy guard at all — it only inherits `HyperApp, EIP712`, unlike the mainline `IntentGatewayV2 is IntrinsicIntents, ExtrinsicIntents, ReentrancyGuardTransient, Initializable`: [2](#0-1) [3](#0-2) 

The vulnerable sequence: the user supplies `order.predispatch.call`, an arbitrary ABI-encoded `Call[]` forwarded verbatim to the `CallDispatcher`: [4](#0-3) 

After that arbitrary external call returns, the function reads the dispatcher's live token balance and uses it directly to (a) build the sweep-back transfer and (b) credit `_orders[commitment][token]` — i.e., the escrow accounting — without any prior balance snapshot to diff against: [5](#0-4) 

Because `ICallDispatcher(dispatcher).dispatch(...)` executes fully attacker-supplied calls (`to`, `value`, `data`), and because `placeOrder` carries no reentrancy lock, an attacker can re-enter `placeOrder` (or any other state-mutating function of the gateway) from within the `dispatch` call. A second, nested `placeOrder` call that also uses `order.predispatch` can push additional tokens into the same `dispatcher` and have them counted as `balance` for the *first* (outer) order's escrow — or, symmetrically, cause the outer call's `balance` read to double-count tokens that a nested call already routed through the dispatcher, crediting `_orders[commitment][token]` for value the gateway never actually escrowed from the reentrant caller. This is the same “measure balance after attacker-controlled execution, then debit/credit accounting from that balance” bug class as the reported InfinityPools issue, where the periphery contract double-counted the swap-forwarder callback's side effects into `collaterals`/`deposits`.

### Impact Explanation
`_orders[commitment][token]` backs the amount a solver can later claim via `_withdraw`/`RedeemEscrow`, and cross-chain `RedeemEscrow` settlement transfers real tokens to fillers based on this map. Inflating `_orders` beyond the tokens genuinely pulled from the user lets an attacker mint phantom escrow entries redeemable for real ERC-20/native balances held by the gateway (funded by other users' orders), i.e., direct theft of protocol/user funds — a High severity, concrete loss-of-funds condition consistent with the required "concrete theft ... of funds" bar.

### Likelihood Explanation
`placeOrder` is a fully permissionless, single-transaction entry point reachable by any unprivileged user; the `predispatch.call` field and the `CallDispatcher` target are both attacker-supplied, and reentrancy from an arbitrary external call (e.g., a malicious ERC-20 hook, or any contract the `Call[]` targets) is a standard, low-cost attack technique — likelihood is High, matching the original report's assessment of the analogous InfinityPools bug.

### Recommendation
Add the same reentrancy protection used in the mainline EVM `IntentGatewayV2` (`ReentrancyGuardTransient`/`nonReentrant`) to the Tron `IntentGatewayV2.placeOrder` (and any other externally callable function that dispatches attacker-controlled `Call[]` before finalizing escrow/dust accounting, e.g. `_execute`/output-call paths if present in the Tron variant). Additionally, snapshot the dispatcher's balance *before* invoking `dispatch(order.predispatch.call)` and compute escrow/dust strictly from the delta, rather than trusting the raw post-call balance, so a reentrant deposit cannot be attributed to the wrong order.

### Proof of Concept
Not independently reproduced against this repository (no forge test harness for the Tron contracts was available in the indexed content); the exploit mechanics mirror the original report's `GeneralSwapForwarder` PoC:
1. Attacker deploys a malicious `Call[]` target (or malicious token) that, when invoked inside `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, re-enters `IntentGatewayV2.placeOrder` with a second order whose `predispatch.assets`/`inputs` route additional tokens to the same shared `dispatcher`.
2. Because there is no `nonReentrant` guard, the nested call completes and moves tokens into `dispatcher` before the outer call's `balance = IERC20(token).balanceOf(dispatcher)` (line 428) is read.
3. The outer call's `balance` now reflects tokens contributed by the nested/reentrant order, so `_orders[commitment][token] += reducedInputs[i].amount` (line 441) credits the outer order's escrow for tokens it did not actually collect from `msg.sender`, while the nested order's own escrow accounting is computed independently — producing a double credit redeemable by two different commitments for the same underlying tokens.
