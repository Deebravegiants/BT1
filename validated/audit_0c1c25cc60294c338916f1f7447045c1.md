### Title
Unvalidated relayer-supplied beneficiary in `pallet-relayer::withdraw` allows a relayer to permanently burn their own accumulated fees - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`pallet_ismp_relayer::Pallet::withdraw` lets a relayer specify an arbitrary `beneficiary: Option<Vec<u8>>` for their fee withdrawal. This value is forwarded, unchecked, into a cross-chain `WithdrawalParams`/`Message::WithdrawRelayerFees` payload that ultimately triggers a token transfer to that address on the destination. Neither the dispatch-side pallet nor the receiving handler validates that the beneficiary is non-zero/non-default or that the amount is non-zero, mirroring the `claimToTreasury`-style zero-address bug from the external report.

### Finding Description
A relayer with accumulated `Fees` calls `withdraw_fees` (unsigned, self-attested via signature) supplying an optional `beneficiary` byte vector [3](#0-2) . `Pallet::withdraw` takes `beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone())` with no validation on its contents, then builds either a substrate `Message::WithdrawRelayerFees{ account, amount }` or an EVM `WithdrawalParams{ beneficiary_address, amount, token }` payload and dispatches it as a fee-less POST request [4](#0-3) .

On the substrate-destination side, `HyperbridgeWithdrawalModule::on_accept` decodes the message and unconditionally executes `T::Currency::transfer(&RELAYER_FEE_ACCOUNT.., &account, amount, Preservation::Expendable)` — there is no check that `account` is not the all-zero `AccountId32` (a burn address with no known private key) and no check that `amount != 0` [5](#0-4) . If `beneficiary` bytes decode to `AccountId32::try_from(&[0u8;32])`, the funds land in an address nobody controls — functionally identical to the reported "burn instead of sending to intended treasury" pattern, except here it is the relayer's own funds and the “destination” they control is malformed/incorrectly encoded.

The EVM-destination analog (`EvmHost.withdraw`, invoked via `HostManager.onAccept`) likewise performs no zero-address/zero-amount check before disbursing: `(bool sent,) = params.beneficiary.call{value: params.amount}("")` for the native path, or `IERC20(params.token).safeTransfer(params.beneficiary, params.amount)` for the ERC20 path [6](#0-5) . For the native-token path a `call` to `address(0)` succeeds and permanently burns the value; the ERC20 path is protected only incidentally because OpenZeppelin's `ERC20._update` reverts on a zero-address recipient [7](#0-6) , which is implementation-specific, not something the protocol code itself enforces.

### Impact Explanation
Medium: a relayer can, through their own bug or a malformed client, submit a withdrawal whose beneficiary is the zero/default account (or, on the EVM native-token side, whose beneficiary is `address(0)`), causing their own already-accumulated fee balance to be irrecoverably burned rather than delivered. `Fees` is zeroed unconditionally after dispatch, regardless of whether the destination-side transfer actually reaches a usable account, so the loss is permanent with no re-claim path. Unlike the original report's "owner mistake" framing, this is reachable by any unprivileged relayer, not a privileged actor, and the loss lands in a system-owned pot (`RELAYER_FEE_ACCOUNT`)/host balance being drained to an unusable address rather than the intended recipient.

### Likelihood Explanation
Requires no privilege beyond being a registered relayer with accrued `Fees` and the ability to submit a normal, unsigned `withdraw_fees`/`withdraw_funds` extrinsic — a routine, permissionless operation performed regularly by the tesseract relayer client [8](#0-7) . The trigger is most plausible via a buggy beneficiary-encoding path in relayer tooling (e.g., malformed short byte vectors zero-padded into an `AccountId32`) rather than deliberate self-harm, but the protocol performs no defensive check to prevent it.

### Recommendation
Add explicit validation before performing the transfer/call in both handlers:
- In `HyperbridgeWithdrawalModule::on_accept` (`modules/pallets/ismp/src/dispatcher.rs`), reject `Message::WithdrawRelayerFees` where `account == T::AccountId::default()` or `amount.is_zero()`, before calling `T::Currency::transfer`.
- In `EvmHost.withdraw` (`evm/src/core/EvmHost.sol`), require `params.beneficiary != address(0)` and `params.amount != 0` before executing either the native `call` or `safeTransfer`, mirroring the recommended `claimToTreasury` fix from the external report.
- Consider adding the same beneficiary validation earlier, in `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`), to fail fast on the source chain rather than burning funds on the destination.

### Proof of Concept
1. A relayer accrues `Fees` for some `dest_chain` via normal delivery + `accumulate_fees`.
2. The relayer (or a buggy client) calls `withdraw_fees` with `beneficiary = Some(vec![0u8; 32])` (or any bytes that decode to the zero `AccountId32`) for a substrate destination.
3. `Pallet::withdraw` accepts this without validation, zeroes `Fees`, and dispatches `Message::WithdrawRelayerFees{ account: AccountId32([0;32]), amount }` [9](#0-8) .
4. On delivery, `HyperbridgeWithdrawalModule::on_accept` transfers `amount` from `RELAYER_FEE_ACCOUNT` to the zero account, an address with no known private key [10](#0-9) .
5. The relayer's fees are permanently lost; `Fees` cannot be reclaimed since it was already zeroed in step 3.

	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

					&account,

				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
