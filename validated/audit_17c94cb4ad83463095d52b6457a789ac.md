### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values that are handed to the application's webhook handler come from separate, unsigned HTTP headers. This breaks the identity binding `HMAC-verified bytes == bytes the handler attributes to a tenant`, because the header carrying the tenant identity is never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate`, which internally calls `verifiable_query.to_signable_string` (i.e. the raw body) against `verifiable_query.hmac` — it never touches `shop`: [3](#0-2) [4](#0-3) 

After the (body-only) HMAC check passes, `request.shop` is forwarded unchanged into `WebhookMetadata`, which is the tenant identifier the host application's handler relies on to know "this event belongs to shop X": [5](#0-4) 

Because the shop header is never included in `to_signable_string`, an attacker who has legitimately received one valid webhook delivery for a shop they control (a normal Shopify merchant, no special privilege needed) possesses a `(raw_body, hmac)` pair that is valid for **any** `shopify-shop-domain` header value, since the app's shared `api_secret_key` HMACs only the body. Replaying that exact body with the `shopify-shop-domain` header swapped to a victim shop's domain (and, since it's also unsigned, an arbitrary `topic`/`webhook_id`) produces a request that still passes `HmacValidator.validate`, yet is now attributed by `Registry.process` to the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion at the webhook boundary: `request.shop == validated_shop` is assumed by every downstream handler, but the equality does not actually hold because `shop` is outside the HMAC's coverage. Any application built on this gem that uses `WebhookMetadata#shop` to key data writes (e.g., updating billing state, order records, uninstall flags, or a merchant's local settings) can be made to apply another shop's genuine event data to a victim shop's tenant record, or vice versa — a cross-tenant access/write primitive achievable by an ordinary, unprivileged owner of any shop that has the app installed.

### Likelihood Explanation
The attacker only needs to be a legitimate (non-privileged) merchant with the app installed on their own store to receive at least one real webhook delivery with a valid `(body, hmac)` pair; no access token, `client_secret`, or admin/leaked credential is required. They then need standard HTTP request capability to resend the webhook to the app's public webhook endpoint with a modified `shop`/`topic`/`webhook_id` header — no privileged access is needed. This depends on the host application actually trusting `WebhookMetadata#shop` for tenant attribution, which is the documented, expected usage of this API.

### Recommendation
Include the tenant-identifying headers (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the body (e.g., compute the HMAC over `shop + topic + webhook_id + raw_body`), so `HmacValidator.validate` fails whenever any of these header values are altered relative to what Shopify originally signed.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; Shopify sends a legitimate webhook:
   - headers: `shopify-topic: orders/create`, `shopify-hmac-sha256: <valid-hmac-of-body>`, `shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id": 123, ...}`
2. Attacker captures this `(body, hmac)` pair (they own this shop, so this is trivially observable — e.g., via their own webhook receiver logs).
3. Attacker resends the identical body and hmac to the app's public webhook endpoint but with `shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` computes `Utils::HmacValidator.validate(request)`, which only checks the body against the hmac — this still passes: [3](#0-2) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {...})` and processes attacker-controlled order data as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
