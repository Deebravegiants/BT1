### Title
Unprotected re-initialization of `LockupContract::new` allows attacker to become lockup owner and steal locked NEAR - (File: `lockup/src/lib.rs`)

### Summary
The `LockupContract::new` `#[init]` function in `lockup/src/lib.rs` does not guard against re-initialization the way every other production contract in this repository does. Every sibling contract (`lockup-factory`, `multisig`, `staking-pool-factory`, `staking-pool`, `voting`, `whitelist`) explicitly asserts `!env::state_exists()` at the top of its `new()` function before writing state, but `LockupContract::new` omits this check entirely. This is the same root-cause class as the external report's `SwapImpl::initialize` finding: an unprotected, callable-more-than-once initializer that lets an unprivileged caller overwrite critical state.

### Finding Description
`LockupContract::new` is marked `#[init]` and, unlike every other contract in the repo, contains no `assert!(!env::state_exists(), ...)` guard: [1](#0-0) 

Compare this with the identical initializer pattern that is present in `lockup-factory`, `multisig`, `staking-pool`, `whitelist`, and `voting`, all of which explicitly check for existing state before allowing initialization to proceed: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Because the entire codebase relies on this explicit `assert!(!env::state_exists(), ...)` pattern (rather than any implicit protection from the `#[init]` attribute alone at `near-sdk = "3.1.0"`), the absence of this same guard in `lockup/src/lib.rs` means `LockupContract::new` can be invoked again on an already-deployed and already-funded lockup account. Any unprivileged account can send a `FunctionCall` transaction targeting the deployed lockup account's `new` method, since NEAR does not restrict calling public contract methods based on caller identity unless the method itself checks `predecessor_account_id`. `new()` performs no such check: [7](#0-6) 

Re-invoking `new()` fully overwrites the `LockupContract` struct, including `owner_account_id`, `staking_pool_whitelist_account_id`, `vesting_information`, and `foundation_account_id`: [8](#0-7) 

An attacker can call `new()` a second time, supplying their own account as `owner_account_id`, a malicious/attacker-controlled `staking_pool_whitelist_account_id`, and `vesting_schedule: None` (bypassing any vesting/foundation-termination controls), thereby fully hijacking ownership and control of the lockup contract's funds.

### Impact Explanation
Once the attacker becomes `owner_account_id`, they gain access to all owner-privileged methods in `lockup/src/owner.rs` (staking pool selection, deposit/stake/unstake/withdraw, and — depending on the lockup/transfer schedule — transfer of released tokens). Combined with attacker-controlled `staking_pool_whitelist_account_id`, the attacker can whitelist and select an attacker-controlled "staking pool" contract and route the locked NEAR balance there. This is a critical, unauthorized takeover of a fund-holding contract by an unprivileged actor, matching the "Unauthorized transfer/withdrawal/release of locked... NEAR" and "Permanent freezing/irrevocable loss of user funds in lockup release" impact categories.

### Likelihood Explanation
Likelihood is high: the entry point is a plain, permissionless `FunctionCall` to a publicly known lockup account ID (lockup contracts are deployed at predictable, discoverable sub-accounts, e.g. via `lockup-factory`). No privileged role, signature, or special access is required — only the ability to send a transaction, which any account can do.

### Recommendation
Add the same reinitialization guard used throughout the rest of the codebase to `LockupContract::new`:

```rust
#[init]
pub fn new(
    owner_account_id: AccountId,
    ...
) -> Self {
    assert!(!env::state_exists(), "The contract is already initialized");
    ...
}
```

This mirrors the fix pattern already applied in `lockup-factory`, `multisig`, `staking-pool`, `staking-pool-factory`, `voting`, and `whitelist`.

### Proof of Concept
1. Foundation/lockup-factory deploys a `LockupContract` at `alice.lockup.near` and calls `new(owner_account_id: "alice.near", ...)`, funding it with locked NEAR.
2. Attacker (any unprivileged account, e.g. `attacker.near`) sends a `FunctionCall` transaction to `alice.lockup.near` calling `new` again with:
   - `owner_account_id: "attacker.near"`
   - `staking_pool_whitelist_account_id: "attacker-whitelist.near"` (an attacker-controlled whitelist contract)
   - `vesting_schedule: None`
   - `foundation_account_id: None`
3. Since `LockupContract::new` performs no `state_exists()` check and no caller check, the call succeeds and overwrites `owner_account_id` to `attacker.near`.
4. Attacker, now the recognized owner, calls owner-only methods (e.g. `select_staking_pool` against their own whitelist, then `deposit_and_stake`/`unstake`/`withdraw`) to redirect and extract the locked NEAR balance.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
