### Title
RAY value overflow in interest accrual permanently freezes a whale market - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
A permissionless caller can create a sufficiently large, highly utilized market position and later trigger `update_indexes(caller, assets)`, causing interest accrual to panic with `MathOverflow` while recomputing utilization from `borrowed * borrow_index`. [1](#0-0) [2](#0-1) 

Because every market mutation loads the same interest-synced cache before repayment, withdrawal, liquidation, or rescue accounting, the first accrual failure leaves `last_timestamp` unchanged and makes every later call fail at the same point. [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
`Controller::update_indexes` is callable by any authorized caller and forwards the caller-selected `Vec<HubAssetKey>` to the pool. [6](#0-5) 

The pool handler loads each market, runs `interest::global_sync`, and only then commits state. [7](#0-6) 

`global_sync` applies one or more `accrue_step` calls before advancing `last_timestamp`; each step must evaluate market utilization. [8](#0-7) 

`calculate_utilization` calls `scaled_to_original` on `borrowed * borrow_index` and `supplied * supply_index`, and the checked fixed-point helper panics with `MathOverflow` when the resulting `i128` value does not fit. [2](#0-1) [9](#0-8) 

The borrow and supply index caps do not prevent this failure because the value conversion overflows before either index reaches its configured cap. [10](#0-9) 

### Impact Explanation
This permanently freezes the affected `(hub_id, asset)` book: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad-debt cleanup cannot run because each path synchronizes interest first. [11](#0-10) [12](#0-11) 

Since the panic happens inside `global_sync` before `mark_accrued` or `commit`, the stale timestamp persists and retrying does not skip the overflowing interval. [13](#0-12) [14](#0-13) 

The repository’s regression test demonstrates the concrete terminal state: after `update_indexes` fails with `MATH_OVERFLOW`, both a one-unit withdrawal and a repayment fail with the same error. [15](#0-14) 

### Likelihood Explanation
The attack is permissionless but economically expensive: an attacker must build a very large supplied book, maintain approximately 98% utilization, and wait for index growth to make the RAY-valued aggregate exceed `i128::MAX`. [16](#0-15) 

The attacker can use ordinary `supply`, `borrow`, and `update_indexes` entrypoints; no privileged role, malformed external dependency, oracle manipulation, or contract upgrade is required. [6](#0-5) [17](#0-16) 

The required market size and multi-year accrual window reduce the likelihood to Medium rather than making the attack immediate. [18](#0-17) 

### Recommendation
Handle aggregate-value overflow as an accrual boundary condition instead of panicking, for example by clamping utilization at `RAY` when debt or supply value exceeds the representable range and by enforcing a market-level maximum RAY value before the overflowing multiplication. [2](#0-1) 

Add a regression test proving that after the value ceiling is reached, `update_indexes`, `withdraw`, `repay`, liquidation, and `seize_positions` remain executable or fail only through an explicit recoverable policy. [15](#0-14) 

### Proof of Concept
The existing harness scenario constructs an 18-decimal market with `1e9` tokens supplied, borrows 98% of it against separate collateral, advances time in one-year increments, and invokes the permissionless index update until accrual fails. [19](#0-18) 

At that point the committed borrow index remains below `MAX_BORROW_INDEX_RAY`, while both `withdraw` and `repay` still panic with `MATH_OVERFLOW`, proving permanent loss of access rather than a single rejected transaction. [10](#0-9)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

    t.supply_raw(BOB, "BIG18", principal);
