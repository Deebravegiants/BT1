## Title
Commission rounding-to-zero in `staking_contract::update_distribution_pool` lets a staker permanently deny operator commission on unlocked stake — ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::update_distribution_pool` re-prices every existing shareholder's position in the `distribution_pool` whenever its `total_coins` changes, and transfers the shareholder's owed commission to the operator by converting a computed `unpaid_commission` coin amount into shares via `pool_u64::amount_to_shares_with_total_coins`, which floors. This is structurally the same bug class as the Salty.IO `StakingRewards._decreaseUserShare` finding: a value that should be deducted/transferred from the user is computed with floor rounding and can be driven to zero by choosing small enough deltas, letting the user (the staker) permanently avoid paying part of what they owe. [1](#0-0) 

### Finding Description
Every time `add_distribution` (called from `unlock_stake`, `switch_operator`, `request_commission_internal`, etc.) or `distribute_internal` runs, it calls `update_distribution_pool(distribution_pool, updated_total_coins, operator, commission_percentage)`. For each non-operator shareholder it computes:

```
let current_worth = pool_u64::shares_to_amount_with_total_coins(distribution_pool, shares, updated_total_coins);
let unpaid_commission = (current_worth - previous_worth) * commission_percentage / 100;
let shares_to_transfer = pool_u64::amount_to_shares_with_total_coins(distribution_pool, unpaid_commission, updated_total_coins);
pool_u64::transfer_shares(distribution_pool, shareholder, operator, shares_to_transfer);
``` [2](#0-1) 

`unpaid_commission` is already floored by integer division (`* commission_percentage / 100`), and `shares_to_transfer` is floored again by `amount_to_shares_with_total_coins` (`pool_u64::multiply_then_divide` → `math64::mul_div`, floor division). Both roundings favor the staker: if the value increase (`current_worth - previous_worth`) per invocation is small enough that either intermediate calculation floors to 0, `shares_to_transfer` becomes 0 and no shares move from the staker to the operator for that increment.

This is exactly the invariant broken in the Salty.IO report: a "virtual" amount that should be subtracted from a user's claimable balance (there: `virtualRewardsToRemove`; here: `unpaid_commission`/`shares_to_transfer`) is computed with floor rounding on a per-call basis, and the caller controls how the operation is split into calls. `update_distribution_pool` is reachable indirectly by the staker through repeated `add_stake`/`unlock_stake`-style flows that funnel into `add_distribution`, each of which recomputes `current_worth - previous_worth` from scratch against the pool's `updated_total_coins`.

### Impact Explanation
If a staker can trigger many small `add_distribution` events (e.g., by unlocking stake in a sequence of tiny amounts as rewards trickle in, or by timing `switch_operator`/`request_commission` calls around small reward increments) such that each individual `current_worth - previous_worth` slice rounds `unpaid_commission`/`shares_to_transfer` down to 0, the staker keeps 100% of shares in the `distribution_pool` that should have been partially transferred to the operator as commission. Repeated across many epochs/calls, this durably diverts commission value away from the operator to the staker — a custody/accounting corruption that moves value to the wrong holder (the staker keeps distribution-pool shares that the operator is contractually owed), directly analogous to the confirmed Salty.IO issue.

### Likelihood Explanation
Exploitability is bounded by how "chunky" reward accrual is relative to `commission_percentage`: because Aptos stake amounts are in octas (10^-8 APT) and epochs pay out relatively large aggregate rewards, driving `(current_worth - previous_worth) * commission_percentage / 100` to exactly 0 across many consecutive calls requires the staker to force very fine-grained recomputation windows (e.g. repeated `unlock_stake` calls of a few octas each, or interleaving `switch_operator`/`add_stake` calls tightly) and a commission percentage set such that rounding is achievable at practical unit sizes. I could not fully trace `unlock_stake`'s exact interaction with `add_distribution` (call not shown before iteration limit was reached) to confirm the precise conditions under which a staker can force many `update_distribution_pool` invocations with sub-threshold deltas at will versus only at coarse-grained points (e.g., once per lockup cycle). Without that confirmation, the practical, at-scale exploitability (as opposed to the mathematical rounding weakness, which is real and reachable from framework code) remains unverified.

### Recommendation
Round `unpaid_commission` and `shares_to_transfer` up (ceiling) rather than down when computing what to transfer from a shareholder to the operator in `update_distribution_pool`, mirroring the Salty.IO fix of rounding `virtualRewardsToRemove` up. Alternatively, track commission owed as a running fractional remainder (dust-carry) across calls so that repeated small deltas cannot systematically bypass commission transfer.

### Proof of Concept
Conceptual PoC (not executed, derived from code reading):
1. Staker creates a staking contract with `commission_percentage = 10`.
2. Instead of calling `unlock_stake`/`add_stake` once for the full reward amount, staker calls it repeatedly with amounts such that each individual `current_worth - previous_worth` computed inside `update_distribution_pool` is under `10` octas (so `* 10 / 100 == 0`), or precisely tuned so the subsequent `amount_to_shares_with_total_coins` floors `shares_to_transfer` to 0.
3. Each such call returns from `update_distribution_pool` without transferring any shares to the operator, while `distribution_pool.update_total_coins(updated_total_coins)` still advances, permanently "banking" the un-transferred worth increase under the staker's shares.
4. Repeating this over many reward-accrual cycles lets the staker accumulate distribution-pool value without ever paying the operator's commission on it, even though `staking_contract.principal`/commission accounting elsewhere assumes commission was charged on every increment. [1](#0-0) [3](#0-2)

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }

    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
