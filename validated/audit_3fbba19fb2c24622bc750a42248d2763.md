### Title
Malicious swap route can execute arbitrary contract code under the caller’s authorization tree and drain unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
XOXNO Lending strategy entrypoints forward caller-controlled route bytes to the configured router while the original account owner’s authorization remains active. Because route-selected pool addresses can invoke additional token transfers during that call, an attacker can craft a route whose venue contract performs an unrelated `transfer(victim, attacker, amount)` from the victim. Soroban simulation records that transfer as a child authorization under the victim’s `swap_collateral` invocation; if the victim signs the simulated authorization tree, the unrelated wallet transfer executes.

### Finding Description
`swap_collateral` authenticates the supplied `caller` and verifies that the caller owns or delegates the target account before processing the swap. [1](#0-0) 

The strategy then withdraws collateral to the controller and passes the caller-supplied `swap` bytes to `swap_tokens_or_passthrough`. [2](#0-1)  For distinct tokens, that helper invokes the configured router inside a flash guard. [3](#0-2) 

The controller narrowly authorizes only its own exact input transfer to the router and measures input/output deltas afterward. [4](#0-3)  Those checks bound the controller’s routed assets, but they do not constrain what other calls route-selected venue code makes while the caller’s root authorization is active.

The included adversarial test models the production router boundary: its router decodes a route-selected `hop_pool`, calls that pool, and pays fair output. [5](#0-4)  The malicious pool then calls a token transfer from the victim to the attacker for a token unrelated to the lending position. [6](#0-5) 

Simulation places the malicious wallet transfer under the victim’s `swap_collateral` authorization entry rather than reporting it as a separate top-level authorization. [7](#0-6)  When the victim signs the recorded tree, the unrelated wallet token is transferred to the attacker while the lending swap itself completes successfully. [8](#0-7) 

### Impact Explanation
A successful exploit can steal any token balance held by the strategy caller, including tokens that are not listed by XOXNO and are unrelated to the position being modified. The protocol’s balance-delta checks, route minimum output, and final account health checks do not bound this loss because they inspect only the controller’s input/output balances and account state.

The caller must sign the poisoned authorization tree, so this is authorization-tree injection rather than an unauthenticated balance change. The impact is still direct theft of user funds, and the signed tree may appear to be normal router authorization unless the wallet or client decodes and compares every nested invocation.

### Likelihood Explanation
The attack requires the victim to submit an attacker-supplied route and authorize the exact tree returned by simulation. That precondition lowers exploitability compared with a purely permissionless protocol flaw.

However, route bytes are opaque to ordinary users and are normally generated off-chain. A malicious quote, compromised route source, deceptive integration, or attacker-provided “custom route” can produce a transaction that economically succeeds while adding a hidden child transfer. The included test demonstrates that recording-mode simulation produces and accepts the poisoned tree, and that enforcement succeeds once that tree is signed. [9](#0-8) 

### Recommendation
Do not allow strategy route bytes to select arbitrary venue contract addresses that execute inside the caller’s authorization context. Bind executable venue addresses to a governance-controlled registry of audited pool contracts, or otherwise prove that each venue implementation cannot make calls requiring the caller’s authorization.

Until routes can be constrained on-chain, clients and wallets must decode both the route and the complete simulated authorization tree, and reject any child invocation other than the expected lending input settlement. This mitigates user signing but does not remove the protocol-level arbitrary-code execution surface.

### Proof of Concept
The repository contains an executable proof in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice owns a debt-free account with USDC collateral and holds an unrelated `wallet_token`.
2. The test registers a router whose `execute_strategy` pulls the configured input, invokes the payload-selected `hop_pool`, and returns a fair ETH output. [10](#0-9) 
3. The payload names an attacker-controlled pool whose `swap` method invokes `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [6](#0-5) 
4. Alice calls `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, malicious_route)`. [11](#0-10) 
5. Simulation records the stolen token transfer as a child of Alice’s `swap_collateral` authorization. [12](#0-11) 
6. Signing that tree results in Alice’s unrelated wallet balance becoming zero and the attacker receiving `WALLET_BALANCE`, while Alice still receives the expected ETH collateral output. [13](#0-12)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
