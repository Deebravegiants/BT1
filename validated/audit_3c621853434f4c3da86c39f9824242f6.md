### Title
Webhook Shop Identity Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via HMAC, but the HMAC signature only covers the raw request body — it never covers the `shopify-shop-domain` or `shopify-topic` headers that the gem hands to the application's webhook handler as the trusted identity of the event. This mirrors the reported bug class: a field the system acts on (`shop`, `topic`) is not covered by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it to the `shopify-hmac-sha256` header: [2](#0-1) 

However, `Registry.process` uses `request.shop` and `request.topic` — both derived directly from unauthenticated, attacker-controlled HTTP headers — to build the `WebhookMetadata` passed to the app's handler, after only checking that the HMAC matches the body: [3](#0-2) 

`shop` and `topic` are parsed straight from headers with no cryptographic binding to the body or to each other: [4](#0-3) 

Because the app's `client_secret` (the HMAC key) is the same across every shop that installs the app, any merchant who installs the app can receive a legitimately-signed webhook body+HMAC pair for their own shop, then replay that exact body/HMAC while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header to any value they choose. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, so `Registry.process` will dispatch the handler believing the event legitimately originated from — or is scoped to — the spoofed shop/topic.

This breaks the intended identity equality: `shop_identity_trusted_by_handler == shop_identity_cryptographically_verified`. In this gem, the left side comes from the raw header value, while the right side is never actually checked.

### Impact Explanation
This is a cross-tenant identity binding failure: any actor capable of installing the app (an "unprivileged" but real installer) can forge the `shop`/`topic` fields delivered to the host application's webhook handler while still passing this gem's own signature check. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., looking up or mutating per-shop data, honoring `shop/redact` or `customers/redact` compliance topics, gating access by shop), this enables cross-tenant data manipulation or spoofed mandatory-compliance events attributed to a shop the attacker does not own.

### Likelihood Explanation
Any user able to install the app on a shop can obtain a validly-signed body/HMAC pair from their own webhook deliveries and replay it against the app's public webhook endpoint with modified `shopify-shop-domain`/`shopify-topic` headers. No access to `client_secret`, tokens, or privileged accounts is required — only reachability of the webhook endpoint and the ability to receive one legitimate webhook, which is available to anyone who installs the app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by re-deriving/validating `shop` against session/token data already known to the host app) so the HMAC check authenticates the full identity tuple the handler relies on, not just the JSON body bytes.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B`), `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: T`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and same `shopify-hmac-sha256: H`, but set `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `shopify-topic`).
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "T-or-forged", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if the event came from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
