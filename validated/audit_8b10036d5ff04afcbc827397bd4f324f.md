### Title
Deflationary/fee-on-transfer underlying tokens cause unbacked minting and vault insolvency in `WrappedHyperFungibleToken` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom` for `params.amount`, then dispatches a cross-chain message containing that same nominal `amount`, without verifying that the vault's balance actually increased by that amount.

### Finding Description
In `send()`, the amount used to build the outgoing message (`_buildDispatchPost`) is `params.amount` taken directly from user input, not the amount actually received by the contract: [4](#0-3) . If `_underlying` is a fee-on-transfer/deflationary token, `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` causes the contract to receive less than `params.amount`, yet the dispatched `Message.amount` — and thus the amount minted on the destination `HyperFungibleToken` via `_mint(beneficiary, message.amount)` — equals the full, unreduced `params.amount` [5](#0-4) . This is the same class of bug flagged in the referenced report: no before/after balance check around the token transfer to account for transfer-time fee deduction. Notably, the codebase already has a fix pattern for exactly this issue in `IntentGatewayV2.placeOrder`, which snapshots `balanceOf` before and after `safeTransferFrom` and updates `order.inputs[i].amount` to the actually-received amount [6](#0-5)  — this same pattern is absent from `WrappedHyperFungibleToken.send()`.

Additionally, on the unlock/refund side, `onAccept` and `onPostRequestTimeout` call `safeTransfer(beneficiary, message.amount)` for the full nominal amount [7](#0-6) , further amplifying any shortfall each time value round-trips through the vault.

### Impact Explanation
Over repeated `send()` calls with a deflationary underlying, the cumulative supply minted on remote `HyperFungibleToken` deployments exceeds the actual token balance locked in `WrappedHyperFungibleToken`. This is an unbacked-mint condition: remote-chain token holders collectively hold claims exceeding the real collateral, so later `onAccept`/unlock calls attempting to pay out the full nominal `message.amount` can drain the vault faster than it is funded, causing legitimate unlock requests to fail (permanent freezing of funds for some users) once the vault is undercollateralized. Since any user can call `send()` with any ERC20 configured as `_underlying` by the owner, this is reachable without any privileged action once such a token is configured.

### Likelihood Explanation
Likelihood depends on the owner configuring a fee-on-transfer/rebasing/deflationary token as `_underlying` via `configure()` (owner-controlled, not attacker-controlled) [8](#0-7) . Given many real-world tokens (e.g., some stablecoins with fee-switch capability, various DeFi rebasing tokens) fall into this class, and the docs describe `WrappedHyperFungibleToken` as a general-purpose wrapper for "existing ERC20 tokens" without restricting to standard-compliant tokens, deployment against such a token is plausible in production use.

### Recommendation
In `send()`, measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call, and use the actual received delta (not `params.amount`) when building the dispatched `Message.amount`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Alternatively, explicitly document and enforce (e.g., via a check or allowlist) that only tokens with standard, unmodified transfer semantics may be configured as `_underlying`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer token that deducts, say, 2% on every `transferFrom`.
2. User A calls `send({ amount: 1000, ... })`. The contract's `safeTransferFrom` pulls 1000 nominal tokens but the contract's balance only increases by 980 (2% fee burned/redirected). `_buildDispatchPost` still encodes `Message.amount = 1000`.
3. The ISMP message is delivered to the destination chain; `HyperFungibleToken.onAccept` mints `1000` tokens to the beneficiary — 20 more than what is actually backed in the vault.
4. Repeating this process compounds the shortfall. Eventually, when remote holders burn tokens and request unlock back on the home chain, `onAccept`'s `safeTransfer(beneficiary, message.amount)` cannot be fully satisfied because `_underlying.balanceOf(address(this))` is less than the sum of nominal amounts owed, causing the transfer to revert and freezing funds for whichever unlock request is processed once the shortfall is exhausted.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
