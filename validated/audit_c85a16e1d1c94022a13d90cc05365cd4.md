## Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop-domain` header to attribute the webhook to a tenant. Because the HMAC signable string never includes the shop identifier, an attacker who can obtain one legitimately-signed webhook (by installing the app on their own store) can replay that exact body/signature pair while substituting a different `shop-domain` header, causing the app to process a forged webhook as if it originated from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers with no cryptographic binding to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Webhooks::Registry.process` uses this validation as its sole authentication gate, and then immediately forwards the unauthenticated `request.shop` value to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop used to attribute/process the webhook == shop whose bytes were HMAC-authenticated`

But the actual binding enforced is only:
`HMAC(raw_body, api_secret_key) == received signature`

with `shop` sourced from an entirely separate, unauthenticated channel (the `shop-domain` header). Since a single app's `api_secret_key` is shared across every shop that installs the app, any shop (including one controlled by an attacker) can legitimately receive a validly-signed webhook body from Shopify. The attacker can then replay that body and its valid HMAC to the app's webhook endpoint while swapping the `shop-domain` (and/or `webhook-id`/`topic`) header to point at a victim shop domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant/shop identity binding, letting an unprivileged attacker (merely an app installer on their own shop) inject arbitrary webhook events attributed to a different, victim shop into the host application's webhook handler. Depending on how the host app's handler uses `data.shop` (e.g., `app/uninstalled` to wipe stored credentials, `orders/create` to inject fraudulent order data, `shop/redact` to trigger data deletion), this is a cross-tenant access/spoofing primitive — matching the "cross-tenant access" Critical impact category, since the gem itself performs no verification tying the claimed shop to the authenticated bytes.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned/controlled shop (an ordinary, unprivileged action any Shopify user can take for a public app), (2) capturing one legitimately Shopify-signed webhook delivery, and (3) replaying it to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged credential is needed — the attacker relies entirely on the shared per-app secret already used to sign their own legitimate webhook traffic.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the claimed `shop-domain` header to a value the app already trusts (e.g., cross-check against a shop that has a valid stored session/access token for this app before processing), rather than trusting the header value populated by `Webhooks::Request#shop` outright in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, which is a normal, unprivileged registration flow.
2. Shopify sends a legitimately-signed webhook (e.g., `orders/create`) to the app's webhook endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body with the app's api_secret_key>`, `x-shopify-topic: orders/create`
   - Body: attacker-controlled order JSON (attacker fully controls the content of their own shop's orders).
3. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `Registry.process` recomputes `HMAC(raw_body, api_secret_key)` — it matches, because it never considers the `shop-domain` header: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, and the host app processes it believing it originated from the victim shop.
