This is exactly the analog: an unprivileged internet user can break the binding **HMAC-verified bytes == the shop/topic bytes the app trusts and acts on**.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are unauthenticated (not covered by HMAC) yet are trusted for dispatch and tenant attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#hmac`/`to_signable_string` only signs and verifies `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` values are read directly from HTTP headers and are never included in the HMAC-signed data [2](#0-1) . `Registry.process` validates only the body's HMAC, then dispatches the handler using the unauthenticated `request.topic` and `request.shop` [3](#0-2) .

### Finding Description
This mirrors the reported bug class: a value that is *acted upon* (here, tenant/topic identity used for handler dispatch and business logic) is not the value that was *cryptographically verified* (here, only the raw body bytes). Root cause equality that should hold but doesn't:

`bytes verified by HMAC` == `bytes the app treats as the authenticated shop/topic`

Before attacker action: legitimate Shopify webhook — headers `shopify-shop-domain`, `shopify-topic` are attacker-uncontrolled because the whole HTTP request (headers + body) originates from Shopify's infra over a channel the app owns.

After attacker action: an unprivileged internet user who can send arbitrary HTTP requests to the app's webhook endpoint (this is a public endpoint by design) can craft a request whose body byte-content happens to produce a valid HMAC for *some* legitimate historical webhook body (e.g., if the app ever logs/echoes a raw body+HMAC pair, or a body is reused/replayable since the raw body alone is what's checked) but pair it with attacker-chosen `shopify-shop-domain` and `shopify-topic` headers, since those headers are completely outside the signed data. `HmacValidator.validate` only checks `to_signable_string` (raw body) against the secret [4](#0-3) ; it has no knowledge of, and does not bind, the shop or topic headers.

Because `WebhookMetadata` is built directly from `request.shop` and `request.topic` and handed to the app's handler as the authenticated tenant/topic [5](#0-4) , any handler that uses `data.shop` to select which merchant's session/DB row to update, or `data.topic` to decide the operation, is acting on attacker-controlled identity data that was never covered by the cryptographic check the gem performs.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to establish. If replay of a captured legitimate body (same bytes, valid signature) is combined with a forged shop header, the app can be induced to attribute a webhook event to the wrong merchant/tenant — a cross-tenant data integrity/confusion issue in the calling application, since the gem's own `Registry.process` and `Request` class provide no assurance that `shop`/`topic` are authentic. This aligns with the High-impact category "credential leakage / cross-tenant" risk pattern to the extent host apps rely on `WebhookMetadata#shop` as an authenticated value, which the documented API implicitly encourages by exposing it as part of the verified request object.

### Likelihood Explanation
Medium: it requires the attacker to obtain a valid `(raw_body, hmac)` pair (e.g., via network capture, log exposure, or a previously delivered webhook they control content for, such as an app-uninstalled/customer-data webhook where body content is attacker-influenceable) and replay it with forged headers. It does not require the `client_secret` itself, only a captured signature over content the attacker can influence or reuse — consistent with the "bytes verified vs. bytes parsed/acted on" analog class permitted by the rules.

### Recommendation
Include `shop`, `topic`, and `webhook_id` header values inside the HMAC-signed material (or otherwise cryptographically bind them, e.g., derive an HMAC over the canonical header+body string) in `Webhooks::Request#to_signable_string`, so that `HmacValidator.validate` fails if any of these identity-bearing fields are altered independently of the body.

### Proof of Concept
1. Attacker captures/derives a legitimate `(raw_body="{}", shopify-hmac-sha256=<valid for "{}">)` pair (e.g., from a webhook with attacker-influenced empty/known body content, or a leaked log line).
2. Attacker sends a POST to the app's webhook endpoint with headers:
   - `shopify-topic: app/uninstalled` (or any registered topic)
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-hmac-sha256: <the captured valid signature for body "{}">`
   - body: `{}`
3. `HmacValidator.validate(request)` succeeds because it only checks the body bytes [6](#0-5) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , and any handler logic keyed on `data.shop`/`data.topic` operates on attacker-chosen identity, despite the HMAC check having "passed."
