## Title
Unbounded `DispatchPost.body`/`to`/`dest` length allows gas-griefing DOS of message delivery — (File: `evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatch(DispatchPost)` accepts an arbitrary-length `body`, `to`, and `dest` with no size cap, and stores/commits it via `request.hash()` (ABI-encode + keccak256 over the whole struct). This mirrors the Hats `details`/`imageURI` bug class: cheap-to-write, unbounded-length payload that is later re-encoded/re-hashed by a party who does not control the size, causing outsized gas costs at delivery time.

## Finding Description
`dispatch(DispatchPost memory post)` builds a `PostRequest` directly from `post.body` (and `post.to`) with no length validation, and computes `commitment = request.hash()`: [1](#0-0) 

This is the pattern flagged in Hats: any unprivileged caller (an app contract acting on behalf of an EOA) can dispatch a request whose `body` is arbitrarily large. On a low-gas-cost source chain, an attacker can cheaply construct a request whose body is, e.g., hundreds of KB.

That request must later be re-hashed and delivered on the destination chain by `HandlerV2.handlePostRequests`, which loops over a *batch* of leaves and computes `leaf.request.hash()` for each one to build the MMR multiproof leaves before verifying and dispatching to the destination `IApp`: [2](#0-1) 

Unlike the Hats case (a pure view function), here the cost is paid by whichever relayer chooses to submit the batch. But — critically — `handlePostRequests` processes a *batch* of leaves in a single transaction (`requestsLen` loop, `leaves[i]`), and other users' legitimate, fee-paying requests can be bundled together with the malicious oversized one in the same MMR multiproof for gas efficiency, as the relayer implementation does when generating contract calls: [3](#0-2) 

If one attacker-controlled request in a batch is bloated enough to blow the destination chain's block gas limit (or make estimateGas prohibitively expensive), the whole batch reverts/fails to execute, which can starve or delay delivery of otherwise legitimate, already-fee-escrowed requests bundled alongside it — the same "make it expensive/impossible for someone else to process" mechanism as the Hats report, just relocated from a view-function reader to a batched relayer-delivery path.

I found no length bound on `DispatchPost.body`/`to`/`dest` anywhere in `EvmHost.sol`'s `dispatch()`, nor in the Substrate-side `pallet_ismp::dispatcher::dispatch_request` (`modules/pallets/ismp/src/dispatcher.rs:92-152`), which likewise passes `dispatch_post.body` straight through into the committed `PostRequest` with no size check: [4](#0-3) 

By contrast, the codebase does demonstrate awareness of this exact bug class elsewhere: `BandwidthManager.purchase()` explicitly bounds its own `app` parameter (`MAX_APP_LENGTH = 32`) specifically because the receiving pallet enforces a bound and unbounded input would let a payer be charged for a message that can never be credited: [5](#0-4) 

No equivalent bound exists for the generic `DispatchPost.body`/`to`/`dest` fields used by the core dispatch path.

## Impact Explanation
An unprivileged dispatcher can submit a POST request with an oversized `body`/`to`/`dest`. Because delivery is batched via `HandlerV2.handlePostRequests`, this can be used to:
- Force relayers to spend far more gas than expected to re-encode/hash the malicious leaf while proving/delivering a batch, discouraging relayers from batching (or relaying at all) and delaying/failing delivery of legitimately fee-paying, co-batched requests — a route-unable-to-deliver-messages condition for affected users.
- On low-cost source chains, cause the same "cheap to write, expensive to process" asymmetry documented in the referenced Hats finding, but applied to a permissionless relayer-facing pipeline instead of a pure view getter.

This does not directly enable theft or unbacked minting, but it can degrade or block message delivery for other users sharing a batch, which the validation rubric treats as a legitimate "route unable to deliver messages" impact class.

## Likelihood Explanation
Feasibility depends on: (1) whether a source-chain deployment has cheap-enough gas to write a sufficiently large `body` (as in the original Hats report, Polygon-class chains are the concern, not Ethereum mainnet); and (2) whether relayers actually batch untrusted third-party requests together rather than delivering them individually. The core contract itself imposes no defense-in-depth cap, so the likelihood is entirely a function of relayer batching behavior and destination-chain gas economics, which I cannot fully verify from the indexed code (relayer batching heuristics beyond `tx.rs` were not further inspected).

## Recommendation
Introduce an explicit maximum length for `DispatchPost.body`, `to`, and `dest` (and the Substrate-side `DispatchPost.body`) enforced in `EvmHost.dispatch()` and `pallet_ismp::dispatch_request`, sized so that a single request's re-encode/hash cost stays a small, bounded fraction of the destination chain's block gas limit — mirroring the `MAX_APP_LENGTH` pattern already used in `BandwidthManager.sol`. Additionally, consider capping per-batch cumulative body size in `HandlerV2.handlePostRequests`/`handleGetResponses` so a single oversized leaf cannot degrade delivery of other bundled requests.

## Proof of Concept
Conceptual (not executed against the indexed repo, since no local reproduction environment is available):
1. Attacker calls an app contract that forwards to `IDispatcher(host).dispatch(DispatchPost{ body: <N-byte blob>, ... })` with `N` sized to approach the destination chain's per-tx/block gas limit when re-hashed and ABI-decoded.
2. A relayer batches this request together with several legitimate pending POST requests into one `HandlerV2.handlePostRequests` call to amortize consensus-proof/MMR-proof gas costs.
3. The oversized leaf's `request.hash()` computation and/or destination `onAccept` decoding pushes the batch's gas usage past the block gas limit or past what is economical for the relayer, causing the whole batch (including the legitimate requests) to fail or be excluded, delaying/blocking their delivery.

I was not able to find or run an existing Foundry/Rust test in the indexed codebase that specifically exercises this batched-body-size DOS scenario, so likelihood/impact should be validated with an actual gas-limit PoC before treating this as confirmed exploitable in production configurations.
