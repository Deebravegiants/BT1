### Title
Pool reserves are derived directly from live SPL vault balances, enabling donation-based reserve manipulation - ([File: program/src/math.rs], [File: program/src/processor.rs])

### Summary
Every swap, deposit, and withdraw instruction in the AMM computes the pool's effective reserves (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) directly from the live SPL token balances of `amm_coin_vault`/`amm_pc_vault`, rather than from an internally-tracked reserve value that is only updated through the program's own accounted instructions. This is the same root-cause pattern as the Nitron incident: a protocol reading a raw, externally-writable balance as its pricing input, allowing anyone to "donate" tokens straight into the vault (bypassing `Deposit`) to skew the ratio consumed by subsequent swap pricing and LP-mint/redeem math.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` takes `pc_amount`/`coin_amount` and simply subtracts the pending PnL, with no validation that these amounts correspond to an internally tracked reserve: [1](#0-0) 

Every caller feeds it the values from `Self::unpack_token_account(&amm_coin_vault_info, ...).amount` / `amm_pc_vault_info.amount` — i.e., the raw, current SPL balance of the vault accounts read at instruction time:
- In swap (`process_swap_base_in`): [2](#0-1) 
- In swap v2 variants (`process_swap_base_in_v2`/`process_swap_base_out_v2`): [3](#0-2) 
- In deposit (`process_deposit`): [4](#0-3) 
- In withdraw path (`total_pc_without_take_pnl`/`total_coin_without_take_pnl` computed the same way before `InvariantPool` math): [5](#0-4) 

`amm_coin_vault_info`/`amm_pc_vault_info` are ordinary SPL Token accounts whose owner is the pool's `$authority` PDA. Nothing prevents an unrelated party from issuing a plain `spl_token::instruction::transfer` (fully outside the Raydium program, no signature from the AMM authority required — SPL `transfer` only requires the *source* owner to sign) directly into these vault addresses. Such a transfer increases the on-chain token balance with **no corresponding update** to `amm.lp_amount` or `TargetOrders.calc_pnl_x/y`, since those fields are only mutated inside the program's own `Deposit`/`Withdraw`/`Swap` handlers. The very next `Deposit`, `Withdraw`, or `Swap` in the same block then computes reserves, price, and `mint_lp_amount`/`out_coin`/`out_pc` off this attacker-inflated balance:
- LP mint sizing uses `InvariantPool::exchange_token_to_pool` against `amm.lp_amount` and the (now-donated) `total_coin_without_take_pnl`: [6](#0-5) 
- LP redemption sizing uses `InvariantPool::exchange_pool_to_token` similarly: [7](#0-6) 
- Swap output uses `swap_token_amount_base_in`/`_out` off the same donated totals: [8](#0-7) 

This is exactly the class of bug in the Nitron incident: an oracle/pricing input sourced from a raw balance an outsider can write to, without any accounting reconciliation.

### Impact Explanation
Because `amm.lp_amount` is a separately tracked field decoupled from the vault's live balance (see `process_initialize2`, where `amm.lp_amount` is set to the full `liquidity` value while a smaller `user_lp_amount = liquidity - 10^decimals` is actually minted to the depositor [9](#0-8) ), any attacker who can inflate the vault balance without minting LP can distort the coin/LP exchange rate. Combined with round-toward-zero LP minting logic, a depositor's `mint_lp_amount` can be pushed toward significantly fewer LP tokens than their contribution warrants right after a donation, transferring value to whichever party already holds the outstanding LP supply (which the attacker can control on a freshly created or thin pool). The same donated-balance skew also distorts swap output/input calculations for any swap executed after the donation, enabling price manipulation against the next trader/depositor/withdrawer in the pool.

### Likelihood Explanation
Exploitation requires no special privileges — a plain SPL token transfer to the pool's public vault address, combinable in the same transaction as the victim's `Deposit`/`Swap`/`Withdraw` (or immediately preceding it). It is most impactful on newly created or low-liquidity pools where `amm.lp_amount` is small and easily skewed, matching typical "first depositor"/thin-pool conditions.

### Recommendation
Do not treat the live SPL balance of `amm_coin_vault`/`amm_pc_vault` as ground truth for reserve/pricing math. Track coin/pc reserves internally in `AmmInfo` (updated only through the program's accounted `Deposit`/`Withdraw`/`Swap` paths) and reconcile against the vault balance only to detect/reject unexpected external transfers (e.g., require vault balance == tracked reserve + pending fees before proceeding, or clamp usable reserves to the tracked value rather than the raw balance).

### Proof of Concept
1. Attacker identifies (or creates) a Raydium pool with a small `amm.lp_amount` and holds a large share of the outstanding LP supply.
2. Attacker submits a standalone `spl_token::instruction::transfer` sending tokens directly into `amm_coin_vault` (or `amm_pc_vault`) — no Raydium instruction involved, no signature from the AMM authority needed.
3. In the same or the next transaction, a victim calls `Deposit`; `process_deposit` reads the now-inflated `amm_coin_vault.amount`/`amm_pc_vault.amount` via `calc_total_without_take_pnl_no_orderbook` (processor.rs:1148-1153) and computes `mint_lp_amount` using `InvariantPool::exchange_token_to_pool` (processor.rs:1243-1250) against the unchanged `amm.lp_amount`, minting the victim disproportionately fewer LP tokens for their deposited value.
4. Attacker calls `Withdraw` with their LP holdings; `InvariantPool::exchange_pool_to_token` (processor.rs:1751-1761) pays out coin/pc proportional to the now-larger vault balance (which includes both the donation and the victim's under-priced deposit), letting the attacker recapture value beyond what they donated.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
