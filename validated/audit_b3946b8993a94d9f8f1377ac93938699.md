### Title
Webhook shop/topic identity spoofing — HMAC signs only the raw body, not the `shop-domain`/`topic` headers used to route/attribute the event ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook solely by HMAC-validating `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read straight from attacker-visible/attacker-suppliable HTTP headers, are never included in the signed payload, yet `Registry.process` binds the (verified) body to the (unverified) `shop`/`topic` when it calls the merchant's handler.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the supplied `hmac`, [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`; the identity fields are exposed via separate header accessors (`shop`, `topic`, `webhook_id`, `api_version`) that are **not** part of the signed string [2](#0-1) .

`Registry.process` validates only the body HMAC and then trusts the unauthenticated `request.topic` and `request.shop` to build the event handed to the merchant's webhook handler: [3](#0-2) 

The identity binding that should hold is:
`HMAC-verified(raw_body)` ⇒ `(shop, topic)` used to process that body — but the gem only proves `HMAC(secret, raw_body) == received_hmac`; it never proves `HMAC(secret, raw_body ∥ shop ∥ topic) == received_hmac`. This breaks the equality `shop_bound_by_signature == shop_used_by_handler`.

Because the HMAC secret (`Context.api_secret_key`, the app's client secret) is shared across every shop that installs the app, any unprivileged party who can install the app on their own (e.g., free/dev) store legitimately receives real webhook deliveries with a valid `raw_body` + `hmac` pair for their own shop's events. Since `shop-domain` and `topic` are not covered by the signature, that same valid `(raw_body, hmac)` pair can be replayed to the same endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a victim shop. `Utils::HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` passes the forged `shop`/`topic` straight into `WebhookMetadata`, deceiving the app into believing the event (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`) originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: an attacker who is nothing more than an installer of the app on their own store can make the app process arbitrary attacker-chosen webhook bodies under an arbitrary victim shop's identity/topic, without ever needing the victim's credentials, `api_secret_key`, or access token. Depending on what the host app's webhook handlers do with `shop`/`topic` (e.g., trigger uninstall cleanup, GDPR redact flows, or update per-shop state keyed by `shop`), this can produce cross-tenant data corruption or a forced uninstall/redact against a shop the attacker doesn't control — a Critical-class cross-tenant access issue per the specified impact criteria.

### Likelihood Explanation
High. Only two publicly obtainable things are needed: (1) install the target app on any store the attacker controls to receive one legitimately signed webhook, and (2) send an HTTP POST to the app's public webhook endpoint with the captured `raw_body`/`hmac-sha256` header unchanged but `shop-domain`/`topic` headers swapped. No secret material, tokens, or privileged access are required, and the vulnerable code path (`Request.new` + `Registry.process`) is exactly the pattern documented for host apps to use.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` (whichever fields the handler trusts) in the HMAC-signed material for webhooks — i.e., extend `Webhooks::Request#to_signable_string` to bind the header-derived identity fields, or otherwise have `Registry.process` cryptographically verify that the claimed `shop`/`topic` match values embedded in (or derivable only from) the authenticated body/metadata before constructing `WebhookMetadata`. At minimum, document loudly that `shop`/`topic` headers are unauthenticated and must not be trusted for tenant routing without additional verification (e.g., cross-checking against a shop record established during OAuth).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = Base64(HMAC-SHA256(app_secret, B))`.
2. Attacker POSTs to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `HMAC(app_secret, B)` — this succeeds because `B`/`H` are the genuine pair from step 1 [4](#0-3) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [5](#0-4)  — the app now processes attacker-controlled data as if it belongs to the victim shop, with a fully "valid" HMAC.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
