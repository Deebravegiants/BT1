The docs explicitly promise `ShopifyAPI::Webhooks::Registry.process` will "verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and expose `data.shop` as a trustworthy field [1](#0-0) , but the HMAC signature only ever covers the raw request body, never the `shop`, `topic`, or `webhook_id` headers.

### Title
Webhook shop/topic/webhook_id attribution is not covered by the HMAC signature, allowing shop spoofing via replayed valid webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies that string against the `hmac-sha256` header using the app's shared `api_secret_key`. The `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers that are never part of the signed content, yet `ShopifyAPI::Webhooks::Registry.process` passes them straight to the app's handler as trusted `WebhookMetadata` after HMAC validation succeeds.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [2](#0-1) 

`request.shop`, `request.topic`, and `request.webhook_id` are all read from headers [3](#0-2) , while `to_signable_string` (the value the HMAC is verified against) returns only the raw body [4](#0-3) . `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [5](#0-4) , so none of the header fields are bound to the signature.

The equality this breaks is: `shop authenticated by HMAC == shop delivered to the handler`. Because `Context.api_secret_key` is the app's single shared client secret used for every shop that installs the app [6](#0-5) , any merchant who installs the app on their own store receives real webhooks from Shopify with a valid HMAC over the body. That merchant can capture one such valid `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a victim tenant's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the attacker-chosen `shop` to the handler unchanged.

### Impact Explanation
This crosses a tenant boundary: a single unprivileged merchant tenant (who legitimately installed the app) can make the app process/attribute webhook events as if they came from an arbitrary other shop, since the `shop` value used for tenant dispatch is not covered by the authentication check that the docs claim confirms the request "did indeed come from Shopify" for that shop. Any host application logic that keys per-tenant side effects (job dispatch, data writes, cache invalidation, billing counters, etc.) off `data.shop` without an independent domain allowlist is exposed to cross-tenant data confusion/injection, matching the High severity "scope or expiry check bypass" / cross-tenant class.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free-tier) merchant who has installed the target app, receive one genuine webhook, and replay it with a modified `shop` header to the same public callback endpoint — no secrets, tokens, or privileged access needed. This is straightforward and repeatable.

### Recommendation
Incorporate the `shop`, `topic`, and `webhook_id` values into the signable content verified by `HmacValidator`, or have `Registry.process` independently confirm that `request.shop` corresponds to a shop with an active registration/session for the topic before invoking the handler, rather than trusting header-derived values that sit outside the HMAC boundary.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; register for topic `orders/create` so Shopify sends real webhooks signed with the app's shared `api_secret_key`.
2. Capture one delivered request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid since `HMAC-SHA256(api_secret_key, B) == H`).
3. Resend the exact same `B`/`H` pair to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally spoof `x-shopify-webhook-id`/`x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because only `B`/`H` are checked [7](#0-6) ; the handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the request never actually originating from that shop.
