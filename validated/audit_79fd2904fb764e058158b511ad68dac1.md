### Title
POA Bridge matches withdrawal status by `assetId` only, causing cross-withdrawal status/hash misattribution in batch withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`findMatchingWithdrawal` in the POA bridge implementation matches a withdrawal's on-chain completion status purely by `assetId`, ignoring `destinationAddress`, `amount`, and `index`. When a single NEAR transaction contains multiple withdrawal legs of the *same* `assetId` (e.g., a batch withdrawal to two different destination addresses), `describeWithdrawal()` for one leg's `WithdrawalIdentifier` can be satisfied by the *other* leg's completed record, causing the SDK to report the wrong `txHash` (and possibly a "completed" status for a leg that is still pending/failed) to the caller.

### Finding Description
`PoaBridge.describeWithdrawal()` retrieves all withdrawals for a NEAR tx hash and picks the first entry whose `near_token_id` matches the requested `assetId`: [1](#0-0) [2](#0-1) 

The code comment explicitly acknowledges the limitation: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." However, nothing upstream in `sdk.ts` prevents a caller from constructing a batch of `WithdrawalParams` that contains two entries with the same `assetId` but different `destinationAddress` values, each producing its own `WithdrawalIdentifier` with a distinct `index`: [3](#0-2) 

Since the API response list is unsorted and matching only checks `near_token_id === assetId`, `describeWithdrawal()` for index 0 can return the `transfer_tx_hash`/status belonging to index 1's withdrawal (which may go to a different destination address), and vice versa. This breaks the equality that the "status reported" must equal "the on-chain outcome for this specific withdrawal leg."

This is functionally analogous to the referenced stETH bug: both illustrate a case where the code substitutes an aggregate/ambiguous value (assetId-only match here, balance-diff-agnostic accounting there) for the precise per-instance state that should have been tracked (per-leg destination+amount here, per-transfer actual amount there), causing the wrong value to be attributed to the wrong recipient/record.

### Impact Explanation
If an integrator uses this SDK to build a batch withdrawal (same token, two different destination addresses) and polls `waitForWithdrawalCompletion`/`watchWithdrawal` per leg, they could:
- Receive a "completed" status with the wrong destination's `txHash` for a leg that has not actually completed, causing the integrator to prematurely credit/finalize that leg (double credit / false completion), or
- Receive the same `txHash` for two different legs, one of which never actually completed on-chain, leading to confusion in reconciliation and potential double-crediting of a user or incorrect refund logic downstream.

This matches the "status or hash misreport making an integrator credit or refund twice" High-severity criterion, since the misattribution occurs entirely from the SDK's data lookup logic, requiring no malicious actor, just a legitimate batch withdrawal usage pattern that the public API does not prevent.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to withdraw the same `assetId` twice in one NEAR transaction (a supported, non-malicious usage pattern via the SDK's batch `withdrawalParams` array support), which is plausible for legitimate batching use cases (e.g., splitting a payout to two recipients in the same token). Nothing in `validateWithdrawal()` or `createWithdrawalIntents()` rejects or warns against this combination, so the failure mode is silently reachable.

### Recommendation
Disambiguate withdrawal matching by more than `assetId`. At minimum, when multiple withdrawals share the same `near_token_id` for a given NEAR tx hash, either:
- Match using `destinationAddress` and `amount` (with fee accounted for) in addition to `assetId`, or
- Throw/return a hard error (instead of silently mis-picking one) so callers know same-token batch legs are unsupported until the POA API/SDK can disambiguate by index, and enforce this rejection in `sdk.ts`'s batch withdrawal path (`createWithdrawalIntents`/`waitForWithdrawalCompletion`) rather than only documenting it in a code comment.

### Proof of Concept
Not executable without live POA bridge API mocks, but the failure is reproducible with the existing test harness pattern used in `poa-bridge.test.ts`:
1. Call `bridge.createWithdrawalIdentifier` twice for the same NEAR `tx.hash`, same `assetId` (`nep141:btc.omft.near`), but `index: 0` with `destinationAddress: A` and `index: 1` with `destinationAddress: B`.
2. Mock `poaBridge.httpClient.getWithdrawalStatus` to return two withdrawal records for that tx hash, both with `near_token_id: "btc.omft.near"`, one `COMPLETED` (destined for `B`) and one `PENDING` (destined for `A`).
3. Call `bridge.describeWithdrawal(widForA)` — per `findMatchingWithdrawal`, it returns the first array element matching `assetId`, which (depending on API ordering) can be the `COMPLETED` record actually belonging to `B`'s withdrawal, returning `{ status: "completed", txHash: B's tx hash }` for `A`'s leg. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
