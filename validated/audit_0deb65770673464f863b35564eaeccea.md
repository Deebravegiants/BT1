### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value solely from the unsigned `x-shopify-shop-domain` HTTP header, while the HMAC signature (verified via `Utils::HmacValidator.validate`) only covers the raw request body (`to_signable_string` returns `@raw_body`). The identity binding `shop_authenticated == shop_used_by_handler` is broken: the HMAC authenticates *bytes* (the body), but the `shop` field that downstream handler logic trusts as the tenant identifier is never part of the signed material.

### Finding Description
`Registry.process` validates a webhook solely with: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`, which in turn recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body, and `shop` is read directly from the `shop-domain` header without any cryptographic binding to that body or to the HMAC: [3](#0-2) 

After successful HMAC validation, the registry hands the handler a `WebhookMetadata` built directly from `request.shop`, i.e. the unauthenticated header value: [1](#0-0) 

Because a Shopify app's webhook signing key (`api_secret_key`/`old_api_secret_key`) is shared across *all* shops that install the app (it is not per-shop), any unprivileged internet user who legitimately operates one shop installation of the target app can:
1. Trigger an action in their own shop that causes Shopify to send a genuine webhook (e.g. `orders/create`), obtaining a body + a valid `x-shopify-hmac-sha256` signature computed with the shared app secret.
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the body bytes against the HMAC — the shop header was never part of the signed input — so the gem reports the webhook as valid and attributes it to the victim shop.

This is precisely the "field acted on but not covered by the HMAC" bug class: the field that the host application uses as the tenant/session key (`shop`) is disjoint from the field verified by the cryptographic signature (`raw_body`).

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` (or `request.shop`) as an authenticated tenant identifier — the documented/intended use, since the gem exposes `shop` as part of the validated webhook data — can be made to process attacker-controlled webhook payloads under a spoofed shop identity. This allows cross-tenant data injection/corruption (e.g. an attacker's own genuine `orders/create` payload being processed as if it belongs to a victim shop), which matches the Critical "cross-tenant access" impact criterion, since it lets an unprivileged multi-tenant participant (any shop that installs the app) act with another tenant's identity within the host app's webhook-driven business logic.

### Likelihood Explanation
Likelihood is realistic for any Shopify app using this gem's webhook registry as documented: an attacker only needs to be a legitimate, unprivileged installer of the target app (any merchant can install most apps) to obtain a validly-signed webhook body/HMAC pair for replay with a forged shop header. No access to the app's `client_secret`, access tokens, or any privileged capability is required — only ordinary use of their own store to generate a genuine webhook event.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook-id`, `api-version`) header values into the HMAC-signed material, e.g. by making `to_signable_string` combine the raw body with a canonical representation of the trusted headers, or by independently verifying that `request.shop` corresponds to a shop with an active, stored session/installation before dispatching to the handler. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is unauthenticated and must be cross-checked against known installed shops by the host application before use.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com` (both use the same app `client_id`/`client_secret`).
2. Attacker performs an action in `attacker-shop` that causes Shopify to POST a genuine webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body, computed with shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled fields...}
   ```
3. Attacker captures this exact body and HMAC value, then resends it directly to the app's webhook endpoint with the header changed:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: <same unmodified body>
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (the body) against the HMAC — the `shop-domain` header substitution is invisible to the check.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker's data>, ...)` and processes it as if it were a legitimate event from `victim-shop`, despite the payload actually originating from and being controlled by the attacker.
