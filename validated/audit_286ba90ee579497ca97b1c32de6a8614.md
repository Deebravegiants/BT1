### Title
Withdrawal status/tx-hash misreport when batching multiple withdrawals of the same asset via PoA Bridge - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` and the underlying `findMatchingWithdrawal()` helper identify which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier` by matching only on `assetId` (via `near_token_id`), ignoring the `index` field that is supposed to disambiguate multiple withdrawals produced by the same NEAR intent transaction.

### Finding Description
`describeWithdrawal` takes a `WithdrawalIdentifier` that includes `tx.hash` (the NEAR intent transaction) and an `index` (the position of this particular withdrawal among possibly several created by the same intent), as defined in `WithdrawalIdentifier` [1](#0-0) .

For POA-routed withdrawals, the status is resolved by fetching all withdrawals tied to the NEAR tx hash and then picking the one whose `near_token_id` matches the requested `assetId` — the `index` argument is explicitly discarded: [2](#0-1) [3](#0-2) 

The code comment explicitly acknowledges the gap: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." The same pattern (and the same acknowledged limitation) exists in the sibling helper used by `waitForWithdrawalCompletion` in `internal-utils`: [4](#0-3) 

The equality that should hold is: *the `txHash`/status reported for withdrawal `i` of a batch must equal the actual on-chain outcome of that specific sub-withdrawal `i`*. Because matching is done with `Array.prototype.find` keyed only by `assetId`, if a single intent transaction produces two (or more) withdrawals of the same NEP-141 asset (e.g., two separate BTC payouts to different destination addresses/amounts within one batched intent), `.find()` always returns the *first* matching entry in the POA API's response for every index that shares that `assetId`. Both `describeWithdrawal({index: 0, ...})` and `describeWithdrawal({index: 1, ...})` for that asset would report the identical `status`/`txHash`, even though they are different withdrawals with (likely) different destination tx hashes on the target chain.

The SDK's own design docs confirm batch withdrawals with independent per-index tracking are a first-class supported/expected use case (multiple tokens or multiple payouts withdrawn in a single intent, tracked by array index for recovery/reconciliation), reinforcing that callers rely on per-index correctness: 

### Impact Explanation
An integrator (e.g., a custodial service or exchange) that uses `sdk.processWithdrawal`/`watchWithdrawal`/`waitForWithdrawalCompletion` with `index`-based tracking to decide when to mark withdrawal #0 vs withdrawal #1 as "delivered" would receive the same `txHash` for both, or the wrong status, once the batch contains two withdrawals of the same asset. This is a status/hash misreport that can make an integrator credit or reconcile a withdrawal twice, or mistakenly treat a pending/failed withdrawal as completed because it was matched to a sibling withdrawal's completed record. This falls under the High-severity bucket described in the rules ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires: (1) an integrator constructing a batch of multiple withdrawal intents that includes ≥2 withdrawals of the *same* NEP-141 asset in a single NEAR transaction (a scenario the SDK's batch-withdrawal design doc treats as a normal, expected pattern — e.g., "USDC to Solana + BTC refund to Bitcoin" is the documented example, and nothing in the code prevents two same-asset withdrawals), and (2) the integrator relying on `index` to disambiguate results, which the RFC's "Array of Promises" / index-correspondence design explicitly encourages. No malicious actor input is required — this is a correctness bug triggered by ordinary usage patterns already anticipated by the codebase's own documentation. The comment in the source acknowledges the case is unhandled, indicating it is a known but unresolved gap rather than a purely theoretical one.

### Recommendation
- Disambiguate withdrawals of the same asset within one NEAR tx by additional fields already present in the POA response (e.g., destination `address`, `amount`) rather than `assetId` alone, or coordinate with the POA bridge API to expose a stable per-withdrawal sequence number.
- Until the POA API supports this, `findMatchingWithdrawal` should detect the ambiguous case (more than one candidate withdrawal sharing the same `assetId` for a given tx hash) and throw/return an explicit "ambiguous/unsupported" result instead of silently returning the first match, so integrators cannot silently double-credit.
- Update `WithdrawalIdentifier`/`describeWithdrawal` consumers' documentation to state this limitation prominently (not just in an internal comment) so integrators do not batch same-asset withdrawals in reliance on per-index tracking until it is fixed.

### Proof of Concept
1. Caller submits a single NEAR intent containing two `ft_withdraw` intents for the same asset, e.g. `nep141:btc.omft.near`, to two different Bitcoin destination addresses (e.g. withdrawal A: 0.01 BTC to address X, withdrawal B: 0.02 BTC to address Y), producing NEAR tx hash `T`.
2. Caller tracks completion using `WithdrawalIdentifier { tx: {hash: T}, index: 0, withdrawalParams: A }` and `{ tx: {hash: T}, index: 1, withdrawalParams: B }`.
3. POA Bridge API's `getWithdrawalStatus({ withdrawal_hash: T })` returns two entries, both with `near_token_id: "btc.omft.near"` but different `transfer_tx_hash` (e.g., `"btc-tx-A"` and `"btc-tx-B"`).
4. `describeWithdrawal` for index 0 calls `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the *first* array element regardless of which index was requested (see `.find()` at packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:426).
5. `describeWithdrawal` for index 1 (a *different* withdrawal, same asset) returns the exact same result object — reporting `"btc-tx-A"` as the destination hash for withdrawal B as well, even though B actually landed as `"btc-tx-B"`.
6. An integrator relying on the promise-per-index pattern documented in the RFC would mark both withdrawal A and withdrawal B "completed" using `"btc-tx-A"`, potentially crediting withdrawal B against the wrong on-chain transaction or double-crediting the user for a single transfer.

This scenario is explicitly reproduced (for a single index, not for the batched same-asset case) by the existing test `"matches withdrawal by assetId, not by index"` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111`, which itself demonstrates that index is not consulted in matching. /**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
