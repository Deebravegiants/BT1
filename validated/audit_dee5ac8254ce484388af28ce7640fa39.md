## Title
Webhook shop-domain spoofing via HMAC that only covers the raw body, not the `shop-domain` header — cross-tenant webhook injection - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, never the `shop-domain`/`topic`/`webhook-id` headers. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the body only and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler. Because the HMAC does not bind the body to the claimed shop, any party who has ever received one legitimately-signed webhook (e.g. by installing the app on their own store) can replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the library will report it as a fully-validated webhook for the victim shop.

### Finding Description
The HMAC verification chain is:
- `Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler: [1](#0-0) 
- `HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header: [2](#0-1) 
- `Webhooks::Request#to_signable_string` is defined to return **only** `@raw_body`: [3](#0-2) 
- `Webhooks::Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated headers with no relation to the signed content: [4](#0-3) 
- After the HMAC check passes, `Registry.process` builds the `WebhookMetadata` passed to the application's handler straight from `request.shop`, `request.topic`, and `request.parsed_body`, with no cross-check that these header values are consistent with anything cryptographically verified: [5](#0-4) 

The identity binding that should hold is:
```
HMAC(secret, signable_string) == received_hmac  AND  signable_string binds shop
```
but the actual binding enforced is only:
```
HMAC(secret, raw_body) == received_hmac
```
`shop` (and `topic`/`webhook_id`) are completely outside the signed material. Any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available to them by simply installing the target app on their own Shopify development store and receiving a real webhook — can present that same pair to the app's public webhook callback URL while forging the `x-shopify-shop-domain` header (and `x-shopify-topic`) to a different, victim shop. The gem will validate this as fully authentic and hand the attacker-chosen `body` content to the app's handler tagged as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant integrity/confusion vulnerability: an unprivileged internet user with no relationship to the victim shop can cause the host application to process attacker-controlled webhook payloads as if they originated from the victim shop (e.g., `orders/create`, `app/uninstalled`, `shop/update` bodies of the attacker's own design), since the gem provides no mechanism to bind the body to the claimed shop or topic. Depending on how the host app's handler uses `data.shop` and `data.body` (e.g., writing records keyed by shop, triggering shop-scoped side effects), this can lead to cross-tenant data corruption, spoofed lifecycle events (like a forged `app/uninstalled` for a shop that never uninstalled), or injection of attacker-controlled data into another merchant's tenant context — squarely a "cross-tenant access" class issue as called out in the impact rules.

### Likelihood Explanation
Likelihood is realistic: any attacker can freely create their own Shopify development/partner store, install the target app, and receive genuinely-signed webhooks for topics they choose to trigger (e.g., updating their own shop's settings, placing test orders). They then simply re-POST the intercepted raw body and `x-shopify-hmac-sha256` header to the app's public webhook route with a forged `x-shopify-shop-domain` header. No secret, token, or privileged access is required — only the ability to install the app once on an attacker-controlled shop, which any internet user can do.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the material that is authenticated, or otherwise cryptographically bind them to the verified body — e.g., verify HMAC over a canonical string that concatenates these headers with the body, or require the host application to independently authorize the shop (e.g., look up an existing session/installation for `request.shop` before trusting it) before acting on `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop`/`#topic` are unauthenticated header values distinct from the HMAC-verified body, and encourage handlers to cross-check `shop` against known installed shops before performing tenant-scoped writes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g. updates a product), receiving from Shopify a legitimately signed request:
   ```
   POST /webhooks
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "title": "attacker chosen"}
   ```
3. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, only changing the shop header:
   ```
   POST /webhooks
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <same valid HMAC>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, "title": "attacker chosen"}
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks the body against the HMAC using the app's own `api_secret_key`, per [6](#0-5) ), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body, as shown in [1](#0-0) .
