### Title
Webhook `shop-domain` Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` identity that the handler receives and trusts as the tenant/shop the event belongs to is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the HMAC-signed bytes at all.

### Finding Description
`Request#to_signable_string` only returns `@raw_body` [1](#0-0)  and `Utils::HmacValidator.validate_signature` computes the signature over exactly that signable string using the app's single `Context.api_secret_key`/`old_api_secret_key` [2](#0-1) . The `shop` attribute the library exposes and forwards to app handlers is derived independently from the `shopify-shop-domain` header [3](#0-2) , which is never part of `to_signable_string`. `Registry.process` checks only `Utils::HmacValidator.validate(request)` before dispatching, then builds `WebhookMetadata` using `request.shop` taken from the header, and hands it to the handler as the trusted tenant identity [4](#0-3) .

Because the API secret (`client_secret`) is shared by the app across every shop that installs it (it is not shop-specific), any shop that installs the app can obtain a legitimately-signed webhook (body + valid HMAC) for itself. The equality the HMAC is meant to enforce is: `hmac == HMAC(secret, signable_string)` where `signable_string` should uniquely identify `(shop, body)`. In this implementation the equality actually enforced is only `hmac == HMAC(secret, raw_body)` — `shop` is entirely outside that binding. An attacker who owns their own installation can therefore take a validly-signed webhook they received, swap the `shopify-shop-domain` header to a victim shop's domain, and resend it to the app's public webhook endpoint; the HMAC still validates because the body/HMAC pair is unchanged, but `WebhookMetadata#shop` now reports the victim's shop to the handler.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-used-as-tenant-key binding described in the rules: the header value acted upon (used as the tenant key for whatever the handler does — e.g. looking up/updating that merchant's stored data) is not covered by the HMAC that is supposed to prove authenticity. This can result in cross-tenant data confusion/corruption in any host application that trusts `WebhookMetadata#shop` as the authenticated tenant for a webhook whose HMAC only proves body authenticity, not shop authenticity.

### Likelihood Explanation
Any developer/attacker can install the app on their own shop (or use any shop that already has it installed) to obtain a validly HMAC-signed webhook body and secret-shared signature, then replay it with an arbitrary `shopify-shop-domain` header value against the app's public webhook endpoint. No privileged credentials, the `client_secret`, or an access token are required — only a legitimately received webhook from the attacker's own tenant.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signable string, or independently verify that the `shopify-shop-domain` header matches a shop the receiving app actually expects/has an active install for, before trusting `request.shop` as the tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header — this is a validly signed `(body, hmac)` pair under the app's shared secret.
2. Replay the exact same body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the unchanged body against the shared secret [5](#0-4) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is `"victim-shop.myshopify.com"` [6](#0-5) , even though the event content and signature were only ever authentic for `attacker.myshopify.com`.
