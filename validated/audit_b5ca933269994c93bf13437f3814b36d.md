### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay/spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that body. The `shop-domain` header — the value the gem hands to the host application as the authoritative tenant identifier for the webhook — is never included in the signed material, so it can be swapped freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` by simply reading the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The signable string used for HMAC verification, however, is only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` accepts any request whose body/HMAC pair validates, then trusts the (unauthenticated) `shop-domain` header verbatim when constructing the object handed to the app's business logic: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop the HMAC-secret owner (Shopify) actually authenticated the payload for`. Because the header is excluded from the signed bytes, that equality is never checked — only `body == HMAC(body)` is checked, and `shop` is orthogonal to it.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook body/HMAC pair for **any** shop (trivially available to an attacker who installs the app on their own store and triggers a webhook, e.g. `orders/create`) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim shop that also has the app installed). `HmacValidator.validate` will still pass because it never inspected the header, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, injecting attacker-controlled payloads into logic keyed by tenant (e.g. session/token lookups, order/inventory writes, GDPR-topic processing) attributed to a shop the attacker does not control. This is a cross-tenant integrity/confidentiality break stemming purely from this gem's verification logic.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on/trigger a webhook from any shop the attacker controls (a normal unprivileged action for anyone who can install a public/dev app), and (2) direct HTTP access to the app's webhook endpoint with attacker-chosen headers, which is inherent to any exposed webhook receiver. No secrets, tokens, or privileged access are required, making this readily reachable by an unprivileged internet user.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in the signed/verified material, or at minimum require the host application to authenticate the returned `shop` against a store of shops that are actually expected to be sending that topic/body before trusting it. Practically, `Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` binds signature validity to the specific shop claimed by the request, e.g. failing verification if a valid body/HMAC pair is replayed under a different `shop-domain` header than the one for which Shopify computed the signature.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`). Capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` that Shopify computed using the app's shared `api_secret_key`.
2. Send a new HTTP request directly to the app's webhook endpoint with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (swapped)
   - Body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.shop == "victim.myshopify.com"` and `body == B`, even though Shopify never issued a signature for `victim.myshopify.com`. The host app's tenant-scoped logic now executes with attacker-controlled data believing it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
