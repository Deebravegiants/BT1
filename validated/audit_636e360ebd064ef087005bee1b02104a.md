### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` identity that is subsequently handed to the app's webhook handler is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) . `Utils::HmacValidator.validate` computes the HMAC over exactly that signable string and compares it against the `hmac-sha256` header value using `OpenSSL.secure_compare` [3](#0-2) .

The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are all pulled straight from unauthenticated HTTP headers: [4](#0-3) . None of these headers are part of `to_signable_string`, so the HMAC provides no integrity guarantee over them.

`Registry.process` verifies only the HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic`, and dispatches it to the registered handler: [5](#0-4) . The `shop` field is exactly the identity binding host apps are expected to rely on to know which merchant/tenant a webhook event belongs to (see how `WebhookMetadata` is populated and consumed by handlers, and the test assertions that check `data.shop`) [6](#0-5) .

Because the signature only binds the body bytes and not the shop/topic headers, a request whose body+HMAC was legitimately generated by Shopify for shop A will still pass `HmacValidator.validate` even if resent (or intercepted/modified in transit before signature verification, e.g. via a proxy, load balancer header rewrite, or replay) with the `x-shopify-shop-domain` header changed to shop B. `Registry.process` would then hand the app's handler a `WebhookMetadata` claiming the event is for shop B while the (identical) body content actually originated from shop A — a cross-tenant identity confusion at the library level, since the gem's own authentication check does not bind `shop` to the signature it validates.

Equality broken: `shop authenticated by HMAC` ≠ `shop delivered to the handler`. The gem validates `HMAC(secret, raw_body)` but trusts `headers["x-shopify-shop-domain"]` unconditionally for the identity used downstream.

### Impact Explanation
This crosses a tenant boundary the gem is responsible for enforcing (Rules explicitly call out "a shop authenticated versus the shop stored/used as a session key" pattern as in-scope). If a host app uses `WebhookMetadata#shop` to select which merchant's data/session to act on (the documented/intended use), an attacker positioned to influence headers on the way to the app (e.g., a compromised/misconfigured intermediary, or any component that forwards Shopify webhook bodies with attacker-controlled headers) can cause cross-tenant processing of webhook data without needing the app's `client_secret` or any credential — only the ability to replay/deliver a body that was once legitimately signed. This is a cross-tenant access issue, one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitation does not require the attacker to know `api_secret_key`; it only requires control over, or the ability to relay, the `x-shopify-shop-domain` header alongside a previously-observed valid `(body, hmac)` pair — a realistic scenario for any app deployed behind a proxy/CDN/log-forwarder that isn't strict about header immutability, or where webhook payloads are queued/relayed internally with headers reconstructed from separate, less-trusted metadata. The root cause is fully within this gem: `Request#to_signable_string` at [2](#0-1)  excludes the very header the library trusts as the tenant identity.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signable payload validated against the HMAC, or independently verify `request.shop` against a known/allow-listed shop before dispatching to handlers, so that the identity used by `WebhookMetadata` is provably bound to the same bytes the HMAC authenticates.

### Proof of Concept
1. Capture a legitimate Shopify webhook delivery for `shop-a.myshopify.com`: raw body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H` [3](#0-2) .
4. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` and invokes the handler [7](#0-6) , causing shop A's webhook content to be processed under shop B's identity.
