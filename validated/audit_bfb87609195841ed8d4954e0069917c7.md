### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned header. `Registry.process` trusts that header value to route webhook data to the app's handler, so a party who possesses one validly-signed webhook payload for their own shop can replay it while altering the shop-domain header to impersonate a different merchant.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the value that gets HMAC-verified in `HmacValidator.validate`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body: [2](#0-1) 

Meanwhile `shop` is parsed straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is never part of the signed material: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` — the unauthenticated header — directly into the handler as the tenant identity: [4](#0-3) 

The equality that should hold is: `shop` bound by the signature == `shop` used to dispatch/attribute the webhook data. Instead: `hmac` authenticates only `raw_body`, while `shop` (and `topic`, `webhook_id`, `api_version`) are trusted verbatim from headers. Any party that has captured one legitimately-signed webhook body (e.g., from their own store, since the same `api_secret_key` signs webhooks for every merchant of a given app) can resend that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop. The signature check still passes because it never looked at the header, so `HmacValidator.validate` returns `true` and the handler executes with `data.shop` set to the attacker-chosen tenant.

### Impact Explanation
This breaks the tenant/shop binding for webhook processing, a cross-tenant confusion: the app's webhook handler cannot distinguish "signed body originated from shop X" from "attacker asserts shop Y in the header while replaying a validly-signed body." Depending on what the handler does with `WebhookMetadata#shop` (e.g., look up/write per-shop records, trigger per-shop side effects, invalidate/rotate credentials, or store data keyed by shop), this enables cross-tenant data corruption or disclosure inside the host app, which is a boundary this gem is expected to enforce since it's the piece performing "webhook authenticity" verification on the host's behalf.

### Likelihood Explanation
Reachable by any unprivileged actor who is a legitimate (even attacker-controlled) merchant installation of the app, since they can generate/observe a validly-HMAC-signed webhook for their own store and then POST it to the app's public webhook endpoint with a modified shop header. No access token, `client_secret`, or privileged account is required — only a normal merchant's own event traffic, which is attacker-controllable content/timing in many webhook topics (e.g., `orders/create`, `customers/update`).

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) as part of the signable material for webhook verification, or otherwise cryptographically bind the shop domain to the HMAC-verified payload before it is handed to `handler.handle`. At minimum, `Registry.process` should not treat the shop header as trusted tenant identity unless it is itself covered by the signature Shopify computes.

### Proof of Concept
1. Register a webhook handler in a host app using this gem, e.g. `orders/create`.
2. As a legitimate merchant "attacker.myshopify.com" with the app installed, capture one real inbound webhook POST (raw body + `x-shopify-hmac-sha256` header) that Shopify sends — validly signed with the app's `api_secret_key`.
3. Replay that exact body/HMAC to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the header as `"victim.myshopify.com"`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the secret and returns `true`.
5. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com", ...)` and performs its logic attributing the (attacker-supplied) payload to the victim shop.
