### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is handed to the host application's webhook handler, and used by the app to decide which tenant's data to mutate, is read from the `shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed material [2](#0-1) . This breaks the intended binding `hmac_signed_bytes == bytes_that_determine_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) . `#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from headers with no cryptographic binding to the body or to the HMAC: [4](#0-3) .

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., only the body) using the single, app-wide `Context.api_secret_key` (the same secret for every installed shop, confirmed in `lib/shopify_api/context.rb`) [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [6](#0-5) , and `WebhookMetadata.shop` is a plain, unauthenticated `String` field [7](#0-6) .

Because the same `api_secret_key` signs webhook bodies for *every* shop that has installed the app, and the header carrying tenant identity is outside the signature, any two bodies with the same content are indistinguishable from Shopify's perspective for HMAC purposes. A party who can obtain one validly-signed `(body, hmac)` pair — e.g. a malicious merchant who installs the app on their own shop, or anyone who intercepts one legitimate delivery over an unencrypted hop/logged proxy — can resend that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true`, since it never looks at the header, and the handler executes with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding failure: the library-level authentication for webhooks guarantees only "this body was signed by our app secret," not "this body is a real event for the shop named in the header." Any host application that (as documented) uses `WebhookMetadata#shop` to select which tenant record to create/update/delete can be made to apply attacker-controlled data to a different, unrelated merchant's records, which is a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimately-signed `(body, hmac)` pair for the target app — trivially available to any merchant who installs the app themselves (no special privilege needed beyond ordinary app installation) — and then to be able to deliver an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header, which is just an unprivileged HTTP request. No access token, `client_secret`, or credential theft is required.

### Recommendation
Bind the shop identity to the signature verification: either include the `shop-domain` header value in the signed/verified material (not possible without changing Shopify's own signing, so instead) require callers to supply the expected shop (e.g., derived from a previously known/registered shop for that webhook subscription, or a `webhook_id` looked up server-side) and compare it against `request.shop` before trusting it, rather than trusting the header value outright inside `Registry.process`/`WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated header data and that host applications must independently verify it belongs to a shop that has a valid, stored session/subscription before acting on it.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Attacker creates an order, causing Shopify to deliver a real webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` (they own the delivery, so no interception is even needed).
4. Attacker sends a POST to the app's webhook endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, returns `true` [8](#0-7) .
6. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [9](#0-8) , and the host app performs the associated action (e.g., creating/mutating a record) under the victim shop's tenant context using attacker-supplied body content.
