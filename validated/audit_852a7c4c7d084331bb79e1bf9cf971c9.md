### Title
Unbounded-gas native-token push in intent fill/withdrawal paths lets a malicious beneficiary grief solvers and permanently block escrow release - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._sendValue` and the inlined native-token push in `_fillSameChain` forward **all remaining gas** in a raw `.call{value: amount}("")` to an attacker-controlled `beneficiary`/recipient address, and treat any failure as a hard revert of the whole transaction (`revert InsufficientNativeToken()`). This is the same anti-pattern flagged in the external report for `RefuelAction`/`TransferAction`: an unbounded low-level call to an arbitrary target, with success required before the caller (solver/relayer) gets anything, lets the recipient consume all forwarded gas and revert, griefing the caller's gas and — for the escrow-withdrawal path — permanently blocking delivery of the message.

### Finding Description
`_sendValue` is the shared native-transfer primitive used throughout the intents apps: [1](#0-0) 

It is used in:
- `_withdraw` (escrow release/refund to `beneficiary`) — invoked from `onAccept` when a relayer delivers a cross-chain `RedeemEscrow`/`RefundEscrow` message: [2](#0-1) 
- `_fillCrossChain`, where the **solver** pushes native output tokens directly to the order's `beneficiary` before the escrow-release POST is even dispatched: [3](#0-2) 
- `_fillSameChain`, with an inlined equivalent (same unbounded forwarding, same revert-on-failure semantics): [4](#0-3) 

In every case, `beneficiary` is attacker-influenced: it comes directly from `order.output.beneficiary`, which is set by the (unprivileged) order creator, or — for `_withdraw` on the source chain — from the cross-chain message's `beneficiary` field that traces back to `msg.sender` of the fill on the destination chain. A malicious beneficiary contract can implement a `receive()`/`fallback()` that burns all forwarded gas in a loop and then reverts. Because `_sendValue`/the inline call forwards the *entire* remaining gas (no gas stipend/limit) and the caller treats `!sent` as a hard revert, the calling transaction:
1. Consumes essentially all of the gas supplied by the caller (solver in `fillOrder`, or the relayer/handler delivering `onAccept` via `EvmHost.dispatchIncoming`), and
2. Reverts entirely, giving the caller no compensation and no completed state change.

For the `EvmHost.dispatchIncoming` → `onAccept` → `_withdraw` path, the outer `EvmHost` call only catches the boolean success and deletes the receipt for a retry: [5](#0-4)  — meaning a griefing beneficiary can force this to fail on *every* retry, permanently preventing that `RedeemEscrow`/`RefundEscrow` message from ever being delivered, while burning relayer gas each attempt.

### Impact Explanation
- **Solver griefing (fillOrder):** A user can place an order whose `output.beneficiary` is a gas-griefing contract. Any solver who calls `fillOrder`/`_fillCrossChain`/`_fillSameChain` to service that order has their entire transaction revert after their gas has been consumed by the malicious `receive()` — a direct, repeatable financial loss to solvers with no recourse, discouraging solver participation (Medium/High depending on gas price and repetition).
- **Permanent message-delivery freeze (escrow release):** Since `_withdraw`'s native push also uses the unbounded, revert-on-failure `_sendValue`, and `EvmHost.dispatchIncoming` only allows retries (never forces success), a beneficiary that is guaranteed to revert makes the `RedeemEscrow`/`RefundEscrow` delivery permanently undeliverable — this matches the "route unable to deliver messages" / permanent freezing-of-funds criteria, since the escrowed input tokens tied to that commitment can never be released to the intended beneficiary.

### Likelihood Explanation
Low difficulty, no special privileges required: any user can place an order (or otherwise become the `beneficiary`/redemption target) with a contract address that implements an unbounded-gas-consuming `receive()`. No front-running of EIP-7702 delegation is even required here (unlike the Otim EOA scenario) — the attacker directly controls and deploys the griefing contract as their `beneficiary` at order-placement time, making exploitation trivial and repeatable against any solver who is willing to fill the order, or against the relayer delivering the corresponding cross-chain settlement message.

### Recommendation
- **Short term:** Cap the gas forwarded in `_sendValue` and the inlined equivalent in `_fillSameChain` (e.g., forward a fixed stipend such as 2300–10000 gas, or an explicit bounded gas limit) so a malicious recipient cannot consume the caller's entire gas budget.
- **Long term:** Decouple compensation/state finalization from the success of the native push: e.g., escrow the ETH for the beneficiary to pull (`withdraw` pattern) rather than pushing it, so that a hostile recipient cannot force the whole transaction (and thus the associated escrow release / solver reward) to revert. For the `onAccept`/`_withdraw` message-delivery path specifically, ensure a griefing beneficiary cannot permanently block delivery — e.g., record the message as delivered/receipted independent of the native push's success, falling back to a pull-based claim for the native leg only.

### Proof of Concept
1. Attacker deploys `EvilBeneficiary` with a `receive()` that runs an unbounded loop (e.g., `while(true){}` guarded only by gas) before an explicit `revert()`.
2. Attacker (as an ordinary user) calls `placeOrder` with `order.output.beneficiary = address(EvilBeneficiary)` and a native (`address(0)`) output asset.
3. A solver calls `fillOrder`, which routes to `_fillCrossChain`/`_fillSameChain`. The `_sendValue(beneficiary, beneficiaryTotal)` (or inline equivalent) call forwards all remaining gas to `EvilBeneficiary`, which burns it and reverts.
4. The `!sent` branch reverts the whole `fillOrder` transaction with `InsufficientNativeToken()`; the solver has paid for (and lost) the gas with no state change and no compensation. Repeating step 3 with any solver reproduces the loss indefinitely.
5. Separately, if the same beneficiary address is used as the redemption target in the cross-chain `RedeemEscrow`/`RefundEscrow` body, every relayer attempt to deliver via `EvmHost.dispatchIncoming` → `onAccept` → `_withdraw` fails the same way, and `EvmHost` merely deletes the receipt for a retry — permanently blocking release of the escrowed input tokens for that commitment.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        for (uint256 i; i < len; i++) {

                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
