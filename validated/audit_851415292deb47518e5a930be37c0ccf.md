### Title
Token Exchange sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop used to construct the HTTP request host from the session token's `dest` claim (`jwt_payload.shop`) and never runs it through `Utils::ShopValidator.sanitize!` before using it to build the outbound `access_token` request that carries `client_id`/`client_secret`. The sibling method in the very same file, `migrate_to_expiring_token`, does perform this sanitization on its `shop` parameter before sending the same credential-bearing request.

### Finding Description
`exchange_token` takes `dest_shop = jwt_payload.shop` and immediately builds `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, which is then handed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` to POST a body containing `client_id` and `client_secret` to the `access_token` endpoint on whatever host is derived from `shop_session.shop`. [1](#0-0) 

`jwt_payload.shop` simply strips the `https://` prefix from the JWT's `dest` claim with no additional domain-format validation: [2](#0-1) 

`JwtPayload#initialize` only verifies the JWT signature and that `aud == Context.api_key`; it never checks that `dest`/`iss` are trusted Shopify domains (e.g. via `ShopValidator`): [3](#0-2) 

By contrast, `migrate_to_expiring_token` — which performs the same class of operation (build a session, then POST `client_secret` to a host derived from that session's shop) — explicitly calls `Utils::ShopValidator.sanitize!(shop)` first: [4](#0-3) 

The intended binding is: `validated_shop (trusted Shopify domain) == host that receives client_secret`. `migrate_to_expiring_token` enforces this equality; `exchange_token` does not — it trusts the raw `dest` claim value as the destination host for the credential-bearing request.

### Impact Explanation
If the `dest` claim value used to build the outbound host is ever not constrained to a genuine `*.myshopify.com`/trusted Shopify domain (defense-in-depth that `ShopValidator` exists specifically to provide, and that the sibling method in the same file already applies), the app's `client_secret` would be sent as part of an HTTP POST to that unvalidated host — an SSRF carrying the app's credentials. This matches the "High — SSRF with the app's credentials" impact class defined in scope.

### Likelihood Explanation
Likelihood is limited by the fact that `dest` lives inside a JWT whose signature is checked against `Context.api_secret_key`/`old_api_secret_key`, so an external attacker who does not already hold the app's secret cannot freely mint a token with an arbitrary `dest`. The finding is therefore a missing defense-in-depth control (present in `migrate_to_expiring_token`, absent in `exchange_token`) rather than a demonstrated end-to-end unauthenticated exploit — I could not construct a concrete path for an unprivileged internet user to control `dest` without already controlling the secret. This uncertainty should be flagged for a background agent to review further, since the asymmetry between the two methods in the same file is a genuine gap, but its practical unprivileged-attacker exploitability could not be fully confirmed with the available in-scope code alone.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or equivalent) to `dest_shop` in `exchange_token` before constructing `shop_session`/`Clients::HttpClient`, mirroring the existing behavior in `migrate_to_expiring_token`, so the host that receives `client_id`/`client_secret` is always constrained to a trusted Shopify domain regardless of the raw `dest` claim value.

### Proof of Concept
Not independently reproducible with an unprivileged attacker under the current in-scope evidence, since triggering an untrusted `dest` value requires a validly-signed JWT, which in turn requires the app's `api_secret_key`. The finding is raised as a concrete code-level asymmetry (missing `ShopValidator.sanitize!` call in `exchange_token` vs. `migrate_to_expiring_token`) rather than a proven exploit chain.
