This confirms the vulnerability: `Registry.process` at [1](#0-0)  only verifies `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`, and `to_signable_string` returns only `@raw_body` [2](#0-1) . The `shop` field used downstream for tenant identification (`WebhookMetadata.new(..., shop: request.shop, ...)`) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , which is never included in the signed bytes.

### Title
Webhook tenant identity (`shop-domain`) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body. The `shop` value that identifies which merchant/tenant the webhook belongs to is taken from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which is completely outside of what the HMAC signs. This breaks the intended binding `hmac(body, client_secret) == verified_shop`.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` before dispatching to the handler [4](#0-3) . `HmacValidator.validate` computes an HMAC-SHA256 over `verifiable_query.to_signable_string` and compares it to the `hmac` field via `OpenSSL.secure_compare` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body` [2](#0-1) ; none of the HTTP headers, including `shop-domain`, are part of the signed material. Yet `request.shop`, sourced directly from that unauthenticated header [3](#0-2) , is passed straight into `WebhookMetadata` and handed to the app's handler as the authoritative tenant identifier [6](#0-5) .

This is the exact bug-class analog described in the rules: "a field acted on but not covered by the HMAC." Any party who can obtain one validly-HMAC-signed webhook body for their own shop (trivial — an attacker can create their own Shopify dev store, subscribe a webhook, and receive an authentic HMAC over a body they control/observe) can replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `shop` set to whatever domain the attacker put in the header — impersonating any tenant.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce: the whole purpose of `stakedButUnverifiedNativeETH`-style "verify before trust" analog here is that `shop` should only be trustworthy once bound to the HMAC-verified bytes. Because it isn't, a caller with any valid signed payload (for any shop, including their own) can make the host application process a webhook as if it originated from a different, victim merchant, letting them inject attacker-controlled data (e.g. `orders/*`, `app/uninstalled`, `customers/redact`, etc.) tagged with a forged `shop`. Depending on how the host app keys per-tenant state/session lookup off `WebhookMetadata#shop`, this enables cross-tenant data corruption or triggering privileged per-shop side effects (e.g. app uninstall cleanup, GDPR redaction) against a shop the attacker does not own.

### Likelihood Explanation
Exploitability requires only an internet-reachable webhook endpoint and one legitimately-signed webhook body, which any developer can generate by installing the app on (or registering webhooks for) their own free/dev store — no access token, `client_secret`, or privileged account is needed. The header is fully attacker-controlled in any raw HTTP request construction (e.g., via curl), independent of what Shopify itself would send, since the gem performs no header-based binding.

### Recommendation
Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind the header values to the HMAC-verified body before trusting `request.shop`. At minimum, `Registry.process` should not treat `request.shop` as authoritative for tenant identification unless it can be shown to correspond to the same webhook subscription that produced the verified body (e.g., by cross-checking against a known/expected shop for that endpoint, or by requiring Shopify's TLS-terminated request path exclusively, which the gem cannot itself guarantee).

### Proof of Concept
```ruby
raw_body = '{"id":1}'
secret = ShopifyAPI::Context.api_secret_key
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
)

# Attacker obtains this valid_hmac by registering their OWN shop's webhook
# and capturing one legitimate delivery (or their own dev store's webhook).

forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, attacker-chosen
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true (only checks raw_body)
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# -> host app processes attacker-controlled body as if it came from victim-shop.myshopify.com
```
