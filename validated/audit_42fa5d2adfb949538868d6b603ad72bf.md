### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing shop-impersonation in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by handlers are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only checks that the body matches the HMAC — it never binds the `shop` (or other) header values into the signed material. As a result, an attacker who can obtain any one HMAC-valid `(body, hmac)` pair signed with the app's shared secret (e.g., by triggering a webhook event on a shop they legitimately control/install the app on) can replay that exact body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. `Registry.process` will accept it as valid and hand the attacker-chosen body to the handler tagged with the victim's shop domain.

### Finding Description
- `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, `api_version` are parsed straight from headers with no cryptographic binding to the signature: [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` compute/compare the HMAC purely over `to_signable_string` (i.e., the body), never incorporating headers such as shop domain: [3](#0-2) 
- `Registry.process` trusts the HMAC check and then dispatches to the handler using `request.shop` taken straight from the (unsigned) header, binding the verified body to an unverified shop identity: [4](#0-3) 

The identity binding that should hold is: `shop_that_signed_the_body == shop_attributed_to_the_event`. Because the signature only covers the body and the app's `api_secret_key` is the same across every shop that installs the app, that equality is never enforced — only `hmac == HMAC(secret, body)` is checked, independent of which shop's header claims to have sent it.

### Impact Explanation
Host applications built on this gem invariably use `WebhookMetadata#shop` (sourced from `request.shop`) as the tenant key to look up the merchant's stored offline access token/session and to decide which merchant record the webhook body applies to (this is the documented usage pattern in `docs/usage/webhooks.md`). An attacker who installs the target app on their own (attacker-controlled) shop can generate any number of legitimately HMAC-signed `(body, hmac)` pairs at will (e.g., by creating orders/products on their own store to trigger webhooks), then replay one of these captured pairs against the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim merchant's domain. `Registry.process` will validate the HMAC (it only checks the body) and invoke the handler with `shop` = victim domain, causing the host app to process attacker-supplied data under the identity of another tenant — a cross-tenant confusion/impersonation that can corrupt or leak per-shop state managed by the host application.

### Likelihood Explanation
Exploitation requires only unprivileged access: an attacker can freely create a development/test shop, install the target Shopify app (many apps are public or freely installable), trigger a webhook of their choosing to obtain a valid `(body, hmac)` pair signed with the shared `api_secret_key`, and then send it to the app's public webhook receiver endpoint with a forged `shop-domain` header. No access token, leaked secret, or privileged account is needed — the whole attack uses only publicly reachable endpoints and the attacker's own shop.

### Recommendation
Bind the shop identity (and other identifying headers) into the HMAC verification path rather than trusting it purely from headers, or alternatively cross-check `request.shop` against the shop context the app expects to receive on that endpoint. Concretely, `Request#to_signable_string` (or `HmacValidator`) should incorporate the `shop-domain` header into the signed message it validates, or `Registry.process` should require callers to supply the expected shop and reject mismatches, so that a body signed for one shop cannot be replayed and attributed to another.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), capturing the raw POST: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (valid signature of `B` computed with the app's shared `api_secret_key`).
2. Attacker POSTs the same `raw_body = B` and `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. Server calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com"...}))`.
4. `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `B`: [5](#0-4) 
5. `handler.handle` is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` even though the body actually originated from the attacker's own shop event: [6](#0-5)
