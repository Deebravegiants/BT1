### Title
`findMatchingWithdrawal` collapses distinct same-asset withdrawals in a batch, causing `describeWithdrawal`/`watchWithdrawal` to report the wrong txHash/status for one of them - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`findMatchingWithdrawal` matches PoA bridge withdrawal records purely by `assetId` (`nep141:<near_token_id>`), ignoring `WithdrawalIdentifier.index` and amount. When a single NEAR intent tx contains two withdrawals of the same PoA asset with different amounts, both `WithdrawalIdentifier`s query the exact same `getWithdrawalStatus` response (keyed only by `tx.hash`) and `Array.prototype.find` always returns the same first matching record for both indices, so one withdrawal's completed `txHash`/status gets reported for the other.

### Finding Description
The equality that must hold is: `describeWithdrawal(wid_i)` reflects the on-chain outcome of withdrawal `i`, for every `i`.

Trace:
- `getWithdrawalStatusWithRetry` calls `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash }, ...)` [1](#0-0)  - the request is keyed only by the shared NEAR tx hash, identical for every withdrawal in the batch, regardless of `index`.
- `describeWithdrawal` then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) .
- `findMatchingWithdrawal` does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — matching by `assetId` only, explicitly documented as not supporting "multiple withdrawals of the same token in a single transaction" [3](#0-2) .
- `createWithdrawalIdentifier` sets `index` per withdrawal but that `index` is never used in the matching logic [4](#0-3) .
- `watchWithdrawal` polls `bridge.describeWithdrawal({...args.wid})` and resolves the caller's promise with `status.txHash` once `status === "completed"` [5](#0-4) .

Because both calls hit the identical API response and `.find()` deterministically returns the first array element matching the shared `assetId`, `describeWithdrawal` for index 0 and index 1 return the *same* record (same `status`, same `transfer_tx_hash`) even though the underlying API returned two distinct withdrawal records (documented as "unsorted") for two genuinely different on-chain transfers. If that first-matched record is `COMPLETED` while the second, unmatched record is still `PENDING` (or vice versa), the caller watching the second withdrawal (`index: 1`) is told it is `completed` with a `txHash`/amount that actually belongs to the other withdrawal, while its own transfer may still be in flight.

No existing guard prevents this: `supports()`, `validateAddress`, `compareAddresses`, and `validateWithdrawal` all operate per-withdrawal and never check for duplicate `assetId` across the batch; there is no dedup/ordering reconciliation using amounts as the code comment itself suggests would be needed.

### Impact Explanation
This is a status/hash misreport, not an on-chain fund misroute: the actual PoA bridge transfers go to their correct destinations independent of this bug. However, an integrator relying on `watchWithdrawal`/`describeWithdrawal` to gate downstream actions (e.g., releasing correspondent funds, crediting a user, marking an invoice paid) can be told a withdrawal completed with a specific `txHash` while its real transfer is still pending or has a different value/destination — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category. It requires only a normal batched withdrawal of the same PoA token appearing twice in one intent, doesn't require any bridge/relayer/RPC compromise, and is repeatable on every such batch.

### Likelihood Explanation
Preconditions: a single NEAR intents transaction with ≥2 withdrawals routed through `PoaBridge` for the same `assetId` (same `near_token_id`), differing in amount/destination. This is producible by any ordinary caller of the public SDK batch-withdrawal API without any special privilege, cost, or race condition — it is entirely deterministic based on how the PoA indexer orders `withdrawals` in its response for the given `tx.hash`. Feasibility is high; the only uncertain part is exactly *which* of the two withdrawals gets which record, but the mismatch itself is guaranteed as soon as one completes before the other or the API list order doesn't match request order.

### Recommendation
Extend `findMatchingWithdrawal` (and `describeWithdrawal`/`createWithdrawalIdentifier`) to disambiguate withdrawals of the same `assetId` within a batch, e.g., by sorting both the requested `withdrawalParams` (filtered to same assetId) and the API's returned `withdrawals` (filtered to same `near_token_id`) by amount and pairing them positionally, as the existing code comment suggests, or by including amount/destination in the matching key if the PoA API supports it. At minimum, detect duplicate `assetId` withdrawals in a batch and refuse to silently pair them by first-match.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return `withdrawals: [ recordA (near_token_id: "zec.omft.near", amount: 50, status: COMPLETED, transfer_tx_hash: "hashA"), recordB (near_token_id: "zec.omft.near", amount: 1000, status: PENDING) ]` for a given `withdrawal_hash`.
2. Build `wid0` with `withdrawalParams.assetId = "nep141:zec.omft.near"`, `amount: 50n`, `index: 0`; `wid1` with same `assetId`, `amount: 1000n`, `index: 1`, both sharing `tx.hash`.
3. Call `bridge.describeWithdrawal(wid0)` → expect `{ status: "completed", txHash: "hashA" }` (correct).
4. Call `bridge.describeWithdrawal(wid1)` → assert it ALSO returns `{ status: "completed", txHash: "hashA" }` instead of reflecting `recordB`'s actual `PENDING` status — i.e., assert `describeWithdrawal(wid1).txHash === describeWithdrawal(wid0).txHash` even though `wid1.withdrawalParams.amount !== wid0.withdrawalParams.amount`, proving the large withdrawal (`wid1`) is falsely reported complete using the small withdrawal's txHash.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
