### Title
Webhook `shop-domain` header is trusted for tenant identification but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (i.e., `shop-domain` header) is read directly from unauthenticated headers and passed downstream to the webhook handler as the tenant identifier. Because the signature does not bind the `shop` value, an attacker who possesses one validly-signed webhook (e.g., a webhook delivered to their own shop/app installation) can replay it with a forged `shop-domain` header for a different (victim) shop, and `Registry.process` will accept it as authentic for the victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic link to the HMAC: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then unconditionally forwards `request.shop` to the handler as the trusted tenant identifier: [3](#0-2) 

The identity binding that should hold is:
`hmac == HMAC(secret, signable_string)` where `signable_string` should equal `body || shop || topic || ...` (everything the app trusts as authenticated), but in this gem it equals `body` alone. As a result:

`HMAC_valid(body) == HMAC_valid(body, shop_claimed)` is **false** — the validation only proves the body's authenticity, not the `(body, shop)` pairing that `WebhookMetadata` treats as trusted.

Since Shopify signs webhooks with the app's single shared `client_secret`/`api_secret_key` (the same secret is used for every shop that has installed the app), any shop that has installed the app can receive a genuinely Shopify-signed webhook, capture the raw body and HMAC, and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop of the same app. The signature still validates because it only checks the body, but `WebhookMetadata#shop` (and therefore any tenant-scoped action the host app takes, e.g. looking up per-shop state or deleting per-shop data for mandatory `shop/redact`/`customers/redact` topics) is attacker-controlled.

### Impact Explanation
This breaks the tenant/identity boundary that the gem's own HMAC validation is supposed to enforce for webhooks — a merchant of the app can impersonate another merchant's shop for any registered webhook topic, since `shop` is not part of the signed payload while it is the value handed to the app as the trusted origin. This matches the Critical bar of cross-tenant access.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free-tier) installer of the target app — no access to `api_secret_key`, no privileged account, and no interception of another tenant's traffic is needed. The attacker simply replays their own valid webhook with a modified header, which any unprivileged internet user who installs the app can do.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise independently bind the claimed `shop-domain` header to the signed body (e.g., have `Utils::HmacValidator.validate` take the header value into account, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop` into what is signed). At minimum, document that `request.shop` is not authenticated by the HMAC and must not be used to select tenant-scoped resources without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers a POST with body `B`, header `x-shopify-hmac-sha256: H = HMAC(secret, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `B` and `H`, then re-sends the same POST to the app's webhook endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only re-computes the HMAC over `@raw_body` (`to_signable_string`), which is unchanged. [4](#0-3) 
4. `Registry.process` calls the registered handler with `shop: request.shop` == `"victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop. [5](#0-4)
