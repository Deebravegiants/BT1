### Verdict

#No vulnerability found for this question.

**Reasoning:** The described attack path is explicitly blocked at the market layer. `repay` in `market.clar` requires: [1](#0-0) 

`(asserts! (is-eq contract-caller tx-sender) ERR-AUTHORIZATION)` — this precondition means `repay` (and therefore `vault-system-repay`/`receive-underlying`) can never be reached via a wrapper/proxy contract that is `contract-caller` while a different principal is `tx-sender`. Any such call reverts with `ERR-AUTHORIZATION` before `vault-system-repay` or `receive-underlying` are invoked, so the scenario where a wrapper contract calls repay `on-behalf-of` a victim while `receive-underlying` pulls funds from the wrapper's deployer's `tx-sender` cannot occur.

Additionally, even ignoring that guard, `system-repay` computes `capped-amount = (min amount debt)` using the vault's own aggregate `total-debt`, and `market.clar`'s `repay` already caps `amount-to-repay` to the specific account's scaled debt before calling `vault-system-repay`, so `amount-to-repay <= debt` holds and `capped-amount` equals `amount-to-repay` in the normal flow — the `principal-scaled` reduction (`capped-reduction`) and the per-user `debt-remove-scaled` call both derive from the same `repaid-scaled-debt`/`amount-to-repay` values computed once in `market.clar`, so they stay consistent: [2](#0-1) [3](#0-2) 

Since the specific attack vector (contract-caller ≠ tx-sender via a wrapper) is rejected by `ERR-AUTHORIZATION` at the market entrypoint, no divergence between `principal-scaled` reduction and per-user debt reduction can be triggered this way.
