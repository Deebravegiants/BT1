### Title
Deposit sandwich attack via optional `other_amount_min` allows depositors to receive under-priced LP tokens - ([File: program/src/processor.rs])

### Summary
`process_deposit` computes the amount of the "other" token and the minted LP amount purely from the *current* on-chain pool ratio (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`), and only rejects the deposit if the computed "other" amount exceeds `deposit.max_coin_amount`/`deposit.max_pc_amount` (upper bound) or, if the caller supplied it, falls below the *optional* `other_amount_min` (lower bound). Because `other_amount_min` is an `Option<u64>` that a caller can simply omit, an attacker can sandwich a deposit transaction — moving the pool ratio in the direction that reduces `mint_lp_amount` for a fixed `max_coin_amount`/`max_pc_amount` — and profit from the depositor receiving proportionally fewer LP tokens for their capital, exactly analogous to the "Ineffective slippage control" issue described for Lockbox V2's `deposit` instruction, which also derives requested liquidity from the manipulable current on-chain price.

### Finding Description
`DepositInstruction` carries `max_coin_amount`, `max_pc_amount`, `base_side`, and an **optional** `other_amount_min`: [1](#0-0) 

During unpacking, if the instruction data does not include the extra 8 bytes, `other_amount_min` is simply `None`: [2](#0-1) 

In `process_deposit`, the pool's current reserves (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) are read live from the vault balances and used to build an `InvariantToken`, which determines the exchange rate at the *current* on-chain price: [3](#0-2) 

For the `base_side == 0` (base coin) case, `deduct_pc_amount` is derived from `deposit.max_coin_amount` at the current ratio, and only checked against the **upper bound** `max_pc_amount` unconditionally; the lower bound (`other_amount_min`) is only enforced `if deposit.other_amount_min.is_some()`: [4](#0-3) 

`mint_lp_amount` is then computed strictly from `deduct_coin_amount` (fixed by the user as `max_coin_amount`) and the *current* `total_coin_without_take_pnl`, with no independent floor on the LP amount received: [5](#0-4) 

The symmetric `base_side != 0` path has the identical structure — mandatory upper-bound check, optional lower-bound check, and `mint_lp_amount` computed only from the fixed input amount and current pool ratio: [6](#0-5) 

Because `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are read live from vault balances at execution time, an attacker can, in the same slot/bundle, execute a swap that shifts the pool ratio in the direction that decreases `mint_lp_amount` for the victim's fixed `max_coin_amount` (or `max_pc_amount`) — the same direction where the mandatory "excess" check (`deduct_pc_amount > max_pc_amount` or `deduct_coin_amount > max_coin_amount`) is *not* triggered — then reverse the swap afterward to extract value, exactly as described in the reported bug class for Lockbox V2's `get_liquidity_from_token_a`/`increase_liquidity` flow. The root cause is identical: the amount of pool ownership (liquidity/LP tokens) credited to the depositor is derived from a price that can be manipulated within a single attacker-controlled bundle, and the only safeguard against this (`other_amount_min`) is optional rather than mandatory.

### Impact Explanation
A liquidity provider who omits `other_amount_min` (or sets it loosely, which SDK/CLI callers may do since it's optional per the instruction and CLI wrapper) can be sandwiched to receive significantly less LP-token value than the fair-market amount for the tokens deposited, while the attacker profits by capturing the difference through the round-trip swap. This is a direct value-extraction/theft-of-LP-value vector reachable by any unprivileged actor submitting ordinary `Deposit`/`SwapBaseIn`/`SwapBaseOut` transactions in a bundle, satisfying the "concrete theft of user or LP funds" bar. Severity is bounded by the fact that a careful caller who always sets a tight `other_amount_min` is protected, similar to the Medium-risk classification in the original report.

### Likelihood Explanation
The `other_amount_min` field being optional is a deliberate legacy-compatibility feature, meaning many existing integrators (CLI, older clients) may not pass it, and instruction data can be crafted directly by any caller without this field regardless of what higher-level clients do. Sandwiching AMM deposits with a preceding/following swap in the same landed bundle is a well-established, low-cost pattern on Solana, making exploitation practical whenever a depositor's transaction lacks the optional bound.

### Recommendation
Make slippage protection on the "other" side mandatory rather than optional: always require and enforce `other_amount_min` (or otherwise bound `mint_lp_amount` directly with a caller-supplied minimum), removing the `Option` branch so that every `Deposit` instruction call is forced to declare an acceptable lower bound and/or a minimum acceptable LP amount, mirroring the fix recommended for Lockbox V2 of deriving liquidity from parameters agreed upon at signing time rather than solely from the mutable on-chain price at execution time.

### Proof of Concept
1. Pool P has coin/pc reserves `Rc`, `Rp`. Victim submits `Deposit{base_side: 0, max_coin_amount: C, max_pc_amount: M, other_amount_min: None}` expecting `mint_lp_amount ≈ C/Rc * lp_amount` at the current ratio.
2. Attacker front-runs with a `SwapBaseIn`/`SwapBaseOut` that increases `Rc` (coin reserve) relative to `Rp` — e.g., swapping coin into the pool for pc — which decreases the pc-per-coin rate. This keeps `deduct_pc_amount = exchange_coin_to_pc(C)` at or below `M` (so the mandatory `ExceededSlippage` check at `program/src/processor.rs:1206` does not trigger), while inflating `Rc`.
3. Victim's `Deposit` executes: `mint_lp_amount = exchange_token_to_pool(C, Rc_inflated)` at `program/src/processor.rs:1244-1250`, which is materially smaller than it would have been at the pre-manipulation ratio, since `Rc` (the denominator) was inflated. Because `other_amount_min` is `None`, no check catches this.
4. Attacker back-runs with the reverse swap, restoring `Rc`/`Rp` and pocketing the difference, having captured the LP value the victim should have received.
