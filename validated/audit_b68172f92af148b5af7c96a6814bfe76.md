### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing shop-spoofing of otherwise-valid webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, but the HMAC signature that `Request` exposes is computed over the raw HTTP body only. The `shop` (and `topic`, `api_version`, `webhook_id`) values that the gem hands to the app's handler as the trusted tenant identifier are taken straight from HTTP headers, which are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` accepts the request purely based on this body-only HMAC check and then forwards the unauthenticated header value `request.shop` to the app's handler as the webhook's shop identity: [3](#0-2) 

The equality the gem should enforce, but doesn't, is:
`HMAC(secret, signed_bytes)` should authenticate `(shop, topic, body)` as one unit, but in practice `HMAC(secret, signed_bytes) == HMAC(secret, raw_body_only)`, i.e. `shop ∉ signed_bytes`. Since a Shopify app's webhook secret (`api_secret_key`) is shared across *all* shops that install the app, any tenant that installs the app (an ordinary, unprivileged action available to anyone) can trigger legitimate webhooks for their own store, capture a genuinely-signed `(body, hmac)` pair, and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch the payload to the handler labeled with the attacker-chosen `shop`.

The gem's own documentation instructs app authors to treat `data.shop` as the trusted tenant key returned from webhook processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so an app following the documented API is directly exposed to this identity-binding gap: [4](#0-3) 

### Impact Explanation
This breaks the tenant boundary the gem is responsible for enforcing: a webhook payload that is cryptographically valid (correct HMAC) can be attributed to an arbitrary, attacker-chosen shop rather than the shop that actually produced it. Any app that keys per-shop state, background jobs, or business logic off `data.shop` (exactly as the gem's documentation recommends) can be made to apply attacker-supplied webhook content (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) under another merchant's identity — a cross-tenant access/data-integrity issue.

### Likelihood Explanation
Any Shopify merchant can install a public app on their own free development store, at which point they legitimately receive real, correctly-signed webhooks for topics the app has registered. Capturing the `(raw body, X-Shopify-Hmac-Sha256)` pair from one such webhook and replaying it with a different `X-Shopify-Shop-Domain` header requires no special privilege, no secret material, and no interaction with Shopify's servers beyond the attacker's own store — well within the reach of an unprivileged internet user.

### Recommendation
Bind the shop identity (and other routing headers such as topic) into the signed bytes checked by `HmacValidator`, or otherwise cryptographically authenticate them — e.g., by including `shop`, `topic`, and `webhook_id` in `to_signable_string`, or by validating that `shop` in the request matches an active, previously-registered session/shop known to the app before dispatching to the handler. At minimum, the gem should document explicitly that `data.shop`/`data.topic` are NOT authenticated by the HMAC and must not be trusted as tenant identifiers without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets the app register the `orders/create` webhook.
2. Attacker places an order, causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
3. Attacker intercepts/logs `(B, H)` (they own the receiving endpoint or can proxy/log the request before it reaches the app).
4. Attacker crafts a new HTTP request to the same app endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Registry.process` → `Utils::HmacValidator.validate(request)` returns `true` because `Request#to_signable_string` only hashes `B`; the handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` even though the payload originated entirely from the attacker's own store.           raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
