### Title
Webhook `topic` and `shop-domain` headers are trusted identity fields but are excluded from HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw HTTP body only, while `topic`, `shop`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC, then dispatches to a handler keyed on the unauthenticated `topic` header and hands the handler an unauthenticated `shop` field as the tenant identity.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers that are never fed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (which only attests to the raw body bytes), and then uses the unauthenticated `request.topic` to select a handler and passes the unauthenticated `request.shop` straight through as the tenant identity in `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata.shop` and `.topic` are typed constants with no further verification, so whatever the handler receives is taken as ground truth for "which shop" and "which event" occurred: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified-bytes == bytes-the-handler-acts-on`

but here:
`HMAC covers {raw_body}` while `handler acts on {raw_body, topic, shop, webhook_id, api_version}`

Any holder of one valid `(raw_body, hmac)` pair — trivially obtainable by any merchant/tenant who installs the app on their own store and triggers a real webhook — can resend that identical body+HMAC to the app's public webhook endpoint while substituting arbitrary `shopify-shop-domain` and/or `shopify-topic` header values. The HMAC check in `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) still passes because it only recomputes the HMAC over `raw_body`, never over the headers: [5](#0-4) 

This is directly analogous to the reported bug class ("a field acted on but not covered by the HMAC"): the library exposes `shop`/`topic` as verified-looking metadata (bundled inside the same `WebhookMetadata` object that also carries the HMAC-checked body) even though those two fields carry no cryptographic binding to the checked bytes.

### Impact Explanation
An attacker who controls one tenant (their own installed shop) can forge webhook deliveries that the host application will process as if they originated from a different shop, achieving cross-tenant confusion/injection: the app's handler will write, overwrite, or act on data keyed by `data.shop` for a victim tenant using attacker-controlled body content, or trigger a handler registered for a different (spoofed) `topic` than the one that actually produced the signed body. This meets the Critical bar of "cross-tenant access."

### Likelihood Explanation
Any actor who can install the app on a shop they control (an ordinary, unprivileged merchant — no special credentials, tokens, or `client_secret` required) can capture a valid `(raw_body, hmac)` pair from their own legitimate webhook traffic and replay it with forged `shopify-shop-domain`/`shopify-topic` headers to the app's public webhook endpoint. No interaction with Shopify's signing key is needed, since only the body — not the headers — is authenticated.

### Recommendation
Bind `topic`, `shop`, and `webhook_id` into the value that is HMAC-verified (or otherwise independently re-derive/validate them from a Shopify-trusted source, e.g. cross-check `shop` against the session/store the delivery is registered for) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by HMAC verification and must not be used as the sole tenant/event identity by host applications.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
2. Attacker resends an HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since HMAC is only over body)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or a different registered topic (forged)
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. The handler registered for the (possibly forged) topic receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
