### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the HMAC of the raw body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers — none of which are covered by that signature — to build the `WebhookMetadata` passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator computes/compares the signature purely against that signable string: [2](#0-1) 

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all sourced from unauthenticated headers — to construct the identity used by the app's handler, immediately after the body-only HMAC check: [3](#0-2) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [4](#0-3) 

The identity binding that should hold is: `shop_that_produced(signed_body) == shop_attributed_to_this_webhook`. Because `shop-domain` is excluded from the signed bytes, an attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` — trivially available to them by installing the app on their own shop and receiving a legitimate webhook for data they themselves control (e.g. a product they created, an order they placed) — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. The gem will report the HMAC as valid (since it only checks the body) and hand the handler a `WebhookMetadata` claiming the victim shop, topic, and webhook id, even though none of those were signed. The docs explicitly instruct app authors to treat `data.shop` as "The shop domain of the webhook" without any caveat that it must be independently re-validated against signed content: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged internet user who merely has (or can obtain) their own app installation can forge webhook events that the app attributes to a different, victim shop. Any handler logic keyed off `data.shop` (order syncing, inventory updates, fulfillment triggers, per-tenant billing/usage counters, etc.) can be manipulated cross-tenant, i.e. cross-tenant access/data injection using only the attacker's own legitimately-signed traffic as raw material.

### Likelihood Explanation
Moderate-to-high: exploitation requires no secrets beyond what any legitimate (even free/unprivileged) merchant of a multi-tenant app already possesses — a single real webhook delivery to capture a valid `(body, hmac)` pair — plus the ability to POST directly to the app's public webhook endpoint with arbitrary headers, which is inherent to how HTTP webhook receivers are exposed.

### Recommendation
Bind the identity fields into the authenticated data, e.g. include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or, at minimum, require the consuming application to check `shop` against its own list of currently-installed/authorized shops before trusting `WebhookMetadata#shop`), and document this requirement prominently rather than presenting `data.shop` as already-trusted.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `products/create`) for a product the attacker controls, capturing the raw POST body `B` and the real `X-Shopify-Hmac-SHA256` header value `H` (valid because it's HMAC(`B`, api_secret_key), and `api_secret_key` is shared across all shops using the app).
2. Send a new POST request to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-SHA256: H` unchanged, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only recomputes HMAC over `B`: [6](#0-5) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the application processes attacker-supplied data attributed to the victim tenant.

          received_signature = verifiable_query.hmac
