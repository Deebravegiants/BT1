### Title
Webhook `shop` identity is trusted without HMAC binding, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop` from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator` only ever covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header is never included in the signed material, so a valid HMAC only proves "this body was signed with the app's secret," not "this body belongs to this shop." `Registry.process` passes the unauthenticated `request.shop` straight into `WebhookMetadata` and the app's handler.

The identity binding that should hold is:
`shop asserted in the header == shop bound by the HMAC-verified bytes`

only validates `verifiable_query.to_signable_string` (the body) against the HMAC. `Registry.process` then trusts the header value unconditionally: [3](#0-2) 

Because every shop installing the same app shares the single `api_secret_key`, any merchant who has legitimately installed the app (an "unprivileged" party from the app's cross-tenant perspective) can capture a genuine, correctly-HMAC-signed webhook body that Shopify sent for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header to name a different, victim shop. The HMAC still validates (it only checks the body), and the gem hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop, when in fact its `shop` binding was never authenticated.

### Impact Explanation
This breaks a tenant boundary: it allows one shop's operator to inject attacker-controlled webhook payloads that the host application will process as if they came from a different shop's session/store, because the only cross-tenant discriminator (`shop`) is not covered by the cryptographic check. Depending on how the host app uses `WebhookMetadata#shop` (e.g., session lookup, data updates, mandatory GDPR webhooks, order/fulfillment state), this enables cross-tenant data corruption or unauthorized actions attributed to a shop the attacker doesn't own — matching the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Requires only that the attacker run/control one legitimate installation of the target app (a normal, unprivileged merchant account) and be able to POST arbitrary headers to the app's public webhook endpoint, which is by design internet-reachable and unauthenticated apart from the HMAC. No access token, `client_secret`, or privileged access is required.

### Recommendation
Include the shop identity (and ideally topic/api-version) inside the HMAC-covered signable string, or otherwise cryptographically bind the `shop` header to the verified body (e.g., require the host app to cross-check `shop` against a value embedded in/derived from the verified payload) before trusting `request.shop` in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receiving genuine webhooks (e.g. `orders/create`) with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures one such `(body, hmac)` pair.
3. Attacker POSTs the same `body` and `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `body` vs `hmac`) — see [4](#0-3) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, processing it as authentic data for the victim tenant.
