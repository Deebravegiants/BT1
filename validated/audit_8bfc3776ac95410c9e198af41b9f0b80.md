### Title
Predictable, unsigned session cookie enables cross-tenant session hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/auth/oauth/session_cookie.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps (and as a fallback path for embedded apps), `ShopifyAPI::Auth::Oauth.validate_auth_callback` issues a `SessionCookie` whose `value` is simply the `Session#id`, and that id is deterministically derived from public data: `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions. This value is neither signed nor bound to any secret. `ShopifyAPI::Utils::SessionUtils.current_session_id`/`cookie_session_id` later trusts this raw cookie value as the lookup key a host app uses to retrieve the stored `Session` (and its `access_token`).

### Finding Description
The identity binding that should hold is: `cookie value presented by browser == session id that Shopify's OAuth flow legitimately established for that browser`. In practice the equality collapses to `cookie value == f(shop, [user_id])`, a value computable by anyone who knows (or guesses) the target's `myshopify.com` domain — information that is not secret.

- `Session.from` computes `id = "offline_#{shop}"` for offline tokens, or `id = "#{shop}_#{associated_user.id}"` for online tokens: [1](#0-0) 
- `validate_auth_callback` puts this predictable id directly into the browser cookie's `value` for non-embedded apps: [2](#0-1) 
- `SessionCookie` is a plain value/expiry struct with no signature or MAC over its contents: [3](#0-2) 
- `SessionUtils.current_session_id`/`cookie_session_id` return the cookie's value unchanged as the authoritative session identifier, with no cross-check against any authenticated claim (e.g., a JWT `dest`/`sub`) for the non-embedded path: [4](#0-3) [5](#0-4) 

Because the id is only a deterministic function of the shop domain (and, for online sessions, a small/guessable numeric user id), an attacker who knows a target's `shop.myshopify.com` (routinely public/discoverable) can construct a cookie value equal to that shop's `offline_<shop>` session id without ever completing OAuth or possessing any secret.

### Impact Explanation
If a host application follows this gem's own utility (`SessionUtils.current_session_id`) to resolve "the current session" from the cookie and then loads the corresponding stored `Session`/`access_token` from its session repository, an attacker can set this predictable value as their own `shopify_app_session` cookie and have the app's authenticated-request pipeline load and act with the victim shop's access token — a cross-tenant access primitive, matching the Critical "cross-tenant access" impact category. This differs from the OAuth callback HMAC check (which validates the *code exchange*, not the cookie used afterward to key merchant sessions) and from the JWT/session-token path, whose `sub`/`dest` claims are cryptographically signed by Shopify.

### Likelihood Explanation
Exploitability depends entirely on whether the host application persists/looks up sessions by an unauthenticated cookie value returned from `SessionUtils`, as the docs' own OAuth example does (storing the session and reading the cookie's `value` to key it): [6](#0-5) . Shop domains are not secret, and offline session ids require no additional randomness at all, so guessing/constructing a valid target id needs no privileged access, tokens, or TLS interception — only knowledge of the target's `.myshopify.com` handle.

### Recommendation
Do not derive the session cookie value from a predictable function of `shop`/`user_id`. Use an unguessable, high-entropy identifier (e.g., `SecureRandom.uuid`, as already used as the default in `Session#initialize`) for the cookie value, and keep the deterministic `"offline_#{shop}"`/`"#{shop}_#{user_id}"` id purely as an internal server-side lookup key, never exposed as the externally-presented credential. Alternatively, sign/MAC the cookie value (e.g., HMAC with `api_secret_key`) so a bare guess of the shop domain cannot produce a valid cookie.

### Proof of Concept
1. Attacker learns/guesses a target's shop domain, e.g. `victim-shop.myshopify.com` (public/discoverable via storefront, app listing, etc.).
2. Attacker computes the offline session id per the gem's own logic: `offline_victim-shop.myshopify.com` [7](#0-6) .
3. Attacker sets their browser's `shopify_app_session` cookie to this value and requests the app's authenticated route.
4. If the host app follows the documented pattern of resolving the session via `SessionUtils.cookie_session_id`/`current_session_id` and loading the corresponding stored session, the request is treated as authenticated for `victim-shop`, giving the attacker access to the merchant's session/access token without ever completing OAuth for that shop.
