### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by computing an HMAC over the raw request body only, yet the `shop` value that a host application uses to attribute the webhook to a specific merchant/tenant is read from an HTTP header that is completely outside the signed bytes. This breaks the identity binding `signed_bytes == acted_on_identity`, letting any actor who can obtain one validly-signed webhook (e.g., by installing the app on their own store) replay that exact body/HMAC pair with a different `shop-domain` header to make the host app process the payload as if it came from a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read straight from unauthenticated headers, not from the signed payload: [2](#0-1) 

`HmacValidator.validate` (used via the shared `VerifiableQuery` interface) only checks that `hmac == HMAC(secret, to_signable_string)`: [3](#0-2) [4](#0-3) 

Because Shopify signs every webhook for an app with the *same* app-level `client_secret` regardless of which shop sent it, a valid `hmac-sha256` header only proves "this body was really sent by Shopify for this app" — it proves nothing about which shop it came from. The `shop` (and `topic`, `webhook_id`, `api_version`) fields that a host application relies on for tenant routing, deduplication, or authorization decisions are transported via headers that sit entirely outside the HMAC's scope.

This is the direct analog of the reported bug class: in the ITS Hub report, an identity value (the origin chain of a token) was not bound to the value the system trusted for balance accounting, letting an attacker substitute an untracked/attacker-controlled origin. Here, the identity value (`shop`) that gates per-tenant processing is not bound to the HMAC-verified bytes, letting an attacker substitute an arbitrary shop identity while keeping a genuinely-signed body.

### Impact Explanation
An attacker who has (or creates) a legitimate installation of the target app on their own store can capture a validly-signed webhook (body + `hmac-sha256` header). They can then resend it to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) headers swapped to reference an arbitrary victim shop. `Utils::HmacValidator.validate` still returns `true` because the signature check only covers `@raw_body`. If the host application follows the documented pattern of trusting `request.shop`/`request.topic` for tenant-scoped side effects (e.g., updating that shop's stored data, revoking access, marking uninstall, inventory changes) without independently confirming the shop truly owns that payload, this results in cross-tenant data confusion/corruption driven entirely through this gem's trusted `Request` object.

### Likelihood Explanation
The attacker only needs one legitimate app installation (their own store) to obtain a validly-signed webhook sample; no access to the app's `client_secret`, access tokens, or any other privileged credential is required. The header manipulation and replay do not require TLS interception since the attacker controls the HTTP request being sent to the app's own public endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content that `to_signable_string` produces (or otherwise verify these fields independently, e.g., by requiring the caller to supply and check the expected shop out-of-band), so the HMAC binds `shop == the value the host app acts on` rather than only covering the body.

### Proof of Concept
1. App is installed on attacker-owned shop `attacker.myshopify.com`; Shopify sends a legitimately signed webhook: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac-of-body>`, plus `@raw_body`.
2. Attacker captures the exact `@raw_body` and `hmac-sha256` value.
3. Attacker resends the same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request; `Utils::HmacValidator.validate` calls `to_signable_string`, which only hashes `@raw_body`—unchanged—so the signature still validates: [1](#0-0) 
5. The host app, trusting `request.shop` returns `"victim.myshopify.com"`, processes the (attacker-controlled) payload as an authentic event for the victim tenant.
