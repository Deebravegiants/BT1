### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (tenant) identifier from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body. Anyone who possesses one genuinely-signed webhook payload (e.g. from their own shop's installation) can replay it to the app's webhook endpoint with an arbitrary `shop-domain` header value, and it will pass HMAC validation while being attributed to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read directly from an unauthenticated header, entirely outside that signed string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the body only) and `request.hmac`, then immediately trusts `request.shop` when constructing the metadata handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator` itself only ever signs/verifies `verifiable_query.to_signable_string`: [4](#0-3) 

The binding that should hold is:
`hmac == HMAC(secret, body || shop || topic || ...)`

but the actual binding enforced is:
`hmac == HMAC(secret, body)` while `shop (used downstream) == header value (unauthenticated, unbound to hmac)`

Because the `shop` header is not part of the signed material, an attacker who has captured or received one legitimately-signed webhook body (which is trivial to obtain — they can trigger a webhook for their own installed/trial shop, since the app's `api_secret_key` is the same across all shops using that app) can resend the identical body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's `WebhookHandler#handle` via `WebhookMetadata`, which most hosting applications use as the tenant key to look up sessions, update local per-shop database rows, etc.

### Impact Explanation
This breaks the identity binding between the HMAC-authenticated payload and the tenant it is attributed to, allowing an unprivileged, previously-installed merchant/attacker to spoof webhook events as if they came from an arbitrary other shop. Any host application that (as documented/intended) relies on `WebhookMetadata#shop`/`request.shop` from this gem to determine which tenant a webhook body belongs to — without independently re-validating that the shop is one whose data actually produced this specific HMAC-signed body — will process attacker-controlled data under a different tenant's identity. This is a cross-tenant impact: it lets an attacker inject or forge events for a shop they do not own, undermining per-tenant isolation. Since exploitation requires no access token, no `api_secret_key`, and only a previously-captured legitimate webhook body/HMAC, this qualifies as Critical (cross-tenant access) per the identity-binding class described in the prompt.

### Likelihood Explanation
Likelihood is high for an attacker who has ever installed the same app on a shop they control (a common, unprivileged scenario for any Shopify app with public installs) — they can capture one legitimate webhook delivery to their own endpoint/shop and then replay it with a forged `shop-domain` header to the app's webhook receiver. No secret material, TLS interception, or privileged account is required; only observation of one's own legitimately delivered webhook.

### Recommendation
Include the `shop` (and other identity-relevant headers such as `topic`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the signed body before trusting it downstream. At minimum, `Request#to_signable_string` should not treat `shop`/`topic` as out-of-band, unauthenticated values when they are subsequently used as the tenant key by consumers of `WebhookMetadata`. Document/require that any hosting application must independently verify that the `shop` in a webhook belongs to a shop it expects to receive `topic` from, or restore integrity binding at the library level.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}` (attacker-controlled content of their own order)
3. Attacker captures this full raw HTTP request (body + HMAC), since it is delivered to an endpoint they control.
4. Attacker resends the identical body and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute/return values based only on the body, so `HmacValidator.validate` returns `true` (as shown in `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, and the attacker-controlled body, causing the host application to process/store attacker data under the victim's tenant identity.
