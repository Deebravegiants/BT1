### Title
Webhook `shop`, `topic`, and `webhook-id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content used for HMAC verification from the raw request body only, while the shop, topic, and webhook-id used to dispatch and process the webhook come from HTTP headers that are never included in that signature. This breaks the identity binding: `hmac_valid(raw_body) == true` is treated as proof that `request.shop`/`request.topic` are authentic, when in fact only the body bytes are authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled from separate, unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches to the topic's handler using the unauthenticated `shop`/`topic`/`webhook_id` values: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is shared across all shops that install the app, any internet user who installs the app on their own shop receives genuine webhook deliveries with a body and HMAC that are valid for that body content. That `(body, hmac)` pair remains cryptographically valid regardless of which `shop-domain`, `topic`, or `webhook-id` header accompanies it, because those headers are outside the signed content. An attacker can therefore replay a legitimately-received `(body, hmac)` pair to the app's webhook endpoint while substituting a different `shop-domain` (impersonating another tenant) and/or a different `topic` (e.g. claiming a mandatory topic like `shop/redact` or `app/uninstalled`), and the library will report the request as HMAC-valid and hand it to the handler as if it originated from the spoofed shop/topic.

This is the same root-cause pattern as the referenced report: a value that is *acted upon* (shop/topic identity used for dispatch) is not the value that is *actually verified* (only body bytes). In the Balancer case the wrong token address was checked; here the wrong "identity" is trusted because the real one is never bound into the HMAC computation the library relies on for authentication.

### Impact Explanation
This allows a self-service, unprivileged installer of the app to forge webhook deliveries that the host application will treat as authentic events for an arbitrary victim shop, since `WebhookMetadata.shop` (built directly from the unauthenticated header) is what apps use to look up/act on a specific tenant's data. Depending on how the host app's handlers use `data.shop`/`data.topic` (e.g., session invalidation on `app/uninstalled`, data deletion on `shop/redact`/`customers/redact`), this can cause cross-tenant data corruption/deletion or unauthorized actions performed against a shop the attacker doesn't control — a cross-tenant impact.

### Likelihood Explanation
Likelihood is constrained: the attacker must be a legitimate installer of the app on some real shop (self-service, so achievable by any internet user for public/self-serve apps) in order to obtain a valid `(body, hmac)` pair, then replay it against the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers. No secret key, TLS interception, or privileged credential is required beyond normal app installation — this keeps it within scope.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the payload), so that the signature check certifies the full identity tuple actually used to dispatch and process the webhook, not just the raw body bytes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a benign event (e.g., `orders/create`), receiving a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the same body `B` and same valid HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` and/or `x-shopify-topic` to `shop/redact`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC (per `to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`); `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to call the registered handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, `topic: "shop/redact"`, causing the host application to act on the victim tenant as if Shopify itself sent that event.
