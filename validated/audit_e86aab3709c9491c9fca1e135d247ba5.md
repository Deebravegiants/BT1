### Title
Webhook shop identity spoofing via unauthenticated `shopify-shop-domain` header not covered by HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated via `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The shop-domain header is never part of the signed material, so the tenant identity a host application receives from this gem for a webhook is not bound to the signature that authenticates the payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from an HTTP header that is not part of that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the received `hmac` value: [3](#0-2) 

Because Shopify signs webhooks using the app's single `api_secret_key` (shared across every shop that has the app installed) and only the body is included in that signature, the `(body, hmac)` pair is valid for the app regardless of which shop it originated from. The identity binding the host application actually needs — "the HMAC-authenticated payload belongs to shop X" — is never enforced by this gem: `shop` (header) and `hmac`-verified `raw_body` are two independent, uncorrelated inputs. This is exactly the analog class called out in the rules: *a field acted on (`shop`) but not covered by the HMAC*.

An unprivileged user who controls (or has previously received, e.g. from their own store's installation of the same app) one genuinely-signed `(raw_body, hmac)` pair can replay it to the host application's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Request#shop` will return the attacker-chosen shop domain. Any host application that trusts `request.shop` (as documented/intended usage of this gem, e.g. to look up the tenant's session/access token or attribute the payload for processing) will process the request as if it came from a different, victim tenant — a cross-tenant identity confusion enabled entirely by this gem's failure to bind `shop` into the verified signature.

### Impact Explanation
This breaks the binding `hmac-verified(raw_body) == shop`, which the equality the rules define as: *a field acted on (`shop`) but not covered by the HMAC*. The result is that a webhook payload authenticated for the app can be attributed to an arbitrary shop chosen by the caller, giving cross-tenant access/confusion for any host application logic keyed on `Request#shop` (session/token lookup, data attribution, authorization decisions). This matches the Critical impact category "cross-tenant access."

### Likelihood Explanation
Medium-to-High: exploitation requires the attacker to possess at least one genuinely-signed `(raw_body, hmac)` pair for the app (trivially obtainable if the attacker's own shop has the app installed, since webhooks are signed with the app-wide secret, not a per-shop secret) and the ability to send an HTTP request with a forged `shopify-shop-domain` header to the host application's public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Bind the shop identity into the verified signature rather than trusting an unauthenticated header for tenant attribution. Options:
- Include the shop-domain header value in `to_signable_string` (would require Shopify to sign headers, so this is a gem-side documentation/consumer issue) — since Shopify does not include headers in the HMAC, the safer fix is to have this gem clearly document and/or enforce that `shop` must be cross-checked by the host application against a known/expected shop (e.g., the shop tied to the webhook subscription topic/route) before being trusted, and never used as the sole tenant key derived from an unauthenticated field.
- At minimum, add a loud warning/guard in `Request#shop` and in the gem's webhook documentation flagging that this value is unauthenticated and must not be used as the sole basis for tenant/session lookup without additional verification (e.g., validating it matches the shop associated with the specific `webhook_id`/subscription registered by the host app).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook request the app sends them, e.g. body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`, and `secret` is shared across all installs of the app).
2. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256: H` to the host application's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. In the gem, `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, never inspecting the shop-domain header: [4](#0-3) 
4. `request.shop` returns `"victim-shop.myshopify.com"`: [2](#0-1) 
5. The host application's webhook handler, trusting `request.shop` as authenticated, processes the (attacker-controlled/replayed) payload attributed to `victim-shop.myshopify.com`.
