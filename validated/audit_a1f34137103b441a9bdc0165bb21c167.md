### Title
Webhook shop identity spoofing via HMAC scope gap — the `X-Shopify-Shop-Domain` header is trusted while only the raw body is authenticated ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that only covers the raw request body, yet `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shop`, `topic`, `api_version`, and `webhook_id` header values to build the `WebhookMetadata` passed to the app's `WebhookHandler`. This mirrors the report's bug class: a field (`shop`) is acted upon by the code but is not covered by the HMAC that is supposed to authenticate the message, breaking the intended binding `verified_bytes == acted_upon_identity`.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac` using `Context.api_secret_key`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, which are outside the HMAC's coverage: [3](#0-2) 

`Registry.process` validates only the HMAC and then constructs `WebhookMetadata` using the header-derived, unauthenticated `shop` value, handing it directly to the host application's handler: [4](#0-3) [5](#0-4) 

The binding that should hold is: `hmac_valid(raw_body, api_secret_key) == true` implies `shop header is authentic for this raw_body`. In fact the code only proves `raw_body` was produced by someone who knows `api_secret_key` — it says nothing about which shop's `x-shopify-shop-domain` header accompanied it. Because `api_secret_key` is the app's single shared secret (used identically for every installed shop, per `Context.api_secret_key`), any party who can obtain one genuinely-signed `(raw_body, hmac)` pair — e.g., by installing the app on their own store and triggering an event whose body content they control (product/order fields, metafields, etc.) — possesses a valid `(raw_body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain` header is attached to the replayed request. This is exactly the reported bug class applied here: “bytes verified versus bytes parsed” / “a shop authenticated versus the shop stored as a session key” — the HMAC proves body authenticity but the code (and downstream host-app logic keyed on `data.shop`) treats the header shop as if it were equally authenticated.

Compare to `Auth::Oauth::AuthQuery`, which correctly folds `shop` into the signed string: [6](#0-5) 
No equivalent binding exists for the webhook `shop` field.

### Impact Explanation
This directly matches the “Cross-tenant access” High-impact category: an attacker who is a merchant on their own shop (an unprivileged internet user with respect to any other merchant's data) can produce a validly-HMAC'd webhook body and then send an HTTP request with that exact body/HMAC combination to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will validate the HMAC successfully (it only checks the body) and hand the handler a `WebhookMetadata` claiming the event is `shop: <victim>`. Any host application that uses `data.shop` to identify the tenant whose stored access token/session/state should be updated (the intended and documented use of `WebhookMetadata#shop`) will process attacker-controlled `body` content under the victim's identity — enabling cross-tenant data corruption/impersonation without needing the victim's credentials.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on an attacker-controlled shop (available to any merchant for a public app) to obtain one legitimately HMAC-signed webhook body, and (2) the ability to send an arbitrary HTTP POST with modified headers to the app's public webhook endpoint (trivial, since webhook endpoints are open HTTP receivers by design). No access token, `client_secret`, or victim credentials are needed. Likelihood is realistic wherever the host app relies on `WebhookMetadata#shop` as a trusted tenant identifier, which is the gem's documented intended usage.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the authenticated material, or otherwise cryptographically tie the header to the body, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (would require a scheme change since Shopify only signs the raw body — alternatively, verify the header's shop against the shop-specific session/access-token store the app already has for that webhook, rather than trusting the header alone), or
- Have `Registry.process` cross-check the header `shop` against a shop known to be currently registered/installed with a valid session before invoking the handler, and document to consuming apps that `WebhookMetadata#shop` must not be treated as fully authenticated without this cross-check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker performs an action that triggers a registered webhook topic (e.g. `products/update`) with attacker-controlled body content (product title/description fields).
3. Shopify sends the legitimate webhook POST to the app; attacker's own reverse proxy/log captures the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header value (a valid HMAC over that body, since it's their own shop's genuine webhook, requiring no secret knowledge).
4. Attacker resends that exact `raw_body` + `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` returns `true` (only the body is checked) per [2](#0-1) ; `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker content>, ...)` per [7](#0-6)  and invokes the app's handler, which acts on the victim shop using attacker-supplied data.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
