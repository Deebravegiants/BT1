### Title
Webhook shop-domain identity is trusted from an unauthenticated HTTP header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the handler a `shop` value taken from the `X-Shopify-Shop-Domain` header — a value that is never included in the HMAC-signed material. The identity binding "`shop` used to attribute/act on the event" versus "`shop` covered by the HMAC" does not hold, so the tenant attribution of a webhook can be forged independently of body authenticity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) . The HMAC validated in `Registry.process` is computed exclusively over this raw body via `HmacValidator.validate`: [2](#0-1)  and [3](#0-2) .

However, the tenant-identifying field consumed by the handler — `shop` — is read directly from the `shopify-shop-domain` HTTP header and is never part of the signed bytes: [4](#0-3) . After the HMAC check passes, `Registry.process` builds `WebhookMetadata` using this unauthenticated `request.shop` and dispatches it to the app's handler: [2](#0-1) .

The identity binding that should hold is:
```
shop_used_by_handler == shop_that_actually_produced_and_signed_the_body
```
Because `shop` is carried in a header outside the HMAC's signable string, this equality is not enforced by the gem. Any two requests with the same raw body and the same valid HMAC (computed with the app's `client_secret`) will pass validation regardless of which shop-domain header accompanies them. An attacker who is a merchant with the app installed on their own store (or who otherwise legitimately triggers a webhook delivery, e.g. via `app/uninstalled` or any webhook whose body content is attacker-influenced or content-agnostic) can capture a valid `(raw_body, hmac)` pair generated for their own shop, then replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Request#initialize` only checks for the *presence* of the header, not its correspondence to the HMAC-covered payload: [5](#0-4) . `Registry.process` will still accept it as valid because the HMAC only ever protects `@raw_body`: [6](#0-5) .

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which merchant's session/access token/state to act on (the documented and expected usage pattern for this gem's webhook handlers), an attacker can cause the app to process attacker-controlled webhook content under an arbitrary victim shop's identity. This breaks the tenant boundary the HMAC check is meant to enforce and can lead to cross-tenant state corruption (e.g., forcing `app/uninstalled` cleanup logic, cache invalidation, or business logic tied to shop identity to run against a shop the attacker does not control) — a cross-tenant impact.

### Likelihood Explanation
Requires the attacker to already possess at least one valid `(body, hmac)` pair, which is trivial to obtain: install the app on a shop the attacker controls (or self-trigger a webhook) and capture the delivered request. No secret material is required beyond what an ordinary merchant/installer already receives. The only extra step is re-POSTing the same bytes with a different `shop-domain` header value to the app's public webhook endpoint, which is directly reachable by any internet client since webhook endpoints are unauthenticated except for the HMAC check performed by this gem.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook-id`) values in the HMAC-signable string, or alternatively require host applications to independently verify that `request.shop` corresponds to a shop with a currently valid session/installation before trusting it, and document this requirement clearly. At minimum, `Registry.process` should not implicitly treat `request.shop` as authenticated data derived from the HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g. `orders/create`) to the app's webhook endpoint. Attacker records the exact raw request body `B` and the `X-Shopify-Hmac-Sha256` header value `H` — this `H` is a valid HMAC of `B` under the app's real `client_secret`.
2. Attacker crafts a new HTTP POST to the same webhook endpoint using the identical body `B` and identical `H` header, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` (i.e., `B` only) and compares it to `H` — validation succeeds because `B` and `H` are unchanged: [7](#0-6) .
4. `WebhookMetadata` is constructed with `shop: request.shop` returning `"victim-shop.myshopify.com"` from the forged header: [8](#0-7) , [4](#0-3) .
5. The app's registered handler executes with attacker-controlled body content attributed to the victim shop, despite the victim never sending this webhook.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
