### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC authenticity check only covers the raw request body. This breaks the identity binding `shop-domain-used-by-handler == shop-domain-authenticated-by-hmac`, allowing an attacker who legitimately receives one authentic webhook (e.g., for their own store) to replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header, causing the host application to process the event as belonging to the victim tenant.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is read straight from the (unauthenticated) `shop-domain` header: [3](#0-2) [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and if it passes, forwards `request.shop` (the header value) directly into `WebhookMetadata` without any additional binding to the signed body: [5](#0-4) 

`Utils::HmacValidator.validate_signature` computes the signature strictly from `verifiable_query.to_signable_string`, i.e., the raw body only — never the headers: [6](#0-5) 

Because the `shop-domain` header is excluded from the signable string, any `(raw_body, valid_hmac)` pair obtained from one authentic webhook delivery (for a shop the attacker legitimately controls) remains valid under a completely different `shop-domain` header value. An attacker can:
1. Install the target app on their own shop (no special privilege required — any merchant can install a public app) and capture one legitimate webhook delivery, recording its exact raw body and its `x-shopify-hmac-sha256` value.
2. Send an HTTP POST directly to the app's webhook endpoint, reusing the captured raw body and HMAC header unmodified, but replacing `x-shopify-shop-domain` with a victim shop's domain.
3. `Utils::HmacValidator.validate` succeeds (it only checks the body against the secret), so `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: <victim-domain>, ...)`.

The host application, trusting `data.shop` from this gem's public API, will apply the webhook's effects (e.g., data updates, uninstall/redact flows, order/customer events) to the victim tenant's account/state, even though the actual signed payload originated from the attacker's own store.

### Impact Explanation
This crosses a tenant boundary: an app built on this gem, following its documented API (`WebhookMetadata#shop` being trustworthy after `Utils::HmacValidator.validate` passes), can be made to attribute attacker-controlled webhook data to an arbitrary victim shop. Depending on the handler logic this enables cross-tenant data corruption, spoofed mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`), or forced state transitions (e.g. simulating `app/uninstalled`) against a shop the attacker does not own — a Critical "cross-tenant access" impact per the defined scope, achievable by an unprivileged internet user with no credentials beyond operating their own (attacker-owned) shop installation.

### Likelihood Explanation
Likelihood is high: no secret material, no privileged account, and no TLS interception are required. The attacker only needs a webhook subscription firing to their own endpoint (trivial to obtain by installing any app that registers webhooks, or simply causing an event on their own store) to harvest one valid `(body, hmac)` pair, and then a single unauthenticated HTTP request to replay it with a forged header. The vulnerability is inherent to the library's `Request`/`HmacValidator`/`Registry` design, not to any misuse by the host application.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values into the HMAC-signable material, or independently verify that the shop identified by the header matches an expected/authorized value (e.g., a shop the app has an active session/install for) before dispatching to handlers. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop-domain header, and `HmacValidator` should reject requests whose authenticated payload doesn't correspond to the claimed tenant.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; a subscribed webhook (e.g., `orders/create`) fires to the app's endpoint with headers including:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <HMAC over raw_body with api_secret_key>`
   - raw body `B`
2. Attacker records `B` and the HMAC value.
3. Attacker sends a new POST to the same endpoint with:
   - body `B` (unmodified)
   - `x-shopify-hmac-sha256: <same recorded HMAC>` (unmodified)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`, `x-shopify-webhook-id` as desired
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against the secret (lib/shopify_api/utils/hmac_validator.rb:26-31).
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)` (lib/shopify_api/webhooks/registry.rb:198-199), causing the host app to process attacker-controlled data as if it originated from the victim shop.
