Based on the evidence gathered, there is a strong analog to the Jenkins CSRF advisory: a signed authorization payload created for one purpose is structurally identical to a payload for a different, unintended purpose, letting an attacker redirect a relayer's funds by replaying/reusing a signature outside its intended context — exactly the "captured credential used for an attacker-specified action" pattern in the report.

### Title
Cross-context signature reuse allows redirecting relayer fees to an attacker-controlled beneficiary - (File: modules/pallets/relayer/src/accumulate.rs, modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-relayer` uses two independently-implemented "signed redirect" flows that both authorize a beneficiary address to receive a relayer's fees, keyed by the same `(relayer_address, state_machine)` nonce. The message hashed for `withdraw_fees` (`message()` in `withdrawal.rs`) and the message hashed for the beneficiary redirect during `accumulate_fees` (`beneficiary_message()` in `accumulate.rs`) both reduce to `keccak256(nonce, state_machine, beneficiary_bytes)` when a beneficiary is supplied. There is no domain-separation tag distinguishing "this signature authorizes a withdrawal" from "this signature authorizes an accumulate-fee redirect."

### Finding Description
`withdrawal.rs::message()`: [1](#0-0) 

and `accumulate.rs::beneficiary_message()`: [2](#0-1) 

produce byte-identical hashes for the same `(nonce, state_machine, beneficiary)` triple, because SCALE-encoding an unwrapped `Vec<u8>`/`&[u8]` beneficiary is identical in both cases (the `Option` wrapper in `withdrawal.rs::message()` is unwrapped via `if let Some(beneficiary) = beneficiary` before encoding, so no `Option` discriminator byte differentiates the two schemes). Both flows read/increment the *same* `Nonce::<T>` storage item keyed by `(address, state_machine)`: [3](#0-2) [4](#0-3) 

Consequently, a signature a relayer produces off-chain to authorize one specific extrinsic (e.g., `withdraw_fees` for a small pending balance) can be intercepted and submitted by anyone (both `accumulate_fees` and `withdraw_fees` are `ensure_none` unsigned extrinsics dispatched by whoever relays them: [5](#0-4) ) into the *other* call path, since the pallet cannot distinguish which action the relayer intended to authorize. An attacker who observes (or is handed) a relayer's signed `(nonce, chain, beneficiary)` payload for a low-value withdrawal can instead submit it via `accumulate_fees`'s beneficiary-redirect path (or vice versa) to redirect the *entire* current/future accumulated balance to their own address, consuming the relayer's nonce in the process and permanently misdirecting funds.

### Impact Explanation
This allows theft of relayer-owed protocol fees: an attacker forwarding a captured signature into the wrong function redirects the entire `Fees::<T>` balance for that `(state_machine, relayer)` to an attacker-chosen beneficiary, and burns the relayer's nonce so the legitimate action can no longer be replayed. This is a concrete theft-of-funds vector reachable by any unprivileged relayer/observer of the mempool or gossip layer, matching the report's core bug class (an authenticated action's credential material reused in an attacker-chosen context to capture value).

### Likelihood Explanation
Requires the attacker to obtain a relayer's signed payload intended for one of the two flows (e.g., by monitoring the unsigned-extrinsic gossip pool before it's included, since these are `ensure_none` transactions with no submitter binding) and resubmit it against the sibling extrinsic before the legitimate one lands. Given `validate_unsigned`-only spam protection and no explicit action-type tag in the signed message, this is plausible for a moderately sophisticated relayer-facing actor monitoring the transaction pool, but does require timing/observation, so likelihood is medium rather than trivial.

### Recommendation
Add an explicit, distinct domain-separation byte/tag to each signed message (`withdrawal.rs::message()` and `accumulate.rs::beneficiary_message()`) identifying the specific call it authorizes (e.g., prefix with a call-specific discriminator such as `b"WITHDRAW"` vs `b"REDIRECT"`), so a signature valid for one extrinsic can never satisfy verification in the other. Consider also using a single shared nonce space with call-bound context to avoid any future flow reusing the same signing scheme unintentionally.

### Proof of Concept
1. Relayer signs `message(nonce=5, chain=Evm(1), beneficiary=Some(attacker_addr))` intending to call `withdraw_fees` for a small pending balance.
2. Before the relayer's `withdraw_fees` extrinsic is included, an observer extracts the signature from the mempool.
3. Observer submits `accumulate_fees` with a `WithdrawalProof.beneficiary_details = Some((attacker_addr, signature))` and a valid delivery-receipt proof for the same relayer/state machine/nonce.
4. `accumulate.rs` verifies the signature against `beneficiary_message(nonce, state_machine, attacker_addr)` — which is byte-identical to the relayer's original signed payload — succeeds, increments the nonce, and credits `Fees::<T>[state_machine][attacker_addr] += total_fee` (the entire currently-accruing fee, potentially far larger than what the relayer intended to withdraw).
5. The relayer's nonce is now consumed, and funds intended for the relayer's own withdrawal are redirected to the attacker. [6](#0-5) [7](#0-6)
