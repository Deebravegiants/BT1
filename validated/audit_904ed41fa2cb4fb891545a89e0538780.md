### Title
Multisig timelock is measured from transaction *creation* time instead of *quorum-reached* time, allowing pre-queued transactions to instantly bypass a newly-imposed execution delay - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
The custom `MultisigAccountTimeLock` feature added to `multisig_account.move` in this fork is intended to force a mandatory waiting period before a fully-approved multisig transaction can execute (so other owners/monitoring can `reject_transaction` a malicious payload before it fires). However, the elapsed time is computed from the transaction's `creation_time_secs`, not from when quorum was reached or when the timelock was configured. This reproduces the exact bug class from the external report: an action ("queue") is performed far in advance of the protected event ("execute"), and the "delay" check silently treats stale, pre-existing timestamps as already satisfied, letting the protected action fire the instant its other precondition (quorum) is met.

### Finding Description
`can_execute_with_timelock` computes: [1](#0-0) 

```
elapsed = now_seconds() - pending_transaction.creation_time_secs
(override_threshold.is_some() && num_approvals >= override_threshold) || elapsed >= timelock
```

`creation_time_secs` is fixed at `create_transaction`/`create_transaction_with_hash` time and never updated. `validate_multisig_transaction` (the VM prologue gate that authorizes execution of the multisig-controlled resource account) relies on this same check: [2](#0-1) 

Because the delay clock starts at creation rather than at the moment quorum/approval is reached (or at the moment the timelock itself becomes active), any transaction that:
- was created before the timelock was configured/enabled, or
- was created and then simply left pending for longer than `timelock_period` while gathering the remaining approvals,

will have `elapsed >= timelock` already true the instant the last required approval arrives — completely skipping the intended review window. This is structurally identical to `queueWithdraw` being callable far in advance of the protected `withdraw`: the "queue" event (`create_transaction`) is decoupled from the state the delay is supposed to gate (quorum being reached / protection being turned on), so an attacker (or a colluding subset of owners) can pre-stage the clock and later trigger the protected action with zero effective delay.

The custody-relevant consequence: `multisig_account` transactions execute arbitrary payloads *as the multisig resource account* (fund transfers, `add_owners`/`remove_owners`, auth-key rotation via `create_transaction`, code-object/module upgrade transactions, etc.). The timelock exists specifically to give defenders time to detect and `reject_transaction` a malicious payload from a possibly-compromised owner before it executes. This bypass nullifies that protection for any pre-existing or slow-collecting transaction.

### Impact Explanation
Any owner (or minority colluding owners) can queue a transaction that transfers APT/fungible assets out of the multisig, rotates its auth key, or removes/add owners, then simply wait until natural elapsed time exceeds `timelock_period` (or wait for a timelock to be added later as a security response) before soliciting/obtaining the final approval. Execution then proceeds immediately, with no enforced review window, defeating the entire purpose of the timelock control and enabling irreversible custody loss (theft of multisig-held APT/fungible assets, ownership takeover via `add_owners`/auth-key rotation) exactly at the moment defenders believed they had time to react.

### Likelihood Explanation
Likelihood is high in the specific scenario of "add timelock as incident response to a suspected compromised owner" (the primary intended use case per the module's own test suite), since any transaction already pending before the timelock is added instantly bypasses it. It's also trivially achievable by design: an owner colludes with fewer than quorum, creates the transaction, waits out `timelock_period` naturally, then convinces/compromises the final approving owner — execution then bypasses the delay entirely instead of enforcing a fresh wait after the quorum-completing approval.

### Recommendation
Anchor the timelock to the event it is meant to protect, not to transaction creation:
- Track the timestamp at which quorum (`num_signatures_required`) was actually reached (e.g., set/refresh a `quorum_reached_time_secs` field the first time `num_approvals_and_rejections` crosses the threshold), and compute `elapsed` from that timestamp instead of `creation_time_secs`.
- Alternatively/additionally, when `upsert_timelock` is called, require that the timelock apply to all currently-pending transactions from the timelock's activation timestamp forward (i.e., `elapsed = now - max(creation_time_secs, timelock_activation_time_secs)`), so pre-existing pending transactions cannot bypass a newly added timelock.

### Proof of Concept
Existing tests already exercise the mechanism that shows the flaw (they only test the "correct" ordering, not the exploitable one): [3](#0-2) 

Exploit variant (not present in the test suite, but directly derivable from the code):
1. `create_with_owners_and_timelock`/`create` a 2-of-3 multisig with **no** timelock configured yet.
2. Owner A calls `create_transaction(owner_1, multisig_account, MALICIOUS_PAYLOAD)` — `creation_time_secs = T0`. Only 1-of-2 approvals exist; it sits pending.
3. Days later, the multisig owners (or an off-chain security process) call `upsert_timelock(multisig_signer, 3600, ...)` to add a 1-hour review delay for all future/pending executions, believing this now protects pending transaction #1 too.
4. Owner B (compromised or colluding) calls `approve_transaction`, reaching quorum (2-of-2). Since `now_seconds() - T0` is already `>> 3600` (days have passed), `can_execute_with_timelock` returns `true` immediately, and `execute` (via `validate_multisig_transaction`) proceeds with **zero** effective delay — completely bypassing the just-added timelock protection, identical in structure to pre-queuing `queueWithdraw` far in advance of the protected `withdraw` delay in the original report.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
