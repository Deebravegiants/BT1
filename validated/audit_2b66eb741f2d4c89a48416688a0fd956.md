The strongest analog to this report exists in the `BandwidthManager` contract, which prices bandwidth tiers in "18-decimal units" and converts them to the local fee token purely via decimal scaling — with no reference to the fee token's actual USD value, exactly mirroring the `OperationalTreasury` bug's 1:1 USD assumption.

### Title
`BandwidthManager.purchase()` assumes the host fee token is worth exactly $1, mispricing bandwidth if the fee token depegs - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` charges buyers a fee-token amount derived only from decimal rescaling of a governance-set, USD-intended `tierPrice` (18-decimal). It never references the fee token's actual market price, silently assuming 1 fee-token unit == 1 USD.

### Finding Description
Tier prices are documented and set by governance as USD-denominated values (e.g. `TIER1_PRICE_18D` representing "$50"), stored as an 18-decimal number with no currency conversion step: [1](#0-0) [2](#0-1) 

At purchase time, the contract converts the 18-decimal price to raw fee-token units using only the token's `decimals()`, with a divisibility check but no price oracle or FX conversion: [3](#0-2) 

The `feeToken` is explicitly documented as "typically DAI" or another stablecoin — i.e. an ERC-20 that the protocol assumes is pegged 1:1 to USD: [4](#0-3) 

This is the same root-cause pattern as the reported `OperationalTreasury` bug: a USD-denominated amount is silently treated as equal to a fixed quantity of an ERC-20 token, with no live price check. If the configured fee token loses its peg (trades below or above $1), every `purchase()` call charges buyers the wrong amount of real economic value relative to the USD price governance intended — buyers underpay (protocol undercharged, a fee-siphon/loss for the protocol treasury) if the token trades below $1, or overpay if it trades above $1.

### Impact Explanation
Every bandwidth purchase transaction is affected identically and continuously for as long as the depeg persists — this is not a one-off edge case but a systemic mispricing of the protocol's `BandwidthManager` storefront revenue, which is meant to fund the bandwidth subscription economics that gate ISMP message delivery for a `(chain, app)`. A sustained depeg causes the protocol to under-collect (or buyers to overpay) relative to the USD-denominated tier prices set by governance, directly affecting protocol treasury funds collected via `purchase()`.

### Likelihood Explanation
Likelihood is low under normal conditions since the fee token is expected to be a reputable stablecoin, but any unprivileged bandwidth purchaser can trigger the mispricing simply by calling `purchase()` — no special access is required, and the flaw is latent in every call, activating automatically whenever the configured fee token's market price diverges from $1 (e.g. a stablecoin depeg event).

### Recommendation
Incorporate the fee token's actual USD price (e.g. via a price oracle) when converting the 18-decimal, USD-denominated `tierPrice` into fee-token units, rather than assuming a fixed 1:1 peg based solely on `decimals()`. Alternatively, explicitly document and enforce (e.g. via a governance-controlled fee-token allowlist restricted to audited, tightly-pegged stablecoins) that `feeToken` must remain pegged, and provide a governance path to pause/adjust pricing quickly if a depeg is detected.

### Proof of Concept
1. Governance calls `dispatch_set_tiers` setting `TierIndex::TierOne` price to `50e18` (intended to mean "$50").
2. Assume the configured `feeToken` (e.g. a stablecoin) depegs and trades at $0.50 instead of $1.00.
3. A buyer calls `BandwidthManager.purchase(app, TierOne, 1, chain)`. The contract computes `amount = (50e18 * 1) / 10**(18-dec)`, transferring the nominal token amount equivalent to "$50 at $1 peg" — but at the current $0.50 market price, the buyer only pays $25 of real value for a "$50" tier, systematically undercharging the protocol.
