### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` field that is subsequently trusted and handed to the application's webhook handler is read from an HTTP header that is excluded from that signature.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` is required for HMAC verification. For `Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks that `HMAC(secret, request.to_signable_string) == request.hmac`, i.e. only the body is authenticated: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded verbatim into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses as the tenant identity for the event: [5](#0-4) [6](#0-5) 

Because Shopify's webhook `X-Shopify-Hmac-Sha256` header is `HMAC-SHA256(app_secret, raw_body)` — the same shared `client_secret` is used for every shop that installed the app, and the shop domain is not part of the signed material — a valid `(raw_body, hmac)` pair from one merchant remains a valid, signature-passing pair no matter what `shop-domain` header accompanies it. The binding that should hold is:
`shop_the_handler_believes_it_is_for == shop_that_produced_this_signed_body`
but the code only proves `hmac_is_valid_for(raw_body)`, never `hmac_is_valid_for(raw_body, shop)`. This is the same class of bug as the reported `_badDebtMapping[collateral] = ...` issue: an identifier that should be bound into the authenticated data structure (there, an accumulator key; here, a tenant key) is instead accepted from an unauthenticated/unbound source and used to route funds/data to the wrong bucket.

### Impact Explanation
If an attacker (or a compromised/malicious third party observing webhook traffic, logs, retries, or replay infrastructure) can obtain one valid `(raw_body, hmac)` pair for any shop using the app — which is easy since webhook deliveries are plain HTTP POSTs that can be captured, and Shopify itself retries/replays the exact same body+hmac many times — they can resend that exact body to the app's webhook endpoint with an arbitrary `shop-domain` header. `Registry.process` will accept it as authentic and invoke the handler believing the event/data belongs to the spoofed shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., `customers/data_request`, `customers/redact`, `shop/redact`, order/product webhooks used to key database writes), this can cause cross-tenant data corruption, data being attributed to/deleted for the wrong merchant, or a merchant's own webhook data being replayed against another merchant's tenant record — a cross-tenant access/integrity violation.

### Likelihood Explanation
Likelihood is High for any app processing more than one shop's webhooks:
- Webhook payloads for mandatory topics (`customers/redact`, `shop/redact`, `customers/data_request`) are often near-identical or empty (`{}`) across many shops, meaning a valid HMAC obtained from one delivery is trivially reusable as-is for a spoofed shop with zero payload construction effort.
- All that is required is a single previously-observed `(body, hmac)` pair — no cryptographic secret, no access token, and no privileged Shopify credential is needed.
- Webhook receivers are public HTTP endpoints, meeting the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the authenticated material before trusting it:
- Include the `shop-domain` (and ideally `topic`/`api-version`) in `to_signable_string`, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription (e.g., via a server-side lookup of which shop the webhook was registered for) rather than trusting the header outright, and reject the request if there's a mismatch.

### Proof of Concept
1. Attacker captures a legitimately delivered webhook for `victim-a.myshopify.com` (e.g., an empty-body `customers/data_request` webhook), including its raw body and its `X-Shopify-Hmac-Sha256` header value. This is trivial to obtain from logs, proxy captures, or by simply being a merchant with an installed instance of the app themselves.
2. Attacker (or any collaborator who is a legitimate, separately-installed merchant of the same app) crafts a new HTTP POST to the app's webhook endpoint using the identical `raw_body` and identical `hmac-sha256` header, but sets `shopify-shop-domain: victim-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the changed shop header — and the validation passes.
4. `WebhookMetadata.new(topic:, shop: "victim-b.myshopify.com", body:, ...)` is built and handed to the app's `WebhookHandler#handle`, which now processes/acts on data intended for `victim-a` as if it belonged to `victim-b`, without either shop having consented to or produced that combination.
