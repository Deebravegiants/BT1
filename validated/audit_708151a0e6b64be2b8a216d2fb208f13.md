### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches the (unauthenticated) `shop-domain` and `topic` headers straight into the handler. Because the identity fields that determine *which tenant* and *which event* are acted upon are never included in the signed bytes, any holder of one valid `(body, hmac)` pair — trivially obtainable by installing the app on an attacker-controlled development store — can replay that pair with forged `shop-domain`/`topic` headers to impersonate a webhook from a different merchant, exactly mirroring the reported class of bug where a value acted upon (`_wstUSRAmount`) diverges from the value actually covered by the security check (`usrAmount`).

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; the `hmac` accessor reads the `hmac-sha256` header, while `shop`, `topic`, and `webhook_id` are read straight from other headers that are never fed into the signable string.

`Utils::HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately uses the unauthenticated `shop` and `topic` header values to route and label the event: [3](#0-2) 

Because `ShopifyAPI::Context.api_secret_key` is a single value shared across *every* shop installing the app, a merchant/attacker who installs the app on their own store receives legitimately-signed webhooks (any topic, any body) whose `(raw_body, hmac)` pair is valid under that shared secret. The identity binding the check is supposed to enforce is:

`shop header used by the handler == shop that the HMAC signature actually authenticates`

but since the HMAC only authenticates `raw_body`, this equality never holds — the attacker can pair *any* previously-obtained valid `(raw_body, hmac)` with a forged `shop-domain` header naming a victim shop, and a forged `topic` header selecting any handler registered in the app, and `Registry.process` will accept and dispatch it as genuine.

### Impact Explanation
This breaks the tenant boundary the webhook system is meant to enforce: an app's webhook handler will execute business logic (e.g., data updates/deletions, `app/uninstalled` cleanup, `shop/redact` handling, order/customer processing) attributing it to a shop the attacker does not control, using body content the attacker fully chooses (from their own store's webhook) but with headers they forge freely. This is a cross-tenant access / spoofing vulnerability against the app built on this gem, requiring no access token, secret key, or privileged account — only the ability to install the app once on any (attacker-controlled) shop to obtain a valid signed body.

### Likelihood Explanation
Medium-to-High: it requires only self-service app installation on any Shopify store (no credential theft) plus direct HTTP access to the app's public webhook endpoint, both realistic for any unprivileged internet user targeting an app that consumes this gem's `Webhooks::Registry`.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`) in the signable content used for HMAC verification, or otherwise separately bind/verify them (e.g., require the `shop` header to match a shop the caller is authorized for, and validate `topic` against the registration actually associated with the delivered `webhook_id`). At minimum, document and enforce that `request.shop`/`request.topic` must not be trusted unless they are cryptographically bound to the verified payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker captures this exact `raw_body` and `hmac` value (their own webhook, no secret needed).
3. Attacker re-sends a POST to the same endpoint with the identical `raw_body`/`hmac`, but headers changed to `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <any-other-registered-topic>`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the secret.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) looks up the handler for the forged `topic` and invokes it with `shop: request.shop` set to `victim-shop.myshopify.com`, causing the app to process attacker-controlled data as if it originated from the victim's store.
