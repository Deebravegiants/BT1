### Title
Unvalidated `open_time` parameter in `Initialize2` can permanently trap a pool in `WaitingTrade` status, disabling swaps forever - (File: program/src/processor.rs)

### Summary
`process_initialize2` accepts an attacker-controlled `open_time: u64` from the `InitializeInstruction2` instruction data and uses it, without any upper-bound validation, to decide the pool's initial status and to gate the only transition path out of `WaitingTrade`. Every swap entrypoint (`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`) only flips the pool from `WaitingTrade` to `SwapOnly` when `clock.unix_timestamp >= amm.state_data.pool_open_time`. If a pool creator sets `open_time` to an astronomically large value (e.g. near `u64::MAX`), that condition can never be satisfied on-chain, permanently locking the pool out of the `SwapOnly` state.

### Finding Description
In `process_initialize2`, the pool's initial status is derived directly from the unvalidated `init.open_time` field supplied by the caller: [1](#0-0) 

No bound check (e.g. "must be within N days of now") is performed on `init.open_time` anywhere in `process_initialize2` before this assignment; the only other checks in that function are on account ownership/PDA derivation and mint equality, not on the numeric time value itself.

Once stored as `amm.state_data.pool_open_time`, the pool can only leave `WaitingTrade` inside the swap handlers, all of which use the identical pattern: [2](#0-1) [3](#0-2) [4](#0-3) 

This mirrors the structure of the referenced report: a user-controlled time/interval-like parameter is accepted at object-creation time without range validation, and later used in a strict comparison against the current on-chain clock that gates a core state transition. Because `open_time` is a raw `u64` of Unix-seconds, a pool creator can set it to a value so far in the future that `Clock::get()?.unix_timestamp` (an `i64`, bounded by real elapsed time) will never reach it, so the `else` branch that sets `AmmStatus::SwapOnly` in the swap handlers is unreachable for that pool's lifetime.

### Impact Explanation
Any pool created with such an `open_time` becomes permanently unable to service swaps: `swap_permission()` gating aside, the specific `WaitingTrade` branch that would otherwise flip status to `SwapOnly` can never execute, so the pool's core AMM function (trading) is disabled indefinitely. Since `Initialize2` is a permissionless, unprivileged instruction reachable by any pool creator with attacker-chosen instruction data, this can be triggered trivially and irreversibly for any newly created pool (the AMM program exposes no instruction to directly reset `pool_open_time` back to a sane value other than `SetOpenTime` via `process_set_params`, which is restricted to the privileged `amm_owner` signer, not the pool creator).

I was not able to fully verify, within the available search budget, whether the `AmmStatus::WaitingTrade` permission set (`deposit_permission()`/`withdraw_permission()`) still allows liquidity withdrawal while stuck in this state; the enum's permission methods live in `program/src/state.rs` but I did not retrieve their bodies before running out of tool calls. If withdrawal remains permitted in `WaitingTrade`, the concrete impact is a permanent denial-of-service on swapping for the pool (and any LP funds deposited afterward earn no trading fees and the pool is effectively unusable) rather than an outright freeze of principal; if withdrawal is also gated the same way, the impact escalates to a permanent freeze of LP funds. This distinction should be confirmed against `AmmStatus`'s permission implementation before treating this as a confirmed fund-freezing bug rather than a permanent-DoS bug.

### Likelihood Explanation
High reachability, low complexity: any account can call `Initialize2` with a single transaction and fully attacker-chosen `open_time`, with no economic cost beyond the normal pool-creation fee, and no signer/privilege requirement beyond being the pool creator.

### Recommendation
- Validate `init.open_time` in `process_initialize2` against a reasonable bound relative to `Clock::get()?.unix_timestamp` (e.g. reject if `open_time` exceeds `now + MAX_ALLOWED_DELAY`).
- Alternatively/additionally, expose a permissionless or creator-only recovery path (or make the `SetOpenTime` `SetParams` action reachable by the pool creator, not only `amm_owner`) so an accidentally/maliciously oversized `open_time` can be corrected without permanently disabling the pool.

### Proof of Concept
1. Attacker calls `Initialize2` (`program/src/processor.rs::process_initialize2`) supplying `InitializeInstruction2 { nonce, open_time: u64::MAX - 1, init_pc_amount, init_coin_amount }`.
2. Since `init.open_time > Clock::get()?.unix_timestamp as u64`, `amm.status` is set to `AmmStatus::WaitingTrade` [1](#0-0) .
3. Any subsequent call to `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2` checks `(clock.unix_timestamp as u64) < amm.state_data.pool_open_time`, which is always true because `pool_open_time` is near `u64::MAX`, so the branch that would set `SwapOnly` is never taken and swaps continue to fail with `AmmError::InvalidStatus` for the lifetime of the pool [2](#0-1) .
4. The pool remains stuck, unable to ever process swaps, and only the privileged `amm_owner` (via `process_set_params`/`AmmParams::SetOpenTime`) can correct `pool_open_time` [5](#0-4) , which the pool creator (an unprivileged actor) cannot invoke.
