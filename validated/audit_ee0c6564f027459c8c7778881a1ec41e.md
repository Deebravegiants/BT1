### Title
Panic (DoS) from unchecked fixed-size buffer write when converting relayer-submitted BEEFY vote signatures - ([File: evm/rust/src/conversions.rs])

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` copies an attacker-controlled, variable-length `signature` byte vector into a fixed 65-byte array using `copy_from_slice` without validating the length first, causing a runtime panic on any length mismatch.

### Finding Description
The conversion function is: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		...
```

`value.signature` originates from ABI-decoding a caller-supplied `BeefyConsensusProof`/`RelayChainProof` payload — a Solidity `bytes` field of arbitrary length, not a fixed-size type. `Vec<u8>::copy_from_slice` into a `[u8; 65]` array **panics** if `sig_bytes.len() != 65`, rather than returning an error. This is the same bug class as CVE-2018-16422: untrusted external input (there, an esteid smartcard response; here, a relayer-submitted consensus proof) is copied into a fixed-size buffer without a length check first, and the panic corresponds to the CVE's "denial of service (application crash)" impact.

The conversion chain is reachable from a fully unsigned, permissionless path:
- `pallet-beefy-consensus-proofs::submit_proof` accepts a `BoundedVec<u8, MaxProofSize>` proof from any signed account (`Signed` origin, open to anyone) [2](#0-1) 
- `verify_and_apply` ABI-decodes the `PROOF_TYPE_NAIVE` payload as `ismp_abi::ecdsa_beefy::BeefyConsensusProof` and converts it `.into()` a `ConsensusMessage` [3](#0-2) 
- That `Into` conversion flows through `RelayChainProof -> MmrProof`, which maps every `Vote` in `signedCommitment.votes` via `Into::into` — i.e. the vulnerable `From<Vote> for SignatureWithAuthorityIndex` [4](#0-3) 

None of these steps validate that each vote's `signature` field is exactly 65 bytes before the fixed-array copy.

### Impact Explanation
A single vote entry in a submitted BEEFY proof with a `signature` field whose length is not 65 bytes causes an unconditional panic inside `From<Vote>`, before any cryptographic (ECDSA/authority-set) verification occurs. In a Substrate/WASM runtime, an unhandled panic during extrinsic execution manifests as a wasm trap, aborting the current execution context; if not caught at a boundary that gracefully converts it to a dispatch error, this can crash the executing node process or halt block production for validators executing the extrinsic — a denial-of-service impacting the route responsible for delivering BEEFY consensus updates (and, transitively, all ISMP messages gated behind that consensus client). This satisfies the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High. The `submit_proof` extrinsic is intentionally permissionless (signed origin, no additional authorization) so anyone can submit a "NAIVE" BEEFY proof consisting of raw ABI bytes. Crafting a `Vote.signature` field of any length other than 65 (e.g., 0, 64, or 66 bytes) is trivial ABI encoding and requires no cryptographic material, satisfying the low-cost/no-privilege reachability bar for this analog set.

### Recommendation
Validate `sig_bytes.len() == 65` in `From<Vote> for SignatureWithAuthorityIndex` (or change the conversion to a fallible `TryFrom`) and propagate a decode error (e.g. `AbiDecodeFailed`) instead of panicking, mirroring the length checks already used elsewhere in the codebase (e.g. `WithdrawalParamsError::InvalidBeneficiaryAddressLength` in `evm/rust/src/host_params.rs`, or the `ByteVector<N>::decode` length check in `modules/utils/bls-utils/src/ssz/byte_vector.rs`).

### Proof of Concept
1. Construct a `BeefyConsensusProof` ABI payload where `relay.signedCommitment.votes[0].signature` is any byte string with length ≠ 65 (e.g., 64 bytes).
2. Prefix with `PROOF_TYPE_NAIVE` and submit via `pallet-beefy-consensus-proofs::submit_proof` from any signed account.
3. `verify_and_apply` ABI-decodes the payload successfully (ABI decoding does not enforce a 65-byte length on a `bytes` field) and calls `.into()` on the resulting `RelayChainProof`, which calls `From<Vote>` for each vote.
4. `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`, before authority-set/signature verification is ever reached.
