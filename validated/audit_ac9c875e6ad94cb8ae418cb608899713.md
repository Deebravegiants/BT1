### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated headers while the HMAC only signs the raw body, enabling cross-tenant webhook replay — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, and `webhook_id` by reading them directly from HTTP headers, but `to_signable_string` — the value that `HmacValidator` actually verifies — returns only the raw request body. The signature therefore never binds the shop/topic/webhook-id metadata to the payload, so any valid `(raw_body, hmac)` pair can be replayed with a different `shop-domain` header and still pass validation, exactly mirroring the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from (attacker/replayer-controlled at the HTTP layer) headers with no cryptographic tie to that signed value: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., only `@raw_body`) and compares it to the received HMAC — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC once, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed into the app's handler: [4](#0-3) 

Because the signature is computed only over the body, the equality that should hold — `shop_bound_by_signature == shop_header_used_by_handler` — is broken: the HMAC proves "this body was signed with the app's secret," but says nothing about which shop the header claims it came from. A merchant who has installed the app on their own shop and thus legitimately receives (or can trigger) a webhook delivery obtains a valid `(raw_body, hmac)` pair for their own tenant. They can then send that identical body+HMAC directly to the app's webhook endpoint (Shopify does not publish a fixed source IP allowlist that this gem enforces, and the gem performs no such check) with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's session/data store to act on (the documented and expected usage pattern per `docs/usage/webhooks.md`), this allows a malicious merchant to inject Shopify-signed-looking webhook data under another tenant's identity — a cross-tenant data-integrity/access issue. This satisfies the Critical "cross-tenant access" impact bucket, since the trust boundary crossed is exactly a shop-identity binding (the field acted upon by the handler is not the field verified by the HMAC).

### Likelihood Explanation
Any party who can install the app on at least one shop (or who intercepts one legitimate delivery) can capture a valid `(raw_body, hmac)` pair without ever needing `api_secret_key`. Replaying it with a modified header requires only a normal unauthenticated HTTP POST to the app's public webhook endpoint. No credentials, token theft, or privileged access are needed — likelihood is high for any app that trusts `WebhookMetadata#shop`/`#topic`/`#webhook_id` as documented.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material, or independently verify that the `shop-domain` header matches an expected, previously-registered shop for that specific webhook delivery (e.g., cross-check against the webhook's known/associated shop, or require the caller to supply the expected shop and compare it against a value that is itself bound into the HMAC computation). At minimum, document and enforce that `Registry.process` callers must not treat header-derived `shop`/`topic`/`webhook_id` as authenticated unless bound to the signature.

### Proof of Concept
1. Merchant A installs the app on `shop-a.myshopify.com` and receives (or triggers) one legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header value.
2. Merchant A sends a POST directly to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop using the same app) and any desired `x-shopify-topic`/`x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: ..., body: <shop A's data>, ...)`, causing the app to process/attribute shop A's payload as if it belongs to shop B.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
