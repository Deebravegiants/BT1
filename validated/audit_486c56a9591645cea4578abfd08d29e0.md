## Analysis: CallDispatcher's unguarded `dispatch()` allows theft of stranded bridge funds

The bug-class in the Bebop report is "arbitrary attacker-controlled call executed under a trusted contract's own identity, with no check on who triggers it or whose funds are moved." Hyperbridge has a directly reachable analog in `CallDispatcher`, the shared singleton used by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution and by `IntentGatewayV2`'s predispatch/postdispatch flows.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone steal residual bridged funds left on the dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no access control — any address can call it and force the dispatcher to execute arbitrary `Call{to, value, data}` entries using the dispatcher's own address as `msg.sender`. `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept()` mints/unlocks tokens to the dispatcher and executes the bridging user's calldata, but performs no sweep-back of unconsumed balance afterward, unlike `IntentGatewayV2`, which explicitly sweeps dust. Any ERC20 or native balance left on the dispatcher after a calldata-execution flow (e.g., DEX slippage refunds) sits there indefinitely and is stealable by any third party.

### Finding Description
`CallDispatcher.dispatch()`: [1](#0-0) 

The function is `external` with no modifier restricting the caller, and the target calls are made with the dispatcher itself as `msg.sender` — "executes calls in its own context (not via `delegatecall`)" as the docs state: [2](#0-1) 

`HyperFungibleToken.onAccept` mints tokens to the beneficiary (which the docs instruct users to set to the `CallDispatcher` address so the attached calls can spend them) and then dispatches the attacker/user-supplied `Call[]`, with no subsequent sweep of leftover balance on the dispatcher: [3](#0-2) 

The identical pattern exists in `WrappedHyperFungibleToken.onAccept`, including the WETH-mode swap example the docs themselves publish, where a Uniswap `swapETHForExactTokens` call refunds unspent ETH to `msg.sender` — which is the `CallDispatcher`, not the end user — leaving native ETH stranded on the dispatcher: [4](#0-3) [5](#0-4) 

By contrast, `IntentGatewayV2`'s postdispatch flow (`IntentsBase._execute`) explicitly sweeps any dispatcher balance back to the gateway after executing the order's calldata, demonstrating that the protocol is aware residual balances can occur but only guards this in one of the two call sites: [6](#0-5) 

Because `dispatch()` has no ownership/authorization check and no sense of "whose balance this call is allowed to move," an attacker can watch the `CallDispatcher`'s token/ETH balances (a public, shared, chain-wide singleton reused by every HFT deployment and every intent-gateway instance) and, the instant a legitimate cross-chain calldata-execution leaves any non-zero balance behind, call `CallDispatcher.dispatch()` themselves with `Call{to: token, data: transfer(attacker, balance)}` (or a plain native-value call for stranded ETH) to redirect the beneficiary's funds to themselves.

### Impact Explanation
This is concrete theft of user funds delivered via a cross-chain transfer: a bridging user is supposed to receive tokens/ETH (post-swap remainder) at the end of their `send()`, but because the dispatcher performs the transfer as itself and nothing sweeps residual value back to the intended beneficiary, any left-over amount is permanently exposed to theft by an unrelated third party who merely calls the public `dispatch()` function. This satisfies "concrete theft ... of funds" for a single relayed message.

### Likelihood Explanation
High likelihood of occurrence in normal usage: the documented, first-party example itself (`swapETHForExactTokens`, `swapExactTokensForTokens` with a `minAmountOut` slippage bound) routinely leaves an exact-in surplus or an ETH refund on the dispatcher. Exploitation requires only monitoring the dispatcher's balance and submitting one ordinary transaction calling `dispatch()` — no privileged role, no proof forgery, and no race against the depositing transaction's atomicity is needed, since the theft happens strictly after the legitimate `onAccept` call has already completed and left the balance stranded.

### Recommendation
- Add a sweep step to `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` (mirroring `IntentsBase._execute`'s dust-collection pattern) that forces any residual ERC20/native balance left on the dispatcher after calldata execution back to the intended beneficiary (or the gateway, to be tracked as dust) within the same atomic call.
- Alternatively/additionally, restrict `CallDispatcher.dispatch()` to only be callable by a registered set of gateway/HFT contracts (an allow-list or `onlyRegisteredCaller` modifier), so third parties cannot invoke arbitrary calls against the dispatcher's balance at all, removing the "unauthenticated actor can move funds held by a trusted contract" primitive entirely.

### Proof of Concept
1. A user bridges `amount` of `DEST_TOKEN` to chain B via `HyperFungibleToken.send()` with `to = CALL_DISPATCHER` and `data` encoding: `approve(router, amount)` + `swapExactTokensForTokens(amount, minAmountOut, path, recipientAddress, deadline)` as shown in the docs' own example: [7](#0-6) 
2. Suppose instead the calldata is `swapETHForExactTokens` (WrappedHFT/WETH mode) as documented: [8](#0-7)  — the router refunds unspent ETH to `msg.sender` (the `CallDispatcher`), leaving native ETH on the dispatcher after `onAccept` completes.
3. Any third party observes `CallDispatcher`'s balance and calls `CallDispatcher.dispatch(abi.encode([Call({to: attackerReceiver, value: strandedBalance, data: ""})]))` directly (`evm/src/utils/CallDispatcher.sol` line 44), which is unauthenticated and unrestricted, transferring the stranded ETH to themselves instead of the original bridging user.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
