### Title
Order escrow can become permanently unrefundable if the user's address is blacklisted by the input token - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` pays out escrowed ERC20 tokens with a hardcoded `safeTransfer(beneficiary, amount)` where `beneficiary` is always `order.user` — the same address that placed the order. If that address becomes unable to receive the escrowed token (e.g. a USDC blacklist), every code path that can return the user's principal (`cancelOrder` same-chain, cross-chain cancel-from-source/-dest, and even order fills that pay the user's output) reverts unconditionally and permanently, freezing the escrowed funds with no recovery mechanism.

### Finding Description
`IntentsBase._withdraw` releases escrowed tokens by iterating the withdrawal request's token list and calling `IERC20(token).safeTransfer(beneficiary, amount)` for each: [1](#0-0) 

`beneficiary` is decoded directly from the `WithdrawalRequest.beneficiary` field, which every caller sets to `order.user`:
- Same-chain cancellation (`_cancelSameChain`) builds the `WithdrawalRequest` with `beneficiary: order.user` and calls `_withdraw` directly, in the same transaction as the user's `cancelOrder()` call: [2](#0-1) 
- Cross-chain cancellation from the destination chain dispatches a `RefundEscrow` message back to the source chain with `beneficiary` fixed to `order.user`: [3](#0-2) 
- The `onAccept` handler on the source chain then calls `_withdraw` for both `RedeemEscrow` and `RefundEscrow` requests: [4](#0-3) 

There is no field, parameter, or admin override anywhere in the `Order`/`WithdrawalRequest` structs or in `_withdraw` that lets a user (or governance) specify a different payout address. If the escrowed input token (e.g., USDC, or any token with an address denylist/pausable-account feature) blacklists `order.user` after the order is placed, every single call path that would return their escrowed principal reverts:
1. `cancelOrder()` same-chain reverts directly, and can be retried indefinitely with the same result.
2. The cross-chain `RefundEscrow`/`RedeemEscrow` delivery through `EvmHost.dispatchIncoming` catches the revert and deletes the request receipt "so it can be retried": [5](#0-4) 
   but retrying calls the exact same `onAccept` → `_withdraw(beneficiary = order.user)` path, so it reverts again forever — the message can never be successfully delivered.
3. The `onGetResponse` cancel-from-source path (verifying the order was never filled) also calls `_withdraw` with the same fixed beneficiary, so it is equally unrecoverable.

The same issue exists in the Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, whose `withdraw()` function performs a raw `token.call(...transfer(beneficiary, amount)...)` with the identical `beneficiary = order.user` binding: [6](#0-5) 

### Impact Explanation
This results in a permanent freeze of the user's escrowed principal. Once an order's `order.user` address becomes unable to receive the escrowed input token, there is no way — cancel, refund, or otherwise — to move those tokens out of the gateway back to the user, since every payout path is hardcoded to that same address and no alternate beneficiary can be supplied. This is a direct, permanent loss of access to user funds locked in the escrow contract, which meets the bar for a Medium-severity freezing-of-funds finding.

### Likelihood Explanation
This requires only that the input token implement some form of address-based transfer restriction (most notably USDC's blacklist, but also any pausable/permissioned ERC20) and that the order's placing address (`order.user`) subsequently becomes restricted for that token — a scenario explicitly acknowledged as realistic by major stablecoin issuers and previously flagged in the referenced Sherlock report for an analogous funder-refund pattern. Since intent escrows are designed to hold arbitrary ERC20 assets including popular stablecoins, and the order creator's own address is used for both order placement and refund receipt, the likelihood of hitting this path is not negligible over the life of the protocol.

### Recommendation
Decouple the token-recipient address from `order.user` for the specific purpose of receiving refunds/releases, or add a pull-based withdrawal pattern: on `_withdraw` transfer failure, credit an internal balance for `beneficiary` (or allow governance/the user to specify/redirect a payout address, similar to the recommendation in the referenced report) rather than reverting the entire withdrawal, so tokens are not permanently trapped in the contract when the designated recipient cannot receive them directly.

### Proof of Concept
1. User places a same-chain (or cross-chain) order via `IntentGatewayV2.placeOrder`, escrowing USDC as `order.inputs`, with `order.user = attacker/victim address A`.
2. Circle blacklists address `A` for USDC (a real-world, permissionless-to-trigger event outside the protocol's control).
3. User (or anyone, post-deadline) calls `cancelOrder()`. On the same-chain path, `_cancelSameChain` builds a `WithdrawalRequest{beneficiary: A}` and calls `_withdraw`, which calls `USDC.safeTransfer(A, amount)`, which reverts because `A` is blacklisted.
4. For the cross-chain path, the destination `_cancelFromDest` dispatches `RefundEscrow{beneficiary: A}` to the source chain; `EvmHost.dispatchIncoming` invokes `onAccept` → `_withdraw`, which reverts on the same `safeTransfer`; the host deletes the request receipt so the message is "retryable," but every retry hits the identical revert.
5. In both cases there is no way to change the beneficiary or otherwise extract the escrowed USDC — it is permanently stuck in the `IntentGatewayV2`/`IntentsBase` contract.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
