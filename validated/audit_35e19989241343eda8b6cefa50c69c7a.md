### Title
Webhook tenant identifier (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, but exposes `shop`, `topic`, and `webhook_id` as separate values parsed straight out of unauthenticated HTTP headers. `Webhooks::Registry.process` treats `Utils::HmacValidator.validate(request)` success as proof the entire webhook request (including its declared shop) is authentic, then forwards `request.shop` to the application's webhook handler as the identity of the tenant that produced the payload.

### Finding Description
The binding that should hold is: `shop_header == shop_bound_by_hmac`. In this implementation that equality does not hold, because:

- `hmac` is computed by Shopify (and verified here) only over the raw request body: `to_signable_string` returns `@raw_body` [1](#0-0) .
- `shop`, `topic`, and `webhook_id` are read from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no involvement in the HMAC computation at all [2](#0-1) .
- `HmacValidator.validate` only ever inspects `verifiable_query.hmac` and `verifiable_query.to_signable_string` (the body) [4](#0-3) .
- `Registry.process` gates entirely on that HMAC check, then constructs `WebhookMetadata` using `request.shop` as the trusted merchant identity and forwards it to the handler [3](#0-2) .

Because the shop-domain header is never part of the signed material, any party who legitimately receives one valid signed webhook body (e.g., the operator of their own installed store, who receives genuine webhooks addressed to them) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still report success because the raw body (the only signed content) is unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop. If the host application does what this gem's own API implies is safe — trust `data.shop` from a webhook that has already passed this gem's HMAC validation — it will process attacker-controlled data under another tenant's identity, e.g., updating that tenant's local records, provisioning resources against the wrong tenant, or triggering tenant-scoped side effects keyed off `data.shop`.

### Impact Explanation
This breaks a tenant-authentication boundary that the HMAC check is supposed to enforce: the gem advertises `Utils::HmacValidator.validate` / `Registry.process` as validating "this webhook," but the shop identity attached to the validated payload is unauthenticated. This is a cross-tenant access primitive supplied by the gem's own webhook-processing code, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine signed webhook body (trivially obtainable by installing the target app on their own shop and capturing any webhook Shopify sends them) and the ability to send an HTTP request to the app's webhook endpoint with a forged `shopify-shop-domain` header — both are unprivileged-internet-user actions with no need for `api_secret_key`, tokens, or TLS interception.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the declared shop to the verified body before it is exposed via `WebhookMetadata`. At minimum, `Registry.process`/`Request` should not present `shop`/`topic`/`webhook_id` as validated fields once `Utils::HmacValidator.validate` has only confirmed the body's integrity — the API should make clear (or enforce) that these header-derived fields are unauthenticated unless independently corroborated (e.g., cross-checked against a session/shop already known to the app for that webhook subscription).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (shop `attacker.myshopify.com`) and captures a legitimate webhook Shopify sends to the app, including its valid `x-shopify-hmac-sha256` header and raw JSON body.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and succeeds, since the shop header is not part of the signed string [5](#0-4) [6](#0-5) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, and performs whatever tenant-scoped action the app implements for that webhook topic under the victim's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
