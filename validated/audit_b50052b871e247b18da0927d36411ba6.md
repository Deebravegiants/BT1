This confirms the exploit path: the gem's documentation explicitly instructs developers to trust `data.shop` (`docs/usage/webhooks.md:14,26`) for tenant routing (e.g., `shop_domain: data.shop`), while the HMAC validation in `ShopifyAPI::Utils::HmacValidator.validate` only covers the raw request body via `to_signable_string` returning `@raw_body` [1](#0-0) , never the `shop-domain` header that `WebhookMetadata` exposes as `shop` [2](#0-1) .

### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks is computed only over the raw request body. This breaks the identity binding `authenticated(shop) == shop used for tenant routing`, allowing any party who can produce one valid `(body, hmac)` pair for the app's shared `client_secret` to relabel that payload as belonging to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header [3](#0-2) . `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) using the app's single, shop-independent `Context.api_secret_key` and compares it to the `hmac` header [2](#0-1) [4](#0-3) . The `shop` value is then handed unverified to the app's handler as `WebhookMetadata` [5](#0-4) . Because the same `client_secret` authenticates webhooks for every shop that installs the app, a merchant who installs the app on their own store (an "unprivileged internet user" relative to other tenants) can capture a legitimate `(body, hmac)` pair delivered to their own webhook endpoint and replay it to the app's webhook URL with the `shop-domain` header rewritten to a victim shop's domain. The HMAC check still passes because it never binds `shop` — only the body — to the signature. This exactly matches the documented library usage pattern that trusts `data.shop` for tenant identification and job dispatch (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) .

### Impact Explanation
This is a cross-tenant boundary violation: an attacker-controlled webhook body is processed under the identity of a different, victim shop, since the host application (following the gem's own documented pattern) uses the unauthenticated `shop` field to route data/state per tenant. Depending on the handler's use of `data.shop` (e.g., to look up the session/access token for that shop or to write records against that shop's database row), this can lead to cross-tenant data injection or corruption using another tenant's identity — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that has been installed by at least one attacker-controlled/malicious merchant, since:
1. The `client_secret` is shared across all shops for a given app (not per-shop), so any legitimately delivered webhook to the attacker's own shop yields a valid `(body, hmac)` pair usable against any shop.
2. The gem provides no protection or warning that `shop` is unauthenticated relative to the HMAC, and its own documentation encourages using `data.shop` directly for tenant dispatch.
3. No additional secret or nonce ties the `shop-domain` header to the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable content that `HmacValidator` verifies, or otherwise cryptographically bind the claimed `shop` to the payload before exposing it via `WebhookMetadata`. At minimum, document prominently that `shop`, `topic`, and other headers are not integrity-protected by the HMAC and that host applications must independently corroborate the shop identity (e.g., cross-checking against the shop tied to the resource IDs in the signed body, or maintaining a webhook-id/shop registry from prior registration) before trusting it for tenant routing.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one such delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker (or any party with network access to the app's public webhook endpoint) resends a request to the app's webhook URL with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` [3](#0-2) ; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` using the app-wide secret [7](#0-6) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` [5](#0-4) , causing the host app to process attacker-controlled content under the victim shop's tenant context.
