### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the **unauthenticated** `shop-domain` header straight to the app's handler as the tenant identifier. Because Shopify signs webhooks with the app's single shared `api_secret_key` (not a per-shop secret) and the signature never covers the shop header, any shop that has legitimately installed the app can capture one of its own genuinely-signed webhooks and replay it with a forged `shop-domain` header, causing the target app to process attacker-controlled data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` as a plain header read, independent of the signed payload: [1](#0-0) 

The value used for HMAC verification, `to_signable_string`, is only the raw JSON body: [2](#0-1) 

`Registry.process` verifies only that body-derived HMAC, and then immediately trusts `request.shop` to build the `WebhookMetadata` passed into the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's `api_secret_key`: [4](#0-3) 

The equality that this breaks:
`shop authenticated (i.e., cryptographically bound into the verified signature)` ≠ `shop acted upon (the header value handed to the handler as the tenant key)`.

Since Shopify uses one shared `client_secret` per app (not per shop) to sign all webhooks for that app, the HMAC only proves "this body was signed by Shopify for *some* installation of this app" — it proves nothing about *which* shop the body belongs to. The shop binding is carried entirely in an unsigned, attacker-modifiable HTTP header.

### Impact Explanation
An unprivileged internet user who installs the target app on their own store (a normal, unprivileged action for any public/custom app) receives real webhooks from Shopify that carry a valid HMAC for arbitrary bodies they can influence (e.g. `products/create`, `orders/create` with content they control on their own store, or fixed-content mandatory topics like `shop/redact`). They can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will accept it as valid (HMAC checks out) and invoke the app's handler with `data.shop` set to the victim's domain and `data.body` set to attacker-controlled content. Any host application that uses `data.shop` to look up the tenant/session record and apply the webhook body (essentially all webhook handlers, per the gem's own documented usage in `docs/usage/webhooks.md`) will apply attacker data to another tenant's records — a cross-tenant data-integrity/confusion vulnerability that could be leveraged to inject spoofed orders/products/customer data, or trigger tenant-scoped side effects (e.g. redaction/GDPR handlers) against a shop that never actually sent the webhook.

### Likelihood Explanation
Requires only: (1) installing the target app on an attacker-owned store, which is unprivileged and self-serve, and (2) sending a forged HTTP request with a copied HMAC/body and a modified header to the app's public webhook endpoint. No secrets, tokens, or privileged access to the victim shop are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed material verified against a per-shop or Shopify-issued canonical value, or additionally verify that `request.shop` matches a shop for which the app holds an active installation/session **and** was the actual recipient of that specific event (e.g., cross-check against Shopify's `X-Shopify-Webhook-Id` via a follow-up API call, or bind the shop into an application-level secondary check) rather than trusting the header purely because the shared-secret HMAC over the body validates.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `products/create`) with body `B`; Shopify sends: headers `x-shopify-topic: products/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: H`, body `B`, where `H = HMAC_SHA256(api_secret_key, B)`.
3. Attacker resends to the app's webhook endpoint with the same `body: B` and `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — matches `H`, validation passes (see [5](#0-4) ).
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` but `body == B` (attacker-controlled), even though `victim-shop` never sent this webhook.
