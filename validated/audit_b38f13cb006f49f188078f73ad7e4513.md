Audit Report

## Title
NULL Pointer Dereference via Unchecked `req.Params` in Vault `handlePublicKeyGet` - (File: core/capabilities/vault/gw_handler.go)

## Summary
`HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` requests directly to `handlePublicKeyGet` without routing them through `GatewayVaultRequestProcessor.ProcessRequest`, which is the only place in this file that performs a `req.Params == nil` check before dereferencing. `handlePublicKeyGet` unconditionally executes `json.Unmarshal(*req.Params, r)`, so a request with `Params` omitted causes a nil-pointer dereference panic.

## Finding Description
In `HandleGatewayMessage`, `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` are all routed through `h.requestProcessor.ProcessRequest`, whose per-method handlers (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) each explicitly check `if req.Params == nil` before unmarshalling [1](#0-0) . `MethodPublicKeyGet`, however, is dispatched directly to `handlePublicKeyGet` with no equivalent check anywhere in the call path [2](#0-1) , and `handlePublicKeyGet` unconditionally dereferences `req.Params`: [3](#0-2) .

Note that the other terminal handlers (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, `handleSecretsList`) in this same file *also* directly dereference `*req.Params` without a local nil check [4](#0-3) , but they are safe because they are only reached after the earlier nil-check performed inside `ProcessRequest`/the corresponding `process*Request` function has already succeeded — `handlePublicKeyGet` has no such precondition guaranteed anywhere.

## Impact Explanation
This is a genuine unguarded nil dereference reachable via `HandleGatewayMessage`, which would panic the goroutine handling that gateway message when a `public_key.get` request omits `params`. This maps to a denial-of-service class of bug in the Vault capability's gateway handler, consistent with the reported "CMS/OpenSSL analog" NULL pointer dereference pattern.

## Likelihood Explanation
`MethodPublicKeyGet` performs no prior authorization or nil-check gate, and a JSON-RPC request omitting the optional `params` field is trivially constructible. The precondition — being able to submit a gateway message addressed to a Vault handler for this method — is the same precondition assumed by the finding itself; I could not verify from the available code whether there is an additional authentication/authorization layer (e.g., in the gateway-side `core/services/gateway/handlers/vault/handler.go` or JWT/allowlist checks) that filters or rejects malformed/unauthenticated requests before they ever reach the node's `HandleGatewayMessage`. My tool budget was exhausted before I could fully confirm whether gateway-side validation (codec-level `missing params` rejection seen in `core/services/gateway/api/jsonrpccodec_test.go`, or handler-level checks in `core/services/gateway/handlers/vault/handler.go`) would block this request before it reaches the node, which is material to whether an "unprivileged" attacker can actually trigger it end-to-end.

## Recommendation
Add an explicit `if req.Params == nil` guard at the top of `handlePublicKeyGet` mirroring the pattern used in `processCreateSecretsRequest`/`processUpdateSecretsRequest`/`processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`, returning `api.UserMessageParseError` (or an equivalent `InvalidVaultParamsError`) instead of dereferencing a nil pointer.

## Proof of Concept
Construct a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, ID: "1"}` with `Params` left `nil` and pass it to `GatewayHandler.HandleGatewayMessage`. This routes to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` on a nil `*json.RawMessage`, panicking. [3](#0-2)
