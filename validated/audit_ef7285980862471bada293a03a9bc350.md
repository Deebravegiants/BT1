### Title
Front-runnable pool creation via `Initialize2` lets an attacker permanently seize a market's deterministic PDAs and force a malicious initial price ([File: program/src/processor.rs])

### Summary
`process_initialize2` derives every pool-identity account (AMM info, coin/pc vaults, LP mint associated seed, target orders) deterministically from the caller-supplied `market_info` pubkey using fixed seed constants, with no requirement that `market_info` be validated as a specific, already-agreed-upon market before the pool is created. Because there is no per-creator or per-attempt nonce in the derivation, whoever's `Initialize2` transaction lands first for a given `market_info` value permanently owns that pool's address space and dictates its initial price (`init.init_pc_amount` / `init.init_coin_amount`) and `open_time`. This mirrors the reported `mintBounty` DDOS pattern where a single string identifier maps 1:1 to a resource with no origin-binding, allowing a malicious actor to front-run and squat the identifier with attacker-chosen parameters.

### Finding Description
`get_associated_address_and_bump_seed` derives the coin vault, pc vault, and AMM account addresses solely from `(program_id, market_account.key, associated_seed)`: [1](#0-0) 

These derived accounts are then created via `generate_amm_associated_spl_token` / `generate_amm_associated_account`, which explicitly reject the call with `AmmError::RepeatCreateAmm` if the target PDA is already owned by something other than the System Program (i.e., already claimed): [2](#0-1) [3](#0-2) 

`process_initialize2` accepts `market_info` as "Just a seed for AMM account. Can be any account," and never validates that it is an authentic, program-owned Serum/OpenBook market before deriving and creating the pool's PDAs: [4](#0-3) [5](#0-4) 

The instruction's economic parameters — `nonce`, `open_time`, `init_pc_amount`, `init_coin_amount` — are fully attacker-controlled and packed directly from instruction data: [6](#0-5) [7](#0-6) 

The processor requires only that the vault amount be non-zero (`amm_coin_vault.amount == 0` check), not that it reflect any fair/expected ratio: [8](#0-7) 

Since the swap price and LP-share accounting are subsequently normalized directly from these vault balances (`x`, `y` used for `target_order.check_init` and the initial `lp_amount`): [9](#0-8) 

any account can be watched in the mempool/observed on-chain (mint pairs and markets are public), then front-run: an attacker submits `Initialize2` for the same `market_info` first, funding the vaults with a minimal, heavily skewed ratio (e.g., depositing 1 unit of coin against a large amount of pc, satisfying only the "non-zero" check) and an arbitrary `open_time`. Once this succeeds, the deterministic PDA is permanently claimed — the legitimate creator's later `Initialize2` for the same market fails at the very first `generate_amm_associated_spl_token` call with `RepeatCreateAmm` (or, if it somehow got past vault creation, at the `AmmInfo::load_mut`/`status != Uninitialized` check yielding `AlreadyInUse`): [10](#0-9) 

Because there is no retry namespace (no per-user seed, no incrementing nonce for a new attempt), the market is permanently stuck with the attacker's skewed-price pool: legitimate liquidity providers who subsequently deposit into (or swap against) this pool inherit the attacker's engineered mispricing and can be arbitraged/drained by the attacker via a follow-up swap, exactly analogous to how the referenced `mintBounty` DDOS lets a malicious user permanently occupy `bountyIdToAddress[_bountyId]` with attacker-chosen `_initOperation` data before the legitimate organization's transaction lands.

### Impact Explanation
This is High severity because it lets an unprivileged attacker permanently seize the canonical pool address for any market and dictate the pool's genesis price/state with minimal capital, either (a) permanently denying the legitimate pool creator the ability to ever instantiate the intended pool for that market (since the PDA derivation has no alternate path), or (b) planting a pool at an adversarial price ratio that subsequent depositors/swappers interact with, enabling the attacker to extract value from later liquidity providers and swappers who assume the pool was created honestly — an insolvent/mispriced pool state directly reachable from a single attacker-controlled transaction.

### Likelihood Explanation
Likelihood is high: `market_info` and mint pairs are public on-chain data, `Initialize2` is callable by anyone (`onlyProxy`-style privilege is absent — only `user_wallet_info.is_signer` is required), and the attacker only needs to win a race (front-run) with a minimal-value pool creation transaction, a pattern already economically incentivized on Solana via priority fees/MEV.

### Recommendation
Bind the pool's identity to more than the bare `market_info` key — e.g., require `market_info` to be validated as owned by the expected market/openbook program before derivation, or additionally seed the PDA derivation/validate initial ratio against an oracle-independent invariant (minimum liquidity value, or a commit-reveal / allow-list scheme for the intended creator) so that a race on `Initialize2` cannot let an arbitrary low-value deposit permanently fix the pool's genesis price for a market.

### Proof of Concept
1. Attacker observes (via RPC or the target's own pending/soon-to-be-submitted transaction) the `market_info` pubkey, `amm_coin_mint`, and `amm_pc_mint` that a legitimate user intends to use for `Initialize2`.
2. Attacker derives the same PDAs via `get_associated_address_and_bump_seed(program_id, market_info, {AMM_ASSOCIATED_SEED, COIN_VAULT_ASSOCIATED_SEED, PC_VAULT_ASSOCIATED_SEED, ...})` (deterministic, no secret needed).
3. Attacker submits `Initialize2` first with a higher priority fee, supplying the same `market_info`/mint accounts but attacker-chosen `init_coin_amount = 1`, `init_pc_amount = <large>` (or vice versa) to fix an extreme price, and `open_time = 0`.
4. Attacker's transaction succeeds; `amm.status` becomes `SwapOnly`/`WaitingTrade` and all PDAs for that market are now owned/initialized.
5. The legitimate user's `Initialize2` transaction for the same market subsequently fails at `generate_amm_associated_spl_token` (`AmmError::RepeatCreateAmm`, program/src/processor.rs:378-381) or at the `AmmInfo` status check (`AmmError::AlreadyInUse`, program/src/processor.rs:845-847) — permanently.
6. Any user who now deposits into or swaps against this pool inherits the attacker-engineered skewed price, which the attacker can arbitrage in a follow-up transaction.
