### Title
Webhook `shop` and `topic` identity is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC signature it validates only covers the raw request body. The `shop` and `topic` values that the handler receives and acts on are taken verbatim from HTTP headers that are never part of the signed material, so a captured, validly-signed webhook payload can be replayed with a different `shop-domain`/`topic` header and will still pass HMAC validation.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field using a constant-time compare: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body, while `hmac`, `topic`, and `shop` are all read independently from HTTP headers: [2](#0-1) [3](#0-2) 

`Registry.process` only checks the HMAC before dispatching, then trusts `request.shop` and `request.topic` unconditionally when constructing the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documentation explicitly claims the full request is verified as coming from Shopify: [5](#0-4) 

This breaks the identity binding: `shop-domain header used by the handler` ≠ `shop covered by the HMAC-verified bytes`. Because the `hmac-sha256` header authenticates only `raw_body`, an attacker who has legitimately received one valid webhook delivery for a shop they control (e.g., their own development/test store, or an app-uninstall/GDPR webhook they can trigger themselves) can resend that exact `body` + `hmac-sha256` header to the same endpoint while substituting `shopify-shop-domain` (and optionally `shopify-topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim shop>, body: <attacker's own captured body>, ...)`. Any multi-tenant app that keys per-shop state, entitlements, or subscription data off `data.shop` — exactly as shown in the gem's own webhook-handler example (`shop_domain: data.shop`) — will apply the attacker's payload to the victim tenant's record.

### Impact Explanation
This crosses a tenant boundary: data or side effects nominally originating from one shop can be attributed to another shop the attacker does not control, purely by manipulating headers that carry no cryptographic binding. Depending on the topic replayed (e.g., `app/uninstalled`, `shop/redact`, `orders/create`), this can trigger deletion of a victim's data, false order/customer records, or a downgrade/cancellation flow — a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs a single legitimately signed webhook body from any shop (including one they control) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — no access to `api_secret_key`, tokens, or the target shop's credentials is required. The library performs no cross-check between the authenticated bytes and the asserted shop/topic, so any host application that follows the documented integration pattern verbatim is affected.

### Recommendation
Bind `shop` and `topic` into the signed material the HMAC validator checks, or otherwise validate that the `shop-domain`/`topic` headers are consistent with an independently verified source (e.g., cross-reference against a known/registered shop and expected topic for the receiving endpoint) before constructing `WebhookMetadata`. At minimum, update `Utils::VerifiableQuery`/`Request#to_signable_string` so header-derived identity fields participate in the HMAC comparison, and update the documentation to no longer claim these fields are verified.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers (or receives) a legitimate webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header value Shopify computed for that body.
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and, if desired, a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence, not correctness, is checked) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `raw_body`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to process attacker-controlled data as if it belongs to the victim shop.
