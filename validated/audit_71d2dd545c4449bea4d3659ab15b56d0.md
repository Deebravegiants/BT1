## Title
NULL/panic dereference on empty BEEFY commitment payload in `submit_proof` (naive path) - (File: `evm/rust/src/conversions.rs`)

### Summary
`pallet-beefy-consensus-proofs::submit_proof` accepts a signed, permissionless proof submission with a `PROOF_TYPE_NAIVE` prefix, ABI-decodes it into `ismp_abi::ecdsa_beefy::BeefyConsensusProof`, and converts it into the runtime's SCALE consensus types via `.into()` before any cryptographic verification runs. That conversion chain bottoms out in `impl From<Commitment> for SpCommitment` in `evm/rust/src/conversions.rs`, which calls `iter.next().expect("commitment has at least one payload entry")` on the attacker-supplied `payload` array. Solidity ABI-encoding permits a zero-length dynamic array, so a submitter can craft a `Commitment.payload = []` and trigger this `.expect()`, panicking the runtime during extrinsic execution — the same class of bug as CVE-2021-45769 (NULL pointer/panic from missing input-length validation before message parsing).

`abi_proof.into()` walks: `BeefyConsensusProof -> ConsensusMessage` (`evm/rust/src/conversions.rs:391`) → `RelayChainProof -> MmrProof` (`conversions.rs:368`) → `value.signedCommitment.commitment.into()` → the vulnerable `Commitment -> SpCommitment` conversion at line 334-354, which unconditionally indexes the first payload element with `.expect(...)`.

Because `BeefyConsensusProof` is decoded purely via ABI type-checking (`abi_decode_params`), an empty `payload` dynamic array is a perfectly valid ABI value — there is no length check before the `.into()` conversion runs, unlike the many other places in this same codebase (`node_codec.rs`, `sync-committee/verifier`, `pharos/spv.rs`) that were explicitly hardened against exactly this "adversarial-input causes `.expect()`/`.unwrap()` panic" bug class.

`submit_proof` is a signed extrinsic callable by anyone (it is the reward-claiming entry point for provers), so any account can submit this crafted payload: [3](#0-2) 

### Impact Explanation
A panic inside pallet logic during extrinsic dispatch, in a `#[transactional]`/normal (non-unsigned-validated) FRAME pallet call, aborts execution of that transaction inside the runtime — in a WASM/host-panic-handling model this typically surfaces as a runtime execution failure, but on native execution or in test/production configurations without panic=abort safety nets it can crash the block-authoring/validating process, taking down collator/validator nodes that include or import the offending block. This matches the "unable to deliver messages" / DoS class explicitly in scope (route unable to deliver messages) rather than a fund-theft primitive: a reliably-triggerable panic in the path that ingests BEEFY consensus updates can stall consensus-state updates for the whole bridge, since `pallet-beefy-consensus-proofs` is the on-ramp for BEEFY finality used by `pallet-ismp` message verification.

### Likelihood Explanation
High: `submit_proof` requires only a normal signed transaction with a valid-looking envelope (no privileged origin, no prior state assumptions) and correctly-shaped ABI encoding except for an intentionally empty `payload` array — trivial to construct offline. The `.expect()` panic fires before any cryptographic/authority-set check, so no valid signatures or MMR proof are needed to reach it.

### Recommendation
Replace the `.expect("commitment has at least one payload entry")` in `impl From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs:334-354`) with a fallible conversion (`TryFrom`) that returns an error for an empty `payload`, and propagate that error through `RelayChainProof -> MmrProof`, `BeefyConsensusProof -> ConsensusMessage`, up to `verify_and_apply`, mapping it to `Error::<T>::AbiDecodeFailed` (or a new `Error::<T>::EmptyCommitmentPayload`) instead of panicking. Apply the same fix to the other `.expect()`s in this file (`evm/rust/src/conversions.rs:340,347,351,363,371,404,409`) that convert attacker-reachable ABI-decoded numeric fields via `try_into().expect(...)`, since oversized `blockNumber`/`validatorSetId`/`authorityIndex` values are equally attacker-controlled inputs to the same submission path.

### Proof of Concept
1. Construct a Solidity `Beefy.BeefyConsensusProof` value where `relay.signedCommitment.commitment.payload` is an empty array (`[]`), ABI-encode it as the parameters expected by `abi_decode_params`.
2. Prefix the encoded bytes with `PROOF_TYPE_NAIVE` (byte `0x00`) to form the `proof` argument.
3. Submit `BeefyConsensusProofs::submit_proof(proof)` as any signed account.
4. Execution reaches `verify_and_apply` → `PROOF_TYPE_NAIVE` branch → `abi_proof.into()` → `Commitment::into()` → `iter.next().expect("commitment has at least one payload entry")` panics, since `payload.into_iter().next()` is `None`.
