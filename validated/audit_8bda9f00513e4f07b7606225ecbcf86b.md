### Title
Webhook `shop-domain` header is not covered by HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body, while the `shop` (from the `X-Shopify-Shop-Domain` header) and `topic` fields are read separately and passed on trusted, unauthenticated. `Registry.process` validates the HMAC over the body only, then forwards `request.shop` straight to the app's handler as the tenant identifier. This breaks the intended binding: `shop_authenticated_by_hmac == shop_used_for_tenant_dispatch`.

### Finding Description
`VerifiableQuery` requires implementers to supply `hmac` and `to_signable_string`, and `HmacValidator.validate` computes the signature purely from `to_signable_string`: [1](#0-0) 

For OAuth's `AuthQuery`, `to_signable_string` deliberately includes every security-relevant field (`code`, `host`, `shop`, `state`, `timestamp`): [2](#0-1) 

But for `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers and are never mixed into the signed string: [3](#0-2) 

`Registry.process` validates the HMAC using only that body-derived signable string, then immediately trusts `request.shop` (and `request.topic`) to select the handler and build the metadata passed to app code: [4](#0-3) 

Because `shop-domain` is excluded from the signed bytes, any request carrying a `(raw_body, hmac)` pair that is valid for shop A also produces a valid `HmacValidator.validate` result when the `X-Shopify-Shop-Domain` header is swapped to shop B (or any other shop string). The gem's own webhook-processing pipeline (not host-app misuse) performs this exact bind-then-trust pattern, so this is a defect intrinsic to the gem rather than a case of the host ignoring documented API.

### Impact Explanation
This is a cross-tenant identity-binding break: the byte range the gem cryptographically verifies (`raw_body`) is not the same byte range the gem treats as authenticated for tenant identity (`shop` header). An app relying on `WebhookMetadata#shop` from `Registry.process` (the gem's own recommended integration path) to select the tenant's data store, mark redaction requests as complete, or gate destructive per-shop operations can be made to act on behalf of an arbitrary victim shop as long as the attacker can supply a `(body, hmac)` pair that is valid under the app's `client_secret` — which the attacker can obtain by installing the app on their own store and observing/replaying a genuine webhook delivery, then re-POSTing it to the app's public webhook endpoint with a forged shop-domain header. This falls under the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) installing the target app on an attacker-controlled store to obtain one legitimate `(raw_body, hmac)` pair, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — no access to `api_secret_key`, tokens, or the victim shop is required. The webhook endpoint is, by design, a publicly reachable, unauthenticated HTTP endpoint that only relies on this HMAC check for trust.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` (all `shopify-*` headers relied upon by handlers) in `Webhooks::Request#to_signable_string`, or otherwise bind them cryptographically to the payload before comparing HMACs, mirroring what `Auth::Oauth::AuthQuery` already does for its own fields.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a real webhook delivery with a known topic and body; attacker records the raw POST body and the `X-Shopify-Hmac-Sha256` header value (`hmac_A`), which is valid under `HmacValidator.validate` because it was computed over that exact body.
2. Attacker sends a new POST directly to the app's public webhook endpoint containing the identical raw body and `hmac_A`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all required headers present), and `HmacValidator.validate(request)` succeeds because `to_signable_string` only checks the (unmodified) body: [3](#0-2) 
4. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, even though the HMAC was never computed with that shop in mind: [4](#0-3)

          received_signature = verifiable_query.hmac

        end
