### Title
Webhook shop/topic identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authorizes an inbound webhook solely by validating an HMAC computed over the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers. None of those header-derived identity fields are covered by the HMAC signature, so an attacker who obtains a single valid `(body, hmac)` pair (e.g. from a webhook that Shopify legitimately sent for their own store) can replay that exact body/HMAC directly to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates because it only ever checked the body, letting the attacker make the host application process the payload as if it belonged to a different (victim) shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only ever consider the raw body: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version`, however, are read straight from attacker-controllable HTTP headers with no cryptographic binding to the body that was actually signed: [3](#0-2) 

`Registry.process` validates only the HMAC and then hands off the header-derived (unauthenticated) `shop` to the app's handler: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` confirm this — the only thing ever compared against the signature is `verifiable_query.to_signable_string`, i.e. the body: [5](#0-4) 

This is the same class of bug as the referenced report: a value that is *acted on* (here, the `shop` identity used to route/attribute the webhook to a tenant) is never included in the *authenticated* material (the HMAC-covered body), so the two can be independently manipulated. An attacker who is a legitimate (even free-tier/unprivileged) installer of the target app on their own store can:

1. Register their own reachable HTTP endpoint as the webhook delivery target (or otherwise capture the exact raw body Shopify sends them for a real event), obtaining a genuine `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's single, install-wide `api_secret_key`.
2. POST that exact body and HMAC header directly to the app's public webhook-processing route, but with `x-shopify-shop-domain` (and optionally `x-shopify-topic`) rewritten to point at a victim shop.
3. `Utils::HmacValidator.validate` succeeds (body unchanged, secret unchanged), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-influenced body content.

Because `api_secret_key`/`client_secret` is shared across all installs of the app (not per-shop), no shop-specific secret is required — only possession of one legitimately-signed body, which any installer can obtain from their own store's webhook traffic.

### Impact Explanation
Applications built on this gem rely on `WebhookMetadata#shop` to determine which tenant a webhook event applies to (e.g., `customers/redact`, `shop/update`, `app/uninstalled`, inventory/order sync). Because the gem provides no binding between the authenticated body and the `shop`/`topic` used for dispatch, an attacker can make the host app act on/against a different merchant's tenant using only their own legitimately-obtained signed payload — a cross-tenant access/action primitive.

### Likelihood Explanation
The attacker only needs to be able to install the target app on any shop (widely available to any internet user for public apps) and be able to send an arbitrary HTTP POST to the app's webhook endpoint (which is by definition internet-reachable, since Shopify itself must reach it). No `api_secret_key`, access token, TLS interception, or privileged account is required — the attacker legitimately generates their own valid `(body, hmac)` pair and simply changes an unauthenticated header before delivery.

### Recommendation
Bind the shop/topic identity to the authenticated request instead of trusting headers independently of the signature:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed payload), or
- Require callers of `Registry.process` to supply/verify the expected shop out-of-band (e.g., matching against the shop tied to the session/subscription that registered the webhook) before dispatching to the handler.

### Proof of Concept
1. As an attacker, install the target Shopify app on `attacker-shop.myshopify.com` and configure its webhook subscription's callback URL to point at an endpoint you control (or otherwise capture an outgoing webhook's raw body/HMAC).
2. Capture the exact `raw_body` and `x-shopify-hmac-sha256` header Shopify sends for a real event (e.g., `orders/create`) — this HMAC is valid because it is computed with the app's shared `api_secret_key` over that body only, per `Request#to_signable_string`.
3. Send that identical `raw_body` and `x-shopify-hmac-sha256` directly to the app's public webhook-processing endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (body/secret unchanged), and `Registry.process` invokes the app handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to process/attribute the attacker's payload to the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
