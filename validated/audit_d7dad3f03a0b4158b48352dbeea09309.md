Audit Report

## Title
Attacker-controlled MessageID lets an unprivileged caller overwrite/block another user's pending gateway callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`handler.HandleLegacyUserMessage` stores a caller's response callback in `h.savedCallbacks` keyed solely by `msg.Body.MessageID`, an attacker-chosen field, with no check for whether that key is already occupied by another in-flight request. Because the map is not scoped by sender identity, two different, independently-signed users who happen to pick (or collide on) the same `MessageID` can have one silently overwrite the other's pending callback slot, causing the original caller's response to be misdelivered or lost until timeout.

## Finding Description
`ProcessRequest` in `core/services/gateway/gateway.go` decodes the JSON-RPC request and only bounds `jsonRequest.ID`/`MessageID` length (`<=200` chars, and separately `MessageIDMaxLen = 128` in `api.Message.Validate`), never checking uniqueness across requests. [1](#0-0)  `Message.Validate()` verifies the signature length, `MessageID` length/format, and extracts the signer via `ExtractSigner()`, binding `Sender` to whoever signed the payload — but it never checks that `MessageID` is unique or that it hasn't been previously claimed by a different signer. [2](#0-1)  Critically, the signature covers `MessageID` as part of the signed payload (`GetRawMessageBody`), which proves a given sender authored a message with that ID, but does **not** prevent a *different* sender from independently signing and submitting their own message using the identical `MessageID` string, since nothing ties `MessageID` values to a specific sender namespace. [3](#0-2) 

In `HandleLegacyUserMessage`, after validation, the handler unconditionally overwrites the map entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
```
with no existence check on `msg.Body.MessageID`. [4](#0-3)  Later, when a DON node responds, `handleWebAPITriggerMessage` looks up and deletes by that same key and delivers the response to whichever callback is currently stored there. [5](#0-4)  If a second, unrelated user submits a validly-signed message with a colliding `MessageID` while the first is still pending (within `defaultCallbackMaxAgeSec = 120s`), the second overwrites the first's callback in the map, so the DON's eventual response is delivered to the second caller while the first caller's `callback.Wait(ctx)` in `gateway.go` times out. [6](#0-5)  None of the existing checks (signature length, payload decode, timestamp staleness, method allowlist) address this, since they validate the message's own well-formedness/freshness, not cross-request key collisions. [7](#0-6) 

## Impact Explanation
This is a genuine cross-user response corruption / availability bug: a legitimate WebAPI trigger caller's response can be silently redirected to a different, unrelated caller (or dropped, causing the legitimate caller to receive a generic gateway timeout instead of the real DON response). This maps to the in-scope "cross-user response corruption" impact category for the gateway request path. It does not enable direct fund movement or node compromise, but it does break the confidentiality/integrity of the request-response pairing that the gateway is supposed to guarantee per-caller.

## Likelihood Explanation
Any party capable of signing and submitting a `web_api_trigger` message to the gateway (any holder of an EOA key permitted to interact with the DON's WebAPI trigger, which by design does not require special operator/admin privilege) can trigger this. The main constraint is that the attacker must know or guess the victim's exact `MessageID` string within the ~120-second pending window; if client SDKs use unpredictable UUIDs this is hard, but nothing in the server enforces this — `MessageID` uniqueness is entirely a client-side convention, not a server-enforced invariant, and the vulnerability is fully realizable, e.g., by an attacker deliberately reusing an ID they observed (via shared infra, logs, or a predictable/sequential ID scheme used by some integrator) or even trivially by racing their own two requests with the same ID against a victim using the same convention.

## Recommendation
Reject a new `HandleLegacyUserMessage` request if `msg.Body.MessageID` already exists in `h.savedCallbacks` (return a conflict/duplicate error) rather than silently overwriting the entry. Consider additionally scoping the map key by `(Sender, MessageID)` rather than `MessageID` alone, since `Sender` is a cryptographically verified value derived from `ExtractSigner()`, so that collisions are only possible within a single sender's own request stream, not across senders. Apply the same fix to `dummyHandler.HandleLegacyUserMessage` in `core/services/gateway/handlers/handler.dummy.go`.

## Proof of Concept
1. User A signs and sends a legacy gateway request with `Body.MessageID = "X"`, `Method = "web_api_trigger"`; `ProcessRequest` → `HandleLegacyUserMessage` stores User A's callback under key `"X"` in `h.savedCallbacks` and forwards the request to all DON members. [8](#0-7) 
2. Before the DON responds, Attacker B (a different signer) sends another validly-signed legacy request also using `Body.MessageID = "X"`; this passes `Message.Validate()` since uniqueness is never checked. [2](#0-1) 
3. `HandleLegacyUserMessage` overwrites `h.savedCallbacks["X"]` with Attacker B's callback.
4. When the DON node responds with `MessageID = "X"`, `handleWebAPITriggerMessage` looks up `"X"`, finds only Attacker B's callback, and delivers the response there; User A's original request stalls until `callback.Wait(ctx)` in `gateway.go` times out and returns "handler timeout". [5](#0-4) 

A Go unit test on `handler.HandleLegacyUserMessage` sending two messages with distinct valid signatures/senders but identical `MessageID`, then simulating a DON response, would demonstrate that the first caller's callback is never invoked and the second caller's callback receives the response.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

// Message signatures are over the following data:
//  1. MessageID aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonID aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
