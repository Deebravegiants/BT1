## Analog Found

### Title
Missing bounds validation on `protocolFeeBps`/`surplusShareBps` in Tron `IntentGatewayV2.setParams`/`onAccept(UpdateParams)` permanently bricks order placement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` enforces that `Params.protocolFeeBps < 10_000` and `Params.surplusShareBps <= 10_000` (and per-destination fee overrides `< 10_000`) via `_validateParams`/`_updateParams` before ever writing them to storage. The Tron variant of the same contract implements its own `setParams` and `onAccept` handling for the identical `Params`/`ParamsUpdate` structs but performs **no validation at all**, letting `protocolFeeBps` (and `_destinationProtocolFees[...]`) be set to any value, including ≥ 10,000 (i.e., ≥ 100%). This mirrors the Celo `setReserveFraction` bug class exactly: a basis-points/fraction value that the arithmetic downstream implicitly assumes is `< 1.0` (`< 10_000` bps) is never checked.

### Finding Description
The reference validation lives in [1](#0-0)  where `_validateParams` requires `p.protocolFeeBps < 10_000`, `p.surplusShareBps <= 10_000`, and each `destinationFeeBps < 10_000` before `_updateParams` commits the change.

The Tron contract exposes the same configuration surface but skips these checks entirely:
- `setParams` writes `_params = p` unconditionally: [2](#0-1) 
- `onAccept`'s `UpdateParams` branch writes `_params = update.params` and `_destinationProtocolFees[stateMachineId] = feeBps` with no bound check on `feeBps` or on `update.params.protocolFeeBps`: [3](#0-2) 

The unchecked value then feeds directly into `placeOrder`'s fee-reduction arithmetic, which assumes `protocolFeeBps < 10_000`: [4](#0-3) 

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

If `protocolFeeBps >= 10_000`, `protocolFee > originalAmount`, and `originalAmount - protocolFee` underflows. Since the contract targets Solidity `^0.8.24` with default overflow/underflow checks, this reverts on every call.

### Impact Explanation
Once an out-of-range `protocolFeeBps` (or a destination-specific override) is written — whether by an operational mistake in a `ParamsUpdate` payload delivered through Hyperbridge, or by the one-shot `setParams` admin call before deployment is finalized — every subsequent `placeOrder` call on that Tron `IntentGatewayV2` deployment permanently reverts with an arithmetic underflow. This is a permanent denial of service on the intent gateway's order-placement path: no user (token bridger/intent placer) can create new orders through this contract until governance dispatches another `UpdateParams` correcting the value — and there is nothing in the contract enforcing that the corrective value is itself valid either, since the same unchecked path is used to "fix" it. This matches the "route unable to deliver messages" / permanent freezing-of-funds-flow category, since new intents cannot be placed and any liquidity that would have been escrowed for that route is blocked at the source.

### Likelihood Explanation
Any accepted `ParamsUpdate` originating from Hyperbridge (the only source `onAccept` permits) that carries `protocolFeeBps >= 10_000` or a destination override `>= 10_000` triggers this immediately and irreversibly for that field — there is no local safeguard to catch an out-of-range value before it lands in storage, unlike the parity EVM implementation which would reject it before writing. The severity is amplified because this is not a validation the caller can easily infer is missing: the struct and comment (`10000 = 100%, 100 = 1%, etc.`) look identical to the validated version, so operators or tooling reusing the same encoding helper across chains have no signal that the Tron deployment lacks the safety check the mainline EVM contract has.

### Recommendation
Port the exact checks from `IntentsBase._validateParams`/`_updateParams` [1](#0-0)  into the Tron contract's `setParams` and `onAccept`'s `UpdateParams` branch: require `p.protocolFeeBps < 10_000`, `p.surplusShareBps <= 10_000`, and each `destinationFees[i].destinationFeeBps < 10_000`, reverting with `InvalidInput()` otherwise, before committing any of these values to storage.

### Proof of Concept
1. Hyperbridge governance (or the one-shot admin via `setParams`) dispatches an `UpdateParams` request to the Tron `IntentGatewayV2` with `params.protocolFeeBps = 15_000` (150%).
2. `onAccept` decodes and unconditionally stores it: `_params = update.params;` (`evm/tron/contracts/apps/IntentGatewayV2.sol:648`).
3. Any user calls `placeOrder` with a nonzero-input order. `protocolFeeBps` (15,000) is read at `evm/tron/contracts/apps/IntentGatewayV2.sol:352-355`, and `protocolFee = originalAmount * 15_000 / 10_000 = 1.5 * originalAmount > originalAmount`.
4. `reducedAmount = originalAmount - protocolFee` underflows and reverts under Solidity 0.8's checked arithmetic, so `placeOrder` reverts for every caller until governance issues a corrective `UpdateParams` — itself unguarded against the same mistake.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
