### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the unauthenticated `X-Shopify-Shop-Domain` header, but the HMAC signature only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` trusts this header-derived `shop` when dispatching to the app's webhook handler, so a merchant who legitimately receives one signed webhook for their own store can replay that exact body/HMAC pair while substituting a different shop domain in the header, causing the app to process the payload as if it came from another tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signable string above and therefore is never bound to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the HMAC purely over `to_signable_string`, i.e. only the body, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC (body only), and then unconditionally trusts `request.shop` (the header) to construct `WebhookMetadata` that is handed to the app's registered handler: [4](#0-3) 

The identity binding that should hold is: `shop value delivered to the handler == shop value cryptographically bound by the HMAC`. Because the header is excluded from the signed bytes, this equality does not hold. Any party that has received one legitimate webhook delivery for their own shop (any merchant who installs the app gets these, e.g. `orders/create`, `app/uninstalled`, etc.) possesses a body+HMAC pair that stays valid no matter what `shop-domain` header accompanies it. They can post that exact body and `X-Shopify-Hmac-Sha256` value directly to the app's public webhook endpoint with the header changed to a victim's `*.myshopify.com` domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` forwards `shop: request.shop` (the forged victim domain) to the handler.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the app's webhook handler will execute business logic (e.g. data ingestion, mandatory GDPR handlers like `shop/redact`, `customers/redact`, `customers/data_request`, or any custom handler keyed by `shop`) attributing forged data to a shop the attacker does not control. This is a cross-tenant integrity/confidentiality issue — data or side effects intended to be scoped to one merchant can be attributed to another merchant purely by an unprivileged actor who has any single valid webhook payload from their own store.

### Likelihood Explanation
Any merchant who installs an app built on this gem automatically receives at least one genuinely signed webhook (e.g., `app/uninstalled`) for their own shop, giving them a valid `(raw_body, hmac)` pair with no need for the `api_secret_key`. Sending an HTTP POST directly to the app's public webhook endpoint with a forged `shop-domain` header is a standard, low-effort replay — no credential theft, TLS interception, or social engineering is required.

### Recommendation
Bind the shop identity into the HMAC-signed material (e.g. include shop domain in the signable content or require it to match a value cryptographically tied to the webhook, consistent with how OAuth's `AuthQuery#to_signable_string` includes `shop`) so that `Registry.process` cannot be fed a `shop` value independent of what was actually signed by Shopify.

### Proof of Concept
1. Malicious merchant `attacker-shop.myshopify.com` installs the target app and captures a legitimately delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Attacker sends a direct POST to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), and header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [5](#0-4) .
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"` [6](#0-5)  and passed to the app's handler, which processes the forged payload believing it originated from the victim shop.
