## Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while only the body is HMAC-verified - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`), the `topic`, `api_version`, and `webhook_id` from plain HTTP headers, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. This breaks the intended binding: *the shop whose secret produced a valid signature* should equal *the shop the handler is told the webhook belongs to*, but the gem never enforces that equality.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from attacker-controllable HTTP headers, with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e. only the body) and compares against `verifiable_query.hmac`: [3](#0-2) 

After that check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and hands it to the app's handler: [4](#0-3) 

Because every shop that installs a given app shares the same `Context.api_secret_key` (the HMAC secret is per-app, not per-shop), any merchant who has legitimately received one real webhook for their own store possesses a `(raw_body, hmac)` pair that is valid under the app's shared secret. Since the `shop` field is not part of the signed content, that same `(raw_body, hmac)` pair can be replayed against the app's public webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to name a **different** merchant. `HmacValidator.validate` will still return `true` (body+hmac unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop, even though that shop never sent or authorized this event.

This is the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is
`shop_that_produced_valid_hmac == shop_delivered_to_handler`
but the gem only enforces `hmac_of_body_is_valid`, leaving `shop` entirely attacker-controlled.

### Impact Explanation
Any application built on this gem's webhook handling receives `data.shop` as trusted merchant identity (this is explicitly documented as safe in `docs/usage/webhooks.md`, telling integrators `shop`, `String` - The shop domain of the webhook). An attacker who is a legitimate merchant of the app (or who otherwise observes one valid webhook delivery, e.g. via logs, a shared proxy, or their own store) can forge webhook deliveries attributed to an arbitrary other shop domain. Downstream apps that key data writes/reads off `data.shop` (as shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into applying another tenant's webhook payload to the attacker's own workflow, or cross-tenant confusion in the reverse direction, causing cross-tenant data access/corruption. This matches the Critical "cross-tenant access" category since the trust boundary between tenants is broken purely through this gem's own verification logic.

### Likelihood Explanation
Exploitation only requires capturing one legitimate webhook body+HMAC pair (trivial for any merchant of a multi-tenant app, since they receive real webhooks for their own store) and the ability to POST to the app's public webhook endpoint with custom headers — no access token, `client_secret`, or privileged account is needed. The webhook endpoint is by design internet-reachable.

### Recommendation
Bind the identity fields to the signed content, or otherwise cryptographically verify `shop` (and ideally `topic`/`webhook_id`) against Shopify's records before trusting them: e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require callers to confirm `request.shop` corresponds to a shop with an active session/registration for `request.webhook_id`/`topic` before dispatching to the handler. At minimum, document loudly that `data.shop` is unauthenticated and must not be used to key merchant-identifying operations without additional verification (e.g. cross-checking against a known session for that shop).

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both share the same `Context.api_secret_key`.
2. Attacker (owner of `shop-a`) triggers a real event and Shopify delivers a legitimate webhook:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: shop-a.myshopify.com
   body: {"id": 1, ...}
   ```
3. Attacker captures `body` and `x-shopify-hmac-sha256` unchanged, then replays:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same-valid-hmac-of-body>
   x-shopify-shop-domain: shop-b.myshopify.com
   body: {"id": 1, ...}      # identical bytes
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` line 27-31).
5. `ShopifyAPI::Webhooks::Registry.process` calls the app handler with `WebhookMetadata(shop: "shop-b.myshopify.com", body: {"id": 1, ...}, ...)` even though `shop-b` never sent this event.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
