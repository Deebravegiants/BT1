### Title
Stale, unrevalidated operator-QR authorization window enables signup with a revoked/deactivated operator - (File: src/plans/mod.rs)

### Summary
The external report describes a Chainlink TWAP oracle that caches a time-weighted price and is trusted for up to a lag window, creating an exploitable gap between the cached value and the true, current on-chain state. The orb-core signup flow has a structurally analogous pattern: after an operator QR-code is validated once against the backend, the resulting authorization (`OperatorData`) is cached locally with a timestamp and is reused, **without re-querying the backend**, for any subsequent signup as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` — a window configured to **23 hours** by default.

### Finding Description
`scan_initial_qr_codes` and `scan_remaining_qr_codes` decide whether to reuse a previously validated operator QR code purely based on a local `Instant` timestamp comparison against `operator_qr_expiration_time`, rather than re-checking operator validity with the backend on every signup: [1](#0-0) 

The same stale-timestamp-based trust decision is used again for the "both QR codes cached" and "operator-only cached" branches: [2](#0-1) 

The only place the operator status is actually verified against the backend is `verify_operator_qr_code`, which is called once (on the branch that misses the cache/expiry check) and stores the *result* (`valid: true` + location data) locally with `Instant::now()`, not a value tied to the backend's real-time state: [3](#0-2) 

The default expiration duration for trusting this cached authorization is set to 23 hours: [4](#0-3) 

This is the same class of defect as the reported TWAP issue: a security-relevant decision (operator authorization to conduct signups) is made against a **cached/lagged value** instead of the ground truth, and the code explicitly tolerates a long window (up to 23h) during which the cached authorization is trusted without re-validation — exactly analogous to trusting a TWAP price during a volatility window instead of the spot price.

### Impact Explanation
If an operator's credentials/authorization are revoked, suspended for fraud, or their permitted location/status changes on the backend after the initial QR validation, the orb will continue to treat that operator as valid and permit them to run signups for up to the full `operator_qr_expiration_time` window (23 hours by default) without any backend re-check. This creates a window in which an operator who should no longer be trusted (e.g., flagged for fraud, deactivated, or geofenced out) can still initiate and complete user signups, binding biometric enrollments to a session that a real-time check would have rejected. This is a cross-signup state bleed / misattributed-authorization risk: multiple downstream signups are effectively backed by a decision that is up to 23 hours stale.

### Likelihood Explanation
Likelihood is moderate: this requires (a) the self-serve/idle-scan code path to be active (`self_serve` config) or the multi-signup reuse path, and (b) the backend-side state of the operator to change within the trust window (revocation, fraud flag, location change) while the orb continues operating on cached authorization. Given that `operator_qr_expiration_time` is explicitly configured to a long value (23h) rather than short-lived, the exploitable window is realistically reachable during normal field operation, not just a contrived edge case.

### Recommendation
- Short term: shrink the reuse window materially and/or force a backend re-validation of operator status on every new signup (or at minimum periodically re-poll operator status) rather than relying solely on a locally cached timestamp expiry.
- Long term: treat the cached `OperatorData.timestamp` the same way a TWAP price staleness fix would: bind trust in the operator authorization to explicit backend confirmation of current status at time of each signup use, and fail closed (force re-scan/re-validation) rather than silently reusing possibly-stale authorization when the backend cannot be reached.

### Proof of Concept
1. Operator scans operator QR code; `verify_operator_qr_code` succeeds, and `OperatorData { timestamp: Instant::now(), .. }` is cached (`src/plans/mod.rs:1543-1568`, `776-781`).
2. Backend subsequently revokes/deactivates the operator (e.g., fraud flag) at T+1 minute.
3. Because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` (23h) still holds, `scan_remaining_qr_codes`/`scan_initial_qr_codes` reuse the cached, now-stale authorization and proceed directly to `scan_user_qr_code` without re-verifying operator status with the backend (`src/plans/mod.rs:756-820`).
4. The orb performs one or more additional signups under the revoked operator's stale authorization until the 23-hour window lapses.
