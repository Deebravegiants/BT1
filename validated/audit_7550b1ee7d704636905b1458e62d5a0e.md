### Title
Webhook HMAC covers only the raw body, not the `shop`, `topic`, `webhook-id` and `api-version` headers that the handler trusts — allows cross-tenant webhook forgery (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and are dispatched to the app's handler as trusted identity fields. This mirrors the report's bug class of "a field acted on but not covered by the HMAC" — here the field is the merchant identity (`shop`) itself, not just a numeric multiplier, so the consequence is cross-tenant rather than a rounding loss.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` gates dispatch solely on this body-only HMAC, then builds `WebhookMetadata` from the unauthenticated header values and hands it to the app's handler as the trusted event identity: [4](#0-3) 

The identity binding that should hold is:
`shop_the_body_was_signed_for == shop_claimed_in_the_x-shopify-shop-domain_header`

but the code only verifies:
`HMAC(raw_body, api_secret_key) == received_hmac`

with no cryptographic tie between the body and the header claims. Because the app's `api_secret_key` (`client_secret`) is shared across every shop that installs the app — not per-tenant — any shop that has legitimately installed the app can capture a genuine `(raw_body, hmac)` pair from its own webhook deliveries and replay that exact pair to the app's webhook endpoint while forging the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers to point at a different (victim) shop and a different topic. `HmacValidator.validate` still returns `true` since it only checks the body bytes, and `Registry.process` will invoke the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: <victim-shop>, ...)`.

### Impact Explanation
This breaks the tenant-isolation guarantee that a delivered webhook's claimed `shop` corresponds to the shop whose secret actually produced the signature-body pairing intended for that request. An app that uses `data.shop` from `WebhookMetadata` to look up/act on merchant records (a documented and expected usage pattern of this gem, e.g. mandatory `customers/data_request`, `customers/redact`, `shop/redact` topics) can be tricked into performing actions attributed to, or exposing data belonging to, a shop the attacker does not control — i.e., cross-tenant access, which the rules classify as Critical impact. It also lets an attacker relabel the `topic`, potentially routing a captured payload into a handler for a more sensitive topic than the one it was originally generated for.

### Likelihood Explanation
Exploitation only requires an unprivileged actor to install the target app on their own (attacker-controlled) shop — a normal, low-privilege action available to any internet user with a Shopify store — capture one legitimate webhook delivery, and replay it with modified headers to the app's public webhook endpoint. No access to the app's `client_secret`, TLS interception, or any victim credential is required, satisfying the "unprivileged internet user" and "no access token/secret needed" constraints.

### Recommendation
Bind the header-derived identity fields into the signed payload before verification, e.g. include `topic`, `shop`, and `webhook_id` in `to_signable_string` (matching what Shopify actually signs), or otherwise cryptographically verify that the claimed headers correspond to the shop/topic the signature was issued for, instead of trusting them purely as-is once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) to capture `raw_body` and its valid `x-shopify-hmac-sha256` value (computed with the app's shared `client_secret`).
2. Send a POST to the app's webhook endpoint with the same `raw_body` and `hmac` bytes, but headers overridden to:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: customers/data_request` (or any topic with a registered handler)
   - `x-shopify-webhook-id`, `x-shopify-api-version`: arbitrary values
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — see `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#L35-38`.
4. The handler executes with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, `topic: "customers/data_request"`, even though the body/HMAC pair was never generated for that shop or topic.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
