### Title
Unvalidated destination `beneficiary`/token address format in IntentGatewayV2 truncates malformed bytes32 to a wrong `address`, permanently misdelivering output funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`placeOrder` accepts `order.output.beneficiary` and all `TokenInfo.token` fields as raw, unvalidated `bytes32` values supplied directly by the caller. The contract never checks that the upper 96 bits are zero (i.e., that the value is a canonically left-padded 20-byte EVM address) before using it. When the escrow is later released, `_withdraw` blindly truncates it with `address(uint160(uint256(body.beneficiary)))`. This is the same bug class as the reported GravityFacet issue: a user/relayer-supplied destination-address field is never validated against the correct address format before funds are moved, so malformed input silently resolves to a different (and effectively unrecoverable) address instead of reverting.

### Finding Description
`PaymentInfo.beneficiary` and `TokenInfo.token` are typed `bytes32` on-chain, and the SDK documentation states plainly that callers are expected to left-pad plain 20-byte addresses into `bytes32` themselves if they bypass the SDK helper (`docs/content/developers/evm/intent-gateway/placing-orders.mdx:77-79`):
```
In the SDK, `TokenInfo.token` and `output.beneficiary` are standard 20-byte EVM addresses (`0x…`). The SDK left-pads them to `bytes32` when encoding the contract call — you do not need to pad them yourself.
```
Nothing in the on-chain contract enforces this convention. `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:194-415`) stores `order.output.beneficiary` verbatim into the commitment hash and event without any bounds/format check. When the order is later filled/refunded, `IntentsBase._withdraw` performs the unchecked truncation:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:452
address beneficiary = address(uint160(uint256(body.beneficiary)));
```
Solidity's `uint160(uint256(x))` truncation silently discards the high-order bytes instead of reverting when they are non-zero. Any `bytes32` value — e.g., a raw 32-byte Substrate/Cosmos account id, a hash, or a simple encoding mistake by an integrator that forgot to left-pad — is accepted as "valid" and converted into some 20-byte address that is unrelated to the value the user actually intended. The same unchecked pattern is repeated for `TokenInfo.token` throughout `placeOrder`/`fillOrder`/`_withdraw`/`_execute` (`evm/src/apps/intentsv2/IntentsBase.sol:457, 508, 643`), and for the `RefundEscrow`/`RedeemEscrow` decode paths that construct `WithdrawalRequest.beneficiary` from cross-chain message bodies.

This mirrors the reported GravityFacet defect exactly: a destination-address field of a foreign/looser format (there: bech32 string; here: `bytes32` account-id space that also covers non-EVM chains) is accepted without validating it matches the expected concrete format (there: bech32 checksum; here: zero-padded upper 96 bits), so malformed/mismatched input causes funds to be delivered to an address nobody controls, and the tokens become permanently unrecoverable there.

### Impact Explanation
This affects a core, unprivileged, directly reachable user flow: `placeOrder` is called by any ordinary user, and `fillOrder`/`_withdraw` release the solver's real output tokens to `address(uint160(uint256(beneficiary)))`. If a caller (self-integrated dApp, wallet, or user manually constructing the struct) supplies an unpadded or otherwise malformed `beneficiary`/token `bytes32` — for instance by reusing a 32-byte account identifier from a non-EVM chain, or an off-by-format encoding bug — the solver's legitimate output payment is sent to an unintended, effectively unrecoverable address on an EVM chain. Because `_withdraw` also finalizes the order (`_filled[commitment] = beneficiary` and it emits `EscrowReleased`), the order is marked filled and cannot be retried, and there is no on-chain re-validation or backend safety net analogous to the "LiFi validates on the backend" mitigation mentioned in the source report — Hyperbridge's IntentGatewayV2 has no external validation layer at all. This is a permanent loss-of-funds condition for the affected order's output leg, which the report classifies as Medium severity for the identical bug class.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a caller (typically an integrator's front-end or a scripted user) to construct the `Order`/`PaymentInfo` struct incorrectly, either through an encoding bug (forgetting to left-pad an address to 32 bytes) or by mistakenly reusing a 32-byte account identifier from a different state-machine convention. This is a plausible and realistic integration mistake, not requiring any malicious actor — it is a user-error class bug (same practical trigger as GravityFacet's destination-address issue), and given that `placeOrder`/`fillOrder` are exposed to arbitrary EOAs/contracts without any format assertion, nothing in the current code prevents or reverts it.

### Recommendation
Add explicit validation in `placeOrder` (and in the cross-chain `RedeemEscrow`/`RefundEscrow` decode paths) that any `bytes32` intended to represent an EVM address has its upper 96 bits equal to zero before it is accepted, e.g.:
```solidity
function _requireValidEvmAddress(bytes32 value) internal pure {
    if (uint256(value) >> 160 != 0) revert InvalidInput();
}
```
Call this on `order.output.beneficiary`, each `TokenInfo.token`, and `WithdrawalRequest.beneficiary` wherever they are decoded/truncated to `address`, so malformed encodings revert instead of silently truncating to an unintended address.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with `order.output = PaymentInfo({ beneficiary: <32-byte value with non-zero upper 96 bits, e.g. a raw Substrate AccountId32>, assets: [...], call: "" })` and valid `inputs`. The call succeeds, escrowing input tokens (`evm/src/apps/IntentGatewayV2.sol:194-415`).
2. A solver calls `fillOrder` with matching `options.outputs`; `_fillSameChain`/`_fillCrossChain` eventually calls `IntentsBase._withdraw(body, ...)` with `body.beneficiary` equal to the malformed value.
3. Inside `_withdraw`, `address beneficiary = address(uint160(uint256(body.beneficiary)));` truncates the value to a 20-byte address that has no relation to the intended recipient (`evm/src/apps/intentsv2/IntentsBase.sol:452`).
4. `IERC20(token).safeTransfer(beneficiary, amount);` sends the solver's real output tokens to this unintended address, `_filled[commitment]` is set, and `EscrowReleased` is emitted — the order is now finalized and the tokens are unrecoverable by the intended recipient.
