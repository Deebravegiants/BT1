### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the shop identity used to attribute and dispatch the webhook comes from an HTTP header that is never included in the signed payload. A holder of one validly-signed webhook (e.g., an attacker who installs the app on their own shop and receives legitimate webhooks) can replay that same body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop, and the signature check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-visible/attacker-replayable HTTP headers, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then dispatches the handler using the unverified `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`, which for webhooks is just the raw body — headers are never part of the signable string: [4](#0-3) 

This breaks the binding that `shop_authenticated == shop_attributed_to_webhook`. The library's own documentation asserts a stronger guarantee than what is implemented: it states that `Registry.process` "will verify the request did indeed come from Shopify," implying the full webhook (including its shop attribution) is authenticated, when in fact only the JSON body bytes are authenticated: [5](#0-4) 

### Impact Explanation
An attacker who installs the target app on a shop they control will legitimately receive Shopify webhooks addressed to their own shop, each with a valid `x-shopify-hmac-sha256` computed over the body using the app's real `api_secret_key`. Because the `shop-domain` header is outside the signed payload, the attacker can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint with the `shop-domain` header rewritten to any victim shop domain. `HmacValidator.validate` will still return `true` (the body bytes and HMAC are unchanged and valid), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled body content. Any app that trusts `data.shop` to select which merchant's records to update (a documented, expected usage per `docs/usage/webhooks.md`) will apply attacker-supplied webhook data under another tenant's identity — a cross-tenant data-integrity/confusion issue reachable without possession of any victim credentials.

### Likelihood Explanation
Any developer/merchant who can install the app on a shop they control obtains valid signed webhook traffic at will (no leaked secret or victim credentials needed), and the webhook endpoint is, by design, a public HTTP endpoint. Crafting the replay only requires copying an intercepted body and HMAC header and changing one other header, which is straightforward for any user who receives legitimate webhooks for their own shop.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., include the shop domain in the signable string, or require the caller to independently confirm that `request.shop` matches a shop domain for which the app currently holds a session/registration before dispatching). At minimum, update `docs/usage/webhooks.md` to accurately state that only the body is authenticated and that consumers must not treat `data.shop`/`data.topic`/`data.webhook_id` as cryptographically bound to the signature.

### Proof of Concept
1. Install the app for `attacker-shop.myshopify.com`; capture a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the real `api_secret_key`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Send a new HTTP request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [6](#0-5) 
, then dispatches `handler.handle` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body content [7](#0-6) 
.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
