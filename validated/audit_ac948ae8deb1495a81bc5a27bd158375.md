### Title
Passphrase-cache inactivity expiry can be retroactively extended by a later auto-lock TTL change - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache` caches the wallet passphrase and treats it as usable only while a stored `TTL` window since `inactiveAt`/`addedAt` has not elapsed. This mirrors the Nouns DAO bug class: a state that is treated as effectively final/expired (an inactive, soon-to-clear cached passphrase) is actually reversible because it depends on a mutable, globally-shared parameter (`autoLockTimerAtom`/TTL) that can be changed *after* the state was recorded, "reviving" a window that should have already expired.

### Finding Description
`scheduleClear()` marks the cache inactive by writing `INACTIVE_AT_KEY = Date.now()` and schedules a clear alarm using the *current* TTL from `#getTtl()` [1](#0-0) . Later, `get()` validates the cached passphrase's freshness using the TTL value *stored at that time* combined with `inactiveAt`: `inactiveAt + ttl > Date.now()` [2](#0-1) .

The TTL itself is not fixed once inactivity starts — `changeTtl(ttl)` can update `#autoLockTimerAtom` and overwrite `TTL_KEY` in storage at any time, including after `inactiveAt` has already been recorded, and it reschedules the clear alarm using the new value [3](#0-2) . Because `get()` reads whatever `TTL_KEY` currently holds (not the TTL that was in effect when the inactivity period began), increasing the auto-lock timer after the app went inactive extends the "still valid" window for a cache that, under the original TTL, would already have expired and been cleared. This is structurally identical to the Nouns issue: the "expiry" condition (`inactiveAt + ttl`, analogous to `eta + GRACE_PERIOD`) is computed against a mutable global config value rather than a value fixed at the moment the final/expired state was entered.

### Impact Explanation
If exploited, this allows a previously-inactive/soon-to-expire cached passphrase to remain valid for use in bypassing the passphrase prompt (auto-unlock) longer than the security model intends. Since the passphrase cache directly gates wallet unlock, an extension of its validity window increases the exposure surface for unauthorized access to the unlocked wallet/secrets by anyone with access to the device during the retroactively-extended window — a secret-disclosure / auth-bypass class impact on the wallet's lock mechanism.

### Likelihood Explanation
Low-to-moderate. It requires the auto-lock timer setting to be increased (`changeTtl` invoked with a larger TTL) while the app is already in its "inactive" phase (i.e., between backgrounding/locking and the scheduled clear alarm firing) — an ordering-dependent, non-malicious-actor-triggerable scenario similar in spirit to the "rare admin event" caveat that the original judges accepted at Medium severity for the Nouns finding.

### Recommendation
Do not use the live/mutable TTL when validating an already-started inactivity window. Freeze the TTL value at the moment `scheduleClear()` (or `set()`) records `inactiveAt`/`addedAt`, and use that frozen value exclusively in `get()`'s expiry check, independent of any subsequent `changeTtl()` calls. Alternatively, on any `changeTtl()` call, immediately re-evaluate `get()`'s expiry condition against `Date.now()` before applying the new TTL, clearing the cache first if it would already be expired under the old TTL.

### Proof of Concept
1. User backgrounds/locks the app; `scheduleClear()` runs, storing `INACTIVE_AT_KEY = t0` and scheduling a clear alarm for `t0 + ttl0` [4](#0-3) .
2. Before the alarm fires, `changeTtl(ttl1)` is invoked with `ttl1 > ttl0` (e.g., user or app logic raises the auto-lock duration), overwriting `TTL_KEY` and rescheduling the alarm using `ttl1` [3](#0-2) .
3. At time `t0 + ttl0 < now < t0 + ttl1`, a call to `get()` computes `inactiveAt + ttl > Date.now()` using the now-larger `ttl1`, returning the cached passphrase as still valid [5](#0-4)  — even though under the TTL in effect when inactivity began (`ttl0`), the cache should already have been cleared.

Note: I was not able to fully trace how `PassphraseCache.get()`'s result is consumed by the unlock flow in `features/application/src/modules/application.ts` within the available index, so the exact end-to-end exploitability (e.g., whether this bypasses a PIN/biometric re-entry prompt) could not be fully confirmed from the indexed code; a Devin session with full repo access would be needed to verify the consuming call sites.

  async changeTtl(ttl: number) {
    const newTtl = Math.min(this.#maxTtl, ttl)

    await this.#autoLockTimerAtom.set(newTtl)

    const passphrase = await this.#storage.get(PASSPHRASE_KEY)

    if (passphrase) {
      await this.#storage.set(TTL_KEY, newTtl)

      void this.#scheduleClear()
    }
  }
