Audit Report

## Title
Integer overflow in `Memory::resize` allows an unprivileged EVM caller to bypass the `EVM_MEMORY_BYTES` cap and panic the interpreter via out-of-bounds slice indexing - (File: substrate/frame/revive/src/vm/evm/memory.rs)

## Summary
`as_usize_or_halt_with` only validates that a `U256` offset fits into a native `usize`, without bounding it against `EVM_MEMORY_BYTES`; the cap check happens later in `Memory::resize`, which relies on `revm::interpreter::num_words(offset.saturating_add(len)) * 32`. Because `num_words` internally computes `(x + 31) / 32` using non-saturating arithmetic, an attacker-supplied `offset` near `usize::MAX` causes this addition to overflow, either panicking (debug/overflow-checks builds) or wrapping to a small value that bypasses the size cap, after which `slice_len`/`set` index the backing `Vec<u8>` out of bounds and panic.

## Finding Description
The claim's code path is confirmed exactly as described:
- `as_usize_or_halt_with` in `substrate/frame/revive/src/vm/evm/util.rs:21-28` checks only that the high limbs are zero and `limbs[0] <= usize::MAX`, with no comparison to `EVM_MEMORY_BYTES`. [1](#0-0) 
- `mload`, `mstore`, and `mstore8` in `substrate/frame/revive/src/vm/evm/instructions/memory.rs:31-62` call `as_usize_or_halt::<E::T>(offset)` then immediately `interpreter.memory.resize(offset, len)`. [2](#0-1) 
- `Memory::resize` in `substrate/frame/revive/src/vm/evm/memory.rs:66-79` computes `target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32` and compares it to `EVM_MEMORY_BYTES`; the `saturating_add` is safe, but `num_words` (external revm helper, `(x+31)/32`) is not saturating, so if `offset` is near `usize::MAX`, the internal `+31` inside `num_words` overflows. [3](#0-2) 
- After `resize`, `slice_len`/`set` in the same file index `self.data[offset..offset+size]` directly with no bounds checking beyond what the caller (i.e., `resize`) is supposed to guarantee. [4](#0-3) [5](#0-4) 

The described flaw is real: the cap check exists only in `resize`, and `as_usize_or_halt` does not perform a bound check that would prevent an oversized offset from reaching `resize` and `num_words`.

However, whether this manifests as a wraparound bypass or a panic depends on the overflow-checks build configuration and on `num_words`'s actual implementation (an external `revm` dependency not present in this repository's index, so its exact overflow behavior on `usize::MAX` could not be directly inspected here). In either case — panic-on-overflow, or wraparound leading to out-of-bounds slice indexing in `slice_len`/`set` — the end result is an unhandled Rust panic reachable from interpreter execution, since none of `slice`, `slice_mut`, `get_word`, `set`, `slice_len`, or `copy` perform their own bounds checks; they all explicitly document "Panics on out of bounds." [6](#0-5) 

## Impact Explanation
A successful trigger causes a Rust panic inside the interpreter during EVM bytecode execution for `pallet-revive`, rather than the intended graceful `Halt::Error(OutOfGas)` rejection. This is reachable by any unprivileged account submitting a normal EVM contract-call transaction with crafted bytecode (`PUSHn <large offset>` followed by `MLOAD`/`MSTORE`/`MSTORE8`), representing an availability/liveness defect for the specific extrinsic's execution path, consistent with the claim's stated impact.

## Likelihood Explanation
The trigger requires no special privileges — only the ability to submit an EVM contract call with attacker-chosen bytecode, which any unprivileged user can do. The offset value needed (`usize::MAX` or close to it) is trivial to construct and deterministic, making the issue, if present, fully and repeatably reachable.

## Recommendation
Bound `offset`/`len` against `EVM_MEMORY_BYTES` using checked/saturating arithmetic before calling `num_words`, e.g. reject any `offset.checked_add(len)` that exceeds `EVM_MEMORY_BYTES`, returning `Halt::Error(OutOfGas)` before invoking `num_words`, `slice_len`, or `set`, as proposed in the report.

## Proof of Concept
Add a unit test to `substrate/frame/revive/src/vm/evm/memory.rs` calling `Memory::<Test>::new().resize(usize::MAX - 31 /* or usize::MAX */, 32)` and asserting the result is `ControlFlow::Break(_)` without panicking, plus an interpreter-level test invoking `mload` with a stack value of `U256::from(usize::MAX)` and asserting a `Halt::Error(OutOfGas)` is returned rather than a panic, exactly as outlined in the submission.

```rust
pub fn as_usize_or_halt_with(value: U256, halt: impl Fn() -> Halt) -> ControlFlow<Halt, usize> {
	let limbs = value.0;
	if (limbs[0] > usize::MAX as u64) | (limbs[1] != 0) | (limbs[2] != 0) | (limbs[3] != 0) {
		ControlFlow::Break(halt())
	} else {
		ControlFlow::Continue(limbs[0] as usize)
	}
}
```

```rust
	interpreter.ext.charge_or_halt(EVMGas(VERYLOW))?;
	let ([], top) = interpreter.stack.popn_top()?;
```

```rust
	pub fn resize(&mut self, offset: usize, len: usize) -> ControlFlow<Halt> {
		let current_len = self.data.len();
		let target_len = revm::interpreter::num_words(offset.saturating_add(len)) * 32;
		if target_len > crate::limits::EVM_MEMORY_BYTES as usize {
			log::debug!(target: crate::LOG_TARGET, "check memory bounds failed: offset={offset} target_len={target_len} current_len={current_len}");
			return ControlFlow::Break(Error::<T>::OutOfGas.into());
		}

		if target_len > current_len {
			self.data.resize(target_len, 0);
		}

		ControlFlow::Continue(())
	}
```
