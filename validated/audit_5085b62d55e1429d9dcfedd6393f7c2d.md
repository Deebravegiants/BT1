### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only authenticates the raw HTTP body of an incoming webhook; the `shop-domain` and `topic` headers that determine *which tenant* and *which handler* the payload is dispatched to are never covered by the HMAC. An attacker who can obtain any single valid `(raw_body, hmac)` pair (trivially available to them as a legitimate merchant who installs the app and receives their own webhooks) can replay that exact body/signature to the app's public webhook endpoint while forging the `shop-domain` and/or `topic` headers, causing the host application to process the payload as if it came from a different shop or a different event type.

### Finding Description
The intended security property of `HmacValidator.validate` is that a webhook request is authentic **as a whole** — i.e. every field the handler relies on (`shop`, `topic`, `body`) should be bound by the signature: `hmac == HMAC(secret, body ∧ shop ∧ topic)`.

In reality, `Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `HmacValidator` computes/compares the signature exclusively against that string: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` verifies only the HMAC over the body, then dispatches to a handler chosen by the unauthenticated `topic`, and forwards the unauthenticated `shop` value straight to the handler: [4](#0-3) 

So the actual equality enforced is `hmac == HMAC(secret, body)`, while the value trusted and acted upon by the handler is `(shop, topic, body)` — a strict superset that is never checked. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the `shop` field used to select/attribute a tenant, and the `topic` field used to select the handler, are outside the cryptographically verified envelope.

**Attack sequence:**
1. Attacker installs the target app on their own store (a normal, unprivileged action) and lets Shopify deliver a legitimate webhook to the app's public endpoint. They capture the exact `raw_body` and the `X-Shopify-Hmac-Sha256` value that Shopify sent (they control their own server/network path for this, no `client_secret` needed).
2. Attacker POSTs the same `raw_body` with the same `hmac` header to the app's public webhook endpoint again, but this time sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `HmacValidator.validate` still returns `true`, because it only checks `raw_body` against the signature — headers are irrelevant to the check.
4. `Registry.process` looks up the handler for the attacker-chosen `topic` and invokes it with `shop: "victim-shop.myshopify.com"`.
5. Any host application logic keyed off `data.shop` (e.g., updating/deleting per-tenant records, gating billing/plan state, revoking access) now executes for the victim tenant using attacker-controlled/replayed content — a cross-tenant identity confusion enabled purely by this gem's incomplete signature coverage.

### Impact Explanation
This breaks the tenant isolation the SDK is supposed to guarantee for webhook handlers: an attacker can cause data belonging to one merchant/shop to be attributed to and acted upon for a different merchant, without ever needing `api_secret_key`, an access token, or any privileged credential. This matches the in-scope "Critical – cross-tenant access" impact category, since the host app has no way, using this gem's API, to distinguish a forged `shop`/`topic` pairing from a genuine one.

### Likelihood Explanation
Likelihood is High/Medium: the attacker only needs to be able to install the app on one shop they control (a normal, unauthenticated onboarding action) to obtain one valid `(body, hmac)` pair, and the webhook endpoint is by design a public, unauthenticated HTTP endpoint that accepts arbitrary headers. No secrets or elevated access are required to mount the replay with modified headers.

### Recommendation
Include the identifying headers in the signed/verified material, or otherwise cryptographically bind them:
- Extend `Request#to_signable_string` (or add a dedicated check in `HmacValidator`/`Registry.process`) to incorporate `shop-domain` and `topic` into the value that is HMAC-verified, or
- Require the host application to pass a pre-registered/expected `shop` (e.g., resolved from a stored per-shop webhook secret or session lookup) and reject the request if it doesn't match the header, rather than trusting `request.shop`/`request.topic` implicitly once only the body's HMAC checks out.

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop and captures a legitimately delivered webhook:
captured_raw_body = '{"id":123}'
captured_hmac = "shopify-real-hmac-b64=="   # Signed with the *shared* app client_secret

# 2. Attacker replays the exact same body/hmac pair to the app's public endpoint,
#    but forges the shop and topic headers (never covered by the signature):
forged_headers = {
  "x-shopify-topic"        => "shop/redact",       # attacker-chosen handler
  "x-shopify-hmac-sha256"  => captured_hmac,        # unchanged, still valid for the body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: forged_headers)

# 3. HMAC validation only checks `raw_body`, so it passes:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the "shop/redact" handler with shop == "victim-shop.myshopify.com",
#    even though that shop never sent this request:
ShopifyAPI::Webhooks::Registry.process(request)
```
Because `HmacValidator` and `Request#to_signable_string` never incorporate `shop` or `topic` ( [1](#0-0) , [5](#0-4) ), step 3 succeeds and step 4 executes handler logic attributed to a shop and/or event type the attacker fully controls.
