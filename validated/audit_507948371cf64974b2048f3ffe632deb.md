Based on the retrieved code, the closest analog to the "anyone can create/add state without authorization" pattern from the external report is in `orb-relay-client`'s message handling, where a `RequestState` message from an app bypasses the standard source-identity check that all other inbound relay messages are subject to.

### Title
`RequestState` message handler bypasses source-identity check, allowing replay of last relayed message to unauthenticated senders - (File: `orb-relay-client/src/client.rs`)

### Summary
The `orb-relay-client`'s `PollerAgent::main_loop` validates the `src.id` of every incoming `RelayPayload` against the expected `dst_id` before buffering it for the consumer — except when the payload is a `self_serve::app::v1::RequestState` message. For that message type, the client unconditionally replies with `self.last_message` (the last message it sent over the channel), skipping the `src.id != self.config.dst_id` authorization check entirely. This mirrors the reported bug class where a state-mutating/state-disclosing operation is reachable without the access-control check that gates all other equivalent code paths.

### Finding Description
In `orb-relay-client/src/client.rs`, the connection's message loop enforces a source check for regular payloads: [1](#0-0) 

Specifically, the branch is:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;
}
```
The `RequestState` branch is evaluated *before* the `src.id != self.config.dst_id` check, so any message classified as `RequestState` triggers a resend of `last_message` regardless of who actually sent it. The code's own comment acknowledges the underlying trust-boundary weakness that enables this: [2](#0-1) 
which states: "We need to split auth and subscription... That will avoid multiplexing messages from different sources," i.e., the client is aware it may receive messages multiplexed from sources other than the intended `dst_id`, yet it does not verify identity before honoring `RequestState`.

This is used both on the orb side and app side (`Mode::Orb`/`Mode::App`) since `PollerAgent` is shared code, meaning any entity able to route a `RequestState` payload to the orb's relay session can force the orb to resend its last outgoing message (e.g. `AnnounceOrbId`, `SignupEnded`, or other self-serve state messages) without being validated as the legitimate counterpart identified by `dst_id`.

### Impact Explanation
Because the source-identity check is skipped specifically for `RequestState`, this creates a path where session state (the last signup/relay message, which can include orb id, signup outcome, or failure feedback) can be replayed to a party that has not been validated as the correct `dst_id`/session peer, at least at this client-library layer. This is analogous to the reported "bypassing access control" defect: a privileged/state-disclosing action reachable without the same authorization gate that protects the equivalent code path for all other message types.

### Likelihood Explanation
Exploitability depends on whether an attacker can get a `RequestState` payload delivered to the orb's client stream with a `src` that isn't the legitimate session peer — this requires either backend-side message multiplexing across sessions (which the code comment implies is a known limitation) or a compromised/malicious relay backend. Under the "no-impact / malicious-peer" exclusion rules, if this requires a malicious relay server or a broken backend routing, likelihood is low; if the backend can route cross-session `RequestState` messages to orbs (which the TODO comment suggests is a real possibility not yet mitigated), likelihood is moderate.

### Recommendation
Enforce the `src.id != self.config.dst_id` check uniformly for all payload types, including `RequestState`, before taking any action (including resending `last_message`). If `RequestState` needs different handling, validate the source's authenticated identity through the same mechanism used for regular payloads rather than special-casing it ahead of the check.

### Proof of Concept
1. Establish a relay connection as an "app" client authenticated for a different session/orb than the target.
2. If the backend or transport allows the message to reach the target orb's `PollerAgent` stream (e.g., due to the multiplexing issue noted in the code's own TODO), send a `self_serve::app::v1::RequestState` payload with `src.id` not equal to the orb's configured `dst_id`.
3. Observe that the `else if src.id != self.config.dst_id` branch is never reached for this payload type — `main_loop` immediately calls `sender_tx.send(self.last_message.clone())`, returning the orb's last relayed message to the requester without validating that the requester is the authorized counterpart.
