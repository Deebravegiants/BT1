### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the shop identity attached to the resulting event is taken from an HTTP header that is never included in that HMAC computation. An attacker who can obtain one genuine, HMAC-signed webhook body (e.g., for their own shop) can replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop, and the signature will still validate, causing the app to process attacker-controlled data under another tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read from HTTP headers that are completely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (i.e., only the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses this same HMAC check as the sole authentication gate, then dispatches the handler using `request.shop` — a value that was never bound to the HMAC: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used by handler`. In reality, the equality is `shop authenticated by HMAC == {}` (nothing, since the body is the only signed content and the merchant's shop domain is not embedded in the JSON payload by Shopify for most topics), while `shop used by handler == header value, unauthenticated`. Consequently, any entity capable of obtaining one valid `(raw_body, hmac)` pair for shop A — trivially available to any merchant who installs the app on their own store, since the app relays every webhook it receives to that merchant's own endpoint testing/logging, or via replay of a captured request — can resubmit the exact same body/HMAC pair while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with shop B's domain. `Utils::HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` will invoke the registered handler with `WebhookMetadata.new(topic: ..., shop: "shop-B.myshopify.com", body: <attacker-chosen-but-signed-for-shop-A body>, ...)`.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce: the app’s webhook handler trusts `request.shop` to route data/side-effects to a specific merchant record (e.g., updating that shop’s session/data store, triggering shop-scoped background jobs), but that value is attacker-controllable independent of the cryptographic check. This is a cross-tenant access vector — data validated as authentic (via HMAC) for one shop can be misattributed to and acted upon for a different shop that never sent it, purely by manipulating an unauthenticated header alongside a replayed, still-valid signature.

### Likelihood Explanation
Requires only ability to send arbitrary HTTP requests to the app's public webhook endpoint plus one legitimately captured `(body, hmac)` pair (e.g., from a shop the attacker controls/installs the app on, or from a webhook whose body is largely attacker-influenced, such as `app/uninstalled` or a custom metafield/order webhook with attacker-supplied content). No access token, `api_secret_key`, or privileged account is needed — matching the "unprivileged internet user" threat model.

### Recommendation
Bind the shop (and topic) into the signed material, or independently authenticate them against the value validated out-of-band. Concretely:
- After HMAC validation, cross-check `request.shop` against the shop associated with the currently active/expected session for that webhook subscription (e.g., verify the shop is a known, previously-installed shop, and correlate via the `webhook_id` fetched over an authenticated GraphQL call), rather than trusting the header directly for dispatch.
- Alternatively, avoid trusting `x-shopify-shop-domain` for any identity-sensitive decision unless the app additionally validates it came from Shopify (e.g., via mTLS/IP allowlisting recommended by Shopify, in addition to HMAC), since the HMAC in this gem provides no such guarantee.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a real webhook delivery (raw body `B` and its valid `x-shopify-hmac-sha256` value `H`, computed by Shopify with the app's real `api_secret_key`).
2. Replay to the app's webhook endpoint:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com

B
```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <parsed B>, ...)` [6](#0-5) , causing the app to act on `B`'s content as if it were legitimately sent by `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
