## Title
Storage-deposit cache key collision in `DirectBridge` lets one withdrawal's cached "storage already exists" result be replayed for a different token/account pair, causing withdrawals to skip a required storage deposit - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naive string concatenation of `contractId` and `accountId` with no delimiter. Because NEAR account IDs are dot-delimited strings that can be arbitrarily re-segmented, two semantically different `(contractId, accountId)` pairs can produce an identical cache key. This is the same root-cause class as the GitLab report: an unqualified/ambiguous cache key lets one tenant's cached entry be served for a different tenant's lookup.

### Finding Description
`estimateWithdrawalFee` calls: [1](#0-0) 

which delegates to: [2](#0-1) 

The key is built as `` `${contractId}${accountId}` `` with no separator. Since NEAR account IDs are composed of dot-separated labels, the split point between `contractId` and `accountId` is not fixed in the resulting string. For example:
- Call 1: `contractId = "ab.near"`, `accountId = "cd.near"` → key `"ab.nearcd.near"`
- Call 2: `contractId = "ab.nearc"`, `accountId = "d.near"` → key `"ab.nearcd.near"` (identical)

Both are syntactically valid NEAR account IDs, so this collision is trivially reachable with real inputs, not a contrived edge case.

The cache is only populated when the queried account already has *sufficient* storage (`result[1] >= result[0]`, see line 295), i.e., precisely the "no fee needed" case: [3](#0-2) 

`estimateWithdrawalFee` then decides whether to charge a storage-deposit fee purely from this cached tuple: [4](#0-3) 

If a first (possibly attacker-controlled) withdrawal populates the cache under a key that later collides with a second, unrelated user's `(contractId, accountId)` pair, the second lookup gets a cache hit and inherits the first pair's "storage already sufficient" result — even though the real destination account has never registered storage on the real token contract. `estimateWithdrawalFee` will then return `storageDepositFee: 0n`, and `createWithdrawalIntents` builds the withdrawal intent without attaching the storage deposit: [5](#0-4) 

### Impact Explanation
On NEAR, `ft_transfer`/`ft_withdraw` to an account without registered storage panics and reverts. If the SDK is run as a shared service instance handling many users' withdrawals (the intended integration pattern per the README), the `storageDepositCache` is shared across all callers on that `DirectBridge` instance. A cache-key collision therefore lets one withdrawal's "storage OK" result leak into a completely different user's withdrawal for a different token/destination, causing that withdrawal's on-chain transaction to fail for lack of the (skipped) storage deposit. This matches the High-severity category "a withdrawal stuck until manual intervention" — the user's funds remain locked in the intents contract until they retry with correct storage handling.

### Likelihood Explanation
Exploitability only requires submitting two withdrawal/fee-estimation requests with attacker-chosen `assetId`/`destinationAddress` values whose concatenation collides — no privileged access, and colliding values are ordinary, valid NEAR account IDs (just shifting where the "dot boundary" falls). Any caller of the shared SDK instance can attempt to prime the cache with such a pair.

### Recommendation
Use a collision-free cache key, e.g. include an explicit delimiter and length-prefix or a proper tuple-based key: `` `${contractId.length}:${contractId}:${accountId}` `` or use a `Map`/`LRUCache` keyed by a composite object/array instead of string concatenation.

### Proof of Concept
1. Attacker calls `estimateWithdrawalFee` (or triggers a code path that calls `getCachedStorageDepositValue`) with `assetId = "nep141:ab.near"`, `destinationAddress = "cd.near"`, where `cd.near` already has sufficient storage on `ab.near`. This populates `storageDepositCache` with key `"ab.nearcd.near"` → `[min, userBal]` where `userBal >= min`.
2. A different, legitimate withdrawal for `assetId = "nep141:ab.nearc"`, `destinationAddress = "d.near"` (an account that has *not* registered storage on `ab.nearc`) computes the same key `"ab.nearcd.near"` and hits the poisoned cache entry.
3. `estimateWithdrawalFee` incorrectly returns `storageDepositFee: 0n`; `createWithdrawalIntents` omits the storage deposit.
4. The resulting `ft_withdraw`/`ft_transfer` on-chain call panics because `d.near` is not registered on `ab.nearc`, and the victim's withdrawal fails/gets stuck, requiring manual retry.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
