### Title
Blocklisted fee payer permanently blocks timeout processing and freezes refunded funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchTimeOut` (both the `PostRequestTimeout` and `GetRequestTimeout` overloads) refunds the relayer fee directly to `meta.sender` — the arbitrary address that originally paid for the dispatched request — via an unguarded `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` call. `feeToken()` is a stablecoin (e.g. USDC/DAI) that can implement an address blocklist. If `meta.sender` is ever blocklisted by the fee token, this transfer reverts and unwinds the entire transaction, including the module callback that had already refunded the underlying bridged asset, permanently preventing that request from ever timing out.

### Finding Description
`dispatchTimeOut` deletes the request commitment, invokes the destination module's `onPostRequestTimeout`/`onGetTimeout` callback, and only afterwards pays out the relayer fee refund to `meta.sender`: [1](#0-0) 

The equivalent GET-timeout path behaves the same way: [2](#0-1) 

Critically, the module callback (`success`) is guarded — a failing callback simply restores `_requestCommitments[commitment]` for retry — but the subsequent `safeTransfer` to `meta.sender` has no such guard. If it reverts, the whole external call reverts, unwinding:
- the earlier `delete _requestCommitments[commitment]`,
- the module's already-executed refund logic (e.g. `HyperFungibleToken.onPostRequestTimeout` re-minting burned tokens to the sender, or `WrappedHyperFungibleToken.onPostRequestTimeout` unlocking escrowed ERC20/WETH): [3](#0-2) [4](#0-3) 

`meta.sender` is fixed at dispatch time as `post.payer`, which for `HyperFungibleToken.send`/`WrappedHyperFungibleToken.send` is simply `msg.sender` — an arbitrary, attacker- or user-controlled address: [5](#0-4) 

`HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` call `dispatchTimeOut` in a loop over a batch of timeouts within a single transaction: [6](#0-5) [7](#0-6) 

Because there is no try/catch around the fee-token transfer, a single blocklisted `meta.sender` in the batch makes the whole batch revert (a relayer can work around this by isolating the offending item into its own transaction, but that specific request can never successfully time out, since every submission that includes it will revert on the same `safeTransfer`).

### Impact Explanation
Once a user's address is added to the fee token's blocklist (which is entirely outside the protocol's control — banks/issuers of centralized stablecoins like USDC do this for sanctions/compliance reasons), any pending or future cross-chain dispatch they paid for can never be timed out. Since the underlying asset refund (burned HFT supply re-mint, or WrappedHFT's locked ERC20/WETH release) happens in the same atomic transaction as the fee refund, the user's bridged principal is permanently frozen — it can neither be delivered (if destination proof never arrives) nor refunded via timeout. This is a direct, stronger analog of the reported bug: instead of blocking repayment to a single lender, an unprivileged party (or external blocklist operator) can permanently freeze bridged funds for any payer address that becomes blocklisted, with no recovery path in the contract.

### Likelihood Explanation
This does not require any privileged role — any user of `HyperFungibleToken.send`/`WrappedHyperFungibleToken.send` (or any `HyperApp` that sets an untrusted `payer`) can become the affected `meta.sender`. Given that Hyperbridge documentation explicitly recommends `feeToken` be a stablecoin like `DAI`/`USDC`, and centralized stablecoins routinely implement blocklists, this is a realistic and externally triggerable condition, not a contrived one.

### Recommendation
Wrap the relayer-fee refund transfer in `dispatchTimeOut` (both overloads) in a try/catch (or use a low-level `call` with a success check) similar to how the module callback failure is handled, and if the transfer fails, credit the amount to an internal withdrawable balance for `meta.sender` instead of pushing the transfer inline. This decouples the timeout settlement (and the module's asset refund) from the fee token's transfer semantics, ensuring a blocklisted payer cannot block the destruction of the underlying escrowed/burned asset refund.

### Proof of Concept
1. User calls `WrappedHyperFungibleToken.send(...)` with `msg.value = 0`, causing `IDispatcher(_host).dispatch` to be invoked with `payer = user` and locking their ERC20 into the contract; `EvmHost.dispatch` stores `FeeMetadata{sender: user, fee: relayerFee}` keyed by the request commitment (`evm/src/core/EvmHost.sol:921-948`).
2. Before the request is delivered or times out, the fee token issuer (e.g. Circle for USDC) adds `user` to its blocklist.
3. The request times out on the destination chain (or was never relayed). A relayer submits `HandlerV2.handlePostRequestTimeouts` with a valid non-membership proof.
4. `EvmHost.dispatchTimeOut` deletes the commitment, successfully calls `WrappedHyperFungibleToken.onPostRequestTimeout`, which unlocks/transfers the underlying ERC20 back to `user` — then attempts `IERC20(feeToken()).safeTransfer(user, meta.fee)`, which reverts because `user` is blocklisted (`evm/src/core/EvmHost.sol:885-906`).
5. The entire `handlePostRequestTimeouts` transaction reverts, rolling back the commitment deletion and the token unlock performed inside `onPostRequestTimeout`. Every future attempt to process this specific timeout (alone or batched) reverts identically, permanently freezing `user`'s bridged funds in the `WrappedHyperFungibleToken` contract.

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
