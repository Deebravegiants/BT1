### Title
Unsynchronized concurrent `unlock()` calls can leave `primarySeedIdAtom` pointing at the wrong seed - ([File: sdks/headless/src/features/wallet-rpc/index.js])

### Summary
`createSeedIngestingProxy`'s `unlock` wrapper reads `target.unlock(...)`'s result and calls `primarySeedIdAtom.set(primarySeedId)` without any locking or sequencing, and the underlying `Wallet#unlock` in `features/wallet/module/wallet.js` is likewise not wrapped in `makeConcurrent` (unlike `create`/`import`). Two overlapping `unlock()` calls with different passphrases can therefore resolve out of invocation order, and whichever resolves last wins the atom write, regardless of which call was actually issued last by the caller.

### Finding Description
The proxy's `unlock` interceptor is:
```js
// sdks/headless/src/features/wallet-rpc/index.js:9-14
return async (...args) => {
  const { primarySeedId } = await target[prop](...args)
  await primarySeedIdAtom.set(primarySeedId)
  return primarySeedId
}
``` [1](#0-0) 

`target.unlock` is `Wallet#unlock`:
```js
// features/wallet/module/wallet.js:282-298
unlock = async ({ passphrase } = {}) => {
  try {
    const { seed } = await this.#getSeed({ passphrase })
    const primarySeedId = await this.#keychain.addSeed(seed)
    this.#primarySeedIdAtom.set(primarySeedId)
    ...
    return { primarySeedId }
  } ...
}
``` [2](#0-1) 

Unlike `create`/`import`, which are explicitly serialized with `makeConcurrent(..., { concurrency: 1 })` [3](#0-2) , `unlock` has no such guard. Each call independently awaits `#getSeed` (storage decryption, whose latency depends on passphrase/KDF cost and I/O) before calling `addSeed` and setting the atom. Two concurrent `unlock({passphrase:A})` / `unlock({passphrase:B})` invocations race: `#getSeed`/`addSeed` completion order is not guaranteed to match call order, so the *last* `this.#primarySeedIdAtom.set(...)` write inside `Wallet#unlock` — and independently the proxy's second `primarySeedIdAtom.set(primarySeedId)` after `await target.unlock(...)` — can be for the seed from the call that was issued first, overwriting the value from a later call whose `#getSeed` resolved earlier. `Keychain#addSeed` also does not remove or lock out the other seed [4](#0-3) , so both seeds remain loaded/unlocked in the keychain, but `primarySeedIdAtom` — which downstream modules such as `addressProviderApi`'s `withWalletAccountInstance` and analytics/connected-origin atoms key off of [5](#0-4) [6](#0-5)  — can end up referencing a stale/unintended seedId that doesn't correspond to the last-resolved `unlock()` call.

No mutex, debounce, or request-sequencing exists anywhere in this path (`createSeedIngestingProxy`, `Wallet#unlock`) to prevent this interleaving.

### Impact Explanation
If `primarySeedIdAtom` ends up holding a seedId different from what the caller's most recent successfully-resolved `unlock()` call returned, any downstream logic keyed off `primarySeedIdAtom` (address derivation, signing context selection, analytics user id, connected-origin/account scoping) can operate against the wrong seed relative to the session's intent. This is a wrong-account/state-confusion condition consistent with the "wallet-account isolation" invariant described in the question, though note both unlocked seeds' key material is present in the keychain simultaneously regardless (this is not a new secret-disclosure vector, but an atom/state desynchronization one).

### Likelihood Explanation
Requires an attacker/dapp capable of firing two overlapping `unlock()` RPC calls before the first resolves — feasible for any origin/dapp that can call `wallet.unlock` twice in quick succession, since there is no debounce, mutex, or request queue on this path. The race window depends on `#getSeed`'s (password-based decryption) latency; it's real but timing-dependent, so the outcome (which call "wins") is nondeterministic rather than deterministically exploitable to target a specific undoing.

### Recommendation
Wrap `Wallet#unlock` with `makeConcurrent(..., { concurrency: 1 })`, matching `create`/`import`, so overlapping `unlock()` invocations serialize and only the last-issued call's result is applied. Additionally, make the `createSeedIngestingProxy` `unlock` wrapper itself serialize concurrent calls (e.g., queue/mutex keyed on the proxy instance) so `primarySeedIdAtom.set` calls cannot be reordered relative to caller invocation order, and consider having `primarySeedIdAtom.set` reflect only the outcome of the most recently *invoked* call (e.g., using a monotonically increasing call token to discard stale results).

### Proof of Concept
Integration test plan:
1. Set up a wallet with two importable seeds/passphrases (A, B) sharing the same wallet instance, wired through `createSeedIngestingProxy`.
2. Mock/stub `#getSeed` (or the underlying storage decrypt) so that the `unlock({passphrase:A})` call's internal decryption resolves *after* the `unlock({passphrase:B})` call's decryption, despite A being invoked first — e.g., inject an artificial delay for passphrase A only.
3. Fire `const pA = proxy.unlock({ passphrase: A })` then immediately `const pB = proxy.unlock({ passphrase: B })`.
4. `await Promise.all([pA, pB])`.
5. Assert `await primarySeedIdAtom.get()` equals `seedId(B)` (the last-issued call), and fails today because it can resolve to `seedId(A)` due to the reordering, demonstrating the atom does not reliably reflect the last-invoked `unlock()` target.
