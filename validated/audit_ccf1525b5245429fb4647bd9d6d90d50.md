This confirms a clear inconsistency: `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before building the session used to send `client_secret`, but `TokenExchange.exchange_token` ( [1](#0-0) ) uses the JWT's `dest` claim directly, unsanitized, as the host that receives the `client_secret`.

### Title
Unvalidated `dest` claim host used as token-exchange endpoint enables `client_secret` exfiltration to attacker-controlled host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop it will send the app's `client_secret` to directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling flows `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both sanitize the `shop` before use.

### Finding Description
`JwtPayload` only verifies the JWT signature (against `Context.api_secret_key`/`old_api_secret_key`) and that `aud == Context.api_key` ( [2](#0-1) ). It performs no validation that the `dest`/`iss` claim is actually a trusted Shopify domain (`*.myshopify.com`, `*.myshopify.io`, `*.spin.dev`, etc.) — that check exists elsewhere as `Utils::ShopValidator` ( [3](#0-2) ) but is never invoked from `JwtPayload` or `TokenExchange`.

`TokenExchange.exchange_token` then takes `jwt_payload.shop` (the raw, unsanitized `dest` value with `https://` stripped) and uses it directly as the session's `shop`, which `Clients::HttpClient` turns straight into the request host: `@base_uri = "https://#{api_host || session.shop}"` ( [4](#0-3) ). The POST body sent to that host includes `client_id` and `client_secret` ( [5](#0-4) ).

This breaks the intended binding: **host validated == host that receives the app's `client_secret`**. Every other credential-sending code path in this gem enforces `validated_shop == request_host` by calling `ShopValidator.sanitize!` first:
- `ClientCredentials.client_credentials`: [6](#0-5) 
- `RefreshToken.refresh_access_token`: [7](#0-6) 

`TokenExchange.exchange_token` is the only credential-sending path that skips this check: [8](#0-7) .

Note `TokenExchange.migrate_to_expiring_token` (a sibling method in the same file) *does* call `Utils::ShopValidator.sanitize!(shop)` ( [9](#0-8) ), further highlighting that `exchange_token` is the outlier that forgot the equivalent check on the value it takes from the JWT.

### Impact Explanation
If `Context.old_api_secret_key` is configured (a supported, common rotation practice per `Context.setup` [10](#0-9) ) or under any future/alternate flow where an attacker can obtain or influence a validly-signed session token whose `dest` claim is not constrained to a `*.myshopify.com`-style host, this code will POST the app's `client_id`/`client_secret` to that attacker-controlled host — a Critical exfiltration of the app's `client_secret`. Even absent forgery of the signature, the missing defense-in-depth check is a direct deviation from the equivalent, deliberately-added checks in `ClientCredentials` and `RefreshToken`, which exist specifically to prevent `client_secret` from being sent to any host not confirmed to be a genuine Shopify domain.

### Likelihood Explanation
Exploitation requires the ability to present a session token whose signature validates (via `api_secret_key` or `old_api_secret_key`) but whose `dest` is attacker-influenced. This is most realistic during a secret-rotation window (`old_api_secret_key` in use) or any host-application integration that constructs/relays session tokens without strictly constraining `dest` — the gem itself provides no defense here, in contrast to its own established pattern in `ClientCredentials`/`RefreshToken`.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` the same way the other flows do:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
before constructing `shop_session` and before it is used to build the request host that receives `client_id`/`client_secret`.

### Proof of Concept
1. Configure `Context.setup` with `old_api_secret_key` set (a supported rotation configuration).
2. Craft (or obtain, during the rotation window) a JWT signed with the old secret containing `aud: <api_key>` and `dest: "https://attacker.example"`.
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: jwt, requested_token_type: ...)`.
4. `JwtPayload.new` accepts the token (signature verifies with `old_api_secret_key`, `aud` matches) — [11](#0-10)  — with no check that `dest` is a Shopify-owned domain.
5. `dest_shop` = `"attacker.example"` is used unsanitized to build `shop_session`, and `Clients::HttpClient` sends the POST containing `client_id`/`client_secret` to `https://attacker.example/admin/oauth/access_token` ( [12](#0-11) , [13](#0-12) ).

          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop

                "The shop is now always taken from the session token's `dest` claim.",

          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
