Cross-Tenant Webhook Spoofing via Unauthenticated `Shop-Domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then dispatches the parsed payload to the app's registered handler tagged with a `shop` value that is read verbatim from the `X-Shopify-Shop-Domain` HTTP header — a field that is never included in the HMAC-signed content. This breaks the identity binding: `HMAC-verified content == body only`, while `identity used downstream == shop-domain header (unverified)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`to_signable_string` returns only `@raw_body` — no headers are part of the signable content: [2](#0-1) 

The `shop` accessor reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is attacker-controlled input on the wire (i.e., whatever the sending party sets in the HTTP headers), and is not covered by the signature: [3](#0-2) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which only checks `request.hmac` against `compute_signature(request.to_signable_string, secret)` (i.e., the raw body) — and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

Because the same `client_secret` is shared by all shops that installed a given app, a valid `hmac-sha256` header exists for any body Shopify has legitimately sent to *any* of the app's shops — including the attacker's own shop, if the attacker has installed the app. An attacker who operates one legitimate installation of the app (unprivileged relative to other tenants, but privileged only over their own shop) can capture a real, validly-signed webhook delivery for their own shop, then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. Because that header isn't part of the HMAC-covered content, `HmacValidator.validate` still returns `true`, and `Registry.process` calls `handler.handle` with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain while the (attacker-controlled) body is processed as if it belongs to the victim tenant.

This exactly matches the report's root-cause pattern: a downstream identity/ownership check operates on data that no longer corresponds to what was verified — here, the `shop` field acted upon by the handler is not covered by the HMAC that gated the request's acceptance.

### Impact Explanation
This is a cross-tenant data-integrity/access issue: an attacker with access to one legitimate app installation can forge webhook events attributed to any other merchant shop the app serves, since the shop identity is never authenticated by the HMAC. Depending on how the host application's `WebhookHandler#handle` implementation uses `WebhookMetadata#shop` (e.g., to look up per-tenant sessions/access tokens, to fulfill orders, redact data, or update per-shop records), this can lead to cross-tenant state corruption or being tricked into acting on another merchant's behalf — matching the "cross-tenant access" Critical-impact category in scope.

### Likelihood Explanation
Requires only: (1) the attacker to be an app user/merchant capable of installing the app on at least one shop they control (an "unprivileged internet user" relative to other tenants), and (2) the ability to send an HTTP POST to the app's public webhook receiving endpoint with a captured/replayed body and a modified `Shop-Domain` header — no access token, `client_secret`, or privileged credential is needed. The gem provides no protection against header spoofing since only the body is HMAC-covered by design.

### Recommendation
Bind the shop identity to the HMAC-verified content, e.g., include the `shop-domain` header (and ideally `topic`, `webhook-id`, `api-version`) in `to_signable_string`, or otherwise cross-verify the `shop-domain` header against a value embedded in the signed body/session/webhook subscription registered for that topic, before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App installs on attacker's own shop `attacker.myshopify.com`; attacker triggers an event (e.g., `orders/create`) causing Shopify to send a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the shared `client_secret`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures this raw request (body + `hmac-sha256` header).
3. Attacker replays the exact same body and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, because it only checks the raw body's HMAC: [6](#0-5) 
5. `Registry.process` then constructs `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed `victim.myshopify.com` value and dispatches it to the app's handler as if it were a legitimate webhook for the victim shop: [7](#0-6)
