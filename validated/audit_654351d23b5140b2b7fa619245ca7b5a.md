This confirms the vulnerability. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers via `shopify_header` [2](#0-1) . `Registry.process` validates only the HMAC of the body, then dispatches the handler using `request.topic` and passes `request.shop` straight into `WebhookMetadata` without any binding to the signed content [3](#0-2) .

### Title
Webhook shop/topic/webhook_id identity fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only. The tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are trusted from the HTTP request without being included in the signed payload, breaking the binding `authenticated_bytes == acted_upon_identity`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) . `Utils::HmacValidator.validate` computes the HMAC over `to_signable_string` and compares it against the `hmac-sha256` header [4](#0-3) . This proves that only the body bytes are authenticated by `Context.api_secret_key`.

However, `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all parsed from headers, not from the signed body — to route the call and to construct `WebhookMetadata` handed to the app's handler [3](#0-2) .

Because the header fields sit entirely outside the HMAC's protected scope, any request whose raw body matches a previously-observed, validly-signed payload will pass HMAC validation regardless of what `shop-domain` or `topic` header values accompany it. An attacker who operates their own Shopify shop (an "unprivileged internet user" with respect to any *other* merchant) receives genuine, correctly-signed webhook deliveries for their own shop. Since many webhook topics carry fixed or attacker-influenceable bodies (e.g., `app/uninstalled`, `shop/redact` with `{}`, or a webhook whose body the attacker fully controls by triggering the event on their own store with chosen content), the attacker can replay that exact raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) to name a victim shop. The signature computed by `HmacValidator.validate_signature` over the identical raw body will still equal the replayed `hmac-sha256` header, so `raise ... unless Utils::HmacValidator.validate(request)` at `Registry.process` passes [5](#0-4) , and the handler executes believing the event originated from the victim shop.

This is the exact analog to the report's insurance-rate binding gap: the value that matters for security decisions (which tenant/shop the event is "for") is not covered by the same authenticator that is checked before acting.

### Impact Explanation
This crosses a tenant boundary: it lets an unprivileged caller cause the app's webhook handler to execute business logic attributing an event to a shop the attacker does not control (e.g. faking `app/uninstalled`, `shop/redact`, `customers/data_request` for a victim tenant, corrupting per-tenant state, triggering data deletion routines, or forging install/uninstall bookkeeping used for billing/session cleanup). This matches the "cross-tenant access" Critical impact category, since the identity binding between the authenticated payload and the acted-upon shop is broken.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuinely-signed webhook (trivial: run your own Shopify dev/trial store and trigger the topic, or use a webhook whose body is fixed/empty across all shops) and to replay it with a forged header at the app's public webhook endpoint. No access to `api_secret_key`, tokens, or credentials of the victim shop is needed — only network access to the app's webhook listener, satisfying the "unprivileged internet user" threat model.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`) in the HMAC-signed material used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them to the payload before `Registry.process` trusts `request.shop`/`request.topic` for routing and handler dispatch. At minimum, document and enforce that the host application must independently verify `request.shop` is a shop for which it has an active installation before acting on the payload, since the gem currently gives no cryptographic guarantee that the header-derived shop matches the signed body's origin.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic whose body is invariant or attacker-controlled (e.g. `shop/redact`, which Shopify sends with a JSON body like `{"shop_id":..., "shop_domain":"attacker-shop.myshopify.com"}` — for topics with fully attacker-influenced content this is direct; for fixed-body topics like some compliance webhooks, the body is identical across all shops).
2. Attacker captures the raw HTTP POST, including the valid `X-Shopify-Hmac-Sha256` header computed by Shopify over that raw body with the app's real `api_secret_key` (unknown to the attacker, but the signature itself is now known and valid for that body).
3. Attacker resends the identical raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because it only checks `raw_body` against the (valid, replayed) signature — the substituted `shop-domain` header is never part of the signed string [7](#0-6) [1](#0-0) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` naming the victim shop, even though the event never occurred for that shop [8](#0-7) .
