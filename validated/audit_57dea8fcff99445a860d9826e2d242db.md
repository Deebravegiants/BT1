### Title
Webhook shop identity spoofing due to `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) that gets attached to processed webhook data from the unsigned `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. This breaks the intended binding `hmac-verified body == originating shop`, letting anyone who can produce (or replay) an HMAC-valid webhook body relabel it as coming from an arbitrary shop.

### Finding Description
`Registry.process` verifies webhook authenticity solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator computes the HMAC only over `request.to_signable_string`, which is defined as: [2](#0-1) 

i.e., only the raw JSON body is covered by the signature. Meanwhile the `shop` value that gets forwarded to the application's handler (used by the host app to attribute the webhook to a tenant) is read straight from a header that is *not* part of the signed content: [3](#0-2) 

and is passed through unchanged into `WebhookMetadata`: [4](#0-3) 

The equality the gem should be enforcing but does not is:
`hmac_verified(raw_body) with secret S` ⇒ `shop == the shop for which Shopify computed that HMAC`

Because `shop` is excluded from the signable string, this equality never actually holds — the gem accepts *any* `shop` header value as long as the body/HMAC pair is valid for *some* installation using the same app secret (all shops of a given app share the same `client_secret` used for webhook signing). An attacker who legitimately installs the app on their own (unprivileged, free) development store can capture a genuine `raw_body` + `X-Shopify-Hmac-Sha256` pair generated by real Shopify traffic to their own shop, then resend that exact body/HMAC pair to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is authentic), and `Registry.process` dispatches the payload to the handler tagged as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem exposes an API contract (`WebhookMetadata#shop`) that host applications are expected to trust as the authenticated source of the webhook, but the value is not bound to the cryptographic proof of authenticity. A host application that keys tenant records, deduplication, inventory sync, or order processing off `WebhookMetadata.shop` can be made to write/attribute attacker-supplied (though HMAC-"valid") data into another merchant's tenant space — a cross-tenant access/data-poisoning primitive satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled store (achievable by any unprivileged internet user for public apps), (2) capturing one legitimate webhook delivery to that store, and (3) resending it with a modified shop header. No access to `api_secret_key`, tokens, or the merchant's credentials is needed.

### Recommendation
Include the shop domain (and topic) in the HMAC-covered signable content, or independently verify the `X-Shopify-Shop-Domain` header against a known/registered shop for the session/installation before trusting it in `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must be independently validated by the host application against its own installation records before being used for tenant routing.

### Proof of Concept
1. Install the target app (any public embedded app) on attacker-controlled dev store `attacker.myshopify.com`.
2. Trigger any webhook topic subscribed by the app (e.g., `products/update`) so Shopify sends a genuine POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `client_secret`).
3. Capture `B` and `H`.
4. Replay a POST to the app's webhook endpoint with the same body `B`, same `H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `B` against `H`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches the handler with `WebhookMetadata.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
