### Title
Webhook shop-domain (tenant identity) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers when invoking the app's handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string against `Context.api_secret_key` [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers without being part of the signed payload [3](#0-2) . `Registry.process` validates the HMAC and, if it passes, immediately forwards `request.shop` and `request.topic` (both header-derived, unauthenticated) into the app's handler as the trusted tenant/topic context: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [4](#0-3) .

The identity binding that should hold is: `shop header used by handler == shop cryptographically bound by the HMAC`. In this implementation that equality does not hold — only the body is signed, so the `shop-domain` header can be swapped freely without invalidating the signature, provided the attacker can produce a body+HMAC pair that validates (e.g., by installing the app on their own store and capturing a legitimate webhook delivery signed with the app's shared `api_secret_key`).

The library's own documentation asserts this call "will verify the request did indeed come from Shopify" and describes `data.shop` as the trusted "shop domain of the webhook" to be relied upon by handlers (see `docs/usage/webhooks.md`, "Process a Webhook" section and the `data` key list), reinforcing that this is the guaranteed authentication contract of `Registry.process`, not a caveat left for the host app to independently address.

### Impact Explanation
Because the app's `api_secret_key` is shared across all shops that install the app (it is not shop-specific), any merchant who installs the app can receive a real webhook for their own store, capture its body and valid HMAC, then POST that identical body/HMAC pair directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will validate the HMAC (it only checks the body) and route the forged event to the handler as though it originated from the victim shop, causing cross-tenant data confusion — e.g., the handler enqueuing work, updating internal state, or triggering merchant-scoped side effects (as shown in the documented handler example calling `perform_later(topic:, shop_domain: data.shop, webhook: data.body)`) under the wrong tenant identity. This is a cross-tenant identity binding break.

### Likelihood Explanation
Any user able to install the app on a shop (a normal, unprivileged install, requiring no special access) can obtain a body+HMAC pair signed with the shared app secret, and the webhook endpoint is a public HTTP route by design, so no credentials, secrets, or elevated access are needed to attempt the header substitution.

### Recommendation
Bind the tenant/topic/webhook-id headers into the signed payload verification (e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string, or independently verify `request.shop` against the set of shops that are known to have valid sessions/installations before dispatching to the handler) so that the shop identity delivered to handlers is cryptographically bound to the same value validated by the HMAC.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker-shop.myshopify.com`); this is a normal, permitted app installation.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a legitimate webhook to the app's public endpoint, signed with `HMAC-SHA256(raw_body, api_secret_key)` and headers including `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` value from that delivery.
4. Replay an HTTP POST directly to the app's public webhook endpoint using the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC [2](#0-1)  — validation passes since the body/HMAC pair is genuinely valid.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [5](#0-4) , processing the attacker's forged payload as though it belongs to the victim shop.
