### Title
Attacker-controlled swap route can inject unauthorized wallet-token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept caller-supplied route bytes and forward them opaquely to the configured router. [1](#0-0)  A crafted route can place attacker-controlled code below the caller-authorized controller invocation and request an unrelated token transfer from the caller; if the victim signs the simulated authorization tree, that transfer executes alongside a valid swap. [2](#0-1) 

### Finding Description
`swap_collateral` authenticates `caller` and verifies account ownership before withdrawing and routing collateral. [3](#0-2)  The shared swap helper then invokes `execute_strategy` with the raw `swap` bytes after authorizing only the controller’s exact input transfer. [1](#0-0)  The controller validates measured input/output balances, but those checks do not constrain other contract calls made by route-selected venue code or additional authorization children requested beneath the caller’s root authorization. [4](#0-3) 

The repository’s malicious-hop proof shows a route-selected pool calling `token.transfer(victim, attacker, amount)` during an otherwise successful `swap_collateral`. [5](#0-4)  Simulation records that unrelated transfer as a child of the victim’s `swap_collateral` authorization rather than as a separate top-level operation. [6](#0-5)  Enforcing mode rejects the same route under an honest root-only tree, but authorizes it when the victim signs the poisoned child, leaving the attacker with the victim’s entire wallet-token balance. [7](#0-6) 

### Impact Explanation
A victim can lose arbitrary balances of unrelated wallet tokens up to the amount included in the poisoned authorization child, independently of the collateral being routed. [8](#0-7)  This is theft of user funds: the protocol checks still receive a fair swap output and preserve account solvency, so they do not detect or bound the additional wallet transfer. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker can deploy the hostile hop contract, encode a valid-looking profitable route through it, and induce a victim to sign the composed lending transaction. [10](#0-9)  The attack depends on the wallet or client signing the unexpected child authorization generated by simulation, but that child is structurally attached under the controller call and can be missed by clients that only display the root invocation. [6](#0-5) 

### Recommendation
Do not allow arbitrary route-selected contracts to execute under lending authorization without constraining their observable authorization effects. Enforce a governance-approved venue/pool registry or an equivalent route-integrity mechanism, and require clients to reject any simulated authorization tree containing children beyond the expected controller-authorized input flow; expected honest trees should contain no unrelated token transfer children. [1](#0-0) 

### Proof of Concept
1. Deploy a contract whose route-invoked function calls `token::Client::transfer(victim, attacker, amount)` for an unrelated token held by the victim. [11](#0-10) 
2. Craft `swap` bytes for the victim’s `swap_collateral(caller, account_id, current, amount, new, swap)` that route through that contract while still returning at least the required output. [12](#0-11) 
3. Ask the victim to sign the composed transaction; simulation nests the unrelated token transfer under the victim’s `swap_collateral` authorization. [13](#0-12) 
4. Submit the signed tree; the swap succeeds and the victim’s unrelated wallet token moves to the attacker. [14](#0-13)
