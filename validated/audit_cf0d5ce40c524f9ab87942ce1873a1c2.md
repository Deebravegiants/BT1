### Title
Webhook shop/topic/api-version/webhook-id identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields — which are read from HTTP headers and handed to the app's webhook handler as trusted, shop-scoped identity data — are excluded from that signature. This breaks the intended binding `hmac == HMAC(body ‖ shop ‖ topic ‖ ...)`; in reality `hmac == HMAC(body)` only.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to build the signed payload: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all sourced from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) and are never included in `to_signable_string`: [3](#0-2) 

These header-derived values are passed straight into `WebhookMetadata`, which the host application's `WebhookHandler#handle` treats as the authoritative shop/tenant identity for the event: [4](#0-3) [5](#0-4) 

This is precisely the class of bug described in the reference report: an ordering/consistency assumption (there, that `EnumerableSet` iteration order stays constant across a mutating operation; here, that the signed bytes cover every field the application relies on) is violated because the mechanism that is supposed to bind related state (`EnumerableSet.remove`'s effect on ordering / the HMAC's coverage of the request) does not actually guarantee it. Here the broken identity binding is: `hmac` is verified against `body` alone, but the app trusts `shop` (and `topic`/`webhook_id`/`api_version`) as if they were also covered by that same signature.

Because `Context.api_secret_key` is a single per-app secret shared across every merchant that installs the app (it is not shop-specific), any merchant who legitimately receives webhooks from Shopify for their own shop obtains a valid `(body, hmac)` pair signed with that shared secret. An unprivileged internet user controlling one legitimate, installed shop can capture one of their own genuine webhook deliveries and replay it directly to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates (it only checks `body`), so `Registry.process` accepts the request and dispatches attacker-controlled `body` content to the app's handler labeled as coming from the victim shop.

### Impact Explanation
This is a Critical cross-tenant issue: it lets a user who controls their own installed shop inject forged webhook events attributed to another tenant (victim shop) into the host application, because the shop identity is not cryptographically bound to the verified payload. Any application logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop billing/subscription state, GDPR redaction records, order records, or webhook-driven data records) can be corrupted or manipulated for a shop the attacker does not control.

### Likelihood Explanation
Likelihood is high for any app exposing a public webhook receiver endpoint (a documented, standard usage pattern of this gem): the attacker only needs one legitimate app installation (any Shopify Partner/developer/merchant account) to obtain a validly signed `(body, hmac)` pair under the shared `api_secret_key`, then can freely swap the `shop-domain` (and other) headers and resend to the app's public endpoint. No access to the app's `client_secret` in the OAuth sense is needed beyond what any installed merchant already causes Shopify to sign on their behalf.

### Recommendation
Include all fields the application will trust — at minimum `shop`, `topic`, `webhook_id`, and `api_version` — in the HMAC-signed payload (`to_signable_string`), or otherwise cryptographically bind them to the body (e.g., canonicalize headers + body before signing, matching what is actually verified). Alternatively, document and enforce that `WebhookMetadata#shop`/`topic` must never be used as a tenant/authorization boundary unless additionally corroborated (e.g., cross-checked against the shop associated with the currently active session/installation).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends this exact HTTP request to the app's public webhook endpoint, but replaces the `x-shopify-shop-domain` header with `victim.myshopify.com` (leaving `B` and `H` untouched).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equals `H` — validation succeeds. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, and the host application processes attacker-chosen data as if it originated from the victim shop. [7](#0-6)
