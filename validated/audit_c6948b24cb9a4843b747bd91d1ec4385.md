### Title
Webhook shop-domain identity spoofing due to HMAC signature not covering the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the shop's identity directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` (via `Registry.process`) only covers the raw request body, not this header. This lets a malicious app-installer replay their own valid, HMAC-signed webhook body while substituting an arbitrary `shop-domain` header, so the app dispatches attacker-controlled data to its handler under the identity of a different, victim shop — a broken identity binding between "shop verified by HMAC" and "shop used by the handler."

### Finding Description
Webhook authenticity is established solely via HMAC: [1](#0-0) 

`process` raises unless `Utils::HmacValidator.validate(request)` succeeds, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler.

The HMAC check itself only signs the raw body: [2](#0-1) 

`to_signable_string` returns `@raw_body` exclusively — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed data.

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it against the received `hmac`: [3](#0-2) 

Since `shop` is parsed from an unauthenticated header while the cryptographic proof-of-origin only binds the body, the equality the gem implicitly promises — "the shop that produced a valid signature == the shop attributed to this webhook" — does not hold. Any party who legitimately receives a real, validly-signed webhook for their own shop (e.g., an app installer) can capture that HTTP request (valid HMAC, unchanged body) and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a different shop's domain. `Registry.process` still finds the HMAC valid (body unchanged) and constructs `WebhookMetadata` with the attacker-chosen `shop`: [4](#0-3) 

The gem's own documentation instructs developers to treat `data.shop` as the trustworthy shop identity for the webhook, e.g. using it directly to key storage/attribution: [5](#0-4) 

So this isn't a case of the host app "ignoring documented behavior" — the gem documents `data.shop` as the verified shop identifier coming out of a call whose entire purpose is "verify the request did indeed come from Shopify" (per the same doc, line 125), yet the shop field it returns is never actually authenticated.

### Impact Explanation
This breaks tenant isolation: a low-privileged, unprivileged app installer (any merchant who installs the app) can cause the app to process attacker-supplied webhook payloads as though they originated from an arbitrary other shop, without needing the app's `client_secret` or any victim credentials. Depending on how the host app uses `data.shop` (as is documented/expected — e.g. keying job attribution, cache updates, order/product sync, deletion flows keyed by shop), this enables cross-tenant data confusion/injection: attacker-controlled webhook bodies get attributed to and processed under a victim shop's identity. This matches the "Critical – cross-tenant access" impact category, since the shop-identity boundary this gem is supposed to enforce via HMAC verification is not actually enforced for the `shop` field it hands to the app.

### Likelihood Explanation
Any merchant who installs the app (a fully unprivileged, standard interaction) can obtain a genuine, validly-HMAC-signed webhook for their own shop simply by triggering a normal store event (e.g. `orders/create`). Replaying that captured request with a modified `shop-domain` header requires no cryptographic secret and no elevated access — only the ability to send an arbitrary HTTP request to the app's public webhook endpoint. This is a low-effort, reliably reproducible attack path.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the data that is cryptographically verified, or otherwise cross-check the header-derived `shop` against a value that is authenticated — e.g., include the shop domain in the HMAC-signed payload used by `to_signable_string`, or validate `request.shop` against the shop associated with the specific webhook subscription (looked up server-side, not trusted from the header) before constructing `WebhookMetadata`. At minimum, document explicitly that `data.shop` is not part of the HMAC-verified payload and must be independently corroborated before being used for tenant attribution.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., updates a product), causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
2. Attacker captures this exact raw body and HMAC value (both remain valid/unchanged).
3. Attacker resends the identical body and HMAC to the app's webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the forged header (`lib/shopify_api/webhooks/request.rb:20-23`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it matches — validation passes (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to process attacker-controlled content under the victim shop's identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
