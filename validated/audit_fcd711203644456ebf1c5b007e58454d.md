### Title
CORS Origin Wildcard Bypass via Suffix-Matching Instead of Subdomain-Boundary Check - (File: core/services/gateway/network/httpserver.go)

### Summary
The gateway's user-facing HTTP server validates cross-origin requests by checking whether the `Origin` header's hostname ends with an allow-listed wildcard suffix, using `strings.HasSuffix`, without verifying a `.` boundary between the matched suffix and the rest of the hostname. This mirrors the FacturaScripts root cause: an authorization decision is made from a naive string comparison against the raw/normalized input rather than a structurally-sound comparison, allowing an attacker-controlled value that merely shares a trailing character sequence to be treated as trusted.

### Finding Description
`isAllowedOrigin` splits both the incoming request's `Origin` header and each configured allowed origin into scheme/host/port, then applies a wildcard check for host entries prefixed with `*.`: [1](#0-0) 

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

If an operator configures `CORSAllowedOrigins = ["*.remix.ethereum.org"]`, the intent is to allow only subdomains like `app.remix.ethereum.org`. After stripping the `*.` prefix, `allowedHost` becomes `remix.ethereum.org`. The subsequent check is a raw suffix match with no requirement that the character preceding the match be a `.` (or that the match start at a label boundary). Consequently, an origin such as `evilremix.ethereum.org` or `notremix.ethereum.org` also satisfies `strings.HasSuffix(originHost, "remix.ethereum.org")` and is treated as an authorized origin, even though it is not a subdomain of `remix.ethereum.org` at all — it is a completely different, attacker-registrable domain.

This is invoked directly from the unauthenticated request path: [2](#0-1) 

```go
func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}
		...
```

`handleRequest` is the handler wired into the gateway's public-facing user server, which processes unauthenticated JSON-RPC requests (e.g., vault operations, workflow requests) reaching the gateway from external browser clients: [3](#0-2) 

The `CORSAllowedOrigins` field is a config-level allowlist meant to scope which third-party web origins (e.g. `remix.ethereum.org`, used by dApp integrations) may make cross-origin browser requests to the gateway and read its JSON-RPC responses via `Access-Control-Allow-Origin` reflection.

### Impact Explanation
Just as the FacturaScripts advisory demonstrates that a prefix-based authorization check can be satisfied by an unintended path, here a suffix-based authorization check can be satisfied by an unintended, attacker-owned domain. Any attacker who registers a domain ending in the allowed suffix (e.g. `evilremix.ethereum.org`, `attacker-remix.ethereum.org`) can host a malicious webpage that:
- Has its `Origin` header accepted by the gateway's CORS check.
- Receives `Access-Control-Allow-Origin: <attacker origin>` reflected back.
- Can then have a victim's browser issue cross-origin JSON-RPC requests to the gateway's user endpoint and read the responses via the browser's fetch/XHR CORS-enabled flow.

Since the gateway user endpoint handles JSON-RPC requests for handlers such as the vault gateway path (`core/capabilities/vault/gw_handler.go`, `core/services/gateway/handlers/vault/handler.go`), a successful CORS bypass expands the set of origins that can interact with these handlers from a victim's authenticated browser session context, enabling cross-origin request/response confusion consistent with the "cross-user response confusion" / allowlist-bypass class called out in the validation criteria. The severity depends on what credentials or session context the browser attaches, but the flaw itself is a concrete authorization/allowlist bypass reachable from an unprivileged, unauthenticated web origin.

### Likelihood Explanation
Exploitation only requires: (1) the operator has configured a wildcard entry in `CORSAllowedOrigins`, and (2) the attacker registers or controls a domain sharing the suffix. Domain registration abuse (buying `evil<suffix>` or similar) is a low-cost, well-known technique, making this readily exploitable wherever wildcard CORS entries are used. No authentication or privileged access is needed — the check is evaluated purely from the `Origin` header on every request to the public gateway endpoint.

### Recommendation
Replace the raw suffix check with a proper subdomain-boundary comparison, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".remix.ethereum.org" (keep the dot)
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures the match only succeeds when `originHost` is exactly the base domain or ends with `.` + the base domain, preventing sibling/attacker domains that merely share a trailing substring from being treated as authorized.

### Proof of Concept
1. Configure the gateway user server with `CORSAllowedOrigins = ["*.remix.ethereum.org"]`.
2. Send a preflight/actual request with header `Origin: https://evilremix.ethereum.org` (or `https://notremix.ethereum.org`) to the gateway's user path.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilremix.ethereum.org", "remix.ethereum.org")` is `true`, and the server responds with `Access-Control-Allow-Origin: https://evilremix.ethereum.org`, granting the attacker origin the same cross-origin read access intended only for genuine subdomains of `remix.ethereum.org`.

*Note: I was unable to fully trace every downstream consumer of the gateway's user-facing responses (e.g., whether any deployment sets `Access-Control-Allow-Credentials`) within the indexed code; this affects exact exploit impact but not the root-cause validity of the allowlist bypass itself.*
