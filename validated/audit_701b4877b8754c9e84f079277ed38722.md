### Title
Webhook `shop` (tenant) identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (and `topic`) fields — which the host application uses to attribute the webhook to a specific merchant/tenant — come from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`, defined in `Request#to_signable_string` as simply `@raw_body`: [1](#0-0) [1](#0-0) 

Meanwhile, `request.shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` then forwards this unauthenticated `shop` value straight to the host app's handler as the tenant identifier: [3](#0-2) 

The equality the code implicitly (and incorrectly) assumes is:
`shop_covered_by_hmac == shop_delivered_to_handler`

In reality: `hmac == HMAC(raw_body)` only, while `shop_delivered_to_handler` is an independent, unauthenticated header value. Nothing prevents `shop_delivered_to_handler` from being any arbitrary string chosen by whoever sends the POST request, as long as they can produce *some* `(raw_body, hmac)` pair that passes `OpenSSL.secure_compare` for that raw_body — which they can obtain by simply observing genuine webhooks Shopify sends to their own (attacker-owned/unprivileged) store.

### Impact Explanation
An unprivileged attacker who operates their own Shopify store (a normal, unprivileged action) receives legitimate webhooks from Shopify with a valid `hmac` for the raw body content. Because the `shop` header is excluded from the signed content, the attacker can replay that exact `(body, hmac)` pair directly to the target app's webhook endpoint while substituting an arbitrary `shop-domain` header value naming a different, victim merchant. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches to the host handler with `WebhookMetadata#shop` set to the spoofed victim shop. Any host application that trusts `data.shop` to select which merchant's session/access token/database row to act on (the documented and expected usage pattern per `docs/usage/webhooks.md`) will process attacker-controlled data under the wrong tenant's identity — a cross-tenant confusion/spoofing primitive.

### Likelihood Explanation
Requires only: (1) the attacker to run or have run any legitimate Shopify store capable of receiving webhooks (trivial, free to obtain), and (2) direct network access to POST to the app's public webhook endpoint with custom headers (webhook endpoints are typically public HTTP(S) endpoints by design). No access token, `client_secret`, or privileged account is needed — the attacker never needs to compute a valid HMAC themselves, only replay one they legitimately received.

### Recommendation
Include the `shop` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signed content, e.g. by having `to_signable_string` incorporate the shop-domain header alongside the raw body, and reject the request if a mismatch is detected. Alternatively, verify `request.shop` against session/shop records established independently of the webhook headers before dispatching to the handler.

### Proof of Concept
1. Attacker creates a Shopify development store `attacker.myshopify.com` and installs the target app, receiving genuine webhooks such as `orders/create` with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker captures the raw JSON `body` and the corresponding valid `hmac` value.
3. Attacker sends a new POST request directly to the app's webhook endpoint with the identical `body`/`hmac`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(body)`: [4](#0-3) 
5. The host app's `WebhookHandler#handle` is invoked with `data.shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own store — a cross-tenant identity spoof.
