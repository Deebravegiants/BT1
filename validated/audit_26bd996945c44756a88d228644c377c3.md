### Title
Missing decimals re-validation in `pallet-psm::redeem` allows stale internal/external decimal snapshots to miscalculate swap amounts - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm` stores two decimal values that must stay in sync with the live metadata of the underlying assets: `PsmInfo::internal_decimals` (a snapshot taken at `create_psm`) and `ExternalAssetInfo::decimals` (a snapshot taken at `add_external_asset`). `mint()` explicitly re-validates these snapshots against live asset metadata via `Self::ensure_decimals_match(...)` before converting amounts, but `redeem()` reads `info.internal_decimals` and `external.decimals` directly, with no equivalent check. If an asset's live decimals diverge from the pallet's stored snapshot (a legitimate, non-privileged pallet-assets `set_metadata` action by the asset's own owner — an actor with no privilege over the PSM instance itself), `redeem()` will silently perform unit conversion using the wrong decimal exponent, producing an incorrect `external_out` amount and burning/crediting the wrong quantities for ordinary users.

### Finding Description
This is the same structural bug class as the external report: two pieces of interdependent configuration state (`sy_minter_address` / `sy_wallet_address` in the report; `PsmInfo::internal_decimals` / `ExternalAssetInfo::decimals` here) are each updatable independently, and only one of the two "consumer" code paths defends against the pair going out of sync.

- The internal decimals snapshot is taken once, at PSM creation: [1](#0-0) 
- `mint()` calls `Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?` before doing any conversion, and documents `Error::DecimalsMismatch` explicitly as a possible failure mode: [2](#0-1) [3](#0-2) 
- `redeem()` performs no such re-check. It reads the (potentially stale) snapshot fields directly and feeds them into the same conversion helpers used by `mint()`: [4](#0-3) 

Since `internal_asset`/`external_asset` decimals live in `pallet-assets` metadata and can be changed post-registration by the asset's own management origin (a normal `set_metadata` call, independent of the PSM's own admins), the snapshot recorded in `PsmInfo`/`ExternalAssetInfo` at `create_psm`/`add_external_asset` time can legitimately drift from the live value — exactly the "two related config values updated by two different operations, not kept in sync" pattern described in the report.

### Impact Explanation
If the internal or external asset's live decimals diverge from the pallet's snapshot, `redeem()`'s `internal_to_external`/`external_to_internal` conversions use the wrong scaling factor. This can make the pallet pay out a wildly different (larger or smaller) external amount than the internal amount burned actually represents, or make the "effective" debt bookkeeping (`PsmDebt`) diverge from the real reserve balance drained. Depending on the direction of the decimals change, either the caller can extract a disproportionate amount of the PSM's external reserve (drain from other users/the protocol) or an ordinary user redeeming gets far less than expected (fund loss for the user), directly matching the report's "loss of funds" outcome for an unprivileged user acting in good faith.

### Likelihood Explanation
No compromise of any trusted role is required to trigger the desync: any asset owner calling the standard `pallet-assets::set_metadata` extrinsic on an asset used by a PSM instance changes the live decimals without any coordination with, or notification to, `pallet-psm`. The PSM's own `try_state` invariant checks (`do_try_state`) verify structural consistency (paired admin records, external counts, reserve ≥ debt) but do not check that the internal/external decimal snapshots still match live metadata, so the drift is not caught by existing runtime safety nets: [5](#0-4) 
Any signed user calling `redeem` after such a change is affected — this is a realistic, permissionless trigger path, not a theoretical one.

### Recommendation
- **Short term:** Call the same `Self::ensure_decimals_match(...)` check in `redeem()` that `mint()` already uses, so both entry points fail closed with `Error::DecimalsMismatch` when live decimals diverge from the stored snapshot, instead of silently using stale values.
- **Long term:** Audit all pallet-psm code paths (and any other pallet that snapshots external metadata such as decimals, addresses, or exchange parameters) to ensure every consumer of a cached/snapshotted value re-validates it against the live source of truth, or refactor to avoid snapshotting mutable external state altogether.

### Proof of Concept
Conceptual scenario (I could not execute this against a live test harness in this pass, so treat the numeric example as illustrative rather than verified output):
1. `create_psm` registers a PSM with `internal_asset` at 6 decimals; `PsmInfo::internal_decimals = 6` is snapshotted.
2. Later, the `internal_asset`'s owner calls `pallet_assets::set_metadata` and changes the asset's decimals to, e.g., 18 (a normal, permissionless action for that asset's own management origin, unrelated to the PSM's admins).
3. A user calls `mint`: `Self::ensure_decimals_match` detects `info.internal_decimals (6) != T::Fungibles::decimals(internal_asset) (18)` and mint fails with `Error::DecimalsMismatch`, so no bad conversion happens.
4. The same user calls `redeem` for the same PSM instance: `redeem()` reads `info.internal_decimals = 6` and `external.decimals` directly (lines 825-826) without any live-value check, and converts using the stale exponent, producing an `external_out` that is off by orders of magnitude from the correct amount — resulting in either reserve drain or user fund loss, unlike `mint`, which is protected.
