Confirmed: the HMAC signature over a webhook request is computed only from the raw body bytes, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are taken directly from unauthenticated HTTP headers and are never included in the signed data.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that signable string using `Context.api_secret_key` [2](#0-1) . However, the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are read straight from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) [3](#0-2)  and are never part of the signed bytes. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_tenant`. In this gem, `hmac_signed_bytes` = `raw_body` only, while `bytes_that_determine_the_tenant` = the `shopify-shop-domain` header value used to populate `WebhookMetadata#shop`. These two are disjoint, so the binding is broken: any request whose `raw_body` matches a body previously (or currently) signed by Shopify for the app's secret will pass `HmacValidator.validate` regardless of what `shop`, `topic`, or `webhook_id` header values accompany it.

An unprivileged party who legitimately operates a shop with the app installed will receive real, validly HMAC-signed webhook deliveries for their own store's events. Because the signature never binds to the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid for the app's webhook endpoint no matter which `shop-domain` header is sent alongside it. A user can therefore replay their own legitimately-signed webhook body against the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `x-shopify-shop-domain` header, and the gem will report the HMAC as valid and hand `Registry.process` a `WebhookMetadata` claiming the event originated from the victim's shop [5](#0-4) .

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app relying on `Utils::HmacValidator.validate(request)` plus `request.shop` to authenticate which merchant a webhook event belongs to can be made to process attacker-controlled body data under a different, victim tenant's identity — matching the "cross-tenant access" impact category. Any downstream action keyed off `WebhookMetadata#shop` (e.g., updating cached shop data, triggering per-shop side effects, or deletion/compliance handlers such as `shop/redact`) executes against the wrong tenant.

### Likelihood Explanation
Likelihood is high for any party who already has the app installed on a shop, which is the normal, unprivileged way to interact with the app — no access token, `client_secret`, or privileged account is required. They only need to capture one of their own real webhook deliveries (trivial, since Shopify sends these automatically) and resend the same body with a modified `shop-domain` header.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-verified signable string (or otherwise separately authenticate them, e.g., by deriving the effective shop only from a value that is cryptographically bound to the signed payload), so that `HmacValidator.validate` fails whenever any header used for tenant/topic identification has been altered relative to what Shopify actually signed.

### Proof of Concept
1. App merchant "attacker.myshopify.com" has the app installed and receives a real webhook delivery for topic `orders/create`:
   - Headers: `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`
   - Body: `{"id": 1, ...}` (HMAC computed by Shopify over this exact raw body with the app's `client_secret`)
2. Attacker resends the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `to_signable_string` (the unchanged raw body) and it matches, so validation succeeds [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` and invokes the app's handler as if the event came from `victim.myshopify.com` [7](#0-6) , even though Shopify never sent this event for that shop.
