### Title
Webhook `shop` (and topic/api_version/webhook_id) header identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as valid for a given `shop` purely based on the unauthenticated `x-shopify-shop-domain` header, while the HMAC signature computed and verified by this gem only ever covers the raw request body, not the shop, topic, webhook-id, or api-version headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` / `validate_signature` compute the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` then dispatches to the app's handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which come straight from HTTP headers and are never included in the signed data: [3](#0-2) [4](#0-3) 

This is the same bug class as the POL report: an **identity/tenant field is acted on but is not covered by the message authentication code**. In the POL bug, the amount burned/distributed diverged from the amount actually authorized by the reward-accounting logic. Here, the `shop` value handed to the app's business logic diverges from what the HMAC actually authenticates — the HMAC proves "this body byte-string was produced with our shared secret," not "this body belongs to shop X."

By contrast, the OAuth callback path (`ShopifyAPI::Auth::Oauth::AuthQuery`) does correctly bind `shop` into the signed string: [5](#0-4) 
which shows the library is capable of, and elsewhere does, bind identity fields into the HMAC — but the webhook path does not do this for `shop`.

**Equality that should hold, but doesn't:**
`shop` header value used by `Registry.process` for tenant attribution == `shop` value cryptographically bound into `hmac`. In reality, `hmac` binds only `raw_body`, and `shop` is fully attacker-controllable independent of the body/HMAC pair.

### Impact Explanation
An attacker who can obtain any single valid `(raw_body, hmac)` pair for their own tenant (e.g. by installing the app on a shop they control and capturing a webhook delivery, since webhook endpoints are just public HTTP(S) URLs configured on the merchant's app) can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` will pass because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) body belongs to the victim shop. If the host app trusts `request.shop`/`data.shop` (as the gem's own API is documented and designed to be used — see `WebhookMetadata.new(shop: request.shop, ...)`) to select which tenant's session/data to update, this results in cross-tenant data confusion/injection: order, product, or GDPR-style payloads can be attributed to and processed under a shop the attacker doesn't own.

This matches the Critical "cross-tenant access" impact category, since it lets one merchant's traffic be misattributed to another merchant purely via unauthenticated header manipulation, defeating the identity binding the gem's own `HmacValidator` is supposed to provide.

### Likelihood Explanation
Moderate to High. No secrets, tokens, or privileged access are required beyond installing the app for a normal (even free/trial) shop and being able to send arbitrary HTTP requests to the public webhook endpoint the app already exposes — both are available to any unprivileged internet user acting as a merchant. The only extra work is capturing one legitimate `(body, hmac)` pair, which is trivial for any topic the attacker's own shop can trigger.

### Recommendation
Bind the identity/routing fields into the HMAC-signed material, not just the raw body: include `shop`, `topic`, `webhook_id`, and `api_version` (as canonicalized header values) in `Request#to_signable_string`, and reject the webhook if these signed values don't match the header values ultimately passed into `WebhookMetadata`. Until then, document clearly (and consider enforcing at the gem level) that consuming code must not trust `request.shop`/`data.shop` as an authenticated tenant identifier from a single webhook delivery without additional server-side reconciliation against the shop that the app has independently registered the webhook for.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook of a topic they know produces a body with no shop-domain reference (e.g., `orders/create`), capturing the request: `raw_body = "{...order json...}"`, `x-shopify-hmac-sha256 = valid_hmac_for(raw_body)`.
2. Attacker resends this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but replaces the header `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(raw_body) == hmac` header — the shop header is never part of the check (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's order json>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and, if the host app trusts `shop` to select the tenant record to update, processes attacker-controlled data under the victim's tenant.
