### Title
Panic-based Denial of Service via Unchecked Decimal Exponentiation Overflow in `Calculator::normalize_decimal`/`restore_decimal` - ([File: program/src/math.rs])

### Summary
The CVE describes an InnoDB bug where a network-reachable, easily-exploitable operation causes MySQL to hang or crash (complete availability DOS) without any data corruption. The closest reachable analog in this program is a `.unwrap()`-triggered panic in the decimal-normalization helpers that are invoked on every `Deposit`, `Withdraw`, and swap instruction whenever PNL is taken, using `pc_decimals`/`coin_decimals` values that originate from attacker-supplied SPL mints at pool creation.

### Finding Description
`Calculator::normalize_decimal`, `Calculator::restore_decimal`, and `Calculator::normalize_decimal_v2` all compute `U128::from(10).checked_pow(native_decimal.into()).unwrap()` and then chain further `.unwrap()`-ed `checked_mul`/`checked_div` calls: [1](#0-0) [2](#0-1) [3](#0-2) 

`native_decimal` in these calls is populated from `amm.pc_decimals` / `amm.coin_decimals`, which are derived from the coin/pc SPL token mints supplied by the pool creator at `Initialize2` time. SPL Token mints allow arbitrary `decimals` values (a `u8`, 0–255) to be set by whoever creates the mint — there is no protocol-level cap forcing "reasonable" decimals (e.g., ≤18). If `native_decimal` is large enough that `10^native_decimal` exceeds `U128::MAX` (roughly decimals ≥ 39), `checked_pow` returns `None` and the subsequent `.unwrap()` panics.

These helpers are exercised on the hot path of `calc_take_pnl`, which is called during `process_deposit`, `process_withdraw`, and both swap variants whenever the AMM computes/restores PNL-adjusted totals: [4](#0-3) 

Because the decimals are fixed permanently in `AmmInfo` once a pool is created with `Initialize2`, any pool created against a maliciously-crafted high-decimals mint becomes permanently unable to process `Deposit`/`Withdraw`/swap instructions that reach `calc_take_pnl` — every such transaction panics deterministically.

### Impact Explanation
Once liquidity providers deposit into such a pool (which looks like any other pool from the client side — nothing prevents interacting with an SPL mint carrying an unusual decimals value), the pool becomes permanently non-functional for the affected code paths: LPs cannot withdraw and traders cannot swap through the PNL-adjustment path, resulting in permanent freezing of LP/user funds held in the pool's vaults. This matches the "complete DOS via crash" bug class from the CVE, but manifested here as a permanent on-chain funds-freezing condition rather than a transient service hang, because the panic is deterministic and unconditional for every future transaction touching that pool's PNL accounting.

### Likelihood Explanation
The path is reachable by a fully unprivileged actor: creating an SPL mint with an arbitrary decimals byte is a standard, permissionless SPL Token operation, and `Initialize2` accepts any coin/pc mint pair supplied by the pool creator without validating decimals bounds (based on the `unpack_mint` usage pattern observed in `processor.rs`; the exact `Initialize2` assignment line could not be fully re-verified due to search-budget limits, but `AmmInfo.pc_decimals`/`coin_decimals` are populated from the supplied mints and consumed unchanged by the `Calculator` helpers). No elevated privileges, validator collusion, or off-chain components are required — a single crafted `Initialize2` transaction is sufficient to poison a pool for all future participants.

### Recommendation
- Reject mints with `decimals` above a safe bound (e.g., ≤ 18) during `Initialize2`.
- Replace all `.unwrap()` calls in `Calculator::normalize_decimal`, `restore_decimal`, and `normalize_decimal_v2` with `.ok_or(AmmError::...)?` so out-of-range decimals produce a graceful `ProgramError` instead of a panic, consistent with the checked-arithmetic error handling already used elsewhere (e.g., `calc_total_without_take_pnl_no_orderbook`).

### Proof of Concept
1. Create two SPL mints where at least one has `decimals = 250` (permissionless via `spl_token::instruction::initialize_mint`).
2. Call `Initialize2` to create an AMM pool using these mints; `amm.pc_decimals`/`amm.coin_decimals` are stored from the mint's decimals field.
3. Have any user (or the LP themselves) submit a `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` instruction against this pool.
4. `process_deposit`/`process_withdraw`/swap processing invokes `Processor::calc_take_pnl`, which calls `Calculator::restore_decimal(..., amm.pc_decimals, ...)`, executing `U128::from(10).checked_pow(250.into())`, which overflows and returns `None`; the following `.unwrap()` panics, aborting the transaction and permanently blocking that instruction path for the pool.
