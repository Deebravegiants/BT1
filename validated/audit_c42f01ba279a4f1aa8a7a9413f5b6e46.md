### Title
Webhook shop-domain tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the request body was signed with the app's secret [2](#0-1) . The `shop-domain` header, however, is read independently from the (unsigned) headers and is the value the app's own handler uses to attribute the webhook to a tenant [3](#0-2) . `Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata` after only checking the HMAC of the body [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes the app attributes the webhook to (topic + body + shop)`

In this gem it instead holds only:
`HMAC-verified bytes == raw_body`
while `shop`, `topic`, `webhook_id`, and `api_version` are taken from headers that are never part of the signed content [5](#0-4) .

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds as long as `hmac == HMAC-SHA256(raw_body, api_secret_key)` [6](#0-5) . It then unconditionally forwards `request.shop` (the `x-shopify-shop-domain`/`shopify-shop-domain` header) into `WebhookMetadata`, which is the sole tenant identifier the handler receives and is documented as "The shop domain of the webhook" [7](#0-6) . There is no code path that cross-checks `shop` against anything covered by the signature, or against a previously known/installed shop for that session.

Because the HMAC signs only the body, any request whose body was legitimately signed by Shopify for **some** shop (e.g., a shop where the attacker has installed the same app and thus legitimately receives real webhook deliveries with valid HMACs) can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop, while the HMAC remains valid because it never covered that header. The app's handler will then process/store/act on that payload as if it belongs to the victim tenant, even though the header attribution was never authenticated.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on to route webhook data per-merchant. An attacker who is themselves a legitimate (if unprivileged, in the sense of having no special access to other merchants' data) app installer can obtain arbitrarily many validly-signed bodies for their own shop and relabel them under any other shop's domain when replaying to the app's webhook endpoint, since the gem performs no verification tying `shop` to the signed content. Depending on how the host application uses `data.shop` (e.g., as a lookup key to update per-tenant records, trigger mandatory GDPR webhooks such as `customers/redact`, or gate business logic), this enables cross-tenant data injection/confusion — data or actions attributed to a shop that never actually generated them. This matches the "Cross-tenant access" class of impact called out in scope.

### Likelihood Explanation
Likely/practical: no `api_secret_key`, access token, or privileged account is required beyond what any merchant already has by installing the app on their own store (which yields real, validly-signed webhook deliveries). The attacker only needs to capture one legitimately-signed webhook body/HMAC pair for their own shop (trivial, since they receive their own webhooks) and resend it with a forged `shop-domain` header. The library performs no additional verification to prevent this, and this vulnerability class is explicitly hinted as in-scope ("a field acted on but not covered by the HMAC").

### Recommendation
Include the identifying headers (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or otherwise verify `shop` against an independently trusted source (e.g., the merchant/session record the app already has for the shop that legitimately registered the webhook) before dispatching to handlers. At minimum, document and/or enforce that host applications must not trust `data.shop` for tenant attribution unless they perform this additional check, and consider exposing a helper in `Registry.process` to validate the shop domain against known installed shops.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and enables an `http` webhook (e.g. `orders/create`).
2. Shopify delivers a real webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - body: `{"id": 1, "note": "attacker-controlled content"}`
3. Attacker captures this raw body + HMAC (both fully known/reproducible to them since it's their own shop's data).
4. Attacker resends the exact same raw body and HMAC to the app's webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` computes HMAC over `raw_body` only [1](#0-0)  — validation succeeds because the body/HMAC pair is untouched.
6. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [8](#0-7)  and attacker-controlled body content, and processes it as if it originated from the victim shop.

Note: this analysis is limited to the in-scope library files; whether a specific host application's webhook handler further validates `shop` (e.g. against stored sessions) is outside this gem's code and was not evaluated here, since it is host-application-dependent.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
