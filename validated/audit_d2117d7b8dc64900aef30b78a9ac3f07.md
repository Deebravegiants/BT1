### Title
Webhook `shop`/`topic`/`webhook_id` headers are not bound to the HMAC signature, enabling cross-tenant webhook forgery via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `hmac` and `to_signable_string` purely from the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are taken from unauthenticated HTTP headers that are never part of the HMAC-signed content. `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop`/`topic` values to the application's webhook handler as if they were verified, breaking the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, verified_bytes)` where `verified_bytes` (body only) ≠ `bytes acted on` (body + shop + topic + webhook_id headers).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`HmacValidator.validate` computes the HMAC only over that signable string and compares it to the `hmac-sha256` header, so it authenticates the body bytes only, not the headers:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from the `shopify-*`/`x-shopify-*` headers with no cryptographic tie to the HMAC:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

`Registry.process` treats a successful body-HMAC check as proof that the entire request (including `shop` and `topic`) is authentic, and passes these header-derived values straight to the app-supplied handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

This means the equality the gem is implicitly asserting — "bytes verified by HMAC == bytes acted on by the handler" — does not hold: the HMAC verifies `raw_body` only, but `handler.handle` acts on `raw_body` **plus** `shop`, `topic`, and `webhook_id`, none of which are covered by the signature.

### Impact Explanation
Any party who can obtain one legitimately Shopify-signed `(raw_body, hmac)` pair for their own store (a normal, unprivileged merchant/app-installer can trivially capture this from their own app's webhook endpoint logs) can replay that exact body to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers. Because `HmacValidator.validate` never inspects those headers, the forged request passes validation, and the host application's handler will process attacker-chosen `shop`/`topic` values as if Shopify itself asserted them for that body. In a multi-tenant app that keys session/data lookups off `WebhookMetadata#shop`, this allows cross-tenant data confusion — data destined for/derived from one shop's webhook can be attributed to a different, victim shop merely by re-sending it with a forged `shop-domain` header, without needing the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires the ability to POST arbitrary headers/body to the app's public webhook route and knowledge of one valid `(raw_body, hmac)` pair — obtainable by any merchant/app installer through their own webhook deliveries, or by intercepting any single webhook in transit. No access token, `client_secret`, or privileged account is required, making this reachable by an unprivileged internet-facing actor once they know/replay one legitimate signed payload.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed content, or independently authenticate them (e.g., by having the application verify `shop` against its own session store before trusting `WebhookMetadata#shop`). At minimum, document that `shop`/`topic`/`webhook_id` are not covered by HMAC verification so consuming applications do not treat them as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook `POST` with body `raw_body` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `raw_body` under the app's real secret) alongside `x-shopify-shop-domain: attacker-shop.myshopify.com` and `x-shopify-topic: orders/create`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but replaces the headers with `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `Webhooks::Request.new` parses these forged headers unchanged; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds because the body/HMAC pair is genuinely valid.
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to process attacker-controlled data as though it were an authentic webhook for `victim-shop.myshopify.com`.
