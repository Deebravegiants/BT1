### Title
Pausing HyperFungibleToken/WrappedHyperFungibleToken blocks the timeout-refund path, freezing already-burned/locked user funds - (File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol)

### Summary
`onPostRequestTimeout()` in `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` is gated by the `whenNotPaused` modifier, the same guard used to stop new outbound transfers via `send()`. This mirrors the Sherlock finding: a protective "closed"/"paused" state that is meant to stop *new* activity also disables the *unwind/recovery* path that protects users who already committed funds before the state changed.

### Finding Description
`send()` burns (or locks) the caller's tokens up front and dispatches an ISMP POST request; the tokens are only made whole again when either (a) `onAccept` on the destination succeeds, or (b) the message times out and `onPostRequestTimeout` re-mints/unlocks the funds to the original sender: [1](#0-0) [2](#0-1) 

`onPostRequestTimeout` is declared `onlyHost whenNotPaused`, so if the contract owner pauses the contract (an ordinary emergency action, not malicious) at any point between a user's `send()` and the eventual timeout proof submission, the `IHost`'s call into `onPostRequestTimeout` reverts: [3](#0-2) 

The same pattern exists in the upgradeable variant and in the wrapped (lock/unlock) variant: [4](#0-3) 

Per `handlePostRequestTimeouts()` in `HandlerV2.sol`, when the host's callback into the app reverts (as it will while paused), the request commitment is deleted from `EvmHost` (`dispatchTimeOut` deletes `_requestCommitments[commitment]` before invoking the app callback), so once the callback fails, the timeout **cannot be resubmitted** in a way that re-triggers `onPostRequestTimeout` with the same accounting — the commitment needed to look the request back up is gone: [5](#0-4) 

This is structurally identical to the reported Perennial issue: `Product` being `closed` only blocks *new* risk-taking actions via `notClosed`, but it inadvertently also disables `closeAll` (used for liquidation), the safety-valve needed to resolve positions opened before closure. Here, pausing the token only intends to stop *new* `send()`/`onAccept()` activity, but it also disables `onPostRequestTimeout`, the safety-valve needed to refund tokens burned/locked by transfers dispatched before the pause.

### Impact Explanation
Users who called `send()` (burning or locking their tokens) before a pause was enacted, and whose message subsequently times out while the contract is paused, cannot recover their funds through the timeout-refund mechanism. Because `EvmHost.dispatchTimeOut` deletes the request commitment regardless of whether the downstream callback reverts is check in `EvmHost` (unlike `dispatchIncoming`, which restores state on failure), the retry-until-success guarantee documented for timeouts (`docs/content/developers/evm/api/ihandler.mdx:146-149`) does not hold for this app once the commitment bookkeeping is already removed on the host side, risking permanent loss of the burned/locked principal for affected users. Even under the more conservative reading (that the message can still be retried after unpausing), users' funds remain frozen for the duration of the pause with no way to recover them, which is at minimum a freezing-of-funds issue.

### Likelihood Explanation
Pausing is a normal, expected operational action (documented as being for "emergency situations or during migrations"), not an attacker-controlled or malicious-admin scenario — it is a legitimate protective mechanism whose side effect unintentionally harms honest users who transacted shortly before the pause. Any in-flight cross-chain transfer that times out during a pause window will hit this path, making the scenario realistic and not requiring any adversarial behavior.

### Recommendation
Do not gate `onPostRequestTimeout` (and the underlying-unlock/refund logic in `WrappedHyperFungibleToken`) behind `whenNotPaused`. Refunding/unwinding a request that was already dispatched should always be permitted, mirroring how `Product.closeAll` should remain callable when `closed`. If a pause must halt everything for safety, ensure the host-side commitment is preserved (not deleted) on a reverted callback in this path so that legitimate retries after unpausing remain possible.

### Proof of Concept
1. User calls `HyperFungibleToken.send(...)`, burning `amount` tokens and dispatching a POST request with a timeout.
2. Owner calls `pause()` for an unrelated emergency reason.
3. The dispatched request times out; a relayer submits a valid timeout proof to `HandlerV2.handlePostRequestTimeouts`.
4. `EvmHost.dispatchTimeOut` deletes the request commitment and calls `onPostRequestTimeout` on the token contract.
5. `onPostRequestTimeout` reverts due to `whenNotPaused`; per `dispatchTimeOut`'s logic (no restoration branch shown for this callback, unlike `dispatchIncoming`), the commitment bookkeeping needed to resubmit is gone.
6. The user's burned tokens are neither delivered on the destination chain nor refunded on the source chain, resulting in loss/freezing of funds tied entirely to the pause state rather than any wrongdoing by the user.

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
