### Title
Bonding-curve swap math rounds against the protocol on every trade, systematically leaking curve reserves - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` and `Router._computeSell` compute the output amount by subtracting a floor-divided value from the current reserve (`reserveToken - k/newReserveAsset` and `reserveAsset - k/newReserveToken`). Because Solidity integer division always rounds down, subtracting a floored quotient always *overstates* the amount owed to the trader. This is the exact rounding-direction defect described in the external report (root cause #1: "no rounding direction specified... rounded up while it should be rounded down"), reproduced here in alt.fun's constant-product bonding curve instead of Basin's Well functions.

### Finding Description
`Pair.swap` enforces a K-floor check with a `+1` slack: [1](#0-0) 

That slack was presumably intended to tolerate a single unit of rounding, but because both `_computeBuy` and `_computeSell` already compute `tokensOut`/`assetOut` via floor division and then subtract, the post-swap product `newTokenReserve * newAssetReserve` is *always* `<= k` by construction — the `+1` check is satisfied trivially for any correctly-rounded call and never actually bounds the size of the K decrease: [2](#0-1)  and [3](#0-2) 

For `_computeSell`: `newReserveToken = reserveToken + amountIn` is exact, and `assetOut = reserveAsset - floor(k/newReserveToken)`. The resulting `newAssetReserve = floor(k/newReserveToken)`, so `newTokenReserve * newAssetReserve <= k`, with the shortfall `k mod newReserveToken` (up to `newReserveToken - 1`) handed to the trader as "free" extra `assetOut`. The same pattern applies on the buy side (`tokensOut = reserveToken - floor(k/newReserveAsset)`), overstating `tokensOut`.

Unlike Basin's `Well`, alt.fun has no `totalSupply()`-style LP accounting to check against `calcLpTokenSupply`; the closest analogous protocol invariant is `Pair.k()` itself, which is meant to be non-decreasing across trades (standard constant-product AMM safety property). This finding shows that invariant is *not actually enforced* — it silently decays on every single buy/sell because the output formulas round in the trader's favor, and the on-chain check that should catch this (`(newTokenReserve+1)*(newAssetReserve+1) < k`) is mathematically incapable of catching it for any floor-computed swap.

### Impact Explanation
Every `Bonding.buy`/`Bonding.sell` call (reachable by any unprivileged trader through `Zap.buy`/`Zap.sell` or directly via an allow-listed router) drains a small amount of value out of the curve's reserves relative to the exact constant-product price. This value leak:
- Directly reduces `assetReserve` (LT) available to be graduated (`ltFromPair = assetReserve - virtualLtReserve` in `_prepareGraduationLiquidity`, `packages/contracts/src/Bonding.sol:1084`), meaning less LT is ultimately deposited into the graduated HyperSwap LP than the curve's own price implied it should raise.
- Compounds over the life of every token (curve trading is unbounded in number of trades before graduation), so the aggregate leakage scales with trading volume/activity, not with any single trade size — a systemic value transfer from the protocol/creator/LP side to traders.
- Is directly analogous to the audited Basin finding: rounding direction was not chosen to favor the protocol, and the "invariant" meant to catch it (`K` floor / `+1` slack here vs. `totalSupply()==calcLpTokenSupply` there) does not actually hold because of how the rounding is baked into the very formula it's supposed to check.

This is a real, protocol-level value-leak with no privileged action required, hence a valid Medium/High-severity analog (continuous fund drain from curve reserves, reducing LT ultimately backing the graduated LP and the protocol's own economics).

### Likelihood Explanation
High likelihood of occurrence — this fires on every single buy/sell on every curve token, with no special conditions required (no donation, no pre-seed, no attacker setup). Any unprivileged trader calling `Zap.buy`/`Zap.sell` (or any allow-listed router calling `Bonding.buy`/`Bonding.sell`) triggers it. Per-trade magnitude is small (bounded by `newReserve - 1` units of one 18-decimal-scaled token, i.e. sub-wei-fraction relative to reserve size), but it is unconditional and cumulative across the token's entire trading lifetime.

### Recommendation
Explicitly choose and enforce the rounding direction that favors the protocol in both `_computeBuy` and `_computeSell`:
- For `_computeBuy`, `tokensOut` should be rounded **down** (favoring the pool), not up. Compute `newReserveToken = ceil(k / newReserveAsset)` and derive `tokensOut = reserveToken - newReserveToken`, or equivalently round the intermediate output down explicitly rather than deriving it from a floor-divided complementary reserve.
- For `_computeSell`, `assetOut` should similarly be rounded down: compute `newReserveAsset = ceil(k / newReserveToken)` and `assetOut = reserveAsset - newReserveAsset`.
- Alternatively, keep floor division for the *reserve* being solved for but round the output amount down by an explicit correction, and strengthen `Pair.swap`'s check to something that meaningfully bounds the *cumulative* per-trade rounding loss (e.g. require `newTokenReserve * newAssetReserve >= k`, i.e. K must never decrease at all after correct rounding), rather than the current formula which is automatically satisfied and provides no real protection.

### Proof of Concept
Numeric illustration (units abstracted): Let `reserveToken = 750_000_000e18`, `reserveAsset = X` (virtual LT), `k = reserveToken * reserveAsset`.
1. A trader sells `amountIn` tokens: `newReserveToken = reserveToken + amountIn`.
2. `assetOut = reserveAsset - floor(k / newReserveToken)`.
3. Because `floor(k / newReserveToken) <= k / newReserveToken` exactly, `assetOut >= reserveAsset - k/newReserveToken`, i.e. the trader receives strictly more LT than the exact constant-product price would give, by an amount up to `(newReserveToken - 1)` LT-wei each time `k mod newReserveToken` is close to its ceiling.
4. `Pair.swap` accepts this because `(newTokenReserve+1)*(newAssetReserve+1) >= k` holds for *any* correctly floor-divided `newAssetReserve = floor(k/newReserveToken)`, as shown algebraically above (`(newTokenReserve+1)*(q+1) - k = newTokenReserve + q + 1 - r >= 0` since `r < newTokenReserve`), so the check never reverts and never limits the leak.
5. Repeating over many trades (`Bonding.buy`/`Bonding.sell` calls from any trader) continuously erodes `Pair.k()`'s backing ratio in the trader's favor, reducing the real LT eventually raised and passed into `_prepareGraduationLiquidity`/`finalizeGraduation` for LP seeding.     function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
