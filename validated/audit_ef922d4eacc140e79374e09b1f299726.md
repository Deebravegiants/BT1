### Title
Unlimited router approval + blind calldata forwarding lets any caller sweep stranded token/ETH balances out of `ExternalActionSwap` as their own output UTXO - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap` computes the amount to credit the caller purely from a post-call balance diff of `outputToken`, while `LifiExternalAction.callRouter` grants the router an unlimited allowance on `inputToken` and forwards fully attacker-controlled calldata without ever checking that the router only consumed `inputAmount` of `inputToken`. Any ERC20/ETH balance already sitting in the `ExternalActionSwap` contract (dust from rounding, a stuck refund, or tokens simply sent to the contract) can therefore be pulled into the router's swap and its proceeds credited entirely to the caller who issues the next `Hinkal.transact` swap call, exceeding what Hinkal actually delta-sent that transaction.

### Finding Description
The invariant that should hold is:
`tokens consumed by the action from inputToken this tx == -deltaAmountChanges[0]` (i.e., `inputAmount`).

In `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:44-68`), `inputAmount` is computed as `uint256(-deltaAmounts[0])` and passed to `callRouter`, but `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) never enforces it:

```solidity
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
require(success, "LI.FI swap failed: erc-20 token");
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
```

`approveUnlimited` (`contracts/TransfererBase.sol:32-43`) sets allowance to `type(uint256).max`, and `externalActionMetadata` is attacker-supplied calldata forwarded verbatim to the fixed `router` address. Nothing ties the amount the router actually pulls via `transferFrom` to `inputAmount` — that parameter is effectively decorative for the ERC20 branch. The only accounting done is a balance diff of `outputToken`, which is agnostic to how much `inputToken` was actually spent.

Consequently, if the `ExternalActionSwap` contract holds any pre-existing balance of `inputToken` (e.g., rounding dust left by a prior legitimate swap, a stray transfer, or an unswept refund), an attacker can craft `externalActionMetadata` for the LI.FI router that spends `inputAmount + strandedBalance` of `inputToken` (allowed because of the unlimited approval), producing a larger `swappedAmount`. That larger amount flows straight through:

```solidity
uint256 amountToSendToHinkal = swappedAmount - totalFee;
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, ... stealthAddressStructure: circomData.stealthAddressStructure ... });
```

back to `msg.sender` (Hinkal), which then mints an on-chain commitment for `circomData.stealthAddressStructure` — an address fully controlled by the attacker.

On the `Hinkal.transact` side (`contracts/Hinkal.sol:97-146`), the balance/UTXO equality check does not catch this:
- For the input-token index, `oldBalances`/`newBalances` are taken around `_externalTransact`, which already transferred `-deltaAmountChanges[0]` to the action before `runAction` runs. Hinkal's own balance change for that leg is fixed by construction and matches `amountChanges[0]` regardless of what the (trusted, registered) action internally does with the funds it received plus whatever else it already held.
- For the output-token index, `utxoAmount` is taken directly from the `utxoSet` the action returns, so `balanceDif == amountChanges[i] + utxoAmount` is satisfied trivially — the check never independently verifies that the credited output amount corresponds only to the declared `inputAmount`.

The circuit/ZK proof does not constrain this either: swap outputs are intentionally created on-chain post-execution (since slippage/output amount can't be known at proof time), so the commitment amount is whatever the action returns at runtime, with no proof-side binding to a specific numeric value.

### Impact Explanation
Any unprivileged caller who finds (or engineers) a nonzero pre-existing balance of some `inputToken` inside the `ExternalActionSwap`/`LifiExternalAction` contract can redirect that balance's swap proceeds into their own shielded output UTXO, stealing value that does not correspond to funds Hinkal sent them for that transaction. Since the action contract is shared across all Hinkal users of that swap route, any stranded balance effectively belongs to the protocol/other users, and this is fully repeatable each time residual balance accumulates (e.g., through fee-on-transfer tokens, rounding, or partial-fill leftovers from earlier swaps). This is direct theft of in-flight/protocol funds via an unauthenticated, unlimited router allowance combined with unchecked balance-diff accounting — Critical severity.

### Likelihood Explanation
Preconditions: some non-zero `inputToken` balance must exist in the `ExternalActionSwap` contract before the attacker's call (from dust/rounding on a prior legitimate swap, a fee-on-transfer token, or a stray/refunded amount). The attacker needs no special privileges — they generate their own valid ZK proof for their own UTXO spend (any legitimate deposit works to drive a real `Hinkal.transact` swap call) and simply craft `externalActionMetadata` for the fixed, whitelisted `router` address that consumes more than `inputAmount`. Cost is a single normal swap transaction; the technique is repeatable every time dust reappears, and an attacker can also actively engineer dust (e.g., via a fee-on-transfer or rebasing token or intentionally leaving unspent approved balance in a prior swap) to manufacture stranded balance to later sweep.

### Recommendation
Enforce a strict input-consumption invariant in `callRouter`/`swap`: snapshot `inputToken` balance before the router call and require that the balance decreased by exactly `inputAmount` (revert otherwise), rather than granting `type(uint256).max` allowance and trusting the router calldata. Alternatively, approve only `inputAmount` (not unlimited) before the call and reset to zero afterward, and add a post-call assertion `getERC20OrETHBalance(inputToken) == balanceBeforeInput - inputAmount` (accounting for fee-on-transfer edge cases explicitly). Any leftover token/ETH balance detected in the contract before a swap should be swept back to a designated protocol treasury or refused, not silently available to the next caller's router call.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `LifiExternalAction`/`ExternalActionSwap`, a mock LI.FI router, and mock ERC20 tokens A (input) and B (output).
2. Seed residual: transfer `R` units of token A directly to the `LifiExternalAction` contract address (simulating stranded dust from a prior swap or fee-on-transfer remainder). Assert `tokenA.balanceOf(action) == R`.
3. Attacker performs a normal deposit/shield flow to obtain a valid UTXO of token A worth `X` (small amount), generates a proof for a swap transaction with `deltaAmounts[0] == -X`, `erc20TokenAddresses = [A, B]`.
4. Craft `externalActionMetadata` calling the mock router's `swap(address tokenIn, uint256 amountIn, address tokenOut)` with `amountIn = X + R` (allowed since `approveUnlimited` grants max allowance regardless of the declared `X`), configured so mock router performs `transferFrom(action, router, X+R)` of token A and sends `swappedAmount` of token B back to the action.
5. Call `Hinkal.transact(...)` with this proof/circomData.
6. Assert: `tokenA.balanceOf(action) == 0` (both `X` and the stranded `R` were consumed), and the resulting on-chain UTXO/commitment amount for token B credited to the attacker's `stealthAddressStructure` corresponds to swapping `X+R`, not just `X` — i.e., `utxoSet[0].amount > f(X)` where `f` is the expected output for spending only `X`.
7. This demonstrates `tokens leaving the action (X+R) != -deltaAmountChanges sent that tx (X)`, with the excess captured by the attacker's own UTXO.
