This confirms the root-cause finding: the `shop` (and `topic`) header is treated as authenticated/trustworthy identity data once HMAC validation passes, but the HMAC signature never actually covers it.

### Title
Webhook `shop`/`topic` identity spoofing via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentically originating from the shop named in the `x-shopify-shop-domain` header once `Utils::HmacValidator.validate` succeeds. However, the HMAC signable string is derived solely from the raw body, so the `shop` and `topic` headers are never bound to the signature. An attacker who legitimately installs the app on their own store (an unprivileged action) can capture a genuinely-signed webhook body/HMAC pair from Shopify and replay it to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header value, causing the app to process attacker-controlled data as if it came from any other shop the app is installed on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from unauthenticated HTTP headers: [4](#0-3) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body only) and compares it against the received `hmac` header: [5](#0-4) 

`Registry.process` uses this same validation result to gate trust for the entire request, then forwards the unauthenticated `request.shop` and `request.topic` values straight into the handler via `WebhookMetadata`: [6](#0-5) 

The broken identity binding is:
`HMAC-verified(raw_body)` ⟹ assumed `shop-domain header == true originating shop`

but in reality `shop-domain header` is attacker-controlled and independent of the signature. Because the app's `api_secret_key` is shared across all shops that install the app, any shop owner (including an attacker who installs their own free/dev-store instance of the app) can generate arbitrarily many validly-HMAC-signed `(body, hmac)` pairs from their own real Shopify webhooks, then replay those bytes to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop that also has the app installed. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` dispatches the (attacker-authored) body to the handler labeled as belonging to the victim shop.

### Impact Explanation
This breaks the tenant-isolation guarantee documented for webhook processing ("this will verify the request did indeed come from Shopify" plus `shop` being "The shop domain of the webhook"). Any host application that uses `data.shop` to route persistence, cache invalidation, authorization, or business logic (the exact pattern shown in the gem's own webhook documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will attribute attacker-crafted webhook content to a victim tenant. This is a cross-tenant data-injection/confusion primitive: attacker-controlled order/product/customer payloads can be injected into a victim shop's processing pipeline, potentially triggering unauthorized state changes, false business events, or record overwrites keyed by shop domain.

### Likelihood Explanation
Exploitation only requires: (1) the attacker being able to install the target app on their own Shopify store (an unprivileged, self-service action available to anyone), (2) triggering any subscribed webhook topic on their own store to obtain a genuine `(raw_body, hmac)` pair, and (3) POSTing that pair to the app's public webhook URL with a forged `x-shopify-shop-domain`/`x-shopify-topic` header. No access token, `client_secret`, or victim credentials are needed — the webhook endpoint is a public URL by design. This does not require the host application to violate documented usage; it follows the exact pattern the gem's own docs recommend.

### Recommendation
Bind the identity-relevant headers into the HMAC-signable string, or otherwise authenticate them independently. Since Shopify's actual HMAC computation (matching what `x-shopify-hmac-sha256` contains) is defined by Shopify and only covers the body, the safer fix is for `Registry.process`/`WebhookMetadata` to not present `shop`/`topic` as verified/trusted fields without additional server-side cross-checks (e.g., requiring the caller to confirm the `shop` header matches an actively-registered webhook subscription id/session for that shop, or validating against Shopify's per-shop webhook registration records) before dispatching to handlers. At minimum, update documentation to explicitly warn that `data.shop`/`data.topic` are NOT covered by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and subscribes to `orders/create`.
2. Attacker triggers an order creation on their own store, capturing the real webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since Shopify signs with the app's shared `api_secret_key`).
3. Attacker sends a new HTTP POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header [7](#0-6) .
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` [5](#0-4) .
6. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host app to process attacker-controlled order data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
