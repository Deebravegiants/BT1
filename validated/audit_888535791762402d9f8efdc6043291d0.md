### Title
Zap has no mechanism to recover stray USDC/LT/Token balances sent via direct ERC20 transfer, causing permanent loss of those funds - ([File: packages/contracts/src/Zap.sol])

### Summary
The Rio report shows that value credited to a contract by a path other than the contract's expected "trigger" (its `receive()` function) is invisible to that contract's distribution accounting and becomes permanently unrecoverable because no method exists to manually sweep/distribute it. `Zap.sol` reproduces this exact bug class: every balance movement inside `Zap` is computed from function-scoped amounts (`usdcAmount`, `netUsdc`, `ltMinted`, `ltReceived`, `tokensOut`) rather than from `balanceOf(address(this))`, and `Zap` exposes no owner-only or permissionless rescue/sweep function anywhere in the contract.

### Finding Description
`Zap._executeBuy` and `Zap._sellInternal` never read `IERC20(usdc).balanceOf(address(this))` or `IERC20(lt).balanceOf(address(this))` to decide how much to forward onward; they operate strictly on the `usdcAmount` pulled via `safeTransferFrom` in the same call and on `ltMinted`/`ltReceived` values returned by the mint/redeem/curve calls: [1](#0-0) [2](#0-1) 

Because a launched `Token`, an LT, and USDC can all be sent to `Zap` via a plain ERC20 `transfer` (an unprivileged, permissionless action explicitly reachable by any wallet, per the analog scope list), any such donation lands on `Zap`'s balance but is never referenced by any accounting path inside `buy`/`sell`/`createToken`. Unlike its sibling contracts, `Zap` has no analogue of `FeeVault.sweepDonations()` (which sweeps USDC surplus above `totalAccruedCreator + protocolBalance` to `feeTo`) or of `Bonding._sweepLTToOwner()` (which sweeps LT above `protectedLT` to `owner()` inside `finalizeGraduation`): [3](#0-2) [4](#0-3) 

A grep of `Zap.sol` for `onlyOwner`/`withdraw`/`rescue`/`sweep` shows only the fee-parameter setters — no function that ever moves an unbacked/undirected balance out of the contract. Any USDC, LT, or launched Token that lands on `Zap` outside the exact in-flight `buy`/`sell` computation is therefore permanently stranded — precisely the "value arrives through a path the contract's accounting doesn't watch, and there is no manual distribution method" failure mode described in the Rio M-4 report, just instantiated against `Zap`'s balance-less accounting instead of a `receive()` function.

### Impact Explanation
Any ERC20 (USDC, a launched `Token`, or an LT) sent directly to the `Zap` proxy address by a mistaken or curious unprivileged wallet is permanently and irrecoverably lost — no owner, creator, or permissionless caller can ever move it out. This is a straightforward theft/freezing-of-funds primitive: funds are locked in a live, in-use contract with zero code path to reach them, for the lifetime of the deployment (or until a UUPS upgrade adds a sweep, at which point the "fix" is identical in spirit to the Rio remediation of adding a manual distribution method).

### Likelihood Explanation
`Zap` is the sole user-facing entry point advertised for buying/selling/creating tokens, so it is the address users are most likely to interact with and, by extension, mistakenly send tokens to directly (e.g., pasting the `Zap` address instead of a token/LP address, or a bot/integration sending an LT balance there instead of calling `sell`). No privilege, timing, or special sequencing is required — a single unprivileged `transfer` call is sufficient to strand funds.

### Recommendation
Add a permissionless or owner-gated sweep function to `Zap`, mirroring `FeeVault.sweepDonations()` / `Bonding._sweepLTToOwner()`, that computes the contract's live balance of USDC/LT/Token, subtracts anything legitimately in-flight (which for `Zap` should always be zero at rest, since `nonReentrant` guards every entry point and no state persists funds between calls), and forwards the surplus to a designated recipient (e.g. `feeTo`/protocol treasury), emitting an event for indexer visibility.

### Proof of Concept
1. Deploy the protocol per its test harness (`Zap`, `Bonding`, `FeeVault`, a mock LT, mock USDC).
2. From an unprivileged wallet, call `usdc.transfer(address(zap), 100e6)` (or `token.transfer(address(zap), amount)` for a launched `Token`, or `lt.transfer(address(zap), amount)`).
3. Observe `usdc.balanceOf(address(zap))` (or the LT/Token balance) is now non-zero.
4. Execute normal `zap.buy(...)`/`zap.sell(...)` flows and observe none of them ever reference or move this donated balance — `_executeBuy`/`_sellInternal` only ever transfer amounts derived from the current call's `usdcAmount`/`tokenAmount`, never `balanceOf(address(this))`.
5. Confirm there is no function on `Zap` (owner-only or otherwise) that can transfer this stranded balance anywhere — the donated funds remain locked in the contract permanently.

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }
