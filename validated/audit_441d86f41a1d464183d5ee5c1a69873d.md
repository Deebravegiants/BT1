### Title
Withdrawal status misreported across batched same-asset withdrawals due to assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches a specific batch-withdrawal entry to a status record returned by the POA Bridge API using only the token's `assetId`, ignoring `destinationAddress` and `amount`. When a caller submits a batched withdrawal (via `IntentsSDK.signAndSendWithdrawalIntent` with an array of `withdrawalParams`) containing two or more withdrawals of the *same* token to *different* destinations/amounts in one NEAR transaction, polling for completion of one withdrawal index can return the `completed` status and `txHash` that actually belongs to a *different* withdrawal index in the same batch.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  selects the first withdrawal record in the API response whose `near_token_id` matches the requested `assetId`:

```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```

This function is called independently for each batched withdrawal index from `describeWithdrawal` [2](#0-1) , which is invoked per-index by the SDK's completion-polling orchestration: [3](#0-2) 

`signAndSendWithdrawalIntent` explicitly supports submitting an array of `withdrawalParams` in a single NEAR transaction (`isBatchMode`) [4](#0-3) . If two entries in that batch share the same `assetId` (e.g., withdrawing the same token to two different destination addresses/amounts), the POA Bridge status API returns multiple withdrawal records for the single NEAR tx hash, distinguished only by `near_token_id`/amount/destination on the API side — but `findMatchingWithdrawal` has no way to disambiguate them and always returns the *first* record with that token id, regardless of which batch index is asking.

The intended equality being broken is: *the status/txHash reported for withdrawal index N must correspond to the on-chain outcome of withdrawal index N's specific (assetId, amount, destinationAddress) tuple.* Instead, the code reports "the outcome of any withdrawal of this asset in this tx," which is a different, weaker guarantee. The code comment even acknowledges this as a known, unhandled edge case ("multiple withdrawals of the same token in a single transaction are not supported").

### Impact Explanation
If withdrawal index 0 (to address A) completes first while withdrawal index 1 (to address B, same asset) is still pending or fails, `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` polling for index 1 will match the same underlying record and report `{status: "completed", txHash: <A's hash>}` for index 1 as well. An integrator relying on this SDK API to confirm delivery before crediting/releasing downstream funds could mark withdrawal to address B as completed based on a txHash that has nothing to do with address B — a status misreport that can cause a double credit or a false confirmation of funds delivered to the wrong destination. This matches the "High" impact category: *"a status or hash misreport making an integrator credit or refund twice."*

### Likelihood Explanation
This requires no adversarial relayer, bridge, or admin behavior — it is triggered by a normal, SDK-supported usage pattern (batch withdrawal of the same token to multiple destinations/amounts in one call), which the SDK's public API explicitly allows. The only precondition is that the POA-bridge status API can, and does, return multiple entries per NEAR tx hash for the same token, which the code's own comments and `findMatchingWithdrawal` documentation acknowledge is a real, unhandled scenario.

### Recommendation
Disambiguate matching using more than `assetId`: at minimum also match on `amount` and `destinationAddress` (and `destinationMemo` where applicable), or use a stable per-index correlation from the POA Bridge API (e.g., an explicit sequence/order field or `external_id`) if available. Until the POA API exposes such a field, the SDK should refuse to report `completed` for batched entries with duplicate `assetId` unless a strict 1:1 mapping (e.g., by sorting API results and withdrawal params by amount, as the existing comment suggests) can be established, and should surface an explicit ambiguity error rather than silently reusing another entry's result.

### Proof of Concept
Conceptual reproduction (not executed, since this is a TypeScript SDK, not a chain-executable PoC):
1. Call `sdk.signAndSendWithdrawalIntent` with `withdrawalParams: [ { assetId: "nep141:usdc.omft.near", amount: 100n, destinationAddress: "addrA" }, { assetId: "nep141:usdc.omft.near", amount: 200n, destinationAddress: "addrB" } ]` — both go into a single NEAR intent tx.
2. POA relayer processes the withdrawal to `addrA` and marks it `COMPLETED` with `transfer_tx_hash = "0xA"`, while `addrB`'s withdrawal is still `PENDING`.
3. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [paramsA, paramsB], intentTx })`.
4. For index 1 (`addrB`), `describeWithdrawal` calls `getWithdrawalStatus` (returns both records), then `findMatchingWithdrawal` filters by `assetId === "nep141:usdc.omft.near"` only, and `.find()` returns the *first* matching record — the `addrA` `COMPLETED` entry — causing index 1 to also resolve as `{status: "completed", txHash: "0xA"}` even though the withdrawal to `addrB` has not completed.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}
