Audit Report

## Title
Non-atomic JWT replay check-and-record in `WorkflowMetadataHandler.Authorize` allows concurrent replay of a single HTTP-trigger JWT - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtReplayCache.isReplay` (which takes an `RLock`) and only records usage via `jwtReplayCache.recordUsage` (a separate `Lock`) after JWT verification and authorized-signer lookup complete. Because these are two independent, non-atomic critical sections, two concurrent requests bearing the identical signed JWT can both pass the `isReplay` check before either calls `recordUsage`, resulting in duplicate acceptance of a single-use token.

## Finding Description
In `Authorize`, the sequence is: verify JWT signature, call `h.jwtCache.isReplay(claims.ID)` (RLock/RUnlock), look up authorized keys, verify signer, and finally call `h.jwtCache.recordUsage(claims.ID)` (Lock/Unlock) at [3](#0-2) . The `isReplay` and `recordUsage` methods are implemented with fully separate mutex sections rather than one combined check-and-set operation [4](#0-3) . This contrasts with the properly atomic pattern used in the Vault component's `RequestReplayGuard.CheckAndRecord`, which performs the existence check and the map write inside a single held lock [5](#0-4) . `Authorize` is reachable from the internet-facing HTTP Trigger path via `httpTriggerHandler.authorizeRequest`, which passes the raw request and JWT straight through with no additional serialization or idempotency guard [1](#0-0) .

## Impact Explanation
If an attacker or hostile intermediary fires two copies of a request carrying the same signed JWT (`jti`) concurrently, both can observe `isReplay == false` before either records usage, and both will pass signer authorization and be dispatched to the DON as legitimate workflow executions. This defeats the single-use guarantee of the JWT `jti`, resulting in duplicate/unauthorized workflow execution using a single authorized token — an unauthorized job run.

## Likelihood Explanation
Exploitation only requires possession of one previously-issued valid JWT and the ability to send two HTTP requests concurrently to the gateway's HTTP Trigger endpoint — trivial for any external client holding a legitimately obtained token, no special privileges needed beyond that. The race window is bounded by JWT verification and workflow/authorized-key lookup time, which is a real, deterministic (not merely theoretical) window since the check and the write are demonstrably in separate critical sections, and no other synchronization (e.g., a per-`jti` or per-request mutex) exists upstream in `httpTriggerHandler.HandleUserTriggerRequest` to serialize these calls.

## Recommendation
Replace the separate `isReplay`/`recordUsage` calls in `Authorize` with a single atomic `checkAndRecord(jti)` method on `jwtReplayCache` that acquires one `mu.Lock()` covering both the existence check and the map insert, mirroring `RequestReplayGuard.CheckAndRecord`. Move this atomic check to occur before or immediately combined with JWT verification result usage so that no window exists between check and commit.

## Proof of Concept
1. Register a workflow and obtain a valid signed JWT for an `HTTPTriggerRequest`, as in `TestHttpTriggerHandler_HandleUserTriggerRequest`.
2. Launch two goroutines concurrently calling `WorkflowMetadataHandler.Authorize(workflowID, tokenString, req)` with the identical token.
3. Because `isReplay` and `recordUsage` are separately locked, both goroutines can observe `isReplay == false` prior to either calling `recordUsage`, causing both to succeed — unlike the sequential-only existing test `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate JWT token and request ID" subtest, which does not exercise concurrency at [2](#0-1) . A concurrency test analogous to `TestRequestReplayGuard_ConcurrentAccess` (used for the Vault guard) but targeting `jwtReplayCache`/`Authorize` would confirm the race deterministically with `-race`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
