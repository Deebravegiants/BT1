### Title
Webhook Shop/Topic/ID Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity using only an HMAC over the raw request body, but then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because the same shared `api_secret_key` is used to sign every shop's webhooks, and because the HMAC is computed only over `@raw_body`, any party who can obtain one validly-signed `(raw_body, hmac)` pair (e.g., by triggering a webhook for their own, legitimately-installed shop) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `topic`/`webhook-id`) headers to impersonate a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers that are never included in the signed string: [2](#0-1) 

`HmacValidator.validate` only checks that `hmac` matches `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it authenticates the body bytes, not the header-carried identity fields: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to construct the metadata handed to the app's handler, with no additional binding check that these header values are the ones Shopify actually associated with the signed body: [4](#0-3) 

This is the same identity-binding gap described in the external report: a value used to drive downstream logic (`rate` for the liquidation math) is not the value that was actually verified (the accrued rate). Here, the value verified is "these body bytes were signed with the app secret," but the value acted upon for tenant identification (`shop`) is never part of what was verified. Equality that should hold — `shop verified-by-signature == shop used-for-tenant-scoping` — does not, because `shop` is outside the HMAC's scope entirely.

### Impact Explanation
Because `api_secret_key` is shared across every shop that installs the app (it is not shop-specific), a legitimately-signed webhook body from Shop A's own install can be replayed against the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to Shop B. Any handler that uses `WebhookMetadata#shop` to scope data writes, cache keys, or side effects (a standard and encouraged usage pattern per this gem's own docs) can be tricked into attributing Shop A's payload to Shop B, i.e., cross-tenant data confusion/injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker needs only to be a real (even free-tier) merchant who has installed the app — they can trivially trigger a webhook for their own shop, capture the raw body and its HMAC, and replay it to the app's public webhook URL with a forged `shop`/`topic`/`webhook-id` header. No access to `api_secret_key`, tokens, or privileged accounts is required beyond normal app installation, which is the intended, unprivileged use case for this gem's webhook consumers.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the verified material, e.g., by requiring handlers to cross-check `request.shop` against an expected/registered shop for the session under which the webhook was registered, or by having `Registry.process` require and verify a shop parameter supplied out-of-band (such as the URL path used for a specific shop's webhook callback) rather than trusting the `shopify-shop-domain` header verbatim. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used for tenant-scoping decisions without independent verification.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled) and let it deliver a real webhook, capturing the exact `raw_body` and `shopify-hmac-sha256` header sent to `/webhooks` (this pair is valid because it's signed with the app's single shared `api_secret_key`, per `HmacValidator.validate`: [5](#0-4) ).
2. Replay an HTTP POST to the same endpoint with the identical `raw_body` and `shopify-hmac-sha256`, but set `shopify-shop-domain: shop-b.myshopify.com` (and optionally alter `shopify-topic`/`shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `@raw_body` is checked: [6](#0-5) .
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "shop-b.myshopify.com"` even though the payload actually originated from Shop A: [7](#0-6) . Any handler logic keyed on `data.shop` now operates on Shop B's tenant context using Shop A's data.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
