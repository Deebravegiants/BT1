### Title
Disabled overfill clamp lets a manipulated Uniswap V4 venue price drain solver funds on intent fills - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Simplex filler's `FXFiller.evaluateOrder` (in `sdk/packages/simplex/src/strategies/fx.ts`) sizes each order leg's payout (`policyMaxOutput`) using a rate that, for venue-priced pairs, comes directly from the live Uniswap V4 pool tick (`UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd`), with no execution-cost or size-impact adjustment. The code previously clamped `policyMaxOutput` to `(1 + maxOverfillBps) × order.output.amount` as a safety bound against "a bug / stale cache / manipulated venue price," but that clamp has been intentionally disabled and now only emits a warning, per the comment at [1](#0-0) .

### Finding Description
This mirrors the "single-sided depositing through the vault with a preliminary step" bug class: an unprivileged actor first shifts an AMM pool's spot price with a swap, then interacts with a system that blindly trusts that pool as its pricing oracle for sizing a payout, and finally reverses the swap to restore the pool, pocketing the difference.

Here, the reachable actor is an intent placer (any unprivileged address that can call `IntentGateway.placeOrder`). The exploit path is:
1. The attacker swaps against the Uniswap V4 pool the filler uses for venue pricing (`docs/content/developers/sdk/api/intent-gateway.mdx:205-225`, `sdk/packages/simplex/docs/ai/flows/venue-pricing-uniswap-v4-funded-pairs.md`) to move `sqrtPriceX96` in their favor. `checkPriceGuard` only rejects deviation from a *static* reference price, not execution cost or self-inflicted short-term manipulation, as noted in [2](#0-1) .
2. The attacker places an order on the manipulated pair. `FXFiller.evaluateOrder` computes `policyMaxOutput` from the manipulated pool mid-price, which can now exceed a sane bound relative to `order.output.amount`.
3. Previously, `policyMaxOutput` was clamped to `overfillCeiling = order.output.amount * (1 + maxOverfillBps) / 10000`, protecting the filler from paying out based on a stale/bad/manipulated price. This clamp has been removed — the code still computes `overfillCeiling` and compares against it, but only to log a warning; `policyMaxOutput = rawPolicyMaxOutput` is used unclamped for the actual fill amount, per [3](#0-2) .
4. The solver's automated bidding pipeline (`ContractInteractionService.prepareBidUserOp`) signs and submits a `UserOperation` that fills the order with the inflated, manipulated-price-derived output amount, and `IntrinsicIntents._fillSameChain` / `ExtrinsicIntents._fillCrossChain` faithfully transfer that amount to the beneficiary since the gateway only checks `solverAmount >= totalRequired`, per [4](#0-3) .
5. The attacker then reverses their initial swap, restoring the pool to its normal price, having profited on the excess output the filler paid from its own inventory (wallet balance or Uniswap V4 LP position withdrawal).

This is the same root cause as the referenced report: a price-sizing mechanism trusts a live, attacker-movable AMM state as ground truth for computing a payout, and the only safety net against that manipulation was explicitly disabled.

### Impact Explanation
Concrete theft of solver funds: the filler pays out tokens sized against a price the attacker temporarily engineered, with no per-leg loss bound in place. Because `desiredOutput`/`policyMaxOutput` feeds directly into `finalOutputAmount` used both for the transfer to the beneficiary and for sizing withdrawals from the Uniswap V4 vault position (`liquidityRemoval`), an attacker can repeatedly extract the solver's inventory (wallet balance and/or LP-backed liquidity) each time they can move the venue pool price within the bounds `checkPriceGuard` still allows. This is a High-severity, fund-loss issue for any solver operating with Uniswap V4 venue pricing.

### Likelihood Explanation
High likelihood: this requires no privileged access — any address that can swap in the referenced Uniswap V4 pool and place an intent order can attempt it. The clamp removal is explicit and documented in the codebase itself (`docs/ai/decisions/...`), confirming the safety mechanism is currently absent by design rather than by oversight, and `checkPriceGuard`'s static-reference-only check does not defend against a short-lived, attacker-created price excursion within its tolerance band, or against repeated exploitation across separate orders each re-manipulating the pool.

### Recommendation
Reinstate an execution-aware bound on `policyMaxOutput` for venue-priced legs instead of a warn-only overfill ceiling: clamp `finalOutputAmount` to `order.output.amount × (1 + maxOverfillBps)` (or otherwise reject/skip the leg) rather than filling the unclamped, price-derived amount. Additionally, incorporate the pool's realized execution cost/size impact (not just the raw mid) into `computeDirectPoolPriceUsd`, and make `checkPriceGuard` detect intra-block/same-transaction price deviation (e.g., via TWAP or a minimum settlement delay) rather than only comparing to a static reference, closing the same-block manipulate-then-fill-then-reverse pattern described in the source report.

### Proof of Concept
Not independently executable from the index alone (requires live Uniswap V4 pool + filler bot deployment to demonstrate end-to-end); the exploit mechanics follow directly from the disabled clamp documented in the filler's own code comment:

// previously protected against a bug / stale cache / manipulated venue
