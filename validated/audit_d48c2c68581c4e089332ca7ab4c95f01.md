## Title
Batch message handlers in `HandlerV2` revert entire relayer transaction when a single item in the batch is stale/duplicate/timed-out - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` each iterate over an untrusted, relayer-submitted batch and `revert` the *entire* transaction as soon as a single element in the batch is a duplicate, timed out, or otherwise already processed — exactly the pattern flagged in the referenced Kairos `repay()` report, where one bad item in a loop DoSes an otherwise-valid batch.

### Finding Description
In `handlePostRequests`, the first loop validates every leaf before verifying the MMR multiproof, and a second loop dispatches each request after checking `requestReceipts`: [1](#0-0) 

The same shape appears in `handleGetResponses` (checking `responseReceipts` per item): [2](#0-1) 

and in `handlePostRequestTimeouts`/`handleGetRequestTimeouts`, which `revert UnknownMessage()` if a request's fee-metadata was already cleared (i.e. already delivered/timed-out by a competing transaction): [3](#0-2) [4](#0-3) 

Because these functions are `external` and process a single MMR multiproof covering the *whole* batch (`request.proof.multiproof` / `message.proof.multiproof`), the batch cannot be partially applied — a `DuplicateMessage()`, `MessageTimedOut()`, or `UnknownMessage()` revert on any one leaf unwinds the whole call, including all other valid, still-pending items. This is architecturally different from `EvmHost.dispatchIncoming`, which was explicitly hardened to *not* revert the batch on a per-item failure (early `return` instead of `revert`): [5](#0-4) 
but the pre-checks executed inside `HandlerV2` *before* `dispatchIncoming` is ever called still use hard reverts, so that mitigation never gets a chance to run for duplicate/timeout/unknown items.

The relayer network itself acknowledges this race exists — `retries.rs` explicitly notes "a batch carrying it twice reverts on the duplicate" as a rationale for de-duplicating parked requests before resubmission: [6](#0-5) 
but this only covers the relayer's own re-submission bookkeeping; it does nothing to protect against a *second, independent* relayer (or the honest relayer's own earlier still-in-flight transaction) delivering one overlapping item first, which is a foreseeable and permissionless race since `handlePostRequests`/etc. are explicitly "permissionless" per the docs.

### Impact Explanation
Relayers batch many POST requests / GET responses / timeouts into one `HandlerV2` call (and/or one `batchCall`) specifically to amortize gas and MMR-proof-verification cost. If any single leaf in that batch was already delivered/timed-out by a race with another relayer (or by the relayer's own concurrent submission), the entire transaction reverts:
- All gas for consensus/state verification and MMR multiproof verification across the whole batch is wasted.
- All other genuinely pending, valid requests/responses/timeouts in that batch fail to be delivered in that attempt, delaying cross-chain message delivery for unrelated users.
- Because relaying is permissionless and competitive, this can recur repeatedly for large batches under normal relayer-network congestion, degrading delivery reliability of the bridge (a "route unable to deliver messages" condition under sustained contention), which is a realistic Medium-severity DoS against message delivery liveness rather than a fund-loss bug.

### Likelihood Explanation
This requires no privileged access — any two independent, permissionless relayers (or the SDK's self-relay flow) racing to deliver overlapping batches of POST requests/responses/timeouts is a normal, expected occurrence in a live relayer network, especially as batch sizes grow to reduce gas overhead as encouraged by `batchCall`/`submit_batch_messages`: [7](#0-6) 

### Recommendation
Change the per-item duplicate/timeout/unknown checks in `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` from hard `revert`s to `continue`/skip semantics for the affected leaf, mirroring the `EvmHost.dispatchIncoming` pattern of tolerating per-item failure without aborting the whole batch. Since the MMR multiproof still needs every original leaf hash to verify the root, the skip must happen only in the dispatch loop (after proof verification), not by dropping leaves from the proof itself — i.e., keep leaves in the proof-verification loop, but downgrade the dispatch loop's `DuplicateMessage`/`UnknownMessage`/`MessageNotTimedOut` reverts to per-item skips that emit an event and continue.

### Proof of Concept
1. Relayer A submits `handlePostRequests` with a batch of 20 `PostRequestLeaf`s and a valid MMR multiproof for all 20.
2. Concurrently, Relayer B submits a transaction delivering just request #7 (e.g., via a single-item `handlePostRequests` call as built by `single_request_messages` in the tesseract retry logic).
3. If Relayer B's transaction is mined first, `host.requestReceipts(leaf.request.hash())` for request #7 is now non-zero.
4. Relayer A's transaction reaches the dispatch loop at [8](#0-7) , hits `DuplicateMessage()` on item #7, and the entire transaction reverts — the other 19 valid, pending requests are not delivered and all gas spent on proof verification is wasted.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
