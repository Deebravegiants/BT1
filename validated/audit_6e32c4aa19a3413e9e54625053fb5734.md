### Title
Webhook HMAC signature does not cover the `shop`, `topic`, `webhook_id`, or `api_version` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface used by `HmacValidator` to authenticate incoming webhooks. The `to_signable_string` method used for HMAC verification returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` — the identity fields the host application relies on to route and attribute the webhook to a specific merchant — are read directly from HTTP headers that are never included in the signed content.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Registry.process` validates the webhook solely via this signable string:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

However, `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all parsed straight from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are completely outside the HMAC's coverage:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

This breaks the intended binding: `HMAC-verified(body) == HMAC-verified(shop attributed to that body)`. In reality the gem only proves `HMAC-verified(body)`, while `shop` (and the other headers) is attacker-controlled and unauthenticated. Since a legitimate merchant (an "unprivileged internet user" relative to other tenants of the same app) regularly receives genuinely signed webhook deliveries for their own shop, they possess a valid `(raw_body, hmac)` pair. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and `Topic`/`Webhook-Id`) to claim the payload originated from a different shop. `HmacValidator.validate` will still pass because it never inspected the header values, and `Registry.process` forwards the forged `shop` value straight into `WebhookMetadata` for the handler to trust and act on.

### Impact Explanation
Any host application that uses `request.shop` from `WebhookMetadata` to key data mutations (e.g., "look up shop X's session/store record and update its order/inventory based on this webhook body") can be tricked into applying a forged tenant identity to a validly-signed but misattributed payload. Because the shop identity is the primary tenant boundary in a multi-tenant Shopify app, this constitutes cross-tenant data confusion/access — matching the Critical "cross-tenant access" impact category, since an unprivileged merchant of Shop A can cause the app to process a legitimately-signed webhook as if it belonged to Shop B.

### Likelihood Explanation
Any merchant who has installed the app receives regular, genuinely-signed webhooks (order updates, product changes, mandatory GDPR topics, etc.), giving them an unlimited supply of valid `(raw_body, hmac)` pairs to replay with a forged `shop-domain` header, with no need for the `api_secret_key`, TLS interception, or privileged access — only the ability to POST to the app's public webhook endpoint.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or independently verify the `shop` value against a value that is bound to the body (e.g., re-fetch/verify shop identity via a signed field inside the JSON body, or require the host app to correlate the header shop with an existing installed-shop session before trusting it), and document that `request.shop`/`request.topic` are NOT covered by `hmac` in `to_signable_string`, so relying on them for authorization decisions without further checks is unsafe.

### Proof of Concept
1. App merchant "shop-a.myshopify.com" installs the app and normally receives a legitimately-signed webhook: 
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: shop-a.myshopify.com`
   - Body: `{"id": 1, "total_price": "100.00", ...}`
2. Attacker (merchant of shop-a) captures this raw body and its valid `x-shopify-hmac-sha256` value (trivial — it is delivered to their own server).
3. Attacker replays the identical body and HMAC header to the app's webhook endpoint, but changes only:
   - `x-shopify-shop-domain: shop-victim.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new` builds the request from headers; `HmacValidator.validate` recomputes the HMAC over `@raw_body` only — this matches the header HMAC because the body is unchanged — the request is accepted as authentic. [5](#0-4) 
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: "shop-victim.myshopify.com", body: <shop-a's order body>, ...))`, causing the host application's handler to process shop-a's order data under shop-victim's tenant context. [2](#0-1)
