Confirmed: `ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with `to_signable_string` returning only `@raw_body`, so the HMAC that `HmacValidator.validate` checks (`lib/shopify_api/utils/hmac_validator.rb`) authenticates the body bytes only — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never part of the signed material, yet `Registry.process` reads `request.shop` straight off the unauthenticated header and hands it to the app's handler as the tenant identifier in `WebhookMetadata`.

### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, allowing cross-tenant data attribution via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then trusts the `shopify-shop-domain` header (exposed as `request.shop`) as the tenant identity that is forwarded to the app's `WebhookHandler` via `WebhookMetadata#shop`. Because the header carrying the tenant identity is not part of the signed data, anyone holding one valid `(raw_body, hmac)` pair — e.g. a merchant on their own store who receives genuine webhooks from Shopify for their shop — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shopify-shop-domain` header, and the app will process/attribute that payload to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on that HMAC check, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to WebhookMetadata`. Because the HMAC never covers the `shopify-shop-domain` header, this equality does not hold — `request.shop` can be swapped freely as long as the body/HMAC pair itself is valid for *some* shop. The gem's own documentation confirms host apps are expected to trust `data.shop` as "The shop domain of the webhook" without any additional verification step: [5](#0-4) 

### Impact Explanation
This breaks the tenant/shop identity binding that `Registry.process` is supposed to enforce via HMAC validation: `Errors::InvalidWebhookError` is only raised for a bad body/HMAC pair, never for a mismatched shop header. Because the app's webhook handler is documented and expected to key all downstream logic (job scheduling, `SessionRepository` lookups, tenant-scoped writes, etc.) off `data.shop`, an attacker who possesses one legitimately-signed `(body, hmac)` pair for their own shop can cause the host application to attribute/process that payload under an arbitrary other shop's identity. This is a cross-tenant data-integrity issue rooted entirely in this gem's webhook verification implementation, not merely a host-application oversight, since the gem asserts the request "did indeed come from Shopify" once HMAC validation passes, but the shop identity is never covered by that guarantee.

### Likelihood Explanation
Any actor who has legitimate access to at least one shop that installed the app (a normal, unprivileged merchant) automatically receives genuinely-signed webhook deliveries for their own store — no `api_secret_key`, access token, or other secret is needed to obtain a valid `(raw_body, hmac)` pair. That pair can then be replayed to the app's public webhook endpoint with a forged `shopify-shop-domain` header. This requires no elevated privilege beyond "run an unprivileged merchant install," directly satisfying the unprivileged-internet-user bar.

### Recommendation
Include the shop, topic, and webhook id in the signed material (or otherwise cryptographically bind them to the body) before trusting them, e.g. compute/verify the HMAC over a canonical string combining `raw_body` with `shop-domain`, `topic`, and `webhook-id`, or require the host application to independently confirm that `request.shop` matches a shop for which a legitimate, currently-active app installation/session exists before dispatching to the handler. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by the host app against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
```ruby
require "shopify_api"
require "openssl"
require "base64"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shhh",
  api_version: "2024-01",
  scope: [],
  host_name: "app.example.com",
  is_private: false,
  is_embedded: true,
)

body = '{"id":1,"note":"hello"}'
# Attacker's own shop legitimately received this webhook from Shopify,
# so they legitimately know a valid (body, hmac) pair for THEIR shop.
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Replay against the app's webhook endpoint, but swap the shop-domain header
# to the victim shop -- HMAC still validates because it never covered this header.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# HMAC validation passes because HmacValidator only checks `body`, never `shop-domain`.
```

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
