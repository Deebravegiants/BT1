### Title
Cross-chain message payload triggers arbitrary runtime-call execution as an attacker-chosen account without signature verification - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet_hyper_fungible_token::on_accept` (the `IsmpModule` callback invoked by the ISMP dispatcher when a POST request from a registered remote token contract is delivered) decodes an optional `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` from the message body and dispatches `runtime_call` as a signed extrinsic. When `signature` is `None`, the origin used for dispatch is derived directly from the message's `from` field — attacker-influenced data inside the ISMP payload — with **no cryptographic proof that the holder of that account authorized the call**.

### Finding Description
On the EVM sender side, `HyperFungibleToken.send()` builds the message body as:
```solidity
bytes memory body = abi.encode(Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
``` [1](#0-0) 

`from` is set to `msg.sender`, i.e. any EOA/contract calling `send()` can set `from` to itself. `data` (which decodes to `SubstrateCalldata`) is fully attacker-controlled — `params.data` is a raw `bytes` parameter of `send()`, unauthenticated by anything beyond ordinary calling permission.

On the destination substrate chain, `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs`:
```rust
let origin = if let Some(signature) = substrate_data.signature {
    // ... verifies signature over (nonce, runtime_call) against `beneficiary`
    beneficiary.clone()
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
...
runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())
``` [2](#0-1) 

When no signature is supplied, the module still dispatches `runtime_call` as `RawOrigin::Signed(origin)`, where `origin` is deterministically derived from `message.from` (or from the EVM `msg.sender` that placed the send, via a fixed zero-padding conversion in the default `EvmToSubstrate` impl):
```rust
fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
    let mut account = [0u8; 32];
    account[12..].copy_from_slice(&addr.0);
    account.into()
}
``` [3](#0-2) 

Because this conversion is a pure deterministic function of the address bytes (not a cryptographic proof of key ownership), and because `message.from`/`message.data` are attacker-supplied at the point of calling `send()`, an attacker can:
1. Call `send()` from any EVM address they control (or name any `from` value they wish, since `from = msg.sender` on that chain — the attacker is free to call from a fresh throwaway address, or, for non-EVM sources, the `from` bytes are taken directly and copied into a 32-byte AccountId with no validation at all),
2. Embed a crafted `SubstrateCalldata{ signature: None, runtime_call: <arbitrary extrinsic> }` in `data`,
3. Have the destination pallet dispatch that arbitrary `runtime_call` as `RawOrigin::Signed(<derived_account>)`.

This is directly analogous to the pglogical CVE pattern: an out-of-band "command" payload (here, a SCALE-encoded `RuntimeCall`) carried inside a cross-chain message is executed by the receiving side's privileged worker (the ISMP `on_accept` callback, which runs with full pallet/runtime dispatch privilege) without adequate authentication of the command's origin. The only gate is `ContractToAsset::<T>::get(source, &from)`, which authenticates the *registered token contract address* on the source chain, not the individual message's `from`/`data` fields, which remain attacker-controlled per-call.

The only mitigating control present is `BaseCallFilter::contains(&runtime_call)`, which filters out globally-disallowed calls (e.g. during maintenance mode) but does **not** prevent dispatch as an arbitrary, attacker-named account for any call the runtime otherwise permits signed accounts to make.

### Impact Explanation
This allows an attacker to execute arbitrary permitted extrinsics as any account whose corresponding EVM-address-encoding or raw-32-byte encoding they choose, without ever proving control of that account's private key. Concretely:
- An attacker can dispatch a `runtime_call` "as" an account they merely picked (e.g., the EVM address `0x0000...0000` maps to AccountId `0x000...000`, or any address for which the attacker knows/guesses the 20-byte value), and that account is credited with having *authorized* the call.
- Combined with the token mint that happens unconditionally in the same `on_accept` (tokens are minted to `beneficiary` derived from `message.to` before the calldata is even parsed), an attacker can, in the same message, mint tokens to an account and then, in the same call, dispatch a runtime call using an origin of their choosing to interact with that freshly-minted balance or any other pallet reachable via a signed origin (e.g. transfers, approvals, staking actions, governance votes if the target account holds tokens/rights) — all attributed to a victim/attacker-chosen account without their consent.
- Because any state-machine's registered peer contract can trigger this path merely by having *any* user call `send()` with crafted `data`, this is reachable by an unprivileged party (any EVM caller of the registered `HyperFungibleToken` peer contract), matching the "single dispatched request" reachability criteria.

This satisfies "unauthorized app action" / partial impersonation-based fund/account manipulation under a High severity given CVSS-like reachability (network, no special privilege beyond being able to call `send()` on a registered peer contract).

### Likelihood Explanation
High. `send()` on the registered EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` peer is a public function callable by anyone; `data` is a free-form parameter with no source-chain-side validation tying it to any signature. The vulnerable code path (`signature: None` branch) is on by design — it's explicitly meant to support unsigned "convert-only" calldata execution, so triggering it requires no special conditions beyond crafting the ABI/SCALE payload.

### Recommendation
Do not permit `runtime_call` dispatch under a signed origin unless a valid signature over `(nonce, runtime_call)` from the corresponding account is verified. Remove (or gate behind an explicit, clearly-labelled unsafe feature) the `None`-signature branch that derives an origin purely from `message.from`/EVM-address conversion; at minimum, restrict that branch to a special-purpose origin (not `RawOrigin::Signed`) with a strictly reduced set of allowed calls (e.g. an `EnsureOrigin` mapped to a "cross-chain, unauthenticated" pseudo-origin that only permits things equivalent to "receive tokens," never arbitrary `RuntimeCall::dispatch`).

### Proof of Concept
1. Deploy/observe an already-registered `HyperFungibleToken` peer pair between chain A (EVM) and chain B (substrate, running `pallet_hyper_fungible_token`).
2. From any EVM account, call:
```solidity
HyperFungibleToken(tokenA).send(SendParams({
    dest: <chain B state machine>,
    to: abi.encodePacked(attackerOrVictimAccountId32),
    amount: 1, // any dust amount, mint step is incidental
    timeout: X,
    relayerFee: fee,
    data: abi.encode(SubstrateCalldata {
        signature: None,
        runtime_call: <SCALE-encoded RuntimeCall, e.g. Balances::transfer_all(dest, false)>
    })
}));
```
3. On delivery, chain B's `pallet_hyper_fungible_token::on_accept` mints the token to `beneficiary` and then, because `substrate_data.signature` is `None`, computes `origin = EvmToSubstrate::convert(H160::from(message.from))` (equal to `msg.sender` on chain A, zero-padded) and dispatches `runtime_call.dispatch(RawOrigin::Signed(origin))`.
4. If `origin` corresponds to an account with any funds/permissions on chain B (e.g., because the attacker previously funded that derived account, or because they merely need `origin` == a fixed/known/guessable account), the arbitrary `runtime_call` executes as that account without any signature from its real key holder — demonstrating unauthenticated privileged dispatch triggered entirely by an unprivileged cross-chain message sender. /// SCALE-encoded calldata for executing a runtime call on the destination substrate chain
#[derive(Debug, Clone, Encode, Decode, scale_info::TypeInfo, PartialEq, Eq)]
pub struct SubstrateCalldata {
	/// Optional SCALE-encoded [MultiSignature](sp_runtime::MultiSignature) of the beneficiary's
	/// account nonce and the encoded runtime call
	pub signature: Option<Vec<u8>>,
	/// SCALE-encoded runtime call to execute
	pub runtime_call: Vec<u8>,
}

/// Setup the runtime provides so this pallet's benchmarks can work with a bridged asset.
