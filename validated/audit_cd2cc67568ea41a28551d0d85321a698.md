### Title
Hostile mint-pre-seed against a permissionless HyperSwap graduation can force an off-curve-close LP open when the rebalance swap budget is exceeded (M-02 regime) - ([File: packages/contracts/src/Bonding.sol])

### Summary
The ALPINE-CVE-2020-12723 analog is a class of bug where a crafted, attacker-controlled input drives an internal bounded computation (Perl's recursive `S_study_chunk`) past the assumption its bound was designed for, producing an incorrect/overflowing result instead of a safe rejection. In alt.fun the structurally equivalent computation is `Bonding._noFeeSwapInput`, the closed-form "rebalance swap size" used by `_seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance` to defuse a front-run HyperSwap V2 mint pre-seed before `finalizeGraduation` deposits the curve-raised liquidity. The size is capped at a fixed per-side budget (`_swapBudget`, 99% of `tokensForLP` or of the LT inventory). An attacker can craft the pre-seed ratio (front-running `Bonding.finalizeGraduation`) so the mathematically required rebalance input exceeds that fixed budget cap; the swap is then clamped, the post-swap pool is left materially off the curve-close ratio, and `_routerDepositAndDispose` deposits the LP at that skewed ratio anyway rather than reverting.

### Finding Description
Graduation is permissionless and two-phase: `Bonding._enterGraduating` computes and caches `tokensForLP` / `ltFromPair` at the curve-close ratio, and any address can later call `Bonding.finalizeGraduation` to create/seed the HyperSwap V2 pair [1](#0-0) . Because `factory.createPair` and `pair.mint` are permissionless on a vanilla V2 pair, an attacker can front-run phase 2 by creating the pair and minting LP at a self-chosen, hostile `(TOKEN, LT)` ratio before `Bonding` ever deposits [2](#0-1) .

To defend against this, `_seedRebalancing` computes a directional rebalance swap via `_pairRebalance`, whose input size is `_noFeeSwapInput(reserveIn, reserveOut, targetN, targetD, maxSwap)` — a closed-form `s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn`, clamped to `maxSwap` [3](#0-2) . `maxSwap` is deliberately bounded to `_swapBudget(...)`, i.e. 99% of the available TOKEN or LT-side inventory [4](#0-3) . The bound exists solely to guarantee `_routerDepositAndDispose` always has a non-zero amount on both sides to deposit (brick resistance), not to guarantee the rebalance actually reaches the target ratio [5](#0-4) .

When the attacker crafts a sufficiently lopsided pre-seed (e.g. TOKEN side at 1% of `tokensForLP`, LT side at 200× `ltFromPair`), the mathematically required `s` to reach the cached curve-close ratio exceeds the 99%-of-inventory cap; `_pairRebalance` clamps `s` to `maxSwap` and the swap only partially corrects the ratio. `_routerDepositAndDispose` then deposits the remaining inventory at the post-swap (still off-ratio) reserves via `router.addLiquidity(min0=1, min1=1, ...)`, which does not enforce the curve-close price — it only prevents a `min()==0` degenerate revert [6](#0-5) . `finalizeGraduation` completes successfully, and the pool opens materially away from the curve-close price. This is the codebase's own acknowledged "M-02" regime, confirmed by `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, which asserts the pool ends up at ≥1.2× the fair price after finalize [7](#0-6) .

This mirrors the Perl CVE's bug class precisely: a fixed, hard bound (recursion budget in Perl / swap budget in `_noFeeSwapInput`) that is sized for the "normal" case is defeated by a crafted extreme input, and instead of safely rejecting the abnormal case, the code proceeds with an incorrect/degraded result (buffer overflow in Perl / off-curve LP price here) because "must never revert" (brick resistance) is prioritized above correctness.

### Impact Explanation
The rules explicitly list "an LP seeded away from the curve close price" as an accepted impact category. Every LP holder (the locked protocol LP via `LPLock`, which represents the entire trading community's post-graduation exit liquidity) is permanently seeded at a mispriced ratio, since `LPLock.recordLock` finalizes a one-shot lock that `finalizeGraduation` cannot skip or retroactively correct [8](#0-7) . Post-graduation traders using `Zap.buy`/`Zap.sell` (or direct HyperSwap swaps) transact against this skewed price until arbitrage closes the gap — which, per the protocol's own accepted-residual test, can be materially more than the "≈50bps" gap the design otherwise targets for ordinary hostile pre-seeds [9](#0-8) ; the M-02 regime is explicitly called out as a case where the pool "opens materially off curve-close," well beyond that ordinary bound.

### Likelihood Explanation
Reaching `finalizeGraduation` in the vulnerable window requires only: (1) observing a `TokenGraduating` event (phase 1 fires inline on a normal, unprivileged buy through `Zap.buy`/`Bonding.buy`), (2) front-running with `factory.createPair` + `transfer` + `pair.mint` at an extreme ratio — all callable by any unprivileged wallet against the permissionless V2 factory/pair — and (3) calling the permissionless `finalizeGraduation` (or waiting for the keeper to call it, since the keeper cannot distinguish a malicious pre-seed from a benign one and must call regardless to avoid bricking the token). No privileged role, upgrade, or off-chain compromise is needed. The main cost to the attacker is funding the oversized side of the pre-seed, and the protocol's own tests show this attack is economically "not profitable" for the attacker in isolation — but the finding's impact (mispriced LP, degraded exit price for the wider trading community) does not depend on attacker profitability, only on execution feasibility, which the shipped tests confirm is fully executable.

### Recommendation
Scale the rebalance swap budget (or the direct-mint fallback threshold `DIRECT_MINT_PRESEED_BPS`) to the actual pre-seed skew rather than a fixed percentage of `tokensForLP`/LT inventory, so that any pre-seed shape whose required rebalance exceeds the fixed budget is routed into a stronger corrective mechanism (e.g., a larger multi-step budget derived from the graduation's `tokensForLP`/`ltFromPair` magnitude, or burn/sweep of a larger disposed remainder) rather than depositing at a still-skewed ratio. At minimum, bound the acceptable post-swap price deviation and, when it cannot be met within budget, prefer routing the deposit through the direct-mint fallback (which the code already uses for the dust case) instead of `_routerDepositAndDispose` at an unreached target ratio, since the direct-mint fallback demonstrably keeps the attacker's captured share bounded and vanishing.

### Proof of Concept
The protocol's own regression suite reproduces this exact scenario: [10](#0-9) 

1. Launch and drive a token to `Graduating` via a normal unprivileged buy (`_enterGraduating`), caching `tokensForLP` / `ltFromPair`.
2. As `griefer` (any unprivileged wallet), front-run by creating the HyperSwap pair and minting LP at `reserveToken = tokensForLP / 100`, `reserveLt = ltFromPair * 200` — a ratio whose required corrective swap (per `_noFeeSwapInputUncapped`) exceeds the `_swapBudget` 99%-of-`tokensForLP` cap.
3. Call `bonding.finalizeGraduation(tokenAddr)` — it succeeds (no brick) per `_pairRebalance`/`_routerDepositAndDispose`'s design.
4. Assert the resulting pool price is ≥1.2× the fair curve-close price (`ltFromPair/tokensForLP`) — confirming the LP is permanently seeded away from the curve close price for all subsequent traders and LP holders.

```text
    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
```

```text
    /// @dev Smallest swap input that drives the pool's reserve ratio
    ///      `(reserveIn + s) / (reserveOut - out)` to `targetN/targetD`
    ///      under the no-fee constant-product model:
    ///        `(reserveIn + s)² = reserveIn * reserveOut * targetN/targetD`
    ///      ⇒ `s = sqrt(reserveIn * reserveOut * targetN/targetD) - reserveIn`,
    ///      capped at `maxSwap`. The actual swap is fee-charging (the pair's
    ///      live fee), so the post-swap ratio drifts from the target by the
    ///      fee; the balanced-subset deposit absorbs the residual without
    ///      donating.
    ///
    ///      `Math.mulDiv` keeps the intermediate product
    ///      `reserveIn * reserveOut * targetN` inside its 512-bit working
    ///      space, but the final result `... / targetD` must still fit in
    ///      uint256. Call sites must keep that invariant — in practice
    ///      both the V2 uint112 reserve cap and the bound that
    ///      `tokensForLP` ≤ `LP_RESERVE` and `ltFromPair` ≤ raised LT
    ///      are well inside the safe envelope. Constructed adversarial
    ///      inputs that violate this would `revert` rather than silently
    ///      truncate, which is the correct failure mode.
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```text
    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```
