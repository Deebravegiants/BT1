### Title
Unchecked-length copy into fixed-size buffer in `HyperFungibleToken::on_accept` causes a runtime panic on relayed messages - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::<T>::on_accept` (the `IsmpModule` handler for `HyperFungibleToken`, reached through `pallet-ismp`'s `handle_unsigned`/dispatch path when a `PostRequest` targets this module) decodes an ABI-encoded `Message` whose `from` field is an attacker-controlled, arbitrary-length `bytes` value set by the sender contract on the source chain. When the request carries calldata with no signature and the source state machine is not EVM, the code copies `from_bytes` directly into a fixed `[u8; 32]` buffer with `copy_from_slice` without first checking that `from_bytes.len() == 32`. A parallel unchecked-length underflow exists on the EVM branch (`from_bytes.len() - 20`). Both are classic "copy attacker length into fixed buffer without validating the length first" bugs — the exact bug class in CVE-2015-9542 (`add_password`/`memcpy` without checking input length against the destination buffer).

### Finding Description [1](#0-0) 

```rust
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(
            &from_bytes[from_bytes.len() - 20..],
        ))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
```

`message` is decoded straight from the ISMP request body via `Message::abi_decode(&body)` at [2](#0-1) , so `message.from` is fully attacker-controlled: any length the source-chain sender contract chooses to encode. This value only reaches the vulnerable branch when the optional `SubstrateCalldata` carries no `signature` (an unsigned/unauthenticated path is explicitly supported per lines 124-187), so no cryptographic check constrains the length of `message.from` before it is used.

Two unguarded operations follow:
- Non-EVM source: `account.copy_from_slice(from_bytes)` into `[0u8; 32]` panics immediately if `from_bytes.len() != 32` (both under- and over-length inputs trap, since `copy_from_slice` requires exact length equality).
- EVM source: `from_bytes.len() - 20` underflows (panicking on overflow-checked builds, or wrapping to a huge `usize` on release builds without overflow checks, producing an out-of-bounds slice index panic) whenever `from_bytes.len() < 20`.

This is the same root cause as the reference CVE: an externally-supplied length is never validated against the fixed destination buffer size before performing a raw memory copy. The codebase's own recent hardening confirms this exact pattern was previously the source of a production incident and fix elsewhere: `modules/utils/serde/src/lib.rs`'s `as_utf8_string::deserialize` and `modules/ismp/core/src/host.rs`'s `StateMachine::from_str` were both patched after `copy_from_slice` panics on unchecked-length untrusted input crashed a node/reachable-from-`BandwidthManager.purchase` path, per the code comments: [3](#0-2) [4](#0-3) 

The `HyperFungibleToken` on-accept path, by contrast, still performs the unchecked copy. In the same function, the "to" recipient side of the same message was correctly length-checked (`to_bytes.len() == 32`/`== 20` before copying), showing the intended validation pattern that was simply omitted for `from`: [5](#0-4) 

### Impact Explanation
`on_accept` executes inside the ISMP message-dispatch path invoked from `handle_unsigned`/relayed-message delivery — any relayer that delivers a `PostRequest` from a registered source contract for this module reaches this code with attacker-influenced input, since the source contract fully controls the `Message.from` encoding. A panic here aborts the extrinsic/block-execution context processing that request, which:
- Prevents delivery of that (and potentially subsequent) cross-chain messages through this route (a message-delivery DoS / "route unable to deliver messages"), and
- In runtimes without safeguards around dispatchable panics, can disrupt block production or the executing worker, mirroring the "crash / possible undefined behavior" impact class of the reference CVE, though here it manifests as a Rust panic/trap rather than memory corruption.

### Likelihood Explanation
High: the only precondition is that the destination `HyperFungibleToken` module is registered for a source contract (`ContractToAsset` mapping) and that the ISMP request carries calldata (`message.data` non-empty) with `substrate_data.signature == None` — a codepath the contract explicitly supports as unsigned/unauthenticated execution. The attacker only needs to control the source-chain contract's encoding of the `from` field (arbitrary length) to trigger the panic; no privileged role, governance, or validator collusion is required.

### Recommendation
Validate `from_bytes.len()` before use, mirroring the existing `to_bytes` handling in the same function:
- For the EVM branch, require `from_bytes.len() >= 20` before slicing, returning an `HftError` variant otherwise.
- For the non-EVM branch, require `from_bytes.len() == 32` before `copy_from_slice`, returning an `HftError` variant otherwise.

### Proof of Concept
1. Register a source EVM (or non-EVM) contract for `HyperFungibleToken` via `ContractToAsset`.
2. From that source contract, dispatch a `PostRequest` whose ABI-encoded body decodes to a `Message` with:
   - `data` = ABI/SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <any valid call> }`
   - `from` = a byte string whose length is neither 20 nor 32 (e.g., 5 bytes, or 0 bytes for the EVM branch to force underflow).
3. Relay this request to the destination chain so `pallet-ismp`'s dispatch invokes `HyperFungibleToken::on_accept`.
4. Execution reaches `account.copy_from_slice(from_bytes)` (or the EVM `from_bytes.len() - 20` subtraction) and panics, aborting message processing for that request.
