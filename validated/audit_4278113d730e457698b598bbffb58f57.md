## Finding

### Title
Webhook Shop/Topic/Metadata Spoofing via HMAC That Only Covers the Raw Body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the **raw body**, then trusts the unsigned `x-shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) headers as the tenant identity handed to the app's handler. Because those headers are never part of the signed data, the binding `signed_bytes == bytes_the_app_acts_on` does not hold for the `shop` field.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are never included in `to_signable_string`: [2](#0-1) 

`Registry.process` verifies only that the HMAC matches the body, then immediately uses `request.shop` and `request.topic` as trusted tenant metadata passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms it only compares `verifiable_query.hmac` against a signature computed over `to_signable_string`, i.e. the body: [4](#0-3) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any shop that has installed the app can legitimately trigger a webhook to the same endpoint, obtaining a body/HMAC pair that is valid for that body under the app's secret. An attacker who controls one installed shop can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds — it never inspected the header — so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's original payload>, ...)`. The equality the code implicitly assumes, `header_shop == hmac_authenticated_shop`, is false; the only authenticated fact is "this body was produced by some shop that has this app installed," not "this body belongs to the shop named in this header."

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `#topic`) to route persistence/business logic per tenant (a standard, documented usage pattern, see `docs/usage/webhooks.md` handler examples) can be made to attribute one merchant's webhook payload to a different, arbitrary merchant record. This is a cross-tenant data-integrity/confusion issue: attacker-controlled data (from their own shop) is processed under another tenant's identity, potentially overwriting or injecting data into a victim shop's records that the host app maintains keyed by `shop`.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on their own store (i.e., an ordinary unprivileged merchant/user of a public app) and be able to POST HTTP requests to the app's public webhook endpoint with attacker-chosen headers — both of which are available to any internet user interacting with a multi-tenant Shopify app. No access token, `client_secret`, or `api_secret_key` is required.

### Recommendation
Extend `VerifiableQuery`/webhook signing so that the identity fields the app relies on (`shop`, `topic`) are cryptographically bound to the signature, or — since Shopify's real HMAC scheme only signs the body — require host applications to independently authenticate `request.shop` against their own installed-shop registry before trusting `WebhookMetadata#shop`, and document this requirement prominently next to `HmacValidator.validate`/`Registry.process` so integrators do not treat header-provided shop/topic as authenticated.

### Proof of Concept
1. Install the app (as an unprivileged merchant) on `attacker-shop.myshopify.com`; trigger any webhook event so Shopify sends a legitimately HMAC-signed request `{ raw_body: B, headers: { hmac-sha256: H, shop-domain: "attacker-shop.myshopify.com", topic: T } }` to the app's public webhook endpoint.
2. Capture `(B, H)` (attacker owns this shop, so no interception needed).
3. Replay a new POST to the same public webhook endpoint with `raw_body: B`, `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: "victim-shop.myshopify.com"`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`; `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), topic: T, ...)`, causing the host app to process attacker-controlled data under the victim shop's tenant identity.
