The report is a real, verifiable analog. The webhook HMAC in this gem's `ShopifyAPI::Webhooks::Request` signs the raw body but not the `shop-domain` header, and that unverified header is what the handler receives and trusted as the tenant identity.

### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically verifies the body but never the `shopify-shop-domain`/`x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` nonetheless takes `request.shop` straight from that unauthenticated header and hands it to the app's webhook handler as the tenant identity, with no independent check that the HMAC-covered body actually originated for that shop.

### Finding Description
`Request#hmac` reads `shopify-hmac-sha256`, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
`Request#shop` is read directly from the `shop-domain` header with no cryptographic binding to the body/signature: [2](#0-1) 
`Registry.process` validates only the HMAC over the body, then forwards `request.shop` (the unverified header) into `WebhookMetadata` that is delivered to the developer's handler as the trusted tenant identifier: [3](#0-2) 
The library's own documentation instructs developers to treat `data.shop` as "The shop domain of the webhook" and use it directly (e.g. `shop_domain: data.shop`) for downstream job dispatch, without any note that this field is unauthenticated:


The identity binding that should hold is: `shop_the_handler_trusts == shop_cryptographically_bound_in_the_HMAC_payload`. In this gem that equality does not hold — the HMAC only proves `secret == HMAC(raw_body)`, not `secret == HMAC(raw_body || shop_domain)`. Since the same `client_secret`/api_secret_key is shared by the app across every merchant shop that installs it, any party capable of obtaining one valid `(raw_body, hmac)` pair from Shopify for any shop (e.g., by installing the app on their own store and capturing a webhook delivery) can present that same, still-valid signature to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will pass because it only checks the body, and the handler will process the payload as if it came from the spoofed shop.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled or replayed body/signature pair (valid for the attacker's own shop) can be delivered to the app claiming to be a different, victim shop, since the shop identity is not bound into the signature. Depending on how the host app uses `data.shop` (e.g. to look up which merchant's session/access token to act on, or to attribute/store data), this enables cross-tenant data confusion or action-on-behalf-of-wrong-shop, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to install the target app on any shop (including one the attacker controls) to capture one legitimate `(raw_body, shopify-hmac-sha256)` pair for a topic of interest, since the app's `api_secret_key` is shared across all shops using the app, not per-shop. No access token, admin credential, or leaked secret is required — only observation of the gem's own signature scheme, which binds the payload but not the sender's identity header.

### Recommendation
Bind the shop identity into the authenticated payload rather than trusting the header value alone. Concretely, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate `shop-domain` (and ideally `webhook-id`/`topic`) into what's verified, or `Registry.process` should independently confirm the `shop` header value against a value already associated with that specific `webhook_id`/session before invoking the handler with it. Document explicitly that `WebhookMetadata#shop` is not itself covered by the HMAC signature.

### Proof of Concept
1. Install the target app on an attacker-owned/free development shop; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate `raw_body` and its `shopify-hmac-sha256` value signed with the app's shared `api_secret_key`.
2. Replay an HTTP POST to the app's webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and a fresh/duplicate `X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body`: [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-controlled data as belonging to `victim-shop.myshopify.com`.
