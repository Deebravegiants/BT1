### Title
Webhook HMAC only signs the request body, not the `X-Shopify-Shop-Domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body, so the HMAC signature Shopify sends never covers the `shop-domain` (or `topic`/`webhook-id`/`api-version`) header. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when building the `WebhookMetadata` handed to the app's handler, so the shop identity used by the host application is an unauthenticated field even though the request "passed" HMAC verification.

### Finding Description
`HmacValidator.validate` computes and compares the signature against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be the raw body only: [2](#0-1) 

All identity/routing headers (`shop`, `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers with no cryptographic binding to the body that was actually HMAC-signed: [3](#0-2) 

`Registry.process` then validates only the body's HMAC and forwards `request.shop` (the unauthenticated header) directly into the metadata passed to the app's webhook handler: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. In reality: `shop covered by HMAC = {}` (nothing) while `shop acted upon by handler = request.shop` (attacker-controlled header). Because the signature never binds the shop domain to the payload, any request with a body+HMAC pair that was legitimately generated for shop A can be replayed with the `X-Shopify-Shop-Domain` header changed to shop B, and `HmacValidator.validate` still returns `true` since it only recomputes the signature over `@raw_body`.

An attacker only needs to obtain one valid `(raw_body, hmac)` pair generated by Shopify for any shop they control (e.g. their own free/dev store, by triggering any webhook topic and capturing the delivery), then replay that exact body and HMAC header to the target app's webhook endpoint while substituting `X-Shopify-Shop-Domain` for the victim's store. No `api_secret_key`, access token, or privileged credential is needed — this is a pure unprivileged-internet-user request that this gem's own webhook-processing code accepts as valid.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as the gem's own `Registry.process` encourages) to decide which tenant's records to update, which merchant's stored access token to use for a follow-up API call, or which tenant's local database rows to write/delete, an attacker can inject arbitrary webhook payloads (subject to needing a valid signed body/topic combination they generated for their own shop) attributed to a victim shop. This is a cross-tenant identity-binding break: the value trusted for tenant routing (`shop` header) is never covered by the credential-derived proof (`HMAC` over body) that the library uses to authenticate the request.

### Likelihood Explanation
Likelihood is high for any app relying on `ShopifyAPI::Webhooks::Registry.process` and trusting `WebhookMetadata#shop`/`#topic` for anything beyond “this raw body was HMAC-signed by someone possessing the shared secret.” The attacker needs no special access — only the ability to receive one legitimate webhook to any shop they control and to send an HTTP POST to the target app's public webhook endpoint.

### Recommendation
Extend `to_signable_string` (or add a separate binding check in `Registry.process`) so the shop domain, topic, webhook id, and api version headers are cryptographically bound to the verified payload — for example, by requiring the host app to independently verify `shop` against its own tenant registry before trusting `WebhookMetadata`, or by documenting explicitly that `HmacValidator.validate` does not authenticate any header, including `shop-domain`, and that consumers must not use `request.shop`/`WebhookMetadata#shop` as a trusted tenant identifier without additional verification (e.g., matching against a known registered shop list) before performing any tenant-scoped write or token lookup.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) pointing at a URL they control, or simply captures a delivery via a proxy.
2. Attacker obtains a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair for that delivery — this HMAC is valid because it's computed by Shopify using the shared `client_secret` over the body only, per: [5](#0-4) 
3. Attacker sends this exact `raw_body` + `X-Shopify-Hmac-Sha256` header to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches, so `Errors::InvalidWebhookError` is not raised: [6](#0-5) 
5. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop — any tenant-scoped action keyed off `data.shop` is now cross-tenant poisoned.
