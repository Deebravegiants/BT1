## Analog Found

### Title
Users cannot reclaim escrowed relayer fees via request timeouts while the host is frozen - ([File: evm/src/core/HandlerV2.sol])

### Summary
The Covalent bug blocks an unrelated user's `unstake()` because `_unstake` unconditionally reverts on `v.frozen` regardless of who is calling or why the validator was frozen. Hyperbridge's `EvmHost`/`HandlerV2` freeze mechanism has the same structural flaw: `FrozenStatus.Incoming`/`All` gates *both* new incoming message delivery *and* the permissionless timeout-processing path that returns a user's already-escrowed relayer fee, even though the two operations have entirely different risk profiles and the affected user has no relationship to the reason the host was frozen.

### Finding Description
`EvmHost.dispatch()` escrows the caller's relayer fee at request time and stores it in `_requestCommitments[commitment]` as `FeeMetadata`, refundable to `post.payer` on timeout: [1](#0-0) 

The only path to reclaim that fee is `HandlerV2.handlePostRequestTimeouts` (and the GET-request analog `handleGetRequestTimeouts`), which any unprivileged caller can invoke once the timeout proof is available: [2](#0-1) 

Both functions are gated by the `notFrozen(host)` modifier, which reverts with `HostFrozen()` whenever the host's `FrozenStatus` is `Incoming` or `All`: [3](#0-2) 

`setFrozenState` can be called by the admin or handler for any reason (e.g. a fraud proof against one specific consensus client, or an incident affecting one destination chain), but it flips a single host-wide flag with no scoping to the request, application, or state machine that is actually implicated: [4](#0-3) 

The result: exactly like the Covalent case where `_unstake` should only have blocked the frozen validator's own actions, `notFrozen` should not block a user's *recovery* of already-escrowed funds via `dispatchTimeOut`, which is fundamentally a "return money already collected" operation, not a "trust new incoming state" operation. Because `dispatchTimeOut` (the function that actually performs the refund) is itself unguarded by any frozen check, only the two `HandlerV2` entry points are — meaning the refund logic was clearly intended to be always available, but the permissionless message that triggers it was accidentally coupled to the same freeze flag used for message-authenticity concerns: [5](#0-4) 

### Impact Explanation
Any user whose POST/GET request happens to be pending across a freeze window loses access to their escrowed relayer fee for the entire duration of the freeze, with no way to bypass this regardless of how unrelated their specific request is to the freeze's cause. If the freeze persists (e.g. governance is slow, or the freeze is `All`/`Incoming` for an extended incident response), user funds already collected by the protocol are locked with no user-triggered escape hatch — a permanent-freezing-of-funds risk scoped far more broadly than necessary, exactly mirroring the "not the user's fault" characteristic of the original report.

### Likelihood Explanation
`setFrozenState` is a normal, expected operational lever (the docs describe it as the mechanism for "security and emergency situations"), so freezes are a realistic, recurring event, not a rare edge case. Every user with a pending, fee-bearing, timed-out request during any such freeze is affected, and the path (`handlePostRequestTimeouts`/`handleGetRequestTimeouts`) is fully permissionless and reachable by anyone attempting to claim their own refund.

### Recommendation
Scope the `notFrozen` check on `handlePostRequestTimeouts`/`handleGetRequestTimeouts` away from fund-recovery flows, e.g. only enforce `notFrozen` for `handlePostRequests`/`handleGetResponses` (new external state being trusted), and let timeout processing (which only unwinds funds already escrowed by the protocol) proceed independent of `FrozenStatus`, similar to how `dispatchTimeOut` itself is not frozen-gated. Alternatively, scope freezes to the specific state machine/consensus client implicated rather than a single global flag covering unrelated pending requests.

### Proof of Concept
1. Alice calls `host.dispatch(DispatchPost{fee: X, payer: Alice, timeout: T, ...})`; her fee `X` is pulled into escrow (`evm/src/core/EvmHost.sol:921-948`).
2. Before her request is delivered, the admin freezes the host with `FrozenStatus.Incoming` (or `All`) for a reason entirely unrelated to Alice's request — e.g. a fraud investigation on a different destination chain's consensus client (`evm/src/core/EvmHost.sol:746-753`).
3. Alice's request times out (`T` elapses). She (or anyone) tries to submit the timeout proof via `HandlerV2.handlePostRequestTimeouts` to trigger her refund.
4. The call reverts with `HostFrozen()` due to the `notFrozen(host)` modifier (`evm/src/core/HandlerV2.sol:106-112`, `254-286`), even though `dispatchTimeOut` itself — the function that actually returns her fee — has no frozen check at all (`evm/src/core/EvmHost.sol:885-906`).
5. Alice's escrowed fee remains locked until governance manually lifts the freeze, with no way for her to reclaim funds tied to a situation she had no part in.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
