## Finding

### Title
Webhook HMAC signature does not cover `shop`, `topic`, or `webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers — none of which are covered by that HMAC. An unprivileged internet user who has received one legitimately-signed webhook (e.g. for their own installed app/shop) can replay the same body+HMAC pair while forging the `shop-domain`/`topic`/`webhook-id` headers, causing the app to process attacker-controlled metadata as if it originated from a different, arbitrary tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controlled headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC (which, per above, only certifies the body bytes) and then trusts the header-derived `shop`/`topic`/`webhook_id` to select the handler and build the metadata object passed to it: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `compute_signature(verifiable_query.to_signable_string, secret) == received_signature`, i.e. it only binds the body — never the headers used for routing/attribution: [4](#0-3) 

**The broken equality:** the gem treats `HMAC-valid(body)` as equivalent to `HMAC-valid(shop, topic, webhook_id, body)`, but only the former is actually checked. This is the same bug class as the report's `decreaseDebtShare`: the check ("interest accrued" / "HMAC verified") does not cover the field actually acted upon ("stale debt/share ratio" / "shop, topic, webhook_id headers").

### Impact Explanation
An attacker who has legitimately received even one webhook from Shopify (e.g., for their own shop with the target app installed) obtains a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. Because the signature covers only the body, the attacker can resend that exact body+signature to the app's webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with values referencing a completely different tenant/topic (e.g. spoofing an `app/uninstalled` or `orders/updated` event for shop B using a body that was actually signed for shop A). `Registry.process` will accept it as valid (HMAC check passes) and hand it to the handler tagged with the forged `shop`, causing the host application to act on falsified per-tenant data — a cross-tenant data integrity/confusion issue. No `api_secret_key`, access token, or privileged account is required beyond ordinary use of one's own installed app to harvest a valid signed payload.

### Likelihood Explanation
Moderate-to-high: any developer/attacker running the app on their own shop can capture a real webhook (body + `hmac-sha256` header) via normal traffic inspection, then replay it with modified headers to the same endpoint. No secret material needs to be broken or leaked — only a genuine signed sample is needed, which the attacker's own shop naturally receives.

### Recommendation
Bind the routing/attribution fields into the signed material, or independently verify them against trusted state:
- Include `shop`, `topic`, and `webhook_id` (or at minimum `shop` and `topic`) in the HMAC signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, matching how `AuthQuery#to_signable_string` binds `shop` into its HMAC (`lib/shopify_api/auth/oauth/auth_query.rb`).
- Alternatively/additionally, cross-check the header-derived `shop` against the registered/expected shop for the session before dispatching to the handler.

### Proof of Concept
1. App receives a legitimate Shopify webhook for `attacker-shop.myshopify.com`, topic `orders/updated`, with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <arbitrary>
   Body: B
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only recomputes HMAC over `B` (see `to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-43`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the `app/uninstalled` handler with `shop: "victim-shop.myshopify.com"`, even though `B` was never signed for that shop/topic combination.

          received_signature = verifiable_query.hmac
