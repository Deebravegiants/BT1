Found a direct analog. The Tron variant of `IntentGatewayV2.placeOrder` regressed a fix that exists in the canonical EVM contract: it credits escrow based on the *nominal* input amount rather than the token amount actually received by the contract.

### Title
Escrow crediting from nominal amount instead of actual received balance allows draining the shared escrow pool via fee-on-transfer/deflationary ERC20 tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron deployment of `IntentGatewayV2`, `placeOrder()`'s non-predispatch escrow path performs `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the full nominal (fee-reduced) amount to `_orders[commitment][token]` without ever checking how much the contract actually received. [1](#0-0) 

### Finding Description
The canonical EVM `IntentGatewayV2.placeOrder()` explicitly measures the actual token balance delta before crediting escrow, precisely to guard against this class of bug: [2](#0-1) 

and even documents the rationale in-line: "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds." [3](#0-2) 

The Tron contract's non-predispatch branch drops this balance-diff check entirely and credits `reducedInputs[i].amount` — a value derived purely from `order.inputs[i].amount` as supplied by the caller — regardless of what `safeTransferFrom` actually delivered to the contract: [4](#0-3) 

Since `_orders[commitment][token]` is per-order bookkeeping against a single shared contract-wide token balance (all orders for the same token draw from the one `IERC20(token).balanceOf(address(this))` pool), crediting more than was actually received inflates total claims against that pool beyond what the contract holds. This is functionally identical to the reported class: trusting a nominal transfer amount instead of verifying actual tokens received, which lets one user's under-delivered transfer be "topped up" out of the pooled balance funded by other users' orders — i.e., other users' escrowed funds can be drained when this attacker's order is later redeemed or cancelled via `withdraw()`, which pays out of the same shared per-token balance: [5](#0-4) 

### Impact Explanation
Any unprivileged user can call `placeOrder()` with an ERC20 input token that delivers less than the requested `amount` on `transferFrom` (fee-on-transfer tokens, deflationary/rebasing tokens, or any token whose effective transferred amount is less than the face value). The contract credits the full nominal amount to escrow, creating a claim against the shared token balance that exceeds what was actually deposited. When later filled/redeemed, `withdraw()` pays this inflated escrow out of the shared pool, which is backed by other legitimate orders' deposits in the same token, resulting in concrete theft/permanent freezing of other users' escrowed funds — matching the Impact: 5 severity of the original report.

### Likelihood Explanation
This is trivially reachable in a single transaction by any unprivileged caller via the standard `placeOrder()` entry point, requiring only picking (or being tricked/routed into) a token with fee-on-transfer or deflationary semantics for one of the order's inputs — no privileged role, governance, or special timing is needed. Likelihood is high.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom` in the non-predispatch branch (and reconcile the predispatch branch's dust accounting against the dispatcher's actual measured balance too), then compute `reducedInputs`/escrow credit from the *actually received* amount rather than the caller-supplied nominal `order.inputs[i].amount`.

### Proof of Concept
1. Deploy/use an ERC20 token with a transfer fee (e.g., 5% fee-on-transfer, common on Tron for USDT-forks/custom tokens) as an order input token.
2. Attacker calls `placeOrder()` with `order.inputs[i].amount = 1000` of this token, holding an approval of 1000 to the gateway.
3. `safeTransferFrom(msg.sender, address(this), 1000)` executes, but due to the 5% fee the contract only actually receives 950 tokens.
4. The contract nonetheless executes `_orders[commitment][token] += reducedInputs[i].amount` using the full nominal (fee-reduced-by-protocol-fee-only) value, e.g. ~1000 (minus protocol fee), not the 950 actually held.
5. Attacker (or any solver acting on their behalf) fills/cancels this order and calls the withdrawal path, which pays out the inflated escrowed amount from the contract's shared token balance — funded by other legitimate orders — draining 50 tokens' worth of value that belongs to other users' escrowed positions in that token.
