Confirmed root cause. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — the HMAC signature never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers, yet `Registry.process` passes `request.shop`, `request.topic`, etc. straight through to the handler as trusted tenant identity.This confirms the full path: the docs explicitly instruct developers to trust `data.shop` as the tenant identity key (`docs/usage/webhooks.md:26`: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), while the actual code (`lib/shopify_api/webhooks/request.rb:36-38`) only signs `@raw_body`, never the `shop-domain` header.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and forwarded to the host app's handler as trusted values. An unprivileged internet user who possesses **any** single validly-signed webhook payload (e.g., from their own installed shop, or any payload captured on the wire) can replay it to the app's webhook endpoint with an arbitrary `shop-domain` header while keeping the original body and HMAC unchanged. The signature still validates, but the (shop, body) pairing has been broken.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to build the signed string and compares it against the provided HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`). For webhooks, `Request#to_signable_string` is:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from HTTP headers with no cryptographic binding to the body or to each other:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates only the HMAC and then unconditionally trusts `request.shop` as the tenant key handed to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler treats as authoritative for (shop, topic, body)`

In this implementation that equality breaks down to:
`HMAC-verified bytes == raw_body only`, while the handler's tenant key `WebhookMetadata.shop` comes from `shop-domain`, a byte range **outside** what was verified.

This mirrors the reported bug class exactly: a field ("acted on" — here, the tenant/shop identity used by the app to store/attribute the webhook) that is not covered by the authentication mechanism ("HMAC"), letting an attacker who controls that field cross a trust boundary — cross-tenant confusion instead of the pool-factory's frozen funds, but the same "verify one thing, trust a different, unverified thing" defect.

### Impact Explanation
Any app using this gem's documented pattern (`docs/usage/webhooks.md:26`, `perform_later(shop_domain: data.shop, ...)`) to key persistence/business logic off `data.shop` is exposed to cross-tenant data corruption: an attacker who has captured or legitimately received one valid `(body, hmac)` pair (e.g., via their own shop's install, which is unprivileged/self-service) can resend it with a forged `shop-domain` header pointing at any victim shop. Depending on the topic the app subscribes to (`app/uninstalled`, `shop/redact`, `customers/data_request`, `orders/create`, etc.), this enables writing/deleting data attributed to a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
The attacker needs only one legitimately-signed webhook body (trivial to obtain by self-installing the target app on a shop they control, which is standard, unprivileged Shopify app installation) and network access to the app's public webhook endpoint. No secret, token, or privileged credential is required — only observation of the gem's own documented header-parsing/verification behavior.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker.myshopify.com` and triggers a webhook, e.g. `app/uninstalled`, capturing the raw POST: headers (including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: app/uninstalled`) and `raw_body: B`.
2. Attacker resends the exact same request to the app's webhook endpoint, only replacing the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`, keeping `B` and `H` untouched.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "app/uninstalled", body: B, ...)` and executes app-uninstall/data-deletion logic for `victim.myshopify.com`, even though nothing about the request was ever authenticated for that shop.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, e.g. include `shop-domain` in `to_signable_string` if Shopify's signing scheme supports header-inclusive verification, or independently verify the `shop-domain` header against a shop known to be associated with the registered webhook (e.g., cross-check against the app's own session/webhook_id records rather than trusting the header verbatim). At minimum, document that `data.shop` from `WebhookMetadata` is not part of the authenticated payload and must not be used as a sole tenant key without additional server-side verification (e.g., confirming the `webhook_id` was actually registered for that shop).
