### Title
Unauthenticated `InitializeBuffer` allows front-running of program-deployment buffer accounts, permanently locking out the legitimate deployer - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `bpf_loader_upgradeable` program's `InitializeBuffer` instruction sets the buffer account's `authority_address` to whatever pubkey is supplied as instruction account index 1, without requiring that account to be a signer, and without requiring the buffer account itself to be a signer. This is the exact bug class described in the external report: an initialization entrypoint with no access control on who may call it and with which parameters, enabling front-running of the deployment sequence.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` by only checking that the buffer account is currently `Uninitialized`, then unconditionally writing the caller-supplied authority key into the buffer state: [1](#0-0) 

Note the contrast with the `Write` instruction handler immediately below it, which does require the authority account to sign (`is_instruction_account_signer(1)`): [2](#0-1) 

`InitializeBuffer` has no equivalent signer check on either the buffer account (index 0) or the proposed authority (index 1). In the standard `solana program deploy` workflow, the buffer account is created in one transaction (`SystemInstruction::CreateAccount`, owned by `bpf_loader_upgradeable`, state `Uninitialized`) and then initialized with `InitializeBuffer` in a separate transaction. Because the buffer pubkey becomes public the moment the `CreateAccount` transaction is observed (in flight, in a block, or via RPC), and `InitializeBuffer` requires no signature from the buffer or the intended authority, any third party can race to submit their own `InitializeBuffer` instruction naming themselves as `authority_address` before the legitimate deployer's `InitializeBuffer` transaction lands.

### Impact Explanation
If the attacker's `InitializeBuffer` lands first:
- The buffer's state transitions from `Uninitialized` to `Buffer { authority_address: Some(attacker) }`.
- The legitimate deployer's own `InitializeBuffer` call now fails with `AccountAlreadyInitialized`, and their subsequent `Write` calls fail with `IncorrectAuthority`/`MissingRequiredSignature` since they no longer control the authority.
- The deployer has already paid the rent-exempt lamports to create the buffer account, but the attacker (as authority) can call `Close` on the buffer, draining its lamports to a recipient of the attacker's choosing — resulting in concrete loss of funds to an unprivileged deployer.
- This also causes deployment failure requiring the deployer to redeploy with a new buffer keypair, matching the "failure of the protocol, need for redeploy" and "loss of funds" impact categories from the original report.

This is a real, reachable, unprivileged-user path in the SVM program-loading surface (`bpf_loader_upgradeable`), not a validator/operator-only or theoretical issue.

### Likelihood Explanation
Exploitation only requires observing a buffer account's `CreateAccount` transaction (public pubkey, standard part of every upgradeable program deploy/upgrade) and racing an `InitializeBuffer` transaction naming the attacker as authority before the legitimate follow-up transaction lands. No special privileges, validator access, or non-standard conditions are required — any user submitting ordinary transactions can attempt this against any in-flight deployment.

### Recommendation
Require the intended authority (and/or the buffer account itself) to sign `InitializeBuffer`, mirroring the signer check already present in the `Write` and `SetAuthority` handlers. Alternatively/additionally, encourage or enforce that buffer account creation and initialization occur atomically within a single transaction so no observable window exists between account creation and authority assignment.

### Proof of Concept
1. Deployer submits `SystemInstruction::CreateAccount` creating buffer account `B` (owner = `bpf_loader_upgradeable`, state `Uninitialized`), funded with rent-exempt lamports.
2. Attacker observes `B`'s pubkey once this transaction is visible (mempool/RPC/block).
3. Attacker submits `UpgradeableLoaderInstruction::InitializeBuffer` with account 0 = `B`, account 1 = attacker's own pubkey (not required to sign, per `programs/bpf_loader/src/lib.rs:158-171`), before the deployer's own `InitializeBuffer` lands.
4. `B`'s state becomes `Buffer { authority_address: Some(attacker) }`.
5. Deployer's subsequent `InitializeBuffer` fails with `AccountAlreadyInitialized`; deployer's `Write` calls fail with `IncorrectAuthority`.
6. Attacker calls `Close` on `B`, draining the deployer-funded rent-exempt lamports to an address of the attacker's choosing.
