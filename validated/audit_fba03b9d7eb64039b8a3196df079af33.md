### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing shop-domain spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body, but the `shop` (tenant identifier) that is handed to the app's webhook handler is read from an unauthenticated HTTP header that is never part of the HMAC-signed bytes.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which compares an HMAC over `request.to_signable_string`: [1](#0-0) 

`Request#to_signable_string` returns only `@raw_body` — the request body — while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight out of HTTP headers that are not included in the signed data: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` compute `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compare against `verifiable_query.hmac`, with no reference at all to the `shop` field: [3](#0-2) 

Once the HMAC passes (because it only vouches for the body), `Registry.process` forwards the **unauthenticated** `request.shop` value directly into `WebhookMetadata`, which is the sole tenant-identifying field passed to the app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

**Broken binding (equality that should hold but doesn't):**
`bytes verified by HMAC` (`@raw_body`) ≠ `bytes used to establish tenant identity` (`shopify-shop-domain` header). The gem verifies one thing (the body) and trusts another, disjoint, attacker-controllable input (the shop header) as the merchant identity passed on to application code — the same "bytes verified vs. bytes parsed/acted-on" class called out in the rules, applied here to the HMAC/shop-domain binding instead of an OAuth/session field.

This differs from Shopify's real webhook delivery in one important way: Shopify's own delivery infrastructure guarantees the `shop-domain` header matches the signed body's origin, so in the intended flow this is not exploitable. However, the gem's `Request` class has no way to enforce that guarantee itself — it merely accepts whatever headers are handed to it in `initialize(raw_body:, headers:)`, with no header value bound into the HMAC-signed string. Any caller (host app, proxy, replay tooling, or middleware bug) that passes through headers verbatim without independently re-deriving `shop` opens a path where a valid HMAC (computed by Shopify for the attacker's own shop) accompanies a spoofed `shopify-shop-domain` header for a different, victim shop, and the library will accept it as authentic for that victim shop.

### Impact Explanation
If a host application relies on this gem's `Request`/`Registry.process` to authenticate the webhook and to establish which merchant the payload belongs to, an attacker who controls their own installed shop (an unprivileged, legitimately-onboarded merchant) can obtain genuinely-HMAC-signed webhook deliveries for their own shop, then re-deliver the same body/HMAC pair with a modified `shopify-shop-domain` header pointing at a victim shop. Because the gem's validation only checks the body signature and never checks that the signed body actually originated for the claimed shop, `WebhookMetadata#shop` will report the victim's domain to the app's handler — a cross-tenant identity spoof within data the gem asserts as verified. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability depends on whether the host app blindly forwards inbound headers to `ShopifyAPI::Webhooks::Request.new` without its own separate validation that the shop belongs to a session/installation matching the signed content — which is exactly the API contract this gem exposes and encourages (`Registry.process` treats HMAC success as full authentication and hands back `shop` as trusted). The gem itself provides no defense-in-depth (e.g., binding `shop` into the signable string, or cross-checking `shop` against an active session/webhook subscription) so any deployment following the documented pattern inherits the gap.

### Recommendation
Include `shop`, `topic`, and `webhook_id` header values in the string that is HMAC-verified (or independently verify the `shop` header against Shopify's known/expected value for the subscription, e.g. by looking up the webhook by `webhook_id`) before trusting `request.shop` in `Registry.process`. At minimum, document prominently that `shop-domain` is unauthenticated and must not be used as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and receives a real webhook, e.g., `orders/create`, with a genuine `X-Shopify-Hmac-Sha256` computed by Shopify over the JSON body using the app's `client_secret`.
2. Attacker captures the raw body and the valid HMAC header, then replays the HTTP request to the app's webhook endpoint but overwrites the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` then `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`@raw_body` only) and it matches, so validation succeeds: [6](#0-5) 
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim-shop.myshopify.com"`, even though the payload actually belongs to `attacker-shop.myshopify.com`, and is passed to the app's handler as trusted, verified data.
