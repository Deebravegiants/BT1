### Title
`Registry.process` trusts the unsigned `shop-domain` header as tenant identity, allowing cross-shop webhook replay - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` validates only that the raw body matches an HMAC computed with the app's shared `api_secret_key`, then builds `WebhookMetadata#shop` straight from the unsigned `X-Shopify-Shop-Domain` header. Because the signature never covers any header, an attacker who legitimately receives one validly-signed webhook (e.g. by installing the app on their own dev store) can replay that exact body to the app's public webhook endpoint with the shop header swapped to an arbitrary victim shop, and the signature check still passes.

### Finding Description
The broken binding: the invariant should be `hmac_valid(body, secret) == true` implies `request.shop == the shop that produced body`. In this code, `hmac_valid(body, secret) == true` only implies the body was signed by *someone* holding `api_secret_key` — it says nothing about which shop's header accompanies it.

- `HmacValidator.validate` calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`. [1](#0-0) 
- `Request#to_signable_string` returns only `@raw_body`; none of the headers participate in the signable string. [2](#0-1) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read verbatim from headers that were never part of the signed content. [3](#0-2) 
- `Registry.process` checks the HMAC, then immediately constructs `WebhookMetadata` using `request.shop` from the header, with no cross-check against the body or any session store. [4](#0-3) 

Root cause: Shopify apps use a single `api_secret_key` shared across every shop that installs the app (the client secret is per-app, not per-shop). An unprivileged attacker can install the app on their own development shop, register their own webhook endpoint, and receive a legitimately, validly-signed webhook whose body and HMAC were computed by Shopify using that same shared secret. Since the HMAC only covers `raw_body`, the attacker can take that (body, HMAC) pair — unmodified — and POST it to the app's public webhook route while substituting `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with any victim shop's values. `Utils::HmacValidator.validate(request)` still returns `true` because it only re-derives the HMAC from `raw_body`, and `Registry.process` hands `WebhookMetadata.new(shop: request.shop, ...)` — now the attacker-chosen victim domain — to the app's handler as if it were authenticated. The gem's own documented handler pattern (`shop: data.shop`) treats this value as trustworthy tenant identity for downstream lookups/enqueues. [5](#0-4) 

No existing guard closes this gap: `HmacValidator.validate` cannot see headers at all (only `to_signable_string`/`hmac` from `VerifiableQuery`) [6](#0-5) ; there is no `ShopValidator.sanitize!`, `state` comparison, or JWT `aud`/`dest` check anywhere in this webhook path (those apply only to OAuth/session-token flows, not `Registry.process`).

### Impact Explanation
Any app relying on `WebhookMetadata#shop` to key per-shop state (session lookup, database records, background job dispatch, GDPR redact routing, etc. — exactly the pattern shown in this gem's own docs) can be made to attribute attacker-controlled or attacker-replayed webhook payloads to an arbitrary victim shop domain. This is a cross-tenant data/identity confusion: one merchant's webhook data can be delivered into another merchant's processing pipeline under the guise of that merchant's shop. Since the app secret is shared across all installs, this is repeatable against **any** shop that has installed the same app, not just the attacker's own store — the attacker only needs to know or guess a target's `*.myshopify.com` domain. Severity matches Critical — cross-tenant access, since it breaks the "single identity per request, derived from an authenticated source" invariant.

### Likelihood Explanation
Preconditions are minimal and fully within the stated attacker capability: create/install the app on an owned dev shop, register a webhook endpoint to capture one legitimately signed callback, then replay that raw body + HMAC to the app's real webhook controller with header fields altered. No secrets, tokens, or privileged access are required, and the attack is trivially repeatable per target shop with negligible cost (a single HTTP replay).

### Recommendation
Bind the trusted shop identity to something the HMAC actually covers, or cryptographically tie the header to the payload:
- Include `shop_domain` (and ideally `topic`, `webhook_id`) inside the HMAC-signed material, or
- Have `Registry.process` cross-validate `request.shop` against a shop value embedded in `parsed_body` (Shopify webhook payloads for most topics include shop-identifying fields) before constructing `WebhookMetadata`, or
- At minimum, document/require that handler implementations must re-verify `data.shop` against their own session/shop registry before trusting it, and consider raising in `Registry.process` if no such secondary verification hook is provided.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_shop_test.rb
require_relative "../test_helper.rb"

class CrossShopWebhookReplayTest < Test::Unit::TestCase
  def test_hmac_valid_but_shop_header_unbound_to_body
    body = "{}"
    hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
    signed_hmac_b64 = Base64.encode64(hmac)

    # Attacker legitimately receives this (body, hmac) pair for their own shop:
    attacker_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => signed_hmac_b64,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-webhook-id" => "attacker-id",
      "x-shopify-api-version" => "2024-01",
    }
    attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
    assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))

    # Attacker replays same body+hmac but swaps the shop header to a victim shop:
    forged_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
    forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

    # Same signature validity -- the shop header was never covered by the HMAC:
    assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))
    assert_equal("victim-shop.myshopify.com", forged_request.shop)

    received_shop = nil
    handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", path: "p", delivery_method: :http, handler: handler)

    ShopifyAPI::Webhooks::Registry.process(forged_request)

    # process() accepted the victim shop identity despite the HMAC only proving the body,
    # not the shop binding: the equality request.shop == "shop that actually produced this body" fails.
    assert_equal("victim-shop.myshopify.com", received_shop)
  end
end
```
