Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is completely excluded from the HMAC that `ShopifyAPI::Webhooks::Registry.process` verifies. The signature only binds the raw request body; it never binds the `shop-domain` header. This breaks the intended identity binding: `HMAC(body) == verified` should imply `shop == the tenant that produced this body`, but the gem never establishes that equality.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely via: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `Request#shop`, which becomes the tenant identifier passed to the app's handler, is read from an attacker/transport-controlled HTTP header (`x-shopify-shop-domain` / `shopify-shop-domain`), not from any signed field: [4](#0-3) [5](#0-4) 

The verified equality is only `HMAC_secret(raw_body) == received_hmac`. The equality the app actually needs — `shop header == the shop whose data is in raw_body` — is never checked anywhere in `HmacValidator`, `Request`, or `Registry`. `Registry.process` then constructs `WebhookMetadata` directly from the unauthenticated header value and hands it to the app's handler as the trusted tenant: [6](#0-5) 

Because Shopify apps share a single `client_secret` (`Context.api_secret_key`) across every installed shop, any merchant who has installed the app can trigger a legitimate webhook delivery for their own store (e.g. update a product), capture the raw body plus its valid `x-shopify-hmac-sha256`, and then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only ever depended on `raw_body`, and `Registry.process` will label the payload with the attacker-supplied `shop` value, delivering it to the handler as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion inside the gem's own webhook-verification primitive: `Request#shop` is exposed as a "verified" attribute of a request that passed `HmacValidator.validate`, but it is not actually covered by that validation. Any application that follows the documented pattern (`data.shop` from `WebhookMetadata` in `handler.handle`) and uses it to key per-tenant storage, jobs, or access-token lookup will process attacker-labeled data under the wrong shop, i.e. cross-tenant access facilitated entirely by this gem's verification API.

### Likelihood Explanation
Requires only that the attacker control (or install) one shop running the target app — no leaked secrets, no privileged access, and no dependence on host-app misuse: the gem's own `Request`/`HmacValidator`/`Registry.process` trio is what fails to bind `shop` to the signed body.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or independently verify that the `shop-domain` header matches a shop value embedded in/derivable from the verified body/session before constructing `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should be extended (or a new check added in `Registry.process`) so the shop identity is cryptographically bound to the verified payload rather than trusted from an unsigned header.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, receiving a valid `client_secret`-independent installation (same shared app secret as all other tenants).
2. Attacker triggers a webhook event on their own shop and captures the resulting request: `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>`.
3. Attacker replays this exact `raw_body` + `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`@raw_body` only) and matches — validation passes.
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the forged `shop-domain` header value `victim-shop.myshopify.com`, and invokes the app's registered handler with this spoofed tenant, per: [1](#0-0)
