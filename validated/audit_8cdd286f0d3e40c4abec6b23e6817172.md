### Title
Unprotected `swapExactOutSingle`/`swapETHForExactTokens` conversion in `EvmHost.dispatch()`/`fundRequest()` has no caller-supplied slippage bound, exposing native-fee payers to sandwich losses - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` let any unprivileged caller pay the dispatch/relayer fee with native token. When `msg.value > 0`, the host calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` directly, without exposing any user-supplied `amountInMax`/slippage parameter — the entire `msg.value` is passed as the max input, and the router pulls whatever ETH price yields exactly `post.fee`/`get.fee`/`amount` fee-tokens out, refunding the rest. ### Finding Description
This is the direct Hyperbridge analog of the reported `exactInputParams` bug class: a swap is executed on-chain with no caller-controlled slippage/price-limit parameter to bound the execution price. Here the router call is `swapETHForExactTokens`, an exact-output swap where `msg.value` is implicitly used as `amountInMax`. Because `msg.value` is fixed at submission and the docs explicitly instruct callers to "send enough native tokens to cover fees" using an off-chain `quote()` estimate [4](#0-3) , a value-conscious caller typically sends close to the quoted amount rather than padding heavily. If a searcher front-runs the transaction by moving the ETH/feeToken pool price, the swap can revert (if `msg.value` becomes insufficient as `amountInMax`) or, in the exact-output design here, still succeed but consume nearly all of the sent `msg.value` as input while only paying out the fixed `post.fee` — the caller receives no explicit minimum-favorable-rate guarantee and the swap price is set entirely by pool state at execution time, not by any value the caller can assert. The same unmitigated pattern also appears in `IntentGatewayV2` (Tron variant), which performs an identical `swapETHForExactTokens{value: msgValue}` call to cover order fees paid in native token [5](#0-4) .

The documentation itself flags a closely related sandwich-attack risk on the `quote()` view function that estimates these swaps: "Do not call `quote()` in smart contract transactions. It uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks" [6](#0-5) , confirming the project itself acknowledges the underlying price-manipulation surface around this native-fee-swap mechanism, but no on-chain slippage bound protects the actual `dispatch()`/`fundRequest()` execution path itself.

### Impact Explanation
An attacker (MEV searcher) observing a pending `dispatch()`/`fundRequest()` call with `msg.value` can manipulate the local Uniswap V2 pool (front-run buy, back-run sell) to shift the ETH/feeToken price. Because the swap has no caller-imposed minimum-output-per-input bound beyond the total `msg.value` ceiling, the victim's transaction either (a) reverts with `UniswapV2Router: EXCESSIVE_INPUT_AMOUNT` wasting gas and requiring resubmission at a worse price, or (b) succeeds while consuming a disproportionately large share of the supplied `msg.value` to cover the same fixed `post.fee`, with the difference captured by the attacker as sandwich profit. This is a direct loss of funds for the transaction submitter, reachable by any user dispatching a cross-chain message and paying in native token — a core, frequently used entry point of the protocol.

### Likelihood Explanation
High reachability: `dispatch()` and `fundRequest()` are the primary, unprivileged, permissionless entry points for sending ISMP messages and paying relayer fees in native token, used routinely by every HyperApp integrator that opts to pay with native ETH/BNB/etc. as documented. Any transaction with `msg.value > 0` triggers the vulnerable swap unconditionally, and MEV sandwich bots actively monitor mempools for AMM swaps of exactly this shape (`swapETHForExactTokens`), making exploitation straightforward and economically motivated whenever pool liquidity is thin relative to the fee amount.

### Recommendation
Add an explicit, caller-supplied maximum native-input (slippage) parameter to `DispatchPost`/`DispatchGet`/`fundRequest`, and pass it as `amountInMax` to the router instead of relying on the entirety of `msg.value`. Alternatively, allow the caller to specify `minFeeTokenOut`/`maxNativeIn` bounds validated against an on-chain oracle-based price check, and enforce a maximum acceptable price deviation from the pool quote before submitting the swap, mirroring the mitigation `SimplexPaymaster.swapAndDeposit` already applies via an oracle-derived `amountOutMin` [7](#0-6) .

### Proof of Concept
1. Attacker monitors mempool for a pending `EvmHost.dispatch(DispatchPost)` call with `msg.value = X` intended to cover `post.fee` in feeToken via the configured Uniswap V2 pool.
2. Attacker front-runs with a large buy of feeToken (or sell of native) to shift the pool price against the victim.
3. Victim's transaction executes `swapETHForExactTokens{value: X}(post.fee, [WETH, feeToken], address(this), block.timestamp)` [1](#0-0)  — either reverting (`EXCESSIVE_INPUT_AMOUNT`, DoS/gas loss) or succeeding while consuming most/all of `X` as input, refunding little to nothing, for the same fixed `post.fee` output.
4. Attacker back-runs to reverse their initial position, capturing the price spread as profit extracted from the victim's overpaid native input.

**Uncertainty note:** I was unable to fully verify the exact revert/refund behavior of the specific `IUniswapV2Router02` implementation configured per-chain (whether it strictly requires `amountInMax >= actual input` or silently over-consumes), since the router contract itself is an external dependency not indexed in this repo. The severity level (Medium, matching the original report) reflects that this is a funds-loss/DoS risk on a fee-payment convenience path rather than a core escrow/settlement fund-drain.
