### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain` header straight through to the handler as the tenant identifier. The `shop` header is never included in the signed material, so any request whose body carries a valid signature (for *any* shop using the app) can claim to belong to any other shop by simply changing that header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read from an unsigned header and exposed as a plain accessor: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop` (and `request.topic`) as authoritative tenant/topic metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `to_signable_string` (the body), never touching headers: [4](#0-3) 

**Binding broken:** the code treats `hmac_valid(body) == true` as implying `request.shop == shop_that_produced_body`, but those are two independent equalities — `hmac_valid(body)` only proves *some* body was signed with the app's shared webhook secret; it says nothing about which shop the `shopify-shop-domain` header claims.

**Why this is reachable by an unprivileged actor:** Shopify signs webhooks for *every* shop that has the app installed using the single, app-wide client secret (not a per-shop secret). An attacker only needs to install the target app on their own low-privilege/trial store (an ordinary, unauthenticated action requiring no special access) to receive genuinely HMAC-valid webhook deliveries for their own shop. They can then replay that exact body/topic to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` forwards `shop: <victim domain>` to the handler as if the event genuinely originated from the victim shop.

### Impact Explanation
This breaks the tenant isolation guarantee the library implicitly provides through `WebhookMetadata#shop`: a host application that uses this field (as documented/intended) to look up the shop's session/access token or to scope data writes will act on the wrong tenant's context based on attacker-controlled input. This is a cross-tenant confusion vector reachable without the app's `client_secret`, without any access token, and without TLS interception — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (1) the ability to install the target app on an attacker-controlled store (a normal, unauthenticated merchant action for public apps) to obtain one legitimately-signed webhook, and (2) sending an HTTP request to the app's public webhook endpoint with a modified header — both trivially available to an unprivileged internet user, no secret material required.

### Recommendation
Include the shop domain (and topic) in the HMAC-signed material, or independently verify `request.shop` against a shop known to have registered/be entitled to receive that specific `webhook_id`/topic before trusting it in `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated and must be cross-checked by the host application against its own session store before being used for any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, receiving normal webhook deliveries signed with the app's shared secret, e.g. topic `orders/create` with body `B` and header `x-shopify-hmac-sha256: HMAC(B)`.
2. Attacker resends the same request to the app's webhook endpoint but replaces the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(B)` — still valid, since only the body is signed (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), and any host logic keyed on `shop` now operates on the wrong tenant using attacker-supplied data.
