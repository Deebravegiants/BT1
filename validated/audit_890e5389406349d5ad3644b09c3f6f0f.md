### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, allowing tenant-attribution spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value that downstream webhook handlers use as the tenant identifier is read from an HTTP header that is never covered by that signature. This breaks the equality "shop authenticated == shop used as the tenant/session key" that the report's bug class targets: the bytes that are cryptographically verified (the body) are not the same bytes that determine which shop a webhook is attributed to.

### Finding Description
`Request#hmac` decodes the `shopify-hmac-sha256` / `x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are pulled straight from headers with no inclusion in the signed payload: [3](#0-2) 

`HmacValidator.validate`/`validate_signature`, the same primitive used for OAuth callback verification, only checks `to_signable_string` against the computed signature: [4](#0-3) 

Because the signature only binds the body, an attacker who possesses one genuine, validly-signed webhook delivery (e.g. one sent to their own app installation/shop) can replay that exact body+HMAC pair while altering the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers. `HmacValidator.validate` will still report success because the body — the only thing it inspects — is unchanged, but `request.shop` will now report an attacker-chosen shop domain. Any app logic that trusts `Request#shop` (or the `WebhookHandler` interface built on it) as the tenant key for routing, deduplication, or authorization decisions will process the payload under the wrong tenant identity.

This matches the report's underlying bug class ("acting on data that was not covered by the integrity check") mapped onto this gem's own webhook verification primitive rather than the ERC20 `transferFrom` example.

### Impact Explanation
This is a cross-tenant identity binding failure: the shop attribution of an authenticated webhook is not itself authenticated. An app that keys per-shop state (installation status, order/customer records, GDPR compliance flags, uninstall handling, etc.) off `request.shop` can have that binding forged despite a "valid" HMAC check, resulting in cross-tenant data confusion — one of the explicitly in-scope Critical impacts ("cross-tenant access").

### Likelihood Explanation
Exploitation requires the attacker to already receive at least one genuine webhook (trivial for anyone with their own store/app installation, which is an unprivileged internet-facing capability, not a leaked credential), and requires the host application to trust `Request#shop`/`WebhookHandler#shop` as an authorization or tenant-scoping key without independently corroborating it — the intended and documented use of this API. No `api_secret_key`, access token, or privileged access is needed beyond what any developer/merchant can obtain by installing the app once.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used for verification, or otherwise cryptographically bind them to the HMAC-covered body (e.g., derive/verify shop from the payload itself rather than an unauthenticated header), so that `to_signable_string` cannot be satisfied while `shop` is altered independently of the signed content.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook: headers include a valid `shopify-hmac-sha256` computed over `raw_body`, and `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical HTTP request to the app's webhook endpoint, keeping `raw_body` and `shopify-hmac-sha256` untouched, but rewrites `shopify-shop-domain` to `victim.myshopify.com` (and optionally `shopify-topic`/`shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` calls `to_signable_string`, which returns only `raw_body`, so `OpenSSL.secure_compare` succeeds — [4](#0-3)  passes.
4. Any handler invoked with `request.shop` (per `Request#shop` at [5](#0-4) ) now processes the attacker's payload as if it originated from `victim.myshopify.com`.
