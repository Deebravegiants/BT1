### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, and then hands the handler a `WebhookMetadata` struct containing `request.shop` — the tenant identity the handler acts on. However, the HMAC signature only ever covers the raw request body; the `shop` field (and `topic`, `api_version`, `webhook_id`) come from HTTP headers that are completely outside the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `X-Shopify-Shop-Domain` header, never included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header — it never touches `shop`: [3](#0-2) 

`Registry.process` gates all further processing on that HMAC check, then immediately forwards `request.shop` — the unauthenticated header — into `WebhookMetadata`, which is the object handed to the app's webhook handler as if it were trusted, tenant-scoped data: [4](#0-3) 

The equality that is broken: `shop-header-used-by-handler == shop-bytes-covered-by-HMAC` does not hold — the header is parsed and trusted, but never verified.

Because the HMAC only signs the body, an attacker who legitimately installs the app on their own store (`attacker.myshopify.com`) receives real, correctly-signed webhooks for that shop. They can replay such a request to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `X-Shopify-Shop-Domain`/`shopify-shop-domain`) header with a victim shop's domain (`victim.myshopify.com`), keeping the original raw body and its valid HMAC untouched. `Utils::HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the (unmodified) signature — the header swap is invisible to it. `Registry.process` then calls the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`.

### Impact Explanation
Any host application that follows this gem's intended pattern — trusting `WebhookMetadata#shop` returned after `Registry.process` succeeds — to select which tenant's session/data to act on (e.g., `shopify_app`-style handlers that look up a shop's session by `data.shop` and update local records) will apply attacker-controlled webhook data to another merchant's tenant. This is a cross-tenant integrity/confidentiality break rooted entirely in this gem's own verification logic (it binds nothing except the body), satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged app installer on any shop (no elevated credentials, no `api_secret_key`, no TLS interception) to obtain real signed webhook traffic for their own tenant, then replay it with a modified `shop` header to any endpoint the app exposes for webhook delivery. This requires no secret material and is fully reachable through this gem's public `Registry.process`/`HmacValidator.validate` API.

### Recommendation
Include the shop domain (and topic/webhook id, if they influence handler behavior) in the HMAC-signed material, or independently verify `request.shop` against the set of shops that legitimately installed/authorized the app (e.g., cross-check against a known/authenticated session) before constructing `WebhookMetadata`. At minimum, `Utils::HmacValidator.validate` should not be presented as validating the entire `Request`, and `Registry.process`/`WebhookMetadata` documentation should explicitly warn that `shop` is unauthenticated header data.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and captures a real webhook delivery (e.g., `orders/create`) with headers:
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - raw JSON body `B`
2. Attacker resends the exact same body `B` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed; `request.shop` returns `"victim.myshopify.com"`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only (per `to_signable_string`/`hmac_validator.rb`), which matches, so `Registry.process` proceeds.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...))` executes with attacker-chosen body content attributed to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
