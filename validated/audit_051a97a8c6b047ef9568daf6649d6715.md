### Title
Donation-inflated `realBalance` can underflow `Router._computeBuy`'s overflow-cap math, DoS-ing the supply-trigger graduation path - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch computes `cappedReserveToken = reserveToken - tokensOut` where `tokensOut` is clamped to the pair's live ERC20 balance (`pair.tokenBalance()`). This subtraction assumes the protocol invariant `reserveToken > tokenBalance` always holds. That invariant can be broken by a plain ERC20 `transfer` of the launched `Token` directly into the `Pair` — a path explicitly reachable by any unrelated wallet — which inflates `tokenBalance()` without touching the virtual `reserveToken`. If the donation is large enough to erase the constant 250M-token gap (`LP_RESERVE`), any subsequent buy that would hit the overflow cap reverts on arithmetic underflow instead of capping.

### Finding Description
At launch `Pair.reserve0` (`tokenReserve`) is seeded to `Token.TOTAL_SUPPLY()` (1B) while only `curveSupply = 75%` (750M) of real tokens are ever transferred into the pair; the difference is the `LP_RESERVE` (250M) held back in `Bonding` for graduation, per `packages/contracts/AGENTS.md` ("Virtual token reserve" section) [1](#0-0) . Every `Router.buy` moves `reserveToken` and the pair's real token balance down by the same `tokensOut`, so `reserveToken - pair.tokenBalance()` is invariantly `LP_RESERVE` under normal trading — this is asserted directly by `test_inv_virtualReserveAlwaysExceedsRealBalance` [2](#0-1) .

Nothing stops any wallet holding the launched `Token` from calling `token.transfer(pair, amount)` directly — this is a permitted, unprivileged path per the analog rules (direct ERC20 transfers of a launched Token into `Pair`). Because `Pair.tokenBalance()` reads the live `balanceOf(address(this))` rather than a stored/reserve-tracked field [3](#0-2) , such a donation inflates `tokenBalance()` without moving `reserveToken`, shrinking (and potentially inverting) the 250M gap.

`Router._computeBuy`'s overflow-cap branch then does:
```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // reserveToken - realBalance
    ...
``` [4](#0-3) 

If a donation has pushed `realBalance` above `reserveToken` (i.e., the attacker donated more than the current `LP_RESERVE` gap), `cappedReserveToken = reserveToken - tokensOut` underflows in Solidity 0.8's checked arithmetic and reverts the whole transaction, rather than the intended `OverflowCapDegenerate()` guard, which only fires for the `== 0` case, not for `>` (underflow). The comment in `test_inv_virtualReserveAlwaysExceedsRealBalance` explicitly says this invariant "is what makes the `cappedReserveToken == 0` branch in `Router._computeBuy` unreachable; if it ever ceased to hold, that branch would revert with `OverflowCapDegenerate` rather than over-pay" [5](#0-4)  — but that statement is only true for the exact-equality case; a strict inversion (`realBalance > reserveToken`) instead produces an unhandled arithmetic-underflow revert, which is a distinct and unguarded failure mode from the one the invariant test claims to cover.

The team is independently aware that donations breaking `realBalance > reserveToken` are dangerous: `Zap.t.sol`'s `_stageDonationAttack` helper and surrounding comments describe exactly this shape — "A TOKEN donation that drives `realBalance > reserveToken` previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg, cascading into a `Zap.buy` DoS. Guard added; tests pin the fix." [6](#0-5) . That guard was added to `Bonding.previewLtUntilGraduation`'s off-chain-preview math, but `Router._computeBuy` — the on-chain function that actually executes buys and enforces the overflow cap — performs the identical `reserveToken - tokensOut` subtraction with no equivalent saturating/guard logic, so the underlying arithmetic hazard remains reachable through the live buy path itself, not just the preview helper.

### Impact Explanation
When the donation pushes `realBalance` strictly above `reserveToken`, any buy sized large enough to hit the overflow-cap branch (i.e., any buy whose naive `tokensOut` quote exceeds `pair.tokenBalance()`) reverts unconditionally instead of capping and executing. Since the supply-exhaustion graduation trigger (`IPair.tokenBalance() == 0`) can only ever be reached via this exact capped-buy code path — the last buy that drains the curve necessarily forces `tokensOut = realBalance` — an attacker who inflates the gap enough can permanently prevent the token from ever graduating via the supply trigger. If the LT's `exchangeRate` is such that the USD trigger (`(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K`) does not fire independently (e.g., a low-rate LT, or a token whose trading volume stalls below the USD threshold), the token can be frozen in `Curve` lifecycle indefinitely, with the last slice of tokens permanently unsellable to any buyer attempting to complete the curve. This is a freezing-of-funds condition on the curve-raised LT and the launched token's sellable supply, reachable purely by an unrelated wallet transferring `Token` into `Pair` — no privileged role required.

### Likelihood Explanation
Medium-High: the attacker needs to acquire and then donate more than `LP_RESERVE` (250M) worth of the launched token's circulating supply back into the pair. Because the curve's own AMM pricing makes acquiring a large fraction of the 750M `curveSupply` increasingly expensive, this is not a trivial dust attack, but it is entirely within reach of a single well-funded unprivileged actor (buy-then-donate, no special permissions, no oracle manipulation, no reentrancy needed) and requires no cooperation from the protocol or other users. The attack is also directly incentive-compatible for anyone who wants to strand a competitor's or their own token pre-graduation (e.g., to prevent a rival launch from reaching HyperSwap).

### Recommendation
Make `Router._computeBuy`'s overflow-cap arithmetic saturating/guarded against `realBalance >= reserveToken`, mirroring whatever fix was applied to `Bonding.previewLtUntilGraduation`'s supply leg — e.g., explicitly check `realBalance < reserveToken` before computing `cappedReserveToken`, and revert with a clear, expected error (or clamp gracefully) rather than allowing an unchecked-arithmetic underflow to brick the transaction. Additionally consider having `Pair`/`Bonding` actively reconcile or reject/redirect stray `Token` donations (e.g., via a `skim`-equivalent for the curve-side pair, analogous to the HyperSwap pre-seed donation handling already implemented for the post-graduation pair) so `tokenBalance()` cannot silently drift from the `reserveToken` accounting that the AMM math depends on.

### Proof of Concept
1. Launch a token via `Zap.createToken`, letting the curve seed with `curveSupply = 750M` tokens in `Pair`, `reserve0 = 1B` (virtual).
2. Attacker (or any wallet) repeatedly calls `Zap.buy` / `Bonding.buy` to purchase a large fraction of the 750M sellable tokens, e.g., 500M tokens, driving `reserveToken` down to `500M` and `pair.tokenBalance()` down to `250M` (gap stays 250M).
3. Attacker then calls `token.transfer(pairAddr, 260_000_000e18)` directly (plain ERC20 transfer, no swap) — pushing `pair.tokenBalance()` to `510M`, now **above** `reserveToken` (`500M`).
4. Any subsequent buyer submits a buy sized so the naive constant-product quote for `tokensOut` exceeds `pair.tokenBalance()` (i.e., attempts to drain the remainder of the curve) — `Router._computeBuy` takes the `tokensOut > realBalance` branch, sets `tokensOut = realBalance (510M)`, and computes `cappedReserveToken = reserveToken (500M) - tokensOut (510M)`, which underflows and reverts the entire buy transaction.
5. Because the supply-exhaustion graduation trigger can only fire through this exact capped-buy code path, the token can no longer graduate via the supply trigger; if the USD trigger also doesn't bind (e.g., LT rate too low), the token is stuck in `Curve` lifecycle with its final tranche of tokens permanently unbuyable, freezing the remaining curve-raised LT and unsold tokens.
