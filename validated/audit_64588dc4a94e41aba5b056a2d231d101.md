### Title
Rebasing/deflationary input tokens can permanently freeze other orders' escrow in `IntentGatewayV2` — ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2` records escrowed order amounts as point-in-time `uint256` values in `_orders[commitment][token]` at `placeOrder` time [1](#0-0) . All orders sharing the same input token draw from one pooled ERC-20 balance held by the gateway contract. If that token's balance can decrease independently of gateway-initiated transfers (e.g. a rebasing token experiencing a negative rebase/slashing event, analogous to stETH), the sum of all `_orders[...]` entries can exceed the contract's actual token balance, and `_withdraw` will revert for later claimants — permanently freezing their escrow. This mirrors the reported Pods Finance issue where point-in-time stETH balances stored in a deposit queue are not adjusted for rebases between deposit and refund.

### Finding Description
`placeOrder` measures the *actual* amount received at deposit time via balance-delta accounting (to protect against fee-on-transfer tokens) and stores that fixed amount in `_orders[commitment][token]`: [2](#0-1) 

This escrow bookkeeping is a **point-in-time snapshot**, identical in structure to the Pods Finance `BaseVault` deposit queue flagged in the external report: an amount recorded once, later paid out unconditionally on refund/withdraw/fill, with no re-validation against the token's live balance.

`_withdraw` (used by both fills and refunds/cancellations) decrements the stored escrow value and transfers exactly that stored `amount`, without ever checking that the contract's live `balanceOf` still covers the sum of all outstanding `_orders` entries for that token: [3](#0-2) 

Because many different orders share the same underlying `IERC20` token pool (there is no per-order token custody — only a per-commitment accounting entry against a shared contract balance), any token whose balance can shrink without a matching gateway-initiated transfer (rebasing tokens, tokens subject to negative yield/slashing, or any deflationary mechanism) breaks the invariant `sum(_orders[*][token]) <= IERC20(token).balanceOf(gateway)`. Once broken, `IERC20(token).safeTransfer(beneficiary, amount)` in `_withdraw` reverts for whichever order(s) exhaust the remaining balance — this is a hard revert (`safeTransfer` reverts on failure), not a partial/adjusted payout, so those orders' escrow becomes **permanently stuck**: `cancelOrder`, `fillOrder`, and the cross-chain `RefundEscrow`/`RedeemEscrow` paths all funnel into this same `_withdraw`, so there is no alternate code path to recover the funds.

This is directly reachable by an unprivileged actor: any user can `placeOrder` with an arbitrary ERC-20 as `order.inputs[i].token` — the contract already anticipates non-standard tokens (see the explicit fee-on-transfer handling in `placeOrder`) but only handles the deposit-side quirk, not the holding-period balance-shrinkage quirk that a rebasing/negative-yield token introduces.

### Impact Explanation
This qualifies as permanent freezing of user funds: once the shared token balance for a given input token falls below the sum of outstanding `_orders` entries (via rebase/slashing), any order whose refund or fill would require more tokens than remain in the pool cannot be settled — `cancelOrder`/`onAccept(RefundEscrow)`/`fillOrder`/`onAccept(RedeemEscrow)` all revert via `_withdraw`'s `safeTransfer`. There is no governance sweep or emergency-withdrawal path for `_orders`-tracked balances (only protocol-fee "dust" is sweepable via `SweepDust`), so affected users' input tokens are unrecoverable through the contract. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is **conditional on token choice**: it only manifests for input tokens whose balance can decrease without a corresponding gateway-initiated transfer (rebasing/negative-yield tokens). `IntentGatewayV2` places no restriction on `order.inputs[i].token` and, per its own tests, is explicitly designed to be used with arbitrary/non-standard ERC-20s (fee-on-transfer tokens are already tested and handled). Given Hyperbridge's model of permissionless order placement across many chains/solvers, use of a rebasing token as an order input is plausible, and the trigger (a negative rebase event, e.g. slashing on a liquid-staking token) is outside the protocol's control — exactly the scenario the original report describes for Pods Finance's stETH vault.

### Recommendation
- Before transferring in `_withdraw`, cap the transferred `amount` (or the escrow bookkeeping unit) to the token's actual live balance for orders sharing that token, and/or track escrow in a manner resilient to balance changes (e.g., normalized/share-based accounting analogous to the "secondary share queue" fix suggested to Pods Finance) rather than raw point-in-time token amounts.
- Alternatively, explicitly disallow or flag rebasing/deflationary tokens as valid `order.inputs`/`output.assets` tokens (similar to how many other protocols block known-rebasing token addresses), since the gateway's shared-pool accounting model is fundamentally incompatible with such tokens.
- At minimum, replace unconditional `safeTransfer` in `_withdraw` with a "transfer whatever is available, and record/allow the shortfall to be reconciled" pattern so a shortfall degrades gracefully instead of bricking arbitrary unrelated orders' withdrawals.

### Proof of Concept
1. Deploy `IntentGatewayV2` and let two users, Alice and Bob, each `placeOrder` with input token `T` (a rebasing ERC-20), each escrowing `1000 T`. Both amounts are recorded in `_orders[commitmentA][T] = 1000` and `_orders[commitmentB][T] = 1000`; gateway holds `2000 T`.
2. `T` undergoes a negative rebase (e.g., an underlying slashing event), and the gateway's actual `balanceOf(gateway)` drops to `1500 T`, while `_orders[commitmentA][T]` and `_orders[commitmentB][T]` remain unchanged at `1000` each (per `placeOrder` in `evm/src/apps/IntentGatewayV2.sol:312-328`, which only captured `T`'s balance delta at deposit time).
3. Alice cancels her order first: `cancelOrder` → `_cancelSameChain`/`_cancelFromDest` → `_withdraw` reads `_orders[commitmentA][T] = 1000`, calls `IERC20(T).safeTransfer(Alice, 1000)` (`evm/src/apps/intentsv2/IntentsBase.sol:461-469`), succeeds; gateway balance falls to `500 T`.
4. Bob attempts to cancel/redeem his order for the recorded `1000 T`: `_withdraw` attempts `safeTransfer(Bob, 1000)` against a `500 T` balance — this reverts, and Bob has no other path to reclaim his escrow. His funds are permanently frozen in the contract.
