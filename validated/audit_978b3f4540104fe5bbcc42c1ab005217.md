### Title
Withdrawal status is matched only by `assetId`, causing status/hash misreport for batched same-token withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
The analog to Caviar's "unfaithful equality" bug class here is a status/hash misreport: `PoaBridge.describeWithdrawal` and the internal-utils `waitForWithdrawalCompletion` helper resolve which on-chain withdrawal record corresponds to a given local `WithdrawalIdentifier` by matching **only on `assetId`**, ignoring the `index` that is supposed to disambiguate multiple withdrawals of the same asset within one intent/transaction.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` matches an on-chain withdrawal record to a `WithdrawalIdentifier` purely by comparing `nep141:${w.data.near_token_id}` to `args.withdrawalParams.assetId`: [1](#0-0) 

`describeWithdrawal` calls this helper passing only `args.withdrawalParams.assetId`, and the caller-supplied `args.index` (which is generated per-bridge-route in `createWithdrawalIdentifiers`) is never used to disambiguate: [2](#0-1) 

The same pattern exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`, where `findMatchingWithdrawal` matches solely on `criteria.assetId`: [3](#0-2) 

The code comment explicitly documents the limitation but frames it only as an unsupported-scenario note, not as a security issue: "matches withdrawal by assetId, not by index" (test at `poa-bridge.test.ts:1054-1111`) confirms behavior — for two different withdrawals of the same asset, `.find()` returns the **first** matching withdrawal in the list regardless of which `index`/withdrawal the caller actually asked about.

The equality that should hold is: *the on-chain withdrawal record returned for withdrawal `index=i` of asset `X` must be the specific record corresponding to `i`'s destination/amount, not merely "any record for asset `X`"*. Because the match key is only `assetId`, if a caller batches two withdrawals of the same POA-bridged token (e.g., two different destination addresses/amounts in a single `processWithdrawal`/multi-withdrawal call), both `WithdrawalIdentifier`s (index 0 and index 1) resolve against the unordered `withdrawals` array using the same predicate, so `.find()` can return the same record for both queries, or return withdrawal #2's record when asked about withdrawal #1.

### Impact Explanation
This breaks the "status/hash reported == actual on-chain outcome for this specific withdrawal" equality. An integrator relying on `describeWithdrawal`/`waitForWithdrawalCompletion` to confirm settlement before crediting a user or releasing funds could:
- Report `completed` with a `transfer_tx_hash` belonging to a *different* withdrawal (wrong destination/amount), causing the integrator to credit/refund the wrong withdrawal as done.
- With two same-asset withdrawals to different destinations, the integrator could conclude both are settled based on one real completion, effectively double-crediting one leg while leaving the other unconfirmed.

This matches the specified High-severity category: "a status or hash misreport making an integrator credit or refund twice." The vulnerability is in the SDK's status-reporting logic itself, not a matter of trusting the POA relayer/API — the API returns correct data, but the SDK misattributes it to the wrong local withdrawal.

### Likelihood Explanation
Requires the caller to submit a batch of withdrawals containing more than one withdrawal of the *same* `assetId` in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call. This is a supported use case per `WithdrawalParams[]` batch APIs (`sdk.ts` `processWithdrawal`, `createWithdrawalIdentifiers`), not an artificial edge case, and the code comment itself acknowledges the scenario is unhandled ("multiple withdrawals of the same token in a single transaction are not supported"). No malicious actor action is required — it is a correctness defect triggered by ordinary legitimate batch usage, so likelihood is Medium-High for integrators that batch same-asset withdrawals.

### Recommendation
- Disambiguate matching using more than `assetId`: also match by `destinationAddress`, `amount`, and/or ordering (`index`) among withdrawals for the same asset, consuming matched records so they aren't reused for a subsequent identifier in the same batch.
- If POA's API cannot support disambiguation, at minimum track consumed indices/records across calls within a batch resolution pass so the same on-chain record is not attributed to two different `WithdrawalIdentifier`s, and explicitly reject/flag ambiguous batches (same asset, no distinguishing field) rather than silently returning a possibly-wrong status.
- Apply the fix in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (`findMatchingWithdrawal`) and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (`findMatchingWithdrawal`), keeping them consistent.

### Proof of Concept
1. Build a batch withdrawal request with two `WithdrawalParams` entries for the same `assetId` (e.g., `nep141:btc.omft.near`) but different `destinationAddress`/`amount`, submitted via `processWithdrawal`/`signAndSendWithdrawalIntent` (batch mode) — supported per `sdk.ts` `signAndSendWithdrawalIntent` and `createWithdrawalIdentifiers`.
2. Both withdrawals get `WithdrawalIdentifier`s with `index: 0` and `index: 1` respectively (per-route counters in `createWithdrawalIdentifiers`), but same `assetId`.
3. Call `describeWithdrawal` for each identifier. Internally, `poaBridge.httpClient.getWithdrawalStatus` returns an unordered list containing both on-chain withdrawal records for that asset.
4. `findMatchingWithdrawal` filters only by `nep141:${w.data.near_token_id} === assetId`, so `.find()` returns the same (first) record for both `index=0` and `index=1` queries — as directly reproduced by the existing test `"matches withdrawal by assetId, not by index"` at `poa-bridge.test.ts:1054-1111`, which demonstrates the API purposely returns two different `chain`/`transfer_tx_hash` entries for the same underlying `assetId` filter mechanism, and only the destination-specific `landingChain`/`address` — not `withdrawalParams.destinationAddress` — happens to align by luck in that test. Constructing the two withdrawals with matching `landingChain` (same destination chain) but different destination address/amount would return the wrong `transfer_tx_hash` for one of them.

```typescript
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```
