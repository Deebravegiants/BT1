### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and dispatch the webhook are read directly from unauthenticated HTTP headers. This breaks the identity binding `hmac(payload) == hmac(shop_header)`; the HMAC only proves the *body* came from Shopify using the app's shared `client_secret`, not that the *shop header* is bound to that body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are pulled straight from headers, which are never part of the signed data: [2](#0-1) 

`Registry.process` validates the HMAC over the (unbound) body, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` and dispatch to the handler: [3](#0-2) 

`HmacValidator.validate` signs/verifies with `Context.api_secret_key`, which is the single `client_secret` shared by the app across **all** installed shops (it is not shop-specific): [4](#0-3) 

Because the secret is shared across tenants and the signature covers only the body, a `(body, hmac)` pair that is valid for shop A's webhook delivery is also a valid `(body, hmac)` pair when replayed with a different `x-shopify-shop-domain` header claiming to be shop B. `Utils::HmacValidator.validate(request)` will still return `true` (the body/HMAC match), and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is attacker-controlled, i.e. `request.shop` is never checked to equal anything cryptographically bound to the signed bytes.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: an unprivileged attacker who legitimately receives (or can trigger, e.g. via `customers/data_request`, `app/uninstalled`, order/product webhooks in their own installed shop) one authentic `(raw_body, hmac)` pair from Shopify can replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header pointing at a victim shop. `Registry.process` will accept it as authentic (HMAC checks out) and invoke the host application's handler believing the event belongs to the victim shop, since the shop identity is not part of what was authenticated. Depending on the handler, this can lead to cross-tenant data being written/read under the wrong shop, uninstall/redact logic firing for the wrong tenant, or state corruption across tenants — satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high given the ease of exploitation: no access token, `api_secret_key`, or privileged account is required — only the ability to install the app on any shop (or otherwise obtain one valid webhook delivery) and the ability to POST to the app's public webhook endpoint with modified headers. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → header-trusted `shop`) is the sole out-of-the-box mechanism this gem provides for verifying and identifying webhook senders, so any host app relying on it as documented is exposed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop to the payload (e.g., verify the shop against session/install records looked up independently, not solely from the header) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical raw body and HMAC header to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `Utils::HmacValidator.validate(request)` at [5](#0-4)  passes because the body/HMAC pair matches (both shops share the app's `client_secret` via `Context.api_secret_key`).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the app's handler, which now believes the event genuinely originated from the victim shop.
