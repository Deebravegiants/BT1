This confirms the vulnerability. The webhook `Request#to_signable_string` (`lib/shopify_api/utils/verifiable_query.rb` + `lib/shopify_api/webhooks/request.rb`) returns only `@raw_body`, so the `HMAC-SHA256` computed by `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates the body bytes only — it never covers the `shop` field that `Registry.process` extracts via `request.shop` and hands to the app's handler as the tenant identifier in `WebhookMetadata`.

### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, excluding the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` therefore proves only "this body was HMAC'd with our app's client secret," never "this body came from shop X." Since a single app's client secret is shared across every shop that has installed the app, any merchant who can trigger a legitimate webhook to their own store can capture a valid `(body, hmac)` pair and replay it with an arbitrary victim `shop-domain` header, and `Registry.process` will treat it as authentic data for the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
It returns `@raw_body` only. The `shop` accessor is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, outside the signed payload: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly over `to_signable_string` and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` uses this validator as the sole authenticity gate, then trusts `request.shop` (unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

This is the direct structural analog of the `flashFee`/`changeFee` bug: an equality the code implicitly relies on — `hmac == HMAC(secret, body ∥ shop)` — actually only holds as `hmac == HMAC(secret, body)`. The `shop` field is acted upon (passed to the handler as the tenant key, as shown in the docs' recommended usage `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) without being bound by the same authentication check that gates the rest of the request.

### Impact Explanation
Because the app's `client_secret`/HMAC key is identical for every shop that installs the app (this is standard Shopify app architecture, not host misconfiguration), any authenticated merchant of the app is a valid holder of a `(raw_body, valid_hmac)` pair for *some* topic. By resending that exact body with the `shop-domain` header swapped to a victim's `myshopify.com` domain, `HmacValidator.validate` still succeeds (it never looked at the shop header), and the handler receives forged data attributed to the victim shop. Any app that uses `data.shop` from `WebhookMetadata` to look up/update per-tenant records (the documented, expected usage pattern) can have its per-tenant state corrupted or trigger tenant-scoped side effects (e.g., fake `orders/create`, `app/uninstalled`, GDPR webhooks) under the identity of a shop the attacker does not control. This is a cross-tenant data-integrity/authentication breach within the meaning of the rules ("cross-tenant access").

### Likelihood Explanation
Any user of the target app is normally entitled to trigger real webhooks for their own shop (e.g., by placing an order, updating a product, etc.), giving them a supply of valid `(body, hmac)` pairs without any privileged access. Forging the header and replaying the POST requires nothing beyond standard HTTP tooling — no `api_secret_key`, no leaked credentials, no TLS interception. The only constraint is that the replayed body's content must make sense for the victim shop's data model, which is easily satisfiable for many webhook topics (e.g. `app/uninstalled`, `shop/update`, or GDPR webhooks whose bodies are shop-scoped but not merchant-specific).

### Recommendation
Bind the shop identity into the HMAC-covered material, or otherwise cryptographically bind `shop` to the signed body before trusting it. Since the gem cannot change what Shopify signs, at minimum documentation/API should make clear that `request.shop` is unauthenticated, and the library should provide (or the `Request`/`Registry.process` contract should require) a way to correlate `request.shop` against the shop associated with the `Session`/webhook subscription that was registered for that specific `webhook_id`/topic, rather than trusting the header value directly. Concretely, `Registry.process` should not hand out `request.shop` as trusted tenant data without an explicit warning, and ideally should require the caller to supply the expected shop (from the session that registered the webhook) to cross-check against `request.shop`.

### Proof of Concept
1. App merchant A installs the app on `attacker.myshopify.com` and performs an action that triggers a real webhook, e.g. `orders/create`. The app's webhook endpoint receives:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid_hmac_over_body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   <body JSON>
   ```
2. Merchant A captures `<body JSON>` and `<valid_hmac_over_body>` (e.g., via a proxy/logging tool they control on their own endpoint).
3. Merchant A replays the exact same request to the app's webhook endpoint but changes only:
   ```
   X-Shopify-Shop-Domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) and it matches — validation succeeds: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: ..., ...)`, and the app processes forged data as if it originated from `victim.myshopify.com`.
