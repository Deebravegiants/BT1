### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, but the `shop` value passed to the app's handler is read from an HTTP header that is never included in the signed material. This breaks the equality `hmac-authenticated bytes == bytes the shop identity is derived from`, letting anyone who can produce a validly-HMAC'd body (e.g. the owner of any shop that has the app installed, who legitimately receives real webhook deliveries) relabel that payload as coming from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: `lib/shopify_api/webhooks/request.rb:35-38`. `ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC solely against this signable string using the app's `api_secret_key`: `lib/shopify_api/utils/hmac_validator.rb:12-31`. Meanwhile, `Request#shop` is derived purely from the `x-shopify-shop-domain`/`shopify-shop-domain` header, with no cryptographic binding to the body or its HMAC: `lib/shopify_api/webhooks/request.rb:20-23, 67-70`.

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` and then trusts `request.shop` to build `WebhookMetadata` that is handed to the app's handler: `lib/shopify_api/webhooks/registry.rb:189-199` and `lib/shopify_api/webhooks/webhook_handler.rb:6-12`. Because the header is excluded from the signable string, the equality that should hold — "the shop whose secret authenticated this body" == "the shop the handler is told this body belongs to" — is not enforced. Any party that can obtain one genuine, validly-HMAC'd webhook body from Shopify (trivial: install the app on their own store and trigger any webhook event) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the untouched body against the app's shared `api_secret_key`, and `Registry.process` passes the attacker-chosen `shop` straight through to `WebhookMetadata`/the handler.

### Impact Explanation
This is a cross-tenant identity-binding bypass carried out entirely with the gem's own webhook-processing logic and no possession of the app's `api_secret_key`, access token, or any victim credentials. A malicious merchant with the app installed on their own store can cause the host application's webhook handler to process/attribute data under a victim shop's identity (e.g., trigger shop-scoped side effects, cache updates, entitlement changes, or logging keyed by `data.shop` for a shop they do not control), since `WebhookMetadata#shop` is fully attacker-controlled while the HMAC only vouches for the body.

### Likelihood Explanation
High reachability: the attacker only needs (a) their own real store with the app installed, from which they can legitimately obtain a webhook whose body and HMAC were generated by Shopify with the app's real secret, and (b) the ability to POST an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no secret material, tokens, or privileged access required.

### Recommendation
Bind the shop identity into the signed/verified material or verify it out-of-band against a trusted source (e.g., validate that `request.shop` matches an installed/known shop record independent of the header, or require the shop domain to be embedded in and verified as part of the HMAC-covered payload) before constructing `WebhookMetadata` and dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw request body and the genuine `x-shopify-hmac-sha256` value Shopify sent to the app's webhook URL.
2. Attacker resends that exact `raw_body` and `x-shopify-hmac-sha256` to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present): `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and matches the (unmodified) genuine HMAC: `lib/shopify_api/webhooks/registry.rb:189-190`, `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` even though the body content is attacker's own: `lib/shopify_api/webhooks/registry.rb:198-199`.
6. The app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` bound to attacker-supplied body content, despite a "valid" HMAC. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
