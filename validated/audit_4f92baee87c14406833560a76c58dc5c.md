Found the exploitable break in `TokenExchange.exchange_token`: the `client_secret` is sent to a host derived from an attacker-influenceable value that is **not covered by the JWT signature verification the same way the other flows are protected**, and — critically — is not passed through `ShopValidator.sanitize!` before being used to build the request host, unlike every sibling method (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`).

### Title
`client_secret` sent to unsanitized host derived from JWT `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the HTTP client's target host directly from `jwt_payload.shop` (the JWT `dest` claim, stripped of `https://`) without ever passing it through `Utils::ShopValidator.sanitize!`, the check every other OAuth credential-exchange method (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) applies to the `shop` value before using it to construct a request host.

### Finding Description
`JwtPayload#shop` simply returns `@dest.gsub("https://", "")` with no format restriction to a Shopify-owned domain: [1](#0-0) 

In `exchange_token`, this unsanitized value becomes `dest_shop`, is used to build `shop_session`, and that session's `.shop` is used by `HttpClient` to construct the request's base URI, to which `client_id`/`client_secret` are POSTed: [2](#0-1) [3](#0-2) 

Every sibling credential-exchange flow instead calls `Utils::ShopValidator.sanitize!(shop)` first, which restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The equality this breaks: **host that receives the `client_secret` == host validated as a trusted Shopify domain**. `exchange_token` sends the secret to whatever `dest_shop` resolves to, while validation (`sanitize!`) is applied everywhere else. The only guard on `dest_shop` is `JwtPayload`'s signature/`aud` check — that check authenticates that *the app's own secret* signed the token, but it does not constrain what the `dest` claim string can contain as a hostname. `JWT.decode` and the `aud == Context.api_key` check do not validate `dest` against `TRUSTED_SHOPIFY_DOMAINS` at all — that responsibility is delegated (inconsistently) to `ShopValidator` at the caller site.

### Impact Explanation
If a session token with an attacker-controlled `dest` claim can be presented to `exchange_token` (e.g., via a self-issued/relayed session token in contexts where the app's own `api_secret_key` is used to sign, or via any path where a token from a different aud/environment is accepted before this check fires), the app's `client_id`/`client_secret` are POSTed to a host of the attacker's choosing — classic SSRF with credential exfiltration (`client_secret` leaves the trust boundary). This matches the **High: SSRF with the app's credentials / credential leakage** impact category.

### Likelihood Explanation
Exploitability strictly requires a validly-signed JWT with `aud == api_key` but an attacker-influenced `dest` claim — this depends on how `session_token` is sourced by the host application (App Bridge normally supplies well-formed `dest` values). Given the rules exclude findings that depend on "the host application ignoring this gem's documented API," and given `JwtPayload`'s HMAC verification does bind `dest` cryptographically to the token issued by Shopify (so under normal operation Shopify itself controls `dest`), the realistic likelihood inside this gem alone is low. However, the **inconsistency** — `sanitize!` applied to 3 of 4 sibling methods but omitted here — is a genuine defense-in-depth gap and root-cause bug in this gem regardless of how session tokens are sourced upstream.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent restricted-domain check) to `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`, consistent with `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`.

### Proof of Concept
1. Obtain/construct a JWT signed with the app's `api_secret_key` where `aud` equals `Context.api_key` but `dest` is set to `https://attacker.example.com` (feasible wherever the session token issuance path is not the standard App Bridge flow trusted purely on Shopify's control of `dest`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. Observe `Clients::HttpClient` construct `@base_uri = "https://attacker.example.com"` (per `lib/shopify_api/clients/http_client.rb:18`) and POST `{client_id, client_secret, ...}` to `attacker.example.com/admin/oauth/access_token`, leaking the app's `client_secret`.
