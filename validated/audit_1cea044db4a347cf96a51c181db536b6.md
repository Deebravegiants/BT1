### Title
`Webhooks::Request` binds only the raw body to the HMAC signature while `shop`, `topic`, and `webhook_id` are taken from unauthenticated headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw request body. However, the tenant-identifying fields `shop`, `topic`, and `webhook_id` — which are handed unverified to app webhook handlers — come from HTTP headers that are never included in the HMAC computation, breaking the binding between "bytes verified" and "identity claimed."

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` returns solely `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the signed payload: [3](#0-2) 

`Registry.process` verifies only the HMAC of the request, then immediately trusts the unauthenticated header-derived `shop` and `topic` values to route and label the payload delivered to the app's handler: [4](#0-3) 

The equality the gem is supposed to enforce is: `shop_that_the_HMAC_authenticates == shop_delivered_to_handler`. In reality, the HMAC only authenticates the body bytes; `shop` (and `topic`/`webhook_id`) are parsed from headers that are never fed into `compute_signature`. Any request whose body matches a previously-observed, validly-signed body (e.g., a webhook payload legitimately delivered to the attacker's own shop) can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the HMAC check will still pass because it never covered that field.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker in control of one shop (a valid, unprivileged installer of the merchant's app) can capture a genuine webhook body sent to their own shop and resend it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will construct `WebhookMetadata` labeling the payload as belonging to whatever shop the attacker put in the header, feeding attacker-controlled tenant identity into the host app's handler. Any app that trusts `data.shop` from `WebhookMetadata` (as documented/intended usage) to select per-tenant records can be tricked into applying another shop's webhook data cross-tenant, satisfying the "cross-tenant access" criteria (Critical).

### Likelihood Explanation
Likelihood is limited by the requirement that the attacker possess or predict a validly-signed body for some content it wants delivered under a different `shop` label — trivially satisfied since the attacker can be a legitimate merchant/install of the very same app, and thus routinely receives HMAC-signed webhook bodies for their own tenant that they can freely replay with a forged `shop-domain` header. No secret, TLS interception, or privileged account is needed beyond ordinary use of the app as any tenant.

### Recommendation
Include the identity-carrying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable content for webhook requests, or otherwise cryptographically bind them (e.g., derive `shop` only from a signed source, never from a raw header) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. As shop `attacker-shop.myshopify.com`, install the target app and let Shopify send it a legitimate webhook, e.g. `orders/create` with body `raw_body` and headers including `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`.
2. Capture `raw_body` and the valid `hmac` value (both directly observable/producible by the attacker as a legitimate tenant, no secret needed).
3. Resend a forged HTTP request to the app's webhook endpoint using the **same** `raw_body` and `hmac` header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds because it only hashes `raw_body` [2](#0-1) .
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` [5](#0-4)  and the app's handler processes attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
