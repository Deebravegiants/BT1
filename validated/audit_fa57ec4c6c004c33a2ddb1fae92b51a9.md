## Analysis

The Filecoin incident describes an attacker flooding a node with messages that bypass filtering/whitelisting, forcing the victim node to spend unbounded compute resources processing them. The closest reachable analog in this codebase is the Gateway's legacy web-API message path, which requires only a valid ECDSA signature (any keypair, not an allowlisted one) and then fans the request out to every DON node — with an explicit, unresolved `TODO` admitting the missing allowlist/rate-limit check.

### Title
Missing sender allowlist/rate-limit on Gateway legacy user messages causes unauthenticated fan-out to all DON nodes - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` accepts any structurally-valid, self-signed message (signature can be generated by anyone, since `Message.Validate()` only verifies signature format/recoverability, not sender identity against any allowlist) and unconditionally broadcasts it to every node in the DON before any allowlist or rate-limit check is applied.

### Finding Description
The gateway's public, unauthenticated HTTP endpoint (`gateway.ProcessRequest`) accepts a raw JSON message, decodes it, and for legacy (DonID-based) requests only calls `msg.Validate()`: [1](#0-0) 

`Message.Validate()` checks field lengths and recovers a signer address from the signature — it never checks that signer against any allowlist; anyone can generate an ECDSA keypair and self-sign a message: [2](#0-1) 

The resolved handler's `HandleLegacyUserMessage` performs only payload-decoding, timestamp-freshness, and method checks. Immediately before broadcasting to nodes, the code contains an explicit acknowledgment that allowlist and rate-limiting are not implemented: [3](#0-2) 

It then saves a callback and sends the request to **every** node in the DON: [4](#0-3) 

This mirrors the Filecoin bug class: an attacker sends a flood of self-authenticated-looking messages through the gateway's filtering path, and because there is no sender allowlist or per-sender rate limit on this path (only a node-side rate limiter exists for the separate `HandleNodeMessage`/outgoing path, not for inbound legacy user messages), every message is forwarded to all DON node members, consuming their processing capacity. The test suite even documents this gap: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` in `handler_test.go`.

### Impact Explanation
An unprivileged, unauthenticated actor (anyone with network access to the gateway's HTTP endpoint) can generate an unlimited number of distinct self-signed messages and cause the gateway to broadcast each one to all DON nodes. This consumes node compute/network resources handling and responding to spurious triggers, degrading availability of legitimate workflow triggers for the DON — directly analogous to the Filecoin incident where malicious messages bypassing the whitelist filter consumed Lotus node computation and degraded/blocked normal task processing. This is a Medium severity availability/DoS issue rather than fund loss or key disclosure.

### Likelihood Explanation
Likelihood is high for triggering the fan-out (no authentication barrier beyond generating a valid signature, which is trivial and free), though the practical severity depends on deployment-specific factors (whether `ExternalInitiatorsEnabled`/this legacy webapi path is actually enabled in production DON configs, and how expensive each node's processing of a `web_api_trigger` is). The `savedCallbacks` map does have max-size/prune protections against unbounded memory growth on the gateway side, but nothing protects the DON nodes from receiving a flood of forwarded requests.

### Recommendation
- Implement the sender allowlist check referenced by the existing `TODO` comment before forwarding legacy user messages to DON nodes, keyed by `msg.Body.Sender` and validated against a per-DON allowlist analogous to what is used elsewhere in the gateway (e.g., `AllowListBasedAuth` in the vault gateway handler).
- Add a per-sender and/or global rate limiter on the legacy `HandleLegacyUserMessage`/`HandleJSONRPCUserMessage` ingestion paths, mirroring the `nodeRateLimiter` already applied to outbound node messages.
- Reject requests from unrecognized senders before performing any DON fan-out, and add metrics/alerts on rejected/rate-limited sender volume.

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no need to be a known/allowlisted DON member or workflow owner).
2. Construct a `Message` with `MethodWebAPITrigger`, a fresh `MessageID`, current `Timestamp`, and sign it with `Message.Sign(privateKey)`.
3. POST the message to the gateway's public HTTP endpoint with a valid `DonID`, repeating with new random keys/`MessageID`s at high volume.
4. Each request passes `Message.Validate()` (only checks signature format/recoverability) and `HandleLegacyUserMessage`'s payload/timestamp/method checks — no allowlist or rate limit rejects it — and is forwarded via `don.SendToNode` to every member of `donConfig.Members`, consuming their processing resources.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
