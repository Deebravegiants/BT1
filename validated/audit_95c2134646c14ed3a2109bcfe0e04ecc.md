Confirmed root cause. The webhook signature only covers the raw request body, while `topic`, `shop`, `api_version`, and `webhook_id` are taken directly from unauthenticated headers and handed to the app's handler as trusted, per-tenant identity data.

### Title
Webhook `shop` (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw HTTP body [1](#0-0)  and `Utils::HmacValidator.validate` verifies the `hmac` header against exactly that string [2](#0-1) . However `Registry.process` trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` — all parsed straight from HTTP headers — and forwards them unchanged to the app's webhook handler as the authoritative tenant/event identity [3](#0-2) . None of these header values are part of the HMAC-covered bytes, so they can be altered without invalidating the signature check.

### Finding Description
The binding that should hold is: `shop value verified by HMAC == shop value delivered to the app's business logic`. In this gem that equality does not hold — the HMAC only authenticates the JSON body bytes (`@raw_body`), never the `x-shopify-shop-domain` (or `shopify-shop-domain`) header that `WebhookMetadata#shop` is populated from [4](#0-3)  and [5](#0-4) .

Because a single `api_secret_key` is shared across every shop installed on a given app, any shop that has installed the app can generate a body+HMAC pair that is cryptographically valid for that shared secret (e.g. by triggering a real webhook event on their own store, or by using the public webhook payload format with a body they fully control, since the HMAC is over body bytes only — not over any request line or headers binding it to a specific topic/shop). That valid `(raw_body, hmac)` pair can then be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to name a different, victim shop. `Utils::HmacValidator.validate` will still succeed, since it never inspects the shop header [6](#0-5) , and `Registry.process` will dispatch the spoofed `shop` value straight into `WebhookMetadata` for the handler to act on [3](#0-2) .

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: an app built on `ShopifyAPI::Webhooks` cannot rely on `WebhookMetadata#shop` being the shop that actually produced the signed payload. A merchant who legitimately installs the app on their own shop can forge webhook deliveries that appear to originate from a different, victim shop, causing the host application to write, update, or act on data under the wrong tenant's identity — a cross-tenant access/integrity violation attributable to this gem's own signature-verification design rather than host misuse.

### Likelihood Explanation
Exploitation only requires an attacker to be a legitimate installer of the target app on any shop (a low bar for public/embedded apps), plus the ability to POST a crafted HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or Shopify infrastructure is needed beyond what a normal merchant install grants.

### Recommendation
Include the tenant/event-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload, or bind them cryptographically to the signature (e.g., verify them against session/shop records established at install time) instead of trusting header values that sit outside the HMAC computation in `to_signable_string`. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated and that host applications must independently verify the shop against their own registered-shop list before trusting webhook data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a real webhook delivery with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` — valid because the app secret is shared across all shops.
2. Attacker resends the same `B` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (body only) and it matches, so validation passes [1](#0-0) .
4. `Registry.process` calls `handler.handle` with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: B ...)` [7](#0-6) , causing the host app to process attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
