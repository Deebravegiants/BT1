This confirms the claim exactly as described. `HandleLegacyUserMessage` writes `h.savedCallbacks[msg.Body.MessageID]` unconditionally with no existence/collision check [1](#0-0) , whereas `Message.Validate()` only checks length/null-suffix, not uniqueness or entropy [2](#0-1) , and the v2 handler explicitly guards against exactly this collision with an `ErrConflict` rejection [3](#0-2) .

Audit Report

## Title
Legacy gateway user message handler allows request-ID collision to hijack or deny another user's saved callback - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
`HandleLegacyUserMessage` stores each pending callback in the shared `savedCallbacks` map keyed only by the attacker-supplied `MessageID`, with no check for an existing in-flight entry before overwriting it. An unprivileged caller can reuse another still-pending request's `MessageID` to overwrite that entry, causing the eventual DON response to be delivered to the attacker's callback instead of the legitimate requester's, while the original caller's request times out.

## Finding Description
`ProcessRequest` validates the incoming legacy `Message` via `msg.Validate()` and then dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [4](#0-3) . `Validate()` only checks that `MessageID` has length 1–128 and doesn't end in a null byte — it enforces no uniqueness or entropy requirement [2](#0-1) . Inside `HandleLegacyUserMessage`, the handler performs an unconditional map write:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 
There is no lookup of an existing, non-expired entry before this write, so a second request bearing the same `MessageID` silently replaces the first caller's stored callback. By contrast, the newer v2 `httpTriggerHandler.setupCallback` explicitly checks `if _, found := h.callbacks[requestID]; found` and rejects the request with `ErrConflict` [3](#0-2) , confirming this collision-guard is a known, intentional mitigation pattern that the legacy path omits.

## Impact Explanation
This maps to the in-scope "cross-user response corruption" / gateway request impersonation category: an unprivileged caller can hijack the DON's response meant for another user's in-flight request (receiving data intended for someone else) and/or deny that user their response (timeout). The `savedCallback` bookkeeping is a shared, capacity-bounded resource (`MaxSavedCallbacks`), and the missing collision guard is a genuine, code-level gap relative to the fixed analog in the v2 handler.

## Likelihood Explanation
Exploitability is fully gated on the attacker knowing or guessing a victim's in-flight `MessageID` within the callback window (default 120s, `CallbackMaxAgeSec`). The claim itself acknowledges this dependency ("Exploitability depends on the attacker knowing or guessing a victim's in-flight MessageID... If client-generated MessageIDs are predictable... likelihood is meaningful; if IDs are always cryptographically random ... exploitability is lower"). No evidence is presented that any real client (chainlink node, gateway SDK, or referenced integration) generates predictable/sequential/observable `MessageID`s — this is speculative. Additionally, exploitation requires producing a validly signed `Message` (since `Validate()` and downstream signature checks apply to every message, per `ValidatedRequestFromMessage` in `HandleLegacyUserMessage`), meaning the attacker must be a legitimate signer of their own message, not simply an anonymous network client with no keys — this narrows, but does not eliminate, the "unprivileged" framing, since any keyholder able to call the endpoint counts as unprivileged for this system's threat model.

The finding is a real defense-in-depth gap and the code behaves exactly as described, but the report itself frames the likelihood as conditional and unproven ("remains a real defense-in-depth gap regardless of current client behavior" — i.e., no concrete demonstrated instance of predictable IDs in this codebase). This is consistent with a valid but likelihood-limited finding rather than a fabricated one.

## Recommendation
In `HandleLegacyUserMessage`, before inserting into `savedCallbacks`, check for an existing non-expired entry keyed by `msg.Body.MessageID` and reject the request (mirroring `httpTriggerHandler.setupCallback`'s `ErrConflict` behavior) instead of silently overwriting it.

## Proof of Concept
1. User A sends a signed legacy `Message` with `MessageID = "shared-id"` to `/user`; gateway stores `savedCallbacks["shared-id"] = <A's callback>` per [1](#0-0)  and forwards to DON members.
2. Before any DON response for `"shared-id"` arrives, attacker B (who must also produce a validly signed `Message`, since signature verification happens upstream) sends their own message with the same `MessageID = "shared-id"`, overwriting `savedCallbacks["shared-id"]` with B's callback.
3. The DON's response for `"shared-id"` is delivered to B's callback instead of A's; A's original request times out.
A Go unit test in `handler_test.go` sending two `HandleLegacyUserMessage` calls with identical `MessageID` and asserting the second overwrites the first (no error returned) would demonstrate the missing guard.
