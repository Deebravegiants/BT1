Confirmed: `apply_delegate_action` in `runtime/runtime/src/actions.rs` only checks the delegate signature, `max_block_height`, `sender_id`/receiver match, and access-key nonce — no chain/genesis/network identifier is ever checked against the delegate action's signed payload.

### Title
Meta-transaction `DelegateAction`/`DelegateActionV2` signatures lack chain/network binding, enabling cross-chain replay of relayed actions - ([File: core/primitives/src/action/delegate.rs])

### Summary
NEAR's meta-transaction feature (NEP-366/NEP-611) lets a user sign a `DelegateAction` that a relayer wraps into an outer `SignedTransaction` and submits on the user's behalf. The outer `SignedTransaction` is bound to a specific chain via its `block_hash` field (checked in `chain_validate`), but the inner `SignedDelegateAction`/`VersionedSignedDelegateAction` signature covers only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — never a chain/genesis/network identifier. This is structurally identical to the reported bug class: a merkle-leaf/signed-payload hash that omits any chain-specific binding, allowing the same signed authorization to be replayed on a different but state-compatible chain.

### Finding Description
The signed hash for a delegate action is computed by `DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash`, which wraps the message in a `SignableMessage` and hashes `discriminant || msg`: [1](#0-0) 

The `SignableMessage` discriminant only distinguishes *message type* (NEP-366 vs NEP-611), not *network/chain*: [2](#0-1) 

Verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) only re-derives this same chain-agnostic hash and checks the ed25519/other signature against it: [3](#0-2) [4](#0-3) 

At execution time, `apply_delegate_action` performs exactly four checks on the inner delegate action: signature validity, `max_block_height` vs current block height, `sender_id` matching the outer transaction's receiver, and access-key/nonce validation — nothing chain-specific: [5](#0-4) 

Only the *outer* `SignedTransaction` carries a `block_hash`, which is validated for freshness/liveness against the local chain (`chain_validate` / `Expired` error), as shown in the replay-protection test: [6](#0-5) 

Because the outer transaction's chain binding is independent from the inner `SignedDelegateAction`'s signature, any party who observes a broadcast `SignedDelegateAction` (it is public once broadcast, and a relayer/observer can extract it from the transaction bytes) can re-wrap the *same* inner delegate action bytes in a *new* outer `SignedTransaction` — with the relayer's own valid nonce and a `block_hash` from a different, state-compatible NEAR chain (e.g., a forked/rolled-back chain, a shadow/canary chain launched from a mainnet state dump via `neard view-state dump-state`, or any two chains sharing the same account/access-key state at the fork point) — and submit it there. As long as the sender's access-key nonce for that public key has not yet been consumed on the other chain, `apply_delegate_action` will accept and execute it, since nothing in the check set differentiates the two chains.

### Impact Explanation
This allows unauthorized replay of a signed meta-transaction's actions (e.g., token transfers, function calls, key/permission changes) on a second, state-compatible NEAR chain that the original signer never intended to interact with, resulting in unauthorized state/balance changes on that chain executed with the sender's authority. The severity is bounded by the requirement that a second chain shares state (nonce) with the origin chain at the point of divergence — this is the same "fork" precondition present in the original report, and is realistic for NEAR-based scenarios such as mirrored/forked test networks (`tools/mirror`) or a chain restarted from a state dump before any transactions using that access key have been submitted on the new chain.

### Likelihood Explanation
Exploitation requires (a) a chain-fork/state-mirroring scenario where two NEAR chains share account state, and (b) the targeted access key's nonce not yet advanced on the second chain for the replayed key. `tools/mirror` documents exactly this kind of forked-chain workflow, and any node operator spinning up a shadow/canary/testnet from a mainnet state dump before rotating keys would be exposed. The delegate action itself is broadcast as plaintext bytes (visible to any relayer or network observer), so capturing it for replay requires no special access.

### Recommendation
Include a chain-specific/network-specific identifier in the `SignableMessage`/`DelegateAction` payload that is hashed and signed (e.g., genesis hash or a configured network ID), and verify it against the executing chain's own identifier inside `apply_delegate_action`, analogous to how the outer `SignedTransaction.block_hash` is chain-validated. This closes the domain-separation gap and prevents a captured `SignedDelegateAction` from being valid on any chain other than the one it was created for.

### Proof of Concept
1. Chain A and Chain B share identical state (e.g., Chain B forked from Chain A's state dump via `tools/mirror`/`view-state dump-state`), with account `alice.near`'s access key nonce at value `N` on both chains.
2. Alice signs a `DelegateAction{sender_id: alice.near, receiver_id: bob.near, actions: [Transfer], nonce: N+1, max_block_height: H, public_key: alice_key}` and hands it to relayer R1 for submission to Chain A only, per `DelegateAction::get_nep461_hash`/`sign` ( [7](#0-6) ).
3. R1 wraps it in an outer `SignedTransaction` with a Chain-A `block_hash` and submits it; it succeeds on Chain A, advancing the nonce there to `N+1`.
4. An attacker (or a colluding relayer) extracts the identical `SignedDelegateAction` bytes from the Chain-A transaction/receipt before Chain B's copy of the nonce is advanced, wraps it in a fresh outer `SignedTransaction` with a valid Chain-B `block_hash` and its own valid nonce, and submits it to Chain B.
5. Chain B's `apply_delegate_action` ( [8](#0-7) ) finds the signature valid, `max_block_height` not yet exceeded, sender/receiver matching, and nonce `N+1` still unused — so it executes the transfer on Chain B without Alice's consent for that chain.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
