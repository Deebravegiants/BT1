### Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` is silently trapped instead of refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it for the exact fee-token amount via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. This Uniswap function only spends `post.fee`/`get.fee`/`amount` worth of ETH and refunds any unused ETH — but the refund goes to `msg.sender` of the swap call, which is `EvmHost` itself, not the original end user who supplied `msg.value`. `EvmHost` has no `receive()`/`fallback()` and no logic to forward that refunded excess back to the caller, so any overpayment of native token is permanently stuck in the contract.

### Finding Description
In `dispatch(DispatchPost memory post)`:
```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
``` [1](#0-0) 

The same pattern exists in `dispatch(DispatchGet memory get)` [2](#0-1)  and in `fundRequest()`:
```solidity
function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            amount, path, address(this), block.timestamp
        );
    } else {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
    }
    ...
}
``` [3](#0-2) 

`UniswapV2Router02.swapETHForExactTokens` only consumes the ETH equivalent of the requested output amount (`post.fee`, `get.fee`, or `amount`) and refunds the remainder of `msg.value` to whoever called it — in this case `EvmHost`, since `EvmHost` itself calls the router with `{value: msg.value}`. Unlike the SDK-level wrappers such as `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()`, which carefully track `msgValue` and forward only the exact remainder to `dispatch{value: msgValue}` [4](#0-3) , and unlike `IntentGatewayV2.placeOrder`, which explicitly refunds excess native token to the user (confirmed by `testPlaceOrder_RefundsExcessNativeToken`) [5](#0-4) , `EvmHost.dispatch()` and `fundRequest()` have no mechanism to return the Uniswap refund to the original caller. There is also no `receive()`/`fallback()` in `EvmHost.sol`, and no accounting variable tracks "excess ETH owed to caller."

Any caller who supplies `msg.value` greater than what is required to purchase `post.fee`/`get.fee`/`amount` worth of fee token — for example, due to price-slippage buffering, a stale quote, or simple user/integration error — has the difference swapped, refunded to the `EvmHost` contract address by the router, and then permanently absorbed into the contract's ETH balance with no withdrawal path for the depositor. This directly mirrors the "amount sent" data-validation issue in the reference report: functions accept native token without properly accounting for/returning unused amounts, causing user funds to become permanently trapped.

### Impact Explanation
This is reachable by any unprivileged caller of `EvmHost.dispatch()` (used by every ISMP-dispatching app, including token bridges and the LayerZero adapter) or `fundRequest()` with a single transaction and overpaid `msg.value`. The excess ETH is permanently locked in the `EvmHost` contract with no code path to reclaim it for the depositor, constituting a permanent freezing-of-funds condition for the overpaid amount. Because `dispatch()` is the primary entry point used by numerous downstream apps (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2` predispatch flows, LayerZero endpoint `send()`), any integrator or user who doesn't compute the exact swap amount precisely (which is essentially impossible on-chain due to price movement between quote and execution) risks losing the excess as unrecoverable funds.

### Likelihood Explanation
Likely to occur in practice: because `swapETHForExactTokens` requires supplying enough ETH to cover slippage, callers are commonly encouraged/forced to over-supply `msg.value` as a buffer, and any excess beyond the exact amount consumed is stranded. This is a straightforward and repeatable occurrence, not requiring any adversarial setup — ordinary usage patterns (buffered gas/price estimation) trigger it.

### Recommendation
- Track the actual ETH consumed by the swap (e.g., use `address(this).balance` before/after the swap call, or capture the router's return value from `swapETHForExactTokens`, which returns the array of amounts actually swapped) and refund any leftover `msg.value` directly to `_msgSender()` within `dispatch()` and `fundRequest()`, mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder`.
- Alternatively, add a `receive()`/sweep mechanism explicitly reserved for forwarding unspent swap proceeds back to the original payer within the same transaction.
- Add regression tests analogous to `testPlaceOrder_RefundsExcessNativeToken` for `EvmHost.dispatch()` and `fundRequest()` to assert that any `msg.value` beyond what the swap consumes is returned to the caller.

### Proof of Concept
1. Alice calls `EvmHost.dispatch(DispatchPost memory post)` with `post.fee = 100` (fee-token units) and sends `msg.value = 1 ether` (over-provisioning to be safe against slippage), per [1](#0-0) .
2. `swapETHForExactTokens{value: 1 ether}(100, path, address(this), deadline)` executes and only spends, say, `0.01 ether` worth of ETH to buy exactly 100 fee tokens; the router refunds the remaining `0.99 ether` to `msg.sender` of the swap call, which is the `EvmHost` contract itself (not Alice).
3. `EvmHost` has no logic to detect or forward this `0.99 ether` refund to Alice; it silently becomes part of the contract's native balance.
4. Alice's request is dispatched and her fee is deducted correctly from the swapped tokens, but she has permanently lost `0.99 ether` with no way to recover it — reproducing the "Bob sends 10 tez and loses them" scenario from the reference report, but for every user of `dispatch()`/`fundRequest()` who over-supplies `msg.value`.

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }
