This confirms the design intent: the gem's own documentation states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` line 125), and `shop` is documented as a trusted identity field passed to the host app's handler (`docs/usage/webhooks.md` lines 12-14, 26). This is exactly the trust boundary that the HMAC binding fails to enforce.

### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw body, while `request.shop` (taken from the `shop-domain`/`x-shopify-shop-domain` header) is never part of the signed material. Any caller who possesses one genuine `(body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving a real webhook at their own endpoint — can replay that exact pair to the app's shared webhook endpoint while substituting an arbitrary `shop-domain` header. The gem accepts this as fully authentic and hands the forged shop identity straight to the host app's handler.

### Finding Description
The equality the gem is supposed to enforce is:
`shop identity acted upon by the handler == shop identity authenticated by the HMAC`

In practice:
- `Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac`. [1](#0-0) 
- For webhook requests, `to_signable_string` is defined as `@raw_body` only, with no shop, topic, or webhook-id bound in. [2](#0-1) 
- `shop` is read straight from an attacker-suppliable header with no cross-check against the signed body. [3](#0-2) 
- `Registry.process` performs exactly one authenticity check — the HMAC — then immediately forwards `request.shop` (and `request.topic`) into the handler as trusted values. [4](#0-3) 

Because the app's `api_secret_key` (used to compute the HMAC) is shared across every merchant that installs the app — it is not a per-shop secret — any merchant who installs the app legitimately receives, at their own webhook endpoint, real `(body, hmac)` pairs signed with that shared secret. That merchant can capture such a pair and re-POST it to the app's webhook route with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the host app's handler with `WebhookMetadata#shop` set to the victim's domain, `body` set to attacker-chosen (real, previously-observed) content, for the topic that was originally captured.

### Impact Explanation
This breaks the shop/tenant identity binding that the HMAC is meant to establish, allowing an unprivileged (but app-installing) internet user to make the host application believe a webhook came from a shop it did not come from — a cross-tenant identity confusion. Depending on how the host app's handler keys its logic off `data.shop` (session lookup, `app/uninstalled` teardown, `shop/redact` GDPR erasure, `customers/data_request`, inventory/order side effects, etc.), this can drive state changes or data operations against a shop the attacker does not control and never had a matching, freshly-signed webhook for. This matches the Critical "cross-tenant access" category: the gem itself provides no way for a host application to detect the spoof, since it explicitly documents that `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`) when in fact only the body is verified.

### Likelihood Explanation
Likelihood is high for any app that is publicly installable (the common case for Shopify apps): becoming an "attacker" only requires installing the app on any store, which is an unprivileged, unauthenticated action from Shopify's perspective. Capturing a `(body, hmac)` pair requires nothing more than receiving one webhook at the attacker's own registered endpoint (which they control) and reading the raw request. No access token, `api_secret_key`, or account privilege escalation is needed — only a normal app install and the ability to send an HTTP request with custom headers to the shared webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically tie the header-derived `shop` to the payload before trusting it. Since Shopify's real webhook HMAC only covers the raw body by design, the gem should instead maintain a mapping from webhook subscription/registration to expected shop (established during OAuth/registration, itself HMAC/session-bound) and reject/ignore any `shop-domain` header value that the app has no active, verified session for — rather than passing an arbitrary attacker-controlled header value straight to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers the same webhook topic (e.g. `app/uninstalled`) that the target app subscribes to.
2. Shopify delivers a legitimate webhook to the attacker's own endpoint:
   - Body: `{"id": ...}` (JSON body content for the topic)
   - Header `X-Shopify-Hmac-Sha256`: `HMAC-SHA256(body, shared api_secret_key)`, Base64-encoded
   - Header `X-Shopify-Shop-Domain`: `attacker-shop.myshopify.com`
3. Attacker captures `(raw_body, hmac_header)` from step 2.
4. Attacker POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the same app's shared webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a request object; `hmac` returns the same valid value, `shop` returns `"victim-shop.myshopify.com"`. [5](#0-4) 
6. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `raw_body`. [6](#0-5) [7](#0-6) 
7. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, so the host application processes an attacker-forged event as if it genuinely originated from the victim shop. [8](#0-7)
