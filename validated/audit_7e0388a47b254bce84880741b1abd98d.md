## Analysis

The JOJO report's bug class — a single privileged executor address gating execution of user-submitted trades, allowing that executor to selectively censor specific users — has a direct analog in Hyperbridge's intents module.

### Title
Single authorized-relayer allowlist lets the relayer censor specific users' escrow releases in IntentGatewayV2 — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` and `onGetResponse` gate every incoming Hyperbridge delivery — including `RedeemEscrow` and `RefundEscrow`, which release users'/solvers' escrowed tokens — behind `_checkRelayer`, which accepts only a single, globally-set `_relayer` address [1](#0-0) . This check runs before any of the body is decoded, in both `onAccept` and `onGetResponse` [2](#0-1) [3](#0-2) .

### Finding Description
Hyperbridge's normal delivery model is permissionless: any relayer can submit a proof to `HandlerV2`, which calls `EvmHost.dispatchIncoming` restricted only to `_hostParams.handler`, and the host forwards the message to the app's `onAccept`/`onGetResponse` with the real submitting address as `relayer` [4](#0-3) . `IntentGatewayV2`/`ExtrinsicIntents`, however, overrides this openness with an app-level allowlist: once `_relayer` is set (via `setRelayer`, callable only through a host-delegatecalled `Execute` governance action) [5](#0-4) , every delivery from any other address reverts with `Unauthorized` before the message body is even read [6](#0-5) .

A reverted `onAccept`/`onGetResponse` call causes the host to delete the pending receipt so the message can be resubmitted later — but only the one authorized relayer address can ever successfully resubmit it [7](#0-6) . This means the single authorized relayer becomes a mandatory chokepoint for delivering:
- `RedeemEscrow` — releasing escrowed input tokens to the solver who filled a cross-chain order.
- `RefundEscrow` — refunding escrowed tokens to the user after a cancellation.

If that relayer selectively refuses to submit the proof for a specific user's or solver's commitment (while continuing to service everyone else), that party's escrowed funds in `_orders[commitment][token]` remain locked indefinitely; no other relayer, however honest, can complete the delivery [8](#0-7) . The same pattern exists in `BridgeToken.onAccept`/`onPostRequestTimeout`, where an unauthorized-relayer delivery is rejected outright and a censored user's incoming mint or timeout refund never lands [9](#0-8) .

### Impact Explanation
A user or solver whose escrow-release/refund message the sole authorized relayer declines to submit has their funds permanently frozen in the gateway's escrow, with no alternative path to trigger delivery — this is a concrete freezing-of-funds impact matching the validated bug class, not merely a resource/liveness inconvenience. Since order placement itself is permissionless (any user can place an order and have funds escrowed) [10](#0-9) , any ordinary counterparty is exposed to this censorship by the relayer operator, exactly mirroring the original report's "user can be censored by trade order sender."

### Likelihood Explanation
The relayer allowlist is armed by default once governance rotates it via `setRelayer`/`Execute` (a normal, expected operational step per the project's own changelog describing this as the intended rollout) [11](#0-10) . Once armed, censoring a specific user requires no special privilege beyond controlling the already-designated relayer key/process — it only requires declining to submit that one user's proof while continuing normal operation for others, which is difficult to detect or prove externally.

### Recommendation
Do not gate fund-release callbacks (`RedeemEscrow`/`RefundEscrow` in `onAccept`, and `onGetResponse`) behind a single mandatory relayer. If relayer restriction is needed for other governance actions, scope `_checkRelayer` to only those actions (e.g., `NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) and leave user-fund-affecting deliveries permissionless, consistent with Hyperbridge's general delivery model.

### Proof of Concept
1. Governance arms the gateway by calling `setRelayer(R)` through the `Execute` path [11](#0-10) .
2. User `A` cancels an order after expiry via `_cancelFromDest`, which dispatches a `RefundEscrow` post request back to the source chain [12](#0-11) .
3. Relayer `R` observes the pending `RefundEscrow` message addressed to `A` and simply never submits the proof to `HandlerV2` for it, while continuing to relay messages for all other users.
4. No other address can successfully call `onAccept` for this message: `_checkRelayer` reverts for any `incoming.relayer != R` [6](#0-5) .
5. `A`'s escrowed tokens in `_orders[commitment][token]` remain locked in the gateway indefinitely, with no way to force delivery.

     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The

        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
