### Title
Untrusted origin can silently escalate to a trusted connection via repeated `add()` calls with no consent enforcement - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins#add` merges the caller-supplied `trusted` and `walletAccount` fields directly into stored origin state via `#setAttributes` with no check for a distinct, verifiable consent marker. Any caller able to invoke this method (exposed unrestricted through `connectedOriginsApi` on the generic RPC surface) can call `add({origin, trusted:false})` followed by `add({origin, trusted:true})` (or supply a different `walletAccount`) and the module will happily persist the escalated/rebound state.

### Finding Description
`add()` at [1](#0-0)  looks up the existing origin record and, if found, calls `#setAttributes` with `trusted: trusted ?? value.trusted` and `walletAccount: walletAccount ?? value.walletAccount` at [2](#0-1) . `#setAttributes` at [3](#0-2)  blindly spreads the new `attributes` over the existing stored connection with no origin-of-request validation, no distinct "user approved" flag, and no check that a previous `trusted:false` state cannot be flipped to `true` (or vice versa) by a plain data-merge call. `isTrusted()` at [4](#0-3)  and `getConnectedAccounts()` at [5](#0-4)  both gate sensitive account disclosure purely on this `trusted` boolean, so whoever controls the `trusted` argument to `add()` controls account exposure.

The `add` method is exported unrestricted as part of the module's public "api" surface at [6](#0-5) , and this codebase's own SDK wiring pattern (`rpc.exposeMethods(sdk)` "deep-traverses the SDK object and exposes all APIs from 'api' nodes") shows that all `type: 'api'` modules, including `connectedOriginsApi`, are exposed as flat RPC methods without a visible per-caller/origin authorization layer in this code [7](#0-6) . I could not locate, within the indexed code, the specific dapp-facing connect handler (e.g., the code behind `solana.connect()` / `ethereum_requestAccounts` documented in `docs/web3-providers/*`) that is supposed to gate calls into `connectedOrigins.add({trusted:true})` behind an actual user-approval popup, nor could I confirm whether the content-script/page-facing RPC channel (`libraries/browser-extension-rpc/content.js`) is restricted to a narrower method allowlist than the full SDK surface used by the trusted extension UI. This is a real gap in what I could verify from the index, not a claim I can fully substantiate as end-to-end reachable from a live untrusted web page without that missing link.

### Impact Explanation
If the `add()` API is reachable by an unprivileged origin (directly or via any RPC path that doesn't itself enforce a separate consent step before calling `connectedOrigins.add`), the origin can self-promote from untrusted to trusted and/or rebind the connection to an arbitrary `walletAccount`, unlocking `getConnectedAccounts()` (address disclosure) and any downstream auto-approve/signing logic that trusts this flag — all without a real "Connect" consent UI interaction. This matches Hydra's "privilege persistence / origin trust bypass" impact category.

### Likelihood Explanation
The module-level code itself has zero defense-in-depth: nothing in `add`/`#setAttributes` distinguishes a legitimate post-approval call from a bare repeated call with an escalated `trusted` flag — this is unconditionally true and trivially reproducible against the module in isolation. Full exploitability against a live wallet depends on whether the dapp-facing connect/approve flow (not found in the indexed code) is the *only* code path that ever invokes `add({trusted:true})`, and whether that path is properly gated behind the consent popup and isolated from arbitrary content-script/page RPC calls. I was unable to confirm or rule this out from the available index, which limits confidence in end-to-end likelihood.

### Recommendation
Add an explicit, non-spoofable consent marker (e.g., a token/nonce generated only by the approval-UI flow, or a separate privileged internal method such as `approve()` distinct from `add()`) that is required to transition `trusted` from `false`/absent to `true` or to change `walletAccount` for an already-connected origin. `add()`/`#setAttributes` should refuse to escalate `trusted` or change `walletAccount` unless this marker is present, and any RPC-exposed API that reaches `connectedOrigins.add` should be explicitly audited to confirm it cannot be invoked directly from an untrusted content-script/page context without passing through the consent UI first.

### Proof of Concept
```js
// features/connected-origins/module/__tests__/connections.test.js style unit test
test('untrusted origin cannot self-escalate to trusted via repeated add()', async () => {
  await connectedOrigins.add({ origin: 'evil.com', connectedAssetName: 'solana', trusted: false })
  expect(await connectedOrigins.isTrusted({ origin: 'evil.com' })).toBe(false)

  // Attacker-controlled second call, no consent marker, same as first call
  await connectedOrigins.add({ origin: 'evil.com', connectedAssetName: 'solana', trusted: true })

  // EXPECTED (secure): should remain untrusted without an explicit approval marker
  // ACTUAL (current code): becomes trusted
  expect(await connectedOrigins.isTrusted({ origin: 'evil.com' })).toBe(false) // fails today
  const accounts = await connectedOrigins.getConnectedAccounts({ origin: 'evil.com' })
  expect(accounts).toEqual([]) // fails today - discloses accounts once trusted
})
```

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
