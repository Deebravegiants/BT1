### Title
Unchecked ERC20/TRC20 return value in `IntentGatewayV2.withdraw` (Tron) leads to escrow write-off without actual token payout - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent funds using a raw low-level `call` to the token's `transfer` selector and only checks that the *call itself* did not revert (`success`). It never decodes/validates the boolean return value that `transfer` is supposed to return. This is the same insecure-transfer pattern flagged in the external report (`PerpDepository.withdrawInsurance` using `transfer` instead of `safeTransfer`): accounting state is updated as if the transfer succeeded even when the token signals failure by returning `false` instead of reverting.

### Finding Description
In `withdraw()`, escrowed token amounts are released to the beneficiary via: [1](#0-0) 

and transaction fees via: [2](#0-1) 

and dust sweeping via: [3](#0-2) 

In all three cases the pattern is:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the low-level call reverted — it does **not** decode the ABI-encoded `bool` that a compliant `transfer()` returns. Any ERC20/TRC20 token that returns `false` on failure (rather than reverting) will make `success == true` even though no tokens were moved. Despite this, the contract proceeds to decrement escrow state (`_orders[body.commitment][token] -= amount;`) and, in the finalize path, deletes the fee entry — permanently marking the funds as paid out.

Notably, this file already imports and aliases OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) as seen at the top of the file, and the sibling non-Tron contracts (`evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/IntentGatewayV2.sol`) consistently use `safeTransfer`/`safeTransferFrom` for the same escrow-release logic: [4](#0-3) 

This confirms the raw-`call` pattern in the Tron contract is an inconsistency/regression relative to the intended safe-transfer semantics, not an intentional design choice.

### Impact Explanation
This function is reachable by any solver/filler settling an intent order or any beneficiary redeeming escrow (`withdraw`, called from `onGetResponse`/GetRequest handling paths in the intents flow). If the escrowed token is a non-standard TRC20/ERC20 that returns `false` instead of reverting on failure (a well-known real-world behavior class, and one of the primary reasons the ecosystem moved to `SafeERC20`), the contract will:
1. Report the transfer as successful.
2. Zero out the escrow accounting (`_orders[...] -= amount`, or delete `TRANSACTION_FEES`).
3. Never move the underlying tokens to the beneficiary.

This results in permanent loss of the beneficiary's funds — the tokens remain stuck in the `IntentGatewayV2` contract with no accounting record left to claim them, since escrow state has already been decremented/deleted. This is a direct instance of "permanent freezing of funds" from the intents escrow.

### Likelihood Explanation
Likelihood is Medium-to-High: it requires the input/output token used for the intent order to be a non-standard ERC20/TRC20 that signals failure via `false` return rather than reverting. Such tokens are common enough (this is precisely why `SafeERC20` exists and is already used everywhere else in this codebase) and Tron's TRC20 ecosystem has a documented history of non-standard implementations, making this more than a theoretical edge case for a Tron deployment.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file family:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
Apply this fix to all three call sites in `evm/tron/contracts/apps/IntentGatewayV2.sol`: the escrow-release loop in `withdraw()`, the transaction-fee payout in `withdraw()`, and the `SweepDust` handling.

### Proof of Concept
1. An order is created with input/output token `T`, a non-standard TRC20 that returns `false` (does not revert) when `transfer` fails (e.g., due to a blacklist, paused state, or insufficient allowance-like internal check).
2. The order is filled and later settled, invoking `withdraw(body, isRefund)` in `evm/tron/contracts/apps/IntentGatewayV2.sol`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` — the call succeeds at the EVM/TVM level, but the encoded return data indicates failure.
4. Since only `success` (the outer call-success flag) is checked, execution continues: `_orders[body.commitment][token] -= amount;` permanently removes the escrow record.
5. No tokens are received by `beneficiary`, yet the contract's internal bookkeeping treats the order as fully settled — the funds are unrecoverably stuck in the contract.
