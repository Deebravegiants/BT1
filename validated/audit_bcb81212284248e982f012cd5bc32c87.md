### Title
Unrestricted, Attacker-Chosen `(app_chain, app)` Bandwidth Subscription Pushes Enable Low-Cost Eviction of a Victim's Paid Bandwidth - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `push_subscription` appends every successful purchase to a FIFO `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024` per `(app_chain, app)` key, evicting the oldest entry once the cap is hit [1](#0-0) [2](#0-1) . Because the purchase message's target `(chain, app)` pair is fully attacker-controlled and unrelated to the payer's identity (the "sponsorship" feature), any unprivileged buyer can call `BandwidthManager.purchase()` on any registered source chain, target any victim app on any chain, and cheaply flood that victim's FIFO list until it evicts the victim's legitimately-paid, higher-value subscription — permanently destroying bandwidth the victim already paid for.

### Finding Description
`BandwidthManager.purchase()` on the EVM side lets any caller specify an arbitrary `app` and `chain` to credit, independent of `msg.sender`, and dispatches the purchase with `fee: 0` [3](#0-2) . This is documented as an intentional "sponsorship" feature: "The purchase message carries its own `chain` ... which is independent of the source chain ... The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`." [4](#0-3) 

On the pallet side, every accepted purchase (or `force_credit`) appends a new `Subscription` to `Allowance::<T>::get(app_chain, app)`, which is a `BoundedVec` capped at 1024 entries; once full, the *oldest* entry is unconditionally evicted regardless of its remaining value [5](#0-4) . The docs explicitly acknowledge this loses paid-for bytes: "Pushing onto a full list (1024 entries) evicts the oldest entry and emits `SubscriptionEvicted` with the lost bytes so the loss is auditable on-chain." [6](#0-5)  There is no per-purchaser rate limit, minimum stake, or reservation mechanism protecting a victim's existing subscriptions from a flood of cheap, attacker-initiated purchases targeting the same `(app_chain, app)` key. A test confirms an arbitrary caller can push repeatedly to evict the oldest subscription in the shared list [7](#0-6) .

This is directly analogous to the reported bug class: an unprivileged, cheap, and unrestricted creation primitive (here, `purchase()` targeting any `(chain, app)`) can be spammed to exhaust/overwrite a bounded, shared resource slot (here, the 1024-entry FIFO), causing loss for a legitimate party — the same root cause (open, low-cost creation with no protective keying/fee floor tied to the resource being consumed) as the original `initialize_sale` finding.

### Impact Explanation
An attacker can purchase the cheapest configured tier (Tier 1) repeatedly, each time setting `chain`/`app` to a specific victim's `(app_chain, app)` pair, to fill that victim's subscription list to the 1024 cap and then push one more, permanently evicting the victim's oldest (and potentially most valuable/most recently-needed) subscription with no possibility of recovery — the `remaining_bytes` are gone and `SubscriptionEvicted` fires only after the fact. If the victim had purchased an expensive, long-duration Tier 4 subscription, the attacker can destroy it by paying only the cost of Tier 1 purchases, which is a direct, permanent loss of paid-for value (funds effectively converted into unusable bandwidth) for the victim, achievable by any unprivileged caller reachable through the standard `purchase()`/`on_accept` path — a bandwidth purchaser attack surface explicitly in scope.

### Likelihood Explanation
The attack requires only calling `BandwidthManager.purchase()` up to ~1024 times with the cheapest available tier and 1 month, targeting a chosen `(chain, app)` pair — no special permissions, no race condition, and it is explicitly enabled ("sponsored") by design since the `chain` field is deliberately unchecked against the caller/source. The cost is bounded by `1024 × cheapest tier price`, which can be economically dwarfed by the value of a victim's larger/expensive subscription, making the attack profitable in griefing/competitive scenarios (e.g., disabling a rival app's ISMP bandwidth).

### Recommendation
- Tie eviction protection to value: either weight the FIFO by remaining value/bytes rather than pure insertion order, or require a minimum bytes/duration floor per push so cheap purchases cannot dominate the queue.
- Consider bounding pushes per `(app_chain, app)` by rate or by the pushing account/chain (e.g., separate quotas per payer) rather than a single global 1024-slot list shared across arbitrary payers.
- Consider disallowing (or gating behind an allowlist/opt-in) third-party sponsorship into another app's bucket, or require the target app to explicitly authorize sponsorship, closing the "any buyer can target any app" surface that enables this griefing.

### Proof of Concept
1. Governance configures `TierOne` with a low price and `TierFour` with a high price/large byte-duration on the pallet and both managers [8](#0-7) .
2. Victim app buys one `TierFour` subscription via `BandwidthManager.purchase(app=Victim, tier=4, months=1, chain=VictimChain)` — this lands as the sole entry in `Allowance::<T>::get(VictimChain, Victim)`.
3. Attacker repeatedly calls `BandwidthManager.purchase(app=Victim, tier=1, months=1, chain=VictimChain)` — permitted because `app`/`chain` are attacker-supplied and unrelated to `msg.sender` [9](#0-8) .
4. Each accepted purchase calls `push_subscription`, appending to the same `Allowance` entry [1](#0-0) .
5. Once the list reaches 1024 entries (all attacker's cheap Tier 1 subs plus the victim's Tier 4 sub at the head), the next attacker purchase triggers `list.remove(0)`, evicting the victim's Tier 4 subscription and emitting `SubscriptionEvicted` with the victim's lost bytes [10](#0-9) , at a fraction of the cost the victim paid.

```rust
		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```

```text
            revert InvalidPurchase();
        }

        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);

        BandwidthPurchaseMsg memory body = BandwidthPurchaseMsg({
            app: app,
            tier: tier,
            months: months,
            chain: chain
        });

            DispatchPost({
                dest: IDispatcher(_host).hyperbridge(),
                to: PALLET_BANDWIDTH_MODULE_ID,
                body: abi.encode(body),
                timeout: 0,
                fee: 0,
                payer: address(this)
            })
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

```rust
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
```
