### Title
Webhook Shop/Topic/ID Spoofing via HMAC that Signs Only the Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken from unauthenticated HTTP headers when dispatching to the registered handler. Because those header values are never part of the signed material, an attacker who owns a legitimately-signed webhook body/HMAC pair (e.g. from installing the app on a shop they control) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim `shop-domain`, `topic`, or `webhook-id`, and the request still passes signature validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors instead read directly from client-supplied HTTP headers, none of which are included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (i.e., only the body) via `Utils::HmacValidator.validate`, and — once that check passes — dispatches the handler using the unauthenticated `request.topic` and `request.shop` headers: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms only that `verifiable_query.to_signable_string` (the raw body) matches the HMAC — it has no knowledge of, and does not bind, the shop/topic/webhook-id headers: [4](#0-3) 

The identity binding that should hold is:
`shop/topic/webhook_id authenticated by HMAC` == `shop/topic/webhook_id acted upon by the handler`

Because the HMAC only covers the body, this equality does not hold: `shop/topic/webhook_id authenticated` = `{body}` while `shop/topic/webhook_id acted upon` = `{header values, unauthenticated}`. An attacker who has captured one valid `(raw_body, hmac)` pair — trivially available to them from a webhook legitimately delivered to their own shop for the app they installed — can resend that exact body and HMAC to the app's public webhook endpoint with forged `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers. The signature check still succeeds (body is byte-identical), and `WebhookMetadata` is constructed with the attacker-chosen shop/topic/webhook_id, causing the app's handler to execute business logic as if it were a genuine webhook for a different (victim) shop or a different topic (e.g. `app/uninstalled`, `shop/redact`, or any handler registered by the host application).

### Impact Explanation
This crosses a tenant boundary: an attacker with no credentials for the victim shop can make the app process attacker-controlled events under the victim shop's identity and/or an attacker-chosen topic, without needing the app's `api_secret_key`, an access token, or any privileged account — they only need one legitimately delivered webhook from their own installation. Depending on the host application's webhook handlers, this can drive cross-tenant data mutation, forged uninstall/redact events, or other tenant-scoped side effects attributed to the wrong shop, which fits the Critical "cross-tenant access" category.

### Likelihood Explanation
Any internet user can install the app (e.g. via a free/dev store) to obtain one valid `(body, hmac)` pair for an arbitrary topic body of their choosing (many webhook payloads are attacker-influenced, e.g. `orders/create` on their own store), then replay that pair against the shared public webhook endpoint with forged headers. No secret material, token, or elevated privilege is required — only the ability to receive one webhook and resend an HTTP request with different headers.

### Recommendation
Bind the shop domain, topic, and webhook id into the signed/verified material (or otherwise cryptographically authenticate them, e.g. by verifying the shop domain returned against a known/allow-listed value from Shopify combined with per-installation secrets), so that a valid HMAC over the body cannot be replayed across different shops, topics, or webhook ids. At minimum, `to_signable_string` should incorporate the header values that the handler subsequently trusts.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. topic `orders/create`, body `{"id":1}}`, with a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `api_secret_key`.
2. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any other topic registered by the app)
   - `x-shopify-webhook-id: <arbitrary>`
3. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) raw body against the (unchanged) HMAC.
4. `Registry.process` looks up the handler for the forged `topic` and invokes it with `shop: "victim-shop.myshopify.com"`, causing the host application to process an attacker-forged event attributed to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
