### Title
Webhook `shop`/`topic`/`webhook-id` identity fields are trusted despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request **body**, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP **headers** that are never covered by that HMAC. Any party able to obtain one legitimate `(body, hmac)` pair — trivially available to anyone who installs the app on their own store — can replay that pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop, and the library will report the webhook as valid and hand the data to the handler tagged with the victim's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery`: [1](#0-0) 

Its `to_signable_string` returns only `@raw_body`, i.e. the HMAC is computed exclusively over the JSON body. `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop` (and the other header fields) to build the data handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the raw body) matches the supplied signature under `Context.api_secret_key`: [4](#0-3) 

This breaks the identity binding `hmac_signed(shop) == shop_used_by_handler`: the gem verifies **bytes of the body**, but acts on a **shop identity from an unauthenticated header**. Because an app is a single client_id used by every installed shop, an attacker who has installed the app on their own shop (a normal, unprivileged action requiring no credentials or secrets) receives fully valid webhook deliveries containing a legitimate `(body, x-shopify-hmac-sha256)` pair for their own store. Since the HMAC never covers `x-shopify-shop-domain`, the attacker can POST that identical `(body, hmac)` pair directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds (it only checks the body/secret), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's forged body>, ...)`, i.e., data the attacker fully controls is delivered to the app under a victim tenant's identity.

### Impact Explanation
This is a cross-tenant boundary violation: the gem allows a request that never originated from — and was never signed for — a specific shop to be processed as if it belongs to that shop. Depending on how the host application persists webhook payloads (nearly always keyed by `data.shop`), this can let an attacker inject or overwrite data under an arbitrary victim merchant's account (e.g., forged `orders/create`, `app/uninstalled`, `shop/update`, GDPR data-request payloads, etc.), a Critical-severity cross-tenant access issue per the given impact criteria. No access token, `client_secret`, or privileged account is required — only the ability to install the app on any shop (including the attacker's own free/dev store) and send raw HTTP POST requests to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is high for any app: any internet user can create a free Shopify partner/dev store, install the target app to trigger a legitimate webhook delivery, capture the raw body and `x-shopify-hmac-sha256` header (e.g., via a proxy or their own receiving endpoint), and then replay it with a substituted `x-shopify-shop-domain` header directly to the app's public webhook URL. No secrets, tokens, or non-public information are needed — only the gem's documented header-vs-body verification behavior in `Webhooks::Request`/`Webhooks::Registry`.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity to the HMAC-verified material, or otherwise ensure `Registry.process` cannot deliver attacker-supplied header values as trusted output. Concretely:
- Extend `Webhooks::Request#to_signable_string` (or add a separate check) so the `shop-domain` header is authenticated as part of verification, or
- Require the host application/library to cross-check `request.shop` against the shop of the specific `access_token`/webhook subscription the payload claims to belong to before invoking the handler, and document/enforce that `WebhookMetadata#shop` must not be trusted as a tenant key unless corroborated by an independently verified source (e.g., a lookup keyed by `webhook_id` registered per-shop).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`.
2. Attacker's own endpoint (or a proxy in front of the app) captures the raw request:
   - Body: `{"id":1,...}` 
   - Header `x-shopify-hmac-sha256: <valid-signature-for-body>`
   - Header `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker crafts a new POST to the app's public webhook route with the **same body and same HMAC header**, but:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `request.to_signable_string` (`@raw_body`, unchanged) and successfully matches the forwarded HMAC: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker-supplied data as belonging to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
