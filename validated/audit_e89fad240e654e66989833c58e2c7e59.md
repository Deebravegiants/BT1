### Title
Solver fills are priced from live, unprotected `sqrtPriceX96` spot reads of Uniswap V4 pools, letting a flash-loan swap manipulate intent fill amounts - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
When a `TradingPair` has no static bid/ask curve, the FX filler prices the pair directly off the instantaneous state of a configured Uniswap V4 pool (`slot0`-equivalent `sqrtPriceX96`/tick read via `StateView.getSlot0`), analogous to the reported `Underlying::UnderlyingMint` reliance on `slot0`. Because this spot price is used, without a TWAP, to size real order fills, an attacker can transiently move the pool price (e.g. with a large swap or flash loan) immediately before/around a solver's fill computation to get an inflated output amount from the solver, or to shrink the notional used for confirmation-depth (reorg-protection) sizing.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` reads live pool state and derives price purely from `sqrtPriceX96`: [1](#0-0) [2](#0-1) 

The underlying state refresh calls `StateView.getSlot0` right before pricing/planning, i.e. it is a spot read with no time-weighting: [3](#0-2) 

This price feeds `FXFiller.referenceRate` and the leg-pricing pipeline (`resolveLegRates` → `computeLegPolicyOutput`) used both to size real fills and to compute the notional used for confirmation-depth/reorg protection: [4](#0-3) 

The project's own internal documentation acknowledges this is a raw spot mid with essentially one guard: [5](#0-4) 

The only mitigation is `checkPriceGuard`, an optional, static `referencePrice` + `maxDeviationBps` band that must be manually configured per position and is not a manipulation-resistant oracle (no TWAP, no liquidity-depth check, no execution-cost/slippage modeling): [6](#0-5) 

If the guard is left unconfigured (explicitly supported — "omit both to leave the chain unguarded"), or if the attacker moves price within the configured deviation band, the spot price flows straight into fill sizing with zero additional defense. Even when the guard is configured, it only bounds deviation from a fixed reference, not from a genuinely time-weighted or liquidity-checked price, so an attacker who knows/matches the operator's `referencePrice` window can still manipulate price within the allowed band to skew output amounts on a given fill.

This is the same root cause as the reported `Underlying.sol` bug: consuming `slot0`/instantaneous pool price directly in a function that computes amounts owed, without TWAP or liquidity-manipulation resistance.

### Impact Explanation
An attacker (any unprivileged actor able to submit a swap on the venue Uniswap V4 pool and place/trigger an intent order) can distort the "USD per exotic token" price the solver uses to compute `PaymentInfo`/output token amounts for a fill. Since the filler treats this as a linear mid-price with no size/impact term (`computeLegPolicyOutput` extends the mid linearly across the whole priced quantity, per the flow doc), a manipulated spot price directly translates into the solver either:
- over-delivering output tokens relative to true value (direct loss of solver/protocol funds), or
- under-collateralizing the notional used for the anti-reorg confirmation-depth policy, weakening the security margin that policy exists to enforce (as explicitly called out in the `referenceRate` comment about a manipulated pool "shrinking the reorg protection").

This is a concrete funds-loss / broken-invariant vector for the intent-filling path, matching the audit-issue's severity class (Medium).

### Likelihood Explanation
Reachable from a single flash-loan-funded swap against the configured venue pool, timed around an intent order fill — no privileged access required. Likelihood is reduced only where operators have configured `referencePrice`/`maxDeviationBps` tightly, but this is optional, per-position config that the codebase itself documents as leaving chains "unguarded" by default, and even when present it does not defend against manipulation within the configured band or against genuinely thin/manipulable pools whose reference price itself becomes stale.

### Recommendation
Replace or augment the raw `sqrtPriceX96`/`slot0`-derived spot price with a manipulation-resistant source before using it to size fills:
- Use a TWAP over a meaningful window (Uniswap V4's oracle/observations, or an external oracle) instead of the instantaneous `getSlot0` result in `computeDirectPoolPriceUsd`.
- Make the `referencePrice`/`maxDeviationBps` price guard mandatory (not optional) for any venue-priced pair, and tighten it based on pool liquidity/depth rather than a purely static admin-set value.
- Incorporate size/impact into `computeLegPolicyOutput` rather than extending the pool mid linearly, so a shallow, easily-moved pool cannot cheaply misprice large fills.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` position for a pair without `bidPriceCurve`/`askPriceCurve` and without `referencePrice`/`maxDeviationBps` (a supported, documented configuration).
2. Attacker takes a flash loan and executes a large swap on the configured Uniswap V4 pool, shifting `sqrtPriceX96` (and thus `token0Price`/`token1Price`) far from the pre-swap price.
3. Attacker (or an accomplice) submits/triggers an intent order matching that pair while the price is skewed.
4. `FXFiller.resolveLegRates`/`referenceRate` calls `UniswapV4FundingPlanner.getExoticTokenPrice`, which calls `state.refresh()` → `StateView.getSlot0` and computes `computeDirectPoolPriceUsd` from the currently-manipulated `sqrtPriceX96`.
5. `computeLegPolicyOutput` sizes the fill output linearly at this skewed price, causing the solver to deliver an incorrect (attacker-favorable) amount of output tokens.
6. Attacker repays the flash loan; the pool price reverts, but the solver's mispriced fill has already executed on-chain.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	/**
	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
