## Analysis: DoS via Unbounded Connection Acceptance on Gateway Listeners

The CVE-2020-8663 bug class is "listener accepts unlimited connections, exhausting file descriptors/memory." Chainlink's Gateway service exposes exactly this pattern on its internet-facing HTTP and WebSocket listeners.

### Title
Unbounded concurrent-connection acceptance on the Gateway's public HTTP/WS listeners enables file-descriptor/memory exhaustion - (File: core/services/gateway/network/httpserver.go, core/services/gateway/network/wsserver.go)

### Summary
Both `NewHTTPServer` and `NewWebSocketServer` construct a standard `net/http.Server` and call `s.server.Serve(s.listener)` / `s.server.ServeTLS(...)` directly on a plain `net.Listener` obtained from `lc.Listen(ctx, "tcp", s.server.Addr)`, with no wrapper limiting the number of concurrently accepted connections. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`HTTPServerConfig` and `WebSocketServerConfig` only expose per-request timeouts (`ReadTimeoutMillis`, `WriteTimeoutMillis`, `RequestTimeoutMillis`) and a request body size limiter (`MaxRequestBytesLimiter`); there is no setting or code path that bounds the number of simultaneously open TCP connections or file descriptors held by the process. [4](#0-3) 

Each accepted connection is handled by `net/http`'s standard per-connection goroutine model. `ReadTimeout`/`ReadHeaderTimeout` bound how long a single connection is allowed to sit idle before the server closes it, but they do not bound how many connections can be open concurrently. An unauthenticated remote client can therefore open connections faster than the timeout elapses (e.g., a large but slow "connection flood," or many parallel TCP handshakes that never send a full HTTP request), consuming one file descriptor and one goroutine per connection until the process runs out of descriptors or memory — this is the exact bug class described in CVE-2020-8663 for Envoy.

The Gateway's HTTP path is reachable by unprivileged/unauthenticated external actors: the v2 capability HTTP trigger handler is explicitly designed to accept requests from external workflow triggers before any JWT/allowlist authorization is performed at the application layer (`httpTriggerHandler.authorizeRequest` only runs after the HTTP request has already been accepted and parsed). [5](#0-4) 

The WebSocket listener (`wsserver.go`) is intended only for authenticated DON nodes, but `handleRequest` still fully accepts the TCP connection and reads/decodes the `Authorization` header before any handshake validation occurs — so the TCP-connection-acceptance step itself is unauthenticated and unbounded. [6](#0-5) 

### Impact Explanation
An attacker who can reach the Gateway's public HTTP listener (used for CRE/workflow HTTP triggers) or the node WebSocket listener can open a very large number of concurrent connections, exhausting the process's file descriptor limit and/or memory used by per-connection goroutines and buffers. Because the Gateway is a single shared internet-facing entry point that also intermediates traffic between DON nodes and the outside world, an outage here denies service to all workflows and nodes routed through it — a availability/DoS impact consistent with the "High" severity of the analog CVE, though it is a resource-exhaustion DoS rather than data compromise.

### Likelihood Explanation
Reaching this bug class requires only unauthenticated TCP connections to a publicly reachable listener — no valid signature, JWT, or node identity is needed to consume a socket/file-descriptor slot. This is a low-effort, low-skill attack (comparable to a classic connection-flood/Slowloris-style attack), and Go's `net/http.Server` does not impose a global connection cap by default, so likelihood is high assuming the Gateway ports are internet-reachable, which is their designed purpose.

### Recommendation
Wrap the raw `net.Listener` with a connection-count limiter (e.g., `golang.org/x/net/netutil.LimitListener`) configured with a sane maximum concurrent-connection value before passing it to `s.server.Serve`/`ServeTLS` in both `httpserver.go` and `wsserver.go`. Additionally, set `http.Server.MaxHeaderBytes` explicitly and consider a global `IdleTimeout` so that connections that complete their handshake but stay idle do not hold descriptors indefinitely. Expose these limits via `HTTPServerConfig`/`WebSocketServerConfig` (similar to the existing `MaxRequestBytesLimiter` pattern) so operators can tune capacity per deployment.

### Proof of Concept
1. Start a Gateway with the v2 HTTP trigger handler enabled and its listener reachable over the network.
2. From an unauthenticated client, open thousands of raw TCP connections to the configured `Host:Port` (e.g., via `for i in $(seq 1 20000); do (exec 3<>/dev/tcp/gateway-host/port &) ; done`), sending no data or a slow trickle of bytes so each connection survives until `ReadTimeoutMillis` expires.
3. Observe that the Gateway process's open file descriptor count climbs unbounded (`lsof -p <pid> | wc -l`), and that legitimate requests to the health-check or trigger endpoints begin to fail or hang once the process hits its file-descriptor limit (`ulimit -n`), demonstrating denial of service.

func (s *httpServer) runServer(ctx context.Context) error {
	var lc net.ListenConfig
	listener, err := lc.Listen(ctx, "tcp", s.server.Addr)
	if err != nil {
		return err
	}
	s.listener = listener
	tlsEnabled := s.config.TLSEnabled

	go func() {
		if tlsEnabled {
			serveErr := s.server.ServeTLS(s.listener, s.config.TLSCertPath, s.config.TLSKeyPath)
			if serveErr != http.ErrServerClosed {
				s.lggr.Error("gateway server closed with error:", serveErr)
			}
		} else {
			serveErr := s.server.Serve(s.listener)
			if serveErr != http.ErrServerClosed {
				s.lggr.Error("gateway server closed with error:", serveErr)
			}
		}
		s.doneCh <- struct{}{}
	}()

func (s *webSocketServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	authHeader := r.Header.Get(WsServerHandshakeAuthHeaderName)
	if len(authHeader) > HandshakeEncodedAuthHeaderMaxLen {
		s.lggr.Debugw("received auth header is too large", "len", len(authHeader))
		w.WriteHeader(http.StatusBadRequest)
		return
	}
	authBytes, err := base64.StdEncoding.DecodeString(authHeader)
	if err != nil {
		s.lggr.Debugw("received auth header can't be base64-decoded", "err", err)
		w.WriteHeader(http.StatusBadRequest)
		return
	}
	attemptID, challenge, err := s.acceptor.StartHandshake(authBytes)
	if err != nil {
		s.lggr.Debugw("received invalid auth header", "err", err)
		w.WriteHeader(http.StatusUnauthorized)
		return
	}
