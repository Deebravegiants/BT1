### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw()` allows escrow accounting corruption via reentrant beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` decrements per-token escrow balances *after* making a low-level external call to the beneficiary (native `.call{value:}` or ERC-20 `token.call`), rather than before, unlike the fixed EVM sibling contract (`IntentsBase.sol`) which was already patched for this exact class of bug.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730) is invoked from `onAccept` when a `RedeemEscrow`/`RefundEscrow` request is delivered [1](#0-0) . Inside the loop over `body.tokens`, the contract performs the external transfer first and only decrements `_orders[body.commitment][token]` afterward: [2](#0-1) 
The transaction-fee payout follows the same pattern — external `.call` to the fee token, then `delete _orders[body.commitment][TRANSACTION_FEES]` afterward: [3](#0-2) 

This is the same root-cause pattern flagged in the external report (state mutated after, not before, an external/third-party call). Critically, the sibling production contract `IntentsBase.sol` (used on standard EVM chains) was already hardened against exactly this bug: it writes `_orders[body.commitment][token] = escrowed - amount;` **before** performing the token transfer [4](#0-3) , and the accompanying regression test suite (`IntrinsicIntentsReentrancyTest.sol`) documents that `_filled`/escrow state must be set/decremented *before* any external call specifically to block reentrant beneficiaries [5](#0-4) . The Tron contract does not carry this fix into its `withdraw()` implementation, and it is not composed from the hardened `IntentsBase`/`ExtrinsicIntents` inheritance chain used by the standard `evm/src/apps/IntentGatewayV2.sol` [6](#0-5) , nor does it inherit `ReentrancyGuardTransient` as that contract does.

Because a beneficiary can be an attacker-controlled contract (any solver/user can be named `beneficiary` of an order they place or fill), a malicious beneficiary's `receive()`/fallback hook fires mid-loop, while `_orders[body.commitment][token]` for that (and other, not-yet-processed) tokens in the same commitment is still un-decremented. If the reentrant context can reach any code path that reads or acts on `_orders[commitment][...]` before the outer call finishes zeroing it out, escrow accounting can be double-counted or corrupted (e.g. mismatched book-keeping across multi-token orders, or dust/fee double-payout), a subset of the "unbacked mint / theft via forged accounting" impact class this scan targets.

### Impact Explanation
Escrow funds and transaction fees are accounted per-token in `_orders[commitment][token]`, decremented only after the token has already left the contract. This inverts the Checks-Effects-Interactions pattern that the project's own tests document as the required fix for this exact contract family. In a multi-token order (common — orders can escrow several `inputs`/fees), a compromised state window exists during the loop where escrow for not-yet-paid tokens is still fully intact while payment for earlier tokens has already been sent, creating a window that a sufficiently crafted reentrant call could exploit to double-spend or drain escrow tied to the same commitment before the loop / outer call completes its accounting.

### Likelihood Explanation
Exploitation requires the beneficiary to be attacker-controlled and requires `withdraw()` to process at least one native-token payout (or a malicious ERC-20 with callback semantics, e.g. ERC-777-like tokens) ahead of other tokens/fees for the same commitment. Since `onAccept` is `onlyHost`-gated, a full reentrant recursion back into `onAccept` requires either a compromised/careless host receipt-ordering (I could not fully confirm `HandlerV2.sol`'s receipt-vs-callback ordering before the response cut off) or another externally reachable entry point that consumes `_orders` mid-call. Given this uncertainty about a full recursive callback path, likelihood is Medium rather than confirmed-High, but the CEI violation itself is a clear and concrete deviation from the pattern the project has already fixed elsewhere in the same codebase, indicating unintentional omission on the Tron port.

### Recommendation
Apply the same fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron `IntentGatewayV2.withdraw()`: decrement/delete `_orders[body.commitment][token]` (and `_orders[body.commitment][TRANSACTION_FEES]`) **before** performing the native/ERC-20 transfer, and mark `_filled`/finalize state up front as done elsewhere. Additionally consider adding `ReentrancyGuardTransient` (as used in the standard `IntentGatewayV2.sol`) to the Tron contract for defense-in-depth.

### Proof of Concept
Not fully constructible without confirming `HandlerV2.sol`'s request-receipt ordering relative to `onAccept` invocation (needed to determine whether external reentry into `onAccept` is possible before the current delivery's receipt is recorded); this could not be verified before the tool budget was exhausted. The concrete, verifiable defect is the CEI violation itself: `withdraw()` performs `beneficiary.call{value: amount}("")` / `token.call(transfer(...))` at lines 703/706/720 before mutating `_orders` at lines 710/722, which is the exact anti-pattern already remediated in the sibling `IntentsBase.sol` contract and covered by dedicated regression tests.
