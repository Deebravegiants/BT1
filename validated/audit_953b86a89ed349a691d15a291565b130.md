### Title
Unconstrained `slippageValues` (and `feeStructure`) — `getHashedCalldata()` is never checked against `circomData.calldataHash` on-chain — (File: `contracts/CircomDataBuilder.sol`)

### Summary
`CircomDataBuilder.getHashedCalldata()`/`getHashedCalldata1()`/`getHashedCalldata2()` are defined to fold `slippageValues` and `feeStructure` (plus `hookData`, `onChainCreation`, etc.) into a hash, presumably so those fields can be bound to the EdDSA-signed message and the ZK public input vector. However, this hash is never recomputed and compared against the attacker-supplied `circomData.calldataHash` field anywhere in the reachable call graph, so `slippageValues`/`feeStructure` are not actually constrained by either the proof or the signature.

### Finding Description
The claimed equality is: `circomData.calldataHash == getHashedCalldata(circomData)` (computed fresh from the *actual* runtime `slippageValues`/`feeStructure` etc.). Tracing usage:

- `getHashedCalldata1` explicitly folds in `circomData.slippageValues` [1](#0-0) , and `getHashedCalldata2` folds in `circomData.feeStructure` [2](#0-1) .
- However, `getSignedMessageHash()` and `formBasicInput()` never call `getHashedCalldata()`; they simply consume the raw, attacker-supplied `circomData.calldataHash` field verbatim as one hash input and as the public-input slot value [3](#0-2) [4](#0-3) .
- A repo-wide search for calls to `getHashedCalldata(` finds only self-references inside `CircomDataBuilder.sol` itself (the definition and its two internal sub-calls) — no other contract (`Hinkal.sol`, `HinkalHelper.sol`, `VerifierFacade`, etc.) ever calls it to validate `circomData.calldataHash`. This means the hash that supposedly "locks in" `slippageValues`/`feeStructure` is computed but never checked against anything on-chain.
- Meanwhile `slippageValues` is *not* itself listed as a public-input signal in `formBasicInput`/`formInputNormal` (only `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `timeStamp`, `outCommitments`, the opaque `calldataHash`, and stealth-address fields are placed in the input vector) [5](#0-4) . The circuit itself (`MainEVMCircuit.circom`) treats `calldataHash` purely as an opaque signal that is folded into the EdDSA-signed message; it never decomposes or re-derives it from `slippageValues`/`feeStructure` because those are not even circuit signals [6](#0-5) .
- Downstream, `circomData.slippageValues[i]` (attacker-chosen, `int256`, sign-controllable) directly gates the balance guard: `require(balanceDif >= circomData.slippageValues[i], "slippage param is violated")` [7](#0-6) , and `feeStructure.feeToken`/`flatFee`/`variableRate` govern real fee deduction against the same leg, e.g. in `_internalTransact` [8](#0-7)  and in `ExternalActionSwap.swap` [9](#0-8) .

Root cause: since nothing recomputes/compares `getHashedCalldata(circomData)` against `circomData.calldataHash`, an attacker who obtains one valid proof + EdDSA signature (over a `signedMessageHash` that embeds some fixed `calldataHash` value `H`) can resubmit the exact same `calldataHash = H` (so both the ZK proof's public inputs and the on-chain recomputation of `signedMessageHash` remain identical and still verify) while freely mutating `slippageValues` and `feeStructure` to arbitrary attacker-chosen values, because neither field is actually re-derived into `H` by any on-chain check.

### Impact Explanation
By setting `slippageValues[i]` to an arbitrarily negative value for the leg where `feeStructure.feeToken` overlaps, the attacker neutralizes the "minimum amount received/given" protection (`balanceDif >= slippageValues[i]`), allowing the same proof to be replayed with a materially different, attacker-favorable balance outcome (e.g., accepting a worse swap result, or manipulating how flat/variable fee deduction interacts with the leg) without the proof ever having constrained that outcome. This is a proof/verifier-bypass class issue: the chain acts on a value (`slippageValues`, `feeStructure`) that the selected circuit never constrained at the corresponding public-signal index, matching the "Critical: proof or verifier bypass" category. It is repeatable per stored proof/signature pair (one proof can be replayed with different slippage/fee combinations as long as `calldataHash` and the rest of the public inputs are held fixed).

### Likelihood Explanation
Preconditions: the attacker only needs their own valid UTXO(s), their own generated proof, and their own EdDSA-signed `signedMessageHash` — all things an unprivileged EOA legitimately controls when calling `Hinkal.transact`. No special role, relay, or victim key is required. The cost is a single legitimate proof generation; the mutation of `slippageValues`/`feeStructure` at submission time is free (just different calldata bytes, not requiring a new proof or signature).

### Recommendation
Before consuming `circomData.calldataHash` anywhere (`formBasicInput`, `getSignedMessageHash`, or earlier in `Hinkal.transact`), add an explicit on-chain check:
```solidity
require(circomData.calldataHash == getHashedCalldata(circomData), "calldata hash mismatch");
```
This forces `slippageValues`, `feeStructure`, `hookData`, `onChainCreation`, `originalSender`, and `extraData` to be cryptographically bound to the same value that is embedded in the EdDSA-signed `signedMessageHash`, preventing any of these fields from being mutated post-signing while reusing the same proof.

### Proof of Concept
Foundry test plan:
1. Generate one valid proof + EdDSA signature for a `CircomData` struct with `slippageValues = [S0, S1]`, `feeStructure = F0`, computing `calldataHash = getHashedCalldata(circomData)` off-chain and embedding it in the signed message (mirroring the wallet's real signing flow).
2. Call `Hinkal.transact` with this original `circomData` — assert success and record `balanceDif`/fee outcome.
3. Construct a second calldata payload: same proof bytes, same `calldataHash`, same everything used in the public input vector — but with `slippageValues` mutated (e.g., a very negative value for the fee-token leg) and/or `feeStructure.flatFee`/`variableRate` changed.
4. Call `Hinkal.transact` again with the mutated payload and the SAME proof.
5. Assert: `verifyProof` returns true for both calls (public input vector unchanged since `slippageValues`/`feeStructure` aren't in it and `calldataHash` is unchanged), yet `balanceDif`/relay-fee outcome differs between the two calls, violating the invariant "every value the chain acts on == the value the circuit constrained at that index."

Note: I was unable to fully inspect the earlier portion of `Hinkal.sol`/`HinkalHelper.sol` (before the `transact` snippet retrieved) to definitively rule out an equality check under a different function name; the repo-wide search for calls to `getHashedCalldata(` found no such cross-file usage, which is the basis for this finding, but this residual gap should be re-verified with a full read of `Hinkal.sol`'s `transact`/`performHinkalChecks` before treating this as fully confirmed.
