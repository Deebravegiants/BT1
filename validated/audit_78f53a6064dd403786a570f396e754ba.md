Given the rules, the closest legitimate analog in this gem's `lib/shopify_api/**` code is a broken binding between the HMAC-covered bytes and the tenant identity field (`shop`) that the webhook pipeline trusts downstream — directly matching the "field acted on but not covered by the HMAC" analog class.

### Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` by reading them straight from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. `Registry.process` trusts `request.shop`/`request.topic` for dispatch immediately after that (incomplete) HMAC check passes.

### Finding Description
`Request#shop` reads the tenant identity purely from the `shop-domain` header: [1](#0-0) 

`Request#to_signable_string`, which is what actually gets HMAC-verified, returns only the raw body bytes — none of the identity headers (`shop`, `topic`, `webhook-id`, `api-version`) are included: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes and compares the HMAC strictly against `verifiable_query.to_signable_string` (the body): [3](#0-2) 

`Registry.process` performs this HMAC check and, immediately on success, builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic`, dispatching it to the app's handler as trusted tenant/topic context: [4](#0-3) 

The broken identity binding, stated as an equality that the code assumes but never enforces:
`shop_used_by_handler (request.shop, header) == shop_covered_by_signature (bytes verified by HmacValidator)`
In reality, `to_signable_string == raw_body` only, so any header value can be substituted without invalidating the signature — the two sides of the equality are never actually checked against each other.

### Impact Explanation
Shopify apps share a single `api_secret_key` across every merchant that installs the app; the HMAC over the webhook body is computed with that same shared secret regardless of which shop the delivery is destined for. An unprivileged internet user who installs the app on their own store (a "shop" they legitimately control) will receive real webhook deliveries with valid `(raw_body, X-Shopify-Hmac-Sha256)` pairs signed by that shared secret. Because the signature never binds `shop-domain`/`topic` to the bytes, that same attacker can resend the identical body+HMAC to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a victim shop. `HmacValidator.validate` still succeeds (only the body is checked), so `Registry.process` dispatches attacker-controlled data attributed to the victim shop into the app's per-tenant webhook handlers (e.g. order/customer sync logic, or the mandatory `customers/redact`, `shop/redact`, `customers/data_request` compliance handlers). This is a cross-tenant boundary crossing achieved without needing the app's `client_secret`/access tokens — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker being able to install the target app on any shop they control to obtain a genuinely signed webhook, and (2) sending a normal HTTP POST to the app's public webhook endpoint with a modified header. No credential theft, TLS interception, or privileged access is needed — this is reachable by any unprivileged internet user who is also a merchant of the app (a very low bar for public apps in the Shopify App Store).

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload before `Registry.process` trusts `request.shop`/`request.topic` for dispatch. At minimum, downstream handlers should not treat `request.shop` as an authenticated tenant identifier unless it has been cross-checked against an independent, already-authenticated record (e.g., the session/shop that requested delivery registration).

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and has the app installed there,
# so Shopify sends them a genuinely-signed webhook:
raw_body = '{"id": 1, "malicious": "payload"}'
valid_hmac_from_shopify = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SHARED_SECRET, raw_body)
) # attacker just captures this from their own real webhook delivery

# Attacker replays the exact same body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "customers/redact",   # or any registered topic
  "x-shopify-hmac-sha256" => valid_hmac_from_shopify,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body checked)
# => handler.handle(data: WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...))
# The app processes attacker-controlled data as if it legitimately originated from victim-shop.
```
