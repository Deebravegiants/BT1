### Title
Unswept leftover native ETH permanently stuck in `EvmHost` after `swapETHForExactTokens` overpayment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH via `msg.value` and swap it for the exact fee-token amount needed using `IUniswapV2Router02.swapETHForExactTokens`. Unlike the analogous fee-swap logic in `IntentGatewayV2.sol`, none of these `EvmHost` functions capture the `amounts` array returned by the swap or refund the unused ETH back to the caller, so any overpayment is permanently trapped in the contract.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)`: [1](#0-0) 

and `dispatch(DispatchGet)`: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

all execute `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. `swapETHForExactTokens` only spends up to the exact ETH required to obtain `fee` units of `feeToken`, refunding any leftover ETH to the *caller of the router* — which is `EvmHost` itself, since it's the one calling `swapETHForExactTokens`. That refunded ETH lands in `EvmHost`'s own balance, but the return value (an `amounts[]` array reporting ETH actually spent) is discarded (`IUniswapV2Router02(uniswapV2).swapETHForExactTokens{...}(...)` is called without capturing its return), and no logic reduces `msg.value` by the spent amount or forwards the difference back to `_msgSender()`.

This is directly analogous to the reported `FeePayer.handleMintFee()` bug class ("the returned value of `call()`/external transfer is not checked... ETH gets stuck on the contract's balance") — here the unchecked/ignored return value is the swap router's leftover-ETH accounting, and the effect is identical: ETH becomes permanently stuck in the protocol contract.

Confirming the contrast, `IntentGatewayV2.sol`'s `placeOrder` does this correctly for the exact same swap call: it captures `amounts[0]`, subtracts it from `msgValue`, and explicitly refunds the remainder to `msg.sender`: [4](#0-3) 

`EvmHost` has no equivalent refund step for its three ETH-accepting entry points, and — as far as could be verified within the available context — no native-ETH sweep/rescue function was found on `EvmHost` to recover stray balance (only `IERC20`-based fee-token transfers are handled). This last point could not be fully confirmed due to index truncation of the full `EvmHost.sol` contents; a Devin session with full file access should double check for any admin/sweep functions before concluding funds are unrecoverable.

### Impact Explanation
Any unprivileged caller who dispatches a POST/GET request or funds a request by paying with native token and supplies `msg.value` greater than the amount needed to buy exactly `post.fee`/`get.fee`/`amount` units of `feeToken` will have the surplus ETH silently swept into the router refund, landing in `EvmHost`'s balance rather than being returned. Over time and across the many relayers/apps/users interacting with `dispatch()`/`fundRequest()` (both are `external payable`, reachable by any transaction), this results in permanent freezing of user funds — real ETH value with no code path to reclaim it. This is a direct "permanent freezing of funds" class issue reachable from a single submitted transaction.

### Likelihood Explanation
High likelihood: any caller who doesn't compute the exact swap input off-chain (e.g. sending a safety margin of ETH, which is common practice and even documented — see the "Estimating Fees" client guidance encouraging quote-then-pad usage patterns) will trigger this on essentially every `dispatch{value: msg.value}(...)` or `fundRequest{value: ...}(...)` call where native payment is used instead of the feeToken. This is not an edge case requiring adversarial conditions — it happens under ordinary, expected usage whenever the caller doesn't send the exact precise wei amount.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned from `swapETHForExactTokens` and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`, `evm/src/apps/IntentGatewayV2.sol:375-397`), using a checked low-level call or `Address.sendValue` that reverts on failure so ETH cannot silently accumulate unaccounted for in the contract.

### Proof of Concept
1. A caller invokes `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `msg.value = 2 ETH`, while `post.fee` only requires `0.1 ETH` worth of swap input to obtain the exact `feeToken` amount.
2. `IUniswapV2Router02.swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)` executes, spending `0.1 ETH` and refunding the remaining `1.9 ETH` back to `EvmHost` (the caller of the router).
3. `EvmHost` never captures the `amounts[]` return value nor issues any refund to `_msgSender()`; the `1.9 ETH` remains part of `address(this).balance`.
4. Repeat across many callers/transactions: ETH accumulates in `EvmHost` with no corresponding accounting entry and, absent a native-ETH withdrawal/sweep function on `EvmHost`, is permanently unrecoverable by the original payers.
