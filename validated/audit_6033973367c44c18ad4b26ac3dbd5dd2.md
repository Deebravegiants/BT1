### Title
Blacklistable escrow token can permanently freeze IntentGatewayV2 escrow via reverting `_withdraw` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
Like EigenLayer's `thirdPartyTransfersForbidden` toggle that a strategy whitelister (a party outside Rio's control) can flip at any time to make Rio's withdrawal calls permanently revert, `IntentGatewayV2`/`ExtrinsicIntents` allows users to escrow **arbitrary ERC-20 tokens** (`order.inputs`) as intent inputs. Common stablecoins (USDC, USDT, and similar) implement issuer-controlled blacklists that can be enabled against any address at any time — a setting entirely outside Hyperbridge's control, analogous to EigenLayer's third-party-transfer-forbidden flag. Since the beneficiary address is embedded immutably in the cross-chain `WithdrawalRequest` body and `_withdraw` unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` for every escrowed token in a loop, a single blacklisted beneficiary/token pair causes the entire release to revert with no fallback path.

### Finding Description
`_withdraw` in `IntentsBase.sol` iterates over all escrowed tokens for a commitment and calls `safeTransfer` unconditionally: [1](#0-0) 

This function is reached from `ExtrinsicIntents.onAccept` when a `RedeemEscrow`/`RefundEscrow` ISMP POST request is delivered from the destination chain, and from `onGetResponse` for cross-chain cancellations: [2](#0-1) 

`onAccept` is called by `EvmHost.dispatchIncoming`, which is the sole entry point HandlerV2 uses to deliver a POST request to the destination application: [3](#0-2) 

If the low-level call to `onAccept` reverts (e.g., because `safeTransfer` reverts due to the beneficiary being blacklisted by the token issuer), the host deletes the receipt and returns without reverting the whole batch — so the message stays "deliverable" and can be retried. However, retrying delivers the exact same immutable `WithdrawalRequest.beneficiary`/token pair, so if the token issuer keeps that address blacklisted, the message can never be successfully delivered, and the escrowed funds for that commitment are permanently stuck: `_orders[commitment][token]` is never decremented, and `_filled[commitment]` is never finalized, so no other recovery path (e.g., a different beneficiary or cancellation) exists once the settlement leg is a `RedeemEscrow`. The order can never move to a resolved state because the token loop must succeed atomically for the withdrawal to finalize.

This mirrors the EigenLayer report precisely: an external, permissionlessly-configurable third-party setting (a blacklist, not an "extreme edge case" like a full pause) can be flipped at any time and Rio/Hyperbridge has no built-in mitigation (no per-token skip-and-continue, no alternate beneficiary mechanism, no pull-based claim pattern) to handle it.

### Impact Explanation
A blacklisted beneficiary permanently freezes the escrowed input tokens for that specific order/commitment. The user's/solver's principal (potentially large amounts, since inputs are user-chosen ERC-20 amounts) becomes permanently unrecoverable, since `_withdraw` requires every token in the batch to transfer successfully before any of the escrow accounting or `_filled` finalization state updates apply. This satisfies "permanent freezing of funds" from an unprivileged, ordinary user/solver-driven code path (placing/filling/cancelling an intent order with an arbitrary ERC-20).

### Likelihood Explanation
Likelihood is realistic and not a purely theoretical/extreme scenario: blacklist functionality is a standard, actively-used feature of major stablecoins (e.g., Circle's USDC, Tether's USDT) that the report's "not an extreme edge-case setting" reasoning directly applies to. Any user placing an order with such a token, or any solver/beneficiary address later becoming blacklisted (for reasons entirely outside Hyperbridge's control, e.g., regulatory action against the wallet), triggers the freeze on the very next attempted settlement delivery.

### Recommendation
Do not let a single token's transfer failure block finalization/state updates for an entire withdrawal batch. Options:
- Update escrow-accounting/`_filled` state before attempting transfers (already partially followed for reentrancy, per the CEI fix), and wrap each token transfer in a try/catch, redirecting failed transfers to a per-beneficiary pull-based claim mapping instead of reverting the whole `_withdraw` call.
- Alternatively, allow a governance/admin path (via the existing `UpdateParams`/`Execute` governance action) to redirect stuck escrow to an alternate address after a timeout, similar to how EigenLayer's report recommends a pass-through/redirect contract pattern.

### Proof of Concept
1. User places a cross-chain order escrowing a blacklistable ERC-20 (e.g., mock USDC-like token) as `order.inputs[0]`, with `beneficiary`/solver address `S`.
2. Token issuer blacklists `S` (a routine, permissionless, third-party action unrelated to Hyperbridge).
3. Solver fills the order on the destination chain; the destination gateway dispatches a `RedeemEscrow` POST request back to the source chain with `WithdrawalRequest.beneficiary = S`.
4. A relayer delivers this via `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `ExtrinsicIntents.onAccept` → `_withdraw`.
5. `IERC20(token).safeTransfer(S, amount)` reverts because `S` is blacklisted; `onAccept` reverts, the host deletes the receipt (retryable) but every subsequent delivery attempt hits the same blacklisted beneficiary and reverts identically. `_orders[commitment][token]` is never decremented; the escrowed input is permanently frozen with no way to redirect it to a non-blacklisted address.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
