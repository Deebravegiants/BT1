### Title
Webhook shop-tenant identity spoofing via header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. The shop that a webhook is attributed to is never part of the signed content, so it can be forged independently of a valid signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the HMAC covers exclusively the JSON payload bytes: [1](#0-0) 

The `shop` accessor, however, reads directly from an attacker-observable HTTP header, unrelated to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Webhooks::Registry.process` uses exactly this check, then immediately trusts `request.shop` as the tenant identifier and hands it to the app's handler as an authenticated fact: [4](#0-3) 

This reproduces the reNFT bug class precisely: the identity-binding equality the gem should guarantee is `verified_bytes == tenant_identifier_bytes`, but in practice `verified_bytes` is `raw_body` while `tenant_identifier_bytes` is the `shop-domain` header — two independent inputs. Before the request: an attacker who is a legitimate merchant on their own store receives a genuine webhook (valid HMAC over their own store's body). After the request: the attacker resends that exact `raw_body`/`hmac` pair to the app's webhook endpoint but substitutes the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched and genuinely valid), yet `request.shop` now returns the victim's domain. The `Registry.process` method (and any handler built on `WebhookMetadata`) receives `shop: <victim shop>` as though Shopify itself vouched for that shop, when in fact only the body content was verified.

### Impact Explanation
This breaks the tenant/shop binding that webhook-consuming apps rely on to route data (e.g., "this order/customer payload belongs to shop X"). An attacker can inject data that is falsely attributed to another merchant's tenant using their own genuinely-signed webhook body, which matches the "cross-tenant access" impact category — forged tenant attribution of otherwise-valid signed data, entirely reachable through this gem's own `Request`/`HmacValidator`/`Registry` code without needing any secret, token, or privileged access.

### Likelihood Explanation
Likelihood is high for any app that (a) is a Shopify merchant itself or can get one legitimate webhook delivered to an app they control, and (b) exposes its webhook endpoint publicly (a normal deployment requirement, since Shopify must be able to reach it). No credentials, TLS interception, or social engineering are required — the attacker only needs to capture one legitimate `raw_body`+`hmac-sha256` pair (trivial, since they can generate webhooks on their own store) and replay it with a modified `shop-domain` header directly to the app's public callback URL.

### Recommendation
Bind the shop (and other headers used for routing, such as `topic`/`webhook_id`) into the signed content that is actually verified, or otherwise never trust `request.shop` as an authenticated tenant claim by itself. Concretely: extend `to_signable_string` (or a separate verification step) to incorporate the `shop-domain` header (and other operative headers) into the value that is HMAC-checked, so any header substitution invalidates the signature. At minimum, document prominently that `WebhookMetadata#shop` is **not** authenticated by the HMAC and that consuming apps must independently confirm the shop is one they have actually installed/have an active session for before trusting the payload's tenant attribution.

### Proof of Concept
1. App attacker "AttackerShop" installs the app and receives a legitimate webhook for topic `orders/create` with a real `x-shopify-hmac-sha256` value computed by Shopify over the JSON body `B`.
2. Attacker captures headers + body of that request.
3. Attacker POSTs directly to the target app's webhook endpoint with:
   - `raw_body = B` (unchanged)
   - `x-shopify-hmac-sha256 = <original, unchanged>`
   - `x-shopify-shop-domain = victim-shop.myshopify.com` (forged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks `raw_body` against the HMAC: [5](#0-4) 
5. `request.shop` returns `"victim-shop.myshopify.com"`, and the handler receives `WebhookMetadata` with that forged shop value, attributing the attacker's data to the victim tenant.
