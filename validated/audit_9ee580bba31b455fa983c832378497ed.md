Audit Report

## Title
`move_claim` unconditionally remaps `Preclaims` to `new` even when the `old` claim was already consumed, corrupting the preclaim linkage with no error signaled - (File: polkadot/runtime/common/src/claims/mod.rs)

## Summary
`Pallet::move_claim` migrates `Claims`/`Vesting`/`Signing` from `old` to `new` via `Option::take`/`map`, which is a silent no-op if `old` has no entry (e.g., already consumed by a prior `claim`). The `Preclaims` remap for `maybe_preclaim`, however, is gated only on whether the stored preclaim value equals `old`, not on whether the migration actually moved a claim, so it can rewrite `Preclaims` to point at `new` even when `new` has no backing `Claims` balance, and the call still returns `Ok(Pays::No.into())` with no error.

## Finding Description
In `move_claim`, the migration logic is: [1](#0-0) 

`Claims::<T>::take(&old).map(|c| Claims::<T>::insert(&new, c))` returns `None`/no-ops if `old` has no claim. The `Preclaims::<T>::mutate` block is conditioned solely on `maybe_o.as_ref().map_or(false, |o| o == &old)` — independent of whether the `Claims::<T>::take(&old)` above actually returned `Some`. `claim` (unsigned, callable by anyone with a valid ECDSA signature for `old`) drains `Claims`, `Vesting`, `Signing` for `old` via `process_claim` but never touches `Preclaims`: [2](#0-1) . Only `attest` removes the `Preclaims` entry, and only after a successful `process_claim`: [3](#0-2) . Thus if `claim`/`claim_attest` for `old` executes before a pending `move_claim(old, new, Some(preclaim))`, the `Preclaims` entry for `preclaim` still equals `old` and gets unconditionally rewritten to `new`, even though `Claims::<T>::get(new)` is empty. This matches the code exactly as described in the submitted claim.

## Impact Explanation
This produces a state inconsistency: `Preclaims` can reference an Ethereum address with no backing `Claims` balance, and `move_claim` gives its caller (a privileged `MoveClaimOrigin`/Root actor) no failure signal that the migration did not actually move any funds. A subsequent `attest` by the affected account will fail with `SignerHasNoClaim` before reaching `Preclaims::<T>::remove`, leaving the account's `Preclaims` entry permanently pointing at a non-existent claim until another privileged intervention. No unauthorized fund transfer occurs — the party racing with `claim()` only receives funds that were already claimable via `old`'s valid signature; the impact is a griefing/DoS of the intended claim-migration outcome for the `preclaim` account holder, not a loss of already-secured funds.

## Likelihood Explanation
Both `move_claim` and `mint_claim`/`Preclaims`-affecting paths require privileged (`MoveClaimOrigin` or Root) action to be in flight simultaneously with an unprivileged actor's `claim`/`claim_attest` call for the same `old` address — this is a genuine race condition triggerable by an unprivileged party (front-running an unsigned extrinsic already visible in the mempool, or the legitimate signature holder racing the migration), consistent with the described exploit path. The precondition is narrow (a pending privileged `move_claim` for a specific `old` value, plus a party with the corresponding valid signature), making this a real but situational bug that depends on specific operational timing during claims administration.

## Recommendation
Make the `Preclaims` remap conditional on the migration actually succeeding — e.g., check whether `Claims::<T>::take(&old)` returned `Some` (or verify `Claims::<T>::contains_key(&new)` after the take/insert) before rewriting `Preclaims`, and/or surface an explicit error (e.g., a dedicated error variant) when `old` no longer has a claim at call time, instead of silently returning `Ok(Pays::No.into())`.

## Proof of Concept
1. In a mock runtime, insert `Claims::<T>::insert(old, amount)` and `Preclaims::<T>::insert(preclaim_account, old)`.
2. Call `Claims::claim(RawOrigin::None.into(), attacker_dest, valid_sig_for_old)`; confirm `Ok` and `Claims::<T>::get(old) == None`.
3. Call `Claims::move_claim(RawOrigin::Root.into(), old, new, Some(preclaim_account))`; confirm it returns `Ok(Pays::No.into())` with no error.
4. Assert `Preclaims::<T>::get(preclaim_account) == Some(new)` while `Claims::<T>::get(new) == None`.
5. Call `Claims::attest(RawOrigin::Signed(preclaim_account).into(), statement)` and confirm it returns `Err(Error::<T>::SignerHasNoClaim)`, with `Preclaims::<T>::get(preclaim_account)` still `Some(new)` afterward — demonstrating the account is stuck with an unbacked preclaim linkage.
