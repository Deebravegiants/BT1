### Title
Division-by-zero panic in `calc_take_pnl` when normalized pc reserve rounds to 0 - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` computes `y2 = x2 * y1 / x1`, where `x1` is the *normalized* (decimal-scaled) total PC reserve. The guard that decides whether to enter this branch is computed from the *raw* (unnormalized) reserve amounts, so it is possible for the guard to pass while the normalized `x1` used as a divisor is `0`, causing an unwrap panic on `checked_div`.

### Finding Description
`calc_take_pnl` receives `x1`/`y1` as decimal-normalized values (`Calculator::normalize_decimal_v2`), computed by the caller from the raw vault balances: [1](#0-0) 

Inside `calc_take_pnl`, the branch is entered based on the **raw** `total_pc_without_take_pnl`/`total_coin_without_take_pnl` values (`pool_pc_amount`, `pool_coin_amount`), not the normalized `x1`/`y1`: [2](#0-1) 

Once inside the branch, the code performs: [3](#0-2) 

`normalize_decimal_v2` scales `val * sys_decimal_value / 10^native_decimal`: [4](#0-3) 

When `sys_decimal_value < 10^pc_decimals` (a normal configuration, e.g. `sys_decimal_value = 10^6` and `pc_decimals = 9`), any raw PC reserve smaller than `10^(pc_decimals - log10(sys_decimal_value))` rounds down to a normalized `x1 == 0`, even though the raw `pool_pc_amount` used in the guard is non-zero. If the guard condition `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` still evaluates true (e.g., because `pool_coin_amount` is large or `calc_pnl_x`/`calc_pnl_y` targets are small/stale), execution reaches `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` with `x1 == 0`, and `.unwrap()` on `None` panics, aborting the transaction.

This is directly analogous to the reported Union Finance bug class: a derived index/ratio value (there `interestIndex`/`borrowIndex`, here the normalized PC reserve `x1`) is assumed non-zero based on a check performed on a *different* representation of the same quantity (there `loan.principal`, here the *raw* reserve amounts), allowing the actual divisor to be zero while the guard passes.

### Impact Explanation
`calc_take_pnl` is invoked from both `Withdraw`/`Withdraw2` and the swap instructions whenever `amm.status != AmmStatus::WithdrawOnly`: [5](#0-4) 

If this panic condition is reachable, any Withdraw or swap transaction against the affected pool state would abort with a runtime panic instead of failing gracefully, denying LPs and swappers the ability to withdraw funds or trade against that pool until state changes — a denial-of-service on user/LP funds access for that pool, consistent with a "permanent freezing of user or LP funds" impact class if the degenerate reserve state persists.

### Likelihood Explanation
Reaching this exact degenerate state requires a specific combination of extremely low raw PC reserves (small enough to round to 0 after decimal normalization) together with a raw-amount guard that still evaluates true relative to the stored `target.calc_pnl_x`/`calc_pnl_y` (open-orders-based PnL baseline) — this combination depends on pool decimals configuration (`pc_decimals` vs `sys_decimal_value`) and on the specific relationship between current reserves and the stored `TargetOrders` PnL snapshot, which I could not fully trace end-to-end (e.g., whether `calc_pnl_x`/`calc_pnl_y` can independently be driven low enough, or whether other guards elsewhere in the deposit/init path prevent raw PC reserves from ever going this low while `TargetOrders` still reflects a stale/small target). This uncertainty means I cannot conclusively confirm reachability from a single attacker-controlled transaction without further tracing of `TargetOrders` update logic, which limits my confidence that this is a fully exploitable Medium-severity issue as opposed to a theoretical hazard under a narrow decimal/precision configuration.

### Recommendation
Use the same representation (normalized values) consistently for both the guard check and the division, or explicitly guard `x1 != 0` before computing `y2`, returning `AmmError::CalcPnlError` (as the existing else-branch does) instead of allowing a panic.

### Proof of Concept
Not independently constructible from static analysis alone — reaching the panic requires knowing/controlling the live `TargetOrders.calc_pnl_x`/`calc_pnl_y` values and raw vault balances at the same time such that the raw-amount guard passes while normalized `x1` is 0; a Devin agent with local test-harness access (as seen in the existing `#[test]` functions in `processor.rs`, e.g. around lines 3122-3243) would be needed to construct and run a concrete repro using `AmmInfo`/`TargetOrders` test fixtures.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
