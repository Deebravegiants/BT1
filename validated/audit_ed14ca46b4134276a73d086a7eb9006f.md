### Title
Unbacked over-minting via one-directional decimal scaling in `convert_to_erc20`/`convert_to_balance` - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token`'s `send()` and inbound `on_accept`/`on_timeout` handlers convert amounts between a chain's local asset decimals and a per-destination-chain ERC20 decimal precision using `convert_to_erc20`/`convert_to_balance`. Both helpers scale using `erc_decimals.saturating_sub(local_decimals)`, which only correctly handles the case where the ERC20 side has **more or equal** decimals than the local asset. When a registered token's local decimals exceed its configured destination `erc_decimals` (a legitimate, unprivileged-reachable configuration, e.g. an 18-decimal native/local asset bridged to a 6-decimal ERC20 representation), the `saturating_sub` collapses to zero and no scaling is applied at all in the direction that actually needs it, causing minted amounts on the destination chain to be inflated by a factor of `10^(local_decimals - erc_decimals)`.

### Finding Description
`convert_to_erc20` (used in `send()`) and `convert_to_balance` (used in `on_accept`/`on_timeout`) are defined as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions assume `erc_decimals >= local_decimals` and only ever scale "up" by the positive difference. When `local_decimals > erc_decimals`, `erc_decimals.saturating_sub(local_decimals)` saturates to `0`, so the exponent is `10^0 = 1` and **no scaling occurs at all**, instead of the required division/multiplication by `10^(local_decimals - erc_decimals)`.

This is exactly the same bug class as the reported H-3 issue: an exchange-rate/decimal conversion that is only correctly implemented for one direction of the decimal delta, silently failing to invert when the "smaller decimal" side is actually the source instead of the destination.

`send()` calls `convert_to_erc20(amount, erc_decimals, decimals)` where `amount`/`decimals` describe the locally escrowed/burned asset and `erc_decimals` is the destination chain's configured ERC20 precision (`Precisions` storage, populated per `(asset, chain)` by `register_token`/`update_token`): [2](#0-1) 

If an asset is registered such that its local decimals (e.g. 18) exceed the destination chain's configured `decimals` (e.g. 6) — a fully legitimate, admin-set configuration reflecting the real decimal precision difference between the local asset and its EVM-side representation — `convert_to_erc20` fails to divide the raw amount down, so the `Message.amount` dispatched to the EVM contract is `10^(18-6) = 10^12` times larger than intended. The counterpart EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract mints exactly that (inflated) amount to the beneficiary, as seen in `on_accept`/mint flow test expectations: [3](#0-2) 

The symmetric bug exists in the inbound direction: `convert_to_balance` is used in `module.rs::on_accept` and `on_timeout` to convert an incoming ERC20-denominated `message.amount` back to local decimals: [4](#0-3) 

If `erc_decimals < decimals` (local), the division again collapses to a no-op instead of the needed multiplication, silently under-crediting the beneficiary. Both directions are broken for the same reason — the helper only supports `erc_decimals >= local_decimals`.

### Impact Explanation
This is a protocol-wide, unbacked-mint vulnerability. Any signed account can call `send()` on a token whose registered decimal configuration has `local_decimals > erc_decimals` for the chosen destination — this is not a malicious-admin scenario, since asymmetric decimals across chains are a normal real-world occurrence (this very pallet's own test comments confirm decimal mismatches are expected and must be "scaled by 10^6 in both directions"; the bug is that the scaling code silently fails in one of the two directions). Exploiting this lets a user escrow/burn a tiny amount of the local asset and receive a mint of `10^(local_decimals - erc_decimals)`× the correct amount on the destination EVM chain, which can then be redeemed/sold, draining the escrowed native currency reserve or diluting the wrapped supply — a direct path to theft/unbacked mint exactly analogous to the referenced Compound H-3 finding's "protocol-wide losses."

### Likelihood Explanation
High reachability: `send()` is a public, signed extrinsic requiring no special privilege, and the trigger condition (a registered `(asset, chain)` pair where local decimals exceed the destination's configured ERC decimals) is a plausible, non-malicious configuration that the pallet's own registration/update flow permits without any validation preventing it (`register_token`/`update_token` accept arbitrary per-chain `decimals` values). No governance compromise or malicious relayer/collator is required — only a normal token registration with differing decimal precisions and a single `send` call.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling with a symmetric conversion that handles both cases explicitly, mirroring the correct fix pattern from the referenced report:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }.to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add unit tests covering both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases, and add a sanity check in `register_token`/`update_token` (or at minimum document/require) that operators verify decimal configuration, though the primary fix must be in the conversion math itself.

### Proof of Concept
1. Governance registers a local asset `X` with `local_decimals = 18` and, for destination chain `EVM-dest`, sets `ChainConfig.decimals = 6` (a legitimate configuration, e.g. the asset is natively 18-decimal but its EVM wrapped representation only carries 6 decimals) via `register_token`.
2. A user calls `send(SendParams { asset_id: X, destination: EVM-dest, amount: 1_000_000_000_000_000_000 /* 1.0 token, 18 decimals */, recipient, .. })`.
3. Inside `send()`: `decimals = 18`, `erc_decimals = 6`. `convert_to_erc20(1e18, 6, 18)` computes `erc_decimals.saturating_sub(local_decimals) = 6u8.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18` (unscaled), instead of the correct `1e18 / 10^12 = 1e6`.
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract, which mints `1e18` raw units to the recipient — interpreted at the contract's actual 6-decimal precision, this is `1,000,000,000,000` whole tokens instead of the intended `1` token, a 10^12x over-mint for every unit escrowed.
