### Title
Fee-on-transfer output tokens let a solver claim full escrow while the beneficiary receives less than owed - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol, evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentGatewayV2`'s same-chain and cross-chain fill paths pay the order beneficiary via `IERC20(token).safeTransferFrom(msg.sender, beneficiary, amount)` and then immediately treat `amount`/`totalRequired` as fully delivered to compute escrow release and fill status, with no check of the beneficiary's actual balance delta.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol`), the solver's output payment is sent directly to the beneficiary: [1](#0-0) 
Immediately after, the code computes `amountFilled`, decides `isFullyFilled`, and on full fill releases the *entire remaining escrow* to the solver: [2](#0-1) 
There is no post-transfer balance check on `beneficiary` — unlike the input side of `placeOrder`, which explicitly measures `balanceOf` before/after specifically to handle fee-on-transfer tokens: [3](#0-2) 

The identical pattern exists in `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`): tokens are pushed to `beneficiary` via `safeTransferFrom`, and the full `order.inputs` are then unconditionally posted for release on the source chain via `RedeemEscrow`, with no verification that the beneficiary actually received `totalRequired`: [4](#0-3) 

If the order's output asset (`order.output.assets[i].token`, chosen by the user when placing the order) is a fee-on-transfer or rebasing token, the beneficiary receives `totalRequired × (1 - fee)` while the contract still marks the fill as complete (`amountFilled == totalRequired`) and releases 100% of the corresponding escrowed input to the solver.

### Impact Explanation
The beneficiary (order user) permanently receives less than the amount the order guaranteed, while the solver is paid the full escrowed input as if the fill were exact. This is a direct, unrecoverable fund loss for the order's beneficiary on every fill involving such a token — the mismatch is baked into escrow accounting rather than being limited to the transfer step, so there is no dust/refund path to make the beneficiary whole. This matches the report's core defect class (funds lost/misaccounted for fee-on-transfer/rebasing tokens during a swap-like operation), now manifesting as a solver-favorable, beneficiary-unfavorable escrow release.

### Likelihood Explanation
No malicious actor is required — any solver simply calling `fillOrder`/the cross-chain equivalent against an order whose output token happens to be fee-on-transfer or rebasing triggers the loss automatically. Because Hyperbridge's `IntentGatewayV2` is a generic multi-token intents system (not restricted to a fixed allowlist of "safe" ERC20s), such tokens can appear as order outputs, especially since the input side of `placeOrder` already anticipates and defends against exactly this class of token, showing the risk is recognized elsewhere in the same contract family but not mitigated here.

### Recommendation
Mirror the fee-on-transfer handling already used for order inputs in `placeOrder`: measure `beneficiary`'s (and protocol's) actual balance delta around each `safeTransferFrom` in `_fillSameChain` and `_fillCrossChain`, and base `amountFilled`/`isFullyFilled`/escrow release strictly on the amount actually received rather than the nominal `fillAmount`/`totalRequired`.

### Proof of Concept
1. User places a same-chain order with `output.assets[0].token` = a 1% fee-on-transfer token, `amount = 1000`, and `inputs[0]` = 1000 USDC escrowed.
2. A solver calls `fillOrder` with `outputs[0].amount = 1000`. `IERC20.safeTransferFrom(solver, beneficiary, 1000)` executes, but the beneficiary's balance only increases by 990 (1% burned as fee).
3. The contract sets `amountFilled = 1000 == totalRequired`, marks `isFullyFilled = true`, and releases the full 1000 USDC escrow to the solver via `_withdraw`.
4. Beneficiary ends up 10 tokens short of the promised output, while the solver received the full input escrow — a permanent shortfall with no compensating mechanism, analogous to the existing `testPlaceOrder_FeeOnTransferToken_*` tests that only cover the input side, confirming no equivalent test/guard exists for the output side.
