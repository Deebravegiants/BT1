This confirms `enforceObservableRules` wraps atom `set` with `makeConcurrent(..., concurrency:1)` internally [1](#0-0) , so `#seedMetadataAtom.set()` calls are serialized and safe even under concurrent `addSeed()` invocations. The vulnerability is confined to `#getExtraSeeds()`/`#setExtraSeeds()` on `walletStorage`, which has no such serialization, combined with the unconditional `this.#keychain.addSeed(data.seed)` call at the end of `addSeed`.

### Title
Unsynchronized check-then-act in `Wallet#addSeed` lets concurrent calls add more seeds to the in-memory keychain than `#maxExtraSeeds` allows, while corrupting persisted `extraSeeds` storage via lost updates - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#addSeed` (features/wallet/module/wallet.js:137-165) is not wrapped in `makeConcurrent`, unlike `create`/`import` which explicitly limit concurrency to 1 [2](#0-1) . Because the cap check (`seeds.length >= this.#maxExtraSeeds`) reads `#getExtraSeeds()` and only later persists via `#setExtraSeeds(seeds)` with a plain read-modify-write on `walletStorage`, concurrent `addSeed` calls race on this check, causing lost updates in `EXTRA_SEEDS_KEY` and an unconditional extra call to `#keychain.addSeed()` for calls that should have been rejected.

### Finding Description
`addSeed` performs: read `#getExtraSeeds()` → check `seeds.length >= #maxExtraSeeds` → push → `#setExtraSeeds(seeds)` (persists whole array) → `#seedMetadataAtom.set(...)` (safe, serialized) → `#keychain.addSeed(data.seed)` (unconditional, no cap check) [3](#0-2) .

`#getExtraSeeds`/`#setExtraSeeds` operate directly on `this.walletStorage` with no locking [4](#0-3) , unlike `create`/`import`, which are explicitly wrapped with `makeConcurrent({ concurrency: 1 })` to serialize access to shared state [2](#0-1) .

If N calls fire concurrently while the persisted length is at `#maxExtraSeeds - 1`, each independently reads the same stale array (length `L < max`), each passes the cap check, and each then unconditionally calls `this.#keychain.addSeed(data.seed)` at the end of the function. Since `walletStorage.set` on `EXTRA_SEEDS_KEY` is a full-array overwrite rather than an append, the persisted array size after all writes settle is at most `L+1` (last-write-wins) — the cap on *persisted storage* can't be exceeded numerically past `#maxExtraSeeds`, but the calls whose writes lost the race still successfully added their seed into the live, in-process `#keychain`, and each also merged its metadata into `#seedMetadataAtom` (safe via `enforceObservableRules`'s internal `makeConcurrent` wrapper) [1](#0-0) . This produces a genuine divergence: `#seedMetadataAtom` and the in-memory `#keychain` can end up tracking more seeds than `#maxExtraSeeds` and more than what's in `walletStorage`'s `EXTRA_SEEDS_KEY`, while some of those "phantom" extra seeds silently disappear from the keychain on the next `lock()`/`unlock()` cycle (which reconstructs keychain state strictly from `#getExtraSeeds()`) [5](#0-4) , leaving orphaned metadata entries in `#seedMetadataAtom` referencing seeds no longer present anywhere.

This is reachable from an unprivileged dapp/RPC path: `application.addSeed` calls `wallet.addSeed` directly with attacker-supplied `mnemonic`/`compatibilityMode` [6](#0-5) , and nothing in the RPC bridge/application layer serializes concurrent `addSeed` invocations the way `create`/`import` are serialized inside `wallet.js`.

### Impact Explanation
Impact is limited to **temporary storage/state integrity corruption**, not secret disclosure or unauthorized signing: the persisted `EXTRA_SEEDS_KEY` array can never mathematically exceed `#maxExtraSeeds` (each write's length is bounded by a validated `L+1 <= maxExtraSeeds`), so this is not "unbounded growth." However, in-memory `#keychain` state and `#seedMetadataAtom` can transiently diverge from persisted `walletStorage`, allowing more than `#maxExtraSeeds` seeds to be usable for signing within the current session, and leaving orphaned/inconsistent metadata entries afterward. This matches a scoped "storage integrity / inconsistent state" impact, but is bounded (session-limited, self-healing on lock/unlock) rather than a durable unbounded-growth or authentication-bypass issue.

### Likelihood Explanation
Requires wallet to be unlocked and the RPC/dapp bridge to allow firing multiple `addSeed` calls concurrently near the `#maxExtraSeeds` boundary — feasible for any origin/dapp with access to `wallet.addSeed`/`application.addSeed`, no privileged state needed. The race window is narrow (between the storage `get` and `set` round trip) but reproducible deterministically in tests by controlling storage latency (as shown in existing atom tests using delayed storage mocks) [7](#0-6) .

### Recommendation
Wrap `addSeed` (and ideally `removeManySeeds`, which has the same read-modify-write pattern on `#getExtraSeeds`/`#setExtraSeeds`) in `makeConcurrent({ concurrency: 1 })`, matching the pattern already used for `create`/`import`, so the check-then-act sequence over `walletStorage`'s `EXTRA_SEEDS_KEY` is serialized and `#keychain.addSeed()` is only called for calls that actually pass the up-to-date cap check.

### Proof of Concept
Integration test in `features/wallet/module/__tests__/index.test.js`:
1. Configure `maxExtraSeeds: 2`. Create/import wallet and unlock.
2. Call `wallet.addSeed({ mnemonic: otherMnemonic })` once to bring stored count to 1 (one below cap).
3. Fire 3 concurrent `wallet.addSeed({...})` calls with 3 distinct valid mnemonics using `Promise.allSettled`.
4. Assert: `seedStorage.namespace('wallet').get('extraSeeds')` length never exceeds `2` (`maxExtraSeeds`) — expected to hold even under the race.
5. Assert (to prove the actual bug): count of seeds present in `keychain` (via spy on `keychain.addSeed` calls or `keychain.exportKey` for each generated seedId) exceeds `maxExtraSeeds`, and/or `seedMetadataAtom.get()` contains more seed entries than `getExtraSeedIds()` returns — demonstrating the metadata/keychain vs. persisted-storage divergence caused by the missing `makeConcurrent` wrapper.
