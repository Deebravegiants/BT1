### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from only the raw request body, while the `shop` (tenant identifier) is read from an HTTP header that is never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid, then dispatches the handler using the unauthenticated `shop` header value. This breaks the identity binding `HMAC(signed_bytes) == HMAC(bytes_acted_on)`, since the `shop` field that determines tenant identity is acted upon but is not part of the bytes that were verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it signs/verifies `verifiable_query.to_signable_string`, which for webhooks is body-only: [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is shared across all shops that install the same app (it is the app's client secret, not a per-shop secret), any unprivileged party who can obtain one genuine `(raw_body, hmac)` pair — e.g., by installing the app on their own store and triggering a webhook event, or via a legitimate own-shop test webhook — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain). The HMAC still validates because it only ever covered the body, and `Registry.process` will hand the forged `shop` to the app's handler as if the event genuinely originated from that other tenant.

This is the same class of bug as the reported analog: a value is trusted and acted on (the command string in `meta-git`, the tenant identifier here) that was never included in the verified/signed material (the sanitized argument, the HMAC digest here).

### Impact Explanation
This allows an attacker who can install the app on any shop (a normal, unprivileged action) to forge webhook events that the host application will process as belonging to a different, victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up sessions, update per-shop records, or trigger the app's own business logic), this can result in cross-tenant data corruption or cross-tenant state changes — a High/Critical impact class ("cross-tenant access") reachable purely through this gem's own webhook-verification code path, without requiring the victim's access token or `api_secret_key`.

### Likelihood Explanation
Moderate to high: an attacker needs only to (a) install the target app on their own or a throwaway shop, which is normal unprivileged behavior for a multi-tenant Shopify app, and (b) capture one legitimate webhook body+HMAC pair sent to the app's public webhook endpoint, which is trivial since the endpoint is Internet-reachable by design. No secrets or privileged access are required to perform the header substitution and replay.

### Recommendation
Bind the tenant identity into the verified material for webhook requests — e.g., include `shop`, `topic`, and `webhook-id` header values in the signable string alongside the body (or otherwise cryptographically bind them), or independently verify that the `shop` header corresponds to a shop session/registration known to the app before dispatching the handler with it. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently corroborated (e.g., against an existing session) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id": 1, ...}
   ```
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) calls `Utils::HmacValidator.validate(request)`, which only checks the body/HMAC pair — this still passes because the body and HMAC are unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, so the host application processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
