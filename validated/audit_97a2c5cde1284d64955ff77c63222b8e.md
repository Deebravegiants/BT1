### Title
Griefing: single already-delivered request/response poisons an entire `HandlerV2` batch, reverting proof verification and delaying delivery of unrelated messages - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` verify an entire batch's Merkle Mountain Range (MMR) membership proof for all `N` requests/responses in one shot, and only *afterwards* check each individual item for a duplicate delivery receipt. Because self-relaying is explicitly permissionless and encouraged (any unrelated party can submit a single leaf via `handlePostRequests` ahead of time), an attacker can pre-deliver one request contained in a relayer's upcoming batch. When the relayer's larger batch transaction then executes, the already-spent MMR proof verification succeeds, but the per-item duplicate check reverts the entire call with `DuplicateMessage()` — wasting the relayer's gas and delaying delivery of every other, unrelated, valid request bundled in that transaction. This is the same bug class as Alchemix's `pokeTokens()` griefing: a batch operation that reverts wholesale because of one item a griefer can unilaterally "complete" first.

### Finding Description
`handlePostRequests` builds the leaf set and verifies the MMR proof for the whole batch **before** checking for duplicates: [1](#0-0) 

The first loop (lines 190-197) only checks destination and timeout, and does **not** check `host.requestReceipts`. The proof verification (lines 199-202) runs against the full leaf array regardless of whether any leaf was already delivered. Only the second loop (lines 204-209) checks `host.requestReceipts(leaf.request.hash()) != address(0)` and reverts the whole call with `DuplicateMessage()` if even a single leaf in the batch was already delivered by someone else.

`handleGetResponses` has the identical two-phase structure and the identical flaw: [2](#0-1) 

Delivery of an individual request/response is explicitly permissionless and self-relaying by any third party is a documented, supported flow: [3](#0-2) [4](#0-3) 

Because anyone with the finalized proof can call `handlePostRequests` for a single leaf (a `PostRequestLeaf` array of length 1 with its own valid MMR proof), a griefer can watch the mempool/indexer for an upcoming relayer batch, front-run it by delivering just one of its constituent requests themselves, and cause the relayer's full-batch `handlePostRequests` (or `batchCall` wrapping it, per `IHandlerV2.batchCall`) to revert entirely: [5](#0-4) 

Because `batchCall` is atomic ("Atomic, any failure reverts the entire batch"), and the SDK/relayer routinely bundles `handleConsensus` together with `handlePostRequests` in a single `batchCall` for self-relay and for the tesseract relayer's batched submission path, a single poisoned leaf can also roll back an accompanying consensus update needed by unrelated, otherwise-valid messages in the same transaction: [6](#0-5) [7](#0-6) 

Note that this is distinct from `EvmHost.dispatchIncoming`, which intentionally avoids reverting the whole batch when an individual module callback fails (it deletes the receipt and returns, letting the rest of the batch proceed): [8](#0-7) 

That defensive pattern (partial success within a batch) exists in the dispatch step but is absent from the duplicate-receipt check in `HandlerV2`'s two handler functions, which is exactly the gap that lets a griefer weaponize one already-delivered leaf against the whole batch.

### Impact Explanation
Any relayer or self-relayer batching multiple `PostRequest`/`GetResponse` deliveries into one `handlePostRequests`/`handleGetResponses`/`batchCall` transaction can have that entire transaction reverted by a third party who has no stake in the messages and gains nothing financially, simply by delivering one of the bundled leaves first. This:
- Wastes the relayer's gas, including the cost of a full MMR multiproof verification (potentially large for big batches) that is discarded on revert.
- Delays delivery of all other unrelated, valid requests/responses bundled in that transaction, and — when a `handleConsensus` call is bundled in the same atomic `batchCall` — can also delay the associated consensus state update needed by other pending messages until the relayer detects the poisoned leaf and resubmits a corrected batch.
- Requires no admin or governance privilege and no financial cost of significance (the attacker only pays the small gas cost for a single-leaf delivery), matching the Immunefi Griefing impact class.

This does not cause theft or permanent loss of funds — the excluded request can be removed and the remaining valid requests redelivered — so it is best characterized, like the original Alchemix finding it mirrors, as a griefing/gas-waste and delivery-delay issue on Hyperbridge's core `HandlerV2` dispatch path.

### Likelihood Explanation
Likelihood is moderate to high in an adversarial environment: self-relaying is explicitly supported and documented, delivery calldata/proofs for individual leaves are discoverable off-chain via the indexer (`postRequestStatusStream`), and batched relayer transactions (`submit_batch_messages`) are visible in the mempool before inclusion, giving a griefer a front-running window on any chain without private/flashbots-style transaction relay.

### Recommendation
Move the duplicate-receipt check into the first loop, before or alongside proof-leaf construction, and skip (rather than include) already-delivered leaves from the proof verification and dispatch — analogous to how `pallet-ismp`'s `handlers::request` re-checks and tolerates a receipt existing without failing the whole batch (`modules/ismp/core/src/handlers/request.rs`), and analogous to `EvmHost.dispatchIncoming`'s pattern of returning early per-item instead of reverting the whole call. This lets legitimate, still-undelivered leaves in a batch succeed even if one leaf was independently delivered beforehand.

### Proof of Concept
1. A relayer builds a `PostRequestMessage` with `requests = [reqA, reqB, reqC]` and a valid MMR `proof` covering all three, intending to call `HandlerV2.handlePostRequests(host, request)`.
2. Before the relayer's transaction lands, an attacker observes `reqB`'s finalized proof (available via the indexer/self-relay flow) and calls `handlePostRequests` themselves with a single-element `PostRequestMessage` containing only `reqB` and its own valid single-leaf MMR proof, setting `host.requestReceipts(reqB.hash())` to a non-zero relayer address.
3. The original relayer's transaction executes: the MMR verification over `[reqA, reqB, reqC]` succeeds (all leaves are still part of the historically finalized MMR root), but the dispatch loop's duplicate check `host.requestReceipts(leaf.request.hash()) != address(0)` at `reqB` is now true, and the entire call reverts with `DuplicateMessage()` — reverting delivery of `reqA` and `reqC` as well, and burning the gas spent on MMR verification.      * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

## Self Relayed Requests

Self-relaying allows you to deliver POST requests to the destination chain yourself, instead of relying on the Hyperbridge relayer network. This is useful when you want full control over delivery timing, need to save on relayer fees, or want to guarantee delivery for critical requests.

The `@hyperbridge/sdk` provides tools to track POST requests and automatically generates the calldata needed to execute [`handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) on the destination chain's [`IHandler`](/developers/evm/api/ihandler) contract.

To learn how to self-relay requests:

1. **[Get Started with the SDK](/developers/sdk/getting-started)** - Install and set up the Hyperbridge SDK
2. **[Track POST Requests](/developers/sdk/tracking/post-requests)** - Monitor request status and extract delivery calldata
3. **[IsmpClient API](/developers/sdk/api/ismp-client)** - Use the [`postRequestStatusStream()`](/developers/sdk/api/ismp-client#postrequeststatusstream) method to get calldata when `HYPERBRIDGE_FINALIZED` status is reached

The SDK automatically generates the [`PostRequestMessage`](/developers/evm/api/ihandler#postrequestmessage) proof and calldata you need to call the [`IHandler.handlePostRequests()`](/developers/evm/api/ihandler#handlepostrequests) function on the destination chain. You can make your users self-relay requests or run a server which can relay requests on behalf of users.

### Self Relaying Requests

When the request reaches `HYPERBRIDGE_FINALIZED` status, the metadata includes a `calldata` field containing the encoded transaction data needed to deliver the request to the destination chain.

**What's in the calldata**: The SDK picks the right shape for the destination handler automatically:

- On **HandlerV1** destinations it's a bare [`handlePostRequests(IHost, PostRequestMessage)`](/developers/evm/api/ihandler#handlepostrequests) — the consensus message must have already landed on the destination (via a separate relayer) before this call can succeed.
- On **HandlerV2** destinations (detected via ERC-165) it's a `batchCall(bytes[])` that bundles `handleConsensus(...)` **and** `handlePostRequests(...)` into a single transaction, pulling the consensus proof directly from Hyperbridge's offchain storage. No separate consensus-message relay is required.

Either way, you submit the raw calldata to the destination's Handler contract — the SDK already selected the correct function selector for you.

**Note:** While the calldata is provided for transparency and advanced use cases, relayers will handle submitting proofs to the destination chain automatically only if a relayer fee was specified when dispatching the POST request. If no relayer fee was provided, you'll need to manually submit this calldata yourself or implement custom relaying logic.

/// Submit a full batch of ISMP messages as a single `IHandlerV2.batchCall` transaction.
///
/// One tx replaces what would otherwise be N separate txs (one per message),
/// cutting gas overhead and nonce management complexity. Atomic: if any
/// inner call reverts, the whole transaction reverts.
pub async fn submit_batch_messages(
	client: &EvmClient,
	messages: Vec<Message>,
) -> anyhow::Result<SubmitOutcome> {
	if messages.is_empty() {
		return Ok((BTreeSet::new(), Vec::new(), Vec::new()));
	}

	let handler_addr = Address::from_slice(&client.handler().await?.0);
	let from = Address::from_slice(&client.address);
	let gas_price = fetch_gas_price(client, false).await?;
	let chain_gas_limit = get_chain_gas_limit(client.state_machine);

	let inner_calls = build_batch_inner_calls(client, &messages).await?;
	let handler_v2 = HandlerV2Instance::new(handler_addr, client.signer.clone());
	let call = handler_v2.batchCall(inner_calls);
	let gas = call.estimate_gas().await.unwrap_or_else(|_| (chain_gas_limit * 8) / 10);
	let calldata = call.calldata().clone();
	let calldata_len = calldata.len();
	let tx_request =
		build_tx_request(from, handler_addr, calldata, gas_price, gas_with_buffer(gas));

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
