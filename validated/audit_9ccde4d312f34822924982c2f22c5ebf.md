### Title
Webhook HMAC signs only `@raw_body`, never `shop`/`topic` headers — captured valid (body, hmac) pairs are freely relabelable and cross-tenant replayable - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/compares the signature solely against that body, never binding it to the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers. An attacker who legitimately receives one valid `(raw_body, hmac)` pair (e.g., from their own dev-shop webhook) can resend that exact byte-identical body/hmac to the same app endpoint with arbitrary `shop-domain`/`topic` headers, and `Registry.process` will accept it and dispatch a `WebhookMetadata` carrying the attacker-chosen `shop`/`topic` values.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`hmac == HMAC(secret, raw_body || shop || topic || webhook_id)` is **false**; in reality `hmac == HMAC(secret, raw_body)` only.

Trace:
- `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 
- `Request#shop`/`#topic`/`#webhook_id` are read straight from attacker-controlled HTTP headers with no signature coverage: [2](#0-1) 
- `HmacValidator.validate_signature` recomputes HMAC over `verifiable_query.to_signable_string` (i.e., `raw_body`) and `secure_compare`s it to the header-supplied `hmac`, independent of any other header: [3](#0-2) 
- `Registry.process` gates only on this HMAC check, then builds `WebhookMetadata` directly from `request.shop`/`request.topic`/`request.webhook_id`, with no cross-check against a known/registered shop list: [4](#0-3) 

Attacker flow: attacker installs the app on their own shop, receives a genuine webhook delivery (`raw_body`, valid `hmac`) for their own store. They replay that identical `raw_body`+`hmac` to the app's webhook endpoint any number of times, each time substituting `x-shopify-shop-domain` and/or `x-shopify-topic` headers. Because `to_signable_string` never includes those headers, `OpenSSL.secure_compare` still matches, `validate` returns `true`, and `handler.handle` is invoked with a `WebhookMetadata` whose `shop`/`topic` were fully attacker-chosen while `body` is the attacker's own genuine payload.

No existing guard in this gem intercepts this: `ShopValidator.sanitize!` is never invoked in the webhook request/registry path (it is only used in OAuth/session flows such as `lib/shopify_api/auth/oauth/auth_query.rb`, `lib/shopify_api/auth/token_exchange.rb`), and there is no webhook-id/nonce replay cache, timestamp check, or shop allow-list comparison anywhere in `lib/shopify_api/webhooks/`.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop`/`#topic` from `Registry.process` to route/attribute data (e.g., to look up a session/access token for that shop, write records tagged with that shop, or branch business logic by topic) can have another tenant's genuine webhook payload replayed and mislabeled as belonging to an arbitrary shop or event type known to the attacker's own delivered event. This is a cross-tenant data-attribution/authentication-bypass condition matching the Critical category "cross-tenant access" — one tenant's (the attacker's) webhook content can be made to appear as another tenant's. It is fully repeatable (no rate limiting, no nonce, no expiry) as long as the attacker retains the captured raw body/hmac pair, and it works against any shop/topic combination the attacker chooses, without needing `api_secret_key` or any credential.

### Likelihood Explanation
- Preconditions: the attacker must possess a genuine `(raw_body, hmac)` pair, which is trivially obtainable by installing the app on their own development shop and letting Shopify deliver one real webhook to them.
- No app secret, TLS interception, or other elevated access is required — the attacker merely POSTs directly to the app's public webhook endpoint with copied body/hmac and forged shop/topic headers.
- Feasibility is high and repeatable indefinitely; this is a design characteristic of the gem's `Request`/`HmacValidator` implementation, not a one-off bug, so it is deterministic and 100% reproducible in a unit test.

### Recommendation
Bind the HMAC signature verification (or an additional authenticated check) to the identifying headers actually used for dispatch: at minimum, host apps consuming `Webhooks::Registry.process` should be advised that `shop`/`topic`/`webhook_id` are unauthenticated relative to the HMAC, and the gem itself should either (a) include `shop`, `topic`, and `webhook_id` in the signable string alongside the body (requires coordinated change since Shopify's platform computes the HMAC over the body only, so this would break compatibility with real deliveries), or (b) at minimum have `Registry.process` cross-validate `request.shop` against `ShopValidator.sanitize!`/a known-registered-shop set before dispatching, and document/require idempotency keying off `webhook_id` with a dedup store to prevent relabeled replays from being treated as distinct events for a different shop.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_tenant_replay_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class CrossTenantReplayTest < Test::Unit::TestCase
      def setup
        super
        @raw_body = '{"id":1,"secret_field":"attacker_shop_data"}'
        @hmac_header = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @raw_body),
        )
        @received_shops = []
        handler = TestHelpers::FakeWebhookHandler.new(
          lambda { |data| @received_shops << data.shop },
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
        )
      end

      def test_same_body_hmac_replayed_with_different_shop_headers_both_accepted
        headers_a = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => @hmac_header,
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        headers_b = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => @hmac_header, # byte-identical hmac
          "x-shopify-shop-domain" => "victim-shop.myshopify.com", # relabeled shop
        }

        req_a = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_a)
        req_b = ShopifyAPI::Webhooks::Request.new(raw_body: @raw_body, headers: headers_b)

        assert(ShopifyAPI::Utils::HmacValidator.validate(req_a))
        assert(ShopifyAPI::Utils::HmacValidator.validate(req_b))

        ShopifyAPI::Webhooks::Registry.process(req_a)
        ShopifyAPI::Webhooks::Registry.process(req_b)

        assert_equal(["attacker-shop.myshopify.com", "victim-shop.myshopify.com"], @received_shops)
      end
    end
  end
end
```
This demonstrates both `validate_signature` calls succeed identically and `Registry.process` dispatches the attacker's own body twice, attributing it to two different shop domains chosen entirely by the attacker via headers.
