### Title
Webhook `shop` (tenant identity) and `topic` are trusted for routing/authorization but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers - which are **not** part of the signed payload - to decide which handler to invoke and which tenant (`shop`) the delivered data belongs to.

### Finding Description
`Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value. [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body` - the `shop`, `topic`, and other headers are excluded from the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` and `request.topic` (both sourced from unauthenticated headers) to select the handler and to populate the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

`WebhookMetadata.shop` is a `T::Struct` field the gem hands to the host app's `WebhookHandler#handle` as the authenticated origin shop for the delivered payload: [4](#0-3) 

This breaks the identity binding: `hmac == HMAC(raw_body)` says nothing about `shop-domain header == originating tenant`. Any party capable of producing one valid `(raw_body, hmac)` pair for a topic they legitimately receive (e.g., a merchant that installed the app on their own shop and receives real webhook deliveries for it) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC check still passes (it only covers `raw_body`), and `Registry.process` will deliver that payload to the handler tagged with the attacker-chosen `shop`, impersonating another tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem asserts to the host application (via `WebhookMetadata#shop`) that a payload came from a specific shop, but that assertion is not covered by the cryptographic check that established authenticity. A host application that uses `WebhookMetadata#shop` (as documented/intended) to route or authorize per-tenant side effects (e.g., writing app data under a shop-domain key, triggering per-shop actions such as data deletion/`GDPR` redact, or account state changes) can be made to act on behalf of, or against, a shop the request did not actually originate from - i.e., cross-tenant access via a forged sender identity, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one legitimately-delivered webhook body+hmac pair (obtainable by simply being a merchant who installs the app, since Shopify sends real webhooks to any installer), and needs to be able to POST directly to the app's public webhook endpoint with a modified header - both of which are available to an ordinary unprivileged app user/merchant without any secret material, credentials, or privileged access. This satisfies the "unprivileged internet user" bar for the analog class described.

### Recommendation
Bind the tenant/topic identity into the signed material instead of trusting bare headers:
- Include `shop-domain` and `topic` in `to_signable_string` (or otherwise incorporate them into the HMAC input), so the signature covers exactly the fields that `Registry.process`/`WebhookMetadata` rely on for identity and routing.
- Alternatively/additionally, document and enforce that host applications must independently verify `WebhookMetadata#shop` against a known/subscribed session for that shop before performing tenant-scoped mutations, since the gem's own guarantee currently does not cover this field.

### Proof of Concept
1. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) and receives a legitimate webhook delivery for a subscribed topic (e.g., `orders/create`), yielding a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's `client_secret`.
2. Attacker replays this exact HTTP request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (topic/body/hmac left untouched).
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`request.rb:36-38`, `hmac_validator.rb:26-31`).
4. `Registry.process` looks up the handler by `request.topic` and invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` even though the payload never originated from that shop (`registry.rb:188-200`).
5. Any host-app logic that keys tenant-scoped actions off `WebhookMetadata#shop` now operates against the wrong tenant.
