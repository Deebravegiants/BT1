### Title
Rounding-favorable buy/sell cycles combined with `Pair.swap`'s `+1` K slack can drain stored `assetReserve` below the launch-time virtual LT reserve, causing a permanent underflow-revert freeze in `Bonding.canGraduate`/`_prepareGraduationLiquidity` - (File: `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
The ALPINE-CVE-2026-42495 class is: a length/size is derived by subtracting two attacker-influenceable, on-disk-derived values without validating that the minuend is ≥ the subtrahend, causing an underflow. alt.fun's analog is the `realLtRaised`/`ltFromPair` computation, which is `storedAssetReserve − virtualLtReserve`, computed in two places that any unprivileged trader can reach via ordinary `Bonding.buy`/`Bonding.sell` (via `Zap.buy`/`Zap.sell`) calls.

### Finding Description
`Bonding` recovers the launch-time virtual LT reserve on the fly and subtracts it from the pair's *stored* `assetReserve` to get the real LT raised by the curve: [1](#0-0) 

and again during graduation prep: [2](#0-1) 

Both subtractions assume `assetReserve ≥ virtualLtReserve` always holds. That invariant depends entirely on `Router`'s buy/sell math and `Pair.swap`'s invariant check never letting the *stored* reserve state drift below the ideal constant-product curve.

`Router._computeBuy` and `Router._computeSell` compute outputs using floor division of `k` by the *new* reserve on the other side: [3](#0-2) [4](#0-3) 

In both `tokensOut = reserveToken - (k / newReserveAsset)` and `assetOut = reserveAsset - (k / newReserveToken)`, the divided term is floor-rounded, which rounds the *subtracted* term down and therefore rounds the *output the trader receives* up — the opposite of the standard AMM safety convention of rounding outputs down in the pool's favor. Every buy and every sell can therefore extract marginally more than the exact continuous-curve amount.

`Pair.swap` then only enforces a loosened invariant with a `+1` slack on both sides: [5](#0-4) 

`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` permits the *actual* stored product `newTokenReserve * newAssetReserve` to sit strictly below `k` by up to roughly `newTokenReserve + newAssetReserve + 1`. Combined with the favorable-to-trader rounding in `_computeBuy`/`_computeSell`, an unprivileged trader can repeatedly buy-then-sell (or sell-then-buy) small amounts on a single `Curve`-stage token. Each round trip is accepted by the loosened K check yet leaves the stored `(tokenReserve, assetReserve)` pair with a slightly smaller real product than the nominal `k`, biased toward decreasing `assetReserve` relative to the ideal curve value for the corresponding `tokenReserve`. Because `virtualLtReserve = k / TOTAL_SUPPLY` is a fixed, immutable identity recovered from `k`, repeated cycles pull the *stored* `assetReserve` down toward — and eventually below — that fixed floor, even though `assetReserve` should mathematically never be able to reach `virtualLtReserve` under exact curve math.

### Impact Explanation
Once `assetReserve < virtualLtReserve`, both:
- `Bonding.canGraduate` (line 692), which is invoked at the end of **every** buy via `_executeBuy` per the project's own docs, and
- `Bonding._prepareGraduationLiquidity` (line 1084), invoked by `_enterGraduating`/`finalizeGraduation`,

underflow and revert in Solidity 0.8's checked arithmetic. Since `canGraduate` is unconditionally called inside every buy, this permanently bricks `Bonding.buy` (and therefore `Zap.buy`) for that token — no further buys can ever succeed. It also makes graduation permanently unreachable for that token, since `_prepareGraduationLiquidity` reverts too. This is a permanent freeze of trader and creator funds: the curve-raised LT and the 750M/250M token split sit stuck on the `Pair`/`Bonding` with no path to trade, sell-triggered graduation, or `finalizeGraduation` recovery — matching the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
The drift per round trip is on the order of a few wei (bounded by the `+1` slack and floor-rounding residuals), and `reserveAsset`/`virtualLtReserve` operate at 1e18-scale LT amounts, so a very large number of round trips would be required from a single attacker to close that gap — likely economically and gas-cost prohibitive at realistic reserve sizes, and each round trip pays the 0.75% Alt Fun fee on both legs which further disincentivizes pure wash-trading. This keeps the likelihood at the lower end, but the path is reachable by a fully unprivileged trader with no special permissions, no reliance on off-chain components, and no upgrade/admin action — only repeated `Zap.buy`/`Zap.sell` calls on a single token they choose to attack (e.g., a token they themselves created, to grief no one but demonstrate/lock a specific token, or a low-liquidity token where the reserve is small enough that the drift-to-reserve ratio is achievable within a bounded number of transactions).

### Recommendation
- Round `_computeBuy`'s `tokensOut` and `_computeSell`'s `assetOut` down using the standard AMM convention (i.e., ceil-round the divisor term consumed by the pool, floor-round the term returned to the trader) so every trade leaves the *pool* with at least as much value as the ideal curve, never less.
- Remove or tighten `Pair.swap`'s `+1` slack to `newTokenReserve * newAssetReserve >= _pool.k` (exact, no slack), or bound the slack to a fixed, provably-safe epsilon rather than a value that scales with reserve size.
- Defensively clamp the subtraction in `_launchTimeVirtualLtReserve`-derived calculations (`canGraduate`, `_prepareGraduationLiquidity`) with a `Math.max`/saturating subtraction so a rounding-induced dip below the virtual floor degrades gracefully (treats real-raised LT as `0`) instead of reverting and permanently bricking the token.

### Proof of Concept
1. Launch a token via `Bonding.launch`/`Zap.createToken` with a small seed, entering `Lifecycle.Curve`.
2. As an unprivileged trader, repeatedly call `Zap.buy(token, small_usdc, 0, referrer)` immediately followed by `Zap.sell(token, tokensJustReceived, 0)` many times on the same token. Each cycle: `Router._computeBuy`/`_computeSell` floor-round in the trader's favor, and `Pair.swap`'s `(x+1)(y+1) >= k` check accepts a stored state whose true product is below `k`.
3. After enough cycles, `(tokenReserve, assetReserve)` no longer satisfies `tokenReserve * assetReserve >= k` in the untouched, i.e. `assetReserve` has drifted below `k / TOTAL_SUPPLY == virtualLtReserve`.
4. The next call to `Bonding.buy` (via `Zap.buy`) reaches `_executeBuy → canGraduate → assetReserve - _launchTimeVirtualLtReserve(...)` at [6](#0-5)  and reverts with an arithmetic underflow panic, permanently freezing that token's curve for every trader, and also breaking `_prepareGraduationLiquidity` at [7](#0-6)  so graduation can never complete either.

*Uncertainty note:* I could not fully verify the exact number of round trips required to cross the drift threshold at realistic reserve magnitudes (this depends on `k`, reserve sizes, and rounding residuals accumulated per trade, which would require a numeric/fuzz simulation not available through static reading). This affects only the likelihood assessment, not the root-cause validity of the underflow path itself.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
