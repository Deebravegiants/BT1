### Title
Permissionless `update_account_threshold` forcibly strips grandfathered LTV snapshots and can freeze a victim's borrows/withdrawals - ([File: contracts/controller/src/risk/params.rs])

### Summary
CVE-2018-16710 is an unauthenticated-access bug: a sensitive endpoint is exposed to anyone, yielding information disclosure and denial of service. The analog in the controller is `update_account_threshold`, a permissionless entrypoint that lets any authenticated-but-unprivileged caller overwrite the cached `loan_to_value` snapshot on *any* account's supply positions. The liquidation-tuple leg is health-factor gated, but the LTV leg is not — so a third party can force-apply a reduced governance LTV to a victim who was grandfathered under the old, higher snapshot, degrading that account's LTV-weighted collateral and breaking the `min_borrow_collateral_usd` floor check that borrows, withdrawals, and strategies enforce. [1](#0-0) 

### Finding Description
`Controller::update_account_threshold(env, caller, has_risks, account_ids)` is declared "Permissionless; requires caller authorization" and dispatches to `risk::params::update_account_threshold`, which only calls `require_authorized_caller` on `caller` — never the account owner — and then iterates arbitrary `account_ids`. [2](#0-1) [3](#0-2) 

For each target, `sync_account_thresholds` loads the victim's supply positions (no owner consent is required beyond the NFT owner being resolvable) and calls `refresh_supply_risk_params`, which unconditionally assigns `position.loan_to_value = effective_config.loan_to_value` and persists the changed map. [4](#0-3) [5](#0-4) 

The protocol intentionally snapshots risk parameters per position: `restamp_listed_supply_ltv` only rewrites positions whose stored LTV differs from the current config, i.e. positions retain their at-entry LTV until restamped. [6](#0-5)  The `FullTuple` scope protects liquidation parameters with an HF ≥ 1.05 gate (`clears_min_hf` / `favors_liquidator`), but the `LtvOnly` scope has no equivalent health or consent gate — lowering a victim's LTV is always permitted. [7](#0-6) 

### Impact Explanation
`get_min_borrow_collateral_usd` is documented as "the LTV-weighted collateral floor ... borrows, withdrawals and strategies check it." [8](#0-7)  After governance legitimately lowers an asset's LTV via `edit_asset_in_spoke`, any account holding that asset keeps its higher stored LTV until restamped. An attacker can call `update_account_threshold(attacker, false, [victim_id])` to collapse the victim's LTV snapshot to the new lower value, reducing `ltv_collateral_in_usd`. For a leveraged account near the floor this can push LTV-weighted collateral below `min_borrow_collateral_usd`, causing `withdraw`, `borrow`, `multiply`, `swap_collateral`, `repay_debt_with_collateral` (with `close_position`), and `flash_position` on that account to revert — a temporary freezing of the victim's collateral until they deleverage or governance restores parameters. It also silently degrades the victim's borrowing power even when solvency is unaffected. This is the "unauthenticated access → denial of service" half of the CVE mapped onto XOXNO: a state-changing operation on *other users' positions* reachable by any unprivileged address with no victim consent and no risk gate on the harmful direction.

### Likelihood Explanation
The attack requires only that current config LTV be lower than the victim's stored snapshot — a routine occurrence whenever governance tightens risk parameters via `edit_asset_in_spoke`. The entrypoint is permissionless, not pause-gated-bypassed (it is `when_not_paused` but so are all normal ops), costs a single call per batch of victims, and needs no capital, flash loan, or oracle manipulation. Every account with a grandfathered higher LTV is a target simultaneously. No privilege, timing window, or victim cooperation is needed. Medium: real and cheap to trigger, but impact is bounded to temporary functional freeze/degraded capacity rather than loss of funds, and it requires a prior governance LTV reduction to create the exploitable gap.

### Recommendation
Gate the LTV downgrade path the same way the liquidation tuple is gated. Concretely, in `refresh_supply_risk_params`/`sync_account_thresholds` (contracts/controller/src/risk/params.rs): when `caller` is not the account owner or delegate and `effective_config.loan_to_value` is lower than the stored snapshot, either skip the position or require the account's resulting state to still satisfy the `min_borrow_collateral_usd` floor and pre-change borrowing status. Alternatively restrict `update_account_threshold` for non-owner callers to only *increase* LTV, or move involuntary restamping behind the liquidation-parameter HF gate so third parties can only tighten terms on accounts that remain comfortably solvent.

### Proof of Concept
1. Governance lists USDC in spoke `s` with `loan_to_value = 8000` BPS and later lowers it to `5000` BPS via `edit_asset_in_spoke`.
2. Victim `V` holds account `A` in spoke `s`, supplied USDC at snapshot LTV 0.8, with open debt such that LTV-weighted collateral at 0.8 is just above `min_borrow_collateral_usd`, but at 0.5 it falls below the floor.
3. Attacker `E` (any address) calls `controller.update_account_threshold(E, false, [A])`.
4. `sync_account_thresholds` resolves `A`'s NFT owner (fail-closed only if unresolvable), `refresh_supply_risk_params` sets `position.loan_to_value = 5000`, `changed = true`, and `set_supply_positions` persists it. [9](#0-8) 
5. `V` now calls `withdraw(A, [(usdc_key, x)])` or `borrow(...)`; the post-operation LTV-weighted collateral check against `min_borrow_collateral_usd` reverts, freezing `V`'s collateral operations until `V` repays enough debt or governance raises LTV — all triggered by an unprivileged third-party call `V` never authorized.

Note: I did not fully verify the exact revert path inside `process_withdraw`'s solvency/floor check or `update_or_remove_supply_position`'s removal condition (e.g., whether LTV 0 can delete a position), so the precise failure mode is inferred from the documented floor semantics at `contracts/controller/src/lib.rs:533-537` rather than traced line-by-line.

```rust
pub(crate) fn restamp_listed_supply_ltv(cache: &mut Context, account: &mut Account) -> bool {
    let mut changed = false;
    let keys = account.supply_positions.keys();
    for hub_asset in keys.iter() {
        let Some(listed) = cache.cached_spoke_asset(account.spoke_id, &hub_asset) else {
            continue;
        };
        let config: AssetConfig = (&listed).into();
        let Some(raw) = account.supply_positions.get(hub_asset.clone()) else {
            continue;
        };
        let mut position = AccountPosition::from(&raw);
        if position.loan_to_value.raw() == config.loan_to_value.raw() {
            continue;
        }
        position.loan_to_value = config.loan_to_value;
        update_or_remove_supply_position(account, &hub_asset, &position);
        changed = true;
    }
    changed
```

```rust
pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}
```
