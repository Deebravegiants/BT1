### Title
Interest-index multiplication can permanently freeze an overgrown market - (File: common/src/rates/simulate.rs)

### Summary
The market accrual path computes `scaled_debt * borrow_index` and `scaled_supply * supply_index` as `i128` RAY values; once interest growth would make either result exceed `i128::MAX`, the accrual reverts before committing a new timestamp, leaving every later operation trapped on the same overflowing accrual. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless except for caller authorization, forwards the selected `HubAssetKey`s to the pool, and the pool calls `interest::global_sync` for each market. [3](#0-2) [4](#0-3) [5](#0-4) 

Inside `accrue_step`, the stored scaled balances are converted to RAY-denominated aggregate values before calculating utilization, and `calculate_supplier_rewards` then multiplies `borrowed` by both the old and new borrow indexes. [1](#0-0) [6](#0-5) 

Those multiplications use `Ray::mul`, which delegates to `mul_div_half_up`; if the exact widened result cannot fit back into `i128`, the function raises `GenericError::MathOverflow`. [7](#0-6) [8](#0-7) [9](#0-8) 

The pool writes the new indexes and timestamp only after `accrue_step` returns, so a transaction crossing the representable-value boundary reverts without advancing `last_timestamp`; every subsequent accrual attempts the same or a larger interval and fails again. [10](#0-9) [11](#0-10) [12](#0-11) 

All ordinary market mutation legs load a synchronized market through `synced_market`, which invokes `global_sync` before applying the operation. [13](#0-12) 

For example, a scaled debt of `9.8e35` becomes unrepresentable once the projected borrow index exceeds approximately `173.6 * RAY`, because `9.8e35 * 173.6e27 / 1e27` is near `i128::MAX`; this is far below the intended index ceiling and therefore can occur while interest remains economically active. [14](#0-13) [15](#0-14) 

### Impact Explanation
Once the threshold is reached, suppliers cannot withdraw and borrowers cannot repay because both operations must accrue the market first; liquidation is blocked by the same dependency. [14](#0-13) [16](#0-15) 

The result is a permanent freezing of user funds and of the affected market’s accounting rather than a one-off failed transaction, since the stored timestamp and indexes remain unchanged while ledger time continues to increase. [17](#0-16) [12](#0-11) 

### Likelihood Explanation
Triggering the terminal revert is permissionless: after the market reaches the vulnerable state, any address can call `update_indexes` with that market’s `HubAssetKey`. [3](#0-2) [4](#0-3) 

Reaching that state requires substantial supplied liquidity, sustained borrowing or supply-index growth, and enough collateral to establish the debt; the existing regression uses one billion 18-decimal tokens of supply and 98% utilization to demonstrate the condition. [18](#0-17) 

The likelihood is therefore market-size dependent rather than universally immediate, but it is deterministic once aggregate scaled exposure and index growth approach the `i128` valuation boundary. [1](#0-0) [9](#0-8) 

### Recommendation
Calculate a per-market representable index ceiling before applying accrual: `min(protocol_index_cap, floor(i128::MAX * RAY / scaled_total))`, computed with widened arithmetic for both `borrowed` and `supplied`. [15](#0-14) [1](#0-0) 

Clamp `new_borrow_index` and `new_supply_index` to those dynamic ceilings and bound accrued rewards so every subsequent aggregate valuation remains representable, or refactor aggregate debt and supply valuation to use a wider numeric type end-to-end. [19](#0-18) [20](#0-19) 

### Proof of Concept
The following sequence assumes a configured 18-decimal market with at least `1_000_000_000` whole tokens of supplier liquidity and sufficient cap headroom, as reproduced by the existing regression fixture. [18](#0-17) 

```rust
let market = HubAssetKey { hub_id, asset: big18 };
let collateral = HubAssetKey { hub_id, asset: col };

let account_id = controller.supply(
    attacker,
    0,
    spoke_id,
    vec![(collateral, sufficient_collateral)],
);

controller.borrow(
    attacker,
    account_id,
    vec![(market, 980_000_000 * 10i128.pow(18))],
    None,
);

// After ledger time advances far enough that
// borrowed_scaled * projected_borrow_index / RAY > i128::MAX:
controller.update_indexes(attacker, vec![market]); // reverts with MathOverflow
```

The checked regression advances time and calls `update_indexes` until `MATH_OVERFLOW`, while the stored borrow index remains below its protocol ceiling. [21](#0-20) 

After that revert, the same fixture demonstrates that both `withdraw` and `repay` fail with `MATH_OVERFLOW`, confirming that the market cannot recover through ordinary user or liquidation flows. [16](#0-15)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
