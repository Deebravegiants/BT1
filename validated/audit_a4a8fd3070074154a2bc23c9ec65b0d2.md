## Analog Found

### Title
Permanent freezing of native-ETH escrow when beneficiary cannot accept a raw ETH transfer - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The IntentsV2 escrow contracts (`ExtrinsicIntents.sol` / `IntrinsicIntents.sol`, via the shared `IntentsBase.sol`) release native-ETH order inputs by calling `_sendValue`, a raw `call{value: amount}("")` that unconditionally reverts if the receiving address cannot accept ETH. Unlike the analogous `WrappedHyperFungibleToken`, which falls back to delivering wrapped ERC-20 (WETH) when the native push fails, `IntentsBase._withdraw` has no fallback: a beneficiary that cannot accept raw ETH permanently blocks release of the escrowed native token, matching the class of bug in the Tokemak `withdraw()` report where the ETH-specific code path could not complete and locked funds.

### Finding Description
`_sendValue` is the sole native-token transfer primitive used by escrow settlement: [1](#0-0) 

It is invoked from `_withdraw`, which is the function that both the cross-chain `RedeemEscrow`/`RefundEscrow` settlement path (`onAccept`) and the same-chain cancel/partial-fill paths use to release escrowed `address(0)` (native ETH) inputs to a beneficiary: [2](#0-1) 

The beneficiary address for a cross-chain settlement is fixed at order-placement/fill time and encoded immutably into the `WithdrawalRequest` body dispatched over Hyperbridge: [3](#0-2) 

If that beneficiary is a smart contract with no payable `receive`/`fallback` (or one that reverts on plain ETH receipt — deliberately or as an implementation artifact, e.g. a multisig, vault, or any contract not written to accept bare value transfers), `_sendValue` reverts, which reverts the whole `onAccept` call. `EvmHost.dispatchIncoming` treats this as an ordinary failed delivery: it deletes the request receipt so the message is nominally "retryable" by a relayer: [4](#0-3) 

However, because the beneficiary encoded in the message body is immutable, every retry hits the identical revert. There is no code path (no re-wrap-to-WETH fallback, no alternate claim function, no way for the beneficiary to specify a different receiving address) to recover the escrowed native ETH — it is stuck in the contract's balance behind the `_orders[commitment][address(0)]` accounting entry forever.

This is structurally the same defect class as the reported Tokemak issue: a withdrawal code path that is only correct for ordinary EOA/payable recipients and has no accommodation for the case where the counterparty cannot receive raw native value, resulting in funds that can never be withdrawn. The `WrappedHyperFungibleToken` contract in the same codebase demonstrates the fix pattern was already known to be necessary elsewhere (try native push, fall back to ERC-20/WETH delivery on failure): [5](#0-4) 

but this mitigation was not applied to the intents escrow's `_sendValue`/`_withdraw`.

### Impact Explanation
Any cross-chain or same-chain intent order whose input token is native ETH and whose eventual beneficiary is a contract address that cannot accept a plain ETH transfer (RedeemEscrow beneficiary = the filler/solver's address at fill time; RefundEscrow/cancellation beneficiary = `order.user`) results in that order's escrowed ETH being permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract with no recovery mechanism. Because a solver address is attacker-controlled at fill time in the cross-chain flow, and `order.user` is user-controlled in the refund/cancellation flow, this can be triggered unintentionally by a normal smart-contract wallet/solver, or intentionally to grief/DoS a specific order's escrow release — constituting a permanent freezing of user or protocol funds.

### Likelihood Explanation
Likelihood is moderate to high in practice: solvers and users increasingly interact via smart-contract wallets, multisigs, or vault contracts, some of which do not implement a payable fallback for unsolicited native-value transfers. No privileged action is required — a single order fill, cancellation, or refund settlement by an unprivileged actor is sufficient to trigger the freeze; it requires no malicious relayer, admin, or governance action, only that the destination address of the payout is a contract lacking a receive/fallback.

### Recommendation
Mirror the pattern already used in `WrappedHyperFungibleToken`: when the native-ETH push in `_sendValue`/`_withdraw` fails, fall back to delivering an equivalent ERC-20/wrapped representation (e.g., wrap into WETH and `safeTransfer` it) instead of reverting the whole settlement. Alternatively, introduce a pull-based claim mechanism that lets the beneficiary (or its recipient of choice) withdraw the escrowed amount later, decoupling `onAccept`'s success from the beneficiary's ability to accept bare ETH.

### Proof of Concept
1. Deploy a minimal contract `NoReceive` with no `receive()`/`payable fallback()`.
2. Place a cross-chain order on the source chain with `inputs = [{token: address(0), amount: X}]` and `output.beneficiary` pointing anywhere valid.
3. On the destination chain, have `NoReceive` (via a proxy/relayer acting on its behalf, or simply set `msg.sender` = `NoReceive` in a forge test using `vm.prank`) call `fillOrder`, making the filler (and therefore the eventual `RedeemEscrow` beneficiary) `NoReceive`.
4. Once the `RedeemEscrow` message is delivered to the source chain and `onAccept` invokes `_withdraw`, the `_sendValue(beneficiary, amount)` call to `NoReceive` reverts, causing `onAccept` to revert. `EvmHost.dispatchIncoming` deletes the receipt (per `evm/src/core/EvmHost.sol` lines 805-817), leaving the message "retryable" — but every subsequent relayer resubmission hits the identical revert since the beneficiary in the message body cannot change, permanently freezing the escrowed `X` ETH in `IntentGatewayV2`/`ExtrinsicIntents`.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
