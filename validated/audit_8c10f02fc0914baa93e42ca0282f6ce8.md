## Analysis

Mapping the report's "single point of failure / unchecked privileged identity" bug class to this gem's actual attack surface, the strongest analog is in webhook processing: **the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are never covered by the HMAC signature**, yet they are trusted as the tenant identity passed to the app's webhook handler.

### Binding that should hold (and doesn't)
`hmac-verified(body)` should imply `shop header == shop that produced body`, but the gem only proves:

`HMAC_valid(raw_body, api_secret_key) == true`

while `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` are all pulled straight from unauthenticated HTTP headers. [1](#0-0) [2](#0-1) 

`Registry.process` verifies the HMAC over the request and then dispatches the handler using the unauthenticated `shop` field: [3](#0-2) 

### Why this is exploitable by an unprivileged actor
Shopify computes webhook HMACs using the **app's `api_secret_key`, which is shared across every shop that installs the app** — it is not shop-specific. Any merchant who installs the app (an "unprivileged internet user" with respect to other tenants of the same app) legitimately receives real webhooks with valid `hmac-sha256` signatures for their own shop and topic. Because the signature only covers `@raw_body` and not the `shop-domain` header, that same attacker can replay the captured `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only recomputes over the body: [4](#0-3) 

The forged request reaches the app's handler tagged with the victim's shop identity, breaking the tenant-isolation binding this gem is expected to provide.

### Title
Webhook `shop-domain`/`topic`/`webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC verified by `Utils::HmacValidator` never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` trusts these headers directly to build the `WebhookMetadata` passed to app handlers.

### Finding Description
Because Shopify apps share a single `api_secret_key` across all installed shops, any merchant with the app installed can capture a genuine `(body, hmac)` pair from a webhook delivered for their own shop and replay it to the same public webhook endpoint with an altered `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at a different, victim shop. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the signature against `raw_body`, so the forged shop header passes verification unchanged, and the handler receives `WebhookMetadata` claiming the data belongs to the victim shop. [3](#0-2) 

### Impact Explanation
If an app's webhook handler uses `data.shop` to select which tenant's records to create/update/delete (a standard and documented pattern), an attacker-installed shop can inject attacker-controlled body content attributed to an arbitrary victim shop, corrupting victim data or triggering tenant-scoped side effects without any credentials belonging to the victim. This is cross-tenant access/data injection across the isolation boundary the HMAC is meant to enforce.

### Likelihood Explanation
Requires only that the attacker be a legitimate (unprivileged relative to other tenants) installer of the target app who can receive their own real webhooks — no `api_secret_key`, access token, or victim credentials needed. The webhook endpoint URL is typically not secret (documented in app configuration), and the shop header is the only "identity" signal not covered by the shared-secret HMAC.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values as part of the signed payload verification (or otherwise cryptographically bind them to `raw_body`), or require the consuming app be documented to cross-check `data.shop` against the shop that owns the specific webhook subscription/id via a separate authenticated lookup rather than trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a legitimate webhook from Shopify for their own shop, capturing `raw_body` and the valid `x-shopify-hmac-sha256` value (both computed with the app's shared `api_secret_key`).
3. Attacker POSTs the same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` verifies `Utils::HmacValidator.validate(request)` against `raw_body` only — validation succeeds.
5. The app's registered handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, as shown by the flow in [3](#0-2)  and the unsigned `shop` accessor in [5](#0-4) .
