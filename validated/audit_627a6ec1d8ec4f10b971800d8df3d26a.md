### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body, not the sender-identifying headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature checked by `Utils::HmacValidator.validate` cryptographically covers just the payload bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values that the app relies on to identify *which tenant* the webhook belongs to are read straight from unauthenticated HTTP headers and are never bound into the signed data. `Registry.process` then forwards these unauthenticated header values directly to the app's handler as the trusted tenant identity.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from HTTP headers with no cryptographic tie to the signed body: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the expected signature over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header: [4](#0-3) 

`Webhooks::Registry.process` accepts the request once this body-only HMAC passes, and then dispatches the handler using the *header-derived* `shop`/`topic`/`webhook_id`, which were never covered by the signature: [5](#0-4) 

The identity-binding equality that should hold is: `bytes verified by HMAC == bytes the handler trusts as the request's tenant identity`. In this implementation, `bytes verified` = `@raw_body` only, while `bytes trusted for tenant identity` = `shop`/`topic` parsed from headers — these two are disjoint. Because the same `api_secret_key` is shared by the app across all of its installed shops, any shop that has the app installed can obtain a body+HMAC pair that is valid for the app's secret, then replay that same body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes, and `Registry.process` will hand the attacker-controlled body to the app's handler tagged with a victim shop's identity.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce. An app that keys locally stored records (orders, customers, inventory, GDPR events, etc.) by `WebhookMetadata#shop` can be made to attribute attacker-supplied webhook content to a different, victim merchant, since the shop identity is never authenticated — only the payload bytes are. This is a cross-tenant data injection primitive stemming directly from the gem's `Webhooks::Request`/`Registry`/`HmacValidator` design, falling under the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Any user who can install the target app on their own store (an ordinary, unprivileged merchant) legitimately receives real webhook deliveries signed with the app's shared `api_secret_key`. Capturing one such delivery (body + `X-Shopify-Hmac-Sha256` header) and replaying it to the app's public webhook URL with a modified `X-Shopify-Shop-Domain` header is a low-effort, purely network-level attack requiring no access to the app's secret, no access token, and no social engineering.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, and ideally `webhook_id`/`api_version`) into the signed material, or otherwise cryptographically verify that the `shop` header matches an expected/allow-listed value before dispatching to the handler — e.g., include the shop domain in `to_signable_string`, or independently verify the webhook belongs to a shop that has an active, known installation before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and subscribes to a webhook topic the app registers (e.g., `orders/create`).
2. Shopify sends the app a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC-SHA256 of `B` using the app's `api_secret_key`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H` (e.g., via their own reverse proxy in front of their store's webhook target, or by triggering a webhook whose body they control, such as an order they create with attacker-controlled line items/notes).
4. Attacker replays the exact same `B`/`H` to the app's public webhook endpoint but changes the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` — the app now processes attacker-controlled content under the victim's tenant identity.
