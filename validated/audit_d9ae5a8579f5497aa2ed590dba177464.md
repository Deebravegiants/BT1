## Title
CORS wildcard origin allowlist bypassed by suffix substring match (missing dot boundary) - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's HTTP CORS layer implements wildcard-domain allowlisting (e.g. `*.ethereum.org`) by stripping the `*.` prefix and checking `strings.HasSuffix(originHost, allowedHost)`. Because the leading dot is discarded along with `*`, the suffix check matches any hostname that merely ends with the same characters, so an attacker-controlled `evilethereum.org` origin is incorrectly treated as trusted for a `*.ethereum.org` policy.

## Finding Description
`isAllowedOrigin` handles wildcard matching at [1](#0-0) . When `allowedHost` is `"*.ethereum.org"`, `allowedHost[2:]` produces `"ethereum.org"` with the delimiting dot removed, so `strings.HasSuffix(originHost, allowedHost)` matches any origin ending in the raw substring `ethereum.org`, including non-subdomains like `evilethereum.org`. This function is reached directly from `handleRequest`, the entry point for every request to the Gateway's user-facing HTTP server, which echoes the attacker-supplied `Origin` back into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true [2](#0-1) . No other check (scheme/port matching, exact-host check) mitigates this, since those checks pass fine for `evilethereum.org` against a `*.ethereum.org` allowed entry with matching scheme/port.

I verified this against the current test suite: [3](#0-2)  only tests a negative case (`ethereum.remix.org`, which doesn't share the suffix at all) — it does not cover the suffix-sharing, non-subdomain case (`evilethereum.org`), confirming the gap in test coverage cited in the report is accurate and the bug is unaddressed.

## Impact Explanation
If an operator configures a wildcard `CORSAllowedOrigins` entry (a supported, documented, and tested feature — see [4](#0-3) ), any attacker who registers a domain sharing the suffix (e.g. `evilethereum.org`) can have their origin granted the same CORS trust as legitimate `*.ethereum.org` subdomains, enabling cross-origin browser access to Gateway JSON-RPC responses that should be scoped to the legitimate subdomain family. This maps to the in-scope "cross-user response corruption" / allowlist bypass impact category for the Gateway.

## Likelihood Explanation
Using a wildcard CORS entry is a normal, supported configuration exercised by the existing test suite, not a misconfiguration. Given that configuration, exploitation requires only an unprivileged attacker controlling a suffix-sharing domain and inducing a browser to send a cross-origin request with a crafted `Origin` header to the Gateway's public endpoint — no authentication, special network position, or host access is needed.

## Recommendation
Preserve the dot boundary when comparing wildcard hosts: compare against `"."+strippedHost` (after removing only the `*`), i.e. require `strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost`. Add regression tests for suffix-sharing, non-subdomain origins (e.g. `evilethereum.org` vs `*.ethereum.org`).

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled = true`, `CORSAllowedOrigins = ["https://*.ethereum.org"]` (as in `startNewServer` at [5](#0-4) ).
2. Send a POST request to the Gateway's request path with header `Origin: https://evilethereum.org`.
3. In `isAllowedOrigin`, `allowedHost` becomes `"ethereum.org"` at [6](#0-5) , and `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates `true`, despite `evilethereum.org` not being a subdomain.
4. The response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the bypass — this can be added as a Go test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` at [7](#0-6)  but asserting the header IS set (demonstrating the bug) instead of empty.
