### Title
Unsynchronized global config update during an in-progress signup can produce fraud-decision inconsistencies across pipeline components - (File: `src/brokers/observer.rs`, `src/plans/biometric_pipeline/mod.rs`, `src/plans/mod.rs`)

### Summary
The Observer background task refreshes the shared `Arc<Mutex<Config>>` every `CONFIG_UPDATE_INTERVAL` (10s) with no coordination with an in-progress signup [1](#0-0) . `do_signup`/the biometric pipeline reads this same mutex multiple times at different points in the signup flow (start of signup, debug-report snapshot, face-identifier model config push, and later fraud-decision reads), each independently locking and cloning whatever value happens to be present at that instant [2](#0-1) [3](#0-2) . This is structurally the same class of bug as the FIVA report: two logically-coupled values (the config used to steer/record the fraud pipeline vs. the config actually enforced by the Python fraud-check agent) are read from a shared store at different times without any transactional/versioned guarantee, so a backend config push landing mid-signup can desynchronize them.

### Finding Description
`Config` is held behind a single `Arc<Mutex<Config>>` shared by the whole process. The `Observer::config_update` task overwrites the entire struct in-place whenever a new backend response arrives, on a fixed timer, independent of whether a signup is currently running:
```rust
observer.config_update = Some(tokio::spawn(async move {
    if let Ok(new_config) = Config::download().await {
        *config.lock().await = new_config;
        ...
``` [4](#0-3) 

During a signup, `do_signup` takes an initial snapshot of `Config` fields (including `pcp_v3`, relay parameters, etc.) and separately clones the config again for the `DebugReport` a few lines later:
```rust
let Config { self_serve, pcp_v3, ... } = *orb.config.lock().await;
...
let debug_report = result.debug_report.insert(DebugReport::builder(
    result.capture_start, &result.signup_id, &qr_codes,
    orb.config.lock().await.clone(),
));
``` [2](#0-1) 

Later, deep inside the biometric pipeline (which starts well after `do_signup`'s initial reads — after QR scan, capture, and a 3-second sleep), `run_update_all_configs` fetches the `face_identifier_model_configs` value from the mutex *again*, independently, and pushes it into the face-identifier Python agent that will actually compute the fraud-relevant estimate used to decide `signup_reason`:
```rust
async fn run_update_all_configs(&mut self, orb: &mut Orb) -> Result<()> {
    let face_identifier_model_configs =
        orb.config.lock().await.face_identifier_model_configs.clone();
    self.run_mega_agent_two(
        orb,
        mega_agent_two::Input::FaceIdentifier(face_identifier::Input::UpdateConfig(
            face_identifier_model_configs,
        )),
    ).await?;
    ...
``` [3](#0-2) 

Independently, the pipeline also asks each Python "mega agent" to report back *its own* currently-loaded config (`mega_agent_one::Input::Config` / `mega_agent_two::Input::Config`), which is simply whatever value is cached in the agent process's own `Environment.config` field at that moment, not necessarily what was just pushed by `run_update_all_configs`:
```rust
self.run_mega_agent_one(orb, mega_agent_one::Input::Config).await?;
self.run_mega_agent_two(orb, mega_agent_two::Input::Config).await?;
``` [5](#0-4) 
```rust
ArchivedInput::Config => {
    tracing::debug!("{}: Received input for Config", MegaAgentTwo::NAME);
    Ok(Output::Config(self.config.clone()))
}
``` [6](#0-5) 

These `mega_agent_one_config`/`mega_agent_two_config` values are then baked into the `Pipeline` returned to the caller and presumably persisted/reported as "the config used for this signup's fraud decision":
```rust
Ok(Pipeline {
    ...
    mega_agent_one_config: mega_agent_one_config.unwrap(),
    mega_agent_two_config: mega_agent_two_config.unwrap(),
})
``` [7](#0-6) 

Because there is no versioning, sequence number, or atomic "config epoch" tying together (a) the config snapshot taken at `do_signup` start, (b) the config snapshot in the `DebugReport`, (c) the config value actually pushed into the face-identifier model via `UpdateConfig`, and (d) the config value later reported back by the agent and recorded as authoritative — a backend config push landing in the ~seconds-long window between these reads (QR scan + 3s sleep + capture + pipeline setup) can result in each of these four readers observing a *different* config generation. This is the same root cause pattern as the FIVA report: components that are supposed to act on a single logically-consistent value each maintain/read their own copy from a shared store, and an update message racing against a business-logic message (here: a config-download task racing against an in-flight signup) can desynchronize them.

### Impact Explanation
If a backend operator tightens or loosens fraud-relevant thresholds (e.g. `child_threshold`, `fraud_check_engine_config`, `face_identifier_model_configs`) while a signup is in flight, the signup can be evaluated, recorded, and reported using a mix of pre-update and post-update configuration: the debug report / audit trail can record one config generation while the actual fraud decision embedded in `face_identifier`'s estimate was computed against a different generation (or vice-versa). This creates cross-signup state bleed / misattributed audit data for a single signup and can, in principle, allow a signup to be processed under a stale (weaker) fraud-check configuration relative to what is recorded as having been enforced, undermining the integrity guarantees the debug report and fraud pipeline are meant to provide.

### Likelihood Explanation
The Observer polls the backend for config updates every 10 seconds regardless of signup state [8](#0-7) , and a full signup (QR scan, sleep, capture, biometric pipeline) spans many seconds, so the race window recurs on essentially every signup, not merely an edge case. However, triggering the *specific* mismatch requires an operator-side config change to happen to land in the exact narrow window between the several independent lock acquisitions, which is not attacker-controlled and requires an unprivileged bystander to have no ability to force the timing — this significantly lowers exploitability relative to a directly attacker-triggerable race.

### Recommendation
- Snapshot the `Config` once per signup (or once per major pipeline decision point) and thread that single, immutable snapshot through `do_signup`, `DebugReport::builder`, `run_update_all_configs`, and the fraud-decision logic, instead of re-locking/cloning the shared mutex at each point.
- Alternatively, add a monotonic "config generation" or "config version" field, and have the pipeline verify that the config version used to configure the fraud-check agent matches the version recorded in the debug report and the version used for the final `signup_reason` decision; if they diverge, fail closed (treat as `SignupReason::Failure`) rather than silently mixing generations.
- Consider delaying/deferring the observer's config-swap while `signup_flag` is set (the codebase already tracks this flag for battery-shutdown logic [9](#0-8) ), applying the new config only after the current signup completes.

### Proof of Concept
Not independently reproducible as a network/tool-driven PoC from the index alone; this is a logical/timing race requiring control over backend config push timing. Deterministic reasoning:
1. Backend operator initiates a signup-affecting config change (e.g. lowers `child_threshold`/tightens `face_identifier_model_configs`) at `t0`.
2. A user begins a signup at `t0 - 2s`; `do_signup` takes its first config snapshot (`orb.config.lock().await`) at `t0 - 2s`, before the update lands [10](#0-9) .
3. Observer's background task downloads and swaps the new config into the shared mutex at `t0` [4](#0-3) .
4. Biometric pipeline runs `run_update_all_configs` at `t0 + 5s` (after QR scan/sleep/capture), reading the *new* config and pushing it to the face-identifier agent [3](#0-2) .
5. The `DebugReport` built at step 2's timeframe still reflects the *old* config [11](#0-10) , so the persisted signup record shows a different config than what was actually enforced by the fraud-check model — reproducing the "index mismatch between two components" failure mode described in the external report.

                Ok(())
            }));
