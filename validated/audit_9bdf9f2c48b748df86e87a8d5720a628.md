Webhook `shop-domain` header is not covered by HMAC verification, allowing tenant-identity spoofing on replayed webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` (and `topic`/`webhook-id`/`api-version`) HTTP header to identify which merchant/tenant the payload belongs to. Because the HMAC signature never covers these headers, an attacker who can obtain any one validly-signed webhook body/HMAC pair can resubmit it to the app's webhook endpoint with a different `shop-domain` header and have it accepted as authentic data for an arbitrary shop.

### Finding Description
The intended identity binding is: `HMAC-SHA256(raw_body, client_secret) == received_hmac` should authenticate the entire webhook payload, including which shop it is for. In reality:

- `Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `Request#shop` (and `topic`, `api_version`, `webhook_id`) are read directly from HTTP headers that are never included in the signable string [2](#0-1) .
- `Utils::HmacValidator.validate` only compares the computed signature of `to_signable_string` (the body) against the `hmac` header [3](#0-2) .
- `Registry.process` gates entirely on this body-only HMAC check, then forwards `request.shop` — the unauthenticated header — straight into `WebhookMetadata` and the app's handler [4](#0-3) .

Binding that is broken (as an equality): the check performed is
`HMAC(body) == hmac_header` (true)
but the identity actually acted upon is
`shop_header == shop_that_authorized_body` (not verified — can be attacker-controlled)

Since `shop-domain` is completely outside the signed material, any bytes verified by HMAC (`body`) are decoupled from the bytes parsed for tenant identity (`shop` header). An unprivileged internet user who is a legitimate merchant/attacker of their **own** store — and therefore naturally receives real, validly-signed webhooks for their own shop from Shopify — can capture one such `(raw_body, hmac)` pair and replay it to the same app endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. `HmacValidator.validate` still succeeds (only the body/HMAC pair is checked), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity binding failure of the kind flagged in the analog report: a field ("shop") that is acted upon by downstream business logic is not covered by the cryptographic check ("HMAC") that is supposed to authenticate the whole message. If the host application uses `WebhookMetadata#shop` to key data writes, cache invalidation, order/inventory sync, or session/access-token lookups (the documented, expected usage per `docs/usage/webhooks.md`), an attacker can inject forged data attributed to a shop they do not control, achieving cross-tenant data corruption/confusion without ever possessing that shop's credentials or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category, since the trust boundary between shops is broken purely through gem-level logic.

### Likelihood Explanation
Likelihood is high for any attacker who can install/operate the app on their own store (a normal, unprivileged action — no special credentials or secrets are required beyond running the app as any merchant would). Capturing their own shop's outbound webhook body+HMAC is trivial (it's delivered to their own registered endpoint), and replaying it with a modified, unauthenticated header requires no cryptographic material at all, since the header is simply never part of the signed content.

### Recommendation
Bind the tenant/topic identity into the authenticated material instead of trusting bare headers:
- Include `shop-domain`, `topic`, and `webhook_id` in the string that is HMAC-verified (e.g., construct a canonical signable string combining these headers with the body), or
- At minimum, cross-check `request.shop` against an independently-verified source (e.g., a known/allow-listed shop derived from a session previously established via OAuth/token exchange) before invoking the handler, rejecting any webhook whose header-derived shop cannot be corroborated.
- Document to consumers that `WebhookMetadata#shop` must not be treated as authenticated by the HMAC check alone, or fix this at the gem layer so consumers get a genuinely authenticated shop value by default.

### Proof of Concept
1. Register a webhook handler and app for shop `attacker-shop.myshopify.com`; Shopify legitimately sends a webhook to your app with:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC of BODY>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `BODY` (arbitrary legitimate order JSON for the attacker's own shop)
2. Capture this exact `(BODY, valid_hmac)` pair (trivial, since it was delivered to infrastructure the attacker controls).
3. Replay a new POST to the same app webhook endpoint, keeping `BODY` and `X-Shopify-Hmac-Sha256` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. Trace through the gem: `Webhooks::Request.new(raw_body: BODY, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => valid_hmac})` → `Registry.process(request)` → `Utils::HmacValidator.validate(request)` returns `true` (it only checks `BODY` against `valid_hmac`, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38) → handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never sent any webhook for that shop with this body.
