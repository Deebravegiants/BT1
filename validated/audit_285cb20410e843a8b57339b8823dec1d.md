### Title
Emporium Min-circuit path lets an unprivileged attacker run unauthenticated arbitrary calls from Emporium's identity with zero balance accounting - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` [1](#0-0) . Combined with `EmporiumUpgradeable.verifyWallet` skipping signature verification whenever `stack.signerAddress == address(0)` [2](#0-1) , an attacker can submit a self-crafted `EmporiumStack` whose stateless op performs an arbitrary `.call()` (e.g. `ERC20.approve(attacker, type(uint256).max)`) executed with `msg.sender == Emporium` [3](#0-2) , while every balance-accounting loop that would normally catch value movement iterates zero times because `erc20TokenAddresses.length == 0`.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**.

- `dimensionsCheck` forces `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` and `circomData.slippageValues.length == dimensions.tokenNumber` [4](#0-3) . An attacker sets `dimensions.tokenNumber = 0`, so `erc20TokenAddresses`, `amountChanges`, `slippageValues`, `onChainCreation`, `inputNullifiers`, and `outCommitments` are all empty — this is fully attacker-controlled and passes all checks trivially.
- `formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and calls `formInputEmporiumMin`, which builds only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) [5](#0-4) .
- The corresponding circuit `MainEVMCircuitMin` proves nothing except `message <== Poseidon(1)([messageSeed])`; `calldataHash` and `outTimeStamp` are declared as public inputs but never constrained against anything inside the circuit [1](#0-0) . This proof requires no ownership of any UTXO, no Merkle inclusion, and no EdDSA signature — any unprivileged party can generate it locally with a random `messageSeed`.
- In `EmporiumUpgradeable.runAction`, the `EmporiumStack` is decoded straight from attacker-supplied `circomData.externalActionData.externalActionMetadata` [6](#0-5) . `verifyWallet` only marks the message used and returns immediately when `stack.signerAddress == address(0)`, performing **no** signature check [2](#0-1) .
- With `signerAddress == 0`, every op falls into "CASE 2: Stateless Interaction", which blocks only the `callHinkalWallet`/`doSendToRelay` selectors and otherwise executes `op.endpoint.call{value: op.value}(op.callData)` verbatim with Emporium as `msg.sender` [3](#0-2) . An attacker can target any ERC20 token and call `approve(attacker, type(uint256).max)`.
- `balancesBefore`/`balancesAfter` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, which is empty, so the entire post-loop that checks `balanceChange < 0` and mints UTXOs is skipped (zero iterations) [7](#0-6) .
- In `Hinkal.transact`, the outer balance/slippage-checking loop also iterates over `circomData.erc20TokenAddresses`, so with length 0 it likewise performs zero iterations and enforces nothing [8](#0-7) . (Note: because `slippageValues.length` must equal `dimensions.tokenNumber == 0`, the "slippage set negative" detail in the question doesn't materially contribute — the real gap is that the array is empty entirely, so no floor is ever enforced regardless of sign.)
- `relayerIsValid` is satisfied trivially by using `circomData.relay == address(0)` and `circomData.originalSender == msg.sender` (self-relay, no whitelisted relay needed) [9](#0-8) [10](#0-9) . `checkOnchainCreation` is a no-op on empty arrays [11](#0-10) . `getHashedCalldata` integrity check still passes because the attacker computes it themselves over their own crafted `circomData` [12](#0-11) . `rootHashHinkal`/`rootHashHinkalIndex` need only reference any real historical root (a public value), not attacker-owned leaves.

**Exact attacker call:** `Hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)` where `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, ATTACKER, type(uint256).max)}], ...})`, `a,b,c` a locally-generated proof for `MainEVMCircuitMin` over an arbitrary `messageSeed`.

**Why guards fail:** `performHinkalChecks`, `dimensionsCheck`, `verifyProof`, `rootHashExists`, and the Hinkal-level balance/slippage `require`s are all satisfied vacuously because every array involved has length 0 by the attacker's own choice, which is exactly what routes the transaction to the near-empty Min circuit. `insertNullifiers`/`insertCommitments` operate on empty arrays too, so no leaf state is even touched. None of these checks were designed to also bound what Emporium's `ops` can do when `signerAddress == 0`.

### Impact Explanation
The attacker obtains unlimited ERC20 `allowance` (or, more generally, arbitrary call execution) from Emporium's own address with **no signature, no proof of asset ownership, and no balance accounting whatsoever**. Any ERC20 balance sitting on the Emporium contract at call time — from other users' in-flight multi-op sequences, deposited-but-not-yet-swept funds, accumulated relay fees, or rounding dust — can subsequently be drained via a plain `transferFrom(Emporium, attacker, amount)` call outside of Hinkal. This is direct theft of in-flight/protocol funds held by the Emporium contract, matching the Critical severity category "direct theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner or prover never authorised." The attack is repeatable for every distinct `emporiumMessage` (bounded only by `usedMessages` nonce reuse protection, which does not limit distinct messages) and for every ERC20 token Emporium happens to hold balance of.

### Likelihood Explanation
- No privileged role is required: any EOA can call `Hinkal.transact` directly, self-relay (`relay == address(0)`), and generate the trivial `MainEVMCircuitMin` proof locally since it only requires knowledge of `messageSeed` (a value they choose themselves).
- The only precondition for extracting real value is that Emporium hold some ERC20 balance at attack time, which naturally occurs during any user's Emporium interaction that leaves funds transiently in the contract (e.g., between op steps, or via `signerAddress != 0` smart-wallet flows that route funds through Emporium first).
- Cost is a single L1/L2 transaction plus gas; feasibility is high given only encoding of calldata and generation of a trivial circuit proof are needed — no cryptographic secrets of victims are required.

### Recommendation
- The Min-circuit path should not be usable to authorize arbitrary `ops` execution. Either bind `calldataHash`/the full `externalActionMetadata` into a circuit constraint that is actually checked (not merely a pass-through public signal), or disallow `signerAddress == address(0)` combined with `erc20TokenAddresses.length == 0` in `EmporiumUpgradeable.runAction`.
- Require `verifyWallet` to always validate a real authorization (signature or minimal proof-bound commitment) for every op, even when `signerAddress == address(0)`.
- Do not allow Emporium to hold a nonzero balance of any token across transactions belonging to other principals without that balance being locked/attributed and revalidated regardless of `erc20TokenAddresses.length`; alternatively, forbid stateless calls to arbitrary `endpoint` addresses whose selector matches known approval/transfer-authorizing functions (`approve`, `increaseAllowance`, `permit`, etc.) unless `erc20TokenAddresses` includes that token and passes the accounting loop.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), and a mock ERC20; register `HINKAL_EMPORIUM_ACTION_ID -> Emporium` in `Hinkal.registerExternalAction`.
2. Simulate Emporium holding a balance: mint tokens directly to the Emporium contract address (representing another user's in-flight funds) — assert `token.balanceOf(emporium) == X > 0`.
3. As `attacker` (unprivileged EOA), build `circomData`:
   - `dimensions.tokenNumber = 0`, `erc20TokenAddresses = []`, `amountChanges = []`, `slippageValues = []`, `onChainCreation = []`, `inputNullifiers = []`, `outCommitments = []`.
   - `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress:0, ops:[{endpoint: token, invokeWallet:false, value:0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)}], ...})`.
   - `relay = address(0)`, `originalSender = attacker`.
   - Compute `calldataHash = CircomDataBuilder.getHashedCalldata(circomData)` off-chain and set it.
   - Generate a valid Groth16 proof `(a,b,c)` for `MainEVMCircuitMin` with a locally chosen `messageSeed`, setting `emporiumMessage = Poseidon(messageSeed)`.
4. Call `hinkal.transact(a, b, c, dimensions, circomData)` as `attacker`.
5. Assert: `token.allowance(emporium, attacker) == type(uint256).max`.
6. Follow-up: `attacker` calls `token.transferFrom(emporium, attacker, X)` directly (outside Hinkal); assert `token.balanceOf(attacker) == X` and `token.balanceOf(emporium) == 0` — i.e., assets moved out of Emporium with `balancesBefore == balancesAfter == []` never having recorded the movement, proving the equality is broken.
