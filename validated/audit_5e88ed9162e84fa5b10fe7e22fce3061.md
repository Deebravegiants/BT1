### Title
Unguarded/optional spot-price oracle in Uniswap V4 venue pricing lets an unprivileged order submitter manipulate solver fill price - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
The PancakeHunny incident stemmed from a protocol computing a mint amount off a spot AMM price that a flash-loan attacker could move within a single transaction, with no TWAP or manipulation-resistant check. Hyperbridge's `simplex` intent-filler package has a structurally identical oracle pattern in its Uniswap V4 "venue pricing" path: an unprivileged party (any order submitter, or anyone who can swap in the same pool the filler is LP'ing) can move the pool's instantaneous `sqrtPriceX96` immediately before/around a fill, and the filler prices its output entirely off that spot read, with only an optional static-reference guard standing between the manipulated price and an actual token release.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` calls `state.refresh()` (which re-reads `getSlot0`/`getLiquidity` from the on-chain `StateView` contract) and then derives the USD price straight from the pool's instantaneous `sqrtPriceX96` via `computeDirectPoolPriceUsd`, using `sdkPool.token0Price`/`token1Price` with no averaging, no fee-tier adjustment, and no size/impact term: [1](#0-0) [2](#0-1) 

This spot price flows directly into `FXFiller.resolveLegRates`, which uses it as the leg's fill rate for a curveless pair (`token0` a USD stable), gated only by `checkPriceGuard`: [3](#0-2) 

`checkPriceGuard` is a no-op by design when the operator hasn't configured a `referencePrice`/`maxDeviationBps` pair for the chain — the docs and code explicitly allow "leave the chain unguarded": [4](#0-3) [5](#0-4) 

Even when configured, the guard only bounds deviation from a **static** reference price — it does not detect or resist a same-transaction/adjacent-block price move, and the internal flow doc for this exact path independently confirms there is no execution-cost or size-impact defense: [6](#0-5) 

The resulting rate is used unmodified to compute the token amount the filler pays out (`computeLegPolicyOutput`), meaning an attacker who cheaply moves the pool's spot price (e.g., a large swap against the filler's LP'd pool, or waiting for a thin/stale pool state) right before submitting an intent order can force the filler to release tokens at an economically unsound rate.

### Impact Explanation
The exotic-token pool that prices these venue legs is the same pool the filler is providing liquidity to (`[vault.uniswapV4]` positions), so it is realistically shallow/thin — exactly the "manipulated, stale, or thin pool" scenario the docs themselves call out as the risk this feature is exposed to. An attacker can submit or induce a swap that skews the spot price, then submit (or have already pending) an intent order that the filler prices off that skewed rate via `resolveLegRates`/`computeLegPolicyOutput`, causing the filler to pay out more value than it receives — a direct loss of filler/solver funds analogous to PancakeHunny's spot-price-driven over-issuance.

### Likelihood Explanation
The guard is opt-in and, per the shipped filler-config template, commonly left unset; even configured, it only screens for large one-shot deviations, not within-tolerance-but-still-manipulated moves, and there is no TWAP fallback anywhere in this path. Any unprivileged intent submitter/swap actor with capital to move the (potentially thin, LP-drained) pool can trigger the condition without any special access.

### Recommendation
Require the price guard to be mandatory for venue-priced pairs rather than optional, and replace/augment the spot `sqrtPriceX96` read with a manipulation-resistant reference (e.g., a TWAP over a minimum observation window, or cross-checking against an independent oracle) before it is used to size a fill; additionally, apply a size/impact-aware price rather than extending the raw mid linearly across the whole quantity.

### Proof of Concept
1. Operator configures a curveless USDC/EXOTIC pair with `[vault.uniswapV4]` funding and no `referencePrice`/`maxDeviationBps` (an explicitly supported configuration per `docs/content/developers/evm/simplex/pricing.mdx:72` and `fx.ts:430`).
2. Attacker swaps a modest amount in the same V4 pool the filler's position sits in, moving `sqrtPriceX96` so `token1Price`/`token0Price` misrepresents EXOTIC's USD value.
3. Attacker (or a colluding party) submits an intent order for that pair.
4. `FXFiller.calculateProfitability` → `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` re-reads the now-manipulated `slot0` and returns the skewed price; `checkPriceGuard` passes trivially (unconfigured), so `computeLegPolicyOutput` sizes the fill at the bad rate and the filler executes, releasing more value than the true market price warrants. 	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
```typescript
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}
```

```typescript
	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

**File:** docs/content/developers/evm/simplex/pricing.mdx (L68-72)
```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
