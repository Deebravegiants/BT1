### Title
Arbitrary `EmporiumOperation.endpoint.call` lets any depositor drain ERC20/ETH balances the Emporium contract holds that are not listed in that transaction's `erc20TokenAddresses` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only reconciles balance changes for tokens explicitly listed in `circomData.erc20TokenAddresses`, but the `EmporiumStack.ops` it executes (fully attacker-controlled via `externalActionMetadata`, requiring no signature when `stack.signerAddress == address(0)`) can call any `endpoint` with any `callData`, completely decoupled from that array. Any balance the shared Emporium contract holds in a token that is omitted from `erc20TokenAddresses` (e.g. stranded/residual funds left by a prior user's transaction that didn't sweep every token it touched, or in-flight funds parked mid-batch) can be moved straight to the attacker with a single `token.transfer(attacker, amount)` op, bypassing every balance/slippage invariant.

### Finding Description
The equality the protocol is meant to preserve is: *tokens leaving the action contract in a transaction == `-deltaAmountChanges` Hinkal sent it that transaction* (plus any amount the ops legitimately generated for a listed token). This is enforced only inside two loops that iterate over `circomData.erc20TokenAddresses`:
- `EmporiumUpgradeable.runAction`, lines [1](#0-0) 
- `Hinkal.transact`'s balance/slippage checks, lines [2](#0-1) 

But the ops that actually execute arbitrary calls run *before* any of that accounting, and are completely independent of `erc20TokenAddresses`: [3](#0-2) 

`stack` (including `ops`, `endpoint`, `callData`, and `signerAddress`) is decoded from `circomData.externalActionData.externalActionMetadata`, which the rules confirm is attacker-controlled. When `stack.signerAddress == address(0)`, `verifyWallet` returns immediately with no signature check at all: [4](#0-3) . In that "Case 2" (stateless) branch, the only restriction is blocking the two wallet selectors; any other `op.endpoint.call{value: op.value}(op.callData)` is executed with `msg.sender == Emporium` [5](#0-4) .

Because `EmporiumUpgradeable` is a single shared, stateful contract across all users (it holds an EIP-712 domain, `usedMessages` mapping, and receives ERC20 transfers from `Hinkal._externalTransact` before every call to `runAction`), any ERC20 balance it is holding at call time — whether from a prior transaction that didn't list every token it touched in `erc20TokenAddresses` (so `handleOut` never swept it out), a partially-consumed deposit, or funds parked mid-multi-op sequence — remains on the contract's balance sheet. An attacker can then submit their own `Hinkal.transact` call with a valid proof for an unrelated/minimal transaction, setting `circomData.erc20TokenAddresses` to omit the token holding the residual balance, and craft `stack.ops = [{invokeWallet:false, endpoint: residualToken, callData: transfer(attacker, residualAmount), value:0}]`. This op executes as a plain `token.transfer` from the Emporium contract (which owns the balance) straight to the attacker, entirely outside of `balancesBefore`/`balancesAfter` tracking for that token (since it's not in the array) and outside of Hinkal's per-token `balanceDif == amountChanges[i] + utxoAmount` check (same reason). No `deltaAmountChanges` entry is ever decremented for the stolen token, breaking the invariant "tokens leaving an action in a tx == `-deltaAmountChanges` Hinkal sent it" — value leaves with zero accounted debit.

None of the existing guards prevent this: `performHinkalChecks`/`dimensionsCheck` constrain shape/consistency of the arrays the user submits but do not force `erc20TokenAddresses` to include every token an op might touch; `verifyProof` only proves the shielded balance math for whatever tokens/amounts the attacker chose to declare; `onlyAllowedRecipient` merely restricts `runAction`'s caller to Hinkal itself, not the content of `ops`; and `BalanceChangeShouldBePositive` in lines 142-144 only applies to tokens present in the array.

### Impact Explanation
This is direct theft of shielded/in-flight user funds (or protocol/relay-held residual funds) from the Emporium contract by an arbitrary unprivileged party, matching the Critical impact category. It is fully repeatable: any time the Emporium contract accumulates a non-zero balance in a token not exhaustively reconciled by a given transaction's `erc20TokenAddresses`, any attacker can sweep it in a subsequent (or same-block, later-ordered) transaction, for the cost of one valid proof of an unrelated minimal transaction plus gas.

### Likelihood Explanation
Requires only that the shared Emporium contract holds a nonzero token balance that some transaction did not fully account for/sweep (a realistic condition given `ops` are arbitrary user-supplied DeFi calls whose output tokens are easy to forget to list, or which legitimately leave dust/rounding remainders, or where a multi-op sequence temporarily parks funds mid-flow). No privileged role, no compromised key, and no cooperation from the victim is needed — only observing (e.g. via mempool/block monitoring) that Emporium holds a balance and then submitting a crafted `transact` call with `signerAddress = address(0)` (no signature required) before it gets swept. Ordering within a block (mempool front-running against the legitimate sweep, or landing after a tx that leaves residue) is what the question specifically calls out, and is fully within an unprivileged attacker's control (standard transaction ordering/gas bidding).

### Recommendation
Enforce that every token whose balance the Emporium contract could touch during `ops` execution is included in, and reconciled against, `circomData.erc20TokenAddresses` before and after the ops loop — e.g. by restricting `op.endpoint` calls so they cannot directly invoke `transfer`/`transferFrom`/similar balance-moving functions on arbitrary tokens outside the declared set, or by requiring the contract to hold zero balance of any token not in `erc20TokenAddresses` both before and after `runAction` (revert otherwise), and by not allowing `stack.signerAddress == address(0)` to bypass all origin/authorization checks on `ops` content. At minimum, add a strict invariant that Emporium's balance for every ERC20 it has ever touched returns to zero (or a known/whitelisted escrow amount) at the end of each `runAction` call, verified independently of the attacker-chosen `erc20TokenAddresses` array.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `EmporiumUpgradeable`; register Emporium as an external action and an allowed recipient.
2. Simulate residual balance: directly mint/transfer `residualAmount` of `TokenR` to the Emporium contract address (representing funds stranded by a prior transaction that didn't list `TokenR` in `erc20TokenAddresses`, or seed it via a first `Hinkal.transact` deposit whose `erc20TokenAddresses` intentionally omits `TokenR` after an op sends output there).
3. As an unrelated unprivileged attacker EOA, generate a valid proof for a minimal/unrelated `Hinkal.transact` call (e.g., a no-op or tiny deposit in a different token `TokenA`), with `circomData.externalActionData.externalActionId` pointing at Emporium and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: TokenR, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualAmount)}]`, and `erc20TokenAddresses` that omits `TokenR`.
4. Call `Hinkal.transact(...)`.
5. Assert: (a) `TokenR.balanceOf(attacker)` increases by `residualAmount` after the call; (b) `circomData.amountChanges`/`deltaAmountChanges` contain no entry for `TokenR` (i.e., `-deltaAmountChanges` sums to 0 for `TokenR`); (c) the transaction does not revert despite `BalanceChangeShouldBePositive` and the Hinkal-level `balanceDif == amountChanges[i] + utxoAmount` check, because `TokenR` was never part of `erc20TokenAddresses`. This demonstrates the equality "tokens leaving the action == `-deltaAmountChanges` Hinkal sent it" is broken.
