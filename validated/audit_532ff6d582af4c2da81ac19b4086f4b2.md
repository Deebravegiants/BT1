### Title
Malicious swap routes can smuggle wallet-draining token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller strategy entrypoints accept an opaque caller-supplied route and invoke the configured router with it, while only constraining the controller’s own input authorization and measured output. [1](#0-0)  A malicious route can execute an unrelated `token.transfer(victim, attacker, amount)` beneath the victim’s signed invocation, allowing theft of wallet assets unrelated to the lending position if the victim signs the poisoned authorization tree. [2](#0-1) 

### Finding Description
`swap_tokens` grants the router one exact controller-to-router input transfer, but forwards the attacker-influenced `swap` payload without validating which contracts that route can call. [1](#0-0)  Reachable entrypoints include `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`; `swap_collateral`, for example, authorizes the caller and passes its supplied route into the withdrawal-and-swap flow. [3](#0-2) 

A rogue hop can call a token contract and request `transfer(victim, attacker, amount)` while execution remains beneath the victim’s controller invocation. [4](#0-3)  Soroban records that unrelated transfer as a child of the victim’s `swap_collateral` authorization rather than rejecting it at encoding time. [5](#0-4) 

The controller’s post-route checks only detect controller input overspending, refund unused input, and require positive measured output. [6](#0-5)  They do not detect that the signed route contained an unrelated child transfer from the caller. [2](#0-1) 

### Impact Explanation
A victim who signs the authorization tree produced for a malicious route can lose unrelated wallet tokens up to the amounts embedded in that tree, while still receiving a valid swap output and passing final account risk checks. [7](#0-6)  The harness demonstrates Alice’s entire `WALLET_BALANCE` moving to the attacker while her `ETH` collateral credit still succeeds. [8](#0-7) 

### Likelihood Explanation
Exploitation requires delivering a crafted route and inducing the account owner or delegate to sign its expanded authorization tree, so it is not fully unilateral. [9](#0-8)  The attack is nevertheless practical because route bytes are opaque to the controller, simulation records the hidden child invocation, and a normal-looking fair output lets the transaction satisfy the protocol’s checks. [10](#0-9) 

### Recommendation
Treat swap routes as untrusted authorization-affecting input and require every client to decode the complete simulated authorization tree before signing. Reject any strategy transaction whose caller authorization contains children other than the expected controller-authorized input transfer, and prominently distinguish the controller’s own authorization from unrelated token transfers requested by nested route contracts.

At the protocol boundary, prefer a route representation that constrains callable venue contracts or otherwise prevents route-controlled code from making caller-authorized sub-invocations. If arbitrary venue addresses remain supported, document the signed-tree requirement at the controller interface and emit enough route-decoded information for wallets to block poisoned children.

### Proof of Concept
The existing harness deploys a router that follows the supplied route to an attacker-controlled hop pool. [11](#0-10)  That hop pool calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` even though that token is not part of the lending market. [12](#0-11) 

Under an honestly signed authorization tree with no malicious child, the unrelated transfer is rejected and rolled back. [13](#0-12)  When the victim signs the simulation-recorded poisoned tree, the unrelated token transfer executes and the attacker receives the full wallet balance. [2](#0-1)
