### Title
Unvalidated SPL mint `decimals` leads to unrecoverable arithmetic-overflow panic in decimal normalization, permanently freezing pool funds - (File: `program/src/processor.rs`, `program/src/math.rs`, `program/src/state.rs`)

### Summary
CVE-2017-10792 describes a NULL-pointer dereference in `ll_insert()` reached when GNU PSPP parses attacker-crafted input, crashing the process (DoS). The reachable analog in this codebase is a class of unchecked, panicking arithmetic (`checked_pow(...).unwrap()`, `checked_mul(...).unwrap()`) inside the decimal-normalization helpers, driven by an attacker-controlled value (`SPL Mint.decimals`) that the AMM never bounds-checks. A crafted mint with an abnormally large `decimals` value, combined with normal pool growth, causes every subsequent instruction that touches that pool's vault balances (`Deposit`, `Withdraw`, both swap directions, `WithdrawPnl`) to panic and abort, permanently freezing the LP/user funds already held in that pool's vaults.

### Finding Description
`Processor::unpack_mint` only checks the SPL token program owner of the mint account; it performs no validation on the `decimals` field before it is consumed: [1](#0-0) 

The unchecked `decimals` (a `u8`, attacker-controlled up to 255 because it comes from an attacker-supplied mint at `Initialize2`) is stored directly into `AmmInfo` and used to compute `sys_decimal_value` via an `unwrap()`-guarded power operation: [2](#0-1) 

`sys_decimal_value` is later multiplied by raw token vault amounts (up to `u64::MAX`) inside `Calculator::normalize_decimal_v2`, again guarded only by `.unwrap()`: [3](#0-2) 

This function is invoked on live vault balances in every liquidity/trading path: `Deposit` [4](#0-3) 
`Withdraw` [5](#0-4) 
and `WithdrawPnl` [6](#0-5) 
as well as inside the initial pool setup in `process_initialize2`. [7](#0-6) 

An attacker can create a pool via `Initialize2` using a self-minted SPL Mint with `decimals` set to a value (e.g. 20–38) small enough that `10^decimals` still fits in `U128` (so `checked_pow` inside `AmmInfo::initialize` succeeds and pool creation completes with small initial liquidity), but large enough that once the pool's vault balance grows through normal trading/deposits to only a few `10^18`–`10^19` raw units (well within `u64::MAX`), the product `val * sys_decimal_value` in `normalize_decimal_v2` overflows `U128::MAX` (~3.4×10^38). At that point `checked_mul(...).unwrap()` panics, aborting the transaction. Because this call is unconditionally reached from `Deposit`, `Withdraw`, both swap directions, and `WithdrawPnl`, the pool becomes permanently unusable — including for withdrawal — once the overflow threshold is crossed.

### Impact Explanation
Once the vault balance crosses the overflow threshold for that pool's `sys_decimal_value`, every instruction touching the vault (including `Withdraw`) unconditionally panics inside `Calculator::normalize_decimal_v2`. On Solana, a panicking instruction aborts and reverts the whole transaction, but it also means there is no code path left that can complete a withdrawal, deposit, or swap for that pool ever again. This permanently locks all coin/pc vault balances and outstanding LP tokens tied to that pool — a permanent freezing of user/LP funds, which meets the required impact bar.

### Likelihood Explanation
Reachable from a single, unprivileged, attacker-crafted transaction: the attacker only needs to mint their own SPL token with an adversarial `decimals` value and pass it as `amm_coin_mint`/`amm_pc_mint` to `Initialize2` — no special privileges, leaked keys, or off-chain components are required. `unpack_mint` and `AmmInfo::initialize` never bound `decimals` to a sane range (e.g. ≤ 9), so the pool creation itself succeeds. The freeze condition is then triggered passively as normal deposits/swaps grow the vault balance past the overflow threshold, or can be accelerated by the attacker (as pool creator/first LP) depositing large amounts directly.

### Recommendation
- Reject mints with `decimals` above a defined safe bound (e.g. ≤ 9, matching realistic SPL token conventions) in `unpack_mint`/`process_initialize2` before storing `coin_decimals`/`pc_decimals`.
- Replace all `.unwrap()` calls on `checked_pow`/`checked_mul`/`checked_div` in `Calculator::normalize_decimal`, `normalize_decimal_v2`, and `restore_decimal` with propagated `ProgramError`s (e.g. `AmmError::CalculationOverflow`) instead of panicking, so that overflow conditions fail gracefully with fund-safety preserved rather than making the vault permanently inaccessible.

### Proof of Concept
1. Attacker mints a new SPL token `M` with `decimals = 24` (or any value in the 20–38 range) and mints a small initial supply to themselves.
2. Attacker calls `Initialize2` pairing `M` with a normal mint (e.g. USDC), depositing a minimal initial liquidity (e.g. `init_coin_amount = 1`, `init_pc_amount = 1`). `sys_decimal_value = 10^24` is computed successfully in `AmmInfo::initialize` (state.rs:736-745) since `10^24 < U128::MAX`, and `normalize_decimal_v2(1, 24, 10^24)` in `process_initialize2` (processor.rs:950-959) does not overflow (`1 * 10^24` fits in `U128`), so pool creation succeeds.
3. Attacker (or normal traders) deposit/swap additional `M` tokens into the pool until the raw coin vault balance exceeds roughly `U128::MAX / 10^24 ≈ 3.4×10^14` raw units — a modest amount well under `u64::MAX`.
4. Any subsequent call to `Deposit`, `Withdraw`, `SwapBaseIn/Out`, or `WithdrawPnl` on this pool invokes `Calculator::normalize_decimal_v2(vault_amount, 24, 10^24)` (math.rs:106-116), where `vault_amount * 10^24` now overflows `U128`, causing `checked_mul(...).unwrap()` to panic and abort the transaction.
5. Because `Withdraw` itself panics through the same code path, all coin/pc vault funds and outstanding LP tokens for this pool become permanently unrecoverable.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
