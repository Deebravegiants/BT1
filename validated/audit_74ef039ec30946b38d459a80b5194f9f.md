### Title
`handle_unsigned` charges a fixed static weight regardless of `messages: Vec<Message>` batch size, letting a zero-fee unsigned extrinsic force unbounded state-proof verification work - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Pallet::handle_unsigned` is dispatched with `#[pallet::weight(weight())]`, where `weight()` returns a single hard-coded constant (`Weight::from_parts(300_000_000, 0)`), independent of how many `Message`s (and, within each `Message::Request`/`Message::Response`, how many individual `PostRequest`/`GetResponse` leaves) are contained in the submitted `Vec<Message>`. The call is unsigned and, per the pallet's own documentation, executed completely free of charge. This is the same fee/resource mismatch pattern as the CKB dep-group advisory: a single cheap (here, zero-cost) unit of work can force the node to perform verification work that scales with an attacker-controlled batch size rather than with the price paid.

Because the extrinsic is unsigned and validated via `ValidateUnsigned::validate_unsigned`, this same full `Self::execute(messages.clone())` work is also performed at transaction-pool validation time, before any weight/fee accounting or block-inclusion decision: [4](#0-3) 

Documentation confirms the design intent — "free" processing, with no described bound on batch size: [5](#0-4) 

This mirrors the CKB advisory precisely: the resources required to process the call (proof verification, storage reads for every commitment/state-machine height referenced) are not linear to any bounded, priced quantity — the declared weight is a flat constant while the actual work is `O(total requests across all messages in the batch)`, and the caller pays nothing (unsigned) for either the mempool validation pass or, once accepted by `frame_system::CheckWeight`, a potentially weight-underpriced block-inclusion pass (frame's weight accounting will only reject the extrinsic if the *declared* 300M weight exceeds the block's remaining weight — a large batch that actually consumes far more CPU/DB reads than 300M weight units will still be scheduled as if it only cost 300M, letting it silently overrun the block's real weight budget).

### Impact Explanation
An unprivileged relayer/message submitter can construct a single `handle_unsigned` extrinsic carrying an arbitrarily large `Vec<Message>` (bounded only by `frame_system`'s raw extrinsic byte-length limit, which does not reflect the cryptographic/verification cost of the contents). Since the weight charged is fixed at 300,000,000 regardless of contents, the runtime's weight accounting will under-price such a call, allowing:
- Excessive CPU/storage-read consumption per block relative to the weight budgeted for it, which can degrade block production time and, in the worst case, make a block miss its production/import time targets — a route/messaging-availability impact ("a route unable to deliver messages") since other pending ISMP messages in the same or subsequent blocks are starved of weight budget.
- The same unbounded work is additionally performed by every node validating the unsigned transaction in the pool (via `validate_unsigned`), multiplying the resource cost network-wide for zero cost to the submitter.

This does not directly cause theft or unbacked minting, but it threatens availability of the messaging pipeline itself, which the validation criteria explicitly accept as in-scope impact ("a route unable to deliver messages").

### Likelihood Explanation
Likelihood is moderate: exploiting this requires constructing valid state/consensus proofs for the included requests/responses (so it's not a trivially free spam vector — the attacker must produce state commitments and membership proofs, similar to CKB's dep-group cells needing to reference real cells). However, once a state machine height/commitment is known and accessible (which is public information published on the source chain), any relayer can batch a very large number of already-known valid requests/responses into a single `handle_unsigned` call, since there is no cap on `messages.len()` nor on the per-message request/response vector lengths, and the weight is flat regardless of batch size.

### Recommendation
- Replace the static `weight()` used for `handle_unsigned` with a weight function that scales with the actual number of messages/requests/responses/timeouts in the batch (e.g., `weight_per_message * messages.len() + Σ per-request costs`), similar to how `pallet_ismp_relayer`/other pallets already benchmark per-item costs.
- Introduce an explicit maximum batch size (a `MaxMessages`/`MaxRequestsPerMessage` config constant, enforced both in `validate_unsigned` and in the call itself), analogous to CKB's 64-cell dep-group cap, so that neither the mempool-validation pass nor block-execution pass can be forced to do unbounded work in one call.
- Ensure the `frame_system::CheckWeight` extension actually rejects extrinsics whose *computed* (not just declared) weight would exceed limits, or benchmark `handle_unsigned`'s weight function directly against representative batch sizes so the flat constant is replaced with an accurate linear/benchmarked cost.

### Proof of Concept
1. Obtain (or wait for) a valid, already-known state machine commitment/height for some source chain (public knowledge, or gathered from a previous consensus update on Hyperbridge).
2. Take a large number `N` of already-valid, previously undelivered `PostRequest`s destined for the same state machine height, and their combined membership proof (or repeat known unresolved requests/timeouts across many messages).
3. Submit a single `handle_unsigned(messages)` extrinsic where `messages` is a `Vec<Message::Request>` containing all `N` requests (or many `Message`s each with many requests), with `N` chosen large enough that verification cost (hashing, storage lookups, proof checks) vastly exceeds the fixed 300,000,000 weight unit budget assigned by `weight()`.
4. Observe that:
   - `validate_unsigned` performs the full `Self::execute(messages.clone())` (all N verifications) purely to validate pool admission, at zero fee, for every node relaying/validating the transaction.
   - If included in a block, the extrinsic is weighed at the flat 300,000,000 regardless of `N`, so the runtime's weight accounting does not reflect the true (much larger) cost incurred, undermining the block's weight-based resource budgeting guarantee.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
