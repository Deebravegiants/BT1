Confirmed: in the OAuth `AuthQuery` (`lib/shopify_api/auth/oauth/auth_query.rb`, lines 33-43), the `shop` field is explicitly included in `to_signable_string`, so it is bound by the HMAC. By contrast, the webhook `Request` class binds only the raw body.

### Title
Webhook shop-domain tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body [1](#0-0)  , while `Registry.process` trusts `request.shop` (read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identity handed to the app's webhook handler after only verifying that HMAC [2](#0-1)  . The `shop` accessor itself simply reads the header with no cross-check against the signed payload [3](#0-2)  .

### Finding Description
The binding that should hold is: `HMAC(body, secret) valid` ⇒ `shop header == shop that produced body`. This gem breaks that equality. `HmacValidator.validate` computes `HMAC(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field [4](#0-3)  . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only — none of the HTTP headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) participate in the signature [1](#0-0)  . Yet `Registry.process` forwards `request.shop` (the unauthenticated header value) directly into `WebhookMetadata` passed to the app's handler as the tenant identifier [5](#0-4)  and the gem's own docs instruct app authors to key their business logic (e.g. `perform_later(topic:, shop_domain: data.shop, ...)`) off this unauthenticated field.

This is precisely the "field acted on but not covered by the HMAC" identity-binding failure the report's bug-class describes: the oracle's stable price was trusted without being bound to real market data, and here the tenant-binding `shop` field is trusted without being bound to the HMAC-protected body. This is a real gap relative to the gem's own `AuthQuery`, which explicitly folds `shop` into `to_signable_string` for OAuth callbacks [6](#0-5)  , showing the maintainers understand the need to bind `shop` into the signature elsewhere but did not do so for webhooks.

### Impact Explanation
An unprivileged internet user who can obtain any one validly-signed Shopify webhook body+HMAC pair for a topic the app subscribes to (e.g. from their own development/test store, which any developer can create) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim shop. Because the header is not part of the signed material, `HmacValidator.validate` still succeeds, and the app's handler receives attacker-controlled body content attributed to the victim tenant (`data.shop`). Depending on how the host app uses `data.shop` (e.g., to look up/update the tenant's local record, enqueue tenant-scoped jobs, or update order/product state), this results in cross-tenant data confusion/corruption — the app performing actions against the wrong merchant's stored data based on forged tenant attribution. This maps to the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: exploitation requires the attacker to have at least one legitimately signed webhook (trivially available to anyone who installs the app on their own shop, including via a free development store, for any topic the app subscribes to), plus network access to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only a shop domain string is forged.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically tie the header to the request: include the `shop` (and ideally `topic`) header values in `to_signable_string` for `Webhooks::Request`, mirroring what `Auth::Oauth::AuthQuery` already does, so that `HmacValidator.validate` fails if the `shop-domain` header is altered from what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook (e.g., `orders/create`) to the app's registered endpoint, capturing the raw `body` and the valid `x-shopify-hmac-sha256` header Shopify computed over that body.
2. Attacker resends the identical `body` and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(body, api_secret_key)` — unaffected by the header change — and the check passes [7](#0-6)  .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...)` [5](#0-4)  and performs tenant-scoped side effects (e.g., DB writes, job enqueues) against the victim's tenant using attacker-controlled body content.
