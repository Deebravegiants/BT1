### Title
Webhook shop/topic identity not bound to HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body alone, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` and handed to app handlers come from unauthenticated HTTP headers that are never covered by that signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [4](#0-3) 
The `hmac`, `shop`, `topic`, `api_version`, and `webhook_id` accessors all read straight from request headers with no cryptographic binding between them and the signed body: [5](#0-4) 
`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` header using a constant-time comparison — this only proves the **body bytes** were signed with the app's shared secret, not that the accompanying `shop-domain`/`topic`/`webhook-id` headers are authentic: [6](#0-5) 
`Registry.process` performs exactly that check and then constructs `WebhookMetadata` straight from the unverified header-derived fields: [2](#0-1) 

The identity binding that should hold is `HMAC_valid(body) ⇒ shop_header == shop_that_produced(body)`. In reality the code only proves `HMAC_valid(body)`; `shop` is accepted as-is from a header outside the signed material. Since `api_secret_key` is a single shared secret for the whole app across every merchant that installs it, any entity that can obtain one genuine `(body, hmac)` pair for the app — for example by installing the app on their own store, a routine unprivileged action — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and/or `x-shopify-topic`) naming a different, victim merchant. The signature still validates because the header isn't part of the signed data.

### Impact Explanation
The app's own webhook handler, following this gem's documented usage, keys tenant-scoped processing (session lookup, order/product sync, job enqueueing) off `data.shop` [7](#0-6) . An attacker can therefore inject webhook events that the app attributes to any other shop using the same app, causing cross-tenant data confusion/corruption (e.g. triggering another merchant's order-processing logic with attacker-chosen body content, or polluting per-shop caches/queues) — this satisfies the cross-tenant access criterion.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint and possession of one legitimately-signed `(body, hmac)` pair from any shop's installation (trivial to obtain by installing the target app on an attacker-controlled test store, which is unprivileged and doesn't require the app's `client_secret`). No credentials of the victim shop are needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the payload before verifying the HMAC), consistent with how `Auth::Oauth::AuthQuery#to_signable_string` binds all identity-relevant fields for OAuth callback verification [8](#0-7) . At minimum, document and enforce that `data.shop` must be cross-checked against the shop of the session/webhook subscription id that was actually registered for that topic before being trusted as a tenant identifier.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker.myshopify.com"
#    and receives a genuine webhook, capturing:
raw_body = '{"id":1,"note":"legit order for attacker shop"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
hmac_header = Base64.encode64(valid_hmac) # captured from real Shopify delivery

# 2. Attacker replays the exact same body+hmac to the app's public webhook URL,
#    but swaps the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => hmac_header,       # unchanged, still valid
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unsigned
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# => HmacValidator.validate(req) succeeds (only raw_body is checked),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    and the app processes attacker-supplied data as if it came from the victim shop.
```
