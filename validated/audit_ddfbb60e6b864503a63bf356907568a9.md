### Title
Webhook shop attribution can be spoofed because `x-shopify-shop-domain` is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by computing an HMAC over the **raw request body only**, while the `shop` attribute used to attribute the webhook to a specific merchant is read from the `x-shopify-shop-domain` HTTP header, which is never included in the signed payload. Any party capable of obtaining one legitimately-signed webhook body/HMAC pair for the app (e.g., a merchant who installs the app on their own shop and receives real webhooks) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` only re-validates the HMAC over the body and then dispatches the handler using the attacker-controlled `shop` value, causing cross-tenant data attribution.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is parsed straight from a header that is not part of the signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` for dispatch after only checking the HMAC and handler existence — there is no check binding `shop` to the signed material: [4](#0-3) 

The broken identity binding is:
`HMAC_secret(raw_body) == received_hmac` is verified, but `shop` (the tenant identifier acted upon in `WebhookMetadata.new(... shop: request.shop ...)`) is never part of the bytes that were verified. So `shop_verified == shop_used_for_dispatch` does not hold — an attacker fully controls `shop_used_for_dispatch` independent of the signature check.

Since the webhook secret (`api_secret_key`) is shared by the app across every shop that installs it, an attacker who installs the app on their own (attacker-controlled) shop will receive real, validly-signed webhooks from Shopify. They can capture one such raw body + HMAC pair (e.g., an `orders/create` payload) and replay it verbatim to the app's public webhook endpoint, only changing the `x-shopify-shop-domain` header to a victim shop's domain. The HMAC check still passes because it never examined the shop header, and `Registry.process` will hand the (attacker-crafted, but validly-shaped) payload to the handler tagged as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged user (any merchant able to install the app) can inject arbitrary webhook events falsely attributed to a different shop of their choosing. Depending on how the host app's webhook handlers use `shop` (e.g., updating per-shop records, triggering per-shop side effects, writing data keyed by `shop`), this enables cross-tenant data injection/corruption — matching the "cross-tenant access" high/critical impact category, since the whole point of validating the HMAC is to establish trust in both the payload and its shop origin, and only the payload is actually authenticated.

### Likelihood Explanation
Likelihood is high for any app open to install by third parties: obtaining a valid signed webhook for one's own shop requires nothing more than installing the app normally (no special privilege, no leaked secret). Replaying it with a modified header is a trivial HTTP request forgery once one legitimate webhook has been observed.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the data that is authenticated, or at minimum cross-check the `shop` header against an out-of-band expected value (e.g., a shop the app expects webhooks from) before trusting it for dispatch. Since Shopify's actual webhook signature is computed only over the raw body by design, the gem should document/require that consuming apps not treat `x-shopify-shop-domain` as authenticated by `HmacValidator`, or the gem should provide an explicit mechanism (e.g., requiring registrants to assert the expected shop per registration) to prevent shop-header spoofing from being silently trusted.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, gets registered for `orders/create` webhooks.
2. Shopify sends a legitimately signed webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled order fields...}
   ```
3. Attacker captures this raw body and HMAC value unmodified.
4. Attacker replays the exact same request to the app's public webhook endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `HmacValidator.validate` recomputes the HMAC over the unmodified body and it matches — validation passes.
6. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` to the app's handler, which processes attacker data as if it originated from `victim-shop.myshopify.com`.
