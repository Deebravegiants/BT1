Based on the in-scope library code (`lib/shopify_api/auth/oauth.rb` and `lib/shopify_api/utils/shop_validator.rb`), I found one genuine identity-binding inconsistency, but I want to be transparent about its limits before stating it.

### Title
Missing Shop-Domain Validation in `Auth::Oauth.begin_auth` Enables Forced OAuth Redirect to an Attacker-Controlled Host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth "authorize" redirect URL directly from the caller-supplied `shop` string with no domain validation, unlike its sibling grant flows.

### Finding Description
`Auth::ClientCredentials.client_credentials` and `Auth::RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` — which restricts the value to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before using `shop` to build the session/host that later receives the app's `client_id`/`client_secret` [1](#0-0) [2](#0-1) [3](#0-2) .

`Auth::Oauth.begin_auth`, however, takes `shop:` and passes it straight into `auth_base_uri(shop)` with **no call to `ShopValidator`** anywhere in the file, producing `auth_route = "https://#{shop}/admin/oauth/authorize?..."` that also embeds the app's `client_id` and `redirect_uri` [4](#0-3) [5](#0-4) . The identity binding that holds elsewhere in the module — "host validated as a trusted Shopify domain" equals "host that receives the app's OAuth credentials" — is broken here: `begin_auth` never validates the host at all.

### Impact Explanation
If a host application (as the library's own docs imply, since `shop` is typically taken from an unauthenticated login-route query parameter) passes a raw, attacker-supplied `shop` value into `begin_auth`, the victim's browser is redirected to `https://{attacker-host}/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&redirect_uri=<APP_HOST>/callback&state=<nonce>` instead of Shopify. This is a "forced OAuth completion" pattern (redirecting the flow to an attacker-controlled endpoint), which the rules list as a High-impact category.

However, I must flag an important limitation: completing the flow to actually exfiltrate the app's `client_secret` would require the follow-on `validate_auth_callback` step to accept attacker-forged callback parameters. That step calls `Utils::HmacValidator.validate(auth_query)` before doing anything else, which recomputes an HMAC-SHA256 over the query using `Context.api_secret_key` (or `old_api_secret_key`) and rejects the request unless it matches [6](#0-5) [7](#0-6) . An attacker without the app's `api_secret_key` cannot forge a passing HMAC for a `shop`/`code` of their choosing, so they cannot make `validate_auth_callback` proceed to POST `client_id`/`client_secret` to their attacker-controlled host [8](#0-7) . That means the strongest concrete consequence I can substantiate purely from unprivileged-attacker capability is the forced redirect itself (leaking `client_id` and `redirect_uri`, and enabling phishing of the merchant's real Shopify credentials on a spoofed authorize page) — not confirmed `client_secret` exfiltration, since the rules explicitly exclude findings that require the app's own secret to execute.

### Likelihood Explanation
Likelihood depends entirely on whether the host application passes an unauthenticated, user-controlled `shop` parameter into `begin_auth` without its own separate domain check — this is a common integration pattern (the gem's own docs show `shop` originating from the login route) but is technically a decision left to the host app, which the rules caution against relying on.

### Recommendation
Add a `Utils::ShopValidator.sanitize!(shop)` call at the top of `Auth::Oauth.begin_auth` (and defensively in `validate_auth_callback` before constructing `null_session`), mirroring `Auth::ClientCredentials.client_credentials` and `Auth::RefreshToken.refresh_access_token`, so `auth_base_uri` can never target a non-Shopify host.

### Proof of Concept
1. Attacker sends victim a link to the app's login route with `shop=attacker.example`.
2. If the host app forwards this directly to `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/callback")`, the returned `auth_route` is `https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&redirect_uri=<APP_HOST>/callback&state=<nonce>` [9](#0-8) .
3. The victim's browser is redirected to the attacker's server instead of Shopify, which can host a phishing page mimicking Shopify's install-consent screen.
4. Any attempt to complete the flow back through `validate_auth_callback` with attacker-chosen parameters is blocked by the `Utils::HmacValidator.validate` check, which requires the real `api_secret_key` — this part of the chain is **not** demonstrated to be bypassable without secret access.

**Caveat:** I was unable to confirm a complete, secret-free path to `client_secret` exfiltration or cross-tenant access; the demonstrated impact is limited to the forced-redirect/phishing-setup step, and its severity assumes the host app trusts an unauthenticated `shop` parameter, which the analog rules discourage building an analog around. I flag this uncertainty explicitly rather than overstating the finding.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
