### Title
Directory traversal in HTTP artifact fetcher bypasses intended base-path restriction - ([File: core/services/workflows/syncer/v2/fetcher.go])

### Summary
`newHTTPFetcher` in `core/services/workflows/syncer/v2/fetcher.go` builds the outbound artifact-fetch URL by concatenating a workflow-supplied path onto a configured base URL without validating that the resulting path stays inside the intended base directory. This mirrors the CVE-2016-10039 bug class (a crafted path parameter causing traversal past an intended base directory on a request handler).

### Finding Description
`NewFetcherFunc` dispatches to either `newFileFetcher` or `newHTTPFetcher` depending on the scheme of the configured base URL [1](#0-0) .

`newFileFetcher` explicitly guards against traversal: it parses `req.URL` with `url.Parse`, cleans the path, joins it onto `basePath`, and then rejects the result unless it is prefixed by `basePath` [2](#0-1) .

`newHTTPFetcher`, however, has no such boundary check. It only does `filepath.Clean` on the raw `req.URL` string (not a proper URL parse) and joins it directly onto the configured base URL's path via `filepath.Join`: [3](#0-2) 

`filepath.Join` itself calls `Clean`, so a `req.URL` value containing enough `../` segments (e.g. `"../../../secret/config"`) will collapse the configured base path (e.g. `/artifacts`) and land on a sibling/unintended path on the same host (e.g. `/secret/config`), rather than being rejected the way the file fetcher rejects an out-of-basePath path.

`req.URL` here is populated from `binaryURL`/`configURL`, which come from `payload.BinaryURL`/`payload.ConfigURL` — values that are registered on-chain by a workflow owner via the Workflow Registry and consumed in `createWorkflowSpec` / `FetchWorkflowArtifacts`: [4](#0-3) [5](#0-4) 

Only when the parsed host of `binaryURL`/`configURL` matches the configured `ArtifactStorageHost` does the store swap in a signed URL from `retrieveFunc`; otherwise the workflow-owner-supplied URL is passed straight through to `fetchFn` [6](#0-5) . This confirms that the path component of the fetch request is attacker (workflow owner)-influenced.

### Impact Explanation
An unprivileged actor able to register a workflow (supplying `BinaryURL`/`ConfigURL`) can craft a path with directory-traversal sequences that, when the fetcher configuration uses an `http`/`https` base URL, escapes the intended base path on the configured storage host. This can result in the node fetching content from unintended paths on that host (e.g., cross-workflow/cross-tenant artifact disclosure or hitting other endpoints reachable under the same host/authority), unlike the file-based fetcher which correctly rejects such escapes. This is a concrete violation of the boundary/allowlist-style restriction that is otherwise enforced for the file-URL case, satisfying the "allowlist/quota bypass" or "cross-user response confusion" criteria.

### Likelihood Explanation
Likelihood is limited by two factors that are not fully confirmed from the available code: (1) whether the `http`/`https` branch of `NewFetcherFunc` (rather than the gateway-routed `FetcherService.Fetch`) is actually wired into the production artifact-fetch path for workflow registry syncer v2, and (2) whether the configured storage host actually segregates workflow/tenant artifacts by directory prefix (which would make the traversal impactful) as opposed to using opaque signed URLs exclusively. The code paths and call sites (`core/cmd/shell.go`, `core/services/cre/cre.go`) that select between `NewFetcherFunc` and the gateway-routed fetcher could not be fully traced within the available tool budget.

### Recommendation
In `newHTTPFetcher`, mirror the containment check already present in `newFileFetcher`: after joining the cleaned path onto the base URL, verify the resulting `u.Path` still has the original base path as a prefix (or is exactly equal to it) before issuing the request, and reject otherwise.

### Proof of Concept
1. Configure a workflow-storage/artifact fetch with an `http(s)` base URL whose path is a subdirectory, e.g. `https://storage.example.com/artifacts/`.
2. Register a workflow whose `ConfigURL` value resolves (after being handled by `newHTTPFetcher`) to a value such as `../../secrets/other-org-config.yaml`.
3. Observe that `filepath.Join(u.Path, cleanPath)` collapses to `/secrets/other-org-config.yaml`, outside the intended `/artifacts/` prefix, and the fetcher requests it without rejection — unlike the equivalent file-URL path traversal test, which is explicitly rejected in `core/services/workflows/syncer/v2/fetcher_test.go` (lines 443-448).
