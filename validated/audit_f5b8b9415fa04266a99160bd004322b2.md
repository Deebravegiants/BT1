## Analysis

I found a concrete identity-binding break in the webhook processing path of this gem. [1](#0-0) 

The `Webhooks::Request#hmac` and `#to_signable_string` methods are the only inputs used by `Utils::HmacValidator.validate` to authenticate an incoming webhook, and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` values are all parsed straight from HTTP headers (`x-shopify-shop-domain`, etc.) and are never included in the signed material. [2](#0-1) 

`Registry.process` validates the HMAC over the request (body only), then immediately trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` passed to the app's handler. [3](#0-2) 

`HmacValidator.validate_signature` only ever checks `verifiable_query.to_signable_string` (the raw body for webhooks) against the computed signature — the `shop` field is never part of the signable string.

This produces a break in the binding: `shop attributed to the event == shop authenticated by the HMAC` does not hold, because the HMAC covers only `raw_body`, not the `shop-domain` header.

### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values that are ultimately delivered to the app's webhook handler exclusively from HTTP headers, while `Utils::HmacValidator` only verifies the HMAC-SHA256 signature against the raw request body (`to_signable_string` returns `@raw_body`). Because the shop identity is not part of the signed payload, an attacker who possesses one valid `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and capturing a webhook Shopify sends them — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled and unauthenticated.

### Finding Description
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare`. [4](#0-3) 
- For webhook requests, `to_signable_string` is simply `@raw_body`. [5](#0-4) 
- `shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-controllable HTTP headers with no cryptographic tie to the body or the HMAC. [6](#0-5) 
- `Registry.process` validates only the HMAC (over the body) and then trusts `request.shop` when constructing the metadata passed to the host app's handler: [2](#0-1) 

The equality that should hold — `shop value cryptographically bound to this webhook payload == shop value delivered to the handler` — is broken: the gem verifies "these bytes (body) came from someone who knows the shared secret" but not "these bytes belong to shop X." Any bytes/HMAC pair valid for shop A's webhook remain valid when replayed with shop B's domain header, since the header is outside the HMAC's scope.

### Impact Explanation
This is a cross-tenant identity confusion / spoofing vulnerability within the gem's own webhook-verification code path (not a misuse of an undocumented API by the host app — the gem's documented `Registry.process` API is exactly what's exploited). A host application that (reasonably, per this gem's contract) trusts `WebhookMetadata#shop` returned by `Registry.process` after successful HMAC validation can be tricked into attributing a webhook event to the wrong tenant, e.g., updating another merchant's order/inventory records, disabling another shop's app configuration, or triggering per-shop side effects (billing, fulfillment, notifications) under the wrong shop identity. This matches the High-impact criteria for identity-binding breaks leading to cross-tenant access.

### Likelihood Explanation
Exploitation requires only an unprivileged actor who can install the app on any store (including a free/dev store) to capture one legitimate `(raw_body, x-shopify-hmac-sha256)` pair sent to the app's webhook endpoint, then replay that exact byte-for-byte body with the same HMAC header but a different `x-shopify-shop-domain` value. No access token, `client_secret`, or `api_secret_key` is needed — the HMAC stays valid because it was never computed over the shop header in the first place.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable material verified by `HmacValidator`, or independently verify that the shop asserted in the header matches a shop the receiving app actually expects/has installed before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked by the host application against its own session/shop registry before use.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`).
2. Capture the raw POST request Shopify sends to the app's webhook endpoint, including the exact `raw_body` and the `x-shopify-hmac-sha256` header value.
3. Resend the identical request to the same endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (called from `Registry.process`) succeeds because it only checks `raw_body` against the HMAC. [2](#0-1) 
5. The host app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` with attacker-controlled body content, despite the event never having occurred for that shop.
