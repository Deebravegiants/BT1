This confirms the pattern precisely: `Webhooks::Request#hmac` is computed only against `@raw_body` via `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`), while `topic`, `shop`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) and are never included in the signable string. `Registry.process` validates the HMAC over the body alone (`lib/shopify_api/webhooks/registry.rb:190`) and then forwards `request.shop`/`request.topic`/`request.webhook_id` straight to the handler (`lib/shopify_api/webhooks/registry.rb:198-199`) without any binding check tying those header values to the signed content.

### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the body bytes exclusively. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read straight from HTTP headers and are handed to the application's webhook handler as trusted, verified data even though none of them are part of the signed content.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
which signs only `@raw_body`. Meanwhile `shop`, `topic`, and `webhook_id` are derived purely from headers: [2](#0-1) 
`Registry.process` validates HMAC over the `Request` object and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` for the handler: [3](#0-2) 
Because the HMAC secret (`api_secret_key`) is a single per-app value (not per-shop), and the signature never binds to `shop-domain`, any request whose body matches a body the attacker has legitimately seen signed for their own shop (e.g. topics with static/empty bodies such as `app/uninstalled`, `shop/redact`, `customers/redact`, `customers/data_request` in `MANDATORY_TOPICS`) will still pass `Utils::HmacValidator.validate` even if the `shop-domain` header is swapped to a different, victim merchant's shop domain. The equality the gem should enforce is: `shop value delivered to the handler == shop value cryptographically bound by the HMAC`. Currently: `shop value delivered to the handler == unauthenticated header value`, which breaks that equality.

### Impact Explanation
If a host application relies on `Registry.process` having already authenticated `WebhookMetadata#shop` (as the gem's own HMAC-validation step implies), an attacker who has legitimately received one webhook delivery for their own store (with a body identical or predictable for a given topic) can replay it with the `shop-domain` header changed to a victim shop. `Registry.process` will accept it as authentic because the HMAC only covers the body, causing the handler to act on data attributed to the wrong tenant — a cross-tenant confusion inside the gem's own trusted verification boundary.

### Likelihood Explanation
This requires only unauthenticated internet access to the app's public webhook endpoint plus knowledge of one legitimately-delivered webhook payload for a topic whose body content doesn't vary by shop (mandatory topics have fixed/near-empty JSON bodies). No secrets, tokens, or privileged access are required — only manipulation of standard, forgeable HTTP headers alongside a replayed, previously-observed valid body+HMAC pair.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in `to_signable_string`, or otherwise cryptographically bind them before they are trusted — e.g., have `Registry.process` re-derive/verify the shop from a source outside attacker control, or require the HMAC to cover the full canonical request line (headers + body) rather than the body alone.

### Proof of Concept
1. App owner registers webhook handler for `app/uninstalled` (body is typically `{}`).
2. Attacker installs the app on their own store `attacker.myshopify.com`, uninstalls it, and captures the resulting legitimate webhook POST, including its valid `shopify-hmac-sha256` header (computed over body `{}`).
3. Attacker replays the exact same request to the app's webhook endpoint, but changes the `shopify-shop-domain` header to `victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only re-computes HMAC over the identical body `{}`.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to treat the event as an authenticated uninstall for the victim shop even though it was forged by an unrelated attacker.
