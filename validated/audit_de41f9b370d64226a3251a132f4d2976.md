### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the request to the registered handler using the `shop-domain` value taken directly from an HTTP header that is never part of the signed bytes. Because a single app's `client_secret` (`Context.api_secret_key`) is shared across every merchant shop that installs the app, any unprivileged attacker who installs the app on their own shop can obtain a genuinely HMAC-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, causing the host application to process attacker-controlled webhook data under the victim's tenant identity.

### Finding Description
The identity binding that should hold is:

`shop` used by the handler for tenant dispatch == `shop` that Shopify actually signed for this payload

but the code only enforces:

`hmac(raw_body, secret) == received_hmac`

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  
- `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no relation to the signed bytes: [2](#0-1) 
- `Registry.process` validates the HMAC against `request` (i.e., against the body only, per `VerifiableQuery`/`to_signable_string`) and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app secret, never incorporating the shop header: [4](#0-3) 

Because the same `client_secret`/`api_secret_key` is used to sign webhooks for every shop that has the app installed, a shop owned by the attacker is a valid signer source. The attacker triggers or receives a legitimately-signed webhook for their own shop (e.g., a topic whose body they fully control, such as a product/order event on their own store, or a generic-body event like `app/uninstalled`), captures the `(raw_body, hmac)` pair, and replays it to the app's public webhook endpoint while substituting the `shop-domain` header with the victim's `myshopify.com` domain. `HmacValidator.validate` still succeeds because it never checked the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-crafted) body originated from the victim shop.

### Impact Explanation
This breaks the tenant identity boundary the gem is supposed to guarantee to host applications: `Registry.process`'s only authentication primitive is the HMAC, and host apps are documented to trust `WebhookMetadata#shop` as the verified source shop. An attacker can inject spoofed/forged data attributed to a victim tenant (cross-tenant data confusion), potentially triggering victim-side business logic (e.g., faking `orders/create`, `app/uninstalled`, or other webhook-driven side effects) without ever needing the victim's credentials or access token.

### Likelihood Explanation
The prerequisite is only that the attacker be an installer of the target multi-tenant app on their own store — a normal, unprivileged action available to any internet user for public apps — and that they can capture one valid `(body, hmac)` pair emitted for their own shop, which Shopify sends automatically. No secret, access token, or privileged access to the app or to Shopify is required.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the authenticated request:
- Include the shop domain (and ideally topic/webhook-id) in `to_signable_string`, or
- Require the host application to independently validate that `request.shop` corresponds to an actual installed/authorized shop session before trusting `WebhookMetadata#shop`, and document this requirement prominently, or
- Reject/flag webhooks where the same raw-body/HMAC pair is replayed with a different `shop-domain` header than previously observed (replay/binding detection) at the `Registry.process` layer.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any public app install is unprivileged).
2. Shopify sends a legitimately signed webhook to the app's endpoint, e.g. for `products/create` with body `attacker_body` and header `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, attacker_body)` — the same `secret` used for every shop the app serves.
3. Attacker replays this exact `(attacker_body, H)` pair directly to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, attacker_body)` and matches `H` — validation succeeds: [5](#0-4) 
6. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_body, ...)`, so the host app processes attacker-controlled content as if it came from the victim shop: [6](#0-5)

          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
