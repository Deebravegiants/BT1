### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never part of the signed content [2](#0-1) . `Registry.process` validates only the HMAC over that raw body before dispatching the handler with the attacker-influenceable header values [3](#0-2) .

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and constant-time-compares it to the received HMAC [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values consumed by the rest of the library come exclusively from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) which are outside the HMAC's scope [2](#0-1) .

`Registry.process` enforces `raise ... unless Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` from the unauthenticated header data [3](#0-2) . The gem gives host applications no signal that `shop`/`topic`/`webhook_id` are unauthenticated — they are exposed identically to the signature-verified `body`, so any consumer that binds tenant identity to `data.shop` (the documented, expected usage, e.g. `assert_equal(@shop, data.shop)` in the test suite [5](#0-4) ) is trusting a value the gem never authenticated.

This breaks the binding: `bytes verified (raw_body) != identity claimed (shop header)`. An unprivileged attacker who can obtain any single genuinely-Shopify-signed webhook body (e.g., by installing the app on their own store and triggering a webhook whose body they can predict or fully control, such as one with an empty `{}` body) can resend that exact body with arbitrary `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers naming a different, victim shop and/or topic. `HmacValidator.validate` will still pass because it only checks the raw body bytes, and the app's handler will be invoked believing the event came from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app processes a webhook under the identity of a shop the attacker does not control, using headers the attacker fully controls. Depending on the handler logic (which typically looks up merchant sessions/data using `data.shop`), this can lead to unauthorized cross-tenant actions — e.g., triggering `app/uninstalled` cleanup, `shop/redact` compliance flows, or any topic handler logic against a victim tenant's session/data using attacker-supplied `body` content. This satisfies the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Any internet user can become a legitimate merchant installer of a public app to obtain real, validly-signed webhook deliveries (bodies with predictable/known content, e.g. topics with empty JSON bodies such as `{}`), then replay the byte-identical body with forged Shopify headers pointing at any other shop domain the target app also serves. No access token, `client_secret`, or privileged account is required — only the ability to receive one legitimate webhook and resend an HTTP request with custom headers to the app's public webhook endpoint.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-signed content (or otherwise cryptographically bind them to the verified body), rather than relying purely on unauthenticated headers. At minimum, document clearly that these header-derived values are not covered by HMAC verification so host applications do not treat `data.shop` as an authenticated tenant identifier without additional verification (e.g., cross-checking against a known, previously-established session/shop mapping).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`, and trigger/observe a webhook delivery whose body is fully known/predictable (e.g., `{}` or an attacker-controlled resource payload).
2. Capture the raw body and the genuine `x-shopify-hmac-sha256` value Shopify computed for that delivery.
3. Resend an HTTP POST to the app's webhook endpoint with:
   - The identical raw body and `x-shopify-hmac-sha256` value captured in step 2.
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any shop served by the app).
   - `x-shopify-topic` set to any topic the app has a handler registered for.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks the raw body bytes against the secret [4](#0-3) , and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [3](#0-2)  — the app now believes this event originated from the victim shop.
