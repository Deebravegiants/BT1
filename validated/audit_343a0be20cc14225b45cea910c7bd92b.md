### Title
Webhook HMAC does not bind the `shop` field, enabling cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`) values used by the app to attribute the webhook to a tenant are read from unsigned HTTP headers. This breaks the intended binding `HMAC_valid(request) == shop_is_authentic`, letting anyone who can obtain one validly-signed webhook body (e.g. from their own installed shop) re-POST it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header and have it accepted as valid for a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` in turn only checks `verifiable_query.to_signable_string` (the raw body) against the HMAC, never anything from headers: [4](#0-3) 

The webhook endpoint is a public URL reachable by anyone on the internet, not gated by mTLS or an IP allowlist. An unprivileged attacker who controls their own Shopify development store (no special credentials needed) can trigger a real webhook delivery for their own shop, capture the `raw_body` + valid `hmac-sha256` header Shopify computed with the app's `client_secret`, and then directly POST that identical body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. Because the header is outside the signed message, `HmacValidator.validate` still returns `true`, and `Registry.process` will dispatch the handler with `shop: <victim-shop>` even though the signed payload actually originated from the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality the gem is supposed to enforce is `hmac_valid(body) => shop_header is authentic for that body`, but the header is never part of what's signed. An app's webhook handler (e.g. anything built on `WebhookMetadata#shop`) can be tricked into processing attacker-controlled data as if it belonged to an arbitrary victim shop — e.g. triggering shop-scoped side effects, cache/database writes keyed by `shop`, or state transitions (uninstall/redact flows, order-processing logic) under the victim's identity, all without ever obtaining the victim's credentials.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop with the app installed (freely obtainable via a Shopify dev store), enabling them to trigger a real webhook and observe a valid `(body, hmac)` pair signed with the target app's secret, and (2) the ability to POST directly to the app's publicly reachable webhook endpoint with a forged `shop-domain` header. No access to the app's `client_secret`, no access token, and no interaction with the victim shop is needed, making this a realistic, low-effort attack path for anyone who can install the target app on their own store.

### Recommendation
Include the shop domain (and topic, delivery id) in the value that is HMAC-verified, or otherwise cryptographically bind the shop-domain header to the signed payload before trusting `Request#shop`/`Request#topic` downstream in `Registry.process`. At minimum, document that consuming apps must not treat `WebhookMetadata#shop` as authenticated unless it is independently corroborated (e.g., verified against the shop that installed the app and is known to have subscribed to that webhook/topic), and consider validating the delivering IP range or requiring mTLS for the webhook endpoint as defense in depth.

### Proof of Concept
1. Attacker creates/uses their own dev shop and installs the target app, obtaining a legitimate webhook delivery to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker crafts a new HTTP POST to the same public webhook endpoint using the same body `B` and same `H` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`B`) only and finds it matches `H` — validation passes. [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
