### Title
Webhook Shop/Topic Identity Spoofing via Header Fields Not Covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then dispatches to a handler and constructs `WebhookMetadata` using the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers — none of which are covered by the HMAC signature. Because the HMAC secret (`Context.api_secret_key`) is a single value shared across every shop that installs the app, any tenant with a legitimate installation can capture a genuinely-signed webhook body and replay it with attacker-chosen `shop-domain`/`topic` headers, producing a request the gem accepts as authentic for an arbitrary shop and/or arbitrary registered topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other request attributes exposed by the class — `shop`, `topic`, `webhook_id`, `api_version` — are read verbatim from HTTP headers and are never part of the signed material: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only over `to_signable_string` (i.e. the raw body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then unconditionally trusts the header-derived `topic` to select the handler and the header-derived `shop`/`webhook_id`/`api_version` to build the metadata handed to application code: [4](#0-3) 

The broken identity binding is: **`shop`/`topic` acted upon by the dispatcher == `shop`/`topic` covered by the HMAC**. In truth, `shop`/`topic` are *not* bound to the signature at all — only the body bytes are. Since the app's `api_secret_key` is identical for every shop that has the app installed, a merchant/tenant that legitimately triggers a webhook on their own store obtains a body+HMAC pair that is valid regardless of which `shop-domain`/`topic` headers accompany it. That tenant can then resend the same HTTP request with the `X-Shopify-Shop-Domain` header changed to a victim shop and/or the `X-Shopify-Topic` header changed to a different registered topic; `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` will dispatch the (attacker-controlled) body to the handler for the spoofed topic, reporting it as originating from the spoofed shop.

### Impact Explanation
This crosses a tenant boundary: a party with legitimate but limited access (their own shop installation) can make the app believe a webhook — carrying attacker-influenced body content — belongs to a different shop, or belongs to a different topic than what actually produced it. Host applications commonly use `WebhookMetadata#shop` to key data writes/deletes (including mandatory GDPR topics like `customers/redact`, `shop/redact` which this gem special-cases), so forging the shop or topic can cause cross-tenant data corruption, spoofed compliance/erasure actions against a victim shop, or type-confused handler execution. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only that the attacker be a tenant capable of installing the app and triggering at least one webhook delivery on their own store — no access to `api_secret_key`, access tokens, or any privileged account is needed, and no interception of Shopify's own traffic is required (the attacker constructs and sends their own HTTP request to the app's public webhook endpoint). This is within reach of an "unprivileged internet user" relative to any other tenant's data, satisfying the required boundary-crossing bar.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` (or otherwise a per-shop identifier) in the HMAC-signed material verified by `Utils::HmacValidator`, or independently validate `request.shop` against the shop associated with an existing/expected session before dispatching, and treat `topic` as untrusted unless corroborated by the signed payload contents. At minimum, document and enforce that consumers of `WebhookMetadata` must not trust `shop`/`topic` for authorization decisions unless cross-checked against known installed shops.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`, both sharing the same app `api_secret_key`.
2. Attacker triggers a real webhook event on their own store (e.g. `orders/create`), capturing the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the shared secret).
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: customers/redact`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only re-derives the HMAC from `B` — the substituted headers are never checked.
5. `ShopifyAPI::Webhooks::Registry.process` looks up the handler for the spoofed topic and invokes it with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to act as though the request genuinely originated from `victim-shop.myshopify.com` for that topic.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
