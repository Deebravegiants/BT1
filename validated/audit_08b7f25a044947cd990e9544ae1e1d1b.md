### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) used to route and process a webhook from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body against the HMAC. The tenant identity that the rest of the code trusts (`request.shop`) is never bound to the cryptographic signature that authenticates the request.

### Finding Description
`Registry.process` authenticates a webhook exclusively via: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which validates `request.hmac` against `HMAC(secret, request.to_signable_string)`: [2](#0-1) 

But `Webhooks::Request#to_signable_string` returns only the raw HTTP body — it does not include `shop`, `topic`, or `webhook_id`: [3](#0-2) 

Meanwhile `request.shop` (and `topic`/`webhook_id`) are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed payload: [4](#0-3) 

This is the exact bug class called out in the rules: "a field acted on but not covered by the HMAC." The equality that should hold is:
`shop_bound_by_signature == shop_the_handler_acts_on`

but in this gem it is actually:
`shop_bound_by_signature == "" (nothing) ; shop_the_handler_acts_on == header["shopify-shop-domain"]`

Since `shop` is not part of the signed bytes, an attacker who obtains any one genuine, validly-signed webhook body+HMAC pair for a given topic (e.g. by installing the same app on a shop they control, or observing/reusing any legitimately delivered webhook payload) can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature still validates (it only ever checked the body), but `WebhookMetadata` — and therefore the app's handler logic — will process the payload under the attacker-chosen `shop`, not the shop that actually produced/signed the data: [5](#0-4) 

### Impact Explanation
This breaks the tenant/authentication boundary the gem is supposed to enforce for inbound webhooks: a host application that trusts `WebhookMetadata#shop` (as the gem's own API/docs imply it should, since it is the only shop identifier exposed by `Registry.process`) can be made to associate one merchant's authentic, HMAC-verified payload with a different merchant's identity. Depending on how the host app keys its data/session lookups off `data.shop`, this enables cross-tenant data confusion/injection — i.e., cross-tenant access, which is listed as a Critical-impact category in this scan's rules.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly signed webhook body/HMAC pair for the given `api_secret_key` and topic. This is realistically achievable by any developer who can install the target app on their own Shopify store (an "unprivileged internet user" relative to *other* merchants' tenants, even though privileged for their own store) — every webhook Shopify sends them for their own store is a valid signed-body/HMAC pair they fully control and can replay with a forged `shop-domain` header. No access to the app's `client_secret`, access tokens, or another merchant's credentials is needed; only interaction with the app's own public webhook endpoint using headers the app does not cryptographically verify.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material verified against the HMAC, or otherwise cryptographically bind the header-derived shop domain to the payload before exposing it via `WebhookMetadata`. At minimum, document prominently that `shop` on `Request`/`WebhookMetadata` is not authenticated by the HMAC and must be independently cross-checked by the host application (e.g., against a shop that is know to have this webhook subscription registered) before being used for tenant-sensitive decisions.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's real `api_secret_key`.
2. Attacker captures the raw body and HMAC header from this delivery.
3. Attacker POSTs the exact same body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id` value corresponding to data they want the app to ingest for the victim).
4. `Webhooks::Request.new` accepts the forged headers (only checks presence, not authenticity) and `Registry.process` validates the HMAC successfully (it only checks the raw body): [1](#0-0) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never produced for or by that shop, breaking the identity binding between the authenticated bytes and the tenant the app believes sent them.
