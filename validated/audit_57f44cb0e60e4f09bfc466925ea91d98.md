### Title
Escrow `withdraw()` and `SweepDust` handling in Tron `IntentGatewayV2` use unchecked low-level `.call` for ERC20 transfers instead of `SafeERC20.safeTransfer` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports `SafeERC20` and declares `using SafeERC20 for IERC20` [1](#0-0) , and correctly uses `safeTransferFrom` when pulling tokens into escrow [2](#0-1) . However, when tokens leave escrow — in `withdraw()` (paying out fillers/refunding users) and in the `SweepDust` branch of `onAccept()` — the contract bypasses `SafeERC20` entirely and instead performs a raw low-level `.call` encoding the ERC20 `transfer` selector, only checking that the call did not revert (`success`) and never decoding/validating the returned boolean.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

And for the fee payout in the same function:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
delete _orders[body.commitment][TRANSACTION_FEES];
``` [4](#0-3) 

And in the `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [5](#0-4) 

`success` here only reflects whether the external call reverted — it does not verify the ABI-decoded return value of `transfer()`. Per the ERC20 standard, a compliant token must return `true`/`false` to indicate success/failure, and some real-world/non-standard tokens (fee-on-transfer edge cases, tokens that return `false` instead of reverting on insufficient balance/blacklist, tokens with no return value that decode incorrectly, or tokens with custom logic) can complete the call without reverting yet fail to actually move the tokens, or move a different amount than requested. This is exactly the class of bug `SafeERC20.safeTransfer` is designed to prevent by checking the return data (see [OpenZeppelin's `SafeERC20`](https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/token/ERC20/utils/SafeERC20.sol)), and which the contract already correctly applies on the deposit side via `safeTransferFrom` [2](#0-1)  but fails to apply on the payout side.

Both `withdraw()` and the `SweepDust` branch update internal escrow accounting (`_orders[...] -= amount`, `delete _orders[...][TRANSACTION_FEES]`) unconditionally once `success` is true [6](#0-5) , and `withdraw()` also marks the order as filled/refunded (`_filled[body.commitment] = beneficiary`) before any of the transfers even happen [7](#0-6) . If the underlying token silently fails (returns `false` without reverting), the contract believes the payout succeeded, decrements/clears the escrow bookkeeping, and marks the commitment as settled — while the beneficiary never actually received the tokens.

`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` message is delivered and authenticated [8](#0-7) , i.e., driven by relayed cross-chain ISMP messages settling intents — a path reachable from any relayer delivering a legitimately proven message from the source chain (solver/filler settlement flow), not requiring privileged/admin access to the gateway itself.

### Impact Explanation
If a configured input/output token, or the host's `feeToken`, is a non-fully-standard ERC20 (returns `false` on failure instead of reverting, or otherwise behaves non-conformantly), a payout to a filler or a refund to the original order-placer can silently fail while the contract's internal escrow accounting is decremented/cleared as though the transfer succeeded. This permanently strands the tokens inside the `IntentGatewayV2` contract with no accounting record referencing them (the `_orders` mapping entry that tracked them has already been reduced or deleted), resulting in a permanent freeze/loss of user or solver funds. This matches the accepted-impact category of "permanent freezing of funds."

### Likelihood Explanation
Likelihood depends on whether any token configured for use with this Tron gateway deviates from strict ERC20 semantics (returns `false` rather than reverting on failure). Given the IntentGateway is designed to be generic across arbitrary ERC20 tokens supplied by users/solvers as intent inputs/outputs, and given Tron/TRC20-style tokens historically include such non-compliant implementations, this is a realistic misconfiguration risk rather than a purely theoretical one. It does not require any malicious actor — it is triggered by ordinary relayed settlement of a legitimate intent involving a non-conformant token.

### Recommendation
Replace all raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` calls in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported and aliased via `using SafeERC20 for IERC20` [1](#0-0) ), matching the pattern already used for `safeTransferFrom` on the deposit side. This ensures both call-revert and return-value semantics are properly validated before escrow accounting is mutated.

### Proof of Concept
1. Configure/deploy the Tron `IntentGatewayV2` for a TRC20/ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., due to an internal blacklist check, paused state, or non-standard accounting) rather than a fully OpenZeppelin-compliant token.
2. A user places an order with that token as an input, which is escrowed via `safeTransferFrom` — succeeds normally [9](#0-8) .
3. Once the order is filled/refunded, a relayer delivers the `RedeemEscrow`/`RefundEscrow` message; `onAccept()` calls `withdraw()` [8](#0-7) .
4. Suppose the token's `transfer()` call to `beneficiary` returns `false` without reverting (e.g., beneficiary transiently blacklisted, or a bug in the token's transfer logic under certain conditions) — `success` is still `true` because the low-level call itself didn't revert [10](#0-9) .
5. `_orders[body.commitment][token] -= amount` executes, and `_filled[body.commitment]` is already set, permanently marking the order as settled even though the beneficiary received nothing — the tokens remain stuck in the `IntentGatewayV2` contract with no bookkeeping path left to reclaim them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
