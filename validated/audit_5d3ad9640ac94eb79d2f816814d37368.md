### Title
Webhook shop-domain header not bound to HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only [1](#0-0) , while the shop identity used by the webhook processing pipeline (`request.shop`) is read directly from the unauthenticated `X-Shopify-Shop-Domain` header [2](#0-1) . `Utils::HmacValidator.validate` only verifies that the raw body was signed with the app's shared `api_secret_key` [3](#0-2) ; it never checks that the signature is bound to the shop domain in the request. Since a single app's `api_secret_key` is shared across every shop that installs the app, any tenant that receives a validly-signed webhook for their own shop can replay the exact same body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and `Registry.process` will accept it and hand the forged shop identity straight to the host app's handler.

### Finding Description
The identity binding that should hold is:
`shop domain authenticated by the HMAC == shop domain the webhook handler attributes the payload to`

In `Request#to_signable_string`, only `@raw_body` is fed into the signature computation [1](#0-0) . The `shop`, `topic`, `webhook-id`, and `api-version` headers are excluded from what gets signed, yet `Registry.process` trusts `request.shop` (and the other headers) as authoritative tenant/topic metadata once `HmacValidator.validate` succeeds:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because `api_secret_key` (the `client_secret`) is a single, app-wide value used for every merchant that installs the app, any merchant/tenant is able to legitimately trigger a webhook to their own endpoint (e.g. by performing an action that fires an `orders/create`-type topic, or even an app/uninstalled webhook) and thereby obtain a body + valid HMAC pair signed with the shared secret. That signed pair remains valid for **any** value of `X-Shopify-Shop-Domain`, because the header is not part of the signed content. Replaying the same raw body with the header swapped to a victim's `*.myshopify.com` domain produces a request that `HmacValidator.validate` still accepts, and `Registry.process` will then invoke the host application's handler believing the payload originated from the victim shop.

### Impact Explanation
This breaks the cross-tenant isolation the HMAC check is meant to enforce. A malicious tenant can inject attacker-controlled webhook payloads that are attributed to a victim shop into the host application's business logic (e.g., causing orders, inventory changes, GDPR/uninstall processing, or any state keyed by `shop` in the handler to be created/mutated for the victim tenant, or poisoning per-shop caches/session lookups keyed by `data.shop`). This is a cross-tenant access primitive stemming purely from a verified-bytes-vs-acted-on-field mismatch in this gem's webhook verification, matching the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Any attacker who can install the target app on their own shop (a normal, unprivileged onboarding action available to any Shopify merchant) can trivially capture one valid signed webhook payload for a topic they control the content of, then replay it with a forged `X-Shopify-Shop-Domain` header. No access token, `api_secret_key`, or privileged credential of the victim is required — only the gem's public webhook endpoint and knowledge of the (documented) header format.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signed content, e.g. by having `to_signable_string` incorporate the shop-domain header alongside the raw body (mirroring how `Oauth::AuthQuery#to_signable_string` signs all identity-relevant fields, not just a subset [5](#0-4) ), or otherwise require host applications to cross-check `request.shop` against a shop known to have registered that specific `webhook_id`/topic before invoking handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`) whose body content they control.
2. Attacker triggers the webhook and captures the raw HTTP request, including `raw_body` and the valid `X-Shopify-Hmac-Sha256` value (signed with the app's shared `api_secret_key`).
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret [6](#0-5) .
5. `Registry.process` calls the host handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com` [7](#0-6) , causing attacker-controlled data to be processed under the victim tenant's identity.
