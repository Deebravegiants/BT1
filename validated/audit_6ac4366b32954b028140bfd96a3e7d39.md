### Title
Token-donation to a curve `Pair` permanently bricks the overflow-cap buy path via an unguarded arithmetic underflow in `Router._computeBuy` - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's real token balance and back-calculates `amountInUsed` for the final, curve-emptying buy. The capped branch computes `cappedReserveToken = reserveToken - tokensOut` and only guards the `== 0` case with `OverflowCapDegenerate`. It does not guard against `tokensOut > reserveToken`, which underflows and panic-reverts instead of raising the named error. This condition is directly reachable by an unprivileged trader who buys tokens on the curve and then donates them straight back into the `Pair` via a plain ERC20 `transfer`, inflating `pair.tokenBalance()` (the "real" balance) above `reserveToken` (the stored/virtual reserve).

### Finding Description
`_computeBuy` reads live `pair.tokenBalance()` as `realBalance` and, when the naive constant-product `tokensOut` exceeds it, caps `tokensOut = realBalance` and recomputes `amountInUsed`: [1](#0-0) 

The protocol's own tests document that a direct token donation to the pair can push `tokenBalance() (realBalance) > reserveToken`, and that this specific inequality was previously *known* to underflow a sibling supply-leg calculation in `Bonding.previewLtUntilGraduation` (issue fixed there): [2](#0-1) [3](#0-2) 

That fix was applied to `Bonding.previewLtUntilGraduation`'s preview math, not to `Router._computeBuy` itself. `Router._computeBuy`'s capped branch performs the identical subtraction, `reserveToken - tokensOut` where `tokensOut` is capped to `realBalance`, i.e. it computes `reserveToken - realBalance`. Once a donation has made `realBalance > reserveToken`, any subsequent buy attempt whose naive `tokensOut` exceeds `realBalance` (i.e. one that would legitimately hit the overflow cap — normally the curve-emptying/graduating buy) causes `cappedReserveToken = reserveToken - tokensOut` to underflow in Solidity 0.8, producing an unhandled `Panic(0x11)` revert rather than the intended `OverflowCapDegenerate()` guard.

The protocol's own invariant test explicitly documents that this branch's safety depends on `pair.tokenBalance() < pair.tokenReserve()` holding at every state of the curve, and that violating it turns the `== 0` guard into a dead check for the wrong failure mode: [4](#0-3) 

But that invariant is only maintained across ordinary buys/sells — it says nothing about direct ERC20 donations of the launched `Token` into the `Pair`, which any holder can perform for free and which is exactly the vector the existing `previewLtUntilGraduation` regression test uses to break the same inequality.

### Impact Explanation
Once an attacker donates enough purchased `Token` back into the `Pair` to make `tokenBalance() > reserveToken`, the curve's overflow-cap buy path (`Router.buy` → `_computeBuy`) becomes permanently broken for any buy attempt that would need to cap at the real balance. Since the overflow cap is specifically the mechanism that lets the curve's final buy consume the remaining real supply and trigger the supply-side graduation trigger (`IPair.tokenBalance() == 0`), this can durably freeze that token's ability to complete its final capped buy and reach the supply-trigger graduation path — a permanent, unprivileged, no-cost griefing vector against the trading availability of that specific bonding curve, analogous to CVE-2017-3638's "hang or frequently repeatable crash" characterization: a reachable input causes the on-chain "query" (the buy transaction) to revert/crash instead of completing, with no recovery path since the underlying `realBalance > reserveToken` state, once created by a donation, is never un-done by ordinary trading.

### Likelihood Explanation
High reachability: any trader can buy tokens through the normal `Zap.buy`/`Bonding.buy` path and then execute a single unprivileged `Token.transfer(pair, amount)` to inflate `tokenBalance()`. The exact drain-then-donate recipe needed to break the `realBalance > reserveToken` inequality is already demonstrated and unit-tested by the project itself (`test_donation_realBalanceExceedsReserveToken`), confirming the precondition is trivially achievable with only curve-buy capital plus gas. Whether a subsequent buy actually trips the `tokensOut > realBalance` branch in `Router._computeBuy` (as opposed to `Bonding.previewLtUntilGraduation`, which is confirmed patched) could not be fully confirmed from the available index — I was not able to locate and read the guarded `previewLtUntilGraduation` implementation in `Bonding.sol` to verify whether an equivalent guard was also added to `Router._computeBuy`'s capped branch, or whether upstream capping in `Bonding`/`Zap` prevents an unguarded buy from ever reaching this exact underflow in production. This should be verified directly against `packages/contracts/src/Bonding.sol` and `packages/contracts/src/Router.sol` in a live session before treating this as confirmed-exploitable in the current codebase state.

### Recommendation
In `Router._computeBuy`, guard the capped branch against `tokensOut (== realBalance) >= reserveToken` (not just `== 0` after subtraction) and revert with a clear, named error (e.g. extend `OverflowCapDegenerate`) whenever `realBalance >= reserveToken`, mirroring the fix already applied to `Bonding.previewLtUntilGraduation`'s supply leg. More robustly, make the overflow-cap math donation-immune by deriving the sellable cap from curve-internal accounting (tokens sold so far) rather than from a live `pair.tokenBalance()` read that donations can inflate, consistent with how the USD graduation trigger was hardened to use stored reserves instead of live `balanceOf`.

### Proof of Concept
1. Launch a token via `Zap.createToken` (creates `Pair` with virtual `reserve0 = 1e9 tokens`, real transferred balance = `750,000,000` tokens).
2. As an unprivileged trader, buy a large chunk of tokens on the curve (as in `test/Zap.t.sol`'s `_stageDonationAttack`), sized so `tokensOut > 250,000,000` per the documented parabola math.
3. `Token(tokenAddr).transfer(pairAddr, donatedTokens)` — a plain ERC20 transfer, no permission needed — inflating `pair.tokenBalance()` above `reserveToken`. This exact step is reproduced by `test_donation_realBalanceExceedsReserveToken` in `test/Zap.t.sol`, which asserts `realBalance > reserveToken` post-donation.
4. Attempt a buy sized to trip `Router._computeBuy`'s overflow cap (`tokensOut > realBalance`, e.g. an oversized buy as in `test_inv_overflowCap_refundsLt`). With `realBalance > reserveToken`, `cappedReserveToken = reserveToken - tokensOut` underflows, and the transaction panics/reverts instead of completing the capped buy or emitting `OverflowCapDegenerate`.
5. Confirm this specific `Router._computeBuy` code path (as opposed to the already-fixed `Bonding.previewLtUntilGraduation`) reverts under this state by instrumenting/forking `test/Router.t.sol`'s overflow-cap test (`test_getAmountOut_...cap binds`, lines 151-170) with a preceding donation step, to determine conclusively whether current production code reverts here.
