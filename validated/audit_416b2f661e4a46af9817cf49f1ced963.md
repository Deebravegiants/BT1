### Title
Duplicate input/output tokens are not rejected in the Tron `IntentGatewayV2.placeOrder`, re-introducing the same-chain partial-fill over-release/premature-finalization bug that was already patched in the main EVM contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The reference EVM `IntentGatewayV2.placeOrder` explicitly rejects orders whose `output.assets` or `inputs` contain the same token more than once, because such duplicates corrupt per-token escrow/partial-fill bookkeeping that is keyed by token address rather than by array index. [1](#0-0) [2](#0-1)  The regression tests explicitly document why: duplicate output legs "share one `_partialFills` bucket" and duplicate input legs cause "same-chain partial fills over-release repeated input escrow." [3](#0-2) [4](#0-3)  The Tron deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `placeOrder`/escrow/withdrawal flow but has none of these duplicate-token guards. [5](#0-4) 

### Finding Description
This is the same root-cause class as the referenced Sherlock report: state that should be tracked per-unique-token is instead populated by iterating an array by index (`order.output.assets[i]`, `order.inputs[i]`), and when two array entries reference the same token, later writes silently collide with or double-count earlier ones instead of being merged/rejected. In the original report this happened in `SdtBuffer`'s reward-token array merged with bribe tokens; in `IntentGatewayV2` it happens via per-index token bookkeeping in `_partialFills[commitment][outputToken]` and in the "reduced inputs" escrow-credit logic.

The maintainers recognized and fixed this exact defect in the primary EVM contract by adding a transient-storage duplicate check over `order.output.assets` before escrow processing [1](#0-0) , and by rejecting duplicate input tokens at the point escrow is credited (`if (_orders[commitment][token] != 0) revert InvalidInput();`). [2](#0-1) 

The Tron contract's `placeOrder` performs the same reduced-input computation and escrow crediting loop but has no equivalent duplicate check anywhere in the function. [6](#0-5)  Consequently, an order with two output legs for the same token, or two input legs for the same token, can be placed on the Tron gateway, and same-chain partial fills (which key progress by `outputToken` in a per-commitment mapping analogous to `_partialFills`) or escrow-crediting logic keyed by index would suffer the same premature-finalization / over-release behavior that the regression tests on the reference contract were written to prevent.

### Impact Explanation
An unprivileged order placer (any user calling `placeOrder`) can construct an order that exploits duplicate output/input token legs. Based on the documented regression behavior on the reference contract, this can cause partial fills to finalize prematurely (treating a partially filled duplicate-token order as fully filled) or cause escrow to be over-released relative to what was actually deposited, resulting in direct loss of escrowed user/solver funds on the Tron IntentGateway deployment. This satisfies "concrete theft or permanent freezing of funds" via unsound escrow accounting reachable from a single `placeOrder`/`fillOrder` transaction pair, matching the report's severity class (High).

### Likelihood Explanation
Likelihood is high: `placeOrder` is a fully permissionless, unprivileged entry point, and constructing an order with a repeated token in `inputs` or `output.assets` requires no special access — only crafting the order struct, which is entirely user-supplied. The main EVM contract's own test suite proves this exact input shape is exploitable absent the fix, and the Tron contract lacks that fix.

### Recommendation
Port the duplicate-token protections from `evm/src/apps/IntentGatewayV2.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`:
- Reject orders whose `order.output.assets` contain a repeated `token` value before any escrow/fill accounting is performed (mirror the transient-storage check in the reference contract). [1](#0-0) 
- Reject orders whose `order.inputs` contain a repeated `token` value at the point escrow is credited, using the same `_orders[commitment][token] != 0` guard pattern. [2](#0-1) 
- Add regression tests mirroring `testRevert_PlaceOrder_DuplicateInputTokens` / `testRevert_PlaceOrder_DuplicateOutputTokens` for the Tron contract. [7](#0-6) [8](#0-7) 

### Proof of Concept
1. On the Tron chain, call `placeOrder` on `evm/tron/contracts/apps/IntentGatewayV2.sol` with an `Order` whose `output.assets` array has two entries for the same token (e.g., DAI legs of 400 and 600), mirroring the reference-contract regression scenario. [9](#0-8)  There is no check in the Tron `placeOrder` to reject this. [5](#0-4) 
2. Because the Tron contract processes escrow/partial-fill state per output-token index (same pattern as the reference contract prior to its fix), a solver filling one of the duplicate output legs can trigger the same premature-finalization/over-release condition the reference contract's regression tests were designed to catch.
3. This yields loss of escrowed input tokens to the solver beyond what the actual output delivered, or premature order finalization that leaves remaining legs unfilled while marking the order filled.

Note: I was unable to trace the full `fillOrder`/same-chain partial-fill implementation inside `evm/tron/contracts/apps/IntentGatewayV2.sol` beyond `placeOrder`/`cancelOrder`/`withdraw` within the available tool budget, so the exact downstream mechanics of the duplicate-token collision in that file (e.g., whether it even implements same-chain partial fills, or only the cross-chain all-or-nothing fill path shown at lines 391-506) could not be fully confirmed. The core finding — that the duplicate-token input/output validation present in `evm/src/apps/IntentGatewayV2.sol` is absent from the Tron variant — is confirmed directly from source.

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }

        // escrow tokens
        uint256 msgValue = msg.value;
        if (order.predispatch.call.length > 0 && order.predispatch.assets.length > 0) {
            address dispatcher = _params.dispatcher;

            // Transfer all predispatch assets to the call dispatcher
            uint256 assetsLen = order.predispatch.assets.length;
            for (uint256 i; i < assetsLen;) {
                address token = address(uint160(uint256(order.predispatch.assets[i].token)));
                uint256 amount = order.predispatch.assets[i].amount;

                if (token == address(0)) {
                    if (amount > msgValue) revert InsufficientNativeToken();
                    msgValue -= amount;

                    (bool sent,) = dispatcher.call{value: amount}("");
                    if (!sent) revert InsufficientNativeToken();
                } else {
                    IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount);
                }

                unchecked {
                    ++i;
                }
            }

            // Execute the call dispatcher with predispatch call
            ICallDispatcher(dispatcher).dispatch(order.predispatch.call);

            // Transfer tokens from call dispatcher back to IntentGateway
            Call[] memory transferCalls = new Call[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                address token = address(uint160(uint256(order.inputs[i].token)));
                uint256 requiredAmount = order.inputs[i].amount;
                uint256 balance;

                if (token == address(0)) {
                    balance = address(dispatcher).balance;
                    if (balance < requiredAmount) revert InsufficientNativeToken();
                    transferCalls[i] = Call({to: address(this), value: balance, data: ""});
                } else {
                    balance = IERC20(token).balanceOf(dispatcher);
                    if (balance < requiredAmount) revert InvalidInput();
                    transferCalls[i] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                }

                uint256 dust = balance - requiredAmount;
                if (dust > 0) emit DustCollected(token, dust);

                // Store reduced amount (after protocol fees) in escrow
                _orders[commitment][token] += reducedInputs[i].amount;

                unchecked {
                    ++i;
                }
            }
