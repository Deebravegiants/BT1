### Title
Webhook `shop-domain` header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and label the webhook are taken from unauthenticated HTTP headers. This breaks the intended binding `verified_bytes == trusted_metadata`, allowing a party who has obtained one validly-signed webhook body (e.g., from their own shop's installation) to relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.shop` (and `request.topic`) to dispatch to a handler and populate `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` only confirms that `compute_signature(verifiable_query.to_signable_string, secret) == hmac`, i.e. it authenticates the body bytes, never the header values: [4](#0-3) 

The equality that should hold is: `shop attributed to the request == shop cryptographically bound to the verified bytes`. Because `shop-domain` sits outside `to_signable_string`, this equality does not hold — the same valid `(raw_body, hmac)` pair remains valid under HMAC validation for *any* `shop-domain` header value the caller supplies.

### Impact Explanation
An unprivileged party who merely operates their own shop (which has installed the host app) receives legitimate webhooks with a valid HMAC computed over a body they fully control the content of (their own shop's webhook payload). Because `shop-domain` is not part of the signed bytes, this exact `(raw_body, hmac)` pair can be replayed with an arbitrary `shopify-shop-domain` header. If the host application (as documented/intended by this gem, via `WebhookMetadata#shop`) uses that field to select the merchant/tenant context — e.g., to look up which shop's session/data the webhook body should be merged into — an attacker can inject data under a victim shop's identity, achieving cross-tenant data confusion. This satisfies the Critical "cross-tenant access" impact category, since the tenant identifier the app relies on for cross-tenant separation is not authenticated by the signature the gem tells developers to trust.

### Likelihood Explanation
Likelihood is moderate: the attacker needs only their own (attacker-owned) shop to have the app installed, which is a normal unprivileged flow, not any special credential. Constructing the replay only requires copying body+HMAC from a webhook they already legitimately received and resending it with a different `shop-domain` header — no secret key or token is needed. The limiting factor is whether the consuming application actually keys tenant lookups off `WebhookMetadata#shop` rather than an independently verified session/shop record, which is application-dependent but is exactly the value this gem exposes and documents for that purpose.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header-derived fields used for routing) in the HMAC-covered signable representation, or otherwise cryptographically bind them to the verified body (e.g., verify shop against a value obtained from a trusted server-side source rather than the header) before they are exposed via `WebhookMetadata`. At minimum, document prominently that `Request#shop`/`#topic` are unauthenticated and must not be used for tenant selection without independent verification.

### Proof of Concept
1. Attacker installs the target app on shop `attacker.myshopify.com`.
2. App fires a legitimate webhook: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `Registry.process` still succeeds because it only checks `B` against `H`: [3](#0-2) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed body of B, ...)`, causing the host app to process attacker-controlled content under the victim shop's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
