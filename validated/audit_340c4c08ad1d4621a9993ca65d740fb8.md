### Title
Placeholder sentinel collision in `withFilesystemFallback` causes wrong-account data disclosure - ([File: adapters/storage-mobile/src/helpers/with-filesystem-fallback.ts])

### Summary
`withFilesystemFallback().get()` decides whether to read from the filesystem fallback purely by comparing the value returned from `storage.get(key)` against the literal placeholder string `'~'` [1](#0-0) . Because storage round-trips values through `JSON.stringify`/`JSON.parse`, any legitimately stored value that is exactly the string `'~'` will be misidentified as the fallback sentinel, causing `get()` to silently divert to `filesystemStorage.get(key)` and return whatever stale data was previously written to disk under that same hashed key.

### Finding Description
`set()` writes small values with `storage.setString(key, JSON.stringify(value))` [2](#0-1) , and `StorageMobile.get`/`batchGet` parses the raw string back with `JSON.parse` before returning it [3](#0-2) . If `value` is the plain string `'~'`, `JSON.stringify('~')` produces `'"~"'`, which is stored under the threshold as ordinary data; on read, `JSON.parse('"~"')` yields the string `'~'` again — identical to the `placeholder` used to mark "large value redirected to filesystem" writes [4](#0-3) . The outer `get()` then treats this legitimately small value as the sentinel and reads `filesystemStorage.get(key)` instead, returning whatever was last written to that key's file on disk — which could be large payload data left behind from a previous account/context that reused the same key (e.g., after an account is deleted and its index/key is reused, or a key namespace is reused across origins).

### Impact Explanation
If a small, legitimately-stored value under some key happens to equal the sentinel string `'~'`, callers reading that key get silently redirected to on-disk data from an unrelated prior write under the same hashed key — an unintended cross-account/cross-context data disclosure that violates STORAGE_INTEGRITY/SECRET_ISOLATION as scoped. This is a real logic defect in the sentinel comparison, reachable purely through the module's public `set`/`get` API with no internal mocking required.

### Likelihood Explanation
Exploitability is narrow: it requires (1) the exact stored `Value` to serialize/deserialize to the literal one-character string `'~'`, and (2) the same key to have previously held a large (>threshold) foreign payload written to the filesystem fallback that was never cleaned up. Precondition (1) is trivially reachable via the ordinary `set(key, '~')`/`get(key)` call sequence — no internal storage mocking is needed, since the collision is a natural consequence of the `JSON.stringify`/`JSON.parse` round trip. Precondition (2) (key reuse with stale foreign data) depends on higher-level wallet code reusing storage keys across accounts/origins, which is plausible for index-based or hashed keys but not guaranteed by this file alone.

### Recommendation
Do not rely on value equality with a plain placeholder string. Instead, wrap the placeholder in a distinguishable envelope (e.g., store `{ __fsFallback: true }` or a value that cannot collide with any legitimate `Value` type, or better, use a positive marker read from a dedicated key/prefix rather than overloading the primary value slot) so genuine data can never be confused with the sentinel.

### Proof of Concept
```ts
// Using createStorageMobile / withFilesystemFallback directly through public API:
const storage = createStorageMobile({
  asyncStorage: asMock,
  androidFallback: { filesystem, threshold: 1000, hashString, rootDir: '/async-storage' },
})

// Simulate stale foreign data left on disk under the same hashed key from a prior large write
await filesystem.writeUtf8(`/async-storage/${hashString('shared-key')}`, JSON.stringify('FOREIGN_SECRET_DATA'))

// Legitimate small write for a different logical owner, whose value happens to be '~'
await storage.set('shared-key', '~')

const result = await storage.get('shared-key')

// BUG: expected '~' (the value actually written), but get() incorrectly returns stale foreign data
expect(result).toBe('~') // fails — actual result is 'FOREIGN_SECRET_DATA'
```
