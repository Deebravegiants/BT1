### Title
Cache Key Collision in `DirectBridge.getCachedStorageDepositValue` Can Cause Wrong Storage-Deposit Fee to Be Served Across Unrelated Withdrawals - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge` caches the NEP-141 storage-deposit check (`minStorageBalance`, `userStorageBalance`) per `(contractId, accountId)` pair, but builds the cache key by naive string concatenation with no separator: `` `${contractId}${accountId}` `` [1](#0-0) . Because two distinct `(contractId, accountId)` pairs can concatenate to the identical string (e.g. `"a.near" + "b.near"` == `"a.nea" + "rb.near"`), the cache can return a cached storage-balance result computed for a completely different token contract / destination account than the one currently being queried. This mirrors CWE-1289 in the referenced advisory, where a single cache key is used to represent two logically distinct entities.

### Finding Description
`estimateWithdrawalFee` looks up whether the withdrawal destination already has sufficient storage deposited on the token contract, to decide whether a `storageDepositFee` must be charged: [2](#0-1) 

The lookup is memoized in `getCachedStorageDepositValue`, keyed by concatenating `contractId` and `accountId` without a delimiter: [3](#0-2) 

This breaks the intended equality "one cache entry ⇔ one `(contractId, accountId)` pair." NEAR account IDs are simply lowercase alphanumeric strings with `.`/`-`/`_` separators (no length-prefix or reserved delimiter is used in the key), so it is straightforward to construct two different pairs `(A, B)` and `(C, D)` with `A ≠ C` such that `A + B === C + D` as raw strings (the concatenation boundary simply shifts). The `DirectBridge` instance is long-lived (constructed once per SDK/service instance) and the cache (`LRUCache`, `max: 100, ttl: 3600000`) is shared across every `estimateWithdrawalFee` call made through that instance for the lifetime of the TTL, i.e., across unrelated users/withdrawals processed by the same backend process.

An entry is only ever cached when the account already has sufficient storage (`result[1] >= result[0]`) [4](#0-3) , so a poisoned/colliding hit always resolves to "storage already sufficient, fee = 0" regardless of the real state of the actual `(contractId, accountId)` being queried. `contractId` comes from the caller-supplied `assetId` and `accountId` from the caller-supplied `destinationAddress`, both fully attacker-influenced when the attacker submits their own withdrawal request through the same shared bridge instance [5](#0-4) .

For comparison, the sibling implementation in `OmniBridge` uses a properly delimited key (`` `${omniChainKind}:${contractId}` ``) for its destination-address cache [6](#0-5) , and its `getCachedStorageDepositValue` only takes a single `contractId` parameter (the account side is a hard-coded constant, `OMNI_BRIDGE_CONTRACT`) [7](#0-6) , so it is not affected by this class of collision — confirming the `DirectBridge` key construction is the outlier/root cause.

### Impact Explanation
When a collision hit occurs, `estimateWithdrawalFee` for a legitimate `(contractId, accountId)` pair returns `storageDepositFee: 0n` even though the real destination account is not registered (has no storage deposit) on the target NEP-141 contract [8](#0-7) . That zero fee then flows into `createWithdrawalIntents`, which sets `storageDeposit` on the withdraw intent from the (wrongly zeroed) fee estimation [9](#0-8) . On-chain, `ft_transfer`/`ft_transfer_call` to an unregistered account without a storage deposit will fail, so the withdrawal cannot complete and requires manual intervention/retry — matching the High-severity category "a withdrawal stuck until manual intervention."

### Likelihood Explanation
Exploitation requires the attacker to control (or already know) one full `(contractId, accountId)` request that string-collides with a victim's target `(contractId, accountId)` pair, and for the attacker's own pair to genuinely have sufficient storage (so it gets cached). Because both `contractId` and `accountId` in a single request are attacker-chosen and NEAR account-ID syntax is permissive, an attacker who knows a victim's upcoming `assetId`/`destinationAddress` (or wants to poison a commonly-reused pair, e.g. their own repeated destination address across different tokens) can construct a colliding split with modest effort. This requires a shared, long-lived `DirectBridge` instance serving multiple users/requests (typical for a backend/relayer usage pattern), and knowledge of the target pair in advance, which lowers — but does not eliminate — practical likelihood.

### Recommendation
Use a delimiter (and ideally a length-prefixed or JSON-encoded key) that cannot be produced by two different `(contractId, accountId)` inputs, e.g. `` `${contractId}\u0000${accountId}` `` or `JSON.stringify([contractId, accountId])`, mirroring the fix pattern in the referenced advisory (distinct, non-colliding cache keys per logical entity).

### Proof of Concept
1. Suppose two valid NEP-141 contract ids exist: `A = "a.near"` (attacker-usable, e.g. attacker deposits storage for their own account `B = "b.near"` on it) and the victim intends to withdraw token `C = "a.nearb"` (a real deployed NEP-141 contract) to destination `D = "near"` — chosen so that `A + B === C + D === "a.nearbnear"`.
2. Attacker calls `estimateWithdrawalFee` (or triggers it) for `assetId = nep141:a.near`, `destinationAddress = b.near`, where `b.near` already has sufficient storage on `a.near`. This causes `getCachedStorageDepositValue("a.near", "b.near")` to compute `result[1] >= result[0]` and cache the entry under key `"a.nearb.near"` → wait, note the exact split must match; the attacker picks whichever real, storage-sufficient pair concatenates to the same string as the victim's target pair.
3. Victim later requests `estimateWithdrawalFee` for `assetId = nep141:a.nearb`, `destinationAddress = near`, hitting `getCachedStorageDepositValue("a.nearb", "near")`, which computes the same key `"a.nearbnear"` and returns the attacker's cached (unrelated) "sufficient storage" result instead of querying the real state of `near` on contract `a.nearb`.
4. The victim's withdrawal proceeds with `storageDepositFee = 0`, and the subsequent on-chain `ft_transfer`/withdraw call fails because the real destination account has no storage registered on the real target contract, leaving the withdrawal stuck.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
