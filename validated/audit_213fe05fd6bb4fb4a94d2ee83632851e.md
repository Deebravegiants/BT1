## Finding: Unmetered proof-size DoS in `pallet-ismp::handle_unsigned`

### Title
Fixed weight metering for `handle_unsigned` lets an unbounded, attacker-crafted consensus proof (GRANDPA justification / BEEFY signature set) consume verification time far exceeding the weight charged, enabling block-execution DoS - (`File: modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is a free, unsigned, permissionless entry point ("Execute the provided batch of ISMP messages for free with valid proofs") that anyone can submit. It is charged a **fixed** weight regardless of the content of the submitted messages: [1](#0-0) [2](#0-1) 

This mirrors CVE-2023-6237's root cause: expensive cryptographic computation is performed on attacker-controlled, unbounded-size input, taking far longer than expected, before the input is rejected as invalid — except here the "expected" cost is what's actually *billed* to the caller via Substrate weight metering, so an attacker gets the CPU-time asymmetry for free.

### Finding Description
`Self::execute(messages.clone())` inside `handle_unsigned` dispatches into `handle_incoming_message`, which for a `Message::Consensus` routes to the configured consensus client's `update_client`/`verify_consensus`: [3](#0-2) 

For the GRANDPA consensus client (not filtered by any runtime's `IsmpCallFilter`, unlike BEEFY — see below), verification walks every precommit in the justification and, for each one, walks an ancestry chain built from the attacker-supplied `unknown_headers`/`votes_ancestries`: [4](#0-3) [5](#0-4) 

Both `self.commit.precommits` (each requiring an Ed25519 `check_message_signature`) and `self.votes_ancestries` (each header hashed and chained) are decoded directly from the untrusted `consensus_proof` bytes with no explicit upper bound in the verifier itself — the only limits are the runtime's general extrinsic-length/block-length caps, which are typically megabytes, not proof-shape-aware. An attacker can submit a single justification with many precommits and a long ancestry chain, driving `O(precommits × ancestry_depth)` signature checks and hash-chain walks.

The BEEFY (ECDSA) verifier has the same unbounded-computation shape: `signatures_length`/`sigLen` is only bounded from *below* (supermajority check), never from *above*, so a caller can pad the signature list far past the authority-set size; every entry still pays for an EC signature recovery before the (cheap) merkle-multi-proof check ultimately rejects the padded set: [6](#0-5) [7](#0-6) 

Both Gargantua and Nexus explicitly filter out raw BEEFY updates from `handle_unsigned` precisely because they know it bypasses the (separately-weighted) SP1 proof path: [8](#0-7) 

but this filter is **BEEFY-specific** — it does not cover GRANDPA (`ismp-grandpa`), which remains fully reachable through the fixed-weight `handle_unsigned` path on any chain configuring it as a `ConsensusClient`. Any deployment of `pallet-ismp` with the GRANDPA client configured (per the documented `Config::ConsensusClients` example) inherits this gap: [9](#0-8) 

### Impact Explanation
Because `handle_unsigned` charges the constant `Weight::from_parts(300_000_000, 0)` no matter how large or expensive the submitted proof actually is, and because it is dispatched with `ensure_none` (no signer, no transaction fee), an attacker can submit unsigned transactions whose *declared* weight is trivial but whose *actual* execution time is many multiples of what was budgeted. Submitted in bulk (bounded only by block/extrinsic length limits, not verification cost), these transactions can consume disproportionate block-authoring time relative to the weight they were charged, degrading block production / increasing block times for the whole chain — a resource-exhaustion/DoS on the runtime's message-dispatch path, reachable by any unprivileged relayer or transaction submitter with no funds at risk (the call is free).

### Likelihood Explanation
High: `handle_unsigned` is explicitly designed to accept arbitrary relayed proofs from anyone for free; validation only checks whether the proof is well-formed and eventually valid/invalid, not how much verification work it costs relative to what's charged. No signature, deposit, or reputation is required to submit it, and the GRANDPA path is unfiltered on the shipped runtimes.

### Recommendation
- Compute `handle_unsigned`'s weight (or a pre-dispatch/`validate_unsigned` rejection) proportionally to the size of the consensus proof / number of signatures and ancestry headers actually present, instead of a flat constant.
- Enforce explicit upper bounds on `signed_commitment.signatures.len()` (BEEFY) capped at (or near) the trusted authority-set size, and on GRANDPA `unknown_headers`/`votes_ancestries` length/`precommits` count, rejecting oversized proofs before any expensive cryptographic work is performed.
- Consider extending the existing BEEFY-specific `IsmpCallFilter` pattern (routing expensive raw multi-sig verification off the free `handle_unsigned` path) to GRANDPA and any other consensus client whose verification cost scales with attacker-controlled proof size.

### Proof of Concept
1. Construct a `Message::Consensus` for the GRANDPA consensus state with a crafted `GrandpaJustification` containing: (a) a maximal number of precommits (bounded only by extrinsic size limits) each with a syntactically valid but unrelated Ed25519 signature, and (b) a long `votes_ancestries` chain requiring a full walk per precommit in `AncestryChain::ancestry`.
2. Submit this as `pallet_ismp::Call::handle_unsigned { messages: vec![consensus_message] }` via an unsigned transaction (as intended by the API, no signer required).
3. Observe that `#[pallet::weight(weight())]` charges the fixed `300_000_000` regardless of proof size, while `verify_grandpa_finality_proof` → `GrandpaJustification::verify_with_voter_set` performs `O(precommits × ancestry_depth)` real cryptographic and hashing work before ultimately returning an error (since the proof isn't genuinely valid) — the wall-clock cost paid by validators processing the block is far greater than the weight billed, and this can be repeated cheaply and in parallel by submitting many such unsigned transactions.

		Message::Request(req) => request::handle(host, req),

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}

/// Gargantua routes all BEEFY consensus updates through `pallet-beefy-consensus-proofs`, which
/// requires each proof to pass SP1 zkVM verification before it can advance the BEEFY state.
/// Allowing raw updates through `handle_unsigned` would bypass that requirement entirely, so
/// any batch that carries a BEEFY consensus message is rejected here. `fund_message` is also
/// disabled because gargantua uses the bandwidth model for request fees; per-message top-ups
/// have no role in that accounting.
///
/// A consensus message only names the state it updates, so we ask the host which client owns
/// that state and compare against BEEFY. Reading from the host remains correct even as more
/// states (Polkadot, Paseo) are bound to the same client over time.
pub struct IsmpCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for IsmpCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		use ::ismp::{host::IsmpHost, messaging::Message};
		match call {
			RuntimeCall::Ismp(pallet_ismp::Call::fund_message { .. }) => false,
			RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
				let host = Ismp::default();
				!messages.iter().any(|message| match message {
					Message::Consensus(consensus) =>
						host.consensus_client_id(consensus.consensus_state_id) ==
							Some(ismp_beefy::BEEFY_CONSENSUS_ID),
					_ => false,
				})
			},
			_ => true,
		}
	}
}
