## Analysis

This maps to the ERC-20 "unsafe transfer return-value" bug class, translated to Clarity/SIP-010 semantics. In Clarity, `try!` unwraps a `(response bool uint)` only on `(err ...)` — it does **not** inspect the boolean payload of an `(ok ...)`. So if a SIP-010 token's `transfer` returns `(ok false)` instead of an `(err ...)` when a transfer fails (exactly the non-standard-token behavior the report describes for USDT-style ERC-20s), the caller treats it as success and proceeds.

### Title
Unchecked SIP-010 `transfer` boolean return in collateral deposit lets users mint phantom collateral - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`receive-tokens` in the market vault calls the asset's `transfer` function and the caller only wraps it in `try!`, which passes through any `(ok false)` result as success. A SIP-010 token whose `transfer` returns `(ok false)` on failure (rather than reverting with `err`, as some non-standard token implementations do) lets a user record collateral in the market-vault's ledger without the underlying tokens ever being received by the contract.

### Finding Description
`collateral-add` in the market vault credits the user's collateral map entry and then attempts to pull tokens from the caller: [1](#0-0) 

The token pull itself is: [2](#0-1) 

`(try! (contract-call? asset transfer amount account current-contract none))` only aborts the transaction if the trait call returns `(err ...)`. It does not check whether the returned boolean inside `(ok ...)` is `true`. Per the SIP-010 trait, `transfer` returns `(response bool uint)`; a conformant reference implementation always signals failure via `err`, but this is a convention, not an enforced invariant — the same non-standard-behavior class the external report flags for ERC-20/USDT (`return false` instead of reverting). Any asset registered through the asset registry whose token contract follows this pattern breaks the identity:

`market-vault token balance (custody) == Σ collateral map entries for that asset`

because `add-user-collateral` (invoked inline in the `let` bindings of `collateral-add`) records the credit while `receive-tokens` silently no-ops. [3](#0-2) 

The same unchecked pattern recurs in the tokenized vaults' underlying-asset intake, e.g. for the ststxbtc vault, which forwards to an externally-controlled token contract via `try!` without checking the boolean: [4](#0-3) 

### Impact Explanation
If any registered collateral/underlying asset's SIP-010 implementation can return `(ok false)` on a failed transfer instead of erring, an attacker can call `collateral-add` (via `market.clar`) and be credited with collateral in the market-vault ledger without transferring any real tokens. That phantom collateral can then be used to `borrow` real assets from other vaults, directly stealing protocol funds and causing insolvency — the collateral backing shown in `market-vault` no longer corresponds to tokens actually custodied.

### Likelihood Explanation
Exploitability is entirely dependent on whether any asset the DAO registers has a SIP-010 `transfer` implementation that returns `(ok false)` on failure rather than reverting. This is plausible for bridged/wrapped or externally-controlled tokens (e.g., `ststxbtc-token-v2`) that Zest does not control, mirroring exactly the non-standard-ERC-20 concern in the source report. Registering such an asset is a normal, intended DAO action (not a compromise), so this does not fall under the excluded "DAO compromise" category.

### Recommendation
After every `contract-call? asset transfer ...`, explicitly assert the returned boolean is `true` (not just that the response is `ok`), e.g.:
```clarity
(let ((ok? (try! (contract-call? asset transfer amount account current-contract none))))
  (asserts! ok? ERR-TRANSFER-FAILED))
```
Apply this to `receive-tokens`/`send-tokens` in `v0-market-vault.clar` and to `receive-underlying`/`send-underlying` in every vault contract that forwards to externally-controlled SIP-010 tokens.

### Proof of Concept
1. DAO registers asset `X` as valid collateral, where `X`'s `transfer` function returns `(ok false)` when the caller lacks sufficient balance/allowance instead of `(err ...)`.
2. Attacker, holding zero balance of `X`, calls `market.collateral-add` with `ft = X` and some `amount`.
3. `market-vault.collateral-add` runs `add-user-collateral` (credits ledger) and calls `receive-tokens`, which calls `X.transfer`; `X` returns `(ok false)` since attacker has no balance.
4. `try!` unwraps `false` without erroring; execution continues; `insert updated-entry` commits the mask update.
5. Attacker now has recorded collateral for asset `X` with no tokens actually held by `market-vault`, and can borrow real assets against this phantom collateral via `market.borrow`. [1](#0-0)
