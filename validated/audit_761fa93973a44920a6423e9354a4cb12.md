Found a genuine and highly analogous root cause: a "user_centric_signup" flag, which is delivered to the orb through the **unprivileged user's QR-code lookup response** (`backend::user_status::request`), is trusted to *skip the backend enrollment verification path entirely* and to directly assign a `Success`/`Error` enrollment status — mirroring the H-04 pattern of an unprivileged input flipping a security-relevant classification (`AssetClass`) that changes downstream risk/verification behavior without additional gating.

### Title
Unverified `user_centric_signup` flag from QR-derived user data bypasses backend enrollment verification, enabling attacker-controlled signup success classification - ([File: src/plans/mod.rs])

### Summary
In `MochiProfileV0.registerAsset()`, an unprivileged caller can flip `_assetClass` for an already-registered asset, changing risk/liquidation logic without any authorization check. The analogous pattern in `orb-core` is in `MasterPlan::do_signup` (`src/plans/mod.rs`): the boolean `user_centric_signup`, sourced from the QR-derived `UserData` returned by `backend::user_status::request` (`src/backend/user_status.rs`), is used to decide whether the orb performs the normal server-verified enrollment (`enroll_user::Plan::run`, which polls the backend and requires `Status::Success`) or instead **locally assigns** `enroll_user::Status::Success`/`Error` purely from the *locally computed* `signup_reason`, with no backend round-trip confirming the enrollment.

### Finding Description
`do_signup` reads `user_centric_signup` out of `qr_codes.user_data` [1](#0-0) , then branches:

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
``` [2](#0-1) 

When `user_centric_signup` is `true`, the code never calls `enroll_user::Plan::run`, which is the path that actually posts the signup to the backend and polls `signup_poll::request` until the backend confirms `Status::Completed`/`success: true` [3](#0-2) . Instead, `enrollment_status` (and thus `result.success`, which gates PCP upload/finalization and the UI's "signup success" state) is derived solely from `signup_reason`, a value computed locally on the orb from the local fraud/pipeline outcome, and is *not confirmed by the backend at all* in this branch.

Critically, `user_centric_signup` itself originates from `orb_qr_link::UserData`, which is decoded from data associated with the **user's QR code** and validated only via a signature/hash check (`user_data.verify(user_data_hash)`), not via any binding to the orb's authorization policy for this specific field [4](#0-3) . This is structurally identical to `registerAsset()`'s flaw: a state field that gates significant downstream security logic (there: `_assetClass` controlling liquidation math; here: `user_centric_signup` controlling whether backend-verified enrollment is bypassed) is set/consumed without an independent authorization re-check comparable to the missing `require(_assetClass[_asset] == 0)`.

### Impact Explanation
If the `user_centric_signup` flag can be influenced or misreported (e.g., stale/cached backend responses, backend bugs, or a compromised/misbehaving companion-app-controlled QR flow feeding into this response), the orb will locally mark a signup as `Success` without ever confirming with the backend that the enrollment (and associated fraud/duplicate checks server-side) actually occurred or passed. This can lead to misattributed or unauthorized signup completion states being recorded in the `DebugReport`/`enrollment_status`, and the corresponding UI "signup success" flow being shown, even though the backend never validated the enrollment — analogous to the liquidation-threshold corruption in the original report, where a single trusted-but-unverified flag silently changes the security-critical evaluation path.

### Likelihood Explanation
The trust boundary is reachable on every user-centric signup path (self-serve / app-driven signups), since `user_centric_signup` is populated directly from the QR-derived/backend response tied to the scanned user QR code, and the orb performs no additional server round-trip to confirm success in that branch. Exploitation likelihood depends on whether an attacker can influence the value or timing of this backend response, which I could not fully verify beyond the code shown (the backend endpoint itself is out of scope of this repo).

### Recommendation
Do not allow `user_centric_signup` to fully bypass server-side confirmation of enrollment outcome. At minimum, require the same `signup_post`/`signup_poll` round trip (or an equivalent authoritative backend confirmation) before setting `enrollment_status` to `Success`, or gate the local-only path behind stronger validation of the QR-derived flag's authenticity, mirroring the recommended `require(...)` guard in the original report — i.e., add an explicit check that the enrollment status was actually confirmed by an authoritative source before it is allowed to be set to `Success`.

### Proof of Concept
Not independently reproducible from static analysis alone; the control-flow trace above (`src/plans/mod.rs:639-656` combined with `src/backend/user_status.rs:163-244`) demonstrates the code path, but exploitability depends on backend-side behavior/data integrity that is outside this repository and was not verified.
