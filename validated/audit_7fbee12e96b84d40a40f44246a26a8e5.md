### Title
Unchecked u128→u64 truncation in `InvariantPool`/`InvariantToken` deposit math allows unbacked LP-token minting and pool insolvency - (File: `program/src/math.rs`)

### Summary
`InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin` and `InvariantPool::exchange_pool_to_token` / `exchange_token_to_pool` compute `A.checked_mul(B).unwrap().checked_div(C).unwrap().as_u64()`. `checked_mul`/`checked_div` operate on `U128` and never overflow (`u64::MAX * u64::MAX < u128::MAX`), so they never panic — but the final `.as_u64()` call **silently truncates** the `U128` quotient to the low 64 bits instead of validating that it fits in `u64`. This is the exact same bug class as the reported `get_delta_b` issue: a wide-multiplication result is assumed to fit a narrower type, and the low limb/bits are returned without checking the high bits, instead of aborting. [1](#0-0) 

### Finding Description
`Calculator::to_u64`/`to_u128` in this codebase correctly use `try_into()` (a checked, error-propagating conversion) [2](#0-1) . However, the exchange-rate helpers used directly in the Deposit/Withdraw paths bypass this safe path and call the truncating `primitive_types::U128::as_u64()` instead: [1](#0-0) 

`process_deposit` uses exactly these helpers to compute both the "other side" amount to deduct and the amount of LP tokens to mint:
- `deduct_pc_amount = invariant.exchange_coin_to_pc(deposit.max_coin_amount, Ceiling)` [3](#0-2) 
- `mint_lp_amount = invariant_coin.exchange_token_to_pool(amm.lp_amount, Floor)` [4](#0-3) 

Both of these ultimately compute `token_total_amount * token_input / token_total` as a `U128`, then truncate to `u64` with `.as_u64()`. If `token_total` (the pool's real reserve on that side, `total_coin_without_take_pnl` or `total_pc_without_take_pnl`) is small relative to `token_input` (the attacker-supplied `deposit.max_coin_amount`/`max_pc_amount`, up to `u64::MAX`) and `token_total_amount` (`amm.lp_amount`), the quotient can exceed `u64::MAX` while still fitting comfortably in `U128` — so no `checked_mul`/`checked_div` panics, and the value is silently wrapped by `.as_u64()`.

Nothing downstream re-validates this: `deduct_pc_amount > deposit.max_pc_amount` is trivially satisfiable by the attacker setting `max_pc_amount = u64::MAX`, and `other_amount_min` is optional and attacker-controlled (they simply omit it). `mint_lp_amount` is minted directly with no upper-bound sanity check against `amm.lp_amount` or reserves: [5](#0-4) 

### Impact Explanation
An attacker who creates (or otherwise drives into a state with) a pool whose reserve on one side is small relative to `amm.lp_amount` and the other reserve can call `Deposit` with a large `max_coin_amount`/`max_pc_amount` to make `amm.lp_amount * deduct_coin_amount / total_coin_without_take_pnl` exceed `2^64`. The `.as_u64()` truncation then yields an attacker-chosen (via offline modular arithmetic) `mint_lp_amount` that is disconnected from the real value deposited — enabling unbacked LP-token minting. Because LP tokens represent a proportional claim on both vaults (`amm_coin_vault`/`amm_pc_vault`) via `Withdraw`, an attacker minting a wrapped/inflated LP balance can subsequently withdraw a disproportionate share of real pool reserves, directly diluting/stealing funds from other liquidity providers and leaving the pool insolvent (`total_coin_without_take_pnl`/`total_pc_without_take_pnl` no longer matching the true backing of outstanding LP supply). This matches the report's "unbacked LP minting / insolvent pool accounting" impact category.

### Likelihood Explanation
The attacker fully controls the `Deposit` instruction's `max_coin_amount`/`max_pc_amount`/`base_side`/`other_amount_min` fields in a single, unprivileged transaction. The only prerequisite is a pool state where reserves are skewed relative to `amm.lp_amount` (e.g., attacker creates the pool themselves via `Initialize2` with a self-minted low-value token on one side and a tiny amount of the valuable token on the other, subject to the `10^lp_mint.decimals` minimum-liquidity lock in `process_initialize2` [6](#0-5) ). This makes the attack self-servable without needing to compromise an existing healthy pool, though achieving the precise overflow-triggering ratio requires careful (but fully computable offline) selection of initial reserves and deposit amounts.

### Recommendation
Replace every `.as_u64()`/`.as_u128()` truncating cast in `InvariantToken`/`InvariantPool` (and any other place converting a `U128`/`U256` computation result down to a narrower integer) with the checked `Calculator::to_u64`/`to_u128` pattern already used elsewhere in the codebase, returning `AmmError::ConversionFailure` (i.e., aborting the transaction) instead of silently wrapping when the value does not fit the target width — mirroring the patch described in the report (validate the high limbs/bits of the product before truncating, and abort if they are non-zero).

### Proof of Concept
Root-cause reproduction (conceptual, following the code path exactly):
1. Let `total_coin_without_take_pnl = C` (real reserve, attacker-controlled to be small relative to `amm.lp_amount`), `amm.lp_amount = L`.
2. Attacker calls `Deposit` with `base_side = 0`, `max_coin_amount = M` chosen such that `L * M / C > u64::MAX` (e.g., pick `C` small and `L`, `M` such that `L*M` exceeds `2^64 * C`).
3. In `process_deposit`, `mint_lp_amount = invariant_coin.exchange_token_to_pool(L, Floor)` computes `U128::from(L).checked_mul(M.into()).unwrap().checked_div(C.into()).unwrap().as_u64()` [7](#0-6) . Because the true quotient exceeds `u64::MAX` but is still `< u128::MAX`, no `unwrap()` panics; `.as_u64()` truncates the quotient modulo `2^64`, producing an arbitrary, attacker-solvable `mint_lp_amount` unrelated to the real deposited value.
4. `amm.lp_amount = amm.lp_amount.checked_add(mint_lp_amount).unwrap()` and the LP tokens are minted to the attacker [5](#0-4) , after which `Withdraw` lets the attacker redeem a disproportionate share of both vaults.

I could not fully verify the exact `lp_mint.decimals` constant or confirm a complete end-to-end numeric example (specific reserve values that simultaneously satisfy the `InitLpAmountTooLess` minimum-liquidity check and the overflow inequality) within the available tool calls — a background Devin session with full repo/build access would be needed to compile a concrete unit test (analogous to the Move PoC in the report) that exercises `Processor::process_deposit`/`InvariantPool::exchange_token_to_pool` with concrete numbers and confirms the wrapped `mint_lp_amount`.
