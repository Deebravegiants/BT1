This confirms the bug pattern. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header [3](#0-2) . `Registry.process` then trusts `request.shop` and dispatches it to the handler after only this body-only HMAC check [4](#0-3) .

### Title
Webhook tenant attribution (`shop`, `topic`, `webhook_id`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, yet the shop attribution used downstream (`shop`, plus `topic`/`webhook_id`) is taken from HTTP headers that are never part of the signed material.

### Finding Description
`Request#to_signable_string` returns just `@raw_body` [1](#0-0) . `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers respectively [2](#0-1) . `Utils::HmacValidator.validate_signature` verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only authenticates the body bytes, never the headers [3](#0-2) . `Registry.process` performs exactly this body-only check and then immediately trusts `request.shop` to build `WebhookMetadata` handed to the app's handler [4](#0-3) .

The identity binding that should hold is: `shop attributed to the event == shop whose data the HMAC authenticates`. Because the app's webhook HMAC secret (`Context.api_secret_key`) is shared across all shops that installed the app — it is not shop-specific — any merchant who has installed the app can legitimately trigger a webhook for their own store, capture the valid `(raw_body, hmac)` pair Shopify sent them, and replay it directly to the app's public webhook endpoint with the `shopify-shop-domain` header (and optionally `topic`/`webhook-id`) rewritten to a victim shop's domain. `HmacValidator.validate` will return `true`, because the raw body's HMAC is still valid under the same shared secret [5](#0-4) , while `request.shop` used to look up/attribute the event is fully attacker-controlled and never checked against anything covered by the signature.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: an unprivileged internet user who legitimately installed the app on their own shop can forge webhook deliveries "as" any other shop that also has the app installed, without ever needing the app's `client_secret`. Depending on how a host application keys off `WebhookMetadata#shop` (e.g., to update/delete records, revoke access, or process GDPR redaction topics), this can lead to cross-tenant data corruption or spoofed mandatory-compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) attributed to a shop the attacker doesn't own. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
The attacker needs no privileged credentials — only their own legitimate app installation (any merchant can do this) and the ability to POST directly to the app's public webhook receiver endpoint with custom headers, which is standard HTTP access. The `shop`, `topic`, and `webhook_id` headers are trivially replaceable since `Request#initialize` performs no cross-check between header contents and the signed body.

### Recommendation
Include the tenant-identifying fields (`shop-domain`, and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload before trusting `request.shop` in `Registry.process`. At minimum, `to_signable_string` should incorporate the shop domain header so a replay against a different `shop-domain` invalidates the signature.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `orders/create`) on their own shop and captures the genuine `raw_body` and `shopify-hmac-sha256` value Shopify sent to the app's endpoint.
3. Attacker replays the identical `raw_body`/`hmac-sha256` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `@raw_body` is checked [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never generated for that shop [7](#0-6) .
