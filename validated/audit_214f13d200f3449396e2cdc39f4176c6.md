### Title
Un-signed/mixed-batch consensus updates permanently erase relayer consensus-reward span - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
### Finding Description
`pallet_consensus_incentives::on_executed` only inspects `messages.get(0)` of a submitted batch to decide whether to reward anyone: [1](#0-0) 

If the first message in a batch is not `Message::Consensus` (e.g. a relayer bundles a `Request`/`Response`/`Timeout` message ahead of a `ConsensusMessage`), or the `signer` bytes on the `ConsensusMessage` fail to decode/recover a valid public key, `maybe_relayer_account` resolves to `None` and `process_message`/`calculate_reward` never run for that batch — no `RelayerRewarded` event, no `LastRewardedHeight` update.

Crucially, the state-machine height watermark is advanced completely independently of this reward path. `update_client` in the core ISMP consensus handler always calls `host.store_latest_commitment_height`, which overwrites `PreviousStateMachineHeight` with the *previous* `LatestStateMachineHeight` on every successful consensus update, regardless of whether any reward was paid: [2](#0-1) [3](#0-2) 

The next time a reward *is* successfully paid, `calculate_reward` computes the payable span using `LastRewardedHeight` and, if that watermark was never set, falls back to `previous_commitment_height` — which by then has already been advanced past the unrewarded update: [4](#0-3) 

So the block-span covered by the unrewarded update is silently and permanently dropped from any future reward computation — it can never be paid to any relayer, analogous to the Malt `RewardThrottle` bug where `fillInEpochGaps`/`populateFromPreviousThrottle` mutate epoch state without funding the epoch, permanently zeroing out a reward that `checkRewardUnderflow` would otherwise have paid.

### Impact Explanation
Any relayer (unprivileged) that submits a consensus-update batch whose first message isn't a `Message::Consensus`, or that intentionally garbles the `signer` field, causes the height watermark (`PreviousStateMachineHeight`/`LatestStateMachineHeight`) to advance without a matching reward. Because the reward baseline (`LastRewardedHeight`) is only ever set on a *successful* payout, and its fallback is the already-advanced `previous_commitment_height`, this permanently and irrecoverably shrinks the reward-eligible span for every subsequent relayer that delivers consensus proofs for that state machine. This is a permanent loss of legitimately earned relayer incentive funds (a "freezing"/unbacked-loss condition on the reward accounting), reachable from a single submitted extrinsic by any relayer — no admin/governance/collator privilege required.

### Likelihood Explanation
High likelihood of accidental triggering (batches naturally mix message types, and `signer` recovery can fail for mundane reasons — malformed signature, wrong key type), and trivially triggerable deliberately by a relayer wanting to grief competitors or simply skip getting rewarded for one update (no extra cost to the attacker, since `update_client`'s correctness checks are independent of `signer`).

### Recommendation
- Do not gate the fee-handler reward path on `messages.get(0)`; iterate the full batch to find any `Message::Consensus` entries regardless of position.
- Decouple the reward baseline from `PreviousStateMachineHeight`/`latest_commitment_height` side effects of `update_client`; persist an explicit "last observed height eligible for reward" watermark that is updated at the same time as the state watermark, independent of whether a specific relayer could be attributed/paid, so that an unrewarded span is queued for a later retry (e.g. from a treasury/overflow-style backstop) rather than permanently discarded.
- Alternatively, always update `LastRewardedHeight` to the new `latest_height` whenever `update_client` succeeds (even if no relayer could be attributed for that specific update), and separately track/settle any "orphaned" reward amounts so they aren't silently zeroed.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock` for state machine `S` (via `update_cost_per_block`).
2. Relayer submits a batch `[Message::Request(...), Message::Consensus(msg_A)]` where `msg_A` advances `S` from height 100 to 1024. `handle_incoming_message` processes each message; `update_client` for `msg_A` calls `store_latest_commitment_height`, setting `PreviousStateMachineHeight[S] = 100`, `LatestStateMachineHeight[S] = 1024`. `on_executed` is then invoked with this message batch; because `messages[0]` is `Message::Request`, `maybe_relayer_account` is `None`, so `process_message` never runs — `LastRewardedHeight[S]` remains unset. No reward paid, no error.
3. A second relayer submits `[Message::Consensus(msg_B)]` correctly signed, advancing `S` from 1024 to 2000. `update_client` sets `PreviousStateMachineHeight[S] = 1024`. `on_executed` now succeeds: `calculate_reward` computes `baseline = LastRewardedHeight.unwrap_or(previous_height) = 1024`, `blocks = 2000 - 1024 = 976`.
4. The 924 blocks of real, valid consensus progress (100→1024) are never paid to any relayer, and there is no remaining on-chain data path to recover or claim that span — the reward is permanently lost, exactly mirroring the Malt `RewardThrottle` "epoch loses its reward" defect described in the source report.

	fn store_latest_commitment_height(&self, height: StateMachineHeight) -> Result<(), Error> {
		let previous_height = LatestStateMachineHeight::<T>::get(height.id).unwrap_or_default();
		PreviousStateMachineHeight::<T>::insert(height.id, previous_height);
		LatestStateMachineHeight::<T>::insert(height.id, height.height);
		Ok(())
	}
