### Title
Mutable `autoApprove`/`trusted` Origin State Allows Rewriting Signing-Authorization Rules After Connection - ([File: features/connected-origins/module/connections.js])

### Summary
The `ConnectedOrigins` module persists per-origin authorization state (`trusted`, `autoApprove`) that governs whether a connected dApp origin can silently retrieve accounts and have its signing requests auto-approved. Both attributes can be rewritten at any time after the origin was first connected, with no snapshot, time-lock, or re-confirmation tied to the state at connection time, mirroring the `setWhitelistReserve()` bug class of mutable post-commitment authorization parameters.

### Finding Description
When an origin is (re)added via `add()`, the `trusted` flag is merged with whatever value is passed in, falling back only to the previous value if omitted: [1](#0-0) 

`isTrusted()` gates `getConnectedAccounts()`, which can return wallet account addresses even while the wallet is locked: [2](#0-1) [3](#0-2) 

Separately, `setAutoApprove()` flips the `autoApprove` attribute for an already-connected origin with no lock, cooldown, or re-verification of the conditions that existed when the origin was first connected: [4](#0-3) 

Both `add` and `setAutoApprove` are exposed directly on the public SDK API surface (`exodus.connectedOrigins.*`), consumed by the UI/background layer without any freeze period after the initial connection: [5](#0-4) 

This is structurally the same bug class as `setWhitelistReserve()`: a security-relevant parameter (`autoApprove`/`trusted`) that determines the rules under which future actions (fund allocation vs. auto-signing) occur, is mutable after the initial trust decision was made, with no lock, versioning, or explicit re-consent tied to the original decision.

### Impact Explanation
If the `autoApprove` or `trusted` flags for an origin can be changed through any code path other than an explicit, freshly-presented user confirmation dialog (e.g., a stale/replayed UI message, a race in the connect flow, or a compromised/malicious extension-side caller reusing the API), a dApp origin's future transactions could be silently signed (`autoApprove: true`) or its addresses silently disclosed while locked (`trusted: true`) — without the user re-affirming that decision under the current connection state. This is analogous to priority/public allocation being silently rewritten after users already committed funds.

### Likelihood Explanation
Medium: `setAutoApprove`/`add` are legitimate, always-callable API methods (not permission-checked beyond being invoked from the extension's own background/UI layer). There is no application-level lock preventing repeated calls to flip `autoApprove`/`trusted` for an origin that a user previously connected under a different trust posture, and no snapshot of the original consent context is recorded or enforced. Exploitability depends on whether any caller (UI bug, message-passing flaw, or malicious extension code sharing the same API surface) can invoke these methods outside of a genuine, contemporaneous user approval — this exact reachability from an untrusted context could not be fully confirmed from the indexed files available.

### Recommendation
- Require the `autoApprove`/`trusted` transition to be tied to a freshly-generated, single-use approval token created at the moment the user consents in the UI, rather than an unrestricted setter callable at any time.
- Snapshot the connection's authorization state at `connect()` time and require an explicit re-approval flow (not a bare `setAutoApprove`/`add` call) to change it later.
- Add rate-limiting/logging around `setAutoApprove` and `trusted` mutations so that any change to an existing origin's authorization posture is auditable and requires the same UX friction as first-time approval.

### Proof of Concept
Not applicable — this analysis is based on static code review of the `ConnectedOrigins` module's mutable trust/auto-approve state; a working end-to-end PoC would require confirming the exact background/UI call site that invokes `setAutoApprove`/`add` in response to dApp `connect()`/`enable()` requests, which was not fully observable in the indexed portion of the repository. A Devin session with full repository access would be needed to trace the RPC bridge handler that wires web3 provider `connect()` calls to `connectedOrigins.add`/`setAutoApprove` and confirm whether an untrusted origin can trigger these mutations without a fresh user gesture.

    const isTrusted = await this.isTrusted({ origin })
