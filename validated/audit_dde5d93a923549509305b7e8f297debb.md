### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` attribute that identifies which merchant/tenant the webhook belongs to is read from an HTTP header that is never covered by the signature. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then unconditionally trusts the header-derived `shop` value when building the `WebhookMetadata` handed to the app's handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0)  while `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` [3](#0-2) , so the header-carried `shop` is never part of the signed material. `Registry.process` validates the HMAC and then directly forwards `request.shop` into `WebhookMetadata` passed to the app's handler without any additional binding check [4](#0-3) .

The identity binding that should hold is: `shop authenticated by HMAC == shop used by the handler as the tenant key`. Because the header is outside the signed bytes, this equality is not enforced by the library. Since a single app has one shared `api_secret_key` used for every merchant's webhooks, a valid `(raw_body, hmac)` pair generated for one shop (e.g., the attacker's own store, which they legitimately control and can receive real webhooks from) remains a **valid HMAC** if replayed with the `shop-domain` header changed to a different (victim) shop. The documentation itself confirms `data.shop` is treated as "The shop domain of the webhook" and is passed straight through to app logic (e.g., `perform_later(shop_domain: data.shop, ...)`) as the tenant key [5](#0-4) .

### Impact Explanation
This breaks the tenant/shop identity binding for any app relying on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` to determine which merchant a webhook belongs to (the documented, intended usage). An attacker who controls a store with the app installed can capture one of their own legitimately-signed webhook deliveries (valid body + HMAC pair, produced with the app's shared secret) and replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. Since the HMAC never covers the header, validation still passes, and the app's handler will process/store data under the victim's tenant identity — cross-tenant data confusion/injection.

### Likelihood Explanation
Requires the attacker to run their own store with the target app installed (a normal merchant, not a privileged account) to obtain at least one legitimately-signed webhook body/HMAC pair, and requires the app's webhook endpoint to be reachable over the internet with no additional per-request authentication beyond this gem's `HmacValidator` — both are the standard, documented deployment pattern for this gem.

### Recommendation
Bind the shop identity into the verified material: either include the shop-domain header in the HMAC-signable string construction, or require callers of `Registry.process`/`Request.new` to independently corroborate `shop` against a previously known/authorized shop for that webhook subscription (e.g., cross-check against the `shop` associated with the `webhook_id` at registration time) before dispatching to the handler.

### Proof of Concept
1. App has shop `attacker.myshopify.com` install and receives a genuine webhook: `raw_body = '{"id":1}'`, headers include `x-shopify-hmac-sha256: <valid-for-body>`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker records this exact `(raw_body, hmac)` pair.
3. Attacker POSTs the same `raw_body` and `hmac` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Utils::HmacValidator.validate(request)` succeeds because it only checks the body-derived HMAC [3](#0-2) .
5. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop == "victim.myshopify.com"` [6](#0-5) , causing the app to process attacker-controlled data under the victim shop's tenant identity.
