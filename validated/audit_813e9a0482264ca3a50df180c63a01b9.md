## Analysis

The externally-reported LiFi issue (ambiguous calldata decoding to bypass `LiFiValidator`) doesn't exist verbatim in this repo — there is no `LiFiValidator`/`extractMainParameters` logic here at all. However, the same root-cause pattern — **trusting attacker-supplied LI.FI/router calldata without validating what it actually moves, and letting that movement escape the balance equation** — reproduces as a concrete bug in `LifiExternalAction`/`ExternalActionSwap`.

### Title
Unbounded token pull via unlimited LI.FI router approval lets externalActionMetadata drain/mint value outside the balance equation - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap()` computes `inputAmount` from the zk-circuit-committed `deltaAmounts[0]`, but never enforces that the router calldata (`externalActionMetadata`, fully attacker/prover-controlled) actually consumes only that amount. `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` — a permanent `type(uint256).max` approval that is never scoped to, or reset per, the declared `inputAmount` — and then blindly forwards the raw calldata to the router.

### Finding Description
`Hinkal._externalTransact` transfers exactly `uint256(-deltaAmountChanges[i])` (the circuit-committed `inputAmount`) into the shared `LifiExternalAction` contract before invoking `runAction` [1](#0-0) . `ExternalActionSwap.swap()` then calls `callRouter` with that `inputAmount`, but the value is only used to compute `swappedAmount` via output-token balance diff — it is never checked against what the router calldata actually pulls [2](#0-1) .

`LifiExternalAction.callRouter` grants the LI.FI router a **permanent, unbounded** allowance via `approveUnlimited`, then forwards the raw, attacker-supplied `externalActionMetadata` bytes directly to `router.call(...)`, with no check that the encoded `LibSwap.SwapData.fromAmount` (or any bridge/receiver parameter inside it) matches `inputAmount` [3](#0-2) . `approveUnlimited` sets allowance to `type(uint256).max` and is idempotent/persistent across calls — it is never reduced back to `inputAmount` after use [4](#0-3) .

Because this action contract is a shared singleton (not spun up per-transaction) and `swap()` never sweeps or verifies leftover `inputToken` balance, any residual `inputToken` dust from prior transactions — left behind because a router call consumed less than the transferred-in `inputAmount` — is measurable and reachable by any later caller. Since the router already holds unlimited allowance, an attacker can commit a tiny `inputAmount` in the zk circuit (satisfying `Hinkal._internalTransact`'s balance equation, `contracts/Hinkal.sol:134-146`) while crafting `externalActionMetadata` whose internal LI.FI `SwapData.fromAmount` is set far higher, pulling the contract's actual (larger) `inputToken` balance through the pre-existing unlimited approval. The resulting `swappedAmount`, derived purely from the output-token balance diff, is credited to the attacker's own new UTXO — value that was never accounted for by `circomData.amountChanges`/`balanceDif` in the equality Hinkal enforces at `contracts/Hinkal.sol:134-146`.

### Impact Explanation
This breaks the core Hinkal invariant that shielded value created must equal on-chain value actually contributed by the depositor (`balanceDif == amountChanges + utxoAmount`). An attacker can mint a shielded UTXO backed by tokens that were never debited from them, funded instead by dust/other funds sitting in the shared `LifiExternalAction` contract — a form of unbacked minting/theft of protocol or other users' residual funds. This meets the Critical bar ("minting shielded value without backing").

### Likelihood Explanation
Requires only an unprivileged EOA capable of submitting a valid proof/deposit through the normal external-action swap path with attacker-chosen `externalActionMetadata`; no admin/relay/owner privilege needed. The main precondition is the existence of exploitable residual `inputToken` balance/allowance headroom in the shared action contract, which naturally accumulates over time given `approveUnlimited`'s unbounded, unreset allowance and lack of any post-swap reconciliation or sweep of unspent `inputToken`.

### Recommendation
- Scope the router approval to exactly `inputAmount` per call (`approveERC20Token`) instead of `approveUnlimited`, and reset it to zero after the call.
- After `callRouter` returns, verify the actual `inputToken` balance decrease equals `inputAmount` (not just check `outputToken` balance increase), so any router calldata that moves more or less than the committed amount reverts.
- Alternatively, decode/validate the router calldata's swap-input parameters against `inputToken`/`inputAmount` before forwarding, rather than trusting the raw bytes blindly.

### Proof of Concept
1. Legitimate deposit/swap tx A: `inputAmount = 1000` DAI transferred into `LifiExternalAction`; the crafted LI.FI `SwapData.fromAmount` inside `externalActionMetadata` is only `900` DAI (still valid, still succeeds) — leaving `100` DAI dust in the contract, and (via `approveUnlimited`) the LI.FI diamond retains unlimited DAI allowance on this contract going forward.
2. Attacker submits deposit tx B with a valid zk proof committing `inputAmount = 1` DAI (satisfying `contracts/Hinkal.sol:134-146`), transferring `1` DAI into `LifiExternalAction`.
3. Attacker's `externalActionMetadata` encodes `SwapData.fromAmount = 101` DAI (covering the `1` DAI just sent plus the `100` DAI dust from step 1), relying on the pre-existing unlimited allowance from step 1.
4. `callRouter` succeeds, pulling `101` DAI total; `swappedAmount` (output-token balance diff) reflects the full `101` DAI swap.
5. Attacker's new UTXO is credited with output corresponding to `101` DAI swapped, while the circuit/balance equation only accounted for `1` DAI — the extra `100` DAI value is minted into the attacker's shielded balance without backing.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
