### Title
Front-runnable escrow accounting for tokens with no deployed code allows theft of genuine users' escrowed funds - (File: evm/src/apps/IntentGatewayV2.sol, evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2.placeOrder` (and its Tron/base equivalents) uses `IERC20(token).safeTransferFrom(...)` to pull input tokens from the caller and then unconditionally credits an internal escrow ledger, `_orders[commitment][token] = reducedInputs[i].amount`, based purely on the requested amount rather than on a verified balance delta relative to what was actually received when the token has no code. The escrow ledger is per-commitment, but the actual ERC20 balance backing all commitments for a given token address is a single shared pool held by the contract. This mirrors the Royco `RecipeOrderbook` bug: a call to `safeTransferFrom` on an address with no contract code trivially "succeeds" (an external call to an EOA/empty address returns success with empty returndata, which OpenZeppelin's `SafeERC20`/`Address.functionCall` treats as a successful transfer), letting an attacker register a fake, fully-escrowed order for a token that has not yet been deployed at a predetermined (e.g., CREATE2) address.

### Finding Description
In `IntentGatewayV2.placeOrder`, when no predispatch call is present, each input token is pulled directly: [1](#0-0) 
and then credited to the commitment's escrow bucket: [2](#0-1) 

If `token` is an address that has no contract code yet (e.g., a CREATE2 address the attacker has pre-computed for a token that will be deployed later, exactly as in the Royco PoC), `safeTransferFrom` will not revert — a low-level call to an address without code returns `success = true` with empty return data, which `SafeERC20`'s optional-return handling accepts as success — even though no tokens actually moved. The contract nonetheless records a legitimate-looking escrow entry `_orders[commitment][token] = amount` for the attacker's order, without ever having received real tokens.

Later, once the real token contract is deployed at that same address and a genuine user places a real order for the same token, `IERC20(token).safeTransferFrom` actually moves real tokens into the gateway, increasing the gateway's on-chain ERC20 balance of that token. This balance is a single pool shared across all commitments, per `_withdraw` in `IntentsBase.sol`, which releases tokens purely from the accounting ledger and the token's global balance, with no cross-check that the releasing commitment's tokens were ever really deposited: [3](#0-2) 

The attacker can then trigger release of their bogus escrow entry (e.g., via same-chain fill/cancel flows in `IntrinsicIntents`/`ExtrinsicIntents`, which call `_withdraw`), causing the gateway to transfer real tokens — funded by the genuine user's deposit — out to the attacker, draining the shared pool. This is the same root cause identified in the Royco report: `SafeTransferLib`/`SafeERC20`-style "safe" transfer helpers succeed silently against code-less addresses, and no check ensures the token actually exists (has code) before crediting escrow.

### Impact Explanation
This allows outright theft of any ERC20 token funds escrowed by other users in `IntentGatewayV2`/`IntentsBase`, once an attacker can predict a future token deployment address (trivial with CREATE2 factories, which are extremely common for stablecoins, LSTs, and wrapped assets). The attacker can create and hold a phantom, fully-"escrowed" order for arbitrary large amounts before the token exists, then drain real deposits made by other users for that token after deployment — a direct, permanent loss of user funds from the intents escrow, satisfying the "concrete theft of funds" bar.

### Likelihood Explanation
Exploitation requires the attacker to know or front-run a deterministic (CREATE2/CREATE) token deployment address before real liquidity for that token is escrowed in the gateway — a realistic and previously demonstrated technique (as in the referenced Royco PoC), requiring no privileged access, only a single `placeOrder` transaction from an ordinary, unprivileged user followed by a normal fill/cancel call once real funds are deposited for the same token address.

### Recommendation
Before crediting `_orders[commitment][token]` (or any escrow ledger) based on the outcome of `safeTransferFrom`, verify that `token` has deployed code (`token.code.length > 0`) — or better, verify the actual received amount via before/after balance deltas restricted to require `balanceAfter > balanceBefore` when a nonzero amount was requested, and revert if the token address has no code, mirroring the Royco fix of adding an explicit code-existence check before pulling funds from the user.

### Proof of Concept
Following the same structure as the Royco PoC referenced in the report:
1. Attacker computes the CREATE2 address of a not-yet-deployed ERC20 token.
2. Attacker calls `IntentGatewayV2.placeOrder` with that token as an input asset and a large `amount`; `safeTransferFrom` silently "succeeds" against the code-less address (see `evm/src/apps/IntentGatewayV2.sol#L312-323`), and `_orders[commitment][token]` is credited with the full amount without any tokens actually being transferred (`evm/src/apps/IntentGatewayV2.sol#L363-373`).
3. The token is deployed later at that exact address.
4. A genuine user places a real order for the same token, transferring real tokens into the gateway via the same `placeOrder` path, increasing the gateway's actual on-chain balance of that token.
5. The attacker triggers a fill/cancel path that calls `_withdraw` for their bogus commitment (`evm/src/apps/intentsv2/IntentsBase.sol#L451-470`); since `_withdraw` only checks the internal ledger and transfers from the shared pool, it sends real tokens (funded by the genuine user) to the attacker, draining the pool.
