Based on my investigation, I found a valid analog of the reported bug class in Hyperbridge's Tron-specific IntentGatewayV2 contract.

### Title
Unsafe transfer of arbitrary ERC20 token in escrow withdrawal allows silent transfer failure while marking orders filled - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The `withdraw()` internal function and the `SweepDust` branch of `onAccept()` in the Tron variant of `IntentGatewayV2` move escrowed ERC20 tokens to beneficiaries using a raw low-level `.call()` with the `IERC20.transfer.selector`, checking only whether the external call itself did not revert (`success`), rather than decoding and validating the ERC20 return value.

### Finding Description
In `withdraw()`, escrowed tokens are released via: [1](#0-0) 

and transaction fees are released the same way: [2](#0-1) 

The `SweepDust` handler in `onAccept()` does the same thing for dust sweeps: [3](#0-2) 

`success` here only reflects whether the low-level call reverted, not whether the token contract's `transfer()` returned `true`. Any ERC20 token whose `transfer()` returns `false` on failure instead of reverting (a legal ERC20 pattern — e.g., paused, blacklisted-recipient, or otherwise non-compliant tokens) will make this check pass even though no tokens were actually moved. Despite this, `withdraw()` unconditionally decrements the escrow accounting and marks the order filled before/around the transfer: [4](#0-3) 

The contract imports and declares `using SafeERC20 for IERC20;`, and correctly uses `safeTransferFrom`/`safeTransfer` elsewhere in the file (e.g. lines 405, 459), but `withdraw()` and the `SweepDust` branch bypass `SafeERC20` and use the raw low-level call pattern instead: [5](#0-4) 

This is the exact same bug class as the referenced Footium report: state (escrow balance, `_filled` mapping) is updated as if the transfer succeeded, while the beneficiary may receive nothing.

This contrasts with the canonical EVM `IntentsBase.sol` withdrawal path, which correctly uses `safeTransfer`: [6](#0-5) 

### Impact Explanation
Any user who creates a same-chain or cross-chain intent order (`newOrder`/`fillOrder` flow) using an arbitrary ERC20 as the input token can end up in a scenario where, on redemption (`RedeemEscrow`)/refund (`RefundEscrow`) delivered via `onAccept`, or resolution via `onGetResponse`, the token transfer to the beneficiary silently fails. Because `_filled[body.commitment]` is set and `_orders[...][token]` is decremented regardless of whether tokens actually moved, the beneficiary permanently loses access to their escrowed funds — the order is marked filled/refunded and cannot be retried or reclaimed. This is a direct, permanent loss-of-funds vulnerability reachable by any unprivileged relayer/user who has escrowed funds using a non-standard-compliant ERC20.

### Likelihood Explanation
Reachability requires only that the input/fee token used for an intent order behaves like a non-reverting ERC20 (returns `false` instead of reverting on failure) — a well-documented category of real-world tokens (e.g., some legacy/compliance tokens, tokens with pausable/blacklist logic). Since `IntentGatewayV2` on Tron accepts arbitrary ERC20 tokens for orders (no token allow-list is evident in the escrow/withdraw logic), and delivery of `RedeemEscrow`/`RefundEscrow`/`SweepDust` messages happens through the normal ISMP `onAccept` dispatch path reachable by relayers, likelihood is realistic whenever such a token is used, not merely theoretical.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the per-token loop and the transaction-fee release) and in the `SweepDust` branch of `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (and consistent with the non-Tron `IntentsBase.sol`). This ensures a `false` return value causes a revert instead of being silently accepted, preventing escrow state from being finalized against an unsuccessful transfer.

### Proof of Concept
1. User creates an intent order on the Tron `IntentGatewayV2` using a token `T` that implements ERC20 but returns `false` (instead of reverting) when a transfer fails (e.g., recipient is blacklisted, or contract enters a paused state after order creation but before settlement).
2. Order is filled/escrowed; `_orders[commitment][T]` records the escrowed amount as in `escrow`/`fillOrder` logic (as seen for the corresponding non-Tron variant in `evm/src/apps/IntentGatewayV2.sol` and `IntentsBase.sol`).
3. A relayer delivers a `RedeemEscrow` (or `RefundEscrow`) message through the ISMP host, invoking `onAccept` → `withdraw(body, ...)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed against `T`; `T.transfer` returns `false` (e.g. beneficiary now blacklisted) but the call itself does not revert, so `success == true`.
5. `withdraw()` proceeds to decrement `_orders[commitment][token]` and set `_filled[commitment] = beneficiary`, emitting `EscrowReleased`/`EscrowRefunded` — even though the beneficiary received zero tokens.
6. The beneficiary has no path to reclaim the escrowed `T` tokens: the order is already marked filled/refunded and the escrow balance is already zeroed out, resulting in a permanent loss of the escrowed funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
