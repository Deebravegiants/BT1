### Title
`Webhooks::Request` HMAC signature does not bind the `shop-domain`/`topic` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` and `topic` — the values that `Webhooks::Registry.process` uses to route and attribute the webhook to a tenant — are read straight from unauthenticated HTTP headers. Since Shopify's webhook secret (`api_secret_key`) is shared by the app across every shop that installs it, any shop owner who has installed the app can capture one of their own genuinely-signed webhooks and re-send it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header pointing at a different (victim) shop. `HmacValidator.validate` will still accept it because the HMAC only covers the body bytes.

### Finding Description
The identity binding that should hold is:

`shop authenticated by HMAC == shop the handler acts on`

but in this code that equality is never enforced.

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is only the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` — the fields that determine which tenant/handler the event is dispatched to — come from headers that are not part of the signed data at all: [3](#0-2) 

`Registry.process` trusts these header-derived values directly after only checking the HMAC of the body: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is identical for every shop that has the app installed, a valid `(body, hmac)` pair captured from one shop's webhook remains cryptographically valid no matter what `shop-domain`/`topic` header values accompany it when replayed. Nothing in the signable string ties the signature to a specific shop or topic, so the attacker can freely substitute those header values.

### Impact Explanation
An attacker who has installed the app on their own store (an ordinary, unprivileged merchant relationship — no access token, `api_secret_key`, or victim credentials required) can capture a webhook Shopify sent for their own shop, then replay the identical body+HMAC to the app's public webhook endpoint with `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers rewritten to target another tenant. `Registry.process` will pass this forged shop/topic straight to the registered `WebhookHandler`, so the handler executes as if the event genuinely originated from the victim shop. Depending on what the handler does (updating per-shop state, provisioning, billing, redact/GDPR compliance flows, etc.), this results in cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not own — a cross-tenant boundary violation.

### Likelihood Explanation
The attacker only needs to be a legitimate installer of the app on any shop (a normal, unprivileged relationship for public apps) and the ability to send arbitrary HTTP requests to the app's public webhook URL — both trivially available to an internet user. No secret keys, tokens, or insider access are required, only the ability to capture one webhook delivery for their own shop and replay it with modified headers.

### Recommendation
Include the authenticating identity fields (at minimum `shop-domain` and `topic`, ideally also `webhook-id`) in the HMAC-signed input, or otherwise cryptographically bind them to the raw body before trusting them in `Registry.process`. If Shopify's own webhook signing scheme genuinely only signs the body, the library should document that host applications must independently verify the shop by looking up the destination via the stored session (not trust the header directly) rather than treating `Request#shop`/`#topic` as authenticated after only checking `HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app: body `B`, headers `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
3. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or the topic).
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `@raw_body` (`to_signable_string`), which is unchanged.
5. `ShopifyAPI::Webhooks::Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"`, `topic: <attacker-chosen>`, and the attacker-controlled body — the handler executes believing the event is authentic data from the victim shop.
