### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking that the HMAC covers the raw request body, but the `shop` value that identifies *which tenant* the webhook belongs to is taken from an unauthenticated HTTP header and passed straight into the handler. Any actor who can obtain one validly-signed webhook body (e.g. by installing the app on their own shop) can replay that exact body to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to name a different (victim) shop, and the HMAC check will still succeed.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC only over `verifiable_query.to_signable_string`. For webhook requests, `Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

None of the Shopify headers — `shop`, `topic`, `webhook_id`, `api_version` — participate in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (derived from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identity for the delivered data, forwarding it unchanged to the app's handler: [3](#0-2) 

The equality that should hold is: *shop bound by the HMAC == shop used to route/attribute the webhook payload*. Because the signature only covers the body, this equality does not hold — `hmac_valid(body, secret) == true` says nothing about the value of the `shop-domain` header. Consequently, `shop` can be set to any value by the request sender as long as the accompanying body was previously and legitimately signed for *some* shop (which an attacker can obtain by simply installing the app on their own store and capturing one of their own genuine webhook deliveries).

Before the attacker's request: `HMAC` validates `(body_A, shop_A)` where `shop_A` is the attacker's own shop.
After the attacker's request: the same `body_A` is replayed with header `shop = shop_victim`; `Utils::HmacValidator.validate` still returns `true` because it only recomputes the HMAC over `body_A`, and `Registry.process` hands `WebhookMetadata.new(... shop: "shop_victim" ...)` to the host application's handler as if it were authentic data belonging to `shop_victim`.

### Impact Explanation
This breaks the tenant boundary the library is expected to enforce for webhook consumers: application code built on top of `ShopifyAPI::Webhooks::Registry.process` reasonably assumes that a webhook whose HMAC validated is both (a) genuinely from Shopify/the app's secret and (b) genuinely about the shop named in the `shop` field, since this is the only "verified" identity information the library exposes to the handler. An attacker with nothing more than their own unprivileged install of the app can forge attribution of arbitrary webhook payload data (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`) to any other shop domain string, causing the host application to process/store data under, or trigger tenant-scoped side effects for, a shop the attacker does not control — a cross-tenant integrity/confusion issue.

### Likelihood Explanation
Likelihood is meaningful but bounded: exploitation requires only (1) installing the target app on an attacker-controlled shop to obtain at least one legitimately HMAC-signed webhook body, and (2) sending that captured body to the app's public webhook endpoint with a forged `shop-domain` header, both of which are unprivileged, internet-reachable actions with no need for the `api_secret_key`, an access token, or any victim credential. The blast radius is limited to whatever information is encoded in the (attacker-controlled) webhook body itself, since the body cannot be arbitrarily rewritten — but the shop attribution of that body is fully attacker-controlled.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body before `Registry.process` trusts them. At minimum, document that `WebhookMetadata#shop` is not covered by the HMAC and must not be treated as an authenticated tenant identifier by consuming applications, or have the library reject processing when a previously-seen `(body, hmac)` pair is replayed with a different `shop` header (e.g. by mixing the shop into the HMAC computation the way `Auth::Oauth::AuthQuery#to_signable_string` mixes `shop` into its OAuth callback HMAC).

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key", api_secret_key: "secret", host: "example.com",
  scope: "read_products", is_embedded: false, api_version: "2024-01",
)

body = '{"id":1,"note":"attacker-controlled order payload"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", body)
) # attacker legitimately obtains this HMAC from a webhook delivered to their OWN shop

# Attacker now sends the SAME body/hmac to the app's webhook endpoint,
# but forges the shop header to point at a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes; handler receives WebhookMetadata with
#    shop: "victim-shop.myshopify.com", even though the body/hmac pair
#    was only ever legitimately signed in the context of the attacker's shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
