### Title
Missing domain separation between relayer fee-withdrawal and beneficiary-redirect signatures allows an unauthorized third party to force a full-balance fee withdrawal - ([File: modules/pallets/relayer/src/accumulate.rs] / [File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`pallet-ismp-relayer` lets a relayer authorize where their earned fees should be paid out via a signed message. Two independent, unsigned extrinsics — `accumulate` (redirect the beneficiary of a freshly-proven fee batch) and `withdraw_fees` (withdraw the relayer's entire accumulated `Fees` balance) — verify signatures over byte-identical payloads and share the same `Nonce` counter. Because the signed message carries no action-type/domain tag, a signature the relayer produced for one action is valid for the other, and any observer of a pending extrinsic can resubmit it against the other call before it lands.

### Finding Description
The beneficiary-redirect signature is built in `beneficiary_message`: [1](#0-0) 

and verified/consumed inside `accumulate`: [2](#0-1) 

The fee-withdrawal signature is built in `message`: [3](#0-2) 

Note that when a beneficiary is supplied, `if let Some(beneficiary) = beneficiary` **unwraps** the `Option`, so the hashed tuple is `(nonce, dest_chain, beneficiary: Vec<u8>)` — exactly the same SCALE-encoded shape (and thus the same `keccak_256` digest) as `beneficiary_message(nonce, state_machine, beneficiary)` when `dest_chain == state_machine`. Both functions read/increment the *same* `Nonce::<T>` storage item keyed by `(address, chain)`: [4](#0-3) [5](#0-4) 

There is no domain separator (e.g. a discriminant byte identifying "accumulate-redirect" vs "withdraw") in either message, and no scoping of the withdrawal to the amount the relayer intended to move. `withdraw` in `withdrawal.rs` always pulls the relayer's *entire* `Fees::<T>` balance for that chain: [6](#0-5) 

Both `accumulate` and `withdraw_fees` are unsigned extrinsics (per the module doc: "this extrinsic is unsigned"), so a pending call sits in the public transaction pool before inclusion, exposing the `(nonce, signature, beneficiary)` tuple to anyone.

### Impact Explanation
A relayer who signs a small, narrowly-scoped beneficiary redirect for `accumulate` (e.g., to route a single newly-proven batch's fee to a specific address `B`) unintentionally produces a signature that is also valid input to `withdraw_fees`. Any third party who observes the pending `accumulate` call can front-run it with `withdraw_fees` using the identical signature/nonce/beneficiary. Since `withdraw_fees` sweeps the *entire* `Fees::<T>` balance (not just the batch amount the relayer intended to redirect) and consumes the shared nonce, this: (1) forces an unauthorized, out-of-scope withdrawal of the relayer's full accrued balance through a code path the relayer never called, and (2) invalidates the relayer's own pending `accumulate` transaction (nonce now stale), causing loss of the newly-claimed batch's fee credit/state (it must be re-proven). This is an unauthorized app action triggered by an unprivileged third party exploiting a signature meant for a narrower purpose — the same bug class as the CVE's mishandled address-change flow, where an identity/destination-changing action was executed with insufficient binding to its intended scope.

### Likelihood Explanation
Medium. It requires: (a) a relayer to use the optional beneficiary-redirect feature of `accumulate` (a supported, documented flow), and (b) an observer capable of seeing pending unsigned extrinsics and racing inclusion — both realistic for public chains with open transaction pools/mempools. No special privilege is needed by the attacker; only timing.

### Recommendation
Bind each signed payload to the specific extrinsic/action it authorizes by including a domain separator (e.g., a fixed discriminant byte or a distinct prefix string such as `b"RELAYER_ACCUMULATE_REDIRECT"` vs `b"RELAYER_WITHDRAW"`) inside both `beneficiary_message` (`modules/pallets/relayer/src/accumulate.rs`) and `message` (`modules/pallets/relayer/src/withdrawal.rs`) before hashing. Additionally, consider using separate `Nonce` namespaces per action type so a signature/nonce consumed by one flow cannot be replayed against the other, and scope `withdraw_fees` to an amount bound in the signed message rather than always sweeping the full `Fees::<T>` balance.

### Proof of Concept
1. Relayer `R` accrues `Fees::<T>::get(dest_chain, R) = 10_000` over time via normal `accumulate` calls (no redirect).
2. `R` proves a new small batch (fee = 50) and wants to redirect just this batch to address `B`. `R` computes `nonce = Nonce::<T>::get(R, dest_chain)` (say 5), signs `beneficiary_message(5, dest_chain, B)`, and submits `accumulate(withdrawal_proof)` with `beneficiary_details = Some((B, sig))`.
3. Before this extrinsic is included, an observer copies `(sig, dest_chain, B)` from the transaction pool and submits `withdraw_fees` with `WithdrawalInputData { signature: sig, dest_chain, beneficiary: Some(B) }`.
4. `withdrawal.rs::message(5, dest_chain, Some(B))` unwraps to `keccak_256((5, dest_chain, B).encode())`, identical to the digest `R` signed; `signature.verify` succeeds since the digest matches bit-for-bit.
5. `Pallet::withdraw` reads `Fees::<T>::get(dest_chain, R) = 10_000` (not 50), increments `Nonce::<T>::get(R, dest_chain)` to 6, dispatches a cross-chain withdrawal of the full 10,000 to `B`, and zeroes `Fees::<T>`.
6. `R`'s original `accumulate` call, still carrying `nonce = 5`, now fails signature/nonce verification and reverts — the 50-fee batch credit is lost, and the full balance has already been swept out through a code path `R` never invoked, entirely at the timing discretion of an unrelated third party.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
