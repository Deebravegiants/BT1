### Title
Webhook HMAC Does Not Cover `shop`, `topic`, or `webhook_id` — Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` (used by `Webhooks::Registry.process`) only verifies that the HMAC matches the body bytes — it never verifies that the `shop-domain`/`topic`/`webhook-id` headers are the ones Shopify actually signed. This breaks the identity binding: `hmac(body) == hmac(body)` is checked, but `shop_header == shop_that_was_actually_notified` is never checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic protection: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` field extracted from the `hmac-sha256` header: [3](#0-2) 

`Registry.process` trusts `request.shop` and `request.topic` for routing and for constructing `WebhookMetadata` handed to the app's handler, based solely on this body-only HMAC check: [4](#0-3) 

Because the signature never binds to the `shop-domain` (or `topic`/`webhook-id`) header, any request bearing a body/HMAC pair that was genuinely signed by Shopify for one delivery can be replayed with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header rewritten to a different value, and it will still pass `HmacValidator.validate`. An attacker who operates their own Shopify store with the target app installed can capture a legitimately-signed webhook body (many webhook topics — e.g. GDPR/compliance webhooks or any topic whose body content the attacker controls or can predict) and resend it to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim merchant. The app's handler receives `WebhookMetadata` claiming the event belongs to the victim shop even though it never occurred there.

### Impact Explanation
This breaks the tenant-identity binding (`shop_header == shop_actually_notified_by_Shopify`) with only a valid-looking body+HMAC pair as the prerequisite — something any merchant with the app installed can obtain from their own store's genuine webhook traffic. Depending on what the host app's webhook handler does with `data.shop` (e.g., updating billing/subscription state, disabling/enabling features, writing audit records, or triggering data actions "on behalf of" that shop), this allows cross-tenant confusion/actions attributed to a shop that never triggered the event — a cross-tenant impact.

### Likelihood Explanation
Requires the attacker to be a legitimate (even trial) merchant of the target app so they can generate a validly-HMAC'd webhook body, then replay it against the endpoint with a forged shop-domain/topic header. No access to `api_secret_key` or the victim's credentials is needed, only observation of one's own webhook deliveries plus the ability to POST to the public webhook endpoint. This is a realistic unprivileged-internet-user path within the library's documented contract of `Registry.process`.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically/independently validate them:
- Require the app (or the gem) to confirm that the `shop` in `WebhookMetadata` matches a shop the app has an active, previously-established session/installation with the correlated `webhook_id`, rather than trusting the header value on the strength of a body-only HMAC.
- At minimum, document/enforce that host applications must cross-check `request.shop` against their own installed-shop registry before acting on webhook data, since the HMAC in this gem does not bind headers.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker-shop.myshopify.com`) and triggers a webhook whose body is attacker-controlled or predictable (e.g., an empty-body compliance webhook, `{}`), receiving a validly Shopify-signed `x-shopify-hmac-sha256` for that exact body.
2. Attacker replays the same raw body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and, if desired, a different `x-shopify-topic`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the HMAC.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this event for that shop.
