## Title
Missing `return` after failed email-claim extraction lets OIDC login succeed and create an authenticated session with an empty/attacker-influenced email - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go`), the `email, ok := claims["email"].(string)` failure branch writes an error response via `c.String(...)` but does not `return`, unlike every other error branch in the same function [1](#0-0) . Because `c.String` does not abort the gin handler, execution falls through to role mapping, session-row insertion, and cookie issuance, resulting in a fully authenticated session being created with `user_email` set to an empty string when the email claim assertion fails.

## Finding Description
Every prior failure path in `handleTokenExchange` — `ShouldBindJSON`, state mismatch, `Exchange`, `id_token` extraction, `Verify`, `idToken.Claims`, `ExtractIDClaimValues`, and role mapping — writes an error response and explicitly `return`s [2](#0-1) . The email-claim check breaks this pattern: it logs and writes `c.String(http.StatusInternalServerError, "Failed to get email from claims")` with no `return` [1](#0-0) . Execution then proceeds to `IDClaimsToUserRole`, inserts a new row into `oidc_sessions` with `strings.ToLower(email)` (empty string when the assertion fails) and the derived role, sets `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, saves the session, and returns `200 OK` with `{"success": true}` [3](#0-2) . `AuthorizedUserWithSession` subsequently trusts this DB row (`user_email`, `user_role`) without re-validating the email content [4](#0-3) , so a session created via this fall-through path is fully usable for authenticated, role-scoped API access.

## Impact Explanation
This breaks the security invariant that a failed identity-attribute extraction should abort authentication; instead, the handler completes login and issues a valid, role-bearing session cookie tied to a session record with a corrupted/empty `user_email`. This falls into the node API authentication/session-integrity impact class: an authenticated session is minted despite failure of an identity check, undermining audit traceability (`audit.AuthLoginSuccessNo2FA` records `email: ""`) and creating potential cross-session collisions on empty-email session bookkeeping.

## Likelihood Explanation
The path is reached during the standard, code-defined `/oidc-login` → `/exchange` flow once a client has a validly-signed ID token whose claims lack a well-formed string `email` field. Triggering this does not require operator/admin access to the node — only completion of the normal OIDC exchange with claims content that omits/mistypes `email` (a real-world IdP configuration variance), so it is reachable within the intended login flow of the code under audit.

## Recommendation
Add the missing `return` immediately after the `c.String(...)` call in the email-claim check, matching the pattern of every other error branch in `handleTokenExchange`, so a failed email extraction aborts the handler before role mapping and session creation occur. Additionally consider adding a `return` after the `oidc_sessions` insert error branch (lines 257-260) for the same reason, since it currently also falls through to session cookie issuance on a DB write failure.

## Proof of Concept
1. Configure the node with `OIDCAuth` against a test/mock OIDC provider.
2. Have the provider return a validly-signed ID token whose claims map omits the `email` key (or supplies a non-string value) while including group claims that map to a valid RBAC role.
3. Drive the standard `/oidc-login` redirect and POST the resulting `code`/`state` to the exchange endpoint handled by `handleTokenExchange`.
4. Observe that despite the internal-server-error write at line 229, execution continues: a row is inserted into `oidc_sessions` with `user_email = ''`, `ginSession.Save()` succeeds, and the client receives `200 OK` `{"success":true}` with a valid, authenticated session cookie usable per the derived role — confirmable via a Go handler-level test asserting a session row and non-error final response despite the failed `ok` assertion.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
