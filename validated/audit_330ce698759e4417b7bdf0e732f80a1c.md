### Title
Zero-share deposit when vault is fully utilized causes silent loss of depositor principal - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
The Zest vault contracts compute shares-to-mint on deposit via `convert-to-shares-preview`, which returns `u0` whenever `total-assets-preview` is zero even though `total-supply-preview` is non-zero. The `deposit` function accepts the user's underlying tokens and increments the vault's `assets` variable unconditionally, but never asserts that the computed share amount (`inkind`) is greater than zero — unlike `redeem`, which explicitly requires `(> inkind u0) ERR-OUTPUT-ZERO`. This asymmetry lets a depositor's real underlying tokens be absorbed into the vault while they receive zero `zft` shares, permanently transferring their principal to existing shareholders.

### Finding Description
`convert-to-shares-preview` is defined identically across all vaults, e.g.: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

`total-assets-preview` is the vault's liquid reserve (`assets` var) plus any not-yet-realized interest above `total-borrowed`: [2](#0-1) 

Because `assets` is decremented on borrow and `total-debt` equals `total-borrowed` immediately after a borrow (before any interest accrual), `ta` becomes exactly `u0` any time the vault is at 100% utilization right after a borrow, while `total-supply` (`ts`) remains non-zero.

`deposit` then uses this `inkind` value without a nonzero check: [3](#0-2) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
  ...
  (inkind (convert-to-shares-preview amount)))
  (asserts! (not (get deposit states)) ERR-PAUSED)
  ...
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  ...
  (try! (receive-underlying amount account))
  (try! (ft-mint? zft inkind recipient))
  (var-set assets (+ current-assets amount))
  ...)
```

With `min-out` at the default `0`, `(>= inkind min-out)` trivially passes even when `inkind` is `0`. `receive-underlying` still pulls the full `amount` of real tokens from the depositor, `ft-mint? zft 0 recipient` mints nothing, and `assets` is increased by the full deposited amount. This breaks the share-minting-vs-backing identity: `Δassets(backing) = amount > 0` while `Δshares = 0`, so the depositor's principal is absorbed into the pool's backing and silently redistributed to existing `zft` holders (their redemption value rises with no dilution). Compare this to `redeem`, which correctly guards the symmetric case: [4](#0-3) 

### Impact Explanation
This is a direct theft of a depositor's principal: real underlying tokens leave the depositor's wallet and enter the vault's backing (`assets`), but zero corresponding shares are minted, and there is no mechanism to reclaim the lost tokens. The lost value is transferred to existing shareholders in the affected vault (their share price effectively rises for free). This qualifies as Critical impact — theft of user funds at rest (deposited principal), not merely unclaimed yield.

### Likelihood Explanation
The triggering condition, `total-assets-preview == 0` while `total-supply-preview > 0`, occurs naturally at 100% utilization immediately following a borrow — a normal, expected market state for a lending protocol (not requiring any DAO/oracle/privileged action). Any unprivileged user calling `deposit` with a default/naive `min-out` of `0` at that moment loses their entire deposited amount. No flashloan, oracle manipulation, or governance compromise is required; it is a purely user-triggerable sequence: borrower drains vault to 100% utilization → victim deposits.

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in `deposit` (mirroring the existing check in `redeem`) in each vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`). More robustly, `convert-to-shares-preview` should never silently degrade a nonzero deposit to zero shares while `total-supply` is nonzero; consider reverting instead of returning `u0` in that branch.

### Proof of Concept
1. Vault starts empty. Alice deposits `1000` underlying: `ts=0` → `inkind = amount = 1000`; `ts` becomes `1000`, `assets = 1000`.
2. A borrower borrows the full `1000` available liquidity. `assets` is decremented to `0`. Immediately after, `total-debt == total-borrowed` (no interest accrued yet), so `total-assets-preview = current-assets(0) + interest(0) = 0`, while `ts = 1000`.
3. Bob calls `deposit(100, 0, bob)`. `convert-to-shares-preview` hits the `(is-eq ta u0)` branch and returns `u0`. `(asserts! (>= inkind min-out))` passes since `0 >= 0`. `receive-underlying` pulls `100` tokens from Bob; `ft-mint? zft 0 bob` mints nothing; `assets` becomes `100`.
4. Bob now holds `0` `zft` shares despite having transferred `100` real tokens into the vault. Alice's existing `1000` shares now redeem against a backing pool that is `100` tokens richer with no dilution — Bob's deposit has been permanently and silently transferred to Alice.
