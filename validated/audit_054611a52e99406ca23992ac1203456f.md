### Title
Self-referential `beneficiary_id` in `DeleteAccountAction` permanently burns the account's balance instead of refunding it - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction.beneficiary_id` is validated only for well-formedness, never for being distinct from the account being deleted. If a user (or a contract issuing a batched `DeleteAccount` action) sets `beneficiary_id` equal to the account's own `account_id`, the resulting balance-refund receipt targets an account that has just been removed from state, causing the refund to fail and the tokens to be irrecoverably burned. This is the direct nearcore analog of the reported "bad redirect" bug, where a self-referential redirect target zeroes out funds that can never be recovered.

### Finding Description
`action_delete_account` computes the account's remaining balance and unconditionally queues a system balance-refund receipt to `delete_account.beneficiary_id`, then removes the account from state in the same action execution: [5](#0-4) .

The only validation performed on `DeleteAccountAction` is that `beneficiary_id` is a syntactically valid account id — there is no check that it differs from the account being deleted: [6](#0-5) .

`Receipt::new_balance_refund` builds this outgoing receipt with `predecessor_id: "system"`, marking it as a refund receipt: [1](#0-0) .

When this receipt is later processed (in a subsequent block, since it's a normal outgoing receipt, not an instant one), `apply_action` computes `is_refund = receipt.predecessor_id().is_system() = true`, which forces `implicit_account_creation_eligible = false` even though the receipt is the sole action: [2](#0-1) .

Because the beneficiary account (== the deleted account) no longer exists, `check_account_existence` routes the `Transfer` action to `check_transfer_to_nonexisting_account`, which explicitly rejects implicit account (re)creation for refunds ("Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse"): [3](#0-2) .

The refund action therefore fails with `AccountDoesNotExist`. Back in the receipt-processing loop, any failed refund (`receipt.predecessor_id().is_system()` and `result.result.is_err()`) has its full deposit added to `stats.balance.other_burnt_amount`, permanently destroying the funds rather than returning them anywhere: [4](#0-3) .

### Impact Explanation
Any account balance transferred via a self-referential `DeleteAccountAction::beneficiary_id` is permanently and irrecoverably burned instead of being paid out, exactly mirroring the reported vault bug class where a bad "redirect to self" zeroes deposits/withdrawals with no way to recover the funds. This is a concrete token-loss bug reachable by any ordinary transaction or contract-issued promise batch (`promise_batch_action_delete_account`) without any special privilege, and it also reduces total effective supply, which is a protocol-level economic inconsistency (funds vanish rather than moving to a valid beneficiary).

### Likelihood Explanation
Trivial to trigger: a single `DeleteAccountAction` where `beneficiary_id == account_id` (either via a directly signed transaction — see `SignedTransaction::delete_account` allowing any beneficiary — or via `promise_batch_action_delete_account` from a contract) suffices. No special permissions, race conditions, or validator misbehavior are required; it is purely a missing input-validation check on an ordinary transaction/action-execution path.

### Recommendation
Add a check in `validate_delete_action` (or in `action_delete_account`) that rejects `beneficiary_id == account_id`, returning an explicit `ActionError` (e.g., a new `DeleteAccountBeneficiaryIsSelf` or similar) instead of silently generating a doomed balance-refund receipt. Alternatively, `action_delete_account` could special-case a self-beneficiary by keeping the balance in the account's `amount` field and skipping deletion, or refuse to delete outright, rather than allowing the balance to be silently burned via a downstream refund failure.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance.
2. Submit a transaction/action with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "alice.near".parse().unwrap() })` where the receipt's `receiver_id` is `alice.near` itself (self-delete, e.g. as exercised by `tx_delete_account` test helper which allows `account_id == account_id` for signer while beneficiary can independently be set to the same value): [7](#0-6) .
3. `action_delete_account` succeeds, queues `Receipt::new_balance_refund(&"alice.near", account_balance)`, and removes `alice.near` from state [8](#0-7) .
4. In a later block, the balance-refund receipt executes against a non-existent `alice.near`; `check_transfer_to_nonexisting_account` rejects implicit creation because `is_refund == true` [9](#0-8) .
5. The refund fails, and its deposit (the entire former balance of `alice.near`) is added to `other_burnt_amount`, permanently destroying it [4](#0-3) .
