### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks proves nothing about the `shop-domain`, `topic`, `api-version`, or `webhook-id` HTTP headers. `Webhooks::Registry.process` nonetheless trusts `request.shop` (parsed straight from the unauthenticated `shop-domain` header) as the tenant identifier handed to the app's webhook handler.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from other, sibling headers that are never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header value; it never touches the other headers: [3](#0-2) 

`Webhooks::Registry.process` calls this validator, and — once it passes — forwards `request.shop` (and `topic`, `webhook_id`, `api_version`) straight into `WebhookMetadata` given to the app's handler, with no separate check binding the shop header to the signed body: [4](#0-3) 

This is the same bug class as the report: a field that is *acted on* (`shop`, used as the tenant/session key by the handler) is not covered by the cryptographic integrity check (the HMAC only signs the body). Because HTTP headers are trivially attacker-controlled on any request delivered to the app's public webhook endpoint, an unprivileged internet user who can obtain one genuinely-signed webhook body/HMAC pair (e.g., by registering a webhook on their own free/dev shop and capturing the delivery, since HMAC-SHA256 secret is the app's shared `api_secret_key` and it signs the same way for every shop) can replay that exact body+HMAC to the target app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) for a different, victim shop domain. `HmacValidator.validate` still passes because it never inspected those headers, and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` as a tenant/session key — e.g., to look up the victim's stored offline access token and perform mutations, or to write data into the victim's tenant record — this allows cross-tenant data injection/confusion using only the attacker's own legitimately-obtained HMAC secret-signed body. This crosses a tenant boundary (Critical class: cross-tenant access) even though it doesn't leak the victim's own access token directly; the attack surface exists purely because the identity-binding field (`shop`) sits outside the authenticated payload.

### Likelihood Explanation
Likelihood is constrained by real-world exploitability: the webhook endpoint must be internet-reachable (true for essentially all apps, as Shopify delivers webhooks over the public internet), and the attacker needs one authentic HMAC over an attacker-controlled body — trivially obtainable by installing the target app on the attacker's own store and capturing a real webhook delivery (the same `api_secret_key` signs all shops' webhooks for a given app). No credentials belonging to the victim are required. This matches the "unprivileged internet user" threat model.

### Recommendation
Include the identity-bearing headers (`shop-domain` at minimum, ideally `topic` and `webhook-id` too) in the signed material, or otherwise cryptographically bind them to the body before trusting them. Since Shopify's own HMAC scheme signs only the raw body by design, the safer mitigation within this gem is to require host applications to cross-check `request.shop` against an out-of-band trusted list of installed shops (e.g., existing session storage) before acting on the webhook, and to document this explicitly, or to reject webhooks whose `shop-domain` doesn't match a shop that this app instance has an active session/token for.

### Proof of Concept
1. Attacker registers the target app on their own Shopify development store (or any store) and configures a webhook subscription (or triggers an event the app already listens for), then captures a real webhook delivery HTTP request, including the `X-Shopify-Hmac-Sha256` header and raw body.
2. Attacker POSTs the exact same body and `X-Shopify-Hmac-Sha256` header to the target app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — [5](#0-4)  — and this matches, since the body and secret are unchanged.
4. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own store — [6](#0-5) .

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
