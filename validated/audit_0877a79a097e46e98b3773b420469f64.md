### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing in `WebhookMetadata` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that string. The `shop` value returned by `Request#shop` comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside the signed data. `Registry.process` passes this unauthenticated `shop` value straight into `WebhookMetadata`, which is handed to the app's webhook handler as the trusted tenant identifier.

### Finding Description
The identity binding that should hold is: `shop value trusted by the handler == shop value cryptographically bound to the signed payload`. In this gem that equality is broken:

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field. [5](#0-4) 
- For webhooks, `to_signable_string` is defined as just the raw body, with no header data mixed in. [3](#0-2) 
- `Request#shop` is read from a header (`shop-domain`) that plays no role in the signature at all. [2](#0-1) 
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` when building `WebhookMetadata` for the handler, with no cross-check between the header and anything cryptographically verified. [4](#0-3) 

Because Shopify apps use a single `client_secret` shared across every shop that installs the app, any merchant who installs the app (an unprivileged, non-technical action) legitimately receives correctly-signed webhook deliveries for their own shop. That merchant can capture one such genuine `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different, victim shop that also has the app installed. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body/hmac pair, and `Registry.process` will construct `WebhookMetadata.new(shop: <victim shop>, ...)` and dispatch it to the handler as if the victim shop generated that event.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an app built on this library cannot distinguish a genuine webhook for shop A from a replayed one falsely attributed to shop B, since the only verified byte range (`raw_body`) says nothing about which shop it came from. Any handler that keys persistence, authorization, or side effects off `WebhookMetadata#shop` (which is the very field the gem exposes for this purpose) can be made to write/act on behalf of, or under the identity of, a shop the attacker doesn't operate — a cross-tenant confusion primitive.

### Likelihood Explanation
The prerequisite is only that the attacker's own store has the target app installed — a normal unprivileged step available to anyone, requiring no `api_secret_key`, no stolen tokens, and no privileged Shopify access. Capturing one legitimate webhook delivery sent to their own endpoint and replaying it to the app's public webhook endpoint with a modified header is trivial and needs no cryptographic material at all.

### Recommendation
Bind the shop (and other headers such as `topic`/`api-version`/`webhook-id` if they are relied upon) into the signed payload check, e.g. include the `shopify-shop-domain` header bytes in `to_signable_string`, or otherwise cross-verify the header value against data derivable from the verified body/session before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the unchanged `hmac` — validation passes. [6](#0-5) 
5. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and passed to the app's handler, which processes attacker-controlled data under the victim shop's identity.
