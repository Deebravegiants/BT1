## Title
Webhook shop/topic identity spoofing via headers not covered by HMAC signature - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant (`shop`), the event type (`topic`), and the `webhook_id` entirely from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` validates only covers the raw request body. Any unprivileged actor who can obtain one legitimately-signed webhook payload (e.g., by installing the app themselves) can replay that exact body/HMAC pair while swapping the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers, and the signature check still passes.

### Finding Description
`Utils::HmacValidator.validate` checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `Request#topic`, and `Request#webhook_id` are all read straight from HTTP headers, none of which are part of the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler based on `request.topic` and constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, all taken from the unauthenticated headers: [4](#0-3) 

The intended binding is:
```
hmac_valid(body) == identity(shop, topic, webhook_id, body)
```
i.e., a valid HMAC should attest to the entire tuple `(shop, topic, webhook_id, body)`. In reality the code only checks:
```
hmac_valid(body) == true
```
and then trusts `shop`, `topic`, and `webhook_id` from headers unconditionally — exactly the same class of bug as MEME404's tier-ordering check that validated only the immediately preceding element instead of validating the full ordering invariant across all inputs. Here, the code validates only the body bytes instead of validating the full `(shop, topic, webhook_id, body)` tuple that the signature is supposed to vouch for.

### Impact Explanation
Any internet user who can install the target app on their own shop (a fully unprivileged action) receives real, validly-HMAC-signed webhook deliveries for their own tenant. Because the header fields are outside the signed scope, that same attacker can resend the identical `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting:
- `shopify-shop-domain` with a victim shop's domain, and/or
- `shopify-topic` with an unrelated topic (e.g. `customers/redact`, `shop/redact`, or any topic the app has registered a handler for), and/or
- `shopify-webhook-id`.

`Registry.process` will accept this as a validly authenticated webhook, and the registered `WebhookHandler` will execute business logic (e.g., data deletion/redaction, cache invalidation, order fulfillment triggers) attributed to a shop the attacker does not control. This is a cross-tenant identity-binding break reachable by any unprivileged actor with no access to the app's `api_secret_key`, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on a shop they control (standard, unprivileged Shopify app installation) to harvest one genuine `(body, hmac)` pair, and then send a crafted HTTP request with altered headers to the app's already-public webhook endpoint. No secrets, tokens, or social engineering are needed — only the ability to send an HTTP request, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the header-derived identity fields into the signed payload verification instead of trusting them independently. Concretely, `Request#to_signable_string` (or `Registry.process`) should incorporate `topic`, `shop`, and `webhook_id` into what gets validated — e.g., re-derive/validate the shop and topic strictly from the trusted Shopify-issued value if such is embedded in the payload, or require that the webhook subscription's actual registered topic/callback for that `webhook_id` matches what Shopify originally issued, rather than accepting attacker-controlled headers as ground truth after checking HMAC over the body alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a real webhook, capturing:
   - Body: `raw_body`
   - Headers: `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Webhook-Id: <id>`
2. Attacker resends an HTTP POST to the app's public webhook endpoint with the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header, but changes:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) passes because it only checks `raw_body` against the HMAC.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` (`lib/shopify_api/webhooks/registry.rb:198`) is built with `shop = "victim-shop.myshopify.com"`, and the app's handler executes as if the event genuinely originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
