### Title
Unchecked index-scaled market totals can permanently freeze a lending market - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary

The interest-accrual path converts scaled market totals into `i128` RAY values before applying the borrow-index ceiling. Once a large market’s `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`, every operation that accrues the market panics with `MathOverflow`, permanently blocking repayment, withdrawal, liquidation, and further index updates. [1](#0-0) [2](#0-1) 

### Finding Description

`Controller::update_indexes` is reachable by an ordinary authenticated caller and forwards the selected `Vec<HubAssetKey>` to the pool. [3](#0-2) [4](#0-3) 

The pool accrues each market by calling `interest::global_sync`, which invokes `accrue_step` for every elapsed chunk. [5](#0-4) [6](#0-5) 

At the start of `accrue_step`, the contract computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` before `update_borrow_index` can clamp the new index. [7](#0-6) 

`scaled_to_original` is a direct `Ray::mul`, and the underlying `mul_div_half_up` panics with `GenericError::MathOverflow` when the result does not fit `i128`. [8](#0-7) [9](#0-8) 

The configured index ceiling is `1e36` raw RAY, but it is applied only inside `update_borrow_index` after the already-overflowing market-value multiplication has occurred. [10](#0-9) [11](#0-10) 

Every normal pool mutation loads a synced market, so once accrual cannot complete, subsequent supply, borrow, withdraw, repay, liquidation-related pool calls, and `update_indexes` all hit the same panic before reaching their operation-specific logic. [12](#0-11) [13](#0-12) 

### Impact Explanation

This is permanent freezing of user funds and effective protocol insolvency for the affected `(hub_id, asset)` market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot clear positions, bad debt cannot be processed, and revenue cannot be claimed because all of those paths require successful market accrual. [12](#0-11) [13](#0-12) 

The repository’s own long-horizon test demonstrates the condition and confirms that the index cap does not engage before the value overflow. [14](#0-13) 

### Likelihood Explanation

An unprivileged address can create the necessary state by supplying a very large admitted amount of the target asset and borrowing a high-utilization amount through an account it controls; `supply` creates an account and `borrow` accepts caller-authorized borrows subject to normal solvency and market caps. [15](#0-14) 

The attack requires a market whose configured caps and available liquidity admit totals close to the protocol’s documented numeric domain boundary, plus enough index growth for `scaled * index` to cross `i128::MAX`. [16](#0-15) 

The exploit does not require privileged access, oracle manipulation, malformed token behavior, or a contract upgrade; the public test uses normal supply, borrow, and `update_indexes` calls to reach `MathOverflow`. [17](#0-16) 

### Recommendation

Rework accrual so index-scaled market totals cannot panic before index bounds are applied. In particular, compute utilization directly from the scaled totals and indexes using `I256` intermediates or a checked ratio, apply the index ceiling before materializing an `i128` market value, and enforce an explicit invariant that every stored scaled total multiplied by its current index remains inside the supported domain. [18](#0-17) [19](#0-18) 

Add pre-mutation domain checks to supply and borrow so newly admitted scaled shares cannot later cross that invariant, and add a recovery path for markets already at the boundary instead of allowing all repayment and exit paths to panic. [20](#0-19) [21](#0-20) 

### Proof of Concept

1. On a listed high-decimal market with sufficiently large caps, the attacker calls `Controller::supply(caller, 0, spoke_id, [(target_asset, principal)])` to create a supply account and fund the market. [22](#0-21) 
2. Using a second account owned by the same caller, the attacker supplies independent collateral and calls `Controller::borrow(caller, borrower_id, [(target_asset, debt)], Some(caller))`, leaving the target market at sustained high utilization. [23](#0-22) 
3. As ledger time advances, anyone calls `Controller::update_indexes(caller, [target_asset])`; accrual repeatedly compounds the borrow index. [3](#0-2) [6](#0-5) 
4. When `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128::MAX`, `scaled_to_original` panics before the index ceiling can clamp the index. [24](#0-23) [8](#0-7) 
5. Subsequent `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `claim_revenue`, and `update_indexes` transactions involving that market fail at the same accrual step. [12](#0-11) [25](#0-24)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```markdown
| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
