### Title
JWT replay-nonce check-then-record is not atomic in `WorkflowMetadataHandler.Authorize`, allowing concurrent replay of a single signed HTTP trigger token - (File: `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`Authorize` checks whether a JWT's `jti` has already been used (`h.jwtCache.isReplay(claims.ID)`) and, only after the signer/authorized-key check succeeds, marks the `jti` as used (`h.jwtCache.recordUsage(claims.ID)`). These two calls are not performed atomically with respect to the authorization decision: nothing prevents a second concurrent call to `Authorize` with the same JWT from passing the `isReplay` check before the first call reaches `recordUsage`. This mirrors the VRF bug class in the report — a value used to gate a one-time, security-relevant action (the nonce/replay check) can still be "used" concurrently by a second request before the state that should prevent it is committed.

### Finding Description
`Authorize` is the single entry point used by the gateway's unprivileged-facing HTTP Trigger handler to authenticate a workflow-execution request signed with a per-request JWT: [1](#0-0) 

The sequence is:
1. Verify JWT signature/claims.
2. `h.jwtCache.isReplay(claims.ID)` — read-check of the replay cache.
3. Look up authorized keys for the workflow and confirm the signer is authorized.
4. `h.jwtCache.recordUsage(claims.ID)` — only now is the `jti` marked used.

The replay cache's read (`isReplay`) and write (`recordUsage`) are two separate calls on `jwtCache` guarded independently (the cache itself uses an internal `sync.RWMutex`, per its field declaration at lines 30-34), but the `Authorize` function does not hold any lock across the whole check-then-record sequence, and does not use an atomic "check-and-set" primitive. Two goroutines invoking `Authorize` concurrently with the same token (same `jti`) can each observe `isReplay == false` before either calls `recordUsage`, and both then pass the authorized-key check and return a valid `*gateway.AuthorizedKey`.

This is directly reachable from an unprivileged actor: `Authorize` is invoked from `httpTriggerHandler.authorizeRequest`, which is called on every inbound `HandleUserTriggerRequest` from the internet-facing gateway before dispatching the trigger to DON members: [2](#0-1) 

Because request IDs (not JWT `jti`s) are what the trigger handler's own duplicate-request guard checks (see the `"duplicate request ID"` test), sending the same signed JWT twice with two different top-level JSON-RPC request IDs bypasses that separate guard and lands purely on the `jwtReplayCache`'s check-then-record window.

### Impact Explanation
A single valid, signed JWT (whose intended semantics are "usable exactly once," per the design rationale stated in the code and reinforced by the error message "JWT token has already been used") can be replayed to trigger more than one workflow execution if the two requests race the `isReplay`/`recordUsage` window. This is an authentication/anti-replay bypass: it lets an unprivileged party who has captured or been given a single-use trigger token cause duplicate/unauthorized job runs of a CRE workflow, which the intended one-shot design assumes cannot happen. Given this is the sole replay defense on this path, the impact is a duplicate/unauthorized job-run execution — a concrete Chainlink-relevant analog to the report's "extra input accepted after the commit point" class.

### Likelihood Explanation
Exploitation requires only sending the same signed request twice back-to-back (two goroutines/parallel HTTP calls) with a small timing window; no special privilege beyond having captured one valid JWT for the workflow is needed. The window is narrow (two in-memory map operations), so reliable exploitation likely requires some retry/racing effort, making likelihood medium rather than trivial — comparable to the "requires minting a new HoneyJar NFT" precondition in the original report.

### Recommendation
Make the replay check-and-mark atomic: acquire a single lock (or use a compare-and-swap style map operation) that checks for existence of `claims.ID` and inserts it in one critical section, rejecting the second concurrent caller before it proceeds to the authorized-key check. Only proceed with signer/workflow authorization after the `jti` has been durably claimed, not after it, so a second concurrent execution with the same token is deterministically not accepted.

### Proof of Concept
Not independently executed against a live gateway in this analysis (no runtime/tooling access); the following is a scenario derived directly from the code paths cited above:
1. Obtain one valid, signed HTTP-trigger JWT for a workflow (`req.Auth`), as any caller of `HandleUserTriggerRequest` normally would.
2. Fire two concurrent `HandleUserTriggerRequest` calls using the same JWT but two different JSON-RPC request IDs (bypassing the separate duplicate-`req.ID` guard).
3. Both calls invoke `httpTriggerHandler.authorizeRequest` → `WorkflowMetadataHandler.Authorize` concurrently; if both reach `h.jwtCache.isReplay(claims.ID)` before either calls `h.jwtCache.recordUsage(claims.ID)`, both are authorized and both workflow executions are dispatched to the DON, i.e., the "single-use" token triggered two executions. func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
```go
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

```go
func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
```
