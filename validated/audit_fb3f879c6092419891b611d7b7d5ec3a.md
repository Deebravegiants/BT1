### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop that the webhook payload is attributed to (`shop`, from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read directly from unauthenticated HTTP headers and never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, breaking the binding `shop authenticated == shop the data is attributed to`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and the identity fields are pulled straight from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`: [3](#0-2) 

Since `to_signable_string` for `Request` is just `@raw_body`, the HMAC only proves that *some* previously-signed body byte sequence was reused — it proves nothing about which shop, topic, or webhook id it is being delivered as. `Registry.process` then does: [4](#0-3) 

`request.shop` (attacker-controlled header) is passed straight into `WebhookMetadata`, which is exactly the value app handlers use to key persistence, authorization, and business logic per-tenant.

Contrast this with the OAuth `AuthQuery`, where `shop` is one of the fields explicitly included inside `to_signable_string` and therefore is bound by the HMAC: [5](#0-4) 

The equality that should hold is: `shop value verified by the HMAC == shop value the webhook is processed/attributed under`. In the `Webhooks::Request` path this equality never has to hold — the HMAC only covers `raw_body`; `shop`, `topic`, and `webhook_id` are unauthenticated headers layered on top of a validly-signed body.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook body/HMAC pair (e.g., by running the app themselves as a merchant/installer on their own shop and capturing an inbound webhook — no `api_secret_key` or Shopify credentials are needed to do this) can replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting the `shop-domain` header to name a different, victim tenant. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that uses the library exactly as documented (trusting `request.shop`/`WebhookMetadata#shop` to select tenant state, e.g., to redact/update/create records, or handle `shop/redact`, `customers/redact`, `customers/data_request` mandatory GDPR topics) will act on attacker-supplied data under another tenant's identity — a cross-tenant access/confusion vulnerability.

### Likelihood Explanation
Every consumer of this gem calls `Utils::HmacValidator.validate`/`Registry.process` exactly as documented, so the vulnerable code path is always reachable by design; the attacker only needs (a) their own legitimate app installation to obtain one valid signed body/HMAC pair for any topic, and (b) the ability to send an HTTP POST with custom headers to the app's public webhook endpoint — both are unprivileged-internet-user capabilities requiring no secret material.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string used for `Webhooks::Request#to_signable_string` (or otherwise cryptographically bind them to the payload before validation), so the HMAC check verifies the same fields that `Registry.process`/`WebhookMetadata` subsequently trust and act upon.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook topic already registered by the app (e.g. `orders/create`), capturing the raw POST body `B` and the `shopify-hmac-sha256: H` header Shopify sent — `H` is a valid HMAC over `B` under the app's `api_secret_key`.
2. Attacker crafts a new HTTP request to the app's webhook endpoint reusing body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses fine; `request.shop` returns `"victim.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because the shop header was never part of the signed material: [6](#0-5) 
5. The app's handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled webhook data as if it originated from the victim shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
