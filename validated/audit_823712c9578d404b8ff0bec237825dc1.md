## Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop` attribute directly from the unauthenticated `shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only ever validates the HMAC over the raw request body. Any party capable of producing (or replaying) a body/HMAC pair that is valid for the app's shared secret can attach an arbitrary `shop-domain` header, and `Registry.process` will accept it as an authentic webhook "from" that shop.

### Finding Description
`Webhooks::Request` implements the `Utils::VerifiableQuery` interface. Its `to_signable_string` returns only the raw body: [1](#0-0) 
while `shop` is read straight from an unauthenticated header with no cryptographic linkage to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature exclusively over `verifiable_query.to_signable_string` (the body), never over the shop header: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate` result as full authentication of the request, then forwards the (unverified) `request.shop` straight to the app's handler as trusted webhook metadata: [4](#0-3) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook" — i.e., it is documented as a trustworthy, verified value: [5](#0-4) [6](#0-5) 

This is the same class of flaw as the reference report: the mechanism binds authorization/validation to one quantity (the raw body bytes) while a security-relevant, acted-upon field (the shop identity used to route data to a tenant) is left outside that binding — i.e., `verified(bytes)` ≠ `acted_on(shop)`.

**Exploit path**: The app's HMAC secret (`api_secret_key`) is shared across all shops that install the app — it is not per-tenant. Any unprivileged internet user who installs the app on their own store (a legitimate, unprivileged installation, not requiring the app's secret or any privileged credential) will receive genuine webhook deliveries for their own shop, each with a valid `x-shopify-hmac-sha256` computed over that request's body using the app's shared secret. Since the shop identity is not part of the signed content, the attacker can capture one such (body, hmac) pair and replay it against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), so `Registry.process` invokes the app's handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain and attacker-controlled body content.

### Impact Explanation
This breaks the tenant boundary that `shop` is meant to enforce: an attacker who is nothing more than an installed, unprivileged user of the app for their own store can forge webhook events that host applications will process as if they originated from any other merchant's store, since `shop` is the documented tenant key used to route/store webhook data (see the `perform_later(topic:, shop_domain: data.shop, ...)` pattern in the docs). Depending on the host app's handler logic (e.g. updating orders/inventory/session-linked records keyed by `shop`), this enables cross-tenant data injection or corruption — qualifying as Critical (cross-tenant access) per the impact taxonomy.

### Likelihood Explanation
Medium: it requires the attacker to be an installed user of the target app (achievable by any internet user installing a public app on a free/dev store) and to be able to POST arbitrary headers to the app's public webhook endpoint, which is by definition internet-reachable. No possession of `api_secret_key` or any Shopify-issued credential belonging to another tenant is required.

### Recommendation
Bind the shop identity into the value that is actually verified. Either:
- Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header value in the signable string used by `HmacValidator`, matching it against a canonical signed representation, or
- Cross-check `request.shop` against the shop associated with the specific webhook subscription/session that the app registered for the incoming `webhook_id`/topic before invoking the handler, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service install).
2. Attacker triggers an event (e.g. creates an order) and captures the resulting legitimate webhook HTTP request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(api_secret_key, B)`).
3. Attacker replays the exact same request to the app's public webhook callback URL, keeping body `B` and header `H`, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate`, which recomputes the HMAC only over `B` — [7](#0-6)  — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` — [8](#0-7)  — even though the event/body actually originated from the attacker's own store.
