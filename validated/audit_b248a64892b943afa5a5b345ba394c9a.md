### Title
Webhook `shop`/`topic` identity is trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery by validating an HMAC, but the HMAC's signable content is defined as *only* the raw request body. The `shop` and `topic` values that are subsequently used to route the request and are handed to the app's handler are read from HTTP headers that are never part of the signed content, so they carry no cryptographic binding to the verified bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` and `request.topic` to look up the handler and build the metadata delivered to the app's business logic: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e. the raw body, and compares it against the value found in the `hmac-sha256` header: [4](#0-3) 

The identity binding that should hold is:
`shop_domain_covered_by_hmac == shop_domain_delivered_to_handler`

but in this implementation the left side is empty (nothing shop-specific is signed) while the right side is attacker-controlled header content. Any entity capable of obtaining one genuine, validly-signed webhook body for *any* shop (e.g. a merchant on their own store who installs the app and receives a legitimate webhook, or anyone who can capture a webhook payload) can replay that exact `raw_body` + `hmac-sha256` header, unmodified, to the app's webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers with a different value. `HmacValidator.validate` still succeeds, because it only checks that the (untouched) body matches the (untouched) signature — the shop/topic headers are outside its scope. `Registry.process` then calls the topic handler with `WebhookMetadata` carrying the attacker-chosen `shop`, which the host application typically uses as the tenant key to load the correct session/access token, update per-shop state, or trigger shop-scoped side effects. This lets an unprivileged webhook sender cross tenant boundaries by mislabeling which shop a validly-signed payload belongs to.

This is the same bug class as the report: the report's `voteTimestamp`/report-id was used to gate a critical decision (`getExcludedCoverageOf`) without checking whether that value came from a state that had actually been verified (a successful vote); here, the `shop`/`topic` used to gate a critical decision (which tenant/handler processes the payload) is taken from data that was never included in the verification (the HMAC).

### Impact Explanation
If a host application uses `data.shop` (as the docs and tests show it is designed to be used) to select which merchant's session, access token, or persisted state to act on, an attacker who can obtain one legitimately-signed webhook body can relabel it to any `shop` value and cause the app to process/attribute that payload as belonging to a different, arbitrary tenant. This is a cross-tenant data/action confusion condition, which is classified as Critical impact ("cross-tenant access") per the rules.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of one genuine `(raw_body, hmac-sha256)` pair — obtainable by any unprivileged actor who installs the app on a shop they control (or otherwise observes a delivered webhook). No access token, `client_secret`, or privileged account is required; only header manipulation on an otherwise-valid replayed request.

### Recommendation
Include the shop domain (and ideally the topic) in the HMAC-signed content, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the verified body (e.g., verify that the delivery's `shop` is consistent with metadata Shopify signs, or require the app to independently confirm shop ownership before trusting `data.shop` for tenant-scoped actions). At minimum, document prominently that `shop`/`topic` headers are unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers a request with a valid `x-shopify-hmac-sha256` header computed over the JSON body using the app's `client_secret`.
2. Attacker captures the raw request: `raw_body` and its `x-shopify-hmac-sha256` value.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `HmacValidator.validate` in `Registry.process` succeeds because it only checks the untouched `raw_body` against the untouched HMAC value — confirmed by `Request#to_signable_string` returning solely `@raw_body`. [1](#0-0) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, delivering attacker-controlled tenant identity to the app's business logic even though the shop/topic were never verified. [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
