### Title
Self-relayed swap silently strands protocol/relay fees in `ExternalActionSwap` when `circomData.relay == address(0)` - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` always computes `relayFee`/`hinkalFee` and subtracts `totalFee` from the amount credited to the user's UTXO, but the actual transfer of that fee is routed through `Transferer.sendToRelay`, which is a no-op whenever `relay == address(0)`. Self-relayed swaps (`circomData.relay == address(0)`, `originalSender == msg.sender`, a path explicitly allowed by `HinkalHelper.performHinkalChecks`) therefore have their fee permanently stuck in the `ExternalActionSwap`/`LifiExternalAction` contract with no sweep mechanism.

### Finding Description
Equality claimed to break: tokens leaving `ExternalActionSwap` for the fee-bearing transaction == the fee amount subtracted from the user's credited UTXO. Trace:

- `HinkalHelper.performHinkalChecks` explicitly allows `relay == address(0)` when `originalSender == sender` [1](#0-0) , i.e. self-relaying is a legitimate, attacker-reachable path, not a misuse.
- In `ExternalActionSwap.swap()`, `hinkalFee`/`relayFee` are computed unconditionally from `swappedAmount`, and `sendToRelay` is called with `circomData.relay` regardless of whether it is zero: [2](#0-1) .
- `Transferer.sendToRelay` no-ops when `relay == address(0)`: [3](#0-2) .
- `totalFee = hinkalFee + (outputToken==feeToken ? relayFee : 0)` is still subtracted from `amountToSendToHinkal`, and only `amountToSendToHinkal` is forwarded to `msg.sender` (the Hinkal contract) via `transferERC20TokenOrETH`. The `totalFee` amount is never transferred anywhere and remains as an idle ERC20/ETH balance inside the `ExternalActionSwap`/`LifiExternalAction` contract, with no owner/admin sweep function present in `ExternalActionBaseV2`, `OwnerHinkal`, or `ExternalActionSwap` itself.
- On the Hinkal side, `Hinkal.transact()`'s balance-equality check (`balanceDif == amountChanges[i] + utxoAmount`) only verifies what actually arrived at the Hinkal contract, matching `amountToSendToHinkal` exactly [4](#0-3) ; this check does not detect or prevent the stranding inside the external action contract, since it only reasons about Hinkal's own balance, not the external action's.

I was unable to confirm the second half of the question's claim (a subsequent unrelated caller can *withdraw* the stranded fee via `callRouter`'s output-side balance measurement). `LifiExternalAction.callRouter` computes `swappedAmount = balanceAfter(outputToken) - balanceBefore(outputToken)` [5](#0-4) . Any pre-existing stranded balance of `outputToken` is already included in `balanceBefore` and cancels out of the subtraction, so it is not counted into a later caller's `swappedAmount`. Extracting the stranded balance would require a different, unverified mechanism (e.g., a later swap using the stranded token as its *input*, combined with `approveUnlimited` and attacker-crafted router calldata that pulls more than the caller's own declared `inputAmount`), which was not traced to completion and is not the mechanism the question describes.

### Impact Explanation
The protocol/relay fee for any self-relayed swap transaction is permanently locked inside the `ExternalActionSwap`/`LifiExternalAction` contract; it is deducted from the user's credited value but never paid to anyone, and there is no sweep/rescue function to recover it. This matches the "High - permanent freezing of protocol/relay fees" category. The claim that this frozen value can subsequently be stolen by an unprivileged third party via the described `callRouter` balance-delta mechanism is not substantiated by the code trace (the delta measurement cancels pre-existing balances), so that specific theft vector should be treated as unverified rather than confirmed.

### Likelihood Explanation
Trivial to trigger and fully attacker-controlled: any unprivileged EOA can call `transact()` directly (`originalSender == msg.sender`, `relay == address(0)`) targeting a registered `LifiExternalAction`/`ExternalActionSwap`, with `circomData.feeStructure.variableRate > 0` and/or `flatFee > 0`. Every such self-relayed swap freezes `totalFee` worth of the output (or fee) token. Repeatable indefinitely by any caller, accumulating value in the contract over time with no recovery path.

### Recommendation
When `circomData.relay == address(0)`, either (a) skip fee computation/deduction entirely so `amountToSendToHinkal == swappedAmount`, or (b) route `hinkalFee`/`relayFee` to a fixed protocol fee-recipient address instead of relying solely on `circomData.relay`, mirroring how `_internalTransact` in `Hinkal.sol` requires `hasPaidToRelay` whenever `relay != address(0)` (and should likewise avoid charging fees when self-relaying). Additionally add an owner-gated rescue/sweep function to `ExternalActionSwap` to recover any tokens that become stranded due to this or other rounding/dust conditions.

### Proof of Concept
Hardhat fork test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` (with a mocked/real router), register the action.
2. As an unprivileged EOA, generate a valid proof for a `transact()` swap call with `circomData.relay = address(0)`, `originalSender = msg.sender`, `feeStructure.variableRate > 0` (and optionally `flatFee > 0` with `feeToken == outputToken`).
3. Execute `transact()`; assert:
   - `LifiExternalAction` balance of `outputToken` increases by exactly `totalFee` (i.e., `totalFee` never left the contract, confirming `sendToRelay` no-op).
   - The minted UTXO credited to the attacker equals `amountToSendToHinkal = swappedAmount - totalFee` (correctly reduced, no over-minting).
4. Run a second, unrelated EOA's `transact()` swap using the same `LifiExternalAction` contract with `outputToken` as its own output token; assert that this second caller's `swappedAmount` equals only `balanceAfter - balanceBefore` measured right before their own router call, i.e. does **not** include the first transaction's stranded `totalFee` (this should hold, refuting the theft-via-callRouter-delta claim).
5. Assert there is no owner or public function capable of recovering the stranded `totalFee`, confirming permanent freezing.
