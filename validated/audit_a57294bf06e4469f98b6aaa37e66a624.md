### Title
Webhook HMAC only signs the raw body, allowing shop identity spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by returning **only** `@raw_body` from `to_signable_string`, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then forwards the header-derived, unsigned `shop` value to the app's handler as the tenant identity, breaking the binding `shop_verified == shop_used_by_handler`.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, which for webhooks is defined as: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled from HTTP headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` verifies only that the HMAC over the body is valid, then trusts `request.shop` (and `request.topic`, `request.webhook_id`) as authenticated tenant/event metadata when constructing `WebhookMetadata` for the handler: [3](#0-2) 

`HmacValidator` itself only checks bytes against the secret; it has no notion of which fields are "covered": [4](#0-3) 

Because the `shopify-shop-domain` (and topic/webhook-id) headers are never included in the HMAC computation, a request whose body+HMAC pair is genuinely valid (signed by Shopify for the app's `client_secret`) will still pass `Utils::HmacValidator.validate(request)` even if the `shop-domain` header is swapped to an arbitrary/victim value. This breaks the identity binding: **bytes verified (body) ≠ bytes the app treats as authenticated tenant identity (shop header)**.

### Impact Explanation
An unprivileged user who installs the app on their own shop legitimately receives real webhook deliveries with valid `X-Shopify-Hmac-Sha256` signatures for their own body content. Because the header carrying `shop-domain` is outside the signed data, that same attacker can resend the identical `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` still passes HMAC validation and hands the handler a `WebhookMetadata` claiming the event originated `shop: <victim shop>`, letting a normal merchant inject spoofed, "verified" webhook events attributed to another tenant. Any app logic that trusts `WebhookMetadata#shop` as an authenticated tenant key (e.g., to update per-shop state, GDPR redaction records, or billing) can be cross-tenant poisoned — this satisfies the High-impact class ("scope or expiry/identity check bypass").

### Likelihood Explanation
No `api_secret_key`, TLS interception, or leaked credentials are required. Any merchant who installs the app is an "unprivileged internet user" relative to other tenants and can trivially capture and replay their own genuine webhook deliveries (raw body + HMAC header are visible to them from their own reverse proxy/logs or by simply issuing a duplicate POST with the same body) against the app's public, internet-reachable webhook endpoint, only editing the shop-identifying header. Likelihood is High for any app that reads `WebhookMetadata#shop` as its trust boundary for the payload — which is the documented purpose of that field.

### Recommendation
Bind the shop/topic/webhook-id headers to the HMAC verification. At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` into what's authenticated (e.g., verify the returned `shop` against a session/store the app already trusts for that installation, or require the app to independently confirm the shop is one it has an active session for) instead of trusting the raw header value as tenant identity solely because the body's HMAC matched.

### Proof of Concept
1. Merchant A installs the app on `shop-a.myshopify.com` and receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Merchant A (or anyone who can capture that request) resends the exact same body `B` and HMAC header `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim tenant).
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `hmac` returns the unchanged `H`, `to_signable_string` returns unchanged `B`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H` — validation succeeds despite the shop header having been altered: [5](#0-4) 
5. The app's registered handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and a body that passed HMAC verification, even though `shop-b` never sent this event.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
