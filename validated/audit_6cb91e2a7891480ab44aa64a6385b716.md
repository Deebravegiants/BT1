### Title
Local-only success determination for user-centric signups bypasses the authoritative backend enrollment check - (File: `src/plans/mod.rs`)

### Summary
In `MasterPlan::do_signup`, when a QR code indicates a "user-centric signup" (`user_centric_signup == true`), the orb determines signup success purely from a *local* `signup_reason` value instead of calling the authoritative `enroll_user` plan that performs the round-trip signup_post/signup_poll exchange with the backend. This mirrors the reported bug class: a secondary/duplicate code path (`leave`) that skips the authoritative state check (`isCommited`) performed by the correct path (`withdrawContribution`), letting callers obtain an outcome inconsistent with the true, backend-verified state.

### Finding Description
`MasterPlan::do_signup` computes a `signup_reason` (`Normal`/`Fraud`/`Failure`) using only orb-local information: whether the biometric `pipeline` succeeded and the local `detect_fraud` result. [1](#0-0) 

Note that in this build `detect_fraud` is a stub that unconditionally returns `false` ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), so `signup_reason` can only be `Normal` or `Failure` locally. [2](#0-1) 

When `user_centric_signup` is set (an attacker/user-controlled value decoded from the scanned user QR code's authenticated app data) and the orb is not configured to `ignore_user_centric_signups`, the code takes a shortcut: it sets `enrollment_status` and `success` directly from the local `signup_reason`, without ever invoking `enroll_user`: [3](#0-2) 

Compare this to the "else" branch, which is the authoritative path: it calls `self.enroll_user(...)`, which runs `enroll_user::Plan::run`. That function posts the signup to the backend via `signup_post::request` and then polls `signup_poll::request` until the backend returns a definitive status. The backend-side poll explicitly covers cases the orb cannot know locally — duplicate signups, legacy signup requests, in-flight matches, and backend-detected fraud: [4](#0-3) [5](#0-4) 

The `user_centric_signup` flag itself originates from the scanned/authenticated user QR data: [6](#0-5) 
and is only overridden when the orb-wide config `ignore_user_centric_signups` is explicitly set to force full enrollment: [7](#0-6) 

Because the `user_centric_signup` branch never contacts `signup_post`/`signup_poll`, the resulting `debug_report.enrollment_status` and `result.success` are never checked against the backend's authoritative decision. The consequence of `result.success` and `enrollment_status` is broad: it drives `dbus::Signup::signup_finished(success)`, `debug_report.signup_successful()`/`signup_orb_failure()` reporting, and UI success/failure state: [8](#0-7) [9](#0-8) 

### Impact Explanation
This is analogous to the `leave` vs `withdrawContribution` bug: the "shortcut" path (`user_centric_signup` branch) determines a signup's success/failure using stale/incomplete local information, bypassing the authoritative check (the backend's `signup_post`/`signup_poll` round trip) that the "correct" path (`enroll_user`) performs. Because backend-side duplicate detection, in-flight match detection, and backend fraud detection are only evaluated in the `enroll_user` path, a user-centric signup can be marked `Success` locally (dbus `signup_finished(true)`, UI success, debug report `signup_successful`) even in scenarios where the backend would have rejected the exact same signup as a duplicate or fraudulent — i.e., a misattributed/unauthorized signup outcome, since the orb never learns of and never enforces the backend's authoritative verdict.

### Likelihood Explanation
`user_centric_signup` is derived from data in the scanned user QR / authenticated app payload and is honored by default (`ignore_user_centric_signups` defaults to `false`), so any signup flow using this QR attribute takes the shortcut path automatically without operator intervention. [10](#0-9) 

### Recommendation
Do not derive final `enrollment_status`/`success` purely from the local `signup_reason` for user-centric signups. Either always route through `enroll_user` (i.e., always perform the `signup_post`/`signup_poll` backend round trip regardless of `user_centric_signup`), or, if the local-decision shortcut must be kept for latency reasons, still perform an asynchronous backend confirmation and reconcile/report discrepancies (duplicate, in-flight match, backend fraud) rather than trusting the local-only path as final.

### Proof of Concept
1. Craft (or have the companion app produce) a user QR / authenticated app payload with `user_centric_signup: true`. [11](#0-10) 
2. Perform a signup on an orb where `ignore_user_centric_signups` is `false` (default).
3. In `do_signup`, since `pipeline` succeeds locally and local `detect_fraud` always returns `false`, `signup_reason == SignupReason::Normal`, causing the code to set `enroll_user::Status::Success` and `success = true` without ever calling `signup_post::request`/`signup_poll::request`. [3](#0-2) 
4. The signup is reported as successful (UI, dbus, debug report) even though the backend was never asked to authoritatively confirm/reject it (e.g., as a duplicate or fraud case), unlike the `enroll_user` path which would have received `SignupVerificationNotSuccessful`/`Fraud` in that scenario. [12](#0-11)

    async fn enroll_user(
        &mut self,
        orb: &mut Orb,
        debug_report: &mut debug_report::Builder,
        capture: &biometric_capture::Capture,
        pipeline: Option<&biometric_pipeline::Pipeline>,
        signup_reason: SignupReason,
    ) -> enroll_user::Status {
        orb.set_phase("User enrollment").await;
        let t = Instant::now();
        let status = Box::pin(
            enroll_user::Plan {
                signup_id: debug_report.signup_id.clone(),
                operator_qr_code: debug_report.operator_qr_code.clone(),
                user_qr_code: debug_report.user_qr_code.clone(),
                s3_region_str: self.s3_region_str.clone(),
                capture,
                pipeline,
                signup_reason,
            }
            .run(orb),
        )
        .await;
        dd_timing!("main.time.signup.user_enrollment", t);

        debug_report.enrollment_status(status.clone());
        status
    }
