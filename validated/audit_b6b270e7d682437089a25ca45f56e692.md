Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop`, with no domain validation performed inside `HttpClient` itself [1](#0-0) . The request body containing `client_secret` is then POSTed to that host [2](#0-1) .

### Title
Missing `dest`-claim domain validation in `TokenExchange.exchange_token` sends `client_secret` to an unverified host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop/host that will receive the app's `client_secret` directly from the session token's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling method `migrate_to_expiring_token` in the same file, which does validate its `shop` argument before use.

### Finding Description
`exchange_token` decodes the session token into a `JwtPayload`, reads `dest_shop = jwt_payload.shop` (i.e. the `dest` claim with `https://` stripped) [3](#0-2) , and immediately uses this value, unsanitized, as the `shop` of the `Session` passed to `Clients::HttpClient`: [4](#0-3) 

`HttpClient` in turn builds the outbound request host straight from `session.shop`: `@base_uri = "https://#{api_host || session.shop}"` [1](#0-0) . The POST body sent to that host includes `client_secret` [5](#0-4) .

By contrast, `migrate_to_expiring_token` in the same module explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host that receives `client_secret` [6](#0-5) , and `ShopValidator` restricts hosts to a fixed allow-list of trusted Shopify domains [7](#0-6) .

The equality that should hold is: `host validated (via ShopValidator against TRUSTED_SHOPIFY_DOMAINS) == host that receives client_secret`. In `exchange_token` this equality does not hold — the host receiving `client_secret` is whatever string is in the JWT `dest` claim, with no allow-list check.

`JwtPayload` only checks the signature (HS256 with `api_secret_key`) and the `aud` claim against `Context.api_key` [8](#0-7) ; it never validates that `dest` is a `*.myshopify.com`/`myshopify.io`/etc. domain. So a syntactically well-formed but non-Shopify `dest` value in a validly-signed token would be forwarded straight through to `HttpClient` as the destination host for the `client_secret`-bearing request.

### Impact Explanation
This matches the "host validated versus host that receives the `client_secret`" identity-binding failure. Because it is `exchange_token`, not `migrate_to_expiring_token`, that omits the check, the app's `client_secret` (and the freshly obtained access/refresh token in the response) could be sent to a host that was never confirmed to be a genuine Shopify domain, which is an SSRF-with-credentials pattern (impact tier: High).

### Likelihood Explanation
Exploitability is gated by one crucial fact I could not fully close out: `JwtPayload.new` only accepts tokens signed with `Context.api_secret_key` (or `old_api_secret_key`) using HS256 [9](#0-8) . In the real Shopify session-token flow, only Shopify (which shares that secret with the app) issues these tokens, and Shopify is expected to always set `dest` to the genuine requesting shop's own domain. An unprivileged internet user who does not already possess the app's `client_secret` cannot forge a token with an attacker-chosen `dest` claim; without that, they cannot exercise this code path to redirect the request to an attacker host. I was not able to verify, from the code available in this repo/index, whether there is any other path (e.g., algorithm confusion, or a downstream consumer using an unverified/unverified-but-parsed `dest`) that would let an unprivileged party control `dest` without secret knowledge — the `JWT.decode` call does pin `algorithm: "HS256"`, which forecloses the classic `alg=none` bypass. Given this gate, the missing validation in `exchange_token` is a real code-level asymmetry/defense-in-depth gap relative to `migrate_to_expiring_token`, but I could not confirm a concrete unprivileged-attacker path to control `dest` and thus could not fully prove exploitability meeting the required "unprivileged internet user, no secrets" threat model.

### Recommendation
For completeness and defense-in-depth (and to keep the identity binding "host validated == host receiving client_secret" consistent across the module), pass `dest_shop` through `Utils::ShopValidator.sanitize!` (as `migrate_to_expiring_token` already does) before constructing `shop_session` and issuing the request in `exchange_token`.

### Proof of Concept
Not able to construct a working end-to-end PoC without control over `api_secret_key`/`client_secret`, since producing a JWT with an attacker-controlled `dest` claim that passes `JwtPayload`'s HS256 signature check requires knowledge of the shared secret, which is explicitly out of scope for this analysis. The asymmetric code path (validated in `migrate_to_expiring_token`, unvalidated in `exchange_token`) is demonstrated by the citations above; a concrete exploit chain would additionally require a way for an unprivileged party to obtain or influence a validly-signed token with a non-Shopify `dest`, which I could not establish from the code available.
