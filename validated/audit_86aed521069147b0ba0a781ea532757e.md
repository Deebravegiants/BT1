### Title
Failed-but-committed `CreateAccount`/`Allocate` instructions permanently consume the per-block `allocated_accounts_data_size` budget for the rest of the slot - ([File: cost-model/src/cost_tracker.rs])

### Summary
`CostTracker::add_transaction_cost` charges `allocated_accounts_data_size` using a purely static, pre-outcome estimate (`CostModel::calculate_allocated_accounts_data_size`) that only inspects instruction opcodes/data, not whether the account allocation actually occurred. Because this same static estimate is also used for the "actual" post-execution cost (`calculate_cost_for_executed_transaction`), and Agave routinely commits transactions with a fee-only/rolled-back state when an instruction fails at runtime (e.g. `InsufficientFundsForRent`), an attacker can cheaply reserve large chunks of the block's account-data-allocation budget without ever creating the accounts, denying other legitimate users the ability to create accounts for the rest of the slot.

### Finding Description
`CostTracker::try_add` -> `would_fit` enforces `allocated_accounts_data_size` against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`, and on success `add_transaction_cost` adds `tx_cost.allocated_accounts_data_size()` to the running total: [1](#0-0) [2](#0-1) 

The value being added, `tx_cost.allocated_accounts_data_size()`, is derived from `CostModel::calculate_allocated_accounts_data_size`, a purely static analysis of the instruction stream (matching on `SystemInstruction::CreateAccount`/`Allocate` and summing the requested `space`) that has no knowledge of whether the instruction will actually succeed at runtime: [3](#0-2) 

Crucially, this exact same static function is invoked both for the pre-execution estimate (`calculate_cost`) and for what is meant to be the "actual" post-execution cost (`calculate_cost_for_executed_transaction`), via the shared `calculate_transaction_cost` helper: [4](#0-3) [5](#0-4) 

The post-execution cost accounting flow (`check_block_cost_limits` / `get_transaction_costs`) treats any transaction with `Ok(committed_tx)` (i.e. it was *committed*, regardless of whether its `status` is an `InstructionError`) as chargeable, and calls `try_add` on it: [6](#0-5) 

Agave's SVM commits transactions with a fee-only status when a runtime `InstructionError` occurs mid-execution (nonce advances and fee deduction persist, other state changes roll back) — this is standard, well-tested behavior: [7](#0-6) [8](#0-7) 

`svm/src/transaction_processing_result.rs` documents this explicitly: [9](#0-8) 

Since `create_account` in the System program fails with `InsufficientFundsForRent`/`AccountAlreadyInUse` etc. only after `allocate_and_assign` has already been "attempted" from the cost model's point of view (the cost model can't distinguish this from a successful allocation — it never executes the instruction, it only parses `SystemInstruction::CreateAccount{ space, .. }`), a transaction containing a `CreateAccount` instruction with a large `space` value that fails at runtime (e.g. supplying `lamports` less than `Rent::minimum_balance(space)`) will:
1. Be admitted by `CostTracker::try_add` pre-execution based on the static estimate.
2. Fail during SVM execution (no account is actually created/no data is actually allocated).
3. Still be `Committed` (fee-only, per `ProcessedTransaction::Executed`/`FeesOnly` semantics), so `get_transaction_costs` returns `Some(...)`, not `None`.
4. Have its actual cost recomputed via `calculate_cost_for_executed_transaction`, which recomputes `allocated_accounts_data_size` from the *same static instruction parse*, i.e. still counts the full requested `space`.
5. That cost is `try_add`'d again into the cost tracker's running `allocated_accounts_data_size` total, and it is **never removed** — `CostTracker::remove`/`remove_added_transaction_costs` is only invoked on retry/rollback paths *before* commit (all-or-nothing batch cancellation), not after a transaction has actually been committed.

There is no mechanism anywhere in `cost_tracker.rs`, `consumer.rs`, or `transaction_execution.rs` that decrements `allocated_accounts_data_size` for a committed-but-failed account-creation transaction. The check `WouldExceedAccountDataBlockLimit` therefore accumulates space for account creations that never happened, for the remainder of the slot.

### Impact Explanation
An unprivileged attacker can broadcast a stream of otherwise-cheap transactions, each containing a `CreateAccount`/`Allocate` instruction requesting `space` close to `MAX_PERMITTED_DATA_LENGTH` combined with an intentionally-insufficient `lamports` (or another runtime-only failure condition that is undetectable by static cost analysis), paying only the base transaction fee (no rent, since the account is never actually created). Each such transaction permanently consumes its (large) share of `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` for the current slot, causing legitimate users' `CreateAccount` transactions to be rejected with `WouldExceedAccountDataBlockLimit` for the remainder of that slot at negligible cost to the attacker. This is a block-resource-exhaustion / griefing DoS on the account-creation cost-tracker limit — underpriced execution relative to the resource reserved, matching Agave's "materially underpriced execution" / DoS bounty category. Impact is bounded to a single slot because `CostTracker::new_from_parent_limits` resets `allocated_accounts_data_size` to 0 for each new bank.

### Likelihood Explanation
Highly feasible and repeatable: the attacker needs no special privileges, only the ability to submit ordinary transactions with self-chosen `lamports`/`space` values in a `CreateAccount`/`Allocate` instruction and a fee payer with just enough balance to cover the base fee (not the rent-exemption minimum). This can be repeated every slot the attacker has transactions land, and the cost per griefed byte is far below the true SOL cost of actually persisting that much account data.

### Recommendation
Do not treat a committed-but-runtime-failed account-creation instruction as consuming the account-data-allocation budget. Options:
- In `get_transaction_costs`/`create_commit_results`, compute `allocated_accounts_data_size` from the actual outcome (e.g. only count space for accounts that transitioned from non-existent/zero-lamport to funded+sized, using the loaded/rollback account info already tracked in `LoadedTransaction`/`RollbackAccounts`), rather than re-deriving it via static instruction parsing in `calculate_cost_for_executed_transaction`.
- Alternatively, when a transaction's `CommittedTransaction::status` is an `Err` (fee-only or instruction error) and no accounts were actually resized, pass `allocated_accounts_data_size = 0` for the post-execution cost used in `try_add`, so the reserved static estimate from admission is corrected down to the real value once execution result is known.

```rust
#[test]
fn test_cost_tracker_griefing_via_failed_create_account() {
    // Build a tx_cost mimicking a CreateAccount instruction requesting large space
    // that will fail execution (insufficient lamports for rent), but is still
    // "committed" (fee-only) — hence get_transaction_costs() -> Some(actual_cost)
    // with allocated_accounts_data_size still equal to the static estimate.
    let mint_keypair = test_setup();
    let tx = build_simple_transaction(&mint_keypair);
    let mut tx_cost = simple_transaction_cost(&tx, 5);
    tx_cost.allocated_accounts_data_size = MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA / 2; // e.g. near MAX_PERMITTED_DATA_LENGTH clamp

    let mut testee = CostTracker::default();
    // Step 1: pre-execution admission succeeds (statically estimated)
    assert!(testee.try_add(&tx_cost).is_ok());

    // Step 2 (simulated): transaction fails at runtime (InsufficientFundsForRent),
    // account is never created, but tx is committed fee-only. In the real flow,
    // `calculate_cost_for_executed_transaction` recomputes the SAME static
    // allocated_accounts_data_size and re-adds it via try_add in
    // check_block_cost_limits/try_add_processed_transaction_costs — it is never
    // subtracted for this committed-but-failed transaction.

    // Assert the bug: allocated_accounts_data_size remains charged even though
    // no account data was ever persisted, blocking a second legitimate
    // CreateAccount of similar size in the same slot.
    let mut legit_tx_cost = simple_transaction_cost(&build_simple_transaction(&Keypair::new()), 5);
    legit_tx_cost.allocated_accounts_data_size = MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA / 2 + 1;
    assert_eq!(
        testee.would_fit(&legit_tx_cost),
        Err(CostTrackerError::WouldExceedAccountDataBlockLimit)
    );
    // No API exists to release tx_cost's allocated_accounts_data_size after
    // the transaction is committed as failed — testee.remove() is only ever
    // called from pre-commit rollback paths.
}
```

```rust
    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }
```

```rust
fn check_block_cost_limits<Tx: TransactionWithMeta>(
    bank: &Bank,
    tx_costs: &[Option<TransactionCost<'_, Tx>>],
) -> TransactionResult<()> {
    let mut cost_tracker = bank.write_cost_tracker().unwrap();
    for tx_cost in tx_costs.iter().flatten() {
        cost_tracker
            .try_add(tx_cost)
            .map_err(TransactionError::from)?;
    }

    Ok(())
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
```
