### Title
`TokenExchange.exchange_token` trusts the unbound JWT `dest` claim as the OAuth token-exchange host, bypassing the trusted-domain binding enforced elsewhere - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host used to send the app's `client_id`/`client_secret` from the raw `dest` claim of a session token, without ever validating that value against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`. Every other place in the gem that turns a caller-supplied "shop" string into an outbound request host (`migrate_to_expiring_token`, `ClientCredentials`, `RefreshToken`) runs it through `Utils::ShopValidator.sanitize!` first. `exchange_token` breaks this invariant.

### Finding Description
`JwtPayload#initialize` only checks the signature and the `aud` claim; it never validates that `dest`/`iss` refer to a trusted Shopify domain: `Context.api_secret_key` verifies the signature, `@aud == Context.api_key` is the only claim binding checked. [1](#0-0) 

`JwtPayload#shop` simply strips the scheme off `dest` and returns it verbatim, with no domain allow-listing: [2](#0-1) 

`TokenExchange.exchange_token` takes this unvalidated value (`dest_shop = jwt_payload.shop`), builds a `Session` from it, and passes that session directly into `HttpClient`, which then sends the request (including `client_id`/`client_secret` in the POST body) to `https://#{session.shop}` : [3](#0-2) [4](#0-3) 

Contrast this with `TokenExchange.migrate_to_expiring_token` in the very same file, which explicitly binds the `shop` parameter to a trusted domain before using it to build the request session: `validated_shop = Utils::ShopValidator.sanitize!(shop)`. [5](#0-4) 

`Utils::ShopValidator` exists precisely to bind an arbitrary "shop" string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted as a request host: [6](#0-5) 

This maps onto the analog class described in the rules ("a JWT claim trusted without being bound"): the binding that should hold is `request_host == sanitize!(dest_claim)`, but the code instead uses `request_host == dest_claim` unconditionally.

### Impact Explanation
If the equality `request_host == sanitize!(dest_claim)` is broken, the app's `client_id` and `client_secret` (the gem's own high-value secret, used in the request body) are sent to whatever host string ends up in the JWT `dest` claim, with no allow-list check. That is the SSRF-with-app-credentials pattern the rules classify as High impact, and it is the same class of bug as `migrate_to_expiring_token` was hardened against via `sanitize!`.

### Likelihood Explanation
This is not concretely exploitable to a high confidence level, which is why I flag it rather than assert it fully. The `dest` claim can only appear in a session token that is HMAC/HS256-signed with the app's own `api_secret_key`; the party who mints session tokens with a legitimate `aud` for a given app is Shopify's own App Bridge/admin infrastructure, not an arbitrary unprivileged internet user, and in normal operation Shopify sets `dest` to the real shop's admin host. I was not able to find, within this gem's code, any mechanism by which an unprivileged caller supplies or controls the `dest` value of a validly-signed token independent of Shopify's session-token issuance. The finding is therefore a structural code-level inconsistency (missing defense-in-depth binding that the codebase itself applies elsewhere) rather than a demonstrated end-to-end exploit chain within this repository alone.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) before using it to construct the `Session`/`HttpClient` request, so the token-exchange request host is always bound to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what a session token's `dest` claim contains.

### Proof of Concept
Not independently reproducible with unprivileged-internet-user access alone: it requires a validly-signed session token whose `dest` claim is not a trusted Shopify domain, which in this gem's normal operation can only be produced by Shopify's own session-token issuance (signed with the app's `api_secret_key`). No path was found in this repository letting an outside caller set an arbitrary `dest` value on a token that will still pass `JwtPayload`'s signature/`aud` check.
