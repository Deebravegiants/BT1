### Title
Malicious swap route can execute arbitrary pool code under the caller’s authorization context and steal wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The lending controller accepts opaque route bytes in `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, then invokes the configured router with a narrowly scoped input-transfer authorization. The route itself can place attacker-controlled pool code on the call stack; from that execution context, malicious code can request additional token transfers from the caller. If those transfers are included in the signed authorization tree, they execute against the victim’s wallet rather than being limited to the routed collateral.

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` authenticates `caller`, authorizes the account owner or delegate, and passes the opaque `swap` bytes through the withdrawal-and-swap path. [1](#0-0) [2](#0-1) 

The swap helper invokes `SwapAggregatorClient::execute_strategy` with the caller-supplied `StrategySwap`. [3](#0-2)  `StrategySwap` is only `Bytes`; the controller performs no venue, pool, token, or callback allowlisting before forwarding it. [4](#0-3) 

Before the router call, the controller authorizes exactly one token transfer of `amount_in` to the configured router. [5](#0-4)  That narrow grant constrains the controller’s intended input payment, but it does not constrain which contract code the route reaches afterward.

The project’s own authorization-boundary documentation states that route-selected pool and token code can run below the caller’s authorization and that a transfer performed by that code is recorded as a child of the caller’s authorization entry. [6](#0-5) 

### Impact Explanation
A crafted route can steal unrelated wallet tokens from a user who signs a poisoned authorization tree. The theft is not limited to the collateral supplied to `swap_collateral`: the malicious pool can add a child authorization for a different token and transfer the victim’s balance to the attacker.

This maps to the Compass issue’s bug class: attacker-controlled connection/route data changes the effective execution environment beyond the expected authentication flow, causing execution of attacker-chosen behavior under the victim’s approval. Here, the arbitrary “command” is arbitrary Soroban contract code reached through route-selected pool addresses.

### Likelihood Explanation
Exploitation requires the victim to invoke a malicious route and authorize the expanded invocation tree. A wallet or client that transparently signs simulated authorization trees without rejecting unexpected child invocations can expose the victim to the theft. The attacker needs no privileged role and can deploy the malicious pool contract themselves.

### Recommendation
Treat swap route data as executable attacker-controlled input, not only as pricing data.

At the protocol boundary, prefer a typed route structure with an allowlist of approved venue pool addresses, or reject routes that can invoke unapproved contracts. At minimum, transaction construction and wallets should decode the route and reject any caller authorization entry containing sub-invocations other than the expected token input transfer. The controller cannot remove Soroban’s authorization-tree risk by checking only its own measured input and output.

### Proof of Concept
1. The victim owns a lending account with collateral and also holds an unrelated wallet token.
2. The attacker deploys a pool-compatible contract whose swap entrypoint returns enough output to satisfy the route while also invoking `wallet_token.transfer(victim, attacker, victim_balance)`.
3. The victim initiates:

```text
swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = collateral_asset,
    amount = collateral_amount,
    new = destination_asset,
    swap = route_referencing_attacker_pool
)
```

4. `process_swap_collateral` verifies the caller and account, withdraws collateral, and forwards the opaque route to the configured router. [2](#0-1) 
5. The router reaches the attacker’s pool. That pool calls the unrelated wallet token’s `transfer` function using the still-active caller authorization context.
6. Simulation records the malicious transfer as a child invocation of the victim’s `swap_collateral` authorization. A signing flow that accepts that tree enables the attacker’s pool to transfer the victim’s wallet token to the attacker, while the swap can still satisfy the controller’s positive-output and final-risk checks.

```rust
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```
