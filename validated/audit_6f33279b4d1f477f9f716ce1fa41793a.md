### Title
MemoizedKeychain#exportKey ignores `exportPublic:false` and serves cached xpub/publicKey - ([File: features/keychain/module/memoized-keychain.js])

### Summary
`MemoizedKeychain#exportKey` only branches on `opts?.exportPrivate` before consulting its public-key cache, completely ignoring `opts.exportPublic`. If a caller previously exported a key with `exportPublic: true`, a later call for the same `keyId` with `exportPublic: false` will still return the cached `{xpub, publicKey}` pair instead of the `{xpub: null, publicKey: null}` that the base `Keychain#exportKey` would produce.

### Finding Description
The base class enforces exact capability scoping: [1](#0-0) . When `exportPublic` is `false`, `publicKey` stays `null` and `xpub` is forced to `null` — no public key material is ever returned.

`MemoizedKeychain#exportKey`, however, decides whether to serve the cache purely based on `exportPrivate`, not `exportPublic`: [2](#0-1) . The cache itself stores only `{xpub, publicKey}` regardless of the `exportPublic` value used to populate it: [3](#0-2)  and [4](#0-3) .

Exploit flow:
1. Caller (or any earlier code path) calls `exportKey(keyId, { exportPrivate: false, exportPublic: true })`. This populates `#publicKeys[cacheKey]` with the real `{xpub, publicKey}`.
2. A subsequent caller calls `exportKey(keyId, { exportPrivate: false, exportPublic: false })`, explicitly opting out of public key disclosure.
3. Since `!opts?.exportPrivate` is `true` in both calls, the memoized wrapper short-circuits and returns the cached object from step 1, containing non-null `xpub`/`publicKey`, without ever calling `super.exportKey` (which would have returned nulls).

Any consumer (e.g., an RPC bridge or dapp-facing API) that relies on `exportPublic: false` to withhold public key data from a given code path/origin will instead receive real key material, because the memoization layer is capability-unaware.

### Impact Explanation
This is an over-disclosure of `xpub`/`publicKey` to a call site that explicitly requested minimal disclosure (`exportPublic: false`). In contexts where `exportKey` results are forwarded across a trust boundary (e.g., a bridge serving different origins/scopes with different disclosure needs), this breaks the minimal-disclosure invariant and can leak public key/xpub data to origins or code paths not entitled to it, undermining origin-scoped consent guarantees.

### Likelihood Explanation
The bug is deterministic and requires no privileged state — only two ordinary `exportKey` calls with the same `keyId`, first with `exportPublic: true` then with `exportPublic: false`. Any code path that inconsistently varies `exportPublic` per call for the same key (e.g. different callers/origins sharing the same keychain instance) triggers this reliably.

### Recommendation
Make the memoization cache key/lookup aware of the requested export scope, or explicitly re-check `opts.exportPublic` before returning cached data — e.g., only serve the cache when `exportPublic` is truthy, and otherwise fall through to `super.exportKey` (or synthesize `{ xpub: null, publicKey: null, ...}` when `exportPublic` is false) so the memoization layer never returns broader data than requested:

```js
exportKey = async (keyId, opts) => {
  if (!opts?.exportPrivate && opts?.exportPublic) {
    const cached = await this.#getCachedKey(keyId)
    if (cached) return cached
  }
  const result = await super.exportKey(keyId, opts)
  if (opts?.exportPublic) this.#setCachedKey(keyId, getPublicKeyData(result))
  return result
}
```
