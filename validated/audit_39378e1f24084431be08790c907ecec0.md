**Analysis:**

`TransactionSliceMetadata::is_immediately_after` is used exclusively as a heuristic to decide whether the block-executor's module/type cache should be flushed between transaction slices — it is not a custody or transaction-validity gate. [1](#0-0)  Its only effect is whether cached verified Move modules are reused or reloaded; it never determines whether a transaction is executed, re-executed, or committed to the ledger.

Actual chunk-continuity and duplicate-execution protection during state sync/replay is enforced independently of this metadata:

1. Incoming chunks (`TransactionListWithProofV2`/`TransactionOutputListWithProofV2`) must carry a valid Merkle accumulator proof against a `verified_target_li` (a signed `LedgerInfoWithSignatures`) before being enqueued — this is real cryptographic validation, not something a `Chunk { begin, end }` value alone can satisfy. [2](#0-1) [3](#0-2) 
2. Before enqueuing, `enqueue_chunk` asserts the chunk's declared `first_version` equals `parent_state.next_version()`, which comes from actual committed DB/state-store progress — not from any attacker-suppliable field — and fails loudly if it does not match. [4](#0-3) 
3. Final commit re-checks this invariant again against `next_version` from the state store before any writes are persisted. [5](#0-4) 

The `Chunk { begin, end }` values in `TransactionSliceMetadata` passed to `DoGetExecutionOutput::by_transaction_execution` (e.g., in `verify_execution`) are computed internally by the chunk executor from already-proof-verified version ranges, not supplied directly as unprivileged/untrusted input. [6](#0-5) [7](#0-6)  There is no unprivileged transaction, package, view, authenticator, API, or bytecode entrypoint that lets an attacker directly set `begin`/`end` and have it substitute for the proof-verified, state-store-derived version checks. Even if `is_immediately_after` returned a false positive, at worst it would cause stale/incorrect module cache reuse (a cache-consistency concern already mitigated by separate environment/hash checks), not re-execution or duplicate write-set application of a committed transaction — because the actual "what to execute" data path is gated by the version-equality assertion against real DB state and the accumulator proof, both of which are independent of this enum's `is_immediately_after` helper.

Since the described exploit requires bypassing cryptographic proof verification and the `parent_state.next_version()` equality check — neither of which is reachable or aliasable via unprivileged input — this does not cross a real custody boundary.
