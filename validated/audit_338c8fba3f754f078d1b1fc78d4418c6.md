### Title
Front-runnable, market-seeded AMM pool PDA allows permanent griefing/DoS of `Initialize2` for a targeted market - (File: `program/src/processor.rs`)

### Summary
The Raydium AMM pool's core accounts (`AmmInfo`, `TargetOrders`, LP mint, coin/pc vaults) are derived as PDAs seeded **only** by the OpenBook/Serum `market` account key and a fixed seed suffix — not by the token mints, the initializer, or any user-supplied nonce/salt. Because the target `market` account is a plaintext, publicly known parameter of any `Initialize2` transaction, an attacker can observe a pending pool-creation transaction in the mempool and front-run it with their own `Initialize2` call using the same `market` account (paired with attacker-chosen mints and minimal funding). Once the deterministic PDA accounts are created and assigned to the program, every subsequent legitimate `Initialize2` attempt for that same market permanently fails with `RepeatCreateAmm`, since the account is no longer owned by the System Program.

### Finding Description
`Processor::generate_amm_associated_account` derives the pool-related PDAs solely from `[program_id, market_address, associated_seed]`: [1](#0-0) 

This helper is used for the `AmmInfo` account and `TargetOrders` account (and the analogous `generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` for LP mint and vaults) purely keyed off the `market_info` account, which the code's own comments describe as "Just a seed for AMM account. Can be any account.": [2](#0-1) [3](#0-2) 

Once created, if the associated account is not owned by the System Program anymore, the instruction unconditionally fails: [4](#0-3) 

Because the PDA depends only on the market key (not on the coin/pc mints the legitimate creator intends to use, nor on the creator's identity), any party who sees a pending `Initialize2` transaction targeting a given market can submit a competing `Initialize2` with the same `market_info` account (using arbitrary/worthless mints and the minimum required funding/fee) and win the race. This permanently claims the deterministic `AmmInfo`/`TargetOrders`/LP-mint/vault PDAs for that market, so every future legitimate `Initialize2` for that exact market will hit `AmmError::RepeatCreateAmm` and can never succeed through this program.

This is the same bug class as the referenced report: a value that should be a globally unique, protocol-critical identifier (here, the market→pool PDA binding) is derived from public, attacker-observable input with no uniqueness reservation mechanism, enabling front-running to permanently block the legitimate operation for that identifier.

### Impact Explanation
This allows a griefer to permanently deny a specific project/market from ever launching an official Raydium AMM pool for that OpenBook/Serum market — a project could be extorted or sabotaged by having its market's PDA "squatted" the moment its pool-creation transaction becomes visible, at low cost to the attacker (they only need to pay the create-pool fee and provide minimal non-zero mint balances for a token pair they control). Since the affected accounts (`AmmInfo`, vaults, LP mint) are permanently occupied and there is no re-initialization/close path exposed to the legitimate market, this is a persistent denial-of-service on core pool-creation functionality tied to that market, analogous to and matching the severity of the reported bounty-ID-squatting DoS.

### Likelihood Explanation
Likelihood is high in practice: pool creation transactions are broadcast publicly before confirmation, the `market` account is a required, visible instruction argument, and the PDA derivation logic in `get_associated_address_and_bump_seed`/`generate_amm_associated_account` is fully deterministic and public. No privileged access is needed — any unprivileged actor with a wallet and minimal token balances can execute the front-run in a single transaction using attacker-chosen accounts and data, consistent with the required attack surface (`Initialize2`).

### Recommendation
Avoid deriving pool PDAs from a value (the market account) that is both attacker-observable pre-confirmation and not bound to the intended creator or mint pair. Options include:
- Incorporate the coin/pc mint pair (or a creator-committed, unpredictable value/hash) into the PDA seed alongside the market, so squatting a market with unrelated/worthless mints does not block the legitimate mint pair.
- Add a commit-reveal or reservation scheme (e.g., require the creator to first reserve the market with a signed, mint-specific commitment) before allowing `Initialize2` account creation.
- Allow the legitimate market/mint owner (or original committer) to reclaim/close a squatted `AmmInfo` PDA that was created with dust/invalid liquidity, restoring the ability to initialize the intended pool.

### Proof of Concept
1. Legitimate user Alice submits `Initialize2` for `market M` intending to create a pool for mints `X`/`Y`, with `amm_pool`, `amm_target_orders`, `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault` all derived via `get_associated_address_and_bump_seed(program_id, M, seed, program_id)` per `program/src/processor.rs:112-126` and `program/src/processor.rs:592-594`.
2. Attacker Bob observes Alice's pending transaction (public `market` key `M`) in the mempool and constructs his own `Initialize2` instruction using the same `market_info = M`, but arbitrary mints `A`/`B` he controls and minimal (e.g., 1 unit) initial liquidity, computing the same deterministic PDAs.
3. Bob's transaction lands first (front-run), executing `generate_amm_associated_account` and friends successfully, assigning ownership of the `AmmInfo`/`TargetOrders`/LP-mint/vault PDAs for market `M` to the AMM program per `program/src/processor.rs:499-544`.
4. Alice's original transaction (or any future retry for market `M`) now fails at the ownership check in `generate_amm_associated_account`, returning `AmmError::RepeatCreateAmm` per `program/src/processor.rs:541-544`, permanently blocking pool creation for market `M` through this program.
