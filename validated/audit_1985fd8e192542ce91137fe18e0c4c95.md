### Title
Webhook shop/topic/webhook_id identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers when dispatching to the merchant's handler. Because these identity fields are never included in the HMAC-signed string, and because the signing secret (`api_secret_key`, the app's shared client secret) is identical for every shop that installs the app, a party that legitimately receives one valid signed webhook body for their own shop can replay those exact bytes to the app's webhook endpoint while forging the `shop-domain` (and `topic`/`webhook-id`) headers to name a different, victim shop.

### Finding Description
The equality the gem is supposed to enforce is:

`shop attributed to the webhook by the handler == shop that Shopify actually generated/authenticated this signed payload for`

Tracing the code:

- `Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` [1](#0-0) .
- For webhooks, `to_signable_string` returns only `@raw_body` — none of the Shopify-supplied identity headers are part of the signed string [2](#0-1) .
- `shop`, `topic`, and `webhook_id` are all read straight from headers, independent of the HMAC [3](#0-2) .
- `Registry.process` validates only the HMAC of the body, then immediately builds `WebhookMetadata` (which becomes the trust boundary the merchant's handler code operates on) using `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of what was authenticated [4](#0-3) .
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field that is handed to the host app's handler as the tenant identifier [5](#0-4) .

Because `api_secret_key` is the app-level client secret — the same value used for every shop that has installed the app, not a per-shop credential (see `Utils::HmacValidator.validate` using `Context.api_secret_key` globally, and its use in OAuth exchange [6](#0-5) ) — any user who installs the app on their own shop can obtain a validly HMAC-signed webhook body (e.g. for a topic whose JSON body contains no shop-identifying fields, such as `app/scopes_update` or many `customers/*`/`shop/*` payloads). That body + HMAC pair remains valid for *any* headers, since the headers are outside the signed content. Replaying the identical bytes with a spoofed `X-Shopify-Shop-Domain` (and matching `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) passes `HmacValidator.validate` unchanged and causes the handler to execute believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is meant to provide to host applications: the one guarantee `Registry.process` is supposed to offer callers is "this event body came from Shopify for this shop." Instead it only guarantees "this body came from Shopify for *some* shop that shares this app's secret." Any host application that uses `WebhookMetadata#shop` to select which merchant's data to mutate, disable, or resync (a normal and encouraged use per the gem's docs) can be tricked into performing that action against a different merchant's tenant — i.e., cross-tenant access/action confusion, which maps to the Critical/High bucket of "cross-tenant access."

### Likelihood Explanation
The prerequisite — being able to install the public app on one's own shop and receive at least one legitimately signed webhook — is available to any unprivileged internet user for apps distributed publicly (App Store or dev stores), satisfying the "unprivileged internet user" threat model. No access token, `api_secret_key`, or privileged account is needed; only a normal shop installation of the target app.

### Recommendation
Include the identity fields that the application will act on (`shop`, `topic`, `webhook_id`) in the HMAC-signed content used for webhook verification, or otherwise cryptographically bind them (e.g., derive/verify them from a per-shop secret or from Shopify's separately-authenticated webhook subscription metadata) before exposing them to `WebhookHandler#handle`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must not be trusted as a tenant key without additional verification (e.g., cross-checking against the shop associated with the stored `webhook_id`/subscription).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action for any public Shopify app).
2. Attacker triggers/receives a legitimate webhook whose JSON body contains no shop-identifying data (e.g. `app/scopes_update`), capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs the exact same body `B` and header `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if needed, a `X-Shopify-Webhook-Id` known/guessed for the victim).
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) .
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", ...)` and invokes the host app's handler with this forged tenant identity [4](#0-3) , causing any shop-scoped side effect in the handler to run against the victim shop instead of the attacker's.
