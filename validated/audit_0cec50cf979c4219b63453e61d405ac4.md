Based on my investigation, the strongest analog to the "anyone can create a vault by directly calling the factory" bug class exists in the QR-code signup-extension handling path.

### Title
Unauthenticated signup extension QR-code bypasses backend user validation and biometric pipeline, allowing a self-attested "successful" signup - (File: src/plans/mod.rs)

### Summary
The Mochi bug is a missing-authorization issue: a function intended only for a privileged caller (`engine`) can be called directly by any unprivileged actor, and the resulting object is then trusted as valid by the rest of the system because validity is determined purely by a self-consistent address computation rather than by checking who created it. The orb-core analog is in the signup-extension ("data acquisition") code path: when both the operator and user QR-codes assert `signup_extension` with a `signup_extension_config`, `handle_user_qr_code` accepts the pair and returns a locally-fabricated `UserData::default()` instead of the backend-authenticated data returned by `verify_user_qr_code`/`backend::user_status::request`. Downstream, `do_signup` treats the presence of `signup_extension_config` as sufficient to mark the signup `success = true`, skipping the biometric pipeline and fraud detection entirely.

### Finding Description
`qr_scan::user::Data::try_parse` accepts a `QR_CODE_SIGNUP_EXTENSION`-formatted string and sets `signup_extension: true` with an attacker-controlled `signup_extension_config` (`mode`, `parameters`), purely from regex-parsed QR text with no cryptographic or backend authentication: [1](#0-0) 

In `handle_user_qr_code`, if *both* the operator and user QR-codes declare `signup_extension()` and a `signup_extension_config` is present, the code short-circuits normal validation and returns a default/unauthenticated `UserData`, bypassing the backend call to `verify_user_qr_code`: [2](#0-1) 

Similarly, `verify_operator_qr_code` short-circuits the operator-side backend validation call entirely when `qr_code.signup_extension()` is true, fabricating a location-data response locally instead of querying the backend: [3](#0-2) 

Finally, in `do_signup`, once a capture is obtained, the presence of `debug_report.signup_extension_config` alone is enough to mark the entire signup `success = true` and return early — skipping `biometric_pipeline`, `detect_fraud`, and all backend PCP upload/verification logic that normally establishes a legitimate signup: [4](#0-3) 

This mirrors the vault-factory bug class: a code path meant to be reached only under a controlled/privileged condition (here, presumably an internal data-acquisition/testing mode) is instead reachable directly from external, self-attested input (a scanned QR code string), and once reached, the system treats the resulting state (a "successful" signup) as if it had gone through the normal trust-establishing process (backend authentication + biometric pipeline).

The gating mechanism is the `internal-data-acquisition` Cargo feature, which is compiled into and used by production binaries/agents (`src/bin/orb-core.rs`, `src/agents/image_notary.rs`, `src/agents/image_uploader.rs`, `src/brokers/orb.rs`, `src/plans/idle.rs`) rather than being test-only code: [5](#0-4) 

I was not able to fully verify within the available index whether the `internal-data-acquisition` feature is enabled in the standard field-deployed orb binary or only in a separate "data acquisition orb" build variant, nor could I confirm what additional runtime gate (e.g., `self.data_acquisition` flag, provisioning, or operator-side authorization) restricts who can present such a QR code in practice — this would need to be checked with full access to `Cargo.toml`'s feature build matrix and deployment configuration, which the current index only partially exposes.

### Impact Explanation
If this feature is compiled into a fielded orb and no other out-of-band control restricts who can present a "signup extension" QR-code pair, an unprivileged party (anyone able to generate/print two QR codes matching the regex) can cause the orb to record a "successful" signup without any real biometric capture verification, backend authentication, or fraud checks — directly analogous to creating a "vault" that the rest of the protocol will treat as valid despite bypassing the intended privileged creation path. This could lead to misattributed/fraudulent signup records and bypassing of liveness/fraud enforcement.

### Likelihood Explanation
Likelihood is contingent on the `internal-data-acquisition` feature being present in production orb builds and on the absence of an independent operator-authentication gate for entering this branch. Given the feature is referenced throughout core production modules (agents, brokers, bin), it does not appear to be a test-only `#[cfg(test)]` path, but I could not confirm the exact build/release configuration that determines whether this code ships active in customer-facing orbs.

### Recommendation
- Ensure the `signup_extension` / data-acquisition QR bypass path can never be reached by unauthenticated, self-attested QR content in production builds; require the same backend authentication (`verify_operator_qr_code` / `verify_user_qr_code`) even when `signup_extension_config` is present, or cryptographically sign/authenticate the QR payload.
- If this path is intended strictly for internal/controlled data-acquisition sessions, gate it with an explicit, backend-verified authorization check (e.g., a signed token from the backend, not merely QR text controlled by whoever prints the code) rather than relying solely on a compile-time feature flag and QR regex match.
- Do not allow `signup_extension_config.is_some()` alone to set `result.success = true` and skip fraud/pipeline checks; require a positive backend confirmation before treating the signup as any kind of valid/successful outcome.

### Proof of Concept
Not executable from the current context (no runtime/build access). Conceptually: generate two QR-code strings matching `QR_CODE_SIGNUP_EXTENSION` (`userid:<id>:<policy>::<mode>[:<params>]::`) — one for "operator" and one for "user" — with a valid `mode` value, present them to the orb in sequence during a signup flow built with the `internal-data-acquisition` feature enabled. Per `handle_user_qr_code`/`verify_operator_qr_code`, both backend validation calls are skipped, and per `do_signup`, the signup completes with `success = true` without biometric pipeline or fraud detection, illustrating the unauthorized bypass of the intended trust-establishment path.
