### Title
Webhook shop-domain and topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature (`to_signable_string`) over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used by the host application to route and attribute the webhook are read directly from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` only proves that the body bytes were signed by Shopify's shared secret — it proves nothing about which shop or topic that signature was intended for.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But the identity fields consumed downstream — `shop`, `topic`, `webhook_id`, `api_version` — come straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC of the body and then hands the unauthenticated `shop`/`topic` values straight to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac-covered bytes == (shop, topic, body)` for the webhook to be attributable to a specific tenant. Instead the binding is only `hmac-covered bytes == body`, i.e. `shop`/`topic` are "a field acted on but not covered by the HMAC." Any entity capable of triggering a legitimate webhook delivery for a body they control (e.g. a merchant who installed the app on their own store and can produce arbitrary resource bodies via the Admin API) can capture the resulting `(body, hmac)` pair from a genuine Shopify-signed webhook and replay that exact pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header value. Because the signature never covered those headers, `HmacValidator.validate` still returns true, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain rather than the shop that actually owns the token/secret pairing that produced the signature.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as returned by this gem) to select which tenant's data/session to mutate — the normal and documented usage pattern — an attacker who controls the body content of any webhook-eligible resource in their own store can force the app to process that payload under an arbitrary victim shop identity. This is a cross-tenant identity crossing entirely enabled by this gem's signature scope, not by application misuse of a documented API: the gem itself exposes `shop`/`topic` as trusted fields derived from headers that its own `HmacValidator` never authenticates.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own working, unprivileged merchant account with the target app installed (to legitimately trigger a webhook and observe a real `(body, hmac)` pair), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No access token, `client_secret`, or privileged account is needed — this is reachable by any merchant who can install the app, which satisfies the "unprivileged internet user" threshold for this class of finding.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the value that is HMAC-validated, or otherwise cryptographically bind them to the signed body (e.g., validate that the `shop-domain` header matches the `dest`/tenant the receiving endpoint expects before trusting `WebhookMetadata#shop`). At minimum, document that `Webhooks::Request#shop` and `#topic` are unauthenticated and must not be used as the sole tenant selector without an out-of-band binding (e.g., matching against the URL path/shop context already established by the app).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and legitimately triggers a webhook whose body they control (e.g., updates a product they own) causing Shopify to POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
2. Attacker captures `raw_body` and the valid `x-shopify-hmac-sha256` value from this genuine delivery.
3. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` to the same app endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` compute the signature over `raw_body` only [4](#0-3) , so `HmacValidator.validate` returns `true`.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` [5](#0-4) , causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
