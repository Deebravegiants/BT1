Confirmed: there is no rescue/sweep mechanism for LT donated directly to the curve `Pair` before graduation. `Router.graduate` (the only function that can move the pair's `assetToken` balance out) is `onlyRole(BONDING_ROLE)` and is only ever invoked once, from `Bonding._prepareGraduationLiquidity`, with an explicit `amount = assetReserve - virtualLtReserve` rather than the live balance [1](#0-0) . ### Title
Direct LT transfers to the curve `Pair` are permanently unrecoverable — no donation-sweep exists (analog: Ledger `xcKSM` stuck-funds report) - (File: `packages/contracts/src/Pair.sol`, `packages/contracts/src/Router.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
Any address can `IERC20(lt).transfer(pair, amount)` directly to a token's bonding-curve `Pair` before or after graduation. Unlike `FeeVault`, which has a permissionless `sweepDonations()` to recover unbacked USDC [3](#0-2) , `Pair`/`Router`/`Bonding` provide no equivalent path to reclaim donated LT — it is permanently stranded in the `Pair` contract.

### Finding Description
`Pair.transferAsset` is the only function capable of moving the pair's LT balance out, and it is gated `onlyRouter` [4](#0-3) . The sole caller is `Router.graduate`, itself gated `onlyRole(BONDING_ROLE)` [5](#0-4) . `Bonding` calls `graduate` exactly once per token, from `_prepareGraduationLiquidity`, passing an explicit `ltFromPair = assetReserve - virtualLtReserve` computed from the pair's *stored* reserves, not its live `balanceOf` [6](#0-5) . This is intentionally donation-resistant for the graduation math, but it means any LT sent directly to the pair (via a plain ERC20 `transfer`, not through `Router.buy`/`sell`) never updates `_pool.assetReserve` and is never captured by `ltFromPair`. Once the token's lifecycle passes `Curve` (into `Graduating`/`Graduated`), `_prepareGraduationLiquidity`/`graduate` becomes unreachable for that token forever, per the code's own note that the leftover is "unreachable... as long as... future `Bonding` upgrades preserve the lifecycle gate" [7](#0-6) . There is no owner-only or permissionless rescue/sweep function on `Pair`, `Router`, or `Bonding` for this donated LT — contrast this with `FeeVault.sweepDonations()`, which exists specifically to solve the analogous problem for USDC [3](#0-2) .

### Impact Explanation
Any LT accidentally or intentionally sent directly to a curve `Pair` (e.g., a user mistakenly using a raw `transfer` instead of `Zap.buy`, or a bot/arbitrage script mis-targeting the pair address) is permanently frozen with no recovery path for the sender, the token creator, or the protocol. This is a permanent freezing of funds, satisfying the Medium/High bar. The amount at risk scales with any leveraged-token (LT) value sent, and there is no cap — a large accidental transfer results in total, irrecoverable loss.

### Likelihood Explanation
Likelihood is moderate: this requires a user or bot to send LT directly to the `Pair` contract address rather than going through `Zap`/`Router`. This is plausible because pair addresses are publicly discoverable (`IUniswapV2Factory`-style `getPair`) and non-technical users or automated scripts unfamiliar with the curve's on-chain accounting could easily make this mistake, exactly as described in the external Ledger report where a mis-sent asset became permanently stuck.

### Recommendation
Add a permissionless sweep function, mirroring `FeeVault.sweepDonations()`, that computes `IERC20(assetToken).balanceOf(pair) - _pool.assetReserve` (the unbacked LT donation) and forwards it to a fee/treasury recipient (or refunds via an owner-attested claim process) both pre- and post-graduation, gated so it can never touch the accounted `assetReserve`.

### Proof of Concept
1. A token is launched via `Bonding.launch`, creating a `Pair` with `assetToken = LT`.
2. Before (or after) the token graduates, any address calls `IERC20(lt).transfer(pairAddress, X)` directly (not through `Zap.buy`).
3. `_pool.assetReserve` in `Pair` is unchanged (only `Pair.swap`/`mint`, both `onlyRouter`, can mutate it) — see `Pair.sol` lines 65-79 and 26-63 (mint) — so the donated `X` LT sits in the pair's `balanceOf` but outside `assetReserve`.
4. On graduation, `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve`, which by construction excludes `X` [8](#0-7) .
5. After graduation, `Router.graduate` can never be called again for this token (lifecycle gate), and no other function can extract LT from the now-abandoned `Pair`. `X` LT is permanently lost.

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

    ///         direct USDC transfers would otherwise inflate `balanceOf` above

        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
