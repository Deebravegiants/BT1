### Title
Withdrawals can permanently revert via `calc_take_pnl`'s unconditional `CalcPnlError`, freezing LP funds unless a privileged status change is made - (File: `program/src/processor.rs`)

### Summary
Both `Deposit` and `Withdraw` unconditionally call `Processor::calc_take_pnl`, which reverts the whole instruction with `AmmError::CalcPnlError` whenever the current pool invariant `k` falls below the previously recorded PnL invariant. This mirrors the referenced Tapioca report pattern: an essential, users-facing operation (there: liquidation; here: LP withdrawal) is wired to an internal computation that can revert, and the only sanctioned bypass is a privileged action (there: returning stale oracle rate; here: an admin switching the pool to `WithdrawOnly` status), which a regular LP cannot trigger themselves.

### Finding Description
`calc_take_pnl` compares `pool_pc_amount * pool_coin_amount` (current k, net of already-recognized PnL) against `calc_pc_amount * calc_coin_amount` (the k recorded the last time PnL was taken, restored to native decimals) [1](#0-0) . If the current invariant is smaller than the recorded one, the function does not attempt any fallback and instead unconditionally returns `Err(AmmError::CalcPnlError)` [2](#0-1) .

`Withdraw` calls this function on every invocation except when the pool status is exactly `WithdrawOnly` [3](#0-2) , and `Deposit` calls it unconditionally with no status guard at all [4](#0-3) . `AmmStatus::WithdrawOnly` can only be set by a privileged admin instruction (e.g. `SetParams`), not by an ordinary LP submitting a withdraw transaction. Consequently, if the pool ever reaches a state where current `k` is below the recorded PnL `k` (which can occur through normal trading/rounding drift over the pool's lifetime, since `target.calc_pnl_x`/`calc_pnl_y` are only updated when PnL is actually taken), every subsequent `Withdraw` transaction from any LP reverts with `CalcPnlError` until an admin manually flips the pool to `WithdrawOnly`.

This directly parallels the referenced bug class: a critical, user-reachable operation is gated behind an internal invariant check that reverts instead of degrading gracefully, and recovery requires a privileged out-of-band action rather than being self-healing within the instruction itself.

### Impact Explanation
If the invariant condition trips, LPs lose the ability to withdraw their funds through the normal instruction path. Since the `swap` instructions do not call `calc_take_pnl` at all (only `Deposit`/`Withdraw` do), trading can continue to push `k` further away from the recorded PnL value while withdrawals remain blocked, and deposits (which have no `WithdrawOnly` bypass at all) would be permanently broken until intervention. This constitutes a freezing of LP funds in-protocol, dependent entirely on an admin taking action to change pool status — analogous to the referenced report's insolvency risk from an essential path (liquidation there, withdrawal here) being blockable by an internal revert condition.

### Likelihood Explanation
Likelihood is uncertain without deeper analysis of exactly how `target.calc_pnl_x`/`calc_pnl_y` are maintained relative to vault balances over the pool's full lifecycle (deposits/withdrawals/order-book interactions), which was not fully traced in this review. The `>=` check is defensive by design (it exists specifically to detect an abnormal state), so triggering it likely requires atypical pool conditions (e.g., large asymmetric trading activity, rounding accumulation, or order-book-driven balance changes) rather than a single trivial user transaction. This should be validated against the full lifecycle of `target_orders` updates before treating it as immediately exploitable.

### Recommendation
Do not let `calc_take_pnl` unconditionally revert the entire `Withdraw`/`Deposit` instruction when the invariant check fails. Instead, similar to the referenced report's fix (falling back to a safe/old value rather than reverting), consider skipping PnL-taking for that instruction (treat `delta_x`/`delta_y` as `0`, as already done in the "no significant PnL" branch) rather than returning `AmmError::CalcPnlError`, so that user-facing `Deposit`/`Withdraw` always succeed even if the internal PnL bookkeeping cannot be updated that block. Reserve the hard error for privileged/administrative code paths only.

### Proof of Concept
No on-chain PoC was constructed. The control-flow trace establishing the finding is:
1. `Withdraw` unconditionally invokes `calc_take_pnl` unless `amm.status == WithdrawOnly` [5](#0-4) .
2. `Deposit` unconditionally invokes `calc_take_pnl` with no status bypass [4](#0-3) .
3. `calc_take_pnl` reverts with `AmmError::CalcPnlError` whenever current k is below the recorded PnL k [6](#0-5) .
4. Reaching this branch causes every subsequent `Deposit`/`Withdraw` transaction to fail on-chain until an admin sets `AmmStatus::WithdrawOnly` (for `Withdraw` only — `Deposit` has no bypass at all), which an ordinary user cannot self-trigger.
