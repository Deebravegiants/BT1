### Title
PoA Bridge `describeWithdrawal` matches withdrawal status by `assetId` only, misreporting completion/tx-hash for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`processWithdrawal`/`waitForWithdrawalCompletion` support batches of `WithdrawalParams[]` in a single NEAR intent transaction [1](#0-0) . When two or more of these batched withdrawals use the **same PoA-bridged `assetId`** (e.g., two different destination addresses/amounts withdrawing the same token in one tx), `PoaBridge.describeWithdrawal` resolves each of them by calling `findMatchingWithdrawal`, which matches purely on `assetId` and ignores `index`/destination/amount [2](#0-1) .

### Finding Description
`findMatchingWithdrawal` is explicitly documented as only distinguishing withdrawals by `assetId`: [3](#0-2) 

Because the PoA bridge status API returns an unsorted `withdrawals` array keyed by `near_token_id`/`defuse_asset_identifier` and not by index or destination address, when a single NEAR transaction contains two withdrawal intents for the same `assetId` (different destination addresses/amounts), `describeWithdrawal({..., index: 0, ...})` and `describeWithdrawal({..., index: 1, ...})` both invoke `findMatchingWithdrawal(withdrawals, assetId)`, which calls `.find()` and returns the **first** array element matching that `assetId` — regardless of which index/withdrawal it actually corresponds to [4](#0-3) .

This breaks the equality "status/txHash reported == the on-chain outcome for *this specific* withdrawal": both `WithdrawalIdentifier`s for the two different destinations end up resolving to the identical `withdrawal` record (same `transfer_tx_hash`, same `status`). If one of the two withdrawals completes on-chain first, both `waitForWithdrawalCompletion` promises (one per index) will resolve as `{status: "completed", txHash: withdrawal.data.transfer_tx_hash}` using the same underlying data — even though only one of the two real underlying transfers has actually happened. The consumer (integrator) has no way to tell them apart via the SDK's returned status, since the mapping intentionally collapses to assetId only.

`createWithdrawalCompletionPromises`/`watchWithdrawal` treat each index's resolved promise independently, so an integrator polling per-withdrawal or crediting on completion could act on both indices as "completed" using the same txHash/status data, even though the actual second on-chain transfer may still be pending or use a different tx hash.

### Impact Explanation
For integrators that batch multiple withdrawals of the same PoA-bridged asset within one intent (a supported SDK code path via `withdrawalParams: WithdrawalParams[]`), this can cause the SDK to report a `completed` status (with a`txHash`) for a withdrawal that has not actually completed to its intended destination, or that another withdrawal's tx hash gets attributed to the wrong destination/withdrawal. This matches "a status or hash misreport making an integrator credit or refund twice" (High impact) since a caller could release/attribute funds off-chain for two distinct destinations based on a single actual completed transfer.

### Likelihood Explanation
Requires only normal (unprivileged) SDK usage: submitting a batch of withdrawals in one NEAR transaction where two or more entries share the same PoA `assetId` (e.g., two users withdrawing the same token, or same user withdrawing to two addresses). No malicious peer, admin, or bridge-operator behavior is needed — it's purely a client-side matching bug reachable through the documented batch API. It is explicitly acknowledged as an unhandled limitation in the code comment, confirming the root cause and its current lack of mitigation.

### Recommendation
Extend the PoA bridge withdrawal-status matching to disambiguate withdrawals sharing the same `assetId` in a batch — e.g., match by destination address and amount (as the code comment already suggests, sorting both sides by amount) rather than by `assetId` alone. At minimum, detect the ambiguous case (multiple withdrawals with the same `assetId` in one tx) and refuse to report `completed` for any of them until the API can disambiguate (or the amounts/destinations differ enough to match uniquely), rather than returning the first match to all callers.

### Proof of Concept
1. Submit a `processWithdrawal`/`signAndSendWithdrawalIntent` batch with two `WithdrawalParams` entries, both using `assetId: "nep141:zec.omft.near"`, but with different `destinationAddress` (A and B) and different `amount`.
2. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [paramsA, paramsB], intentTx })`.
3. Internally, for each index, `PoaBridge.describeWithdrawal` calls `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: tx.hash })`, which can return two `withdrawals[]` entries (one per intent), both with `near_token_id: "zec.omft.near"`.
4. `findMatchingWithdrawal(withdrawals, "nep141:zec.omft.near")` returns the same first element for both index 0 and index 1 calls (see `poa-bridge.test.ts` test "matches withdrawal by assetId, not by index", which documents and asserts this exact behavior for the single-match case) [5](#0-4) .
5. If withdrawal A completes on-chain first (status `COMPLETED`, `transfer_tx_hash: X`) while B is still pending, both index-0 and index-1 promises resolve `{status: "completed", txHash: X}`, misreporting B as completed with A's transaction hash.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
	}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
