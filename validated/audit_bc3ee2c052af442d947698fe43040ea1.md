### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content solely from the raw HTTP body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC computation. `Registry.process` validates only `Utils::HmacValidator.validate(request)` — an HMAC over the body — and then unconditionally trusts `request.shop` when building the `WebhookMetadata` object passed to the host application's webhook handler.

### Finding Description
The identity binding broken here is: `HMAC(body, api_secret_key) valid` ⇏ `shop header == shop that produced body`. Because the `api_secret_key` is shared across all shops/stores that install a given app (it is not a per-shop secret), any actor who can install the app on their own store (an "unprivileged internet user" with respect to any other shop) can:
1. Install the app on an attacker-controlled shop and trigger any webhook topic they choose (e.g. by creating/updating a resource, or via `app/uninstalled`, `shop/redact`, etc.), producing a genuinely-signed `(raw_body, hmac)` pair signed with the real `api_secret_key`.
2. Capture that raw body and its valid `x-shopify-hmac-sha256` value.
3. Replay the request to the app's public webhook endpoint, keeping the body and HMAC unchanged, but swapping the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to a victim shop's domain.

`Utils::HmacValidator.validate` at `lib/shopify_api/utils/hmac_validator.rb:13-22` will pass because it only recomputes over `verifiable_query.to_signable_string`, which is just the raw body — untouched by the header swap. `Registry.process` at `lib/shopify_api/webhooks/registry.rb:189-199` then dispatches the handler with `WebhookMetadata` carrying the attacker-chosen `shop` value as if Shopify itself certified that binding. ### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to guarantee: `shop` is the identifier host applications use to route webhook side effects (data updates, deletions, redaction, uninstall handling, etc.) to the correct tenant's records. An attacker can forge a payload that the host application believes was authentically emitted by Shopify for a victim shop, while its content is fully attacker-controlled (since it originates from a webhook the attacker legitimately triggered on their own store). This satisfies the "Critical - cross-tenant access" bucket: an unprivileged, unauthenticated-with-respect-to-the-victim actor can cause the app to act on/for a different tenant using data that never actually came from that tenant.

### Likelihood Explanation
Likelihood is high for any app author who trusts `WebhookMetadata#shop` (as constructed by this gem) without independently re-verifying it against another out-of-band signal. The gem's own `Registry.process` performs no such independent binding — it explicitly treats `HmacValidator.validate(request) == true` as sufficient authorization to proceed with the header-derived `shop`. Any internet user who can install the target app on a shop they control (a normal, unprivileged flow) can generate valid `(body, hmac)` pairs and then freely target arbitrary shop domains by manipulating headers on a replayed HTTP request to the app's public webhook endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header-derived shop to the specific installation/secret that produced the body — e.g., validate that the resolved shop matches a shop-specific secret/session rather than a single global `api_secret_key`, or include the shop domain in the HMAC computation. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoping decisions without additional verification (e.g., correlating against a known installed-shop list before acting).

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`. Trigger a webhook (e.g. `products/update`) with attacker-chosen JSON body `B`. Shopify signs it: `hmac = HMAC-SHA256(api_secret_key, B)`.
2. Capture the resulting request headers/body from the attacker's own endpoint logs.
3. Send a new HTTP POST to the victim app's real webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: unchanged, valid `hmac`
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: unchanged or forged to a different registered topic
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because the HMAC only covers `B`. The handler executes with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, topic: ...)`, causing the host application to perform shop-scoped actions attributed to the victim shop using attacker-supplied data.
