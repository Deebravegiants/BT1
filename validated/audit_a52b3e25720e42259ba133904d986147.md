Audit Report

## Title
Unbounded, fee-exempt HRMP-notification flooding of `DownwardMessageQueue` bypasses `DeliveryFeeFactor` backpressure - ([File: polkadot/runtime/parachains/src/dmp.rs])

## Summary
`Pallet::<T>::queue_downward_message` only *records* congestion via `increase_fee_factor` once the queue length crosses a threshold; it never charges or throttles the caller inline. That fee factor is consumed exclusively by the priced XCM-send path (`ExponentialPrice::price_for_delivery`), while HRMP's `send_to_para` (used by `hrmp_init_open_channel`/`hrmp_accept_open_channel`/`hrmp_close_channel`) calls `queue_downward_message` directly with no fee dependency at all. This lets a parachain that controls both ends of a request/cancel cycle enqueue downward messages to a victim para repeatedly at a fixed cost that never scales with the resulting `DeliveryFeeFactor`, and once `dmq_max_length` is hit, `can_queue_downward_message` rejects new messages for everyone — including the priced/legitimate senders — while the attacker's own cancel/re-init cycle continues to succeed (the failure to enqueue is swallowed via `debug_assert!(false)`, a no-op in release builds).

## Finding Description
`queue_downward_message` enforces the hard cap in `can_queue_downward_message` and only bumps `DeliveryFeeFactor` bookkeeping after the queue length exceeds `dmq_max_length/THRESHOLD_FACTOR`; it performs no fee debit itself [1](#0-0) . `DeliveryFeeFactor` is only read/applied by `ExponentialPrice::price_for_delivery`, which is the pricing hook for the `ChildParachainRouter`/priced XCM-send path, not something `queue_downward_message` itself checks or requires [2](#0-1) .

HRMP's `send_to_para` calls `dmp::Pallet::<T>::queue_downward_message` unconditionally for channel-management notifications, and if that call fails because the queue is full, the failure is only logged and asserted with `debug_assert!(false)` — a no-op in release/production builds — so the caller's own state transitions proceed regardless [3](#0-2) . `init_open_channel` (invoked by the dispatchable `hrmp_init_open_channel`) requires only that no existing open request or channel exists for `(origin, recipient)` and that the origin has not exceeded `hrmp_max_parachain_outbound_channels` concurrent requests, then reserves a refundable deposit and sends the notification via `send_to_para` [4](#0-3) . `hrmp_init_open_channel` and `hrmp_cancel_open_request` are both dispatchable via `ensure_parachain` origin, i.e. triggerable by any parachain via UMP/Transact without relay-chain privilege [5](#0-4) [6](#0-5) . `verify_fee_factor_reaches_high_value` demonstrates that repeated `queue_downward_message` calls alone (independent of any payment) push the fee factor above `100_000_000` while the queue approaches `dmq_max_length` [7](#0-6) .

The core broken assumption is that `DeliveryFeeFactor`/congestion pricing is a universal backpressure mechanism on `DownwardMessageQueue` growth. In fact it is scoped only to the `ExponentialPrice`-priced send path; any other caller of `queue_downward_message` (such as HRMP's internal notification sends) is completely exempt from that cost, so it cannot be relied upon as a general anti-flooding control for the queue itself.

## Impact Explanation
Once a victim para's downward message queue is driven near `dmq_max_length` by repeated notification injection, `can_queue_downward_message` rejects further enqueue attempts for *all* senders, including governance/system messages and priced XCM sends, producing a denial-of-service on downward message delivery to that para [8](#0-7) . Simultaneously, legitimate senders using the priced path pay an inflated fee driven by the same congestion the attacker caused for free. This is a real, in-scope liveness/availability impact on message delivery to an arbitrary target parachain, driven purely by relay-chain runtime logic rather than any external or node-level failure.

## Likelihood Explanation
The only precondition is control of a single parachain capable of dispatching HRMP calls via `Origin::Parachain` (UMP/Transact) — a capability any parachain has by default, without governance or elevated privilege. The `hrmp_init_open_channel` → `hrmp_cancel_open_request` cycle is fully repeatable (deposit refunded on cancel, request-count slot freed), so the attacker can regenerate notifications toward the same victim indefinitely, bounded only by their own UMP/weight throughput rather than by the victim's rising fee factor, since the notification path never consults it.

## Recommendation
Tie HRMP-notification-triggered `queue_downward_message` calls to the same `DeliveryFeeFactor` congestion signal used for priced sends — e.g., require the initiating para to pay/burn a fee scaled by the target's current fee factor, or reject/rate-limit notification sends once a target para's queue is above the threshold. Additionally, harden `send_to_para`'s error handling so that a full queue is surfaced as a real dispatch error (rather than a release-mode no-op `debug_assert!`), and consider a cooldown or per-session cap on open/cancel cycles for the same `(origin, recipient)` pair to prevent cheap regeneration of notifications.

## Proof of Concept
Extend `dmp/tests.rs`'s `verify_fee_factor_reaches_high_value` pattern into an HRMP integration test: register attacker para `A` and victim para `V`; loop `hrmp_init_open_channel(A → V)` then `hrmp_cancel_open_request` for the same pair, asserting each cycle appends one DM to `V`'s queue while the attacker's reserved balance returns to baseline after each cycle; show `Dmp::dmq_length(V)` climbing to `dmq_max_length` and `DeliveryFeeFactor::<Test>::get(V)` growing to an extreme value; finally show that once at capacity, a simulated legitimate `queue_downward_message(V, ...)` call returns `Err(QueueDownwardMessageError::ExceedsMaxMessageSize)`, confirming the DoS on downward delivery to `V`.

	pub fn can_queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: &ParaId,
		msg: &DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len() as u32;
		if serialized_len > config.max_downward_message_size {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// Hard limit on Queue size
		if Self::dmq_length(*para) > Self::dmq_max_length(config.max_downward_message_size) {
			return Err(QueueDownwardMessageError::ExceedsMaxMessageSize);
		}

		// If the head exists, we assume the parachain is legit and exists.
		if !paras::Heads::<T>::contains_key(para) {
			return Err(QueueDownwardMessageError::Unroutable);
		}

		Ok(())
	}

	/// Enqueue a downward message to a specific recipient para.
	///
	/// When encoded, the message should not exceed the `config.max_downward_message_size`.
	/// Otherwise, the message won't be sent and `Err` will be returned.
	///
	/// It is possible to send a downward message to a non-existent para. That, however, would lead
	/// to a dangling storage. If the caller cannot statically prove that the recipient exists
	/// then the caller should perform a runtime check.
	pub fn queue_downward_message(
		config: &HostConfiguration<BlockNumberFor<T>>,
		para: ParaId,
		msg: DownwardMessage,
	) -> Result<(), QueueDownwardMessageError> {
		let serialized_len = msg.len();
		Self::can_queue_downward_message(config, &para, &msg)?;

		let inbound = InboundDownwardQueue::<T>::push_back(para, msg)
			.map_err(|_| QueueDownwardMessageError::ExceedsMaxQueueSize)?;
		let q_len = InboundDownwardQueue::<T>::len(para).unwrap_or(0);

		// obtain the new link in the MQC and update the head.
		DownwardMessageQueueHeads::<T>::mutate(para, |head| {
			let new_head =
				BlakeTwo256::hash_of(&(*head, inbound.sent_at, T::Hashing::hash_of(&inbound.msg)));
			*head = new_head;
		});

		let threshold =
			Self::dmq_max_length(config.max_downward_message_size).saturating_div(THRESHOLD_FACTOR);
		if q_len > threshold as u64 {
			Self::increase_fee_factor(para, serialized_len as u128);
		}

		Ok(())
	}

	fn send_to_para(

#[test]
fn verify_fee_factor_reaches_high_value() {
	let a = ParaId::from(123);
	let mut genesis = default_genesis_config();
	genesis.configuration.config.max_downward_message_size = 51200;
	new_test_ext_integrity(genesis, || {
		register_paras(&[a]);

		let max_messages =
			Dmp::dmq_max_length(ActiveConfig::<Test>::get().max_downward_message_size);
		let mut total_fee_factor = FixedU128::from_float(1.0);
		for _ in 1..max_messages {
			assert_ok!(queue_downward_message(a, vec![]));
			total_fee_factor = total_fee_factor + (DeliveryFeeFactor::<Test>::get(a));
		}
		assert!(total_fee_factor > FixedU128::from_u32(100_000_000));
	});
}
