Based on my analysis of the webhook processing flow, I found a valid analog to the reported bug class.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using only the HMAC of the raw request body, but the `shop` (and `topic`, `webhook_id`, `api_version`) values that the app's handler acts on are read directly from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the HMAC [3](#0-2) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

Because all shops installed on a given app share the same `client_secret` (the HMAC key), a raw body + HMAC pair that is valid for one shop is *also* a valid HMAC for any other shop — the body/HMAC pair carries no shop identity. The `shop` field the handler actually acts on is only supplied via a header that is completely outside the signed material. This is precisely the "field acted on but not covered by the HMAC" identity-binding violation: `Request#shop` (unauthenticated header) ≠ the value actually authenticated by `HmacValidator.validate` (only `@raw_body`).

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) Shopify store can legitimately trigger a webhook delivery for a topic whose body content is shop-agnostic (or attacker-controllable in a way that doesn't reveal shop identity), capture the raw body and its valid `shopify-hmac-sha256` value from their own store's webhook delivery, then directly POST that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the raw body against the app's `client_secret` — a value common to all installs. The app then executes the registered handler believing the event is scoped to the victim shop's `WebhookMetadata#shop` [5](#0-4) , causing cross-tenant confusion in host-application logic that keys database writes, deletions, or state transitions off of `data.shop` (e.g., mandatory compliance topics like `customers/redact`, `shop/redact` are registered through this exact registry [6](#0-5) ). This crosses a tenant boundary without requiring any of the app's actual secrets tied to the victim.

### Likelihood Explanation
Requires only the ability to self-install the app on an attacker-owned store to legitimately obtain one valid `(raw_body, hmac)` pair (no leaked credentials, no privileged access, no TLS interception), plus a plain HTTP POST to the app's public webhook callback endpoint with a forged header — well within reach of an unprivileged internet user.

### Recommendation
Bind the shop (and topic/webhook id) into the material that is verified, not just trusted from a header. For example, incorporate the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values into `to_signable_string` (or independently verify them against a shop-associated secret/session before dispatching to the handler), so the identity used to route/act on the webhook is cryptographically bound to the same signature that authenticates the payload.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, triggering a real webhook delivery for a topic with static/shop-agnostic body content (e.g. an empty-body or predictable-body topic).
2. Attacker's endpoint (or a proxy they control) captures the raw body `B` and the corresponding `shopify-hmac-sha256` header value `H` from that legitimate delivery — both valid under the app's shared `client_secret`.
3. Attacker sends a POST directly to the target app's webhook endpoint with headers `shopify-hmac-sha256: H`, `shopify-shop-domain: victim-shop.myshopify.com`, `shopify-topic: <same topic>`, and body `B`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `B` against `H` using the shared secret) [7](#0-6) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the host app to act as if the event originated from the victim shop.
