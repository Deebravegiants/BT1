### Title
Transient supply-cap stuffing can DoS `supply` for other users - ([File: contracts/controller/src/spoke_usage.rs](contracts/controller/src/spoke_usage.rs))

### Summary
The Carapace bug class — an attacker inflating a global accounting variable so a post-deposit ceiling check reverts for the victim, then undoing the inflation because there is no cooldown — maps onto XOXNO Lending's per-spoke supply cap. `SpokeUsageContext::apply_entry` enforces `SpokeAssetConfig.supply_cap` on every supply entry and reverts with `SpokeSupplyCapReached` once `usage + new_shares > cap_scaled`, while exits (`apply_exit`) are unchecked and there is no deposit→withdraw cooldown anywhere in the controller or pool. A single unprivileged address can fill the remaining cap headroom, cause every other depositor's `supply` to revert, and withdraw freely afterwards.

### Finding Description
Supply caps are tracked per `(spoke_id, HubAssetKey)` as scaled share usage. `apply_entry` calls `enforce_spoke_cap`, which converts the configured asset-unit cap into the scaled domain via `calculate_scaled_cap` and asserts `usage + delta <= cap_scaled`, reverting with `SpokeSupplyCapReached` otherwise (`contracts/controller/src/spoke_usage.rs:102-115`, `144-157`). [1](#0-0) [2](#0-1) 

Mirroring the report's leverage-ratio ceiling, the usage is minted into global state at supply time and only released on exit, and `apply_exit` never consults the cap (`spoke_usage.rs:119-139`). [3](#0-2)  Withdrawal is gated only by `require_reserves`, `require_utilization_below_max`, and `require_supply_for_debt` — no time-based cooldown or per-account lock exists (`contracts/pool/README.md` guards table; `contracts/controller/src/positions/supply.rs::settle_withdraw`). [4](#0-3)  In a low-utilization market, an attacker who supplies up to the cap can withdraw the entire amount in the next transaction, exactly like the report's open-cycle withdraw.

The attack:
1. Victim submits `supply(caller, account_id, ttl, payments=[(hub_asset, X)])` to the controller.
2. Attacker calls `supply` with `cap_headroom - epsilon` of the same `(hub, asset)`, pushing `supplied_scaled_ray` to the cap.
3. The victim's `supply` reverts `SpokeSupplyCapReached` (`next_scaled > cap_scaled`).
4. Attacker calls `withdraw` (amount 0 = withdraw-all sentinel) and exits; cap usage drops, and the attacker can repeat on any future deposit.

### Impact Explanation
Temporary denial of deposits for all other users of a spoke/asset market while the attacker holds the cap-filling position — the same user-facing impact as the reported bug (deposits revert while the attacker chooses to hold). Borrowers are also indirectly affected: they cannot add collateral via `supply` to defend a position approaching liquidation, which can turn the deposit DoS into a liquidation that would not otherwise have happened. The attacker's capital is recovered in full on withdraw (only rounding dust is lost), so the cost is opportunity cost of capital equal to the cap headroom.

### Likelihood Explanation
Feasible for any unprivileged address with sufficient balance of the asset; no privilege, oracle manipulation, or leaked key needed. It is weaker than the original in two respects: (a) Stellar has no public mempool sandwiching, so the attacker must hold the cap while victim transactions land rather than flash-frontrunning a single victim, requiring real capital roughly equal to the remaining cap headroom; (b) the cap is an intended admission limit, so "cap reached" alone is designed behavior. However, unlike a legitimate full market, a single actor cycling usage to selectively block others is an abuse the design does not mitigate, and the sized caps in `configs/mainnet/spokes.json` (e.g. 5M USDC) are within reach of whales/flash-capable treasury actors. Medium likelihood, Medium severity.

### Recommendation
Mitigations consistent with the codebase's existing shape:
- Enforce a per-account share of the cap (e.g. max fraction of `cap_scaled` per account), so one actor cannot consume all headroom.
- Alternatively add a short lockup/cooldown on newly minted supply shares (e.g. shares minted within N ledgers cannot be fully withdrawn), making cap-stuffing costly to sustain and impossible to cycle cheaply — the direct analog of the report's `block.number + 1` recommendation.
- At minimum, emit an event when a market is at/near cap so integrators can warn users before submitting `supply`.

### Proof of Concept
Using the test harness (`tests/test-harness`):

```rust
#[test]
fn supply_cap_stuffing_blocks_victim_deposit() {
    let mut t = LendingTest::new().standard_two_asset().build();
    // Legit user supplies; USDC supply_cap configured to e.g. 5M.
    t.supply(BOB, "USDC", 1_000.0);

    // Attacker fills the remaining cap headroom.
    let headroom = /* cap_scaled - usage at index, minus epsilon */;
    t.supply_raw(ATTACKER, "USDC", headroom);

    // Victim's supply reverts with SpokeSupplyCapReached.
    assert_contract_error(
        t.try_supply(ALICE, "USDC", 1.0),
        errors::SPOKE_SUPPLY_CAP_REACHED,
    );

    // Attacker withdraws everything in the next tx; no cooldown.
    let acct = t.resolve_account_id(ATTACKER);
    t.ctrl_client().withdraw(&attacker, &acct, &leg(&t, "USDC", 0), &None);

    // Now the victim can deposit again — the block was transient,
    // repeatable, and cost the attacker nothing but capital float.
    t.supply(ALICE, "USDC", 1.0);
}
```

The mechanics match `enforce_spoke_cap` reverting on `next_scaled > cap_scaled` (`spoke_usage.rs:153-156`) and the unrestricted exit path in `settle_withdraw`/`apply_withdraw_batch` (`contracts/controller/src/positions/supply.rs`).

```rust
    pub(crate) fn apply_exit(
        &mut self,
        side: UsageSide,
        hub_asset: &HubAssetKey,
        delta_scaled: Ray,
    ) {
        if delta_scaled == Ray::ZERO {
            return;
        }
        let Some(mut usage) = self.load_usage_row(hub_asset) else {
            return;
        };
        let next = side
            .scaled(&usage)
            .checked_sub(delta_scaled.raw())
            .unwrap_or_else(|| panic_with_error!(&self.env, GenericError::MathOverflow));

        assert_with_error!(&self.env, next >= 0, GenericError::InternalError);
        side.set_scaled(&mut usage, next);
        self.usage.set(hub_asset.clone(), usage);
    }
```

```rust
fn enforce_spoke_cap(
    env: &Env,
    side: UsageSide,
    usage: &SpokeUsageRaw,
    delta_scaled: Ray,
    cap: i128,
    index: Ray,
    decimals: u32,
) -> Ray {
    let cap_scaled = calculate_scaled_cap(env, cap, decimals, index);
    let next_scaled = Ray::from(side.scaled(usage)).checked_add(env, delta_scaled);
    assert_with_error!(env, next_scaled <= cap_scaled, side.cap_error());
    next_scaled
}
```
