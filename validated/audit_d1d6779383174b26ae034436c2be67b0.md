### Title
`validateBchAddress` legacy branch accepts base58 strings with no checksum verification, letting corrupted BCH addresses pass into PoA withdrawal memo - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateBchAddress` accepts any string matching `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` or `/^3[...]{25,34}$/` as a valid legacy BCH address without decoding base58 or verifying the double-SHA256 checksum, unlike `validateBtcBase58Address` used for `Chains.Bitcoin`, which fully decodes and checks the checksum. This lets an unspendable, checksum-corrupted legacy address pass `validateAddress(address, Chains.BitcoinCash)` and flow unmodified into `PoaBridge.createWithdrawalIntents`'s `WITHDRAW_TO:<address>` memo.

### Finding Description
The claimed broken equality is: *`validateAddress(address, Chains.BitcoinCash) === true` should imply the address is base58Check-decodable with a valid checksum (matching the guarantee made for `Chains.Bitcoin` via `validateBtcBase58Address`)*. Tracing the code:

- `validateAddress` (packages/intents-sdk/src/lib/validateAddress.ts:34-35) dispatches `Chains.BitcoinCash` to `validateBchAddress`.
- `validateBchAddress` (packages/intents-sdk/src/lib/validateAddress.ts:214-225) first tests the legacy branch with pure regex against character-set and length only, returning `true` immediately with **no** `base58.decode`, no length-in-bytes check, and no `sha256(sha256(payload))` checksum comparison.
- Contrast with `validateBtcBase58Address` (packages/intents-sdk/src/lib/validateAddress.ts:140-158), which decodes base58, checks decoded byte length is exactly 25, checks version byte, and verifies the 4-byte checksum against `sha256(sha256(payload))`.
- A base58 string matching the legacy regex shape can have a corrupted checksum (e.g., one character mutated from a real address) while still passing the regex — the regex only constrains character set and length range, not the checksum bytes.
- Once `validateAddress` returns `true`, `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:181-188) accepts the address (throwing only if `validateAddress` returns `false`).
- `PoaBridge.createWithdrawalIntents` → `createWithdrawIntentPrimitive` → `createWithdrawMemo` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:28-49) strips a `bitcoincash:` prefix (a no-op for legacy addresses, since they have none) and encodes the address verbatim into `WITHDRAW_TO:<address>` in the `ft_withdraw` intent memo.

This is a real gap in this repo's own validation logic, not a trust assumption about an external RPC/bridge/relayer: the SDK itself claims (in its own `validateBtcBase58Address` sibling function and doc comment "Validates address FORMAT only") to check base58Check-style addresses, but the BCH legacy branch skips the checksum step entirely, so the code path inside this repo produces a memo for an address that is provably invalid by the same checksum rule the repo already implements elsewhere.

### Impact Explanation
The `ft_withdraw` intent's `memo` field (`WITHDRAW_TO:<corrupted-address>`) is what the PoA bridge relayer parses to determine the on-chain BCH destination. If `destinationAddress` is a legacy string with a corrupted checksum, `validateAddress` incorrectly reports it as valid, `PoaBridge.validateWithdrawal` does not reject it, and the SDK proceeds to sign and submit an intent instructing the relayer to send BCH to an address that cannot be correctly decoded/is not a real recipient. This matches the "funds delivered to a wrong address/chain/contract with no recovery" Critical category, since a legacy base58 string with a bad checksum does not correspond to any real hash160 payload the sender controls, and there is no on-chain mechanism to recover funds sent this way. This is repeatable per withdrawal call.

### Likelihood Explanation
The precondition is simply that the caller (an ordinary SDK user or an integrator forwarding a counterparty-supplied `destinationAddress`) submits a BCH withdrawal with a legacy-format address whose checksum is wrong (e.g., a typo, or a deliberately mutated character) — no privileged access or malicious infrastructure required. The attacker's cost is negligible (constructing/mutating a base58 string), and the flaw is deterministic and always reproducible for `Chains.BitcoinCash` withdrawals routed through PoA.

### Recommendation
Update `validateBchAddress`'s legacy branch to fully decode the base58 string and verify the checksum, mirroring `validateBtcBase58Address`: `base58.decode(address)`, require exactly 25 decoded bytes, validate the version byte (0x00 for P2PKH, 0x05 for P2SH), and verify `checksum === sha256(sha256(payload)).subarray(0,4)` before returning `true`.
