## Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop identity for an incoming webhook from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while `Utils::HmacValidator` only verifies the HMAC over the raw request body. The header that `Webhooks::Registry.process` uses to route and tenant-scope the webhook is never bound to the signature that proves the payload originated from Shopify with the app's secret.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` reads the `hmac-sha256` header value: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it against the received HMAC using `Context.api_secret_key`: [2](#0-1) 

`Webhooks::Registry.process` validates that HMAC, then immediately trusts `request.shop` (read from the `shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed to the handler, alongside the parsed body: [3](#0-2) 

The identity binding the gem should enforce is `hmac == HMAC(secret, shop || topic || body)`, but the actual check is only `hmac == HMAC(secret, body)`. The `shop` (and `topic`, `webhook_id`, `api_version`) fields are "acted on but not covered by the HMAC." Because the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, any signed body from one tenant remains validly signed regardless of which shop header accompanies it.

### Impact Explanation
An unprivileged internet user can install the same public app on their own (e.g. free/dev) store, trigger a webhook event to obtain a legitimately Shopify-signed `(body, hmac)` pair for their own shop, then replay that same body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks body vs. HMAC), and `Registry.process` hands the handler `shop: <victim>` with attacker-controlled `body`. Any host application that scopes webhook side effects (order creation, data sync, GDPR requests, uninstall/app-subscription state, etc.) by `data.shop` will apply the attacker's payload to the victim tenant's data — a cross-tenant access/injection.

### Likelihood Explanation
Reachable by any unprivileged internet user with no access to `api_secret_key`, no leaked credentials, and no privileged account: only knowledge of the target app's public webhook URL and the ability to install the app on a self-controlled store to harvest one valid signed payload.

### Recommendation
Bind the identity fields to the signature: include `shop`, `topic`, and `webhook_id` in the signable string verified by `HmacValidator`, or require the host application to compare `request.shop` against the shop the app already has an active/expected session/subscription for before trusting `WebhookMetadata#shop`. At minimum, document and enforce that `shop` must never be trusted as authenticated unless it is cross-checked against a known, previously-registered shop for that specific webhook subscription.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (free/dev store), and triggers a webhook event (e.g. `orders/create`), capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header sent by Shopify.
2. Attacker POSTs the exact same body + HMAC header to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (checking only body vs. HMAC) returns `true`; `Webhooks::Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the host app to process attacker-controlled data under the victim's tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
