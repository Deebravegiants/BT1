### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — HMAC only covers the raw body (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value that `Registry.process` hands to the app's webhook handler as the tenant identifier is therefore never cryptographically bound to the signature that authenticates the request.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop` and `#topic` are read straight from headers that are not part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then, without any additional binding of `shop` to the signature, forwards `request.shop` to the registered handler as the tenant identity for the event: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares the signature purely against `verifiable_query.to_signable_string` (i.e., only the body), never touching headers: [4](#0-3) 

The equality that should hold is: **shop the HMAC authenticates == shop the handler acts on**. Because the signature only covers `@raw_body`, this equality is not enforced — `request.shop` (the field acted on / passed to `WebhookMetadata.new(... shop: request.shop ...)`) is disjoint from the bytes actually verified by the HMAC. Anyone who possesses one valid `(raw_body, hmac)` pair for the app (e.g., a merchant who installed the app on their own store, an unprivileged internet user relative to any *other* tenant of the app) can replay that exact body/hmac to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` still passes because it only checks the body against the shared `client_secret`; the handler then executes business logic attributing the attacker-controlled body to an arbitrary victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding that downstream host applications rely on to route webhook data to the correct merchant record (this maps to the "cross-tenant access" impact category). An attacker who is a legitimate, low-privilege user of the shared app (owns a store that has installed the app) can forge webhook deliveries that appear to originate from any other shop using the app, injecting attacker-chosen body content under a victim shop's identity into the app's handler logic (e.g., order/customer create-update handlers, GDPR redact handlers), since the gem provides no mechanism to bind `shop` to the HMAC.

### Likelihood Explanation
Likelihood is high for any app that has more than one installing shop (the normal case for a public/multi-tenant app): the attacker only needs a valid `(body, hmac)` pair from a webhook legitimately delivered to their own store, and control over an HTTP client to hit the app's public webhook endpoint with modified headers. No access token, `client_secret`, or privileged account is required — only participation as an ordinary merchant of the app.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, not just the raw body, e.g., by including the relevant Shopify headers in `to_signable_string`, or by independently confirming (via a signed claim or a server-side, per-shop lookup) that the shop header matches the shop the credential/secret belongs to before it is passed to `WebhookMetadata`. At minimum, document that `request.shop` is untrusted header data and must be revalidated against a shop the app has records for before use as a tenant key downstream.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value (a valid `(body, hmac)` pair signed with the app's shared `client_secret`).
2. Attacker POSTs to the app's webhook endpoint reusing the identical `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds a request object; `Utils::HmacValidator.validate` calls `to_signable_string`, which returns only `@raw_body` — unchanged from step 1 — so the signature check in `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) invokes the registered handler with `WebhookMetadata.new(shop: request.shop, ...)`, where `request.shop` is now `"victim-shop.myshopify.com"` even though the payload actually belongs to the attacker's own shop, causing the host app to process attacker-controlled data under the victim's tenant identity.
