### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied, unauthenticated `shop-domain` header straight to the handler as the identity of the shop the webhook is "for." The `shop` field acted upon is not covered by the HMAC that is verified, breaking the intended binding `hmac_covers(shop) == shop_trusted_by_handler`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled from HTTP headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC and then immediately trusts `request.shop` (along with the other header-derived fields) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — the shop header is never fed into the HMAC computation: [4](#0-3) 

Because Shopify webhooks for an app are signed with the single app-level `client_secret` (`Context.api_secret_key`) shared across every shop that installs the app — not a per-shop secret — a `(raw_body, hmac)` pair that is valid for one shop is also valid for every other shop that uses the same app. An attacker who controls (or has installed) the app on their own development/test store can capture a legitimately-signed webhook `(raw_body, hmac)` for their own store, then POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled.

The documentation explicitly tells integrators to trust `data.shop` as "The shop domain of the webhook" and to use it directly, e.g. to route work per-tenant (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this is the gem's own documented, intended way of consuming `shop`: [5](#0-4) [6](#0-5) 

This is the same bug class as the Fedimint report: a value used to make a security/identity decision (there, the peg-out amount fed into unchecked arithmetic; here, the `shop` field fed to the tenant-identifying handler) is not actually covered/validated by the mechanism that is supposed to guard it (there, `MAX_MONEY`/overflow checks; here, the HMAC signature).

### Impact Explanation
This breaks the identity binding `shop authenticated == shop delivered to handler`, letting an unprivileged actor who can obtain any one valid signed webhook for the same app (e.g., by installing the app themselves on a test store) forge webhooks that the host application will process as belonging to an arbitrary other tenant shop. Since apps commonly use `data.shop` to look up the tenant's session/access token and act on that tenant's data (exactly as the gem's own docs instruct), this enables cross-tenant confusion — e.g., injecting fabricated order/customer/fulfillment events attributed to a victim shop, or having the host app perform tenant-scoped actions using the victim shop's stored credentials in response to attacker-controlled data. This matches the "Critical — cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker must be able to obtain at least one legitimately HMAC-signed `(raw_body, hmac)` pair for the target app, which is trivially available to anyone who installs the app on their own store (public apps allow this) and registers any webhook topic. From there, replaying the body with a modified `shop` header requires no secret, token, or privileged access — only network access to the app's public webhook endpoint. The main variable is whether the host application actually uses `data.shop` for tenant-sensitive decisions, which is exactly what the gem's documentation recommends.

### Recommendation
Do not treat `shop-domain` (or `topic`/`api_version`/`webhook-id`) as authenticated merely because the HMAC over the body validated. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked against an existing, independently-established session/shop record before being trusted for tenant-scoped actions. Where feasible, extend `to_signable_string` (or add a secondary check in `Registry.process`) to bind the shop domain into the verified material, or require callers to correlate `data.shop` with a shop for which a valid installed session already exists before acting on the payload.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker-shop.myshopify.com` and register a webhook topic (e.g., `orders/create`).
2. Trigger the topic so Shopify sends a legitimately signed webhook: capture `raw_body` and the `X-Shopify-Hmac-Sha256` header value.
3. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the same app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `raw_body` against the app's single `api_secret_key`), and `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store, demonstrating the unauthenticated shop-binding.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
