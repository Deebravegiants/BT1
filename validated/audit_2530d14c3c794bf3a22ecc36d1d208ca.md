Based on the code found, this vulnerability is real and reproducible.

### Title
`limitEphemeralContainerSecretReferences` fails to validate EphemeralContainer VolumeMounts against ServiceAccount-mountable secrets, allowing disclosure of unauthorized secret-backed volumes - (File: plugin/pkg/admission/serviceaccount/admission.go)

### Summary
The `Plugin.limitEphemeralContainerSecretReferences` function, invoked on `PATCH/UPDATE` of the `pods/ephemeralcontainers` subresource, only inspects `container.Env` and `container.EnvFrom` for secret references, never `container.VolumeMounts`. An attacker who can add an EphemeralContainer can mount an existing pod `Volume` backed by a `Secret` that the pod's ServiceAccount does not reference, bypassing the enforcement entirely.

### Finding Description
In `plugin/pkg/admission/serviceaccount/admission.go`, `Validate()` routes ephemeral-container updates to `limitEphemeralContainerSecretReferences`: [1](#0-0) 

That function builds `mountableSecrets` from `serviceAccount.Secrets` and only walks `container.Env`/`container.EnvFrom` of `pod.Spec.EphemeralContainers`: [2](#0-1) 

It never inspects `container.VolumeMounts`. Compare this with the CREATE-time equivalent, `limitSecretReferences`, which does check `pod.Spec.Volumes` for secret-backed volumes (lines 323-332) — but that check runs against `pod.Spec.Volumes` as a whole at pod creation, not per-container, and it is not re-invoked for the ephemeral-container update path. So an attacker adding an ephemeral container with `VolumeMounts` referencing a pre-existing secret-backed pod volume never gets checked against the ServiceAccount's mountable secrets, since that gate only fires via `limitSecretReferences` at pod CREATE time and `limitEphemeralContainerSecretReferences` doesn't call it or replicate the volume check.

Attack flow: pod already has a secret-backed `Volume` (e.g., mounted by another container, added by an operator, or admitted before the ServiceAccount's mountable secret list was tightened). Attacker with only `update`/`patch` on `pods/ephemeralcontainers` sends `PATCH /api/v1/namespaces/ns/pods/{name}/ephemeralcontainers` adding an `EphemeralContainer` whose `VolumeMounts` mounts that volume. Since the check only inspects Env/EnvFrom, admission passes, kubelet mounts the volume into the ephemeral container, and the attacker can read the secret's contents by executing into (or reading logs/exec of) the ephemeral container.

### Impact Explanation
This is unauthorized secret disclosure: a namespace-scoped principal limited to the `ephemeralcontainers` subresource can read the contents of any secret mounted as a volume on a pod, even if the pod's ServiceAccount is not entitled to that secret under `enforceMountableSecrets`/`kubernetes.io/enforce-mountable-secrets`. This maps to a control-plane/admission-bypass class bug — the `ServiceAccount` admission plugin's secret-mountability guarantee is not exactly enforced for the ephemeral-container path.

### Likelihood Explanation
Preconditions required for the check to matter: the ServiceAccount admission plugin's `LimitSecretReferences` must be enabled globally, or the target ServiceAccount must carry the `kubernetes.io/enforce-mountable-secrets: "true"` annotation (see `enforceMountableSecrets`, lines 271-282; `LimitSecretReferences` defaults to `false` in `NewServiceAccount()`, line 104). When that enforcement is active — which is exactly the scenario this admission gate exists for — the bypass is deterministic and repeatable: any principal with only `update`/`patch` on `pods/ephemeralcontainers` and knowledge of an existing secret-backed volume name on the target pod can exploit it every time, with no dependency on race conditions or timing.

### Recommendation
Extend `limitEphemeralContainerSecretReferences` to also validate `container.VolumeMounts` for each ephemeral container against the pod's declared `Volumes`, resolving to secret-backed volumes and checking their `SecretName` against `mountableSecrets`, mirroring the volume-checking logic already present in `limitSecretReferences` (lines 323-332).

### Proof of Concept
Table-driven unit test extending the existing tests in `plugin/pkg/admission/serviceaccount/admission_test.go` for the ephemeral-containers Validate path:
1. Create a `ServiceAccount` with `enforce-mountable-secrets: "true"` and `Secrets: []` (no secrets referenced).
2. Create a `Pod` (already admitted) with `Spec.ServiceAccountName` set to that SA and `Spec.Volumes` containing a `Volume{Name: "secret-vol", VolumeSource: VolumeSource{Secret: &SecretVolumeSource{SecretName: "forbidden-secret"}}}`.
3. Build an `admission.Attributes` for `UPDATE` on subresource `ephemeralcontainers` with a new object that adds `EphemeralContainers: [{EphemeralContainerCommon: {Name: "debug", VolumeMounts: [{Name: "secret-vol", MountPath: "/secret"}]}}]` (no Env/EnvFrom).
4. Call `Plugin.Validate(ctx, attrs, o)`.
5. Expected (secure) assertion: `Validate` returns an `admission.NewForbidden` error referencing `forbidden-secret`.
6. Actual current behavior: `Validate` returns `nil` (no error), demonstrating the VolumeMounts gap.
