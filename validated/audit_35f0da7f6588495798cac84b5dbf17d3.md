The webhook `Request.shop` value used by handlers (`Registry.process` → `WebhookMetadata.new(... shop: request.shop ...)`) comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature only covers `@raw_body` via `to_signable_string` [1](#0-0) . The `shop` header is never included in the signed payload, so `Utils::HmacValidator.validate(request)` only proves the body bytes were signed with the app's secret — it says nothing about which shop the request actually originated from [2](#0-1) . `Registry.process` trusts this unauthenticated header directly when dispatching to the handler [3](#0-2) .

### Title
Webhook `shop` field is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute exposed to webhook handlers entirely from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) HTTP header. The HMAC validation performed by `Utils::HmacValidator` only signs `@raw_body` (`to_signable_string` returns just the raw body), never the shop header, topic header, or any other header. Because the shop identity that reaches application code is unauthenticated, any request bearing a validly-signed body (e.g. from a webhook the attacker's own shop legitimately received, since the HMAC secret is per-app, not per-shop) can be replayed with an arbitrary `shop-domain` header, letting an unprivileged actor attribute the webhook payload to any other tenant of the same app.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body` — none of the Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) participate in the signature [5](#0-4) . Yet `shop` is read straight from that unsigned header [6](#0-5) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, and then builds `WebhookMetadata` using `request.shop` as the tenant identity handed to the app's handler code: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [3](#0-2) .

The `api_secret_key` used for the HMAC is a single app-wide secret (`Context.api_secret_key`), identical for every shop that installs the app — it is not shop-specific. Because of this, the equality the code implicitly assumes — "HMAC valid ⇒ this body was sent by the shop named in the `shop-domain` header" — does not hold: HMAC validity only proves "this body was signed with this app's secret by *some* installation," not by the specific shop asserted in the header. An attacker who controls (or has access to) any shop that has this same app installed can capture a legitimate webhook delivery (valid body + valid HMAC for shop A), then resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with shop B's domain. `HmacValidator.validate` still passes (body/signature untouched), and `Registry.process` will hand the handler `WebhookMetadata` claiming the data came from shop B, even though it did not.

### Impact Explanation
This breaks the tenant binding "the shop that generated and authenticated the webhook == the shop the app's handler code believes and acts upon," enabling cross-tenant data confusion/injection: an attacker can make the app process (and potentially persist/react to) forged data under another merchant's identity — e.g. triggering `orders/create`, `app/uninstalled`, `customers/data_request`, etc. handling logic attributed to a victim shop of the attacker's choosing, using only their own legitimately-signed webhook traffic. This matches the report's underlying bug class — a field acted upon (here `shop`) that is not covered by the authentication check (HMAC) — mapped onto this gem's cross-tenant webhook trust boundary.

### Likelihood Explanation
Any developer/merchant who installs the same public app can generate arbitrarily many legitimately-HMAC-signed webhook payloads for their own shop (by triggering shop events), then replay the raw body against the app's webhook receiver endpoint with a forged `shop-domain` header pointing at any other shop, since nothing in the library rejects header/shop mismatches or requires shop-specific signing material.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed payload check, or otherwise verify that the header-derived `shop` corresponds to an installation session already known/expected for this delivery, rather than trusting an unsigned header outright. At minimum, document/require host applications to independently verify `shop` against their own installed-shop records before trusting `WebhookMetadata#shop`, since the gem alone cannot cryptographically bind it given only body-only HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. updates a product) causing Shopify to POST a signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `api_secret_key`), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures this request, then re-sends it directly to the app's webhook receiver endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but replacing `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body(B), ...)` — the app now processes attacker-controlled data as if it originated from the victim shop [8](#0-7) .
