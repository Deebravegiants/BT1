### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `msg.value` back two independent deposit/UTXO-minting checks in the same `transact` call - ([File: contracts/Hinkal.sol])

### Summary
`Hinkal.transact` computes the ETH `balanceDif` for a token slot as `newBalances[i] + msg.value - oldBalances[i]` [1](#0-0)  and this formula is evaluated independently for every index `i` whose `erc20TokenAddresses[i] == address(0)`. Because `oldBalances`/`newBalances` are the same contract-wide ETH balance regardless of index, `balanceDif` is identical (and equal to `msg.value`, when no other ETH moves) at every occurrence of `address(0)` in the array. No code path deduplicates `erc20TokenAddresses`, so an attacker listing `address(0)` twice gets the single real `msg.value` payment validated as backing for two separate token slots, each of which can independently mint a shielded output worth `msg.value`.

### Finding Description
Broken equality: the protocol invariant should be `sum over i of (real ETH received in this call) == sum over i of (accounted deposit/UTXO value for address(0) slots)`, i.e. `msg.value` should back exactly one accounting term. Instead, per index `i`, `balanceDif[i] == amountChanges[i] (or 0 if onChainCreation) + utxoAmount[i]` is checked separately at Hinkal.sol:137-146 [2](#0-1) , and for `address(0)` slots `balanceDif` always includes the *full* `msg.value` term (lines 100-104) regardless of how many times `address(0)` appears.

Exact path for an internal transaction (`externalActionId == 0`):
1. Attacker calls `transact` with `circomData.erc20TokenAddresses = [address(0), address(0), ...]` (two entries for native ETH), sending `msg.value = V`.
2. `performHinkalChecks` → `dimensionsCheck` and `checkOnchainCreation` in `HinkalHelper.sol` only validate array-length equality and per-slot onChainCreation/amountChanges/nullifier consistency [3](#0-2) ; nothing rejects duplicate token addresses.
3. `_internalTransact` iterates the array; for both index `i1` and `i2` (both `address(0)`) with `amountChanges[i] > 0`, it calls `transferERC20TokenFromOrCheckETH`, which for ETH only requires `msg.value == _value` [4](#0-3) . Setting `amountChanges[i1] = amountChanges[i2] = V` satisfies this check twice without any second ETH transfer.
4. Back in `transact`, the balance-equation loop computes `balanceDif = V` at both `i1` and `i2` (address(0) formula, oldBalances==newBalances since no extra ETH moved) and checks `balanceDif == amountChanges[i]` at each index independently - both pass with `amountChanges[i1]=amountChanges[i2]=V`.
5. The circuit only enforces `inTotal[i] + amountChanges[i] === outTotal[i]` per index (no cross-index awareness of duplicate token addresses), so the attacker can generate a valid proof producing two output commitments of value `V` each (one per index) for a single real deposit of `V`.

Result: attacker mints `2V` of shielded ETH value backed by only `V` real ETH sent to the contract.

Existing guards fail because: `dimensionsCheck`/`checkOnchainCreation` never assert uniqueness of `erc20TokenAddresses`; the balance-diff formula for `address(0)` is computed per-index using the call-wide `msg.value` rather than being apportioned/consumed once across the array; and the circuit's `inTotal + amountChanges === outTotal` constraint is local to each token slot and has no notion that two slots reference the same underlying asset.

### Impact Explanation
The attacker mints unbacked shielded ETH value inside the Hinkal shielded pool, directly causing protocol insolvency (contract ETH backing is less than the sum of shielded UTXOs). This matches "Critical: minting shielded value without backing (protocol insolvency)". The attack is repeatable per transaction and scales with however many duplicate `address(0)` slots the `Dimensions.tokenNumber` allows, each additional duplicate multiplying the unbacked mint.

### Likelihood Explanation
- Preconditions: none beyond being able to call `transact` as any unprivileged user with a self-generated valid proof for a deposit circuit configuration (`externalActionId == 0`, i.e., a normal internal deposit) and `dimensions.tokenNumber >= 2`.
- No relay, whitelisted role, or victim funds are required; attacker only spends the real gas + the single genuine `msg.value` and gains double (or more) that value in shielded credit.
- Cost is low (one transaction, standard proof generation for a deposit with two token slots both mapped to `address(0)`), and it is fully repeatable.

### Recommendation
Deduplicate `erc20TokenAddresses` (revert on repeated addresses) in `dimensionsCheck`/`checkOnchainCreation`, or restructure the balance-diff accounting so `msg.value` is consumed/apportioned once across the array (e.g., track a single running "ETH accounted" accumulator across all indices and require it equal `msg.value` exactly once, rather than checking `balanceDif == amountChanges[i]` independently per occurrence of `address(0)`).

### Proof of Concept
Foundry/Hardhat plan:
1. Deploy Hinkal with a mock verifier that accepts attacker-supplied proofs (or use the real verifier and locally generate a valid proof for a 2-token-slot circuit where both slots are `address(0)`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`, empty input nullifiers, and two output commitments each encoding value `V`).
2. Call `Hinkal.transact{value: V}(...)` with `circomData.erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [int256(V), int256(V)]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
3. Assert: `address(hinkal).balance == balanceBefore + V` (only one real ETH transfer occurred) while two output commitments each carrying claimed value `V` were inserted via `insertCommitments` — i.e., total newly claimed shielded ETH value (`2V`) exceeds the actual ETH balance delta (`V`), proving `msg.value backing != exactly one accounting term`.
