Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` — defined as the raw JSON body only. The `shop` field, which the gem exposes to the app's handler as the tenant identity (`WebhookMetadata#shop`), is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed bytes. This breaks the identity binding `hmac(signed_bytes) == hmac(body)` versus the value trusted for tenant routing, `tenant_used_by_app == header["shop-domain"]`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shop`, `topic`, `webhook_id`, and `api_version` headers are excluded from the signable string. `HmacValidator.validate` and `validate_signature` confirm the HMAC is computed only against `to_signable_string`: [3](#0-2) 

`Registry.process` gates only on this HMAC check, then forwards `request.shop` (the unauthenticated header value) straight into `WebhookMetadata`, which the documented handler API uses as the shop/tenant key: [4](#0-3) [5](#0-4) 

The gem's own docs instruct integrators to treat `data.shop` as the shop identity for routing/queuing work (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), confirming this is the gem's intended, documented binding between the HMAC-validated request and tenant identity: [6](#0-5) 

Critically, `Context.api_secret_key` used for HMAC validation is the app's single `client_secret`, shared across *every* shop that installs the app — it is not shop-specific: [7](#0-6) 

Consequently, any unprivileged user can install the public app on their own (attacker-controlled) development/test store — a legitimate, unprivileged action — and receive genuine Shopify webhooks for that store, each with a valid HMAC computed with the shared app secret over the raw body. Because the `shop-domain` header is outside the signed bytes, the attacker can replay the exact `raw_body` + valid `hmac-sha256` header they received, but substitute an arbitrary victim `shop-domain` header value, and POST it to the app's public webhook endpoint. `Registry.process` will accept it as valid (the body hash matches) and dispatch it to the handler with `WebhookMetadata#shop` set to the victim's shop domain, even though the payload content actually originates from the attacker's own store.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality the app relies on, `webhook.shop == the tenant that actually produced/authorized this body`, does not hold, because `shop` is unauthenticated header data while only the body bytes are HMAC-verified. Any host app using the gem as documented (keying work off `data.shop`) can be made to process attacker-supplied body content under a victim shop's identity — e.g., queuing jobs, updating cached shop state, or triggering shop-scoped side effects attributed to a shop the attacker does not control. This matches the Critical category of cross-tenant access.

### Likelihood Explanation
Likelihood is High for apps following the documented pattern: the only prerequisite is the ability to install the app on any shop (which is normal, unprivileged usage for public apps) to harvest a validly-signed body/HMAC pair, then replay it with a forged `shop-domain` header to the app's public webhook callback URL. No access token, `client_secret`, or privileged account is required — only observation of Shopify's own outgoing webhook traffic to the attacker's own store.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., derive/verify `shop` from a value inside the signed JSON body, or require the host application to independently confirm the `shop` header corresponds to a shop with an active, matching webhook registration/session before trusting it). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target public app on their own Shopify store (`attacker.myshopify.com`) — no special privileges required.
2. Shopify sends a legitimate webhook (e.g., `orders/create`) to the app's callback URL, with body `B` and header `x-shopify-hmac-sha256: HMAC(client_secret, B)`.
3. Attacker captures `B` and the HMAC header, then re-sends the same body `B` and HMAC to the app's public webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` over `B` only (lib/shopify_api/webhooks/request.rb:36-38, lib/shopify_api/utils/hmac_validator.rb:12-31) — it passes, because the body is unchanged.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` (lib/shopify_api/webhooks/registry.rb:198-199) and processes attacker-controlled data as if it came from the victim shop.
