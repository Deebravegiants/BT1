### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant spoofing of webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity used by the app (`shop`) from an HTTP header, but `to_signable_string` only signs the raw request body, so the HMAC never binds the `shopify-shop-domain` header. `Webhooks::Registry.process` validates only the HMAC over the body and then dispatches to the host app's handler using the unauthenticated `shop` header value, so a handler that trusts `request.shop`/`WebhookMetadata#shop` for tenant-scoped side effects can be made to act on the wrong tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. only the body) and then immediately hands the header-derived `request.shop` to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string`: [4](#0-3) 

This is the same bug class as the external report: a value that is used as an identity/binding key (`_tokenId` in the analog, `shop` here) is not the value that was actually verified/bound by the authentication mechanism (HMAC signature only covers the raw body, not the shop header). The equality that should hold — `shop used by handler == shop cryptographically bound by the signature` — does not hold, since the signature only proves "this body was produced with the app's `client_secret`", not "this body belongs to shop X".

Because all shops installed on a multi-tenant app share the same app `client_secret`, any legitimately installed merchant (including an attacker who installs the app on their own store) receives real, correctly-HMAC-signed webhooks for their own shop. That attacker can capture such a webhook (raw body + valid HMAC) and replay it to the app's webhook endpoint after changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to a victim shop's domain. `HmacValidator.validate` will still succeed because it never inspects the shop header, and `Registry.process` will invoke the host app's handler with `WebhookMetadata.shop` set to the victim's domain while the body content is attacker-controlled.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, `api_secret_key`, or any merchant's access token — only a legitimate installation of the app on the attacker's own shop is required. Any host application logic that keys authorization, data writes, or GDPR/compliance actions (e.g. `shop/redact`, `customers/redact`, `customers/data_request`) off `WebhookMetadata#shop` can be tricked into acting against a different tenant with attacker-supplied body content. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker be a legitimate merchant/installer of the same app (trivial for a public/multi-tenant app), and (2) the ability to send an arbitrary HTTP request with attacker-chosen headers to the app's public webhook endpoint (which webhook endpoints are, by design). No secrets, session tokens, or privileged access are needed — only observing one's own legitimately delivered webhook and headers.

### Recommendation
Bind the shop (and ideally topic/webhook-id/api-version) into the signed material, or otherwise verify that the shop domain in the header matches a shop domain independently known to be authorized for the received body (e.g., verify the shop against the session/store associated with the topic-specific expected sender, or include shop in an HMAC-computed string via a design similar to Shopify's actual webhook verification which signs the full request, not just the body-derived digest). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not allow header values to be trusted for tenant identification unless those headers are part of what was verified.

### Proof of Concept
1. Install the vulnerable/host app on attacker-controlled shop `attacker.myshopify.com`; the app is multi-tenant and uses a single `client_secret`/`api_secret_key` for all installs.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) on `attacker.myshopify.com`; capture the raw POST body and the `x-shopify-hmac-sha256` header — this HMAC is valid because it is computed only from `raw_body` per [1](#0-0) .
3. Replay this exact body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (body/HMAC pair is genuinely valid) per [5](#0-4) , and `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim.myshopify.com"` while the body content is attacker-controlled data from the attacker's own store, per [6](#0-5) .

          received_signature = verifiable_query.hmac
