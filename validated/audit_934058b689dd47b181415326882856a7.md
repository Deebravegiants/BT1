### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing tenant impersonation in `ShopifyAPI::Webhooks::Request` / `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` only proves that `@raw_body` was signed with the app's `client_secret`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken from unauthenticated headers and are never included in the signed material, yet `Registry.process` passes `request.shop` straight into the `WebhookMetadata` object delivered to the host application's handler.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers with no integrity binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC and then forwards the unauthenticated `request.shop`/`topic`/`webhook_id` values to the registered handler: [4](#0-3) 

Because Shopify uses the **same `client_secret` for every shop that installs a given app**, any merchant who installs the app receives genuine webhooks whose `(raw_body, hmac)` pair is valid under that app's shared secret. A malicious merchant can capture one such legitimate `(body, hmac)` pair from their own store, then replay it against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` will still succeed — it only checks the body — and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, with attacker-controlled body content.

This breaks the intended equality: `shop asserted by the unauthenticated header == shop bound by the HMAC signature`. In reality, the HMAC binds only the body, not the tenant identity.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as delivered by this gem) to select which merchant's session/access token to act on, or to attribute/store data per-tenant, can be tricked into processing forged, attacker-crafted body content under a victim shop's identity — i.e., cross-tenant confusion driven directly by this gem's webhook-processing contract, since the gem asserts the request is HMAC-verified without the `shop` field being part of that verification.

### Likelihood Explanation
Requires the attacker to install the target app on a shop they control (or otherwise obtain one genuine `(body, hmac)` pair for that app, e.g. from any real webhook they've received) and to be able to POST to the app's public webhook endpoint with custom headers — no privileged credentials, tokens, or `client_secret` knowledge are needed. This is a realistic capability for "any unprivileged internet user" who can install the target Shopify app.

### Recommendation
Do not treat `request.shop`/`topic`/`webhook_id` as trusted identifiers based solely on the body HMAC. Either:
- Include the shop domain (and topic/webhook id) in the signed material used for HMAC verification, or
- Require the host application to independently verify that `shop` in the webhook payload matches an existing, previously-established session/installation record before using it to select credentials, and document this gap clearly in `docs/usage/webhooks.md`.

### Proof of Concept
1. App `X` is installed on attacker-controlled shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`; both use the same `Context.api_secret_key` for app `X`.
2. Attacker captures a genuine webhook delivery to their own endpoint: `raw_body = B`, header `x-shopify-hmac-sha256 = H`, where `H = Base64(HMAC-SHA256(secret, B))`.
3. Attacker POSTs to the app's webhook endpoint with `raw_body = B`, `x-shopify-hmac-sha256 = H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com` and (optionally) an arbitrary `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only hashes `B`. [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata` where `shop == "victim.myshopify.com"`, even though the payload `B` originated from the attacker's own store event. [6](#0-5)
