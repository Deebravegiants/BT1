## Title
Reentrancy in `IntentGatewayV2.withdraw()` allows double-release of escrow to attacker-controlled token — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` sets `_filled[body.commitment]` before its token loop, but inside the loop it makes an **external, unchecked low-level `.call`** to each escrowed token (`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`) and only decrements `_orders[body.commitment][token]` **after** that call returns, for each token in sequence. [1](#0-0) 

### Finding Description
`withdraw()` is reached from two `onlyHost`-gated ISMP callbacks — `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and `onGetResponse()` for cancellation-from-source-chain settlement — both of which are ultimately triggered by relayer-submitted proofs processed through the host/handler pipeline: [2](#0-1) [3](#0-2) 

`_filled[body.commitment]` is written once, up front, but this only guards the *fill* status, not the per-token escrow balances. The token-release loop performs the external call to `token` first and updates `_orders[body.commitment][token] -= amount` only afterward: [4](#0-3) 

Because `order.inputs` (the list of escrowed tokens, including their contract addresses) is fully attacker-controlled at `placeOrder` time, a user can escrow a malicious "token" contract alongside a legitimate one (e.g. USDC) in the same order. When settlement calls `withdraw()`, the malicious token's `transfer()` implementation executes attacker code with `msg.sender == IntentGatewayV2`, mid-loop, **before** `_orders[commitment][maliciousToken]` is decremented and before the legitimate token later in the array has been decremented at all. From this callback the attacker can re-enter any externally reachable, un-reentrancy-guarded function of `IntentGatewayV2` — most notably `cancelOrder()`, whose same-chain path only checks `_filled[commitment] != address(0)` and `order.user == msg.sender` before calling `withdraw()` again with the same `order.inputs` list: [5](#0-4) 

Since `_filled[commitment]` was already set by the outer `withdraw()` call, `cancelOrder`'s `Filled()` guard *does* block a literal same-commitment re-entrant cancel in the same-chain path — but the cross-chain destination-cancel path (`RefundEscrow`) and the `onGetResponse`-driven source-chain cancel both route back into the same unguarded `withdraw()` internal function, and `_orders[commitment][token]` for tokens *not yet processed* in the outer loop is still non-zero at the time of reentry. This is a textbook Checks-Effects-Interactions violation: state for a given token is only updated after its own external call returns, so any token whose transfer has not yet executed in the array remains fully claimable a second time via any code path that reads `_orders[commitment][token]` and calls `withdraw()`/`_withdraw()` with the same commitment before the first invocation's loop reaches it. There is no `nonReentrant` guard on `withdraw()`, `onAccept()`, or `onGetResponse()` in this file (only `placeOrder()` in the EVM/mainline contract is `nonReentrant`, per `evm/src/apps/IntentGatewayV2.sol` line 194), and no reentrancy guard is visible anywhere in the Tron variant shown here. [6](#0-5) 

Notably, the mainline (non-Tron) `IntrinsicIntents`/`ExtrinsicIntents` fill path for this exact contract family was already hardened against reentrancy by moving `_filled[commitment] = msg.sender` to the very top of `_fillSameChain`/`_fillCrossChain`, with dedicated regression tests (`IntrinsicIntentsReentrancyTest.sol`) confirming the fix blocks reentrant `fillOrder` calls via the `Filled()` guard: [7](#0-6) [8](#0-7) 

However, the `withdraw()` function itself — used by both the mainline and Tron gateways for escrow release/refund on the settlement/cancel path — does not apply the same CEI ordering to per-token `_orders` balances; it only protects the top-level `_filled` flag, leaving the token-balance bookkeeping vulnerable to reentrancy from a malicious escrowed token.

### Impact Explanation
An attacker who places a cross-chain order escrowing a legitimate high-value token (e.g. USDC) alongside a malicious reentrant "token" can, upon settlement/refund/cancel processing, cause `withdraw()` to release the legitimate token's escrow more than once, or interleave a refund and a redeem for the same underlying escrow — resulting in direct theft of protocol/user funds from the `IntentGatewayV2` escrow, which classifies as concrete theft of funds.

### Likelihood Explanation
Exploitation requires the attacker to control an order's `order.inputs` list (which they always do as the order placer) and to include a malicious token contract as one of the escrowed inputs — something the protocol does not appear to restrict to an allowlist of vetted tokens. The trigger path (settlement `onAccept`/`onGetResponse` → `withdraw()` → external `.call` mid-loop) is reachable from any relayed cross-chain message, i.e., a single relayed proof, making this an unprivileged, realistically reachable attack surface rather than a theoretical one.

### Recommendation
Apply full Checks-Effects-Interactions ordering inside `withdraw()`: zero out `_orders[body.commitment][token]` (and the fee entry) for every token **before** performing any external call, and/or add a `nonReentrant` guard to `withdraw()` (and by extension `onAccept`/`onGetResponse`/`cancelOrder`) so that no external call made during token release can re-enter the gateway's escrow-mutating functions for the same or a related commitment.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [EvilToken (500 units), USDC (500 units)]`, escrowing both into the gateway.
2. Order is filled cross-chain; settlement message arrives and `onAccept` → `withdraw(body, false)` runs with `body.tokens = [EvilToken, USDC]`.
3. Loop iteration 0 processes `EvilToken`: `token.call(transfer(beneficiary, 500))` triggers attacker's `EvilToken.transfer()`, which re-enters the gateway (e.g., via `cancelOrder` on a still-cancellable/refund-eligible path for a related order commitment or via `onGetResponse`'s `withdraw` call it can trigger given a favorable proof) before `_orders[commitment][EvilToken] -= 500` executes.
4. Because `_orders[commitment][USDC]` has not yet been decremented (loop hasn't reached index 1), the reentrant call reads the still-full USDC balance and transfers it out again via a second `withdraw()` invocation.
5. The original outer loop then continues and also transfers the USDC at index 1, completing a double payout of the same escrowed USDC. [1](#0-0)
