### Title
Permanent pool-creation griefing via unchecked `market_info` seed in `process_initialize2` - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every PDA needed for a pool (target orders, LP mint, coin vault, pc vault, and the `AmmInfo` account itself) solely from the `market_info` account key, with no validation that the caller is authorized to bind that market to a pool or that the supplied mints correspond to that market. Any unprivileged user can call `Initialize2` first, using an arbitrary/target `market_info` account together with attacker-chosen (e.g. worthless, self-minted) coin/pc mints and minimal deposit amounts, permanently occupying the PDA address space tied to that market. This mirrors the reported bug class of "a reachable call consumes a shared identifier, permanently blocking the legitimate registration path" — except here the reachable path requires no privilege at all.

### Finding Description
In `process_initialize2`, the `market_info` account is explicitly documented as unchecked: "Just a seed for AMM account. Can be any account." [1](#0-0) 

All associated accounts for the pool — target orders, LP mint, coin vault, pc vault, and the `AmmInfo` PDA itself — are derived exclusively from `market_info.key` and a fixed seed constant, with no cross-check against the coin/pc mints or against any legitimate market ownership: [2](#0-1) 

The derivation and creation helper (`generate_amm_associated_account` / `generate_amm_associated_spl_token`) only checks that the derived PDA is currently owned by the system program; once created it is assigned to `program_id` and any subsequent attempt to reuse the same `market_info` seed fails with `AmmError::RepeatCreateAmm`: [3](#0-2) 

Because `market_info` is never validated to be a genuine OpenBook market corresponding to the intended `amm_coin_mint`/`amm_pc_mint` pair, and the only signer requirement is the caller's own wallet, [4](#0-3)  an attacker can submit `Initialize2` first for a `market_info` pubkey that a legitimate project intends to use, using throwaway mints and minimal `init_coin_amount`/`init_pc_amount`, permanently consuming that market's PDA namespace (`AmmInfo` becomes non-`Uninitialized`, and the target-orders/lp-mint/vault PDAs become owned by `program_id`): [5](#0-4) 

Any subsequent, legitimate `Initialize2` call using that same `market_info` account will unconditionally fail (`RepeatCreateAmm` / `AlreadyInUse`), permanently blocking the real project from ever creating a Raydium pool bound to that market account.

### Impact Explanation
This is a permanent, unrecoverable denial-of-service on pool creation for a targeted market: once squatted, the legitimate project can never bind that specific market account to a Raydium AMM pool via `Initialize2`, since the PDA derivation is deterministic and collision is permanent (no reset/removal path exists for `AmmInfo`, vault, or LP-mint PDAs). This can be weaponized to grief/extort specific projects preparing a token launch, or to disrupt competitor pool listings, with the attacker's cost limited to rent plus a trivial dummy-token deposit.

### Likelihood Explanation
The precondition is trivial: `Initialize2` is a fully permissionless instruction reachable in a single transaction with attacker-chosen accounts (arbitrary `market_info`, self-created worthless mints) and attacker-chosen data (`nonce`, `init_coin_amount`, `init_pc_amount`). No elevated privilege, timing dependency on validator behavior, or off-chain component is required — only knowledge of the target `market_info` pubkey the victim intends to use, which is often predictable/observable (e.g. newly created OpenBook markets are public before the corresponding Raydium pool is created).

### Recommendation
Bind the derived PDAs to a value that a squatter cannot cheaply/independently choose to match the victim's intended pool, e.g., derive seeds from `(market_info.key, amm_coin_mint, amm_pc_mint)` and/or require verification that `market_info` is an actual OpenBook market whose base/quote mints match `amm_coin_mint_info`/`amm_pc_mint_info`. Alternatively, restrict `Initialize2` to require that `market_info` be validated on-chain (owner == market program, and its embedded mint fields match the supplied coin/pc mints) before any PDA is created, so an attacker cannot bind an arbitrary/unrelated market account to a bogus pool.

### Proof of Concept
1. Observe or predict a `market_info` pubkey that a legitimate project will use for their upcoming pool (e.g. a freshly created OpenBook market for token X/USDC).
2. Before the legitimate team calls `Initialize2`, submit an `Initialize2` transaction as an unprivileged attacker using that same `market_info` account, but supplying attacker-created/worthless `amm_coin_mint`/`amm_pc_mint` and minimal `init_coin_amount`/`init_pc_amount`.
3. `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` succeed because all derived PDAs are currently system-owned, and `AmmInfo::load_mut` sees `status == Uninitialized`, so initialization completes and `amm.status` is set to `Initialized`. [5](#0-4) 
4. The legitimate team later calls `Initialize2` with the real `market_info`, correct mints, and real liquidity; `generate_amm_associated_account` for the AMM/target-orders/vault PDAs finds them already assigned to `program_id` and returns `AmmError::RepeatCreateAmm`, permanently preventing pool creation for that market. [6](#0-5)
