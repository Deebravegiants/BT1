### Title
Webhook shop-domain (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop-domain` (and `topic`/`webhook-id`) HTTP headers, which are never part of the signed material, to build the `WebhookMetadata` handed to the application's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

The identity binding that should hold is: `shop header == shop cryptographically bound to the signed payload`. Because `HmacValidator.validate` only checks `secret + raw_body -> hmac` (via `VerifiableQuery#to_signable_string`, which for webhooks is `@raw_body` alone): [4](#0-3) 

...an unprivileged internet user who has legitimately installed the app on their own store (a normal, unprivileged sign-up flow) will receive a real webhook from Shopify: a `(raw_body, hmac)` pair signed with the app's single, shared `client_secret`. Since the same `client_secret` is used for every shop that installs the app, this `(raw_body, hmac)` pair is valid for **any** shop — the signature says nothing about which shop it came from. The attacker can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers to claim any other, victim shop domain. `process` will validate the HMAC successfully (it only checks the body) and will dispatch `WebhookMetadata` claiming to be from the victim shop to the app's handler, exactly matching the documented contract that `data.shop` is "The shop domain of the webhook."

### Impact Explanation
This breaks the tenant boundary: the app's own webhook handler is documented to trust `data.shop` as the authenticated tenant identifier, but that value is never covered by the HMAC. Any app that keys per-shop data mutation, order/customer processing, mandatory GDPR redaction (`shop/redact`, `customers/redact`, `customers/data_request`), or state updates off `data.shop` can be made to process forged events attributed to an arbitrary victim shop, using a signature obtained from the attacker's own (unprivileged, self-installed) tenant. This is a cross-tenant access primitive against any application built on this gem's webhook processing API.

### Likelihood Explanation
Exploitation requires no leaked secrets, no privileged account, and no TLS interception: any user can sign up for the app on their own shop (free/unprivileged), capture the resulting webhook `raw_body`/`hmac`, and replay it to the same public endpoint with altered `shop-domain`/`topic` headers. `Registry.process` performs no additional check tying the header-derived `shop` to the signed body.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify the shop against a signed value obtained from Shopify metadata, not a bare header), before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev/test store, `attacker.myshopify.com`, and lets the app register for `orders/create`.
2. Shopify sends a real webhook to the app's endpoint:
   - Body: `raw_body`
   - Headers: `x-shopify-hmac-sha256: HMAC(raw_body, client_secret)`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`
3. Attacker captures this `(raw_body, hmac)` pair (trivial — it's their own traffic to their own server/proxy).
4. Attacker POSTs the identical `raw_body` and `x-shopify-hmac-sha256` value to the same public endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: ...)`, spoofing a webhook as belonging to a shop the attacker never installed the app on.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
