### Title
Unprivileged caller can get PoaBridge/HotBridge to sign a withdrawal to an all-zero (unownable) Sui address because `validateSuiAddress` performs only a format regex check with no zero-address or on-chain existence guard - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateSuiAddress` only checks `/^(?:0x)?[a-fA-F0-9]{64}$/`, so `0x` + 64 zeros passes format validation with no special-case rejection, unlike `validateEthAddress`, which explicitly blocks the zero address and the EIP-3675 "dead" burn address. Neither `PoaBridge.validateWithdrawal` nor `HotBridge.validateWithdrawal` add any additional Sui-specific ownability/existence check (no trustline-like check, no account-existence RPC call as done for NEAR in `DirectBridge`), so the unmodified all-zero address flows straight into the signed withdrawal intent's memo/msg.

### Finding Description
The claimed broken equality is: **address format-valid != address a Sui wallet can control**. Tracing the code confirms this divergence is real and unguarded for Sui specifically.

`validateAddress` dispatches Sui destination addresses to:
```ts
function validateSuiAddress(address: string) {
	return /^(?:0x)?[a-fA-F0-9]{64}$/.test(address);
}
``` [1](#0-0) 

This is purely a byte-length/hex-charset check with no checksum and no rejection of degenerate values. Contrast with the Ethereum path, which explicitly special-cases and rejects the null and burn addresses before delegating to `viem`'s `isAddress`:
```ts
function validateEthAddress(address: string) {
	if (
		address === "0x0000000000000000000000000000000000000000" ||
		address.toLowerCase() === "0x000000000000000000000000000000000000dead"
	) {
		return false;
	}
	return isAddress(address, { strict: true });
}
``` [2](#0-1) 

No equivalent zero-address guard exists for Sui, Aptos, Movement, or Starknet (all of which share the same permissive hex-regex style validators) [3](#0-2) .

`PoaBridge.validateWithdrawal` calls `validateAddress`, then only checks that the destination doesn't equal the token's own origin-chain address via `compareAddresses`, and (for XRPL only) performs an account-existence RPC check. There is no Sui-specific existence/ownability check: [4](#0-3) 

`HotBridge.validateWithdrawal` follows the identical pattern - `validateAddress`, then `compareAddresses` against the token address, with an additional Stellar-only trustline check that does not extend to Sui: [5](#0-4) 

`compareAddresses` for Sui only normalizes hex casing/leading zeros to compare against the token's own address; it does not detect or reject the zero address as a special sentinel: [6](#0-5) 

Once validation passes, `PoaBridge.createWithdrawalIntents` builds the `ft_withdraw` intent whose `memo` embeds the raw, unmodified `destinationAddress` (`WITHDRAW_TO:<address>`), which the off-chain PoA relayer parses to determine where to send funds on the destination chain: [7](#0-6) 
This gets returned by `createWithdrawalIntents` and signed by the SDK's flow (`sdk.ts` -> `createWithdrawalIntents`) with no further address vetting: [8](#0-7) 

For HotBridge, the raw `destinationAddress` is passed as `receiver` into `hotSdk.buildGaslessWithdrawIntent`, again unmodified and unvetted for ownability: [9](#0-8) 

**Important caveat on the existing test suite**: the PoaBridge test suite's "blocks non corresponding addresses" case labeled "UDSC Sui" actually uses viem's `zeroAddress` (`0x` + 40 hex zeros, Ethereum format), which fails `validateSuiAddress`'s 64-hex-character length check for an unrelated reason (wrong length), not because of any zero-address-specific rejection: [10](#0-9) 
This test does **not** cover the actual attack input (`0x` + 64 hex zeros), so it provides no protection against the scenario in this question.

### Impact Explanation
An unprivileged caller (an ordinary user, or a counterparty whose `destinationAddress` string an integrator forwards unmodified into the SDK) can supply `"0x" + "0".repeat(64)` as the Sui `destinationAddress`. `validateAddress` returns `true`, `PoaBridge.validateWithdrawal`/`HotBridge.validateWithdrawal` raise no error, and `createWithdrawalIntents` builds and returns an `ft_withdraw`/`mt_withdraw` intent whose memo/msg contains that address unmodified. If this intent is subsequently signed and submitted, the underlying bridge relayer will attempt to deliver funds to that address on Sui. Since no private key controls the all-zero address (it is not a valid Sui account any wallet can hold - the zero address on many chains is a burn/unspendable sentinel), the funds become unrecoverable once the withdrawal executes. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery." The bug is repeatable per call and requires no special privilege - only a plausible-looking hex string.

### Likelihood Explanation
Preconditions are minimal: any caller invoking `IntentsSDK.createWithdrawalIntents` (or the bridges directly) with `assetId` mapped to a Sui-chain asset and `destinationAddress` = an all-zero (or otherwise valid-format but non-existent) 64-hex-char string. No RPC mocking beyond the existing `getCachedSupportedTokens` HTTP mock is needed for PoaBridge; HotBridge similarly requires only mocking `hotSdk.buildGaslessWithdrawIntent`. The attacker cost is zero - crafting a 64-character hex string is trivial, and the SDK offers no warning or rejection. Whether an actual fund loss occurs still depends on this generated intent being signed and executed by intents.near/the bridge (outside this repo's direct control), but the SDK's job of producing a safe, sign-ready intent fails at this step, which is the scope of this finding.

### Recommendation
Add an explicit rejection of the well-known unownable/degenerate Sui address (all-zero, and any other publicly known burn addresses) in `validateSuiAddress`, mirroring the existing `validateEthAddress` zero/dead-address guard in `packages/intents-sdk/src/lib/validateAddress.ts`. Additionally, consider extending `validateAddress`'s hex-based validators for Aptos/Movement/Starknet with the same all-zero guard, since they share the same vulnerability pattern.

// Aptos/Movement/Sui/Starknet addresses are hex field elements: case is not
// significant, and both zero-padded (0x000...01) and short (0x1) forms refer
// to the same address.
function compareHexAddress(a: string, b: string): boolean {
	const normalizedA = normalizeHexAddress(a);
	const normalizedB = normalizeHexAddress(b);
	if (normalizedA === null || normalizedB === null) return false;
	return normalizedA === normalizedB;
}

function normalizeHexAddress(address: string): string | null {
	const withoutPrefix = address.toLowerCase().startsWith("0x")
		? address.slice(2)
		: address;
	if (withoutPrefix.length === 0 || !/^[0-9a-fA-F]+$/.test(withoutPrefix)) {
		return null;
	}
	const withoutLeadingZeros = withoutPrefix.replace(/^0+/, "");
	return withoutLeadingZeros.toLowerCase() || "0";
}

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	destinationMemo: string | undefined;
	amount: bigint;
}): Extract<IntentPrimitive, { intent: "ft_withdraw" }> {
	const { contractId: tokenAccountId } = utils.parseDefuseAssetId(
		params.assetId,
	);
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: tokenAccountId,
		amount: params.amount.toString(),
		memo: createWithdrawMemo({
			receiverAddress: params.destinationAddress,
			xrpMemo: params.destinationMemo,
		}),
		min_gas: MIN_GAS_AMOUNT,
	};
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}

	public async createWithdrawalIntents(args: {

						amount: actualAmount,
					},
					feeEstimation: args.feeEstimation,
					referral: args.referral ?? this.referral,
				});
			}
		}
