## Title
Webhook `shop-domain` (and topic) header is not covered by the HMAC signature, allowing a validated body to be replayed under a spoofed shop — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate` succeeds, then hands the handler the `shop`, `topic`, `api_version`, and `webhook_id` values straight from the request headers. The HMAC, however, is computed only over the raw request body — none of these header fields are cryptographically bound to the signature. This breaks the equality the module implicitly claims: `hmac_valid? == request_authentic_for(shop, topic, body)`; in reality `hmac_valid? == body_authentic()` only.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no relation to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm the signature is computed solely from `verifiable_query.to_signable_string`, i.e., the raw body: [4](#0-3) 

Because the `shop-domain` header sits entirely outside the HMAC's scope, any HTTP request whose **body** carries a valid HMAC for `Context.api_secret_key` will pass validation regardless of which shop domain, topic, or webhook id is asserted in the headers. An attacker who can obtain one valid `(body, hmac)` pair — for example from their own store's legitimately delivered webhook, or from a topic where body content is attacker-influenced/predictable — can resend that exact body+hmac pair to the same endpoint while swapping the `x-shopify-shop-domain` header to a victim shop. `Registry.process` will accept it as valid and invoke the handler with `shop: <victim>` alongside attacker-supplied body content, since nothing binds the shop identity to the signed bytes.

### Impact Explanation
This crosses a tenant boundary: the gem is presenting the host application's webhook handler with attacker-controlled `shop` + `body` combination that was never actually issued by Shopify for that shop. Any host logic that uses `WebhookMetadata#shop` to select the tenant/session context (the intended and documented use, per `webhook_handler.rb`) can be made to write/process data against the wrong merchant's session using attacker-chosen payload content — i.e., cross-tenant access driven purely by an unauthenticated header value that the gem never validates as bound to the signature.

### Likelihood Explanation
Exploitability depends on the attacker being able to acquire at least one valid `(body, hmac)` pair signed with the app's `api_secret_key` for some webhook delivery (e.g., from their own installed/legitimate shop instance, which is a normal, unprivileged capability for any merchant who installs the app), and then replaying that exact body against the app's public webhook endpoint with a different `shop-domain` header. No access to the app's secret or any privileged credential is required — only the ability to receive/capture one's own legitimate webhook and resend it.

### Recommendation
Bind the shop domain (and ideally the topic) into the signed payload verification path — e.g., include the `shop-domain` header value in `to_signable_string`, or otherwise verify out-of-band that the `shop` claimed in the headers actually corresponds to a shop with an active session/installation before trusting it, rather than deriving trust solely from a body-only HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (or otherwise gets a legitimate webhook delivered to their own endpoint capture) and receives a real webhook request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-body>`, and body `B`.
2. Attacker resends the same raw body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(body, secret)` — this still matches, since the body/hmac pair is unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, so the host application processes attacker data under the victim's tenant identity: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
