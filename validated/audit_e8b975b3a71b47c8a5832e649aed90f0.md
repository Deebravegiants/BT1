### Title
`placeOrder()` on the Tron IntentGatewayV2 permanently locks user overpaid native ETH/TRX with no refund path - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` accepts native-token overpayment via `msg.value` but, unlike its EVM counterpart, never refunds the unspent remainder back to the caller and never persists it as recoverable escrow. The excess is silently stranded in the contract.

### Finding Description
`placeOrder` tracks a running `msgValue` local variable as it consumes `msg.value` to cover native-token order inputs [1](#0-0)  and, if `order.fees > 0`, either swaps remaining `msgValue` for the fee token via `swapETHForExactTokens{value: msgValue}` or pulls the fee token via `safeTransferFrom` [2](#0-1) . After this block the function immediately emits `OrderPlaced` and returns [3](#0-2) . There is no check of the leftover `msgValue` and no call to send it back to `msg.sender`.

This is a direct analog of the reported `mintFounderHero()` bug class: the contract computes a required payment, allows the caller to send more than required via `msg.value`, and provides no mechanism to reclaim the difference.

Contrast with the equivalent EVM contract, `evm/src/apps/IntentGatewayV2.sol`, which explicitly refunds unspent native tokens after the same fee-swap logic:
```
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [4](#0-3) 

The Tron file has no equivalent statement anywhere in `placeOrder`, and grepping the file for refund/`_sendValue` patterns confirms it only appears in unrelated code paths (`cancelOrder`, `onAccept`, `withdraw`), not in `placeOrder`. There is also no way for the user to later reclaim this ETH: `_orders[commitment][address(0)]` is only credited with the exact `reducedInputs[i].amount` for the native input leg [5](#0-4) , so the overpaid amount is not tracked in escrow and cannot be withdrawn via `withdraw()` on fill/cancel/refund. The only path that moves stray native balance out of the contract is `SweepDust`, which is triggered exclusively by a privileged cross-chain message from Hyperbridge governance (`RequestKind.SweepDust`) [6](#0-5) , not by the user.

### Impact Explanation
Any unprivileged user who calls `placeOrder` with `msg.value` exceeding the sum of native input amounts plus the native-to-feeToken swap cost permanently loses the excess. This is a direct, user-triggered fund freeze on the Tron deployment of the Intent Gateway, reachable from a single submitted transaction with no admin, governance, or attacker collusion required. Given that Tron transactions routinely originate from wallets/SDKs that may over-provision `msg.value` (mirroring the exact same defensive pattern the EVM tests validate — e.g. `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, `testPlaceOrder_RefundsExcessNativeToken`), routine overpayment is a realistic, not contrived, scenario.

### Likelihood Explanation
High. The pattern of sending `nativeValue`/`value` slightly higher than the computed minimum (to survive slippage in the Uniswap `swapETHForExactTokens` call, or simple gross-input-plus-fee framing as documented in `placing-orders.mdx`) is the officially recommended integration pattern [7](#0-6) . Every ordinary caller following this documented flow on the Tron gateway will lose any overpaid amount, with no error or revert to warn them.

### Recommendation
Add the same "refund unspent native tokens" step present in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`: after computing/consuming `msgValue` for inputs and fees, if `msgValue > 0`, send it back to `msg.sender` (e.g., via a low-level `call{value: msgValue}("")` with success check, matching the pattern already used elsewhere in this same file for native transfers). Alternatively, tighten validation so `msg.value` must exactly equal the sum of required native inputs plus the exact swap cost, causing the transaction to revert on overpayment rather than silently retaining funds.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` where `order.inputs` contains one native-token (`address(0)`) leg of `1 ether` and `order.fees = X` (paid via native swap).
2. User sends `msg.value = 1 ether + swapCost + 0.5 ether` (intentional/unintentional overpayment, exactly as the EVM-side test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` demonstrates is a legitimate caller pattern) [8](#0-7) .
3. In the Tron contract: the native input leg consumes `1 ether` from `msgValue` [9](#0-8) ; the fee block consumes `swapCost` via `swapETHForExactTokens{value: msgValue}` — note it forwards the *entire remaining* `msgValue` including the 0.5 ether surplus to the router as `amountInMaximum`-style spend and never updates or checks a residual, unlike the EVM version which does `msgValue -= amounts[0]` [10](#0-9)  vs the Tron version, which has no such line [11](#0-10) .
4. Function returns; the 0.5 ether surplus is now stuck in the contract balance, uncredited to any escrow slot the user can withdraw, and only movable via the privileged `SweepDust` governance message.

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
