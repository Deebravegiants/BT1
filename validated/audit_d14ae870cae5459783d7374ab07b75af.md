Audit Report

## Title
Unsigned integer wraparound in message staleness check allows bypass of the freshness/anti-replay guard - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` casts the attacker-controlled `int64` field `payload.Timestamp` to `uint` when checking message freshness, without validating it is non-negative or within a sane range first. A negative `Timestamp` wraps to a very large `uint`, making the staleness comparison `uint(now)-MaxAllowedMessageAgeSec > uint(payload.Timestamp)` always false, bypassing the freshness/anti-replay check entirely.

## Finding Description
`TriggerRequestPayload.Timestamp` is declared as `int64` and is populated directly from client-supplied JSON via `json.Unmarshal(body.Payload, &payload)` [1](#0-0)  and [2](#0-1) . Before the staleness check, the code only rejects `Timestamp == 0` [3](#0-2) ; it performs no lower/upper bound validation. `HandlerConfig.MaxAllowedMessageAgeSec` is a `uint` [4](#0-3) , and the freshness comparison casts the signed `payload.Timestamp` to `uint` and compares against `uint(now) - MaxAllowedMessageAgeSec` [5](#0-4) . A negative `int64` timestamp converts to a value near `2^64`, which is always greater than `uint(now)-MaxAllowedMessageAgeSec`, so the `>` condition is false and the "stale message" rejection branch never executes. If it passes, the message is forwarded unmodified to every DON member node [6](#0-5) .

## Impact Explanation
This is a real logic defect: the staleness/freshness check can be defeated by sending a negative `timestamp` value in the JSON payload, causing the check to be bypassed instead of correctly rejecting the malformed/out-of-range timestamp. However, the actual security value of the bypassed check is limited: bypassing it does not forge signatures, does not allow impersonation of another user, and does not bypass authentication — it only means a message with an invalid/negative timestamp field is forwarded to DON nodes rather than being rejected with "stale message." The message must still pass whatever signature/message-validation happens upstream in `ValidatedRequestFromMessage` and DON-side processing. There is no fund movement, key exfiltration, or auth bypass demonstrated; the impact is limited to the DON nodes receiving a `web_api_trigger` message with a nonsensical timestamp field, which downstream trigger-processing logic (not shown to be reachable here) would need to separately validate. This does not clearly map to any of the listed in-scope high-impact categories (auth/role bypass, key exfiltration, unauthorized fund movement, gateway impersonation, allowlist bypass, cross-user response corruption) — it is a minor input-validation robustness issue in a supplementary freshness check, not a replay-attack enabler, since it doesn't allow replaying a genuinely old message with a valid past timestamp (that would require the wraparound to make an old, valid `Timestamp` appear fresh, which isn't the primary scenario described — the described PoC uses a negative timestamp, which is itself invalid input, not a genuinely stale replayed message).

## Likelihood Explanation
The `Timestamp` field is fully attacker-controlled and trivial to set to a negative value in an unprivileged request; the bug is real and easily triggered, but its practical exploitation value against any specific downstream harm is not established beyond causing an already-questionable input to bypass a redundant check.

## Recommendation
Validate `payload.Timestamp > 0` (and not too far in the future) before comparison, and perform the freshness check with signed 64-bit arithmetic (`time.Unix(payload.Timestamp, 0)`, compared via `time.Time.Before`/`Sub`) rather than casting to `uint`.

## Proof of Concept
Send a `web_api_trigger` legacy message with `payload.Timestamp = -1` to the gateway's user-facing endpoint; the "stale message" branch in `HandleLegacyUserMessage` (handler.go:372-383) is skipped due to unsigned wraparound, and the message is forwarded to DON member nodes despite carrying an invalid timestamp.
