### Title
Fee-on-transfer input tokens cause escrow over-crediting and insolvency in the Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows input tokens using `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount` based on the *stated* input amount, without ever measuring the actual token balance received. This is exactly the accounting-related bug class from the referenced report: the contract assumes `transferFrom` delivers the full requested amount and never verifies actual received balance.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the code calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments the escrow ledger `_orders[commitment][token]` by `reducedInputs[i].amount`, which is derived directly from the user-supplied `order.inputs[i].amount` (minus protocol fee), not from any measured balance delta.

If `token` is a fee-on-transfer (deflationary) ERC-20, the gateway contract actually receives less than `order.inputs[i].amount`. The escrow mapping `_orders[commitment][token]` is nevertheless credited for the full nominal amount. This directly creates a shortfall between the sum of all `_orders[...][token]` claims and the contract's real token balance.

This is contrasted with the maintained (non-Tron) implementation `evm/src/apps/IntentGatewayV2.sol`, which explicitly guards against this by measuring the balance delta: [2](#0-1) 
and has dedicated regression tests confirming the fix (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`. The Tron contract does not carry this fix over into its escrow-accounting path — the predispatch branch of the Tron contract does perform balance-based dust accounting (`balance = IERC20(token).balanceOf(dispatcher)`), but the simple/direct deposit branch (lines 450-469) does not.

### Impact Explanation
When a user places an order with a fee-on-transfer token as input, the escrow accounting (`_orders[commitment][token]`) overstates the contract's actual holdings for that token by the transfer-fee amount. Because escrow accounting is a shared ledger across all orders for a given token, this creates a system-wide deficit: the sum of all outstanding claims (`_orders[commitment][token]` across all commitments) can exceed the contract's actual token balance.

Consequences:
- Whichever order (solver fill, cancellation, or refund) is redeemed last for that token will find the contract under-collateralized and the transfer will fail or partially drain funds meant for a different, still-outstanding order — a permanent freezing/loss-of-funds condition for at least one legitimate order holder.
- Because the shortfall is silently absorbed into a shared pool rather than isolated per-order, other users' escrowed funds can effectively be drained to cover the missing amount for the fee-on-transfer order, i.e. cross-order fund leakage.
- This qualifies as a valid Medium/High severity accounting bug per the rules (concrete freezing/loss of escrowed user funds), reachable directly by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer token.

### Likelihood Explanation
Likelihood is moderate to high: any user (not just an attacker) can trigger this simply by using a common deflationary/fee-on-transfer ERC-20 (a well-known token category that exists on many chains, including Tron/TRC-20 analogs) as an order input. No special privileges or preconditions are required beyond `placeOrder` accepting an arbitrary `token` address in `order.inputs`, which it does.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the actual token balance before and after `safeTransferFrom` in the non-predispatch escrow path of the Tron contract, and use the measured delta (rather than the stated `order.inputs[i].amount`) to compute `reducedInputs`/`_orders[commitment][token]` credits, e.g.:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
then compute `reducedInputs`/commitment/escrow credit from this corrected amount, consistent with the mainline EVM implementation.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 `FOT` (as in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`'s `FeeOnTransferToken`, e.g. 1% fee) on the Tron-targeted `IntentGatewayV2`.
2. User approves and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `safeTransferFrom(user, gateway, 1000e18)` executes; gateway actually receives `990e18` (1% burned/fee).
4. `_orders[commitment][FOT]` is credited `1000e18` (or `1000e18` minus protocol fee), not `990e18`.
5. Repeat with a second unrelated order for the same `FOT` token that deposits correctly-accounted funds.
6. When both orders attempt to be filled/cancelled, the cumulative claimed escrow (`sum of _orders[...][FOT]`) exceeds `FOT.balanceOf(gateway)`, causing the later redemption to revert (fund freeze) or, in more compounded scenarios, draining escrow meant for other users.

**Caveat/uncertainty**: I based this on static reading of `evm/tron/contracts/apps/IntentGatewayV2.sol`; I could not find/run Tron-specific fee-on-transfer regression tests analogous to those covering `evm/src/apps/IntentGatewayV2.sol`, and I have not been able to confirm whether this Tron contract file is actively deployed/in-scope versus a stale copy of an older version. If it is not actually deployed on Tron mainnet, this finding is theoretical for that specific file, though the code pattern itself is the vulnerability described in the report.
