## Finding: Webhook `shop` and `topic` are not covered by the HMAC signature

The relevant code path lives in `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

`Request#to_signable_string` only returns the raw HTTP body — it does not include the shop domain or topic: [1](#0-0) 

`shop` and `topic` are instead read straight from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` verifies the HMAC over that body-only string, then dispatches using the header-derived `topic`, and constructs `WebhookMetadata` (passed to the app's handler) using the header-derived `shop`: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [4](#0-3) 

### The identity binding that breaks

The intended equality is: `hmac == HMAC(secret, body)` **and** `shop == the shop that generated that body`. In this code, only the first half is checked — the `shop` (and `topic`) the app trusts when routing/attributing the webhook is never part of the signed payload.

### Why this is exploitable by an unprivileged actor

Any user can install a public app on their own (even a free/dev) store and receive one legitimate, validly-signed webhook (raw body + `x-shopify-hmac-sha256`). Because `shop-domain` and `topic` are outside the signed content, that same `(raw_body, hmac)` pair remains valid when POSTed again with `x-shopify-shop-domain` (and/or `x-shopify-topic`) swapped to any victim shop. `HmacValidator.validate` still returns `true` because it never looked at those headers, and `Registry.process` will hand the attacker-chosen `shop`/`topic`/body combination to the app's webhook handler as if it legitimately came from the victim shop — a cross-tenant data-attribution/injection issue for any app that uses `WebhookMetadata#shop` to select the tenant record to update.

This matches the "field acted on but not covered by the HMAC" bug class explicitly called out in scope, and results in cross-tenant impact without needing `api_secret_key`, an access token, or any privileged account — only the ability to install the app once and replay an HTTP request.

### Title
Webhook `shop`/`topic` headers unauthenticated — HMAC covers only the body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC validated by `Utils::HmacValidator.validate` in `Registry.process` never covers the `shop-domain` or `topic` headers used for routing and tenant attribution.

### Finding Description
`Request` extracts `shop`, `topic`, `webhook_id`, `api_version` from HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) that are entirely independent from the value used to compute/verify the HMAC (`to_signable_string`, lines 35-38, returns only the body). `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only the body's HMAC, then uses the unauthenticated `topic` to select the handler and the unauthenticated `shop` to build `WebhookMetadata` passed to the app. Any previously-observed valid `(body, hmac)` pair — trivially obtainable by installing the app on an attacker-controlled store — can be replayed with different `shop`/`topic` header values, since nothing in the signed content binds them together.

### Impact Explanation
Cross-tenant access: an app that trusts `WebhookMetadata#shop` to know which merchant's data to update/act on can be made to process attacker-supplied webhook bodies "as if" they came from an arbitrary victim shop, since the shop identity is never part of the cryptographically verified content.

### Likelihood Explanation
High — no credentials, tokens, or `api_secret_key` needed by the attacker. Only a single legitimate webhook delivery (obtainable by installing any public app that ships this library) is required as raw material for the replay.

### Recommendation
Include `shop`, `topic`, and other headers relied on for authorization/routing decisions in the HMAC-signed payload (or otherwise cryptographically bind them to the body), so the signature verifies the full identity tuple `(shop, topic, body)` rather than the body alone.

### Proof of Concept
1. Install the target app on an attacker-controlled dev store `evil.myshopify.com`; capture one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for secret-signed `B`).
2. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim.myshopify.com` (and, if desired, a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which only re-derives HMAC over `B` — validation succeeds.
4. The app's registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen>, body: <attacker-chosen>, ...)`, causing the host application to act on `victim.myshopify.com`'s tenant record with attacker-controlled webhook content.

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
