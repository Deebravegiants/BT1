### Title
Webhook `shop-domain` Header Not Covered by HMAC Allows Cross-Tenant Impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `HmacValidator.validate` checks binds to the body bytes only. The `shop-domain` (and `topic`, `webhook_id`) headers are read separately via `shopify_header` and are never part of the signed data, yet `Registry.process` trusts `request.shop` as the authoritative tenant identifier when dispatching to the app's webhook handler.

### Finding Description
`Registry.process` validates the request with `Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and calls `handler.handle(data: ...)`. [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC. [3](#0-2) 

For webhook requests, `to_signable_string` is defined to return `@raw_body` exclusively — the `shop`, `topic`, and `webhook_id` accessors read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) that are completely outside the signed payload. [4](#0-3) 

The equality the code implicitly assumes is: `shop header == tenant that produced the HMAC-signed body`. In reality, the HMAC only proves `body == HMAC_secret(body)`; it says nothing about which shop header accompanied it. Because every shop installed on a given app shares the *same* `client_secret`/signing key, a party who legitimately receives a genuine webhook for their own shop (a valid, unprivileged install of the app) possesses a body+HMAC pair that remains valid for that exact body regardless of which `shop-domain` header value is sent alongside it. That party can then resend the same body with a `shop-domain` header naming a different shop, and `Registry.process` will pass that spoofed shop straight to the handler as the authenticated tenant.

### Impact Explanation
This breaks the tenant/shop authentication boundary: `handler.handle` receives `WebhookMetadata#shop` believing it to be cryptographically tied to the payload, when it is not. Any downstream logic in the host application that keys off `WebhookMetadata#shop` (e.g., looking up which merchant's data/session to update, un-installing, GDPR redaction routing) can be tricked into acting on the wrong tenant's context using data supplied by an unrelated shop — a cross-tenant confusion analogous to the "swapping of pools" flaw (acting on an unverified identity field alongside verified-but-differently-scoped data).

### Likelihood Explanation
Exploitation requires only: (1) the app is installed on any shop the attacker controls (a normal, unprivileged merchant install — not a leaked secret), (2) the attacker's own webhook endpoint or logs to capture one legitimate `raw_body` + `X-Shopify-Hmac-Sha256` pair from their own shop, and (3) the ability to POST that same body/HMAC to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header. No secret, token, or privileged access is needed beyond a self-service app install.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the signature (e.g., re-derive/validate the shop against the session associated with the webhook, or require the caller to cross-check `shop` against an independently-verified per-shop identifier before trusting it in `WebhookMetadata`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`, and `secret` is shared across all shops using this app).
2. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body `B`, identical `X-Shopify-Hmac-Sha256: H`, but with `X-Shopify-Shop-Domain: victim.myshopify.com` (and `X-Shopify-Topic` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...with victim domain...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e., `B` only) and matches `H` — validation **succeeds**. [2](#0-1) 
4. `handler.handle` is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload/HMAC pair never originated from Shopify for that shop — the host app processes attacker-supplied data under the victim's tenant identity.

          received_signature = verifiable_query.hmac
