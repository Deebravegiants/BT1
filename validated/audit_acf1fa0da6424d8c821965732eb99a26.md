### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (and `topic`, `webhook_id`, `api_version`) is read from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when building the `WebhookMetadata` that is handed to the app's handler. This breaks the intended identity binding between "the HMAC that proves the request body was produced by Shopify" and "the shop the body is attributed to," letting anyone who can produce one validly-signed webhook body replay it under an arbitrary victim shop identity.

### Finding Description
The HMAC is only computed over the raw body: [1](#0-0) 

`shop` is read straight from a header, which is not part of that signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it against the received `hmac`: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata delivered to the app's handler — none of these header-derived values are re-validated against anything tied to the signature: [4](#0-3) 

The documented handler contract explicitly instructs apps to key their tenant logic off `data.shop`: [5](#0-4) 

Because all shops that install the same app share one signing secret (`Context.api_secret_key`, and optionally `Context.old_api_secret_key`) — the HMAC is app-scoped, not shop-scoped — an attacker who legitimately installs the target app on their own store can generate any number of genuinely-signed `(raw_body, hmac)` pairs (e.g. by creating orders/products/customers on their own store, or by triggering mandatory compliance topics like `shop/redact`, `customers/redact`, `app/uninstalled`). The attacker can then POST that same, still-validly-signed body directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for the victim's shop domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` reports the event to the handler as if it came from the victim shop.

This is precisely the "field acted on but not covered by the HMAC" identity-binding break called out in scope: the equality the code implicitly assumes — `shop header used by the handler == shop that produced the signed body` — does not hold and is never checked.

### Impact Explanation
This is a cross-tenant access vulnerability: an unprivileged internet user (any merchant/attacker able to install the app on a store they control) can make the app believe an event occurred for a different tenant (victim shop) than the one that actually produced it. Depending on how the host app implements its handler (per the documented contract, keyed on `data.shop`), this can be used to inject fabricated data attributed to a victim shop, trigger mandatory GDPR/compliance webhook logic (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim's tenant, or spoof `app/uninstalled` to make the app deprovision/wipe a victim shop's stored session/access token — all without ever touching the victim's actual store or credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that exposes an HTTP webhook endpoint per the documented usage (`docs/usage/webhooks.md`): the attacker needs only to install the app on their own shop (a normal unprivileged action), capture one legitimately-signed webhook delivery for any registered topic, and replay it with a modified `shop-domain` header to the same public endpoint. No secret material, TLS interception, or victim interaction is required.

### Recommendation
Bind the shop identity into the signature verification path rather than trusting an unauthenticated header:
- Have `Registry.process` (or the app, per documented guidance) cross-check `request.shop` against an expected/registered shop for that webhook subscription before dispatching to the handler, or
- Extend `to_signable_string` / the HMAC validation step to incorporate the `shop-domain`, `topic`, and `webhook-id` headers so that tampering with them invalidates the HMAC, mirroring the fix pattern used for `chain_hash` binding in the referenced report (bind the "wire" identity into the value that is actually verified).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for topic `orders/create` (or any topic the app handles).
2. Shopify delivers a real webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over BODY using app's client_secret>`, `x-shopify-topic: orders/create`
   - Body: `BODY` (JSON payload, largely attacker-controlled content since it's the attacker's own order/customer/product data)
3. Attacker replays the exact same `BODY` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but swaps the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `BODY` — it succeeds because the body is unmodified: [6](#0-5) 
5. `WebhookMetadata` is built with `shop: request.shop` = `"victim-shop.myshopify.com"` and passed to the app's handler as if the event genuinely originated from the victim's store: [7](#0-6) 
6. The host application's handler (built per the documented contract) processes/persists the attacker-controlled body under the victim shop's tenant context.

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
