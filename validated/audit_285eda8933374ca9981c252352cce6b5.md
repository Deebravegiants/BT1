## Title
Webhook shop attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, but the `shop` (and `topic`/`api_version`/`webhook_id`) value that identifies *which tenant* the webhook belongs to is read from an HTTP header that is never included in the signed content. Any attacker who can obtain one valid `(body, HMAC)` pair for a shop they control can replay it to the same endpoint with the `shop-domain` header rewritten to a different merchant, and the request still passes `Utils::HmacValidator.validate`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers that are completely outside the HMAC's scope: [2](#0-1) 

`Registry.process` validates the request using only this body-based HMAC, then immediately trusts `request.shop` as the tenant identifier passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop used as the tenant key for handler.handle`

In this code, the left side is empty — the HMAC never covers `shop-domain` — so the equality is never enforced. Since the app's `api_secret_key` is a single per-app secret shared across every installed shop (not a per-shop secret), any merchant who has legitimately installed the app can:
1. Trigger a real webhook event in their own shop (shop A) and capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — both values are visible to them since it's their own webhook delivery.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` changed to a victim shop (shop B) that also uses the app.
3. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret; it never inspects the shop header.
4. `Registry.process` invokes the app's `WebhookHandler#handle` with `data.shop == shop B`, causing attacker-controlled webhook content to be processed as if it originated from shop B.

### Impact Explanation
This breaks the cross-tenant isolation the gem is expected to provide. Depending on how the host application uses `WebhookMetadata#shop` (which the library's own docs recommend using directly to key persistence/job dispatch, e.g. `perform_later(shop_domain: data.shop, ...)`), an attacker can:
- Inject forged data attributed to a shop they don't control (e.g., fake `orders/create` payloads processed under shop B's account).
- Trigger mandatory compliance webhooks (`customers/redact`, `shop/redact`, `customers/data_request`) against a victim shop using attacker-crafted body content, potentially causing unwanted data redaction/deletion for a tenant the attacker has no relationship with.

This is a cross-tenant access vulnerability achievable by any unprivileged party that has installed the app on at least one shop — no access token, API secret, or privileged account is required beyond normal app installation.

### Likelihood Explanation
Any developer/merchant who installs the app becomes able to generate valid `(body, hmac)` pairs for their own shop and can immediately attempt this replay against the shared webhook endpoint with a different `shop-domain` header. No credential theft, TLS interception, or social engineering is needed — only observing one's own legitimately delivered webhook.

### Recommendation
Bind the shop identity into the signed/verified material, or otherwise cryptographically tie the shop header to the specific delivery, e.g.:
- Require the host app to verify that the `shop-domain` header corresponds to a shop with an active, previously-established registration/session before trusting `data.shop`, and reject requests where the shop doesn't match an expected value (e.g., known via route/session), and/or
- Document/enforce that `Registry.process` callers must independently confirm the tenant, since the HMAC alone does not authenticate the shop attribution — update `HmacValidator`/`Request` so that shop, topic, and webhook id are included in the signature verification path where feasible, matching Shopify's actual webhook authenticity guarantees.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has the app installed there.
# 1. Trigger any webhook (e.g., orders/create) on shop-a and capture the raw body + HMAC header
#    that Shopify sent to the app's endpoint.
raw_body = '{"id":1,"note":"legit order on shop-a"}'
hmac_header = "<value captured from the real Shopify request>"

# 2. Replay the exact same body/HMAC to the same endpoint, but swap the shop header
#    to a victim shop that also uses the app.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,      # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim shop, not covered by HMAC
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. This passes because HmacValidator only checks raw_body against the shared api_secret_key.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with data.shop == "shop-b.myshopify.com",
#    even though the payload actually originated from shop-a.
```
