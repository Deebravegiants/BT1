## Title
Unrestricted `CallDispatcher.dispatch()` Allows Anyone to Steal Any ETH/ERC20 Balance Held by the Shared CallDispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a permanently deployed, shared singleton used by `IntentGatewayV2`, `IntentsBase`/`ExtrinsicIntents`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` as a temporary holder of user funds during predispatch/postdispatch calldata execution. Its `dispatch(bytes memory encoded)` function is fully `external` with zero access control — any unprivileged caller can invoke it directly with an arbitrary `Call[]` payload and redirect whatever ETH or ERC20 balance the dispatcher currently holds to any address, exactly analogous to the reported `D3Proxy.refundETH()` bug where anyone could drain the contract's balance.

### Finding Description
`CallDispatcher.dispatch` has no caller restriction and no check on the balance being moved — it simply executes every `Call{to, value, data}` the caller supplies: [1](#0-0) 

The contract also has an unrestricted `receive()` that accepts ETH from anyone: [2](#0-1) 

`CallDispatcher` is not an ephemeral, per-call contract — it is deployed once and reused for the lifetime of the associated apps, as shown by the deploy scripts and docs that list it among stable, addressable "contract addresses": [3](#0-2) [4](#0-3) 

It genuinely holds real user assets mid-flow. In `IntentGatewayV2.placeOrder`, predispatch assets (including native ETH) are transferred directly to the `dispatcher` address before any calldata executes, then swept back: [5](#0-4) 

In `IntentsBase._execute`, output tokens/ETH are also routed through and left temporarily on the same shared `dispatcher` before being swept back and counted as protocol dust: [6](#0-5) 

And `WrappedHyperFungibleTokenUpgradeable`/`HyperFungibleToken` deliver bridged tokens (potentially unwrapped native ETH) directly to the `CallDispatcher` address before invoking `dispatch()` on user-supplied calldata: [7](#0-6) 

Because the dispatcher is shared across every app and every order/transfer that routes through it, any dust, partially-swept balance, slippage residue, or accidentally-sent ETH sitting in the dispatcher's balance at any point is not protected — anyone can call `dispatch()` on the well-known, addressable `CallDispatcher` contract with a `Call[]` that sends the current balance to themselves, in the exact same permissionless pattern as the reported `refundETH()` bug, except generalized to arbitrary ERC20 tokens as well as native ETH, and to an attacker-chosen destination rather than only `msg.sender`.

### Impact Explanation
Any ETH or ERC20 tokens transiently held by the shared `CallDispatcher` — whether from `IntentGatewayV2` predispatch/postdispatch flows, `IntentsBase`/`ExtrinsicIntents` output-calldata execution, or `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-triggered bridging — can be permissionlessly stolen by any address that observes or anticipates a non-zero balance on the dispatcher. This constitutes concrete theft of user/protocol funds routed through a core, shared Hyperbridge periphery contract.

### Likelihood Explanation
`dispatch()` requires no privilege and no proof — a bare call with attacker-controlled `Call[]` targeting `CallDispatcher`'s own balance is trivially reachable by any account, at any time the dispatcher is not at zero balance (e.g., between the asset-in and sweep-back steps of a multi-call sequence, on slippage dust, or via any wayward direct ETH transfer via `receive()`).

### Recommendation
Restrict `CallDispatcher.dispatch()` so it can only be invoked by the specific app contract that owns/initiated the current batch of calls (e.g., an authorized-caller mapping/modifier set at construction or per-app instance), or make the dispatcher single-use/ephemeral per invocation (e.g., deploy a fresh minimal-proxy dispatcher per call, or use `CREATE2`+`SELFDESTRUCT`/transient patterns) so no persistent, sweepable balance can ever be observed by third parties. At minimum, add reentrancy protection and ensure balances never rest on the dispatcher outside of the atomic transaction that deposits and sweeps them.

### Proof of Concept
1. Wait for (or trigger, e.g., via a `WrappedHyperFungibleToken` bridge-and-swap that leaves rounding dust) a state where `CallDispatcher` holds a non-zero ETH or ERC20 balance — this is a normal, recurring condition given its use in `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken` flows.
2. From any account, call `CallDispatcher.dispatch(abi.encode(calls))` where `calls[0] = Call({to: attackerAddress, value: address(dispatcher).balance, data: ""})` for ETH, or an ERC20 `transfer(attacker, balance)` payload for tokens.
3. `dispatch()` executes the call unconditionally (no `onlyOwner`/`onlyApp` check exists), transferring the dispatcher's balance to the attacker.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
