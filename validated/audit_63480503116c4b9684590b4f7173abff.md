### Title
Non-embedded session cookie value is trusted as a session id without any integrity binding, enabling cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw `shopify_app_session` cookie value verbatim as the session id for non-embedded apps, with no signature, HMAC, or other proof that the value was produced by this gem's own OAuth flow rather than forged by the caller.

### Finding Description
For non-embedded apps, `current_session_id` reads the session id directly out of the cookie jar: [1](#0-0) 
and `cookie_session_id` simply returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` unchanged: [2](#0-1) 

The cookie itself carries no cryptographic binding to the OAuth flow that created it — `SessionCookie` is a plain struct with `name`, `value`, `expires`, and no signature field: [3](#0-2) 

During `validate_auth_callback`, the cookie's `value` is deterministically derived from the shop domain (and user id for online sessions) via `Session.from` / `session.id`: [4](#0-3) 
and the id formats are predictable and computable by anyone who knows the shop domain: [5](#0-4) 

The identity binding that should hold is: **bytes read from the cookie == bytes this gem's OAuth flow actually wrote for the current legitimate visitor's shop**. Because the cookie is unsigned plaintext, that equality is never checked — only the *name* of the cookie is checked, not its provenance. Any value placed under `shopify_app_session` (e.g., `offline_victim-shop.myshopify.com`) is accepted as-is and handed back to the host application as "the" session id to look up in its session store, per the documented usage: [6](#0-5) 

This matches the report's bug class of a value trusted without any cryptographic tie to the authentication event that supposedly produced it, analogous to "a session id derived from unauthenticated bytes."

### Impact Explanation
Session ids for offline sessions are simply `"offline_#{shop}"` — fully derivable from a publicly known shop domain, with zero secret material. If an attacker can get their own unsigned cookie value set/overwritten under the `shopify_app_session` name (cookie tossing from a sibling subdomain, response-splitting/header-injection elsewhere in the host stack, or any other mechanism that lets them control this one cookie), the host application built on this gem will resolve `current_session_id` to a different, victim shop's session id, retrieve that shop's stored `Session` (including its access token) from its session repository, and use it to make Admin API calls as the victim shop — resulting in cross-tenant access and access-token misuse.

### Likelihood Explanation
Exploitation requires the attacker to control the value of one specific cookie name in the victim's browser session for a non-embedded app, and it requires the host application to trust `current_session_id`'s return value directly for session lookup as documented. Because the session-id format is fully predictable from public shop domain names, no brute forcing or secret guessing is needed once cookie control is achieved — the entire protection rests on the gem never verifying that the cookie value was produced by its own `validate_auth_callback`.

### Recommendation
Bind the cookie value to the OAuth flow with a MAC (e.g., HMAC using `Context.api_secret_key`) covering the session id, and verify that MAC in `cookie_session_id`/`current_session_id` before treating the value as trusted. Alternatively, store only an opaque, unpredictable, server-generated token in the cookie and keep the shop-to-session mapping server-side, so a forged cookie value cannot be mapped to any other tenant's session.

### Proof of Concept
1. Attacker knows (or discovers) a victim's public shop domain, e.g. `victim-shop.myshopify.com` (shop domains are not secret).
2. Attacker computes the offline session id `offline_victim-shop.myshopify.com` per `offline_session_id`. [7](#0-6) 
3. Attacker sets their own browser's `shopify_app_session` cookie to that value (via any mechanism giving them control of that single cookie — no secret required since the cookie is unsigned plaintext).
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `offline_victim-shop.myshopify.com` verbatim. [1](#0-0) 
5. The host app looks up this id in its session store and retrieves the victim shop's `Session` object, including its access token, and uses it for subsequent Admin API calls — completing cross-tenant access.

          end
        end

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
