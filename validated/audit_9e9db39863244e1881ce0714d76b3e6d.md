### Title
`pallet-assets::do_transfer_approved` Does Not Check the Delegate's `AccountStatus`, Allowing a Blocked Spender to Still Move Approved Funds - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
`pallet-assets` has an account-level blacklist mechanism (`AccountStatus::Blocked`) analogous to the USDKG `notBlackListed` modifier. The `block()` extrinsic is meant to stop an account from further use of the asset. However, the transfer-on-behalf path, `do_transfer_approved` (invoked by the `transfer_approved` extrinsic), only validates the `owner` and `destination` accounts' status — never the delegate's (spender's) own `AccountStatus`. This is the exact same flaw as the USDKG `transferFrom()` bug: the modifier is applied to the token-holding parties but not to the address that is actually authorizing/executing the transfer.

### Finding Description
`pallet-assets` models a blacklist via `AccountStatus::Blocked`: [1](#0-0) 

An asset's `Freezer` can block an account with the `block()` extrinsic: [2](#0-1) 

Regular transfers correctly check the status of both the sender and the receiver, as confirmed by the pallet's own tests (`transferring_from_blocked_account_should_not_work`, `transferring_to_blocked_account_should_not_work`): [3](#0-2) 

However, the approval-based transfer path, `do_transfer_approved`, only fetches the `owner`/`delegate` approval, deducts the approved amount, and calls `transfer_and_die(id, owner, destination, amount, ...)`. It never inspects the delegate's own `AccountStatus`: [4](#0-3) 

This is reachable both from the `transfer_approved` extrinsic: [5](#0-4) 

and from the `fungibles::approvals::Mutate::transfer_from` trait implementation used by downstream integrations such as the ERC-20 precompile in `pallet-revive`: [6](#0-5) [7](#0-6) 

Because `transfer_and_die` only enforces the `owner`'s and `destination`'s account status (mirroring the balance mutation parties), a delegate that has been blocked by the asset's Freezer/admin retains full ability to execute `transfer_approved` using any pre-existing approvals, moving funds from any `owner` who approved it to any `destination`, entirely bypassing the block.

### Impact Explanation
This mirrors the exact impact scenario from the external report: a compliance/security team blocks a known-malicious or compromised address (e.g. a compromised contract that received approvals from victims as collateral/lending logic), expecting `block()` to stop that address from moving any assets it can access. Because the delegate's status is never checked in `do_transfer_approved`, the blocked address can still drain every outstanding approval granted to it prior to being blocked, defeating the purpose of the block/freezer mechanism entirely. Given `pallet-assets` underpins asset issuance on Asset Hub and other parachains, this undermines the compliance/security guarantees the blocking feature is meant to provide.

### Likelihood Explanation
High for any unprivileged account that already holds outstanding approvals at the time it is blocked. No privileged role compromise is required on the attacker's side — the attacker is simply the delegate itself (e.g. an already-compromised or malicious contract/account), and it calls the ordinary signed, permissionless extrinsic `transfer_approved` (or the analogous ERC-20 `transferFrom` precompile call) using approvals set up before the block. The only precondition is that approvals already exist, which is common in DeFi/collateral use of `pallet-assets`.

### Recommendation
In `do_transfer_approved` (`substrate/frame/assets/src/functions.rs`), before executing the transfer, check the delegate's own `Account` entry and reject with `Error::<T, I>::Frozen` (or a new `Error::<T,I>::Blocked`) if `AccountStatus::is_blocked()` (or `is_frozen()`) is true for the delegate — mirroring the checks already applied to `owner` and `destination` inside `transfer_and_die`.

### Proof of Concept
1. Admin creates asset `0`; account `1` mints balance and approves account `3` (delegate) to spend `50` via `approve_transfer`.
2. Asset's Freezer calls `Assets::block(freezer_origin, 0, 3)`, blocking delegate `3`.
3. Delegate `3` (still signed, unprivileged) calls `Assets::transfer_approved(RuntimeOrigin::signed(3), 0, 1, 2, 50)`.
4. Because `do_transfer_approved` never checks `3`'s own `AccountStatus`, the call succeeds and funds move from `1` to `2`, despite `3` being blocked — contradicting the documented intent of `block()` ("Disallow further unprivileged transfers of an asset id to and from an account") and the existing test coverage that only validates `owner`/`destination` blocking, not delegate blocking, as seen at [3](#0-2) .

/// The status of an asset account.
#[derive(Clone, Encode, Decode, Eq, PartialEq, Debug, MaxEncodedLen, TypeInfo)]
pub enum AccountStatus {
	/// Asset account can receive and transfer the assets.
	Liquid,
	/// Asset account cannot transfer the assets.
	Frozen,
	/// Asset account cannot receive and transfer the assets.
	Blocked,
}
impl AccountStatus {
	/// Returns `true` if frozen or blocked.
	pub fn is_frozen(&self) -> bool {
		matches!(self, AccountStatus::Frozen | AccountStatus::Blocked)
	}
	/// Returns `true` if blocked.
	pub fn is_blocked(&self) -> bool {
		matches!(self, AccountStatus::Blocked)
	}
}

		/// Origin must be Signed and the sender should be the Freezer of the asset `id`.
		///
		/// - `id`: The identifier of the account's asset.
		/// - `who`: The account to be unblocked.
		///
		/// Emits `Blocked`.
		///
		/// Weight: `O(1)`
		#[pallet::call_index(31)]
		pub fn block(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Blocked;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Blocked { asset_id: id, who });
			Ok(())
		}

	pub fn do_transfer_approved(
		id: T::AssetId,
		owner: &T::AccountId,
		delegate: &T::AccountId,
		destination: &T::AccountId,
		amount: T::Balance,
	) -> DispatchResult {
		let mut owner_died: Option<DeadConsequence> = None;

		let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(d.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);

		Approvals::<T, I>::try_mutate_exists(
			(id.clone(), &owner, delegate),
			|maybe_approved| -> DispatchResult {
				let mut approved = maybe_approved.take().ok_or(Error::<T, I>::Unapproved)?;
				let remaining =
					approved.amount.checked_sub(&amount).ok_or(Error::<T, I>::Unapproved)?;

				let f = TransferFlags { keep_alive: false, best_effort: false, burn_dust: false };
				owner_died =
					Self::transfer_and_die(id.clone(), owner, destination, amount, None, f)?.1;

				if remaining.is_zero() {
					T::Currency::unreserve(owner, approved.deposit);
					Asset::<T, I>::mutate(id.clone(), |maybe_details| {
						if let Some(details) = maybe_details {
							details.approvals.saturating_dec();
						}
					});
				} else {
					approved.amount = remaining;
					*maybe_approved = Some(approved);
				}
				Ok(())
			},
		)?;

		// Execute hook outside of `mutate`.
		if let Some(Remove) = owner_died {
			T::Freezer::died(id.clone(), owner);
			T::Holder::died(id, owner);
		}
		Ok(())
	}
