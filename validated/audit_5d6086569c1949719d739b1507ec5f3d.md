### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable content from the raw request body only, but exposes `shop` (from the `X-Shopify-Shop-Domain` header) as a trusted, verified attribute that host applications use to attribute the webhook payload to a specific tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over exactly `to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

But `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic binding to the body/HMAC and no sanitization against `ShopValidator`: [3](#0-2) 

The gem's own documentation confirms that `Registry.process` verifies the request "did indeed come from Shopify" and then forwards `data.shop` to the app's handler as the trusted tenant identifier used for storage/enqueueing (`shop_domain: data.shop`): [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop asserted by header == shop cryptographically bound to the signed bytes`. Because `to_signable_string` binds only the body, this equality is never checked — the header is trusted implicitly while only the body is authenticated with the shared secret.

### Impact Explanation
Any user who possesses one legitimately-signed webhook payload for their own shop (installed app owner can trivially capture their own real webhook requests) can replay that same raw body with an arbitrary `shopify-shop-domain` header value. Because the HMAC only signs `@raw_body`, the signature still validates via `HmacValidator.validate`/`Registry.process`, but the application will process/store the (attacker-chosen) payload under a different, spoofed shop identity — a cross-tenant data injection into another merchant's records, matching the "shop authenticated versus shop stored as session key/tenant identifier" analog class.

### Likelihood Explanation
Likelihood is high for any developer using the gem exactly as documented: `Registry.process` is the only verification step recommended, and the handler contract explicitly hands `data.shop` to the app as an already-validated tenant key. Nothing in the reachable code path (`Request` → `HmacValidator` → `Registry.process` → `WebhookHandler`) cross-checks the header against the signed bytes.

### Recommendation
Include the shop domain (and topic/webhook-id) inside the HMAC-signed content, or independently verify the `shop` header against a known/registered shop for that HMAC before exposing it to the handler, so the identity used to route/store data is cryptographically bound to the same bytes the HMAC verifies.

### Proof of Concept
1. App owner installs the app for `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and its valid `X-Shopify-Hmac-Sha256` header (this HMAC was computed by Shopify over the body only).
2. Attacker replays the same `raw_body` and same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` (lib/shopify_api/webhooks/request.rb:10-38) only look at the body/HMAC header, so `Utils::HmacValidator.validate` returns `true`.
4. `Registry.process` calls the handler with `data.shop == "victim-shop.myshopify.com"`, causing the host app to store/act on attacker-controlled data as if it belonged to `victim-shop`, per the documented handler pattern in docs/usage/webhooks.md:19-29.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
