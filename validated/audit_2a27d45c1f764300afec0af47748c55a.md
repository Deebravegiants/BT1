### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies an incoming webhook by checking only that the HMAC of the raw request body matches, then blindly trusts the `shop` value taken from an HTTP header when building the `WebhookMetadata` passed to the app's handler. The HMAC signature never covers the `shop` header, so the "verified" bytes and the "trusted shop identity" bytes are two disjoint sets — breaking the binding `verified_bytes == identity_bytes_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC of the request (i.e. of `raw_body` only) and, if valid, immediately forwards `request.shop` (the unauthenticated header value) to the registered handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature computed over `verifiable_query.to_signable_string` (the body) matches, but says nothing about the header-derived `shop`: [4](#0-3) 

Because the HMAC is computed with the app's `api_secret_key` over the body only, any request carrying a body + HMAC pair that was legitimately produced by Shopify for *some* shop (e.g. the attacker's own shop, which they fully control and can trigger webhook-firing events on) remains cryptographically valid no matter what `shop` header value is attached to the replayed request. An attacker who operates their own install of the app can capture one of their own valid webhook deliveries (raw body + `x-shopify-hmac-sha256`) and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches, since it never covered the header) and dispatch it to the handler tagged with the victim's shop, i.e. `WebhookMetadata#shop` reports the wrong tenant.

This exactly matches the report's root-cause pattern: a value used to drive a security-relevant decision that is not included in the value actually verified by the cryptographic check (analogous to the auction's success condition ignoring claimable fees that affect the same pool state being checked).

### Impact Explanation
Any downstream logic that keys persistence, authorization, or side effects off `WebhookMetadata#shop` (exactly what the gem's own documentation instructs consumers to do, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute one shop's webhook body to a different shop merely by an attacker forging the `shop` header while replaying a body+HMAC pair they legitimately obtained from their own tenant. This is a cross-tenant identity-binding break enabled purely by this gem's `HmacValidator`/`Webhooks::Request`/`Webhooks::Registry` design, requiring no access token, `api_secret_key`, or privileged account — only the ability to trigger a webhook on a shop the attacker controls and to send an arbitrary HTTP request to the app's public webhook endpoint.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must (1) control or have access to a shop that has the target app installed so they can capture a genuinely-signed webhook body/HMAC pair, and (2) know/guess the target's webhook endpoint (public, documented path). Both are realistic for any developer/tester able to install a public app on their own store, which is the standard "unprivileged internet user" capability level for Shopify apps.

### Recommendation
Include the `shop` (and ideally `topic`) as part of the signed payload verification, or bind the HMAC check itself to the specific shop by validating that the `x-shopify-shop-domain` header corresponds to a shop this app instance is actually installed for (looked up via stored session) rather than trusting the header verbatim after only validating body HMAC. At minimum, `Webhooks::Request#to_signable_string` should not be the sole basis for authenticating which shop the webhook is attributed to; document/require handlers to independently confirm shop legitimacy (e.g., via an existing offline session for that shop) before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers an event (e.g., `orders/create`) to receive a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and finds it matches `H` — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process/attribute the attacker-controlled body under the victim shop's identity.
