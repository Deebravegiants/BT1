### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop-tenant identity (`shop-domain` header) and other routing metadata (`topic`, `api_version`, `webhook-id`) are read directly from unauthenticated HTTP headers and are never included in the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` trusts these unauthenticated header values to select the handler and to populate the `shop` field passed to the app's webhook handler, breaking the binding between "bytes verified" and "identity acted on."

### Finding Description
The HMAC binding that Shopify webhooks rely on is supposed to guarantee: *the shop and topic that produced this signed body are the shop and topic the app acts on*. In this gem that equality is broken:

- `to_signable_string` only returns `@raw_body`: [1](#0-0) 

- `shop`, `topic`, `api_version`, and `webhook_id` are all derived from headers that are not part of the signed string: [2](#0-1) 

- `Registry.process` validates the HMAC against `to_signable_string` (i.e. only the body) and then unconditionally trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build the metadata handed to the app's business logic: [3](#0-2) 

- The shared HMAC validator only ever hashes `verifiable_query.to_signable_string`, so for webhooks that string is exclusively the body bytes: [4](#0-3) 

This is exactly the bug class described in the external report: an operation (webhook dispatch/handling, analogous to `participate()`'s host-chain-only mint) is executed based on an identity value (`shop`) that is *not* bound by the cryptographic check that is supposed to authorize the operation. The equality that should hold is:

`HMAC(secret, signed_bytes)` valid ⇒ `signed_bytes` uniquely determines `(body, shop, topic)`

but in this implementation:

`HMAC(secret, body)` valid ⇏ `shop` or `topic` are authentic — only `body` is authentic.

### Impact Explanation
Any merchant that has installed the app on their own store (an "unprivileged" party relative to other tenants) receives legitimate webhooks from Shopify with a valid `body` + `hmac-sha256` pair for their own shop. Because `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not part of the signed material, that same `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with a different `shop-domain` header (and/or different `topic`/`webhook-id`). The app's `WebhookMetadata` — and therefore any tenant-scoped logic downstream (e.g., "update shop X's local record") — is built from these forged headers: [5](#0-4) 

This allows one tenant to inject or trigger webhook-processing logic scoped to another tenant/shop, which is a cross-tenant access issue.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal, unprivileged action) can obtain a real `(body, hmac)` pair from Shopify's own webhook delivery, then replay it with modified headers to the same public webhook endpoint. No access token, `client_secret`, or privileged account is required — only observation of one's own legitimate webhook traffic, which any merchant using the app can do.

### Recommendation
Include the tenant/routing-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, `to_signable_string` should not be limited to `@raw_body` alone when other header-derived fields are used to drive tenant-scoped behavior.

### Proof of Concept
1. Merchant M installs the app on `shop-m.myshopify.com` and receives a real webhook from Shopify: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret), `x-shopify-shop-domain: shop-m.myshopify.com`, `x-shopify-topic: orders/create`.
2. M captures `B` and `H` from their own legitimate traffic.
3. M sends a new HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only hashes `B`: [6](#0-5) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on behalf of `victim-shop.myshopify.com` using content that was never actually sent by Shopify for that shop.
