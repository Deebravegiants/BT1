### Title
Unbounded in-memory bid cache keyed on attacker-controlled `(commitment, filler)` pairs from mempool transactions - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The intents-coprocessor RPC node maintains an in-process `BidCache` that is populated directly from the transaction pool's *ready* notification stream, before any transaction is included in a block. Every `place_bid` extrinsic that becomes "ready" in the pool causes an entry to be inserted into a `HashMap<H256, OrderBids>` keyed by order `commitment`, with an inner unbounded `Vec<BidEntry>` per commitment keyed by attacker-supplied `filler`. Eviction only happens on a periodic timer tick via `remove_expired`, using a TTL window (`ttl: Duration`), not on insertion. This mirrors the Spring Kafka CWE-770 pattern of an unbounded cache growing on unauthenticated/attacker-controlled selector-style input before any bound or backpressure is applied.

### Finding Description
`BidCache::insert` [1](#0-0)  is called from `run_bid_watcher`, which is driven purely by `pool.import_notification_stream()` — i.e., transactions merely reaching the "ready" state in the mempool, not chain inclusion: [2](#0-1) .

For every ready `place_bid` extrinsic, `extract_bid` decodes the signed sender as `filler` and the call's `commitment`/`user_op` as attacker-controlled payload [3](#0-2) . Both the outer map key (`commitment`) and inner per-entry key (`filler`) are fully attacker-controlled, and both the number of distinct commitments and the number of fillers per commitment are unbounded on insertion — there is no cap enforced in `insert`, unlike `get_bids_for_order`'s on-chain read path which explicitly caps iteration at `MAX_ON_CHAIN_BIDS = 30` [4](#0-3) .

Cleanup is purely time-based and decoupled from insertion pressure: `remove_expired` runs only on a `tokio::time::interval(cleanup_interval)` tick [5](#0-4) , and `BidCache::remove_expired` sweeps entries whose `first_seen` exceeds `ttl` [6](#0-5) . Since `first_seen` is set once per commitment on first insert and never refreshed, and pruning only happens on the timer, an attacker can flood the pool with `place_bid` transactions carrying unique `commitment`+`filler` combinations faster than the TTL/cleanup interval can reclaim them, growing the `HashMap`/`Vec<BidEntry>` (each holding attacker-supplied `user_op: Vec<u8>` bytes) without bound for the duration of one TTL window, and repeating indefinitely as long as the attacker sustains submission of new "ready" transactions (which need not ever be finalized on-chain).

### Impact Explanation
This runs on every RPC/collator node exposing the intents-coprocessor RPC (`IntentsRpcHandler`), used for sub-second bid discovery [7](#0-6) . Unbounded growth of this heap-resident structure can exhaust node memory, causing GC-style thrash and process crash/OOM — a direct availability impact (CWE-770), consistent with the CVSS `A:H` component of the referenced advisory. A crashed or unresponsive RPC/collator node degrades bid discovery and message-dispatch responsiveness for the intents/relayer pipeline that depends on this node.

### Likelihood Explanation
Reaching "ready" state in the transaction pool requires only a validly signed `place_bid` extrinsic (nonce and fee-payment validity), not execution or finalization, and not a large token balance — an attacker can sustain many transactions from disposable/sybil accounts with unique `commitment` and `filler`/`user_op` values, none of which need to ever be mined. Because insertion is uncapped and unrelated to eviction timing, the attack surface is straightforward and reachable by any unprivileged party able to submit transactions to the node's mempool.

### Recommendation
- Cap the total number of tracked commitments and/or entries per commitment in `BidCache` (mirroring the `MAX_ON_CHAIN_BIDS` bound already used for on-chain reads), rejecting or evicting-oldest once the cap is hit.
- Evict/reject on insertion pressure (e.g., LRU with a hard capacity) rather than relying solely on a periodic TTL sweep decoupled from insertion rate.
- Consider bounding memory per entry (e.g., cap `user_op` size) and/or requiring the transaction to be removed from the cache if it's evicted from the pool (`pool.import_notification_stream` has a corresponding removal/invalid stream) rather than only expiring by TTL.

### Proof of Concept
1. Run a node exposing the intents-coprocessor RPC with `run_bid_watcher` wired to the transaction pool (as in `parachain/node/src/service.rs`).
2. From many funded accounts, submit `place_bid(commitment, user_op)` extrinsics to the node's transaction pool with unique `commitment` values (and/or unique signer per bid) faster than the configured `cleanup_interval`/`ttl` allows expiry — none need to be included in a block.
3. Observe `BidCache.bids` (`HashMap<H256, OrderBids>`) grow without bound as `import_notification_stream` fires for each ready transaction and `BidCache::insert` [1](#0-0)  adds a new entry each time, with no cap, eventually exhausting node memory.

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}

pub fn extract_bid<T, Extra>(encoded: &[u8]) -> Option<(H256, Vec<u8>, Vec<u8>)>
where
	T: pallet_intents_coprocessor::Config,
	T::RuntimeCall: frame_support::traits::IsSubType<pallet_intents_coprocessor::Call<T>>
		+ DecodeWithMemTracking,
	T::AccountId: Encode + From<[u8; 32]> + DecodeWithMemTracking,
	Extra: DecodeWithMemTracking,
{
	let xt = sp_runtime::generic::UncheckedExtrinsic::<
		sp_runtime::MultiAddress<T::AccountId, ()>,
		T::RuntimeCall,
		sp_runtime::MultiSignature,
		Extra,
	>::decode(&mut &encoded[..])
	.ok()?;

	let filler = match &xt.preamble {
		sp_runtime::generic::Preamble::Signed(address, _, _) => match address {
			sp_runtime::MultiAddress::Id(id) => id.encode(),
			_ => return None,
		},
		_ => return None,
	};

	match xt.function.is_sub_type()? {
		pallet_intents_coprocessor::Call::place_bid { commitment, user_op } =>
			Some((commitment.clone(), filler, user_op.to_vec())),
		_ => None,
	}
}
