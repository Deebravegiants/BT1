### Title
Relayers Can Self-Deal the `OutboundRequestDeliveryReward` Treasury by Withdrawing Their Own Fees and "Relaying" the Withdrawal to Themselves - (File: `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
`pallet-relayer` pays a treasury-funded, per-`module_id` reward (`OutboundRequestDeliveryReward`) to whoever proves delivery of a "hyperbridge-originated" system request, because those requests are dispatched with zero attached fee and would otherwise have no economic incentive to be relayed. One of the allowlisted modules is the relayer pallet's own fee-withdrawal path. Nothing stops the same account that triggers its own withdrawal from also being the "relayer" that proves delivery and claims the reward, letting any relayer mint a treasury payout on demand from their own dust-sized withdrawals — exactly the "attacker controls both sides of a subsidized transfer" pattern in the Connext `SponsorVault` report.

### Finding Description
`Pallet::withdraw` lets any address with accrued relayer fees `>= min_withdrawal_amount` dispatch a zero-fee ISMP `PostRequest` from `MODULE_ID` (the relayer pallet) instructing the destination to disburse the withdrawer's fee balance: [1](#0-0) 

This dispatch is deliberately fee-less (`FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }`), which is exactly the class of message `OutboundRequestDeliveryReward` was designed to compensate, per the design doc: [2](#0-1) 

The claim path, `process_outbound_request_delivery_claim`, pays the configured `OutboundRequestDeliveryReward[module_id]` from the treasury to any `payee` who can prove (via destination state proof + signature) that they delivered the request — with no check that the claimant is a disinterested third party rather than the same account that caused the request to be dispatched in the first place: [3](#0-2) 

Because the withdrawal-triggering relayer and the delivery-proving/reward-claiming relayer can be the identical account, a relayer can:
1. Accrue any small amount of real relayer fee (`Fees[dest_chain][address]`) ≥ `MinWithdrawal`.
2. Call `withdraw()`, dispatching a fee-less system request with `from = MODULE_ID` (the relayer pallet, an allowlisted, reward-eligible module).
3. Relay/deliver that request to the destination themselves (or collude with whoever does).
4. Submit `OutboundRequestDeliveryClaim` with themselves as `payee`, collecting `OutboundRequestDeliveryReward[relayer_module_id]` from the treasury.

The reward amount is a flat, governance-set per-module value sized for the economics of *real*, disinterested relayers delivering system messages (host-executive updates, intents-coprocessor responses, etc.), not for the cost of delivering a single relayer's own tiny withdrawal. There is no linkage requiring the reward to be proportional to, or bounded by, the value/size of the underlying withdrawal, and no check that `payee` differs from the account whose fee balance funded the withdrawal.

### Impact Explanation
This is a direct analog of the `SponsorVault` self-dealing exploit: an actor who can trigger a subsidized action (the fee-less system dispatch) and also collect the subsidy meant to incentivize an independent party (the delivery reward) can repeatedly extract treasury funds for a cost far below the reward received. Since `withdraw()` is permissionless to any relayer with `Fees >= min_withdrawal_amount` (potentially a dust threshold), and the reward is a fixed governance-configured amount per claim, a relayer can repeatedly withdraw small legitimate balances purely to manufacture claimable "deliveries," draining `OutboundRequestDeliveryReward`'s treasury funding stream with no requirement that a genuine, disinterested relayer performed the work.

### Likelihood Explanation
Likelihood is High for any relayer that already earns legitimate fees (a normal, expected participant): no privileged access is needed, only an accrued `Fees` balance above the minimum withdrawal threshold, which any active relayer naturally has. The exploit requires no cross-chain race against honest routers/liquidity providers (unlike the original report) — it is entirely self-contained and repeatable at will, bounded only by how quickly the attacker can re-accrue `Fees` and by gas/proof costs on both chains, both of which are far below a governance-set reward if that reward is calibrated for larger system messages (e.g., host-executive updates).

### Recommendation
- Do not allow the reward-claim `payee` (or the recovered relayer identity) to equal the account whose own withdrawal (or other self-triggered dispatch) generated the request being claimed.
- Alternatively, exclude the relayer pallet's own withdrawal-request module from `OutboundRequestDeliveryReward` eligibility, or size/scale that specific module's reward to be no greater than the realistic cost of delivering a withdrawal request, removing the profit margin from self-relaying.
- Consider requiring proof that the delivering account is distinct from the account named in the underlying request body (the `beneficiary`/withdrawer), or rate-limit/cap total `OutboundRequestDeliveryReward` payouts per account per epoch to bound the damage from self-dealing.

### Proof of Concept
1. Relayer `R` legitimately proves a real delivery on some chain and accrues `Fees[dest][R] = min_withdrawal_amount` via `accumulate_fee_and_deposit_event`. [4](#0-3) 
2. `R` calls `Pallet::withdraw` with `dest_chain = D`, dispatching a fee-less `PostRequest{ from: MODULE_ID, ... }` to `D`. [5](#0-4) 
3. `R` (or a colluding party controlled by `R`) submits/relays this request to `D`, causing `RequestReceipts[commitment]` on `D` to record `R` (or `R`'s controlled key) as the delivering relayer.
4. `R` submits `OutboundRequestDeliveryClaim{ request, state_proof, payee: R, signature }` to `pallet-relayer`. Since `OutboundRequestDeliveryReward[MODULE_ID] > 0` (relayer withdrawal path is an allowlisted module per the design doc), the claim passes all checks and the treasury pays `reward` to `R`. [6](#0-5) 
5. `R` repeats steps 1–4 indefinitely, each time paying only gas/proof costs plus re-accruing a dust-sized `min_withdrawal_amount`, while collecting the full flat `OutboundRequestDeliveryReward` from the treasury each cycle — net profit per cycle equal to `reward - (gas + proof costs)`.

```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.
```

```rust
	pub fn process_outbound_request_delivery_claim(
		claim: OutboundRequestDeliveryClaim,
	) -> DispatchResult {
		let OutboundRequestDeliveryClaim { request, state_proof, payee, signature } = claim;
		let destination = state_proof.height.id.state_id;

		let commitment = hash_request::<<T as Config>::IsmpHost>(&Request::Post(request.clone()));

		let host = <T as Config>::IsmpHost::default();
		ensure!(
			request.source == host.host_state_machine(),
			Error::<T>::OutboundRequestSourceNotHyperbridge,
		);

		ensure!(
			RequestCommitments::<T>::get(commitment).is_some(),
			Error::<T>::OutboundRequestNotKnown,
		);

		ensure!(
			!OutboundRequestsClaimed::<T>::contains_key(commitment),
			Error::<T>::OutboundRequestAlreadyClaimed,
		);

		let module_id: BoundedVec<u8, ModuleIdBound> = request
			.from
			.clone()
			.try_into()
			.map_err(|_| Error::<T>::OutboundRequestModuleIdTooLong)?;
		let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
		ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);

		ensure!(destination == request.dest, Error::<T>::MismatchedStateMachine);

		let state_machine = ismp::handlers::validate_state_machine(&host, state_proof.height)
			.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let receipt_key = state_machine
			.receipts_state_trie_key(vec![commitment])
			.into_iter()
			.next()
			.ok_or(Error::<T>::OutboundRequestUnsupportedDestination)?;
		let proof_results =
			Self::verify_withdrawal_proof(&*state_machine, &state_proof, vec![receipt_key.clone()])
				.map_err(|_| Error::<T>::OutboundDestinationStateNotKnown)?;
		let raw = proof_results
			.get(&receipt_key)
			.cloned()
			.flatten()
			.ok_or(Error::<T>::OutboundDeliveryNotProven)?;

		let delivered_by = Self::decode_receipt_relayer(destination, &raw)?;

		let msg = outbound_request_delivery_message(commitment, destination, payee);
		let recovered = signature.verify(&msg, None).map_err(|_| Error::<T>::InvalidSignature)?;
		ensure!(recovered == delivered_by, Error::<T>::OutboundRequestSignerMismatch);

		let treasury: T::AccountId =
			<T as Config>::TreasuryPalletId::get().into_account_truncating();
		let payee_account: T::AccountId = payee.into();
		<<T as pallet_ismp::Config>::Currency as Mutate<T::AccountId>>::transfer(
			&treasury,
			&payee_account,
			reward,
			Preservation::Preserve,
		)
		.map_err(|_| Error::<T>::OutboundRequestRewardTransferFailed)?;

		OutboundRequestsClaimed::<T>::insert(commitment, ());

		Self::deposit_event(Event::OutboundRequestDeliveryRewarded {
			commitment,
			state_machine: destination,
			module_id,
			relayer: payee_account,
			amount: reward,
		});

		Ok(())
	}
```

```rust
	pub fn accumulate_fee_and_deposit_event(
		state_machine: StateMachine,
		address: Vec<u8>,
		fee: U256,
	) {
		let _ = Fees::<T>::try_mutate(state_machine, address.clone(), |inner| {
			*inner += fee;
			Ok::<(), ()>(())
		});

		Self::deposit_event(Event::<T>::AccumulateFees {
			address: sp_runtime::BoundedVec::truncate_from(address),
			state_machine,
			amount: fee,
		});
	}
```
