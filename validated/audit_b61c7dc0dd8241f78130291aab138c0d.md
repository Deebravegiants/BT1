Confirmed: the webhook HMAC covers only the raw request body via `to_signable_string` returning `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight into `WebhookMetadata` for the host app's handler to trust as the tenant identity.### Title
Webhook `shop` (tenant) header is not covered by the HMAC signature, allowing shop-domain spoofing on otherwise valid webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers — none of which are included in the signed payload. This breaks the intended binding `hmac_signed_bytes == identity_bytes_trusted`, since only the body is signed while the shop-domain header that identifies the tenant is not.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from the HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac-sha256` header value — it never incorporates the shop-domain header into the signed material: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check, then immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) and dispatches it to the host application's handler as the trusted tenant identity: [4](#0-3) 

`WebhookMetadata` treats `shop` as a first-class, trusted field passed to `WebhookHandler#handle`: [5](#0-4) 

Because the same `api_secret_key` is used to sign webhooks for every shop that installs the app, an attacker who controls (or installs the app on) any one shop can capture a legitimate webhook delivery for that shop — with a valid HMAC over the body — and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different, victim shop domain. Because the shop-domain header is excluded from `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` will happily dispatch a `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` carrying the attacker's own body content. The intended binding is `shop_claimed_in_dispatch == shop_that_actually_produced_and_signed_the_bytes`; this gem breaks that equality because the shop claim is not part of the signed bytes.

### Impact Explanation
Any host application that uses `request.shop` / `WebhookMetadata#shop` (the documented and only means the gem exposes for identifying which tenant a webhook belongs to) to select a session, look up per-shop state, or route data will process attacker-controlled data under a spoofed tenant identity — a cross-tenant confusion primitive rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` code, not in any misuse of an undocumented API by the host app. This matches the Critical "cross-tenant access" impact category since one merchant's webhook traffic can be attributed to another merchant's shop.

### Likelihood Explanation
Requires only that the attacker control or install the app on any single shop (an unprivileged action available to any merchant/developer who can install a public or custom app) — no access token, `api_secret_key`, or privileged credential is needed since the attacker legitimately receives their own valid signed webhook and merely rewrites the unsigned shop-domain header before forwarding it to the app's endpoint.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, e.g. compute the signature over a canonical string combining these headers with the body, or otherwise cryptographically bind the shop domain to the same MAC that authenticates the body so that `to_signable_string` cannot be satisfied by cross-shop replay.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for that shop; Shopify sends the request with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
2. Attacker intercepts this request (they are the recipient's own proxy/endpoint) and resends it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged body) and successfully matches the original signature, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` now set to `victim-shop.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb:198-199`, despite the payload actually originating from and being signed for `attacker-shop.myshopify.com`.
