### Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC exclusively over that body. The `shop` (and `topic`, `webhook_id`, `api_version`) values come from unauthenticated HTTP headers and are never part of the signed material, yet `Registry.process` trusts `request.shop` as the tenant identifier passed to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only `@raw_body` is signed - the `shop` header used elsewhere is excluded.

`Registry.process` validates the HMAC and then immediately uses `request.shop` (read straight from the header) to build the `WebhookMetadata` handed to the app's handler: [2](#0-1) 

`Request#shop` is a raw, unauthenticated header read: [3](#0-2) 

The `HmacValidator` only compares the HMAC over `to_signable_string`: [4](#0-3) 

This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_tenant_id`. The equality that should hold is:
`shop_used_by_handler == shop_covered_by_hmac`
but in fact `shop_covered_by_hmac == ∅` (the shop header is not part of the signed string at all), while `shop_used_by_handler == request.shop` (the raw, attacker-controlled header).

### Impact Explanation
Any actor who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — trivially achievable by installing the app on their own (attacker-controlled) development/test shop and receiving a genuine webhook — can replay that exact body+HMAC combination to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from a different, victim shop. Any app logic that keys per-tenant state, authorization, or data lookups off `WebhookMetadata#shop` can be tricked into acting on/for the wrong tenant — a cross-tenant boundary violation with no use of the victim's or app's access token, satisfying the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is realistic: obtaining a legitimately-signed webhook body is possible for any unprivileged internet user by installing the app on a shop they control (Shopify app installation is generally open), then capturing the resulting webhook's body+HMAC and replaying it with a forged shop header to the same public callback endpoint. No `api_secret_key`, access token, or victim credentials are needed — only observation of one's own legitimate webhook traffic.

### Recommendation
Include the tenant-identifying header (`shop`) — and ideally `topic`/`webhook_id`/`api_version` — as part of the material verified against the HMAC, or otherwise cryptographically bind the shop domain to the signed payload before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that consuming applications must independently verify `data.shop` against a known/expected shop for that webhook subscription rather than trusting the header value implicitly.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to capture a real `raw_body` and its corresponding `x-shopify-hmac-sha256` value signed by the app's `client_secret`.
2. Resend that exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and desired `x-shopify-topic`/`x-shopify-webhook-id`).
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only re-computes the HMAC over `raw_body`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the app's `handler.handle` with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload was never associated with that shop, letting the attacker inject spoofed events attributed to another tenant.
