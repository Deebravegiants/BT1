### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by checking the HMAC over the raw request body only, but then trusts the `shop` value taken from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header — a value that is never covered by that HMAC — as the tenant identity passed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the request header without any cryptographic binding to that signature: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop` from that unauthenticated header, handing it to the app's handler as the authoritative tenant identifier: [3](#0-2) 

Because a Shopify app's webhook client secret (`Context.api_secret_key`) is shared across *every* shop that installs the app, any body/HMAC pair that is valid for one shop is also a valid HMAC for the exact same body on every other shop of that app — the signature never binds the body to a specific shop domain. An attacker who can obtain one genuine, validly-signed webhook body (trivially available to them by installing the target app on their own store, which any unprivileged internet user with a free Shopify dev/trial shop can do) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop's domain. `HmacValidator.validate` will pass (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

This is the same class of bug described in the analog hint: "a field acted on but not covered by the HMAC" — here the identity-binding equality that should hold is `shop (header, trusted) == shop (cryptographically bound to hmac(body))`, but the gem never establishes that binding; it is `shop (header) ∈ {anything attacker supplies}` regardless of `hmac(body)`.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (as the gem's own documentation instructs — see `docs/usage/webhooks.md`, `data.shop`) to select which merchant's records to create/update/associate with incoming webhook data is exposed to cross-tenant data injection/misattribution: an attacker-controlled shop can cause the app to process webhook payloads as if they came from a victim shop. This matches the "cross-tenant access" Critical impact category, since the trust boundary between tenants (shops) is broken by the gem's own verification primitive.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned/trial Shopify store to obtain one legitimately-signed webhook body/HMAC pair (no special privilege — any Shopify Partner/dev account can do this for free), and (2) sending a forged HTTP request to the app's public webhook endpoint with that captured body/HMAC and a victim's shop domain in the header. No knowledge of `api_secret_key`, access tokens, or the victim's credentials is required, and the request path (`Registry.process` → handler) is exactly the one the gem documents apps to use.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is verified, not just the raw body — e.g., have `Registry.process` require that the `shop` from the header matches a shop with which the app has installed/active session state before invoking the handler, or otherwise avoid presenting `request.shop` as a "verified" field. At minimum, the gem's documentation and `WebhookMetadata` should make clear that `shop` is unauthenticated header data and must be independently validated (e.g., against an existing offline session) by the host application before being trusted.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to capture a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `client_secret`.
2. Replay an HTTP POST to the app's webhook route with the same `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` in [4](#0-3) 
 returns `true` because it only checks `raw_body`.
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [5](#0-4) 
 even though the payload actually originated from the attacker's own shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
