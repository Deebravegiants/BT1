### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, but `ShopifyAPI::Webhooks::Registry.process` uses the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header to determine which tenant a webhook belongs to when invoking the app's handler. Because the shop identity is never included in the HMAC-signed material, the signature check cannot detect a mismatch between "the shop whose secret actually produced this HMAC/body" and "the shop the request claims to be from."

### Finding Description
Shopify computes the webhook HMAC as `HMAC-SHA256(client_secret, raw_body)` and delivers it in the `X-Shopify-Hmac-Sha256` header together with separate headers for `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version`. In this gem:

- `Request#hmac` reads the `hmac-sha256` header value [5](#0-4) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from headers with no cryptographic binding [2](#0-1) .
- `Request#to_signable_string` — the only thing actually authenticated by the HMAC comparison — returns just `@raw_body` [1](#0-0) .
- `HmacValidator.validate_signature` computes the signature over `to_signable_string` (body only) and does a constant-time compare against the received header [3](#0-2) .
- `Registry.process` gates only on this body-only HMAC check, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler [4](#0-3) .

The identity binding that should hold is: `shop header value == shop that the HMAC actually authenticates`. Because the HMAC never covers the `shop-domain` header, this equality is not enforced anywhere in the gem. Any request whose body+HMAC pair is valid for *some* shop of the app (i.e., was legitimately produced and observed once, e.g. by a merchant inspecting their own webhook delivery logs, or captured off a non-TLS hop/log) can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to name a *different* shop of the same app. `Registry.process` will accept it as HMAC-valid and hand the handler data tagged with the attacker-chosen `shop`, `topic`, and `webhook_id`, none of which were actually authenticated.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to preserve for webhook processing: a body/HMAC pair that only proves "this body was HMAC'd with the app's shared secret" is used by `Registry.process` as if it also proved "and it came from shop X." An attacker with a network position to observe a single legitimate webhook delivery (their own shop's, or one leaked via logs/proxies) can force the app to process that payload under an arbitrary `shop` value, corrupting per-tenant data attribution, triggering mandatory-compliance handlers (e.g. `shop/redact`, `customers/redact`, `customers/data_request`) or business-logic handlers against the wrong tenant, and confusing whatever tenant-keyed storage the host application keys off `WebhookMetadata#shop`. This matches the High-severity class of cross-tenant access achieved without any access token or `client_secret` leakage — only knowledge of one valid body/HMAC pair is needed.

### Likelihood Explanation
Requires: (1) the app registers HTTP webhook handlers (a documented, common configuration) and (2) the attacker obtains one legitimate `(raw_body, hmac-sha256)` pair — achievable from their own shop's webhook deliveries (which they legitimately receive as a merchant/app installer) or via interception in transit/at a proxy/logging layer, then replays it to the app's public webhook endpoint with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged account is needed; the attack is fully driven by an unprivileged party who can install the app on their own shop.

### Recommendation
Bind the identity headers into the authenticated material instead of trusting them independently of the HMAC. At minimum, include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g., by having the host verify `shop` against a previously known/registered shop for that webhook subscription before dispatch) so that a mismatch between the claimed identity headers and the HMAC-authenticated body is detectable and rejected in `HmacValidator.validate`/`Registry.process`.

### Proof of Concept
1. App has a registered HTTP webhook handler via `Registry.add_registration(topic: "orders/create", ...)`.
2. Attacker (a merchant who has installed the app on `attacker-shop.myshopify.com`) triggers an `orders/create` event on their own shop and captures the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair from Shopify's real delivery to the app's public endpoint (e.g., via a request logger, proxy, or shared hosting log).
3. Attacker POSTs to the same app endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Request.new` parses headers/body [6](#0-5) ; `HmacValidator.validate(request)` succeeds because it only re-hashes `raw_body` [7](#0-6) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [8](#0-7) , causing the host app to process/store the attacker's own order data as if it belonged to `victim-shop.myshopify.com`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
