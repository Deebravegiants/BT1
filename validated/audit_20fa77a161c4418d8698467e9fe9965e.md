### Title
Missing duplicate-signer check in BEEFY consensus verification allows vote-count inflation to bypass the 2/3+1 supermajority threshold - ([File: evm/src/consensus/EcdsaBeefy.sol], [File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
Both the Solidity and Rust BEEFY consensus verifiers determine whether a relay-chain commitment has reached the required 2/3+1 authority supermajority purely from the *length* of the submitted votes/signatures array, without ever checking that the `authorityIndex`/`index` values identifying the signers are unique. This is the same bug class described in the external report: a count-based quorum check that validates "sorted"/"well-formed" input but never verifies uniqueness of the participant identifiers, letting a relayer inflate the apparent participant count with repeated entries for the same authority.

### Finding Description
In `EcdsaBeefy.sol::verifyMmrUpdateProof()`, the supermajority check is: [1](#0-0) 

`sigLen` is simply `relayProof.signedCommitment.votes.length` and is checked with `checkParticipationThreshold(sigLen, authoritySet.len)`: [2](#0-1) 

Nowhere in `verifyMmrUpdateProof` (or in the subsequent loop building `authorities[i]` from `vote.authorityIndex`) is there a check that all `vote.authorityIndex` values in `relayProof.signedCommitment.votes` are distinct: [3](#0-2) 

The equivalent Rust light-client verifier has the identical pattern: `signatures_length` is the raw array length used for the threshold check, and `authority_indices` built from `mmr.signed_commitment.signatures` is never deduplicated before being passed to the merkle multi-proof verification: [4](#0-3) 

This is directly analogous to the reported `registerValidator()` issue: the code validates a structural property of the list (ascending order/sorted, or in this case "the merkle multi-proof mathematically checks out for the claimed indices") but never validates that the list's *identifying keys* (operator IDs vs. authority indices) are unique before using the list's length to satisfy a security-critical quorum requirement.

Notably, this codebase has already recognized and fixed exactly this bug class elsewhere:
- The Pharos BLS verifier explicitly deduplicates `participant_keys` before checking stake/signature validity, returning `Error::DuplicateParticipant` on failure: [5](#0-4) 
- The Tendermint verifier explicitly rejects validator sets/participants that reuse the same address twice, with a comment stating this is required because "a duplicate signals a set that was not built honestly": [6](#0-5) 

The BEEFY verifiers (both Solidity and Rust), which gate consensus state updates and downstream parachain-header/state-commitment acceptance for Hyperbridge's EVM and Substrate light clients, lack this same protection.

### Impact Explanation
BEEFY is used by `EcdsaBeefy.sol` and `pallet-beefy` consensus clients to admit new relay-chain/parachain state commitments into Hyperbridge — this is the trust root for cross-chain state and message proofs on all BEEFY-secured routes. If the participation-count check can be satisfied without a genuine 2/3+1 of *distinct* authorities (e.g., by repeating a real `(authorityIndex, signature)` vote entry to pad `sigLen`/`signatures_length`), an adversarial minority of relay-chain validators (below the honest-majority assumption) colluding with a relayer could get a consensus update accepted that does not actually carry a genuine supermajority endorsement. Since BEEFY consensus updates are the entry point for state commitments used by `IConsensusV2`/ISMP proof verification, a forged or premature commitment can propagate unsound state roots that are subsequently used to forge message-delivery or state-proof verification, i.e., unsound state commitment / forged message delivery per the impact criteria.

### Likelihood Explanation
This path is reachable by any relayer submitting a BEEFY consensus proof through `EcdsaBeefy.verify()` or the equivalent unsigned extrinsic handled by `pallet-beefy-consensus-proofs`/`beefy_verifier::verify_consensus`, which are the exact unprivileged "relayed proof" surfaces called out as in-scope. Exploitability further depends on whether the downstream merkle multi-proof implementation (`MerkleMultiProof.VerifyProof` for Solidity, `rs_merkle::MerkleProof::verify` for Rust) tolerates a repeated index/leaf pair in its input set; this external library is not audited as part of this analysis, so likelihood should be treated as Medium pending confirmation of that library's dedup behavior — but the root-cause gap (no duplicate-authority check at the consensus-verifier layer, unlike the sibling Pharos/Tendermint verifiers) is concretely present and matches the reported bug class exactly.

### Recommendation
Add an explicit uniqueness check on `vote.authorityIndex` (Solidity) / `sig.index` (Rust) before computing `sigLen`/`signatures_length` and before it is used in `checkParticipationThreshold`/`check_participation_threshold`, mirroring the `ensure_unique_addresses` (Tendermint) and `verify_validator_membership` deduplication (Pharos) already implemented elsewhere in this codebase. Reject the proof (e.g., a new `DuplicateAuthorityIndex`/`DuplicateVote` error) if any duplicate index is found.

### Proof of Concept
1. Obtain a genuine BEEFY `SignedCommitment` for a given `blockNumber` where only slightly less than 2/3+1 of the authority set has signed (e.g., 65% instead of 67%+1) — an achievable scenario if the relayer colludes with, or captures signatures from, a bare-minority-short set of authorities.
2. Construct `relayProof.signedCommitment.votes` by including all genuine `(authorityIndex, signature)` pairs, then duplicating one or more existing entries (same `authorityIndex`, same `signature`) until `votes.length` (`sigLen`) satisfies `checkParticipationThreshold(sigLen, authoritySet.len)`.
3. Submit this crafted `RelayChainProof` to `EcdsaBeefy.verify()`. Because `checkParticipationThreshold` only inspects `votes.length` and the per-vote ECDSA recovery/merkle-membership check only validates that each *individual* `(authorityIndex, signature)` pair is a member of the authority set (not that indices across the array are distinct), the duplicated entries pass every existing check while representing no additional distinct signer.
4. If the underlying `MerkleMultiProof.VerifyProof` (or `rs_merkle::MerkleProof::verify` in the Rust path) does not itself reject duplicate leaf indices in its input, the consensus update is accepted despite lacking a genuine supermajority of distinct authorities.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

	let mmr_root_data = commitment
		.payload
		.get_raw(&MMR_ROOT_PAYLOAD_ID)
		.ok_or(Error::MmrRootHashMissing)?;

	if mmr_root_data.len() != 32 {
		return Err(Error::InvalidMmrRootHashLength { len: mmr_root_data.len() });
	}
	let mmr_root = H256::from_slice(mmr_root_data);

	let commitment_hash = H::keccak256(&commitment.encode());
	let mut authority_leaves: Vec<[u8; 32]> = Vec::new();
	let mut authority_indices = Vec::new();

	for sig in mmr.signed_commitment.signatures.iter() {
		let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)
			.map_err(|_| Error::FailedToRecoverPublicKey)?;

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

	let valid = merkle_proof.verify(
		authority_set.keyset_commitment.into(),
		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}
