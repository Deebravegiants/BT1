### Title
Webhook Shop Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` fields entirely from unauthenticated HTTP headers, while `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is only the raw request body. The identity binding the app relies on (`hmac_valid → shop_header is authentic`) does not hold, because the `shop-domain` header is never part of the HMAC-covered bytes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two methods `Utils::HmacValidator.validate` uses to authenticate a webhook: [1](#0-0) [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
```

`to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` computes and compares an HMAC over the body bytes only: [2](#0-1) 

`Registry.process` then trusts `request.shop` (and `request.topic`, `request.webhook_id`) — none of which are covered by the signature — to build the metadata passed into the app's handler: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

Because every app registered with Shopify shares a single `client_secret`/`api_secret_key` across **all** shops that install it, any shop that legitimately installs the app can trigger a real webhook event on its own store, capture the resulting `(raw_body, hmac)` pair — which is validly signed with the app's one shared secret — and resubmit it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the HMAC; `Registry.process` still hands the (attacker-editable) `shop` value through unchanged to the app's handler.

This breaks the intended identity binding:
`hmac_valid(raw_body) == true` should imply `request.shop == the_shop_that_actually_sent_this_event`, but the gem never enforces that equality — the `shop` field is "acted on but not covered by the HMAC," exactly the ambiguous-binding bug class described in the reference report (fields used by the application that aren't cryptographically tied together).

### Impact Explanation
Any app built on this gem that keys tenant data, session lookup, or business logic off `WebhookMetadata#shop` (a normal, documented usage pattern) can be made to apply a webhook payload under an attacker-chosen shop identity, despite a "valid" HMAC. This is a cross-tenant identity confusion: an unprivileged app user (any merchant who installs the app) can cause the app to process data as if it originated from a different, victim tenant, without ever needing that victim's credentials, session, or the app's `client_secret`.

### Likelihood Explanation
Any merchant who installs the app can generate at least one legitimate, validly-signed webhook body simply by using their own store (updating an order, product, etc. based on whichever topics the app subscribes to), and can freely resubmit that body with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header to the app's public webhook endpoint, since header values are never validated against the signed payload. No secret material or privileged access is required beyond normal app installation.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) as part of the HMAC-signed content that `Request#to_signable_string` verifies, or otherwise cryptographically bind the claimed `shop` to the payload before it is exposed via `Request#shop`/`WebhookMetadata#shop`. At minimum, document loudly that `request.shop` is not authenticated by the HMAC and must be independently verified (e.g., cross-checked against a known/expected shop for the delivery) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g. `orders/create`) on that shop; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent to the app's webhook endpoint — this HMAC is valid because it's signed with the app's single shared `api_secret_key`.
3. Replay the exact same body/HMAC to the app's webhook endpoint, but change the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `@raw_body` against the HMAC) via `lib/shopify_api/webhooks/request.rb`'s `to_signable_string`.
5. `ShopifyAPI::Webhooks::Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler, which processes attacker-supplied data under the victim's tenant identity.
