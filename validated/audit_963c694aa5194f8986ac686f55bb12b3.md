### Title
`validateStellarAddress` accepts checksum-invalid Stellar addresses via format-only regex - (File: packages/intents-sdk/src/lib/validateAddress.ts)

### Summary
`validateStellarAddress` only checks `/^G[A-Z0-9]{55}$/` and never verifies the base32 CRC16-XModem checksum that a real Stellar `G...` address must carry [1](#0-0) . This means `validateAddress(addr, Chains.Stellar)` returns `true` for a syntactically-shaped but checksum-corrupted string, whereas the equality that should hold — "an address accepted by `validateAddress` is a decodable Stellar account ID" — is broken.

### Finding Description
The broken equality is: `validateAddress(addr, Chains.Stellar) === true` should imply `stellarAddressToBytes(addr)` succeeds (i.e., the address decodes to a valid 32-byte ed25519 public key with correct CRC16 checksum). The real decode/encode logic used elsewhere in the repo, `stellarAddressToBytes`/`bytesToStellarAddress` in `packages/internal-utils/src/utils/stellarAddressToBytes.ts`, does enforce base32 round-tripping and CRC16-XModem checksum verification [2](#0-1) . But `validateAddress`'s Stellar branch does not call this function or perform any checksum check — it is a bare regex [1](#0-0) , so a 56-character string starting with `G` and composed of valid base32 characters but with a flipped checksum byte will pass `validateAddress`.

However, to determine actual exploitability I need to confirm whether `stellarAddressToBytes` (the strict, checksum-verifying function) is invoked anywhere in the Stellar withdrawal path before the destination address is embedded into the outgoing intent/transaction. I found `stellarAddressToBytes` referenced in `packages/internal-utils/src/utils/authIdentity.ts` and `prepareBroadcastRequest.ts`, but I was not able to fully trace, within my remaining tool budget, whether the HOT-bridge or intents-bridge Stellar withdrawal code path (`hot-bridge.ts`, `direct-bridge.ts`, `intents-bridge.ts`, `omni-bridge.ts`, `poa-bridge.ts`, all of which import `validateAddress`) calls `stellarAddressToBytes` downstream as a second, stronger validation gate before constructing the on-chain transaction, or whether it relies solely on `validateAddress`'s regex result and passes the raw string through to the destination/memo field of the intent.

This is a material gap: if a second checksum-enforcing decode step exists downstream (which is plausible, since `stellarAddressToBytes` exists specifically for this purpose and is used by other parts of the codebase, e.g. `authIdentity.ts`), then the checksum-invalid address would simply fail later with a thrown `Error("invalid checksum")` rather than being embedded unchecked into a signed intent — meaning no funds are actually misrouted, only a later error is raised (functionally a UX/DoS issue, not a Critical "funds routed to unspendable/wrong address" issue). If no such downstream check exists, the finding as described would hold.

### Impact Explanation
Uncertain/not confirmed. If a downstream checksum-verifying decode (e.g. `stellarAddressToBytes`) is present anywhere in the Stellar-destination withdrawal path, the corrupted-checksum address would be rejected before intent construction, and the scenario in the question does not materialize as a fund-misrouting bug — it would at most be an early, harmless validation gap that a later, stronger validation catches. If no such downstream check exists, the impact would match the question's Critical claim (funds directed at an unverified/likely-unspendable Stellar address, no recovery).

### Likelihood Explanation
Not established — I could not confirm within the available searches that the raw, regex-validated Stellar address flows unchecked all the way to intent construction (i.e., that no second checksum decode happens in `hot-bridge.ts`/`intents-bridge.ts`/`omni-bridge.ts` etc. before the destination is finalized).

### Recommendation
Regardless of whether a downstream guard exists, `validateStellarAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` should be hardened to call the existing `stellarAddressToBytes` (from `@defuse-protocol/internal-utils`) instead of a bare regex, so that the CRC16 checksum and base32 round-trip are verified at the point of format validation — defense in depth regardless of what other checks exist downstream.

### Proof of Concept
Not fully verifiable as "funds misrouted" without confirming the downstream path; the following narrower test is reproducible and safe to state:
```ts
// vitest, packages/intents-sdk/src/lib/validateAddress.spec.ts
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";
import { stellarAddressToBytes } from "@defuse-protocol/internal-utils"; // or direct path

it("accepts a checksum-corrupted but format-valid Stellar address", () => {
  const valid = "GA7QYNF7SOWQ3GLR2BGMZEHXAVIRZA4KVWLTJJFC7MGXUA74P7UJVSGZ"; // example 56-char G-address
  const corrupted = valid.slice(0, -1) + (valid.at(-1) === "A" ? "B" : "A"); // flip last checksum char
  expect(validateAddress(corrupted, Chains.Stellar)).toBe(true);
  expect(() => stellarAddressToBytes(corrupted)).toThrow(/checksum/i);
});
```
This proves the divergence between `validateAddress` and the checksum-aware decoder exists at the validation-function level, but does **not** by itself prove that this divergence reaches intent construction/signing — that requires tracing the Stellar withdrawal call sites (`hot-bridge.ts`, `intents-bridge.ts`, `omni-bridge.ts`, `direct-bridge.ts`, `poa-bridge.ts`) to see if any of them decode the address a second time before embedding it in the signed intent, which I was unable to complete before running out of tool budget. A follow-up Devin session with full repo access should trace these call sites to confirm or refute the Critical-impact claim before this is treated as a confirmed vulnerability.

export function stellarAddressToBytes(encoded: string): Uint8Array {
	if (typeof encoded !== "string") {
		throw new TypeError("encoded argument must be of type String");
	}

	const decoded = base32.decode(encoded);
	const payload = decoded.slice(0, -2);
	const data = payload.slice(1);
	const checksum = decoded.slice(-2);

	if (encoded !== base32.encode(decoded)) {
		throw new Error("invalid encoded string");
	}

	const expectedChecksum = calculateChecksum(payload);

	if (!verifyChecksum(expectedChecksum, checksum)) {
		throw new Error("invalid checksum");
	}

	return new Uint8Array(data);
}
