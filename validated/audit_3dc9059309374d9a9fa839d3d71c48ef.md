### Title
Webhook shop/topic identity spoofing via HMAC signature that only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator` authenticates the payload bytes but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Webhooks::Registry.process` subsequently trusts and hands to the app's handler.

### Finding Description
The report's bug class is "a field is acted on but not covered by the cryptographic check, breaking an identity binding." Here the equality that should hold is:

`hmac_signature == HMAC(secret, bytes_that_determine_which_shop/topic_the_event_is_attributed_to)`

but the actual implementation computes:

`hmac_signature == HMAC(secret, raw_body_only)` [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic coverage: [2](#0-1) 

`Registry.process` validates only the HMAC (i.e., only the body) and then unconditionally trusts `request.shop` and `request.topic` to dispatch the handler and build `WebhookMetadata`: [3](#0-2) 

Because the signature never covers the headers, any request with a *previously observed, genuinely-signed* `(raw_body, hmac)` pair remains valid under `HmacValidator.validate` even if the `shop-domain`, `topic`, or `webhook-id` headers are swapped for different values before the request reaches the app's endpoint. This breaks the binding "shop claimed in the metadata == shop that the HMAC actually authenticates," which is exactly the identity-binding class called out in scope (shop authenticated vs. shop trusted downstream; bytes verified vs. bytes/fields parsed and acted upon).

### Impact Explanation
An unprivileged user who controls a Shopify store running the vulnerable app can trivially obtain one legitimately-signed `(raw_body, hmac)` pair by triggering any webhook event on their own store (e.g. `orders/create`). They can then present that same body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain (or the `topic` header for a different registered topic). Since `to_signable_string` only depends on the body, `HmacValidator.validate` still passes, and the handler executes believing the event legitimately originated from the victim shop/topic. If the host app uses `WebhookMetadata#shop` to key merchant-specific storage, authorization, or session lookups (the intended and documented use, per `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`), this enables cross-tenant data confusion/write, satisfying the "cross-tenant access" criterion for a Critical-impact finding, or at minimum a scope/topic-check bypass (High) if used to route data into a handler not intended for that event type.

### Likelihood Explanation
Likelihood is high for any app that relies on `request.shop`/`request.topic` from the parsed `Webhooks::Request` for anything beyond pure logging: no access token, `client_secret`, or privileged account is required — only the ability to trigger one real webhook on an account the attacker legitimately controls, then replay it with modified headers to the app's public webhook endpoint.

### Recommendation
Include the shop domain, topic, and webhook id in the signable payload (or otherwise cryptographically bind them, e.g. via a signed header set as Shopify's newer webhook formats do), so `HmacValidator.validate` fails whenever any of those identity-determining fields have been altered relative to what was actually signed. Short term, `Webhooks::Registry.process` should not trust `request.shop`/`request.topic` unless they are covered by the verified signature.

### Proof of Concept
1. Attacker's own store `attacker-shop.myshopify.com` has the vulnerable app installed and triggers `orders/create`. Shopify sends:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: w1
   Body: B
   ```
2. Attacker intercepts this request to their own endpoint and resends it to the app's webhook endpoint with `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`), keeping `Body: B` and the HMAC header unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (`= B`) only — this matches, so validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` even though `victim-shop.myshopify.com` never actually sent this event, demonstrating the broken shop/topic identity binding.
