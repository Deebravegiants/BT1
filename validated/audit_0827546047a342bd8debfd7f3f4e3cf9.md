### Title
Auto-generated wallet passphrase stored in plaintext next to the encrypted seed, defeating seed-at-rest encryption - (File: features/wallet/module/wallet.js)

### Summary
When `usePassword: true` and `useAutoGeneratedPassword: true` (a supported, tested configuration of `@exodus/wallet`), the wallet mnemonic/seed is "encrypted" at rest using a randomly generated passphrase. However, that passphrase is itself stored unencrypted in the very same underlying storage as the encrypted seed, because it is written/read without ever passing a `{ passphrase }` option to `walletStorage`.

### Finding Description
`Wallet#setSeed` stores the seed with an encryption passphrase: [1](#0-0) 

When no user passphrase is supplied and `useAutoGeneratedPassword` is enabled, a random passphrase is generated with `genPassphrase()` and persisted via `this.walletStorage.set(GENERATED_PASSPHRASE_KEY, passphrase)` — note the call has **no** `{ passphrase }` option: [2](#0-1) 

It is later read back the same unprotected way: [3](#0-2) 

The `seedStorage`/`walletStorage` implementations that ship with hydra (e.g. `@exodus/browser-extension-adapters/seco-storage`) treat the `{ passphrase }` option as the switch between encrypted and plaintext storage: if no passphrase is passed, the value is written/read as **plaintext** on the underlying (unsafe) storage: [4](#0-3) 

Meanwhile the seed itself IS encrypted with that same generated passphrase: [5](#0-4) 

The net effect: the encrypted seed ciphertext and its decryption key (the auto-generated passphrase) both live, unauthenticated relationship aside, in the same underlying storage medium — with the key stored in the clear. Whatever storage adapter backs `seedStorage` on a given platform (browser-extension `chrome.storage.local`, `storage-unsafe-desktop`'s flat JSON file, etc.) will contain both the ciphertext and the key needed to open it, in the same file/database, with the key unprotected. This is functionally equivalent to "not using platform encryption" — the encryption step becomes security theater because the wrapping key is exposed right beside the protected data, exactly the failure mode described in the source report (private keys/seed material at rest with no real protection against a local attacker who can read the storage medium).

This is confirmed by the test matrix in `features/wallet/module/__tests__/index.test.js`, which explicitly exercises `{ usePassword: true, useAutoGeneratedPassword: true }` as a supported configuration: [6](#0-5) 

### Impact Explanation
Any local attacker (or malicious code) with read access to the raw storage medium backing `seedStorage` — e.g., the browser extension's `chrome.storage.local` data on disk, a desktop app's unsafe-storage JSON file, or any other unencrypted-at-the-OS-level medium — can retrieve both the `generatedPassphrase` value (plaintext) and the encrypted `seed` blob, then trivially decrypt the mnemonic/seed offline. This directly leads to full wallet compromise: theft of the master seed and all derived private keys, exactly the exploit scenario described in the original report (an attacker with local/file access, e.g. at an unlocked or otherwise-accessible workstation/browser profile, defeats "encryption" that is not actually backed by platform-level key protection such as OS keychain/keystore).

### Likelihood Explanation
This is not a hypothetical mis-configuration — `useAutoGeneratedPassword: true` combined with `usePassword: true` is a first-class, tested configuration path in the `@exodus/wallet` module, intended precisely for the "no user password / auto-unlock" UX (as also seen in the SDK playground reference to `exodus.wallet.unlock()` "auto-unlocks for ease of use"). Any deployment that chooses this mode (to avoid prompting the user for a password) inherits this weakness by construction — the vulnerability requires no special conditions beyond that config choice, and read access to the storage medium (local file, browser profile storage, etc.), which matches the report's local-attacker threat model.

### Recommendation
- **Short term:** Never store the auto-generated passphrase itself via the same unauthenticated/plaintext path as other unsafe data. At minimum, protect `GENERATED_PASSPHRASE_KEY` with a platform-provided secret store (e.g., OS keychain, Android Keystore, or `@exodus/keystore-mobile`-style secure enclave storage) rather than the same flat/JSON storage used for the encrypted seed.
- **Long term:** Route all "auto-generated password" material through platform hardware-backed secure storage (macOS Keychain, Windows Credential Manager/DPAPI, Android/iOS Keystore/Secure Enclave) instead of `seedStorage`'s generic passphrase-gated storage, so that the key protecting the seed is never persisted in the same unencrypted medium as the ciphertext it protects.

### Proof of Concept
1. Configure the wallet with `config: { usePassword: true, useAutoGeneratedPassword: true, ... }` (matches `features/wallet/module/__tests__/index.test.js:34-35`).
2. Call `wallet.create({})` with no `passphrase` argument. Internally: `#setSeed` generates `passphrase = genPassphrase()` and calls `walletStorage.set(GENERATED_PASSPHRASE_KEY, passphrase)` (no `{passphrase}` option) and `walletStorage.set(SEED_KEY, seed, { passphrase })`.
3. Inspect the raw underlying storage backing `seedStorage` (e.g. the JSON file used by `storage-unsafe-desktop`, or `chrome.storage.local` for the browser extension). Observe that the `generatedPassphrase` entry under the `wallet` namespace is stored as plaintext base64, while `seed` is stored as ciphertext.
4. Using only that raw storage dump (no login/session, no OS keychain access, no user password), decrypt the `seed` entry with the plaintext `generatedPassphrase` value to recover the wallet mnemonic/seed — full compromise achieved purely from local file/storage read access.
