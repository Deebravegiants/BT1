Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers with no cryptographic binding to the HMAC [2](#0-1) . `Registry.process` validates only that `HmacValidator.validate(request)` passes and then forwards `request.shop` (and topic/webhook_id/api_version) straight into `WebhookMetadata`, which is delivered to the host app's handler as trusted, tenant-identifying data [3](#0-2) . `HmacValidator.validate_signature` computes the signature only over `to_signable_string` (the raw body) [4](#0-3) .

### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without being bound to the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, but the shop domain, topic, webhook id, and API version headers used to attribute the webhook to a specific merchant are read from unauthenticated headers and never covered by the HMAC.

### Finding Description
`Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` returns true [5](#0-4) . That validation only checks that `HMAC-SHA256(secret, raw_body)` matches the `x-shopify-hmac-sha256` header [1](#0-0) [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values, however, come straight from HTTP headers with no signature coverage at all [6](#0-5) . Once the body's HMAC checks out, `Registry.process` passes the unauthenticated `request.shop` value into `WebhookMetadata`, which the host application's `WebhookHandler#handle` treats as the authoritative tenant identifier for the event [7](#0-6) [8](#0-7) .

This breaks the intended binding `shop_header == shop_that_produced_this_signed_body`. Because the field acted on (`shop`) is not covered by the HMAC that is checked, any body+HMAC pair that was legitimately generated for one shop remains fully valid when replayed with a different `x-shopify-shop-domain` (or `x-shopify-topic`/`x-shopify-webhook-id`) header value, since neither the validator nor `process` cross-checks these headers against anything cryptographically tied to the signature.

### Impact Explanation
An attacker who can install the app on their own (or any) Shopify development store obtains genuine `(raw_body, hmac)` pairs signed with the app's real `client_secret`-derived key, since Shopify computes the HMAC purely over the JSON payload. By resending that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or topic/webhook id) header for a victim shop, the request still passes `HmacValidator.validate` and the handler is invoked believing the event, including whatever body content, belongs to the victim shop. Any host application that keys per-tenant business logic, data writes, or access-token lookups off `WebhookMetadata#shop` can be made to attribute attacker-supplied webhook content to another merchant, resulting in cross-tenant data corruption/impersonation, satisfying the "cross-tenant access" impact criterion.

### Likelihood Explanation
Reaching this requires only the ability to send raw HTTP requests to the app's public webhook endpoint plus a single genuine webhook capture (trivially obtainable by installing the app on an attacker-controlled or free development store). No credentials, tokens, or privileged access to the app's `client_secret` are needed — this is directly reachable by an unprivileged internet user via the library's own request-processing code path.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or otherwise cryptographically bind them to the raw body before trusting them — e.g., verify `request.shop` against an expected/previously-registered shop for the delivery, or require host applications to independently confirm the shop is one they consider installed rather than passing the raw header value through untouched via `WebhookMetadata`. At minimum, document clearly in `Request`/`Registry` that `shop`, `topic`, and `webhook_id` are unauthenticated header values not covered by the HMAC and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify development store and capture a legitimate webhook delivery, e.g. `orders/create`, noting the raw JSON body `B` and the `x-shopify-hmac-sha256` header value `H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forge `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [9](#0-8) , `HmacValidator.validate` returns `true` because it only checks `B` against `H` [10](#0-9) , and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the attacker's body content to be processed as if it originated from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
