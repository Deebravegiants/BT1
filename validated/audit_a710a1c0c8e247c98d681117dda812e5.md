Confirmed: `getDefaultAddress` calls `#assertAssetSourceIsSupported`, which throws `UnsupportedAssetSourceError` when an asset isn't supported for a given wallet account/hardware wallet [1](#0-0) , and the codebase elsewhere explicitly wraps such calls in try/catch specifically "because hardware wallet account may not support coin" [2](#0-1) . `connections.js` does **not** guard against this.

### Title
Single unsupported asset/wallet-account address derivation blocks origin revocation (`untrust`/`disconnect`) - (File: `features/connected-origins/module/connections.js`)

### Summary
`ConnectedOrigins#setData` rebuilds the shared `connectedAccountsAtom` for **every** enabled wallet account across **every** asset connected by **any** origin, via `#getAccounts`/`#getWalletAccountAddresses`, which calls `addressProvider.getDefaultAddress` without a try/catch. If address derivation throws for even one (walletAccount, assetName) pair, the whole aggregate write fails, and every mutating method that goes through `#setData`/`#setAttributes` — including `untrust`, `disconnect`, `setAutoApprove`, `setFavorite`, `add`, `connect`, `updateConnection`, `clearConnections` — throws and never persists.

### Finding Description
`getConnectedAccounts`-adjacent internals aggregate addresses across all enabled wallet accounts for the union of assets connected by *all* trusted origins: [3](#0-2) [4](#0-3) 

`#getWalletAccountAddresses` calls `this.#addressProvider.getDefaultAddress({ assetName, walletAccount })` for every asset connected by any origin, for every enabled wallet account, with no per-item error isolation [5](#0-4) . `getDefaultAddress` performs `#assertAssetSourceIsSupported`, throwing `UnsupportedAssetSourceError` if the asset/account pair is unsupported (e.g., a hardware wallet account added later that doesn't support one of the many previously-connected origins' assets, or any asset-source lookup failure) [1](#0-0) . This is a documented, expected failure mode elsewhere in the codebase, where callers explicitly catch it (e.g. `getWalletAccounts` in `asset-client-interface.js`) because "hardware wallet account may not support coin" [6](#0-5) .

Because `#setData` awaits `#getAccounts(assetNames)` before writing atoms, a single failing (walletAccount, assetName) combination — coming from *any* connected origin's asset list, not necessarily the one being modified — causes the promise chain to reject, and none of the following complete or persist:
- `untrust` (revoke a dApp's trust) [7](#0-6) 
- `disconnect` (kill an active connection) [8](#0-7) 
- `setAutoApprove` (turn off silent auto-approval) [9](#0-8) 
- `clearConnections` [10](#0-9) 

This mirrors the reported bug class exactly: an aggregate operation iterates over "many protocols" (here, many wallet accounts × many connected-origin asset names) and a single failing element halts state-mutating operations for all others, including the operations meant to remove/limit exposure.

### Impact Explanation
This is a cross-origin/account privilege-bleed risk: the user's attempt to `untrust` a malicious or compromised dApp origin, or to `setAutoApprove(false)`/`disconnect`, silently throws and the origin remains trusted/auto-approved/connected in `connectedOriginsAtom`. Because `getConnectedAccounts`/`isTrusted`/`isAutoApprove` are explicitly documented as usable "while the wallet is locked" to gate dApp interactions [11](#0-10) , a stuck-trusted origin retains the ability to request connected addresses/signing flows that should have been revoked — an unauthorized, persistent dApp-account privilege bleed, not merely a UI freeze.

### Likelihood Explanation
Adding a new wallet account (e.g., a hardware wallet with narrower asset support, or any future incompatibility) while origins remain connected to other assets is a realistic, non-adversarial condition — no malicious peer/operator is required, only an ordinary combination of an existing connected origin's asset list and a wallet account that can't derive one of those assets. Given `enabledWalletAccountsAtom` can include many accounts/sources (seed, hardware, exodus), and origins can list arbitrary `assetNames` [12](#0-11) , the odds of at least one unsupported pairing existing are non-trivial over time — closely mirroring the "many protocols, many tokens" likelihood argument from the source report.

### Recommendation
In `#getWalletAccountAddresses`, wrap `this.#addressProvider.getDefaultAddress(...)` in a try/catch (as already done for the analogous case in `asset-client-interface.js`), skipping/nulling unsupported (walletAccount, assetName) pairs instead of letting the exception propagate and block `#setData`. Ensure security-sensitive paths (`untrust`, `disconnect`, `setAutoApprove(false)`, `clearConnections`) can always complete even if address recomputation partially fails — e.g., persist the origin-list mutation first/independently of the best-effort `connectedAccountsAtom` refresh, rather than gating both on the same rejecting promise chain.

### Proof of Concept
1. Connect and trust origin A, granting it access to `assetNames: ['bitcoin', 'someAssetX']`.
2. Add/enable a new wallet account (e.g., hardware wallet account) whose asset-source support does not include `someAssetX`, via `enabledWalletAccountsAtom`.
3. Call `connectedOrigins.untrust({ origin: 'A' })` (or `setAutoApprove({ origin: 'A', value: false })`).
4. `untrust` → `#setData` → `#getAccounts(['bitcoin','someAssetX'])` → `#getWalletAccountAddresses` calls `addressProvider.getDefaultAddress({ assetName: 'someAssetX', walletAccount: newHwAccount })`, which throws `UnsupportedAssetSourceError` per `#assertAssetSourceIsSupported` [1](#0-0) .
5. The rejection propagates out of `untrust`; `connectedOriginsAtom` is never updated — origin A remains trusted/auto-approved despite the explicit revocation attempt, confirmed by re-reading `connectedOriginsAtom.get()` still containing origin A with `trusted: true`.

  #getAccounts = async (assetNames) => {
    const walletAccounts = Object.values(await this.#enabledWalletAccountsAtom.get())

    const entries = await Promise.all(
      walletAccounts.map(async (walletAccount) => [
        walletAccount.toString(),
        {
          addresses: await this.#getWalletAccountAddresses(walletAccount, assetNames),
        },
      ])
    )

    return Object.fromEntries(entries)
  }

  #getWalletAccountAddresses = async (walletAccount, assetNames) => {
    const connectedAccounts = await this.#connectedAccountsAtom.get()
    const entries = await Promise.all(
      assetNames.map(async (assetName) => {
        const existingAddress = connectedAccounts[walletAccount]?.addresses[assetName]
        if (existingAddress) {
          return [assetName, existingAddress]
        }

        const address = await this.#addressProvider.getDefaultAddress({ assetName, walletAccount })
        return [assetName, address.toString()]
      })
    )

    return Object.fromEntries(entries)
  }
