### Title
Unexpected revert on the curve-draining boundary buy due to ceil-rounded `amountInUsed` exceeding the LT actually supplied - ([File: packages/contracts/src/Router.sol], [File: packages/contracts/src/Zap.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch back-calculates `amountInUsed` with a ceiling division that is independent of, and inconsistent with, the floor-rounded uncapped `tokensOut` calculation that decided to trigger the cap in the first place. This can make the recomputed `amountInUsed` exceed the LT amount the caller actually minted/supplied (`ltMinted`) for a buy sized to exactly (or very nearly) drain the curve's real token balance — the same rounding-direction mismatch class as the reported `PartialFillLib::partition()` bug, where a `mulDivUp`-style ceiling on a derived amount makes it exceed the reference amount it is checked/subtracted against, causing a revert on a transaction that should succeed.

### Finding Description
`Router._computeBuy` computes the uncapped output with a **floor** division: [1](#0-0) 

```
newReserveAsset = reserveAsset + amountInUsed;
tokensOut = reserveToken - (k / newReserveAsset);   // k/newReserveAsset floors → tokensOut can round UP
...
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    cappedReserveToken = reserveToken - tokensOut;                 // fixed, independent of amountIn
    cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;  // CEIL division
    amountInUsed = cappedReserveAsset - reserveAsset;               // rounds amountInUsed UP
}
```

Because the uncapped `tokensOut` is itself rounded *up* by the floor division `k / newReserveAsset`, a buy that is sized to be *exactly enough* to sell out the remaining `realBalance` can already appear to overshoot it (`tokensOut > realBalance`) purely from that rounding artifact, tripping the cap branch. Once inside the cap branch, `amountInUsed` is recomputed from a completely independent ceiling division (`(k + cappedReserveToken - 1) / cappedReserveToken`), which has no guaranteed relationship to the original `amountIn`. Because one leg floors and the other ceils, `amountInUsed` can come out **strictly greater** than the `amountIn` (i.e., `ltMinted`) that was actually passed in by the caller.

This value flows directly into `Zap`'s buy path, where the LT actually available is exactly `ltMinted`: [2](#0-1) 

```
ltMinted = IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0);
(tokensOut, amountInUsed) = _buyOnCurve(tokenAddress, lt, ltMinted);
...
uint256 ltExcess = ltMinted - amountInUsed;   // underflows/reverts if amountInUsed > ltMinted
```

If `amountInUsed` (post-cap, ceil-rounded) exceeds `ltMinted`, `ltMinted - amountInUsed` underflows and the whole `Zap.buy` transaction reverts with an arithmetic-underflow panic — even though the buy was correctly sized to exactly deplete the curve's remaining real balance (the graduation-triggering buy the AGENTS.md docs describe as the "overflow buy cap" invariant). This is structurally the same bug class as the audited `_validatePartition` issue: a value produced by a ceiling/rounding-up operation is compared against (here: subtracted from) a reference amount it was implicitly supposed to equal, and the mismatched rounding direction makes the "exact fill" case revert instead of succeed.

Separately, inside `Router.buy` itself, `IERC20(asset).safeTransferFrom(to, pairAddr, amountInUsed)` pulls `amountInUsed` LT from the caller; if `amountInUsed` exceeds the LT balance/allowance the caller actually holds for this trade (exactly `ltMinted`), the ERC20 transfer reverts for the same underlying reason.

### Impact Explanation
Any unprivileged trader calling `Zap.buy`/`Zap.buyWithPermit` with an amount landing on or near the overflow-cap boundary (the natural "buy out the rest of the curve and trigger graduation" trade) can have their otherwise-valid transaction revert unexpectedly. This:
- Denies traders the ability to execute the exact boundary buy that should succeed and trigger graduation, forcing manual trial-and-error resizing of the buy amount.
- Can cause a filler/arbitrageur racing to be the graduation-triggering buyer to lose that trade to a different actor who submits a slightly different amount, mirroring the "fillers may end up losing their winning arbitrage" impact called out in the original report.
- Is a Medium-severity availability/logic defect on a core, frequently-hit code path (every buy that could deplete the curve), not a fund-theft bug, since no funds are lost — the transaction simply reverts.

### Likelihood Explanation
The bug is only reachable at the overflow-cap boundary, which is a narrow but *naturally occurring* input size (any buy attempting to acquire the remaining curve supply, which is exactly the buy size a rational graduation-seeking trader or automated buyer would submit). Because `Router._computeBuy`'s two divisions round in opposite directions with no reconciliation, the mismatch is a function of `k` and `cappedReserveToken`'s residues and will occur for specific but realistically reachable reserve states, so likelihood is Medium.

### Recommendation
Clamp the recomputed `amountInUsed` so it can never exceed the original `amountIn`/`ltMinted` (e.g., `amountInUsed = min(amountInUsed, amountIn)`), or align the rounding of the uncapped `tokensOut > realBalance` check with the capped-branch's ceiling division so the two computations are consistent at the boundary. At minimum, guard the `Zap.sol` subtraction (`ltMinted - amountInUsed`) with a check that treats `amountInUsed > ltMinted` as `amountInUsed = ltMinted` (or reverts with a clear, intentional error) instead of letting it panic on unsigned underflow.

### Proof of Concept
Exact reserve/`k` values that trigger the mismatch were not empirically derived in this review (would require enumerating `(reserveToken, reserveAsset, amountIn)` combinations where `floor(k/(reserveAsset+amountIn))` rounds `tokensOut` just over `realBalance` while the independently-ceiled `amountInUsed` exceeds `amountIn`). The mechanism is proven structurally by the code cited above: `tokensOut` in the uncapped path is computed via a **floor** division while `amountInUsed` in the capped path is recomputed via an unrelated **ceiling** division on a different divisor (`cappedReserveToken`, fixed once `tokensOut` is clamped to `realBalance`), so there is no invariant in the code guaranteeing `amountInUsed <= amountIn`. A concrete failing case can be constructed/fuzzed directly against `Router._computeBuy` (as exposed via `previewBuy`) by searching reserve states where `tokensOut(amountIn)` crosses `realBalance` by the smallest possible margin — this is exactly the class of input the existing `test_getAmountOut_buy_capsAtSellableBalance` / `test_inv_overflowCap_refundsLt` tests exercise, but neither test asserts the specific invariant `amountInUsed <= amountIn` that this finding shows is unguaranteed.     function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
