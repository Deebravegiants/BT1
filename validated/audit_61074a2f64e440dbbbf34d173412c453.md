### Title
Webhook HMAC signature does not bind the `shop-domain` (or `topic`) header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop-domain` and `topic` headers — which the handler trusts as the tenant/event identity — are never included in the signed material. Since the app's `api_secret_key` is shared across every shop that installs the app, any unprivileged merchant who has installed the app on their own store can capture a genuinely-signed `(body, hmac)` pair from their own webhook deliveries and replay it to the app's shared webhook endpoint with a forged `shop-domain` header pointing at a victim shop, causing the app to process attacker-controlled data as if it originated from the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from unauthenticated HTTP headers, none of which participate in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check, then forwards `request.shop` (an unauthenticated header) directly to the handler as the trusted tenant identity, along with `request.topic`: [4](#0-3) 

The binding that should hold is:
`hmac_signed_bytes == (shop, topic, body)` — but the actual equality enforced is only `hmac_signed_bytes == body`.

Because the app's `api_secret_key` used to compute this HMAC is the same for all shops that install the app (it is the app's client secret, not a per-shop secret), any merchant can install the public app on their own store, trigger an event (e.g. `orders/create`) to receive a legitimately Shopify-signed `(body, hmac)` webhook delivery, then re-POST that exact `body` and `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to name a different, victim shop that also uses the same app. `HmacValidator.validate` still returns `true` (the body/HMAC pair is valid for the shared secret), and `Registry.process` dispatches the attacker-controlled body to the handler tagged with `shop: <victim shop>`.

### Impact Explanation
This breaks the tenant identity binding an app relies on: the handler receives data purportedly from the victim shop, sourced entirely from attacker-controlled content that Shopify signed for the attacker's own store. Depending on how the host application's webhook handler uses `data.shop`/`data.body` (e.g., writing to per-shop records, triggering shop-scoped side effects), this enables cross-tenant data injection/corruption — the "cross-tenant access" class explicitly in scope.

### Likelihood Explanation
Any internet user can become a legitimate (if low-privilege) merchant installer of a public Shopify app, giving them a valid `(body, hmac)` sample without needing the app's `api_secret_key`, an access token, or any special privilege — only the ability to install the target app on a store they control and issue a normal HTTP POST with modified headers to the app's public webhook endpoint.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the shop/topic to the HMAC (e.g., verify against a per-shop expectation registered at webhook creation time) so that a valid HMAC for one shop's payload cannot be replayed under a different shop's identity.

### Proof of Concept
1. Install the target public app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger a webhook event (e.g. create an order) so Shopify sends a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid_hmac>`, and body `B`.
3. Capture `B` and `<valid_hmac>` (attacker controls their own endpoint infra or logs, or simply observes their own app's stored side effects to confirm receipt).
4. Replay `POST <app_webhook_endpoint>` with the same body `B` and header `x-shopify-hmac-sha256: <valid_hmac>`, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (per lib/shopify_api/utils/hmac_validator.rb:26-31, since only `B` is signed), and `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` and the attacker's crafted body content (lib/shopify_api/webhooks/registry.rb:188-200).
