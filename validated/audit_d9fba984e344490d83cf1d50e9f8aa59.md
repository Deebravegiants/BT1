### Title
Bad-debt index floor resurrects wiped supply claims that drain recapitalized cash - (File: contracts/pool/src/interest.rs)

### Summary
`apply_bad_debt_to_supply_index` clamps the post-write-down supply index up to `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) instead of letting it reach zero. Suppliers whose claims were meant to be fully socialized therefore retain a positive residual token claim. The market's `require_backed_market`/`require_reserves` gates only block extraction while cash is short; the permissionless `recapitalize` path credits fresh cash against `backing_shortfall` without minting shares or burning the dead claims. Once any recapitalizer fills the shortfall, every wiped-out supplier can call `withdraw` and pull real tokens for a claim the write-down was supposed to destroy. The pool's own test pins this: `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` shows a stranded position draining an entire fresh deposit to zero.

### Finding Description
The bug class (memory corruption / wrong-object reuse via crafted input, CVE-2018-4161) maps onto accounting corruption here: a clamp intended as a safety floor rewrites the post-condition of the write-down itself. In `contracts/pool/src/interest.rs:88` the new index is `new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW))`. When `bad_debt >= total_supplied_value`, `remaining = 0`, `reduction_factor = 0`, and mathematically the index — and every claim under it — should be zero. Instead the floor restores the index to `10^24`, so `unscale_supply_floor` returns a positive phantom balance for every supplier (`contracts/pool/tests/interest.rs:339-341`: `stranded > 0`, "floor clamp leaves userA a phantom claim").

Docs acknowledge the residual (`docs/reference/formulas.md:397-400`, INV-IDX-02 "can preserve an unbacked residual claim") but the exploitability is completed by `contracts/pool/src/ops/recapitalize.rs:52-57`: `applied = min(amount, backing_shortfall)` is credited to `cash` with no share mint and no neutralization of residual claims. `backing_shortfall` counts `floor(supply_value)` including the phantom claims, so a recapitalizer's donation directly backs them. After one `recapitalize` that covers the shortfall, `require_reserves` passes and `withdraw` pays out.

Unprivileged path:
1. Attacker (or any market participant) holds supply in market M.
2. An insolvent account's bad debt in M is permissionlessly cleaned (`clean_bad_debt`, eligible when collateral ≤ $5), triggering `apply_bad_debt_to_supply_index`; on a wipeout the index clamps at `RAY/1000` and all suppliers keep ~0.1%-of-value residual claims.
3. Anyone calls `recapitalize(M, amount)` — the controller transfers tokens to the pool, cash is credited up to the shortfall, excess refunded.
4. Each phantom holder calls `withdraw` and receives real tokens against claims that were economically destroyed in step 2.

### Impact Explanation
Theft of user funds: recapitalized cash intended to restore honest backing is paid out to dead claims. In a full wipeout the residual aggregate is bounded at roughly 1/1000 of the pre-wipeout supply value, but on a large market that is still a material sum taken from whoever recapitalizes — and the residual claims are prioritized identically to honest claims, so the drain is guaranteed rather than proportional. Alternatively the same mechanics let an attacker who engineers bad debt retain a claim the design intended to zero.

### Likelihood Explanation
Requires a near-total bad-debt wipeout in one market (`bad_debt >= total_supplied_value` at seize time) and a subsequent recapitalization. The utilization cap (`max_utilization ≤ 95%`) makes a single liquidation insufficient; a wipeout needs collateral-price collapse across a large debt book plus permissionless cleanup. Conditional and bounded in size — Medium.

### Recommendation
When `bad_debt >= total_supplied_value`, burn residual claims instead of clamping: either set the supply index to zero and require explicit re-initialization, or track wiped claims separately and exclude them from `supplied`/`backing_shortfall` so `recapitalize` never backs them. At minimum, exclude claims whose value derives solely from the floor clamp from withdrawal eligibility (e.g., gate `withdraw` on `backing_shortfall == 0 && index > SUPPLY_INDEX_FLOOR_RAW`).

### Proof of Concept
The pool test `test_raw_cache_floor_residual_can_consume_fresh_cash_without_supply_guard` (`contracts/pool/tests/interest.rs:317-369`) already demonstrates the primitive: after `apply_bad_debt_to_supply_index(cache, 2× total supply)`, the index sits at `SUPPLY_INDEX_FLOOR_RAW`, `stranded > 0`, and the stranded position withdraws exactly the fresh cash credited to the market, leaving an honest supplier's claim unbacked (`cash() < b_claim`, `cash() == 0`). In production the identical sequence is reachable via `clean_bad_debt` (wipeout + clamp), `recapitalize` (cash credit covering `backing_shortfall`), then `withdraw` (phantom payout).
