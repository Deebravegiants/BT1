### Title
Stale `_requestCommitments` fee metadata after a successful GET response allows double payment of the relayer fee / escrowed funds - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse, address)` pays out the relayer fee from `_requestCommitments[commitment]` on success but never deletes that entry, unlike every sibling dispatch path in the same contract (`dispatchIncoming(PostRequest,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, `dispatchTimeOut(PostRequestTimeout,...)`), all of which clear their replay-protection/fee state as part of a successful (or retried) completion. This is analogous to the CVE-2021-22945 bug class: a resource (`fee`/`FeeMetadata`) is "freed" from the caller's perspective (fee already paid out) but the pointer to it (`_requestCommitments[commitment]`) is kept alive, allowing it to be read and acted upon again in a later call.

### Finding Description [1](#0-0) 

In `dispatchIncoming(GetResponse memory response, address relayer)`:
1. `_responseReceipts[commitment]` is set unconditionally as replay protection for redelivery of the same `GetResponse` through `HandlerV2.handleGetResponses` (which separately checks `host.responseReceipts(...).relayer != address(0)` before calling `dispatchIncoming`, see `evm/src/core/HandlerV2.sol` lines 241-246).
2. On successful `onGetResponse` delivery, the relayer fee is read directly from `_requestCommitments[commitment].fee` and paid out via `IERC20(feeToken()).safeTransfer(relayer, fee)`.
3. Crucially, `_requestCommitments[commitment]` is **never deleted** on this success path (compare with `dispatchTimeOut(GetRequestTimeout...)` at lines 856-877 and `dispatchTimeOut(PostRequestTimeout...)` at lines 885-906, both of which `delete _requestCommitments[commitment]` before invoking the module callback, restoring it only on failure for retry).

Because the `FeeMetadata` (including the non-zero `fee`) survives a successful GET response delivery, this stale entry remains readable by any subsequent code path that consults `_requestCommitments[commitment]`. In particular:
- `handleGetRequestTimeouts` in `HandlerV2.sol` (lines 293-321) fetches `FeeMetadata memory meta = host.requestCommitments(commitment)` and, provided a state proof shows no *Hyperbridge-side* response receipt exists for the request, calls `host.dispatchTimeOut(GetRequestTimeout(...), meta, commitment)` — which refunds `meta.fee` a second time to `meta.sender`.
- Whether this second payout is achievable in practice depends on how/when Hyperbridge itself records a response receipt for a GET request relative to this EVM host's local response delivery (which is not proven by the same non-membership key checked here — the timeout path proves non-membership on Hyperbridge's trie, not on this EVM host's `_responseReceipts`). This coupling between two independently-updated commitments (local `_responseReceipts` vs. Hyperbridge `ResponseReceipts`) combined with `_requestCommitments` never being cleared on the success path is the structural flaw analogous to the UAF/double-free: stale state that should have been invalidated after first use remains live for reuse.

### Impact Explanation
If the stale `_requestCommitments[commitment]` fee metadata can be paired with a valid GET-timeout proof after the corresponding response was already successfully delivered and paid, this results in unbacked double payment of escrowed relayer fees from the host's fee-token balance — a direct theft/drain of protocol-held funds, reachable by any relayer/user who can submit the timeout message with a (possibly stale-timestamp) proof. Even absent that exact double-refund path, the missing cleanup on the primary GET-response success path is a clear deviation from the pattern used everywhere else in the file, and leaves commitment/fee state permanently un-freed, which is itself a fund-accounting inconsistency in the escrow the contract is supposed to guarantee.

### Likelihood Explanation
Medium: exploitation requires the attacker to construct a valid state-machine proof of non-membership of the response-receipt key on Hyperbridge's own trie for a request whose response was already delivered locally on the EVM host — this depends on Hyperbridge's exact bookkeeping timing for GET responses (which was not fully verifiable from the indexed code). Regardless of full timeout-based exploitability, the missing `delete _requestCommitments[commitment]` in the GET-response success branch is a clear code defect matching the reported bug class, and warrants an audit fix to bring it in line with the other three dispatch/timeout success paths in the same contract.

### Recommendation
Add `delete _requestCommitments[commitment];` immediately after the successful fee payout in `dispatchIncoming(GetResponse memory response, address relayer)` (mirroring the pattern in `dispatchTimeOut` for both GET and POST timeouts), so the fee metadata cannot be read or reused by any later flow (e.g., `handleGetRequestTimeouts`) once the response has been successfully delivered and paid.

### Proof of Concept
Conceptual PoC (pending confirmation of Hyperbridge's exact GET-response-receipt bookkeeping, which limits full end-to-end verification from the indexed code):
1. Dispatch a `DispatchGet` from `EvmHost`, creating `_requestCommitments[commitment] = FeeMetadata{sender, fee}` [2](#0-1) .
2. Relayer submits `handleGetResponses` with a valid response leaf; `dispatchIncoming(GetResponse,...)` succeeds, pays `fee` to the relayer, but leaves `_requestCommitments[commitment]` intact [3](#0-2) .
3. Later, if a valid `GetTimeoutMessage` non-membership proof (against Hyperbridge's own response-receipt trie key, independent from this host's `_responseReceipts`) can still be produced/timed for the same commitment, submit `handleGetRequestTimeouts` → `dispatchTimeOut(GetRequestTimeout...)`, which reads the still-present `meta.fee` and refunds it again to `meta.sender` [4](#0-3) , resulting in the fee being paid out twice for a single GET request.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
