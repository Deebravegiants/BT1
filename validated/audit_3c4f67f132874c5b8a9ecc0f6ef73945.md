### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds `shop`, `topic`, `webhook-id`, and `api-version` to un-signed HTTP headers, while `Registry.process` only verifies the HMAC over the raw request body. An attacker who captures one legitimate webhook delivery (body + valid HMAC) for their own store can replay that exact body/HMAC pair while substituting a different `x-shopify-shop-domain` header value, and the signature check will still pass. This breaks the identity binding that `shop == the tenant whose data was actually authenticated by Shopify's signature`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header — it never incorporates `shop`, `topic`, or any other header into the signed material: [3](#0-2) [4](#0-3) 

`Registry.process` performs exactly this check and then forwards the unauthenticated `request.shop` value straight into the handler's `WebhookMetadata`: [5](#0-4) 

Because the `hmac-sha256` signature is computed only from the raw body, it stays valid for *any* combination of headers as long as the body bytes are unchanged. The binding that should hold is:
`shop authenticated by Shopify's HMAC == shop delivered to the app's handler`
but the implementation actually enforces only:
`raw_body authenticated by Shopify's HMAC == raw_body delivered to the app's handler`
with `shop` (and `topic`/`webhook_id`/`api_version`) passed through unchecked.

### Impact Explanation
Any unprivileged internet user who can install the app on their own store (or otherwise trigger/observe one legitimate webhook delivery for a store they control) obtains a `(raw_body, hmac)` pair that Shopify's servers will always accept as authentic, since the HMAC never binds to the shop domain. That attacker can then POST the identical body/HMAC to the victim application's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at any other merchant's shop. `Registry.process` will accept it as a validly signed webhook and hand `WebhookMetadata.new(shop: <attacker-chosen-shop>, body: <attacker's original body>, ...)` to the app's registered handler. Any host application that uses `data.shop` to decide which merchant's records to update, delete, or sync (a documented and expected pattern per this gem's own `WebhookMetadata`/handler API) will apply the attacker's payload against a shop it was never delivered for — a cross-tenant data integrity breach reachable with no credentials beyond a free store signup.

### Likelihood Explanation
The attack requires no access to `api_secret_key`, no leaked credentials, and no privileged account — only the ability to install the target app on a shop the attacker controls (or otherwise observe one webhook delivery) and then send one crafted HTTP request with modified headers to the app's public webhook endpoint. This is achievable by any unprivileged internet user and directly exercises the gem's own `Webhooks::Request`/`Webhooks::Registry.process` code path with no reliance on host-application misbehavior beyond the intended, documented use of `data.shop`.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signed material that `HmacValidator` checks, or otherwise cryptographically bind the header values to the HMAC (e.g., require the signature to cover a canonical string composed of body + shop domain), so that a valid signature for one shop/body pair cannot be replayed with a different shop header. At minimum, `Registry.process` should independently validate that the `shop` header corresponds to a shop the app has an active session/webhook registration for before invoking handlers.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook POST, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <validHmacForBody>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the identical request to the app's webhook endpoint, changing only `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim.myshopify.com`, keeping body and `hmac-sha256` header unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it validates only `request.hmac` against `Digest::HMAC(secret, raw_body)`: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's chosen body, even though Shopify never sent this webhook for `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
