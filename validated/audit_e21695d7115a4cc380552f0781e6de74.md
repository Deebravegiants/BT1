### Title
`IntentGatewayV2.placeOrder` (Tron variant) escrows the declared amount instead of the actually-received token amount, causing under-collateralized escrow for fee-on-transfer/rebasing/rounding tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`'s non-predispatch escrow branch pulls `order.inputs[i].amount` via `safeTransferFrom` but then credits `_orders[commitment][token]` with `reducedInputs[i].amount`, which is derived from the *declared* `order.inputs[i].amount` (minus protocol fee), never from the token balance actually received by the contract.

`reducedInputs[i].amount` is computed purely from `order.inputs[i].amount` (the user-declared amount) at lines 359-374, with no correction for what the token transfer actually delivered. For any token whose `transferFrom` moves fewer units than the requested `amount` — fee-on-transfer tokens, or share/rebasing tokens like Lido's `stETH` that round shares down by 1-2 wei (the exact bug class in the referenced report) — the contract's real balance of `token` ends up strictly less than the sum recorded in `_orders[commitment][token]`.

This is the same root-cause pattern the report describes: passing the pre-transfer "intended" amount downstream instead of measuring the actual balance delta. Notably, the **EVM mainline** `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this class of bug — its non-predispatch branch explicitly does:
```solidity
// evm/src/apps/IntentGatewayV2.sol:320-322
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
```
and its predispatch branch also measures `received` via balance diffs before computing `reducedInputs`. The Tron fork (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not contain this fix in either its predispatch or non-predispatch escrow paths — both branches store `reducedInputs[i].amount`/`requiredAmount` computed from the original declared amount, not the measured balance received.

### Impact Explanation
Because `_orders[commitment][token]` is the ledger the protocol uses to (a) pay a filler/solver upon `RedeemEscrow`/settlement and (b) determine refund amounts on cancellation/timeout, an escrow entry that is inflated relative to the contract's actual token holdings means:
- Settlement/refund calls that pay out `_orders[commitment][token]` can revert due to insufficient contract balance (denial-of-service on that order, and potentially on unrelated orders sharing the same token pool if funds are drawn from a shared balance rather than a per-order sub-balance), or
- If the shortfall is drawn from the token's *shared* contract balance (rather than being strictly per-order segregated), it can silently consume funds belonging to other orders' escrow, permanently under-funding them — a fund-freezing/loss condition for other order placers.

This matches the "Medium/High, DoS via balance shortfall" classification of the referenced report, reachable by any unprivileged user simply calling `placeOrder` with such a token as an input, with no privileged role required.

### Likelihood Explanation
High for any deployment of this Tron contract that allows fee-on-transfer or share/rebasing ERC-20 tokens as intent inputs (a normal, permissionless configuration point — token allow-listing is not visible in this file), and it happens deterministically on every affected transfer, not merely as an edge case. Given the mainline EVM contract was already patched for this exact class of bug, its absence here indicates the Tron variant diverged from the fix.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the actual token balance delta (`balanceOf` before/after `safeTransferFrom`) for each input in both the predispatch and non-predispatch escrow branches of `evm/tron/contracts/apps/IntentGatewayV2.sol`, and compute `reducedInputs`/the escrow credit and the commitment from that actually-received amount rather than the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Configure (or a user submits) an order whose `order.inputs[0].token` is a token that delivers less than the requested amount on `transferFrom` (e.g., stETH-style share rounding, or a fee-on-transfer token) with `amount = A`.
2. `placeOrder` calls `safeTransferFrom(msg.sender, address(this), A)`; actual tokens received by the contract are `A - δ` (`δ` = 1-2 wei for stETH rounding, or the fee for FoT tokens).
3. `_orders[commitment][token]` is incremented by `reducedInputs[0].amount = A - protocolFee`, i.e., based on `A`, not `A - δ`.
4. The contract's real `token` balance is short by `δ` relative to the sum of all `_orders[...][token]` entries.
5. When the order is later filled/redeemed or refunded and the code attempts to transfer out `_orders[commitment][token]`, the transfer can revert for insufficient balance (DoS), or, if balances are pooled across orders, drain balance intended for a different order's escrow.
