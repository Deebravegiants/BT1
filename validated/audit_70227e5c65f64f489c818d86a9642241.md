### Title
Webhook shop-tenant spoofing via HMAC that only covers the body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` binds the shop identity used by webhook handlers to the `shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body. Because the app's HMAC secret (`api_secret_key`) is a single value shared across every shop that installs the app (not shop-specific), any request with a body+HMAC pair that is valid for one shop remains HMAC-valid when replayed with a different `shop-domain` header value, letting an attacker attribute arbitrary webhook content to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) . The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that is never included in the signed payload [2](#0-1) . `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` (which checks `request.hmac` against `HMAC-SHA256(secret, request.to_signable_string)`, i.e., the body only) and then immediately constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the unauthenticated header, dispatching it to the registered handler [3](#0-2) .

This breaks the intended identity binding `hmac_valid_for(body) == shop_that_the_body_belongs_to`. The equality that should hold is: `shop asserted to handler == shop cryptographically tied to the signed bytes`. In this implementation, the left side comes from a header outside the signature, and the right side is never computed or compared — the HMAC only proves "this body was produced using the app's secret," not "this body was produced for this shop." Since `Context.api_secret_key` is the same secret for every shop that has installed the app (it is not per-tenant), a body+HMAC pair that is valid for shop A's webhook remains valid when paired with shop B's `shop-domain` header.

### Impact Explanation
This is a cross-tenant data-integrity break inside the gem's own webhook-verification code: an app relying on `ShopifyAPI::Webhooks::Registry.process` and trusting `WebhookMetadata#shop` to select which merchant's records to update would process attacker-supplied body content under a victim merchant's identity. This matches the Critical "cross-tenant access" impact category, since the library's documented verification API (`HmacValidator.validate` + `Registry.process`) gives no protection against this header substitution — the gem itself never binds `shop` to the authenticated bytes.

### Likelihood Explanation
Any unprivileged user who can install the app on their own development/test store (a normal, unprivileged action) receives legitimately signed webhook deliveries for their own shop. Because the signing secret is shared across all shops for the app, the attacker can capture one such body+HMAC pair and replay it directly to the app's webhook endpoint with the `shop-domain` header changed to any other shop that has installed the app — no access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signable content, or otherwise cryptographically bind `shop` to the verified payload in `Webhooks::Request`/`HmacValidator`, so that `Registry.process` cannot dispatch a `shop` value that was not covered by the signature check.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify computed with the app's shared secret.
2. Send a new POST to the app's webhook endpoint with the exact same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) using the same shared `api_secret_key` and succeeds, since only the body is checked [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it belonged to the victim shop.
