This confirms the claim precisely. The code shows `jsonrpc.Request[json.RawMessage]` contains an `Auth` field populated with the caller's JWT bearer token, as demonstrated by `Auth: "jwt-token"` in test fixtures [1](#0-0)  and the outbound helper that strips `Auth` before logging/transmission via `outboundRequestWithoutAuth` [2](#0-1) , confirming the field is treated as sensitive elsewhere in the codebase. Both flagged `Debugw` calls log the entire `req`/`request` struct — which is a Go struct containing the `Auth` string field — before authorization occurs: `HandleJSONRPCUserMessage` logs `"request", req` at line 403, prior to the `ProcessRequest` call at line 427 [3](#0-2) [4](#0-3) , and `HandleGatewayMessage` logs `"req", req` at line 182 before the authorization switch [5](#0-4) . Zap's `Debugw`/sugared logger with a struct value (not implementing `zapcore.ObjectMarshaler`) will serialize it via reflection (or `%v`), which will include all exported fields including `Auth`, since no custom marshaler or redaction exists on `jsonrpc.Request`. Elsewhere in the same codebase, the pattern of using `"hasAuth", req.Auth != ""` instead of the raw field is used deliberately in `authorizer.go` [6](#0-5) , confirming that raw `Auth` logging is recognized as unsafe elsewhere but was missed in these two locations. The existing regression test only guards the invalid-params error path at Info level, explicitly excluding the pre-existing whole-request Debug log from its scope, as noted in the test comment itself [7](#0-6) , so there is no protection for the two entry-point Debug logs identified in the claim.

This is a legitimate, reachable credential-disclosure issue: it requires no privileged access to trigger (only Debug-level logging enabled on the node, a documented/supported operator configuration [8](#0-7) ), and any unprivileged client sending a normal JWT-authenticated request causes the JWT bearer token to be written to logs.

Audit Report

## Title
Vault gateway handlers log the full JSON-RPC request — including the authentication credential (`req.Auth`) — at Debug level before authorization - ([File: core/services/gateway/handlers/vault/handler.go], [File: core/capabilities/vault/gw_handler.go])

## Summary
`HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` and `HandleGatewayMessage` in `core/capabilities/vault/gw_handler.go` both log the full `jsonrpc.Request[json.RawMessage]` object via `Debugw` before any authorization check runs. Since `req.Auth` carries the caller's JWT bearer credential, enabling Debug logging causes every inbound Vault request's raw JWT and payload to be written to node logs.

## Finding Description
`HandleJSONRPCUserMessage` executes `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` at line 403, unconditionally for every inbound request, prior to `h.requestProcessor.ProcessRequest` at line 427 which performs authorization. Likewise, `HandleGatewayMessage` executes `reqLggr.Debugw("received message from gateway", "req", req)` at line 182, before the method switch that performs authorization. In both cases `req` is a `jsonrpc.Request[json.RawMessage]` struct carrying the `Auth` field, which is the JWT used for per-request authorization (confirmed by `req.Auth` usage throughout `authorizer.go` and the test suite's use of `Auth: "jwt-token"`). Neither `jsonrpc.Request` nor the `Debugw` calls apply any redaction, unlike the deliberate `"hasAuth", req.Auth != ""` boolean pattern used elsewhere in `authorizer.go`, showing the team is otherwise aware `Auth` should not be logged raw. The existing `TestVaultHandler_InvalidParamsDoesNotLogRawParams` test explicitly excludes this pre-existing Debug log from its scope (observing at Info level), so it provides no protection against this leak.

## Impact Explanation
When a node operator enables `Log.Level = 'debug'` — a documented, supported configuration — every JWT-authenticated Vault request (secrets create/update/delete/list) causes the caller's raw bearer JWT and request payload to be written into the node's logs. Anyone with read access to those logs (log aggregation systems, shipped log files) can recover a valid JWT within its validity window, enabling replay/analysis of a legitimate credential — a credential/secret exfiltration impact in the same class as CVE-2019-11407.

## Likelihood Explanation
No special privilege is needed to trigger the log lines: any client authorized to talk to the gateway (the normal, intended access path for Vault users) causes both log statements to fire on every message, regardless of whether authorization ultimately succeeds. The sole precondition — Debug logging enabled — is a common, documented, non-privileged operational setting, making this a straightforward disclosure any time the node runs at that log level.

## Recommendation
- Remove the `req`/`request` field from the `Debugw` calls in `HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:403`) and `HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:182`).
- Replace with redacted summaries (e.g., `"hasAuth", req.Auth != ""`), matching the existing pattern in `authorizer.go`, and avoid logging raw `req.Params`.
- Extend log-leakage regression tests to cover these two unconditional entry-point Debug logs, not just the invalid-params path.

## Proof of Concept
1. Configure a node with `Log.Level = 'debug'`.
2. As a client holding a valid JWT, send a `vault.secrets.list` (or any Vault method) JSON-RPC request through the gateway with `Auth` populated.
3. Observe the node logs contain `"received message from gateway" req=<struct including raw Auth JWT>` (`core/capabilities/vault/gw_handler.go:182`) and/or `"handling vault request" ... request=<struct including raw Auth JWT>` (`core/services/gateway/handlers/vault/handler.go:403`), disclosing the bearer JWT in plaintext logs.
