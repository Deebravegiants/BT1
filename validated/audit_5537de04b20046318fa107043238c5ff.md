### Title
Failed encryption due to WebCrypto `getRandomValues` 65536-byte quota leaves plaintext secret buffers unwiped in memory - ([File: libraries/browser-extension-adapters/seco-storage/seco.js])

### Summary
`encryptString` computes the ciphertext, then attempts to zero out the plaintext-derived buffers (`databuffer`, `gzipped`, `expanded`) sequentially using `globalThis.crypto.getRandomValues()`. Because this API enforces a 65536-byte quota per call and throws `QuotaExceededError` beyond it, a sufficiently large value passed through `storage.set(key, value, { passphrase })` can cause the wipe sequence to abort partway through, leaving one or more plaintext-derived buffers un-zeroed while the computed ciphertext is silently discarded.

### Finding Description
In `encryptString`, the plaintext is transformed and encrypted before any wiping occurs: [1](#0-0) 

The wipe calls run in fixed order: `databuffer` (raw plaintext), then `gzipped` (compressed plaintext), then `expanded` (padded plaintext copy fed to `_encrypt`). `expand32k` pads/expands the buffer to a block size, so `expanded` is always at least as large as `gzipped` and can exceed 65536 bytes well before `databuffer` does. Node's WebCrypto `crypto.getRandomValues` implementation enforces the same 65536-byte quota as browsers and throws when exceeded. If `gzipped` or `expanded` exceeds that quota, the corresponding `getRandomValues` call throws, the surrounding `try/catch` swallows it and rethrows a generic `Unable to encrypt data` error, and the still-unwiped buffer(s) — which are copies of/derived from the caller's plaintext secret — remain resident in memory with no further attempt at zeroing. This is reachable through `index.js`'s `_set`, which builds `data` via `BJSON.stringify(value)` and forwards it unchecked to `seco.encryptString`: [2](#0-1) 

There is no size validation or chunked wiping anywhere in this path, so any caller able to route a sufficiently large value into `storage.set(key, value, { passphrase })` (e.g., importing a large backup blob or oversized remote-config payload) can trigger this partial-wipe/discard behavior.

### Impact Explanation
This is a memory-hygiene/secret-residency weakness: on this specific size-triggered failure path, plaintext-derived buffers that would otherwise be explicitly zeroed are left intact in the process heap indefinitely (subject to GC), while the encryption result is discarded entirely (no ciphertext is persisted or returned). This widens the window during which the secret is recoverable via memory-inspection primitives (e.g., process dump, other memory-disclosure bug, GC-lifecycle timing), though it does not by itself grant an attacker read access to memory — it is a "secrets don't stay secret as long as intended" weakness rather than direct unauthorized signing/disclosure.

### Likelihood Explanation
Triggering requires only that an oversized value be routed through `set()`/`batchSet()` with a `passphrase` option — e.g., a large imported backup or a bloated remote-config document — and does not require any privileged state. The size threshold (buffer ≥ ~65536 bytes after gzip+expand) is easily crafted deterministically by an attacker controlling the size of the stored value.

### Recommendation
Pre-validate `data`/derived buffer sizes against the WebCrypto quota before encryption, or replace `crypto.getRandomValues` wiping with a wipe routine that chunks writes into ≤65536-byte slices (looping over the buffer) so partial buffers are always fully overwritten regardless of length, and ensure buffers are wiped in a `finally` block (covering the failure path) rather than only on the success path after `_encrypt`.

### Proof of Concept
Unit test (`seco.test.js`):
1. Call `encryptString({ data: 'x'.repeat(200_000), key: 'passphrase', appVersion: '1.0' })` (200KB is large enough that gzip+expand still exceeds 65536 bytes for non-compressible data, e.g. random bytes instead of repeated char).
2. Spy on `globalThis.crypto.getRandomValues` to record which buffer instances are passed to it before a `QuotaExceededError`/`RangeError` is thrown (Node's `getRandomValues` throws for `byteLength > 65536`).
3. Assert the function throws `Unable to encrypt data`.
4. Assert that the buffer that triggered the quota error (and any subsequent buffer in the sequence, e.g. `expanded` if `gzipped` failed first) still contains its original (non-random, non-zero) plaintext-derived bytes — i.e., `getRandomValues` was never invoked on it — demonstrating the buffer was never wiped.
5. Expected (failing) assertion: all three buffers (`databuffer`, `gzipped`, `expanded`) should be fully zeroed/randomized even when `_encrypt`'s output is discarded; the current implementation fails this assertion for buffers beyond the one that first exceeded the quota.
