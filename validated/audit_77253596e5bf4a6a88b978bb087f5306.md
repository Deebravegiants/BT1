Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only checks the HMAC against `to_signable_string` (the body) [3](#0-2) , and once that passes, `Registry.process` trusts `request.shop` and `request.topic` verbatim to build the `WebhookMetadata` dispatched to the app's handler [4](#0-3) .

### Title
Webhook `shop`/`topic` headers are trusted without being bound to the HMAC-signed payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values that the gem hands to the merchant's webhook handler are read straight from request headers that are not covered by that signature. Since Shopify webhook HMACs are computed with the app's `client_secret`, which is identical for every shop that has installed the app, any tenant that has installed the app can capture one of their own genuinely-signed webhook deliveries and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header swapped to a different, victim shop. The signature check still passes because it only validates the body, letting the attacker's shop inject data attributed to another shop.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only involve the raw body [5](#0-4) , and `HmacValidator.validate_signature` recomputes and compares the digest exclusively over `verifiable_query.to_signable_string` [3](#0-2) . This means the equality the code actually enforces is `HMAC(body, client_secret) == received_signature`, not `HMAC(body ∥ shop ∥ topic, client_secret) == received_signature`. However, `Registry.process` treats the header-derived `request.shop` and `request.topic` as authoritative tenant/routing identifiers once that narrower check succeeds, passing them into `WebhookMetadata` for the handler to act on [4](#0-3) . Because `client_secret` is shared across every shop that installs the same app, an attacker who legitimately controls one installed shop can replay a genuine, correctly-signed webhook body under a forged `shop-domain` (and `topic`) header for a different shop, and the gem will accept it as authentic and hand the forged identity to the handler.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: a party with no relationship to the victim shop, other than being another customer of the same app, can make the app process attacker-supplied webhook payloads as if they came from the victim shop. Depending on how the host application uses `data.shop` (e.g., to look up the shop's session/store record and write data, trigger redaction, or update local records), this enables cross-tenant data corruption/injection under a forged shop identity, which falls under cross-tenant access.

### Likelihood Explanation
Exploitation only requires the attacker to run/install the app on a shop they control (a normal, low-privilege capability for any of the app's own merchants) and to have an HTTP client capable of resending a captured POST with a modified header — no access to `client_secret`, tokens, or the target shop is required.

### Recommendation
Bind the webhook's claimed shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or otherwise cross-check `request.shop` against an out-of-band trusted source before dispatch (e.g., verify the shop is one that is actually subscribed/registered for that topic, or require the host application to correlate `shop` with a stored subscription record) instead of trusting the raw header once only the body's HMAC has been validated.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook POST from Shopify for some topic, e.g. body `{"id":1}` with headers `X-Shopify-Hmac-Sha256: <valid-for-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker resends the exact same body and HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so `Registry.process` proceeds [6](#0-5) .
4. `WebhookMetadata.shop` is set to `victim-shop.myshopify.com` from the forged header [7](#0-6) , and the app's handler processes attacker-controlled data attributed to the victim shop.
