## Title
Silent failure of credit balance debit on capability overspend allows quota bypass in CRE workflow metering - ([File: core/services/workflows/metering/metering.go])

## Summary
In `Report.Settle`, when a capability's aggregated reported spend (`spentCredits`) exceeds the amount earmarked for that step (`step.Deduction`), the code attempts to "refund" the difference via `r.balance.Add(step.Deduction.Sub(spentCredits))`. Since `balanceStore.Add` rejects negative arguments with `ErrInvalidAmount`, this call silently no-ops in the overspend case, leaving `r.balance` still reflecting only the amount pre-deducted by `Deduct`/`Minus` rather than the true (higher) spend, while `r.balance.AddSpent(spentCredits)` correctly records the true spend only in the separate billing-receipt counter. [1](#0-0) [2](#0-1) 

## Finding Description
`Deduct` (via `ByResource`/`ByDerivedAvailability`) earmarks a step's spend by calling `r.balance.Minus(bal)`, immediately subtracting the earmarked amount from the local in-execution balance. [3](#0-2) [4](#0-3) 

`Settle` is later called with the capability's actual reported spend, aggregates it into `spentCredits`, and is meant to true-up the balance: return the unspent earmark if `spentCredits < step.Deduction`, or claw back the extra if `spentCredits > step.Deduction`. [5](#0-4)  The reconciliation is implemented as a single call to `balanceStore.Add(step.Deduction.Sub(spentCredits))`, whose guard `if amount.LessThan(decimal.Zero) { return ErrInvalidAmount }` causes the balance to remain unmodified whenever `spentCredits > step.Deduction` — exactly the overspend case that should reduce the balance further. [1](#0-0) [6](#0-5)  The only observable effect is an `Info`-level log ("invariant: spend exceeded reserve"), with no compensating `Minus` call and no fail-safe switch to metering mode. `r.balance.AddSpent(spentCredits)` still runs unconditionally, so the true spend is recorded correctly in the separate `spent` accumulator used at receipt time, but not reflected in `r.balance`, which is what gates subsequent `Deduct` calls via `getMaxSpendForInvocation`/`ByDerivedAvailability`. [7](#0-6) 

This reproduces the described root-cause pattern: a "loss"/overspend branch that should reduce a tracked value is dropped because the update path only handles the non-negative case.

## Impact Explanation
Because `r.balance` is not corrected downward on overspend, later steps within the same workflow execution compute their spend ceilings (`ByDerivedAvailability` → `getMaxSpendForInvocation`) from an inflated balance. This allows a single workflow execution to authorize cumulative capability spend (compute, gas, HTTP calls, etc.) beyond what was actually reserved from the billing service via `Reserve`, since the discrepancy is only corrected after the fact when `AddSpent`/`SendReceipt` report the true total to billing at the end of execution. This maps to a quota/spend-limit-bypass class issue within the CRE metering enforcement path rather than a pure accounting cosmetic bug, since it can let one execution consume more resources than its reserved credit budget permits before it is caught.

## Likelihood Explanation
No operator/admin access is required to reach this code path — it executes automatically inside every workflow execution's normal `Deduct`/`Settle` cycle. However, triggering the overspend condition itself requires a capability step's aggregated node-reported spend to exceed its earmarked `Deduction`, which in `ByDerivedAvailability` is derived from `r.balance` split across concurrent call slots. This can occur from legitimate variance (e.g., gas price fluctuation, concurrent-slot division underestimating usage) without any external attacker input, or could be amplified by a capability node inflating its reported `SpendValue`/`SpendValueInGasUnits` (the latter edges toward a malicious/misbehaving DON-node scenario). The bug's occurrence is not directly and deterministically controllable by an unprivileged external HTTP-trigger caller, but the underlying accounting flaw is real and independent of that caller's privilege level — it is a general metering-integrity defect reachable during ordinary, non-privileged workflow execution.

## Recommendation
In `Report.Settle`, explicitly branch on the sign of `step.Deduction.Sub(spentCredits)` instead of relying on `balanceStore.Add`'s validation to implicitly signal an error. If `spentCredits <= step.Deduction`, refund the difference with `Add`; if `spentCredits > step.Deduction`, call `balance.Minus` (or an equivalent that clamps at zero) for the excess amount and consider switching the report to metering/fail-safe mode, ensuring the balance used to gate subsequent `Deduct` calls always reflects true remaining credits.

## Proof of Concept
1. Call `Report.Reserve` to set a fixed starting balance from the billing service.
2. Call `Deduct` for step A using `ByDerivedAvailability`, which computes `Deduction = D` and calls `balance.Minus(D)`.
3. Call `Settle` for step A with `metadata.Metering` node responses whose aggregated `spentCredits > D`.
4. Assert (unit test on `metering.go`) that after `Settle`, `r.balance.Get()` is unchanged from its post-`Minus(D)` value instead of being further reduced by `spentCredits - D`, while `r.balance.GetSpent()` correctly equals `spentCredits`.
5. Call `Deduct` again for step B and observe that `getMaxSpendForInvocation` computes its limit from the not-fully-decremented `r.balance`, granting a higher spend ceiling than the true remaining reserved credits would allow.

// ByResource returns a DeductOpt that earmarks a specified amount of local universal credit balance for a given spend
// type.
func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     capabilityID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		bal, err := r.balance.ConvertToBalance(spendType, amount)
		if err != nil {
			// Fail open, continue optimistically
			r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
		}

		step.Deduction = bal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return []capabilities.SpendLimit{}, r.balance.Minus(bal)
	}

// ByDerivedAvailability returns a DeductOpt that derives the maximum spend limit based on the user spend limit and
// the number of open concurrent call slots.
func ByDerivedAvailability(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
	info capabilities.CapabilityInfo,
	config *values.Map,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     info.ID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		limit, err := r.getMaxSpendForInvocation(userSpendLimit, openConcurrentCallSlots)
		if err != nil {
			return nil, err
		}

		if !limit.Valid {
			return []capabilities.SpendLimit{}, nil
		}

		step.Deduction = limit.Decimal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return r.creditToSpendingLimits(info, config, limit.Decimal), r.balance.Minus(limit.Decimal)
	}
}

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
