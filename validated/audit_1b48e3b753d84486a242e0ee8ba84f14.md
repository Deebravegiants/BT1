Confirmed: `Commitment.payload` is an unbounded `Payload[]` array (`evm/src/consensus/Types.sol:77-86`), with no length cap anywhere in `RelayChainProof`/`SignedCommitment`/`BeefyConsensusProof`, and `Codec.Encode(Commitment)` rebuilds it via repeated `bytes.concat` inside a loop.

### Title
Unbounded `Commitment.payload` re-encoding via `bytes.concat` loop causes quadratic gas DoS in BEEFY consensus verification - ([File: evm/src/consensus/Codec.sol])

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` re-encodes the relayer-supplied `Commitment` struct with `Codec.Encode(commitment)` to recompute `commitmentHash` for `ecrecover`. `Codec.Encode` loops over `commitment.payload` (an attacker-controlled, unbounded `Payload[]` array) and calls `bytes.concat` once per element, each time reallocating and copying the entire accumulated buffer. This is the same complexity class as the Django `MultiPartParser` CVE: a decoder/encoder that repeatedly re-processes/re-copies attacker-controlled input in a loop with no size cap, producing quadratic (`O(n²)`) work from linear input size.

### Finding Description
`Codec.Encode(Commitment memory commitment)`: [1](#0-0) 
iterates `payloadLen = commitment.payload.length` times, and on every iteration does `payload = bytes.concat(payload, ...)`. In Solidity, `bytes.concat` allocates a brand-new `bytes` array and copies both operands into it — it does not append in place. Doing this inside a loop over `payload` means the total number of bytes copied grows quadratically with `payloadLen` (each iteration re-copies everything accumulated so far).

`Commitment` is defined with an unbounded array: [2](#0-1) 

Nothing in `RelayChainProof`, `SignedCommitment`, or `BeefyConsensusProof` bounds `payload.length`: [3](#0-2) 

This structure is decoded straight from calldata supplied by any permissionless caller of `EcdsaBeefy.verify` (reached via `HandlerV2.handleConsensus`, itself permissionless per `evm/src/core/HandlerV2.sol:144`), and `verifyMmrUpdateProof` calls the quadratic encoder on the very first pass over the untrusted commitment, before any signature or authority-set check can reject it cheaply: [4](#0-3) 

An attacker can craft a `Commitment.payload` array with a large number of small `Payload` entries (each `{bytes2 id; bytes data;}`), submit it via `handleConsensus`/`batchCall`, and force `Codec.Encode` to perform `O(n²)` memory copy work relative to `payload.length` before the transaction ever gets to signature verification or reverts. Because gas cost scales quadratically with attacker-supplied array length, this is a `CWE-407: Inefficient Algorithmic Complexity` issue directly analogous to the reported Django `MultiPartParser` base64-whitespace bug — both are algorithmic-complexity blowups triggered by attacker-controlled, insufficiently bounded input processed in a loop that repeatedly reprocesses/recopies the whole buffer.

### Impact Explanation
This is reachable by any unprivileged relayer submitting a consensus proof to `HandlerV2.handleConsensus` (or bundled in `batchCall`), matching the required "unprivileged message dispatcher/relayer" reachability. A crafted payload array can consume attacker-controlled but victim-paid gas disproportionately (if gas-sponsored) or, more importantly, make the worst-case gas cost of `handleConsensus` far exceed what block gas limits allow for legitimately-sized commitments, effectively making it possible to construct a `Commitment` that cannot be processed within a block gas limit — a denial of the consensus-update path (a "route unable to deliver messages" outcome, since the BEEFY consensus client is the entry point that unblocks all cross-chain message delivery on that route). Because `EcdsaBeefy` is the fallback ECDSA verifier for chains without SNARK infra, DoS'ing this path can stall consensus updates and thus stall the entire bridge route.

Severity is Medium, consistent with the reference advisory's severity and CVSS profile (availability impact only, no confidentiality/integrity impact, low privilege, network-reachable).

### Likelihood Explanation
Medium-to-High: The `payload` field's only real-world content is normally a single MMR-root entry (`"mh"`), so nothing rejects an oversized array before `Codec.Encode` is invoked; there is no explicit `payload.length` cap in `Types.sol`, `EcdsaBeefy.sol`, or the ABI decoding of `BeefyConsensusProof`. Constructing the malicious calldata requires no special permissions, no valid signatures, and no consensus knowledge — just a large `Payload[]` array, since the quadratic cost is paid before signature/authority checks fail.

### Recommendation
Bound `commitment.payload.length` to a small constant (e.g., 1–4) at the very start of `verify`/`verifyMmrUpdateProof`, rejecting with a revert before calling `Codec.Encode`. Additionally, rewrite `Codec.Encode` to pre-size a single buffer and write into it with `Bytes`-style in-place assembly writes instead of repeated `bytes.concat`, eliminating the quadratic blowup regardless of array size.

### Proof of Concept
1. Construct a `BeefyConsensusProof` whose `relay.signedCommitment.commitment.payload` array contains, e.g., 10,000 minimal `Payload{ id: 0x0000, data: "" }` entries (only one entry needs `id == "mh"` with 32-byte data to pass the `mmrRoot` extraction check; the rest are padding).
2. Submit it via `EcdsaBeefy.verify(previousState, proof)` (directly, or through `HandlerV2.handleConsensus`).
3. Observe that `verifyMmrUpdateProof`'s call to `Codec.Encode(commitment)` at `evm/src/consensus/EcdsaBeefy.sol:152` performs `O(payloadLen²)` `bytes.concat` copies, causing gas consumption (and, at sufficiently large `payloadLen`, an out-of-block-gas revert) far exceeding the cost implied by the actual encoded payload size — confirming the same class of algorithmic-complexity DoS described in CVE-2026-33033, applied here to the on-chain BEEFY commitment encoder rather than Django's multipart base64 decoder.

    function Encode(Commitment memory commitment) internal pure returns (bytes memory) {
        uint256 payloadLen = commitment.payload.length;
        bytes memory payload = bytes("");
        for (uint256 i = 0; i < payloadLen; i++) {
            payload = bytes.concat(
                payload,
                abi.encodePacked(commitment.payload[i].id),
                ScaleCodec.encodeBytes(commitment.payload[i].data)
            );
        }

        return bytes.concat(
            ScaleCodec.encodeUintCompact(payloadLen),
            payload,
            ScaleCodec.encode32(commitment.blockNumber),
            ScaleCodec.encode64(commitment.validatorSetId)
        );
    }
