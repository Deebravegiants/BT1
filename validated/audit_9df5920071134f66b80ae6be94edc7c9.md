This is a genuine finding. `Webhooks::Request#to_signable_string` only returns `@raw_body`, so the HMAC signature verified by `Utils::HmacValidator.validate` covers only the JSON body — never the `x-shopify-shop-domain` header returned by `Request#shop`, which `Registry.process` passes straight to the handler as the tenant identifier.### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The shop domain is never part of the signed material, so a party who can obtain any one valid `(raw_body, hmac)` pair for the app (e.g. by installing the app on a shop they control and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The app will accept the payload as authentic and dispatch it to the handler under the attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cross-check against anything cryptographically bound to the request: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` field; it never incorporates `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity handed to the app's business logic: [4](#0-3) 

The identity binding broken here is: `shop authenticated (bound by HMAC) == shop acted upon (used to route/store data)`. In this gem, `request.shop` (acted upon) is disjoint from what the HMAC actually covers (`raw_body` only), so the equality does not hold. This is the same bug class as the report's H-10: a field that downstream logic treats as trusted/bound to the verified action (the LCG share-price/asset accounting) is not actually covered by the verification step (the HMAC/`transferFrom` success), leading the two ledgers (verified vs. acted-upon) to diverge.

Because the app's `client_secret` (and thus the webhook signing key) is shared across every shop on which the app is installed, a normal merchant/tenant (an "unprivileged" party relative to *other* tenants) who installs the app on their own store receives genuinely-signed `(raw_body, hmac)` pairs from Shopify. Nothing in this gem prevents that same valid pair from being replayed against the same public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop. `HmacValidator.validate` will still return `true` (the body and HMAC are untouched and genuinely matched), and `Registry.process` will call the handler with `shop: <victim-shop>` while the body content actually originated from the attacker's own shop.

### Impact Explanation
This yields cross-tenant confusion in a multi-tenant embedded app: the webhook handler is invoked believing the payload belongs to a different merchant's shop than it actually does. Depending on how the host application's `WebhookHandler` implementation uses `WebhookMetadata#shop` (e.g., to select which tenant's database record to update, to trigger tenant-scoped side effects, or to log/attribute an event), this can let one tenant inject or associate arbitrary attacker-controlled webhook data (of a topic/shape they can trigger on their own store) into another tenant's context — a cross-tenant access/confusion vulnerability rooted entirely in this gem's `Webhooks::Request`/`Registry` design, independent of how any specific host app implements its handler.

### Likelihood Explanation
Requires only: (1) ability to install the target app on a shop the attacker controls (a normal, low-privilege action for any Shopify merchant/developer, not a "privileged account" or leaked credential), and (2) network access to POST to the app's public webhook endpoint with custom headers — both are attacker-reachable without TLS interception, secrets, or social engineering. The attacker does not need `api_secret_key` itself, only a legitimately-issued `(body, hmac)` pair that Shopify computed for them.

### Recommendation
Bind the shop identity into the verified material. Options:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in `Request#to_signable_string`/the HMAC computation if Shopify's webhook signing scheme supports it, or
- At minimum, cross-validate `request.shop` against an independently trusted source (e.g., require the caller to look up and confirm the shop has an active session/registration for the given `webhook_id`/topic before dispatch), so that a body signed for shop A cannot be attributed to shop B purely via a header value.
- Document/enforce that consumers of `WebhookMetadata#shop` must not treat it as cryptographically authenticated unless the gem itself binds it to the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Attacker triggers a webhook topic they control (e.g., updates a product) causing Shopify to POST to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` (e.g., via their own reverse proxy/logging in front of the endpoint they control, or by having the app's webhook path world-observable to them in their own infra) and immediately re-POSTs the identical body `B` and header `x-shopify-hmac-sha256: H` to the same app webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true`: [5](#0-4) 
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` even though the payload content originated from `attacker-shop`: [6](#0-5)
