### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` value that identifies which tenant the webhook belongs to is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed payload. Any party capable of producing one genuinely-signed webhook (e.g., a merchant who has installed the app themselves) can therefore replay that same body/HMAC pair while swapping the `shop-domain` header to point at a different shop, and the app built on this gem will process it as an authenticated event for the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

Meanwhile, the `shop` accessor used to attribute the webhook to a tenant is pulled straight from an unauthenticated header: [3](#0-2) 

`Registry.process` validates only the HMAC and then hands `request.shop` directly to the application's handler with no cross-check against any signed field: [4](#0-3) 

This breaks the identity binding `signed_content == content_acted_on`: the HMAC only proves the *body* came from someone holding the shared `api_secret_key`, but the *shop* field that consuming applications use as the tenant/session key is never part of that proof. Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app (a legitimate, unprivileged user of the app, not requiring the app's secret) will naturally receive genuinely-HMAC-signed webhooks for their own shop's events. That merchant can capture one such request and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain — the HMAC still validates because it only covers the body, and `WebhookMetadata.new(shop: request.shop, ...)` reports the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker can cause an application built on this gem to process attacker-controlled webhook data as if it belonged to a different merchant's shop. Depending on how the host application keys its data/session lookups off `WebhookMetadata#shop` (a pattern this gem's own webhook API encourages, since `shop` is the only tenant identifier exposed alongside the parsed body), this enables cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control — matching the "Critical: cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own store (a normal, unprivileged path — no `api_secret_key`, access token, or leaked credentials required). Triggering an event in their own shop yields a validly-HMAC-signed body; replaying it with a modified `shop-domain` header is trivial since that header is not covered by the signature at all.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the HMAC-signed content, or otherwise cryptographically tie the shop header to the signed payload before `Registry.process` passes it to handlers. At minimum, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop-domain header (mirroring Shopify's actual webhook HMAC scheme, which signs the full raw body per delivery but relies on TLS + shop-scoped webhook endpoints/secrets in some configurations) — and the library should document/enforce that consuming apps cannot trust `WebhookMetadata#shop` as an authenticated tenant identifier unless corroborated by an out-of-band verified mapping (e.g., comparing against the shop tied to the webhook subscription actually registered, or requiring per-shop webhook secrets).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, giving them a legitimate valid `api_secret_key`-signed webhook delivery, e.g. for `orders/create`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - Body: `{"id": 1, ...}`
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but changes only:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`; validation succeeds because the HMAC only covers `@raw_body`, unaffected by the header change: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, and any app logic keyed on `shop` (e.g., "look up victim's records and apply this order data") now operates against the victim tenant using attacker-supplied content.
