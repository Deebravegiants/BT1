### Title
Missing market-value bound lets accrual overflow and permanently freeze a lending market - (File: `common/src/rates/simulate.rs`)

### Summary
A market whose scaled borrow book can grow beyond the `i128` RAY-value domain will hit `MathOverflow` during index accrual before the borrow-index ceiling is reached. [1](#0-0)   
Because every pool operation syncs the market first, the failed accrual blocks repayment, withdrawal, liquidation, and later index updates. [2](#0-1)   
This is a permanent-freezing-of-funds analog: new exposure is capped by indexes and share limits, but the protocol does not ensure that `scaled_amount * index` remains representable as the market accrues. [3](#0-2) 

### Finding Description
`accrue_step` converts the scaled borrow and supply books to original RAY value using `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [4](#0-3)   
It then compounds the borrow index and calculates rewards as `borrowed * new_borrow_index - borrowed * old_borrow_index`, so a sufficiently large scaled book can overflow before `MAX_BORROW_INDEX_RAY` is reached. [3](#0-2)   
Although `update_borrow_index` caps the index itself at `MAX_BORROW_INDEX_RAY`, that cap does not bound the separately computed market value, which is where the arithmetic failure occurs. [5](#0-4)   
Supply-side accrual has the same shape because `update_supply_index` multiplies `supplied` by `old_index` before adding rewards. [6](#0-5) 

The permissionless controller endpoint `update_indexes(caller, assets)` requires only caller authorization and forwards the request to the pool. [7](#0-6) [8](#0-7)   
Once the pool enters the failing state, `global_sync` aborts before `mark_accrued`, so every subsequent call retries the same overflowing accrual. [9](#0-8) 

### Impact Explanation
All suppliers’ principal and all borrowers’ collateral can become permanently frozen in the affected market. [2](#0-1)   
Withdrawals call `load_leg`, which invokes `synced_market` and therefore runs `global_sync` before burning supply or paying out cash. [10](#0-9)   
Repayments likewise call `load_leg` and accrue before debt shares can be burned or cash credited. [11](#0-10)   
The repository’s own regression test demonstrates that, after the cliff, both `withdraw` and `repay` fail with `MathOverflow`, while the borrow index remains below its configured cap. [12](#0-11) 

### Likelihood Explanation
Triggering the condition requires an unusually large market and sustained high utilization rather than ordinary deposits. [13](#0-12)   
The demonstrated setup uses one billion 18-decimal tokens of supply and a 98% borrow, then advances time until the RAY-valued book crosses the `i128` boundary. [14](#0-13)   
No privileged role is needed at the trigger point because any authenticated caller can invoke `update_indexes`, and the same overflow is reachable organically through any later user operation. [7](#0-6)   
The capital and time requirements lower the practical likelihood, but the resulting market-wide and irreversible freeze supports at least Medium severity. [15](#0-14) 

### Recommendation
Before minting supply, debt, or protocol-revenue shares, enforce a domain bound based on the worst-case index rather than only checking the share amount itself. [16](#0-15)   
For example, reject entries that would make `scaled * MAX_BORROW_INDEX_RAY / RAY` or `scaled * MAX_SUPPLY_INDEX_RAY / RAY` exceed `i128::MAX`, and apply equivalent checked-value handling inside `accrue_step`. [17](#0-16)   
If accrual can no longer be represented, fail entry accruals predictably with a dedicated error and provide a governor-controlled rescue/recapitalization path that does not depend on the overflowing accrual. [9](#0-8) 

### Proof of Concept
The existing integration test reproduces the failure end to end: it configures an 18-decimal market, supplies `1_000_000_000 * 10^18` base units, supplies collateral, and borrows 98% of the market. [13](#0-12)   
It then advances ledger time in yearly steps and calls the permissionless index-update path until `update_indexes` returns `MathOverflow`. [18](#0-17)   
The assertion confirms that the stored borrow index is still below `MAX_BORROW_INDEX_RAY`, proving that the configured index ceiling did not prevent the value-domain overflow. [19](#0-18)   
Finally, attempts to withdraw one unit and repay the debt both fail with the same `MathOverflow`, demonstrating permanent market lockup. [20](#0-19)

pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);

    let new_supply_index = update_supply_index(env, supplied, supply_index, supplier_rewards);
    let supplier_shortfall = supply_index_reward_shortfall(
        env,
        supplied,
        supply_index,
        new_supply_index,
        supplier_rewards,
    );

    let protocol_reward = protocol_fee.checked_add(env, supplier_shortfall);
    // Shares are valued at the new supply index, which the caller stores for
    // this step.
    let revenue_shares = if protocol_reward == Ray::ZERO {
        Ray::ZERO
    } else {
        protocol_fee_shares(env, protocol_reward, new_supply_index, supplied)
    };

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Accrues interest, resolves the repay amount into burned debt shares and
/// overpayment, burns the shares, and credits the net repay to cash without
/// transferring the overpayment refund. Panics if a positive net repay would
/// burn zero scaled shares.
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);

    let snapshot = cache.commit();

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
