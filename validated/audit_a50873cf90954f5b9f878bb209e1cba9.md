### Title
`Auth::Oauth.begin_auth` builds the OAuth authorization redirect from an unvalidated `shop` parameter, unlike every other credential-issuing flow in the gem - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` uses the caller-supplied `shop:` argument directly to construct `auth_base_uri(shop)`, which becomes the host the merchant's browser is redirected to (`https://#{shop}/admin/oauth/authorize`), along with `client_id`, `scope`, `redirect_uri` and the anti-CSRF `state` nonce. Every other credential-issuing entry point in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token` via the JWT `dest` claim) runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build a request host. `begin_auth` does not.

### Finding Description
The bug-class analogy: the external report shows two computations (`totalTokensForCreators`, `totalTokensForBuyers`) that are supposed to be bound to the same authoritative state (`emittedTokenWad`) but are instead computed independently, breaking the intended invariant. The equivalent binding here is: **the host that receives the OAuth authorization request must equal a value validated as a genuine Shopify domain**, i.e. `redirect_host == ShopValidator.sanitize!(shop)`.

- `Auth::Oauth.begin_auth(shop:, redirect_path:, ...)` at [1](#0-0)  takes `shop` straight from the caller (typically an unauthenticated request parameter in the host app's login route, as documented) and passes it unsanitized into `auth_base_uri(shop)`: [2](#0-1) 
  This builds `"https://#{shop}/admin"` and the resulting `auth_route` embeds `client_id`, `scope`, `redirect_uri`, and `state` as query parameters targeted at that host.
- Compare this to the sibling flows, both of which call `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build a request session/host: [3](#0-2) [4](#0-3) 
- `Utils::ShopValidator.sanitize!` exists specifically to enforce that a shop value is a trusted `*.myshopify.com`/`*.myshopify.io`/etc. domain before it is used to build a URL that will receive sensitive parameters: [5](#0-4) [6](#0-5) 
- `validate_auth_callback` does separately re-verify the returned `shop` via HMAC on the callback (`Utils::HmacValidator.validate(auth_query)` at [7](#0-6) ), so the callback stage cannot be spoofed. The gap is specifically in `begin_auth`, the redirect-generation stage, which happens before any HMAC exists to check.

### Impact Explanation
Because `begin_auth` never checks that `shop` is a trusted Shopify domain, an unprivileged internet user who controls the value passed as `shop` (e.g. by supplying an arbitrary `shop` query-string/header value to the host application's login route, exactly the pattern shown in this gem's own `docs/usage/oauth.md` example `shop = request.headers["Shop"]`) can force `begin_auth` to produce an `auth_route` pointing at an attacker-controlled host instead of `*.myshopify.com`. The victim's browser is then redirected (with the app's `client_id`, requested `scope`, the app's real `redirect_uri`, and the freshly minted anti-CSRF `state` nonce) to that attacker host. This matches the report's "forced OAuth completion" impact category: the attacker can host a page at that domain that immediately 302s the browser onward with attacker-chosen `code`/`state` values back to the app's own callback endpoint, since the CSRF nonce cookie was already set by the legitimate app for that browser session and the app has no way, at `begin_auth` time, to detect that the "shop" it redirected to was never a real Shopify domain. This can be leveraged to attempt to complete an OAuth grant against a shop the attacker chooses, or to phish the merchant with a spoofed authorize screen at a domain the app itself generated and vouched for in its redirect.

### Likelihood Explanation
`shop` is, by this gem's own documented usage pattern, taken from an unauthenticated inbound request value at the very start of the OAuth flow (before any Shopify-issued credential exists to validate it), so the attacker fully controls this input with no privileges required. The missing check is a simple oversight relative to the parallel, already-present `ShopValidator.sanitize!` calls in `client_credentials.rb` and `refresh_token.rb`, making this a straightforward, reliably reachable path.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain` and raise on `nil`) at the top of `Auth::Oauth.begin_auth`, and use the sanitized value both when building `auth_base_uri` and anywhere else `shop` is echoed into the redirect, mirroring the existing pattern used by `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
```ruby
# Host app login route (per this gem's docs/usage/oauth.md):
#   shop = request.headers["Shop"]
#   ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")

ShopifyAPI::Context.setup(api_key: "APP_KEY", api_secret_key: "APP_SECRET",
  host: "myapp.example.com", scope: "read_products", is_embedded: false, ...)

result = ShopifyAPI::Auth::Oauth.begin_auth(
  shop: "attacker.example",       # not a myshopify.com domain, never validated
  redirect_path: "/auth/callback",
)

result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=APP_KEY&scope=read_products
#     &redirect_uri=https%3A%2F%2Fmyapp.example.com%2Fauth%2Fcallback&state=<nonce>&grant_options%5B%5D="
```
The victim's browser is redirected to `attacker.example` with the app's `client_id`, real callback URL, and CSRF `state` cookie value already set — none of which is caught because `begin_auth` never runs `shop` through `Utils::ShopValidator`, unlike `ClientCredentials.client_credentials`/`RefreshToken.refresh_access_token`, which reject `"attacker.example"` per `test/auth/client_credentials_test.rb` (`test_client_credentials_rejects_non_shopify_domain`) and the analogous `ShopValidator` test suite.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
