### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator.validate` checks is computed only over the raw request body. Because the shop identifier is never part of the signed material, `ShopifyAPI::Webhooks::Registry.process` accepts any `shop` value paired with a correctly-signed body, breaking the binding between "HMAC-verified" and "tenant asserted."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which calls `request.to_signable_string`, i.e. the body only) and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC only over `verifiable_query.to_signable_string`: [4](#0-3) 

Equality that should hold: `shop_bound_by_hmac == shop_delivered_to_handler`. In reality: `shop_bound_by_hmac` doesn't exist at all — the HMAC only covers `raw_body`. The `shop` field consumed by `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` is entirely outside the signed scope, so any (body, hmac) pair that verifies for shop A also verifies for any attacker-chosen shop-domain header value B.

### Impact Explanation
A caller who possesses one valid `(raw_body, hmac)` pair — e.g. by having their own shop legitimately receive a webhook from Shopify for that body, or by encountering any leaked/observable webhook payload — can resubmit that exact body and HMAC to the app's webhook endpoint while substituting a different `shop-domain` header. `Registry.process` will pass HMAC validation and dispatch the handler with `data.shop` set to the attacker-chosen shop, even though the signature was never computed for that shop. Any host application that uses `data.shop` to select which merchant's records to update (the documented, expected usage per `docs/usage/webhooks.md`) can be made to apply another tenant's webhook payload to a different tenant — a cross-tenant integrity/confusion issue reachable without the `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of one legitimate `(body, hmac)` pair (trivially obtainable by an attacker who installs the app on their own store, a normal unprivileged action). No secrets, tokens, or elevated access are required to perform the header substitution itself, since the header is never included in the HMAC's signable string.

### Recommendation
Bind `shop` (and other headers/metadata the handler relies on) into the signed material used for verification — e.g. require the caller to supply the shop domain and validate it against an independently known active webhook registration/session for that topic, rather than trusting a raw header once only the body's HMAC has been checked. At minimum, document/verify at the `Registry.process` layer that `request.shop` corresponds to a shop with an active, expected subscription for `request.topic` before dispatching to the handler.

### Proof of Concept
```ruby
body = "{}"
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Legitimate delivery for "shop-a.myshopify.com"
headers_a = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-a.myshopify.com",
}
req_a = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_a)
ShopifyAPI::Utils::HmacValidator.validate(req_a) # => true

# Same body + same hmac, attacker swaps the shop-domain header
headers_b = headers_a.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
req_b = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_b)
ShopifyAPI::Utils::HmacValidator.validate(req_b) # => true, still passes

ShopifyAPI::Webhooks::Registry.process(req_b)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
# even though the HMAC was never computed with victim-shop's identity in scope
```
