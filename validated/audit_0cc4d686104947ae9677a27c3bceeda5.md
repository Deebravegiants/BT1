### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute (and `topic`, `api_version`, `webhook_id`) from raw HTTP headers, but the HMAC signature computed by `Utils::HmacValidator` only signs the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity for dispatching to the app's handler, without that value ever being part of the signed material.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` for a webhook request returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed string: [2](#0-1) 

`Registry.process` only checks that the HMAC over the body is valid, and then dispatches the shop taken from the (unsigned) header straight to the app's handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, body)` and compares it to the `hmac-sha256` header — it never incorporates `shop`, `topic`, or `webhook-id`: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used to select/attribute the tenant` == `shop bound inside the HMAC-signed payload`

but the code enforces only:
`HMAC(secret, raw_body) == received_hmac`

with `shop` left completely outside that equality. Because `api_secret_key` is a single app-level secret shared across every shop that installs the app (not a per-shop secret), any merchant who legitimately installs the app receives genuine, validly-signed webhooks for their own store. Such a merchant (an "unprivileged internet user" with respect to any other tenant) can capture one of these valid `(raw_body, hmac-sha256)` pairs and POST it directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds — it only checks the body — so `Registry.process` will call the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled or replayed body>, ...)`, exactly as documented for consumers: [5](#0-4) [6](#0-5) 

This is the same class of bug as the referenced report: a field that is acted upon (here, the tenant-identifying `shop`) is never covered by the integrity check (here, the HMAC), so the enforced equality silently diverges from the equality the application logic actually depends on.

### Impact Explanation
Any host application that follows this gem's documented contract — trusting `data.shop` from `WebhookMetadata` as the authenticated tenant for a webhook, as the docs explicitly instruct — will misattribute a validly-signed webhook to an arbitrary, attacker-chosen shop. This is a cross-tenant data-integrity violation: an attacker-controlled webhook body (replayed from their own shop, or any topic the attacker can trigger, e.g. `products/update`, `orders/create`, `app/uninstalled`) can be injected into another merchant's data pipeline under that merchant's identity, since the gem provides no mechanism to bind `shop` to the signed content. This satisfies the High-impact bar of a cross-tenant boundary crossing achieved purely through this gem's own verification logic, without needing the app's `client_secret`/`api_secret_key`, TLS interception, or any privileged account beyond a normal, unprivileged merchant installation.

### Likelihood Explanation
Likelihood is High: the only capability an attacker needs is to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action available to any Shopify merchant/developer — receive one legitimate webhook, and replay the exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, brute-forcing, or race condition is required; the gem's own `Registry.process` unconditionally accepts the header-derived `shop` once the body-only HMAC check passes.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`/`api_version`) into the value that is cryptographically verified before it is trusted, e.g. by including these header values in `to_signable_string`, or by requiring the host application to independently correlate `request.shop` against a shop the app has separately verified owns the delivered `webhook_id`/subscription. At minimum, document clearly that `shop` in `WebhookMetadata` is not itself authenticated by the HMAC and must not be used as a sole tenant-authorization signal.

### Proof of Concept
1. App developer/attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures one delivered webhook's raw body `B` and its valid `X-Shopify-Hmac-Sha256: H` header (`H = Base64(HMAC-SHA256(api_secret_key, B))`).
3. Attacker sends a POST directly to the app's public webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged/valid), but `X-Shopify-Shop-Domain: victim.myshopify.com` and any desired `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` succeeds because it only recomputes the HMAC over `B`: [7](#0-6) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on `victim.myshopify.com`'s behalf using attacker-supplied data: [3](#0-2)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
