This codebase has extensive length/size guards on most attacker-reachable paths (e.g. `MAX_PROOF_DEPTH` in Pharos SPV, `MAX_VALIDATORS` in Pharos verifier, `BoundedVec<u8, MaxProofSize>` in `pallet-beefy-consensus-proofs`, and a `MaxCallSize` guard in `pallet-call-decompressor`). However, one directly analogous and reachable gap exists in `pallet-ismp`'s free/unsigned message-execution path.

### Title
Unbounded-size free `handle_unsigned` ISMP message batch enables mempool-validation Denial of Service - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Pallet::handle_unsigned` accepts an unbounded `Vec<Message>` and is dispatched as a fee-less unsigned extrinsic. Its `ValidateUnsigned::validate_unsigned` implementation fully executes the batch (`Self::execute(messages.clone())`, including consensus/state-proof verification) on every node that receives the transaction over gossip, before any fee or proportional weight is charged. Because neither the call, the `Vec<Message>`, nor its nested collections (`RequestMessage.requests`, `ConsensusMessage.consensus_proof`, MMR/authority proofs, etc.) carry a length bound, and the declared extrinsic weight is a fixed constant regardless of batch size, an attacker can submit arbitrarily large/expensive message batches for free and force every full node to redo expensive cryptographic verification (BLS/ECDSA aggregate checks, MMR/SSZ/merkle-trie proof walks) purely to reject or accept the transaction into the pool.

### Finding Description
`handle_unsigned` is declared with a fixed nominal weight independent of its input size: [1](#0-0) 

and [2](#0-1) 

The pallet's `ValidateUnsigned::validate_unsigned` — which fires on every node that gossips or receives the transaction, not just the block author — decodes and *fully executes* the entire batch, including all state-machine membership/consensus proof verification, before any weight/fee accounting has occurred: [3](#0-2) 

`Self::execute` iterates every message in the batch and calls the full ISMP handler pipeline (proof verification, dispatch) for each: [4](#0-3) 

Nothing bounds the number of `Message`s in the call, nor the size of nested structures such as `RequestMessage.requests` (a plain `Vec<PostRequest>`), `ConsensusMessage.consensus_proof` (a plain `Vec<u8>` that may encode e.g. a BEEFY `MmrProof` with an attacker-chosen number of `SignatureWithAuthorityIndex` entries), or proof byte blobs. This project already recognizes this exact bug class and guards against it elsewhere:
- `pallet-beefy-consensus-proofs` bounds its proof submission to `BoundedVec<u8, MaxProofSize>`, rejecting oversized proofs at the transaction-pool decode stage: [5](#0-4) 
- `pallet-call-decompressor` explicitly bounds `encoded_call_size` against `MaxCallSize` at the single choke point reachable from the unsigned mempool path, with an inline comment describing precisely this class of attack ("a fee-less attacker could claim `encoded_call_size = u32::MAX`... before any size check"): [6](#0-5) 

`pallet-ismp`'s `handle_unsigned`/`validate_unsigned` has no equivalent gate on `messages: Vec<Message>` size or on the aggregate proof/request-batch sizes it contains, despite doing strictly more expensive work per byte (full ISMP message dispatch and consensus verification) than the call-decompressor's decompression step.

### Impact Explanation
This is the free/unsigned/unprivileged entry point ("This allows users execute ISMP datagrams for free. Use with caution.") explicitly reachable by any relayer or unprivileged party, matching the allowed-analog class "pallet-ismp handle_unsigned". Because `validate_unsigned` re-executes the full batch on every full node during gossip propagation — at zero cost to the submitter and with a declared weight that does not scale with the actual work performed — an attacker can craft a single large `Vec<Message>` (e.g., many `PostRequest`s, or a consensus message carrying a maximal authority-set signature/proof) that is computationally expensive to verify (signature recovery, merkle/MMR/SSZ proof walking) but cheap to construct and submit repeatedly. This can degrade or stall block-production/transaction-pool validation network-wide — a Denial of Service on the node/relayer layer, directly analogous to the Shopware unbounded-length-input DoS.

### Likelihood Explanation
High: the extrinsic is explicitly unsigned/permissionless and free by design, requiring no stake, fee, or prior state. No length cap exists on the batch or its nested collections at the pallet level; only generic node-level extrinsic/block-length limits apply, which are far larger than what's needed to make verification expensive (e.g., large signature counts or deep multi-proofs).

### Recommendation
Bound `handle_unsigned`'s `messages: Vec<Message>` (and/or the nested `Vec<PostRequest>`/proof byte lengths it can carry) with an explicit `BoundedVec`/max-count and max-byte-size check performed inside `validate_unsigned` *before* `Self::execute` is invoked — mirroring the pattern already used in `pallet-beefy-consensus-proofs` (`BoundedVec<u8, MaxProofSize>`) and `pallet-call-decompressor` (`MaxCallSize` check up front). Additionally, consider deriving the declared extrinsic weight from the actual batch/proof size rather than a fixed constant, so oversized batches are naturally weight-limited rather than silently under-charged.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` extrinsic whose `messages: Vec<Message>` contains a single `Message::Consensus(ConsensusMessage { consensus_proof, .. })` where `consensus_proof` SCALE-encodes a `MmrProof`/`BeefyConsensusProof`-like structure with a very large `signatures`/`votes` vector (or a `Message::Request(RequestMessage { requests, .. })` with a very large `Vec<PostRequest>`).
2. Submit this as an unsigned transaction to any node's RPC/gossip endpoint, at zero cost (unsigned, no fee).
3. Observe that every peer node that receives the transaction invokes `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` and performs full signature/proof verification for the oversized batch before deciding whether to admit it to the pool — regardless of whether the batch is ultimately valid.
4. Repeat/flood with many such transactions (cheap to generate, free to submit) to consume CPU across the network's nodes during mempool validation, causing a Denial of Service.
