Based on my research, the closest custody-grade analog to the "ticking interest → threshold crossing → bypassed protection" bug class in this codebase is in the Aptos `multisig_account` timelock mechanism, where the elapsed-time computation is anchored to a stale `creation_time_secs` value that predates a newly-installed protective timelock, letting the timelock be nullified for transactions that were already pending before it was activated.

### Title
Multisig Timelock Protection Bypass via Stale `creation_time_secs` Anchoring — Newly-Installed Timelocks Provide No Delay for Pre-Existing Pending Transactions - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account`'s optional `MultisigAccountTimeLock` is meant to give owners of a multisig-controlled treasury a mandatory delay window between reaching quorum and executing a transaction, so that a compromised/coerced-signer scenario can be detected and mitigated (e.g., by removing the bad owner) before funds move. The delay is computed as `now_seconds() - pending_transaction.creation_time_secs >= timelock_period` in `can_execute_with_timelock`. Because `creation_time_secs` is fixed at the moment the transaction was originally proposed — not from when the timelock was actually activated — any transaction that was already sitting in the queue before a timelock is installed (or before its period is increased) inherits time that already elapsed prior to the protection existing. This directly mirrors the reported bug class: a naturally "ticking" state value (elapsed time, analogous to accruing interest) can already be past a newly-set threshold the instant the protective control is activated, defeating the very custody safeguard the control was meant to provide.

### Finding Description

`upsert_timelock_internal` allows any owner-approved multisig self-transaction to install or change `MultisigAccountTimeLock.timelock_period`/`override_threshold` at any time, without touching or resetting `creation_time_secs` of already-queued `MultisigTransaction` entries: [2](#0-1) 

The `MultisigTransaction` struct fixes `creation_time_secs` once, at proposal time, regardless of what timelock configuration exists later: [3](#0-2) 

The maintainers' own doc comment on `upsert_timelock` explicitly acknowledges this behavior: [4](#0-3) 

Custody invariant broken: "a multisig-controlled asset protected by a k-of-n + timelock policy cannot be moved sooner than `timelock_period` seconds after the delay control is active for a given pending transaction." Because `elapsed` is measured from the original proposal time rather than `max(creation_time_secs, timelock_activation_time)`, a transaction that already has (or later gains) quorum can become immediately executable the moment a *new or strengthened* timelock is installed, if enough wall-clock time already passed since it was first proposed — even though from the perspective of the timelock's existence, zero seconds of delay have actually been enforced.

### Impact Explanation
Impact is High for any treasury, DAO, or code-object/resource-account controlled by a `multisig_account` that relies on a timelock as an incident-response safety net (the documented design intent: buy owners time to detect and remove a compromised signer before a quorum-approved transfer executes). If:
1. A malicious or compromised owner proposes a draining transaction (e.g., `coin::transfer`/`object::transfer`/FA withdraw of resource-account-held assets) and it sits in the queue accumulating age (naturally, or deliberately delayed by the attacker), and
2. Honest owners, upon detecting suspicious activity, reactively install a timelock (or raise `timelock_period`) as a defensive measure once quorum is close to being reached,

then the already-elapsed age of the pending transaction is credited toward the new timelock, potentially satisfying `elapsed >= timelock_period` immediately, allowing the attacker to execute and move custody-held value (APT, FAs, or code-object-controlled resources) out of the account before the intended delay has actually run — silently defeating the protective control at the exact moment it is needed. This corrupts the "recoverable window" invariant asset custodians are relying on.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a multisig configured to add/adjust a timelock reactively rather than proactively at account creation, and (b) a pending transaction that predates that timelock change by at least `timelock_period` seconds. Both conditions are realistic in a real incident-response scenario (the whole point of a "break glass, tighten timelock now" reaction), and no special privilege beyond normal owner voting rights is required to trigger the bypass — it is a property of the passage of time relative to when the control was installed, not an exploit requiring extra approvals beyond what quorum already grants.

### Recommendation
Anchor the elapsed-time computation to `max(pending_transaction.creation_time_secs, timelock_activation_time)` by recording a `activated_at_secs` (or per-transaction `timelock_baseline_secs`) field in `MultisigAccountTimeLock`/`MultisigTransaction`, and using that as the origin for the `elapsed >= timelock_period` check in `can_execute_with_timelock`. Alternatively, on `upsert_timelock_internal`, snapshot `now_seconds()` and require `elapsed_since_upsert >= timelock_period` for any pending transaction that existed before the call, rather than crediting pre-existing elapsed time toward a freshly (re-)installed control.

### Proof of Concept
1. Create a multisig account with 2-of-3 owners and no timelock: `create_with_owners(...)`.
2. Owner A proposes a draining transaction (`create_transaction`) at `t0`; it accumulates 1 approval automatically.
3. Wait 14 days of real time (or simulate `timestamp` advancement in a Move unit test) without a second approval yet.
4. Owners notice suspicious activity and, as a safety measure, execute `upsert_timelock(multisig_account, MAX_TIMELOCK_PERIOD /* 14 days */, none)` via a fast-tracked multisig transaction (self-call).
5. Immediately after, Owner B (compromised or colluding) approves the original draining transaction, reaching quorum.
6. Call `can_execute`/execute the draining transaction: `elapsed = now_seconds() - t0 >= 14 days` is already true (because 14 days passed at step 3, before the timelock even existed), so `can_execute_with_timelock` returns `true` and the transaction executes with zero seconds of actual delay under the newly-installed timelock, moving multisig-held assets out before the intended protection window elapses.     inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
            });
        }

        emit(TimelockUpdated {
            multisig_account: multisig_address,
            timelock_period,
            override_threshold,
        });
    }
