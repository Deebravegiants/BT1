### Title
Webhook shop/topic identity not covered by HMAC, enabling cross-tenant replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — used by `Registry.process` to select the handler and to identify the tenant the event belongs to — are read verbatim from HTTP headers that are never included in the signed material. This is the same class of defect as the reported "predictable price hash" issue: an identity-relevant field (shop/topic) is not bound into the cryptographic check that is supposed to guarantee its authenticity, so the value can be swapped by a replaying/adjacent party without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), via `OpenSSL.secure_compare`: [3](#0-2)  It never inspects or binds `shop`, `topic`, or `webhook_id`.

`Registry.process` then trusts the header-derived `shop`/`topic` once the (body-only) HMAC passes, and hands them to the app's handler as the tenant identity: [4](#0-3) 

The equality this breaks is: *`shop` authenticated by the HMAC* should equal *`shop` acted upon by the handler*. In this implementation, `hmac == HMAC(secret, raw_body)` says nothing about `shop`; the code implicitly assumes `hmac_valid? ⇒ shop_header_is_authentic`, but the two are decoupled. Any request whose body byte-for-byte matches a body that once produced a valid signature (e.g., a genuinely-received webhook for the attacker's own store, replayed with a different `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header) will pass `HmacValidator.validate` and be dispatched to the handler with attacker-chosen `shop`/`topic` metadata.

### Impact Explanation
This crosses a tenant boundary: it allows cross-tenant identity spoofing at the point the app's webhook handler decides *which shop's* data to update/delete/fulfill based on `WebhookMetadata#shop`. Any app whose handler logic branches, loads, or persists data keyed by `data.shop` (which the docs and `WebhookMetadata` explicitly expose for that purpose) can be made to act on behalf of, or against, a different shop than the one that actually produced the signed payload — despite the HMAC check passing. This matches the "cross-tenant access" Critical impact category, since the HMAC is the sole authenticity guarantee the gem provides for webhook processing.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately received (or to control) at least one valid `(body, hmac)` pair — trivially available to any merchant/developer who has installed the app on their own store and received one real webhook, since the body content for many topics is attacker-influenced (e.g., product/order fields they control) or predictable/reusable across shops (e.g., `shop/redact`, empty-body test payloads, or webhooks whose JSON body doesn't itself embed the shop domain). No access to `api_secret_key` or the app's access token is needed — only replay of an already-signed request with modified headers, which the gem does nothing to prevent because headers are outside the signed scope by design of the current `to_signable_string` implementation.

### Recommendation
Bind the tenant/topic identity into the value verified by `HmacValidator`, not just into fields trusted after the check. Options:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for verification (this deviates from Shopify's wire format, so instead cross-check the header-provided `shop` against an independently trusted source, e.g., require the caller to pass an expected shop/session and assert `request.shop == expected_shop` before invoking the handler).
- At minimum, document and enforce that consumers of `WebhookMetadata#shop` must never treat it as authenticated on its own, and add a `Registry.process` parameter that restricts processing to a known/expected shop for that request context.

### Proof of Concept
1. Install the app on `attacker.myshopify.com` and configure a webhook topic (e.g., `orders/create` with a body the attacker controls, such as a specifically crafted order note or empty test body `{}`).
2. Capture the resulting legitimate request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)` — valid per `compute_signature`: [5](#0-4) 
3. Replay the exact same `(B, H)` pair to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `HmacValidator.validate` succeeds because it only checks `H` against `B`, which are unchanged; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches to the handler with `shop: "victim.myshopify.com"`, even though `victim.myshopify.com` never sent this webhook.
