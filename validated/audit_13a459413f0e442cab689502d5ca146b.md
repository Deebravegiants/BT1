## Analog Found

### Title
Unbounded VLA-style memory allocation from unauthenticated header bytes decoded before merkle-proof verification - (File: evm/src/consensus/Codec.sol / evm/src/consensus/EcdsaBeefy.sol)

### Summary
CVE-2021-3527 is a QEMU bug where an unbounded, attacker-influenced length field is used to size a variable-length stack allocation before the corresponding data is validated, letting a malicious peer force an oversized allocation and crash the process. The same "size-from-untrusted-input, allocate-before-validate" pattern exists in Hyperbridge's ECDSA BEEFY consensus client: `Codec.DecodeHeader` reads a SCALE compact-encoded digest count directly from caller-supplied bytes and immediately allocates a memory array of that size — and this decode runs on parachain header bytes that have not yet been authenticated against the BEEFY-signed MMR root.

### Finding Description
`EcdsaBeefy.verifyParachainHeaderProof` iterates over attacker-supplied `proof.parachains[i].header` and calls `Codec.DecodeHeader(para.header)` for every entry *before* the batch's merkle multi-proof against `headsRoot` is checked: [1](#0-0) 

Only after this per-header decode loop completes does the code verify `MerkleMultiProof.VerifyProof(headsRoot, proof.proof, leaves, proof.leafCount)`, meaning each `para.header` is fully attacker-controlled, unauthenticated bytes at decode time.

Inside `Codec.DecodeHeader`, the digest count is read as an unbounded SCALE compact integer and used directly to size a dynamic memory array with no upper-bound check: [2](#0-1) 

`ScaleCodec.decodeUintCompact` supports the "mode 3" encoding, which decodes up to an 8-byte (near `uint64::MAX`) value: [3](#0-2) 

There is no maximum-digest-count guard anywhere between reading this length and calling `new Digest[](length)`, unlike other proof-depth/length guards found elsewhere in the codebase (e.g., `MAX_PROOF_DEPTH` in the Pharos SPV verifier, `MAX_VALIDATORS` in the Pharos state-proof verifier, and the `CallSizeOutOfBound` gate in `pallet-call-decompressor`), all of which explicitly bound untrusted lengths before doing work proportional to them.

### Impact Explanation
Any unprivileged relayer calling the EVM host's `handleConsensus`/`verify()` entry point for the ECDSA BEEFY light client can submit a `ParachainProof` containing one crafted `Parachain.header` whose SCALE digest-count field is set to a very large value. `Codec.DecodeHeader` will attempt `new Digest[](length)` for that huge length, triggering Solidity's quadratic memory-expansion gas cost and reverting the entire `verify()` call with out-of-gas — before the honest signature/merkle checks that would otherwise reject the header ever run. Because a single malicious header aborts the whole batched call, this can be used to reliably block delivery of legitimate, batched consensus updates and the ISMP messages bundled with them (per `generate_batched_contract_calls`/`batchCall`) on the ECDSA-BEEFY-secured route, i.e., a route rendered unable to deliver messages, at negligible cost to the attacker (crafting the header requires no valid signatures).

### Likelihood Explanation
High: constructing the malicious `ParachainProof.parachains[i].header` requires no cryptographic material — it's plain bytes with a manipulated SCALE compact length prefix — and the call path (`verify` → `verifyParachainHeaderProof` → `Codec.DecodeHeader`) is reachable by any address able to submit a consensus/message batch to the EVM host using the ECDSA BEEFY consensus client.

### Recommendation
Enforce an explicit maximum digest count (and/or maximum header length) before allocating `Digest[]` in `Codec.DecodeHeader`, and/or reorder `verifyParachainHeaderProof` so the merkle multi-proof against `headsRoot` is verified before any per-header decoding occurs, ensuring only already-authenticated header bytes are parsed.

### Proof of Concept
1. Construct a `ParachainProof` with one `Parachain` entry whose `header` bytes are: 32-byte parent hash + SCALE-compact block number + 32-byte state root + 32-byte extrinsics root + a SCALE compact-encoded digest-count using the "mode 3" prefix decoding to a very large value (e.g., close to `uint64::MAX`), with no actual digest data following.
2. Submit this `ParachainProof` alongside a `RelayChainProof` (real or dummy, since the depth-count DoS happens before/independent of any signature-supermajority failure ordering as long as `verifyMmrUpdateProof` doesn't itself revert first) to `EcdsaBeefy.verify` via `HandlerV2.handleConsensus`.
3. Execution enters `verifyParachainHeaderProof`, calls `Codec.DecodeHeader(para.header)`, which executes `Digest[] memory digests = new Digest[](length)` with the attacker-chosen huge `length`, causing the transaction to run out of gas and revert before `MerkleMultiProof.VerifyProof` is ever reached — demonstrating that fully unauthenticated header content controls a large, unbounded memory allocation.
