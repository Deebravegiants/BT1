### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`/`webhook_id`/`api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` are read directly from unauthenticated HTTP headers. The equality the gem is supposed to enforce — "the `shop` value trusted by the handler == the `shop` value the HMAC actually authenticates" — does not hold, because the HMAC never covers the `shop` header at all.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop` is pulled straight from the `shop-domain` header with no cryptographic binding to the signature: [3](#0-2) 

`Utils::HmacValidator.validate` verifies the HMAC purely against `to_signable_string` (i.e., the raw body) and the app's `client_secret`: [4](#0-3) 

`Webhooks::Registry.process` performs exactly this check, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, without any additional verification that the shop actually matches the body's content or a known/expected shop: [5](#0-4) 

Because Shopify's webhook signature (and thus this gem's re-implementation of it) only ever signs the body — not any header — an unprivileged actor who legitimately receives real, correctly-signed webhooks for their **own** shop (by simply installing the app on a shop they control, which requires no special privilege) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) with an arbitrary victim shop's domain. `HmacValidator.validate` will still succeed, since it only checks the body against the shared `client_secret`, and `Registry.process` will hand the host application a `WebhookMetadata` object claiming the (forged) body/topic came from the victim shop. This breaks the tenant-isolation invariant the whole verification step exists to guarantee: **HMAC-validated event ⇒ event genuinely originated for the `shop` recorded on it.**

### Impact Explanation
This is a cross-tenant confusion / forgery vector: any application built on this gem that uses `WebhookMetadata#shop` to select which merchant's session/access token/data record to update, delete, or act upon (a very common pattern, e.g. `app/uninstalled`, `shop/redact`, order/customer webhooks) can be tricked into applying an attacker-controlled payload under another merchant's identity. Depending on the host app's handler logic this can lead to cross-tenant data corruption, unauthorized state changes (e.g. faking a `shop/redact` or `app/uninstalled` event against a victim shop), or other actions being incorrectly attributed to a shop the attacker does not control — a direct violation of the "impact must be...cross-tenant access" criterion.

### Likelihood Explanation
The webhook endpoint is by design an unauthenticated, internet-reachable HTTP endpoint (that is the entire point of webhooks). Obtaining a valid `(body, hmac)` pair requires only installing the app on any shop the attacker controls (a dev/trial store is free and requires no special privilege) and capturing one delivered webhook. No access to `api_secret_key`, tokens, or the app's other tenants is needed — only the `shop-domain` header of the replayed request needs to be changed, which this gem never validates against the signature.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) values into the signable content, or otherwise cryptographically bind them to the verified body — e.g., have `to_signable_string` incorporate the shop domain, or require callers to pass the expected shop and compare it against a value derived from an authenticated source (such as a previously stored session) rather than trusting the raw header value once HMAC validation of the body succeeds. At minimum, document loudly that `request.shop`/`request.topic` are unauthenticated header values and must not be used for tenant selection without independent verification, and consider adding an explicit check in `Registry.process` that the resolved shop matches an expected/registered shop before dispatching to the handler.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the identical raw body and HMAC header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `Digest.hexencode(...) == compute_signature(request.to_signable_string, secret)` — `to_signable_string` is just `@raw_body`, unaffected by the header substitution: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: {"id":1}, ...)`, i.e., attacker-controlled data now impersonates the victim shop in the host application.
