### Title
Timing-based user enumeration in `/sessions` login endpoint via early-exit `FindUser` lookup - (File: `core/sessions/localauth/orm.go`)

### Summary
The unauthenticated `/sessions` login endpoint is vulnerable to a timing side-channel that allows an attacker to enumerate valid Chainlink node user emails, mirroring CVE-2021-29621 (Flask-AppBuilder timing-based user enumeration during database authentication).

### Finding Description
`SessionsController.Create` accepts unauthenticated POST requests to `/sessions` and forwards the request body directly into `AuthenticationProvider().CreateSession(ctx, sr)`: [1](#0-0) 

The local authentication implementation of `CreateSession` first looks up the user by email, and returns immediately on a "no such user" error — before ever touching the password hash comparison: [2](#0-1) 

`FindUser`/`findUser` is a fast indexed SQL lookup (`SELECT * FROM users WHERE lower(email) = lower($1)`): [3](#0-2) 

When the email *does* exist, execution proceeds past the fast DB lookup into `utils.CheckPasswordHash`, which performs a bcrypt hash comparison — a deliberately expensive, constant-but-large-cost operation (tens to hundreds of milliseconds) — before returning "Invalid password": [4](#0-3) 

Because a nonexistent email short-circuits before the bcrypt comparison while a valid email always pays the bcrypt cost, the two failure paths (`"Invalid email"` vs `"Invalid password"`) are distinguishable both by response content and by a large, measurable timing gap (bcrypt cost factor timing vs. a plain indexed SQL miss). The `constantTimeEmailCompare` call at line 154 is a no-op with respect to preventing this since it only executes for emails `FindUser` already matched — it does not equalize the timing between "user exists" and "user does not exist" branches, which is exactly the same root cause pattern as the referenced Flask-AppBuilder advisory. The identical pattern (fast-fail `GetContext` before bcrypt) also exists in the LDAP and OIDC local-admin fallback paths: [5](#0-4) [6](#0-5) 

The route is reachable by any unauthenticated client, gated only by a rate limiter (a fixed request quota, not a fix for the timing signal itself): [7](#0-6) 

### Impact Explanation
An unauthenticated attacker can distinguish "email not registered" from "email registered, wrong password" responses purely by measuring server response latency (bcrypt verification vs. a fast SQL miss), or via the differing error messages ("Invalid email" vs "Invalid password") which are propagated back to the HTTP client as the error body via `jsonAPIError`: [8](#0-7) 
This enables enumeration of valid Chainlink Node Operator API accounts, which is valuable reconnaissance for follow-on credential stuffing/brute-force attacks against the node's admin API.

### Likelihood Explanation
The endpoint is internet-facing and requires no authentication or special privilege — only a POST body with an email guess. The main mitigating factor is the configured rate limiter on the unauthenticated `/sessions` group, which throttles but does not eliminate the number of requests available for statistical timing analysis over time (attackers can still sample slowly and repeatedly, or use the direct error-message difference which requires no timing analysis at all).

### Recommendation
Perform a dummy/fixed-cost password hash comparison (e.g., against a static bcrypt hash) whenever `FindUser` fails to find a matching email, so that both "user not found" and "user found, wrong password" paths always incur the same bcrypt cost before returning. Additionally, return a single generic "invalid credentials" error for both cases instead of distinct "Invalid email"/"Invalid password" messages, and apply the same fix consistently across `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go` (`localLoginFallback`), and `core/sessions/oidcauth/oidc.go` (`localLoginFallback`).

### Proof of Concept
1. Send `POST /sessions` with `{"email":"admin@existing.com","password":"wrong"}` — measure response latency (includes bcrypt compare) and observe body contains `"Invalid password"`.
2. Send `POST /sessions` with `{"email":"nonexistent@nowhere.com","password":"wrong"}` — measure response latency (fast SQL miss, no bcrypt) and observe body contains `"Invalid email"`.
3. Repeat step 1/2 for a list of candidate emails; requests that consistently take the longer bcrypt-inclusive path (or return the "Invalid password" message) are valid registered accounts, exactly as described in `core/web/sessions_controller_test.go`'s existing "incorrect email" vs "incorrect pwd" test cases which already exercise these two distinct code paths: [9](#0-8)

	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
