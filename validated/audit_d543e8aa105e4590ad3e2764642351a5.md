Found a solid analog. The core issue: Shopify's webhook HMAC in this gem only signs the raw request body — the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and handed to the app's webhook handler as if they were verified.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in that signable string. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these header-derived fields when dispatching to the app's webhook handler, breaking the binding between "the payload cryptographically proven to come from Shopify" and "the shop/topic the app believes it belongs to."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed directly from headers, none of which participate in the HMAC computation: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the received HMAC: [3](#0-2) 

`Registry.process` validates that HMAC, then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler with no further check that these values correspond to the body that was actually signed: [4](#0-3) 

Because the HMAC is a per-app secret (`Context.api_secret_key`), it is identical across every shop/tenant that installs the app and across every topic. A holder of any one genuinely-signed `(raw_body, hmac)` pair — e.g., a merchant who installed the app and received a legitimate webhook for their own shop — can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers. `HmacValidator.validate` will still pass because it only checks the (unmodified) body, and `Registry.process` will dispatch the handler with the attacker-supplied `shop`/`topic`/`webhook_id` values as if Shopify had certified them for that shop and topic.

This is the same bug class as the referenced report: a value that is acted upon (there, `triggerFee`; here, `shop`/`topic`/`webhook_id`) is not covered by the same authorization/verification mechanism (there, fund transfer authorization; here, HMAC signature) that governs the rest of the operation.

### Impact Explanation
This breaks the identity binding `shop authenticated by Shopify's HMAC == shop the host app's handler acts on`. A host application's `WebhookHandler#handle` receives a `WebhookMetadata` whose `shop` is not actually bound to the signed payload, enabling cross-tenant data confusion: an attacker-controlled webhook (in terms of claimed shop/topic) can be injected into another tenant's processing pipeline as long as any one valid signed body for the app is known. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to possess at least one legitimately-signed webhook payload for the app (trivially obtainable by installing the app on any store, or intercepting one's own store's webhook traffic) and the ability to POST to the exposed webhook receiver endpoint with modified headers — no `api_secret_key`, access token, or privileged access is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them to the raw body before trusting them), so that `HmacValidator.validate` fails if any of these header-derived identifiers have been altered relative to what Shopify actually signed for that specific delivery.

### Proof of Concept
1. Install the app on Shop A and capture a legitimate webhook POST: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app secret) and `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` (a victim tenant) and/or `X-Shopify-Topic`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` in [5](#0-4) 
still returns `true` because it only checks `raw_body` against `H`.
4. `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with the attacker-chosen `shop`/`topic`, causing the host app to process/store data under the wrong tenant.
