### Title
Excess `msg.value` is never refunded in `IntentGatewayV2.placeOrder()` (Tron variant), permanently trapping user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` accepts native token via `msg.value` to cover native input legs and, optionally, the order's dispatch fee (swapped via Uniswap). Unlike the canonical EVM implementation, this version never refunds any left-over `msgValue` to the caller after escrowing inputs and paying fees.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` tracks a running `msgValue` local variable that is decremented as native-token inputs are escrowed [1](#0-0)  and, if `order.fees > 0`, further consumed by a Uniswap `swapETHForExactTokens{value: msgValue}` call to pay the dispatch fee in fee-token [2](#0-1) . After this, the function immediately emits `OrderPlaced` and returns [3](#0-2)  — there is no branch that sends any remaining `msgValue` back to `msg.sender`.

This is a direct analog of the reported `Allo._createPool()` bug class: whenever a user supplies more native token than strictly required (e.g., overestimating the Uniswap swap cost for `order.fees`, or simply sending more ETH than the sum of native `order.inputs`), the surplus silently accumulates in the contract's balance instead of being returned.

Compare this to the canonical (non-Tron) `IntentGatewayV2.sol`, which explicitly refunds the difference: `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` immediately after fee escrow [4](#0-3) . The Tron port is missing this exact final refund step, confirmed by tests explicitly validating the refund behavior of the non-Tron path but absent for the Tron path [5](#0-4) .

The Uniswap swap itself (`swapETHForExactTokens`) only spends up to `order.fees` worth of ETH and can return unspent ETH to the caller in some wrapper implementations [6](#0-5) , but in the vanilla `IUniswapV2Router02.swapETHForExactTokens` (as used here), unspent ETH from an over-supplied `msg.value` is refunded to the *caller of the router*, which is the `IntentGatewayV2` contract itself — not the original order-placing user. Without the missing `_sendValue(msg.sender, msgValue)` step, that refunded ETH (plus any leftover native input dust) remains locked inside `IntentGatewayV2` and is not attributable to, or recoverable by, the depositing user.

### Impact Explanation
Any user overpaying `msg.value` on `placeOrder()` — whether from over-estimating gas/fee-swap costs or simple UI rounding — has that excess permanently trapped in the contract. There is no escrow accounting, refund path, or event tracking this surplus as belonging to the user; the contract's balance simply grows. Because the funds are unaccounted for in the `_orders` mapping (they weren't recorded as an input or a fee), they are unrecoverable by normal user-facing functions (`cancelOrder`, `fillOrder`), constituting a permanent freezing/loss of user funds. This matches the "Medium" severity bar (concrete freezing of funds reachable by any unprivileged order placer).

### Likelihood Explanation
Likelihood is high: any user placing an order with a native-token fee swap (`order.fees > 0` and paying with native token) who doesn't send the *exact* wei amount consumed by `swapETHForExactTokens` will lose the difference. Since front-ends must estimate Uniswap swap costs in advance (subject to slippage/price movement), slight over-provisioning of `msg.value` is a normal and expected user behavior — exactly the scenario the non-Tron sibling contract explicitly guards against with its refund logic and dedicated tests.

### Recommendation
Add the same trailing refund logic present in the canonical `IntentGatewayV2.sol`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
right before the `OrderPlaced` event emission in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder()`, mirroring `evm/src/apps/IntentGatewayV2.sol` lines 394-397.

### Proof of Concept
1. User calls `placeOrder{value: X}(order, graffiti)` where `order.inputs` contains only ERC20 tokens (no native `address(0)` input) and `order.fees > 0`.
2. `msgValue` starts at `X` and is untouched by the ERC20-only input loop (lines 451-469).
3. The fee-escrow branch performs `swapETHForExactTokens{value: msgValue}(order.fees, ...)`, which spends only enough ETH to acquire `order.fees` fee-tokens; typically far less than `X` if `X` was provided generously to cover slippage [7](#0-6) .
4. The unspent ETH returned by the router lands in `IntentGatewayV2`'s balance, `msgValue` in the contract's storage/local state is never decremented to zero nor refunded.
5. Function returns after emitting `OrderPlaced` [3](#0-2)  without ever calling `msg.sender.call{value: ...}`.
6. The surplus ETH is now stuck in the contract, unattributed to any order or escrow entry, and unrecoverable by the user through any exposed function.
