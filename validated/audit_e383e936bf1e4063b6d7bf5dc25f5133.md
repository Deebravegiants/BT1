## Title
Webhook `shop` identity field is not covered by HMAC verification, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the request's HMAC before dispatching to the app's webhook handler, giving the impression that the whole request — including the shop identity — has been authenticated. In reality, the HMAC signature is computed only over the raw request body, while the `shop` value handed to the handler is read directly, unauthenticated, from the `x-shopify-shop-domain` header. Any attacker who can obtain one validly-signed `(body, hmac)` pair (e.g. by triggering a webhook to their own installed shop) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `shop-domain` header, and `Registry.process` will accept it as valid and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — it does not include the shop domain, topic, or any other header: [2](#0-1) 

The `shop` accessor, however, is read straight from the (unsigned) `shopify-shop-domain` / `x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then immediately trusts `request.shop` when constructing the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header_is_authentic == true`, but the equality that actually holds is only `hmac_valid(body) == true`; `shop` is an independent, attacker-controllable field once a single valid `(body, hmac)` pair is known.

### Impact Explanation
Because `shop` is not bound to the HMAC, an attacker who legitimately controls a shop that has the app installed can:
1. Trigger a webhook whose body they influence (e.g. `orders/create`, `products/update`) for their own shop, obtaining Shopify's genuine `x-shopify-hmac-sha256` value for that body.
2. Replay the exact raw body and HMAC header to the app's public webhook endpoint, but with `x-shopify-shop-domain` changed to a victim shop's domain.
3. `HmacValidator.validate` succeeds (it only checks the body against the shared `api_secret_key`), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain.

Any host application that uses `WebhookMetadata#shop` as the tenant key to persist or act on data (the pattern this library's own documentation and tests assume, e.g. `shop_test`/`registry_test` asserting `data.shop`) will write or act upon attacker-controlled webhook data under a different merchant's tenant. This is a cross-tenant data-integrity/confidentiality violation reachable without the attacker ever possessing the `client_secret`/`api_secret_key`.

### Likelihood Explanation
Exploitation requires only: (a) being a normal, unprivileged merchant with the target app installed on any shop (to obtain one valid signed body/HMAC pair), and (b) being able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both trivially available to any internet user who installs the app on a shop they control. No access to secrets, tokens, or the app's infrastructure is required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content, or otherwise cryptographically bind the `shop-domain` header to the verified payload before trusting it (e.g., compute the HMAC over `shop + topic + raw_body`, or require the host app to independently confirm that the shop present in the header is one that legitimately owns an active session/installation) before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) with attacker-chosen order data; capture the raw POST body and its genuine `x-shopify-hmac-sha256` header from Shopify's delivery.
3. Resend the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` (body unchanged), `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker data as if it originated from the victim's shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
