### Title
Arbitrary token drain from `EmporiumUpgradeable` via `erc20TokenAddresses.length==0` + `signerAddress==address(0)` bypass of all balance/signature guards - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a transaction uses the "Emporium Min" input form (`circomData.erc20TokenAddresses.length == 0`), every balance-diff invariant in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` is skipped because those checks are all `for (i = 0; i < circomData.erc20TokenAddresses.length; i++)` loops. Combined with `verifyWallet` short-circuiting when `stack.signerAddress == address(0)`, an attacker can execute arbitrary `EmporiumOperation`s (e.g. `token.transfer(attacker, D)`) with zero authorization and zero accounting, draining any ERC20/ETH balance the `Emporium` contract happens to hold.

### Finding Description
The broken equality: tokens leaving `Emporium` via `op.endpoint.call(...)` (`D`) is never compared against `-deltaAmountChanges` (always `int256[](0)` when `erc20TokenAddresses.length==0`), because the comparison loop itself never runs.

Path:
1. `dimensionsCheck` in `contracts/HinkalHelper.sol` only enforces that `erc20TokenAddresses.length == dimensions.tokenNumber` and that `amountChanges`, `inputNullifiers`, `outCommitments`, `encryptedOutputs` all equal that same length — it never inspects `externalActionData.externalActionMetadata` (the `EmporiumStack`/ops). [1](#0-0) 
2. With `tokenNumber = 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, whose only public signals are `emporiumMessage`, `timeStamp`, `calldataHash`. [2](#0-1) 
3. `circuits/MainEVMCircuitMin.circom` is trivial — it only proves `message = Poseidon(messageSeed)` and constrains `calldataHash`/`outTimeStamp` as public inputs; it places **no constraint whatsoever** on the ops/`callData` bytes inside `externalActionMetadata`. [3](#0-2) 
4. `calldataHash` is just `keccak256`-style hash of the attacker's own `circomData` (`getHashedCalldata`), which the attacker fully controls and can always make match — it is not tied to any spent nullifier or shielded value.
5. In `Hinkal._externalTransact`, `deltaAmountChanges = new int256[](circomData.erc20TokenAddresses.length)` → length `0` when the attacker sets `erc20TokenAddresses = []`. [4](#0-3) 
6. In `EmporiumUpgradeable.runAction`, `verifyWallet` is called with `stack.signerAddress == address(0)`; it marks `usedMessages` and returns immediately without checking any EIP-712 signature over the ops. [5](#0-4) 
7. The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` unconditionally (CASE 2, stateless), e.g. `token.transfer(attacker, D)`, with `msg.sender == Emporium`. [6](#0-5) 
8. `payRelayFees` and the post-call `balancesBefore`/`balancesAfter`/`BalanceChangeShouldBePositive` check are all `for (i = 0; i < circomData.erc20TokenAddresses.length; i++)` loops — with length `0` they never execute, so the stolen `D` is never detected and no UTXO is minted for it. [7](#0-6) 
9. Back in `Hinkal.transact`, the same `oldBalances`/`newBalances`/`balanceDif` invariant loop is keyed off `circomData.erc20TokenAddresses.length`, again `0`, so it also never fires; `insertNullifiers`/`insertCommitments` are no-ops on empty arrays. [8](#0-7) 

Every guard that could stop this (`dimensionsCheck`, `checkOnchainCreation`, `verifyProof`/circuit constraints, `verifyWallet`, the two balance-diff loops) is either scoped to `erc20TokenAddresses.length` (which the attacker sets to 0) or bypassed by `signerAddress == address(0)`. `onlyAllowedRecipient` is satisfied trivially because the call is routed through `Hinkal` (the registered `externalActionMap` address), which is an allowed recipient — the attacker never needs a privileged role.

### Impact Explanation
Any ERC20 (or ETH, since `Emporium` has a `receive()`) balance sitting on `EmporiumUpgradeable` — dust from rounding in `handleOut`, other users' stranded funds, protocol/relay residue — can be transferred to the attacker with no shielded value ever debited, no nullifier spent, and no UTXO created to account for it. This is direct theft of protocol/relay/other-user funds parked in the shared `Emporium` contract, and is repeatable every time `D > 0` accumulates, at zero cost beyond gas and a self-generated proof for the trivial `MainEVMCircuitMin` circuit. This matches "Critical – direct theft of shielded or in-flight user funds" / at minimum "High – theft of protocol/relay fees" depending on whose funds are parked there at the time.

### Likelihood Explanation
Preconditions: `token.balanceOf(Emporium) = D > 0` (achievable via normal rounding dust from `handleOut`, or any prior partial-fill/rounding flow) and the `Emporium` external action being registered (`externalActionMap[HINKAL_EMPORIUM_ACTION_ID] == Emporium`), which is standard deployment configuration, not a privileged precondition for the attacker to trigger. The attacker needs only: craft `circomData` with `erc20TokenAddresses=[]`, `EmporiumStack{signerAddress: address(0), ops:[...]}`, generate a proof for the trivial `MainEVMCircuitMin` circuit (no secret witness beyond an arbitrary `messageSeed`), and call `Hinkal.transact`. No relay, owner, or victim cooperation is required. Fully repeatable for every unit of dust that appears.

### Recommendation
Do not gate the balance-diff/slippage invariant checks on `circomData.erc20TokenAddresses.length`. When using the Emporium-Min path (`tokenNumber == 0`), either (a) forbid any op whose `callData` selector matches ERC20/ETH-moving functions (`transfer`, `transferFrom`, `approve`, etc.) unless `stack.signerAddress != address(0)` and its signature is verified, or (b) always require `verifyWallet`'s EIP-712 signature check for the ops array regardless of `signerAddress`, decoupling "who authorized these calls" from "whether shielded balances changed." At minimum, require `stack.signerAddress != address(0)` whenever `erc20TokenAddresses.length == 0`, since that is the only remaining authorization mechanism for the ops in that code path.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered via `registerExternalAction`), and a mock ERC20 `token`.
2. Seed dust: perform a legitimate Emporium swap flow (or directly `token.transfer(address(emporium), D)` to simulate rounding remainder) so `token.balanceOf(emporium) == D > 0`.
3. As `attacker` (unprivileged EOA), build `CircomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporium, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(token.transfer, (attacker, D))}]})}`, `calldataHash = getHashedCalldata(circomData)`.
4. Generate a valid Groth16 proof locally for `MainEVMCircuitMin` with arbitrary `messageSeed`, matching public signals `emporiumMessage/timeStamp/calldataHash`.
5. Call `hinkal.transact(a, b, c, dimensions{tokenNumber:0,...}, circomData)` from `attacker`.
6. Assert: tx succeeds; `token.balanceOf(attacker)` increased by exactly `D`; `token.balanceOf(emporium)` decreased by `D`; assert no entry was added to `nullifiers` mapping and no new leaf inserted into the merkle tree (`insertCommitments` no-op) — i.e. `-deltaAmountChanges` (0) != actual tokens moved (`D`) confirms the broken equality.
