### Title
Webhook shop identity not bound to HMAC-verified bytes enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The Firedancer report's root cause is a broken identity/size binding: the trust decision (Merkle proof depth) is taken from attacker-controlled bytes that were never validated against the allocation that later gets written into. The Ruby analog here is a broken *identity binding* of the same shape: `ShopifyAPI::Webhooks::Registry.process` authenticates a webhook using an HMAC that covers only the raw body, then trusts a separate, unauthenticated header (`shop-domain`) as the tenant identity used to dispatch and process the payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers that are never included in the HMAC-signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)`, and then immediately dispatches to the app handler using `request.shop` as the tenant identity, with no additional binding check between the authenticated body and the claimed shop: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body for webhooks) and compare it to the `hmac` header; they never fold in `shop`: [4](#0-3) 

The identity binding that should hold is:
`authenticated(shop, body) == (shop_header, body)` — i.e., the shop the app treats the payload as belonging to must be the same shop the HMAC secret was used to attest for. Instead the code enforces only `authenticated(body) == body`, and separately trusts `shop_header` unauthenticated. Because every shop that installs the same app shares the single app-level `api_secret_key` (there is no per-shop signing key), any shop merchant that legitimately receives a validly-signed webhook for their own shop can replay the exact same `raw_body` + `hmac-sha256` header while substituting a different `shop-domain` header value. The signature still validates (it never covered the shop header), and `Registry.process` will hand the replayed payload to the handler tagged as belonging to a different, victim shop — exactly the same class of bug as the report: "bytes verified" (body) diverges from "identity acted on" (shop).

This contrasts with `ShopifyAPI::Auth::Oauth::AuthQuery`, where the equivalent `shop` field *is* included inside `to_signable_string` and thus is properly bound to the HMAC: [5](#0-4) 

showing the gem's own OAuth path treats `shop` as security-relevant and binds it, while the webhook path does not.

### Impact Explanation
An attacker who is any low-privilege merchant with the target app installed on their own shop can receive genuinely-signed webhooks for their own store, then replay the untouched body/HMAC pair to the app's webhook endpoint with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a different, victim shop that also has the app installed. Because `Registry.process` only checks the HMAC of the body and trusts the header-derived `shop` for dispatch, the host application will process/act on this payload as if it were authentic data belonging to the victim tenant — a cross-tenant confusion/injection that can corrupt per-shop state, trigger unintended actions (e.g., app/uninstall handling, GDPR redact flows) or forge business events attributed to the wrong merchant. This matches the "Critical – cross-tenant access" impact category, since the effective merchant-identity boundary is not enforced by the gem.

### Likelihood Explanation
The precondition — installing the app on an attacker-controlled shop to legitimately receive one correctly-signed webhook — is trivial for any developer app that supports public/multiple-shop installs, and the API secret key is shared across all shops of the app (not per-shop), so no privileged credentials beyond ordinary merchant self-service access are required. The replay itself is a simple unauthenticated HTTP POST with a substituted header, requiring no cryptographic material and no interaction with the app's `client_secret` or access tokens.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified material, mirroring what `AuthQuery#to_signable_string` already does for OAuth: include `shop`, `topic`, and `webhook_id` in the signable string computed in `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the header-derived shop identity to the signed payload before it is handed to `WebhookMetadata`/handlers in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled `attacker-shop.myshopify.com`; capture a legitimate webhook Shopify sends: `raw_body = B`, header `shopify-hmac-sha256 = H = HMAC-SHA256(secret, B)`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Replay the exact same request to the app's webhook endpoint, changing only `shopify-shop-domain` to `victim-shop.myshopify.com` (keep `B` and `H` untouched).
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, so `Registry.process` proceeds: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body `B`, despite the payload never having been authenticated for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
