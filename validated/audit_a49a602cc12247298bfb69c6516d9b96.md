### Title
POA bridge status matches only by `assetId`, ignoring `index`/destination — misreports withdrawal status/txHash for same-asset batch withdrawals to different addresses - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a withdrawal leg by calling `findMatchingWithdrawal`, which selects the first API-returned entry whose `near_token_id` matches `assetId`, without ever consulting `index` or `destinationAddress`. When a single NEAR intent batches two POA-route legs with the same `assetId` but different `destinationAddress`, both `describeWithdrawal` calls (`index: 0` and `index: 1`) query the identical `withdrawal_hash` and resolve to the same array entry, so the second leg is reported as completed with the first leg's `transfer_tx_hash`.

### Finding Description
The broken equality: `describeWithdrawal({..., index:0}).txHash` should equal the destination-chain outcome of leg 0 (wallet A), and `describeWithdrawal({..., index:1}).txHash` should equal the outcome of leg 1 (wallet B). Because matching is done purely by `assetId`: [1](#0-0) [2](#0-1) 

both calls end up equal to each other instead — `describeWithdrawal(wid0) === describeWithdrawal(wid1)` when both legs share `assetId`.

Root cause / reachable path:
1. An ordinary user calls `sdk.signAndSendWithdrawalIntent` (or `processWithdrawal`) with `withdrawalParams` containing two POA-route legs, same `assetId` (`nep141:btc.omft.near`), different `destinationAddress`.
2. `createWithdrawalIdentifiers` assigns index per bridge route via a shared counter keyed by `bridge.route`, so both legs get `PoaBridge` and indexes `0` and `1`, and both share the same `intentTx` (`tx.hash`): [3](#0-2) 
3. `watchWithdrawal` for each `wid` calls `bridge.describeWithdrawal({...wid, logger})`: [4](#0-3) 
4. `getWithdrawalStatusWithRetry` queries the POA API keyed only by `args.tx.hash` (the shared NEAR intent tx hash), so both calls return the identical `withdrawals` list containing both legs' statuses: [5](#0-4) 
5. `findMatchingWithdrawal` finds by `nep141:${near_token_id} === assetId` only, taking the first match in the array irrespective of caller's `index` or `withdrawalParams.destinationAddress` — a limitation explicitly called out in the code's own comment ("multiple withdrawals of the same token in a single transaction are not supported").

Existing guards that don't help: `validateAddress`/`compareAddresses` validate a single address against the token's own address, not against sibling legs in the batch; `supports()` and `assert` checks only gate route eligibility and asset parsing, not per-leg identity; there is no per-index/per-address correlation performed anywhere in the POA path.

### Impact Explanation
An integrator relying on `watchWithdrawal`/`waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` results per index will receive, for withdrawal index 1 (destined for wallet B), the `status: "completed"` and `txHash` belonging to withdrawal index 0 (wallet A), while wallet B's actual transfer may still be pending or may fail. This is a status/hash misreport that can cause an integrator to credit or release funds for a withdrawal that has not actually completed to the reported address — matching the High-severity category ("a status or hash misreport making an integrator credit or refund twice"). The condition is repeatable on every batch containing ≥2 POA-route legs of the same `assetId`.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: an ordinary user constructs a batch withdrawal (`withdrawalParams` array) with two legs of the same POA-supported `assetId` and two different `destinationAddress` values, and calls `sdk.signAndSendWithdrawalIntent`/`processWithdrawal` — a documented, public batch-withdrawal feature (see README's "Batch Withdrawals" section). No special route/token state beyond "asset supported by PoaBridge" is required, and no privileged access or malicious infra is needed. Cost is a single normal transaction; the mismatch occurs on essentially every poll immediately after the first leg completes.

### Recommendation
Correlate `findMatchingWithdrawal` results with the specific leg using data the POA API returns per entry (e.g., match on `address`/`destinationAddress` and `amount`, not just token id), or reject/serialize same-asset legs within a batch until the POA API supports disambiguation by order, as the code comment already anticipates (sorting both sides by amount when POA API adds support).

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
