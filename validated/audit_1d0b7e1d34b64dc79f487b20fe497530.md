### Title
Missing shop domain validation in `Oauth.begin_auth` allows the OAuth anti-CSRF nonce to be redirected to an attacker-controlled host, enabling forced OAuth completion / session fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` string without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, unlike every other credential-issuing code path in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`). This lets an attacker cause the app to redirect a victim's browser — together with the freshly generated anti-CSRF `state` nonce — to an arbitrary host instead of a genuine `*.myshopify.com` shop.

### Finding Description
`begin_auth` computes the redirect target purely from the untrusted `shop` argument: [1](#0-0) 

`auth_base_uri` uses that same unsanitized `shop` to build `https://#{shop}/admin`: [2](#0-1) 

The `state` nonce, which is the sole binding between the browser session and the eventual callback, is placed both in a cookie on the victim's browser and as a `state` query parameter on the very URL that gets sent to `shop`: [3](#0-2) 

Compare this to `TokenExchange.exchange_token`, `ClientCredentials`, and `RefreshToken`, which all call `ShopValidator` to ensure the shop is a real Shopify domain before it is trusted: [4](#0-3) 

`Oauth.begin_auth`/`validate_auth_callback` never invoke this validator, so the identity binding that should hold — "`shop` == a genuine `*.myshopify.com`/trusted Shopify domain" — is not enforced at the point where the flow starts. Once `state` (and thus the CSRF-binding secret) has been leaked to the attacker's own server via the redirect, the attacker can drive their own legitimate Shopify test/dev shop through a real OAuth authorization, and manually construct the final redirect to the app's real callback with:
- `state` = the nonce stolen from the victim's initial redirect,
- `shop`, `code` = values from the attacker's own real Shopify install,
- `hmac` = the real, validly-signed HMAC Shopify issued for that install.

`validate_auth_callback` only checks that HMAC validity and that `state == cookies[state]` — both of which are satisfied here even though the "session" being finalized belongs to the attacker's shop, not to any shop the victim ever intended to interact with: [5](#0-4) 

Because `Session.from(shop: auth_query.shop, ...)` and the resulting session cookie are derived entirely from attacker-supplied but Shopify-signed data, the victim's browser ends up holding an authenticated app session bound to the attacker's shop — the classic "forced OAuth completion / session fixation" pattern.

### Impact Explanation
This breaks the identity binding `shop initiated by begin_auth == shop actually running the OAuth dialog`, letting an attacker hijack the OAuth state machine and force a victim's browser into a session controlled by the attacker's own Shopify store, without ever needing the app's `client_secret` or API key. This matches the report's "High" bucket criteria for session fixation / forced OAuth completion.

### Likelihood Explanation
Requires the host application to pass an unsanitized, user/attacker-influenced `shop` value into `begin_auth` (e.g., taken from a query string or header, as shown in this gem's own documentation example using `request.headers["Shop"]`), and requires the attacker to own a real Shopify shop to legitimately complete OAuth and produce a validly HMAC-signed callback. Both preconditions are realistic for typical embedded-app integration patterns documented for this gem.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` on `shop` inside `Oauth.begin_auth` (and defensively again in `validate_auth_callback` against `auth_query.shop`) before constructing `auth_base_uri`, exactly as is already done in `TokenExchange`, `ClientCredentials`, and `RefreshToken`, so redirects (and the accompanying anti-CSRF nonce) can never be sent to a non-Shopify host.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example.com", redirect_path: "/auth/callback")` using an attacker-controlled `shop` value (e.g., taken from a request header, per the gem's documented usage pattern).
2. `begin_auth` sets a `state` cookie on the victim's browser and redirects the browser to `https://attacker.example.com/admin/oauth/authorize?...&state=<nonce>...` — see `Oauth.begin_auth`/`auth_base_uri` at `lib/shopify_api/auth/oauth.rb:22-52` and `117-128`.
3. Attacker's server receives the `state` nonce directly as a URL query parameter.
4. Attacker completes a real OAuth authorization on their own legitimate Shopify shop, then redirects the victim's browser to the app's real callback URL, substituting the stolen `state`, along with `shop`/`code`/`hmac` from their own genuine, Shopify-signed install.
5. `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-73`) passes both the HMAC check and the `state == cookie` check, and issues a session/cookie bound to the attacker's shop to the victim's browser.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
