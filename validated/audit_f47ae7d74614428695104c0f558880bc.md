### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header trusted by handler without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body with HMAC, but the tenant-identifying `shop` header (and topic/webhook-id/api-version) are read straight from unauthenticated HTTP headers and passed on to the app's webhook handler as trusted values.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` verifies that string against the HMAC header using the app's `api_secret_key` [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` validates only the HMAC of the body, then forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.parsed_body` straight to the app's handler as the trusted tenant context: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [4](#0-3) .

This is the same class of bug as the report's "argument not covered by the guard": the value acted upon by the caller (`shop`, used by the handler to select which tenant's data to mutate) is not the value verified by the security check (only `@raw_body` is HMAC-covered). The binding that should hold is:
`request.shop` (used by handler) == `shop` bound inside the HMAC-covered payload
but in this implementation `request.shop` comes from an out-of-band header that carries no signature at all.

Because the app's `api_secret_key` is shared across every shop/tenant that installs the app, any shop that receives a legitimate webhook (a valid `(raw_body, hmac)` pair for its own shop) can replay that exact body+hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header for a different tenant. `Registry.process` will still consider the HMAC valid (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding relied upon by any handler that uses `WebhookMetadata#shop` to decide which tenant's records to read or write (e.g., store lookups, `Session` retrieval, cache keys). An attacker who is a genuine installed merchant of the app can inject data or trigger actions "as" an arbitrary other shop, since the signature that is supposed to prove authenticity says nothing about which shop the payload is for. This matches the "cross-tenant access" impact category from the disclosure rules, since a request that is cryptographically valid for tenant A gets attributed to tenant B purely by header substitution.

### Likelihood Explanation
Likelihood is High for any app whose webhook handler trusts `shop` from `WebhookMetadata` to scope tenant data (a very common pattern, as shown in the docs' own webhook handling guidance). The attacker only needs their own valid webhook deliveries (which every installed merchant naturally receives) and the ability to POST arbitrary headers to the app's public webhook endpoint — no access token, secret, or privileged account is required, satisfying the "unprivileged internet user" scope of this scan.

### Recommendation
Bind the tenant/topic identity into the HMAC-covered material, or otherwise cross-check header claims against Shopify's own authoritative source: e.g., include `shop`, `topic`, and `webhook_id` in the signed payload validated by `HmacValidator`, or require the handler-facing `shop` to be resolved from a previously-established, per-tenant webhook secret/session rather than an unauthenticated header. At minimum, document/require that consuming apps must not trust `WebhookMetadata#shop` as tenant-authoritative unless independently corroborated (e.g., via the registered webhook ID looked up from Shopify).

### Proof of Concept
1. App installs on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both signed with the same `api_secret_key`.
2. Attacker's own shop receives a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id` if the handler is topic-specific but body-format-compatible).
4. `HmacValidator.validate` in `Utils::HmacValidator.validate_signature` [5](#0-4)  passes because it only checks `raw_body` against the HMAC.
5. `Registry.process` [4](#0-3)  invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on data attributed to the victim tenant using attacker-controlled body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
