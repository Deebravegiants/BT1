### Title
Missing fee-vs-amount validation in `createWithdrawalIntents` allows negative `actualAmount` to be signed into a withdrawal intent - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`IntentsSDK.createWithdrawalIntents` computes `actualAmount = withdrawalParams.amount - feeEstimation.amount` when `feeInclusive` is true, but never checks that `feeEstimation.amount <= withdrawalParams.amount`. The `FeeExceedsAmountError` guard exists only in `_estimateWithdrawalFee`, not on this path, so a caller-supplied `feeEstimation.amount` greater than `withdrawalParams.amount` produces a negative BigInt that flows unchecked into the constructed intent.

### Finding Description
Equality that should hold: `actualAmount == withdrawalParams.amount - feeEstimation.amount >= 0`, and the resulting intent's transferred `amount` should equal a valid non-negative debit consistent with the caller's authorized funds.

In `createWithdrawalIntents`, for `feeInclusive: true`:
```
const actualAmount = args.withdrawalParams.feeInclusive
    ? args.withdrawalParams.amount - args.feeEstimation.amount
    : args.withdrawalParams.amount;
``` [3](#0-2) 

This `actualAmount` is passed straight to `bridge.validateWithdrawal(...)` and then to `bridge.createWithdrawalIntents(...)`. Every bridge's `validateWithdrawal` I inspected (e.g. `IntentsBridge.validateWithdrawal`) only validates `destinationAddress`/memo/asset support — none checks `amount >= 0` or `amount > 0`. There is no call to `FeeExceedsAmountError` anywhere on this path; that class is only constructed inside `_estimateWithdrawalFee` (a separate method used for fee quoting, not for intent construction). Since `feeEstimation` is caller-supplied input to `createWithdrawalIntents` (an SDK caller can pass any `FeeEstimation` object, e.g. from a stale/forged quote or a permissionless solver's quote it forwarded), an attacker who controls or influences the `feeEstimation` argument can set `feeEstimation.amount > withdrawalParams.amount`, yielding a negative `actualAmount`. This negative BigInt then gets serialized via `.toString()` into the `amount` field of intents such as `transfer`/`ft_withdraw` (see `IntentsBridge.createWithdrawalIntents` building `tokens: { [assetId]: amount.toString() }`), producing a `"-N"` string.

### Impact Explanation
If a negative amount string reaches an intent that the caller then signs and the relayer/contract accepts (or if it silently reverses the transfer direction), a caller could construct and sign an intent moving funds in ways they never intended, or the signed payload could fail unpredictably downstream while funds are already committed to signing. This matches the "fee error draining a material share of the amount" style Critical impact category described in the prompt, since the bug is a real missing invariant check in the SDK.

### Likelihood Explanation
The precondition is that the caller of `createWithdrawalIntents` supplies (or forwards from an untrusted quote/solver) a `feeEstimation.amount` exceeding `withdrawalParams.amount` while `feeInclusive: true`. This is directly reachable since both `withdrawalParams` and `feeEstimation` are ordinary parameters of the public SDK method with no cross-validation performed by the SDK itself before constructing intents.

### Recommendation
Add an explicit guard in `createWithdrawalIntents` (mirroring the one in `_estimateWithdrawalFee`) that throws `FeeExceedsAmountError` when `feeInclusive` is true and `feeEstimation.amount > withdrawalParams.amount`, before computing `actualAmount` and before calling `bridge.validateWithdrawal`/`bridge.createWithdrawalIntents`.

### Proof of Concept
```ts
// vitest, packages/intents-sdk/src/sdk.test.ts style
it("throws FeeExceedsAmountError instead of producing a negative amount", async () => {
  const sdk = new IntentsSDK({ referral: "test" });
  await expect(
    sdk.createWithdrawalIntents({
      withdrawalParams: {
        assetId: "nep141:usdc.near",
        amount: 100n,
        feeInclusive: true,
        destinationAddress: "user.near",
        routeConfig: { route: RouteEnum.InternalTransfer },
      },
      feeEstimation: { amount: 500n, quote: null, underlyingFees: {} },
    }),
  ).rejects.toThrow(FeeExceedsAmountError);
});
```
Assertions on both sides of the equality: before the fix, `actualAmount = 100n - 500n = -400n`, and the resulting intent's `tokens["nep141:usdc.near"]` (or `amount`) field equals `"-400"` — a negative string — violating `actualAmount >= 0`. After the fix, the call throws `FeeExceedsAmountError` and no intent is constructed.
