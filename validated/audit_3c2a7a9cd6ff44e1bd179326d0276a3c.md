Analyzing the webhook validation flow, I found that this matches the bug class exactly.

## Finding [1](#0-0) 

`Webhooks::Request#to_signable_string` returns only `@raw_body` — the HMAC signature that Shopify sends only ever covers the JSON body bytes. [2](#0-1) 

Meanwhile, `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header via `shopify_header`, a field that plays no part whatsoever in `to_signable_string`. [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body HMAC), then immediately trusts `request.shop` to build `WebhookMetadata` and hands it to the app's handler. [4](#0-3) 

`HmacValidator.validate` only calls `verifiable_query.to_signable_string` — for webhooks that's the raw body — and never touches `shop`.

### Title
Webhook shop-domain header is not covered by HMAC validation, enabling cross-tenant shop spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body. The `shop` value that `Registry.process` passes to app handlers as the tenant identity is taken from an HTTP header that is completely outside that signed content.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HmacValidator == shop delivered to the app's webhook handler`

In this gem that equality does not hold. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field on the same object. For `Webhooks::Request`, `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) is defined as `@raw_body` alone — it contains no reference to `shop`. The `shop` accessor instead reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header (`lib/shopify_api/webhooks/request.rb:67-70`), a value that is never mixed into the signed material.

`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) checks `Utils::HmacValidator.validate(request)` — which only proves "this body was signed with the app's secret at some point" — and then unconditionally forwards `request.shop` to the app's handler as the authoritative tenant for that payload.

Since a single app-wide `client_secret` signs webhooks for every merchant that installs the app, a valid `(raw_body, hmac)` pair legitimately produced for shop A carries no cryptographic tie to shop A. Anyone able to submit a request with that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but with the `shopify-shop-domain` header swapped to shop B, passes `HmacValidator.validate` unchanged while `Registry.process` reports the event as originating from shop B.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an HMAC-valid webhook can be attributed to an arbitrary shop domain chosen by whoever submits the HTTP request, not the shop that actually generated the signed body. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., `app/uninstalled`, GDPR shop-redact, or any handler that keys deletion/state changes off `data.shop`), this enables cross-tenant data corruption or destructive actions performed against a victim shop using content sourced from an unrelated shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design; no additional secret beyond a previously-observed valid `(raw_body, hmac)` pair is required. An attacker only needs one legitimately-delivered webhook (e.g., from their own store, if they are also a merchant using the app, or any other means of capturing one) to replay with an arbitrary `shop` header value.

### Recommendation
Include the shop domain in the signed material the request exposes, or otherwise cryptographically bind `shop` to the HMAC-checked payload, e.g., have `Webhooks::Request#to_signable_string` incorporate the `shop` header value (mirroring how `Oauth::AuthQuery#to_signable_string` includes `shop`), so `HmacValidator.validate` fails whenever the shop header has been altered relative to the body it accompanies.

### Proof of Concept
1. Attacker observes/captures any previously delivered, validly-signed webhook request `raw_body` + `shopify-hmac-sha256` header (e.g. from their own shop's `app/uninstalled` event).
2. Attacker POSTs the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, replacing only `shopify-shop-domain` with the victim shop's domain.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `shop` is the victim domain.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — it passes, because the body/HMAC pair is untouched.
5. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))`, delivering the payload to the app's handler tagged with the victim's shop domain, even though it was never actually produced for that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private
