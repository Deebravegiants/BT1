### Title
Oversized UDP datagram to TPU causes `Packet::meta().size` to exceed buffer capacity, breaking the "not discarded ⇒ has data" invariant and triggering `unreachable!()` panic in forwarding stage - (File: `streamer/src/recvmmsg.rs`)

### Summary
`recv_mmsg` (Linux path) copies the kernel-reported `msg_len` from `libc::recvmmsg` directly into `pkt.meta_mut().size` without clamping it to `buffer.len()` (`PACKET_DATA_SIZE`). For UDP/`SOCK_DGRAM` sockets, `recvmsg`/`recvmmsg` report the *full* datagram length even when the payload is truncated to fit the supplied `iovec`, so an attacker sending an oversized UDP datagram to a public TPU/TPU-forward socket can make `meta().size` exceed the actual number of valid bytes in the packet buffer while `discard()` remains `false`.

### Finding Description
In `streamer/src/recvmmsg.rs`, each `iovec` is sized to `packet.buffer_mut().len()` (`PACKET_DATA_SIZE`, 1232 bytes) [1](#0-0) , but after the syscall the code trusts the kernel-reported length unconditionally: [2](#0-1) 

For datagram sockets it is standard, documented POSIX/Linux behavior that `recv(2)`/`recvfrom(2)`/`recvmsg(2)` (and by extension `recvmmsg(2)`) report the size of the *original* datagram, not the truncated amount copied into the caller's buffer, when the datagram exceeds the supplied buffer. An unprivileged attacker can therefore `send_to()` a UDP datagram larger than 1232 bytes (up to 65507 bytes) to the TPU/TPU-forward port and force `hdr_ref.msg_len` to be, e.g., 9000, while only 1232 bytes of actual payload were written into `packet.buffer_mut()`. `meta().size` is then set to 9000 with `discard()` still `false` (the default `Meta`, never marked discarded here).

Downstream code assumes that any non-discarded packet has valid data spanning `meta().size` bytes. For example, `forwarding_stage.rs` explicitly encodes this assumption and panics via `unreachable!()` if it is violated: [3](#0-2) 

Because `meta().size` (9000) exceeds the packet's actual backing buffer (1232 bytes), a bounds-checked `data(..)` implementation (as seen in the sibling `BytesPacket::data`, which uses `self.buffer.get(index)`, i.e., `Option`-returning bounds checks rather than raw indexing) will return `None` even though `discard()` is `false` — precisely the case the code asserts is impossible, hitting `unreachable!()` and panicking the thread that processes ingress packets.

Note: The concrete `Packet` type (`buffer_mut`, `data`, `meta`) is defined in the external `solana_packet` crate, which is out of scope per SECURITY.md as a dependency, so I cannot directly confirm from this repo whether that crate's `data()` panics via unchecked slicing or returns `None` via bounds-checked `.get()`. Either way — a raw slice panic or the `unreachable!()` in `forwarding_stage.rs` — the attacker-controlled oversized `meta().size` from `recv_mmsg` is the root cause reachable entirely from in-scope, in-repo code (`streamer/src/recvmmsg.rs`, `core/src/forwarding_stage.rs`).

### Impact Explanation
A single unprivileged attacker with a raw UDP socket can crash the thread ingesting packets from the public TPU-forward socket (and potentially other consumers of `recv_mmsg`-sourced packets) by sending one oversized UDP datagram. Because every validator runs identical logic on identical attacker input, this can be repeated cluster-wide, causing coordinated packet-ingestion panics — a node-wide DoS / potential consensus-availability impact, matching the "panic/abort halting node operation" bounty category.

### Likelihood Explanation
- No stake, keys, or special network position required — just `UdpSocket::send_to()` to a public TPU/TPU-forward port.
- Relies only on well-established, documented kernel datagram semantics (oversized-datagram length reporting), not a race condition or timing-sensitive bug.
- Fully deterministic and trivially repeatable.
- The one open uncertainty is whether some earlier filter (e.g. `initial_packet_meta_filter`, or bounds-checking inside the external `solana_packet` crate) already clamps or discards packets whose `meta().size` exceeds `PACKET_DATA_SIZE` before they reach `forwarding_stage.rs` or banking-stage sanitization; I could not verify this because `initial_packet_meta_filter`'s body and the `solana_packet` crate source were not available in this repo's index.

### Recommendation
In `streamer/src/recvmmsg.rs`, clamp `pkt.meta_mut().size` to `buffer.len()` (or explicitly mark the packet as `discard()`/truncated) instead of trusting `hdr_ref.msg_len` verbatim:
```rust
let len = (hdr_ref.msg_len as usize).min(pkt.buffer_mut().len());
pkt.meta_mut().size = len;
```
Additionally, add a defensive check anywhere `meta().size` is trusted (e.g., before the `unreachable!()` in `forwarding_stage.rs`) to treat `size > buffer capacity` as a malformed/discarded packet rather than assuming it can't happen.

### Proof of Concept
```rust
// streamer/src/recvmmsg.rs - additional test
#[test]
#[cfg(target_os = "linux")]
pub fn test_recv_mmsg_oversized_datagram_size_exceeds_buffer() {
    let (reader, addr, sender, _saddr) =
        test_setup_reader_sender(IpAddr::V4(Ipv4Addr::LOCALHOST)).unwrap();

    // Send a UDP datagram larger than PACKET_DATA_SIZE.
    let oversized_len = PACKET_DATA_SIZE + 2000;
    let data = vec![0xAAu8; oversized_len];
    sender.send_to(&data[..], addr).unwrap();

    let mut packets = vec![Packet::default(); 1];
    let recv = recv_mmsg(&reader, &mut packets[..]).unwrap();
    assert_eq!(recv, 1);

    // BUG: meta().size exceeds the packet's actual buffer capacity.
    assert!(
        packets[0].meta().size <= PACKET_DATA_SIZE,
        "meta().size ({}) exceeds buffer capacity ({}) - invariant violated",
        packets[0].meta().size,
        PACKET_DATA_SIZE
    );
}
```
Expected today: this assertion fails, demonstrating `meta().size > PACKET_DATA_SIZE`. A follow-on integration test feeding such a packet through `forwarding_stage::buffer_packet_batches` (with `discard()` false) should be added to confirm it reaches the `unreachable!()` panic path rather than being filtered earlier.
