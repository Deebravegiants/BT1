### Title
Arbitrary router calldata + unlimited allowance in `ExternalActionSwap`/`LifiExternalAction` lets attacker divert swap proceeds and stranded token balances to themselves - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an **unlimited** ERC20 allowance and then executes fully attacker‑controlled `externalActionMetadata` calldata against that router with no constraint on which token, amount, or recipient the router call actually touches. Because the accounting invariant "tokens leaving the action == -deltaAmountChanges Hinkal sent it" is enforced only indirectly, via `Hinkal.transact`'s balance-diff check against an attacker-chosen `slippageValues[i]` floor, an attacker can craft a swap transaction that pulls more than `inputAmount` (including any residual/stranded `inputToken`/`outputToken` balance already sitting in the action from a prior transaction) and routes the bulk of the output to an address they control, while returning only the self-chosen minimal `slippageValues[1]` amount back to the action/Hinkal to pass all checks.

### Finding Description
The invariant that should hold is: **tokens leaving the action contract in a given tx == `-deltaAmountChanges` that Hinkal sent it that tx** (plus whatever legitimate swap output is produced and returned). In `ExternalActionSwap.swap`: [1](#0-0) 

`inputAmount` is derived only from `deltaAmounts[0]` (what Hinkal transferred this tx), but the actual token movement is delegated to `callRouter`, which in `LifiExternalAction` does: [2](#0-1) 

`approveUnlimited(inputToken, router)` grants the router infinite allowance on the action's balance of `inputToken` — persisting across transactions (this is the "persistent approval" set by any prior swap op). The subsequent `router.call(externalActionMetadata)` executes **attacker-supplied calldata** (per the rules, the attacker fully controls `externalActionMetadata`), which is not constrained to spend exactly `inputAmount`, nor to send the resulting `outputToken` back to `address(this)`. Since the router has unlimited approval, the attacker can encode a router call that:
1. Pulls the current `inputAmount` **plus** any pre-existing/stranded `inputToken` balance already parked in the action contract (e.g., dust or unswept remainder from a prior LI.FI swap operation), and
2. Routes the swap output to an attacker-controlled address instead of back to the action contract.

The only downstream check is in `Hinkal.transact`: [3](#0-2) 

`balanceDif >= circomData.slippageValues[i]` is checked against **Hinkal's own balance**, and `slippageValues[i]` is a value the attacker themselves supplies inside the proof's public `CircomData`. `ExternalActionSwap.swap` only requires `slippageValues[1] != 0` (nonzero), not any economically meaningful floor: [4](#0-3) 

So the attacker sets `slippageValues[1] = 1` (or any negligible value), diverts almost the entire true swap output (this tx's legitimate proceeds plus the stranded balance pulled via the unlimited approval) to themselves via the router call's destination parameter, and returns only 1 wei to the action, which forwards it to Hinkal via `transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal)`. Hinkal's `balanceDif` check passes trivially against the attacker-chosen floor, and `Hinkal`'s balance-equation check (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied because the attacker also sets a correspondingly tiny UTXO output. For the token index whose `amountChanges[i] == 0` (typically the output token, since `_externalTransact` only pushes funds to the action when `deltaAmountChanges[i] < 0`): [5](#0-4) 

Hinkal never pre-funds or independently tracks that token's movement — all integrity for it relies entirely on the action's own bookkeeping, which the attacker fully controls through the router calldata. None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, or `onlyAllowedRecipient` constrain what the router does with its unlimited allowance or where it sends the swap output; they only validate proof structure, root membership, and Hinkal's own balance deltas versus attacker-supplied public inputs.

### Impact Explanation
An unprivileged attacker can steal both (a) in-flight funds Hinkal sent to the action for the current swap beyond what's declared back to Hinkal, and (b) any previously stranded/residual token balance left in the action by prior operations (which, due to the unlimited persistent router approval, is always spendable by anyone who can supply router calldata through a subsequent swap transaction). This is direct theft of shielded/in-flight user funds, matching the "Critical: direct theft of shielded or in-flight user funds" category. It is repeatable on every transaction routed through `LifiExternalAction`, and worsens over time as stranded balances accumulate.

### Likelihood Explanation
Preconditions are minimal: the action contract must have executed at least one prior swap for the token (which is normal usage and sets the unlimited approval permanently), and the attacker only needs to deposit/generate a valid Hinkal proof for their own UTXOs and craft `externalActionMetadata`/`slippageValues` — both explicitly attacker-controlled per the threat model. No privileged role, oracle manipulation, or social engineering is required, making this highly feasible and repeatable.

### Recommendation
- Do not use `approveUnlimited`; approve only `inputAmount` immediately before the router call and reset to zero afterward.
- Validate that the router call actually delivers `outputToken` to `address(this)` and that the amount consumed of `inputToken` from the action's balance equals exactly `inputAmount` (e.g., snapshot and diff both input and output balances, reverting on excess input consumption).
- Enforce a protocol-side minimum meaningful slippage floor rather than trusting an attacker-supplied, unbounded-but-nonzero `slippageValues[1]`.
- Sweep/prevent stranded balances from persisting in the action contract, or ensure any leftover balance cannot be reached via arbitrary attacker calldata to the router.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` (or a mock LI.FI router that supports a "swap with custom recipient" call) with a real/mock router.
2. Seed the "residual": send `outputToken` (or `inputToken`) directly to the `LifiExternalAction` contract address outside of any Hinkal flow, simulating dust left from a prior swap.
3. Craft a Hinkal `transact` call with a valid proof where `circomData.externalActionData.externalActionMetadata` encodes a router call whose destination/recipient parameter is the attacker's EOA and whose `amountIn` covers both the tx's `inputAmount` and the seeded residual (using the router's allowance from `approveUnlimited`).
4. Set `circomData.slippageValues[1] = 1` and a correspondingly minimal UTXO output amount.
5. Assert:
   - `balanceOf(outputToken, attacker)` after tx `>` amount attacker should legitimately receive (should be 0 beyond their own deposited value).
   - `balanceDif` computed inside `Hinkal.transact` equals the tiny `slippageValues[1]`/UTXO amount, i.e., `balanceDif == amountChanges[1] + utxoAmount` passes only because both sides were minimized, not because real value was accounted for.
   - Total value that left the `LifiExternalAction` contract in the tx (input balance decrease) `>` `uint256(-deltaAmountChanges[0])` that Hinkal actually sent it that tx — breaking the target invariant.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
