## Finding

### Title
Unchecked ERC20 return-data in `IntentGatewayV2.withdraw()`/`SweepDust` silently accepts failed transfers, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron-specific `IntentGatewayV2` contract uses `SafeERC20` (`safeTransferFrom`/`safeTransfer`) when *pulling* tokens into escrow, but switches to a raw, unchecked low-level `.call` when *paying out* escrowed funds in `withdraw()` and in the `SweepDust` admin action. The success check only inspects whether the low-level call itself reverted, and never decodes/validates the boolean return data, which is the exact inverse of the "too-strict" `Erc20CheckedTransfer` bug class from the report: instead of over-rejecting valid non-standard tokens, this code under-validates and can treat a token transfer that returns `false` (a legitimate ERC20 failure signal that doesn't revert) as a success.

`success` here only reflects whether the external call reverted — it does not decode `returndata` to confirm the ERC20 contract actually returned `true`. Per ERC20, a compliant token is allowed to return `false` (rather than revert) to indicate a failed transfer (e.g., due to blacklist checks, paused state, or insufficient allowance edge cases on certain token implementations). With this code, such a `false` return is indistinguishable from a `true` return, so `if (!success) revert TransferFailed();` never fires, and execution proceeds to decrement `_orders[body.commitment][token] -= amount;` as if the beneficiary was paid.

This is reachable from an unprivileged path: `withdraw()` is invoked from `onAccept` for `RequestKind.RedeemEscrow`/`RefundEscrow` incoming ISMP requests (after `authenticate`), i.e., any relayed message that has been proven to the host can drive escrow settlement: [4](#0-3) 

and from `onGetResponse` for the refund-by-timeout flow: [5](#0-4) 

Note the equivalent EVM (non-Tron) `IntentGatewayV2.sol` uses `IERC20(...).safeTransfer`/`safeTransferFrom` uniformly throughout, so this issue is specific to the Tron variant's `withdraw`/`SweepDust` payout code paths.

### Impact Explanation
If a solver/beneficiary or fee-recipient token implementation ever returns `false` on failure instead of reverting (a valid, spec-compliant ERC20 behavior, and one that is realistic on TRON where TRC20/USDT-style tokens have historically diverged from strict ERC20 semantics), the escrow accounting (`_orders[commitment][token]`) is decremented and the fill/refund is marked complete via `_filled[body.commitment] = beneficiary`, while the intended recipient never actually receives the tokens. Because the escrow slot is zeroed out and the request is marked filled, there is no retry path — the underlying tokens remain locked in the `IntentGatewayV2` contract with no accounting entry pointing to them, making them permanently unrecoverable by the intended party. This matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
Triggering this requires a token used as an intent input/output/fee token whose `transfer` returns `false` on failure without reverting. This is a real, if not universal, ERC20 behavior; it can also be induced by a malicious/blacklisting token integrated as an order asset, or by any token that returns `false` for edge cases like transferring to a blacklisted/frozen address. Given the intents system is designed to be permissionless with respect to which ERC20s can be used as inputs/outputs, a solver or user can select such a token when constructing an order, so the trigger condition is within reach of ordinary, unprivileged usage rather than requiring a compromised admin.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used elsewhere in the same contract via `using SafeERC20 for IERC20;`), which decodes and validates the boolean return value (or absence thereof) consistently with the rest of the contract's escrow-input logic.

### Proof of Concept
1. Create/select an order whose output or fee token is a token contract that returns `false` (does not revert) when `transfer` fails for a specific recipient (e.g., a blacklist-style token, or any custom malicious token supplied as an intent asset).
2. A solver fills the order; relayer delivers the proven `RedeemEscrow` request to `IntentGatewayV2.onAccept`, invoking `withdraw()`. [6](#0-5) 
3. `token.call(...)` succeeds at the EVM call level (no revert) but the token internally returns `false`; `success` is `true`, so `if (!success) revert TransferFailed();` does not trigger.
4. `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment] = beneficiary;` marks the order filled, even though the beneficiary received zero tokens — the tokens remain stuck in the `IntentGatewayV2` contract with no remaining escrow accounting entry to reclaim them.
