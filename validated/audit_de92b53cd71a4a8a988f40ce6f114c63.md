### Title
Webhook `shop-domain`, `topic` and `webhook-id` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the body bytes but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Registry.process` then trusts those unauthenticated headers to decide which shop and topic the event belongs to and dispatches the handler accordingly, breaking the intended binding `hmac-signed bytes == data acted upon`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

which is exactly `@raw_body`, and is what `Utils::HmacValidator.validate` HMAC-verifies: [2](#0-1) 

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers with no cryptographic tie to the HMAC digest: [3](#0-2) 

`Registry.process` validates only the body HMAC and then dispatches the handler using these unauthenticated header values: [4](#0-3) 

Because the signature covers only the JSON body (which is frequently generic, e.g. `{}` or a small predictable payload for topics like `shop/redact`, `customers/redact`, or `app/uninstalled`), an unprivileged internet user who legitimately receives a real webhook from Shopify for *their own* shop (any merchant can install the app and trigger their own webhooks) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop, a forged `topic` header selecting a different (possibly more sensitive) registered handler, and/or a forged `webhook-id`. The HMAC will still validate because it only ever checked the body bytes, not the headers driving the handler dispatch and the `shop`/`topic`/`webhook_id` fields handed to `WebhookMetadata`.

This is the same bug class as the report: an authentic-looking signed event (`CardTopup`-equivalent = a validated `HmacValidator.validate` result) can be produced for an arbitrary victim identity (shop) using data an attacker legitimately controls, because the signature does not bind every field that downstream code treats as trusted.

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop acted upon by the handler`. An app's `WebhookHandler#handle` implementation (as recommended by this gem, see `docs/`) typically uses `WebhookMetadata#shop` to look up or mutate per-tenant state (e.g., process a `shop/redact` or `customers/redact` GDPR request, or process `app/uninstalled` to revoke access, or process any custom topic) — an attacker can trigger this business logic against an arbitrary victim shop merely by replaying a webhook they legitimately received for their own store with substituted headers, producing cross-tenant impact: false GDPR redaction/deletion triggers, false uninstall processing, or false state-changing webhook handling for a shop the attacker does not control.

### Likelihood Explanation
High likelihood: any Shopify merchant can install the app (or use a dev store) to receive a genuine webhook + valid HMAC for a low-entropy/predictable body (e.g., mandatory compliance topics send fixed-shape JSON), then simply resend that raw body with a modified `shop-domain`/`topic` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the target shop is required.

### Recommendation
Bind the header-derived identity fields into the signed material that `HmacValidator` checks, or otherwise independently verify them: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring Shopify's canonical webhook signing scheme if it supports header inclusion), or cross-check the header-derived shop/topic against a value independently obtained via an authenticated channel (such as validating the webhook against a per-shop secret or verifying the shop is one that is actually installed and matches an active session) before dispatching `WebhookMetadata` to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers a mandatory webhook (e.g. `customers/redact`) and captures the raw POST body (often `{}` or a small fixed JSON) along with the `X-Shopify-Hmac-SHA256` header Shopify computed for it, per `HmacValidator.validate_signature`: [2](#0-1) 
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (no header/body binding check) at [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body`, then dispatches `handler.handle` with `shop: "victim-shop.myshopify.com"`: [4](#0-3) 
6. The app's handler executes shop-scoped logic (e.g., redaction/uninstall processing) against the victim shop, believing it received an authentic Shopify-signed webhook for that shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
