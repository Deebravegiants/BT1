### Title
Webhook `shop-domain` (and topic/webhook-id) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are taken from unauthenticated HTTP headers — are never included in the signed content, yet they are trusted downstream to identify which tenant (shop) a webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to them: [2](#0-1) 

`Utils::HmacValidator.validate` / `validate_signature` compute the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the `hmac` value, never touching the headers: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler with the attacker-controllable `shop` header value: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` is verified, but the code (and every downstream consumer of `WebhookMetadata#shop`, typically used as the tenant/session lookup key by host apps) implicitly assumes `shop == the tenant that generated this authenticated body`. That equality is never checked — `shop` is free-floating, unauthenticated header data.

### Impact Explanation
Any unprivileged internet user who can install the app on their own (e.g. free/dev) shop receives genuine webhook deliveries from Shopify with valid HMACs computed over the JSON body. Because the `shop-domain` header is outside the signed content, that same attacker can replay the request to the app's webhook endpoint after changing only the `X-Shopify-Shop-Domain` header to a victim shop's domain (and/or the topic/webhook-id headers). `Registry.process` will still validate successfully (the body HMAC matches) and will invoke the registered handler with `WebhookMetadata.shop` set to the victim's domain instead of the attacker's own shop. Any host application that uses this `shop` value to select which tenant's data/session the webhook body should be applied to (the documented and expected usage pattern) will process attacker-supplied body content under another merchant's identity — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops and receives recurring webhooks (orders, products, etc.), since obtaining one genuine `(body, hmac)` pair only requires operating (or trialing) the app on any shop — no special privilege, no secret, and no social engineering required. The only requirement is guessing/knowing a victim shop's `.myshopify.com` domain, which is public information.

### Recommendation
Bind the `shop`, `topic`, `webhook_id`, and `api_version` values into the signed material (or otherwise cryptographically verify them), e.g. by including them in the HMAC computation, or by validating that the shop stored in `WebhookMetadata` matches an expected/allow-listed value tied to the webhook body's content, so the header values cannot be swapped independently of the authenticated body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)` header.
2. Attacker POSTs the same body `B` and the same header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, which is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` dispatches to the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host application to process attacker-controlled body content as if it originated from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
