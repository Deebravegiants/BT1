## Analysis

The `WrappedHyperFungibleTokenUpgradeable` contract implements a lock/unlock bridge for arbitrary ERC20 tokens across Hyperbridge-connected chains. In `send()`, the contract locks `params.amount` of the underlying token by calling `safeTransferFrom`, but never measures what it actually received: [1](#0-0) 

For a fee-on-transfer underlying token, the contract's actual balance increase is less than `params.amount`, yet the dispatched cross-chain `Message.amount` (used to build the ISMP `PostRequest` body) still carries the full requested `params.amount`: [2](#0-1) 

On the destination chain, `onAccept()` unconditionally unlocks (`safeTransfer`) that inflated `message.amount` to the beneficiary from its own local pool of locked underlying tokens: [3](#0-2) 

This is directly analogous to the reported Harpie `Vault` bug: the accounting record (dispatched/escrowed amount) is created from the *requested* amount rather than the token balance actually received, so it silently overstates what backs it. Each fee-on-transfer transfer drains the destination-side pool by more than the source-side pool actually gained, progressively insolvency-ing the bridge's locked reserves; eventually other users' legitimate `send()`/unlock operations on that pair revert with insufficient balance, permanently freezing their funds.

By contrast, the current `IntentGatewayV2.placeOrder()` code explicitly guards against this by measuring `balanceOf` before/after each `safeTransferFrom` and mutating `order.inputs[i].amount` to the actual received amount before computing the escrow/commitment: [4](#0-3) 

and is covered by dedicated fee-on-transfer tests [5](#0-4) . However, the older Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) still calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and stores `reducedInputs[i].amount` into escrow without ever checking actual received balance: [6](#0-5) 

This Tron path has the same root-cause gap, but `WrappedHyperFungibleTokenUpgradeable.send()`/`onAccept()` is the clearest, currently-relied-upon analog since it lacks any of the balance-diffing protection the main `IntentGatewayV2.sol` already applies, and it directly propagates the inflated amount into a cross-chain mint/unlock message rather than a purely local escrow.

### Title
Fee-on-transfer tokens cause unbacked cross-chain unlock and pool insolvency in `WrappedHyperFungibleTokenUpgradeable` - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`WrappedHyperFungibleTokenUpgradeable.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` without verifying the contract's actual balance increase, then dispatches a cross-chain message that encodes the requested `params.amount` rather than the amount actually received.

### Finding Description
`send()` at [7](#0-6)  pulls tokens with `safeTransferFrom` but does not diff `balanceOf(address(this))` before/after. `_buildDispatchPost()` then encodes `params.amount` verbatim into the `HyperFungibleTokenUpgradeable.Message` body [2](#0-1) . If `_underlying` is a fee-on-transfer token, the contract actually locks less than `params.amount`. On the destination chain, `onAccept()` transfers out the full, unadjusted `message.amount` to the beneficiary from its own locked-token pool [8](#0-7) , which is strictly more than what was actually backed on the source side for that transfer.

### Impact Explanation
Every fee-on-transfer `send()` call drains the destination chain's locked-token reserve by more than the corresponding amount that was actually locked on the source chain. Repeated use of this path (deliberately or incidentally, since anyone can call `send()` for any configured `_underlying` token) causes accumulated insolvency: the pool on one or both sides no longer holds enough underlying tokens to satisfy legitimate unlocks/refunds for other users, permanently freezing their funds once the shortfall manifests (a `safeTransfer` reverting for insufficient balance).

### Likelihood Explanation
Any user can call `send()` with an underlying token address that has fee-on-transfer semantics (a known category of "weird ERC20" per the referenced `weird-erc20` catalogue), and the contract owner's `configure()` call determines `_underlying` per deployment — there's no code path preventing fee-on-transfer tokens from being configured. No special privilege is required to trigger the discrepancy; a single `send()` call is enough to under-fund the corresponding cross-chain unlock, and this is a straightforward, repeatable one-transaction trigger.

### Recommendation
In `send()`, measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta as the `amount` encoded into the dispatched `Message` (mirroring the balance-diffing fix already applied in `IntentGatewayV2.placeOrder()`). Apply the same fix to any other lock/mint or lock/unlock paths (including the Tron `IntentGatewayV2.placeOrder`) that still trust caller-declared amounts instead of measured token balances.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleTokenUpgradeable` with a fee-on-transfer `_underlying` token (e.g., 1% transfer tax) on chain A and B.
2. Alice calls `send({amount: 1000, dest: B, to: Alice})` on chain A. Chain A's contract actually receives only 990 tokens, but the dispatched message still encodes `amount: 1000`.
3. On chain B, `onAccept()` unlocks 1000 tokens to Alice from chain B's locked-token pool, even though chain A only ever backed 990.
4. Repeating this creates a growing shortfall between the tokens locked across chains and the tokens promised for unlock, eventually causing `safeTransfer` calls to revert for other users' withdrawals due to insufficient contract balance — permanently freezing their funds.

            msgValue = msgValue - params.amount;

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
