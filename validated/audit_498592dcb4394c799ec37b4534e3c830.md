### Title
Vetoing a stale state commitment resets `_latestStateMachineHeight` to `1`, allowing subsequent consensus updates to silently overwrite older, already-settled state commitments and reset their challenge-period clock, permanently blocking message delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets the per-state-machine `_latestStateMachineHeight` pointer to the hard-coded value `1` whenever the vetoed height happens to be the current latest height, instead of restoring it to the previous valid height (as the Substrate `pallet-ismp` equivalent does via `PreviousStateMachineHeight`). This re-opens *every* height above `1` — including heights whose commitments were legitimately verified and already relied upon for message delivery — to be overwritten by the next `handleConsensus` call in `HandlerV2.sol`, which only checks `intermediate.height > latestHeight` before calling `storeStateMachineCommitment`, with no check that a commitment for that height doesn't already exist.

### Finding Description
`EvmHost.storeStateMachineCommitment` unconditionally overwrites both the state commitment and its update timestamp for a given height: [1](#0-0) 

`HandlerV2.handleConsensus` gates the call to `storeStateMachineCommitment` only on `intermediate.height > latestHeight`, with no check that the height is unwritten: [2](#0-1) 

Contrast this with the Substrate `pallet-ismp` consensus handler, which explicitly refuses to overwrite a height that already has a stored commitment (`if host.state_machine_commitment(state_height).is_ok() { continue; }`), showing this is the intended invariant across the protocol: [3](#0-2) 

The bug is in how `EvmHost` resets `_latestStateMachineHeight` after a fisherman veto of a bad commitment: [4](#0-3) 

When the vetoed height equals the current latest height, the pointer is reset to `1` rather than to the previous valid height. Because `handleConsensus`'s only guard is `intermediate.height > latestHeight`, once `_latestStateMachineHeight` collapses to `1`, *any* height greater than `1` — including heights well below the vetoed one that already carry live, correctly verified commitments — becomes eligible again for `storeStateMachineCommitment` to be called on it in a subsequent consensus update. This silently overwrites the existing commitment and, critically, resets `_stateCommitmentsUpdateTime[height]` to `block.timestamp`.

This exactly mirrors the CVE's bug class: an operation intended to correct/expire one record (the veto) instead causes a *different, otherwise-settled* cached record's freshness/validity window to be reset/extended when it is subsequently rewritten — undermining the entire purpose of the delay/TTL mechanism protecting it.

### Impact Explanation
`HandlerV2.handlePostRequests` (and the analogous response/timeout handlers) gate message delivery on the challenge period having elapsed since the state commitment's update time: [5](#0-4) 

If an attacker (or any relayer, honest or not) can trigger a veto of the current latest height — e.g. by relaying a state commitment for the latest height that a fisherman then vetoes as part of normal operation — `_latestStateMachineHeight` drops to `1`. Any subsequent legitimate consensus update whose intermediate states include an older height that already has pending requests/responses proven against it will re-store that height's commitment and reset its `_stateCommitmentsUpdateTime` to `block.timestamp`. This restarts the challenge-period clock for that height indefinitely. As long as a relayer keeps repeating this (each new consensus update naturally re-includes recently finalized heights until they're superseded), all pending requests/responses whose proofs are anchored to that height can be perpetually denied by `ChallengePeriodNotElapsed`, permanently freezing message delivery for that route — a "route unable to deliver messages" outcome explicitly in scope. It also corrupts the commitment content itself if the re-verified intermediate differs from what's already stored, undermining state-commitment integrity that requests/responses/timeouts all rely on.

### Likelihood Explanation
Triggering the precondition requires only a single veto of the current latest-height commitment (a normal, expected event in the fisherman/veto flow for state-commitment fraud) and then a routine subsequent consensus update whose intermediates re-touch an older height. Both are reachable via a single relayed consensus proof and a single veto — no privileged role or governance action is needed, and any relayer can supply the consensus proof that re-includes the older height.

### Recommendation
Fix `deleteStateMachineCommitmentInternal` to reset `_latestStateMachineHeight[height.stateMachineId]` to the previous valid height (tracked analogously to Substrate's `PreviousStateMachineHeight`) rather than the constant `1`. Additionally, mirror the Substrate handler's invariant in `HandlerV2.handleConsensus` by refusing to call `storeStateMachineCommitment` for a height that already has a non-empty commitment stored, regardless of the `latestHeight` comparison.

### Proof of Concept
1. Relayer submits `handleConsensus` proof advancing state machine `X` to height `H2` (latest becomes `H2`), with an earlier height `H1 < H2` already committed and referenced by pending request proofs.
2. A fisherman detects `H2`'s commitment is fraudulent and calls the veto path, invoking `EvmHost.deleteStateMachineCommitment(height=H2, fisherman)`. Since `H2 == _latestStateMachineHeight[X]`, the pointer resets to `1` instead of `H1`.
3. Relayer submits another valid `handleConsensus` proof whose intermediates include height `H1` (naturally re-included by the consensus client's verify output since `H1` is still within its finalized range). `HandlerV2.handleConsensus`'s check `latestHeight(=1) != 0 && intermediate.height(H1) > latestHeight(1)` passes, so `host.storeStateMachineCommitment(H1, ...)` is called again, overwriting `_stateCommitmentsUpdateTime[X][H1]` to the current `block.timestamp`.
4. Any `handlePostRequests`/`handleGetResponses`/timeout call whose proof height is `H1` now fails `ChallengePeriodNotElapsed` again, even though it had already elapsed before step 3 — and this can be repeated indefinitely by resubmitting consensus proofs, permanently blocking delivery of messages proven at `H1`.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
