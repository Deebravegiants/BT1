Based on the analysis, the `to_signable_string` for `Webhooks::Request` returns only the raw body [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only this body-based HMAC and then dispatches the handler using the unauthenticated `shop`/`topic`/`webhook_id` header values [3](#0-2) .

### Title
Webhook tenant/topic identity spoofing via HMAC that covers only the body, not the shop/topic headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, and `webhook_id` fields that the host application uses to attribute and route the event are taken from unauthenticated HTTP headers. This breaks the identity binding: `HMAC-covered bytes (raw_body) != bytes acted on for tenant/topic routing (headers: shop-domain, topic, webhook-id)`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from headers, none of which are included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `to_signable_string` (i.e. the body): [4](#0-3) 

`Registry.process` accepts any request whose body HMAC validates, then unconditionally forwards `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) into `WebhookMetadata` for the handler to act on: [3](#0-2) 

Because the API secret key (`Context.api_secret_key`) used to sign webhooks is shared across every shop/tenant that has the app installed, and only the body is bound to the signature, an attacker who obtains one valid `(body, hmac)` pair for their own tenant — for example, by registering a custom webhook subscription via the Admin API that points at an endpoint they control, using their own legitimately-installed access token (a tenant-level, unprivileged capability) — can replay that exact `(body, hmac)` pair to the app's real webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` will dispatch the handler believing the event originated from a different shop and/or topic than it actually did.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata#shop` to key any tenant-specific action (e.g., updating billing state, disabling a store, writing to per-shop data based on `data.shop`, or dispatching topic-specific side effects based on `data.topic`), this weakness lets one tenant forge events that are misattributed to another tenant, i.e., cross-tenant access/tampering — a Critical-class impact per this gem's own trust boundary (the HMAC is the only integrity guarantee provided over an otherwise-untrusted public HTTP endpoint).

### Likelihood Explanation
This is not theoretical replay over intercepted TLS: any tenant who has installed the app already possesses a legitimate access token for their own shop and can call the Admin API to (re)register a webhook subscription pointing at a server they control, which causes Shopify to deliver a body correctly HMAC-signed with the app's shared secret. That signed body/HMAC pair can then be resent to the app's actual webhook endpoint with forged routing headers, entirely from the public internet, without ever needing `api_secret_key` itself.

### Recommendation
Bind the routing-critical fields into the signed content model, or otherwise validate them out-of-band: e.g., require the handler/registry to cross-check `shop`, `topic`, and `webhook_id` against Shopify's own webhook delivery records (via the Admin API) before trusting them, or extend `to_signable_string` to be computed the same way Shopify computes its signature (Shopify signs only the body by design), and instead have the registry/host application treat `shop`/`topic` header values as untrusted metadata that must be independently corroborated (e.g. re-fetching the resource referenced in the body via an API call scoped to the claimed shop) before being used for any privileged, tenant-differentiating action.

### Proof of Concept
1. Tenant A installs the app and receives an offline access token for `shop-a.myshopify.com`.
2. Tenant A uses the Admin API (via their own token) to register/re-point a webhook subscription for topic `orders/create` to an attacker-controlled listener (`https://attacker.example/collect`).
3. Tenant A triggers the event in their own store; Shopify POSTs the event to the attacker's listener with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`.
4. Attacker captures `(raw_body, hmac)`.
5. Attacker POSTs the exact same `raw_body` to the app's real webhook endpoint (`ShopifyAPI::Webhooks::Registry.process`), but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant) and/or a different `x-shopify-topic`.
6. `Utils::HmacValidator.validate` succeeds (line-for-line reproducing `to_signable_string`/body match), and `Registry.process` dispatches the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: <forged-topic>, ...)`, per [3](#0-2) , causing the host app to act as though the event came from shop-b under the forged topic.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
