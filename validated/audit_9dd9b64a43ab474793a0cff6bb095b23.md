### Title
Permanent freezing of pool liquidity via unguarded division-by-zero in `Calculator::calc_x_power` reachable from `calc_take_pnl` (Deposit/Withdraw/WithdrawPnl) - (File: program/src/math.rs, program/src/processor.rs)

### Summary
`Calculator::calc_x_power`, invoked by `Processor::calc_take_pnl` on every `Deposit`, `Withdraw`, and `WithdrawPnl` call, performs `.checked_div(current_y).unwrap()` where `current_y` is a decimal-normalized token amount that can legitimately be `0`. Because the normalization function `normalize_decimal_v2` truncates small raw vault balances to `0`, an attacker or the pool creator can drive the pool into a state where this division-by-zero panics on every subsequent call, permanently bricking deposits/withdrawals for the pool.

### Finding Description
`Calculator::normalize_decimal_v2` converts a raw token amount into "sys_decimal_value" units via integer division: [1](#0-0) 

For a token with `coin_decimals = 9` and the default `sys_decimal_value = 10^6`, any raw balance below `1000` truncates to `0`. This is a normal, legitimately reachable value — not an error condition — analogous to `summarize = 0` in the TensorFlow report being a valid but unguarded input.

`Processor::calc_take_pnl` uses these normalized amounts (`x1`, `y1`) as `current_x`/`current_y` inputs to `Calculator::calc_x_power`: [2](#0-1) 

`Calculator::calc_x_power` unconditionally divides by `current_y` with `.unwrap()`, with no zero-check: [3](#0-2) 

`calc_take_pnl` is called from all three of the reachable, unprivileged-facing instructions that touch pool liquidity:
- `process_deposit` (any depositor): [4](#0-3) 
- `process_withdraw`/`process_withdrawpnl` (LP holder / configured pnl_owner path, both reuse the same vulnerable code path): [5](#0-4) 

The state that triggers the zero-normalized amount is directly attacker-reachable in two ways:
1. **At pool creation**: `Initialize2` only enforces `liquidity = sqrt(pc_amount * coin_amount) > 10^lp_decimals`, not a floor on either individual side, so a pool creator can seed the pool with a very small coin (or pc) balance while a large amount on the other side satisfies the sqrt check: [6](#0-5) 
`TargetOrders::check_init` is then seeded with `x`, `y` computed from this same normalization, so `calc_pnl_y` (or `calc_pnl_x`) is stored as `0`: [7](#0-6) 

2. **On an existing pool**: swaps only prevent complete drain via a strict `<` check (`swap_amount_out >= total_.._without_take_pnl` is rejected, but any smaller residual is allowed), so a well-capitalized swapper can push the raw vault balance on one side down to a residual amount whose normalized value is `0`: [8](#0-7) 

Once either normalized `x1` or `y1` is `0` and the `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount` branch is taken (trivially true when both sides are `0`, e.g., right after init), `calc_x_power`'s `checked_div(current_y).unwrap()` panics, aborting the transaction. Because every future `Deposit`/`Withdraw`/`WithdrawPnl` re-derives the same zero-normalized amount from the (now permanently small) vault balance, the panic recurs on every subsequent call — permanently freezing the initial depositor's and any subsequently deposited LP funds, with no path to recovery (no admin instruction repairs `TargetOrders`/vault balances).

### Impact Explanation
This causes permanent freezing of LP/user funds: once triggered, no LP holder can ever withdraw their share and no further deposits can succeed, because every code path that calls `calc_take_pnl` panics deterministically. This matches the "permanent freezing of user or LP funds" acceptance criterion, and is reachable through a single submitted transaction with attacker-chosen accounts/data (either a malicious pool creator seeding a skewed pool, or a swapper pushing a normal pool into the same skewed state).

### Likelihood Explanation
High for maliciously-created pools (trivial to seed a skewed pool at `Initialize2` since only the sqrt(x*y) floor is enforced, not per-side minimums) and plausible for existing pools with sufficiently capitalized swaps that reduce one side of the pool near its dust threshold. No privileged role or off-chain component is required — an ordinary user submitting standard `Initialize2`/`Deposit`/`Withdraw`/swap instructions with crafted amounts can trigger it.

### Recommendation
- Add explicit zero-checks before the divisions in `Calculator::calc_x_power` and return a proper `AmmError` (e.g., `AmmError::CalcPnlError`) instead of panicking via `.unwrap()`.
- Enforce minimum normalized (not just raw) amounts for both `pc` and `coin` sides at `Initialize2`, ensuring `normalize_decimal_v2` never yields `0` for the initial `target_x`/`target_y`.
- In swap processing, additionally guard against reducing the normalized remaining balance on either side to `0`, not just the raw balance.

### Proof of Concept
1. Call `Initialize2` for a token pair where `coin_decimals = 9`, `sys_decimal_value = 1_000_000`, seeding `amm_coin_vault.amount = 500` (raw units) and `amm_pc_vault.amount` large enough that `sqrt(pc_amount * 500) > 10^lp_decimals` passes.
   - `y = normalize_decimal_v2(500, 9, 1_000_000) = 500 * 1_000_000 / 10^9 = 0` (truncated).
   - `TargetOrders.calc_pnl_y = 0` is stored via `check_init`.
2. Call `Deposit` (any account) on this pool.
   - `total_coin_without_take_pnl` is still `500` (or similar dust amount), so `y1 = normalize_decimal_v2(500, 9, 1_000_000) = 0` again.
   - `calc_take_pnl` computes `pool_pc_amount*pool_coin_amount(0) >= calc_pc_amount*calc_coin_amount(0)` → true, enters the branch.
   - `Calculator::calc_x_power(calc_pnl_x, calc_pnl_y=0, x1, y1=0)` executes `.checked_div(current_y)` with `current_y = 0`, which is `None`, and `.unwrap()` panics — the transaction aborts.
3. Every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` on this pool panics identically, permanently freezing the funds already deposited (including the pool creator's own initial LP tokens) and preventing any future deposit.

        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }
