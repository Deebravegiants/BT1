### Title
`ValidateSecurityContext` blocks `CAP_SYS_ADMIN` + `allowPrivilegeEscalation=false` only via case-sensitive exact-string match, allowing trivial bypass via case-variant capability names - ([File: pkg/apis/core/validation/validation.go])

### Finding Description
`ValidateSecurityContext` implements a specific business rule intended to reject any container that sets `allowPrivilegeEscalation=false` while also requesting the `CAP_SYS_ADMIN` capability (a capability that itself enables privilege-escalation-equivalent operations), unless the `allowSysAdminWhenPrivilegeEscalationFalse` compatibility flag is set: [1](#0-0) 

The check at line 8832 performs an exact, case-sensitive string comparison: `string(cap) == "CAP_SYS_ADMIN"`. Kubernetes' `Capability` API type is a bare string with no format/casing validation enforced by this function or elsewhere in this validation path, so an unprivileged user with only pod-create rights in a namespace (Restricted PSA not enforced) can submit `securityContext.allowPrivilegeEscalation: false` together with `capabilities.add: ["cap_sys_admin"]` (or `"Cap_Sys_Admin"`, `"CAP_sys_admin"`, etc.). Because the comparison is exact-match only, none of these variants trip the check, and the pod spec is persisted by the API server even though the validation's explicit intent — as documented by the adjacent error message "cannot set `allowPrivilegeEscalation` to false and `capabilities.Add` CAP_SYS_ADMIN" — is to forbid exactly this combination.

### Impact Explanation
This is a validation-totality bug: the guard rail meant to prevent a specific dangerous capability/flag combination is defeated by trivial input casing, letting a spec that the code explicitly intends to reject be persisted in etcd. Whether this translates into actual `CAP_SYS_ADMIN` being granted inside the running container depends on how the kubelet/container-runtime canonicalizes capability names before handing them to the OCI runtime; that normalization step lives outside `pkg/apis/core/validation` (in kubelet/CRI/runtime code) and was not confirmed within this repository's validation package. If that downstream layer normalizes capability names case-insensitively (a common convenience behavior in the Kubernetes ecosystem, where short/mixed-case capability names like `NET_ADMIN` are historically accepted and canonicalized), the bypass results in an actual privilege escalation matching the "Pod Security / admission bypass" bounty class. If the downstream layer instead requires exact `CAP_XXX` canonical form, the practical effect is limited to a persisted invalid/unintended spec (container likely fails to start), which is a lower-severity validation-integrity defect rather than a confirmed privilege escalation.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only ordinary pod-create RBAC in a namespace where the Restricted Pod Security Admission level is not enforced (baseline/privileged/unset), which is a common real-world configuration. No cluster-admin, node, or webhook access is required. The bypass itself (submitting a lowercase capability string) is trivially reproducible via a normal `kubectl create` or API call.

### Recommendation
Normalize the capability string before comparison (e.g., `strings.EqualFold(string(cap), "CAP_SYS_ADMIN")` or uppercase both sides), and apply the same normalization consistently to any other capability-name business-rule checks in this file, so the check cannot be bypassed by case variation.

### Proof of Concept
Unit test (table-driven) in `pkg/apis/core/validation/validation_test.go`:
1. Call `ValidateSecurityContext(sc, fldPath, false, false)` with:
   - `sc.AllowPrivilegeEscalation = pointer.Bool(false)`
   - `sc.Capabilities.Add = []core.Capability{"cap_sys_admin"}`
2. Assert `len(allErrs) == 0` (demonstrating the exact-match check at line 8832 fails to catch the lowercase variant, contrary to the intended behavior for the canonical `"CAP_SYS_ADMIN"` value, which does produce an error).
3. Compare against a control case using `"CAP_SYS_ADMIN"` (uppercase) and assert `len(allErrs) == 1`, confirming the inconsistency is purely due to casing.

Further integration-level confirmation of whether this results in actual capability grant inside the container would require tracing kubelet's capability-to-OCI-spec translation code and the container runtime's capability name canonicalization, which is outside `pkg/apis/core/validation` and was not verified in this repository.
