### Title
Theft of victim funds via stale ERC20 approvals left on the shared Emporium by CASE 2 - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable` is a **single shared contract** for all users, and its CASE 2 "stateless" branch executes `op.endpoint.call(op.callData)` with the Emporium itself as `msg.sender`/token owner, with no restriction on `op.endpoint` or `op.callData`. If any user's op leaves a residual `IERC20.approve(router, amount)` from Emporium to a router, that allowance lives in the token contract's storage (keyed by `owner = Emporium`), independent of and outliving that user's transaction, and can be swept by any later, unrelated caller.

### Finding Description
Equality that should hold, per `runAction`, for each token `i` actually touched during the batch of ops:

`amount_pulled_from(emporium, token_i) == -deltaAmountChanges[i]` (tokens flowing out of Emporium must be accounted for by the caller's own declared withdrawal).

The loop in `runAction` only computes and checks this for tokens present in `circomData.erc20TokenAddresses`: [1](#0-0) 

CASE 2 itself places no constraint on which token/endpoint/allowance an op may touch: [2](#0-1) 

Root cause / exploit flow:
1. At some earlier, unrelated time, a victim's own `runAction` batch includes a CASE 2 op `token.approve(dexRouter, amount)` (owner = Emporium, since Emporium itself performs the call) intended to be immediately consumed by a following swap op in the same batch. If the router pulls less than the approved amount (partial fill, slippage-tolerant multi-hop, or an "approve-max" style op), a nonzero allowance `token.allowance(emporium, dexRouter)` survives after the victim's transaction ends. This allowance is *global* state on the ERC20 contract, not scoped to the victim.
2. The attacker — an ordinary user with no special role — crafts their own `runAction` call whose `circomData.erc20TokenAddresses` **omits `token` entirely**. Their CASE 2 op calls `dexRouter.swap(..., recipient: attacker)`. The router internally calls `token.transferFrom(emporium, dexRouter, amount)`, consuming the stale allowance, and sends the swap proceeds to the attacker-controlled `recipient`.
3. Because `token` is not in the attacker's `circomData.erc20TokenAddresses` array, the `balancesBefore`/`balancesAfter` accounting loop never observes it — the balance-conservation check (`BalanceChangeShouldBePositive`) is only evaluated for tokens the attacker chose to list. `-deltaAmountChanges[i]` is never compared against the actual amount pulled for `token`, so the equality is silently vacuous (0 == amount_pulled is never even computed).
4. The circuit-level constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`, etc.) only constrain the UTXOs and tokens that are part of the attacker's own proof; they have no visibility into arbitrary side effects of an unconstrained `op.endpoint.call`, so they cannot prevent this.

None of the existing guards catch this: `onlyAllowedRecipient` only checks that the caller of `runAction` is the trusted Hinkal router, not that `op.endpoint`/`op.callData` are safe; `verifyWallet`/EIP-712 signature checks only bind the *victim's* own ops, not the attacker's; and the balance-based conservation check is scoped per-token to whatever the caller declares, making it trivially bypassable by omission.

### Impact Explanation
An unrelated attacker can steal any ERC20 tokens for which a prior user's legitimate (or even accidental) CASE 2 approve-then-swap sequence left a nonzero allowance from the shared Emporium contract to a router. This is direct theft of value that was never the attacker's, executed purely through the attacker's own valid proof/circomData, with the funds redirected to an attacker-chosen address. This matches the **Critical** category ("direct theft of shielded or in-flight user funds"). It is repeatable for every distinct stale allowance left behind by any user, on any router the Emporium has approved.

### Likelihood Explanation
Preconditions: (a) some user's CASE 2 batch previously called `approve` on Emporium's behalf and the router did not fully consume the allowance (a realistic occurrence for approve-then-swap patterns, especially with routers using partial-fill/multi-hop execution or intentionally reusable approvals for gas savings), and (b) the attacker can identify this via public on-chain `allowance(emporium, router)` state (trivially observable). Attacker cost is a single normal deposit + proof generation for their own op — no privileged role required, no cooperation from the victim needed. Given Emporium's stateless-op design intentionally allows arbitrary `endpoint.call(callData)`, and approvals are ERC20-contract-level state that outlives a single transaction on a shared contract, this is a structurally likely occurrence, not a contrived edge case.

### Recommendation
- Never leave persistent allowances from the shared Emporium to third-party contracts: require every CASE 2 `approve` to be paired and immediately zeroed within the same batch (`approve(router, 0)` at the end of the ops, or use single-use permit/pull patterns), or restrict `op.endpoint`/selectors allowed in CASE 2 to a vetted allow-list (similar to `_isAllowedRecipient`) that disallows raw `approve` calls to arbitrary spenders.
- Alternatively, redesign so that Emporium never holds a standing balance/allowance across transactions: sweep/revoke all approvals to the ops' endpoints at the end of every `runAction`, or require `circomData.erc20TokenAddresses` to be exhaustive and provably match every token whose balance/allowance changed during the batch (fail-closed instead of the current "unlisted tokens = unchecked" behavior).
- As defense in depth, enforce that the balance-conservation check in `runAction` scans allowances granted during the batch and requires they be reset to 0 before completion.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock ERC20 `TOKEN`, and a mock router `MockRouter` whose `swap(uint256 amount, address recipient)` calls `TOKEN.transferFrom(emporium, router, amount)` then transfers output tokens to `recipient`.
2. Victim transaction: call `runAction` with a CASE 2 op sequence `[TOKEN.approve(router, 1000), router.swap(400, victim)]` where circomData declares a deposit that funds Emporium with `1000 TOKEN` and lists `TOKEN` in `erc20TokenAddresses` with matching `deltaAmountChanges`. After this call, assert `TOKEN.allowance(emporium, router) == 600` (stale allowance survives) and `TOKEN.balanceOf(emporium) == 600`.
3. Attacker transaction: build `circomData` for the attacker's own deposit of some *other* token (or none), with `erc20TokenAddresses` **not including `TOKEN`**, deltaAmountChanges matching only the attacker's own declared tokens. CASE 2 op: `router.swap(600, attacker)`.
4. Call `runAction` as the attacker. Assert:
   - The call succeeds (no revert from `BalanceChangeShouldBePositive`) because `TOKEN` was never in `erc20TokenAddresses`.
   - `TOKEN.balanceOf(emporium) == 0` (victim's remaining 600 drained).
   - `TOKEN.balanceOf(attacker) == 600` (proceeds redirected to attacker).
   - Assert the two sides of the intended equality: `amount_pulled_from(emporium, TOKEN) = 600` while the attacker's declared `-deltaAmountChanges` for `TOKEN` was never computed/enforced (array omits it) — demonstrating the broken invariant.
