## Title
Unchecked ERC20 `transfer` return value in `CallDispatcher`-routed sweeps causes stuck/lost funds for non-reverting tokens - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`CallDispatcher.dispatch()` executes arbitrary calls with a raw, low-level `.call` and only checks that the call did not *revert* — it never inspects the returned ABI-encoded boolean that ERC20's `transfer`/`transferFrom` are supposed to return. `IntentGatewayV2`/`IntentsBase` build ERC20 `transfer` calls with `abi.encodeWithSelector(IERC20.transfer.selector, ...)` and route them through this dispatcher for both predispatch and postdispatch (output) sweeps, so any output token that returns `false` on failure instead of reverting (e.g. USDT-style non-standard, blacklistable, or paused tokens) will be silently treated as a successful transfer.

### Finding Description
`CallDispatcher.dispatch` performs: [1](#0-0) 

Only `success` (i.e., non-revert) is checked; the returned `bool` payload of a `transfer()` call is discarded.

`IntentsBase._execute` (invoked on order fill to run `order.output.call` postdispatch calldata) sweeps any residual token balance left on the dispatcher back to the gateway using this same unchecked path: [2](#0-1) 

The `DustCollected(token, balance)` event is emitted based purely on `IERC20(token).balanceOf(dispatcher)` *before* the sweep executes, and there is no subsequent balance check to confirm the tokens actually arrived at `address(this)`. If the `transfer` call returns `false` without reverting, `CallDispatcher` reports success, `DustCollected` has already fired claiming the dust was collected, but the tokens remain stranded on the `CallDispatcher` contract — which has no owner-controlled sweep/rescue function — permanently freezing them.

The same unchecked `IERC20.transfer.selector` construction is used in the predispatch sweep of `placeOrder` in both the EVM and Tron `IntentGatewayV2.sol`: [3](#0-2) [4](#0-3) 

While that particular call site does reconcile actual received balance afterward (setting `order.inputs[i].amount = received`), the underlying tokens that failed to move are still left stuck inside the `CallDispatcher`, since a silent-failure transfer leaves the dispatcher still holding the balance while the gateway's escrow accounting is reduced to zero for that leg — the user's tokens are effectively lost with no owner/recovery path on `CallDispatcher`.

This is the same bug class as the referenced Sherlock report on Sense's `AutoRoller.sol`: an unchecked `transfer()` call assumes success whenever the call doesn't revert, permanently trapping funds when interacting with non-standard ERC20 tokens.

### Impact Explanation
Any solver-supplied `order.output.call`/`order.predispatch.call` involving a non-standard ERC20 output/input token (returns `false` instead of reverting on failure) can cause tokens to become permanently stuck in the `CallDispatcher` contract with no recovery mechanism, while the protocol's own bookkeeping (`DustCollected` event, `order.inputs[i].amount`) diverges from reality. This is a concrete path to permanent freezing/loss of funds reachable by any intent solver or user filling/placing an order with calldata — satisfying Medium severity per the analogous audit finding.

### Likelihood Explanation
This path is reachable by any unprivileged intent solver or user who places/fills an order using the calldata (predispatch/postdispatch) feature of `IntentGatewayV2`, which is a normal, documented usage pattern (swap-then-escrow / fill-then-act). It only requires an output/input token whose `transfer` can return `false` without reverting under some condition (paused, blacklisted, insufficient allowance edge cases in non-standard implementations) — a realistic condition for arbitrary ERC20s that solvers/users may route.

### Recommendation
Have `CallDispatcher.dispatch` (or the callers constructing ERC20 transfer `Call`s) decode and validate the boolean return data for calls targeting known ERC20 `transfer`/`transferFrom` selectors, or better, replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` sweep pattern in `IntentsBase._execute` and the `placeOrder` predispatch/postdispatch sweeps with `SafeERC20.safeTransfer` semantics performed directly by the gateway (pulling funds via a trusted path) rather than routing raw transfer calldata through the generic, return-value-blind `CallDispatcher`.

### Proof of Concept
1. A solver fills an order whose `order.output.assets` includes a token `T` implementing `transfer` that returns `false` (does not revert) once some internal condition is hit (e.g., temporarily paused, blacklisted recipient, or a buggy/malicious token deliberately deployed by the solver as the output token).
2. `_execute` computes `balance = IERC20(T).balanceOf(dispatcher)` > 0, emits `DustCollected(T, balance)`, and builds a sweep `Call` to `T.transfer(address(this), balance)`.
3. `ICallDispatcher(dispatcher).dispatch(...)` executes `T.transfer(...)` via low-level `.call`; `T` returns `false` but does not revert, so `success == true` in `CallDispatcher.dispatch` and no revert occurs.
4. The gateway believes it collected `balance` as dust (event already emitted) but the tokens never left the `CallDispatcher`. Since `CallDispatcher` has no sweep/rescue function callable by the gateway or an admin, the funds are permanently stuck. [1](#0-0) [5](#0-4)

            Call memory call = calls[i];

                revert NotContract(to);

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});

                }

                        value: 0,
