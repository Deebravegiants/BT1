### Title
Webhook HMAC does not cover the `shop`/topic/id headers, allowing shop-domain spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` (and `topic`, `webhook-id`, `api-version`) values that the handler receives and that the host application uses to key tenant-scoped data are taken directly from HTTP headers that are **not** part of the signed payload [2](#0-1) . This breaks the binding: `shop (HMAC-authenticated origin of the body) == shop (header value trusted for tenant dispatch)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`HmacValidator.validate` computes/verifies the HMAC exclusively against that signable string [4](#0-3) .

`Registry.process` gates entirely on that HMAC check and then dispatches to the handler using `request.shop`, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC: [5](#0-4) [6](#0-5) 

Because the HMAC is computed only from the JSON body (using the app's shared `client_secret`, common to every installed shop), any party who can obtain one valid `(body, hmac)` pair for a given topic — e.g., by installing the app on their own shop and receiving a legitimate webhook — can resend the identical body/HMAC while substituting the `shop-domain` header to any value. `Utils::HmacValidator.validate` will still pass, since it never inspects the shop header, and `Registry.process` will invoke `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, ...))` with the attacker-chosen shop value.

### Impact Explanation
Applications built on this gem commonly use the `shop` value returned in `WebhookMetadata` to look up per-tenant session/access-token state or to key deletion/uninstall/GDPR handling logic (e.g. `shop/redact`, `app/uninstalled`). Because that value is unauthenticated relative to the HMAC, an attacker can cause the host application to process a valid, signature-passing webhook payload as if it belongs to an arbitrary shop of the attacker's choosing — a cross-tenant identity confusion. This satisfies the High-impact class "scope/expiry check bypass" adjacent condition of a broken tenant identity binding, since the shop actually authenticated (none — HMAC covers only the body) diverges from the shop trusted for dispatch.

### Likelihood Explanation
Exploitability requires only the capability any unprivileged internet user already has for this gem's threat model: install/uninstall the target app on a shop they control (or otherwise trigger/capture a legitimately signed webhook), then replay the body+HMAC to the app's public webhook endpoint with a modified shop-domain header. No `api_secret_key`, access token, or privileged access is required — the request never needs to be re-signed because the header is outside the HMAC's coverage.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the value that is HMAC-verified, or otherwise cryptographically bind the shop header to the signed payload before dispatch. At minimum, `Registry.process`/`Request` should require the caller to supply the expected shop (from an already-authenticated session context) and assert it matches `request.shop`, rather than trusting the header value implicitly for tenant dispatch.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and captures a legitimate webhook POST, e.g. body `{"id":123}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — unchanged — so validation succeeds [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` [8](#0-7) , and any host-app logic keyed on `data.shop` now acts on the victim's tenant using attacker-supplied data.
