## Title
Malicious input token in a same-order token batch permanently freezes co-escrowed legitimate assets in `IntentGatewayV2` cross-chain redemption - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder` lets the order creator pick an arbitrary set of `order.inputs` token addresses with no validation beyond a balance/allowance pull, exactly as `CollateralManager.commitCollateral` let a caller pick arbitrary collateral tokens for a bid. When the order is later filled cross-chain, the resulting `WithdrawalRequest.tokens` array (equal to `order.inputs`) is redeemed on the source chain by `_withdraw`, which iterates the whole array and unconditionally calls `safeTransfer` on every token in one atomic loop. A single attacker-crafted, always-reverting ERC20 placed alongside a legitimate token (e.g. USDC) in the same order will cause the entire redemption to revert every time it is attempted — and because the settlement message is dispatched with `timeout: 0` (never times out), there is no fallback path that ever frees the legitimate co-escrowed funds.

### Finding Description
`placeOrder` (`evm/src/apps/IntentGatewayV2.sol:312-373`) accepts caller-supplied `order.inputs[i].token` addresses with no allow-listing, pulling each via `safeTransferFrom`/native value and crediting `_orders[commitment][token]` for every token, including attacker-deployed ones. [1](#0-0) 

For a cross-chain order, `_fillCrossChain` forwards `order.inputs` verbatim as the token list of the `RedeemEscrow` settlement message dispatched back to the source chain, with a hard-coded `timeout: 0` (no expiry) via `_post`. [2](#0-1) [3](#0-2) 

On the source chain, `onAccept` decodes the `WithdrawalRequest` and calls `_withdraw`, which loops over `body.tokens` (i.e., the attacker-chosen `order.inputs`) and calls `IERC20(token).safeTransfer(beneficiary, amount)` for every entry with no isolation between tokens — one reverting token aborts the whole function. [4](#0-3) [5](#0-4) 

`EvmHost.dispatchIncoming` treats an `onAccept` revert as a retryable failure: it deletes the request receipt and returns without an error, so the message is neither delivered nor rejected — it stays permanently "pending redelivery." [6](#0-5) 

Because a malicious token's revert-on-transfer condition is fully attacker-controlled and does not need to ever clear, and because the `RedeemEscrow` message was dispatched with `timeout: 0`, this request can never time out and never successfully deliver. The `_orders[commitment][...]` balances for every token in that order — including the genuinely valuable one — remain locked in the `IntentGatewayV2` contract on the source chain forever. This is the same root cause as the CollateralManager report: an unprivileged party can freely inject an arbitrary/malicious asset into a batched collection that is later iterated over as a single unit for release, and one poisoned entry blocks release of all co-bundled legitimate entries with no per-item isolation or access control on which assets may be added to the batch.

### Impact Explanation
This is a real, exploitable path to permanent freezing of funds: a solver who has already delivered genuine output tokens on the destination chain (irreversible, atomic real-value transfer) can be permanently denied the escrowed input tokens on the source chain, and the user's original escrowed input tokens (e.g., USDC) become permanently stuck in the gateway contract with no reachable retry, refund, or timeout path. This qualifies as High/Critical: concrete permanent freezing of funds triggered by a single `placeOrder` transaction from an unprivileged user plus a normal fill/relay flow, matching the "route unable to deliver messages" / "permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
Likelihood is high: `placeOrder` performs no validation of the token contracts supplied in `order.inputs` beyond a successful transfer-in, so any user can pair a legitimate stablecoin input with a self-deployed ERC20 that unconditionally reverts on outbound `transfer` (or reverts under attacker-chosen conditions revealed only after the destination fill has occurred). No special privileges, governance, or malicious-relayer/collator assumptions are needed — only a standard order placement and a normal solver fill.

### Recommendation
Do not process multiple tokens for the same withdrawal atomically. Either:
- Isolate each token transfer in `_withdraw` with a low-level `call`/`try/catch` and credit any failed transfer to a per-token pull-based claim mechanism instead of reverting the whole batch, or
- Maintain a protocol-level allow-list/registry of tokens permitted as `order.inputs`, rejecting unknown/arbitrary token contracts at `placeOrder` time, or
- Give `RedeemEscrow`/`RefundEscrow` messages a real, bounded `timeout` (not `0`) so a stuck settlement can fall back to a recovery/refund path instead of remaining undeliverable indefinitely.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transferFrom` (into the gateway) always succeeds but whose `transfer` (out of the gateway) always reverts.
2. Attacker calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000}, {token: EvilToken, amount: 1} ]`, destination on another chain. Both legs escrow successfully: `_orders[commitment][USDC] = 1000`, `_orders[commitment][EvilToken] = 1` (`evm/src/apps/IntentGatewayV2.sol:313-373`).
3. A solver calls `fillOrder` on the destination chain, delivering the required output tokens to the beneficiary and triggering `_fillCrossChain`, which dispatches a `RedeemEscrow` post request (`tokens: order.inputs`) with `timeout: 0` back to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`, `:126-142`).
4. A relayer delivers the request; `onAccept` calls `_withdraw`, which iterates `[USDC, EvilToken]` and reverts on the `EvilToken.transfer` call (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`).
5. `EvmHost.dispatchIncoming` catches the revert, deletes the receipt so the message "can be retried" (`evm/src/core/EvmHost.sol:809-816`), but every retry hits the same always-reverting `EvilToken.transfer` and fails identically forever; since the message timeout is `0`, it can never time out into a refund path.
6. The escrowed 1000 USDC is now permanently locked in the source-chain `IntentGatewayV2` contract — the solver, who already paid the real output on the destination chain, can never claim it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
