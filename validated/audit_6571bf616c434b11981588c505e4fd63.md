## Title
Webhook shop identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are taken directly from unauthenticated HTTP headers. This breaks the identity binding `hmac == HMAC(secret, body)` from the fact actually relied upon downstream: `data.shop == authenticated shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no validation against the signed payload or against `ShopValidator`: [2](#0-1) 

`Registry.process` validates the HMAC over the body and then constructs webhook metadata using this unauthenticated `shop` header value: [3](#0-2) 

`HmacValidator.validate` (and `validate_signature`) computes and compares the HMAC purely over `to_signable_string`, i.e., the raw body, using the app's single shared `api_secret_key` — the same secret is used for every shop that has the app installed, so the HMAC does not bind the signature to a particular shop: [4](#0-3) 

Because the secret is shared across all merchants/tenants of the app and the shop identity is excluded from the signed string, any two shops that produce an identical raw body (e.g., identical/replayable webhook payloads, or an attacker who controls their own shop and can arrange for a specific body) yield an HMAC that is valid regardless of which shop header is attached. An attacker who owns/installs the app on their own shop can capture a legitimately-signed `(raw_body, hmac)` pair from their own webhook deliveries, then replay that exact body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects `shop`), so `Registry.process` invokes the merchant's handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim shop as the source, even though the authenticated bytes only prove the body came from someone holding the app secret — not that it came from the victim.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on when processing webhooks (e.g., `app/uninstalled`, `orders/paid`, `customers/data_request`, GDPR webhooks, etc.). Since `data.shop` is the sole tenant discriminator passed to the handler and is not cryptographically bound to the signed payload, an attacker who can generate one valid signed webhook body for any shop can attribute arbitrary webhook events/data to a different shop of their choosing, resulting in cross-tenant data injection/confusion in the host application (e.g., forging an `app/uninstalled` event for a victim shop, or writing attacker-supplied order/customer data under a victim shop's identity). This matches the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires the attacker to be able to install the app on a shop they control (a standard, unprivileged install available to any merchant/developer for public or development apps) and to capture one valid signed webhook delivery for that shop, then replay it with a modified shop header against the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only ordinary use of the app as an unprivileged shop owner plus a network request forging a header, which is squarely within an "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the HMAC-verified data. At minimum:
- Include `shop` (and `topic`, `webhook_id`) in the signable string used by `Request#to_signable_string`, or
- Derive/validate the shop exclusively from a value that is cryptographically tied to the delivery (e.g., cross-check the header shop against a per-shop secret/session already on file for that shop, rather than trusting the header verbatim), and
- Run the shop domain header through `ShopValidator.sanitize!`/`sanitize_shop_domain` before use, and reject processing if the header shop cannot be corroborated by data covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., a topic whose body content the attacker fully controls, such as a custom/product webhook with attacker-created content) so Shopify delivers a request with headers:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - body: `raw_body`
2. Attacker captures `raw_body` and the valid `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a forged HTTP request directly to the app's webhook endpoint with the same `raw_body` and same `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker's parsed body, ...)`, causing the host application to act on attacker-controlled data under the victim shop's identity. [5](#0-4) [6](#0-5)
