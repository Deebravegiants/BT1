### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any actor who can obtain one valid `(raw_body, hmac)` pair for a webhook (e.g. from their own shop's installation of the same app) can replay it against the app's shared webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will report the payload as authentic and originating from the spoofed shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`shop` is a separate header value that is never part of the signed data: [2](#0-1) 

`Registry.process` verifies the request purely through `Utils::HmacValidator.validate(request)`, which recomputes the signature over `to_signable_string` (the body only) and compares it to the supplied `hmac`. It never checks that `shop` is bound to that signature: [3](#0-2) [4](#0-3) 

Once validated, `request.shop` is forwarded verbatim into `WebhookMetadata` and handed to the app's handler as the trusted tenant identifier: [5](#0-4) 

The identity binding broken here is: `hmac == HMAC(secret, raw_body)` is verified, but the value actually acted upon by the handler is `shop` (from an unauthenticated header), not `raw_body` alone. Since the app's `client_secret` (and therefore the webhook HMAC key) is shared across every shop that installs the app, a valid `(raw_body, hmac)` pair captured from one tenant's own webhook traffic remains cryptographically valid when replayed with a different `shop-domain` header — the signature says nothing about which shop it belongs to.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a malicious merchant who has legitimately installed the app on their own store can capture any webhook delivered to their own installation and replay it to the shared webhook endpoint with a forged `shop-domain` header pointing at a victim shop. `Registry.process` will accept it as authentic (HMAC passes) and invoke the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled. Any host application that uses `data.shop` to select which tenant's records to update (a documented, expected usage pattern) can be tricked into writing attacker-supplied data under another merchant's identity — a cross-tenant access/data-integrity violation.

### Likelihood Explanation
Medium: it requires the attacker to (a) run the same app on their own store to legitimately receive a signed webhook, and (b) know or predict the shared webhook endpoint URL (typically a fixed, public route). Both preconditions are realistic for any external developer/merchant who has installed a public Shopify app, making this reachable by an unprivileged internet user without needing the app's `client_secret`.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, or independently corroborate `shop` against data embedded in the signed body (e.g., a `shop_domain`/`shop_id` field parsed from `parsed_body`) before trusting it in `WebhookMetadata`. At minimum, document and enforce that consumers must cross-check `data.shop` against body content, or extend `to_signable_string`/`HmacValidator` to incorporate the shop header so that a captured signature cannot be replayed under a different tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and captures a legitimately delivered webhook request: headers include `X-Shopify-Hmac-Sha256: <hmac>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`, with some `raw_body`.
2. Attacker sends a new HTTP request to the app's shared webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and succeeds (see `lib/shopify_api/webhooks/registry.rb:190` and `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
