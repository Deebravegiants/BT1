### Title
Failed cross-contract call to the staking pool during `refresh_staking_pool_balance`/`withdraw_all_from_staking_pool`/termination flows can permanently stick `staking_information.status` at `Busy`, freezing the lockup - (File: `lockup/src/owner.rs`, `lockup/src/owner_callbacks.rs`, `lockup/src/foundation.rs`, `lockup/src/foundation_callbacks.rs`)

### Summary
This is the NEAR analog of the reported Loihi issue: an unexpected/failed response from an external system (here, the staking pool the lockup contract delegates to) can permanently lock up the calling contract because the callback that is supposed to reset the internal state machine never executes its body when the underlying promise fails.

### Finding Description
The `LockupContract` implements a simple state machine (`TransactionStatus::Idle`/`Busy`) to serialize interactions with an external staking pool contract. Every owner/foundation action that talks to the staking pool sets the status to `Busy` before firing the cross-contract call, and relies on the corresponding callback to reset it back to `Idle`: [1](#0-0) .

Most callbacks (`on_staking_pool_deposit`, `on_staking_pool_stake`, `on_staking_pool_unstake`, `on_staking_pool_withdraw`, `on_staking_pool_unstake_all`) use `is_promise_success()` to check the promise outcome and unconditionally reset the status regardless of success or failure, e.g.: [2](#0-1) .

However, several callbacks instead take a `#[callback]`-annotated parameter, which is decoded by near-sdk-rs from the promise's return value. When the promise fails, near-sdk-rs generated code panics before the function body ever executes, so the status reset logic inside the function never runs:
- `on_get_account_total_balance`, invoked from `refresh_staking_pool_balance`: [3](#0-2) 
- `on_get_account_unstaked_balance_to_withdraw_by_owner`, invoked from `withdraw_all_from_staking_pool`: [4](#0-3) 
- `on_get_account_staked_balance_to_unstake`/`on_get_account_unstaked_balance_to_withdraw`, invoked from the Foundation's `termination_prepare_to_withdraw`: [5](#0-4)  and [6](#0-5) .

If the staking pool ever fails to answer `get_account_total_balance`/`get_account_staked_balance`/`get_account_unstaked_balance` successfully (e.g., due to a bug, an incompatible upgrade of the whitelisted staking pool contract, running out of gas, or any other unexpected behavior of that external system — exactly the class of event described in the external report), the calling receipt panics entirely and `staking_information.status` remains `Busy` forever, since the status was already committed to state by the earlier (already-executed) receipt that initiated the call.

Once `status == Busy` permanently, `assert_staking_pool_is_idle()` blocks every subsequent staking-pool interaction (`deposit_to_staking_pool`, `deposit_and_stake`, `unstake`, `unstake_all`, `withdraw_from_staking_pool`, `withdraw_all_from_staking_pool`, `refresh_staking_pool_balance`, and the Foundation's `termination_prepare_to_withdraw`): [7](#0-6) . There is no owner/foundation method to force-reset `staking_information.status` back to `Idle`, so the lockup contract (and any tokens routed through the selected staking pool) becomes permanently unusable.

### Impact Explanation
This matches the "Critical — Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release... unstake-withdraw... flows" category. A single misbehaving response from the whitelisted staking pool during a routine `refresh_staking_pool_balance` or `withdraw_all_from_staking_pool` call, or during vesting termination, permanently deadlocks the state machine with no recovery path, exactly analogous to the reported Loihi assimilator lock-up.

### Likelihood Explanation
Likelihood depends on an external staking pool contract failing to respond successfully to `get_account_total_balance`/`get_account_staked_balance`/`get_account_unstaked_balance` view-style cross-contract calls — this can happen due to a staking-pool-side bug, contract upgrade incompatibility, gas exhaustion under network congestion, or any other non-malicious misbehavior, not requiring a compromised or malicious actor. Because the vulnerable calls are part of the contract's normal, routinely-used flows (`refresh_staking_pool_balance` is documented as the standard way to sync rewards), the exposure window is continuous throughout the lockup's lifetime.

### Recommendation
Use `#[callback_result]` (or check `env::promise_result`) instead of `#[callback]` for `on_get_account_total_balance`, `on_get_account_unstaked_balance_to_withdraw_by_owner`, `on_get_account_staked_balance_to_unstake`, and `on_get_account_unstaked_balance_to_withdraw`, mirroring the pattern already used in `on_staking_pool_deposit`/`on_staking_pool_unstake`, so the callback body always executes and can reset `staking_information.status` to `Idle` on failure. Additionally, consider adding an owner/foundation "force reset" / emergency-unstuck method (subject to a time-lock or confirmation window, as recommended in the original report) to recover from any residual stuck states.

### Proof of Concept
1. Owner calls `select_staking_pool` and selects a whitelisted staking pool.
2. Owner calls `refresh_staking_pool_balance()`, which sets `staking_information.status = Busy` and fires `ext_staking_pool::get_account_total_balance(...).then(ext_self_owner::on_get_account_total_balance(...))` [8](#0-7) .
3. The staking pool's `get_account_total_balance` view call fails/reverts (e.g., due to a staking-pool-side bug or incompatible upgrade).
4. Because `on_get_account_total_balance` takes a `#[callback]` parameter, near-sdk-rs generated code panics on the failed promise result before the function body (which would call `self.set_staking_pool_status(TransactionStatus::Idle)`) ever runs [3](#0-2) .
5. `staking_information.status` remains `Busy` permanently; every subsequent call to `deposit_to_staking_pool`, `unstake`, `withdraw_from_staking_pool`, `withdraw_all_from_staking_pool`, `refresh_staking_pool_balance`, or the Foundation's `termination_prepare_to_withdraw` now panics via `assert_staking_pool_is_idle()` [7](#0-6) , permanently freezing the funds routed through that staking pool.

    pub fn termination_prepare_to_withdraw(&mut self) -> Promise {
        self.assert_called_by_foundation();
        self.assert_staking_pool_is_idle();

        let status = self.get_termination_status();

        match status {
            None => {
                env::panic(b"There is no termination in progress");
            }
            Some(TerminationStatus::UnstakingInProgress)
            | Some(TerminationStatus::WithdrawingFromStakingPoolInProgress)
            | Some(TerminationStatus::WithdrawingFromAccountInProgress) => {
                env::panic(b"Another transaction is already in progress.");
            }
            Some(TerminationStatus::ReadyToWithdraw) => {
                env::panic(b"The account is ready to withdraw unvested balance.")
            }
            Some(TerminationStatus::VestingTerminatedWithDeficit) => {
                // Need to unstake
                self.set_termination_status(TerminationStatus::UnstakingInProgress);
                self.set_staking_pool_status(TransactionStatus::Busy);
                env::log(b"Termination Step: Going to unstake everything from the staking pool");

                ext_staking_pool::get_account_staked_balance(
                    env::current_account_id(),
