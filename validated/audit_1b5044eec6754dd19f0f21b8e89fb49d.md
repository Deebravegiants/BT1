Webhook `shop-domain` and `topic` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [1](#0-0) , then builds the `WebhookMetadata` object handed to the app's `WebhookHandler` directly from unauthenticated HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) [2](#0-1) . Because `Request#to_signable_string` returns only `@raw_body` [3](#0-2) , the `shop`, `topic`, `webhook_id`, and `api_version` fields exposed by `Request` [4](#0-3)  are never covered by the HMAC computed in `Utils::HmacValidator.validate_signature` [5](#0-4) . This matches the report's bug class: "a field acted on but not covered by the HMAC."

### Finding Description
The equality that should hold is:

`shop attributed to the webhook payload (used by app to select/act on tenant data) == shop that the HMAC actually authenticates`

In reality, the HMAC signature only proves "this body was produced with knowledge of `api_secret_key`" — it says nothing about which shop, topic, or webhook id that body belongs to. `Registry.process` treats `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` as if they were verified alongside the body, since it passes them straight into `WebhookMetadata` right after the HMAC check passes [6](#0-5) , with no cross-check between the header value and any signed content.

Because a webhook endpoint is a public HTTP listener, any internet user can POST directly to it, supplying arbitrary headers together with any `(body, hmac)` pair. The `api_secret_key` used to sign webhooks is shared across every shop that has installed the app (it is the app's client secret, not a per-shop secret) [7](#0-6) . An attacker who installs the target app on their own (e.g., free development) store will legitimately receive real webhooks from Shopify — each with a valid `(body, hmac-sha256)` pair signed by the app's actual `api_secret_key`. Because the `shop-domain`, `topic`, and `webhook-id` headers are not part of the signed content, the attacker can replay that exact valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain / a different registered topic. `HmacValidator.validate` will still succeed because it only recomputes the signature over `@raw_body` [8](#0-7) , and `Registry.process` will happily dispatch to the handler for the forged topic with `WebhookMetadata#shop` set to the victim's domain [9](#0-8) .

Any app logic that keys off `WebhookMetadata#shop` to look up/act on that shop's stored session, access token, or tenant data (a very common and gem-encouraged pattern, since `shop` is the only tenant identifier surfaced by the struct) will act on the wrong tenant, believing the request is authenticated for that shop because the HMAC check passed.

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who has merely installed the target app on their own store (no special privileges, no access token, no leaked credentials) can cause the app to process a forged webhook labeled as originating from a different merchant's shop. Depending on the handler's use of `data.shop`, this can be leveraged for cross-tenant actions (Critical: cross-tenant access), matching the report's underlying pattern of exploiting an identity value that travels alongside — but outside — the cryptographically verified payload.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled shop (widely available via free development stores) to harvest one legitimate `(body, hmac)` pair, and (2) direct HTTP access to the app's public webhook receiving endpoint, which is by definition internet-reachable. No secrets, tokens, or victim interaction are needed.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` into the authenticated context instead of trusting raw headers: either include them in the signed content verified against the HMAC, or independently verify `request.shop` against the set of shops actually known/installed for this app (e.g., cross-check against a stored session for that shop id) before constructing `WebhookMetadata`, rejecting the request if the header-derived shop cannot be corroborated. At minimum, document that `WebhookMetadata#shop`/`#topic` are NOT covered by the HMAC and must not be used as an authorization boundary by consuming applications.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`). Shopify delivers a real webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B` under the app's `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` (e.g., via a request logger they control, or by running their own receiving proxy).
3. Attacker sends a new POST directly to the app's webhook endpoint with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic` value that is registered on the app).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [10](#0-9) , which passes because it only checks `B` against `H`.
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [2](#0-1) , causing the app to process attacker-supplied data attributed to the victim's tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
