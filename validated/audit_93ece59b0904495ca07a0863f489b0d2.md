### Title
Truncating decimal conversion in `pallet-hyper-fungible-token` permanently traps dust on every EVM→Substrate transfer with mismatched decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` bridges tokens between EVM chains (`HyperFungibleToken`/`WrappedHyperFungibleToken` contracts) and this substrate chain. When a transfer arrives from EVM (`on_accept`) or is refunded on timeout (`on_timeout`), the pallet converts the ERC20-denominated `U256` amount into the local `Balance` type via `convert_to_balance`, which performs a floor division. Whenever `erc_decimals > local_decimals` — a configuration explicitly allowed and enforced at registration (`config.decimals >= local_decimals`) — any incoming amount that is not an exact multiple of `10^(erc_decimals - local_decimals)` loses its remainder permanently: it is neither credited to the beneficiary nor returned to the sender. This is the same rounding/dust root cause as the referenced wlsETH `burn` report (value computed via a lossy conversion between two units of account, with no way to recover the truncated remainder), except here it is a token-bridge mint/burn path reachable by any relayer delivering an ISMP message from an unprivileged EVM sender.

### Finding Description
`convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs`: [1](#0-0) 

divides by `10^(erc_decimals - local_decimals)` with plain integer division, discarding the remainder. This is called from `on_accept`: [2](#0-1) 

and from `on_timeout`: [3](#0-2) 

Registration validates only that `erc_decimals >= local_decimals`, i.e. it explicitly allows (and is the normal expected case) that the EVM side carries strictly more precision than the substrate side: [4](#0-3) 

The reverse direction (`send`, substrate → EVM) uses `convert_to_erc20`, a pure multiplication that is exact and loses nothing: [5](#0-4) [6](#0-5) 

So the asymmetry is: outgoing (local→EVM) scaling is lossless (multiply-up), but incoming (EVM→local) scaling is lossy (divide-down, floor). Every EVM-originated `Message.amount` (an arbitrary `uint256` chosen by an unprivileged EVM caller of `HyperFungibleToken.send`/`WrappedHyperFungibleToken.send`) that is not an exact multiple of the decimal scale factor causes the truncated remainder to vanish:
- For a native asset routed back from EVM, the pallet's escrow account (`pallet_account()`) is only debited by the caller pulling `amount = floor(value/scale)`; the on-chain ERC20 side already burned/locked the *full* pre-scaled amount, so the dust remains permanently un-attributable inside the pallet account (it is not owned by anyone, cannot be withdrawn by any extrinsic, and is not tracked).
- For a non-native (mint/burn) asset, `mint_into` only mints `floor(value/scale)`; the corresponding full amount was burned on the EVM side, so total cross-chain supply permanently shrinks by the dust on every transfer — an unrecoverable value leak analogous to lsETH shares being under-redeemed in the reported wlsETH bug.

This can compound: a user round-tripping funds (EVM → Substrate → EVM) will find `convert_to_erc20(convert_to_balance(x))  < x` whenever `x` isn't scale-aligned, so each round trip burns additional real value with no accounting trail and no path to reclaim it — mirroring the wlsETH report's "dust... accumulate from different users and turn into a big number" concern, except here it's silently destroyed value rather than just locked in a contract.

### Impact Explanation
This is a direct, permanent loss of user funds triggerable by any unprivileged EVM sender using the standard bridging `send` function — no privileged role, governance, or malicious relayer is required; a relayer merely delivers a legitimately-signed ISMP `PostRequest`/timeout that the protocol is designed to accept. Because `erc_decimals >= local_decimals` is a normal, expected, and validated configuration (e.g., an 18-decimal EVM token bridging to a 10- or 12-decimal substrate asset), this is not an edge case but the default operating mode for most asset pairs, and dust is lost on essentially every transfer whose amount isn't perfectly scale-aligned (which is common for interest-bearing/rebasing tokens, fee-adjusted amounts, or simply user-chosen non-round amounts). Over time this compounds into a meaningful, unrecoverable loss of backing for both native-custody assets (escrowed value stranded in the pallet account) and non-native mint/burn assets (permanent supply shrinkage / unbacked burn on the EVM side without a matching mint locally). This satisfies "permanent freezing of funds" / "unbacked mint" criteria.

### Likelihood Explanation
High likelihood: it triggers automatically on ordinary token-bridge usage whenever the registered EVM decimals exceed the local asset's decimals (an intentionally supported and common configuration) and the bridged amount is not an exact multiple of the resulting scale factor. No attacker coordination, privileged access, or unusual conditions are needed — every regular user transfer that doesn't happen to align to the scale boundary reproduces the loss.

### Recommendation
Do not silently floor-truncate the EVM→local conversion. Options:
1. Reject transfers whose amount is not an exact multiple of `10^(erc_decimals - local_decimals)` (mirroring the `BandwidthManager.sol` `PriceNotRepresentable` pattern already used elsewhere in this codebase for the same class of scaling problem), or
2. Track/accumulate the truncated remainder per asset/chain in dedicated storage and expose an extrinsic (or fold it into a later transfer) so it is eventually credited rather than permanently lost, or
3. Change the local asset's `Balance`/decimals representation to match the EVM side exactly (no precision loss possible), avoiding any scaling division on the credit path.

### Proof of Concept
1. Register asset `A` with `native = false` (mint/burn custody) and `Precisions[A][EVM-X] = 18`, while the local asset `A`'s own `decimals() = 12` (allowed since `18 >= 12` passes `ErcDecimalsBelowLocal` check in `register_token`). [7](#0-6) 
2. On the EVM chain, an unprivileged user calls `HyperFungibleToken.send(...)` (or `WrappedHyperFungibleToken.send`) with `amount = 1_000_000_000_000_000_001` (18-decimal precision, one wei above a round number), burning/locking that exact amount on the EVM contract and dispatching a `Message` with that `amount`.
3. A relayer delivers the resulting ISMP `PostRequest` to this pallet's `on_accept`. [8](#0-7) 
4. `convert_to_balance` computes `value / 10^(18-12) = value / 1_000_000`, i.e. `1_000_000_000_000_000_001 / 1_000_000 = 1_000_000_000_000` (floor), discarding the `000001` (0.000001) worth of EVM-side dust.
5. `mint_into` credits only the floored amount to the beneficiary; the extra unit of value burned on EVM is never minted anywhere on the substrate side and cannot be reclaimed by any pallet extrinsic — permanently lost. Repeating this transfer pattern (e.g., automated/high-frequency bridging, or interest-bearing token balances that are rarely scale-aligned) accumulates unbacked losses over time.

*(Note: I could not fully verify from the indexed EVM contract source, `evm/src/utils/HyperFungibleTokenImpl.sol`, whether `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` themselves perform any decimal normalization before dispatch, as the docs only reference the ABI-encoded `Message` struct and the file glob for the full send/receive Solidity implementation did not return a match in the index. If those contracts already enforce scale-alignment before dispatch, the exposure window would be narrower; a Devin session with full repo access should confirm this before treating severity as final.)*

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
