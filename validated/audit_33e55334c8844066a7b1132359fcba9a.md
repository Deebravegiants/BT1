### Title
Cross-Tenant Webhook Spoofing via Unsigned `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb](file))

### Summary
`ShopifyAPI::Webhooks::Request` derives the identity of the webhook's originating shop from the `x-shopify-shop-domain` HTTP header [1](#0-0)  but the HMAC signature that authenticates the request is computed exclusively over the raw request body [2](#0-1) . The `shop` field is never part of the signed content, so it can be freely substituted by anyone who can produce (or replay) a validly-HMAC'd body, breaking the binding `authenticated_bytes == identity_used_for_authorization`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a request by recomputing HMAC-SHA256 over `verifiable_query.to_signable_string` using the app's shared `Context.api_secret_key` and comparing it to the `hmac` field [3](#0-2) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) ; none of the `x-shopify-*` headers (topic, shop-domain, webhook-id, api-version) are included in the bytes that are cryptographically bound to the signature.

`Registry.process` trusts this unauthenticated `shop` value directly: it validates only the HMAC, then forwards `request.shop` unchanged into the handler's `WebhookMetadata` [4](#0-3) . Because `Context.api_secret_key` is a single value shared by the app across every installed shop (it's the client secret of the app, not per-shop), the same secret produces a valid signature for the same raw body regardless of which shop it is claimed to belong to. An unprivileged actor who controls a shop that has this app installed can:

1. Trigger a legitimate webhook event on their own shop (e.g., `customers/data_request`, `app/uninstalled`, `shop/update`), capturing the resulting `raw_body`, valid `hmac`, and headers sent to the app's webhook endpoint.
2. Replay that exact HTTP body (with its still-valid HMAC, since the signature never covered the shop header) to the app's public webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain.
3. `HmacValidator.validate` passes because it only checks the body bytes, and `Registry.process` dispatches the handler with `WebhookMetadata` claiming the event belongs to the victim shop [5](#0-4) .

This is the identity-binding failure named in the rules: "a shop authenticated versus the shop stored as a session key" / "a field acted on but not covered by the HMAC." The equality that should hold is `hmac_signed_bytes ⊇ {shop}`; instead `hmac_signed_bytes = {raw_body}` and `shop` is taken from an unauthenticated header, so `authenticated(shop) == false` while `handler_uses(shop) == true`.

### Impact Explanation
Any host application that keys per-tenant state (installation status, subscription/redaction flags, customer data deletion, uninstall cleanup, config values) off `WebhookMetadata#shop` as delivered by this gem can have that state corrupted for an arbitrary victim shop by a completely different, unprivileged merchant who merely has the app installed on their own store. Depending on the handler, this can manifest as cross-tenant data manipulation (e.g., forging `app/uninstalled` or `shop/redact` against a victim, or forging `customers/data_request`/`customers/redact` to trigger deletion/export flows for a shop the attacker does not own) — this satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only: (a) the attacker's own shop has the target app installed (an unprivileged, publicly available action for any Shopify merchant), and (b) the ability to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers, both trivially satisfied by an internet-based attacker with no special credentials, tokens, or social engineering. The only "secret" involved (the api_secret_key) is never exposed and isn't needed, since the attacker reuses a signature that Shopify itself already produced for their own account.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material or otherwise verify it independently of the header before dispatching. Concretely, either:
- Have `VerifiableQuery#to_signable_string` for `Webhooks::Request` include the `shop`, `topic`, and `webhook-id` header values canonically, and require Shopify's signature to cover them (this would require coordinating with Shopify's actual webhook signing scheme), or
- After HMAC validation, cross-check `request.shop` against an independently trusted source, e.g. the shop associated with the specific webhook/subscription id via a stored mapping (per-shop webhook registration records), rejecting the event if they don't match, analogous to binding `pendingPasskeyHash` inside the proof's public signal in the referenced fix.
