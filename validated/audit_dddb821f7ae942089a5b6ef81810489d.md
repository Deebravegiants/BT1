### Title
Backend-controlled `user_centric_signup` flag lets fraud-flagged signups skip the enrollment/fraud-report call - (File: src/plans/mod.rs)

### Summary
In the Reserve report, governance manipulates the RSR/RToken distribution ratio, which is computed once early (in `BackingManager`) and re-derived later (in `Distributor`), to make sure the final, consequential settlement uses a much more favorable ratio than the one that was actually supposed to apply — silently avoiding the DAO fee. The orb-core signup flow has an analogous "compute-early, decide-late" pattern: the `user_centric_signup` value is captured from the backend/app response at QR-verification time (long before fraud detection runs), and that stale value is later used to decide whether the orb should even send the fraud/enrollment outcome to the backend at all.

### Finding Description
`user_centric_signup` is read from `qr_codes.user_data.user_centric_signup` at line 573 of `src/plans/mod.rs`, captured immediately after QR code scanning/verification — well before biometric capture, the biometric pipeline, and fraud detection have run. [1](#0-0) 

The value originates from `authenticated_app_data.user_centric_signup` returned by the `user_status` endpoint, i.e. it is effectively supplied via the user-side flow (the mobile app / user QR-driven session status), not derived from the fraud-detection outcome. [2](#0-1) 

Later in the same `do_signup` function, after the biometric pipeline runs and `detect_fraud` determines `signup_reason` (`Normal`, `Failure`, or `Fraud`), the code branches on the *stale* `user_centric_signup` flag:

```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason)).await
        .is_success()
};
``` [3](#0-2) 

When `user_centric_signup == true`, the orb never calls `enroll_user`, and therefore never calls `signup_post::request`, which is the only network call that reports the computed `signup_reason` (including `SignupReason::Fraud`) to the backend. [4](#0-3) [5](#0-4) 

This mirrors the root cause of the Reserve finding precisely: a value that is supposed to gate a "settlement"/reporting action is fixed early in the flow (before the fraud outcome is even known), and a second, later decision point (whether to invoke `enroll_user`/`signup_post`) trusts that early value instead of re-checking it against the final fraud outcome. Just as in the Reserve bug — where the DAO-fee-bearing distribution step could be skipped/deferred by exploiting the split between the `BackingManager`'s and `Distributor`'s two separate ratio computations — here the backend-fraud-reporting step (`enroll_user`) can be entirely bypassed for `user_centric_signup` sessions regardless of the fraud outcome computed afterward.

### Impact Explanation
If `user_centric_signup` sessions can be induced or naturally occur alongside `SignupReason::Fraud`, the orb determines `success = false` purely locally (`signup_reason == SignupReason::Normal` evaluates to `false`) without ever notifying the backend fraud-processing pipeline via `signup_post::request`. This means:
- The backend never records the biometric data/fraud signal for that session (`enroll_user`/`signup_post` is the only channel that uploads `codes`, `signature`, and `reason: FRAUD` to the signup backend).
- Cross-signup fraud correlation, iris-code duplicate detection, and any DAO/backend-side enforcement tied to the `signup_post` call are silently skipped for every user-centric session, fraudulent or not.
- This is a state-bleed/misattribution risk: the true fraud determination is computed but never persisted or communicated, undermining fraud/liveness enforcement guarantees that depend on the backend receiving every signup outcome.

### Likelihood Explanation
The branch is gated by `user_centric_signup`, a value that is not derived from, or re-validated against, the fraud outcome; it is fixed at session-status time. Any session that legitimately (or through app-side manipulation of the session-status response) is user-centric will always take this bypass path when `ignore_user_centric_signups` is left at its default (`false`), making this reachable on the normal, unprivileged (non-operator) signup path without any special configuration.

### Recommendation
Do not gate the decision to call `enroll_user`/`signup_post` on a value captured before the fraud outcome is known. Either always call `enroll_user` (and let it internally decide what response to give the app) regardless of `user_centric_signup`, or re-validate/refresh `user_centric_signup` at the point of the final decision so it cannot silently suppress reporting of a `SignupReason::Fraud` result. At minimum, ensure `signup_post::request` (or an equivalent reporting call) is always invoked for `SignupReason::Fraud` outcomes even in the `user_centric_signup` branch.

### Proof of Concept
1. Complete QR scanning such that `qr_codes.user_data.user_centric_signup == true` (this value comes from the user/app-side session status response, captured at `src/plans/mod.rs:573`, before any biometric or fraud check).
2. Proceed through biometric capture and the biometric pipeline; suppose `detect_fraud` returns `true`, so `signup_reason = SignupReason::Fraud` (`src/plans/mod.rs:563-571`).
3. At `src/plans/mod.rs:639`, since `user_centric_signup` is `true` and `ignore_user_centric_signups` is `false` (default), the `else` branch calling `enroll_user` (and thus `signup_post::request`) is never executed.
4. The orb only sets local `debug_report.enrollment_status` to `Error` and returns `success = false` — the backend `signup_post` endpoint is never called with `reason: FRAUD`, so the backend never learns about, records, or acts on this fraud determination.
