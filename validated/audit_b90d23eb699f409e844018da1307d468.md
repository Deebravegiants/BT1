## Title
Reentrancy in `withdraw` due to external token transfer before escrow-balance decrement, with no reentrancy guard on the Tron `IntentGatewayV2` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron variant of `IntentGatewayV2` performs a low-level external call to an attacker-controllable ERC-20 `token` address before decrementing the corresponding `_orders[commitment][token]` escrow balance, and the contract has no reentrancy guard anywhere in the file. This is the same bug class as the reported `depositBribeERC20` issue: a state-mutating external call is made to caller-influenced code before the accounting variable that gates further withdrawals is updated.

### Finding Description
`withdraw` sets `_filled[body.commitment] = beneficiary` and then, for each token in the request, checks `_orders[body.commitment][token] == 0`, performs the transfer via a raw `.call`, and only afterwards subtracts the amount from storage: [1](#0-0) 

The `token` address is not restricted to a vetted allow-list — it originates from `order.inputs[i].token` supplied by any unprivileged caller of `placeOrder`: [2](#0-1) 

Because the transfer (`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`) happens before `_orders[body.commitment][token] -= amount`, a malicious ERC-20 contract used as the escrowed input token can, inside its `transfer` implementation, re-enter the gateway (e.g. via `cancelOrder`, `placeOrder`, or another externally reachable function that reads/writes `_orders[commitment][token]` for the same commitment) while the balance is still un-decremented, and extract value a second time against the same escrow entry before the original call unwinds and performs its own decrement.

This directly mirrors the reported `BribeVault.depositBribeERC20` root cause: an external call to a caller-supplied contract is interleaved with critical accounting state, rather than following checks-effects-interactions.

Compounding this, unlike the primary `evm/src/apps/IntentGatewayV2.sol`, which imports and uses `ReentrancyGuardTransient` (`nonReentrant` appears 6 times), the Tron contract imports no reentrancy guard at all: [3](#0-2) 

versus [4](#0-3) 

### Impact Explanation
`withdraw` releases escrowed value out of the gateway's pooled token balance (which can hold funds belonging to many unrelated orders). A reentrant call that exploits the un-decremented `_orders[commitment][token]` entry can drain more value than was legitimately escrowed for that commitment, at the expense of the shared pool — concrete theft of escrowed funds, matching the "Medium" severity class of the source report (fund draining via reentrancy on an escrow/vault-style contract).

### Likelihood Explanation
Reaching `withdraw` only requires: (1) placing an order with a malicious, attacker-deployed ERC20 as an input token via `placeOrder` (fully permissionless — no `DEPOSITOR_ROLE`-style restriction exists here, unlike the original report, actually making this *more* reachable than the source bug), and (2) having that order settled (filled or refunded) so that `withdraw` is invoked with the malicious token in `body.tokens`. Both are ordinary user-triggered flows already exercised in the test-suite (e.g. `IntentGatewayV2SameChainTest.sol`'s `FeeOnTransferToken`, which shows the codebase already anticipates hostile ERC-20 behavior for these code paths, but hasn't hardened `withdraw` in the Tron variant against reentrancy).

### Recommendation
Apply checks-effects-interactions in `withdraw`: decrement `_orders[body.commitment][token]` (and `delete`/reset `TRANSACTION_FEES`) before making the external `.call`/native transfer, and add a `nonReentrant` guard (mirroring `ReentrancyGuardTransient` used in `evm/src/apps/IntentGatewayV2.sol`) to the Tron contract's externally-reachable entry points (`placeOrder`, `fillOrder`, `onAccept`/`onGetResponse` paths that lead into `withdraw`).

### Proof of Concept
1. Attacker deploys a malicious ERC-20 whose `transfer(address,uint256)` re-enters the `IntentGatewayV2` (Tron) contract, e.g. calling `cancelOrder` for the same order/commitment.
2. Attacker calls `placeOrder` with this malicious token as `order.inputs[0].token`, escrowing `_orders[commitment][token] = amount` (see `evm/tron/contracts/apps/IntentGatewayV2.sol:361-385`, `440-463`).
3. Order settles and the ISMP host delivers a `RedeemEscrow`/`RefundEscrow` request, invoking `withdraw(body, ...)` at `evm/tron/contracts/apps/IntentGatewayV2.sol:691-730`.
4. Inside the loop, `token.call(...transfer...)` (line 706) triggers the malicious token's callback before line 710's decrement executes.
5. The callback re-enters (e.g. `cancelOrder`) and, seeing `_orders[commitment][token]` still non-zero, triggers a second payout against the same escrow entry.
6. The original `withdraw` call resumes and decrements the balance once, but the pool has already paid out twice for a single escrowed amount. [5](#0-4)
