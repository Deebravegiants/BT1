### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated HTTP headers that are never included in the signed material, yet they are trusted and forwarded as the tenant identifier to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` (and `topic`, `webhook_id`, `api_version`) are extracted from HTTP headers that are entirely outside that signed string: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (i.e. body only) and compares it against the `hmac-sha256` header using the app's shared `api_secret_key`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `request.shop` — an unauthenticated header value — is forwarded verbatim into `WebhookMetadata`, which host applications use to determine which merchant/tenant the payload belongs to: [5](#0-4) 

The broken identity binding is: `HMAC-SHA256(api_secret_key, raw_body) == header["hmac-sha256"]` is treated as proof that `(shop, topic, webhook_id, api_version, raw_body)` as a whole is authentic, when in fact only `raw_body` is bound to the signature. `shop` is "acted on" (used as the tenant key for routing/storing data) but not "covered" by the HMAC — the exact class of binding failure described in the ENS report, where a downstream identity/ownership decision is made using data that the signature/verification step never actually covers.

Because the same `api_secret_key` (the app's client secret) is used to sign webhooks for every shop that installs the app, any store owner who installs the app — an unprivileged action available to any internet user with a Shopify dev/partner account — receives legitimately signed webhooks for their own store. Since the HMAC never binds to the `shop-domain` header, that attacker can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` will still succeed (it only re-hashes `raw_body`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

### Impact Explanation
This is a cross-tenant vulnerability (High/Critical impact category): an attacker can make the host application process attacker-influenced webhook data (order, customer, app-uninstalled, etc., depending on which topics the attacker can generate for their own shop) under a victim shop's identity. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g. to look up/act on stored per-shop credentials or data), this can lead to cross-tenant data corruption or triggering privileged per-shop logic (such as `shop/redact` or `app/uninstalled` handling) against a shop the attacker does not own.

### Likelihood Explanation
Any internet user can create a shop/install the target app to obtain a stream of legitimately HMAC-signed webhooks. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to replay HTTP requests with a modified `shop-domain` header to the app's public webhook endpoint. The check that gate-keeps this endpoint, `Utils::HmacValidator.validate`, provably does not depend on that header at all.

### Recommendation
Include the shop domain, topic, webhook id, and api version in the HMAC-covered content used by `Request#to_signable_string` (or otherwise cryptographically bind the header values to the signature), so `Utils::HmacValidator.validate` cannot succeed unless the entire tuple `(shop, topic, webhook_id, api_version, raw_body)` presented to the handler matches what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receiving valid webhooks such as `orders/create` signed with the app's shared secret.
2. Attacker captures one such request: headers `shopify-hmac-sha256: <valid>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, plus `raw_body`.
3. Attacker replays the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `raw_body` — this passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's raw_body>, ...)`, causing the host app to process attacker-supplied data as if it originated from the victim shop.
