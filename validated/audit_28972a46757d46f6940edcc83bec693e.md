### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches handler data (`shop`, `topic`, `webhook_id`, `api_version`) that is read straight from unauthenticated HTTP headers. None of these header values are part of the signed payload, so the "shop" identity the handler receives is not cryptographically bound to the signature that authorized the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers that are never included in the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, and then forwards the unauthenticated `request.shop` value into `WebhookMetadata` which is handed to the app's handler as the tenant identity: [3](#0-2) 

`WebhookMetadata` treats `shop` as a first-class trusted field the host application is expected to use to select the tenant/session to act on: [4](#0-3) 

`HmacValidator.validate` confirms the signature is over `verifiable_query.to_signable_string` (the body) using the app's shared `api_secret_key` - a secret that is identical for every shop that has installed the app, not shop-specific: [5](#0-4) 

The identity binding that should hold is: **`shop header used by the handler == shop for which the body+HMAC pair was actually issued by Shopify`**. Because the HMAC only covers the body and the secret is shared across all shops on the app, that equality is not enforced by this code. Any party that can obtain a valid `(body, hmac)` pair signed with the app's `api_secret_key` for their own shop's events (e.g., a merchant who installs the app and triggers a real webhook for their own store, or replays a previously delivered webhook) can resend that exact body+HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers to any other value. `Registry.process` accepts it as valid because `HmacValidator.validate` only checks the body signature, and then hands the forged `shop` value to the handler as if it were authenticated.

### Impact Explanation
This breaks the shop-identity binding on which multi-tenant webhook processing depends. If a host application uses `WebhookMetadata#shop` to select which merchant's session/data store to update in response to a webhook (the documented and expected usage pattern), an attacker who controls one tenant on a shared app installation can cause the handler to process attacker-supplied body content while asserting it belongs to a different, victim shop - a cross-tenant data-integrity/injection issue. This matches the Critical "cross-tenant access" impact category, since it lets one authenticated tenant on a multi-tenant app inject data attributed to another tenant.

### Likelihood Explanation
Likelihood is Medium-High for any host app built on this gem in the common configuration (single app, many merchant installs, one shared `api_secret_key`), because:
- Any legitimate merchant that installs the app can generate a body+HMAC pair signed with the shared secret simply by triggering a real Shopify event on their own store.
- Forging the plain HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) requires no cryptographic material at all.
- The library provides no API to detect or prevent header/body mismatch; `Registry.process` performs no additional binding check beyond `HmacValidator.validate`.

### Recommendation
Bind the tenant-identifying fields into the authenticated material before trusting them, e.g.:
- Extend `VerifiableQuery`/`to_signable_string` (or add a dedicated check in `Registry.process`) to require the caller to supply the expected shop for the session/registration being processed, and reject the webhook if `request.shop` does not match a shop the caller expects to receive events from.
- At minimum, document prominently that `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are unauthenticated and must not be used for authorization or tenant selection without an out-of-band check (e.g., verifying the shop is an actual installed/active tenant before acting on the payload).
- Consider mixing the header values into the signable string check where Shopify's webhook contract allows it, or require the host app to pass the expected shop into `Registry.process` and fail closed on mismatch.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a real event (e.g., creates an order) so Shopify sends a legitimately-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (computed with the app's `api_secret_key`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` and replays it to the app's webhook endpoint, substituting the header `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `topic`/`webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes the HMAC over `B` only and finds it matches `H` — validation succeeds: [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, even though Shopify never issued this payload for `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
