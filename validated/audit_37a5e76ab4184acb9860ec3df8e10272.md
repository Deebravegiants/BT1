### Title
`validate()` allows structurally unbalanced/duplicated root `<svg>` tags because it never tracks tag nesting or root-tag count - ([File: libraries/svg-safe/src/validate.mjs])

### Finding Description
`validate()` in `libraries/svg-safe/src/validate.mjs` iterates the flat token list produced by `tokenizeFile()`/`tokenizeLine()` and, for every tag, only checks (a) that the tag name is in the `allTags` allow-list and (b) that each attribute matches a per-tag regex whitelist in `validateOption()`. [1](#0-0) 
There is no stack/depth tracking anywhere in the file: no code verifies that a closing tag (`/tag`) matches the most-recently-opened tag of the same name, that there is exactly one root `<svg>` element, or that the document as a whole is balanced. `tokenizeFile` itself is a pure lexical splitter with no notion of nesting. [2](#0-1) 
As a result, an SVG string such as `<svg xmlns="...">...</svg><svg xmlns="..."><use href="#x"/></svg>` (duplicated root) or one missing/duplicating `</svg>` passes `validate()`, since each individual `<svg .../>`, `<use .../>`, and `</svg>` token independently satisfies the allow-list/attribute checks.

This icon data flows from `assets-module.js#fetchToken`/`#fetchTokens` (custom-token registry API responses) through `#storeIcons` into `adapters/storage-icons-browser/src/utils.js#unzipIcon` (which calls `cleanup()` → `validate()`) and `adapters/storage-icons-mobile/src/icons-storage.js` (which calls `cleanupSVG`/`validateSVG`), then back out via `getIcon()`. [3](#0-2) [4](#0-3) [5](#0-4) 

However, I was unable to locate the actual rendering path where the returned icon string is inserted into the DOM/native view tree (no `dangerouslySetInnerHTML`, `SvgXml`, or similar sink was found in the indexed codebase). Whether a structurally-malformed but tag/attribute-whitelisted SVG string can actually "escape" its intended container depends entirely on how the consumer renders it (e.g., as a raw string via `innerHTML`, versus parsed into a proper DOM/React tree via `DOMParser`/JSX, versus wrapped in an `<img src="data:image/svg+xml,...">`). If rendered via `<img>` (a common, safe pattern for icons), a malformed/unbalanced SVG would simply fail to rasterize or render blank — it cannot execute script or escape the `<img>` boundary, since `<img>` does not execute embedded scripts or attach live DOM nodes from the SVG. If instead rendered as a live inline DOM fragment (e.g., `innerHTML`/React `dangerouslySetInnerHTML` or a native SVG XML parser that fails open on unbalanced tags), a duplicated/unbalanced root could produce sibling elements outside the intended single-root container in that specific DOM subtree, but even then, browsers/`DOMParser`-based renderers auto-close and self-heal malformed SVG per the HTML/XML parsing algorithm rather than "reaching outside" arbitrary DOM scope — this would be a rendering/layout glitch, not a certified path to "scriptable wallet control," since the `allTags` allow-list already excludes `<script>` and event-handler attributes, and `validateOption` allow-lists reject `<use href="http://...">` (external references) per the `use-href.svg`/`use-href-external.svg` fixtures. [6](#0-5) [7](#0-6) 

### Impact Explanation
Confirmed: `validate()` has no structural/nesting-balance invariant, so a crafted SVG with duplicated/missing root `<svg>`/`</svg>` tags or a dangling sibling `<use>` element passes validation as long as every individual tag/attribute is on the allow-list. This is a real gap relative to a "structurally valid XML" guarantee.

Not confirmed: that this structural gap is exploitable into "wallet DOM/view hierarchy" compromise or scriptable control. `validate()`'s allow-lists already block `<script>` tags, inline event handlers, and external `href`/`xlink:href` references (only local `#id` fragment refs and `data:image/png|jpeg;base64,...` are allowed), so even a structurally malformed SVG cannot smuggle script execution or network-reaching content through this validator. Without visibility into the actual DOM-insertion/rendering sink (not found in the indexed codebase — this may be due to index size limits), there is no demonstrated path from "unbalanced root tags" to unauthorized signing, secret disclosure, auth bypass, or any wallet-compromise behavior as required by the bounty rules.

### Likelihood Explanation
The precondition (return of a custom-token icon SVG from a remote registry, an "API response" per the threat model) is plausible and attacker-reachable if the token-icon submission pipeline allows arbitrary SVG bodies. However, likelihood of actual compromise is low/unproven because (a) the existing attribute allow-list already forecloses script injection and external resource loading regardless of nesting balance, and (b) no rendering sink was found in-repo that would treat a malformed/duplicated-root SVG as "reaching outside the intended icon container into the surrounding wallet DOM." The scenario as described requires a "lenient renderer" assumption that is not substantiated by any code found in this repository.

### Recommendation
Even though no concrete exploit path to wallet compromise was found, hardening `validate()`/`tokenizeFile()` to enforce structural invariants (single root `<svg>`...`</svg>`, no unbalanced/duplicated tags, stack-based matching of open/close tag names) is good defense-in-depth and closes the gap identified: maintain a tag stack while iterating tokens in `validate()`, push on open tags, pop-and-compare on close tags (`/tag`), and assert the stack is empty with exactly one top-level `svg` element at the end of iteration.

### Proof of Concept

1. `duplicate-root.svg`: `<svg xmlns="http://www.w3.org/2000/svg"><path d="M0 0"/></svg><svg xmlns="http://www.w3.org/2000/svg"><use href="#x"/></svg>` — expect `validate()` to currently NOT throw (demonstrating the gap), and assert it SHOULD throw once the fix lands.
2. `missing-close.svg`: `<svg xmlns="http://www.w3.org/2000/svg"><path d="M0 0"/>` (no `</svg>`) — same expectation.
3. `mismatched-close.svg`: `<svg xmlns="http://www.w3.org/2000/svg"><g><path d="M0 0"/></g></path></svg>` — closing tag doesn't match opening tag order.

Note this PoC only demonstrates the structural-validation gap in `validate()` itself; it does not demonstrate a reproducible wallet-compromise impact, since no rendering sink turning this into DOM escape or script execution was located in the codebase.

function tokenizeFile(raw) {
  // Splits file into xml tags or text content
  assert(typeof raw === 'string', 'tokenizeFile: raw is not a string')
  const tokens = []
  let i = 0
  while (i < raw.length) {
    let j = raw.indexOf('<', i)
    if (j === i) {
      j = raw.indexOf('>', i)
      assert(j > i, 'tokenizeFile: > expected')
      j++
    } else if (j === -1) {
      j = raw.length
    }

    tokens.push(raw.slice(i, j))
    i = j
  }

  // Verify that we missed no characters
  assert(tokens.join('') === raw, 'tokenizeFile: characters are missing')
  return tokens
}

export function validate(raw) {
  assert(typeof raw === 'string', `validate: raw is not a string`)
  assert(!/['`]/u.test(raw), `validate: "${raw}" is not valid`) // just an extra check
  for (const token of tokenizeFile(raw)) {
    if (token.trim() === '') continue
    const [tag, ...options] = tokenizeLine(token)
    assert(allTags.has(tag), `validate: invalid tag "${tag}"`)
    if (tag.startsWith('/')) assert(options.length === 0, `validate: "${tag}" starts with /`)
    for (const option of options) validateOption(tag, option.replace(/^ +/u, ''))
  }
}

import { gunzip } from 'zlib'
import { cleanup } from '@exodus/svg-safe'

export const unzipIcon = async (base64) => {
  const buff = Buffer.from(base64, 'base64')
  const unzip = await new Promise((resolve, reject) => {
    gunzip(buff, (err, res) => {
      if (err) {
        reject(err)
        return
      }

      resolve(res)
    })
  })
  return cleanup(unzip.toString('utf8'))
}
