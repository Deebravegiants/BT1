### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are excluded from the signature. `Registry.process` trusts these header-derived values once the body-only HMAC passes, so an attacker who has ever obtained one valid `(raw_body, hmac)` pair (e.g., from their own store, or by capturing any legitimately-delivered webhook) can replay that exact body/HMAC while substituting the `x-shopify-shop-domain` header for a victim shop, and the request will pass validation and be dispatched to the app's handler as if it originated from the victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all sourced from HTTP headers, which are never included in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body-bound HMAC, then immediately trusts the header-derived `shop`/`topic`/`webhook_id` to build the `WebhookMetadata` passed into the application's handler: [3](#0-2) 

The identity binding that should hold is: `hmac_valid(raw_body) == true` should imply `shop header == shop that raw_body legitimately belongs to`. In reality the HMAC only proves "this body was signed once with the app's `client_secret`" — it says nothing about which shop, topic, or webhook id that body is attached to. Because the signable string never incorporates `shop`, `topic`, or `webhook_id`, any header value can be substituted after the fact without invalidating the signature.

### Impact Explanation
This breaks the tenant boundary between shops for a multi-tenant app. An attacker who has access to any single valid `(raw_body, hmac)` pair — for instance by installing the target app for free on their own development/test store and capturing a delivered webhook (`app/uninstalled`, `customers/redact`, `orders/create`, etc.) — can resend that exact body and HMAC to the app's webhook endpoint while setting `x-shopify-shop-domain` to an arbitrary victim shop domain. `Utils::HmacValidator.validate(request)` still returns `true` because the signature only ever covered the body, and the app's `WebhookHandler` will execute with `WebhookMetadata#shop` set to the attacker-chosen victim domain. Depending on the handler's logic (e.g., data-redaction, uninstall cleanup, order/customer sync), this can result in cross-tenant data corruption or deletion attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one genuine `(raw_body, hmac)` pair, which is straightforward to obtain by installing any public app that registers webhooks on a throwaway development store (a normal, unprivileged action), then replaying it against the same app's webhook endpoint with a forged shop header. No access to `api_secret_key` or any merchant's access token is required.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them (e.g., verify the HMAC over a canonical string combining the header values and body, not the body alone). At minimum, `Registry.process` should not use header-derived `shop`/`topic`/`webhook_id` as identity for dispatch unless those fields are provably part of what was signed.

### Proof of Concept
1. Register a webhook handler and install the target app on an attacker-controlled shop (`attacker-shop.myshopify.com`) to receive one legitimate webhook delivery, capturing `raw_body` and the `shopify-hmac-sha256` header.
2. Construct a new HTTP request to the app's webhook endpoint using the exact same `raw_body` and `shopify-hmac-sha256`, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `Digest.hexencode(...)` against `to_signable_string` (`raw_body`), per `lib/shopify_api/webhooks/request.rb` lines 10-13 and 35-38.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop` equal to `victim-shop.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb` lines 188-199 — the app's business logic now executes attributing the event to the victim shop.
