### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unsigned HTTP headers while HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`, which delegates to `request.to_signable_string`. That method returns only `@raw_body`. Meanwhile, the tenant-identifying `shop` field (along with `topic` and `webhook_id`) is read from HTTP headers (`shopify-shop-domain` / `x-shopify-shop-domain`) that are never part of the signed content, and is then handed directly to the host application's `WebhookHandler#handle` as `WebhookMetadata#shop` without any cryptographic binding to that specific header value.

### Finding Description
The equality that should hold is: `shop attributed to a processed webhook == shop that the HMAC signature actually authenticates`. In this gem that equality is broken.

- `HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature and compares it against `verifiable_query.hmac`.
- For `Webhooks::Request`, `hmac` is extracted from the `shopify-hmac-sha256` header, and `to_signable_string` returns `@raw_body` only [4](#0-3) .
- The `shop`, `topic`, and `webhook_id` accessors read directly from separate, unsigned headers [5](#0-4) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` verbatim [2](#0-1) .

Because the HMAC digest is computed purely over the JSON body and the shared `client_secret`/`api_secret_key`, any request carrying a byte-identical body and a correctly-computed HMAC for that body will pass validation regardless of what value is placed in the `shopify-shop-domain` header. An unprivileged attacker who has observed (or can otherwise obtain) one legitimate webhook delivery — body + HMAC pair — for any shop (including their own store, which they fully control and can trigger webhook events on) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim tenant. The signature still validates because the header isn't part of the signed content, and the handler receives `WebhookMetadata` attributing that (attacker-chosen) data to the victim shop.

### Impact Explanation
This crosses the tenant boundary that the report criteria call out: cross-tenant confusion via an identity field (`shop`) that is acted upon by the host application but not bound by the cryptographic proof (HMAC) that is supposed to authenticate the request. Any host app that keys per-tenant business logic (e.g., updating a specific merchant's local records, deciding GDPR redaction scope for `customers/redact`/`shop/redact`, billing, entitlements) off `WebhookMetadata#shop` can be made to apply attacker-controlled webhook content to the wrong shop's data using only a body/HMAC pair the attacker can legitimately generate for their own store. This matches the report's "field acted on but not covered by the HMAC" pattern and rises to a cross-tenant data integrity issue.

### Likelihood Explanation
Requires only an unprivileged actor with a Shopify development/test store capable of triggering the same webhook topic to obtain a valid body+HMAC pair, plus control over the headers of the HTTP request delivered to the app's webhook endpoint (trivial for anyone who can send arbitrary HTTP requests to the app's public webhook route). No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the signable content (or otherwise cryptographically bind them, e.g., by having the app-level per-shop secret depend on the shop, or verifying the header values against out-of-band registered webhook metadata) so that the HMAC authenticates the full identity tuple, not just the body bytes.

### Proof of Concept
1. Attacker owns/controls Test-Shop-A and triggers a webhook topic the target app also subscribes to (e.g. `orders/create`), capturing the raw POST body `B` and the valid `shopify-hmac-sha256: H` header Shopify sent for `B` (computed with the app's shared secret, since it's the same app installed on the attacker's store).
2. Attacker crafts a new POST to the victim app's webhook endpoint with the identical body `B`, identical `shopify-hmac-sha256: H`, but headers `shopify-shop-domain: victim-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-webhook-id: <arbitrary>`.
3. `Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H` — validation succeeds.
4. `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...))` is invoked, and the host app processes attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.
