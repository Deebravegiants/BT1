### Title
Pausing a collateral asset does not stop new borrows of other assets against its stale/manipulated valuation - (File: contracts/controller/src/positions/mod.rs)

### Summary
Mirroring M-21's "pause is only forward-facing" class: `set_spoke_asset_flags`/`edit_asset_in_spoke` can mark a spoke listing `paused`, which gates entry and exit *for that asset only*. The flag is never consulted when the paused asset is used as collateral backing a *new borrow* of a different, unpaused asset in the same spoke. `validate_position_entry_gates` calls `require_can_borrow` only on each borrowed leg's `hub_asset`; the account's existing supply positions — including ones in a `paused` (or `frozen`) listing — keep contributing their stored LTV/LT stamps and their current oracle price to the health-factor check. So whatever made the guardian hit pause (a manipulated Aquarius leg, a collapsing NAV, a compromised feed) remains fully valid as collateral: the lockdown only stops future flows of that asset, not the already-recorded exposure.

### Finding Description
- `require_can_borrow` → `require_listed_unhalted_config` → `enforce_spoke_asset_flags(..., FreezePolicy::BlockOnEntry)` runs per borrowed leg only (`contracts/controller/src/positions/mod.rs:188-213`, loop at 243-252). No flag check is applied to the account's collateral legs during `borrow`.
- After the pool mutation, `enforce_post_pool_solvency` → `validation::require_post_pool_risk_gates` computes HF from `account.supply_positions` using stored `loan_to_value`/`liquidation_threshold` stamps and `cache.cached_price` for each asset — again with no `paused`/`frozen` consultation on collateral assets (`positions/mod.rs:83-91`, `risk/params.rs:44-64`).
- INV-HALT-02 / ADR-0008 document that `paused` gates "entries and exits for that spoke asset" and that seizure deliberately ignores `paused`; nothing invalidates a paused asset's collateral contribution. The docs even note "interest continues during listing pauses," confirming the design treats stored state as live.

Attack path reachable by a single unprivileged address:
1. Attacker supplies asset X and opens minimal debt (or none) while X's Aquarius/RedStone price is honest.
2. Attacker moves X's Aquarius pool price upward with their own trades (in-scope: own trades on Aquarius/Soroswap), inside the aggregator sanity band so `prices` still resolves.
3. Risk team observes the anomaly and the GUARDIAN calls `set_spoke_asset_flags(spoke, {hub, X}, paused=true, ...)` via governance `execute` — the intended lockdown.
4. Attacker calls controller `borrow(caller, account_id, spoke_id, assets=[{hub,Y}], to=attacker)` for any other listed asset Y. The flag check only inspects Y's listing; X's `paused` flag is irrelevant, and the inflated X price still satisfies HF.

### Impact Explanation
The pause fails to contain the very state it was meant to freeze. An attacker can extract new borrows (real tokens leaving the pool) against collateral whose valuation motivated an emergency flag — i.e., borrows that would have been rejected had the pause actually invalidated the suspect collateral. This is direct theft of pool funds / protocol insolvency when the inflated collateral value is fictitious. Even absent manipulation, a paused-because-broken feed leaves HF computed on a price the protocol itself has flagged as untrustworthy.

### Likelihood Explanation
Requires the pause to be motivated by price/collateral integrity (exactly the scenario the report describes: "if we want to pause an asset, something fishy has already occurred"). The window exists from flag-set until either the position is liquidated (still allowed — `SeizureLeg` only checks `no_seize`) or prices normalize. Medium likelihood, conditional on an incident in progress; the borrowing leg itself is trivially permissionless.

### Recommendation
When a listing is `paused` (and arguably `frozen`), exclude that asset's supply positions from collateral valuation in `calculate_account_risk_totals`/`require_post_pool_risk_gates`, or at minimum reject `borrow`/`multiply`/`flash_position` for accounts holding the paused asset. The per-leg-only flag check in `validate_position_entry_gates` should be complemented by a collateral-side scan so that a lockdown is not purely forward-facing. Note this must be weighed against liquidations still needing to read the paused collateral's value (seizure leg already handles this via `SeizureLeg`).

### Proof of Concept
1. `supply(caller=attacker, account_id=0, spoke_id=S, assets=[{hub, X, amount}])` — succeeds, position stamps stored.
2. Attacker swaps on Aquarius pool for X to push its computed USD price up within `[min_sanity_price_wad, max_sanity_price_wad]`.
3. Guardian: governance `set_spoke_asset_flags(caller=guardian, spoke_id=S, hub_asset={hub,X}, paused=true, frozen=false, no_seize=false)` — lands immediately (ratchet, no timelock).
4. `supply`/`withdraw`/`repay` on X now revert `SpokeAssetPaused` (#315), confirming the lockdown is active.
5. `borrow(caller=attacker, account_id=A, spoke_id=S, assets=[{hub, Y, amount}], to=attacker)` — `require_can_borrow` checks only Y's flags; the post-pool HF gate credits X at the manipulated price and stored stamps. Call succeeds and Y is paid out.
6. Result: fresh debt drawn against collateral the protocol explicitly halted — identical in shape to `getPrice()` still serving the pre-pause malicious TWAP in M-21.

Uncertainty: this assessment relies on `validate_position_entry_gates` iterating only the borrowed `aggregated` legs and on `require_post_pool_risk_gates` not consulting flags for collateral legs — the former is verified in `positions/mod.rs`; the latter is inferred from the documented invariant set (INV-HALT-02 enumerates the only flag gates) rather than a direct read of the full risk-totals function body, which was not fully retrieved within the iteration budget. If `calculate_account_risk_totals` internally skips flagged listings, the finding collapses.
