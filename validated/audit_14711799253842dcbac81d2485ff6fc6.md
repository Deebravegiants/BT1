## Title
Unchecked zero-length body indexing in `IntentGatewayV2.onAccept` causes out-of-bounds panic, permanently blocking message delivery - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

## Summary
`IntentGatewayV2.onAccept` reads `incoming.request.body[0]` to determine the `RequestKind` before any length validation or source authentication is performed. A cross-chain `PostRequest` delivered through the ISMP `HandlerV2`/host pipeline with an empty `body` causes Solidity's array-index bounds check to revert the entire delivery transaction with a `Panic(0x32)` (array out-of-bounds access) — the same root-cause class as CVE-2016-5316 (an out-of-bounds read on attacker-crafted input reaching a parsing routine before validation), except here the "read" is bounds-checked by the EVM and manifests as a hard revert rather than memory corruption.

`incoming.request.body[0]` is indexed unconditionally, with no `body.length > 0` guard, and *before* `authenticate(incoming.request)` is called for the branches that do authenticate. Any account can dispatch a cross-chain `PostRequest` on a supported source chain whose `to` field targets this contract's address; once relayed and proven via the destination `HandlerV2`/consensus client, `onAccept` is invoked by `onlyHost` with attacker-controlled `body` bytes, including a zero-length body. This mirrors the CVE-2016-5316 bug class: a length-derived read/index performed on attacker-supplied data ahead of validation, causing the routine handling that data to fail/crash on malformed input.

## Impact Explanation
A relayer that successfully proves and submits such a malformed message to the host will have the `onAccept` call revert with an EVM panic. Because the message was already consumed/marked as delivered at the point `HandlerV2` invokes the module callback (the standard ISMP delivery flow calls `IIsmpModule.onAccept` and any revert there propagates through and reverts the whole handling transaction for that request), a message targeting `IntentGatewayV2` with an empty body cannot be delivered — matching the accepted impact category "a route unable to deliver messages." This does not corrupt state or directly steal funds, but it lets any unprivileged party craft an undeliverable message against this specific application endpoint, and depending on how `HandlerV2` batches messages, a single malformed request can also cause the revert of the surrounding batch, denying delivery of well-formed sibling messages in the same transaction.

## Likelihood Explanation
High feasibility: dispatching a cross-chain `PostRequest` with an empty body to an arbitrary destination address (including `IntentGatewayV2`) requires no special privilege — it is the same permission level as any legitimate order message. The only additional requirement is that the message actually be relayed and proven, which is routine relayer behavior and does not require the relayer's cooperation with intent — any relayer processing the mempool/queue would trigger this.

## Recommendation
Validate `incoming.request.body.length > 0` at the top of `onAccept` before indexing `body[0]`, returning/reverting with a typed error (e.g. `EmptyRequestBody()`) instead of relying on the implicit array-bounds panic. Apply the same guard to `onGetResponse`'s `incoming.response.values[0]` access, and audit other `body[1:]`/`body[0]` accesses across the `IApp` implementations in this repo for the same missing length check.

## Proof of Concept
1. On a supported source chain, any address calls the local ISMP dispatcher/host to send a `PostRequest` with `to = <IntentGatewayV2 address on dest chain>`, `body = ""` (zero bytes), and a normal fee/timeout.
2. A relayer proves and submits this request through the destination `HandlerV2`.
3. `HandlerV2` invokes `IntentGatewayV2.onAccept(incoming)` with `incoming.request.body.length == 0`.
4. Execution reaches `RequestKind(uint8(incoming.request.body[0]))`; Solidity's implicit bounds check on `bytes calldata` indexing reverts with `Panic(0x32)`.
5. The handling transaction reverts, and the message is not delivered — reproducible deterministically for any zero-length body targeting this contract, without requiring any secret or privileged role.

**Uncertainty note:** I could not fully trace `HandlerV2`'s exact delivery-loop semantics (e.g., whether a single message revert aborts an entire batch, and whether IntentGatewayV2 is the only affected `IApp`) within the available search budget — this would require reading `HandlerV2.sol`'s `handlePostRequests` implementation directly, which the index did not surface completely. A Devin session with full repo access should verify the exact batching/blast-radius behavior before treating this as more than a per-message DoS.
