### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant shop spoofing via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers that are never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` when building the `WebhookMetadata` passed to the app's handler, even though that field carries no cryptographic binding to the HMAC that was just verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read straight from a header with no relation to the signed bytes: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the received `hmac`: [3](#0-2) 

`Registry.process` calls this validator and, on success, forwards `request.shop` — an unverified header — directly to the app's webhook handler as the tenant identifier: [4](#0-3) 

This is the same binding gap described in the external report (an amount not checked against what is authorized): here, the *shop* value acted upon by the handler is not covered by the equality that the HMAC is supposed to guarantee. Concretely: `HMAC_valid(raw_body)` is verified, but `shop_used_by_handler == shop_header` is never checked against anything the HMAC covers. Compare this to `Auth::Oauth::AuthQuery`, where `shop` **is** explicitly included in `to_signable_string` and therefore is bound by the HMAC: [5](#0-4) 

Because the same `api_secret_key` is shared across every shop/install of a given app, any actor who can obtain one genuine `(raw_body, hmac)` pair (e.g., by triggering a webhook on their own shop, or replaying a captured one) can resend that exact body/HMAC pair while swapping the `x-shopify-shop-domain` header to a victim shop's domain. `Registry.process` still validates because the HMAC only checks the body, and the forged `shop` is passed straight into `WebhookMetadata` for the handler to act on.

### Impact Explanation
If the consuming application uses `WebhookMetadata#shop` (as documented/intended) to key persistence, cache invalidation, or trigger tenant-scoped side effects, this allows cross-tenant data confusion/injection: a request that Shopify never actually sent for the victim shop is processed as if it were an authentic webhook for that shop, with a valid-looking HMAC. This matches the "cross-tenant access" Critical impact bucket, since the trust boundary between shops in a multi-tenant app is broken purely through this gem's webhook verification logic.

### Likelihood Explanation
Exploitation requires only: (1) that the attacker's own shop has installed the app (to legitimately trigger any webhook and capture a valid `(body, hmac)` pair for a topic/body they control or can predict), and (2) that the app processes webhooks with this gem's `Registry.process`/`Request`. No access to `api_secret_key`, tokens, or TLS interception is needed — only the ability to relay an HTTP request with modified headers, which is fully within reach of an "unprivileged internet user" who is merely a legitimate installer of the app on their own store.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signed/verified content, or otherwise cryptographically bind them to the HMAC check — e.g., verify the HMAC over `raw_body + shop + topic` (matching Shopify's actual webhook signing semantics if it already covers these), and have `Registry.process` reject requests where the `shop` header cannot be validated against the same secret/signature used for the body. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant identifier without independent verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`) with a body they control (`{}` is sufficient), obtaining a valid `x-shopify-hmac-sha256` value computed by Shopify over that raw body using the app's shared `api_secret_key`.
2. Attacker (or a script replaying the captured request) resends the identical raw body and `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `@raw_body` — this passes because the body/HMAC pair is genuinely valid: [6](#0-5) 
4. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and a valid signature status, despite Shopify never having sent this webhook for that shop.
