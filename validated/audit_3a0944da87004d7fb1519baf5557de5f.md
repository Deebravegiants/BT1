### Title
Webhook `shop-domain` Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop-domain` header — which is *not* part of the signed material — as the tenant identity used to dispatch the event to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator` computes the signature exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

The `shop` (`shopify-shop-domain`/`x-shopify-shop-domain` header), `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers and are never included in the signed bytes: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then immediately trusts `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

The identity binding the gem implicitly claims to enforce is: *"the shop that authored this webhook body" == "the shop named in the `shop-domain` header."* Because the header is excluded from the HMAC, this equality is never actually checked — only "the body bytes were signed by someone holding `api_secret_key`" is verified, and that someone can be any shop that has installed the app (i.e., any tenant able to trigger a webhook delivery for its own store, which is unprivileged, ordinary merchant activity, not a leaked/privileged credential).

### Impact Explanation
An attacker who operates their own (attacker-owned) shop with the app installed can capture a legitimate `(raw_body, hmac)` pair delivered to the app's public webhook endpoint for their own store, then resend that exact `(raw_body, hmac)` pair to the same endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. Since `HmacValidator.validate` only checks the body against the header-independent HMAC, the replayed request still validates successfully. The app's handler receives `WebhookMetadata` with `shop` set to the attacker-chosen victim domain, causing the app to process, store, or act on that webhook as if it originated from the victim tenant — a cross-tenant confusion/access primitive within the app's own request-processing surface, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (ordinary onboarding, not a privileged action), (2) capturing a webhook delivery aimed at the app's public endpoint (the endpoint URL is typically fixed/discoverable), and (3) resending it with a modified header, no cryptographic secret or credential theft needed. This is a plausible, moderate-effort attack path fully within the unprivileged internet-user threat model.

### Recommendation
Bind the asserted tenant identity to the authenticated bytes: include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable string in `Request#to_signable_string`, or independently cross-check the header-derived shop against a shop identifier embedded in the signed body/payload before dispatching to handlers, so that the shop used for authorization equals the shop actually covered by the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook topic (e.g. `orders/create`) targeted at the app's registered public webhook URL.
2. Attacker intercepts/records the delivered POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because it was genuinely computed by Shopify with the shared `api_secret_key`).
3. Attacker resends `POST /webhooks` with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H`, so validation passes.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to treat the payload as belonging to `victim-shop`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
