### Title
Missing base58Check checksum verification in `validateDogeAddress` allows funds to be sent to a non-existent/wrong Dogecoin address - (`packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateDogeAddress` only checks the address against a permissive regex `/^[DA][1-9A-HJ-NP-Za-km-z]{25,33}$/` and never decodes/verifies the base58Check checksum, unlike every other base58 chain validator in the same file (`validateBtcBase58Address`, `validateLitecoinBase58Address`, `validateTronBase58Address`, `validateDashAddress`). Any string that merely matches the character class and length range — including a mistyped/garbled address with a different or invalid checksum — is accepted as a valid Dogecoin destination and flows unchanged into the signed withdrawal intent.

### Finding Description
The broken equality is: **the (chain, address) pair the SDK approves via `validateAddress` == a real, checksummed Dogecoin address that decodes to an actual public-key/script hash**. For every other base58-based chain implemented in this file, that equality is enforced by decoding the base58 payload and recomputing the double-SHA256 checksum, e.g. `validateBtcBase58Address` [1](#0-0)  and `validateDashAddress` [2](#0-1) .

`validateDogeAddress`, however, is reduced to a bare regex test with no decoding step at all: [3](#0-2) 

This function is reached from the dispatcher in `validateAddress` for `Chains.Dogecoin` [4](#0-3) .

The withdrawal path calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` inside `PoaBridge.validateWithdrawal` and only throws if it returns `false`: [5](#0-4) . For Dogecoin there is no follow-up chain-specific check analogous to the XRPL account-info lookup performed a few lines later for `Chains.XRPL` [6](#0-5) , so an address that passes the regex but fails checksum verification proceeds straight into `createWithdrawIntentPrimitive` unchanged.

Root cause: the regex `/^[DA][1-9A-HJ-NP-Za-km-z]{25,33}$/` only constrains the base58 alphabet and rough length; it accepts a huge superset of strings that are not valid base58Check-encoded Dogecoin payloads (wrong length after decode, wrong version byte, or — most importantly for the attack described — correct length/version but a checksum mismatch caused by a single flipped/typo'd character). Because there is no `base58.decode` + double-SHA256 checksum comparison, a single-character typo that still satisfies the regex is indistinguishable from a genuine address.

### Impact Explanation
An attacker (or an ordinary user's own typo, or a counterparty-supplied `destinationAddress` an integrator forwards unchecked) can cause `validateAddress` to approve a Dogecoin string that is not a decodable, checksummed address. This string is embedded verbatim into the `WITHDRAW_TO` memo of the signed `ft_withdraw` intent produced by `createWithdrawIntentPrimitive`, so the user ends up authorizing/signing a withdrawal to a destination that does not correspond to any real, checksum-valid wallet. Funds sent to such an address on a UTXO chain like Dogecoin are unrecoverable. This matches the Critical category: "funds delivered to a wrong/unrecoverable address... user's own funds."

### Likelihood Explanation
Preconditions are minimal and require no special privileges: route = `PoaBridge`, `assetInfo.blockchain === Chains.Dogecoin`, and a `destinationAddress` string that matches the regex but has an invalid checksum (e.g., one flipped base58 character in an otherwise real address, which still satisfies the character class/length constraints in the overwhelming majority of cases since checksum-breaking edits rarely change length or leave the alphabet). This is trivially reproducible by any caller of the public withdrawal API and requires zero cost beyond crafting the string.

### Recommendation
Rewrite `validateDogeAddress` to decode the address with `base58.decode`, verify total length is 25 bytes (version + 20-byte hash160 + 4-byte checksum), verify the version byte matches Dogecoin's known mainnet prefixes (0x1E for P2PKH `D...`, 0x16 for P2SH), and recompute/compare the double-SHA256 checksum — mirroring the pattern already used in `validateBtcBase58Address`, `validateLitecoinBase58Address`, `validateTronBase58Address`, and `validateDashAddress` in the same file.

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
```

export function validateDashAddress(address: string): boolean {
	try {
		const decoded: Uint8Array = base58.decode(address);

		// version (1) + payload (20) + checksum (4)
		if (decoded.length !== 25) return false;

		const version = decoded[0];
		if (
			version !== 0x4c && // P2PKH
			version !== 0x10 // P2SH
		) {
			return false;
		}

		const payload = decoded.subarray(0, 21);
		const checksum = decoded.subarray(21, 25);

		const hash1 = sha256(payload);
		const hash2 = sha256(hash1);
		const expectedChecksum = hash2.subarray(0, 4);

		for (let i = 0; i < 4; i++) {
			if (checksum[i] !== expectedChecksum[i]) return false;
		}

		return true;
	} catch {
		return false;
	}
```
