### Title
Unauthenticated `/sessions` login endpoint leaks distinct error messages that enable user email/account enumeration - ([File: core/web/sessions_controller.go])

### Summary
The Liferay CVE-2021-33321 describes an insecure default where the "forgot password" flow returns distinguishable responses for existing vs. non-existing emails, letting an unauthenticated attacker enumerate valid user accounts. The chainlink node's local login endpoint (`POST /sessions`) exhibits the same class of bug: an unauthenticated caller can distinguish "email doesn't exist," "email exists but password wrong," and "email exists and has MFA enabled" by observing different error responses, without needing any credentials.

### Finding Description
`SessionsController.Create` in [1](#0-0)  is reachable by an unauthenticated client and performs two email-existence checks before authentication succeeds:

1. It first calls `GetUserWebAuthn(ctx, sr.Email)` to check for MFA registration, and only populates WebAuthn session data if tokens exist [2](#0-1) .
2. It calls `CreateSession(ctx, sr)` and, on any failure, directly relays the underlying Go error object to the HTTP client via `jsonAPIError(c, http.StatusUnauthorized, err)` [3](#0-2) .

The underlying `CreateSession` implementation in `localauth/orm.go` returns semantically distinct errors depending on account state:
- If `FindUser` fails to find the email, it returns that raw lookup error immediately [4](#0-3) .
- If the email exists but doesn't match (case-insensitive constant time compare fails, which can only happen due to normalization edge cases since `FindUser` already matched it), it returns `"Invalid email"` [5](#0-4) .
- If the email matches but the password is wrong, it returns `"Invalid password"` and logs an audit event distinctly named for a password mismatch (as opposed to email mismatch) [6](#0-5) .
- If the email/password are correct but the account has MFA enrolled and no WebAuthn attestation was sent, the function returns a JSON-serialized WebAuthn challenge object as the error string itself [7](#0-6) .

Because `jsonAPIError` forwards the error text to the client (confirmed by the same pattern of returning literal message text such as `"old password does not match"` back to callers elsewhere in this codebase, e.g. [8](#0-7) ), an unauthenticated attacker submitting different emails to `/sessions` can distinguish:
- Non-existent email → generic lookup error.
- Existing email + wrong password → `"Invalid password"`.
- Existing email with MFA enabled → a WebAuthn challenge JSON blob (proves the account exists and has 2FA configured) surfaces before any password check would need to succeed on subsequent legitimate calls; combined with the WebAuthn probe in step 1, the number of registered tokens is also observable.

This is directly analogous to the Liferay bug class (CWE-640, "weak password recovery mechanism" / account enumeration through differential responses on an unauthenticated endpoint) — here manifesting on the authentication endpoint itself rather than a password-reset endpoint, but with the same unprivileged-actor reachability and impact (email/account enumeration).

### Impact Explanation
An external, unauthenticated actor can enumerate valid admin/API usernames (emails) on an exposed chainlink node UI/API, and additionally learn whether MFA is enabled for a given account. This information supports targeted credential-stuffing, phishing, or brute-force attacks against confirmed-valid accounts and undermines any assumption that account existence is confidential. It does not by itself grant authentication bypass or fund movement, matching the "no impact beyond confidentiality of account existence" profile of CVE-2021-33321 (CVSS C:H/I:N/A:N).

### Likelihood Explanation
Likelihood is high for exposed nodes: the `/sessions` endpoint is unauthenticated by design (it's the login endpoint) and reachable directly by any network client with access to the operator UI/API, requiring no privileges, no social engineering, and no rate-limiting bypass beyond simple repeated requests.

### Proof of Concept
1. Send `POST /sessions` with `{"email":"nonexistent@test.com","password":"x"}` — observe generic/lookup-failure error.
2. Send `POST /sessions` with `{"email":"<known-valid-admin>@node.com","password":"wrongpwd"}` — observe `"Invalid password"` error, confirming the email exists.
3. If the valid account has WebAuthn/MFA enrolled, repeat step 2 with correct password and no `webAuthnData` — the response body contains a JSON WebAuthn challenge object, confirming both valid credentials and MFA status without completing login.

This flow lets an attacker iterate over a candidate email list and classify each as nonexistent / existing-wrong-password / existing-with-MFA purely from response content, which is the enumeration bug class flagged in the Liferay advisory.

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
