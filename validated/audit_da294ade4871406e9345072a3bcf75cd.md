Confirmed: `EvmHost.dispatch(DispatchPost)` at `evm/src/core/EvmHost.sol:936-944` sets `request.from = abi.encodePacked(_msgSender())` — i.e., `from` is set to whatever contract called `dispatch()` on the *source chain's* host, entirely under the caller's control (any attacker can deploy an arbitrary contract and dispatch a message as itself). There is no cryptographic tie between `from` and the honest gateway other than the address value itself, so authentication in receiving apps must rely on validating `(source chain, from address)` against an explicit allow-list — which is exactly what `authenticate()` in the Tron `IntentGatewayV2` fails to do.

### Title
Insecure fallback in `IntentGatewayV2.instance()` lets an unregistered source chain authenticate as a known peer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` on the Tron build resolves a `stateMachineId` to a trusted peer-gateway address, but when no peer is registered for that chain it silently falls back to `address(this)` instead of reverting. `authenticate()` uses this value to gate the only two privileged inbound actions (`RedeemEscrow`, `RefundEscrow`). Because `PostRequest.from` is fully attacker-controlled on the source chain (set to `msg.sender` by `EvmHost.dispatch`), an attacker who deploys any contract at the vulnerable gateway's own address on an unregistered-but-ISMP-connected state machine can satisfy `authenticate()` and trigger escrow withdrawal logic that should only be reachable from a genuine, governance-registered `IntentGatewayV2` peer.

### Finding Description
`instance()`/`authenticate()`: [1](#0-0) 

Compare with the canonical (non-Tron) implementation, which reverts instead of falling back: [2](#0-1) 

`authenticate()` is the only gate protecting the withdrawal path: [3](#0-2) 

`request.from` is attacker-controlled: `EvmHost.dispatch()` sets it to the caller of `dispatch()`, not to any registered/verified peer identity: [4](#0-3) 

Because `instance(request.source)` returns `address(this)` for any chain that was never explicitly added via `NewDeployment`, `authenticate()`'s check `instance(request.source) != module` becomes `address(this) != module`. An attacker who deploys (e.g. via `CREATE2` with matching bytecode/salt, or simply by being first to deploy at that address on a chain nobody has claimed) a contract at the exact address of the victim `IntentGatewayV2` on any state machine whose consensus Hyperbridge already verifies but that was never registered as a peer for *this* gateway, can dispatch a `PostRequest` with `from = address(this)` and an arbitrary `source` (the unregistered chain). This request will pass `authenticate()` and be treated as coming from a "known instance," even though no governance action ever registered that chain.

This mirrors the zrok SSRF bug class precisely: a lookup/resolution function meant to authenticate a request against a fixed, pre-registered target instead defaults to trusting the caller's own identity when the lookup misses, letting attacker-supplied context (the unregistered `request.source`) silently override the intended trust boundary.

### Impact Explanation
`onAccept` uses `authenticate()` to gate `RedeemEscrow`/`RefundEscrow`, which release escrowed order funds (`withdraw()`), per the `onAccept` dispatch logic: [5](#0-4) 

A forged "known instance" authentication lets an attacker request the release of escrowed order tokens (`WithdrawalRequest`) that were never legitimately filled/refunded on a real peer chain, i.e., theft of escrowed user funds from the IntentGateway. This satisfies "concrete theft ... of funds" per the validation criteria, and is reachable from a single dispatched ISMP message — no governance, admin, or relayer collusion required beyond permissionless message delivery (`HandlerV2.handlePostRequests`/`dispatchIncoming`, which is explicitly permissionless).

### Likelihood Explanation
The attacker needs to (a) control a contract whose address matches the victim gateway's address on some ISMP-connected chain not registered as a peer, and (b) craft a plausible `WithdrawalRequest` body referencing an existing order commitment with non-zero escrow. Address-matching via `CREATE2` replay across EVM-compatible chains is a well-documented, practical technique (identical deployer, salt, and init code reproduce the same address on any chain), making (a) achievable without any privileged access. Delivery of the forged message only requires a standard, permissionless relay through `HandlerV2`. This is assessed as Medium-High likelihood, gated mainly by whether the specific deployment addresses can be replayed on a chain within Hyperbridge's supported consensus set.

### Recommendation
Change `IntentGatewayV2.instance()`/`authenticate()` on the Tron contract to match `IntentsBase._instance()`: revert with `UnknownInstance()` (or equivalent) when `_instances[keccak256(stateMachineId)] == address(0)`, rather than falling back to `address(this)`. Audit all other Tron-specific divergences from `IntentsBase.sol` for similar silently-permissive fallbacks.

### Proof of Concept
1. Attacker identifies the exact contract address `G` of the victim `IntentGatewayV2` deployment (public knowledge).
2. Attacker deploys an arbitrary contract at address `G` via `CREATE2` (same deployer/salt/bytecode) on any EVM state machine `X` whose consensus Hyperbridge tracks but which was never added to `G`'s `_instances` map (i.e., no `NewDeployment` was ever processed for `X`).
3. From that contract on chain `X`, attacker calls `IDispatcher(host).dispatch(DispatchPost{ dest: <victim chain>, to: abi.encodePacked(G), body: abi.encodePacked(uint8(RequestKind.RefundEscrow), abi.encode(WithdrawalRequest{ commitment: <existing order commitment>, tokens: <order tokens>, beneficiary: attacker }))})`. `EvmHost.dispatch` sets `request.from = abi.encodePacked(G)` automatically since attacker's contract is deployed at `G`.
4. A relayer (or the attacker itself, permissionlessly) delivers this via `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `IntentGatewayV2.onAccept`.
5. `authenticate()` computes `instance(X)`; since `X` is unregistered, it returns `address(this) == G`, matching `request.from == G`, so authentication passes.
6. `withdraw()` executes, releasing escrowed tokens for the referenced commitment to the attacker-chosen beneficiary — funds theft without ever having a legitimate peer registered on chain `X`.
