### Title
Webhook `shop`/`topic` Headers Are Not Covered by the HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only covers the raw request body. The `shop-domain` and `topic` headers used to identify the tenant and dispatch the handler are never included in the signed material, so they can be freely modified by anyone who can produce a body/HMAC pair that is valid for the app's secret.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches to a handler using `request.topic` and passes `request.shop` straight into `WebhookMetadata` without any additional binding check between the signed body and the claimed shop/topic: [3](#0-2) 

The documented integration pattern instructs host apps to pass raw headers directly from the inbound HTTP request into `Request.new`, and to trust `data.shop`/`data.topic` in the handler as the tenant identity for the webhook, e.g. enqueuing background work keyed by `shop_domain: data.shop`: [4](#0-3) [5](#0-4) 

The identity binding that is broken is: `shop header authenticated by HmacValidator == shop header used to attribute webhook data to a tenant`. In fact `HmacValidator.validate` proves nothing about the `shop-domain` header — it only proves the *body bytes* were signed by someone possessing `Context.api_secret_key` (i.e., Shopify, for *some* webhook, to *some* shop running this same app). Because the same `api_secret_key` is shared across every shop installed on a given app, and the signature covers only the JSON body, any webhook payload/HMAC pair that Shopify legitimately delivered for one shop remains a **valid HMAC signature for that identical body no matter what `shop-domain` and `topic` headers are attached to it**. An attacker who can obtain (or predict) one such (body, hmac) pair — e.g. by installing the app on a shop they control and capturing a webhook delivery to their own endpoint, or by intercepting/observing a delivery — can resend that exact body/HMAC with a different `x-shopify-shop-domain` header. `Registry.process` will accept it as valid and hand `WebhookMetadata(shop: <attacker-chosen-shop>, body: <replayed-body>, ...)` to the app's handler.

### Impact Explanation
Any handler that uses `data.shop` from `WebhookMetadata` to decide which tenant's data to mutate (delete customer data, deprovision on `app/uninstalled`, update order/product records, etc. — exactly the pattern shown in this gem's own documentation) can be made to act on the wrong shop's identifier while using attacker-supplied or replayed body content. This is a cross-tenant integrity issue: the gem's `Registry.process` gives the false assurance that "the request did indeed come from Shopify" for the claimed shop/topic (per the gem's own docs), when in reality only the body bytes are authenticated, not the tenant attribution. This satisfies the "cross-tenant access" impact category, since a request nominally scoped to Shop A's webhook delivery can be relabeled to Shop B and processed as if it belonged to Shop B by the host application's handler, using only information the gem itself hands the handler as trusted.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimate (body, HMAC) pair signed with the target app's `api_secret_key`. In the most direct scenario, an attacker who has installed the app on their own shop (a normal, unprivileged action for any Shopify merchant/developer) automatically receives HMAC-signed webhook deliveries for their own shop and topic. They can replay that exact body+HMAC to the app's webhook endpoint with the `shop-domain` (and/or `topic`) header changed, without needing the `api_secret_key`, an access token, or any privileged position. The likelihood is therefore realistic for any app whose webhook handler trusts `data.shop`/`data.topic` for tenant/topic dispatch, as documented.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the signed material (or otherwise cryptographically verify them) instead of trusting raw headers, for example by including these header values as part of `to_signable_string`, or by requiring the host app to independently corroborate the `shop-domain` header against a known, previously-established session/shop record before invoking the handler. At minimum, document prominently that `data.shop`/`data.topic` in `WebhookMetadata` are not covered by the HMAC and must not be treated as authenticated tenant/topic identifiers on their own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any unprivileged Shopify merchant can do this) and registers/receives a legitimate webhook delivery, e.g. `orders/create`, capturing the raw body `B` and the resulting `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify using the app's `api_secret_key`, which the attacker does not need to know).
2. Attacker sends a POST to the app's webhook endpoint with the exact same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`, if the topic dispatch is also desired to differ).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because `compute_signature(body, secret) == H` (the body was not modified) — see `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) looks up the handler by `request.topic` and calls it with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)`.
5. The host app's handler — following the pattern from `docs/usage/webhooks.md` lines 19-29 — performs an action attributed to `victim-shop.myshopify.com` using data that was never actually sent by or about that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
