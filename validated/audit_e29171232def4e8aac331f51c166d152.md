### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, then hands the handler a `shop` value taken directly from an HTTP header. That header is never included in the bytes that are HMAC-verified, so the "verified" property (the HMAC) and the property the handler actually trusts (the shop identity) are decoupled — the same root-cause pattern as `RewardsEngine` clearing `unitsAccrued` without also clearing the paired `rewardDebt` baseline.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers and are not part of the signed string: [2](#0-1) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` gates entirely on that HMAC check, then forwards the *unverified* `request.shop` header straight to the app-supplied handler as the tenant identifier: [4](#0-3) 

This is the exact analog of the reported bug: the invariant that should hold is `shop-that-produced-hmac == shop-header-trusted-by-handler`. The library only checks `hmac(body) == hmac`, but never binds `shop` (or `topic`/`webhook_id`) into that computation, so the "cleared/reset" side (HMAC validity) and the "baseline" side (tenant identity used downstream) can diverge — just like `unitsAccrued` and `rewardDebt` diverging when one is reset without the other.

Compounding this, the library's own documentation asserts a stronger guarantee than what is actually enforced: "This will verify the request did indeed come from Shopify" with no caveat that only the body — not the shop/topic/webhook-id headers — is authenticated: [5](#0-4) [6](#0-5) 

A developer following the documented `data.shop`/`data.topic` contract has no indication these fields require independent verification, so they will reasonably treat them as authenticated tenant/topic identifiers, exactly as `data.shop` is used in the documented example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

### Impact Explanation
An unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair for a given topic — trivially, by installing the app on their own free/dev store and capturing a webhook they legitimately received — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header for a victim shop. `HmacValidator.validate` still succeeds because it never reads those headers, so `Registry.process` dispatches to the handler with `shop` set to the victim's domain. Any handler that trusts `data.shop`/`data.topic` (as the shipped documentation instructs) will process attacker-controlled webhook content under the victim's tenant context — e.g., enqueuing background jobs keyed by `shop_domain: data.shop`, writing to per-shop records, or triggering shop-scoped side effects — a cross-tenant confusion/injection primitive achieved without any credentials.

### Likelihood Explanation
Getting one valid signed webhook body is straightforward for any developer/attacker who installs the target app on a shop they control (a normal, unprivileged path), since Shopify sends real webhooks for ordinary store events. No `api_secret_key`, access token, or privileged access is required to mount the replay against another tenant's identity once such a captured payload exists.

### Recommendation
Bind the header-derived identity fields into the HMAC-verified surface, mirroring the OAuth `AuthQuery#to_signable_string`, which does include `shop` in the signed payload: [7](#0-6) 

For webhooks, either (a) require and cross-check the `shop`, `topic`, and `webhook_id` headers against the registry/registration state before dispatch (e.g., verify the `shop` corresponds to a shop that actually has this webhook/topic registered), or (b) clearly document that `to_signable_string` covers body bytes only and that `shop`/`topic`/`webhook_id` must be independently corroborated by the consuming app before being trusted as tenant identifiers — analogous to resetting `rewardDebt` whenever `unitsAccrued` is reset, i.e., keep the "verified" and "trusted" fields consistent.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header sent to the app's callback endpoint.
2. Attacker replays that exact `raw_body` and `hmac` header to the same endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally the topic/webhook-id headers).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it since all required headers are present.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` — this matches, since `raw_body` and `hmac` are unchanged from step 1.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the handler to act as if this attacker-controlled webhook data legitimately came from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        end
