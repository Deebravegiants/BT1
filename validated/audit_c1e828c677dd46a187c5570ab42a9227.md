This confirms the finding: the docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and document `data.shop` as a trusted field representing "The shop domain of the webhook" (`docs/usage/webhooks.md:14`) that apps are expected to use directly (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)` at `docs/usage/webhooks.md:26`). However, the HMAC only covers the raw body, not the shop-domain header, so "verification" does not actually bind the shop identity.

### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by computing an HMAC over the raw request body only, then trusts the `shop` value taken from an unsigned HTTP header when dispatching to the app's handler. The gem's own documentation instructs apps to treat this `shop` value as an authenticated per-tenant identifier, but the signature never binds the header to the body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, at [1](#0-0) , while `#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the signed payload: [2](#0-1) .

`Registry.process` calls `Utils::HmacValidator.validate(request)` and, if it passes, immediately builds `WebhookMetadata` using `request.shop` as the tenant identifier passed to the app's handler: [3](#0-2) .

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body), and compares it against the caller-supplied `hmac`: [4](#0-3) . Nothing in this call path re-derives or checks the `shop` field against the signature.

The equality that should hold is: `hmac_signed_shop == dispatched_shop`. In reality the gem only enforces `hmac_signed_body == received_body`; the `shop` field is asserted, not verified, breaking that binding.

The gem's own docs instruct developers to trust this exact field as authenticated: `data.shop` is documented as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`), used directly for per-tenant dispatch in the example handler (`docs/usage/webhooks.md:26`), and the processing method is explicitly documented to "verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`) — implying the entire request, including shop, is authenticated. This is a gap in the gem's own verification logic, not a case of the host app ignoring documented guidance.

### Impact Explanation
Any party capable of producing (or replaying) a validly-signed webhook body for one shop — e.g., a merchant who installs the target app on their own store and thus legitimately receives genuinely-HMAC-signed webhook deliveries for that store — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will accept it as valid (the HMAC still matches the unmodified body) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that follows the gem's documented pattern of keying storage, background jobs, or per-tenant business logic off `data.shop` (as shown in the gem's own example) will process/attribute this data under the wrong tenant — a cross-tenant identity confusion achievable by an unprivileged internet user with no access token, `client_secret`, or leaked credential of the victim required.

### Likelihood Explanation
The prerequisite (having previously received one genuinely-signed webhook body of one's own, or reusing any known valid body/HMAC pair) is trivial for anyone who can install the target Shopify app themselves, since apps typically accept installs from any shop. Constructing the spoofed request is a single HTTP POST with a modified header. No secret material of the victim or the app is needed.

### Recommendation
Include the shop domain (and other identifying headers, e.g., `topic`, `api-version`) in the signable string that is HMAC-verified, or otherwise cryptographically bind the header-provided `shop` to the verified body before it is handed to the handler as an authenticated field. At minimum, document clearly that `data.shop` is unauthenticated and must be independently cross-checked (e.g., against a shop for which a registration/session is known) before being used for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw body `B` and the resulting valid header `X-Shopify-Hmac-Sha256: H` (H is a legitimate HMAC of `B` under the app's real secret, computed by Shopify).
2. POST to the app's webhook endpoint with the same `raw_body = B`, the same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only (`to_signable_string`) and matches `H`, passing validation: [5](#0-4) .
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` — as constructed at [6](#0-5)  — and, following the gem's documented usage pattern, performs shop-scoped work (e.g., enqueuing a job keyed by `shop_domain: data.shop`) against `victim.myshopify.com` using attacker-supplied data.
