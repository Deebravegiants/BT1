### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header [1](#0-0) , but the HMAC signature that `Registry.process` validates is computed only over the raw request body [2](#0-1) . The header is never part of the signed bytes, so `shop` is unauthenticated with respect to the HMAC check.

### Finding Description
`Registry.process` accepts a webhook if `Utils::HmacValidator.validate(request)` succeeds [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` [4](#0-3) , and for `Webhooks::Request` that method returns only `@raw_body` [2](#0-1) . The `shop` accessor used downstream is pulled from the `shopify-shop-domain` header, which is not included in the signed string at all [1](#0-0) .

After a valid HMAC check, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.parsed_body`, etc., and passes it to the app's registered handler [5](#0-4) . The gem's own documentation instructs app authors to trust `data.shop` as "The shop domain of the webhook" and to use it directly to route/attribute work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) .

This breaks the intended identity binding: `hmac-verified(raw_body) == authenticated(shop)`. In reality, the HMAC only proves the body bytes came from an entity holding `api_secret_key` (i.e., Shopify, for any shop using this app's credentials); it proves nothing about which shop the header claims. Since Shopify signs webhook bodies with the app's single shared `client_secret` across all shops that installed the app, a genuine, validly-signed `(raw_body, hmac)` pair obtained for one tenant (e.g., the attacker's own installed test shop) remains valid for any `shop-domain` header value the attacker chooses to send, because the header is outside the signed payload.

### Impact Explanation
An attacker who has installed the app on their own shop (or otherwise obtains one legitimate webhook delivery) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim tenant. Because the gem hands this attacker-controlled `shop` straight to the app's handler as the trusted tenant identifier, this enables cross-tenant data confusion/injection in any host application that follows the documented pattern of keying stored/queued work by `data.shop` — e.g., writing or queuing another merchant's data under the attacker's chosen shop, or vice versa. This matches the "cross-tenant access" class of impact, since the tenant-binding guarantee the gem is expected to provide (HMAC-verified request ⇒ correct originating shop) does not hold.

### Likelihood Explanation
Requires only that the attacker can install the app on a shop they control (or otherwise capture one valid webhook delivery+HMAC) and can send arbitrary HTTP headers to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. The host application must rely on `data.shop` from `WebhookMetadata` per the gem's documented usage, which is the expected integration pattern.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material for webhooks, or otherwise independently authenticate the shop, rather than deriving it solely from an unsigned header. At minimum, `Webhooks::Request#to_signable_string` should incorporate the `shop-domain` header value so that `HmacValidator.validate` binds the verified signature to the specific shop the payload claims to be from, matching Shopify's actual signing behavior if it includes shop context, or documenting clearly that `shop` must not be trusted without additional verification.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; the app registers an HTTP webhook handler and endpoint per the documented pattern [7](#0-6) .
2. Shopify delivers a legitimate webhook to the attacker's shop with body `B` and a correctly computed `x-shopify-hmac-sha256` header for `B` (signed with the app's shared `api_secret_key`).
3. Attacker resends the exact same `raw_body: B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers [8](#0-7) , and `Registry.process` validates the HMAC successfully (since it only checks `B` against the signature) [9](#0-8) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body actually originated from and describes the attacker's own shop, causing the host app to process/attribute this data as belonging to the victim tenant.
