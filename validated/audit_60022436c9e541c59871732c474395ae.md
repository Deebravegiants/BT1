### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` checks the HMAC exclusively against that signable string [2](#0-1) . The `shop` value used downstream, however, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed bytes [3](#0-2) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: **shop authenticated by the HMAC == shop acted upon by the handler**. Here it does not: the bytes verified (`@raw_body`) are disjoint from the bytes that carry the tenant identity (`shopify-shop-domain` header). Concretely:

- `HmacValidator.validate_signature` recomputes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and does a constant-time compare against the `hmac` header [2](#0-1) .
- For webhook requests, `to_signable_string` is defined as just the raw JSON body [1](#0-0) . This matches Shopify's actual webhook signing scheme (Shopify HMACs only the body), so this by itself is expected behavior, not a bug in isolation.
- The vulnerability is in how the *unauthenticated* `shop` header is then treated as trusted tenant identity: `Registry.process` does `raise ... unless Utils::HmacValidator.validate(request)` and then builds `WebhookMetadata.new(... shop: request.shop ...)` without any additional binding between the verified body and the claimed shop [4](#0-3) .

Because the header is outside the HMAC, any two fields "(body, hmac)" that are valid together remain valid together no matter what `shop` header accompanies them. An attacker who can obtain one genuine `(body, hmac)` pair - trivially, by having the app installed on their own store and receiving webhooks for it - can replay that exact body+HMAC to the same endpoint while substituting an arbitrary victim `x-shopify-shop-domain` value. The check `Utils::HmacValidator.validate(request)` still passes because it only re-derives the HMAC from the body, and `Registry.process` forwards the attacker-chosen `shop` to the handler as if it were verified.

### Impact Explanation
Any host application whose `WebhookHandler` implementation uses `data.shop` to look up per-tenant session/state (a pattern universally recommended and used in Shopify apps, see `WebhookMetadata`/`WebhookHandler` usage) will process attacker-supplied webhook content as if it originated from a different, victim shop. This crosses the tenant boundary the gem is expected to enforce via HMAC validation, satisfying the "cross-tenant access" criterion, since the host app's own trust decision (which shop's data/session to touch) is made using a value this gem asserts is safe by virtue of "the HMAC validated" but that value was never covered by that HMAC.

### Likelihood Explanation
Reachable by an unprivileged internet user with no access to `api_secret_key`: obtaining one legitimate `(body, hmac)` pair only requires installing the target app on any store the attacker controls (a normal, permitted action for public apps) or observing/replaying a previously delivered webhook to the app's public endpoint. No secret material is required to perform the header substitution - only the ability to POST to the app's public webhook URL with attacker-chosen headers and the previously captured body/HMAC.

### Recommendation
Bind the shop identity into what is authenticated: either include `X-Shopify-Shop-Domain` in the signable string used for the webhook HMAC comparison (not fully possible without deviating from Shopify's documented signing, since Shopify itself does not sign the header), or - more practically for this gem - have `Registry.process`/`WebhookMetadata` cross-check `request.shop` against a shop already known/authorized for this app (e.g., an installed-shop lookup) before invoking the handler, and clearly document in `Webhooks::Request`/`Registry` that `shop` is unauthenticated header data that must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) to capture a genuine `raw_body` and its `x-shopify-hmac-sha256` value from Shopify.
2. Replay that exact `raw_body` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` instead of `attacker.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC secret and never inspects the shop header [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` and the attacker's body [6](#0-5) , causing the host app to act on victim tenant data using attacker-controlled content.
