### Title
Offline session cookie value is a deterministic, guessable identifier (`offline_#{shop}`) accepted verbatim as the session lookup key - ([File: lib/shopify_api/auth/oauth/session_cookie.rb], [lib/shopify_api/utils/session_utils.rb], [lib/shopify_api/auth/oauth.rb], [lib/shopify_api/auth/session.rb])

### Summary
`Session.from` assigns offline sessions the id `"offline_#{shop}"` [1](#0-0) , and `Oauth.validate_auth_callback` stores exactly this value, unmodified and unsigned, as the `shopify_app_session` cookie's value [2](#0-1) . `SessionUtils.cookie_session_id` then returns that cookie value verbatim as the session lookup id for non-embedded apps, with no HMAC/signature check [3](#0-2) . Because the id is fully derived from the public shop domain (no random/secret component), an attacker who knows or guesses a target shop's `.myshopify.com` domain can synthesize this value themselves and present it as a `Cookie` header without ever having received it from the app.

### Finding Description
The binding the host app relies on is: `cookie_session_id(cookies) == <opaque, unguessable session identifier issued only via legitimate Set-Cookie after OAuth completion>`. Tracing the code shows this binding does not hold, because the "opaque" identifier is actually the deterministic string `"offline_" + shop`:

- `Session.from` (offline branch): `id = "offline_#{shop}"` [1](#0-0) 
- `Oauth.validate_auth_callback` sets the cookie's `value` to `session.id` for non-embedded apps: `SessionCookie.new(value: session.id, expires: ...)` [4](#0-3) 
- `SessionUtils.current_session_id`, for non-embedded flow (`Context.embedded?` false), reads the cookie and returns `cookie_session_id(cookies)` with no cryptographic check [5](#0-4) [3](#0-2) 
- No call to `Utils::HmacValidator.validate` or any comparison against a value derived from `Context.api_secret_key` occurs anywhere in this path.

Attacker's exact request: `GET /admin_path` with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`, where the attacker computed this string themselves from the victim's publicly known `.myshopify.com` domain — they never received it via a legitimate Set-Cookie. The host app, following the documented pattern (`current_session_id(nil, cookies, false)` → `SessionRepository.retrieve_session_for_shop`/equivalent lookup keyed by this id), will find and load `victim-shop`'s persisted offline `Session` (containing its access token) if that shop has already installed the app, and treat the attacker's request as authenticated for `victim-shop`.

Existing guards do not prevent this: `HmacValidator.validate` is only invoked in `Oauth.validate_auth_callback` for the OAuth callback step [6](#0-5) , not in the `current_session_id`/`cookie_session_id` path used on every subsequent app request. `Context.embedded?` merely selects the JWT-vs-cookie branch; it does not add authentication to the cookie branch. Docs recommend `secure`/`http_only` cookie flags [7](#0-6) , but `HttpOnly`/`Secure` only prevent JS-based theft or cleartext interception from a *victim's* browser — they do nothing to stop an attacker from directly sending a self-crafted `Cookie` header in their own HTTP request to the app, since the value itself carries no secret entropy for the server to verify.

### Impact Explanation
An attacker who knows any shop's public `myshopify.com` domain can construct `"offline_#{shop}"`, send it as a cookie to a non-embedded app built with this gem, and have the app resolve and use that shop's persisted offline session (including its access token) for the attacker's request. This is cross-tenant access to another merchant's access token/session, matching the Critical category (theft of a merchant access token / cross-tenant access). It is repeatable against any shop that has installed the target app and whose domain is known, with no per-attacker cost beyond one HTTP request.

### Likelihood Explanation
Preconditions: the host non-embedded app must use `SessionUtils.current_session_id` with the cookie fallback (as documented) and must key its persisted session storage directly on this id without additional binding to the requester (e.g., no server-side session/CSRF token independent of the id). Shopify shop domains are commonly discoverable (public storefront, app listing, merchant-provided support requests, etc.), so guessing/knowing `victim-shop.myshopify.com` is low effort. The attacker cost is a single crafted HTTP request; no secrets, no MITM, no XSS needed.

### Recommendation
Do not use a fully public/deterministic string as the session cookie value. Either (a) generate a random, unguessable session token independent of `shop` to store in the cookie, mapping it server-side (in the host app or this gem's session persistence contract) to the actual `offline_#{shop}` session id, or (b) sign/HMAC the cookie value with `Context.api_secret_key` in `SessionCookie`/`cookie_session_id` and verify the signature in `SessionUtils.cookie_session_id` before treating it as trusted, rejecting cookies that fail verification.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_session_id_accepts_forged_deterministic_offline_id
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  forged_cookie_value = "offline_victim-shop.myshopify.com" # attacker computes this without ever
                                                              # receiving a Set-Cookie from the app
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # No HMAC/signature check performed anywhere in this call path;
  # forged id is trusted verbatim as the lookup key for victim-shop's session.
  assert_equal forged_cookie_value, result
  assert_equal "offline_victim-shop.myshopify.com",
    ShopifyAPI::Utils::SessionUtils.offline_session_id("victim-shop.myshopify.com")
end
```
This demonstrates that `current_session_id`/`cookie_session_id` return the attacker-supplied cookie value unmodified and unverified, and that this value is identical in format to the deterministic id (`"offline_#{shop}"`) the app itself would generate and use as a storage key for the victim's real session — confirming the value can be forged purely from public shop-domain knowledge.
