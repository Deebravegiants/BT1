### Title
Balance-conservation loop in `Hinkal.transact` is fully skippable via empty `erc20TokenAddresses` + `HINKAL_EMPORIUM_ACTION_ID`, letting an unsigned Emporium op drain the Emporium contract's balance with zero on-chain accounting - (File: `contracts/Hinkal.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`Hinkal.transact` only checks `balanceDif == amountChanges[i] + utxoAmount` inside a `for` loop bounded by `circomData.erc20TokenAddresses.length`. When a caller selects `externalActionId == HINKAL_EMPORIUM_ACTION_ID` with an empty `erc20TokenAddresses` array, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which proves nothing about UTXOs, tokens, or amounts (only a trivial `Poseidon(messageSeed)` check), and the same empty array makes every balance/accounting loop in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` execute zero iterations. Combined with `verifyWallet`'s early-return when `stack.signerAddress == address(0)` (no EIP-712 signature required in that branch), this lets any unprivileged address execute an arbitrary `op.endpoint.call{value: op.value}(op.callData)` from the Emporium contract with no proof of ownership and no balance reconciliation, draining whatever ETH/ERC20 balance currently sits on the Emporium contract.

### Finding Description
The equality under test is:
`balanceDif == (onChainCreation[i] ? 0 : circomData.amountChanges[i]) + int256(utxoAmount)` — evaluated per token in `Hinkal.sol` lines 97-147 [1](#0-0) .

That loop is bounded by `circomData.erc20TokenAddresses.length`. `CircomDataBuilder.formInputForCircom` explicitly special-cases the situation where `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID && circomData.erc20TokenAddresses.length == 0`, returning `formInputEmporiumMin`'s trivial public-input vector (`emporiumMessage`, `timeStamp`, `calldataHash` only) instead of the normal vector that encodes `erc20TokenAddresses`/`amountChanges`/nullifiers/commitments [2](#0-1) . The corresponding circuit, `MainEVMCircuitMin`, only constrains `message === Poseidon(messageSeed)` — it never touches nullifiers, roots, or amounts [3](#0-2) . Any address can locally generate a valid proof for this circuit by choosing an arbitrary `messageSeed`.

`rootHashExists` still runs, but since `rootHashHinkal` is not part of the Min circuit's public inputs, the attacker can pass any already-existing root (e.g., genesis) — it constrains nothing about the attacker's ownership of value [4](#0-3) .

With `erc20TokenAddresses = []`:
- `oldBalances`/`newBalances` in `Hinkal.transact` are computed over an empty array [5](#0-4) , and the `balanceDif` reconciliation loop at lines 97-147 executes zero times.
- `_externalTransact`'s `deltaAmountChanges` array is also length 0 [6](#0-5) , so no deposit into Emporium is required/verified, but `runAction` is still invoked.
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` and the reconciliation loop (`for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`) also run zero times [7](#0-6) , so `handleOut`/UTXO creation is skipped entirely — no accounting of the ops' effect on Emporium's balance happens anywhere.
- `verifyWallet` marks the message used and, when `stack.signerAddress == address(0)`, returns immediately without any signature check [8](#0-7) .
- With `signerAddress == address(0)`, every op takes the "Stateless Interaction" branch: `op.endpoint.call{value: op.value}(op.callData)`, executed with `msg.sender == EmporiumUpgradeable`, spending Emporium's own held ETH/ERC20 balance [9](#0-8) .

**Attacker's call**: craft `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []` (satisfying `dimensionsCheck` with `dimensions.tokenNumber = 0`), `externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: attackerControlledCall, invokeWallet:false, value: X, callData: ...}] }`, and a locally-generated `MainEVMCircuitMin` proof for a self-chosen `messageSeed`. Call `Hinkal.transact(a,b,c,dimensions,circomData)`. `EmporiumUpgradeable.receive()` accepts ETH from any sender, so an attacker (or accidental user) leaves ETH/tokens on the Emporium contract's balance, which this path then drains with no `require` reverting.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate internal array-length consistency, none of which forces `erc20TokenAddresses.length > 0`; `verifyProof` succeeds because the chosen circuit (Min) proves nothing about value; `rootHashExists` is satisfiable with any valid historical root; the `balanceDif` conservation `require`s in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` are structurally unreachable (loop bound = 0); and `verifyWallet` explicitly skips signature verification when `signerAddress == address(0)`.

### Impact Explanation
Any unprivileged address can seize ETH/ERC20 tokens currently held by the `EmporiumUpgradeable` contract (e.g., ETH sent to its unconditional `receive()`, dust from prior swaps in tokens not declared in a given `erc20TokenAddresses` list, or any balance temporarily parked there) without depositing any of their own value, without a real UTXO/nullifier, and without triggering the protocol's core value-conservation invariant anywhere in the call stack. This is repeatable per unique `emporiumMessage` nonce (a value fully controlled by the attacker) and costs only gas plus generation of a trivial proof. This matches "direct theft of shielded or in-flight user funds" / "theft of protocol funds," Critical.

### Likelihood Explanation
Preconditions are entirely attacker-controlled: choose `HINKAL_EMPORIUM_ACTION_ID`, empty token/amount arrays, `signerAddress = address(0)`, and any op with arbitrary `endpoint`/`callData`/`value`. No tree state, victim cooperation, or privileged role is required — only that the Emporium contract holds exploitable balance at call time (which can be seeded by the attacker itself via `receive()`, or opportunistically after any prior interaction leaves residual balance). Proof generation for `MainEVMCircuitMin` requires only knowledge of a self-chosen `messageSeed`, trivially computable off-chain.

### Recommendation
Do not allow `formInputEmporiumMin`/`erc20TokenAddresses.length == 0` to bypass balance accounting when `ops` can move value. Either (a) require `stack.ops.length == 0` whenever `circomData.erc20TokenAddresses.length == 0`, or (b) always run `runAction`'s before/after balance check against the full set of tokens actually touched by `ops` (not just `circomData.erc20TokenAddresses`), or (c) forbid `stack.signerAddress == address(0)` combined with a non-empty `ops` array from ever using the Min-circuit/zero-token path, forcing full signature verification and balance reconciliation whenever any op can transfer value out of the Emporium contract.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register the Emporium action id, and register a verifier for `dimensions.tokenNumber == 0` mapped to `MainEVMCircuitMin`.
2. Send ETH to `EmporiumUpgradeable` directly (simulate residual/parked balance), e.g. `vm.deal` then a raw `call` to its `receive()`.
3. As an unprivileged `attacker` EOA, build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerReceiver, invokeWallet: false, value: X, callData: ""}]}`.
4. Generate a valid `MainEVMCircuitMin` proof locally for a self-chosen `messageSeed`, matching `calldataHash`/`timeStamp`.
5. Call `hinkal.transact(a,b,c,dimensions,circomData)` from `attacker`.
6. Assert: (i) the transaction does not revert; (ii) `attackerReceiver.balance` increased by `X`; (iii) no `balanceDif == amountChanges[i] + utxoAmount` `require` in `Hinkal.sol` (lines 137-146) was ever evaluated (e.g., via a modified/instrumented build reverting a counter, or by observing the loop body is unreachable since `circomData.erc20TokenAddresses.length == 0`); (iv) `EmporiumUpgradeable`'s own balance-check loop in `runAction` (lines 132-151) is likewise unreached.

    function formInputEmporiumMin(

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
