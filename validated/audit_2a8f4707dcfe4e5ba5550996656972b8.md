### Title
Blocklisted or self-selected beneficiary permanently locks escrowed funds in `WrappedHyperFungibleToken` when `timeout == 0` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` lets any caller lock an arbitrary ERC20 (e.g. USDC) in the contract and pick an arbitrary destination beneficiary and `timeout` value, including `timeout == 0` ("no timeout... messages will never expire", per `docs/content/developers/evm/messaging/post-requests.mdx:44`). On delivery, `onAccept` pushes the underlying token to that beneficiary via `IERC20(_underlying).safeTransfer(beneficiary, message.amount)`. If the beneficiary is on the underlying token's blocklist (e.g. USDC) at delivery time — either because it was already blocklisted, or because it becomes blocklisted after the funds were escrowed — this transfer reverts every time delivery is retried, and with `timeout == 0` there is no way to ever reclaim the escrowed funds via `onPostRequestTimeout`, since that refund path is only reachable once a timeout proof can be submitted.

### Finding Description
`send()` escrows the underlying ERC20 in the contract: [1](#0-0) 

The recipient (`beneficiary`) and `timeout` are both attacker/user-controlled `SendParams` fields with no validation against blocklists and no minimum timeout enforcement: [2](#0-1) 

On the destination chain, `EvmHost.dispatch()` honors `timeout == 0` by setting `timeoutTimestamp = 0`, meaning the request can never expire: [3](#0-2) 

Delivery pushes the underlying token directly to the beneficiary: [4](#0-3) 

If the underlying ERC20 is a blocklist-capable token (the docs explicitly show `WrappedHFT (USDC)` as the intended home-chain deployment) and `beneficiary` is or becomes blocklisted, `safeTransfer` reverts, causing the whole `onAccept` call to revert. `EvmHost.dispatchIncoming` treats a reverted `onAccept` as retryable — it deletes the receipt and returns without recording delivery, so the relayer (or anyone) can retry the same request indefinitely, and it will fail forever as long as the beneficiary stays blocklisted: [5](#0-4) 

Recovery for a failed/undelivered request is only possible through the timeout path, which re-pays the original sender (not the stuck beneficiary): [6](#0-5) 

But the timeout mechanism inherently requires a non-zero `timeoutTimestamp` to become eligible; a request dispatched with `timeout == 0` never reaches a state where a timeout proof is submittable, so the escrow can never be freed through `onPostRequestTimeout`, and there is no owner/governance override in `WrappedHyperFungibleToken` to redirect or reclaim escrowed funds. This mirrors the referenced Sherlock finding's root cause: an unprivileged, user-chosen receiver address can be (or become) blocklisted, the transfer to it reverts on every attempt, and the funds that were locked to fund the transfer become permanently stuck with no recall mechanism — the exact "expiry/reclaim" gap the original report's recommendation was meant to close, except here even the recommended fix (timeout-based reclaim) is bypassable by simply setting `timeout = 0`.

### Impact Explanation
Any user calling `WrappedHyperFungibleToken.send()` with `timeout = 0` and a beneficiary that is (or later becomes) blocklisted on the underlying ERC20 permanently freezes their own escrowed funds in the contract, with no possible recovery path (no timeout refund, no owner override). This is a permanent freezing-of-funds bug reachable from a single unprivileged `send()` transaction, matching the "permanent freezing of funds" acceptance criterion. Because `timeout` is fully attacker/user controlled and defaults to a valid "never expires" mode by design, this is not a rare edge case requiring privileged access — it is directly reachable by any caller of the public `send()` function.

### Likelihood Explanation
Likelihood is Medium: it requires either (a) a user unknowingly bridging to a beneficiary that is later blocklisted while having chosen `timeout = 0` (a documented, intentionally-supported "no timeout" mode), or (b) a malicious actor tricking another party into bridging to a pre-selected soon-to-be-blocklisted address with `timeout = 0`. Both are realistic given `timeout = 0` is an explicitly documented, first-class option, and blocklist-capable tokens like USDC are the stated intended underlying asset for this contract.

### Recommendation
- Enforce a maximum bound on `timeout` (disallow `timeout == 0` / "never expires") for `WrappedHyperFungibleToken.send()`, or otherwise guarantee a bounded recovery window for every dispatched transfer.
- Alternatively, change `onAccept`'s delivery to a pull-based claim pattern (similar to the WETH fallback already implemented for failed native sends) so a reverted push-transfer to a blocklisted beneficiary does not permanently block recovery, e.g. falling back to crediting an internal claimable balance instead of leaving funds solely escrowed against an unconditionally-retried failing call.
- Consider adding an owner/governance-gated emergency recovery path for stuck escrow balances tied to requests that have been failing delivery for an extended period, independent of the ISMP timeout mechanism.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying = USDC` (a blocklist-capable ERC20) as shown in the docs' intended topology (`WrappedHFT (USDC)` on Ethereum).
2. Alice calls `send({ dest: <chainB>, to: Bob, amount: 1000e6, timeout: 0, ... })`. `send()` calls `IERC20(USDC).safeTransferFrom(Alice, address(this), 1000e6)`, escrowing 1000 USDC in the contract [7](#0-6) .
3. Before the message is relayed/delivered on chain B, Circle blocklists Bob's address on USDC (chain B's USDC deployment).
4. The relayer submits the proof; `EvmHost.dispatchIncoming` calls `onAccept`, which calls `IERC20(_underlying).safeTransfer(Bob, 1000e6)` — this reverts because Bob is blocklisted [8](#0-7) .
5. `dispatchIncoming` catches the revert, deletes the receipt, and returns, allowing indefinite retries that will always fail the same way [9](#0-8) .
6. Because `timeout == 0` was used, `timeoutTimestamp` was set to `0` at dispatch [3](#0-2) , so the request can never be proven as timed out, and `onPostRequestTimeout`'s refund path (which would otherwise return the 1000 USDC to Alice) is never reachable. Alice's 1000 USDC is permanently stuck in the `WrappedHyperFungibleToken` contract on chain A.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
