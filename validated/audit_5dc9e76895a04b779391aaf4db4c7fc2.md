### Title
Dual graduation trigger has no minimum-raise floor on the supply-exhaustion path, letting `finalizeGraduation` permanently brick on `INSUFFICIENT_LIQUIDITY_MINTED` and freeze curve-raised LT + 250M reserved tokens - (File: packages/contracts/src/Bonding.sol)

### Summary
CVE-2017-6345 is a class of bug where a required teardown/guard step is missing on one code path while present on a sibling path, so an internal invariant that the rest of the system assumes always holds gets silently violated and the system later hits a hard, unrecoverable failure (`BUG_ON`). alt.fun has the same shape in its graduation dual-trigger: the USD trigger enforces a `$9K` minimum raise before a token can graduate, but the supply trigger (`tokenBalance() == 0`) enforces no minimum raise at all. A token whose curve is fully sold out while `ltFromPair` is dust-small (or even zero) can still flip to `Lifecycle.Graduating` and cache dust `(tokensForLP, ltFromPair)` values. When `finalizeGraduation` later tries to seed a fresh HyperSwap pair with these dust amounts via `pair.mint`, the pool's `MINIMUM_LIQUIDITY` subtraction underflows/reverts, and — because the cached amounts in `pendingGraduation` are fixed and there is no retry-with-different-amounts or rescue path — every future call to `finalizeGraduation` for that token reverts identically forever.

### Finding Description
`triggerGraduation`/the inline post-buy path calls `_enterGraduating`, which pins `(tokensForLP, ltFromPair)` from `_prepareGraduationLiquidity` at whatever reserves exist at that instant: [1](#0-0) 

The dual trigger's supply leg has no dollar floor analogous to the USD leg's `$9K` threshold — it fires purely on `IPair.tokenBalance() == 0`, i.e. whenever the curve's real token supply is exhausted, regardless of how little LT was actually raised: [2](#0-1) 

That means `ltFromPair` (and by the price-preserving ratio, `tokensForLP`) can be pinned at a dust value — this is reachable through a sequence of ordinary curve sells/buys that drain `tokenBalance()` to zero at a very low LT price, or via a low-liquidity LT whose `exchangeRate()` makes the curve cheap to exhaust. `_enterGraduating` unconditionally freezes the token into `Lifecycle.Graduating` and caches these dust amounts: [3](#0-2) 

`finalizeGraduation` is permissionless and re-uses the exact cached `(p.tokensForLP, p.ltFromPair)` every time it is invoked — there is no code path that recomputes or adjusts these values: [4](#0-3) 

For a freshly-created HyperSwap pair (the overwhelmingly common case, `totalSupply() == 0`), `_seedUniswapV2Direct` routes straight to `_seedDirectMint`: [5](#0-4) 

`_seedDirectMint` transfers the dust `tokensForLP`/`ltFromPair` to the pair and calls `pair.mint(lpLock)` directly: [6](#0-5) 

Standard UniswapV2-shape `mint()` computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` on the first mint and reverts (`INSUFFICIENT_LIQUIDITY_MINTED`) if that underflows/is zero. Because `tokensForLP`/`ltFromPair` are dust by construction on this trigger path, `sqrt(tokensForLP * ltFromPair)` can fall below `MINIMUM_LIQUIDITY` (1000 wei on canonical V2 forks), making the `mint()` call revert every single time `finalizeGraduation` is invoked, with no way to change the outcome since the cached amounts never change and there is no owner/rescue function that can rewrite `pendingGraduation[token]` or cancel graduation back to `Lifecycle.Curve`.

This is the analog of CVE-2017-6345's "missing destructor in required circumstances": the protocol's own documentation explicitly frames the two-phase design's central invariant as "Phase 2 must never revert under any pre-seed shape" and enumerates hostile-pre-seed defenses (`_seedRebalancing`, `_pairRebalance`, `_seedDirectMint` fallbacks, `_swapBudget`'s 1% reservation) precisely to guarantee that brick-resistance — but none of those defenses address a *self-inflicted* dust amount originating from the supply trigger itself, because that trigger was never given the USD-trigger's `$9K` floor: [7](#0-6) 

### Impact Explanation
Once a token enters `Lifecycle.Graduating` via the dust supply trigger, it can never reach `Lifecycle.Graduated`: `finalizeGraduation` deterministically reverts on `pair.mint`. This permanently freezes:
- the LT already drained from the curve pair into `Bonding` via `Router.graduate` in `_prepareGraduationLiquidity`,
- the up-to-250M `LP_RESERVE` tokens parked in `Bonding` awaiting LP seeding,
- and the token itself, since `Bonding.buy`/`sell` are frozen for any lifecycle other than `Curve` and there is no unwind path back to `Curve`.

This satisfies the "permanent freezing of trader, creator or LP funds" impact bar without any privileged action — the graduation trigger is reachable purely through ordinary permissionless buys/sells and the permissionless `triggerGraduation`/`finalizeGraduation` entry points.

### Likelihood Explanation
Reachability is unprivileged and mechanical: any trader can sell/buy on the curve to drive `tokenBalance()` to zero at a low LT price (or target a low-liquidity/newly-launched LT), and any address can then call `Bonding.triggerGraduation` and `Bonding.finalizeGraduation`. No governance, no upgrade, no off-chain component is required. The main uncertainty is the exact dust threshold needed to underflow `MINIMUM_LIQUIDITY` on the specific HyperSwap V2 pair implementation in use, which I could not independently confirm from the indexed contract sources (the pair implementation itself is out of scope per the rules), so likelihood should be assessed against the deployed pair's actual `MINIMUM_LIQUIDITY` constant.

### Recommendation
Apply the same minimum-raise floor to the supply-exhaustion trigger that already exists for the USD trigger (e.g., require `ltFromPair` to exceed a floor comfortably above the target pair's `MINIMUM_LIQUIDITY` before allowing `_enterGraduating` to fire on `tokenBalance() == 0`), or add a rescue path that lets `finalizeGraduation` fall back to a non-LP disposition (e.g., sweep dust LT/tokens to the owner and mark the token `Graduated` without seeding LP) when `tokensForLP`/`ltFromPair` are below the viable-mint floor.

### Proof of Concept
1. Launch a token via `Zap.createToken` with the minimum seed.
2. Drive the curve's real token supply (`IPair.tokenBalance()`) to zero through ordinary `Bonding.sell`/`buy` calls at a depressed LT exchange rate, such that `assetReserve - virtualLtReserve` (i.e. `ltFromPair`) is dust (e.g., single-digit wei).
3. Call `Bonding.triggerGraduation(token)` (or let the closing sell/buy trigger it inline) — `canGraduate` returns true purely off the supply leg, `_enterGraduating` caches dust `tokensForLP`/`ltFromPair` in `pendingGraduation[token]`.
4. Call `Bonding.finalizeGraduation(token)` — `_ensureUniswapV2Pair` creates a fresh pair, `_seedUniswapV2Direct` → `_seedDirectMint` transfers the dust amounts and calls `pair.mint(lpLock)`, which reverts with `INSUFFICIENT_LIQUIDITY_MINTED` because `sqrt(tokensForLP * ltFromPair) <= MINIMUM_LIQUIDITY`.
5. Every subsequent call to `finalizeGraduation(token)` reverts identically — the token is permanently stuck in `Lifecycle.Graduating`, with its curve-raised LT and `LP_RESERVE` tokens frozen in `Bonding` with no recovery function.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
