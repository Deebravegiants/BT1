### Title
Webhook `shop` identity is read from an HMAC-unverified header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, but the `shop` value that is handed to the app's webhook handler as the authoritative tenant identity is taken from the `X-Shopify-Shop-Domain` header, which is not part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which compares an HMAC computed over `request.to_signable_string` against the `hmac` field: [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` (along with `topic`, `webhook_id`, `api_version`) is derived independently from HTTP headers via `shopify_header` [3](#0-2) .

This breaks the intended binding: **the tenant authenticated by the HMAC (the request body) ≠ the tenant used as the identity key (the `shop-domain` header)**. Once HMAC validation passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., and dispatches it to the app-registered handler unmodified: [1](#0-0) .

Because the HMAC secret (`Context.api_secret_key`) is the app's single shared client secret — not a per-shop secret — any merchant who installs the app on their own store legitimately receives real, validly-signed webhook deliveries from Shopify. That merchant (an "unprivileged internet user" relative to other tenants of the same app) can capture one such genuine webhook and resend the exact same raw body directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain. Since `to_signable_string` never included these headers, `HmacValidator.validate` still succeeds, and the app's handler will process the (unmodified) payload as if it belongs to the victim shop.

### Impact Explanation
This enables cross-tenant confusion: data intended for/about attacker's own shop can be attributed to a different (victim) shop inside the app's webhook processing pipeline, because the gem exposes `shop` as a trusted, HMAC-validated identity when it is in fact unauthenticated header data. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select which merchant's records to update/delete, or which tenant's cached tokens/settings to invalidate), this can lead to cross-tenant data corruption or unauthorized actions against a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any actor who can install the app on a store they control (which is the normal onboarding flow for public apps) can trivially capture a real webhook delivery and replay it with a modified header, without needing the app's `client_secret` or any privileged credential. The only cost is registering/owning one shop instance of the app, which is the baseline "unprivileged internet user" capability for this kind of app.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind the header-derived shop identity to the signed body), or require the caller to independently corroborate the header-derived shop against a known/expected shop before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are not covered by webhook HMAC verification, since the current API implies otherwise by calling `Utils::HmacValidator.validate(request)` a single unified "validation" step.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook to the app endpoint with body `B` and headers including `X-Shopify-Hmac-Sha256: H(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` (unmodified) and the exact same `X-Shopify-Hmac-Sha256: H(secret, B)` value directly to the app's webhook endpoint, but changes the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [4](#0-3) ; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches, so validation passes [5](#0-4) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed_body(B), ...)` [1](#0-0) , causing the app to act as though this webhook genuinely originated from `victim.myshopify.com`.
