Webhook `shop-domain` header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` (and `topic`/`webhook_id`) values are read straight from HTTP headers that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and hands it directly to the app's handler as the tenant identifier, so an attacker who can produce (or replay) one valid `(body, hmac)` pair can freely swap the `shop-domain` header to impersonate a different merchant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac`: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop bound to hmac`. In this implementation that equality never has to hold — the HMAC only proves "this body was signed with our secret for *some* request at some point," not "this body was signed *for this specific shop*." Because the `shop` header sits outside the signed bytes, `shop-domain(header) ⊄ signable_bytes`, breaking the binding the report's bug class targets (a field acted upon but not covered by the HMAC).

### Impact Explanation
This is a High severity scope/tenant-binding issue: the webhook callback endpoint is a public, unauthenticated HTTP endpoint (per `docs/usage/webhooks.md`, the host app simply calls `Registry.process` on any incoming POST to the registered path). Any unprivileged internet user who obtains one legitimate, unmodified webhook payload+HMAC (e.g., by installing the target app on their own low-value/free trial shop and capturing a webhook it receives) can replay that exact `raw_body`/`hmac-sha256` pair while substituting an arbitrary `shop-domain` header. The HMAC check still passes because the header is not part of the signed string, and the handler is invoked believing the event belongs to the attacker-chosen victim shop. Downstream handlers that key persistence, deduplication, or business logic off `data.shop` (as the gem's own documentation recommends, e.g. `perform_later(shop_domain: data.shop, ...)`) will process data under the wrong tenant, achieving cross-tenant data confusion/injection without possessing the victim's session or access token.

### Likelihood Explanation
Likelihood is high for any app that exposes its webhook route publicly (the documented, standard integration pattern) and relies on `data.shop` from the callback for tenant attribution. The only prerequisite is obtaining a single valid signed webhook body — trivially available to anyone who installs the app on a shop they control, since Shopify sends real webhooks to installed apps.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or independently verify that the `shop-domain` header matches the shop associated with the specific webhook subscription/session before dispatching to the handler. At minimum, document prominently that `data.shop` from `Registry.process` is unauthenticated and must not be used as a tenant key without additional verification (e.g., cross-checking against a known/registered shop list).

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook Shopify sends to the app's callback URL, e.g. body `{"id":1}` with headers:
   `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid hmac of body>`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same request to the same callback URL, but change only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` still succeeds because it only checks `Digest.hexencode(...)` against `HMAC(secret, raw_body)` — the header value never enters the computation: [5](#0-4) 
4. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now equals `"victim.myshopify.com"`, even though the body/topic actually originated from the attacker's own shop: [6](#0-5) 
5. Any handler logic keyed on `data.shop` (persistence, job routing, idempotency keys, notifications) now operates as if the event came from `victim.myshopify.com`.
