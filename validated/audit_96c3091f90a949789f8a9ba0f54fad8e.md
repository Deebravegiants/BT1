Confirmed: the `Registry.process` HMAC check only validates `Request#to_signable_string` (`@raw_body`), while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers (`shopify-shop-domain`, etc.) that are never part of the signed data. This is the exact "field acted on but not covered by the HMAC" pattern.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that signable string using the app's `client_secret` [2](#0-1) . Meanwhile `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header without any cryptographic binding to that header's value [3](#0-2) . `Registry.process` accepts the request purely based on this body-only HMAC check and then dispatches the handler using the unauthenticated `shop` value [4](#0-3) .

### Finding Description
The equality this code implicitly assumes is:

`shop asserted by header == shop that the HMAC-signed body actually belongs to`

but this equality is never enforced. The HMAC only authenticates the *bytes of the body*; it says nothing about which shop that body was generated for. An unprivileged attacker who controls any Shopify store (a free/dev store is enough) can install the target app on their own store, trigger a real webhook (e.g. `orders/create`), and legitimately receive a body + `X-Shopify-Hmac-Sha256` pair that is validly signed with the app's shared `client_secret` (the secret is the same across all shops using the app, only the payload/shop differs). The attacker then replays that exact body and HMAC header to the app's webhook endpoint, but substitutes the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body`, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` to the handler with the attacker-chosen shop value [5](#0-4) .

### Impact Explanation
Any application built on this gem that trusts `data.shop` from `WebhookMetadata` to select which merchant's session/access token/business record to act on (the documented and expected usage pattern for webhook handlers) can be made to apply attacker-controlled webhook data under a victim shop's identity — i.e., cross-tenant access/confusion, achieved without possessing the victim's access token or the app's `client_secret`. This satisfies the Critical impact bar for cross-tenant access.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the app on a shop they control (a standard, unprivileged capability for any Shopify developer/merchant), since no leaked credential or privileged account is required — only observation of one legitimate webhook delivery to their own store and a header rewrite on replay.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived `shop` value to the signed payload before it is trusted, e.g. by having `Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` alongside `@raw_body`, and rejecting requests where these headers are not covered by the signature.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g., update an order) to receive a real webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [6](#0-5) ; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` [7](#0-6) ; `Registry.process` calls the registered handler with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's store [4](#0-3) .

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
