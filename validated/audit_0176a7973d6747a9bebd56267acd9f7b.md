## Analysis

The reported class of bug ("value trusted for identity/authorization purposes is inconsistent with the value that was actually verified") maps cleanly onto how this gem exposes Shopify webhook data in `ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry`. [1](#0-0) [2](#0-1) 

### Title
Webhook shop identity is not bound to the HMAC-verified bytes, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates nothing but the body bytes. The `shop` value used everywhere downstream (`Registry.process`, `WebhookMetadata.shop`) is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed payload. This breaks the identity binding `HMAC-verified-bytes == shop-attributed-to-this-request`.

### Finding Description
`AuthQuery` binds every field it cares about (`code`, `host`, `shop`, `state`, `timestamp`) into `to_signable_string`, so the OAuth callback's HMAC actually covers the `shop` value it later trusts. [3](#0-2) 

`Webhooks::Request` does not do the same. Its `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from unauthenticated headers, while `to_signable_string` only returns `@raw_body`: [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the body) and compares it to the `hmac` field: [5](#0-4) 

`Registry.process` treats a passing HMAC check as authorization to trust `request.shop` and hands it straight to the app's handler: [2](#0-1) 

Because the app's `client_secret` (the HMAC key) is shared across every shop that has installed the app, any merchant who installs the app can generate a legitimately-signed `(raw_body, hmac)` pair for a topic of their choosing (e.g. by triggering `app/uninstalled` or `products/update` on their own store and capturing the delivered payload). That valid `(body, hmac)` pair remains valid for the *same secret* regardless of which shop domain header accompanies it, since the header is outside the signed content. The attacker can then replay that body+hmac to the target app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header claiming to be a victim shop. `HmacValidator.validate` returns `true` (the body/secret pair matches), and `Registry.process` forwards `shop: request.shop` (attacker-controlled) into `WebhookMetadata`, so the host application's handler will process/act on this event as if it originated from the victim shop.

### Impact Explanation
This lets an unprivileged internet user (any merchant who has ever installed the app) inject events attributed to a different, victim tenant into the app's webhook processing pipeline — a cross-tenant identity confusion. Depending on what the host app does with `WebhookMetadata.shop` (look up stored access tokens/sessions, trigger data mutation, GDPR redaction, uninstall cleanup, etc.), this can lead to cross-tenant data corruption or unauthorized actions performed against a shop the attacker does not control, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Any user who can install the app (even a free/dev-store install) can obtain a validly-signed webhook body/HMAC pair, since the signing secret is the app's single shared `client_secret`, not shop-specific. Replaying it with a forged shop header requires only basic HTTP tooling and no privileged credentials or leaked secrets, making this readily exploitable by any unprivileged internet actor who can install the target app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the value that is HMAC-verified, or otherwise cryptographically bind the `shop` header to a value under Shopify's control that is covered by the signature (Shopify's newer webhook payloads/headers should be checked for shop-scoped verification options). At minimum, `Webhooks::Request`/`Registry` should require host applications to cross-check `request.shop` against a known-installed shop list before trusting it, and the gem's documentation/API should make explicit that `request.shop` is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook delivery (e.g. update a product) and intercepts the raw POST Shopify sends to the app's webhook endpoint, capturing the exact `raw_body` and `x-shopify-hmac-sha256` header.
3. Attacker replays that exact `raw_body` + `x-shopify-hmac-sha256` to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared `client_secret`.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from that shop, per: [6](#0-5)

          received_signature = verifiable_query.hmac
