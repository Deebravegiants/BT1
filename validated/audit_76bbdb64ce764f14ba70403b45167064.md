### Title
Webhook HMAC Does Not Bind `shop`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then unconditionally trusts the header-derived `shop` and `topic` to route and tag the payload for the host app's handler. This breaks the intended binding: "shop authenticated" (by HMAC) should equal "shop the handler is told the data belongs to," but the HMAC never covers the shop claim.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string, and then, on success, builds `WebhookMetadata` directly from the same untrusted headers and dispatches it to the host app's handler: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [4](#0-3) 

Because the signable string is body-only, a valid `(raw_body, hmac)` pair computed by Shopify for one shop/topic remains cryptographically valid no matter what `shop-domain`, `topic`, `webhook-id`, or `api-version` headers accompany it. The gem's `process` method never checks that these headers are consistent with anything it validated — it trusts them unconditionally once the body's HMAC checks out.

The equality that should hold is:
`shop authenticated by HMAC == shop passed to WebhookMetadata`
but in this implementation the HMAC authenticates only the body, so:
`shop authenticated by HMAC ⊄ shop passed to WebhookMetadata`

### Impact Explanation
An unprivileged attacker who can obtain any one genuinely-signed webhook delivery for a shop they control (e.g., by installing the app on their own store, which is normal, unprivileged self-service action) can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair. They can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `Registry.process` will validate successfully (since HMAC only covers the untouched body) and hand `WebhookMetadata` down to the host application's handler tagged with the victim's shop. Any host application that uses `WebhookMetadata#shop` as a tenant key (as documented and demonstrated in the gem's own webhook usage docs) will process/store attacker-controlled data under the victim's tenant, resulting in cross-tenant data injection/corruption.

### Likelihood Explanation
Any developer/merchant can self-install the app to capture a legitimately-signed webhook body+HMAC for their own shop; no access to `api_secret_key` or any credential is required, and no assumption is made beyond the gem's documented API being used as intended by the host application (`ShopifyAPI::Webhooks::Registry.process` exactly as documented in `docs/usage/webhooks.md`).

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them, e.g., only trust `shop`/`topic` when they are supplied out-of-band by the webhook subscription record rather than the request itself), so that `Registry.process` cannot be fed a validly-signed body accompanied by attacker-chosen shop/topic headers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, triggering a real webhook delivery. They capture the raw POST body and the `x-shopify-hmac-sha256` header — both valid and Shopify-signed.
2. Attacker resends the exact same body to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and, if desired, an `x-shopify-topic` for a sensitive topic that the victim also has registered):
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <hmac copied from attacker's own delivery>
x-shopify-shop-domain: victim.myshopify.com
x-shopify-webhook-id: <copied>
x-shopify-api-version: 2024-01

<raw_body copied verbatim from attacker's own delivery>
```
3. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` line 190 validates HMAC successfully (body unchanged), then dispatches `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` to the host app's handler, which processes attacker-controlled data as if it originated from the victim's shop.
