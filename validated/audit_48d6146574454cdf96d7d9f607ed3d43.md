### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `hmac` and signable string solely from the raw HTTP body [1](#0-0)  and `to_signable_string` returns only `@raw_body` [2](#0-1) , while the `shop` field that identifies the tenant is read straight out of an unauthenticated HTTP header [3](#0-2) . `Registry.process` validates only the HMAC over the body and then forwards `request.shop` unchecked into the handler as the trusted tenant identity [4](#0-3) .

### Finding Description
The binding that should hold is: `HMAC-verified bytes == bytes that determine tenant identity`. Here, `HmacValidator.validate` only signs/verifies `verifiable_query.to_signable_string`, which for webhooks is exclusively the raw body [5](#0-4) . The `shop-domain` header — the value the app is told to trust as the originating merchant — is never part of the signed payload.

Because Shopify signs a webhook's `X-Shopify-Hmac-Sha256` using the app's own `client_secret` over the raw body, and the body content for a webhook fired by any legitimately installed shop is largely controlled by that shop's own merchant actions (e.g., an order's `note`, a product's `title`, a customer field, etc.), an attacker who installs the app on their own shop can:
1. Trigger a real, Shopify-signed webhook with an attacker-crafted body via ordinary storefront/admin actions on their own store.
2. Capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — a validly signed pair, since HMAC only covers the body.
3. Replay this exact body+HMAC to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.

`Registry.process` will accept it: `Utils::HmacValidator.validate(request)` succeeds (body/HMAC pair is genuine) [6](#0-5) , and `WebhookMetadata.shop` is populated with the victim's spoofed domain [7](#0-6) . The handler then processes attacker-controlled body content under the victim shop's identity, as shown in the documented usage pattern where `data.shop` is trusted directly for tenant-scoped work (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [8](#0-7) .

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: `shop identity trusted by the app` ends up decoupled from `shop identity that actually produced the signed bytes`. Any app that uses `data.shop` from `ShopifyAPI::Webhooks::WebhookMetadata` to key per-tenant storage, dispatch background jobs, or make authorization decisions can have attacker-controlled data injected and attributed to an arbitrary victim shop — a cross-tenant access/data-integrity violation, which the rules classify as Critical impact.

### Likelihood Explanation
The prerequisite is only that the attacker can install the same app on a shop they control (a normal, unprivileged app-install action requiring no leaked credentials) and can influence body content transmitted in a subscribed webhook topic, then replay the request with a modified header to the app's public webhook endpoint. No access to `api_secret_key` or any privileged account is required — only observation of the app's own outgoing webhook traffic pattern and a basic HTTP replay, both actions available to an ordinary internet-facing merchant/attacker.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) values into the HMAC-signed payload used for verification — e.g., verify webhooks per-shop by cross-checking the `shop-domain` header against session storage/known-installed shops before trusting it, or require the signable string in `Webhooks::Request#to_signable_string` to also incorporate the shop-domain header so a mismatch invalidates the signature. Document prominently that `WebhookMetadata.shop` is not itself HMAC-authenticated and must be revalidated by the consuming app against its own list of installed shops before being used for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker owns shop `attacker.myshopify.com` with the target app installed.
# Attacker performs an action (e.g., updates an order note) so Shopify sends a
# legitimately HMAC-signed webhook to the app:
#   raw_body = '{"id":1,"note":"<attacker payload>"}'
#   headers  = {
#     "x-shopify-topic"        => "orders/updated",
#     "x-shopify-hmac-sha256"  => "<valid HMAC over raw_body, computed by Shopify using the app's secret>",
#     "x-shopify-shop-domain"  => "attacker.myshopify.com",
#   }
#
# Attacker intercepts/replays this exact body + HMAC to the app's webhook
# endpoint, only changing the shop header:
headers["x-shopify-shop-domain"] = "victim.myshopify.com"

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) still returns true, because the signature
#    only ever covered `raw_body`, not the shop header.
# => The registered handler receives WebhookMetadata(shop: "victim.myshopify.com",
#    body: {"id"=>1,"note"=>"<attacker payload>"}, ...) and processes attacker
#    content under the victim's tenant identity.
```
