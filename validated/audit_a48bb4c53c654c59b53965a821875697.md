I have enough evidence to confirm the vulnerability. The gem's own documentation explicitly recommends trusting `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), yet that field is never part of the HMAC-signed material.

### Title
Webhook `shop` (tenant identity) header is not covered by HMAC validation, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop-domain` header (unauthenticated) as the tenant identity passed to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that signable string [2](#0-1) . The `shop` accessor, however, is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2) , with no equality binding to anything the HMAC covers.

`Registry.process` validates only the HMAC (`Utils::HmacValidator.validate(request)`) and then builds `WebhookMetadata` directly from `request.shop`, handing it to the app's handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding that should hold is: `shop-domain header == shop bound inside HMAC-signed content`. It does not — the HMAC only proves "this body byte-string was produced with our app's shared client secret," not "this body was sent for shop X." Because the HMAC secret (`api_secret_key`) is shared across every shop installation of the app (it's the app's client secret, not a per-shop key), a valid signed body/HMAC pair obtained from any one shop's legitimate webhook delivery remains valid when replayed with a forged `shop-domain` header pointing at a different shop.

The gem's own documentation instructs developers to trust `data.shop` directly for shop-scoped operations, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) , so this unauthenticated field is the intended mechanism apps use to select which merchant's session/data the webhook body should be applied to.

### Impact Explanation
An attacker who can obtain one valid signed webhook body (e.g., from their own installed/dev shop, or a topic with predictable/replayable body content such as `app/uninstalled` or a resource id they control) can replay that exact HTTP request while substituting the `shop-domain` header for a victim shop. Since the gem reports this as a validly-authenticated webhook for the victim shop, any host application following the documented pattern of trusting `data.shop` for tenant-scoped side effects (queuing jobs against `shop_domain`, updating per-shop records, revoking data, etc.) will act on forged cross-tenant input. This satisfies the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint (no access token, secret, or privileged account needed) and one legitimate webhook capture, which is trivial for an attacker who owns any shop that has the app installed (a shop is unprivileged/free to obtain). The `api_version` and `webhook_id` fields have the same problem, but `shop` is the most consequential since it drives tenant scoping in every documented usage pattern.

### Recommendation
Bind the shop identity into the authenticated material: either include the `shop-domain` (and ideally `webhook-id`, `api-version`) header values in the string that is HMAC-verified, or otherwise cryptographically bind the header to the signed body (e.g., signing `raw_body + shop_domain` server-side per Shopify's actual webhook signing scheme, and rejecting requests where the header-derived shop doesn't match). At minimum, document prominently that `data.shop` is not authenticated by `Registry.process` and must not be trusted for tenant-scoping decisions without independent verification (e.g., cross-checking against a known/registered shop list tied to a valid access token).

### Proof of Concept
1. App has webhooks registered; attacker installs the app on shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `app/uninstalled` with an empty/predictable body `{}`), capturing the raw body and the `x-shopify-hmac-sha256` value.
2. Attacker replays that exact body + HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body bytes against the shared `api_secret_key` [6](#0-5) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , and the host app (following documented guidance) performs a tenant-scoped action (e.g., queues an uninstall/data-redaction job) against the victim shop it never authorized.
