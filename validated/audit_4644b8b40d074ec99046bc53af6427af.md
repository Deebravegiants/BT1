### Title
Unbounded, unweighted `handle_unsigned` batch execution enables free computational DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Pallet::handle_unsigned` accepts an arbitrary `Vec<Message>` and is declared with a fixed, size-independent weight, while being executable as a fee-free unsigned extrinsic by anyone. Each message (`RequestMessage.requests`, `ResponseMessage.requests`, a BEEFY `ConsensusMessage` with many parachain headers, etc.) is processed in an unbounded loop over attacker-controlled batch contents, with no on-chain cap on the number of items or the size/complexity of the accompanying proofs. This is the same "unbounded loop reachable by an unprivileged caller" defect described in the reference Uniswap V3 report, mapped onto pallet-ismp's `handle_unsigned` dispatch path explicitly called out in the analog rules.

### Finding Description
`handle_unsigned` is declared with a static weight independent of the batch it carries: [1](#0-0) [2](#0-1) 

The comment on `weight()` states these static weights "should get overridden by the FeeHandler," but `FeeHandler::on_executed` only computes `actual_weight` *after* the batch has already been fully executed: [3](#0-2) [4](#0-3) 

`Pallet::execute` (called from both `validate_unsigned` and `handle_unsigned` itself) iterates over every message in the submitted `Vec<Message>` with no length or complexity cap, invoking `handle_incoming_message` per item: [5](#0-4) 

Crucially, this same unbounded loop is run once during `validate_unsigned` in the transaction pool (for free, without even reaching a block) and again during actual dispatch: [6](#0-5) 

Downstream handlers (`handlers/request.rs`, `handlers/response.rs`) further loop per-request performing dedup checks, membership-proof verification, and module dispatch, with the loop bound set entirely by the submitter's `requests` vector length: [7](#0-6) [8](#0-7) 

The documentation itself flags the exposure: pallet-ismp "allows users execute ISMP datagrams for free. Use with caution," relying only on `validate_unsigned`'s pool-level check to prevent spam — but that check *is* the same expensive unbounded computation: [9](#0-8) 

This mirrors the Uniswap V3 report's core defect: a permissionless entry point drives a loop whose iteration count is fully attacker-controlled (batch size / proof complexity) while the declared cost accounting (there: gas; here: `Weight::from_parts(300_000_000, 0)`) does not scale with the actual work, so `frame_system::CheckWeight`/block-weight budgeting and mempool throughput can be exhausted by legitimately-proved but maximally-sized submissions.

### Impact Explanation
An attacker who can generate valid state/consensus proofs (e.g., self-dispatch many small POST/GET requests on a source chain they control, or replay/construct a BEEFY proof carrying many parachain headers) can submit `handle_unsigned` calls whose true execution cost (membership-proof verification, per-item dedup, offchain-storage writes, module dispatch) is far larger than the flat 300,000,000 weight the runtime charges against the block weight limit. Because these are fee-free unsigned transactions, the attacker pays no transaction fee for the work performed, and validators/collators must re-run the same unbounded loop during `validate_unsigned` for every pool submission. This can starve block production time and/or block weight budget, denying honest relayers the ability to get their (legitimate, revenue-bearing) messages included — a network/route availability failure ("a route unable to deliver messages") satisfying the "Medium/High" DoS bar in the analog rules.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to produce *valid* proofs (state membership proofs, or a genuine BEEFY/consensus proof), which requires real (if cheap) activity on a source chain, similar to the Uniswap scenario requiring an attacker to create many 1-wei positions. As in that report, the cost asymmetry (cheap to create many small verifiable items vs. expensive/unbounded to process them in one settlement/verification call) is the crux of the risk, and no batch-size or weight-scaling cap was found in `handle_unsigned`, `Pallet::execute`, or the request/response handlers during this review.

### Recommendation
- Cap `messages.len()` (and per-message `requests.len()` / header counts) in `handle_unsigned`, rejecting oversized batches in `validate_unsigned` before full execution.
- Make the declared `#[pallet::weight(...)]` for `handle_unsigned` a function of the actual batch size/proof complexity (e.g., benchmarked per-item weight × item count) rather than a fixed constant, so `CheckWeight` enforces a real bound pre-dispatch.
- Consider bounding proof depth/size (similar to the existing `MAX_PROOF_DEPTH` guard in `modules/consensus/pharos/primitives/src/spv.rs`) uniformly across all consensus/state-proof verifiers reachable from `handle_unsigned`.
- Document and enforce these bounds explicitly, consistent with the long-term Uniswap recommendation to bound and document all attacker-influenced parameters.

### Proof of Concept
Conceptual PoC (execution/environment access needed to fully validate battle conditions, not available in this read-only review):
1. On a source chain, dispatch N (e.g., tens of thousands) minimal POST requests destined for the target parachain, each cheap to create.
2. Once finalized/provable, submit one `Ismp::handle_unsigned` unsigned extrinsic with `messages = [Message::Request(RequestMessage { requests: <all N requests>, proof, signer })]`.
3. Observe: `validate_unsigned` fully executes `Pallet::execute` (looping per request through membership-proof verification, dedup, and module dispatch) for free in the transaction pool, and — if accepted — again on dispatch, while `#[pallet::weight(weight())]` still charges only `Weight::from_parts(300_000_000, 0)` against the block's weight limit, independent of N.
4. Repeat concurrently from multiple free unsigned submissions to consume collator validation time / block weight disproportionately to any fee paid, degrading throughput for legitimate relayers.

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
