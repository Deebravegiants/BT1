### Title
Unauthenticated, attacker-controlled cookie value trusted as session identifier - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `SessionUtils.current_session_id` returns whatever string is present in the `shopify_app_session` cookie with zero cryptographic verification. Because session IDs are deterministic, non-secret strings derived from the public shop domain (`offline_#{shop}` / `#{shop}_#{user_id}`), an attacker can simply set that cookie to another shop's predictable session ID in their own raw HTTP request and have the gem hand back that identifier as if it were authenticated.

### Finding Description
The broken binding: `SessionUtils.current_session_id(nil, cookies, online) == session id backed by an authenticated shop` is assumed by any host app performing a direct session-store lookup by this returned string, but this equality never holds on the cookie path.

Code path:
- `current_session_id` for non-embedded apps only checks that the cookie key exists, then calls `cookie_session_id(cookies)` directly: [1](#0-0) 
- `cookie_session_id` simply reads the raw cookie value with no signature, HMAC, or format re-derivation check: [2](#0-1) 
- Session IDs are deterministic strings built purely from the shop domain (and, for online sessions, a user id), not random secrets: [3](#0-2) [4](#0-3) 
- The only place this cookie value is cryptographically anchored to a real OAuth flow is at initial callback time, via `Utils::HmacValidator.validate(auth_query)` and the `state == auth_query.state` check, and even there the cookie's *outgoing* value is simply set to `session.id` (the deterministic string) rather than a random opaque token bound server-side to the session: [5](#0-4) 

Root cause: HMAC/state validation is only enforced during `validate_auth_callback` (the one-time OAuth completion), but every *subsequent* request that calls `current_session_id` for a non-embedded app trusts the raw `Cookie` header value with no re-validation. Since a `Cookie:` header is fully attacker-controlled on any HTTP client (curl, Postman, or a browser under the attacker's control) regardless of `secure`/`httponly` flags on cookies the *server* sets — those flags only prevent script-based reading/theft of a cookie the browser already holds, they do nothing to stop an attacker from sending their own chosen cookie value to the target domain — an attacker can craft a request directly containing `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. Since the ID format is fully deterministic and derived only from the public shop domain, no secret is required to construct it.

None of the gem's existing guards intervene on this path: `HmacValidator.validate` and the OAuth `state` check only run inside `Oauth.validate_auth_callback`, not inside `SessionUtils.current_session_id`; `JwtPayload`'s `aud`/`sub` checks only apply to the embedded/JWT branch; `Context.setup?`/`private?`/`embedded?` do not gate the non-embedded cookie branch at all — the `else` branch at lines 31-36 runs unconditionally whenever `Context.embedded?` is false.

### Impact Explanation
If the host app's session store performs a direct lookup by the ID this gem returns (as the gem's own OAuth documentation instructs), an attacker who knows or guesses a victim shop's domain — public information in virtually all cases (myshopify.com subdomains, install links, storefront URLs) — can obtain that shop's stored `Session`, including its `access_token`, and use it to make authenticated Admin API calls against the victim's store. This is a cross-tenant credential exposure entirely within this gem's trust boundary (the cookie-to-session-id mapping), repeatable against any shop whose domain the attacker can enumerate or observe, with no per-request cryptographic gate to stop it.

### Likelihood Explanation
Preconditions: a non-embedded app using the documented `SessionUtils.current_session_id(nil, cookies, online)` call and a session store that looks sessions up directly by the returned ID (the documented pattern in `docs/usage/oauth.md`, e.g., `MyApp::SessionRepository.store_session(...)` keyed by `session.id`). Attacker cost is trivial: no secret, no token, no privileged access — just knowledge of the target shop's domain and the ability to send one HTTP request with a crafted `Cookie` header. This is fully repeatable against any number of victim shops.

### Recommendation
Do not treat the raw session-cookie value as a trusted, self-authenticating identifier. Either (a) bind the cookie to a server-side, randomly generated opaque token that is looked up (not derived) to find the real deterministic session ID, or (b) sign/HMAC the cookie value with the app's secret and verify that signature inside `cookie_session_id` before returning it, so an attacker cannot forge or predict a valid cookie value without knowledge of a server-side secret.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (conceptual addition)
def test_cookie_session_id_accepts_attacker_forged_shop_id_with_no_signature_check
  forged_cookie = { "shopify_app_session" => "offline_victim-shop.myshopify.com" }

  # No HmacValidator, no ShopValidator, no JWT check is invoked anywhere in this call.
  result = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookie, false)

  assert_equal "offline_victim-shop.myshopify.com", result
end
```
This demonstrates that `current_session_id` returns exactly the attacker-chosen string with no validation performed anywhere in the call chain, confirming the broken binding.
