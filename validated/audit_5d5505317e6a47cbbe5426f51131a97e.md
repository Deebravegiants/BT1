### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the tenant-identifying fields (`shop`, `topic`, `webhook_id`) are read directly from HTTP headers that are never included in the signed data. `ShopifyAPI::Utils::HmacValidator.validate` only proves that the *body* was produced by someone possessing the app's `client_secret`; it says nothing about which shop or topic that body belongs to. `ShopifyAPI::Webhooks::Registry.process` then trusts `request.shop` and `request.topic` unconditionally when dispatching to the registered handler, breaking the intended binding "shop attributed to a webhook" = "shop the HMAC actually authenticates."

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is fed into the signable string. The `shop`, `topic`, and `webhook_id` accessors instead read directly from HTTP headers: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` then dispatches using the unauthenticated `request.shop` / `request.topic` fields after only checking that the body-HMAC is valid: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is a single per-app secret shared across *every* shop that has installed the app — not a per-shop secret — any valid `(raw_body, hmac)` pair generated for one shop's webhook (which a merchant or attacker-owning-a-shop can trivially obtain from their own legitimately delivered webhooks) remains a cryptographically valid pair. An attacker who owns/operates their own shop with the app installed can capture their own webhook `(body, X-Shopify-Hmac-SHA256)` and then submit that exact pair to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to name a *different* victim shop. `HmacValidator.validate` will still return `true` (it only checks the body against the shared app secret), and `Registry.process` will hand the attacker-supplied body to the handler tagged with the victim's shop identity via `WebhookMetadata`. This breaks the equality "the shop the HMAC authenticates" == "the shop the handler believes the data came from," which is exactly the same class of business-logic/identity-binding gap identified in the external report (data whose provenance is not covered by the intended validation is trusted by the workflow).

### Impact Explanation
This is a cross-tenant boundary violation: the gem's own webhook-processing logic (`Registry.process`) attributes attacker-controlled body content to an arbitrary victim shop identity, purely because the `shop-domain` header is not bound by the cryptographic check. Any host application that uses `request.shop`/`WebhookMetadata#shop` to key per-tenant state (e.g., to select which merchant's records to update, cache, or delete) can be made to apply attacker-supplied webhook data to another merchant's tenant, without ever needing the victim's or the app's real credentials — only requiring the attacker to run their own shop with the app installed. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Any unprivileged internet user can install the target app on their own free/dev Shopify store, trigger any webhook topic they are subscribed to (e.g., `orders/create`), capture the resulting `(raw_body, X-Shopify-Hmac-SHA256)` pair from their own store's traffic, and replay it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secret material, privileged account, or credential theft is required beyond controlling one's own shop — a normal, unprivileged capability.

### Recommendation
Bind the shop (and ideally topic) identity into the value that is cryptographically verified, rather than trusting the corresponding header independently of the HMAC:
- Compare the shop domain supplied in `X-Shopify-Shop-Domain` against the shop that the host application expects for the specific webhook endpoint/session context, and reject mismatches, or
- Have `Request#to_signable_string` incorporate `shop`/`topic` alongside the raw body so `HmacValidator.validate` cryptographically proves the pairing (this would require corresponding server-side signing changes on Shopify's side, so at minimum the gem should document/require callers to independently re-verify `shop` against their own session/tenant records before trusting `WebhookMetadata#shop`), and
- Update `Registry.process` documentation/behavior so integrators are explicitly warned that `request.shop` is unauthenticated header data and must not be used as the sole tenant key without additional verification against a known/installed-shop list.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (app's `client_secret` is shared across all installs).
2. Attacker triggers a webhook subscription (e.g., `orders/create`) on their own store and captures the legitimate `(raw_body, X-Shopify-Hmac-SHA256)` pair delivered to the app's webhook endpoint.
3. Attacker crafts a new HTTP request to the same webhook endpoint reusing the captured `raw_body` and `X-Shopify-Hmac-SHA256` header unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the HMAC over `raw_body` only, matches the (still-valid) signature, and returns `true`.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls the registered handler with `shop: request.shop` == `"victim-shop.myshopify.com"`, even though the body/content actually originated from the attacker's own store — demonstrating that shop identity is not bound by the HMAC check.
