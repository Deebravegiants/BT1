## Analysis

The Sherlock report describes `MarginTrading.sol` executing user-controlled calldata against an unchecked `_swapAddress`, letting `AllowedProxy` make arbitrary calls that steal tokens held by the contract. The closest analog in this Hyperbridge codebase is `CallDispatcher`, the shared helper contract used by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to execute attacker/user-supplied `Call[]` payloads while briefly holding bridged/escrowed tokens. [1](#0-0) 

`dispatch()` is `external` with **no access-control modifier at all** — any unprivileged account can call it directly, at any time, completely independent of any order or bridge message. It performs `to.call{value: call.value}(call.data)` for arbitrary `to`/`data` pairs, with only an `extcodesize` check.

`CallDispatcher` is a single shared/reused instance referenced from `_params.dispatcher` by every order in `IntentGatewayV2`: [2](#0-1) 

and also by `HyperFungibleToken`/`WrappedHyperFungibleToken` on every cross-chain receive with calldata: [3](#0-2) 

The project's own docs acknowledge the risk of approvals set through order calldata but frame it only as an order-author hygiene issue ("use exact amounts... since the dispatcher holds tokens temporarily"): [4](#0-3) 

That mitigation assumes only an order's *own* calldata can set an approval on the dispatcher. Because `dispatch()` has no caller restriction, an attacker doesn't need to place any order at all — they can call `CallDispatcher.dispatch()` directly to make the dispatcher `approve()` an arbitrary spender for an arbitrary ERC-20 token, or register malicious hooks (e.g., ERC1820 `tokensReceived`) on behalf of the dispatcher, since the dispatcher itself is `msg.sender` during the call. Any tokens that later transiently land in the dispatcher (predispatch/postdispatch legs of unrelated users' orders, or HFT calldata-execution mints) before the same-transaction sweep runs are then exposed to that pre-planted approval/hook.

### Title
Unauthenticated `CallDispatcher.dispatch()` lets any attacker pre-plant token approvals/hooks to steal funds transiting the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes arbitrary `Call[]` payloads with zero caller restriction. Because this single contract instance is reused by `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` to transiently hold users' bridged/escrowed tokens during predispatch/postdispatch execution, any unprivileged party can call `dispatch()` directly (outside of any order or bridge message) to grant themselves a standing ERC-20 `approve()` or register a malicious token-hook against the dispatcher for an arbitrary token, and later drain that token whenever it transits the dispatcher on behalf of other users.

### Finding Description
`dispatch()` has no access control: [1](#0-0) 

Any address (not just `IntentGatewayV2`/`HyperFungibleToken`) can call it and instruct the dispatcher (as `msg.sender` in the sub-call) to:
- call `IERC20(anyToken).approve(attacker, type(uint256).max)`, or
- call an ERC-1820-style registry to register an attacker-controlled `tokensReceived`/`tokensToSend` hook for itself.

The dispatcher is a single shared instance stored in `Params.dispatcher` and used across every order: [2](#0-1) 

and by the tron `IntentGatewayV2` predispatch flow, where user tokens are transferred to the dispatcher, arbitrary calldata is dispatched, then a balance-based sweep runs — all sequential external calls in one transaction: [5](#0-4) 

as well as by both HFT variants on every calldata-bearing receive: [3](#0-2) [6](#0-5) 

Because approvals/hook registrations set via `dispatch()` persist indefinitely (ERC-20 approvals never expire on their own, and hooks stay registered until overwritten), an attacker does not need to wait for or interact with any specific order — they simply pre-plant state on the dispatcher for popular tokens, then trigger drainage the next time that token transits the dispatcher, either via a hook callback fired mid-transaction (before the sweep executes) or by racing any window where dust is left un-swept because the sweep logic only clears balances of tokens explicitly listed in that particular order's `inputs`/`output.assets`: [7](#0-6) 

This mirrors the reported `MarginTrading.sol` bug class exactly: an unchecked, arbitrary-call surface (`_swapAddress`/`dispatch()`) lets an unprivileged actor cause the holder contract to grant approvals that are later used to steal funds belonging to other users of the same shared contract.

### Impact Explanation
The `CallDispatcher` transiently custodies real user/solver funds (input tokens being escrowed, output tokens delivered by solvers, and bridged HFT amounts) for every `IntentGatewayV2`/`HyperFungibleToken`/`WrappedHyperFungibleToken` user. A successful exploit results in direct, unauthorized token theft from whichever token type the attacker chose to pre-approve, drawn from funds belonging to unrelated users mid-transaction — concrete theft of funds reachable purely from an unprivileged, permissionless call.

### Likelihood Explanation
Calling `dispatch()` costs nothing beyond gas and requires no privilege, deposit, or order placement — it is directly reachable by anyone at any time. The remaining requirement (a token landing in the dispatcher with either a callback hook or dust left outside the per-order sweep scope) is protocol-flow dependent, but the setup step itself (planting the approval/hook) is trivial, free, and can be done proactively for any number of tokens in advance, making this a standing, low-cost backdoor into the shared dispatcher rather than a narrow one-off condition.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the authorized calling contract(s) (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), e.g., via a constructor-set allowlist of callers or per-deployment dedicated dispatcher instances instead of a single globally shared one. Additionally, consider enforcing that any `approve()` calls routed through `dispatch()` use bounded/exact amounts (rather than relying on a documentation-only recommendation), and ensure sweep logic clears the dispatcher's balance of every token actually touched during execution, not only tokens declared in the order's `inputs`/`output.assets`.

### Proof of Concept
1. Attacker (no prior interaction with the protocol) sends a transaction directly to the deployed `CallDispatcher` address, calling `dispatch(encoded)` where `encoded` decodes to `Call[]{ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) }`.
2. `CallDispatcher.dispatch()` executes this with no caller check, so `msg.sender` inside the `approve` call is the dispatcher itself, setting `USDC.allowance(dispatcher, attacker) = max`.
3. Attacker repeats step 1 for every popular token (DAI, USDT, WETH, etc.) and/or registers a malicious ERC-1820 `tokensReceived` implementer for the dispatcher address for any ERC-777-style token in use.
4. When any legitimate user's order or HFT-calldata delivery routes one of these tokens through the dispatcher (e.g., predispatch/postdispatch swap intermediate token, or `HyperFungibleToken.onAccept` minting to `_dispatcher` with `data`), the attacker's pre-planted hook fires (or a sweep-scope gap leaves dust), and the attacker calls `USDC.transferFrom(dispatcher, attacker, balance)` to drain the tokens before/around the automatic sweep-back to the gateway.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
