Confirmed: the `shop-domain` header (`ShopifyAPI::Webhooks::Request#shop`) is never included in the HMAC-signed content — `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), and `Utils::HmacValidator.validate` only checks that raw body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-22`). Yet `Registry.process` trusts `request.shop` unconditionally and hands it straight to the app's webhook handler as the tenant identifier (`lib/shopify_api/webhooks/registry.rb:188-199`, `lib/shopify_api/webhooks/webhook_handler.rb:6-11`).

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only the raw request body. The `shop` value, read from the `X-Shopify-Shop-Domain` (or legacy `Shopify-Shop-Domain`) header, is completely outside the HMAC's scope. Because Shopify signs webhook payloads with a single app-wide `client_secret` shared across every shop that installs the app, a party holding one valid `(raw_body, hmac)` pair from any shop's webhook can present that same pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, since it never covered the header, and `Registry.process` forwards the attacker-chosen `shop` value to the app's handler unchecked.

### Finding Description
The identity binding that should hold is:
`shop header value == shop whose secret produced the HMAC`

In practice this equality is never checked. `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
and `HmacValidator.validate`/`validate_signature` computes/compares the HMAC purely against that signable string and the app's `api_secret_key`: [2](#0-1) 

`Request#shop` is read straight from headers, with no cryptographic tie to the HMAC: [3](#0-2) 

`Registry.process` gates only on the HMAC, then passes `request.shop` directly into `WebhookMetadata`, which is delivered to the app's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

Because `api_secret_key` is a single per-app secret shared across all installing shops (not a per-shop key), any request bearing a body+HMAC pair that is valid for the app — regardless of which shop it originated from — passes verification. The `shop` field the handler relies on for tenant-scoped logic (e.g., "look up store record for this shop and update it with this body") is attacker-controllable independent of the signature. Documentation explicitly tells integrators to trust `data.shop` as the webhook's shop domain: [6](#0-5) 

### Impact Explanation
This breaks the shop-identity binding relied upon by every consumer of the gem's webhook processing API, enabling cross-tenant data confusion in the host application: an attacker who can obtain any one valid signed webhook payload for the app (e.g., by triggering a webhook-worthy event on their own installed shop, or intercepting one) can relabel it as coming from a different (victim) shop by only changing the `shop-domain` header, and the app's handler will process/store it under the victim shop's identity. Depending on how the host app uses `data.shop` (common patterns: looking up the shop's session/access token, updating shop-scoped database rows, deduplicating by `shop`+`webhook_id`), this can lead to writing attacker-controlled data into another tenant's records — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to possess one legitimately-signed `(raw_body, hmac)` pair for the shared app secret — readily obtainable by installing the app on any store the attacker controls and triggering a webhook, or from any recon of webhook deliveries. No access token, `client_secret`, or privileged account is required beyond routine, unprivileged use of the app as an installed merchant. The gem provides no guard against header/HMAC mismatch, so every consumer of `ShopifyAPI::Webhooks::Registry.process` inherits this gap unless they independently re-verify the shop out-of-band (which the gem's own docs do not instruct them to do).

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`) header values into the HMAC-verified content, or otherwise cryptographically tie them to the verified payload — for example, include the shop domain in `to_signable_string`'s canonical string signed by Shopify, or require the app to cross-check `request.shop` against a shop that is independently known to have an active webhook subscription/session before trusting it. At minimum, document prominently that `data.shop` is unauthenticated and must not be used to key sensitive per-tenant operations without additional verification.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`) with the shared `client_secret`.
2. Attacker triggers the webhook naturally, capturing the legitimate `raw_body` and `X-Shopify-Hmac-Sha256` value Shopify sent.
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the spoofed shop header; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on attacker-supplied body content under the victim shop's identity.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
