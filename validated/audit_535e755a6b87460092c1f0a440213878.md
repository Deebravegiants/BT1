### Title
Webhook `shop`, `topic`, and `webhook_id` identifiers are not covered by the HMAC signature, allowing cross-tenant spoofing via header replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` verifies nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Webhooks::Registry.process` nevertheless trusts `request.shop` (and `request.topic`) taken straight from these unauthenticated headers to build the `WebhookMetadata` handed to the app's webhook handler.

### Finding Description
The HMAC binding for inbound webhooks is defined here: [1](#0-0) 

`to_signable_string` returns `@raw_body` only. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `to_signable_string` (the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` treats a passing HMAC check as authorization to trust the whole `request` object — including `request.shop`, which is dispatched unchanged into `WebhookMetadata` and passed to the app-registered handler: [4](#0-3) 

This is the "field acted on but not covered by the HMAC" pattern: the identity binding that should hold is `hmac == HMAC(secret, body ++ shop ++ topic)`, but the actual check is `hmac == HMAC(secret, body)`. `shop` and `topic` are accepted as unauthenticated bytes and forwarded as if Shopify-attested.

Any entity that can receive a legitimately-signed webhook from Shopify for their own store (i.e., any merchant/attacker who installs the target app, or any third party who can observe/replay a delivered webhook body+HMAC — Shopify webhooks are typically not encrypted in transit beyond TLS, but signature reuse across headers is the issue regardless of how the pair is obtained) can replay the exact `(raw_body, hmac)` pair to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header value. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will invoke the merchant's webhook handler with attacker-chosen `shop`/`topic` values in `WebhookMetadata`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: apps rely on `WebhookMetadata#shop` to determine which merchant's data a webhook body applies to (e.g., "update/delete data for shop X"). An attacker controlling the `shop`/`topic` header on an otherwise validly-signed request can cause the host application to process attacker-supplied body content under a victim's `shop` identity, i.e., cross-tenant data confusion/injection. This meets the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
The `Request` class is documented/expected to be constructed directly from raw inbound webhook HTTP headers and body by host apps (see `docs/usage/webhooks.md` usage pattern and `test/webhooks/request_test.rb`), and `Registry.process` is the standard dispatch path. No secret, access token, or privileged account is required beyond the ability to obtain one validly-signed `(body, hmac)` pair from Shopify (e.g., from the attacker's own installed instance of the app) and resend it with modified headers to the target app's public webhook endpoint.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified signable content, or otherwise cryptographically authenticate them (e.g., include them in `to_signable_string`, or require the caller to separately verify shop/topic against a value obtained through an authenticated channel) before trusting them in `WebhookMetadata`. At minimum, document and enforce that `shop`/`topic` header values must not be trusted for authorization decisions unless independently corroborated (e.g., cross-checked against `Context`-known installed shops).

### Proof of Concept
1. Install/operate the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) so Shopify delivers a request with a valid `X-Shopify-Hmac-Sha256` for the JSON body `B`.
2. Capture `(B, hmac)`.
3. Send a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: hmac` (unchanged), but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body`.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host app to act on body `B` as if it belonged to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
