Confirmed: `WebhookMetadata.shop` is passed directly from `request.shop` (the `x-shopify-shop-domain` header) without being covered by the HMAC.### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header as the tenant identity handed to the app's handler. Because the shop domain is never part of the HMAC-signed material, any party who can obtain one validly-signed webhook body/HMAC pair for the shared app secret can replay it with an arbitrary `shop` header value and have the app process it as if it belonged to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from an HTTP header, independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` — the object handed to the app-supplied `WebhookHandler` — using `request.shop`, which was never checked against the HMAC: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated field forwarded straight to the handler: [4](#0-3) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac` — for a `Request` object that string is the raw body alone: [5](#0-4) 

The broken identity binding, stated as an equality that the code fails to enforce: `HMAC(raw_body, api_secret_key) valid` should imply `shop == tenant that produced raw_body`, but the implementation only proves the former and blindly trusts the latter from a mutable HTTP header. This is exactly the bug class in the report — "a field acted on but not covered by the HMAC" — the `shop` value that the app's handler uses to key its per-tenant logic (session lookup, database writes, order processing, etc.) is not part of what is cryptographically verified.

Contrast this with the OAuth callback path, where `shop` *is* included in the signed string (`AuthQuery#to_signable_string`), showing the library is aware that `shop` should normally be part of what's authenticated — but this discipline was not applied to the webhook path.

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop/tenant that installs the app (this is standard Shopify architecture, not attacker-obtained), any unprivileged internet user can:
1. Install the public app on their own (free) development shop.
2. Trigger a real event (e.g. create an order, update a product) that causes Shopify to send a genuinely-signed webhook — with a valid `X-Shopify-Hmac-Sha256` computed over a body the attacker fully controls the content of — to the app's public webhook endpoint.
3. Capture that raw HTTP request (body + HMAC unchanged) and replay it to the same endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain that also has the app installed.
4. Because `to_signable_string` never includes the shop header, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches the forged event to the app's handler tagged with the victim's shop.

This crosses the tenant boundary: the app's business logic (order fulfillment, inventory updates, financial records, etc., depending on the app) is executed under the victim shop's identity using attacker-controlled body content, with no access token, secret, or privileged account required — only the ability to install the app on one's own store, which is available to any internet user for a public app. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. The prerequisite (installing a public app on a free/dev store and triggering an event) requires no special privilege, and capturing/replaying an HTTP request is trivial. The vulnerability is structural — every webhook delivery is susceptible, not just an edge case.

### Recommendation
Bind the trusted shop identity to the signed payload before it is used:
- Prefer deriving/confirming shop identity from data that is part of the signed body (many Shopify webhook payloads include shop-identifying fields), or
- Require the app to look up and confirm that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it, or
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used for tenant-scoping decisions without an additional binding check, and consider incorporating the shop domain into `to_signable_string` if Shopify's webhook signing ever supports per-shop or header-inclusive signatures.

### Proof of Concept
```ruby
# Attacker installs the app on their own free dev store "attacker.myshopify.com"
# and triggers an event, e.g. via the Admin API, causing Shopify to POST a
# genuinely HMAC-signed webhook to the app's endpoint:
#
#   POST /webhooks
#   X-Shopify-Topic: orders/create
#   X-Shopify-Hmac-Sha256: <valid HMAC over BODY, computed with shared api_secret_key>
#   X-Shopify-Shop-Domain: attacker.myshopify.com
#   Body: BODY   # attacker fully controls contents (their own order)

# Attacker captures this request and replays it verbatim except for the shop header:
#
#   POST /webhooks
#   X-Shopify-Topic: orders/create
#   X-Shopify-Hmac-Sha256: <same valid HMAC, unchanged>
#   X-Shopify-Shop-Domain: victim-shop.myshopify.com   # forged
#   Body: BODY   # unchanged

request = ShopifyAPI::Webhooks::Request.new(
  raw_body: BODY,
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => VALID_HMAC_BASE64,   # still valid, body unchanged
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  },
)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because HMAC only covers raw_body

ShopifyAPI::Webhooks::Registry.process(request)
# => Handler#handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", body: BODY, ...)
# The app now processes attacker-controlled data attributed to the victim tenant.
