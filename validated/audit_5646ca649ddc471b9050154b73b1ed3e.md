### Title
Rounding-driven pool value decay lets an attacker permanently brick `Deposit` and `Withdraw` via `AmmError::CalcPnlError` in `calc_take_pnl` - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` in `program/src/processor.rs` enforces an assumed invariant — that the current pool value (`total_pc_without_take_pnl * total_coin_without_take_pnl`) is always `>=` the value recorded at the last pnl checkpoint (`target_orders.calc_pnl_x * calc_pnl_y`) — and hard-fails with `AmmError::CalcPnlError` if that assumption is violated, with no recovery path other than a code upgrade. This mirrors the Y2K `Carousel::mintRollovers` pattern: a function assumes an invariant that the protocol never actually guarantees is monotonic, and once violated the function (and everything that calls it) reverts forever.

### Finding Description
`calc_take_pnl` ( [1](#0-0) ) computes `pool_pc_amount.checked_mul(pool_coin_amount)` and compares it against `calc_pc_amount.checked_mul(calc_coin_amount)` (the values recorded in `TargetOrders.calc_pnl_x` / `calc_pnl_y` at the last deposit/withdraw/pnl-withdraw). If the current product is smaller, the function returns `Err(AmmError::CalcPnlError)` unconditionally ( [2](#0-1) ).

This function is called:
- Unconditionally in `process_deposit`, with no way to bypass it ( [3](#0-2) ).
- Unconditionally in `process_withdrawpnl` ( [4](#0-3) ).
- In `process_withdraw`, unless `amm.status == WithdrawOnly` (an owner-only status that a regular LP cannot set) ( [5](#0-4) ).

Critically, none of the four swap instructions (`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_in_v2`, `process_swap_base_out_v2`) call `calc_take_pnl` or update `target_orders.calc_pnl_x/y` — they only read `calc_total_without_take_pnl_no_orderbook` ( [6](#0-5) ) and perform the trade using truncating integer math (`swap_token_amount_base_in`/`swap_token_amount_base_out`, `checked_ceil_div` for fees). Every swap therefore has the potential to shift the pool's `pc*coin` product away from the last recorded `calc_pnl_x*calc_pnl_y` checkpoint purely through decimal-normalization rounding (`normalize_decimal_v2`/`restore_decimal` truncate via `checked_div`, see `program/src/math.rs:80-116`) — an unprivileged actor fully controls the sequence and sizing of swap instructions (`swap_base_in`/`swap_base_out`/v2), which are reachable by any signer with token balances.

Because the checkpoint (`calc_pnl_x`, `calc_pnl_y`) is only updated by `calc_take_pnl` inside deposit/withdraw, and swaps can freely move the raw vault balances between those checkpoints, an attacker who crafts a sequence of small/edge-case swaps that push `total_pc*total_coin` below the last recorded product can cause the next `Deposit` call (and most `Withdraw` calls) to permanently revert with `CalcPnlError`. There is no unprivileged remediation instruction: `AmmParams::Status` (`process_set_params`, [7](#0-6) ) requires the hardcoded `config_feature::amm_owner::ID` signer, and even that only unblocks `Withdraw` (via `WithdrawOnly`), not `Deposit`, which has no bypass at all.

### Impact Explanation
Once triggered, `process_deposit` becomes permanently unusable for that pool (no LP can add liquidity ever again), and `process_withdraw` is unusable for all LPs unless the privileged `amm_owner` proactively sets `WithdrawOnly` — which is not guaranteed and is outside the attacker's or LPs' control. This is a permanent freezing of LP funds/functionality for the pool, satisfying the "permanent freezing of user or LP funds" impact bar from an unprivileged, single-transaction-reachable trigger (a sequence of ordinary swap instructions).

### Likelihood Explanation
Likelihood depends on whether realistic rounding in `swap_token_amount_base_in/out`, `normalize_decimal_v2`, and `restore_decimal` can actually decrease `total_pc*total_coin` below the checkpoint recorded at the last deposit/withdraw for some token-decimal combination and swap-amount pattern. I was not able to fully construct/verify a concrete numeric counterexample within this session's iteration budget — the `checked_ceil_div` on fees is directional (rounds fees up, i.e., in the pool's favor), and swap output uses `swap_token_amount_base_in`/`_out` (definitions not fully inspected). This leaves genuine uncertainty about whether the invariant can actually be violated through normal/adversarial swap sequences alone, or whether it is truly monotonically non-decreasing by construction (in which case this would not be practically exploitable, similar to how the original Y2K report also relied on an admin-triggered rather than purely adversarial path).

### Recommendation
- Verify formally (or via fuzzing) that `total_pc_without_take_pnl * total_coin_without_take_pnl` is monotonically non-decreasing between pnl checkpoints under all valid sequences of `swap_base_in`/`swap_base_out` (v1/v2) instructions, accounting for decimal-normalization rounding.
- If it is not strictly guaranteed, replace the hard revert in `calc_take_pnl` with a graceful no-op path (skip pnl-taking and continue deposit/withdraw) instead of aborting the entire instruction, so a rounding-induced invariant miss cannot permanently disable `Deposit`/`Withdraw`.
- Add an owner-callable recovery/reset instruction for `TargetOrders.calc_pnl_x/y` so pools are not permanently bricked if the invariant is ever violated in practice.

### Proof of Concept
Not fully constructed — requires a concrete numeric sequence of swap instructions (using `swap_base_in`/`swap_base_out`) that, through `normalize_decimal_v2`/`restore_decimal` truncation, drives `amm_pc_vault.amount * amm_coin_vault.amount` (adjusted for `need_take_pnl_pc/coin`) below `target_orders.calc_pnl_x * calc_pnl_y` as recorded at the last successful `Deposit`/`Withdraw`, followed by a `Deposit` call that then reverts with `AmmError::CalcPnlError` on every subsequent attempt. Confirming this requires deeper analysis of `Calculator::swap_token_amount_base_in`/`swap_token_amount_base_out` (in `program/src/math.rs`, not fully read in this session) and a test harness exercising many swap iterations across various decimal configurations, which should be done with local test execution before treating this as confirmed.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
