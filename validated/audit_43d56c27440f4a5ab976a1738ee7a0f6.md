### Title
Operator QR-code authorization is reused for up to 23 hours based solely on a local timer, without re-checking backend validity - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::scan_remaining_qr_codes` and `scan_initial_qr_codes` treat a previously-validated operator QR code as still authorized purely based on an elapsed local `Instant` timer (`operator_qr_expiration_time`, default 23 hours), without re-querying the backend to confirm the operator is still valid. This mirrors the `AuctionHouse` bug class of trusting a local time window as a proxy for the true state of an external system (sequencer uptime / backend authorization), rather than actually verifying that state.

### Finding Description
The operator QR-code validity is established once via a network call to `backend::operator_status::request`, which returns `valid: bool` and `location_data` from the backend. [1](#0-0) 

After this single check, `OperatorData` is cached with a local `timestamp: Instant`, and subsequent signups reuse this cached authorization as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` — a purely local, backend-independent condition: [2](#0-1) 

The same pattern exists in `scan_initial_qr_codes`, which only re-scans/re-verifies the operator QR code once the local elapsed time exceeds `operator_qr_expiration_time`: [3](#0-2) 

`operator_qr_expiration_time` defaults to 23 hours and is a config value that governs this window, analogous to the fixed auction duration in the reported bug that assumes market/state conditions hold for a fixed time period without checking whether the authoritative external source (sequencer, or here the backend authorization service) is actually still confirming that state: [4](#0-3) 

Just as the `AuctionHouse` Dutch auction assumes a bid will occur within its duration without checking whether the sequencer (source of truth for price/liveness) is actually up, this code assumes an operator's authorization remains valid for the entire elapsed window without checking whether the backend (source of truth for operator validity) would still confirm it. If an operator's authorization is revoked, their account is suspended, or their location changes on the backend during that window, the orb will continue to accept signups under the stale, no-longer-valid operator authorization for up to 23 hours, since no re-verification call is made until the local timer expires.

### Impact Explanation
This can result in signups being processed under an operator authorization that the backend would no longer consider valid (revoked operator, changed location/country restrictions, etc.), because the orb never re-confirms operator authorization state — it only checks a local clock. This is a misattributed/unauthorized signup risk: signups get attributed to and gated by an operator identity/location that is stale relative to the backend's authoritative state, for a window controlled entirely by client-side elapsed time rather than a live check of the authorizing service.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an operator's backend authorization state to change (revocation, suspension, location change) within the up-to-23-hour reuse window while the orb continues operating with the cached operator data — a plausible but not everyday occurrence, similar to the low likelihood of the sequencer-outage scenario in the original report.

### Recommendation
Re-validate the operator QR/authorization with the backend periodically or before each signup batch, rather than relying solely on a local elapsed-time timer. Alternatively, shorten `operator_qr_expiration_time` significantly and/or force a fresh backend check whenever there is any indication of a network reconnect or backend config refresh, so that cached operator authorization cannot outlive the backend's actual view of validity for an extended, unchecked period.

### Proof of Concept
1. Operator scans QR; `verify_operator_qr_code` succeeds, `OperatorData.timestamp` is set to `Instant::now()`.
2. Backend later revokes/suspends the operator (e.g., fraud detected on operator account) or changes location restrictions.
3. Within `operator_qr_expiration_time` (default 23h), `scan_remaining_qr_codes` matches the `operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch and skips re-verification, reusing the (now stale) `operator_data` for subsequent signups.
4. Signups proceed under the stale operator authorization/location data until the local timer eventually expires, with no backend re-check having occurred in between.
