### Title
Stale delegate grant re-arms on NFT return, letting a former delegate drain the reacquired account - (File: contracts/controller/src/storage/account.rs)

### Summary
Controller delegate grants are stored as `DelegateGrant { granted_by, delegates }` keyed only by `account_id`, with no transfer epoch. `get_delegates` treats the grant as live whenever `granted_by == current NFT owner`. If the position NFT leaves the granting owner and later returns before any intervening owner calls `add_delegate`/`remove_delegate`, the old delegate list silently becomes authoritative again, and the delegate — an address the reacquiring owner may have forgotten or never known about — can `borrow` and `withdraw` the account's funds to an arbitrary recipient.

### Finding Description
`storage::get_delegates` filters the stored grant solely on `grant.granted_by == *owner`, so validity is decided by current NFT ownership rather than by when the grant was created (contracts/controller/src/storage/account.rs:176-181). `require_owner_or_delegate` accepts any `caller` that is both an active registered position manager and contained in that list (contracts/controller/src/account.rs:114-127). After that check, `process_withdraw` pays out to `to.unwrap_or(caller)`, an external recipient of the delegate's choosing (contracts/controller/src/positions/supply.rs:140-157), and `borrow` pays the borrowed assets out the same way.

Nothing in the NFT `transfer`/`transfer_from` path purges or versions the `Delegates(account_id)` entry; the only purge paths are the new owner's `add_delegate` (overwrite) or `remove_delegate` (storage delete at account.rs:236-238). A buyer who receives the NFT and never touches delegate entries — a normal workflow, since grants are invisible unless queried — leaves the previous owner's grant dormant but intact. If that same NFT is later transferred or sold back to the original `granted_by` address, the grant is immediately live again, and the stale delegate regains full spend authority over whatever collateral and borrowing power the account holds at that moment.

### Impact Explanation
Theft of user funds. The re-armed delegate can call `withdraw` with `to = attacker_address` to pull all withdrawable collateral, and `borrow` up to the account's LTV/health-factor limits, routing proceeds to itself. The returning owner has no on-chain signal that delegation was restored — no event or bump marks the re-activation — and the account's value at re-acquisition may be far larger than when the grant was made.

### Likelihood Explanation
Requires the specific sequence: owner A grants delegate D, NFT moves to B, B performs no delegate write, NFT returns to A, and D is still an active position manager. Each step is a normal unprivileged action (`position-nft::transfer`, `controller::add_delegate`). Position NFTs are intended to be tradable, so round-trips through marketplaces or OTC trades back to a prior holder are plausible; a malicious delegate can also actively arrange to sell the NFT back to the victim's address. Bounded by the delegate needing active manager registration, which keeps this at Medium rather than High.

### Recommendation
Version the grant by transfer epoch or owner-change nonce: e.g., store an `ownership_epoch` incremented in the controller's account-owner resolution whenever the NFT owner changes (or a monotonic counter maintained alongside `Delegates`), and require `grant.epoch == current_epoch` in `get_delegates`. Alternatively, have the controller hook the NFT transfer path to delete `ControllerKey::Delegates(account_id)` on every ownership change, so grants can never outlive the granting ownership.

### Proof of Concept
1. Alice owns account `A` (NFT id `A`) with collateral; governance registers contract `D` as an active position manager; Alice calls `add_delegate(caller=alice, account_id=A, delegate=D)`.
2. Alice transfers NFT `A` to Bob. `get_delegates(A, bob)` reads empty; `D`'s grant is dormant but still stored.
3. Bob uses the account normally, never calls `add_delegate`/`remove_delegate`, then sells/transfers NFT `A` back to Alice.
4. `get_delegates(A, alice)` returns `[D]` again (`grant.granted_by == alice`). `D` calls `withdraw(caller=D, account_id=A, withdrawals=[(collateral, 0)], to=Some(D))` and `borrow(..., to=Some(D))`, passing `require_owner_or_delegate` and draining the account within solvency gates.
