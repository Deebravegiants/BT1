## Title
Webhook `shop` field is unauthenticated by the HMAC signature, enabling cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw request body against the HMAC signature, then blindly trusts the `shop-domain` header to determine which tenant the event belongs to. The gem's documentation explicitly tells app developers that `Registry.process` "will verify the request did indeed come from Shopify" before calling the handler, but the signature covers only the body — not the shop identity — so this claim is false for the shop binding specifically.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` is read directly and unauthenticated from the `shop-domain` header: [2](#0-1) 

`HmacValidator.validate` computes the HMAC only over `to_signable_string` (the body), never incorporating the shop header: [3](#0-2) 

`Registry.process` then passes `request.shop` straight into the handler as the tenant identity, after only checking that HMAC-over-body is valid: [4](#0-3) 

This is exactly the pattern the reference report warns about: **a field acted upon (`shop`, used by the handler as the tenant key) is not covered by the binding check (the HMAC)**. The equality that should hold is:
`shop_that_signed_the_body == shop_passed_to_handler`
but the code only guarantees `hmac(body, secret) == received_hmac`; it never binds `shop` into that computation.

Documentation reinforces the false sense of security: developers are told the `data.shop` field can be used directly to route/store webhook data, and that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

### Impact Explanation
Any unprivileged internet user who operates their own Shopify store with the target app installed (a legitimate, unprivileged action) can:
1. Trigger a real webhook event on their own store, capturing the exact `raw_body` and its valid `X-Shopify-Hmac-Sha256` value (signed with the app's shared `client_secret`, but the attacker doesn't need to know the secret — they simply observe a legitimately-signed request Shopify sends to the app's public webhook endpoint).
2. Replay that exact `raw_body` + HMAC pair directly to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with an arbitrary victim shop domain.
3. Because HMAC validation ignores the shop header entirely, `HmacValidator.validate` still returns `true`, and `Registry.process` invokes the handler with `data.shop` set to the victim's domain while `data.body` is the attacker's own (attacker-controlled) payload.

Any handler that uses `data.shop` to select which tenant's records to create/update/delete (the pattern the docs themselves recommend: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-controlled data under a victim shop's identity — a cross-tenant data injection/impersonation, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
High. No credentials, TLS interception, or privileged account are required — only owning/installing the app on any store (which is the normal, unprivileged onboarding flow for a public app) and being able to send an arbitrary HTTP POST to the app's public webhook URL, which by design must be internet-reachable to receive Shopify's webhooks.

### Recommendation
Bind the shop identity into the HMAC-checked material, or otherwise cryptographically/authoritatively verify that the `shop-domain` header matches the shop the HMAC was actually generated for (e.g., by cross-checking against a shop known to be currently installed/authorized for the app, or by including relevant headers in the signable string if Shopify's webhook signing scheme supports it). At minimum, update `ShopifyAPI::Webhooks::Request#to_signable_string`/`HmacValidator` so the `shop` header cannot be swapped independently of the signed body, and update documentation to stop asserting that `Registry.process` fully "verifies the request did indeed come from Shopify" when only the body is authenticated.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Step 1: Attacker triggers a webhook on their own store (e.g. orders/create)
# and captures the raw body + valid HMAC that Shopify sent to the app's endpoint:
raw_body = '{"id": 1, "note": "malicious payload"}'
valid_hmac = "<hmac Shopify computed over raw_body with the app's client_secret>"

# Step 2: Attacker POSTs directly to the app's public webhook endpoint,
# reusing the same body + hmac, but swaps the shop header to a victim:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body+secret match)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
# The app now processes attacker-controlled data as if it belongs to victim-shop.
```
