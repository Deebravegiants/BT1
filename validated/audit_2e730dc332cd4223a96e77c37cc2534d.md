### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop-domain` header straight to the handler as the tenant identifier. Because the `shop` field is never included in the signed material, a party that possesses one *valid* (body, HMAC) pair for their own shop can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook for a different shop.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` show the HMAC is computed only from the raw body: [1](#0-0) [2](#0-1) 

`shop` is read from a separate, unauthenticated header: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, so it never touches `shop`: [4](#0-3) 

`Registry.process` uses this validation result as the sole authentication gate, then forwards `request.shop` verbatim to the handler as the tenant identity for the webhook payload: [5](#0-4) 

The equality the code implicitly assumes is: *`shop` used to attribute/route the webhook == the shop for which the HMAC was actually computed by Shopify*. In reality, the HMAC only proves "this body was signed with `api_secret_key`" — it says nothing about which shop the header claims to be from. Any actor who can obtain one valid `(raw_body, hmac)` pair (e.g., a legitimate merchant of the app receiving their own genuine webhook deliveries) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` / `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body and HMAC match), and `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the victim's domain, even though the body content actually belongs to the attacker's shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged internet user (a merchant/holder of the app on their own shop) can make the host application believe a webhook body originated from a different, victim tenant. Depending on how the host app's handler uses `data.shop` (e.g., keying database writes, triggering shop-scoped side effects, uninstall/redact flows), this enables cross-tenant data corruption or cross-tenant action injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high for any app that has more than one installing shop: it requires no access to `api_secret_key`, no TLS interception, and no social engineering — only the ability to receive one's own legitimate webhook (trivial for anyone who installs the app) and resend it with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the `shop` claim into the HMAC-verified material, or otherwise cryptographically tie the shop identity to the signed payload before trusting it — e.g., include the shop-domain in `to_signable_string`, or cross-check `request.shop` against a shop the app has an active, provisioned session/webhook registration for, before constructing `WebhookMetadata`. At minimum, document that `shop-domain` is unauthenticated and must not be trusted as an identity boundary by consuming applications.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a genuine webhook to the attacker's endpoint:
   - `x-shopify-hmac-sha256: <valid_hmac_of_body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id": 1, ...}`
3. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook route, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5)  which succeeds because it only checks the body/HMAC pair, and the handler is invoked with `shop: "victim.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled data under the victim's tenant identity.
