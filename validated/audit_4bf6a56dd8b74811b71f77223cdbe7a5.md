### Title
Webhook `shop` (tenant) field is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant identifier) is read from an unauthenticated header and passed straight through to the app's handler. This breaks the identity binding `authenticated_bytes == bytes_the_app_trusts_for_tenant_selection`, letting an unprivileged attacker replay a genuine, previously-observed webhook body under an arbitrary `shop-domain` header and have `Registry.process` accept it as valid for that victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the HMAC input: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` — the unauthenticated header value — directly to the app's handler as the tenant identity for the event: [4](#0-3) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` (and `host`) are explicitly included inside `to_signable_string` and therefore cryptographically bound to the HMAC: [5](#0-4) 

This shows the gem's own pattern elsewhere is to bind the tenant-identifying field into the signed payload — but `Webhooks::Request` fails to do so for `shop`. Since the app's HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, any party who can obtain one genuine `(raw_body, hmac)` pair — e.g., by installing the app on their own store and capturing the webhook Shopify sends them — can resend that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks `verifiable_query.to_signable_string` (the body), never the `shop` field: [6](#0-5) 

The equality that should hold but does not:
`bytes_covered_by_HMAC == bytes_the_app_uses_to_select_the_tenant`
Instead: `bytes_covered_by_HMAC (raw_body only) != tenant_field_used_by_handler (shop header, unauthenticated)`.

### Impact Explanation
This is a cross-tenant boundary violation: an attacker (any user able to install the app once, or who has observed one legitimate webhook) can make the app process attacker-controlled webhook content while attributing it to a shop domain they do not own or control, and the gem's own validation reports it as authentic. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select which merchant record to update, delete, or act upon), this enables cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high for any app that exposes a webhook endpoint publicly (as is required by Shopify's webhook delivery model) and that trusts `WebhookMetadata#shop` as the tenant key without independent verification (e.g., checking the `webhook_id` against a per-shop registration). The attacker only needs one authentic webhook body+HMAC sample, obtainable by installing the app on their own store — no secret, no privileged access, and no TLS interception required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is verified, similarly to how `AuthQuery#to_signable_string` binds `shop`/`host`/`state`. Since Shopify's wire format only signs the body, the gem should additionally cross-check the header-provided `shop`/`webhook_id` against the app's own webhook registration/subscription records before invoking the handler, rather than passing the raw header value straight through as trusted tenant identity.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Attacker sends a new POST directly to the app's public webhook endpoint with the same captured body and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (no HMAC check yet): [7](#0-6) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` and matches — validation succeeds despite the spoofed shop header: [8](#0-7) 
5. The handler is invoked with `shop: "victim.myshopify.com"` and the attacker-originated body, which the host app treats as an authentic event for the victim tenant: [9](#0-8)

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
