### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks is computed exclusively over the request body. The `shop` (tenant identity), `topic`, `webhook-id`, and `api_version` fields are all read straight from HTTP headers and are never included in the signed bytes. `Registry#process` trusts `request.shop` as the tenant identifier it hands to the app's `WebhookHandler#handle` via `WebhookMetadata`, without re-deriving or binding it to anything the HMAC covers.

### Finding Description
The identity binding that should hold is:
`bytes verified by HMAC == bytes used to attribute the webhook to a tenant (shop)`

In this gem:
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header. [1](#0-0) 
- For webhooks, `to_signable_string` is only `@raw_body`: [2](#0-1) 
- But `shop`, `topic`, `webhook_id`, and `api_version` are read from headers that are completely outside the signed payload: [3](#0-2) 
- `Registry#process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the host app's handler: [4](#0-3) 
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field the handler is expected to use as the tenant key: [5](#0-4) 

So the equality that should hold before/after verification is broken: before the attacker's request, `hmac` is valid for `(body_bytes, shop=A)` as delivered by Shopify to a merchant who installed the app on shop `A`; after the attacker's request, the same `(body_bytes, hmac)` pair is replayed with `shop` header rewritten to `B`, and `HmacValidator.validate` still returns `true` because it never inspects the `shop` header at all.

### Impact Explanation
Because the shared `api_secret_key` is identical for every merchant of the app, any merchant who installs the app (an unprivileged internet user with respect to other tenants) legitimately receives HMAC-signed webhook deliveries for their own shop. That merchant can capture a `(raw_body, hmac)` pair from their own genuine webhook and re-POST it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still accept it since the signature check never involves the shop header, and `Registry#process` will hand the host application a `WebhookMetadata` claiming the payload originated from the victim shop. If the host app uses `data.shop` to select which tenant's record/session to mutate (the intended and documented use of this field), this is a cross-tenant data-confusion/write vector — satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Any app merchant can trigger their own webhooks (e.g., updating a product, customer, or order) to obtain a validly-signed `(body, hmac)` pair, then simply replay the POST with a different `shop` header value. No secret material beyond what the attacker already legitimately possesses (as an installed merchant) is required, and no additional validation stands in the way inside this gem: `Registry#process` only checks the HMAC and the topic's registered handler. [6](#0-5) 

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-covered signable string, or otherwise cryptographically bind them, rather than trusting header values that sit outside the signature. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, and `Registry#process` should reject a webhook if the header-derived `shop` cannot be tied to the same trust boundary the signature vouches for (e.g., require the app to independently validate that the caller is authorized for that shop id before trusting `WebhookMetadata.shop`).

### Proof of Concept
1. Merchant M installs the app on `m-shop.myshopify.com`. M triggers a benign webhook (e.g., updates a product) and captures the raw POST: headers include `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: m-shop.myshopify.com`, with `raw_body` = `{"id":123,...}`.
2. M replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (all other headers/body unchanged).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`raw_body` only) and finds it matches — validation passes. [7](#0-6) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "victim-shop.myshopify.com"` and delivered to the host app's `handle` method as if it were a legitimate webhook from the victim shop, even though the victim never sent it. [8](#0-7)
