This confirms the exploit path. `ShopifyAPI::Webhooks::Registry.process` (in `lib/shopify_api/webhooks/registry.rb`) validates only `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`, and `Webhooks::Request#to_signable_string` (in `lib/shopify_api/webhooks/request.rb`) returns only `@raw_body`. The `shop` field (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is read directly via `Request#shop` and passed unauthenticated into `WebhookMetadata.new(topic:, shop: request.shop, ...)`, which `docs/usage/webhooks.md` explicitly tells host apps to trust as "The shop domain of the webhook" for tenant-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Title
Webhook `shop` (tenant) field is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw webhook body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The signable string used for that HMAC is `@raw_body` alone [2](#0-1) , while `shop` is read straight from the `shopify-shop-domain` header with no cryptographic binding to the body or the HMAC [3](#0-2) . The unauthenticated `shop` is then handed to the host application's handler as the tenant identity for the event [4](#0-3) [5](#0-4) .

### Finding Description
This gem's Admin API webhook HMAC secret (`api_secret_key`, the app's client secret) is shared across every shop that installs the app — it is not per-shop. `HmacValidator.validate_signature` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the received `hmac` header [6](#0-5) . For a webhook `Request`, `to_signable_string` returns only the raw JSON body, never the `shop`, `topic`, `webhook_id`, or `api_version` headers [2](#0-1) .

The intended equality this mechanism should enforce is:
`shop that authored/owns this webhook payload == shop attributed to this event by the app`

But because only the body bytes are signed, the actual enforced equality is only:
`HMAC(body, api_secret_key) == received_hmac`

Any attacker who can install the app on their own shop (a normal, low-privilege action — no special credentials required) will receive genuine webhooks from Shopify for their own shop with valid HMACs computed using the shared `api_secret_key`. Because the same secret validates webhooks for all installs of the app, the attacker can replay one of these self-generated, validly-signed webhook requests to the victim app's webhook endpoint while substituting the `shopify-shop-domain` header (and, if desired, `topic`/`webhook_id`) with a different (target) shop's domain. `HmacValidator.validate` still returns `true` because the body is unchanged, and `Registry.process` proceeds to invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen value [4](#0-3) .

The documentation explicitly instructs host apps to trust `data.shop` as the tenant identifier for subsequent per-shop work (e.g., enqueuing tenant-scoped jobs) [7](#0-6) , so this gem's public contract binds tenant identity to an unauthenticated header value even though a signature mechanism is present and could have covered it.

### Impact Explanation
This breaks the identity binding between the authenticated payload and the tenant it is attributed to, i.e. cross-tenant confusion. A host app that keys any side effect (data writes, notifications, deduplication state, per-shop workflows) off `WebhookMetadata#shop` as delivered by this gem can be made to process an attacker-supplied event body under a victim shop's identity, or vice versa attribute the attacker's own webhook traffic to a shop they don't control. This falls under the "cross-tenant access" Critical impact category, since the gem's own verification primitive (`HmacValidator`) is the mechanism relied upon to establish trust, and it does not cover the field the API contract says identifies the tenant.

### Likelihood Explanation
The prerequisite is only that the attacker can install the target app on a shop they control — an ordinary, unprivileged action available to any merchant/developer, not a leaked credential, TLS interception, or social engineering. Producing the forged request is a routine HTTP replay with one header changed. No `api_secret_key` or token theft is needed because the shared secret already validates the attacker's own legitimate traffic.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable material verified by `HmacValidator`, or otherwise cryptographically bind the shop domain conveyed in `WebhookMetadata` to the verified payload (e.g., cross-check the header-derived shop against a shop value embedded in and covered by the signed body, or require callers to pair the `shop` header with a server-side registration lookup keyed by webhook id/topic combination that was registered for that specific shop) rather than trusting the raw header as-is in `Webhooks::Request#shop` [3](#0-2) .

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` through the normal OAuth flow.
2. Shopify sends the attacker's app instance a legitimate webhook, e.g. `orders/create`, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures this raw request (body + HMAC unchanged) and re-sends it to the same app's webhook endpoint, replacing only the `x-shopify-shop-domain` header value with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object whose `shop` now returns `"victim-shop.myshopify.com"` while `hmac`/`to_signable_string` are unaffected because they never read the shop header [8](#0-7) .
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the same unchanged body and the shared `api_secret_key`, so it still matches and validation passes [9](#0-8) .
6. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and any tenant-scoped logic in the host app (as shown in the documented pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) now operates attributing the attacker's payload to the victim shop [10](#0-9) .
