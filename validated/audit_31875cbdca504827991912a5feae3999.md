Audit Report

## Title
JWT replay guard in `WorkflowMetadataHandler.Authorize` is check-then-act (non-atomic), allowing a captured JWT to be replayed via concurrent requests - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` authenticates unprivileged, internet-facing HTTP-trigger workflow-execution requests via JWT, relying on `jwtReplayCache` to prevent replay of a given `jti`. The replay check (`isReplay`) and the replay recording (`recordUsage`) are two independent, separately-locked operations rather than a single atomic check-and-set, so two concurrent requests carrying the identical JWT can both pass the replay check before either records usage.

## Finding Description
`Authorize` verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` (a read-locked cache lookup), then performs authorized-key/signer validation, and only afterward calls `h.jwtCache.recordUsage(claims.ID)` (a write-locked cache insert) [4](#0-3) . The underlying `jwtReplayCache` implements `isReplay` and `recordUsage` as separate critical sections under a `sync.RWMutex`, with no lock held across the check-then-record sequence in `Authorize` [3](#0-2) . This is a textbook TOCTOU: nothing prevents two goroutines handling two concurrent requests with the same `jti` from both observing "not yet used" and both proceeding through the rest of authorization before either records the usage.

## Impact Explanation
An unprivileged holder of a single signed JWT (e.g., one that has been observed/intercepted, or simply the legitimate client itself misbehaving/retrying) can fire two near-simultaneous requests to the gateway's HTTP-trigger endpoint and have both authorized, defeating the single-use guarantee the replay cache is designed to enforce. This can result in duplicate, unauthorized workflow executions from a single signed authorization, which maps to the in-scope "unauthorized job run" / gateway request impersonation impact class.

## Likelihood Explanation
The race requires no special privileges, network position, or credentials beyond a single valid JWT and the ability to send two concurrent HTTP requests — well within reach of an unprivileged client and trivially scriptable, though the race window is narrow (bounded by the time between the `isReplay` check and the `recordUsage` call).

## Recommendation
Make check-and-record atomic under a single `jwtReplayCache` write-lock critical section (e.g., a `checkAndRecord(jti)` method that reserves the `jti` immediately if absent and reports replay otherwise), and perform this reservation immediately after JWT signature verification, before other authorization work, rolling back only on legitimate downstream authorization failure if strict "success-only" recording is required.

## Proof of Concept
1. Generate one valid HTTP-trigger JWT (`jti = X`) signed by an authorized workflow key.
2. Fire two concurrent HTTP requests to the gateway's HTTP-trigger endpoint carrying the identical JWT.
3. Add a small sleep/delay (or rely on natural scheduling) between the `isReplay` check and `recordUsage` in `Authorize`, or use `go test -race` with a unit test that calls `Authorize` twice in parallel goroutines with the same `claims.ID`, asserting both return success — demonstrating that the second call should have been rejected but is not.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
