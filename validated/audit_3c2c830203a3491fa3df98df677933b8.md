### Title
Mutable `ignore_user_centric_signups` config re-read mid-signup can bypass server-side duplicate/fraud enrollment check - (File: src/plans/mod.rs)

### Summary
`MasterPlan::do_signup` snapshots several config fields (`self_serve`, `pcp_v3`, QR/relay timeouts) once at the start of the signup "batch" [1](#0-0) , but the decision of whether to skip the backend enrollment/duplicate-detection step is instead re-read fresh from the shared `Arc<Mutex<Config>>` at the very end of the same signup, long after capture and the biometric pipeline have completed [2](#0-1) . Because the global config is refreshed by an independent background task roughly every 10 seconds while a signup is in progress, the value of `ignore_user_centric_signups` used to decide enrollment can differ from the value in effect when the signup started.

### Finding Description
The orb-wide `Config` is stored behind `Arc<Mutex<Config>>` and updated by `DefaultPlan::config_update` in the observer broker, independent of any in-progress signup, on a `CONFIG_UPDATE_INTERVAL` of 10 seconds [3](#0-2) [4](#0-3) .

`do_signup` treats the signup as a single logical unit ("batch"): it takes one snapshot of config fields at the top of the function for consistent use through QR scanning and relay setup [1](#0-0) . However, deep into the same signup — after `biometric_capture`, `biometric_pipeline`, and `detect_fraud` have all run (a sequence that can take much longer than the 10-second config refresh interval) — the code re-locks the config and reads `ignore_user_centric_signups` fresh instead of using the value pinned at the start of the batch:

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    ...
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason)).await
        .is_success()
};
``` [2](#0-1) 

When `ignore_user_centric_signups` is `false` and `user_centric_signup` is true, the branch is taken that trusts the app's self-reported outcome and **skips** `enroll_user`, meaning the backend `signup_post`/`signup_poll` round-trip — which is explicitly documented as the mechanism that catches "Backend duplicates," "Backend inflight matches," and "Backend detected fraud" [5](#0-4)  — never executes for that signup. If this config flag flips between the start of the signup batch and this late check (an operator/backend-driven config push mid-signup), a single logical signup can non-deterministically either perform or skip the authoritative duplicate/fraud verification, exactly analogous to the Bancor market maker allowing the pricing formula to change mid-batch.

### Impact Explanation
If `ignore_user_centric_signups` transitions from `true` to `false` partway through a signup that started as user-centric, the enrollment decision becomes inconsistent with what the rest of the signup (QR handling, debug report, relay messaging) was built around — this is a correctness/consistency bug, but on its own doesn't grant unauthorized access.

The more serious direction is the reverse: if the flag is `false` at the start (server-side enrollment enforced by policy) but the orb's cached config is updated to `true` before this late check runs, the signup silently skips the backend's duplicate/fraud-detection round trip (`enroll_user::Plan::run` → `signup_post`/`signup_poll`), and the signup is marked successful based purely on the local `signup_reason == SignupReason::Normal`, even though the local `detect_fraud`/fraud-check pipeline in this build is a no-op ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS") [6](#0-5) . This effectively removes the only real safeguard against duplicate/misattributed enrollment for that specific signup, without any explicit operator intent tied to that particular signup — the outcome depends purely on network timing of an unrelated background config fetch.

### Likelihood Explanation
Exploiting this requires the orb's config to be updated by the backend while a signup is actively mid-flight — a window that plausibly spans many seconds to tens of seconds (QR scan, 3s pre-capture sleep, biometric capture, biometric pipeline, fraud detection), well beyond the 10-second background config refresh cadence. This does not require a malicious/compromised orb operator to intentionally target the race for a specific signup — any operator-triggered config push overlapping with an in-progress signup is sufficient to trigger the inconsistency, making it feasible under fairly ordinary operational conditions rather than requiring precise crafted timing by an attacker.

### Recommendation
Snapshot the entire signup-relevant `Config` (including `ignore_user_centric_signups`) once at the start of `do_signup`, alongside the other fields already destructured there [1](#0-0) , and thread that single snapshot through to the enrollment decision at line 639 instead of re-locking `orb.config` mid-signup. More generally, any config value that affects a decision made partway through a signup should be captured once at the start of that signup and reused, rather than re-read from the shared mutable `Arc<Mutex<Config>>` at arbitrary points during the batch — mirroring the fix applied to the Bancor market maker, which pinned the formula reference to the batch instead of allowing it to be updated mid-batch.

### Proof of Concept
1. Set backend config with `ignore_user_centric_signups = false` (server-side enrollment enforced) and start a user-centric signup (`user_centric_signup = true` in the user QR payload).
2. While the signup is between `biometric_capture` and the final enrollment decision (i.e., during `biometric_pipeline`/`detect_fraud`, which combined can take well over 10 seconds), push a backend config update setting `ignore_user_centric_signups = true`.
3. The observer's background `config_update` task [7](#0-6)  refreshes `orb.config` before `do_signup` reaches line 639.
4. `do_signup` re-reads `orb.config.lock().await.ignore_user_centric_signups` as `true`, takes the "trust user-centric" branch, and never calls `enroll_user` — the signup is marked successful without the backend duplicate/fraud check ever running, despite the config in effect at the start of the signup requiring it [2](#0-1) .
