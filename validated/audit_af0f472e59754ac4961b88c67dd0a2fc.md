### Title
Webhook `shop` domain is trusted unauthenticated while only the raw body is covered by the HMAC, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable material from the raw body only, while the `shop` (and `topic`/`webhook_id`) values are read directly from HTTP headers that are never included in the signature. `Registry.process` validates the HMAC and then forwards the unauthenticated `shop` header value straight to the app's webhook handler. Any party that can obtain one genuinely-signed `(body, hmac)` pair for the app (e.g. by installing the app on their own store) can replay that exact body/HMAC combination while substituting an arbitrary `x-shopify-shop-domain` header, since that header is never part of the signed data. The handler will process the payload as if it legitimately belongs to the victim's shop, breaking the tenant identity binding the whole webhook flow is supposed to guarantee.

The documented usage pattern explicitly instructs integrators to key merchant-specific side effects off this unauthenticated field, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`: [5](#0-4) 

The identity binding that should hold is:
`HMAC_valid ⇒ (body, shop, topic, webhook_id) all originated from Shopify for that shop`

but the code only guarantees:
`HMAC_valid ⇒ body originated from Shopify` (for *some* shop using this app's secret)

Since `api_secret_key` is shared across every merchant installation of the app, any unprivileged individual who installs the app on their own store receives genuinely HMAC-signed webhook requests. They can capture one such `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different, victim merchant. `Utils::HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the forged victim domain.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to route side effects (billing state, data deletion/cleanup on `app/uninstalled`, resource sync, per-tenant caches, etc.) to the correct tenant. An attacker-controlled account (any merchant who can install the app) can cause the handler to execute as though the event happened on a different, unrelated shop — a cross-tenant confusion/access primitive. Given the library's own documentation encourages keying tenant-specific actions off `data.shop`, this is exploitable by design in typical integrations. This is classified Critical per the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) — no access to `api_secret_key`, access tokens, or privileged accounts is required. They only need to capture a single legitimately delivered webhook and can replay it indefinitely against the app's public webhook endpoint with a forged shop header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed material, or otherwise cryptographically bind them to the signature (Shopify does not include these in its HMAC by protocol, so the gem should instead validate that `request.shop` corresponds to a shop with a known, previously-registered session/install for this app before trusting it, and/or expose this risk clearly in documentation so integrators don't key authorization decisions off the unauthenticated header). At minimum, update `docs/usage/webhooks.md` to warn that `data.shop` is not covered by HMAC verification and must be independently validated (e.g., against the app's installed-shop store) before being used for any tenant-scoped side effect.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `app/uninstalled`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
3. Attacker captures the raw body and HMAC, then resends the same body and HMAC header to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only hashes `@raw_body`, unchanged from step 2.
5. `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host app to run shop-scoped logic (e.g. cleanup/uninstall handling) against the victim's tenant.
