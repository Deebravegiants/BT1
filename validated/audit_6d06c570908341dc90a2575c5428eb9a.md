### Title
SSRF with app credentials: `exchange_token` builds the request host from an unsanitized JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` decodes a caller-supplied session token (JWT) and uses the `dest` claim verbatim as the hostname for the outbound `/admin/oauth/access_token` request that carries the app's `client_id`/`client_secret`. Every other credential-bearing flow in the same file and module (`migrate_to_expiring_token`, `client_credentials`, `refresh_token`) passes the shop through `Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is used to build a request host. `exchange_token` skips that step. ### Finding Description
This mirrors the report's bug class: a value is trusted and acted upon (used to construct the HTTP host that receives the `client_secret`) without going through the binding/validation check that a nearly identical code path enforces. `JwtPayload` only verifies that the JWT is signed with the app's own `api_secret_key` and that `aud == Context.api_key` — it never verifies that `dest` is actually a `*.myshopify.com`/trusted Shopify domain. [7](#0-6) 

`HttpClient#initialize` then builds `@base_uri` directly from `session.shop` (i.e., the unsanitized `dest_shop`): [8](#0-7) 

The identity binding that should hold is: `host that receives client_id/client_secret == a Shopify-controlled domain`. Because `dest` is only cryptographically bound to "was signed with our api_secret_key", not to "is a Shopify domain," any actor who can obtain a validly-signed session token for this app (e.g., a session token issued to the app for one shop, or one crafted through any other supported issuance path) with an attacker-controlled `dest` value can redirect the token-exchange POST — including `client_id` and `client_secret` — to an arbitrary host.

### Impact Explanation
This is High severity per the SSRF-with-app-credentials category: `client_secret` (the app's Shopify API secret) is sent in the POST body to a host derived from unsanitized attacker-influenced JWT content. Exfiltration of `client_secret` allows full app impersonation (Critical-adjacent), satisfying the "SSRF with the app's credentials" and "credential leakage" impact bars from the rules.

### Likelihood Explanation
Likelihood depends entirely on whether an attacker can obtain/craft a JWT satisfying `aud == Context.api_key` and signed with the app's `api_secret_key` but with an arbitrary `dest`. Note that `JwtPayload`'s HMAC check only requires knowledge of `api_secret_key` (which is out of scope per the rules — "anything requiring `api_secret_key` ... or leaked credentials" is explicitly excluded). Absent a way to obtain such a token without the secret, this reduces to a defense-in-depth/inconsistency issue rather than a directly exploitable unauthenticated bypass.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` in `exchange_token` before constructing `shop_session`/`HttpClient`, consistent with `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`.

### Proof of Concept
Not reproducible without a validly-signed JWT for the app's `api_key`, which requires `api_secret_key` — out of scope per the rules. The inconsistency (missing `ShopValidator.sanitize!` call in `exchange_token` vs. all sibling methods) is the concrete, provable root cause; a full unauthenticated exploit chain could not be demonstrated within the gem's own code without a credential the rules exclude.
