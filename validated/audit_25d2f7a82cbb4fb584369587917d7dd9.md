### Title
`validateSerialized` for Monero public keys accepts arbitrary strings with no hex/length checks, letting `assertStorageFormatLegacy` admit malformed data that later throws at read-time - (File: `features/public-key-provider/module/store/formats/serialization/monero-public-key.ts`)

### Summary
`validateSerialized` in `monero-public-key.ts` only checks that `spendPub`, `viewPub`, `viewPriv` are `typeof === 'string'`, with no hex-format or length validation. Since `assertStorageFormatLegacy` (in `formats/storage/legacy.ts`) relies solely on this function to gate persisted public-key entries, a restored backup/import containing three arbitrary (non-hex, arbitrary-length) strings under those field names passes the integrity check, is written to `StorageFormatLegacy`, and only fails later when `PublicKeyStore.get()` calls `serialization.publicKey.deserialize()`, which does enforce hex/length invariants via `assert`.

### Finding Description
The call chain is: `new StorageFormatLegacyBuilder({ data })` (`features/public-key-provider/module/store/formats/storage/legacy.ts:37-41`) → `assertStorageFormatLegacy(data)` (`legacy.ts:118-155`) → for each `publicKeyWithMetadata`, `serialization.publicKey.validateSerialized(publicKey)` (`legacy.ts:146-150`), which dispatches to `moneroKeys.validateSerialized` when the value is an object (`formats/serialization/index.ts:9-13`).

`moneroKeys.validateSerialized` (`monero-public-key.ts:17-25`):
```
typeof serialized === 'object' &&
serialized !== null &&
typeof spendPub === 'string' &&
typeof viewPriv === 'string' &&
typeof viewPub === 'string'
```
There is no check that the strings are valid hex or of the expected length (32/33 bytes typical for these keys). A malformed backup such as `{ spendPub: 'not-hex', viewPub: 'x', viewPriv: '💥'.repeat(10000) }` returns `true`, so `assertStorageFormatLegacy` accepts it and `StorageFormatLegacyBuilder` clones/persists it into the atom-backed store. [1](#0-0) [2](#0-1) 

The real hex/length validation only happens later in `deserialize` (`monero-public-key.ts:42-58`), which does `Buffer.from(serialized.spendPub, 'hex')` and then `assert(serialized.spendPub.length === 2 * spendPub.length, ...)`. This is only reached when `PublicKeyStore.get()` is called (`public-key-store.ts:126-127`), meaning the malformed entry sits accepted in storage until a later read throws an uncaught assertion error. [3](#0-2) [4](#0-3) 

### Impact Explanation
This is a data-integrity gate failure: `assertStorageFormatLegacy` is documented as existing specifically "to help prevent any erroneous data from being written to the store" (`legacy.ts:112-117`), but it fails to do so for Monero public keys because it defers all real validation to `serialize`/`deserialize`, which are not invoked at admission time. The practical impact is bounded to a Denial-of-Service on subsequent reads of that specific derivation-path entry (`PublicKeyStore.get()` throws an uncaught assertion error), or persistent storage of malformed/oversized public-key blobs. It does not directly leak secrets or bypass signing/auth, since `deserialize`'s length assertions still prevent using bogus keys for cryptographic operations — the malformed value simply blows up instead of silently succeeding. [5](#0-4) 

### Likelihood Explanation
Requires the attacker to control an import/restore path reaching `StorageFormatLegacyBuilder({ data })` (e.g., a maliciously crafted wallet backup/import file). Given such access, forging the three string fields is trivial and 100% reproducible — no cryptographic knowledge or secrets are needed, only object-shape knowledge that is visible directly in this open-source file.

### Recommendation
Tighten `validateSerialized` in `monero-public-key.ts` to enforce hex-string format and expected byte length for `spendPub`, `viewPub`, and `viewPriv` (e.g., via a shared `isHex(value, expectedByteLength)` helper), matching the same checks already performed in `deserialize`, so that `assertStorageFormatLegacy` truly rejects malformed entries at admission time instead of deferring failure to read-time.

### Proof of Concept
Unit test in `features/public-key-provider/module/store/__tests__/storage-format-legacy.test.ts` style:
```ts
import { StorageFormatLegacyBuilder } from '../formats/storage/legacy.js'

it('should reject Monero public key with non-hex/oversized fields', () => {
  const maliciousData = {
    fixture_account: {
      "m/44'/128'/0'": {
        publicKey: {
          spendPub: 'not-hex-at-all',
          viewPub: 'x',
          viewPriv: 'z'.repeat(100000),
        },
        chain: [0, 0, 0],
      },
    },
  }

  expect(() => new StorageFormatLegacyBuilder({ data: maliciousData })).toThrow()
})
```
Expected (current, vulnerable behavior): the constructor does NOT throw, because `validateSerialized` returns `true` on typeof checks alone — demonstrating the integrity gate is bypassed. After applying the recommended fix, this same test should throw, and a follow-up `publicKeyStore.get(...)` call on such a persisted-but-malformed entry should be shown to throw at deserialize-time in the current code, confirming the DoS-at-read-time impact.

const deserialize = (serialized: MoneroPublicKey) => {
  assert(typeof serialized === 'object', `expected serialized monero public key to be an object`)

  const spendPub = Buffer.from(serialized.spendPub, 'hex')
  const viewPriv = Buffer.from(serialized.viewPriv, 'hex')

      'assetNamePublicKeysMap in deserializedData must be object'
    )

        assert(

        )
        assert(
          typeof publicKeyWithMetadata === 'object',
          'publicKeysWithMetadata in deserializedData must be an object'
