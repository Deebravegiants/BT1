Confirmed: `WebhookMetadata.shop` is passed directly into every handler's `handle` call, forming the trust anchor apps use to attribute the webhook to a tenant, while the HMAC signature never covers that value.

### Title
Webhook shop-domain header is unauthenticated by the HMAC, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `api_version`, `webhook_id`) values from HTTP headers that are never included in the HMAC-covered payload, yet `Registry.process` treats a valid HMAC as proof of the whole request's authenticity, including the shop attribution handed to app-provided handlers.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 
while `shop` (and other identifying fields) are read straight from headers with no cryptographic binding to the body/HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC over that signable string, then forwards `request.shop` unchanged into the `WebhookMetadata` given to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms `HMAC(secret, raw_body)` matches, but `secret` is the app's single `api_secret_key`, shared across every shop that has installed the app: [4](#0-3) 

The intended binding is `hmac_valid(body, secret) == true` implies `shop header == originating shop`. Because the shop header is outside the signed content and the secret is shared across all tenants of the app, that equality does not hold: any user who can trigger a legitimate webhook to the app (e.g., by installing the app on their own store, shop A) obtains a `(raw_body, hmac)` pair that is valid under the app's secret. They can then POST that same body/hmac pair directly to the app's public webhook endpoint with `x-shopify-shop-domain` (or `shopify-shop-domain`) rewritten to a victim shop B. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` will call the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <attacker's own webhook body>, ...)`.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide. Any app that uses `request.shop`/`data.shop` to decide which merchant's records to update, uninstall, erase (e.g., GDPR `shop/redact`, `customers/redact`), or otherwise act on, can be made to perform cross-tenant actions using attacker-supplied body content attributed to an arbitrary victim shop — satisfying the "cross-tenant access" Critical impact category, since it lets an unprivileged user of the app forge events on behalf of any other installed shop without holding that shop's credentials.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged installer of the target app (to obtain one valid signed webhook body/HMAC pair) and network access to the app's public webhook endpoint to replay it with a forged shop header — no access token, `client_secret`, or privileged account is needed, matching the "unprivileged internet user" threat model. This is fully within the gem's own webhook verification code path, not a host-application misuse of a documented API.

### Recommendation
Bind the shop identity into the value that is actually authenticated: include the `shop-domain` header (and `topic`/`webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically tie the header-derived `shop` to the signed payload before it is exposed via `WebhookMetadata`, so a captured `(body, hmac)` pair from one shop cannot be replayed against another shop's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers/receives any webhook, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify (both are valid because `HmacValidator` only signs `raw_body` with the app's shared `api_secret_key`, as shown in `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing that exact `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` over `raw_body` only — it passes — and then invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, as seen in `lib/shopify_api/webhooks/registry.rb` lines 188-200.
4. Any app logic keyed off `data.shop` (e.g., "delete data for shop", "mark shop uninstalled") now executes against the victim shop using attacker-supplied data.
