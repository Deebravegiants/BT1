### Title
Flashloan-manipulable Uniswap V4 pool spot price used as unimpacted oracle for Simplex intent-solver order pricing - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's `UniswapV4FundingPlanner.getExoticTokenPrice` (and `computeDirectPoolPriceUsd`) derives the USD price of a "venue-priced" pair directly from a Uniswap V4 pool's current `sqrtPriceX96` (via `sdkPool.token0Price`/`token1Price`), with no TWAP, no size/impact term, and no execution-cost adjustment. This spot price feeds `resolveLegRates` in the filler's order-pricing pipeline, and is used both to size intent fills and, when `referencePrice`/`maxDeviationBps` guards are configured, to gate whether a fill proceeds at all.

### Finding Description
`getExoticTokenPrice` (`sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts:206-240`) iterates the solver's configured V4 positions and calls `computeDirectPoolPriceUsd`, which returns `sdkPool.token0Price`/`token1Price` verbatim as "the raw pool mid" [1](#0-0) . This is documented explicitly in the flow notes: *"`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96`... there is no size or impact term... `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost."* [2](#0-1) 

This price is consumed directly by the FX strategy's order-pricing path (`resolveLegRates` → `venuePriceMemo()` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice`), which picks the position with the largest pool liquidity and derives `rate = 1 / venueUsd` [3](#0-2) . The docs for operators confirm the pool "acts as the price oracle instead of a static curve," that pricing "trusts the live pool," and that the only mitigation — `referencePrice`/`maxDeviationBps` — is optional and, if omitted, "leave[s] the chain unguarded" [4](#0-3) .

This is structurally the same bug class as the OneRing exploit: a flashloan/large swap moves an AMM pool's spot price within a single block, and a dependent protocol treats that instantaneous spot price as ground truth to price a value-transferring operation (in OneRing's case, vault deposit/withdraw valuation; here, the amount of exotic token an intent solver commits to deliver for a fixed USD-denominated input). Even where `maxDeviationBps` is configured, an attacker only needs to move the pool within the configured tolerance band (a static, operator-chosen percentage) to obtain a favorably-priced fill — the guard bounds deviation from a reference, not manipulation resistance or execution-cost realism.

### Impact Explanation
A solver that prices "venue-priced" pairs (pairs configured under `[vault.uniswapV4]` without static bid/ask curves) can be induced to fill an intent order at a manipulated exchange rate. Because `computeLegPolicyOutput` "extends the mid linearly across the whole priced quantity" with no size/impact term [2](#0-1) , an attacker who transiently depresses the exotic token's pool price can submit/win an intent order that pays out disproportionately more exotic token per unit of USD input than the pool's true depth supports, extracting value from the solver's escrow-backed fill (and, since the exotic tokens are literally withdrawn from the solver's own V4 LP position via `planWithdrawalForToken`, directly drains solver-owned liquidity). This is a concrete theft-of-funds vector against the intent solver's committed capital, reachable by any party able to submit an order and briefly move the referenced pool (e.g., via a flash swap/flashloan), which is exactly the "intents escrow and bids" surface in scope.

### Likelihood Explanation
Likelihood depends on solver configuration: pairs relying on pool-based pricing without `referencePrice`/`maxDeviationBps` are explicitly "unguarded" per the docs [5](#0-4) , making exploitation straightforward. Even with the guard configured, an attacker can still profit by manipulating price within the allowed `maxDeviationBps` band, since the guard only rejects outliers relative to a static reference and does not account for the order's actual size/impact against the pool's real depth. Thin-liquidity V4 pools (which the planner explicitly may select, since it picks "the most-liquid qualifying pool" only among the solver's *own* configured positions, not necessarily deep market pools) make this cheaper to execute.

### Recommendation
Replace instantaneous `sqrtPriceX96`-derived spot pricing with a TWAP/observation-based price, or size-aware quoting that accounts for pool depth/impact rather than a linear extension of the mid price across the whole order quantity. Make `referencePrice`/`maxDeviationBps` mandatory (not optional) for any pool-priced pair, and tighten the deviation check to also validate against the order's notional relative to pool depth, not just a static percentage band.

### Proof of Concept
Not independently reproducible from the indexed context — this repo does not contain a fork test analogous to the OneRing `DeFiHackLabs` PoC. Conceptually: (1) attacker flash-swaps a V4 pool backing a solver's configured exotic-token position, moving `sqrtPriceX96` favorably; (2) attacker submits an intent order sized to exploit the resulting `venueUsd` price via `getExoticTokenPrice`/`resolveLegRates` before the pool reverts to equilibrium; (3) if a guard is configured, the manipulation is kept within `maxDeviationBps`; (4) the solver's `UniswapV4FundingPlanner.planWithdrawalForToken` withdraws exotic tokens from its own LP position at the manipulated rate to fill the order, realizing a loss for the solver / gain for the attacker.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers

[[pairs]]

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
