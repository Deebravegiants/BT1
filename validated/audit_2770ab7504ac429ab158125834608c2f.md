### Title
User-Centric Signup Flow Bypasses Backend Duplicate/Fraud Enforcement - ([File: src/plans/mod.rs])

### Summary
`Plan::do_signup` in `src/plans/mod.rs` has two branches for finalizing a signup: an orb-centric path that calls the backend enrollment endpoint (`enroll_user`, which performs `signup_post`/`signup_poll` and returns the backend's duplicate/fraud verdict), and a `user_centric_signup` path that skips this backend call entirely and derives `success` purely from a locally computed `signup_reason`.

### Finding Description
In `do_signup`, after biometric capture and PCP building, the code branches on `user_centric_signup`: [1](#0-0) 

When `user_centric_signup && !ignore_user_centric_signups` is true, `success` is set to `signup_reason == SignupReason::Normal` without ever calling `self.enroll_user(...)`, i.e. without ever making the network request (`signup_post`/`signup_poll`) that lets the backend perform its own duplicate-signup and fraud verification: [2](#0-1) 

The `signup_reason` used to gate this local decision is computed from `detect_fraud`, which in this build has had all fraud logic removed and unconditionally returns `false`: [3](#0-2) 

This is structurally the same bug class as the referenced GMX report: there are two code paths for finalizing/settling an operation (decrease-position via ERC20 vs. native ETH; here, orb-centric vs. user-centric signup completion), and the enforcement logic (protocol fee collection in GMX; backend-side duplicate/fraud enrollment check here) is only wired into one of the two paths. The alternate path silently skips the enforcement step that the rest of the system relies on for correctness.

### Impact Explanation
For user-centric signups, the orb never asks the backend to validate/register the enrollment via `signup_post`/`signup_poll`, meaning the backend-side duplicate detection and fraud verdict (the actual enforcement mechanism this codebase relies on for global uniqueness of a Worldcoin signup) is bypassed. Combined with the local `detect_fraud` being a stub that always returns `false`, a signup taking the `user_centric_signup` branch will be marked `Success` as soon as the local biometric pipeline succeeds, with no server round-trip to catch duplicates/fraud that the orb-centric path would have caught. This can result in signups being locally reported as successful/attributed without backend corroboration, a form of misattributed signup completion.

### Likelihood Explanation
`user_centric_signup` is a boolean returned by the signup backend as part of `authenticated_app_data` during user QR validation, not something a client can set directly in most circumstances (`backend/user_status.rs`). However, it is a live production flag (`ignore_user_centric_signups` is a config toggle that operators can flip only globally, not per-signup), so any code path in which app-side data legitimately produces `user_centric_signup = true` today, or any client capable of influencing the flag returned to the orb, results in this reduced-assurance completion path being taken with no additional server-side gate before the orb marks the signup as `Success`.

### Recommendation
Ensure the `user_centric_signup` path also performs (or awaits confirmation of) the same backend duplicate/fraud verification that `enroll_user` performs for orb-centric signups before setting `success = true`, rather than deriving success solely from the locally computed `signup_reason`. At minimum, restore real fraud-detection logic in `detect_fraud` (currently a no-op stub) so that the local `signup_reason` is not trivially `Normal` for every completed pipeline run.

Not applicable — this is a code-path/logic analysis based on `src/plans/mod.rs` `do_signup`/`detect_fraud`; no exploit harness is available in this ask-only investigation.

        &mut self,
        orb: &mut Orb,
        debug_report: &mut debug_report::Builder,
        capture: &biometric_capture::Capture,
        pipeline: Option<&biometric_pipeline::Pipeline>,
        signup_reason: SignupReason,

                s3_region_str: self.s3_region_str.clone(),

                pipeline,
                signup_reason,
            }
            .run(orb),
        )
        .await;
        dd_timing!("main.time.signup.user_enrollment", t);

        debug_report.enrollment_status(status.clone());
