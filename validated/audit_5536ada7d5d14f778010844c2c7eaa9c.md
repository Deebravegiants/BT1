### Title
Unvalidated swap venues can abuse a user's strategy authorization to drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied route bytes and forward them to the configured swap router without restricting the contracts named by that route. A malicious route can therefore place attacker-controlled pool code on the call stack beneath the user's authorized controller call. When that code invokes a token `transfer` from the user, Soroban records the transfer as a child of the user's authorization tree; if the user signs the poisoned simulated tree, the venue can transfer unrelated wallet assets to an attacker while still returning enough swap output to satisfy the strategy checks.

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` accepts an arbitrary `Bytes` route from the authorized caller and forwards it through `withdraw_and_swap_from_supply` into `swap_tokens_or_passthrough`. [1](#0-0) [2](#0-1) 

The controller authenticates only the top-level caller and later invokes `execute_strategy(controller, amount_in, swap)` with the caller-controlled bytes. Its post-call checks only measure the input-token spend and output-token receipt; they do not decode the route, identify venue addresses, or bound other calls performed while the route executes. [3](#0-2) [4](#0-3) 

The router route format identifies each hop's `pool` through the attacker-controlled `assets` registry and dispatches the selected venue to that address. [5](#0-4) [6](#0-5)  For example, a Soroswap hop invokes `get_reserves` and `swap` on the route-supplied pool address, so an arbitrary contract can execute inside the strategy call. [7](#0-6) 

Soroban authorization matching is not limited to calls made directly by the controller. The repository's authorization test demonstrates that a token transfer initiated by route-selected pool code is recorded beneath the user's `swap_collateral` authorization entry, and that signing that child permits the transfer. [8](#0-7) [9](#0-8) [10](#0-9) 

### Impact Explanation
This is theft of user funds. A malicious pool can transfer any spendable token held by the victim to an attacker, including assets that were never supplied to or listed by the lending protocol. The demonstrated transfer removes the victim's entire unrelated-token balance while the strategy still deposits the expected swap output. [11](#0-10) [12](#0-11) 

The impact is not bounded by `amount_in`, route minimum output, final health factor, controller token balances, or market risk parameters. Those controls protect the strategy's routed funds, while the malicious child transfer drains a separate wallet asset under the victim's signed authorization tree. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The attacker needs to induce the victim to execute a controller strategy containing the malicious route and then sign the authorization tree returned by simulation. This is reachable through the normal route-supplying path for `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, all of which accept route bytes from the caller. [15](#0-14) [16](#0-15) [17](#0-16) 

The malicious venue can return a fair-looking output, making the economic result of the route appear normal. The only visible warning is an additional child authorization in the transaction's auth tree; users or integrations that verify route economics without validating every recorded child invocation remain exposed. The repository test shows that the route succeeds in recording mode and that signing the recorded child authorizes the theft. [18](#0-17) [19](#0-18) 

### Recommendation
Do not allow route payloads to name arbitrary executable pool contracts. Resolve venues through immutable or governance-approved venue/pool identifiers, or maintain an authenticated pool registry checked before dispatch. Separately, make route verification mandatory in SDKs and wallet integrations: simulate the complete transaction, decode every `AuthorizedInvocation`, and reject any child call other than the exact expected token input transfer. Until venue identity is constrained on-chain, users must not sign strategy authorization trees containing unrelated token transfers.

### Proof of Concept
The existing host-level test constructs a `RogueHopPool` whose `swap` method calls `token::transfer(victim, attacker, amount)` for an unrelated wallet token. It then encodes that pool in the route and calls `swap_collateral` with Alice as `caller`, `SWAP_IN_USDC` as the withdrawn collateral, and `FAIR_OUT_ETH` as the expected output. [20](#0-19) [21](#0-20) 

In recording mode, the rogue transfer is attached as a child of Alice's `swap_collateral` invocation, Alice's wallet balance becomes zero, the attacker receives `WALLET_BALANCE`, and Alice still receives the fair ETH supply output. In enforcing mode, the same rogue transfer is rejected under an honest root-only tree but succeeds when Alice signs the poisoned child. [9](#0-8) [22](#0-21)

pub(crate) fn swap(ctx: &HopContext<'_>) {
    let token_in_is_0 = ctx.hop.token_in < ctx.hop.token_out;

    let no_args: Vec<Val> = vec![ctx.env];
    let (reserve_0, reserve_1): (i128, i128) = ctx.env.invoke_contract(
        &ctx.hop.pool,
        &Symbol::new(ctx.env, "get_reserves"),
        no_args,
    );
    let (reserve_in, reserve_out) = if token_in_is_0 {
        (reserve_0, reserve_1)
    } else {
        (reserve_1, reserve_0)
    };

    let requested_out = soroswap_amount_out(ctx.env, ctx.amount_in, reserve_in, reserve_out);
    if requested_out <= 0 {
        panic_with_error!(ctx.env, Error::ZeroOutput);
    }

    let token_client = token::Client::new(ctx.env, &ctx.hop.token_in);
    token_client.transfer(ctx.router, &ctx.hop.pool, &ctx.amount_in);

    let (amount_0_out, amount_1_out) = if token_in_is_0 {
        (0_i128, requested_out)
    } else {
        (requested_out, 0_i128)
    };
    let args: Vec<Val> = vec![
        ctx.env,
        amount_0_out.into_val(ctx.env),
        amount_1_out.into_val(ctx.env),
        ctx.router.into_val(ctx.env),
    ];
    let _: () = ctx
        .env
        .invoke_contract(&ctx.hop.pool, &symbol_short!("swap"), args);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();

    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        sub_invocations: std::vec![stolen_transfer],

    assert_eq!(s.wallet(&s.alice), 0);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])

    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);

    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
