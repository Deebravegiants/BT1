### Title
Webhook HMAC does not bind the `shop` (or `topic`) header, enabling cross-tenant webhook replay/spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw HTTP body only, while the shop identity used to dispatch and process the webhook is taken from an unauthenticated header. This breaks the intended binding `authenticated(bytes) == acted_on(shop)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies that `hmac` matches `HMAC(secret, to_signable_string)`, i.e. it authenticates the body bytes, never the shop or topic headers: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` and dispatch to the app's handler, treating this unauthenticated header value as the tenant identity for the event: [4](#0-3) 

Because a single `api_secret_key` is shared across every shop that installs the app, any merchant who has legitimately installed the app receives real webhooks with a valid HMAC computed over their own request body. That merchant (an unprivileged internet user with respect to any other tenant) can capture one such legitimately-signed webhook and resend it to the app's webhook endpoint after changing only the `x-shopify-shop-domain` header to name a different, victim shop. Since the header is outside `to_signable_string`, the HMAC computed over the (unchanged) body remains valid, so `HmacValidator.validate` still returns `true`. The app's handler then executes with `shop: request.shop` pointing at the victim tenant — an equality mismatch between what the HMAC authenticates (`body bytes` signed by the app's secret) and what the code acts on (`shop` header used as tenant key), i.e. `authenticated(body) ≠ authorized(shop header used for dispatch)`.

### Impact Explanation
This lets one tenant's legitimately-received webhook be replayed against the app under a different shop's identity, all while passing the gem's own HMAC check. Depending on how the host app's webhook handlers use `data.shop` (e.g. app/uninstalled, shop/redact, customers/data_request, or any handler that mutates state keyed by shop), this enables cross-tenant state corruption or disclosure without possessing the victim's credentials — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant who installs the app (a low-privilege, unauthenticated-w.r.t.-other-tenants party) can capture their own valid webhook (e.g. via a proxy) and replay it with a modified shop header. No access token, `api_secret_key`, or other privileged credential is required — only the ability to receive one's own app webhooks, which is a normal, unprivileged capability of any app installer.

### Recommendation
Bind the trust-sensitive identifiers into the signed material, or otherwise cryptographically tie the `shop`/`topic` headers to the authenticated payload before they are used to construct `WebhookMetadata`. At minimum, `Registry.process` should independently verify that `request.shop` corresponds to a shop the app has an active session/installation for (and ideally that the webhook was addressed to this app instance), rather than trusting the header value outright once the body-only HMAC passes.

### Proof of Concept
1. As a merchant, install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook request the app sends, e.g. body `{}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over "{}">`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled`
2. Resend the identical body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` still succeeds because it only checks the HMAC against `@raw_body`, per [1](#0-0) .
4. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, per [4](#0-3) , causing the app to act on the victim tenant using data supplied by the attacker.
