### Title
Webhook shop attribution is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop identity that the handler acts on (`request.shop`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the signed bytes. `Webhooks::Registry.process` validates the HMAC and then unconditionally trusts the header-derived `shop` value when dispatching to the app's handler, so the tenant binding `verified_bytes == acted_on_shop` does not hold.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header that is completely outside that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — it never touches the shop header: [3](#0-2) 

`Webhooks::Registry.process` validates only that body-bound HMAC, then forwards `request.shop` (the unbound header) straight into the handler as the tenant identifier: [4](#0-3) 

Because the shop header is never part of the signed payload, an attacker who possesses one legitimately-signed `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own store, which they control as an ordinary, unprivileged Shopify merchant/app installer) can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` calls the handler with `shop: <attacker-chosen shop>` even though the signed content actually originated from a different store. This is precisely the "field acted on but not covered by the HMAC" identity-binding break described in the analog bug class: `totalAllocPoint` diluting rewards because pool identity/weight wasn't re-validated is structurally the same defect as "shop" being trusted for tenant attribution without being bound by the same cryptographic check that authenticates the payload.

### Impact Explanation
This breaks the tenant boundary that host applications rely on this gem to enforce: `Webhooks::WebhookHandler` implementations key persistence, authorization, and business logic off `data.shop`, assuming it was verified alongside the HMAC. An attacker can cause the app to process/attribute genuine (HMAC-valid) webhook data under a shop domain of their choosing, i.e., cross-tenant confusion at the point where this gem hands verified data to the host app. This satisfies the Critical "cross-tenant access" impact category since the attacker crosses the shop/tenant boundary using only a body+signature pair they can legitimately obtain for their own shop.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint and one legitimately signed webhook payload the attacker can obtain by installing the app on their own (unprivileged) Shopify store and capturing/replaying the delivery — no `api_secret_key`, access token, or privileged account is needed. This is a realistic, low-effort attack path for any internet user who can install/interact with the target Shopify app as a merchant.

### Recommendation
Include the shop domain (and topic) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the request before it is trusted — e.g., verify the shop domain against session/installation state independent of the header, or require the signature to cover a canonical string that includes `shop-domain` and `topic` in addition to the raw body, matching Shopify's documented webhook verification guidance.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify delivers a legitimately HMAC-signed request to the app's webhook endpoint.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` header of that delivery (e.g. via a proxy they control, or because their own endpoint config allows them to log it).
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` and matches the replayed header — validation passes.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to process the attacker's own webhook payload as if it belonged to the victim shop. [4](#0-3)
