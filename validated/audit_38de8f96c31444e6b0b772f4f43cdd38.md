Based on the report's bug-class pattern ("a field acted on but not covered by the HMAC"), the closest in-scope analog is the webhook `Request` in this gem. [1](#0-0) 

### Title
Webhook shop-tenant binding is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `HmacValidator.validate` in `Registry.process` authenticates the body bytes only. The `shop` value (read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) that is subsequently used as the tenant identity for the webhook is never part of the signed content. [2](#0-1) [3](#0-2) 

### Finding Description
`Registry.process` verifies the incoming webhook using `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, request.to_signable_string)` and compares it to the `hmac` header value: [4](#0-3) 

`to_signable_string` is defined to be exactly `@raw_body` — it does not include `shop`, `topic`, `api_version`, or `webhook_id`, all of which come straight from HTTP headers: [5](#0-4) 

The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. In this implementation that equality does not hold — the HMAC only proves "this body byte-string was authorized by someone holding the api_secret_key at some point," while the `shop` used to build `WebhookMetadata` (and passed to the handler for tenant-scoped processing, e.g., looking up the merchant record or writing tenant data) comes from an unauthenticated header.

Any actor who can obtain one legitimate `(raw_body, hmac)` pair — for example an unprivileged user who installs the app on their own store and thus receives genuine webhook deliveries with a valid signature over the body — can replay that exact body and signature to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still accept it because it never looks at that header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the source: [6](#0-5) 

If the host application trusts `data.shop` to select the tenant record/session to act on (the intended and documented use of this field), this allows an attacker to inject attacker-controlled webhook payloads that are processed as if they belonged to a different merchant — a cross-tenant identity-binding break, directly analogous to the "amount not covered by fillCompleted/amount binding" flaw in the report (a value trusted for downstream action that isn't covered by the verification check).

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on when reading `WebhookMetadata#shop`, enabling cross-tenant data injection/confusion using only the attacker's own legitimately-issued webhook (no access to another merchant's token or the app's `client_secret` is required). This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target public app on an attacker-controlled shop (or otherwise obtain one valid raw_body+hmac pair for the app), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No secrets need to be guessed or leaked — the HMAC math simply never touches the header being trusted.

### Recommendation
Bind the tenant-identifying header(s) into the signed content actually verified, or otherwise verify that the `shop-domain` header matches a shop known to have this webhook/topic legitimately registered before trusting it for tenant-scoped effects downstream. At minimum, document clearly that `request.shop`/`WebhookMetadata#shop` is not cryptographically authenticated and must not be used as a sole tenant-selection key by consuming applications.

### Proof of Concept
1. Attacker installs the target public Shopify app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`), capturing the resulting raw request body `B` and the genuine `x-shopify-hmac-sha256` value `H` that Shopify computed over `B`.
2. Attacker sends `POST <app-webhook-endpoint>` with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes HMAC over `to_signable_string` (`== B`) and it matches `H`, so verification passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
