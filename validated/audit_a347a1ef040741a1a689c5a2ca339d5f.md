Audit Report

## Title
`add_tip` in `pallet_snowbridge_system_frontend` omits the `Halted` operating-mode check enforced on `register_token`, allowing users to swap/burn assets and dispatch XCM to Bridge Hub during a halt - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`register_token` in `pallet_snowbridge_system_frontend` explicitly checks `ExportOperatingMode`/`Halted` before proceeding, while the sibling extrinsic `add_tip` does not, even though both call the same shared helpers (`swap_fee_asset_and_burn`, `send_transact_call`) that burn user assets and dispatch an XCM `Transact` to Bridge Hub. [1](#0-0) [2](#0-1)  This is a genuine, verified code inconsistency, and any signed account can trigger `add_tip` without the halt check being applied at that call site.

## Finding Description
`ExportOperatingMode<T>` is a governance/root-controlled halt flag [3](#0-2) . `register_token` gates on it with `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);` before calling `swap_fee_asset_and_burn` and `send_transact_call` [4](#0-3) . `add_tip` calls the identical `swap_fee_asset_and_burn`/`send_transact_call` helpers but performs no such check [2](#0-1) .

However, the pallet-local `ExportOperatingMode` is not the only enforcement point for the halt semantics. The pallet also implements `ExportPausedQuery`, which is consumed by `PausableExporter` wired directly into the asset-hub `XcmRouter` for the leg that exports XCM directly to Ethereum's `GlobalConsensus` network [5](#0-4) [6](#0-5) . That check is confirmed by an emulated integration test showing direct exports to Ethereum are blocked when the frontend pallet is halted [7](#0-6) .

Critically, both `register_token`'s and `add_tip`'s `send_transact_call` route their XCM to `T::BridgeHubLocation` (a sibling parachain, via `Transact`), not directly to the Ethereum `GlobalConsensus` network [8](#0-7) . That means neither extrinsic's Bridge Hub-bound XCM passes through the `PausableExporter`/`ExportPausedQuery` gate at all — that gate only protects direct-to-Ethereum XCM traffic on the `XcmRouter`. The *only* protection against the local swap/burn/dispatch executing while halted is the pallet-local `ensure!` check, and that check is present in `register_token` but missing in `add_tip`. This confirms the claim's root cause exactly as described: the check is applied inconsistently between the two sibling extrinsics that reach the same shared logic.

On the Bridge Hub side, the backend `pallet_snowbridge_system_v2::add_tip` also performs no operating-mode check before crediting `InboundQueue::add_tip`/`OutboundQueue::add_tip` [9](#0-8) , so there is no compensating halt enforcement downstream either.

## Impact Explanation
When governance halts the frontend pallet via `set_operating_mode(Halted)`, a normal signed user can still call `add_tip`, causing the pallet to swap an arbitrary configured fee asset for Ether (or burn Ether directly) via `swap_fee_asset_and_burn`, and dispatch an XCM `Transact` `AddTip` call to Bridge Hub via `send_transact_call` — with none of this gated by the halt flag. This directly undermines the intended effect of `set_operating_mode(Halted)`, allowing continued asset burns/swaps and cross-chain messaging traffic while the operator believes the export path is stopped. This is a real, concrete inconsistency between two dispatchables performing near-identical operations in the same pallet, matching a legitimate "missing check" class of finding, though the downstream impact is bounded to tip/reward-related traffic to already-committed messages rather than creating a wholly new asset export to Ethereum.

## Likelihood Explanation
High. `add_tip` is a normal signed extrinsic (`ensure_signed(origin)?`) requiring no special privilege, and any account holding a supported fee asset can trigger it at any time, including immediately after a root-triggered halt.

## Recommendation
Add `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);` at the start of `add_tip`, mirroring the check in `register_token`, so the halt flag uniformly gates every dispatchable that reaches `swap_fee_asset_and_burn`/`send_transact_call`. Additionally, consider whether the backend `pallet_snowbridge_system_v2::add_tip` on Bridge Hub should also check its own operating mode before crediting reward tips, since it currently has no such check either.

## Proof of Concept
1. Root calls `SnowbridgeSystemFrontend::set_operating_mode(Halted)` on Asset Hub, setting `ExportOperatingMode::<T>` to `Halted`.
2. A regular signed user with a fee asset balance calls `add_tip(origin, message_id, asset)`.
3. Because `add_tip` has no halt check, it proceeds to swap/burn the user's asset via `swap_fee_asset_and_burn` and successfully dispatches the `Transact` XCM to Bridge Hub via `send_transact_call`, despite the pallet being halted — while an equivalent call to `register_token` under the same halted state would fail with `Error::<T>::Halted`.

pub struct PausableExporter<PausedQuery, InnerExporter>(PhantomData<(PausedQuery, InnerExporter)>);

impl<PausedQuery: ExportPausedQuery, InnerExporter: SendXcm> SendXcm
	for PausableExporter<PausedQuery, InnerExporter>
{
	type Ticket = InnerExporter::Ticket;

	fn validate(
		destination: &mut Option<Location>,
		message: &mut Option<Xcm<()>>,
	) -> SendResult<Self::Ticket> {
		match PausedQuery::is_paused() {
			true => Err(SendError::NotApplicable),
			false => InnerExporter::validate(destination, message),
		}
	}

	fn deliver(ticket: Self::Ticket) -> Result<XcmHash, SendError> {
		match PausedQuery::is_paused() {
			true => Err(SendError::NotApplicable),
			false => InnerExporter::deliver(ticket),
		}
	}
}

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
