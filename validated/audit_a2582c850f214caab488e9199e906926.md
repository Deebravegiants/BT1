### Title
Unrefunded Excess Native Token in `IntentGatewayV2.placeOrder` (Tron) Permanently Locks User Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron variant of `IntentGatewayV2.sol`, `placeOrder` performs an exact-output native-to-fee-token swap via `swapETHForExactTokens` when the user pays the order fee with native token (`msg.value`), but unlike the main EVM implementation, it never refunds the unspent portion of `msgValue` back to the caller. Any native token sent in excess of what the swap actually consumes is silently retained by the contract and lost to the user.

### Finding Description
`placeOrder` in the Tron contract computes `msgValue = msg.value` and, when `order.fees > 0` and `msgValue > 0`, swaps native token for the exact fee amount: [1](#0-0) 

`swapETHForExactTokens` only consumes as much native token as the pool requires to deliver `order.fees` of the fee token; any leftover is refunded by the router to the caller of the swap — i.e., to this contract (`address(this)`), not to the user. The function then proceeds directly to `emit OrderPlaced(...)` without ever returning the unspent `msgValue` (or the router's native refund) to `msg.sender`: [2](#0-1) 

This is the exact bug class from the external report: an operation that is supposed to consume only part of a user-supplied amount (here, an exact-output swap) leaves a residual amount unrefunded on a path where the refund step is missing, so the excess is absorbed by the contract instead of being returned to the payer.

By contrast, the primary EVM implementation (`evm/src/apps/IntentGatewayV2.sol`) explicitly tracks `amounts[0]` spent by the swap and refunds any leftover native value to the user: [3](#0-2) 

The Tron contract has no equivalent `msgValue -= amounts[0]` accounting nor a final `if (msgValue > 0) refund` step, confirming the refund logic present in the canonical implementation is missing in this variant.

### Impact Explanation
Any user placing an order on the Tron deployment and paying the solver/protocol fee with native token will permanently lose the unspent portion of the native token they sent with the transaction — it is neither escrowed for the order, tracked as protocol dust, nor recoverable through `cancelOrder`/`withdraw`, since those functions only operate over `order.inputs` and `TRANSACTION_FEES` escrow entries, not over stray native balance. Because users commonly overestimate the native amount needed for the fee swap (as documented in the SDK/docs guidance for the main EVM path, which relies on this exact refund to make sending "generous" native values safe), this results in real, permanent loss of user funds on every fee-swap-by-native-token order placed through this contract.

### Likelihood Explanation
High likelihood: this path executes on every `placeOrder` call where `order.fees > 0` and the caller supplies native token instead of the fee token directly — a normal, documented flow (see `docs/content/developers/evm/intent-gateway/placing-orders.mdx`, which explicitly says "unused native is refunded" for this flow). No malicious actor or special conditions are required; it triggers automatically whenever the native amount sent exceeds the exact amount the AMM needs.

### Recommendation
Mirror the canonical EVM implementation: capture the `amounts` array returned by `swapETHForExactTokens`, subtract the actually-spent amount from `msgValue`, and refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder` (and audit `fillOrder`/other native-value-accepting entry points in the Tron contract for the same missing refund pattern).

### Proof of Concept
1. User calls `placeOrder{value: 5 ether}(order, graffiti)` on the Tron `IntentGatewayV2`, with `order.fees = 1 * 1e18` (fee token units) and no `order.predispatch`.
2. `msgValue = 5 ether`; since `order.fees > 0` and `msgValue > 0`, the contract calls `swapETHForExactTokens{value: 5 ether}(order.fees, path, address(this), block.timestamp)`.
3. The router only needs, say, `0.01 ether` to produce `order.fees` of the fee token; it refunds `4.99 ether` to `address(this)` (the gateway), not to the user.
4. `placeOrder` finishes and emits `OrderPlaced` without ever touching the remaining `msgValue`/native balance.
5. The `4.99 ether` is now permanently stuck in the `IntentGatewayV2` contract, unassociated with any escrow entry, and unrecoverable by the user through any public function.
