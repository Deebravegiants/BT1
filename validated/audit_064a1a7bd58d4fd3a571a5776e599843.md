### Title
Missing per-token uniqueness check in `runAction`/`handleOut` allows duplicate `erc20TokenAddresses` entries to drain stranded/dust balances beyond `-deltaAmountChanges` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` snapshots balances into `balancesBefore`/`balancesAfter` and derives a per-index `balanceChange` that is transferred out via `handleOut` and turned into an output UTXO, but it never enforces that `circomData.erc20TokenAddresses` contains unique addresses. An attacker who is fully in control of `erc20TokenAddresses` ordering/content and `deltaAmountChanges` can list the same token twice; both indices independently read the same on-chain balance and both independently trigger a `transferERC20TokenOrETH` payout, so the action pays out the token's raw balance delta once per duplicate index instead of once total, letting the attacker cash out any dust/stranded balance sitting in the contract from a prior transaction, well beyond `-deltaAmountChanges` actually funded to the action in that transaction.

### Finding Description
The invariant the protocol relies on is: **tokens leaving the action in a tx == `-deltaAmountChanges` Hinkal sent it that tx.**

The relevant loop: [1](#0-0) 

For each index `i` in the attacker-supplied `circomData.erc20TokenAddresses`, `balanceChange` is computed purely from the *current on-chain ERC20/ETH balance* of that address, snapshotted before and after the ops run: [2](#0-1) [3](#0-2) 

There is no check that the addresses in `circomData.erc20TokenAddresses` are distinct. If the same token address `T` appears at two indices `i1` and `i2`, `balancesBefore[i1] == balancesBefore[i2]` and `balancesAfter[i1] == balancesAfter[i2]` because they are both queries against the *same* physical `T.balanceOf(address(this))`. Each index independently computes its own `balanceChange`, adjusted by that index's own `deltaAmountChanges[i]`: [4](#0-3) 

and then independently calls `handleOut`, which unconditionally transfers `uint256(balanceChange)` of `T` to `msg.sender` and mints a UTXO record for it: [5](#0-4) 

Because the raw "after − before" component of `T`'s balance is a single physical quantity but is read and paid out **once per duplicate index**, the sum of payouts for `T` across `i1` and `i2` can exceed the single legitimate amount that `-deltaAmountChanges` for `T` actually represents. The second (or further) payout is only possible if the contract's actual `T` balance can still cover it after the first `transferERC20TokenOrETH` call succeeds — which is exactly the case when the action already holds a stranded/dust balance of `T` left over from a prior transaction (e.g., a partially completed op, rounding leftover, or a previous multi-leg action that never fully swept its balance). That dust silently backs the phantom second transfer, letting the attacker extract value the protocol never sent them via `-deltaAmountChanges` in the current transaction.

The `feeStructure.feeToken` overlap makes this worse in `payRelayFees`, which has the identical lack-of-uniqueness flaw: [6](#0-5) 
When the duplicated token equals `feeStructure.feeToken`, `isFeeToken` and `flatFee`/`calculateRelayFee` are evaluated independently for both duplicate indices, and `foundToken` is a mere boolean that doesn't dedupe the charge. This lets an attacker manipulate how much (if anything) is actually deducted per leg while still keeping enough of the pre-existing dust intact to be swept via the duplicate-index `handleOut` payout described above.

Existing guards do not prevent this: `verifyWallet`/`performHinkalChecks` validate the signature/message and dimensions but never validate uniqueness of `erc20TokenAddresses`; the `balanceChange < 0` revert only guards against negative net changes per index, not against the same positive delta being paid out twice; and the circuit's `inTotal + amountChanges === outTotal` constraint operates on the `deltaAmountChanges` array the attacker themselves supplies per index — it does not, and cannot, know that two indices refer to the same physical ERC20 balance on-chain.

### Impact Explanation
An attacker can drain any dust/stranded ERC20 or ETH balance sitting in the `EmporiumUpgradeable` action contract — funds that belong to the protocol or to other users from prior transactions — by simply duplicating that token's address in `circomData.erc20TokenAddresses` and crafting matching `deltaAmountChanges`/ops so that the duplicate index's `handleOut` call succeeds against the leftover balance. This is direct theft of in-flight/stranded protocol funds by an unprivileged actor, matching the Critical "direct theft of shielded or in-flight user funds" category. It is repeatable for as long as stranded balances accumulate (e.g., every incomplete or rounding-leaving transaction adds to the pool the attacker can later sweep).

### Likelihood Explanation
Preconditions: the Emporium action contract must hold a non-zero residual/dust balance of some token (plausible over time from partial ops, rounding, or slippage-leaving legs). The attacker needs no privileged role — they fully control `externalActionMetadata` (hence `erc20TokenAddresses` ordering/duplication and the ops list) and `deltaAmountChanges`, and can generate their own proof for their own legitimate UTXOs to satisfy `verifyProof`/circuit constraints for the "real" leg while free-riding the duplicate index on existing dust. Cost is limited to gas and constructing a valid proof for their own funds; the attack is repeatable each time dust accumulates.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `runAction` (e.g., revert on duplicate addresses, or aggregate `deltaAmountChanges` per unique token before computing `balanceChange` once per unique token) so that a single physical balance cannot be read and transferred out more than once per transaction. Apply the same deduplication in `payRelayFees` so fee deduction cannot be evaluated multiple times for the same physical token.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` and an ERC20 mock token `T`. Directly transfer a "dust" amount `D` of `T` to the Emporium contract to simulate a stranded balance from a prior transaction (bypassing normal flow, e.g. `T.transfer(emporium, D)`).
2. Construct `CircomData` with `erc20TokenAddresses = [T, T]` (duplicate), an `externalActionMetadata` encoding an `EmporiumStack` with a no-op `ops` array (or an op that doesn't touch `T`), and `deltaAmountChanges = [0, 0]` (or values chosen so no fee/fund transfer for `T` is required from Hinkal).
3. Call `runAction` (via the appropriate Hinkal entrypoint/mock invoking it as `msg.sender`) and assert:
   - Before: `T.balanceOf(emporium) == D`.
   - After: `T.balanceOf(attacker-controlled msg.sender) == D` (or more, if ops also legitimately generate output), and `T.balanceOf(emporium) == 0` — i.e., more tokens left the action than `-deltaAmountChanges` (`0`) authorized, and `handleOut` produced two UTXO records for the same physical balance.
4. Assert the equality `tokens_transferred_out(T) == -deltaAmountChanges(T)` is violated (LHS `> 0` while RHS `== 0`), confirming the invariant break.

        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
