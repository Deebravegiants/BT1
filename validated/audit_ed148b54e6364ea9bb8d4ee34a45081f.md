### Title
Webhook Shop Domain Spoofing via HMAC Scope Gap - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the shop identity (`X-Shopify-Shop-Domain` header) that is handed to the app's webhook handler is never included in that HMAC computation. Any party that can obtain one valid `(body, hmac)` pair — for example by installing the app on their own store and receiving a genuine webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC check still passes because it is computed only from `@raw_body`, so the handler processes attacker-controlled data under a spoofed, victim-chosen shop identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

and `shop` is read directly from an unauthenticated header with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` when building the metadata passed to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms the check is scoped to whatever `to_signable_string` returns — for webhooks, that is the body only, never the shop header: [4](#0-3) 

This is the same class of defect referenced in the external report: an external interaction (`_safeMint`/state mutation happening on unchecked/unbound data) is analogous here to trusting a field (`shop`) that is *acted on* (used to build `WebhookMetadata` and dispatched to app logic) but is *not covered* by the cryptographic check (`HmacValidator.validate`) that is supposed to establish trust in the whole request. Contrast with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed parameters: [5](#0-4) 

so the OAuth flow correctly binds `shop == HMAC-verified shop`, while the webhook flow does not.

### Impact Explanation
This breaks the identity binding `shop authenticated (via HMAC) == shop acted upon (delivered to handler)`. An attacker who is themselves a legitimate merchant/installer of the target app (an "unprivileged internet user" relative to any *other* tenant) can obtain a valid `(raw_body, hmac)` pair from their own store's real webhook traffic, then forge a request to the app's public webhook endpoint with that same pair but an arbitrary `shop-domain` header. Because `Registry.process` never re-derives or checks the shop against the signed payload, the host application's handler will execute business logic (e.g., `shop/redact`, `customers/data_request`, order/fulfillment updates, uninstall handling) attributing it to a shop the attacker does not own — i.e., cross-tenant action injection using data intended only for the attacker's own store.

### Likelihood Explanation
Any app developer that registers a handler and relies on `WebhookMetadata#shop` (which is the documented and expected usage pattern of this gem, not a host-app misuse) is exposed. The only prerequisite is that the attacker possess one genuine `(body, hmac)` pair, which any merchant with the app installed on their own store can trivially obtain by triggering an event and capturing the resulting webhook.

### Recommendation
Bind the shop domain into the value verified by the HMAC for webhook requests — e.g., include `shop-domain` (and ideally `topic`, `webhook-id`) in the signable string used by `Webhooks::Request#to_signable_string`, or independently verify that the shop reported in the header matches an expected/registered shop before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker sends a forged POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and compares to `H` — this passes since `B` and `H` are unchanged. [6](#0-5) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-controlled body, and performs whatever business logic is registered for that topic under the victim's identity.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
