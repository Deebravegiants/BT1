I found a strong finding here. The `SimplexPaymaster` decision doc directly describes the analogous bug class: an undelivered governance request stays valid indefinitely and a superseded request delivered out of order can hand control to the wrong party — mirroring the Cooler bug where a stale proposal (from a party who no longer controls the resource) remains acceptable.

### Title
Undelivered `SetRelayer`/`UpgradeContract` governance requests never expire, letting a superseded request be delivered after a newer one, handing control to an unintended key - ([File: sdk/packages/simplex/docs/ai/decisions/2026-09-07-paymaster-relayer-gate-open-while-unset-never-settable-to-zero.md])

### Summary
`SimplexPaymaster.onAccept` (and analogously `ExtrinsicIntents`/`IntentGatewayV2` `setRelayer`/`Execute` rotation paths) process governance-originated ISMP requests such as `SetRelayer(newKey)` with no expiry and no invalidation of previously-dispatched-but-undelivered requests for the same slot. Hyperbridge governance picks *when* to dispatch a rotation, but the relayer that ultimately delivers it picks *which* dispatched message lands, and in what order, since ISMP requests are delivered independently and there is no on-chain sequencing/cancellation of a stale one once a newer one has been issued.

### Finding Description
This is structurally the same defect class as the Cooler bug: a party (the "old lender"/current governance owner) issues an update (`provideNewTermsForRoll` / `SetRelayer`), and later issues a new update to the same slot before the first is consumed, but the old update is not invalidated — it remains independently deliverable/acceptable. In Cooler, the borrower could still accept stale lender terms after the loan was transferred to a new lender. Here, the documented risk is explicit: "never dispatch a second `SetRelayer` or `UpgradeContract` while one is undelivered, since requests never expire and the relayer picks delivery order, so a superseded `SetRelayer(A)` delivered last hands A the sole key" [1](#0-0) .

The same mechanics apply to `HostManager`/`EvmHost` governance and to `ExtrinsicIntents`/`IntentGatewayV2` relayer rotation, all of which are delivered as ordinary ISMP `PostRequest`s that any relayer can pick up and submit whenever it likes, with no on-chain concept of "this rotation is stale, a newer one exists." `ExtrinsicIntents._setRelayer` is unconditionally the sole writer invoked from `initialize`, `migrate`, and `setRelayer` via the `Execute` action [2](#0-1) , and `onAccept` merely checks the relayer gate and Hyperbridge-source before decoding and delegatecalling the action — nothing about supersession of an in-flight, previously-dispatched rotation to that same contract [3](#0-2) .

### Impact Explanation
If governance dispatches `SetRelayer(A)` and then, before it is delivered/observed as delivered, decides to dispatch `SetRelayer(B)` instead (e.g. because key `A` was later found compromised or provisioned incorrectly), a relayer (honest or malicious) can still choose to deliver the stale `SetRelayer(A)` message. Because ISMP requests carry no freshness/sequence check against the currently-installed relayer beyond "current relayer signed it," and delivery order is entirely relayer-controlled, the superseded key `A` can end up as the sole authorized relayer for governance on that contract — even though the intent was to replace it with `B`. This can result in unauthorized app action / forged message delivery authority ending up with an unintended party, and since this key alone gates all future `Execute` (delegatecall) actions including upgrades, it is a path to full contract takeover.

### Likelihood Explanation
Requires governance to issue two competing rotations to the same target before the first is confirmed delivered — an operational sequencing mistake rather than a routine flow, so likelihood is moderate. However, the project's own decision doc flags this as a known, currently-unmitigated risk ("Accepted and not mitigated") rather than a stale/theoretical corner case, which raises confidence this is a real, currently-exploitable gap under realistic governance error conditions (e.g. re-dispatching a correction after noticing the wrong key was set).

### Recommendation
Add a nonce/sequence number or "supersedes" reference into the `SetRelayer`/`Execute` rotation payload that the contract enforces monotonically (reject delivery of any rotation whose sequence number is not newer than the last applied one), analogous to clearing Cooler's stale `loan.request` on any subsequent update. Alternatively, before dispatching a corrective rotation, cancel/timeout the superseded outbound ISMP request so it can no longer be delivered.

### Proof of Concept
1. Governance dispatches ISMP PostRequest `R1 = SetRelayer(A)` to `ExtrinsicIntents`/`HostManager` from the current authorized relayer.
2. Before any relayer delivers `R1`, governance detects an issue and dispatches `R2 = SetRelayer(B)` to the same contract.
3. A relayer (or the operator of key `A`, colluding with a relayer) delivers `R1` first. `onAccept` validates the Hyperbridge-source and current-relayer checks (both still pass, since `R1` was legitimately signed under the still-current relayer at dispatch time) and installs `A` as the new relayer, per `_setRelayer` [2](#0-1) .
4. `R2` is now addressed to a relayer (`A`) whose installation was never intended to stick; whether `R2` can still land depends on delivery semantics, but the documented failure mode is that `R1`, delivered last, "hands A the sole key" — permanently, since there is no longer a path back to `B` without `A`'s cooperation.
