### Title
Webhook `shop` tenant identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string`). The shop-domain header is never included in the signed material, so it can be freely modified without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`Utils::HmacValidator#validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string`: [4](#0-3) 

`Request#shop` is read directly from the `shopify-shop-domain` header, which is not part of the signable string: [5](#0-4) 

`Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) as the tenant identity forwarded to the app's handler via `WebhookMetadata`: [6](#0-5) 

The identity binding that should hold is:
```
shop_used_by_handler == shop_that_HMAC_authenticates
```
But in reality:
```
shop_used_by_handler = shopify-shop-domain header (attacker-controllable, unsigned)
shop_that_HMAC_authenticates = undefined (HMAC only covers raw_body)
```
Any party capable of producing one valid `(raw_body, hmac)` pair for shop A (e.g., their own installed instance of the app receiving legitimate Shopify-delivered webhooks) can present that exact same body+HMAC to the app's webhook endpoint again but with the `shopify-shop-domain` header set to shop B. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` while the actual signed content came from shop A's delivery. This is exactly analogous to the UStb `_beforeTokenTransfer` bug: the code enforces one identity check (`hasRole`/HMAC-of-body) while acting on a different, unchecked field (`from`/`shop`) that is assumed—but never proven—to correspond.

### Impact Explanation
This breaks tenant isolation for any app built on this gem: cross-tenant webhook injection lets one merchant (or anyone with access to one legitimate webhook delivery for a shop they control) cause the host application to process attacker-chosen webhook bodies under another shop's identity. Depending on how the host app's handler consumes `data.shop` (e.g., to look up that shop's session/access token, update stored order/customer data, or trigger `app/uninstalled` cleanup for another tenant), this can lead to cross-tenant data corruption or unauthorized actions being taken against another merchant's data — matching the Critical "cross-tenant access" impact category, since the gem itself provides no cryptographic binding between the claimed shop and the verified payload.

### Likelihood Explanation
Likelihood is non-trivial: unlike a random third party who cannot forge a valid `(body, hmac)` pair without `api_secret_key`, a merchant who has installed the app is a legitimate source of one or more valid `(body, hmac)` pairs, since Shopify signs and delivers real webhooks to the app for their own shop. That merchant (or anyone who can capture such a delivery, e.g., via logs, proxies, or a malicious insider on their own infra) can replay it against the same endpoint with only the `shopify-shop-domain` header altered. No `api_secret_key`, session, or access token is required — only a previously observed legitimate webhook delivery for any shop using the app.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the signed material, or otherwise cryptographically tie the claimed `shop` header to the HMAC verification — e.g., include the shop-domain header in `to_signable_string`, or have `HmacValidator.validate` take the full header set and verify shop-domain against a per-shop secret/session rather than trusting the header verbatim. At minimum, document that host applications must independently verify `data.shop` against a shop they have an active, verified session/installation for before acting on webhook data.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid HMAC of BODY signed with api_secret_key>
   shopify-shop-domain: shop-a.myshopify.com
   BODY: {"id": 123, ...}
   ```
2. Attacker (who controls `shop-a` or intercepted this delivery) resends the identical request but changes only the header:
   ```
   shopify-shop-domain: shop-b.myshopify.com
   ```
   with the same `BODY` and same `shopify-hmac-sha256` value.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only [7](#0-6)  — validation succeeds because the body is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [8](#0-7)  using the attacker-supplied `shop-b.myshopify.com`, and the host app's `handle(data:)` processes shop A's payload as if it belongs to shop B.
