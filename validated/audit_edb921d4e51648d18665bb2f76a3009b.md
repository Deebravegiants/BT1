### Title
Draining a priced Aquarius pool bricks liquidation and bad-debt cleanup through a dust LP collateral leg - ([File: contracts/price-aggregator/src/providers/aquarius.rs])

### Summary
An unprivileged borrower can place a tiny listed Aquarius LP token into their collateral set, then remove enough liquidity from that pool to push its total value below `min_pool_value_wad`. The LP oracle becomes unpriceable, and because account valuation loads every collateral leg, `liquidate`, `clean_bad_debt`, and collateral `withdraw` all revert until the pool is recapitalized.

### Finding Description
The Aquarius LP oracle recomputes total pool value from live reserves and total shares. If the resulting value is below the configured `min_pool_value_wad`, `read` returns `InsufficientAquariusLiquidity`. [1](#0-0) 

The aggregator’s strict `prices` path propagates any unusable source as a panic rather than skipping the collateral. [2](#0-1) [3](#0-2) 

Supplying a new collateral leg only checks listing/entry permissions and mints pool shares; it does not first prove that the collateral is priceable. [4](#0-3) [5](#0-4) 

Liquidation planning calls `calculate_account_risk_totals`, which loads prices for every key in both `supply_positions` and `borrow_positions`. [6](#0-5) [7](#0-6)  Therefore one unpriceable dust LP leg aborts liquidation before repayment or seizure.

The same all-position valuation is performed by permissionless `clean_bad_debt`. [8](#0-7)  Normal withdrawal also reaches post-pool solvency and cannot remove the poisoned leg while the account remains risky. [9](#0-8) 

### Impact Explanation
The borrower can repeatedly create a window in which underwater debt cannot be liquidated or cleaned up. During that window, interest continues to accrue and collateral/debt market movement can increase protocol bad debt. This is a temporary freezing of liquidation/cleanup funds and can contribute to protocol insolvency.

If the attacker controls enough LP shares, they can trigger the condition by withdrawing liquidity from Aquarius. They can later restore liquidity to make the LP oracle usable again, making the shield reusable rather than a one-time outage.

### Likelihood Explanation
Likelihood is Medium. It requires:

- A listed collateral asset whose oracle contains an Aquarius LP source.
- Attacker-controlled LP liquidity sufficient to reduce pool value below `min_pool_value_wad`.
- The borrower supplying a nonzero amount of that LP token while it is still accepted.
- A debt position that later becomes liquidatable.

No privileged role, leaked key, oracle-signer dishonesty, or contract upgrade is required. The attacker may use their own Aquarius liquidity withdrawal, which is within the permitted threat model.

### Recommendation
Do not let an arbitrary residual collateral leg make the entire account unprocessable. Liquidation and cleanup should:

- Treat a small unpriceable collateral leg as zero-valued for risk admission after applying explicit minimum-value/dust policy, or exclude it from seizeable collateral while preserving an auditable residual.
- Permit forced removal/quarantine of collateral below a strict USD dust floor.
- Consider pricing LP collateral using a bounded fallback only if manipulation-resistant; otherwise preserve fail-closed pricing but isolate the failing leg from unrelated liquidation legs.
- Recheck `min_pool_value_wad` against realistic attacker-controlled withdrawal sizes so normal liquidity provision cannot cheaply make a listed collateral oracle unavailable.

### Proof of Concept
1. Attacker supplies normal collateral `C` and borrows asset `D`, leaving the account close to liquidation.
2. Attacker calls:

   `Controller::supply(caller=attacker, account_id=A, spoke_id=S, assets=[(AquariusLpKey, dust_amount)])`

   The call transfers `dust_amount` and mints a supply position without requiring a successful LP price resolution.
3. Attacker withdraws their Aquarius liquidity, lowering live reserves enough that `price_wad * total_shares / share_unit < min_pool_value_wad`.
4. The LP asset’s configured price source now returns `InsufficientAquariusLiquidity`.
5. A liquidator calls:

   `Controller::liquidate(liquidator=L, account_id=A, debt_payments=[(D, amount)], seize_mode=SeizeMode::Transfer)`

   `build_liquidation_plan` invokes `calculate_account_risk_totals`, which loads the LP leg’s price; the aggregator panics, so the whole liquidation reverts.
6. Any caller calling `Controller::clean_bad_debt(caller, A)` reaches the same all-position valuation and reverts.
7. The borrower’s own `withdraw` of the LP dust also reverts because post-pool solvency reloads all supply and debt prices.
8. Restoring Aquarius liquidity raises pool value above `min_pool_value_wad`; the same liquidation then becomes executable again, demonstrating attacker-controlled temporary freezing.

/// Requires open debt and the selected insolvency gate, then cleans up the account.
fn socialize_bad_debt(env: &Env, account_id: u64, gate: BadDebtGate) {
    let mut cache = Context::new(env);
    let account = storage::get_account(env, account_id);

    assert_with_error!(
        env,
        !account.borrow_positions.is_empty(),
        CollateralError::DebtPositionNotFound
    );

    let totals = risk::calculate_account_risk_totals(
        env,
        &mut cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    let admits = match gate {
        BadDebtGate::DustCapped => {
            is_socializable_bad_debt(totals.total_debt, totals.total_collateral)
        }
        BadDebtGate::InsolventOnly => totals.total_debt > totals.total_collateral,
    };
    assert_with_error!(env, admits, CollateralError::CannotCleanBadDebt);

    bad_debt::execute_bad_debt_cleanup(env, &mut cache, account_id, &account, &totals);
