## Title
`EvmHost` sets Uniswap V2 swap deadline to `block.timestamp`, nullifying deadline protection and enabling MEV sandwich extraction on native-fee dispatches - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert native ETH sent with the call into the fee token via `IUniswapV2Router02.swapETHForExactTokens`, but pass `block.timestamp` (evaluated at execution time) as the `deadline` argument instead of a caller-supplied, pre-signing deadline. ### Finding Description
Uniswap's `deadline` parameter is only meaningful when it is chosen by the caller at signing time (e.g. `block.timestamp + N`) and checked against the block's `block.timestamp` at execution time. Passing `block.timestamp` itself as the deadline means the router's internal `ensure(deadline)` check (`require(deadline >= block.timestamp)`) is evaluated against the *same* `block.timestamp` used to construct it, so it can never fail — the protection is a no-op regardless of how long the transaction sits in the mempool.

Any unprivileged user who calls `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with `msg.value > 0` (paying the relayer fee in native token instead of the fee token) triggers this swap. Because there is no real staleness bound:

1. The dispatch transaction can be broadcast with a low gas price and remain pending in the mempool for an extended period while the ETH/feeToken pool price drifts.
2. When the transaction is eventually included (or is immediately visible to searchers), an MEV actor can sandwich the `swapETHForExactTokens` call: since it is an exact-output swap bounded only by `msg.value` as the implicit input cap, an attacker can manipulate the pool price beforehand to force the swap to consume close to the full `msg.value` for the same `post.fee`/`get.fee`/`amount` of fee tokens, extracting the difference as MEV profit at the caller's expense, then revert the price afterward.
3. Because these are core dispatch paths of `EvmHost` — the entrypoint reachable by every unprivileged message dispatcher — this affects any user or application paying the ISMP dispatch fee in native token.

This is exactly the bug class in the referenced report: a swap lacking genuine, caller-chosen deadline protection lets pending transactions be executed against a stale/manipulated price, and the "deadline = block.timestamp" pattern is a well-known variant that appears to provide protection but does not.

### Impact Explanation
Users paying dispatch/fund-request fees with native ETH can be sandwiched, losing more ETH than the fair-market cost of the required fee tokens. Since `EvmHost.dispatch` is the fundamental entrypoint for POST/GET message dispatch on every EVM deployment of Hyperbridge, and `fundRequest` is used to top up pending request fees, this is reachable from ordinary user activity (a single dispatched request or fee top-up) without any privileged role. The loss is a real transfer of value to an MEV searcher, extracted from users of the protocol's core dispatch path — classified as concrete value extraction/theft of funds, matching the High-severity classification of the analog.

### Likelihood Explanation
Likelihood is high: any transaction paying in native token that experiences even brief mempool delay (public mempool visibility, congestion, low gas price, or simply being observed pre-confirmation) is sandwichable, since the deadline check imposes zero real restriction. No special conditions are needed beyond normal MEV searcher activity on the relevant EVM chain, and the swap path is exercised by ordinary, unprivileged callers of `dispatch`/`fundRequest`.

### Recommendation
Add a caller-supplied `deadline` (or a bounded max-slippage/max-input parameter) to `DispatchPost`, `DispatchGet`, and `fundRequest`, and pass that value (not `block.timestamp`) into `swapETHForExactTokens`. At minimum, compute the deadline off-chain and pass it as a parameter validated against a reasonable window, so a transaction that has been stuck in the mempool past its intended execution window reverts instead of executing at an arbitrary later price.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: msg.value}(DispatchPost{...})` intending to pay the relayer fee in native ETH, sending a transaction with a modest gas price during normal network conditions.
2. The transaction stays pending in the public mempool.
3. A searcher observes the pending call to `dispatch`, and, immediately before inclusion, trades against the ETH/feeToken pool to move the price unfavorably for the exact-output swap.
4. `EvmHost.dispatch` executes `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` — since `deadline == block.timestamp` at execution time, `ensure(deadline)` trivially passes no matter how stale the intent was.
5. The swap consumes more ETH than it would have under fair pricing (up to the `msg.value` cap) to produce the same `post.fee` fee tokens; the searcher reverts the price afterward, pocketing the difference extracted from the user's `msg.value`. [1](#0-0)
