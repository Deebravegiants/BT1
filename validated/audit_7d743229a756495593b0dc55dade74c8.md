### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC signature exclusively from the raw request body via `to_signable_string`, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers that are never included in the signed material. `Registry.process` validates only that the body's HMAC is correct and then forwards the unauthenticated `shop` header value straight to the app's webhook handler as trusted shop identity, breaking the intended binding: `HMAC-verified bytes == body only`, but `shop identity used by handler == header value`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor instead reads the `shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of that signable string: [2](#0-1) .

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string`, i.e. body only) and, on success, immediately constructs `WebhookMetadata.new(topic:, shop: request.shop, ...)` and invokes the app's handler with it: [3](#0-2) . `HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it with the `hmac` field: [4](#0-3) .

Because the same `api_secret_key` is shared by the app across all shops that installed it (it is the app's `client_secret`, not a per-shop secret), a real webhook delivered to shop A carries a valid HMAC over the body, computed with the app-wide secret. An attacker who controls shop A (installs the app on their own store) can legitimately receive such a webhook, and can then replay the exact same body/HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value (e.g. victim shop B's domain). `Registry.process` will still pass HMAC validation (since only the body is checked) and will call the handler with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from shop A. The identity binding the library appears to guarantee — "this webhook, and its `shop`, came from Shopify for that shop" — is not actually enforced for the `shop` field.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which reasonably leads app authors to trust `data.shop` as authenticated: [5](#0-4) , and the “Best Practices” snippet even shows dispatching background jobs keyed on `data.shop` without further validation: [6](#0-5) .

### Impact Explanation
This crosses a tenant boundary using only the app's own shared secret (no shop-specific or victim credentials required): an attacker with a legitimate installation on their own store can forge webhook events "from" any other shop's domain that has ever installed the app, causing the host application to process or persist data under the wrong tenant's identity (e.g., updating another merchant's order/product records, triggering background jobs `shop_domain: <victim>`, or corrupting per-shop caches/state). This matches the "Cross-tenant access" Critical impact category, since the shop-identity binding the library implicitly promises is not enforced.

### Likelihood Explanation
Medium-High. Exploitation requires only:
1. Being (or becoming) a merchant who installs the target app on any store, which is normally open to any internet user for a public app.
2. Capturing one legitimate webhook body+HMAC pair from that install (trivial — receive any webhook at the registered callback URL).
3. Replaying that body with an altered `shop-domain` header to the same callback endpoint.

No access to `api_secret_key`, access tokens, or victim credentials is needed, and the request path (`Request.new` → `Registry.process`) is exactly the one recommended in the gem's own documentation.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values into the HMAC-signed material, or otherwise cryptographically verify the shop header against Shopify's TLS-terminated delivery metadata before trusting it. At minimum:
- Include the `shop-domain` header (and topic) in `to_signable_string` so a mismatch invalidates the signature, or
- Require app authors to cross-check `request.shop` against a shop known to have an active, registered webhook subscription/session before acting on the payload, and document this requirement prominently instead of implying that `process` fully "verifies the request did indeed come from Shopify" for the shop identity as well as the body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining a valid installation that receives real webhooks signed with the app's shared `api_secret_key`.
2. Attacker triggers (or waits for) a webhook, e.g. `orders/create`, and captures the raw POST body `B` and its `X-Shopify-Hmac-Sha256` header `H` (valid because `H = HMAC_SHA256(api_secret_key, B)` per `Request#hmac`/`to_signable_string`).
3. Attacker resends an HTTP POST to the app's webhook callback route with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the app; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (per `lib/shopify_api/webhooks/registry.rb` lines 188-199), causing the app to act on attacker-controlled data attributed to the victim shop.

Note: I was unable to fully verify from the indexed code whether any downstream reference implementation (e.g., in the companion `shopify_app` gem, which is out of scope here) adds an independent shop/session cross-check before processing webhook data; within this gem's in-scope code (`lib/shopify_api/webhooks/**`, `lib/shopify_api/utils/hmac_validator.rb`), no such check exists.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
