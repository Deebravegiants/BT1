### Title
Unvalidated fee-token decimals cause permanent underflow revert in `BandwidthManager.purchase()` for tokens with >18 decimals - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` computes the local-decimal scaling factor for the host's fee token as `10 ** (18 - dec)` without checking that `dec <= 18`. If the ISMP host's configured `feeToken()` ever has more than 18 decimals, this subtraction underflows and every call to `purchase()` reverts unconditionally, permanently bricking bandwidth purchasing (and therefore bandwidth-gated message dispatch) on that chain.

### Finding Description
`purchase()` reads the host's fee token, its decimals, and computes the scale factor inline with no bounds check: [1](#0-0) 

```solidity
uint256 total18d = price18d * months;
address feeToken = IDispatcher(_host).feeToken();
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 scale = 10 ** (18 - dec);
if (total18d % scale != 0) revert PriceNotRepresentable();
uint256 amount = total18d / scale;
```

`feeToken` is not app-local configuration — it is `IDispatcher(_host).feeToken()`, the single fee token used for the entire ISMP host, including relayer fee accounting elsewhere in the protocol. If that token has `decimals() > 18` (e.g. YAM-style 24-decimal tokens, as called out explicitly in the protocol's own documentation), `18 - dec` underflows a `uint8`/`uint256` subtraction and reverts on every single invocation of `purchase()`.

This is the exact bug class from the referenced Ajna report: unvalidated assumption that ERC20 `decimals()` is `<= 18`, causing the scaling arithmetic to revert rather than degrade gracefully. The project's own documentation acknowledges the underflow exists and only dismisses it because "the supported fee tokens are all ≤ 18 decimals" — a config assumption with no on-chain enforcement: [2](#0-1) 

### Impact Explanation
If a chain's ISMP host is ever configured with a >18-decimal fee token, `BandwidthManager.purchase()` reverts unconditionally and permanently for every caller on that chain — there is no way to top up bandwidth quota for any app. Since `BandwidthGate::try_consume` rejects dispatches once an app's byte quota is exhausted (`Insufficient`), any non-allowlisted app on that chain becomes permanently unable to accrue new bandwidth and, once its existing quota is drained, permanently unable to dispatch ISMP messages through that route — a concrete "route unable to deliver messages" condition described in the validation criteria. Funds already sent to the manager for a still-in-flight purchase are unaffected, but no new purchases (and no future bandwidth-gated dispatches) can succeed on the affected chain.

### Likelihood Explanation
This requires a specific configuration precondition (host fee token with >18 decimals) rather than being triggerable by an attacker against an already-correctly-configured deployment. However, Hyperbridge explicitly targets deployment across many EVM chains with varying token ecosystems (per its own multi-chain scope), and the underflow is silent until the condition occurs — there is no deploy-time or `setHost`-time validation guarding against it. Once triggered, the break is total and permanent for that chain's bandwidth feature, matching the "liveness risk" characterization in the source report.

### Recommendation
Guard the scaling computation in `purchase()` (and any other location performing `10 ** (18 - decimals)`), e.g.:
```solidity
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 amount;
if (dec == 18) {
    amount = total18d;
} else if (dec < 18) {
    uint256 scale = 10 ** (18 - dec);
    if (total18d % scale != 0) revert PriceNotRepresentable();
    amount = total18d / scale;
} else {
    uint256 scale = 10 ** (dec - 18);
    amount = total18d * scale;
}
```
This mirrors the safe pattern already implemented in `VWAPOracle._normalizeAmount` elsewhere in the same repo, which correctly branches on `decimals < 18` vs `> 18`: [3](#0-2) 

### Proof of Concept
1. Deploy an ISMP host whose `feeToken()` returns an ERC20 with `decimals() == 24` (e.g. a YAM-style token).
2. Deploy `BandwidthManager`, call `setHost(hostAddr)`, and configure a tier price via `SetTiers`.
3. Any caller invokes `manager.purchase(app, tier, months, chain)`.
4. Execution reaches `uint256 scale = 10 ** (18 - dec);` with `dec = 24`; `18 - dec` underflows and the call reverts for every subsequent invocation, permanently disabling bandwidth purchases (and, once existing quotas drain, ISMP dispatch for non-allowlisted apps) on that chain. [4](#0-3)

Two implications:

1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
2. **Tier prices must be representable at the local fee-token's decimals after multiplication by `months`.** A tier priced at `10**12` (a hypothetical sub-penny SKU) and a 6-decimal fee token would revert with `PriceNotRepresentable()` because the 18-decimal value doesn't divide cleanly.     function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
