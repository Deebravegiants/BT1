### Title
Webhook shop attribution is not bound to the HMAC-signed payload, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` identifier used downstream to attribute the webhook event to a tenant is read from an HTTP header that is never included in the signed payload. This breaks the identity binding: `hmac_valid(raw_body) == true` does not imply `shop_header == shop_that_generated(raw_body)`. This mirrors the reported bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Utils::HmacValidator.validate` verifies the `hmac` field against `to_signable_string`, and for webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identifier passed to the app's handler: [3](#0-2) 

The library's own documentation instructs host apps to use `data.shop` as "The shop domain of the webhook" and to key business logic on it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [4](#0-3) 

Because `shop` is never part of the signed string, an attacker who can obtain any single valid `(raw_body, hmac)` pair for a webhook delivered to the app (e.g. from a webhook the attacker's own installed/test shop legitimately receives) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` with `shop` set to the attacker-chosen domain and `body` from the replayed payload — i.e., the equality `shop_verified_by_hmac == shop_used_for_tenant_attribution` does not hold.

### Impact Explanation
This is a cross-tenant identity confusion: the gem provides no cryptographic guarantee that a signature-valid webhook body actually originated for the `shop` value the app is told to attribute it to. Any host application that follows the gem's documented pattern of using `data.shop` to route/store data per tenant (as explicitly recommended in `docs/usage/webhooks.md`) is exposed to cross-tenant data injection/misattribution — an attacker-controlled shop domain paired with a replayed, HMAC-valid body. This falls under "cross-tenant access" impact.

### Likelihood Explanation
Likelihood is constrained by the requirement that the attacker first obtain at least one legitimate `(raw_body, hmac)` pair — for example by installing the app as their own shop and receiving one real webhook delivery, or capturing one via any means available to an unprivileged tenant. Once obtained, no secret material is needed to replay it under a different `shop` header value, since the shop is not covered by the signature. This is a structural weakness in the library's `Webhooks::Request`/`Registry` design rather than requiring any privileged secret.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the value that is HMAC-verified, or otherwise cryptographically bind the `shop` header to the signed body before exposing it via `WebhookMetadata#shop`. At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop/topic headers, and update `Utils::HmacValidator`/`compute_signature` accordingly so that verification fails if the shop header is altered relative to the originally signed request.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers a webhook, receiving one legitimate delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret).
2. Attacker POSTs to the app's webhook endpoint with the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — validation succeeds ( [5](#0-4) ).
4. `request.shop` returns `"victim.myshopify.com"` from the header ( [2](#0-1) ), and the handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` ( [6](#0-5) ), causing the host app to process attacker-supplied data under the victim shop's tenant context.
