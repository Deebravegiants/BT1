### Title
Nonce wraparound to zero via `checked_add(...).unwrap_or(T::Nonce::zero())` in `prepare_nonce_for_account` enables replay of an old low-nonce extrinsic - ([File: substrate/frame/system/src/extensions/check_nonce.rs])

### Summary
`CheckNonce::prepare_nonce_for_account` silently wraps `account.nonce` back to `T::Nonce::zero()` instead of erroring when the current nonce is `T::Nonce::MAX`. Because `validate_nonce_for_account`'s only staleness guard is `nonce < account.nonce`, once the stored nonce wraps to `0` an attacker (or anyone possessing a previously broadcast, still-validly-signed low-nonce extrinsic from that account) can resubmit it and have it accepted again as if it were new.

### Finding Description
The nonce lifecycle is split across two functions in `substrate/frame/system/src/extensions/check_nonce.rs`:

- `validate_nonce_for_account` (lines 70-91) rejects a submitted `nonce` only if `nonce < account.nonce` (`InvalidTransaction::Stale`). [1](#0-0) 
- `prepare_nonce_for_account` (lines 94-105) rejects the nonce only if `nonce > account.nonce` (`InvalidTransaction::Future`), then computes the next stored nonce as `nonce.checked_add(&T::Nonce::one()).unwrap_or(T::Nonce::zero())`. [2](#0-1) 

Combining the two checks (`validate` requires `nonce >= account.nonce`, `prepare` requires `nonce <= account.nonce`), only `nonce == account.nonce` can ever succeed and be dispatched, and each successful extrinsic advances `account.nonce` by exactly 1 — so an account nonce sequence must pass through `0, 1, 2, …, MAX-1, MAX` in order, with no gaps, before wraparound is even reachable.

Once `account.nonce == T::Nonce::MAX` and the attacker submits one more valid extrinsic with `nonce == MAX`, the addition `MAX.checked_add(1)` returns `None`, and `unwrap_or(T::Nonce::zero())` resets the stored nonce to `0` instead of returning an error. At this point:

- `crate::Account::<T>::get(who).nonce == 0`.
- Any old, already-executed and still cryptographically valid signed extrinsic from that account with nonce `0` (the account's very first-ever transaction, whose signed bytes an attacker may have retained/observed on-chain) will pass `validate_nonce_for_account` because `0 < 0` is false (not stale), and will pass `prepare_nonce_for_account` because `0 > 0` is false (not future). It is re-executed, and the account nonce advances to `1` again.

This directly violates the strict-monotonicity/no-reuse nonce invariant: the "staleness" check (`nonce < account.nonce`) is the *only* replay guard, and it is defeated as soon as `account.nonce` wraps below a previously-used value.

### Impact Explanation
If successfully triggered, this allows unprivileged replay of a previously executed signed extrinsic (e.g., a `Balances::transfer`, a `Proxy::proxy` call, or any other signed call) once the victim account's nonce space wraps from `T::Nonce::MAX` back to `0`. This is a double-execution/double-spend of an already-settled transaction, bypassing `CheckNonce`'s replay protection entirely — matching the scoped impact in the question.

### Likelihood Explanation
The precondition — driving a single account's nonce to `T::Nonce::MAX` through exactly-sequential, individually-valid extrinsics (no skipping, since only `nonce == account.nonce` is ever accepted) — is the limiting factor:

- For chains where `T::Nonce = u32` (this repo's `parachain`/`solochain` templates, `cumulus/test/runtime`, `glutton-westend`, `yet-another-parachain`, and other test/dev configurations all use `type Nonce = u32`), `T::Nonce::MAX` is ~4.29×10⁹, which is large but not implausible for a long-lived, low-fee/dev/test chain, and is trivially reachable as a unit/property test at the type level (mocking `account.nonce = u32::MAX` directly in storage or driving it via repeated `system::remark` calls in a test harness).
- For production chains using `u64` nonces, reaching `MAX` via real signed extrinsics is economically and practically infeasible (would require billions of dollars in fees and enormous time), so the real-world exploitability on such chains is negligible today, though the underlying logic flaw is identical and becomes a bug the moment a runtime configures a narrow `Nonce` type or nonce is otherwise attacker-influenced (e.g., mis-migrated account data).
- The flaw is deterministic and 100% repeatable once the precondition is met — there is no timing race or partial mitigation; the wraparound branch (`unwrap_or(T::Nonce::zero())`) always fires on overflow and always permits reuse of nonce `0` (and, transiently, of any old nonce `<=` the new wrapped value before the account catches back up).

### Recommendation
Change `prepare_nonce_for_account` to return an error (e.g., a new `InvalidTransaction` variant or `InvalidTransaction::ExhaustsResources`/similar) when `nonce.checked_add(&T::Nonce::one())` overflows, instead of silently wrapping to `T::Nonce::zero()`:
```rust
nonce = nonce.checked_add(&T::Nonce::one())
    .ok_or(InvalidTransaction::Custom(NONCE_OVERFLOW_ERROR).into())?;
```
This permanently freezes further transactions from that specific account once its nonce is exhausted (a policy decision), but prevents nonce recycling and the associated replay.

### Proof of Concept
Rust unit/integration test in `substrate/frame/system/src/extensions/check_nonce.rs` test module:
```rust
#[test]
fn nonce_wraps_and_permits_replay() {
    new_test_ext().execute_with(|| {
        // Force account 1 to the max representable nonce.
        crate::Account::<Test>::insert(1, crate::AccountInfo {
            nonce: u64::MAX.into(), // or u32::MAX for a narrow-Nonce mock runtime
            consumers: 0, providers: 1, sufficients: 0, data: 0,
        });
        let info = DispatchInfo::default();
        let len = 0usize;

        // One more valid tx at nonce == MAX triggers wraparound instead of erroring.
        assert_ok!(CheckNonce::<Test>(u64::MAX.into())
            .validate_and_prepare(Some(1).into(), CALL, &info, len, 0));
        assert_eq!(crate::Account::<Test>::get(1).nonce, 0u64.into());

        // Replay: an "old" extrinsic carrying nonce == 0 is now accepted again.
        assert_ok!(CheckNonce::<Test>(0u64.into())
            .validate_and_prepare(Some(1).into(), CALL, &info, len, 0));
        // Expected (fixed) behavior: the second validate_and_prepare should be
        // rejected as InvalidTransaction::Stale/overflow, not Ok(()).
    })
}
```
Assertions: `prepare_nonce_for_account` at `nonce == T::Nonce::MAX` must return `Err(...)` rather than `Ok(())` with a wrapped-to-zero stored nonce; and after any such state, `validate_nonce_for_account` must never accept a `nonce` value that was previously consumed by that account.
