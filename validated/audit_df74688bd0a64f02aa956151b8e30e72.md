### Title
Webhook HMAC Only Signs the Request Body, Not the `shop-domain`/`topic`/`webhook-id` Headers — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature over the raw HTTP body only. The `shop`, `topic`, `webhook_id`, and `api_version` values — all read directly from unauthenticated HTTP headers — are never included in the signed content, yet `ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof the whole request, including these header-derived fields, "did indeed come from Shopify" (per the gem's own documentation) and hands them straight to the host app's handler as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read verbatim from the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (i.e., the body only) and then, on success, forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which were covered by that HMAC — to the app's handler as trusted metadata: [3](#0-2) 

The `HmacValidator` itself simply HMACs whatever `to_signable_string` returns with the app's `api_secret_key`: [4](#0-3) 

Because the signature only depends on the app's single, shop-independent `client_secret` and the body bytes, and never on the `shop-domain` header, any two webhook deliveries with the same body produce the same valid HMAC regardless of which shop they claim to be from. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole payload (including `data.shop`) is authenticated: [5](#0-4) 
but the implementation only authenticates the body bytes, not the tenant-identifying header. This breaks the identity binding: `HMAC-authenticated bytes (raw_body)` should equal `bytes used to determine the tenant (shop-domain header)`, but they do not — the shop header is verified as *present* (`Request#initialize` only checks that the header key exists) but never as *authentic*.

### Impact Explanation
An attacker who is simply able to install the target app on their own store (any unprivileged merchant/developer can do this for a public app) can trigger a legitimate webhook delivery to the app's public HTTP callback endpoint, capturing a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`. Because the signature is independent of the `shop-domain` header, the attacker can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will accept the HMAC as valid and pass `shop: <victim-domain>` to the host application's webhook handler, which — following the gem's documented contract — treats it as the authenticated source shop. This lets the attacker inject/attribute arbitrary webhook data (orders, customer records, `shop/redact`, `customers/data_request`, etc.) to a victim tenant, i.e., cross-tenant data injection/impersonation without ever needing the victim's credentials.

### Likelihood Explanation
Reaching this flaw requires only: (1) the ability to install the target app on an attacker-controlled shop (trivial for any public app), and (2) network access to the app's public webhook endpoint (required by design, since Shopify calls it over the internet). No access token, `api_secret_key`, or privileged account for the victim shop is needed — only unprivileged-internet-user capability, satisfying the scope's threat model.

### Recommendation
Include the tenant-identifying and routing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body (e.g., derive the signable string from a canonical concatenation of headers + body) so that a valid signature can only be produced for the exact combination Shopify sent. At minimum, document clearly that `data.shop` is not authenticated by the HMAC check and require host apps to independently confirm the shop against a known, registered session/webhook subscription before trusting it.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own store "attacker-shop.myshopify.com"
#    and lets Shopify deliver a legitimate webhook, e.g. "customers/create":
#    -> captures raw_body = '{"id":123,"email":"whatever@attacker.com"}'
#    -> captures valid header: x-shopify-hmac-sha256 = Base64(HMAC-SHA256(client_secret, raw_body))

# 2. Attacker replays the exact same body/HMAC to the app's public webhook endpoint,
#    but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"        => "customers/create",
  "x-shopify-hmac-sha256"  => captured_hmac,       # still valid, since HMAC only covers raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",  # spoofed, unauthenticated
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. Registry.process passes HMAC validation (body-only) and forwards
#    request.shop == "victim-shop.myshopify.com" to the host app's handler as trusted:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
