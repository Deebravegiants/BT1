### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Request#shop`, `#topic`, `#api_version` and `#webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then hands the *unverified* `shop` header straight to the application's webhook handler via `WebhookMetadata`. This is the same class of defect as the reported `ERC1155Bridgable` issue: a value that is acted upon (the tenant identity) is not covered by the cryptographic binding (the HMAC) that is supposed to guarantee its authenticity.

### Finding Description
`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from HTTP headers that are never included in the signed string: [3](#0-2) 

`Registry.process` validates only this body-only HMAC and then dispatches the request to the handler using the unauthenticated `request.shop` value as the tenant identity: [4](#0-3) 

The equality that should hold is:
`shop_header == shop_that_the_HMAC_owner_authorized_this_payload_for`

But the implementation only proves:
`HMAC(secret, raw_body) == received_hmac`

with no cryptographic link between `raw_body` and `shop-domain`/`topic`/`webhook-id` headers. Consequently, an attacker who can produce (or replay) *any* validly-HMAC-signed body — e.g., from their own shop's genuine webhook delivery, since `Context.api_secret_key` is shared across all shops installing the same app — can freely relabel the `shop-domain` header to an arbitrary victim shop domain while keeping the same signed body. The `Registry.process` code path performs no independent check that the signed body actually originated for that shop.

### Impact Explanation
This breaks the tenant/shop identity binding on inbound webhook processing. Since `WebhookMetadata.shop` (attacker-controlled) is passed unchanged to the host application's `WebhookHandler#handle`, and this is the *only* signal apps use to attribute a webhook payload to a merchant/tenant, an attacker who is themselves an installed merchant (or who can capture one legitimate signed delivery) can forge cross-tenant webhook deliveries: content signed under their own shop's payload can be attributed to a victim shop's identifier, and vice versa — content that legitimately belongs to a victim shop (if captured/replayed) can be relabeled with an attacker's `webhook-id`/`topic`. This matches the "cross-tenant access" Critical impact category, since any application that trusts `WebhookMetadata#shop` to select the tenant record to update (a documented, expected use per the gem's `docs/usage/webhooks.md` guidance) can have data written to or read from the wrong tenant.

### Likelihood Explanation
Exploitation requires the attacker to control an installed shop (or otherwise obtain one validly-signed webhook body) for the shared app `client_secret`/`api_secret_key`, which is a normal, low-privilege condition for any merchant who installs the app — not a leaked-credential or TLS-interception scenario. The gem's own `Registry.process` performs no additional binding check, so every host application built on this gem's documented webhook API inherits the flaw by default.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the body (e.g., concatenate normalized header values with the raw body before hashing) so that `Utils::HmacValidator.validate` fails if any of these headers are altered after Shopify signs the payload.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker intercepts/replays this request to the app's own webhook endpoint but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `x-shopify-webhook-id`/`x-shopify-topic`), leaving the body and HMAC untouched.
3. `Request.new(raw_body:, headers:)` builds the request with the forged `shop` value: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC — the forged `shop-domain` header is never checked: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated for `attacker-shop.myshopify.com`, causing the host application to process attacker-controlled webhook content under the victim tenant's identity.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
