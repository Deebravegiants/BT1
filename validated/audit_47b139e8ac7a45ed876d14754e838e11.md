### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant spoofing of the webhook source shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares its HMAC against `Context.api_secret_key` [1](#0-0) . However, `Request#to_signable_string` returns only the raw request body (`@raw_body`), and `Request#shop` is read from an unauthenticated, unsigned HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) [2](#0-1) [3](#0-2) .

The identity binding this breaks, expressed as an equality that must hold but doesn't:
`hmac_signed_bytes(request) == body_only`, while `tenant_identity_used_by_handler(request) == header["shop-domain"]`.

Because a single Shopify app has one `client_secret`/`api_secret_key` shared across every shop that installs it, HMAC validity only proves "this body was signed with our app's secret" — it proves nothing about which shop the header claims to be from. `Registry.process` passes `request.shop` straight into `WebhookMetadata` and dispatches to the registered handler without any additional shop-binding check [1](#0-0) .

An attacker who is a legitimate (even free/trial) merchant with the app installed on their own shop can capture one valid `(raw_body, hmac)` pair from a webhook Shopify sends them (or replay any prior legitimate webhook body they possess), then resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates (it only covers the body, computed with the same app-wide secret), so `Registry.process` will accept it and hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` [4](#0-3) .

### Impact Explanation
Host applications reasonably treat `WebhookMetadata#shop` (sourced from `Request#shop`) as an authenticated tenant identifier once the gem confirms `HmacValidator.validate` — but the gem does not bind that field to the signature. This lets an attacker who has any valid app-signed webhook body inject data under an arbitrary victim shop's identity into the app's webhook processing pipeline, i.e., cross-tenant access/spoofing without needing the app's `client_secret`, an access token, or any credential belonging to the victim. Depending on how the host app's handler uses `shop` (billing state, order/customer sync, mandatory GDPR webhook handling, uninstall/redact logic, etc.), this can corrupt or exfiltrate victim-tenant data, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who can install the target app on their own store (common for public apps) or who otherwise obtains one legitimate `(body, hmac)` pair — no secret material, TLS interception, or privileged access is required, only the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a forged header.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) fields as part of the HMAC-signable content, or otherwise cryptographically bind the claimed shop domain to the validated payload before it is used as a tenant identifier in `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` unless it is verified against out-of-band state (e.g., a previously stored, per-shop webhook secret/session) rather than relying purely on the app-wide `api_secret_key` HMAC over the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives a real webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value.
2. Attacker POSTs to the app's webhook endpoint with the identical `raw_body`/HMAC but sets header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header into `shop` [5](#0-4) , and `HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key` [6](#0-5) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though the body's real origin is the attacker's own shop [4](#0-3) .
