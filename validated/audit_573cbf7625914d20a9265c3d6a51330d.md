### Title
Router-controlled code can smuggle an unrelated wallet transfer under a `swap_collateral` authorization - (File: contracts/controller/src/strategies/swap_collateral.rs)

### Summary
`swap_collateral` authorizes the caller once, then executes attacker-supplied route bytes through the configured router. A malicious route venue can invoke an unrelated `token.transfer(victim, attacker, amount)` while execution is still under the caller’s `swap_collateral` authorization; Soroban records that transfer as a child invocation the victim must sign. [1](#0-0) [2](#0-1) 

### Finding Description
`process_swap_collateral` calls `caller.require_auth()`, verifies that the caller owns or delegates the account, and passes the opaque `swap` payload into `withdraw_and_swap_from_supply`. [1](#0-0) 

`swap_tokens` authorizes only the controller’s exact input-token transfer to the router, but the router invocation itself is arbitrary route-selected code reached through `router.execute_strategy(&controller, &amount_in, swap)`. [3](#0-2) 

The controller only checks that its input balance did not overspend and that its output balance increased; neither check prevents a nested venue from making a different token transfer from the signed-in caller. [4](#0-3) 

The regression test demonstrates the behavior directly: simulation records `token.transfer(victim, attacker, WALLET_BALANCE)` as a sub-invocation of the victim’s `swap_collateral` authorization, and enforcement succeeds when that poisoned tree is signed. [5](#0-4) [6](#0-5) 

### Impact Explanation
A user intending to authorize a collateral swap can lose unrelated tokens held directly in their wallet, in addition to executing the intended swap. [7](#0-6) 

The test moves an unlisted wallet token from Alice to the attacker while the collateral swap still completes successfully and deposits the expected output. [8](#0-7) 

### Likelihood Explanation
The attack requires the victim to sign an authorization tree containing the extra child transfer, matching the interactive-authorization-spoofing class of the external report. [9](#0-8) 

It does not require privileged access or a race window: the attacker supplies a route that both satisfies the swap output checks and invokes code that requests the victim’s unrelated token transfer. [10](#0-9) 

The exploit is viable whenever route construction or wallet presentation fails to make every signed child authorization unmistakable to the user. [11](#0-10) 

### Recommendation
Treat route-selected contracts as hostile authorization contexts and prevent them from adding caller-scoped child invocations. [2](#0-1) 

Prefer narrowing the user’s authorization to a dedicated, non-dispatching operation, or restructuring settlement so the router only receives contract authorization and never executes route-controlled code beneath the user’s root `require_auth`. [12](#0-11) 

Clients and wallets must also display the complete authorization tree and reject a `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` invocation containing unexpected token-transfer children. [13](#0-12) 

### Proof of Concept
1. Alice owns a funded lending account and holds an unrelated wallet token controlled by `wallet_token`. [14](#0-13) 

2. The attacker deploys a route pool containing a plan to call `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [15](#0-14) 

3. The attacker supplies Alice a `swap_collateral` route that invokes that pool while still paying enough output to satisfy the swap checks. [10](#0-9) 

4. Simulation records the unrelated wallet transfer beneath Alice’s `swap_collateral` root authorization. [16](#0-15) 

5. If Alice signs the returned tree, the host accepts the nested transfer and the attacker receives `WALLET_BALANCE`; without that child in the signed tree, the same transfer is rejected. [11](#0-10)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
