## Title
Attacker-controllable direct-transfer token vault imbalance causes deterministic panic/unwrap-abort in `calc_take_pnl`, permanently bricking swap/deposit/withdraw for a pool - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` recomputes the AMM's PnL state on every `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn(V2)` and `SwapBaseOut(V2)` call using `unwrap()`-heavy `U128`/checked arithmetic that assumes the vault's real token balances (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) are always consistent with the AMM's internally tracked `target.calc_pnl_x` / `target.calc_pnl_y` invariant values.

### Finding Description
`calc_take_pnl` derives `total_pc_without_take_pnl`/`total_coin_without_take_pnl` from the live SPL token vault balances via `Calculator::calc_total_without_take_pnl_no_orderbook(amm_pc_vault.amount, amm_coin_vault.amount, &amm)` [1](#0-0) , then performs a chain of `checked_*().unwrap()` operations to compute the new invariant (`x2`, `y2`, `diff_x`, `diff_y`, `delta_x`, `delta_y`, `pc_pnl_amount`, `coin_pnl_amount`) and to update `need_take_pnl_pc/coin` [2](#0-1) .

The AMM's coin/pc vault accounts are ordinary SPL token accounts owned by the pool authority PDA. Any unprivileged actor can perform a normal `spl_token::instruction::transfer` (or `transfer_checked`) directly into `amm_coin_vault`/`amm_pc_vault` without going through Raydium's `Deposit`/`Swap` instructions at all — this requires no signer authority over the AMM and no special permission, since SPL token transfers only require the source-account owner to sign, and vault deposits are not restricted to the AMM program. This is the classic "donation"/balance-manipulation vector common to constant-product AMMs.

Because `calc_take_pnl` blindly trusts `amm_pc_vault.amount`/`amm_coin_vault.amount` as ground truth and then does un-guarded subtraction/sqrt/division math against the previously stored `target.calc_pnl_x`/`calc_pnl_y` (which were computed from the balances at the time of the last successful call), a sufficiently large or precisely timed direct donation can push the `x1`/`y1` values (normalized invariant coordinates) out of the range the `checked_sub(...).unwrap()` chain expects — e.g. `x1.checked_sub(x2).unwrap()` at [3](#0-2)  or the subsequent `target_orders.calc_pnl_x = x1.checked_sub(...).unwrap().checked_sub(U128::from(delta_x)).unwrap()...` in the caller [4](#0-3) . Any underflow/overflow in these `unwrap()` calls causes an immediate Rust panic, aborting the instruction with `ProgramError::Custom` corresponding to a panic (BPF program panic).

Since `calc_take_pnl` runs unconditionally at the top of every `Deposit`, `Withdraw`, `WithdrawPnl`, and both `SwapBaseIn`/`SwapBaseOut` (and V2) code paths before any state-mutating transfer occurs [5](#0-4) [6](#0-5) , once a vault balance is pushed into an inconsistent state that triggers the panic, *every subsequent call to any of these instructions* will deterministically panic and fail, because the token balances (attacker-inflated) persist on-chain and nothing in the codebase provides a path to recompute/reset `target.calc_pnl_x`/`calc_pnl_y` back into a consistent state without going through the same panicking code path. This effectively **permanently bricks the pool** — no user can swap, deposit, or withdraw, and LP holders' funds become frozen in the vaults with no recovery instruction available to unprivileged users (only `SetParams`/`WithdrawPnl`, which are owner/admin-gated and would ALSO invoke the same panicking `calc_take_pnl` path for `WithdrawPnl`).

### Impact Explanation
This matches the reported bug class (CWE-129/CWE-20/CWE-248/CWE-400/CWE-617/CWE-755 — unchecked arithmetic/assertion causing a crash from a maliciously/externally influenced value) but manifests in Raydium as **permanent freezing of LP and swap-user funds** rather than a transient service panic, because Solana state changes are atomic per-transaction and the corrupting vault balance is not reset by a failed transaction — it was set by a separate, successful, permissionless token transfer. This satisfies the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium: triggering the exact underflow requires the attacker to compute/predict specific vault balances relative to the pool's internally tracked `calc_pnl_x`/`calc_pnl_y`, `sys_decimal_value`, and fee ratios, which is deterministic and computable off-chain from public on-chain state (all values needed — `AmmInfo`, `TargetOrders`, vault balances — are readable by anyone). No signer authority over the AMM is needed; only an SPL token transfer to a public vault address is needed, which is always permissionless.

### Recommendation
- Replace `unwrap()`-based arithmetic in `calc_take_pnl` (and the `target_orders.calc_pnl_x/y` update logic in the callers) with checked arithmetic that returns an `AmmError`/`ProgramError` instead of panicking.
- Validate/clamp vault balances against sane bounds before using them in invariant math, and/or track internally-accounted balances separately from raw external SPL balances to avoid trusting arbitrary external donations as invariant state.
- Add a recovery/re-sync path (admin or otherwise) that can safely rebase `TargetOrders.calc_pnl_x/calc_pnl_y` from current vault balances without going through the panicking computation.

### Proof of Concept
1. Identify a target Raydium pool's `amm_coin_vault`/`amm_pc_vault` addresses and read `AmmInfo`/`TargetOrders` state (all public).
2. Compute, off-chain, a donation amount to one vault (via a standard `spl_token::instruction::transfer` from an attacker-controlled token account into the vault) that pushes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` such that `x1.checked_sub(x2)` or a later `checked_sub` in `calc_take_pnl`/`target_orders.calc_pnl_x` update underflows.
3. Submit the donation transfer (no interaction with the Raydium program required).
4. Call any of `Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut` on the pool; observe the transaction fails due to a panic inside `calc_take_pnl`/the target-orders update.
5. Confirm all subsequent calls to these instructions on the same pool continue to fail identically, with no unprivileged recovery path — pool is permanently unusable.

*Note: I was unable to fully trace `Calculator::calc_x_power`, `Calculator::restore_decimal`, and `Calculator::normalize_decimal_v2` in this session to derive the exact numeric threshold that triggers the underflow; the index does not appear to have surfaced their full source in my searches. A background Devin session with full repository access would be needed to compute the precise donation amount and produce a concrete numeric PoC/exploit script.*
