### Title
Webhook `shop` identity field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using an HMAC that covers only the raw request body, while the `shop` field that the library extracts and hands to the application's webhook handler is taken from an unauthenticated HTTP header. This is structurally the same bug class described in the external report: a value that is *acted on* (here, shop attribution) is not covered by the value that is cryptographically *verified* (the HMAC), breaking the binding `verified_bytes == acted_on_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns **only the raw body** (`@raw_body`), never the headers: [3](#0-2) 

Meanwhile, `request.shop` — the value passed to the application's handler as the tenant identifier — is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of the signed payload: [4](#0-3) [5](#0-4) 

This `shop` value flows unmodified into `WebhookMetadata` passed to the application handler: [6](#0-5) 

The documented handler contract explicitly tells integrators to treat `data.shop` as "the shop domain of the webhook" and to key application logic (e.g., background job dispatch) off it: [7](#0-6) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across every shop that installs the app, any unprivileged internet user who installs the app on their own store can obtain a genuine webhook delivery for their own body content, complete with a valid `x-shopify-hmac-sha256` value. Since the signature covers only the body and not the `shop` header, that same body+HMAC pair remains valid if replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop's domain. `HmacValidator.validate` returns `true` in that case because it never inspects or binds the shop header, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim shop while the (attacker-controlled) body is treated as authentic and attributable to a different, victim tenant.

The binding that should hold is:
`hmac_signed_bytes == bytes_the_application_attributes_to_a_tenant`
but the actual invariant enforced by this gem is only:
`hmac_signed_bytes == raw_body`, while `shop` (the tenant key) is taken from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant confusion primitive: an attacker with a legitimate, self-obtained webhook (from their own installed shop) can cause the host application to process attacker-supplied webhook content while it is misattributed to an arbitrary victim shop domain, purely by forging the shop header on a replayed HTTP POST to the app's public webhook endpoint. Any host application that uses `data.shop` (as the library's own documentation instructs) to select a tenant record, dispatch a per-shop background job, or perform per-shop side effects (e.g., updating order/inventory data keyed by shop) can be manipulated into acting on forged data under another merchant's identity — a cross-tenant impact.

### Likelihood Explanation
The webhook endpoint is a public HTTP route by design (`ShopifyAPI::Webhooks::Registry.process` is invoked directly on `request.raw_post`/headers with no additional network-layer restriction documented or enforced by this gem). Obtaining a signed body from one's own store requires no privileges beyond installing the app on a self-owned shop — something any unprivileged internet user with a free Shopify development store can do. No access token, `api_secret_key`, or victim credential is required; only control of HTTP request headers to the public webhook route.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) header values into the HMAC-verified data, or otherwise cryptographically authenticate the shop identity — for example, by including the relevant headers in `to_signable_string`, or by requiring applications to look up the destination shop from a value that is itself covered by the signature (as Shopify's own webhook signing does not sign headers, so this is a case where documented shop-header trust needs to be paired with strict IP allowlisting/mTLS or with an authenticated correlation, such as validating that a corresponding registration/webhook_id belongs to the claimed shop). At minimum, document prominently that `data.shop` is unauthenticated and must not be used as the sole tenant-selection key without additional verification (e.g., cross-checking against the shop associated with the `webhook_id` via a stored registration/session).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures the app to receive an `orders/create` webhook.
2. Shopify delivers a legitimate webhook POST to the app's endpoint with headers including:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over the JSON body, using the app's api_secret_key>`
3. Attacker captures this raw body and HMAC value (they own the shop, so this is not privileged data).
4. Attacker replays the exact same body and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only [3](#0-2)  — validation succeeds because the body and HMAC match, despite the shop header being forged.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` [8](#0-7) , and the host application processes attacker data as if it originated from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
