## Custody Analog Found

### Title
`liquidity_pool::set_stable_fee` / `set_volatile_fee` allow swap fees to exceed the module's hardcoded `MAX_SWAP_FEES_BPS` cap - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
The Aptos swap example module declares a hardcoded ceiling for swap fees, `MAX_SWAP_FEES_BPS = 25` (0.25%), analogous to Wildcat's `MinimumAnnualInterestBips`/`MaximumAnnualInterestBips`. Just like `WildcatMarketController.setAnnualInterestBips` allowed the borrower to bypass the factory-enforced interest bounds after market creation, `liquidity_pool::set_stable_fee` and `liquidity_pool::set_volatile_fee` allow the `fee_manager` to change a pool's fee percentage after initialization without any validation against `MAX_SWAP_FEES_BPS` (or even against `FEE_SCALE`).

### Finding Description
`MAX_SWAP_FEES_BPS` is declared as a protocol-wide constant: [1](#0-0) 

At pool-config initialization time, defaults are set within this intended range (`stable_fee_bps: 10`, `volatile_fee_bps: 20`): [2](#0-1) 

Every newly created pool inherits its fee from these config values at creation time: [3](#0-2) 

However, the mutator functions that let the `fee_manager` role change these values later perform **no bounds check whatsoever** — not against `MAX_SWAP_FEES_BPS`, and not even against `FEE_SCALE` (10000, i.e., 100%): [4](#0-3) 

This mirrors the Wildcat pattern exactly: a hardcoded, protocol-committed range exists and is enforced only at creation, but the corresponding "update" entry point omits the check entirely, letting the privileged role push a config value outside of the range the protocol guarantees to depositors/traders.

### Impact Explanation
`swap_fee_bps` directly determines how much of every swapper's input is diverted from the constant-product pool reserves into the pool's dedicated `fees_store_1`/`fees_store_2` (custody-relevant value redirection) rather than being credited toward the swap output or LP reserves. Because `set_stable_fee`/`set_volatile_fee` can set this value arbitrarily (unbounded `u64`, no upper check), the `fee_manager` can:
- Set the fee near or at `FEE_SCALE` (10000 bps = 100%), diverting nearly the entire swap input into the fee stores instead of the swapper receiving output — a direct custody/value-diversion corruption for every subsequent swap on that pool.
- Set a fee value large enough to break downstream fee/output arithmetic in the swap calculation path, potentially causing reverts that lock user funds mid-transaction or produce incorrect output amounts that violate the pool's `k`-invariant guarantee that other logic (e.g., `EK_BEFORE_SWAP_GREATER_THAN_EK_AFTER_SWAP` check) depends on.

This breaks the custody invariant that "fungible asset metadata, primary and secondary stores... must preserve supply and holder identity" — the value that should flow to the swapper's output store instead flows to the fee stores in unbounded proportion, since the only bound (`MAX_SWAP_FEES_BPS`) that the protocol advertises is never enforced outside of pool creation.

### Likelihood Explanation
The `fee_manager` is a privileged role, so exploitation requires either a compromised/malicious `fee_manager` key or a governance mistake — same privilege level as the Wildcat borrower in the original finding. Given the original report was rated Medium severity specifically because it let a privileged-but-bounded actor exceed the protocol's own stated bounds, this is a direct code-shape analog rather than a generic admin-trust issue, and is easily triggerable via a single unguarded entry function call.

### Recommendation
Add a bounds check in both setters, mirroring the creation-time flow:
```move
public entry fun set_stable_fee(fee_manager: &signer, new_fee_bps: u64) acquires LiquidityPoolConfigs {
    assert!(new_fee_bps <= MAX_SWAP_FEES_BPS, error::invalid_argument(EFEE_OUT_OF_BOUNDS));
    let pool_configs = fee_manager_only_mut_liquidity_pool_configs(fee_manager);
    pool_configs.stable_fee_bps = new_fee_bps;
}
```
and identically for `set_volatile_fee`. Optionally propagate the update to existing pools' `swap_fee_bps` under the same bound, or otherwise document/enforce that existing pools are unaffected by config changes.

### Proof of Concept
Conceptual PoC (mirrors the Wildcat PoC structure):
1. Deploy the swap module; `initialize()` sets `stable_fee_bps = 10`, `volatile_fee_bps = 20`, both within `MAX_SWAP_FEES_BPS = 25`.
2. As `fee_manager` (`@deployer`), call `liquidity_pool::set_volatile_fee(fee_manager, 9999)` — no assertion fires because `set_volatile_fee` performs no range check.
3. Create/use a volatile pool; every subsequent swap now inherits/uses a fee bps far outside the protocol's `MAX_SWAP_FEES_BPS = 25` ceiling, diverting nearly 100% of swappers' input into the fee stores instead of the expected output — a value-custody violation not possible for the same role to achieve at pool-creation time (where the cap presumably would apply via the config values, though even creation-time never checks `MAX_SWAP_FEES_BPS`).

Note: I was unable to fully trace how `swap_fee_bps` feeds into the exact output-amount arithmetic (`get_amount_out`/swap execution) within the tool-call budget, so the precise overflow/underflow behavior at extreme bps values (e.g., whether it aborts safely or produces a silently wrong output) is not fully confirmed and should be verified in a live Devin session with full repository access.
