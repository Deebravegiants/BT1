## Finding

### Title
Webhook HMAC Signature Does Not Cover the `shop`/`topic`/`webhook-id` Headers, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` fields — read directly from HTTP headers — are never included in the signed content, so any attacker who can reach the app's public webhook endpoint can present a validly-signed body under an arbitrary, attacker-chosen shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface. Its `to_signable_string` method returns only the raw request body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC only against `to_signable_string`, i.e. the body — never the headers: [3](#0-2) 

`Registry.process` trusts the header-derived `shop` and `topic` unconditionally once the body HMAC passes, and hands them directly to the app's handler as the tenant identity: [4](#0-3) 

This is precisely the "field acted on but not covered by the HMAC" pattern from the report: the request's *authority* (which shop this data belongs to) is asserted by an unsigned header, while only the *payload bytes* are cryptographically verified. Since the shop identifier that the host application uses to select a tenant/session is not bound to the signature, an attacker can decouple "verified bytes" (the body) from "the shop the app believes sent them" (the header).

Concretely: an attacker who operates their own development/test shop can register a webhook and receive a legitimately Shopify-signed payload (valid body + HMAC computed with the app's real `api_secret_key`). They can then replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with a different, victim shop's domain. `HmacValidator.validate` still succeeds because it only re-derives the HMAC from the (unchanged) body, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
Most Shopify apps use the webhook's `shop` field as the tenant key to select which merchant's session/data record to update (e.g., inventory sync, order sync, GDPR `customers/redact`, `shop/redact`, `app/uninstalled`). By forging this field while keeping a body the attacker fully controls (from their own shop), an attacker can inject or associate arbitrary data with a shop they do not control — a cross-tenant access/data-integrity violation. Depending on how the host app processes specific topics (e.g., `app/uninstalled`, `customers/data_request`), this can also be leveraged to trigger unauthorized state changes against a shop that never actually sent the webhook.

### Likelihood Explanation
The webhook endpoint is, by design, a public unauthenticated HTTP endpoint (the whole point of HMAC verification is to substitute for authentication). Obtaining one validly-signed body/HMAC pair only requires operating any shop that installs the app (trivial for an attacker with a free/dev store) and registering any webhook topic. Forging the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` HTTP headers on the replayed request requires no special access — headers are attacker-controlled input in any raw HTTP request.

### Recommendation
Include the identity-bearing metadata (`shop`, `topic`, `webhook_id`, `api_version`) in the signed content, or otherwise cryptographically bind them to the payload the same way Shopify does for the standard `X-Shopify-Hmac-SHA256` header on genuine deliveries (which Shopify itself binds only to the body, but relies on TLS + secret delivery — this library's re-implementation must not let downstream apps trust headers as if they were covered). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are NOT covered by the HMAC and must not be used by host applications as an authoritative tenant identifier without additional verification (e.g., cross-checking against the shop associated with the currently stored/expected webhook registration for that specific `webhook_id`).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers a webhook, e.g. for `orders/create`.
2. Shopify delivers a genuine POST with headers:
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-SHA256: <valid HMAC of raw body B using the app's real api_secret_key>`
   - Body `B` (attacker fully controls content of the order they place).
3. Attacker replays the identical body `B` and identical `X-Shopify-Hmac-SHA256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers as-is; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `raw_body` — passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker-controlled>, ...)`, and the host application processes attacker-controlled data under the victim's tenant identity. [4](#0-3) [5](#0-4)
