### Title
`calc_take_pnl` uses a zero-tolerance invariant check that can permanently revert Deposit/Withdraw due to accumulated decimal-rounding error - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` gates every deposit, withdraw, and `withdraw_pnl` operation on a strict, tolerance-free comparison between the pool's live reserves and the last recorded "no-pnl" snapshot (`target_orders.calc_pnl_x`/`calc_pnl_y`). Because the reserves and the snapshot are round-tripped through truncating fixed-point conversions (`normalize_decimal_v2` / `restore_decimal`) on every call, rounding error accumulates over the life of the pool. Once accumulated truncation causes the live `k` to fall marginally below the recorded snapshot `k`, the hard `>=` check fails and `AmmError::CalcPnlError` is returned unconditionally, with no governance-adjustable tolerance — exactly the bug class described in the Notional report (a hardcoded, zero-margin delta check that breaks down as rounding error accumulates).

### Finding Description
In `calc_take_pnl`: [1](#0-0) 

the code restores `target.calc_pnl_x`/`calc_pnl_y` (stored in `sys_decimal_value` units) back to native decimals via `Calculator::restore_decimal`, then requires:

```
pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount
```

else it returns `AmmError::CalcPnlError`: [2](#0-1) 

`normalize_decimal_v2` and `restore_decimal` both perform integer division (truncating), with no rounding-error budget built into the comparison: [3](#0-2) 

Every deposit and withdraw call updates `target_orders.calc_pnl_x`/`calc_pnl_y` by round-tripping amounts through `normalize_decimal_v2` and subtracting `delta_x`/`delta_y` (itself derived from a truncating `integer_sqrt` and fee-ratio division): [4](#0-3) [5](#0-4) 

Each of these round trips can shave off fractional units due to floor division. Because `calc_pnl_x`/`calc_pnl_y` are threaded forward from state written by the *previous* call rather than recomputed from scratch, these small losses compound call after call. There is no governance-configurable slack analogous to Notional's `REBALANCING_UNDERLYING_DELTA` — the comparison is a bare `>=` with zero tolerance, so once enough deposit/withdraw cycles accrue truncation loss such that `pool_pc*pool_coin` dips even 1 unit below `calc_pc*calc_coin`, the function reverts.

This check is not a peripheral utility — it is invoked on the two unprivileged, fund-moving instructions reachable directly by any user:
- Deposit path: [6](#0-5) 
- Withdraw path: [7](#0-6) 
- WithdrawPnl path: [8](#0-7) 

### Impact Explanation
If the accumulated truncation ever causes `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`, `calc_take_pnl` returns `AmmError::CalcPnlError` and the enclosing `process_deposit`/`process_withdraw`/`process_withdraw_pnl` instructions abort. Because both Deposit and Withdraw call this same function and update the same `calc_pnl_x`/`calc_pnl_y` state that is carried forward, a pool that reaches this state becomes permanently unable to process withdrawals or deposits (LPs cannot get their underlying coin/pc back, and the admin cannot withdraw the pool's accrued pnl), which is a fund-freezing condition for LP capital in that AMM pool — matching Notional's "unable to rebalance / funds stuck" impact class, translated to "unable to withdraw / deposit."

### Likelihood Explanation
Every deposit and withdraw call performs a `restore_decimal`→`normalize_decimal_v2` round trip and an `integer_sqrt`-based delta calculation, each of which can floor away sub-unit amounts. This is deterministic, protocol-level truncation (not an attacker-injected condition), so likelihood scales with pool activity (number of deposit/withdraw calls) and is higher for pools with small `sys_decimal_value`/native-decimal mismatches or heavy deposit/withdraw churn, similar to how Notional's accumulated delta grows with the number of holdings/rebalances.

### Recommendation
Introduce a small, explicit tolerance (or recompute `calc_pnl_x`/`calc_pnl_y` fully from current reserves each time rather than incrementally subtracting/adding truncated deltas) so that sub-unit rounding noise cannot trip the `CalcPnlError` guard. At minimum, allow the comparison to accept `pool_pc_amount * pool_coin_amount + EPSILON >= calc_pc_amount * calc_coin_amount`, with `EPSILON` sized to the decimal precision in use, instead of a strict, zero-tolerance inequality.

### Proof of Concept
Not executed against a live cluster; the code path is deterministic:
1. Repeatedly call Deposit then Withdraw (or WithdrawPnl) on a pool with non-trivial `pc_decimals`/`coin_decimals` vs `sys_decimal_value` scaling (e.g., 6 vs 9 decimals) so that `normalize_decimal_v2`/`restore_decimal` truncate on each round trip, per [9](#0-8) .
2. Each call updates `target_orders.calc_pnl_x`/`calc_pnl_y` via the truncating arithmetic shown in [5](#0-4) , carrying forward any lost precision into the next call's snapshot.
3. Once enough cycles accumulate loss such that `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount`, the very next Deposit or Withdraw call hits the `else` branch in [2](#0-1)  and reverts with `CalcPnlError`, after which the pool can no longer process deposits or withdrawals.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)

    }
