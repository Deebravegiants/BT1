### Title
Session ID for non-embedded/cookie-based apps is derived directly from an unauthenticated, predictable client cookie value — session fixation / cross-tenant session hijacking (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` has two code paths for resolving "who is making this request": an embedded-app path that cryptographically verifies the caller's identity via a signed JWT, and a cookie-based path (used for all non-embedded apps, and as a fallback for embedded apps) that simply echoes back whatever value the client sent in the `shopify_app_session` cookie — with no signature, no binding to `api_secret_key`, and no verification of any kind.

### Finding Description
In the embedded flow, `current_session_id` derives the session id via `session_id_from_shopify_id_token`, which constructs a `Auth::JwtPayload` — this decodes and verifies the JWT signature with `Context.api_secret_key` before trusting any claim (`shop`, `sub`) inside it: [1](#0-0) 

By contrast, the cookie-based path — used unconditionally for non-embedded apps, and as the embedded fallback when no bearer token is present — takes the raw cookie value and returns it directly as the session id, with zero verification: [2](#0-1) [3](#0-2) 

The identity binding that should hold is: `session_id used to look up a stored access token` == `session_id that was actually issued to this browser as a result of a completed, HMAC-validated OAuth callback`. The JWT path enforces this equality via cryptographic signature. The cookie path does not enforce it at all — `cookie_session_id` is pure pass-through of client-supplied bytes.

This is compounded by the fact that the session id format is deterministic and derivable from public information: for offline (non-user-specific) sessions it is `"offline_#{shop}"`, and for online sessions `"#{shop}_#{user_id}"`: [4](#0-3) 

`shop` is simply the target store's `myshopify.com` domain (public knowledge), so the entire session id space for offline sessions is guessable with no secret material at all.

The `SessionCookie` struct that is set in the browser after OAuth also carries no signature or HMAC over its `value` — it is a plain struct: [5](#0-4) 

And it is populated directly from `session.id` for non-embedded (or non-embedded-cookie) flows in `Oauth.validate_auth_callback`: [6](#0-5) 

Because nothing ties the cookie's *value* back to the fact that *this browser* actually completed the HMAC-validated `/admin/oauth/authorize` → `/callback` round trip for that shop, any party able to place an arbitrary value into the `shopify_app_session` cookie on the application's origin (e.g., via session fixation from a sibling subdomain, a cookie set before login/consent, or any cookie-injection primitive in the host app) can force `current_session_id` to resolve to `"offline_victim-shop.myshopify.com"` and thereby cause the host application's session repository lookup (which apps are documented to key by this exact id) to hand back the victim shop's real, previously-issued access token.

### Impact Explanation
If the host application follows the documented pattern (look up the stored `Session` by the id returned from `SessionUtils.current_session_id`, then use it to make authenticated Admin API calls on the caller's behalf), an attacker who controls the cookie value gets the application to act using another shop's access token — a cross-tenant access / session-fixation condition, which the scope rules explicitly list as a High-impact category ("session fixation or forced OAuth completion").

### Likelihood Explanation
No secret material (`api_secret_key`, access token) is needed to construct the target session id — it is derived purely from the public shop domain. The only prerequisite is a way to set/inject that specific cookie value for the application's own domain, which is the class of primitive session-fixation attacks are built on. The severity is data/impact-dependent on the host app's session-repository implementation, but the library itself provides no defense-in-depth here, unlike the embedded/JWT path, which is exactly the asymmetry this analog is built to flag.

### Recommendation
Do not treat the raw cookie value as a trusted, final session identifier. Either:
- Cryptographically sign/HMAC the cookie's value (e.g., with `Context.api_secret_key`) when it is set in `validate_auth_callback`, and verify that signature in `cookie_session_id` before returning it, mirroring the protection already given to the JWT path; or
- Bind the cookie to a per-flow, unpredictable nonce (similar to the `state` nonce already used in `begin_auth`) rather than the deterministic `offline_#{shop}` / `#{shop}_#{user_id}` scheme, so guessing/fixating a valid id is infeasible without observing the actual cookie issued to the legitimate browser.

### Proof of Concept
1. Attacker knows (or discovers) the victim's shop domain `victim-shop.myshopify.com` (public).
2. Attacker forces/sets a cookie `shopify_app_session=offline_victim-shop.myshopify.com` on the application's origin against their own browser session (via any cookie-fixation/injection vector on the host app, e.g., setting the cookie before authentication, a sibling-subdomain cookie write, or a response that reflects a cookie value).
3. Attacker sends a request to the application; the app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`.
4. `cookie_session_id` returns `"offline_victim-shop.myshopify.com"` verbatim — no check that this browser ever completed OAuth for that shop. [3](#0-2) 
5. The host app looks up the stored `Session` for that id (per the documented `SessionRepository` pattern) and uses its `access_token` to serve the attacker's request against `victim-shop`'s data — cross-tenant access achieved without ever knowing the victim's actual access token or the app's `client_secret`.

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end
