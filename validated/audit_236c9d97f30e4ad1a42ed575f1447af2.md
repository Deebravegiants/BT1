### Title
Webhook shop/topic/id metadata spoofable despite valid HMAC — cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but `to_signable_string` (the value that is actually HMAC-verified) returns only `@raw_body`. `Utils::HmacValidator.validate` therefore proves that the *body* bytes were produced by Shopify with the app's secret, but proves nothing about which shop, topic, or webhook subscription the metadata headers claim to represent.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns just the raw body: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable headers: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC only over `to_signable_string` (the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` trusts this validation and then forwards the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` values directly to the app's handler: [4](#0-3) 

The identity binding that should hold is: **shop-domain header used to key tenant data == shop that Shopify's HMAC actually attests to**. That equality does not hold — the HMAC attests only to the body, not to the shop/topic/webhook-id metadata. Any entity capable of triggering one authentic webhook delivery to the app (e.g. by installing the app for free on their own development store, which any unprivileged internet user can do) can capture a single valid `(raw_body, hmac-sha256)` pair from Shopify and then replay it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. `HmacValidator.validate` still succeeds because it only checks the untouched body against the untouched HMAC, and `Registry.process` hands the forged shop identity to the handler as if it were authentic, per the documented usage pattern: [5](#0-4) 

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: it enables cross-tenant impersonation of webhook events. A host app that (as documented) uses `data.shop` to select which merchant's data/session to act on can be tricked into attributing a webhook payload it received from Shop A to Shop B, or into re-labeling an innocuous topic as a sensitive one (e.g. relabeling `carts/update` as `app/uninstalled` or `shop/redact`), since neither the topic nor the shop is part of the signed material. This matches the "cross-tenant access" Critical-impact category for this analysis.

### Likelihood Explanation
High. No secrets, tokens, or privileged access are required — only a single authentic webhook delivery captured from the attacker's own (freely installable) shop, and the ability to POST arbitrary headers to the app's public webhook receiver endpoint, both of which are available to any unprivileged internet user who installs the app once.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-verified signable string, or otherwise cryptographically bind them to the body (e.g., verify them independently against a per-shop stored value rather than trusting the header verbatim). At minimum, `to_signable_string` should not diverge from the set of fields `Registry.process`/`WebhookMetadata` exposes to handlers as trusted, authenticated data.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []

          end

        end

        @headers = headers
        @raw_body = raw_body
      end
