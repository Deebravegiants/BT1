### Title
Fraud/liveness detection is fully stubbed out, allowing every signup to bypass on-Orb fraud checks - (File: `src/plans/mod.rs`, `src/plans/fraud_check.rs`)

### Summary
The external report's bug class is "a security-critical authorization gate exists in name only and never actually enforces anything" (`_authorizeUpgrade()` present but not checking `msg.sender`). The direct analog in `orb-core` is `Plan::detect_fraud` in `src/plans/mod.rs`, which is the gate that is supposed to block fraudulent/spoofed signups, but which is hard-coded to always return `Ok(false)` (no fraud), and its backing `fraud_check::Report`/`FraudChecks` machinery in `src/plans/fraud_check.rs` has `N_FRAUD_CHECKS` set to `0` with every check array literally empty (`[]`). The enforcement point exists in the code, is called on every signup, but performs no real validation, exactly mirroring the reported pattern of a present-but-non-functional authorization/validation hook.

### Finding Description
`Plan::do_signup` in `src/plans/mod.rs` calls: [1](#0-0) 
which computes `fraud_detected` from `self.detect_fraud(...)`. That function is defined as: [2](#0-1) 
Note the explicit comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` followed by an unconditional `Ok(false)`. Regardless of the biometric pipeline output, `fraud_detected` is always `false`.

The supporting `fraud_check` module reinforces this: `N_FRAUD_CHECKS` is hard-coded to `0`, and every method that should enumerate/evaluate individual fraud signals returns an empty array: [3](#0-2) [4](#0-3) 
And `FraudChecks::run` unconditionally returns an empty `Report`: [5](#0-4) 

Just as the Solidity report found `_authorizeUpgrade()` present but not verifying `msg.sender` (letting any caller upgrade), here `detect_fraud`/`FraudChecks` are present, wired into the signup flow, and invoked on every signup, but structurally cannot ever flag fraud since the check arrays are always empty. The root cause is identical in shape: a mandatory security gate that is implemented as a no-op instead of performing real validation.

### Impact Explanation
Because `fraud_detected` is always `false`, `signup_reason` in `do_signup` can never become `SignupReason::Fraud` due to on-Orb fraud detection: [6](#0-5) 
This means any Orb-detected fraud/liveness/spoofing signal that this pipeline stage was meant to catch (e.g., presentation attacks, occlusion-based spoofing, or other biometric fraud heuristics referenced by `PipelineFailureFeedbackMessage`) is silently ignored, and the signup proceeds to enrollment as if legitimate. This directly matches the requested impact categories of "fraud/liveness bypass" — an attacker attempting to spoof a signup at the Orb only needs to pass whatever remains of the biometric capture/pipeline stage; the dedicated fraud-check gate provides zero additional protection.

### Likelihood Explanation
High/certain: this is not a conditional or feature-gated bypass reachable only under special circumstances — it is the only code path (`N_FRAUD_CHECKS = 0` and `Ok(false)` unconditionally), so it applies to every single signup on every Orb running this code, with no attacker action required beyond attempting a normal signup.

### Recommendation
Restore (or re-implement) concrete fraud/liveness checks in `FraudChecks::run` / `fraud_check::Report` so that `N_FRAUD_CHECKS` reflects real evaluated signals, and make `detect_fraud` in `src/plans/mod.rs` actually evaluate `pipeline` data (occlusion, spoofing signals, etc.) rather than unconditionally returning `Ok(false)`. At minimum, document this as an intentional FOSS build limitation and ensure production builds (non-FOSS) restore full fraud-check enforcement before deployment.

### Proof of Concept
1. Run any signup on the Orb (with any capture, even one that should trigger fraud/liveness heuristics that `PipelineFailureFeedbackMessage` variants imply, e.g., `ContactLenses`, `Mask`, `MultipleFaces`, `EyesOcclusion`).
2. Observe `Plan::detect_fraud` (`src/plans/mod.rs:1392-1406`) is invoked; because `N_FRAUD_CHECKS == 0`, `fraud_checks_strict()` always returns `[]`, and `detect_fraud` returns `Ok(false)` unconditionally.
3. `signup_reason` therefore is computed as `SignupReason::Normal` (assuming pipeline succeeded), and the signup proceeds to `enroll_user`/backend submission as a normal, non-fraudulent signup, with no possibility for the on-Orb fraud engine to ever flag it as fraud.
