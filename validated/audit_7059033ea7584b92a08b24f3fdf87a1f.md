Confirmed: `HmacValidator.validate` uses a single, app-wide `Context.api_secret_key` (and optional `Context.old_api_secret_key`) for every shop — there is no per-shop secret lookup here.### Title
`Webhooks::Request#to_signable_string` signs only the raw body, so the unsigned `shop`, `topic`, `webhook_id`, and `api_version` headers can be relabelled to attribute a valid webhook to any shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , so `HmacValidator.validate` verifies the body against a single app-wide `Context.api_secret_key` [2](#0-1)  without covering any header, including `shop-domain`, `topic`, or `webhook_id`, which `Registry.process` reads separately from the request and passes uncontested to the handler [3](#0-2) . The "two spellings" detail in `initialize` (accepting either `shopify-#{name}` or `x-shopify-#{name}`) is not the actual root cause — even with only one spelling supported, no header is ever included in `to_signable_string`, so the exact same relabelling attack works.

### Finding Description
The claimed binding would be: `shopify_header("shop-domain")` used by `Registry.process` to select the tenant is bound to (i.e., cryptographically covered by) the HMAC verified via `to_signable_string`. Tracing the code shows this equality never holds: `to_signable_string` returns `@raw_body` alone [1](#0-0) , `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled from `@headers` via `shopify_header`, which is not part of the signable string [4](#0-3) [5](#0-4) . `initialize`'s presence check only requires that at least one spelling of `topic`, `hmac-sha256`, and `shop-domain` exist per name — it does not tie the accepted values to what `shopify_header` later resolves, but this discrepancy is irrelevant to the exploit because neither spelling is ever hashed. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`, using one app-level `Context.api_secret_key` (with an optional `Context.old_api_secret_key` fallback) for all shops/tenants of the app [6](#0-5) . `Registry.process` validates the HMAC, then trusts `request.topic` and `request.shop` straight from headers to route and construct `WebhookMetadata` for the handler [3](#0-2) .

Exploit flow: the attacker creates their own development shop, installs the app, and receives a legitimately-signed webhook (body + HMAC) from Shopify for their own shop. Because the HMAC secret is the single app-level `client_secret` shared across all shops using this app (not a per-shop secret), the attacker can POST that exact same `raw_body` and `x-shopify-hmac-sha256` header to the app's webhook endpoint while setting `x-shopify-shop-domain` to a victim merchant's domain. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret; `Registry.process` then calls the handler with `shop: request.shop` set to the victim's domain, i.e., a forged/relabelled tenant attribution for content the app will treat as an authentic event for the victim.

No existing guard in this codebase prevents this: `HmacValidator.validate`/`validate_signature` never see or check headers [7](#0-6) ; `ShopValidator.sanitize!`, `state` comparison, `JwtPayload`'s `aud` check, and `Context.setup?`/`private?`/`embedded?` are unrelated to the webhook path and do not run here.

### Impact Explanation
An attacker who has any single genuinely-signed webhook body from their own shop can cause the host app to process it as if it originated from an arbitrary victim shop, since `shop`, `topic`, and `webhook_id` are all taken from unsigned headers [8](#0-7) . This is repeatable against arbitrary victim shop domains chosen by the attacker (the domain is a free-form string not validated against any allow-list in this file), and each host app's handler is fully responsible for whatever cross-tenant consequences follow (e.g., writing attacker-supplied body content into a victim's tenant data, triggering a victim-scoped side effect). This matches "cross-tenant access" impact, contingent on how the host app's webhook handler uses `WebhookMetadata#shop`.

However, this is standard, documented behavior of Shopify's webhook HMAC scheme in general (Shopify's own webhook signature only ever covers the raw body, not headers) — it is not a gem-introduced defect distinct from the platform's design, and mitigating it fully would require either verifying `shop` against an independent, previously-known set of installed shops (which host apps are expected to do, and which the `Registry`/session storage layer of this gem does not itself perform in `Registry.process`) or Shopify issuing per-shop webhook secrets. The gem provides no header-independent shop verification step in `Registry.process`.

### Likelihood Explanation
Preconditions are modest for an unprivileged attacker: they need one working self-hosted or trial install of the target app (registering their own webhook endpoint and shop) to obtain one legitimately-signed body+HMAC pair, then can replay it against the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` value. This requires no secret material and is fully repeatable per attacker-chosen victim domain, so likelihood is high assuming the host app trusts `WebhookMetadata#shop` without independent verification (e.g., checking that the shop is actually installed and that this specific webhook/topic was expected from it).

### Recommendation
Have `Registry.process` (or the host app, if using this gem as documented) independently verify that `request.shop` corresponds to a shop with an active installation/session before invoking the handler, rather than trusting `shopify_header("shop-domain")` on faith once the body HMAC passes. Longer term, `to_signable_string` cannot itself bind headers into the HMAC because Shopify's real webhook signature does not cover headers; the mitigation belongs at the app-integration layer (shop-existence check), not purely inside `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (illustrative, not present as-is)
def test_shop_header_can_be_relabelled_without_invalidating_hmac
  body = '{"id":1}'
  secret = ShopifyAPI::Context.api_secret_key
  hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
  )

  headers_shop_a = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  }
  headers_shop_b = headers_shop_a.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

  request_a = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_shop_a)
  request_b = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_shop_b)

  assert ShopifyAPI::Utils::HmacValidator.validate(request_a)
  assert ShopifyAPI::Utils::HmacValidator.validate(request_b) # same body/hmac, still valid
  refute_equal request_a.shop, request_b.shop # same signature, two different attributed shops
end
```
This demonstrates the core claim — one valid signature is accepted for two different `shop` values — using `Utils::HmacValidator.validate` and `Webhooks::Request` directly, matching the "fast validation" the question requests. Whether this rises to "Critical - authentication bypass" for a given deployment depends entirely on whether the host app's webhook handler trusts `WebhookMetadata#shop` without an independent installed-shop check, which is outside `lib/shopify_api/webhooks/request.rb` and outside what I could verify further within the provided tool budget.
