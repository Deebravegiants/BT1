Confirmed: the webhook HMAC only signs the raw body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers and passed to the handler as trusted tenant identity, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Title
Webhook HMAC only signs the request body, letting the `shop` and `topic` headers be forged for cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the body bytes were signed by the app's client secret [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never covered by the signature [3](#0-2) . `Registry.process` then dispatches the handler based on the unauthenticated `request.topic` and hands the unauthenticated `request.shop` to the handler as the tenant identity [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop/topic authenticated by HMAC == shop/topic acted on by the handler`. In this gem that equality is broken because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, and the signature is computed only over `@raw_body`:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```
`lib/shopify_api/webhooks/request.rb:35-38`

`shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers that sit outside this signed string:

```ruby
def topic
  T.cast(shopify_header("topic"), String)
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`lib/shopify_api/webhooks/request.rb:15-23`

`Registry.process` validates the HMAC, then trusts these unauthenticated fields to select the handler and to build the `WebhookMetadata` passed into merchant/tenant-specific business logic:

```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
`lib/shopify_api/webhooks/registry.rb:188-199`

Because the app's HMAC secret is identical for all shops using the app, any actor who installs the app on their own store (an unprivileged, non-attacker-controlled action any merchant can take) receives genuine webhook deliveries with a valid `hmac-sha256` header computed over a body they at least partly influence (e.g., via product/customer/order field content). Since `shop`, `topic`, `webhook_id`, and `api_version` are not part of the signed content, that attacker can replay the same `raw_body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (a victim tenant) and/or an arbitrary `shopify-topic` header, and the signature will still validate. The handler then processes attacker-supplied data as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant confusion / spoofing bypass: the HMAC check is supposed to bind body integrity and authenticity, but `Registry.process` implicitly treats it as also authenticating `shop` and `topic`, which it does not. A host application built on this gem that keys any state (subscription status, GDPR redaction handling, data sync, billing) off `WebhookMetadata#shop`/`#topic` can be made to apply attacker-influenced data or trigger attacker-chosen handlers under another merchant's shop identity, which matches the "cross-tenant access" class of Critical impact.

### Likelihood Explanation
Exploitability only requires the attacker to be a legitimate (even free-tier) installer of the app — no `api_secret_key`, access token, or privileged account is needed, satisfying the required unprivileged-internet-user threat model. The attacker needs an HTTP client capable of replaying a captured request with modified headers, which is trivial once the app is installed on their own store and delivers at least one webhook.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed content used by `HmacValidator`, or otherwise cryptographically bind these header values to the request (e.g., re-verify `shop` against a per-shop stored secret/session, or require the host application to independently validate that the `shop` header corresponds to an installation that is expected to receive the given `topic`). At minimum, document that `request.shop` and `request.topic` are not covered by the HMAC and must not be treated as authenticated by callers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook event (e.g., update a product) so Shopify sends a real webhook with body `B` and header `shopify-hmac-sha256: H = HMAC(client_secret, B)`.
2. Capture this request.
3. Replay the same body `B` and header `shopify-hmac-sha256: H` to the app's webhook endpoint, but replace `shopify-shop-domain: attacker.myshopify.com` with `shopify-shop-domain: victim.myshopify.com` (and optionally swap `shopify-topic` to another registered topic).
4. `Utils::HmacValidator.validate(request)` returns `true` because only `B` is signed [1](#0-0) .
5. `Registry.process` invokes the handler with `WebhookMetadata#shop == "victim.myshopify.com"` even though the request never touched Shopify's systems for that shop [5](#0-4) .
