### Title
Webhook `shop` field is not covered by the HMAC signature, allowing tenant-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook using only the raw request body against the `X-Shopify-Hmac-Sha256` header, but the `shop` identity (`X-Shopify-Shop-Domain` header) passed to the application's webhook handler is never included in the HMAC-verified bytes.

### Finding Description
`Registry.process` treats a webhook as authentic solely based on `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the shop domain is not part of the signed data [3](#0-2) .

Once the HMAC check passes, `request.shop` (derived purely from the unauthenticated `shopify-shop-domain` header) is forwarded to the app's handler as the tenant identity in `WebhookMetadata` [4](#0-3) , and `WebhookMetadata.shop` is a plain `String` field with no binding back to the signed body [5](#0-4) .

This breaks the identity binding: `shop attributed to webhook == shop verified by HMAC` is false. The equality that should hold is `HMAC-covered bytes ⊇ {shop, body}`, but in reality `HMAC-covered bytes == {body}` only, while `shop` is parsed from an unauthenticated header.

Concretely: if an attacker knows (or can compute) a valid `(raw_body, hmac)` pair signed with the app's secret for *any* shop's webhook — e.g., because they operate their own store installed on the app and thus legitimately receive correctly-signed webhooks addressed to their own shop — they can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still succeed because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop, even though Shopify never sent that data for that shop.

### Impact Explanation
This lets an unprivileged attacker (any merchant who can obtain one legitimately signed webhook, or anyone who can otherwise capture/replay a signed body) cause the host application to process webhook content under a `shop` identity it did not verify. Since apps typically use `WebhookMetadata.shop` to select which merchant's session/data the payload applies to, this is a cross-tenant attribution/data-integrity issue: attacker-controlled body content (from their own legitimately-signed webhook) can be attributed to a victim shop, or vice versa, without any additional secret being required. This matches the "field acted on but not covered by the HMAC" analog class and rises to a cross-tenant boundary break.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: exploitation requires the attacker to first obtain at least one validly-signed `(body, hmac)` pair for the *same* `client_secret`/app (most naturally by being a legitimate merchant of the same installed app, or by capturing a delivered webhook), since the HMAC is keyed with the app's `api_secret_key`/`client_secret` and the attacker cannot forge new bodies for arbitrary content. However, no privileged credential (access token, `client_secret` value itself) is required — only observation/replay of one legitimate webhook delivery, which is fully within reach of an "unprivileged internet user" who is also a merchant of the same app.

### Recommendation
Include the shop domain (and ideally topic, webhook id, and api version) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the `shop` header to the signature (e.g., verify that the shop domain matches an out-of-band expected value for the session context) before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata.shop` is unauthenticated and must be cross-checked by the consuming application against a known session mapping before being trusted.

### Proof of Concept
1. Attacker registers/owns their own shop `attacker.myshopify.com` with the target app, and legitimately receives a Shopify webhook for a topic the app has registered a handler for. They capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value — both valid and correctly signed with the app's `api_secret_key`.
2. Attacker crafts a new HTTP request to the same public webhook endpoint (`WebhookController#webhook` per the documented Rails integration [6](#0-5) ), reusing the exact captured `raw_body` and `hmac` header unchanged, but setting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds (the shop header was never part of the signed bytes) [7](#0-6) [3](#0-2) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` [8](#0-7) , causing the app to process attacker-controlled webhook content as if it originated from and applies to the victim's shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
