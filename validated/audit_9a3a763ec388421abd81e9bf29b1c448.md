### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the host application's handler are taken verbatim from unauthenticated HTTP headers. Because a single app-wide `api_secret_key` is used to sign webhooks for *every* shop that has installed the app, any merchant (an unprivileged internet user with respect to other tenants) can obtain a validly-signed webhook body from their own store and replay it with a forged `X-Shopify-Shop-Domain` header to make the app attribute that data to a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from headers with no relationship to the signed content: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it validates the body bytes, never the shop/topic headers: [3](#0-2) 

`Registry.process` then forwards the unauthenticated `request.shop` straight into `WebhookMetadata` handed to the host app's handler, after only checking the body HMAC: [4](#0-3) 

The binding that should hold is:
`hmac_verified(secret, bytes) == (bytes, shop)` — i.e. the shop the app acts on should be cryptographically bound to the same material that was verified. Instead the gem verifies `hmac_verified(secret, raw_body)` but hands out `shop` from an independent, unauthenticated channel (the header), so the equality `verified_bytes == acted_on_identity` does not hold.

Because Shopify apps share one `client_secret` (`Context.api_secret_key`) across all shops that install them, any merchant can:
1. Install the app on their own shop and trigger a webhook (e.g. `orders/create`) with attacker-chosen body content.
2. Capture the resulting `raw_body` + valid `X-Shopify-Hmac-Sha256` pair (this is a genuine, correctly-signed webhook — no secret needs to be recovered).
3. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) rewritten to name a victim shop that also uses the app.
4. `Utils::HmacValidator.validate` succeeds (body/HMAC pair is valid), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

Any host application that uses `data.shop` from `WebhookMetadata` (as recommended in the gem's own docs) to look up the tenant/session to apply the webhook body to will now apply attacker-controlled data under the identity of a different tenant.

### Impact Explanation
This breaks a tenant identity binding entirely within this gem's own webhook-processing code path (`Webhooks::Request` + `Webhooks::Registry.process` + `Utils::HmacValidator`), without requiring any leaked credential — the attacker only needs the ability to install the app on their own store, which is the normal unprivileged flow for any Shopify merchant. The result is cross-tenant confusion: attacker-controlled webhook data is delivered to the host app labeled as belonging to a victim shop, which the app's own documented usage pattern (`data.shop`) uses to key tenant data.

### Likelihood Explanation
High reachability: no special component, no secret theft, no privileged account is required — just installing the app on an attacker-owned shop (or using any legitimately-installed shop's public webhook capabilities) and a single crafted HTTP replay with a modified header, since the HMAC only signs the body.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the signed body (e.g., require the caller to additionally verify that `request.shop` matches an actively-installed session known to the app, and document this as mandatory rather than optional). At minimum, the library should not present `request.shop`/`WebhookMetadata#shop` as trusted output of `Registry.process` when nothing in `Utils::HmacValidator.validate` covers it.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`.
2. Trigger `orders/create` (or any subscribed topic) with attacker-controlled body content; capture `raw_body` and the resulting `X-Shopify-Hmac-Sha256` value from the genuine webhook POST Shopify sends to the app.
3. Resend an HTTP POST to the app's webhook endpoint with the same `raw_body` and same `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` accepts the request (`Utils::HmacValidator.validate` passes because it only checks the body) and invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
