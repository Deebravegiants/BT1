### Title
Webhook `shop-domain` Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header to identify which tenant the webhook belongs to before dispatching it to the app's handler. Because the shop-domain header is never included in the signed bytes, an attacker who can obtain any single valid `(raw_body, hmac)` pair for the app (e.g. by owning/controlling one installation of the app) can replay that exact body with an `hmac-sha256` signature that still validates, while substituting the `shop-domain` header for a victim shop. The handler then processes that payload under the identity of the victim tenant, breaking the binding "shop the HMAC authenticates" == "shop the handler receives".

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header and is not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over exactly `to_signable_string`, i.e. only `@raw_body`, using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` performs this HMAC check and, if it passes, immediately trusts `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's `WebhookHandler`: [4](#0-3) 

`WebhookMetadata#shop` is then handed to the host application's handler as the authoritative tenant identifier for the event: [5](#0-4) 

Identity binding broken (equality that should hold but doesn't):
`shop authenticated by HMAC` (nothing — HMAC only proves `raw_body` bytes were signed with `api_secret_key`) ≠ `shop delivered to the handler as WebhookMetadata#shop` (fully attacker-controlled header value).

Since the same `api_secret_key` is shared across all shops/tenants of a given app, any party that can obtain one legitimate `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and inspects the webhook their own server receives — can resend that exact body/HMAC pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header. The gem will accept it as valid and hand the body's data to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant confusion: the gem lets a caller who controls or has observed one shop's webhook traffic have their webhook body attributed to a different, unrelated shop. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g. `customers/redact`, `shop/redact`, `orders/*`, `app/uninstalled`), this can be leveraged to trigger cross-tenant data mutation/deletion, spoof mandatory compliance webhooks against a victim shop, or otherwise make the app believe an event pertains to a shop it did not originate from. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) that host applications rely on this gem to authenticate is not actually cryptographically bound to the signature.

### Likelihood Explanation
Exploitability requires obtaining at least one legitimate `(raw_body, hmac)` pair for the target app — achievable by any unprivileged user who installs the app on a store they control (a normal, unprivileged action for any Shopify merchant) and captures the webhook request their own server receives. No access to `api_secret_key`, access tokens, or the victim's data is required. The replay itself is a simple unauthenticated HTTP POST to the app's own webhook endpoint with a forged `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload verification, or otherwise cryptographically bind the `shop-domain` header to the request — e.g., by having `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` incorporate the header value into the signed string it checks, or by requiring host applications to independently validate that `request.shop` matches a shop with an active, previously-established session/installation before trusting `WebhookMetadata#shop`, and documenting this precondition clearly if the gem intentionally leaves cross-request tenant correlation to the caller.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) to be delivered to the app's webhook endpoint.
2. Attacker's own server captures the exact `raw_body` and `x-shopify-hmac-sha256` header from this legitimate, correctly-signed webhook request.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the secret — this passes because the body/HMAC pair is unchanged. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"`, even though the body content actually originated from the attacker's own shop. [2](#0-1) 
6. The host application's business logic acts on this event believing it pertains to `victim-shop.myshopify.com`.
