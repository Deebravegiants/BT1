## Title
Unchecked-empty-array panic in BEEFY naive-proof ABI conversion crashes the runtime on submission of an attacker-crafted proof - (File: evm/rust/src/conversions.rs)

## Summary
`pallet-beefy-consensus-proofs::submit_proof` (permissionless, `ensure_signed` — any account can call it) accepts a raw proof, and for `PROOF_TYPE_NAIVE` decodes it as ABI-encoded `BeefyConsensusProof` and converts it to the SCALE-encoded `ConsensusMessage` used internally, before that message is ever run through the cryptographic BEEFY checks. That conversion chain (`ecdsa_beefy::BeefyConsensusProof` → `ConsensusMessage` → ... → `Commitment` → `SpCommitment`) contains an unconditional `.expect()` on the first element of an attacker-controlled `payload` vector, which panics the runtime instead of returning a typed error.

## Finding Description
`Pallet::do_submit_proof` / `Pallet::verify_and_apply` in `modules/pallets/beefy-consensus-proofs/src/lib.rs` decode the naive-proof branch via:

```rust
let abi_proof = <ismp_abi::ecdsa_beefy::BeefyConsensusProof as SolType>::abi_decode_params(abi_payload)
    .map_err(|_| Error::<T>::AbiDecodeFailed)?;
let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
``` [1](#0-0) 

That `Into<ConsensusMessage>` conversion for `BeefyConsensusProof` calls `message.mmr.into()` (`RelayChainProof` → `MmrProof`), which converts `value.signedCommitment.commitment.into()` — i.e. the Solidity `Commitment` struct into `SpCommitment`:

```rust
impl From<Commitment> for SpCommitment {
    fn from(value: Commitment) -> Self {
        let mut iter = value.payload.into_iter();
        let first = iter.next().expect("commitment has at least one payload entry");
        ...
    }
}
``` [2](#0-1) 

`payload` is a `Vec<Payload>` field of the ABI-decoded struct that the caller fully controls at the byte level (`abi_decode_params` will happily decode an empty dynamic array). Because `abi_decode_params` only validates ABI well-formedness, not business invariants, an attacker can submit a proof whose `signedCommitment.commitment.payload` array is empty. `abi_decode_params` succeeds, `.into()` is invoked, and the `.expect(...)` on `iter.next()` panics — this happens *before* any cryptographic (ECDSA signature / authority set) verification occurs, so no valid signature or authority membership is required to trigger it. This is the same bug class as the reported Go `crypto/x509` issue: a malformed/degenerate structural field (empty DNS-name-like list / empty payload list) that a later, unrelated check assumes is non-empty, causing an unchecked index/`.expect()` panic during verification of untrusted input.

This is structurally identical to several *already-fixed* panic regressions elsewhere in this same codebase (e.g. `modules/consensus/beefy/verifier/src/lib.rs:225-257`'s `leaf_indices[0]` guard, `modules/consensus/grandpa/verifier/src/error.rs`'s `RelayHeaderNotInUnknownHeaders`, `modules/consensus/sync-committee/verifier/src/lib.rs:184-192`'s multiproof-length guard, and `modules/consensus/pharos/primitives/src/spv.rs`'s `nibble_at_depth`/`MAX_PROOF_DEPTH` guards) — all of which replaced an `.expect()`/index panic on attacker-controlled proof shape with a typed `Err`. This particular `.expect("commitment has at least one payload entry")` in `evm/rust/src/conversions.rs` was not covered by that hardening pass.

## Impact Explanation
`submit_proof` is dispatched with `#[frame_support::transactional]` on a normal signed extrinsic [3](#0-2) . A Rust panic inside runtime (WASM) execution during extrinsic dispatch is not gracefully caught as a `DispatchError` — it aborts execution of the block/import for every collator/validator applying that extrinsic, which is a chain-halting / block-production-disrupting condition (all nodes that try to import the block containing this transaction panic identically). This is a "route unable to deliver messages" condition at minimum (the BEEFY consensus-update path becomes unusable while the fault is present/exploited) and, more severely, an availability failure for the whole parachain, since panics during transaction execution are typically not isolated per-transaction the way `DispatchError` is.

## Likelihood Explanation
Any account can call `submit_proof` with a signed origin (no permissions, no funds required beyond the transaction fee) and provide `PROOF_TYPE_NAIVE` with a hand-crafted ABI payload whose `commitment.payload` array is empty. This requires no cryptographic material, no authority set knowledge, and no prior state — it purely exploits the type-conversion path that runs before any signature check. `verify_and_apply` and `do_submit_proof` both hit this same conversion before the `handlers::handle_incoming_message` cryptographic checks run [4](#0-3) , so the panic is trivially and repeatably reachable.

## Recommendation
Replace the `.expect("commitment has at least one payload entry")` in `From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs:334-354`) with a fallible conversion (`TryFrom`) that returns a typed decode error when `payload` is empty, and thread that error through `BeefyConsensusProof -> ConsensusMessage`, `RelayChainProof -> MmrProof`, and the pallet's `AbiDecodeFailed`/decode-error path so a malformed naive proof is rejected with a `DispatchError` instead of panicking. Audit the rest of `evm/rust/src/conversions.rs` for the same pattern (several sibling conversions use `.expect("... out of bounds")` on `try_into()`, which are comparatively benign numeric truncation guards, but the `payload` `.expect` is the one operating on an attacker-controlled-length collection and should be fixed first).

## Proof of Concept
1. Craft an ABI-encoded `BeefyConsensusProof` (Solidity tuple `(RelayChainProof, ParachainProof)`) whose `relay.signedCommitment.commitment.payload` is an empty array (valid, well-formed ABI encoding of a zero-length dynamic array) — all other fields can be arbitrary/zeroed since they are never reached.
2. Prefix the encoded bytes with `PROOF_TYPE_NAIVE` (`0x00`) to build the wire-format `proof: Vec<u8>` expected by `submit_proof`.
3. Submit `BeefyConsensusProofs::submit_proof(proof)` as a signed extrinsic from any funded account (mirrors the "malformed naive bytes" style test already present at `parachain/simtests/src/pallet_beefy_consensus_proofs.rs:378-388`, except here the bytes ABI-decode successfully but carry a structurally-empty `payload`).
4. Runtime execution panics inside `From<Commitment> for SpCommitment` during `Self::verify_and_apply(&proof)` before any signature check, instead of returning `Error::<T>::AbiDecodeFailed`/`VerificationFailed`.
