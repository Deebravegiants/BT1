### Title
Unbounded swap amount lets any caller drain tokens stranded in `LifiExternalAction` from a prior partial-fill refund - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` measures a swap's result purely as `outputToken` balance delta and grants the LI.FI router an unlimited, standing approval on `inputToken`, without ever checking that the amount consumed from the contract equals the caller's own `inputAmount` (`-deltaAmounts[0]`). Because the contract is a shared pool for all callers, any `inputToken` that ends up sitting in `LifiExternalAction` - for example a partial-fill refund the router sends back to the contract instead of forwarding it anywhere else - can be swept by a later, unrelated caller's swap and credited to that caller's own output UTXO.

### Finding Description
The claimed equality is: *the amount Hinkal escrows to the action for caller X's call* (`-deltaAmountChanges[i]`, sent in `Hinkal._externalTransact`, `contracts/Hinkal.sol:247-256`) *should equal the net `inputToken` actually consumed by `callRouter` for that specific call*. Nothing in the code enforces this.

- `Hinkal._externalTransact` (`contracts/Hinkal.sol:234-261`) pushes `-deltaAmountChanges[i]` of `inputToken` into `circomData.externalActionData.externalAddress` (the `LifiExternalAction` contract) and then calls `runAction`. This transfer only adds to whatever balance the contract already holds; it does not escrow the funds per-call.
- `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`) computes `inputAmount = uint256(-deltaAmounts[0])` from the caller's own proof-derived delta, then calls `callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata)`.
- `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) calls `approveUnlimited(inputToken, router)` and then `router.call(externalActionMetadata)` with **caller-supplied, arbitrary calldata**. `inputAmount` is passed into the function but is never used to bound, validate, or restrict what the router calldata actually withdraws from the contract. `swappedAmount` is computed solely as `getERC20OrETHBalance(outputToken) - balanceBefore`, i.e. the raw balance delta of the *output* side only.
- Because the router allowance on `inputToken` is unlimited (`approveUnlimited`) and unrelated to `inputAmount`, the router can pull (and the attacker's own crafted `externalActionMetadata` can request) any amount of `inputToken` currently held by `LifiExternalAction`, not just the caller's own `inputAmount`. If a prior caller's swap ended in a partial fill (LI.FI router refunds the unspent portion of `inputToken` back to `msg.sender`, i.e. back to `LifiExternalAction` itself since `LifiExternalAction` is the one calling the router), that unspent portion remains as an ERC20 balance on `LifiExternalAction` with no owner-tracking.
- A second, unrelated caller then submits their own `transact()` using the same `externalActionId`/`externalAddress` (LifiExternalAction), their own small deposit, but crafts (or obtains from LI.FI's own quoting API) `externalActionMetadata` whose encoded swap amount is larger than their own `inputAmount`, up to the full `inputToken` balance now sitting in the contract (their deposit + the stranded refund). The router happily executes this larger swap using the unlimited allowance and available balance.
- Back in `swap()`, `swappedAmount` reflects the *full* larger trade (their contribution + the stolen refund), and `amountToSendToHinkal = swappedAmount - totalFee` is transferred to `msg.sender` (Hinkal) and returned as a single UTXO in `utxoSet`.
- In `Hinkal.transact` (`contracts/Hinkal.sol:82-147`), the balance-diff checks (`balanceDif >= circomData.slippageValues[i]` and `balanceDif == amountChanges[i] + utxoAmount`) are self-referential: `utxoAmount` is derived directly from the very `utxoSet` the action just returned, so any inflated `swappedAmount` trivially satisfies both checks. Nothing in `Hinkal.sol`, `ExternalActionSwap.sol`, or the circuit (`inTotal + amountChanges[i] === outTotal` in `circuits/MainEVMCircuit.circom:168`) ties `swappedAmount`/`utxoAmount` back to the specific caller's own `inputAmount` that Hinkal escrowed for their call - the circuit only constrains the caller's *own* declared `amountChanges`, it has no visibility into what actually happened inside the shared external-action contract.

Root cause: `LifiExternalAction`/`ExternalActionSwap` treat the contract's own token balance as a fungible, un-owned pool rather than escrowing/tracking funds per call, while granting the router an unlimited, unrestricted allowance and letting the caller's own calldata dictate how much of that pool is spent.

### Impact Explanation
A subsequent unprivileged caller can receive a shielded UTXO backed by tokens they never deposited - direct theft of another depositor's in-flight/refunded funds that were temporarily held by the `LifiExternalAction` contract. This matches the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable any time a partial fill (or any other event that leaves residual `inputToken`/`outputToken` balance in the contract) occurs and a subsequent caller is quick enough to route through the same action before the balance is otherwise consumed.

### Likelihood Explanation
Preconditions: (1) some prior swap through `LifiExternalAction` must leave a residual token balance in the contract (a partial fill by the LI.FI router is a normal, expected occurrence, not an edge case, for aggregator-routed swaps with slippage/liquidity limits); (2) the attacker must submit their own `transact()` with a swap through the same `externalActionId` before the stranded balance is otherwise drained, and must craft `externalActionMetadata` that instructs the router to pull more than their own escrowed `inputAmount`. Both are achievable by any unprivileged EOA who can generate their own proof/UTXO and construct arbitrary calldata for the router (e.g., by requesting a larger quote from LI.FI's own API for a `fromAmount` they don't actually intend to deposit, relying on the pre-existing balance to cover the difference). No special role or timing beyond "act before the residue is swept" is required, and the attacker's cost is limited to their own small deposit and gas.

### Recommendation
Do not rely on raw pre/post balance diffs of the shared action contract to determine what was consumed/produced for a given call. Either (a) escrow and track balances per-call (e.g., transfer input tokens with an exact-amount `approve`/pull instead of `approveUnlimited`, and revert if the router consumes more than `inputAmount` of `inputToken`, checked via a balance-diff assertion on the input side too), or (b) sweep/return any leftover `inputToken` balance to the original depositor (or back into Hinkal as a UTXO for them) immediately after each swap so no residue can ever remain for a later caller to claim. Additionally, bound `approveUnlimited` allowances to the exact `inputAmount` per call rather than a standing unlimited approval.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` (or equivalent test harness wired the same way), and a mock LI.FI router with two entrypoints: `swapPartial(...)` that pulls only a fraction of the offered allowance/balance and leaves the rest, and `swapFull(...)` that pulls whatever `fromAmount` is encoded in its calldata (up to available balance/allowance), mimicking real aggregator behavior.
2. Caller A deposits inputToken X into a UTXO, then calls `Hinkal.transact` with `externalActionData` pointing at `LifiExternalAction`, `externalActionMetadata` encoding a call to `swapPartial` for `inputAmount = 100`. Have the mock router only pull `60` and leave `40` of X sitting on `LifiExternalAction`. Assert: `LifiExternalAction`'s X balance is `40` after the tx, and Caller A's resulting UTXO reflects only the swap of `60`.
3. Caller B (unrelated address, no relation to A) deposits a small amount of X (say `1`) and calls `Hinkal.transact` through the same `LifiExternalAction`, with `externalActionMetadata` encoding a call to `swapFull` requesting `fromAmount = 41` (their `1` plus A's stranded `40`).
4. Assert the equality both sides: LHS = `-deltaAmountChanges[0]` that Hinkal escrowed for B's call (`= 1`); RHS = actual `inputToken` consumed by `callRouter` for B's call (`= 41`, since `getERC20OrETHBalance(inputToken)` on `LifiExternalAction` drops by `41`). Show LHS != RHS.
5. Assert Caller B's resulting output UTXO amount (`utxoSet[0].amount` returned from `runAction`, matching `Hinkal`'s minted commitment) is proportional to `41` worth of swapped output, not `1`, i.e., strictly greater than what B's own `inputAmount` of `1` could have produced - demonstrating B walked away with value derived from A's stranded refund.     function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );
