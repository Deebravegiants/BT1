### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant shop-spoofing of processed webhooks - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw body against the `X-Shopify-Hmac-Sha256` header, but the `shop` identity handed to the host application's handler is read from the unauthenticated `X-Shopify-Shop-Domain` header, which is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is the value of the `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` header: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that signable string (the body) and compares it to the received signature — the `shop` header plays no role in the signature computation or check: [3](#0-2) 

`Registry.process` relies on this same validation, then immediately trusts `request.shop` (the raw header value) as the tenant identity passed into the app's handler via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Shopify signs all webhooks for an app with the single, per-app `client_secret` (the same `Context.api_secret_key` used across every shop that installs the app), not a per-shop key. Because the signature only covers the body, and the `shop` field is a separate, independently-controlled header, `shop` is an "identity field acted on but not covered by the HMAC": the equality the code implicitly assumes — `shop-header == shop-that-produced-this-signed-body` — is never checked or enforced anywhere in this library.

An unprivileged attacker who installs the target app on their own (attacker-controlled) shop can receive genuine, validly-signed webhooks for that shop. Because the raw body and HMAC are decoupled from the shop identity, the attacker can capture a legitimately signed `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with `X-Shopify-Shop-Domain` rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body against the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim's `shop` for data that actually originated from the attacker's own shop.

### Impact Explanation
Any host application that uses the `WebhookMetadata#shop` value returned by this library to select tenant scope (e.g., updating a shop record, crediting an account, writing order/customer data keyed by `shop`) can be made to attribute attacker-controlled payloads to an arbitrary victim shop, since the library provides no binding between the authenticated bytes and the claimed tenant. This is a cross-tenant data integrity/confusion issue reachable by any unprivileged user who can install the app on a shop they control — no access token, leaked secret, or privileged account is required.

### Likelihood Explanation
Installing an app on a free/dev shop is something any internet user can do, and capturing one's own webhook traffic (raw body + `X-Shopify-Hmac-Sha256` header) requires no special access. Replaying it with a modified `X-Shopify-Shop-Domain` header against the app's public webhook endpoint is trivial once the mismatch between "what is signed" and "what is trusted as identity" is understood.

### Recommendation
Bind the shop identity to the authenticated content: include the shop domain (and ideally topic/webhook id) in the signed material that `HmacValidator` verifies, or independently verify that the shop header matches an out-of-band-known/registered shop for the topic before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically bound to the HMAC and must not be trusted as an authenticated tenant identifier by host applications without additional verification (e.g., cross-checking against the session/shop that registered the webhook).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop the attacker fully controls) — no special privileges are required for this.
2. Shopify sends a legitimate webhook to the app's endpoint with a body such as `{"id":123}`, headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` and a valid `X-Shopify-Hmac-Sha256` computed with the app's `client_secret` over that body.
3. Attacker captures this `(raw_body, hmac_header)` pair.
4. Attacker replays a POST to the same webhook endpoint with the identical `raw_body`/`X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key` [6](#0-5) 
6. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and any host logic keyed on `shop` now acts on the victim's tenant with attacker-supplied data [7](#0-6)
