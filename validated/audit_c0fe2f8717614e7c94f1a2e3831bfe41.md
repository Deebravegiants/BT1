### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing but are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used to route and attribute the webhook are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body HMAC and then hands the header-derived `shop` value straight to the app's handler as the tenant identity, breaking the intended binding between "bytes verified" and "identity acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` verifies the signature against `verifiable_query.to_signable_string` (i.e., the body only): [3](#0-2) 

`Registry.process` performs this HMAC check and then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header value) as the tenant identity passed to the app's handler: [4](#0-3) 

The intended equality is: `shop attributed to the webhook == shop cryptographically bound by the HMAC`. In this implementation the actual equality is: `HMAC(body, secret) == HMAC(body, secret)` while `shop` is taken from an out-of-band header that participates in neither the signable string nor any secondary check. Because only the body is signed, any bytes (body, valid-hmac) pair obtained from a genuine Shopify webhook delivery (e.g., to an attacker-owned/attacker-installed shop) remains valid regardless of which `shop-domain` (or `topic`) header is attached when replayed to the same public webhook endpoint.

### Impact Explanation
An unprivileged attacker who can install the target app on their own store (as any Shopify merchant can) will receive genuine webhook deliveries with valid HMAC signatures for events happening in their own shop. By replaying that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, the attacker causes the app to process attacker-controlled webhook data attributed to the victim tenant. This is a cross-tenant identity confusion: the app's webhook handler will act on data as if it originated from the victim shop's install, even though it was generated by the attacker's own shop. Depending on the handler logic (e.g., app/uninstalled, shop/redact, orders/create), this can lead to unauthorized cross-tenant state changes, data injection, or triggering of privileged per-shop workflows under a false tenant identity — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop` (the gem's documented output) to select per-tenant behavior, since that is the intended and only way to consume webhook data from this gem. The attacker only needs the ability to install the target app once as any ordinary merchant (or to observe any legitimately delivered webhook body+HMAC pair) and to send an arbitrary HTTP POST to the app's public webhook URL with attacker-chosen headers — no credentials, tokens, or secrets are required.

### Recommendation
- Short term: Include `shop`, `topic`, and `webhook_id` header values in the signable string that the HMAC covers, or otherwise cryptographically bind them (e.g., verify the `shop` header against the shop the webhook subscription was registered for, using an authenticated lookup) before trusting them in `WebhookMetadata`.
- Long term: Add tests asserting that tampering with `shop-domain`/`topic` headers on an otherwise-valid signed webhook request is rejected, and document to consuming apps that these header values are not currently authenticated by this gem.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers an event (e.g., creates an order) that causes Shopify to deliver a genuine webhook to the app's public webhook endpoint, with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body using the app's `client_secret`.
2. Attacker captures this raw HTTP request (`raw_body` + `x-shopify-hmac-sha256` + other headers).
3. Attacker resends the identical request to the same public webhook endpoint, changing only `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) to a victim shop's domain, leaving `raw_body` and `x-shopify-hmac-sha256` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) signature: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.shop` set to the victim's domain, even though the event actually originated from the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
