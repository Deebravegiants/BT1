### Title
Missing L2 Sequencer Uptime Check in SimplexPaymaster Chainlink Oracle Pricing - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments (USDC/USDT/any Chainlink-fed token) against the native asset using two Chainlink `AggregatorV3Interface.latestRoundData()` calls in `_getOraclePrice`, and is deployed on Arbitrum, Optimism, and Base — all L2s with a centralized sequencer. The function only validates `answer > 0` and `updatedAt` staleness; it never checks a Chainlink L2 Sequencer Uptime feed, so if the sequencer goes down and later restarts, stale/incorrect price data can be treated as valid during the standard Chainlink "grace period," allowing gas payments to be mispriced.

### Finding Description
`_getOraclePrice` reads Chainlink round data and enforces only two conditions: a positive `answer`, and `block.timestamp - updatedAt <= maxOracleAge`: [1](#0-0) 

This is used for every gas-payment pricing computation in `_tokenPrice`, which both `getTokenPrice`/`estimateTokenCost` (off-chain estimation) and `_fetchDetails` (the actual on-chain pricing used during ERC-4337 validation) rely on: [2](#0-1) [3](#0-2) 

Unlike Ethereum L1, Arbitrum, Optimism, and Base rely on a single sequencer to order and submit transactions; when the sequencer is down, Chainlink price feeds on that L2 stop updating, and Chainlink recommends gating oracle consumers with a sequencer-uptime feed plus a grace period after restart, since prices immediately after a sequencer restart can be stale, out of sync with L1 market prices, or manipulable before the first fresh Chainlink round lands. The paymaster is confirmed to run on these sequencer-based L2s, since its price-feed addresses list Arbitrum, Optimism, and Base (mainnet and testnet) explicitly: [4](#0-3) 

No check of `AggregatorV3Interface(sequencerUptimeFeed).latestRoundData()` (or equivalent grace-period gating) exists anywhere in `SimplexPaymaster.sol`, `_registerToken`, `_updateParams`, or `initialize`, meaning `_getOraclePrice`'s staleness bound is the only protection, and it is insufficient during/after a sequencer outage.

### Impact Explanation
This pricing function directly determines how much ERC-20 stablecoin is pulled from a UserOperation sender to sponsor gas (`_fetchDetails` → `_prefund`/`PaymasterERC20._postOp`), and also determines the minimum acceptable output when the treasury recycles fees through `swapAndDeposit`: [5](#0-4) 
If the sequencer restarts and a Chainlink feed reports a price from before the outage (still "fresh" per `maxOracleAge`) that has diverged from the true native/token market price, an attacker can submit UserOperations (or otherwise time the treasury's swap) to be charged at a stale exchange rate, extracting value from the paymaster's stablecoin balance or from the swap execution, resulting in economic loss for the paymaster/treasury.

### Likelihood Explanation
Exploitation only requires observing an L2 sequencer outage/restart on Arbitrum, Optimism, or Base and submitting a UserOperation through the paymaster during the window before the feed catches up — this is a fully permissionless, low-cost action requiring no privileged role, matching the same conditions as the referenced report's Arbitrum sequencer scenario.

### Recommendation
Add a Chainlink L2 Sequencer Uptime Feed check (per-chain configurable, similar to `nativeOracle`/token oracles) in `_getOraclePrice`, reverting or requiring a grace period (e.g., Chainlink's recommended pattern of checking `startedAt` of the sequencer feed plus a configurable `GRACE_PERIOD_TIME`) before trusting price data on any chain where a sequencer feed exists.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum/Optimism/Base per `DeploySimplexPaymaster.s.sol` with `nativeOracle`/token oracle set to the chain's Chainlink feed.
2. Simulate a sequencer outage/restart on the target L2 fork (or observe a live outage window).
3. During the grace period after restart, submit a `PackedUserOperation` with mode 0x00/0x02 paymasterData; `_fetchDetails` computes `tokenPrice` via `_tokenPrice`/`_getOraclePrice` using the stale-but-not-yet-expired Chainlink round.
4. Because the answer passes both the `answer > 0` and `maxOracleAge` checks despite reflecting pre-outage market conditions, the sender is charged (or the treasury swap executes) at an incorrect exchange rate, demonstrating value extraction analogous to `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts` not covering the sequencer-down scenario: [6](#0-5)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
