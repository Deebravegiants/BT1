### Title
`begin_auth` builds OAuth redirect from unvalidated `shop` param, enabling forced OAuth completion off Shopify's domain - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` constructs the OAuth authorization URL via `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` directly from the caller-supplied `shop` string, without ever invoking `Utils::ShopValidator.sanitize!`. Since the host app documentation instructs passing the raw `shop` query param to `begin_auth`, an attacker controlling that param can force the OAuth flow to redirect to an attacker-controlled host, carrying `client_id`, `scope`, `redirect_uri`, and `state`.

### Finding Description
The claimed binding is: `shop_used_as_redirect_host == shop_validated_by_ShopValidator`. Tracing the code shows this is false — the validator is never called on this path.

In `lib/shopify_api/auth/oauth.rb`, `begin_auth(shop:, redirect_path:, ...)` computes:
```ruby
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
``` [1](#0-0) 

and the private helper:
```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [2](#0-1) 

There is no call to `ShopifyAPI::Utils::ShopValidator.sanitize!` or `sanitize_shop_domain` anywhere in `begin_auth` or `auth_base_uri`. The only guards executed are `Context.setup?` and `Context.private?`, neither of which validate the `shop` string's domain. [3](#0-2) 

`ShopValidator.sanitize!` exists in the gem specifically to restrict `shop` to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-configured `myshopify_domain`, raising `Errors::InvalidShopError` otherwise: [4](#0-3) 

but it is simply not invoked by `begin_auth`. The gem's documented usage flow (`docs/usage/oauth.md`) has the host app pass the `shop` query param straight from `/login?shop=...` into `begin_auth`. An attacker requests `GET /login?shop=evil-host.example.com`, and `auth_base_uri("evil-host.example.com")` returns `"https://evil-host.example.com/admin"`, so the resulting `auth_route` points at the attacker's host while still embedding the real `client_id`, `scope`, `redirect_uri`, and freshly generated `state`. `validate_auth_callback`'s `HmacValidator` and state check operate on the *callback*, not on this outbound redirect, so they cannot prevent the browser from being sent off-domain during `begin_auth`.

### Impact Explanation
The victim's browser is redirected to an attacker-controlled host that receives the app's real `client_id`, requested `scope`, `redirect_uri`, and the session `state`. The attacker's server can use this to phish the merchant for OAuth completion, harvest the `state`/`redirect_uri` for further attacks, or otherwise force OAuth completion outside Shopify's domain. This matches the High severity category: "SSRF driving an authenticated request to an unintended host, session fixation or forced OAuth completion." It is repeatable against arbitrary victims/host-app users, since any value of `shop` is accepted unchanged for every invocation of `begin_auth`.

### Likelihood Explanation
No credentials or special access are required — an unprivileged attacker only needs to control the `shop` query parameter on the host app's login route, which is the exact documented entry point for OAuth in `docs/usage/oauth.md`. The attack costs nothing beyond a single crafted URL and works on the first request; there is no dependency on prior installs, webhooks, or secrets.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` at the top of `begin_auth` (and reuse the sanitized/normalized host in `auth_base_uri`) before constructing `auth_route`, raising `Errors::InvalidShopError` for any `shop` value that isn't a trusted Shopify domain.

### Proof of Concept
Add to `test/auth/oauth_test.rb` (no WebMock needed — pure string construction):
```ruby
def test_begin_auth_does_not_validate_shop_and_redirects_off_shopify_domain
  ShopifyAPI::Context.setup(
    api_key: "key", api_secret_key: "secret", api_version: "unstable",
    scope: "read_products", host_name: "app-host.example", is_private: false,
    is_embedded: false, session_storage: ShopifyAPI::Auth::FileSessionStorage.new
  )

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil-host.example.com", redirect_path: "/callback")

  auth_uri = URI.parse(result[:auth_route])
  assert_equal("evil-host.example.com", auth_uri.host,
    "shop should have been rejected by ShopValidator.sanitize! but was used unchanged as redirect host")
end
```
Both sides of the binding: expected `shop_validated_by_ShopValidator` (should raise `Errors::InvalidShopError` for `evil-host.example.com`) vs. actual `shop_used_as_redirect_host` (`"evil-host.example.com"`, taken verbatim) — they diverge, confirming the vulnerability.
