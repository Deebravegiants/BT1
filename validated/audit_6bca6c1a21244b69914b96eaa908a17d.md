## Title
Webhook Shop-Domain Spoofing via HMAC Scope Gap Enables Cross-Tenant Webhook Injection — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The webhook HMAC validation in this gem signs and verifies only the raw request body, while the `shop` identity that the webhook handler trusts and acts on is taken from an unauthenticated HTTP header. Any party that can obtain one validly-signed webhook (e.g., by installing the app on their own store, which any unprivileged internet user can do) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header for any other shop, and the gem will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read directly from a caller-supplied header with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` accepts the request once `HmacValidator.validate` passes, then forwards the **unverified** `request.shop` value straight into the handler's `WebhookMetadata`, which apps use to key their tenant-scoped operations (e.g., updating the correct shop's order/customer record): [4](#0-3) 

The identity binding that should hold is:
`shop_header == shop_bound_by_hmac`

but the actual binding enforced is only:
`hmac(shared_secret, raw_body) == received_hmac`

with `shop` entirely outside that signed scope. Because the HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that installs the same app, any unprivileged user who installs the app on their own store receives genuine webhooks (valid body + valid HMAC) for events they fully control (e.g., `orders/create` with attacker-chosen field values). They can then POST that same raw body and HMAC to the app's webhook endpoint while setting `shopify-shop-domain` to a victim shop already using the app. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` dispatches the payload labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an attacker with only unprivileged access to their own store install can inject attacker-controlled webhook payloads that the host application will process as if they originated from a different (victim) merchant. Any downstream logic that uses `WebhookMetadata#shop` to select the tenant record to write/notify/act on (a standard pattern for webhook handlers) can be corrupted with cross-tenant data — satisfying the "cross-tenant access" Critical impact category, since the confidentiality/integrity boundary between separate merchants' data is defeated using only the identity binding gap in this gem's own webhook verification code.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-owned development/trial store — a normal, unprivileged action any internet user can take, and (2) sending a forged HTTP request to the app's public webhook endpoint with a substituted shop header, which requires no secrets and no interaction with Shopify's servers. This is a low-effort, reliably reproducible attack path against the gem's own `Utils::HmacValidator`/`Webhooks::Registry` logic.

### Recommendation
Bind the shop identity into the signed material, or otherwise independently authenticate it, before trusting `request.shop` in `Registry.process`:
- Include the `shop` (and `topic`) in `Webhooks::Request#to_signable_string` used for HMAC verification, or
- Require the app to cross-check `request.shop` against a shop known to have an active webhook subscription/session (e.g., verify the shop has a stored access token) before dispatching, rejecting webhooks for shops with no matching prior registration/session, and
- Document/enforce that `WebhookMetadata#shop` must not be trusted for tenant selection unless corroborated by a mechanism outside the replayable body HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers `orders/create`, receiving a genuine webhook request:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <validHmacOfBody>`, `x-shopify-shop-domain: attacker.myshopify.com`
   - Body: `{"id": 1, "note": "attacker-controlled content"}`
2. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over the (unchanged) body and it matches — validation passes: [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {...attacker content...}, ...)` and invokes the app's handler, which processes attacker-controlled data under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
