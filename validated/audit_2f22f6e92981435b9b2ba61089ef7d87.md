### Title
Optimistic local update of `Gateways::<T>` params before cross-chain delivery is confirmed causes governance/gateway param divergence - (File: `modules/pallets/intents-coprocessor/src/lib.rs`)

### Summary
`pallet-ismp-intents-coprocessor::update_params` mirrors the exact `minRentalDayDivisor` bug class: a governance-controlled parameter is held in two places — the pallet's `Gateways::<T>` storage (the "treasury"/source-of-truth) and each deployed `IntentGatewayV2` instance's `_params` storage on the destination chain (the "market"). The pallet writes its own copy of the new params to storage immediately after dispatching the cross-chain update, without waiting for or reacting to delivery confirmation, so the two copies can diverge whenever the dispatched message fails, times out, or is otherwise not applied on the destination gateway.

### Finding Description
`update_params` in `modules/pallets/intents-coprocessor/src/lib.rs` reads the current `gateway_info` from `Gateways::<T>`, merges the update, dispatches a cross-chain `UpdateParams` request to the gateway, and then immediately writes the merged params back into `Gateways::<T>` and emits `GatewayParamsUpdated`: [1](#0-0) 

The on-chain effect only happens once the ISMP `UpdateParams` request is delivered to the specific `IntentGatewayV2` instance's `onAccept`, which then updates `_params` and `_destinationProtocolFees` via `_updateParams`: [2](#0-1) 

Because `Gateways::<T>::insert` happens synchronously with dispatch and is not conditioned on, or later reconciled with, actual delivery, any request that never lands on the destination gateway (timeout, relayer failure, destination-side revert, gateway paused, wrong recipient, etc.) leaves the pallet's `Gateways` record permanently ahead of the deployed gateway's real `_params`/`_destinationProtocolFees`. This is structurally identical to `minRentalDayDivisor`: a single logical parameter is copied into a remote instance at one point in time, the "hub" record is updated but the instance is not guaranteed to follow, and there is no mechanism forcing them back into agreement.

### Impact Explanation
Governance and any off-chain tooling that reads `Gateways::<T>` (fee quoting, solver-selection assumptions, protocol-fee accounting, destination-fee overrides) will operate on the assumption that the deployed `IntentGatewayV2` reflects the new `protocolFeeBps`, `surplusShareBps`, `solverSelection`, `priceOracle`, or per-destination fee overrides, while the live gateway contract on the destination chain still enforces the old values. This can misprice orders (solvers/users computing fees or acceptable fills based on the pallet's optimistic state while the contract charges/enforces the stale one), silently disable an intended `solverSelection` protection (unauthorized fills reaching a gateway that governance believed already required session-key authorization), or cause protocol-fee bookkeeping mismatches that lead to loss of expected protocol revenue or user overpayment/underpayment relative to what governance intended. Because the pallet has no re-sync or retry-until-confirmed logic, this drift is permanent until a subsequent successful `update_params` call happens to reconcile it.

### Likelihood Explanation
Any relayer/message-delivery failure, destination-side pause, revert in `_validateParams`, or simple timeout on the `UpdateParams` dispatch is sufficient to trigger the divergence — no privileged or malicious actor is required. Cross-chain message delivery failures are a normal, expected occurrence in this system (the codebase's own consensus/relayer paths handle timeouts and reverts as first-class cases), making this a realistic and not merely theoretical scenario. Since the local `Gateways` update happens unconditionally regardless of dispatch outcome, the window for divergence is opened on every single call to `update_params`.

### Recommendation
Do not treat the local `Gateways::<T>` write as authoritative until the corresponding `UpdateParams` request is confirmed delivered (or is provably committed) on the destination gateway. Options: (1) update `Gateways::<T>` only upon a confirmed response/ack from the destination gateway rather than optimistically at dispatch time, (2) track a `pending` vs `applied` params state and expose both so integrators do not treat `Gateways::<T>` as ground truth for the live contract, or (3) add a reconciliation/query path that lets governance detect and resend/re-drive a lagging gateway's params, analogous to how the report's remediation for `minRentalDayDivisor` was to explicitly document/accept the risk — here, the divergence should at minimum be observable and correctable rather than silent and permanent.

### Proof of Concept
1. Governance calls `update_params` for `state_machine = X`, changing `protocolFeeBps` from 100 to 50 and adding a destination fee override. [3](#0-2) 
2. `Self::dispatch(state_machine, gateway_info.gateway, body)?` succeeds at the pallet level (the local dispatch call does not fail), but the underlying ISMP message to the `IntentGatewayV2` on chain `X` subsequently times out or the relayer never delivers it (a normal failure mode elsewhere handled by the timeout/`onGetTimeout`/`onPostRequestTimeout` paths in `EvmHost.sol`). [4](#0-3) 
3. Regardless of that outcome, the pallet immediately writes the new params into `Gateways::<T>` and emits `GatewayParamsUpdated`, so all downstream consumers of `Gateways::<T>` (SDK fee quoting, other pallets, UIs) believe `protocolFeeBps = 50` and the new destination fee are live. [5](#0-4) 
4. The actual `IntentGatewayV2._params.protocolFeeBps` on chain `X` remains `100` and `_destinationProtocolFees` remains unset, since `_updateParams` never ran. [2](#0-1) 
5. Orders placed against gateway `X` continue to be charged the old 100bps fee (and any solver-selection/price-oracle assumptions remain the old ones) while every off-chain and on-pallet consumer of `Gateways::<T>` computes against the new, never-applied values — mirroring exactly the `minRentalDayDivisor` divergence between the treasury (source of truth) and an individual market (deployed instance) in the referenced report.

		pub fn update_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			params_update: types::ParamsUpdate,
		) -> DispatchResult {
			T::GovernanceOrigin::ensure_origin(origin)?;

			// Get gateway info
			let mut gateway_info =
				Gateways::<T>::get(state_machine).ok_or(Error::<T>::GatewayNotFound)?;

			// Store old params for event
			let old_params = gateway_info.params.clone();

			// Merge update with current params
			let updated_params = gateway_info.params.update(params_update.clone());

			// Create complete params update for cross-chain dispatch
			let complete_update = types::CompleteParamsUpdate {
				params: updated_params.clone(),
				destination_fees: params_update.destination_fees.unwrap_or_default(),
			};

			// Prepare cross-chain request
			let request = RequestKind::UpdateParams(complete_update);
			let body = request.encode_body();

			// Dispatch cross-chain message
			Self::dispatch(state_machine, gateway_info.gateway, body)?;

			// Update local storage
			gateway_info.params = updated_params.clone();
			Gateways::<T>::insert(state_machine, gateway_info);

			Self::deposit_event(Event::GatewayParamsUpdated {
				state_machine,
				old_params,
				new_params: updated_params,
			});

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
