## Finding

### Title
Missing zero-address validation on relayer fee withdrawal `beneficiary` leads to permanent loss of withdrawn fees - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The `pallet-ismp-relayer` withdrawal flow lets any relayer redirect their accumulated cross-chain fees to an arbitrary `beneficiary` address with no validation that the address is non-zero/well-formed, before dispatching an irreversible cross-chain payout instruction.

### Finding Description
`Pallet::withdraw` (the handler behind the unsigned `withdraw_fees` extrinsic) accepts a caller-supplied, optional `beneficiary` byte vector inside `WithdrawalInputData`: [1](#0-0) 

The pallet only verifies the *signature* over `(nonce, dest_chain, beneficiary)` to authenticate that the relayer authorized this specific payload — it never checks that the `beneficiary` bytes represent a valid, non-zero destination: [2](#0-1) 

For substrate destinations, `beneficiary_address` is coerced directly into an `AccountId32` — an all-zero 32-byte value passes `try_from` cleanly and produces a valid (but unspendable/burn) account. For EVM destinations, the raw bytes are packed into `WithdrawalParams.beneficiary_address` and ABI-encoded for the destination `HostManager`: [3](#0-2) 

The only check performed prior to dispatch is a length check (`abi_encode` requires exactly 20 bytes for EVM); there is no `address(0)` guard. The same missing-validation pattern is mirrored in the analogous host-executive protocol-fee withdrawal path, which also just ABI-encodes and dispatches without checking the beneficiary: [4](#0-3) 

On the EVM side, once delivered, `HostManager.onAccept` forwards the decoded `WithdrawParams` straight to `IHostManager(_params.host).withdraw(withdrawParams)`: [5](#0-4) 

The sibling `BandwidthManager` withdrawal handler in the same codebase demonstrates the exact settlement pattern used for beneficiary payouts — a native-token branch that sends value via a raw low-level call with no zero-address guard: [6](#0-5) 

A raw `.call{value: amount}("")` to `address(0)` succeeds and permanently burns the funds (unlike ERC-20 `safeTransfer`, which typically reverts on a zero recipient). Since `withdraw_fees` zeroes the relayer's `Fees` entry and increments the nonce *before* the cross-chain request is delivered (irreversibly committing the withdrawal), an accidental or buggy `beneficiary` of all zero bytes results in permanently and unrecoverably lost fees once the message lands on an EVM destination configured for native-token payout.

### Impact Explanation
Funds (accumulated relayer fees, potentially large sums across many delivered messages) are burned irrecoverably if a zero/invalid beneficiary is supplied — whether via a malformed client, automation bug in the tesseract relayer (`beneficiary` field is attacker/operator supplied per `execute_withdrawal` in `tesseract/messaging/substrate/src/calls.rs`), or a corrupted signature payload. This matches the reported bug class (missing address validation on a fee-recipient field leading to fees being misdirected or lost), reachable from a single unsigned extrinsic call — no privileged role required.

### Likelihood Explanation
`withdraw_fees` is an unsigned, permissionless extrinsic that any relayer (or any actor holding a relayer's signing key, or a buggy relaying client) can submit; the beneficiary field is fully attacker/operator-controlled and unchecked. Given automated relayer software builds this payload programmatically (see `tesseract/messaging/substrate/src/calls.rs`), a configuration or serialization bug producing an all-zero beneficiary is a realistic occurrence, and there is no on-chain safety net to catch it before the irreversible fee-zeroing and cross-chain dispatch occur.

### Recommendation
Validate `beneficiary` before zeroing `Fees` and dispatching: reject all-zero 20-byte EVM addresses and all-zero 32-byte substrate account IDs (and any other well-known burn addresses) in `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`) and in the analogous `pallet-ismp-host-executive::withdraw` path (`modules/pallets/host-executive/src/lib.rs`). Additionally, consider having `EvmHost`/`HostManager`'s native-token payout branch explicitly revert on `beneficiary == address(0)` rather than relying on the low-level call succeeding silently.

### Proof of Concept
1. A relayer (or a buggy tesseract client) calls the unsigned `withdraw_fees` extrinsic with `dest_chain = StateMachine::Evm(x)` and `beneficiary = Some(vec![0u8; 20])`.
2. `Pallet::withdraw` verifies only the signature over `(nonce, dest_chain, beneficiary)` — this succeeds since the relayer legitimately signed the (buggy) payload.
3. `Fees::<T>` for the relayer is read and then implicitly zeroed via the dispatch flow; `WithdrawalParams { beneficiary_address: [0;20], amount, token: fee_token }` is ABI-encoded and dispatched as a POST request to the destination chain's `HostManager`.
4. On delivery, `HostManager.onAccept` calls `IHostManager(host).withdraw(params)`, which for a native-token withdrawal performs `address(0).call{value: amount}("")` — this succeeds, permanently burning the relayer's entire accumulated fee balance with no recovery path.
