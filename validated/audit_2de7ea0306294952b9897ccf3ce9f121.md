Confirmed: `approveUnlimited` grants `type(uint256).max` allowance to `router` [1](#0-0) , and `Hinkal.transact`'s balance-equality check only compares Hinkal's own balance delta against `amountChanges`/`utxoAmount`, with no visibility into how much of the action contract's own pre-existing token balance was actually spent [2](#0-1) .

### Title
Uncapped input consumption in `ExternalActionSwap.swap` lets any caller sweep residual/stranded token balances via the LI.FI router call - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` computes `inputAmount` from `-deltaAmounts[0]` (the amount Hinkal transferred in for this specific transaction) but never verifies that the router call in `callRouter` actually consumed exactly that amount of `inputToken` from the contract's balance. Because `approveUnlimited` grants the router an unlimited allowance and the router calldata (`externalActionMetadata`) is fully attacker-supplied, any balance of `inputToken` already sitting in the `ExternalActionSwap`/`LifiExternalAction` contract — whether from a prior partial-fill refund, rounding dust, or tokens stranded because `swap()` only ever handles `erc20TokenAddresses[0]` and `[1]` and silently ignores any additional negative-delta tokens sent to the action — can be pulled into the swap and monetized as extra output token credited to the caller's own UTXO.

### Finding Description
The invariant that should hold is:

`amount of inputToken actually consumed from the ExternalActionSwap contract during callRouter == -deltaAmounts[0]` (i.e., exactly what Hinkal sent it this transaction, no more).

In `swap()`, `inputAmount` is derived purely from `deltaAmounts[0]` [3](#0-2) , and it is passed to `callRouter`, but `callRouter` in `LifiExternalAction` only measures the resulting change in **output**-token balance (`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`) and never checks that the **input**-token balance decreased by exactly `inputAmount` [4](#0-3) . Since `approveUnlimited(inputToken, router)` grants `type(uint256).max` allowance [1](#0-0) , and `externalActionMetadata` is attacker-controlled calldata forwarded verbatim to `router.call`, the router will pull whatever amount the calldata specifies (up to the full contract balance), not just `inputAmount`.

Root cause / how residual balance accumulates in the contract:
1. `swap()` only reads `circomData.erc20TokenAddresses[0]` and `[1]` [5](#0-4) , but `Hinkal._externalTransact` forwards **every** token in `erc20TokenAddresses` with a negative `deltaAmountChanges[i]` to the action address via `transferERC20TokenOrETH` [6](#0-5) . An attacker (who fully controls `erc20TokenAddresses` ordering and `amountChanges`) can craft a valid proof/transaction with a third token index whose negative delta is sent to the swap action but is never referenced, refunded, or reported back via `utxoSet` — it is permanently stranded as a plain balance in the action contract.
2. Real LI.FI aggregator calls can also legitimately refund unspent input token directly to the caller (this contract) on partial fills/slippage protection, again leaving residual `inputToken` balance in the contract that `swap()` never sweeps or accounts for.

In a subsequent, unrelated transaction that also uses `inputToken` as its swap input, `Hinkal`'s balance equation is self-consistent from Hinkal's point of view: `balanceDif == amountChanges[i] + utxoAmount` is satisfied because the attacker crafts their own proof/`amountChanges` to match whatever actual `swappedAmount` the router produces [7](#0-6) . Hinkal has no way to know that part of the swapped input came from a residual balance already resident in the external action contract rather than from `-deltaAmountChanges` sent this transaction, since it only checks its own balance delta, not the action contract's internal input-token consumption. The attacker crafts `externalActionMetadata` so the router pulls `inputAmount + residual`, producing extra `outputToken`, all of which flows to `msg.sender` (Hinkal) and gets credited to the attacker's own freshly generated output UTXO.

### Impact Explanation
An unprivileged caller can capture token value that does not belong to their own declared `-deltaAmountChanges`, effectively stealing value stranded in the shared `ExternalActionSwap`/`LifiExternalAction` contract (either self-stranded value belonging to a different party, or dust/partial-fill refunds from other users' prior swaps) and converting it into their own shielded output UTXO. This is repeatable every time residual balance accumulates in the contract, and matches "Critical: direct theft of shielded or in-flight user funds."

### Likelihood Explanation
The attacker needs: (a) the ability to craft `erc20TokenAddresses`/`amountChanges` for a multi-token transaction (or simply to observe/wait for a legitimate partial-fill refund to land in the contract), and (b) the ability to craft `externalActionMetadata` targeting the fixed `router` such that it pulls more than `inputAmount` (feasible since the router's calldata directly encodes the amount to be pulled and the contract grants it unlimited allowance). Both are explicitly listed as attacker-controlled inputs. No privileged role is required, and the attack is repeatable whenever residual balance exists.

### Recommendation
In `ExternalActionSwap.swap`/`LifiExternalAction.callRouter`, measure and enforce the **input**-token balance delta the same way the output is measured: snapshot `inputToken` balance before the router call and require `balanceBefore - balanceAfter == inputAmount` (revert otherwise), and grant only a bounded approval (`approveToken(inputToken, router, inputAmount)`) instead of `approveUnlimited`, resetting/revoking any leftover allowance after the call. Additionally, either explicitly reject/handle `erc20TokenAddresses` entries beyond index 0/1 in `swap()`, or generalize the function to account for and return every token forwarded to it so nothing can be silently stranded.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `LifiExternalAction` with a mock router that: on a specific calldata selector, performs `transferFrom(action, router, amount)` where `amount` is decoded from calldata (simulating LI.FI behavior), then returns a fixed output token amount to the action contract.
2. Transaction A: seed the residual — either (i) directly transfer `residual` amount of `inputToken` to the `LifiExternalAction` contract address (simulating a partial-fill refund/stranded token), or (ii) run a legitimate `Hinkal.transact` with 3 tokens where token index 2 has negative delta routed to the action and never consumed by `swap()`.
3. Transaction B (attacker, unrelated proof/UTXOs): call `Hinkal.transact` with `erc20TokenAddresses = [inputToken, outputToken]`, `amountChanges[0] = -inputAmount` (small, legitimately funded), craft `externalActionMetadata` so the mock router pulls `inputAmount + residual` from the action contract.
4. Assert: `outputToken` UTXO amount credited to attacker > what `inputAmount` alone would produce; assert the action contract's `inputToken` balance dropped by `inputAmount + residual` while Hinkal only accounted for `inputAmount` via `deltaAmountChanges`; assert attacker's shielded balance increased by value equal to `residual`'s converted worth, i.e., `swappedAmount(inputAmount) != swappedAmount(inputAmount + residual)` and the latter, not the former, is what gets credited despite Hinkal only being told about `inputAmount`.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
