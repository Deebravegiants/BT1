### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, while the HMAC signature validated by `Utils::HmacValidator` covers only the raw request body. `Registry.process` trusts `request.shop` as the tenant identifier when dispatching to the handler, without that value being bound to the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, i.e., the HMAC (`hmac-sha256` header) is computed/verified over the JSON body alone: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of `to_signable_string` and therefore is never covered by the HMAC check: [2](#0-1) 

`Registry.process` validates the HMAC against the body only, then unconditionally uses `request.shop` (from the header) as the tenant identity passed to the app's webhook handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` field, confirming the header value used for tenant binding is outside the signed data: [4](#0-3) 

This breaks the intended identity binding: `shop header claimed == shop actually processed`, where the equality should be `shop covered by HMAC == shop used by handler`, but instead it is `shop header (unauthenticated) == shop used by handler`.

### Impact Explanation
Any party capable of observing a legitimately signed webhook body/HMAC pair for shop A (e.g., via logs, a compromised proxy, or a webhook consumer with wide read access) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for shop B. The HMAC check still passes (it only covers the body), and `Registry.process` will hand the payload to the handler tagged as belonging to shop B via `WebhookMetadata#shop`. If the host application uses this `shop` value to select which tenant's session/database record to act on (a very common pattern, e.g. `customers/redact`, `shop/redact`, order/customer webhooks), this results in cross-tenant data being attributed to, or actions being taken against, the wrong shop. This satisfies the "cross-tenant access" Critical impact category, contingent on the header actually being attacker-controllable up to the app's own endpoint (see Likelihood).

### Likelihood Explanation
Exploitability depends on whether an attacker can control or spoof the `shop-domain` header value reaching this code, since genuine Shopify-to-app delivery is normally over HTTPS directly to the registered callback URL. This is more likely to be exploitable when: the app sits behind a reverse proxy/load balancer that forwards a `X-Shopify-Shop-Domain`-style header without stripping attacker-supplied duplicates, or when webhook payloads are relayed through an intermediate queue (pub/sub, event bridge) where header/attribute separation from the signed body is easier to tamper with before reaching `Webhooks::Request.new`. Within the scope of this gem alone, the root cause -- HMAC coverage excluding the tenant-identifying field -- is a concrete, provable code defect, but full exploitation requires a header-spoofing vector at the transport layer, which is outside this gem's control.

### Recommendation
Bind the shop identity to the signed payload instead of (or in addition to) the header:
- Cross-check `request.shop` against a `shop`/`shop_domain` field embedded in the parsed webhook body (many webhook payloads include shop-identifying fields), rejecting on mismatch, or
- Extend `to_signable_string` / the HMAC-validated data set to include the `shop-domain`, `topic`, and `webhook-id` headers so tampering with them invalidates the signature, mirroring how Shopify's own webhook verification recommends binding headers that drive authorization decisions.

### Proof of Concept
1. Capture a legitimately delivered webhook for `shop-a.myshopify.com`: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Replay the request to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B` only) and matches `H` successfully. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the signed body `B` originated from and describes `shop-a`, so any handler logic keyed on `data.shop` operates on the wrong tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
