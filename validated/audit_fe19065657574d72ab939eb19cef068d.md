Based on my investigation, I've found a genuine timing-discrepancy analog in the orb-core signup authorization flow that mirrors the reported bug class.

### Title
Stale operator/user QR-code validation is trusted through the entire biometric capture and signup submission, creating a validity-window bypass - ([File: src/plans/mod.rs])

### Summary
Similar to the reported protocol issue where health-factor evaluation and slashing use different time bases, orb-core's signup flow validates the operator and user QR codes against the backend once (`verify_operator_qr_code` / `verify_user_qr_code`), then relies on that stale validation result throughout the entire biometric capture and package upload, without ever re-checking validity at the moment the actual signup is submitted to the backend.

### Finding Description
`scan_remaining_qr_codes` only re-triggers a fresh operator QR scan when the *client-side* `Instant`-based expiry `operator_data.timestamp.elapsed() < operator_qr_expiration_time` has lapsed [1](#0-0) . Once resolved, `do_signup` proceeds to use those already-validated `operator_data` / `qr_codes.user_data` values across a long sequence of operations: an `orb_relay_announce_orb_id` round trip, a fixed 3 second sleep, the full `biometric_capture` (which can take up to `BIOMETRIC_CAPTURE_TIMEOUT` or `self_serve_biometric_capture_timeout`), the biometric pipeline, fraud detection, and PCP package building/upload [2](#0-1) .

At no point between the original `backend::operator_status::request` / `backend::user_status::request` calls [3](#0-2) [4](#0-3)  and the final `signup_post::request` submission [5](#0-4)  is the operator/user validity re-confirmed against current backend state. The `operator_qr_expiration_time` check is a purely local `Instant` clock decision that governs whether to *re-scan*, not whether the already-fetched validation result is still authoritative when the enrollment is finally committed with `enroll_user::Plan::run` [6](#0-5) .

This is structurally the same class of bug as the reported issue: one subsystem's authorization decision (`coverage`/health, here QR validity) is computed at an early timestamp, while the subsystem that actually commits/enforces the consequence (`slash`, here `signup_post::request`) executes later using data bound to that earlier, now-possibly-stale, timestamp — with no re-synchronization between the two time bases.

### Impact Explanation
If the backend revokes/invalidates an operator or user session (e.g., distributor blocked, user banned, session state changed) during the multi-second-to-multi-minute window between validation and the actual signup POST, orb-core will still submit and attempt to complete the enrollment using the stale, already-invalidated identity binding, because the local code path never re-checks `operator_status`/`user_status` before finalizing. This can result in unauthorized or misattributed signups going through despite the backend having withdrawn authorization for that operator/user pairing during the intervening window.

### Likelihood Explanation
The window is deterministic and always present on every signup — the 3-second sleep plus the full biometric capture duration (potentially tens of seconds) is guaranteed elapsed time between validation and submission on every single run. No special conditions or race manipulation is needed to open this window; it simply requires the backend-side state to change during that interval, which is a normal operational scenario (e.g. an operator being deactivated mid-session).

### Recommendation
- **Short term:** Re-validate operator and user QR code status against the backend immediately before calling `signup_post::request` in `do_signup`/`enroll_user::Plan::run`, rather than relying solely on the earlier `verify_operator_qr_code`/`verify_user_qr_code` results.
- **Long term:** Bind the validity check's freshness explicitly to the actual submission time (not just to whether a QR re-scan is required), e.g. by having the backend return a short-lived signup authorization token tied to the validation response that is checked again at submission time, similar to enforcing consistent time bases for both authorization and consequence.

### Proof of Concept
1. Start a signup: operator and user QR codes are validated successfully via `verify_operator_qr_code`/`verify_user_qr_code`.
2. Before `signup_post::request` fires (i.e., during the 3s pre-capture sleep or the biometric capture phase), have the backend invalidate the operator's or user's session (this is entirely a backend-side state change, not something orb-core is aware of).
3. Observe that `do_signup` continues unaffected — it never re-queries `operator_status`/`user_status` — and eventually calls `signup_post::request` with the stale `operator_qr_code`/`user_qr_code`, completing an enrollment that should have been rejected. [2](#0-1)
