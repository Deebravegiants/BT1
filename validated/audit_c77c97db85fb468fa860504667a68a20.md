This confirms the vulnerability. The `shop` value that the gem hands to app handlers is read straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header and never enters the HMAC computation, while `Registry.process` only validates the signature over the raw body.

### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates covers exclusively the JSON body — not the `shop-domain` header. The `shop` accessor used to route/attribute the webhook to a tenant is read directly and unauthenticated from the header. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_the_tenant`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only the raw body. `Request#shop` is derived purely from request headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the body) against the computed signature, and then immediately forwards `request.shop` to the app's handler without any additional check that this shop matches the body/signature: [3](#0-2) 

Because the signature check and the `shop` value are decoupled, any request whose body+HMAC pair is valid for the app's secret (e.g., a genuine webhook the attacker legitimately received for their *own* shop, since installing the app is unprivileged) can be replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a victim shop. `HmacValidator.validate` still succeeds because it only recomputes the signature over the body: [4](#0-3) 
`Registry.process` then calls `handler.handle` with `WebhookMetadata` carrying the forged `shop`, so the host application processes attacker-supplied data attributed to a shop it doesn't come from: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who has installed the app on their own store (a legitimate, unprivileged action) can obtain genuine `(body, hmac)` pairs and replay them against the webhook endpoint while spoofing the shop-domain header to any victim shop. Any app logic keyed off `data.shop` (data attribution, per-shop billing/state updates, mandatory `shop/redact`/`customers/redact` compliance flows, session/data deletion, etc.) can be triggered under a false tenant identity, since the gem provides no guarantee that `shop` is the same tenant that produced the signed body. This matches the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) installer of the target app — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. Capturing one's own webhook traffic and replaying it with a modified header is straightforward for any developer with basic HTTP tooling, making this readily reachable by an unprivileged external actor.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the signed payload verification, e.g., include the `X-Shopify-Shop-Domain` header value as part of `to_signable_string`, or have `Registry.process` independently verify that the shop asserted in the header matches an expected/registered shop for that webhook subscription before dispatching to the handler. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant-sensitive decisions without additional verification.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and receives a genuine webhook, e.g. for topic "orders/create":
raw_body = '{"id":1,"note":"hi"}'
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
) # this is a *valid* signature the app issued for the attacker's own shop

# Attacker replays the same body+hmac to the app's public webhook callback,
# but forges the shop-domain header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (only checks raw_body),
# and the registered handler is invoked with data.shop == "victim-shop.myshopify.com",
# even though the payload never originated from that shop.
```
