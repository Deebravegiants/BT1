### Title
`WrappedHyperFungibleToken.configure()` lets the owner silently swap the escrowed `underlying` token, permanently stranding all previously locked tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`configure()` allows the owner to change `_underlying` at any time, without ever checking whether the contract still holds a locked balance of the *previous* underlying token. Because `send()`, `onAccept()`, and `onPostRequestTimeout()` all reference `_underlying` unconditionally, any user tokens locked prior to a `configure()` call that changes the underlying address become permanently unreachable — no code path can ever move the old token out of the contract again.

### Finding Description
`WrappedHyperFungibleToken` locks a single ERC20 (`_underlying`) as users bridge out, and unlocks it as bridged-in transfers arrive (`onAccept`) or timeouts are refunded (`onPostRequestTimeout`): [1](#0-0) [2](#0-1) [3](#0-2) 

`configure()` is the only setter for `_underlying`, and unlike `_host` (which is set-once, guarded by `if (_host == address(0))`), `_underlying` is unconditionally overwritten on every call, with no check that the contract's balance of the current `_underlying` is zero: [4](#0-3) 

This mirrors the reported bug class exactly: a privileged setter reassigns "the token the contract operates on" while funds of the *old* token are still resident in the contract, and after the switch nothing in the contract's logic can ever reference the old token again — `onAccept` and `onPostRequestTimeout` only ever call `IERC20(_underlying)`/`IWETH(_underlying)` using the *current* value. Any in-flight bridge-out that was locked under the old underlying (waiting for the peer chain's mint confirmation, or waiting to time out) becomes permanently stuck: the eventual `onPostRequestTimeout` refund and any pending `onAccept` release for that old token will operate on the *new* `_underlying` contract instead, either reverting (wrong token behavior/allowances) or worse, mistakenly moving the *new* token's balance to satisfy an old-token-denominated message.

Notably, the codebase already recognizes and defends against this exact class of bug elsewhere: `EvmHost.updateHostParamsInternal` explicitly reverts with `CannotChangeFeeToken` if the old fee token's balance is non-zero before allowing a fee-token change: [5](#0-4) 
No equivalent guard exists for `WrappedHyperFungibleToken.configure()`.

### Impact Explanation
Any tokens locked in the contract at the time of a `configure()` call that changes `underlying` become permanently frozen — the contract can no longer transfer them out through any function, since every transfer path hardcodes `_underlying` to the newly configured address. This is a direct, permanent freezing-of-funds vulnerability affecting user deposits escrowed by this Hyperbridge token-bridging contract (Medium/High severity per the Sherlock classification of the analogous finding, since it can permanently lock user funds without recourse).

### Likelihood Explanation
This requires the contract owner (a trusted but not infallible actor — e.g., during token migration, decimal fix, or wrapping a different asset) to call `configure()` a second time with a different `underlying` while in-flight sends exist. This is a realistic operational scenario for a long-lived bridge deployment undergoing configuration updates, and the contract provides no protection or warning against it, unlike the analogous `EvmHost` fee-token change which is explicitly guarded.

### Recommendation
Mirror the `EvmHost` fee-token pattern: before allowing `_underlying` to change to a new value, require that `IERC20(_underlying).balanceOf(address(this)) == 0`, or alternatively sweep/refund the existing balance to a designated recipient before updating. Example:
```solidity
function configure(WrappedConfigOptions calldata options) external onlyOwner {
    if (_host == address(0)) {
        _host = options.host;
    }
    if (_underlying != address(0) && _underlying != options.underlying) {
        if (IERC20(_underlying).balanceOf(address(this)) != 0) revert CannotChangeUnderlying();
    }
    _dispatcher = options.dispatcher;
    _underlying = options.underlying;
    _isWeth = options.isWeth;
}
```

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `underlying = USDC`.
2. Alice calls `send()` locking 1000 USDC, dispatching a POST request to the peer chain (message still in flight, not yet timed out).
3. Before delivery/timeout, the owner calls `configure()` again with `underlying = DAI` (e.g., to fix a misconfiguration or migrate).
4. The contract's 1000 USDC balance is now orphaned: `onAccept`/`onPostRequestTimeout` for Alice's pending message will operate on `_underlying == DAI`, either reverting (if DAI balance is insufficient) or — if DAI happens to be funded by unrelated flows — incorrectly paying out DAI instead of USDC, while the original 1000 USDC remains stuck in the contract forever with no function able to move it.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
