### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain HTTP-header reads, but `to_signable_string` — the value that `HmacValidator` actually verifies — only covers the raw request body. `Registry.process` trusts `request.shop` for tenant attribution after checking only the body's HMAC, so the binding `hmac_signed_content == (body, shop, topic)` that the code implicitly relies on is really only `hmac_signed_content == body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read straight from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e. of `to_signable_string`, the body) and then, without any further tenant check, forwards `request.shop` and `request.topic` straight to the handler as the trusted tenant/topic metadata: [3](#0-2) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [4](#0-3) 

So a request whose body+HMAC pair is valid for shop A can be replayed with the `shopify-shop-domain` header (and/or `shopify-topic`) changed to shop B, and the check `Utils::HmacValidator.validate(request)` still passes, because the header fields were never covered by the signature. The handler then processes the webhook believing it came from shop B, i.e. exactly the analog described in the report: a field the code acts on (`shop`) is not covered by the integrity check (HMAC) that is supposed to establish the trust boundary.

### Impact Explanation
This breaks the identity binding "authenticated body ⇒ authenticated shop" used by every app that self-hosts a webhook endpoint with this gem. An app that dispatches per-shop side effects based on `WebhookMetadata#shop` (billing, GDPR redaction routing, feature toggles, data writes keyed by shop) can be made to attribute a legitimately-signed payload to the wrong tenant, i.e. cross-tenant access/action — a Critical-severity impact per the rules.

### Likelihood Explanation
Exploitation requires an attacker to possess one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for any topic/shop (e.g. by triggering a webhook event on their own store and capturing the request before it is delivered to the app's endpoint, or any other channel that yields one legitimate signed payload). Because `api_secret_key` itself is never needed by the attacker — only a previously observed valid signature+body — this is reachable by an unprivileged internet user who controls a shop that can trigger webhook events, without needing the target's or the app's secret. This matches the rules' exclusion of "requires api_secret_key" (not required here) and is a genuine gem-code root cause, not a host-application misuse.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, `to_signable_string` should incorporate the shop domain and topic so `HmacValidator.validate` fails if either has been altered relative to the signed payload.

### Proof of Concept
1. Attacker owns `shop-a.myshopify.com`, installs the target app, and triggers a webhook event (e.g. `orders/create`) so Shopify sends a request with body `B` and header `x-shopify-hmac-sha256: H` (valid signature for `B` under the app's secret) to the app's webhook endpoint.
2. Attacker captures `B` and `H` (e.g., via a proxy they control in front of their own endpoint, or by running their own receiver first).
3. Attacker crafts a new HTTP POST to the app's real webhook endpoint with the same body `B` and same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unchanged. [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to act as though the payload originated from the victim shop.
