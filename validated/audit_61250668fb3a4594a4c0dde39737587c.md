### Title
Storage-deposit cache key collision from unseparated string concatenation lets one (token, account) pair's cached balance be served for a different pair - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no separator: `` `${contractId}${accountId}` ``. Because NEAR account IDs share the same character set (lowercase letters, digits, `.`, `_`, `-`), two distinct `(contractId, accountId)` pairs can produce an identical concatenated string, letting an attacker poison the shared cache entry used by `estimateWithdrawalFee`/`createWithdrawalIntents` for a different, unrelated withdrawal.

### Finding Description
`DirectBridge` maintains a single, long-lived `storageDepositCache` (an `LRUCache`) as an instance field: [1](#0-0) 

The cache key is computed without any delimiter between the two dynamic segments: [2](#0-1) 

Because `contractId` (the withdrawn token's NEAR account id) and `accountId` (the withdrawal destination NEAR account id) are both attacker-influenced strings drawn from the same NEAR account-id alphabet, an attacker can choose `assetId`/`destinationAddress` values whose concatenation collides with the concatenation of a different, legitimate `(contractId, accountId)` pair — e.g. `contractId = "usdc.near"`, `accountId = "1abc.near"` collides with `contractId = "usdc.near1"`, `accountId = "abc.near"` (both yield key `"usdc.near1abc.near"`).

`DirectBridge` is constructed once inside `IntentsSDK` and reused for the lifetime of that SDK instance, so this cache is shared across all withdrawal requests processed by that instance (the normal server-side usage pattern where one `IntentsSDK` object serves many end users/withdrawals). The call site that feeds this cache is: [3](#0-2) 

The equality broken here is: the `(minStorageBalance, userStorageBalance)` pair returned and used to compute `storageDepositFee` is not guaranteed to belong to the `(contractId, destinationAddress)` pair actually being validated — it can be the value cached for a colliding, unrelated pair.

### Impact Explanation
`estimateWithdrawalFee` uses the (possibly colliding) cached tuple to decide the `storageDepositFee` that is embedded into the withdrawal intent built in `createWithdrawalIntents` (`storageDeposit: getUnderlyingFee(...)`): [4](#0-3) 

Two concrete outcomes follow from a crafted collision:
- If the attacker first seeds the cache with a pair whose `userStorageBalance >= minStorageBalance` (looks "already funded"), a later legitimate call whose real `(contractId, destinationAddress)` collides to the same key incorrectly gets `storageDepositFee: 0n`. The resulting withdrawal intent omits the needed NEAR storage deposit, so the on-chain NEP-141 transfer to the (actually unregistered) destination account fails — funds become stuck pending manual intervention.
- If the colliding cached entry instead encodes a deficit, a victim's withdrawal can be charged a `feeAmount = minStorageBalance - userStorageBalance` that has no relation to their real account state — an unwarranted fee overcharge deducted from the withdrawal.

Both outcomes match the High-severity categories in scope ("a withdrawal stuck until manual intervention" and "a fee overcharge").

### Likelihood Explanation
Exploitability only requires an unprivileged caller who can invoke `estimateWithdrawalFee`/`createWithdrawalIntents` with attacker-chosen `assetId` and `destinationAddress` values (standard SDK usage, no privileged role needed) against a long-lived `IntentsSDK`/`DirectBridge` instance shared across users/requests, which is the typical integrator deployment pattern (one SDK instance backing a service). Constructing a colliding NEAR account-id pair is a straightforward string-arithmetic exercise since NEAR account ids allow `.`, `_`, `-`, digits, and lowercase letters, giving many valid collision candidates.

### Recommendation
Use a collision-safe cache key that unambiguously delimits and/or length-prefixes the two components, e.g. `` `${contractId.length}:${contractId}|${accountId}` `` or a structured key using a tuple-aware cache, or simply hash `JSON.stringify([contractId, accountId])`. Apply the same fix to any other cache in the codebase keyed by naive string concatenation of two independent identifiers (e.g. `accountExistenceCache` should be checked for analogous risk if it is ever keyed on more than one field).

### Proof of Concept
1. Instantiate `IntentsSDK` once (simulating a shared server-side instance).
2. Call `sdk.estimateWithdrawalFee` for `assetId = "nep141:usdc.near1"`, `destinationAddress = "abc.near"` such that the underlying `getCachedStorageDepositValue("usdc.near1", "abc.near")` returns/caches a tuple where `userStorageBalance >= minStorageBalance` (i.e., the destination already has sufficient deposit) — cache key becomes `"usdc.near1abc.near"`.
3. A different legitimate withdrawal request for `assetId = "nep141:usdc.near"`, `destinationAddress = "1abc.near"` (a distinct token/account pair that actually lacks a storage deposit) calls `getCachedStorageDepositValue("usdc.near", "1abc.near")`, which produces the same key `"usdc.near1abc.near"` and hits the poisoned cache entry from step 2.
4. `estimateWithdrawalFee` returns `storageDepositFee: 0n` for this second, unrelated withdrawal even though the real destination account is not storage-registered on `usdc.near`.
5. The resulting withdrawal intent from `createWithdrawalIntents` omits the required storage deposit, causing the on-chain transfer to fail and funds to be stuck at the bridge/intents contract pending manual resolution.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
