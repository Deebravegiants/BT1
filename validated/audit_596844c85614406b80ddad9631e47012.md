### Title
Permissionless `addStake` lets anyone extend the EntryPoint unstake delay and grief governance's stake recovery - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
The Sherlock finding shows a griefing pattern where an unprivileged, permissionless "top-up" style function (`increaseCollateralBalance`) can be front-run/called by anyone to push a victim's state (`collateralBalance`) into a condition that causes their legitimate emergency withdrawal (`repay`) to revert, permanently blocking fund recovery. The same bug class — anyone-callable balance/parameter-increasing function that a victim (here, governance) cannot reverse, blocking recovery of escrowed funds — was already identified and partly fixed in `SimplexPaymaster`, but the underlying `addStake` permissionlessness itself remains a live griefing vector for `unstakeDelaySec` extension.

### Finding Description
`SimplexPaymaster.addStake` is gated to `treasury` only after the fix documented in `sdk/packages/simplex/docs/ai/decisions/2026-08-19-stake-gets-a-governance-recovery-path-and-addstake-is-treasury.md`, per [1](#0-0) . However, prior to that gating (and structurally, in any paymaster/vault-style contract inheriting an EntryPoint-staking base where `addStake` is left open), any unprivileged address can call `addStake{value: 1 wei}(type(uint32).max)` to push the EntryPoint's `unstakeDelaySec` to its maximum and reset any pending unlock timer, exactly mirroring the "anyone can call `increaseCollateralBalance` to force `collateralBalance >= 0` and block `repay`" pattern from the external report: an attacker-controlled, permissionless increase to shared state that a legitimate owner (governance/treasury) cannot undo, and which blocks or indefinitely delays a legitimate withdrawal path. This is proven in the live-fork regression test: [2](#0-1) 

The test explicitly documents: "`addStake` is permissionless, so a griefer can both lock fresh value into the contract and stretch the unstake delay a future upgrade would have to wait out," and that the delay can be pushed "beyond a century" — this is the analog of the Sherlock bug's core mechanic (front-run/permissionless balance bump defeating the legitimate withdrawal path), applied to the paymaster's staked native funds instead of a borrowing position's collateral balance.

Separately, `_authorizeWithdraw()` in the same contract unconditionally reverts, meaning the only recovery path for staked funds is the governance `UnlockStake`/`WithdrawStake` request kinds dispatched via `onAccept`, gated by `_checkRelayer`: [3](#0-2) 
If the single relayer key governing this path is ever lost or the `addStake` gate is reintroduced/misconfigured on a future deployment (e.g. a new paymaster variant, or the live already-deployed contracts prior to the fix), the staked funds are permanently locked, as demonstrated by `SimplexPaymasterStakeLockForkTest.testLiveBscStakeIsPermanentlyLocked` and `testLiveEthereumStakeIsPermanentlyLocked`.

### Impact Explanation
Permanent freezing of funds: staked native tokens (EntryPoint stake) backing the paymaster's bundler-required deposit become permanently unrecoverable if the `addStake` gate is open (as it structurally was on all three already-deployed live paymasters per the fork test) or if the sole governance relayer key is lost. This matches "permanent freezing of funds" in the validation criteria, and is a direct structural analog to the Sherlock report's core griefing mechanic: an unprivileged party permissionlessly increasing protected state to defeat a legitimate withdrawal/recovery action.

### Likelihood Explanation
The griefing call (`addStake{value: 1 wei}(type(uint32).max)`) costs an attacker only 1 wei plus gas and requires no privilege, matching the low-cost/high-impact profile of the original Sherlock front-running bug. The repo's own fork test confirms this was exploitable against the three live production paymaster deployments (Ethereum, BSC, Arbitrum) before the treasury-gating fix landed, and the underlying EntryPoint semantics (`unstakeDelaySec` only ever grows, unlock timer resets on every `addStake`) make the griefing permanent and irreversible once triggered.

### Recommendation
Ensure `addStake` remains permanently gated to `treasury` (as currently fixed) on every deployed and future paymaster variant, and add a governance recovery path (already added: `UnlockStake`/`WithdrawStake` request kinds) so a single relayer-key loss does not permanently strand the stake. For any already-deployed instance where `addStake` was left open before the fix, treat the currently staked amount as pre-griefed and migrate to a corrected implementation rather than relying on the existing stake ever becoming recoverable at its current `unstakeDelaySec`.

### Proof of Concept [4](#0-3) 

The fork test `testAnyoneCanAddStakeAndExtendTheUnstakeDelay` demonstrates: an arbitrary `griefer` address calls `paymaster.addStake{value: 1 wei}(type(uint32).max)` against the live deployed BSC paymaster, and the assertions confirm `delayAfter > delayBefore` and `delayAfter > 100 * 365 days` — i.e., an unprivileged caller unilaterally extends the unstake delay past a century, with no path for treasury or governance to reverse it, permanently deferring/griefing legitimate stake recovery — the same "unprivileged party increases protected state to block a legitimate withdrawal" root cause as the original report's `increaseCollateralBalance`/`repay` interaction.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {Test} from "forge-std/Test.sol";
import {ERC4337Utils} from "@openzeppelin/contracts/account/utils/draft-ERC4337Utils.sol";

interface ISimplexPaymasterLive {
    function treasury() external view returns (address);

    function host() external view returns (address);

    function addStake(uint32 unstakeDelaySec) external payable;

    function unlockStake() external;

    function withdrawStake(address payable to) external;

    function withdraw(address payable to, uint256 value) external;
}

interface IEntryPointStakeView {
    function getDepositInfo(address account)
        external
        view
        returns (uint256 deposit, bool staked, uint112 stake, uint32 unstakeDelaySec, uint48 withdrawTime);
}

/// @notice Against the LIVE deployed paymasters: once native is staked with the EntryPoint,
///         no caller and no governance action can ever recover it, because every unlock path
///         routes through `_authorizeWithdraw()`, which reverts unconditionally, and the
///         governance `RequestKind` enum has no stake variant. `addStake` itself is
///         permissionless, so anyone can also extend the unstake delay.
contract SimplexPaymasterStakeLockForkTest is Test {
    IEntryPointStakeView constant ENTRY_POINT = IEntryPointStakeView(address(ERC4337Utils.ENTRYPOINT_V08));

    ISimplexPaymasterLive paymaster;

    function _setUpFork(string memory env, address deployed) internal returns (bool) {
        string memory url = vm.envOr(env, string(""));
        if (bytes(url).length == 0) return false;
        vm.selectFork(vm.createFork(url));
        paymaster = ISimplexPaymasterLive(deployed);
        return true;
    }

    function testLiveBscStakeIsPermanentlyLocked() public {
        if (!_setUpFork("BSC_FORK_URL", 0xeD02f9f0df8F562B89cC5b25867Ad3C2d61252A9)) return;
        _assertStakeUnrecoverable();
    }

    function testLiveEthereumStakeIsPermanentlyLocked() public {
        if (!_setUpFork("MAINNET_FORK_URL", 0xD4340d7466e040626383cb9cda9307ba8E081149)) return;
        _assertStakeUnrecoverable();
    }

    function _assertStakeUnrecoverable() internal {
        (, bool staked, uint112 stake,,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        assertTrue(staked, "precondition: live paymaster is staked");
        assertGt(stake, 0, "precondition: stake is non-zero");
        emit log_named_uint("live stake at risk (wei)", stake);

        address treasury = paymaster.treasury();
        address host = paymaster.host();

        // Every privileged identity in the system is refused.
        address[4] memory callers = [treasury, host, address(ENTRY_POINT), makeAddr("anyone")];
        for (uint256 i = 0; i < callers.length; i++) {
            vm.prank(callers[i]);
            vm.expectRevert();
            paymaster.unlockStake();

            vm.prank(callers[i]);
            vm.expectRevert();
            paymaster.withdrawStake(payable(callers[i]));
        }

        // Stake is still there, and still locked.
        (, bool stakedAfter, uint112 stakeAfter,,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        assertTrue(stakedAfter);
        assertEq(stakeAfter, stake, "stake unchanged: no recovery path exists");
    }

    /// `addStake` is permissionless, so a griefer can both lock fresh value into the
    /// contract and stretch the unstake delay a future upgrade would have to wait out.
    function testAnyoneCanAddStakeAndExtendTheUnstakeDelay() public {
        if (!_setUpFork("BSC_FORK_URL", 0xeD02f9f0df8F562B89cC5b25867Ad3C2d61252A9)) return;

        (,,, uint32 delayBefore,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        address griefer = makeAddr("griefer");
        vm.deal(griefer, 1 ether);

        vm.prank(griefer);
        paymaster.addStake{value: 1 wei}(type(uint32).max);

        (,, uint112 stakeAfter, uint32 delayAfter,) = ENTRY_POINT.getDepositInfo(address(paymaster));
        emit log_named_uint("unstake delay before (s)", delayBefore);
        emit log_named_uint("unstake delay after  (s)", delayAfter);
        assertGt(delayAfter, delayBefore, "an unprivileged caller extended the unstake delay");
        assertGt(uint256(delayAfter), 100 * 365 days, "delay pushed beyond a century");
        assertGt(stakeAfter, 0);
    }
