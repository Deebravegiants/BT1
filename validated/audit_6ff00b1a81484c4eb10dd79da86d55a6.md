### Title
`RequestState` message handling in Orb-Relay client bypasses source-identity verification, allowing unauthenticated replay of signup session state - (File: `orb-relay-client/src/client.rs`)

### Summary
`PollerAgent::main_loop` in the Orb-Relay client enforces a source-identity check (`src.id != self.config.dst_id`) before accepting any inbound relay message and forwarding it into the session's message buffer. However, one specific message type — `self_serve::app::v1::RequestState` — is handled in a branch that executes *before* this check and never performs it, causing the Orb to reply with its last sent signup-state message to whoever produced a `RequestState`-shaped payload, without verifying that the sender is actually the App bound to that signup session (`dst_id`). This mirrors the RubiconMarket `this.offer` bug class: a single code path that skips the authorization/identity check applied to every sibling path, letting an unverified party trigger privileged behavior.

### Finding Description
In `main_loop`, every inbound `RelayPayload` is supposed to be validated against `self.config.dst_id` before being buffered for consumption by the rest of the signup flow: [1](#0-0) 

Specifically:
```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
``` [2](#0-1) 

Every payload other than `RequestState` is subject to `src.id != self.config.dst_id`, a check the code's own author flags as necessary to "avoid multiplexing messages from different sources" on the same relay connection (see the `TODO` above `main_loop`) [3](#0-2) . The `RequestState` branch, however, unconditionally replays `self.last_message` — the most recent state message the Orb sent for this specific signup session — with no verification that the requester is the legitimate App counterpart. This is structurally identical to the `this.offer` flaw: a privileged operation (state disclosure/replay) is reachable through a path that omits the sender-verification gate that protects the equivalent operation everywhere else in the same function.

`orb-relay-client` is not test-only tooling; it backs the production self-serve signup flow. The Orb creates a session-scoped relay client and announces `AnnounceOrbId`, waits for `StartCapture`, sends `CaptureStarted`/`CaptureTriggerTimeout`, and finally `SignupEnded` (with `failure_feedback`) over this same channel: [4](#0-3) [5](#0-4) [6](#0-5) 

Any of these become `self.last_message` and are exactly what gets replayed to an unverified `RequestState` sender.

### Impact Explanation
An unprivileged party able to inject (or cause the relay server to deliver) a `RequestState`-shaped message on the Orb's relay stream — without being the legitimate App identified by `dst_id` — can force the Orb to resend the current signup session's last announced state (e.g. `AnnounceOrbId`, `CaptureStarted`, `CaptureTriggerTimeout`, or `SignupEnded` with `failure_feedback`) without passing the same-origin check every other message type requires. This is a cross-signup state disclosure: session-scoped signup progress/result information leaks outside the verified App/Orb identity binding that the rest of the protocol relies on for correctness.

### Likelihood Explanation
The bypass is unconditional and requires no privilege beyond the ability to place a `RequestState`-typed payload onto the stream the relay server routes to this Orb connection; it does not depend on a malicious relay server operator, hardware access, or a test-only code path — it is a logic flaw in the shipped `orb-relay-client` crate that participates in every self-serve signup.

### Recommendation
Move the `src.id != self.config.dst_id` check to apply uniformly to all inbound payload types, including `RequestState`, before deciding to reply with `self.last_message`. Only after confirming `src.id == self.config.dst_id` should the client honor a `RequestState` replay request.

### Proof of Concept
1. Establish (or otherwise cause the relay server to deliver on) an Orb-side `PollerAgent` connection for signup session `S` bound to `dst_id = <expected App id>`.
2. From any source other than the expected App (i.e., an entity whose `src.id != dst_id`), send a payload matching `self_serve::app::v1::RequestState` on that stream.
3. Observe that `main_loop` matches the `RequestState` branch first and immediately calls `sender_tx.send(self.last_message.clone())`, replaying the Orb's most recent signup-state message (e.g. `SignupEnded`) — with no check that the requester is the legitimate `dst_id`-bound App, unlike every other message type handled two lines later at `src.id != self.config.dst_id`.

    let Config {
        self_serve,

        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
