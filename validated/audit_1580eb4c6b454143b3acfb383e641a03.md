### Title
Donation-forced `OverflowCapDegenerate` permanently disables curve depletion and can brick graduation - ([File: packages/contracts/src/Router.sol])

### Summary
The CVE describes a remote, unprivileged input that drives `HandleAuthenticationFailure` into an unhandled edge case that panics the AMF, denying service. The analogous class in alt.fun is an unprivileged, capital-only ERC20 donation of a launched `Token` directly into its `Pair` that forces the bonding-curve buy math's defensive overflow-cap branch in `Router._computeBuy` to hit its own degenerate guard on every subsequent tail-end buy, permanently reverting instead of completing — a self-inflicted, unrecoverable DoS on that curve's ability to fully deplete.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real token balance and back-derives `amountInUsed` from the invariant when a buy tries to consume more supply than remains: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

`reserveToken` is the *virtual* token reserve tracked in `Pair`'s stored `Pool.tokenReserve`, which is only ever mutated in lockstep with `tokenBalance()` (the real ERC20 balance) by ordinary `swap()` calls — both decrease by the same `tokenOut` amount on every buy. Under normal operation the gap `reserveToken - tokenBalance()` is therefore an invariant fixed at `LP_RESERVE` (250,000,000e18), set once at launch: [2](#0-1) 

That invariant is broken by a plain, unprivileged `IERC20.transfer` of the launched `Token` directly to the `Pair` address — explicitly a permitted attack surface (donations into `Pair`). A donation increases `tokenBalance()` (`realBalance`) without touching the stored `reserveToken`, shrinking the gap by exactly the donated amount:

```
gap = reserveToken - tokenBalance() = LP_RESERVE - totalDonated
```

An attacker who accumulates and donates exactly `LP_RESERVE` (250,000,000e18) tokens (obtainable by buying on the curve itself, which sells up to 750,000,000e18 tokens, then transferring the held tokens to `Pair` instead of selling them back) drives `gap` to exactly `0`. From that point on, **every** future buy whose uncapped `tokensOut` computation exceeds the (now donation-inflated) real balance — i.e. every buy attempting to finish depleting the curve — lands on `cappedReserveToken == 0` and reverts with `OverflowCapDegenerate()` permanently, since the gap can never be closed or reopened (no code path restores it).

This makes the supply-based graduation trigger (`IPair(pair).tokenBalance() == 0` in `canGraduate`) permanently unreachable for that token: [3](#0-2) 

If the USD-value trigger has not independently crossed `graduationThresholdUsd` (e.g. the paired LT has depreciated so accrued LT-denominated raise undershoots the USD threshold even as real token supply nears exhaustion), the token is stuck forever in `Lifecycle.Curve`: it can never enter `_enterGraduating`/`finalizeGraduation`, its `LP_RESERVE` tokens and all curve-raised LT remain locked in `Pair` with no extraction path (LT only leaves `Pair` via `Router.graduate`, itself only reachable from `_prepareGraduationLiquidity` during graduation), and the token can never reach the HyperSwap V2 market.

### Impact Explanation
This is a permanent, unrecoverable denial of service against a specific token's bonding curve: any buyer's attempt to complete the sellout reverts indefinitely, and if the USD trigger doesn't independently fire, the curve-raised LT and reserved tokens are permanently frozen in `Pair`/`Bonding` with no owner or router rescue path for that state. This satisfies the "permanent freezing of trader, creator, or LP funds" bar and is High severity given it is triggerable by any unprivileged wallet with sufficient (but attainable, since obtained via the curve itself) token holdings and a single `ERC20.transfer`.

### Likelihood Explanation
The precondition is capital-intensive (acquiring and donating exactly `LP_RESERVE` = 25% of total supply) but requires no privilege, no cooperation from the protocol, and is fully deterministic — the attacker can read `getReserves()`/`tokenBalance()` live and donate the exact residual amount needed to zero the gap. It is most attractive against a token whose paired LT is depreciating (so the USD trigger lags), making the supply trigger the only path to graduation and turning this into a targeted, economically rational attack (e.g. to freeze a competitor's launch or extort the creator).

### Recommendation
Do not `revert` on `cappedReserveToken == 0` in `Router._computeBuy`; instead treat it as a legitimate boundary (e.g. clamp `amountInUsed`/`tokensOut` using a saturating calculation, or fall back to draining the remaining real balance at the last valid ratio) so a donation-shrunk gap degrades gracefully rather than permanently reverting. Additionally, consider having `canGraduate`'s supply trigger account for/ignore donation-inflated `tokenBalance()` the same way the USD trigger already excludes donations from `assetReserve`, so a token's ability to graduate is never coupled to an attacker-manipulable raw ERC20 balance.

### Proof of Concept
1. Launch a token via `Zap.createToken`; curve seeds `Pair` with `curveSupply = 750,000,000e18` real tokens and virtual `tokenReserve = 1,000,000,000e18` (`LP_RESERVE` gap = `250,000,000e18`).
2. Attacker buys/accumulates `250,000,000e18` of the launched `Token` via ordinary `Zap.buy` calls against the curve (capital-intensive but permissionless).
3. Attacker calls `Token.transfer(pairAddress, 250_000_000e18)` directly — a plain unrestricted ERC20 transfer, bypassing `Bonding`/`Router` entirely.
4. `Pair.tokenBalance()` (real ERC20 balance) is now inflated by the donation while `Pool.tokenReserve` (virtual, stored) is untouched: `reserveToken - tokenBalance() == 0`.
5. Any subsequent buyer whose buy would otherwise trigger the tail-cap branch in `Router._computeBuy` (i.e. any buy attempting to consume the remaining real supply) now hits `cappedReserveToken == 0` and reverts with `OverflowCapDegenerate()` — permanently, for every future such attempt.
6. `IPair(pair).tokenBalance() == 0` can never become true through the buy path again, so `Bonding.canGraduate`'s supply leg is permanently disabled for this token; if the USD leg hasn't independently fired, the token and its escrowed LT/tokens are frozen in `Lifecycle.Curve` indefinitely.

```text
    /// @dev Capped: `amountInUsed` is back-calculated from the K invariant
    ///      (rounded up so the curve never under-charges).
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```

```text
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();

        if (info.creator == address(0)) return false;
```
