### Title
Fee-on-Transfer tokens cause escrow over-accounting and insolvency in `placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal `_orders` escrow ledger with the user-specified/protocol-fee-reduced input amount instead of the amount of tokens actually received by the contract via `safeTransferFrom`. For any ERC20 with a transfer fee/deflationary mechanism, the contract will under-collect tokens relative to what it records as escrowed, creating a shortfall that can be drained from other users' legitimately escrowed balances.

### Finding Description
In `placeOrder`'s non-predispatch branch, tokens are pulled with a plain `safeTransferFrom` and the escrow mapping is incremented by `reducedInputs[i].amount` (derived from the *stated* `order.inputs[i].amount`), without ever measuring the contract's actual token balance before/after the transfer: [1](#0-0) 

The predispatch branch has the same flaw for tokens moved to the dispatcher and back: it checks `balance < requiredAmount` for a sufficiency assertion, but still books `reducedInputs[i].amount` into escrow rather than the amount actually swept into the gateway, and it never re-derives `order.inputs[i].amount` from measured balances the way the sibling EVM implementation does: [2](#0-1) 

This is a regression relative to the parallel, already-patched implementation at `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots balances before and after every transfer and mutates `order.inputs[i].amount` to the measured delta for exactly this reason: [3](#0-2) [4](#0-3) 

The existence of dedicated fee-on-transfer regression tests for the `evm/src` gateway (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) confirms this is a known, intentionally-mitigated bug class for this codebase — the Tron fork simply lacks the corresponding fix: [5](#0-4) 

### Impact Explanation
With a fee-on-transfer or deflationary ERC20 as `order.inputs[0].token`, `IntentGatewayV2` (Tron) will hold strictly less of that token than the amount it records in `_orders[commitment][token]`. Since escrow accounting per-token is a shared ledger keyed by commitment/token, but the actual balance held by the contract is the aggregate over all orders in that token, any order using a fee-on-transfer token creates a permanent solvency gap: the contract's token balance for that asset will be smaller than the sum of amounts it believes are escrowed and owed to solvers/depositors. Whoever fills/cancels/redeems later (whether the FoT order's own solver or another legitimate order using the same token) can encounter reverts or, if withdrawal logic does not individually verify balance sufficiency per-call, an implicit socialized loss where later claimants cannot be paid in full — a form of fund freezing/insolvency for other users' escrowed tokens. This matches the "concrete theft or permanent freezing of funds" bar since honest depositors' escrowed value becomes unbacked by actual contract balance.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with an arbitrary ERC20 input token — no privileged role is required, and the intents system is explicitly designed to accept arbitrary user-specified tokens (`order.inputs[i].token`). The bug is deterministic (not probabilistic) for any FoT/deflationary/rebasing-on-transfer token, and the parallel `evm/src` implementation's need for balance-based accounting (with matching tests) confirms this is a realistic and anticipated token class for this system.

### Recommendation
Apply the same balance-before/after pattern already used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: capture `IERC20(token).balanceOf(address(this))` immediately before and after `safeTransferFrom` (and the analogous dispatcher-sweep balances in the predispatch branch), derive the actual received amount from the delta, mutate `order.inputs[i].amount` to that measured value before computing `reducedInputs`/the commitment, and only credit `_orders[commitment][token]` with the fee-reduced *actual received* amount.

### Proof of Concept
1. Deploy a 1%-fee ERC20 (e.g., the `FeeOnTransferToken` test contract already present in the repo's test suite) and mint balance to a user.
2. User calls `IntentGatewayV2.placeOrder` (Tron variant) with `order.inputs[0] = {token: FOT, amount: 1000e18}`, having approved the gateway for `1000e18`.
3. `safeTransferFrom` moves `1000e18` from the user, but the gateway's balance only increases by `990e18` (1% burned in transfer) — confirmed by the fee-on-transfer mechanics validated in `FeeOnTransferToken._transfer`: [6](#0-5) .
4. `_orders[commitment][FOT]` is nonetheless incremented by `reducedInputs[0].amount`, which is computed from the full `1000e18` (minus protocol fee only), i.e. it records more than the `990e18` actually held.
5. Any subsequent solver fill/cancel/refund flow that pays out based on `_orders[commitment][token]` will pay out more FOT than the gateway holds for that token in aggregate, causing reverts or under-collateralized payouts for other orders sharing that token balance.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
