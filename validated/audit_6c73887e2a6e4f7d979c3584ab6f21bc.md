Based on the analysis, I've confirmed the vulnerability.

### Title
Webhook shop identity is trusted from an unauthenticated header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop` identity taken from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — trivially available to anyone who installs the app on their own store and receives a real webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the request will pass validation and be dispatched to the app's handler as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` (and `topic`, `api_version`, `webhook_id`) are read straight from client-supplied HTTP headers, entirely outside the HMAC computation: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) and compares it against `request.hmac`: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `request.shop` (the unauthenticated header value) is handed directly to the app's `WebhookHandler` as the trusted tenant identifier, with no cross-check that the signed body actually pertains to that shop: [5](#0-4) 

This breaks the intended identity binding: `shop header used by the handler == shop that produced/authorized the signed body`. In reality, the binding only enforced is `hmac == HMAC(body, client_secret)`, with `shop` free-floating and attacker-controlled.

### Impact Explanation
An attacker who has any account with the target app installed on their own store (a completely unprivileged relationship to any other merchant) receives legitimate webhooks for their own shop, each with a valid `(raw_body, hmac)` pair signed by the app's real `client_secret`. Because `shop` is not part of the signed payload, the attacker can resend that exact body+HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to any victim shop's domain. The signature still validates, and the app's handler executes business logic believing the event came from the victim tenant. Depending on what the integrating app does in its webhook handlers (e.g., mandatory `customers/redact`, `shop/redact`, `app/uninstalled`, inventory/order updates keyed by `shop`), this can cause cross-tenant data corruption, spoofed deprovisioning/redaction actions against a victim's data, or state confusion between tenants — a cross-tenant boundary violation achieved purely through this gem's own webhook verification logic.

### Likelihood Explanation
The prerequisite is low: any user able to install the target app on any shop (including their own, which is normal unprivileged app-installation activity, not a privileged credential) can harvest a valid signed webhook body/HMAC pair for topics they control, then replay it with a forged shop-domain header at will. No access token, `client_secret`, or privileged access to the victim tenant is required.

### Recommendation
Bind the shop identity to the signed material, not to an out-of-band header. Options: (1) include the shop domain (and ideally webhook ID / topic) in the string that is HMAC-verified, if Shopify's webhook contract allows constructing the check over header+body; or, since this gem cannot change Shopify's actual signature scheme, (2) have `Registry.process` cross-validate `request.shop` against the shop identifier embedded in `request.parsed_body` (most Shopify webhook payloads include a shop/domain or resource-owner field) before dispatching to the handler, and document this requirement clearly for consumers implementing `WebhookHandler#handle` so they don't unconditionally trust `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, receiving a legitimate webhook, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `client_secret`).
2. Attacker resends this exact HTTP request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(B, client_secret)` and compares to `H` — this still matches since `B` and `H` are unmodified.
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...))`, executing the app's business logic under the victim's tenant identity even though the payload actually originated from and describes the attacker's own shop.
