### Title
Webhook shop-domain and topic headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only that the body matches the HMAC and then dispatches the handler using the unauthenticated `shop` and `topic` values, breaking the equality "shop authenticated by HMAC == shop used to process the event."

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 
`shop`, `topic`, `webhook_id`, and `api_version` are all extracted directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), while `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it against the `hmac` value from `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` uses this validation, then immediately forwards the unauthenticated `request.shop` and `request.topic` to the handler: [4](#0-3) 

Because none of `shop`, `topic`, `webhook_id`, or `api_version` are part of the HMAC-signed content, an attacker who possesses **any single legitimately-signed webhook body** (e.g. by installing the app on their own store and triggering a webhook there) can replay the exact body + hmac header pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`) header with an arbitrary value. The HMAC check still passes because it never inspected those headers, yet `WebhookMetadata` — and therefore the host application's per-tenant business logic — is invoked believing the event originated from the spoofed shop/topic.

This precisely matches the "field acted on but not covered by the HMAC" bug class from the reference report (there, `lastCollateralError_Offset` is used in later accounting without being reset/bound correctly; here, `shop`/`topic` are used to route trust-sensitive logic without being bound by the same signature that is supposed to authenticate the request).

### Impact Explanation
Host applications built on this gem are documented to trust `WebhookMetadata#shop` as the tenant identifier for a webhook event (used to look up the correct merchant record/session, apply per-shop business logic, etc.). Since this field is not authenticated by the HMAC, an unprivileged internet user who can generate at least one legitimately signed webhook for a shop they control can forge the shop identity on that payload, causing the host app to process attacker-supplied data as if it belonged to a different, victim tenant. This is a cross-tenant confusion vulnerability at the library's trust boundary, matching the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on a shop the attacker controls (free/dev store, not a privileged account, standard for testing any Shopify app), (2) capturing one legitimately delivered webhook request (topic/body/hmac), and (3) replaying it to the app's public webhook endpoint with a modified `shop-domain` (and optionally `topic`) header. No knowledge of `api_secret_key` or any merchant's access token is required, since the HMAC secret never needs to be recomputed — the original signature is reused unchanged.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-verified signable content (or otherwise cryptographically bind them to the verified body), e.g. by including the relevant headers in the string that is HMAC-verified, so that tampering with any of them after the fact invalidates the signature. At minimum, document and enforce that host applications must independently establish shop identity (e.g. via the webhook subscription id looked up from Shopify APIs) rather than trusting `request.shop`/`WebhookMetadata#shop` outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the full HTTP request Shopify sends: raw body `B`, and headers `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical raw body `B` and identical `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` returns only the unchanged raw body, the recomputed HMAC matches the received one and validation succeeds.
4. The handler is invoked via `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host application to process attacker data under the victim's tenant identity.
