### Title
Webhook Shop Domain Not Covered by HMAC Signature — Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) used for dispatching webhook data entirely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks is computed over the raw request body only. Because the shop identity is never part of the signed payload, any party capable of producing a request with a body/HMAC pair that passes validation (or replaying/modifying a previously captured one) can attach an arbitrary `x-shopify-shop-domain` value and have the app process the webhook as if it belonged to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers, none of which feed into the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `hmac` against `to_signable_string`, i.e. the body — the `shop` value used everywhere downstream is not part of the equality the HMAC check performs: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's business logic, with no secondary binding between the signed body and the claimed shop: [4](#0-3) 

This is the same identity-binding gap described in the report's bug class: a field that is *acted on* (the shop the webhook is attributed to, used as the tenant/session key for the handler) is not *covered by the HMAC* that is supposed to authenticate the request. The equality that should hold — `shop_authenticated_by_signature == shop_used_for_dispatch` — is never enforced; the second value is taken from attacker-controllable bytes.

### Impact Explanation
An app built on this gem uses `WebhookMetadata#shop` to decide which tenant's records to update (e.g., persisting order/customer data, revoking access, updating billing state). Since `shop` is not bound to the HMAC, a request whose body+HMAC pair is valid for shop A can be replayed/relayed with the header changed to shop B, causing the handler to write/act on shop B's data using shop A's payload — a cross-tenant data confusion. Depending on the handler's semantics (e.g., `app/uninstalled`, `shop/redact`) this can lead to unauthorized state changes for a shop the caller does not control.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for some topic (e.g., because they are a legitimate merchant of the app receiving genuine webhooks for their own shop, or they can intercept one in transit). Given such a pair, changing only the `x-shopify-shop-domain` header before delivery to the app's webhook endpoint is trivial, since the header is not part of what `HmacValidator` checks. This makes the likelihood moderate — bounded by the attacker's ability to obtain a validly-signed body, not by any cryptographic weakness.

### Recommendation
Bind the tenant identity to the signed payload before trusting it:
- Include `shop` (and ideally `topic`/`webhook_id`) inside `to_signable_string` so the HMAC covers the full set of fields the handler relies on, or
- After HMAC validation, additionally verify that `request.shop` matches the shop associated with the specific webhook/subscription id that was registered, rejecting mismatches.

### Proof of Concept
1. Obtain a valid webhook delivery for shop `attacker-shop.myshopify.com` (its own installed instance of the app), capturing `raw_body` and the `x-shopify-hmac-sha256` header.
2. Resend the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled data under the victim's tenant identity: [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
