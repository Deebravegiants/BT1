## Analysis

The SPOKpark "rollback attack" is characterized by an attacker exploiting return-flow inconsistencies: an operation is treated as successful and state is finalized even though the underlying value transfer silently failed/was rolled back. The closest concrete analog reachable by an unprivileged relayer/module callback in this codebase is the Tron-specific `IntentGatewayV2.withdraw()` implementation, which departs from the audited EVM version's `SafeERC20` usage and instead uses a raw low-level `.call` that only checks call success, not the ABI-encoded boolean return value of `transfer`.

### Title
Unchecked ERC20/TRC20 return value in `withdraw()` lets escrow accounting finalize while token payout silently fails - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` implements token payout in `withdraw()` using a raw `.call` to the token contract and only checks the boolean success of the *call itself*, never decoding/validating the ERC20 `transfer` return value. [1](#0-0)  Any token that returns `false` on failure instead of reverting (or any non-contract/EOA address supplied as the token) will make the call succeed while no value is actually transferred, yet the function proceeds to mark the order as filled and decrement escrow accounting as if the payout succeeded.

### Finding Description
`withdraw()` is invoked from two unprivileged, message-triggered entry points: `onAccept` handling `RedeemEscrow`/`RefundEscrow` POST requests relayed from a peer instance [2](#0-1) , and `onGetResponse` handling a relayed GET response for cross-chain cancellation [3](#0-2) . Inside `withdraw()`, the order is marked filled first (correct CEI ordering) [4](#0-3) , but the actual asset payout uses:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

This only reverts if the low-level call itself reverts. It does not decode `returndata` to check `transfer`'s boolean result. Tokens (or TRC20-style tokens common on Tron) that return `false` on a failed transfer rather than reverting will make `success == true` while no tokens move. The same unchecked pattern is repeated for fee payout [5](#0-4)  and in the `SweepDust` handler [6](#0-5) .

This is a meaningful regression relative to the canonical EVM implementation, which performs the equivalent payout via `SafeERC20.safeTransfer`, reverting the whole operation (including the `_orders` decrement and `_filled` write) if the transfer fails: [7](#0-6) . The Tron contract deliberately drops this safety net.

Once `withdraw()` "succeeds" despite a failed transfer, `_orders[body.commitment][token] -= amount` permanently reduces the escrow accounting [8](#0-7)  and `_filled[body.commitment]` is already set, so the request/response can never be replayed or retried by a relayer — the tokens remain stuck in the contract with no accounting path to recover them for the intended beneficiary.

### Impact Explanation
This is a permanent freezing-of-funds condition: legitimate escrowed input tokens or transaction fees credited to a solver/user on a successful fill or refund can be silently lost if the token contract does not strictly follow the revert-on-failure convention, or if a malicious/unusual token address is used in the order's `TokenInfo.token` field (which is attacker-supplied at `placeOrder` time and never restricted to a known-safe allowlist). Because `_filled`/`_orders` are updated unconditionally on “call success” rather than truthful transfer success, there is no way to retry delivery once this occurs.

### Likelihood Explanation
Reachable by any relayer delivering a normal `RedeemEscrow`/`RefundEscrow` POST message or a GET response to `onGetResponse` — both standard, permissionless Hyperbridge message-delivery paths — as long as the order references a token whose `transfer` can return `false` instead of reverting (common among some TRC20/ERC20 tokens), or references an EOA/non-standard address as `token`. No special privilege is required to place an order with an arbitrary token address.

### Recommendation
Replace the raw `.call` + success-only check in `withdraw()` (and in the `SweepDust` branch of `onAccept`) with `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`, so that a failed or non-boolean-compliant transfer reverts the entire withdrawal atomically instead of finalizing escrow state against a failed payout.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs[0].token` set to the address of a TRC20 token that returns `false` on failed `transfer` (or to an EOA address entirely).
2. Order is filled/redeemed normally, and eventually `withdraw()` is invoked via `onAccept`/`onGetResponse`.
3. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` even though the underlying `transfer` logically failed (returned `false`) or no code exists at `token`.
4. `_orders[commitment][token] -= amount` executes and `_filled[commitment]` remains set from the top of the function — the beneficiary never receives funds and the escrow can never be redeemed again.
