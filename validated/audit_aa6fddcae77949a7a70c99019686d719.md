### Title
Webhook `shop` identity is taken from an HTTP header that is not covered by the HMAC signature, allowing shop-domain spoofing in verified webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. An attacker who can get any validly-signed webhook body (e.g. by triggering an event on their own store) can attach an arbitrary `shop-domain` header to it, and the request will still pass `HmacValidator.validate`, causing the host application to process the webhook as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

and `hmac` is derived from the `hmac-sha256` header: [2](#0-1) 

`shop` is read from a completely separate header that is never included in the signed payload: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC, i.e. only the raw body bytes: [4](#0-3) 

This is structurally the same bug class as the `FluxToken.calculateBPT` report: a value that is *used* to determine a privileged outcome (there, the mint amount; here, the tenant/shop that owns the webhook data) is not actually covered by the integrity check that is supposed to bind it (there, division by `BPS`; here, inclusion in the HMAC signable string). The identity equality that should hold is:

`shop_used_by_handler == shop_that_HMAC-signed_the_request`

but what the code actually guarantees is only:

`raw_body_bytes == HMAC(raw_body_bytes, secret)`

with `shop` supplied out-of-band and unauthenticated.

### Impact Explanation
Any application built on this gem that follows the documented pattern of calling `HmacValidator.validate(request)` and then trusting `request.shop` to route/attribute webhook data (a standard multi-tenant pattern, and the one used inside the gem's own `Webhooks::Registry`, which passes `request.shop` to registered handlers) is vulnerable to a **cross-tenant data confusion**: a party who legitimately owns Shop A (and can therefore obtain genuinely-signed webhook payloads for Shop A, e.g., by installing the app and triggering benign webhook-firing actions) can resend that same signed body with the `X-Shopify-Shop-Domain` header rewritten to Shop B. The HMAC check still passes because it never inspected the shop header, and the host application will process/attribute the payload as belonging to Shop B. Depending on the handler, this can lead to cross-tenant data injection or state corruption — this maps to the "Critical: cross-tenant access" impact category, since the gem's own verification primitive gives false assurance that the shop field is authenticated when it is not.

### Likelihood Explanation
Likelihood is high for any adopter who relies on the gem's `HmacValidator`/`Webhooks::Request` abstraction as the sole authentication mechanism for incoming webhooks (as the gem's README/registry pattern encourages) and does not separately re-validate the shop domain out-of-band (e.g., against Shopify's IP allowlist or a separately maintained shop-registration table). The attacker only needs a legitimately installed/authorized shop of their own to generate valid signed bodies, no secret key or privileged credentials are required.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signed payload verification path, or explicitly document that `Request#shop` is unauthenticated and must not be trusted for tenant attribution unless independently verified. Concretely, `HmacValidator.validate` should be changed to bind the header-derived identity fields into `to_signable_string`, or `Webhooks::Registry`/consuming code should cross-check `request.shop` against a shop known to have originated the specific `webhook_id`/topic combination via the Shopify API rather than trusting the header directly.

### Proof of Concept
1. Install the app on shop `legit-shop.myshopify.com` and capture a genuine webhook POST, including its raw body and the valid `X-Shopify-Hmac-Sha256` header (computed by Shopify over that body with the app's `client_secret`).
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The host application calls `ShopifyAPI::Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `@raw_body` (`to_signable_string`) — it never inspects `shop` — so validation succeeds.
4. The application, trusting `request.shop`, processes/stores the payload under `victim-shop.myshopify.com`, even though the payload actually originated from `legit-shop.myshopify.com`.
