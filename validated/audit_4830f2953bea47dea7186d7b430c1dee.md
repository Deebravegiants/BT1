## Answer

**No vulnerability found for this question.**

### Analysis

The claimed equality break is: for a deposit-direction index (`deltaAmountChanges[i] > 0`), `EmporiumUpgradeable.runAction`'s `balanceChange` is never corrected by `deltaAmountChanges[i]`, so an attacker could mint an under-backed UTXO by manipulating `stack.ops` ordering.

Tracing the actual value flow shows this correction is unnecessary for `deltaAmountChanges[i] > 0` and the exploit does not go through:

1. In `Hinkal._externalTransact` ( [1](#0-0) ), Hinkal only pre-funds the Emporium contract when `deltaAmountChanges[i] < 0`. For `deltaAmountChanges[i] > 0`, nothing is pre-funded, so `EmporiumUpgradeable.runAction`'s `balancesBefore[i]`/`balancesAfter[i]` diff is the actual, unadjusted amount that ops caused to accumulate in Emporium — the `-= deltaAmountChanges[i]` correction is only needed to cancel out the pre-funding that happened for negative deltas [2](#0-1) .

2. `handleOut` only creates a UTXO and transfers real tokens to `msg.sender` (Hinkal) when `balanceChange > 0` [3](#0-2) . If the attacker's ops net the Emporium balance to zero (deposit then withdraw to an attacker endpoint), `balanceChange <= 0`, so `handleOut` returns a zero-amount UTXO — no tokens are sent to Hinkal and no UTXO enters `utxoSet` for that index.

3. Critically, the actual backing check happens independently in `Hinkal.sol`, using Hinkal's *own* real ERC20 balance (not Emporium's internal bookkeeping): `balanceDif = newBalances[i] - oldBalances[i]` measured around the whole `_externalTransact` call, compared against `(onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` [4](#0-3) . Since `utxoAmount` is derived only from real UTXOs actually returned by `runAction` (backed by real `transferERC20TokenOrETH` calls), and `balanceDif` is the real physical balance change of the Hinkal contract, this equation forces `amountChanges[i]` to be exactly what is left over after the real transferred `utxoAmount` is subtracted. If the attacker nets the Emporium balance change to zero (no real tokens returned to Hinkal) while claiming `amountChanges[i] > 0`, then `balanceDif == 0` and `utxoAmount == 0`, forcing the check `0 == amountChanges[i] + 0` to fail and revert with `"Balance Diff Should be equal to sum of onchain and offchain created commitments"`.

So `EmporiumUpgradeable.runAction`'s internal `balanceChange`/`BalanceChangeShouldBePositive()` guard is not the binding security control for this scenario — the outer balance equation in `Hinkal.sol`, based on Hinkal's real token balance, is what backstops any claimed `amountChanges[i]`. There is no way to net the ops to make `balanceDif` (real tokens received by Hinkal) exceed the real `utxoAmount` transferred, since both quantities are derived from the same physical token movement (`handleOut`'s `transferERC20TokenOrETH`). The attacker cannot make the equality hold with an inflated `amountChanges[i]` unless real tokens actually back it, which requires a genuinely larger deposit — contradicting the premise of siphoning tokens externally while still passing the check. [5](#0-4)
