This confirms the vulnerability. The gem's `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC signature only over the raw request body, while the `shop` field (from the unauthenticated `shop-domain` header) is passed unchecked to the host app's handler as the tenant identifier.

### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over `request.to_signable_string` (the raw body). The `shop` value used to identify which merchant/tenant the webhook belongs to is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. An attacker who can obtain any one validly-signed webhook payload (e.g., by installing the target app on their own store, a routine unprivileged action) can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The HMAC check still passes (it only checks the body), yet `WebhookMetadata#shop` is now attacker-controlled and gets handed directly to the host application's `handle` method, which per the gem's own documented usage (`docs/usage/webhooks.md`) is expected to key persistence/business logic (e.g., `shop_domain: data.shop`) off this trusted-looking field.

### Finding Description
The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the tenant-scoped handler`

In this gem it does not:
- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Webhooks::Request#shop` is read straight from an unauthenticated header with no cryptographic binding to the HMAC: [2](#0-1) 
- `HmacValidator.validate_signature` computes/compares the digest solely against `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app-supplied handler: [4](#0-3) 
- `WebhookMetadata.shop` is a plain `String` field with no further verification: [5](#0-4) 
- The gem's own documentation instructs consuming apps to trust `data.shop` as the tenant key for downstream processing: [6](#0-5) 

Because the HMAC only binds the request body and never the `shop-domain` header, any party holding one legitimately-signed webhook body (obtainable by installing the app on an attacker-owned store, which requires no privileged credentials) can forge the header to name a victim shop. The HMAC verification succeeds because it never inspected that header, and the gem hands the forged `shop` straight to the host app as if Shopify had authenticated it for that tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: the value `shop` that host applications key their per-merchant data/actions on is not actually authenticated, only the payload bytes are. An attacker can cause a target application to process/attribute webhook data (order data, GDPR events, app-uninstall notifications, etc.) under an arbitrary victim shop domain, i.e., cross-tenant data confusion/injection driven entirely by a forged, unauthenticated header. This matches the Critical "cross-tenant access" impact category, since it lets an unprivileged actor make the app treat attacker-supplied webhook content as authentic input for a different shop.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs (a) the ability to install the target app on their own development/trial store (an ordinary, unprivileged action any Shopify user can perform to obtain a validly-HMAC-signed webhook body from Shopify itself for a chosen topic/body), and (b) the ability to POST to the app's publicly reachable webhook endpoint with a custom `shop-domain` header, which requires no secret key, access token, or privileged account.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cross-check the header-derived shop against an independently-verified source (e.g., verify the shop is a shop with an active, previously-established session/webhook subscription id recorded server-side by the app) before dispatching `WebhookMetadata` to handlers. At minimum, document prominently that `data.shop` is unauthenticated and must not be trusted as a tenant key without additional verification, or extend `HmacValidator`/`Request#to_signable_string` so verification incorporates the shop-domain header value, rejecting the webhook if it doesn't match what Shopify actually signed.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`, triggering Shopify to send a legitimately HMAC-signed webhook, e.g. `orders/create`, to the app's public callback URL, with headers:
   - `X-Shopify-Hmac-Sha256: <valid signature over body B>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - body `B`
2. Attacker captures this raw request (they own the store, so no privileged access is required to intercept their own webhook).
3. Attacker resends the identical body `B` and identical `X-Shopify-Hmac-Sha256` value to the same endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over body `B` only (per `lib/shopify_api/utils/hmac_validator.rb` and `Request#to_signable_string`) — it matches, since the body is unchanged.
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: ...))`, per `lib/shopify_api/webhooks/registry.rb` lines 198-199, causing the host app to process attacker-controlled webhook content as if it originated from `victim-shop.myshopify.com`.
