### Title
Unauthenticated swap-out amount panics the program via unchecked `checked_sub().unwrap()` in `swap_token_amount_base_out` — (File: `program/src/math.rs`)

### Summary
`process_swap_base_out` and `process_swap_base_out_v2` pass the caller-supplied `swap.amount_out` directly into `Calculator::swap_token_amount_base_out` before validating it against the pool's actual reserves. Inside that function, the reserve is decremented by `amount_out` using `checked_sub(...).unwrap()` with no prior bound check, so any attacker-supplied `amount_out` greater than or equal to the relevant pool reserve causes an integer-underflow `None` result that is immediately `.unwrap()`ed, panicking the instruction handler.

### Finding Description
`process_swap_base_out` computes `total_pc_without_take_pnl` / `total_coin_without_take_pnl` from the vault balances [4](#0-3) , then immediately calls:
```
let swap_in_before_add_fee = Calculator::swap_token_amount_base_out(
    swap.amount_out.into(),
    total_pc_without_take_pnl.into(),
    total_coin_without_take_pnl.into(),
    swap_direction,
);
``` [1](#0-0) 

Inside `swap_token_amount_base_out`, for the `Coin2PC` direction:
```
let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
```
and for `PC2Coin`:
```
let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
``` [5](#0-4) 

`amount_out` comes straight from instruction data (`SwapInstructionBaseOut::amount_out`) decoded in `AmmInstruction::unpack` [6](#0-5)  — it is fully attacker-controlled with no upper bound at this point. If the attacker sets `amount_out >= total_pc_without_take_pnl` (or `>= total_coin_without_take_pnl` for the other direction), `checked_sub` returns `None`, and `.unwrap()` panics.

The only place that legitimately guards against `amount_out` exceeding the pool reserve is the `if swap.amount_out >= total_pc_without_take_pnl { return Err(AmmError::InsufficientFunds.into()); }` check [2](#0-1) , but this check is reached only *after* the panicking computation at line 2172–2177, so it never has a chance to short-circuit the panic. The identical pattern exists in `process_swap_base_out_v2` [7](#0-6) .

This is the same bug class as the reported nimiq-consensus advisory: an unprivileged actor supplies external, attacker-chosen data (a locator hash for nimiq; a swap amount for Raydium) that selects/enters a computation path whose internal invariant ("hash is a macro block" / "amount_out is within pool reserves") isn't actually enforced before an `.unwrap()` is reached, causing a reachable-assertion panic.

### Impact Explanation
Any unprivileged user can submit a single `SwapBaseOut` (opcode 5, or `SwapBaseOutV2` opcode 17) transaction with attacker-chosen `amm_info`/vault accounts (an existing valid pool) and an oversized `amount_out`, causing the Solana runtime to abort the instruction with a Rust panic instead of a controlled `ProgramError`. This is a Denial-of-Service against the specific swap-out instruction path for that pool: legitimate `SwapBaseOut`/`SwapBaseOutV2` calls that happen to encode an out-of-range `amount_out` (which any external client/aggregator could unintentionally construct, e.g. due to stale reserve caching) will also panic. Because the underlying token vaults, pool state and LP shares are untouched (the panic happens before any CPI/transfer), user/LP funds are not directly stolen or permanently frozen by this specific call, but it does constitute a reachable assertion / crash of the on-chain program logic reachable by a single attacker-controlled transaction, matching the CWE-617 (Reachable Assertion) class of the external report. Given the scope restrictions (no low/best-practice/no-impact analogs), this qualifies as a Medium-severity availability issue for the swap-out instruction path rather than a fund-theft/insolvency bug.

### Likelihood Explanation
Trivial to trigger: no signer other than the ordinary swapper is needed, no special account permissions, and no race condition — a single crafted instruction with `amount_out` set above the pool's `total_pc_without_take_pnl`/`total_coin_without_take_pnl` deterministically panics every time.

### Recommendation
Move the reserve-sufficiency check (`swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl`) to occur **before** calling `Calculator::swap_token_amount_base_out`, in both `process_swap_base_out` and `process_swap_base_out_v2`, returning `AmmError::InsufficientFunds` early. Additionally, replace the unchecked `.unwrap()` in `swap_token_amount_base_out`'s `checked_sub` calls with `.ok_or(AmmError::CheckedSubOverflow)?` (propagating a `ProgramError` instead of panicking) so that any future caller of this shared math function cannot re-introduce the same unwrap-panic pattern.

### Proof of Concept
1. Attacker (or any user) picks an existing pool `P` with known `amm_info`, vaults, and computes `total_pc_without_take_pnl` (e.g., by reading the pc vault balance and the `need_take_pnl_pc` field, both readable on-chain).
2. Attacker submits a `SwapBaseOut` (or `SwapBaseOutV2`) instruction against pool `P` with `amount_out = total_pc_without_take_pnl` (or any larger value) for the `Coin2PC` direction (`max_amount_in` can be any value; it's never reached).
3. `process_swap_base_out` executes the status checks, computes `total_pc_without_take_pnl`, and calls `Calculator::swap_token_amount_base_out(amount_out, total_pc_without_take_pnl, total_coin_without_take_pnl, Coin2PC)` [1](#0-0) .
4. Inside that function, `total_pc_without_take_pnl.checked_sub(amount_out)` evaluates to `None` because `amount_out >= total_pc_without_take_pnl`, and `.unwrap()` panics [8](#0-7) , aborting the transaction with a runtime panic rather than a clean `ProgramError`.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
