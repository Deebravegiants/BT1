### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/topic dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, and that validator signs only the raw HTTP body. The `shop-domain` and `topic` HTTP headers — which are used unmodified to select the handler and to build the `WebhookMetadata` passed into app code — are not part of the signed material at all.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC over exactly that signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` accepts the request as authentic once this body-only HMAC passes, then dispatches using the unauthenticated `topic` header to select the handler and forwards the unauthenticated `shop` header straight into the handler payload: [3](#0-2) 

`Request#shop` and `Request#topic` are read directly from headers with no cryptographic linkage to the signed body: [4](#0-3) 

The identity equality this breaks is: `shop_header_used_for_tenant_dispatch == shop_bound_by_hmac`. In this code that equality never holds, because the HMAC binds nothing but the byte content of the body. Since Shopify webhook HMACs are computed with the app's single `api_secret_key`, which is shared across every merchant that has installed the app, any unprivileged internet user who can install the app on their own (attacker-controlled) shop obtains legitimate `(body, hmac)` pairs signed with that same secret. That attacker can then replay a self-obtained valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop and/or the `X-Shopify-Topic` header for a different topic. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will route the forged headers straight to the topic handler bound to the wrong shop.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary the gem is responsible for authenticating: `Registry.process` is the library's HMAC-gatekeeping entry point, and host apps rely on `WebhookMetadata#shop`/`#topic` as trustworthy, HMAC-verified values once `process` succeeds. Because `shop` and `topic` are not covered by the signature, an attacker can impersonate a different merchant's webhook delivery (cross-tenant) or relabel a payload as a different topic than the one that was actually signed, causing the host application to perform shop-scoped side effects (e.g., data deletion for `customers/redact`, order processing, mandatory-topic handling) attributed to the wrong tenant.

### Likelihood Explanation
Exploitation requires no privileged credentials beyond what any unprivileged developer can obtain: install the target app on an attacker-owned development store to receive at least one genuine webhook delivery (body + valid HMAC) signed with the app's shared `api_secret_key`, then replay that exact body with forged `shop`/`topic` headers to the app's public webhook endpoint. No access token, `client_secret`, or account takeover is needed — only the ability to receive one webhook as a legitimate (if adversarial) merchant.

### Recommendation
Bind the `shop-domain` and `topic` (and `webhook-id`) header values into the signed material verified by `Utils::HmacValidator`, or otherwise fold them into `Webhooks::Request#to_signable_string` so the HMAC covers the values that `Registry.process` uses for dispatch, not just the body bytes. At minimum, document prominently that `shop`/`topic` headers are unauthenticated and that host apps must independently verify the `shop` against a known/expected tenant before acting on `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`, completing OAuth normally (no special privilege needed).
2. Shopify delivers a legitimate webhook to the app's endpoint for topic `orders/create` with body `B` and a valid `X-Shopify-Hmac-Sha256` header computed as `HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, hmac)` and replays it to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com` and/or `X-Shopify-Topic` to `shop/redact`.
4. `Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — it matches, because the body `B` is unchanged.
5. `Registry.process` proceeds, dispatching to the handler for the forged `topic` and constructing `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host app to act as if the victim shop sent this webhook/topic.
