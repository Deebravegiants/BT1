### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` trusts these header-derived values once the body HMAC checks out, so an attacker who legitimately receives one valid, HMAC-signed webhook body (e.g., from their own shop where the app is installed) can replay that exact body with a forged `shop-domain` header pointing at a different (victim) shop, and the library will treat it as an authentic webhook "from" the victim tenant.

### Finding Description
The binding that should hold is:

`HMAC(secret, signed_bytes) == received_hmac` **and** `signed_bytes` includes every field the handler subsequently trusts as the event's tenant identity (`shop`).

In this gem, `to_signable_string` only returns the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers that are never part of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `to_signable_string` (the body) against the HMAC secret: [3](#0-2) 

`Registry.process` accepts the request once that body-only check passes and immediately hands the *header-derived* `shop` to the handler as the event's tenant identity, with no secondary check that this shop is the one the payload actually originated from: [4](#0-3) 

Because `shop` is never part of `to_signable_string`, the equality that the code actually enforces is `HMAC(secret, body) == received_hmac`, not `HMAC(secret, body || shop) == received_hmac`. Any `(body, hmac)` pair that is valid for *some* shop is valid for *every* shop header value, since the shop is outside the authenticated bytes.

### Impact Explanation
An unprivileged user who installs the app on their own store (a shop they legitimately control) will receive genuine webhook deliveries with valid `(body, hmac)` pairs computed with the app's real `api_secret_key`. By capturing one such delivery and replaying the identical body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with an arbitrary victim shop domain, the attacker causes `Registry.process` to invoke the app's webhook handler with `shop: "victim-shop.myshopify.com"` even though the payload content is entirely attacker-controlled. Any host application that uses the `shop` value from `WebhookMetadata` to select the tenant record, session, or access token to act on (which is the documented/expected use of this field) will apply attacker-controlled webhook data to another merchant's tenant context — a cross-tenant data-integrity/access violation.

### Likelihood Explanation
Likelihood is moderate-to-high: any user can obtain a real installation of a Shopify app on a free development store and trigger events that generate real signed webhook bodies, then replay them directly against the app's public webhook endpoint with a modified shop header — no secret key, access token, or privileged account is required, only network access to the app's own webhook URL.

### Recommendation
Include the intended tenant-binding fields (at minimum `shop`, and ideally `topic`/`webhook_id`) in the HMAC-covered signable string, or independently verify that the header-derived `shop` matches a value bound to the signed payload (e.g., by having callers supply/verify the expected shop out-of-band, and documenting that the header `shop` value must not be trusted for tenant selection without such verification). At minimum, update `Webhooks::Request#to_signable_string` so it can't be satisfied by a body signed for one shop while headers claim another.

### Proof of Concept
```ruby
# Attacker step 1: legitimately installs the app on their own shop and
# captures a real, validly-signed webhook delivery.
raw_body = '{"id":1,"note":"attacker controlled content"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker step 2: replays the same body+hmac, but swaps the shop-domain
# header to the victim's shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HMAC only validates raw_body, not the shop header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ..., ...))
```
