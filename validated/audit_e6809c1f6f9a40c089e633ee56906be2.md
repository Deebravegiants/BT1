### Title
Webhook `shop-domain` header is never covered by HMAC and never passed through `ShopValidator.sanitize!`, so `WebhookMetadata#shop` is an unauthenticated, unsanitized attacker-controlled string - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`Registry.process` builds `WebhookMetadata` directly from `request.shop`, which is read straight off the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header with no call to `ShopValidator.sanitize!` and no format check. Critically, `HmacValidator.validate` only signs `request.to_signable_string` (the raw body), never the headers, so the `shop-domain` header is not cryptographically bound to the HMAC at all, meaning it is trivially forgeable independent of body content.

### Finding Description
Binding claimed broken: `shop value stored in WebhookMetadata == a shop value that passed ShopValidator` — **confirmed FALSE**.

- `Registry.process` reads the shop directly off the request and constructs the struct with no sanitation call: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [1](#0-0) .
- `Request#shop` is a raw pass-through of the header value with only a `String` cast, no format/domain validation: [2](#0-1) .
- `WebhookMetadata` is a plain `T::Struct` with `const :shop, String` — Sorbet only enforces the type is `String`, not that it is a valid `*.myshopify.com` domain: [3](#0-2) .
- `HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, which for `Request` is `@raw_body` — headers (including `shop-domain`) are excluded from the signed material entirely: [4](#0-3) [5](#0-4) .
- `ShopValidator.sanitize!` exists in the gem and is used in OAuth/token-exchange flows, but it is never referenced anywhere in `lib/shopify_api/webhooks/` — confirmed by searching the codebase, where all matches for `ShopValidator` are in `test/utils/shop_validator_test.rb`, `lib/shopify_api/utils/shop_validator.rb`, `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/clients/graphql/storefront.rb` — none in the webhook path.

Exploit flow: an attacker installs the app on their own real development shop and receives one legitimately-signed webhook for it (they can trigger this themselves, e.g. via `customers/redact` or any subscribed topic). Since the HMAC covers only the raw body, the attacker can replay that exact request to the app's public webhook endpoint while rewriting the `X-Shopify-Shop-Domain` header to any arbitrary string (e.g. `evil.attacker.com`, or another merchant's real `*.myshopify.com` domain). `HmacValidator.validate` still returns `true` because the signable string (raw body) is unchanged, and `Registry.process` passes the forged shop straight into `WebhookMetadata`, which the host app's `handle` implementation receives as `data.shop` believing it authenticated.

None of the existing guards catch this: `HmacValidator.validate` only authenticates the body, `ShopValidator.sanitize!` is never invoked in this path, and Sorbet's `String` typing on `WebhookMetadata#shop` performs no domain validation.

### Impact Explanation
Host applications built on this gem are documented to key persistence, tenant lookups, and business logic off `data.shop` from `WebhookHandler#handle`. Because the shop value is unauthenticated, an attacker can make the app record or act on webhook data under a shop identifier of their choosing — including a real victim merchant's `*.myshopify.com` domain — enabling cross-tenant data corruption or confusion (e.g. redact/data_request events falsely attributed to another shop, or app-specific business data written against a victim's tenant key). This matches the "Critical - cross-tenant access" category since one tenant's forged event can be made to touch another tenant's data record.

### Likelihood Explanation
The attacker only needs a legitimately signed webhook body, which they can generate for free and repeatably by installing the app on their own shop (a normal, self-service action) and capturing any webhook delivery. No `api_secret_key`, access token, or privileged access is required — they only replay the same body with a modified header to the app's public webhook receiving endpoint. This is directly repeatable against arbitrary victim shop identifiers of the attacker's choosing.

### Recommendation
Validate `request.shop` in `Registry.process` (or in `Request#shop`) via `Utils::ShopValidator.sanitize!` before constructing `WebhookMetadata`, rejecting any value that isn't a well-formed `*.myshopify.com` domain. More fundamentally, since headers are outside the HMAC signature envelope, the gem should not treat `shop-domain`, `topic`, `api-version`, or `webhook-id` headers as trusted/authenticated at all unless it also verifies them against the actual registered shop associated with the app/session, or Shopify's webhook payload includes the shop in the signed body for cross-checking.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_spoof_test.rb
require "test_helper"

class RegistryShopSpoofTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @handler = Class.new do
      extend T::Sig
      include ShopifyAPI::Webhooks::WebhookHandler
      class << self
        attr_accessor :received
      end
      def handle(data:)
        self.class.received = data
      end
    end
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "customers/redact", delivery_method: :http,
      path: "/webhooks", handler: @handler.new)
  end

  def test_spoofed_shop_domain_passes_hmac_and_reaches_handler
    raw_body = '{"customer": {"id": 1}}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
    )

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: raw_body,
      headers: {
        "X-Shopify-Topic" => "customers/redact",
        "X-Shopify-Hmac-Sha256" => hmac,
        "X-Shopify-Shop-Domain" => "evil.attacker.com", # not attacker's real shop, not any myshopify.com domain
        "X-Shopify-Api-Version" => "2023-01",
        "X-Shopify-Webhook-Id" => "123",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    # Binding under test: shop stored in WebhookMetadata == a shop that passed ShopValidator
    assert_equal("evil.attacker.com", @handler.received.shop) # no exception raised, no sanitize! applied
  end
end
```
This demonstrates `HmacValidator.validate` returns `true` for a body/HMAC pair produced independent of the `shop-domain` header value, and `Registry.process` forwards the unsanitized, forgeable `shop` string into `WebhookMetadata` with no `ShopValidator.sanitize!` check anywhere in the call path.
