## Title
Webhook shop-domain spoofing via HMAC that only covers the request body, not the `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw body alone, while `topic`, `shop`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only that HMAC and then dispatches the handler using `request.shop`, so the shop identity delivered to the app is never itself covered by the signature it just verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC computed over the body, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity equality the library implicitly claims to guarantee is:
`hmac_valid(body) == true` implies `shop header == shop that produced this signed body`

But because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across *every* shop that installs the app, not per-tenant, any shop that has installed the app can legitimately obtain a `(raw_body, valid hmac)` pair for content it controls (e.g. triggering an `orders/create`, `app/uninstalled`, or any subscribed webhook by acting in its own store). Since the `shop` header is not part of the signed material, an attacker who owns Shop A can replay that same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. `HmacValidator.validate` (see `lib/shopify_api/utils/hmac_validator.rb`) still succeeds because it only re-derives the HMAC from `to_signable_string`/body, and `Registry.process` then calls the app's handler believing the (attacker-controlled) payload originated from the victim shop. [4](#0-3) 

This is the same bug class as the referenced report: a value (`swappedAmount` there, `shop` here) is used downstream as though it were validated by the check that just ran, when in fact it sits outside the boundary the check actually covers.

### Impact Explanation
Any application relying on `ShopifyAPI::Webhooks::Registry.process` to authenticate the originating shop from `request.shop` can be tricked into processing attacker-supplied webhook payloads under another tenant's shop identity — a cross-tenant confusion/injection primitive within the host app's webhook-handling logic (e.g. forged `app/uninstalled`, `shop/update`, `customers/data_request`, or order/fulfillment events attributed to a shop the attacker does not control).

### Likelihood Explanation
Requires only that the attacker's own store be a legitimate install of the target app (any developer/merchant can install most public apps) plus the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint — no access to `api_secret_key` or any victim credential is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the HMAC-signable string, or otherwise cryptographically bind the shop identity into the verified material in `Request#to_signable_string`, so a signature computed for one shop's payload cannot be replayed with a different shop header. At minimum, document that `request.shop` must never be trusted as an authenticated tenant identifier by consuming applications, since it is unauthenticated header data — but the safer fix is to make the gem itself bind it.

### Proof of Concept
1. App has a single `client_secret` shared by all installations.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g. via the Admin UI) to receive a legitimately signed `(raw_body, X-Shopify-Hmac-Sha256)` pair from Shopify.
3. Attacker POSTs that identical `raw_body` and `X-Shopify-Hmac-Sha256` to the target app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body bytes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, believing it is an authentic event from the victim's store.
