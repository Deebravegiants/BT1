### Title
Webhook HMAC signs only the raw body, never `shop-domain`, `topic`, or `webhook-id` headers, letting an attacker replay a validly-signed body under a forged victim shop and arbitrary webhook-id - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Utils::HmacValidator.validate` computes the HMAC exclusively over that string, so `shop-domain`, `topic`, and `webhook-id` headers are never authenticated. An attacker who legitimately receives one validly-signed webhook (e.g., from their own dev-store install) can resend the identical body+HMAC to the app's shared webhook endpoint with the `shop-domain` header swapped to a victim shop and the `webhook-id` swapped to an arbitrary fresh value, and `Registry.process` will accept it as authentic.

### Finding Description
The broken binding, stated as an equality that does NOT hold:
`webhook_id used by host-app dedup logic (WebhookMetadata#webhook_id, sourced from request.webhook_id)` == `webhook_id (or shop) authenticated by the HMAC signature` — the right-hand side is actually `∅` (nothing), because: [1](#0-0)  `to_signable_string` returns `@raw_body` only: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are all read straight from unauthenticated headers: [3](#0-2) 

`HmacValidator.validate` only ever compares an HMAC over `verifiable_query.to_signable_string`: [4](#0-3) 

`Registry.process` validates HMAC once, then blindly builds `WebhookMetadata` from `request.shop` and `request.webhook_id`, both unauthenticated: [5](#0-4) 

Exploit flow: the attacker installs the app on their own development shop, receives one genuine `orders/create` (or any topic) webhook — a real `raw_body` plus a real `x-shopify-hmac-sha256` computed by Shopify with `Context.api_secret_key`. Because host apps register a single shared callback path per topic for all shops (as documented: `path: 'callback/orders/create'`), the attacker POSTs the exact same `raw_body` and `hmac` to that same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-webhook-id: <any-fresh-uuid>`. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, which is unchanged, so it passes. `Registry.process` then invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", webhook_id: "<attacker-chosen>", body: <attacker's original content>)`. Any host-app idempotency/dedup logic keyed on `webhook_id`, and any per-shop mutation logic keyed on `shop`, treats this as a brand-new legitimate event for the victim tenant.

No existing guard in this gem prevents this: `ShopValidator` is never invoked in the webhook path (only used in OAuth/token-exchange flows), and there is no per-shop callback URL binding or nonce/webhook-id signing anywhere in `lib/shopify_api/webhooks/*`.

### Impact Explanation
An attacker can inject forged, replayed webhook payloads that a host app will attribute to any arbitrary victim shop, bypassing both HMAC-based shop binding and webhook_id-based deduplication simultaneously. This is repeatable indefinitely (attacker mints a new webhook-id per replay) and against arbitrary victim shop domains (myshopify.com domains are guessable/enumerable), causing cross-tenant data corruption or forged mutation of victim shop data — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
The attacker needs only: (1) their own dev-store app install to obtain one genuine signed webhook body/HMAC pair, and (2) network access to POST to the app's public, shared webhook callback URL — both squarely within the stated unprivileged attacker capabilities. No secret, token, or privileged access is required, and the host app is using the gem exactly as documented (single shared endpoint per topic, `shop`/`webhook_id` read from `WebhookMetadata`).

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the authenticated signable content (or otherwise cryptographically associate them with the verified body), and/or require host apps to validate `request.shop` against their own list of installed/authorized shops before trusting `WebhookMetadata#shop` and using `webhook_id` for deduplication. At minimum, document this gap explicitly so host apps do not rely on unauthenticated headers for tenant separation.

### Proof of Concept
```ruby
# test/webhooks/registry_replay_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryReplayTest < Test::Unit::TestCase
      def test_replay_with_forged_shop_and_webhook_id_passes_validation
        topic = "orders/create"
        raw_body = '{"id":1,"note":"legit order on attacker shop"}'
        real_hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body),
        )

        captured = nil
        handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| captured = data })
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: topic, path: "callback/orders/create", delivery_method: :http, handler: handler,
        )

        # Attacker forges shop-domain (victim) and webhook-id (fresh), body+hmac unchanged
        forged_headers = {
          "x-shopify-topic" => topic,
          "x-shopify-hmac-sha256" => real_hmac,
          "x-shopify-shop-domain" => "victim-shop.myshopify.com",
          "x-shopify-webhook-id" => "attacker-chosen-fresh-id-#{SecureRandom.uuid}",
          "x-shopify-api-version" => "2024-01",
        }
        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

        # No exception is raised -- HMAC check passes despite forged shop/webhook_id
        ShopifyAPI::Webhooks::Registry.process(forged_request)

        assert_equal("victim-shop.myshopify.com", captured.shop)
        assert_equal(forged_headers["x-shopify-webhook-id"], captured.webhook_id)
      end
    end
  end
end
```
This asserts both sides of the broken binding directly: the HMAC (computed only from `raw_body`) validates successfully, while `captured.shop` and `captured.webhook_id` — the values a host app would act on for tenant identification and deduplication — are fully attacker-controlled and unauthenticated.
