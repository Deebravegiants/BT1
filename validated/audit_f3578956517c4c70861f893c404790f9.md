## Title
Webhook Shop/Topic Spoofing via HMAC That Only Covers the Request Body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body, while the merchant identity (`shop`) and message type (`topic`) that the library trusts and hands to the app's webhook handler are taken from unauthenticated HTTP headers. This breaks the identity binding "the shop authenticated == the shop acted upon," allowing any holder of one validly-signed webhook payload (trivially obtainable by installing the app on their own store) to relabel that payload as belonging to a different merchant and have it processed as such.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body HMAC, then immediately trusts the unauthenticated `request.shop` and `request.topic` to route and label the webhook for the host application's handler: [4](#0-3) 

Because the `api_secret_key` is a single shared secret for the whole app (not per-shop), any merchant who installs the app can receive a legitimately-signed webhook for their own store, then replay that exact body against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different merchant. `HmacValidator.validate` will still pass, because it only checks the body bytes, and `Registry.process` will hand the attacker-controlled body to the handler labeled as originating from the victim shop/topic.

### Impact Explanation
This breaks the binding "shop authenticated by HMAC == shop acted upon by the handler," enabling cross-tenant data injection: an unprivileged, if once-installed, attacker can make the host application process attacker-chosen webhook payloads under a victim merchant's identity (or under a different topic than what was actually signed), corrupting or injecting data attributed to another tenant. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a normal merchant who has installed the app (an unprivileged, publicly available action) to obtain at least one validly HMAC-signed body, and knowledge of a target shop's domain (public information, e.g. `victim.myshopify.com`). The webhook receiving endpoint is by design publicly reachable (Shopify itself posts to it over the open internet), so no additional access is required to replay the captured payload with modified headers.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable content used for HMAC verification, or otherwise cryptographically bind the header-derived identity fields to the signed body before they are trusted by `Registry.process`/handed to handlers. At minimum, document and encourage host applications to independently verify `webhook_id`/`shop` against known/expected values rather than trusting them purely from headers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. body `{"id":123}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's shared `api_secret_key`.
2. Attacker resends the exact same body and HMAC header to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic` to a different registered topic).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` succeeds because it validates only `@raw_body`, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-199) invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-controlled data as if it came from the victim merchant.
