### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC signature of the raw request body, then trusts the `shop` (and `topic`, `webhook_id`) values taken from HTTP headers — which are never included in the signed payload — when constructing the `WebhookMetadata` passed to the host application's handler.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, i.e. the HMAC binds nothing but the JSON body to the app's `api_secret_key`: [2](#0-1) .

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers, entirely outside the signed content: [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with these header-derived, unauthenticated values: [4](#0-3) . The resulting `WebhookMetadata` struct — including `shop` — is exactly what host applications use to identify which tenant/session a webhook body belongs to: [5](#0-4) .

The identity binding that should hold is: `shop header used by the handler == shop cryptographically bound to the signed body`. Because the HMAC key (`Context.api_secret_key`) is a single, per-app secret shared across every shop that installs the app — not a per-shop secret — any party who can obtain one valid `(body, hmac)` pair (e.g., by installing the app on their own store and receiving a legitimate webhook, which any unprivileged internet user can do since app installation itself requires no special privilege) can replay that exact body+hmac pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass, because it never inspected the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) body originated from a completely different, victim shop.

### Impact Explanation
This breaks the tenant boundary the library is supposed to guarantee to host applications: an attacker-controlled webhook body, cryptographically valid under the shared app secret, can be attributed to an arbitrary victim shop domain. If the host application (as intended and documented) uses `WebhookMetadata#shop` to look up the corresponding merchant session/store and applies the body's contents to that tenant's data (e.g., updating orders, products, or customer data for "shop"), the attacker achieves cross-tenant data injection/corruption using only their own (legitimately obtained) webhook credentials replayed against another tenant's identifier. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled development/trial store to receive at least one real, validly-signed webhook (a barrier-free, unprivileged action for any developer app), and (2) sending a forged HTTP POST directly to the app's public webhook endpoint with the captured body/HMAC pair and a substituted `shop-domain` header. No access to another merchant's token, session, or secret is needed, and no TLS interception or social engineering is required — only knowledge of the (already-public) webhook endpoint URL and standard HTTP tooling.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-covered content, or otherwise cryptographically verify that the `shop` header matches the shop the app actually expects for that specific webhook delivery, before constructing `WebhookMetadata`. At minimum, `Utils::HmacValidator` should be updated so `to_signable_string` (or an equivalent check in `Registry.process`) incorporates the shop domain, closing the gap between what is authenticated and what is trusted by handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker replays a raw POST directly to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and succeeds [6](#0-5) .
4. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)` [7](#0-6) , causing the host app to process attacker-supplied data under the victim shop's identity.
