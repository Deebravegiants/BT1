### Title
Missing verifying_contract equality check on signedIntents.before/after allows cross-contract payload injection into atomic batch - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`composeMultiPayloads` (packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts:190-214) blindly concatenates `signedIntents.before`/`signedIntents.after` MultiPayloads with the freshly-signed payload and hands the array straight to `intentRelayer.publishIntents` for atomic execution, without ever asserting that every payload's `verifying_contract` equals `this.envConfig.contractID` used for the new payload. This lets a caller (or an integrator who forwards counterparty-supplied signed payloads through `signAndSendIntent`) splice in a MultiPayload signed for a different contract into the same atomic batch.

### Finding Description
The broken equality is:

`signedIntents.before[i].verifying_contract === envConfig.contractID` (and same for `after[i]`)

`signAndSendIntent` (lines 58-136) computes `verifyingContract = this.envConfig.contractID` (line 70) and uses it only for the payload it itself signs (`intentPayload`, line 72). It never inspects `signedIntents.before`/`after` at all. Those are passed straight into `composeMultiPayloads(multiPayload, signedIntents)` (line 100), which does:

```
result.push(...signedIntents.before);
result.push(newPayload);
result.push(...signedIntents.after);
```

with no field-level validation on `before`/`after` entries — [1](#0-0) . The resulting array is passed unchecked to `this.intentRelayer.publishIntents({ multiPayloads: composedPayloads, quoteHashes }, ...)` (lines 108-114) for atomic publication.

The existing unit test suite for this file itself constructs `before`/`after` MultiPayloads with `verifying_contract: ""` (empty string, clearly different from `"intents.near"` used elsewhere in the same test file) and asserts they are forwarded unchanged into `publishIntents`, which confirms no validation exists and that the composition function is contract-agnostic by design/oversight — [2](#0-1) .

`signAndSendIntent` (the public-facing SDK method) simply forwards `args.signedIntents` into `IntentExecuter.signAndSendIntent` without any equality check — [3](#0-2) . `signAndSendWithdrawalIntent` similarly forwards `args.intent?.signedIntents` — [4](#0-3) .

Exploit flow: attacker supplies (or an integrator forwards) a `foreignPayload` whose `verifying_contract` is `"intents.other-shard"` in `signedIntents.before`. `envConfig.contractID` for the running SDK instance is `"intents.near"`. `composeMultiPayloads` returns `[foreignPayload, newPayload]` and `publishIntents` is called with this mixed-contract array with no thrown error and no filtering.

Why existing guards don't catch this: there is no `validateAddress`, `compareAddresses`, or any sanity `assert` in this code path that compares `verifying_contract` across the composed array; the only place `verifying_contract` is set is when building the *new* payload (line 70-75), and it is never read back out of `before`/`after` for comparison.

### Impact Explanation
Whether this reaches the "Critical" bar depends on what `intentRelayer.publishIntents` and the destination contract actually do with a mismatched `verifying_contract` on-chain. The relayer/NEAR contract's own signature verification presumably ties each MultiPayload's signature to the `verifying_contract` string encoded inside its payload (NEP-413/EIP-191 style signing schemes typically bind the signature to the exact JSON payload including `verifying_contract`), so a payload signed for `"intents.other-shard"` would only be verifiable by that other shard's contract, not `"intents.near"`. I was not able to fully trace `IntentRelayerPublic.publishIntents` or the on-chain `intents.near` contract's atomic-batch semantics in this pass to confirm whether it (a) rejects cross-contract entries at the relayer/contract level, or (b) routes each payload to its own `verifying_contract` destination independently (in which case there is no "wrong contract execution", just an independent, harmless routing), or (c) genuinely treats the whole batch as bound to one contract and could misexecute. This distinction is central to whether the impact is Critical/High or a non-issue, and I could not verify it with the tools available in this pass.

### Likelihood Explanation
Precondition is only that the caller passes `signedIntents.before`/`after` with at least one entry — no special contract or route state is required, and no privileged role is needed to call `signAndSendIntent`. However, actually obtaining a validly-signed foreign-contract MultiPayload requires either the attacker's own signature (self-harm only) or a counterparty-provided payload the integrator blindly forwards without checking `verifying_contract` — which is an unusual integration pattern, since `signedIntents` in this SDK's documented use case (README/shared-types) is intended for the *caller's own* pre-signed intents (e.g., nonce invalidation, custom composition), not for un-validated third-party payloads.

### Recommendation
In `composeMultiPayloads` (or immediately before calling it in `signAndSendIntent`), parse each entry of `signedIntents.before`/`after` and assert `JSON.parse(entry.payload).verifying_contract === this.envConfig.contractID`, throwing an explicit error (e.g., `InvalidSignedIntentContractError`) if any entry does not match before ever calling `publishIntents`.

### Proof of Concept
Not producing a full PoC in this response because the on-chain/relayer behavior for a mismatched `verifying_contract` batch could not be confirmed within this pass — see Impact Explanation. A vitest test mocking `intentRelayer.publishIntents` (as already done in `intent-executer.test.ts`'s "composes intents with prepend only" test) and asserting `publishIntents` is called with a `before` entry whose `verifying_contract` differs from `envConfig.contractID`, with no thrown error, is straightforward to reproduce and matches the existing test pattern that already uses `verifying_contract: ""`. What is needed to convert this into a confirmed vulnerability is verification of `IntentRelayerPublic.publishIntents` (packages/intents-sdk/src/intents/intent-relayer-impl/intent-relayer-public.ts) and the NEAR `intents` contract's atomic multi-payload execution semantics to establish that a genuinely wrong-contract payload is executed (not merely rejected or independently routed).
