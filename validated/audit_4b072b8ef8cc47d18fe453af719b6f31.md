### Title
Operator QR-code expiration is validated only at scan time, allowing signup completion/enrollment under a stale operator identity binding - (File: src/plans/mod.rs)

### Summary
The report describes a "no re-check before finalization" bug class: a request is validated against a time-bounded phase at the moment it is *issued*, but the state can transition out of that valid window before the operation actually *completes*, and no re-check is performed at completion, resulting in inconsistent/insolvable state or misattribution. The orb-core signup flow has a structurally analogous pattern with the operator QR-code identity binding: `operator_qr_expiration_time` is checked only when resolving/scanning QR codes, but the identity ("operator_data`") captured at that check is carried unchanged through biometric capture, pipeline processing, fraud checks, and enrollment, and used at submission time without re-validation.

### Finding Description
`MasterPlan::scan_remaining_qr_codes` validates operator identity freshness by comparing `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time` before proceeding: [1](#0-0) 

Once this check passes, the resulting `operator_data` (and its embedded `qr_code`) is bound into `ResolvedQrCodes`/`QrCodes`, and flows unchanged through the rest of `do_signup`: biometric capture, biometric pipeline, fraud detection, and PCP/enrollment construction: [2](#0-1) 

None of these downstream stages re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time`. The operator identity is ultimately embedded as `distributorId` in the backend signup request built from `operator_qr_code.user_id`: [3](#0-2) 

and also threaded into the `personal_custody_package::Credentials` used to build/upload the PCP: [4](#0-3) 

The elapsed time between the operator-QR freshness check and the final `enroll_user`/`signup_post::request` call is not bounded by `operator_qr_expiration_time` — it also includes biometric capture (`BIOMETRIC_CAPTURE_TIMEOUT` / `self_serve_biometric_capture_timeout`), pipeline processing, and enrollment polling (`POLL_STATUS_COUNT * POLL_STATUS_INTERVAL` = up to 60s, times `RETRIES_COUNT` retries): [5](#0-4) [6](#0-5) 

This mirrors the reported bug class exactly: a time-window validity check (`operator_qr_expiration_time`, analogous to the `Buy` phase check) is performed only at request-issuance time (`scan_remaining_qr_codes`), while the operation that actually consumes/commits that validated state (`signup_post::request` inside `enroll_user::Plan::run`, analogous to `purchase()`) executes later without any re-check, after a variable and potentially long delay caused by asynchronous, difficulty-dependent processing (biometric capture + pipeline + polling).

### Impact Explanation
If the operator's QR-code validity window expires during the capture/pipeline/enrollment stages (e.g., because an operator's authorization was time-limited for a reason — session control, audit boundary, distributor rotation), the signup is nonetheless finalized and submitted to the backend still bound to that now-stale operator identity (`distributorId`) and included in the uploaded personal custody package/debug report. This is a cross-signup / cross-session identity-binding integrity issue: a signup can be misattributed to an operator identity that the orb's own configured expiration policy considers no longer valid, without any enforcement at the point where the binding is actually persisted (backend signup submission).

### Likelihood Explanation
The likelihood scales with signup duration: biometric capture, pipeline scoring, and the enrollment polling loop (up to `POLL_STATUS_COUNT * POLL_STATUS_INTERVAL` = 60s per retry, times `RETRIES_COUNT` = 3 retries) can push the actual submission well past the original freshness check, especially under slow network conditions (`signup_poll`/`signup_post` errors triggering retries) or slow pipeline processing. Because `operator_qr_expiration_time` is operator-configurable and no code path re-validates it after the initial scan, any deployment with an aggressive expiration setting relative to typical signup duration would trigger this deterministically.

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` immediately before the operator identity is committed/used — i.e., right before constructing `personal_custody_package::Credentials` and right before invoking `enroll_user::Plan::run`/`signup_post::request` in `do_signup`. If expired, abort the signup (fail closed) rather than submitting with a stale binding, consistent with how `scan_remaining_qr_codes` already treats expiration as invalidating the operator data at scan time.

### Proof of Concept
1. Configure a short `operator_qr_expiration_time` (e.g., a few seconds) relative to a normal signup duration.
2. Scan operator + user QR codes; `scan_remaining_qr_codes` passes because `operator_data.timestamp.elapsed() < operator_qr_expiration_time` at that instant (`src/plans/mod.rs:794-820`).
3. Proceed through `biometric_capture` → `biometric_pipeline` → `detect_fraud` → `enroll_user` (`src/plans/mod.rs:553-656`), which together can take well beyond `operator_qr_expiration_time` (enrollment polling alone allows up to 60s per attempt, `src/plans/enroll_user.rs:26-28,91-102`).
4. `enroll_user::Plan::run` calls `signup_post::request` using the original (now expired) `operator_qr_code.user_id` as `distributorId` (`src/backend/signup_post.rs:100-133`) — no expiration check is performed anywhere in this path.
5. The signup completes and is recorded against the stale operator identity, even though the orb's own policy (`operator_qr_expiration_time`) says that identity should no longer be trusted.
