### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC before dispatching it to the app's registered handler, but the HMAC only ever covers the raw request body. The `shop-domain` header — which is passed straight through to the handler as the authoritative tenant identifier — is never part of the signed material. The identity binding the developer implicitly relies on (`HMAC-valid request` ⇒ `shop header is trustworthy`) does not actually hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the (attacker-controllable, unsigned) `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a `Webhooks::Request` is the body only, and compares it against the `hmac-sha256` header using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately forwards `request.shop` — unauthenticated — to the app's handler as the tenant identity for the event: [4](#0-3) 

The broken identity equality is:
`bytes_verified_by_hmac (raw_body)` ≠ `identity_field_trusted_by_handler (shop-domain header)`

Because the `api_secret_key` is shared across every shop that has the app installed (it is not per-shop), any merchant who installs the app can generate arbitrarily many legitimately-HMAC-signed `(body, hmac)` pairs for their own shop (by triggering webhook events on their own store, e.g. `app/uninstalled`, `orders/create`, GDPR `shop/redact`, etc.). That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will succeed (it only checks the body against the secret, which the attacker already legitimately obtained a valid signature for), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an app built on this gem cannot distinguish "this event genuinely occurred on shop X" from "this event occurred on my own shop but I relabeled it as shop X." Depending on what the host app does with `WebhookMetadata#shop` (data lookups, session invalidation, GDPR redaction, deprovisioning on `app/uninstalled`), a malicious merchant can inject forged, cross-tenant events — e.g. forcing the app to treat a fabricated `app/uninstalled` or `shop/redact` payload as belonging to a victim shop, corrupting or deleting that victim's stored data/session. This is a cross-tenant access issue reachable by any unprivileged party who can install the app on a shop they control (no leaked credentials or privileged access required).

### Likelihood Explanation
Any developer/merchant able to install the app on a shop of their own can trivially generate valid `(body, hmac)` pairs by triggering webhook events (including uninstalling the app to get an `app/uninstalled` webhook, or a customer/shop GDPR webhook). No access token, `api_secret_key`, or account privilege beyond "can install the app" is required. The exploit is a simple HTTP replay with one header changed.

### Recommendation
Bind the `shop-domain` header into the value that is HMAC-verified, or otherwise independently authenticate it before trusting it downstream. Options:
- Include the `shop-domain` (and other identity-bearing headers such as `webhook-id`/`api-version`) in the signable string used for HMAC verification, if Shopify's webhook signing scheme supports it, or
- Cross-check `request.shop` against the shop associated with the session/store that owns the app installation before dispatching to the handler, and document clearly to gem consumers that `WebhookMetadata#shop` is **not** authenticated by the HMAC check alone.
- At minimum, update `Registry.process`/docs to warn that `request.shop` must be independently validated (e.g., against a known list of installed shops) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., uninstalls the app, or performs an action that fires `orders/create`), causing Shopify to POST a webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - body `B`
3. Attacker's own server (or a proxy they control in front of the real endpoint) intercepts/replays this exact request to the app's real webhook endpoint, but rewrites the header to:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - keeps the same body `B` and the same `x-shopify-hmac-sha256` value.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (per `lib/shopify_api/webhooks/request.rb#L35-38` and `lib/shopify_api/utils/hmac_validator.rb#L26-31`).
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb#L198-199`) and processes the attacker-controlled event as if it originated from the victim shop.
