### Title
Path traversal in Simplex `UiServer`'s static file handler via a bare `startsWith` root-prefix check - (File: `sdk/packages/simplex/src/services/server/static.ts`)

### Summary
`serveStatic()` guards path traversal by resolving the requested path and checking `requested.startsWith(root)`, the same class of bug the XWiki advisory describes (an HTTP-reachable static-file context that can be walked outside its intended directory to read arbitrary files on the host). This function is wired directly into every unauthenticated GET/HEAD request handled by Simplex's operator/setup dashboard.

### Finding Description
`serveStatic` resolves the requested URL against the configured UI dist directory and only checks that the resolved absolute path starts with the resolved root string: [1](#0-0) 

`String.prototype.startsWith` performs no path-separator boundary check, so any resolved path that merely shares the same string prefix as `root` — e.g. a sibling directory/file such as `<root>-something` or `<root>2` — passes the guard even though it lies outside the intended served directory. This is the canonical "prefix matching without a trailing separator" traversal bypass, and it is the exact mechanism the referenced XWiki advisory exploits: a static-resource context that is nominally confined to a webapp/asset directory but can be walked to arbitrary files reachable from the process (config, credentials, etc.).

The Simplex codebase itself documents this as an outstanding, unfixed weakness rather than a false positive: [2](#0-1) 

The vulnerable function is reached unauthenticated on every non-API GET/HEAD request: [3](#0-2) 

`UiServer` is explicitly documented as unauthenticated-by-design ("binding is the boundary"), and the CSRF/`X-Simplex-UI` header check only applies to non-GET/HEAD methods, so a plain `GET` — the method used for static file serving — bypasses that defense entirely: [4](#0-3) 

Any party able to reach this HTTP listener — the loopback port, a paired remote device over the tunnel, or (per the same changelog) a TCP-to-socket bridge — can therefore attempt to read files outside `uiDistDir` on the host running the Simplex intent filler.

### Impact Explanation
If a filesystem layout places any file or directory adjacent to `uiDistDir` whose name shares `uiDistDir`'s string prefix (e.g. `dist/ui-backup`, `dist/uiX`, or any directory created by packaging/install tooling with a similar name), an attacker reaching the UI server can read that file's contents, including potentially sensitive material accessible to the Simplex process (filler TOML config, signer material, SQLite activity/order databases) — a pure confidentiality impact, matching the referenced advisory's `C:H/I:N/A:N` profile. This is a CWE-284 improper-access-control class bug on the intent solver's own management surface.

### Likelihood Explanation
Exploitability depends on the operator's specific install/dist directory naming producing a prefix collision, so it is not universally triggerable out of the box; however, the guard is provably insufficient by construction (no separator check), the maintainers' own security-audit notes flag it as a known unresolved gap, and the reachable surface (unauthenticated GET on the operator/solver dashboard, including over the paired-device tunnel) makes it a realistic target once such a layout exists.

### Recommendation
Replace the `startsWith` check with a boundary-safe comparison, e.g. verify `requested === root || requested.startsWith(root + path.sep)`, or use `path.relative(root, requested)` and reject any result starting with `..` or being absolute.

### Proof of Concept
1. Configure `uiDistDir` to a path `X` and ensure a sibling path `X-secret/private.toml` exists on the host (e.g. via packaging layout or an attacker-influenced install path).
2. Send `GET /../X-secret/private.toml` (via a raw socket request, since browsers normalize `../`, as already done in the repo's own traversal test) to the Simplex `UiServer` listener.
3. `resolve(join(X, "../X-secret/private.toml"))` produces a path starting with the string `X-secret`, which still satisfies `requested.startsWith(root)` because `root === X` is a string prefix of `X-secret`, so the file's contents are returned instead of a 403. [5](#0-4)

export function serveStatic(res: ServerResponse, uiDistDir: string, urlPath: string): boolean {
	const root = resolve(uiDistDir)
	let decodedPath: string
	try {
		decodedPath = decodeURIComponent(urlPath)
	} catch {
		decodedPath = urlPath
	}
	const requested = resolve(join(root, decodedPath === "/" ? "index.html" : decodedPath))
	if (!requested.startsWith(root)) {
		res.writeHead(403, { "Content-Type": "text/plain" })
		res.end("Forbidden")
		return true
	}
