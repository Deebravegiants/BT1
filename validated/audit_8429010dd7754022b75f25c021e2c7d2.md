## Finding

### Title
Silent truncation in `convert_to_balance` permanently discards sub-unit value on every EVM→Substrate HyperFungibleToken transfer - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
`pallet-hyper-fungible-token`'s `convert_to_balance` performs an integer floor-division to scale an incoming ERC20 `U256` amount (18-decimal EVM precision, or whatever `erc_decimals` is configured) down to the pallet's local balance precision. Any fractional remainder below the local asset's smallest unit is silently dropped, on every single incoming transfer, with no dust-tracking, no minimum-transfer enforcement, and no path to ever credit the discarded remainder to anyone.

### Finding Description
`convert_to_balance` is defined as: [1](#0-0) 

It divides the raw `U256` value by `10^(erc_decimals - local_decimals)` using integer division, which floors. This function is invoked in two unprivileged, message-driven code paths:

1. `IsmpModule::on_accept` — the normal receive path for every incoming cross-chain transfer originated by burning/locking tokens on an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract: [2](#0-1) 

2. `IsmpModule::on_timeout` — the refund path when an outbound message from this chain times out, reusing the same conversion to recompute the refund amount: [3](#0-2) 

The registration/update extrinsics only enforce `erc_decimals >= local_decimals` (`ErcDecimalsBelowLocal`), guaranteeing the scale factor `10^(erc_decimals - local_decimals)` is a positive integer power of ten — but they enforce nothing about the *granularity* of amounts a peer EVM contract will actually send: [4](#0-3) 

For the `send()` direction (Substrate → EVM), the local amount is always an exact multiple of the local unit, so `convert_to_erc20` (a pure multiplication) is lossless and the resulting ERC20 amount is always an exact multiple of the scale factor: [5](#0-4) 

However, on the EVM side, `HyperFungibleToken.send()` burns an arbitrary `uint256 amount` chosen by the caller with no relation to any 10^n rounding rule — the ERC20 token's own decimals (typically 18) are the caller's native precision: [6](#0-5) 

Any caller can burn an amount on EVM that is *not* an exact multiple of `10^(erc_decimals - local_decimals)` (e.g. sending `100.0000015 TOKEN` at 18 decimals into a pallet asset with 6 local decimals), and the fractional remainder below the local unit is unconditionally floored away in `on_accept`/`on_timeout` with no accounting, no event, and no recovery mechanism — the dust is burned on the EVM side (real value destroyed there) but never minted/released on the Substrate side.

### Impact Explanation
This is the same rounding-truncation bug class as the referenced `OperationalStaking._sharesToTokens`/`_tokensToShares` finding: a floor-division conversion between two fixed-point representations of value, exercised by every unprivileged user transaction, that discards non-representable remainders. Here the effect is stronger than mere "balance drift" — it is a **permanent, unrecoverable loss of user funds** on every transfer whose EVM-side amount is not an exact multiple of the scale factor, with no dust ledger, no batching/sweep mechanism, and (for the native/custody asset model) a growing gap between the amount escrowed in `pallet_account()` on the destination and the true supply that should be redeemable, since `on_timeout` uses the identical lossy conversion to compute refunds — a timed-out transfer can refund strictly less than was actually escrowed for it if the amount wasn't a clean multiple. Across many users/transfers this compounds into a systemic backing/liability mismatch for the escrow model, and for the mint/burn model it is silent value destruction on every fractional transfer. This satisfies the "permanent freezing/loss of user funds" bar via a route any user can trigger with a single dispatched message.

### Likelihood Explanation
High likelihood of occurrence in practice: any deployer that registers a token with `erc_decimals > local_decimals` (the normal case, since EVM ERC20s are almost universally 18 decimals while Substrate balances are commonly 6–12 decimals) exposes this on every single transfer whose amount doesn't happen to be decimal-aligned. No special privileges, race conditions, or malicious actors are required — an ordinary user simply entering an amount with more precision than the local asset supports triggers permanent fund loss.

### Recommendation
- Reject (rather than silently floor) incoming amounts that are not an exact multiple of the scale factor in `on_accept`/`on_timeout`, or
- Track the truncated remainder per-beneficiary/per-asset and allow it to be swept/claimed once it accumulates to a full local unit, and
- Ensure `on_timeout` refunds are computed from the exact amount that was actually escrowed/burned at `send()` time (e.g., by carrying the local-denomination amount in the message or in local storage) rather than re-deriving it by re-flooring the ERC20 amount, so a timeout can never refund less than was actually locked.

### Proof of Concept
1. Deployer registers asset `X` with `local_decimals = 6` on Substrate and `erc_decimals = 18` for EVM chain `E` (passes the `ErcDecimalsBelowLocal` check since 18 ≥ 6).
2. A user calls `HyperFungibleToken(X_E).send()` on EVM with `amount = 1_000_000_000_000_000_001` (i.e., `1 token + 1 wei`), burning that exact amount on EVM: [7](#0-6) 
3. The message is delivered to `pallet-hyper-fungible-token::on_accept` on Substrate; `convert_to_balance(1_000_000_000_000_000_001, 18, 6)` computes `1_000_000_000_000_000_001 / 10^12 = 1_000_000` (floors), silently discarding the `1` wei worth of extra value: [1](#0-0) 
4. The beneficiary is minted/credited exactly `1_000_000` local units — the fractional wei is permanently gone; no event, error, or ledger entry records the loss, and nothing on either chain can ever recover it.
