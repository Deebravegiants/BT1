### Title
Plaintext Logging of Identity-Binding Data (`identity_commitment`) at INFO Level - ([File: src/backend/user_status.rs])

### Summary
`src/backend/user_status.rs` logs the entire `orb_qr_link::UserData` struct — including the user's `identity_commitment` and `self_custody_public_key` — at `INFO` level via `Debug` formatting, with no redaction. `DEFAULT_LOG_LEVEL` for the orb's logger is `"debug"` [1](#0-0) , meaning this statement executes and is persisted on every real, in-scope signup with the default runtime configuration.

### Finding Description
During QR-code validation for a signup, `user_status::request` logs the raw `authenticated_app_data` returned from the backend before it is destructured or used: [2](#0-1) 

The logged struct, `orb_qr_link::UserData`, is later destructured to extract `identity_commitment`, `self_custody_public_key` (`user_public_key`), `pcp_version`, `user_centric_signup`, and `orb_relay_app_id`: [3](#0-2) 

`identity_commitment` is the cryptographic identity-binding value tied to the signup (the value later verified against `user_data_hash` from the QR code, and the field ultimately mapped into `UserData.id_commitment` used throughout the signup pipeline): [4](#0-3) [5](#0-4) 

This is precisely the class of bug described in the external report: use of unstructured logging (`tracing::info!`/`Debug` formatting, analogous to `console.error`) of sensitive, user-derived identity data with no redaction, masking, or level-based restriction. There is no `#[cfg(...)]` gate around this call — unlike the QR-detection logs guarded behind `internal-data-acquisition`, this line runs unconditionally for every user in the normal signup flow.

### Impact Explanation
`identity_commitment` is the core value binding a specific human to a specific signup/enrollment session — it is the functional analog of a "who this biometric belongs to" pointer. Persisting it in plaintext application logs (which, per `src/logger.rs`, default to `debug` level and are written via `flexi_logger`/journald-style sinks) creates a durable, potentially exported record correlating QR-code sessions, orb devices, and identity commitments outside of the encrypted/backend-controlled channels the rest of the signup pipeline uses (e.g., `personal_custody_package.rs`, which deliberately salts and hashes equivalent identifiers before persisting them: [6](#0-5) ). If these logs are collected, shipped, or accessed outside the intended trust boundary (crash reports, log aggregation, debugging sessions), this enables cross-signup correlation/deanonymization of users — the kind of "cross-signup state bleed" / identity-binding disclosure the validation rules call out as acceptable impact.

### Likelihood Explanation
This code path executes on every valid QR-code/session-status response during normal, unprivileged user-facing signup activity — no attacker action or malicious peer/operator is required, and no feature flag gates it. Given `DEFAULT_LOG_LEVEL = "debug"`, `INFO`-level logs are emitted by default. The main uncertainty is the downstream retention/export policy of these logs (I was not able to find code in this repo that ships raw application logs off-device, e.g. to the backend or a third-party aggregator — only Datadog *metrics*, not log lines, were found being exported: [7](#0-6) ). Whether this data leaves the device depends on infrastructure outside this repository's scope.

### Recommendation
- Remove or redact the `tracing::info!("User QR-data: {user_data:?}");` statement; log only non-identifying fields (e.g., `pcp_version`, `user_centric_signup`) explicitly rather than the full struct via `Debug`.
- Avoid deriving/using `Debug` for structs containing `identity_commitment` or key material in any code path reachable at `INFO` or lower.
- Move any necessary diagnostic detail to `TRACE` level and ensure production log level defaults exclude it, or add a dedicated redaction step similar to the salting approach already used in `personal_custody_package.rs`.
- Audit other unconditional `tracing::info!("{...:?}")` calls that log full QR/user-data structs (e.g., `qr_code:?}` logs in `plans/mod.rs`, `backend/operator_status.rs`) for the same pattern.

### Proof of Concept
1. Run the orb-core signup flow with default logging configuration (`DEFAULT_LOG_LEVEL = "debug"`).
2. Complete a normal user QR-code scan such that `backend::user_status::request` receives a valid `Response` with `backend_keys` and `authenticated_app_data` populated.
3. Observe that `src/backend/user_status.rs:164` emits `INFO User QR-data: UserData { identity_commitment: "<value>", self_custody_public_key: "<value>", ... }` into the orb's log stream, with no redaction — exposing the identity commitment tied to that signup session in plaintext logs.
