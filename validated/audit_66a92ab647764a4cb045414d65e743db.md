### Title
`describeWithdrawal` misreports withdrawal status/txHash when a batch contains multiple withdrawals of the same PoA `assetId` - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome for a withdrawal by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which matches purely on `assetId` and ignores the `WithdrawalIdentifier.index`. When a single signed intent batches two `ft_withdraw` primitives for the same `assetId` (different `destinationAddress`), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` calls resolve to the identical first array element, so both indices get reported with the same status/`transfer_tx_hash` regardless of which withdrawal actually produced that hash.

### Finding Description
The broken equality: `STATUS_TRUTH(index=0)` should equal the outcome of withdrawal #0, and `STATUS_TRUTH(index=1)` should equal the outcome of withdrawal #1; these must differ when the two withdrawals have distinct `transfer_tx_hash` values. In the actual code: [1](#0-0) 

`describeWithdrawal` calls `getWithdrawalStatusWithRetry` (keyed by `args.tx.hash`, the shared NEAR tx hash of the batched intent) and then: [2](#0-1) 

`findMatchingWithdrawal` uses `Array.prototype.find` filtering only by `nep141:${w.data.near_token_id} === assetId`, with no use of `args.index`. The code comment on lines 409-417 explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported." For two same-`assetId` withdrawals in one batch, `createWithdrawalIdentifier` assigns them `index: 0` and `index: 1` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` lines 295-311), but since `args.tx.hash` is identical for both (same batched NEAR transaction) and `assetId` is identical, both calls to `describeWithdrawal` query the same status response and `find` returns the *same* first-matching entry in both cases — not the entry corresponding to the caller's actual `index`. If the indexer returns two `COMPLETED` records with different `transfer_tx_hash` in array order that does not match the intended index/amount ordering, both `index:0` and `index:1` calls report the identical `(status, txHash)` pair, which is provably wrong for at least one of them.

Existing guards do not prevent this: `supports()`, `validateAddress`, `compareAddresses`, and `validateWithdrawal` only validate individual withdrawal parameters and do not detect or reject duplicate-`assetId` withdrawals within a batch; there is no `assert` anywhere checking uniqueness of `assetId` across a batch's withdrawal identifiers.

### Impact Explanation
An integrator using `sdk.waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` over a batch containing two same-token PoA withdrawals to two different destination addresses receives a misreported `(status, txHash)` for at least one of the two `watchWithdrawal` calls — both resolve to the same underlying record. If the integrator uses the reported hash as proof of settlement per withdrawal (e.g., to release custody, mark an off-chain ledger entry as paid, or to reconcile with a bridge partner), it can credit/refund the wrong withdrawal or double-count a single actual transfer as evidence for two distinct withdrawals. This matches the "High" category: "a status or hash misreport making an integrator credit or refund twice." It is repeatable by any user who batches two withdrawals of the same PoA-supported token in a single signed intent to different destinations — no privileged access required.

### Likelihood Explanation
Preconditions: the PoA bridge indexer must return multiple `COMPLETED` (or otherwise distinct-status) records for the same `near_token_id` under one NEAR transaction hash, in an order that doesn't correspond to intended index ordering. This is a normal outcome of the indexer's response to a legitimate two-leg batch (not a malicious indexer) — the code comment itself states the API "doesn't currently support" disambiguating multiple withdrawals of the same token, which is the intrinsic limitation being exploited, not an attacker-crafted API response. Attacker cost is minimal: simply construct/sign an intent with two `ft_withdraw` primitives of the same PoA `assetId`, different destinations. This is fully repeatable per batch.

### Recommendation
`findMatchingWithdrawal` (and `describeWithdrawal`) must disambiguate withdrawals of the same `assetId` within a batch, e.g., by matching on amount (accounting for fee) in addition to `assetId`, or by sorting both the withdrawal params and the API's returned withdrawals by amount before pairing by position, as the code comment itself suggests. Until then, `PoaBridge.supports()` or the SDK's batch-construction path should reject/flag batches containing more than one withdrawal of the same `assetId`, so callers get an explicit unsupported-batch error rather than a silent misreport.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):

Mock `poaBridge.httpClient.getWithdrawalStatus` to return `{ withdrawals: [ { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_B" } }, { status: "COMPLETED", data: { near_token_id: "btc.omft.near", transfer_tx_hash: "TX_A" } } ] }` (unsorted; TX_A logically belongs to withdrawal index 0, TX_B to index 1).
2. Construct a `PoaBridge` instance with a valid `envConfig`.
3. Call `bridge.describeWithdrawal({ index: 0, withdrawalParams: { assetId: "nep141:btc.omft.near", ... }, tx: { hash: "SHARED_TX" }, landingChain })`.
4. Call `bridge.describeWithdrawal({ index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", ... }, tx: { hash: "SHARED_TX" }, landingChain })`.
5. Assert: `result0.txHash === result1.txHash === "TX_B"` (both calls return the identical first array match), proving the reported hash for index 0 does not equal the intended `TX_A` for withdrawal #0 — the equality `STATUS_TRUTH(index=0) == outcome(withdrawal #0)` is broken.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
