### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` cause per-index double-counting of `msg.value`, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
In `Hinkal.transact`, the balance-equation loop adds `msg.value` back into `balanceDif` independently for every array index whose `erc20TokenAddresses[i] == address(0)`, rather than once globally. Because `erc20TokenAddresses` (and its parallel arrays `amountChanges`, `onChainCreation`, `slippageValues`) have no uniqueness constraint, an attacker can list `address(0)` twice, use one index to back an on-chain UTXO created by `DepositOnChainUtxosExternalAction` and the other index to back an off-chain deposit (`amountChanges[j] > 0`), and satisfy both balance checks with a single ETH payment.

### Finding Description
The equality the code intends to enforce is: for each token `i`, `realBalanceDelta(token_i) == amountTerm(token_i) + utxoAmount(token_i)`, where `realBalanceDelta` reflects the *actual* net movement of that specific token caused by this transaction, counted exactly once.

For `address(0)` (ETH), because `msg.value` is credited to `address(this).balance` before the function body runs, `oldBalances[i]` (read at [1](#0-0) ) already includes the incoming ETH. The code compensates with: [2](#0-1) 

This compensation is correct *once per transaction*, but it is applied inside a loop over every entry of `circomData.erc20TokenAddresses`, and nothing prevents that array from containing `address(0)` more than once — `dimensionsCheck` in `HinkalHelper.sol` only checks array *lengths* match `dimensions.tokenNumber`, never uniqueness of the token addresses [3](#0-2) . `checkOnchainCreation` only constrains, per index, that `onChainCreation[i] == true` implies `amountChanges[i] == 0` and zero input nullifiers for that index [4](#0-3)  — it does not forbid two different indices both mapping to `address(0)`, one with `onChainCreation=true` and another with `onChainCreation=false, amountChanges>0`.

Since `oldBalances`/`newBalances` are single arrays computed once, before and after the external action call [5](#0-4) , any two indices `i` and `j` both equal to `address(0)` will read the identical balance snapshot. If no ETH is actually moved during the external action itself (as is the case for `DepositOnChainUtxosExternalAction`, which for the ETH leg never calls `transferERC20TokenFrom`/`transferETH` — it only does so for ERC20 tokens, see the `tokenAddress != address(0)` guard [6](#0-5) ), then `newBalances[i] == oldBalances[i]` for both indices, so:

```
balanceDif[i] = 0 + msg.value = msg.value
balanceDif[j] = 0 + msg.value = msg.value
```

Both are the *same* `msg.value`, yet checked independently against two separate accounting terms:
- Index `i` (`onChainCreation[i]=true`, `amountChanges[i]=0`): `require(balanceDif == 0 + utxoAmount)` → attacker sets the `DepositOnChainUtxosExternalAction` metadata so `utxoAmount == msg.value`, creating a real on-chain UTXO of that value.
- Index `j` (`onChainCreation[j]=false`, `amountChanges[j] = msg.value`): `require(balanceDif == amountChanges[j] + 0)` → satisfied because `amountChanges[j] == msg.value`. This is the "deposit" branch that the circuit's `inTotal + amountChanges === outTotal` constraint uses to justify minting new off-chain shielded output commitments of value `amountChanges[j]` at index `j` — the attacker supplies their own valid proof for this arithmetic relation since it's self-consistent (they control all circuit inputs for their own leaves).

Both `require` statements at [7](#0-6)  pass with a single `msg.value` payment, but the attacker receives *two* backed value terms: one on-chain UTXO worth `msg.value` (from `DepositOnChainUtxosExternalAction`) and one freshly minted off-chain shielded note worth `msg.value` (from the `amountChanges[j]` deposit branch encoded into the SNARK's public inputs and committed via `insertCommitments`). Net effect: attacker pays 1×ETH into the contract and walks away with 2×ETH of accounted shielded/on-chain value.

None of the existing guards catch this:
- `performHinkalChecks`/`dimensionsCheck` only validate array *lengths*, not that `erc20TokenAddresses` entries are unique.
- `checkOnchainCreation` validates per-index consistency (`onChainCreation[i]` implies `amountChanges[i]==0`) but is blind to cross-index duplication of the same underlying token.
- The circuit constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`) operate purely on the numeric relationship supplied per index and have no notion of ETH custody — they cannot detect that two different token-array slots refer to the same underlying asset and the same `msg.value`.
- `transferERC20TokenFromOrCheckETH`'s `require(msg.value == _value, ...)` check (used in `_internalTransact`, not in this external-action path) is not invoked here since `DepositOnChainUtxosExternalAction` never calls it for the ETH leg.

### Impact Explanation
An unprivileged attacker mints unbacked shielded/on-chain ETH value equal to their `msg.value` for every additional duplicate `address(0)` entry they add to `erc20TokenAddresses` (bounded by the maximum `tokenNumber` supported by the deployed verifier/circuit dimensions). This is direct protocol insolvency — shielded value is created without ETH backing it, matching the Critical severity category ("minting shielded value without backing"). The attack is fully repeatable by any address with the ability to generate a valid proof for their own leaves and can be scaled by increasing the number of duplicate `address(0)` slots up to the maximum array length allowed by the deployed verifier.

### Likelihood Explanation
Preconditions are minimal and fully within attacker control: they need to call `Hinkal.transact` with a `CircomData` where `erc20TokenAddresses` contains `address(0)` at least twice, one entry configured as an on-chain UTXO creation via `DepositOnChainUtxosExternalAction` (`onChainCreation[i]=true`, matching `utxoAmounts` metadata) and another entry as a normal off-chain deposit (`onChainCreation[j]=false`, `amountChanges[j]=msg.value`), and a self-generated valid SNARK proof for their own leaves (fully permitted for the attacker's own funds/UTXOs per the threat model). No relay, admin, or third-party cooperation is required, and the cost is exactly one legitimate deposit's worth of gas plus `msg.value` — the exploit is repeatable indefinitely.

### Recommendation
Deduplicate the `msg.value` compensation so it is applied at most once per transaction regardless of how many times `address(0)` appears in `erc20TokenAddresses` — e.g., track whether the ETH compensation has already been applied with a boolean flag, or require `erc20TokenAddresses` to contain unique entries (reject duplicates in `dimensionsCheck`/`performHinkalChecks`), and additionally enforce that `msg.value` exactly equals the sum of all positive ETH-backed terms (`amountChanges[i] > 0` for ETH plus `utxoAmount` for ETH-onChainCreation entries) once, globally, rather than per-index.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `DepositOnChainUtxosExternalAction` (registered as an allowed external action / recipient), and a verifier stub or use locally generated Groth16 proofs for a circuit build matching two token slots.
2. Construct `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`:
   - index 0: `onChainCreation[0] = true`, `amountChanges[0] = 0`, `inputNullifiers[0] = [0,...]`, external action metadata `utxoAmounts[0] = [1 ether]`.
   - index 1: `onChainCreation[1] = false`, `amountChanges[1] = 1 ether`, with valid `outCommitments[1]`/`encryptedOutputs[1]` and a matching proof satisfying `inTotal + amountChanges === outTotal` for that index (e.g., 0 inputs, one new 1-ether output commitment).
   - `slippageValues = [0, 1 ether]` (or values that satisfy `balanceDif >= slippageValues[i]`).
3. Call `Hinkal.transact{value: 1 ether}(a, b, c, dimensions, circomData)` from the attacker EOA.
4. Assert both `require` checks at [7](#0-6)  pass with a single `1 ether` `msg.value`.
5. Assert: `address(this).balance` increased by exactly `1 ether` (backing only one term), while the sum of value credited to the attacker — `onChainCommitments` UTXO of `1 ether` (from `DepositOnChainUtxosExternalAction`) **plus** the newly inserted off-chain commitment of `1 ether` at index 1 — equals `2 ether`. This demonstrates `mintedShieldedValue (2 ether) > ETH backing (1 ether)`, proving the equality `msg.value backing == exactly one accounting term` is violated.
