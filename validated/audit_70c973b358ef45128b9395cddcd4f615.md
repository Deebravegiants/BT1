### Title
Omni Bridge accepts Starknet zero-address (`0x0`) as a valid withdrawal destination, unlike other chains where the zero/burn address is explicitly rejected - (`packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
`validateStarknetAddress` only checks that the input matches `/^0x[a-fA-F0-9]{1,64}$/`, so `"0x0"` (and any other short felt) passes format validation and is treated as a spendable withdrawal destination. Unlike `validateEthAddress`, which explicitly special-cases and rejects the zero address (`0x00...00`) and burn address (`0x...dead`), no equivalent check exists for Starknet, and neither `OmniBridge.validateWithdrawal` nor `deriveOmniWithdrawIntentParams` add one before the address is embedded into the signed `ft_withdraw` intent.

### Finding Description
The broken equality is: *validated destination address* (any felt matching `0x[a-fA-F0-9]{1,64}`) should equal *a spendable, non-burn recipient address*, but for Starknet these are not equivalent.

- `validateStarknetAddress` at [1](#0-0)  accepts `"0x0"` because a single hex digit satisfies `{1,64}`. The project's own test suite documents this as intended ("Short addresses are valid (leading zeros omitted)") at [2](#0-1) .
- By contrast, the Ethereum-family validator in the same file explicitly blocks the zero address and the well-known burn address before delegating to `isAddress`: [3](#0-2) . No such carve-out exists for Starknet, revealing an inconsistency in the codebase's own security model for "unspendable" addresses.
- `OmniBridge.validateWithdrawal` calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` and only throws `InvalidDestinationAddressForWithdrawalError` if that returns `false` [4](#0-3) . The only other destination check in that function is `compareAddresses` against the destination-chain token address (unrelated to zero-address protection) [5](#0-4) .
- `deriveOmniWithdrawIntentParams` unconditionally builds `recipient = omniAddress(params.omniChainKind, destinationAddress)` from the raw input with no additional sanity check [6](#0-5) , and this `recipient` is what ends up in the signed `ft_withdraw` intent via `createWithdrawIntentsPrimitive`.

An attacker (an ordinary user, or an integrator forwarding a counterparty-supplied `destinationAddress`) simply supplies `destinationAddress = "0x0"` for a Starknet-bound Omni withdrawal. The call chain `sdk.createWithdrawalIntents → OmniBridge.validateWithdrawal → validateAddress → true → deriveOmniWithdrawIntentParams → omniAddress` produces a signed intent whose `msg.recipient` is the Starknet zero felt, with no guard preventing it.

### Impact Explanation
Funds debited from the user's intents balance are routed to the Starknet zero address in the signed `ft_withdraw` payload, with no path to recover them once the withdrawal settles — this matches the Critical category ("funds delivered to a wrong address/chain/contract with no recovery"). This affects any user or integrator-forwarded request specifying a Starknet destination via the Omni route, and is repeatable per withdrawal call.

### Likelihood Explanation
Preconditions are minimal: an Omni-routed withdrawal to Starknet where the token is supported and destination-token-address checks and min-amount checks pass — all achievable by an ordinary unprivileged caller supplying `destinationAddress = "0x0"` (or `"0x1"`, etc.) as a normal-looking value with no special privileges required. Cost to the attacker is nothing beyond a normal withdrawal request; the only "cost" is to whichever party's funds get routed to `0x0` (self-inflicted for a direct SDK user, or inflicted on the counterparty if an integrator blindly forwards attacker-supplied addresses).

### Recommendation
In `validateStarknetAddress` (`packages/intents-sdk/src/lib/validateAddress.ts`), reject the zero felt (and optionally other well-known burn addresses) analogous to `validateEthAddress`, e.g. explicitly disallow `"0x0"` and its zero-padded equivalents before accepting the regex match.

### Proof of Concept
Vitest plan (mocks only HTTP/RPC as needed by `OmniBridge`, no other mocking):
1. Call `validateAddress("0x0", Chains.Starknet)` directly and assert it returns `true` (documenting the format-only gap) — using `packages/intents-sdk/src/lib/validateAddress.ts`.
2. Construct an `OmniBridge` instance with a mocked `nearProvider`/`omniBridgeAPI` sufficient to pass `makeAssetInfo`/`getCachedDestinationTokenAddress`/`getCachedTokenDecimals` for a Starknet-bridged token, then call `validateWithdrawal({ assetId, amount, destinationAddress: "0x0", feeEstimation, routeConfig: { route: RouteEnum.OmniBridge, chain: Chains.Starknet } })` and assert it resolves (does **not** throw `InvalidDestinationAddressForWithdrawalError`).
3. Call `deriveOmniWithdrawIntentParams({ assetId, destinationAddress: "0x0", actualAmount, omniChainKind: ChainKind.Strk, intentsContract, feeEstimation })` and assert `result.recipient === omniAddress(ChainKind.Strk, "0x0")`, confirming the zero felt is embedded as `msg.recipient` in the eventual `ft_withdraw` intent.
