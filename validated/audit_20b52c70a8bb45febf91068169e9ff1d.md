### Title
Cache-key collision in `getCachedStorageDepositValue` lets one withdrawal's storage-deposit result be substituted for a different token/account pair, causing storage-deposit fees to be silently skipped - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naive string concatenation of `contractId` and `accountId` with no separator: `` `${contractId}${accountId}` ``. Because NEAR account IDs are built from `[a-z0-9-_]` segments separated by dots, two different `(contractId, accountId)` pairs can concatenate to the identical string (the split point between the two fields is ambiguous). This is analogous to the reported bug class: state that should be scoped to one entity (a specific token+destination pair, like the report's per-token `feeData`) is instead aliased/overwritten across a different entity, breaking the equality "the storage-deposit result used for withdrawal X is the result computed for withdrawal X" (i.e., the fee eligible/charged for a token+destination pair is not the one actually validated for that pair).

### Finding Description
`estimateWithdrawalFee` calls:
```
const [minStorageBalance, userStorageBalance] =
    await this.getCachedStorageDepositValue(
        tokenAccountId,
        args.withdrawalParams.destinationAddress,
    );
``` [1](#0-0) 

and the cache itself:
```

    accountId: string,

    if (cached !== undefined) {

    if (result[1] >= result[0]) {

``` [2](#0-1) 

Because `key = contractId + accountId` (no delimiter), two distinct pairs can collide, e.g. `contractId="usdc.near"`, `accountId="tkn.near"` (`key = "usdc.neartkn.near"`) versus `contractId="usdc.neart"`, `accountId="kn.near"` (`key = "usdc.neartkn.near"`). Both `"usdc.neart"` and `"kn.near"` and `"tkn.near"` are valid NEAR account IDs under the SDK's own validator (`ACCOUNT_ID_REGEX`, dot-separated `[a-z0-9-_]+` segments, 2-64 chars) [3](#0-2) , and this validator is what gates `assetId`/`destinationAddress` parsing (`parseDefuseAssetId` and `validateAddress`) before the cache is consulted [4](#0-3) [5](#0-4) .

`storageDepositCache` is an instance-level `LRUCache` shared by every call made through a given `DirectBridge`/SDK instance [6](#0-5) ; any long-lived server/backend process (typical SDK integration) processes withdrawals for many different users/tokens through the same instance, so a colliding pair triggered by one withdrawal poisons the result read by an unrelated, later withdrawal for the colliding pair.

The stored `[minStorageBalance, userStorageBalance]` result directly determines whether a storage-deposit fee is charged and passed through to intent construction:
```
if (minStorageBalance <= userStorageBalance) {
    return { amount: 0n, ..., storageDepositFee: 0n };
}
...
underlyingFees: { [RouteEnum.NearWithdrawal]: { storageDepositFee: feeAmount } }
``` [7](#0-6) 
and that `storageDepositFee` feeds `createWithdrawIntentPrimitive`'s `storage_deposit` field of the `ft_withdraw` intent:
```
storage_deposit:
    params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
``` [8](#0-7) 

Only the cache is only ever poisoned to the "sufficient balance" branch (`if (result[1] >= result[0])` gates the `set`) [9](#0-8) , meaning the exploitable direction is always "storageDepositFee wrongly reported as 0" for the real (colliding) pair, never an over-charge — the guard on `set` only stores results indicating the destination account already has sufficient storage, so a collision can only cause the real transfer to omit the required `storage_deposit` amount, not add a spurious one.

### Impact Explanation
When the real pair's `estimateWithdrawalFee` hits a poisoned cache entry from an unrelated colliding pair reporting sufficient storage balance, the SDK reports `storageDepositFee: 0` and omits `storage_deposit` from the `ft_withdraw` intent even though the actual destination account on the actual token contract does not have sufficient/any registered storage. On NEP-141 tokens that require storage registration (most standard implementations), the resulting `ft_transfer`/`ft_withdraw` receipt fails at the token contract because the receiver is not registered, causing the withdrawal to fail and requiring the integrator to notice the failure and manually retry with the correct storage deposit — i.e., a withdrawal that appears validated/priced by the SDK gets stuck until manual intervention, matching the "High" impact bucket ("a withdrawal stuck until manual intervention"). Because the affected withdrawal was reported as fully estimated/validated (fee = 0, no error thrown), an integrator relying on the SDK's `FeeEstimation`/`validateWithdrawal` result would proceed to sign and broadcast an intent that fails on-chain, without knowing beforehand that a storage deposit is actually required.

### Likelihood Explanation
Triggering requires only supplying two distinct nep141 `assetId`s / destination accounts to a shared long-lived `DirectBridge`/SDK instance where the concatenations of `contractId+accountId` collide - no privileged access, no signature or bridge-operator collusion needed. An attacker only needs to know (or predict) the contract ID / destination-account naming pattern used by the victim's withdrawal to craft a colliding pair (e.g. by choosing his own withdrawal's `assetId`/`destinationAddress` to alias a known/target token+account combination) and issue an estimate/withdrawal for it before the victim's request populates or reuses the cache. Realistically this requires the attacker to know exact strings, so likelihood is moderate rather than trivial, but the root cause is a straightforward deterministic string-concatenation collision, not any external trust assumption, so it is a genuine, reachable defect distinct from tests/DoS/rate-limit concerns.

### Recommendation
Use an unambiguous cache key that cannot collide across different `(contractId, accountId)` pairs, e.g. join with a delimiter that cannot appear in either NEAR account ID component, or use a structured key/tuple:
```ts
const key = `${contractId}:${accountId}`; // ':' is not a legal NEAR account-id character
```
or better, key by a `Map` keyed on `[contractId, accountId]` pairs, or JSON-encode the tuple. Apply the same review to any other cache keys built via string concatenation in the codebase to rule out similar aliasing.

### Proof of Concept
```ts
import { DirectBridge } from "packages/intents-sdk/src/bridges/direct-bridge/direct-bridge";

// Pair A: real user withdrawing "usdc.near" tokens to "tkn.near"
// Pair B: attacker-controlled withdrawal using "usdc.neart" tokens to "kn.near"
// Both concatenate to the same cache key: "usdc.neartkn.near"

const bridge = new DirectBridge({ envConfig, nearProvider });

// 1. Attacker triggers estimateWithdrawalFee for Pair B first, where the
//    attacker's own destination account ("kn.near") already has sufficient
//    storage balance for token "usdc.neart" (real, valid NEP-141 contract IDs
//    the attacker controls/knows), causing:
//    getCachedStorageDepositValue("usdc.neart", "kn.near")
//      -> key "usdc.neartkn.near" -> cached as [min, user>=min]
await bridge.estimateWithdrawalFee({
  withdrawalParams: {
    assetId: "nep141:usdc.neart",
    destinationAddress: "kn.near",
    routeConfig: createNearWithdrawalRoute(),
    amount: 1n,
  },
});

// 2. Victim later withdraws "usdc.near" to "tkn.near", where "tkn.near" has
//    NOT registered storage for "usdc.near". Same cache key is hit:
//    getCachedStorageDepositValue("usdc.near", "tkn.near")
//      -> key "usdc.neartkn.near" -> cache HIT returns Pair B's [min, sufficient]
const fee = await bridge.estimateWithdrawalFee({
  withdrawalParams: {
    assetId: "nep141:usdc.near",
    destinationAddress: "tkn.near",
    routeConfig: createNearWithdrawalRoute(),
    amount: 1_000_000n,
  },
});
// fee.underlyingFees[RouteEnum.NearWithdrawal].storageDepositFee === 0n
// even though "tkn.near" has no storage registered for "usdc.near".

// 3. createWithdrawalIntents() therefore omits storage_deposit from the
//    ft_withdraw intent, and the resulting NEAR transaction fails on-chain
//    at the token contract because the receiver lacks storage — the
//    withdrawal is stuck until manually retried with the correct deposit.
```
Note: exact collision requires the attacker to know/control valid NEP-141 contract IDs whose concatenation aliases the target pair; I was not able to execute this against a live NEAR RPC/token contract to confirm the exact on-chain revert behavior for a specific token, so the PoC demonstrates the cache-key collision and its propagation into `FeeEstimation`/intent construction in-code rather than an end-to-end on-chain failure trace.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}

export function parseDefuseAssetId(
	assetId: string,
): ParseDefuseAssetIdReturnType {
	const [tokenStandard, tokenContractId, multiTokenId] = assetId.split(":");

	assert(
		tokenContractId != null && validateNearAddress(tokenContractId),
		"Incorrect format of assetId",
	);

	switch (tokenStandard) {
		case "nep141":
			return {
				standard: "nep141",
				contractId: tokenContractId,
			};
		case "nep245": {
			assert(multiTokenId != null, "Incorrect NEP-245 token format");
			return {
				standard: "nep245",
				contractId: tokenContractId,
				tokenId: multiTokenId,
			};
		}
		default:
			assert(false, `Unsupported token standard: ${tokenStandard}`);
	}
