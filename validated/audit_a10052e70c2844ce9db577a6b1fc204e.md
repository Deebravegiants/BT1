### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `hmac` used for validation from the `shopify-hmac-sha256` header, but the value it signs (`to_signable_string`) is only the raw request body. The `shop` (tenant identity), `topic`, `webhook-id`, and `api-version` fields come from separate, unsigned HTTP headers and are never included in the HMAC-checked bytes. `ShopifyAPI::Webhooks::Registry.process` nonetheless trusts `request.shop` as the tenant identifier and forwards it directly to the app's handler. [1](#0-0) [2](#0-1) 

### Finding Description
The identity binding that should hold is:

`hmac-authenticated bytes == bytes that determine which shop/tenant the webhook is attributed to`

In `Request#to_signable_string`, only `@raw_body` is returned, so `Utils::HmacValidator.validate` (in `hmac_validator.rb`) verifies solely that the *body* was produced with the app's `client_secret`: [3](#0-2) [4](#0-3) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [5](#0-4) 

`Registry.process` validates the HMAC and then, without any further check that the header-derived `shop` corresponds to the shop whose secret actually produced the body/HMAC, passes `request.shop` on to the registered handler as `WebhookMetadata#shop`: [6](#0-5) 

Because the `shop-domain` header is outside the signed material, `computed_signature(body, secret) == received_signature` holds true regardless of what value is put in the `shop-domain` header. An attacker who can obtain any single valid (body, hmac) pair for the shared app secret — e.g., by installing the app on their own (attacker-owned, unprivileged) shop and receiving one legitimate webhook delivery — can resend that same body+hmac pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. HMAC validation still passes because it only checks the body bytes, and the handler receives attacker-controlled body data tagged with the victim's shop identity.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook processing: `shop` is used by host applications as the per-tenant key to route/persist data (order records, customer records, uninstall/redact triggers, etc.), yet it is never authenticated. An attacker can inject spoofed data attributed to a victim merchant's tenant into the app, a cross-tenant access/injection vulnerability with Critical severity per the given impact categories.

### Likelihood Explanation
Reachability is straightforward: any unprivileged actor able to install the app on a shop they control receives legitimate webhook deliveries whose (body, hmac) pairs remain valid forever (no timestamp/nonce binding shop identity into the signed payload), and the webhook endpoint is a public HTTP endpoint by design. No access token, `api_secret_key`, or privileged account is required — only reuse of a body/hmac pair the attacker legitimately received for their own tenant. Difficulty is low.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-supplied shop to the session/shop that installed the app (e.g., cross-check `request.shop` against a known/registered shop record before invoking handlers, or require the host application to validate that `shop` matches an existing authenticated session for that tenant before trusting `WebhookMetadata#shop`). Short term, document and enforce that consumers of `Registry.process`/`WebhookMetadata` must independently verify `shop` against their own tenant records rather than trusting it as authenticated by the HMAC check.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (no special privilege required — any Shopify merchant/developer can do this).
2. Shopify sends a legitimate webhook to the app, e.g. headers:
   ```
   x-shopify-topic: customers/create
   x-shopify-hmac-sha256: <valid hmac of body B>
   x-shopify-shop-domain: attacker.myshopify.com
   ```
   with body `B` (JSON containing attacker-controlled customer data).
3. Attacker replays the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate(request)` computes `HMAC(secret, B)` and compares to the received hmac — this still matches because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) never includes the shop header.
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's crafted body, causing the app to process attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
