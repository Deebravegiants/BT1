### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but `HmacValidator` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The tenant-identifying `shop` field is therefore never bound to the cryptographic signature that "proves" the webhook is authentic.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

while `shop` (and `topic`, `webhook_id`) are pulled straight from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the metadata handed to the app's handler, with no cross-check that the shop header matches anything covered by the signature: [4](#0-3) 

The equality the code implicitly assumes is: `shop header value == shop that produced/owns this signed body`. That equality is never enforced — the HMAC only proves "this body was signed with the app secret at some point," not "this body came from shop X." Any request whose body+HMAC pair is valid (for example, one legitimately delivered to the app for an attacker-controlled/attacker-installed shop) can be resubmitted with an arbitrary `shopify-shop-domain` header and will still pass `HmacValidator.validate`.

### Impact Explanation
An attacker who installs the app on their own store receives genuinely-signed webhook deliveries (body + valid HMAC) for that store. By replaying that exact body/HMAC pair against the app's webhook endpoint while substituting a different `shopify-shop-domain` header, they can make `ShopifyAPI::Webhooks::Registry.process` construct a `WebhookMetadata` object that attributes the (attacker-controlled) payload to an arbitrary victim shop. Any host application that uses `WebhookMetadata#shop` from this gem to scope data writes/lookups (the exact usage pattern this library is designed to enable) will process or persist attacker-controlled data under another tenant's identity — a cross-tenant data integrity breach with the app's own valid credentials as the delivery mechanism.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (an ordinary, unprivileged action available to any Shopify merchant/developer), and (2) the ability to send an arbitrary HTTP request to the app's webhook endpoint with a forged `shop-domain` header — both trivially available to any internet user, no `api_secret_key` or stolen token needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signed content, or otherwise cryptographically bind them to the verified body (e.g., derive/verify shop identity from a value that Shopify itself signs, or require the caller to pass an out-of-band verified shop from session/token context rather than trusting the header). At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as the sole tenant key without additional verification (e.g., cross-referencing against an active, stored session for that shop).

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; capture a real webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`) sent by Shopify to the app's webhook endpoint.
2. Resend the identical request to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so validation succeeds.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to associate attacker-supplied data with the victim tenant.
