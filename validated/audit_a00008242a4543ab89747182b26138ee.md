### Title
Unrestricted arbitrary calls in `EmporiumUpgradeable.runAction`'s stateless op loop allow theft of any residual/untracked ERC20 balance held by the Emporium contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` reconciles balances only for the tokens explicitly listed in the caller-chosen `circomData.erc20TokenAddresses` array. The "Stateless Interaction" branch of the ops loop lets the attacker's own `externalActionMetadata` invoke **any** `endpoint.call(callData)` with no whitelist beyond blocking the `callHinkalWallet`/`doSendToRelay` selectors. Any ERC20 balance the Emporium contract holds for a token *not* included in that transaction's `erc20TokenAddresses` array is completely invisible to the `balanceChange`/`handleOut` accounting, so it can be drained (via `transfer`/`approve`+`transferFrom`) by any unprivileged attacker who simply omits that token from their own `erc20TokenAddresses` list.

### Finding Description
The invariant that should hold is: *for every token that leaves the Emporium action in a transaction, that outflow equals `-deltaAmountChanges` Hinkal sent into the action for that token, reconciled via `balancesBefore`/`balancesAfter` and returned through `handleOut`*.

`runAction` only computes `balancesBefore`/`balancesAfter` for `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

That array is fully attacker-chosen calldata, part of the same `CircomData` the attacker submits for their own transaction. Meanwhile the ops loop performs raw external calls with attacker-controlled `endpoint`/`callData`/`value`, with essentially no restriction: [3](#0-2) 

`EmporiumStack`/`EmporiumOperation` (decoded straight from `externalActionMetadata`) place no constraint on `endpoint` being a token from `circomData.erc20TokenAddresses`, nor any allow-list of endpoints: [4](#0-3) 

The only gate on `runAction` itself is `onlyAllowedRecipient`, which just checks `msg.sender` is Hinkal (i.e. that the call is coming through the normal `Hinkal.transact -> _externalTransact -> IExternalActionV2.runAction` path), not that the *ops* it executes are restricted in any way: [5](#0-4) 

Root cause: because `EmporiumUpgradeable` is a single persistent contract shared by all users, any ERC20 (or ETH) balance it ends up holding for a token that is not part of a given transaction's `erc20TokenAddresses` set - e.g. dust/refunds left by multi-hop router swaps in a previous, unrelated transaction, a directly-sent (accidental) token transfer to the Emporium address, or an intermediate token used mid-swap that the attacker simply never lists - is invisible to that transaction's balance/slippage checks in both `EmporiumUpgradeable.runAction` and `Hinkal.transact`'s balance-diff/UTXO reconciliation: [6](#0-5) 

An unprivileged attacker exploits this by submitting a normal, otherwise-valid Hinkal transaction through the Emporium action whose `erc20TokenAddresses` array simply **omits** the token they intend to steal, and whose `EmporiumStack.ops` contains one extra "Stateless Interaction" entry: `endpoint = <victimToken>`, `callData = abi.encodeCall(IERC20.transfer, (attacker, EmporiumUpgradeable.balanceOf(<victimToken>)))` (or an `approve(attacker, type(uint256).max)` call to later `transferFrom` at will). Because `<victimToken>` is not in `circomData.erc20TokenAddresses`, none of the `balancesBefore[i]`/`balancesAfter[i]`, `balanceChange`, `handleOut`, or Hinkal's own `balanceDif`/`utxoAmount` checks ever look at it, so this arbitrary transfer/approval passes through with zero reverts, and the stolen tokens never need to appear in the returned `utxoSet` or be matched to any `deltaAmountChanges` entry.

### Impact Explanation
Any ERC20 balance that accumulates in the shared `EmporiumUpgradeable` contract outside of the specific token set a transaction declares (dust from swap slippage/refunds in prior unrelated transactions, mis-sent tokens, or intermediate-hop tokens from other users' swaps) can be permissionlessly and repeatedly stolen by any attacker, with no privileged role required. This is direct theft of value that legitimately belongs to the protocol/other shielded users and was never returned through the proper Hinkal UTXO/output path, matching the "Critical: direct theft of shielded or in-flight user funds" category. The attack is trivially repeatable every time residual balance appears (e.g., after every swap that leaves dust in a token outside the current transaction's declared token set) and costs the attacker only the gas for one extra crafted op.

### Likelihood Explanation
No special preconditions beyond the Emporium contract holding a nonzero balance of some token that a subsequent (or the same, for direct transfers) transaction does not declare in `erc20TokenAddresses`. Given Emporium is used generically for arbitrary DEX/router calls via `op.endpoint.call(...)`, non-zero dust/refund balances in unlisted tokens are a realistic and recurring occurrence. The attacker only needs to be able to submit an ordinary Hinkal/Emporium transaction (any unprivileged user can) with a crafted `externalActionMetadata`; no relay, admin, or victim cooperation is needed, making this highly feasible and repeatable.

### Recommendation
Restrict the "Stateless Interaction" (and ideally also the wallet-invoked) op endpoints/selectors to a governance-controlled allow-list (e.g., known DEX routers) and explicitly forbid calling `approve`/`transfer`/`transferFrom`-style selectors on arbitrary ERC20 contracts from within `runAction`. Additionally, enforce that any token balance change touched by op execution must correspond to an entry in `circomData.erc20TokenAddresses`, e.g. by snapshotting/settling balances for a superset of tokens the ops are permitted to interact with, or by disallowing `op.endpoint` from being an address the caller did not declare and settle in `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as the registered Emporium external action), a mock ERC20 `TokenX`, and register a mock DEX/router.
2. Seed a residual balance: have a first transaction (either a plain `TokenX.transfer(EmporiumUpgradeable, dust)` from an unrelated address, or a legitimate swap tx whose `erc20TokenAddresses` doesn't include `TokenX` but whose router call leaves `dust` of `TokenX` in Emporium) so `TokenX.balanceOf(EmporiumUpgradeable) == dust > 0`.
3. As the attacker (any EOA with their own shielded UTXO/proof, no special role), submit a normal `Hinkal.transact` call through the Emporium action whose `circomData.erc20TokenAddresses` array does **not** include `TokenX`, and whose `EmporiumStack.ops` contains one extra op: `endpoint = TokenX`, `invokeWallet = false`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, dust)`.
4. Assert the transaction succeeds (no revert from `BalanceChangeShouldBePositive`, slippage checks, or balance-diff checks in `Hinkal.transact`).
5. Assert `TokenX.balanceOf(attacker)` increased by `dust` while no corresponding entry for `TokenX` appears in the returned `utxoSet` and no `deltaAmountChanges` entry accounts for it - demonstrating tokens left the action without being tied to any `-deltaAmountChanges` Hinkal sent it in that transaction.
