### Title
Native-ETH escrow refunds/redemptions can be permanently frozen if the beneficiary rejects the transfer - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw`, used by every cross-chain escrow release path in the Intent Gateway (`RedeemEscrow`, `RefundEscrow`, same-chain cancel, cross-chain fill), sends native-ETH inputs with `_sendValue`, which reverts with `InsufficientNativeToken` when the recipient rejects the call. The beneficiary address is fixed inside the signed/committed order data (`order.user` for refunds, the filler for redemptions) and cannot be altered by whoever triggers the withdrawal, mirroring the reported "withdrawToken may not work" pattern where a hard-coded recipient that cannot accept the asset makes withdrawal permanently unreachable.

### Finding Description
`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` releases escrowed input/output tokens to a `beneficiary` decoded from the `WithdrawalRequest`: [1](#0-0) 

For native ETH (`token == address(0)`), the transfer goes through `_sendValue`, which reverts unconditionally if the low-level call fails: [2](#0-1) 

`_withdraw` is reached from `ExtrinsicIntents.onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain messages) and `onGetResponse` (source-chain cancel): [3](#0-2) 

and from `IntrinsicIntents._cancelSameChain`/fill paths for same-chain orders: [4](#0-3) 

In all of these paths the beneficiary is a value baked into the order/commitment (`order.user` for refunds, `msg.sender`/filler for fills) — none of the withdrawal entry points let the caller override it. If `order.user` (for a native-ETH-input order) is a smart contract without a payable `receive`/`fallback`, or one whose fallback deterministically reverts, then:
- Same-chain cancel: the user's own `cancelOrder()` call reverts — self-inflicted, low impact.
- Cross-chain refund/redeem (`onAccept`) and source-chain cancel (`onGetResponse`): the ISMP host's `EvmHost.dispatchIncoming` catches the revert, deletes the request receipt, and leaves the message "retryable" rather than reverting the whole batch: [5](#0-4) 

Because the message body (and thus the beneficiary) is fixed by the original commitment, every future retry of the exact same request replays the same failing transfer to the same non-accepting address — the escrowed native ETH can never be released. This is functionally identical to the reported bug class: a recipient that cannot receive the asset, combined with no mechanism to redirect or force the payout, permanently strands the funds in the contract.

### Impact Explanation
Native-ETH order inputs escrowed for a user (or protocol fee token, if it is ever native) whose `order.user` address is a contract that reverts on plain ETH transfers become permanently unrecoverable through the cross-chain refund/redeem flow, since `WithdrawalRequest.beneficiary` cannot be changed by anyone (not the relayer, not governance's `SweepDust`, which is scoped to protocol dust rather than a specific user's escrow). This is a permanent freezing of user funds — a Medium/High-severity impact per the ISMP handling design, which assumes failed `onAccept` calls are recoverable by retrying, but retrying cannot succeed when the failure is deterministic and tied to immutable order data.

### Likelihood Explanation
Any user (or an attacker griefing another party, e.g. setting `order.user` to a hostile contract, or a legitimate smart-contract wallet without a `receive()` function) placing a native-ETH-input order and later triggering a cross-chain cancel/refund would hit this. It requires no privileged access — an ordinary order placement plus a normal cross-chain cancellation (a message any relayer/user can trigger per the destination-cancel flow) is enough to reach the stuck state.

### Recommendation
For native-ETH payouts in `_withdraw`/`_sendValue`, do not let a failed push revert the whole withdrawal:
- Fall back to a pull-payment pattern (e.g., credit an internal balance the beneficiary can later withdraw with `IERC20`-style semantics or explicit `claim()`), or
- Wrap native ETH into WETH and transfer the ERC-20 when the raw ETH push fails (the same pattern already used in `WrappedHyperFungibleToken.onPostRequestTimeout`/`WrappedHyperFungibleTokenUpgradeable.onPostRequestTimeout`, which re-wrap and deliver WETH if the native push is rejected): [6](#0-5) 

This ensures the withdrawal always settles instead of remaining stuck on an unconditional low-level call revert tied to an immutable beneficiary.

### Proof of Concept
1. Deploy a malicious/non-payable smart-contract wallet `Bad` with no `receive()`/`fallback()`.
2. `Bad` (or an attacker on `Bad`'s behalf) places a cross-chain order via `placeOrder` with `order.user = address(Bad)` and a native-ETH input (`token == address(0)`), escrowing ETH in the source-chain `IntentGatewayV2`.
3. After the deadline, anyone calls `cancelOrder(order, ...)` from the destination chain (`ExtrinsicIntents._cancelFromDest`), which dispatches `RefundEscrow` back to the source chain via Hyperbridge.
4. The relayer delivers the `RefundEscrow` POST request; `ExtrinsicIntents.onAccept` decodes `WithdrawalRequest{beneficiary: order.user}` and calls `_withdraw`, which calls `_sendValue(address(Bad), amount)`.
5. `Bad`'s absent `receive()` makes the low-level call fail; `_sendValue` reverts with `InsufficientNativeToken()`; `EvmHost.dispatchIncoming` catches this, deletes the receipt, and the message stays "retryable."
6. Any subsequent delivery of the same `RefundEscrow` message replays the identical failing transfer to `address(Bad)` — the escrowed ETH remains locked in the gateway indefinitely, with no path (short of a contract upgrade) to redirect it to a receiving address.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);

            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
