### Title
Unauthenticated livestream TCP connection allows disclosure of victim's biometric camera frames to attacker - ([File: src/agents/livestream/mod.rs])

### Finding Description
The livestream agent's event loop handles `Event::Connected(addr)` by unconditionally creating a new `Downstream` bound to the connecting socket's IP and installing it as the active render target: `downstream = Some(Arc::new(Downstream::new(addr.ip())?))` [1](#0-0) . This `Event::Connected` is produced by `Upstream::poll_next`, which simply accepts any TCP connection on port 9201 with no authentication, token, or identity check whatsoever: `self.listener.poll_accept(cx)` followed by `Poll::Ready(Some(Ok(Event::Connected(addr))))` [2](#0-1) . Any client that connects replaces the previously active downstream target — there is no session/identity binding, no verification that the connecting peer is the operator who initiated the current signup. Once connected, every subsequent `Input::IrEyeFrame`/`Input::IrFaceFrame`/`Input::RgbFrame` received while a signup is in progress is rendered and pushed via `gpu.render(events, move |buffer| downstream.push(&buffer))` to whichever socket is currently registered as `downstream` [3](#0-2) [4](#0-3) . The `Downstream::new` implementation opens a raw UDP sink directly to the attacker-controlled IP on port 9200 with no credential exchange [5](#0-4) .

### Impact Explanation
Any network client that can reach TCP port 9201 on the Orb can hijack the livestream target mid-signup and receive raw IR eye/face and RGB camera frames of an unrelated, in-progress signup, without any authorization. This is a direct biometric data disclosure to an unauthenticated third party, matching the audited invariant "biometric secrets stay contained to the scanned user's session."

### Likelihood Explanation
The livestream feature must be compiled in (`feature = "livestream"`) and explicitly enabled via the `--livestream` CLI flag, which calls `orb.enable_livestream()?` [6](#0-5) . When enabled, exploitation requires nothing more than network reachability to port 9201 during an active signup — no credentials, no operator interaction, no hardware access — making it trivially repeatable whenever this diagnostic mode is active in a networked deployment.

### Recommendation
Require the `Upstream` TCP listener to perform mutual authentication (e.g., a shared secret/token established out-of-band with the operator's viewer client) before accepting `Event::Connected`, and bind the accepted downstream target to the specific signup/operator session rather than blindly trusting the connecting IP. Reject or ignore new connections that arrive while a different, still-authorized viewer session is active.

### Proof of Concept
Integration test: start the `livestream::Agent` with the `Upstream` listener bound to a test port; connect one TCP client (simulating the legitimate operator) to receive an `Event::Connected`; send `Input::IrEyeFrame` tagged with signup-A pixel data into the agent's port. While the frame is being rendered/pushed, open a second TCP connection from a different socket ("attacker") without any token; assert that this second connection now becomes `downstream` (verified via a second `Event::Connected` overriding the render target), and assert that subsequent UDP video packets sent by `Downstream::push` containing signup-A frame bytes are received on the attacker's UDP socket.
