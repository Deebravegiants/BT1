### Title
Rebasing/Deflationary Input Tokens Corrupt Shared Escrow Accounting in `IntentGatewayV2`, Permanently Freezing Other Orders' Funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder()` accepts **any** ERC20 address the user supplies as `order.inputs[i].token`, with no allow-list or token vetting [1](#0-0) . All escrowed balances for a given token are pooled in the single gateway contract, keyed only by `_orders[commitment][token]` accounting entries, not by segregated per-order reserves [2](#0-1) . If a rebasing or otherwise balance-decreasing token is used as the input for one order, a negative rebase after escrow shrinks the gateway's actual on-chain balance below the sum of `_orders[...][token]` owed to all outstanding orders denominated in that same token, exactly the "accounting system will break" bug class described in the external report.

### Finding Description
`placeOrder()` mitigates fee-on-transfer *deposits* by measuring `balanceOf` before/after the transfer and using the actual received amount as `order.inputs[i].amount` [3](#0-2) . This only protects the deposit-time snapshot; it does nothing about balance decreases that occur **after** escrow (e.g., a negative/elastic rebase of an Ampleforth-style token, or any token whose `balanceOf` can independently decrease while sitting in the gateway).

The redemption path, `_withdraw()`, never re-validates that the gateway's actual token balance still covers the accounted `_orders[commitment][token]` value. It simply decrements the stored ledger and calls `safeTransfer`:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
``` [4](#0-3) 

Because the gateway pools balances for the same token address across unrelated commitments/orders (there is no per-order token custody, only an internal ledger split by `commitment`), once one order's input token loses value while parked in the contract, the *sum* of all `_orders[...][token]` entries for that token can exceed the contract's real balance. Whichever order attempts `_withdraw`/release/cancel once the pool is depleted will have its `safeTransfer` revert, reverting the whole `onAccept`/`withdraw`/`cancel` call. This is the same failure mode as the original Venus report: the internal accounting assumes deposited balance can only stay flat or grow, and a `currentBalance < accountedBalance` case is never handled.

Unlike Venus (which enforces an internal governance guideline to bar such tokens from being listed), `IntentGatewayV2` is a **permissionless** protocol — any unprivileged user chooses the input token per order at `placeOrder()` time, so a single attacker-controlled or naturally rebasing ERC20 reaching this code path is sufficient to corrupt the shared ledger for every other legitimate order using the same token address.

### Impact Explanation
Once the pooled balance for a token falls short of the sum of outstanding `_orders[...][token]` entries:
- Legitimate solvers can no longer be paid via `withdraw()`/`_withdraw()` for any order sharing that token, since `safeTransfer` reverts and the entire settlement transaction (including the cross-chain `RedeemEscrow` `onAccept` call) fails.
- For cross-chain orders this blocks delivery of the settlement message permanently (it cannot be replayed successfully as long as the shortfall persists), which matches the "route unable to deliver messages" / permanent freezing of funds impact class.
- Users' escrowed principal for unrelated, otherwise-valid orders becomes permanently unrecoverable, since neither `withdraw` nor `cancel`/refund flows can move more tokens out than the contract actually holds.

This is a Medium/High severity issue: it doesn't let an attacker steal funds directly, but it can permanently freeze other users' and solvers' funds in the shared escrow pool by supplying a single malicious/rebasing token as an order input.

### Likelihood Explanation
Likelihood is moderate: it requires a token whose balance can decrease post-transfer while parked in the gateway (rebasing, token with admin-controlled negative rebasing, or a token with clawback/burn hooks). `placeOrder()` places no restriction on the token address supplied by the user [1](#0-0) , so any user (not a privileged admin) can trigger this by placing a single order with such a token — no governance or admin cooperation is required, satisfying the "single submitted transaction" reachability bar.

### Recommendation
- Before releasing escrow in `_withdraw()`, verify the gateway's actual `balanceOf(token)` still covers the requested `amount` (or the aggregate outstanding `_orders` for that token), and handle shortfalls explicitly (e.g., pro-rate, or revert with a distinguishable error rather than corrupting downstream orders).
- Consider tracking per-token global outstanding-escrow totals and reconciling them against `balanceOf` at both deposit and withdrawal time, similar to the recommended fix for `updateAssetsState()`, so a decrease is detected and attributed rather than silently causing insufficient-balance failures for unrelated orders.
- Alternatively, restrict `placeOrder`/`fillOrder` input/output tokens to a vetted allow-list (mirroring Venus's internal guideline) if pooled multi-order custody per token address is intended to continue.

### Proof of Concept
1. Attacker deploys/uses a rebasing ERC20 `RBT` where `balanceOf` can decrease for existing holders (e.g., simulate a negative rebase via `rebase(-X%)` callable by anyone or by design).
2. Attacker calls `placeOrder()` with `inputs[0] = {token: RBT, amount: 1000}`; the balance-diff at deposit records `_orders[commitment1][RBT] = 1000` (matches actual balance, e.g. all initial deposits pass the fee-on-transfer test path) [3](#0-2) .
3. A separate, legitimate user places another order using the same `RBT` token: `_orders[commitment2][RBT] = 500`. Gateway's actual `RBT.balanceOf(gateway) == 1500`.
4. The rebase triggers, shrinking `RBT.balanceOf(gateway)` to, say, `900` — well below the `1500` total owed across `_orders[commitment1][RBT]` and `_orders[commitment2][RBT]`.
5. `commitment1`'s order is filled/redeemed first and succeeds (`_withdraw` transfers `1000`... but only 900 exist, so actually whichever order attempts withdrawal first when balance < ledger reverts). Regardless of ordering, once total ledgered `> balanceOf`, the last order(s) to attempt `_withdraw()`/`onAccept(RedeemEscrow)` will revert on `safeTransfer`, permanently freezing that legitimate user's/solver's funds — this call cannot be made to succeed again since the token balance deficit is structural, not transient.
