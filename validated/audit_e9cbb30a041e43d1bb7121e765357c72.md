### Title
Unbounded loop via cyclic ancestry headers in GRANDPA `Chain::ancestry` causes consensus-verification DoS - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent-hash pointers through a relayer-supplied set of headers (`votes_ancestries`) with a plain `while current_hash != base` loop and no cycle detection or iteration bound. A relayer submitting a GRANDPA consensus proof can craft two or more headers whose `parent_hash` fields reference each other, forming a cycle disconnected from `base_hash`. When `finality_grandpa::validate_commit` (and the explicit per-precommit call in `verify_with_voter_set`) invokes `ancestry()` on such input, the loop never reaches `base` and never terminates, while `route` grows without bound — the same "circular reference with no termination condition" root cause as the liquidjs `{% block %}` DoS (GHSA-4rc3-7j7w-m548), just expressed as an iterative loop over an attacker-built cyclic graph instead of recursive template rendering.

### Finding Description
`AncestryChain::new` builds a `BTreeMap<H::Hash, H>` directly from the untrusted `votes_ancestries: Vec<H>` field of a `GrandpaJustification` [1](#0-0) . The `Chain::ancestry` implementation then walks `parent_hash` pointers from `block` to `base`:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
``` [2](#0-1) 

There is no `visited` set, no cap derived from `self.ancestry.len()`, and no depth limit. Because each header's hash is computed over its own encoded content (including whatever `parent_hash` value the attacker chooses), an attacker can construct two headers `A` and `B` where `A.parent_hash = hash(B)` and `B.parent_hash = hash(A)` — no hash collision is required, just self-consistent encoding. Once such a pair is included in `votes_ancestries` and one of them is reachable as a precommit target or via the "GHOST" ancestor search inside `finality_grandpa::validate_commit`, the `while` loop in `ancestry()` bounces between `A` and `B` forever: `current_hash` never equals `base`, and `route` grows without bound.

This is invoked from `GrandpaJustification::verify_with_voter_set`, which runs `finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain)` first (using this same `Chain` implementation internally) and then explicitly for each precommit target: `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` [3](#0-2) [4](#0-3) . `votes_ancestries` and the commit's precommits are entirely attacker-controlled fields of a GRANDPA consensus message submitted through the ISMP GRANDPA consensus client (`modules/ismp/clients/grandpa/src/consensus.rs`), which is reached via the unsigned `pallet_ismp::handle_unsigned` extrinsic path that any unprivileged relayer can submit.

### Impact Explanation
Verifying a crafted GRANDPA consensus proof drives the verifying node's block-execution/transaction-validation thread into an unterminated loop that also grows an unbounded `Vec<H::Hash>` in memory. Because consensus proof verification runs during runtime execution (and/or unsigned-extrinsic validation) on every node/collator that processes the transaction, this can hang or OOM-crash validators/collators processing the malicious extrinsic — a denial of service against the GRANDPA consensus-client route, which is one of the primary mechanisms by which state commitments are delivered into Hyperbridge (`pallet-ismp`). A stalled or crashed node on this path can render the route unable to deliver/verify messages, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
High. No signature checks or authority-set membership are required to build the cyclic header pair — an attacker only needs to control the encoded bytes of two headers so their `parent_hash` fields reference each other; this is pure data construction, not cryptographic forgery. The justification's commit/precommit signatures are checked, but a `GrandpaJustification` can be assembled by any relayer submitting `handle_unsigned`; the vulnerable code path (`AncestryChain::ancestry`) has no bound before or during the loop, and the entry point (parsing/decoding a submitted consensus message) does not reject a Vec<Header> containing header-hash cycles.

### Recommendation
Bound `AncestryChain::ancestry` by the size of the known header set and detect cycles explicitly: track visited hashes in a `BTreeSet`, and return `finality_grandpa::Error::NotDescendent` (or a dedicated error) as soon as a hash is revisited or once the number of hops exceeds `self.ancestry.len()`. Apply the same defensive bound pattern already used elsewhere in the codebase (e.g., the Pharos SPV `MAX_PROOF_DEPTH` guard and the call-decompressor's `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT`) to cap traversal depth up front.

### Proof of Concept
1. Construct header `B0` with an arbitrary parent hash `P0` (unrelated to `base_hash`).
2. Construct header `A` with `parent_hash = hash(B0-with-parent-set-to-hash(A))` — concretely, solve for a consistent pair `(A, B)` by fixing all other fields and setting:
   - `A.parent_hash = hash(B)`
   - `B.parent_hash = hash(A)`
   (Both hashes are simple deterministic hash-of-encoding computations, not preimage/collision attacks — the attacker freely chooses both headers' content.)
3. Include `A` and `B` in `votes_ancestries`, and craft one precommit whose `target_hash == hash(A)` (or otherwise reachable only through the `A`/`B` cycle), while `base_hash` is any other block not equal to `hash(A)` or `hash(B)`.
4. Submit the resulting `GrandpaJustification` as part of a GRANDPA consensus update message via the ISMP `handle_unsigned` extrinsic.
5. When `verify_with_voter_set` is executed, `finality_grandpa::validate_commit`/the explicit `ancestry_chain.ancestry(base_hash, hash(A))` call enters the `while current_hash != base` loop, which alternates `current_hash` between `hash(A)` and `hash(B)` forever, growing `route` without bound and never returning — hanging (and eventually exhausting memory on) the verifying node.
