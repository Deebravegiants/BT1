### Title
Webhook `shop` identity is trusted from an HTTP header that is not covered by the webhook HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used downstream by webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature verified by `Registry.process` only covers the raw request body. Any two fields can be freely mismatched by an attacker who controls the request headers, breaking the binding `hmac-verified bytes == identity used by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the (attacker-suppliable) `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cross-check against the signed body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry#process` validates the HMAC over that same `to_signable_string` (body-only) value and then unconditionally forwards `request.shop` to the app's handler as the trusted tenant identity: [3](#0-2) 

So the equality the gem is supposed to guarantee — "the shop this data is attributed to" == "the shop whose secret produced this HMAC" — does not hold. The HMAC only proves "this body byte-string was signed with the app's `client_secret`" (indirectly, since Shopify is the only other holder of the secret); it says nothing about which shop header accompanies it. `shop` is documented as a fully trusted identity field passed straight to the handler: [4](#0-3) 

### Impact Explanation
An attacker who can observe one legitimate (body, hmac) pair delivered to a multi-tenant app that installs this library for many shops (e.g., a merchant who is legitimately entitled to their own shop's webhook traffic, or anyone with read access to logs/proxies in front of the webhook endpoint) can replay that exact body+hmac to the app's public webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds because it only recomputes the signature over `@raw_body`, so `Registry.process` will invoke the app's handler believing the payload belongs to the attacker-chosen shop. This is a cross-tenant confused-deputy: data legitimately tied to shop A gets attributed to shop B inside the host application (e.g., inventory/order data written into shop B's tenant, side effects triggered against shop B), without ever needing shop B's credentials or the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires capturing one legitimate webhook body+signature pair (something an app-installing merchant naturally receives for their own shop) and resending it with a modified shop header to the app's public webhook route — no secrets, tokens, or privileged access to the target shop are required. This is a realistic, low-effort attack for any user of a multi-tenant Shopify app built on this gem.

### Recommendation
Include the tenant-identifying fields (at minimum `shop`, and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived `shop` value to the verified payload, so a valid HMAC cannot be replayed against a different shop identity.

### Proof of Concept
1. App AttackerCo installs the vulnerable app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. AttackerCo POSTs the same body `B` and same `H` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`, per `to_signable_string` returning `@raw_body`.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, causing the host app to process attacker-controlled/replayed data under `victim-shop`'s tenant identity.

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
