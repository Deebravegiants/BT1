### Title
Integer overflow in `Bonding._noFeeSwapInput`'s `Math.mulDiv` call permanently bricks `finalizeGraduation`, freezing curve-raised LT and the 250M LP reserve - ([File: packages/contracts/src/Bonding.sol])

### Summary
The CVE class is a crafted-input-driven overflow/corruption inside a "finalize"-style routine that a remote party can trigger to cause a Denial of Service. The direct analog in alt.fun is `Bonding._noFeeSwapInput`, called from the hostile-pre-seed rebalance path inside `finalizeGraduation` (Phase 2 of graduation). A crafted pre-seed of the HyperSwap V2 pair combined with a curve whose `ltFromPair`/`tokensForLP` ratio is attacker-steerable can drive the unguarded multiplication inside `Math.mulDiv` past `uint256` capacity, causing an unconditional revert that permanently bricks graduation for that token.

### Finding Description
`_noFeeSwapInput` computes the swap size needed to rebalance a hostile mint pre-seed toward the curve-close ratio: [1](#0-0) 

```solidity
function _noFeeSwapInput(
    uint256 reserveIn,
    uint256 reserveOut,
    uint256 targetN,
    uint256 targetD,
    uint256 maxSwap
) internal pure returns (uint256) {
    if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
        return 0;
    }
    uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
    ...
```

The natspec claims the intermediate `reserveIn * reserveOut * targetN` stays inside `Math.mulDiv`'s 512-bit working space, but `reserveIn * reserveOut` is evaluated as a **plain `uint256` multiplication before `Math.mulDiv` is even called** — only the *second* multiplication (`product * targetN`) benefits from the 512-bit widening, and the **final division result must still fit in 256 bits or `Math.mulDiv` reverts** (OpenZeppelin's `mulDiv` reverts on overflow rather than truncating).

`reserveIn`/`reserveOut` come directly from the attacker-controlled HyperSwap V2 pair reserves (Regime 3, "mint pre-seed") [2](#0-1) , and are `uint112`-bounded (~5.19e33). `targetN`/`targetD` are `tokensForLP`/`ltFromPair` (or their reciprocal), which are curve-economics-derived and can be made extremely small relative to `LP_RESERVE` when a malicious creator pairs the launch with an LT whose `exchangeRate()` is engineered to be very high, shrinking `virtualLtReserve = VIRTUAL_LIQUIDITY_USD*1e18/exchangeRate` (and therefore the real LT needed to cross the USD graduation threshold) down to a handful of wei: [3](#0-2) 

With `targetD` (e.g. `ltFromPair`) pushed to single-digit wei while the attacker pre-seeds the pair with reserves near the `uint112` ceiling, `product * targetN / targetD` overflows `uint256`, and `Math.mulDiv` reverts. This call is unconditional — it runs before `maxSwap`/`_swapBudget` capping is even applied — so none of the documented "brick resistance" mitigations (`_swapBudget`, the `DIRECT_MINT_PRESEED_BPS` band, the `_pairRebalance` false-return fallback) intercept it: [4](#0-3) 

The revert propagates unhandled through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`: [5](#0-4) 

Because `_enterGraduating` already flipped `lifecycle` to `Graduating` and froze trading, and `finalizeGraduation` is the only path back to `Lifecycle.Graduated`, a permanently-reverting `finalizeGraduation` leaves the token stuck in `Graduating` forever.

### Impact Explanation
This is a permanent freeze of funds: the curve-raised LT (`ltFromPair`, transferred out of `Pair` via `Router.graduate` during Phase 1) and the 250M `LP_RESERVE` tokens parked on `Bonding` between phases become permanently unrecoverable — there is no admin rescue path for a `Graduating`-stuck token, and trading is frozen so LP/creator/trader funds cannot be withdrawn either. This matches the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
Reachable end-to-end by unprivileged actors using only in-scope entry points: `Zap.createToken` (to pick/launch against a high-`exchangeRate` LT and shrink `virtualLtReserve`), ordinary curve buys to reach graduation with a minimal `ltFromPair`, and a permissionless HyperSwap V2 `factory.createPair` + `transfer` + `pair.mint` pre-seed (the documented Regime-3 attack surface) sized to push `reserveIn * reserveOut * targetN / targetD` past `uint256`. No privileged role, upgrade, or off-chain component is required.

### Recommendation
Compute `reserveIn * reserveOut` using `Math.mulDiv`'s full-precision path (e.g., `Math.mulDiv(reserveIn, reserveOut, 1)` intermediate held as a 512-bit value combined with `targetN`/`targetD` in a single safe fixed-point helper, or reorder operations to divide before multiplying where safe), and add an explicit fallback (matching the existing `_pairRebalance` false-return / `_seedDirectMint` pattern) for the case where the ratio computation would overflow, so `finalizeGraduation` truly can never revert regardless of pre-seed shape, consistent with the documented invariant.

### Proof of Concept
1. Creator calls `Zap.createToken` pairing the new token with an LT whose `exchangeRate()` is chosen/engineered to be extremely high, so `virtualLtReserve = VIRTUAL_LIQUIDITY_USD * 1e18 / exchangeRate` rounds to a very small value (bounded above only by `ExchangeRateTooLow`, not below).
2. Buy the curve to the point the USD graduation trigger fires with `ltFromPair` (real LT raised) reduced to a tiny wei value while `tokensForLP` remains sizeable relative to it, flipping lifecycle to `Graduating` via `_enterGraduating`.
3. Before `finalizeGraduation` is called, front-run: `IUniswapV2Factory.createPair(token, lt)`, then `transfer` large `token`/`lt` amounts to the pair (sized near the `uint112` reserve ceiling) and call `pair.mint(attacker)` to land in Regime 3.
4. Call (or let the keeper call) `finalizeGraduation(token)`. `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput` computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` where the division result exceeds `uint256`, causing `Math.mulDiv` to revert; the revert is unhandled and `finalizeGraduation` reverts every time it is called, permanently stranding the token in `Lifecycle.Graduating`.

        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);

        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);

        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
