Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` implements wildcard CORS origin matching (e.g. `https://*.ethereum.org`) using an unanchored `strings.HasSuffix(originHost, allowedHost)` check that does not enforce a domain-label boundary. An attacker who registers any domain that merely ends with the configured suffix string (e.g. `evil-ethereum.org` against a `*.ethereum.org` rule) is incorrectly treated as an allow-listed origin, even though it is not a genuine subdomain.

## Finding Description
`isAllowedOrigin` parses the `Origin` header and each configured `CORSAllowedOrigins` entry into scheme/host/port. For wildcard entries it strips the `*.` prefix and performs `strings.HasSuffix(originHost, allowedHost)` with no check that the character preceding the matched suffix is a `.` boundary: [1](#0-0) . This allows any string suffix match — not just true DNS subdomains — to pass. `handleRequest` then reflects the attacker-controlled `Origin` value directly into `Access-Control-Allow-Origin` (plus `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`) whenever `CORSEnabled` and `isAllowedOrigin` return true: [2](#0-1) . The existing test suite only exercises non-matching cases like `ethereum.remix.org`, wrong scheme, or missing port, and never a same-suffix-but-different-domain case such as `evil-ethereum.org`, leaving this gap unverified: [3](#0-2) .

## Impact Explanation
This is a concrete allowlist-bypass affecting the internet-facing Gateway HTTP server that fronts JSON-RPC handlers for the DON/capabilities gateway. When an operator configures a wildcard CORS entry (a supported, documented pattern per `CORSAllowedOrigins` config and sample configs), an attacker-registered domain that merely shares a string suffix with the intended trusted domain will be granted CORS trust it should not have, letting the attacker's web page read cross-origin gateway responses and issue authorized-looking preflighted requests from a victim's browser. This weakens the operator-configured origin restriction, matching the in-scope "allowlist ... bypass" impact category for the gateway.

## Likelihood Explanation
Exploitation requires only that the operator has enabled `CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins`, and that the attacker registers/controls a domain string ending in the configured suffix — both trivially achievable by an unauthenticated remote actor with no prior access to the gateway or its credentials. The bug is purely a header-controlled server-side string comparison, requiring no social engineering, admin access, or special privileges.

## Recommendation
Anchor the wildcard match to a domain-label boundary in `isAllowedOrigin`, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
Add regression tests covering non-subdomain suffix collisions (e.g., `evil-ethereum.org` vs. `*.ethereum.org`) to ensure they are rejected.

## Proof of Concept
1. Start the gateway HTTP server with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"https://*.ethereum.org"}`.
2. Send a request to the gateway's configured path with header `Origin: https://evil-ethereum.org`.
3. Observe the response contains `Access-Control-Allow-Origin: https://evil-ethereum.org`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers`, despite `evil-ethereum.org` not being a subdomain of `ethereum.org`.
4. This can be codified as a Go unit test in `core/services/gateway/network/httpserver_test.go` analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, asserting that `evil-ethereum.org` is currently (incorrectly) accepted, then verifying the fix rejects it.

	if s.config.CORSEnabled {
