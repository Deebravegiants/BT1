### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the byte content of the body. The `shop` (from `X-Shopify-Shop-Domain`), `topic`, and `webhook_id` used downstream to attribute the webhook to a tenant are taken straight from unauthenticated HTTP headers and are never bound into the HMAC computation.

### Finding Description
The intended binding is: `hmac == HMAC(secret, shop ‖ topic ‖ body)` for the same `shop` value that the handler subsequently trusts. Instead the actual binding implemented is `hmac == HMAC(secret, body)` only, while `Registry.process` reads `request.shop` from the header and forwards it, unauthenticated, into `WebhookMetadata` given to the app's handler.

`Request#shop`, `#topic`, and `#webhook_id` are all pulled from `shopify_header`, i.e. plain incoming HTTP headers with no cryptographic tie to the signed payload: [6](#0-5) 

`to_signable_string` only returns the raw body: [2](#0-1) 

`Registry.process` validates only that signature, then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [3](#0-2) 

`HmacValidator.validate_signature` computes the digest purely from `to_signable_string`, so it can never detect a header substitution: [4](#0-3) 

Because a single app has one shared `api_secret_key` across every merchant that installs it, any party that receives one genuine, HMAC-signed webhook delivery for their own store (which they legitimately can, simply by installing the app on a shop they control) possesses a `(raw_body, hmac)` pair that is valid under the app's secret regardless of which shop it is replayed as. Replaying that exact body/hmac pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim merchant passes `HmacValidator.validate` unchanged, because the header is outside the signed content. The gem's own documented usage pattern amplifies this because apps are told to trust `data.shop` as the tenant key without any further verification: [7](#0-6) 

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically-verified content (the body) and the value (`shop`) an integrating app uses to route/attribute that content to a specific merchant's data/session. An attacker who is a legitimate, unprivileged installer of the app on their own shop can make the app process attacker-controlled webhook content while attributing it to an arbitrary victim shop, achieving cross-tenant data confusion/injection through the app's webhook-processing pipeline — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem that follows the documented pattern (using `data.shop` to key persisted state, e.g. `shop_domain: data.shop` as shown in the gem's own docs) without independently re-verifying that the delivering shop matches an authorized session for that shop. The only prerequisite is that the attacker can install the target app on a shop they control (a normal, unprivileged action), then capture and replay one real webhook delivery with a modified shop header — no access token, `client_secret`, or privileged credential is required.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header claims to the signed body, e.g. by including the shop domain in `to_signable_string` (matching Shopify's documented webhook verification which authenticates the header value itself), or by requiring the app to independently confirm that `request.shop` corresponds to a shop for which the app holds an active, previously-established session before trusting the payload as belonging to that shop:

```ruby
# lib/shopify_api/webhooks/request.rb
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```
Document clearly that `data.shop` must not be trusted as tenant-authoritative unless the app cross-checks it against a known, previously authorized session for that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (a normal, unprivileged OAuth install using the app's public install flow).
2. Shopify delivers a real webhook (e.g. `orders/create`) to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON `raw_body`.
3. Attacker replays the exact same `raw_body` (and thus the exact same valid `X-Shopify-Hmac-Sha256`) to the app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, raw_body)` — unchanged and still valid — then invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker-controlled JSON> ...)`.
5. The app processes attacker-controlled data as if it belongs to `victim.myshopify.com`, per the documented handler pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`.
