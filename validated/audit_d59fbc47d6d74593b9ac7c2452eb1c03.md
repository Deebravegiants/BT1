### Title
Protocol fee silently stranded (permanently frozen) in `ExternalActionSwap` when a transaction is self-relayed - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
The external report criticizes LI.FI's `FeeCollector` for being invoked out-of-band via a crafted multicall (`_executeAndCheckSwaps()`), meaning fees can be skipped entirely if a caller bypasses the frontend. Hinkal does not reuse that pattern — its swap fee logic is baked directly into `ExternalActionSwap.swap()` and the `feeStructure` is cryptographically bound to the transaction via `calldataHash` [1](#0-0) , so the LI.FI-style "fee call is optional" bypass has no analog here. However, investigating the fee-payment code path in the same file surfaced a genuine, in-scope defect: when a transaction has no relay (`circomData.relay == address(0)`), the protocol's own `hinkalFee` is computed and deducted from the amount returned to the user, but is never actually transferred anywhere — it is permanently stuck in the `ExternalActionSwap`/`LifiExternalAction` contract.

### Finding Description
In `swap()`, `hinkalFee` is always computed from the swapped output regardless of whether a relay is used: [2](#0-1) 

The fee is "paid" only through `sendToRelay(circomData.relay, ..., token)`, and `sendToRelay` is a strict no-op when `relay == address(0)`: [3](#0-2) 

Despite this no-op, `totalFee` (which includes `hinkalFee`) is still subtracted before computing `amountToSendToHinkal`, which is the only amount forwarded back to `msg.sender` (the `Hinkal` contract, on to the user's UTXO): [4](#0-3) 

The difference (`hinkalFee`, and `relayFee` too if `feeStructure.feeToken != outputToken`) therefore remains in the `ExternalActionSwap`/`LifiExternalAction` contract's own token balance. `ExternalActionBaseV2` (the shared base for these external actions) exposes no rescue/withdraw/sweep function for the owner to recover such stranded tokens: [5](#0-4) 

Nothing in `Hinkal.transact()`'s balance-diff/slippage check catches this, since it only checks that the amount actually credited back to Hinkal is consistent with the UTXO created — it has no visibility into whether the fee that was subtracted actually reached a relay.

### Impact Explanation
Any swap transaction executed without a relay (`relay == address(0)`, i.e., self-relayed by the user directly) silently loses the computed `hinkalFee` (and potentially `relayFee` when fee token differs from output token) into the external-action contract's balance with no path to recovery. This is a permanent freezing of protocol fee value — funds that the user paid (in the sense that they never receive them back as a UTXO) but that also never reach any beneficiary (relay or protocol treasury). Over the life of the protocol, this can accumulate stuck ERC20/ETH balances in `ExternalActionSwap`/`LifiExternalAction` with no owner-facing extraction mechanism found in scope.

### Likelihood Explanation
High — this occurs on the ordinary and expected "self-relay" code path (`relay == address(0)`), which is explicitly supported elsewhere in the codebase (`_internalTransact` in `Hinkal.sol` explicitly allows and handles `relay == address(0)` as a normal, fee-free case). Any user or integrator submitting a swap without a relay hits this path deterministically, not via an edge case or attacker-crafted input.

### Recommendation
- When `circomData.relay == address(0)`, either do not deduct `hinkalFee`/`relayFee` from `amountToSendToHinkal` at all, or route the fee to an explicit protocol treasury address instead of relying solely on `sendToRelay`'s relay-gated no-op.
- Add a rescue/sweep function (restricted to owner/governance) on `ExternalActionSwap`/`ExternalActionBaseV2` to recover any tokens accidentally stranded in these action contracts.

### Proof of Concept
1. User submits a valid `transact()` call whose `externalActionData.externalActionId` routes to `LifiExternalAction`, with `circomData.relay = address(0)` and `feeStructure.variableRate > 0`.
2. `Hinkal._externalTransact` forwards to `LifiExternalAction.runAction` → `ExternalActionSwap.swap()`.
3. `callRouter` performs the LI.FI swap, producing `swappedAmount` of `outputToken` held by the action contract.
4. `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, variableRate)` is computed and non-zero.
5. `sendToRelay(address(0), hinkalFee, outputToken)` no-ops (per `Transferer.sendToRelay`'s `relay != address(0)` guard) — no transfer occurs.
6. `amountToSendToHinkal = swappedAmount - totalFee` is sent to `Hinkal`; the `hinkalFee` amount remains permanently in `ExternalActionSwap`'s token balance, unreachable by any exposed function.

import {CircomData} from "../types/CircomData.sol";
import {UTXO} from "../types/UTXO.sol";
import {IExternalActionV2} from "../types/IExternalActionV2.sol";
import {OwnerHinkal} from "../OwnerHinkal.sol";

abstract contract ExternalActionBaseV2 is IExternalActionV2, OwnerHinkal {
    mapping(address => bool) internal isAllowedRecipient;

    /*
     * @dev Modifier to check if the sender is allowed to call the action
     * @dev Used to handle VolatileTokenAction and Hinkal interactions
     */
    modifier onlyAllowedRecipient() {
        require(
            isAllowedRecipient[msg.sender],
            "ExternalActionBase: sender not allowed"
        );
        _;
    }

    constructor(address[] memory _allowedRecipients) {
        for (uint i = 0; i < _allowedRecipients.length; i++) {
            isAllowedRecipient[_allowedRecipients[i]] = true;
        }
    }

    function setAllowedRecipients(
        address[] calldata recipients
    ) external onlyOwner {
        for (uint i = 0; i < recipients.length; i++) {
            require(recipients[i] != address(0), "zero address!");
            isAllowedRecipient[recipients[i]] = true;
        }
    }

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external virtual returns (UTXO[] memory utxoSet) {}
}
