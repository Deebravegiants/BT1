This confirms the DoS vector: `handlePostRequestTimeouts` and `handleGetRequestTimeouts` iterate over a batch of timeouts in a single transaction and call `host.dispatchTimeOut(...)` for each entry without any try/catch, meaning a single reverting iteration reverts the entire batch [1](#0-0) [2](#0-1) . Inside `EvmHost.dispatchTimeOut`, if the module callback succeeds, the fee refund is sent unconditionally via `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` with no zero-address check [3](#0-2) . `meta.sender` is `FeeMetadata.sender`, which is set from `post.payer`, a value the dispatching contract/EOA fully controls when calling `dispatch(DispatchPost)` [4](#0-3) .

### Title
Zero-address `FeeMetadata.sender` (payer) can DoS the entire batched `dispatchTimeOut` path in `HandlerV2`/`EvmHost` - (File: evm/src/core/EvmHost.sol, evm/src/core/HandlerV2.sol)

### Summary
An unprivileged dispatcher can set `post.payer = address(0)` on a POST request. If that request times out and `onPostRequestTimeout` succeeds on the destination-side module, `EvmHost.dispatchTimeOut` unconditionally attempts `feeToken().safeTransfer(address(0), meta.fee)`. If `feeToken()` reverts on transfers to the zero address (e.g., USDC-style tokens), this call reverts the surrounding `dispatchTimeOut`, and because `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` invoke `dispatchTimeOut` in a loop with no isolation (no try/catch), the entire batched timeout-processing transaction reverts — blocking timeout settlement for every other, unrelated request bundled in that same relayer submission.

### Finding Description
`EvmHost.dispatch(DispatchPost)` stores `FeeMetadata({sender: post.payer, fee: post.fee})` keyed by the request commitment, with `post.payer` taken directly from caller-supplied calldata and never validated against `address(0)` [4](#0-3) .

When that request later times out, `HandlerV2.handlePostRequestTimeouts` verifies the non-membership proof for each timed-out request in a batch, then calls `host.dispatchTimeOut(...)` for each one inside an unguarded `for` loop [1](#0-0) . The same pattern exists for GET timeouts in `handleGetRequestTimeouts` [2](#0-1) .

`EvmHost.dispatchTimeOut` calls the source module's `onPostRequestTimeout`; if that succeeds, it refunds the fee to `meta.sender` with no zero-address guard: `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` [3](#0-2) . The identical unguarded pattern exists in `dispatchIncoming(GetResponse)` for `IApp.onGetResponse` fee payouts and in `dispatchTimeOut(GetRequestTimeout,...)` [5](#0-4) .

If `feeToken()` is a real-world stablecoin that explicitly disallows transfers to the zero address (this class of behavior is exactly what the original report demonstrates via USDC's `_transfer` zero-address checks), the `safeTransfer` call reverts. Since `dispatchTimeOut` is called without try/catch inside `HandlerV2`'s batch loop, that single revert propagates and reverts the whole `handlePostRequestTimeouts`/`handleGetRequestTimeouts` transaction — including all other legitimate, unrelated timeout entries bundled by the relayer in the same call. Because timeout processing is typically batched by relayers for gas efficiency, this can repeatedly block delivery of timeout refunds for many users until the poisoned commitment is filtered out of every future batch, a non-trivial off-chain workaround requirement that itself constitutes a denial of service on the honest relay/refund path.

### Impact Explanation
This matches the "route unable to deliver messages" impact category: a single unprivileged dispatch with `payer = address(0)` and non-zero fee poisons that request's timeout commitment such that any batch containing it permanently reverts, denying timeout-fee refunds/settlement to every other request relayers choose to bundle alongside it, until relayers learn to exclude the poisoned commitment. This is reachable by any address able to call `EvmHost.dispatch(DispatchPost)` directly (or via any `IDispatcher`-calling app that fails to sanitize `payer`), with no special privileges required.

### Likelihood Explanation
Likelihood is straightforward: any user can call `dispatch(DispatchPost{... payer: address(0), fee: someNonZeroFee ...})` directly against `EvmHost`, since `payer` is a free-form parameter with no validation. The only precondition is that the request must actually time out and its module callback must succeed (or the request must simply exist as a `GetResponse`/timeout with `meta.fee != 0`), and `feeToken()` must be a token that reverts on zero-address transfers (true for widely used tokens such as USDC).

### Recommendation
Validate `post.payer != address(0)` (and `get.payer != address(0)`) in `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)`, or guard every unconditional `feeToken().safeTransfer(recipient, fee)` call (in `dispatchIncoming`, `dispatchTimeOut` for both POST and GET) with a `recipient != address(0)` check, skipping (not reverting) the transfer when the recipient is the zero address so batch processing in `HandlerV2` cannot be denial-of-serviced by a single poisoned commitment.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchPost{ dest: X, body: ..., timeout: T, fee: 1e18, payer: address(0) })`, paying `post.fee` from their own balance via `feeToken().safeTransferFrom(_msgSender(), address(this), post.fee)` [4](#0-3) . This stores `FeeMetadata({sender: address(0), fee: 1e18})` for the resulting commitment.
2. Let the request time out (or never get delivered), so `request.timeout()` elapses.
3. A relayer submits `HandlerV2.handlePostRequestTimeouts` with a batch that includes the attacker's timed-out request alongside several legitimate ones.
4. For the attacker's entry, `host.dispatchTimeOut(...)` is invoked; if the destination module's `onPostRequestTimeout` succeeds, `EvmHost` attempts `feeToken().safeTransfer(address(0), 1e18)` [3](#0-2) .
5. If `feeToken()` reverts transfers to `address(0)` (e.g., a USDC-like token), the whole `handlePostRequestTimeouts` call reverts, and none of the batched requests' timeouts are processed — including the legitimate, unrelated ones.
