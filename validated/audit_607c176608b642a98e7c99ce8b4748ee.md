### Title
Webhook `shop-domain` header is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value (taken from the `X-Shopify-Shop-Domain` header) is never included in that signature. `ShopifyAPI::Webhooks::Registry.process` validates only the body/HMAC pair and then dispatches the handler using the unauthenticated `shop` header value, breaking the identity binding `HMAC-authenticated bytes == bytes acted on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside of what is HMAC-verified: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` (which only checks `to_signable_string`, i.e., the raw body, against the shared `api_secret_key`) and then constructs `WebhookMetadata` using the unverified `request.shop`: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm the signature covers only `verifiable_query.to_signable_string` (the raw body for webhooks) and compares it against `verifiable_query.hmac`: [4](#0-3) 

Because a single app uses one shared `api_secret_key` for all shops that install it, any body+HMAC pair that Shopify legitimately sends for **one** shop (e.g., the attacker's own shop, which they fully control as an app installer) is a cryptographically valid signature for that same raw body regardless of which `shop-domain` header accompanies it. The library performs no binding between the header-supplied `shop` and the signed payload, so an attacker who owns a legitimate installation can capture a genuine `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim tenant. `HmacValidator.validate` will accept it because the signature check only depends on the body and the shared secret, not on the header.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook processing: `WebhookMetadata.shop`, which host applications use to route/attribute webhook data to a specific merchant, is derived from data that is never authenticated. An attacker with a legitimate install of the app (any unprivileged internet user who installs a free/dev app instance) can inject arbitrary attacker-chosen webhook payloads (product/order/customer data, etc., since they control the shop that produces the original signed body) that the host app will process as if they belong to a victim shop of their choosing. Depending on how the host application persists/handles webhook data keyed by `shop`, this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to have any working installation of the target app to obtain a validly-signed `(raw_body, hmac)` pair (self-service, not privileged), and requires the app's webhook endpoint to be reachable directly (typical for any public webhook receiver, since webhook endpoints are plain HTTP(S) endpoints with no additional transport-level Shopify-only authentication enforced by this gem). No access to `api_secret_key`, access tokens, or victim credentials is needed.

### Recommendation
Include the shop domain (and other routing-relevant headers such as `topic`/`api_version`) in the HMAC-signed content the gem verifies, or otherwise cryptographically bind the `shop` value to the payload before exposing it via `WebhookMetadata`. At minimum, document that `Registry.process`/`WebhookMetadata.shop` is not an authenticated value and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (self-service, no special privileges).
2. Attacker triggers a webhook event (e.g., updates a product) causing Shopify to POST a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair, signed with the app's shared `api_secret_key`, to the app's webhook endpoint.
3. Attacker captures this `raw_body` and its valid `hmac` header value.
4. Attacker replays a forged HTTP POST directly to the app's public webhook endpoint with the same `raw_body`/`hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only presence, not authenticity, of `shop-domain` is checked): [5](#0-4) 
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers `raw_body`: [6](#0-5) 
7. The handler is invoked with `WebhookMetadata.new(..., shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"`, even though the payload was generated by the attacker's own shop, achieving cross-tenant data injection at the application layer.

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
