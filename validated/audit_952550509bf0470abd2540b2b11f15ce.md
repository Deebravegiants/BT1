## Title
Webhook HMAC covers only the raw body, not the `shop`/`topic` headers acted upon by the handler — enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `Utils::HmacValidator.validate` in `Webhooks::Registry.process` authenticates the *body bytes* only. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are taken straight from HTTP headers and then acted upon (routing to a handler, and passed to application code as the identity of the shop that triggered the event) — are never part of the signed data. This is the same class of bug as the reported `LibSilo.transferStalk()` issue: a value that the code treats as authenticated/bound is actually independent of the cryptographic check that is supposed to bind it.

### Finding Description
`lib/shopify_api/webhooks/request.rb`:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end

sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header [3](#0-2) . Because `to_signable_string` is only `@raw_body`, the signature never covers `shop`, `topic`, `webhook_id`, or `api_version`.

`Webhooks::Registry.process` trusts these unauthenticated header values to route the event and to construct the data handed to the merchant's own handler code:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding this breaks: `shop authenticated == shop the code acts on`. The HMAC only proves "Shopify (or anyone holding the shared app secret's signature over this exact body) produced this body"; it proves nothing about which shop the body/headers claim to be from.

### Impact Explanation
Because a single app's `api_secret_key` is shared across every shop that has the app installed, any merchant who installs the app can receive a legitimately-signed webhook delivery to their own shop (body + valid HMAC). They can then replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different, victim shop's domain. Signature validation still passes because only the body is checked, but `Registry.process` now hands the application handler a `WebhookMetadata` claiming the event belongs to the victim shop. This breaks tenant isolation (cross-tenant impact): a handler that updates per-shop state (order processing, GDPR `customers/redact`/`shop/redact` handling, inventory sync, etc.) keyed off `WebhookMetadata#shop` will act on the victim shop using attacker-controlled body content.

### Likelihood Explanation
Any user who can install the target app on a shop they control (a normal, unprivileged install — no special credentials or leaked secrets needed) can obtain a validly-signed webhook body/HMAC pair and replay it with forged headers to the app's public webhook endpoint. This requires no access to `api_secret_key`, no access token, and no privileged account — it only depends on functionality the gem exposes as-is.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically/structurally bind them to the verified payload (e.g., require that `shop`/`topic` be re-derived from fields inside the verified JSON body rather than from unauthenticated headers), consistent with treating "bytes verified" and "bytes acted on" as the same set.

### Proof of Concept
1. App installed on `attacker-shop.myshopify.com`; Shopify delivers a real webhook, e.g. `orders/create`, to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker captures `B` and its valid HMAC (trivial — it was delivered to their own server/shop).
3. Attacker POSTs the same `B` and the same HMAC header to the app's webhook endpoint again, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (only `B` is checked) — [5](#0-4) ; `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though the event never originated from that shop.
