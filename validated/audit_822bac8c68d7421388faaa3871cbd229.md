### Title
`updateConnection` lets an already-trusted origin change `connectedAssetName` to an asset never granted via `assetNames`, exposing new-asset addresses through `getConnectedAccounts` without re-consent - ([File: features/connected-origins/module/connections.js])

### Summary
`updateConnection` only writes `connectedAssetName` (and `icon`) via `#setAttributes`/`#setData`, without validating that the new `connectedAssetName` is already contained in the origin's existing `assetNames` grant list. Because `getConnectedAccounts` computes the exposed asset set as the union of `value.connectedAssetName` and `value.assetNames`, and `#setData` repopulates `connectedAccountsAtom` for any asset referenced anywhere (including a freshly-set `connectedAssetName`), calling `updateConnection` with a new `connectedAssetName` silently expands what a trusted origin can read.

### Finding Description
`updateConnection` in [1](#0-0)  takes `connectedAssetName` and writes it directly onto the origin's stored attributes with no check against the origin's `assetNames` array (the array that represents what assets the user actually consented to expose per `add`, see [2](#0-1) ).

`#setAttributes` → `#setData` then recomputes the derived asset list across **all** connections (`#getConnectedAssets`, [3](#0-2) ) and fetches/derives addresses for every asset referenced by any `connectedAssetName` or `assetNames`, populating `connectedAccountsAtom` with addresses for the newly set asset.

`getConnectedAccounts` then computes the exposed asset set as `[value.connectedAssetName, ...(value.assetNames ?? [])]` ( [4](#0-3) ) and returns `pick(addresses, assetNames)` for the active and enabled wallet accounts. Since `connectedAssetName` is unioned in regardless of whether it appears in `assetNames`, an origin that was only ever granted `assetNames: ['ethereum']` can call `updateConnection({ origin, connectedAssetName: 'solana' })` and immediately have `solana` addresses returned by `getConnectedAccounts`, even though `solana` was never part of the consented `assetNames` set.

The only gate in `getConnectedAccounts` is `isTrusted` (i.e., the origin object still exists and `trusted !== false`) — [5](#0-4)  — there is no re-validation that the currently active `connectedAssetName` is a subset of the previously approved `assetNames`.

### Impact Explanation
This allows disclosure of wallet addresses for an asset/chain the user never explicitly approved for a given origin, bypassing the intended per-asset consent model implemented by `assetNames`. This is an address-disclosure/authorization-scope-bypass bug: it does not enable signing or fund movement, but it does let an already-connected origin silently escalate which chain's addresses it can read without a new approval prompt, which is a real origin-trust/account-scoping violation (matches an "unauthorized address/account disclosure due to origin scope bypass" class of impact, one tier below key/signing compromise).

### Likelihood Explanation
Precondition: the origin must already be trusted for at least one asset (i.e., have gone through a legitimate connect flow once). Given that, the exploit requires only a single call to `updateConnection` with an unapproved `connectedAssetName`, and no other guard blocks it — highly feasible and fully deterministic/repeatable if `updateConnection` is reachable from a dapp-facing code path with attacker-controlled `connectedAssetName`. Note: this analysis could not fully confirm that `updateConnection` is reachable directly from untrusted dapp/origin input (as opposed to being invoked by privileged wallet UI code only) — the only concrete caller found was in unit tests via `features/connected-origins/module/__tests__/connections.test.js`, and no provider/background RPC handler wiring dapp `connectedAssetName` input into `updateConnection` could be located in the indexed code (index size limits may have excluded relevant provider/background files). If reachable from dapp input, the bug is real and trivially exploitable as described.

### Recommendation
In `updateConnection`, validate that `connectedAssetName` is a member of the origin's existing `assetNames` before allowing it to change; if not, reject the update or require it to go through `add`'s consent path (which merges into `assetNames`). Alternatively, in `getConnectedAccounts`, only union `connectedAssetName` into the exposed set if it is also present in `assetNames`, so an update-only asset can never be exposed without having also been consented via `assetNames`.

### Proof of Concept
Integration test (`features/connected-origins/module/__tests__/connections.test.js` style):
```js
test('updateConnection cannot expose an asset outside assetNames', async () => {
  await connectedOrigins.add({
    origin: 'exodus.com',
    name: 'Exodus',
    icon: 'exodus_icon',
    connectedAssetName: 'ethereum',
    assetNames: ['ethereum'],
    trusted: true,
  })

  await connectedOrigins.updateConnection({ origin: 'exodus.com', connectedAssetName: 'solana' })

  const accounts = await connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })
  for (const account of accounts) {
    expect(account.addresses).not.toHaveProperty('solana')
  }
})
```
Expected (buggy) result: the assertion fails because `solana` addresses are present in `account.addresses`, since `updateConnection` alone caused `solana` to be unioned into the exposed asset list.

  updateConnection = async ({ origin, icon, connectedAssetName }) => {
    const value = await this.#getOrigin({ origin })

    if (!value) return

    const attributes = {}

    if (icon) {
      attributes.icon = icon
    }

    if (connectedAssetName) {
      attributes.connectedAssetName = connectedAssetName
    }

    await this.#setAttributes({ origin, attributes })
  }
