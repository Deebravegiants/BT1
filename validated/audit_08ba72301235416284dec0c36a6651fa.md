### Title
Unauthenticated `CallDispatcher.dispatch()` allows any unprivileged caller to drain funds held by the shared dispatch singleton - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no caller restriction whatsoever — it is a bare `external` function with no `onlyHost`, `onlyGateway`, or `msg.sender` check of any kind. `IntentGatewayV2`/`IntentsBase` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` family all route arbitrary, order/message-supplied `Call[]` batches through one shared `CallDispatcher` instance (`_params.dispatcher` / `_dispatcher`), and this instance can also directly receive native value via its unrestricted `receive()`. Any unauthorized address can call `dispatch()` on this shared, fund-holding contract at any time to move out whatever ETH/ERC20 balance happens to sit on it, independent of whether that caller ever placed or filled an order.

### Finding Description
`CallDispatcher.sol` implements: [1](#0-0) 

`dispatch(bytes memory encoded)` decodes an attacker-suppliable `Call[]` and executes each `to.call{value: call.value}(call.data)` with no check on `msg.sender`. Only the target's `extcodesize` is validated; the *caller* of `dispatch` is never authenticated.

This same singleton is the fund-handling backbone of two major app surfaces reachable by unprivileged users:

- `IntentGatewayV2.placeOrder`/`fillOrder` transfer user/solver-supplied `predispatch`/`output` assets into `_params.dispatcher`, invoke `ICallDispatcher(dispatcher).dispatch(...)` with order-creator- or solver-controlled calldata, then attempt to sweep the dispatcher's balance for only the tokens explicitly listed in `order.inputs`/`order.output.assets`: [2](#0-1) [3](#0-2) 

- `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` forward any non-empty message `data` straight to the same `CallDispatcher`: [4](#0-3) 

Because the sweep logic only ever accounts for tokens present in the known `inputs`/`outputs` arrays, and because the calldata executed by `dispatch()` is itself controlled by whoever created the order or triggered the message (a swap that yields a bonus/airdropped token, rounding dust, a token not enumerated in the sweep loop, or ETH deposited directly via the unrestricted `receive()`), residual balances can be left standing on the `CallDispatcher` between transactions. Since `dispatch()` performs no `msg.sender` check, *any* address — not the gateway, not the token contract, not Hyperbridge — can call it directly with a `Call[]` that transfers that residual balance to itself.

### Impact Explanation
This is a concrete theft primitive on a shared, protocol-wide utility contract: any value (native or ERC20) that ends up on the `CallDispatcher` for any reason outside the exact narrow sweep set the calling app anticipated is permanently exposed to extraction by an unrelated, unprivileged account. Given the `CallDispatcher` is explicitly documented to "hold and forward native tokens" and is shared across `IntentGatewayV2`, `HyperFungibleToken`, and `WrappedHyperFungibleToken` deployments, this is a High-severity fund-safety gap consistent with the "contract vulnerability leading to unauthorized fund extraction" bug class described in the Dough Finance report.

### Likelihood Explanation
Likelihood is elevated by the fact that the dispatcher's `receive()` is unconditionally payable (anyone can push ETH onto it), and dust/leftover-balance scenarios are explicitly anticipated by the protocol's own dust-sweeping logic and events (`DustCollected`) — meaning non-zero residual balances on the dispatcher are a designed-for, recurring occurrence, not an edge case. Any observer monitoring the dispatcher's balance can race to call `dispatch()` before the owning app's own sweep transaction executes, or exploit any token/flow not covered by the sweep enumeration.

### Recommendation
Restrict `CallDispatcher.dispatch()` to authorized callers only (e.g., an `onlyAuthorized` allowlist of the specific `IntentGatewayV2`/`HyperFungibleToken` instances configured to use it, or deploy a dedicated dispatcher per app instance rather than sharing one singleton). Additionally, ensure sweep logic in `IntentsBase._execute`/`placeOrder`/`fillOrder` fully drains the dispatcher of any token balance (not just the tokens explicitly listed in `inputs`/`outputs`) before returning control, and consider disabling or gating the `receive()` fallback.

### Proof of Concept
1. A user places an order via `IntentGatewayV2.placeOrder` with `predispatch.call` that performs a swap producing a token not present in `order.inputs` (e.g. a reward/bonus token from the DEX), or a fill leaves ETH dust on the dispatcher that isn't part of `order.output.assets`.
2. Because `IntentsBase._execute`/the predispatch sweep in `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol` / `evm/tron/contracts/apps/IntentGatewayV2.sol`, lines ~236-311) only sweeps tokens enumerated in `order.inputs`/`order.output.assets`, this unaccounted token/ETH balance remains on `_params.dispatcher`.
3. An unrelated attacker, who never interacted with the gateway, calls `CallDispatcher.dispatch(abi.encode(Call[]))` directly (`evm/src/utils/CallDispatcher.sol`, lines 44-61) with `to = <that token>`, `data = transfer(attacker, balance)` (or, for ETH, `to = attacker, value = dispatcher.balance`). Since `dispatch()` performs no caller check, the call succeeds and the attacker walks away with the dispatcher's stranded balance.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
