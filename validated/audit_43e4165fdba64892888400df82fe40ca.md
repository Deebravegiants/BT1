Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` only ever verifies the raw body bytes against the HMAC header, never the shop/topic headers [3](#0-2) , and `Registry.process` builds `WebhookMetadata` directly from `request.topic`/`request.shop` after only checking that HMAC [4](#0-3) .

### Title
Webhook shop/topic identity is unauthenticated — HMAC covers only the body, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers to identify which tenant and event a webhook belongs to, but the HMAC signature verification only ever covers the raw request body — never these identity headers. Since the app's `api_secret_key` is shared across every merchant installation (it is not shop-specific), an attacker who legitimately installs the app on their own store can capture a genuine, validly-signed webhook delivery and replay the exact same `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain`/`topic`/`webhook-id` headers with values belonging to a different (victim) shop or a different topic. The signature still validates because it never bound those fields.

### Finding Description
The identity binding that should hold is:
`hmac_valid(request) == true` should imply `request.shop == the shop that actually generated this event` AND `request.topic == the actual topic Shopify fired`.

Instead, `to_signable_string` returns only `@raw_body` [1](#0-0) , so the equality that is actually checked is only `hmac == HMAC(secret, raw_body)`, with `shop`, `topic`, and `webhook_id` sourced from headers that participate in no cryptographic check at all [5](#0-4) .

`HmacValidator.validate` reinforces this: it calls `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` — for a `Webhooks::Request`, that signable string is the body alone [6](#0-5) .

`Registry.process` then raises only if the HMAC fails, and otherwise constructs `WebhookMetadata` directly from the unauthenticated `request.topic` and `request.shop` values before invoking the registered handler [4](#0-3) .

Because the app's HMAC secret (`api_secret_key`) is the same for all shops that install the app — it is per-app, not per-shop, per `Context.api_secret_key` usage throughout `HmacValidator` — any shop that installs the app can receive a legitimately-signed webhook body/HMAC pair for its own events. That `(body, hmac)` pair remains valid regardless of which `shop-domain`/`topic`/`webhook-id` headers are attached, since those headers are never part of the signed data. An attacker can therefore forge the identity of the event without ever learning the secret.

### Impact Explanation
This breaks the tenant identity boundary that `Registry.process` implicitly relies on: the handler is invoked believing `data.shop` and `data.topic` are authentic, but they are attacker-controlled strings paired with attacker-supplied (but originally legitimate) body bytes. Depending on how the host application's webhook handler uses `data.shop`/`data.topic` (e.g., to look up/update per-shop records, to route GDPR `shop/redact` or `customers/data_request` compliance actions, or to trigger app-uninstalled cleanup), this allows cross-tenant data confusion or spoofed compliance/lifecycle events attributed to a shop that never sent them — a cross-tenant access class issue.

### Likelihood Explanation
Any unprivileged internet user can install a public/free Shopify app on their own development store, causing the app to legitimately receive a real webhook with a valid `(body, hmac)` pair for that install. No access token, `client_secret`, or leaked credential is required — the attacker only needs to be able to trigger and capture one real webhook delivery for their own shop, then POST it directly to the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the data that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify `shop` against the session/shop the app expects for that webhook subscription, and treat `webhook_id` as a nonce to reject replays). At minimum, `to_signable_string` should not return only the body when the consumer (`Registry.process`) also trusts header-derived `shop`/`topic` values without independent verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged action any developer can perform).
2. Shopify sends a real webhook to the app's endpoint, e.g. topic `customers/data_request` with body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` from their own delivery (e.g., via a request-logging proxy on their own endpoint before/while it's processed).
4. Attacker POSTs to the app's webhook endpoint again, body `B`, HMAC header `H` (both valid, unmodified), but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: shop/redact`.
5. `HmacValidator.validate` only checks `B` against `H` via `to_signable_string`/`hmac`, which passes since neither value changed [7](#0-6) .
6. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [8](#0-7) , causing the app to process a forged event attributed to a shop and/or topic that never actually produced it.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
